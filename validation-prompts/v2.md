# Critical Verification Gates - All Must Pass

Your task: decide whether a reported finding is `Valid`, and if it is valid, determine whether the correct severity is `High`, `Medium`, or `Low / QA`.

You must answer three separate questions in order:

1. Does the bug actually exist in the current code?
2. Is the reported root cause independently in-scope and correctly framed?
3. Does the actual runtime impact justify `High` / `Medium`, or is it only `Low / QA`?

Do not collapse those questions together. A real bug is not automatically a High/Medium finding.

---

## Evidence Hierarchy

Use this order of authority:

1. Current code and reachable execution path
2. Runtime safeguards and actual state transitions on the affected path
3. Scope, support assumptions, and current deployment / integration model
4. NatSpec, comments, and docs
5. PoC quality and exploit evidence

If code and docs conflict, code wins on bug existence. Docs still matter for scope, intent, and whether something is by design.

---

## Core Validation Principles

- Judge bug existence, root-cause quality, and severity separately.
- A missing standard protection is not automatically `High` / `Medium`.
- A named safeguard only counts if it materially constrains the exact path at issue.
- Fail-open, stale, incomplete, bypassable, or wrong-path safeguards do not save a finding from `Valid`.
- A downstream symptom, alternate patch site, or weaker restatement of a deeper issue is not automatically an independent `High` / `Medium`.
- Timing-sensitive or market-sensitive does not mean low likelihood if the conditions are realistic and permissionless.
- Unsupported token behavior, unsupported integrations, admin misconfiguration, and user-selected bad parameters are not protocol `High` / `Medium` unless the protocol explicitly supports them or forces users into the unsafe path.
- If a real bug exists but independently material `High` / `Medium` impact is not proven, classify it as `Low / QA` or `Needs Review`, not `High` / `Medium`.
- Use `Needs Review` sparingly. It is for real ambiguity, not for avoiding a severity call.

---

## Pre-Gate Sanity Check - Verify The Bug Exists

Before checking the gates, verify the reported path in the actual code.

### Step 1: Trace The Code Path

- Locate the exact function, state variable, and dependency path mentioned in the finding.
- Trace the execution path step by step.
- Confirm the claimed state transition, bypass, or failure can occur in the current code.

Invalid if:

- the function or path does not exist
- the report relies on removed code or impossible control flow
- the described exploit path contradicts the code

### Step 2: Verify The Requirement Or Invariant Is Real

- Check whether the claimed property is required by the code, docs, comments, or surrounding logic.
- If documentation is thin, still ask whether the runtime path clearly relies on the invariant.
- Check whether similar functions or adjacent logic enforce the same property.

Invalid if:

- the invariant is invented and not supported by code or intended behavior
- the report assumes a requirement that the system plainly does not try to satisfy

### Step 3: Identify The Actual Root Cause

- Ask whether the report points to the real broken check, broken state transition, or broken safeguard.
- Ask whether the report is only describing a downstream consequence of a deeper issue.

Downgrade to `Low / QA` or `Invalid` if:

- the report is only a derivative symptom of a deeper issue
- the report names the wrong root cause and does not establish independent material impact
- the report suggests a fix at a surface call site, but the real vulnerability lives elsewhere

### Step 4: Reproduce The Preconditions

- Can the issue be triggered today, with current code, under realistic preconditions?
- Are the preconditions reachable, economically rational, and internally consistent?

Invalid if:

- the required state is unreachable
- the attack requires contradictory assumptions
- the exploit requires impossible preconditions

If the sanity check fails, mark `Invalid`.

## Gate 1: Scope Check

Invalid if:

- the root cause lives entirely in out-of-scope code
- the report only depends on unsupported external behavior
- the issue is view-only, cosmetic, event-only, or purely informational

Valid if:

- in-scope code creates the bug
- in-scope code misuses an out-of-scope dependency in a way that creates the bug on the current path

---

## Gate 2: User Error Check

Critical question: does the exploit require a user to make a bad choice the protocol does not force?

Invalid if the issue requires:

- a user choosing a malicious recipient, target, or route
- a user supplying obviously unsafe parameters such as bad slippage, bad deadlines, or bad amounts
- a user signing arbitrary malicious data the protocol does not force
- a user ignoring a clear protocol-provided safety control

Valid if:

- the user follows the intended flow and the protocol still fails to protect them
- the attacker can exploit the issue without relying on user mistakes
- the protocol forces users into the unsafe state

---

## Gate 3: Root-Cause Independence Check

Critical question: is this finding independently material, or is it a weaker restatement of another deeper bug?

Downgrade or reject if:

- the report only rephrases a deeper root cause
- the issue disappears if the real underlying bug is fixed elsewhere
- the report identifies a weaker surface symptom without proving its own independent material impact

Keep as a separate finding only if:

- the report identifies a distinct broken path, or
- it proves independent material impact even if another deeper bug also exists

---

## Gate 4: Impact Classification

Use the actual exposed runtime path, not the ideal design.

### High

- substantial theft, seizure, or permanent loss of assets
- permissionless or realistically reachable core authorization takeover
- major protocol liveness break or major economic extraction from a core workflow

### Medium

- material but bounded loss
- extractable accounting drift or mispricing
- DoS of critical actions under realistic conditions
- meaningful privilege escalation or state corruption without full takeover

### Low / QA

- minor execution degradation
- bounded price worsening while effective limits still materially cap the risk
- nuisance griefing with cheap retry or straightforward operational recovery
- unsupported-token compatibility issues
- derivative symptoms of deeper issues
- real bugs with only limited or operationally minor impact

Important:

- Missing a standard protection is not automatically `Medium`.
- A real bug can still be only `Low / QA`.
- Conversely, a bug is not downgraded just because it is not an instant full drain.

---

## Gate 5: Likelihood And Economic Plausibility

### Common

- no unusual preconditions
- attacker can exploit at will
- no meaningful capital, timing, or coordination burden

### Occasional

- requires realistic timing, sequencing, front-running, helper contracts, or common market conditions
- still permissionless and practical

### Rare

- requires multiple unlikely conditions
- depends on irrational attacker self-harm
- depends on unsupported assets or unusual environments
- depends on privileged mistakes or unlikely trusted-party failures

Important:

- Do not classify an issue as rare just because the attacker must watch the mempool, front-run, wait for ordinary market conditions, or deploy a helper contract.
- Do classify an issue as low-likelihood if the attacker must burn value, rely on unsupported behavior, or wait for multiple unlikely failures to align.

---

## Gate 6: Governance / Centralization / Deployment Check

Critical question: can a responsible admin or deployer prevent this entirely through correct setup and expected operational hygiene?

Reject or downgrade if the issue requires:

- incorrect deployment target or environment
- missing initialization or missing role grants before enabling the feature
- malicious or unsupported integration choice
- trusted component failure or misbehavior
- bad parameter selection that responsible governance controls directly

Keep as valid if:

- the bug remains after correct setup
- the code fails to validate or bind an expected admin action at runtime
- the exploit is available to non-privileged actors despite responsible operations

Do not dismiss a finding just because governance exists. Dismiss it only if correct governance behavior fully prevents the issue.

---

## Gate 7: Supported Asset / Integration Assumptions

Reject or downgrade if the issue depends on:

- fee-on-transfer, rebasing, broken-return-value, or other non-standard token behavior that is not explicitly supported
- unsupported bridge, oracle, router, or integration semantics
- special-case asset behavior that the protocol does not claim to support

Keep as valid if:

- the protocol explicitly supports the behavior, or
- the issue still exists with supported assets and integrations

Non-standard compatibility issues are usually not protocol `High` / `Medium` by default.

---

## Gate 8: Speculation And Current-Code Check

Invalid if the issue depends on:

- future upgrades or future integrations
- hypothetical admin mistakes not required by the current path
- trusted components failing in ways the current code does not require
- states that do not exist today

Valid if:

- the exploit works now on current code
- the required inputs and runtime conditions are available today

---

## Gate 9: Documentation-Only And By-Design Check

Invalid if:

- the report is only a documentation problem
- the behavior is clearly intentional and does not violate an actual runtime safety property
- the component is intentionally public, destructive, or unrestricted by design, and no harmed invariant is shown

Valid if:

- docs or comments describe intended protection, but the code still fails open
- the code violates the system's own runtime assumptions even if the docs are sparse

Documentation does not rescue broken code. But documentation can show that behavior is deliberate and therefore not a bug.

---

## Gate 10: Existing Safeguards Check

Critical question: does the code already have an effective safeguard on the exact path that prevents or materially bounds the claimed impact?

Treat the safeguard as effective only if it:

- applies on the affected path
- uses materially sufficient parameters
- does not fail open
- cannot be trivially bypassed

Reject or downgrade if an effective safeguard already prevents or materially bounds the impact.

Keep as valid if the safeguard is:

- missing
- incomplete
- stale
- fail-open
- bypassable
- on a different path
- too weak to materially bound the loss or liveness break

Do not give credit to a safeguard merely because it exists somewhere in the codebase or appears in a comment.

---

## Gate 11: Exploitability And Evidence Check

Require:

- a concrete trigger path
- a realistic actor model
- a state change consistent with the claimed impact
- enough exploit evidence for the class of claim being made

Reject or downgrade if:

- the exploit path is hand-wavy or internally inconsistent
- the report asserts a major impact without enough evidence
- the judging standard requires a PoC for that class of exploit and the evidence is missing or insufficient

---

## Gate 12: Configuration / Environment Check

If the finding depends on constants, environment, or feature flags:

- check whether the values are production values or test values
- check whether the affected path is actually enabled
- check whether suspicious values are clearly placeholders or disabled settings

Reject or downgrade if the issue only exists under clearly non-production or intentionally disabled settings.

---

## Final Tie-Breaker And Output Rules

- Never auto-upgrade to `Valid` just because a protection is "usually expected."
- Never auto-reject just because docs mention the behavior.
- If bug existence is uncertain, mark `Invalid`.
- If the bug exists but independent `High` / `Medium` impact is not proven, mark `Low / QA` or `Needs Review`, not `High` / `Medium`.
- If the bug exists and the supposed safeguard is non-binding, stale, incomplete, or fail-open on the actual path, do not downgrade solely because exploitation needs realistic timing, sequencing, or market conditions.
- State which gates passed and failed.
- Use `Needs Review` only when the bug may be real but the independent `High` / `Medium` case remains genuinely unresolved after the gate analysis.
