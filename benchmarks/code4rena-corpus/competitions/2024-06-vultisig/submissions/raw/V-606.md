# Vulnerability details

## Impact
In the `buy()` function where, it checks if the investor already has a position. If they do, it assigns the existing NFT token ID to `tokenId`. However, if the investor doesn't have a position, it increments `_nextId` and assigns the new token ID to `tokenId`.

This could lead to an issue where both cases do not adequately initialize the `tokenId` variable. It should be ensured that `tokenId` is correctly initialized regardless of whether the investor already has a position.

## Proof of Concept
[ILOPool.sol#L143-L148](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L143-L148)
```solidity
if (balanceOf(recipient) == 0) {
    _mint(recipient, (tokenId = _nextId++));
    _positionVests[tokenId].schedule = _vestingConfigs[0].schedule;
} else {
    tokenId = tokenOfOwnerByIndex(recipient, 0);
}
```
**Logs:**
```solidity
Buy(recipient, tokenId, raiseAmount, liquidityDelta)
```
**Impact**
If the `tokenId` variable is not properly initialized in both cases, it could lead to the following issues:
   * Incorrect token ownership and vesting schedules.
   * Duplicate token IDs.
   * Errors in the `Buy` event emission.
