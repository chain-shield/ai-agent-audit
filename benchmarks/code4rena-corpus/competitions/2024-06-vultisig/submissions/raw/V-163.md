# Vulnerability details

## Impact
The current implementation of the `receive` function does not update the `_contributed` mapping to reflect the amount of ETH each address has contributed. This omission leads to several potential problems:

```javascript
/// @notice Contributed ETH amounts
    mapping(address => uint256) private _contributed;
```

The contract cannot track the total amount of ETH contributed by each address. This makes it impossible to enforce any contribution limits, such as a maximum cap.

Any other parts of the contract relying on the `_contributed` mapping to manage or reference contribution amounts will not function correctly.

## Proof of Concept
Consider the following scenario with the current implementation:

Address A sends 2 ETH to the contract.
The contract does not update _contributed for Address A.
Address A sends another 2 ETH to the contract.
The contract again does not update _contributed for Address A.
If there was supposed to be a 3 ETH cap, Address A has now sent a total of 4 ETH without any checks or tracking.

Example
Here’s the current receive function without the _contributed update:

```javascript
receive() external payable {
    if (_isSelfWhitelistDisabled) {
        revert SelfWhitelistDisabled();
    }
    if (_isBlacklisted[_msgSender()]) {
        revert Blacklisted();
    }
    _addWhitelistedAddress(_msgSender());
    payable(_msgSender()).transfer(msg.value);
}
```

## Recommended Mitigation Steps
To address this issue, update the `_contributed` mapping within the receive function to keep track of the contributions made by each address. This can be done by adding a line that increments the `_contributed` mapping by the msg.value.

```javascript
uint256 newContribution = _contributed[_msgSender()] + msg.value;
    if (newContribution > _maxAddressCap) {
        revert ExceedsMaxAddressCap();
    }
    _contributed[_msgSender()] = newContribution;

```
