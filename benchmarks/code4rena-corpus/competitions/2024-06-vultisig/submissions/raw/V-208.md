# Vulnerability details

## Impact

In the current implementation of `UniswapV3Oracle`, `peek()` function uses hard-coded slippage protection equal to 5%. The problem is that the slippage can be much and much more (or less - that will also make some problems) and this may block the `checkWhitelist()` function call.

## Proof of Concept

Let's take a look at the `peek()` function:

https://github.com/code-423n4/2024-06-vultisig/blob/main/hardhat-vultisig/contracts/oracles/uniswap/UniswapV3Oracle.sol#L45
```
 return (quotedWETHAmount * baseAmount * 95) / 1e20; // 100 / 1e18
```

It uses hard-coded 5% slippage which can create some potential problems. The function is used when calculating `estimatedETHAmount`:

https://github.com/code-423n4/2024-06-vultisig/blob/main/hardhat-vultisig/contracts/Whitelist.sol#L221
```
  uint256 estimatedETHAmount = IOracle(_oracle).peek(amount);
```
But in practice the slippage can be more or less and the users will not be able to use whitelist functionality as their tx will revert. Or, in other case, this slippage may be too much for some users as they are not willing to agree for 5% slippage tolerance.

## Tools Used

Manual review.

## Recommended Mitigation Steps

The slippage parameter should not be fixed and be user-supplied.
