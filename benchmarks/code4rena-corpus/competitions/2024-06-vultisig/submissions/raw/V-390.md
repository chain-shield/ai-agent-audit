# Vulnerability details

## Vulnerability Detail
The vulnerability lies inside `_initUniV3PoolIfNecessary`, this function is called whenever `initProject` is called.

`initProject` ==> `_initUniV3PoolIfNecessary`

<details>

```solidity
function _initUniV3PoolIfNecessary(PoolAddress.PoolKey memory poolKey, uint160 sqrtPriceX96) internal returns (address pool) {
        pool = IUniswapV3Factory(UNIV3_FACTORY).getPool(poolKey.token0, poolKey.token1, poolKey.fee);
        if (pool == address(0)) {
            pool = IUniswapV3Factory(UNIV3_FACTORY).createPool(poolKey.token0, poolKey.token1, poolKey.fee); 
            IUniswapV3Pool(pool).initialize(sqrtPriceX96);
        } else {
            (uint160 sqrtPriceX96Existing, , , , , , ) = IUniswapV3Pool(pool).slot0(); 
            if (sqrtPriceX96Existing == 0) {
                IUniswapV3Pool(pool).initialize(sqrtPriceX96);
            } else {
                require(sqrtPriceX96Existing == sqrtPriceX96, "UV3P"); 
            }
        }
    }
```
    
</details>


If `initProject` is called after the uniswap pool is deployed AND initialized then the following require statement must hold true

```solidity
require(sqrtPriceX96Existing == sqrtPriceX96, "UV3P"); 
```

This opens up an attack vector to front run `initProject` by deploying a new pool or manipulate an existing pool so that `sqrtPriceX96Existing != params.initialPoolPriceX96`. This will cause the require statement to fail therefore `initProject` will revert.

The steps to the attack are clearly outlined in the POC comments

## Impact
Attacker can DOS the important `initProject` function by deploying/manipulating the slot0 price of the associated uniswap pool
