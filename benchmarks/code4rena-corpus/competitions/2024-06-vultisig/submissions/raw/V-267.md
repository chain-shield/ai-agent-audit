# Vulnerability details

## Impact

Users can avoid paying fees for the raise token.

## Proof of Concept

In order to understand this vulnereability, we should first understand how buying/claiming works.

If a user wants to buy into a pool, he will call `ILOPool::buy()` which is:
- Checking if the user is whitelisted
- Checking if the presale is still ongoing
- Checking that the user does not exceed the hardcap
- Checking that maxSale amount is not exceeded
- Checking that the maxCapPerUser is not exceeded
- Calculating the liquidity shares that a position will get and transfers the tokens from the user

```solidity
  function buy(
        uint256 raiseAmount,
        address recipient
    ) external override returns (uint256 tokenId, uint128 liquidityDelta) {
        // @review -> Check if user is whitelisted
        require(_isWhitelisted(recipient), "UA");
        // @review -> Check if the presale is still ongoing
        require(
            block.timestamp > saleInfo.start && block.timestamp < saleInfo.end,
            "ST"
        );


        // @review -> Check if the user does not exceed hardcap with the new amount
        require(saleInfo.hardCap - totalRaised >= raiseAmount, "HC");

        totalRaised += raiseAmount;

        //@review -> Check if we are not exceeding maxSaleAmount
        require(totalSold() <= saleInfo.maxSaleAmount, "SA");


        // @review - Mint or get the tokenId of the user
        if (balanceOf(recipient) == 0) {
            _mint(recipient, (tokenId = _nextId++));
            _positionVests[tokenId].schedule = _vestingConfigs[0].schedule;
        } else {
            tokenId = tokenOfOwnerByIndex(recipient, 0);
        }

        Position storage _position = _positions[tokenId];
        //@review - Check if the position exceeds maxCapPerUser
        require(
            raiseAmount <= saleInfo.maxCapPerUser - _position.raiseAmount,
            "UC"
        );
        _position.raiseAmount += raiseAmount;

        // @review - Calculate liquidity shares
        if (RAISE_TOKEN == _cachedPoolKey.token0) {
            liquidityDelta = LiquidityAmounts.getLiquidityForAmount0(
                SQRT_RATIO_X96,
                SQRT_RATIO_UPPER_X96,
                raiseAmount
            );
        } else {
            liquidityDelta = LiquidityAmounts.getLiquidityForAmount1(
                SQRT_RATIO_LOWER_X96,
                SQRT_RATIO_X96,
                raiseAmount
            );
        }

        require(liquidityDelta > 0, "ZA");


        // @review - Calculate the shares the users will get according to the vestingConfig
        liquidityDelta = uint128(
            FullMath.mulDiv(liquidityDelta, _vestingConfigs[0].shares, BPS)
        );

        //@review ->  increase investor's liquidity
        _position.liquidity += liquidityDelta;

        
        _positionVests[tokenId].totalLiquidity = _position.liquidity;

        TransferHelper.safeTransferFrom(
            RAISE_TOKEN,
            msg.sender,
            address(this),
            raiseAmount
        );

        emit Buy(recipient, tokenId, raiseAmount, liquidityDelta);
    }

```

After that the user waits for the team to launch the pool. This is done by calling `ILOPool::launch()`, the function deposits liquidity into the pool and distributes the amount according to the `vestingConfigs`. In the end it marks `_launchSucceeded` as true, which now allows for user to start claiming.

After the user buys he waits until the project is launched. When the team launches the project we deposit the tokens as liquidity into the project's uniswapv3 pool and we start the vesting period.

The `ILOPool::claim` function calculates the claimable liquidity linearly overtime. The more time that passes on the more liquidity shares will be unlocked, and if the time passed exceeds the vesting schedule's end time all of the liquidity shares will be unlocked.

As we can see from above after burning the position's liqudity, we are applying fees by calling `_deductFees()`. The function takes two amounts and a feeBPS which according to `IntegrationTestBase.sol`, `platformFee=10` and `performanceFee=1000`.

```solidity
    //@review -> From every liquidity collected there will be paid a 0.1% fee.
    uint16 constant PLATFORM_FEE = 10; // 0.1%
    //@review -> From every fees accumulated there will be paid a 10% fee.
    uint16 constant PERFORMANCE_FEE = 1000; // 10%
```

```solidity
function _deductFees(
        uint256 amount0,
        uint256 amount1,
        uint16 feeBPS
    ) internal pure returns (uint256 amount0Left, uint256 amount1Left) {
        //@review - BPS=10_000
        amount0Left = amount0 - FullMath.mulDiv(amount0, feeBPS, BPS);
        amount1Left = amount1 - FullMath.mulDiv(amount1, feeBPS, BPS);
    }
```

However, the problem lies within `_deductFees`. As we can see when calculating `amount0Left` and `amount1Left`, we are subtracting the current amount with the `(amount * feeBPS) / BPS`, which is rounded down in a benefit of the user.

For the PoCs, I will use the feeBPS values from `IntegrationTestBase.sol`, since they are the only source of truth we have for the fees.

Now, knowing how the user buys/claims, and how the protocol applies fees to the amounts of burned liquidity we can take many paths to exploit this and not pay the fees.

For the simplicity of the examples, assume that token0 is the raise token (even if the token is token1 the outcome will still be the same)

Most of the exploits can be done with any token with small decimals. For the examples, we will be using GUSD which has 2 decimals, and since, we need our position to be of maximum 999 or 9.99 GUSD per position, this is the best token to do that. This can be done with any token with small decimals, but it will not be as effective. WBTC(8 decimals) or 0.65$ per position.

If the team drops the `PLATFORM_FEE` even more that amounts can be greater.

Here are ways to make sure that amount0 will always be < 1000.

1. If the team is malicious they can set the maxCapPerUser < 1000, to make sure no one will ever pay fees:
  - Malicious team creates a pool with a `raiseToken=GUSD`
  - Then they set `maxCapPerUser` to 999 or 9.99 GUSD.
  - Users can create new wallets and deposit as much as they want.
  - Upon claiming, users will have a maximum of 999 amount0 tokens per position.

2. Creating multiple accounts (this is achievable, without the need to set the maxCap):
  - Users create multiple accounts and deposit 999 tokens into each position.
  - They can create 30 positions of 999 ($9.99) for a total value of $300 and avoid fees.

3. Claiming in smaller amounts:
  - Users can claim in small increments to keep the amount0 < 1000.
  - This approach requires many transactions, but can be feasible on low-cost EVM chains.


Now that we know how to keep amount0 < 1000, since as mentioned above `_deductFees` is rounding down in benefit of the user the calculated amounts will be:

For amount0, calling `_deductFees()` will update it as `999 - (999 * 10 / 10_000) = 999 - 0 = 999`, and the user avoids paying the platformFee.

If we were rounding it up, it would be `999 - (999 * 10 / 10_000) = 999 - 1 = 998`, and the user will have payed the platformFee of `1`.

With the amount being so small there is even a possibility that the accumulated fees will be < 10. For example, if `fees0=99` -> `_deductFees()` will update fees0 as `9 -((9 * 1000) / 10_000) = 9 - 0 = 9` and the user avoids the performanceFee.

If we were rounding it up, it would be  `9 -((9 * 1000) / 10_000) = 9 - 1 = 8`, and the user would have payed the performanceFee of `1`.

## Recommended Mitigation Steps

My recommended mitigation is rather simple, just round up when calculating `amount0Left` and `amount1Left`.

```solidity
    function _deductFees(
        uint256 amount0,
        uint256 amount1,
        uint16 feeBPS
    ) internal pure returns (uint256 amount0Left, uint256 amount1Left) {
-       amount0Left = amount0 - FullMath.mulDiv(amount0, feeBPS, BPS);
-       amount1Left = amount1 - FullMath.mulDiv(amount1, feeBPS, BPS);
+       amount0Left = amount0 - FullMath.mulDivRoundingUp(amount0, feeBPS, BPS);
+       amount1Left = amount1 - FullMath.mulDivRoundingUp(amount1, feeBPS, BPS);
    }
```
