# Vulnerability details

## Impact
When the ILOPool launches on an active uniswap pool (pool with liquidity), it will allow an attacker to frontrun the liquidity minting and benefit from the price change or making the launch fail completely.

## Proof of Concept

Given the [documentation](https://docs.uniswap.org/contracts/v3/guides/providing-liquidity/mint-a-position#calling-mint) of uniswap about minting new positions. The contract that calls "mint" on a pool must verify that the amounts that the contract wants to send matches the amount that the uniswap pool asks (the contract should also define some slippage to avoid reverts for incorrect amounts).

When [calculating](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOPool.sol#L285-L293) the amount of token0 and token1 to send, the [amount0Min or amount1Min](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOPool.sol#L280-L281) can be equal to 0. This contract verifies that the amounts sent [matches](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/base/LiquidityManagement.sol#L56) the minimum amount asked. 

```solidity
    function addLiquidity(AddLiquidityParams memory params)
        internal
        returns (
            uint256 amount0,
            uint256 amount1
        )
    {
        (amount0, amount1) = params.pool.mint(
            address(this),
            TICK_LOWER,
            TICK_UPPER,
            params.liquidity,
            ""
        );

        require(amount0 >= params.amount0Min && amount1 >= params.amount1Min, 'Price slippage check');
    }
```

We check for the minimum sent of both amounts. The problem is that we never [initialize the minimum sold token amount](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOPool.sol#L278-L293) to send. 

```solidity
    function launch() external override OnlyManager() {
       ...
            uint256 amount0;
            uint256 amount1;
            uint256 amount0Min;
            uint256 amount1Min;
            address token0Addr = _cachedPoolKey.token0;

            if (token0Addr == RAISE_TOKEN) { 
                // HERE  amount1Min is NOT initialized
                amount0 = totalRaised;
                amount0Min = totalRaised;
                (amount1, liquidity) = _saleAmountNeeded(totalRaised);
            } else {
                // HERE  amount0Min is NOT initialized
                (amount0, liquidity) = _saleAmountNeeded(totalRaised);
                amount1 = totalRaised;
                amount1Min = totalRaised;
            }

            // WE ADD LIQUIDITY BUT DONT VALIDATE amount0Min or amount1Min since they are NOT INITIALIZED (equal to 0)
            (amount0, amount1) = addLiquidity(AddLiquidityParams({
                pool: IUniswapV3Pool(uniV3PoolAddress),
                liquidity: liquidity,
                amount0Desired: amount0,
                amount1Desired: amount1,
                amount0Min: amount0Min,
                amount1Min: amount1Min
            }));

            ...
    }
```

Thus, a frontrunner can benefit from this amount not being checked by buying or selling. Example:

- ILOPool launches, it wants to send X amount of raise token and Y amount of sold token.

- ILOPool sends the transaction, [checking](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/base/LiquidityManagement.sol#L56) that at least X amount of raise token is sent to the pool. But it [doesn't check(https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOPool.sol#L280-L293) for the Y amount of sold token, so this can be a very small amount, close to 0. This is because the sold token minimum amount is not initialized.

- A frontrunner sees the tx on the mempool, the frontrunner can manipulate how much of the sold token is deposited from the smart contract. This can be done by buying or selling tokens on the pool and moving its price. This can create two scenarios:
   - The launch fails because the price increases too much and the ILOPool doesn't have enough of the raise token to deposit
   - The frontrunner bough a lot of sold tokens. The ILOPool deposits a very small amount of sold tokens. Then the attacker can sell for a profit, since the ILOPool deposited a lot of the raise token and very little of the sold token (price went up).

## Tools Used

Manual review

## Recommended Mitigation Steps

Initialize the minimum amount to send of both tokens and add some slippage calculation in case of price differences during the deposit. This will avoid the contract to revert during the deposit.
