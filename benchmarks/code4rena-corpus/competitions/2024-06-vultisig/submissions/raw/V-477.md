# Vulnerability details

## Summary

**Context:**
Function [approveAndCall()](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/Vultisig.sol#L16) is used to approve vultisig tokens to a spender and make an external call to function receiveApproval() on the spender contract, which uses transferFrom() to spend the allowance provided.

**Root cause:**
In the function approveAndCall() though, the internal function _approve() [here](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/Vultisig.sol#L18) and the external call [here](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/Vultisig.sol#L21) are called with msg.sender instead of using _msgSender() from the Context.sol library inherited by the ERC20 token contract.

**Impact:**
This is being reported as a Medium-severity risk issue since all user facing public functions in the ERC20 token contract i.e. [transfer()](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/442886ed5ff8a0b9ab477b191f5238541ee6d772/contracts/token/ERC20/ERC20.sol#L104), [transferFrom()](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/442886ed5ff8a0b9ab477b191f5238541ee6d772/contracts/token/ERC20/ERC20.sol#L149) and even [approve()](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/442886ed5ff8a0b9ab477b191f5238541ee6d772/contracts/token/ERC20/ERC20.sol#L127) itself uses _msgSender() to retrieve data about the sender of the transaction. When dealing with meta-transactions, the account sending and paying for execution may not be the actual sender but might be some sort of GSN ([1](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/v3.4.0/contracts/GSN/GSNRecipient.sol#L90), [2](https://opengsn.org/)).

This can break the composability with external applications that use approveAndCall() to approve + transfer at the same time to save gas for the trusted spender contract. 

## Proof of Concept

In the Vultisig contract below, we can see that Line 21 and Line 25 directly use msg.sender instead of _msgSender(). As stated above, this can prevent applications from composing and using this specific functionality of the token.
```solidity
File: Vultisig.sol
18:     function approveAndCall(address spender, uint256 amount, bytes calldata extraData) external returns (bool) {
19:         // Approve the spender to spend the tokens
20:         
21:         _approve(msg.sender, spender, amount);
22: 
23:         // Call the receiveApproval function on the spender contract
24:         
25:         IApproveAndCallReceiver(spender).receiveApproval(msg.sender, amount, address(this), extraData);
26: 
27:         return true;
28:     }
```

Manual Review

## Recommended Mitigation Steps
Replace both msg.sender instances with _msgSender().
