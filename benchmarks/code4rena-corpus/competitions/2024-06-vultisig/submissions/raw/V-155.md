# Vulnerability details

## Impact
Due to the accuracy of the division, there will always be a little bit left in the pool when calculating the unlocked liquidity. Each user's vest will have a little bit left, and the accumulation is not a decimal.

## Proof of Concept
When the user receives the unlocked liquidity, it will be calculated how much liquidity the user has unlocked. During the calculation process, due to accuracy issues, each vest will [have a little leftover](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L418-L421), and cumulatively, each pool will leave a lot of tokens.
```solidity
            // if vest already end, all the shares are unlocked
            // otherwise we calculate shares of unlocked times and get the unlocked share number
            // all vest after current unlocking vest is ignored
            if (vest.end < block.timestamp) {
                liquidityUnlocked += uint128(FullMath.mulDiv(
                    vest.shares, 
                    totalLiquidity, 
                    BPS
                ));
            } else {
                liquidityUnlocked += uint128(FullMath.mulDiv(
                    vest.shares * totalLiquidity, 
                    block.timestamp - vest.start, 
                    (vest.end - vest.start) * BPS
                ));
            }
```

## Tools Used
manual

## Recommended Mitigation Steps
It is recommended to add up the unlocked shares and finally divide them by BPS. Only when the total number of shares is equal to BPS can all be unlocked.
