# Vulnerability details

## Impact
In the `receive()`, It attempts to send the received ETH back to the sender, but it does so after adding the sender to the allowlist.
```solidity
receive() external payable {
    if (_isSelfWhitelistDisabled) {
        revert SelfWhitelistDisabled();
    }
    if (_isBlacklisted[_msgSender()]) {
        revert Blacklisted();
    }
    _addWhitelistedAddress(_msgSender());
    payable(_msgSender()).transfer(msg.value);
}
```
It first adds the sender to the whitelist by calling `_addWhitelistedAddress(_msgSender())`, and then it attempts to send the received ETH back to the sender using `payable(_msgSender()).transfer(msg.value)`.

However, if the sender is a contract that doesn't expect to receive ETH (i.e., it doesn't have a `receive()` or `fallback()` function), the `transfer` call will fail, and the transaction will be reverted. As a result, the sender will be added to the whitelist, but the received ETH will be stuck in the contract.

## Recommended Mitigation Steps
Should send the ETH back to the sender before adding them to the whitelist. By sending the ETH back first and then adding the sender to the whitelist, you ensure that the whitelist addition only occurs if the ETH transfer is successful.
```solidity
receive() external payable {
    if (_isSelfWhitelistDisabled) {
        revert SelfWhitelistDisabled();
    }
    if (_isBlacklisted[_msgSender()]) {
        revert Blacklisted();
    }
    payable(_msgSender()).transfer(msg.value);
    _addWhitelistedAddress(_msgSender());
}
```
