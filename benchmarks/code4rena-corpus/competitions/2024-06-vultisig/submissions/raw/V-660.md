# Vulnerability details

## Impact

The `claim` function in the smart contract lacks direct slippage control mechanisms when burning liquidity and collecting tokens, potentially leading to adverse financial consequences for users. In volatile market conditions, the absence of explicit price protection during the token collection phase may result in users receiving significantly fewer tokens than expected. This vulnerability can undermine user confidence in the platform's fairness and security, potentially deterring participation and investment, and negatively affecting the liquidity and stability of the pool.

## Proof of Concept

https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L196

```solidity
IUniswapV3Pool pool = IUniswapV3Pool(_cachedUniV3PoolAddress);
Position storage position = _positions[tokenId];
{
    IILOManager.Project memory _project = IILOManager(MANAGER).project(address(pool));

    uint128 positionLiquidity = position.liquidity;
    require(positionLiquidity >= liquidity2Claim);

    // get amount of token0 and token1 that pool will return for us
    (amount0, amount1) = pool.burn(TICK_LOWER, TICK_UPPER, liquidity2Claim);

    // get amount of token0 and token1 after deduct platform fee
    (amount0, amount1) = _deductFees(amount0, amount1, _project.platformFee);
}
```

This code snippet demonstrates that while the contract ensures the specified liquidity can be burned (`pool.burn(TICK_LOWER, TICK_UPPER, liquidity2Claim)`), it does not ensure that the amounts of `amount0` and `amount1` tokens received are within a safe range relative to current market prices. The amounts are accepted as-is from the pool's response, which can vary significantly, especially in volatile markets.

## Recommended Mitigation Steps

Allow users to specify a maximum allowable slippage percentage when initiating the claim transaction.
