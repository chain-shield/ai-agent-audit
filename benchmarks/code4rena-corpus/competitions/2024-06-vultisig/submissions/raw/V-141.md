# Vulnerability details

## Impact
`_refundProject` function transfers the entire balance of `SALE_TOKEN` held by the contract to the `projectAdmin` address. This can result in the project admin receiving more tokens than intended if the contract holds more `SALE_TOKEN` than the amount sold during the sale.

## Proof of Concept
To begin, lets consider how `ILOPool` can hold more `SALE_TOKEN` than the amount that was supposed to be sold.


Firstly, lets navigate to the `launch` function. When the `launch` function is called, the contract calculates the amount of `SALE_TOKEN` needed for the liquidity pool and adds it to the Uniswap V3 pool. Any leftover `SALE_TOKEN` that was not needed for the liquidity pool remains in the contract until it is refunded to the project admin as seen in this code snippet:

   ```solidity
   function launch() external override OnlyManager() {
       // ... other code ...

       // actually deploy liquidity to uniswap pool
       (amount0, amount1) = addLiquidity(AddLiquidityParams({
           pool: IUniswapV3Pool(uniV3PoolAddress),
           liquidity: liquidity,
           amount0Desired: amount0,
           amount1Desired: amount1,
           amount0Min: amount0Min,
           amount1Min: amount1Min
       }));

       // ... other code ...

       // transfer back leftover sale token to project admin
       _refundProject(_project.admin);

       _launchSucceeded = true;
   }
   ```


Also, If the ILO (Initial Liquidity Offering) does not succeed (i.e., the soft cap is not met), the `claimProjectRefund` function can be called by the manager to refund the remaining `SALE_TOKEN` to the project admin. Until this function is called, the leftover `SALE_TOKEN` remains in the contract:

   ```solidity
   function claimProjectRefund(address projectAdmin) external override refundable() OnlyManager() returns(uint256 refundAmount) {
       return _refundProject(projectAdmin);
   }
   ```

Additionally, the contract also handles vesting schedules for the `SALE_TOKEN`. If there are any tokens that are part of the vesting schedule but not yet vested, they will remain in the contract until they are vested and claimed.

   ```solidity
   function _unlockedLiquidity(uint256 tokenId) internal view override returns (uint128 liquidityUnlocked) {
       PositionVest storage _positionVest = _positionVests[tokenId];
       LinearVest[] storage vestingSchedule = _positionVest.schedule;
       uint128 totalLiquidity = _positionVest.totalLiquidity;

       for (uint256 index = 0; index < vestingSchedule.length; index++) {
           LinearVest storage vest = vestingSchedule[index];

           // if vest is not started, skip this vest and all following vest
           if (block.timestamp < vest.start) {
               break;
           }

           // if vest already end, all the shares are unlocked
           // otherwise we calculate shares of unlocked times and get the unlocked share number
           // all vest after current unlocking vest is ignored
           if (vest.end < block.timestamp) {
               liquidityUnlocked += uint128(FullMath.mulDiv(
                   vest.shares, 
                   totalLiquidity, 
                   BPS
               ));
           } else {
               liquidityUnlocked += uint128(FullMath.mulDiv(
                   vest.shares * totalLiquidity, 
                   block.timestamp - vest.start, 
                   (vest.end - vest.start) * BPS
               ));
           }
       }
   }
   ```

Now to the main issue, the `_refundProject` function transfers the entire balance of `SALE_TOKEN` held by `ILOPool` to the `projectAdmin` address without considering the amount of tokens actually sold during the sale. This can result in the project admin receiving more tokens than intended if the contract holds more `SALE_TOKEN` than the amount sold(which is possible from the stances cited above).

```solidity
function _refundProject(address projectAdmin) internal returns (uint256 refundAmount) {
    refundAmount = IERC20(SALE_TOKEN).balanceOf(address(this));
    if (refundAmount > 0) {
        TransferHelper.safeTransfer(SALE_TOKEN, projectAdmin, refundAmount);
        emit ProjectRefund(projectAdmin, refundAmount);
    }
}
```

## Recommended Mitigation Steps

`_refundProject` should be tweaked to calculate the refund amount based on the difference between the total `SALE_TOKEN` balance and the amount of tokens actually sold.

```diff
function _refundProject(address projectAdmin) internal returns (uint256 refundAmount) {
-    refundAmount = IERC20(SALE_TOKEN).balanceOf(address(this));
+    uint256 totalBalance = IERC20(SALE_TOKEN).balanceOf(address(this));
+    uint256 totalSoldAmount = totalSold();
+    refundAmount = totalBalance > totalSoldAmount ? totalBalance - totalSoldAmount : 0;
    if (refundAmount > 0) {
        TransferHelper.safeTransfer(SALE_TOKEN, projectAdmin, refundAmount);
        emit ProjectRefund(projectAdmin, refundAmount);
    }
}
```
