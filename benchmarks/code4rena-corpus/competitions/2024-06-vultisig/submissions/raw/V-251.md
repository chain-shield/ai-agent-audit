# Vulnerability details

## Proof of Concept
The `PeripheryPayments` contract assumes a 1:1 conversion rate between Ether (ETH) and Wrapped Ether (WETH) during payment processing. This assumption is encapsulated in the following code snippet:
```solidity
function pay(
    address token,
    address payer,
    address recipient,
    uint256 value
) internal {
    if (token == WETH9 && address(this).balance >= value) {
        // pay with WETH9
        IWETH9(WETH9).deposit{value: value}(); // wrap only what is needed to pay
        IWETH9(WETH9).transfer(recipient, value);
    } else if (payer == address(this)) {
        // pay with tokens already in the contract (for the exact input multihop case)
        TransferHelper.safeTransfer(token, recipient, value);
    } else {
        // pull payment
        TransferHelper.safeTransferFrom(token, payer, recipient, value);
    }
}
```
In the code above, the pay function handles the payment logic. When the token is WETH9 and the contract's balance is sufficient, it deposits Ether into WETH9 and then transfers the WETH to the recipient. The assumption here is that 1 ETH will always convert to exactly 1 WETH.

This assumption may fail due to:
1. Precision and conversion errors between ETH (with 18 decimals) and WETH (typically following the ERC20 standard with 18 decimals).
2. External factors such as network congestion or unusual blockchain conditions affecting the conversion process.

## Impact
If the 1:1 conversion assumption fails, it can result in discrepancies in payment amounts, potentially causing the contract to either overpay or underpay the recipient. 
## Tools Used
Manual
## Recommended Mitigation Steps
Add explicit checks and balances around the conversion logic and Only proceeding with the transfer if the conversion check passes, preventing potential payment discrepancies.
