# Vulnerability details

## Impact
https://github.com/code-423n4/2024-06-vultisig?tab=readme-ov-file#main-invariants states:
- `Vultisig token will be initially listed on UniswapV3(VULT/ETH pool). Whitelist contract will handle the initial whitelist launch`.
- `In whitelist contract, there's checkWhitelist function which checks if` `from address is uniswap v3 pool which holds liquidity, then it means, this transfer is the buy action. We will apply the following WL logic.`

Moreover, the `checkWhitelist` function's comment states that `We only add limitations for buy actions via uniswap v3 pool`.

Thus, it is an invariant that the whitelist logic should only apply to buy actions through the VULT/ETH pool. However, such whitelist logic also applies to other non-buy actions through the VULT/ETH pool, which breaks such invariant.

https://github.com/code-423n4/2024-06-vultisig/blob/58ebda57ccf6a74bdef2b88eb18a62ec4ad46112/hardhat-vultisig/contracts/Whitelist.sol#L204-L228
```solidity
    function checkWhitelist(address from, address to, uint256 amount) external onlyVultisig {
        if (from == _pool && to != owner()) {
            // We only add limitations for buy actions via uniswap v3 pool
            // Still need to ignore WL check if it's owner related actions
            if (_locked) {
                revert Locked();
            }

            if (_isBlacklisted[to]) {
                revert Blacklisted();
            }

            if (_allowedWhitelistIndex == 0 || _whitelistIndex[to] > _allowedWhitelistIndex) {
                revert NotWhitelisted();
            }

            // // Calculate rough ETH amount for VULT amount
            uint256 estimatedETHAmount = IOracle(_oracle).peek(amount);
            if (_contributed[to] + estimatedETHAmount > _maxAddressCap) {
                revert MaxAddressCapOverflow();
            }

            _contributed[to] += estimatedETHAmount;
        }
    }
```

For example, a flash loan action through the VULT/ETH pool can be triggered by calling the following `flash` function that also calls the `_beforeTokenTransfer` function below, which further calls the `checkWhitelist` function. For such action, `from == _pool && to != owner()` would be true so the whitelist logic applies to this flash loan action even though such action is not a buy action. Because the user pays back the flash loan in a single transaction, none of VULT tokens are bought, and such whitelist logic should not apply to such non-buy action but that is not the case. In this case, `_contributed[to]` is increased for the user when it should not happen; since the increased `_contributed[to]` reduces the available amount that can be contributed before `_maxAddressCap` is reached, the possible VULT token amount that such user can truly buy would always be lower than the VULT token amount allowed by `_maxAddressCap` for such user to buy. As a result, such user can only buy less VULT tokens than what she or he is entitled to.

## Proof of Concept
The following steps can occur for the described scenario.
1. Alice calls the VULT/ETH pool's `flash` function to take a flash loan of VULT tokens that are worth 1 ETH.
2. Alice pays back the flash loan in the single transaction, where the flash loan is borrowed, so all of her borrowed VULT tokens are returned.
3. Although she did not buy any VULT tokens, `_contributed[to]` for Alice has increased to 1 ETH.
4. The possible VULT tokens for Alice to later buy can at most be worth 2 ETH instead of 3 ETH that should be allowed by `_maxAddressCap`. Thus, Alice can only buy less VULT tokens than what she is entitled to.

## Tools Used
Manual Review

## Recommended Mitigation Steps
One mitigation is to reverse the effect of the whitelist logic on non-buy actions, such as a flash loan action, by updating the `checkWhitelist` function to decrement `_contributed[from]` by `estimatedETHAmount` if `to == _pool && from != owner()` is true.
