# Vulnerability details

## Impact
Initialize Function cannot be called in Pool Contract
## Proof of Concept
```solidity
constructor() ERC721('', '') {
>>>        _disableInitialize();
    }

...

 function initialize(InitPoolParams calldata params) external override whenNotInitialized() {
       ...
    }
```
The code above shows how the constructor and initialization is handled in the pool contract, the problem is that the constructor at deployments would disable the ablility to initialize even though the initialize(...) function requires the whenNotInitialized() modifier, this implementation contradicts each other, a look at the Initializable contract below shows that once _disableInitialize() has been called _initialized   is set to true which means subsequent call of whenNotInitialized() will fail since it requires _initialized to be false. it can also be seen in the contract that there is no function to enable initialize after disabling it 
```solidity
// SPDX-License-Identifier: BUSL-1.1 

pragma solidity =0.7.6;

abstract contract Initializable {
    bool private _initialized;
    function _disableInitialize() internal {
>>>        _initialized = true;
    }
    modifier whenNotInitialized() {
>>>        require(!_initialized);
        _;
        _initialized = true;
    }
    modifier afterInitialize() {
        require(_initialized);
        _;
    }
}
```

## Recommended Mitigation Steps
Maybe Protocol intends to use afterInitialize() modifier for initialize call instead, whichever the case maybe Protocol should add a function to the Initializable.sol contract to ensure Initialize can be enabled back when needed and it should be only accessible by trusted admin
```solidity
+++ function _enableInitialize() internal onlyManager() {
+++        _initialized = false;
+++    }
```
