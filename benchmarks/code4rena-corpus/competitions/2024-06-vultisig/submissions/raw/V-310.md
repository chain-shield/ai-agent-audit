# Vulnerability details


## Proof of Concept

Take a look at https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/Whitelist.sol#L204-L229

```solidity
    function checkWhitelist(address from, address to, uint256 amount) external onlyVultisig {
        if (from == _pool && to != owner()) {
            // We only add limitations for buy actions via uniswap v3 pool
            // Still need to ignore WL check if it's owner related actions
            if (_locked) {
                revert Locked();
            }
            if (_isBlacklisted[to]) {
                revert Blacklisted();
            }

            if (_allowedWhitelistIndex == 0 || _whitelistIndex[to] > _allowedWhitelistIndex) {
                revert NotWhitelisted();
            }

            // // Calculate rough ETH amount for VULT amount
    //@audit
            uint256 estimatedETHAmount = IOracle(_oracle).peek(amount);
            if (_contributed[to] + estimatedETHAmount > _maxAddressCap) {
                revert MaxAddressCapOverflow();
            }

            _contributed[to] += estimatedETHAmount;
        }
    }

```

This function is called via the `_beforeTokenTransfer` hook as clearly documented [here](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/Whitelist.sol#L14), problem however is in the implementation of the `IOracle(_oracle).peek()`, see https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/oracles/uniswap/UniswapV3Oracle.sol#L39-L46

```solidity
    function peek(uint256 baseAmount) external view returns (uint256) {
        uint32 longestPeriod = OracleLibrary.getOldestObservationSecondsAgo(pool);
        uint32 period = PERIOD < longestPeriod ? PERIOD : longestPeriod;
        int24 tick = OracleLibrary.consult(pool, period);
        uint256 quotedWETHAmount = OracleLibrary.getQuoteAtTick(tick, BASE_AMOUNT, baseToken, WETH);
        // Apply 5% slippage
        return (quotedWETHAmount * baseAmount * 95) / 1e20; // 100 / 1e18
    }
```

Evidently, there is a hardcoded `5%` slippage applied to the function's execution, this would then mean that, whether there is slippage or not (assume ~1% slippage), the execution still assumes there to be 5%, which in the hinted case would mean that a user would miss out on 4% in the case the slippage was only 1%.

Using the current values, ETH is worth $4000
Protocol has a max deposit value of 3 ETH, _that could be higher in the future_.
User contributes 3 ETH.
1% slippage occurred.
User's `_contributed[to] += estimatedETHAmount;` gets unfairly set to 2,85 ETH, whereas it should be 2,97 ETH (considering the 1% slippage), i.e (0.12 ETH or `~$500` worth of contribution has been skimmed off of the user).

_Would be key to note that this also means that if two users, A & B make a contribution where user A's contribution had a 1% slippage and user B's had a 4% slippage they both receive the same `contributed[to]` value which is unfair to user A._ 

## Impact


Broken accounting on the real amount of contributions users provide, which could unfairly skim off 4% of users contribution or even more depending on the amount of real slippage that occurred during the contribution.


## Recommended Mitigation Steps
Integrate the real amount of contribution users do and don't hardcode the slippage.
