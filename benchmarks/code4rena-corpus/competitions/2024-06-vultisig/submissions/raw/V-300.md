# Vulnerability details

## Impact
The protocol deploys ILOPool(s) using the cloneDeterministic method from OpenZeppelin's Clones library, which uses the CREATE2 opcode. The deployment process is as follows:

```js
    bytes32 salt = keccak256(abi.encodePacked(
        ChainId.get(),
        params.uniV3Pool,
        _initializedILOPools[params.uniV3Pool].length
    ));
    iloPoolAddress = Clones.cloneDeterministic(ILO_POOL_IMPLEMENTATION, salt);
```
Out of these three values used to compute the salt, `params.uniV3Pool` is known to any user monitoring the mempool as soon as the transaction is broadcasted. 

Furthermore, since the protocol only intends to deploy on Ethereum mainnet, the `chainId` is always fixed to `1`.

The `_initializedILOPools[params.uniV3Pool].length` is only updated after a successful `ILOManager::initPool` call. Since for the first ILOPool deployment for a particular `params.uniV3Pool`, the length is `0`, making the salt predictable.

For the master, `ILO_POOL_IMPLEMENTATION` is used, which is a public variable. 

This allows a malicious actor to deploy a contract with the same master and salt before the protocol does, making every call to `ILOManager::initPool` revert as there is already a contract at the address that create2 tries to deploys to.

This can be done repeatedly resulting in a DoS for `ILOManager::initPool`.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Change the salt generation mechanism to include a random nonce.
