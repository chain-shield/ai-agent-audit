# Vulnerability details

## Impact
The current implementation of the receive function uses the transfer method to return ETH to the sender. This approach forwards only 2300 gas to the recipient, which may not be sufficient for non-trivial operations in a receive or fallback function. This limitation can lead to several issues:

Inability to Receive ETH: If the sender is a contract that requires more than 2300 gas to execute its receive function, the ETH transfer will fail.
Permanent Loss of Funds: The failure of the transfer function will revert the entire transaction, preventing the sender from being whitelisted and potentially causing the sent ETH to be locked or lost if not handled properly.

## Proof of Concept
Example

Contract A is a multisig wallet or any smart contract with a receive function that consumes more than 2300 gas.
Contract A sends 1 ETH to the receive function of the target contract.
The target contract attempts to whitelist A and then return the 1 ETH using payable(msg.sender).transfer(msg.value).
Since A's receive function requires more than 2300 gas, the transfer fails, causing the entire transaction to revert.
As a result, A is not whitelisted, and the 1 ETH is not returned.

Here is the current implementation of the receive function:

```javascript
receive() external payable {
    if (_isSelfWhitelistDisabled) {
        revert SelfWhitelistDisabled();
    }
    if (_isBlacklisted[_msgSender()]) {
        revert Blacklisted();
    }
    _addWhitelistedAddress(_msgSender());
    payable(_msgSender()).transfer(msg.value); // Potential vulnerability
}
```

## Recommended Mitigation Steps
To mitigate this issue, replace the `transfer` method with `call`. The call method forwards all available gas, allowing the recipient contract to execute more complex logic in its receive function. Ensure to check the success of the call and handle failures appropriately.
