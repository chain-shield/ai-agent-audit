# Vulnerability details

An ILOPool has a maxCapPerUser set in the SaleInfo struct by the project admin, to limit the amount of raise amount deposited by a single user. This is done to prevent a single user from buying up major portions of the total liquidity of the ILOPool ie. SaleInfo.hardCap.

When the whitelist is open to all, it is understandable that maxCapPerUser can be bypassed : any user can hold many addresses and use all of their controlled addresses to repeatedly mint liquidity positions, upto the maxCap on all of them.

However, even when there is a whitelist, the maxCapPerUser is totally ineffective. Lets look at the buy function used to invest and deposit liquidity.

```
    function buy(uint256 raiseAmount, address recipient)
        external override 
        returns (
            uint256 tokenId,
            uint128 liquidityDelta
        )
    {
        require(_isWhitelisted(recipient), "UA");

///... some code

        // if investor already have a position, just increase raise amount and liquidity
        // otherwise, mint new nft for investor and assign vesting schedules
        if (balanceOf(recipient) == 0) {
            _mint(recipient, (tokenId = _nextId++));
            _positionVests[tokenId].schedule = _vestingConfigs[0].schedule;
        } else {
            tokenId = tokenOfOwnerByIndex(recipient, 0);
        }

        Position storage _position = _positions[tokenId];
        require(raiseAmount <= saleInfo.maxCapPerUser - _position.raiseAmount, "UC");
        _position.raiseAmount += raiseAmount;

///... more code
}
```

If the investor (whitelisted recipient address) already has a position NFT token minted, then more liquidity bought is added on top of the position info, and this is then checked to not cross maxCapPerUser. This is how it should always work.

But there is a catch, in order to determine if the recipient indeed has a previously minted NFT, the logic checks if NFT balance of their address is zero. Now ILOPool inherits from openzeppelin's ERC721 so the NFT owner can freely transfer their NFT token as there is no code to stop them from doing so in ILOPool. 

An attacker can do this :
1. Mint one NFT with their whitelisted recipient address, upto maxcap of raise tokens liquidity
2. Transfer out the NFT token to some other address they own
3. Call ILOPool.buy() again, now balanceOf recipient address will be zero and will mint a new tokenID where the same recipient can again buy upto maxcap of raise tokens liquidity
4. Repeat the process many times until totalRaised reaches the hardcap, now attacker holds most of the liquidity


## Impact

maxCapPerUser limit has been bypassed leading to the possibility of a single whale controlling most of the liquidity for the ILOPool and thus for the corresponding tick range in the to-be-deployed uniswap pool after launch.

This bars other investors from participation, and exposes the uniswap pool to dangers of a handful of LPs controlling possibly the entire liquidity of the launched uniswap pool, if they manage to attack all ILOPools of a project in the same way. The SALE_TOKEN can now potentially (depends on the trading price when whale withdraws liquidity) be owned by a handful of whales who can manipulate the pools as well as the project governance decisions using these tokens.

## Recommended Mitigation Steps
Add a _beforeTokenTransfer() override function which only allows liquidity NFT position to be transferred when launchSucceeded == true. An additional check will need to be added to this hook to skip the launchSucceeded check when from = address(0) to allow minting.
