# Vulnerability details

### Description
The team [announced per discord](https://discord.com/channels/810916927919620096/1250420964773203988/1253297246854709338) that their ILO Contracts will be launched on several L2's.

Whenever a user wants to `claimRefund` he has to wait for `block.timestamp > refundDeadline`:
```javascript

    modifier refundable() {
        if (!_refundTriggered) {
            // if ilo pool is lauch sucessfully, we can not refund anymore
            require(!_launchSucceeded, "PL");
            IILOManager.Project memory _project = IILOManager(MANAGER).project(_cachedUniV3PoolAddress);
->            require(block.timestamp >= _project.refundDeadline, "RFT");

            _refundTriggered = true;
        }
        _;
    }
```

The `refundDeadline` is set to 7 days after the `params.launchtime`:
```javascript
   int64 refundDeadline = params.launchTime + DEFAULT_DEADLINE_OFFSET;

```
This means that the ILOPool manager has 7 days to launch the pool without anyone being able to refund. once the 7 days have passed, a user can call `claimRefund`. Once a user performs this action the Admin will be unable to perform `launch` since the `refundTriggered` will be true:

```javascript
 function launch() external override OnlyManager() {
        require(!_launchSucceeded, "PL");
        // when refund triggered, we can not launch pool anymore
->        require(!_refundTriggered, "IRF");
    
```

The issue, however, is that when an L2 is paused, the `launch` function cannot be called, yet the `DEFAULT_DEADLINE_OFFSET` continues to count down. If the L2 is unpaused and the 7 days have passed, a user can front-run the admin by calling `claimRefund`, which prevents the `ILOPool` from being launched.

Example:
- Bob wants to `launch` his `ILOPool` with the current `block.timestamp = params.launchTime + 6 days + 23 hours`
- As of now no one is able to perform a refund since the `block.timestamp != refundDeadline`
-  L2 pauses
- time goes by, the L2 unpauses at `block.timestamp = params.launchTime + 7 days`
- User observes this and frontruns Bob by calling `claimRefund`
- Bob is unable to `launch` his pool

### Tools used
Manual Review

### Recommendation
Simply remove the `claimRefund` function, whenever a refund has to occur the `Admin` just calls `claimProjectRefund`. Alternatively, come up with some sort of logic to mitigate this situation.
