# Vulnerability details

## Vulnerability Details

During buy, the code first checks if specified recipient has a token or not. It mints new token to recipient if recipient donot already possess one. However, if recipient already possess a token, it just increment the position and liquidity associated with the recipient's already owned token. See below:
```
        if (balanceOf(recipient) == 0) {
            _mint(recipient, (tokenId = _nextId++));
            _positionVests[tokenId].schedule = _vestingConfigs[0].schedule;
        } else {
            tokenId = tokenOfOwnerByIndex(recipient, 0);
        }
```



Also, during launch too, the code mints a token to each of the recipients of a vesting configurations except the vesting at the 0 index. 

           ` _mint(projectConfig.recipient, (tokenId = _nextId++));`


However, in the launch, the code doesnot check whether vesting recipient already has a tokenId or a position, it just mints the recipient right away a new token.

Now, the Uniswap NFT manager standard recommends that for every minted token, the totalSupply() ought to be updated as well. See the docs and respective code at:

 `https://uniswapv3book.com/milestone_6/nft-manager.html`

```
tokenId = nextTokenId++;
_mint(params.recipient, tokenId);
totalSupply++;

```

2. Now, the protocol handles the update of totalSupply through tokenOwners.length, ie, the number of token holders is equal to totalSupply. It uses the totalSupply() function of the ERC721 nft contract. 


3. Now, before launch, a project.recipient can be specified as the whitelisted recipient to receive a tokenId through the buy function. This means that a  project.recipient can hold 2 tokens at a time within the pool, and yet still the accounting for totalSupply will be counted as one, as same recipient holds the 2 tokens.


## Impact
For 3 different vesting configurations, there are 3 different vesting recipients. Now, assuming each holds additional token , that makes 3 more tokens than the totalSupply the protocol accounts for. 

Now, as the protocol grows and inculcates the totalSupply in its critical calculations and computations, the result is that those calculations will be flawed.

## Recommended Mitigation Steps

In launch, before minting out the tokens to the vesting recipients, check to ensure that they donot already possess a token, just as it's done in buy function. If they already possess a token, just increment their position and liquidity as done in buy function.
