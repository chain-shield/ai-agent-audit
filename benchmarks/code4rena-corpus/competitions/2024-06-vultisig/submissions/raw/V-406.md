# Vulnerability details

## Impact

A single user can use multiple addresses to secure all available slots in the whitelist while `_isSelfWhitelistDisabled` is permitted. This would allow the user to evade `_maxAddressCap`, even with a minimal amount of tokens, since the checks in `checkWhitelist` are weak. This enables a user to repeatedly buy and sell tokens with a small amount until reaching the checkWhitelist.

## Proof of Concept

The receive function could be used to accept all of the attacker's addresses into the whitelist by only paying for the gas.

```
receive() external payable {
        if (_isSelfWhitelistDisabled) {
            revert SelfWhitelistDisabled();
        }
        if (_isBlacklisted[_msgSender()]) {
            revert Blacklisted();
        }
        _addWhitelistedAddress(_msgSender());
        payable(_msgSender()).transfer(msg.value);
    }
```

After that, tokens could be bought and sold repeatedly from the pool (since checkWhitelist is called from `_beforeTokenTransfer`), until reaching _maxAddressCap with each address in the whitelist.

## Recommended Mitigation Steps

When generating the whitelist, if you want to avoid Sybil attacks, it is advisable to increase the requirements for users to be part of the whitelist.
