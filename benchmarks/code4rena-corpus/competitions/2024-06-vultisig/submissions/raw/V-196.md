# Vulnerability details

The `TickMath.sol` and `FullMath.sol` libraries were taken from Uniswap. However Uniswap implements them with solidity version `< 0.8.0`. This solidity version introduces overflow and underflow protection. Which means operations will revert if they lead to overflow/underflow. 

The issue is that the version upper cap has been removed in this protocol's implementation but the arithmetic operations are not be wrapped in an unchecked block.

## Impact
`TickMath.sol:getSqrtRatioAtTick()` is used to get the upper/lower sqrtRatioX96 in `ILOManager.sol`:
```solidity
        uint160 sqrtRatioLowerX96 = TickMath.getSqrtRatioAtTick(params.tickLower);
        uint160 sqrtRatioUpperX96 = TickMath.getSqrtRatioAtTick(params.tickUpper);
```
`FullMath.sol: mulDiv()` is used multiple times in `ILOPool.sol`.

## Proof of Concept
`getSqrtRatioAtTick()` will not behave as intended since it relies implicitly on overflows.

In `mulDiv()` when a phantom overflow (a multiplication and division where an intermediate value overflows 256 bits) occurs the execution will revert and the correct result won't be returned.

This issue has also been addressed by Spearbit as a High/Medium severity:
[Issue 1](https://solodit.xyz/issues/use-unchecked-intickmathsol-andfullmathsol-spearbit-overlay-pdf)
[Issue 2](https://solodit.xyz/issues/tickmath-might-revert-in-solidity-version-08-spearbit-timeless-pdf)
[Issue 3](https://solodit.xyz/issues/fullmath-requires-overflow-behavior-spearbit-morpho-pdf)

## Recommended Mitigation Steps
Use the modified version of the original `TickMath.sol` and `FullMath.sol` for version `^0.8.0` that can be found [here](https://github.com/Uniswap/v3-core/tree/0.8/contracts/libraries). These implementations wrap the arithmetic operations in an `unchecked` block to handle the overflow.
