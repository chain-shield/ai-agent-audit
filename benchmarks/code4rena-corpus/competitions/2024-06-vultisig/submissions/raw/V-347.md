# Vulnerability details

## Impact
- The Total Liquidity Locked for Vest will be lower than expected as Position vested total Liquidity Updated does not consider liquidity that has been claimed before re-updating total liquidity value
- Based on the usage of Position Vested Total Liquidity at [L458](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOPool.sol#L458) & [L195](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOPool.sol#L195) of the contract, Liquidity that has been been previously claimed is wrongly calculated as zero allowing overinflated Claimable Liquidity value breaking Protocol functionality

The code above from the ILOPool contract shows how liquidity claim is made, it can be noted that position.liquidity is reduced by the amount of liquidity that is to be claimed, the significance of this implementation would be understood better by taking a look at the implementation in the code below which shows how claimed token is calculated by subtracting position.liquidity from positionVests.totalLiquidity which shows why only position.liquidity was reduced when claim was done in code above and why positionVests totalLiquidity & positions liquidity end up with different values.
```solidity
 function _claimableLiquidity(uint256 tokenId) internal view override returns (uint128) {
 >>>       uint128 liquidityClaimed = _positionVests[tokenId].totalLiquidity - _positions[tokenId].liquidity;
        uint128 liquidityUnlocked = _unlockedLiquidity(tokenId);
        return liquidityClaimed < liquidityUnlocked ? liquidityUnlocked - liquidityClaimed : 0;
    }
```
However the problem is that after claim must have taken place with positionVests totalLiquidity & positions liquidity ending up with different values. The call of buy(...) function in the contract failed to put the uniqueness of this two variables into consideration during update of new values.
The implementation of the update of the two variables as noted in the pointers in the buy() function provided below shows that instead of adding the liquidityDelta that was bought to positionVests totalLiquidity & positions liquidity individually, positionVests totalLiquidity was updated in totality by the value of positions liquidity eliminating the pre-existing value of claimable liquidity that makes these two variables different

### Scenario Proof
Assuming 
 positionVests totalLiquidity = 1000
 positions liquidity = 1000
if 700 liquidity is claimed new value become
 positionVests totalLiquidity = 1000
 positions liquidity = 300   i.e (1000 - 700)

Then new liquidity of 500 is bought with buy(...) function
 positionVests totalLiquidity = 800 instead of 1500
 positions liquidity = 800   i.e (300 + 500)
The new calulation of already claimed liquidity returns zero i.e 800 - 800 instead of 700 from 1500 - 800

## Recommended Mitigation Steps
