# Vulnerability details

## Impact
The receive function currently lacks a check for whether the contract is in a locked state (_locked). This omission can lead to several potential issues:

During periods when the contract is supposed to be locked, incoming transactions via receive can still trigger unintended actions, compromising security measures put in place by the contract owner.

Without the lock check, the contract may perform actions such as updating state variables or accepting ETH transfers when it should be inactive or restricted.
It can lead to inconsistent behavior where certain transactions are processed when they should be rejected based on the contract's operational state.

Failure to check _locked allows transactions to continue, potentially leading to funds being processed or state variables being updated when they should remain unchanged.

## Proof of Concept
```javascript
receive() external payable {
    if (_isSelfWhitelistDisabled) {
        revert SelfWhitelistDisabled();
    }
    if (_isBlacklisted[_msgSender()]) {
        revert Blacklisted();
    }
    _addWhitelistedAddress(_msgSender());
    payable(_msgSender()).transfer(msg.value);
}
```

## Recommended Mitigation Steps
Before any logic execution in the receive function, verify the state of _locked.
If _locked is true, revert the transaction with an appropriate error message (Locked()).
