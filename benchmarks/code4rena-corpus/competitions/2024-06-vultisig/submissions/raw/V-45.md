# Vulnerability details

## Impact
- Denial of service by frontrunning:

Any Attacker can cause any user's transaction to the `initILOPool(...)`  to revert by frontrunning the victim's transaction with malicious properties of `param` except the `params.uniV3Pool` property that's used to calculate the `salt`.


## Proof of Concept
The `initILOPool(...)`  uses the `Clones.cloneDeterministic(...)` to create a deterministic `iloPoolAddress` address.

The `Clones.cloneDeterministic(...)` uses `CREATE2` opcode and the `CREATE2` is used to deterministically calculate an address. 

`CREATE2` calculates the deterministic address with the following:

- 0xFF, serving as a constant to avert collisions with CREATE.
- The contract address from which Create2 is invoked.
- A salt (32 bytes), an arbitrary value supplied by the sender.
- The bytecode of the contract slated for deployment.

```solidity
new_address = hash(0xFF, contractSender, salt, bytecode)
```

The `salt` parameter passed to the `Clones.cloneDeterministic(...)` function is supposed to be calculated in a way another user cannot exploit to cause grief to the victim and that is by including the `msg.sender` in the `keccack(...)` function that calculates the hash just like `chainId` included in the salt to prevent multichain exploit.

## Exploit Scenario
1. Bob calls the `initILOPool(params)` function in a  
2. Alice copies Bob's `params` parameter before Bob's tx is executed
3. Alice changes all properties of the `params` struct parameter to malicious properties. Only the `params.uniV3Pool` is not changed.
4. Alice frontruns Bob's tx to call the same initILOPool(params)  function.
5. Alice's transaction succeeds while that of Bob fails(GRIEFING)
6. Bob's transaction fails because Alice already created `iloPoolAddress` before Bob
7. Alice can execute this attack to anyone any number of times.

## Recommended Mitigation Steps
Consider including `msg.sender` in the `salt` calculation to mitigate this attack.
