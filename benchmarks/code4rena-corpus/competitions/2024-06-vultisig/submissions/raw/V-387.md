# Vulnerability details

In `VultisigWhitelisted.sol`, the contract allows for the assignment of a whitelist contract. This whitelist contract not only assigns the `vultisig` token but also manages state, including blacklisted and whitelisted addresses. It is crucial for the code to ensure that the whitelist contract starts with an empty state and correctly assigns the `vultisig` token. To achieve this, executing both operations in a single atomic transaction is proposed to prevent any issues with stale or improperly initialized data.

## Impact

In the current implementation of `VultisigWhitelisted.sol`, there is a potential issue related to assigning a `whitelist` contract. Specifically:

1. **Token Assignment Consistency:** When assigning a new `whitelist` contract, it's crucial to ensure that the associated `vultisig` token is correctly assigned to this new contract instance. Failure to do so could lead to inconsistencies where the `vultisig` token does not correspond to the expected contract, potentially causing operational errors or security vulnerabilities.

2. **State Management of Whitelist Contract:** The `whitelist` contract can maintain state, such as blacklisted and whitelisted addresses. When assigning a new `whitelist` contract, it's essential to verify that this contract starts with a clean state. Failing to reset or clear the state could result in unintended access permissions or operational discrepancies.
## Proof of concept

#### First Problem Scenario:

When `VultisigWhitelisted` assigns a new `whitelist` contract:

- **Token Assignment Verification:** Ensure that the `vultisig` token assigned to the new `whitelist` contract is the correct one and matches expectations.
- **State Initialization:** Verify that the state of the new `whitelist` contract is empty or appropriately initialized to prevent stale or conflicting data from affecting operations.

#### Second Problem Scenario:

If an existing `Whitelist` is reassigned to a new `vultisig` token:

- **State Reset Requirement:** Prior to assigning the new `vultisig` token, ensure that the state of the existing `Whitelist` contract, including any blacklisted or whitelisted addresses, is reset or cleared. This prevents potential conflicts or unauthorized access due to outdated state information.
