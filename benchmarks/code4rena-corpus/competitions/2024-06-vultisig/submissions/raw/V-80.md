# Vulnerability details

## Impact
Due to applying a slippage when querying the oracle this allows for users to contribute above the maximum amount allocated per address, if multiple users contribute during the whitelist phase in a very short amount of time this widens the spread due to using a TWAP oracle as well.

This also creates an accounting error because when calling the `Whitelist` contract
`contributed()` it will return a lower amount then what was actually contributed

## Recommended Mitigation Steps

Due to the difficulty in calculating the expected amount out when making a Uniswap V3 swap within this call's context, I recommend refactoring the accounting logic to enforce storing precise numbers, and tracking a max purchase amount of tokens.

We can do this by replacing

```solidity
            // // Calculate rough ETH amount for VULT amount
            uint256 estimatedETHAmount = IOracle(_oracle).peek(amount);
            if (_contributed[to] + estimatedETHAmount > _maxAddressCap) {
                revert MaxAddressCapOverflow();
            }
```

With this

```solidity
            // // Calculate rough ETH amount for VULT amount
            uint256 amountOfTokensPurchased = amount
           // Optionally we can rename `_contributed[to]` to a different variable name for clarity as well
            if (_contributed[to] + amountOfTokensPurchased > _maxAddressCap) {
                revert MaxAddressCapOverflow();
            }
```
