# Vulnerability details

Vultisig token uses a whitelist contract to grant access to users during the whitelist period. If self-whitelisting is enabled, users can simply send some amount of ether to the whitelist contract, and they will get whitelisted. 

The receive() function in the whitelist contract is as follows : 

```
   receive() external payable {
        if (_isSelfWhitelistDisabled) {
            revert SelfWhitelistDisabled();
        }
        if (_isBlacklisted[_msgSender()]) {
            revert Blacklisted();
        }
        _addWhitelistedAddress(_msgSender());
        payable(_msgSender()).transfer(msg.value);
    }
```
Notice how it tries to send the ```msg.value``` back to the caller using ```payable(address).transfer``` function.

```.transfer``` only sends 2300 gas, which is not enough for the recipient to execute any non-trivial logic in a receive() or fallback function.

This breaks usability for a set of users : 
- contracts where payable callback spends more than 2300 gas (which is only enough to emit something)
- The contract is called through a proxy which itself uses up the 2300 gas, causing out of gas reverts.

Example of such contracts are multisigs and smart wallet accounts like Safes (such as [this one](https://etherscan.io/address/0xd1e6626310fd54eceb5b9a51da2ec329d6d4b68a)): it is not enough for Safes () to receive funds, which require > 6k gas for the call to just reach the implementation contract and emit an event.

Multisig safes are especially relevant here because the whitelist contract is made to facilitate a whitelisted token sale, some DAOs and investors will need to use their multisig wallets/ safes to buy using their treasury ETH only accessible from the multisig, and get a share of the VULT tokens in their DAO holdings, but they can't do so as they will not be able to enter the whitelist. 

The 4analyzer report [miscategorizes this issue as an unsafe ERC20 transfer](https://github.com/code-423n4/2024-06-vultisig/blob/main/4naly3er-report.md#l-13-unsafe-erc20-operations), which is wrong. In addition to that, there is an impact other than the one mentioned there.

## Impact
Important contract functionality becomes inaccessible to a set of users, it should be accessible to all and especially DAO and investor multisigs as this is a token sale.

This will hurt the prospects of the vultisig token and prevent wider adoption of the token. There will be less participants in the initial token sale. 

## Proof of Concept
This is copied from Gnosis safe proxy code :
```
pragma solidity ^0.8.24;

contract Safe {
    fallback() external payable {
        // solhint-disable-next-line no-inline-assembly
        assembly {
            let _singleton := and(sload(0), 0xffffffffffffffffffffffffffffffffffffffff)
            // 0xa619486e == keccak("masterCopy()"). The value is right padded to 32-bytes with 0s
            if eq(calldataload(0), 0xa619486e00000000000000000000000000000000000000000000000000000000) {
                mstore(0, _singleton)
                return(0, 0x20)
            }
            calldatacopy(0, 0, calldatasize())
            let success := delegatecall(gas(), _singleton, 0, calldatasize(), 0, 0)
            returndatacopy(0, 0, returndatasize())
            if eq(success, 0) {
                revert(0, returndatasize())
            }
            return(0, returndatasize())
        }
    }
}
```

Even with empty calldata, if you send any amount of ether eg. 1 wei to it, it will consume 4811 gas units, so this fallback will revert when called via .transfer.

## Recommended Mitigation Steps
Use call() instead of transfer() to send ETH:

```
(bool success, ) = payable(msg.sender).call{value: _withdrawRequest.amountToRedeem}("");
require(success, "ETH transfer failed");
```

This forwards all available gas and allows contract recipients to execute arbitrary logic.
