# Vulnerability details

## Impact
The current implementation of the `receive` function does not check whether the ETH contribution exceeds the `_maxAddressCap`. This omission leads to several potential problems:

Violation of Contribution Limits: Addresses can contribute more ETH than the maximum allowed cap, defeating the purpose of having a cap.
Some participants might contribute more than others, potentially leading to centralization or unfair advantages.

## Proof of Concept
Consider the following scenario with the current implementation:

_maxAddressCap is set to 3 ETH.
Address B sends 2 ETH to the contract. Since there is no check, the contract accepts it.
Address B sends another 2 ETH to the contract. Again, there is no check, so the contract accepts it.
Address B has now contributed a total of 4 ETH, which exceeds the 3 ETH cap.
Example
Here’s the current receive function without the `_maxAddressCap` check:

```javascript
receive() external payable {
    if (_isSelfWhitelistDisabled) {
        revert SelfWhitelistDisabled();
    }
    if (_isBlacklisted[_msgSender()]) {
        revert Blacklisted();
    }
    _addWhitelistedAddress(_msgSender());
    payable(_msgSender()).transfer(msg.value);
}
```

## Recommended Mitigation Steps

To address this issue, implement a check within the receive function to ensure that the amount of ETH sent do not exceed the _maxAddressCap. If the new sent ETH would exceed the cap, the transaction should revert.

```javascript

    if (msg.value > _maxAddressCap) {
        revert ExceedsMaxAddressCap();
    }
```
