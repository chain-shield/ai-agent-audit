# Vulnerability details

## Impact
- An actual owner of the project will not be able to launch ILO using this platform
## Description
Anyone can call `initProject` and claim the ownership of the project corresponding with its UniswapV3 pool.  
```solidity
function initProject(InitProjectParams calldata params) external override afterInitialize() returns(address uniV3PoolAddress) {
    uint64 refundDeadline = params.launchTime + DEFAULT_DEADLINE_OFFSET;

    PoolAddress.PoolKey memory poolKey = PoolAddress.getPoolKey(params.saleToken, params.raiseToken, params.fee);
    uniV3PoolAddress = _initUniV3PoolIfNecessary(poolKey, params.initialPoolPriceX96);
    
    _cacheProject(uniV3PoolAddress, params.saleToken, params.raiseToken, params.fee, params.initialPoolPriceX96, params.launchTime, refundDeadline);
    emit ProjectCreated(uniV3PoolAddress, _cachedProject[uniV3PoolAddress]);
}
```
The owner's address is recorded in `_cacheProject`  
```solidity
function _cacheProject(
        address uniV3PoolAddress,
        address saleToken,
        address raiseToken,
        uint24 fee,
        uint160 initialPoolPriceX96,
        uint64 launchTime,
        uint64 refundDeadline
    ) internal {
        Project storage _project = _cachedProject[uniV3PoolAddress]; 
        require(_project.uniV3PoolAddress == address(0), "RE");

        _project.platformFee = PLATFORM_FEE;
        _project.performanceFee = PERFORMANCE_FEE;
        _project.admin = msg.sender;
        _project.saleToken = saleToken;
    ...
    ...
```
The init project information is stored in a mapping variable `_cachedProject` using UniswapV3 pool address as a key.  

There is also a check to prevent the project from being initialized twice.

If the ownership is claimed by adversaries before the actual project's owner, they will no longer be able to launch ILO with their own token because one can't deploy a new addess of UniswapV3 pool with the same token and fee configuration.  


## Proof-of-Concept
The following test demonstrates that anyone can call `initProject` function and calling it twice would throw a revert because `_project.uniV3PoolAddress` already existed.  
### Steps
1. Add following test function in `2024-06-vultisig/test/ILOManager.t.sol`  
2. Run `forge test --match-contract ILOManagerTest --match-test testInitProjectTwice -vvvv`  
3. Observe that the first call to `initProject` succeed and the second revert with error string: "RE"  

```solidity
    function testInitProjectTwice() public {
        vm.prank(makeAddr("actor_1"));
        iloManager.initProject(IILOManager.InitProjectParams({
                    saleToken: mockProject().saleToken,
                    raiseToken: mockProject().raiseToken,
                    fee: 10000,
                    initialPoolPriceX96: mockProject().initialPoolPriceX96+1, 
                    launchTime: mockProject().launchTime
                })
            );
        vm.startPrank(makeAddr("actor_2"));
        vm.expectRevert(bytes("RE"));
        iloManager.initProject(IILOManager.InitProjectParams({
                    saleToken: mockProject().saleToken,
                    raiseToken: mockProject().raiseToken,
                    fee: 10000,
                    initialPoolPriceX96: mockProject().initialPoolPriceX96+1, 
                    launchTime: mockProject().launchTime
                })
            );
        vm.stopPrank();
    }
```

## Rationale for severity
Adversaries can use this bug to prevent project's owner from launching an ILO with the protocol. Project's owner will have to deploy a new token contract in order to launch another ILO.  

Hence, the high severity

## Recommended Mitigations
As ILO will mostly be used for Token Generation Event (TGE), a small balance of project's token can be used as a proof of ownership for ILO.  

Consider adding a check requiring that `msg.sender` must own at least 1 wei of `SALE_TOKEN` as a proof of project's ownership.  

Choosing token balance as a proof of ownership instead of contract's owner to make the contract compatible with ALL ERC20 tokens.  

**Note**: Even if someone were to deploy UniswapV3 pool before project's owner calling `initProject` and initialize the pool with an arbitrary initial pool price, the project's owner can still change `slot0.sqrtPriceX96` in an empty pool by calling `swap` function directly on UniswapV3 pool and proceeed to call `initProject`.  

### Suggested fix
```solidity
function initProject(InitProjectParams calldata params) external override afterInitialize() returns(address uniV3PoolAddress) {
    require( IERC20(params.saleToken).balanceOf(msg.sender) > 0, "Not an actual project's owner" );
    uint64 refundDeadline = params.launchTime + DEFAULT_DEADLINE_OFFSET;

    PoolAddress.PoolKey memory poolKey = PoolAddress.getPoolKey(params.saleToken, params.raiseToken, params.fee);
    uniV3PoolAddress = _initUniV3PoolIfNecessary(poolKey, params.initialPoolPriceX96);
    
    _cacheProject(uniV3PoolAddress, params.saleToken, params.raiseToken, params.fee, params.initialPoolPriceX96, params.launchTime, refundDeadline);
    emit ProjectCreated(uniV3PoolAddress, _cachedProject[uniV3PoolAddress]);
}
```
