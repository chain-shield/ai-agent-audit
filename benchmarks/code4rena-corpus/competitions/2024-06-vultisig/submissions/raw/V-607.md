# Vulnerability details

## Impact
Imagine an investor participated in a previous sale and holds NFT ID 1. Now, they join a new sale. The code might incorrectly fetch NFT ID 1 (using `tokenOfOwnerByIndex`), even though the investor should receive a new NFT for this sale. Consequently, the `raiseAmount` and `liquidity` for NFT ID 1 (from the previous sale) would be updated, leading to incorrect accounting and potentially impacting vesting schedules.

1. The code aims to fetch the existing token ID for an investor already holding a position. However, it uses `tokenOfOwnerByIndex(recipient, 0)`, which retrieves the token ID at index 0 for the recipient. This approach assumes that an investor can only hold one NFT, which might be false. This logic breaks down if an investor acquires multiple NFTs (e.g., by participating in various rounds or through transfers).

2. The code might update the `_position` data for the wrong NFT due to incorrect token ID retrieval. If an investor has multiple positions and the retrieved token ID doesn't correspond to the intended position, the `raiseAmount` and `liquidity` will be updated incorrectly.

3. The code checks if the user has a balance of NFTs (balanceOf(recipient) == 0) to determine if they are new investors. However, it needs to check if the user has a position in this sale. A user could have participated in a previous sale and held an NFT, but this function would treat them as a new investor in the current sale.

## Proof of Concept
[ILOPool.sol:buy](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L126-L176)

1. [tokenOfOwnerByIndex()](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L147) and Multiple NFT Ownership:

_Concept:_ The `tokenOfOwnerByIndex(address owner, uint256 index)` commonly found in ERC721 NFT contracts, retrieves the token ID owned by a specific address at a given index. The index represents the order in which the tokens were minted or transferred to that address.
**Issue**: If an investor participates in multiple sales or receives NFTs through transfers, they might own multiple NFTs from the same contract. Using [tokenOfOwnerByIndex(recipient, 0)](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L147) consistently will only fetch the first NFT they received, potentially leading to incorrect data updates.

2. **_Impact of Incorrect Position Updates_**
Updating the wrong `_position` data will result in incorrect tracking of raise amounts, liquidity allocations, and vesting schedules. This can lead to discrepancies in investor balances, distribution calculations, and overall pool accounting.
_If an investor's contributions are misallocated to a different position, they might receive more or fewer rewards than they are entitled to. This creates an uneven playing field and can erode trust in the ILO pool._

**_Example_**
1. **Investor 1 Participates in Sale 1**
    - `saleInfo` is set up for Sale 1.
    - Investor 1 calls `buy()` with `raiseAmount = 100`.
    - A new NFT (token ID 1) is minted for Investor 1.
    - `_positions[1]` is updated: `raiseAmount = 100`.

2. **Investor 2 Participates in Sale 1**
    - Investor 2 calls `buy()` with` raiseAmount = 150`.
    - A new NFT (token ID 2) is minted for Investor 2.
    - `_positions[2]` is updated: `raiseAmount = 150`.

3. **Investor 1 Participates in Sale 2**
    - `saleInfo` is updated for Sale 2.
    - Investor 1 calls `buy()` with `raiseAmount = 200`.
    - **Bug Manifestation**
       * `balanceOf(investor1)` is not 0 (they own NFT ID 1).
       * `tokenOfOwnerByIndex(investor1, 0)` returns token ID 1.
       * Incorrectly, `_positions[1].raiseAmount` is updated to 300 (100 + 200), even though this contribution should be associated with Sale 

**Proof of Impact**
  * Investor 1's contribution in Sale 2 is incorrectly attributed to their position in Sale 1.
  * `_positions` data is inaccurate, leading to incorrect accounting and potential issues with reward distribution and vesting.

## Recommended Mitigation Steps
Instead of a single `_positions` mapping, consider using a nested mapping like `mapping(uint256 => mapping(address => Position))` `_salePositions;`, where the first key is the sale ID and the second key is the investor's address. This allows you to store positions separately for each sale.
