# Vulnerability details

## Impact
The absence of the `tokenURI` function in the ILOPool contract, which is a crucial part of the [ERC721 Metadata standard](https://eips.ethereum.org/EIPS/eip-721#specification), has significant implications for the interoperability and usability of the tokens managed by the contract. Without this function, the tokens lack standardized metadata accessibility, hindering their seamless integration with other ERC721-compliant applications, marketplaces, and wallets.

The ERC721 Metadata standard provides a unified interface for retrieving token-specific metadata, such as `name`, `description`, `image`, and other `attributes`. By not implementing the `tokenURI` function, the `ILOPool` contract breaks compatibility with the broader ecosystem of ERC721.


## Proof of Concept
The ILOPool contract, while implementing the ERC721 standard, does not include the implementation of the `tokenURI` function, which is defined in the `IERC721Metadata` interface. Look at this part of the code:

https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L53-L59

```solidity
contract ILOPool is
    ERC721,
    IILOPool,
    ILOWhitelist,
    ILOVest,
    Initializable,
    Multicall,
    ILOPoolImmutableState,
    LiquidityManagement
{
    // ...

    function name() public pure override(ERC721, IERC721Metadata) returns (string memory) {
        return 'KRYSTAL ILOPool V1';
    }

    function symbol() public pure override(ERC721, IERC721Metadata) returns (string memory) {
        return 'KRYSTAL-ILO-V1';
    }

    // ...
}
```

As seen in the code above, the ILOPool contract overrides the `name` and `symbol` functions from the `IERC721Metadata` interface. However, it does not implement the `tokenURI` function, which is also part of the same interface.

[The `tokenURI` function is defined in the `IERC721Metadata` interface as follows:](https://eips.ethereum.org/EIPS/eip-721#specification)

```solidity
interface IERC721Metadata {
    // ...

    /// @notice A distinct Uniform Resource Identifier (URI) for a given asset.
    /// @dev Throws if `_tokenId` is not a valid NFT. URIs are defined in RFC
    ///  3986. The URI may point to a JSON file that conforms to the "ERC721
    ///  Metadata JSON Schema".
    function tokenURI(uint256 _tokenId) external view returns (string memory);
}
```

The purpose of the `tokenURI` function is to return a distinct URI for a given token identified by `_tokenId`. This URI should point to a JSON file that conforms to the "ERC721 Metadata JSON Schema," which specifies the structure and fields for representing token metadata.

By not implementing the `tokenURI` function, the `ILOPool` contract fails to provide a standardized way to retrieve metadata for the tokens it manages. This omission breaks compliance with the ERC721 Metadata standard and according to the [README](https://github.com/code-423n4/2024-06-vultisig#eip-compliance-checklist), `ILOPool` is to be compliant with EIP-721.

## Recommended Mitigation Steps
To address the non-compliance with the ERC721 Metadata standard and ensure full compatibility, `ILOPool` should implement the `tokenURI` function as specified in the [`IERC721Metadata` interface](https://eips.ethereum.org/EIPS/eip-721#specification). The implementation should adhere to the following guidelines:

- The `tokenURI` function should accept a `_tokenId` parameter representing the unique identifier of the token for which metadata is being requested.

- The function should return a valid URI (Uniform Resource Identifier) pointing to the metadata file associated with the given `_tokenId`. The URI should follow the format specified in RFC 3986.

- The metadata file referenced by the URI should conform to the "ERC721 Metadata JSON Schema," which defines the structure and fields for representing token metadata. The JSON file should include relevant information such as the token's name, description, image URL, and any other desired attributes.

- The `tokenURI` function should revert if the provided `_tokenId` does not correspond to a valid token managed by the ILOPool contract.

- The implementation should handle the generation and management of metadata files, ensuring that each token has a unique and accessible metadata URI.
