# Vulnerability details

## Impact

The incorrect handling of decimal scaling in the [peek function](https://github.com/code-423n4/2024-06-vultisig/blob/main/hardhat-vultisig/contracts/oracles/uniswap/UniswapV3Oracle.sol#L39) of the UniswapV3Oracle smart contract can lead to significant errors in the calculated token prices. The function attempts to apply a 5% slippage adjustment and scale the result to the appropriate decimal precision but fails due to incorrect arithmetic operations.

This may also expose the contract to arbitrage opportunities, exploiting the discrepancy between the intended and computed token prices.

## Proof of Concept

The vulnerability results in the function returning a value that is considerably off than expected due to an excessive reduction factor (1e20 instead of 1e18), compounded by an incorrect integration of the slippage calculation. This miscomputation can lead to significant financial inaccuracies, impacting users' transactions by providing misleading financial data.

The function is designed to calculate the TWAP adjusted by a 5% slippage. However, the implementation multiplies quotedWETHAmount and baseAmount by 95 (intending a 5% reduction) and then divides by 1e20 rather than correctly applying the slippage and adjusting for token decimal places (1e18 for the tokens used). This incorrect calculation alters the output value due to the additional division by 100, which is not accounted for in the intended decimal adjustment.

Since the intention is to apply a 5% reduction and then adjust for the resulting decimal scale correctly, the division by 1e20 does both but will alter the final amount due to the additional factor of 1e2 (100 times smaller than expected).

Incorrect Implementation:
quotedWETHAmount = 1e18  # 1 ETH in wei
baseAmount = 1e18  # 1 unit of VULT in wei
result = (quotedWETHAmount * baseAmount * 95) / 1e20
`result --> 9.5e+17`

Correct Implementation:
quotedWETHAmount = 1e18  # 1 ETH in wei
baseAmount = 1e18  # 1 unit of VULT in wei
result = (quotedWETHAmount * baseAmount * 95 / 100) / 1e18
`result --> 9.499999999999999e+17`

In practice, ensuring that calculations are exact and correctly implemented as intended is vital for maintaining the expected functionality of financial applications.

## Recommended Mitigation Steps

Modify the function to apply the 5% slippage correctly before adjusting for decimal precision:

```diff
    function peek(uint256 baseAmount) external view returns (uint256) {
        uint32 longestPeriod = OracleLibrary.getOldestObservationSecondsAgo(pool);
        uint32 period = PERIOD < longestPeriod ? PERIOD : longestPeriod;
        int24 tick = OracleLibrary.consult(pool, period);
        uint256 quotedWETHAmount = OracleLibrary.getQuoteAtTick(tick, BASE_AMOUNT, baseToken, WETH);
        // Apply 5% slippage
-        return (quotedWETHAmount * baseAmount * 95) / 1e20; // 100 / 1e18
+        return (quotedWETHAmount * baseAmount * 95 / 100) / 1e18;
    }
```
