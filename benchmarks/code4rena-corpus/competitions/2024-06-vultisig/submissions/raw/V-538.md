# Vulnerability details

### **Relevant Context**
ILOPool are user(project admin) supplied pools, which gets deployed  after every call to `initILOPool` which creates unique pools based on the projects requirements and settings to be used for sale and vest. These pools are susceptible to be frontrun and drained by malicious actors.

### **Relevant Context**
These past reports details and shows how attackers can take advantage of the CREATE2 opcode in performing this exploit

### **Finding Description**

Whenever a project is being created through `initProject`, the next step is to deploy and initialize a pool to which will be used for sale and vest, One project can init many ILO Pools.

The initILOPool make use of OpenZeppelin's `cloneDeterministic` function which is responsible for a deploying  a new pool using CREATE2 under the hood. The `cloneDeterministic` takes in two parameters which are; 
- ILO_POOL_IMPLEMENTATION and salt.

Based on the contract, the ILO_POOL_IMPLEMENTATION is a public address that can easily be gotten on chain, while the salt is an encoded hash of `ChainId.get()`, `params.uniV3Pool` `_initializedILOPools[params.uniV3Pool].length` which are also all visible on chain.

An attacker can frontrun the project and easily compute all these values together and then deploys a malicious contract at the predetermined address using CREATE2 while setting allowance for himself before self destructing the contract.

This self destructed contract will still have the malicious actor as having allowance to spend the contracts balance and then when the original project deploys it pool at the said address, the attacker can wipe out all the funds present in the contract at that instance


Assuming the attacker has already found an address collision against an undeployed ILOPool, let's say 0xCOLLIDED. The steps for complete draining of the Pool are as follow;
First tx:
- Deploy the attack contract onto address 0xCOLLIDED.
- Set infinite allowance for {0xCOLLIDED ---> attacker wallet} for any token they want.
- Destroy the contract using selfdestruct.


Second tx:
- Deploy the ILOPool to 0xCOLLIDED.
- Wait until the Pool will hold as many tokens as you want and drain it.
- The attacker has stolen all funds from the Pool.


### Impact Summary

- Pool Frontrunning can have all ILOPool funds drained by an attacker

### Severity Explanation

The likelyhood is High as it does not require much efforts or large computational power.
The impact is also high, as projects funds can be drained before they are even aware of it.

### **Proof of Concept**

Below is a simple smart contract example illustrating how an attacker can front-run and deploy a pool using CREATE2, set allowances for themselves, and then self-destruct to anticipate the original contract deployment to steal funds.

```solidity

    // SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract Attack {
    address public owner;
    address public vulnerable;

    constructor(address _owner) {
        owner = _owner;
    }

    function deployVulnerableContract(bytes32 salt, address _vulnerable) public {
        bytes memory bytecode = abi.encodePacked(
            type(Vulnerable).creationCode,
            abi.encode(_vulnerable)
        );
        address addr;
        assembly {
            addr := create2(0, add(bytecode, 0x20), mload(bytecode), salt)
        }
        vulnerable = addr;
    }

    function setAllowanceAndSelfDestruct(address token, address spender, uint256 amount) public {
        // Assuming the vulnerable contract is an ERC20 token
        (bool success, ) = vulnerable.call(
            abi.encodeWithSignature("approve(address,uint256)", spender, amount)
        );
        require(success, "Approval failed");

        // Self-destruct to free up the address for the original contract
        selfdestruct(payable(owner));
    }
}


```


## **Recommendation**

Consider also adding and encoding `block.timestamp` and `block.number` combined with the  salt and a nonce to ensure uniqueness. This approach adds more entropy and variability, making it difficult for an attacker to predict the salt and pre-deploy a contract.
