# Vulnerability details

## Impact
Attackers can make users not allowed for whitelist when Self Whitelist gets enabled

## Proof of Concept
When Self Whitelist gets enabled, users can get themselves whitelisted and as well increase the whitelistIndex by transferring native ETH directly to the contract:
```solidity
receive() external payable {
        if (_isSelfWhitelistDisabled) {
            revert SelfWhitelistDisabled();
        }
        if (_isBlacklisted[_msgSender()]) {
            revert Blacklisted();
        }
@>      _addWhitelistedAddress(_msgSender());
        payable(_msgSender()).transfer(msg.value);
    }
``` 
However, the ETH will be sent back to the sender at the transaction. Also note that the Whitelist.sol contract can set a max AllowedWhitelistIndex (`_allowedWhitelistIndex`) which gets checked on transfers:
```solidity
if (_allowedWhitelistIndex == 0 || _whitelistIndex[to] > _allowedWhitelistIndex) {
                revert NotWhitelisted();
            }
```
This means if someone add more whitelisted address more than the `_allowedWhitelistIndex`, the following whitelisted address will not be allowed for whitelist. The issue here is when the self whitelist gets enabled there is no restriction in performing this with no cost.

- Attacker makes a contract that transfers ETH to it, and deploys it multiple times
- Honest user attempts using the Self Whitelist feature
- Attacker front-runs this and triggers the multiple attack contracts in a single transaction such that _whitelistCount > _allowedWhitelistIndex
- User address becomes ineligible for whitelist
