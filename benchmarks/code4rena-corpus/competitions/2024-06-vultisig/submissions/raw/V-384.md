# Vulnerability details

In the current implementation, a project can contain an unlimited number of pools. However, this poses a potential Denial of Service (DoS) risk during the initialization phase of the project. Specifically, during the execution of the `ILOManager::launch` function, the code iterates through all pools and calls the `ILOPool::launch` function for each one. Inside `ILOPool::launch`, there is another loop that iterates through all `VestingConfig` objects (except the first one). The nested iterations result in a high computational load, potentially making it infeasible to launch the project if there are too many pools or vesting configurations.

## Impact

- **High Gas Consumption**: The nested iterations can result in excessive gas consumption, making the `launch` operation prohibitively expensive for users.
- **Potential Denial of Service**: If the gas required exceeds the block gas limit, the project initialization will fail, causing a DoS.
- **Loss of User Confidence**: High gas costs and failed transactions can lead to a loss of faith in the system.

## Recommended mitigation steps

- **Limit the Number of Pools**: Introduce a maximum limit on the number of pools a project can have to ensure the launch operation remains within a reasonable gas limit.

- **Limit the number of Vesting Configs**: Introduce a maximum limit on the number of `VestingConfig` objects that can be associated with each pool.

- **Documentation and Warnings**: Clearly document the limitations and potential issues in the system's documentation. Warn users about the potential high gas costs when creating a large number of pools or vesting configurations.
