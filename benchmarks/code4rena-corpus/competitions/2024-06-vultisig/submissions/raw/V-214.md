# Vulnerability details

## Impact
Funds will be locked in the contract, if the Admin tries to call the ILOManager.claimRefund due to out-of-gas in the calling contract if it returns a massive amount of data.

## Proof of Concept
         function claimRefund(address uniV3PoolAddress) external override onlyProjectAdmin(uniV3PoolAddress) returns(uint256 totalRefundAmount) {
        require(_cachedProject[uniV3PoolAddress].refundDeadline < block.timestamp, "RFT");
        address[] memory initializedPools = _initializedILOPools[uniV3PoolAddress];
        for (uint256 i = 0; i < initializedPools.length; i++) {
            totalRefundAmount += IILOPool(initializedPools[i]).claimProjectRefund(_cachedProject[uniV3PoolAddress].admin);

This function is designed to claimRefund by the ProjectAdmin, however inside the function, we have some calls from outside of the function which dynamic arrays with no bound.

        address[] memory initializedPools = _initializedILOPools[uniV3PoolAddress];

This takes in the arrays of the initiaizedILOPools, of which the initializedILOpools is also a dynamic array. below

    mapping(address => address[]) private _initializedILOPools; // map uniV3Pool => list of initialized ilo pools

In addition to the For loop which runs through the initialized pools assigning the refund amount below

        for (uint256 i = 0; i < initializedPools.length; i++) {
            totalRefundAmount += IILOPool(initializedPools[i]).claimProjectRefund(_cachedProject[uniV3PoolAddress].admin);

Where the problem lies is if the total number of InitializedPools become large, the run through these numbers might lead to out of Gas, hence funds are stuck in the contract. Check  https://swcregistry.io/docs/SWC-113/


## Tools Used
Manual Review

## Recommended Mitigation Steps
 Avoid combining multiple calls in a single transaction, especially when calls are executed as part of a loop
    Always assume that external calls can fail
    Implement the contract logic to handle failed calls
