# Vulnerability details

## Impact
The liquidity amount to deposit from the ILOPool on launch is wrongly calculated. Assumes that the uniswap pool price is static, for projects with already circulating supply this is not the case. 

When the deposit amount of the payment token (the one given by investors) is less than the amount in the ILOPool, this leftover will be stuck in the contract (loss of funds)

## Proof of Concept
The [launch function](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOPool.sol#L269) deposits liquidity into the uniswap pool. For this it calculates the amount of token0 and token1 to deposit using [_saleAmountNeeded](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOPool.sol#L382). This function assumes that the price is static, which is a wrong assumption for projects that have already circulating supply between investors. 

```solidity
    function _saleAmountNeeded(uint256 raiseAmount) internal view returns (
        uint256 saleAmountNeeded,
        uint128 liquidity
    ) {
        if (raiseAmount == 0) return (0, 0);

        if (_cachedPoolKey.token0 == SALE_TOKEN) {
            // liquidity1 raised
            // SQRT_RATIO_X96 IS THE CURRENT PRICE. STATIC AND NOT FETCHED FROM POOL
            liquidity = LiquidityAmounts.getLiquidityForAmount1(SQRT_RATIO_LOWER_X96, SQRT_RATIO_X96, raiseAmount);
            saleAmountNeeded = SqrtPriceMathPartial.getAmount0Delta(SQRT_RATIO_X96, SQRT_RATIO_UPPER_X96, liquidity, true);
        } else {
            // liquidity0 raised
            // SQRT_RATIO_X96 IS THE CURRENT PRICE. STATIC AND NOT FETCHED FROM POOL
            liquidity = LiquidityAmounts.getLiquidityForAmount0(SQRT_RATIO_X96, SQRT_RATIO_UPPER_X96, raiseAmount);
            saleAmountNeeded = SqrtPriceMathPartial.getAmount1Delta(SQRT_RATIO_LOWER_X96, SQRT_RATIO_X96, liquidity, true);
        }
    }
```

THe function _saleAmountNeeded calculates the sale token amount needed on the pool given the raise amount with the following [formulas](https://uniswapv3book.com/milestone_1/calculating-liquidity.html#token-amounts-calculation-again). This function uses the uniswap library [SqrtPriceMathPartial.getAmount0Delta](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/libraries/SqrtPriceMathPartial.sol#L12-L20C14) and [getAmount1Delta](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/libraries/SqrtPriceMathPartial.sol#L42-L49). These should calculate the amount of token0 and token1 respectively given two prices. 

The problem arises when the price moves and the amount of token returned is wrong. Example:

- Project and ILOPool are deployed and investors already deposited tokens to buy.
- The token0 is the project's token and token1 is the liquidity token given by investors. 
- The price of the pool moves to the right, thus for the position chosen by the project owners between ticks a and b now requires more of token0 (sale token) and less of token1 (raise token).
- The ILOPool contains X amount of token1 (raise token) and since the liquidity position now requires less of this token, two scenarios can happen:
  - The ILOPool contains enough token0 (sale token) to deposit liquidity, thus the  leftovers of token1 are stuck in the contract.
  - The ILOPool doesn't contains enough of token0 to deposit, thus the launch always fails because the ILOPool doesn't transfer enough of token0.
  - [amounts asked](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/base/LiquidityManagement.sol#L20-L29).
  - [actual transfer](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/base/PeripheryPayments.sol#L31-L38)

## Tools Used
Manual review

## Recommended Mitigation Steps
When calculating the token amounts to transfer, don't rely on the stored initial price for projects with active pools.

The amount of tokens transferred by the investors should be refundable after launch. To avoid leftovers on their side.
