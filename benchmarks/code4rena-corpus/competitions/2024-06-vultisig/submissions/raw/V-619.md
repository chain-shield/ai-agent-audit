# Vulnerability details

## Vulnerability Details
As described in the function `Whitelist::receive`, the protocol allows any user to self whitelist himself by sending a random amount of ETH to the `Whitelist` contract. If the whitelist is not disabled or the address is not blacklisted, the user will be whitelisted and the user's ETH amount will be sent back to him.

```javascript

receive() external payable {
        if (_isSelfWhitelistDisabled) {
            revert SelfWhitelistDisabled();
        }
        if (_isBlacklisted[_msgSender()]) {
            revert Blacklisted();
        }
>>      _addWhitelistedAddress(_msgSender());
        payable(_msgSender()).transfer(msg.value);
}

```

The `Whitelist::_addWhitelistedAddress` function increases the `_whitelistCount` value if the address is not whitelisted before.

```javascript

function _addWhitelistedAddress(address whitelisted) private {
        if (_whitelistIndex[whitelisted] == 0) {
            _whitelistIndex[whitelisted] = ++_whitelistCount;
        }
}

```

On the other hand, a maximum number of whitelisted addresses is maintained via the variable `Whitelist::_allowedWhitelistIndex`. Each address is verified if eligible for whitelist via the function `Whitelist::checkWhitelist`. As depicted in the condition below, if an address has its whitelist index bigger than `_allowedWhitelistIndex`, it can't be whitelisted.

```javascript

function checkWhitelist(address from, address to, uint256 amount) external onlyVultisig {
        if (from == _pool && to != owner()) {
...

>>          if (_allowedWhitelistIndex == 0 ||
            _whitelistIndex[to] > _allowedWhitelistIndex) {
                // q TODO: check again this condition
                revert NotWhitelisted();
            }
...
}

```

Such conditions can be abused by any attacker to generate multiple random addresses. Each address can then send 1 wei to the `Whitelist` contract to be whitelisted. This will rapidly increase the length of the array `_whitelistIndex`, to reach the maximum number of the whitelist users rapidly. As a result, a legitimate user can't be self-whitelisted anymore.


## Impact

When the self-whitelist period starts, an attacker could flood the `Whitelist` contract with random addresses and self-whitelist these addresses by transferring only 1 wei. The total number of whitelisted addresses allowed by the protocol will be reached instantly, hence, block any new user from joining the protocol because they can't not whitelist their address anymore.

## Proof of Concept
Scenario:
- The self whitelist period starts, which allows at max 10 addresses for example
- An attacker creates randomly multiple addresses and whitelist these addresses by sending ETH to the `Whitelist` contract
- A legitimate user can not whitelist his address anymore, hence, he can't interact with the protocol

        });
      }

      // A legitimate buyer want to whitelist his address in order to join the protocol
      // The current whitelistCount is now 12,

      // and the previous two addresses added by the deployVultisigWhitelistedFixture function : buyer and otherAccount
      expect(await whitelist.whitelistCount()).to.eq(12);
      // Generate new user account with a new address
      const newUserAccount = await ethers.getImpersonatedSigner(
        ethers.Wallet.createRandom().address
      );
      // Assume that this user has 1 ETH, it can be any value
      // it just needs to be bigger than the amount of ETH that he sends to the Whitelist contract
      await network.provider.send("hardhat_setBalance", [

As the attacker is not required to lose any funds, this attack is likely to happen, which can seriously disrupt the usage of the protocol towards potential investors.

Manual review.

## Recommended Mitigation Steps

It's not trivial to prevent this attack from happening. The protocol could monitor for mass whitelisting transactions and trigger the blacklisting mechanism to remove the malicious addresses. In addition, it can be useful to require an entrance fee to be whitelisted. Such a fee can be returned to the user afterward when he makes legitimate interactions with the protocol.
