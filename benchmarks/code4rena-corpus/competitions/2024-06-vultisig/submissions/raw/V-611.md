# Vulnerability details

## Vulnerability Detail
Within the `buy()` function in `ILOPool.sol` the protocol intends to limit how much a single user can buy. This is done by the following check

```solidity
// if investor already have a position, just increase raise amount and liquidity
        // otherwise, mint new nft for investor and assign vesting schedules
        if (balanceOf(recipient) == 0) { 
            _mint(recipient, (tokenId = _nextId++));
            _positionVests[tokenId].schedule = _vestingConfigs[0].schedule;
        } else {
            tokenId = tokenOfOwnerByIndex(recipient, 0);
        }

        Position storage _position = _positions[tokenId];
        require(raiseAmount <= saleInfo.maxCapPerUser - _position.raiseAmount, "UC"); 
        _position.raiseAmount += raiseAmount; 
```

An attacker can call `buy()` and then transfer the minted NFT to some other address they own. Now they can call buy again and will be minted a new NFT. The attacker has clearly bypassed their buy limit by this method.

## Impact
Attacker has bypassed their cap per user

Since there is a `maxSaleAmount` the attacker may prevent some other investor from buying

Since the attacker has exceeded their limit, the `softCap` will be reached earlier so they can call `launch` earlier before other investors buy


## Proof of Concept
Attack involves the following steps

1. Attacker calls buy() and is minted an NFT
2. Attacker transfers the NFT to another one of their wallets using ILOPool.transferFrom()
3. The attacker calls buy() again, since `balanceOf(attacker) == 0` they will be minted a new NFT at the next tokenId

## Tools Used
Manual review

## Recommended Mitigation Steps
Disable transferring the NFT
