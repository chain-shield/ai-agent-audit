# Vulnerability details

## Impact
```solidity
function consult(address pool, uint32 period) internal view returns (int24 timeWeightedAverageTick) {
    require(period != 0, "BP");

    uint32[] memory secondAgos = new uint32[](2);
    secondAgos[0] = period;
    secondAgos[1] = 0;

    (int56[] memory tickCumulatives, ) = IUniswapV3Pool(pool).observe(secondAgos);
    int56 tickCumulativesDelta = tickCumulatives[1] - tickCumulatives[0];

    timeWeightedAverageTick = int24(tickCumulativesDelta / int56(uint56(period)));

    // Always round to negative infinity
    if (tickCumulativesDelta < 0 && (tickCumulativesDelta % int56(uint56(period)) != 0)) timeWeightedAverageTick--;
}
```
The way the time-weighted average tick is calculated. The code divides `tickCumulativesDelta` by `period` to get the average, but this doesn't account for the fact that the ticks may not have been updated constantly.

**For Example**

Let's say the `period` is 10 seconds, and the following tick updates happened:
   - Time 0: Tick = 100
   - Time 5: Tick = 200
   - Time 10: Tick = 300

The code would calculate the `tickCumulativesDelta` as (300 - 100) = 200, and the `timeWeightedAverageTick` as 200 / 10 = 20. However, the correct time-weighted average tick should be 250, because the tick was at 200 for half of the period and at 300 for the other half.

## Proof of Concept
The `consult` function assumes that the difference between tick cumulative directly corresponds to the time period provided. This is flawed because.
   1. **Uneven Tick Updates**: Uniswap V3 pools don't guarantee ticks will be updated at a constant rate. Updates happen when the price moves outside the current tick range, which can be frequent or infrequent.
   2. **Limited Observations**: The pool stores a limited history of tick observations (`observationCardinality`). If the requested `period` goes beyond the available history, the calculation becomes inaccurate.

**Conceptual Example:**

Imagine a pool where the price oscillates rapidly for a short time, causing many tick updates. Then, the price stabilizes for an extended period. If you request the average tick over a time that includes both the volatile and stable periods, the original consult function would be skewed towards the volatile period because it had more tick updates, even if the price spent much longer in the stable range.

## Recommended Mitigation Steps
The code needs to account for the tick updates' timestamps. This can be done by using the `cardinality` and `observationIndex` values returned by the `slot0()` function of the Uniswap V3 pool.
```solidity
function consult(address pool, uint32 period) internal view returns (int24 timeWeightedAverageTick) {
    require(period != 0, "BP");

    (, , uint16 observationIndex, uint16 observationCardinality, , , ) = IUniswapV3Pool(pool).slot0();

    // Get the timestamps and tick cumulatives of the two most recent observations
    (uint32 observationTimestamp1, int56 tickCumulative1, , ) = IUniswapV3Pool(pool).observations(observationIndex);
    (uint32 observationTimestamp0, int56 tickCumulative0, , ) = IUniswapV3Pool(pool).observations((observationIndex + observationCardinality - 1) % observationCardinality);

    // Calculate the time-weighted average tick
    int56 tickCumulativesDelta = tickCumulative1 - tickCumulative0;
    uint32 timeElapsed = observationTimestamp1 - observationTimestamp0;
    timeWeightedAverageTick = int24(tickCumulativesDelta * int56(uint56(period)) / int56(uint56(timeElapsed)));
}
```
