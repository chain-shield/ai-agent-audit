# Vulnerability details

## Impact
The `Whitelist` contract allows users to self-whitelist by sending ETH to the contract. If the self-whitelist feature is enabled, the contract sends back the received ETH to the sender using the low-level `transfer()` function. 

However, from [solidity docs](https://docs.soliditylang.org/en/v0.8.25/contracts.html#receive-ether-function),`transfer()` only forwards 2300 gas, which is insufficient for the recipient to execute any non-trivial logic in a `receive()` or `fallback` function. This can lead to a situation where the ETH transfer fails if the recipient is a contract that requires more than 2300 gas to process the transfer. As a result, the ETH could be locked in the `Whitelist` contract indefinitely, leading to a potential loss of funds for users who interact with the contract via multisig wallets or other smart contracts.

From the solidity docs:
>In the worst case, the receive function can only rely on 2300 gas being available (for example when send or transfer is used), leaving little room to perform other operations except basic logging. The following operations will consume more gas than the 2300 gas stipend:
>- Writing to storage
>- Creating a contract
>- Calling an external function which consumes a large amount of gas
>- Sending Ether


Also worthy to note that a similar bug was reported in the just concluded `Renzo` contest as seen here: https://github.com/code-423n4/2024-04-renzo-findings/issues/612

## Proof of Concept
The `Whitelist` contract includes a `receive()` function that handles ETH transfers for self-whitelisting: https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/Whitelist.sol#L65-L74

```solidity
receive() external payable {
    if (_isSelfWhitelistDisabled) {
        revert SelfWhitelistDisabled();
    }
    if (_isBlacklisted[_msgSender()]) {
        revert Blacklisted();
    }
    _addWhitelistedAddress(_msgSender());
    payable(_msgSender()).transfer(msg.value);
}
```

In this function, the contract sends back the received ETH to the sender using `transfer()`. However, `transfer()` only forwards 2300 gas, which is not enough for the recipient to execute any non-trivial logic in a `receive()` or `fallback` function. For instance, multisig wallets or other smart contracts that have a `receive()` function requiring more than 2300 gas will fail to receive the ETH, causing the transaction to revert.

To summarise:
1. **Self-Whitelist Process**: Users can self-whitelist by sending ETH to the `Whitelist` contract. The contract checks if self-whitelisting is enabled and if the sender is not blacklisted. If these conditions are met, the sender is added to the whitelist, and the received ETH is sent back to the sender.

2. **Gas Limitation with `transfer()`**: The `transfer()` function only forwards 2300 gas, which is sufficient for simple transfers but not for contracts that require more gas to execute their `receive()` or `fallback` functions. This limitation can cause the ETH transfer to fail if the recipient is a contract that needs more gas.

3. **Impact on Multisig Wallets and Smart Contracts**: If a user interacts with the `Whitelist` contract using a multisig wallet or another smart contract that has a `receive()` function requiring more than 2300 gas, the ETH transfer will fail. This will cause the transaction to revert, and the ETH will remain locked in the `Whitelist` contract.

4. **Permanent Lockup of Funds**: Since the `receive()` function uses `transfer()`, any failed transfer due to gas limitations will result in the ETH being locked in the contract. Users who interact with the contract via multisig wallets or other smart contracts will be unable to retrieve their ETH, leading to a potential loss of funds.

Let's consider a scenario:
1. Alice uses a multisig wallet contract to send 1 ETH to the `Whitelist` contract to self-whitelist.
2. The multisig wallet contract is the `msg.sender` and gets saved as the whitelisted address.
3. The `Whitelist` contract attempts to send back the 1 ETH to the multisig wallet using `transfer()`.
4. The multisig wallet has a `receive()` function that requires more than 2300 gas to execute.
5. The `transfer()` function fails due to insufficient gas, causing the transaction to revert.
6. The 1 ETH is now locked in the `Whitelist` contract, and Alice cannot retrieve it.

## Recommended Mitigation Steps
So as to avoid potential lockup of ETH in the `Whitelist` contract, replace the use of `transfer()` with `call()`. The `call()` function forwards all available gas, allowing the recipient contract to execute arbitrary logic in its `receive()` function.
