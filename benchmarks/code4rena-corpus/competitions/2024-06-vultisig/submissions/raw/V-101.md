# Vulnerability details

## Impact
The current check (`>`) means the `launch()` function cannot be called at the exact `launchTime`, only after it. Users might expect to launch exactly at `launchTime` but this will always revert.

## Vulnerability details
The [launch()](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOManager.sol#L187-L198) function is designed to initiate the launch of a project associated with a Uniswap V3 pool.
```solidity
function launch(address uniV3PoolAddress) external override {
        require(block.timestamp > _cachedProject[uniV3PoolAddress].launchTime, "LT");
        (uint160 sqrtPriceX96, , , , , , ) = IUniswapV3Pool(uniV3PoolAddress).slot0();
        require(_cachedProject[uniV3PoolAddress].initialPoolPriceX96 == sqrtPriceX96, "UV3P");
        address[] memory initializedPools = _initializedILOPools[uniV3PoolAddress];
        require(initializedPools.length > 0, "NP");
        for (uint256 i = 0; i < initializedPools.length; i++) {
            IILOPool(initializedPools[i]).launch();
        }

        emit ProjectLaunch(uniV3PoolAddress);
    }
```
However, the current implementation of the `launch()` function in the `ILOManager` contract uses [the following check](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOManager.sol#L188) to determine if the project can be launched:
```solidiy
require(block.timestamp > _cachedProject[uniV3PoolAddress].launchTime, "LT");
```
The condition `block.timestamp > _cachedProject[uniV3PoolAddress].launchTime` requires the block timestamp to be strictly greater than the `launchTime`. This means the function cannot be called at the exact `launchTime`, only in subsequent blocks. 

For example, if launchTime is set to `1620000000` (Unix timestamp), the function can only be called when `block.timestamp` is `1620000001` or later. This introduces an unnecessary `delay` and prevents precise timing for the launch event.

Users typically expect that if an event is scheduled for a specific time, they should be able to trigger it exactly at that time. If users attempt to call the function exactly at `launchTime` and it fails due to the `>` condition, it can lead to frustration.

## Recommended Mitigation Steps
Ensures the function can be called exactly at `launchTime` or later.
```diff
-   require(block.timestamp > _cachedProject[uniV3PoolAddress].launchTime, "LT");
+   require(block.timestamp >= _cachedProject[uniV3PoolAddress].launchTime, "LT");
```
