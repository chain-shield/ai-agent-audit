# Vulnerability details

When initializing a new project, _initUniV3PoolIfNecessary() is called which checks if the corresponding uniswap v3 pool has already been deployed and initialized, and if its not, deploy/ initialize the pool to a favorable price set by the project.

The problem is that anyone can deploy a pool for a set of tokens and feeTier via the uniswapV3Factory. 

An attacker can use this to grief a project by frontrunning their initProject call to deploy a uniswap v3 pool for the given set of tokens (and maybe all fee tiers) and also initialize it to set a price favorable to themselves but not favorable to the project.

## Impact
The result of this would be that either the project initialization would be DOS'ed or they would be forced to use an initial price set by the attacker, because a pool corresponding to a particular token pair can only be deployed once on uniswap (for each fee tier).

The project team would need to change their raise token and even then they could be attacked again.

Manual review

## Recommended Mitigation Steps
I cannot see a straightforward guaranteed solution for this. Either use a service like flashbots for initProject calls on ILOManager's frontend, or enforce that the project should have already deployed and initialized the uniswap pool and document the advisory of using flashbots.
