# Vulnerability details

After a pool has been launched, investors can call claim to get back the unlocked part of their liquidity along with any LP fees earned on that liquidity until then. 

*This is a complex issue, please read till the end.*

The function first calculates the claimable liquidity of the investor's based on the total liquidity unlocked from all the vesting schedules uptil now. 

liquidity2Claim = _claimableLiquidity()

```
    function _claimableLiquidity(uint256 tokenId) internal view override returns (uint128) {
        uint128 liquidityClaimed = _positionVests[tokenId].totalLiquidity - _positions[tokenId].liquidity;
        uint128 liquidityUnlocked = _unlockedLiquidity(tokenId);
        return liquidityClaimed < liquidityUnlocked ? liquidityUnlocked - liquidityClaimed : 0;
    }
```

Here, _unlockedLiquidity() just returns the total amount of liquidity unlocked for the position since the vesting start uptil now. Then we subtract any liquidity that was already claimed and return the remaining amount as liquidity2Claim. This means this would be a portion of the NFT position(tokenID)'s actual deposited liquidity.

Now back to the execution of claim() function. 

Now it calls the pool.burn function to burn exactly "liquidity2Claim" amount out of the whole position of this particular ILOPool in the uniswap v3 pool.

The burn function can be [seen here](https://github.com/Uniswap/v3-core/blob/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/UniswapV3Pool.sol#L517). 

It modifies the position and does a lot of operations to update the position info and returns amount0 and amount1 : the amount of token0 and token1 obtained from burning exactly "liquidity2Claim" out of the whole aggregated liquidity. These amounts are then added to tokensOwed0 and tokensOwed1, and they can be collected later. 

What is relevant to the issue is this particular flow : burn() => [_modifyPosition()](https://github.com/Uniswap/v3-core/blob/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/UniswapV3Pool.sol#L319) => [_updatePosition()](https://github.com/Uniswap/v3-core/blob/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/UniswapV3Pool.sol#L379) => [position.update()](https://github.com/Uniswap/v3-core/blob/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/UniswapV3Pool.sol#L442) => [Position Library](https://github.com/Uniswap/v3-core/blob/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/libraries/Position.sol#L44)

Lets have a look at the logic in position.update :

```
   function update(
        Info storage self,
        int128 liquidityDelta,
        uint256 feeGrowthInside0X128,
        uint256 feeGrowthInside1X128
    ) internal {
        Info memory _self = self;

        uint128 liquidityNext;
        if (liquidityDelta == 0) {
            require(_self.liquidity > 0, 'NP'); // disallow pokes for 0 liquidity positions
            liquidityNext = _self.liquidity;
        } else {
            liquidityNext = LiquidityMath.addDelta(_self.liquidity, liquidityDelta);
        }

        // calculate accumulated fees
        uint128 tokensOwed0 =
            uint128(
                FullMath.mulDiv(
                    feeGrowthInside0X128 - _self.feeGrowthInside0LastX128,
                    _self.liquidity,
                    FixedPoint128.Q128
                )
            );
        uint128 tokensOwed1 =
            uint128(
                FullMath.mulDiv(
                    feeGrowthInside1X128 - _self.feeGrowthInside1LastX128,
                    _self.liquidity,
                    FixedPoint128.Q128
                )
            );

        // update the position
        if (liquidityDelta != 0) self.liquidity = liquidityNext;
        self.feeGrowthInside0LastX128 = feeGrowthInside0X128;
        self.feeGrowthInside1LastX128 = feeGrowthInside1X128;
        if (tokensOwed0 > 0 || tokensOwed1 > 0) {
            // overflow is acceptable, have to withdraw before you hit type(uint128).max fees
            self.tokensOwed0 += tokensOwed0;
            self.tokensOwed1 += tokensOwed1;
        }
    }
```

We can see that the first parameter "self" here is the state of position, which means the complete aggregate LP position of the ILOPool, [fetched here](https://github.com/Uniswap/v3-core/blob/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/UniswapV3Pool.sol#L386) and passed to the update function [here](https://github.com/Uniswap/v3-core/blob/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/UniswapV3Pool.sol#L442) and liquidityDelta here is the liquidity2Claim that we passed into the burn function from the ILOPool.claim call.


In position.update() here we first calculate the fees earned in terms of token0 and token1 on the whole "aggregated position of the ILOPool" because according to the uniswap pool, the ILOPool contract is actually the owner of the sum of all the ILOPool's investors' liquidity, we can see in [launch](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L296) function that the entire liquidity of all investors is deployed together with ILOPool as the position recipient. 

Uptil now, this context should be clear : "self.liquidity" corresponds to the whole liquidity position of the ILOPool (which means sum of liquidity deposited by all investors of the ILOPool), and we are calculating fees earned by this whole position and then adding it to the tokensOwed0 and tokensOwed1 at the last lines here (self.tokensOwed0 += tokensOwed0;).

Now lets move back to the ILOPool.claim() function.

After burning the required liquidity from the uniswap pool, the function now calculates fees earned by this particular investor's tokenID (which is investor's total liquidity but only a portion of the entire ILOPool's liquidity holdings):

```
  (, uint256 feeGrowthInside0LastX128, uint256 feeGrowthInside1LastX128, , ) = pool.positions(positionKey);
  uint256 fees0 = FullMath.mulDiv(
                                feeGrowthInside0LastX128 - position.feeGrowthInside0LastX128,
                                positionLiquidity,
                                FixedPoint128.Q128
                            ); 

```

Here, "positionLiquidity" is the entire remaining deposited liquidity of the single investor corresponding to the NFT tokenID, [see here](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L201).

So the amount and fees to be returned to the investor has been calculated. Now we need to collect these amounts from the uniswap pool. 

```
        // real amount collected from uintswap pool
        (uint128 amountCollected0, uint128 amountCollected1) = pool.collect(
            address(this),
            TICK_LOWER,
            TICK_UPPER,
            type(uint128).max,
            type(uint128).max
        );
```

In uniswap [pool.collect()](https://github.com/Uniswap/v3-core/blob/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/UniswapV3Pool.sol#L500) function, whenever type(uint128).max will be passed, it will collect the max possible amounts for both tokens ie. stored in the tokensOwed0 and tokensOwed1.

Note that these tokensOwed0 and tokensOwed1 have just been stored in the burn call within same claim() function. These amounts include the amounts obtained from burning specific investor liquidity and the **fees earned from the whole ILOPool's liquidity position**. Thus amount0Collected and amount1Collected now include burned liquidity amounts, and the fees earned by the whole ILOPool position which means it also includes fees that should be given to the other investors when they call claim() and their deserved fees gets calculated based on their own tokenID's feegrowth indexes. This would work correctly as part of these amounts uptil the current time have already been claimed under amount0Collected and amount1Collected and would keep sitting in the contract.

But this is not the case because of the following line at the end of the claim() function :

```
        address feeTaker = IILOManager(MANAGER).FEE_TAKER();
        // transfer fee to fee taker
        TransferHelper.safeTransfer(_cachedPoolKey.token0, feeTaker, amountCollected0-amount0);
        TransferHelper.safeTransfer(_cachedPoolKey.token1, feeTaker, amountCollected1-amount1);
```

The whole of the ILOPool position's earned fees (other than the claiming investor's amounts redeemed) get transferred to the feeTaker !!

This is wrong because these amounts belonged to the other investors who have not claimed these yet (based on the above context).

## Impact
Most of the investors will lose out on LP position fees everytime one of them calls ILOPool.claim() because whole of the earned uniswap fees gets transferred to the feeTaker. 

Since we can assume that every now and then one or the other investor would keep calling the claim() function, the LP fees will keep going out from the contract.

Additionally, after a point, this will cause a permanent DOS for all investors when they try to claim their unlocked liquidity because amounts to be transferred  are [calculated here](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L230), but the contract will not have these funds and would revert in TransferHelper.safeTransfer due to lack of token balances in the contract. 

All these amounts would have been already collected and sent out to the feeTaker.

## Recommended Mitigation Steps
Store the feeTaker's fees in a local variable separately inside the claim() function and only send these amounts to the feeTaker. The rest of the collected amount can keep sitting in the ILOPool contract and will be transferred later to other investors who claim liquidity.
