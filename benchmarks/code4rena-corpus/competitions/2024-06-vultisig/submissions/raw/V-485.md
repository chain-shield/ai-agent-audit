# Vulnerability details

## Summary

**Context:**
The variable _selfWhitelistDisabled is used by the owner of Whitelist.sol contract to enable and disable self whitelisting through the receive() function [here](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/Whitelist.sol#L65). 

**Root cause:**
During the deployment of the contract though, _selfWhitelistDisabled is not set to true to initially disable the self whitelist functionality. 

**Impact:**
This would allow anyone to self whitelist themselves once deployment is made but before the owner disables self whitelist. This could be used as an advantage over other users to have a guaranteed spot in the whitelist.

**Note: There is no deploy script for this in the [/script](https://github.com/code-423n4/2024-06-vultisig/tree/main/script) directory so we cannot assume that a batched call would've been made during deployment to also call the function [setIsSelfWhitelistDisabled()](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/Whitelist.sol#L154).**

## Proof of Concept

1. Team deploys the Whitelist.sol contract. Here we can see that _selfWhitelistDisabled is not set to true.

```solidity
File: Whitelist.sol
50:     constructor() {
51:         _maxAddressCap = 3 ether;
52:         _locked = true; // Initially, liquidity will be locked
53:     }
```

2. Before the owner calls the function [setIsSelfWhitelistDisabled()](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/Whitelist.sol#L154), an attacker frontruns it with a 0 value call to the receive function. Making a 0 value call would not raise any suspicions as well since the contract balance would be 0. The call goes through since:
 - Line 70 - The condition evaluates to false.
 - Line 73 - The caller is not blacklisted.  
 - Line 76 - The caller is added to the whitelist.
 - Line 78 - 0 msg.value transfer occurs.

```solidity
File: Whitelist.sol
69:     receive() external payable {
70:         if (_isSelfWhitelistDisabled) {
71:             revert SelfWhitelistDisabled();
72:         }
73:         if (_isBlacklisted[_msgSender()]) {
74:             revert Blacklisted();
75:         }
76:         _addWhitelistedAddress(_msgSender());
77:         
78:         payable(_msgSender()).transfer(msg.value);
79:     }
```

Here is a simple POC to prove 0 msg.value calls go through:
 - Add to Remix in sample file
 - Deploy the contract and read the value of x to be 0.
 - Call transact at the bottom without any msg.data.
 - Read the value of x to be 10.
```solidity
// SPDX-License-Identifier: GPL-3.0-only
pragma solidity 0.8.19;

contract ContractG {

    uint256 public x;

    receive() external payable {
        x = 10;
        payable(msg.sender).transfer(msg.value);
    }
}
```
