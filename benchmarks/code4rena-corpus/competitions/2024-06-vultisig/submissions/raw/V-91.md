# Vulnerability details

## Impact

The protocol using this oracle could face significant financial losses due to mispriced trades.

## Vulnerability Details

The combination of the `UniswapV3Oracle` contract and the `OracleLibrary` is crucial in determining price feeds based on Uniswap V3 Pool data. However, the reliance on certain Uniswap V3 pool mechanincs introduces potential vulnerabilities, particularly when it comes to the manipulation of `slot0` which is the most recent data point and can be manipulated easily via MEV bots and Flashloans with sandwich attacks.

The `UniswapV3Oracle` relies heavily on the state of `slot0` for its calculations as it contains critical data such as the current price, tick, and observation indices. Any manipulation of `slot0` directly affects the outputs of the oracle, leading to potential mispricing.

The function `getOldestObservationSEcondsAgo` determines how far back the oldest price observation was recorded. If an attacker can manipulate the pool to create misleading observations, this could affect the period calculation.

The `consult` function uses these observations to calculate a TWAP, which is supposed to smooth out short-term price volatility, however if observations have been manipulated, the TWAP itself becomse unreliable.

Aside from this, the `peek` function applies a static 5% slippage protection. This static value does not adapt to market conditions or levels of manipulation, making it potentially insufficient during high volatility or manipulation events.

## PoC

Consider the following scenario:

An attacker identifies the target Uniswap V3 pool (VULT/WETH) and the oracle using it
He takes out a large flash loan of VULT and/or WETH
Then he conducts large trades to manipulate the price in the VULT/WELTH pool, which directly affects the `slot0` data and the recorded observations. This will skew the dataset the oracle uses.
The `OracleLibrary.consult()` function retrieves the manipulated observations. The TWAP calculation is based on these skewed observations, resulting in an incorrect average price.
The `peek()` function applies a static 5% slippage, which may not cover the extend of manipulation. The attacker can then exploit the difference between the manipulated TWAP price and the actual market price. This would allow arbitrage opportunities from the discrepancy between the manipulated oracle price and other market prices.
Tha attacker then completes the trades to profit from these discrepancies, often completing the flash loan repayment and extracting the profit.

Manual review

## Recommended mitigation steps

Implement a dynamic slippage mechanism that adjusts based on market conditions and detected volatility. Also consider using multiple data sources or oracles to cross-verify prices and reduce dependency on a single source.
