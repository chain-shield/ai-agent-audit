# Vulnerability details

## Impact
In the `Whitelist::checkWhitelist()` function the `to` address is supposed to be checked for being whitelisted with this check:
```javascript
if (
                _allowedWhitelistIndex == 0 ||
                _whitelistIndex[to] > _allowedWhitelistIndex
            ) {
                revert NotWhitelisted();
            }
```
However, this statement only checks whether this whitelist index is smaller than the maximum allowed whitelist index, and whether the max index is not 0.

This is a critical issue, because this means that the `checkWhitelist()` call only checks if the whitelist is locked, the user is blacklisted, or whether they contributed the max amount, completely failing to check whether the address is whitelisted.


## Proof of Concept
To run the PoC paste the following code to the `describe("Checkwhitelist", function () {` branch of the `hardhat-vultisig/test/unit/Whitelist.ts` test file:
```
it.only("Doesn't revert when address is not whitelisted", async function () {
			const { whitelist, pool, otherAccount, batchedAccount, mockContract } =
				await loadFixture(deployWhitelistFixture);

			await whitelist.setVultisig(mockContract);

			await whitelist.setLocked(false);

			// Whitelist only one address - we'll see that call to checkWhitelist for batchedAccount DOESN'T revert with NotWhitelisted
			await whitelist.addWhitelistedAddress(otherAccount);
			await whitelist.setAllowedWhitelistIndex(1);
			const anotherAccount = await ethers.getSigners();

			await expect(
				whitelist.connect(mockContract).checkWhitelist(pool, batchedAccount, 0)
			).not.to.be.revertedWithCustomError(whitelist, "NotWhitelisted");
		});
```
and run `npx hardhat test` in the `hardhat-vultisig` directory. 

This test showcases that even though `batchedAccount` was not whitelisted, `checkWhitelist()` does not revert with `NotWhitelisted` custom error.

## Recommended Mitigation Steps
To mitigate this issue make the following change to the `checkWhitelist()` function:
```diff
if (
-               _allowedWhitelistIndex == 0 ||
+               _whitelistIndex[to] == 0 || 
                _whitelistIndex[to] > _allowedWhitelistIndex
            ) {
                revert NotWhitelisted();
            }
```
checking whether `_allowedWhitelistIndex == 0` is unnecessary, because if it wasn't set before this call, the `_whitelistIndex[to] > _allowedWhitelistIndex` will always fail.

The following note is only a recommendation, which is NOT required to mitigate this issue. 

Also, this concern in the `checkWhitelist()` function could be easily avoided by checking whether the `++_whitelistCount` value is greater than `_allowedWhitelistIndex` directly in `_addWhitelistedAddress`. The `addWhitelistedAddress()` and `addBatchWhitelist()` are admin functions, but this check would simply require that the admins changed the max whitelist index fist, and only then added an address to the whitelist:
```diff
+error MaxWhitelistIndexReached();

function _addWhitelistedAddress(address whitelisted) private {
+       uint nextIndex = ++_whitelistCount;

+       if (nextIndex > _allowedWhitelistIndex) {
+           revert MaxWhitelistIndexReached();
+       }

        if (_whitelistIndex[whitelisted] == 0) {
-           _whitelistIndex[whitelisted] = ++_whitelistCount;
+           _whitelistIndex[whitelisted] = nextIndex;
        }
    }
```
