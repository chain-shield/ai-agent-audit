# Vulnerability details

## Impact
[ILOPool.sol:buy#L141-L148](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L141-L148)
```solidity
if (balanceOf(recipient) == 0) {
    _mint(recipient, (tokenId = _nextId++));
    _positionVests[tokenId].schedule = _vestingConfigs[0].schedule;
} else {
    tokenId = tokenOfOwnerByIndex(recipient, 0);
}
```
The issue is that the code assumes that if the recipient already has a balance, they will only have one token. It retrieves the token ID using `tokenOfOwnerByIndex(recipient, 0)`, which returns the token ID at index 0 for the given recipient.

However, if the recipient holds multiple tokens, this code will always retrieve the token ID at index 0, ignoring any other tokens they may own. This can lead to incorrect behavior and updating the wrong position.

## Proof of Concept
* Assume a recipient `0xABC` already holds two tokens with IDs `1` and `2`.
* The `buy` function is called with the following parameters:
    * `raiseAmount`: 100 tokens
    * `recipient`: 0xABC`
* Inside the `buy` function, the code checks if the recipient already has a balance using `balanceOf(recipient)`.
* Since `0xABC` holds two tokens, `balanceOf(recipient)` returns a value greater than `0`.
* The code then retrieves the token ID using `tokenOfOwnerByIndex(recipient, 0)`, which returns token ID `1`.
* The code updates the position associated with token ID 1 by adding the `raiseAmount` to `_position.raiseAmount` and updating the liquidity.
* However, the position associated with token ID 2 remains unchanged, even though the recipient 0xABC intended to contribute to both positions.

## Recommended Mitigation Steps
Consider the possibility that a recipient may hold multiple tokens and handle that scenario accordingly.
```solidity
_mint(recipient, (tokenId = _nextId++));
_positionVests[tokenId].schedule = _vestingConfigs[0].schedule;
```
