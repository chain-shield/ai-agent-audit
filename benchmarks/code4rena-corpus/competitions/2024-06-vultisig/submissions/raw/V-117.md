# Vulnerability details

### Summary

The `VultisigWhitelisted` contract is designed to have a whitelisting mechanism for controlling token transfers. However, the method `VultisigWhitelisted::setWhitelistContract` allows the whitelist contract address to be reset to a non-zero address even after it has been set to zero. This can lead to serious security and trust issues in the protocol.

[VultisigWhitelisted.sol](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/extensions/VultisigWhitelisted.sol#L23)
```solidity
contract VultisigWhitelisted is Vultisig {

    ...

    /// @notice Ownable function to set new whitelist contract address
    function setWhitelistContract(address newWhitelistContract) external onlyOwner {
        _whitelistContract = newWhitelistContract;
    }

    /// @notice Before token transfer hook
    /// @dev It will call `checkWhitelist` function and if it's succsessful, it will transfer tokens, unless revert
    function _beforeTokenTransfer(address from, address to, uint256 amount) internal override {
        if (_whitelistContract != address(0)) {
            IWhitelist(_whitelistContract).checkWhitelist(from, to, amount);
        }
        super._beforeTokenTransfer(from, to, amount);
    }
}


```

### Impact

1. **Trust and Transparency Issues**: Users of the protocol may lose trust due to the potential reactivation of the whitelist mechanism. The whitelist functionality is supposed to be disabled permanently after being set to the zero address. Allowing it to be reset to a non-zero address contradicts this, reducing the protocol's transparency and reliability.
   
2. **Security Vulnerability**: If an attacker gains control over the `owner` role, they could reset the whitelist contract address to a malicious contract. This contract could implement the `checkWhitelist` function to steal or freeze user tokens during transfers. This poses a significant risk to the security of user funds.

Given that this issue affects the core token contract of the project, it is critical to address it to prevent potential exploits and maintain user confidence.

### Recommended Mitigation Steps

To mitigate this issue, it is recommended to modify the `setWhitelistContract` function to prevent it from resetting the whitelist contract address once it has been set to zero. Additionally, the whitelist contract address should be set initially in the constructor.
