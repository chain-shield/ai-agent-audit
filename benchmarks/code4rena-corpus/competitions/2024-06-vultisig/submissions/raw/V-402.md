# Vulnerability details

## Proof of Concept
The vulnerability in the `PeripheryPayments` contract lies in its handling of Ether transfers, particularly in the `receive` function and the `pay` function. Let's examine each aspect in detail:
```solidity
receive() external payable {
    require(msg.sender == WETH9, 'Not WETH9');
}
```
 The function intends to restrict Ether reception to only transactions originating from the WETH9 contract. It relies solely on `msg.sender` to verify the origin of the Ether. This can be problematic because `msg.sender` can be manipulated or spoofed under certain conditions.  An attacker could exploit this by sending Ether with a different `msg.sender` or by invoking the fallback function in a malicious contract to bypass this check.
The `pay` function handles both Ether and ERC20 token payments within the contract:
```solidity
function pay(
    address token,
    address payer,
    address recipient,
    uint256 value
) internal {
    if (token == WETH9 && address(this).balance >= value) {
        IWETH9(WETH9).deposit{value: value}(); // wrap only what is needed to pay
        IWETH9(WETH9).transfer(recipient, value);
    } else if (payer == address(this)) {
        TransferHelper.safeTransfer(token, recipient, value);
    } else {
        TransferHelper.safeTransferFrom(token, payer, recipient, value);
    }
}

```
The function distinguishes between paying with WETH9 (by depositing Ether into WETH9 and transferring tokens) and paying with other tokens or from another address. It does not explicitly verify the source of the Ether used to deposit into WETH9. It assumes that the contract's Ether balance (address(this).balance) is legitimate and intended for the WETH9 deposit.
## Example Scenario:
- An attacker identifies the `PeripheryPayments` contract's address and discovers that it accepts Ether through its `receive` function.
- The attacker deploys a malicious contract with a fallback function that sends Ether to the `PeripheryPayments` contract but manipulates the `msg.sender` to appear as if it's coming from WETH9.
- The malicious contract triggers its fallback function, sending a significant amount of Ether to the `PeripheryPayments` contract.
- Due to a flaw in the `receive` function's verification mechanism (`require(msg.sender == WETH9)`), the `PeripheryPayments` contract mistakenly accepts this Ether as if it came from WETH9.
## Impact
The `pay` function in `PeripheryPayments` checks its balance and attempts to deposit Ether into WETH9 based on the balance it perceives (`address(this).balance`). However, this balance has been artificially inflated due to the unauthorized Ether transfer. Consequently, the `pay` function may attempt to deposit more Ether into WETH9 than it should, exceeding the contract's actual available funds or disrupting its intended payment logic. If the pay function proceeds with the WETH9 deposit, it may result in unintended withdrawals or transfers of tokens associated with the deposited Ether.
This could lead to a situation where tokens intended for legitimate payments are redirected or withdrawn without authorization, causing financial loss or disruption to the contract's operations.

## Recommended Mitigation Steps
Instead of solely relying on `msg.sender`, implement additional checks or use cryptographic verification mechanisms to ensure that Ether is coming from the expected source (in this case, WETH9).
