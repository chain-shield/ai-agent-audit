# Vulnerability details

## Impact
The `whitelist` contract allows users to put themselves on the whitelist by transferring ether to the contract.
Once added to the whitelist, the ether is sent back to the user, and the ether is transmitted using the transfer method

```solidity
payable(_msgSender()).transfer(msg.value);
```
However, `transfer()` only forwards 2300 gas, which is not enough for the recipient to execute any non-trivial logic in a `receive()` or `fallback` function. For instance, it is not enough for Safes to receive funds, which require > 6k gas for the call to reach the implementation contract and emit an event.
If the user sends ether using contract account like a multisig or smart contract wallet that has a receive() function requiring >2300 gas,then the ether stays in the contract 
## Proof of Concept
Alice sends ether from her multisig wallet to the whitelist contract, after adding her to the whitelist, there is not enough gas to send the ether back and the ETH will be stuck in the contract

## Recommended Mitigation Steps
Use `call()` instead of `transfer()` to send ETH

```solidity
(bool success, ) = payable(msg.sender).call{value: msg.value}("");
require(success, "ETH transfer failed");
``` 
to avoid `reentrancy` you can set `gasLimit`
```solidity
(bool success, ) = payable(msg.sender).call{value: msg.value, gasLimit:25000}("");
require(success, "ETH transfer failed");
```
