# Vulnerability details

```UniswapV3Oracle.sol``` has a peek() function that is used to calculate the expected amount of eth required to purchase a "baseAmount" of VULT tokens. This is important because the protocol wants to store this ETH amount "contributed" and only allow upto a maxAddressCap of eth amount to be used by a single address in the whitelist period, in order to limit the VULT tokens acquired by any whitelisted address in the initial phase.  

Now lets see how this amount is calculated. 

```
function peek(uint256 baseAmount) external view returns (uint256) {
        uint32 longestPeriod = OracleLibrary.getOldestObservationSecondsAgo(pool);
        uint32 period = PERIOD < longestPeriod ? PERIOD : longestPeriod;
        int24 tick = OracleLibrary.consult(pool, period);
        uint256 quotedWETHAmount = OracleLibrary.getQuoteAtTick(tick, BASE_AMOUNT, baseToken, WETH);
        // Apply 5% slippage
        return (quotedWETHAmount * baseAmount * 95) / 1e20; // 100 / 1e18
    }
```

```peek()``` takes in a baseAmount which is the VULT tokens intended to be transferred to the buyer from the uniswap pool, during a purchase transaction. 

[OracleLibrary.getOldestObservationSecondsAgo(pool)](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/oracles/uniswap/uniswapv0.8/OracleLibrary.sol#L61) is used to find out difference between current block timestamp and the timestamp of the oldest observation recorded in the observations array of uniswap pool. And if this period is smaller than 30 minutes TWAP window, then we only query the price for this smaller time period instead of the full TWAP window, because it is assumed that there are no obervations recorded in the pool to fulfill the price queries of a time 30 minutes back in the past. 

The problem is that the longestPeriod returned by ```getOldestObservationSecondsAgo()``` depends on the cardinality of the pool, ie. the current size of the observations array.

See ```OracleLibrary.getOldestObservationSecondsAgo()``` ->

```
   function getOldestObservationSecondsAgo(address pool) internal view returns (uint32 secondsAgo) {
        (, , uint16 observationIndex, uint16 observationCardinality, , , ) = IUniswapV3Pool(pool).slot0();
        require(observationCardinality > 0, "NI");

        (uint32 observationTimestamp, , , bool initialized) = IUniswapV3Pool(pool).observations(
            (observationIndex + 1) % observationCardinality
        );

        // The next index might not be initialized if the cardinality is in the process of increasing
        // In this case the oldest observation is always in index 0
        if (!initialized) {
            (observationTimestamp, , , ) = IUniswapV3Pool(pool).observations(0);
        }

        secondsAgo = uint32(block.timestamp) - observationTimestamp;
    }
```

This first queries the current observationCardinality from pool.slot0 and then tries to read the oldest observation still present in the observations array.

Now this issue needs in depth understanding of [how the cardinality works](https://uniswapv3book.com/milestone_5/price-oracle.html#increasing-cardinality). 

When a pool is launched, the default cardinality is 1, ie. only 1 observation is stored in the observations array and it is repeatedly overwritten by the next values every time an observation is recorded (and the timestamp is also overwritten), that is once a block and when a swap happens. 

If the cardinality remains 1 or less than ~150 (ie. 30 minutes TWAP window that we are using), then the oldest period we have in the observations array will always be less than 30 minutes.

Now the problem is the cardinality does not automatically increase. It needs to be manually set by calling ```pool.increaseObservationCardinalityNext()``` which sets the cardinality value to a number which means the number of allowed observations in the observations array until the oldest one gets overwritten.

If it remains 1 or less than ~150 then the oldest observation will keep getting overwritten in every block that has at least one swap and hence getOldestObservationSecondsAgo will always return a period that is smaller than ~30 minutes. 

This is a disaster because it could mean there is only 1 observation and the TWAP price query keeps returning the price from this one block (until and unless there is a long sequence of blocks ~150 where no trade has happened in the pool, which is unlikely). This comes down to the TWAP becoming a spot price which can be easily manipulated.

An attacker could do the following : 
- See that the pool's cardinality is 1 or a smaller number far less than the safe ~150 block TWAP window
- Manipulate the price at the end of a block
- Make any small trade at the start of next block, this will store the price that existed at the end of the last block as an observation for the current block, note that this overwrites a previous observation
- If we have only 1 cardinality, then in the same transaction buy VULT tokens. The TWAP price queried will essentially be a manipulated 1-block spot price, and attacker could acquire a lot more VULT tokens than deserved (based on the same maxAddressCap)


## Impact
Because TWAP could essentially become a spot price oracle, an attacker (or even under normal operations), one could acquire a lot more total VULT tokens than deserved, which is unfavorable to all other users.

The TWAP does not work like a TWAP.

## Recommended Mitigation Steps
The solution is simple, as soon as the pool is launched, the admin needs to call [pool.increaseObservationCardinalityNext()](https://github.com/Uniswap/v3-core/blob/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/UniswapV3Pool.sol#L255) and set it to >150 so that there are actually observations that could be queried to get the accurate TWAP price our current TWAP window of 30 minutes demands.
