# Vulnerability details

## Impact
Denial of service for users of the protocol and stealing of user's asset. If a user intends to create new pool and deposit some funds in it then an attacker can frontrun the user's txns and capture the deposit amounts.

## Proof of Concept

https://vscode.dev/github/code-423n4/2024-06-vultisig/blob/main/src/ILOManager.sol#L79-L84

The `initILOPool` function is responsible for creating new `iloPoolAddress` It does this using the `Clones.cloneDeterministic` function.

The new `iloPoolAddress` depends solely upon the `_salt` parameter provided by the user. Once the user's create transaction is broadcasted, the `_salt` parameter can be viewed by anyone watching the public mempool.

This public readability of _salt parameter creates:

User broadcasts two transactions, first one to create a pool with XXXX as the salt and second one to deposit some ETH into the new pool.
The attacker views these pending transactions and frontruns them to create a `iloPoolAddress` for himself with same XXXX salt.
The new pool gets created for the attacker, the address of this pool will be same as what the user will be expecting for his pool.
The user's create pool transaction gets reverted but deposit transaction gets executed successfully. Hence the user deposited ETH in attacker's pool.
Being the owner of the pool the attacker simply withdraws the deposited ETH from the `iloPoolAddress`. This attack can be repeated again and again resulting in DoS for the `initILOPool` function.

## Tools Used

Manual Review

## Recommended Mitigation Steps

Consider making the upcoming pool address user specific by combining the salt value with user's address by dding `msg.sender` to the `salt` argument passed to `cloneDeterministic`
