# Vulnerability details

## Impact

In the current implementation of `ILOManager` smart contract, there is a function called `initProject()` that creates a project (with ILO pools in it in the future) and assigns to the uniV3 pool (projectId). The problem is that anybody can front-run the creation of the pool by creating the same one and making the tx of the sender to revert. 

## Proof of Concept

Currently the only requirement for the `initProject()` is that it has to be called after initialization:

https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOManager.sol#L57
```
 function initProject(InitProjectParams calldata params) external override afterInitialize() returns(address uniV3PoolAddress)
```

Inside of it `_cacheProject()` is called:

https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOManager.sol#L63
```
  _cacheProject(uniV3PoolAddress, params.saleToken, params.raiseToken, params.fee, params.initialPoolPriceX96, params.launchTime, refundDeadline);
```


`_cacheProject()` requires so that the project with the same params had not been attached to uniV3 pool:

https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOManager.sol#L134
```
require(_project.uniV3PoolAddress == address(0), "RE");
```

This creates a situation where anybody can front-run anyone by providing the same params for the pool initialization and make the initial sender's tx revert as at the time of the calling the `uniV3PoolAddress` will already be != address(0).

## Tools Used

Manual review.

## Recommended Mitigation Steps

Create some fees for this scenario / implement different mechanism to prevent from implementing this attack.
