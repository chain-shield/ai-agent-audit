# Vulnerability details

## Impact
The tick spacing designated to its respective fee must be checked to prevent creation of invalid ILOPools who will never be able to successfully deposit liquidity into the given pool. 

## Proof of Concept
The Uniswap v3 Factory currently holds 3 different tiers of fees: 3000, 500, 100.
Each one has its own respective tickSpacing, which gives valid ticks to choose as ranges to deposit liquidity on. 
Fee 3000: Initializable ticks must be % 60 = 0. (60, 120)
Fee 500: Initializable ticks must be % 200 = 0. (-600, -400)
Fee 100: Any ticks is initializable.            (45, 145)

Users who pass in the wrong LOWER & UPPER ticks, will have every attempt of ILOPool.launch() fail silently, since UniswapV3Pools dont throw an error message for this specific error.

Please note that the given examples are real values on the UniswapV3Factory on Ethereum mainnet. But other forks of Univ3, like Pancakeswap & others, use different fees, therefore different tick spacings are required.

## Tools Used
Manual analysis.

## Recommended Mitigation Steps
1) Make an external call to the uniswap v3 factory's mapping to see if the given fee exists as a value. (Since the AMM admins can change these, i would strongly oppose hardcoding these values.)
2) Passed LOWER & UPPER tick values must equal 0 with the returned number using a modulo against it.

uint24 mod = IUniswapV3Factory(FACTORY).feeAmountTickSpacing(param.fee)
require(mod  != 0); // Must exist.
require(param.TL % mod == 0 && param.TU % mod == 0);

This would ensure that the fee, together with the ticks are valid. This must be checkd uppon creation of the project or presale.
