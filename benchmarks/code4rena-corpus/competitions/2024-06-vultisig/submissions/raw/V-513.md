# Vulnerability details

## Impact
`amount0` and `amount1` returned by the following `UniswapV3Pool.burn` function would include swap fees that the LP is entitled to. The reasons are as follows:
- The `UniswapV3Pool.burn` function's comment states: `Can be used to trigger a recalculation of fees owed to a position by calling with an amount of 0`. When the LP has accumulated some swap fees over time, he can call the `UniswapV3Pool.burn` function with 0 as the `amount` input. In this case, `amount0` and/or `amount1` are/is such positive swap fees, and incrementing `position.tokensOwed0` and/or `position.tokensOwed1` by `amount0` and/or `amount1` causes `position.tokensOwed0` and/or `position.tokensOwed1` to include such swap fees.
- The comment of the `UniswapV3Pool.collect` function below states: `Does not recompute fees earned, which must be done either via mint or burn of any amount of liquidity`. When the `UniswapV3Pool.collect` function is called, parts or all of `position.tokensOwed0` and `position.tokensOwed1` are transferred to `recipient`. After the LP burns 0 `amount`, his recipient can still receive the accumulated swap fees that he is entitled to because `position.tokensOwed0` and `position.tokensOwed1` were incremented by the `amount0` and `amount1`, which include such positive swap fees, in his `UniswapV3Pool.burn` function call.

However, the following `claim` function incorrectly assumes that `amount0` and `amount1` returned by the `UniswapV3Pool.burn` function exclude swap fees that the LP is entitled to. After `amount0 += fees0` and `amount1 += fees1` are executed, `amount0` and `amount1`, which already include the swap fees, are further incremented by parts or full of such swap fees; this makes `amount0` and `amount1` higher than what they should be. When the `UniswapV3Pool.collect` function is called, `amountCollected0` and `amountCollected1`, which only include the swap fees once, that are the real token amounts collected can be less than such `amount0` and `amount1`, which incorrectly contain too much swap fee amounts, depending on `_project.platformFee` and `_project.performanceFee`. In this situation, the real token amounts collected are not enough to cover the transfers of `amount0` and `amount1` to `ownerOf(tokenId)` so the `claim` function call reverts. As a result, the investor loses the token amounts that he should be allowed to claim.

## Proof of Concept
The following steps can occur for the described scenario.
1. `_project.platformFee` and `_project.performanceFee` are set to 0 for the project.
2. Alice invests in an ilo pool of this project and mints a `tokenId`.
3. After this ilo pool is launched, multiple swaps occur in the corresponding Uniswap V3 pool.
4. After becoming fully vested, Alice calls the `claim` function for her `tokenId`.
	- `amount0` returned by the `pool.burn` function call equals `101e18`, which includes a swap fee of `1e18` accumulated for Alice.
	- When `amount0 += fees0` is executed, `amount0` is increased to `101e18 + 1e18 = 102e18`.
	- When the `pool.collect` function is called, the real `token0` amount collected is `101e18`.
	- Executing `TransferHelper.safeTransfer(_cachedPoolKey.token0, ownerOf(tokenId), amount0)` reverts because the `101e18` real `token0` amount collected is less than the `102e18` `amount0`.
5. Since Alice's `claim` function call reverts, she loses the token amounts that she should be able to claim.

## Recommended Mitigation Steps
The `claim` function can be updated as follows:
1. calculate and accumulate the fees for `feeTaker` according to `_project.platformFee` and `_project.performanceFee`;
2. transfer such fees to `feeTaker` instead of transferring `amountCollected0-amount0` and `amountCollected1-amount1` to `feeTaker`;
3. transfer `amountCollected0` and `amountCollected1` minus such fees to `ownerOf(tokenId)` instead of incrementing `amount0` and `amount1` by `fees0` and `fees1` and transferring such `amount0` and `amount1` to `ownerOf(tokenId)`.
