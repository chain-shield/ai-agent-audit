# Vulnerability details

## Impact

The protocol supports a self-whitelisting process where users can send `ETH` directly to `Whitelist` contract, and they will receive the `ETH` they transfered back.

[Whitelist.sol#L65-L74](https://github.com/code-423n4/2024-06-vultisig/blob/main/hardhat-vultisig/contracts/Whitelist.sol#L65-L74)
```solidity
    receive() external payable {
        if (_isSelfWhitelistDisabled) {
            revert SelfWhitelistDisabled();
        }
        if (_isBlacklisted[_msgSender()]) {
            revert Blacklisted();
        }
        _addWhitelistedAddress(_msgSender());
@>      payable(_msgSender()).transfer(msg.value);
    }
``` 

The problem here is that it uses `transfer()` function to send `ETH` back to the called which only uses `2300` gas units, and this is not sufficient for Smart Contract Wallets (like Safe Wallets) to handle the receiving of ETH, which will cause it to revert.

This will prevent users who have Smart Contract or Multisig wallets from whitelisting themselves.

## Proof of Concept

- Bob has a smart contract wallet and waits for the protocol to get launched.
- The protocol chooses to support self-whitelisting.
- Bob Sends ETH from his wallet to the `WhiteList` contract.
- Transaction reverts, and Bob does not know why this occurs.
- Whitelist users get filled out by other users who whitelisted themselves.
- Bob failed to be one of the whitelists, although he was one of the first people to call the function.

## Recommended Mitigation Steps
Uses `call()` instead of `transfer()`, to transfer all required gas.

> WhiteList::receive()
```diff
    receive() external payable {
        ...
-       payable(_msgSender()).transfer(msg.value);
+       (bool success, ) = payable(_msgSender()).call{value: msg.value}("");
+       require(success, "WhiteList: Transfering ETH back failed");
    }
```
