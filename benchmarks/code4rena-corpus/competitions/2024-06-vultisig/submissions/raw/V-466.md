# Vulnerability details

## Impact
The use of delegatecall inside a loop within a payable function (multicall) poses a significant security risk. If any of the called functions are payable or make use of msg.value, it can lead to unexpected behaviors or vulnerabilities such as reentrancy attacks or unintended ether transfers. This can compromise the integrity of the contract and potentially lead to loss of funds.

## Proof of Concept
Alice implements a new function in the core protocol that modifies user balances based on the msg.value received in transactions.
Eve notices the use of ``delegatecall`` within the ``multicall`` function, which retains the ``msg.value`` for each call in the loop.
Eve crafts a series of calls using the ``multicall`` function, ensuring that each call increases her balance by the original ``msg.value`` without actually transferring funds multiple times.
As a result, Eve can exploit this vulnerability to increase her balance multiple times within a single transaction, effectively stealing funds from the system.
```solidity
abstract contract Multicall is IMulticall {
    /// @inheritdoc IMulticall
    function multicall(bytes[] calldata data) public payable override returns (bytes[] memory results) {
        results = new bytes[](data.length);
        for (uint256 i = 0; i < data.length; i++) {
            (bool success, bytes memory result) = address(this).delegatecall(data[i]);

            if (!success) {
                // Next 5 lines from https://ethereum.stackexchange.com/a/83577
                if (result.length < 68) revert();
                assembly {
                    result := add(result, 0x04)
                }
                revert(abi.decode(result, (string)));
            }

            results[i] = result;
        }
    }
}
```
