# Vulnerability details

## Issue Description

A project pool, after being deployed, can enter two different states:

* **Launch**: If the pool sale's soft cap is reached and a refund is not triggered, the pool can be launched, and liquidity is deployed to UniV3.
* **Refund**: If a pool fails to reach the sale soft cap before the refund deadline, a refund can be triggered (by anyone). Buyers get back their Raise tokens by calling `ILOPool::claimRefund`, and the project admin gets refunded their Sale tokens by calling `ILOManager::claimRefund` (which invokes `ILOPool::claimProjectRefund` under the hood).

To understand the issue highlighted in this report, it is important to note that a single project can have multiple independent pools, which can be added by the project admin through `ILOManager::initILOPool`. The launch/refund state (explained above) is unique to each pool. For example, PoolA could get launched while PoolB fails to reach the soft cap and gets refunded.

The issue arises in projects with multiple pools (the intended use for projects), where some pools get launched, and some fail and must be refunded.

In this scenario, for the project admin to get their sales tokens back from the pools, they must invoke the `ILOManager::claimRefund` function:

```solidity
function claimRefund(
    address uniV3PoolAddress
)
    external
    override
    onlyProjectAdmin(uniV3PoolAddress)
    returns (uint256 totalRefundAmount)
{
    require(
        _cachedProject[uniV3PoolAddress].refundDeadline < block.timestamp,
        "RFT"
    );
    address[] memory initializedPools = _initializedILOPools[
        uniV3PoolAddress
    ];
    for (uint256 i = 0; i < initializedPools.length; i++) {
        //@audit could be DOSed if a single pool or more get launched and some fail, SALE tokens will get stuck in the unlaunched pools
        totalRefundAmount += IILOPool(initializedPools[i])
            .claimProjectRefund(_cachedProject[uniV3PoolAddress].admin);
    }
}
```

As shown, the function iterates over all the initialized pools and attempts to get a refund for each one. However, in the scenario where some pools have been launched, calling `ILOPool::claimProjectRefund` on them will revert because a refund wasn't triggered in those pools (as they were successfully launched). The `refundable` modifier will throw an error as shown below:

```solidity
function claimProjectRefund(
    address projectAdmin
) external override refundable OnlyManager returns (uint256 refundAmount) {
    return _refundProject(projectAdmin);
}
```

```solidity
modifier refundable() {
    if (!_refundTriggered) {
        // if ILO pool is launched successfully, we cannot refund anymore
        require(!_launchSucceeded, "PL");
        IILOManager.Project memory _project = IILOManager(MANAGER).project(
            _cachedUniV3PoolAddress
        );
        require(block.timestamp >= _project.refundDeadline, "RFT");

        _refundTriggered = true;
    }
    _;
}
```

The impact of this issue is that the `ILOManager::claimRefund` function can be DOSed, preventing the project admin from retrieving their Sale tokens from the unlaunched pools. The funds will remain stuck there indefinitely.

## Example Scenario

To illustrate this issue:

* Suppose we have a project with three pools: PoolA, PoolB, and PoolC.
* PoolA and PoolB fail to reach the soft cap and need to be refunded.
* PoolC successfully reaches the soft cap and is launched.
* When the project admin calls `ILOManager::claimRefund`, the function will iterate through PoolA, PoolB, and PoolC.
* Calling `ILOPool::claimProjectRefund` on PoolC will revert because it was successfully launched, causing the entire `ILOManager::claimRefund` function to fail.
* As a result, the admin cannot retrieve the Sale tokens from PoolA and PoolB, leaving them stuck.

## Impact

There is a risk of DOS in the `ILOManager::claimRefund` function if a project contains multiple pools and some get launched while others fail. In such cases, the project admin will be unable to get their Sale tokens refunded, leaving the tokens stuck inside the pool contracts.

## Recommended Mitigation

To address this issue, there are two viable options that can be added to the `ILOManager::claimRefund` function:

* Add a check to verify the status of each pool (launch/refund) and only invoke `ILOPool::claimProjectRefund` if a refund has been triggered for the specific pool (recommended).
* Use a try/catch block when invoking `ILOPool::claimProjectRefund` on each pool, so that reverts from launched pools do not prevent the refund of others.
