# Vulnerability details

 
 


 
 [Multicall](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/base/Multicall.sol) is a pattern to call several contract endpoints in one transaction, using `delegatecall`. A contract endpoint may implicitly assume that it is called in a single transaction, by looking at `msg.value`. Since the value is defined per transaction, calling the same endpoint twice in one `multicall` means that the same `msg.value` may be read several times, even though the value was only transferred once.

[ILOPool](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#) contract inherits from the [Multicall](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/base/Multicall.sol) contract  which provides a  [multicall(bytes[] calldata data)](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/base/Multicall.sol#L11) function. This function allows batching multiple function calls into a single transaction. Each subcall within `multicall` inherits the full `msg.value`, meaning that if a `payable` function like [claim( )](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L184) is called multiple times within the same multicall,  it will  process the same `msg.value` each time.



 However, passing a `tokenId` which holds multiple ETH deposits by calling the [claim( )](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L184) function  will use the same `msg.value` in each subcall.
 This results in multiple deposits being counted, leading to a total sum that is much larger than the actually deposited value, potentially up to the contract's entire ETH holdings , allowing an attacker to drain the contract.


## Impact
Contract holdings can be emptied as a malicious user can exploit the multicall function to repeatedly call [claim( )](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L184), each time using the full `msg.value`, leading to significant over-accounting of ETH deposits and potential depletion of the contract's funds 

## Proof of Concept
The [ILOPool](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#) contract's [claim()](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L184) function is payable and processes ETH deposits. When used within the multicall function, the same `msg.value` is reused for each subcall

An attacker can exploit this as follows : 

1. The attacker prepares a batch transaction using the multicall by calling the [claim()](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L184) function with 1 ETH.
2. By calling claim 5 times in a single `multicall`, the attacker effectively gets credited with 5 ETH worth of value in exchange for 1 ETH.
3. The attacker then calls [claimRefund()](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L350) to withdraw all the claims.

This results in the attacker withdrawing 5 ETH in total for the initial deposit of 1 ETH, effectively draining the contract.
