# Vulnerability details

## Vulnerability Details

During `buy`, the code calculates the liquidity shares associated with an investor. This calculation of liquidity shares (ie, Liquidity Delta) is dependent on the value of _cachePoolKey.token0 at the time of the buy. 

 CASE 1: It calculates the liquidity Delta if _cachePoolKey.token0 == RAISE_TOKEN in one way. In this case, it calls the `getLiquidityForAmount0` from the LiquidityAmounts library,and assign the return value of this function call to the liquidityDelta.
However, upon analyzing the `getLiquidityForAmount0`, it's found that the code first calculates for a certain variable called (uint256 intermediate), and then wrapped into the FullMath.mulDiv function. The calculation is 

intermediate = (SQRT_RATIO_X96 * SQRT_RATIO_UPPER_X96) / FixedPoint96.Q96 . 

It then proceeds to calculate the liquidityDelta as:

liquidityDelta = (raisedAmount * intermediate) / (SQRT_RATIO_UPPER_X96 - SQRT_RATIO_X96)





 CASE 2:  And if _cachePoolKey.token0 is any other token, it calculates the liquidity Delta in another way. It calls the `getLiquidityForAmount1` function on the LiquidityAmounts library. The calculation in this function is straightforward.

liquidityDelta = (raisedAmount * FixedPoint96.Q96) / (SQRT_RATIO_X96 - SQRT_RATIO_LOWER_X96)




Assume some usual values for the constants as following:
SQRT_RATIO_X96 =                sqrt(1.001) * 2^(96)
SQRT_RATIO_UPPPER_X96 =         sqrt(1.007) * 2^(96)
SQRT_RATIO_LOWER_X96 =          sqrt(0.997) * 2^(96)

raisedAmount =  500

With these values, and same rasedAmount used in both cases, it is seen that, 
for CASE 1:   liquidityDelta = 167_666;

for CASE 2:   liquidityDelta = 249_874;

Now, liquidityDelta for CASE 2 is 32.9% higher than that of CASE 1. 

## Impact
Given that, 2 investors, Alice and Bob both buy a token. 
Alice, being malicious, buys the token with 500 when she realizes that `_cachePoolKey.token0 != RAISE_TOKEN`. Bob, however, unbeknowst to him, buys the token with the same amount (500) when `_cachePoolkey.token0 == RAISE_TOKEN`. 

Although they both purchase the tokens with same amount( and since RAISE_TOKEN is what is transferred from users, same value too), Bob receives less liquidity shares than Alice. And Alice receives more than Bob. 

This can become catastrophic when Alice decides to pay less to receive same liquidity shares Bob paid more for. 
For example, with the assumed values. For a token Bob paid 500 to receive 167_666 liquidity shares. Alice can decide to pay 336, and she will receive the same 167_666 liquidity shares as Bob.

## Proof of Concept
Per the configuration in IILOPoolTest contract in the tests folder, drop this test into the ILOPool.t.sol file, and ran. First modify the configuration so that `_cachePoolKey.token0 == SALE_TOKEN`

```
function testSaleTokenAsToken0BuyLiquidity() external {
        deal(address(SALE_TOKEN), INVESTOR, 55000 ether);
        vm.prank(PROJECT_OWNER);
       IILOWhitelist(iloPool).batchWhitelist(_getListAddressFromAddress(INVESTOR));
        vm.prank(INVESTOR);
        IERC20(SALE_TOKEN).approve(iloPool, 1000000000 ether);
        (uint256 InvestorTokenId, uint256 InvestorLiquidity) = _buyFor(INVESTOR, SALE_START+1, 50000 ether);
        console.log("Investor liquidity Delta returned from buy if SALE_TOKEN == _cachePoolKey.token0 is: ", InvestorLiquidity);

```
After running this test, it is seen that, returned investor liquidity logged is
`5000000000000000000135`



Now, run the below test too for `RAISE_TOKEN == _cachePoolKey.token0` using the current configurations without modifying anything.


## Recommended Mitigation Steps

I recommend the protocol uses one method to calculate the associated liquidity delta of investors, so as to avoid discrepancies. Perhaps, since in the final transfer of funds from the msg.sender to the contract, the code transfers `RAISE_TOKEN`, it could use only the liquidity calculation associated with the RAISE_TOKEN. 
`https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L173`
I entreat the team to further analyse the recommendations, and properly test the fixes to handle other edge cases.
