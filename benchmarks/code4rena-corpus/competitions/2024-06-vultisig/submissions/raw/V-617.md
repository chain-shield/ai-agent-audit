# Vulnerability details

## Impact

- When an `ILOPool` is initialized with the `$VULT` token being the sale token, users can buy shares of the liquidity before the project launch (via `ILOPool.buy()`) then claim their `VULT` token via `ILOPool.claim()` where the claimed sale token will be burnt from the pool liquidity and sent to the user.

```js
function claim(uint256 tokenId)
        external
        payable
        override
        isAuthorizedForToken(tokenId)
        returns (uint256 amount0, uint256 amount1)
    {

        //....
                // transfer token for user
        TransferHelper.safeTransfer(_cachedPoolKey.token0, ownerOf(tokenId), amount0);
        TransferHelper.safeTransfer(_cachedPoolKey.token1, ownerOf(tokenId), amount1);

        //....
    }
```

The `VaultSigWhitelisted` token contract has a `_beforeTokenTransfer()` hook that checks if the recipient account (`to`) is whitelisted before transferring tokens to it:

```js
    /// @notice Before token transfer hook
    /// @dev It will call `checkWhitelist` function and if it's succsessful, it will transfer tokens, unless revert
    function _beforeTokenTransfer(
        address from,
        address to,
        uint256 amount
    ) internal override {
        if (_whitelistContract != address(0)) {
            IWhitelist(_whitelistContract).checkWhitelist(from, to, amount);
        }
        super._beforeTokenTransfer(from, to, amount);
    }
```

where:

```js
function checkWhitelist(
        address from,
        address to,
        uint256 amount
    ) external onlyVultisig {
        if (from == _pool && to != owner()) {
            // We only add limitations for buy actions via uniswap v3 pool
            // Still need to ignore WL check if it's owner related actions
            if (_locked) {
                revert Locked();
            }

            if (_isBlacklisted[to]) {
                revert Blacklisted();
            }

            if (
                _allowedWhitelistIndex == 0 ||
                _whitelistIndex[to] > _allowedWhitelistIndex
            ) {
                revert NotWhitelisted();
            }

            // // Calculate rough ETH amount for VULT amount
            uint256 estimatedETHAmount = IOracle(_oracle).peek(amount);
            if (_contributed[to] + estimatedETHAmount > _maxAddressCap) {
                revert MaxAddressCapOverflow();
            }

            _contributed[to] += estimatedETHAmount;
        }
    }
```

but as can be noticed, the check on whitlisting **is only done** if `from == _pool && to != owner()`, and this can easily bypassed if the claimer (which is a whitelisted account that has completed the whitlisting process) transfers his `$VULT` tokens to a blacklisted account after he claims his `$VULT` tokens as the check above will not be done.

**TL;DR** a blacklisted account can have `$VULT` tokens by buying from a whitelisted account then transferring tokens to him.

> **note:** another two issues were reported regarding the mechanism of the `checkWhitelist` that have similar introduction but differ in impact:
> a. `Whitelist._maxAddressCap` can be bypassed when claiming `$VULT` tokens.
> b. Investors might not be able to claim their `$VULT` sale tokens if priced high.

## Tools Used

Manual Review.

## Recommended Mitigation Steps

Update `checkWhitelist()` to check if the receiver through a direct transfer (not via ILOPool claim) is a whitelisted account.
