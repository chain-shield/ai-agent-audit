# Vulnerability details

## Issue Description

The `ILOPool::buy` function allows whitelisted users to buy pool liquidity shares before liquidity is launched to UniV3. To buy liquidity, they must pay a certain amount of RAISE tokens. Each whitelisted user has a maximum amount of RAISE tokens they can use, represented by `maxCapPerUser`. This limit is checked inside the function, as shown below:

```solidity
function buy(
    uint256 raiseAmount,
    address recipient
) external override returns (uint256 tokenId, uint128 liquidityDelta) {
    require(_isWhitelisted(recipient), "UA");
    require(
        block.timestamp > saleInfo.start && block.timestamp < saleInfo.end,
        "ST"
    );
    // check if raise amount over capacity
    require(saleInfo.hardCap - totalRaised >= raiseAmount, "HC");
    totalRaised += raiseAmount;

    require(totalSold() <= saleInfo.maxSaleAmount, "SA");

    // if investor already has a position, just increase raise amount and liquidity
    // otherwise, mint new nft for investor and assign vesting schedules
    if (balanceOf(recipient) == 0) {
        _mint(recipient, (tokenId = _nextId++));
        _positionVests[tokenId].schedule = _vestingConfigs[0].schedule;
    } else {
        tokenId = tokenOfOwnerByIndex(recipient, 0);
    }

    Position storage _position = _positions[tokenId];
    require(
        raiseAmount <= saleInfo.maxCapPerUser - _position.raiseAmount,
        "UC"
    );
    _position.raiseAmount += raiseAmount;

    ...
}
```

The issue that arises is that the cap is tracked on a per token (ERC721 position token) basis and not on the whitelisted user address (represented by `recipient` above). The following scenario can occur:

* Suppose RAISE token is ETH and `maxCapPerUser = 10 ETH`.
* Bob is a whitelisted user who calls the `ILOPool::buy` function to get liquidity by sending 10 ETH.
* Bob receives an NFT representing his position `tokenId = 5`, and as he already reached the buy cap, he shouldn't be able to buy again.
* Bob transfers his newly minted position NFT to another address (another wallet he owns).
* Bob calls `ILOPool::buy` function again. He is able to pass the check `balanceOf(recipient) == 0` as he doesn't hold any NFT in his current address (it was transferred in the step before), thus Bob gets minted another ERC721 position `tokenId = 6`.
* Because Bob with his new NFT, buys liquidity again by sending 10 ETH.
* Bob now owns two position NFTs the one with `tokenId = 6` in his first wallet and the second `tokenId = 5` that he transferred to the other wallet.
* Bob was able to bypass the `maxCapPerUser = 10 ETH` as he bought 20 ETH worth of liquidity, and he can repeat this process as many times as he wants.

In the above scenario, Bob, a whitelisted user, was able to bypass the maximum cap set for each user by repeatedly transferring the NFT he get minted to another address (in order to always have the `balanceOf(recipient) == 0` check be true). This goes against the intent of the project sale program.

## Impact

The impact of this issue is significant as it undermines the integrity of the sale process. By allowing users to bypass the `maxCapPerUser` limit, it creates an unfair advantage for certain users, allowing them to acquire more tokens than intended. This can lead to several problems:

* **Unfair Distribution**: The sale's intended cap per user is rendered ineffective, allowing certain users to accumulate a disproportionate amount of tokens.

* **Market Manipulation**: Users with excess tokens could potentially manipulate the market, affecting the token price and stability.

Manual review, VS Code

## Recommended Mitigation

To avoid this issue, consider the following options:

* Track the maximum cap for each recipient address instead of the minted position NFT.
* Add a state variable that tracks if a user has already minted an NFT position, instead of using `balanceOf(recipient)`, which can be manipulated.
* Disable position NFT transfers during the sale period.
