# Vulnerability details

### Description 

The protocol introduces a `self whitelisting` mechanism, which enables users to send funds to the `whitelist` contract to become whitelisted when this feature is enabled. This is also noted in the  [documentation](https://code4rena.com/audits/2024-06-vultisig).
```javascript
// Set allowed whitelisted index(Especially when self whitelist is allowed, anyone can just send ETH and get whitelisted slot and each slot will be assigned by an index called `whitelistIndex`.
```
The `whitelist` contract has a `receive` function that handles the `self whitelist` logic:
```javascript
    receive() external payable {
        if (_isSelfWhitelistDisabled) {
            revert SelfWhitelistDisabled();
        }
        if (_isBlacklisted[_msgSender()]) {
            revert Blacklisted();
        }
        _addWhitelistedAddress(_msgSender());
        payable(_msgSender()).transfer(msg.value);
    }
```
`receive()` triggers whenever a user sends ETH to the contract. Several checks are performed, such as ensuring that `self whitelisting` is enabled. If the user passes all these checks, they will be whitelisted and the funds will be sent back to them.

However, there is a problem with using `transfer()` instead of `call()`. 
```javascript
payable(_msgSender()).transfer(msg.value);
```
The `transfer` function only forwards 2300 gas. If a multisig or smart contract attempts to `self whitelist`, their `receive()` function, which requires more than 2300 gas, will fail to receive the funds. 

Ultimately the funds will be stuck inside the `whitelist` contract. 

### Tools Used
Manual review

### Recommendation
Use `call()` instead of `transfer()`
