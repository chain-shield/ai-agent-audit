# Vulnerability details

`Whitelist.sol: checkWhitelist()` is intended to check if a buyer is eligible for token transfers. However even if a user is not whitelisted he will still pass the whitelist check in this function.

## Impact
Possibly loss of funds for the protocol. Because `checkWhitelist()` is used in the `_beforeTokenTransfer` hook this means that non-whitelisted users will still be able to get token transfers.

## Proof of Concept
Here is the problematic if statement in `checkWhitelist()`:
```solidity
            if (_allowedWhitelistIndex == 0 || _whitelistIndex[to] > _allowedWhitelistIndex) {
                revert NotWhitelisted();
            }
```
The index for every whitelisted user is stored in the `_whitelistIndex` mapping. `_allowedWhitelistIndex` is used to determine how many users are allowed to be whitelisted. For example if the mapping contains indexes of 10 users but `_allowedWhitelistIndex` is 5 then only the first 5 whitelisted users are eligible. That's why we are comparing them.

The issue is that if the `to` address is not whitelisted the mapping will return zero and the check `_whitelistIndex[to] > _allowedWhitelistIndex` will be false and it will not revert like it should.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Check if `_whitelistIndex` mapping returns zero. This check should be sufficient because whitelisted user indexes start from 1 not 0.

```diff
-           if (_allowedWhitelistIndex == 0 || _whitelistIndex[to] > _allowedWhitelistIndex) {
+           if (_allowedWhitelistIndex == 0 || _whitelistIndex[to] == 0 || _whitelistIndex[to] > _allowedWhitelistIndex) {
                revert NotWhitelisted();
            }
```
