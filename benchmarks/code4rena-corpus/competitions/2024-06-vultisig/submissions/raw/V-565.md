# Vulnerability details

## Proof of Concept

The `ILOManager` currently allows:

* Projects to initialize by calling `initProject`.

* Project Admins to create multiple `ILOPool` instances for a project.

* The `launch` function to be called once the investor buying period is completed.

**Current implementation:**

```solidity

    function launch(address uniV3PoolAddress) external override {
        require(block.timestamp > _cachedProject[uniV3PoolAddress].launchTime, "LT");
        (uint160 sqrtPriceX96, , , , , , ) = IUniswapV3Pool(uniV3PoolAddress).slot0();
        require(_cachedProject[uniV3PoolAddress].initialPoolPriceX96 == sqrtPriceX96, "UV3P");
        address[] memory initializedPools = _initializedILOPools[uniV3PoolAddress];
        require(initializedPools.length > 0, "NP");
        for (uint256 i = 0; i < initializedPools.length; i++) {
@->         IILOPool(initializedPools[i]).launch();
        }

        emit ProjectLaunch(uniV3PoolAddress);
    }


```

Now Consider the following situation:

* Alice creates a project with 5 `ILOPool` instances, each having a soft cap of `80k ether`.

* During the sale period, 4 `ILOPool` instances successfully meet the soft cap.

* The last `ILOPool` ends with `75k ether` at the end of the sale period.

This leads to DoS in `launch` function as:

* Alice cannot update the soft cap.

* Alice cannot add the remaining 5k ether herself as buying is not allowed after the sale end time.

* Alice cannot launch the 4 successful Pools while refunding the last one.

The root cause is the use of a single `launch` function to launch all `ILOPool` instances together. If any one of the pools fails to meet its soft cap, the launch process is blocked for all pools.

## Recommended Mitigation Steps

Implement an additional function in `ILOManager` to launch an `ILOPool` individually.
