# Vulnerability details

## Impact
In the current implementation of the contract, there is no direct vulnerability. However, using the `safeMint` function instead of `mint` in the `launch` function could potentially lead to unexpected errors, protocol funds loss, and miscalculations. (or any other external call within the function)

## Proof of Concept
the `launch` function only set the `_launchSucceeded` to true at the end of the function:

if the protocol will use `_safeMint` instead than `mint`, or any other function that will include an external call to a different contract, unexpected errors may occur.
For instance, if one of the `_vestingConfigs` receivers, will be a contract implementing `onERC721Received` hook, he will be able to call by other wallets to the `ILOPool::claimRefund` function, if it is refundable, since the `_launchSucceeded` was not updated yet.
this will grant this receiver the same exact shares, however will change balances and might cause enexpected errors.

## Recommended Mitigation Steps
follow CEI and set `_launchSucceeded = true` at the beginning of the `launch` function, before any external calls or state changes occur. This ensures that once `_launchSucceeded` is set, functions like `claimRefund` cannot be called, thus reducing the risk of unintended interactions and vulnerabilities.
