# Vulnerability details



## Impact

The `Vultisig` contract fails to correctly validate whether the recipient of a token transfer is whitelisted. This oversight allows non-whitelisted addresses to receive tokens, potentially breaching security measures intended to restrict token distribution only to approved recipients. 

1. **Compliance Violation**: The failure to enforce whitelisting can result in violations of compliance requirements, especially in regulated environments.

## Proof of Concept

 Scenario: Failure to Properly Enforce Whitelisting in `Vultisig`

1. **Token Transfer Hook**: The `_beforeTokenTransfer` function is designed to validate transfers using the `checkWhitelist` function.

 ```solidity
   function _beforeTokenTransfer(address from, address to, uint256 amount) internal override {
       if (_whitelistContract != address(0)) {
           IWhitelist(_whitelistContract).checkWhitelist(from, to, amount);
       }
       super._beforeTokenTransfer(from, to, amount);
   }
 ```

2. **Whitelist Check**: The `checkWhitelist` function performs several validations but fails to properly check if the recipient (`to`) is whitelisted.

Link to the intended behaviour in the README 
https://code4rena.com/audits/2024-06-vultisig#:~:text=%2D%20Buyer%20whitelist%20index%20is%20within%20allowed%20index%20range(starting%20from%201%20and%20within%201%20~%20allowedWhitelistIndex%20%2D%20inclusive)

   >  /// @dev Revert if locked,
  > not whitelisted, 
 >blacklisted or 
>already contributed more than capped amount

 ```solidity
   function checkWhitelist(address from, address to, uint256 amount) external onlyVultisig {
       if (from == _pool && to != owner()) {
           if (_locked) {
               revert Locked();
           }

           if (_isBlacklisted[to]) {
               revert Blacklisted();
           }

           if (_allowedWhitelistIndex == 0 || _whitelistIndex[to] > _allowedWhitelistIndex) {
               revert NotWhitelisted();
           }

           uint256 estimatedETHAmount = IOracle(_oracle).peek(amount);
           if (_contributed[to] + estimatedETHAmount > _maxAddressCap) {
               revert MaxAddressCapOverflow();
           }

           _contributed[to] += estimatedETHAmount;
       }
   }
 ```

   **Issue**: The check `_whitelistIndex[to] > _allowedWhitelistIndex` incorrectly passes when `_whitelistIndex[to]` is `0`, which means `to` is not whitelisted.

3. **Failure Scenario**: If the `_whitelistIndex` of the recipient is `0`, the check `if (_allowedWhitelistIndex == 0 || _whitelistIndex[to] > _allowedWhitelistIndex)` incorrectly evaluates to `ok`, allowing the transfer to proceed even if `to` is not whitelisted.

## Recommended Mitigation Steps

To ensure proper validation of the whitelist and prevent unauthorized transfers, update the `checkWhitelist` function to correctly validate if the recipient (`to`) is whitelisted.



**Update `checkWhitelist` Function**:

   Modify the `checkWhitelist` function to include an additional check to ensure `to` is whitelisted.

   **Proposed Update**:

  ```solidity
   function checkWhitelist(address from, address to, uint256 amount) external onlyVultisig {
       if (from == _pool && to != owner()) {
           if (_locked) {
               revert Locked();
           }

           if (_isBlacklisted[to]) {
               revert Blacklisted();
           }

           if (_whitelistIndex[to] == 0 || _whitelistIndex[to] == 0 || _whitelistIndex[to] > _allowedWhitelistIndex ) {
               revert NotWhitelisted();
           }

           uint256 estimatedETHAmount = IOracle(_oracle).peek(amount);
           if (_contributed[to] + estimatedETHAmount > _maxAddressCap) {
               revert MaxAddressCapOverflow();
           }

           _contributed[to] += estimatedETHAmount;
       }
   }
  ```

   **Key Change**: Add `_whitelistIndex[to] == 0` to properly revert if `to` is not whitelisted.
