# Vulnerability details

### Summary

The `Vultisig` contract is supposed to represent a burnable ERC20 token as per the `project documentation`. However, the current implementation does not include any public methods to call the internal `_burn` function, leading to a discrepancy between the documentation and the actual smart contract code.

https://docs.vultisig.com/vultisig-token/usdvltx#the-vultisig-token-usdvult

```
The Vultisig Token $VULT
- 100,000,000 starting supply
- 80% in launch liquidity
- 20% allocated to an airdrop
- ERC20 with ERC777 extensions: approveAndCall() and _beforeTransferHook()
- Ownable, but not mintable (to set launch params)
- Burnable
```

```solidity
contract Vultisig is ERC20, Ownable {
    constructor() ERC20("Vultisig Token", "VULT") {
        _mint(_msgSender(), 100_000_000 * 1e18);
    }

    function approveAndCall(address spender, uint256 amount, bytes calldata extraData) external returns (bool) {
        // Approve the spender to spend the tokens
        _approve(msg.sender, spender, amount);

        // Call the receiveApproval function on the spender contract
        IApproveAndCallReceiver(spender).receiveApproval(msg.sender, amount, address(this), extraData);

        return true;
    }
}
```

### Impact

1. **Functionality Mismatch**: Users and developers relying on the project documentation may expect to have the ability to `burn` tokens. The absence of this functionality in the contract can cause confusion and mistrust.
2. **Reduced Token Utility**: Burning tokens is a critical feature for managing token supply and implementing various tokenomics strategies. The lack of this feature can limit the token's utility and flexibility.

### Severity

**Medium**: While this issue does not pose a direct security threat, it significantly affects the usability and transparency of the token as described in the project documentation.

### Recommended Mitigation Steps

To resolve this issue, there are two potential approaches:

1. **Update the Documentation**: If the intention is not to support token burning, the project documentation should be revised to remove any references to this functionality.

2. **Implement Token Burning Functionality**: If token burning is a desired feature, the contract should inherit from `ERC20Burnable` and implement the necessary methods to support burning tokens. 

Revised implementation using `ERC20Burnable`:

```solidity
abstract contract ERC20Burnable is Context, ERC20 {
    using SafeMath for uint256;

    function burn(uint256 amount) public virtual {
        _burn(_msgSender(), amount);
    }

    function burnFrom(address account, uint256 amount) public virtual {
        uint256 decreasedAllowance = allowance(account, _msgSender()).sub(amount, "ERC20: burn amount exceeds allowance");

        _approve(account, _msgSender(), decreasedAllowance);
        _burn(account, amount);
    }
}

contract Vultisig is ERC20Burnable, Ownable {
    constructor() ERC20("Vultisig Token", "VULT") {
        _mint(_msgSender(), 100_000_000 * 1e18);
    }

    function approveAndCall(address spender, uint256 amount, bytes calldata extraData) external returns (bool) {
        // Approve the spender to spend the tokens
        _approve(msg.sender, spender, amount);

        // Call the receiveApproval function on the spender contract
        IApproveAndCallReceiver(spender).receiveApproval(msg.sender, amount, address(this), extraData);

        return true;
    }
}
```

### Explanation

- **Inheritance from `ERC20Burnable`**: The `Vultisig` contract now inherits from `ERC20Burnable`, enabling the burning functionality.
- **Public Burn Methods**: The `ERC20Burnable` contract includes the `burn` and `burnFrom` methods, allowing users to burn their tokens or burn tokens from an allowance, respectively.
