# Vulnerability details

## Impact
The `getTickAtSqrtRatio` function in `TickMath.so`l aims to compute the tick corresponding to a given square root price. While the code implements a binary search-like approach to achieve this, there's a subtle yet significant bug.

**The Bug:**
The issue lies in the final comparison used to determine whether `tickHigh` or `tickLow` is the correct tick: [TickMath.sol#L203-L208](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/oracles/uniswap/uniswapv0.8/TickMath.sol#L203-L208)
```solidity
tick = tickLow == tickHi
    ? tickLow
    : getSqrtRatioAtTick(tickHi) <= sqrtPriceX96
        ? tickHi
        : tickLow;
```
The code checks if `getSqrtRatioAtTick(tickHi)` is less than or equal to `sqrtPriceX96`. However, the logic should be reversed. If `getSqrtRatioAtTick(tickHi)` is less than or equal to `sqrtPriceX96`, it implies that `tickHi` is too low, and we should return `tickLow` instead.

**Why this is a bug:**
This incorrect comparison can lead to returning a tick that's one step too high, causing inaccuracies in subsequent calculations that rely on this function.

## Proof of Concept
How the bug manifests
   1. **Scenario:** Imagine `sqrtPriceX96` falls between the square root prices represented by `tickLow` and `tickHi`.
   2. **Bugged Behavior:** The code might incorrectly return `tickHi` even if `getSqrtRatioAtTick(tickHi)` is smaller than `sqrtPriceX96`. This happens because it's checking for `<=` instead of `>`.

## Recommended Mitigation Steps
reverse the comparison in the final conditional statement:
```solidity
tick = tickLow == tickHi
    ? tickLow
    : getSqrtRatioAtTick(tickHi) > sqrtPriceX96 // Corrected comparison
        ? tickHi
        : tickLow;
```
By changing `<=` to `>,` we ensure that if `getSqrtRatioAtTick(tickHi)` is greater than `sqrtPriceX96`, we return `tickHi` (as it's a closer match). Otherwise, we return `tickLow.`
