# Vulnerability details

## Impact
Inside the `ILOVest.sol::_validateVestSchedule` there isn't a proper validation for overlapping, there can also be a case when someone enters a config with an `end` timestamp being less than the `start` time and this will lead to underflow when calculating the `ILOPool.sol::_unlockedLiquidity` unlocked liquidity.

Overlapping Vesting and vesting with an `end` timestamp less than the `start` and can lead to getting rewards earlier than the vested

## Proof of Concept
To reproduce this create a regular project and set the linear vest configs to an array similar to this

```javascript
uint64 constant VEST_START_0 = 1717693200; // Thu Jun 06 2024 17:00:00 GMT+0000
uint64 constant VEST_END_0 = 1717779600; // Fri Jun 07 2024 17:00:00 GMT+0000
uint64 constant VEST_START_1 = 1717779600; // Sat Jun 07 2024 17:00:00 GMT+0000
uint64 constant INVALID_VEST_START_2 = VEST_START_0 + 800;
uint64 constant INVALID_VEST_END_2 = VEST_START_1 + 400;
uint64 constant INVALID_VEST_START_3 = VEST_START_1 + 800;
uint64 constant INVALID_VEST_END_3 = VEST_START_0 + 400;

// VL0-VL1, VL1-VL0, VL0+ - VL1+, VL1++-VL0+
IILOVest.LinearVest[] memory linearVestConfigs = new IILOVest.LinearVest[](4);
linearVestConfigs[0] = IILOVest.LinearVest({
    shares: 3000, // 30%
    start: VEST_START_0,
    end: VEST_END_0
});
linearVestConfigs[1] = IILOVest.LinearVest({
    shares: 4000, // 40%
    start: VEST_START_1,
    end: VEST_START_0
});
linearVestConfigs[2] = IILOVest.LinearVest({
    shares: 1500, // 15%
    start: INVALID_VEST_START_2, // VEST_START_0 + 800
    end: INVALID_VEST_END_2 // VEST_START_1 + 400
});
linearVestConfigs[3] = IILOVest.LinearVest({
    shares: 1500, // 15%
    start: INVALID_VEST_START_3, // VEST_START_1 + 800
    end: INVALID_VEST_END_3 // VEST_START_0 + 400
});

IILOVest.VestingConfig[] memory vestingConfigs = new IILOVest.VestingConfig[](1);
vestingConfigs[0] = IILOVest.VestingConfig({
    shares: 10000, // 100%
    recipient: address(0),
    schedule: linearVestConfigs
});
```

You will see that the pool is successfully initialized with this type of vest config, in other words, the `ILOVest.sol::_validateVestSchedule` didn't manage to validate the config.

Next, invest in the pool and launch it.
You can warp to a time in a vesting period with an `end` less than the `start`, for example: `INVALID_VEST_START_3 + 10`.
Now when you call a function from `ILOPool.sol` that invokes `ILOPool.sol::_unlockedLiquidity`, the function gets inside

```javascript
else {
    liquidityUnlocked += uint128(
        FullMath.mulDiv(
            vest.shares * totalLiquidity, block.timestamp - vest.start, (vest.end - vest.start) * BPS
        )
    );
}
```

and calculates incorrect `liquidityUnlocked`.
This will trigger an underflow in the `vest.end - vest.start`
