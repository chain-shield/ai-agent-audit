# Vulnerability details

## Impact
This vulnerability could result in a Denial of Service (DoS) attack on the entire protocol, and potentially leading to financial losses and unexpected operational issues.

## Proof of Concept
The `initProject` function lacks parameter validation, allowing any user to call it with arbitrary parameters to initialize a new project. This oversight means that a malicious actor could front-run `initProject` calls with minimal base parameters, effectively monopolizing the creation of new projects and preventing legitimate launches.

```javascript
    /// @inheritdoc IILOManager
    function initProject(InitProjectParams calldata params) external override afterInitialize() returns(address uniV3PoolAddress) {
        uint64 refundDeadline = params.launchTime + DEFAULT_DEADLINE_OFFSET;

        PoolAddress.PoolKey memory poolKey = PoolAddress.getPoolKey(params.saleToken, params.raiseToken, params.fee);
        uniV3PoolAddress = _initUniV3PoolIfNecessary(poolKey, params.initialPoolPriceX96);
        
        _cacheProject(uniV3PoolAddress, params.saleToken, params.raiseToken, params.fee, params.initialPoolPriceX96, params.launchTime, refundDeadline);
        emit ProjectCreated(uniV3PoolAddress, _cachedProject[uniV3PoolAddress]);
    }
```
The poolKey is determined by the same two tokens, meaning that once a pool with this poolKey is generated, subsequent attempts to initialize a project with the same tokens will fail. This could render the entire protocol unusable and, in certain scenarios, lead to financial losses.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Implement validation in `initProject` to ensure that the `msg.sender` owns both tokens involved (at least one of each, for example). This restriction will restrict initialization privileges to project owners only, mitigating the risk of unauthorized initialization and potential DoS attacks.
