# Vulnerability details

## Impact
Project admins can create pools for their project by calling `ILOManager::initILOPool`, and passing in `params` argument, which specifies the initial pool values.

Once these pool values are verified, a new `ILOPool` is created for the project. The problem is that the tick values specified by the project admin are not verified correctly if it is in-range within the `initial pool price`.

The `initial pool price` is the ratio of the pool at the time the project was initialized. It is crucial that this price is within the range of the tick range specified by the caller, because the price calculations depend on it.

These price calculations include the amount of liquidity investors earn from the `raise tokens` sent and the amount of liquidity minted to the project.

A malicious project admin can manipulate these price calculations by specifying a tick range below the `initial pool price`, causing users to earn less tokens.

## Proof of Concept
When projects are initialized, the pool values are cached, including the `initialPoolPriceX96`, which represents the current ratio of the `Uniswap V3 pool`.

[ILOManager.sol#L142](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOManager.sol#L142)
```javascript
_project.initialPoolPriceX96 = initialPoolPriceX96;
```

The project admin can proceed to initialize `ILOPools`, where they can specify the tick range of the pool.

[ILOManager.sol#L88-L90](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOManager.sol#L88-L90)
```javascript
    uint160 sqrtRatioLowerX96 = TickMath.getSqrtRatioAtTick(params.tickLower);
    uint160 sqrtRatioUpperX96 = TickMath.getSqrtRatioAtTick(params.tickUpper);
    require(sqrtRatioLowerX96 < _project.initialPoolPriceX96 && sqrtRatioLowerX96 < sqrtRatioUpperX96, "RANGE");
```

The problem is with the check `require(sqrtRatioLowerX96 < _project.initialPoolPriceX96 && sqrtRatioLowerX96 < sqrtRatioUpperX96, "RANGE")`.

There is no verification that `_project.initialPoolPriceX96  < sqrtRatioUpperX96`. This is problematic, as it defeats the purpose of the `range` verification.

A malicious project admin can specify a `sqrtRatioUpperX96` that is far lower than `_project.initialPoolPriceX96`.

These values are initialized in the `ILOPool`, and used in calculations in `buy()`, `claim()`, `launch()` functions.

[ILOPool.sol#L72-L76](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOPool.sol#L72-L76)
```javascript
    TICK_LOWER = params.tickLower;
    TICK_UPPER = params.tickUpper;
    SQRT_RATIO_LOWER_X96 = params.sqrtRatioLowerX96;
    SQRT_RATIO_UPPER_X96 = params.sqrtRatioUpperX96;
    SQRT_RATIO_X96 = _project.initialPoolPriceX96;
```

This could impact investors, who may receive less liquidity for the amount of `raise tokens` they invest:

[ILOPool.sol#L155-L159](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOPool.sol#L155-L159)
```javascript
    if (RAISE_TOKEN == _cachedPoolKey.token0) {
        liquidityDelta = LiquidityAmounts.getLiquidityForAmount0(SQRT_RATIO_X96, SQRT_RATIO_UPPER_X96, raiseAmount);
    } else {
        liquidityDelta = LiquidityAmounts.getLiquidityForAmount1(SQRT_RATIO_LOWER_X96, SQRT_RATIO_X96, raiseAmount);
    }
```

Or cause users to earn less on claims

[ILOPool.sol#L242-L248](https://github.com/code-423n4/2024-06-vultisig/blob/main/src/ILOPool.sol#L242-L248)

## Recommended Mitigation Steps
Make the following changes to ensure that the prices are in-range

```diff
- require(sqrtRatioLowerX96 < _project.initialPoolPriceX96 && sqrtRatioLowerX96 < sqrtRatioUpperX96, "RANGE");
+ require(sqrtRatioLowerX96 < _project.initialPoolPriceX96 && _project.initialPoolPriceX96 < sqrtRatioUpperX96 && sqrtRatioLowerX96 < sqrtRatioUpperX96, "RANGE"); 
```
