# Vulnerability details

## Impact
A pool can be blocked from ever launching trapping all funds from users until the `refundDeadline` restriction is met due to an optimistic check as seen below.

```solidity
        (uint160 sqrtPriceX96, , , , , , ) = IUniswapV3Pool(uniV3PoolAddress).slot0();
        require(_cachedProject[uniV3PoolAddress].initialPoolPriceX96 == sqrtPriceX96, "UV3P");
```

This check is unsafe for several reasons. Firstly because this assumes that all `ILOPool` contracts will be for new pools, however the `ILOManager` allows creation of pools that could be already trading. If any user makes a trade on the pool and the price changes, unless the original `sqrtPriceX96` is reach again the pool will be unable to launch and all users funds will be trapped.

Secondly if a user wants to use this pool to bootstrap liquidity for their new protocol, if any user comes across tokens, for example from an airdrop or past sale. They can now add liquidity directly through Uniswap V3, and make trades to change the price of the `sqrtPriceX96` to effectively lock all raised funds in the contract indefinetly.


Important to note that because of [this](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOManager.sol#L90) check as seen below in `initILOPool()` a pool can also be prevented from ever deploying if this value falls below `sqrtRatioLowerX96`.

```solidity
require(sqrtRatioLowerX96 < _project.initialPoolPriceX96 && sqrtRatioLowerX96 < sqrtRatioUpperX96, "RANGE");
```

## Recommended Mitigation Steps

I recommend removing this optimistic check

```solidity
        (uint160 sqrtPriceX96, , , , , , ) = IUniswapV3Pool(uniV3PoolAddress).slot0();
        require(_cachedProject[uniV3PoolAddress].initialPoolPriceX96 == sqrtPriceX96, "UV3P");
```

This will allow pools to add liquidity in the defined range no matter what the state of the pool is.
