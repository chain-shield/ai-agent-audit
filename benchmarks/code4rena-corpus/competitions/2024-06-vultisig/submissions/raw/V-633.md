# Vulnerability details

## Impact
`initProject` in `ILOManager` is prone to Denial-Of-Service attacks, preventing users from creating new projects.

## Proof of Concept
Look at the `initProject` function:

```solidity
    function initProject(InitProjectParams calldata params) external override afterInitialize() returns(address uniV3PoolAddress) {
        uint64 refundDeadline = params.launchTime + DEFAULT_DEADLINE_OFFSET;

        PoolAddress.PoolKey memory poolKey = PoolAddress.getPoolKey(params.saleToken, params.raiseToken, params.fee);
        uniV3PoolAddress = _initUniV3PoolIfNecessary(poolKey, params.initialPoolPriceX96);
        
        _cacheProject(uniV3PoolAddress, params.saleToken, params.raiseToken, params.fee, params.initialPoolPriceX96, params.launchTime, refundDeadline);
        emit ProjectCreated(uniV3PoolAddress, _cachedProject[uniV3PoolAddress]);
    }
```

When a user tries to create a project, they would call this function. An attacker observes this transaction in the mempool and front-runs it. In the params, the attacker would keep the `params.saleToken, params.raiseToken, params.fee` same as the initial user's transaction. This would generate the same `poolKey`. This would also generate the same pool address that the user wanted. Note that this pool address is used as the key in the `_cachedProject` mapping. 

Here, the front-runner/malicious attacker has control over the `params.launchTime` and thus also over the `refundDeadline` value. They also become the `projectAdmin`:

```soldity
    function _cacheProject(
        address uniV3PoolAddress,
        address saleToken,
        address raiseToken,
        uint24 fee,
        uint160 initialPoolPriceX96,
        uint64 launchTime,
        uint64 refundDeadline
    ) internal {
        Project storage _project = _cachedProject[uniV3PoolAddress];
        require(_project.uniV3PoolAddress == address(0), "RE");

        _project.platformFee = PLATFORM_FEE;
        _project.performanceFee = PERFORMANCE_FEE;
        _project.admin = msg.sender; // attacker becomes admin
```

Hence, the pools will never be launched. The attack becomes even more feasible if the innocent user has already initialised the Uniswap pool, and thus the attacker would have to spend less on gas fees. 

This attack becomes extremely problematic, cause then the user would have to create another pool with different fees. There are only "1%, 0.3%, 0.05%, and 0.01% fee tiers" in Uniswap. So, if the attacker carries out this attack 4 times, then the project won't be able to launch itself with the intended raise token. They will have to change it. 

The attacker can keep doing this as long as they want hence inflating the severity.

## Tools Used
Manual review

## Recommended Mitigation Steps
Either make the `initProject` permissioned or instead of using the Uniswap pool address as the key in the `_cachedProject` mapping, take a hash of all the params in the `InitProjectParams` struct including the address for the project admin.
