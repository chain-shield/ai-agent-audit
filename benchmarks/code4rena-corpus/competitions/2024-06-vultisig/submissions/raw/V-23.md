# Vulnerability details

## Impact
Using tx.origin can lead to an unintended party gaining control of the contract. This happens because tx.origin refers to the original sender of the transaction, which can be different from msg.sender if the transaction is relayed through another contract. As a result, the contract might mistakenly assign ownership to an intermediary contract instead of the actual deployer.

## Proof of Concept
Original Constructor (Vulnerable):

constructor() {
    transferOwnership(tx.origin);
}

Explanation:
In this version, the ownership is transferred to tx.origin. If the contract deployment is proxied or relayed through another contract, tx.origin will point to the address that initially initiated the transaction, which might not be the intended owner.

Exploiting the Vulnerability:

An attacker deploys a relay contract.
The attacker uses this relay contract to deploy the ILOManager contract.
The tx.origin points to the attacker's address, not the actual deployer's address.
The attacker gains ownership of the ILOManager contract.
In this scenario, the owner of ILOManager becomes the attacker because tx.origin refers to the attacker's address who initiated the transaction through the Relay contract.

## Tools Used
Manual Review

## Recommended Mitigation Steps
To prevent this, use msg.sender instead of tx.origin in the constructor to ensure the correct owner is set. msg.sender accurately represents the address that directly interacts with the contract.

constructor() {
    transferOwnership(msg.sender);
}

In the secure version, msg.sender is used to transfer ownership. This ensures that the ownership is correctly assigned to the address that directly interacts with the contract.
