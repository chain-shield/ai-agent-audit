# Vulnerability details

## Vulnerability details
The `checkWhitelist` function in the `Whitelist` contract aims to enforce restrictions during the whitelist period. It checks if the sender (`from`) is the Uniswap V3 pool and the recipient (`to`) is not the owner. If these conditions are met, it proceeds to apply whitelist checks.

However, the check for the Uniswap V3 pool is flawed. It simply compares the sender's address to the stored `_pool` address. This is insufficient because the actual interaction with the pool occurs through the pool's contract, not directly from the pool's address.

As a result, anyone can bypass the whitelist check by directly interacting with the pool's contract to perform actions such as adding/removing liquidity or collecting fees. These actions are also subject to whitelist restrictions and should not be allowed during the whitelist period.

Furthermore, the exclusion of transactions where the recipient (`to`) is the owner could be exploited. If an attacker can manipulate the transaction to make it appear as if the owner is the recipient, they could bypass the whitelist entirely, regardless of the sender.

## Impact
This vulnerability allows attackers to bypass the whitelist restrictions and perform various actions on the Uniswap V3 pool during the whitelist period. This could lead to:

*   Unfair Token Distribution: Early buyers could acquire a disproportionate share of tokens through various pool interactions, potentially harming the project's tokenomics and community sentiment.
*   Market Manipulation: The unrestricted pool interactions could lead to artificial price manipulation, creating a false sense of demand and potentially misleading other investors.
*   Financial Losses: If the project relies on the whitelist to raise funds or control initial token distribution, this vulnerability could undermine those goals and lead to financial losses.

## Proof of Concept
1.  **Setup:**
    *   Deploy the `VultisigWhitelisted`, `Whitelist`, and `UniswapV3Oracle` contracts.
    *   Set up a Uniswap V3 pool for the VULT/ETH pair.
    *   Configure the `Whitelist` contract with the correct pool and oracle addresses.
    *   Add some initial liquidity to the pool.

2.  **Attacker Interaction:**
    *   The attacker interacts directly with the pool's contract to perform actions such as:
        *   Swapping ETH for VULT tokens using `swapExactInputSingle`.
        *   Adding liquidity to the pool using `mint`.
        *   Removing liquidity from the pool using `burn`.
        *   Collecting fees from the pool using `collect`.
    *   Since the attacker is interacting directly with the pool contract, the `checkWhitelist` function in the `Whitelist` contract is not triggered, or is bypassed due to the owner exclusion.
    *   The attacker successfully performs these actions without any whitelist restrictions.

3.  **Verification:**
    *   Check the attacker's VULT token balance and ETH balance. They should have changed according to the actions performed.
    *   Check the pool's liquidity and fee statistics. They should also reflect the attacker's actions.

This PoC demonstrates how the incorrect check for Uniswap V3 pool interactions and the potential owner manipulation allow attackers to bypass the whitelist and perform various actions on the pool freely.

## Recommended Mitigation Steps
1.  **Correct Pool Interaction Check:** Modify the `checkWhitelist` function to correctly identify interactions originating from the Uniswap V3 pool contract. This could involve checking the calldata or using a more robust method to verify the interaction source.
2.  **Remove or Secure Owner Exclusion:** Consider removing the exclusion for transactions where the recipient is the owner. If this exclusion is necessary, implement additional checks to ensure that the owner is not being impersonated or manipulated into participating in malicious transactions.
3.  **Implement Additional Whitelist Checks:** Explore adding more comprehensive whitelist checks for all relevant pool interactions, including adding/removing liquidity and collecting fees. This would ensure that all actions are restricted during the whitelist period, preventing any potential bypasses.
