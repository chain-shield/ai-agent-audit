# Vulnerability details

## Impact
Selfwhitelisted logic allows anyone to be whitelisted.
Combining this with a hardcap for whitelists could go wrong and restrict legit users.
Selfwhitelisted logic can be maliciously used to spam addresses, which would result in temporary DoS if the allowedWhitelistedIndex is exceeded. Until the limit is increased again.


## Proof of Concept
As per the ReadMe documentation:

> -Set allowed whitelisted index(Especially when self whitelist is allowed, anyone can just send ETH and get whitelisted slot and each
> slot will be assigned by an index called `whitelistIndex`.  There
> could be some suspicious actors so owner can add those addresses to
> the blacklist. In this case, the total whitelisted addresses will be
> `whitelistCount - blacklistedCount`. So owner can increase
> allowedWhitelistedIndex by blacklistedCount to make sure that always 1k whitelisted slots are secured.)

This would simply not work. 
Even if some of those are filtered out by blacklisting and increasing the limit again, it would be a never ending cycle.
If someone wants to he can always backrun the transaction for increasing the limit with the blacklistedCount and spam validations for addresses that would not be used, in order to block DoS the whitelist.


## Tools Used
Manual review

## Recommended Mitigation Steps
Don't combine selfwhitelist with allowedWhitelistedIndex logic. If selfwhitelist is allowed, there should not be a limit for whitelisting. It just restricts legit users.
