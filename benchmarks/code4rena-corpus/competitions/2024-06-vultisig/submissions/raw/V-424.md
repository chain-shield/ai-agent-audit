# Vulnerability details

## Issue Description

A project pool, after being deployed, can enter two different states:

* **Launch**: If the pool sale's soft cap is reached and a refund is not triggered, the pool can be launched, and liquidity is deployed to UniV3.

* **Refund**: If a pool fails to reach the sale soft cap before the refund deadline, a refund can be triggered (by anyone). Buyers get back their Raise tokens by calling `ILOPool::claimRefund`, and the project admin gets refunded their Sale tokens by calling `ILOManager::claimRefund` (which invokes `ILOPool::claimProjectRefund` under the hood).

To understand the issue highlighted in this report, it is important to note that a single project can have multiple independent pools, which can be added by the project admin through `ILOManager::initILOPool`. The launch/refund state (explained above) is unique to each pool. For example, PoolA could get launched while PoolB fails to reach the soft cap and gets refunded.

The issue arises in projects with multiple pools (the intended use for projects), where some pools get launched, and some fail and must be refunded.

In this scenario, the project admin must invoke the `ILOManager::launch` function to launch the project pools:

```solidity
/// @inheritdoc IILOManager
function launch(address uniV3PoolAddress) external override {
    require(
        block.timestamp > _cachedProject[uniV3PoolAddress].launchTime,
        "LT"
    );
    (uint160 sqrtPriceX96, , , , , , ) = IUniswapV3Pool(uniV3PoolAddress)
        .slot0();
    require(
        _cachedProject[uniV3PoolAddress].initialPoolPriceX96 ==
            sqrtPriceX96,
        "UV3P"
    );
    address[] memory initializedPools = _initializedILOPools[
        uniV3PoolAddress
    ];
    require(initializedPools.length > 0, "NP");
    for (uint256 i = 0; i < initializedPools.length; i++) {
        //@audit could be DOSed if one pool doesn't reach softcap while others do
        IILOPool(initializedPools[i]).launch();
    }

    emit ProjectLaunch(uniV3PoolAddress);
}
```

The function iterates over all the initialized pools and attempts to launch each one. However, if some pools fail to reach the soft cap, calling `IILOPool::launch` on those pools will revert, causing the entire `ILOManager::launch` function to fail. This will prevent the successful pools from being launched.

The `IILOPool::launch` function, which checks the soft cap, will revert if the soft cap is not met as shown below:

```solidity
function launch() external override OnlyManager {
    require(!_launchSucceeded, "PL");
    // when refund triggered, we cannot launch pool anymore
    require(!_refundTriggered, "IRF");
    // make sure that soft cap requirement is met
    require(totalRaised >= saleInfo.softCap, "SC");
    
    //...
}
```

The impact of this issue is that the `ILOManager::launch` function can be DOSed, preventing the project admin from launching any pools if even one pool fails to meet the soft cap.

## Example Scenario

To illustrate this issue:

* Suppose we have a project with three pools: PoolA, PoolB, and PoolC.
* PoolA and PoolB successfully reach the soft cap and are ready to be launched.
* PoolC fails to reach the soft cap and cannot be launched.
* When the project admin calls `ILOManager::launch`, the function will iterate through PoolA, PoolB, and PoolC.
* Calling `IILOPool::launch` on PoolC will revert because it did not meet the soft cap, causing the entire `ILOManager::launch` function to fail.
* As a result, the admin cannot launch PoolA and PoolB even if they meet all the launch conditions.

## Impact

There is a risk of DOS in the `ILOManager::launch` function if a project contains multiple pools and some fail to reach the soft cap. In such cases, the project admin will be unable to launch any pools, leaving the successfully funded pools in a state where they cannot be deployed to UniV3.

Manual review, VS Code

## Recommended Mitigation

To address this issue, there are two viable options that can be added to the `ILOManager::launch` function:

* Add a check to verify the status of each pool (soft cap met or not) and only invoke `IILOPool::launch` if the specific pool has met the launch conditions (recommended).
* Use a try/catch block when invoking `IILOPool::launch` on each pool, so that reverts from pools that did not meet the soft cap do not prevent the launch of other pools.
