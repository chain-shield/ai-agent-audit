# Vulnerability details

When the pool is just launched, there are no price observations, which means that the price will be calculated as the initially fed value of sqrtPriceX96. As the trading activity starts, the spot price will be very volatile. The TWAP will be meaningless and prices returned will be highly manipulatable. This is because the twap period will depend on the time difference between block.timestamp and the  oldest observation present in the Observations array of Uniswap V3 Pool. 

Even after the first TWAP window has passed, and there are enough recorded observations to be able to calculate a meaningful 30-minute TWAP price, it will be using the haphazard prices (that were recorded before in the volatile trading activity) to find the average price. 

This means at least for the first TWAP window, as well as the following few hours, the TWAP prices returned will be unreliable and some users might be allowed to buy more than deserved amount of VULT tokens because of the calculation in UniswapV3Oracle.peek(), at the expense of other less sophisticated users buying from the pool.


## Impact

This will lead to a token sale where early hour participants with knowledge of sophisticated manipulation strategies can get an edge over the max VULT that can be acquired with the same amount of ETH, which they can later sell for profit.

Token sale opportunity should be equal to all users based on an accurate and reliable TWAP price. Additionally, users who acquire more than deserved VULT tokens via manipulation can become disproportionate holder of VULT. 

## Proof of Concept

Here, longestPeriod is the time difference between the current timestamp and the oldest recorded observation still present in the observations array(see [OracleLibrary.getOldestObservationSecondsAgo()](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/oracles/uniswap/uniswapv0.8/OracleLibrary.sol#L75)). When it is smaller than 30 minutes, the consult() function will use this smaller duration. These conditions are true until the first TWAP window after launch passes.

```
    function peek(uint256 baseAmount) external view returns (uint256) {
        uint32 longestPeriod = OracleLibrary.getOldestObservationSecondsAgo(pool);
        uint32 period = PERIOD < longestPeriod ? PERIOD : longestPeriod;
        int24 tick = OracleLibrary.consult(pool, period);
        uint256 quotedWETHAmount = OracleLibrary.getQuoteAtTick(tick, BASE_AMOUNT,      baseToken, WETH);
        // Apply 5% slippage
        return (quotedWETHAmount * baseAmount * 95) / 1e20; // 100 / 1e18
    }
```

Thus, the TWAP returned will essentially be a volatile spot price for the initial duration.

## Recommended Mitigation Steps
To counter this, after a pool is initialized, the price derived from initial liquidity needs to be maintained for the whole of the first TWAP window, ie. for the first 30 minutes after the pool is launched. This will ensure that on the first swap, a reliable price gets recorded as an observation for the whole twap window, based on which a reliable twap price can be guaranteed for the early period, even for the first participants.

This can be done by only allowing the VULT token transfers to be unlocked after 30 minutes of the pool's launch (see [pool](https://github.com/Uniswap/v3-core/blob/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/UniswapV3Pool.sol#L276)). After this, the first swap will record an observation such that the initial liquidity reserves' price was maintained for the first 30 minutes ie. the full TWAP window. 

Add these lines to Whitelist.sol:setLocked() function, any buying transactions will revert in _beforeTokenTransfer => checkWhitelist() before at least 30 minutes have passed since pool initialization. 

```
require(_pool.observations[0].initialized, "Pool not initialized");
require(block.timestamp > _pool.observations[0].blockTimestamp + 30 minutes, "TWAP window has not passed");
```
