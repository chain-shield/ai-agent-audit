# Vulnerability details

## Impact
The idea of Whitelist for Vultisig is to restrict access for purchasing a token via Pool for some period of time. 
But actual whitelisting functionality in Whitelist implemented incorrectly and will open access for everyone.
Also, because of this vulnerability **maxAddressCap** protection also wouldn't work, because there is no issues for any user to buy tokens for other their addresses.

While it's hard to evaluate how critical it can be for a contract, but such issue breaks Main invariants described in the contract details. So it should be considered as an issue.

## Proof of Concept
1) Whitelist check validates existing users in whitelist array, and enable transaction for N amount of users by their index. To enable whitelist logic admin should put  **_allowedWhitelistIndex > 0**. But because index for a non existing address always will be 0 every user that not included in whitelist can bypass this check.

```
            if (_allowedWhitelistIndex == 0 || _whitelistIndex[to] > _allowedWhitelistIndex) {
                revert NotWhitelisted();
            }
```

2) The side effect of this issue also brings another vulnerability with **maxAddressCap**. Without working whitelist, such cap make no sense, because attacker can create multiple addresses and bypass it.
```
            uint256 estimatedETHAmount = IOracle(_oracle).peek(amount);
            if (_contributed[to] + estimatedETHAmount > _maxAddressCap) {
                revert MaxAddressCapOverflow();
            }

            _contributed[to] += estimatedETHAmount;
```


## Tools Used
Manual

## Recommended Mitigation Steps
Add check for 0 index.
```
            if (_allowedWhitelistIndex == 0 || _whitelistIndex[to] == 0 || _whitelistIndex[to] > _allowedWhitelistIndex) {
                revert NotWhitelisted();
            }
```
