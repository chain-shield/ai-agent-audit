# Vulnerability details

## Impact
The logic in the _unlockedLiquidity function, where it breaks out of the loop if the current timestamp is less than the start of a vesting period (vest.start), 
```
  if (block.timestamp < vest.start) {
                break;
            }
```
incorrectly calculates liquidity.This is because the loop termination upon encountering a vest that has not yet started assumes that all subsequent vests are also not started. However, when vests are not strictly ordered by their start times, a later vest in the array might have already started, and its liquidity would then be incorrectly excluded from the calculation.This could lead to scenarios where liquidity that should be unlocked (because the vesting period has started for subsequent entries in the vesting schedule) is not counted, thus providing inaccurate or unintended results the implementation could miss unlocking liquidity for vests that should be unlocked but are positioned after a vest that has not yet started.

## Proof of Concept
- Consider a scenario where vesting schedules are not in chronological order.

- For example, a vesting schedule with a later start date appears before one with an earlier start date in the array.

- Deploy the ILOPool contract and initialize it with out-of-order vesting schedules.

- Attempt to calculate unlocked liquidity using the _unlockedLiquidity function.

- The function will break out of the loop upon encountering a vest that has not yet started, incorrectly excluding subsequent vests that should be unlocked.

## Tools Used
Manual

## Recommended Mitigation Steps;
- Modifying the loop to check each vest independently of the others
```
if (block.timestamp < vest.start) {
              continue++
            }

```
- Ensuring that the vesting schedule is always sorted by the start time before being processed
