# Vulnerability details

## Impact
As the current version of OracleLibrary.sol is [>=0.5.0](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/oracles/uniswap/uniswapv0.8/OracleLibrary.sol#L2) due to which any call that could lead to overflow and underflow will get reverted.
This happens because in solidity 0.8.0 checked is by default as mentioned in their [docs](https://docs.soliditylang.org/en/latest/control-structures.html#checked-or-unchecked-arithmetic)
This happens due to not implementing an unchecked block [OracleLibrary.sol#consult](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/oracles/uniswap/uniswapv0.8/OracleLibrary.sol#L14) could give a wrong value.
## Proof of Concept
**Scenario: Overflow**
- [tickCumulativesDelta](https://github.com/code-423n4/2024-06-vultisig/blob/cb72b1e9053c02a58d874ff376359a83dc3f0742/hardhat-vultisig/contracts/oracles/uniswap/uniswapv0.8/OracleLibrary.sol#L22): -1 (Assuming a negative delta for this example)
- period: block.timestamp (Positive integer)
Here's why overflow can occur
The calculation would be int24(-1 / block.timestamp). This results in a negative int24 value (let's say x).
The if statement checks if tickCumulativesDelta (which is 1 in this case) is negative and has a non-zero remainder after dividing by period. Since block.timestamp is positive, there will always be a remainder.
Due to the negative bias, the code attempts to decrement timeWeightedAverageTick (which has the value x from the calculation).
If -x is the minimum representable value for int24 (negative 2^23), decrementing it will cause an overflow and wrap around to the maximum positive value (2^23 - 1).
