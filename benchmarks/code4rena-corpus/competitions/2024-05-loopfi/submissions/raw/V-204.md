# Vulnerability details

## Impact
Users can lose their  `ETH`. contract can be drained.
Users can get a denial of services if they can not withdraw their deposits `ETH` .


## Proof of Concept

if users deposited  `ETH` , a malicious user can deposit almost the same amount of `WETH` and their `balances` will be mapped with `ETH` address not `WETH` token address in this line https://github.com/code-423n4/2024-05-loop/blob/40167e469edde09969643b6808c57e25d1b9c203/src/PrelaunchPoints.sol#L191

The malicious user can then call the `withdraw` function with the `ETH` address not the `WETH` address even though they deposited `WETH` and steal all user deposits and the withdraw transfer will go through.

`balances[_receiver][ETH] += _amount`

## Tools Used
manual 

## Recommended Mitigation Steps

change line 191 from : `balances[_receiver][ETH] += _amount` to this code
 `balances[_receiver][WETH] += _amount`

```diff
      function _processLock(address _token, uint256 _amount, address _receiver, bytes32 _referral)
        internal
        onlyBeforeDate(loopActivation)
    {
        if (_amount == 0) {
            revert CannotLockZero();
        }
        if (_token == ETH) {
            totalSupply = totalSupply + _amount;
            balances[_receiver][ETH] += _amount;
        } else {
            if (!isTokenAllowed[_token]) {
                revert TokenNotAllowed();
            }
            IERC20(_token).safeTransferFrom(msg.sender, address(this), _amount);

            if (_token == address(WETH)) {
                WETH.withdraw(_amount);
                totalSupply = totalSupply + _amount;
-                balances[_receiver][ETH] += _amount;
+                balances[_receiver][WETH] += _amount;
            } else {
                balances[_receiver][_token] += _amount;
            }
        }

        emit Locked(_receiver, _amount, _token, _referral);
    }
```
