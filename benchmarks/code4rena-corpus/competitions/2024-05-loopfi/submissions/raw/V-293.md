# Vulnerability details

## Impact
The following exploit, if executed, could lead to any user "withdrawing" their locked funds after the startClaimDate by using the claim() function with a custom _data payload.  
This, depending on the implementation of the points-handling logic of the protocol, could result in the handing out of points for nearly no cost to the attacker since the Withdrawn event is never emitted, without the protocol gaining any substantial liquidity in return.  

## Proof of Concept
Due to a lack of time and the complexity of the attack, the exploit hasn't been tested but it seems plausible it'll work, potentially requiring some adjustments.  
Following is a brief outline of the steps required, with code snippets provided where possible.  
Steps:  
1. Before the loopActivation date, the user locks some allowed LRT tokens to obtain points from the protocol.  
Note that this doesn't work with WETH or ETH since they are automatically converted to lpETH without user interaction via convertAllETH().  
2. After the startClaimDate, the user cannot withdraw their tokens anymore but can call the claim() function, providing the address of the LRT, a percentage between 0-100, the Exchange value referring to UniswapV3 and a custom _data payload that contains the exploit.  
3. The payload is crafted to pass all the checks performed by _validateData(): it uses the correct function selector to call sellTokenForEthToUniswapV3() defined inside 0x's [UniswapV3Feature contract](https://github.com/0xProject/protocol/blob/development/contracts/zero-ex/contracts/src/features/UniswapV3Feature.sol), it has WETH as the output token as detected by the _decodeUniswapV3Data() function, uses a valid inputToken and the correct inputTokenAmount and the recipient is the PrelaunchPoints contract.  
Payload _data sketch:  
```
0x803ba26d // UniswapV3Feature.sellTokenForEthToUniswapV3() function selector
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx // offset from the start of calldata at which the attack's encodedPath starts (ignoring the selector). Needs to be computed using the encoded length of the path intended for validation
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx // address of the LRT token to be swapped out of the PrelaunchPoints contract
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx // inputTokenAmount
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx // minBuyAmount, parameter of swap ignored by the validation function
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx // address of the deployed PrelaunchPoints contract, the recipient of the swap
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx // lenth of the encoded path array that is checked during validation
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx // swap input token address used for validation aka LRT token
... // swap hops  
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx // swap output token positioned in the last position of the path array, compute offset by using the encodedLength. The validation function expects this to be the WETH address
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx // lenth of the encoded path array that is used for the attack. This is where the offset at the start of the payload will point!
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx // swap input token address used for the attack aka LRT token
... // swap hops  
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx // swap output token positioned in the last position of the path array, compute offset by using the encodedLength. This will point to the token controlled by the attacker.
```  
The whole exploit relies on the second line of the payload, through which the expected/validated swap path is ignored and the attacker is able to choose one arbitrarily.  
4. The attacker now needs to create a Uniswap pool containing a pair of tokens, one of which needs to be the LRT that they want to smuggle out of the protocol, the other token should ideally be a worthless one that they set up and of which they control the minting. This in order to easily manipulate the swap price of one for the other.  
The idea being that the pool will receive liquidity by the attacker, the attacker will use the exploit to force the PrelaunchPoints contract to swap() the LRT tokens for the worthless ones and finally the attacker will pull their liquidity from the pool.  
This will leave the attacker with both the valuable LRT tokens and the protocol points accrued with them, while the protocol will be empty-handed.  
5. For the last part of the _claim() function, _fillQuote() will then be called without issues, executing the above mentioned swap and the claimedAmount, which will be 0 since no ETH will be deposited in the account by the swap.  
Even accounting for an hypothetical revert if the claimedAmount value is 0 when given as an argument to deposit(), this could be circumvented by giving a small amount of ether to the contract before executing the exploit.  
This terminates the part of the attack concerning the PrelaunchPoints contract.  
6. Regarding the [UniswapV3Feature contract](https://github.com/0xProject/protocol/blob/development/contracts/zero-ex/contracts/src/features/UniswapV3Feature.sol), to avoid any reverts in the sellTokenForEthToUniswapV3 function, it might be necessary to send the exchangeProxy contract a small amount of WETH so that the WETH.withdraw() on [line 120](https://github.com/0xProject/protocol/blob/e66307ba319e8c3e2a456767403298b576abc85e/contracts/zero-ex/contracts/src/features/UniswapV3Feature.sol#L120) won't fail due to a balance of WETH equal to 0.  
Furthermore, since the attacker is in control of the pool, they can determine the exchange rate and make the [buyAmount](https://github.com/0xProject/protocol/blob/e66307ba319e8c3e2a456767403298b576abc85e/contracts/zero-ex/contracts/src/features/UniswapV3Feature.sol#L113C9-L113C18) required arbitrarily small.  

This concludes the exploit.  
Note: this only seems to be viable using the UniswapV3 code path, a brief analysis of the transformations provided by 0x makes it appear unlikely to succeed, therefore the scenario in which the Exchange used is TransformERC20 should be safe.

## Tools Used
Only manual analysis of the code was used to spot the issue.  
The exploit is made possible by the way that *bytes* arguments are encoded in solidity, as outlined in the [solidity documentation](https://docs.soliditylang.org/en/latest/abi-spec.html#use-of-dynamic-types).

## Recommended Mitigation Steps
To avoid this problem, it should be sufficient to also decode and validate the offset at which the uniswap router path is located instead of just skipping it as done in [line 457](https://github.com/code-423n4/2024-05-loop/blob/40167e469edde09969643b6808c57e25d1b9c203/src/PrelaunchPoints.sol#L457).  
Making that value available in the _validateData() function, specifically in the [UniswapV3 case](https://github.com/code-423n4/2024-05-loop/blob/40167e469edde09969643b6808c57e25d1b9c203/src/PrelaunchPoints.sol#L414).  
The contract then just needs to check that the user is not "smuggling" a different path, compared to the one that the function is verifying, by making sure that the offset at which the *bytes* array is located equals exactly 0xA0, meaning that it starts in the *calldata* position right after the end of the decoded *recipient* field.
