# Vulnerability details


## Impact
The improper handling of the `loopActivation` variable in the `PrelaunchPoints.sol` contract can lead to inconsistent behavior, unexpected consequences, and potential security issues. The issue arises from the fact that `loopActivation` is initially set to a timestamp 120 days in the future from the contract deployment, but it can be unexpectedly overwritten when the `setLoopAddresses` function is called.


The inconsistency in setting and updating `loopActivation` can lead to the following impacts:

1. Users may unexpectedly be unable to perform certain actions, such as locking tokens or setting loop addresses, if `loopActivation` is prematurely updated to the current `block.timestamp`.

2. The contract's behavior may become unpredictable and difficult to reason about, as the timeline for certain actions can change dynamically based on when `setLoopAddresses` is called.

The affected functions that rely on `loopActivation` include:

1. `_processLock` (lines 172-198):

## Proof of Concept
The vulnerability can be demonstrated as follows:

Initially, `loopActivation` is set to a timestamp 120 days in the future from the contract deployment:
https://github.com/code-423n4/2024-05-loop/blob/0dc8467ccff27230e7c0530b619524cc8401e22a/src/PrelaunchPoints.sol#L102-L102
```solidity
constructor(address _exchangeProxy, address _wethAddress, address[] memory _allowedTokens) {
    // ...
    loopActivation = uint32(block.timestamp + 120 days);
    // ...
}
```

But, when `setLoopAddresses` is called, `loopActivation` is overwritten with the current `block.timestamp`:
https://github.com/code-423n4/2024-05-loop/blob/0dc8467ccff27230e7c0530b619524cc8401e22a/src/PrelaunchPoints.sol#L348-L351
```solidity
function setLoopAddresses(address _loopAddress, address _vaultAddress)
    external
    onlyAuthorized
    onlyBeforeDate(loopActivation)
{
    // ...
    loopActivation = uint32(block.timestamp);
    // ...
}
```

This inconsistency allows `loopActivation` to be unexpectedly modified, leading to the aforementioned impacts and potential vulnerabilities.

## Recommended Mitigation Steps

If the 120-day period from the contract deployment should be strictly enforced:
   - Remove the assignment of `block.timestamp` to `loopActivation` in the `setLoopAddresses` function.
   - Consider removing the `onlyBeforeDate(loopActivation)` modifier from the `setLoopAddresses` function to allow setting loop addresses at any time.

Alternatively, update the constructor to set a default value for `loopActivation` that aligns with the expected behavior when `setLoopAddresses` is called if flexibility in setting `loopActivation` is intended
