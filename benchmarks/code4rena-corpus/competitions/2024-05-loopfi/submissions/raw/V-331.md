# Vulnerability details

## Impact

Loss of user funds

## Proof of Concept

[\_claim](https://github.com/code-423n4/2024-05-loop/blob/40167e469edde09969643b6808c57e25d1b9c203/src/PrelaunchPoints.sol#L240) function is the main internal function for the depositors to claim the lpETH ater the claim date.

```solidity
Contract: PrelaunchPoints.sol

240:     function _claim(address _token, address _receiver, uint8 _percentage, Exchange _exchange, bytes calldata _data)
241:         internal
242:         returns (uint256 claimedAmount)
243:     {
244:         uint256 userStake = balances[msg.sender][_token];
245:         if (userStake == 0) {
246:             revert NothingToClaim();
247:         }
248:         if (_token == ETH) {
249:             claimedAmount = userStake.mulDiv(totalLpETH, totalSupply);
250:             balances[msg.sender][_token] = 0;
251:             lpETH.safeTransfer(_receiver, claimedAmount);
252:         } else {
253:             uint256 userClaim = userStake * _percentage / 100;
254:             _validateData(_token, userClaim, _exchange, _data);
255:             balances[msg.sender][_token] = userStake - userClaim;
256:
257:             // At this point there should not be any ETH in the contract
258:             // Swap token to ETH
259:             _fillQuote(IERC20(_token), userClaim, _data);
260:
261:             // Convert swapped ETH to lpETH (1 to 1 conversion)
262:             claimedAmount = address(this).balance;
263:             lpETH.deposit{value: claimedAmount}(_receiver);
264:         }
265:         emit Claimed(msg.sender, _token, claimedAmount);
266:     }
```

According to the `_token` in `balances` mapping, the lpETH amounts are either transferred to the users (If the token is ETH), or swapped through `0x API` by means of DeFi platforms.

To quote the amounts in ETH (to deposit in lpETH), `_fillQuote` function is called with the `userClaim` amount (if the deposit is not ETH, the user can claim lpETH in parts)

```solidity
Contract: PrelaunchPoints.sol

491:     function _fillQuote(IERC20 _sellToken, uint256 _amount, bytes calldata _swapCallData) internal {
492:         // Track our balance of the buyToken to determine how much we've bought.
493:         uint256 boughtETHAmount = address(this).balance;
494:
495:         require(_sellToken.approve(exchangeProxy, _amount));
496:
497:         (bool success,) = payable(exchangeProxy).call{value: 0}(_swapCallData);
498:         if (!success) {
499:             revert SwapCallFailed();
500:         }
501:
502:         // Use our current buyToken balance to determine how much we've bought.
503:         boughtETHAmount = address(this).balance - boughtETHAmount;
504:         emit SwappedTokens(address(_sellToken), _amount, boughtETHAmount);
505:     }
```

`_fillQuote` caches the ETH balance at L: 493 and calculates the received amount at L:503 either to account the already existing ETH in the contract OR the slippage occurring during swap.
Accordingly, `_claim` function deposits the balance to lpETH contract and the user receives 1:1 pegged lpETH after deposit call.

However, above misses the point where the slippage will effect the user balances.

As referred earlier, `_fillQuote` takes `userClaim` amount for approval, and the `_swapCallData` is prepared on frontend as per the Discord Server convos, and the same `userClaim` is being swapped.
And before, the amount is substracted for CEI pattern compliance.

```solidity
Contract: PrelaunchPoints.sol

255:  balances[msg.sender][_token] = userStake - userClaim;
```

So if the swap ends with a slippage - less ETH received then the `userClaim` - the user will lose the difference
If 0 slippage ratio is opted during the swap - the user will end in inability to claim due to MEV

## Tools Used

Manual Review

## Recommended Mitigation Steps

After the token swap, verify the actual amount of tokens swapped and adjust the user's balance based on this amount rather than the pre-determined `userClaim`.
