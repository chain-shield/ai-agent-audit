# Vulnerability details

## Impact
The contract is intended to only work with Wrapped LRT tokens, but it does 
now validate that the token being allowed by admin is indeed a wrapped LRT token
and not a rebase token which might break system assumptions

Moreover, the contract also allows the allowing of zero address as a valid token.


## Proof of Concept

The `allowToken` method is used to allow a token address to be supported by the platform.

```solidity
/**
     * @param _token address of a wrapped LRT token
     * @dev ONLY add wrapped LRT tokens. Contract not compatible with rebase tokens.
     */
    function allowToken(address _token) external onlyAuthorized {
        isTokenAllowed[_token] = true;
    }
```

However, the Protocol clearly states in the Natspec that `ONLY add wrapped LRT tokens. Contract not compatible with rebase tokens.`

and the passed `_token` address has to be one of a `wrapped LRT token`

However, the code does not check if it indeed is a wrapped LRT token 

Plus most importantly, it MUST NOT be a Rebase token because protocol is incompatible with the Rebase tokens.

Additionally, due to the lack of a zero address check on input token address by the user,

the contract has the ability to accidentally allow zero address as a valid token
( the likelihood for zero address token being passed is very low but it is considerable ) .

Due to which system's assumptions that it is operating only on non-zero addressed Allowed LRT tokens and not rebase tokens can completely put the contract in a bricked state.

## Tools Used
Manual review
## Recommended Mitigation Steps
Implement specific logic to check if the contract is not a rebase token and is a wrapped LRT token + a sanity check on the parameter token address.
