# Vulnerability details

## Impact
The protocol only allows the tokens to be recovered by the Authorized address
if the token to be recovered is not one of these

- lpETH Token
- Supported/Allowed tokens i.e isAllowed[token] =true

However, if such tokens are sent accidentally to the contract, they can never be recovered due to this check and lack of any other way to the tokens out.

## Proof of Concept
The lock, staking, and claiming functions are well-designed to only return the amount 
of supported tokens the user deserves.

If any tokens are accidentally sent to the contract , following method is used to recover those tokens

```solidity
    function recoverERC20(address tokenAddress, uint256 tokenAmount) external onlyAuthorized {
        if (tokenAddress == address(lpETH) || isTokenAllowed[tokenAddress]) {
            revert NotValidToken();
        }
        IERC20(tokenAddress).safeTransfer(owner, tokenAmount);

        emit Recovered(tokenAddress, tokenAmount);
    }
```
If the accidently sent tokens include one that are supported by the protocol or 
that includes lpETH , then these tokens will stuck in the contract forever as their 
is no edge case win which contract is willing to let anyone withdraw those assets
that does not belong to anyone.

This might lead to a loss of funds/tokens to users.

The likelihood is Low but the impact is High.

More importantly, the protocol cares about such scenarios and tries to mitigate 

this issue which tells us that protocol cares about this scenario 

that no tokens should be stuck in the contract but it fails to completely mitigate 

the risk for the stuck tokens and recovering them.

So high severity might be appropriate but it can be at least a valid medium 
 
## Tools Used
Manual review
## Recommended Mitigation Steps
Add some sort of accounting mapping for each token, how many are inside the 

contract belongs to the users who have locked or staked using appropriate methods 

and allow any extra tokens by the admin.
