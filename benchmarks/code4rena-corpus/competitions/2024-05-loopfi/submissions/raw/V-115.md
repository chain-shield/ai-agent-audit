# Vulnerability details

## Impact
The _validateData function in the smart contract does not include a check for the expiration of the UniswapV3 selector. This oversight can result in transactions pending in the mempool for extended periods, potentially leading to unfairly swapped values for users. This is due to fluctuations in the prices of ETH or the allowed tokens, which can significantly impact the outcome of the claim.

## Proof of Concept
In the `_validateData` function below
```
function _validateData(address _token, uint256 _amount, Exchange _exchange, bytes calldata _data) internal view {
        address inputToken;
        address outputToken;
        uint256 inputTokenAmount;
        address recipient;
        bytes4 selector;
```

There is no deadline check, which means a user can call the claim txn with low txn fee due to expensive gas, this would pass the `_validateData` function, and go to the exchangeProxy Contract which implementation below has no check for deadline or expiration

```
 bytes4 selector = msg.data.readBytes4(0);
        address impl = getFunctionImplementation(selector);
        if (impl == address(0)) {
            _revertWithData(LibProxyRichErrors.NotImplementedError(selector));
        }

        (bool success, bytes memory resultData) = impl.delegatecall(msg.data);
        if (!success) {
            _revertWithData(resultData);
        }
        _returnWithData(resultData);
```

Consider a scenario where a newbie user attempts to claim 10 rETH with a low transaction fee (expensive gas in Ethereum), assuming a 5% slippage. This transaction might remain in the mempool for several hours. During this time, the price of ETH could change, affecting the initial exchange rate of 10 rETH to approximately 10 ETH. If the price of ETH slightly drops against rETH before the peg recovers, the exchange rate could shift to around 9.7 ETH, resulting in a significant loss for the user due to the price change.

Conversely, if the price of ETH increases, the exchange rate for rETH to ETH could rise to around 10.2 ETH. This situation could enable an MEV bot to sandwich the transaction, still holding the outdated 9.7 ETH as slippage. The bot could then profit at the expense of the user to about `10.2 - 9.7 ETH = 0.5 ETH`.
