# Vulnerability details

### Impact
The function does not account for possible transfer fees deducted by some ERC20 tokens, which can result in incorrect balance updates within the contract. This discrepancy can lead to financial inaccuracies, affecting the integrity of the contract's token management.

### Proof of Concept
In `PrelaunchPoints._proccessLock`, the contract assumes that the entire [_amount](https://github.com/code-423n4/2024-05-loop/blob/40167e469edde09969643b6808c57e25d1b9c203/src/PrelaunchPoints.sol#L172) specified by the user is transferred to the contract:
```solidity
IERC20(_token).safeTransferFrom(msg.sender, address(this), _amount);
```
However, if `_token` implements a transfer fee, the actual amount received by the contract will be less than `_amount`. The subsequent balance update does not consider this possibility:
```solidity
balances[_receiver][_token] += _amount;
```
This results in the contract recording more tokens than actually received, leading to inflated balance entries.

### Tools Used
- Manual Review

### Recommended Mitigation Steps
1. **Verify Actual Transfer Amount**: After the `safeTransferFrom` call, query the contract's balance of the token to determine the actual amount received. Update the user's balance based on this actual amount rather than the input `_amount`.
