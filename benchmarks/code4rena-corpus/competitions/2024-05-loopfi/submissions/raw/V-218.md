# Vulnerability details

## Description

On `claim` and `claimAndStake` function, internal `_claim` function is called. From the NatSpec we can see that, claiming functionality is called by a user to get their vested `lpETH`. 

In those functions, the user provides `_token` address as input. And we know from the NatSpec, `@param _token: Address of the token to convert to lpETH`. As a input, a user also need to provide how much he wants to claim (in `_percentage`)

But, when a user attempts to claim a portion of their lpETH after a certain period of time, the function incorrectly zeroes out the user's entire ETH balance instead of deducting only the claimed amount and there is no usage of the `_percentage` amounts he wants in the calculation. 
```solidity
    claimedAmount = userStake.mulDiv(totalLpETH, totalSupply);
    balances[msg.sender][_token] = 0;
    lpETH.safeTransfer(_receiver, claimedAmount);
```

But, its perfectly done for the non-ETH tokens ( LSTs).
```solidity
    uint256 userClaim = userStake * _percentage / 100;
    _validateData(_token, userClaim, _exchange, _data);
    balances[msg.sender][_token] = userStake - userClaim;
```
This issue leads to users losing access to the remaining unclaimed lpETH, resulting in a significant loss of funds.


## Impact

Users who intend to claim only a portion of their  lpETH will lose access to the remaining unclaimed funds. This can result in a significant financial loss for users, as their entire ETH balance is wiped out even if they only meant to claim a fraction of it.


## Proof of Concept

Let's consider the following scenario:

1. User A locks 100 ETH in the `PrelaunchPoints` contract.
2. After the `startClaimDate` time, User A decides to claim 50% of his lpETH.
3. User A calls the `claim` or `claimAndStake` function, that calls `_claim` function internally with the appropriate parameters, specifying `_token` as `ETH` and `_percentage` as 50.
4. The function calculates the `userStake` & `claimedAmount` based on the `totalLpETH`, `totalSupply` and the user's lock amount.
5. However, instead of deducting only the `claimedAmount` from User A's balance, the function sets `balances[msg.sender][_token]` to zero.
6. As a result, User A's entire ETH balance of 100 ETH is wiped out, even though they only intended to claim 50 lpETH.
7. User A loses access to the remaining 50 lpETH, which was not part of the claim.

### How the Vulnerability Will Occur

The vulnerability occurs due to the flawed logic in the `_claim` function when handling partial claims for lpETH. The function fails to consider the percentage of the claim and instead zeroes out the user's entire ETH balance (lpETH claiming).

This vulnerability will manifest whenever a user attempts to claim a portion of their locked ETH using the `_claim` function. Instead of deducting only the claimed amount from the user's balance, the function will erase the entire balance, resulting in the loss of any unclaimed funds.

## Recommended Mitigation Steps

To mitigate this, the `_claim` function should be modified to correctly handle partial claims for lpETH when the `_token` is ETH. Instead of zeroing out the user's entire balance, the function should deduct only the claimed amount from the balance.

Here's the recommended code change:

```solidity
if (_token == ETH) {
    claimedAmount = userStake.mulDiv(totalLpETH, totalSupply);
    uint256 remainingBalance = userStake - claimedAmount;
    balances[msg.sender][_token] = remainingBalance;
}
```

Calculate the `remainingBalance` by subtracting the `claimedAmount` from the `userStake`. Then update the user's balance with the `remainingBalance` instead of setting it to zero.

Here's a diff representation of the changes:

```diff
if (_token == ETH) {
    claimedAmount = userStake.mulDiv(totalLpETH, totalSupply);
-   balances[msg.sender][_token] = 0;
+   uint256 remainingBalance = userStake - claimedAmount;
+   balances[msg.sender][_token] = remainingBalance;
}
```
