# Vulnerability details

## Impact
This vulnerability arises due to the lack of validation for the ```_percentage``` parameter in the ```_claim``` function. It is an ```internal``` function which is called by ```claim``` and ```claimAndStake``` functions which are both exposed to users. Users can call these functions with values greater than 100%, and calculations within the function can lead to claims exceeding the user's actual stake, potentially causing an integer underflow in balance calculations. This can allow users to erroneously withdraw or manipulate token amounts far exceeding their balances, leading to unauthorized asset transfers and depletion of the contract’s resources.

## Proof of Concept
The ```_percentage``` parameter in the ```_claim``` function is defined as a ```uint8```, allowing values from 0 to 255. When this parameter is set to values greater than 100%, specifically up to 255, the function performs calculations that can lead to claims exceeding the user's actual stake. For instance, an attacker can exploit this vulnerability by calling the ```claim``` function with a ```_percentage``` parameter set to 255. Here’s what occurs:

**Calculation**
```uint256 userClaim = userStake * 255 / 100;``` results in a ```userClaim``` that is more than double the user's stake if they have a non-zero balance.

**Balance Update**
```balances[msg.sender][_token] = userStake - userClaim;``` will underflow because userClaim exceeds userStake, resulting in an extremely large balance being set due to the properties of unsigned integers in Solidity.

**Let's assume:**
userStake: The user has 100 tokens staked.
_percentage: The user submits a claim with 255%.
_token: We'll use a generic ERC20 token for simplicity.

The user calls the ```claim``` function which calls the ```_claim``` function.

The function executes the following calculation to determine userClaim:
uint256 userClaim = userStake * _percentage / 100;

Plugging in the values:
userClaim = 100 * 255 / 100;
userClaim = 255;

The balance update line in the function is:
balances[msg.sender][_token] = userStake - userClaim;

Plugging in the values:
balances[msg.sender][_token] = 100 - 255;

Underflow:
Since Solidity uses unsigned integers, subtracting a larger number from a smaller one results in an underflow:

balances[msg.sender][_token] = 2^256 - 1 - (255 - 100);
balances[msg.sender][_token] = 2^256 - 1 - 155;

This underflow causes the balance to wrap around to a tremendously large number, effectively giving the user access to more tokens than the total supposed supply or what is available in the contract.

## Recommended Mitigation Steps
Incorporate input validation at the beginning of the ```_claim``` function. Validate the input percentage to ensure it's within the expected range. Also, a common check is to validate the token address to prevent operations on a zero address. I have included them in the snippet below:
```
function _claim(address _token, address _receiver, uint8 _percentage, Exchange _exchange, bytes calldata _data)
    internal
    returns (uint256 claimedAmount)
{
    // Validate the input percentage to ensure it's within the expected range.
    require(_percentage >= 1 && _percentage <= 100, "Invalid percentage: must be between 1% and 100%");

    // Validate the token address to prevent operations on a zero address.
    require(_token != address(0), "Invalid token address");

    uint256 userStake = balances[msg.sender][_token];
    if (userStake == 0) {
        revert NothingToClaim();
    }
    if (_token == ETH) {
        claimedAmount = userStake.mulDiv(totalLpETH, totalSupply);
        balances[msg.sender][_token] = 0;
        lpETH.safeTransfer(_receiver, claimedAmount);
    } else {
        uint256 userClaim = userStake * _percentage / 100;
        _validateData(_token, userClaim, _exchange, _data);
        balances[msg.sender][_token] = userStake - userClaim;

        // At this point there should not be any ETH in the contract
        // Swap token to ETH
        _fillQuote(IERC20(_token), userClaim, _data);

        // Convert swapped ETH to lpETH (1 to 1 conversion)
        claimedAmount = address(this).balance;
        lpETH.deposit{value: claimedAmount}(_receiver);
    }
    emit Claimed(msg.sender, _token, claimedAmount);
}
```

***Important Note***
In the above code snippet, I have limited the ```_percentage``` to be between 1 and 100 (inclusive). However, you could consider a ```percentage``` of 0. If it is allowed for ```_percentage = 0```, then 

User claim would be 0: ```userClaim = userStake * 0 / 100 = 0;```

Balance Update: ```balances[msg.sender][_token] = userStake - 0;``` effectively leaves the balance unchanged.

Considerations with ```_percentage = 0```:

**Redundant Operations**
Even though setting _percentage to 0 does not lead to incorrect balances or immediate vulnerabilities, it triggers function calls and state changes (like balance checks and event emissions) that consume gas without performing any meaningful action.

**Potential Gas Waste**
Users can inadvertently or maliciously call these functions with 0%, leading to wasted gas and unnecessary load on the network.
