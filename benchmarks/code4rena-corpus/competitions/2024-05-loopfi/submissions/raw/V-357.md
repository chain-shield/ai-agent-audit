# Vulnerability details

## Impact

The PrelaunchPoints contract allows the owner to unilaterally change critical contract addresses like the lpETH and lpETHVault addresses using the `setLoopAddresses` function. This lacks the security of a multisig requirement and could allow a compromised or malicious owner to direct user funds to the wrong contracts.

## Description

The `setLoopAddresses` function can be called by the contract owner to set the `lpETH` and `lpETHVault` contract addresses that are critical to the functioning of the PrelaunchPoints contract

https://github.com/code-423n4/2024-05-loop/blob/main/src/PrelaunchPoints.sol#L348

```solidity
function setLoopAddresses(address _loopAddress, address _vaultAddress) 
    external
    onlyAuthorized
    onlyBeforeDate(loopActivation)
{
    lpETH = ILpETH(_loopAddress);
    lpETHVault = ILpETHVault(_vaultAddress);
    loopActivation = uint32(block.timestamp);
    
    emit LoopAddressesUpdated(_loopAddress, _vaultAddress);
}
```

These addresses determine where user funds (both ETH and lpETH) are sent when users lock ETH, claim lpETH rewards, or stake lpETH in the vault. 

The issue is that the `onlyAuthorized` modifier only checks that the caller is the contract owner, giving the owner unilateral control over setting these addresses:

```solidity
modifier onlyAuthorized() {
    if (msg.sender != owner) {
        revert NotAuthorized();
    }
    _;
}
```

If the owner account is compromised, or the owner turns out to be malicious, they could call `setLoopAddresses` with malicious contract addresses to steal user funds when they interact with the contract. 

There is no multisig requirement or time delay to changing these critical addresses, which significantly reduces the security of user funds and the trustworthiness of the protocol. A multisig requirement would ensure that no single compromised account could make such critical changes.

## Proof of Concept

A malicious owner could deploy malicious contracts that mimic the lpETH and lpETHVault interfaces but steal any ETH or tokens sent to them. They could then call `setLoopAddresses` with the addresses of these malicious contracts:

```solidity
maliciousLpETH = new MaliciousLpETH();
maliciousLpETHVault = new MaliciousLpETHVault();
prelaunchPoints.setLoopAddresses(address(maliciousLpETH), address(maliciousLpETHVault));
```

Now any users who lock ETH or claim lpETH rewards will have their funds sent to the malicious contracts and stolen, until the malicious addresses are noticed and changed again by the owner.

Manual code review

## Recommended Mitigation Steps

The main recommendation is to require a multisig to change critical addresses like `lpETH` and `lpETHVault`. This could be achieved by:

1. Having the contract owned by a multisig wallet that requires multiple signers to confirm transactions.
2. Implementing an on-chain multisig mechanism where changing these addresses requires approval from a minimum number of pre-defined signers.  
3. Using a timelock contract as the owner that enforces a time delay between when an address change is requested and when it can be executed, giving time for others to notice and react.
