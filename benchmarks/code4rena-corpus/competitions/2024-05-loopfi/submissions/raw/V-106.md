# Vulnerability details

## Impact
One of the main concerns of the protocol as stated in contest readme is 

user funds should not be locked for undesirable times

```
Attack ideas (where to focus for bugs)
   1. Malicious 0x protocol calldata crafting by users to steal funds on claim
   2. User funds getting locked forever
```

However that is possible in the claim function when 

the total amount of tokens >>> total lp eth 

totalSupply > totalLpETH

More concretely if the user has the balance x to withdraw 

then if 

x*totalLpEth < totalSupply 

then the user's tokens will be locked for a long time until a lot of other 

depositors start claiming their tokens through claim effectively reducing the totalSupply

## Proof of Concept
Inside the `_claim` method , the amount to be claimed in case of eth token

is calculated as follows 

```solidity
      claimedAmount = userStake.mulDiv(totalLpETH, totalSupply);
```

If a user has a balance of 1 ether in the contract being locked .
The totalLpEth being 10 ether ( the amount of lpETH users have locked in the contract )

and totalSupply being 10 Million .

Totalsupply being such larger number ( maybe a lot larger than that ) is possible

because the totalSupply variable is increased in both cases of locks 

native or erc20.

```
  function _processLock(address _token, uint256 _amount, address _receiver, bytes32 _referral)
        internal
        onlyBeforeDate(loopActivation)
    {
        if (_amount == 0) {
            revert CannotLockZero();
        }
        if (_token == ETH) {
            totalSupply = totalSupply + _amount;
            balances[_receiver][ETH] += _amount;
        } 
           //SNIP
            if (_token == address(WETH)) {
                WETH.withdraw(_amount);
                totalSupply = totalSupply + _amount;
                balances[_receiver][ETH] += _amount;
            ]

        //SNIP
}
```

and decreased only in withdraw function , whose frequency to being used 

is far less than locking actions 

```
    totalSupply = totalSupply - lockedAmount;
```

As more people will lock their funds for longer times , increasing the totalSupply

variable and rarely decrease happen in it due to withdraw being called 

the totalSupply is bound to be a large number.

However the totalLpETH is calculated from the balance of eth the contract has

and as it is just dependent on eth balance and not the other erc20 tokens 

( which , in practical markets are far in numbers - and people are more likely to hold  other erc20 tokens than just lpETH tokens )

This balance will be lower .

Now users having big balances like 1000 tokens or 1 million tokens to claim

because then the userStake amount will be large and effectively calculating the 

claimedAmount correct 

```
 claimedAmount = userStake.mulDiv(totalLpETH, totalSupply);
```

however this will be problem for small balanced users whose claimedAmount will appear to be zero due to the relatively low product value of `userStake * totalLpETH` 

in comparison to the value `totalSupply`

due to which users will face their funds being locked for certain undesired times

### Additional attack vector
If the `totalSupply` variable is high enough and the product of `userStake` and `totalLpETH` is not a factor of `totalSupply`, then user might lose as much as 
`totalSupply-1` tokens because their balance is turned to zero now 

```solidity
balances[msg.sender][_token] = 0;
```

For example ,
if totalSupply = 1 million , userStake =1000 , totalLpETH = 1000,
the claimedAmount will be 1.

however if totalSupply = 1 million , userStake =999 , totalLpETH = 1000

(999*1000)/1000000 => 999000/1000000 = 0 ,

additionally if the  userStake =1999 , totalLpETH = 1000

1999*1000/1000000=1999000/1000000 => 1

The claimed amount is still 1 , which means the user will lose their 999000 tokens.
