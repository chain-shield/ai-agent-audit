# Vulnerability details

## Severity

Medium

## Impact

The impact of the vulnerability within the `PreLaunchPoints.sol` contract is significant. Due to the improper handling of the enum variable `Exchange` in the `_validateData` function, the contract is susceptible to incorrect behavior when the `Exchange` value is not explicitly provided by the user. As the default value of an enum is always 0, if the user doesn't input the exchange, it will default to `Exchange.UniswapV3`. This can lead to unintended and potentially harmful consequences, such as incorrect token swaps or unauthorized transfers.

## Proof of Concept

The vulnerability can be observed in the following code snippet from the `PreLaunchPoints.sol` contract:

```solidity
   // Vulnerable code block
if (_exchange == Exchange.UniswapV3) {
    (inputToken, outputToken, inputTokenAmount, recipient, selector) = _decodeUniswapV3Data(_data);
    if (selector != UNI_SELECTOR) {
        revert WrongSelector(selector);
    }
}
```

## Tools Used

The issue was discovered through manual code review and analysis.

## Recommended Mitigation Steps

To mitigate this vulnerability, consider updating the `Exchange` enum definition to include a value explicitly representing "none" or "invalid". This ensures that if the user does not provide a valid exchange value, the contract can detect and handle this scenario appropriately.

```solidity
enum Exchange {
  None,
  UniswapV3,
  TransformERC20
}
```

By adding a `None` value to the enum, you provide a clear indication that no exchange value has been provided. Then, in the `_validateData` function, you can check for this `None` value and handle it accordingly to prevent unintended behavior.
