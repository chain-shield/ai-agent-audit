# Vulnerability details

## Impact
The contract does not appear to have a mechanism to track whether tokens have already been claimed. The _claim function resets the user's balance for the claimed token to zero for ETH claims but does not for other tokens, which could lead to double claiming
`balances[msg.sender][_token] = 0;`
Since _claim is an internal function, its direct exposure to external calls is limited. However, it's called by public functions `claim` and `claimAndStake`, which means the missing claim tracking for non-ETH tokens can still be exploited through these public entry points.

The vulnerability arises because the `_claim` function does not account for the total amount of non-ETH tokens that have been converted to lpETH and claimed by the user. This means that if a user claims less than 100% of their stake, the remaining balance is left in the contract without any tracking of how much lpETH has already been minted against it. As a result, a user could potentially claim more lpETH than they are entitled to by claiming their stake in portions.

## Proof of Concept
```
function _claim(address _token, address _receiver, uint8 _percentage, Exchange _exchange, bytes calldata _data)
        internal
        returns (uint256 claimedAmount)
    {
        uint256 userStake = balances[msg.sender][_token];
        if (userStake == 0) {
            revert NothingToClaim();
        }
        if (_token == ETH) {
            claimedAmount = userStake.mulDiv(totalLpETH, totalSupply);
            balances[msg.sender][_token] = 0;
            lpETH.safeTransfer(_receiver, claimedAmount);
        } else {
            uint256 userClaim = userStake * _percentage / 100;
            _validateData(_token, userClaim, _exchange, _data);
            balances[msg.sender][_token] = userStake - userClaim;

            // At this point there should not be any ETH in the contract
            // Swap token to ETH
            _fillQuote(IERC20(_token), userClaim, _data);

            // Convert swapped ETH to lpETH (1 to 1 conversion)
            claimedAmount = address(this).balance;
            lpETH.deposit{value: claimedAmount}(_receiver);
        }
        emit Claimed(msg.sender, _token, claimedAmount);
    }
```

This vulnerability could lead to an inflation of the lpETH supply, as users could claim more lpETH than their original stake would allow. This would dilute the value of lpETH for all holders and could be exploited to drain the contract of its ETH reserves, leading to financial loss for the protocol and its users.

## Recommended Mitigation Steps

To mitigate this vulnerability, the contract should track the total amount of `lpETH` that has been claimed against each user's non-ETH token stake. This could be done by introducing a new mapping to store the amount of lpETH claimed per user per token. The `_claim` function should then be updated to check against this mapping to ensure that users cannot claim more lpETH than their stake entitles them to
