# Vulnerability details

## Impact
Detailed description of the impact of this finding.

In theory, users lock their WETH through the lock() function, and their balances should be recorded as balances [_receiver] [WETH]. However, users are not aware that their balances are actually recorded as balances [_receiver] [ETH]. Therefore, when they want to retrieve their WETH through the withdraw() function, the function will be revert() because 'balances [msg. sender] [_token]==0', which means that the project does not respond to the service.

Similarly, when a user queries their WETH balance through the balances() function, the result returned is 0.

## Recommended Mitigation Steps

My suggestion is to [here](https://github.com/code-423n4/2024-05-loop/blob/40167e469edde09969643b6808c57e25d1b9c203/src/PrelaunchPoints.sol#L283-L285)Change to:

```solidity
        uint256 lockedAmount;
       
        if (_token == WETH) {
        	lockedAmount = balances[msg.sender][ETH];
        }
        
        lockedAmount = balances[msg.sender][_token];
        balances[msg.sender][_token] = 0;
```

In this way, users can lock the same token with draw() based on what token was locked when the lock() function was first called.
