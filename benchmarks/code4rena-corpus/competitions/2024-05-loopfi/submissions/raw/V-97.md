# Vulnerability details

## Impact
The `claim` and `claimAndStake` methods are broken ,

and will lead to denial of service for the next 82 years

because the `startClaimDate` is set to `82 years` from now

and these functions are only executed `after the startClaimDate has passed`

## Proof of Concept

Inside the constructor of the contract , the `startClaimDate` is set to uint32.max value

```solidity
   constructor(address _exchangeProxy, address _wethAddress, address[] memory _allowedTokens) {
        
        loopActivation = uint32(block.timestamp + 120 days);
        startClaimDate = 4294967295; // Max uint32 ~ year 2107
         //snip


```
Because according to [epochconverter](https://www.epochconverter.com/),  The timestamp value `4294967295` is 82 years from now because it is the timestamp of
```
Assuming that this timestamp is in seconds:
GMT: Sunday, 7 February 2106 06:28:15
Your time zone: Sunday, 7 February 2106 11:28:15 GMT+05:00
Relative: In 82 years
```
Now on the claim and ClaimAndStake methods , there is onlyAfterDate modifier 

```solidity
function claim(address _token, uint8 _percentage, Exchange _exchange, bytes calldata _data)
        external
        onlyAfterDate(startClaimDate)

        _claim(_token, msg.sender, _percentage, _exchange, _data);
    }
 function claimAndStake(address _token, uint8 _percentage, Exchange _exchange, bytes calldata _data)
```

where the `onlyAfterDate` modifier ensures 

