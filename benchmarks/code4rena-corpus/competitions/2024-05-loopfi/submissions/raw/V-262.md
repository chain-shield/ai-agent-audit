# Vulnerability details

## Impact
The `_processLock` function fails to check if the receiver address is an address zero or sender's address, and this impact the contract these ways.

Scenario 1

If user mistakenly input address zero or dead address, then their money is gone. For the sake that users can be clumsy sometimes and make terrible mistake when they paste address, it is important that this is verified.

Scenario 2

If users paste the same wallet, they are sending the transaction from, then there is no need for `LockFor` function. The aim of these function is to allow users to lock token/ETH for their friend, failing to verifying that the wallet is not theirs defeats this purpose and destroy the integrity of the smart contract.


## Proof of Concept
```solidity
function testLockForIssueCanBeZeroAddress(uint256 lockAmount) public {
    lockAmount = bound(lockAmount, 1, INITIAL_SUPPLY);
    lrt.approve(address(prelaunchPoints), lockAmount );
    
    // Lock tokens for recipient 1 which is an address 0
    address recipient1 = address(0);
    prelaunchPoints.lockFor(address(lrt), lockAmount, recipient1, referral);
    assertEq(prelaunchPoints.balances(recipient1, address(lrt)), lockAmount);

    
}
function testLockForIssueSendercanBeRecipent(uint256 lockAmount) public {
    lockAmount = bound(lockAmount, 1, INITIAL_SUPPLY);
    lrt.approve(address(prelaunchPoints), lockAmount);
    

    // Lock tokens for recipient 2 which is also the caller
    address recipient2 = msg.sender;
    prelaunchPoints.lockFor(address(lrt), lockAmount, recipient2, referral);
    assertEq(prelaunchPoints.balances(recipient2, address(lrt)), lockAmount);
}
```
