# Vulnerability details

## Impact

When the user wants to claim `lpETH` they are eligible for using `claim()` or `claimAndStake()` function, they need to provide the `_data` parameter that was generated in the front-end based on the call to the 0x API. To make the call, `sellAmount` had to be specified by the user. The issue is that when the user chooses the `sellAmount` to be a number that is not a divisor of the `userStake` , the call will always fail due to incorrect rounding when trying to find the appropriate `_percentage` value for the following calculation:
```javascript
uint256 userClaim = (userStake * _percentage) / 100;
```

## Proof of Concept

1. The user locks 3e18 of any LRT - say `rswETH`.
2. After `startClaimDate` is set they call `claim()` for rswETH token with the `inputTokenAmount` set to 1e18  encoded in `_data` parameter - intending to claim 1/3 of the `lpETH` they're eligible for, and `_percentage` set to 33 (%).
3. Their call will fail reverting with `WrongDataAmount()` as `inputTokenAmount = 1e18`, while `_amount = 0.99e18` ( 3e18 * 33 / 100 ).

To run a PoC, change the code in `PrelaunchPoints0x.test.ts` to the code in this [gist](https://gist.github.com/bbl4de/034585d9a8589a1717d2987ad6c36f5c) and run the test with `yarn hardhat test`.

Manual review
 
## Recommended Mitigation Steps

Consider removing `_percentage` parameter and use `inputTokenAmount` decoded from the `_data` parameter as `userClaim` instead. For example by returning it from `_validateData` and ensuring it is not more than the user is eligible for ( `inputTokenAmount <= userClaim`.
