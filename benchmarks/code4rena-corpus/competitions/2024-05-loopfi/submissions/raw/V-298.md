# Vulnerability details

## Impact
User who has deposited `WETH` into the contract could have his funds locked under a certain condition.

## Proof of Concept
This is the `_processLock()` function:
```solidity
    function _processLock(address _token, uint256 _amount, address _receiver, bytes32 _referral)
        internal
        onlyBeforeDate(loopActivation)
    {
        if (_amount == 0) {
            revert CannotLockZero();
        }
        if (_token == ETH) {
            totalSupply = totalSupply + _amount;
            balances[_receiver][ETH] += _amount;
        } else {
            if (!isTokenAllowed[_token]) {
                revert TokenNotAllowed();
            }
            IERC20(_token).safeTransferFrom(msg.sender, address(this), _amount);


            if (_token == address(WETH)) {
                WETH.withdraw(_amount);
                totalSupply = totalSupply + _amount;
                balances[_receiver][ETH] += _amount;
            } else {
                balances[_receiver][_token] += _amount;
            }
        }


        emit Locked(_receiver, _amount, _token, _referral);
    }
```
Whenever a user deposits `WETH` into the contract, his tokens get exchanged for `ETH` and essentially start getting treated as such throughout the contract.

If a user decides that he wants to withdraw his `WETH`, he would have to call the `withdraw()` function:
```solidity
function withdraw(address _token) external {
        if (!emergencyMode) {
            if (block.timestamp <= loopActivation) {
                revert CurrentlyNotPossible();
            }
            if (block.timestamp >= startClaimDate) {
                revert NoLongerPossible();
            }
        }

        uint256 lockedAmount = balances[msg.sender][_token];
        balances[msg.sender][_token] = 0;

        if (lockedAmount == 0) {
            revert CannotWithdrawZero();
        }
        if (_token == ETH) {
            if (block.timestamp >= startClaimDate){
                revert UseClaimInstead();
            }
            totalSupply = totalSupply - lockedAmount;

            (bool sent,) = msg.sender.call{value: lockedAmount}("");

            if (!sent) {
                revert FailedToSendEther();
            }
        } else {
            IERC20(_token).safeTransfer(msg.sender, lockedAmount);
        }

        emit Withdrawn(msg.sender, _token, lockedAmount);
    }
```
There, he has to put `ETH` address in order to get his funds back.
Imagine the following scenario:
1. Bob creates a contract to interact with this contract
2. He funds it with some WETH
3. He deposits his WETH into the contract (he might not even know that his WETH will get converted to ETH and will start getting treated as such)
4. At a later point, he decides to withdraw
5. He might even try to put his `WETH` address first and this will revert
6. He will put the `ETH` address and if he hasn't implemented a `receive()` function, that will revert causing his funds to get locked

The contract relies on the users carefully examining what the code does and realize that their WETH will be converted into ETH and will be treated as such. As we know, most users are not proficient in a coding language. A user could just check the public `isTokenAllowed` mapping for the `WETH` address and see that it is allowed and then proceed with the scenario above.

## Tools Used
Manual Review
## Recommended Mitigation Steps
Have logic in the `if (!sent)` check in the `withdraw()` function that allows users who deposited `WETH` to have an alternative way to claim them.
