# Vulnerability details

## Description

The README clearly states that,
`Once these addresses are set, all deposits are paused and users have  7 days  to withdraw their tokens in case they changed their mind, or they detected a malicious contract being set. On withdrawal, users loose all their points.
After these  7 days  the owner can call  convertAllETH, that converts all ETH in the contract for  lpETH.`

 That clearly means users should have a 7-day window (referred to as `TIMELOCK`) to withdraw their tokens after the loop contract addresses are set (if they change their mind). During this period, all deposits are supposed to be paused. But in the `withdraw` function , 7-day TIMELOCK period is not explicitly enforced, potentially preventing users from withdrawing their funds as intended.

Let's see the code snippet:

```solidity
function withdraw(address _token) external {
    if (!emergencyMode) {
        if (block.timestamp <= loopActivation) {
            revert CurrentlyNotPossible();
        }
        if (block.timestamp >= startClaimDate) {
            revert NoLongerPossible();
        }
    }
    // Withdrawal logic...
}
```

The issue lies in the conditions checked within the `withdraw` function. The function only verifies if the current timestamp is before `loopActivation` or after `startClaimDate`, without explicitly considering the 7-day TIMELOCK period. 
This means that when (`!emergencyMode`) after `loopActivation`, when the TIMELOCK period starts (before the convertAllETH and startCLaimDate start), A user can't withdraw his funds.

## Impact

The lack of enforcement for the `TIMELOCK` withdrawal window can have significant consequences:

1. **Locked Funds**: Users who intend to withdraw their funds within the documented 7-day window may find themselves unable to do so if `startClaimDate` is set prematurely. This can result in users' funds being locked in the contract, contrary to their expectations and the stated functionality.

2. **User Dissatisfaction**: The inability to withdraw funds during the promised window can lead to user dissatisfaction and loss of trust in the contract and the platform. Users may feel misled or deceived if they are unable to access their funds as documented.

Consider the following scenario:

1. The PrelaunchPoints contract sets the `loopActivation` timestamp, and users are informed that they have a 7-day window to reconsider their participation and withdraw their funds if desired.
2. A user decides to withdraw their funds on the 6th day after (changes his mind) and`loopActivation` has done already.
3. Then the user tries to withdraw his funds, as he knows that he can withdraw within 7 days (before `convertAllETH`).
4. The `withdraw` function will revert with the `NoLongerPossible` error, preventing the user from accessing their funds during the promised withdrawal window because startClaimDate has not started

This scenario illustrates how the lack of explicit enforcement of the TIMELOCK withdrawal window can lead to users being unable to withdraw their funds as intended, contrary to the documented ([README](https://github.com/code-423n4/2024-05-loop/blob/main/README.md#description))  functionalities of the contract.

## Recommended Mitigation Steps

To mitigate this issue, the `withdraw` function should be modified to explicitly enforce the 7-day `TIMELOCK` withdrawal window. The function should allow withdrawals if the current timestamp is within 7 days of `loopActivation`.
and not done `converAllETH` called by the owner
