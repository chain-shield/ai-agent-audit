# Vulnerability details

## Impact
Users depositing `WETH` will be unable to claim rewards or stakes, leading to potential financial losses and reduced trust in the protocol.


## Proof of Concept
In the `PrelaunchPoints.sol` contract, there is a critical issue regarding how balances are recorded and managed for users who deposit WETH (Wrapped ETH).
when the users deposits WETH using `lock()` then it calls the  `_parselock()` function,it directly converts to ETH 
```
if (_token == address(WETH)) {
                WETH.withdraw(_amount);
                totalSupply = totalSupply + _amount;
                balances[_receiver][ETH] += _amount;//@audit-should be WETH
            }
```
now as we see during WETH deposit,contract recorded the user balance in ETH i.e ` balances[_receiver][ETH] += _amount;`
and when the user call the claim function with the WETH token,user gets always reverted with error `NothingToClaim();`
because it calculates the userStake as `uint256 userStake = balances[msg.sender][WETH];` here this always returns zero because during lock it recorded balance of weth as  
` balances[_receiver][ETH] += _amount`.therefore `userStake` will be always `0` and due to
```
if (userStake == 0) {
            revert NothingToClaim();
        }
```
WETH users get always reverted and gets nothing in return

Steps to Reproduce:
1. A user deposits WETH into the contract using the lock or lockFor functions.
2. The contract converts WETH to ETH and records the deposit under the user's ETH balance.
3. The user attempts to claim their stake or rewards using WETH as the token parameter.
4. The contract checks for a WETH balance, finds none, and returns a NothingToClaim error, despite the user having a balance derived from WETH deposits.

```
if (_token == address(WETH)) {
                WETH.withdraw(_amount);     
                totalSupply = totalSupply + _amount;

                balances[_receiver][WETH] += _amount;
            } 
```
and change logic in _claim() function
