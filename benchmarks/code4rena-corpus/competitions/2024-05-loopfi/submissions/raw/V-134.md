# Vulnerability details

## Impact
The users will not be able to look tokens if he uses setLoopAddresses() first after deploying the contract. 

## Proof of Concept
For example, a user deployed a contract and became the owner of the contract. 
```solidity
constructor(address _exchangeProxy, address _wethAddress, address[] memory _allowedTokens) {
        owner = msg.sender;
        exchangeProxy = _exchangeProxy;
        WETH = IWETH(_wethAddress);

        loopActivation = uint32(block.timestamp + 120 days);
        startClaimDate = 4294967295; // Max uint32 ~ year 2107 
       ...
}
```
The constructor initializes the ```loopActivation = uint32(block.timestamp + 120 days)``` variable.

https://github.com/code-423n4/2024-05-loop/blob/main/src/PrelaunchPoints.sol#L102

Next, the contract owner first decided not to set the addresses and used the ``setLoopAddresses()`` function. 

The ```loopActivation``` variable then sets ```uint32(block.timestamp)```.

https://github.com/code-423n4/2024-05-loop/blob/main/src/PrelaunchPoints.sol#L355

```solidity
function setLoopAddresses(address _loopAddress, address _vaultAddress)
        external
        onlyAuthorized
        onlyBeforeDate(loopActivation)
    {
        lpETH = ILpETH(_loopAddress);
        lpETHVault = ILpETHVault(_vaultAddress);
        loopActivation = uint32(block.timestamp);

        emit LoopAddressesUpdated(_loopAddress, _vaultAddress);
    }
```
Next, the users decided to lock his tokens or ETH and use one of the functions lockETH, lockETHFor, lock, lockFor, but he will not be able to send, because in the ```_processLock()``` function the modifier ```onlyBeforeDate(loopActivation)``` will never pass the check, because ```block.timestamp``` will always be larger. 

For example, after the contract owner has called ```setLoopAddresses()``` and ```loopActivation = uint32(block.timestamp)``` has been set, next the contract owner calls look().

https://github.com/code-423n4/2024-05-loop/blob/main/src/PrelaunchPoints.sol#L143-L148

```solidity
 function lock(address _token, uint256 _amount, bytes32 _referral) external {
        if (_token == ETH) {
            revert InvalidToken();
        }
        _processLock(_token, _amount, msg.sender, _referral);
    }
```
The lock() function then goes to the ```_processLock()``` function.

https://github.com/code-423n4/2024-05-loop/blob/main/src/PrelaunchPoints.sol#L172-L198

```solidity
function _processLock(address _token, uint256 _amount, address _receiver, bytes32 _referral)
        internal
        onlyBeforeDate(loopActivation)
    {
        if (_amount == 0) {
            revert CannotLockZero();
         ...
        }
```
The onlyBeforeDate(loopActivation) modifier is checked in the ```_processLock``` function. 

https://github.com/code-423n4/2024-05-loop/blob/main/src/PrelaunchPoints.sol#L525-L530

```solidity
modifier onlyBeforeDate(uint256 limitDate) {
        if (block.timestamp >= limitDate) {
            revert NoLongerPossible();
        }
        _;
    }
```
However, the check will never be passed here because the block.timestamp in the modifier will always be greater than the ```limitDate``` to which ```loopActivation``` is passed which was set in ```setLoopAddresses()```.

This renders the contract useless as the users will not be able to send tokens.
