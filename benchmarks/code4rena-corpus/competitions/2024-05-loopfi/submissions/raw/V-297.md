# Vulnerability details

## Impact
A malicious user can hunt for free tokens with an extremely low risk, just 1 wei of any of the allowed tokens which he can also later claim, allowing him to screw other users for virtually no risk.

## Proof of Concept
This is the `claim()` function:
```solidity
function _claim(address _token, address _receiver, uint8 _percentage, Exchange _exchange, bytes calldata _data)
        internal
        returns (uint256 claimedAmount)
    {
        uint256 userStake = balances[msg.sender][_token];
        if (userStake == 0) {
            revert NothingToClaim();
        }
        if (_token == ETH) {
            claimedAmount = userStake.mulDiv(totalLpETH, totalSupply);
            balances[msg.sender][_token] = 0;
            lpETH.safeTransfer(_receiver, claimedAmount);
        } else {
            uint256 userClaim = userStake * _percentage / 100;
            _validateData(_token, userClaim, _exchange, _data);
            balances[msg.sender][_token] = userStake - userClaim;

            // At this point there should not be any ETH in the contract
            // Swap token to ETH
            _fillQuote(IERC20(_token), userClaim, _data);

            // Convert swapped ETH to lpETH (1 to 1 conversion)
            claimedAmount = address(this).balance;
            lpETH.deposit{value: claimedAmount}(_receiver);
        }
        emit Claimed(msg.sender, _token, claimedAmount);
    }
```
We can see that any user can end up in the if/else statements as long as he has at least 1 wei of token locked. Thus, a malicious user can lock 1 wei of any of the allowed tokens and end up in the `else` statement as that token is not ETH.

Then, there are some validations and his 1 wei will get converted to ETH. Then, the issue arises because `claimedAmount` gets the value of `address(this).balance`. Since, any user can call the `receive()` function of the contract and send Ether directly, they can claim any ETH that was sent that way. Furthermore, he could even do this more than once if he puts percentage to be at 0.

While this issue relies on a user mistakenly calling the `receive()` function of the contract, this is not the actual root cause of the issue and it also allows malicious users to game the system and get `lpETH` tokens for free, esentially allowing a person with low morals and ethics to own a share of the total supply of `lpETH` which is definitely not ideal for any protocol. The issue doesn't just allow a careless user to lose his Ethereum which would clearly be his mistake but allows a malicious actor to steal his tokens thus I believe that this issue should be a Medium issue and not a Low.

## Tools Used
Manual Review
## Recommended Mitigation Steps
Cache the `address(this).balance` before the swap and then use the difference between the cached balance and the newly fetched one to determine the `claimedAmount`.
