# Vulnerability details

## Issue Description
The user wants to lock their token by calling any lock functions, which leads to the `_processLock` internal function. However, before their transaction is confirmed, the admin executes the `setLoopAddresses` function, changing the `loopActivation` state. This change allows for the potential reordering of transactions by frontrunners, resulting in the user's transaction being reverted.
```java
function _processLock(address _token, uint256 _amount, address _receiver, bytes32 _referral)
        internal
@>        onlyBeforeDate(loopActivation) {
        // ...
}
```
```java
function setLoopAddresses(address _loopAddress, address _vaultAddress)
        external
        onlyAuthorized
        onlyBeforeDate(loopActivation)
    {
        lpETH = ILpETH(_loopAddress);
        lpETHVault = ILpETHVault(_vaultAddress);
@>        loopActivation = uint32(block.timestamp);

        emit LoopAddressesUpdated(_loopAddress, _vaultAddress);
    }
```

## Impact
Users miss their chance to lock their tokens due to the potential reordering of transactions by frontrunners, leading to the user's transaction being reverted.

## Proof of Concept
Here is the scenario:
1.  Alice (or multiple users) wants to lock her token by calling any lock functions which leads to the `_processLock` internal function which initiates the locking before the `loopActivation` state (`block.timestamp < loopActivation`).
2. While Alice's transaction is pending in the mempool, the contract owner executes the `setLoopAddresses` function, updating the `loopActivation` state to the current timestamp.
3. Frontrunners observe the pending transactions and reorder them, potentially causing Alice's transaction (or multiple users) to be reverted because the `onlyBeforeDate(loopActivation)` modifier no longer passes.


## Tools Used
manual review

## Recommended Mitigation Steps
*Let the owner of the contract initiate the user's token*. implement a queue system where the locking process is controlled correctly. explore the possibility of batching transactions where the contract receives and aggregates user tokens but won't update the balances. then before calling the `setLoopAddresses`, the owner initiates the locking process and updates the user balances on behalf of the users. the owner makes sure the tx succeeds and then calls the `setLoopAddresses` **Safely**
