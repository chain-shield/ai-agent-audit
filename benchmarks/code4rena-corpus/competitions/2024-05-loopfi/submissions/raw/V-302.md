# Vulnerability details

## Vulnerability Details 
In the contract the totalSupply is correctly updated when ETH is locked directly and when WETH is locked and converted to ETH
And  is used in the calculation for claimedAmount when the token is ETH, but it is not updated within the _claim function, the  totalSupply is not reflect the correct state after claims are processed here 

```solidity
function _claim(address _token, address _receiver, uint8 _percentage, Exchange _exchange, bytes calldata _data)
    internal
    returns (uint256 claimedAmount)
{
    uint256 userStake = balances[msg.sender][_token];
    if (userStake == 0) {
        revert NothingToClaim();
    }
    if (_token == ETH) {
        claimedAmount = userStake.mulDiv(totalLpETH, totalSupply);
        balances[msg.sender][_token] = 0;
        lpETH.safeTransfer(_receiver, claimedAmount);
    } else {
        uint256 userClaim = userStake * _percentage / 100;
        _validateData(_token, userClaim, _exchange, _data);
        balances[msg.sender][_token] = userStake - userClaim;

        _fillQuote(IERC20(_token), userClaim, _data);

        claimedAmount = address(this).balance;
        lpETH.deposit{value: claimedAmount}(_receiver);
    }
    emit Claimed(msg.sender, _token, claimedAmount);
}

```
In the convertAllETH function 
It’s not adjust totalSupply, it only handles the conversion of ETH to lpETH and updates totalLpETH.
And in the withdraw The totalSupply is updated correctly during ETH withdrawals before the startClaimDate., after the startClaimDate, users must claim instead of withdraw, which lead to issues if totalSupply isn't managed correctly during claims.
There is a discrepancy in how totalSupply is managed. 
It is not consistently updated across all functions that modify the balances of tokens considered part of the stakable assets. 
And this inconsistency can lead to incorrect calculations in reward distributions, especially in functions like _claim where totalSupply is used to determine the proportion of assets a user is entitled to



## Root of the bug 

the bug is in the _claim function, is fails to correctly adjust totalSupply when a user claims their staked tokens. Specifically, the function's logic only updates the lpETH_balance but does not adjust totalSupply for non-ETH tokens correctly.

## Impact
Users can receive more or fewer lpETH tokens than they are entitled to based on their actual stake, leading to unfair rewards distribution.
