# Vulnerability details

## Impact

The PrelaunchPoints contract allows users to specify a percentage of their locked tokens to claim as lpETH rewards in the `claim` and `claimAndStake` functions. However, this percentage is not properly validated, which could allow users to claim more tokens than they actually have locked, potentially draining the contract of its assets.

## Issue Description

The `claim` and `claimAndStake` functions take a `_percentage` parameter that specifies what percent of the user's locked token balance should be claimed and converted to lpETH.

The `_claim` internal function then calculates the amount of tokens to claim based on this percentage:

```solidity
function _claim(address _token, address _receiver, uint8 _percentage, Exchange _exchange, bytes calldata _data)
    internal
    returns (uint256 claimedAmount) 
{
    uint256 userStake = balances[msg.sender][_token];
    if (userStake == 0) {
        revert NothingToClaim();
    }
    if (_token == ETH) {
        claimedAmount = userStake.mulDiv(totalLpETH, totalSupply);
        balances[msg.sender][_token] = 0; 
        lpETH.safeTransfer(_receiver, claimedAmount);
    } else {
        uint256 userClaim = userStake * _percentage / 100;
        _validateData(_token, userClaim, _exchange, _data);
        balances[msg.sender][_token] = userStake - userClaim;
        ...
    }
    ...
}
```

The issue is that `_percentage` is not validated to be less than or equal to 100. If a user passes a `_percentage` greater than 100, they will be able to claim more tokens than they actually have locked.

For example, if a user has 100 ABC tokens locked and they call `claim` with `_percentage = 200`, then `userClaim` will be calculated as 200 ABC tokens. The contract will then subtract 200 ABC from the user's balance and attempt to swap and transfer 200 ABC worth of ETH/lpETH to the user.

This effectively allows users to withdraw tokens that belong to other users or the contract itself, since the `balances` mapping can underflow and the contract will transfer out more assets than the user deposited.

## Proof of Concept

Consider a user who has locked 100 ABC tokens in the PrelaunchPoints contract. The contract itself holds 1000 ABC tokens in total.

The user calls `claim` with the following parameters:
```
_token = ABC
_percentage = 200
_exchange = Exchange.UniswapV3 
_data = VALID_SWAP_DATA_FOR_200_ABC
```

In `_claim`, `userClaim` will be calculated as:
```
userClaim = 100 * 200 / 100 = 200 ABC
```

The contract will then set the user's balance to:
```
balances[user][ABC] = 100 - 200 = -100 ABC
```

And will swap and transfer 200 ABC worth of ETH/lpETH to the user.

The user has effectively extracted an extra 100 ABC from the contract that belonged to other users or the contract itself.

If the user repeats this multiple times, they can drain a significant portion of the contract's ABC token balance.

Manual code review and analysis.

## Recommended Mitigation Steps

Add validation to ensure that `_percentage` is less than or equal to 100 in the `_claim` function:

```solidity
function _claim(address _token, address _receiver, uint8 _percentage, Exchange _exchange, bytes calldata _data)
    internal
    returns (uint256 claimedAmount) 
{
    require(_percentage <= 100, "Percentage must be less than or equal to 100");
    ...
}
```

This will ensure that users can't claim more than 100% of their locked token balance.
