# Vulnerability details

## Bug Report: Withdraw Function Vulnerability

### Summary:
The withdraw function in the contract includes a safeguard to prevent users from withdrawing Ether after a certain date (`startClaimDate`). However, there is a potential risk of user confusion or error if they attempt to withdraw Ether after this date, despite the function correctly advising against it.

### Bug Location:
The bug lies in the conditional checks related to the withdrawal of Ether (`_token == ETH`). Specifically, the issue occurs when users attempt to withdraw Ether after a certain date (`startClaimDate`). If the condition `block.timestamp >= startClaimDate` is met, the function reverts with the message `UseClaimInstead()`, advising users to use a different method for claiming funds after that date. However, there is a risk that users may still attempt to withdraw Ether despite this advisory, resulting in a reverted transaction.

### Impact:
If users mistakenly or intentionally trigger the condition to withdraw Ether after `startClaimDate`, the transaction will be reverted, and the Ether will remain in the contract. While the function advises users to use a different method for claiming funds after this date, there is still a risk of user error.

### Vulnerability Details:
The withdraw function includes a condition to revert transactions if users attempt to withdraw Ether after `startClaimDate`. While this prevents funds from being withdrawn after the specified date, there is a possibility of users mistakenly or intentionally triggering this condition, resulting in a reverted transaction.

### Proof of Concept:
The vulnerable code snippet can be found below:

```solidity
function withdraw(address _token) external {
    if (!emergencyMode) {
        if (block.timestamp <= loopActivation) {
            revert CurrentlyNotPossible();
        }

        // IDK why we should have this??
        if (block.timestamp >= startClaimDate) {
            revert NoLongerPossible();
        }
    }

    uint256 lockedAmount = balances[msg.sender][_token];
    balances[msg.sender][_token] = 0;

    if (lockedAmount == 0) {
        revert CannotWithdrawZero();
    }
    if (_token == ETH) {
        if (block.timestamp >= startClaimDate){
            revert UseClaimInstead();
        }
        totalSupply = totalSupply - lockedAmount;

        (bool sent,) = msg.sender.call{value: lockedAmount}("");

        if (!sent) {
            revert FailedToSendEther();
        }
    } else {
        IERC20(_token).safeTransfer(msg.sender, lockedAmount);
    }

    emit Withdrawn(msg.sender, _token, lockedAmount);
}
```

### Recommendation:
While the withdraw function includes a safeguard against withdrawing Ether after `startClaimDate`, additional measures could be implemented to further prevent user confusion or error. This could involve enhancing the function's documentation or providing clearer messaging to users about the appropriate withdrawal procedures.

### Conclusion:
The withdraw function effectively prevents Ether withdrawals after `startClaimDate`, but there remains a risk of user error if users attempt to withdraw funds after this date. By improving user guidance and communication, developers can reduce the likelihood of mistaken or intentional triggering of the revert condition and enhance the overall user experience.
