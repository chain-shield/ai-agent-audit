# Vulnerability details

## Impact
The claim method converts the sellToken to eth by swapping it.

However not all of the listed tokens price are same. Accordint to contest readme the targetted tokens are 

```
WETH, weETH, ezETH, rsETH, rswETH, uniETH, pufETH
```

However , there is a price difference in all of these tokens

which leads to users receiving less amount of tokens than the minimum 

acceptable by them if their transaction is delayed.


## Proof of Concept

The claim method is defined as 

```solidity
    function _claim(address _token, address _receiver, uint8 _percentage, Exchange _exchange, bytes calldata _data)
        internal
        returns (uint256 claimedAmount)
    {
        uint256 userStake = balances[msg.sender][_token];
        if (userStake == 0) {
            revert NothingToClaim();
        }
        if (_token == ETH) {
            claimedAmount = userStake.mulDiv(totalLpETH, totalSupply);
            balances[msg.sender][_token] = 0;
            lpETH.safeTransfer(_receiver, claimedAmount);
        } else {
            uint256 userClaim = userStake * _percentage / 100;
            _validateData(_token, userClaim, _exchange, _data);
            balances[msg.sender][_token] = userStake - userClaim;

            // At this point there should not be any ETH in the contract
            // Swap token to ETH
            _fillQuote(IERC20(_token), userClaim, _data);

            // Convert swapped ETH to lpETH (1 to 1 conversion)
            claimedAmount = address(this).balance;
            lpETH.deposit{value: claimedAmount}(_receiver);
        }
        emit Claimed(msg.sender, _token, claimedAmount);
    }
```

where `_fillQuote` doess the swap.

The current prices of these assets as of 5th May 2024 are

```
wEth $3,139.79
weETH $3,254.00
ezETH $3,088.86
RSETH $3,148.76

```

we can observe other is significant difference here .
So it means if the user claims at some time t1 ( swap happens at time t1 )

then the amount of eth they get back is x  , but if there transaction gets 

delayed and the price of target token rise , returning user amount y , where 

x > y by an amount >50$ then they will incur a loss of 50$ or more 

however there anticipated returned value might be the profit of 50$.

This clearly leads to ( on one aspect of the scene ) loss of funds to users in ETH.

which could have been prevented by protocol giving user the flexibility of

specifying slippage params .

## Recommended Mitigation Steps
Give user the flexibility of specifying slippage params such as the minimum amount 

of tokens out he wants to receive and the deadline param to specify what is the 

acceptable time range until the transaction execution can be acceptable for the user.
