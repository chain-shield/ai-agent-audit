# Vulnerability details

## Summary
The `ReentrancyGuardUpgradeable` contract from `OpenZeppelin` provides a modifier `nonReentrant` that prevents `reentrancy` attacks. It needs to be `initialized` to set the initial state for the `guard`. 

Without initialization, the `guard state` might be incorrect, and the `nonReentrant` modifier may not function as expected, leaving the contract vulnerable.

## Proof of Concept
[WithdrawQueue](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L11-L16) contract is `ReentrancyGuardUpgradeable`:
```solidity
contract WithdrawQueue is
    Initializable,
    PausableUpgradeable,
    ReentrancyGuardUpgradeable, // @audit Inherited Here
    WithdrawQueueStorageV1
{
```
However, this is not initialized in the [initialize()](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L64-L82) function:
```solidity
    function initialize(
        IRoleManager _roleManager,
        IRestakeManager _restakeManager,
        IEzEthToken _ezETH,
        IRenzoOracle _renzoOracle,
        uint256 _coolDownPeriod,
        TokenWithdrawBuffer[] calldata _withdrawalBufferTarget
    ) external initializer {
        //...

        __Pausable_init();
        // @audit Missing ReentrancyGuardUpgradeable initialization

        //...
    }
```
If the `ReentrancyGuardUpgradeable` is not initialized, the internal state variable `_status` in the `ReentrancyGuard` contract might not be set to the initial value expected by the `nonReentrant` modifier. The `nonReentrant` modifier works by checking and toggling this state variable to ensure that no `reentrant calls` can be made.

**Here's how the `nonReentrant` modifier looks**:
```solidity
modifier nonReentrant() {
    // On the first call to nonReentrant, _notEntered will be true
    require(_status != _ENTERED, "ReentrancyGuard: reentrant call");

    // Any calls to nonReentrant after this point will fail
    _status = _ENTERED;

    _;

    // By setting it back to _NOT_ENTERED upon completion,
    // the guard is reset for the next call to nonReentrant
    _status = _NOT_ENTERED;
}
```
If `_status` is not set to the initial value `_NOT_ENTERED` (which is typically 1), the `nonReentrant` modifier will not work as intended.

The functions affected by the missing initialization of `ReentrancyGuardUpgradeable` are those using the `nonReentrant` modifier:

- [fillEthWithdrawBuffer()](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L182)
- [fillERC20WithdrawBuffer(address _asset, uint256 _amount)](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L195)
- [withdraw(uint256 _amount, address _assetOut)](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L206)
- [claim(uint256 withdrawRequestIndex)](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L279)

2. `xRenzoDeposit` contract also inherits from ReentrancyGuardUpgradeable but is not initialized

## Impact
1. Modifier Failure: 
The `nonReentrant` modifier checks `_status` to ensure it's not `_ENTERED` (typically 2). If `_status` is not initialized to `_NOT_ENTERED`, the modifier may falsely assume a reentrant call is happening and revert legitimate transactions, or it may not prevent reentrant calls if `_status` is incorrectly set to `_ENTERED`.
2. Reentrancy Attacks: 
Without proper initialization, the contract is potentially open to `reentrancy` attacks. An `attacker` could exploit this by making a recursive call back into the contract before the initial function execution finishes, manipulating contract state or draining funds.

This is a Medium Risk according to [c4 Docs](https://docs.code4rena.com/awarding/judging-criteria/severity-categorization) 
> 2 — Med: Assets not at direct risk, but the function of the protocol or its availability could be impacted, or leak value with a hypothetical attack path with stated assumptions, but external requirements.

## Recommended Mitigation Steps
To ensure proper initialization, the `initialize()` function should include the initialization call for `ReentrancyGuardUpgradeable`:
```soidity
function initialize(
    // parameters
) external initializer {
    // existing initialization code

    // @audit Initialize the ReentrancyGuardUpgradeable
    __ReentrancyGuard_init();
}
```
The `__ReentrancyGuard_init()` function sets `_status` to `_NOT_ENTERED`, ensuring that the `nonReentrant` modifier will function correctly to prevent reentrant calls.
