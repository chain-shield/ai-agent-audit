# Vulnerability details

## Impact
This is vulnerable to readonly-reentrancy function (if read in other function) [TimelockController.isOperationDone(bytes32)](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/TimelockController.sol#L176-L178) 
```solidity
    function isOperationDone(bytes32 id) public view virtual returns (bool) {
        return getTimestamp(id) == _DONE_TIMESTAMP;
    }
```
State variables read that were written after the external call(s):
- TimelockController._timestamps
[(contracts/TimelockController.sol#32)](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/TimelockController.sol#L32) was read at `getTimestamp(id) == _DONE_TIMESTAMP`
[(contracts/TimelockController.sol#177)](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/TimelockController.sol#L177) This variable was written at (after external call):
- _afterCall(id) ([contracts/TimelockController.sol#327](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/TimelockController.sol#L327))

The issue is that the function reads the `_timestamps` state variable, which is written to after an external call, if another function calls `isOperationDone` and then modifies the `_timestamps` variable, it could potentially cause a reentrancy vulnerability.

Here's a breakdown of the issue:

  * `isOperationDone` function checks if an operation is done by checking if the timestamp for that operation is equal to the `_DONE_TIMESTAMP` ([line 177](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/TimelockController.sol#L177)).
  * The `_timestamps` variable is read in the `getTimestamp` function ([line 177](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/TimelockController.sol#L177)), which is a separate function that retrieves the timestamp for a given ID.
  * However, the `_timestamps` variable is written to in the `_afterCall` function ([line 327](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/TimelockController.sol#L327)), which is called after an external call.

If an attacker can call a function that modifies the `_timestamps` variable after the external call, they could potentially re-enter the `isOperationDone` function and cause unintended behavior.

## Proof of Concept
In a scenario where an attacker Creates a user account (e.g., attacker) and a target contract (e.g., TargetContract) that will interact with the TimelockController contract.

  * Call the execute function on the TimelockController contract with the attacker account, passing in the target contract's address, a value, payload, predecessor, and salt. This will trigger the `_afterCall` function, which writes to the `_timestamps` variable.
```solidity
contract.execute(targetContract, 0, payload, predecessor, salt);
```
  * Immediately call the `isOperationDone` function with the same `id` parameter used in the execute function. This will read the `_timestamps` variable, which was just modified.
```solidity
bool isDone = contract.isOperationDone(id);
```
**Expected behavior:** The `isOperationDone` function should return false, as the operation has not yet been marked as done.

**Actual behavior:** Due to the reentrancy vulnerability, the `isOperationDone` function returns true, indicating that the operation is done, even though it has not been marked as done.

With the `isOperationDone` function returning true, the attacker can now exploit this behavior to manipulate the contract's logic. For example, they can call the TargetContract's functions, thinking that the operation is done, while in reality, it has not been marked as done.

## Recommended Mitigation Steps
Ensure that the `_timestamps` variable is not modified after the external call, or to use a different approach to check if an operation is done. Use a separate mapping to store the operation status instead of relying on the `_timestamps` variable.
```solidity
mapping(bytes32 => bool) private _operationStatus;

function isOperationDone(bytes32 id) public view virtual returns (bool) {
    return _operationStatus[id];
}
```
Alternatively, use the `block.timestamp` directly in the `isOperationDone` function to avoid relying on the `_timestamps` variable.
```solidity
function isOperationDone(bytes32 id) public view virtual returns (bool) {
    return block.timestamp == _DONE_TIMESTAMP;
}
```
