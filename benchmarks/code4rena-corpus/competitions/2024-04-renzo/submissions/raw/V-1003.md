# Vulnerability details

## Impact
The [`xRenzoDeposit`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Bridge/L2/xRenzoDeposit.sol) contract allows users to deposit ETH or WETH on L2 in exchange for `xezETH` tokens. The exchange rate between the deposited asset and `xezETH` is determined by calling the internal [`getMintRate()`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Bridge/L2/xRenzoDeposit.sol#L289) function. 

`getMintRate()` is supposed to return the latest price from either the oracle (by calling `oracle.getMintRate()`) or from the `lastPrice` state variable, which can be updated directly by a receiver contract or the owner via [`updatePrice()`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Bridge/L2/xRenzoDeposit.sol#L310) and [`updatePriceByOwner()`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Bridge/L2/xRenzoDeposit.sol#L320) respectively.

The intention is for `getMintRate()` to always return the most recent price, whether it comes from the oracle or the receiver/owner. However, `getMintRate()` does not gracefully handle the case where `oracle.getMintRate()` reverts, failing to return a value even if a fresh `lastPrice` is available to be used.

In `RenzoOracleL2`, [`getMintRate()`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Bridge/L2/Oracle/RenzoOracleL2.sol#L50) fetches the latest round data from a custom Chainlink price feed, but reverts if the timestamp of this data is older than `MAX_TIME_WINDOW` (24 hours + 60 seconds):

```solidity
function getMintRate() public view returns (uint256, uint256) {
    (, int256 price, , uint256 timestamp, ) = oracle.latestRoundData();
    if (timestamp < block.timestamp - MAX_TIME_WINDOW) revert OraclePriceExpired();
    // ...
}
```

If `oracle.getMintRate()` reverts, `xRenzoDeposit.getMintRate()` will also revert, bubbling up the revert reason. This will prevent `getMintRate()` from falling back to the receiver or owner-provided `lastPrice`, and will cause the whole deposit transaction to revert.

The staleness check in `RenzoOracleL2.getMintRate()` is unnecessary, because `xRenzoDeposit._deposit()` already checks the returned timestamp and reverts if it is stale. The redundant check in the oracle will brick deposits whenever the oracle price is stale, even if there is a more recent price available from the receiver or owner.

## Proof of Concept
1. Oracle price on L2 becomes stale, i.e. its timestamp is older than 24 hours + 60 seconds
2. User attempts to call `depositETH()` or `deposit()` to deposit assets and mint `xezETH`
3. `_deposit()` is called internally, which calls `getMintRate()`
4. `getMintRate()` calls `oracle.getMintRate()`
5. `oracle.getMintRate()` reverts with `OraclePriceExpired`
6. The revert bubbles up and causes `xRenzoDeposit.getMintRate()` to revert
7. The user's deposit transaction fails
8. Any subsequent attempts to deposit by any user will also revert at step 6

## Recommended Mitigation Steps
Remove the staleness check and revert from `RenzoOracleL2.getMintRate()`.

The staleness check is already performed in `xRenzoDeposit._deposit()`, so it is redundant and harmful to have it in `RenzoOracleL2.getMintRate()` as well. Removing it will allow `xRenzoDeposit.getMintRate()` to fall back gracefully to the receiver or owner price when the oracle is stale.
