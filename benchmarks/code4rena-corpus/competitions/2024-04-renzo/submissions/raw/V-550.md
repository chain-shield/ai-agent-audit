# Vulnerability details

## Description
When a user creates a `withdraw` request, the amount to be redeemed is added to `claimReserve[assetOut]`.
```javascript
    function withdraw(uint256 _amount, address _assetOut) external nonReentrant {
 //.. ommitted code
        // add redeem amount to claimReserve of claim asset
 ->     claimReserve[_assetOut] += amountToRedeem;
//.. ommitted code

```
This ensures that the `_amount`, which the user specified, is reserved for claiming. 

Whenever `deposit` gets called the `bufferToFill` is calculated by calling `getBufferDeficit()`
```javascript
    function deposit(
        IERC20 _collateralToken,
        uint256 _amount,
        uint256 _referralId
    ) public nonReentrant notPaused {

//.. ommitted code
        // Check the withdraw buffer and fill if below buffer target
->      uint256 bufferToFill = depositQueue.withdrawQueue().getBufferDeficit(
            address(_collateralToken)
        );
        //.. ommitted code
```

`getBufferDeficit()` will call `getAvailableToWithdraw()`
```javascript
    function getBufferDeficit(address _asset) public view returns (uint256) {
->      uint256 availableToWithdraw = getAvailableToWithdraw(_asset);
        return
            withdrawalBufferTarget[_asset] > availableToWithdraw
                ? withdrawalBufferTarget[_asset] - availableToWithdraw
                : 0;
    }

    function getAvailableToWithdraw(address _asset) public view returns (uint256) {
        if (_asset != IS_NATIVE) {
            return IERC20(_asset).balanceOf(address(this)) - claimReserve[_asset];
        } else {
            return address(this).balance - claimReserve[_asset];
        }
    }
```
Let's take `NATIVE_TOKEN` as an example.
In the case of `NATIVE_TOKEN`,  `address(this).balance - claimReserve[_asset]` is returned. 

Inside `getBufferDeficit()`, this amount is checked against the `withdrawalBufferTarget`:
```javascript
    function getBufferDeficit(address _asset) public view returns (uint256) {
        uint256 availableToWithdraw = getAvailableToWithdraw(_asset);
        return
            withdrawalBufferTarget[_asset] > availableToWithdraw
                ? withdrawalBufferTarget[_asset] - availableToWithdraw
                : 0;
    }
```
After all of this the `bufferToFill` is returned and is now checked against the `_amount` that the user wants to deposit:
```javascript
//.. ommitted code
        uint256 bufferToFill = depositQueue.withdrawQueue().getBufferDeficit(
            address(_collateralToken)
        );
        if (bufferToFill > 0) {
->            bufferToFill = (_amount <= bufferToFill) ? _amount : bufferToFill;
//.. ommitted code
```
If the `amount` is less than or equal to  `buffertoFill`, `bufferToFill` will be set to `_amount`.
If this is the case the   `_amount -= bufferToFill;` will always result in 0. 

However, the problem is that `operatorDelegator.deposit(_collateralToken, _amount)` will always fail if `_amount` is 0.
```javascript
    function deposit(
        IERC20 token,
        uint256 tokenAmount
    ) external nonReentrant onlyRestakeManager returns (uint256 shares) {
->        if (address(tokenStrategyMapping[token]) == address(0x0) || tokenAmount == 0)
->            revert InvalidZeroInput();
//.. ommitted code
    }
```

This means that a user will not be able to deposit into Renzo Protocol when the `bufferToFill` is more than the amount that the user wants to deposit. This breaks the core functionality of the project and renders the deposit function void. Note that this does exploit does not even need a malicious user, `deposit()` will break with honest users interacting with the protocol.

## POC
Let:
1. `withdrawalBufferTarget[ETH] = 250e18`
2. `address(withdrawQueue).balance = 200e18`

- Alice calls `withdrawQueue.withdraw(50e18)`
	- This sets `claimReserve[ETH] = 50e18`
- Bob calls `deposit(30e18)`
	- `bufferToFill` will be calculated using these two functions:
```javascript
    function getBufferDeficit(address _asset) public view returns (uint256) {
		uint256 availableToWithdraw = getAvailableToWithdraw(_asset);
        return
            withdrawalBufferTarget[_asset] > availableToWithdraw
                ? withdrawalBufferTarget[_asset] - availableToWithdraw
                : 0;
    }

    function getAvailableToWithdraw(address _asset) public view returns (uint256) {
        if (_asset != IS_NATIVE) {
            return IERC20(_asset).balanceOf(address(this)) - claimReserve[_asset];
        } else {
            return address(this).balance - claimReserve[_asset];
        }
    }
```
- `availableToWithdraw` will be `200e18 - 50e18 = 150e18`
- `withdrawBufferTarget[ETH] > availableToWithdraw` will be `true` because `250e18 > 150e18`
- `bufferToFill` will be set to `100e18`
- This `if (bufferToFill > 0) {` will be entered:
	- `bufferToFill = (_amount <= bufferToFill) ? _amount : bufferToFill`
	- `_amount` is `30e18`, as specified in the parameters of the `deposit()` call.
	- `30e18 < 100e18` will evaluate to `true`
	- `bufferToFill` will be set to `_amount`, which is `30e18`
	- Then:
	- `_amount -= bufferToFill;
	- Since `_amount` and `bufferToFill` are the same amount, this will always result in `0`.
- Finally, after the `if-statement` is completed and the `withdrawBuffer` is filled, the following call is made which will fail because `_amount` is `0`:
- `operatorDelegator.deposit(_collateralToken, _amount);`
```javascript
    function deposit(
        IERC20 token,
        uint256 tokenAmount
    ) external nonReentrant onlyRestakeManager returns (uint256 shares) {
->        if (address(tokenStrategyMapping[token]) == address(0x0) || tokenAmount == 0)
->            revert InvalidZeroInput();
//.. ommitted code
```

## Recommendation
Implement a check that ensures that when `_amount = 0`, `operatorDelegator.deposit(_collateralToken, _amount);` will not be called.
