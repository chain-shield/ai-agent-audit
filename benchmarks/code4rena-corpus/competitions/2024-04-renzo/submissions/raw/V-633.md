# Vulnerability details

## Summary
The `mint()` function does not restrict `bridges` from minting tokens to their own addresses.

## Proof of Concept
The [setLimits()](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Bridge/xERC20/contracts/XERC20.sol#L135-L143) function is designed to allow the `owner` of the contract to update the minting and burning limits for a specific `bridge`.
```solidity
    function setLimits(
        address _bridge,
        uint256 _mintingLimit,
        uint256 _burningLimit
    ) external onlyOwner {
        _changeMinterLimit(_bridge, _mintingLimit);
        _changeBurnerLimit(_bridge, _burningLimit);
        emit BridgeLimitsSet(_mintingLimit, _burningLimit, _bridge);
    }
```
However, once these limits are set, the contract does not enforce any restrictions on whom the `bridge` can mint tokens to. This means that a `bridge`, once given a minting limit, could potentially choose to mint tokens to its own address instead of another user's address.

[mint()](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Bridge/xERC20/contracts/XERC20.sol#L96-L98) function:
This function is designed to be called by a `bridge` to mint tokens for a `_user`. 
```solidity
    // @notice Mints tokens for a user
    // @dev Can only be called by a bridge
    function mint(address _user, uint256 _amount) public virtual {
        _mintWithCaller(msg.sender, _user, _amount);
    }
```
And the internal [_mintWithCaller()](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Bridge/xERC20/contracts/XERC20.sol#L348-L358) function:
```solidity
    function _mintWithCaller(address _caller, address _user, uint256 _amount) internal {
        // Do not allow 0 value mints
        if (_amount == 0) revert IXERC20_INVALID_0_VALUE();


        if (_caller != lockbox) {
            uint256 _currentLimit = mintingCurrentLimitOf(_caller);
            if (_currentLimit < _amount) revert IXERC20_NotHighEnoughLimits();
            _useMinterLimits(_caller, _amount);
        }
        _mint(_user, _amount);
    }
```
Since `_mintWithCaller()` does not discriminate against the `_user` parameter, a bridge could call `mint()` with its own address as `_user`. The contract would then proceed to mint tokens to the `bridge`'s address, provided the minting limit allows for it.

By this, `bridges` can therefore increase their own token balances, which may not be the intended use case.

## Impact
This also means that if a `_user` wants to mint tokens, the `bridge` wont be in a position to offer the service as their minting limit would be zero after minting completely to themselves.

## Tools Used
Manual Review

## Recommended Mitigation Steps
To mitigate the risk of bridges self-minting and depleting their capacity to serve users:
- Amend the `mint()` function to restrict `bridges` from minting to their own addresses.
