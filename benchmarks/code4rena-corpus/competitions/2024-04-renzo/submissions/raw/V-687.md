# Vulnerability details

A validator staked balance can drop (slashing, penalties) while it's balance not yet verified on Eigenlayer. If this happens the protocol will not account for the losses.

Staking ETH to an operator validator requires two steps:

1. An admin calls [DepositQueue::stakeEthFromQueue()](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Deposits/DepositQueue.sol#L187):
    1. `32 ETH` are deposited in the validator
    2. The `stakedButNotVerifiedEth` variable is [increased by `32 ETH`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L358)

2. An admin calls [OperatorDelegator::verifyWithdrawalCredentials()](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L364):
    1. The `stakeButNotVerifiedEth` variable is decreased by the [current effective balance of the validator](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L385)

There is a timeframe between step `1` and step `2` in which the validator could receive penalties or could be slashed. In step `2` the variable `stakeButNotVerifiedEth` will only be lowered by the current effective balance of the validator, but the variable was increased by `32ETH` during step`1`. Because the variable is used in the [TVL calculation](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L343-L344), and was not properly lowered by `32ETH`, the protocol will consider the TVL to be higher than it actually is.

## Impact

The TVL will be considered higher than it actually is by the protocol, making some `ezETH` impossible to redeem for `ETH` because those `ETH` don't exist.

## Proof of Concept

1. An admin calls [DepositQueue::stakeEthFromQueue()](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Deposits/DepositQueue.sol#L187) to deposit `32ETH` into Alice validator
2. Alice validator receives some penalties, reducing the validator balance to `31ETH`
3. An admin calls [OperatorDelegator::verifyWithdrawalCredentials()](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L364), this will lower the `stakeButNotVerifiedEth` variable to `1ETH` and set the `podOwnerShares[]` [variable on Eigenlayer](https://github.com/Layr-Labs/eigenlayer-contracts/blob/mainnet/src/contracts/pods/EigenPodManager.sol#L118) to `31 ETH`.

Because both `podOwnerShares[]` (`31 ETH`) and `stakeButNotVerifiedEth` (`1 ETH`) are used in the TVL calculations, the protocol will consider the TVL to be equal to `32ETH` but the TVL should be `31ETH`.

## Recommended Mitigation Steps

Always lower the `stakeButNotVerifiedEth` by `32ETH` when executing [OperatorDelegator::verifyWithdrawalCredentials()](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L364). In case this fix is implemented and the situation described in the report happens, the TVL will instantly drop. The protocol should be able to handle instant TVL drops by implementing a proper withdrawal queue.
