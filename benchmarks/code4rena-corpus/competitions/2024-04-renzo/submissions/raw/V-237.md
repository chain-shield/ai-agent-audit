# Vulnerability details

## Impact

The passed amount `RenzoOracle#lookupTokenAmountFromValue` is in wei ( 18 decimals ) as evident from the WithdraQueue#withdraw from where it is called

to calculate the amount of tokens to redeem.

```solidity
  amountToRedeem = renzoOracle.lookupTokenAmountFromValue(
                IERC20(_assetOut),
                amountToRedeem
            );
```
This is also evident from the function's Natspec 

```  

/// @dev Given a single token and value, return amount of tokens needed to represent that value
    /// Assumes the token value is already denominated in the same decimal precision as the oracle
    function lookupTokenAmountFromValue(
        IERC20 _token,
        uint256 _value
    ) external view returns (uint256) {
        AggregatorV3Interface oracle = tokenOracleLookup[_token];
        if (address(oracle) == address(0x0)) revert OracleNotFound();

        (, int256 price, , uint256 timestamp, ) = oracle.latestRoundData();
        if (timestamp < block.timestamp - MAX_TIME_WINDOW) revert OraclePriceExpired();
        if (price <= 0) revert InvalidOraclePrice();

        // Price is times 10**18 ensure token amount is scaled
        return (_value * SCALE_FACTOR) / uint256(price);
    }

```

`//Assumes the token value is already denominated in the same decimal precision as the oracle`
if we take a look in RenzoOracle , the oracle decimals are ensured to be 18

```
  /// @dev Sets addresses for oracle lookup.  Permission gated to oracel admins only.
    /// Set to address 0x0 to disable lookups for the token.
    function setOracleAddress(
        IERC20 _token,
        AggregatorV3Interface _oracleAddress
    ) external nonReentrant onlyOracleAdmin {
        if (address(_token) == address(0x0)) revert InvalidZeroInput();

        // Verify that the pricing of the oracle is 18 decimals - pricing calculations will be off otherwise
        if (_oracleAddress.decimals() != 18)
            revert InvalidTokenDecimals(18, _oracleAddress.decimals());

        tokenOracleLookup[_token] = _oracleAddress;
        emit OracleAddressUpdated(_token, _oracleAddress);
    }
```
it means the value will be in 18 decimals.

however , the `lookupTokenAmountFromValue` multiplies the value with 10**18 

which is incorrect that will returning an amount 10**18 times more than it should.

## Proof of Concept
For example, suppose 
price of input token is 3000$.

and users pass in the `value` to withdraw worth 1e18.

What this function will do is it will return 1e18*10**18=10^35 
Due to `value` being multiplied by SCALER FACTOR.

effectively returning this huge amount which far greater than billions of times than the amount it should return

as a result withdraw function from withdraw queue will redeem so much tokens that 

we can't even image .

This will push huge orders in `withdrawRequests` mapping for msg.sender

When the tokens are not available to be withdrawn ( lack of token out balance in 

the contract ) , the user will face Denial of service in claim function 

because token transfers call will fail 

