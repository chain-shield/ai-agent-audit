# Vulnerability details

## Summarize 
The smart contract's claim function is susceptible to front-running attacks. This vulnerability allows a malicious actor to observe pending withdrawal requests and claim them before the original requester, potentially leading to unfair outcomes or losses for honest participants.
## Impact
The impact of this vulnerability is significant, especially in a decentralized finance (DeFi) context where transactions can have substantial financial implications. Front-running can lead to users receiving less than expected from their withdrawal requests or even losing their claims entirely. This can undermine trust in the contract and potentially lead to legal and financial disputes among users.
## Proof of Concept
To illustrate the concept of front-running, consider the following scenario:

Observation: A malicious actor monitors the blockchain for pending transactions involving the claim function.
Execution: Before the original requester's transaction is confirmed, the malicious actor sends their own transaction to claim the same withdrawal request.
Exploitation: By claiming the withdrawal request first, the malicious actor effectively "front-runs" the original requester, potentially leading to unfair outcomes.

## Recommended Mitigation Steps
To protect the claim function from front-running attacks, we can implement a commit-reveal scheme. This involves splitting the claim process into two steps: a commit phase where users submit a hashed version of their intended withdrawal request, and a reveal phase where users reveal the actual withdrawal request. This approach ensures that a malicious actor cannot predict the exact withdrawal request a user will claim, thus mitigating the risk of front-running.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

contract WithdrawalContract {
    // Assuming other parts of the contract are defined here

    // Mapping to store commitments
    mapping(address => bytes32) public commitments;

    // Function to commit to a withdrawal request
    function commitToClaim(uint256 withdrawRequestIndex) external {
        require(withdrawRequestIndex < withdrawRequests[msg.sender].length, "Invalid withdrawal request index");
        bytes32 commitment = keccak256(abi.encodePacked(withdrawRequestIndex));
        commitments[msg.sender] = commitment;
    }

    // Modified claim function with reveal phase
    function claim(uint256 withdrawRequestIndex) external nonReentrant {
        // Check if the commitment matches the revealed withdrawal request index
        require(keccak256(abi.encodePacked(withdrawRequestIndex)) == commitments[msg.sender], "Commitment does not match");

        // Clear the commitment
        commitments[msg.sender] = bytes32(0);

        // Proceed with the original claim logic
        WithdrawRequest memory _withdrawRequest = withdrawRequests[msg.sender][withdrawRequestIndex];
        require(block.timestamp - _withdrawRequest.createdAt >= coolDownPeriod, "Claim too early");

        // Subtract value from claim reserve for claim asset
        claimReserve[_withdrawRequest.collateralToken] -= _withdrawRequest.amountToRedeem;

        // Delete the withdraw request
        withdrawRequests[msg.sender][withdrawRequestIndex] = withdrawRequests[msg.sender][withdrawRequests[msg.sender].length - 1];
        withdrawRequests[msg.sender].pop();

        // Burn ezETH locked for withdraw request
        ezETH.burn(address(this), _withdrawRequest.ezETHLocked);

        // Send selected redeem asset to user
        if (_withdrawRequest.collateralToken == IS_NATIVE) {
            payable(msg.sender).transfer(_withdrawRequest.amountToRedeem);
        } else {
            IERC20(_withdrawRequest.collateralToken).transfer(msg.sender, _withdrawRequest.amountToRedeem);
        }

        // Emit the event
        emit WithdrawRequestClaimed(_withdrawRequest);
    }
}

Key Changes:
Commit Phase: Introduced a new function commitToClaim that allows users to commit to a withdrawal request by submitting a hashed version of the withdrawal request index. This function stores the commitment in a mapping.
Reveal Phase: Modified the claim function to include a check that verifies the commitment matches the revealed withdrawal request index. This ensures that the user is claiming the withdrawal request they originally committed to.
Clear Commitment: After the claim is processed, the commitment is cleared to prevent the same withdrawal request from being claimed multiple times.
