# Vulnerability details

## Summary
As per [Sponsor](https://github.com/code-423n4/2024-04-renzo/blob/main/README.md?plain=1#L329):
```javascript
* ezETH should be minted or redeemed based on current supply and TVL.
```
The calculation of the TVL is broken due to a wrongly executed nested loop, resulting in breaking this invariant.
## Description
The function `calculateTVLs()` is a critical function that is used numerous of times to calculate the current TVL.
```javascript
    function calculateTVLs() public view returns (uint256[][] memory, uint256[] memory, uint256) {
        //.. ommitted code
    }
```

However, there is a problem in the way the TVL is calculated. 
To be specific, when calculating the `totalWithdrawalQueueValue`, the data parameters passed to the `loopupTokenValue` function are wrong:
```javascript
    function calculateTVLs() public view returns (uint256[][] memory, uint256[] memory, uint256) {
        //.. ommitted code
        for (uint256 i = 0; i < odLength; ) {
            // Track the TVL for this OD
            uint256 operatorTVL = 0;

            // Track the individual token TVLs for this OD - native ETH will be last item in the array
            uint256[] memory operatorValues = new uint256[](collateralTokens.length + 1);
            operatorDelegatorTokenTVLs[i] = operatorValues;

            // Iterate through the tokens and get the value of each
            uint256 tokenLength = collateralTokens.length;
            for (uint256 j = 0; j < tokenLength; ) {
                // Get the value of this token

                uint256 operatorBalance = operatorDelegators[i].getTokenBalanceFromStrategy(
                    collateralTokens[j]
                );

                // Set the value in the array for this OD
                operatorValues[j] = renzoOracle.lookupTokenValue(
                    collateralTokens[j],
                    operatorBalance
                );

                // Add it to the total TVL for this OD
                operatorTVL += operatorValues[j];

                // record token value of withdraw queue
->              if (!withdrawQueueTokenBalanceRecorded) {
                    totalWithdrawalQueueValue += renzoOracle.lookupTokenValue(
                        collateralTokens[i],
                        collateralTokens[j].balanceOf(withdrawQueue)
                    );
                }

                unchecked {
                    ++j;
                }
            }

            // Get the value of native ETH staked for the OD
            uint256 operatorEthBalance = operatorDelegators[i].getStakedETHBalance();

            // Save it to the array for the OD
            operatorValues[operatorValues.length - 1] = operatorEthBalance;

            // Add it to the total TVL for this OD
            operatorTVL += operatorEthBalance;

            // Add it to the total TVL for the protocol
            totalTVL += operatorTVL;

            // Save the TVL for this OD
            operatorDelegatorTVLs[i] = operatorTVL;

            // Set withdrawQueueTokenBalanceRecorded flag to true
->          withdrawQueueTokenBalanceRecorded = true;

            unchecked {
                ++i;
            }
        }

```
`calculateTVLs` has a nested `for-loop`. In the first loop:
- i = 0
- j = 0

Since `withdrawQueueTokenBalanceRecorded = false`, we will enter the following `codeblock`:
```javascript
->              if (!withdrawQueueTokenBalanceRecorded) {
                    totalWithdrawalQueueValue += renzoOracle.lookupTokenValue(
                        collateralTokens[i],
                        collateralTokens[j].balanceOf(withdrawQueue)
                    );
                }
```
Let's say:
- `collateralTokens[0] = stETH`
- `collateralTokens[1] = wbETH`
Due to the fact that this `codeblock` is in the `nested loop`, `renzoOracle.lookupTokenValue` will be called with the parameters:
```javascript
    // first nested loop
    totalWithdrawalQueueValue += renzoOracle.lookupTokenValue(
        stETH,
        stETH.balanceOf(withdrawQueue)
    );

    // second nested loop
    totalWithdrawalQueueValue += renzoOracle.lookupTokenValue(
        stETH,
        wbETH.balanceOf(withdrawQueue)
    );
```

The second nested loop will use the `wbETH balance` of`address(withdrawQueue)`.
Since this value is obviously incorrect, when doing the calculation in `lookupTokenValue`, the return value will be wrong.

```javascript
    function lookupTokenValue(IERC20 _token, uint256 _balance) public view returns (uint256) {
        AggregatorV3Interface oracle = tokenOracleLookup[_token];
        if (address(oracle) == address(0x0)) revert OracleNotFound();

        (, int256 price, , uint256 timestamp, ) = oracle.latestRoundData();
        if (timestamp < block.timestamp - MAX_TIME_WINDOW) revert OraclePriceExpired();
        if (price <= 0) revert InvalidOraclePrice();

        // Price is times 10**18 ensure value amount is scaled
        return (uint256(price) * _balance) / SCALE_FACTOR;
    }
```

After this nested loop is finished, the `withdrawQueueTokenBalanceRecorded` flag will be set to `true`:
```javascript
->          withdrawQueueTokenBalanceRecorded = true;
```

Which means that the `totalWithdrawalQueueValue ` variable will only be updated in the first nested loop, and during this update it will be updated with the wrong values, poisining the TVL amount.

## Impact
Due to the fact that the project builds upon the correct calculation of the TVL, since the users will be able to mint more or less due to incorrect calculation, we say the impact is high.
