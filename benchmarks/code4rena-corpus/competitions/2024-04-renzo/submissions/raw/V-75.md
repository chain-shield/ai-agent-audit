# Vulnerability details

## Impact
The `verifyAndProcessWithdrawals` function in the `OperatorDelegator` contract processes a large number of withdrawals and performs complex operations on the provided data. If the arrays of withdrawal proofs, validator fields, and withdrawal fields are large, it can consume a significant amount of gas, potentially leading to a DoS condition.

An admin can provide large arrays of withdrawal proofs, validator fields, and withdrawal fields when calling the `verifyAndProcessWithdrawals` function, causing the transaction to consume an excessive amount of gas. This can result in the transaction exceeding the block gas limit and reverting, making the contract unusable or preventing other transactions from being processed. Consequently, the protocol's functionality and availability can be disrupted.

The Admin does not have to be malicious, an admin can be benevolent and still accidently trigger the Denial of service if the arrays added are too large.


## Proof of Concept

An admin, who has the `NativeEthRestakeAdmin` privileges, creates large arrays of withdrawal proofs, validator fields, and withdrawal fields.

The admin calls the `verifyAndProcessWithdrawals` function with the large input arrays.

The unbounded loop in the function is triggered, consuming a significant amount of gas and potentially exceeding the block gas limit.

The transaction reverts, causing a Denial of Service condition and disrupting the protocol's withdrawal processing functionality.

## Recommended Mitigation Steps
Consider implementing pagination or batching mechanisms to limit the number of withdrawals processed in a single transaction. This can be achieved by accepting a maximum limit parameter and processing the withdrawals in smaller batches. Additionally, consider optimizing the gas consumption of the `verifyAndProcessWithdrawals` function by streamlining the operations performed on the provided data.
