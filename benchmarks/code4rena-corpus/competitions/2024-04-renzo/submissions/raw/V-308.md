# Vulnerability details

## Impact
The `OptimismMintableXERC20Factory` contract, uses `abi.encodePacked()` to generate salt values for creating new contracts using CREATE3. However, `abi.encodePacked()` does not pad the input data to 32 bytes, which can lead to hash collisions.

When using `abi.encodePacked()` with dynamic types (such as strings or addresses) as input to a hash function like `keccak256()`, there is a risk of hash collisions. This means that different input data can result in the same hash value, which can lead to unintended contract deployments or other security issues.

For example, abi.encodePacked(0x123, 0x456) would result in the same hash as abi.encodePacked(0x1, 0x23456), which could potentially allow an attacker to deploy a malicious contract with the same address as a legitimate contract.

## Proof of Concept
Deploy a malicious contract that contains a function to generate salt values using `abi.encodePacked()`.

In the malicious contract, implement a function that takes two different sets of input parameters and generates salt values using `abi.encodePacked()`.

Call the salt generation function in the malicious contract with the two different sets of input parameters.

Observe that the resulting salt values are the same, despite the input parameters being different.

Attempt to deploy a malicious contract using the generated salt value, potentially colliding with the deployment of a legitimate contract by the `OptimismMintableXERC20Factory`.

## Recommended Mitigation Steps
Use `abi.encode()` instead of `abi.encodePacked()` when generating salt values for contract deployments. `abi.encode()` pads the input data to 32 bytes, which helps prevent hash collisions.
Plus, it's recommended to use `bytes.concat()` instead of `abi.encodePacked()` when concatenating strings or bytes, as `bytes.concat()` is more resistant to hash collisions.
