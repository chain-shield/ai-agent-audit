# Vulnerability details

## Vulnerability Detail
When an admin calls `DepositQueue.sweepERC20()`, it approves the tokens to the `RestakeManager`, and calls `RestakeManager.depositTokenRewardsFromProtocol()`.

Then, that function deposits 100% of the received tokens straight to the chosen `OperatorDelegator`:

```solidity
/// @dev Deposit ERC20 token rewards from the Deposit Queue
/// Only callable by the deposit queue
function depositTokenRewardsFromProtocol(
    IERC20 _token,
    uint256 _amount
) external onlyDepositQueue {
    // Get the TVLs for each operator delegator and the total TVL
    (, uint256[] memory operatorDelegatorTVLs, uint256 totalTVL) = calculateTVLs();

    // Determine which operator delegator to use
    IOperatorDelegator operatorDelegator = chooseOperatorDelegatorForDeposit(
        operatorDelegatorTVLs,
        totalTVL
    );

    // Transfer the tokens to this address
    _token.safeTransferFrom(msg.sender, address(this), _amount);

    // Approve the tokens to the operator delegator
    _token.safeApprove(address(operatorDelegator), _amount);

    // Deposit the tokens into EigenLayer
    operatorDelegator.deposit(_token, _amount); //@audit Not reserving any funds for WithdrawQueue!!
}
```

The issue is that the `WithdrawQueue`'s buffer is not being prioritised in this flow.

The protocol intends to prioritise filling the `WithdrawQueue` before re-depositing rewards back into EigenLayer, as mentioned by the sponsor here:
> **ME:** hey @0xJJ, for rewards that the protocol obtained, is it number 1 priority to re-deposit it to an OperatorDelegator, or is it higher priority to fill the WithdrawQueue's buffer first? 

> **@0xJJ:** First priority is to fill the withdrawQueue and then remaining gets deposited back to EigenLayer.

## Impact
The withdraw queue's buffer is not maintained, which can lead to inability for users to withdraw their funds. This would be a critical disruption to protocol functionality.

## Recommended Mitigation Steps
In `depositTokenRewardsFromProtocol()`, consider adding the following logic before depositing the remaining `_amount` to the `OperatorDelegator`.

This ensures that the `WithdrawQueue` is prioritised over re-depositing into `EigenLayer`.
```solidity
// Check the withdraw buffer and fill if below buffer target
uint256 bufferToFill = withdrawQueue.getBufferDeficit(
    address(_token)
);
if (bufferToFill > 0) {

    // cap the 'bufferToFill' at '_amount'
    if ((_amount <= bufferToFill)) {
        bufferToFill = _amount;
    }
    // update amount to send to the operator Delegator
    _amount -= bufferToFill;

    // safe Approve for depositQueue
    _token.safeApprove(address(depositQueue), bufferToFill);

    // fill Withdraw Buffer via depositQueue
    depositQueue.fillERC20withdrawBuffer(address(_token), bufferToFill);
}
```
