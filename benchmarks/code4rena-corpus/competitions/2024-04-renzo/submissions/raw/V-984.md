# Vulnerability details

## Issue Description

When a user deposits ETH or wETH into the L2 `xRenzoDeposit` contract, the internal `_deposit` function is called and it's responsible for trading ETH/wETH into nextETH and then minting xezETH to the depositor.

```solidity
function _deposit(
    uint256 _amountIn,
    uint256 _minOut,
    uint256 _deadline
) internal returns (uint256) {
    // calculate bridgeFee for deposit amount
    uint256 bridgeFee = getBridgeFeeShare(_amountIn);
    // subtract from _amountIn and add to bridgeFeeCollected
    _amountIn -= bridgeFee;
    bridgeFeeCollected += bridgeFee;

    // Trade deposit tokens for nextWETH
    uint256 amountOut = _trade(_amountIn, _deadline);
    
    ...

    // Mint xezETH to the user
    IXERC20(address(xezETH)).mint(msg.sender, xezETHAmount);

    // Emit the event and return amount minted
    emit Deposit(msg.sender, _amountIn, xezETHAmount);
    return xezETHAmount;
}
```

Let's focus on the `_trade` function which handles the trade of deposit tokens for nextWETH:

```solidity
function _trade(uint256 _amountIn, uint256 _deadline) internal returns (uint256) {
    // Approve the deposit asset to the connext contract
    depositToken.safeApprove(address(connext), _amountIn);

    // We will accept any amount of tokens out here... The caller of this function should verify the amount meets minimums
    uint256 minOut = 0;

    // Swap the tokens
    uint256 amountNextWETH = connext.swapExact(
        swapKey,
        _amountIn,
        address(depositToken),
        address(collateralToken),
        minOut,
        _deadline
    );

    // Subtract the bridge router fee
    if (bridgeRouterFeeBps > 0) {
        uint256 fee = (amountNextWETH * bridgeRouterFeeBps) / 10_000;
        amountNextWETH -= fee;
    }

    return amountNextWETH;
}
```

As it can be seen after executing the swap using `connext.swapExact`, the function will deduct a portion of the output nextETH amount as a bridge router fee, so this fee portion will not be considered when minting xezETH to the user.

After the deposit all the nextETH (including the bridge router fee amount) is kept inside the contract until the `sweep()` function is called to initiate the transfer to L1:

```solidity
function sweep() public payable nonReentrant {
    // Verify the caller is whitelisted
    if (!allowedBridgeSweepers[msg.sender]) {
        revert UnauthorizedBridgeSweeper();
    }

    // Get the balance of nextWETH in the contract
    uint256 balance = collateralToken.balanceOf(address(this));

    // If there is no balance, return
    if (balance == 0) {
        revert InvalidZeroOutput();
    }

    // Approve it to the connext contract
    collateralToken.safeApprove(address(connext), balance);

    // Need to send some calldata so it triggers xReceive on the target
    bytes memory bridgeCallData = abi.encode(balance);

    connext.xcall{ value: msg.value }(
        bridgeDestinationDomain,
        bridgeTargetAddress,
        address(collateralToken),
        msg.sender,
        balance,
        0, // Asset is already nextWETH, so no slippage will be incurred
        bridgeCallData
    );

    // send collected bridge fee to sweeper
    _recoverBridgeFee();

    // Emit the event
    emit BridgeSwept(bridgeDestinationDomain, bridgeTargetAddress, msg.sender, balance);
}
```

We can see that the function transfer all the nextETH contract balance (which is the `collateralToken` in the code above) to L1, and because as demonstrated above the bridge router fees are also part of the nextETH contract balance they will be sent to L1 as well.

In the L1, those funds will be locked into a lockBox and can only be withdrawn by burning the received xezETH later on, this is an issue because there is no xezETH tokens that are backing the bridge router fees that were also sent to L1 as those were excluded from the mint calculation when the user deposits and thus those funds will end up stuck in the lock box without possibility to withdraw them.

It's worth noting that in the L2 `xRenzoDeposit` contract there is a `recoverERC20` function that could be invoked by the owner to get those fees before the `sweep()` call, but this will be difficult as the owner will not know what exact amount of fees to withdraw, add to that the `sweep()` function could be called before he has the ability to invoke `recoverERC20` as there will be multiple possible callers for the function (all parties with the flag `allowedBridgeSweepers` set to true).

This issue could potentially result in a loss of funds for the protocol.

## Impact

The nextETH bridge router fees generated when users deposit into the L2 `xRenzoDeposit` could end up stuck forever into the lock box on L1 resulting in a loss of funds for the protocol.

## Tools Used

Manual review, VS Code

## Recommended Mitigation

To address this issue, there must be a state variable that tracks the amount of nextETH bridge router fees accumulated (similar to the `bridgeFeeCollected` state tracker used for the bridge fee share) and those must be excluded in the `sweep()` call.
