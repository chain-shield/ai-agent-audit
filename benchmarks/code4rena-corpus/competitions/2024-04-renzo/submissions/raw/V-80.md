# Vulnerability details

## Summary

According to Docs:
```solidity
Renzo allows users to deposit either ETH or LSTs (like stETH and wbETH), 
and in return, it mints an equivalent amount of ezETH, a reward-bearing token.
```
From this, the protocol accepts `stETH` as collateral that a user can deposit to mint `ezETH`. However, as a `rebasing token`, the protocol needs to integrate them into the system. But as it is now the system is definitely not compatible with such tokens.

## Proof of Concept
`deposit()`, `depositTokenRewardsFromProtocol()` and any other accounting related functions perform operations using inputed/recorded `amounts`. They don't query the `existing balance` of tokens before or after receiving/sending in order to properly account for tokens that shift balance over time (`rebasing`).

> [deposit()](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L491-L576)
```solidity
    function deposit(
        IERC20 _collateralToken,
        uint256 _amount,
        uint256 _referralId
    ) public nonReentrant notPaused {
        // Verify collateral token is in the list - call will revert if not found
        uint256 tokenIndex = getCollateralTokenIndex(_collateralToken);

        // @audit No balance query before transfer

        // Transfer the collateral token to this address
        _collateralToken.safeTransferFrom(msg.sender, address(this), _amount);

        //...

        // Mint the ezETH
        ezETH.mint(msg.sender, ezETHToMint);


        //...
    }
```

> [depositTokenRewardsFromProtocol()](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L647-L668)

```solidity
    function depositTokenRewardsFromProtocol(
        IERC20 _token,
        uint256 _amount
    ) external onlyDepositQueue {
        //...

        // Transfer the tokens to this address
        _token.safeTransferFrom(msg.sender, address(this), _amount);


        // Approve the tokens to the operator delegator
        _token.safeApprove(address(operatorDelegator), _amount);

```

Depositing `rebasing` tokens into a system that does not support them can lead to several issues:
- Incorrect Balance Tracking: 
The system may not account for balance changes due to rebases, leading to incorrect display or accounting of the user's holdings.
- Value Discrepancies: 
The value of the user's deposit could be misrepresented, as the system might not update the user's balance in response to the token's supply changes.

## Impact
Impact - High - It simply won't work.

## Tools Used
Manual review

## Recommended Mitigation Steps
Adjust the code to check the `token.balanceOf()` before and after doing any operation related to the token transfers.
