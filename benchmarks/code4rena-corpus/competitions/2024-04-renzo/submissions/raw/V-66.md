# Vulnerability details

## Impact
The `receive` function in the `DepositQueue` contract does not check the return value of the low-level call made to the `depositQueue` contract. If the call fails, the transaction will still be considered successful, and the `RewardsDeposited` event will be emitted, leading to an inconsistent state.

If the call to the `depositQueue` contract fails, but the transaction is still considered successful, it can lead to several issues:

Loss of Funds: If the `depositQueue` contract fails to handle the received Ether correctly, the funds sent to it may be lost or stuck in the contract.

Inconsistent State: The `DepositQueue` contract may update its internal state or emit events as if the call succeeded, even though it actually failed.

Misleading Events: The emitted `RewardsDeposited` event may provide misleading information to users and external systems, indicating that rewards were forwarded successfully when they were not.


## Proof of Concept
Create a new test file in the test folder and copy and paste the code below into the new test file:

```javascript
// SPDX-License-Identifier: MIT
pragma solidity 0.8.19;

import {Test} from "forge-std/Test.sol";
import "../contracts/Deposits/DepositQueue.sol";
import "../contracts/RestakeManager.sol";
import "../contracts/Permissions/RoleManager.sol";
import "../contracts/Delegation/OperatorDelegator.sol";

contract MockRoleManager is RoleManager {
    constructor(address _testContract) {
        _disableInitializers();
        _grantRole(DEFAULT_ADMIN_ROLE, msg.sender);
        _grantRole(RESTAKE_MANAGER_ADMIN, _testContract);
    }
}

contract MockDepositQueue is DepositQueue {
    constructor(IRoleManager _roleManager) {
        _disableInitializers();
        roleManager = _roleManager;
    }
}

contract MockRestakeManager is RestakeManager {
    function setDepositQueue(IDepositQueue _depositQueue) external {
        depositQueue = _depositQueue;
    }
}

contract DepositQueueTest is Test {
    MockRoleManager public roleManager;
    MockDepositQueue public depositQueue;
    MockRestakeManager public restakeManager;

    function setUp() public {
        roleManager = new MockRoleManager(address(this));
        restakeManager = new MockRestakeManager();
        depositQueue = new MockDepositQueue(roleManager);
        depositQueue.setRestakeManager(restakeManager);
        restakeManager.setDepositQueue(depositQueue);
    }

    function testUncheckedReturnValueInReceive() public {
        // Arrange
        vm.deal(address(depositQueue), 1 ether);

        // Act
        (bool success,) = address(depositQueue).call{value: 1 ether}("");

        // Assert
        assertFalse(success, "Expected the call to fail");
    }

}
```
Run this test with `forge test --mt testUncheckedReturnValueInReceive`

A walkthrough of the test:
The depositQueue contract is funded with 1 ether using vm.deal.
A low-level call is made to the receive function of the depositQueue contract, sending 1 ether.
The test asserts that the call should fail by checking the success variable.

After running this test, you will see that the test passes, indicating that the receive function does not handle the failure case correctly, and the transaction is considered successful even when the call fails.

The unchecked return value vulnerability exists in the following line:
```javascript
(bool success, ) = feeAddress.call{ value: feeAmount }("");
```

And the unchecked return value vulnerability can be found here:
https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Deposits/DepositQueue.sol?plain=1#L168

An attacker could potentially exploit this vulnerability by performing the following steps:

The attacker sets up a malicious contract as the `feeAddress`.
When the receive function is called, and the protocol fees are sent to the malicious contract, the attacker's contract intentionally reverts or fails.
The `DepositQueue` contract continues execution without checking the return value of the call, considering the transaction successful.
The attacker can repeatedly trigger this scenario, causing the protocol fees to be lost and the `DepositQueue` contract to emit misleading events.

## Recommended Mitigation Steps
Check the return value of the low-level call in the receive function of the `DepositQueue` contract. If the call fails, the transaction should be reverted to prevent inconsistent state and ensure that the `RewardsDeposited` event is emitted only when the rewards are actually forwarded successfully.

Add a require statement to check the success variable. By adding a require statement to check the success variable, the transaction will revert if the call to the `depositQueue` contract fails, preventing inconsistent state and ensuring accurate event emission.
