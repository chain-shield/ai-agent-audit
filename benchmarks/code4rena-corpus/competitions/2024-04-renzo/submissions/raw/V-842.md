# Vulnerability details

## Description
Calculation of total TVL in the protocol is critical for deposits, withdrawals, reward deposit and calculation of EzETH. From `RestakeManager.calculateTVLs()`. Next math is relevant for the calculation of total TVL:

$$getOperatorDelegatorTokenTVL(OdIndex,token) = operatorDelegators[OdIndex].getTokenBalanceFromStrategy(token) \times oracle[token].latestRoundData().price$$

$$getOperatorDelegatorTokenTVLEth(OdIndex) = operatorDelegators[OdIndex].getStakedETHBalance()$$

$$getOperatorDelegatorTVL(OdIndex) = (\sum_{i = 0}^{|collateralTokens|} operatorDelegators[OdIndex].getTokenBalanceFromStrategy(collateralTokens[i]) \times oracle[collateralTokens[i]].latestRoundData().price) + getOperatorDelegatorTokenTVLEth(OdIndex)$$

$$getWithdrawalQueueValue(token) = token.balanceOf(withdrawQueue) \times oracle[token].latestRoundData().price$$

$TotalTVL = (\sum_{i = 0}^{|operatorDelegators|} getOperatorDelegatorTVL(i)) + depositQueue.balance + withdrawQueue.balance + \sum_{j = 0}^{|collateralTokens|}getWithdrawalQueueValue(collateralTokens[j])$

$$mintEzETH(collateralToken,collateralAmount) = \frac{ezETH.totalSupply}{1 - \frac{ collateralAmount \times oracle[collateralToken].latestRoundData().price}{collateralAmount \times oracle[collateralToken].latestRoundData().price + TotalTVL}} - ezETH.totalSupply$$ 

The main problem with current implementation is the calculation of term $\sum_{j = 0}^{|collateralTokens|}getWithdrawalQueueValue(collateralTokens[j])$ in $TotalTVL$ which is not done properly, breaking many critical invariants. 

## Impact
Invariants related to deposits, withdrawals, reward deposits, and EzETH rate calculation are broken due to wrong implementation of total TVL in function`RestakeManager.calculateTVLs()`

## POC
Notice comment in this simplified code snippet from `RestakeManager.calculateTVLs()`:
```solidity
for (uint256 i = 0; i < odLength; ) {
    //...
    for (uint256 j = 0; j < tokenLength; ) {
        // ..
        if (!withdrawQueueTokenBalanceRecorded) {
            // @follow-up Record in first iteration
            // for each token
            totalWithdrawalQueueValue += renzoOracle.lookupTokenValue(
                collateralTokens[i], // @audit Choice based on OD, notice i
                collateralTokens[j].balanceOf(withdrawQueue) // @audit Choice based on token, notice j
            );
        }
        //...
    }
    //...
    withdrawQueueTokenBalanceRecorded = true;
    //...
}
```

Renzo protocol seems to be trying to save gas when calculating `totalWithdrawalQueueValue` by recording the value only in the first iteration of the loop related to operator delegators.

First of all this apporach is not effective given that they are copying in a memory variable `collateralTokens[j]`.

Second, and most important, in each iteration they query the correct collateral token balance that is held by the withdraw queue, but they simple chose the incorrect token to calculate when the call to `renzoOracle.lookupTokenValue(IERC20,uint256)` is done, given that as first parameter they sent `collateralTokens[i]`, when it should be `collateralTokens[j]`.

This leads to wrong calculation of `totalWithdrawalQueueValue`, affecting the calculation of total TVL and therefore affecting critical functions related to deposit, withdrawals, reward deposits, and EzETH rate calculation.

## Recommended mitagation
Simply choose the correct variable when calculating `totalWithdrawalQueueValue` in `RestakeManager.calculateTVLs()`.


```diff
    if (!withdrawQueueTokenBalanceRecorded) {
        totalWithdrawalQueueValue += renzoOracle.lookupTokenValue(
-           collateralTokens[i],
+           collateralTokens[j],
            collateralTokens[j].balanceOf(withdrawQueue)
        );
    }
```
