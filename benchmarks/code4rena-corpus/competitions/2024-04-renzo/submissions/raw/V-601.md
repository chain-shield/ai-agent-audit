# Vulnerability details

## Vulnerability Detail
The expected withdrawal flow in the `OperatorDelegator` is:
1. Admin calls `OperatorDelegator.queueWithdrawals()`
2. Admin/anyone calls `OperatorDelegator.verifyAndProcessWithdrawals()`
3. Admin calls `OperatorDelegator.completeQueuedWithdrawal()`

Step 1 increases `queuedShares[strategy]` for each strategy by the withdrawal amount, and Step 3 decreases the value by the same amount. 

The issue is that the protocol has not accounted for the following scenario:

For any reason, the operator can call `DelegationManager.undelegate(staker)` where `staker` is the `OperatorDelegator` contract.
This is normal functionality of EigenLayer's `DelegationManager` contract.
(Here are the [docs for the `undelegate()` function](https://github.com/Layr-Labs/eigenlayer-contracts/blob/dev/docs/core/DelegationManager.md#undelegate))

This function calls `_removeSharesAndQueueWithdrawal()` for each strategy, to queue a withdrawal for all the staker's strategies.

Now these funds can only be obtained by admin calling `OperatorDelegator.completeQueuedWithdrawal()`, so the funds are supposed to be retrievable.

**The key issue:**
However since these withdrawals were not queued via `queueWithdrawals()`, the `queuedShares[strategyAddress]` mapping was not incremented as expected. This means that the following line in `completeQueuedWithdrawal()` will revert due to underflow:

[OperatorDelegator.sol#L280-281](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol#L281)
```solidity
// deduct queued shares for tracking TVL
queuedShares[address(tokens[i])] -= withdrawal.shares[i];
```

This means that `completeQueuedWithdrawal()` will be un-callable, so the operator can (knowingly or unknowingly) grief the ENTIRE value of all the delegated shares by simply calling `undelegate()`.

## Impact

### Primary Impact:
When an operator calls `undelegate(staker)` where the `staker` is an `OperatorDelegator`, it permanently locks the ALL the staked  funds of that specific `OperatorDelegator`, they will be irretrievable due to underflow in `OperatorDelegator.completeQueudWithdrawal()`.

Note that the impact of this issue is not the same as a malicious operator simply misbehaving and getting the validators slashed.
This is because unlike in this vulnerability, getting slashed would equally affect ALL the stakers in the EigenPod/Strategy, not just one. 

### Secondary Impact:
A secondary impact is that since the `podOwnerShares` of the `OperatorDelegator` has been drastically decreased without increasing `queuedShares[strategy]` (which is what is expected to happen when the admin calls `OperatorDelegator.queueWithdrawals`), the values returned by `getStakedETHBalance` and `getTokenBalanceFromStrategy` will be severely lower. This leads to lower TVL calculations. ezETH holders who observe this in the mempool can front-run it to withdraw their ezETH at a much better rate, stealing value from the protocol. 

## Proof of Concept
Consider the following scenario:

Initial state: queuedShares[ETH] = 0, `podOwnerShares[OD]` = 32 ether

1. Operator calls `DelegationManager.undelegate(staker)`
    - staker is the `OperatorDelegator` address
    - this queues the 32 ether to be withdrawn
2. Renzo admin calls `OperatorDelegator.completeQueuedWithdrawal()` as this is the only way to obtain the withdrawn funds.
    - This call will always revert since it tries to subtract 32 ether from `queuedShares[ETH]` which will revert due to underflow.
    - Hence, all the withdrawn funds (32 ether) are stuck forever

The above example is only for ether, but the same issue arises for all the different strategies that the `OperatorDelegator` has shares in.

## Recommended Mitigation Steps
Add an extra boolean flag within `completeQueuedWithdrawals` so that if true, skips the decrementing of `queuedShares[address(tokens[i])]` when withdrawing funds after `DelegationManager.undelegate()` was called.

This will prevent it from reverting.

Example:
```diff
+   if (!skipUpdateQueuedShares) {
         // deduct queued shares for tracking TVL
         queuedShares[address(tokens[i])] -= withdrawal.shares[i];
+    }
```
