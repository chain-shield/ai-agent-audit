# Vulnerability details

## Impact

The direct storage collision between `roleManager` and `_owner` on same `slot 51` could lead to the loss of the `roleManager`'s reference to the `IRoleManager` contract, which is crucial for managing oracle admin roles. This could disrupt the contract's ability to perform necessary checks and operations, potentially exposing the contract to unauthorized access or failed transactions. Additionally, the `_owner` variable in `RenzoOracleL2` would overwrite the `roleManager` variable from `RenzoOracle` upon upgrade, leading to a loss of functionality related to role management and potentially compromising the contract's governance model.

## Proof of Concept
During a manual review of the `RenzoOracle` and `RenzoOracleL2` contracts using Visual Studio Code, I discovered a critical issue related to storage collision. Specifically, the `roleManager` variable in `RenzoOracle` and the `_owner` variable in `RenzoOracleL2` both occupy the same storage slot (51). This collision poses a significant risk to the integrity and functionality of the contracts, as it could lead to unintended overwriting of data and potential security vulnerabilities.

The issue can be reproduced by doing storage inspection on both contracts:

`forge inspect RenzoOracleL2 storage`

```
      "astId": 18875,
      "contract": "contracts/Bridge/L2/Oracle/RenzoOracleL2.sol:RenzoOracleL2",
@>      "label": "_owner",
      "offset": 0,
@>      "slot": "51",
      "type": "t_address"
```

and

`forge inspect RenzoOracle storage`

```
      "astId": 13289,
      "contract": "contracts/Oracle/RenzoOracle.sol:RenzoOracle",
@>      "label": "roleManager",
      "offset": 0,
@>      "slot": "51",
      "type": "t_contract(IRoleManager)13396"
```

The `forge inspect storage` command revealed that both `roleManager` in `RenzoOracle` and `_owner` in `RenzoOracleL2` occupy the same storage slot (51). This direct observation indicates a storage collision, as the `_owner` variable in `RenzoOracleL2` would overwrite the `roleManager` variable from `RenzoOracle` upon upgrade.

The specific line of code that utilizes `roleManager` is as follows:

```solidity
@> if (!roleManager.isOracleAdmin(msg.sender)) revert NotOracleAdmin();
```

This line checks if the sender (`msg.sender`) is an admin of the oracle by calling the `isOracleAdmin` function on the `roleManager` contract. The discovery of this storage collision raises concerns about the upgrade process from `RenzoOracle` to `RenzoOracleL2`, as it could inadvertently disrupt this functionality.

## Tools Used

Manual review using Visual Studio Code

## Recommended Mitigation Steps with Fix Code

To mitigate this issue, it is recommended to adjust the storage layout in `RenzoOracleL2` to ensure that the `_owner` variable does not overwrite the `roleManager` variable. This could involve reassigning the `_owner` variable to a different storage slot or using a `__gap` variable to reserve space for future upgrades without affecting existing storage slots.
