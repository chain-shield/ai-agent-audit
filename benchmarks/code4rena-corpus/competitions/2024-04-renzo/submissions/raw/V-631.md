# Vulnerability details

## Impact

Setting `feeBasisPoints` to 100% makes the protocol not be able to receive reward ETH and not be able to process the reward tokens.

## Proof of Concept

When receiving ETH reward, the function `receive()` is invoked. If `feeBasisPoints` was set to 100%, `feeAmount` is set to `msg.value` at `L167`, and `remainingRewards` is set to 0 at `L174`. As a result, invoking `_checkAndFillETHWithdrawBuffer()` function at `L176` will be reverted due to the 0 amount. So, this protocol can't receive rewards.

```solidity
    receive() external payable nonReentrant {
        uint256 feeAmount = 0;
        // Take protocol cut of rewards if enabled
        if (feeAddress != address(0x0) && feeBasisPoints > 0) {
167         feeAmount = (msg.value * feeBasisPoints) / 10000;
            (bool success, ) = feeAddress.call{ value: feeAmount }("");
            if (!success) revert TransferFailed();

            emit ProtocolFeesPaid(IERC20(address(0x0)), feeAmount, feeAddress);
        }
        // update remaining rewards
174     uint256 remainingRewards = msg.value - feeAmount;
        // Check and fill ETH withdraw buffer if required
176     _checkAndFillETHWithdrawBuffer(remainingRewards);

        // Add to the total earned
        totalEarned[address(0x0)] = totalEarned[address(0x0)] + remainingRewards;

        // Emit the rewards event
        emit RewardsDeposited(IERC20(address(0x0)), remainingRewards);
    }
```

This problem also occurs at the function `sweepERC20()`, and makes frozen assets.

Manual review

## Recommended Mitigation Steps

There are 2 different ways to fix this issue.

1. Don't allow to set the `feeBasisPoints` to 100%.

