# Vulnerability details


## Impact

Dust ETH amount can be kept in `stakedButNotVerifierEth` which will overvalue the Operator's staked ETH balance.

## Proof of Concept

### Root cause

The staking in EigenLayer is done through two steps:
- `OperatorDelegator.stakeETH`: This will be called from `RestakeManager` to stake 32ETH
- `OperatorDelegator.verifyWithdrawalCredentials`: This will be called from the RestakeAdmin, and interact will EigenLayer to credit shares to the OperatorDelegator

`OperatorDelegator.stakeETH` will always be called with 32ETH and will track the [deposited value into `stakedButNotVerifiedEth`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L358):

```solidity
    /// @dev Stake ETH in the EigenLayer
    /// Only the Restake Manager should call this function
    function stakeEth(
        bytes calldata pubkey,
        bytes calldata signature,
        bytes32 depositDataRoot
    ) external payable onlyRestakeManager {
        // Call the stake function in the EigenPodManager
        eigenPodManager.stake{ value: msg.value }(pubkey, signature, depositDataRoot);

        // Increment the staked but not verified ETH
        stakedButNotVerifiedEth += msg.value;
    }
```


Then, when `verifyWithdrawalCredentials` is called, [the `stakedButNotVerifiedEth` variable is decreased by the effective balance of the validator](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L382-L385).

However, due to slashing, the effective balance of the validator could be lower than the deposited 32 ETH. This will let dust amount in `stakedButNotVerifiedEth` that will never be erasable as `EigenLayer.verifyWithdrawalCredentials` will not be reexecutable (status of validator must be inactive).

```solidity
    /// @dev Verifies the withdrawal credentials for a withdrawal
    /// This will allow the EigenPodManager to verify the withdrawal credentials and credit the OD with shares
    /// Only the native eth restake admin should call this function
    function verifyWithdrawalCredentials(
        uint64 oracleTimestamp,
        BeaconChainProofs.StateRootProof calldata stateRootProof,
        uint40[] calldata validatorIndices,
        bytes[] calldata withdrawalCredentialProofs,
        bytes32[][] calldata validatorFields
    ) external onlyNativeEthRestakeAdmin {
        uint256 gasBefore = gasleft();
        eigenPod.verifyWithdrawalCredentials(
            oracleTimestamp,
            stateRootProof,
            validatorIndices,
            withdrawalCredentialProofs,
            validatorFields
        );

        // Decrement the staked but not verified ETH
        for (uint256 i = 0; i < validatorFields.length; ) {
            uint64 validatorCurrentBalanceGwei = BeaconChainProofs.getEffectiveBalanceGwei(
                validatorFields[i]
            );
            stakedButNotVerifiedEth -= (validatorCurrentBalanceGwei * GWEI_TO_WEI);// @POC: The effective balance is used here, not the deposited amount
            unchecked {
                ++i;
            }
        }
        // update the gas spent for RestakeAdmin
        _recordGas(gasBefore);
    }
```

This dust amount in `stakedButNotVerifiedEth` is accounted in [`getStakedETHBalance`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L343-L344). So the returned staked ETH balance will be over estimated.

```solidity
    /// @dev Gets the amount of ETH staked in the EigenLayer
    function getStakedETHBalance() external view returns (uint256) {
        // accounts for current podOwner shares + stakedButNotVerified ETH + queued withdraw shares
        int256 podOwnerShares = eigenPodManager.podOwnerShares(address(this));
        return
            podOwnerShares < 0
                ? queuedShares[IS_NATIVE] + stakedButNotVerifiedEth - uint256(-podOwnerShares)
                : queuedShares[IS_NATIVE] + stakedButNotVerifiedEth + uint256(podOwnerShares);
    }
```

### Scenario

First, 32 ETH are staked into EigenLayer to a specific validator.

Then, the validator is slashed and its beacon chain balance goes below 31.75 ETH. Its effective balance is now 31 ETH.

Finally, `verifyWithdrawalCredentials` is called with this 31 ETH effective balance, letting 1 ETH dust amount in `stakedButNotVerifiedEth` that can never be erased.

## Tools Used
Manual review

## Recommended Mitigation Steps

Consider modifying the logic used for `stakedButNotVerifiedEth`.

The staked amount is 32 ETH, so it `stakedButNotVerifiedEth` should be increased and decreased by these 32 ETH and not the effective balance of the validator.
