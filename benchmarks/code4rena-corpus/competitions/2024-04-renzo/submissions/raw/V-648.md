# Vulnerability details

## Impact
Using directly the transfer function of token is not safe as token implementations can differ. This opens the possibility in the future Renzo to support new tokens with different implementations and lead to unexpected behaviours and even loss of funds.

## Proof of Concept
The only occurance of this is in [`WithdrawQueue.sol:claim()`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L305-L308)

```solidity
function claim(uint256 withdrawRequestIndex) external nonReentrant {
    ...
    // send selected redeem asset to user
    if (_withdrawRequest.collateralToken == IS_NATIVE) {
        ...
    } else {
        IERC20(_withdrawRequest.collateralToken).transfer(
            msg.sender,
            _withdrawRequest.amountToRedeem
        );
    }
    ...
}
```

In case the token implementation on error returns false instead of reverting then the WithdrawQueue contract can think that it sent the tokens to the user successfully when in reality this was not the case. In such situation the user loses his funds.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Always use the safe version of transfer/transferFrom -> safeTransfer() or safeTransferFrom()
