# Vulnerability details

## Impact
The OperatorDelegator contract relies on admins calling different protocol functions. The contract implements a mechanism to track gas spent by admins must be able to refund the amounts. However, it overrides the receive function in a way which forwards any ETH it receives to the depositQueue. Admins are intended to call the receive function to withdraw their ETH, however any calls to it will refund 0 because the contract cannot hold any ETH, at least not through a standard deposit.

This means that the protocol must use alternative ways to deposit ETH in the OperatorDelegators, for example through miner rewards, or other ways. This would be very impractical and inefficient, since there will be excess value left and seems to not be the intention in the first place.

## Proof of Concept
Let's first take a look at how gas spent by admins is accounted for. This is done in the _recordGas() function:

https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L481
```js
    function _recordGas(uint256 initialGas) internal {
        uint256 gasSpent = (initialGas - gasleft() + baseGasAmountSpent) * tx.gasprice;
        adminGasSpentInWei[msg.sender] += gasSpent;
        emit GasSpent(msg.sender, gasSpent);
    }
```
This accounting function is called in [queueWithdrawals()](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L253), [completeQueuedWithdrawal()](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L323), [verifyWithdrawalCredentials()](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L391) [and verifyAndProcessWithdrawals()](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L423). These are all admin managed functions. Admins spent gas on these functions and are expected to receive a refund for the gas spent. That refund can be requested by calling the receive function(sending native tokens via call()) on the OperatorDelegator contract.

Let's now look at how the receive function is implemeneted in the OperatorDelegator contract:

https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L501
```js
    /**
     * @notice Users should NOT send ETH directly to this contract unless they want to donate to existing ezETH holders.
     *        This is an internal protocol function.
     * @dev Handle ETH sent to this contract - will get forwarded to the deposit queue for restaking as a protocol reward
     * @dev If msg.sender is eigenPod then forward ETH to deposit queue without taking cut (i.e. full withdrawal from beacon chain)
     */
    receive() external payable nonReentrant {
        // check if sender contract is EigenPod. forward full withdrawal eth received
        if (msg.sender == address(eigenPod)) {
            restakeManager.depositQueue().forwardFullWithdrawalETH{ value: msg.value }();
        } else {
            // considered as protocol reward
            uint256 gasRefunded = 0;
            uint256 remainingAmount = msg.value;
            if (adminGasSpentInWei[tx.origin] > 0) {
                gasRefunded = _refundGas();
                // update the remaining amount
                remainingAmount -= gasRefunded;
                // If no funds left, return
                if (remainingAmount == 0) {
                    return;
                }
            }
            // Forward remaining balance to the deposit queue
            address destination = address(restakeManager.depositQueue());
            (bool success, ) = destination.call{ value: remainingAmount }("");
            if (!success) revert TransferFailed();

            emit RewardsForwarded(destination, remainingAmount);
        }
    }
```
As we can see, if the `adminGasSpentInWei[tx.origin] > 0` boolean evaluates to true, meaning the sender is an admin that needs a gas refund, the [_refundGas()](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L481) function is called. However, notice that any remaining amount sent as msg.value is forwarded to the depositQueue, regardless of who the caller is.

As a result, no one is able to actually deposit funds in the OperatorDelegator contract, at least not in a standard way. Thus, the _refundsGas() function will always send 0 tokens as a refund, due to it's implementation:

https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L48
```js
    function _refundGas() internal returns (uint256) {
        uint256 gasRefund = address(this).balance >= adminGasSpentInWei[tx.origin]
            ? adminGasSpentInWei[tx.origin]
            : address(this).balance;
        bool success = payable(tx.origin).send(gasRefund);
        if (!success) revert TransferFailed();

        // reset gas spent by admin
        adminGasSpentInWei[tx.origin] -= gasRefund;

        emit GasRefunded(tx.origin, gasRefund);
        return gasRefund;
    }
```

As we can see, since address(this).balance will be 0, the gas refund will be 0.
