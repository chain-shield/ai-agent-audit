# Vulnerability details

## Impact
Users may be unable to `deposit` funds if the TVL limit is reached, potentially leading to a loss of opportunity and trust in the protocol.

## Proof of Concept

Assume [maxDepositTVL](https://github.com/code-423n4/2024-04-renzo/blob/1c7cc4e632564349b204b4b5e5f494c9b0bc631d/contracts/RestakeManager.sol#L215) is currently set to `70,000 ETH`.

The current TVL is `69,990 ETH`.

A normal user attempts to deposit 10 ETH by calling `depositETH()`.

A malicious user observes the transaction in the mempool and decides to front-run.

The malicious user submits a transaction with a higher gas price to deposit 10 ETH, calling `depositETH()` as well.

The malicious user's transaction is mined first, increasing the TVL to 70,000 ETH.

The normal user's transaction is processed after but fails because `maxDepositTVL` has been reached.

```javascript
    function depositETH(uint256 _referralId) public payable nonReentrant notPaused {
        // Get the total TVL

        // Enforce TVL limit if set
        if (maxDepositTVL != 0 && totalTVL + msg.value > maxDepositTVL) {
            revert MaxTVLReached();
            //......
        }
    }
```

The normal user's deposit transaction is rejected, and they may lose the gas fee without their deposit being processed. Due to the `maxDepositTVL` check, the normal user is unable to deposit, resulting in the failure of the transaction

## Tools Used
Manual Review

## Recommended Mitigation Steps
Implement a fair ordering system like a first-come-first-serve queue to process deposits in the order they are received.

Dynamic Limits: Introduce dynamic maxDepositTVL limits that can adjust based on the number of pending transactions or a rolling time window.
