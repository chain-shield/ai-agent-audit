# Vulnerability details

## Impact
If EigenPod is in deficit due to slashing (or inactivity leak), repayments of native ETH will allow users that withdraw before a Renzo admin unstakes from EigenLayer to get a better exchange price for their ezETH at the expense of all other users in the system.

From [EigenLayer docs](https://github.com/Layr-Labs/eigenlayer-contracts/blob/dev/docs/core/EigenPodManager.md#depositing-into-eigenlayer) it can be seen that it's possible for an EigenPod to be in deficit (owe more to EigenLayer than it currently holds in a validator): 
>  Pod Owner's beacon chain ETH balance decreases (maybe due to slashing), and someone provides a proof of this to EigenPod.verifyBalanceUpdates. In this case, the Pod Owner will have negative shares in the EigenPodManager.

Which results in the negative shares being repaid out of the withdrawn assets. 

On the Renzo side this would imply that in the event of a slashing or [inactivity leak](https://docs.ethstaker.cc/ethstaker-knowledge-base/help/downtime-explained) (due to validator being offline) the `WithdrawQueue` would receive `32 ETH - deficit` after an admin unstakes from EigenLayer to fill the withdrawal buffer by executing the following call sequence (as mentioned by the sponsor in the competition chat): 

```
1. OperatorDelegator::queueWithdrawals
2. OperatorDelegator::verifyAndProcessWithdrawals
3. OperatorDelegator::completeWithdrawals
```

The greater effect of this is that it decreases the value of ezETH tokens in the following calculation used to determine how much a user should receive: 
```solidity
    function calculateRedeemAmount(
        uint256 _ezETHBeingBurned,
        uint256 _existingEzETHSupply,
        uint256 _currentValueInProtocol
    ) external pure returns (uint256) {
       // @audit _currentValueInProtocol decreases after unstaking is completed in EigenLayer
        uint256 redeemAmount = (_currentValueInProtocol * _ezETHBeingBurned) / _existingEzETHSupply;
       ...
}
```

This implies that users that submitted their withdrawal request before the withdrawal from EigenLayer will be unaffected by this price change whereas users that submit their request after will have their ezETH exchanged at a lower price. 

Given that the withdrawal from EigenLayer is an asynchronous process( requiring at least [`minWithdrawalDelayBlocks`](https://github.com/Layr-Labs/eigenlayer-contracts/blob/dev/docs/core/DelegationManager.md#completequeuedwithdrawal) to have passed) a user could frontrun the call by the admin to `completeWithdrawals` in order to get a better withdrawal price. If there is sufficient liquidity in the withdrawal buffer to execute this malicious user's withdrawal the subsequent loss to the protocol would be `amount * (originalPrice - priceAfterNativeETHUnstake)`. 

## Proof of Concept
1. Alice submits a withdrawal request but there is insufficient liquidity in the withdrawal buffer to complete her request so it reverts at [L236](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L236)
2. Seeing this the Renzo admin with the `NATIVE_ETH_RESTAKE_ADMIN` role calls `OperatorDelegator::queueWithdrawals` to fill the withdrawal buffer to allow Alice to withdraw her ETH. 
3. While the ETH was staked in EigenLayer, the Renzo validator experienced a period of downtime, resulting in a deficit due to inactivity leak that must be repaid as the ETH is withdrawn from EigenLayer, resulting in `32 ETH - deficit` ETH being sent to the withdrawal buffer.
4. Bob has a bot monitoring the mempool for any calls to `queueWithdrawals` that would return less than 32 ETH to Renzo and so frontruns the admin's call to `completeWithdrawals` to withdraw his stake before the decrease in price of ezETH. Note that he doesn't need to withdraw native staked ETH, he could withdraw an LST asset which has greater liquidity in the withdrawal buffer.  
5. Bob profits `amount * (originalPrice - priceAfterNativeETHUnstake)` more than he would have if he withdrew under normal conditions.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Introduce a mechanism into the `WithdrawQueue::withdraw` function which checks if there is a deficit in the EigenLayer stake and accounts for this deficit in the TVL calculation.
