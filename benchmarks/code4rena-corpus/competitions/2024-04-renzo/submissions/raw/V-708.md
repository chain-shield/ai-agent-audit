# Vulnerability details

## Summary
The `OperatorDelegator::getTokenBalanceFromStrategy` function is used to calculate the amount of tokens deposited by the OperatorDelegator in the Strategy. The calculation of the `OperatorDelegator::getTokenBalanceFromStrategy` function is wrong.


## Impact
The `OperatorDelegator::getTokenBalanceFromStrategy` function is used in the `RestakeManager::calculateTVL` function which in turn is used to the total value of assets in the protocol. This return values of calculateTVL is used to determine the [amount to mint](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L566) and [amount to redeem](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L223) ezETH tokens and depositing and withdrawing from Eigen Layer.

The wrong calculation of the token Balance in strategies will result in the TVL being less than the actual TVL. The effects of this are
- Minting will result in minting more ezETH than it should have.
- Redeeming will result in redeeming less amount of token than it should have
- More TVL in the protocol than the max TVL Limit.

## Proof of Concept

Once a withdrawal from the Strategy is initiated the shares of the amounts withdrawn is stored in the state variable `OperatorDelegator::queuedShares`. This keeps track of the total shares which are waiting to be withdrawn.

Hence while calculating the token balance deposited in a Strategy, we have to add the tokens values of the shares waiting to be withdrawn as well (i.e token amounts corresponding to `queuedShares`). But in [line 329](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol#L329C13-L329C25) a logic error has been made which results in the queuedShares of the token never being considered for the balance calculation.

```solidity
queuedShares[address(this)] == 0 // Here since address(this) is not a token, it will never have shares
                ? tokenStrategyMapping[token].userUnderlyingView(address(this))
                : tokenStrategyMapping[token].userUnderlyingView(address(this)) +
                    tokenStrategyMapping[token].sharesToUnderlyingView(
                        queuedShares[address(token)]
                    );
```
From the above code snippet we can see that since address(this) is not a token, it will never have any shares and the condition will always remain true. Which will only make it only take into account the `userUnderlyingView` of the address and the queuedShares is never taken into consideration.

## Recommended Mitigation Steps

```diff
- queuedShares[address(this)] == 0
+ queuedShares[address(token)] == 0
```
