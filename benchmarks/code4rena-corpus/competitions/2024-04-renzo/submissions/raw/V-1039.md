# Vulnerability details

## Impact

`chooseOperatorDelegatorForDeposit()` is called whenever a deposit is initiated to choose the operator based on percentage alllocatons allocated by admin for eacho operators.

There is a check that checks each operator delegator TVL against their allocation by admin, if it is still lower, deposits will go through into that operator delegator. 


[RestakeManager.sol#L378-L381](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L378-L381)

```solidity
function chooseOperatorDelegatorForDeposit(
    uint256[] memory tvls,
    uint256 totalTVL
) public view returns (IOperatorDelegator) {
    // Ensure OperatorDelegator list is not empty
    if (operatorDelegators.length == 0) revert NotFound();

    // If there is only one operator delegator, return it
    if (operatorDelegators.length == 1) {
        return operatorDelegators[0];
    }

    // Otherwise, find the operator delegator with TVL below the threshold
    // @audit wrong additional division of basis points, won't revert, can bypass TVL limits
    uint256 tvlLength = tvls.length;
    for (uint256 i = 0; i < tvlLength; ) {
        if (
@>           tvls[i] <
            (operatorDelegatorAllocations[operatorDelegators[i]] * totalTVL) /
                BASIS_POINTS /
                BASIS_POINTS
        ) {
            return operatorDelegators[i];
        }

        unchecked {
            ++i;
        }
    }

    // Default to the first operator delegator
    return operatorDelegators[0];
}
```

Notice the computation of `operatorDelegatorAllocations * totalTVL / BASIS_POINTS / BASIS_POINTS`. Since  `operatorDelegatorAllocations` is determined in 2 decimal precision, we shouldn't be dividing by `BASIS_POINTS` again, and as such this incorrect additional division will always overestimate the intended allocation allowed for each operator by 100x, causing the function to return early and deposit going through to the operator delegator even if tvl limit had been reached.
