# Vulnerability details


## Proof of Concept

First notice how the index is being attached to withdrawal requests https://github.com/code-423n4/2024-04-renzo/blob/1c7cc4e632564349b204b4b5e5f494c9b0bc631d/contracts/Withdraw/WithdrawQueue.sol#L242-L263

```solidity
    function withdraw(uint256 _amount, address _assetOut) external nonReentrant {
//(...snip)
        withdrawRequests[msg.sender].push(
            WithdrawRequest(
                _assetOut,
                withdrawRequestNonce,
                amountToRedeem,
                _amount,
                block.timestamp
            )
        );

        // add redeem amount to claimReserve of claim asset
        claimReserve[_assetOut] += amountToRedeem;

        emit WithdrawRequestCreated(/
            withdrawRequestNonce,
            msg.sender,
            _assetOut,
            amountToRedeem,
            _amount,
            withdrawRequests[msg.sender].length - 1
        );
    }
```

Having [this](https://github.com/code-423n4/2024-04-renzo/blob/1c7cc4e632564349b204b4b5e5f494c9b0bc631d/contracts/Withdraw/WithdrawQueue.sol#L33) in mind and applying common logic to the concept, the simple explanation of how the indexing works is that if a user creates 5 withdrawal requests within the cooldownPeriod _(which is highly possible, considering the cool down period is documented to be a week)_ the length of the array as at the time of creating the 5th index would be 4 then the above `withdrawRequests[msg.sender].push()` execution it makes the length 5 and then `withdrawRequests[msg.sender].length - 1` is chosen as the index so the user now have withdrawal requests with indexes from `0-4`, that's to say if there are 5 withdrawal requests, the least index is `0` for the first request and the highest index is `4` for the fifth request.

Now look at how the withdrawals are being claimed after the cooldown period https://github.com/code-423n4/2024-04-renzo/blob/1c7cc4e632564349b204b4b5e5f494c9b0bc631d/contracts/Withdraw/WithdrawQueue.sol#L279-L312

```solidity
    function claim(uint256 withdrawRequestIndex) external nonReentrant {
        // check if provided withdrawRequest Index is valid
        //@audit
        if (withdrawRequestIndex >= withdrawRequests[msg.sender].length)
            revert InvalidWithdrawIndex();

        WithdrawRequest memory _withdrawRequest = withdrawRequests[msg.sender][
            withdrawRequestIndex
        ];
        if (block.timestamp - _withdrawRequest.createdAt < coolDownPeriod) revert EarlyClaim();

        // subtract value from claim reserve for claim asset
        claimReserve[_withdrawRequest.collateralToken] -= _withdrawRequest.amountToRedeem;

        // delete the withdraw request
        withdrawRequests[msg.sender][withdrawRequestIndex] = withdrawRequests[msg.sender][
            withdrawRequests[msg.sender].length - 1
        ];//@audit
        withdrawRequests[msg.sender].pop();

        // burn ezETH locked for withdraw request
        ezETH.burn(address(this), _withdrawRequest.ezETHLocked);

        // send selected redeem asset to user
        if (_withdrawRequest.collateralToken == IS_NATIVE) {
            payable(msg.sender).transfer(_withdrawRequest.amountToRedeem);
        } else {
            IERC20(_withdrawRequest.collateralToken).transfer(
                msg.sender,
                _withdrawRequest.amountToRedeem
            );
        }
        // emit the event
        emit WithdrawRequestClaimed(_withdrawRequest);
    }
```

We can see that there is a check to ensure that the current index is not greater than the current length, this would lead to attempts queued withdrawals for users to fail if they use the data provided by the contracts when they queue the withdrawals ... using our already hinted example of 5 withdrawal requests look at these next scenarios,

- For POC sake we assume there is a day gap between all requests.
- Before claiming any request our indexes for all requests are [0, 1, 2, 3, 4].
- The 7th day passes, so the first request is ripe for claim and gets claimed, since while claiming the request [this](https://github.com/code-423n4/2024-04-renzo/blob/1c7cc4e632564349b204b4b5e5f494c9b0bc631d/contracts/Withdraw/WithdrawQueue.sol#L292-L297) method of removing the index is applied, i.e swapping the last with the current one to claimed, our indexes for all requests would now be [4, 1, 2, 3].
- The 8th day passes, so the second request is ripe for claim and gets claimed, since while claiming the request [this](https://github.com/code-423n4/2024-04-renzo/blob/1c7cc4e632564349b204b4b5e5f494c9b0bc631d/contracts/Withdraw/WithdrawQueue.sol#L292-L297) method of removing the index is applied, i.e swapping the last with the current one to claimed, our indexes for all requests would now be [4, 3, 2].
- The 9th day passes, so the third request is ripe for claim and gets claimed, since while claiming the request [this](https://github.com/code-423n4/2024-04-renzo/blob/1c7cc4e632564349b204b4b5e5f494c9b0bc631d/contracts/Withdraw/WithdrawQueue.sol#L292-L297) method of removing the index is applied, i.e in this case the last index is the one that's been claimed so it just gets popped our indexes for all requests would now be [4, 3].

- After the 10th/11th day if the user passes in the indexes of the unclaimed withdrawals [the `if (withdrawRequestIndex >= withdrawRequests[msg.sender].length)` check]() always reverts the call as either of 4 & 3 are greater than the current length which is `2`.

> Keep in mind that the current documentation provided for withdrawals clearly state that ._..the parameters for the withdrawals can be found in the event logs from the previous steps..._ see the last steps from the withdrawal flow documented here: https://github.com/code-423n4/2024-04-renzo?tab=readme-ov-file#withdraw-flow.

## Impact

Users who have multiple rewards queued would encounter reverts when trying to claim the later indexes of these withdrawals, albeit this would be more of an issue to non-tech savvy users who blindly trust the index announced by [this](https://github.com/code-423n4/2024-04-renzo/blob/1c7cc4e632564349b204b4b5e5f494c9b0bc631d/contracts/Withdraw/WithdrawQueue.sol#L261) to be unchangeable for a specific withdrawal requests.

## Recommended Mitigation Steps

Consider reimplementing the logic and instead have a map like check for the indexes announced by [this](https://github.com/code-423n4/2024-04-renzo/blob/1c7cc4e632564349b204b4b5e5f494c9b0bc631d/contracts/Withdraw/WithdrawQueue.sol#L261) instead of directly checking it against the length, this way we then set the mapping value of the claimed index whenever it gets claimed and the index can be an ever increasing value for a user, alternatively it could be clearly documented to users that `0` is the safe index and they can always use this index to get out their requests if the requested withdrawal has passed it's cooldown period.
