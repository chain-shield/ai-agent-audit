# Vulnerability details

## Impact
contract `XERC20` inherits from `Initializable`, `ERC20Upgradeable`, and other upgradeable contracts. Also, it is inherited by `OptimismMintableXERC20`. Failing to define the storage gap in `XERC20` may cause storage collision during the upgrade and cause subsequent critical errors.


## Proof of Concept
contract `XERC20` inherits from `Initializable`, `ERC20Upgradeable`, and other upgradeable contracts.

```solidity
contract XERC20 is
    Initializable,
    ERC20Upgradeable,
    OwnableUpgradeable,
    IXERC20,
    ERC20PermitUpgradeable
```

Also, `XERC20` is inherited by `OptimismMintableXERC20`.

```solidity
contract OptimismMintableXERC20 is ERC165Upgradeable, XERC20, IOptimismMintableERC20 {
```

The problem is that in `XERC20`, there is no storage gap defined. If in a later upgrade, some variables are added for `XERC20`, this will cause storage collision in `OptimismMintableXERC20` and cause severe consequences according to [OZ DOC](https://docs.openzeppelin.com/upgrades-plugins/1.x/writing-upgradeable#modifying-your-contracts).

Currently, the contract uses `@openzeppelin/contracts-upgradeable": "^4.9.3"`, so `_gap` is still required to be defined for `XERC20`.

## Tools Used
Manual

## Recommended Mitigation Steps
It is recommended to add `_gap` in `XERC20` contract.
