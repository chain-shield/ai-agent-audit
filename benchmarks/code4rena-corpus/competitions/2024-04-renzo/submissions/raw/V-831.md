# Vulnerability details

## Impact
Setting allowances with safeApprove to a non-zero value directly is dangerous. In case there is any allowance already present the safeApprove usage will revert if the new value is not 0 resulting in the possibility of reverts.

## Proof of Concept
SafeApprove is used in many places through out the protocol and it never sets the allowance to 0 before assigning the new one. 

In case a 3rd party contract or Renzo contract logic is changed that does not spent the whole allowance of a transfer call the second time such call is made to the same entity is going to revert due to this check:

```solidity
    function safeApprove(IERC20 token, address spender, uint256 value) internal {
        // safeApprove should only be called when setting an initial allowance,
        // or when resetting it to zero. To increase and decrease it, use
        // 'safeIncreaseAllowance' and 'safeDecreaseAllowance'
@>      require(
            (value == 0) || (token.allowance(address(this), spender) == 0),
            "SafeERC20: approve from non-zero to non-zero allowance"
        );
        _callOptionalReturn(token, abi.encodeWithSelector(token.approve.selector, spender, value));
    }
```

## Tools Used
Manual Review

## Recommended Mitigation Steps
Set allowance to 0 first or use safeIncreaseAllowance/safeDecreaseAllowance.
