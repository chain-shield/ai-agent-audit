# Vulnerability details

## Impact
In the withdrawalQueue.sol, the ``withdraw()`` is used to start the withdrawal process for a user, which is then finalized using ``claim()``. However, this is an issue for the protocol and users because:

- The protocol includes collateral funds already rrequested in the ``withdraw`` process in it's TVL when calculating
- The tokens to be burnt are not burnt in the initial ``withdraw`` function. 
- The amount to be sent to the sent to the user is set before the actual transfer is made.

Since the ``_withdrawRequest.amountToRedeem`` is set in the ``withdraw``, and there exists a time delay of ``coolDownPeriod`` before finalization, it is expected that price will flunctuate during the wait period. 
When the price flunctuation between that period is suffiently large, the protocol will over pay the user using the old amount that was previously set. This causes a deficit in the protocol since the caculated TVL used for other transactions included these tokens used as collateral
When the price drops sufficiently, the user looses a large part of their funds since the amount has been previously set.Considering that withdrawal requests cannot be reversed, the user has no choice but to complete the transaction. Meanwhile, the live prices are being used for deposits and TVL caculations.




Also by not finalizing withdrawals, a user can start multiple withdrawal process, all using the same TVL and therefore the ``calculateRedeemAmount`` rate, instead of a decreased rate after each withdrawal application.

## Recommended Mitigation Steps
Since this is an economic impact bug, I would like to suggest a few solutions.
- Don't add collateral tokens already requested for to the TVL. Since ezETH is already transferred from the user.
- Do the actual exchange rate calculation inside ``claim()``
- Implement a slippage parameter to determine a minimum amount expected, and reverse the transfer if the final amount is less than slippage
