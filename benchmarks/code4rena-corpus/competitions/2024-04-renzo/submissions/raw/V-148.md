# Vulnerability details

## Impact

`OperatorDelegator.getTokenBalanceFromStrategy` undervalues the token balance deposited into EigenLayer's StrategyManager, by not taking queued withdrawal shares into calculation.

This leads to:
- undervaluation of the total TVL in `RestakeManager.calculateTVLs`
- undervaluation of the operators' TVLs in `RestakeManager.calculateTVLs`
  
Undervaluation of the total TVL then leads to:
- bypass of the `maxDepositTVL` and `collateralTokenTvlLimits` during deposits: as queued withdrawal shares are not accounted, the maximum TVL can be exceeded
- overvaluation of the `ezETH` amount to mint to the user
- undervaluation of the value to withdraw to the user during withdrawals

Undervaluation of the operators' TVL then leads to:
- incorrect choosing of the operator delegator to which deposit is made

## Proof of Concept

### Incorrect calculation

During the token balance calculations in `OperatorDelegator.getTokenBalanceFromStrategy`, [the condition checks if there are shares queued for the address `this`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L329) instead of checking it for the current token.

*Note: the `@dev` comment indicates that accounting "queued withdrawal shares" is expected.*


```solidity
    /// @dev Gets the underlying token amount from the amount of shares + queued withdrawal shares
    function getTokenBalanceFromStrategy(IERC20 token) external view returns (uint256) {
        return
            queuedShares[address(this)] == 0// @POC: `queuedShares[address(this)]` is never written. It will always be zero, so `queuedShares[address(token)]` will never be used during this calculation
                ? tokenStrategyMapping[token].userUnderlyingView(address(this))
                : tokenStrategyMapping[token].userUnderlyingView(address(this)) +
                    tokenStrategyMapping[token].sharesToUnderlyingView(
                        queuedShares[address(token)]
                    );
    }
```

This mistake leads the `getTokenBalanceFromStrategy` function to never take the queued shares into calculation of the balance.

When there are queued shares, the returned token balance will be undervalued.

Indeed, [during withdrawal, data are written to `queuedShares[address(token)]`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L232) and not `queuedShares[address(this)]`.

```solidity
    function queueWithdrawals(
        IERC20[] calldata tokens,
        uint256[] calldata tokenAmounts
    ) external nonReentrant onlyNativeEthRestakeAdmin returns (bytes32) {
        // ...

        for (uint256 i; i < tokens.length; ) {
            // ...

            // track shares of tokens withdraw for TVL
            queuedShares[address(tokens[i])] += queuedWithdrawalParams[0].shares[i]; // @POC: see here, there is no `queuedShares[address(this)]`
            
            //...
        }
```

### Impacts of the incorrect calculation

As explained in the **Impact** section, there are multiple impacts. Here is shown the impact on the `ezETH` amount calculation.


[`RestakeManager.calculateTVLs` uses the operatorDelegator's token balance](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L302-L304) to [calculate the protocol's TVL](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L338).

```solidity
    function calculateTVLs() public view returns (uint256[][] memory, uint256[] memory, uint256) {
        uint256[][] memory operatorDelegatorTokenTVLs = new uint256[][](operatorDelegators.length);
        uint256[] memory operatorDelegatorTVLs = new uint256[](operatorDelegators.length);
        uint256 totalTVL = 0;

        // ...

        for (uint256 i = 0; i < odLength; ) {
            // Track the TVL for this OD
            uint256 operatorTVL = 0;

            // Track the individual token TVLs for this OD - native ETH will be last item in the array
            uint256[] memory operatorValues = new uint256[](collateralTokens.length + 1);
            operatorDelegatorTokenTVLs[i] = operatorValues;

            // Iterate through the tokens and get the value of each
            uint256 tokenLength = collateralTokens.length;
            for (uint256 j = 0; j < tokenLength; ) {
                // Get the value of this token

                uint256 operatorBalance = operatorDelegators[i].getTokenBalanceFromStrategy(// @POC: get incorrect token balance
                    collateralTokens[j]
                );

                // Set the value in the array for this OD
                operatorValues[j] = renzoOracle.lookupTokenValue(// @POC: calculate incorrect operator values
                    collateralTokens[j],
                    operatorBalance
                );

                // Add it to the total TVL for this OD
                operatorTVL += operatorValues[j];// @POC: calculate incorrect operator TVL

                // ...
            }

            // ...

            totalTVL += operatorTVL; // @POC: add the incorrect operator TVL to TVL

            // ...
        }

        // ...

        return (operatorDelegatorTokenTVLs, operatorDelegatorTVLs, totalTVL);// @POC: return incorrect TVL
    }
```

Finally, the TVL is used in `deposit` and `depositETH` to calculate the amount of `ezETH` minted to the user. Only the [`deposit` case is shown here](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L499-L504) with the corresponding [amount calculation](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L565-L569).

```solidity
    function deposit(
        IERC20 _collateralToken,
        uint256 _amount,
        uint256 _referralId
    ) public nonReentrant notPaused {
        // ...

        // Get the TVLs for each operator delegator and the total TVL
        (
            uint256[][] memory operatorDelegatorTokenTVLs,
            uint256[] memory operatorDelegatorTVLs,
            uint256 totalTVL
        ) = calculateTVLs(); // @POC: incorrect totalTVL

        // ...

        // Calculate how much ezETH to mint
        uint256 ezETHToMint = renzoOracle.calculateMintAmount(// @POC: incorrect `ezETHToMint`
            totalTVL,// @POC: incorrect totalTVL
            collateralTokenValue,
            ezETH.totalSupply()
        );

        // Mint the ezETH
        ezETH.mint(msg.sender, ezETHToMint);// @POC: Minting to user

        // Emit the deposit event
        emit Deposit(msg.sender, _collateralToken, _amount, ezETHToMint, _referralId);
    }
```

[The mint amount calculation is](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Oracle/RenzoOracle.sol#L134-L143): 
- `inflationPercentage = collateralTokenValue / (totalTVL + collateralTokenValue)`
- `newEzETHSupply = ezETHSupply / (1 - inflationPercentage)`
- `mintAmount = newEzETHSupply - ezETHSupply`

So, the lower is `totalTVL`, the bigger is `inflationPercentage`, the bigger is `newEzETHSupply` and the bigger is the amount minted to the user.

An attacker could exploit this to mint more ezETH when there are queued withdraw shares, letting him make a profit when selling them.

## Recommended Mitigation Steps

The condition should check `queuedShares[address(token)] == 0` instead of `queuedShares[address(this)] == 0`, to properly take the queued shares into calculations of the token balance.

The following snippet shows such a fix.

```solidity
    function getTokenBalanceFromStrategy(IERC20 token) external view returns (uint256) {
        return
            queuedShares[address(token)] == 0
                ? tokenStrategyMapping[token].userUnderlyingView(address(this))
                : tokenStrategyMapping[token].userUnderlyingView(address(this)) +
                    tokenStrategyMapping[token].sharesToUnderlyingView(
                        queuedShares[address(token)]
                    );
    }
```
