# Vulnerability details


## Impact
One of the the calculations inside `chooseOperatorDelegatorForDeposit` method is incorrect due to which the `operator delegator with TVL below the threshold` will not be returned rather incorrect operator delegators will be returned which will affect the deposit functionality because that funds will be approved to the wrong delegated operator addresses.

The problem is also present in `chooseOperatorDelegatorForWithdraw` but currently there is not function using it 
but it will affect the future withdrawal functionalities depending operator delegator selection by this method.

## Proof of Concept

One of the important variables is BASIS_POINTS
```solidity
    /// @dev Basis points used for percentages (100 basis points equals 1%)
    uint256 constant BASIS_POINTS = 100;

```
This variable is used in multiple places.
One such place is `chooseOperatorDelegatorForDeposit` which is used by deposit methods of restake manager 

```solidity
 function deposit(
        IERC20 _collateralToken,
        uint256 _amount,
        uint256 _referralId
    ) public nonReentrant notPaused {
//snip

 // Determine which operator delegator to use
        IOperatorDelegator operatorDelegator = chooseOperatorDelegatorForDeposit(
            operatorDelegatorTVLs,
            totalTVL
        );

        // Approve the tokens to the operator delegator
        _collateralToken.safeApprove(address(operatorDelegator), _amount);

        // Call deposit on the operator delegator
        operatorDelegator.deposit(_collateralToken, _amount);

//snip
}

```

we see that the returned operatorDelegator address needs to be correct otherwise the caller of deposit method

will lose their tokens.

however , a wrong address can be in-fact returned.

Let's take a look at this method 

```solidity

    function chooseOperatorDelegatorForDeposit(
        uint256[] memory tvls,
        uint256 totalTVL
    ) public view returns (IOperatorDelegator) {
        // Ensure OperatorDelegator list is not empty
        if (operatorDelegators.length == 0) revert NotFound();

        // If there is only one operator delegator, return it
        if (operatorDelegators.length == 1) {
            return operatorDelegators[0];
        }

        // Otherwise, find the operator delegator with TVL below the threshold
        uint256 tvlLength = tvls.length;
        for (uint256 i = 0; i < tvlLength; ) {
            if (
                tvls[i] <
                (operatorDelegatorAllocations[operatorDelegators[i]] * totalTVL) /BASIS_POINTS /BASIS_POINTS
            ) {
                return operatorDelegators[i];
            }

            unchecked {
                ++i;
            }
        }

        // Default to the first operator delegator
        return operatorDelegators[0];
    }
```

we see the right address will have this constraint 

`find the operator delegator with TVL below the threshold`

the core logic is this if condition 

```solidity
 if (
    tvls[i] < (operatorDelegatorAllocations[operatorDelegators[i]] * totalTVL) /BASIS_POINTS /BASIS_POINTS) {
                return operatorDelegators[i];
            }
```

if the iterated item's tvl is less than the right hand side calculation `(operatorDelegatorAllocations[operatorDelegators[i]] * totalTVL) /BASIS_POINTS /BASIS_POINTS)`

this method will return that address as the correct `operatorDelegator` for the current operation.

However this r.h.s calculation is incorrect .

Recall the value of BASIS_POINTS = 100 , 

and in this equation if we substitute the value , we get 

`(operatorDelegatorAllocations[operatorDelegators[i]] * totalTVL) / 100 / 100 )`


where if see that the self division of 100 `100 / 100` results in `1`

so the r.h.s calculation is infact reduces to this equation 

`(operatorDelegatorAllocations[operatorDelegators[i]])`

which is incorrect .

in fact the correct equation has to be something like 

`operatorDelegatorAllocations[operatorDelegators[i]]/10000` where 10000 are the total basis points to divide with 

to normalize the equation result.

Due to this mistake the result of `(operatorDelegatorAllocations[operatorDelegators[i]] * totalTVL) /BASIS_POINTS /BASIS_POINTS)`

will result in incorrect calculation of this expression 

```solidity
 if ( tvls[i] < (operatorDelegatorAllocations[operatorDelegators[i]] * totalTVL) /BASIS_POINTS /BASIS_POINTS)
     {
        return operatorDelegators[i];
    }
```
 and hence the result of this core expression will evaluates to true or false 

on wrong instances of operatorDelegators returning wrong operatorDelegator for deposit functionality 

which will result in depositing tokens in wrong operatorDelegator address and effectively losing deposited tokens amount.

This is also true for withdraw functionality `chooseOperatorDelegatorForWithdraw` having the same problem.

which will affect the 

```solidity
  if (
                operatorDelegatorTVLs[i] >
                (operatorDelegatorAllocations[operatorDelegators[i]] * totalTVL) /
                    BASIS_POINTS /
                    BASIS_POINTS &&
                operatorDelegatorTokenTVLs[i][tokenIndex] >= ezETHValue
            ) {
                return operatorDelegators[i];
            }
```

## Recommended Mitigation Steps

Modify the if condition in `chooseOperatorDelegatorForDeposit` & `chooseOperatorDelegatorForWithdraw` to following respectively 

```solidity
 if ( tvls[i] < (operatorDelegatorAllocations[operatorDelegators[i]] * totalTVL) /BASIS_POINTS * BASIS_POINTS)
     {
        return operatorDelegators[i];
    }
```

and

```solidity
 if (
                operatorDelegatorTVLs[i] >
                (operatorDelegatorAllocations[operatorDelegators[i]] * totalTVL) /
                    BASIS_POINTS *
                    BASIS_POINTS &&
                operatorDelegatorTokenTVLs[i][tokenIndex] >= ezETHValue
            ) {
                return operatorDelegators[i];
            }
```

However , if division by Total basis points i.e 10000 is not intended , summon an internal team meating to decide how the

operator delegator should be selected for both deposits and withdrawals.
