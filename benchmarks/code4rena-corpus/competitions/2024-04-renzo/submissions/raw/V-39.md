# Vulnerability details

## Description
The `WithdrawQueue.sol` contract is responsible for handling withdrawal requests which include burning the ezETH tokens. However, it is observed that the contract does not have the required `onlyMinterBurner` role to call the `burn` function on the `ezEthToken.sol` contract. This missing privilege will cause every call to the `claim` function, which attempts to burn ezETH, to fail, resulting in a critical functionality issue for the withdraw process.

## Impact
As a result of this oversight, users will be unable to successfully claim their withdrawal requests, effectively locking their funds in the `WithdrawQueue.sol` contract indefinitely. This not only disrupts the normal operation of the system but also severely affects trust in the platform and can lead to loss of reputation, user dissatisfaction, and potential financial loss for the users.

## Proof of Concept
- The `burn` function in `ezEthToken.sol` is restricted to `onlyMinterBurner`:
  ```solidity
  function burn(address from, uint256 amount) external onlyMinterBurner {
      _burn(from, amount);
  }
  ```
- The `claim` function in `WithdrawQueue.sol` attempts to burn ezETH without the necessary role:
  ```solidity
  ezETH.burn(address(this), _withdrawRequest.ezETHLocked);
  ```
- The setup script `setup.ts` grants the `RX_ETH_MINTER_BURNER` role only to the `RestakeManager` and not to the `WithdrawQueue`:
  ```typescript
  await roleManager.grantRole(
      await roleManager.RX_ETH_MINTER_BURNER(),
      await restakeManager.getAddress(),
  );
  ```

## Tools Used
Manual code review was performed to analyze the smart contract logic and the respective privileges each contract has related to ezETH token operations.

## Recommended Mitigation Steps
The burning logic should be adjusted to ensure the `WithdrawQueue` contract has permission to execute the `burn` function. There are two potential solutions:

1. Assign the MinterBurner role to the `WithdrawQueue` contract:
   Modify the setup configuration in `setup.ts` to grant the `RX_ETH_MINTER_BURNER` role to the `WithdrawQueue` contract, allowing it to call the `burn` function directly.
   
2. Move the burning logic to `RestakeManager`:
   Refactor the contracts so that the `claim` function in `WithdrawQueue.sol` calls a function in the `RestakeManager` contract, which would then handle the burning process. This ensures that all ezETH token burns are centralized through the `RestakeManager` that already has the necessary `onlyMinterBurner` privilege.

   The refactored process would involve the following steps:
   - Add a new function in `RestakeManager.sol` to handle the burning of ezETH.
   - Have `WithdrawQueue.sol` call this new function in `RestakeManager` when a user claims their withdrawal.
   - Ensure that the new burn function in `RestakeManager` can only be called by the `WithdrawQueue` contract to uphold security and prevent misuse of the burn functionality.
