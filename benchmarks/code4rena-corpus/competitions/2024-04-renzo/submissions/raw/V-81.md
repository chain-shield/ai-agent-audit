# Vulnerability details

## Impact
The `getMintRate()` returns the ezETH price which is used to calculate the xezETH amount to mint to the depositor. This function uses **CCIPReceiver** which get collateral price directly from L1 and also another oracle price feed(which is generally our **RenzoOracleL2** contract). 

Amoung the two price feed, the `getMintRate()` returns the most recently updated price of ezETH,

*File: xRenzoDeposit.sol*
```solidity
function getMintRate() public view returns (uint256, uint256) {
    ...snip...	
    if (address(oracle) != address(0)) {
        (uint256 oraclePrice, uint256 oracleTimestamp) = oracle.getMintRate();
        // @audit-info its using the most recently updated price below 
        return
            oracleTimestamp > lastPriceTimestamp
                ? (oraclePrice, oracleTimestamp)
                : (lastPrice, lastPriceTimestamp);
    } else {
        return (lastPrice, lastPriceTimestamp);
    }
}
```
However, the issue is if either of oracle hardcoded the lastTimestamp to current `block.timestamp`, the `getMintRate()` will always return the price corresponding to that price feed. Currently, the one of the affected token is `wBETH`. 

Here is the oracle contract for wBETH used by RenzoOracleL2(further used by `xRenzoDeposit` contract as second price feed). It can be seen here that the `latestRoundData()` internally call `_getWBETHData()` which harcoded the updatedAt to `block.timestamp`.
https://github.com/code-423n4/2024-04-renzo/blob/1c7cc4e632564349b204b4b5e5f494c9b0bc631d/contracts/Oracle/Binance/WBETHShim.sol#L12 


As an impact, if the price diverge by more than 10%, then `xRenzoDeposit` contract will reflect those price during minting of the xezETH token, which could possibly be avoided if the price from `CCIPReceiver` contract was used, as it has the in-built check for price divergence.
