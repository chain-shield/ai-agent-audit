# Vulnerability details

## Impact
In `DepositQueue.sol` `feeAmount` is calculated by multiplying the amount of tokens being processed by `feeBasisPoints` and then dividing by `10000`, however this is done utilising base solidity 

## Proof of Concept
```solidity
    receive() external payable nonReentrant {
        uint256 feeAmount = 0;
        // Take protocol cut of rewards if enabled
        if (feeAddress != address(0x0) && feeBasisPoints > 0) {
            feeAmount = (msg.value * feeBasisPoints) / 10000;
            (bool success, ) = feeAddress.call{ value: feeAmount }("");
            if (!success) revert TransferFailed();

            emit ProtocolFeesPaid(IERC20(address(0x0)), feeAmount, feeAddress);
        }
```
`feeAmount` can be rounded down to 0 if
`(msg.value * feeBasisPoints) < 10000` this will lead to precision loss of the fee, leading to protocol loss of fees.

## Tools Used

## Recommended Mitigation Steps

Use a math library that will round in favour of the protocol in calculations. In this instance round up, meaning that a small fee will always be paid, meaning users cannot bypass fees.
