# Vulnerability details

## Impact
```calculateTVLs()``` will return an incorrect value as the operatorTVL of the last erc20 token on the list for each delegator because it overrides the correct value with the operator ETH tvl later in the function.

The impact here is that there will be an incorrect enforcement of collateralTokenTVL limits
```solidity
  // Enforce TVL limit if set, 0 means the check is not enabled
        if (maxDepositTVL != 0 && totalTVL + collateralTokenValue > maxDepositTVL) {
            revert MaxTVLReached();
        }

        // Enforce individual token TVL limit if set, 0 means the check is not enabled
        if (collateralTokenTvlLimits[_collateralToken] != 0) {
            // Track the current token's TVL
            uint256 currentTokenTVL = 0;

            // For each OD, add up the token TVLs
            uint256 odLength = operatorDelegatorTokenTVLs.length;
            for (uint256 i = 0; i < odLength; ) {
         @>     currentTokenTVL += operatorDelegatorTokenTVLs[i][tokenIndex]; //@audit-issue note last erc20 token was replaced with ethTvl
                unchecked {
                    ++i;
                }
            }

            // Check if it is over the limit
            if (currentTokenTVL + collateralTokenValue > collateralTokenTvlLimits[_collateralToken])
                revert MaxTokenTVLReached(); //@audit-issue this could lead to incorrect outcome!
        }
```
Since the ```operatorDelegatorTokenTVLs``` last erc20 token was replaced with ethTvl, the check will be inaccurate.

So, in cases where the last erc20(being deposited by user) token already has it max tvl reached, since the value has been replaced for etc tvl which is lower, tvl limit of that token will not hold.

This could also lead to a DOS, if the ethTVL already exceeds the tvl of the last erc20 token(which is what the user is depositing), function will revert due to incorrect check.
