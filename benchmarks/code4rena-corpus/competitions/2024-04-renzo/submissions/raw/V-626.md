# Vulnerability details

## Impact
The issue in the `setFeeConfig` function lies in the lack of validation for the fee basis points (`_feeBasisPoints`). If _feeBasisPoints is set to zero, there is no specific handling for this scenario. This oversight can lead to potential issues and unintended consequences.

There exists also a type of case where `_feeBasisPoints` and `_feeAddress` both are zero and they are assigned wihtout further checks. If `_feeAddress` is valid then there will be zero fee basis points set that also creates issues for the protocol.

If `_feeBasisPoints` is unintentionally set to zero and `_feeAddress` is left unchanged or set to a non-zero address, users might expect fees to be disabled. However, fees could still be deducted due to the presence of a non-zero _feeAddress.

Failing to handle the scenario where _feeBasisPoints is zero compromises the contract's integrity and transparency. It introduces ambiguity into the fee configuration process, raising concerns about the contract's reliability and trustworthiness.

## Proof of Concept
See the following code:

```
 function setFeeConfig(
        address _feeAddress,
        uint256 _feeBasisPoints
    ) external onlyRestakeManagerAdmin {
        // Verify address is set if basis points are non-zero
        if (_feeBasisPoints > 0) {
            if (_feeAddress == address(0x0)) revert InvalidZeroInput();
        }

        // Verify basis points are not over 100%
        if (_feeBasisPoints > 10000) revert OverMaxBasisPoints();

        feeAddress = _feeAddress;
        feeBasisPoints = _feeBasisPoints;

        emit FeeConfigUpdated(_feeAddress, _feeBasisPoints);
    }
```
