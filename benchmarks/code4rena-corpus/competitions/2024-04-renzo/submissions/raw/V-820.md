# Vulnerability details

## Impact
Due to wrong check the `getTokenBalanceFromStrategy` will only return value of share not the queued withdrawal shares.
## Proof of Concept
The Protocol implement a algorithm which allows it to deposit the new assets in OperatorDelegator which does not have below the threshold allowed if there is no such a OperatorDelegator then it allows the deposit into first OperatorDelegator.
to do so it fetch the `operatorDelegatorTVLs` calculated in `calculateTVLs` function. lets have a look at the code.
1. The `calculateTVLs` get the amount of share for OperatorDelegator using `getTokenBalanceFromStrategy`

`301` return the balance of `OperatorDelegator`, `306` calculate its value,  `312` add this value to `operatorTVL`, and `340` add the final value to `operatorDelegatorTVLs`. after loop got executed it returns `operatorDelegatorTVLs` which is then used to identify the right `OperatorDelegator` for deposit.
This is the purpose of `operatorDelegatorTVLs` value , let now have a look at `getTokenBalanceFromStrategy`.

So now lets check where this `queuedShares` got updated.
3. When new withdrawal is queued the amount of withdrawal is added to `queuedShares` and maps to its token address.
```solidity
/2024-04-renzo/contracts/Delegation/OperatorDelegator.sol:232
```

have a look at `@1>` and `@2>` it can be observed that the `@1>` check the `queuedShares` amount using `address(this)` which will always have `0` balance becuase `@2>` the values saved in `queuedShares` map to `token address`.

So the impact is that it will not added the values which is in `queuedShares` due to wrong map key.
