# Vulnerability details

## Summary
`Fee-loss` arises from the incorrect handling of the `bridgeFee` deduction in the `_deposit()` function. 

## Proof of Concept
Both `depositETH()` and `deposit()` functions are entry points for users to deposit funds and mint `xezETH`. Here's a brief explanation:

1. [depositETH()](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Bridge/L2/xRenzoDeposit.sol#L168-L191):
- Users send `ETH` to the contract.
- `ETH` is wrapped into `WETH`.
- Calls `_deposit()` with the wrapped amount.
```solidity
//...
// Wrap the deposit ETH to WETH
IWeth(address(depositToken)).deposit{ value: msg.value }();
//...
return _deposit(wrappedAmount, _minOut, _deadline);
```

2. [deposit()](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Bridge/L2/xRenzoDeposit.sol#L204-L217):
- Users deposit `depositToken`.
- Calls `_deposit()` with the amount specified.
```solidity
//...
// Transfer deposit tokens from user to this contract
depositToken.safeTransferFrom(msg.sender, address(this), _amountIn);
//...
return _deposit(_amountIn, _minOut, _deadline);
```
3. [_deposit()](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Bridge/L2/xRenzoDeposit.sol#L227-L271):
- This is the internal function that trade deposit tokens for `nextWETH` and mint `xezETH`
```solidity
//...

/ calculate bridgeFee for deposit amount
uint256 bridgeFee = getBridgeFeeShare(_amountIn);
// subtract from _amountIn and add to bridgeFeeCollected
_amountIn -= bridgeFee;
bridgeFeeCollected += bridgeFee;

// Trade deposit tokens for nextWETH
uint256 amountOut = _trade(_amountIn, _deadline); // @audit Incorrect amount used

//...
```
As it can be seen from above, `4 steps` are involved upto this point:
1. `bridgeFee` is calculated from `getBridgeFeeShare()`. 
2. `bridgeFee` is subtracted from `_amountIn`.
3. `bridgeFeeCollected` is incremented by this value
4. Deposit tokens are traded for `nextWETH`.

The [_trade()](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Bridge/L2/xRenzoDeposit.sol#L367-L391) function is responsible for swapping the deposited tokens (`depositToken`) for `nextWETH` using the `connext` contract. It approves the `connext` contract to spend the tokens and then calls its `swapExact()` function to perform the `swap`.

```solidity
// Approve the deposit asset to the connext contract
depositToken.safeApprove(address(connext), _amountIn);

// Swap the tokens
uint256 amountNextWETH = connext.swapExact(
    swapKey,
    _amountIn,
    address(depositToken),
    address(collateralToken),
    minOut,
    _deadline
);
```
After the `swap`, it deducts the bridge router fee (if any) from the `amountNextWETH` received, which is then returned by the function and used to mint `xezETH`.

##### Fee-loss
The problem is that `_amountIn` should be reduced by `bridgeFee` before calling `_trade()`, but the code uses the original `_amountIn` value, not accounting for the deducted `bridgeFee`.

```solidity
// Trade deposit tokens for nextWETH
uint256 amountOut = _trade(_amountIn, _deadline);
``` 
When `_trade()` is invoked, the whole amount of tokens deposited by the user (`_amountIn`) is traded for `nextWETH`. This means that whatever `bridgeFee` that was calculated is not taken into account as the user gets `amountOut` in form of `nextWETH` equivalent to the traded total deposited tokens.

Now there are `two types of fees` here:
1. `bridgeFee` --->. This is deducted from the `_amountIn` before any swap or minting is done. 
2. `bridge router fee` ---> It only comes in play during trading and will only be deducted if `bridgeRouterFeeBps > 0`.

So whether `bridge router fee` is deductable or not, `bridgeFee` must always be deducted from `_amountIn` and therefore invoking `_trade()` with the whole `_amountIn` cancels out the previous `bridgeFee` deducted. 

## Impact
The protocol gets no `bridgeFee` at all as the whole `_amountIn` is traded for `nextWETH` for the user. In other words, the user doesn't pay any `bridgeFee` for their deposited tokens. 

## Tools Used
Manual Review

## Recommended Mitigation Steps
The correct approach would be to adjust the `_amountIn` before trading:

```solidity
// Adjusted amount after bridge fee deduction
uint256 adjustedAmountIn = _amountIn - bridgeFee;

// Trade adjusted deposit tokens for nextWETH
uint256 amountOut = _trade(adjustedAmountIn, _deadline);
```
By using `adjustedAmountIn` for the trade, the contract ensures that only the correct amount of tokens, net of the `bridgeFee`, is used, preventing the `fee-loss` issue.
