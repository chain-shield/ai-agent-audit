# Vulnerability details

## Impact
The impact of this issue is that the deposit function cannot directly support native tokens. Users attempting to deposit native tokens will encounter errors or unintended behavior due to the lack of handling for such tokens. This limitation reduces the usability and flexibility of the contract, potentially leading to user frustration and decreased adoption.


## Proof of Concept
The issue stems from the `_deposit` function's lack of support for native tokens. Currently, the function is designed to handle the deposit of ERC20 tokens using the `safeTransferFrom` function, but it lacks explicit handling for native tokens. Below is the relevant excerpt from the `_deposit` function:
```solidity
function _deposit(address _to, uint256 _amount) internal {
    if (!IS_NATIVE) {
        ERC20.safeTransferFrom(msg.sender, address(this), _amount);
    }

    XERC20.mint(_to, _amount);
    emit Deposit(_to, _amount);
}

```
As evident, the function checks whether the deposited token is native (`IS_NATIVE`), and if not, it transfers ERC20 tokens using `safeTransferFrom` and then mints `XERC20` tokens for the recipient. However, there is no explicit handling provided for native tokens, thus rendering the deposit function incompatible with them.

Manual
## Recommended Mitigation Steps
Enable support for native tokens, the `_deposit` function must be updated to include explicit handling for native token deposits. This can be achieved by implementing logic to directly receive and process native token transfers within the function.
