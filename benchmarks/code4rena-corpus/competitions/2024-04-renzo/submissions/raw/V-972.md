# Vulnerability details

## Impact
By incorrectly interpreting the percentage breakdown, the first operator on the list is always favored and the deposit will be sent to him even if the allocation is set to 0% and another operator to 100%.

## Proof of Concept
Each operatorDelegator has configured what percentage of deposits it should receive.
```solidity
//RestakeManagerStorage.sol

     /// @dev Mapping to store the allocations to each operatorDelegator
     /// Stored in basis points (e.g. 1% = 100)
     mapping(IOperatorDelegator => uint256) public operatorDelegatorAllocations;
```

The percentage value for each operator can be set in the full range 0-100%, regardless of the value set in other operators.
You can define the allocation while adding the operator `function addOperatorDelegator(IOperatorDelegator _newOperatorDelegator, uint256 _allocationBasisPoints)` or change it after adding `function setOperatorDelegatorAllocation(IOperatorDelegator _operatorDelegator,uint256 _allocationBasisPoints)`.

None of the above-mentioned functions checks and changes the value of other operators, which is why the overall value may exceed 100%.


A problem may arise if we have several operators, we set 0% for the first operator, 100% for the second, and 0% for the subsequent ones.

The operator to which the deposit will be sent is checked using the condition marked below in the `RestakeManager:chooseOperatorDelegatorForDeposit` function.
```solidity
//RestakeManager.sol

     function chooseOperatorDelegatorForDeposit(
         uint256[] memory tvls,
         uint256 totalTVL
     ) public view returns (IOperatorDelegator) {
         // Ensure OperatorDelegator list is not empty
         if (operatorDelegators.length == 0) revert NotFound();

         // If there is only one operator delegate, return it
         if (operatorDelegators.length == 1) {
             return operatorDelegators[0];
         }

         // Otherwise, find the operator delegator with TVL below the threshold
         uint256 tvlLength = tvls.length;
         for (uint256 i = 0; i < tvlLength; ) {
             if (                                  <@AUDIT
                 tvls[i] <
                 (operatorDelegatorAllocations[operatorDelegators[i]] * totalTVL) /
                     BASIS_POINTS /
                     BASIS_POINTS
             ) {
                 return operatorDelegators[i];
             }

             unchecked {
                 ++i;
             }
         }

         // Default to the first operator delegator
         return operatorDelegators[0];
     }

```

The above condition does not allow for an exact <= comparison, so it will not pass the value of 100%, but will redirect the deposit to the first operator that has the value set to 0%.

Even if the first operator is set as default, it should not receive the deposit if another operator has the allocation set to 100%. The default first operator should only be used when the sum of the percentages of settings per operator is less than 100%, then everything beyond what is set should go to the default.

## Tools Used
Manual review & excel sheet

## Recommended Mitigation Steps

If the system is to allocate deposits randomly, a solution may be to add another deposit to the least loaded operator.

If the system is to respect the percentage division correctly, then each update or addition/removal of an operator should result in the appropriate setting of the percentage division. 
Setting the ranges can be done by sending an array with the full percentage breakdown with each update, which will simplify validation (sum == 100%). Additionally, a special condition should be added to support the 100% setting for a single operator.
