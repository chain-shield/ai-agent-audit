# Vulnerability details

## Impact
The `calculateMintAmount` function within the `RenzoOracle` contract lacks a division by zero and underflow checks, resulting in the contract reverting unexpectedly and disrupting normal operations.

If the `inflationPercentaage` equals the `SCALE_FACTOR`, a divide by zero error could occur when attempting to calculate the `newEzETHSupply`. If the division by zero error occurs, the contract would revert abruptly, halting any ongoing transactions and potentially leaving the contract in an inconsistent or unrecoverable state.

The line `uint256 mintAmount = newEzETHSupply - _existingEzETHSupply;` within the `calculateMintAmount` function lacks underflow protection. This absence of a safeguard could potentially result in an underflow error if the `_existingEzETHSupply` exceeds the `newEzETHSupply`. An underflow error in the minting calculation could lead to a negative mint amount, disrupting the integrity of the token supply and potentially causing inconsistencies in the system.

## Proof of Concept
See the following code:

```
function calculateMintAmount(
        uint256 _currentValueInProtocol,
        uint256 _newValueAdded,
        uint256 _existingEzETHSupply
    ) external pure returns (uint256) {
        // For first mint, just return the new value added.
        // Checking both current value and existing supply to guard against gaming the initial mint
        if (_currentValueInProtocol == 0 || _existingEzETHSupply == 0) {
            return _newValueAdded; // value is priced in base units, so divide by scale factor
        }

        // Calculate the percentage of value after the deposit
        uint256 inflationPercentaage = (SCALE_FACTOR * _newValueAdded) /
            (_currentValueInProtocol + _newValueAdded);

        // Calculate the new supply
        uint256 newEzETHSupply = (_existingEzETHSupply * SCALE_FACTOR) /
            (SCALE_FACTOR - inflationPercentaage);

        // Subtract the old supply from the new supply to get the amount to mint
        uint256 mintAmount = newEzETHSupply - _existingEzETHSupply;

        // Sanity check
        if (mintAmount == 0) revert InvalidTokenAmount();

        return mintAmount;
    }
```

## Recommended Mitigation Steps
First of all use SafeMath library for these type of issues. And Also ensure that `inflationPercentaage` is always less than `SCALE_FACTOR`. 

Also add a conditional check before subtracting _`existingEzETHSupply` from `newEzETHSupply` to ensure that the mint amount does not result in an underflow condition.
