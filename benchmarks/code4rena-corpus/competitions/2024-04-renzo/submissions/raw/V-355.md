# Vulnerability details

## Impact

Changes to the actual balance of validators are updated when an [EigenPod::verifyBalanceUpdates()](https://github.com/Layr-Labs/eigenlayer-contracts/blob/90a0f6aee79b4a38e1b63b32f9627f21b1162fbb/src/contracts/pods/EigenPod.sol#L188-L224) is called on an EigenPod. The slashing of an EigenPod is therefore known before it is updated in the EigenLayer system.

A malicious user can abuse this by front-running the [verifyBalanceUpdates()](https://github.com/Layr-Labs/eigenlayer-contracts/blob/90a0f6aee79b4a38e1b63b32f9627f21b1162fbb/src/contracts/pods/EigenPod.sol#L188-L224) call to circumvent the slashing penalty.

+ To Illustrate:

A user can monitor the validators and request a withdrawal via [WithdrawQueue::withdraw](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L206-L263) function when a validator is slashed to front-run calls to [verifyBalanceUpdates()](https://github.com/Layr-Labs/eigenlayer-contracts/blob/90a0f6aee79b4a38e1b63b32f9627f21b1162fbb/src/contracts/pods/EigenPod.sol#L188-L224), hence claiming more ether than they are entitled to.
This is because the total value locked for the system has still not accounted for the slashing that happened.

For example:
Let's analyze this issue by observing two users in the system, Bob and Alice who own 5 ezETH each.
Assuming the following simplified state, with just one validator:
current ezETH supply = 32e18
current protocol TVL = 32 ether

If the validator is slashed for 16 eth, and Bob front runs the call to the [EigenPod::verifyBalanceUpdates()](https://github.com/Layr-Labs/eigenlayer-contracts/blob/90a0f6aee79b4a38e1b63b32f9627f21b1162fbb/src/contracts/pods/EigenPod.sol#L188-L224) function to request a withdrawal via [WithdrawQueue::withdraw](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L206-L263) function, to burn all of his ezETH for ether, the amount of ether Bob receives is calculated [here](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Oracle/RenzoOracle.sol#L152-L164), as:
redeem amount = current TVL * ezTH to burn / ezETH supply 
= 32e18 * 5e18 / 32e18 ==> 5e18

Bob will now be eligible to claim 5 ether for his 5 ezETH after the cool-down period, via a call to [WithdrawQueue::claim](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L206-L263) function.

Current State after Bob's withdrawal:
ezETH Supply = 32e18 - 5e18 ==> 27e18
TVL = 32 ether - 5 ether = 27 ether ==> 27 ether


After [verifyBalanceUpdates](https://github.com/Layr-Labs/eigenlayer-contracts/blob/90a0f6aee79b4a38e1b63b32f9627f21b1162fbb/src/contracts/pods/EigenPod.sol#L188-L224) is called on the EigenPod, the current state will now be:
ezETH Supply = 27e18 
TVL = 27 ether - 16 ether ==> 11 ether

If Alice tries to withdraw after this update:
redeem amount = current TVL * ezTH to burn / ezETH supply 
= 11e18 * 5e18 / 27e18 ==> 5e18

Alice will be eligible to ~2 ether for her 5 ezETH.

Without any interference, Bob would have received:
redeem amount = TVL * ezTH to burn / ezETH supply 
= 16e18 * 5e18 / 32e18 ==> 2.5e18

Bob has thus stolen 2.5 ether from other users while avoiding any losses.

## Recommended Mitigation Steps
