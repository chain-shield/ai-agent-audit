# Vulnerability details

The [`OperatorDelegator`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol) contract allows an admin to queue withdrawals of tokens from EigenLayer strategies via the [`queueWithdrawals()`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol#L193) function. These queued withdrawals are later completed via the [`completeQueuedWithdrawal()`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol#L265) function. 

When completing a queued withdrawal, any tokens withdrawn over the `WithdrawQueue`'s buffer amount for that token are deposited back into the corresponding EigenLayer strategy via [`OperatorDelegator._deposit()`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol#L162). However, before depositing back into the strategy, `completeQueuedWithdrawal()` tops up the `WithdrawQueue`'s buffer for the token if it is below the target amount.

This is done by approving the `DepositQueue` to spend the tokens and then calling [`DepositQueue.fillERC20withdrawBuffer()`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Deposits/DepositQueue.sol#L134). However, `fillERC20withdrawBuffer()` has the [`onlyRestakeManager`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Deposits/DepositQueue.sol#L50-L53) modifier which only allows the `RestakeManager` contract to call it. 

Therefore, any queued withdrawal that contains a token with a buffer deficit in the `WithdrawQueue` will fail when the admin tries to complete it, unless the `withdrawQueueAdmin` first nullifies the deficit by adjusting the buffer target.

## Impact
Queued withdrawals containing tokens with a `WithdrawQueue` buffer deficit will fail when the admin attempts to complete them via `completeQueuedWithdrawal()`. 

More severely, this prevents collateral tokens from being withdrawn out of EigenLayer strategies into the `WithdrawQueue`. As a result, once collateral tokens are deposited into EigenLayer via an `OperatorDelegator`, they can never be removed. This is because any attempt to withdraw them will fail on trying to top up the `WithdrawQueue` buffer.

## Proof of Concept
1. Admin queues a withdrawal of token X via `OperatorDelegator.queueWithdrawals()`
2. Token X's balance in the `WithdrawQueue` falls below the buffer target amount
3. Admin calls `completeQueuedWithdrawal()` to complete the queued withdrawal of token X
4. `completeQueuedWithdrawal()` calculates an amount of token X to top up the `WithdrawQueue` buffer with
5. It approves the `DepositQueue` to spend token X and calls `fillERC20withdrawBuffer()`
6. `fillERC20withdrawBuffer()` reverts because it can only be called by the `RestakeManager`
7. The queued withdrawal fails and token X remains stuck in EigenLayer

## Recommended Mitigation Steps
Remove the `onlyRestakeManager` modifier from `DepositQueue.fillERC20withdrawBuffer()`:

```diff
- function fillERC20withdrawBuffer(address token, uint256 amount) external onlyRestakeManager {  
+ function fillERC20withdrawBuffer(address token, uint256 amount) external {
```

This would allow both the `RestakeManager` and the different `OperatorDelegator` contracts to top up the `WithdrawQueue` buffer when needed. 

Any calls to `fillERC20withdrawBuffer()` can only add tokens to the `WithdrawQueue`, which benefits the protocol. There is no risk of funds being stolen or drained by allowing this function to be called by any address. Therefore, having no access control modifier on `fillERC20withdrawBuffer()` is safe and solves the issue.
