# Vulnerability details

## Impact
According to the `withdraw` token having enough `ezETH` can allow a user to choose the output token to receive his equivalent value. This brings up an issue

A case of some tokens like native ETH having more withdrawal pressure than say stETH withdrawals. This could lead to serious DOS on withdrawals once availableToWithdraw for ETH gets lower than the withdrawal amount or is zero while a lot of value is stuck in other tokens like stETH.

A large base of users could decide to only withdraw in ETH for example which could be due to preference, issue on pegged token like depegging issues, and others.

## Proof of Concept
Any approved token is accepted for withdrawal as seen in

```solidity
function withdraw(uint256 _amount, address _assetOut) external nonReentrant {
...
// check if provided assetOut is supported
        if (withdrawalBufferTarget[_assetOut] == 0) revert UnsupportedWithdrawAsset();
```

and we see a check for withdrawal redeemable at
```solidity
// revert if amount to redeem is greater than withdrawBufferTarget
        if (amountToRedeem > getAvailableToWithdraw(_assetOut)) revert NotEnoughWithdrawBuffer();
```

## Tools Used
Manual Review

## Recommended Mitigation Steps
- Track tokens deposited by users and use that determine the token withdrawable by a user.
- Implement swaps between approved tokens based on the tokens with more availableToWithdraw value to reduce withdrawal pressure on tokens across boards
