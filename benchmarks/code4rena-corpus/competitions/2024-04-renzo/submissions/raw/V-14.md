# Vulnerability details

## Impact
The use of `.transfer()` in the `recoverNative` function could lead to unexpected transfer failures if the recipient contract has a fallback function that requires more than 2300 gas. This limitation could result in funds being stuck in the contract or unintended behavior in the recipient contract.


## Proof of Concept
```solidity
payable(_to).transfer(_amount);
```
To illustrate the potential impact of this vulnerability, consider a scenario where the `_to` address is a contract with a fallback function that requires more than 2300 gas. In such a case, the `transfer` function will revert, and the Ether will remain stuck in the `xRenzoBridge` contract. Here's an example of such a contract:
```solidity
contract GasGuzzler {
    receive() external payable {
        // Consume more than 2300 gas
        uint256 i;
        for (i = 0; i < 1000; i++) {
            // Some computation
        }
    }
}
```
If the `recoverNative` function is called with `_to` set to the address of the `GasGuzzler` contract, the transfer will fail, and the Ether will remain in the `xRenzoBridge` contract.

## Tools Used

* Solidity documentation
* OpenZeppelin's Solidity security recommendations

## Recommended Mitigation Steps
To mitigate this vulnerability, it is recommended to replace the `.transfer()` method with the `.call{value: _amount}("")` method in the `recoverNative` function. This will forward all available gas and allow for more complex functionality in the recipient contract. Additionally, it is recommended to implement necessary checks to handle potential errors and ensure that the function returns a boolean indicating success or failure. The updated code should look like this:
```solidity
(bool success, ) = payable(_to).call{value: _amount}("");
require(success, "Transfer failed");
```
This change will ensure that the transfer function has enough gas to execute any code in the recipient contract and provide better error handling.
