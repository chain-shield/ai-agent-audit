# Vulnerability details

## Impact
The minDelay() passed into the constructor is not validated and hence can be zero.
As it is initialized as zero, any change scheduled by the proposer can also pass the delay as zero for that execution.

This leaves a vulnerability for scheduling proposal with immediate execution. This defeats the purpose of timelock. Also, as timelock is a provision for parties to quit incase they are not comfortable with the coming changes, then the most underlying element is the minimum time available for someone to exit.

Since there is no minimum time for the delay and totally managed by the admin roles, there is nothing enforcing that parties will have the time window to exit.

The timestamps mapping to id remembers the effective time when scheduled and hence even if the minDelay() is reconfigured to a different value, it does not effect the already queues schedules.

The only option would be for the canceller to cancel all such schedules, if not already executed.


## Proof of Concept

minDelay can be 0 or any number, which can be updated to a new number by calling updateDelay through the schedule process. So, the window of time available to parties is not defined.

```
  function updateDelay(uint256 newDelay) external virtual {
        require(msg.sender == address(this), "TimelockController: caller must be timelock");
        emit MinDelayChange(_minDelay, newDelay);
        _minDelay = newDelay;
    }
```

## Recommended Mitigation Steps
a) Declare a constant as BASE_MIN_DELAY
b) The base min delay should be sufficient for parties to exit incase they are not comfortable with the upcoming change. 
c) The minDelay Variable can hold value greater than or equal to BASE_MIN_DELAY, there by assuring that parties will get atleast BASE_MIN_DELAY of time window before the proposal is execute.
