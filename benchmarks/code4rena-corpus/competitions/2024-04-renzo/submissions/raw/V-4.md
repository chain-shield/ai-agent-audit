# Vulnerability details

## Impact
The excessive token approval vulnerability in the xReceive function poses a medium risk by potentially allowing the xezETHLockbox contract broader access to ezETH tokens than necessary. This could lead to unauthorized token usage if the xezETHLockbox is compromised or contains a bug. Since ERC-20 token approvals are a common attack vector, improperly managed approvals can lead to financial losses by enabling unauthorized transfers of valuable tokens. The impact is particularly significant given the financial nature of the transactions involved, potentially affecting user trust and the platform’s liquidity.

## Proof of Concept
The issue stems from the practice of approving a potentially large amount of ezETH for transfer by the xezETHLockbox before the actual need is confirmed. This approval is not immediately revoked or adjusted after the specific transaction, leaving an open window where excess tokens might be accessible:

```
xRenzoBridge.sol

function xReceive(bytes32 _transferId, uint256 _amount, address _asset, address _originSender, uint32 _origin, bytes memory) external nonReentrant returns (bytes memory) {
...
    // Approve the lockbox to spend the ezETH
    ezETH.safeApprove(address(xezETHLockbox), ezETHAmount);

    // Send to the lockbox to be wrapped into xezETH
    xezETHLockbox.deposit(ezETHAmount);
...
}
```

## Recommended Mitigation Steps
To effectively mitigate the excessive token approval vulnerability in the xReceive function of the xRenzoBridge.sol contract, it is crucial to adjust the token approval and handling procedures to be more restrictive. The recommended approach is to approve only the exact amount of ezETH needed just before it's used by the xezETHLockbox and then immediately revoke this approval after the deposit is complete. This can be implemented by calling safeApprove to set the allowance to the necessary amount right before the deposit and then resetting the allowance to zero right after the deposit operation.
```
xRenzoBridge.sol

function xReceive(bytes32 _transferId, uint256 _amount, address _asset, address _originSender, uint32 _origin, bytes memory) external nonReentrant returns (bytes memory) {
...

    // Approve the lockbox to spend the exact amount of ezETH required
    ezETH.safeApprove(address(xezETHLockbox), ezETHAmount);

    // Send to the lockbox to be wrapped into xezETH
    xezETHLockbox.deposit(ezETHAmount);

    // Immediately revoke the approval after use
    ezETH.safeApprove(address(xezETHLockbox), 0);
...
}
```
Using this code minimizes the risk associated with token allowances by limiting the duration and amount of the approval. By only allowing access to the tokens when absolutely necessary and immediately revoking this access, the contract reduces the attack surface related to token theft or misuse, particularly in the event of a compromised or buggy external contract.

This highlights the importance of adhering to the principle of least privilege in smart contract operations. By not minimizing the time and amount of token approvals, the contract inadvertently extends an open invitation to attackers. The simple act of resetting the token allowance (safeApprove(address(xezETHLockbox), 0)) immediately after its required use could close this vulnerability, significantly enhancing the security of the contract against unauthorized access and potential exploitation.
