# Vulnerability details

## Impact
The impact of this vulnerability is the potential for unfair distribution of ezETH tokens, skewing the tokenomics of the protocol. The attacker could gain an excessive amount of ezETH tokens compared to the actual value they contributed, undermining the fairness and stability of the system.


## Proof of Concept
The vulnerability in the `calculateMintAmount` function of the ezETH protocol smart contract allows for the exploitation of the initial deposit phase. This function is responsible for determining the amount of ezETH tokens to mint based on various parameters such as the current protocol value, new deposits, and existing ezETH supply.

The critical flaw lies in the conditional check within the function, specifically when either the current protocol value or the existing ezETH supply is zero. Let's examine the vulnerable portion of the code:
```solidity
if (_currentValueInProtocol == 0 || _existingEzETHSupply == 0) {
    return _newValueAdded; // value is priced in base units, so divide by scale factor
}
```
In this condition, if `_currentValueInProtocol` or `_existingEzETHSupply` equals zero, the function simply returns `_newValueAdded`, which represents the value of the deposit being made. This implies that during the initial deposit phase where there's no existing protocol value or ezETH supply, the entire deposit amount would be minted into ezETH tokens.

Now, let's explore how this vulnerability can be exploited:

Imagine a scenario where a malicious actor is aware of this vulnerability and is the first to deposit funds into the protocol. By making an exceptionally large deposit, the attacker can artificially inflate the initial protocol value. Since there's no comparison against existing values, the entire deposit amount would be converted into `ezETH` tokens.

As a result, the attacker gains a disproportionate amount of `ezETH` tokens relative to the actual value they contributed to the protocol. This gives them an unfair advantage and undermines the fairness and stability of the system.

In essence, this vulnerability allows the initial depositor to manipulate the minting process to their advantage, resulting in an imbalance in the distribution of `ezETH` tokens.

## Tools Used
Manual
## Recommended Mitigation Steps
Introduce a predefined initial value for the protocol or impose limits on the amount of tokens that can be minted during the initial deposit period.
