# Vulnerability details

## Summary

The operatorDelegator, integral to handling transactions with EigenLayer—from deposits to withdrawals—facilitates the queueWithdrawals function for initiating withdrawals. However, due to a flaw in a function responsible for returning the value of tokens within the operatorDelegator, the TVL is miscalculated, creating an opportunity for users to illicitly extract funds.

## Vulnerability Detail

the function `getTokenBalanceFromStrategy` is used to get the token balance of a operatorDelegator, which is important for tvl calculation:
```solidity=327
function getTokenBalanceFromStrategy(IERC20 token) external view returns (uint256) {
        return
=>            queuedShares[address(this)] == 0
                ? tokenStrategyMapping[token].userUnderlyingView(address(this))
                : tokenStrategyMapping[token].userUnderlyingView(address(this)) +
                    tokenStrategyMapping[token].sharesToUnderlyingView(
                        queuedShares[address(token)]
                    );
    }
```

it basically queries the strategy for each token in eiganLayer and gets how much tokens are deposited there. it uses the queuedShares mapping to tell it how many shares have been queued for withdrawal and to add them, because as you queue a withdrawal in eiganlayer, shares arent giving to you directly there is a withdrawal period.

it's stored like this 
```solidity=232
queuedShares[address(tokens[i])] += queuedWithdrawalParams[0].shares[i];
```

but as we can see in `getTokenBalanceFromStrategy` at line 537 it used erroneously queuedShares[address(this)] instead of the token. 
and because queuedShares[address(this)] is always 0 , it always thinks it never has any shares queued , making it reort less token amounts when there is actively queuing shares. 
this allows a malicious user to steal funds from other restakers  risk free, by frontrunning queued shares with a withdrawal and then afterwards depositing the same funds to get more ezETH.

## Proof Of Concept

- attackScenario
    - Assumptions:
        - there are 10 users each with 10 ezETH 
        - there is 100 stETH in the protocol
        - STETH:ETH = 1:1
        - a operatorDelegator submtted a transaction to withdraw 20 stETH
        - Bob is one of the 10 users
    1. Bob sees the `queueWithdrawals` transaction and frontruns it calling withdraw 10 ezETH, basically locking him at 10stETH after the cooldown period.
    2. afterwards the call to queueWithdrawals executes, and now the tvl is wrongly set to 80stETH instead of 100 until the withdrawal completes
    3. Bob deposits 10stETH (not necessarily the one he withdrew if the cooldown period is longer than eiganlayer) getting 10*totalSupply(ezETH)/totalTVL = 10*90/80 = 11.25 ezETH
    4. afterwards the admin calls completeQueuedWithdrawal to complete the wthrawal and bring back the tvl to 100ETH
    5. now bob owns 11.25 instead of 10 while not depositing any more stETH than the other users, he effectivley now owns 11.25 stETH instead of 10 stETH
    6. basically there is a free arbitrage to happen by anybody and the bigger the share of the pool he deposits after the queuewithdrawal the bigger he is going to steal form other users

steal of user funds
