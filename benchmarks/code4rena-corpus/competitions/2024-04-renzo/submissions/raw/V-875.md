# Vulnerability details

## Impact
Having a reserved amount in the `withdrawQueue` can cause an uneven distribution of deposits among operator delegators.

## Proof of Concept
When someone wants to take money out of the system, it's set aside to be claimed later. During this time, it's still counted when calculating the total value locked (TVL) in the system.

But if someone has asked to withdraw but hasn't actually claimed it yet, it can mess up the calculations.

For example, imagine there are 5 operator delegators (OD) each supposed to get 20% of the deposits, and the total value locked is 1000.

Now, someone asks to take out 900 but hasn't actually claimed it yet, so the protocol still considers there's 1000 as TVL. If someone tries to deposit in more fund, the system will think each OD should get 20% of 1000, which is 200. So, the first OD will get any new deposit until it reaches 200, even though 900 is actually reserved to be claimed.

If 180 is deposited, the first OD will get it, and now the protocol thinks there's 1180 as TVL, with 200 belonging to the first OD and only 80 for the other ODs. When the person finally claim their 900, the protocol will consider there's only 280 as TVL, with 200 belonging to the first OD and only 80 for the rest. This means the first OD ends up with 71% of the total value locked, which isn't what was expected.

## Recommended Mitigation Steps
When deciding where to put new deposits, the system shouldn't count the reserved money as part of the total value locked.
