# Vulnerability details

## **Vulnerability Details:**

The **[setTokenStrategy](https://github.com/code-423n4/2024-04-renzo/blob/1c7cc4e632564349b204b4b5e5f494c9b0bc631d/contracts/Delegation/OperatorDelegator.sol#L106)** function in the **OperatorDelegator** contract can set a token's strategy to **0x0** to remove the ability to deposit and withdraw into the strategy. However, there is currently an edge case in the implementation that could be problematic.

```solidity
    /// @dev Sets the strategy for a given token - setting strategy to 0x0 removes the ability to deposit and withdraw token
    function setTokenStrategy(IERC20 _token, IStrategy _strategy) external nonReentrant onlyOperatorDelegatorAdmin {
        if (address(_token) == address(0x0)) revert InvalidZeroInput();

        tokenStrategyMapping[_token] = _strategy;
        emit TokenStrategyUpdated(_token, _strategy);
    }
```

### Assume the following:

- The protocol creates a full withdrawal request for a token strategy then sets the strategy address to **0x0** to disable future deposits into the strategy.
- The **[completeQueuedWithdrawal](https://github.com/code-423n4/2024-04-renzo/blob/1c7cc4e632564349b204b4b5e5f494c9b0bc631d/contracts/Delegation/OperatorDelegator.sol#L265)** function is then called to complete the withdrawal. However, as seen at the end of the function below, it will attempt to redeposit any remaining tokens back into EigenLayer. Because the strategy was set to **0x0**, this will always revert.

```solidity
    function completeQueuedWithdrawal(
        IDelegationManager.Withdrawal calldata withdrawal,
        IERC20[] calldata tokens,
        uint256 middlewareTimesIndex
    ) external nonReentrant onlyNativeEthRestakeAdmin {
        ...
                // Deposit remaining tokens back to eigenLayer
                if (balanceOfToken > 0) {
                    _deposit(tokens[i], balanceOfToken);
                }
            }
            unchecked {
                ++i;
            }
        }
	...
    }
```

- An option could be to not disable the strategy until the claim, but this would make it impossible to restrict deposits into the strategy, and another withdrawal request would have to be created. Furthermore, restricting the collateral token or the operator in the **RestakeManager** contract would hinder other functionalities.

## **Impact:**

- Severity: Medium. The current implementation could lead to being unable to disable strategies efficiently.
- Likelihood: Medium. While not a common scenario, if a token strategy is needed to be disabled this problem could occur.

## **Tools Used:**

- Manual analysis

## **Recommendation:**

Consider adding an option in the **completeQueuedWithdrawal** function where it can be specified whether withdrawn tokens should be redeposited or not. This would provide more flexibility and avoid unexpected reverts in scenarios where a strategy has been disabled.
