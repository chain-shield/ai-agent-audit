# Vulnerability details

## Impact
https://docs.chain.link/data-feeds#check-the-timestamp-of-the-latest-answer states that `the aggregator updates its ``latestAnswer`` when the value deviates beyond a specified threshold or when the heartbeat idle time has passed` and `During periods of low volatility, the heartbeat triggers updates to the latest answer`. In https://data.chain.link/feeds/ethereum/mainnet/steth-eth, https://data.chain.link/feeds/base/base/steth-eth, and https://data.chain.link/feeds/arbitrum/mainnet/steth-eth, hovering over Trigger parameters's information sign indicates that these stETH / ETH oracles' heartbeats are respectively 86400 seconds. This means that the price provided by each of these oracles should at latest be updated when 86400 seconds have passed since the last price was written onchain in order to be not stale.

However, in the `RenzoOracle` contract, `MAX_TIME_WINDOW` is set to `86400 + 60`. In the `RenzoOracle.lookupTokenValue` and `RenzoOracle.lookupTokenAmountFromValue` functions below, `if (timestamp < block.timestamp - MAX_TIME_WINDOW) revert OraclePriceExpired()` is executed, where `timestamp` is the `updatedAt` returned by `oracle.latestRoundData()`. When `timestamp` is more than `block.timestamp - 86400 - 60` and less than `block.timestamp - 86400`, such `timestamp` is already stale because the relevant stETH / ETH oracle's heartbeat is 86400 seconds; yet, such `timestamp` is not considered as being stale since `timestamp < block.timestamp - MAX_TIME_WINDOW` is false. For example, if `timestamp` is `block.timestamp - 86400 - 59`, a new `timestamp` should at latest be provided at `block.timestamp - 59` but such new `timestamp` is not provided; in this case, the `timestamp`, which is `block.timestamp - 86400 - 59`, is stale but the `RenzoOracle.lookupTokenValue` and `RenzoOracle.lookupTokenAmountFromValue` functions would not consider such `timestamp` as being stale. Because calling `RenzoOracle.lookupTokenValue` and `RenzoOracle.lookupTokenAmountFromValue` functions for such stale `timestamp` would not revert, the `RestakeManager.deposit` and `WithdrawQueue.withdraw` functions that call these functions can use the stale price provided at such stale `timestamp`, which respectively cause inaccurate ezETH amount to be minted and inaccurate collateral token amount to be redeemed.

import { Test } from "forge-std/Test.sol"; // solhint-disable-line no-unused-import

contract C4Test4 is Test {
    // same MAX_TIME_WINDOW is used in RenzoOracle contract
    uint256 constant MAX_TIME_WINDOW = 86400 + 60; // 24 hours + 60 seconds

    function oracleTimeCheckMock(uint256 timestamp) public {
        // same check for updatedAt returned by Chainlink oracle
        //   is used in RenzoOracle.lookupTokenValue and RenzoOracle.lookupTokenAmountFromValue functions
        require(timestamp >= block.timestamp - MAX_TIME_WINDOW, "OraclePriceExpired");
    }

    function test_stalePriceCanBeConsideredNotStale() external {
        vm.warp(123456789);

        // if updatedAt returned by Chainlink oracle is block.timestamp - 86400 - 59,
        //   a new price should be at latest returned at block.timestamp - 59 because heartbeat is 86400
        //   so updatedAt that equals block.timestamp - 86400 - 59 should already be stale

## Recommended Mitigation Steps
https://github.com/code-423n4/2024-04-renzo/blob/549f774626b71dd13a427561d4743535a9cc0dca/contracts/Oracle/RenzoOracle.sol#L26 can be updated to the following code.
```solidity
    uint256 MAX_TIME_WINDOW = 86400;
```

Then, a function, which is only callable for the protocol's trusted admin, can be added for updating `MAX_TIME_WINDOW`. This can accommodate situations where the existing supported tokens' oracles' heartbeats change to be different from 86400 or new supported tokens' oracles or the existing supported tokens' oracles on new supported chains have heartbeats that are not 86400.
