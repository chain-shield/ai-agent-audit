# Vulnerability details

## Impact
The `RestakeManager.sol` contract has two deposit functions. The `deposit` function between lines 491-576, I have already reported. This bug finding is for the `deposit` function between lines 473-475. 

This `deposit` function is a convenience wrapper that calls the other deposit function, and is therefore also vulnerable by extension.

The `deposit` function(lines 473-475) does not have any mechanisms in place to protect against replay attacks. Replay attacks occur when a valid transaction is maliciously repeated or copied to perform unauthorized actions. This vulnerability could allow an attacker to steal funds by replaying a victim's failed transactions.

Without proper replay attack protection, an attacker could potentially replay a victim's failed transactions to siphon funds from the protocol. This could lead to significant financial losses for the victims and undermine the overall security of the protocol.


## Proof of Concept

Suppose Bob, the attacker, observes Alice, the victim, attempting to deposit tokens into the protocol. If Alice's transaction fails for any reason, Bob could intercept the transaction data and repeatedly resubmit it to the protocol, effectively draining Alice's funds.

## Tools Used
Manual review

## Recommended Mitigation Steps
Nonce-based Replay Protection: Require each transaction to include a unique nonce value that is incremented with each successful transaction. This ensures that a replayed transaction will be rejected by the protocol.
