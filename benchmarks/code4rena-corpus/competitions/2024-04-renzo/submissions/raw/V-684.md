# Vulnerability details


## Cause

When a new collateral token is added to the `RestakeManager`, there will be no TVL cap between the [calls to `addCollateralToken`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L220) [and `setTokenTvlLimit`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L709). This is because [`collateralTokenTvlLimits` can only be set after the collateral token is added (disallowed before that)](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L710-L711), and a [0 TVL cap is interpreted as an unlimited cap instead of 0](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L515-L531). This will allow backrunning `addCollateralToken` with an arbitrarily large deposit before any TVL cap is set. 
## Impact

For a newly listed collateral that is planned to be added with a small TVL limit, a deposit far exceeding the planned TVL limit puts the protocol in danger (due to uncapped exposure despite the intention to limit it), breaking the core safety mechanism of TVL limits.

- An exploiter may mint an excessive amount of ezETH for the new collateral, exposing the protocol to unintended and excessive risk. 
- The exploiter may withdraw other assets and use this opportunity to "trade" the "new collateral" at an arbitrarily large size and 0 cost, which is not available elsewhere, "offloading" the risky or illiquid collateral to ezETH holders.
- The exploiter, taking the full planned TVL cap of the collateral token, prevents users from depositing it, despite the intention to make it available for deposits.
- The protocol admins will need to manually cycle other collateral assets through the protocol to withdraw the excess "new collateral".

## Proof of Concept

1. A new collateral token is scheduled to be added with an initially small TVL cap.
2. An attacker [backruns `addCollateralToken`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L220) with a deposit much larger than the TVL cap, [minting a much larger amount of ezETH than intended for the new collateral](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L515-L531).
3. The attacker may withdraw other collateral assets if their intention was to exchange the asset.
4. Contrary to the intention, other users are not able to deposit the new collateral asset, creating a DoS for that collateral type.
5. The protocol admins need to manually cycle other assets to withdraw and dispose of the excess collateral, incurring operational costs.

## Recommended Mitigation Steps

Treat 0 TVL limit as a 0 cap, and explicitly set non-zero TVL limits to allow deposits for assets:

```diff
-        // Enforce individual token TVL limit if set, 0 means the check is not enabled
-        if (collateralTokenTvlLimits[_collateralToken] != 0) {
            // Track the current token's TVL
            uint256 currentTokenTVL = 0;

            // For each OD, add up the token TVLs
            uint256 odLength = operatorDelegatorTokenTVLs.length;
            for (uint256 i = 0; i < odLength; ) {
                currentTokenTVL += operatorDelegatorTokenTVLs[i][tokenIndex];
                unchecked {
                    ++i;
                }
            }

            // Check if it is over the limit
            if (currentTokenTVL + collateralTokenValue > collateralTokenTvlLimits[_collateralToken])
                revert MaxTokenTVLReached();
-        }
```
