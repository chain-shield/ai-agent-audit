# Vulnerability details

## Impact
All earned rewards may not be redeposited into the protocol, leading to a discrepancy between the expected and actual rewards distribution.

## Proof of Concept
The vulnerability lies in the discrepancy between the intended behavior outlined in the protocol documentation and the actual implementation of reward handling within the `DepositQueue` contract. Let's dissect the code to understand the issue more thoroughly.
 In the contract's `receive` function, which is invoked when ETH is sent to the contract, rewards earned by the protocol are processed. Here's the relevant snippet:
```solidity
// receive function to handle ETH sent to the contract
receive() external payable nonReentrant {
    uint256 feeAmount = 0;
    // Take protocol cut of rewards if enabled
    if (feeAddress != address(0x0) && feeBasisPoints > 0) {
        feeAmount = (msg.value * feeBasisPoints) / 10000;
        (bool success, ) = feeAddress.call{ value: feeAmount }("");
        if (!success) revert TransferFailed();

        emit ProtocolFeesPaid(IERC20(address(0x0)), feeAmount, feeAddress);
    }
    // update remaining rewards
    uint256 remainingRewards = msg.value - feeAmount;
    // Check and fill ETH withdraw buffer if required
    _checkAndFillETHWithdrawBuffer(remainingRewards);

    // Add to the total earned
    totalEarned[address(0x0)] = totalEarned[address(0x0)] + remainingRewards;

    // Emit the rewards event
    emit RewardsDeposited(IERC20(address(0x0)), remainingRewards);
}

```
The contract deducts a protocol fee (`feeAmount`) from the total rewards received if the fee configuration is enabled. However, it only accounts for this deducted fee and then processes the remaining rewards. The deducted fee is transferred to the `feeAddress`, if configured, but the remaining rewards are not guaranteed to be redeposited into the protocol.
After deducting the protocol fee, the contract updates the `totalEarned` mapping to include the remaining rewards and emits a `RewardsDeposited` event. However, there's no explicit logic to ensure that these remaining rewards are redeposited back into the protocol, as mandated by the protocol documentation.
## Tools Used
Manual
## Recommended Mitigation Steps
Ensure that after deducting the protocol fee, the remaining rewards are explicitly redeposited back into the protocol.
