# Vulnerability details

[`RestakeManager.deposit()`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L491) function first checks, if there is withdraw buffer to be filled or not, if there is then it first fills that buffer and then forwards the tokens to get deposited into the EigenLayer Strategy.

In short, collateral tokens will be first transferred from the `user` to the `RestakeManager` contract. From there it will be transferred to the `depositQueue` contract & from there to the `withdrawQueue`. And if there are any tokens remains, then those tokens will be transferred into the `OperatorDelegator` contract and lastly from there the tokens will be deposited into the EL Strategy:
```solidity
    function deposit(IERC20 _collateralToken, uint256 _amount,uint256 _referralId) public nonReentrant notPaused {
        ...
        _collateralToken.safeTransferFrom(msg.sender, address(this), _amount);
        uint256 bufferToFill = depositQueue.withdrawQueue().getBufferDeficit(address(_collateralToken));
        if (bufferToFill > 0) {
            bufferToFill = (_amount <= bufferToFill) ? _amount : bufferToFill;
            _amount -= bufferToFill;
            _collateralToken.safeApprove(address(depositQueue), bufferToFill);
            depositQueue.fillERC20withdrawBuffer(address(_collateralToken), bufferToFill);
        }
        if(_amount > 0){
            _collateralToken.safeApprove(address(operatorDelegator), _amount);
            operatorDelegator.deposit(_collateralToken, _amount);
        }
        ...
    }
```

The problems are that the code tries to transfer the expected amounts instead of the actual amounts and the `stETH` have intrinsic rounding down problems. It's a [known issue](https://docs.lido.fi/guides/lido-tokens-integration-guide/#1-2-wei-corner-case), and the stETH balance of an account could be lower of 1-2 wei because of rounding down. The rounding down issue is not problematic only for when the balance is displayed, but also when transfers are performed. Transferring amount from accountA to accountB could lead accountB to receive less amount.

As we have seen above, that the collateral tokens will be transferred 3-4 times, which means that the probability of this issue occurring is very high, and if any of those transfers fails then the whole trx will simply revert and user will gonna be unable to deposit stETHs.

## Impact
Broken Functionality - Users are not gonna be able to deposit one of the two collateral tokens, stETH.

## Recommended Mitigation Steps
Transfer the actual token balance instead of expected amounts:
```diff
    function fillERC20withdrawBuffer(address _asset,uint256 _amount) external nonReentrant onlyRestakeManager {
         if (_amount == 0 || _asset == address(0)) revert InvalidZeroInput();
+        uint256 balanceBefore = IERC20(_asset).balanceOf(address(this));
         IERC20(_asset).safeTransferFrom(msg.sender, address(this), _amount);
+        uint256 balanceAfter = IERC20(_asset).balanceOf(address(this));
+        uint256 actualBalance = balanceAfter - balanceBefore;
+        require(actualBalance > 0, "No Tokens Received");
-        IERC20(_asset).safeApprove(address(withdrawQueue), _amount);
+        IERC20(_asset).safeApprove(address(withdrawQueue), actualBalance);
-        withdrawQueue.fillERC20WithdrawBuffer(_asset, _amount);
+        withdrawQueue.fillERC20WithdrawBuffer(_asset, actualBalance);
    }
```
