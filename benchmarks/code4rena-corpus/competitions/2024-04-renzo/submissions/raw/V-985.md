# Vulnerability details

The [`RestakeManager.calculateTVLs()`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L274) function serves to calculate the protocol's TVL, which is used together with the total ezETH supply to determine the mint and redeem rates. This function iterates through all `OperatorDelegator` contracts and sums up the value of their staked collateral tokens and ETH, and adds the balance of collateral tokens held in the `WithdrawQueue` contract.

This is implemented as an outer loop that iterates over the operator delegators, and an inner loop that iterates over the collateral tokens for each operator delegator.

However, there is an issue with how the TVL locked in the withdrawal queues is accounted for. The TVL in the queue is only counted if there is at least one operator delegator. If there are no operator delegators, either when the protocol is freshly deployed or if they are later removed e.g. in order to migrate to new ones, the queues will not be accounted for in the TVL calculation, leading to an incorrect value being reported.

This incorrect TVL value is then used in the [`depositETH()`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L592) function to calculate the amount of ezETH to mint for a given ETH deposit. If the TVL is underreported due to the issue described above, users will be able to mint ezETH at an artificially inflated rate.

## Impact
If the protocol has no operator delegators, either when it is freshly deployed or if they are later removed, users will be able to mint ezETH at an artificially inflated rate when calling `depositETH()`. This is because the TVL used in the calculation will be underreported, not accounting for the value locked in the withdrawal queue.

## Proof of Concept
Consider the following scenario:

1. The protocol is freshly deployed, and no operator delegators have been added yet.
2. All user deposits go to the withdrawal queue, so it holds a significant amount of value in various collateral tokens.
3. User calls `depositETH()` with an ETH amount, which calls  `calculateTVLs()`.
4. `calculateTVLs()` only reports the ETH value in the deposit and withdraw queues.
8. User receives more ezETH than they should, based on the actual total value locked in the protocol.

The same scenario could occur if the protocol previously had operator delegators, but they were later removed, leaving the queues holding value that is not accounted for in the TVL calculation.

## Recommended Mitigation Steps
To fix this issue, the order of the loops should be swapped. The outer loop should iterate over the collateral tokens, and the inner loop should iterate over the operator delegators. This way, the value locked in the queues can be accounted for outside the inner loop, regardless of whether there are any operator delegators or not.

```solidity
// Iterate through the collateral tokens
for (uint256 j = 0; j < collateralTokens.length; j++) {
    uint256 tokenBalance = collateralTokens[j].balanceOf(withdrawQueue);
    totalWithdrawalQueueValue += renzoOracle.lookupTokenValue(collateralTokens[j], tokenBalance);

    // Iterate through the operator delegators
    for (uint256 i = 0; i < operatorDelegators.length; i++) {
        // ...
    }
}
```

Additionally, the `withdrawQueueTokenBalanceRecorded` flag should be removed, as it is no longer needed with the swapped loop order.
