# Vulnerability details

## Impact
All the things which depends on `totalTVL` will be effect because the value return is not right like the limit for deposits, getRate(), calculation of mint and redeem  etc. 

## Proof of Concept
The protocol uses `totalTVLs` to calculate the TVLs for each operator delegator on this basis of this  TVLs , we identify the rate of `ezETH:ETH`.

This function will iterate over operators and collateral tokens and return the value of `totalTVL` , `operatorDelegatorTVLs`, and `operatorDelegatorTokenTVLs`.
@1> When it iterate over collateral token list  , the token locked in withdrawal queue is also calculated. so the second loop `j` will give us access to each collateral token address in the list . but the code uses `i` index of first loop due to which the TVl locked in withdrawal queue will only be calculated with the first collateral token.

The collateral tokens have different value in ETH. Due to which the return vaule will be wrong .
1. Let suppose we have [`STETH`, `CBETH`] in collateral array, and with balance of [10 , 20] in withdrawal queue.
2. On time if writing this report the price of `STETH/ETH = 0.9999284463` and `CBETH/ETH=1.0681`. but I will assume that `STETH/ETH=1e17` and `CBETH/ETH=1e18` for simplicity.
3. In first alteration i=0 and j will start from 0 to 1 as follows:
  a. The code will calls `renzoOracle.lookupTokenValue` with `STETH` oracle address and 10 token as balance. here j =0 and the calculation would be `(1e17*10)/1e18 = 1` add the return value to `totalWithdrawalQueueValue`. 
  b. In next alteration the i=0 and j=1 so the balance will be 5 now but the oracle address is still if `STETH` so the return value will be `(1e17*20)/1e18=2` , but it has to be 20 here.
