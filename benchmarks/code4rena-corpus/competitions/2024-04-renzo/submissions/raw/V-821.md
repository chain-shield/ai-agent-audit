# Vulnerability details

## Summary
[Inflation Attacks](https://www.youtube.com/watch?v=3IMw7xbxJgY) usually happen in Vault like systems. A vault is any contract where funds are deposited and managed by the contract. This also has a receipt token to keep track of the deposited funds and manage it etc. There is usually an exchange rate between the deposited token and the receipt token. And this exchange rate might vary with time and other metrics. With respect to Renzo, the deposited token can be ETH, stETH etc. And the receipt token is the ezETH.

Renzo calculates it TVL by directly using the [`address(depositQueue).balance`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L352) and [`address(withdrawalQueue).balance`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L355). This makes it vulnerable to inflation attacks.

## Impact

Inflation attacks can cause loss of funds for early depositors and in case of Renzo can DOS any deposit less than a certain amount. And even deposits higher than that amount will loose funds due to this 

## Proof of Concept
The issue lies in the [`RenzoOracle::calculateMintAmount`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Oracle/RenzoOracle.sol#L123) function.

```solidity
function calculateMintAmount(
        uint256 _currentValueInProtocol,
        uint256 _newValueAdded,
        uint256 _existingEzETHSupply
    ) external pure returns (uint256) {
        // For first mint, just return the new value added.
        // Checking both current value and existing supply to guard against gaming the initial mint
        if (_currentValueInProtocol == 0 || _existingEzETHSupply == 0) {
            return _newValueAdded; // value is priced in base units, so divide by scale factor
        }

        // Calculate the percentage of value after the deposit
        uint256 inflationPercentaage = (SCALE_FACTOR * _newValueAdded) /
            (_currentValueInProtocol + _newValueAdded);

        // Calculate the new supply
        uint256 newEzETHSupply = (_existingEzETHSupply * SCALE_FACTOR) /
            (SCALE_FACTOR - inflationPercentaage);

        // Subtract the old supply from the new supply to get the amount to mint
        uint256 mintAmount = newEzETHSupply - _existingEzETHSupply;

        // Sanity check
        if (mintAmount == 0) revert InvalidTokenAmount();

        return mintAmount;
    }
```

This function is responsible to calculate the amount to ezETH tokens to be minted to a depositor, depending on the current Value locked in the protocol, the value of the newly deposited tokens and the existing ezETH supply.

Lets go through an scenario to better understand how the attack might happen.

Lets assume Renzo has just launched and has no TVL. Alice wants to deposit 1 ETH into Renzo and she broadcasts a transaction for the same. Now Bob(the attacker) sees Alices transaction and frontrun the transaction by doing a couple of thing.

1. Bob deposits 1 wei into Renzo. Gets 1 wei of ezETH minted. 
2. Bob directly sends 1.05 ETH to the `DepositQueue` contract. Its `recieve` function splits that 1.05 ETH into protocol fees and sends the rest to the WithdrawQueue contract.

Lets go into more details and how the states change in each step.

#### Bob deposits 1 wei into Renzo. Gets 1 wei of ezETH minted
The state at the beginning of this step is
```solidity
currentValueInProtocol = 0
ezETHSupply = 0
```
Since this is the first every deposit into Renzo, there is no TVL and no ezETHSupply.

As Bob deposits 1 wei, since TVL and ezETHSupply is zero according to [line 131](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Oracle/RenzoOracle.sol#L131), 1 wei of ezETH is minted to Bob.
After this step the state is.
```solidity
currentValueInProtocol = 1 wei
ezETHSupply = 1 wei
```

#### Bob directly sends 1.05 ETH to the `DepositQueue` contract.
Now Bob directly sends 1.05 ETH to the `DepositQueue` contract. The `DepositQueue` contract's [`receive`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Deposits/DepositQueue.sol#L163) function is executed. There the fee is calculated and is sent to the fee address. In this scenarios lets assume the fee is 5%. So approximately 0.05 ETH (more like 0.047ETH but lets round it off for calculation) is sent to the fee address. And the remaining 1 ETH is send to the WithdrawQueue as it doesn't have any Buffer as of yet(other than the 1 wei of ETH Bob deposited).

Now the state of the Protocol is
```solidity
currentValueInProtocol = 1 ETH + 1 wei
ezETHSupply = 1 wei
```
#### Alice's transaction is executed, and it reverts
Now Alice's transaction will revert cause the amount of ezETH to be minted for her will become 0.

Lets see go line by in the `RenzoOracle::calculateMintAmount` function.
```solidity
function calculateMintAmount(
        uint256 _currentValueInProtocol,
        uint256 _newValueAdded,
        uint256 _existingEzETHSupply
    ) external pure returns (uint256) {
```

- The _currentValueInProtocol is the currentValueInProtocol which is currently 1 ETH + 1 wei.
- The _newValueAdded is the amount of ETH Alice is depositing which is 1 ETH
- The _existingEzETHSupply is the current ezETH supply which is 1 wei

In the next line,
```solidity
if (_currentValueInProtocol == 0 || _existingEzETHSupply == 0) {
            return _newValueAdded; // value is priced in base units, so divide by scale factor
        }
```
Neither `_currentValueInProtocol` or `_existingEzETHSupply` is zero. Hence it doesn't revert.

In the next lines,
```solidity
uint256 inflationPercentaage = (SCALE_FACTOR * _newValueAdded) /
            (_currentValueInProtocol + _newValueAdded);
``` 
The `inflationPercentaage` is 499999999999999999 wei as the SCALE_FACTOR= 1e18, and 1 ETH is 1e18 wei.

In the next line,
```solidity
uint256 newEzETHSupply = (_existingEzETHSupply * SCALE_FACTOR) /
            (SCALE_FACTOR - inflationPercentaage);
```
The newEzETHSupply will becomes rounded off to 1. 

In the next lines we can see where it reverts

```solidity
uint256 mintAmount = newEzETHSupply - _existingEzETHSupply;

// Sanity check
if (mintAmount == 0) revert InvalidTokenAmount();

```
Since the _existingEzETHSupply is 1 and newEzETHSupply is also 1. The mintAmount is 0 and it reverts.

Hence any deposit of less than 2 ETH will result in a Denial of Service. Even then if its 2 ETH or more, the ezETH tokens minted will be 1 wei and now the state of the protocol will be
```solidity
currentValueInProtocol = 3 ETH + 1 wei
ezETHSupply = 2 wei
```  
Now Bob will be able to redeem his 1 wei of ezETH token and get make 1.5 ETH. Basically stealing 0.5 ETH from Alice.
