# Vulnerability details

## Impact

The `RestakeManager.Deposit()` function can be reverted, even when there is sufficient capacity available in `operatorDelegators`. This is highly likely, as `operatorDelegators` can utilize different strategies for the same ERC20 token.

## Proof of Concept

Strategies inherited from `StrategyBaseTVLLimits` have two restrictions on the deposit amount, enforced through the `maxTotalDeposits` and `maxPerDeposit` parameters. 

https://github.com/Layr-Labs/eigenlayer-contracts/blob/dev/src/contracts/strategies/StrategyBaseTVLLimits.sol#L79-L84

```solidity
    contract StrategyBaseTVLLimits is StrategyBase {
        /// The maximum deposit (in underlyingToken) that this strategy will accept per deposit
@>      uint256 public maxPerDeposit;

        /// The maximum deposits (in underlyingToken) that this strategy will hold
@>      uint256 public maxTotalDeposits;
        [...]

        function _beforeDeposit(IERC20 token, uint256 amount) internal virtual override {
@>          require(amount <= maxPerDeposit, "StrategyBaseTVLLimits: max per deposit exceeded");
@>          require(_tokenBalance() <= maxTotalDeposits, "StrategyBaseTVLLimits: max deposits exceeded");

            super._beforeDeposit(token, amount);
        }
        [...]
    }
```

However, the allocation mechanism for `operatorDelegators` does not take these restrictions into account. It only considers the total value of all assets delegated into the `operatorDelegator`

https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L362-L393

```solidity

        // If there is only one operator delegator, return it

            return operatorDelegators[0];
        }

        // Otherwise, find the operator delegator with TVL below the threshold
        uint256 tvlLength = tvls.length;
        for (uint256 i = 0; i < tvlLength; ) {
            if (
@>              tvls[i] <
                (operatorDelegatorAllocations[operatorDelegators[i]] * totalTVL) /
                    BASIS_POINTS /
                    BASIS_POINTS
            ) {
                return operatorDelegators[i];
            }

            unchecked {
                ++i;
            }

@>      return operatorDelegators[0];

```

As a result, the `RestakeManager.Deposit()` function can be reverted unreasonably in two cases:
(i) When the deposit amount exceeds the maxPerDeposit limit of the strategy for the chosen operatorDelegator.
(ii) When the total token balance held by the strategy for the chosen operatorDelegator, including the new deposit amount, exceeds the maxTotalDeposits limit of the strategy.

However, in the cases where the deposit is rejected due to exceeding the maxPerDeposit or maxTotalDeposits limits, there could still be sufficient capacity available in other `operatorDelegators`. This is because the current allocation mechanism only considers the total value of all assets delegated into the `operatorDelegator`, without taking into account the different strategies that may be used for the same ERC20 token.

## Recommended Mitigation Steps

The collateral token distribution mechanism employed by the RestakeManager for operatorDelegators should be improved.
