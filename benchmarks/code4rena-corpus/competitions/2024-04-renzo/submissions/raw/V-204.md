# Vulnerability details

## Impact
The `claim` function in the WithdrawQueue contract is intended to allow users to claim their withdrawal requests after a cooldown period. Upon claiming, the function should remove the associated withdrawal request from both the array and the mapping, effectively erasing all data related to the request and ensuring that it cannot be accessed or manipulated further.

However, due to the incomplete removal of data, the vulnerability allows the data associated with claimed withdrawal requests to persist in the mapping even after the request has been logically removed from the array. This means that sensitive user information, such as withdrawal amounts and timestamps, remains accessible through the mapping, creating a risk of unauthorized access or manipulation.
## Proof of Concept
The `WithdrawQueue` contract exhibits a vulnerability in its handling of withdrawal requests. The vulnerability arises from incomplete data removal when a user claims their withdrawal request.

In the `WithdrawQueue` contract, withdrawal requests from users are stored in both an array and a mapping. The array `withdrawRequests` holds the indexes of the withdrawal requests associated with each user, while the mapping `withdrawRequests` stores the actual withdrawal request data keyed by user addresses.
```solidity

    struct WithdrawRequest {
        address collateralToken;
        uint256 withdrawRequestID;
        uint256 amountToRedeem;
        uint256 ezETHLocked;
        uint256 createdAt;
    }
```
When a user claims their withdrawal request, the claim function is called. This function correctly removes the request from the array by overwriting it with the last element of the array and then popping the last element. However, it fails to clear the associated data from the mapping.
```solidity
    /// @dev mapiing of withdraw requests array, indexed by user address
    mapping(address => WithdrawRequest[]) public withdrawRequests;
}
```
This incomplete removal leaves the data associated with the claimed withdrawal request accessible through the mapping. Although the request is logically removed from the array, its data remains intact in the mapping, posing a security risk.

## Recommended Mitigation Steps
One effective mitigation to address the incomplete data removal vulnerability in the `WithdrawQueue` contract is to ensure that all associated data related to claimed withdrawal requests is fully deleted from both the array and the mapping within the claim function.

```solidity
function claim(uint256 withdrawRequestIndex) external nonReentrant {
    // Ensure the provided withdrawRequestIndex is valid
    if (withdrawRequestIndex >= withdrawRequests[msg.sender].length)
        revert InvalidWithdrawIndex();

    // Retrieve the withdrawal request from the array
    WithdrawRequest memory _withdrawRequest = withdrawRequests[msg.sender][withdrawRequestIndex];

    // Ensure that the cooldown period has elapsed
    if (block.timestamp - _withdrawRequest.createdAt < coolDownPeriod) revert EarlyClaim();

    delete withdrawRequests[msg.sender][withdrawRequestIndex];

    // Remove the request from the array

    withdrawRequests[msg.sender].pop();
```
