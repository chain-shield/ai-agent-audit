# Vulnerability details

## Impact
1. Break of Protocol Functionality as only the first operator Delegator would always be chosen for Deposit by the chooseOperatorDelegatorForDeposit(...) function in Restake Manager contract
2. Break of Protocol Functionality as operator Delegator with tvl below proper threshold would be chosen for Withdrawal by the chooseOperatorDelegatorForWithdraw(...) function as against Protocol expectation at [L416](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L416) of the Restake Manager contract
## Proof of Concept
Due to the Similarity in Error causing both impacts, for the purpose of this report major focus would be given to the error in first impact.

The depositTokenRewardsFromProtocol(...) function above from the RestakeManager contract shows how Token Reward is Deposited from the Protocol, as noted from the pointers above the point of interest is how the Operator Delegator to be used is determined from the list operators, each operators tvls and the cumulative total tvl is used to make a choice of of one operator.
The break down of how an operator tvl is calculated at [L307](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L307) of the calculateTVLs(...) function shows that, an Operator tvl is based on an Operator actual token values in the contract while totalTVL is the the total.
The problem is in the chooseOperatorDelegatorForDeposit(...) functiion code below that shows how a choice is made.

It can be noted that apart from each operator tvl and total tvl, each operator has a basis point allocated to them i.e operatorDelegatorAllocations[...], this is different from the individual tvl value of each operator. Based on protocol documentation and implementation the cumulative sum of all operators allocation must add up to 10000 i.e 100% of the total tvl. 
Based on the first pointer the operator choice is made based on the first operator delegator with TVL below the threshold i.e below the percentage value allocated to the operator. The problem is that there is a mistake in the calculation. Basis point which is suppose to act at percentage was divided twice instead of once which will reduce the allocation value excessively thereby making it impossible for the each users tvl to be below the calculated allocated tvl( since it is now extremely small), the function would therefore have to result to the default of first operator in the array based on [L392](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L392) whether it meets threshold standard or not.
### Scenario Proof
Assuming we are working with a sample of 4 operators
operators = [ 30 , 45 , 35 , 70 ] ,
total tvl = 180 ,
and allocation = [10%, 50%, 15%, 30%] (must sum up to 100%),
the current implementation to make a operator choice looks like this
 30 < 10 * 180 / 100 / 100
 30 < 0.18 (0.18 is obviously an error and 30 cant be below  0.18 or any of the consequent operator for that matter there by resulting to using the default first operator even though 30 is not below 18 that would have been the normal value.
The correct value would have been 
30 < 10 * 180 / 100
30 < 18  for first operator
then 30 < 50 * 180 / 100
30 < 90  for second operator
then 30 < 15 * 180 / 100
30 < 27  for third operator
etc.
The point is that if the implementation was correct the second operator is the first operator that falls below the threshold (30 < 90) and should should have been chosen but the default is always chosen as the functionality is broken due to this error.
The error that leads to the second impact is also similar in many ways to this explanation and should both be corrected
