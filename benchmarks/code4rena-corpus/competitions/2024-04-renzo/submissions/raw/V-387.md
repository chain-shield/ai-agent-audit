# Vulnerability details

## Impact
`RestakeManager.getTotalRewardsEarned()` incorrectly calculates the rewards earned from the eigenPod, breaking the contract composability and providing false values to external protocols reading from it.

## Vulnerability details
`RestakeManager.getTotalRewardsEarned()` is used to calculate the rewards earned from the protocol as the sum of all eigen pod balances + the rewards registered in the `depositQueue`:

https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L695-L704

```solidity
function getTotalRewardsEarned() external view returns (uint256) {
        uint256 totalRewards = 0;

        // First get the ETH rewards tracked in the deposit queue
        totalRewards += depositQueue.totalEarned(address(0x0));

        // For each token, get the total rewards earned from the deposit queue and price it in ETH
        uint256 tokenLength = collateralTokens.length;
        for (uint256 i = 0; i < tokenLength; ) {
            // Get the amount
            uint256 tokenRewardAmount = depositQueue.totalEarned(address(collateralTokens[i]));

            // Convert via the price oracle
            totalRewards += renzoOracle.lookupTokenValue(collateralTokens[i], tokenRewardAmount);

            unchecked {
                ++i;
            }
        }

        // For each OperatorDelegator, get the balance (these are rewards from staking that have not been restaked)
        // Funds in OD's EigenPod are assumed to be rewards in M1 until exiting validators or withdrawals are supported
        // Pending unstaked delayed withdrawal amounts are pending being routed into the DepositQueue after a delay

        uint256 odLength = operatorDelegators.length;
        for (uint256 i = 0; i < odLength; ) {
            totalRewards += address(operatorDelegators[i].eigenPod()).balance;
            unchecked {
                ++i;
            }
        }

        return totalRewards;
    }
```
Pay attention to the comment added for the `eigenPod` calculations:

`For each OperatorDelegator, get the balance (these are rewards from staking that have not been restaked). Funds in OD's EigenPod are assumed to be rewards in M1 until exiting validators or withdrawals are supported. Pending unstaked delayed withdrawal amounts are pending being routed into the DepositQueue after a delay`

The latest version of the protocol brakes those assumptions with the introduction of the `withdraw flow`, meaning EigenPod withdrawals and validator exits are now supported. This argument is further reinforced by [looking at the new functions inside](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol#L193-L265) `OperatorDelegator` - `queueWithdrawals` & `completeQueuedWithdrawal`. Those have been commented out in the [currently deployed version](https://etherscan.io/address/0x0683c3cc018fb76874fdcc8620d15c4e467e34ca#code).

Since the assumptions have changed and withdraws have been enabled, the calculation of rewards is not valid anymore, because it will now include full validator withdrawals that have been send to the Pod, which won't be true, because those are not rewards.

When funds are withdrawn from the validator partially (validator rewards) or fully (exiting the validator) in both cases the validator transfers the funds to the `EigenPod`. Those transfers are subsequently proven by the pod owner through `EigenPod.verifyAndProcessWithdrawals()`.

In case of a partial withdraw (rewards) the amount is sent to the `DelayedWithdrawRouter` to be claimed by the podOwner after a delay. In case of a full withdraw it stays in the Pod.

[The pod for the currently deployed `OperatorDelegator.sol` also has enabled](https://etherscan.io/address/0x2641C2ded63a0C640629F5eDF1189e0f53C06561#readProxyContract) restaking (migrated to M2)

The conclusion is that `eigenPod().balance` will include not only the rewards but also the unstaked ETH from the validator. Meaning that the reported rewards will be massively inflated

## Recommended Mitigation Steps

The partial withdrawals (rewards sent from the validator) after being proven with `EigenPod.verifyAndProcessWithdrawals()` are send to the `DelayedWithdrawRouter`.

This has already been handled by calculating the rewards routed to `DepositQueue`
 
Any additional ETH send to the pod that is not exited by the validator is accummulated in the `nonBeaconChainETHBalanceWei` storage variable and claimable through the `withdrawNonBeaconChainETHBalanceWei()` function.

So a proper way to calculate the rewards in the EigenPod would be to get only the the `nonBeaconChain ETH`:


```solidity
uint256 totalRewards;
...
totalRewards +=  eigenPod().nonBeaconChainETHBalanceWei()
```
