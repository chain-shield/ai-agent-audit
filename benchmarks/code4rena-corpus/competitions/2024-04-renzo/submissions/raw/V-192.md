# Vulnerability details

## Impact
The `mint` and `burn` functions in OptimismMintableXERC20.sol will not work as expected because the `optimismBridge` is not marked as `msg.sender` in the `_mintWithCaller` function. This defeats the purpose of the contract as it cannot mint or burn tokens. Important to note fixing the issue by marking OptimismMintableXERC20.sol as a bridge opens up another attack vector in which users can freely mint tokens (or in some cases burn tokens) as pointed out in another of my reports. 

## Proof of Concept

From OptimismMintableXERC20.sol, the bridge address is declared, which is presumably to make the contract compliant with [ERC7281](https://ethereum-magicians.org/t/erc-7281-sovereign-bridged-tokens/14979) which allows directly burning through bridges.

```solidity
    function bridge() public view override returns (address) {
        return optimismBridge;
    }
```
The bridge is declared upon contract initialization.
```solidity
    function initialize(
        string memory _name,
        string memory _symbol,
        address _factory,
        address _l1Token,
        address _optimismBridge
    ) public initializer {
...
        optimismBridge = _optimismBridge;
    }
```

Working with the `mint` function, it calls `mint` in XERC20.sol

```solidity
    function mint(address _to, uint256 _amount) public override(XERC20, IOptimismMintableERC20) {
        XERC20.mint(_to, _amount);
    }
```

The function calls the `_mintWithCaller` passing in `msg.sender` as the caller, which is OptimismMintableXERC20.sol
```solidity
    function mint(address _user, uint256 _amount) public virtual {
        _mintWithCaller(msg.sender, _user, _amount);
    }
```
The `_mintWithCaller` function checks if caller is not lockbox, it attempts to get the current mint limit of the caller, i.e OptimismMintableXERC20.sol.

```solidity
    function _mintWithCaller(address _caller, address _user, uint256 _amount) internal {
        // Do not allow 0 value mints
        if (_amount == 0) revert IXERC20_INVALID_0_VALUE();

        if (_caller != lockbox) {
            uint256 _currentLimit = mintingCurrentLimitOf(_caller); //@note
            if (_currentLimit < _amount) revert IXERC20_NotHighEnoughLimits();
            _useMinterLimits(_caller, _amount);
        }
        _mint(_user, _amount);
    }
```
But due to the fact that it most likely will not be marked as a bridge, as the actual Optimism Bridge had been declared upon initialization as described above, the returned `_currentLimit` will be zero, causing the function chain to revert. 
The same applies to the [`burn`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Bridge/xERC20/contracts/optimism/OptimismMintableXERC20.sol#L68) function too as it follows the same pattern.

While, OptimismMintableXERC20.sol can be [set](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Bridge/xERC20/contracts/XERC20.sol#L135) as a bridge, it goes against the EIP and also opens up the protocol to an excessive minting attack vector due to the lack of access control on the `mint` function.

## Recommended Mitigation Steps
Best way to fix this

In the mint function: 
```solidity
        function mint(address _to, uint256 _amount) public override(XERC20, IOptimismMintableERC20) {
        XERC20._mintWithCaller(bridge(), _user, _amount);
    }
```
In the burn function:

```solidity
    function burn(address _from, uint256 _amount) public override(XERC20, IOptimismMintableERC20) {
        XERC20._burnWithCaller(bridge(), _user, _amount);
    }
```
