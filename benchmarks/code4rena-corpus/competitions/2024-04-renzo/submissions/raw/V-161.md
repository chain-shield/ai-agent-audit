# Vulnerability details

## Impact
The DocString/Natspec of the method `fillEthWithdrawBuffer` states that it is 

access controlled by the Restake manager - only restake manager is able to call it 

with access control imposed by ``

but the modifier used is `onlyDepositQueue` which ensures only the deposit Queue 

contract will be able to call this method .


```solidity
 /**
     * @notice  fill Eth WithdrawBuffer from RestakeManager deposits
     * @dev     permissioned call (onlyRestakeManager)
     */

 function fillEthWithdrawBuffer() external payable nonReentrant onlyDepositQueue {
        emit EthBufferFilled(msg.value);
    }
```

But this check given in Natspec is not really enforced 

## Proof of Concept

If we take a look at DepositQueue calls to WithdrawQueue's fillEthWithdrawBuffer 

method we see that in fact it is being in  one function.

```solidity


  function _checkAndFillETHWithdrawBuffer(uint256 _amount) internal {
        // Check the withdraw buffer and fill if below buffer target
        uint256 bufferToFill = withdrawQueue.getBufferDeficit(IS_NATIVE);

        if (bufferToFill > 0) {
            bufferToFill = (_amount <= bufferToFill) ? _amount : bufferToFill;

            // fill withdraw buffer from received ETH
            withdrawQueue.fillEthWithdrawBuffer{ value: bufferToFill }();

            emit BufferFilled(IS_NATIVE, bufferToFill);
        }
    }
```

Taking a look at where it is being called :

```solidity
 function depositETHFromProtocol() external payable onlyRestakeManager {
        _checkAndFillETHWithdrawBuffer(msg.value);
        emit ETHDepositedFromProtocol(msg.value);
    }

 function forwardFullWithdrawalETH() external payable nonReentrant {
        // Check and fill ETH withdraw buffer if required
        _checkAndFillETHWithdrawBuffer(msg.value);
        emit FullWithdrawalETHReceived(msg.value);
    }
  receive() external payable nonReentrant {
        uint256 feeAmount = 0;
        // Take protocol cut of rewards if enabled
        if (feeAddress != address(0x0) && feeBasisPoints > 0) {
            feeAmount = (msg.value * feeBasisPoints) / 10000;
            (bool success, ) = feeAddress.call{ value: feeAmount }("");
            if (!success) revert TransferFailed();

            emit ProtocolFeesPaid(IERC20(address(0x0)), feeAmount, feeAddress);
        }
        // update remaining rewards
        uint256 remainingRewards = msg.value - feeAmount;
        // Check and fill ETH withdraw buffer if required
        _checkAndFillETHWithdrawBuffer(remainingRewards);

        // Add to the total earned
        totalEarned[address(0x0)] = totalEarned[address(0x0)] + remainingRewards;

        // Emit the rewards event
        emit RewardsDeposited(IERC20(address(0x0)), remainingRewards);
    }

```

we can see that the assumption that `WithdrawQueue#fillEthWithdrawBuffer` is being 

called only by a Restake manager holds only for `depositETHFromProtocol`

which has that explicit modifier but the other two code blocks

`forwardFullWithdrawalETH` and `receive` are open to anyone to call.

So if anyone is able to call those functions, anyone is able to call `WithdrawQueue#fillEthWithdrawBuffer` which conflicts with the stated docs/Natspec of the function.

This might break the protocol's assumptions and lead to unforeseen situations

## Tools Used
Manual review
## Recommended Mitigation Steps
Please clearly document who can call this function.

If the `WithdrawQueue#fillEthWithdrawBuffer` is intended to only be called

by a Restake manager , make sure that the msg.sender is the restake manager

in both `forwardFullWithdrawalETH` and `receive` methods of DepositQueue.

This will help in staying consistent with protocol's long term goals and 

assumptions leading to a consistent system for future.
