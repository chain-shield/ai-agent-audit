# Vulnerability details

## Impact
The RenzoOracleL2 does not account for price feed's deviation from the original price. Which can result in getMintRate function returning less than or greater than the actual value which will be used to incorrectly mint the amount of ezETH user will receive when they call xRenzoDeposit#deposit method.

RenzoL2Oracle#getMintrate

```solidity

  function getMintRate() public view returns (uint256, uint256) {
        (, int256 price, , uint256 timestamp, ) = oracle.latestRoundData();
        if (timestamp < block.timestamp - MAX_TIME_WINDOW) revert OraclePriceExpired();
        // scale the price to have 18 decimals
        uint256 _scaledPrice = (uint256(price)) * 10 ** (18 - oracle.decimals());
        if (_scaledPrice < 1 ether) revert InvalidOraclePrice();
        return (_scaledPrice, timestamp);
    }
```

For example xRenzoDeposit#deposit method fetches price from this function , and with no validation of price amount, it calculates the eth amount to be returned

```solidity

  function _deposit(
        uint256 _amountIn,
        uint256 _minOut,
        uint256 _deadline
    ) internal returns (uint256) {
         //snip

        // Fetch price and timestamp of ezETH from the configured price feed
        (uint256 _lastPrice, uint256 _lastPriceTimestamp) = getMintRate();

        // snip
        uint256 xezETHAmount = (1e18 * amountOut) / _lastPrice;

        // Check that the user will get the minimum amount of xezETH
        if (xezETHAmount < _minOut) {
            revert InsufficientOutputAmount();
        }
        //snip
        
// Mint xezETH to the user
        IXERC20(address(xezETH)).mint(msg.sender, xezETHAmount);

        // Emit the event and return amount minted
        emit Deposit(msg.sender, _amountIn, xezETHAmount);
        return xezETHAmount;
    }
```
The `getMintRate` of RenzoDeposit calls the `RenzoOracleL2.getMintRate()` method.

However if the returned price deviates sufficiently from the original price , 
it can cause unwanted scenarios see PoC section.

See the deviation is `0.5%` .

currently the price of eth is `3,101 USD` & Renzo ETH `$3,050.05`

So let's take the price of ezETH $3,050.05

A `0.5% deviation` means a deviation of `15$`.

It means the price given by the oracle might be less than `15$`.

If the price is returned so , the user will get ezETH worth 15$ less in the deposit function call of xRenzoDeposit facing a loss of 15$

Now you might think the loss of 15$ is nothing but take a look at the following people 

A loss of 15$ means A loss of `4500 PKR` for a Pakistani 

A loss of 15$ means A loss of `21090.56 NGR` for a Nigerian

A loss of 15$ means A loss of `630937.52 Irani rial` for an Irani Citizen

this loss will escalate when the `ezEth price` goes up let's say the price reaches `10000$`

then the loss will be `50$` now again that will be 

`15000 PKR`

`70k NGR`

`2.1 Million for Irani citizens`

So you see these losses are substantial for users on the other side of the world
whose currency is not natively USD.

This small in-accountancy of deviation will lead to `Losses of Millions` for some users.

Since direct loss of funds is involved, so High severity is appropriate.

## Recommended Mitigation Steps
Add Deviation handling mechanism for returned price 

There can be multiple solutions and the protocol has to think about how to fix it.
one is using some fallback oracle and using the average of prices fetched from Chainlink and that oracle -i.e pyth

The second solution is to do the following (might not be totally efficient )

( (price - (0.5% of price)) +  (price + (0.5% of price)) ) / 2

Implementing any efficient solution can `save someone Millions` and thousands to others.
