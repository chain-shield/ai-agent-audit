# Vulnerability details

## Impact
In the xRenzoDeposit contract, decimals were enforced only during initialization in which the contract expected all tokens, including ETH when wrapped to WETH to have 18 decimals for pricing and calculations but unfortunately, there was no explicit check for that in the depositETH and deposit functions.

The xRenzoDeposit contract expects all tokens involved in transactions to have 18 decimals for pricing. This is explicitly stated in the contract with the declaration:

```
uint8 public constant EXPECTED_DECIMALS = 18;
```
The deposit and depositETH function doesn't explicitly set the restrictions of decimals which can lead to loss of funds for user during price calculations.

This constant is used to ensure that all tokens being handled by the contract, such as the deposit token, collateral token, and the xezETH token, adhere to this decimal requirement. The contract includes checks during initialization to verify that these tokens indeed have 18 decimals. If any token does not meet this requirement, the contract initialization will revert with an error indicating the mismatch in expected decimals. But no, the initialization of decimals in a contract doesn't automatically imply that decimals are checked in all functions of the same contract. Initialization typically occurs in the constructor or during contract deployment, and it sets initial values or parameters for the contract's state variables.

It's important to note that some tokens, like USDC, have a different number of decimals than the standard 18. Additionally, if any user-created ERC-20 token sets its decimals to a uint8 bound, it could also lead to incorrect price calculations. If these tokens are deposited, it could result in a loss of funds due to inaccurate pricing for the USDC/WETH pair.
