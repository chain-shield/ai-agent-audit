# Vulnerability details

## Summary

The restakeManager:calculateTVLs function is tasked with aggregating the total value locked (TVL) within the protocol by summing the values in the operator delegator, deposit queue, and withdrawal queue. However, it currently omits ERC20 rewards stored in the deposit queue, which can lead to discrepancies in reward distribution. This oversight allows users to potentially exploit the timing of reward inclusion, front-running the system to claim a disproportionate share of the rewards.

## Vulnerability Detail

the `depositQueue` contract is responsible for getting rewards from eiganlayer , it is able to accept ETH rewards from beaconChain validators in eiganLayer, but it also is able to accept erc20 rewards once they add them to eiganLayer. these rewards are gotten back into the system by calling `sweepERC20`:
```solidity=254
function sweepERC20(IERC20 token) external onlyERC20RewardsAdmin {
        uint256 balance = IERC20(token).balanceOf(address(this));
        if (balance > 0) {
            uint256 feeAmount = 0;

            // Sweep fees if configured
            if (feeAddress != address(0x0) && feeBasisPoints > 0) {
                feeAmount = (balance * feeBasisPoints) / 10000;
                IERC20(token).safeTransfer(feeAddress, feeAmount);

                emit ProtocolFeesPaid(token, feeAmount, feeAddress);
            }

            // Approve and deposit the rewards
            token.approve(address(restakeManager), balance - feeAmount);
            restakeManager.depositTokenRewardsFromProtocol(token, balance - feeAmount);

            // Add to the total earned
            totalEarned[address(token)] = totalEarned[address(token)] + balance - feeAmount;

            // Emit the rewards event
            emit RewardsDeposited(IERC20(address(token)), balance - feeAmount);
        }
    }
```

this basically sends the rewards back to th staekManager whee he restakes them back to the operator delegators.

```solidity=647
function depositTokenRewardsFromProtocol(
        IERC20 _token,
        uint256 _amount
    ) external onlyDepositQueue {
        // Get the TVLs for each operator delegator and the total TVL
        (, uint256[] memory operatorDelegatorTVLs, uint256 totalTVL) = calculateTVLs();

        // Determine which operator delegator to use
        IOperatorDelegator operatorDelegator = chooseOperatorDelegatorForDeposit(
            operatorDelegatorTVLs,
            totalTVL
        );

        // Transfer the tokens to this address
        _token.safeTransferFrom(msg.sender, address(this), _amount);

        // Approve the tokens to the operator delegator
        _token.safeApprove(address(operatorDelegator), _amount);

        // Deposit the tokens into EigenLayer
        operatorDelegator.deposit(_token, _amount);
    }
```

However, there is a critical oversight in how the TVL is calculated; only ETH balances are considered:
```solidity=352
totalTVL += address(depositQueue).balance;
```

This exclusion means that until an admin triggers the sweepERC20, ERC20 rewards remain unaccounted for in the TVL. This delay can be exploited by malicious actors who, by timing their deposits and withdrawals around the sweepERC20 execution, can manipulate their share of the distributed rewards, gaining an unfair advantage.

## Proof Of Concept

- attack scenario
    - assumptions
        - there are 10 depositors all with 10 ezETH each and 100 ETH in tvl
        - the depositQueue just got rewards with 10stETH
        - the admin is calling the sweepERC20 function
        - STETH/ETH = 1:1
    1. bob frontruns the sweepERC20 call , by depositing 100stETH getting 100 ezETH
    2. the sweepERC20 function goes through sweeping rewards to operator delegator
    3. now the tvl = 100 + 100 + 10 = 210 ETH and BOB owns 50% of ezETH supply
    4. bob queues a withdrawal with 100 ezETH getting 105 stETH in return
    5. he basically stole 5 stETH from all the other ezETH depositors that actually staked their stETH to accrue those rewards

## Impact

steal of user's rewards by malicious user

Manual Review

## Recommendation

to prevent such exploits, the protocol should adjust its TVL calculation to include ERC20 tokens held in the deposit queue, similar to how it handles the withdrawal queue.
