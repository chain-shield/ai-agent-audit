# Vulnerability details

## Vulnerability Detail
When `OperatorDelegator.stakeETH()` is called by `RestakeManager`, the storage variable `stakedButNotVerifiedETH` is incremented:
```solidity
stakedButNotVerifiedEth += msg.value; 
```

Then later when admin calls `OperatorDelegator.verifyWithdrawalCredentials()`, the variable is decremented:
```solidity
uint64 validatorCurrentBalanceGwei = BeaconChainProofs.getEffectiveBalanceGwei(
    validatorFields[i]
);
stakedButNotVerifiedEth -= (validatorCurrentBalanceGwei * GWEI_TO_WEI); 
```

As seen above, it is decremented by the effective balance of the validator. 

However, the code does not consider the fact that since the funds have been staked in the beacon chain contract (this occurs in the same tx as `OperatorDelegator.stakeETH()`), they can be slashed.

However since the validator could have been slashed, the effective balance of the validator may not be 32 (it can be less than that).

Hence, `stakedButNotVerifiedEth` will not be reduced to 0 even though after calling `verifyWithdrawalCredentials()` there would be `0` unverified ETH that has been staked.

Since the value of `stakedButNotVerifiedEth` is now inflated, the value returned by `OperatorDelegator.getStakedETHBalance()` will be inflated. This will inflate the total TVL calculated within `RestakeManager.calculateTVLs()`. This will inflate the value of ezETH more than what it should be.

## Impact
Users can withdraw collateral tokens at a higher rate than they should be allowed to, due to the inflation of ezETH's value. This breaks the main invariant stated in the README: 

> ezETH should be minted or redeemed based on current supply and TVL

## Proof of Concept
Consider the following scenario:
1. Admin calls `DepositQueue.stakeEthFromQueue()`, this ends up calling `OperatorDelegator.stakeETH{value: 32 ether}()`
    - this increments `stakedButNotVerifiedEth` by 32 ether
    - within this transaction, the 32 ether is deposited into the beacon chain deposit contract for ethereum staking
2. The validator misbehaves and gets slashed, so it's effective balance drops to 20 ether. (lost 12 ether)
3. The admin calls `OperatorDelegator.verifyWithdrawalCredentials()`, and this decrements `stakedButNotVerifiedEth` by 20 ether.
4. As a result, `stakedButNotVerifiedEth` = 12 ether (even though it should be 0)

Now, `totalTVL` is calculated to be 12 ether more than what it should be, causing the value of ezETH to be inflated. This allows people to redeem more collateral tokens than what is deserved, leading to loss for the protocol.
