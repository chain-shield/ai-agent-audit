# Vulnerability details

## Impact
The contract DepositQueue.sol does not sufficiently validate the `_asset` address in the `fillERC20withdrawBuffer` function leading to a potential vulnerability where any troublesome token (e.g a token having re-entrancy in its `transferFrom` function) could be spent arbitrarily.


## Proof of Concept
https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Deposits/DepositQueue.sol#L134-L145

```solidity
function fillERC20withdrawBuffer(
        address _asset,
        uint256 _amount
    ) external nonReentrant onlyRestakeManager {
        // safeTransfer from restake manager to this address
        IERC20(_asset).safeTransferFrom(msg.sender, address(this), _amount);
        ...
    }
```

## Recommended Mitigation Steps

To mitigate the risk we could accept tokens that are only pre-approved.

Furthermore, it is paramount to have checks on tokens to strictly allow transactions from particular addresses. The contract can maintain a list of allowed tokens which can be added or removed by the contract owner or through a DAO mechanism. Code snippet below shows an example of this implementation. 

Update the contract to include an `allowedTokens` mapping with a function to allow the contract owner to manage the list of allowed tokens.

```solidity
mapping (address => bool) public allowedTokens;

function allowToken(address token, bool allowed) external onlyOwner {
    allowedTokens[token] = allowed;
}
```

Then assert in the `fillERC20withdrawBuffer` function that the token is allowed before making the transfer.

```solidity
require(allowedTokens[_asset], "Token not allowed");

// safeTransfer from restake manager to this address
IERC20(_asset).safeTransferFrom(msg.sender, address(this), _amount);
