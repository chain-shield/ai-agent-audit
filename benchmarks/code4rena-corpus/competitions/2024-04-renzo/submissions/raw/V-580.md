# Vulnerability details

## Impact

`RenzoOracle` and `RenzoOracleL2` assume that the prices returned from Chainlink always come in 18-decimal format. This is not always correct.

## Proof of Concept

```solidity
function lookupTokenAmountFromValue(
    IERC20 _token,
    uint256 _value
) external view returns (uint256) {
    AggregatorV3Interface oracle = tokenOracleLookup[_token];
    if (address(oracle) == address(0x0)) revert OracleNotFound();

    (, int256 price, , uint256 timestamp, ) = oracle.latestRoundData();
    if (timestamp < block.timestamp - MAX_TIME_WINDOW) revert OraclePriceExpired();
    if (price <= 0) revert InvalidOraclePrice();

    // Price is times 10**18 ensure token amount is scaled
    return (_value * SCALE_FACTOR) / uint256(price);
}
```

As can be seen in the example above from `RenzoOracle`, the function expects the oracle to always return prices with 18 decimal places. This might not be the case, as there are a lot of pairs that return 8-decimal results. In that case the following calculation will be incorrect:

```solidity
// Price is times 10**18 ensure token amount is scaled
return (_value * SCALE_FACTOR) / uint256(price);
```

It currently assumes that both `_value` and `price` use 18 decimals but it doesn't try to upscale ones with 8 decimals.

## Tools Used

Manual Review

## Recommended Mitigation Steps

Apply proper scaling in the affected functions when the price is not in 18 decimals.
