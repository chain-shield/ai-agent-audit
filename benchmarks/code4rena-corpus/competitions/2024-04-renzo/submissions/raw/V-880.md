# Vulnerability details

## Bug description

When depositing assets, Renzo will always verify the withdrawal queue to see if enough assets are deposited in it so that withdrawals can be fulfilled. This check is done in the deposit flows, where the following steps are performed to verify the withdrawal queue’s balance:

1. The withdraw queue's `bufferToFill` is obtained by calling `getBufferDeficit`. `bufferToFill` corresponds to the remaining amount needed for the withdraw queue to be filled.
2.  If there’s still room to fill in the withdraw queue (i.e `bufferToFill > 0`), then some of the tokens deposited by the user will be sent to the withdraw queue. The amount to send is determined by the following conditions:
    1. If the amount deposited by the user is smaller than the buffer to fill, then **all the user’s deposited tokens** will be sent to the withdraw queue
    2. Otherwise, the `bufferToFill` will be substracted from the amount to deposit and deposited into the withdraw queue. The remaining amount will then be deposited into the operator delegator

```solidity
File: RestakeManager.sol

function deposit(
        IERC20 _collateralToken,
        uint256 _amount,
        uint256 _referralId
    ) public nonReentrant notPaused {
        ...

        // Transfer the collateral token to this address
        _collateralToken.safeTransferFrom(msg.sender, address(this), _amount);

        // @audit-info Transfer deposit to Renzo's withdraw queue
        // Check the withdraw buffer and fill if below buffer target
        uint256 bufferToFill = depositQueue.withdrawQueue().getBufferDeficit(
            address(_collateralToken)
        );

        if (bufferToFill > 0) { 
            bufferToFill = (_amount <= bufferToFill) ? _amount : bufferToFill;
            // update amount to send to the operator Delegator
            _amount -= bufferToFill;

            // safe Approve for depositQueue
            _collateralToken.safeApprove(address(depositQueue), bufferToFill);

            // fill Withdraw Buffer via depositQueue
            depositQueue.fillERC20withdrawBuffer(address(_collateralToken), bufferToFill);
        }

        // Approve the tokens to the operator delegator
        _collateralToken.safeApprove(address(operatorDelegator), _amount); 

        // Call deposit on the operator delegator
        operatorDelegator.deposit(_collateralToken, _amount); 
				
				...

}
```

The problem is found when the amount deposited by the user is smaller than the buffer to fill. As mentioned, all the deposited tokens will be sent to the withdraw queue, so after exiting the `if (bufferToFill > 0) {`  conditional and depositing into the operator delegator, `_amount` will be 0, given that all the amount has been deposited into the withdraw queue.

If this situation arises, transactions will always revert, given that a 0 `_amount` will be intended to be deposited into the operator delegator when calling `operatorDelegator.deposit`.

The `OperatorDelegator` implementation shows how 0 amount deposits will always revert with `InvalidZeroInput()` :

```solidity
 File: OperatorDelegator.sol
 
 function deposit(
        IERC20 token,
        uint256 tokenAmount
    ) external nonReentrant onlyRestakeManager returns (uint256 shares) {
        if (address(tokenStrategyMapping[token]) == address(0x0) || tokenAmount == 0)
            revert InvalidZeroInput();

        ...
    }
```

So users won’t be able to deposit an amount smaller than the `bufferToFill`, given that the transaction will always revert when trying to deposit.

## Impact

Medium. Some user interactions will always revert, making it compulsory to always deposit at least `bufferToFill` amount. This can be especially impactful if the buffer to fill is a big amount because several withdrawals have emptied the withdraw queue.

## Recommended Mitigation

If the amount to be deposited is smaller than the `bufferToFill`, don’t deposit any asset into the Operator Delegator:
