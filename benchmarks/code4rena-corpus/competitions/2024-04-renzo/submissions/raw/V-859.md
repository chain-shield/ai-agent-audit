# Vulnerability details

## Title
Withdrawal queue TVL should be excluded when minting new ezETH token with `RestakeManager::deposit()`

## Line of code
https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L491

## Impact
When users deposit using the function `RestakeManage::deposit` it mints the ezETH in exchange of token deposit amount. Now if we look into the the `ezETHToMint`, It calls the `RenzoOracle::calculateMintAmount` with `totalTVL`, `collateralTokenValue`, `ezETH.totalSupply()`. 
```solidity
 uint256 ezETHToMint = renzoOracle.calculateMintAmount(
            totalTVL,
            collateralTokenValue,
            ezETH.totalSupply()
        );
```

From the `RenzoOracle::calculateMintAmount`, we can get that for the same amount of token added and the same existing supply and the higher the current total TVL, the less token minted.
When `totalTVL` is calculated from `calculateTVLs()` function. If we look into, when the total TVL is calculated, we include the withdrawal queque amount also. This will impact the amount of ezETH to be minted as the total TVL will increase if we add the `totalWithdrawalQueueValue`, decreasing the ezETH mint amount.

We have simulated the scenario with this python script:

```python 
ETH = 10 ** 18
currentValueInProtocol = 10 * ETH
new_value_added = 20 * ETH
SCALE_FACTOR = 10 ** 18

def calc_mint_amount(currentValueInProtocol, new_value_added, existingSupply):

    inflationPercentage = (SCALE_FACTOR * new_value_added) / (currentValueInProtocol + new_value_added)

    newEzETH = (existingSupply * SCALE_FACTOR) / (SCALE_FACTOR - inflationPercentage)

    return newEzETH - existingSupply

def full_print(a):
    print ('{:f}'.format(a))

# TVL is 50 ETH
# withdrawal queue balance is 50 ETH

mint_amount = calc_mint_amount(50 * ETH + 50 * ETH, 20 * ETH, 50 * ETH)
full_print(mint_amount)

# TVL is 50 ETH
mint_amount = calc_mint_amount(50 * ETH, 20 * ETH, 50 * ETH)
full_print(mint_amount)
```
Output: 
```bash
    
9999999999999991808.000000
20000000000000000000.000000

```
Basically, Assume that TVL is 50 ETH and the withdrawal queue balance is 50 ETH, the minted amount will be 9999999999999991808. While if we exclude the withdrawal queue balance and use the TVL as 50 ETH, the minted amount is 20000000000000000000

In the worst, malicious user can deposit the token to the withdrawal queue directly to inflate the TVL and make user receive less token when minting. The fund in withdrawal queue will be distributed to the user that burnt their ezETH and should not be counted as the total TVL which impacting minting.

Because of adding withdrawal queue balance, it will impact the calculation of amount of ezETH to be minted with this [calculateMintAmount](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Oracle/RenzoOracle.sol#L123C4-L149C6)

```solidity
 function calculateMintAmount(
        uint256 _currentValueInProtocol,
        uint256 _newValueAdded,
        uint256 _existingEzETHSupply
    ) external pure returns (uint256) {
        // For first mint, just return the new value added.
        // Checking both current value and existing supply to guard against gaming the initial mint
        if (_currentValueInProtocol == 0 || _existingEzETHSupply == 0) {
            return _newValueAdded; // value is priced in base units, so divide by scale factor
        }

        // Calculate the percentage of value after the deposit
        uint256 inflationPercentaage = (SCALE_FACTOR * _newValueAdded) /
            (_currentValueInProtocol + _newValueAdded);

        // Calculate the new supply
        uint256 newEzETHSupply = (_existingEzETHSupply * SCALE_FACTOR) /
            (SCALE_FACTOR - inflationPercentaage);

        // Subtract the old supply from the new supply to get the amount to mint
        uint256 mintAmount = newEzETHSupply - _existingEzETHSupply;

        // Sanity check
        if (mintAmount == 0) revert InvalidTokenAmount();

        return mintAmount;
    }
```
