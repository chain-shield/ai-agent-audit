# Vulnerability details

## Impact
Users cannot deposit less than the withdraw buffer deficit for the deposited collateral token.

## Proof of Concept
### Relevant Code
```solidity

contract RestakeManager is Initializable, ReentrancyGuardUpgradeable, RestakeManagerStorageV2 {
    // ...

    function deposit(
        IERC20 _collateralToken,
        uint256 _amount,
        uint256 _referralId
    ) public nonReentrant notPaused {

        // Check the withdraw buffer and fill if below buffer target

            address(_collateralToken)
        );
        if (bufferToFill > 0) {
            bufferToFill = (_amount <= bufferToFill) ? _amount : bufferToFill; // <==== Audit (A)

            _amount -= bufferToFill; // <==== Audit (B)

        _collateralToken.safeApprove(address(operatorDelegator), _amount);

        // Call deposit on the operator delegator
        operatorDelegator.deposit(_collateralToken, _amount); // <==== Audit (C)

        // ...
    }

    // ...
}
```

### Root Cause
When the withdraw queue for the deposited collateral token has a buffer deficit, the deposited collateral with be used to fill that buffer deficit.

The problem arises when the user deposited amount is lower than or equal to the buffer deficit as the final amount to deposit to the operator delegator ends up being 0 and causes a revert.

### Scenario
Assuming a withdraw queue buffer deficit of `2 ether` for `stETH` and Bob tries to deposit `1 ether` of `stETH` :
* `bufferFill` will be equal to `1 ether` (**Audit (A)**)
* `_amount` will be equal to `0` (**Audit (B)**)
* `operatorDelegator.deposit(_collateralToken, _amount)` (**Audit (C)**) will revert because of the zero amount check (**Audit (D)**).

This forces Bob to at least deposit `2 ether + 1 wei` of `stETH`.
