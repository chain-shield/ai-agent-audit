# Vulnerability details

## Impact

Users will get more ezETH than intended.

## Proof of Concept

When depositing ETH via `restakeManager.depositETH()`, the function first calculates the total value locked TVL of the protocol.

```
    function depositETH(uint256 _referralId) public payable nonReentrant notPaused {
        // Get the total TVL
        (, , uint256 totalTVL) = calculateTVLs();


        // Enforce TVL limit if set
        if (maxDepositTVL != 0 && totalTVL + msg.value > maxDepositTVL) {
            revert MaxTVLReached();
        }
```

This TVL is counted by getting the value from the operatorDelegator contract through `getTokenBalanceFromStrategy()` and `getStakedETHBalance()`, which gets its value from Eigenlayer contract. The TVL also includes the value locked in the withdrawal queue, this includes the deposit buffer and the amount waiting to be withdrawn by users.

What is not included is the value locked in the DepositQueue. Only when 32 ETH is locked in the depositQueue, it will then be transferred to EigenLayer with the owner calling `stakeETHFromQueue()` in the DepositQueue contract, but before that, it will stay idle in the DepositQueue contract.

```
  function stakeEthFromQueue(
        IOperatorDelegator operatorDelegator,
        bytes calldata pubkey,
        bytes calldata signature,
        bytes32 depositDataRoot
    ) external onlyNativeEthRestakeAdmin {
        uint256 gasBefore = gasleft();
        // Send the ETH and the params through to the restake manager
        restakeManager.stakeEthInOperatorDelegator{ value: 32 ether }(
            operatorDelegator,
            pubkey,
            signature,
            depositDataRoot
        );

        emit ETHStakedFromQueue(operatorDelegator, pubkey, 32 ether, address(this).balance);

        // Refund the gas to the Admin address if enough ETH available
        _refundGas(gasBefore);
    }
```

The `depositETH()` function will then deposit the amount of ETH into the depositQueue and calculate the mint amount. 

When withdrawing tokens, the TVL is calculated and the ezETH amount is exchanged to the requested token, with the conversion rate calculated through `renzoOracle.calculateRedeemAmount`. Note the higher the `_currentValueInProtocol`, the larger the `redeemAmount`.

```
 function calculateRedeemAmount(
        uint256 _ezETHBeingBurned,
        uint256 _existingEzETHSupply,
        uint256 _currentValueInProtocol
    ) external pure returns (uint256) {
        // This is just returning the percentage of TVL that matches the percentage of ezETH being burned
>       uint256 redeemAmount = (_currentValueInProtocol * _ezETHBeingBurned) / _existingEzETHSupply;

        // Sanity check
        if (redeemAmount == 0) revert InvalidTokenAmount();

        return redeemAmount;
    }
```

What the user can do is that when the user sees that the depositQueue is reaching 32 ETH, or has already reached 32 ETH, it can call `depositETH()`, frontrunning the DepositQueue's owner `stakeEthFromQueue()` call. This means that they will mint tokens with lower TVL.

After `stakeEthFromQueue()` is called, the user can immediately withdraw the ezETH he gets and get more ETH than when he first deposits, since TVL will drastically increase when the value 32 ETH is factored into the TVL.

Let's say current value in protocol is 100k, ezETH == ETH == 1,000 USD

User deposits 1 ETH, gets 1 ezETH.

32 ETH is deposited into the protocol, which raises the TVL by 32k.

User withdraws 1 ezETH, `calculateRedeemAmount()` is called.

132k * 1 ezETH / 101 ezETH = 1.3 ETH

User deposits 1 ETH and gets back 1.3 ETH.

It should be noted that the higher the TVL, the lesser the value extracted.

## Recommended Mitigation Steps

Since TVL already calculates the value in the withdrawQueue contract, it should also calculate the value in the depositQueue contract to prevent any sandwich attacks.
