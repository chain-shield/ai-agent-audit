# Vulnerability details

## Impact
Detailed description of the impact of this finding.
The protocol is not compatible with token such as USDT because of the Approval Face Protection due to which if before setting an approval the existing approval is non zero then the transaction reverts for such tokens.

## Proof of Concept
Take following example.

1. Restake Manager calls DepositQueue.sol#fillERC20withdrawBuffer with asset being erc20 token with approval face protection i.e USDT with some non zero amount
2. Inside the code there is approval going on

```solidity
    function fillERC20withdrawBuffer(
        address _asset,
        uint256 _amount
    ) external nonReentrant onlyRestakeManager {
        if (_amount == 0 || _asset == address(0)) revert InvalidZeroInput();
        // safeTransfer from restake manager to this address
        IERC20(_asset).safeTransferFrom(msg.sender, address(this), _amount);
        // approve the token amount for withdraw queue
        IERC20(_asset).safeApprove(address(withdrawQueue), _amount);
        // call the withdraw queue to fill up the buffer
        withdrawQueue.fillERC20WithdrawBuffer(_asset, _amount);
    }
```

```solidity
  IERC20(_asset).safeApprove(address(withdrawQueue), _amount);
```

If the approval already set is non zero , then this function call will revert 

reverting the filling of the erc20 withdraw buffer.

The situation will escalate when a lot of erc220 withdraw buffers contain underlying assets such as usdt.

this will lead to DoS for such kind of withdraw buffers.

## Recommended Mitigation Steps
Add a zero approval transaction 

```solidity
// approve the token amount for withdraw queue
IERC20(_asset).safeApprove(address(withdrawQueue), 0);
IERC20(_asset).safeApprove(address(withdrawQueue), _amount);

```
