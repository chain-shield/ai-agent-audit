# Vulnerability details

## Impact
`RestakeManager::deposit()` allow anyone to put their LRT as a collateral for the ezETH token. However the issue is, if the deposited amount is not enough to fill the withdraw buffer to its target, the user txn will likely reverts. 
## Proof of Concept
When user deposit, the funds channel to the two external contract i.e. depositQueue and operatorDelegator. If the `_amount` deposited is `<=` to the `bufferToFill`, the user entire deposited `_amount` is transfer to the depositQueue contract, leaving behind `_amount=0` for the operatorDelegator contract. 
https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L546-L556
```solidity
        if (bufferToFill > 0) {
>@          bufferToFill = (_amount <= bufferToFill) ? _amount : bufferToFill;
            // update amount to send to the operator Delegator
>@          _amount -= bufferToFill;

            // safe Approve for depositQueue
            _collateralToken.safeApprove(address(depositQueue), bufferToFill);

            // fill Withdraw Buffer via depositQueue
            depositQueue.fillERC20withdrawBuffer(address(_collateralToken), bufferToFill);
        }
```

Say `withdrawalBufferTarget[stETH] = 20 ether`, during the initial stages of the protocol high likelihood its unfilled yet. Now, for any user its required atleast `20 ether + 1wei` of stETH to make a successuful deposit, which is rarely gonna happen. 

*Note there is no fund loss since the txn reverted. But there could be onboarding issues due to above reason.*

## Recommended Mitigation Steps
Since only the restakeManager allowed to call `deposit()` on opeartorDelegator, I suggest either removing `tokenAmount == 0` check or call operatorDelegator for non-zero tokenAmount only.
