# Vulnerability details

## Impact
EigenLayer withdrawals can be DoSed by sandwiching the complete withdrawal transaction. The cost for the attack is only the gas that will be provided for 2 transactions. Also the attacker has to wait coolDownPeriod to actually get back to assets back. However, the assets are guaranteed to be returned to attacker so the time that needs to pass is not a threat for the attacker

## Proof of Concept
EigenLayer withdrawals are initiated firstly and then there is a wait period of approx 1 week which an another tx has to be sent to network. So, first tx will queue the withdrawal from EigenLayer and the second tx will actually claim the tokens which the process takes around a week. 

If the Renzo buffer is empty meaning that there should be some idle funds in withdraw queue for user withdrawals, there are 2 ways to satisfy this. 
1- If a user deposits, their deposit will directly go to withdraw queue and increases buffer
2- Admin role can unstake funds via following the above EigenLayer flow which will result idle tokens in withdraw queue hence increase in buffer.

Let's see how the `completeQueuedWithdrawals` function implemented in Renzo:
```solidity
function completeQueuedWithdrawal(
        IDelegationManager.Withdrawal calldata withdrawal,
        IERC20[] calldata tokens,
        uint256 middlewareTimesIndex
    ) external nonReentrant onlyNativeEthRestakeAdmin {
        .
        .
        // complete the queued withdrawal from EigenLayer with receiveAsToken set to true
        delegationManager.completeQueuedWithdrawal(withdrawal, tokens, middlewareTimesIndex, true);

        IWithdrawQueue withdrawQueue = restakeManager.depositQueue().withdrawQueue();
        for (uint256 i; i < tokens.length; ) {
            .
            .
            // check if token is not Native ETH
            if (address(tokens[i]) != IS_NATIVE) {
                // Check the withdraw buffer and fill if below buffer target
                uint256 bufferToFill = withdrawQueue.getBufferDeficit(address(tokens[i]));

                // get balance of this contract
                uint256 balanceOfToken = tokens[i].balanceOf(address(this));
                -> if (bufferToFill > 0) {
                    bufferToFill = (balanceOfToken <= bufferToFill) ? balanceOfToken : bufferToFill;

                    // update amount to send to the operator Delegator
                    balanceOfToken -= bufferToFill;

                    // safe Approve for depositQueue
                    tokens[i].safeApprove(address(restakeManager.depositQueue()), bufferToFill);

                    // fill Withdraw Buffer via depositQueue
                    restakeManager.depositQueue().fillERC20withdrawBuffer(
                        address(tokens[i]),
                        bufferToFill
                    );
                }

                // Deposit remaining tokens back to eigenLayer
                if (balanceOfToken > 0) {
                    _deposit(tokens[i], balanceOfToken);
                }
            }
            unchecked {
                ++i;
            }
        } 
        .
        .
    }
```

As we can see above, if the time when the complete queued withdrawal happens, which as we know this is approx after 7 days when the first queue tx is called; if the buffer is full meaning that there are no other additional tokens needed then the code will skip returning tokens to withdrawal queue and instead redeposits the freshly withdrawn funds back to EigenLayer strategies. 

An attacker can fill the buffer just before the complete withdrawal tx to make function send back the freshly withdrawn funds back to EigenLayer and then attacker withdraws his funds from Renzo immediately. 

#### Textual PoC:
Assume there are 100 WBETH worth EigenLayer WBETH strategies with a single operator. Also, there are no idle funds in the withdrawal queue. Also, the buffer amount for WBETH is 10, which means that there should be 10 WBETH in the withdrawal queue for user withdrawals. 
Admin sees that there are no new deposits and decides to withdraw 10 WBETH worth of EigenLayer shares to fill the buffer. Admin first have to call queue withdrawals and initiate the 7 day withdrawal period. After 7 days, when admin is eligible to call complete withdrawal the buffer is still empty which means everything works as expected. However, attacker sees that and sandwiches the admins complete withdrawal function as follows:
1- Attacker deposits the exact amount that makes the buffer full, which in our case its 10 WBETH 
2- Admin complete withdrawal tx executes, since buffer is full all funds deployed back to EigenLayer
3- Attacker immediately withdraws from Renzo. This withdrawal will also act as an initiation of a proper withdrawal just like EigenLayer. However, attacker is guaranteed to withdraw its funds after the delay passes since the funds are idle in the withdraw queue and claimReserve[WBETH] is updated and buffer is 0 back again.

function test_completeWithdrawal_canBeSandwiched_toGrief() external {

        // withdraw 10e18 WBETH
        IERC20[] memory _tokens = new IERC20[](1);

        IDelegationManager.Withdrawal memory w = IDelegationManager.Withdrawal(address(od1), address(0), address(od1), 0, blockNo, _strats, _amounts); 
        vm.stopPrank();

        // we know that the buffer to fill is 10 WBETH so lets deposit just before the withdrawal
        deal(address(WBETH), tapir, 10e18);
        vm.prank(tapir);

        vm.roll(block.number + 216000 + 1);
        vm.prank(management);
        od1.completeQueuedWithdrawal(w, _tokens, 0);

        // since the funds are liquid in withdraw queue, tapir can just withdraw it immediately in a single block
        vm.startPrank(tapir);
        wq.withdraw(10e18, address(WBETH));

## Recommended Mitigation Steps
Regardless of the excess withdrawal do not redeposit the funds back to eigen layer and add a functionality to re-deposit the funds in withdraw queue to operators.
