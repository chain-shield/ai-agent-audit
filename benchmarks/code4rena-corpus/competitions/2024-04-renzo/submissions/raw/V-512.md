# Vulnerability details

## Impact
Operator Delegators that are not actively participating in the RestakeManager's ETH staking can still have ETH deposits and verify withdrawal credentials. This can lead to the RestakeManager miscalculating the TVL for ETH.

Miscalculation of the total ETH holdings managed by the RestakeManager. Withdrawals can fail because the calculated ETH is not available in the active Operator Delegators, but the TVL indicates that there is ETH available to withdraw.

## Proof of Concept
An Operator Delegator can have ETH deposits by calling the `stakeEth` function in the OperatorDelegator contract:

https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol#L349-L359

```solidity
 function stakeEth(
        bytes calldata pubkey,
        bytes calldata signature,
        bytes32 depositDataRoot
    ) external payable onlyRestakeManager {
        // Call the stake function in the EigenPodManager
        eigenPodManager.stake{ value: msg.value }(pubkey, signature, depositDataRoot);

        // Increment the staked but not verified ETH
        stakedButNotVerifiedEth += msg.value;
    }
```

...even if it is not actively participating in the `RestakeManager`'s ETH staking strategy. The OperatorDelegator can also call `verifyWithdrawalCredentials` to increase its EigenPod shares and decrease the queued ETH, regardless of whether it is an active Operator Delegator in the RestakeManager.

Now, let's examine how the TVL for ETH is calculated in the RestakeManager:

https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L274-L358
```solidity
function calculateTVLs() public view returns (uint256[][] memory, uint256[] memory, uint256) {
    // ...
    for (uint256 i = 0; i < odLength; ) {
        // ...
        // Get the value of native ETH staked for the OD
        uint256 operatorEthBalance = operatorDelegators[i].getStakedETHBalance();

        // Save it to the array for the OD
        operatorValues[operatorValues.length - 1] = operatorEthBalance;

        // Add it to the total TVL for this OD
        operatorTVL += operatorEthBalance;

        // Add it to the total TVL for the protocol
        totalTVL += operatorTVL;
        // ...
    }
    // ...
}
```

As we can see above, the `RestakeManager` loops through all the Operator Delegators, regardless of whether they are actively participating in the ETH staking strategy or not.

Since an inactive Operator Delegator can have EigenPod shares, the TVL calculation will account for it. However, since the Operator Delegator is not actively participating in ETH deposits (not in the RestakeManager's list of active Operator Delegators), withdrawals or deposits to this specific Operator Delegator are not possible through the RestakeManager. Hence, the TVL is accounting for an Operator Delegator's EigenPod shares, which the RestakeManager assumes is not actively participating.

### Textual PoC
Assume there are 5 Operator Delegators, but only 4 of them are actively participating in the RestakeManager's ETH staking strategy. This means that 1 Operator Delegator is not in the RestakeManager's list of active Operator Delegators. However, this Operator Delegator can still have ETH deposits and can verify them. Since the TVL calculation loops over all the Operator Delegators, not just the ones actively participating in the ETH staking strategy, the calculated TVL will be incorrect.


## Tools Used
Manual review

## Recommended Mitigtion Steps
Add a check in the `verifyWithdrawalCredentials` function to ensure that it can only be called if the Operator Delegator is actively participating in the RestakeManager's ETH staking strategy. Additionally, modify the TVL calculation in the RestakeManager to only account for the ETH balances of active Operator Delegators.
