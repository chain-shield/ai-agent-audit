# Vulnerability details

## Impact

L1 contract sends an undervalued ezETH price to L2.

This can allow users to mint more ezETH on L2 than expected for the same amount of ETH.


## Proof of Concept

### Root cause

The [`xRenzoBridge.sendPrice` function retrieves the ezETH price](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Bridge/L1/xRenzoBridge.sol#L215) to send it to the L2 contracts.
ezETH price is calculated in the `BalancerRateProvider.getRate` function based on [the totalTVL](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RateProvider/BalancerRateProvider.sol#L31) in protocol and the ezETH total supply.

```solidity
    /// @dev Returns the current rate of ezETH in ETH
    function getRate() external view returns (uint256) {
        // Get the total TVL priced in ETH from restakeManager
        (, , uint256 totalTVL) = restakeManager.calculateTVLs();

        // Get the total supply of the ezETH token
        uint256 totalSupply = ezETHToken.totalSupply();

        // Sanity check
        if (totalSupply == 0 || totalTVL == 0) revert InvalidZeroInput();

        // Return the rate
        return (10 ** 18 * totalTVL) / totalSupply;
    }
```

However, the `totalTVL` calculated in `RestakeManager.calculateTVLs()` has two issues that will reduce the amount of total TVL:
- issue 01: `WithdrawalQueue`'s value is incorrectly accounted in totalTVL due to [a confusion in variable names](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L317-L319)
- issue 02: All the `OperatorDelegator` contracts do not account withdraw queued shares in totalTVL due to [an incorrect condition](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Delegation/OperatorDelegator.sol#L329)

Combined, these two issues can decrease the `totalTVL` value [returned by `RestakeManager.calculateTVLs()`](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L274-L358).
As this `totalTVL` will be incorrect, the `getRate()` function will return an incorrect price and this price will be bridged to L2.

Then, an undervalued price can be used by users to mint more ezETH tokens on the L2 than on the L1 for a same amount of ETH, bridge back these funds to L1 and exchange them back to ETH on L1.
This will drain value from the protocol.

## Recommended Mitigation Steps

Consider fixing the two issues explained in the root cause section.

### Fix issue 01

Consider fixing the index used for the `collateralTokens` in [the `calculateTVLs` function](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/RestakeManager.sol#L316-L321).

The following patch implements such a fix:

```diff
diff --git a/contracts/RestakeManager.sol b/contracts/RestakeManager.sol
index 8c754e6..ceb32d0 100644
--- a/contracts/RestakeManager.sol
+++ b/contracts/RestakeManager.sol
@@ -315,7 +315,7 @@ contract RestakeManager is Initializable, ReentrancyGuardUpgradeable, RestakeMan

                     totalWithdrawalQueueValue += renzoOracle.lookupTokenValue(
-                        collateralTokens[i],
+                        collateralTokens[j],
                         collateralTokens[j].balanceOf(withdrawQueue)

```

*Note: The patch can be applied with `git apply`.*
