# Vulnerability details

`RestakeManager:calculateTVLs()` loops trough the registered OperatorDelegators and adds up their token balances (deposited) to compute the TVL of the whole system.

The token balance of a single OperatorDelegator is retrieved by this line:

```js
uint256 operatorBalance = operatorDelegators[i].getTokenBalanceFromStrategy(
    collateralTokens[j]
);
```

The issue is found in how `OperatorDelegator:getTokenBalanceFromStrategy()` handles 0-address strategies (not-set):

```js
function getTokenBalanceFromStrategy(IERC20 token) external view returns (uint256) {
    return
        queuedShares[address(this)] == 0
            ? tokenStrategyMapping[token].userUnderlyingView(address(this))
            : tokenStrategyMapping[token].userUnderlyingView(address(this)) +
                tokenStrategyMapping[token].sharesToUnderlyingView(
                    queuedShares[address(token)]
                );
}
```

If `tokenStrategyMapping[token] = address(0)` the call to `userUnderlyingView` will revert... making impossible to execute `RestakeManager:calculateTVLs()`.


## Impact

No one will be able to mint ezETH if at lest one OperatorDelegator does not support a registered collateral token.

I believe this issue to be considered as a medium since it can temprorarly block the protocol but can be easily resolved by contacting the OperatorDelegator causing it.

## Recommended Mitigation Steps

Make `OperatorDelegator:getTokenBalanceFromStrategy()` return 0 if the token is not supported.

```diff
function getTokenBalanceFromStrategy(IERC20 token) external view returns (uint256) {
+   if (tokenStrategyMapping[token] == address(0)) return 0;
    return
        queuedShares[address(this)] == 0
            ? tokenStrategyMapping[token].userUnderlyingView(address(this))
            : tokenStrategyMapping[token].userUnderlyingView(address(this)) +
                tokenStrategyMapping[token].sharesToUnderlyingView(
                    queuedShares[address(token)]
                );
}
```
