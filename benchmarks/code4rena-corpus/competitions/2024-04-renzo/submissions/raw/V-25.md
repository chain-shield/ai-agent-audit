# Vulnerability details


The `WithdrawQueue:Withdraw()` function handles withdrawal requests and calculates the total TVL for converting LP tokens into underlying assets. However, it mistakenly adds an additional amount of token assets to the TVL calculation.

Within the `RestakeManager::calculateTVL()`, it calls the `OperatorDelegator::getTokenBalanceFromStrategy`:
```solidity
                uint256 operatorBalance = operatorDelegators[i].getTokenBalanceFromStrategy(
                    collateralTokens[j]
                );
```

Upon examining the function, it retrieves the underlying token amount by combining the shares with queued withdrawal shares. Users submitting withdrawal requests are consolidated through `queuedShares`, which represents the mapping of token shares in EigenLayer's withdrawal queue. Consequently, this results in obtaining shares from the withdrawal queue that were not part of the deposited strategy.

```solidity

    function getTokenBalanceFromStrategy(IERC20 token) external view returns (uint256) {
        return
            queuedShares[address(this)] == 0 // mapping of token shares in withdraw queue of EigenLayer
                ? tokenStrategyMapping[token].userUnderlyingView(address(this))
                : tokenStrategyMapping[token].userUnderlyingView(address(this)) +
                    tokenStrategyMapping[token].sharesToUnderlyingView(
                        queuedShares[address(token)]
                    ); 
    }
```
The Eigenlayer's codebase snippet provided above uses the following two functions: 

This function is used to convert a number of shares to the equivalent amount of underlying tokens for this strategy.
```
    function sharesToUnderlyingView(uint256 amountShares) public view virtual override returns (uint256) {
        if (totalShares == 0) {
            return amountShares;
        } else {
            return (_tokenBalance() * amountShares) / totalShares;
        }
```

Lastly, this function fetches the current underlying value of all of the `user's shares in
this strategy
```solidity

    function userUnderlyingView(address user) external view virtual returns (uint256) {
        return sharesToUnderlyingView(shares(user));
    }
```

Within the Eigenlayer, you can see that the token withdrawal from  [queueWithdrawal](https://github.com/code-423n4/2023-04-eigenlayer/blob/main/docs/EigenLayer-withdrawal-flow.md#queueing-a-withdrawal) also removes the user's shares in staker-specific storage and the corresponding shares delegated to the operator. Hence there is a need for `tokenStrategyMapping[token].sharesToUnderlyingView(queuedShares[address(token)]` to get shares within the withdrawal queue.

Knowing that shares were accounted for, the implementation accumulates more underlying asset into withdrawal queue in `RestakeManager::calculateTVLs()`:
```solidity
    function calculateTVLs() public view returns (uint256[][] memory, uint256[] memory, uint256) {
                -- SNIP --
                if (!withdrawQueueTokenBalanceRecorded) {
                    totalWithdrawalQueueValue += renzoOracle.lookupTokenValue(
                        collateralTokens[i],
                        collateralTokens[j].balanceOf(withdrawQueue) //@audit redundant since it was already added in getTokenBalanceFromStrategy
                    );
                }
```



## Impact
The additional withdrawal queue balance can inflate the total value locked (TVL) and lead to incorrect calculations.

Manual Review
## Recommended Mitigation Steps
Remove the `withdrawQueueTokenBalanceRecorded` the state variable, the if statement and `totalWithdrawalQueueValue` variable implementations.
