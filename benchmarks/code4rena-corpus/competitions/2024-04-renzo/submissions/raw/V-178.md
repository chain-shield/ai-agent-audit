# Vulnerability details

## Impact
In the `xRenzoDeposit.sol` smart contract, the `depositETH` function is not equipped with any safeguards against replay attacks. Replay attacks involve the malicious duplication of a legitimate transaction, which can lead to unauthorized actions being performed. This vulnerability could potentially enable an attacker to steal funds by re-enacting a transaction that initially failed for the victim.

This `depositETH` function lacks safeguards against replay attacks, and an adversary could exploit this vulnerability by repeating a user's unsuccessful transactions. This malicious activity could result in substantial monetary losses for the victims and jeopardize the security framework of the protocol. The financial impact can be significant, as an attacker can potentially steal large amounts of user funds by exploiting this vulnerability across multiple victims.

## Proof of Concept

The attacker observes Alice, the victim, attempting to deposit ETH into the protocol using the `depositETH()` function.

The attacker intercepts Alice's failed transaction and obtains the transaction data, including the `_minOut` and `_deadline` parameters.

The attacker waits for a brief period, then resubmits the same transaction data to the `depositETH()` function.

Since the protocol does not have any mechanisms to prevent replay attacks, the protocol will execute the transaction again, effectively draining Alice's ETH.

The attacker can repeat this process until Alice's entire ETH balance is drained from the protocol.

The attacker can repeat this process as many time as they want on many victims.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Implement nonce-based or other mechanisms to ensure that each transaction can only be executed once, preventing replay attacks.
