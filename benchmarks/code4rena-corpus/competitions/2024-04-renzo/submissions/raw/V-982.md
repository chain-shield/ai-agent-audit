# Vulnerability details

## Vulnerability Detail
The first depositor can inflate the value of ezETH to steal significant value from the second user

It is not possible to extract all the value from the second depositor because ezETH performs the following check in `calculateMintAmount`

``` solidity
// Sanity check
if (mintAmount == 0) revert InvalidTokenAmount();
```

But it is still possible to extract a significant amount of value from the second user's deposit.

1. The attacker must be the first depositor, they will deposit 1 wei of ETH for 1 ezETH
2. Then when an innocent bob sends a Tx to deposit 40 ETH for ezETH
3. The attacker sees bob's Tx and frontruns it by sending (20 ETH - 1 wei) to the depositQueue, raising the TVL to 20 ETH
4. Now bob's Tx goes through, when calculating how much EzETH he should get in the `calculateMintAmount()` function using the following params _currentValueInProtocol = 20e18, _existingEzETHSupply = 1, _newValueAdded = 40e18
5. Bob is minted 1 ezETH
6. The attacker withdraws their 1 ezETH, the redeemed ETH amount is calculated in the `calculateRedeemAmount` function using the following params _currentValueInProtocol = 60e18, _ezETHBeingBurned = 1, _existingEzETHSupply = 2
7. The attacker redeems 30 ETH, they have made a profit of 10 ETH while bob has a loss of 10 ETH

An attacker could extract even more value if they mathematically optimised how much they raised the TVL by when frontrunning the honest user.

## Impact
The second depositor loses a significant amount of their reposit unfairly to an attacker

## Proof of Concept

``` solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.25;

contract InflationAttackPOC {

    uint256 SCALE_FACTOR= 1e18;

    function calculateMintAmount(
        uint256 _currentValueInProtocol,
        uint256 _newValueAdded,
        uint256 _existingEzETHSupply
    ) external view returns (uint256) {
        // For first mint, just return the new value added.
        // Checking both current value and existing supply to guard against gaming the initial mint
        if (_currentValueInProtocol == 0 || _existingEzETHSupply == 0) {
            return _newValueAdded; // value is priced in base units, so divide by scale factor
        }
        uint256 mintAmount;
        //!@audit find a way to exploit this sussy mathematics. is it equivalent to the more obvious logic? check other protocols.
        {
        // Calculate the percentage of value after the deposit
        uint256 inflationPercentaage = (SCALE_FACTOR * _newValueAdded) /
            (_currentValueInProtocol + _newValueAdded); // inflationPercentage ∝ _newValueAdded

        // Calculate the new supply
        uint256 newEzETHSupply = (_existingEzETHSupply * SCALE_FACTOR) /
            (SCALE_FACTOR - inflationPercentaage);

        // Subtract the old supply from the new supply to get the amount to mint
        mintAmount = newEzETHSupply - _existingEzETHSupply;
        }

        // Sanity check
        if (mintAmount == 0) revert();

        return mintAmount;
    }

    function calculateRedeemAmount(
       
        uint256 _currentValueInProtocol,
        uint256 _ezETHBeingBurned,
        uint256 _existingEzETHSupply

    ) external pure returns (uint256) {
        // This is just returning the percentage of TVL that matches the percentage of ezETH being burned
        uint256 redeemAmount = (_currentValueInProtocol * _ezETHBeingBurned) / _existingEzETHSupply;

        // Sanity check
        if (redeemAmount == 0) revert();

        return redeemAmount;
    }
}
```
