# Vulnerability details

## Impact
`DepositQueue` contract receives reward tokens that are forwarded to it from the EigenLayer, these rewards can be any ERC20 tokens like LSTs, AVS tokens and Middleware service specific Tokens. But when Calculating the TVL of the protocol, when these tokens are in the `DepositQueue` contract before being swept back to the OD, they are not utilized to calculate the TVl, since ezETH is a reward bearing token, the impact of rewards earned by staking determines the value of the token, which means more rewards earned the more the value of the ezETH increases, and anyone looking to redeem their token will get a lesser reedem value for their ezETH

## Proof of Concept
They are three factors to this issue 

- The fact that reward tokens are sent to the `DepositQueue` contract, and they have to be swept manually by an admin as shown below 

```solidity
 function sweepERC20(IERC20 token) external onlyERC20RewardsAdmin {
```

- The fact That when calculating the totalTVL, only native eth tokens are considered and not other ERC20 reward tokens

```solidity
...more code

        // Get the value of native ETH held in the deposit queue and add it to the total TVL
        totalTVL += address(depositQueue).balance;

        // Add native ETH help in withdraw Queue and totalWithdrawalQueueValue to totalTVL
        totalTVL += (address(withdrawQueue).balance + totalWithdrawalQueueValue);
...more code
```
Here the Eth balance of the Contract is considered but not the other reward tokens that are present in the contract leading to a lesser TVL

- When Users reedeem their ezETH, the logic is that the percentage of the ezETH that is about to be redeemed, is the percentage of the TVL, which the user will get back as shown below,

```solidity
 function calculateRedeemAmount(
        uint256 _ezETHBeingBurned,
        uint256 _existingEzETHSupply,
        uint256 _currentValueInProtocol
    ) external pure returns (uint256) {
        // This is just returning the percentage of TVL that matches the percentage of ezETH being burned
        uint256 redeemAmount = (_currentValueInProtocol * _ezETHBeingBurned) / _existingEzETHSupply;

        // Sanity check
        if (redeemAmount == 0) revert InvalidTokenAmount();

        return redeemAmount;
    }
```
This means More TVL gives more value to your ezETH, with Less TVL users will get less value for their tokens

## Recommended Mitigation Steps
When Calculating the TVL, a array of reward tokens should be implemented to loop over the balance of the `DepsoitQueue` in the event that they have not being swept by the admin, which will give an accurate return value
