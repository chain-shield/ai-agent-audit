# Vulnerability details

## Impact
This leads to 

- an overstated TVL since the underlying value of the  `collateralToken` equivalent of the shares *queued for withdrawal* from the `strategyManager` are counted twice for each `collateralToken` per Operator delegator
- the overstated TVL in turn could lead to inflating `collateralToken` value  during token withdrawals and this could be exploited by a malicious user

## Proof of Concept
[`RestakeManger::calculateTVLs(...)`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L302) is called to calculate the TVLs of each  `operatorDelegator` for each individual token (`operatorDelegatorTokenTVLs`), total for each OD (`operatorDelegatorTVLs`), and total for the protocol (`totalTVL`).

However, on `L302:` of the `RestakeManager.sol` makes an internal call is made to [`operatorDelegators[i].getTokenBalanceFromStrategy(collateralTokens[j])`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol#L331-L334) for every collateral token that an `operatorDelegators` deposits into the `strategy`.

as shown on `L329` of the `OperatorDelegator.sol`, the function checks if the `operatorDelegator` has any any shares queued for withdrawal and if it does it tries to *add* the underlying value of the queued share to the value of the actively staked shares in the `strategyManager` (which includes the queued shares as they have not been removed from strategy at this point)

This is wrong because 

- the `queuedShares[address(this)]` are still in the `strategy`  and as such adding the value instead of subtracting means the value will be counted twice counted twice.
- the queued shares are up for withdrawal pending a delay period and as such they should not account for the TVL of the protocol

## POC

- `OD1` has 3000 total shares in `strategy1` equivalent to 3000 underlying asset,
- there are 500 shares queued for withdrawal for `OD1` in the Eigen Layer `strategy1` equivalent to 500 underlying asset,
- [`getTokenBalanceFromStrategy(...)`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol#L331-L334) is intended to  return 3500 shares for `OD1` but will return the same 3000 shares owing to another vulnerability shown in `L333` in `OperatorDelegator.sol` (the developer assumes shares are queued on behalf of the token instead of the `operatorDelegator`)

## Recommended Mitigation Steps
Modify the `OperatorDelegator::getTokenBalanceFromStrategy(...)` function as shown below

