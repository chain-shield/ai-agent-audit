# Vulnerability details

## Impact

In DepositQue.sol there is a no function to sweep excess native rewards unless they are in multiples of 32 Ether. This essentially locks rewards for an undetermined amount of time. The only way that native rewards can be removed from the protocol is through the _checkAndFillETHWithdrawBuffer(...) function which is reliant on the withdrawQue to give an amount to fill the buffer, However even the excess rewards are still left in the protocol and can only be removed if they reach a multiple of 32 ETH. Such a situation gets economically costly, dangerous and highly likely as the cost of Native token continues to rise.

## Proof of Concept

Consider the [receive()](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Deposits/DepositQueue.sol#L163) function which fills the withdrawal queue buffer with the remaining rewards after fee deduction

```
if (feeAddress != address(0x0) && feeBasisPoints > 0) {
            feeAmount = (msg.value * feeBasisPoints) / 10000;
            (bool success, ) = feeAddress.call{ value: feeAmount }("");
            if (!success) revert TransferFailed();

            emit ProtocolFeesPaid(IERC20(address(0x0)), feeAmount, feeAddress);
        }
        // update remaining rewards
        uint256 remainingRewards = msg.value - feeAmount;
        // Check and fill ETH withdraw buffer if required
        _checkAndFillETHWithdrawBuffer(remainingRewards);

```

However not all the remaining rewards are swept to the withdrawal queue

```
function _checkAndFillETHWithdrawBuffer(uint256 _amount) internal {
        // Check the withdraw buffer and fill if below buffer target
        uint256 bufferToFill = withdrawQueue.getBufferDeficit(IS_NATIVE);

        if (bufferToFill > 0) {
            bufferToFill = (_amount <= bufferToFill) ? _amount : bufferToFill;

            // fill withdraw buffer from received ETH
            withdrawQueue.fillEthWithdrawBuffer{ value: bufferToFill }();

            emit BufferFilled(IS_NATIVE, bufferToFill);
        }
```

If either there is no buffer deficit or the remaining rewards are greater than the required bufferToFill then an excess remains in the protocol only extractable through the [stakeEthFromQueue(...)](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Deposits/DepositQueue.sol#L195) function.

As such there are too many unpredictable external factors that can leave any excess less than 32 ETH locked in the protocol for an undetermined amount of time. The extraction of these funds is solely dependent on an unlimited supply of ETHER always running through the contract.

## Recommended Mitigation Steps

I would recommend that a function to either SWEEP all native token be added to the protocol or a function to directly extract native token in the situation that it remains locked.
