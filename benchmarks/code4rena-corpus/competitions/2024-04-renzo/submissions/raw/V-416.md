# Vulnerability details


## Impact
[RestakeManager::deposit](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L491-L576) function is intended to be called by users to deposit LRTs into the protocol, to be minted a computed amount of ezETH.
On deposit, the [WithdrawQueue()::getBufferDeficit](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Withdraw/WithdrawQueue.sol#L170-L176) function is called to get the current buffer deficit. If the returned deficit is non-zero, all or a portion of the user deposited amount could be used up to fill the `WithdrawQueue` contract buffer. 

The buffer here is used to ensure the `WithdrawQueue` contract always has an x amount of the collateral token to handle withdrawal requests. For example, assuming the buffer target for stETH is set to 1,000 stETH and there are currently only 500 stETH available for withdrawal, 500 more stETH will be needed to fill the `WithdrawQueue` stETH buffer. If a user, let's say Alice deposits 200 stETH, all of her deposit amount will be used up to fill the `WithdrawQueue` stETH buffer.
```solidity
        if (bufferToFill > 0) {
            bufferToFill = (_amount <= bufferToFill) ? _amount : bufferToFill;
            // update amount to send to the operator Delegator
            _amount -= bufferToFill;

            // safe Approve for depositQueue
            _collateralToken.safeApprove(address(depositQueue), bufferToFill);

            // fill Withdraw Buffer via depositQueue
            depositQueue.fillERC20withdrawBuffer(address(_collateralToken), bufferToFill);
        }
```
Since the full input amount is used up to fill the buffer, the amount will now be zero. i.e. 200 - 200 ==> 0
```solidity
       _amount -= bufferToFill;
```
The problem here is that the functionality then goes on to try to deposit this zero amount into the [OperatorDelegator](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol#L143-L154) contract.
```solidity
        operatorDelegator.deposit(_collateralToken, _amount);
```
Notice the zero amount revert in [OperatorDelegator::deposit](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol#L143-L154) function below:
```solidity
    function deposit(
        IERC20 token,
        uint256 tokenAmount
    ) external nonReentrant onlyRestakeManager returns (uint256 shares) {
//@audit ------> Reverts on zero token amount
        if (address(tokenStrategyMapping[token]) == address(0x0) || tokenAmount == 0)
            revert InvalidZeroInput();

        // Move the tokens into this contract
        token.safeTransferFrom(msg.sender, address(this), tokenAmount);

        return _deposit(token, tokenAmount);
    }
```
This will hence always result in a revert whenever the token buffer deficit is greater than or equal to the user deposit amount.

## Recommended Mitigation Steps
Wrap the call in an `if` statement, to only deposit if the `_amount` is non-zero, i.e.:
```solidity
        if (_amount > 0) {
            operatorDelegator.deposit(_collateralToken, _amount);
        }
```
