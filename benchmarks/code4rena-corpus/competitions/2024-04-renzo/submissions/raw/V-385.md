# Vulnerability details

## Impact
 The lack of a guarded salt can potentially allow an attacker to front-run the deployment transaction and deploy a contract with the same salt on another chain, leading to address collisions or loss of control over the deployed contract.

## Proof of Concept
The `XERC20Factory` contract utilizes the CREATE3 utility to deploy new contracts deterministically, a process crucial for ensuring consistency and predictability within the blockchain ecosystem. This deployment mechanism involves the generation of salts derived from various input parameters, which are then used to calculate the deployment address of the contract.

However, a critical vulnerability arises from the way salts are constructed within the `_deployXERC20` and `_deployLockbox` functions. In both cases, the salts are formed without adhering to the recommended best practice, which advocates for setting the first 20 bytes of the salt to `msg.sender`. Let's examine the vulnerability in detail:

In `_deployXERC20`, the salt construction is as follows:
```solidity
bytes32 _salt = keccak256(abi.encodePacked(_name, _symbol, msg.sender));
_xerc20 = CREATE3.deploy(_salt, _bytecode, 0);
```
Similarly, in _deployLockbox, the salt construction is as follows:
```solidity
bytes32 _salt = keccak256(abi.encodePacked(_xerc20, _baseToken, msg.sender));
_lockbox = payable(CREATE3.deploy(_salt, _bytecode, 0));
```
While these functions aim to deploy new `XERC20` and `XERC20Lockbox` contracts deterministically, the oversight in salt construction deviates from recommended practices. This deviation can potentially introduce security vulnerabilities into the system.

## Recommended Mitigation Steps
To mitigate this issue, the contract should include the deployer's address in the first 20 bytes of the salt to ensure that only the intended deployer can deploy the contract with that specific salt. This can be done by modifying the salt generation to include the deployer's address.
