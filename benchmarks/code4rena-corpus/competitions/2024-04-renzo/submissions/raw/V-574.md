# Vulnerability details

## Impact
`OptimismMintableXERC20` storage variables will be overridden in case its parent contract `XERC20` is upgraded.

## Vulnerability details
In order to better handle tokens bridging to different L2s, the protocol employs [the XERC20 standard, designed to make the process easier and more reliable](https://hackmd.io/@arjunbhuptani/xerc20-bridge-spec). 

[The `XERC20.sol` contract](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Bridge/xERC20/contracts/XERC20.sol#L16) has been modified to use the upgradeability pattern of OpenZeppelin.

Additionally a separate version has been created to be used on Optimism L2, called `OptimismMintableXERC20`. It inherits `XERC20.sol` and overrides some methods so that it meets the `OptimismMintable` interface required for bridging tokens by Optimism.

It also [defines 2 new variables `l1Token` & `optimismBridge`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Bridge/xERC20/contracts/optimism/OptimismMintableXERC20.sol#L11-L20):

```solidity
contract OptimismMintableXERC20 is ERC165Upgradeable, XERC20, IOptimismMintableERC20 {
    /**
     * @notice The address of the l1 token (remoteToken)
     */
    address public l1Token;

    /**
     * @notice The address of the optimism canonical bridge
     */
    address public optimismBridge;

........

}

````

And this is where the problem lies. Since `XERC20.sol` is already defined as upgradeable, it means it can change in the future and new state variables can be added.

Since `OptimismMintableXERC20` inherits `XERC20.sol` and due to the way inheritance affects storage slots if `XERC20.sol` adds a new variable it will collide with the slot of the first variable of `OptimismMintableXERC20` - `l1Token`. As a result it will overwrite it and brick token minting.


## Proof of Concept

Here is a visual explanation. I'm only including the last variable of `XERC20` since it is the important one:

#### Current storage variable layout

| XERC20   | OptimismMintableXERC20|
| -------- | ------- |
| mapping(address => Bridge) public bridges (`LAST VARIABLE`)|    |
|  | address public l1Token ( `FIRST VARIABLE`)|
|  | address public optimismBridge (`2nd VARIABLE`)|

- You can see that currently `OptimismMintableXERC20` first variable starts right after the last defined variable in `XERC20`

#### Upgraded storage layout

| XERC20   | OptimismMintableXERC20|
| -------- | ------- |
| mapping(address => Bridge) public bridges|    |
| address someNewVariable (`LAST VARIABLE`) | address public l1Token ( `FIRST VARIABLE`)|
|  | address public optimismBridge (`2nd VARIABLE`)|

- In this scenario `XERC20` adds a new address variable which as you can see from the table takes the storage slot previously used by the `l1Token` for `OptimismMintableXERC20`. Respectively `l1Token` now references the next slot for `optimismBridge` which will break the minting.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Consider using a separate storage contract just as you have done for the core Renzo contracts. This will prevent storage collisions and will allow new state variables to be safely added.

Note: Do not forget to put it as the last contract in the inheritance chain.
