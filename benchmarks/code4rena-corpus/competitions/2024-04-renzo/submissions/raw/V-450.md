# Vulnerability details

## Vulnerability Detail
The contest README says:
> ezETH Transfer Restrictions: 

> When the protocol launches, it is intended to not have ezETH be transferrable. A user will deposit and get ezETH minted to their account, but they will not be able to transfer it out of their account until the protocol is ready to allow it. If the withdrawal flow is enabled, they can still withdraw from the protocol (token can be minted and burned by RestakeManager, even if transfers are restricted).

From this, clearly the protocol intends for the following functionality to be available simultaneously:
1. ezETH is non-transferrable
2. ezETH can still be withdrawn via the withdrawal flow

However in order for withdrawal, the user must transfer ezETH to the WithdrawalQueue. This will revert since ezETH will not be transferrable. Hence, withdrawal will be impossible when ezETH is non-transferrable. This goes against the above requirements stated in the README.

## Impact
The intended functionality of the protocol (Withdrawing while ezETH is non-transferrable) will not be possible.

## Proof of Concept
The `WithdrawQueue.withdraw()` function requires transferring of ezETH from the user to the `WithdrawQueue` contract:

https://github.com/code-423n4/2024-04-renzo/blob/1c7cc4e632564349b204b4b5e5f494c9b0bc631d/contracts/Withdraw/WithdrawQueue.sol#L214

## Tools Used
Manual Review

## Recommended Mitigation Steps
Allow transferring of ezETH when `msg.sender` is `WithdrawQueue`. This will allow the protocol's intended functionality to work properly.
