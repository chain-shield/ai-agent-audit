# Vulnerability details

## Impact
There is a possibility of underflow `WithdrawQueue:claim` & `DepositQueue:sweepERC20` functions. 

In calculation of `WithdrawQueue:claim` claim reserve deduction
 ```(claimReserve[_withdrawRequest.collateralToken] -= _withdrawRequest.amountToRedeem)``` 

If the amount to redeem exceeds the claim reserve balance, resulting in an incorrect calculation and potentially negative claim reserve balance. Negative balances could lead to unexpected behavior, disrupting contract operations, and causing financial losses for users.

Exploiting this vulnerability could allow attckers to drain the claim reserve, affecting the availability of funds for legitimate withdrawal requests.

The `DepositQueue:sweepERC20 ` function is designed to sweep any accumulated ERC20 tokens in the contract to the RestakeManager. However, it fails to properly validate the remaining balance after deducting fees, which can result in an underflow if the fee amount exceeds the total balance of the ERC20 token. This underflow issue can lead to unexpected behavior and compromise the integrity of the contract's token management functionality.

## Proof of Concept
See the following code:

```
 function claim(uint256 withdrawRequestIndex) external nonReentrant {
        // check if provided withdrawRequest Index is valid
        if (withdrawRequestIndex >= withdrawRequests[msg.sender].length)
            revert InvalidWithdrawIndex();

        WithdrawRequest memory _withdrawRequest = withdrawRequests[msg.sender][
            withdrawRequestIndex
        ];
        if (block.timestamp - _withdrawRequest.createdAt < coolDownPeriod) revert EarlyClaim();

        // subtract value from claim reserve for claim asset
        claimReserve[_withdrawRequest.collateralToken] -= _withdrawRequest.amountToRedeem;

        // delete the withdraw request
        withdrawRequests[msg.sender][withdrawRequestIndex] = withdrawRequests[msg.sender][
            withdrawRequests[msg.sender].length - 1
        ];
        withdrawRequests[msg.sender].pop();

        // burn ezETH locked for withdraw request
        ezETH.burn(address(this), _withdrawRequest.ezETHLocked);

        // send selected redeem asset to user
        if (_withdrawRequest.collateralToken == IS_NATIVE) {
            payable(msg.sender).transfer(_withdrawRequest.amountToRedeem);
        } else {
            IERC20(_withdrawRequest.collateralToken).transfer(
                msg.sender,
                _withdrawRequest.amountToRedeem
            );
        }
        // emit the event
        emit WithdrawRequestClaimed(_withdrawRequest);
    }
```

```
 function sweepERC20(IERC20 token) external onlyERC20RewardsAdmin {
        uint256 balance = IERC20(token).balanceOf(address(this));
        if (balance > 0) {
            uint256 feeAmount = 0;

            // Sweep fees if configured
            if (feeAddress != address(0x0) && feeBasisPoints > 0) {
                feeAmount = (balance * feeBasisPoints) / 10000;
                IERC20(token).safeTransfer(feeAddress, feeAmount);

                emit ProtocolFeesPaid(token, feeAmount, feeAddress);
            }

            // Approve and deposit the rewards
            token.approve(address(restakeManager), balance - feeAmount);
            restakeManager.depositTokenRewardsFromProtocol(token, balance - feeAmount);

            // Add to the total earned
            totalEarned[address(token)] = totalEarned[address(token)] + balance - feeAmount;

            // Emit the rewards event
            emit RewardsDeposited(IERC20(address(token)), balance - feeAmount);
        }
    }
```

## Recommended Mitigation Steps
First of all user SafeMath Library. 

Then for `WithdrawQueue:claim`, before deducting the redemption amount from the claim reserve, verify that the claim reserve balance for the corresponding collateral token is sufficient to cover the withdrawal. Check if `claimReserve[_withdrawRequest.collateralToken]` is greater than or equal to `_withdrawRequest.amountToRedeem` to prevent underflow.

For `DepositQueue:sweepERC20`, implement robust validation checks to ensure that the fee amount does not exceed the total balance of the ERC20 token before performing the subtraction operation.
