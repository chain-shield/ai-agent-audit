# Vulnerability details

DOS by donation attack
We start by 
attacker deposit 1 wei and receive 1 share by the calculateMintAmount function shortcut in RenzoOracle.sol#L131.
attacker deposit 2 * 10^18 -1 wei and will receive 10^18 -1 shares to a total of 10^18 shares. see calculation1 at the end.
state: assets 2 * 10^18, shares 10^18
attacker withdraw 10^18 -1 shares and receive 2 * 10^18 - 2 wei. see calculation2 at the end.
state: **assets 2, shares 1**

Now after we are in this state we can start the donation attack.

Each time we deposit 2 * TotalAssets-1 so we receive only 1 share and withdraw it, so each time we donate TotalAssets/2. so each time the share is multiplied by 1.5 so the make one share the worth more than 100 ETH it takes log(10^20)/log(1.5) = 114
To do this we need to withdraw each time before we deposit (there could be optimizations here but at worst case we need 114 withdraws)
So if the withdraw cooldown will be up 0 the attacker can do this in a single block. In the current design there is a check that cooldown is not 0 in the withdraw queue.
If the cooldown is 1 sec (which it could be), this attack will take 114 blocks which is 23 minutes to DOS the system because any deposit of less than 100ETH will get 0 shares and it will revert.
The attacker only loss gas but not the ETH (He can always withdraw his share).

To mitigate this it is possible to only take from the user the value of the shares he is getting and not more so there will by no donations. Another option is to have a first deposit/virtual shares so the first deposit cannot inflate the value of a single share.
