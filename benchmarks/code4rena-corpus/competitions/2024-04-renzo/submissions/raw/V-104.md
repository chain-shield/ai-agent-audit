# Vulnerability details

## Impact
In the `_execute` function of the `TimelockController` contract, a low-level `call` is used to send Ether and execute arbitrary code at a target address. However, if the target account does not exist, the `call` will return `true` even though the transaction did not have the intended effect. This can lead to silent failures where the transaction appears to succeed but no action is actually performed.

A similar issue was acknowledged [here](https://solodit.xyz/issues/m-07-low-level-transfer-via-call-can-fail-silently-code4rena-rolla-rolla-contest-git) and it was of medium severity.

## Proof of Concept
```solidity
function _execute(address target, uint256 value, bytes calldata data) internal virtual {
        (bool success, ) = target.call{ value: value }(data);
        require(success, "TimelockController: underlying transaction reverted");
    }
```

Per the Solidity docs:

> The low-level functions call, delegatecall and staticcall return true as their first return value if the account called is non-existent, as part of the design of the EVM. Account existence must be checked prior to calling if needed."

Please find the documentation here: https://docs.soliditylang.org/en/develop/control-structures.html#error-handling-assert-require-revert-and-exceptions


There's another instance of the issue;

Another instance is in the `DepositQueue` contract, specifically in the `receive()` function. Just as described above, the function does not check the return value of the low-level call when transferring the fee amount to the `feeAddress`.

https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Deposits/DepositQueue.sol#L168

```solidity
(bool success, ) = feeAddress.call{ value: feeAmount }("");
if (!success) revert TransferFailed();
```

The `TransferFailed()` error is only thrown if the low-level call itself fails (i.e., it runs out of gas or the call stack depth is exceeded). However, if the `feeAddress` is a contract that doesn't accept plain ETH transfers (i.e., it doesn't have a `receive()` or `fallback()` function), the call will succeed but the ETH transfer will fail silently.

This means that the fee amount will be deducted from the `msg.value`, but it won't actually be transferred to the `feeAddress`. As a result, the fee will be permanently lost, and the `totalEarned` will be incorrectly updated with the remaining rewards.

## Recommended Mitigation Steps
Check for the account's existence prior to transferring.


For the second instance, consider using the `transfer()` function instead of a low-level call to transfer the fee amount.
