# Vulnerability details

## Impact
based on the comments this function is meant to be only called by the bridge

```javascript
 /**
     * @notice Burns tokens for a user
  @--.   * @dev Can only be called by a bridge
     * @param _user The address of the user who needs tokens burned
     * @param _amount The amount of tokens being burned
     */

    function burn(address _user, uint256 _amount) public virtual {
        if (msg.sender != _user) {
            _spendAllowance(_user, msg.sender, _amount);
        }

        _burnWithCaller(msg.sender, _user, _amount);
    }
```

This vulnerability allows an unexpected spender to burn tokens on behalf of a user, potentially leading to unauthorized token transfers and unexpected behavior.
## Proof of Concept
An attacker, instead of the user, calls the burn function with the user's address as _user parameter. If the burn function is not properly protected, the attacker can spend the user's allowance to burn tokens. The attacker's address would be recorded as the msg.sender, but the tokens would be subtracted from the user's balance. to spend the allowance of _user for msg.sender. However, it's unusual for burn to spend someone else's allowance, as burning typically involves the caller's tokens. This design might be unconventional and could potentially lead to unexpected behavior.

## Recommended Mitigation Steps
To mitigate this vulnerability, ensure that only the user or authorized addresses can call the burn function. Consider implementing an access control mechanism to restrict access to the function. Additionally.

Here's a revised version with improved access control:

function burn(address _user, uint256 _amount) public virtual {
    require(msg.sender == _user || isAuthorized(msg.sender), "Unauthorized");
