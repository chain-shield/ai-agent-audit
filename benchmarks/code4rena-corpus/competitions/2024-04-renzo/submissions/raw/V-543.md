# Vulnerability details

## Impact
The function first checks for zero values in `_amount` and `_assetOut`, which is good practice to prevent trivial calls and ensure meaningful input.
However, the function transfers ezETH tokens `(IERC20(address(ezETH)).safeTransferFrom(msg.sender, address(this), _amount))` before performing all necessary checks. This could potentially lock funds in the contract if subsequent checks fail after the transfer.

## Proof of Concept

One of the first steps when withdraw function is called is to transfers ezETH tokens (IERC20(address(ezETH)).safeTransferFrom(msg.sender, address(this), _amount)) before performing all necessary checks.
If any of these steps fails, the user will lose their shares:
1.The check if (withdrawalBufferTarget[_assetOut] == 0) revert UnsupportedWithdrawAsset();
2.redemption calculation (if _assetOut is not native ETH)
3.(if (amountToRedeem > getAvailableToWithdraw(_assetOut)) revert NotEnoughWithdrawBuffer();

The amount calculated to be needed for the withdrawal is then compared to the amount available from getAvailableToWithdraw(_assetOut).
If the available amount is less than the amount needed to redeem, the transaction is reverted using revert NotEnoughWithdrawBuffer();. This prevents the execution of a withdrawal that cannot be fully supported by the available assets.

This means there is the possibility for this revert happening. This possibility will lead to users losing their shares. This is an edge case.

## Recommended Mitigation Steps
Ensure that all checks are done before any state-changing actions are taken, especially those involving the token transfers. Perform check effects interaction for the withdrawal function
