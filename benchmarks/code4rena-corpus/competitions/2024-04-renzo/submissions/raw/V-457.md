# Vulnerability details

## Impact
Incorrect accumulation of unverified staked ETH inside `OperatorDelegator.sol` can lead to inflated values and TVLs.

## Vulnerability details
`OperatorDelegator.sol` is the contract in Renzo protocol responsible for interacting with `EigenLayer`. When staking ETH it uses a storage variable called  `stakedButNotVerifiedEth` that is used to record the amount sent for staking in the validator. 

Staking happens through the `OperatorDelegator::stakeEth()` function, where `stakedButNotVerifiedEth` gets incremented with the staked value (32 ETH):

https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol#L349-L359
```solidity
     /// @dev Stake ETH in the EigenLayer
    /// Only the Restake Manager should call this function
    function stakeEth(
        bytes calldata pubkey,
        bytes calldata signature,
        bytes32 depositDataRoot
    ) external payable onlyRestakeManager {
        // Call the stake function in the EigenPodManager
        eigenPodManager.stake{ value: msg.value }(pubkey, signature, depositDataRoot);

        // Increment the staked but not verified ETH
        stakedButNotVerifiedEth += msg.value;
    }
```

Later the stake must get verified on EigenLayer through the `OperatorDelegator::verifyWithdrawalCredentials()`, where `stakedButNotVerifiedEth` gets reduced back:

https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol#L364
```solidity
function verifyWithdrawalCredentials(
        uint64 oracleTimestamp,
        BeaconChainProofs.StateRootProof calldata stateRootProof,
        uint40[] calldata validatorIndices,
        bytes[] calldata withdrawalCredentialProofs,
        bytes32[][] calldata validatorFields
    ) external onlyNativeEthRestakeAdmin {
        ....

        // Decrement the staked but not verified ETH
        for (uint256 i = 0; i < validatorFields.length; ) {
            uint64 validatorCurrentBalanceGwei = BeaconChainProofs.getEffectiveBalanceGwei(
                validatorFields[i]
            );
            
            stakedButNotVerifiedEth -= (validatorCurrentBalanceGwei * GWEI_TO_WEI);
            unchecked {
                ++i;
            }
        }
        // update the gas spent for RestakeAdmin
        _recordGas(gasBefore);
    }
```

The problem here is that the amount to reduce is calculated using the effective balances of the validator, [which as the description in EigenLayer says can overestimate it up to `0.25 ETH`](https://github.com/Layr-Labs/eigenlayer-contracts/blob/dbfa12128a41341b936f3e8da5d6da58c6233877/src/contracts/pods/EigenPod.sol#L467-L472):

> Note that this is the "effective" balance of the validator rather than the current balance.  Effective balance is generated via a hystersis function such that an effective balance, always a multiple of 1 ETH, will only lower to the next multiple of 1 ETH if the current balance is less than 0.25 ETH below their current effective balance.  For example, if the effective balance is 31ETH, it only falls to 30ETH when the true balance falls below 30.75ETH.  Thus in the worst case, the effective balance is overestimating the actual validator balance by 0.25 ETH. 

It is also quite well explained [here](https://eth2book.info/capella/part2/incentives/balances/#hysteresis).
 
This means that in case the 32 ETH that was staked in the validator drops with more than 0.25 ETH before `verifyWithdrawalCredentials` is called `getEffectiveBalanceGwei()` would report 31 ETH.

The result is that the `stakedButNotVerifiedEth` that was incremented with 32 in stakeEth() will be reduced by 31 -> leaving 1 ETH left over, which stays permanently.

Since the value is used in the function for calculating the ETHbalance for the TVLs it will inflate the balances with `1 ETH`:

https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Delegation/OperatorDelegator.sol#L338-L345
```solidity
function getStakedETHBalance() external view returns (uint256) {
        // accounts for current podOwner shares + stakedButNotVerified ETH + queued withdraw shares
        int256 podOwnerShares = eigenPodManager.podOwnerShares(address(this));
        return
            podOwnerShares < 0
                ? queuedShares[IS_NATIVE] + stakedButNotVerifiedEth - uint256(-podOwnerShares)
                : queuedShares[IS_NATIVE] + stakedButNotVerifiedEth + uint256(podOwnerShares);
    }

```

## Recommended Mitigation Steps

Consider always reducing the `stakedButNotVerifiedEth` variable by 32 ETH. Since this is the required amount to stake to validators in order to prevent the difference in balance to accumulate and get reported as TVL
