# Vulnerability details

## Title
Token TVL is miss-calculated and inflated and count multiple times in RestakeManager.

## Line of code
https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L274

## Impact
The function `RestakeManager::calculateTVLs`in RestakeManager  is used to calculate the TVLs for each operator delegator by individual token, total for each OD, and total for the protocol. At the line [283](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L283), 

we can see `bool withdrawQueueTokenBalanceRecorded = false;` is set as false in the outer loop, not inner loop

When this flag is false, we are adding the token balance of the withdrawal queue to total TVL. Now if we look inside the nested loop, the `withdrawQueueTokenBalanceRecorded` is set true. 
```solidity
@>      if (!withdrawQueueTokenBalanceRecorded) {
                    totalWithdrawalQueueValue += renzoOracle.lookupTokenValue(
                        collateralTokens[i],
                        collateralTokens[j].balanceOf(withdrawQueue)
                    );
                }
```
The problem is that the `withdrawQueueTokenBalanceRecorded` is meant to set to false in internal loop and the code should track if each token's balance is already counted as TVL. If not, the TVL for ERC20 token can be counted more than one times.

## Proof of Concept

Lets look at the [RestakeManager::calculateTVLs](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/RestakeManager.sol#L274) and how it works.

```solidity

        ...

        bool withdrawQueueTokenBalanceRecorded = false;
        address withdrawQueue = address(depositQueue.withdrawQueue());

                    collateralTokens[j]

                    collateralTokens[j],

@>              if (!withdrawQueueTokenBalanceRecorded) {

        totalTVL += (address(withdrawQueue).balance + totalWithdrawalQueueValue);

```

The first for loop here `for (uint256 i = 0; i < odLength; ){}` go through all operator delegator, then for each delegator it counts the collateral balance.

Now, lets consider one of the collateral token is WBETH (wrapped binance ETH) and there are two operator delegators, The balance of the WBETH will be counted twiced due to `withdrawQueueTokenBalanceRecorded` set as true in the second loop and added twice to TVL, which is incorrect. The TVL will be heavily inflated and impacting mint/redeem amount ultimately.

When computing redeem amount, we are calling [calculateRedeemAmount](https://github.com/code-423n4/2024-04-renzo/blob/519e518f2d8dec9acf6482b84a181e403070d22d/contracts/Oracle/RenzoOracle.sol#L152)

```solidity
 function calculateRedeemAmount(
        uint256 _ezETHBeingBurned,
        uint256 _existingEzETHSupply,
        uint256 _currentValueInProtocol
    ) external pure returns (uint256) {
        // This is just returning the percentage of TVL that matches the percentage of ezETH being burned
        uint256 redeemAmount = (_currentValueInProtocol * _ezETHBeingBurned) / _existingEzETHSupply;

        // Sanity check
        if (redeemAmount == 0) revert InvalidTokenAmount();

        return redeemAmount;
    }
```

the math is:

```
 uint256 redeemAmount = (_currentValueInProtocol * _ezETHBeingBurned) / _existingEzETHSupply;
```

consider the _ezETH burned is 1 ETH, existing total supply is 10000 ETH,

assume the _currentValueInProtocol contains 8000 ETH and 2000 WBETH,

and ETH and WBETH equals price = 3000 USD

the true redeem amonut should be 

(8000 ETH + 2000 WBETH) * 3000 * 1 ETH redeem amount / (10000 ETH total supply)

but if we count the WBETH TVL more than one times,

the redeem amonut is incorrectly inflated.

the python script simulation shows the difference

```python
ETH = 10 ** 18

ETH_amount = 8000 * ETH

WBETH_amount = 2000 * ETH

price = 3000

ezETHBurned = 1 * ETH

total_supply = 10000 * ETH

def get_redeem_amount(ezETHBurned, total_supply, WBETH_amount, ETH_amount, price):
    return (ETH_amount + WBETH_amount * price) * ezETHBurned / total_supply

# true redeem amount
redeem_amount = get_redeem_amount(ezETHBurned, total_supply, WBETH_amount, ETH_amount, price)
print("true redeem amount", redeem_amount)

# inflated redeem amount

redeem_amount = get_redeem_amount(ezETHBurned, total_supply, WBETH_amount * 2, ETH_amount, price)
print("inflated redeem amount", redeem_amount)
```

the running output is:

```solidity
true redeem amount 6.008e+20
inflated redeem amount 1.2008e+21
```

but inflating and count the WBETH amount twices, the redeem amount is inflated a lot.

Manual Review

## Recommended Mitigation Steps


Do not count the TVL of token multiple times and track the token in withdrawal queue to make sure each token's TVL is only counted once.
