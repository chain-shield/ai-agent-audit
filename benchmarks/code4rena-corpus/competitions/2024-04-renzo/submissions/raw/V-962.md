# Vulnerability details

## Summary

In the stakeManager:deposit process, users deposit LSTs into the protocol, which first attempts to fill the withdrawal buffer. However, if the deposited amount is smaller or equal to the buffer requirement, the entire amount is absorbed, leaving nothing to be forwarded to the operatorDelegator. This is problematic because the operatorDelegator's deposit function reverts if the deposit amount is zero, effectively blocking non large deposits from processing.

## Vulnerability Detail

the function `stakeManager:deposit` is used to deposit an lst to operatorDelegators , first the users deposited amount is used to fill the withdraw buffer: 
```solidity=543
uint256 bufferToFill = depositQueue.withdrawQueue().getBufferDeficit(
            address(_collateralToken)
        );
        if (bufferToFill > 0) {
=>            bufferToFill = (_amount <= bufferToFill) ? _amount : bufferToFill;
            // update amount to send to the operator Delegator
            _amount -= bufferToFill;

            // safe Approve for depositQueue
            _collateralToken.safeApprove(address(depositQueue), bufferToFill);

            // fill Withdraw Buffer via depositQueue
            depositQueue.fillERC20withdrawBuffer(address(_collateralToken), bufferToFill);
        }
```

and as we can see if the user deposits an amount smaller or equal to the withdraw buffer , all of it will go to the withdrawal queue. and `_amount = 0`.

next the user's funds get depsited into a operator delegator :
```solidity=562
operatorDelegator.deposit(_collateralToken, _amount);
```

here is the code for this deposit call:
```solidity=143
function deposit(
        IERC20 token,
        uint256 tokenAmount
    ) external nonReentrant onlyRestakeManager returns (uint256 shares) {
=>        if (address(tokenStrategyMapping[token]) == address(0x0) || tokenAmount == 0)
            revert InvalidZeroInput();
```

as we can see it reverts for zero amounts

This design flaw restricts users with non large amounts of LST from participating in the protocol until larger deposits reduce the withdrawal buffer, potentially creating a high barrier to entry

## Impact

This issue significantly limits accessibility for users with smaller funds, as they cannot deposit unless they exceed the withdrawal buffer amount, which might be relatively high. This can deter smaller investors from using the platform, reducing the protocol's overall inclusivity and liquidity.

## Tool used

Manual Review

## Recommendation

skip depositing into a delegator if the user's amount becomes 0 after filling the withdraw buffer.
