# Vulnerability details

## Impact
`RenzoOracleL2` & `RenzoOracle` use the same heartbeat for all price feeds when checking if the data feed is fresh and also not verifying prices enough for staleness. 

The issue with this is that the `STETH/USD` oracle has a 3600s heartbeat, `STETH/ETH` oracle has 86400s heartbeat, `ETH/USD` has 3600s and vice versa. In short all feeds have different heartbeats which means that for each price feed, the `MAX_TIME_WINDOW` should be different. 

Consequently, even after verifying the freshness of a value, it could still be stale according to the specific oracle's update schedule, potentially leading to inaccurate price data.

Attackers could exploit the discrepancy in staleness assessments to manipulate the contract's behavior. By strategically timing transactions or oracle queries, attackers may exploit perceived data freshness to their advantage.

Either protocol or user will face loss of funds if oracle is considered fresh and price is accpeted at one price level while the real one is either dropped or pumped too much.

Even if we consider that all price feeds have the same heartbeat, still in `86400 + 60`, this 60 can also cause staleness. 

It also checking the price in `xRenzoDeposit:_deposit` function i.e 
```  
 if (block.timestamp > _lastPriceTimestamp + 1 days) {
            revert OraclePriceExpired();
  }
``` 

## Proof of Concept
Lets see the following scenario:

- The RenzoOracle contract is deployed and initialized with default parameters, including a fixed time window for staleness checks set to 86460 seconds (24 hours + 60 seconds).
- Chainlink oracles are configured with varying update intervals: Oracle A updates every 3600 seconds (1 hour), while Oracle B updates every 86400 seconds.
- User Alice queries the RenzoOracle contract for the latest price of a token using Oracle A.
- The contract retrieves the latest price data from Oracle A and timestamps the query.
- As per the contract's staleness check mechanism, the retrieved price data from Oracle A is considered fresh if its timestamp is within the fixed time window of 86460 seconds.
- However, since Oracle A updates every 3600 seconds, its data may become stale before the contract's fixed time window elapses.

## Recommended Mitigation Steps
User custom `MAX_TIME_WINDOW` for each price feed as this most of the price feeds have different heartbeats. 

The latestRoundData function also returns `roundId` and `answeredInRound`. You can check answeredInRound against the current roundId. If answeredInRound is less than roundId, the answer is being carried over. If answeredInRound is equal to roundId, then the answer is fresh.

Add the following extra lines for verification too:

```
 (roundID, int256 price, , timestamp, answeredInRound) = USDT.latestRoundData();
    require(price > 0, "ChainLink: Invalid Price");
    require(answeredInRound >= roundID, "ChainLink: Stale USDT price");
```
