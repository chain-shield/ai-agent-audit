# Vulnerability details

BRIDGE_ADMIN is not a trusted role according to the contest page. They are given access to recover ERC20 that are `accidentally` sent to the [xRenzoBridge](https://github.com/code-423n4/2024-04-renzo/blob/main/contracts/Bridge/L1/xRenzoBridge.sol#L299-L307)

```solidity
/*
* @notice  Sweeps accidental ERC20 value sent to the contract
* @dev     Restricted to be called by the bridge admin only.
* @param   _token  address of the ERC20 token
* @param   _amount  amount of ERC20 token
* @param   _to  destination address
*/
function recoverERC20(address _token, uint256 _amount, address _to) external onlyBridgeAdmin {
    IERC20(_token).safeTransfer(_to, _amount);
}
```

If `xReceive` fails, the bridge WETH would be sent to the contract address. This is from [connext docs](https://docs.connext.network/developers/guides/handling-failures#reverts-on-receiver-contract).

> If the call on the receiver contract (also referred to as "target" contract) reverts, funds sent in with the call will end up on the receiver contract. To avoid situations where user funds get stuck on the receivers, developers should build any contract implementing IXReceive defensively.

It is possible for xReceive to revert such as `MaxTVLReached` on `restakeManager.depositETH`. This means that WETH could be on xRenzoBridge. This WETH is meant to be deposited into the protocol and not swept by an untrusted role. An untrusted role should not have access to the funds that belong to the protocol.


## Impact
An untrusted role has access to the protocol funds.

## Proof of Concept
* 5000 WETH is sent from L2
* `xReceive` fails on L1 because of `MaxTVLReached`
* The 5000 WETH is sent to xRenzoBridge nonetheless
* untrusted BRIDGE_ADMIN sweeps the 5000 WETH that belongs to the protocol

## Tools Used
Manual Review

## Recommended Mitigation Steps
Give BRIDGE_ADMIN access to only trusted individual. Or exclude WETH from being recovered and create another mechanism to rescue WETH that are transferred when xReceive fails.
