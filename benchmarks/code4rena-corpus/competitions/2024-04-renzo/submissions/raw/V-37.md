# Vulnerability details

## Impact
The Renzo protocol heavily depends on Chainlink oracle price feeds for a wide range of critical operations. These operations include, but are not limited to, the minting and burning of ezETH tokens, calculations of total value locked (TVL), and the distribution of rewards. Manipulation or inaccuracies in these price feeds can have severe consequences.

Oracle manipulation involves exploiting vulnerabilities in a blockchain oracle system, leading it to report incorrect or outdated information about off-chain events. This form of manipulation is often a component of broader strategic attacks against financial protocols. By influencing oracles, malicious actors can cause a protocol’s smart contracts to execute based on erroneous data, thus benefiting from manipulated outcomes to the detriment of legitimate users.

If oracle prices are deliberately manipulated to deviate from true market values - whether inflated or deflated - it could lead to the issuance or destruction of ezETH tokens in amounts that do not align with the underlying assets' real value. Beyond affecting token balances, such discrepancies can distort the accuracy of TVL calculations and reward distributions, creating potentially exploitative arbitrage opportunities. These opportunities can lead to the draining of funds from the protocol and may result in significant financial losses for its users. Moreover, persistent inaccuracies due to compromised oracle data can erode trust in the protocol’s reliability and security, potentially destabilizing the entire ecosystem over time.

## Proof of Concept
Multiple critical contracts with key functions rely heavily on a single oracle without aggregation or additional checks beyond basic staleness and positive price validation. Taking this into account, any manipulation or corruption of the oracle data can lead to widespread inaccuracies across all main operational aspects of Renzo. This includes, but is not limited to, token minting, total value locked (TVL) calculations, and reward distributions. Such vulnerabilities could compromise the integrity and financial stability of the entire protocol.

Oracle manipulation attacks leverage weaknesses in one or more components of an oracle’s architecture. The goal of an oracle manipulation attack is usually to force the oracle into misreporting information and trigger invalid execution in a smart contract that uses data from the compromised oracle. 

**Data Sources**
Since the data source determines the quality of information reported by an oracle, attackers often target it as part of oracle manipulation attacks. Spot price manipulation is a classic example of this kind of attack. 

Here is an example:

1. An overcollateralised lending protocol uses the spot price of an asset - taken from a decentralised exchange like Uniswap - to calculate the value of a user’s collateral. This helps determine how much the user can borrow or when the debt position is nearing an undercollateralised status. 

2. Using flash loans, an attacker can create artificial demand for a token and inflate its price on a specific market. This in turn leads the DEX - acting as a price oracle - to report abnormally high prices for the asset, which causes the lending protocol to incorrectly value user-provided collateral and issue “bad loans”. 

While manipulating spot prices on a DEX is more common, this attack could occur in many other places such as centralised exchanges (CEX). Other sources of data can also be corrupted to achieve similar purposes - for example, hacking an API service that provides asset price information and changing reported values.

## Recommended Mitigation Steps
###### Use Fallback Mechanisms
A popular strategy among DeFI projects is to use a dual oracle system that combines an off-chain oracle (eg. Chainlink Price Feeds or UMA’s optimistic oracle) and an on-chain oracle (eg. Uniswap V3 TWAP oracles). This provides a degree of security and fault tolerance since the system can switch to another oracle if using the default option is infeasible (e.g. if the oracle’s data becomes corrupted).

###### Use Decentralised Oracles
While using a centralised oracle is nice for efficiency, the downsides (mostly) outweigh the benefits. A decentralised oracle service that utilises multiple reporters isn’t entirely secure against manipulation, but the costs are usually high enough to deter such attacks. Ideally, you want an oracle with sound cryptoeconomic incentives (like staking on the accuracy of data or assigning reputation scores).

###### Monitor Oracle Performance
It is not advisable to assume that the data provided by a particular oracle is valid - the incoming data must be at intervals instead of blindly trusting oracles to function correctly. This could mean, for instance, creating a script that compares the prices provided by an oracle to values from another source (at every few blocks) and checking for large deviations.
