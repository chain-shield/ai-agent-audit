# Vulnerability details

## Vulnerability Detail
When `EigenPod.verifyAndProcessWithdrawals` is called, the funds are sent to the `DelayedWithdrawalRouter` and attributed to the `OperatorDelegator`. This can be seen in the below two code snippets:


``` solidity
function verifyAndProcessWithdrawals(
    ...
    ...
    _sendETH_AsDelayedWithdrawal(podOwner, withdrawalSummary.amountToSendGwei * GWEI_TO_WEI);
    ...
```


``` solidity
function _sendETH_AsDelayedWithdrawal(address recipient, uint256 amountWei) internal {
        delayedWithdrawalRouter.createDelayedWithdrawal{value: amountWei}(podOwner, recipient);
    }
```
When calling `_sendETH_AsDelayedWithdrawal()`, the `recipient` is set to `podOwner` which is the `OperatorDelegator` contract.


Now to redeem the funds (to the recipient), any user can call the following permissionless function in EigenLayer `DelayedWithdrawalRouter::claimDelayedWithdrawals`

<Details>
<summary>claimDelayedWithdrawals</summary>

``` solidity
/**
     * @notice Called in order to withdraw delayed withdrawals made to the `recipient` that have passed the `withdrawalDelayBlocks` period.
     * @param recipient The address to claim delayedWithdrawals for.
     * @param maxNumberOfDelayedWithdrawalsToClaim Used to limit the maximum number of delayedWithdrawals to loop through claiming.
     * @dev
     *      WARNING: Note that the caller of this function cannot control where the funds are sent, but they can control when the
     *              funds are sent once the withdrawal becomes claimable.
     */
    function claimDelayedWithdrawals(
        address recipient,
        uint256 maxNumberOfDelayedWithdrawalsToClaim
    ) external nonReentrant onlyWhenNotPaused(PAUSED_DELAYED_WITHDRAWAL_CLAIMS) {
        _claimDelayedWithdrawals(recipient, maxNumberOfDelayedWithdrawalsToClaim);
    }
```

</Details>


This will end up sending ETH to the set `recipient` through the internal function `_claimDelayedWithdrawals`

<Details>
<summary>_claimDelayedWithdrawals</summary>

``` solidity
function _claimDelayedWithdrawals(address recipient, uint256 maxNumberOfDelayedWithdrawalsToClaim) internal {
        ...
        ...
        // actually send the ETH
        if (amountToSend != 0) {
            AddressUpgradeable.sendValue(payable(recipient), amountToSend);
        }
        emit DelayedWithdrawalsClaimed(recipient, amountToSend, delayedWithdrawalsCompletedBefore + i);
    }      
```
    
</Details>


Since the recipient was set as the `OperatorDelegator`, it will trigger the `OperatorDelegator::receive()` function that ends up sending the ETH to the DepositQueue, which will increase the TVL of the protocol.

Therefore whenever the `DelayedWithdrawalRouter.createDelayedWithdrawal()` function is called  with the `OperatorDelegator` as the recipient, an attacker can take advantage of this with a sandwich attack. It includes the following steps:

1. Attacker mints ezETH at the current TVL level
2. Attacker calls `DelayedWithdrawalRouter.claimDelayedWithdrawals()` which will end up increasing the TVL of the protocol
3. Attacker backruns the call to `claimDelayedWithdrawals` by redeeming all their minted ezETH at the higher exchange rate (since TVL increased), obtaining ether (or LSTs) at a confirmed profit

## Impact
A portion of the ETH rewards can be stolen from honest users with 0 risk. The attacker makes profit while reducing the yield of honest stakers.

This significantly reduces the incentive for honest users to stake their funds for continuous periods since any non-participant can simply front-run the forwarding of rewards from `RewardHandler` to `DepositQueue` and steal rewards.
