# Vulnerability details

## Impact
The `RestakeManager::deposit` function does not have any mechanisms in place to prevent malicious dust transactions that could cause legitimate transactions to revert. There are no explicit checks or limits on transaction sizes or amounts, which could lead to potential disruption of normal user transactions.

Malicious actors could submit dust transactions to the `RestakeManager` contract, with negligible amounts, to cause legitimate transactions to fail. Attackers could do this to every transaction. This will disrupt the normal operation of the protocol and negatively impact users. 


## Proof of Concept
A very common scenario:

Alice is a legitimate user of the protocol, who wants to deposit a large amount of tokens into the protocol to earn rewards. Bob, on the other hand, is a malicious actor who wants to disrupt Alice's transactions by leveraging the lack of dust transaction prevention in the protocol.

Step 1: Observe Alice's Pending Transactions
Bob closely monitors the mempool for any pending transactions submitted by Alice to the `RestakeManager` contract. He identifies Alice's large deposit transaction that is waiting to be included in a block.

Step 2: Front-run Alice's Transaction with Dust Transactions
Knowing that the `RestakeManager` contract does not have any mechanisms to prevent dust transactions, Bob quickly submits multiple small, malicious transactions to the contract, depositing negligible amounts of the same token that Alice is trying to deposit.

Step 3: Cause Alice's Legitimate Transaction to Revert
When Alice's large deposit transaction is processed, the `RestakeManager` contract will first execute Bob's dust transactions. Since the contract does not have any checks or limits on transaction sizes, these dust transactions will be accepted and processed.

However, the execution of the dust transactions can potentially cause the contract's internal state to become inconsistent or exceed certain limits (e.g., the maximum number of OperatorDelegators or collateral tokens). As a result, when Alice's legitimate, large deposit transaction is executed, it will revert due to the protocol's inability to handle the state changes caused by the malicious dust transactions.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Implement checks to prevent transactions with non-material amounts from affecting the contract's state or execution flow.
