# Vulnerability details

## Impact
The predictability of the _salt used in the _deployLockbox function could potentially expose the XERC20Factory contract to front-running attacks. In this attack, a malicious actor could anticipate the outcome of the function call, pre-compute the address of the lockbox, and interact with it before the legitimate transaction is confirmed. This could lead to unauthorized access or manipulation of the deployed lockbox contract, compromising the integrity and security of the ptotocol.
## Proof of Concept
```solidity
function _deployLockbox(
        address _xerc20,
        address _baseToken,
        bool _isNative,
        address _proxyAdmin
    ) internal returns (address payable _lockbox) {
>>>        bytes32 _salt = keccak256(abi.encodePacked(_xerc20, _baseToken, msg.sender));

        // Initialize function - sent as 3rd argument to the proxy constructor
        bytes memory initializeBytecode = abi.encodeCall(
            XERC20Lockbox.initialize,
            (_xerc20, _baseToken, _isNative)
        );

        bytes memory _creation = type(TransparentUpgradeableProxy).creationCode;

        // Constructor in Proxy takes (logic, admin, data)
        bytes memory _bytecode = abi.encodePacked(
            _creation,
            abi.encode(lockboxImplementation, _proxyAdmin, initializeBytecode)
        );

>>>        _lockbox = payable(CREATE3.deploy(_salt, _bytecode, 0));

        XERC20(_xerc20).setLockbox(address(_lockbox));
        EnumerableSetUpgradeable.add(_lockboxRegistryArray, _lockbox);
        _lockboxRegistry[_xerc20] = _lockbox;
    }
```
As noted in the pointers in the code above, the _salt used in the CREATE3.deploy function is derived from the _xerc20, _baseToken, and msg.sender variables. Given that these variables are likely known or predictable, an attacker could compute the _salt off-chain and anticipate the address of the lockbox. They could then send a transaction with a higher gas price to “front-run” the legitimate transaction, allowing them to interact with the lockbox before the original caller.

## Recommended Mitigation Steps
Instead of using predictable variables to compute the _salt, Protocol should consider using a source of randomness that cannot be predicted by an external observer. This could be achieved by incorporating block variables (like block.timestamp or blockhash) or using a commit-reveal scheme.
