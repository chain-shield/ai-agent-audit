# Vulnerability details

## Impact
Several implementation contracts have initialization functions that can be front-run,allowing an attacker to incorrectly initialize the contracts.Due to the use of the delegatecall proxy pattern, many of the contracts cannot be
initialized with a constructor, and have initializer functions:

```

 /// @dev Initializes the contract with initial vars
    function initialize(
        IRoleManager _roleManager,
        IEzEthToken _ezETH,
        IRenzoOracle _renzoOracle,
        IStrategyManager _strategyManager,
        IDelegationManager _delegationManager,
        IDepositQueue _depositQueue
    ) public initializer {
        __ReentrancyGuard_init();

        roleManager = _roleManager;
        ezETH = _ezETH;
        renzoOracle = _renzoOracle;
        strategyManager = _strategyManager;
        delegationManager = _delegationManager;
        depositQueue = _depositQueue;
        paused = false;
    }
```

An attacker could front-run these functions and initialize the contracts with malicious values.

This issue is also present in several other functions in the Renzo codebase:
- xRenzoBridge - initialize
- RenzoOracleL2 - initialize
- xRenzoDeposit - initialize
- XERC20 - initialize
- XERC20Factory - initialize
- And 10+ other files too

## Proof of Concept
Lets take `RestakeManager` scenario in place. Bob deploys the `RestakeManager` contract. Eve front-runs the contract initialization and sets her own address for these important role addresss. As a result, she will be able to control all functions related to the RestakeManager.

## Tools Used
Manual Review
## Recommended Mitigation Steps
Short term, either use a factory pattern that will prevent front-running of the initialization, or ensure that the deployment scripts have robust protections against front-running attacks.

Long term, carefully review the Solidity documentation, especially the “Warnings” section, as well as the pitfalls of using the delegatecall proxy pattern.
