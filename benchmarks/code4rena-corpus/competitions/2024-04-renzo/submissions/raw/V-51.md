# Vulnerability details

## Impact

25% of the first deposit into Renzo can be stolen through a frontrunning attack.

## Proof of Concept

In Renzo's [`calculateMintAmount` function, this line](https://github.com/Renzo-Protocol/contracts-public/blob/0530cbd20590677da5fa6fd32a0a8b250a9eb028/contracts/Oracle/RenzoOracle.sol#L114-L116) is meant to defend against the first deposit attack by ensuring the `ezEth` minted is equal to assets deposited when the vault or supply is empty. This formula is also copied to Ion's codebase. However, an alteration can be made to the first deposit attack to bypass this check, where `_currentValueInProtocol > 0` and ` _existingEzETHSupply == 0`.

The first deposit attack can be executed using this sequence:

Let's say a user deposits `D` assets for the initial deposit

1.Attacker deposits 1 asset to get 1 `ezEth`
2. Attacker donate/transfers `D / 2 + 1` assets into the contract
3. Victim deposits D assets. In return they get `1.99999` shares which rounds down to `1` share. Note that the totalSupply of `ezEth` is `1` so the ` _existingEzETHSupply == 0` condition passes. `_currentValueInProtocol == D/2 + 1`
4. Due to the large rounding error the attacker ends up making 25% of the first deposit as profit. 

There is a description of a similar attack at the bottom of [this page/ReadMe](https://github.com/ZeframLou/bunni) with the subtitle "Frontrunning the first deposit may steal 1/4 of the deposit". 

## Tools Used

Manual Review

## Recommended Mitigation Steps

Use either an initial minting of shares similar to Uniswap v2 or use OpenZeppelin's ERC4626 vault inflation mitigation with virtual shares and decimal offset.
