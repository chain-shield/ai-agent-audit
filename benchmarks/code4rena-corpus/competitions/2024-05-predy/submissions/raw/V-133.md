Now going to the implementation of `SlippageLib` we can see that `MAX_ACCEPTABLE_SQRT_PRICE_RANGE` is `1.5%`, i.e https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/SlippageLib.sol#L12-L14

```solidity
    uint256 public constant MAX_ACCEPTABLE_SQRT_PRICE_RANGE = 100747209;

```

And whenever the `SlippageLib.checkPrice()` is queried it checks to see that in whatever case since the `MAX_ACCEPTABLE_SQRT_PRICE_RANGE` in our case `!=0` that the amount of slippage carried on the trade is not more than this value, i.e https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/SlippageLib.sol#L20-L55

```solidity

    function checkPrice(
        uint256 sqrtBasePrice,
        IPredyPool.TradeResult memory tradeResult,
        uint256 slippageTolerance,
        uint256 maxAcceptableSqrtPriceRange
    ) internal pure {
        uint256 basePrice = Math.calSqrtPriceToPrice(sqrtBasePrice);

        if (tradeResult.averagePrice == 0) {
            revert InvalidAveragePrice();
        }

        if (tradeResult.averagePrice > 0) {
            // short
            if (basePrice.lower(slippageTolerance) > uint256(tradeResult.averagePrice)) {
                revert SlippageTooLarge();
            }
        } else if (tradeResult.averagePrice < 0) {
            // long
            if (basePrice.upper(slippageTolerance) < uint256(-tradeResult.averagePrice)) {
                revert SlippageTooLarge();
            }
        }

        if (
            maxAcceptableSqrtPriceRange > 0
                && (
                    tradeResult.sqrtPrice < sqrtBasePrice * 1e8 / maxAcceptableSqrtPriceRange
                        || sqrtBasePrice * maxAcceptableSqrtPriceRange / 1e8 < tradeResult.sqrtPrice
                )
        ) {
            revert OutOfAcceptablePriceRange();
        }
    }
}
```

Issue however is that this integration is wrong, due to the logic of hardcoding `MAX_ACCEPTABLE_SQRT_PRICE_RANGE`, this is because:

- All assets to be traded don't have the same market movement/volatility.
  - That's to say for trades in quite fresh/new assets that heavily move the market, there'd be a heavy DOS to trading, cause if the movement is more than `1.5%` the trade fails.
- If we leave market movement/volatility aside and consider monetary value, a simple logic is that a user placing a trade for a pricy asset like WBTC might not want to accept up to `1.5%` slippage on their trade, but would willingly accept that on an asset that's not as pricy as WBTC.

## Impact

As hinted under the last section of _Proof of Concept_, The issue highlighted in the report concerns the Gamma Market's trading mechanism, specifically its handling of slippage across various assets. The core problem is that the protocol applies a **fixed** 1.5% max slippage tolerance to **all trades**, regardless of the asset's market volatility or the user's preference. This approach is flawed for several reasons:

- For newly introduced or highly volatile assets, the fixed 1.5% slippage tolerance can lead to a denial of service (DoS) situation. If the market movement exceeds 1.5%, trades fail, preventing users from participating in the market. This outcome is particularly problematic for new assets where high volatility is expected and desired among traders.

- Users may be willing to accept higher slippage rates for cheaper assets but not for more valuable ones like WBTC. The current system does not account for this nuance, treating all assets uniformly and potentially discouraging participation in markets for more expensive assets due to the perceived risk associated with the fixed slippage rate.

> Subtly, though for assets with minimal market movement, such as those that rarely experience significant price changes, the fixed 1.5% slippage tolerance exposes users to unnecessary risk. A malicious actor could exploit this by causing a larger than expected price movement, potentially skimming off up to 1.3% of the trade value without affecting the trade's success. This scenario is unfair to users who expect a lower slippage rate, typically around 0.2%, for these less volatile assets... _(though in this case we expect users ton take the necessary protection by providing their own valid slippage)_.

## Recommended Mitigation Steps

Generally, hardcoding in contexts like explained in this report is not advised, cause protocol is not planning on integrating with only one type of asset/token, which makes the hardcoded nature of the `MAX_ACCEPTABLE_SQRT_PRICE_RANGE` currently mean that integration with some of these to-be supported asset/token unsafe, this is also quite a common safe logic within DEFI protocol as similar cases are considered inherent issue with lending DeFi protocols, say for example _...a lending protocol could face continuous failures of long durations in the case they integrate liquidation bots that have the same strict confidence intervals and TWAP restrictions for all integrated assets, so the way these protocols would go about to solve this would be to then adopt different ranges of tolerances for different behaviors to ensure everything moves smoother..._ not exactly the same case with what this report is about, but I assume it's a good example to give.

> TLDR, A fix would be to consider making the `MAX_ACCEPTABLE_SQRT_PRICE_RANGE` configurable on asset-per-asset basis after enough investigation on the market movements of these assets.
