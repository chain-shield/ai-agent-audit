# Vulnerability details

## Impact
This can lead to

- updating the `_assetStatus.lastFee0Growth` from a range where the position’s liquidity was never provided breaking protocol functionality
- a DOS on rebalancing whenever subsequent reallocation calls are made for the position preventing actual rebalancing of the position

## Summary
the [_assetStatus.lastFee{0/1}Growth](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/Perp.sol#L385-L406)  is used in the calculation of _assetStatus.fee{0/1}Growth .

It is possible that `_sqrtAssetStatus.totalAmount == _sqrtAssetStatus.borrowedAmount` making the available liquidity in the LP position that constitutes a Squart zero. This can cause 

- DOS the reallocation of the LP funds.
- update fees from a range where liquidity is not allocated

The `PredyPool::reallocate(...)` function can is permissionless and can be called by anyone.  According to the [docs](https://docs.predy.finance/predy-v6/dev/architecture/flowchart#reallocate), 
> *…the LP position is reallocated around the current tick*

The execution flow is partially described below on a high level as required by this report

```solidity
-> PredyPool::reallocate(...)
 -> ReallocationLogic::reallocate(...)
  -> Perp::reallocate(...)
   -> IUniswapV3Pool(_sqrtAssetStatus.uniswapPool)::slot0() 
   ...
   -> getAvailableLiquidityAmount(...)
	   -> IUniswapV3Pool(_uniswapPool).positions(positionKey)
   -> if (totalLiquidityAmount == 0)
X   -> Reallocation::getNewRange(...)   
	   -> Reallocation::_getNewRange(...)        
    -> saveLastFeeGrowth(...)
```

The `Reallocation::getNewRange(...)` function returns the new lower/upper ticks with respect to the the `currentTick` of the pool. However, the problem is that, as seen on L255 above the returned lower/upper tick values are used to update (or are stored in) the `_sqrtAssetStatus.tickLower` / `_sqrtAssetStatus.tickUpper` thereby changing the state of the `_sqrtAssetStatus`  without actually allocating liquidity to the range bounded by these new ticks in the Uniswap pool itself.

## Proof of Concept
- Consider a LP in a pool with `rangeSize` = 100 and `rebalanceThreshold` = 50 and
    - `sqrtAssetStatus.uniswapPool` current tick =  80
    - `_sqrtAssetStatus.tickLower` = 30
    - `_sqrtAssetStatus.tickUpper` = 130
- assume the position is *completely borrowed* and as such available liquidity equal to zero on L220
- due to trades performed in the pool,  `sqrtAssetStatus.uniswapPool` current tick =  -150 and both the `rebalanceThreshold` and the `rangeSize` have been exceeded (this can be made worse by the fact that  `slot0` is used to get the current tick in L206 above)
- `PredyPool::reallocate(...)` is called and `totalLiquidityAmount` is evaluated to zero L220
- `Reallocation::getNewRange(...)` is called on L225 and L226.
- `_sqrtAssetStatus.tickLower` and `_sqrtAssetStatus.tickUpper` are now updated on L225 to (-250, -50) respectively.
    - `_sqrtAssetStatus.tickLower` = -250
    - `_sqrtAssetStatus.tickUpper` = -50
    - `isRangeChanged` = true
    - `relocationOccurred` = false
- reallocation of the position was not done but the `_sqrtAssetStatus.tickLower`/ `_sqrtAssetStatus.tickUpper` have been updated to a new range where the LP position that constitutes the Squart does not exist at because the position was not reallocated to that tick range.
- Also the range has been successfully changed but the position is not reallocated, and because there is no liquidity available to be reallocated.
- `PredyPool::reallocate(...)` is called again while the pool is still totally borrowed with the `sqrtAssetStatus.uniswapPool` current tick =  -95
- `totalLiquidityAmount` is evaluated to zero L220 from the previously changed range where the positions liquidity was not assigned to
- `_sqrtAssetStatus.tickLower` and `_sqrtAssetStatus.tickUpper` are now updated on L225 to (-250, -50) respectively.
    - `_sqrtAssetStatus.tickLower` = -195
    - `_sqrtAssetStatus.tickUpper` = 5
    - `isRangeChanged` = true
    - `relocationOccurred` = false
- while this is ongoing,
    - the `Perp::reallocate(...)` call will always return on L238 and as such the position status is not updated because `Perp::updateRebalancePosition(...)` where `_sqrtAssetStatus.totalAmount` is updated is never reached which also means that will continue to be zero since it is read (L220) from a tick range where there is no liquidity.
    - `saveLastFeeGrowth(...)` will record fees from a tick region where the squart LP’s position liquidity has not been moved to. or does not exist in.
