# Vulnerability details

## Impact
The `liquidate()` function performs the square root of the TWAP after a possible trade. This can be exploited by attackers who can manipulate the price and reset it back to the initial price at no external arbitrage risk unlike what would have been incurred if the price data was taken at the end of the block.

## Proof of Concept
The function `liquidate()` inside the LiquidationLogic library checks for the square root of the corresponding TWAP. This check is performed to ensure that the price is 
within the slippage tolerance range. 
The root cause of the issue is that the TWAP is updated after interest rates apply and rebalance updates.
For reference, the [RareSkills](https://www.rareskills.io/post/twap-uniswap-v2) shows how TWAP calculation patterns should be applied.

If we look at the function `liquidate()` we can see that the sqrt TWAP is checked after applying the interest rate and updating the rebalances:

```Solidity
    function liquidate(
        uint256 vaultId,
        uint256 closeRatio,
        GlobalDataLibrary.GlobalData storage globalData,
        bytes memory settlementData
    ) external returns (IPredyPool.TradeResult memory tradeResult) {
    ...
        // update interest growth
        ApplyInterestLib.applyInterestForToken(globalData.pairs, vault.openPosition.pairId);

        // update rebalance interest growth
        Perp.updateRebalanceInterestGrowth(pairStatus, pairStatus.sqrtAssetStatus);

    ...
        // Check if the price is within the slippage tolerance range to ensure that the price does not become
        // excessively favorable to the liquidator.
        SlippageLib.checkPrice(  // This check
            sqrtOraclePrice,
            tradeResult,
            slippageTolerance,
            tradeParams.tradeAmountSqrt == 0 ? 0 : _MAX_ACCEPTABLE_SQRT_PRICE_RANGE
        );
    ...
    }
```

## Recommended Mitigation Steps

The square root TWAP check needs to be called before rebalance updates and interest rate application
