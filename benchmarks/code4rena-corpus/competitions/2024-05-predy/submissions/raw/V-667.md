# Vulnerability details

## Impact
The ability of miners to reorder transactions within a block can lead to the bypassing of the check that prevents applying interest rates multiple times in the same block. This can result in incorrect interest rate calculations and potentially exploitable vulnerabilities in the smart contract. Attackers may take advantage of this issue to manipulate the interest rates applied to assets, leading to financial losses or unintended behavior of the contract.


## Proof of Concept
The affected code snippet is in the `applyInterestForToken` function:

```solidity
// avoid applying interest rate multiple times in the same block
if (pairStatus.lastUpdateTimestamp >= block.timestamp) {
    return;
}
```

Consider a scenario where two transactions calling the `applyInterestForToken` function are included in the same block:
- Transaction 1 has a `lastUpdateTimestamp` of 1000
- Transaction 2 has a `lastUpdateTimestamp` of 1500

If a miner reorders the transactions such that Transaction 2 is executed before Transaction 1, the check `pairStatus.lastUpdateTimestamp >= block.timestamp` will pass for both transactions, even though the interest rate should have been applied only once in the block.

## Recommended Mitigation Steps
1. Use `block.number` instead of `block.timestamp` for comparison:
```solidity
// avoid applying interest rate multiple times in the same block
if (pairStatus.lastUpdateBlockNumber >= block.number) {
    return;
}
```
Update the `PairStatus` struct to include a `lastUpdateBlockNumber` field and store the current `block.number` when updating the interest rates.

2. Implement additional checks to ensure interest rate is applied only once per block:
```solidity
// avoid applying interest rate multiple times in the same block
if (pairStatus.lastUpdateBlockNumber == block.number) {
    return;
}
pairStatus.lastUpdateBlockNumber = block.number;
```
This ensures that the interest rate is applied only once per unique block number, regardless of the order of transactions.

3. Consider using an oracle or external source of time that is not controlled by miners for more reliable timestamp information.
