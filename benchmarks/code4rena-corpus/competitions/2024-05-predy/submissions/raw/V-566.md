# Vulnerability details

## Summary
The `GlobalData.sol` contract contains functions for validating `vaultId` and `pairId`. The current validation logic incorrectly invalidates the latest valid IDs due to non-strict comparison, potentially leading to unexpected transaction reverts and disruptions in protocol operations. This issue requires an update to the validation logic to correctly handle the full range of valid IDs.
## Impact
The incorrect validation logic has the following impacts:

- Invalidation of Latest Valid IDs: IDs equal to vaultCount and pairsCount are incorrectly considered invalid.
- Transaction Failures: Valid transactions involving the highest valid vault or pair IDs may revert, causing user frustration and operational disruptions.

## Proof of Concept
The issue can be observed in the following functions within the GlobalDataLibrary:

1. validateVaultId:
```
function validateVaultId(GlobalDataLibrary.GlobalData storage globalData, uint256 vaultId) internal view {
    if (vaultId <= 0 || globalData.vaultCount <= vaultId) revert IPredyPool.InvalidPairId();
}
```
2. validate:
```
function validate(GlobalDataLibrary.GlobalData storage globalData, uint256 pairId) internal view {
    if (pairId <= 0 || globalData.pairsCount <= pairId) revert IPredyPool.InvalidPairId();
}
```


## Tools Used
Manual code review
## Recommended Mitigation Steps
Update the comparison in both functions to use strict inequality for the upper bound check:
1. validateVaultId:
```
function validateVaultId(GlobalDataLibrary.GlobalData storage globalData, uint256 vaultId) internal view {
    if (vaultId <= 0 || globalData.vaultCount < vaultId) revert IPredyPool.InvalidPairId();
}
```
2. validate:
```
function validate(GlobalDataLibrary.GlobalData storage globalData, uint256 pairId) internal view {
    if (pairId <= 0 || globalData.pairsCount < pairId) revert IPredyPool.InvalidPairId();
}
```
