# Vulnerability details

## Impact
I know `withdrawProtocolRevenue` has only operator modifier. But, if the operator account becomes compromised and that allows an attacker to gain control of the operator's privileges, then the attacker could potentially exploit the reentrancy vulnerability here.

- Withdrawal of funds from the contract without proper permission.
- Manipulation of the contract's state, leading to unexpected behavior.
- Asset losses for users of the contract.

## Proof of Concept
- Attacker gains control of the operator's permissions.
- Attacker recursively calls the withdrawProtocolRevenue function before the state is updated.
- Attacker drains funds from the contract or manipulates its state as desired.

## Tools Used
Manual Code Review

## Recommended Mitigation Steps
1. Upgrade the security measures for the operator account. Using a hardware wallet or multi-signature scheme could help as far as I know.
2. Implement a reentrancy guard in the withdrawProtocolRevenue function to prevent reentrancy attacks. Could be manual Codex or 3rd party OppenZepplin's.
```solidity
bool private _locked;

modifier _noReentrancy() {
    require(!_locked, "Reentrant call detected");
    _locked = true;
    _;
    _locked = false;
}
```
