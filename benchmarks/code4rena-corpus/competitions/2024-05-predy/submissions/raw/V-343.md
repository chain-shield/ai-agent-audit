# Vulnerability details

## Impact
Having block.timestamp for slippage specification is not a ideal check, since block.timestamp is the time when the function is executed. The transaction can be sitting in the mempool & executed after a long time.
This can be done easily via a MEV. A MEV bot detects the pending transaction. Since the outdated maximum slippage value now allows for high slippage, the bot sandwiches Alice, resulting in significant profit for the bot and significant loss for Alice.

## Proof of Concept

AMMs provide their users with an option to limit the execution of their pending actions, such as swaps or adding and removing liquidity. The most common solution is to include a deadline timestamp as a parameter (for example see Uniswap V2 and Uniswap V3). If such an option is not present, users can unknowingly perform bad trades:

But since the protocol has a specific deadline check while checking for [order verification](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/gamma/GammaTradeMarket.sol#L445) which checks the deadline in--> [Validate()](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/orders/ResolvedOrder.sol#L28)

Which basically means that a miner or mev can execute the order through uniswap just before the deadline check.

## Tools Used
Uniswap 

## Recommended Mitigation Steps
Have a deadline check like uniswap. OR 
decode the deadline parameter from OrderInfo struct and pass it along the swap.
