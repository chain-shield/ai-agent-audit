# Vulnerability details

## Proof of Concept
In the provided `PerpMarketV1` contract, the absence of nonce management within the order validation process creates a susceptibility to replay attacks. This means that a valid signed order can be reused multiple times to execute the same trade, potentially leading to unintended multiple trades and financial loss.

Here is the relevant part of the code from the `ResolvedOrderLib` library, which is responsible for validating resolved orders:
```solidity
library ResolvedOrderLib {
    /// @notice thrown when the order targets a different market contract
    error InvalidMarket();

    /// @notice thrown if the order has expired
    error DeadlinePassed();

    /// @notice Validates a resolved order, reverting if invalid
    /// @param resolvedOrder resovled order
    function validate(ResolvedOrder memory resolvedOrder) internal view {
        if (address(this) != address(resolvedOrder.info.market)) {
            revert InvalidMarket();
        }

        if (block.timestamp > resolvedOrder.info.deadline) {
            revert DeadlinePassed();
        }
    }
}
```
The `validate` function only checks if the order's target market is correct and if the order has not expired. There is no mechanism to ensure that each order is unique and can only be executed once. Specifically, there is no nonce check to prevent the reuse of the same order.
Nonce management is a critical security feature in order validation. A nonce is a unique number that is used only once per order. When an order is signed and executed, its nonce should be recorded and checked to ensure it hasn't been used before. Without this check, an attacker can capture a signed order and replay it multiple times, leading to multiple unauthorized executions of the same order.

In the current implementation, the contract is missing nonce checks. For example, consider the `_verifyOrderV3` function in the `PerpMarketV1` contract:
```solidity
function _verifyOrderV3(ResolvedOrder memory resolvedOrder, uint256 cost) internal view {
    if (block.timestamp > resolvedOrder.info.deadline) {
        revert("Order expired");
    }

    if (address(this) != address(resolvedOrder.info.market)) {
        revert("Invalid market");
    }

    // Other checks...

    // No nonce check
}

```
Without a nonce check, the `resolvedOrder` can be replayed by an attacker if they have the signed message. This can be done by sending the same order repeatedly to the contract, resulting in multiple trades being executed from a single signed order. This is a classic replay attack.

Using a unique hash for each order along with signature verification does not fully mitigate the replay attack issue. While a unique hash and signature verification ensure the authenticity of the order, they do not inherently prevent the same order from being executed multiple times. This is because the signature can be reused unless there is an additional mechanism to track the usage of each unique order.

When an order is created, a hash of the order data is generated, and this hash is signed by the trader. The signed hash is then used to verify the order's authenticity when it is submitted to the contract. This ensures that the order was indeed created and signed by the trader. However, without additional tracking, the same signed hash can be resubmitted to the contract multiple times, leading to the same order being executed multiple times.

 Here's how a replay attack would work in this context:
- A trader creates an order, which is then hashed and signed.
- The hash and signature are stored on the blockchain when the order is submitted.
- An attacker captures the signed order (hash and signature).
- The attacker resubmits the same signed order multiple times.
- The contract verifies the signature each time, confirming its authenticity, and executes the order repeatedly.

Additionally, nonces should always be incremented to ensure that the nonce used in the permit is unique hence preventing signature replay attacks. 
## Impact
The primary impact of this vulnerability is financial loss due to unintended multiple executions of the same trade. An attacker can exploit this to drain funds from a trader's account by repeatedly submitting the same valid order. This can lead to significant financial loss for the trader and undermine the integrity of the trading platform.

## Recommended Mitigation Steps
Nonces ensure uniqueness: Each order includes a unique nonce, ensuring that every order hash is unique.
Tracking used nonces: The contract maintains a record of used nonces for each trader. Once a nonce is used, it cannot be reused.
Add Nonce to `OrderInfo`:
```solidity
struct OrderInfo {
    address market;
    address trader;
    uint256 nonce;
    uint256 deadline;
}
```
Maintain Used Nonces:
```solidity
mapping(address => mapping(uint256 => bool)) public usedNonces;
```
Validate Nonce in `_verifyOrderV3`:
```solidity
function _verifyOrderV3(ResolvedOrder memory resolvedOrder, uint256 cost) internal {
    if (block.timestamp > resolvedOrder.info.deadline) {
        revert("Order expired");
    }

    if (address(this) != address(resolvedOrder.info.market)) {
        revert("Invalid market");
    }

    // Check if nonce has been used
    if (usedNonces[resolvedOrder.info.trader][resolvedOrder.info.nonce]) {
        revert("Nonce already used");
    }

    // Mark nonce as used
    usedNonces[resolvedOrder.info.trader][resolvedOrder.info.nonce] = true;

    // Other checks...
}

```
