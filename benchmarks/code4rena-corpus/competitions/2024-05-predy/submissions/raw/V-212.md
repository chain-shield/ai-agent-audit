# Vulnerability details

## Impact
`execLiquidationCall()` in `GammaTradeMarket.sol` proceeds to remove the position if fully liquidated (i.e `closeRatio == 1e18`) by invoking `_removePosition(vaultId);`. However this is not done if liquidation is performed via `execLiquidationCall()` in:
1. `BaseMarket.sol`. 
2. `BaseMarketUpgradable.sol`

Therefore, the liquidated position is never removed in all instances.

## Vulnerability Details
The [execLiquidationCall()](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/gamma/GammaTradeMarket.sol#L138-L149) in `GammaTradeMarket.sol`    first calls  `_predyPool.execLiquidationCall()` to liquidate an unsafe vault.

```solidity
        IFillerMarket.SettlementParamsV3 memory settlementParams
    ) external override returns (IPredyPool.TradeResult memory tradeResult) {

            _predyPool.execLiquidationCall(vaultId, closeRatio, _getSettlementDataFromV3(settlementParams, msg.sender));

        if (closeRatio == 1e18) {
@>          _removePosition(vaultId); // @audit Position removed here
        }

```
As seen, when a position is fully liquidated (i.e., `closeRatio is 1e18`, indicating 100% closure), it calls [_removePosition(vaultId)](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/gamma/GammaTradeMarket.sol#L402-L406) to clean up the position from the contract's records. This is because when a position is `fully liquidated`, it is essential to remove all references to this position to maintain the integrity of the contract's state. 

However, the `execLiquidationCall()` functions in `BaseMarket.sol` and `BaseMarketUpgradable.sol` do not perform this extra step.

[BaseMarket:execLiquidationCall()](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/base/BaseMarket.sol#L47-L53)

```solidity
        return _predyPool.execLiquidationCall(vaultId, closeRatio, _getSettlementData(settlementParams));

```

[BaseMarketUpgradable:execLiquidationCall()](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/base/BaseMarketUpgradable.sol#L96-L103)

These two only invokes `_predyPool.execLiquidationCall()` simillar to `GammaTradeMarket.execLiquidationCall()` but do not remove the `vaultId` in the end even when a position is `fully liquidated`.

Therefore the `userPositions` mapping and `positionIDs` list will still contain references to positions that are no longer active as the contract's state will not accurately reflect the actual positions, leading to potential discrepancies in data.

## Recommended Mitigation Steps
Since all these `execLiquidationCall()` functions work through `PredyPool.execLiquidationCall()` via the interface call `_predyPool.execLiquidationCall()`, the check should be migrated to `PredyPool.execLiquidationCall()` so that any of the calls result in performing the position removal.

Modify `PredyPool.execLiquidationCall()` as follows:
```diff
    function execLiquidationCall(uint256 vaultId, uint256 closeRatio, bytes memory settlementData)
        external
        nonReentrant
        returns (TradeResult memory tradeResult)
    {
        tradeResult = LiquidationLogic.liquidate(vaultId, closeRatio, globalData, settlementData);

+       if (closeRatio == 1e18) {
+           _removePosition(vaultId); // @audit Position is now removed in all instances
+       }
    }
```
