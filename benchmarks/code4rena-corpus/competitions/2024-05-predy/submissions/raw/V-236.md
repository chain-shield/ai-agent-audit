# Vulnerability details

## Impact
`USDC` is supported by the protocol. Note, it has `blacklist` functionality thus `USDC` tokens cannot be transfered to/from blacklisted addresses.

During `pool` creation, the `operator` sets the `poolOwner` address. `withdrawCreatorRevenue()` can then be called only by this address to withdraw accumulated `creator revenue`.

However, if this address is  `pool.token`  blacklisted, the `safeTransfer()` will revert. As a result, these accumulated `creator revenue` cannot be withdrawn by the `poolOwner`.

## Vulnerability Details
[withdrawCreatorRevenue()](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/PredyPool.sol#L199-L213) withdraws accumulated creator revenue:
```solidity
    function withdrawCreatorRevenue(uint256 pairId, bool isQuoteToken) external onlyPoolOwner(pairId) {
        Perp.AssetPoolStatus storage pool = _getAssetStatusPool(pairId, isQuoteToken);

        uint256 amount = pool.accumulatedCreatorRevenue;

        require(amount > 0, "AZ");

        pool.accumulatedCreatorRevenue = 0;

        if (amount > 0) {
            ERC20(pool.token).safeTransfer(msg.sender, amount); // @audit-issue Cannot wihdraw if blacklisted by USDC
        }

        emit CreatorRevenueWithdrawn(pairId, isQuoteToken, amount);
    }
```
If `pool.token` is `USDC` and the `poolOwner` is `blacklisted`, the withdrawal might DoS. As such, accumulated creator revenue cannot be withdrawn.

I acknowledge that their is a way for the `poolOwner` to update this pool ownership by registering another `owner`.
This is done by calling [updatePoolOwner()](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/PredyPool.sol#L157-L159):
```solidity
    function updatePoolOwner(uint256 pairId, address poolOwner) external onlyPoolOwner(pairId) {
        AddPairLogic.updatePoolOwner(globalData.pairs[pairId], poolOwner);
    }
```
The problem though arises from the fact that incoming owner could also be `blacklisted`. This problem can be recurrent resulting in these accumulated creator revenue being permanently stuck within the protocol.

## Recommended Mitigation Steps
Allow the `poolOwner` to provide their own receiving `to` address during withdrawal.
```diff
-   function withdrawCreatorRevenue(uint256 pairId, bool isQuoteToken) external onlyPoolOwner(pairId) {
+   function withdrawCreatorRevenue(uint256 pairId, address to, bool isQuoteToken) external onlyPoolOwner(pairId) {
        Perp.AssetPoolStatus storage pool = _getAssetStatusPool(pairId, isQuoteToken);

        uint256 amount = pool.accumulatedCreatorRevenue;

        require(amount > 0, "AZ");

        pool.accumulatedCreatorRevenue = 0;

        if (amount > 0) {
-            ERC20(pool.token).safeTransfer(msg.sender, amount);
+            ERC20(pool.token).safeTransfer(to, amount);
        }

        emit CreatorRevenueWithdrawn(pairId, isQuoteToken, amount);
    }
```
