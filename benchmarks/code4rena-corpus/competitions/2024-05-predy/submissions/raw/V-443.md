# Vulnerability details

## Impact
Allowing creation of new PriceFeeds by Re-org attack may adversely affect pricing in PriceFeed.sol contracts.

## Proof of Concept
The `PriceFeedFactory.sol#createPriceFeed()` function deploys a new `PriceFeed` using the `new` keyword, where the address derivation depends only on the arguments passed. This internally uses the `CREATE` opcode, which can be susceptible to reorg attacks. 

https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/PriceFeed.sol#L18-L25

```solidity
File: PriceFeedFactory.sol
         function createPriceFeed(address quotePrice, bytes32 priceId, uint256 decimalsDiff) external returns (address) {
@>    PriceFeed priceFeed = new PriceFeed(quotePrice, _pyth, priceId, decimalsDiff); 
        emit PriceFeedCreated(quotePrice, priceId, decimalsDiff, address(priceFeed));
        return address(priceFeed);
}
```

The `create` opcode is used when deploying new contracts using the new keyword. This opcode can be susceptible to reorg attacks because the address of the newly created contract is deterministic and depends only on the sender's address and nonce. In the case of optimistic rollups like Optimism and Arbitrum, reorgs can occur if a fraud proof is submitted, causing blocks to be reverted.

According to the [README](https://github.com/code-423n4/2024-05-predy#general-questions), the protocol is going to be deployed on Arbitrum, Optimism and Base.

| Question| Answer|
|-|-|
|Chains the protocol will be deployed on| Arbitrum,Base,Optimism|



Now, optimistic rollups chains like Optimism/Arbitrum are suspect to reorgs since if someone finds a fraud the blocks will be reverted, even though the user receives a confirmation.


Let's look at this scenario: 
##### Initial Setup

1. **Deployment**: The `PriceFeedFactory` contract is deployed on an optimistic rollup chain like Arbitrum or Optimism.
2. **User Interaction**: A user (let's call them Alice) interacts with the `PriceFeedFactory` contract to create a new `PriceFeed` contract.

##### Step-by-Step Scenario

1. **Alice Calls `createPriceFeed`**:
   - Alice calls the `createPriceFeed` function with specific parameters: `quotePrice`, `priceId`, and `decimalsDiff`.
   - The `createPriceFeed` function uses the `new` keyword to deploy a new `PriceFeed` contract.
   - The address of the new `PriceFeed` contract is determined by Alice's address and her current nonce.

2. **Transaction Confirmation**:
   - The transaction is included in a block and initially confirmed.
   - The `PriceFeedCreated` event is emitted, and the address of the new `PriceFeed` contract is logged.

3. **Re-org Occurs**:
   - A fraud proof is submitted, causing a re-org on the chain.
   - The block containing Alice's transaction is reverted.
   - Alice's nonce is reset to its previous value.

4. **Alice's Transaction is Re-included**:
   - Alice's transaction is re-included in a new block.
   - However, due to the re-org, the state of the chain has changed, and Alice's nonce might have been incremented by other transactions that were included in the meantime.

5. **Different Contract Address**:
   - When the `createPriceFeed` function is executed again, the nonce used for the `CREATE` opcode is different.
   - As a result, the address of the newly created `PriceFeed` contract is different from the one initially generated.
