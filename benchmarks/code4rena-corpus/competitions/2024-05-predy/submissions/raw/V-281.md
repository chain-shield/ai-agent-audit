# Vulnerability details



Pool owners can change the rate at which borrowing fees grow by calling `updateIRMParams`. When this function is called, the following parameters can be changed for both the quote and base token. This causes borrowing fees that have yet to be calculated (time difference between the last time `applyInterestForToken` is called and the current time) to grow by the new rate instead of the rate that existed during that time.

```
    struct IRMParams {
        uint256 baseRate;
        uint256 kinkRate;
        uint256 slope1;
        uint256 slope2;
    }
```

These parameters are then used whenever the `applyInterestForToken` function is called. Specifically, these parameters are used to determine the interest rate. The higher the `slope1` and `slope2` are, the more fees users will pay.

```
        if (utilizationRatio <= irmParams.kinkRate) {
            ir += (utilizationRatio * irmParams.slope1) / _ONE;
        } else {
            ir += (irmParams.kinkRate * irmParams.slope1) / _ONE;
            ir += (irmParams.slope2 * (utilizationRatio - irmParams.kinkRate)) / _ONE;
        }
```

Before state changes made in core functions such as `trade`, `supply`, and `withdraw` are called, the `applyInterestForToken` function is also called to apply the required interest for the amount of time that has passed since the last update. This function is not called before any state changes from `updateIRMParams` take place. Because of this, the amount of fees that are going to be updated will be based on the new IRM params, which wrongly leads to a jump in borrowing fees, pushing positions that are borderline unhealthy to be unexpectedly liquidated.

This doesn't have to be a malicious act by the pool owner; it will naturally and inevitably happen when any of the pool owners update the interest rates. At which point, if the rate is raised, it will wrongly charge borrowers more. If it is lowered, it will wrongly charge borrowers not enough.

## Impact
IRM updates will wrongly lead to jumps in borrowing fees as well as unexpected liquidations.

## Proof of Concept

- Alice creates a pool and supplies a sufficient amount of quote and base tokens for users to borrow.
- Bob opens a 2x long position supplying $1000 in collateral.
- 1 day passes, and if `applyInterestForToken` were to be called, he would end up owing $10 in fees, but currently `applyInterestForToken` has not been called.
- Moments later, Alice calls `updateIRMParams` and raises the `slope1` to collect more fees going forward.
- The price does not change, and Bob closes the position expecting to have his $1000 collateral minus the $10 in fees.
- `applyInterestForToken` is called upon Bob closing his position.
- `applyInterestForToken` wrongly uses the new IRM rates, which now calculates Bob owes $20 in borrowing fees.
- The order finishes executing, and Bob wrongly receives $980 instead of what should have been $990.
## Tools Used

Manual analysis.

## Recommended Mitigation Steps

Call `applyInterestForToken` inside of `updateIRMParams` before the state changes occur. This will ensure all borrowing fee growth is based on the correct interest rate for its time.
