# Vulnerability details

When a traders position is undercollateralized they get eligible for liquidation. The liquidation process sends any left over margin back to the trader and if the remaining margin is negative the liquidiator will pay the protocol. This process ensures the protocol is collateralized and that LP funds are safe. 
However this logic can be exploited by a malicious actor by setting the `trader` address to zero and when undercollateralized to negative the liquidiator will have to pay regardless.

## Impact
 Liquidators will be forced to cover the negative margin for positions with a `trader` address set to zero, resulting in a direct financial loss as they receive nothing in return.

## Proof of Concept
https://github.com/code-423n4/2024-05-predy/blob/main/src%2Flibraries%2Forders%2FOrderInfoLib.sol#L4-L9
```solidity
struct OrderInfo {
    address market;
    address trader;
    uint256 nonce;
    uint256 deadline;
}
```

The `trader` address can be set to zero without validation:
https://github.com/code-423n4/2024-05-predy/blob/main/src%2Flibraries%2Forders%2FOrderInfoLib.sol#L18-L20
```solidity
function hash(OrderInfo memory info) internal pure returns (bytes32) {
    return keccak256(abi.encode(ORDER_INFO_TYPE_HASH, info.market, info.trader, info.nonce, info.deadline));
}
```

When the order gets executed, the `trader` address is set as the `recipient`:
https://github.com/code-423n4/2024-05-predy/blob/main/src%2Fmarkets%2Fperp%2FPerpMarketV1.sol#L210
```solidity
_predyPool.updateRecepient(tradeResult.vaultId, perpOrder.info.trader);
```

In `predyPool`, there is no validation on the `recipient` address:
https://github.com/code-423n4/2024-05-predy/blob/main/src%2FPredyPool.sol#L286-L292
```solidity
    function updateRecepient(uint256 vaultId, address recipient) external onlyVaultOwner(vaultId) {
        DataType.Vault storage vault = globalData.vaults[vaultId];

        vault.recipient = recipient;

        emit RecepientUpdated(vaultId, recipient);
    }
```

During liquidation, if the remaining margin is negative, the liquidator is required to cover the shortfall:
https://github.com/code-423n4/2024-05-predy/blob/main/src%2Flibraries%2Flogic%2FLiquidationLogic.sol#L101-L108
```solidity
            } else if (remainingMargin < 0) {
                vault.margin = 0;

                // To prevent the liquidator from unfairly profiting through arbitrage trades in the AMM and passing losses onto the protocol,
                // any losses that cannot be covered by the vault must be compensated by the liquidator
                ERC20(pairStatus.quotePool.token).safeTransferFrom(msg.sender, address(this), uint256(-remainingMargin));
            }
        }
```

If `vault.recipient` is the zero address, the liquidator will still be required to pay the negative margin, receiving nothing in return. This creates a significant risk and disincentive for liquidators.

 Example Scenario

1. A malicious user creates an order with significant debt, setting the `trader` address to zero.
2. The position becomes under-collateralized.
3. A liquidator attempts to liquidate the position.
4. The remaining margin is negative, and the liquidator is forced to cover the debt.
5. The liquidator receives no compensation because the `recipient` is the zero address, resulting in a financial loss.

## Recommended Mitigation Steps

Validate `trader` Address: Add validation to ensure that the `trader` address is not zero when creating an order.
```solidity
    function hash(OrderInfo memory info) internal pure returns (bytes32) {
        require(info.trader != address(0), "Trader address cannot be zero");
        return keccak256(abi.encode(ORDER_INFO_TYPE_HASH, info.market, info.trader, info.nonce, info.deadline));
    }
   ```
