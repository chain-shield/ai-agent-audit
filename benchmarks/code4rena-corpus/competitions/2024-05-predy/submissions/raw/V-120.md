## Proof of Concept

Whenever there is a need to liquidate a user via `LiquidationLogic#liquidate()`, the trade ends up being placed on the PredyPool in this line:
https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/logic/LiquidationLogic.sol#L66-L68

```solidity

        tradeResult = Trade.trade(globalData, tradeParams, settlementData);

```

Now this attempt at trading routes it's logic to `TradeLogic.trade()` as can be seen in this [line](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/PredyPool.sol#L278), which ends up directly calling `Trade.trade()` as seen from [here](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/logic/TradeLogic.sol#L42).

Now going to the implementation of `Trade.trade()` we can see the below https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/Trade.sol#L32-L47

Now when `decrease()` is called there is always a check that there is enough liquidity present for the withdrawal to be processed which one would expect as a valid case since generally across lending protocols when utilization rate is high we expect the liquidity to be minimal, i.e https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/Perp.sol#L719-L726

```solidity
    function decrease(SqrtPerpAssetStatus memory _assetStatus, uint256 _liquidityAmount)
        internal
        returns (int256 receivedAmount0, int256 receivedAmount1)
    {
        if (_assetStatus.totalAmount - _assetStatus.borrowedAmount < _liquidityAmount) {
            revert NoCFMMLiquidityError();
        }
        //(snip)
        }

```

Where `NoCFMMLiquidityError` is only thrown when there is [not enough liquidity for the required withdrawal](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/Perp.sol#L30-L31).

All the above end up routing to the fact that a liquidation **can't occur** if there is not enough liquidity to process the withdrawal since the attempt to `decrease()` would always revert, which then means in valid instances during the lifetime of protocol, valid liquidations would not be processed which then probes protocol to allow for the ingestion of more bad debt and extensively a bank run, this logic also leaves this approach vulnerable to a malicious actor who takes actions that end up making his account liquidatable, but at the same time the malicious actor withdraws from the pool to ensure that not enough liquidity is present in the pool to get their positions liquidated. Would be key to note that in this case the malicious actor doesn't even need to withdraw 100% of the available liquidity, but rather just enough to have their positions not being liquidated, also partial liquidations wouldn't really sort this out as the position is going to be massive _(a whale position)_ and partial liquidation using the current available liquidity would only skim off not much from the position.

## Impact

Liquidations will fail when there is not enough liquidity, causing bad debt on the protocol if the price moves against the borrower. Would be key to note that liquidations are a core invariant of any lending protocol and should never fail in order to prevent bad debt, and ultimately, a bank run.

So a malicious actor can use this vulnerability to make their positions not liquidatable by always ensuring that the liquidity present is not enough to process their liquidations, _( or frontrunning a liquidation and withdrawing liquidity with another account, though in this case this is hardly a path to follow considering protocol deploys on optimistic L2 chains which are not really susceptible to frontrunning issues.)_

## Recommended Mitigation Steps

When liquidating consider reimplementing the logic not to revert when the liquidity available is not enough to process liquidations
