# Vulnerability details

## Impact
The `PreedyPool::withdrwaProtocolRevenue` is intended to get the revenue fees and can be withdrawn by the admin, unfortunately it's initializes the accumulatedRevenue in the pool to 0 and then still makes a check to know if the amount is > 0 before sending out the funds from the protocol. The double checks it makes makes funds lost in the protocol

## Proof of Concept
```solidity
        Perp.AssetPoolStatus storage pool = _getAssetStatusPool(pairId, isQuoteToken); //gets assets status pool of the pairId and isQuoteToken store it as pool

        uint256 amount = pool.accumulatedProtocolRevenue; //retrieves the accumulatedProtocol revenue in the pool and save as amount

        require(amount > 0, "AZ"); //require the amount is greater zero or throws AZ

        pool.accumulatedProtocolRevenue = 0; //sets the accumulatedProtocolRevenue to 0

```
After retrieving the amount from the pool of accummulatedProtocolRevenue, 

```solidity
      //@audit // the second amount > 0 may likely not pass because the protocolRevenue is being set to 0 back
        if (amount > 0) {
            ERC20(pool.token).safeTransfer(msg.sender, amount); //checks if the amount greater than zero, then pool token to the caller(msg.sender), the amount
        }

```

## Tools Used
Manual
## Recommended Mitigation Steps
Remove either of the checks, or the require statement
```solidity
if (amount > 0) {
        pool.accumulatedProtocolRevenue = 0; 
        ERC20(pool.token)safeTransfer(msg.sender, amount);
}
```
