# Vulnerability details

Whenever traders wants to interact with the protocol they hash their orders which will later be executed by the filler if opening positions.
The protocol uses partial and full liquidation by specifiying the ` closeRatio` .  In the case of partial liquidation, there can be a remaining margin that needs to be transferred to the recipient. If the liquidation is complete, there might be a shortfall, resulting in a negative margin that the liquidator needs to cover.

However there is a critical issue where setting the `trader` address to zero (`0x0`) In the order info can prevent liquidations from occurring when the position is under collateralized. This results in liquidators wasting gas fees on attempts to liquidate positions that cannot be liquidated. 

The liquidation logic includes the following steps:
1. The logic checks whether a vault is eligible for liquidation.2. If the remaining margin is positive, it transfers the margin to the vault's recipient.
3. If the remaining margin is negative, it requires the liquidator to compensate for the shortfall.

However, if the `trader` address (which is set in `OrderInfo`) is zero (`0x0`), the liquidation process silently fails when it attempts to transfer the remaining margin to the recipient. This is because the recipient is set to the `trader` address, and transferring tokens to the zero address is not allowed.

## Impact 
Positions with a `trader` address set to zero cannot be liquidated, potentially locking funds in these positions indefinitely.
   Liquidators will repeatedly attempt to liquidate these positions, incurring gas fees without success.
    EiLocked positions can negatively impact the overall liquidity and health of the pool, leading to potential losses for liquidity providers

## Proof Of Concept
https://github.com/code-423n4/2024-05-predy/blob/main/src%2Flibraries%2Forders%2FOrderInfoLib.sol#L4-L9
```solidity
struct OrderInfo {
    address market;
    address trader;
    uint256 nonce;
    uint256 deadline;
}
```
None of the struct parameters are verified before hashing, `trader` can be set to zero 
https://github.com/code-423n4/2024-05-predy/blob/main/src%2Flibraries%2Forders%2FOrderInfoLib.sol#L18-L20
```solidity
    function hash(OrderInfo memory info) internal pure returns (bytes32) {
        return keccak256(abi.encode(ORDER_INFO_TYPE_HASH, info.market, info.trader, info.nonce, info.deadline));
    }
}
```
When the order gets executed it sets the `trader` address as the `recipient`
https://github.com/code-423n4/2024-05-predy/blob/main/src%2Fmarkets%2Fperp%2FPerpMarketV1.sol#L210-L211
```solidity
_predyPool.updateRecepient(tradeResult.vaultId, perpOrder.info.trader);
        }
```

In predyPool there's no validation on the `recepient` address either 
https://github.com/code-423n4/2024-05-predy/blob/main/src%2FPredyPool.sol#L286-L292
```solidity
function updateRecepient(uint256 vaultId, address recipient) external onlyVaultOwner(vaultId) {
        DataType.Vault storage vault = globalData.vaults[vaultId];

        vault.recipient = recipient;

        emit RecepientUpdated(vaultId, recipient);
    }
```
The `vault.recipient` will effectively be zero if the `order.info.trader` is set to zero.

During liquiditation if the remaining margin is positive it will be sent back to the `recipient` and if the `recipient` is zero it fails silently because the next condition requires the remaining margin to be less than zero.
https://github.com/code-423n4/2024-05-predy/blob/main/src%2Flibraries%2Flogic%2FLiquidationLogic.sol#L92-L100
```solidity
if (remainingMargin > 0) {
    if (vault.recipient != address(0)) {
        // Send the remaining margin to the recipient.
        vault.margin = 0;
        sentMarginAmount = uint256(remainingMargin);
        ERC20(pairStatus.quotePool.token).safeTransfer(vault.recipient, sentMarginAmount);
    }
} else if (remainingMargin < 0) {
    vault.margin = 0;
    // Liquidator compensates for the shortfall.
    ERC20(pairStatus.quotePool.token).safeTransferFrom(msg.sender, address(this), uint256(-remainingMargin));
}
```
if `vault.recipient` is the zero address, the transfer will not occur, effectively making the position unliquidatable.

## Recommended Mitigation Steps
Add validation to ensure that the `trader` address is not zero when creating an order.
   ```solidity
    function hash(OrderInfo memory info) internal pure returns (bytes32) {
        require(info.trader != address(0), "Trader address cannot be zero");
        return keccak256(abi.encode(ORDER_INFO_TYPE_HASH, info.market, info.trader, info.nonce, info.deadline));
    }
    ```
