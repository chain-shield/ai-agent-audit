# Vulnerability details

## Impact
If the base and quote tokens are swapped, it could affect how liquidity is added or removed from pools, potentially leading to imbalances or inefficiencies. Also, trades executed against these incorrectly assigned tokens could result in unintended outcomes, affecting users' balances and positions.


## Proof of Concept
The `addPair` function in the provided Solidity code is designed to add a new token pair to a system. The function accepts various parameters, including addresses for the quote and base tokens, and interacts with the Uniswap V3 protocol to manage these tokens. A critical aspect of this function is the correct assignment of token roles, specifically determining which token is the quote token (`token0`) and which is the base token (`token1`).

Upon reviewing the code, particularly the section where the function checks if the `stableTokenAddress` (assumed to be the quote token) is either `token0` or `token1` in the Uniswap pool:

It relies on the `_isQuoteZero` flag to determine which token is the quote token and assigns the other token as the base token accordingly. While this approach works under the assumption that the `_isQuoteZero` flag is accurately set elsewhere in the code, it does not provide a robust mechanism to ensure that the tokens are always assigned correctly according to their intended roles.
The correctness of the token assignment heavily depends on the accurate determination of the `_isQuoteZero` flag outside of the `_storePairStatus` function. Any inaccuracies or assumptions in the logic that sets this flag could lead to incorrect assignments.
Given the provided Solidity code, the `_isQuoteZero` flag is determined within the `addPair` function based on whether the `stableTokenAddress` (the quote token) is `token0` or `token1` in the Uniswap pool:

The `_storePairStatus` function stores the pair status with the quote token and base token correctly identified based on the `_isQuoteZero` flag. This mechanism relies on the accurate determination of the `_isQuoteZero` flag to ensure that the tokens are assigned correctly according to their intended roles.

Let's consider a scenario where the stableTokenAddress is indeed token0 in the Uniswap pool, meaning isQuoteZero would be true. In this case, the _storePairStatus function is called with isQuoteZero set to true, and it assigns token1 as the base token and token0 as the quote token, which aligns with the intended roles.

However, if there were an error in the logic that determines the `_isQuoteZero` flag, leading to it being incorrectly set (for example, due to a bug or incorrect assumptions about the token order in the pool), this could result in incorrect assignments. Specifically:

- If `isQuoteZero` were incorrectly set to false when `stableTokenAddress` is actually `token0`, the `_storePairStatus` function would incorrectly assign `token0` as the base token and `token1` as the quote token.
- Conversely, if `isQuoteZero` were incorrectly set to true when `stableTokenAddress` is actually `token1`, the `_storePairStatus` function would also incorrectly assign `token0` as the base token and `token1` as the quote token.

This lack of enforcement means that while the function ensures one of the tokens is the quote token, it does not guarantee the specific roles of `token0` and `token1` according to the intended configuration. This check alone does not guarantee that the tokens are correctly assigned as `token0` and `token1`. It only verifies that one of the tokens is correct. There's no enforcement to ensure that the `token0` and `token1` are assigned according to the intended configuration (i.e., `token0` should be the quote token and `token1` should be the base token).
