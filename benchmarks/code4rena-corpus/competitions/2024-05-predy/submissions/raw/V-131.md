# Vulnerability details


## Proof of Concept

In mulliple instances the `predyPool.take` function is queried.
For example see https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpMarketV1.sol#L127-L130

```solidity
            } else if (marginAmountUpdate < 0) {//@audit this would always revert due to the `onlyByLocker` modifier on the `predyPool.take()` function.
                _predyPool.take(true, callbackData.trader, uint256(-marginAmountUpdate));
            }

```

Problem however is that the `predyPool.take` function includes a modifier restricting the calls only to the current locker: https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/PredyPool.sol#L329-L332

```solidity
    function take(bool isQuoteAsset, address to, uint256 amount) external onlyByLocker {
        globalData.take(isQuoteAsset, to, amount);
    }

```

See implementation of `onlyByLocker` https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/PredyPool.sol#L52-L56

```solidity
    modifier onlyByLocker() {
        address locker = globalData.lockData.locker;
        if (msg.sender != locker) revert LockedBy(locker);
        _;
    }
```

Now would be key to note that multiple other instances query the `predyPool.take` function as can be confirmed by this search command: [https://github.com/search?q=repo%3Acode-423n4%2F2024-05-predy++predyPool.take%28+NOT+language%3APython+language%3A%22Gerber+Image%22+NOT+path%3A%2F%5Elib%5C%2Fopenzeppelin-contracts%5C%2F%2F+NOT+path%3A%2F%5Elib%5C%2Fsolmate%5C%2Fsrc%5C%2F%2F+NOT+path%3A%2F%5Elib%5C%2Fpermit2%5C%2Flib%5C%2Fsolmate%5C%2Fsrc%5C%2F%2F+NOT+path%3A%2F%5Elib%5C%2Fpermit2%5C%2Flib%5C%2Fopenzeppelin-contracts%5C%2Fcontracts%5C%2F%2F+NOT+path%3A%2F%5Elib%5C%2Fpermit2%5C%2Ftest%5C%2F%2F+path%3A%2F%5Esrc%5C%2F%2F&type=code](https://github.com/search?q=repo%3Acode-423n4%2F2024-05-predy++predyPool.take%28+NOT+language%3APython+language%3A%22Gerber+Image%22+NOT+path%3A%2F%5Elib%5C%2Fopenzeppelin-contracts%5C%2F%2F+NOT+path%3A%2F%5Elib%5C%2Fsolmate%5C%2Fsrc%5C%2F%2F+NOT+path%3A%2F%5Elib%5C%2Fpermit2%5C%2Flib%5C%2Fsolmate%5C%2Fsrc%5C%2F%2F+NOT+path%3A%2F%5Elib%5C%2Fpermit2%5C%2Flib%5C%2Fopenzeppelin-contracts%5C%2Fcontracts%5C%2F%2F+NOT+path%3A%2F%5Elib%5C%2Fpermit2%5C%2Ftest%5C%2F%2F+path%3A%2F%5Esrc%5C%2F%2F&type=code), i.e from the `GammaTradeMarket.sol` and also an instance in the `SettlementCallbackLib.sol` asides the one from `PerpMarketV1.sol` hinted above.

Now since the modifier exists on the `predyPool.take` function, this then causes the attempt at _taking_ from these contracts to revert, considering they are not all the `locker` that's expected to access the `predyPool.take` function.

## Impact

DOS to core functionalities that require the success of the query to `predyPool.take`, in the case of this then means that when [` (marginAmountUpdate < 0)`](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpMarketV1.sol#L127) the `PerpMarketV1#predyTradeAfterCallback()` function would revert.

> And the same case applicable to other instances where `predyPool.take` is being queried since the `msg.sender` of this query is not going to be the `locker` the `predyPool.take` function always [reverts](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/PredyPool.sol#L329).

## Recommended Mitigation Steps

Consider accepting more than the `locker` in `predyPool.take`, and instead whitelist the contracts where this function is going to be called from instead.
