# Vulnerability details

## Impact
Incorrect check for available liquidity in the `decrease` function could result in the following scenarios:

**`Inability to decrease liquidity`** If the available liquidity (`_assetStatus.totalAmount - _assetStatus.borrowedAmount`) is equal to the requested liquidity amount (`_liquidityAmount`), the function will revert with the `NoCFMMLiquidityError`. Means that users will not be able to decrease their liquidity position even when they have enough liquidity available.

**`Potential loss of funds`** If the available liquidity is slightly less than the requested liquidity amount (e.g., available liquidity is 99, and requested liquidity is 100), the function will not revert, and the `burn` operation will be executed. But since the available liquidity is insufficient, the `burn` operation may fail or result in unexpected behavior, potentially leading to loss of funds or other unintended consequences.

## Proof of Concept
The incorrect check is: [#L723-L725](https://github.com/code-423n4/2024-05-predy/blob/2fb1e0ec7a52fc06c2e9c8e561bccba84302e4bb/src/libraries/Perp.sol#L723-L725)
```solidity
if (_assetStatus.totalAmount - _assetStatus.borrowedAmount < _liquidityAmount) {
    revert NoCFMMLiquidityError();
}
```
This check assumes that `_assetStatus.totalAmount` represents the total liquidity deposited, and `_assetStatus.borrowedAmount` represents the amount of liquidity that has been borrowed or used, the code does not provide enough context to determine if this assumption is correct.

> If the assumption is correct, then the check is incorrect because it should ensure that the available liquidity (`_assetStatus.totalAmount - _assetStatus.borrowedAmount`) is greater than or equal to the requested liquidity amount (`_liquidityAmount`), not strictly greater.

Consider the following scenario

`_assetStatus.totalAmount` = 1000
`_assetStatus.borrowedAmount` = 900
`_liquidityAmount` = 100

In this case, the available liquidity is `1000 - 900 = 100`, which is equal to the requested liquidity amount of 100.

With the current implementation, the check `_assetStatus.totalAmount - _assetStatus.borrowedAmount < _liquidityAmount` will evaluate to `false` (100 is not less than 100), and the function will proceed to execute the `burn` operation.

However, since the available liquidity is exactly equal to the requested liquidity amount, the burn operation may fail or result in unexpected behavior, potentially leading to loss of funds or other unintended consequences.

By changing the check to `_assetStatus.totalAmount - _assetStatus.borrowedAmount <= _liquidityAmount`, the function will correctly revert in this scenario, preventing issues and ensuring that the available liquidity is strictly greater than the requested liquidity amount before proceeding with the burn operation.

```diff
    revert NoCFMMLiquidityError();

```
The correct check should be:
```diff
+ if (_assetStatus.totalAmount - _assetStatus.borrowedAmount <= _liquidityAmount) {
    revert NoCFMMLiquidityError();
}
```
This change ensures that the function will revert if the available liquidity is less than or equal to the requested liquidity amount, which is the intended behavior.
