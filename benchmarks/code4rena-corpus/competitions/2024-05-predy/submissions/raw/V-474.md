# Vulnerability details

## Summary

Assumptions:
- Quote Token: USDC
- Base Token: WBTC
- SqrtPriceX96 of Bitcoin: 2112882623242900292931827723567 (as of June 5th)
- token0 of the WBTC/USDC Pool: WBTC


Within `Trade::trade` we get the square root price by calling `Trade::getSqrtPrice`, which retrieves the current sqrtPriceX96 from UniswapV3Pool::slot0 and converts it as follows:

```solidity
function convertSqrtPrice(uint160 sqrtPriceX96, bool isQuoteZero) internal pure returns (uint160) {
        if (isQuoteZero) {
            return uint160((Constants.Q96 << Constants.RESOLUTION) / sqrtPriceX96);
        } else {
            return sqrtPriceX96;
        }
    }
```

Since the quote token (USDC) is not token0 we don't do any additional work and just return the sqrtPriceX96

After that we call the `Trade::swap` function, which is where the problem occurs.

As we can see from the snippet, above, if `totalBaseAmount` is 0, we call `calculateStableAmount`with params of the sqrtPrice which is `2112882623242900292931827723567` and the base amount which is hardcoded as `1e18`, then we return early by calling `divToStable`.

The condition for the `totalBaseAmount` to be 0, is if perp trading and squart trading are executed in same trade, resulting in a perfectly delta-neutral position.

Since, the protocol expects to use WBTC, which is a token with 8 decimals of precision. Passing `1e18` for the base amount, will result in `divToStable` to return the amounts for 10 billions bitcoins instead of 1.

## Impact

Since the amount returned from `Trade::divToStable` will be with ten more 0s, there is no way for either the user to pay from the position nor for the callback to take this much from the vault. Simply, because there is no way that both will have such a big balance of WBTC.
