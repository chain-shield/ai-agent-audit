# Vulnerability details

## Impact
Every time, the pool owner updates the fee rate, the protocol should compute the 
accrued fees since the last Update Timestamp to the time of update should be computed and reflected on the accumulated protocol revenue and creator revenue.

If the new fee rate is applied directly into the config without considering the time passed since the last update, the new fee rate will apply since the last update time stamp, which is incorrect. 

## Proof of Concept
When pool Owner updates the fee rate , before the new fee rates are applied on to the global storage, the logic should first compute the accrued fee for the time period of update time until now and reflected on the accumulated protocol revenue and creator revenue.

The current implementation does not consider the time passed since the last update, stored the new rate directly to the global storage. As such the new fee rate gets applied for the old period as well.

The correct implementation is to use old fee rate until the time of update for computation of accumulated revenues and update the global storage so that new fee rate becomes effective from the point of update by the pool owner.

```
 function updateFeeRatio(uint256 pairId, uint8 feeRatio) external onlyPoolOwner(pairId) {
        AddPairLogic.updateFeeRatio(globalData.pairs[pairId], feeRatio);
    }
```


## Tools Used
Manual review.

## Recommended Mitigation Steps
The recommendation is to call ApplyInterestLib::applyInterestForToken() for the pairId before updating the global storage. This will ensure the accruals are computed based on old fee rate.
