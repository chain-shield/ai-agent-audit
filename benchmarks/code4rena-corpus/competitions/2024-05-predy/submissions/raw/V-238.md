# Vulnerability details

A weakness in the PredyPool contract, specifically a reentrancy vulnerability, with an explanation and a code snippet.

Weakness: Reentrancy vulnerability in the `execLiquidationCall` function

The `execLiquidationCall` function calls the `take` function of the GlobalDataLibrary, which could potentially be a malicious contract. An attacker could exploit this by creating a malicious settlement contract that calls the `take` function in its constructor or callback, causing a reentrancy attack and stealing funds.

Code snippet demonstrating the vulnerability:

```solidity
function execLiquidationCall(
    uint256 vaultId,
    uint256 closeRatio,
    bytes memory settlementData
) external nonReentrant returns (TradeResult memory tradeResult) {
    ...
    globalData.take(isQuoteAsset, to, amount); // Potentially vulnerable line
    ...
}

function take(bool isQuoteAsset, address to, uint256 amount) external onlyByLocker {
    if (isQuoteAsset) {
        ERC20(globalData.quoteAsset).safeTransferFrom(address(this), to, amount);
    } else {
        ERC20(globalData.baseAsset).safeTransferFrom(address(this), to, amount);
    }
}
```

Explanation of the method for exploitation:

1. An attacker creates a malicious settlement contract (SettlementContract) that implements the ISettlement interface.
2. The attacker initiates a liquidation process on the PredyPool contract by calling the `execLiquidationCall` function with the SettlementContract address as the `to` parameter.
3. When the `globalData.take` function is called within `execLiquidationCall`, it transfers funds from the PredyPool contract to the SettlementContract.
4. In the SettlementContract's constructor or callback, the attacker calls the `execLiquidationCall` function again, reentering the PredyPool contract.
5. By repeating steps 3 and 4, the attacker can continuously steal funds from the PredyPool contract until the contract is drained.

To protect against this vulnerability, use the Checks-Effects-Interactions pattern and ensure that all state changes are made before calling external contracts. Additionally, consider implementing require statements to check if the contract is already in a liquidation process before initiating a new one.

Here is the updated `execLiquidationCall` function, addressing the reentrancy vulnerability:

```solidity
function execLiquidationCall(
    uint256 vaultId,
    uint256 closeRatio,
    bytes memory settlementData
) external nonReentrant returns (TradeResult memory tradeResult) {
    ...
    require(!isLiquidating[vaultId], "Liquidation in progress");
    isLiquidating[vaultId] = true;

    globalData.take(isQuoteAsset, to, amount);

    isLiquidating[vaultId] = false;
    ...
}
```

This updated code adds a `isLiquidating` state variable to track ongoing liquidation processes and prevents reentrancy by checking this variable before initiating a new liquidation. By implementing this simple state check, the reentrancy vulnerability can be effectively mitigated.
