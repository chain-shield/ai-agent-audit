# Vulnerability details


When `calculateMinMargin` is called, it will need to calculate the minimum margin in part by calling `calculateMinValue`, which will use the `UniHelper` contract, specifically the `getSqrtTWAP` function that retrieves the tick cumulatives based on the present time as well as 30 minutes ago.

```
    uint256 internal constant _ORACLE_PERIOD = 30 minutes;
```

Most of the UniHelper contract correctly mirrors Uniswap's implementation. However, there is one key check missing that ends up affecting all pools that have tokens with low prices. This is because negative ticks in the current implementation round up instead of rounding down. Per Uniswap, this function should always round towards negative infinity.

https://github.com/Uniswap/v3-periphery/blob/697c2474757ea89fec12a4e6db16a574fe259610/contracts/libraries/OracleLibrary.sol#L30-L36

```
 // Always round to negative infinity
        if (tickCumulativesDelta < 0 && (tickCumulativesDelta % secondsAgo != 0)) arithmeticMeanTick--;
```

Which currently the Predy implementation does not.

```
 int24 tick = int24((tickCumulatives[1] - tickCumulatives[0]) / int56(int256(ago)));
```

## Impact
In instances where the `tick` is a negative value and the difference between `tickCumulatives[1]` and `tickCumulatives[0]` does not divide evenly into `ago`, the `tick` will round up, making the returned price greater than it actually is. This value is referenced when a liquidation is attempted, and with an inflated price, the liquidation may fail even though the position is eligible for liquidation. In addition to unhealthy positions being allowed to exist, this will also be used when determining the minimum amount of margin needed.

Overall, anywhere this function `getSqrtTWAP` is used, it will return an inaccurate value for ticks that are negative, hindering the functionality of the protocol.
## Proof of Concept
```
int24 tick = int24((tickCumulatives[1] - tickCumulatives[0]) / int56(int256(ago)));
```

The delta between `tickCumulatives[1]` and `tickCumulatives[0]` is negative -4500

```
int24 tick = -4500 / 1800;
int24 tick = -2.5;
```

Because Solidity does not have decimals, the `.5` portion will be trimmed `-2.5 => -2`.

`-2 > -2.5` which means that the tick value rounded up, leading to a larger and inaccurate/unsafe price to be used.

## Recommended Mitigation Steps
Similar to Uniswap, add the following check before using `tick` to calculate `sqrtPriceX96`.

```
if ((tickCumulatives[1] - tickCumulatives[0]) < 0 && ((tickCumulatives[1] - tickCumulatives[0]) % ago != 0)) tick--;
```

Making the end of the function:

```
int24 tick = int24((tickCumulatives[1] - tickCumulatives[0]) / int56(int256(ago)));

if ((tickCumulatives[1] - tickCumulatives[0]) < 0 && ((tickCumulatives[1] - tickCumulatives[0]) % ago != 0)) tick--;

uint160 sqrtPriceX96 = TickMath.getSqrtRatioAtTick(tick);

return (sqrtPriceX96, ago);
```
