# Vulnerability details


## Proof of Concept

First see https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/README.md#L146-L153

```markdown
| Question                                | Answer                 |
| --------------------------------------- | ---------------------- |
| Chains the protocol will be deployed on | Arbitrum,Base,Optimism |
```

From the above, we can conclude that protocol is to deploy on optimistic L2 chains where re-orgs occur quite often and we have to factor in the issue with the sequencer being down for a while.

Currently, protocol also implements a liquidating logic, which is present here: https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/logic/LiquidationLogic.sol#L39

Issue however is that this logic and all the routes it takes via the `checkVaultIsDanger()` and then `Position.isLiquidatable()` only checks for vault's current status in regards to it's liquidatable state without giving the users quite a minute duration to get their positions back afloat in the case the sequencer was down when they became liquidatable.

Note that it is quite a common logic in DEFI to provide users with some time in the case where they actually become liquidatable when the sequencer was down, even the popular AAVE, has a [Price Oracle Sentinel](https://github.com/aave-dao/aave-v3-origin/blob/38e7cfb49069837fae99750d8db37f19735fedd7/src/core/contracts/protocol/configuration/PriceOracleSentinel.sol#L71-L74) set that checks for the sequencer being up or down and provide users with grace periods when they become liquidatable... more can be seen from the [Aave V3 Technical Paper](https://github.com/aave/aave-v3-core/blob/master/techpaper/Aave_V3_Technical_Paper.pdf).

However in Predy's case, this is not being taken into account, this then leaves users to be unfairly liquidated

## Impact

Unfair liquidation of users since they are not given a short grace period once the sequencer comes back up.

> NB: Note that although there is a subtle possibility of passing in the transactions via the delayed inbox, not only is this _technically_ not available to all users it also doesn't solve the issue cause if transactions are passed via the delayed inbox, the sequencer only includes the message from the inbox after a delay of ~ 10 minutes [(if not more)](https://zerocap.com/insights/research-lab/arbitrum-arb-deep-dive/#:~:text=An%20honest%20sequencer) when it comes back up which is so as to ensure that the transaction/message’s arrival will not be affected by a reorganisation of the base layer chain... which would mean that the positions are still susceptible to being unfairly liquidated even if the users try their best on having their positions afloat.

## Recommended Mitigation Steps

Consider integrating a check to see if the sequencer is down, if yes then block off some core functionalities, in the case where the sequencer is up, then check for how long it's been up for, set a `grace period` value and ensure that this grace period duration has passed before allowing back access to these core functionalities.
