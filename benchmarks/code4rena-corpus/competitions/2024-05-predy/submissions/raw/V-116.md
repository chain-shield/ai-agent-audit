This function is used to check a vault's safety status and also get the slippage tolerance, to do this it uses the helper function to achieve it's goal `PositionCalculator.isLiquidatable()` whose implementation just checks if the position is indeed liquidatable or not as the name suggests and does this [by checking if the vault value is greater than the minMargin returned by the `calculateMinMargin()`](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/PositionCalculator.sol#L41).

## Impact

`PositionCalculator.isLiquidatable()` is going to use wrong price data to validate the liquidatable state of a position which bubbles back up to `LiquidationLogic#checkVaultIsDanger()` wrongly indicating that vault is in danger whereas it's not or [reverting, claiming that a vault is not in danger](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/logic/LiquidationLogic.sol#L145) where as it is... which showcases how protocol's core logic is broken.

> Would be key to note that the `LiquidationLogic#checkVaultIsDanger` is always called whenever [there is a need to liquidate](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/logic/LiquidationLogic.sol#L57-L58) which would mean that the implementation of the function being wrong would mean the liquidation logic is also broken.

## Recommended Mitigation Steps

Consider shortening the TWAP duration to as low as 5 minutes, this is because, this way the price is not going to be lagging and we can ensure the right status of a vault in regards to it's danger status is going to be reported
