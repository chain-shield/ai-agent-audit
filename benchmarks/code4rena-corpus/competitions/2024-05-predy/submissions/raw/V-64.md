# Vulnerability details

## Impact
The protocol is using `block.timestamp` as the `deadline` argument while performing swaps, which completely defeats the purpose of using a `deadline`.

Failure to provide a proper `deadline` value enables pending transactions to be maliciously executed at a later point. Transactions that provide an insufficient amount of gas such that they are not mined within a reasonable amount of time, can be picked by `malicious actors` or `MEV` bots and executed later in detriment of the submitter.

Using `block.timestamp` as the `deadline` is effectively a no-operation that has no effect nor protection. Since `block.timestamp` will take the timestamp value when the transaction gets mined, the check will end up comparing `block.timestamp` against the same value.

See [this](https://github.com/Uniswap/v3-periphery/blob/697c2474757ea89fec12a4e6db16a574fe259610/contracts/base/PeripheryValidation.sol#L7).

## Tools Used
Manual Review

## Recommended Mitigation Steps
Include a check to ensure that the current `block.timestamp` is less than or equal to the `deadline` specified in the parameters. If the current timestamp is greater than the `deadline`, the function should `revert` the transaction.
