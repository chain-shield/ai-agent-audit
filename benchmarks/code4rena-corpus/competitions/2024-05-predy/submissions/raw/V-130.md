# Vulnerability details


## Proof of Concept

Take a look at https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpMarketLib.sol#L138-L177

```solidity
    function validateStopPrice(
        uint256 oraclePrice,
        uint256 tradePrice,
        int256 tradeAmount,
        uint256 stopPrice,
        bytes memory auctionData
    ) internal pure returns (bool) {
        AuctionParams memory auctionParams = abi.decode(auctionData, (AuctionParams));

        uint256 decayedSlippageTorelance = DecayLib.decay2(
            auctionParams.startPrice,
            auctionParams.endPrice,
            auctionParams.startTime,
            auctionParams.endTime,
            ratio(oraclePrice, stopPrice)
        );

        if (tradeAmount > 0) {
            // buy
            if (stopPrice > oraclePrice) {
                return false;
            }

            if (tradePrice > Bps.upper(oraclePrice, decayedSlippageTorelance)) {
                return false;
            }
        } else if (tradeAmount < 0) {
            // sell
            if (stopPrice < oraclePrice) {
                return false;
            }

            if (tradePrice < Bps.lower(oraclePrice, decayedSlippageTorelance)) {
                return false;
            }
        }

        return true;
    }

```

This function is used to validate the stop prices and is expected to revert in the case where the [trade price is higher than `Bps.upper(oraclePrice, decayedSlippageTorelance)) `](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpMarketLib.sol#L161) in the case of buy, alternatively in the case of a sell order the function is expected to revert when [trade price is lower than `Bps.lower(oraclePrice, decayedSlippageTorelance)) `](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpMarketLib.sol#L170)/

Issue however is that protocol implements the `decayedSlippageTorelance` logic somewhat not so safe, this is because the way the [ratio that's attached to the call to `decay2` ](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpMarketLib.sol#L147-L153) is being gotten has a disparity since not in all instances are sure that `oraclePrice < stopPrice` or `oraclePrice > stopPrice` is going to hold true. See https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpMarketLib.sol#L178-L187

```solidity
    function ratio(uint256 price1, uint256 price2) internal pure returns (uint256) {
        if (price1 == price2) {
            return 0;
        } else if (price1 > price2) {
            return (price1 - price2) * Bps.ONE / price2;
        } else {
            return (price2 - price1) * Bps.ONE / price2;
        }
    }

```

Evidently, `price2` is always the denominator, whether it's higher or not, that's to say in some cases, since the value returned from this function is used to get `decayedSlippageTorelance`, the value would be over/undervalued, this is because, assume to rough math cases:

- First case, Price1 = 100, price2 = 150, the ratio returned would be`((150-100) * Bps.ONE / 150)` ~= 3333, however
- Second case, Price1 = 150, price2 = 100, the ratio returned would be`((150-100) * Bps.ONE / 100)` = 5000,
  > These are obviously the same prices but see how much they differ when they undergo the `ratio`.

Now that's to say we can conclude due to this disparity in how the ratio is being gotten, the [data returned from `DecayLib.decay2()` ](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpMarketLib.sol#L148-L153) is going to be so different for pretty much the same case, and this essentially leads to the validation to fail for one of the instance and not for the other in [this section](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpMarketLib.sol#L161-L173) depending on the `tradePrice`, which is because the call to either of to `Bps` only multiplies/divides the value of the `price` by the `decayedSlippageTorelance` which would be different in two same cases.

## Impact

Protocol unintentionally implements a disparsed method when validating the spot prices, since the same prices, just depending on if being `price1` or `price2` would lead to a revert in one of the cases.

## Recommended Mitigation Steps

Consider reimplementing the logic on how to get the slippage. That is either always use the lower price as the denominator or always use the higher price as the denominator, this way no matter what `price1` or `price2` is the execution of the validation of the spot prices functions the same.
