# Vulnerability details

## Description of the Issue
[GammaTradeMarket:execLiquidationCall](https://github.com/code-423n4/2024-05-predy/blob/e96f378007e3dc56b184079f0c0e4fe48a72efaa/src/markets/gamma/GammaTradeMarket.sol#L138-L149) is responsible for executing the liquidation of a vault (position) in the Predy Pool. The function takes three parameters:
```solidity
>>      uint256 vaultId,
>>      uint256 closeRatio,
>>      IFillerMarket.SettlementParamsV3 memory settlementParams
    ) external override returns (IPredyPool.TradeResult memory tradeResult) {
>>      tradeResult =
>>          _predyPool.execLiquidationCall(vaultId, closeRatio, _getSettlementDataFromV3(settlementParams, msg.sender));


>>      if (closeRatio == 1e18) {
>>          _removePosition(vaultId);
        }
    }
```
`vaultId`: The ID of the vault to be liquidated.
`closeRatio`: The ratio (between 0 and 1e18) indicating the percentage of the vault to be liquidated.
`settlementParams`: Settlement parameters required for the liquidation process.
```solidity
            _predyPool.execLiquidationCall(vaultId, closeRatio, _getSettlementDataFromV3(settlementParams, msg.sender));


        if (closeRatio == 1e18) {
            _removePosition(vaultId);
        }
```
The function first calls `_predyPool.execLiquidationCall` with the provided parameters to execute the liquidation. After this call, it checks if `closeRatio` is equal to `1e18` (100%), and if so, it removes the position by calling `_removePosition(vaultId)`.

## Impact
The issue arises when the `_predyPool.execLiquidationCall` function fails or reverts for any reason. In such a case, the position should still be removed if `closeRatio` is set to `1e18`, indicating a full liquidation. However, here's the catch, due to the order of operations in the current implementation, the position removal step is executed after the liquidation call, which means that if the liquidation call fails, the position will not be removed, even if `closeRatio` is set to `1e18`, and this can lead to several issues which are:-

**`Inconsistent State`** If the liquidation call fails, but the position is not removed, the system can end up in an inconsistent state where a vault is marked for liquidation but still exists in the system.

**`Stuck Funds`** If the position is not removed after a failed liquidation attempt, the funds associated with that position may become stuck or inaccessible, leading to potential fund loss or denial of service.

**`Incorrect Accounting`** The failure to remove the position after a failed liquidation attempt can lead to incorrect accounting of positions, margins, and other related data in the system, potentially causing further issues down the line.

## Recommended Mitigation Steps
The order of operations should be reversed. First, check `if closeRatio == 1e18`, and if so, remove the position using `_removePosition(vaultId)`. Then, call `_predyPool.execLiquidationCall` to execute the liquidation.
```solidity
function execLiquidationCall(
    uint256 vaultId,
    uint256 closeRatio,
    IFillerMarket.SettlementParamsV3 memory settlementParams
) external override returns (IPredyPool.TradeResult memory tradeResult) {
    if (closeRatio == 1e18) {
        _removePosition(vaultId);
    }

    tradeResult = _predyPool.execLiquidationCall(
        vaultId,
        closeRatio,
        _getSettlementDataFromV3(settlementParams, msg.sender)
    );
}
```
By making this change, the position will be removed first if `closeRatio` is set to `1e18`, ensuring that the position is always removed before executing the liquidation call. This way, even if the liquidation call fails or reverts, the position will still be removed as intended.
