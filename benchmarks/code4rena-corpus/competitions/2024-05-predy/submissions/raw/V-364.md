# Vulnerability details

## Impact
Currently the `PriceFeed` contract has a VALID_TIME_PERIOD for staleness check as below

```javascript
uint256 private constant VALID_TIME_PERIOD = 5 * 60;
```

However, in the current implementation there are no checks for the VALID_TIME_PERIOD that prevents staleness in the chainlink operation,
This oversight poses a significant risk of utilizing stale price data, potentially leading to incorrect calculations and financial implications for the protocol.

```javascript
function getSqrtPrice() external view returns (uint256 sqrtPrice) {
        (, int256 quoteAnswer,,,) = AggregatorV3Interface(_quotePriceFeed).latestRoundData();

        IPyth.Price memory basePrice = IPyth(_pyth).getPriceNoOlderThan(_priceId, VALID_TIME_PERIOD);

        require(basePrice.expo == -8, "INVALID_EXP");

        require(quoteAnswer > 0 && basePrice.price > 0);

        uint256 price = uint256(int256(basePrice.price)) * Constants.Q96 / uint256(quoteAnswer);
        price = price * Constants.Q96 / _decimalsDiff;

        sqrtPrice = FixedPointMathLib.sqrt(price);
    }
```

chainlink also has its own heartbeat which should be employed to avoid staleness,

however, ensure the VALID_TIME_PERIOD is not a constant but add them in a mapping because there are different heartbeats for different priceFeed

## Recommended Mitigation Steps
To address this issue, it is recommended to implement staleness checks for the Chainlink price feed data within the `getSqrtPrice` function. This can be achieved by defining a maximum staleness threshold for Chainlink data and validating the recency of the price update before using it in calculations. Remember to use different heartbeats for different priceFeeds.
