# Vulnerability details

## Impact
Since the token prices are used in many contracts from executing a order to liquidation, stale data could be catastrophic for the project.

## Proof of Concept
The PriceFeed.getSqrtPrice() function is used to get the price of base tokens, the problem is that the function does not check for necesaary round or timestamp checks and directly delegates them for price calculation with the pyth oracle returned price. So if the pyth oracle returned price is ok but chainlink has stale results the overall price display would be wrong The protocol uses chainlink for fetching the prices of quote tokens.

This omission can lead to issues if Chainlink starts a new round and struggles to establish consensus on the new value for the oracle. Without proper checks, consumers of this contract may continue using outdated, stale, or incorrect data if oracles are unable to submit and start a new round. Possible reasons for this could include Chainlink nodes abandoning the oracle, chain congestion, or vulnerabilities/attacks on the Chainlink system.


Also When using Chainlink with L2 chains like Arbitrum, smart contracts must check whether the L2 Sequencer is down to avoid stale pricing data that appears fresh - Chainlink’s official documentation provides an example implementation. 

## Tools Used
Chainlink

## Recommended Mitigation Steps
Read the updatedAt return value from the Chainlink.latestRoundData() function and verify that is not older than than specific time tolerance.
```
require(block.timestamp - udpatedData < toleranceTime, "stale price");
```
Additionaly also add the check for roundId 
```
require(answeredInRound >= roundId, "Stale price");
```

And for L2 sequencer check the official chainlink docs [here](https://docs.chain.link/data-feeds/l2-sequencer-feeds#example-code)
