# Vulnerability details

## Impact
The absence of a proper removal mechanism for Uniswap pools from the `allowedUniswapPools` mapping can lead to excessive gas consumption and potential out-of-gas errors. As the number of entries in the mapping grows over time without the ability to remove outdated or unnecessary entries, gas costs for interactions involving this mapping will increase. This mismanagement could eventually render certain operations prohibitively expensive or impossible due to gas limitations, causing disruptions and reducing the contract's usability and efficiency.

The impact of this issue can manifest in the following ways:
1. Increased gas costs for functions that interact with the `allowedUniswapPools` mapping, such as `uniswapV3MintCallback`.
2. Risk of out-of-gas errors when executing functions that involve iterating over or checking the `allowedUniswapPools` mapping, potentially causing transaction failures and disrupting normal contract operations.
3. Gradual degradation of contract performance and responsiveness as the mapping size grows unchecked.
4. Difficulty in managing and maintaining the list of allowed Uniswap pools, as there is no way to remove pools that are no longer needed or relevant.


The issue lies in the absence of a mechanism to remove Uniswap pools from the `allowedUniswapPools` mapping. Here's the relevant code snippet from the `PredyPool` contract that illustrates the potential problem:

### Affected Code Snippet
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.17;

// ... [imports]

contract PredyPool is IPredyPool, IUniswapV3MintCallback, Initializable, ReentrancyGuardUpgradeable {
    // ... [state variables and modifiers]

    mapping(address => bool) public allowedUniswapPools;

    // ... [constructor and initializer]

    /// @dev Callback for Uniswap V3 pool.
    function uniswapV3MintCallback(uint256 amount0, uint256 amount1, bytes calldata) external override {
        // Only the uniswap pool has access to this function.
        require(allowedUniswapPools[msg.sender]);

        IUniswapV3Pool uniswapPool = IUniswapV3Pool(msg.sender);

        if (amount0 > 0) {
            ERC20(uniswapPool.token0()).safeTransfer(msg.sender, amount0);
        }
        if (amount1 > 0) {
            ERC20(uniswapPool.token1()).safeTransfer(msg.sender, amount1);
        }
    }

    // ... [other functions]
}
```

### Proof of Concept:
1. Over time, the `allowedUniswapPools` mapping accumulates a large number of entries as new pools are added.
2. Without a removal mechanism, old or unused Uniswap pools remain in the mapping, increasing the size and gas cost of operations that interact with this mapping.
3. Eventually, the gas cost becomes so high that certain functions, such as `uniswapV3MintCallback`, risk running out of gas during execution, causing failures and disruptions.

### Scenario:
Consider the scenario where the contract owner adds many Uniswap pools over time but never removes any:

```solidity
// Example of continuously adding pools without removal
allowedUniswapPools[poolAddress1] = true;
allowedUniswapPools[poolAddress2] = true;
// ... many more additions
allowedUniswapPools[poolAddressN] = true;
```

Without a removal mechanism, each call to `uniswapV3MintCallback` involves checking a potentially very large mapping, increasing the gas cost and risking out-of-gas errors.

## Recommended Mitigation Steps
To mitigate this issue, it is recommended to implement the following:

1. Add a function to remove Uniswap pools from the `allowedUniswapPools` mapping. This function should be accessible only to the contract operator.

```solidity
/**
 * @notice Removes a Uniswap pool, preventing it from accessing the callback function.
 * @dev Only the operator can call this function.
 * @param pool The address of the Uniswap pool to remove.
 */
function removeUniswapPool(address pool) external onlyOperator {
    require(allowedUniswapPools[pool], "Pool is not currently enabled");
    delete allowedUniswapPools[pool];
}
```
