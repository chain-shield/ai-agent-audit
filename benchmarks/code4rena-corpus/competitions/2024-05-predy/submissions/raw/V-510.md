# Vulnerability details

## Root of the bug 

The vulnerability is arises when a contract grants token approval without resetting the previous allowance to zero and  This issue is occurs, where the functions approve a certain amount of tokens for the swap router but do not reset any existing approvals. And  This can lead to the approved amount accumulating over time, creating a vulnerability that malicious actors can exploit to transfer more tokens than intended.
Here is the Function swapExactIn

```solidity

function swapExactIn(
    address,
    address baseToken,
    bytes memory data,
    uint256 amountIn,
    uint256 amountOutMinimum,
    address recipient
) external override returns (uint256 amountOut) {
    ERC20(baseToken).safeTransferFrom(msg.sender, address(this), amountIn);
    ERC20(baseToken).approve(address(_swapRouter), amountIn);  <—— Vulnerable line

    amountOut = _swapRouter.exactInput(
        ISwapRouter.ExactInputParams(data, recipient, block.timestamp, amountIn, amountOutMinimum)
    );
}
```
In the function swapExactOut

```Solidity 

function swapExactOut(
    address quoteToken,
    address,
    bytes memory data,
    uint256 amountOut,
    uint256 amountInMaximum,
    address recipient
) external override returns (uint256 amountIn) {
    ERC20(quoteToken).safeTransferFrom(msg.sender, address(this), amountInMaximum);
    ERC20(quoteToken).approve(address(_swapRouter), amountInMaximum);  <—- Vulnerable part

    amountIn = _swapRouter.exactOutput(
        ISwapRouter.ExactOutputParams(data, recipient, block.timestamp, amountOut, amountInMaximum)
    );

    if (amountInMaximum > amountIn) {
        ERC20(quoteToken).safeTransfer(msg.sender, amountInMaximum - amountIn);
    }
}

```
It’s that the failure to clear previous token approvals, causing cumulative approvals that can be exploited
## Impact

The over-approval is can lead to unauthorized token transfers, allowing an attacker to repeatedly drain funds from the contract, and  resulting  financial losses for users.

## Proof of Concept
The Uniswap documentation is recommends that contracts should generally reduce the approved allowance to zero before setting a new approval to avoid over-approval issues here 
```solidity
// First reduce the spender's allowance to 0 and then set the desired value:
token.approve(spender, 0);
token.approve(spender, amount);
This prevents lingering approval that might be exploited
```
As scenario of attack : 
- Let’s that Alice has 1000 tokens of BaseToken and 1000 tokens of QuoteToken so The UniswapSettlement contract and a UniswapRouter are set up to facilitate token swaps.
- so  Alice performs a swap using swapExactIn with an initial approval.
- and the  contract approves tokens without resetting previous allowances.
An attacker exploits the remaining approval for unauthorized transactions.
- Alice wants to swap 500 BaseToken for at least 475 tokens of another asset using swapExactIn, Alice transfers 500 BaseToken to the contract.
- The contract approves 500 tokens for the UniswapRouter without resetting any previous approval as result Alice receives 475 tokens and 
The approval of 500 tokens remains active
- now The attacker notices that the approval for BaseToken is still 500 tokens.
- And They can use this approval to initiate a transfer using the UniswapRouter, potentially transferring all 500 tokens that Alice approved, without her knowledge.
- The attacker call a function that utilizes the lingering approval to transfer the remaining tokens
- Alice now wants to swap for an exact amount using swapExactOut. She sets a maximum of 500 QuoteToken
- Alice transfers 500 QuoteToken to the contract.
The contract approves 500 tokens for the UniswapRouter without resetting any previous approval
- Alice swaps her tokens as intended.
- The approval for 500 tokens remains active, and if not fully used, can be exploited similarly
## Tools Used
Manual review 
## Recommended Mitigation Steps
It’s need to modify the swapExactIn and swapExactOut functions to reset the approval to zero before setting a new approval amount
