# Vulnerability details

[PredyPool::supply()](https://github.com/code-423n4/2024-05-predy/blob/main/src/PredyPool.sol#L222C4-L228C6) is used by lenders to provide liquidity either as `quoteToken` or as `baseToken` to the lending pool. In return, they receive bond tokens, which are shares of the pool. The problem is that this function is susceptible to the [Inflation Attack](https://mixbytes.io/blog/overview-of-the-inflation-attack), in which the first depositor can be front-runned by an attacker to steal their deposit.

## Impact

[PredyPool](https://github.com/code-423n4/2024-05-predy/blob/main/src/PredyPool.sol) acts as a vault: accounts deposit some tokens and get back another token (share) that represents their participation in the vault.

These types of contracts are potentially vulnerable to the inflation attack: an attacker can front-run the initial deposit to the vault to inflate the value of a share and render the front-runned deposit worthless.

In this contract, no validation is done in the number of minted tokens. This means that an attacker can execute the attack by front-running the initial deposit. See *Proof of Concept* for a detailed walkthrough of the issue.

## Proof of Concept

The flow is as follows:

- A user registers a new trading pair by calling [PredyPool::registerPair()](https://github.com/code-423n4/2024-05-predy/blob/main/src/PredyPool.sol#L109C4-L111C6).
- To supply liquidity to the newly created pool, the user calls [PredyPool::supply()](https://github.com/code-423n4/2024-05-predy/blob/main/src/PredyPool.sol#L222C4-L228C6) providing the pool's `pairId` and the desired `supplyAmount`.
- This triggers [SupplyLogic::supply()](https://github.com/code-423n4/2024-05-predy/blob/main/src/libraries/logic/SupplyLogic.sol#L22C4-L44C6), which in turn calls [SupplyLogic::receiveTokenAndMintBond()](https://github.com/code-423n4/2024-05-predy/blob/main/src/libraries/logic/SupplyLogic.sol#L46C3-L55C6) These functions work together to mint `bond tokens` to the user and adding liquidity to the pool.

Imagine the following scenario:

1. Bob creates a new trading pair by calling  [PredyPool::registerPair()](https://github.com/code-423n4/2024-05-predy/blob/main/src/PredyPool.sol#L109C4-L111C6).

2. Bob initiates a transaction using [PredyPool::supply()](https://github.com/code-423n4/2024-05-predy/blob/main/src/PredyPool.sol#L222C4-L228C6). He provides the pool's `pairId` and intends to supply `5 WETH` (5e18 worth of tokens). This transaction gets added to the public mempool, which is a temporary storage area for pending transactions.

3. Alice has been monitoring the mempool for profitable opportunities. She sees Bob's transaction and decides to frontrun it. Frontrunning refers to exploiting the fact that transactions aren't processed instantly. Alice submits two transactions before Bob's:

- A [PredyPool::supply()](https://github.com/code-423n4/2024-05-predy/blob/main/src/PredyPool.sol#L222C4-L228C6) call with a minimal amount (`1 wei`) to establish herself as the first liquidity provider. This small contribution grants her a tiny share of the pool.
- A direct transfer of `10 WETH` (10e18 worth of tokens) to the pool contract.

4. Since Alice was the first to call [PredyPool::supply()](https://github.com/code-423n4/2024-05-predy/blob/main/src/PredyPool.sol#L222C4-L228C6), even with a minimal amount, she gets priority in share allocation. This means Bob receives 0 `bond tokens` even though he supplied `5 WETH`.

5. After successfully frontrunning Bob for `bond tokens`, Alice can now withdraw her contributions. She initiates another transaction to withdraw her initial `1 wei`. However, due to the way the pool contract is designed, Alice might be able to withdraw not only his `1 wei` but also Bob's whole deposit.

This can be replayed multiple times until the depositors notice the problem

The first depositor can be front run by an attacker and as a result will lose a considerable part of the shares provided.

## Recommended Mitigation Steps

UniswapV2 fixed this with two types of protection:

[First](https://github.com/Uniswap/v2-core/blob/master/contracts/UniswapV2Pair.sol#L119-L121), on the first mint it actually mints the first 1000 shares to the zero address.

[Second](https://github.com/Uniswap/v2-core/blob/ee547b17853e71ed4e0101ccfd52e70d5acded58/contracts/UniswapV2Pair.sol#L125), it requires that the minted shares are not 0.

Implementing them both will resolve this vulnerability.
