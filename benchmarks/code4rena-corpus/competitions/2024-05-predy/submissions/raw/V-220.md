# Vulnerability details

## Impact
The impact is that the `calculateSlippageTolerance` function may return incorrect slippage tolerance values when `currentTime` is less than `startTime`. This can lead to unexpected behavior in the system that relies on accurate slippage tolerance calculations.

Here in this code, the elapsed variable is calculated as follows: [GammaTradeMarketLib#calculateSlippageTolerance#L150](https://github.com/code-423n4/2024-05-predy/blob/e96f378007e3dc56b184079f0c0e4fe48a72efaa/src/markets/gamma/GammaTradeMarketLib.sol#L150)
```solidity
uint256 elapsed = (currentTime - startTime) * Bps.ONE / auctionParams.auctionPeriod;
```
The problem arises when `currentTime` is less than `startTime`. In Solidity, unsigned integer types (like `uint256`) are used to represent non-negative integers. When an underflow occurs (i.e., the result of an operation is less than the minimum value for the type), the value "wraps around" to the maximum value for that type.

For example, if `currentTime` is 1 and `startTime` is 2, the subtraction `currentTime - startTime` will result in an underflow, and the value of elapsed will be a very large number (close to the maximum value of `uint256`).

To illustrate the underflow behavior
```solidity
pragma solidity ^0.8.0;

contract UnderflowExample {
    function testUnderflow() public pure returns (uint256) {
        uint256 a = 1;
        uint256 b = 2;
        return b - a; // This will underflow and return a very large value
    }
}
```
In the `testUnderflow` function, `b - a` will underflow because `2 - 1` is less than the minimum value for `uint256` (which is 0). The result will be a very large value (close to the maximum value of `uint256`).

Now, let's consider the impact of this underflow in the `calculateSlippageTolerance` function. If elapsed becomes a very large value due to the underflow, the subsequent calculations will be incorrect. Specifically, the condition `elapsed > Bps.ONE` will always be true, and the function will always return `auctionParams.maxSlippageTolerance`, even when it should return a value between `minSlippageTolerance` and `maxSlippageTolerance`.

## Recommended Mitigation Steps
Should first check if `currentTime` is greater than `startTime` before performing the subtraction
```solidity
function calculateSlippageTolerance(uint256 startTime, uint256 currentTime, AuctionParams memory auctionParams)
    internal
    pure
    returns (uint256)
{
    if (currentTime <= startTime) {
        return auctionParams.minSlippageTolerance;
    }

    uint256 elapsedTime = currentTime - startTime;
    uint256 elapsed = elapsedTime * Bps.ONE / auctionParams.auctionPeriod;

    if (elapsed > Bps.ONE) {
        return auctionParams.maxSlippageTolerance;
    }

    return (
        auctionParams.minSlippageTolerance
            + elapsed * (auctionParams.maxSlippageTolerance - auctionParams.minSlippageTolerance) / Bps.ONE
    );
}
```
In the above update we first check if `currentTime` is less than or equal to `startTime`, and if so, return the `minSlippageTolerance`. Otherwise, we calculate `elapsedTime` as `currentTime - startTime`, ensuring that the subtraction will not underflow. Then, we proceed with the original calculations using `elapsedTime`.
