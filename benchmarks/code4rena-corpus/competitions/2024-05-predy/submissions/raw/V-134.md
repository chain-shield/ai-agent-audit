# Vulnerability details

## Impact
The `supply()` and `withdraw()` functions allows a `lender` to supply/withdraw either the `quoteToken` or the `baseToken` to/from the lending pool. During  supply, `bond` tokens are minted for the `lender` and during withdrawa, these tokens get burned in the process.

However, the protocol does not implement any measures to prevent supply and withdrawals within the same `block` which offers an easy path for `flash-loan` attack.

An `attacker` is able to use a `flash loan` to manipulate the price of a token supplied to the pool and then withdraw a different asset at an advantageous rate due to the manipulated price.

## Proof of Concept
1. The attacker starts by obtaining a flash loan of Token A (`quoteToken`) from a lending platform that offers such loans.
2. The attacker calls the [supply()](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/PredyPool.sol#L222-L228) function with the borrowed Token A.
```solidity
function supply(uint256 pairId, bool isQuoteAsset, uint256 supplyAmount)
    external
    nonReentrant
    returns (uint256 finalSuppliedAmount)
{
    return SupplyLogic.supply(globalData, pairId, supplyAmount, isQuoteAsset);
}
```
3. Perform actions that manipulate the pool's state or token prices to inflate the value of bond tokens. This could involve:
- Manipulating the Uniswap pool prices.
4. With the inflated price of `bond` tokens, the attacker uses the [withdraw()](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/PredyPool.sol#L237-L243) function to withdraw Token B(`baseToken`), which has not been manipulated.
```solidity
function withdraw(uint256 pairId, bool isQuoteAsset, uint256 withdrawAmount)
    external
    nonReentrant
    returns (uint256 finalBurnAmount, uint256 finalWithdrawAmount)
{
    return SupplyLogic.withdraw(globalData, pairId, withdrawAmount, isQuoteAsset);
}
```
5. The attacker sells the withdrawn Token B on the open market at its actual value.
Before the end of the transaction, the attacker repays the flash loan with Token A, completing the exploit.

The issue here is that the protocol does not have any mechanisms in place to prevent the manipulation of the collateral's price.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Introduce a mechanism that enforces a minimum number of blocks between critical actions such as supplying collateral and withdrawing assets.

```solidity
mapping(address => uint256) public lastSupplyBlock;
uint256 public minBlockDelay;

// @audit Update the supply() function to record the current block number:
function supply(uint256 pairId, bool isQuoteAsset, uint256 supplyAmount) 
    external  
    nonReentrant 
    returns (uint256 finalSuppliedAmount) 
{
    // Record the block number when the user supplies collateral
    lastSupplyBlock[msg.sender] = block.number;
    // ...
}

// @audit Modify the withdraw() function to check if a certain number of blocks have passed since the last supply:
function withdrawCollateral(uint256 pairId, bool isQuoteAsset, uint256 withdrawAmount) 
    external 
    nonReentrant 
    returns (uint256 finalBurnAmount, uint256 finalWithdrawAmount) 
{

    // Ensure the minimum block delay has passed since the last supply action
    require(block.number >= lastSupplyBlock[msg.sender] + minBlockDelay, "Min block delay not passed");
    // ... (existing code)
}

// @audit Add a state variable for the minimum block delay and a function to set it (only callable by the contract owner or admin):
function setMinBlockDelay(uint256 _minBlockDelay) external onlyOwner {
    minBlockDelay = _minBlockDelay;
}
```
This approach ensures that there is a mandatory waiting period between when tokens are supplied and when they can be withdrawn, reducing the risk of flash loan price manipulation within a single transaction.
