# Vulnerability details

## Impact

The price feed hardcodes the valid time period to about 300 seconds which is bad for two reasons.
1. The hardocded value is incorrect for arbitrum, too large, allowing for stale prices to be used. 
2. Considering that the protocol aims to deploy to different chains, the pyth declared valid time period for the chains can be different, and hardcoding risks beiung too small on certain chains and too large on others which can lead to a host of unexpected behaviours.

Use of stale prices risks the protocol working with incorrect pricing will affect a lot of the protocol operations.

## Proof of Concept
From PriceFeed.sol, the valid time period is hardcoded to `5 * 60`;
```solidity
  uint256 private constant VALID_TIME_PERIOD = 5 * 60; 
```

This is then used to in the `getSqrtPrice` function, in  `getPriceNoOlderThan` functions.

```solidity
    function getSqrtPrice() external view returns (uint256 sqrtPrice) {
        (, int256 quoteAnswer,,,) = AggregatorV3Interface(_quotePriceFeed).latestRoundData();

        IPyth.Price memory basePrice = IPyth(_pyth).getPriceNoOlderThan(_priceId, VALID_TIME_PERIOD);
    .......
```

However, the hardcoded valid time period is too large for arbitrum. According to pyth [docs](https://docs.pyth.network/price-feeds/api-reference/evm/configuration), the valid time period for arbitrum is 60 seconds.

Also according to the getprice [evm reference](https://github.com/pyth-network/documentation/blob/f9e61d6948a2142888550117e5023bc6479219f9/pages/price-feeds/api-reference/evm/get-price.mdx#get-price)

> This function reverts with a StalePrice error if the on-chain price has not been updated within the last getValidTimePeriod() seconds. The default valid time period is set to a reasonable default on each chain and is typically around 1 minute.

This means that price updates later than the reasonable default of 60 seconds will be accepted which will already be stale. This is used to get the `sqrtPrice` in the `getSqrtPrice` function. The function is extensively in the protocol to calculate `getSqrtIndexPrice` and to [calculate min margin](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/PositionCalculator.sol#L75) which helps check for a position's liquidatable state. It's also used in gamma market to [`autoHedge`](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/gamma/GammaTradeMarket.sol#L237), [`autoClose`](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/gamma/GammaTradeMarket.sol#L286) and to do [both](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/gamma/GammaTradeMarket.sol#L346). It's also used in [PerpMarketV1 contract](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpMarketV1.sol#L227)

Also, as the protocol aims to deploy on Arbitrum, Base, Optimism, the hardcoded value might be too low for Base and Optimism(no concrete info could be found). This will cause unexpected reversions as price updates time are much higher than the hardcoded time, thus causing actual valid prices to be rejected as being stale.
