# Vulnerability details

## Impact
`SettlementCallbackLib.execSettlement`, The code checks if `settlementParams.fee` is less than 0, and if so, it transfers the absolute value of `settlementParams.fee` from the `settlementParams.sender` to the `predyPool` contract but the code does not handle the case where `settlementParams.fee` is greater than 0.

If `settlementParams.fee` is positive, the code should transfer the fee amount from the predyPool contract to the `settlementParams.sender`. The current implementation does not perform this transfer, which could lead to a loss of funds or an incorrect fee calculation.

**`Loss of funds`** If a positive fee is expected to be paid to the `settlementParams.sender`, the lack of a transfer mechanism means that the sender will not receive the fee they are entitled to. _This can lead to a loss of funds for the sender._

**`Incorrect fee calculation`** If the fee is intended to be paid to the `settlementParams.sender` for certain types of settlements, the absence of a transfer mechanism can lead to an incorrect fee calculation or an inconsistent fee structure.

**`Violation of contract logic`** The contract's logic may assume that fees are properly transferred between the involved parties. If this assumption is violated, it can lead to unexpected behavior or inconsistencies in the contract's state.

The issue lies in the [SettlementCallbackLib.execSettlement](https://github.com/code-423n4/2024-05-predy/blob/2fb1e0ec7a52fc06c2e9c8e561bccba84302e4bb/src/base/SettlementCallbackLib.sol#L40-L58), specifically in the handling of the `settlementParams.fee` value. 
```solidity
function execSettlement(
    IPredyPool predyPool,
    address quoteToken,
    address baseToken,
    SettlementParams memory settlementParams,
    int256 baseAmountDelta
) internal {
    if (settlementParams.fee < 0) {
        ERC20(quoteToken).safeTransferFrom(
            settlementParams.sender, address(predyPool), uint256(-settlementParams.fee)
        );
    }

    execSettlementInternal(predyPool, quoteToken, baseToken, settlementParams, baseAmountDelta);

    // Missing code to handle positive settlementParams.fee
}
```
We can see, that the code only handles the case where `settlementParams.fee` is less than 0. In this case, it transfers the absolute value of `settlementParams.fee` from the `settlementParams.sender` to the `predyPool` contract.

There is no code to handle the case where `settlementParams.fee` is greater than 0. This means that if a positive fee is expected to be paid to the `settlementParams.sender`, the code will not perform the necessary transfer, leading to the potential issues mentioned above.

## Proof of Concept
A settlement is initiated with `settlementParams.fee` set to a positive value, let's say 100.
The `execSettlement` function is called with these parameters.
The code executes the `if` block for negative fees, but since the fee is positive, it skips this block.
The `execSettlementInternal` function is called, but there is no code to handle the positive fee.
The function completes without transferring the fee of 100 from the `predyPool` contract to the `settlementParams.sender`.

In this scenario, the `settlementParams.sender` does not receive the fee they are entitled to, resulting in a loss of funds or an incorrect fee calculation.

## Recommended Mitigation Steps
Add an additional `else` block to handle the case where `settlementParams.fee` is greater than 0
```solidity
if (settlementParams.fee < 0) {
    ERC20(quoteToken).safeTransferFrom(
        settlementParams.sender, address(predyPool), uint256(-settlementParams.fee)
    );
} else if (settlementParams.fee > 0) {
    predyPool.take(true, settlementParams.sender, uint256(settlementParams.fee));
}
```
