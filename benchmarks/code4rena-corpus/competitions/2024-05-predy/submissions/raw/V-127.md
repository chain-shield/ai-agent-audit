# Vulnerability details


## Proof of Concept

Take a look at https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpMarketV1.sol#L102-L142

```solidity
    function predyTradeAfterCallback(
        IPredyPool.TradeParams memory tradeParams,
        IPredyPool.TradeResult memory tradeResult
    ) external override(BaseHookCallbackUpgradable) onlyPredyPool {
        CallbackData memory callbackData = abi.decode(tradeParams.extraData, (CallbackData));
        ERC20 quoteToken = ERC20(_getQuoteTokenAddress(tradeParams.pairId));

        if (callbackData.callbackSource == CallbackSource.QUOTE) {
            _revertTradeResult(tradeResult);
        } else if (callbackData.callbackSource == CallbackSource.QUOTE3) {
            _revertTradeResult(tradeResult);
        } else if (callbackData.callbackSource == CallbackSource.TRADE3) {
            int256 marginAmountUpdate =
                _calculateInitialMargin(tradeParams.vaultId, tradeParams.pairId, callbackData.leverage);

            uint256 cost = 0;

            if (marginAmountUpdate > 0) {
                cost = uint256(marginAmountUpdate);
            }
        //@audit
            _verifyOrderV3(callbackData.resolvedOrder, cost);

            if (marginAmountUpdate > 0) {
                quoteToken.safeTransfer(address(_predyPool), uint256(marginAmountUpdate));
            } else if (marginAmountUpdate < 0) {
                _predyPool.take(true, callbackD/ata.trader, uint256(-marginAmountUpdate));
            }

            emit PerpTraded2(
                callbackData.trader,
                tradeParams.pairId,
                tradeResult.vaultId,
                tradeParams.tradeAmount,
                tradeResult.payoff,
                tradeResult.fee,
                marginAmountUpdate,
                callbackData.orderId
            );
        }
    }
```

This function is called and is implemented as the callback after a trade in the predy pool, issue as hinted by the @audit tag however is that this function does not implement a try catch mechanism when verifying it's order via `_verifyOrderV3`, take a look at the implementation of `_verifyOrderV3` here https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpMarketV1.sol#L326-L338

```solidity

    function _verifyOrderV3(ResolvedOrder memory order, uint256 amount) internal {
        order.validate();

        _permit2.permitWitnessTransferFrom(
            order.toPermit(),
            ISignatureTransfer.SignatureTransferDetails({to: address(this), requestedAmount: amount}),
            order.info.trader,
            order.hash,
            PerpOrderV3Lib.PERMIT2_ORDER_TYPE,
            order.sig
        );
    }
```

We can see that `permit2` is being used to grant the permits, this then leaves this attempt vulnerable to the popular bug case where a griefer can just frontrun the execution in the mempool copy past the exact transaction to `permit2`, then when the original execution from `_verifyOrderV3` is to be executed it always reverts, due to the signature already being used.

## Impact

DOS to protocol's core functionality as the `PerpMarketV1# predyTradeAfterCallback()` would now revert.

> NB: The same bug idea is applicable to the same context where the `_verifyOrder()` routes it's verification via `permit2`, i.e even [this instance](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/gamma/GammaTradeMarket.sol#L444-L456) from `GammaTradeMarket.sol`

## Recommended Mitigation Steps

Consider querying the the `permit2` verification in `_verifyOrderV3` in a try-catch this way no frontrun bug case makes the attempt to bubble up and revert.
