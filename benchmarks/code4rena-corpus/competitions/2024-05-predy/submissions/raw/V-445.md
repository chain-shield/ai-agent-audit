# Vulnerability details

## Impact
Since the implementation of Uniswap fees can overflow, there is a case where the fees overflow and cause an underflow, however as the the protocol is using solidity pragma over 0.8 this will cause a revert because it is not in an unchecked block. 

## Proof of Concept
https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/Perp.sol#L384C7-L388C10
```solidity
			  uint256 f0;
        uint256 f1;
  // overflow of feeGrowth is unchecked in Uniswap V3
        unchecked {
            f0 = feeGrowthInside0X128 - _assetStatus.lastFee0Growth;
            f1 = feeGrowthInside1X128 - _assetStatus.lastFee1Growth;
        }
```

Here you can see that f0 and f1, are calculated in an unchecked block. 

https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/libraries/Perp.sol#L398-L400
```solidity
  _assetStatus.fee0Growth += FullMath.mulDiv(
            f0, _assetStatus.totalAmount + _assetStatus.borrowedAmount * spreadParam / 1000, _assetStatus.totalAmount
        );
        _assetStatus.fee1Growth += FullMath.mulDiv(
            f1, _assetStatus.totalAmount + _assetStatus.borrowedAmount * spreadParam / 1000, _assetStatus.totalAmount
        );
```
On these lines you can see that f0 and f1 are used in a multiplication. 

Now lets consider the following scenario:
1) lastFee0Growth, lastFee1Growth are a positive number 
2) feeGrowthInside0X128, feeGrowthInside1X128 were just claimed or overflow to 0 
3) this will cause the calculation to underflow of fee0Growth and/or fee1Growth
4) protocol will continue reverting

## Tools Used
Manual Analysis
## Recommended Mitigation Steps
Make f0 and f1 int256 and if they are negative numbers the function should return.
