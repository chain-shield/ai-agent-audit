# Vulnerability details

## Root of the bug 
The bug is arise from the absence of validation on the data in the `swapExactIn` and `swapExactOut` functions. 
These functions directly pass the data to Uniswap's router without any checks, cause The data is  used for routing swaps in Uniswap's exactInput and exactOutput , is passed without validation.
and This parameter should typically contain the routing path for a swap, specifying the sequence of token pairs involved in the trade. If not validated, a  malicious or malformed data can cause swaps to route through unexpected or harmful paths, resulting in incorrect token transfers or financial losses.

- Here in `swapExactIn` the  data is passed directly to `ISwapRouter.ExactInputParams `without any checks:

```solidity
ISwapRouter.ExactInputParams(data, recipient, block.timestamp, amountIn, amountOutMinimum)
```
- And here in `swapExactOut` also the data is passed directly to `ISwapRouter.ExactOutputParas `without validation: 

```solidity
ISwapRouter.ExactOutputParams(data, recipient, block.timestamp, amountOut, amountInMaximum)
```
## Impact
The issue is can result in unauthorized or incorrect swaps, leading to financial loss
## Proof of Concept

The documentation in the UniswapSettlement contract indicates that critical operations, as swaps, should be carefully managed and controlled by specific actors, and any parameters involved should be securely handled to avoid misuse.
Here : 

```solidity
"Operator/PoolCreator: Currently, the Operator and PoolCreator are the same and hold the admin role in the Predy protocol. Operator can register pairs and PoolCreator can update the parameters of registered pairs."
This implies that functions involving significant operations like swaps should have controlled access and should only be performed by authorized actors to prevent unauthorized use.
```
And here for Parameter Management:

```solidity
"For specific usage, please refer to the Interest Rate Model. PoolOwner specifies the address that can update the pool's settings. PriceFeed specifies the contract that can obtain the oracle price for the pair. If a zero address is specified, the TWAP from the UniswapPool will be used as the oracle price."
This highlights the importance of secure and validated parameters, such as data in swap operations, to avoid exploitation.
```
```solidity
"Register a pair of quoteToken and baseToken. In practice, register the corresponding Uniswap pool with the quoteToken. The token in the Uniswap pool that is not the quoteToken will become the baseToken."
```
- here a scenario show the issue : 
- let’s say that an an attacker, discovers that the data parameter is not validated in the swapExactIn function. And She prepares malicious data that, when used, could route tokens through unintended paths 
- an example of malicious 
` data bytes memory maliciousData = hex"deadbeef"; // Invalid routing path `
- now the attacker sends a transaction to the swapExactIn function with the crafted malicious data as an example :  
```solidity 
uniswapSettlement.swapExactIn(
    address(this),
    baseToken,
    maliciousData,
    1000,
    950,
    address(this)
);
```
- as result The exactInput function receives the malicious data, attempting to execute a swap with an invalid or malicious routing path.
- Since data is not validated, this could result in the swap failing or tokens being routed incorrectly.
the attacker  can exploit this to steal tokens from the contract or execute unintended swaps that could lead to financial loss.
