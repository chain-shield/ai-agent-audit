# Vulnerability details

## Impact
`PerpMarketLib#validateTrade` in the following condition [#L97-L104](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpMarketLib.sol#L97-L104)
```solidity
} else if (limitPrice > 0 && stopPrice > 0) {
    // limit & stop order
    if (
        !validateLimitPrice(tradePrice, tradeAmount, limitPrice)
            && !validateStopPrice(oraclePrice, tradePrice, tradeAmount, stopPrice, auctionData)
    ) {
        revert LimitStopOrderDoesNotMatch();
    }
}
```
The condition: [#L100-L101](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpMarketLib.sol#L100-L101)
```solidity
!validateLimitPrice(tradePrice, tradeAmount, limitPrice) && !validateStopPrice(oraclePrice, tradePrice, tradeAmount, stopPrice, auctionData)
```
is using the logical AND (`&&`) operator, which means that the `LimitStopOrderDoesNotMatch` error will only be reverted if both `validateLimitPrice` and `validateStopPrice` return false.

However the intended behavior seems to be that the error should be reverted if either the limit price condition or the stop price condition is not met. In other words, the error should be reverted if at least one of the two conditions is not satisfied.

An example to illustrate the impact of this issue:

Suppose we have the following trade parameters:

`tradePrice` = 100
`tradeAmount` = 10
`limitPrice` = 90
`stopPrice` = 110
`oraclePrice` = 105

In this case, the `validateLimitPrice` function should return false because the `tradePrice` (100) is greater than the `limitPrice` (90) for a buy order (`tradeAmount` is positive).

However, the `validateStopPrice` function should return true because the `tradePrice` (100) is less than the `oraclePrice` (105) plus the slippage tolerance (calculated based on `auctionData`), which is a valid condition for a buy order.

With the current implementation, the condition:
```solidity
!validateLimitPrice(tradePrice, tradeAmount, limitPrice) && !validateStopPrice(oraclePrice, tradePrice, tradeAmount, stopPrice, auctionData)
```
will evaluate to:
```solidity
true && false
```
which is `false`.

As a result, the `LimitStopOrderDoesNotMatch` error will not be reverted, and the invalid trade (violating the limit price condition) will be allowed to execute.

```solidity
import "../src/markets/perp/PerpMarketLib.sol";

contract PerpMarketLibTest is Test {
    function testValidateTrade() public {
        // Mock trade result
        IPredyPool.TradeResult memory tradeResult;
        tradeResult.payoff.perpEntryUpdate = 100;
        tradeResult.payoff.perpPayoff = 0;
        tradeResult.sqrtTwap = 10 * 2 ** 96;

        // Mock trade parameters
        int256 tradeAmount = 10;
        uint256 limitPrice = 90 * 2 ** 96;
        uint256 stopPrice = 110 * 2 ** 96;
        bytes memory auctionData = abi.encode(PerpMarketLib.AuctionParams(1001000, 1005000, 0, 10000));

        // Calculate trade price
        uint256 tradePrice = Math.abs(tradeResult.payoff.perpEntryUpdate + tradeResult.payoff.perpPayoff)
            * Constants.Q96 / Math.abs(tradeAmount);
        uint256 oraclePrice = Math.calSqrtPriceToPrice(tradeResult.sqrtTwap);

        // Case 1: Both validateLimitPrice and validateStopPrice return false (current implementation)
        vm.expectRevert(PerpMarketLib.LimitStopOrderDoesNotMatch.selector);
        PerpMarketLib.validateTrade(
            tradeResult,
            tradeAmount,
            limitPrice,
            stopPrice,
            auctionData
        );

        // Case 2: Intended behavior - revert if either validateLimitPrice or validateStopPrice returns false
        vm.mockCall(
            address(this),
            abi.encodeWithSelector(PerpMarketLib.validateLimitPrice.selector, tradePrice, tradeAmount, limitPrice),
            abi.encode(false)
        );
        vm.mockCall(
            address(this),
            abi.encodeWithSelector(PerpMarketLib.validateStopPrice.selector, oraclePrice, tradePrice, tradeAmount, stopPrice, auctionData),
            abi.encode(true)
        );
        vm.expectRevert(PerpMarketLib.LimitStopOrderDoesNotMatch.selector);
        PerpMarketLib.validateTrade(
            tradeResult,
            tradeAmount,
            limitPrice,
            stopPrice,
            auctionData
        );
    }
}
```
In this test, we first set up mock trade result and trade parameters. We then calculate the `tradePrice` and `oraclePrice` based on the provided data.

In the first case, we test the current implementation where both `validateLimitPrice` and `validateStopPrice` return `false`. We expect the `LimitStopOrderDoesNotMatch` error to be reverted, but it doesn't due to the logical AND condition.

In the second case, we mock the `validateLimitPrice` and `validateStopPrice` functions to return `false` and `true`, respectively. This represents the scenario where the limit price condition is not met, but the stop price condition is met. According to the intended behavior, the `LimitStopOrderDoesNotMatch` error should be reverted in this case, which is what we test for.

_By running this test, you can see that the first case fails (the error is not reverted when both conditions are false), while the second case passes (the error is reverted when either condition is false), demonstrating the issue and the intended behavior._

## Recommended Mitigation Steps
The logical condition should be changed to use the OR (`||`) operator instead of AND (`&&`).
```solidity
if (
    !validateLimitPrice(tradePrice, tradeAmount, limitPrice)
        || !validateStopPrice(oraclePrice, tradePrice, tradeAmount, stopPrice, auctionData)
) {
    revert LimitStopOrderDoesNotMatch();
}
```
With this change, the `LimitStopOrderDoesNotMatch` error will be reverted if either the limit price condition or the stop price condition is not met, ensuring that only valid trades are executed.
