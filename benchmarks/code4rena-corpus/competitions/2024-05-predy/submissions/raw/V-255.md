# Vulnerability details

## Impact
```solidity
// src/PredyPool.sol

...
contract PredyPool is IPredyPool, IUniswapV3MintCallback, Initializable, ReentrancyGuardUpgradeable {
...
	function setOperator(address newOperator) external onlyOperator {
	    require(newOperator != address(0));
	    operator = newOperator;
	
	    emit OperatorUpdated(newOperator);
	}
...
}
```
According to the protocol documentation, https://docs.predy.finance/predy-v6/dev/architecture#operator-poolcreator, the operator holds the admin role in the protocol, which is a critical one. Nevertheless, the function `setOperator` allows a new operator address to be set via a single-step action. While the new address is validated against zero address, there is no other validation to confirm that this address is correct. So, in case of a human error while invoking the `setOperator` function, the control over the protocol is lost forever. 

## Proof of Concept
The description of the impact is self-explanatory.

## Tools Used
Manual checking.

## Recommended Mitigation Steps
Implement a two-step process to set a new `operator`, where the current operator first approves the new address as a `pendingNewOperator`. Then, as a second step, the `pendingNewOperator` claims the operator role ownership in a separate transaction. If it happens that the `setOperator` function sets an incorrect address in the first place, the current operator can invoke the `setOperator` function again with the re-verified new address.
