# Vulnerability details

When adding a pair, if no oracle address is specified, the uniswap twap oracle will be used instead.

The twap oracle function in this implementation doesn't account for negative ticks, this results in inaccurate price feeds. 

## Impact

In the context of this protocol inaccurate price will result in position unjustly getting liquidated, similarly position that ought to be liquidated might avoid it since the holding of certain assets might become overvalued. 

AutoHeging and closing will be affected, making the system inaccurate.

This flaw will make position involving Margin inaccurate, Margin is pillar concept of this protocol, it is best to aim for accuracy, because inaccurate prices lead to inaccurate trading performances. Which defeats the whole purpose of the protocol.

## Proof of Concept

Let's look at the current [tickCumulative processing](https://github.com/code-423n4/2024-05-predy/blob/2fb1e0ec7a52fc06c2e9c8e561bccba84302e4bb/src/libraries/UniHelper.sol#L70-L74):

```
        int56[] memory tickCumulatives = abi.decode(data, (int56[]));

        int24 tick = int24((tickCumulatives[1] - tickCumulatives[0]) / int56(int256(ago)));
        uint160 sqrtPriceX96 = TickMath.getSqrtRatioAtTick(tick);
```

The problem now is that in the case if our `tick` is negative, i.e int24(tickCumulatives[0] - tickCumulatives[1] < 0) , then the tick should be rounded down as it's done in the uniswap library.

But this is not being done and as a result, in case if int24(tickCumulatives[0] - tickCumulatives[1]) is negative and (tickCumulatives[0] - tickCumulatives[1]) % secondsAgo != 0, then the returned tick will be bigger then it should be, which will directly influence the price, since the price obtained through the tick.
