# Vulnerability details

## Impact
The absence of a proper mechanism to disable Uniswap pools in the `allowedUniswapPools` mapping can lead to unauthorized access to the `uniswapV3MintCallback` function. This vulnerability allows malicious entities to continue calling the callback function even after their pool should have been disabled. As a result, attackers can potentially drain the contract's funds by forcing token transfers through unauthorized minting operations. This poses a significant security risk to the entire system, compromising the integrity and safety of the assets managed by the contract.


## Proof of Concept
The vulnerability is located in the missing functionality to disable Uniswap pools in the `allowedUniswapPools` mapping. Here is the affected code snippet from the `PredyPool` contract:

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.17;

contract PredyPool is IPredyPool, IUniswapV3MintCallback, Initializable, ReentrancyGuardUpgradeable {
    // ...

    mapping(address => bool) public allowedUniswapPools;

    // ...

    /// @dev Callback for Uniswap V3 pool.
    function uniswapV3MintCallback(uint256 amount0, uint256 amount1, bytes calldata) external override {
        // Only the uniswap pool has access to this function.
        require(allowedUniswapPools[msg.sender]);

        IUniswapV3Pool uniswapPool = IUniswapV3Pool(msg.sender);

        if (amount0 > 0) {
            ERC20(uniswapPool.token0()).safeTransfer(msg.sender, amount0);
        }
        if (amount1 > 0) {
            ERC20(uniswapPool.token1()).safeTransfer(msg.sender, amount1);
        }
    }

    // ...
}
```

## Tools Used
Manual

## Recommended Mitigation Steps
Add functions to enable and disable Uniswap pools in the `allowedUniswapPools` mapping. These functions should be accessible only to the contract operator.
