# Vulnerability details

## Impact
`PredyPool.withdrawProtocolRevenue`, the `pool.accumulatedProtocolRevenue` is set to zero before the actual token transfer is performed. If the token transfer fails for any reason (e.g., insufficient balance, transfer reverted, etc.), the `accumulatedProtocolRevenue` would be reset to zero, but no tokens would be transferred.

The problematic code: [PredyPool.withdrawProtocolRevenue#L184-L188](https://github.com/code-423n4/2024-05-predy/blob/2fb1e0ec7a52fc06c2e9c8e561bccba84302e4bb/src/PredyPool.sol#L184-L188)
```solidity
pool.accumulatedProtocolRevenue = 0;

if (amount > 0) {
    ERC20(pool.token).safeTransfer(msg.sender, amount);
}
```
The `PredyPool.withdrawProtocolRevenue` is responsible for withdrawing the accumulated protocol revenue from the asset pool. The protocol revenue is stored in the `accumulatedProtocolRevenue` variable of the `AssetPoolStatus` struct. If the token transfer fails due to any reason (e.g., insufficient balance, transfer reverted, etc.), the `accumulatedProtocolRevenue` is reset to zero, even though no tokens were actually transferred.

> If the token transfer fails, the protocol revenue that was supposed to be withdrawn is permanently lost, as the `accumulatedProtocolRevenue` is reset to zero, and there's no way to recover or withdraw the lost revenue.

`PredyPool.withdrawProtocolRevenue` retrieves the `AssetPoolStatus` struct for the given `pairId` and `isQuoteToken`: [PredyPool.withdrawProtocolRevenue#L178](https://github.com/code-423n4/2024-05-predy/blob/2fb1e0ec7a52fc06c2e9c8e561bccba84302e4bb/src/PredyPool.sol#L178)
```solidity
Perp.AssetPoolStatus storage pool = _getAssetStatusPool(pairId, isQuoteToken);
```
The function then checks if there's any accumulated protocol revenue to withdraw:
```solidity
uint256 amount = pool.accumulatedProtocolRevenue;
require(amount > 0, "AZ");
```
The problematic part is that the `accumulatedProtocolRevenue` is reset to zero before the actual token transfer:
```solidity
pool.accumulatedProtocolRevenue = 0;

if (amount > 0) {
    ERC20(pool.token).safeTransfer(msg.sender, amount);
}
```
If the `safeTransfer` call fails for any reason, the `accumulatedProtocolRevenue` has already been reset to zero, leading to a permanent loss of the protocol revenue.

## Proof of Concept
Let's assume that the `AssetPoolStatus` struct has the following values
```solidity
Perp.AssetPoolStatus pool = {
    // ...
    accumulatedProtocolRevenue: 1000, // 1000 tokens of protocol revenue
    token: 0x1234567890abcdef... // ERC20 token address
}
```
Now, if the `safeTransfer` call fails (e.g., due to insufficient balance), the `accumulatedProtocolRevenue` will be reset to zero, even though no tokens were transferred:
```solidity
pool.accumulatedProtocolRevenue = 0; // Reset to 0
ERC20(pool.token).safeTransfer(msg.sender, 1000); // Transfer fails

// The protocol revenue of 1000 tokens is permanently lost
```

## Recommended Mitigation Steps
the order of operations should be reversed. The token transfer should be performed first, and if it succeeds, then the `accumulatedProtocolRevenue` should be set to zero. By making this change, if the token transfer fails for any reason, the `accumulatedProtocolRevenue` will not be reset, and the protocol revenue can be withdrawn again in the future.

```solidity
if (amount > 0) {
    ERC20(pool.token).safeTransfer(msg.sender, amount);
    pool.accumulatedProtocolRevenue = 0;
}
```
