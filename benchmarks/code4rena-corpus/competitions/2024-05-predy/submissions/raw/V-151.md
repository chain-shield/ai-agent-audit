# Vulnerability details

## Impact
[isLiquidatable function](https://github.com/code-423n4/2024-05-predy/blob/e96f378007e3dc56b184079f0c0e4fe48a72efaa/src/libraries/PositionCalculator.sol#L34-L46) is responsible for determining whether a vault (position) is eligible for liquidation based on its safety and the presence of an open position. The safety of a vault is determined by comparing its value (`vaultValue`) with the minimum required margin (`minMargin`) and checking if the vault's margin (`_vault.margin`) is non-negative.

`_isLiquidatable` variable: [Here L45](https://github.com/code-423n4/2024-05-predy/blob/e96f378007e3dc56b184079f0c0e4fe48a72efaa/src/libraries/PositionCalculator.sol#L45)
```solidity
_isLiquidatable = !isSafe && hasPosition;
```

If a vault is not safe (i.e., `vaultValue < minMargin or _vault.margin < 0`) and there is no open position (`hasPosition` is `false`), the function should return true for `_isLiquidatable`, indicating that the vault is eligible for liquidation. Besides, due to the bug in the calculation of `_isLiquidatable`, the function incorrectly returns false in this scenario.

**The impact can lead to the following consequences**
> If a vault is not safe and has no open position, it should be liquidated to prevent potential losses, but with the current bug, such vaults will be incorrectly marked as not liquidatable, missing the opportunity to liquidate them and potentially leading to losses for the protocol.

> In cases where a vault is not safe but has an open position, the function will correctly mark it as liquidatable, if the vault becomes unsafe and the position is closed (e.g., due to a trade or rebalancing), the function will incorrectly mark it as not liquidatable, even though it should be eligible for liquidation.

> If unsafe vaults are not liquidated due to the bug, the protocol may incur losses if the price moves further against the position, potentially leading to negative vault margins and the inability to recover funds.

## Proof of Concept
Consider the following scenario
```solidity
DataType.PairStatus pairStatus;
DataType.Vault vault;
DataType.FeeAmount feeAmount;

// Assume the following values:
int256 minMargin = 1000;
int256 vaultValue = 900; // Vault value is less than the minimum required margin
vault.margin = 0; // Vault margin is non-negative

// Calculate the necessary values
(minMargin, vaultValue, hasPosition, sqrtOraclePrice) = calculateMinMargin(pairStatus, vault, feeAmount);

// Calculation of isSafe
bool isSafe = vaultValue >= minMargin && vault.margin >= 0;
// isSafe = false (since vaultValue < minMargin)

// Calculation of _isLiquidatable (with the bug)
_isLiquidatable = !isSafe && hasPosition;
// Assume hasPosition = false (no open position)
// _isLiquidatable = false (INCORRECT, should be true)
```
In this scenario, the vault is not safe (`vaultValue < minMargin`), and there is no open position (`hasPosition` is `false`). According to the correct logic, the vault should be marked as liquidatable (`_isLiquidatable` should be `true`). Due to the bug in the calculation of `_isLiquidatable`, the function incorrectly returns false, indicating that the vault is not liquidatable.

**Here's why:**
- The vault is not safe (`isSafe` is `false`) because the vault value is less than the minimum required margin.
- There is no open position (`hasPosition` is `false`.
- According to the correct logic, the vault should be marked as liquidatable (`_isLiquidatable` should be `true`) because it's not safe.

## Recommended Mitigation Steps
The `_isLiquidatable` calculation should be modified as follows
```solidity
_isLiquidatable = !isSafe || !hasPosition;
```
This way, the function will correctly return `true` for `_isLiquidatable` if either the vault is not safe (`!isSafe`) or there is no open position (`!hasPosition`).

By negating the `hasPosition` condition, the function will accurately determine whether a vault is liquidatable based on its safety and the presence of an open position.
