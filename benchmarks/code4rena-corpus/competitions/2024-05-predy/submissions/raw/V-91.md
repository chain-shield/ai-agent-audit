# Vulnerability details

## Impact
`getAvailableLiquidityAmount` retrieves the liquidity amount for a specific position by calling the `positions` function of the `IUniswapV3Pool` contract. nonetheless, the positions function returns a tuple with multiple values, and the function is only returning the first value of the tuple, which is the `liquidity` amount.

According to the UniswapV3 Core documentation, the positions function returns the following values
```solidity
(
    uint128 liquidity,
    uint256 feeGrowthInside0LastX128,
    uint256 feeGrowthInside1LastX128,
    uint128 tokensOwed0,
    uint128 tokensOwed1
)
```
By only returning the liquidity value, the function is ignoring the other values in the tuple, which could lead to issues or unexpected behavior if those values are needed elsewhere in the codebase. By ignoring the other values in the tuple, the function is potentially limiting the functionality and extensibility of the codebase, as well as increasing the risk of bugs.

## Proof of Concept
Code snippet: [getAvailableLiquidityAmount](https://github.com/code-423n4/2024-05-predy/blob/2fb1e0ec7a52fc06c2e9c8e561bccba84302e4bb/src/libraries/Perp.sol#L332-L343)
```solidity
function getAvailableLiquidityAmount(
    address _controllerAddress,
    address _uniswapPool,
    int24 _tickLower,
    int24 _tickUpper
) internal view returns (uint128) {
    bytes32 positionKey = PositionKey.compute(_controllerAddress, _tickLower, _tickUpper);

    // This line only returns the `liquidity` value from the tuple
    (uint128 liquidity,,,,) = IUniswapV3Pool(_uniswapPool).positions(positionKey);

    return liquidity;
}
```
By only returning the liquidity value, the `getAvailableLiquidityAmount` function is ignoring the other values in the tuple, which could lead to issues.

For example, if the codebase needs to track the fee growth or tokens owed for a specific position, it would not be able to retrieve those values from the `getAvailableLiquidityAmount` function. This could result in incorrect calculations, missing data, or other bugs.

To illustrate the concept further, let's consider a hypothetical scenario where the codebase needs to calculate the total fees owed for a position. Without access to the `feeGrowthInside0LastX128` and `feeGrowthInside1LastX128` values, it would be impossible to perform this calculation accurately.

Example of how the code might need to be modified to handle this scenario:
```solidity
function getTotalFeesOwed(

        uint128 liquidity,

    ) = IUniswapV3Pool(_uniswapPool).positions(positionKey);

```
In this example, the `getTotalFeesOwed` function needs access to the `feeGrowthInside0LastX128`, `feeGrowthInside1LastX128`, and `liquidity` values to accurately calculate the total fees owed for the position. Without retrieving these values from the `positions` function, it would be impossible to implement this functionality correctly.

Creating separate functions to retrieve each of the values returned by the `positions` function, if needed.
