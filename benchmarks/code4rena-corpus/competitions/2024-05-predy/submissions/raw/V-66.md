# Vulnerability details

## Impact
[src/markets/perp/PerpOrder.sol#resolve](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/markets/perp/PerpOrder.sol#L73-L77) uses a ternary operator to assign the value of `amount` based on the condition `perpOrder.marginAmount > 0`. If the condition is true, it converts `perpOrder.marginAmount` (an `int256` value) to `uint256` using an explicit cast. However, if `perpOrder.marginAmount` is negative, the explicit cast will not preserve the negative value but instead convert it to a large positive `uint256` value due to the way two's complement representation works for signed integers.
```solidity
function resolve(PerpOrder memory perpOrder, bytes memory sig) internal pure returns (ResolvedOrder memory) {
    uint256 amount = perpOrder.marginAmount > 0 ? uint256(perpOrder.marginAmount) : 0;

    return ResolvedOrder(perpOrder.info, perpOrder.entryTokenAddress, amount, hash(perpOrder), sig);
}
```
For example, if `perpOrder.marginAmount is -1`, it will be converted to `0xffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff` (the maximum value of `uint256`), which is an extremely large positive value.

The incorrect conversion of negative `marginAmount` values violates the invariants and assumptions that the system have regarding the valid range of values for the amount field in the `ResolvedOrder` struct.

## Proof of Concept
See the following example>
```solidity
PerpOrder memory order = PerpOrder({
    info: OrderInfo(...),
    pairId: 1,
    entryTokenAddress: 0x1234567890123456789012345678901234567890,
    tradeAmount: -1000,
    marginAmount: -100,
    takeProfitPrice: 0,
    stopLossPrice: 0,
    slippageTolerance: 0,
    leverage: 1,
    validatorAddress: 0x0000000000000000000000000000000000000000,
    validationData: ""
});

bytes memory sig = "0x..."; // Some signature

ResolvedOrder memory resolvedOrder = PerpOrderLib.resolve(order, sig);

// resolvedOrder.amount will be 0xffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff64
// which is an extremely large positive value, instead of the expected -100
```
The `marginAmount` is set to `-100`, but the `resolve` function will incorrectly convert it to the maximum value of `uint256`, which could lead to unexpected behavior.

## Recommended Mitigation Steps
Should handle negative values of `marginAmount` correctly. One way to do this is to use the `abs` function from the Solidity standard library to get the absolute value of `marginAmount`, and then check if it's positive or zero before assigning it to `amount`.
```solidity
function resolve(PerpOrder memory perpOrder, bytes memory sig) internal pure returns (ResolvedOrder memory) {
    uint256 amount;
    if (perpOrder.marginAmount >= 0) {
        amount = uint256(perpOrder.marginAmount);
    } else {
        amount = uint256(-perpOrder.marginAmount);
    }

    return ResolvedOrder(perpOrder.info, perpOrder.entryTokenAddress, amount, hash(perpOrder), sig);
}
```
