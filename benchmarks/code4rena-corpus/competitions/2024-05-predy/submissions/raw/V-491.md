# Vulnerability details

## Impact
The protocol allows users to open positions for trading, which they can later close.

Positions act as vaults, which store information regarding the user's position, such as `vault owner`, `vault recipient`, `pair id`, `quote token used by pair` 

When creating a vault, if the user enters `vault id = 0`, a new vault will be created for them with a unique `vault id`. 

If `vault id != 0`, this means the user already has a position open, so the vault is fetched from the mapping.

The problem is that the very first vault which is created will have a `vault id = 0`. This means that whenever the user decides to close their vault, it will create a new vault for them instead of using their vault which has id of 0.

The position will be locked permanently and user will be unable to close, causing loss of funds.

When no vaults are created, the initial `vaultCount` will be 0. When the first vault is created, it will be given the id of `globalData.vaultCount`, which will be 0.

After creating the vault, `globalData.vaultCount` is incremented, so that the next vaults created will have id's of 1,2,3...etc.

Therefore, the first position will have id of 0. However, we can see that whenever the `vaultId` is 0, a new vault is always created, and a new `vault.id` is returned.

Each time the user's vault is fetched via this function, it will create a new vault for them with new parameters, instead of returning the vault that was created for them.

This creates an issue where the user is never able to close their position.
