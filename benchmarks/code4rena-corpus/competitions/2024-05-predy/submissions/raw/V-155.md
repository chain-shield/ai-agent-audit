# Vulnerability details

## Impact
`PositionCalculator:calculateMinValue` is responsible for calculating the minimum value, vault value, debt value, and determining if a position exists based on the provided `positionParams`. The line `hasPosition = hasPosition || getHasPositionFlag(positionParams);` is meant to update the `hasPosition` flag based on the `positionParams`.

But the way the logical OR operator (`||`) works in most programming languages, including Solidity, the right-hand side of the expression (`getHasPositionFlag(positionParams)`) is only evaluated if the left-hand side (`hasPosition`) is false. This means that if `hasPosition` is initially true, the `getHasPositionFlag` function will not be called, and the value of `hasPosition` will remain true regardless of the actual position parameters.

**Scenario of the impact:**

Assume the `calculateMinValue` is called with `hasPosition` initially set to `true` (e.g., from a previous iteration or calculation).
The `positionParams` passed to the function indicate that there is no position (e.g., `amountSqrt` and `amountUnderlying` are both zero).
The line `hasPosition = hasPosition || getHasPositionFlag(positionParams);` is executed.
Since `hasPosition` is already `true`, the `getHasPositionFlag(positionParams)` function is not evaluated, and the value of `hasPosition` remains `true`.
The subsequent calculations and margin requirements will be based on the incorrect assumption that there is a position, even though the `positionParams` indicate otherwise.

This can lead to incorrect margin calculations, incorrect position values, and potentially incorrect liquidation or margin call decisions. It violates the expected behavior of the function, which should accurately determine the presence of a position based on the provided `positionParams`.

## Proof of Concept
In the [PositionCalculator:calculateMinValue](https://github.com/code-423n4/2024-05-predy/blob/e96f378007e3dc56b184079f0c0e4fe48a72efaa/src/libraries/PositionCalculator.sol#L117-L133), the issue is related to the [#line 129](https://github.com/code-423n4/2024-05-predy/blob/e96f378007e3dc56b184079f0c0e4fe48a72efaa/src/libraries/PositionCalculator.sol#L129)
```solidity
hasPosition = hasPosition || getHasPositionFlag(positionParams);
```
The `getHasPositionFlag` function is defined as follows: [#Lines 175-177](https://github.com/code-423n4/2024-05-predy/blob/e96f378007e3dc56b184079f0c0e4fe48a72efaa/src/libraries/PositionCalculator.sol#L175-L177)
```solidity
function getHasPositionFlag(PositionParams memory _positionParams) internal pure returns (bool) {
    return _positionParams.amountSqrt != 0 || _positionParams.amountBase != 0;
}
```
The problem is that the `hasPosition` variable is being assigned the result of the `getHasPositionFlag` function, but it is also being used in the same expression. This means that if `hasPosition` is initially true, the `getHasPositionFlag` function will not be evaluated, and the value of `hasPosition` will remain true even if the `positionParams` indicate that there is no position.

## Recommended Mitigation Steps
Should separate the assignment and the logical OR operation into two separate lines.
```solidity
bool hasPositionFlag = getHasPositionFlag(positionParams);
hasPosition = hasPosition || hasPositionFlag;
```
This way, the `getHasPositionFlag` function will always be evaluated, and the value of `hasPosition` will be correctly updated based on the result of the function and its previous value.
