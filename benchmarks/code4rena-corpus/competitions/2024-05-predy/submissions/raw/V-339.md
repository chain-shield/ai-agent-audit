# Vulnerability details

## Impact

Vault owners can avoid liquidation by giving setting a blacklisted user as a recipient of his vault when the `quoteToken` has a blacklist mechanism, so any liquidations that transfer the excess collateral to the recipient will fail.

## Proof of Concept

We can see that the `PredyPool::execLiquidationCall` checks if the position has been fully liquidated (hasPosition == false) and if so, it also checks and transfers the remaining margin to the `vault::recipient` that the **vault owner** has set:

And here we can see that the vault owner can freely change the vault recipient, possibly front running liquidation, or giving such address that will block the liquidation at the time of opening it:

[PredyPool.sol](https://github.com/code-423n4/2024-05-predy/blob/a9246db5f874a91fb71c296aac6a66902289306a/src/PredyPool.sol#L281-L292)

```solidity
/**
* @notice Updates the recipient. If the position is liquidated, the remaining margin is sent to the recipient.
* @param vaultId The id of the vault.
* @param recipient if recipient is zero address, protocol never transfers margin.
*/
function updateRecepient(uint256 vaultId, address recipient) external onlyVaultOwner(vaultId) {
  DataType.Vault storage vault = globalData.vaults[vaultId];

  vault.recipient = recipient;

  emit RecepientUpdated(vaultId, recipient);
}
```

So from there malicious trader can create vault and pass arbitrary address as a recipient in case the `quoteToken` being used has a [blocklist/blacklist mechanism](https://github.com/d-xo/weird-erc20?tab=readme-ov-file#tokens-with-blocklists) (USDC, USDT).

Then when his position is eligible for liquidation but his `remainingMargin` is greater than 0 or the trader changes his `recipient`, so the if check at the snippet above is bypassed all the transaction will be reverting and  accruing bad debt to the system.

## Recommended Mitigation Steps

Use pull-over-pull architecture - keep the excess margin, so the recipient itself to claim it.
