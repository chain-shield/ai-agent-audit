# Vulnerability details

`EbtcZapRouter` contract, which inherits from `ZapRouterBase`, is designed to facilitate various operations involving CDPs (Collateralized Debt Positions) and different forms of Ethereum (ETH, stETH, wstETH). One of the key invariants of this contract, as stated in [ZapRouterPropertiesDescriptions.sol](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/invariants/ZapRouterPropertiesDescriptions.sol#L17-L18), is that the `ZapRouter` should not hold any tokens after each operation, except for potential rounding issues.

The contract implements a mechanism to transfer any remaining stETH back to the caller after operations: [EbtcLeverageZapRouter.so#L459-465](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/EbtcLeverageZapRouter.sol#L459-L466)
```solidity
if (_zapStEthBalanceDiff > 0) {
    _transferStEthToCaller(
        _cdpId,
        EthVariantZapOperationType.AdjustCdp,
        _params.useWstETHForDecrease,
        _zapStEthBalanceDiff
    );
}
```
This mechanism aligns with the invariant described in [ZapRouterPropertiesDescriptions.sol#L17-L18](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/invariants/ZapRouterPropertiesDescriptions.sol#L17-L18)
```solidity
    string constant ZR_06 =
        "ZR-06: The balance of wstETH in the ZapRouter should never change after creation";
```
However, the contract lacks similar checks and transfer mechanisms for other tokens that might be involved in operations, particularly `eBTC`. This could lead to a scenario where `non-stETH` tokens are inadvertently retained in the contract after operations, violating the intended invariant.

## Impact
* **Violation of contract invariant**: The ZapRouter may retain non-stETH tokens, contradicting the principle that it should not hold any tokens after operations.
* If tokens are retained in the contract, users may lose access to these funds.
* **Increased attack surface:** Accumulated tokens in the contract could become a target for potential exploits.

## Proof of Concept
1. A user operates using the ZapRouter that involves both stETH and eBTC.
2. When the operation is complete, the contract checks for and returns any remaining stETH to the user.
3. a small amount of eBTC remains in the contract due to rounding errors or unforeseen circumstances.
4. The contract has no mechanism to detect or return this eBTC balance.
5. Over time, as multiple users perform operations, eBTC accumulates in the contract.

Manual review
## Recommended Mitigation Steps
1.  Implement a general token sweeping mechanism that checks for balances of all relevant tokens (stETH, eBTC, etc.) after each operation.
2. Extend the existing `_transferStEthToCaller()` function to handle multiple token types, or create separate functions for each token type.
3. Add a public function that allows the contract owner or users to sweep any remaining tokens to their rightful owners.
```solidity
function sweepTokens(address[] memory tokens) external {
    for (uint i = 0; i < tokens.length; i++) {
        IERC20 token = IERC20(tokens[i]);
        uint256 balance = token.balanceOf(address(this));
        if (balance > 0) {
            token.transfer(msg.sender, balance);
        }
    }
}
```
This function should be called at the end of each operation or made available for users to call if they suspect tokens have been left in the contract.
