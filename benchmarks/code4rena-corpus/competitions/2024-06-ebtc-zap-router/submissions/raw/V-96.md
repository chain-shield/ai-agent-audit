# Vulnerability details

## Impact
The LeverageZapRouterBase module implements a slippage check(.ie Post check) to ensure the  State of a Cdp after an operation is within the user  specified slippage range.This is achieved by comparing the (collateral,debt) of a cdp with the expected (collateral,debt).The _getPostCheck()[https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/LeverageZapRouterBase.sol#L257] function is used to compute the expectedCollateral ,the method accepts the _totalCollateral parameter(Steth supplied to a cdp) [https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/LeverageZapRouterBase.sol#L257]
and apply the slippage to compute the expectedCollateral.The issue is that when the _getPostCheck() is called in the _openCdpOperation(),stETHToDeposit parameter is passed as the total-collateral without deducting the LiquidatorReward,and the stethToDeposit is defined as the total steth to be deposited in a cdp.When opening a cdp, depositing  X STETH would result in (X-LIQUIDATOR-REWARD ) as the Liquidator-Reward is deducted from the deposit and the remainder is recorded as the user totalCollateral.So performing slippage check without deducting the Liquidator-reward would result in the expectedCollateral being greater than the resulting collateral.
The Zap router is supposed to implement similar logic,when a user deposit's X STETH's the slippage check should be between X-LIQUIDATOR-REWARD as shares and the resulting cdp shares
