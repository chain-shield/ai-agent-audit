# Vulnerability details

## Impact
The function `excessivelySafeCall` is used to call external contract and get if the transaction is successful or not. However, in the `_doSwap` call, the the `_maxCopy` is set as `0`. This means that the returned value will all be threw away. The check `success` actually doesn't work with protocol (like Balancer V2) that returns `ERROR-CODE` or `False` instead of reverting.

## Proof of Concept
In the function `_doSwap` call, the `excessivelySafeCall` is being called with `_maxCopy` set as `0`.

```solidity
	(bool success, ) = excessivelySafeCall(
		swapData.addressForSwap,
		gasleft(),
		0,
		0,
		swapData.calldataForSwap
	);
	require(success, "Call has failed");

```

This means that in `excessivelySafeCall`, all returned data is all dropped.

```solidity
	// limit our copy to 256 bytes
	_toCopy := returndatasize()
	if gt(_toCopy, _maxCopy) {
		_toCopy := _maxCopy
	}
	// Store the length of the copied bytes
	mstore(_returnData, _toCopy)
```

This however, doesn't comply with some protocol which returns [Error-Code like BalancerV2](https://docs.balancer.fi/reference/contracts/error-codes.html) or [False like ZRX or EURS](https://etherscan.io/address/0xe41d2489571d322189246dafa5ebde1f4699f498#code) instead of reverting.

Although in `LeverageZapRouterBase` limits the `addressForSwap` and `addressForApprove` to be only `DEX` which points to `0x` or `1inch`. But in `LeverageMacroBase` contract, people could also call `doOperation` as the entry point and the `swapData.addressForSwap` is never limited. Thus this would cause issues when the `doOperation`  is later used to interact with incompatible protocols.

## Tools Used
Manual

## Recommended Mitigation Steps
To mitigate this issue:
- Remove the function `doOperation` as it's not in use or explicitly specify the protocol that is incompatible.
- Check `0x` or `1inch` if there is such cases.
