# Vulnerability details

## Impact
Detailed description of the impact of this finding.
```ZapRouterBase._permitPositionManagerApproval()``` will bypass an expired permit. The try-catch clause for```ZapRouterBase._permitPositionManagerApproval()``` help prevent the permit front-running DOS attack, however, the catch body is empty. As a  result, ```ZapRouterBase._permitPositionManagerApproval()``` will bypass an expired permit.

## Proof of Concept
Provide direct links to all referenced code in GitHub. Add screenshots, logs, or any other relevant proof that illustrates the concept.

The following steps show how come a permit will still be valid even after it expires.

1. Suppose a permit by user A will expire in 10 minutes. User B front-run and execute the permit before it expires. 

[https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/ZapRouterBase.sol#L115-L133](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/ZapRouterBase.sol#L115-L133)

2. After 11 minutes, the permit has expired. Since the permit has already been executed by user A before it expired, ```ZapRouterBase._permitPositionManagerApproval()``` will still run through without revert due to the try-catch structure; meanwhile, ```BorrowerOperations._requireBorrowerOrPositionManagerAndUpdateManagerApproval``` will pass since the approval has already been set and there is no check of deadline in this function. 

3. The main issue here is that there might be a time gap between the execution of the permit (can be done by anymore), and the use of the permit (```BorrowerOperations._openCdp()```), which might be at a time when the permit has already expired. The later will not check whether the permit has expired or not. The call of ```BorrowerOperations._openCdp()``` will call ```_requireBorrowerOrPositionManagerAndUpdateManagerApproval()``` to check ONLY the approval without checking the deadline.

[https://github.com/ebtc-protocol/ebtc/blob/2da05f2d1354190eacf64ec256d2c5c5358e5fa2/packages/contracts/contracts/BorrowerOperations.sol#L443-L551](https://github.com/ebtc-protocol/ebtc/blob/2da05f2d1354190eacf64ec256d2c5c5358e5fa2/packages/contracts/contracts/BorrowerOperations.sol#L443-L551)

2. I run the following command ```forge test --match-test test_ZapOpenCdp_WithWstEth_LowLeverage -vv```. The result shows that the expired permit was bypassed. If we deleted the line ```borrowerOperations.permitPositionManagerApproval```, then it will show that the permit will not work since it has expired. 

3. The POC shows that after a permit was executed (due to front-running), then even after a long time, a user can still execute openCdp to open a Cdp even after the permit has expired since the try-catch clause of ```ZapRouterBase._permitPositionManagerApproval()``` will ignore the failure and the check in ```BorrowerOperations._requireBorrowerOrPositionManagerAndUpdateManagerApproval``` does not check the deadline at all.

## Recommended Mitigation Steps
Modify the  _permitPositionManagerApproval() so that the catch clause will check the deadline; we don't need to check approval here since it will be checked later in ```BorrowerOperations._requireBorrowerOrPositionManagerAndUpdateManagerApproval```. This is consistent with the suggestion in (https://www.trust-security.xyz/post/permission-denied) where the catch clause will still check the allowance amount. An empty catch clause is a danger. 

```diff
function _permitPositionManagerApproval(
        IBorrowerOperations borrowerOperations,
        PositionManagerPermit memory _positionManagerPermit
    ) internal {
        try
            borrowerOperations.permitPositionManagerApproval(
                msg.sender,
                address(this),
                IPositionManagers.PositionManagerApproval.OneTime,
                _positionManagerPermit.deadline,
                _positionManagerPermit.v,
                _positionManagerPermit.r,
                _positionManagerPermit.s
            )
        {} catch {
             // @audit: we still need to check the deadline here, we do not need to check approval since it will be checked later in ```BorrowerOperations._requireBorrowerOrPositionManagerAndUpdateManagerApproval``` anyway
+            require(block.timestamp <= _positionManagerPermit.deadline, "the permit has expired.");
 
            /// @notice adding try...catch around to mitigate potential permit front-running
            /// see: https://www.trust-security.xyz/post/permission-denied
        }
```
