# Vulnerability details

## Impact
 `doOperation` function is marked as `external`, but it always reverts with the message "disabled". This means that the function is effectively unusable and cannot be called by any external contract or user.

The comment above the `revert` statement suggests that the intention was to prevent the owner from doing arbitrary calls. However, by reverting unconditionally, it prevents anyone from using the `doOperation` function, not just the owner.

## Proof of Concept
The `doOperation` is part of the LeverageZapRouterBase contract, which is an abstract contract that inherits from `ZapRouterBase`, `LeverageMacroBase`, `ReentrancyGuard`, and `IEbtcLeverageZapRouter`. This contract serves as a base for implementing a leverage zap router functionality.
```solidity
abstract contract LeverageZapRouterBase is ZapRouterBase, LeverageMacroBase, ReentrancyGuard, IEbtcLeverageZapRouter {
    // ...

    function doOperation(
        FlashLoanType flType,
        uint256 borrowAmount,
        LeverageMacroOperation calldata operation,
        PostOperationCheck postCheckType,
        PostCheckParams calldata checkParams
    ) external override {
        // prevents the owner from doing arbitrary calls
        revert("disabled");
    }

    // ...
}
```
The function is marked as `external`, which means it can be called by external contracts or users. However, the function body always reverts to the message "disabled", effectively preventing anyone from executing the intended operation.

The impact of this is that the `doOperation` function is rendered unusable, and any external contract or user attempting to call this function will encounter a revert, causing their transaction to fail.

## Recommended Mitigation Steps
If the goal is to restrict access to the `doOperation` function, a better approach would be to use access control modifiers or checks to allow only authorized users or contracts to call the function, rather than completely disabling it.
