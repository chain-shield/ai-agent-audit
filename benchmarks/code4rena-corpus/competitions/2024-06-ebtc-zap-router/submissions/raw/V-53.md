# Vulnerability details

## Impact
The collateral validation buffer checking logic is flawed, it provides no slippage protection and brings liquidation risk to user.

## Proof of Concept
When a user calls to open a CDP, [_openCdpOperation()](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/LeverageZapRouterBase.sol#L165-L170) is called and `PostCheckParams` is generated and passed to [_doOperation(https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-protocol/packages/contracts/contracts/LeverageMacroBase.sol#L167-L174)], and is used to check against the actual CDP status.
```
        _doOperation(
            FlashLoanType.stETH,
            _flAmount,
            op,
            PostOperationCheck.openCdp,
@>          _getPostCheckParams(
                _cdpId,
                _cdp.eBTCToMint,
                stETH.getSharesByPooledEth(_cdp.stETHToDeposit),
                ICdpManagerData.Status.active,
                _tradeData.collValidationBufferBPS
            ),
            _cdpId
        );
```
This `PostCheckParams` is crafted as below: 
```
            PostCheckParams({
                expectedDebt: CheckValueAndType({value: _debt, operator: Operator.equal}),
@>              expectedCollateral: CheckValueAndType({
@>                  value:  _totalCollateral * _collValidationBuffer / BPS,
@>                  operator: Operator.gte
@>              }),
                cdpId: _cdpId,
                expectedStatus: _status
            });
```
We can see the value of `expectedCollateral` is `_totalCollateral * _collValidationBuffer / BPS`, and the operator is `Operator.gte`. Later `expectedCollateral` is used to [check against the actual CDP collateral](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-protocol/packages/contracts/contracts/LeverageMacroBase.sol#L222).

Assuming `_totalCollateral = 100e18` and `_collValidationBuffer = 10500`, then `expectedCollateral = 105e18`, because `Operator.gte` is assigned for the check, it means the actual collateral can be any value no more than `105e18`, and there is no slippage protection (collateral might be affected by things like rebase etc), results in the actual collateral is lower than expected. Since debt is fixed, less collateral means lower ICR, this brings more liquidation risk to the user.

In addition to that, when opens a CDP, `_stEthDepositAmount` is used to calculate `expectedCollateral`, however, in [BorrowerOperations](https://etherscan.io/address/0xd366e016Ae0677CdCE93472e603b75051E022AD0#code#F1#L456) the actual CDP collateral is calculated based on the net stEth balance, this inconsistency may prevent transaction from reverting when it should be.

## Recommended Mitigation Steps
The current collateral validation buffer logic is a bit convoluted and provides no slippage control.

It is recommended to refactor the logic and use `Operator.lte` instead, e.g. `collValidationBufferBPS = 9000` indicates the actual collateral should not be less than `_stEthDepositAmount * 90%`.

As for the inconsistency:
