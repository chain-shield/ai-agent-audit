# Vulnerability details

## Impact
Due to wrong judgment, the user's slippage settings may not work, resulting in slippage losses.

## Proof of Concept
After adding cdp, there is a check to check the relationship between the actual cdp and the expected cdp. The user can set the maximum acceptable slippage through collValidationBuffer. For simplicity, assume collValidationBuffer]]BPS. That is, the user does not accept slippage, then The check should be that the actual Collateral is greater than or equal to the expectedCollateral expected by the user.
However in the code, [the operation is get](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/LeverageZapRouterBase.sol#L267-L269). This means [checking that the user's expected expectedCollateral is greater than or equal to the actual Collateral](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-protocol/packages/contracts/contracts/LeverageMacroBase.sol#L281-L282). This does not make any sense for the slippage check, which will not protect the user even if the user suffers slippage, even if the actualCollateral==0 also satisfies the condition.
```solidity
                expectedCollateral: CheckValueAndType({
                    value:  _totalCollateral * _collValidationBuffer / BPS,
                    operator: Operator.gte
```
