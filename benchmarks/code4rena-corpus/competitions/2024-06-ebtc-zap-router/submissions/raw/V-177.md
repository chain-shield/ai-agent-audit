# Vulnerability details

## Vulnerability Detail
We could leverage the ability that we could control the function signature & parameters that will be called on the 1inch or 0x DEXes to make arbitrary calls.

In LeverageZapRouterBase we use set the `swaps[0].calldataForSwap `to the `_tradeData.exchangeData`, which we pass as a parameter when we call either openCDP/adjustCDP/closeCDP. DEX is hardcoded, but we can adjust exchangeData.
```solidity
    function _getSwapOperations(address _tokenIn, address _tokenOut, TradeData calldata _tradeData)
        internal
        view
        returns (SwapOperation[] memory swaps)
    {
        swaps = new SwapOperation[](1);

        swaps[0].tokenForSwap = _tokenIn;
@>>     swaps[0].addressForApprove = DEX;
        swaps[0].exactApproveAmount = _tradeData.approvalAmount;
@>>     swaps[0].addressForSwap = DEX;
@>>     swaps[0].calldataForSwap = _tradeData.exchangeData;
        if (_tradeData.performSwapChecks) {
            swaps[0].swapChecks = _getSwapChecks(_tokenOut, _tradeData.expectedMinOut);
        }
    }
```

## Impact
One very easy way to reproduce this behavior is on the closeCDP position to increase the debt/amount in exchangeData (Check POC for details). This way, a user can actually swap more eBTC than needed, and the transaction will be successful. Then the user will close the position, and the "dust" left will be swept to the user. In this case, it will be a lot more than just dust, if the swap amount is big.

A bigger problem could be that this way can also allow someone to call other functions on 1inch or 0x or potentially even swap malicious tokens (which mimic normal behaviour, as the EbtcLeverageZapRouter only cares if we have received the stETH/eBTC as balance after swap, so we could do repayment), or you could call a function that allows **arbitrary calls.** (There are swap functions on the 1inch router which allow you to specify arbitrary data/addresses, which can be dangerous, as we are calling the swap from the EbtcLeverageZapRouter - [etherscan](https://etherscan.io/address/0x111111125421ca6dc452d289314280a0f8842a65#writeContract)). 

Also, since we would probably call the **proxy contract** of the DEX, it's possible that **in the future**, **new** functionalities that can be exploited could be introduced.
Generally, **this approach is not safe** and can leave room for **vulnerabilities**.

## Proof of Concept

## Recommended Mitigation Steps
I suggest changing the approach and not allowing the user to specify important things like function signature and parameters in the exchangeData. Tokens to swap should not be passed with it, as well as the function we are calling, even if the DEX is trusted. 
Also, you would probably want to limit the amount that can be swapped as eBTC, so users cannot end up with huge eBTC amounts when using closeCDP().
