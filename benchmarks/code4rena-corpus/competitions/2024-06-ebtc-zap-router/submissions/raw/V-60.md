# Vulnerability details

`sweepToCaller()` function that transfers all eBTC and collateral balances to the caller without assessing any fees. This is designed to clear out any remaining token balances from the contract after operations. However, it does not take into account whether these balances resulted from operations that should have incurred fees, particularly in cases where debt was increased.

The protocol's design, as indicated in the attack ideas, states that _"Fee should be assessed only when debt increases"_. However, the `sweepToCaller()` function does not differentiate between balances that should be subject to fees and those that shouldn't. This creates a bypass of the fee mechanism, which could lead to unintended financial consequences for the protocol.
[LeverageMacroBase.sol#sweepToCaller()](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-protocol/packages/contracts/contracts/LeverageMacroBase.sol#L247-L263)
```solidity
    function sweepToCaller() public {
        _assertOwner();
        /**
         * SWEEP TO CALLER *
         */
        // Safe unchecked because known tokens
        uint256 ebtcBal = ebtcToken.balanceOf(address(this));
        uint256 collateralBal = stETH.sharesOf(address(this));


        if (ebtcBal > 0) {
            ebtcToken.transfer(msg.sender, ebtcBal);
        }


        if (collateralBal > 0) {
            stETH.transferShares(msg.sender, collateralBal);
        }
    }
```
This function transfers all balances without any fee assessment or consideration of the operations that led to these balances.

## Impact
If fees are meant to be a source of revenue for the protocol, this bypass could lead to significant financial losses over time.

Users who understand this mechanism could potentially exploit it to avoid paying fees, gaining an unfair advantage over other users who pay fees through normal operations.

If the fee structure is part of the protocol's economic model or security mechanism, bypassing it could potentially destabilize the system or reduce its security.

## Proof of Concept
1. User initiates an operation that increases debt, which should incur a fee.
2. The operation completes, leaving a balance of eBTC or collateral in the contract that includes the amount that should be subject to fees.
3. User calls `sweepToCaller()`.
4. All balances are transferred to the user without any fee deduction.
5. The protocol loses the fee revenue it should have collected from the debt-increasing operation.

## Recommended Mitigation Steps
1. Implement a fee tracking mechanism that records when fees should be applied due to debt-increasing operations.
2. Modify the `sweepToCaller()` function to check this fee tracker and deduct appropriate fees before transferring balances.
3. Alternatively, ensure that fees are always deducted immediately after debt-increasing operations, leaving no fee-liable balances in the contract.

function sweepToCaller() public {
