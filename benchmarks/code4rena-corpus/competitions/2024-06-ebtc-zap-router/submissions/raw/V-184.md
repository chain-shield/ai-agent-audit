# Vulnerability details

## Vulnerability Details
In Solidity, the low-level `call` function is used to interact with other contracts or send Ether. It returns two values: a boolean indicating success or failure, and a bytes array containing any returned data. When using `call`, it's crucial to check the boolean return value to ensure the operation succeeded. Failing to do so can lead to silent failures, where a transaction appears to complete successfully even if the underlying operation failed.

In Ethereum, failed calls do not automatically revert the transaction. Instead, they return `false`, allowing the calling contract to handle the failure. If this return value is not checked, the contract may continue execution as if the call succeeded, potentially leading to inconsistent state or unexpected behavior.

## Description:
In the `_depositRawEthIntoLido` function of the ZapRouterBase contract, there is an unchecked low-level `call` used to deposit ETH into the Lido contract:

https://github.com/code-423n4/2024-06-badger/blob/main/ebtc-zap-router/src/ZapRouterBase.sol#L34

```solidity
function _depositRawEthIntoLido(uint256 _initialETH) internal returns (uint256) {
    uint256 _balBefore = stEth.balanceOf(address(this));
    payable(address(stEth)).call{value: _initialETH}("");
    uint256 _deposit = stEth.balanceOf(address(this)) - _balBefore;
    return _deposit;
}
```

The `call` function's return value is not checked, which means:

1. If the Lido contract's receive function reverts or if the call fails for any other reason, this function will not revert.
2. The function will continue execution and calculate `_deposit` based on the balance difference, which may be zero or incorrect in case of a failed call.
3. The calling function will receive a potentially incorrect deposit amount and continue execution, assuming the deposit was successful.

## Impact
This issue can lead to:
- Inconsistent contract state
- Loss of user funds if the deposit fails silently
- Incorrect accounting of deposited amounts
- Potential vulnerabilities if other parts of the contract rely on this deposit being successful

## Mitigation

To fix this issue, the return value of the `call` function should be checked, and the transaction should revert if the call fails. Additionally, using a proper interface for the Lido contract would provide better type safety and reduce the risk of errors.
