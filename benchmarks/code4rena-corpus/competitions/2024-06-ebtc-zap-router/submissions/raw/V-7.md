# Vulnerability details

There is a precision loss vulnerability in the conversion between stETH and wstETH tokens in the ZapRouterBase contract. This could lead to a loss of funds for users in certain scenarios.

Impact:
Users could lose a small amount of funds due to rounding errors when converting between stETH and wstETH. Over time or with large amounts, this could result in significant cumulative losses.

Vulnerability Details:
In the ZapRouterBase contract, the _convertWstEthToStETH function is used to convert wstETH to stETH. However, this function doesn't account for potential precision loss during the conversion process.

The vulnerable code is in the ZapRouterBase.sol file:

```solidity
function _convertWstEthToStETH(uint256 _initialWstETH) internal returns (uint256) {
    require(
        wstEth.transferFrom(msg.sender, address(this), _initialWstETH),
        "EbtcZapRouter: transfer wstETH failure!"
    );

    uint256 _stETHBalBefore = stEth.balanceOf(address(this));
    IWstETH(address(wstEth)).unwrap(_initialWstETH);
    uint256 _stETHReiceived = stEth.balanceOf(address(this)) - _stETHBalBefore;

    return _stETHReiceived;
}
```

The issue arises because the conversion from wstETH to stETH (and vice versa) is not always exact due to the way these tokens are implemented. The stETH token can rebase, which means its total supply can change over time. This can lead to small discrepancies in the conversion process.

Proof of Concept:
1. User A deposits 100 wstETH into the system.
2. The system converts 100 wstETH to stETH, resulting in, say, 99.99999999 stETH due to precision loss.
3. When User A withdraws, they receive 99.99999999 stETH instead of the full 100 stETH equivalent.
4. The remaining 0.00000001 stETH is effectively lost.

This issue becomes more significant with larger amounts or frequent conversions.

Recommended Mitigation:
Implement a "dust collection" mechanism that keeps track of the tiny amounts lost in conversions. These collected amounts can be redistributed to users or handled in a fair manner.

Additionally, consider adding a small buffer when converting from wstETH to stETH to ensure users always receive at least the amount they expect:

```solidity
function _convertWstEthToStETH(uint256 _initialWstETH) internal returns (uint256) {
    require(
        wstEth.transferFrom(msg.sender, address(this), _initialWstETH),
        "EbtcZapRouter: transfer wstETH failure!"
    );

    uint256 _stETHBalBefore = stEth.balanceOf(address(this));
    IWstETH(address(wstEth)).unwrap(_initialWstETH);
    uint256 _stETHReiceived = stEth.balanceOf(address(this)) - _stETHBalBefore;

    // Add a small buffer (e.g., 0.01%) to account for potential precision loss
    uint256 _bufferedAmount = _stETHReiceived * 10001 / 10000;
    
    return _bufferedAmount;
}
```

This approach ensures that users always receive at least the amount they expect, even if there's a small precision loss during conversion.
