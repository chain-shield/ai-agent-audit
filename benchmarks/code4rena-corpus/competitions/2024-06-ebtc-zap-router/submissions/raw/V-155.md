# Vulnerability details

## Impact
If a user mistakenly sends `stETH/eBTC` to the contract, these funds could be utilized by the next user during the `openCdp`/`closeCdp` process. This might involve using the funds for swapping or flashloan payback, potentially compromising the intended operation and fairness of the system.

## Proof of Concept
In the `ZapRouterBase` contract, the balance of `stETH` is determined by checking the before-and-after balances, implying that only the amount explicitly sent is considered in the operation.

```solidity
    function _depositRawEthIntoLido(uint256 _initialETH) internal returns (uint256) {
        // check before-after balances for 1-wei corner case
        uint256 _balBefore = stEth.balanceOf(address(this));
        // TODO call submit() with a referral?
        payable(address(stEth)).call{value: _initialETH}("");
        uint256 _deposit = stEth.balanceOf(address(this)) - _balBefore;
        return _deposit;
    }
```

However, if a user mistakenly sends additional `stETH/eBTC` to the contract, these funds could be used by the next user during `openCdp` and `closeCdp` operations in several ways:

- **Swapping Process:** The mistakenly sent funds could be used in interactions with a DEX to swap for other assets, as the `exactApproveAmount` and actual `swapAmount` can be specified by the caller to cover the current funds.

```solidity
    function _getSwapOperations(
        address _tokenIn,
        address _tokenOut,
        TradeData calldata _tradeData
    ) internal view returns (SwapOperation[] memory swaps) {
        swaps = new SwapOperation[](1);

        swaps[0].tokenForSwap = _tokenIn;
        swaps[0].addressForApprove = DEX;
        swaps[0].exactApproveAmount = _tradeData.approvalAmount;
        swaps[0].addressForSwap = DEX;
        swaps[0].calldataForSwap = _tradeData.exchangeData;
        if (_tradeData.performSwapChecks) {
            swaps[0].swapChecks = _getSwapChecks(_tokenOut, _tradeData.expectedMinOut);            
        }
    }
```

- **Flashloan Payback:** The mistakenly sent funds could also be used to help cover the repayment of a flashloan, ensuring the transaction succeeds.
```
        if (flType == FlashLoanType.eBTC) {
            IERC3156FlashLender(address(borrowerOperations)).flashLoan(
                IERC3156FlashBorrower(address(this)),
                address(ebtcToken),
                borrowAmount,
                abi.encode(operation)
            );
        } else if (flType == FlashLoanType.stETH) {
            IERC3156FlashLender(address(activePool)).flashLoan(
                IERC3156FlashBorrower(address(this)),
                address(stETH),
                borrowAmount,
                abi.encode(operation)
            );
```

- **Sweeping Remaining Funds:** Any leftover funds could be swept to the `msg.sender` at the end of the transaction.

As a result, the next user could exploit the mistakenly sent funds to facilitate `openCdp`, `adjustCdp`, and `closeCdp` operations, potentially leading to unintended financial advantages.

## Tools Used
Manual

## Recommended Mitigation Steps

- **Restrict Fund Usage:** Implement restrictions to prevent the use of mistakenly sent funds in operations.
- **Documentation and Comments:** Add detailed documentation and comments to clearly state that any funds mistakenly sent to the contract cannot be retrieved, ensuring users are aware of this risk.
