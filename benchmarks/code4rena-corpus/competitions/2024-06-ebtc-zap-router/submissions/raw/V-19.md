# Vulnerability details

## Summary
While the code does assess fees only when debt increases, there's a potential issue with how the fee amount is calculated in [LeverageZapRouterBase._adjustCdpCallback#309](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/LeverageZapRouterBase.sol#L309)
```solidity
IERC20(address(ebtcToken)).safeTransfer(zapFeeReceiver, flData._EBTCChange * zapFeeBPS / BPS);
```
This line calculates the fee as `flData._EBTCChange * zapFeeBPS / BPS`. However, `_EBTCChange` represents the total debt change, not just the newly borrowed amount.

**Example:**
   * Existing debt: 100 eBTC
   * User increases debt by 10 eBTC
   * _EBTCChange = 10 eBTC
   * zapFeeBPS = 100 (1%)

The code would calculate the fee as `10 * 100 / 10000 = 0.1 eBTC`, which is 1% of the **total debt change**. However, the fee should ideally be calculated only on the **newly borrowed** **amount (10 eBTC)**, resulting in a fee of 0.01 eBTC.

This discrepancy could lead to overcharging users when they increase their debt.

## Impact
Users are overcharged on debt increases, leading to a loss of funds.

## Proof of Concept
The vulnerability resides within the `_adjustCdpCallback` function of the LeverageZapRouterBase contract, which is inherited by `EbtcLeverageZapRouter`. This function is called after a user adjusts their CDP, and it's responsible for transferring the fee to the `zapFeeReceiver` when the debt is increased.
```solidity
function _adjustCdpCallback(bytes memory data) internal override {
    if (zapFeeBPS > 0) {
        AdjustCdpOperation memory flData = abi.decode(data, (AdjustCdpOperation));

        // ... CDP adjustment logic ...

        if (flData._isDebtIncrease) {
            // Vulnerability: Fee calculated on total debt change (_EBTCChange)
            IERC20(address(ebtcToken)).safeTransfer(zapFeeReceiver, flData._EBTCChange * zapFeeBPS / BPS); 
        }
    } else {
        // ...
    }
}
```
Let's consider a scenario where the `zapFeeBPS` is set to 100 (representing a 1% fee).

1. **Initial State**: A user has an existing CDP with a debt of 100 eBTC.
2. **Debt Increase**: The user interacts with the `EbtcLeverageZapRouter` to increase their debt by 10 eBTC.
3. **Fee Calculation**: The `_adjustCdpCallback` function is triggered. Since `_isDebtIncrease` is true, the fee calculation logic is executed.
4. **Flawed Logic:** The code calculates the fee as `flData._EBTCChange * zapFeeBPS / BPS`, where `_EBTCChange` is 10 eBTC (the total debt change). This results in a fee of 0.1 eBTC (1% of 10 eBTC).
5. **Overcharged Fee:** The user is charged 0.1 eBTC as a fee, which is 10 times higher than the intended fee of 0.01 eBTC (1% of the actual borrowed amount, which is 10 eBTC).

#### Impact
The direct impact is the overcharging of users when they increase their CDP debt.
* `zapFeeBPS:` A higher fee percentage results in a larger discrepancy between the intended fee and the charged fee.
* **Debt Difference:** A larger difference between the existing debt and the debt increase amplifies the overcharge.

## Recommended Mitigation Steps
The fee calculation logic should be modified to consider only the newly borrowed amount. One approach is to introduce a new variable within the `AdjustCdpOperation` struct to explicitly track the newly borrowed amount.
```solidity
struct AdjustCdpOperation {
    // ... other parameters ...
    uint256 _EBTCChange; // Total eBTC debt amount withdrawn or repaid
    uint256 _newEBTCBorrowed; // Newly borrowed eBTC amount 
    // ... other parameters ...
}
```
The `_adjustCdpCallback` function can then be updated to use `_newEBTCBorrowed` for fee calculation:
```solidity
// Updated fee calculation logic
IERC20(address(ebtcToken)).safeTransfer(zapFeeReceiver, flData._newEBTCBorrowed * zapFeeBPS / BPS); 
```
