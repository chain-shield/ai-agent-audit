# Vulnerability details

The `openCdpWithWstEth` function allows users to specify the `_stEthDepositAmount` independently of the actual collateral converted from `_wstEthMarginBalance`. This can lead to situations where a CDP  is created with insufficient collateral. The  logic does not enforce that the converted margin balance (`_collVal`) matches the specified deposit amount (`_stEthDepositAmount`),resulting in under-collateralized positions.


## Impact
This will lead to the creation of CDPs that do not have enough collateral backing the issued debt. As a result, the stability of the protocol will be compromised. Users can exploit this to take out more debt than they should be able to.

By paying a very low `_wstEthMarginBalance` and a high `_stEthDepositAmount`, a user can create a CDP with very little actual collateral, effectively bypassing the system's checks and leading to an under-collateralized position.

When the call to Lido is made using `stETH.getSharesByPooledEth(_cdp.stETHToDeposit)`, it converts the amount of `stETHToDeposit` to its equivalent shares in Lido's system. This conversion is based on the total supply of stETH and the underlying pooled ETH.

However, due to the issue of "Inconsistent Collateral Assignment in `openCdpWithWstEth` Function," this call can potentially lead to under-collateralized CDP creation if not properly checked. Let's break down the flow and the implications:


1. **User Inputs Arbitrary Collateral Amount**:
   - The user can input any value for `_stEthDepositAmount`.
   - This value is used to set `cdp.stETHToDeposit`.

2. **Conversion to Lido Shares**:
   - The function `stETH.getSharesByPooledEth(_cdp.stETHToDeposit)` converts `_stEthDepositAmount` to the corresponding Lido shares.
   - The returned value represents how many Lido shares correspond to the specified stETH amount.

3. **Post-Check Parameters**:
   - The post-check parameters include `expectedCollateral`, which is calculated as `stETH.getSharesByPooledEth(_cdp.stETHToDeposit) * _tradeData.collValidationBufferBPS / BPS`.
   - This is meant to validate that the expected collateral is sufficient.

4. **Post-Operation Check**:
   - The post-operation check validates that the actual collateral in the CDP (`cdpInfo.coll`) is greater than or equal to the `expectedCollateral`.


The issue arises because the user can specify an arbitrarily high `_stEthDeposunt`, inflating the expected collateral and passing the post-operation checks, even if the actual collateral deposited is insufficient.

## Recommended Mitigation Steps
ensure that the actual converted collateral (`_collVal`) matches the specified deposit amount (`_stEthDepositAmount`). 

```solidity
function openCdpWithWstEth(
    uint256 _debt,
    bytes32 _upperHint,
    bytes32 _lowerHint,
    uint256 _stEthLoanAmount,
    uint256 _wstEthMarginBalance,
    uint256 _stEthDepositAmount,
    bytes calldata _positionManagerPermit,
    TradeData calldata _tradeData
) external returns (bytes32 cdpId) {
    uint256 _collVal = _convertWstEthToStETH(_wstEthMarginBalance);

    // Ensure the converted margin balance equals the deposit amount
    require(_collVal == _stEthDepositAmount, "EbtcZapRouter: Margin and deposit amounts do not match");

    cdpId = _openCdp(
        _debt,
        _upperHint,
        _lowerHint,
        _stEthLoanAmount,
        _collVal,
        _stEthDepositAmount,
        _positionManagerPermit,
        _tradeData
    );

    emit ZapOperationEthVariant(
        cdpId,
        EthVariantZapOperationType.OpenCdp,
        true,
        address(wstEth),
        _wstEthMarginBalance,
        _collVal,
        msg.sender
    );
}
```
Added a check to ensure `_collVal` (converted margin balance) is equal to `_stEthDepositAmount`.
