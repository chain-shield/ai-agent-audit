# Vulnerability details

The `_permitPositionManagerApproval()` function attempts to mitigate potential permit front-running using a try-catch block. However, this approach may not fully address the underlying vulnerability and could lead to security risks.

The function calls `borrowerOperations.permitPositionManagerApproval()` with the following parameters:
- `msg.sender` as the owner
- `address(this)` as the position manager
- `IPositionManagers.PositionManagerApproval.OneTime` as the approval type
- Various permit-related parameters (`deadline`, `v`, `r`, `s`)

The try-catch block is implemented as follows: [ZapRouterBase.sol#L119-L132](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/ZapRouterBase.sol#L119-L132)

```solidity
try
    borrowerOperations.permitPositionManagerApproval(
        msg.sender,
        address(this),
        IPositionManagers.PositionManagerApproval.OneTime,
        _positionManagerPermit.deadline,
        _positionManagerPermit.v,
        _positionManagerPermit.r,
        _positionManagerPermit.s
    )
{} catch {
    /// @notice adding try...catch around to mitigate potential permit front-running
    /// see: https://www.trust-security.xyz/post/permission-denied
}
```

While the intention is to mitigate front-running, this approach may introduce new vulnerabilities/mask important errors.

## Impact
1. The current implementation catches all exceptions without logging or handling them, potentially hiding critical errors or unexpected behavior.
2. Users and developers may assume that the front-running issue is fully resolved, when in reality, it may still be possible under certain conditions.
3. If the permit operation fails silently, it could lead to an inconsistent state between the contract and the user's expectations, potentially causing further issues in subsequent operations.

## Proof of Concept
Consider the following scenario:

1. An attacker monitors the mempool for `_permitPositionManagerApproval()` transactions.
2. When a legitimate transaction is detected, the attacker front-runs it with a higher gas price.
3. The attacker's transaction is processed first, invalidating the legitimate user's permit.
4. When the legitimate transaction is processed, it fails silently due to the try-catch block.
5. The user assumes their permit was successful, but in reality, it wasn't applied.

## Recommended Mitigation Steps
If keeping the try-catch approach, consider logging the error or emitting an event to provide transparency:

```solidity
try
    borrowerOperations.permitPositionManagerApproval(
        msg.sender,
        address(this),
        IPositionManagers.PositionManagerApproval.OneTime,
        _positionManagerPermit.deadline,
        _positionManagerPermit.v,
        _positionManagerPermit.r,
        _positionManagerPermit.s
    )
{} catch Error(string memory reason) {
    emit PermitOperationFailed(msg.sender, reason);
}
```

Or Consider implementing a status check after the permit operation to ensure it was successful, and revert the transaction if not:

```solidity
bool success = borrowerOperations.isPositionManagerApproved(msg.sender, address(this));
require(success, "Position manager approval failed");
```
