# Vulnerability details


## Proof of Concept

Take a look at https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/ZapRouterBase.sol#L72-L105

```solidity
    function _transferStEthToCaller(
        bytes32 _cdpId,
        EthVariantZapOperationType _operationType,
        bool _useWstETH,
        uint256 _stEthVal
    ) internal {
        if (_useWstETH) {
            // return wrapped version(WstETH)
            uint256 _wstETHVal = IWstETH(address(wstEth)).wrap(_stEthVal);
            emit ZapOperationEthVariant(
                _cdpId,
                _operationType,
                false,
                address(wstEth),
                _wstETHVal,
                _stEthVal,
                msg.sender
            );

            wstEth.transfer(msg.sender, _wstETHVal);
        } else {
            // return original collateral(stETH)
            emit ZapOperationEthVariant(
                _cdpId,
                _operationType,
                false,
                address(stEth),
                _stEthVal,
                _stEthVal,
                msg.sender
            );
            stEth.transfer(msg.sender, _stEthVal);
        }
    }
```

This function ends up being called in the case a cdp position is being closeed, i.e from [here](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/EbtcLeverageZapRouter.sol#L307-L308) in `EbtcLeverageZapRouter#_closeCdp()` or when it's been adjusted [here](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/EbtcLeverageZapRouter.sol#L460-L466) in `EbtcLeverageZapRouter#_adjustCdp()`, issue however is that with the current implementation, with every single position that is being closed, there would be 1-2 wei that's accumulating and not being sent to the user, this is because the[ amount of stETH that's being sent](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/EbtcLeverageZapRouter.sol#L301) is been cut-off by 1-2 wei since a normal `transfer()` is being used and not `transferFrom`.

Here is what [Lido's official docs](https://docs.lido.fi/guides/lido-tokens-integration-guide/#1-2-wei-corner-case) has to say about the 1-2-wei-corner-case

```rust
stETH balance calculation includes integer division, and there is a common case when the whole stETH balance can't be transferred from the account while leaving the last 1-2 wei on the sender's account. The same thing can actually happen at any transfer or deposit transaction. In the future, when the stETH/share rate will be greater, the error can become a bit bigger. To avoid it, one can use `transferShares` to be precise.
```

## Impact

As hinted under _Proof of Concept_, since we are sure of a 1-2 wei cut off from from the transfers, [the cut-off amount could be higher](https://docs.lido.fi/guides/lido-tokens-integration-guide/#1-2-wei-corner-case), then this leads to a break in protocol's accounting in regards to the amount of funds attached to a cdp position that gets closed, since not all the funds would be transferred to the user, i.e a minute loss of funds for users.

## Recommended Mitigation Steps

Consider directly using `transferShares` for stETH transfers, like is currently done in https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/LeverageZapRouterBase.sol#L88-L98

```solidity
    function _sweepStEth() private {
        /**
         * SWEEP TO CALLER *
         */
        // Safe unchecked because known tokens
        uint256 bal = stEth.sharesOf(address(this));

        if (bal > 0) {
            stEth.transferShares(msg.sender, bal);
        }
    }
```
