# Vulnerability details

## Impact
The function `ZapRouterBase::_depositRawEthIntoLido()` is using a low level `call` method to send raw `ETH`. This method, when failing to send out the `ETH`, will NOT revert the trxn, instead it will return a bool as `false`. However, the `_depositRawEthIntoLido()` function does not check that returned boolean before proceeding to the next steps. This will lead to the `_deposit` return value being `0` when that trxn fails, and this `0` will eventually be passed to the upstream functions to adjust the CDPs. 

The direct impact is that the adjust CDP operations will **NOT** work as the user expected and how it is supposed to be; moreover, the user's fund will get stuck in the router contract of `EbtcLeverageZapRouter` in the form of native `ETH`. The sweep functions the protocol has in design cannot help in this case, because those functions can only sweep tokens(eBTC and stETH) but not native `ETH`. These impacts combined absolutely make the issue **HIGH** severity.

The user touchpoint functions directly impacted by this issue are, for example, `adjustCdpWithEth` and `adjustCdpWithWrappedEth`. The other downstream validations in these functions are not adequate enough to catch the issue, hence cannot help revert it.

## Proof of Concept

The problematic piece of code is this:
```
    function _depositRawEthIntoLido(uint256 _initialETH) internal returns (uint256) {
        // check before-after balances for 1-wei corner case
        uint256 _balBefore = stEth.balanceOf(address(this));
        // TODO call submit() with a referral?
        payable(address(stEth)).call{value: _initialETH}(""); // @auditor ----- Didn't check the returned boolean
        uint256 _deposit = stEth.balanceOf(address(this)) - _balBefore;
        return _deposit; // @auditor ----- 0 value will be returned if the call method above failed
    }
```

Then, the `0` value will be returned to the upstream `_params.stEthMarginBalance` for adjustCDP operations. These operations will be performed on this wrong and unexpected value shown as below:

```
_adjustCdp(
    _cdpId, 
    _params, // @auditor ----- unexpected 0 value here in _params.stEthMarginBalance
    _positionManagerPermit, 
    _tradeData, 
    _zapStEthBalanceBefore
);
```

I wrote a test function as the POC shown below:

1. Setup: first, need to revise the `receiver()` in `ebtc-zap-router\lib\ebtc\packages\contracts\contracts\TestContracts\CollateralTokenTester.sol` to make it always revert. This is to simulate the situation where the router contract sending native `ETH` to Lido and the call method shall not be successful.
```
    receive() external payable {
        revert();
    }
```

2. Then, add this test function below in the contract `ebtc-zap-router/test/LeverageZaps.t.sol` and run it.
```
    function test_adjustCdp_debtIncrease_stEth_lido_revert() public {
        seedActivePool();

        (address user, bytes32 cdpId) = createLeveragedPosition(MarginType.stETH);

        IEbtcZapRouter.PositionManagerPermit memory pmPermit = createPermit(user);

        uint256 debtChange = 2e18;
        uint256 marginIncrease = 0.5e18;
        uint256 collValue = (_debtToCollateral(debtChange) * COLLATERAL_BUFFER) / 10000;
        uint256 flAmount = _debtToCollateral(debtChange);

        _before();
        vm.startPrank(user);
        leverageZapRouter.adjustCdpWithEth{value: 0.5e18}(
            cdpId,
            _getAdjustCdpParams(
                flAmount,
                int256(debtChange),
                int256(collValue),
                int256(marginIncrease),
                false
            ),
            abi.encode(pmPermit),
            _getExactInDebtToCollateralTradeData(debtChange)
        );
        vm.stopPrank();
        _after();

        // Test zap fee
        assertEq(
            eBTCToken.balanceOf(testFeeReceiver),
            ((1e18 + debtChange) * defaultZapFee) / 10000
        );

        _checkZapStatusAfterOperation(user);

        // The 0.5e18 worth of ETH sent from the user will get stuck in the router contract!!
        assertEq(address(leverageZapRouter).balance, 0.5e18);
    }
```

This test will pass, which means the adjust CDP operation can be executed with the unexpected and wrong `0` return value, it will **NOT** revert the trxn. In addition, the user's fund gets stuck in the router contract, because the native ETH transfer to Lido was not successful.

## Recommended Mitigation Steps
Must check the returned boolean of the `call` method, for example:
```
(bool success, ) = payable(address(stEth)).call{value: _initialETH}("");
require(success, "Sending ETH to Lido failed!");
```
