# Vulnerability details

`LeverageZapRouterBase` contract implements fee assessment mechanisms for various CDP (Collateralized Debt Position) operations. However, there is an inconsistency in how fees are applied across different operations, specifically between adjusting existing CDPs and opening new ones.

In the [_adjustCdpCallback()](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/LeverageZapRouterBase.sol#L294-L313) function, fees are only assessed when the debt increases:
```solidity
function _adjustCdpCallback(bytes memory data) internal override { 
    if (zapFeeBPS > 0) { 
        AdjustCdpOperation memory flData = abi.decode(data, (AdjustCdpOperation)); 
        
        // ... (operation logic) 
        if (flData._isDebtIncrease) { 
            IERC20(address(ebtcToken)).safeTransfer(zapFeeReceiver, flData._EBTCChange * zapFeeBPS / BPS); } 
        } else { 
            super._adjustCdpCallback(data); } }
```
However, in the [_openCdpForCallback()](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/LeverageZapRouterBase.sol#L276-L292) function, fees are always assessed, regardless of whether it's a debt increase:
```solidity
function _openCdpForCallback(bytes memory data) internal override { 
    if (zapFeeBPS > 0) { 
        OpenCdpForOperation memory flData = abi.decode(data, (OpenCdpForOperation)); 
        
        // ... (operation logic) 
        
        IERC20(address(ebtcToken)).safeTransfer(zapFeeReceiver, flData.eBTCToMint * zapFeeBPS / BPS); 
    } else { 
        super._openCdpForCallback(data); 
       } 
    }
```
This inconsistency could lead to users being charged fees in situations where they shouldn't be, particularly when opening new CDPs without increasing debt.

## Impact
Unfair fee assessment for users opening new CDPs without increasing debt

Potential economic imbalance in the protocol's fee structure

Inconsistency with the stated principle that fees should only be assessed on debt increases

## Proof of Concept
1. User A adjusts an existing CDP, increasing the debt by 100 eBTC
    - Fees are correctly assessed on the 100 eBTC increase
2. User B opens a new CDP with 100 eBTC debt
    - Fees are assessed on the entire 100 eBTC, even though this isn't technically a "debt increase" from the user's perspective

## Recommended Mitigation Steps
Align the fee assessment logic in `_openCdpForCallback()` with the principle of only charging fees on debt increases. This can be achieved by:

1. Treating the entire amount in a new CDP as a debt increase (current behavior), but documenting this decision and its rationale.

2. Alternatively, modify the `_openCdpForCallback()` function to only assess fees on the debt portion of new CDPs:
```solidity
function _openCdpForCallback(bytes memory data) internal override { 
    if (zapFeeBPS > 0) { 
        OpenCdpForOperation memory flData = abi.decode(data, (OpenCdpForOperation)); 
        
        bytes32 _cdpId = borrowerOperations.openCdpFor(
             flData.eBTCToMint, 
             flData._upperHint, 
             flData._lowerHint, 
             flData.stETHToDeposit, 
             flData.borrower );

            // Only assess fees on the debt portion
    uint256 debtPortion = _calculateDebtPortion(flData.eBTCToMint, flData.stETHToDeposit);
    IERC20(address(ebtcToken)).safeTransfer(zapFeeReceiver, debtPortion * zapFeeBPS / BPS);
} else {
    super._openCdpForCallback(data);
}
```
However, this approach would require implementing a `_calculateDebtPortion()` function to determine the portion of the minted eBTC that represents new debt.
