# Vulnerability details

The `EbtcLeverageZapRouter` contract allows users to perform various operations on Collateralized Debt Positions (CDPs) using different forms of Ether as collateral. These operations include opening, adjusting, and closing CDPs. The contract uses a position manager approval mechanism to allow the router to act on behalf of the user. However, the current implementation does not adequately ensure that this approval is revoked after each operation, potentially leaving users vulnerable to unauthorized actions on their CDPs.

In the `_openCdp()` and `_adjustCdp()` functions, the contract attempts to revoke the position manager approval after the operation is completed: [EbtcLeverageZapRouter.sol#L245-L247](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/EbtcLeverageZapRouter.sol#L245-L247)
```solidity
        if (_positionManagerPermit.length > 0) {
            borrowerOperations.renouncePositionManagerApproval(msg.sender);
        }
```
There is no verification that this revocation was successful. If the revocation fails for any reason, the router would retain approval to act on the user's behalf, which could be exploited in subsequent transactions.

## Impact
If the position manager's approval is not properly revoked, it could lead to several serious consequences:

1. In the worst-case scenario, an attacker could manipulate CDPs to extract value, potentially leading to significant financial losses for users.
2. Users expect their approval to be temporary and specific to a single operation. Lingering approvals violate this expectation and the principle of least privilege.

## Proof of Concept
Consider the following scenario:

1. A user calls `openCdpWithEth()` to open a new CDP.
2. The `_openCdp()` function is executed, which includes granting position manager approval to the router.
3. After the CDP is opened, the contract attempts to revoke the approval, but the revocation fails silently (e.g., due to a gas limit issue or a bug in the `borrowerOperations` contract).
4. The approval remains active, allowing the router to perform future operations on the user's CDP without explicit permission.
