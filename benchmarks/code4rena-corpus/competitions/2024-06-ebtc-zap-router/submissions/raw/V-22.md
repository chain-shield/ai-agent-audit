# Vulnerability details

## Summary
There's an issue with how the zap fee is handled within the `_openCdpForCallback` and `_adjustCdpCallback` functions. The bug is that the zap fee is being deducted from the full amount of eBTC minted/the full debt increase, without adjusting the actual amount minted or borrowed for the user. Users are receiving less eBTC than they expected, while still incurring the full debt.
```solidity
function _openCdpForCallback(bytes memory data) internal override {
    if (zapFeeBPS > 0) {
        OpenCdpForOperation memory flData = abi.decode(data, (OpenCdpForOperation));

        bytes32 _cdpId = borrowerOperations.openCdpFor(
            flData.eBTCToMint,
            flData._upperHint,
            flData._lowerHint,
            flData.stETHToDeposit,
            flData.borrower
        );

        IERC20(address(ebtcToken)).safeTransfer(zapFeeReceiver, flData.eBTCToMint * zapFeeBPS / BPS);
    } else {
        super._openCdpForCallback(data);
    }
}

function _adjustCdpCallback(bytes memory data) internal override {
    if (zapFeeBPS > 0) {
        AdjustCdpOperation memory flData = abi.decode(data, (AdjustCdpOperation));

        borrowerOperations.adjustCdpWithColl(
            flData._cdpId,
            flData._stEthBalanceDecrease,
            flData._EBTCChange,
            flData._isDebtIncrease,
            flData._upperHint,
            flData._lowerHint,
            flData._stEthBalanceIncrease
        );

        if (flData._isDebtIncrease) {
            IERC20(address(ebtcToken)).safeTransfer(zapFeeReceiver, flData._EBTCChange * zapFeeBPS / BPS);
        }
    } else {
        super._adjustCdpCallback(data);
    }
}
```
## Impact
This bug violates the expectation that **"Fee should be assessed only when debt increases"** because it's not adjusting the debt increase to account for the fee.

The fee is calculated based on the full amount of eBTC minted or debt increased, but this fee is not accounted for in the actual operation.
```solidity
// In _openCdpForCallback
bytes32 _cdpId = borrowerOperations.openCdpFor(
    flData.eBTCToMint,
    flData._upperHint,
    flData._lowerHint,
    flData.stETHToDeposit,
    flData.borrower
);

IERC20(address(ebtcToken)).safeTransfer(zapFeeReceiver, flData.eBTCToMint * zapFeeBPS / BPS);

// In _adjustCdpCallback
borrowerOperations.adjustCdpWithColl(
    flData._cdpId,
    flData._stEthBalanceDecrease,
    flData._EBTCChange,
    flData._isDebtIncrease,
    flData._upperHint,
    flData._lowerHint,
    flData._stEthBalanceIncrease
);

if (flData._isDebtIncrease) {
    IERC20(address(ebtcToken)).safeTransfer(zapFeeReceiver, flData._EBTCChange * zapFeeBPS / BPS);
}
```
The issue is that the full amount (`flData.eBTCToMint` or `flData._EBTCChange`) is used in the CDP operation, and then the fee is transferred out. The user's CDP is created/adjusted for the full amount, but they receive less eBTC than expected due to the fee.

We can walk through a scenario:
1. A user wants to open a CDP and mint 1000 eBTC.
2. The zapFeeBPS is set to 50 (0.5%).
3. The `_openCdpForCallback` function is called with `flData.eBTCToMint = 1000`.
4. A CDP is opened for 1000 eBTC.
5. 5 eBTC (1000 * 50 / 10000) is transferred to the zapFeeReceiver.
6. The user's CDP now has a debt of 1000 eBTC, but they only received 995 eBTC.

## Proof of Concept
1. First, let's look at the [EbtcLeverageZapRouter contract](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/EbtcLeverageZapRouter.sol#L171-L248)
2. At the [LeverageZapRouterBase contract](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-zap-router/src/LeverageZapRouterBase.sol#L276-L310) where the bug is present

1. Assume the following parameters:
    - User wants to open a CDP and mint 1000 eBTC
    - `zapFeeBPS` is set to 50 (0.5%)
    - `BPS` constant is 10000

2. The user calls openCdp function with _debt = 1000 eBTC.

3. This call propagates to _openCdp, which then calls `_openCdpOperation`.

4. Inside `_openCdpOperation`, it eventually calls `_openCdpForCallback`.

5. In `_openCdpForCallback`: a. It calls `borrowerOperations.openCdpFor` with `flData.eBTCToMint = 1000 eBTC`. b. Then it calculates and transfers the fee: `1000 * 50 / 10000 = 5 eBTC`.

6. The result of this operation:

    - A CDP is opened with a debt of 1000 eBTC
    - 5 eBTC is transferred to `zapFeeReceiver`
    - The user effectively receives only 995 eBTC, but their CDP has a debt of 1000 eBTC

## Tools Used
Manual Audit
## Recommended Mitigation Steps
The amount of eBTC minted or the debt increase should be adjusted to account for the fee before operating. The fee should be calculated and subtracted from the requested amount, ensuring that the user receives the correct amount of eBTC after the fee is deducted.
