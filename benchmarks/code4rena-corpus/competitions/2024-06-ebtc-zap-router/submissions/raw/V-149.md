# Vulnerability details


## Impact
The incorrect comparison logic within the `_doCheckValueType` function can lead to improper validation of post-operation conditions. This can cause the protocol to either allow operations that should be blocked or reject operations that should be allowed, leading to potential security and functional issues.

## Proof of Concept
The [`_doCheckValueType` function](https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-protocol/packages/contracts/contracts/LeverageMacroBase.sol#L277-L290) is designed to verify if a value satisfies certain conditions based on the provided operator. However, there is an error in the comparison logic for the `gte` (greater than or equal to) and `lte` (less than or equal to) operators.

Here is the problematic code snippet:

```solidity
function _doCheckValueType(CheckValueAndType memory check, uint256 valueToCheck) internal {
    if (check.operator == Operator.skip) {
        // Early return
        return;
    } else if (check.operator == Operator.gte) {
        require(check.value >= valueToCheck, "!LeverageMacroReference: gte post check");
    } else if (check.operator == Operator.lte) {
        require(check.value <= valueToCheck, "!LeverageMacroReference: let post check");
    } else if (check.operator == Operator.equal) {
        require(check.value == valueToCheck, "!LeverageMacroReference: equal post check");
    } else {
        revert("Operator not found");
    }
}
```

The issue lies in the `gte` and `lte` checks. The `gte` check should confirm that `valueToCheck` is greater than or equal to `check.value`, and the `lte` check should confirm that `valueToCheck` is less than or equal to `check.value`. The current implementation does the reverse.

- For `gte`, ensure that `valueToCheck` is greater than or equal to `check.value`.
