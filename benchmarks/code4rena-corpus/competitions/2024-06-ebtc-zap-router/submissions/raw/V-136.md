# Vulnerability details

## Vulnerability Details

1. In the call to `[openCdp()]` external function of the <EbtcLeverageZapRouter> contract, there's a collateral value based on the margin Amount that is transferred to the ZapRouterBase contract from the user. This represents the user's collateral put up to open the cdp... See #L181 of `EbtcLeverageZapRouter::openCdp` function. 
 + The contract then calls the internal [_openCdp] function, with the fifth param as this margin collateral value put up
2. In the internal [_openCdp()] , the function does not do anything with the user's put up collateral.. 
 + In fact, the put-up collateral isnot used anywhere within this function.. it's absolutely neglected..
 + `# instead of setting the openCdpForOperation.stEthToDeposit = collateralValue , it mistakenly sets it to stEthDepositAmount.` Now this is a user input parameter that can be set to any arbitrary value.
 + The only check associated with this stEthDepositAmount parameter is that it's supposed to be greater than 2.2e18, which means a user can set that input to a really high value, like type(uint256).max.

3. The contract then calls the internal [LeverageZapRouterBase::_openCdpForOperation] function with params of the newly set values for the openCdpForOperation struct.
 + This in turn calls the internal [LeverageMacroBase::_doOperation].
 + There is a return array that's passed into the [_doOperation] function as a parameter. This return array is obtained via the call to [_getPostCheckParams] with an interesting parameter here:

 `<stETH.getSharesByPooledEth(openCdpForOperation.stEthToDeposit)>   =====>>>>>> because of the inflated value set to this, the return shares will be extremely high...... Now, this function calculates the collateral shares using (this extremely high value * tradeData.collValidationBufferBPS)/ 10000, and the resultant gets assigned to PostCheckParams.expectedCollateral value`.....

4. Now, because we are opening a cdp position, the flashloan type to execute inside the `[_doOperation]` function will be stEth. This will call the flashloan function on the ActivePool contract. 
 + In the flashloan return callback from the ActivePool Contract to the leverageMacroBase contract, there's a call to `_handleOperation` which in turn calls `_openCdpForCallback(encoded_Data)`. The encoded_Data includes the eBTC token to mint as debt, and the put up inflated collateral <stETHToDeposit>.
+ Now inside the `[_openCdpForCallback]`, there's a call to the `borrowerOperations::openCdpFor --> _openCdp` function with params of the encoded_Data including the: `<stETHToDeposit>` inflated arbitrary value that was set from the beginning in the `EbtcLeverageZapRouter::openCdpFor` function .

5. Now this `borrowerOperations::_openCdp` uses the inflated collateral shares of the user as the user's put up collateral margin, which in truth, isn't. Look at some instances it utilizes this artificially inflated value
+ OpenCdpLocals memory vars;
  `vars.netStEthBalance = _calcNetStEthBalance(stETHToDeposit)`;

+ It even calculates a user's collateral shares based on this inflated value:
 uint256 _netCollAsShares = collateral.getSharesByPooledEth(`vars.netStEthBalance`)

+ It even calculates a user's ICR based on this artificially inflated value:
  vars.ICR = EbtcMath._compute(`vars.netStETHBalance`, vars.debt, vars.price)


6. Now after all checks, it finally initializes the cdp for the user within the borrowerOperations contract by calling `cdpManager::initializeCdp` function,and sets the user's collateral shares to this inflated arbitrary value
```
        cdpManager.initializeCdp(
            _cdpId,
            vars.debt,
            _netCollAsShares,
            _liquidatorRewardShares,
            _borrower
        );
```

7. Now, the malicious user armed with an infinite number of collateral shares, can close his position to receive this number of shares although he really didnot put up that much collateral, effectively stealing from the protocol including the shares of other users.

8. Malicious user puts up a 100 wei of stEth as the collateral stEth margin amount. However, he sets the `stEthDepositAmount` parameter to an extremely high value, say 1_000_000 e18. To write this value as his collateral shares in the cdp he is about to open, he sets the total expected debt parameter to be 1000 wei (This is because there is a require check that the expected debt should be 0 or greater than 1000). He also sets the stEthLoanAmount, ie, the flashloan amount to any value > 0, say 50 wei too. Now, this leveraged cpd position will be opened with user's collateral as 1_000_000e18. The malicious user can then later close his cdp position to take away his associated collateral, in this case, his 1_000_000e18 even though he didnot put up this amount of collateral in the first place.  


## Impact
1. Now, armed with this high collateral shares, comes with very high collateralization Ratio. Now with this extremely high ICR associated with the malicious user's cdp, he can borrow an extremely high amount of eBTC tokens from the protocol (even when he sets the flash loan amount to a very low value), and yet still his ICR will be above the minimum, effectively stealing the eBTC tokens from the protocol. 

2. When malicious user calls `EbtcLeverageZapRouter::closeCdp()`, his put up collateral is sent back to him, and his position is closed. However, the collateral shares that will be sent to the malicious user is the inflated collateral he had set when opening the leveraged position. The withdrawal will pass as he won't have any bad debt in the protocol. This will effectively have led to the stolen of either protocol shares or shares of other users or both. 


3. Malicious user can even DoS the protocol, by preventing other legitimate users from opening a position. 
 + When a user opens a leveraged position, and `cdpManager::initiliazeCdp` is called, `totalStaked` state variable of the `CdpManagerStorage.sol` contract is updated by being incremented by the user's cdp.stake value. See below#

`https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-protocol/packages/contracts/contracts/CdpManager.sol#L947`

`https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-protocol/packages/contracts/contracts/CdpManagerStorage.sol#L414-L423`

 + Now, this user's cdp.stake value is dependent on the user's cdp.coll value. So with high cdp.coll value comes with high cdp.stake value, which in turn increases the ` uint256 totalStake` state variable exponentially. #See below:

`https://github.com/code-423n4/2024-06-badger/blob/9173558ee1ac8a78a7ae0a39b97b50ff0dd9e0f8/ebtc-protocol/packages/contracts/contracts/CdpManagerStorage.sol#L426-L430`

+ Malicious user can attempt to push the `uint256 totalStaked` state variable to an extremely high value that is almost equal to type(uint256).max by opening 2 or more seperate leveraged positions.

+ Now, when legitimate users attempts to open a leveraged position, with their put up collateral margin, the `totalStaked` state variable will overflow, and the transaction to open a position will revert, effectively DoSing the protocol permanently.
