# Vulnerability details

The function verifyInstance rigidly checks if the staking token returned from a staking contract matches the OLAS token. This strict check can cause valid staking contracts using different tokens to fail verification, restricting the system's ability to integrate diverse staking mechanisms.

## Impact
This implementation prevents the incorporation of staking contracts that use tokens other than OLAS, potentially excluding beneficial partnerships and integrations that could enhance the platform's value and functionality.

## Proof of Concept
Suppose Alice sets up a new staking contract using a new token, NOT_OLAS, intending to integrate with the platform. Bob, an administrator, attempts to verify Alice's contract using verifyInstance:

1. Alice deploys her staking contract with NOT_OLAS.
2. Bob calls verifyInstance with Alice's contract address.
3. The function fetches the staking token from Alice's contract, which returns NOT_OLAS.
4. The verification fails because NOT_OLAS != OLAS, even though Alice's contract is secure and functions correctly.

This example shows how the rigid check could wrongly exclude Alice's legitimate and potentially valuable staking contract from the platform.

## Recommended Mitigation Steps
Adjust the verification logic to:

- Allow a list of approved tokens, not just OLAS, enhancing flexibility.
- Include a registry where new tokens can be proposed and approved for use in staking contracts through a governance process or administrative approval, ensuring security and diversity.
