# Vulnerability details

## Impact

The `_calculateStakingRewards` function in `StakingBase.sol` is responsible for calculating staking rewards for all services. However, there is a potential issue in the calculation of the `ts` variable, which represents the time difference used for reward calculation. If the `sInfo.tsStart` (the time a service started staking) is greater than the `tsCheckpointLast` (the timestamp of the last checkpoint), the `ts` is calculated as `block.timestamp - sInfo.tsStart`. This could lead to incorrect reward calculations if a service is staked after the last checkpoint, as the reward would be calculated based on the time since the service started staking, rather than the time since the last checkpoint.

This could result in some services receiving more rewards than they are entitled to, while others may receive less. This could create an unfair advantage for some participants and undermine the integrity of the staking system.

## Proof of Concept

Consider the following scenario:

1.  The last checkpoint occurred at timestamp 100.
2.  Service A started staking at timestamp 80.
3.  Service B started staking at timestamp 120.
4.  The current timestamp is 150.

According to the current implementation of `_calculateStakingRewards`, the time difference (`ts`) for both services would be calculated as:

*   Service A: `ts = 150 - 80 = 70`
*   Service B: `ts = 150 - 120 = 30`

However, the correct calculation for Service B should be:

*   Service B: `ts = 150 - 100 = 50` (time since the last checkpoint)

This discrepancy could lead to Service A receiving a disproportionately larger reward than Service B, even though Service B has been staked for a longer duration since the last checkpoint.

## Recommended Mitigation Steps

To mitigate this issue, the calculation of the `ts` variable in the `_calculateStakingRewards` function should be modified to consider the `tsCheckpointLast` when a service starts staking after the last checkpoint. The corrected code would look like this:

```solidity
// Calculate the liveness ratio in 1e18 value
// This subtraction is always positive or zero, as the last checkpoint is at most block.timestamp
ts = block.timestamp - serviceCheckpoint;
if (tsCheckpointLast > sInfo.tsStart) {
    ts = tsCheckpointLast - sInfo.tsStart;
}
```

This change ensures that the reward calculation is based on the time elapsed since the last checkpoint, regardless of when a service started staking.
