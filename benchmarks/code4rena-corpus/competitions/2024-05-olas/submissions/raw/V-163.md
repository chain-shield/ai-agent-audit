# Vulnerability details

## Impact

`VoteWeighting` smart contract is used by the protocol to enable Olas DAO members (via veOLAS) to vote on staking programs, assigning weights according to their preferences. It has individual weight params and also the cumulative ones. In the `_getSum()` function we update the bias and the slope of the point. However, if we remove a nominee, it becomes impossible to update those params in the next week.

## Proof of Concept

According to the spec:

```
To ensure compatibility with veOLAS, changes in vote weights per staking contract are scheduled for the next week
```

`_getSum()` function takes the current value of the `timeSum` and loops over `MAX_NUM_WEEKS`. And if the `t > block.timestamp` condition becomes true, the loop simply breaks:

https://github.com/code-423n4/2024-05-olas/blob/main/governance/contracts/VoteWeighting.sol#L225-230
```
  uint256 t = timeSum;
        Point memory pt = pointsSum[t];
        for (uint256 i = 0; i < MAX_NUM_WEEKS; i++) {
            if (t > block.timestamp) {
                break;
            }

```

So let's say `_getSum()` was called and the next time it can be called is 1 week later. At the same time, at the end of this week (say, day 6), a nominee is removed. Now `timeSum` value is updated:

https://github.com/code-423n4/2024-05-olas/blob/main/governance/contracts/VoteWeighting.sol#L605
```
 uint256 nextTime = (block.timestamp + WEEK) / WEEK * WEEK;
```

https://github.com/code-423n4/2024-05-olas/blob/main/governance/contracts/VoteWeighting.sol#L612
```
timeSum = nextTime;
```

There is also a call to the `_getSum()` inside of `removeNominee()`. However, it's day 6 and nothing is still updated. So basically the `timeSum` is assigned to the week later and now if we call `_getSum()`, the loop will break. So it basically can take far more than 1 week and it breaks compatibility with veOLAS.

Manual review.

## Recommended Mitigation Steps

Make sure `timeSum` param is correctly updated.
