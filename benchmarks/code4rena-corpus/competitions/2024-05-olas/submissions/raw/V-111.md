# Vulnerability details

## Impact
In the _sendMessage function, the code, `totalCost` is calculated as follows: [@ArbitrumDepositProcessorL1.sol:165](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/staking/ArbitrumDepositProcessorL1.sol#L165)
```solidity
uint256 totalCost = cost[0] + cost[1];
```
However, `cost[0]` is only set if `transferAmount > 0`. If `transferAmount` is zero, `cost[0]` remains uninitialized and holds its default value of zero.

The bug occurs when `transferAmount` is zero. In this case, `totalCost` will only include the value of cost[1], which represents the cost for the message transfer. The value of cost[0], which should represent the token transfer cost, is not taken into account.

As a result, when `transferAmount` is zero, the check `if (totalCost > msg.value)` may pass even if `msg.value` is insufficient to cover the total cost of the transaction.

The impact is that it introduces a vulnerability in the `_sendMessage` function when `transferAmount` is zero. 
[@ArbitrumDepositProcessorL1.sol:152-170](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/staking/ArbitrumDepositProcessorL1.sol#L152-L170)
```solidity
uint256[] memory cost = new uint256[](2);
if (transferAmount > 0) {
    if (maxSubmissionCostToken == 0) {
        revert ZeroValue();
    }

    // Calculate token transfer gas cost
    cost[0] = maxSubmissionCostToken + TOKEN_GAS_LIMIT * gasPriceBid;
}

// Calculate cost for the message transfer
cost[1] = maxSubmissionCostMessage + gasLimitMessage * gasPriceBid;
// Get the total cost
uint256 totalCost = cost[0] + cost[1];

// Check fot msg.value to cover the total cost
if (totalCost > msg.value) {
    revert LowerThan(msg.value, totalCost);
}
```
1. Insufficient Payment Check:
   - When `transferAmount` is zero, `cost[0]` remains uninitialized and holds its default value of zero.
   - The `totalCost` calculation only includes `cost[1]`, which represents the cost for the message transfer.
   - The check `if (totalCost > msg.value)` may pass even if `msg.value` is insufficient to cover the total cost of the transaction.
   - This means that a user can potentially execute the `_sendMessage` function without providing enough payment to cover the required costs.

2. Unintended Behavior:
   - If `transferAmount` is zero and `msg.value` is greater than or equal to cost[1], the function will proceed with the message transfer even though the token transfer cost (`cost[0]`) is not accounted for.
   - This can lead to unexpected behavior and inconsistencies in the contract's functionality.

## Proof of Concept
Assume the following scenario.

   - `transferAmount` is set to zero.
   - `maxSubmissionCostMessage` is set to 100.
   - `gasLimitMessage` is set to 50,000.
   - `gasPriceBid` is set to 10 gwei.

In this case:

   - `cost[0] remains uninitialized and holds its default value of zero.
   - `cost[1]` is calculated as `100 + 50,000 * 10 gwei = 500,000,100 gwei`.
   - `totalCost` is calculated as `0 + 500,000,100 gwei = 500,000,100 gwei`.

If a user sends a transaction with `msg.value` equal to or greater than `500,000,100 gwei`, the `if (totalCost > msg.value)` check will pass, even though the user has not provided any payment for the token transfer cost (`cost[0]`).

## Recommended Mitigation Steps
We can initialize `cost[0]` to zero before the conditional statement.
```solidity
uint256[] memory cost = new uint256[](2);
cost[0] = 0; // Initialize cost[0] to zero

if (transferAmount > 0) {
    if (maxSubmissionCostToken == 0) {
        revert ZeroValue();
    }

    // Calculate token transfer gas cost
    cost[0] = maxSubmissionCostToken + TOKEN_GAS_LIMIT * gasPriceBid;
}
```
By initializing `cost[0]` to zero, the `totalCost` calculation will always include the correct values, regardless of whether `transferAmount` is zero or not.
