# Vulnerability details

## Description
The processData internal function at the DefaultTargetDispenserL2 contract has a staking queue that receives new staking amounts to be redeemed in the future, in case the contract doesn't have enough OLAS balance to cover the requests. This can be seen in the following snippet:
```solidity
if (IToken(olas).balanceOf(address(this)) >= amount && localPaused == 1) {
                // Approve and transfer OLAS to the service staking target
                IToken(olas).approve(target, amount);
                IStaking(target).deposit(amount);

                emit StakingTargetDeposited(target, amount);
            } else {
                // Hash of target + amount + batchNonce
                bytes32 queueHash = keccak256(abi.encode(target, amount, batchNonce));
                // Queue the hash for further redeem
                stakingQueueingNonces[queueHash] = true;

                emit StakingRequestQueued(queueHash, target, amount, batchNonce, localPaused);
            }
```

While this works fine in the context of data processing, redeeming the queued staking incentive is not as straightforward. As the redeem function does not enforce any priority for hashes that have been received first, staking targets are able to redeem at any point.
## Impact
Queued staking incentives may never be redeemable, even if they have been queued much earlier than smaller incentives. The reason for that is the smaller incentives will be able to skip waiting periods by calling redeem as soon as any OLAS balance is added to the DefaultTargetDispenserL2 contract and bigger incentives targets will be required to wait till there is enough balance to cover their incentives.


## Tools Used
Manual review

## Recommended Mitigation Steps
Make sure to add a FIFO mechanism to ensure staking incentives are orderly distributed. 
An interesting mechanic would be to ensure the queue is fully paid before distributing incentives to new targets at the processData function. 
Another interesting addition would be at the redeem function, where a FIFO logic could be enforced by utilizing the batchNonce to allow prior incentives earners to redeem first.
