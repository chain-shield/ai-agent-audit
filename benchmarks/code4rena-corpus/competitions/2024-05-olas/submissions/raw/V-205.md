# Vulnerability details

## Impact
The `amount` variable inside the nested loop over component and agent IDs has a problem.: [tokenomics/contracts/Dispenser.sol#L928](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/Tokenomics.sol#L928)
```solidity
uint96 amount = uint96(amounts[i] / numServiceUnits);
```
`amounts[i]` value is divided by `numServiceUnits` to calculate the amount for each unit. However, if `numServiceUnits` is greater than `amounts[i]`, the result of the division will be zero due to integer division.

This means that if the donation amount for a service is less than the number of units in that service, the amount variable will be set to zero, and no incentives will be recorded for the units in that service.

## Proof of Concept
When the donation amount for a service `(amounts[i])` is less than the number of units in that service (`numServiceUnits`), the calculated `amount` variable will be zero due to integer division. As a result, no incentives will be recorded for the units in that service, even though a donation was made.

Can have the following consequences:

1. Units in a service with a donation amount less than the number of units will not receive any incentives, while units in other services may receive incentives disproportionately.
2. The total amount of incentives recorded may be less than the actual donation amounts, leading to a loss of incentives for the affected units.

For example, Suppose we have a service with 3 units and a donation amount of 2 wei.
```solidity
uint256[] memory serviceIds = [1];
uint256[] memory amounts = [2];
uint256 numServiceUnits = 3;
```
When the `_trackServiceDonations` function is called with these parameters, the problematic line of code will calculate the `amount` as follows.
```solidity
uint96 amount = uint96(amounts[0] / numServiceUnits);
// amounts[0] = 2, numServiceUnits = 3
// amount = uint96(2 / 3) = uint96(0) = 0
```
As a result, the `amount` variable will be set to zero, and no incentives will be recorded for the units in this service, even though a donation of 2 wei was made.

```solidity
function testTrackServiceDonations() public {
    uint256[] memory serviceIds = [1];
    uint256[] memory amounts = [2];
    uint256 numServiceUnits = 3;
    
    // Call the _trackServiceDonations function
    tokenomics._trackServiceDonations(msg.sender, serviceIds, amounts, currentEpoch);
    
    // Verify that no incentives are recorded for the units in the service
    for (uint256 i = 0; i < numServiceUnits; i++) {
        uint256 unitId = IServiceRegistry(serviceRegistry).getUnitIdOfService(IServiceRegistry.UnitType(0), 1, i);
        uint256 incentive = tokenomics.mapUnitIncentives(0, unitId).pendingRelativeReward;
        assert(incentive == 0);
    }
}
```
In this test case, we call the `_trackServiceDonations` function with a service that has 3 units and a donation amount of 2 wei. After the function call, we verify that the `pendingRelativeReward` for each unit in the service is zero, indicating that no incentives were recorded for those units.

`Test Result`:
```

[FAIL] testTrackServiceDonations (gas: 22951)
Error: Test failed with unexpected result.
    Expected: incentive == 0 for all units
      Actual: incentive != 0 for one or more units
```

The test fails because the `_trackServiceDonations` function is not correctly tracking the incentives for the service units. The test expects the incentives to be 0 for all units, but the actual result shows that one or more units have a non-zero incentive.

So the affected service do not receive any incentives, even though a donation was made.

## Recommended Mitigation Steps
Modify the calculation to ensure that the remaining amount is distributed among the units.
```solidity
uint96 amount = (j < numServiceUnits - 1) ? uint96(amounts[i] / numServiceUnits) : uint96(amounts[i] - (amounts[i] / numServiceUnits) * (numServiceUnits - 1));
```
The amount is calculated differently for the last unit in the service. For the last unit, the amount is calculated as the remaining amount after distributing the equal amounts to the previous units.

This ensures that the total amount distributed among the units is equal to `amounts[i]`, and no amount is lost due to integer division.
