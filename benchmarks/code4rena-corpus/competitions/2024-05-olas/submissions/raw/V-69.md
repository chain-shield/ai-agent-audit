# Vulnerability details

## Impact

Users who have locked their OLAS tokens cannot vote during the last voting period (i.e. last week) of their lock period due to an incorrect check in the `VoteWeighting` contract.

Despite having available voting power for the entire last voting period, a strict inequality check prevents users from voting. For example, if a user locks their OLAS for 1 week, they lose the ability to vote for the entire lock period. If they lock it for 2 weeks, they lose the ability to vote for 50% of their lock period, and so on.

As a result of this issue, users miss out on the opportunity to vote, potentially affecting critical decisions and reducing the effectiveness of their locked tokens. Additionally, their OLAS tokens remain locked and illiquid during a period in which they cannot vote.

## Proof of Concept

The issue lies in the `voteForNomineeWeights()` function of the `VoteWeighting` contract, specifically in the following check:

```sol
        uint256 lockEnd = IVEOLAS(ve).lockedEnd(msg.sender);
        uint256 nextTime = (block.timestamp + WEEK) / WEEK * WEEK; 
        
        // Check for the lock end expiration
        if (nextTime >= lockEnd) {
            revert LockExpired(msg.sender, lockEnd, nextTime);
        }
```

This code calculates the start time of the next voting period (`nextTime`) and checks that the user's lock end time (`lockEnd`) is strictly less than `nextTime`.

However, as shown in the `_createLockFor()` function in `veOLAS`, all unlock times are rounded down to weeks:

```sol
        // Lock time is rounded down to weeks
        // Cannot practically overflow because block.timestamp + unlockTime (max 4 years) << 2^64-1
        unchecked {
            unlockTime = ((block.timestamp + unlockTime) / WEEK) * WEEK;
        }
```

Due to this rounding down, the user's `lockEnd` will be equal to `nextTime`, causing the voting function to revert and preventing the user from voting during their last nominee voting period.

### Example Scenario

1. Alice locks her OLAS tokens in `veOLAS` for 2 weeks.
2. A week later, Alice attempts to vote since at this point she has 50% of her voting power (due to decay).

**Expected:** Alice should be able to successfully cast her vote for nominees.

**Actual:** Alice's transaction is reverted. Due to the above-mentioned issue, she cannot cast her vote, while her tokens remain locked and illiquid.

## Recommended Mitigation Steps

To address this issue, the check in `VoteWeighting` should be updated as follows:

```sol
        // Check for the lock end expiration
        if (nextTime > lockEnd) {
            revert LockExpired(msg.sender, lockEnd, nextTime);
        }
```

This change will ensure that users can still vote in their last nominee voting period, thereby fully utilizing their voting power throughout the entire lock period.
