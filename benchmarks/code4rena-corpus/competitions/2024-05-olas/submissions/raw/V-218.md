# Vulnerability details

The function getStakingState does not define a default staking state for services that are neither evicted nor currently staked. This oversight can lead to ambiguous behavior when querying the staking state of services that have never been staked or have been unstaked without being evicted.

## Impact
This can cause confusion or incorrect assumptions in the system's operation, potentially leading to errors in interfacing systems or user interfaces that rely on a well-defined staking state for all services.

## Proof of Concept
Consider querying a service that was registered but never staked. The function will return an uninitialized staking state, which might lead to undefined behavior depending on how the state is consumed by calling contracts or interfaces.

## Tools Used

## Recommended Mitigation Steps
Add a default state, such as Unstaked, to handle cases where sInfo.tsStart is 0 and sInfo.inactivity does not exceed maxInactivityDuration. This would ensure that all paths return a valid state, clarifying the system's behavior and improving robustness.

`if (sInfo.inactivity > maxInactivityDuration) {
    stakingState = StakingState.Evicted;
} else if (sInfo.tsStart > 0) {
    stakingState = StakingState.Staked;
} else {
    stakingState = StakingState.Unstaked;  // Default state for services that are not staked or evicted
}`
