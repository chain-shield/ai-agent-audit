# Vulnerability details

## Impact
`changeStakingParams` function has an issue in the following lines: [tokenomics/contracts/Dispenser.sol#L771-L775](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/Tokenomics.sol#L771-L775)
```solidity
// All the adjustments will be accounted for in the next epoch
uint256 eCounter = epochCounter + 1;
StakingPoint storage stakingPoint = mapEpochStakingPoints[eCounter];
stakingPoint.maxStakingIncentive = uint96(_maxStakingIncentive);
stakingPoint.minStakingWeight = uint16(_minStakingWeight);
```
The problem is that the function directly accesses and modifies the `StakingPoint` struct for the next epoch (`epochCounter + 1`) without checking if that epoch already exists in the `mapEpochStakingPoints` mapping.

If the `changeStakingParams` function is called multiple times within the same epoch, it will overwrite the staking parameters for the next epoch each time. **`This can lead to unexpected behavior and loss of previously set staking parameters.`**

> If the DAO or the contract owner calls the `changeStakingParams` multiple times within the same epoch, only the last set of staking parameters will be effective for the next epoch. Any previous calls to the function within the same epoch will be overwritten, and their intended staking parameter changes will be lost.

This can cause confusion and inconsistency in the staking mechanism, as the actual staking parameters applied in the next epoch may not reflect the intended changes made by the DAO or the contract owner.

In this code, the `eCounter` variable is set to the next epoch by incrementing the current `epochCounter` by 1. Then, the `stakingPoint` variable is declared as a reference to the `StakingPoint` struct in the `mapEpochStakingPoints` mapping for the next epoch.

The issue arises because the code directly modifies the `maxStakingIncentive` and `minStakingWeight` fields of the `stakingPoint` struct without checking if the `StakingPoint` entry for the next epoch already exists in the mapping.

**`Example Scenario`**: Let's consider an example scenario to illustrate the impact.

  1. Assume the current `epochCounter` is 5.
  2. The DAO calls the `changeStakingParams` function with the following parameters:
   - `_maxStakingIncentive` = 1000
   - `_minStakingWeight` = 5000

  3. The function executes and sets the staking parameters for the next epoch (epoch 6) in the `mapEpochStakingPoints` mapping.
  4. Later within the same epoch (epoch 5), the DAO calls the `changeStakingParams` function again with different parameters:
   - `_maxStakingIncentive` = 1500
   - `_minStakingWeight` = 6000

  5. The function executes again and overwrites the previously set staking parameters for epoch 6 in the `mapEpochStakingPoints` mapping.

In this scenario, the first call to `changeStakingParams` with `_maxStakingIncentive` = 1000 and `_minStakingWeight` = 5000 is effectively lost, and only the second call with `_maxStakingIncentive` = 1500 and `_minStakingWeight` = 6000 will be applied in epoch 6.

## Recommended Mitigation Steps
First, check if the `StakingPoint` struct for the next epoch already exists in the mapping. If it doesn't exist, you can create a new entry in the mapping before modifying the staking parameters.
```solidity
// All the adjustments will be accounted for in the next epoch
uint256 eCounter = epochCounter + 1;
if (mapEpochStakingPoints[eCounter].maxStakingIncentive == 0 && 
    mapEpochStakingPoints[eCounter].minStakingWeight == 0) {
    // Create a new entry in the mapping for the next epoch
    mapEpochStakingPoints[eCounter] = StakingPoint({
        maxStakingIncentive: uint96(_maxStakingIncentive),
        minStakingWeight: uint16(_minStakingWeight)
    });
} else {
    // Update the existing staking parameters for the next epoch
    mapEpochStakingPoints[eCounter].maxStakingIncentive = uint96(_maxStakingIncentive);
    mapEpochStakingPoints[eCounter].minStakingWeight = uint16(_minStakingWeight);
}
```

If an entry already exists, the function will update the existing staking parameters instead of overwriting them.
