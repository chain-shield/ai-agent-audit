# Vulnerability details

## Impact
Getter functions like `getNomineeId` and `getNextAllowedVotingTimes` return corrupted values from a removed nominee that will err off chain calculations instead of rightfully returning 0 for `getNomineeId` and reverting with `NomineeDoesNotExist` error in `getNextAllowedVotingTimes`.

## Proof of Concept

In removeNominee, we see that 
```
    function removeNominee(bytes32 account, uint256 chainId) external {
    .
    .

        // Get the nominee id in the nominee set
        uint256 id = mapNomineeIds[nomineeHash];
    .
        // Remove nominee from the map
@>      mapNomineeIds[nomineeHash] = 0;

        // Shuffle the current last nominee id in the set to be placed to the removed one
        nominee = setNominees[setNominees.length - 1];
        bytes32 replacedNomineeHash = keccak256(abi.encode(nominee));
@>      mapNomineeIds[replacedNomineeHash] = id;
        setNominees[id] = nominee;
        // Pop the last element from the set
        setNominees.pop();
    .
    .
    .
}
```

* Here, in the code. the `mapNomineeIds` for the nomineeHash to remove is set 0 at the start.

* `mapNomineesIds` for the last element is overwritten with the id of the just removed nomineeHash.

* Then the last nominee is taken from `setNominees` and it's set to the id position in the array of `setNominees`

* The `setNominees` pops the last element

This approach works when the element to remove is not the last element in `setNominees`, However when the element to remove is the last element then the nominee is removed from `setNominees`. The id it has lingers in the value of `mapNomineeIds` as we're overwriting it with the id of the removed element.

This errs getter functionalities since mapNomineeIds is assumed to be zero for removed nominees but it need not be the case, confusing users and off chain processors.

## Tools Used
Manual analysis

## Recommended Mitigation Steps
Have `mapNomineeIds[replacedNomineeHash] = id` only when id of nominee to remove isn't the last
