# Vulnerability details

## Impact
In the `_getSum` function the loop condition and the update of `timeSum`. [VoteWeighting:_getSum#L227-L246](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L227-L246)
```solidity
for (uint256 i = 0; i < MAX_NUM_WEEKS; i++) {
    if (t > block.timestamp) {
        break;
    }
    // ...
    if (t > block.timestamp) {
        timeSum = t;
    }
}
```
The issue is that the loop continues to iterate even when `t` exceeds `block.timestamp`. This means that the function will keep updating `pointsSum` and `timeSum` for future timestamps, which is not the intended behavior.

## Proof of Concept
```solidity
// Assume the current block.timestamp is 1000 and WEEK is 7 (for simplicity)
// timeSum is initially set to 1000

// First iteration:
// t = 1000, pointsSum[1000] is updated

// Second iteration:
// t = 1007, pointsSum[1007] is updated, timeSum is updated to 1007

// Third iteration:
// t = 1014, pointsSum[1014] is updated, timeSum is updated to 1014

// ...

// The loop continues until i reaches MAX_NUM_WEEKS or t exceeds block.timestamp
```
The function updates `pointsSum` and `timeSum` for future timestamps (1007, 1014, etc.), even though the current `block.timestamp` is 1000. This leads to the inclusion of vote weights from future data points, resulting in incorrect calculations and potential manipulation.

## Tools Used
Vs

## Recommended Mitigation Steps
Update the loop condition to break when `t` exceeds `block.timestamp`.
```solidity
for (uint256 i = 0; i < MAX_NUM_WEEKS && t <= block.timestamp; i++) {
    // ...
    pointsSum[t] = pt;
    timeSum = t;
    t += WEEK;
}
```
The loop condition is changed to `i < MAX_NUM_WEEKS && t <= block.timestamp`, ensuring that the loop breaks when `t` exceeds `block.timestamp`.
The update of `timeSum` is moved outside the conditional statement and is performed in each iteration.
The increment of `t` is moved to the end of the loop to ensure proper iteration.
