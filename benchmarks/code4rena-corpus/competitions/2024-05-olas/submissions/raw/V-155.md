# Vulnerability details

## Impact

The current implementation of `Dispenser` allows to return some amount back to `Tokenomics` if a nominee (staking target) hasn't met the minimum staking weight requirement. The problem is that the contract does it inconsistently making return amount greater than it should be in the case when the weight of the nominee is less than minimum staking weight.


## Proof of Concept

Inside of the `claimStakingIncentives()` function there is a call to an internal function `calculateStakingIncentives()` that calculates the amounts that would be sent to the targets and the amount that would return back to the `Tokenomics` (if the minimal requirement was not met):

https://github.com/code-423n4/2024-05-olas/blob/main/tokenomics/contracts/Dispenser.sol#L911-914
```  
if (stakingWeight < uint256(stakingPoint.minStakingWeight) * 1e14) {
                // If vote weighting staking weight is lower than the defined threshold - return the staking incentive
                returnAmount = ((stakingDiff + availableStakingAmount) * stakingWeight) / 1e18;
            } 
```

The problem is that the function uses one formula for return amount for the user that hasn't met criteria and the different one when everything is fine:

https://github.com/code-423n4/2024-05-olas/blob/main/tokenomics/contracts/Dispenser.sol#L918
```
 returnAmount = (stakingDiff * stakingWeight) / 1e18;
```

Let's consider the following example:

```
availableStakingAmount = 200
totalWeightSum = 100
```

So the if-condition is used and we get the `stakeDiff` equal to 100:

https://github.com/code-423n4/2024-05-olas/blob/main/tokenomics/contracts/Dispenser.sol#L904-907
```
if (availableStakingAmount > totalWeightSum) {
                stakingDiff = availableStakingAmount - totalWeightSum;
                availableStakingAmount = totalWeightSum;
            }
```

Let's say there are 3 users:

User have weight of 1 (1%)
User2 have weight of 49
User3 have weight of 50

`minStakingWeight` param is set to 5% so the first user is not eligible for incentives and the `returnAmount` is calculated:

```
(100 + 200) * 1 / 100 = 3 tokens
```

Then we calculate incentive amount and return amount for other users:

User2 staking incentive:

https://github.com/code-423n4/2024-05-olas/blob/main/tokenomics/contracts/Dispenser.sol#L916
```
stakingIncentive = (availableStakingAmount * stakingWeight) / 1e18;
```


```
100 (availableStakingAmount) * 49 / 100 = 49 tokens
```

User2 return amount:

https://github.com/code-423n4/2024-05-olas/blob/main/tokenomics/contracts/Dispenser.sol#L918
```
returnAmount = (stakingDiff * stakingWeight) / 1e18;
```

```
103 (stakingDiff) * 49 / 100 = 50 tokens
```


User3 staking incentive = 100 * 50 / 100 = 50 tokens
User3 return amount = 153 * 50 / 100 = 76 tokens

This scenario assumes that the calls are made in sequential order from user1 to user3.

So by summing up the total return amount and total staking incentive we get 228
 tokens that is more than the initial amount of 200 (`availableStakingAmount`) making the `stakingIncentive` parameter in `Tokenomics` overinflated.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Change the formula to avoid returning abundant amounts back to the `Tokenomics` contract.
