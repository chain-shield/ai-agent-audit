# Vulnerability details

## Impact
`nextTime` variable is used to set the `timeWeight` for the new nominee. The intention is to round up the current timestamp to the next multiple of `WEEK`, so that the nominee's weight is updated at the beginning of the next week. However, the current calculation `(block.timestamp + WEEK) / WEEK * WEEK` fails to handle the case when `block.timestamp` is already a multiple of `WEEK`.

Code: [VoteWeighting/_addNominee#L309](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L309)
```solidity
uint256 nextTime = (block.timestamp + WEEK) / WEEK * WEEK;
```
The intention behind this calculation seems to be to round up the current timestamp to the next multiple of `WEEK`. However, there's a potential issue with this calculation when `block.timestamp` is already a multiple of `WEEK`.

If `nextTime` is set to the current week instead of the next week, the nominee's weight will be updated at the beginning of the current week, rather than the beginning of the next week. This means that the nominee's weight will be updated too early, affecting the voting process and the overall weight distribution among nominees.

## Proof of Concept
```solidity
pragma solidity ^0.8.0;

contract Example {
    uint256 public constant WEEK = 604800; // 1 week in seconds

    function calculateNextTime(uint256 timestamp) public pure returns (uint256) {
        return (timestamp + WEEK) / WEEK * WEEK;
    }
}
```
If we deploy this contract and call the `calculateNextTime` function with a timestamp that is a multiple of `WEEK`, the output would be the same as the input timestamp.

Here's why:
  1. `timestamp + WEEK` would result in a value that is still a multiple of `WEEK`.
  2. Dividing that result by `WEEK` would result in an integer (since timestamp is a multiple of `WEEK`).
  3. Multiplying that integer by `WEEK` would result in the original timestamp value.

For example, if we call `calculateNextTime` with a timestamp of `1209600` (which is a multiple of `WEEK`), the output would be `1209600`.

The current implementation of the `calculateNextTime` has a bug. When called with a timestamp that is already a multiple of `WEEK`, it simply returns the same timestamp instead of rounding up to the next multiple of `WEEK`.

Calling `calculateNextTime` with `1209600` (2 weeks in seconds) should return `1814400` (3 weeks in seconds), which is the next multiple of `WEEK`. However, due to the bug, it incorrectly returns `1209600`.

```solidity
Example example = new Example();

// Call the function with a timestamp that is a multiple of WEEK
uint256 timestamp = 1209600; // 2 weeks in seconds
uint256 nextTime = example.calculateNextTime(timestamp);

// Output: nextTime = 1209600 (should be 1814400, which is the next multiple of WEEK)
```
This proves that the current calculation in the `_addNominee` can lead to incorrect `timeWeight` values when `block.timestamp` is a multiple of `WEEK`.

## Recommended Mitigation Steps
Modify the calculation to ensure that `nextTime` is always set to the next multiple of `WEEK` after the current timestamp, even when `block.timestamp` is already a multiple of WEEK
```solidity
uint256 nextTime = ((block.timestamp + WEEK - 1) / WEEK) * WEEK;
```
This calculation first adds `WEEK - 1` to `block.timestamp`, ensuring that the result is always greater than or equal to the current timestamp. Then, it rounds down to the nearest multiple of `WEEK` and multiplies it by `WEEK` to get the next multiple of `WEEK` after the current timestamp.
