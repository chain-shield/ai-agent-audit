# Vulnerability details

## Vulnerability Details: Lack of Access Control in `addNomineeEVM` Function

### Description
The `addNomineeEVM` function in the `VoteWeighting` contract lacks any form of access control, allowing any external account to call this function. This can lead to unauthorized users adding nominees, potentially causing spam, denial of service (DoS) attacks, and compromising the integrity of the nomination process.

### Vulnerability Type
- Access Control
- Denial of Service (DoS)
- Data Integrity

### Affected Code
The vulnerability is located in the `addNomineeEVM` function of the `VoteWeighting` contract. The relevant code section can be found [here](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L324-L344).

```solidity
function addNomineeEVM(address account, uint256 chainId) external {
    // Check for the zero address
    if (account == address(0)) {
        revert ZeroAddress();
    }

    // Check for zero chain Id
    if (chainId == 0) {
        revert ZeroValue();
    }

    // Check for the chain Id overflow
    if (chainId > MAX_EVM_CHAIN_ID) {
        revert Overflow(chainId, MAX_EVM_CHAIN_ID);
    }

    Nominee memory nominee = Nominee(bytes32(uint256(uint160(account))), chainId);

    // Record nominee instance
    _addNominee(nominee);
}
```

Additionally, the `Nominee` struct and `setNominees` array are defined as follows:

```solidity
struct Nominee {
    bytes32 account;
    uint256 chainId;
}

Nominee[] public setNominees;
uint256 public constant MAX_EVM_CHAIN_ID = type(uint64).max / 2 - 36;

Therefore, since solidity will create a getter function for public variables a few attackers can see the chainId and MAX_EVM_CHAIN_ID. For example we may assume that good chainId(s) will be well distributed inside `setNominees` array.
```
The relevant code for these definitions can be found [here](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L159).

### Impact
1. **Unauthorized Access:** Any user can call the `addNomineeEVM` function and add nominees without restriction.
2. **Spam and DoS Attacks:** Malicious actors can flood the contract with numerous or invalid nominees, potentially leading to DoS attacks.
3. **Data Integrity:** The integrity of the nomination process is compromised as unauthorized or fake nominees can be added.

### Recommended Mitigation
To address these vulnerabilities, the following changes are recommended:

1. **Implement Access Control:**
   Use access control mechanisms such as `onlyOwner` or role-based access controls to restrict who can call the `addNomineeEVM` function. For example:
   ```solidity
   modifier onlyOwner() {
       require(msg.sender == owner, "Not authorized");
       _;
   }

   function addNomineeEVM(address account, uint256 chainId) external onlyOwner {
       // function body
   }
   ```
