# Vulnerability details

### Vulnerability Details: Dangerous Race Condition and Bad Practice in Array Handling

**Vulnerability Type:**
- Dangerous Race Condition
- Bad Practice in Array Handling

**Location in Code:**
- [VoteWeighting.sol#L621-L627](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L621-L627)

**Description:**
The current implementation of removing the last element from the `setNominees` array and shuffling the elements can lead to dangerous race conditions and is considered a bad practice. This is because arrays are class properties and can be accessed and modified concurrently, leading to potential inconsistencies and unexpected behavior.

Here's the problematic section of the code:

```solidity
// Shuffle the current last nominee id in the set to be placed to the removed one
nominee = setNominees[setNominees.length - 1];
bytes32 replacedNomineeHash = keccak256(abi.encode(nominee));
mapNomineeIds[replacedNomineeHash] = id;
setNominees[id] = nominee;
// Pop the last element from the set
setNominees.pop();
```

### Issues Identified:

1. **Race Condition:**
   The access and modification of `setNominees` and `mapNomineeIds` without proper synchronization can lead to race conditions. Multiple concurrent calls to this code segment can result in corrupted state or unexpected behavior due to simultaneous reads and writes.

2. **Accessing and Popping from the Array:**
   The code assumes that `setNominees` is not empty without explicit checks, which can lead to runtime errors if `setNominees` is empty. This can disrupt the flow of the contract and result in failed transactions.

3. **Bad Practice in Array Handling:**
   Directly manipulating class properties without encapsulation or checks is a bad practice. It makes the code harder to maintain and reason about, especially in a concurrent execution environment like blockchain.

### Recommended Fix:

Implement a function to safely remove and return an element from the array while ensuring atomicity of operations. Here’s an improved version of the code:

for example usage of pop without specification of the desired element is not entirely safe. 

for example usage of setNominees.length - 1 at two individuals lines or essentially setNominees.length - 1 initially then finally pop() will not be entirely safe.

if this was a possibility for example where nominee = setNominees.pop(); will be preferred
if this was a possibility for example where nominee = setNominees.remove(index); will be preferred

```
