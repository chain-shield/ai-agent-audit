# Vulnerability details

## Vulnerability Report: Bypassing `voteForNomineeWeights` Security Mechanisms

### Overview

This report highlights a critical vulnerability in the `voteForNomineeWeights` function of the `VoteWeighting` contract. The vulnerability stems from the lack of access control that persists well into the `addNomineeEVM` function, which is a critical piece in bypassing the intended security mechanisms of the `voteForNomineeWeights` function. This document provides a step-by-step explanation of how an attacker can exploit this vulnerability, the variables and logic that can be manipulated, and the state changes that will occur as a result.

### Affected Function
The primary function affected by this vulnerability is `voteForNomineeWeights`, which is designed to allow users to vote on the weights of different nominees.

### Links to Code
- `voteForNomineeWeights` function: [Link](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L483)
- `addNomineeEVM` function: [Link](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L324-L344)

### Step-by-Step Explanation of the Attack

1. **Exploiting the `addNomineeEVM` Function**:
   - **Public Access**: The `addNomineeEVM` function can be called by anyone.
   - **Lack of Access Control**: There are no restrictions on who can call this function, allowing any user to add a nominee.
   - **Adding Unauthorized Nominees**: An attacker can add nominees with arbitrary addresses and chain IDs, bypassing any intended restrictions on nominee additions.

2. **Setting Up for `voteForNomineeWeights`**:
   - **Initialize Parameters**: The attacker initializes parameters for the `voteForNomineeWeights` function with the unauthorized nominee added in the previous step.
   - **Construct Nominee Hash**: The `voteForNomineeWeights` function uses the `account` and `chainId` to create a nominee hash, which uniquely identifies the nominee.

3. **Voting for Nominee Weights**:
   - **Get User Voting Power**: The function retrieves the user's voting power and checks if the user has enough power to vote for the nominee's weight.
   - **Calculate New and Old Slopes**: The function calculates new and old slopes and biases based on the user's voting power and the nominee's current weight.
   - **Update Nominee Weight**: The function updates the nominee's weight based on the calculated slopes and biases.

4. **Potential Manipulations**:
   - **Manipulating Slope and Bias Calculations**: By adding unauthorized nominees, an attacker can manipulate the slope and bias calculations to favor their nominees.
   - **Vote Too Often**: The function checks if the user is voting too frequently. However, since the nominee is unauthorized, this check can be bypassed.
   - **Overflow Check**: The function checks if the new voting power exceeds the maximum allowed weight. An attacker can set a weight that bypasses this check.

5. **State Changes**:
   - **Persistent State Changes**: Once the unauthorized nominee is added, all state changes associated with this nominee persist. This includes changes to the `pointsWeight` mapping, which tracks the weight of each nominee.
   - **Impact on Nominee Weights**: Unauthorized nominees can significantly alter the weight distribution, affecting the overall voting process and the outcome of votes.

### Impact
- **Unauthorized Access**: The lack of access control allows any user to add nominees, compromising the integrity of the nomination process.
- **Manipulated Voting**: Unauthorized nominees can manipulate the voting process, affecting the distribution of weights and the outcome of votes.
- **Persistent State Changes**: Unauthorized state changes can persist, leading to long-term effects on the contract's state and behavior.

### Recommended Mitigations
To address these vulnerabilities, the following changes are recommended:

1. **Implement Access Control**:
   - Use access control mechanisms such as `onlyOwner` or role-based access controls to restrict who can call the `addNomineeEVM` function.

2. **Validate Nominee Existence**:
   - Ensure that nominees cannot be added multiple times or after being removed. Implement additional checks to validate the nominee's existence and eligibility.

3. **Re-evaluate Voting Mechanisms**:
   - Enhance the security checks within the `voteForNomineeWeights` function to ensure that unauthorized nominees cannot manipulate the voting process.

### Conclusion
This report highlights the critical vulnerability in the `voteForNomineeWeights` function, stemming from the lack of access control in the `addNomineeEVM` function. By implementing the recommended mitigations, the contract's security and integrity can be significantly improved, preventing unauthorized access and manipulation of the voting process.

## Vulnerability Report: Bypassing Checks and Manipulating Voting Power in `voteForNomineeWeights`

### Overview

This report identifies a vulnerability in the `voteForNomineeWeights` function of the `VoteWeighting` contract, where various checks are bypassed due to default zero values for unknown `msg.sender`. This allows an attacker to predict and manipulate the voting power, leading to unauthorized changes in nominee weights.

### Affected Function
The primary function affected by this vulnerability is `voteForNomineeWeights`.

### Links to Code
- `voteForNomineeWeights` function: [Link](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L483)
- `getLastUserPoint` function: [Link](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/veOLAS.sol#L145-L150)
- `lockedEnd` function: [Link](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/veOLAS.sol#L153)

### Detailed Analysis

1. **Initialization of Variables for Unknown `msg.sender`**:
   - If `msg.sender` does not exist in the contract's mappings, functions like `getLastUserPoint` and `lockedEnd` return default zero values.
   - **`getLastUserPoint`**: Returns an uninitialized `PointVoting` struct, where `slope` and other fields are 0.
   - **`lockedEnd`**: Returns 0 if `msg.sender` has no locked balance.

2. **Predicting Power Used**:
   - **Old Slope and Bias**: For unknown `msg.sender`, `oldSlope` is uninitialized, resulting in `oldSlope.slope` and `oldSlope.end` being 0.
   - **New Slope and Bias**: Calculated as:
     ```solidity
     VotedSlope memory newSlope = VotedSlope({
         slope: uint256(uint128(userSlope)) * weight / MAX_WEIGHT,
         end: lockEnd,
         power: weight
     });
     ```
     Given `userSlope` and `lockEnd` are 0, `newSlope.slope` and `newSlope.end` are also 0. Hence, `newBias` becomes 0.
   - **Power Used**: 
     ```solidity
     uint256 powerUsed = voteUserPower[msg.sender];
     powerUsed = powerUsed + newSlope.power - oldSlope.power;
     voteUserPower[msg.sender] = powerUsed;
     ```
     Since both `newSlope.power` and `oldSlope.power` are 0 for unknown `msg.sender`, `powerUsed` equals `weight`.

3. **Bypassing Checks**:
   - **Weight Check**:
     ```solidity
     if (weight > MAX_WEIGHT) {
         revert Overflow(weight, MAX_WEIGHT);
     }
     ```
     This check ensures `weight` is within a valid range.
   - **Last Voting Time Check**:
     ```solidity
     uint256 nextAllowedVotingTime = lastUserVote[msg.sender][nomineeHash] + WEIGHT_VOTE_DELAY;
     if (nextAllowedVotingTime > block.timestamp) {
         revert VoteTooOften(msg.sender, block.timestamp, nextAllowedVotingTime);
     }
     ```
     For unknown `msg.sender`, `lastUserVote[msg.sender][nomineeHash]` is 0, making `nextAllowedVotingTime` equal to `WEIGHT_VOTE_DELAY`. Since this is significantly less than the current timestamp, the check is bypassed.

4. **State Changes**:
   - The unauthorized state changes persist, affecting the contract's state and behavior. For example:
     ```solidity
     pointsWeight[nomineeHash][nextTime].bias = _maxAndSub(_getWeight(account, chainId) + newBias, oldBias);
     ```
     Here, both `newBias` and `oldBias` are 0, so `pointsWeight[nomineeHash][nextTime].bias` is not altered significantly, but the unauthorized state change persists.

### Steps Taken by an Attacker

1. **Add Unauthorized Nominee**:
   - Using the public `addNomineeEVM` function, an attacker adds a nominee with arbitrary `account` and `chainId`.

2. **Prepare to Vote**:
   - The attacker initializes parameters for `voteForNomineeWeights` with the unauthorized nominee.

3. **Predict Power Used**:
   - The attacker predicts that `powerUsed` will equal the `weight` argument due to default zero values for unknown `msg.sender`.

4. **Bypass Checks**:
   - Bypass weight and last voting time checks due to known zero values for unknown `msg.sender`.

5. **Update State**:
   - Make unauthorized state changes that persist in the contract, affecting nominee weights and the overall voting process.

### Impact
- **Unauthorized Voting**: Allows an attacker to vote with predictable power, bypassing intended restrictions.
- **Persistent State Changes**: Unauthorized state changes persist, compromising the integrity of the contract.
- **Manipulated Voting Power**: An attacker can manipulate voting power to affect the outcome of votes and the distribution of weights.

### Recommended Mitigations

1. **Implement Access Control**:
   - Restrict access to critical functions like `addNomineeEVM` using `onlyOwner` or role-based access controls.

2. **Enhance Validation**:
   - Validate that `msg.sender` exists in the relevant mappings before proceeding with calculations and state changes.

3. **Re-evaluate Voting Mechanisms**:
   - Strengthen security checks within the `voteForNomineeWeights` function to prevent bypassing and unauthorized state changes.

### Conclusion
This report highlights how an attacker can exploit default zero values for unknown `msg.sender` to bypass checks and manipulate voting power in the `voteForNomineeWeights` function. By implementing the recommended mitigations, the contract's security and integrity can be significantly enhanced, preventing unauthorized access and manipulation of the voting process.

### Denial of Service (DoS) Potential
While the main issue is access control, the vulnerability also has a potential DoS component:

**Spam and Overload**: By allowing unauthorized additions and votes, an attacker can flood the system with bogus nominations or votes, potentially leading to a denial of service by overwhelming the system or causing it to reach its resource limits.
