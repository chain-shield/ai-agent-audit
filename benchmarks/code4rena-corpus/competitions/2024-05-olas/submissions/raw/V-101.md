# Vulnerability details

## Impact
In the `unstake` function, the loop searches for the service index in the `serviceIds` array as follows. [@StakingBase.unstake:835-843](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/registries/contracts/staking/StakingBase.sol#L835-L843)
```solidity
for (; idx < serviceIds.length; ++idx) {
    // Service is still in a global staking set if it is found in the services set,
    // and is not present in the evicted set
    if (evictServiceIds[idx] == serviceId) {
        break;
    } else if (serviceIds[idx] == serviceId) {
        inSet = true;
        break;
    }
}
```
The problem is that if the `serviceId` is found in the `evictServiceIds` array, the loop breaks without setting the `inSet` flag to true. This means that even if the service is still in the `serviceIds` array, it will be considered as not being part of the staked services set.

## Proof of Concept
The purpose of the loop is to determine whether the service being unstaked is still part of the staked services set. It does this by searching for the `serviceId` in both the `serviceIds` and `evictServiceIds` arrays.

If the `serviceId` is found in the `evictServiceIds` array, it means that the service has been evicted and should no longer be considered as part of the staked services set. In this case, the loop breaks without setting the `inSet` flag to `true`.

However, if the `serviceId` is also present in the `serviceIds` array, it means that the service is still part of the staked services set, even if it has been evicted. This is because the `serviceIds` array represents the global set of staked services, while the `evictServiceIds` array represents the services that have been evicted in the current epoch.

The bug occurs when the `serviceId` is found in both arrays. In this case, the loop breaks when it finds the `serviceId` in the `evictServiceIds` array, without setting the `inSet` flag to true. As a result, the subsequent logic considers the service as not being part of the staked services set, even though it is still present in the `serviceIds` array.

This can lead to incorrect behavior in the following code block: [@StakingBase.unstake:855-860](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/registries/contracts/staking/StakingBase.sol#L855-L860)
```solidity
// Update the set of staked service Ids
// If the index was not found, the service was evicted and is not part of staked services set
if (inSet) {
    setServiceIds[idx] = setServiceIds[setServiceIds.length - 1];
    setServiceIds.pop();
}
```
If `inSet` is not set to `true` when it should be, the code will not remove the service from the `setServiceIds` array, even though it should be removed since it is being unstaked.

This can result in the `setServiceIds` array containing services that have been unstaked, leading to inconsistencies in the staking state and potentially affecting other functions that rely on the accuracy of the `setServiceIds` array.

For illustration of the concept, consider the following scenario.

  - The `serviceIds` array contains the following service IDs: [1, 2, 3, 4, 5]
  - The `evictServiceIds` array contains the following service IDs: [2, 4]
  - The service with ID 4 is being unstaked

In this case, the loop will find the service ID 4 in the `evictServiceIds` array and break without setting `inSet` to `true`. As a result, the service will not be removed from the `setServiceIds` array, even though it should be since it is being unstaked.

## Recommended Mitigation Steps
Update the loop to set `inSet` to `true` when the `serviceId` is found in the `serviceIds` array, regardless of whether it is also found in the `evictServiceIds` array. With this change, the `inSet` flag will be set correctly, and the subsequent logic to update the set of staked service IDs will work as intended.
```solidity
for (; idx < serviceIds.length; ++idx) {
    if (serviceIds[idx] == serviceId) {
        inSet = true;
    }
    if (evictServiceIds[idx] == serviceId) {
        break;
    }
}
```
