# Vulnerability details

## Impact
`_sendMessage` checks if the provided `msg.value` is enough to cover the cost of gas for delivery. If `msg.value` is lower than the cost, it reverts with the `LowerThan` error. However, the issue is that the function does not handle the case where `msg.value` is greater than the cost. If a user sends more ETH than required, the excess ETH will be stuck in the contract and cannot be recovered. [@>tokenomics/contracts/staking/WormholeTargetDispenserL2.sol#L114-L117](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/staking/WormholeTargetDispenserL2.sol#L114-L117)
```solidity
// Check that provided msg.value is enough to cover the cost
if (cost > msg.value) {
    revert LowerThan(msg.value, cost);
}
```
The issue can lead to a scenario where users accidentally send more ETH than required to cover the gas cost for message delivery. If this happens, the excess ETH will be stuck in the contract and cannot be recovered by the user. 

_**`Explanation:`**_ The `_sendMessage` function is responsible for sending a message from the L2 contract to the L1 contract. It takes the `amount` and `bridgePayload` as parameters. The function performs various checks and calculations, including verifying the bridge payload length, extracting the `refundAccount` and `gasLimitMessage` from the payload, and checking the gas limit values.

One of the crucial steps is to obtain a quote for the cost of gas for message delivery using the `quoteEVMDeliveryPrice` function of the `IBridge` interface. The function then checks if the provided `msg.value` is enough to cover this cost.

If the `msg.value` is lower than the cost, the function reverts with the `LowerThan` error, indicating that the user has not sent enough ETH to cover the gas cost.

_However, the issue arises when the user sends more ETH than required. The function does not have any mechanism to handle this scenario and refund the excess ETH back to the user. As a result, the excess ETH remains stuck in the contract._

## Proof of Concept
1. The user wants to send a message from the L2 contract to the L1 contract.
2. The user calls the `_sendMessage` function and provides the necessary parameters, including the amount and `bridgePayload`.
3. The function calculates the cost of gas for message delivery using `quoteEVMDeliveryPrice`, and let's assume the cost is 0.01 ETH.
4. The user accidentally sends 0.02 ETH as `msg.value` when calling the function.
5. The function checks if `msg.value` is enough to cover the cost, which it is in this case.
6. The function proceeds to send the message to the L1 contract using the `sendPayloadToEvm` function of the `IBridge` interface, passing the calculated cost as the `value`.
7. After sending the message, the function completes execution without refunding the excess 0.01 ETH back to the user.
8. The excess 0.01 ETH remains stuck in the contract, and the user has no way to retrieve it.

## Recommended Mitigation Steps
You can modify the code to refund the excess ETH back to the sender. By adding the refund logic after sending the message to L1, any excess ETH sent by the user will be returned to them.
```solidity
// Check that provided msg.value is enough to cover the cost
if (cost > msg.value) {
    revert LowerThan(msg.value, cost);
}

// Send the message to L1
uint64 sequence = IBridge(l2MessageRelayer).sendPayloadToEvm{value: cost}(uint16(l1SourceChainId),
    l1DepositProcessor, abi.encode(amount), 0, gasLimitMessage, uint16(l1SourceChainId), refundAccount);

// Refund excess ETH back to the sender
if (msg.value > cost) {
    payable(msg.sender).transfer(msg.value - cost);
}
```
It's important to handle the case where `msg.value` is greater than the required cost to ensure that users don't accidentally lose funds and to maintain the expected behavior of the contract.
