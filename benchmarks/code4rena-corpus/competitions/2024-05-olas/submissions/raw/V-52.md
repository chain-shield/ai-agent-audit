# Vulnerability details

## Impact
The `addNomineeNonEVM` function responsible for adding a new non-EVM nominee address along with the associated chain ID. The function includes a check to prevent underflow conditions for the `chainId` parameter. However, the condition is implemented incorrectly, leading to the opposite behavior of what was intended.

Here's the relevant code snippet: [addNomineeNonEVM#L356-L358](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L356-L358)
```solidity
if (MAX_EVM_CHAIN_ID >= chainId) {
    revert Underflow(chainId, MAX_EVM_CHAIN_ID + 1);
}
```
This check intends to revert the transaction if the provided `chainId` is less than or equal to `MAX_EVM_CHAIN_ID`, as these values are considered invalid and could lead to an underflow condition. However, the condition `MAX_EVM_CHAIN_ID >= chainId` is checking the opposite: it will only revert if the `chainId` is greater than or equal to `MAX_EVM_CHAIN_ID`.

This means that the function will accept any `chainId` value that is less than or equal to `MAX_EVM_CHAIN_ID`, even if those values are intended to be invalid.

## Proof of Concept
By allowing invalid `chainId` values to be accepted, the contract may be susceptible to underflow vulnerabilities in other parts of the code that rely on the `chainId` value being within a valid range.

The contract may violate certain invariants or assumptions made by other parts of the system, leading to unpredictable behavior and potential vulnerabilities.

To illustrate the concept further, let's consider a scenario where `MAX_EVM_CHAIN_ID` is set to `10`. According to the current implementation, any `chainId` value less than or equal to `10` will be accepted, even if the intended behavior is to only accept values greater than 10.

For instance, if a malicious user provides a `chainId` value of `0`, the condition `MAX_EVM_CHAIN_ID >= chainId` (i.e., `10 >= 0`) will evaluate to true, and the function will proceed without reverting, potentially leading to unintended consequences.

## Recommended Mitigation Steps
The correct condition should be
```solidity
if (chainId <= MAX_EVM_CHAIN_ID) {
    revert Underflow(chainId, MAX_EVM_CHAIN_ID + 1);
}
```
This way, the function will revert to the `Underflow` error if the provided `chainId` is less than or equal to `MAX_EVM_CHAIN_ID`, which is the intended behavior to prevent underflow.
