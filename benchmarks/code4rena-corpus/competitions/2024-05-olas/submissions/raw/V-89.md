# Vulnerability details

## Impact
In the DefaultDepositProcessor.sol looking at the child contract - OptimismDepositProcessorL1 default is the default one as it the abstract regardless of the bridge contract helps in sending of message to the L2 target set.

However, in the ```_sendMessage``` in the OpitmismDefaultDepositProcessor, case of revert may likely happen and any revert like this can block the L1<->L2 communication from processing to the L2 target contract.

## Proof of Concept
```
  function sendMessage(
        address target,
        uint256 stakingIncentive,
        bytes memory bridgePayload,
        uint256 transferAmount
    ) external virtual payable {
        // Check for the dispenser contract to be the msg.sender
        if (msg.sender != l1Dispenser) {
            revert ManagerOnly(l1Dispenser, msg.sender);
        }

        // Construct one-element arrays from targets and amounts
        address[] memory targets = new address[](1);
        targets[0] = target;
        uint256[] memory stakingIncentives = new uint256[](1);
        stakingIncentives[0] = stakingIncentive;

        // Send the message to L2
        uint256 sequence = _sendMessage(targets, stakingIncentives, bridgePayload, transferAmount);
```

From the [defaulProcessor.sol](https://github.com/code-423n4/2024-05-olas/blob/3ce502ec8b475885b90668e617f3983cea3ae29f/tokenomics/contracts/staking/DefaultDepositProcessorL1.sol#L150) we can see that _sendMessage() can be found in [OpDefaultDepositProcessor.sol](https://github.com/code-423n4/2024-05-olas/blob/3ce502ec8b475885b90668e617f3983cea3ae29f/tokenomics/contracts/staking/OptimismDepositProcessorL1.sol#L95C3-L116C10) which has a vulnerability of [Approve(0)](https://github.com/code-423n4/2024-05-olas/blob/3ce502ec8b475885b90668e617f3983cea3ae29f/tokenomics/contracts/staking/OptimismDepositProcessorL1.sol#L111) not been set before been called, this approve function was sued so many parts of the codebase but here as it was used to approve the l1TokenRelayer to spend some ```transferAmount```, Transaction will revert when using unsupported token Like USDT [see](https://etherscan.io/address/0xdac17f958d2ee523a2206206994597c13d831ec7#code)

However, there also might be cases where no sufficient funds in the OLAS causing a revert when the balanceOf(Olas) is less than the transferedAmount leading to insufficient allowance to cover up for transferAmount. As the case maybe OLas might have done approval for l1TokenRelayer to spend some of it token over time.

Lastly, there is no error handling in this codebase in a situation where a fault happens as the transaction happens.

The Optimism bridge deosn't support all kinds of tokens such as rebasing, fee-on token transfer: 

https://docs.optimism.io/chain/tokenlist

It is essential that a bridge provides instant guaranteed finality, as the absence of any guarantees of finality necessitates a transaction reversion mechanism that will negatively affect the user experience or profitability of the service.
