# Vulnerability details

## Impact
Adding the retainer as a nominee in the early days of the protocol launch while it is voted for after a long time could lead to a situation that returning these allocated staking incentives to the `Tokenomics` inflation would be highly gas consuming, and leading to waste of gas for users.

## Proof of Concept
 - A malicious user, in the early days of the protocol launch, adds the `retainer` as a nominee by calling the function `addNomineeEVM(retainer, 1)` where `retainer` is the address of retainer set during contruction of `Dispenser` and `1` is the Ethereum chain id.
 ```solidity
     function addNomineeEVM(address account, uint256 chainId) external {
        // Check for the zero address

            revert ZeroValue();

            revert Overflow(chainId, MAX_EVM_CHAIN_ID);

        Nominee memory nominee = Nominee(bytes32(uint256(uint160(account))), chainId);

        _addNominee(nominee);
 ```

 - After a long time, suppose there are nonzero staking weight on the retainer, in other words during this time someone had voted for the retainer. 
 - In order to return the staking incentives related to the retainer to the `Tokenomics`, the function `retain` should be called. In this function, it goes through a for-loop to iterate over the epochs from the first claimed epoch to the last claimed epoch related to the retainer, and sum all the staking incentives allocated to the retainer. Finally, it returns the sum to the contract `tokenomics`.  
 ```solidity
     function retain() external {
        //....

        // Go over epochs and retain funds to return back to the tokenomics
        for (uint256 j = firstClaimedEpoch; j < lastClaimedEpoch; ++j) {
            // Get service staking info
            ITokenomics.StakingPoint memory stakingPoint = ITokenomics(tokenomics).mapEpochStakingPoints(j);

            // Get epoch end time
            uint256 endTime = ITokenomics(tokenomics).getEpochEndTime(j);

            // Get the staking weight for each epoch
            (uint256 stakingWeight, ) = IVoteWeighting(voteWeighting).nomineeRelativeWeight(retainer,
                block.chainid, endTime);

            totalReturnAmount += stakingPoint.stakingIncentive * stakingWeight;
        }
        totalReturnAmount /= 1e18;

        if (totalReturnAmount > 0) {
            ITokenomics(tokenomics).refundFromStaking(totalReturnAmount);
        }

        emit Retained(msg.sender, totalReturnAmount);

        _locked = 1;
    }
 ```
 https://github.com/code-423n4/2024-05-olas/blob/main/tokenomics/contracts/Dispenser.sol#L1146

  - The issue is that the retainer was added as a nominee in epoch 1, but it is voted in epoch X. So, from epoch 1 to epoch X, no incentives are allocated to the retainer. Thus, it is useless to iterate over this range of epochs to calculate the total incentives allocated to the retainer. But, when the function `retain` is called, it iterates from epoch 1 to `1 + maxNumClaimingEpochs`, among that, from epoch 1 to epoch X is just waste of gas to the user who called this function. So, the malicious user could force the users to consume more gas when they call the function `retain`.

### Tests

**Test1 (normal case):**

In the following test it is assumed that `epochLen = 10 days`, and `maxNumClaimingEpochs = 100`. The retainer is added and voted for at epoch 102, then the function `retain` is called at epoch 103. The gas consumption of calling this function would be just `168_754`, because it iterates only over one epoch (from 102 to 103).
```javascript

            const snapshot = await helpers.takeSnapshot();

            // Set staking fraction to 100%
            await tokenomics.changeIncentiveFractions(0, 0, 0, 0, 0, 100);
            // Changing staking parameters
            await tokenomics.changeStakingParams(50, 10);

            // Checkpoint to apply changes
            await helpers.time.increase(epochLen);
            await tokenomics.checkpoint();


            // Unpause the dispenser
            await dispenser.setPauseState(0);

            // Checkpoint to get to the next epochs
            for (let i = 0; i < 100; i++) {
                await helpers.time.increase(epochLen);
                await tokenomics.checkpoint();

            await vw.setNomineeRelativeWeight(convertBytes32ToAddress(retainer), chainId, 1);
```

## Recommended Mitigation Steps

The following modification is recommended:

 - First: When the retainer is added as a nominee, it should force the caller to vote for it as well. By doing so, a malicious user can not just add retainer as nominee, and he must vote for it as well. 

 - Second: Whenever an user votes for the retainer, it should call the function `retain` as well to update its last claimed epoch to the current epoch. By doing so, there will not be a large number of epochs to be iterated over later.

 - Third: Allow the user to input the number of epoch to iterate.
 ```solidity
     function retain(uint256 _num) external {
        //....
        if(_num > maxNumClaimingEpochs){
            _num = maxNumClaimingEpochs;
        }
        (uint256 firstClaimedEpoch, uint256 lastClaimedEpoch) =
            _checkpointNomineeAndGetClaimedEpochCounters(retainerHash, _num_);
    }
 ```
