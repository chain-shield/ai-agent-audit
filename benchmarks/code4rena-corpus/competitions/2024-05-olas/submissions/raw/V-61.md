# Vulnerability details

## Impact
In the `_claim` function, the code does not update the `sInfo.nonces` value after claiming the reward. The `nonces` field is likely used to track the number of times rewards have been claimed for a service. By not incrementing it after a successful claim, it may lead to inconsistencies or incorrect tracking of the claiming process.

Referenced Code: [#StakingBase.sol:507-511](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/registries/contracts/staking/StakingBase.sol#L507-L511)
```solidity
// Transfer accumulated rewards to the service multisig
// Note that the reentrancy is not possible since the reward is set to zero
address multisig = sInfo.multisig;
_withdraw(multisig, reward);

emit RewardClaimed(epochCounter, serviceId, msg.sender, multisig, sInfo.nonces, reward);
```
We can see, the `sInfo.nonces` value is not incremented after the `_withdraw` function call, which transfers the rewards to the service's multisig address. This missing increment is the root cause of the inconsistencies and potential issues described above.

The `RewardClaimed` event emitted at the end of the `_claim` function includes the `sInfo.nonces` value. Suppose this value is not incremented after a successful claim. In that case, the emitted event will contain an incorrect nonces value, providing misleading information to event listeners or off-chain systems that rely on these events for tracking and monitoring purposes.

## Proof of Concept
Imagine a scenario where a service owner claims rewards multiple times without the `nonces` value being incremented.

1. Initial state:

  - Service ID: 1
  - Service owner: 0xABC...
  - Rewards: 100 tokens
  - Nonces: 0

2. First reward claim:

  - Service owner calls `_claim(1, true)`
  - Rewards (100 tokens) are transferred to the service's multisig address
  - Nonces remains at 0
  - Event emitted: `RewardClaimed(epochCounter, 1, 0xABC..., multisig, 0, 100)`

3. Second reward claim:

  - Service owner calls `_claim(1, true)` again
  - Rewards (0 tokens) are transferred to the service's multisig address (assuming no new rewards have been added)
  - Nonces still remains at 0
  - Event emitted: `RewardClaimed(epochCounter, 1, 0xABC..., multisig, 0, 0)`

In this scenario, the service owner was able to claim rewards multiple times without the value of the `nonce` being incremented, leading to inconsistent tracking and incorrect emission of events.

## Recommended Mitigation Steps
We should increment the `sInfo.nonces` value after the reward has been successfully transferred.
```solidity
// Transfer accumulated rewards to the service multisig
// Note that the reentrancy is not possible since the reward is set to zero
address multisig = sInfo.multisig;
_withdraw(multisig, reward);

// Increment the nonces value
sInfo.nonces++;

emit RewardClaimed(epochCounter, serviceId, msg.sender, multisig, sInfo.nonces, reward);
```
By incrementing `sInfo.nonces` after the `_withdraw function` call, we ensure that the nonces value is properly updated to reflect the successful reward claim.
