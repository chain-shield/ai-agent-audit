# Vulnerability details

## Impact

Unsafe usage of `syncWithheldAmountMaintenance` can lead to double accounting.

## Proof of Concept

In both L1 and L2 contracts, there is a Maintenance function in case the bridge fails.

DefaultTargetDispenserL2.sol lays out the possible bridge failure scenarios,

```
/// @dev Processes the data manually provided by the DAO in order to restore the data that was not delivered from L1.
    /// @notice Here are possible bridge failure scenarios and the way to act via the DAO vote:
>   ///         - Both token and message delivery fails: re-send OLAS to the contract (separate vote), call this function;
>   ///         - Token transfer succeeds, message fails: call this function;
>   ///         - Token transfer fails, message succeeds: re-send OLAS to the contract (separate vote).
    /// @param data Bytes message data that was not delivered from L1.
    function processDataMaintenance(bytes memory data) external {
        // Check for the contract ownership
        if (msg.sender != owner) {
            revert OwnerOnly(msg.sender, owner);
        }

        // Process the data
        _processData(data);
    }
```

L1 Dispenser contract also has a maintenance function in case of a bridge failure:

```
  /// @dev Syncs the withheld amount manually by the DAO in order to restore the data that was not delivered from L2.
    /// @notice The possible bridge failure scenario that requires to act via the DAO vote includes:
>   ///         - Message from L2 to L1 fails: need to call this function.
    /// @param chainId L2 chain Id.
    /// @param amount Withheld amount that was not delivered from L2.
    function syncWithheldAmountMaintenance(uint256 chainId, uint256 amount) external {
        // Check the contract ownership
        if (msg.sender != owner) {
            revert OwnerOnly(msg.sender, owner);
        }

        // Check zero value chain Id and amount
        if (chainId == 0 || amount == 0) {
            revert ZeroValue();
        }

        // The sync must never happen for the L1 chain Id itself, as dispenser exists strictly on L1-s
        if (chainId == block.chainid) {
            revert WrongChainId(chainId);
        }

        // Get bridging decimals for a specified chain Id
        address depositProcessor = mapChainIdDepositProcessors[chainId];
        uint256 bridgingDecimals = IDepositProcessor(depositProcessor).getBridgingDecimals();

        // Normalize the synced withheld amount via maintenance is correct
        if (bridgingDecimals < 18) {
            uint256 normalizedAmount = amount / (10 ** (18 - bridgingDecimals));
            normalizedAmount *= 10 ** (18 - bridgingDecimals);
            // Downsize staking incentive to a specified number of bridging decimals
            amount = normalizedAmount;
        }

        // The overall amount is bound by the OLAS projected maximum amount for years to come
        uint256 withheldAmount = mapChainIdWithheldAmounts[chainId] + amount;
        if (withheldAmount > type(uint96).max) {
            revert Overflow(withheldAmount, type(uint96).max);
        }

        // Add to the withheld amount
        mapChainIdWithheldAmounts[chainId] = withheldAmount;

        emit WithheldAmountSynced(chainId, amount, withheldAmount);
    }
```

There are two parts to bridging. Giving an example for Wormhole, the first part is the source chain relaying the message to the relayer and having all the checks (VAA, Guardian). The second part is on the destination chain, having the relayer call the receiveWormholeMessage() function.

The bridge can fail on other side, source or destination. If it fails on the source, the caller can just redo the bridge transaction. If the transaction fails on the destination (L2), the caller has the option to re-call the transaction through the wormhole relayer.

If the message repeatedly fails on the destination chain, the maintenance function comes in handy, as it bypass the relayer calls and change the state in L2. 

The edge case is that the message on the destination chain can still pass after the first failure. However, the state changes in the source change is permanent. For example, if there is a call from L2 -> L1, (syncWithheldTokens()), the `withheldAmount` is set to zero.

```
    function syncWithheldTokens(bytes memory bridgePayload) external payable {
 // Check the withheld amount to be greater than zero
        uint256 amount = withheldAmount;
        if (amount == 0) {
            revert ZeroValue();
        }
```

The message is sent to L1 but fails, so maintenance function is called and updates `mapChainIdWithheldAmounts[chainId]`.

```

   // The overall amount is bound by the OLAS projected maximum amount for years to come

```

This failed message is still inside the relayer contract, and can still be replayed. If it is replayed again, it will lead to double accounting. 

## Tools Used

Manual Review

## Recommended Mitigation Steps

If the maintenance function is ever used, make sure that there is an option in the source chain to revert the state changes, in case the failed message passes after the maintenance is called.
