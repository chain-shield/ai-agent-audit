# Vulnerability details

## Impact

In the current implementation of `Tokenomics` smart contract there is a `stakingIncentive` parameter meaning there is some predetermined amount of staking incentives for each epoch that are based on the OLAS inflation schedule and cannot exceed set bounds. However, due to incorrect assumption, the parameter can potentially overflow as the user can use the `returnAmount` from previous epochs.

## Proof of Concept

There's the following assumption:

```
// This scenario is not realistically possible, as the refund comes back from the allocated inflation.
        if (stakingIncentive > type(uint96).max) {
            revert Overflow(stakingIncentive, type(uint96).max);
        }

```

This assumption is based on the fact that `stakingIncentive` param is a certain number for each epoch that's calculated based on the annual OLAS inflation:

https://github.com/code-423n4/2024-05-olas/blob/main/tokenomics/contracts/Tokenomics.sol#L234-236
```
// Amount of OLAS that funds service staking incentives for the epoch based on the inflation schedule
    // After 10 years, the OLAS inflation rate is 2% per year. It would take 220+ years to reach 2^96 - 1
    uint96 stakingIncentive;
```

However, the function `claimStakingIncentives()` inside of `Dispenser` smart contract allows to loop over several epoch and returns `totalReturnAmount` back which is considered as sum of all return amounts over several epochs:

https://github.com/code-423n4/2024-05-olas/blob/main/tokenomics/contracts/Dispenser.sol#L993-994
```
 (uint256 stakingIncentive, uint256 returnAmount, uint256 lastClaimedEpoch, bytes32 nomineeHash) =
            calculateStakingIncentives(numClaimedEpochs, chainId, stakingTarget, bridgingDecimals);
```

https://github.com/code-423n4/2024-05-olas/blob/main/tokenomics/contracts/Dispenser.sol#L854-859
```
returns (
        uint256 totalStakingIncentive,
        uint256 totalReturnAmount,
        uint256 lastClaimedEpoch,
        bytes32 nomineeHash
    )

```

And the final:

https://github.com/code-423n4/2024-05-olas/blob/main/tokenomics/contracts/Dispenser.sol#L944
```
   totalReturnAmount += returnAmount;
```

This can create a situation where some number of users don't make a claim for a huge number of epochs and then decide to synchronously claim in one epoch leading to subsequent potential reverts of `refundFromStaking()` because of overflow for the next users.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Limit the number of epochs that can remain unclaimed or create some new mechanism.
