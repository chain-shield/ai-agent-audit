# Vulnerability details

## Impact
1. Wrong eviction of services.
2. Undistributed reward for some services that should get reward.

> /// @dev Checks if the service multisig liveness ratio passes the defined liveness threshold.
According to the description above, the ```isRatioPass``` is based on liveness period.

However, based on the check in the  ```_calculateStakingRewards()``` function, when there are no available awards for distribution, it returns an empty array for ```serviceIds```, and ```tsCheckPointLast``` is only updated when ```serviceIds``` is > 1.
```solidity
 if (
            block.timestamp - tsCheckpointLast >= livenessPeriod &&
            lastAvailableRewards > 0
        ) {

When next ```checkPoint``` is called, if the service nonce is yet to increase further, nonce difference is divided by an increased time difference leading to a reduced threshold, which might lead to service eviction or not rewarding service that initially met the threshold in the previous liveness period. 

## Proof of Concept
In ```checkPoint```, ```tsCheckPointLast``` is only updated when ```serviceIds``` > 1.
```solidity
 // If service Ids are returned, then the checkpoint takes place
        if (serviceIds.length > 0) {
...
// Record the current timestamp such that next calculations start from this point of time
            tsCheckpoint = block.timestamp;
```

### Instance
If liveness period is 2000sec, pass ratio is 90%
1. After a liveness period where available reward is zero, Service A has nonce difference of 1,800, which makes the ration 90%, calling checkpoint fails to update ```tsCheckpount```.
2. If deposit is made in the next block and checkpoint is called, service A will not get reward if nonce has not increased, and incase where service A has been warned, it get evicted.
```solidity
 // Calculate the liveness nonce ratio
