# Vulnerability details

## Impact
The current implementation for verifying that the [multisig address](https://github.com/code-423n4/2024-05-olas/blob/3ce502ec8b475885b90668e617f3983cea3ae29f/registries/contracts/staking/StakingBase.sol#L760) corresponds to the authorized multisig proxy bytecode hash is incorrect. The method used to retrieve the bytecode hash is invalid, which can lead to bypassing security checks and potentially allowing unauthorized multisig contracts.

## Proof of Concept
```
// Check that the multisig address corresponds to the authorized multisig proxy bytecode hash
bytes32 multisigProxyHash = keccak256(service.multisig.code);
if (proxyHash != multisigProxyHash) {
    revert UnauthorizedMultisig(service.multisig);
}

```
[```service.multisig.code```](https://github.com/code-423n4/2024-05-olas/blob/3ce502ec8b475885b90668e617f3983cea3ae29f/registries/contracts/staking/StakingBase.sol#L760) is not a valid way to access the bytecode of a contract in Solidity.

Since the bytecode hash is not correctly retrieved, the security check comparing proxyHash and multisigProxyHash will not function as intended, potentially allowing unauthorized multisig addresses to pass the verification.


An attacker can exploit this vulnerability by providing an unauthorized multisig address, which would pass the flawed security check. This can lead to unauthorized access and operations within the system, potentially causing loss of funds or control over critical contract functions.

## Tools Used
Manual review, Solodit

## Recommended Mitigation Steps
Update the code to correctly retrieve and compare the bytecode hash using the extcodehash opcode.

```
   // Get the bytecode hash of the multisig address
        bytes32 multisigProxyHash;
        assembly {
            multisigProxyHash := extcodehash(multisig)
        }

        // Compare with the expected proxy hash
        if (proxyHash != multisigProxyHash) {
            revert("UnauthorizedMultisig");
        }
```
