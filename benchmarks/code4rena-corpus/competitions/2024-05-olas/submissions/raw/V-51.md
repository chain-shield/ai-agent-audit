# Vulnerability details

## Impact
The `Nominee` struct is defined as follows: [VoteWeighting#L121-L124](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L121-L124)
```solidity
struct Nominee {
    bytes32 data;
    uint256 chainId;
}
```
The intention is to pack both the nominee's address (a 20-byte value) and the chain ID into a single `bytes32` value, which is stored in the `data` field of the `Nominee` struct. However, the way this packing is done in the `VoteWeighting:addNomineeEVM` function is incorrect: [#L340](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L340)
```solidity
Nominee memory nominee = Nominee(bytes32(uint256(uint160(account))), chainId);
```
Here's what's happening:

`uint160(account)` truncates the `account` address (which is a 20-byte value) to its least significant 20 bytes, effectively discarding the most significant 12 bytes. This means that if the `account` address starts with any non-zero bytes, those bytes will be lost.

`uint256(uint160(account))` then pads the truncated 20-byte value with leading zeros to create a 32-byte value.

`bytes32(uint256(uint160(account)))` converts this 32-byte value to a `bytes32` type, which is fine.

However, the `chainId` value is not being properly packed into the `bytes32` value. Instead, it is simply being assigned as the second member of the `Nominee` struct, which is not the intended behavior.

This means that when you try to retrieve the nominee's address and chain ID from the `Nominee` struct, you will not get the correct values. The address will be truncated, and the chain ID will be stored separately, rather than being packed into the `bytes32` value.

**`Suppose we have the following values:`**
```solidity
account = 0x1234567890abcdef1234567890abcdef12345678
chainId = 1
```
After executing the line `Nominee memory nominee = Nominee(bytes32(uint256(uint160(account))), chainId);`, the `Nominee` struct will have the following values:
```solidity
nominee.data = 0x0000000000000000000000009abcdef1234567890abcdef12345678
nominee.chainId = 1
```
As we can see, the most significant 12 bytes of the `account` address (`0x1234567890abcdef`) have been lost, and the `chainId` is stored separately in the `chainId` field of the Nominee struct.

This can lead to data loss and incorrect behavior when trying to retrieve and use the `nominee` information. For example, if you try to look up a nominee by their address and chain ID, you may not find the correct nominee because the address has been truncated, and the chain ID is not properly packed into the `bytes32` value.

## Recommended Mitigation Steps
We should consider using a different approach to pack the account address and `chainId` into a single `bytes32` value by using bit shifting and bitwise operations to combine the two values into a single `bytes32` value.

How you could do it:
```solidity
bytes32 packedValue = bytes32(uint256(uint160(account)) | (chainId << 160));
Nominee memory nominee = Nominee(packedValue);
```
In this approach, the `account` address is first converted to a `uint160` value, and then cast to a `uint256`. The `chainId` is then shifted left by 160 bits (20 bytes) and combined with the account value using the bitwise OR operator. This effectively packs the account address into the least significant 20 bytes of the `bytes32` value, and the `chainId` into the most significant 12 bytes.
