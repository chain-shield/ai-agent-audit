# Vulnerability details

## Impact

From StakingToken.sol and StakingNativeToken.sol, anyone can deposit the staking token or ETH into whose value will be added to the currently available rewards. This can be weaponized by malicious users to trigger a fund lockup for unsuspecting users for a period of `minStakingDuration` before which tokens can be retrieved. This is due to the fact that a user cannot stake if there are no available rewards i.e (`availableRewards` == 0), and can only unstake before `minStakingDuration` if there are no available rewards i.e (`availableRewards` == 0). A malcious user therefore has a degree of control over user's funds and for as low as 1 wei can temporarily lock them up.

## Proof of Concept

First, in StakingNativeToken.sol, it can be seen that there is a `recieve` function to which anyone can send ETH as low as 1 wei, and this ETH is added as part of the available rewards.

```solidity
    receive() external payable {
        // Add to the contract and available rewards balances
        uint256 newBalance = balance + msg.value;
        uint256 newAvailableRewards = availableRewards + msg.value;

        // Record the new actual balance and available rewards
        balance = newBalance;
        availableRewards = newAvailableRewards;

        emit Deposit(msg.sender, msg.value, newBalance, newAvailableRewards);
    }
```
The same can be observed in `deposit` function in StakingToken.sol as anyone can deposit as low as 1 wei of the stakingToken into the contract and the available rewards is now increased. 

```solidity
    function deposit(uint256 amount) external {
        // Add to the contract and available rewards balances
        uint256 newBalance = balance + amount;
        uint256 newAvailableRewards = availableRewards + amount;

        // Record the new actual balance and available rewards
        balance = newBalance;
        availableRewards = newAvailableRewards;

        // Add to the overall balance
        SafeTransferLib.safeTransferFrom(stakingToken, msg.sender, address(this), amount);

        emit Deposit(msg.sender, amount, newBalance, newAvailableRewards);
    }
```
Now, to prevent staking when there're no available rewards, the function reverts if `availableRewards` = 0. This is infact very likely to happen after the staking program is over and there are no more available rewards to distribute. Hence, to prevent users from unnecessarily locking up their funds, staking is disabled when there are no rewards.
```solidity
    function stake(uint256 serviceId) external {
        // Check if there available rewards
        if (availableRewards == 0) {
            revert NoRewardsAvailable();
        }
......
    }

```
THe same can be observed in the `unstake` function which allows unstaking if there are no available rewards left without having to wait for long unstaking durations.
```solidity
    function unstake(uint256 serviceId) external returns (uint256 reward) {
    ......
        // Check that the service has staked long enough, or if there are no rewards left
        uint256 ts = block.timestamp - tsStart;
        if (ts <= minStakingDuration && availableRewards > 0) {
            revert NotEnoughTimeStaked(serviceId, ts, minStakingDuration);
        }

    ......
    }
```

Seeing as this is the case, any once can temporarily cause a lockup fund for stakers for as little as 1 wei, giving off virtually no rewards to gain, while preventing stakers from being able to access their funds.

Imagine a scenario in which the protocol has decided to stop running their staking programs, after distribtuing the last set of rewards.

An unsuspecting user calls the `stake` function. Under ideal circumstances, the function will revert since there are no rewards. But a malicious user can frontrun the call to the stake function to deposit 1 wei of the stakingToken. The victim's call goes through since `availableRewards` is now greater than 0, while also not being able to unstake at least until `minStakingDuration` has passed. Also important to note is that during this time period, he will not earn a lot of rewards.

On the other end of the spectrum, unstaking for any and all users who haven't staked beyond the `minStakingDuration` will also be delayed, at the cost of 1 wei, with no significant rewards being accrued during this delay.

## Tools Used
Manual code review

## Recommended Mitigation Steps

Two ways to fix this. The best way is to introduce access control into the `receive` and the `deposit` functions.
Another way is to set a minimum deposit amount in both functions. The amount should be large enough to dissuade any potential griefers and if they go ahead with the deposit, enough for stakers to accrue meaningful reward amount from while waiting to unstake.
