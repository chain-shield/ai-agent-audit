# Vulnerability details

## Impact
According to the Ethereum contract address generation scheme, the correct order of parameters should be:
```solidity
keccak256(0xff ++ address(this) ++ salt ++ keccak256(init_code))[12:]
```
However, in the getProxyAddressWithNonce code, the order of parameters is incorrect: [@StakingFactory.sol:150-154](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/registries/contracts/staking/StakingFactory.sol#L150-L154)
```solidity
bytes32 hash = keccak256(
    abi.encodePacked(
        bytes1(0xff), address(this), salt, keccak256(deploymentData)
    )
);
```
The `salt` and `keccak256(deploymentData)` are in the wrong order. The correct order should be:
```solidity
bytes32 hash = keccak256(
    abi.encodePacked(
        bytes1(0xff), address(this), keccak256(deploymentData), salt
    )
);
```
This bug will result in incorrect proxy addresses being calculated, which can lead to unexpected behavior and potential vulnerabilities.

## Proof of Concept
Refer to the Ethereum contract address generation scheme, which is documented in the Ethereum Yellow Paper https://ethereum.github.io/yellowpaper/paper.pdf in section 7.2 "Contract Creation" and Appendix F "Signing Transactions".

The Ethereum Yellow Paper clearly specifies the order of parameters for contract address generation:
```solidity
keccak256(0xff ++ address(this) ++ salt ++ keccak256(init_code))[12:]
```
This further validates that the order of parameters in the provided code is incorrect.

The bug in the `getProxyAddressWithNonce` can lead to incorrect proxy address calculations, unintended contract interactions, increased collision risks, and difficulties in contract verification.
