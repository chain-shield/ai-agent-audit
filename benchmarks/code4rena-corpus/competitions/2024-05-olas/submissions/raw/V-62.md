# Vulnerability details

## Impact
In `_calculateStakingRewards` function, the calculation of `eligibleServiceRewards` and the population of `eligibleServiceIds`. In the code, when a service passes the liveness check (`ratioPass` is true), the reward is calculated and stored in `eligibleServiceRewards[numServices]`, and the corresponding service ID is stored in `eligibleServiceIds[numServices]`. However, `numServices` is incremented after these assignments.

This means that the first eligible service reward will be stored at index `0`, but the subsequent eligible service rewards will be stored at indices 1, 2, and so on, leaving gaps in the `eligibleServiceRewards` array. The same issue applies to the `eligibleServiceIds` array.

## Proof of Concept
When the rewards are distributed based on the `eligibleServiceRewards` and `eligibleServiceIds` arrays, some services may receive incorrect reward amounts or no rewards at all.

The bug occurs within the `if (ratioPass)` block. The `eligibleServiceRewards` and `eligibleServiceIds` arrays are populated using the `numServices` variable as the index. However, `numServices` is incremented after the assignments, leading to gaps in the arrays.

**`See this scenario:`**
```solidity
// Assume there are three services with IDs: 1, 2, and 3
// Service 1 and 3 pass the liveness check, while service 2 fails

// Inside the loop in _calculateStakingRewards function
if (ratioPass) {
    eligibleServiceRewards[numServices] = rewardsPerSecond * ts;
    totalRewards += eligibleServiceRewards[numServices];
    eligibleServiceIds[numServices] = serviceIds[i];
    ++numServices;
} else {
    serviceInactivity[i] = ts;
}

// After the loop, the arrays will look like this:
eligibleServiceRewards = [reward1, 0, reward3, 0, 0]
eligibleServiceIds = [1, 0, 3, 0, 0]
```
In this scenario, service 1 and 3 rewards are stored at indices 0 and 2, respectively, leaving gaps at indices 1, 3, and 4. This inconsistency can lead to incorrect reward distribution and make it difficult to understand the mapping between service IDs and rewards.

## Recommended Mitigation Steps
We should increment `numServices` before assigning the values to `eligibleServiceRewards` and `eligibleServiceIds`
```solidity
// Record the reward for the service if it has provided enough transactions
if (ratioPass) {
    // Increment numServices before assigning values
    ++numServices;
    // Calculate the reward up until now and record its value for the corresponding service
    eligibleServiceRewards[numServices - 1] = rewardsPerSecond * ts;
    totalRewards += eligibleServiceRewards[numServices - 1];
    eligibleServiceIds[numServices - 1] = serviceIds[i];
} else {
    serviceInactivity[i] = ts;
}
```
By incrementing `numServices` before the assignments, the eligible service rewards and IDs will be stored consecutively in their respective arrays, avoiding any gaps.
