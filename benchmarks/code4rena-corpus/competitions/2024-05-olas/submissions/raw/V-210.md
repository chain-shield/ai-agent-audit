# Vulnerability details

The `_checkRatioPass` function is critical for maintaining the integrity and security of a staking mechanism by verifying the activity of a service through nonce comparison over time. This function checks the liveness of a multisig address by comparing the current nonces with the last recorded nonces over a given time span (`ts`). 

The current implementation uses the condition `returnData.length > 63`, which is incorrect and potentially harmful. This check is supposed to ensure that the returned data contains at least two nonces, which is necessary for a meaningful comparison. However, the condition `returnData.length > 63` is not sufficient to guarantee this.

## POC

1. **ABI Encoding Standards**:
   - According to the ABI encoding rules, the dynamic array encoding consists of a 32-byte length prefix followed by the array elements.
   - For an array with two nonces, the encoded data length should be:
     \[
     \text{Length field (32 bytes)} + \text{Nonce 1 (32 bytes)} + \text{Nonce 2 (32 bytes)} = 96 \text{ bytes}
     \]

2. **Impact of the Incorrect Check**:
   - If the length check is set to `returnData.length > 63`, it only ensures the presence of one nonce (32 bytes length field + 32 bytes for one nonce).
   - This could result in situations where only one nonce is available, making it impossible to perform a valid comparison of activity levels.
   - Without at least two nonces, the function cannot accurately measure the change in nonce values over time, rendering the liveness check ineffective.
   - This can lead to incorrect determinations about the service's activity, potentially affecting the integrity of the staking mechanism.

## Impact
- **Security and Integrity Risks**:
  - By not properly verifying the presence of at least two nonces, the staking mechanism may fail to detect inactivity or insufficient activity levels of the multisig.
  - This compromises the liveness checks, which are critical for ensuring that services are actively participating and not just occupying staking slots without genuine activity.

- **Operational Issues**:
  - Services that should be flagged for inactivity may continue to be considered active, receiving rewards or maintaining their staked status without meeting the required activity criteria.
  - This miscalculation could affect the distribution of rewards and the overall fairness of the staking system.

## Recommended Mitigation Steps

The correct check should ensure that the return data contains at least 96 bytes, which accounts for the 32-byte length field and two 32-byte nonces. Therefore, the condition should be updated to:

```solidity
if (success && returnData.length >= 96 && (returnData.length % 32 == 0)) {
    // Parse nonces
    currentNonces = abi.decode(returnData, (uint256[]));

    // Get the ratio pass activity check
    activityData = abi.encodeCall(IActivityChecker.isRatioPass, (currentNonces, lastNonces, ts));
    (success, returnData) = activityChecker.staticcall(activityData);

    // The return data must match the size of bool

    }
}
```
