# Vulnerability details

## Impact
An attacker can force the protocol to distribute staking incentives to staking instances two times by engineering the staking instances and misusing the replayability of bridging protocols.

## Proof of Concept

The attack scenario is as follows:

 - The attacker creates two staking instances (instanceA and instanceB) by calling the function `createStakingInstance`. Note that both are valid and honest contracts, so the malicious intention of the attacker is not recognizable. Morevoer, the attacker creates these two instances with two different addresses, so that the `deployer` of these instances will be different from each other.

  - The issues is that when the function `deposit` on instanceB is called, it is reverted, because the attacker already paused it. By doing so, the whole function execution of `_processData` will be reverted, and the message delivery will be failed. So, none of the instances A and B will receive the incentives. This revert is recorded by the bridge protocol to be replayed later. Take the Optimism as an example of the bridge protocol, the failed message delivery is recorded in the following code, allowing to be replayed again later:

   - Now everything is fine and as expected, and DAO could solve the issue of message delivery failure. 
   - Later, some amount of incentive tokens are again delivered from L1 to L2 on `OptimismTargetDispenserL2` to be distributed to other staking instances.
   - Now, the attacker notices that `OptimismTargetDispenserL2` has nonzero balance again. So, the attacker calls the function `pause(false)` on instanceB.
   - Then the attacker calls the function `relayMessage` on Optimism with the same message which was failed before to replay that old failed message delivery. By doing so, again the function `receiveMessage` and then `_processData` on `OptimismTargetDispenserL2` will be called. The decoded data will be `targets = [instanceA, instanceB], amounts = [90e18, 10e18]`. This time, when the function `deposit` on instanceB is called, it will not revert, because the attacker unpaused it already. So, these instances will receive their portions. Note that when DAO had solved the failed message delivery issue, it distributed 90e18 to instanceA. Now, the attacker, by replaying the failed message, force the protocol to distribute 90e18 and 10e18 to instance A and B, respectively. So, instance A in total received 180e18 (90e18 + 90e18), which is not correct, and it is two times of what was expected.
   - Thus, the attacker (who created instance A and B) could force the protocol to distribute to incentive A twice, instead of once.

The root cause of this issue is that:

 - When DAO solves such failed message delivery issues, it does not invalidate the original stuck transaction. So, whenever the obstacle is removed, that stuck transaction can be replayed again leading to such issue.
 - In the function `_processData`, whenever there is an interaction with the staking instance, it is not implemented with cautious. Since a staking instance can be created through the factory with customized implementation, it can easily be implemented so that it reverts the message delivery and lead to stuck of staking incentives distribution. There are two points that during the message delivery, it interacts with the staking instance contract:
   1. During deposit: the attacker can reverts here directly.

Some Notes:
 - For simplicity, I was assuming that there are two staking instances. But, to apply the attack unrecognizable and forcing the DAO to solve the issue, the attacker claims the staking incentives of multiple instances including instances created by other users and those created by the attacker. So on L2, the staking incentives will be distributed to multiple instances. Since, the DAO can only recognize that instance B was the root cause of this issue, they will skip it from being rewarded, and distribute the staking incentives to other instances including instanceA (which was created by the attacker). After the attack, instanceA and other instances (created by other users) will receive the staking incentives twice. For example, the attacker calls `claimStakingIncentivesBatch` to distribute incentives to instances [A, B, C, D, E, ...] where instances A and B are created by the attacker, and only instance B reverts leading to stopping of distribution flow. So, DAO would have to solve the issue, because the incentives distribution to instances A, C, D, E, ... are failed. Thus, DAO, by skipping the incentive distribution to instance B, distribute the incentives to other instances.
 - **Note that this issue is not conditional on DAO mistakes. Because, the incentives are bridged from L1 to L2, but they are not distributed to instances on L2, so, DAO must solve this issue by distributing incentives to instances that are not causing this issue by calling `processDataMaintenance`. After the DAO calls this function, the attacker can replay it by using the replayability feature of the bridging protocol.**
 - It is not necessary that the contract `OptimismTargetDispenserL2` has enough balance to apply this attack. Even if its balance is not enough, it will be queued in the mapping `stakingQueueingNonces` to be redeemed later.
 - The attacker can add the instanceB as nominee and vote a small amount for it just to make staking incentives of instanceB nonzero. By doing so, later it is possible to distribute staking incentives to this instance and apply the attack. In other words, it is not necessary that instanceB waits for other users to vote for it.
 - The explained customized implementation of instanceB is just an example to stuck the message delivery flow and apply the attack. So, the staking instance can be implemented differently (instead of just adding a pausing mechanism to the deposit functionality). 
 - The whitelisting is an optional mechanism (the `verifier` address could be zero or `implementationsCheck` could be false).

In summary:

The attacker creates an instance that can revert when the staking incentive is going to be deposited into it. Then, the attacker votes for it to entitle for incentives. When a batch of incentives are going to be distributed to instances, the attacker's instance will revert and it stops the flow of incentives distribution. Then DAO solves this issue manually. Then the attacker replays the failed transaction using the bridging protocol. By doing so, the incentive distribution is done twice to the instances.

## Recommended Mitigation Steps

The following solutions are recommended:

 - A boolean shuld be assigned to each staking batch data so that the DAO can invalidate them in such scenarios. 
 ```solidity
mapping(bytes32 => bool) public is Executed;
function _processData(bytes memory data) internal {
    //.....
    isExecuted(!keccack256(data), "already executed");
    isExecuted[keccak256(data)] = true;
    //.....
}

    function processDataMaintenance(bytes memory data, bytes memory stuckData) external {
        // ...
        isExecuted[keccak256(stuckData)] = true;
    }
```

 - To each bridging message a unique id should be assigned, so that each batch is distinguishable from one another.
 ```solidity
    function _sendMessage(
        address[] memory targets,
        uint256[] memory stakingIncentives,

        uint256 transferAmount

```
