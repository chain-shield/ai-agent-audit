# Vulnerability details

## Impact

Contract : voteWeighting 
When the last item in the `setNominees` array is removed via the `removeNominee` function, 
there is an accounting error in the `mapNomineeIds` mapping,
wherein the removed Nominee gets reassigned the same ID, instead of 0.

This same ID is assigned to the subsequent nominee that gets added.
Resulting in 2 Nominees sharing the same ID.

This incorrect Nominee ID Tracking results in unexpected outcomes
in the following functions relying on `mapNomineeIds` mapping.
- `getNextAllowedVotingTimes()`
- `getNomineeId()`
- `removeNominee()`
- `_getWeight()`

## Proof of Concept

Contract : VoteWeighting

1. Assume the following initial state

```
setNominees = [0, Nominee1, Nominee2, Nominee3]

mapNomineeIds:
mapNomineeIds[hash(nominee1)] = 1
mapNomineeIds[hash(nominee2)] = 2
mapNomineeIds[hash(nominee3)] = 3
```

2. Owner removes Nominee3, the last item in the  `setNominees ` array.

```
uint256 beforeRemovalId =   VoteWeightingContract.getNomineeId(Nominee3Addr, 1);
vm.prank(owner);
VoteWeightingContract.removeNominee(Nominee3Addr, 1);
uint256 afterRemovalId = VoteWeightingContract.getNomineeId(Nominee3Addr, 1);
assertEq(beforeRemovalId , afterRemovalId);
```
3. This results in, 

- `Nominee3` still having the same ID (3), instead of being set to 0.

- The same ID (3) is assigned to the next Nominee (say Nominee4) that gets added as well.

## Tools Used

Manual Review, Foundry

## Recommended Mitigation Steps

One potential solution is to move the `mapNomineeIds[nomineeHash] = 0` to the end.

```
        // Shuffle the current last nominee id in the set to be placed to the removed one
        nominee = setNominees[setNominees.length - 1];
        bytes32 replacedNomineeHash = keccak256(abi.encode(nominee));
        mapNomineeIds[replacedNomineeHash] = id;
        setNominees[id] = nominee;
        // Pop the last element from the set
        setNominees.pop();
        
        // Remove nominee from the map
        mapNomineeIds[nomineeHash] = 0;
```
