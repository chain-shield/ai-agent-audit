# Vulnerability details

## Relevant Context

In the [claimStakingIncentives()](https://github.com/code-423n4/2024-05-olas/blob/main/tokenomics/contracts/Dispenser.sol#L953C3-L1048C1) function allows users to claim staking incentives for a specific staking target. It calculates the staking incentives based on the provided `numClaimedEpochs`, `chainId`, and `stakingTarget`. The function also handles the distribution of the staking incentives to the corresponding deposit processor.

## Finding Description

The bug lies in the [claimStakingIncentives()](https://github.com/code-423n4/2024-05-olas/blob/main/tokenomics/contracts/Dispenser.sol#L953C3-L1048C1) function. The function does not properly handle the case when the `stakingIncentive` is `> 0`, but the `transferAmount` is `0` due to the withheld amount being `>=` to the `stakingIncentive`.

Here's the relevant code:

```solidity
// Check if staking incentive is deposited
if (stakingIncentive > 0) {
    transferAmount = stakingIncentive;
    // Account for possible withheld OLAS amounts
    // Note: in case of normalized staking incentives with bridging decimals, this is correctly managed
    // as normalized amounts are returned from another side
    uint256 withheldAmount = mapChainIdWithheldAmounts[chainId];
    if (withheldAmount > 0) {
        // If withheld amount is enough to cover all the staking incentives, the transfer of OLAS is not needed
        if (withheldAmount >= transferAmount) {
            withheldAmount -= transferAmount;
            transferAmount = 0;
        } else {
            // Otherwise, reduce the transfer of tokens for the OLAS withheld amount
            transferAmount -= withheldAmount;
            withheldAmount = 0;
        }
        mapChainIdWithheldAmounts[chainId] = withheldAmount;
    }

    // Check if minting is needed as the actual OLAS transfer is required
    if (transferAmount > 0) {
        uint256 olasBalance = IToken(olas).balanceOf(address(this));

        // Mint tokens to self in order to distribute to the staking deposit processor
        ITreasury(treasury).withdrawToAccount(address(this), 0, transferAmount);

        // Check the balance after the mint
        olasBalance = IToken(olas).balanceOf(address(this)) - olasBalance;
        if (olasBalance != transferAmount) {
            revert WrongAmount(olasBalance, transferAmount);
        }
    }

    // Dispense to a service staking target
    _distributeStakingIncentives(chainId, stakingTarget, stakingIncentive, bridgePayload, transferAmount);
}
```

If the `withheldAmount` is `>=` the `transferAmount`, the code sets `transferAmount` to `0`. However, it still proceeds to call the `_distributeStakingIncentives` function with the original `stakingIncentive` value, even though no tokens were minted or transferred.

## Impact Explanation

This bug therefore leads to a situation where the contract incorrectly distributes staking incentives to the deposit processor without actually transferring the required `OLAS` tokens. As a result, the deposit processor may receive inflated staking incentives, potentially leading to an inconsistent state and improper distribution of rewards.

## Likelihood Explanation

The likelihood of this bug occurring depends on the frequency and magnitude of withheld amounts. But if the withheld amounts are consistently high enough to cover the staking incentives, this bug will be triggered more often. Even if it occurs rarely, it can still have a significant impact on the integrity of the staking incentives distribution.

## Recommendation

To fix the bug, the [claimStakingIncentives()](https://github.com/code-423n4/2024-05-olas/blob/main/tokenomics/contracts/Dispenser.sol#L953C3-L1048C1) function should update the `stakingIncentive` value based on the `transferAmount` after accounting for the withheld amount. If the `transferAmount` becomes `0`, the `stakingIncentive` should also be set to `0`.

Here's the corrected code:

```solidity
// Check if staking incentive is deposited
if (stakingIncentive > 0) {
    transferAmount = stakingIncentive;
    // Account for possible withheld OLAS amounts
    // Note: in case of normalized staking incentives with bridging decimals, this is correctly managed
    // as normalized amounts are returned from another side
    uint256 withheldAmount = mapChainIdWithheldAmounts[chainId];
    if (withheldAmount > 0) {
        // If withheld amount is enough to cover all the staking incentives, the transfer of OLAS is not needed
        if (withheldAmount >= transferAmount) {
            withheldAmount -= transferAmount;
            transferAmount = 0;
            stakingIncentive = 0; // Set stakingIncentive to zero
        } else {
            // Otherwise, reduce the transfer of tokens for the OLAS withheld amount
            transferAmount -= withheldAmount;
            stakingIncentive = transferAmount; // Update stakingIncentive
            withheldAmount = 0;
        }
        mapChainIdWithheldAmounts[chainId] = withheldAmount;
    }

    // Check if minting is needed as the actual OLAS transfer is required
    if (transferAmount > 0) {
        uint256 olasBalance = IToken(olas).balanceOf(address(this));

        // Mint tokens to self in order to distribute to the staking deposit processor
        ITreasury(treasury).withdrawToAccount(address(this), 0, transferAmount);

        // Check the balance after the mint
        olasBalance = IToken(olas).balanceOf(address(this)) - olasBalance;
        if (olasBalance != transferAmount) {
            revert WrongAmount(olasBalance, transferAmount);
        }
    }

    // Dispense to a service staking target
    _distributeStakingIncentives(chainId, stakingTarget, stakingIncentive, bridgePayload, transferAmount);
}
```

By updating the `stakingIncentive` value based on the `transferAmount`, the contract ensures that the deposit processor receives the correct amounts of staking incentives, aligned with the actual transferred `OLAS` tokens.

Note that my recommendation assumes that the deposit processor expects the `stakingIncentive` value to match the actual transferred amount. If the deposit processor relies on the original `stakingIncentive` value for other purposes, additional adjustments may be necessary.
