# Vulnerability details

## Impact
```solidity
// Check for the retainer hash
if (retainerHash == nomineeHash) {
    revert WrongAccount(retainer);
}
```
The purpose of this check seems to be preventing the removal of the retainer account. However, the check is comparing the `retainerHash` with the `nomineeHash`. If the `nomineeHash` happens to match the `retainerHash`, the function will revert with the `WrongAccount` error, even if the `nomineeHash` does not correspond to the actual retainer address.

## Proof of Concept
The bug in the `removeNominee` function allows for the unintended removal of the retainer account. If an attacker manages to find a `nomineeHash` that matches the `retainerHash`, they can exploit this vulnerability to remove the retainer account from the system, even though the `nomineeHash` does not correspond to the actual retainer address.

```solidity
// Check for the retainer hash
if (retainerHash == nomineeHash) {
    revert WrongAccount(retainer);
}
```
**Explanation:** The purpose of this code snippet is to prevent the removal of the retainer account. The `retainerHash` is likely a stored hash value representing the retainer account, while the `nomineeHash` is the hash of the account that is being removed.

However, the issue lies in the comparison between `retainerHash` and `nomineeHash`. The code is directly comparing these two hash values, assuming that if they match, the `nomineeHash` corresponds to the retainer account. But this assumption is flawed because hash collisions can occur.

In Solidity, the `==` operator compares the binary representation of the values. If two different inputs happen to have the same hash value (i.e., a hash collision), the condition `retainerHash == nomineeHash` will evaluate to `true`, even though the `nomineeHash` does not correspond to the retainer address.

An example:

  1. Suppose the `retainerHash` is set to a specific value, let's say 0x1234567890abcdef.
  2. An attacker finds an account with a different address, let's say `0xattackeraddress`, that happens to have the same hash value as `retainerHash` when hashed using the same hashing algorithm.
  3. The attacker calls the `removeNominee` function with the `nomineeHash` set to `0x1234567890abcdef`.
  4. The condition `retainerHash == nomineeHash` evaluates to true since both values are the same.
  5. The function reverts with the `WrongAccount` error, effectively removing the account associated with `0xattackeraddress`, even though it is not the actual retainer account.

## Recommended Mitigation Steps
The comparison should be made between the `nomineeHash` and the hash of the retainer address, rather than the `retainerHash`. 
```solidity
// Check for the retainer address
if (keccak256(abi.encodePacked(retainer)) == nomineeHash) {
    revert WrongAccount(retainer);
}
```
By hashing the `retainer` address using `keccak256` and comparing it with the `nomineeHash`, the function will correctly identify if the provided `nomineeHash` corresponds to the `retainer` address and revert accordingly.
