# Vulnerability details

## Description
When executing the deposit internal function at the EthereumDepositProcessor contract, the contract calls StakingFactory.verifyInstanceAndGetEmissionsAmount to check the validity of parameters.
In this context, the verifyInstance function at the StakingVerifier contract checks if the instance receiving the deposit has its rewardsPerSecond within acceptable bounds otherwise it reverts the call by returning the false boolean:
```solidity
function verifyInstance(address instance, address implementation) external view returns (bool) {
        ...
        // Check for the staking parameters
        // This is a must have parameter for all staking contracts
        uint256 rewardsPerSecond = IStaking(instance).rewardsPerSecond();
        if (rewardsPerSecond > rewardsPerSecondLimit) {
            return false;
        }
        ...
}    
```

The changeStakingLimits function at the StakingVerifier contract allows the owner to arbitrarily change the rewardsPerSecondLimit public uint256 without checking if this breaks the integration with any staking instance.
This can lead to staking instances not being able to receive deposits after the limits are altered.

## Impact
Some staking instances may lose their ability to receive deposits due to a non-sanity-checked admin function.
Even though the function is admin-controlled, the issue is a case of unintended side-effects of an admin function that lead to the bricking of a contract's functionality.
As a staking instance's rewardsPerSecond variable is only able to be altered during the initialization of the StakingBase contract, this admin action renders the staking instances unable to receive deposits till the admin changes back the rewards per second limit.
This can lead to the loss of services as their staking instances have to be redeployed from scratch.

## Tools Used
Manual review
## Recommended Mitigation Steps
Ensure changes in reward limits are properly communicated and have enough time for services to adapt beforehand.
An option to reduce the impact of changeStakingLimits calls would be to add a function for staking contract owners to change their rewardsPerSecond after its initialization.
