# Vulnerability details

## Impact
`trackServiceDonations` function checks if the service IDs exist in the `IServiceRegistry` contract, but it does not validate the length of the `amounts` array against the length of the `serviceIds` array.

If the amounts array has a different length than the `serviceIds` array, it could lead to unexpected behavior or out-of-bounds access when calling the `_trackServiceDonations` function.

## Proof of Concept
If the `amounts` array has a different length than the `serviceIds` array, it can lead to several issues.

   1. If the `amounts` array is shorter than the `serviceIds` array, accessing elements beyond the length of amounts inside the `_trackServiceDonations` function may result in reading invalid or uninitialized memory, leading to unexpected behavior or even contract failures.

   2. If the `amounts` array is longer than the `serviceIds` array, some donation amounts may be ignored or not properly associated with their corresponding service IDs. This can lead to incorrect tracking of service donations and discrepancies in the recorded data.

   3. Without proper validation, the contract may silently proceed with mismatched array lengths, making it difficult to detect and diagnose issues related to service donations.

The `trackServiceDonations` function is defined in the [tokenomics/contracts/Dispenser.sol#L990-L1027](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/Tokenomics.sol#L990-L1027)
```solidity
function trackServiceDonations(
    address donator,
    uint256[] memory serviceIds,
    uint256[] memory amounts,
    uint256 donationETH
) external {
    // ...

    // Get the number of services
    uint256 numServices = serviceIds.length;
    // Loop over service Ids, accumulate donation value and check for the service existence
    for (uint256 i = 0; i < numServices; ++i) {
        // Check for the service Id existence
        if (!IServiceRegistry(serviceRegistry).exists(serviceIds[i])) {
            revert ServiceDoesNotExist(serviceIds[i]);
        }
    }

    // ...

    // Track service donations
    _trackServiceDonations(donator, serviceIds, amounts, curEpoch);

    // ...
}
```
As you can see, the function checks for the existence of service IDs using the `IServiceRegistry` contract, but it does not validate the length of the `amounts` array against the `serviceIds` array before calling the `_trackServiceDonations` function.

Let's consider a scenario where the `serviceIds` array has a length of 3, but the amounts array has a length of 2. Here's an example of how it could lead to unexpected behavior.
```solidity
uint256[] memory serviceIds = [1, 2, 3];
uint256[] memory amounts = [100, 200];

trackServiceDonations(msg.sender, serviceIds, amounts, 1 ether);
```
In this case, the `trackServiceDonations` function would proceed without validation of the array lengths. When calling the `_trackServiceDonations` function, it may attempt to access the third element of the `amounts` array, which doesn't exist, leading to out-of-bounds access and potential issues.

## Recommended Mitigation Steps
Add a check to ensure that the lengths of `serviceIds` and amounts arrays are equal before proceeding with the rest of the function.
```solidity
// Get the number of services
uint256 numServices = serviceIds.length;

// Check if the lengths of serviceIds and amounts arrays are equal
if (numServices != amounts.length) {
    revert InvalidArrayLengths();
}
```
Adding this check ensures that the `serviceIds` and amounts arrays have the same length, preventing potential issues when calling the `_trackServiceDonations` function.
