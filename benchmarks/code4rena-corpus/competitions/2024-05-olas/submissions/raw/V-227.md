# Vulnerability details

## Description
The syncWithheldTokens function in the context of Dispenser contracts is used to sync withheld token amounts with the L1. 
At the DefaultTargetDispenserL2 contract, it requires no special role to be called and does no sanity checks on the user-inputted bridgePayload bytes memory argument. 
In the context of the OptimismTargetDispenserL2 this is catastrophic, as the bridgePayload is used to determine the cost and the gas limit of the message relayed. 

Now, if we take a look at the sendMessage implementation of the [sendMessage function at the Optimism CrossDomainMessenger contract](https://github.com/ethereum-optimism/optimism/blob/c76c5420c43d1d7d07175b65e89d74925f7a3899/packages/contracts-bedrock/src/universal/CrossDomainMessenger.sol#L176) and at the internal [sendMessage function at the Optimism L2CrossDomainMessenger contract]([optimism/packages/contracts-bedrock/src/L2/L2CrossDomainMessenger.sol at b92dc8ff026e20fabe1f3015718ce4e6e6bdaf97 · ethereum-optimism/optimism (github.com)](https://github.com/ethereum-optimism/optimism/blob/b92dc8ff026e20fabe1f3015718ce4e6e6bdaf97/packages/contracts-bedrock/src/L2/L2CrossDomainMessenger.sol#L43C4-L47C6)) we can notice the cost and msg.value are not sanity checked during a message call:

This enables a malicious caller to attempt to send a message through the Optimism Messenger that doesn't have enough funds to pay for its costs - as the cost is not determined by any sort of calculation, but a variable that the function caller can set at the bridgePayload:
```solidity
function _sendMessage(uint256 amount, bytes memory bridgePayload) internal override {
        ...
        (uint256 cost, uint256 gasLimitMessage) = abi.decode(bridgePayload, (uint256, uint256));
        
    // Check for zero value
        if (cost == 0) {
            revert ZeroValue();
        }

        // Check that provided msg.value is enough to cover the cost
        if (cost > msg.value) {
            revert LowerThan(msg.value, cost);
        }
        ...
}

```

With this in mind, the malicious party can set a very small cost value, such as 1 wei, send 1 wei as the msg.value and then the message will be unrelayable and any ETH sent will be permanently locked - per [optimism/packages/contracts-bedrock/src/universal/CrossDomainMessenger.sol at c76c5420c43d1d7d07175b65e89d74925f7a3899 · ethereum-optimism/optimism (github.com)](https://github.com/ethereum-optimism/optimism/blob/c76c5420c43d1d7d07175b65e89d74925f7a3899/packages/contracts-bedrock/src/universal/CrossDomainMessenger.sol#L170) as it cannot cover the message costs.

The issue with that is syncWithheldTokens assumes any message sent is adequately relayed and sets the withheldAmount to zero when called:
```solidity
function syncWithheldTokens(bytes memory bridgePayload) external payable {
        ...
        // Zero the withheld amount
        withheldAmount = 0;
        ...
}
```
## Impact
Users can pay a small amount of ether to zero withheld amounts held by the OptimismTargetDispenserL2 contract without really syncing with the L1.
This can break the Dispenser contract as it relies on those amounts to calculate how much OLAS to transfer when distributing staking incentives.

## Tools Used
Manual review
## Recommended Mitigation Steps
The cost variable must be sanity checked at the sendMessage internal function of the OptimismTargetDispenserL2 contract to ensure it is at least of a minimum amount for the message to be relayed.
There are two mitigation options, the first one is to try and attempt to simulate costs and have the msg.sender pay at least its value.
The other one would be to only update the witheldAmount variable after an acknowledgement of message receival at the L1.
