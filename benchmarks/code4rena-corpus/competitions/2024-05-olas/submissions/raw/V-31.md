# Vulnerability details

## Impact
The way the l2Dispenser address is derived from the `sourceAddress`. In the line: [@>tokenomics/contracts/staking/WormholeDepositProcessorL1.sol#L125](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/staking/WormholeDepositProcessorL1.sol#L125)
```solidity
address l2Dispenser = address(uint160(uint256(sourceAddress)));
```
The `sourceAddress` is a `bytes32` value, which is directly converted to a `uint256` and then truncated to a `uint160` before being converted to an `address`. This approach assumes that the `sourceAddress` is always a valid Ethereum address encoded as a `bytes32`. If the `sourceAddress` is not a valid Ethereum address or if it contains additional data beyond the 20-byte address, this conversion could lead to unexpected behavior or even loss of funds.

## Proof of Concept
This can result in loss of funds, unauthorized access, or disruption of the contract's intended functionality.

For example:

Suppose the sourceAddress is set to the following value:
```solidity
bytes32 sourceAddress = 0x1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef;
```
In this case, the `sourceAddress` is a `bytes32` value that is not a valid Ethereum address. When the vulnerable code is executed, it will convert the `sourceAddress` to a `uint256`, truncate it to a `uint160`, and then convert it to an address:
```solidity
uint256 convertedAddress = uint256(sourceAddress);
// convertedAddress = 0x1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef

uint160 truncatedAddress = uint160(convertedAddress);
// truncatedAddress = 0x1234567890abcdef1234567890abcdef12345678

address l2Dispenser = address(truncatedAddress);
// l2Dispenser = 0x1234567890AbCDEF1234567890aBcDeF12345678
```
As a result, the derived `l2Dispenser` address is not the intended recipient and could potentially be an attacker-controlled address.

Proof of Concept to demonstrate that an attacker could craft a malicious `sourceAddress` value that, when converted using the vulnerable code, results in a valid Ethereum address under their control. They could then exploit this vulnerability to redirect funds or perform unauthorized actions.

For example, an attacker could set the `sourceAddress` to a value like:
```solidity
bytes32 sourceAddress = 0x000000000000000000000000attackerAddress0000000000000000000000000000;
```
Where `attackerAddress` is the attacker's Ethereum address. When the vulnerable code is executed, it will derive the `l2Dispenser` address as the attacker's address, allowing them to receive funds or perform actions intended for the legitimate recipient.

## Recommended Mitigation Steps
Make it in a way to ensure that the `sourceAddress` is properly validated and extracted before converting it to an `address`. By using `bytes20(sourceAddress)`, we extract the first 20 bytes of the `sourceAddress` and convert them to an address, discarding any additional data that may be present in the `bytes32` value.
```solidity
address l2Dispenser = address(bytes20(sourceAddress));
```
