# Vulnerability details

## Impact
`_setL2TargetDispenser` has a significant impact on the flexibility and maintainability of the contract. By allowing the owner to set the l2TargetDispenser address and then immediately revoking the owner role, the contract becomes permanently `ownerless` after the first call to this function. This means that once the `l2TargetDispenser` address is set, it cannot be modified or updated in the future, even if there is a legitimate need to do so.

Consider a scenario where the initially set `l2TargetDispenser` address becomes compromised, invalid, or needs to be updated due to changes in the system architecture. In such cases, the contract would be stuck with the outdated or problematic address, potentially leading to system failures, lost funds, or security vulnerabilities.

Furthermore, the inability to update the `l2TargetDispenser` address limits the contract's adaptability to future requirements or improvements. If new features or integrations require a different `l2TargetDispenser` address, the contract would need to be redeployed, which can be costly and disruptive to the existing system.

```solidity
function _setL2TargetDispenser(address l2Dispenser) internal {
    // Check the contract ownership
    if (msg.sender != owner) {
        revert OwnerOnly(owner, msg.sender);
    }

    // The L2 target dispenser must have a non zero address
    if (l2Dispenser == address(0)) {
        revert ZeroAddress();
    }
    l2TargetDispenser = l2Dispenser;

    // Revoke the owner role making the contract ownerless
    owner = address(0);

    emit L2TargetDispenserUpdated(l2Dispenser);
}
```
As you can see, after setting the `l2TargetDispenser` address, the function immediately sets the owner variable to `address(0)`, effectively revoking the owner role and making the contract ownerless.

## Proof of Concept
To illustrate the impact of this issue, let's consider a simple proof of concept:

1. The contract is deployed with an initial owner address.
2. The owner calls the `_setL2TargetDispenser` function, providing a valid `l2Dispenser` address.
3. The `l2TargetDispenser` address is set, and the owner role is revoked, making the contract ownerless.
4. Later, it is discovered that the `l2TargetDispenser` address needs to be updated due to a security vulnerability or system upgrade.
5. However, since the contract is now ownerless, there is no way to modify the `l2TargetDispenser` address, leaving the contract stuck with the outdated or vulnerable address.

We can see how the current implementation of the `_setL2TargetDispenser` function can lead to a situation where the contract becomes inflexible and unable to adapt to future requirements or address potential issues with the `l2TargetDispenser address`.

## Recommended Mitigation Steps
1. Instead of revoking the owner role completely, consider implementing a multi-step ownership transfer process. This allows the current owner to propose a new owner, and the proposed owner can then accept the ownership transfer. This way, the ownership can be transferred when needed while still maintaining control over the contract.

2. If sticking with the current approach of making the contract ownerless after setting the `l2TargetDispenser`, consider implementing a time-lock mechanism. This means that after setting the `l2TargetDispenser`, the contract remains ownerless for a certain period of time (e.g., 24 hours or 7 days). During this time, the owner has the ability to revert the changes if any issues are discovered. Once the time-lock period expires, the contract becomes permanently ownerless.
