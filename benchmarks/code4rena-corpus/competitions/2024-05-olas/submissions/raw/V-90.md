# Vulnerability details

## Impact
The DAO is only able to increase the `withheldAmount` in cases where the syncing message is failed to be bridged from L2 to L1. This can lead to a big issue when the third party bridge is unresponsive for some time, and then it becomes responsive and allowing to replay the failed transaction.

## Proof of Concept
Whenever there is nonzero `withheldAmount` on L2, it should be synced on L1. This is done by calling the function `syncWithheldTokens`, where it bridges a message consisting of the value of `withheldAmount` to L1.

```solidity
    function syncWithheldTokens(bytes memory bridgePayload) external payable {
        // Reentrancy guard
        if (_locked > 1) {
            revert ReentrancyGuard();
        }
        _locked = 2;

        // Pause check
        if (paused == 2) {
            revert Paused();
        }

        // Check the withheld amount to be greater than zero
        uint256 amount = withheldAmount;
        if (amount == 0) {
            revert ZeroValue();
        }

        // Zero the withheld amount
        withheldAmount = 0;

        // Send a message to sync the withheld amount
        _sendMessage(amount, bridgePayload);

        emit WithheldAmountSynced(msg.sender, amount);

        _locked = 1;
    }
```

In cases where bridging this message (to sync the `withheldAmount` on both layers) from L2 to L1 fails, the DAO is able to sync it manually, by calling the function `syncWithheldAmountMaintenance`.
```solidity
    function syncWithheldAmountMaintenance(uint256 chainId, uint256 amount) external {
        // Check the contract ownership
        if (msg.sender != owner) {
            revert OwnerOnly(msg.sender, owner);
        }

        // Check zero value chain Id and amount
        if (chainId == 0 || amount == 0) {
            revert ZeroValue();
        }

        // The sync must never happen for the L1 chain Id itself, as dispenser exists strictly on L1-s
        if (chainId == block.chainid) {
            revert WrongChainId(chainId);
        }

        // Get bridging decimals for a specified chain Id
        address depositProcessor = mapChainIdDepositProcessors[chainId];
        uint256 bridgingDecimals = IDepositProcessor(depositProcessor).getBridgingDecimals();

        // Normalize the synced withheld amount via maintenance is correct
        if (bridgingDecimals < 18) {
            uint256 normalizedAmount = amount / (10 ** (18 - bridgingDecimals));
            normalizedAmount *= 10 ** (18 - bridgingDecimals);
            // Downsize staking incentive to a specified number of bridging decimals
            amount = normalizedAmount;
        }

        // The overall amount is bound by the OLAS projected maximum amount for years to come
        uint256 withheldAmount = mapChainIdWithheldAmounts[chainId] + amount;
        if (withheldAmount > type(uint96).max) {
            revert Overflow(withheldAmount, type(uint96).max);
        }

        // Add to the withheld amount
        mapChainIdWithheldAmounts[chainId] = withheldAmount;

        emit WithheldAmountSynced(chainId, amount, withheldAmount);
    }
```

The issue is that DAO is able to **only** increase the mapping `mapChainIdWithheldAmounts` with the parameter `amount`, **not** to decrease.
```solidity

```

This can be a problem in the following scenario:

 - Suppose the `withheldAmount` value is 100e18 on L2.
 - A message is bridged from L2 to L1 to sync the `withheldAmount` value on L1 by calling `syncWithheldTokens`. 
 - The bridge (take Optimism as an example) does not deliver this message to L1 for any reason. For example, suppose the contract `OptimismPortal` is paused. Note that assumption of `OptimismPortal` being paused is just a simple assumption to make the scenario understandable. More complex and realistic cases leading to stuck of a transaction is related to the bridge protocols which are out-of-scope.
 https://github.com/ethereum-optimism/optimism/blob/65ec61dde94ffa93342728d324fecf474d228e1f/packages/contracts-bedrock/contracts/L1/OptimismPortal.sol#L327
 - So, DAO manually syncs this value on L1 by calling `syncWithheldAmountMaintenance`. Thus, we will have the mapping `mapChainIdWithheldAmounts[10] = 100e18` (where 10 is the chain id of OP Mainnet).
 - Later, suppose the `OptimismPortal` is unpaused and continues to working. Now, anyone can replay the stuck transaction (old failed message delivery) on L1.
  https://github.com/ethereum-optimism/optimism/blob/65ec61dde94ffa93342728d324fecf474d228e1f/packages/contracts-bedrock/contracts/L1/OptimismPortal.sol#L325
  https://github.com/ethereum-optimism/optimism/blob/65ec61dde94ffa93342728d324fecf474d228e1f/packages/contracts-bedrock/contracts/universal/CrossDomainMessenger.sol#L303
 - By doing so, the function `syncWithheldAmount(10, 100e18)` will be called, and it adds 100e18 to the mapping `mapChainIdWithheldAmounts[10]`. So, we will have: `mapChainIdWithheldAmounts[10] = 200e18`. This shows that `Dispenser` on L1 assumes that the contract `OptimismTargetDispenserL2` is holding 200e18 token, while in reality it is only holding 100e18.
 - This leads to a big issue. Because, later when staking incentives again are supposed to be distributed to Op Mainnet, it will transfer `stakingIncentive - 200e18`.

## Recommended Mitigation Steps

It is recommended that DAO be able to set the value of `withheldAmount` directly (not just increasing) in these cases:
```solidity
    function syncWithheldAmountMaintenance(uint256 chainId, uint256 amount) external {
        // .....

        // Check zero value chain Id and amount
        if (chainId == 0) {
            revert ZeroValue();
        }

        // .....


        if (amount > type(uint96).max) {
            revert Overflow(amount, type(uint96).max);
        }

        mapChainIdWithheldAmounts[chainId] = amount;

    }
```

Or, assign a nonce to the bridging message, so that in cases where DAO manually sets `withheldAmount`, invalidates those messages as well to not be replayable.
