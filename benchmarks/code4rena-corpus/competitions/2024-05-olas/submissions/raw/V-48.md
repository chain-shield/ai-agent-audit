# Vulnerability details

## Impact
In the current implementation, the loop in the `_getWeight` function is defined as follows: [#L267-L270](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L267-L270)
```solidity
for (uint256 i = 0; i < MAX_NUM_WEEKS; i++) {
    if (t > block.timestamp) {
        break;
    }
    // ...
}
```
The loop iterates up to `MAX_NUM_WEEKS` times, regardless of the value of `t` in relation to the current block timestamp. The issue arises when `t` exceeds `block.timestamp` during the loop iterations.

Consider the following scenario.

- `MAX_NUM_WEEKS` is set to a large value, such as 52 (representing one year).
- The nominee's weight has not been updated for a long time, resulting in t being significantly larger than block.timestamp.

In this scenario, the loop will continue to iterate even after `t` exceeds `block.timestamp`. The code inside the loop will be executed unnecessarily, performing computations and state updates that have no effect on the final result.

Code: [#L267-L286](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L267-L286)
```solidity
for (uint256 i = 0; i < MAX_NUM_WEEKS; i++) {
    if (t > block.timestamp) {
        break;
    }
    t += WEEK;
    uint256 dBias = pt.slope * WEEK;
    if (pt.bias > dBias) {
        pt.bias -= dBias;
        uint256 dSlope = changesWeight[nomineeHash][t];
        pt.slope -= dSlope;
    } else {
        pt.bias = 0;
        pt.slope = 0;
    }

    pointsWeight[nomineeHash][t] = pt;
    if (t > block.timestamp) {
        timeWeight[nomineeHash] = t;
    }
}
```
The unnecessary iterations and computations inside the loop lead to excessive gas consumption. Each iteration performs the following operations:

- Addition of `WEEK` to `t`.
- Multiplication of `pt.`and `WEEK` to calculate `dBias`.
- Subtraction of `dBias` from `pt.bias` if `pt.bias` is greater than `dBias`.
- Retrieval of `dSlope` from `changesWeight` mapping and subtraction from `pt.slope`.
- Update of `pt.bias` and `pt.slope` to zero if `pt.bias` is not greater than `dBias`.
- Update of `pointsWeight` mapping with the updated pt values.
- Update of `timeWeight` mapping if t exceeds `block.timestamp`.

These operations consume gas, and performing them unnecessarily for each iteration after `t` exceeds `block.timestamp` leads to excessive gas consumption.

## Proof of Concept
To illustrate the impact, let's consider an example:

- `MAX_NUM_WEEKS` is set to 52.
- The current `block.timestamp` is 1000.
- The nominee's `t` value is 2000.

In this case, the loop will iterate 52 times, even though t already exceeds `block.timestamp` from the beginning. The loop will perform unnecessary computations and state updates for all 52 iterations, consuming extra gas.

## Recommended Mitigation Steps
The loop condition should be modified to break out of the loop when `t` exceeds `block.timestamp`.
```solidity
for (uint256 i = 0; i < MAX_NUM_WEEKS && t <= block.timestamp; i++) {
    // ...
}
```
By adding the condition `t <= block.timestamp` to the loop condition, the loop will exit early when `t` exceeds the current block timestamp.
