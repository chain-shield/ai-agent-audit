# Vulnerability details

## Impact
The front-running vulnerability discovered in the ``claimStakingIncentivesBatch`` function of the Dispenser contract allows an attacker to exploit transaction ordering to manipulate state changes and transaction outcomes. By preempting transactions, an attacker could potentially alter the sequence of critical operations. Legitimate users claiming staking incentives might receive less than expected due to the attacker's manipulation.Attackers can exploit the vulnerability to gain a larger share of staking rewards, undermining the fairness of the system. 
## Proof of Concept
The provided test rule highlights the potential for a front-running vulnerability in the ``claimStakingIncentivesBatch`` function by simulating two transactions and analysing their outcomes.

Understanding the Code Snippet:
f(e1, arg): This represents a call to the function ``claimStakingIncentivesBatch()`` within a specific environment (e1) with arguments (arg).
!lastReverted: This checks if the previous call to f did not revert (meaning it was successful).
env e2; calldata arg2: These lines define a new environment (e2) and arguments (arg2) for a second call to f.
require e2.msg.sender != e1.msg.sender: This ensures the sender addresses for the two calls (f(e1, arg) and f(e2, arg2)) are different, likely simulating two separate users.
f(e2, arg2) at initialStorage: This calls f again in the e2 environment with arg2 arguments, but crucially, it uses initialStorage. This suggests the attacker might be trying to exploit the initial state of the contract before the first call modifies it.
f@withrevert(e1, arg): This calls f again in the e1 environment with arg arguments, but with a @withrevert decorator, indicating it's expected to revert.
!lastReverted: This checks if the last call to f reverted (as expected).

How it Reveals Frontrunning:

Exploiting Initial State (f(e2, arg2) at initialStorage): The second call (f(e2, arg2)) in a different environment (e2) attempts to exploit the initial state (before the first call's modifications). This suggests the attacker might be trying to manipulate calculations or checks that rely on storage variables in their original state.
Second Call Outcome Uncertain: The outcome of this second call with initialStorage is unclear. However, the attacker might be hoping to gain an advantage based on the initial state, potentially leading to the first call receiving less than intended or failing altogether.
