# Vulnerability details

## Impact
The incorrect logic in the `unstake` function's condition may prevent services from unstaking even when they have met the minimum staking duration requirement. This can lead to services being locked in the staking contract unintentionally.


## Proof of Concept
Take a look at the `unstake` function:

https://github.com/code-423n4/2024-05-olas/blob/9b812d9d8cade3ecbd0043ae2fbd70a9d969b901/registries/contracts/staking/StakingBase.sol#L817-L820

```solidity
// Check that the service has staked long enough, or if there are no rewards left
uint256 ts = block.timestamp - tsStart;
if (ts <= minStakingDuration && availableRewards > 0) {
    revert NotEnoughTimeStaked(serviceId, ts, minStakingDuration);
}
```
[And the Inline comment states that:](https://github.com/code-423n4/2024-05-olas/blob/9b812d9d8cade3ecbd0043ae2fbd70a9d969b901/registries/contracts/staking/StakingBase.sol#L816)

```solidity
 // Check that the service has staked long enough, or if there are no rewards left
```

However, the condition `ts <= minStakingDuration && availableRewards > 0` uses the `&&` operator, which means that the `NotEnoughTimeStaked` error will only be thrown if both conditions are true. Albeit, the intended behavior seems to be to allow unstaking if either the minimum staking duration has been met `OR` if there are no rewards left.

## Recommended Mitigation Steps:
Update the condition in the `unstake` function to use the `||` (logical OR) operator instead of `&&` (logical AND):

```diff
   // Check that the service has staked long enough, or if there are no rewards left
    uint256 ts = block.timestamp - tsStart;
-   if (ts <= minStakingDuration && availableRewards > 0) {
+   if (ts <= minStakingDuration || availableRewards > 0) {
      revert NotEnoughTimeStaked(serviceId, ts, minStakingDuration);
}
```
