# Vulnerability details

## Impact
[getNextAllowedVotingTimes](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L779-L805) will return an incorrect next allowed voting time for voters who have never voted for a particular nominee. 

**This can lead to two potential problems:**

**`Allowing voters to vote too early`** If the `lastUserVote[voters[i]][nomineeHash]` is `0`, adding `WEIGHT_VOTE_DELAY` to it will result in a next allowed voting time that is equal to `WEIGHT_VOTE_DELAY`. This means that the voter will be allowed to vote immediately after the function call, even though they have never voted for that nominee before. This violates the intended behavior of enforcing a delay between votes for the same nominee.

**`Underflow issue`** If `WEIGHT_VOTE_DELAY` is a large value (e.g., a year or more), adding it to `0` can cause an underflow in the `uint256` data type, resulting in an extremely large value for the next allowed voting time. This can effectively lock the voter out from voting for that nominee for an extended period.

## Proof of Concept
Suppose we have the following setup:

`WEIGHT_VOTE_DELAY` is set to `365 days` (approximately one year)
Voter `0x1234...` has never voted for the nominee with the hash `0x5678...`
The current block timestamp is `1677628800` (March 1, 2023, 00:00:00 UTC)

When calling `getNextAllowedVotingTimes` with the nominee hash `0x5678...` and the voter `0x1234...`, the function will calculate the next allowed voting time as follows:
```solidity
nextAllowedVotingTimes[i] = lastUserVote[0x1234...][0x5678...] + WEIGHT_VOTE_DELAY;
                           = 0 + 365 days;
                           = 0;
```
Due to the underflow issue, the next allowed voting time is calculated as `0`, which means the voter `0x1234...` will be allowed to vote immediately, even though they have never voted for that nominee before.

Ref Code: [getNextAllowedVotingTimes#L804](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/governance/contracts/VoteWeighting.sol#L804)
```solidity
nextAllowedVotingTimes[i] = lastUserVote[voters[i]][nomineeHash] + WEIGHT_VOTE_DELAY;
```
This line assumes that `lastUserVote[voters[i]][nomineeHash]` is always initialized and has a valid value. However, if a voter has never voted for a particular nominee before, the `lastUserVote` mapping will not have an entry for that voter-nominee combination.

In such cases, the value of `lastUserVote[voters[i]][nomineeHash]` will be the default value of `uint256`, which is `0`. Adding `WEIGHT_VOTE_DELAY` to `0` will result in an incorrect next allowed voting time.

## Recommended Mitigation Steps
Check if `lastUserVote[voters[i]][nomineeHash]` is `0` and handle the case where the voter has never voted for the nominee before is using the current block timestamp as the starting point for the next allowed voting time if `lastUserVote[voters[i]][nomineeHash]` is `0`.
```solidity
nextAllowedVotingTimes[i] = lastUserVote[voters[i]][nomineeHash] > 0
    ? lastUserVote[voters[i]][nomineeHash] + WEIGHT_VOTE_DELAY
    : block.timestamp + WEIGHT_VOTE_DELAY;
```
This way, if `lastUserVote[voters[i]][nomineeHash]` is `0` (i.e., the voter has never voted for the nominee before), the next allowed voting time will be calculated based on the current block timestamp plus the `WEIGHT_VOTE_DELAY`.
