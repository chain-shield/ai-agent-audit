# Vulnerability details

## Impact
Incorrect order of arguments passed to the `sendTokenWithPayloadToEvm` function in the `_sendMessage` function can have significant implications for the functionality and security: [@>tokenomics/contracts/staking/WormholeDepositProcessorL1.sol#L96-L98](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/staking/WormholeDepositProcessorL1.sol#L96-L98)
```solidity
sequence = sendTokenWithPayloadToEvm(uint16(wormholeTargetChainId), l2TargetDispenser, data, 0,
    gasLimitMessage, olas, transferAmount, uint16(l2TargetChainId), refundAccount);
```
The bug is related to the order of arguments passed to the `sendTokenWithPayloadToEvm` function. According to the Wormhole documentation and the source code, the correct order of arguments for `sendTokenWithPayloadToEvm` should be: https://github.com/wormhole-foundation/hello-token
```solidity
function sendTokenWithPayloadToEvm(
    uint16 recipientChain,
    bytes32 recipient,
    bytes memory payload,
    uint256 arbiterFee,
    uint32 nonce,
    uint256 amount,
    uint16 tokenChainId,
    bytes32 tokenAddress,
    address refundAddress
) public payable returns (uint64 sequence)
```
In the `_sendMessage` function, the arguments are passed in the wrong order. The `gasLimitMessage` is passed as the nonce argument, and the `olas` variable is passed as the `arbiterFee` argument, which is incorrect.

_**`Details of the Impacts`**_
1. Incorrect gas limit:
   - In the current implementation, `gasLimitMessage` is passed as the nonce argument to `sendTokenWithPayloadToEvm`.
   - The `nonce` argument is typically used to prevent replay attacks and ensure the uniqueness of each message.
   - By passing `gasLimitMessage` as `nonce`, the intended gas limit for the message is not being properly set, which can lead to unexpected behavior and potential failures in message execution on the target chain.

2. Incorrect token address:
   - The `olas` variable, which likely represents the token address, is passed as the `arbiterFee` argument to `sendTokenWithPayloadToEvm`.
   - The `arbiterFee` argument is used to specify the fee paid to the arbiter for processing the message.
   - By passing the token address as the `arbiterFee`, the contract is essentially treating the token address as a fee amount, which is incorrect and can lead to unintended consequences.

3. Potential loss of funds:
   - If the `olas` variable contains a valid token address, passing it as the `arbiterFee` could result in the contract attempting to transfer tokens to an invalid address or an unintended recipient.
   - This could lead to the loss of tokens and funds associated with the message transmission.

## Recommended Mitigation Steps
Update the line to pass the arguments in the correct order:
```solidity
sequence = sendTokenWithPayloadToEvm(uint16(wormholeTargetChainId), l2TargetDispenser, data, 0,
    0, transferAmount, uint16(l2TargetChainId), olas, refundAccount);
```
Here, the nonce argument is set to `0`, and the `olas` variable is passed as the `tokenAddress` argument, which is the correct order according to the Wormhole documentation.
