# Vulnerability details

## Impact
`claimOwnerIncentives` function starts by checking the `_locked` variable [tokenomics/contracts/Dispenser.sol#L94-L797](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/Dispenser.sol#L794-L797)
```solidity
if (_locked > 1) {
    revert ReentrancyGuard();
}
_locked = 2;
```
If `_locked` is greater than 1, it reverts with a `ReentrancyGuard` error. Otherwise, it sets `_locked` to 2.

However, at the end of the function, it sets `_locked` back to 1
```solidity
_locked = 1;
```
This means that if the function is called again before the first call completes, `_locked` will be 1, and the reentrancy guard will not prevent the second call from executing.

## Proof of Concept
In the case of the [tokenomics/contracts/Dispenser.sol#claimOwnerIncentives](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/Dispenser.sol#L789-L837) function, the reentrancy guard is not implemented correctly. The purpose of the reentrancy guard is to prevent multiple calls to the function from executing concurrently. However, due to the incorrect setting of the `_locked` variable at the end of the function, the guard becomes ineffective.

For example:
```solidity
function claimOwnerIncentives() external {
    if (_locked > 1) {
        revert ReentrancyGuard();
    }
    _locked = 2;

    // Perform some operations
    // ...

    // Vulnerable code: Set _locked back to 1
    _locked = 1;
}
```
If an attacker makes a recursive call to `claimOwnerIncentives` before the first call completes, the second call will bypass the reentrancy guard because `_locked` is set to 1.

## Tools Used
Manual Review

## Recommended Mitigation Steps
The function should set `_locked` back to 0 (or its initial value) at the end instead of setting it to 1. This ensures that the reentrancy guard is properly reset and will prevent subsequent calls until the first call completes.
```solidity
_locked = 0;
```
By setting `_locked` to 0 at the end, the reentrancy guard will work as intended, preventing multiple calls to the function from executing concurrently.
