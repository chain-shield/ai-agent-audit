# Vulnerability details

## Impact
The normalization of the `amount` when the `bridgingDecimals` is less than 18 in `syncWithheldAmountMaintenance` function: [tokenomics/contracts/Dispenser.sol#L1220-L1225](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/Dispenser.sol#L1220-L1225)
```solidity
if (bridgingDecimals < 18) {
    uint256 normalizedAmount = amount / (10 ** (18 - bridgingDecimals));
    normalizedAmount *= 10 ** (18 - bridgingDecimals);
    // Downsize staking incentive to a specified number of bridging decimals
    amount = normalizedAmount;
}
```
The issue is that the normalization process is incorrect. The current code divides `amount` by `10 ** (18 - bridgingDecimals)` and then multiplies the result by the same factor. This effectively cancels out the division and leaves `amount` unchanged.

1. Impact on Withheld Amounts:
   - The purpose of the `syncWithheldAmountMaintenance` function is to manually sync the withheld amount from L2 to L1 in case of a bridge failure scenario.
   - The bug in the normalization process fails to correctly adjust the amount when the `bridgingDecimals` is less than 18.
   - As a result, the withheld amount being synced will not be accurately represented in the L1 contract.
   - This can lead to discrepancies between the actual withheld amount on L2 and the recorded withheld amount on L1.

2. Incorrect Normalization:
   - The problem code attempts to normalize the `amount` based on the `bridgingDecimals`.
   - However, the normalization process is flawed because it divides `amount` by `10 ** (18 - bridgingDecimals)` and then multiplies the result by the same factor.
   - This effectively cancels out the division and leaves `amount` unchanged, defeating the purpose of normalization.
   - As a consequence, the `amount` is not correctly adjusted to the specified number of bridging decimals.

## Proof of Concept
* Let's consider an example:
  - Suppose `amount` is 1000 and `bridgingDecimals` is 6.
  - The expected normalized amount should be 1000 / (10 ** (18 - 6)) = 1000 / (10 ** 12) = 0.000001.
  - However, with the current bug, the normalization process will be:
   - `normalizedAmount` = 1000 / (10 ** (18 - 6)) = 0.000001
   - `normalizedAmount` *= 10 ** (18 - 6) = 0.000001 * (10 ** 12) = 1000

* The resulting `amount` remains unchanged at 1000, which is incorrect.

## Tools Used
Manual Review

## Recommended Mitigation Steps
We should remove the multiplication step.
```solidity
if (bridgingDecimals < 18) {
    uint256 normalizedAmount = amount / (10 ** (18 - bridgingDecimals));
    // Downsize staking incentive to a specified number of bridging decimals
    amount = normalizedAmount;
}
```
With this fix, the `amount` will be correctly normalized to the specified number of bridging decimals when `bridgingDecimals` is less than 18.
