# Vulnerability details

## Impact
In the `refundFromBondProgram`, Currently the code performs the addition first and then checks if the result exceeds` type(uint96).max`: [tokenomics/contracts/Dispenser.sol#L814-L820](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/Tokenomics.sol#L814-L820)
```solidity
uint256 eBond = effectiveBond + amount;
if (eBond > type(uint96).max) {
    revert Overflow(eBond, type(uint96).max);
}
effectiveBond = uint96(eBond);
```
This approach allows for an overflow to occur before the check is performed. If `effectiveBond` is already close to `type(uint96).max` and `amount` is large enough, the addition can overflow, resulting in an incorrect value for `eBond`.

## Proof of Concept
The current implementation of the `refundFromBondProgram` function is vulnerable to an overflow when calculating the new `effectiveBond` value. The addition operation `effectiveBond + amount` is performed first, and then the result is checked against `type(uint96).max`. However, if `effectiveBond` is already close to `type(uint96).max` and `amount` is large enough, the addition can overflow, resulting in an incorrect value for `eBond`.

For example, consider the following scenario:

   - `effectiveBond` is initially set to `type(uint96).max - 100`.
   - The `refundFromBondProgram` function is called with an `amount` equal to 200.

In this case, the addition `effectiveBond + amount` will overflow, resulting in `eBond` being a small value instead of the expected large value. This overflow goes undetected because the check `eBond > type(uint96).max` is performed after the addition.

2. Violation of Invariant: The code includes an invariant comment: [tokenomics/contracts/Dispenser.sol#L807](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/Tokenomics.sol#L807)
   ```solidity
   /// #if_succeeds {:msg "effectiveBond"} old(effectiveBond + amount) <= type(uint96).max ==> effectiveBond == old(effectiveBond) + amount;
   ```
This invariant suggests that if `old(effectiveBond + amount)` is less than or equal to `type(uint96).max`, then `effectiveBond` should be equal to `old(effectiveBond) + amount` after the function execution. However, due to the overflow vulnerability, this invariant can be violated.

In the scenario where an overflow occurs, `effectiveBond` will not be equal to `old(effectiveBond) + amount`, breaking the expected behavior and violating the invariant.

## Recommended Mitigation Steps
It'll be best to perform the overflow check before updating `effectiveBond`.
```solidity
function refundFromBondProgram(uint256 amount) external {
    // Check for the depository access
    if (depository != msg.sender) {
        revert ManagerOnly(msg.sender, depository);
    }

    if (amount > type(uint96).max - effectiveBond) {
        revert Overflow(effectiveBond + amount, type(uint96).max);
    }
    effectiveBond += uint96(amount);
    emit EffectiveBondUpdated(epochCounter, effectiveBond);
}
```
This way, the overflow check is performed before updating `effectiveBond`. If the addition of amount to `effectiveBond` would exceed `type(uint96).max`, the function reverts with an `Overflow` error. Otherwise, `effectiveBond` is safely updated using the `+=` operator, which automatically truncates the result to `uint96`.
