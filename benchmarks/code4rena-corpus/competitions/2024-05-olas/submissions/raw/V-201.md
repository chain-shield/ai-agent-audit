# Vulnerability details

## Impact
tokenomics/contracts/Dispenser.sol#changeIncentiveFractions function assumes that the sum of `_rewardComponentFraction` and `_rewardAgentFraction` is always less than or equal to 100. Yet it doesn't enforce this condition properly. If the sum of these fractions is less than 100, the `rewardTreasuryFraction` will be calculated incorrectly.

Here's the line: [tokenomics/contracts/Dispenser.sol#L735](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/Tokenomics.sol#L735)
```solidity
tp.epochPoint.rewardTreasuryFraction = uint8(100 - _rewardComponentFraction - _rewardAgentFraction);
```
If `_rewardComponentFraction + _rewardAgentFraction` is less than 100, the `rewardTreasuryFraction` will be set to a value greater than the actual leftover fraction.

## Proof of Concept
[tokenomics/contracts/Dispenser.sol#changeIncentiveFractions](https://github.com/code-423n4/2024-05-olas/blob/e2a8bc31d2769bfb578a06cc64919ad369a82c08/tokenomics/contracts/Tokenomics.sol#L703-L746)
If the sum of `_rewardComponentFraction` and `_rewardAgentFraction` is less than 100, the `rewardTreasuryFraction` will be set to a value greater than the actual leftover fraction. This means that the treasury will receive more rewards than intended, while the components and agents will receive less.

For example, let's say `_rewardComponentFraction` is 30 and `_rewardAgentFraction` is 50. The sum of these fractions is 80, which is less than 100. According to the current implementation, the `rewardTreasuryFraction` will be calculated as:
```solidity
tp.epochPoint.rewardTreasuryFraction = uint8(100 - _rewardComponentFraction - _rewardAgentFraction);
```
In this case, `rewardTreasuryFraction` will be set to 100 - 30 - 50 = 20. However, the actual leftover fraction should be 100 - 80 = 20, not 20.

This issue can lead to an incorrect distribution of rewards, favoring the treasury over the components and agents.

Referenced Code: tokenomics/contracts/Tokenomics.sol, lines 735-736
```solidity
// Rewards are always distributed in full: the leftovers will be allocated to treasury
tp.epochPoint.rewardTreasuryFraction = uint8(100 - _rewardComponentFraction - _rewardAgentFraction);
```

Consider the following scenario:

  1. The `changeIncentiveFractions` function is called with `_rewardComponentFraction = 30` and `_rewardAgentFraction = 50`.
  2. The function checks that the sum of these fractions is not greater than 100, which passes.
  3. The `rewardTreasuryFraction` is calculated as `100 - 30 - 50 = 20`.
  4. The `rewardTreasuryFraction` is set to 20, even though the actual leftover fraction should be `100 - (30 + 50) = 20`.

As a result, the treasury will receive 20% of the rewards, while it should only receive 20% based on the provided fractions.

## Recommended Mitigation Steps
Modify the check for the sum of fractions to ensure that it equals 100 exactly.
```solidity
if (_rewardComponentFraction + _rewardAgentFraction != 100) {
    revert WrongAmount(_rewardComponentFraction + _rewardAgentFraction, 100);
}
```
By changing the condition from `>` to `!=`, you ensure that the sum of `_rewardComponentFraction` and `_rewardAgentFraction` must be exactly 100. This way, there won't be any discrepancy in the calculation of `rewardTreasuryFraction`.

Additionally, you can remove the line that calculates `rewardTreasuryFraction` since it will always be zero if the fractions add up to 100:
```solidity
// Remove this line
// tp.epochPoint.rewardTreasuryFraction = uint8(100 - _rewardComponentFraction - _rewardAgentFraction);
```
By making these changes, I think we can ensure that the `changeIncentiveFractions` function works as intended and avoids any potential bugs related to the calculation of the treasury fraction.
