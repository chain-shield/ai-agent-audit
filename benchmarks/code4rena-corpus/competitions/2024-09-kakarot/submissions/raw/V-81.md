# Vulnerability details

Users are able to cheaply execute such "precompiled" functions (`ECMUL`) for a fixed gas cost (with no real penalty for intentionally submitting bad inputs), then this leads to wasted compute / overloading the underlying nodes / sequencers by running *very* computationally intense tasks, at a hardware level.

This *will* cause unnecessary computation and as a side effect, potentially cause a network wide (or localized) DoS, by intentional continuous (cheap / fixed cost) performance degredation by a malicious actor.

## Proof of Concept

This issue refers to the `ec_mul.cairo` file in `kakarot-ssj`.

File: `https://github.com/kkrt-labs/kakarot-ssj/blob/d4a7873d6f071813165ca7c7adb2f029287d14ca/crates/evm/src/precompiles/ec_operations/ec_mul.cairo#L21`

The current implementation in `ec_mul.cairo` of the `ECMUL` opcode does not follow the specification, through missing logic, as set out in the original EIP ([EIP-196](https://eips.ethereum.org/EIPS/eip-196#gas-costs)), and later updated in [EIP-1108](https://eips.ethereum.org/EIPS/eip-1108).

This is also more briefly summarized on [evm.codes](https://www.evm.codes/precompiled):

_"The gas cost is fixed at 6000. However, if the input does not allow to compute a valid result, all the gas sent is consumed."_

Regardless of the actual gas cost, the important difference is that *all* gas in the current context is consumed, *if* the input is truly invalid (to try discourage network overcomputation of such intensive logic).

The current implemenation in `ec_mul.cairo` only has a fixed _"base"_ gas fee which does not account for this logical flow (where all gas in the context should be consumed on invalid input). For example, looking at the existing logic in `ec_mul.cairo`:

```rust
// ec_mul.cairo

// ...

const BASE_COST: u64 = 6000;
const U256_BYTES_LEN: usize = 32;

pub impl EcMul of Precompile {
    fn address() -> EthAddress {
        0x7.try_into().unwrap()
    }

    fn exec(mut input: Span<u8>) -> Result<(u64, Span<u8>), EVMError> {
        let gas = BASE_COST;

        // Pad the input to 128 bytes to avoid out-of-bounds accesses
        let mut input = input.pad_right_with_zeroes(96);

        let x1_bytes = *(input.multi_pop_front::<32>().unwrap());
        let x1: u256 = load_word(U256_BYTES_LEN, x1_bytes.unbox().span());

        let y1_bytes = *(input.multi_pop_front::<32>().unwrap());
        let y1: u256 = load_word(U256_BYTES_LEN, y1_bytes.unbox().span());

        let s_bytes = *(input.multi_pop_front::<32>().unwrap());
        let s: u256 = load_word(U256_BYTES_LEN, s_bytes.unbox().span());

        let (x, y) = match ec_mul(x1, y1, s) {
            Option::Some((x, y)) => { (x, y) },
            Option::None => {
                // NOTE: At this point, there should be a better way of bubbling up this specific type, to increment the gas to charge the full amount in context e.g. gas = u64::MAX; or another approach
                return Result::Err(EVMError::InvalidParameter('invalid ec_mul parameters'));
            },
        };

        // Append x and y to the result bytes.
        let mut result_bytes = array![];
        let x_bytes = x.to_be_bytes_padded();
        result_bytes.append_span(x_bytes);
        let y_bytes = y.to_be_bytes_padded();
        result_bytes.append_span(y_bytes);

        return Result::Ok((gas, result_bytes.span()));
    }
}

// ...
```

This issue can be demonstrated by generating inputs specifically _not_ on the `BN254` curve and checking the output gas of the function.

The following inputs were generated using $y^2 \equiv x^3 + 3 \mod (p)$, so that: $x = 2$ and $y = 5$, therefore not satisfying the `BN254` equation i.e. $ 5^2 \not\equiv 2^3 + 3 \mod (p) $:

```rust
// ec_mul.cairo

#[cfg(test)]
mod tests {
    // ...
    
    use super::EcMul;

    #[test]
    fn test_ec_mul_bad_gas() {
        // Pick some inputs that ARE NOT on the BN254 curve
        // E.g. this is false: 5^2 = 2^3 + 3 mod p
        let input = [2, 5, 2].span();

        // Now run the ECMUL operation!
        let (gas, _) = EcMul::exec(input).expect('ec_mul failed!');

        // And check that it equals 6000 (since we provided non valid inputs!)
        // NOTE: There is no specific VM handling logic which checks for the ECMUL failure either!
        assert!(gas > 6000, "gas was not greater than the base fee even with bad parameters!");
    }

// ...

}
```

Due to the current design pattern, this function is unlikely to be a suitable place to return the gas, and it is more likely in practice to be moved to the [`precompiles.cairo` logic](https://github.com/kkrt-labs/kakarot-ssj/blob/d4a7873d6f071813165ca7c7adb2f029287d14ca/crates/evm/src/precompiles.cairo#L107) to specifically consume all the remaining gas in the context, however at this time there appears to be no such logic.

## Recommended Mitigation Steps

The best approach would be to follow the EIP-196's logic and consume all the gas in the context, if the inputs have been invalidated. 

Unfortunately, since the existing implementation doesn't demonstrate a clear way to do this through the reverting mechanism, a new approach would need to be added. This could be either:

1. Return the gas used on `EVMError`s: This would require all errors to bubble up the gas, when in most cases it would be `0`, aside from this edge case.
2. Add a specific `EVMError` enum type, which is a subset of the `EVMError::InvalidParameter(...)`, which can be checked for this issue, so that the VM can know to deduct all remain gas in the context.

However, a simpler approach to demonstrate a fix, (without redesigning the error propagation channels) would be to consume all gas left if the `EcMul::exec(...)` fails, since it appears to only revert due to `EvmError::InvalidParameter(...)` (a more extensive / hollistic approach would be to implement point 1 or 2 mentioned).

One solution is as simple as changing the [`precompiles.cairo` logic](https://github.com/kkrt-labs/kakarot-ssj/blob/d4a7873d6f071813165ca7c7adb2f029287d14ca/crates/evm/src/precompiles.cairo#L107):

```rust
// precompiles.cairo

// ...

fn exec_precompile(ref vm: VM) -> Result<(), EVMError> {
    // ...
    0x07 => { EcMul::exec(input)? },
    // ...
}
```

To handle the error with additional logic this time:

```rust
// precompiles.cairo

// ...

fn exec_precompile(ref vm: VM) -> Result<(), EVMError> {
    // ...
    0x07 => { 
        // Check the output status!
        match EcMul::exec(input) {
            Result::Ok(it) => (it), // If it was okay, then leave it and proceed as normal!
            Result::Err(_) => (vm.gas_left(), [].span()) // If it wasn't, then take up ALL of the gas left (the transaction itself should then revert with OutOfGas after this point, since all of gasLeft was used!)
        } 
    },
    // ...
}
```

This approach would mean that if an error were to occur during the `ECMUL` opcode's execution, then all remaining gas in the context would immediately be used, thereby matching the EIP's mentioned. As outlined this approach would not work if it was expected that errors _other_ than `EvmError::InvalidParameter(...)` could occur in `EcMul::exec(...)`.
