# Vulnerability details

There is an inconsistency when storage keys are cached as part of an access list. If the new value is zero, the contract may unintentionally revert to default values. This can create discrepancies between the expected and actual contract state.

The issue arises from the following:

Cached Keys: When a storage key is cached in an access list, it means that the contract has read the value at that key. However, the cached value might not be the most recent one if the storage has been modified since the last read.
Zero Value Handling: The _save_storage function checks if the value is 0. If it is, it assumes that the key is cached and has not been modified. However, this assumption can be incorrect if the storage has been modified after the key was cached.
As a result, there's a risk that the function might fail to update the storage correctly for cached keys that have been modified. This could lead to inconsistencies in the contract's state and potentially compromise its security or functionality.

To address this issue, you could consider the following approaches:

Remove Cached Keys: Before updating the storage, check if the key is cached in the access list. If it is, remove the key from the cache to ensure that the function always updates the storage correctly.

Re-read Cached Keys: Instead of assuming that a cached key has not been modified, you could re-read the value from the storage before updating it. This would ensure that the function always has the most recent value.
