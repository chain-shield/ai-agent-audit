# Vulnerability details

## Impact

Initialization of a `DualVmToken.sol` can accept invalid inputs (invalid starknet addresses) that cannot be recovered post deployment of the `DualVmToken` contract. When this happens, this causes `DualVmToken` contract instances to point to invalid starknet addresses (immutably), and therefore make the instance of the contract unusable.

## Proof of Concept

The `constructor` logic of the `DualVmToken.sol`[1] does not validate whether the `_kakarot` _or_ `_starknetToken` addresses are valid starknet addresses. This is important as in other parts of the code this is ensured with a simple check such as in the `_transferFrom(...)` function call:

```
// DualVmToken.sol

if (from >= STARKNET_FIELD_PRIME || to >= STARKNET_FIELD_PRIME) {
    revert InvalidStarknetAddress();
}
```

This means that if a `DualVmToken` is ever deployed with bad addresses as input, the contract can no longer be used and there is no way to easily overwrite these parameters, as they are both immutable:

```
// DualVmToken.sol

/// @dev The address of the starknet token to call
uint256 public immutable starknetToken;

/// @dev The address of the kakarot starknet contract to call
uint256 public immutable kakarot;
```

## Recommended Mitigation Steps

The simplest mitigation approach would be to ensure that the constructor enforces the same validity checks (as other transfer logic) for the input addresses upon creation such as:

```
// DualVmToken.sol

constructor(uint256 _kakarot, uint256 _starknetToken) {
    if (_kakarot >= STARKNET_FIELD_PRIME || _starknetToken >= STARKNET_FIELD_PRIME) {
        revert InvalidStarknetAddress();
    }
    kakarot = _kakarot;
    starknetToken = _starknetToken;
}
```

This logic would mean that the constructor, and therefore the deployment of the contract fails, so another _correct_ contract could be deployed in its place (instead of the ERC20 unnecessarily occupying the address).

Naturally this should also be avoided by adding setter methods to these addresses (also ideally with validity checks), or by ensuring every user deploys such a contract behind a proxy, but this should really be in the core constructor logic (especially if the parameters are marked `immutable`).
