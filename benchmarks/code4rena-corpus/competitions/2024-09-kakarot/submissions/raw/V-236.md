# Vulnerability details

## Summary 
In the `eth_send_transaction` function of StarkNet’s `eth_rpc.cairo` contract, using `get_caller_address()` can return a 0 address if the contract is called directly. This could lead to various issues, including invalid origin address generation, nonce retrieval errors, unintended transaction failures, security bypasses, and unintended state changes. Adding a check to validate that `caller_address` is not 0 at the start of the function can mitigate these risks. This enhances the security and reliability of the contract, ensuring that only valid transactions are processed and preventing unauthorized actions or unintended state changes.

## Proof of Concept
The `eth_send_transaction` function of the eth_rpc.cairo contract allows performing Ethereum-style transactions on StarkNet. It uses the `get_caller_address` function to get the caller.

According to the [cairo-lang documentation](https://docs.cairo-lang.org/hello_starknet/user_auth.html#), “get_caller_address() returns the address of the source contract that called this contract. It can be the address of the account contract or the address of another contract (if the function was invoked by another contract). When the contract is called directly (rather than through a contract), the function returns 0”. 

If get_caller_address() returns a 0 address, it could lead to several issues in the eth_send_transaction function:
Invalid Origin: The function uses Kakarot.safe_get_evm_address(starknet_caller_address) to get the origin address. If the input is 0, it might result in an invalid or unexpected EVM address.
Nonce Retrieval: The function calls IAccount.get_nonce(starknet_caller_address). If the address is 0, it might fail to retrieve a valid nonce or return an unexpected value.
Transaction Execution: When calling Kakarot.eth_call, an invalid origin address could lead to unexpected behavior in the EVM execution, potentially causing the transaction to fail or produce incorrect results.
Security Implications: A 0 address might bypass certain security checks, potentially allowing unauthorized actions.
State Changes: Even if the transaction fails due to the 0 address, the function still calls Starknet.commit(state), which could lead to unintended state changes.

## Recommended Mitigation Steps
To mitigate these issues, it would be advisable to add a check at the beginning of the function to ensure that the caller address is not 0. This check would prevent the function from proceeding with an invalid caller address, enhancing the security and reliability of the contract.
