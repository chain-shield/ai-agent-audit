# Vulnerability details

**Summary**:  
An out-of-bounds read vulnerability exists in the `parse_access_list` function, where inadequate validation of RLP (Recursive Length Prefix) encoded data leads to potential memory overreads. A malicious prover could exploit this flaw to manipulate transaction data, undermining system integrity.

**Description**:  
When processing transactions via `eth_send_raw_unsigned_tx`, the transaction data is decoded using `EthTransaction.decode`. Depending on the transaction type, it is further processed by one of the following functions: `decode_legacy_tx`, `decode_2930`, or `decode_1559`. The decoded transaction is represented in the form of an `RLP.Item` structure:

```cairo
struct Item {
    data_len: felt,
    data: felt*,
    is_list: felt,
}
```

It is essential that `data_len` be validated before accessing the `data` field to prevent out-of-bounds memory access. However, in the `parse_access_list` function, this validation is missing, which leads to multiple potential out-of-bounds reads.

The `decode_raw` function that processes RLP data is responsible for ensuring correct decoding, but in some cases, the `data_len` of an `RLP.Item` may be zero, particularly when dealing with lists of zero length:

```cairo
func decode_raw{range_check_ptr}(items: Item*, data_len: felt, data: felt*) -> felt {
    alloc_locals;

    if (data_len == 0) {
        return 0;
    }

    let (rlp_type, offset, len) = decode_type_unsafe(data);
    assert [range_check_ptr] = offset + len;
    local remaining_data_len = data_len - [range_check_ptr];
    assert_nn(remaining_data_len);

    if (rlp_type == TYPE_LIST) {
        let (sub_items: Item*) = alloc();
        let sub_items_len = decode_raw(items=sub_items, data_len=len, data=data + offset);
        assert [items] = Item(sub_items_len, cast(sub_items, felt*), TRUE);
    } else {
        assert [items] = Item(data_len=len, data=data + offset, is_list=FALSE);
    }
    return 1 + sub_items_len;
}
```

This logic can lead to situations where an `RLP.Item` has a `data_len` of zero, particularly when the decoded data consists of just one byte (e.g., `0xc0`, which is interpreted as an empty list). The function `decode_type_unsafe` confirms that such data can result in:

```cairo
(TYPE_LIST, 1, 0)  // Meaning the list is empty, with data_len = 0
```

However, this possibility is not properly handled in the `parse_access_list` function.

The vulnerable code in `parse_access_list` is as follows:

```cairo
func parse_access_list{range_check_ptr}(
    parsed_list: felt*, access_list_len: felt, access_list: RLP.Item*
) -> felt {
    alloc_locals;
    if (access_list_len == 0) {
        return 0;
    }

    // Address
    let address_item = cast(access_list.data, RLP.Item*);
    let address = Helpers.bytes20_to_felt(address_item.data);

    // List<StorageKeys>
    let keys_item = cast(access_list.data + RLP.Item.SIZE, RLP.Item*);
    let keys_len = keys_item.data_len;
    assert [parsed_list] = address;
    assert [parsed_list + 1] = keys_len;

    let keys = cast(keys_item.data, RLP.Item*);
    parse_storage_keys(parsed_list + 2, keys_len, keys);

    let serialized_len = parse_access_list(
        parsed_list + 2 + keys_len * Uint256.SIZE,
        access_list_len - 1,
        access_list + RLP.Item.SIZE,
    );
    return serialized_len + 2 + keys_len * Uint256.SIZE;
}
```

**Multiple Out-of-Bounds Reads**:

1. **`access_list.data` and `address_item`**:  
   The line:
   ```cairo
   let address_item = cast(access_list.data, RLP.Item*);
   ```
   Can result in an out-of-bounds read if `access_list.data_len` is zero. 
   Notice that from the upper level code
   ```cairo
   let access_list_len = parse_access_list(
       access_list, items[7].data_len, cast(items[7].data, RLP.Item*)
   );
   ```
   access_list_len is the access_list.data_len, so the check
   ```
   if (access_list_len == 0) {
       return 0;
   }
   ```
   does not prevent the out-of-bounds situation in our case.

2. **`address_item.data_len` and `bytes20_to_felt`**:  
   If `address_item.data_len` is less than 20 bytes (or zero), the following line will trigger an out-of-bounds read:
   ```cairo
   let address = Helpers.bytes20_to_felt(address_item.data);
   ```

3. **`keys_item` Dereference**:  
   Without validating that `access_list.data_len` is large enough to hold an additional `RLP.Item`, the following line could also cause an out-of-bounds read:
   ```cairo
   let keys_item = cast(access_list.data + RLP.Item.SIZE, RLP.Item*);
   ```

In all these cases, a malicious prover could exploit the out-of-bounds read to falsify the data being read and passed through the system.

**Impact**:  
Exploiting this vulnerability would allow a malicious actor to manipulate transaction data by faking or corrupting access lists. This could lead to unauthorized access to data, inaccurate transaction processing, or even broader system-level vulnerabilities that compromise transaction integrity and state manipulation.

**Recommendation**:  
The `parse_access_list` function should enforce strict checks on `data_len` for both `access_list` and `address_item` before accessing their data. Specifically:
- Validate that `access_list.data_len` is sufficient before casting or dereferencing.
- Ensure that `address_item.data_len` is at least 20 bytes before calling `bytes20_to_felt`.
- Confirm that `access_list.data_len` can accommodate the dereferencing of subsequent items like `keys_item`.
