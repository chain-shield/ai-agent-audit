# Vulnerability details


## Proof of Concept

Take a look at https://github.com/kkrt-labs/kakarot/blob/6496ee1d18380dae5b069c27b3129d82ae282419/cairo_zero/utils/utils.cairo#L238

```cairo
    func try_parse_destination_from_bytes(bytes_len: felt, bytes: felt*) -> model.Option {
        if (bytes_len != 20) {
            with_attr error_message("Bytes has length {bytes_len}, expected 0 or 20") {
                assert bytes_len = 0;
            }
            let res = model.Option(is_some=0, value=0);
            return res;
        }
        let address = bytes20_to_felt(bytes);
        let res = model.Option(is_some=1, value=address);
        return res;
    }
```

This function is used to to parse an EVM address from a byte array.

All usages of this helper function are made during transaction parsing to decode the destination address.

Now the length and data decoded from the RLP-encoded transaction are passed directly to the function,
without checking the data length. The following example is from the `decode_1559` function, with the
other instances of the implementation having a virtually equivalent flaw:

https://github.com/kkrt-labs/kakarot/blob/697100af34444b3931c18596cec56c454caf28ed/src/utils/eth_transaction.cairo#L164-L222

Now whereas the[ `3.19` issue from the Zellic audi](https://github.com/kkrt-labs/kakarot/blob/main/audits/cairo_zero/Kakarot%20EVM%20-%20Zellic%20Audit%20Report.pdf)t has been fixed with this `PR`, i.e now the function does not immediately return zero if the length of the address is not `20`, the fix introduced a new issue where valid transactions would now fail.

Problem with the current implementation however is that it would always fail for valid transactions like contract deployment transactions, this is because contract creation transactions are to non addresses and in such cases we should have the `bytes_len == 0`, this can also be seen to be the intended implementation from the protocol as hinted in the documented [error message that returns](https://github.com/kkrt-labs/kakarot/blob/6496ee1d18380dae5b069c27b3129d82ae282419/cairo_zero/utils/utils.cairo#L240), i.e `"Bytes has length {bytes_len}, expected 0 or 20"`, but instead we enforce it to only be `20`

## Impact

The [check ](https://github.com/kkrt-labs/kakarot/blob/6496ee1d18380dae5b069c27b3129d82ae282419/cairo_zero/utils/utils.cairo#L240) for `"Bytes has length {bytes_len}, expected 0 or 20"` is wrong and instead only enforces that the tx address length is `20` which causes for valid txs to no addresses or addresses of `0` length to always fail.

## Recommended Mitigation Steps

Change the check [here ](https://github.com/kkrt-labs/kakarot/blob/6496ee1d18380dae5b069c27b3129d82ae282419/cairo_zero/utils/utils.cairo#L240) to instead see if the length is `0` or `20` and not just `20`.
