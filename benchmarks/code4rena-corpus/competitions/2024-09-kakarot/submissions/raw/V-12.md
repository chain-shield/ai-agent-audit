# Vulnerability details

## Description
While reviewing the `exec_returndatacopy` function in `environmental_information.cairo`, I discovered an implementation bug reminiscent of an issue stressed in Zellic's previous audit. Specifically, the function incorrectly skips memory writes when the `returndata_offset` is greater than or equal to $2^{128}$

Let's look at the `exec_returndatacopy` function:
```cairo
func exec_returndatacopy{...}(evm: model.EVM*) -> model.EVM* {
    alloc_locals;

    let (popped) = Stack.pop_n(3);
    let memory_offset = popped[0];
    let returndata_offset = popped[1];
    let size = popped[2];

    // ...SNIP [Gas calculations and memory expansion] ...

    tempvar memory = new model.Memory(
        word_dict_start=memory.word_dict_start,
        word_dict=memory.word_dict,
        words_len=memory_expansion.new_words_len,
    );

 
    let (sliced_data: felt*) = alloc();
    if (returndata_offset.high != 0) {
        // We still check for OOB returndatacopy
        let (max_index, carry) = uint256_add(returndata_offset, size);
        let (high, low) = split_felt(evm.return_data_len);
        let (is_in_bounds) = uint256_le(max_index, Uint256(low=low, high=high));
        let is_in_bounds = is_in_bounds * (1 - carry);
        if (is_in_bounds == FALSE) {
            let (revert_reason_len, revert_reason) = Errors.outOfBoundsRead();
            let evm = EVM.stop(evm, revert_reason_len, revert_reason, Errors.EXCEPTIONAL_HALT);
            return evm;
        }
        return evm;
    }
```
The highlighted early return `return evm;` occurs when `returndata_offset.high != 0`. In this case, if the offset is greater than or equal to $2^{128}$, the function exits without performing any memory writes to the destination offset.

However, according to the [EVM specification](https://ethereum.github.io/yellowpaper/paper.pdf), when the source offset in `RETURNDATACOPY` is beyond the end of the return data, zeros should be written to the destination in memory. By skipping the memory write, the function deviates from the expected behavior, potentially leaving old or uninitialized data in memory where zeros should be.

This is similar to the issue found in the previous Zellic audit report, which stated:
> [Incorrectly Skipped Memory Writes in CALLDATACOPY, CODECOPY, and EXTCODECOPY](https://github.com/kkrt-labs/kakarot/blob/697100af34444b3931c18596cec56c454caf28ed/audits/Kakarot%20EVM%20-%20Zellic%20Audit%20Report.pdf)

In the current codebase, the same kind of issue exists in the `exec_returndatacopy` function. When the `returndata_offset` has a high part not equal to zero, indicating a large offset, the function should write zeros to the memory region starting at memory_offset and spanning size bytes, but it does not.


## Impact
Incorrectly skipping memory writes can lead to unexpected behavior in smart contracts that rely on `RETURNDATACOPY`. This could potentially be exploited in specific scenarios, resulting in vulnerabilities in contract execution where memory contents are assumed to be zeros but actually contain old data.

## Recommendations
To resolve this issue, the incorrect early return should be removed, and the function should ensure that zeros are written to the destination memory when the source offset is out of bounds.
```cairo
if (returndata_offset.high != 0) {
    // We still check for OOB returndatacopy
    let (max_index, carry) = uint256_add(returndata_offset, size);
    let (high, low) = split_felt(evm.return_data_len);
    let (is_in_bounds) = uint256_le(max_index, Uint256(low=low, high=high));
    let is_in_bounds = is_in_bounds * (1 - carry);
    if (is_in_bounds == FALSE) {
        let (revert_reason_len, revert_reason) = Errors.outOfBoundsRead();
        let evm = EVM.stop(evm, revert_reason_len, revert_reason, Errors.EXCEPTIONAL_HALT);
        return evm;
    }
    // Write zeros to memory
    memset(dst=sliced_data, value=0, n=size.low);
    Memory.store_n(size.low, sliced_data, memory_offset.low);
    return evm;
}
```
By adding the `memset` and `Memory.store_n` calls, we ensure that zeros are written to the destination memory region, conforming to the EVM specification.
