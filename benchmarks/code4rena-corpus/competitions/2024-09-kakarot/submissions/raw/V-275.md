# Vulnerability details

## Description
In the `L1KakarotMessaging` contract, all messages that are sent to the L2 will include a sender address. Due to [the security concerns](https://docs.optimism.io/chain/differences#address-aliasing), an address aliasing is applied to the sender addresses. This can be seen in the `sendMessageToL2` [function](https://github.com/kkrt-labs/kakarot/blob/7411a5520e8a00be6f5243a50c160e66ad285563/solidity_contracts/src/L1L2Messaging/L1KakarotMessaging.sol#L35):

```Solidity
 function sendMessageToL2(address to, uint248 value, bytes calldata data) external payable {
        uint256 totalLength = data.length + 4;
        uint256[] memory convertedData = new uint256[](totalLength);
        convertedData[0] = uint256(uint160(AddressAliasHelper.applyL1ToL2Alias(msg.sender)));
```

The `applyL1ToL2Alias` function basically adds a certain offset to the sender's address. If the receiving contract wants to get back the original address this address can be un-aliased by subtracting the offset. This can be seen in the `AddressAliasHelper` [contract](https://github.com/kkrt-labs/kakarot/blob/7411a5520e8a00be6f5243a50c160e66ad285563/solidity_contracts/src/L1L2Messaging/AddressAliasHelper.sol#L30):

```Solidity
    function applyL1ToL2Alias(address l1Address) internal pure returns (address l2Address) {
        unchecked {
            l2Address = address(uint160(l1Address) + offset);
        }
    }
```

The problem is this aliased address is directly used by the Kakarot as the sender's address in the Kakarot. In the L1 -> L2 messages, `l1_sender` is an [aliased address](https://github.com/kkrt-labs/kakarot/blob/7411a5520e8a00be6f5243a50c160e66ad285563/src/kakarot/kakarot.cairo#L380):
```
let (_, state, _, _) = Kakarot.handle_l1_message(l1_sender, to_address, value, data_len, data);
```

This means that if a user wants to send an L1 -> L2 message to Kakarot, they will never be able to use their own address. The sender balance will always be zero because the aliased address will not have any balance. If the L1 -> L2 message contains a value, this will be deducted from the L1 aliased address on L2. However, this aliased address is not an actual account on L2. It will never actually hold a balance on L2 unless the user specifically sends native tokens to the aliased address on L2. For this reason, any transaction that sends value will revert on Starknet.    



## Recommended Mitigation Steps

Only alias addresses that originate from smart contracts. In fact that's how it's done in [the Optimism as well](https://docs.optimism.io/chain/differences#address-aliasing):
```
When transactions are sent from L1 to L2 by an Externally Owned Account, the address of the sender of the transaction on L2 will be set to the address of the sender of the transaction on L1. However, the address of the sender of a transaction on L2 will be different if the transaction was triggered by a smart contract on L1.
```
