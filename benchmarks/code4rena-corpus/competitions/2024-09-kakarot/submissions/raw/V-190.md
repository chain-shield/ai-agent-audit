# Vulnerability details


## Proof of Concept

Take a look at https://github.com/kkrt-labs/kakarot/blob/697100af34444b3931c18596cec56c454caf28ed/src/utils/eth_transaction.cairo#L164-L222

```cairo

        tx_data_len: felt, tx_data: felt*
    ) -> model.EthTransaction* {
        alloc_locals;

        let (tx_items: RLP.Item*) = alloc();
        RLP.decode(tx_items, tx_data_len - 1, tx_data + 1);

        assert [tx_items].is_list = TRUE;
        let items_len = [tx_items].data_len;
        let items = cast([tx_items].data, RLP.Item*);

        assert items_len = 9;
        assert items[0].is_list = FALSE;
        assert items[1].is_list = FALSE;
        assert items[2].is_list = FALSE;
        assert items[3].is_list = FALSE;

        assert_nn(31 - items[2].data_len);
        let max_priority_fee_per_gas = Helpers.bytes_to_felt(items[2].data_len, items[2].data);
        assert_nn(31 - items[3].data_len);

```

This function is used to decode an Ethereum transaction with fee market, and as the name of the function shows and also as [has been documented](https://github.com/kkrt-labs/kakarot/blob/697100af34444b3931c18596cec56c454caf28ed/src/utils/eth_transaction.cairo#L159-L163), this implementation is done to support [EIP-1559](https://github.com/ethereum/EIPs/blob/master/EIPS/eip-1559.md).

Issue however is that this function would always fail when decoding the tx with fee market, since [we enforce that the items length to be decoded must be `9`](https://github.com/kkrt-labs/kakarot/blob/697100af34444b3931c18596cec56c454caf28ed/src/utils/eth_transaction.cairo#L176) whereas [the EIP has them to be `11` instead](https://github.com/ethereum/EIPs/blob/master/EIPS/eip-1559.md#abstract):

> `rlp([chain_id, nonce, max_priority_fee_per_gas, max_fee_per_gas, gas_limit, destination, amount, data, access_list, signature_y_parity, signature_r, signature_s])`.

To showcase how this is wrong we can go to the sister implementation of `decode_legacy_tx()` that's to work in accordance with EIP-155 we can see how different correct implementations have been make for the amount of fields in the tx, i.e how Pre eip-155 txs have 6 fields and post eip-155 txs have 9 fields, as such the assertions being made for the amount of items in the field is with the correct value, i.e 9 if it's post the eip or assured to be 6 if it's pre the EIP see https://github.com/kkrt-labs/kakarot/blob/697100af34444b3931c18596cec56c454caf28ed/src/utils/eth_transaction.cairo#L64-L76.

## Impact

Ethereum transactions with fee markets can never be decoded.

## Recommended Mitigation Steps

Correct the assertion to reflect the amount of items in the field.
