# Vulnerability details

Proof of Concept
Exploit Description:
The add_transfer function in the contract modifies account balances after making external calls. This exposes the function to reentrancy attacks, where an attacker could exploit the external call mechanism to recursively call the add_transfer function before the state is updated. This could lead to unauthorized balance transfers or manipulations, allowing an attacker to drain funds or alter the contract state unexpectedly.

https://github.com/kkrt-labs/kakarot/blob/7411a5520e8a00be6f5243a50c160e66ad285563/src/kakarot/state.cairo#L361C1-L409C6

Hypothetical Attack Scenario: In this scenario, an attacker could create a malicious contract that calls add_transfer with a transfer.amount that exceeds the current balance. The malicious contract can then re-enter the add_transfer function before the state has been updated, allowing it to manipulate balances as follows:

// Malicious transfer call by the attacker
let malicious_transfer = Transfer(sender=attacker.evm, recipient=attacker.evm, amount=large_amount);
let result = add_transfer(malicious_transfer);

Result: The attacker can invoke the add_transfer function repeatedly before the balances are updated, leading to unauthorized transfers from their account or potentially draining funds from the contract.

Recommended Mitigation Steps
To address the identified reentrancy vulnerability in the add_transfer function, the following measures are recommended:

State Update Before External Calls:

Always update the state (i.e., balances) before making any external calls. This practice ensures that the contract's state is consistent and reduces the risk of reentrancy.

// Update balances before any external calls
let (local sender_balance_new) = uint256_sub([sender.balance], transfer.amount);
let (local recipient_balance_new, carry) = uint256_add([recipient.balance], transfer.amount);

let sender = Account.set_balance(sender, &sender_balance_new);
let recipient = Account.set_balance(recipient, &recipient_balance_new);

// Commit the new balances to state
dict_write{dict_ptr=accounts}(key=transfer.sender.evm, new_value=cast(sender, felt));
dict_write{dict_ptr=accounts}(key=transfer.recipient.evm, new_value=cast(recipient, felt));
Implement a Reentrancy Guard:

Introduce a reentrancy guard mechanism that prevents recursive calls to the add_transfer function. A simple boolean flag can indicate whether the function is currently executing.

let mut reentrancy_guard: felt = 0;  // Reentrancy guard variable

func add_transfer(...) {
    assert reentrancy_guard == 0;  // Check for reentrancy
    reentrancy_guard = 1;          // Set guard

    // Function logic...
    // Update state as needed

    reentrancy_guard = 0;          // Reset guard at the end
}
Thorough Testing and Auditing:

Conduct extensive testing, including unit tests and fuzz testing, to ensure that the implementation of these mitigation measures effectively prevents reentrancy attacks. Consider employing external audits to validate the security of the contract.
Monitoring for Unusual Activity:

Implement monitoring mechanisms to track unusual patterns of contract interaction. Alert systems can be established to detect potential reentrancy attack attempts, allowing for quick intervention.
User Education and Documentation:

Provide clear documentation and guidance on safe contract interaction practices to users and developers interfacing with the contract. This can help mitigate risks associated with unintentional misuse of the contract's functions.
