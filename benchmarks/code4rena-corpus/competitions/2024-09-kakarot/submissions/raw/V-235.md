# Vulnerability details

## Background: The StarkNet Block Reorganization

On April 4, 2024, StarkNet experienced a significant block reorganization incident due to a rounding error bug. This event led to transaction backlog and disruption in block production, highlighting vulnerabilities in cross-layer messaging systems. The incident demonstrated that applications leveraging StarkNet's cross-layer messaging must be designed with robust reorg protection mechanisms.

## Description

The CairoLib library implementation contains critical vulnerability in its cross-layer messaging and state management functions (`sendMessageToL1` and `callCairo`). The vulnerability becomes particularly acute during StarkNet block reorganization events, where messages could be duplicated or processed out of order while network state is being reorganized.


## Code Snippet

```solidity
library CairoLib {
    address constant CAIRO_PRECOMPILE_ADDRESS = 0x0000000000000000000000000000000000075001;
    address constant CAIRO_MESSAGING_ADDRESS = 0x0000000000000000000000000000000000075002;

    function sendMessageToL1(bytes memory payload) internal {
        // No protection against reorgs or message duplication
        (bool success,) = CAIRO_MESSAGING_ADDRESS.call(payload);
        require(success, "CairoLib: sendMessageToL1 failed");
    }

    function callCairo(uint256 contractAddress, uint256 functionSelector, uint256[] memory data)
        internal
        returns (bytes memory)
    {
        bytes memory callData =
            abi.encodeWithSignature("call_contract(uint256,uint256,uint256[])", 
                contractAddress, 
                functionSelector, 
                data
            );

        // No state consistency checks during reorgs
        (bool success, bytes memory result) = CAIRO_PRECOMPILE_ADDRESS.call(callData);
        require(success, string(abi.encodePacked("CairoLib: call_contract failed with: ", result)));

        return result;
    }
}
```


## Impact

1. Message Duplication:
- During a reorg, messages sent via `sendMessageToL1` could be duplicated
- Asset bridges could process the same transfer multiple times
- Governance actions could be executed repeatedly

2. State Inconsistency:
- L2 state changes via `callCairo` could be rolled back while L1 messages persist
- Critical L1-L2 operations might be partially executed

3. Message Order Violation:
- Related messages could arrive out of order on L1
- Sequential operations could be processed in incorrect order


## Fix

Implement message sequencing and block verification:

```solidity
contract SecureCairoLib {
    uint256 private messageNonce;
    mapping(uint256 => bool) private processedMessages;
    uint256 private lastProcessedBlock;

    struct MessageContext {
        uint256 nonce;
        uint256 blockNumber;
        uint256 timestamp;
    }

    function sendMessageToL1Secure(bytes memory payload) internal {
        // Create message context
        MessageContext memory context = MessageContext({
            nonce: messageNonce++,
            blockNumber: block.number,
            timestamp: block.timestamp
        });

        // Create and verify message hash
        bytes32 messageHash = keccak256(abi.encode(context, payload));
        require(!processedMessages[messageHash], "Message already processed");

        // Verify block sequence
        require(block.number > lastProcessedBlock, "Invalid block sequence");

        // Mark message as processed
        processedMessages[messageHash] = true;
        lastProcessedBlock = block.number;

        // Send message with context
        bytes memory securePayload = abi.encode(context, payload);
        sendMessageToL1(securePayload);
    }
}
```

## Test

```solidity
contract CairoLibTest {
    using CairoLib for *;
    
    function testReorgVulnerability() public {
        // Setup
        uint256 amount = 100;
        address user = address(0x1);
        
        // Initial bridge operation
        vm.prank(user);
        bridgeAssets(amount);
        
        // Record messages sent to L1
        bytes32 messageHash1 = getLastMessageHash();
        
        // Simulate reorg
        vm.roll(block.number - 1);
        
        // Retry operation
        vm.prank(user);
        bridgeAssets(amount);
        bytes32 messageHash2 = getLastMessageHash();
        
        // Assert different message hashes for same operation
        assertTrue(messageHash1 != messageHash2, 
                  "Duplicate messages detected");
    }
}
```

## Recommended Actions

1. Immediate:
- Add message sequencing using block numbers and nonces
- Implement message deduplication
- Add block sequence verification
- Track processed messages

2. Long-term:
- Implement message expiration mechanism
- Add circuit breaker for reorg detection
