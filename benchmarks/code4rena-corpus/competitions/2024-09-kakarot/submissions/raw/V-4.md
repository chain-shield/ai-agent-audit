# Vulnerability details

#### Overview
The vulnerability is caused by a logic error in the function `initialize_jumpdests`, which handles jump destination initialization by processing the bytecode array. This logic flaw can be exploited by a malicious prover to trigger oob access to the provided bytecode array, leading to unconstrained memory content being used.

#### Description
The function `initialize_jumpdests` uses a loop to iterate over the bytecode array and identify valid jump destinations based on the opcode values. The loop control is implemented using a temporary variable `continue_loop`, which is updated based on an intermediate value `a`. The following snippet highlights the logic used for loop control:

```cairo
%{ memory[ap] = 0 if 0 <= (ids.a % PRIME) < range_check_builtin.bound else 1 %}
```

A malicious prover could bypass the intended checks by manipulating the value written to `memory[ap]` directly to `1`, causing the loop to continue indefinitely or access unintended memory locations. This manipulation could result in the loop index `i` becoming much larger than `bytecode_len`, leading to an OOB access when `opcode` is fetched:

```cairo
tempvar opcode = [bytecode + i];
```

Although the function attempts to validate the index `i` using the following statement:

```cairo
let check = Helpers.is_le_unchecked(bytecode_len, i);
assert check = 1;
```

The check currently uses an incorrect assertion logic. It ensures that `bytecode_len` is less than or equal to `i`, rather than verifying that `i` is less than or equal to `bytecode_len`. As a result, the assertion does not effectively protect against OOB access.

#### Impact
This vulnerability allows a malicious prover to read memory beyond the bounds of the `bytecode` array. An out-of-bounds read is not constrained, which means the malicious prover could manipulate and fake the content of the `opcode` array.

#### Recommendation Fix
To address this issue, the assertion logic at the end of the function should be modified to correctly validate the index `i`. Specifically, the statement:

```cairo
let check = Helpers.is_le_unchecked(bytecode_len, i);
```

should be updated to:

```cairo
let check = Helpers.is_le_unchecked(i, bytecode_len);
```

This change will ensure that the index `i` is always less than or equal to `bytecode_len`, thereby preventing out-of-bounds access to the `bytecode` array.
