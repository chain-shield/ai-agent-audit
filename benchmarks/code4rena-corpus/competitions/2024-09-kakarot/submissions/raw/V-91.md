# Vulnerability details

The `execute()` function in `interpreter.cairo` subtracts the maximum gas fee from the caller's balance without checking whether the caller's balance is sufficient. As explained in the developer comments, the balance check is omitted because `balance > effective_fee ` has already been verified in `eth_send_raw_unsigned_tx()`. There is however another entry point, `handle_l1_message()`, that doesn't have the check. As a consequence, the subtraction will underflow if the sender of the l1 message has insufficient funds to cover `max_fee`.

This will leave the caller account with an inflated balance for the entire transaction. Calls to the `balance` or `selfbalance` opcodes will return the inflated balance. The transaction will be valid as long as the sender does not transfer more than their real balance - otherwise, the transfer of the underlying Starknet token will fail and the Starknet transaction (message from L1) will revert. The impact of this issue is therefore limited to spoofing the account balance, impacting any logic that depends on balance checks.

Also, note that the caller account needs to have enough actual funds (in underlying Starknet tokens) to cover the final gas fees.

## Proof of Concept

The following test demonstrates the issue.

```
class TestL1Handler:
    @SyscallHandler.patch("IERC20.balanceOf", lambda addr, data: [0, 1])
    def test_balance_underflow_in_l1_handler(self, cairo_run):
        res = cairo_run(
            "test__handle_l1_message",
            from_address=0xABC,
            l1_sender=0xABC,
            to_address=0xABC,
            value=0xABC,
            data=[],
        )

        assert int(res['accounts']['0x0000000000000000000000000000000000000aBc']['balance'], 16) == 0xffffffffffffffffffffffffffffadf8
```

## Recommended Mitigation Steps

In `handle_l1_message()`, verify that the sender balance is sufficient to cover `msg.value` + `max_gas`.
