# Vulnerability details

## Summary

The [verify_eth_signature_uint256](https://github.com/kkrt-labs/kakarot/blob/697100af34444b3931c18596cec56c454caf28ed/src/utils/signature.cairo#L13-L35) function in Kakarot zkEVM’s signature implementation lacks enforcement of the lower s value limit in ECDSA signature verification, which can lead to signature malleability.

## Issue Details

### Background

In Ethereum, ECDSA signatures are used to authenticate transactions and messages. A signature consists of three components:

- **`r`**: The x-coordinate of a point on the elliptic curve.
- **`s`**: A scalar value derived during the signing process.
- **`v`**: The recovery identifier, indicating the y-parity of the public key.

For security reasons, and to prevent signature malleability, Ethereum enforces that the s component must satisfy:

$$
0 < s < \frac{secp256k1n}{2} + 1
$$

where secp256k1n is the order of the secp256k1 curve.


### Current Implementation

The `verify_eth_signature_uint256` function in the Kakarot zkEVM implementation is responsible for verifying Ethereum ECDSA signatures. Below is the relevant code:

```cairo
%lang starknet

from starkware.cairo.common.cairo_builtins import BitwiseBuiltin
from starkware.cairo.common.cairo_secp.bigint3 import BigInt3
from starkware.cairo.common.cairo_secp.signature import validate_signature_entry
from starkware.cairo.common.uint256 import Uint256
from kakarot.interfaces.interfaces import ICairo1Helpers
from starkware.cairo.common.cairo_secp.bigint import uint256_to_bigint

namespace Signature {
    // A version of verify_eth_signature, with msg_hash, r, and s as Uint256
    // and using the Cairo1 helpers class.
    func verify_eth_signature_uint256{
        syscall_ptr: felt*, range_check_ptr, bitwise_ptr: BitwiseBuiltin*
    }(
        msg_hash: Uint256,
        r: Uint256,
        s: Uint256,
        v: felt,
        eth_address: felt,
        helpers_class: felt
    ) {
        alloc_locals;
        let (msg_hash_bigint: BigInt3) = uint256_to_bigint(msg_hash);
        let (r_bigint: BigInt3) = uint256_to_bigint(r);
        let (s_bigint: BigInt3) = uint256_to_bigint(s);

        with_attr error_message("Signature out of range.") {
            validate_signature_entry(r_bigint);
            validate_signature_entry(s_bigint);
        }

        with_attr error_message("Invalid signature.") {
            let (success, recovered_address) = ICairo1Helpers.library_call_recover_eth_address(
                class_hash=helpers_class,
                msg_hash=msg_hash,
                r=r,
                s=s,
                y_parity=v
            );
            assert success = 1;
            assert eth_address = recovered_address;
        }
        return ();
    }
}
```

In this function:

- The signature components `r` and `s` are converted to `BigInt3` representations.
- The `validate_signature_entry` function is called on both `r_bigint` and `s_bigint` to ensure they are within valid ranges.


The `validate_signature_entry` function is intended to verify that a given value is within the valid range for ECDSA signature components.

```cairo
// Verifies that val is in the range [1, N) and that the limbs of val are in the range [0, BASE).
func validate_signature_entry{range_check_ptr}(val: BigInt3) {
    assert_nn_le(val.d2, N2);
    assert_nn_le(val.d1, BASE - 1);
    assert_nn_le(val.d0, BASE - 1);

    if (val.d2 == N2) {
        if (val.d1 == N1) {
            assert_nn_le(val.d0, N0 - 1);
            return ();
        }
        assert_nn_le(val.d1, N1 - 1);
        return ();
    }

    // Check that val > 0.
    if (val.d2 == 0) {
        if (val.d1 == 0) {
            assert_not_zero(val.d0);
            return ();
        }
    }
    return ();
}
```

In this function:

- It verifies that `val` is greater than zero and less than `N`, the order of the secp256k1 curve.
- It ensures that each limb of `val` is within the appropriate range.

The issue here is that, the function does not enforce that
 
$$
s \leq \frac{n}{2}
$$

which is required to prevent signature malleability.



### Impact

One of the most immediate risks associated with signature malleability attacks is the potential for transaction replays and double-spending.

Attackers can generate alternative signatures that remain valid but differ from the original signature. Such occurrences can result in discrepancies in transaction verification, potentially undermining the security of the blockchain network.

## Recommendations

To address the issue, validate that the s value to enforce 
$$
0 < s < \frac{secp256k1n}{2} + 1
$$
