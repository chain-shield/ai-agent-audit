# Vulnerability details

## Summary
The Kakarot contracts exhibit an inconsistency in how they calculate the `chain_id`. While most of the code uses the `unsigned_div_rem` function to limit the `chain_id` to 53 bits, ensuring compatibility with systems like JavaScript, the `eth_transaction.cairo` contract's decoding functions (`decode_legacy_tx`, `decode_2930`, and `decode_1559`) rely on `bytes_to_felt`, which does not enforce this limit. This discrepancy can lead to several problems, including potential security risks from chain ID mismatches, possible overflow issues, repay attacks, and integration difficulties with external systems expecting a uniform format.

## Proof of Concept 
In Kakarot's smart contract library, there is a discrepancy in how the `chain_id` is calculated across different modules. Most contracts, including audit contracts, use the `unsigned_div_rem` function to compute `chain_id`, which limits it to a value within 53 bits. This limitation is intentional as it aligns with the maximum safe integer range supported by JavaScript and other systems, ensuring interoperability. The value `2^53` (9007199254740992) is the largest safe integer that JavaScript can handle without precision issues.

// @dev Inlined version of unsigned_div_rem
// Returns q and r such that:
//  0 <= q < rc_bound, 0 <= r < div and value = q * div + r.
//
// Assumption: 0 < div <= PRIME / rc_bound.
// Prover assumption: value / div < rc_bound.
//
// The value of div is restricted to make sure there is no overflow.
// q * div + r < (q + 1) * div <= rc_bound * (PRIME / rc_bound) = PRIME.
func unsigned_div_rem{range_check_ptr}(value, div) -> (q: felt, r: felt) {
    let r = [range_check_ptr];
    let q = [range_check_ptr + 1];
    let range_check_ptr = range_check_ptr + 2;
    %{
        from starkware.cairo.common.math_utils import assert_integer
        assert_integer(ids.div)
        assert 0 < ids.div <= PRIME // range_check_builtin.bound, \
            f'div={hex(ids.div)} is out of the valid range.'
        ids.q, ids.r = divmod(ids.value, ids.div)
    %}

    // equivalent to assert_le(r, div - 1);
    tempvar a = div - 1 - r;
    %{
        from starkware.cairo.common.math_utils import assert_integer
        assert_integer(ids.a)
        assert 0 <= ids.a % PRIME < range_check_builtin.bound, f'a = {ids.a} is out of range.'
    %}
    a = [range_check_ptr];
    let range_check_ptr = range_check_ptr + 1;

    assert value = q * div + r;
    return (q, r);
}

**Issues:**
1. **Inconsistency**: The use of two different methods to calculate `chain_id` can lead to inconsistent behavior across the system.
2. **Potential Overflow**: The `bytes_to_felt` function does not limit the result's size, while `unsigned_div_rem` restricts it to 53 bits. This mismatch may cause overflows in certain operations or mismatches in expected values.
3. **Compatibility Concerns**: External systems interacting with Kakarot may expect a consistent format for `chain_id`, and this discrepancy could cause integration issues.
4. **Security Risks**: Inconsistent `chain_id` calculations might open vulnerabilities, such as replay attacks, where a transaction valid on one network could be maliciously executed on another.

## Recommended Mitigation Steps
To address these issues, it is recommended to standardize the `chain_id` calculation across the entire codebase. The preferred approach should align with Ethereum's standard practices and ensure compatibility across all modules, particularly in handling replay protection and interactions with external systems. This will also reduce the risk of potential security vulnerabilities stemming from inconsistent `chain_id` interpretations.
