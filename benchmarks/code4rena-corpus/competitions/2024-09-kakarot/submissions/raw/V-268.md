# Vulnerability details

## Proof of Concept
Throughout the codebase, kakarot deals with uint128 values as offset, but geth deals with uint64 values.

For example, in exec_calldatasize opcode, if the value > uint64, [kakarot](https://github.com/kkrt-labs/kakarot/blob/7411a5520e8a00be6f5243a50c160e66ad285563/src/kakarot/instructions/environmental_information.cairo#L152) pushes it as is, but [geth](https://github.com/ethereum/go-ethereum/blob/master/core/vm/instructions.go#L291-L293) wraps it down to a uint64 field

This could lead to different execution of same transaction on kakarot and evm.

Other instances are:

- [exec_calldataload](https://github.com/kkrt-labs/kakarot/blob/7411a5520e8a00be6f5243a50c160e66ad285563/src/kakarot/instructions/environmental_information.cairo#L136) pushes 0 if offset >2^128, whereas [geth](https://github.com/ethereum/go-ethereum/blob/master/core/vm/instructions.go#L286-L287) pushes 0 if offset > 2^64

## Recommended Mitigation Steps
Use uint64 typed values where appropriate according to geth implementation
