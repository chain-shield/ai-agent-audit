# Vulnerability details

Vulnerability Details:
The execute_starknet_call() and eth_send_transaction() functions involve external calls, which could introduce reentrancy risks. If the to parameter in these functions references a contract that re-enters the calling function, it could exploit reentrancy vulnerabilities by manipulating the contract’s state or draining funds.
Code References:
execute_starknet_call()
eth_send_transaction()
The potential reentrancy risk arises from the fact that both functions interact with external contracts without reentrancy protection mechanisms in place, leaving them vulnerable to recursive calls that could occur before state changes are finalized.

Proof of Concept:
Reentrancy in eth_send_transaction():
The eth_send_transaction() function sends a transaction to an external contract via the to parameter.
If the target contract calls back into eth_send_transaction() (or any vulnerable state-modifying function), it could cause state to be manipulated before it’s properly updated.

Reentrancy in execute_starknet_call():
Similarly, the execute_starknet_call() function could allow for reentrancy if the external call to to references a contract that recursively calls back into execute_starknet_call() or other state-dependent functions.

Attack Scenario:
An attacker creates a malicious contract that re-enters the vulnerable functions before critical state changes occur (such as transferring funds or updating balances).
By leveraging this reentrancy, the attacker can repeatedly withdraw or manipulate the contract state, leading to loss of funds or other unintended behavior.

Impact:
Fund Draining: Reentrancy could allow an attacker to drain funds from the contract by repeatedly re-entering the function before state changes are finalized.
State Manipulation: Critical contract state variables could be modified in unintended ways by recursive reentrant calls, causing logic flaws or incorrect contract behavior.

Recommended Mitigation Steps:
Implement Reentrancy Guards:
Use a reentrancy guard mechanism (e.g., a mutex or flag) to prevent recursive function calls during sensitive operations. For example:
if reentrancy_guard != 0:
    revert('Reentrancy detected');
reentrancy_guard = 1;

// Execute sensitive logic

reentrancy_guard = 0;

Avoid External Calls After State Changes:
Ensure that any external calls to untrusted contracts are made after critical state changes are finalized. This limits the impact of reentrant calls by ensuring the contract state is already in a consistent state.

Thorough Testing:
Test the functions in various scenarios, including recursive calls and reentrancy attacks, to ensure the proper functioning of the reentrancy guard and contract state management.
