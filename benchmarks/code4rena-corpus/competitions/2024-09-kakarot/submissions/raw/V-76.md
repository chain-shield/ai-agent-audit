# Vulnerability details

## Summary
The `DualVmToken.sol` contract features four `allowance` functions to get token authorization between Ethereum and Starknet addresses. However, its two `approve` functions only emit `Approval` events for specific cases, leaving out scenarios where Starknet addresses authorize spending for either Ethereum or Starknet addresses. This oversight can lead to unreliable interactions with external systems, complicating monitoring for users and developers. To enhance transparency and reliability, it's recommended to introduce `Approval` events for all authorization scenarios involving Starknet addresses.

## Proof of Concept
The four `allowance` functions in the `DualVmToken.sol` contract are mainly used to handle authorization queries between different types of addresses (Ethereum addresses and Starknet addresses). These four `allowance` functions cover four different authorization scenarios: 
1. Querying the token amount authorized by an Ethereum address owner to an Ethereum address spender,
2. Querying the token amount authorized by an Ethereum address owner to a Starknet address spender,
3. Querying the token amount authorized by a Starknet address owner to an Ethereum address spender, 
4. Querying the token amount authorized by a Starknet address owner to a Starknet address spender.

Similarly, the two `approve` functions in the `DualVmToken.sol` contract are primarily designed to allow token holders to authorize other addresses (whether Ethereum or Starknet addresses) to spend a certain amount of tokens. These two `approve` functions should also handle the four types of authorizations:
1. Ethereum address authorizing an Ethereum address,
2. Ethereum address authorizing a Starknet address,
3. Starknet address authorizing an Ethereum address, 
4. Starknet address authorizing a Starknet address.

```solidity
    /// @dev Approve an evm account spender for a specific amount
    function approve(address spender, uint256 amount) external returns (bool) {
        uint256[] memory spenderAddressCalldata = new uint256[](1);
        spenderAddressCalldata[0] = uint256(uint160(spender));
        uint256 spenderStarknetAddress =
            abi.decode(kakarot.staticcallCairo("get_starknet_address", spenderAddressCalldata), (uint256));

        _approve(spenderStarknetAddress, amount);

        emit Approval(msg.sender, spender, amount);
        return true;
    }

    /// @dev Approve a starknet address for a specific amount
    /// @param spender The starknet address to approve
    /// @param amount The amount of tokens to approve
    /// @return True if the approval was successful
    function approve(uint256 spender, uint256 amount) external returns (bool) {
        _approve(spender, amount);
        emit Approval(msg.sender, spender, amount);
        return true;
    }

```


However, the issue is that there are only two types of `Approval` events: 
1. Ethereum address authorizing an Ethereum address, 
2. Ethereum address authorizing a Starknet address.

[kakarot/solidity_contracts/src/CairoPrecompiles/DualVmToken.sol:Approval-L44-48](https://github.com/kkrt-labs/kakarot/blob/7411a5520e8a00be6f5243a50c160e66ad285563/solidity_contracts/src/CairoPrecompiles/DualVmToken.sol#L44C1-L48C84)
```solidity

    /// @dev Emitted when the allowance of a spender over the owner's tokens is set
    event Approval(address indexed owner, address indexed spender, uint256 amount);

    /// @dev Emitted when the allowance of a starknet address spender over the owner's tokens is set
    event Approval(address indexed owner, uint256 indexed spender, uint256 amount);

```

This means that when a Starknet address authorizes either an Ethereum address or another Starknet address, the corresponding `Approval` event is not emitted. This is a critical mechanism for interacting with frontend interfaces, wallets, and other smart contracts. If the events are not emitted, external systems will be unable to track changes in approvals, making interactions with the contract unreliable. This lack of visibility could lead to confusion and increased risk for users and developers, as they won’t be able to properly monitor on-chain operations.

## Recommended Mitigation Steps
Add corresponding `Approval` events for cases where a Starknet address authorizes an Ethereum address or another Starknet address to ensure that all authorization changes are properly tracked.
