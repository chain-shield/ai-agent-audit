# Vulnerability details

## Proof of Concept

Currently the protocol does not follow EIP-3651 that introduced warm coinbase payments:

https://github.com/ethereum/EIPs/blob/master/EIPS/eip-3651.md

Take a look at the `interpreter` functionality:

https://github.com/kkrt-labs/kakarot/blob/7411a5520e8a00be6f5243a50c160e66ad285563/src/kakarot/interpreter.cairo#L916
```
 let coinbase = State.get_account(env.coinbase);
```

First, we derive `coinbase` from the `State`. And then create a payment to this address:

https://github.com/kkrt-labs/kakarot/blob/7411a5520e8a00be6f5243a50c160e66ad285563/src/kakarot/interpreter.cairo#L1032-1037
```
  let transfer = model.Transfer(sender.address, coinbase.address, actual_fee_u256);

        with state {
            State.add_transfer(transfer);
            State.finalize();
        }
```

However, according to the EIP-3651, it has to be done like that:

```
At the start of transaction execution, accessed_addresses shall be initialized to also include the address returned by COINBASE (0x41).
```

However, there is no such operation when executing a transaction inside of the `interpreter`. This creates a deviation from the EVM spec and also introduces additional gas costs for the users when making coinbase payments.

## Recommended Mitigation Steps

Take a look at how `coinbase` payment is added to the access list in the geth implementation:

https://github.com/ethereum/go-ethereum/blob/master/core/state/statedb.go#L1341-1343
```
if rules.IsShanghai { // EIP-3651: warm coinbase
			al.AddAddress(coinbase)
		}

```
