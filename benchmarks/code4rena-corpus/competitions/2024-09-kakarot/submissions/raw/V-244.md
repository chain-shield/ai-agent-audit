# Vulnerability details



## Impact
The SIGNEXTEND opcode in Kakarot incorrectly handles edge cases where `byteNum = 31`, leading to different behavior compared to the Geth implementation. This could cause state divergences when executing smart contracts that rely on SIGNEXTEND operations with byte number 31, potentially breaking EVM compatibility.

## Proof of Concept
The issue lies in how the input range validation is performed in 

Kakarot checks if byteNum >= 32:
```cairo
let (byte_num_gt_word_size) = uint256_le(Uint256(32, 0), byte_num);
if (byte_num_gt_word_size != 0) {
	return x;
}
```


This leads to different behavior if byteNum is 31. Check this demonstration using the input value 0x80:

```sh
Input: 0x80 (binary: 10000000)

Case 1: byteNum = 30
- Geth: Performs sign extension
- Kakarot: Performs sign extension
MATCH ✓

Case 2: byteNum = 31
- Geth: Returns input unchanged
- Kakarot: Performs sign extension 
MISMATCH ❌

Case 3: byteNum = 32
- Geth: Returns input unchanged
- Kakarot: Returns input unchanged
MATCH ✓

Case 4: byteNum = 33
- Geth: Returns input unchanged
- Kakarot: Returns input unchanged
MATCH ✓
```

The flow of execution:

- When byteNum = 31:
   - Geth: 31 > 30 evaluates to TRUE → returns input unchanged
   - Kakarot: 32 <= 31 evaluates to FALSE → performs sign extension

- This mismatch affects a critical edge case in the SIGNEXTEND operation, where Geth specifies that any byteNum > 30 should return the input unchanged, while Kakarot continues to perform sign extension for byteNum = 31.

## Recommended Mitigation Steps
Update the input range check in Kakarot to match Geth's behavior by changing the condition to check if byteNum > 30 instead of byteNum >= 32.
