# Vulnerability details

**Summary**:  
An out-of-bounds read vulnerability exists in the `parse_storage_keys` function, which processes storage keys within Ethereum transactions. This issue can be exploited by a malicious prover to manipulate transaction data, potentially leading to serious security implications.

**Description**:  
When processing transactions via `eth_send_raw_unsigned_tx`, the transaction data (`tx_data`) is decoded using the `EthTransaction.decode` function. Based on the type of transaction, the data is further decoded by one of the following methods: `decode_legacy_tx`, `decode_2930`, or `decode_1559`. The resulting decoded transaction is represented as an `RLP.Item` structure:

```cairo
struct Item {
    data_len: felt,
    data: felt*,
    is_list: felt,
}
```

In the context of this structure, it is critical to verify that the `data_len` field accurately reflects the size of the `data` buffer before accessing its contents. However, in the `parse_storage_keys` function, the `keys_list.data_len` is not adequately checked, leading to an out-of-bounds read.

The relevant code is as follows:

```cairo
func parse_storage_keys{range_check_ptr}(
    parsed_keys: felt*, keys_list_len: felt, keys_list: RLP.Item*
) {
    alloc_locals;
    if (keys_list_len == 0) {
        return ();
    }

    let key = Helpers.bytes32_to_uint256(keys_list.data);
    assert [parsed_keys] = key.low;
    assert [parsed_keys + 1] = key.high;

    parse_storage_keys(
        parsed_keys + Uint256.SIZE, keys_list_len - 1, keys_list + RLP.Item.SIZE
    );
    return ();
}
```

The function directly accesses `keys_list.data` via the line:

```cairo
let key = Helpers.bytes32_to_uint256(keys_list.data);
```

If `keys_list.data_len` is less than 32 bytes, this access will read memory out of bounds, as `bytes32_to_uint256` expects at least 32 bytes of data to operate correctly. The absence of a check on `keys_list.data_len` before dereferencing `keys_list.data` opens up the potential for an attacker to exploit this vulnerability.

**Impact**:  
A malicious prover could leverage this out-of-bounds read to manipulate or fake the storage keys being read from the transaction. This could result in forged or manipulated data within the transaction, potentially compromising the integrity of the system and leading to unauthorized actions. Depending on the context of the transaction, this could lead to severe consequences, such as:

- Inaccurate storage key interpretation.
- Forged data that bypasses security checks.
- Manipulation of state data, leading to unauthorized access or control over storage.

**Recommendation**:  
To mitigate this issue, a proper check should be implemented to ensure that `keys_list.data_len` is at least 32 bytes before attempting to access `keys_list.data`. Specifically, the function should validate the size of the data field to prevent out-of-bounds reads and enforce proper memory safety.
