# Vulnerability details

Vulnerability Details:
The PrecompileEcRecover contract relies on the ICairo1Helpers interface to generate Keccak hashes for recovering Ethereum addresses. The Keccak hash is essential in this process as it transforms the public key into the corresponding Ethereum address. However, the hash generation is dependent on external helper functions from the ICairo1Helpers interface. If these external helper functions are not implemented correctly or securely, it can lead to incorrect address recovery or potentially even more severe vulnerabilities.

Key Issues:
Dependency on external helpers: The library_call_keccak function used to generate the Keccak hash is called through ICairo1Helpers. If this function is insecure or produces incorrect hashes, it would cause the Ethereum address derived from the public key to be incorrect.
Impact: Incorrect Keccak hash generation could lead to the wrong Ethereum addresses being derived from valid public keys, disrupting the integrity of the signature recovery process. This could allow attackers to spoof identities or disrupt contract functionality.
Relevant Code:
let (helpers_class) = Kakarot_cairo1_helpers_class_hash.read();
let (point_hash) = ICairo1Helpers.library_call_keccak(
    class_hash=helpers_class,
    words_len=8,
    words=inputs_start,
    last_input_word=0,
    last_input_num_bytes=0,
);

This code invokes the external Keccak helper function to generate the hash of the public key, but its correctness is entirely dependent on the secure implementation of the helper function.

Proof of Concept:
An attacker or a malicious third-party contract could modify or deploy a vulnerable implementation of the ICairo1Helpers interface that generates incorrect Keccak hashes. This would result in:
Incorrect Ethereum addresses: Derived addresses would not correspond to the intended public keys, breaking the Ethereum signature verification mechanism.
Identity spoofing: An attacker could leverage incorrect address recovery to impersonate another address.
No direct code change is required by the attacker—simply modifying the underlying helper implementation could cause address recovery issues.
Example:

func library_call_keccak{
    syscall_ptr: felt*,
    pedersen_ptr: HashBuiltin*,
    range_check_ptr,
    bitwise_ptr: BitwiseBuiltin*,
}(class_hash, words_len, words, last_input_word, last_input_num_bytes) -> (point_hash) {
    // Generates a wrong hash, either intentionally or due to a bug.
    let incorrect_hash = <malicious_value>;
    return (point_hash=incorrect_hash);
}

Recommended Mitigation Steps:
Test the Helper Implementation:
Ensure that the library_call_keccak function from ICairo1Helpers is rigorously tested with various inputs and scenarios. The output should match known Keccak hashes for public keys, ensuring correctness.
Internal Keccak Implementation:
As a more secure alternative, implement a known, well-tested Keccak hashing algorithm directly within the contract rather than depending on external libraries. This reduces dependency risks and ensures full control over the hashing mechanism.
Auditing External Helpers:
If using external libraries is unavoidable, perform regular audits of those libraries to ensure they are correctly implemented and free from vulnerabilities.
