# Vulnerability details

## Description

***Submitter note**: This is speculation on future code. This issue is currently not exploitable, and some stars have to align for it to become as such - but if it did happen, the consequences seem severe. This edge case is not really outlined in the [severity categorization doc](https://docs.code4rena.com/awarding/judging-criteria/severity-categorization). Therefore, according to [other risk assessment techniques](https://en.wikipedia.org/wiki/Risk_matrix), I'm defaulting to a Medium risk issue assuming the possibility of downgrading.*

The tempvar `a` [might underflow](https://github.com/kkrt-labs/kakarot/blob/038b3a3fa66cd1b8959665fed3e2eb7934e146b1/src/kakarot/evm.cairo#L173) if the `amount` argument is bigger than `self.gas_left`. This is generally caught with the range check pointer, however, it is possible to call this function with such a value that the underflow still happens but it isn't caught:

$$
l - x < rc \mod PRIME\\
x > l - rc \mod PRIME
$$
where
$l$ = `self.gas_left`, $x$ - `amount`, $rc$ - `range_check_builtin.bound`.

For the default test case value of $1000000$, $rc=340282366920938463463374607431768211455$ and the cairo prime this simplifies to:
$$
x > 1000000 - 340282366920938463463374607431768211455 \mod PRIME\\
x > 3618502788666131213697322783095070105282824848410658236509717448704104809026
$$
or in the general case
$$
x > 3618502788666131213697322783095070105282824848410658236509717448704103809026 + l
$$

(obviously also bound by `PRIME`)

Such a value will pass the range check with no modifications on the prover's side. Since an updated value of gas left [is set to `a`](https://github.com/kkrt-labs/kakarot/blob/038b3a3fa66cd1b8959665fed3e2eb7934e146b1/src/kakarot/evm.cairo#L201), this will result in a new `gas_left` value being an arbitrarily large integer between $0$ and $rc$. In the worst case scenario, this will be about $10^{38}$ gas.

It is to be noted that this issue is currently never called with values so big, but it is possible within the EVM spec. A way to get values so big is to invoke a memory expansion operation. It is currently possible to get gas costs so big that way, and we can verify this by solving for the new word size for memory expansion:
$$
\lfloor\frac{m^2}{512}\rfloor + 3m \approx \frac{m^2}{512} + 3m
\\
\frac{m^2}{512} + 3m = x
\\
\frac{m^2}{512} + 3m - x = 0
$$

which [rules out to about](https://www.wolframalpha.com/input?i=x%5E2%2F512+%2B+3*x+-+3618502788666131213697322783095070105282824848410658236509717448704103809026+%3D+0) (given $x=3618502788666131213697322783095070105282824848410658236509717448704103809026$):
$$
m \approx 2^{130}
$$

This is within the memory limit of the EVM. This *exact* value might be hard to attain in practice, but it is feasible (taking the Yellowpaper as the source of truth) to call the vulnerable function with a value that satisfies the silent underflow condition. In such a scenario, a transaction might contain a big memory expansion instruction, followed by a long sequence of arbitrary code, and then even spawn another EVM context with new memory and repeat this indefinitely. This basically means a DOS of the EVM.

One possible way this could potentially be exploited in practice (however not currently in scope) is if a memory expansion cost calculation is not saturated by expansions to $2^{32}$ ([which is admittedly done throughout the codebase](https://github.com/kkrt-labs/kakarot/blob/038b3a3fa66cd1b8959665fed3e2eb7934e146b1/src/kakarot/instructions/memory_operations.cairo#L37-L44))

## Recommended Mitigation Steps

Range check the `amount` argument. Alternatively, limit *all* cost expansion by some small but practical value, as is done in other Ethereum implementations [like geth](https://github.com/ethereum/go-ethereum/blob/80bdab757dfb0f6d73fb869d834979536fe474e5/core/vm/gas_table.go#L34-L41).
