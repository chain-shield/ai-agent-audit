# Vulnerability details


## Proof of Concept

Take a look at https://github.com/kkrt-labs/kakarot/blob/697100af34444b3931c18596cec56c454caf28ed/src/utils/eth_transaction.cairo#L101-L157

```cairo


    func decode_2930{bitwise_ptr: BitwiseBuiltin*, range_check_ptr}(
        tx_data_len: felt, tx_data: felt*
    ) -> model.EthTransaction* {
        alloc_locals;

        let (tx_items: RLP.Item*) = alloc();
        RLP.decode(tx_items, tx_data_len - 1, tx_data + 1);

        assert [tx_items].is_list = TRUE;
        let items_len = [tx_items].data_len;
        let items = cast([tx_items].data, RLP.Item*);

        assert items_len = 8;
        assert items[0].is_list = FALSE;
        assert items[1].is_list = FALSE;
        assert items[2].is_list = FALSE;
        assert items[3].is_list = FALSE;
        assert items[4].is_list = FALSE;
        assert items[5].is_list = FALSE;
        assert items[6].is_list = FALSE;
        assert items[7].is_list = TRUE;

        //snip
        tempvar tx = new model.EthTransaction(
            signer_nonce=nonce,
            gas_limit=gas_limit,
            max_priority_fee_per_gas=gas_price,
            max_fee_per_gas=gas_price,
            destination=destination,
            amount=amount,
            payload_len=payload_len,
            payload=payload,
            access_list_len=access_list_len,
            access_list=access_list,
            chain_id=model.Option(is_some=1, value=chain_id),
        );
        return tx;
    }
```

This function is used to decode an Ethereum transaction with optional access list, and as the name of the function shows and also as [has been documented](https://github.com/kkrt-labs/kakarot/blob/697100af34444b3931c18596cec56c454caf28ed/src/utils/eth_transaction.cairo#L96C16-L101), this implementation is done to support [EIP-2930](https://github.com/ethereum/EIPs/blob/master/EIPS/eip-2930.md).

Issue however is that this function would always fail when decoding the tx with these access lists, since [we enforce that the items length to be decoded must be `8`](https://github.com/kkrt-labs/kakarot/blob/697100af34444b3931c18596cec56c454caf28ed/src/utils/eth_transaction.cairo#L113) whereas [the EIP has them to be `11` instead](https://github.com/ethereum/EIPs/blob/master/EIPS/eip-2930.md#abstract):

> `rlp([chainId, nonce, gasPrice, gasLimit, to, value, data, accessList, signatureYParity, signatureR, signatureS])`.

To showcase how this is wrong we can go to the sister implementation of `decode_legacy_tx()` that's to work in accordance with EIP-155 we can see how different correct implementations have been make for the amount of fields in the tx, i.e how Pre eip-155 txs have 6 fields and post eip-155 txs have 9 fields, as such the assertions being made for the amount of items in the field is with the correct value, i.e 9 if it's post the eip or assured to be 6 if it's pre the EIP https://github.com/kkrt-labs/kakarot/blob/697100af34444b3931c18596cec56c454caf28ed/src/utils/eth_transaction.cairo#L64-L76:

```cairo
    func decode_legacy_tx{bitwise_ptr: BitwiseBuiltin*, range_check_ptr}(
        tx_data_len: felt, tx_data: felt*
    ) -> model.EthTransaction* {
        // see https://github.com/ethereum/EIPs/blob/master/EIPS/eip-155.md
        //..snip
        if (items_len == 6) {
            tempvar is_some = 0;
            tempvar chain_id = 0;
        } else {
            assert items_len = 9;
            assert items[6].is_list = FALSE;
            assert items[7].is_list = FALSE;
            assert items[8].is_list = FALSE;
            let chain_id = Helpers.bytes_to_felt(items[6].data_len, items[6].data);

            tempvar is_some = 1;
            tempvar chain_id = chain_id;
        }
        //..snip
    }
```

## Impact

Intended funcitonality is broken, considering protocol is expected to be able to decode any Ethereum transaction with optional access list, however this fails in the current system.

## Recommended Mitigation Steps

Remove the assertion that the items in the field must be 8 and have it be the correct value of `11`.
