# Vulnerability details

## Proof of Concept

In the current implementation of the `library.cairo` (accounts library), the transaction's signature is verified after extracting all the elements of the signature. The problem is that the `y_parity` (v part of the signature) is incorrectly calculated. Take a look at the following lines:

https://github.com/kkrt-labs/kakarot/blob/7411a5520e8a00be6f5243a50c160e66ad285563/src/kakarot/accounts/library.cairo#L169-177
```
 if (tx_type == 0) {
            let is_eip155_tx = is_nn(28 - v);
            assert pre_eip155_tx = is_eip155_tx;
            if (is_eip155_tx != FALSE) {
                assert y_parity = v - 27;
            } else {
                assert y_parity = (v - 2 * chain_id - 35);
            }
            tempvar range_check_ptr = range_check_ptr;
```

First, the code verifies if the transaction follows EIP-155 specification. However, when checking the TRUE / FALSE values, it makes a mistake: if the `is_eip155_tx != FALSE` meaning it's `TRUE` and transaction follows EIP-155 specification, the `y_parity` value is not calculated correctly:

https://eips.ethereum.org/EIPS/eip-155
```
If you do, then the v of the signature MUST be set to {0,1} + CHAIN_ID * 2 + 35 where {0,1} is the parity of the y value of the curve point for which r is the x-value in the secp256k1 signing process

```

As per spec, if chainId is available (which was the purpose of EIP-155), the `y_parity` has to be calculated as following:

https://github.com/kkrt-labs/kakarot/blob/7411a5520e8a00be6f5243a50c160e66ad285563/src/kakarot/accounts/library.cairo#L175
```
assert y_parity = (v - 2 * chain_id - 35);
```

But the value is calculated this way if `is_eip155_tx == FALSE` which is not true as it's quite the opposite. This will result in an incorrect calculation of v value according to the EIP-155 spec.

## Recommended Mitigation Steps

Change the lines so that `y_parity` is calculated properly according to the EIP-155 spec.
