# Vulnerability details

## Impact
Reentrant attack

## Proof of Concept

`execute_starknet_call` avoids reentrant attacks by determining whether `to_address` is `kakarot_address` (core contract) :

```rust
@external
func execute_starknet_call{syscall_ptr: felt*, pedersen_ptr: HashBuiltin*, range_check_ptr}(
    to: felt, function_selector: felt, calldata_len: felt, calldata: felt*
) -> (retdata_len: felt, retdata: felt*, success: felt) {
    Ownable.assert_only_owner();
    let (kakarot_address) = Ownable.owner();
    let is_get_starknet_address = Helpers.is_zero(
        GET_STARKNET_ADDRESS_SELECTOR - function_selector
    );
    // Helpers.is_zero ->  if(input==0) return 1 else return 0 
    let is_kakarot = Helpers.is_zero(kakarot_address - to); //to == owner -> is_kakarot = 1

    // function_selector == GET_STARKNET_ADDRESS_SELECTOR -> is_forbidden = 0
    // to = owner (is_kakarot =1) && function_selector != GET_STARKNET_ADDRESS_SELECTOR -> is_forbidden = 1
    tempvar is_forbidden = is_kakarot * (1 - is_get_starknet_address); 
    if (is_forbidden != FALSE) {
@>      let (error_len, error) = Errors.kakarotReentrancy();
        return (error_len, error, FALSE);
    }
    let (retdata_len, retdata) = call_contract(to, function_selector, calldata_len, calldata);
    return (retdata_len, retdata, TRUE);
}
```

However, this still does not prevent reentrant attacks if the attacker specifies `to_address` as the Account contract and calls the `execute_from_outside` function in the account contract to execute a transaction again (reentrant).

1. Since `to_address` is not equal to `kakarot_address`, it can pass kakarotReentrancy's check.
2. The nonce and storage space of the account are changed after the evm order ends(Starknet.commit). If a new transaction is initiated during the execution of the evm order, the old nonce and data store are used in the new transaction.

This leads to the problem of reentrant attacks that are common in evm, and the creation of accounts can also be a problem of duplicate creation.

Attack Scenario:

1. User A initiates transaction that invokes a function in attacker B's contract. The attacker obtains user A's transaction signature in advance and uses this signature to repeat the transaction through `execute_from_outside`.

2. When an attacker calls a third-party contract, he signs it with his private key in the fallback function (or some other type of callback), and then initiates another transaction with `execute_from_outside`, causing a common reentrant attack problem.
