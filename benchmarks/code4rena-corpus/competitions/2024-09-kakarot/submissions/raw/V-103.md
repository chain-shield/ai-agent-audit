# Vulnerability details

## Summary
The `prevRandao` plays a vital role in ensuring the security and fairness of Ethereum's PoS system by generating randomness for validator selection. If allowing an owner to modify this value, it risks significant security breaches, manipulation, and loss of trust in the project. It is recommended to adopt consensus mechanisms to safeguard the project.

## Proof of Concept
In the Kakarot project, the function `set_prev_randao` allows the `owner` to set the `prevRandao` value. In Ethereum's Proof of Stake (PoS) system, `prevRandao` was introduced after the Merge, replacing the old "difficulty" field. The full term is "previous randomness accumulated in deterministic order." It plays a critical role in generating randomness for Ethereum's consensus mechanism, ensuring fairness and unpredictability in the validator selection process.

The `prevRandao` is stored in the block header and is used to generate new randomness, which ensures the randomness needed for the selection of validators cannot be manipulated. Validators submit their own randomness seed during block creation, contributing to the update of the Randao value. This randomness ensures that the process is fair and not predictable or manipulable.

**Updating `prevRandao` in Ethereum:**
The update process of `prevRandao` is part of Ethereum’s consensus mechanism. In Geth’s PoS engine, the value of `prevRandao` is inherited from the previous block’s Randao value and is updated through hashing. In most implementations, such as Geth, this value is set automatically during block creation and cannot be manually changed via a setter function, unlike the Kakarot project. You can find the official Ethereum consensus specifications and related code in repositories like [Ethereum Consensus Specs](https://github.com/ethereum/consensus-specs).

```go
// FinalizeAndAssemble implements consensus.Engine, setting the final state and
// assembling the block.
func (beacon *Beacon) FinalizeAndAssemble(chain consensus.ChainHeaderReader, header *types.Header, state *state.StateDB, body *types.Body, receipts []*types.Receipt) (*types.Block, error) {
	if !beacon.IsPoSHeader(header) {
		return beacon.ethone.FinalizeAndAssemble(chain, header, state, body, receipts)
	}
	shanghai := chain.Config().IsShanghai(header.Number, header.Time)
	if shanghai {
		// All blocks after Shanghai must include a withdrawals root.
		if body.Withdrawals == nil {
			body.Withdrawals = make([]*types.Withdrawal, 0)
		}
	} else {
		if len(body.Withdrawals) > 0 {
			return nil, errors.New("withdrawals set before Shanghai activation")
		}
	}
	// Finalize and assemble the block.
	beacon.Finalize(chain, header, state, body)

	// Assign the final state root to header.
	header.Root = state.IntermediateRoot(true)

	// Assemble the final block.
	block := types.NewBlock(header, body, receipts, trie.NewStackTrie(nil))

	// Create the block witness and attach to block.
	// This step needs to happen as late as possible to catch all access events.
	if chain.Config().IsVerkle(header.Number, header.Time) {
		keys := state.AccessEvents().Keys()

		// Open the pre-tree to prove the pre-state against
		parent := chain.GetHeaderByNumber(header.Number.Uint64() - 1)
		if parent == nil {
			return nil, fmt.Errorf("nil parent header for block %d", header.Number)
		}

		preTrie, err := state.Database().OpenTrie(parent.Root)
		if err != nil {
			return nil, fmt.Errorf("error opening pre-state tree root: %w", err)
		}

		vktPreTrie, okpre := preTrie.(*trie.VerkleTrie)
		vktPostTrie, okpost := state.GetTrie().(*trie.VerkleTrie)
		if okpre && okpost {
			if len(keys) > 0 {
				verkleProof, stateDiff, err := vktPreTrie.Proof(vktPostTrie, keys, vktPreTrie.FlatdbNodeResolver)
				if err != nil {
					return nil, fmt.Errorf("error generating verkle proof for block %d: %w", header.Number, err)
				}
				block = block.WithWitness(&types.ExecutionWitness{StateDiff: stateDiff, VerkleProof: verkleProof})
			}
		}
	}

	return block, nil
}
```

**Risks of Modifying `prevRandao`:**
If `prevRandao` can be modified by an `owner` or any central authority, it undermines the security and fairness of the entire PoS mechanism. Such a modification could allow someone to manipulate validator selection, compromising the integrity of the system. The modification would also affect smart contracts and decentralized applications (dApps) that rely on blockchain randomness, such as lotteries or random number generation, making them vulnerable to manipulation.

More broadly, the ability to alter `prevRandao` could lead to a breakdown of the consensus mechanism. Other nodes would not recognize blocks where `prevRandao` was modified as valid, which could lead to blockchain forks or even a collapse of the network.

**Implications:**
If the `owner` can modify `prevRandao`, it poses a significant threat to the reputation. Users and investors could lose trust, suspecting that the project is a scam or is vulnerable to exploitation. The project’s reputation could suffer, leading to a loss of community support, financial backing, and potential regulatory scrutiny.

## Recommended Mitigation Steps
Function that allows an `owner` to modify critical consensus values like `prevRandao` should be removed and adopt PoS Consensus Mechanisms.
