# Vulnerability details

## Proof of Concept
The register_account function does not include any protection against front-running attacks. This function allows any account to register itself by calling the register_account method. A malicious actor could monitor the network for registration transactions and submit their own transaction with higher gas fees before the legitimate transaction, effectively registering the target account before the rightful owner.

This type of attack, known as front-running, could lead to the incorrect registration of accounts, where attackers preemptively claim ownership of StarkNet addresses mapped to specific Ethereum addresses (evm_address) that they don’t own.

```
@external
func register_account{syscall_ptr: felt*, pedersen_ptr: HashBuiltin*, range_check_ptr}(
    evm_address: felt
) {
    Pausable.assert_not_paused();
    return Kakarot.register_account(evm_address);
}
```

Consider the following scenario:

Alice wants to register her Ethereum address (0xAlice) to a StarkNet account using the register_account function.
A malicious user, Mallory, monitors the transaction pool and detects Alice’s registration transaction.
Before Alice’s transaction is mined, Mallory sends her own transaction with a higher gas fee, registering the same Ethereum address (0xAlice) to her own StarkNet account.
Mallory’s transaction is mined first, and the StarkNet account is registered under her control instead of Alice’s.
Mallory has now claimed the StarkNet account corresponding to Alice's Ethereum address. This could potentially allow Mallory to execute unauthorized transactions or impersonate Alice in the system.


Account Takeover: A malicious actor can front-run legitimate users and register their Ethereum addresses to their own StarkNet accounts.
Loss of Control: The legitimate owner of the Ethereum address will lose control over the corresponding StarkNet account, making it impossible for them to register or manage their account properly.
Potential Financial Loss: If funds or assets are tied to these accounts, the rightful owner could suffer a financial loss as they would not have control over the account.


## Recommended Mitigation Steps
To prevent front-running attacks, consider implementing nonce-based protection or using StarkNet’s own cryptographic signature mechanism to ensure that only the owner of the corresponding Ethereum address can register the account. Here are some potential solutions:

Nonces or Challenge-Response Mechanism:

Introduce a challenge-response system where the user has to prove that they own the Ethereum address before registering it. This can be done using cryptographic signatures.
Before allowing the registration, the contract could require a signed message from the Ethereum address, ensuring only the legitimate owner can register the corresponding StarkNet account.


```
@external
func register_account{syscall_ptr: felt*, pedersen_ptr: HashBuiltin*, range_check_ptr}(
    evm_address: felt, signature: Uint256
) {
    Pausable.assert_not_paused();
    // Ensure the user owns the evm_address by verifying the signature
    assert Kakarot.verify_signature(evm_address, signature) == TRUE;
    return Kakarot.register_account(evm_address);
}
```

Timed Delays for Registration:

Introduce a short delay window for registration transactions, where once an address is submitted for registration, other attempts to register the same address are blocked for a certain period, allowing the first transaction to go through without being front-run.
StarkNet Account Locking:

Lock the StarkNet account as soon as the registration transaction is initiated, preventing any competing transactions for the same Ethereum address from being processed until the original transaction is either confirmed or rejected.
