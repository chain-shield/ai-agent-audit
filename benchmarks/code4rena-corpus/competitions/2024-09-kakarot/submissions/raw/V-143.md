# Vulnerability details

## Proof of Concept

Currently the validity of the initcode is done the following way:

```
 tempvar is_initcode_invalid = is_deploy_tx * is_nn(
            bytecode_len - (2 * Constants.MAX_CODE_SIZE + 1)
        );
```

`is_deploy_tx` is set to 1 if we're actually deploying the contract and it's multiplied by the `is_nn(
 bytecode_len - (2 * Constants.MAX_CODE_SIZE + 1);`. But it's not actually correct as this line checks for the non-negative result of the subtraction of `bytecode_len` and `(2 * Constants.MAX_CODE_SIZE + 1)` effectively meaning that ` bytecode_len` > `(2 * Constants.MAX_CODE_SIZE + 1)`. That's not actually correct as the `bytecode_len` has to be only checked against `MAX_CODE_SIZE * 2` and not after adding 1 to it. This results in a situation where the code can be valid (`bytecode_len >  (2 * Constants.MAX_CODE_SIZE)` but due to this check it would marked as invalid. Even though it's an extreme situation, the protocol has to be compatible under all conditions.

According to the geth client implementation:

```
if rules.IsShanghai && contractCreation && len(msg.Data) > params.MaxInitCodeSize {
		return nil, fmt.Errorf("%w: code size %v limit %v", ErrMaxInitCodeSizeExceeded, len(msg.Data), params.MaxInitCodeSize)
	}
```

https://github.com/ethereum-optimism/op-geth/blob/7e9a329329807553ec66bca3d49dfba2da3ae71e/params/protocol_params.go#L140
```
MaxInitCodeSize = 2 * MaxCodeSize // Maximum initcode to permit in a creation transaction and create instructions
```

This can result in a situation where init code was calculated as the maximum allowed init code size according to the geth client but fail to be implemented in the Karakot.

## Recommended Mitigation Steps

Change the check on this:

```
 tempvar is_initcode_invalid = is_deploy_tx * is_nn(
            bytecode_len - 2 * Constants.MAX_CODE_SIZE)
        );
```
