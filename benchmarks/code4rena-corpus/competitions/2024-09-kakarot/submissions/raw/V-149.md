# Vulnerability details

Vulnerability Details:
The run function in the PrecompileEcRecover contract does not perform adequate input validation, particularly for the cryptographic signature components r, s, and the overall structure of the input data. This omission poses a critical security risk:
Lack of Input Size Verification: The function accepts an input array but does not ensure that its length matches the expected size for an Ethereum signature. Specifically, it should validate that the input contains exactly 32 bytes for r, 32 bytes for s, and 32 bytes for the message hash, in addition to the v value.
No Validation for r and s: The values of r and s, which are crucial to the secp256k1 signature verification process, are not validated for proper range or format. Invalid or malformed values for these components could cause unexpected behavior during cryptographic operations.
Limited Validation for v: Although the function checks if v is 27 or 28, it does not fully validate the entire signature structure, which might allow an attacker to pass malformed inputs.

This lack of validation can lead to various issues such as:
Out-of-bounds memory access: If the input data is not properly sized, memory access could exceed bounds during the cryptographic operations.
Corruption of contract state: Malformed inputs could result in incorrect public key recovery, leading to potential misuse of funds or misattribution of signatures.

Proof of Concept:
An attacker could craft a malicious transaction that supplies malformed inputs (especially for the cryptographic components r, s, or the message hash), which could result in incorrect recovery or trigger out-of-bounds memory access.
For example:
let malformed_input = [
    <invalid_msg_hash>,  // Invalid message hash or wrong size
    <invalid_r>,         // Invalid r value or wrong size
    <invalid_s>,         // Invalid s value or wrong size

];

Consequences:
Memory Corruption: The function might access memory outside of expected bounds, leading to potential crashes or data corruption.
Invalid Signature Recovery: Malformed or incorrect values for r, s, or the message hash could result in an incorrect address being recovered from the signature, leading to loss or misappropriation of funds.

Recommended Mitigation Steps:
Input Length Validation: Add a check to ensure that the input_len corresponds to the exact expected size of an Ethereum signature:
32 bytes for r, 32 bytes for s, 32 bytes for the message hash, and 1 byte for v.
Structure Validation: Before proceeding with cryptographic operations, validate that r and s are within the expected ranges for secp256k1 curve points.
Graceful Failure: Add error-handling logic to revert or return an error if the input does not conform to the expected structure or contains invalid values.
