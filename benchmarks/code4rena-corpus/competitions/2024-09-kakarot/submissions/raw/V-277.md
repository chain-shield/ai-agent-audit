# Vulnerability details

Vulnerability Details
1.Location: 
    - In the `saturated_sub` function, there’s a return value of 0 if the subtraction result is negative. This means that an attacker can theoretically keep calling this function with values that lead to repeated calls with predictable results, thus exhausting the computational resources.

    ```cairo
    func saturated_sub{range_check_ptr}(a, b) -> felt {
        let res = a - b;
        let is_res_nn = is_nn(res);
        if (is_res_nn != FALSE) {
            return res;
        }
        return 0; // Here, an attacker could exploit this logic
    }
    ```

2.Denial of Service:
   - In the `initialize_jumpdests` function, improper handling of bytecode lengths could lead to infinite loops or excessive memory allocation for unsuccessful jump verifications.
   
   ```cairo
   func initialize_jumpdests{range_check_ptr}(bytecode_len: felt, bytecode: felt*) -> (
       valid_jumpdests_start: DictAccess*, valid_jumpdests: DictAccess*
   ) {
       // If the bytecode length is not handled correctly, it could lead to excessive resource consumption
       ...
       jmp body if bytecode_len != 0; // Improper termination conditions
   }
   ```

3.Potential Infinite Loops: 
   - The `try_parse_destination_from_bytes` function incorrectly confirms the bytes format which may lead to unnecessary computations or a potential DoS vector if the provided values are not controllable.
   
   ```cairo
   func try_parse_destination_from_bytes(bytes_len: felt, bytes: felt*) -> model.Option {
       if (bytes_len != 20) {
           with_attr error_message("Bytes has length {bytes_len}, expected 0 or 20") {
               assert bytes_len = 0; // Mismanagement of input data can cause unwanted calls
           }
       ...
   }
   ```

Proof of Concept
The exploitation could occur in a contract that relies heavily on the `saturated_sub` functionality to handle transfers based on user inputs. An attacker could craft inputs that repeatedly result in the return value being 0, leading to an excessive number of internal calls that hinder the execution of essential functions, leading to a potential Denial-of-Service (DoS) condition.

For example, an attacker can find and consistently use inputs that subtract from a predetermined threshold that will always yield negative results, filling up the stack trace or causing memory exhaustion after multiple invocations of the `saturated_sub` function.
Additional Evidence

Recommended Mitigation Steps
1.Return Pattern Revamp**: Modify the `saturated_sub` function to throw an error or revert the transaction instead of returning 0. This would prevent function abuse.
  
   ```cairo
   if (is_res_nn == FALSE) {
       revert(); // Ensure that a failed state doesn't return a benign value
   }
   ```

2.Buffer Length Validation**: Implement stricter validation on input lengths before the functions proceed to loop constructs, particularly in `initialize_jumpdests`. Ensure that it exits gracefully rather than entering potential infinite loops.

3.Consider Rate Limiting**: Introduce limits on function invocations on functions that are processing external inputs. These can be inherent checks within the functions to prevent overwhelming the system.

4.Testing and Auditing**: Review code coverage tests to simulate aggressive usage patterns that could lead to the discovery of these DoS vulnerabilities under varying loads.
