# Vulnerability details

Vulnerability Details:
In the PrecompileEcRecover contract's run function, the v value is checked to ensure it matches either 27 or 28, which is part of the standard ECDSA signature format in Ethereum. However, no checks are performed on the r and s values, which represent crucial parts of the signature.

Key Issues:
No validation for r and s: The code assumes that the r and s values are correctly formatted and valid without checking whether they lie within the correct range for the secp256k1 elliptic curve.
Consequences of invalid r or s:
Signature Forgery: If r and s are not validated, an attacker could forge signatures, as invalid values could bypass the cryptographic checks.
Denial of Service (DoS): Invalid r or s values could cause the elliptic curve operations to behave unexpectedly, possibly resulting in excessive gas usage or failure of the recovery process, disrupting the contract's functionality.
Relevant Code:
let r = Helpers.bytes_to_uint256(32, input_padded + 32 * 2);
let s = Helpers.bytes_to_uint256(32, input_padded + 32 * 3);

// v is validated, but r and s are not.
if ((v - 27) * (v - 28) != 0) {
    let (output) = alloc();
    return (0, output, GAS_COST_EC_RECOVER, 0);
}

The lack of range validation for r and s introduces a critical vulnerability, allowing attackers to exploit the signature recovery process.

Proof of Concept:
An attacker could supply invalid or out-of-range values for r or s to exploit this vulnerability. For example:
let malicious_r = <invalid_r_value>;   // r should be within the secp256k1 curve order
let malicious_s = <invalid_s_value>;   // s should be in the range 0 < s < secp256k1 order
let v = 27;                            // Valid v value
let input = [msg_hash, malicious_r, malicious_s, v];

Potential impacts:
Signature Forgery: The elliptic curve recovery might return an invalid or incorrect public key, allowing an attacker to bypass signature verification.
Denial of Service (DoS): Supplying out-of-range values for r or s could lead to excessive computation, resulting in a gas drain or unexpected contract behavior.

Recommended Mitigation Steps:
Validate r and s Values:
Add checks to ensure that r and s conform to the secp256k1 curve requirements before performing elliptic curve recovery. For example:
Ensure that r and s are both positive and non-zero.
Ensure that r and s are smaller than the secp256k1 curve order (a constant value).

Example validation:
let secp256k1_order = <secp256k1_order_value>;
if (r == 0 or r >= secp256k1_order or s == 0 or s >= secp256k1_order) {
    revert();  // Invalid signature values
}

Range Check for s:
Ensure that s is checked to lie within 0 < s < secp256k1 order, following EIP-2 (which mandates lower s values to prevent signature malleability).
Graceful Error Handling:
Add error-handling logic that properly reverts the transaction or fails safely if r or s are found to be invalid, preventing excessive gas consumption or unexpected contract behavior.
