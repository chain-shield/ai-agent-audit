# Vulnerability details

## Summary
The `_commit_account` function in the `starknet.cairo` contract is designed to commit account state to StarkNet’s storage backend. However, while creating the `model.Transfer` structure, the `burn_address` field is passed as a value, whereas the `recipient` field is expected to be a pointer (`Address*`). Passing the `recipient` as a value (`Address`) instead of a pointer can cause type mismatches, resulting in either compilation errors or memory access issues. This can lead to crashes, unpredictable behavior, or even security vulnerabilities like unauthorized memory access.

## Proof of Concept

However, the `recipient` field in the `model.Transfer` structure is expected to be a pointer (i.e., `Address*`), not a value (`Address`).
[kakarot/src/kakarot/model.cairo:Transfer-L118-126](https://github.com/kkrt-labs/kakarot/blob/7411a5520e8a00be6f5243a50c160e66ad285563/src/kakarot/model.cairo#L118C1-L126C6)

```cairo
    // @dev A struct to save Starknet native ETH transfers to be made when finalizing a tx
    // @param sender Pointer to the sender's address.
    // @param recipient Pointer to the recipient's address.
    // @param amount The amount to be transferred.
    struct Transfer {
        sender: Address*,
        recipient: Address*,
        amount: Uint256,
    }
```

**Issue:**
If the `recipient` is passed as an `Address` rather than `Address*` (a pointer), this leads to a type mismatch. This could cause either a compile-time error or a runtime error, depending on how the compiler handles and reports such issues.

- **Compile-time error**: If the compiler performs strict type checks, it will raise an error, indicating that the `Transfer` structure expects an `Address*` type but is receiving an `Address` type.
  
- **Memory layout mismatch**: Even if the code compiles, the memory layout for `Address` and `Address*` is different. An `Address*` is a pointer, typically occupying one word, while an `Address` structure might occupy several words. This mismatch can lead to incorrect memory reads/writes.

- **Dereferencing issues**: The function assumes that both the `sender` and `recipient` fields are pointers. If an `Address` value is stored instead of a pointer, dereferencing the "pointer" will attempt to access the wrong memory location, leading to unpredictable behavior.
- **Segmentation faults and Security vulnerabilities**: The application might crash due to invalid memory access when trying to dereference a non-pointer value. Incorrect memory access could lead to vulnerabilities, such as information leakage or unauthorized memory access.

## Recommended Mitigation Steps
Ensure that the `recipient` field in the `model.Transfer` structure is passed as a pointer (`Address*`) rather than a value. This will prevent type mismatches, memory access issues, and potential vulnerabilities during runtime. Proper use of pointers ensures better memory management and secure contract execution.
