# Vulnerability details

## Impact
The way the [minLockDuration](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L98-L112) is set, the `minLockDuration` is set to `_lockdropData.end - _lockdropData.start`. This calculation assumes that the start and end values are always in the correct order (i.e., `start` is less than `end`).

If the `start` value is greater than the `end` value, the calculation `_lockdropData.end - _lockdropData.start` will result in a negative value, which may not be the intended behavior for the minLockDuration.

## Proof of Concept
If the `start` value is greater than the `end` value, the calculated `minLockDuration` will be negative. This means that the `lockdrop` duration will be negative, which is logically incorrect and can lead to unexpected behavior in other parts of the system that rely on the `lockdrop` duration.

Having a negative `lockdrop` duration can potentially introduce security vulnerabilities. For example, if the `lockdrop` duration is used to enforce certain time-based restrictions or conditions, a negative duration could bypass these restrictions or lead to unintended consequences.

Here's how this issue can manifest in the code
```solidity
function lock(uint256 duration) external {
    if (duration < lockdrop.minLockDuration)
        revert InvalidDurationError(duration, lockdrop.minLockDuration);

    // ... (rest of the locking logic)
}
```
In the lock function above, if the `minLockDuration` is negative due to the incorrect calculation in `configureLockdrop`, any positive duration value passed to the lock function will be considered valid, even if it's shorter than the intended minimum lock duration.

To illustrate the concept further, let's consider an example:

Suppose the `configureLockdrop` function is called with the following values.
```solidity
_lockdropData.start = 1685724000 (June 2, 2023, 12:00:00 AM)
_lockdropData.end = 1684032000 (May 14, 2023, 12:00:00 AM)
```
In this case, the `minLockDuration` will be calculated as
```solidity
_lockdropData.end - _lockdropData.start
= 1684032000 - 1685724000
= -1692000 (negative value)
```
This negative `minLockDuration` value can lead to unexpected behavior and potential vulnerabilities in other parts of the system that rely on the `lockdrop` duration.

## Recommended Mitigation Steps
Add an additional check to ensure that the `minLockDuration` is always a positive value, or you can use the abs function from the Solidity standard library to take the absolute value of the difference between `end` and `start`.
```solidity
function configureLockdrop(Lockdrop calldata _lockdropData) external onlyAdmin {
    if (_lockdropData.end < block.timestamp)
        revert LockdropEndedError(_lockdropData.end, uint32(block.timestamp));
    if (_lockdropData.start >= _lockdropData.end)
        revert LockdropInvalidError();

    uint256 minLockDuration = _lockdropData.end - _lockdropData.start;
    if (minLockDuration == 0)
        revert LockdropInvalidError();

    lockdrop = Lockdrop({
        start: _lockdropData.start,
        end: _lockdropData.end,
        minLockDuration: minLockDuration
    });

    emit LockDropConfigured(_lockdropData);
}
```
