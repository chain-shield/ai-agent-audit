# Vulnerability details

The `lock` function is responsible for locking a user's tokens for a specified `_duaration`. Where users can only unlock their tokens once their `unlockTime` has elapsed. However, the `LockManager.sol` contract includes a `lockOnBehalf` function, which allows any user to lock tokens on behalf of another user.

Now a malicious user or attacker can exploit the `lockOnBehalf` function. By locking same tokens with a `0 quantity ` on behalf of another user, and can repeatedly extend their `unlockTime`.

## Impact

Denial of Service (DoS) Attack: Bob, the attacker, can continuously extend the `unlockTime` of Alice's tokens, preventing her from unlocking her funds as intended.

```javascript
 if (lockedToken.unlockTime > uint32(block.timestamp))
            revert TokenStillLockedError();
```

## Proof of Concept

Scenario:

1. Let's assume a user, Alice, locks 10 WETH tokens with a default `_lockduration` of 30 days.
```javascript
if (_lockDuration == 0) {
  _lockDuration = lockdrop.minLockDuration;
}
```

2. Alice's `unlockTime` is calculated as follows:
```javascript
lockedToken.unlockTime = uint32(block.timestamp) + uint32(_lockDuration);
```

3. After 10 days, an attacker, Bob, maliciously locks 0 tokens for Alice via `lockOnBehalf` function.

4. Consequently, Alice's unlock time gets extended by 10 days, as her lock time is reset by Bob's action.

5. Bob can repeat this process.

## Tools Used
Manual review.

## Recommended Mitigation Steps

Consider implementing minimum and maximum limits for tokens that can be locked by users in `_lock` function.
Or restrict access to the `lockOnBehalf` function to authorized users only.
