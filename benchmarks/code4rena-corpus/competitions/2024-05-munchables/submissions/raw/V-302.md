# Vulnerability details

## Impact
The handling of the `address(0)` case, which represents the native token (e.g., Ether) in the `unlock` function is an issue. The code currently checks if `_tokenContract` is equal to `address(0)` and, if so, it attempts to transfer the native token using `payable(msg.sender).transfer(_quantity)`. But this line of code can potentially fail if the contract does not have enough balance to transfer the requested amount.

## Proof of Concept
The `unlock` function is responsible for transferring tokens (either ERC20 tokens or native tokens like Ether) back to the user after their lock period has ended. The problematic code is: [src/managers/LockManager.sol#L420](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L420)
```solidity
payable(msg.sender).transfer(_quantity);
```
This line attempts to transfer the native token (Ether) to the `msg.sender` using the `transfer` function. However, the `transfer` function has a specific behavior that can lead to unexpected results and potential loss of funds.

According to the Solidity documentation, the `transfer` function is a low-level function that forwards a specific amount of Ether to the recipient. If the contract does not have enough balance to cover the requested amount, the `transfer` function will revert the entire transaction, and any state changes made before the `transfer` call will be reverted as well.

This means that if the contract's Ether balance is lower than the requested `_quantity`, the entire `unlock` function will revert, and the user will not receive their tokens back. Additionally, any state changes made within the function, such as updating the locked token quantity or forcing the harvest, will also be reverted, leading to inconsistent contract state.

**let's consider the following scenario**

Alice locks 10 ETH in the contract.
After the lock period, Alice calls the `unlock` function to retrieve her 10 ETH.
However, due to some previous operations or external factors, the contract's Ether balance is only 5 ETH.
When the `payable(msg.sender).transfer(_quantity)`line is executed with `_quantity` being 10 ETH, the `transfer` function will revert because the contract does not have enough balance.
As a result, the entire `unlock` function will revert, and Alice will not receive her 10 ETH back.
Furthermore, any state changes made within the `unlock` function, such as updating the locked token quantity or forcing the harvest, will also be reverted, leading to inconsistent contract state.

## Recommended Mitigation Steps
A better approach would be to use the `call` function instead of `transfer`. The `call` function allows you to specify the amount of gas to be forwarded with the call, ensuring that the transfer will not fail due to insufficient gas. Additionally, it provides more flexibility in handling the return value and potential errors.
```solidity
function unlock(address _tokenContract, uint256 _quantity) external notPaused nonReentrant {
    // ... (existing code)

    if (_tokenContract == address(0)) {
        // Transfer native token (e.g., Ether)
        (bool success, ) = msg.sender.call{value: _quantity}("");
        require(success, "Transfer failed");
    } else {
        // Transfer ERC20 token
        IERC20 token = IERC20(_tokenContract);
        require(token.transfer(msg.sender, _quantity), "ERC20 transfer failed");
    }

    emit Unlocked(msg.sender, _tokenContract, _quantity);
}
```
the `call` function is used to transfer the native token, and the return value is checked to ensure the `transfer` was successful. For ERC20 tokens, the transfer function is still used, but the return value is checked to handle potential failures.
