# Vulnerability details

## Impact
Based on the total accumulated wrong accounting the last a couple of users that wish to unlock will not be able to because there won't be enough funds in the contract.

## Proof of Concept
Users transfers are recorded without having in mind the nuances of fee on transfer tokens.

Currently in [`_lock()`](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L311) the total locked amount is recorded without subtracting the potential fee.

Code reference: [`link`](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L380)

```solidity
function _lock(
    address _tokenContract,
    uint256 _quantity,
    address _tokenOwner,
    address _lockRecipient
) private {
    ...
    lockedToken.quantity += _quantity;
    ...
}
```

This will cause users who call [`unlock()`](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L401) to withdraw more than they should, leaving the last users calling [`unlock()`](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L401) without available funds to claim.

Code reference: [`link`](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L401-L427)

```solidity
function unlock(
    address _tokenContract,
    uint256 _quantity
) external notPaused nonReentrant {
    ...
@>  lockedToken.quantity -= _quantity;

    // send token
    if (_tokenContract == address(0)) {
        payable(msg.sender).transfer(_quantity);
    } else {
        IERC20 token = IERC20(_tokenContract);
@>      token.transfer(msg.sender, _quantity);
    }

    emit Unlocked(msg.sender, _tokenContract, _quantity);

```
