# Vulnerability details

## Impact
The current implementation allows `lockRecipient` to call [lockOnBehalf](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L275) and assign themselves as the `onBehalfOf` address.
Due to this some tokens like `DSToken` on *Ethereum* will not attempt to decrease the caller's allowance if the sender is the same as the caller. This gives `transferFrom` the same semantics as `transfer` in this case.

## Recommended Mitigation Steps
- Introduce a check that doesn't allow `lockRecipient` address to be same as `onBehalfOf` address.
