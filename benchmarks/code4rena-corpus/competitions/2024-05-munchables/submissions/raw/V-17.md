# Vulnerability details

## Impact
The contract cannot receive `ETH` due to the `receive()` and `fallback()` functions reverting transactions. This means that any attempt to lock `ETH` using `_tokenContract` as `address(0)` in `lockOnBehalf()` or `lock()` will fail.

## Proof of Concept
The contract has [receive()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L93-L95) and [fallback()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L89-L91) functions that revert any ETH sent to it:
```solidity
fallback() external payable {
    revert LockManagerInvalidCallError();
}

receive() external payable {
    revert LockManagerRefuseETHError();
}
```

The [lockOnBehalf()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L275-L294) and [lock()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L297-L309) functions call the private `_lock()` function to handle the locking logic:
```solidity
function lockOnBehalf(
    address _tokenContract,
    uint256 _quantity,
    address _onBehalfOf
) external payable notPaused onlyActiveToken(_tokenContract) onlyConfiguredToken(_tokenContract) nonReentrant {
    address tokenOwner = msg.sender;
    address lockRecipient = msg.sender;
    if (_onBehalfOf != address(0)) {
        lockRecipient = _onBehalfOf;
    }

    _lock(_tokenContract, _quantity, tokenOwner, lockRecipient);
}

function lock(
    address _tokenContract,
    uint256 _quantity
) external payable notPaused onlyActiveToken(_tokenContract) onlyConfiguredToken(_tokenContract) nonReentrant {
    _lock(_tokenContract, _quantity, msg.sender, msg.sender);
}
```

The [_lock()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L324-L331) function checks if `_tokenContract` is `address(0)` to handle `ETH` locking:
```solidity
function _lock(
    address _tokenContract,
    uint256 _quantity,
    address _tokenOwner,
    address _lockRecipient
) private {
    // Check if the token is ETH
    if (_tokenContract == address(0)) {
        if (msg.value != _quantity) revert ETHValueIncorrectError();
    } else {
        if (msg.value != 0) revert InvalidMessageValueError();
        IERC20 token = IERC20(_tokenContract);
        uint256 allowance = token.allowance(_tokenOwner, address(this));
        if (allowance < _quantity) revert InsufficientAllowanceError();
    }

    // Locking logic continues...
}
```
###### Problem: Contract Cannot Receive ETH
Even though `_lock()` checks for ETH and compares `msg.value` with `_quantity`, the contract's `receive()` and `fallback()` functions will revert any ETH sent to it. This creates a contradiction:

- `_lock()` allows for ETH locking in theory.
- `receive()` and `fallback()` prevent the contract from actually receiving ETH.

## Tools Used
Manual Review

## Recommended Mitigation Steps
1. Allow ETH Reception: 
Modify or remove the `receive()` and `fallback()` functions to allow the contract to accept ETH.
2. Remove ETH Locking Logic: 
Remove the logic in `_lock()` that handles ETH if the contract is not intended to lock ETH.
