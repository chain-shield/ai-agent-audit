# Vulnerability details

## Impact
The way the `LockedTokenWithMetadata` array is created and populated in the getLocked function is an issue.

The problem: [src/managers/LockManager.sol#L433-L437](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L433-L437)
```solidity
        uint256 configuredTokensLength = configuredTokenContracts.length;
        LockedTokenWithMetadata[]
            memory tmpLockedTokens = new LockedTokenWithMetadata[](
                configuredTokensLength
            );
```
This creates a new array in memory with a length equal to the number of configured token contracts. However, the `LockedTokenWithMetadata` struct contains an `address` member, which is not initialized when creating the array.

When the array is populated in the subsequent loop, the address member of each `LockedTokenWithMetadata` struct is left uninitialized, leading to unexpected behavior or errors.

## Proof of Concept
The `LockedTokenWithMetadata` struct contains two members `lockedToken` (which is another struct) and `tokenContract` (an address type).

When creating an array of `LockedTokenWithMetadata` structs in memory, the line: https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L433-L437

initializes the `lockedToken` member of each struct in the array with its default value (since `LockedToken` is a struct), but it does not initialize the `tokenContract` member, which is an `address` type.

In Solidity, when you create an array of structs in memory, the members of the structs are not automatically initialized. This means that the `tokenContract` member of each `LockedTokenWithMetadata` struct in the `tmpLockedTokens` array will have an uninitialized value, which is essentially a random value from memory.

Later, when the `tmpLockedTokens` array is populated in the loop: [src/managers/LockManager.sol#L438-L455](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L438-L455)
```solidity
for (uint256 i; i < configuredTokensLength; i++) {
    LockedToken memory tmpLockedToken;
    tmpLockedToken.unlockTime = lockedTokens[_player][configuredTokenContracts[i]].unlockTime;
    tmpLockedToken.quantity = lockedTokens[_player][configuredTokenContracts[i]].quantity;
    tmpLockedToken.lastLockTime = lockedTokens[_player][configuredTokenContracts[i]].lastLockTime;
    tmpLockedToken.remainder = lockedTokens[_player][configuredTokenContracts[i]].remainder;
    tmpLockedTokens[i] = LockedTokenWithMetadata(tmpLockedToken, configuredTokenContracts[i]);
}
```
the `tokenContract` member of each `LockedTokenWithMetadata` struct is overwritten with the correct value from `configuredTokenContracts[i]`. However, the initial uninitialized value of `tokenContract` may have already caused issues or unexpected behavior in other parts of the contract or external code that interacts with the `getLocked` function.

## Recommended Mitigation Steps
Should initialize the address member of each `LockedTokenWithMetadata` struct in the loop. 
```solidity
function getLocked(address _player) external view returns (LockedTokenWithMetadata[] memory _lockedTokens) {
    uint256 configuredTokensLength = configuredTokenContracts.length;
    _lockedTokens = new LockedTokenWithMetadata[](configuredTokensLength);
    for (uint256 i; i < configuredTokensLength; i++) {
        address tokenContract = configuredTokenContracts[i];      // <--
        LockedToken memory tmpLockedToken = lockedTokens[_player][tokenContract];     // <--
        _lockedTokens[i] = LockedTokenWithMetadata(tmpLockedToken, tokenContract);    // <--
    }
}
```
With this modification now the `LockedTokenWithMetadata` array is created with the correct length, and each element is initialized with the corresponding `LockedToken` data and the token contract address.
