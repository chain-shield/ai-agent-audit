# Vulnerability details

## Summary
**Context:**
The [unlock()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L401) function intentionally does not check if configured token is inactive in order to allow users to unlock their tokens and receive their harvested rewards.

**Issue:**
The issue is that if a token is deactivated, all the schnibbles earned for that token are lost. This is because the [getLockedWeightedValue()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L461C14-L461C36) does not consider the weighted value of the quantity of tokens that were locked by the user for the whole lock period due to [this check](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L470). 

## Proof of Concept

1. Let's say user has 100 tokens already locked in for X period of time.

2. Admin deactivates the token by calling [configureToken()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L115) with _tokenData.active set to false.

3. Now that user's locked period is complete, the user calls [unlock()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L401).

4. Function [unlock()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L401) calls the forceHarvest() function on the AccountManager contract, which calls the [_harvest()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/AccountManager.sol#L372) internal function, followed by [getSchnibbles()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/AccountManager.sol#L363) and finally retrieves the locked token weight from the [getLockedWeightedValue()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L461C14-L461C36) function. As we can see in the getLockedWeightedValue() function, it skips the inactive tokens. Due to this, the value returned is 0.

5. The value of 0 is returned to the _harvest() function, where it is stored in dailySchnibbles. Since dailySchnibbles (0) is then multiplied by bonus, the schnibbles earned are 0.

```solidity
    function _harvest(address _caller) private returns (uint256 _harvested) {
        (uint256 dailySchnibbles, uint256 bonus) = getDailySchnibbles(_caller);
        dailySchnibbles += ((dailySchnibbles * bonus) / 1e18);

        uint256 secondsToClaim = block.timestamp -
            players[_caller].lastHarvestDate;
        uint256 harvestedSchnibbles = (dailySchnibbles * secondsToClaim) /
            1 days;

        players[_caller].unfedSchnibbles += harvestedSchnibbles;
        players[_caller].lastHarvestDate = uint32(block.timestamp);

        _harvested = harvestedSchnibbles;

        emit Harvested(_caller, harvestedSchnibbles);
    }
```

Through this, we can see that how the call goes through without providing the user with their required schnibbles even though they locked the tokens for X period of time before the token was made inactive.

## Recommended Mitigation Steps
Consider removing this `configuredTokens[configuredTokenContracts[i]].active` condition from the getLockedWeightedValue() function. Removing it will have no issues as per my review since new locks cannot be created for an inactive token due to onlyActiveToken() modifier on the lock() function [here](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L304). For existing locks pending to be unlocked, users can unlock their tokens and receive the expected schnibbles.
