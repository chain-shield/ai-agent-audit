# Vulnerability details

## Impact
The calculation of the `deltaDecimal` value in `getLockedWeightedValue` function, The code assumes that all tokens have a maximum of 18 decimals and calculates `deltaDecimal` as follows: [/LockManager.sol#L473-L745](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L473-L475)
```solidity
                uint256 deltaDecimal = 10 **
                    (18 -
                        configuredTokens[configuredTokenContracts[i]].decimals);
```
This calculation is incorrect for tokens with more than 18 decimals. For example, if a token has 20 decimals, the calculation would result in `10 ** (-2)`, which is an invalid operation and will likely cause an arithmetic underflow or revert.

## Proof of Concept
The issue with the `getLockedWeightedValue` function is the calculation of the `deltaDecimal` value, which is used to adjust the locked token quantity based on the token's decimals. The code assumes that all tokens have a maximum of 18 decimals, but this assumption is incorrect and can lead to incorrect calculations or even a revert in certain cases.

Here's the relevant code snippet: [/LockManager.sol#L473-L483](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L473-L483)
```solidity
                uint256 deltaDecimal = 10 **
                    (18 -
                        configuredTokens[configuredTokenContracts[i]].decimals);
                lockedWeighted +=
                    (deltaDecimal *
                        lockedTokens[_player][configuredTokenContracts[i]]
                            .quantity *
                        configuredTokens[configuredTokenContracts[i]]
                            .usdPrice) /
                    1e18;
            }
```
The `deltaDecimal` value is calculated as `10 ** (18 - configuredTokens[configuredTokenContracts[i]].decimals)`. This calculation is intended to adjust the locked token quantity to a value with 18 decimals, which is assumed to be the maximum number of decimals for any token.

However, if a token has more than 18 decimals, the calculation will result in an invalid operation. For example, if a token has 20 decimals, the calculation would be `10 ** (18 - 20) = 10 ** (-2)`, which is an invalid operation in Solidity and will likely cause an arithmetic underflow or revert.

An example to the issue:

Suppose we have a token with 20 decimals, and the locked quantity for a player is 1000000000000000000000 (1 token with 20 decimals). The `usdPrice` for this token is 1e18 (1 USD).

The expected locked weighted value for this token should be:
```solidity
1 * 1e18 = 1e18
```
However, with the current implementation, the calculation would be:
```solidity
uint256 deltaDecimal = 10 ** (18 - 20) = 10 ** (-2) = 0;
lockedWeighted += (0 * 1000000000000000000000 * 1e18) / 1e18 = 0;
```
As you can see, the `deltaDecimal` value becomes 0 due to the invalid operation `10 ** (-2)`, resulting in an incorrect locked weighted value of 0 instead of the expected 1e18.

This can lead to incorrect calculations of the locked weighted value for tokens with more than 18 decimals, potentially affecting the overall functionality of the contract and any systems or calculations that rely on this value.

## Recommended Mitigation Steps
The code should handle tokens with more than 18 decimals correctly. One possible solution is to use a conditional statement to handle the cases where the token's decimals are greater than 18.
```solidity
uint256 deltaDecimal;
if (configuredTokens[configuredTokenContracts[i]].decimals <= 18) {
    deltaDecimal = 10 ** (18 - configuredTokens[configuredTokenContracts[i]].decimals);
} else {
    deltaDecimal = 10 ** (configuredTokens[configuredTokenContracts[i]].decimals - 18);
}
```
This way, the `deltaDecimal` value will be calculated correctly for tokens with any number of decimals, ensuring that the weighted value calculation is accurate.
