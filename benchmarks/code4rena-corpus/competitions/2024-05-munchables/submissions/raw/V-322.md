# Vulnerability details

## Impact
`approveUSDPrice/disapproveUSDPrice` may be executed at wrong proposal id , which is not proposed by proposer.

## Proof of Concept

 Current function `approveUSDPrice/disapproveUSDPrice` is using price as param.

```solidity

   function approveUSDPrice(
@>        uint256 _price
    )
   ...

    if (usdUpdateProposal.proposedPrice != _price)
    revert ProposalPriceNotMatchedError();
```
Suppose one situation:
1. Current propose id  100,  price  1.1. Proposer1 call `approveUSDPrice` do this propose, id 100, price 1.1.
 due the low gas or some other reason, Proposer1's approve transaction is possible stay in mempool. 
   other proposer disapproved this proposal, so the proposal is not passed.

2.Again, same price proposal created,  proposal id 101，price 1.1.  The previous proposer1's approve transaction is still in mempool.  
It's possible that proposer1's approve transaction is executed at proposal id 101.
The issue is if proposal1 disapproved the proposal 101,  since previous tx has executed at proposal 101, he cann't disapprove the same proposal again. 


The may cause some problem in propose process if we take price as param in `approveUSDPrice/disapproveUSDPrice` function.

manual 

## Recommended Mitigation Steps

repalce proposal id as param in `approveUSDPrice/disapproveUSDPrice` function.
