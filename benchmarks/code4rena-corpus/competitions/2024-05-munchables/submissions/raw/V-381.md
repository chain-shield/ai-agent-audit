# Vulnerability details

## Impact

The vulnerability in the `lockOnBehalf` function allows an attacker to indefinitely extend the lock duration of any user's tokens without their consent. This could potentially lock a user's funds for an extended period, hindering their ability to access them.
Based on the Attack to look out for in the README 
https://code4rena.com/audits/2024-05-munchables#top:~:text=The%20most%20important%20thing%20is%20that%20funds%20cannot%20get%20locked%20forever%2C


## Proof of Concept

The `lockOnBehalf` function enables users to lock tokens on behalf of another user (`_onBehalfOf`). However, it lacks a crucial check for approval from the target user (`_onBehalfOf`).

This check only verifies that the token owner (`_tokenOwner`) has approved the contract to transfer the specified amount (`_quantity`) for themselves. It doesn't ensure that the target user (`_onBehalfOf`) has authorized the attacker to lock tokens on their behalf.

**How the Attack Works:**

1. The attacker can call `lockOnBehalf` with a minimal/dust AMOUNT or zero `_quantity` for the target user's address (`_onBehalfOf`).
2. Since the `_quantity` check is missing for approvals,

 [ ensure that token owner has the permission to lock on behalf of uint256 allowance = token.allowance(lockrecipient,_tokenOwner );] 

the lock duration gets updated based on the existing settings (`playerSettings[_lockRecipient].lockDuration`).

3. The attacker can repeatedly call this function with minimal amounts, effectively extending the lock duration indefinitely for the target user.

## Recommended Mitigation Steps

- Implement a check for approval from the target user (`_onBehalfOf`) before extending their lock duration in the `lockOnBehalf` function. This check should hold for both Eth,weth and other ERC20 tokens.
