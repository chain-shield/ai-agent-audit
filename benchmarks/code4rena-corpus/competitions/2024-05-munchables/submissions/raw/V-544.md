# Vulnerability details

## Impact
unlock can deliver incorrect rewards amounts or more than expected, because of lockedToken.quantity.

## Proof of Concept
[unlock](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L401) method is decreasing the _quantity after a harvest is done.
```
accountManager.forceHarvest(msg.sender);

lockedToken.quantity -= _quantity;
```
let's explore the flow  of forceHarvest. -> means a call is done:
[forceHarvest](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L414) -> [_harvest](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/AccountManager.sol#L372) -> [getDailySchnibbles](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/AccountManager.sol#L373) -> [getLockedWeightedValue](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/AccountManager.sol#L366).

Above we can see that `forceHarvest` is relying on _lockedWeightedValue that returned from [getLockedWeightedValue](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L461), the issue here is when lockedWeighted gets calculated relying on [quantity](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L479).
```
lockedWeighted +=
		(deltaDecimal *
			lockedTokens[_player][configuredTokenContracts[i]]
				.quantity *
			configuredTokens[configuredTokenContracts[i]]
				.usdPrice) /
		1e18;
```

let's get back again to `unlock` method, is being called before decreasing the _quantity at [L414](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L414), meaning in `getLockedWeightedValue` is being called before decreasing or updating `lockedToken.quantity`, let's put this in mind for the next scenario:
- Alex has of lockedToken.quantity as 10e18.
- Alex called unlock for 1e18 _quantity amount.
- forceHarvest will be done and call getLockedWeightedValue.
- `getLockedWeightedValue` will calculate `lockedWeighted` according to current [quantity](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L479) which is 100e18 at the moment (no decrease done yet).
- Alex can keep calling for low partial amounts (_quantity), and harvest more than it should be, since the decrease `lockedToken.quantity -= _quantity`[L416](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L416) is happening after forceHarvest.

This behavior would be problematic and cause incorrect `getLockedWeightedValue` very time that a user calls unlock method for partial _quantity.

The issue arise when one can keep calling unlock for low amounts and make unlock calculated rewards for old quantity every time, assuming we have 100e18 quantity:
- unlock for 10e18 _quantity -> getLockedWeightedValue calculate `lockedWeighted` for 100e18.
- again unlock for 10e18 _quantity -> getLockedWeightedValue calculate `lockedWeighted` for 90e18.
- again unlock for 10e18 _quantity -> getLockedWeightedValue calculate `lockedWeighted` for 70e18 and so on...


## Tools Used
Manual Review

## Recommended Mitigation Steps
- The decrease of quantity should be done before `forceHarvest`.
- Calculations for lockedWeighted at `getLockedWeightedValue` should be done on the requested partial _quantity of unlock, not the remaning value of lockedTokens[_player][configuredTokenContracts[i]].quantity.
