# Vulnerability details

## Root Cause



A malicious or selfish actor among the `PriceFeed` roles can repeatedly submit invalid proposals or proposals that are in conflict with others. They can block the execution of new proposals by constantly back-running any transactions that attempt to resolve the pending proposal. This creates a race condition where a bad actor submits a new proposal just before the current one is resolved, effectively causing a denial of service for `setUSDThresholds` and `proposeUSDPrice`.



## Code Sample



```solidity

function setUSDThresholds(
    uint8 _approve, 
    uint8 _disapprove 
) external onlyAdmin {

    if (usdUpdateProposal.proposer != address(0)) // @audit potential DOS vulnerability

        revert ProposalInProgressError();        

    APPROVE_THRESHOLD = _approve;

    DISAPPROVE_THRESHOLD = _disapprove;    

    emit USDThresholdUpdated(_approve, _disapprove);

}



function proposeUSDPrice(
    uint256 _price, 
    address[] calldata _contracts 
) external onlyOneOfRoles([
    Role.PriceFeed_1, 
    Role.PriceFeed_2, 
    Role.PriceFeed_3, 
    Role.PriceFeed_4, 
    Role.PriceFeed_5 
]) {

    if (usdUpdateProposal.proposer != address(0)) // @audit potential DOS vulnerability
        revert ProposalInProgressError();
        

    if (_contracts.length == 0) 
        revert ProposalInvalidContractsError();        

    delete usdUpdateProposal;    

    // Redescribes proposal structure
    ++_usdProposalId;
    usdUpdateProposal.proposedDate = uint32(block.timestamp);
    usdUpdateProposal.proposer = msg.sender;
    usdUpdateProposal.proposedPrice = _price;
    usdUpdateProposal.contracts = _contracts;
    usdUpdateProposal.approvals[msg.sender] = _usdProposalId;
    usdUpdateProposal.approvalsCount++;    

    emit ProposedUSDPrice(msg.sender, _price);

}

```



## Outcome/Impact


A price feeder can create a scenario where legitimate proposals cannot be resolved due to continuous invalid proposal submissions. This situation could essentially lock the `setUSDThresholds` and `proposeUSDPrice` functions indefinitely, preventing critical updates and functionalities reliant on accurate price feeds. Additionally, this creates a race condition, causing significant operational delays or ultimately a full denial of service for price updates.



## Function Call Patterns



```solidity

// Malicious repeated proposeUSDPrice calls to prevent any other proposal acceptance


lockManager.proposeUSDPrice(invalidPrice1, validContracts); // First invalid proposal


// Each subsequent call by legitimate users to resolve or propose would fail.

lockManager.setUSDThresholds(newApproveThreshold, newDisapproveThreshold); // Would revert

lockManager.proposeUSDPrice(validPrice, validContracts); // Would revert



// Simulate race condition where attacker back-runs legitimate transactions

lockManager.disapproveUSDPrice(invalidPrice1); // legitimate attempt
lockManager.disapproveUSDPrice(invalidPrice1); // legitimate attempt
lockManager.disapproveUSDPrice(invalidPrice1); // legitimate attempt to reach DISAPPROVE_THRESHOLD

// attacker promptly back-runs with

lockManager.proposeUSDPrice(invalidPrice2, invalidContracts); // attacker's new invalid proposal

```


## Recommendation


To mitigate this vulnerability, implement a restriction preventing repeated proposals from the same proposer immediately after a previous proposal is defeated. Adding a time-based cooldown or a strict cycle check whereby a failed proposer cannot submit consecutive proposals without interleaving from other nodes can substantially reduce the risk:
