# Vulnerability details

## Impact
A user may unintentionally set lockDuration to less than minLockDuration, which makes it impossible to lock anymore.

## Proof of Concept

```solidity
    function setLockDuration(uint256 _duration) external notPaused {
        if (_duration > configStorage.getUint(StorageKey.MaxLockDuration))
            revert MaximumLockDurationError();

        playerSettings[msg.sender].lockDuration = uint32(_duration);
        // update any existing lock
        uint256 configuredTokensLength = configuredTokenContracts.length;
        for (uint256 i; i < configuredTokensLength; i++) {
            address tokenContract = configuredTokenContracts[i];
            if (lockedTokens[msg.sender][tokenContract].quantity > 0) {
                // check they are not setting lock time before current unlocktime
                if (
@>                  uint32(block.timestamp) + uint32(_duration) <
                    lockedTokens[msg.sender][tokenContract].unlockTime
                ) {
                    revert LockDurationReducedError();
                }

                uint32 lastLockTime = lockedTokens[msg.sender][tokenContract]
                    .lastLockTime;
                lockedTokens[msg.sender][tokenContract].unlockTime =
                    lastLockTime +
                    uint32(_duration);
            }
        }

        emit LockDuration(msg.sender, _duration);
    }
```

setLockDuration changes the lockDuration and unlockTime for the called user.

In the above logic, the _duration received as an argument can be very small.

Consider the following situation

- block.timestamp : 10000
- unlockTime: 10010
- _duration: 10
- minLockDuration: 1000

With the above assumptions, no revert occurs because the value of `uint32(block.timestamp) + uint32(_duration)` is 10010, which is equal to unlockTime.

This means that lockDuration can be less than minLockDuration.

This may be intentional. For example, minLockDuration is 30 days, because a user might want to increase the unlock from 5/27 to 5/28 by just one day.

This is definitely a helpful feature from a project perspective.

However, this small lockDuration makes the lock unusable.

The revert occurs because _lockDuration is smaller than minLockDuration.

Since minLockDuration updates the duration of all tokens, if a user wants to add a lock on only a specific token, they must wait for an unlock, then unlock and re-lock.

This means that waiting for the unlock pushes back the unlock of the next lock.

This is not a good user experience and can lead to abandonment on unlock.

## Tools Used

VS Code

## Recommended Mitigation Steps

It is recommended to modify _duration in setLockDuration so that it is greater than minLockDuration.
