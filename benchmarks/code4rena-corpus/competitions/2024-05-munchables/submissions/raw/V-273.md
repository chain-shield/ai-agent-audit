# Vulnerability details

## Impact
There are multiple issues that can arise when it comes to changing the maximum lock duration, as well as some instances with the minimum lock duration.

- If the maximum lock duration is ever decreased, users which have had the previous maximum duration will be able to bypass it when staking outside of lockdrop events.
- The minimum lock duration can also be bypassed outside of lockdrop events. 
- Due to a missing minimum lock duration check when calling `setLockDuration`, if it's set below a certain minimum during a lock drop event (or prior to it), the `_lock` function will keep reverting.  

## Proof of Concept
When a user locks their funds (or someone else does on their behalf), the checks for whether the lock time is less than the minimum one or above the maximum one is present in the code block which is only executed during lockdrop events.

```
 if (lockdrop.start <= uint32(block.timestamp) && lockdrop.end >= uint32(block.timestamp)) {
            if (
                _lockDuration < lockdrop.minLockDuration
                    || _lockDuration > uint32(configStorage.getUint(StorageKey.MaxLockDuration))
            ) revert InvalidLockDurationError();
```

If the lockdrop event has passed / isn't set, but the maximum lock duration was decreased in the meantime, users which have had their "old maximum lock period" decide to lock their funds outside of lockdrop events will be able to bypass this and still lock them for the "old maximum".

- Current max lock duration(`StorageKey.MaxLockDuration`) is 90 days.
- Bob has his `lockDuration` set at 90 days.
- Protocol admin decreases the maximum lock duration to 80 days.
- Bob will still be able to lock his tokens for a duration of 90 days (even now the maximum is 80) outside of lockdrop events. 

The above also goes for minimum lock times (even though they're particularly connected to lockdrop events).

The other problem is that there is no check for minimum duration times when calling `setLockDuration` allowing users to set the lock duration below the minimum which would cause the `_lock` function to revert during lockdrop events.

The above scenario can be especially problematic if the minimum duration that a user has set is below the minimum amount and the user expects someone else to lock the funds on their behalf, this will lead to constant reverts, until the lock period is changed and set above the minimum one.


## Tools Used
Manual Review

## Recommended Mitigation Steps
Introduce maximum lock period checks outside of lockdrop events in the `_lock` function, as well as introduce minimum lock period checks when setting the lock period as well in the `setLockPeriod`.
