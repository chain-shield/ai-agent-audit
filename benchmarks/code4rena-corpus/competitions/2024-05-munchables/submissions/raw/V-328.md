# Vulnerability details

## Description
The lock private function can be executed from the lock and from the lockOnBehalf public functions.
When called in periods outside of lock drops, the lock private function does a wrong state management on a locked token's remainder.
Let's analyze it in-depth:
The remainder uint256 variable is initialized as equal to zero:
```solidity
uint256 remainder;
```

Then the function proceeds to update this variable only if the current block timestamp is within the lockdrop bounds:
```solidity
if (
            lockdrop.start <= uint32(block.timestamp) &&
            lockdrop.end >= uint32(block.timestamp)
        ) {
...
remainder = quantity % configuredToken.nftCost;
...
}
```

Finally it takes the current remainder value and updates the remainder at the lockedToken storage mapping:
```solidity
lockedToken.remainder = remainder;
```

The issue with that is that if we don't ever reach the if block limited by the lock drop start and end, we put a zero-valued remainder at the storage in lockedToken.remainder. This removes any remainder the user had left.
## Impact
Users that call lock outside of the lockdrop period will lose the remainders accumulated on previous deposits
## Tools Used
Manual review
## Recommended Mitigation Steps
Make sure to avoid updating the remainder storage variable inside a lockedToken if the currently calculated value is not different than the previously held. An interesting way would to keep the remainder value would be through an else block:
```solidity
if (
            lockdrop.start <= uint32(block.timestamp) &&
            lockdrop.end >= uint32(block.timestamp)
        ) {
...
}
else {
	remainder = lockedToken.remainder;
}
```

This should suffice to ensure the remainder is not lost in such cases.
