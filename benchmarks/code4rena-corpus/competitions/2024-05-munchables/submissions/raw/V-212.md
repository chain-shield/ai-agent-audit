# Vulnerability details

## Impact
In the way the `_usdProposalId` is incremented and assigned to the `usdUpdateProposal.approvals` mapping. The line `++_usdProposalId;` increments the `_usdProposalId` variable before assigning it to the `usdUpdateProposal.approvals` mapping. This means that the first proposal will have an "ID of 1", while subsequent proposals will have IDs starting from "2".

This can lead to a bug where the approvals for the first proposal will be stored with an "ID of 1", but subsequent proposals will have their approvals stored with different IDs, making it difficult to track approvals for each proposal correctly.

_I observed that the line `++_usdProposalId;` increments the `_usdProposalId` variable before it is assigned to the `usdUpdateProposal.approvals` mapping._

_Since the `_usdProposalId` is incremented before being assigned, the first proposal will have an ID of 1, while subsequent proposals will have IDs starting from 2._

## Proof of Concept
The `proposeUSDPrice` function is responsible for creating a new proposal to update the USD price for one or more token contracts. It initializes a `usdUpdateProposal` struct with the proposed price, the list of contracts, and other relevant information. Additionally, it stores the approval of the proposer in the `usdUpdateProposal.approvals` mapping, using the `_usdProposalId` as the key. [LockManager.sol#L166-L174](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L166-L174)
```solidity
        usdUpdateProposal.proposedDate = uint32(block.timestamp);
        usdUpdateProposal.proposer = msg.sender;
        usdUpdateProposal.proposedPrice = _price;
        usdUpdateProposal.contracts = _contracts;
        usdUpdateProposal.approvals[msg.sender] = _usdProposalId;
        usdUpdateProposal.approvalsCount++;


        emit ProposedUSDPrice(msg.sender, _price);
    }
```
The issue is in the line `++_usdProposalId`;, which increments the `_usdProposalId` variable before assigning it to the `usdUpdateProposal.approvals` mapping. This means that for the first proposal, the `_usdProposalId` will be 1, and the proposer's approval will be stored with a key of 1 in the `usdUpdateProposal.approvals` mapping.

However, for subsequent proposals, the `_usdProposalId` will be incremented before being assigned to the `usdUpdateProposal.approvals` mapping. This means that the second proposal will have a `_usdProposalId` of 2, the third proposal will have a `_usdProposalId` of 3, and so on.

>: The impact of this issue is that it becomes difficult to track approvals for each proposal correctly. When other users approve or disapprove a proposal, they will use the `_usdProposalId` as the key in the `usdUpdateProposal.approvals` mapping. However, since the `_usdProposalId` is incremented before being assigned for the first proposal, the approvals for subsequent proposals will be stored with different IDs than the first proposal.

For example, let's say the first proposal has an ID of 1, and the second proposal has an ID of 2. If a user approves the second proposal, their approval will be stored with a key of 2 in the `usdUpdateProposal.approvals` mapping. However, when checking for approvals for the first proposal, the code will look for approvals with a key of 1, which may not include the approval for the second proposal.

This can lead to incorrect tracking of approvals, where approvals for one proposal may be counted towards another proposal, or approvals may be missed altogether. It can also make it difficult to correctly identify which proposal a particular approval or disapproval is associated with.

> I thought about scenarios where other users approve or disapprove proposals, and how the `_usdProposalId` would be used as the key in the `usdUpdateProposal.approvals` mapping. I realized that approvals for different proposals could be mixed up or missed altogether due to the incorrect IDs.

## Recommended Mitigation Steps
The code should increment the `_usdProposalId` after assigning it to the `usdUpdateProposal.approvals` mapping. 
```solidity
usdUpdateProposal.proposedDate = uint32(block.timestamp);
usdUpdateProposal.proposer = msg.sender;
usdUpdateProposal.proposedPrice = _price;
usdUpdateProposal.contracts = _contracts;
usdUpdateProposal.approvals[msg.sender] = _usdProposalId; // Assign the current _usdProposalId
usdUpdateProposal.approvalsCount++;

_usdProposalId++; // Increment _usdProposalId after assigning it

emit ProposedUSDPrice(msg.sender, _price);
```
By making this change, the first proposal will have an ID of 0, and subsequent proposals will have IDs starting from 1, ensuring that approvals are correctly tracked for each proposal.
