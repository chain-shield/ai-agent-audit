# Vulnerability details

## Impact
In the `setUSDThresholds` function (Lines 129-L139), the check for an existing proposal: [src/managers/LockManager.sol#L133-L134](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L133-L134)
```solidity
if (usdUpdateProposal.proposer != address(0))
    revert ProposalInProgressError();
```
This check assumes that `usdUpdateProposal.proposer` is set to the zero address (`address(0)`) when there is no proposal in progress. But, this may not always be the case, as the `usdUpdateProposal` struct could potentially have its proposer field set to a non-zero address even when there is no active proposal.

## Proof of Concept
The issue with the check `if (usdUpdateProposal.proposer != address(0))` in the `setUSDThresholds` function is that it assumes that the `usdUpdateProposal.proposer` field is set to the zero address (`address(0)`) when there is no proposal in progress.

> If the `usdUpdateProposal.proposer` field is not correctly reset to `address(0)` when a proposal is resolved (either approved, rejected, or removed), the check `if (usdUpdateProposal.proposer != address(0))` will fail, and the function will revert with the `ProposalInProgressError` even when there is no active proposal.

> If the `usdUpdateProposal.proposer` field is incorrectly set to a non-zero address due to a bug or unexpected state change, the check `if (usdUpdateProposal.proposer != address(0))` will pass, allowing the function to proceed even when there is an active proposal. This could lead to unexpected behavior, such as overwriting or modifying the threshold values while a proposal is still in progress.

> The code relies on the `usdUpdateProposal.proposer` field to implicitly track the state of a proposal. However, this approach is error-prone and can lead to inconsistencies if the state is not correctly managed throughout the contract's lifecycle.

To illustrate the concept, let's consider an example scenario:
```solidity
// Initial state
usdUpdateProposal.proposer = address(0); // No active proposal

// A new proposal is created
usdUpdateProposal.proposer = priceFeed1; // Active proposal

// Assume a bug or unexpected state change occurs
usdUpdateProposal.proposer = address(0xF230927711C6Dd0e2f0); // Incorrect state

// Calling setUSDThresholds will pass the check
setUSDThresholds(2, 3); // Modifies thresholds while a proposal is active
```
In this example, due to a bug or unexpected state change, the `usdUpdateProposal.proposer` field is set to a non-zero address (0xF230927711C6Dd0e2f0) even though there is an active proposal. When `setUSDThresholds` is called, the check `if (usdUpdateProposal.proposer != address(0))` will pass, allowing the function to modify the threshold values while a proposal is still in progress, leading to unexpected behavior.

## Recommended Mitigation Steps
I believe a safer approach would be to introduce a separate boolean flag or state variable to track whether a proposal is currently in progress or not. This flag should be set to `true` when a new proposal is created and reset to `false` when the proposal is either approved, rejected, or removed.
```solidity
bool public usdProposalInProgress;

function setUSDThresholds(
    uint8 _approve,
    uint8 _disapprove
) external onlyAdmin {
    if (usdProposalInProgress)
        revert ProposalInProgressError();
    
    APPROVE_THRESHOLD = _approve;
    DISAPPROVE_THRESHOLD = _disapprove;

    emit USDThresholdUpdated(_approve, _disapprove);
}
```
The `usdProposalInProgress` flag is checked instead of relying on the `usdUpdateProposal.proposer` field. This flag should be set to `true` when a new proposal is created and reset to `false` when the proposal is resolved.
