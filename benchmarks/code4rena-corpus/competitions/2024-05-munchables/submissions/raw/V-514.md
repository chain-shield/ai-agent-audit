# Vulnerability details

## Impact
Detailed description of the impact of this finding.
### Vulnerability: Read-Only Re-entrancy in the `getLocked` Function

#### Description:
The `getLocked` function (lines 430 to 458) in the `LockManager` contract is susceptible to a read-only re-entrancy attack. This function iterates over the `configuredTokenContracts` array to retrieve locked token information for a specified player. Although the function does not modify the state, it calls external contracts via the `IERC20` interface to fetch token data, which can be exploited.

#### Impact:
An attacker could exploit this vulnerability by deploying a malicious token contract that re-enters the `getLocked` function during the external call. This could result in infinite loops or incorrect data being returned, potentially causing denial of service or providing misleading information to users.

#### Example Scenario:
1. An attacker deploys a malicious token contract with a re-entrancy attack in its `balanceOf` function.
2. The attacker configures this malicious token in the `LockManager` contract.
3. When the `getLocked` function is called, the malicious token's `balanceOf` function re-enters the `getLocked` function, causing an infinite loop or other unintended behavior.

#### Recommendation:
To mitigate this vulnerability, avoid making external calls within loops or functions that read state. Instead, consider caching necessary data before performing any external calls or use a pull-based approach where external contracts provide data in a controlled manner. Additionally, ensure that any external calls are made after all internal state changes are completed to prevent re-entrancy attacks.

#### Location:
The `getLocked` function in `LockManager.sol` (lines 430-458) is potentially vulnerable to read-only re-entrancy if read in other functions. The state variable `lockedTokens` is read after external calls at several points within the function:

- Read at lines 440-442: `tmpLockedToken.unlockTime = lockedTokens[_player][configuredTokenContracts[i]].unlockTime`
- Read at lines 443-445: `tmpLockedToken.quantity = lockedTokens[_player][configuredTokenContracts[i]].quantity`
- Read at lines 446-448: `tmpLockedToken.lastLockTime = lockedTokens[_player][configuredTokenContracts[i]].lastLockTime`
- Read at lines 449-451: `tmpLockedToken.remainder = lockedTokens[_player][configuredTokenContracts[i]].remainder`
- Read at lines 452-455: `tmpLockedTokens[i] = LockedTokenWithMetadata(tmpLockedToken, configuredTokenContracts[i])`
- Read at line 438: `i++`

These variables were written after external calls at:

- Line 416: `lockedToken.quantity -= _quantity`
- Line 379: `lockedToken.remainder = remainder`
- Line 380: `lockedToken.quantity += _quantity`
- Line 381: `lockedToken.lastLockTime = uint32(block.timestamp)`
- Lines 382-384: `lockedToken.unlockTime = uint32(block.timestamp) + uint32(_lockDuration)`

## Recommended Mitigation Steps
### Recommendation to Resolve Read-Only Re-entrancy in the `getLocked` Function

#### Description:
The `getLocked` function in the `LockManager` contract is susceptible to a read-only re-entrancy attack due to potential external calls within the loop. To mitigate this vulnerability, we need to ensure that no external calls are made within the loop or that the function is structured in a way that prevents re-entrancy.

#### Steps to Resolve:

1. **Avoid External Calls in Loops:**
   Ensure that no external calls are made within the loop. In this case, the LockedTokenWithMetadata.

2. **Use Memory for Intermediate Storage:**
   Store intermediate results in memory before performing any operations that could potentially involve external calls. This ensures that the state is not modified during the loop.

3. **Re-entrancy Guard:**
   Although the function is read-only, adding a re-entrancy guard can provide an additional layer of protection.

4. **Review External Calls:**
   Ensure that any external calls made within the function are safe and do not lead to re-entrancy. In this case, the LockedTokenWithMetadata.

```solidity
function getLocked(
    address _player
) external view returns (LockedTokenWithMetadata[] memory _lockedTokens) {
    uint256 configuredTokensLength = configuredTokenContracts.length;
    LockedTokenWithMetadata[] memory tmpLockedTokens = new LockedTokenWithMetadata[](configuredTokensLength);

    for (uint256 i; i < configuredTokensLength; i++) {
        // Store intermediate results in memory
        LockedToken memory tmpLockedToken = lockedTokens[_player][configuredTokenContracts[i]];

        // Populate the temporary array with locked token data
        tmpLockedTokens[i] = LockedTokenWithMetadata(
            tmpLockedToken,
            configuredTokenContracts[i]
        );
    }

    _lockedTokens = tmpLockedTokens;
}
```

#### Summary:
By storing intermediate results in memory and ensuring no external calls are made within the loop, we can mitigate the risk of read-only re-entrancy attacks. Additionally, reviewing and ensuring the safety of any external calls can further protect against such vulnerabilities.
