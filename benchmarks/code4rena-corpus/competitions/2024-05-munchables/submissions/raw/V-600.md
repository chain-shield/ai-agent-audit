# Vulnerability details

## Description
```lockedToken.remainder``` is set to zero(0) when users lock token during non-LockDrop period (that is, ```block.timestamp > lockdrop.end```). This results in wastage of their remainder that could have been used up in the subsequent LockDrop period to mint NFTs.

## Proof of Concept
The following is a detailed step-by-step explanation of the issue.

Let us assume that user X locks 6500 eth Ether during a LockDrop period through the ```lock()``` function:

https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L297

```
    function lock(
        address _tokenContract,
        uint256 _quantity
    )
        external
        payable
        notPaused
        onlyActiveToken(_tokenContract)
        onlyConfiguredToken(_tokenContract)
        nonReentrant
    {
        _lock(_tokenContract, _quantity, msg.sender, msg.sender);
    }
```
After locking, X has the following data associated:

```
        lockedToken.remainder = 500 ether;
        lockedToken.quantity = 6500 ether;
```

This is assuming nft cost for Ether is 1000 eth (for making calculations simple).

Now, after some time, the LockDrop period ends.

X again locks 100 eth Ether through the ```lock()``` function. However, after this transaction, X has the following data associated:

```
        lockedToken.remainder = 0 ether;
        lockedToken.quantity = 6600 ether;
```
The remainder is set to zero(0)!

To visualize the gravity of this issue, assume the second lock, that X performed during the non-LockDrop period, did not happen. So, X still has the following associated data:

```
        lockedToken.remainder = 500 ether;
        lockedToken.quantity = 6500 ether;
```
That is, their remainder (during the LockDrop period) is preserved. Now, in a subsequent LockDrop period, X would have minted 1 NFT by locking 500 eth Ether (nft cost is assumed to be 1000 eth). This would not be the case now, as now:

```
        lockedToken.remainder = 0 ether;
``` 
To mint an NFT in the subsequent LockDrop period, X has to lock complete 1000 eth. This clearly shows that the remainder, associated with X from the previous LockDrop period, has not carried over to the subsequent LockDrop event, just because X locked 100 eth Ether during the non-LockDrop period.

The root cause of this issue is that remainder is not preserved when tokens are locked during non-LockDrop period.


## Impact
Impact: The protocol would want a functionality wherein the remainder of the locked tokens of users get carried over. This is also evident in the ```unlock()``` function that the ```lockedToken.remainder``` is not set to zero(0) when users unlock their token; the remainder could be used upon subsequent locks. 

However, this is a valid issue that shows this functionality of the protocol is hindered, making it a case of Medium.

Likelihood: Since the users are exposed to both LockDrop and non-LockDrop periods frequently, the likelihood seems High.

## Recommended Mitigation Steps
It is recommended to handle ```lockedToken``` data separately for the case of non-LockDrop period.
In the ```_lock()``` function, a local variable, ```_prevRemainder```, could store the previous remainder. If non-LockDrop period exists, then:
```
        lockedToken.remainder = _prevRemainder;
        lockedToken.quantity += _quantity;
```
