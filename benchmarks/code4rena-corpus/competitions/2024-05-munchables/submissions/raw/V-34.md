# Vulnerability details

## Description
The player is able to set a lock duration `lower then the minimum` established (`lockdrop.minLockDuration`). The root cause is because `setLockDuration` lacks lower bound validation against `_duration` parameter. 

Afterward, when the player try to lock his tokens, he will get `InvalidLockDurationError` error if a lockdrop is active, but otherwise the player will be able to call `lock/unlock at will without any restriction` using for example a `1 second duration`, granted spending gas, but that seems to be unexpected behavior and should not be allowed. Furthermore, this will have an impact `accountManager.forceHarvest` as this is called everytime by those functions, it's not clear if this could cause any type of side effects in the game. Overall, this seems to warran `Medium` severity.

## Impacts
`setLockDuration` can bypass `lockdrop.minLockDuration` check as no validation is made on the lower bound, which has two negatives impact:
1. `Lockdrop active`: The player will have to call `setLockDuration` again as calling `lock` will always revert with `InvalidLockDurationError`, which is not very user friendly and make the player waste gas.
2. `Lockdrop inactive`: The player can `grief` the contract as much as he wants to waste gas by calling lock/unlock, which will emit Locked/Unlocked, and might cause side effects du to the call of `forceHarvest`.

## PoC
Add the following tests in `SpeedRun.t.sol` and run the following command, both tests will pass confirming the issue reported.
```
forge test --match-test=test_setLockDurationToZero
forge test --match-test=test_setLockDurationToOneSecAndLockUnlock
```

```solidity
    event LockDuration(address indexed _player, uint256 _duration);
    function test_setLockDurationToZero() public {
        address nobody = address(78);
        deployContracts();

        vm.prank(nobody);
        vm.expectEmit();
        emit LockDuration(nobody, 0);
        lm.setLockDuration(0);
    }
	
	
    function test_setLockDurationToOneSecAndLockUnlock() public {
        uint256 lockAmount = 10e18;
        deployContracts();

        // Set lock ducation for 1 second, which is under the minimum which is 1 day
        vm.expectEmit();
        emit LockDuration(address(this), 1);
        lm.setLockDuration(1);

        // Register me
        amp.register(MunchablesCommonLib.Realm(3), address(0));

        // Pass the lockdrop which is 259201, so about 3 days
        uint256 timing = 4 days;
        vm.warp(timing);

        // Lock/Unlock at every second
        for (uint256 i; i < 100; i++) {
            // Lock at time (t)
            lm.lock{value: lockAmount}(address(0), lockAmount);

            // Move at t+1 second, which is our duration
            timing++;
            vm.warp(timing);

            // Unlock the token
            lm.unlock(address(0), lockAmount);
        }
    }
```	

## Recommended Mitigation Steps
Add the lower bound validation for the duration. This would be also more consistent with the [default value](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L349-L351) made in `lock`.


```diff
    function setLockDuration(uint256 _duration) external notPaused {
        if (_duration > configStorage.getUint(StorageKey.MaxLockDuration))
            revert MaximumLockDurationError();
+       if (_duration < lockdrop.minLockDuration)
+           revert MinimumLockDurationError();

        playerSettings[msg.sender].lockDuration = uint32(_duration);

    }
```	
