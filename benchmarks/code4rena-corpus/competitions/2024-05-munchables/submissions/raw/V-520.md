# Vulnerability details

## Impact
The `LockManager.sol::_lock()` function in its current form is not compatible with fee-on-transfer tokens, as it assumes the full `_quantity` is transferred when locking tokens. This assumption can lead to inaccurate balance updates and calculations. 

## Proof of Concept
Fee-on-transfer tokens are tokens that deduct a fee whenever they are transferred.
According to the protocol's read-me, fee-on transfer ERC20 tokens are in-scope for the audit:
> Fee on transfer -	Yes

For fee-on-transfer tokens, the actual amount received by the contract will be less than the `_quantity` specified by the user due to the fee deduction.

The current function does not account for the possibility that the amount received might be less than `_quantity`. 
[LockManager.sol#L374-L377](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L374-L377)
```js
// Transfer erc tokens
    if (_tokenContract != address(0)) {
        IERC20 token = IERC20(_tokenContract);
        token.transferFrom(_tokenOwner, address(this), _quantity);
    }
```
This could lead to incorrect calculations and state updates, as the function assumes the full amount is transferred.
```js
lockedToken.quantity += _quantity; 
```

Example Scenario:
1. Alice approves 1,000 tokens.
2. Contract checks and confirms 1,000 tokens allowance.
3. Alice calls `_lock` with `_quantity` set to 1,000 tokens.
4. Due to the 2% fee, only 980 tokens are transferred to the contract.
5. lockedToken.quantity += _quantity; incorrectly adds 1,000 tokens.
6. lockedToken.remainder = remainder; 

and subsequent logic assumes full 1,000 tokens, which is incorrect.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Modify the `_lock()` function to check the contract's balance before and after the token transfer to correctly account for fee-on-transfer tokens.
