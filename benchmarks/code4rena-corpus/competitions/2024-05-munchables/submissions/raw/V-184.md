# Vulnerability details

## Impact

According to provided [documentation](https://github.com/code-423n4/2024-05-munchables/blob/main/README.md#erc20-token-behaviors-in-scope), protocol accepts ERC-20 tokens with low decimals:

```
ERC20 token behaviors in scope
[...]
Low decimals ( < 6)	Yes
High decimals ( > 18)	Yes
```

However, the code-base does not respect the documentation and does not work properly with tokens with low decimals.

The calculations will be incorrect, leading to loss.


## Proof of Concept

[File: LockManager.sol](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L472-L482)
```
                // We are assuming all tokens have a maximum of 18 decimals and that USD Price is denoted in 1e18
                uint256 deltaDecimal = 10 **
                    (18 -
                        configuredTokens[configuredTokenContracts[i]].decimals);
                lockedWeighted +=
                    (deltaDecimal *
                        lockedTokens[_player][configuredTokenContracts[i]]
                            .quantity *
                        configuredTokens[configuredTokenContracts[i]]
                            .usdPrice) /
                    1e18;
```

The comment at line 472 states that: `We are assuming all tokens have a maximum of 18 decimals and that USD Price is denoted in 1e18`. However, this assumption is wrong, because the documentation straightforwardly states that ERC-20 with low decimals ( < 6) are in scope.

When provided ERC-20 have less than 18 decimals, the expression `(18 - configuredTokens[configuredTokenContracts[i]].decimals)` will return incorrect result, leading to loss. Line 474 assumes that tokens in `configuredTokens` have 18 decimals. However, if they have less decimals, the scaling will be calculated incorrectly, leading to loss.


## Tools Used

Manual code review


## Recommended Mitigation Steps

Do not assume that all tokens have a maximum of 18 decimals - because the documentation straightforwardly states that's not true. According to documentation, protocol should support tokens with both low ( < 6) and high ( > 18) decimals.
