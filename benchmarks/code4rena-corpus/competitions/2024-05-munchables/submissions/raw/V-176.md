# Vulnerability details

## Impact

According to provided [documentation](https://github.com/code-423n4/2024-05-munchables/blob/main/guides/CONSTANTS.md), roles:
* `PriceFeed_1`
* `PriceFeed_2`
* `PriceFeed_3`
* `PriceFeed_4`
* `PriceFeed_5`

are the addresses allowed to propose and vote on USD price updates. This implies, that there are 5 different roles (`PriceFeed_1` - `PriceFeed_5`) which can propose USD price and/or vote for that proposal.
Each role can contain multiple of addresses (to confirm that, please take a look at `setRole()` function from `ConfigStorage.sol` - a single role can be assigned to multiple of addresses).
This (having 5 roles, each containing multiple of addresses), allows us to assume, that there might be a lot of addresses which can vote for the proposal.

However, the protocol implements `APPROVE_THRESHOLD` and `DISAPPROVE_THRESHOLD` as `uint8`, which basically means, that the max threshold for executing or removing a proposal is 255 (`type(uint8).max`). This obviously is not enough when there are many voters.

Moreover, please notice, that according to provided documentation, I treat (`PriceFeed_1` - `PriceFeed_5`) as non-trusted roles, because the protocol explicitly mentions that no roles are trusted:

[File: README.md](https://github.com/code-423n4/2024-05-munchables/blob/main/README.md#all-trusted-roles-in-the-protocol)
```
All trusted roles in the protocol

N/A
```


## Proof of Concept

Function `approveUSDPrice()` (which allows to vote for the proposal) and function `disapproveUSDPrice()` (which allows to vote against the proposal) implements `onlyOneOfToles()` modifier:

```
        onlyOneOfRoles(
            [
                Role.PriceFeed_1,
                Role.PriceFeed_2,
                Role.PriceFeed_3,
                Role.PriceFeed_4,
                Role.PriceFeed_5
            ]
        )
```

This modifier basically states, that any address which belongs to role `Role.PriceFeed_1`, `Role.PriceFeed_2`, `Role.PriceFeed_3`, `Role.PriceFeed_4`, `Role.PriceFeed_5` can vote for (or against) the proposal.

As 5 roles (each of those role can contain multiple of addresses) can vote for/against the proposal - we should assume that voting is designed for a significantly big number of users.

Each voting is bound by previously defined threshold (if there are more "yes" votes than the defined threshold, the proposal will be executed):

[File: LockManager.sol](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L506-L509)
```
    function _execUSDPriceUpdate() internal {
        if (
            usdUpdateProposal.approvalsCount >= APPROVE_THRESHOLD &&
            usdUpdateProposal.disapprovalsCount < DISAPPROVE_THRESHOLD
```
However, the `APPROVE_THRESHOLD` and `DISAPPROVE_THRESHOLD` are defined as `uint8`:

[File: LockManager](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L16-L18C)
```
    uint8 APPROVE_THRESHOLD = 3;
    /// @notice Threshold for removing a proposal
    uint8 DISAPPROVE_THRESHOLD = 3;
```

This means, that the maximum `APPROVE_THRESHOLD` could be 255. This limit might not be enough when there are multiple of voters.

Having multiple of roles which allows to vote for the proposal implies, that protocol expects a lot of users taking part in the voting. The more voters available to vote, the bigger threshold should be. E.g., the default value of `APPROVE_THRESHOLD` is set to `3`. For the scenario, that there are only 5 users who are able to vote, this threshold states that more than half of eligible to vote users need to approve the proposal. However, this threshold becomes negligible when the number of users who can vote is being significantly increased.

E.g., let's assume that there are 1500 users who can vote. The maximum threshold for accepting the proposal is 255, thus it's less than 20% users which can accept the proposal (255/1500 = 0.17) - and it's not possible to increase the threshold.

Because the maximum value of `APPROVE_THRESHOLD` is 255, the maximum threshold to approve the proposal is defined as below:

```
255 / (numberOfUsersWithRole(Role.PriceFeed_1) + numberOfUsersWithRole(Role.PriceFeed_2) + numberOfUsersWithRole(Role.PriceFeed_3) + numberOfUsersWithRole(Role.PriceFeed_4) + numberOfUsersWithRole(Role.PriceFeed_5))
```

When there are a lot of users who can vote - it won't be possible to set a proper threshold. This put the whole voting for a proposal at risk - even for the maximum threshold, only 255 votes would be enough to accept any proposal.

Manual code review


## Recommended Mitigation Steps

Define `APPROVE_THRESHOLD` and `DISAPPROVE_THRESHOLD` as `uint256` (or `uint32` at least). This would allow to set higher thresholds when protocol will have more users in `Role.PriceFeed_1`, `Role.PriceFeed_2`, `Role.PriceFeed_3`, `Role.PriceFeed_4`, `Role.PriceFeed_5` roles.
