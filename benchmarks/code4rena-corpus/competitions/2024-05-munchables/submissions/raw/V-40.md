# Vulnerability details


## Proof of Concept

Take a look at https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L401-L427

```solidity
    function unlock(
        address _tokenContract,
        uint256 _quantity
    ) external notPaused nonReentrant {
        LockedToken storage lockedToken = lockedTokens[msg.sender][
            _tokenContract
        ];
        //@audit
        if (lockedToken.quantity < _quantity)
            revert InsufficientLockAmountError();
        if (lockedToken.unlockTime > uint32(block.timestamp))
            revert TokenStillLockedError();

        // force harvest to make sure that they get the schnibbles that they are entitled to
        accountManager.forceHarvest(msg.sender);

        lockedToken.quantity -= _quantity;

        // send token
        if (_tokenContract == address(0)) {
            payable(msg.sender).transfer(_quantity);
        } else {
          //@audit
            IERC20 token = IERC20(_tokenContract);
            token.transfer(msg.sender, _quantity);
        }

        emit Unlocked(msg.sender, _tokenContract, _quantity);
    }
```

This is the function that's used so as to unlock the player's tokens we can see that there is a check to ensure the amount to be withdrawn is less than the amount that was previously locked by the `msg.sender` for the specific token.

Now from the readme we can see the below: https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/README.md#L144-L148

| Question                                                                                                                                                   | Answer |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| [Balance changes outside of transfers](https://github.com/d-xo/weird-erc20?tab=readme-ov-file#balance-modifications-outside-of-transfers-rebasingairdrops) | Yes    |

Now issue is that if the locked token is then set as a token whose balance changes outside transfer which would most probably be the case as `USDB` is one of the core tokens integrated. Considering `USDB` is a rebasing token, this then means that the `quantity` of tokens that was specified [when the tokens were to be locked by the user](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L374-L377), would definitely have changed by the time the unlock duration passes and users would like to withdraw.

This could lead to one of the protocol's invariant listed below being broken: https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/README.md#L184-L187

```markdown
## Attack ideas (where to focus for bugs)

The most important thing is that funds cannot get locked forever, people cannot take other people's funds, and that people cannot reduce lockup times that are previously set.
```

Cause in the case of a negative rebase, users who unlock earlier on would steal tokens from other users. _`(intentionally/unintentionally)`_.

## Impact

This would lead to multiple cases depending on how the balance of the tokens have changed, let's use the logic of rebasing tokens to prove the impacts.

- In the case of multiple positive rebases during the unlock duration:

  - This would mean that all users that are attempting to unlock would encounter loss of funds, cause their stored state `quantity` data is the maximum they can receive and all the rebase from their deposits would be unfairly not sent to them.

- In the case of multiple negative rebases during the unlock duration:
  - This would mean that the users stored state `quantity` data is actually inflated and users withdrawing the maximum would mean that they are _unintentionally(intentionally)_ stealing from other users, as later users that would try to unlock all the quantity they locked would encounter reverts in the attempt to [transfer](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L423) as the contract does not have enough funds to cover the transfer due to the previous withdrawals from other users.

## Recommended Mitigation Steps

Consider a tracking system on the rebases for the lock token in order to know the real amount of `quantity` a user has locked in respect to the rebases that have occurred since the they locked their tokens. Alternatively, don't support these tokens, a logic like that of bad debt socialisation could be integrated where everyone shares the loss if it is a negative rebase, and otherwise if it is a positive rebase.
