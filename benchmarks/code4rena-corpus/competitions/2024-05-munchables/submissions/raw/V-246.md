# Vulnerability details

## Impact
Detailed description of the impact of this finding.
### Vulnerability: Unchecked Transfer on the `unlock` Function within the `LockManager` Contract

#### Description:
The `unlock` function in the `LockManager` contract is responsible for unlocking and transferring tokens back to the user. However, the function uses the `IERC20.transfer` method instead of the safer `IERC20.safeTransfer` method provided by OpenZeppelin's SafeERC20 library. This introduces a potential vulnerability where the transfer might fail silently without reverting the transaction, leading to unexpected behavior and potential loss of funds.

#### Affected Code:
```solidity
// Lines 401 to 427
function unlock(
    address _tokenContract,
    uint256 _quantity
) external notPaused nonReentrant {
    LockedToken storage lockedToken = lockedTokens[msg.sender][_tokenContract];
    if (lockedToken.quantity < _quantity)
        revert InsufficientLockAmountError();
    if (lockedToken.unlockTime > uint32(block.timestamp))
        revert TokenStillLockedError();

    // force harvest to make sure that they get the schnibbles that they are entitled to
    accountManager.forceHarvest(msg.sender);

    lockedToken.quantity -= _quantity;

    // send token
    if (_tokenContract == address(0)) {
        payable(msg.sender).transfer(_quantity);
    } else {
        IERC20 token = IERC20(_tokenContract);
        token.transfer(msg.sender, _quantity); // Vulnerable line
    }

    emit Unlocked(msg.sender, _tokenContract, _quantity);
}
```

#### Impact:
1. **Silent Failures**: If the `transfer` method fails (e.g., due to insufficient balance or allowance), it will return `false` but not revert the transaction. This can lead to a situation where the contract state is updated (e.g., `lockedToken.quantity` is decreased) without actually transferring the tokens, causing inconsistencies and potential loss of funds.
2. **Loss of Funds**: Users may believe their tokens have been successfully unlocked and transferred, but in reality, the tokens remain in the contract, leading to potential loss of access to their funds.

#### Recommendation:
Replace the usage of `IERC20.transfer` with `IERC20.safeTransfer` from OpenZeppelin's SafeERC20 library to ensure that any transfer failures will revert the transaction, maintaining the integrity of the contract state and preventing potential loss of funds.

#### Suggested Fix:
```solidity
// Import SafeERC20 library
import "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";

// Use SafeERC20 for token transfers
using SafeERC20 for IERC20;

        payable(msg.sender).transfer(_quantity);
    } else {
        IERC20 token = IERC20(_tokenContract);
        token.safeTransfer(msg.sender, _quantity); // Use safeTransfer
    }

    emit Unlocked(msg.sender, _tokenContract, _quantity);
}
```

By using `safeTransfer`, the contract ensures that any transfer failures will revert the transaction, thereby maintaining the consistency and security of the contract.
