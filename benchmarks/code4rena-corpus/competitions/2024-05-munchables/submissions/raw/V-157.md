# Vulnerability details

## Vulnerability details 
When setting lockDuration in `setLockDuration()`, user `must` set the `block.timestamp + duration` greater than `all` lockedTokens `unlockTime`
```solidity
function setLockDuration(uint256 _duration) external notPaused {
      ...
                if (
                    uint32(block.timestamp) + uint32(_duration) <
                    lockedTokens[msg.sender][tokenContract].unlockTime
                ) {
                    revert LockDurationReducedError();
                }
      ...
    }

```
Now this is `problem` because either trx. will revert or it will `unnecessarily` increase the `unlockTime` for token which is going to unlock `soon`

//Taking time in hrs for easier explanation
1. Suppose user `locked` his tokenA at 1PM and minLockDuration = 5hrs then lastLockTime = 1PM & unlockTime = 6PM(1PM + 5hrs) for tokenA
2. Again at 4PM, user locked tokenB then lastLockTime = 4PM & unlockTime = 9PM(4PM + 5hrs) for tokenB
3. His `lockDuration = 5hrs` ie equal to minLockDuration(this is set in _lock())
4. User wanted to change his `lockDuration = 3hrs`(currently time is 4PM)
5. For tokenA, block.timestamp + duration = 4PM + 3hrs = 7PM ie greater than 6PM(tokenA's unlockTime), check will pass
6. For tokenB, block.timestamp + duration = 4PM + 3hrs = 7PM ie less than 9PM(tokenB's unlockTime), check will not pass
7. As a result trx. will revert or user have to increase his duration, which will increase the unlockTime of tokens that are going to be unlocked earlier like tokenA 

## Impact
User will not be able to update his `lockDuration`
