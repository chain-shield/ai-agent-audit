# Vulnerability details

## Impact

The `LockManager` contract's `_lock` function uses the `transferFrom` method to transfer tokens from a user's address to the contract. However, not all ERC20 tokens adhere to the standard of reverting on failure; some tokens, such as ZRX, return false instead of reverting. If the `transferFrom` function fails and returns false, but this return value is not checked, it can lead to tokens not being transferred as intended. This oversight can cause significant issues, such as inaccurate token balances, failure to lock tokens, and potential loss of funds or contract malfunction.

## Proof of Concept

In the `LockManager` contract, the `_lock` function contains the following code:

```solidity
if (_tokenContract != address(0)) {
    IERC20 token = IERC20(_tokenContract);
    token.transferFrom(_tokenOwner, address(this), _quantity);
}
```

If the `transferFrom` function fails (e.g., the token contract returns false), this failure will not be detected, and the function will proceed as if the tokens were successfully transferred.

### Example of Vulnerable Token

Some tokens, such as ZRX, do not revert on failure but instead return false. You can find more examples of such tokens in the [Weird ERC20 tokens list](https://github.com/d-xo/weird-erc20/#no-revert-on-failure).

## Recommended Mitigation Steps

To ensure safe token transfers, use the `safeTransferFrom` method provided by the OpenZeppelin `SafeERC20` library. This method handles non-standard ERC20 tokens that return false instead of reverting on failure.

Refactor the `_lock` function as follows:

1. Import the SafeERC20 library:

   ```solidity
   import "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";
   ```

2. Use the `safeTransferFrom` method:
   ```solidity
   if (_tokenContract != address(0)) {
       IERC20 token = IERC20(_tokenContract);
       SafeERC20.safeTransferFrom(token, _tokenOwner, address(this), _quantity);
   }
   ```

This change ensures that the transfer will revert if it fails, thereby maintaining the contract's integrity and preventing potential issues arising from failed token transfers.

By implementing `safeTransferFrom`, you safeguard against the risks associated with tokens that do not revert on failure, ensuring that the `_lock` function operates as intended and only proceeds when tokens are successfully transferred.
