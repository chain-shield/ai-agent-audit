# Vulnerability details

## Impact
An attacker can call `lockOnBehalf` to extend the user's lockout time before the user is about to be unlocked. The `lockOnBehalf` function does not limit the minimum number of lockouts, so an attacker can spend 1wei of tokens at a time to continually extend the user's lockout time.

## Proof of Concept
When `_lock` function is called, `lockedToken.unlockTime` will be extended:
```solidity
lockedToken.lastLockTime = uint32(block.timestamp);
        lockedToken.unlockTime =
            uint32(block.timestamp) +
            uint32(_lockDuration);
```
In `unlock` function, a check is performed on `lockedToken.unlockTime`:
```solidity
if (lockedToken.unlockTime > uint32(block.timestamp))
            revert TokenStillLockedError();
```
So an attacker can keep calling `lockOnBehalf` to extend the lock time, and the user's locked token will never be able to be unlocked.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Consider setting a minimum number of locked tokens in `_lock` function.
