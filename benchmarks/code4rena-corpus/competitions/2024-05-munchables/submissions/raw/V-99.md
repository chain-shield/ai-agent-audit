# Vulnerability details

## Impact

Impact is HIGH. This issue could potentially lead to loss of funds and can make a user unable to unlock their locked tokens.

## Proof of Concept

For the scope of this audit, the [README](https://github.com/code-423n4/2024-05-munchables#general-questions) states that we can assume more tokens can be added for use in `LockManager` in future.

ERC20 token behaviors in scope:
| Question| Answer|
|-|-|
|Doesn't revert on failure|	Yes|

In the `LockManager.sol` contract, the `transferFrom` and transfer function is used without checking its return value:

```solidity
IERC20 token = IERC20(_tokenContract);
token.transferFrom(_tokenOwner, address(this), _quantity);
```

```solidity
 // send token
        if (_tokenContract == address(0)) {
            payable(msg.sender).transfer(_quantity);
        } else {
            IERC20 token = IERC20(_tokenContract);
            token.transfer(msg.sender, _quantity);
        }
```


Now, `ZRX` is a token that fits these conditions and can theoretically be used in `LockManager` as a principal token. https://coinmarketcap.com/dexscan/ethereum/0xfa97aa5002124fe7edd36584628300e8d81df042/

ZRX is a token that does not revert on failure, instead it simply returns a bool value that is not checked.

If `_tokenContract` is a token that does not revert on failure, this call could fail silently, allowing the rest of the function to execute as if the transfer were successful.

Similarly, `BNB` just like ZRX does not revert on failure, instead it simply returns a bool value that is not checked too: https://etherscan.io/token/0xB8c77482e45F1F44dE1745F52C74426C631bDD52



Now in the current scope, Unsafe transfers are used in [_lock](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L376) and [unlock](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L420-L423) functions.

Since these attempts to transfer could silently fail, this then leads to multiple scenarios like:

- Loss of Funds: If a user attempts to lock tokens using a token that does not revert on failure, and the transferFrom operation fails silently, the user might still believe their tokens are successfully locked. Albeit, due to the lack of actual token transfer, the user's tokens would not be properly recorded in the contract's state. This could lead to the user losing access to their tokens indefinitely, as the contract would not recognize them as being locked.

- Incorrect Rewards Calculation: The LockManager contract [calculates rewards](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L341) based on the amount of tokens locked and the duration of the lock. If the token transfer fails but the contract proceeds as if it succeeded, the reward calculations could be skewed, resulting in users receiving less than what they are entitled to.

- Inability to Unlock Tokens: Since the contract relies on accurate tracking of locked tokens to facilitate unlocking, a failed transfer could mean that the contract's state does not reflect the user's intention to lock tokens. Consequently, the user might find themselves unable to unlock their tokens, effectively leading to loses.


## Tools Used
Manual review

## Recommended Mitigation Steps:

Ensure that the return value of `transferFrom` is always checked, and the transaction is reverted if the transfer fails Or use openzeppelin's `SafeERC20`'s library
