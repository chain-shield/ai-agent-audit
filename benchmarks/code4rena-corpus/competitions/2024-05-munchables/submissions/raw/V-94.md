# Vulnerability details

## Impact
The LockManager contract, as currently implemented, does not account for the native rebasing features of  USDB on the Blast network. This is a gateway to inaccuracies in tracking locked token balances and missed opportunities for optimizing yield accrual for locked tokens. Specifically, the contract fails to adjust locked balances in response to rebasing events, does not consider the dynamic nature of rebasing token balances during lock/unlock operations, and overlooks the integration of yield management strategies compatible with Blast's rebasing features. Native yield reward tokens in ERC20 such as WETHRebasing/USDB rewards will be lost.

Read more here:
- https://metalayerlabs.mintlify.app/building/guides/weth-yield
- https://metalayerlabs.mintlify.app/about-blast#how-blast-works

## Proof of Concept

### Adjusting Locked Balances
LockManager does not have mechanisms to adjust the recorded balances of locked tokens in response to rebasing events. This can cause discrepancies between the contract's recorded balances and the actual balances of rebasing tokens (ETH, USDB).

### Interactions with Rebasing Tokens
The contract assumes static token balances during lock/unlock operations, which contradicts the dynamic balance adjustments inherent to rebasing tokens on Blast.

```solidity
function lock(
    address _tokenContract,
    uint256 _quantity
) external payable notPaused onlyActiveToken(_tokenContract) onlyConfiguredToken(_tokenContract) nonReentrant {
    _lock(_tokenContract, _quantity, msg.sender, msg.sender);
}

function unlock(
    address _tokenContract,
    uint256 _quantity
) external notPaused nonReentrant {
    LockedToken storage lockedToken = lockedTokens[msg.sender][_tokenContract];
    if (lockedToken.quantity < _quantity)
        revert InsufficientLockAmountError();
    if (lockedToken.unlockTime > uint32(block.timestamp))
        revert TokenStillLockedError();

    // force harvest to make sure that they get the schnibbles that they are entitled to
    accountManager.forceHarvest(msg.sender);

    lockedToken.quantity -= _quantity;

    // send token
    if (_tokenContract == address(0)) {
        payable(msg.sender).transfer(_quantity);
    } else {
        IERC20 token = IERC20(_tokenContract);
        token.transfer(msg.sender, _quantity);
    }

    emit Unlocked(msg.sender, _tokenContract, _quantity);
}
```

### Yield Accrual and Token Operations
The automatic yield accrual from rebasing tokens presents an opportunity for users to earn yield on their locked tokens. However, the LockManager does not explicitly account for or utilize the rebasing features to maximize yield for locked tokens. This could result in a missed opportunity to enhance the value proposition for users engaging with locking mechanisms on Blast.

## Recommended Mitigation Steps:
The dev team should consider Integrating functionality to regularly check and adjust the recorded balances of locked rebasing tokens to reflect the current actual balances. This can be fixed by listening for rebasing events or periodically recalculating locked balances based on the current actual balances on Blast.

Also consider incorporate logic to manage the yield modes of WETH and USDB for locked tokens, leveraging Blast's capability to configure tokens for automatic yield, void, or claimable yield modes. This would allow the contract to optimize yield accrual strategies for the benefit of users and the contract itself.
