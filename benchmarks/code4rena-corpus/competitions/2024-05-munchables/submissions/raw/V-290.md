# Vulnerability details

## Impact
In the `onlyConfiguredToken` modifier ([lines 47-51](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L47-L51)), the condition checks if the `nftCost` of the configured token is zero. If it is zero, the modifier reverts with the `TokenNotConfiguredError`. However, this condition may not be sufficient to determine if a token is configured or not.

A token could be considered "configured" even if its `nftCost` is zero, as long as other properties like `usdPrice` or active are set. By checking only the `nftCost`, the modifier may incorrectly revert for tokens that are configured but have a zero `nftCost`.

## Proof of Concept
The issue with the `onlyConfiguredToken` modifier is that it relies solely on the `nftCost` field of the `ConfiguredToken` struct to determine if a token is configured or not. This approach may lead to unintended behavior and incorrect reverts in certain scenarios.

**The `ConfiguredToken` Struct**
```solidity
struct ConfiguredToken {
    uint256 usdPrice;
    uint256 nftCost;
    bool active;
    uint8 decimals;
}
```
The `ConfiguredToken` struct represents the configuration data for a token, including its USD price, NFT cost, active state, and decimal places.

**The `configuredTokens` Mapping:** [src/managers/LockManager.sol#20](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L20)
```solidity
mapping(address => ConfiguredToken) public configuredTokens;
```
The `configuredTokens` mapping stores the `ConfiguredToken` struct for each configured token contract address.

**The `onlyConfiguredToken` Modifier:** [src/managers/LockManager.sol#L47-L51](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L47-L51)
```solidity
modifier onlyConfiguredToken(address _tokenContract) {
    if (configuredTokens[_tokenContract].nftCost == 0)
        revert TokenNotConfiguredError();
    _;
}
```
The `onlyConfiguredToken` modifier checks if the `nftCost` field of the `ConfiguredToken` struct for the given `_tokenContract` address is zero. If it is zero, the modifier reverts with the `TokenNotConfiguredError`.

**Impact**
The issue with this approach is that a token could be considered "configured" even if its `nftCost` is zero, as long as other properties like `usdPrice` or active are set. By checking only the `nftCost` field, the modifier may incorrectly revert for tokens that are configured but have a zero `nftCost`.

For example, consider the following scenario:

An admin configures a token with the following values:
```solidity
configuredTokens[tokenAddress] = ConfiguredToken({
    usdPrice: 1000000000000000000, // 1 USD
    nftCost: 0, // No NFT cost
    active: true,
    decimals: 18
});
```
Later, when a function that uses the `onlyConfiguredToken` modifier is called with the `tokenAddress`, the modifier will revert with the `TokenNotConfiguredError` because the `nftCost` is zero, even though the token is considered configured with a valid USD price and active state.

This behavior could lead to unexpected reverts and prevent legitimate operations from being executed, potentially causing issues in the contract's functionality.

## Recommended Mitigation Steps
Modify the condition in the `onlyConfiguredToken` modifier to check if the entire `configuredTokens[_tokenContract]` struct is empty or has some default values, rather than checking only the `nftCost` field.
```solidity
if (configuredTokens[_tokenContract].usdPrice == 0 && configuredTokens[_tokenContract].active == false)
    revert TokenNotConfiguredError();
```
This condition checks if both `usdPrice` and `active` fields are set to their default values (0 and false, respectively), indicating that the token is not configured.
