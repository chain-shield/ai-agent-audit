# Vulnerability details

## Impact
For the calculation of the `numberNFTs` variable in the following lines: [src/managers/LockManager.sol#L363-L364](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L363-L364)
```solidity
remainder = quantity % configuredToken.nftCost;
numberNFTs = (quantity - remainder) / configuredToken.nftCost;
```
The problem is that the calculation of `numberNFTs` does not consider the case where the `remainder` is greater than zero. In such a scenario, the user should still receive an additional NFT, but the current implementation would not account for that.

For example, let's assume `quantity` is 101 and `configuredToken.nftCost` is 100. The calculation would result in

`remainder = 1`
`numberNFTs = (101 - 1) / 100 = 1`

However, the correct number of NFTs that should be minted is 2 (one for the full 100 units and another for the remaining 1 unit).

When a user locks tokens, the contract calculates the number of NFTs they should receive based on the locked quantity and the configured `nftCost`. However, the current implementation fails to account for cases where the locked quantity is not an exact multiple of the `nftCost`.

For example, let's assume the `nftCost` is set to 100 tokens. If a user locks 201 tokens, the correct number of NFTs they should receive is 3 (2 for the first 200 tokens, and 1 for the remaining 1 token). However, the current implementation would only grant them 2 NFTs, as shown in the following code snippet:
```solidity
uint256 quantity = 201;
uint256 nftCost = 100;

uint256 remainder = quantity % nftCost; // remainder = 1
uint256 numberNFTs = (quantity - remainder) / nftCost; // numberNFTs = 2 (incorrect)
```
This issue can lead to users losing value, as they would be entitled to more NFTs than they actually receive.

## Proof of Concept
Let's consider the following test case:
```solidity
import "forge-std/Test.sol";

contract LockManagerTest is Test {
    function testNFTCalculation() public {
        uint256 quantity = 201;
        uint256 nftCost = 100;

        uint256 remainder = quantity % nftCost; // remainder = 1
        uint256 numberNFTs = (quantity - remainder) / nftCost; // numberNFTs = 2 (incorrect)

        // Correct calculation
        uint256 correctNumberNFTs = (quantity + nftCost - 1) / nftCost; // correctNumberNFTs = 3

        assertEq(numberNFTs, 2); // Fails, expected 3
        assertEq(correctNumberNFTs, 3); // Passes
    }
}
```
In this test case, we simulate the scenario where a user locks 201 tokens, and the `nftCost` is set to 100. The current implementation calculates `numberNFTs` as 2, which is incorrect. The correct calculation should be 3, as demonstrated by the `correctNumberNFTs` variable.

When running this test, the first assertion (`assertEq(numberNFTs, 2)`) will fail, indicating that the current implementation is incorrect. The second assertion (`assertEq(correctNumberNFTs, 3)`) will pass, confirming that the correct calculation should yield 3 NFTs for a locked quantity of 201 tokens with an `nftCost` of 100.

## Recommended Mitigation Steps
Should modify the calculation of `numberNFTs` as follows
```solidity
remainder = quantity % configuredToken.nftCost;
numberNFTs = (quantity / configuredToken.nftCost) + (remainder > 0 ? 1 : 0);
```
This way, if there is a non-zero remainder, an additional NFT will be minted to account for the remaining units.

Alternatively, you could use integer division and round up the result
```solidity
numberNFTs = (quantity + configuredToken.nftCost - 1) / configuredToken.nftCost;
```
This approach ensures that any non-zero remainder will result in an additional NFT being minted.
