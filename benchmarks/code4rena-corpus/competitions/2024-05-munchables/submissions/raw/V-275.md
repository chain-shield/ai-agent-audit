# Vulnerability details

## Impact
Users looking to utilize the remainder of their deposited balance or whole balance on the next deposit with a lock duration meeting lockdrop or more days do not get minted NFTs for their locked tokens hence, forfeiting any points that should have been claimed by feeding their Munchables.

## Proof of Concept

Two test cases below where the lock duration is 1 day and another where the lock duration is 4 days. Both users deposit the same total ethers (3), only user A gets minted 3 Munchables NFT and thus can feed, earn points, or claim whereas user B cannot do any of the above three things because they do not get minted Munchables in the first place and trying to reveal NFTs reverts for user B.

This issue stems from the way the lock drop is configured.

- Suppose a lockdrop of 3 days ensues
- User registers and sets their lockup duration to 4 days
- Users ideally can lock for up to 90 days which is the current maximum lock duration
- The user deposits 0.5 ether today and has no more ether to make the deposit whole because maybe they get 0.5 ether in 4 days from another protocol
- It's now the 4th day, the user deposits another 0.5 ether and meets the NFT mint cost of 1 ether because their previously logged remainder of 0.5 ether plus the new lock of 0.5 ether equals 1 ether
- The user doesn't get minted any Munchables NFT hence have just wasted the entire time since the first lock 4 days ago.
- Even though they did lock up tokens for the current lock drop, the user doesn't get any Munchables NFT and cannot perform all the crucial protocol functionalities like earning points from feeding such tokens, NFT reveals, etc.

```solidity
function test_lockAt3DayBelow() public {
        uint256 lockAmount = 9e17;

        console.log("Beginning run()");
        deployContracts();

        // register me
        amp.register(MunchablesCommonLib.Realm(3), address(0));
        logSnuggery("Initial snuggery");

        // lock tokens
        lm.lock{value: lockAmount}(address(0), lockAmount);
        
        lm.setLockDuration(1 days);

        logPlayer("Player after lock");
        logLockedTokens("After First Lock");

        uint256 unlockTime = block.timestamp + 1 days;
        console.log("Warping to", unlockTime);

        vm.warp(unlockTime);
        console.log("Warped to:", block.timestamp);
        
        lm.lock{value: 1e17}(address(0), 1e17);
        logPlayer("Player after relock");
        logLockedTokens("After Lock additional 0.1 ETH");

        lm.lock{value: 1e18}(address(0), 1e18);
        logPlayer("Player after relock");
        logLockedTokens("After Lock additional 10 ETH");

        lm.lock{value: 1e18}(address(0), 1e18);
        logPlayer("Player after relock");
        logLockedTokens("After Lock additional 10 ETH");

        uint16 unrevealedNFTs = nfto.getUnrevealedNFTs(address(this));
        console.log("Unrevealed NFTs:", unrevealedNFTs);

        // check balance of this contract in NFT
        uint256 nftBalance = IERC721(address(nft)).balanceOf(address(this));
        console.log("NFT Balance: ", nftBalance);

        // claim a primordial
        pm.claimPrimordial();
        logSnuggery("Snuggery after primordial claim");

        // reveal 1 nft
        nfto.startReveal();

        uint256 unrevealedNFTsOne = nfto.getUnrevealedNFTs(address(this));
        console.log("Unrevealed NFTs after claim primordial:", unrevealedNFTsOne);
    }
```

## Recommended Mitigation Steps
The utilization of a remainder is great but the lock drop is not configured to handle the above case. One way to ensure users locking up can mint NFT during the lock drop regardless is to still mint NFT to them as long as they initially deposited during the lock drop phase
