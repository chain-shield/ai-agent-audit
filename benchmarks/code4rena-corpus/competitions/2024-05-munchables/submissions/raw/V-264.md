# Vulnerability details

## Impact
Using a fee-on-transfer token in the _lock function can cause issues in several parts of the code.

## Proof of Concept
In the contest page, we can see that ERC20 used by the protocol are ```USDB, WETH, (assume we can add more to the future for use in LockManager)``` and under ```ERC20 token behaviors in scope``` we see that ```fee on transfer``` tokens are in scope which means that fee on transfer tokens will be used in the future.

However, using a fee-on-transfer token in the _lock function can cause issues in several parts of the code.

https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L311-L398

```solidity
    function _lock(
        address _tokenContract,
        uint256 _quantity,
        address _tokenOwner,
        address _lockRecipient
    ) private {
        (
            address _mainAccount,
            MunchablesCommonLib.Player memory _player
        ) = accountManager.getPlayer(_lockRecipient);
        if (_mainAccount != _lockRecipient) revert SubAccountCannotLockError();
        if (_player.registrationDate == 0) revert AccountNotRegisteredError();
        // check approvals and value of tx matches
        if (_tokenContract == address(0)) {
            if (msg.value != _quantity) revert ETHValueIncorrectError();
        } else {
            if (msg.value != 0) revert InvalidMessageValueError();
            IERC20 token = IERC20(_tokenContract);
            uint256 allowance = token.allowance(_tokenOwner, address(this));
            if (allowance < _quantity) revert InsufficientAllowanceError();
        }

        LockedToken storage lockedToken = lockedTokens[_lockRecipient][
            _tokenContract
        ];
        ConfiguredToken storage configuredToken = configuredTokens[
            _tokenContract
        ];

        // they will receive schnibbles at the new rate since last harvest if not for force harvest
        accountManager.forceHarvest(_lockRecipient);

        // add remainder from any previous lock
        uint256 quantity = _quantity + lockedToken.remainder;
        uint256 remainder;
        uint256 numberNFTs;
        uint32 _lockDuration = playerSettings[_lockRecipient].lockDuration;

        if (_lockDuration == 0) {
            _lockDuration = lockdrop.minLockDuration;
        }
        if (
            lockdrop.start <= uint32(block.timestamp) &&
            lockdrop.end >= uint32(block.timestamp)
        ) {
            if (
                _lockDuration < lockdrop.minLockDuration ||
                _lockDuration >
                uint32(configStorage.getUint(StorageKey.MaxLockDuration))
            ) revert InvalidLockDurationError();
            if (msg.sender != address(migrationManager)) {
                // calculate number of nfts
                remainder = quantity % configuredToken.nftCost;
                numberNFTs = (quantity - remainder) / configuredToken.nftCost;

                if (numberNFTs > type(uint16).max) revert TooManyNFTsError();

                // Tell nftOverlord that the player has new unopened Munchables
                nftOverlord.addReveal(_lockRecipient, uint16(numberNFTs));
            }
        }

        // Transfer erc tokens
        if (_tokenContract != address(0)) {
            IERC20 token = IERC20(_tokenContract);
            token.transferFrom(_tokenOwner, address(this), _quantity);
        }

        lockedToken.remainder = remainder;
        lockedToken.quantity += _quantity;
        lockedToken.lastLockTime = uint32(block.timestamp);
        lockedToken.unlockTime =
            uint32(block.timestamp) +
            uint32(_lockDuration);

        // set their lock duration in playerSettings
        playerSettings[_lockRecipient].lockDuration = _lockDuration;

        emit Locked(
            _lockRecipient,
            _tokenOwner,
            _tokenContract,
            _quantity,
            remainder,
            numberNFTs,
            _lockDuration
        );
    }
```
Let's understand the issues:
https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L327-L330
  ```solidity
  IERC20 token = IERC20(_tokenContract);
  uint256 allowance = token.allowance(_tokenOwner, address(this));
  if (allowance < _quantity) revert InsufficientAllowanceError();
```
The allowance check is used to ensure that the ```_lock``` function can transfer ```_quantity``` tokens from the ```_tokenOwner``` to the contract. But with fee on transfer token, the actual amount transferred to the contract will be less than ```_quantity``` due to the fee. 

https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L376
```solidity
token.transferFrom(_tokenOwner, address(this), _quantity);
```
Here, with a fee-on-transfer token, the actual amount received by the contract will be less than the ```_quantity```. This difference is not accounted for in the function, leading to incorrect assumptions about the received amount.

https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L380
```solidity
lockedToken.quantity += _quantity;
```
Here, the function updates the ```lockedToken.quantity``` by ```_quantity```. Because the actual amount received is less than the ```_quantity```, this will incorrectly inflate the ```lockedToken.quantity```, leading to a mismatch between the recorded locked amount and the actual tokens held by the contract.

## Tools Used
Manual Review
## Recommended Mitigation Steps
Add the following code to handle fee on transfer tokens in the ```_lock``` function.
```solidity
 // Calculate the initial balance
        uint256 initialBalance = token.balanceOf(address(this));
        
        // Transfer tokens and calculate the actual received amount
        token.transferFrom(_tokenOwner, address(this), _quantity);
        uint256 finalBalance = token.balanceOf(address(this));
        uint256 actualReceivedAmount = finalBalance - initialBalance;

        // Use actualReceivedAmount instead of _quantity
        _quantity = actualReceivedAmount;

```
