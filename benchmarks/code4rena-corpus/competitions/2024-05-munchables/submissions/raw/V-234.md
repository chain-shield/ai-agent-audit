# Vulnerability details

## Impact
Protocol not supporting fee-on-transfer token

## Proof of Concept
In contest page it has a section which is `ERC20 token behaviors in scope`
there it mentioned that `Fee on transfer  =  Yes`

But user functions like `lock()` & `unlock()` which call `_lock()` and `unlock()` does not have any code to support this.

Above 2 just doing regular `ERC20` and `ETH` transfer.
`_lock()` has
```solidity
        if (_tokenContract != address(0)) {
            IERC20 token = IERC20(_tokenContract); 
            token.transferFrom(_tokenOwner, address(this), _quantity); 
        }
```
https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L390-L393

`unlock()` has
```solidity
        // send token
        if (_tokenContract == address(0)) {
            payable(msg.sender).transfer(_quantity); 
        } else {
            IERC20 token = IERC20(_tokenContract);
            token.transfer(msg.sender, _quantity);         }
```
Which is clearly shows fee on transfer token no considered here, If fee-on-tranfer token Used in curent implementation then end user will suffer as there will not enough fund for him to withdraw

## Tools Used
Manual Review

## Recommended Mitigation Steps
Classic way to support fee-on-transfer is to track before and after balance on every deposit and adjust User's deposited quantity variable according to difference in after and before value.
