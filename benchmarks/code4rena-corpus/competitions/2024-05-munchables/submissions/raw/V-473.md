# Vulnerability details

## Impact
A malicious user can exploit ```lockOnBehalf()``` to continuously the lock of another user fund by simply depositing dust amount of token. 

User funds could be permanently locked away as long as the attacker wants.

## Proof of Concept
1. Bob creates a lock and increased duration to maxDuration.
2. Bob is 5mins away from unlocking funds.
3. Alice calls ```lockOnBehalf()``` with one Wei and Bod address as the ```lockRecipient```

```solidity
    function lockOnBehalf(
        address _tokenContract,
        uint256 _quantity,
        address _onBehalfOf
    )
        external
        payable
        notPaused
        onlyActiveToken(_tokenContract)
        onlyConfiguredToken(_tokenContract)
        nonReentrant
    {
        address tokenOwner = msg.sender;
        address lockRecipient = msg.sender;
        if (_onBehalfOf != address(0)) {
            lockRecipient = _onBehalfOf;
        }

        _lock(_tokenContract, _quantity, tokenOwner, lockRecipient);
    }
```
4. Bob lockDuration is looked up and ```unlockTime``` is extended with ```lockDuration``` to start another cycle.
```solidity
...
 uint32 _lockDuration = playerSettings[_lockRecipient].lockDuration;
...
 lockedToken.unlockTime =
            uint32(block.timestamp) +
            uint32(_lockDuration);
```

## Tools Used
Manual review. 

## Recommended Mitigation Steps
Map locks to different unlockTime.
1. User token locks should be an array.
2. ArrayIndex should then be mapped to unLockTime.
