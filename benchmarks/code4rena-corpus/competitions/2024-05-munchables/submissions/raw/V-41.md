# Vulnerability details

## Impact
According to Documentation, 

```
the lockdrop period refers to a specific timeframe 
during which participants can lock up their tokens 
to receive rewards and benefits.

[...]

2. Locking Tokens During the Lockdrop: When tokens 
are locked using the lock function, the contract 
checks if the current timestamp is within the lockdrop 
period defined by the start and end times. If it is, 
and the lock duration meets the specified minimum and 
maximum durations, the tokens are successfully locked.

[...]

This mechanism allows the LockManager to handle token 
locks securely and according to the predefined rules 
of the lockdrop period, ensuring that participants can 
only lock their tokens during the specified timeframe 
and under the correct conditions.
```

However, outside the lockdrop timeframe, is still possible to lock tokens without receiving any NFT. This leads to loss of funds by players who are not aware that the lockdrop timeframe is closed.

## Proof of Concept
The [_lock() method](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L311-L398) can be called through the [lock() method](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L296-L309) by a player who would lock his/her funds and mint munchables.

This function can be called, according to documentation, only during the lockdrop timeframe. To assert this, there is a check inside [LockManager.sol#L352-L355](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L352-L355):

```
LockManager.sol#L352-L355

352      if (
353        lockdrop.start <= uint32(block.timestamp) &&
354        lockdrop.end >= uint32(block.timestamp)
355      ) {
```

However, if this check is not satisfied, the function doesn't revert: it continues with lines [LockManager.sol#L373-L397](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L373-L397). In particular, it executes lines [LockManager.sol#L373-L377](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L373-L377):

```
LockManager.sol#L373-L377

373      // Transfer erc tokens
374      if (_tokenContract != address(0)) {
375        IERC20 token = IERC20(_tokenContract);
376        token.transferFrom(_tokenOwner, address(this), _quantity);
377      }
```

i.e., it transfers token from the player to this contract (or eth, because the `lock()` method is `payable`).

Even if the issue is due to a wrong behavior of the player, the documentation states that this behavior shouldn't be possible. Furthermore, developers disabled the `receive()` method ([LockManager.sol#L93-L95](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L93-L95)) and this fact is a clue that they don't want to receive undeserved funds to this contract.
Because this issue leads to losses of player's funds, we report it as High. Because `lockdrop.start` and `lockdrop.end` are `uint32`, we want to stress that a player could lose his/her funds because his/her transaction has been processed 1 second after the end of the lockdrop timeframe.
