# Vulnerability details

## Impact
The `approveUSDPrice` function is responsible for allowing authorized price feed addresses to approve a proposed USD price update. However, due to the `_usdProposalId` is not explicitly defined or passed as a parameter to the function. It seems to be an internal variable or state variable that is not shown in the code snippet, once a proposal is approved and executed (or removed), the contract may become unable to accept new proposals. However, the function checks if the caller has already approved the proposal using the following line: [LockManager.sol#L194-L195](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L194-L195)
```solidity
if (usdUpdateProposal.approvals[msg.sender] == _usdProposalId)
    revert ProposalAlreadyApprovedError();
```
The problem is that if the `_usdProposalId` is not reset or updated after a proposal is executed or removed, this check may fail even for a new proposal. For example, if a previous proposal was approved, and the `_usdProposalId` was not reset, the next time a new proposal is made, the function will revert with the `ProposalAlreadyApprovedError` for any caller who had approved the previous proposal.

## Proof of Concept
Let's assume the following sequence of events:

a. A new USD price proposal is made by calling `proposeUSDPrice`. Let's say the `_usdProposalId` is set to 1 internally.
b. One or more authorized price feed addresses call `approveUSDPrice` and approve the proposal with `_usdProposalId` equal to `1`.
c. The proposal is either executed (if enough approvals are received) or removed (if enough disapprovals are received).
d. However, the `_usdProposalId` is not reset or updated after the proposal is executed or removed.

Now, when a new proposal is made by calling `proposeUSDPrice` again, the `_usdProposalId` is still set to `1`. When an authorized price feed address tries to call `approveUSDPrice` for the new proposal, the following check will fail: [/LockManager.sol#L194-L195](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L194-L195)
```solidity
if (usdUpdateProposal.approvals[msg.sender] == _usdProposalId)
    revert ProposalAlreadyApprovedError();
```
This is because `usdUpdateProposal.approvals[msg.sender]` is still set to `1` (from the previous proposal), and `_usdProposalId` is also `1`. Therefore, the function will revert with the `ProposalAlreadyApprovedError` for any authorized price feed address that had approved the previous proposal.

Referenced Code: The relevant code snippet is:
```solidity
if (usdUpdateProposal.approvals[msg.sender] == _usdProposalId)
    revert ProposalAlreadyApprovedError();
```
This check is intended to prevent an authorized price feed address from approving the same proposal multiple times. However, due to the lack of proper management of the `_usdProposalId`, it can inadvertently prevent new proposals from being approved.

## Recommended Mitigation Steps
The `_usdProposalId` should be reset or updated after a proposal is executed or removed. This could be done by introducing a new state variable to track the current proposal ID or by resetting the `_usdProposalId` to a default value (e.g., 0) when a proposal is executed or removed.

Alternatively, instead of using a separate `_usdProposalId`, the function could check if the `usdUpdateProposal.approvals[msg.sender]` is equal to the `usdUpdateProposal.proposedPrice`, which would ensure that the check is specific to the current proposal.
