# Vulnerability details

## Impact
`_execUSDPriceUpdate` does not handle the case where the `usdUpdateProposal` is not approved. The function only executes the update logic if the following condition is met: [src/managers/LockManager.sol#L507-L510](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L507-L510)
```solidity
if (
    usdUpdateProposal.approvalsCount >= APPROVE_THRESHOLD &&
    usdUpdateProposal.disapprovalsCount < DISAPPROVE_THRESHOLD
)
```
If this condition is not met, the function will simply exit without executing the update logic or resetting the `usdUpdateProposal` struct. This means that if the proposal is not approved, the `usdUpdateProposal` struct will remain in its current state, potentially leading to stale or inconsistent data.

## Proof of Concept
Not handling the case where the `usdUpdateProposal` is not approved can lead to stale or inconsistent data in the contract's state.

**Stale Proposal Data**: If the proposal is not approved, the `usdUpdateProposal` struct will retain its current state, including the proposer address, the `proposedPrice`, the contracts array, and the approvals and disapprovals mappings. This means that the next time a new proposal is made, the struct will still contain data from the previous proposal, leading to confusion or incorrect behavior.

**Incorrect Approvals and Disapprovals**: The approvals and disapprovals mappings in the `usdUpdateProposal` struct keep track of which addresses have approved or disapproved the current proposal. If the proposal is not approved and these mappings are not reset, they could lead to incorrect behavior when a new proposal is made. For example, an address that disapproved the previous proposal might be incorrectly counted as having disapproved the new proposal, even though they haven't explicitly done so.

**Inconsistent State**: By not resetting the `usdUpdateProposal` struct when a proposal is not approved, the contract's state can become inconsistent. The struct may contain a mix of data from the current proposal and previous proposals, making it difficult to reason about the contract's behavior and potentially leading to unexpected issues or vulnerabilities.

## Recommended Mitigation Steps
To handle the case where the proposal is not approved, consider adding an `else` block to reset or clear the `usdUpdateProposal` struct. This would ensure that the `struct` is in a clean state for the next proposal.
```solidity
function _execUSDPriceUpdate() internal {
    if (
        usdUpdateProposal.approvalsCount >= APPROVE_THRESHOLD &&
        usdUpdateProposal.disapprovalsCount < DISAPPROVE_THRESHOLD
    ) {
        // Execute the update logic as before
        // ...
        delete usdUpdateProposal;
    } else {
        // Proposal not approved, reset the usdUpdateProposal struct
        delete usdUpdateProposal;
    }
}
```
By adding this `else` block, you ensure that the `usdUpdateProposal` struct is reset regardless of whether the proposal is approved or not. This can help maintain data consistency and prevent potential issues caused by stale or inconsistent data in the struct.
