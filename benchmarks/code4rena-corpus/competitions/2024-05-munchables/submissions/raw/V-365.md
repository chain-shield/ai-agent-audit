# Vulnerability details

## Impact
In the audit page of the contest it is stated by the protocol team that we can assume that they will add additional tokens and additionally they have marked the rebasing token behaviour in scope for the contest. 

However, there is no implemented support for rebasing tokens in the protocol. 

## Proof of Concept
The problem is that the `lock()` function does not account for ERC20 tokens that are inflationary/deflationary. So let's say the user sends 20 tokens but after some time they are equal only to 18. The protocol will still account the 20 tokens instead of the 18.

We can see this here:
https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L311

```solidity
 function _lock(address _tokenContract, uint256 _quantity, address _tokenOwner, address _lockRecipient) private {
      
        ...

>>      if (_tokenContract != address(0)) {
            IERC20 token = IERC20(_tokenContract);
            token.transferFrom(_tokenOwner, address(this), _quantity);
        }


        lockedToken.remainder = remainder;
>>      lockedToken.quantity += _quantity;
        lockedToken.lastLockTime = uint32(block.timestamp);
        lockedToken.unlockTime = uint32(block.timestamp) + uint32(_lockDuration);

        playerSettings[_lockRecipient].lockDuration = _lockDuration;

        emit Locked(_lockRecipient, _tokenOwner, _tokenContract, _quantity, remainder, numberNFTs, _lockDuration);
    }

```
This will lead to unexpected behaviour and loss of funds to the protocol because when a user calls `unlock()` the protocol will send 20 tokens back to him instead of 18

## Tools Used
Manual Analysis
## Recommended Mitigation Steps
You can either explicitly document that you do not support tokens with rebasing mechanism or you can do the following:

For rebasing tokens, when they go down in value, you should have a method to update the cached reserves accordingly, based on the balance held. This is a complex solution.
For rebasing tokens, when they go up in value, you should add a method to actually transfer the excess tokens out of the protocol.
