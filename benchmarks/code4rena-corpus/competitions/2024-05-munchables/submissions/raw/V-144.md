# Vulnerability details

## Impact

When locking tokens on behalf of another address, the [lockOnBehalf](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L275C4-L294C6) function uses the token approval of the caller (`msg.sender`) instead of the approval of the intended lock recipient (`_onBehalfOf`). This means that if the caller has an approved allowance, for the token, they can lock tokens on behalf of any other address without their explicit permission.

This issue could lead to unexpected and unauthorized token locks, potentially causing consistent inconveniences and financial loss for the affected users.

## Proof of Concept

Here's the code highlighting the affected part of [function lockOnBehalf()](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L275C4-L294C6):

```solidity
function lockOnBehalf(
    address _tokenContract,
    uint256 _quantity,
    address _onBehalfOf
)
    external
    payable
    notPaused
    onlyActiveToken(_tokenContract)
    onlyConfiguredToken(_tokenContract)
    nonReentrant
{
    address tokenOwner = msg.sender;
    address lockRecipient = msg.sender;
    if (_onBehalfOf != address(0)) {
        lockRecipient = _onBehalfOf;
    }

    _lock(_tokenContract, _quantity, tokenOwner, lockRecipient);
}
```

Wherein the issue lies, is in the fact that the [_lock()](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L311) function is called with [`tokenOwner` set to `msg.sender` instead of `_onBehalfOf`](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L287C1-L291C10). This means that the token approval is checked against the caller's allowance rather than the intended lock recipient's allowance.

To demonstrate this issue, consider this:
1. Alice approves the LockManager contract to transfer 1000 tokens on her behalf.
2. Alice calls `lockOnBehalf` with `_onBehalfOf` set to Bob's address and `_quantity` set to 500 tokens.
3. The LockManager contract locks 500 tokens on behalf of Bob, even though Bob didn't approve the transfer.

Here's a TS test that verifies this:

```typescript
describe("when using lockOnBehalf", () => {
  beforeEach(async () => {
    await testClient.setBalance({
      address: bob,
      value: parseEther("10"),
    });
  });

  it("should lock token for other player", async () => {
    const { request } = await testContracts.lockManager.contract.simulate.lockOnBehalf(
      [zeroAddress, parseEther("1"), alice],
      { account: bob, value: parseEther("1") }
    );
    const txHash = await testClient.writeContract(request);
    await assertLockSuccess({
      testContracts,
      testERC20Contract,
      numberNFTs: 0n,
      player: alice,
      quantity: parseEther("1"),
      lockedQuantity: parseEther("1"),
      remainder: 0n,
      sender: bob,
      tokenContractAddress: zeroAddress,
      txHash,
    });
  });
});
```
- This test can be copied and pasted into the `lock.test.ts` file within the `describe("when using lockOnBehalf", ...)` block to integrate it with the test suite

This test specifically demonstrates how Bob can lock tokens on behalf of Alice without Alice's approval, verifying the unauthorized token locking issue.

## Recommended Mitigation Steps

To mitigate this issue, the `lockOnBehalf` function should be modified to check the token approval of the intended lock recipient (`_onBehalfOf`) instead of the caller (`msg.sender`). Here's the mitigated change:

```solidity
function lockOnBehalf(
    address _tokenContract,
    uint256 _quantity,
    address _onBehalfOf
)
    external
    payable
    notPaused
    onlyActiveToken(_tokenContract)
    onlyConfiguredToken(_tokenContract)
    nonReentrant
{
    address lockRecipient = _onBehalfOf;
    if (lockRecipient == address(0)) {
        lockRecipient = msg.sender;
    }

    _lock(_tokenContract, _quantity, lockRecipient, lockRecipient);
}
```

By passing in `lockRecipient` as both the `_tokenOwner` and `_lockRecipient` arguments to the `_lock` function, we ensure that the token approval is checked against the intended recipient's allowance.
