# Vulnerability details

## Impact
The locking behavior will be locked once the remaining time of the `lockDrop` is less than `minLockDuration`. Currently, no check prevents this happening even from the first second of the lockdrop. 

The admin can configure lockDrop periods with the `configureLockdrop`. It allows the admin to set both the start and end periods as well as the minimum amount of time, which the users can lock for. 

Currently there are checks, which prevent the admin to set lockdrops in unachievable times. For example, you can not set lockdrop in the past, or one, which starts after the end period. 

However, setting a `minLockDuration`, which is bigger than the whole duration of the lockdrop is still possible. That means that, until a new lockdrop period is set, the users won't be able to lock funds in the protocol


## Proof of Concept
1. Admin sets a lockDrop period for 1 day with `minLockDuration` of 1 day and 1 hour
2. Users can't use `lock` as they can't satisfy both the `minLockDuration` and the lockDrop period



## Tools Used
Manual Review

## Recommended Mitigation Steps
Add a check, which will revert if the admin adds unachievable `minLockDuration`
```solidity
if(_lockdropData.end - _lockdropData.start >= _lockdropData.minLockDuration) {
revert LockdropInvalidError();
}
```
