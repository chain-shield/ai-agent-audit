# Vulnerability details

## Impact
In current implementation, both `approveUSDPrice` and `disapproveUSDPrice` are allowed to be called for the same one proposal. 
For `approveUSDPrice`, if `usdUpdateProposal.approvalsCount >= APPROVE_THRESHOLD` is met, `_execUSDPriceUpdate` will be called to [update the price](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L202-L204).
On the other hand, for `disapproveUSDPrice`, if `usdUpdateProposal.disapprovalsCount >= DISAPPROVE_THRESHOLD` is met, the proposal will [be deleted](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L237-L241)

## Proof of Concept
There is an extreme case that those two functions might not work as expected.
Suppose both `usdUpdateProposal.approvalsCount` and `usdUpdateProposal.disapprovalsCount` are 3

1. Role.PriceFeed_1 calls `proposeUSDPrice` to create a proposal, and Role.PriceFeed_2 calls `approveUSDPrice` to approve the proposal
2. Role.PriceFeed_3 and Role.PriceFeed_4 calls `disapproveUSDPrice`
3. now both `usdUpdateProposal.approvalsCount` and `usdUpdateProposal.disapprovalsCount` are 2
4. Role.PriceFeed_5 calls `approveUSDPrice` to approve the proposal, but later it calls `disapproveUSDPrice` to disapprove the **same** proposal
5. If everything works as expected, Role.PriceFeed_5's `approveUSDPrice` will be executed first, and [_execUSDPriceUpdate](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L202-L204) will be executed.
6. But if the re-org happens, `disapproveUSDPrice` will be executed first, and the proposal [will be cleared](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L237-L241)
