# Vulnerability details

## Impact
The current implementation of the _lock function can lead to inaccurate calculations of the number of NFTs to be awarded when locking tokens with different decimals. This discrepancy arises because the function does not normalize token amounts to a consistent decimal scale before performing arithmetic operations. As a result, users might receive an incorrect number of NFTs, potentially undermining the fairness and accuracy of the system.

Proof of Concept (PoC):


Assume two tokens: Token A with 18 decimals and Token B with 6 decimals.
Let configuredToken.nftCost be 1,000,000,000,000,000,000 (1 * 10^18) for Token A and 1,000,000 (1 * 10^6) for Token B.
A user locks 2 * 10^18 units of Token A and 2 * 10^6 units of Token B.
Current Calculation in the Function:

For Token A:
```
numberNFTs = (2 * 10^18 - 0) / 1,000,000,000,000,000,000 = 2
```
For Token B:
```
numberNFTs = (2 * 10^6 - 0) / 1,000,000 = 2
```
Here, the calculations are correct because the decimals match the nftCost.
Potential Issue with Mismatched Decimals:

If the configuredToken.nftCost was not adjusted for token decimals, the calculation could go wrong. For example, if configuredToken.nftCost for Token A was mistakenly set as 1,000,000 (matching Token B's decimal), the calculation would be:
```
numberNFTs = (2 * 10^18 - 0) / 1,000,000 = 2 * 10^12
```
This would result in an erroneously high number of NFTs, illustrating the need for proper normalization.

manual review

## Recommended Mitigation Steps
Normalize token amounts to a common decimal scale before performing calculations to ensure consistency and accuracy
