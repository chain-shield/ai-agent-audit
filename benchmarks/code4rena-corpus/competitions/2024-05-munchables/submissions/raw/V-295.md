# Vulnerability details

## Impact
The line `++_usdProposalId;` increments the `_usdProposalId` before assigning it to the `usdUpdateProposal.approvals[msg.sender]`. This means that if the function is called multiple times by the same sender before any other approvals or disapprovals, the `usdUpdateProposal.approvals[msg.sender]` will be set to different values for each call, potentially leading to incorrect tracking of approvals.

The scenario where the bug can occur:

Sender A calls `proposeUSDPrice` with `_price = 100` and `_contracts = [...]`.
`_usdProposalId` is incremented to 1.
`usdUpdateProposal.approvals[A]` is set to 1.
Sender A calls `proposeUSDPrice` again with `_price = 200` and `_contracts = [...]` before any other approvals or disapprovals.
`_usdProposalId` is incremented to 2.
`usdUpdateProposal.approvals[A]` is set to 2, overwriting the previous value of 1.

Now, if another price feed approves or disapproves the proposal with `_usdProposalId = 1`, it will be associated with the wrong proposal, leading to incorrect tracking of approvals and disapprovals.

## Proof of Concept
[src/managers/LockManager.sol#L164-L170](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L164-L170)

This can lead to incorrect tracking of approvals and disapprovals for USD price proposals, potentially allowing unauthorized price updates or preventing legitimate price updates from being applied.

**Description of the impact and how the bug can manifest**
The `_usdProposalId` is used as a unique identifier to track approvals and disapprovals for each USD price proposal. By incrementing `_usdProposalId` before assigning it to u`sdUpdateProposal.approvals[msg.sender]`, the same sender can end up with different `_usdProposalId` values for the same proposal if they call `proposeUSDPrice` multiple times before any other approvals or disapprovals.

Example:
```solidity
// Sender A proposes a price of 100
proposeUSDPrice(100, [...]);
// _usdProposalId = 1
// usdUpdateProposal.approvals[A] = 1

// Sender A proposes a price of 200 before any other approvals/disapprovals
proposeUSDPrice(200, [...]);
// _usdProposalId = 2
// usdUpdateProposal.approvals[A] = 2 (overwritten)
```
The `approveUSDPrice` and `disapproveUSDPrice` functions rely on the `_usdProposalId` to determine if a sender has already approved or disapproved a proposal. If the `_usdProposalId` is incorrect due to the bug, these functions may incorrectly count approvals or disapprovals, potentially leading to unauthorized price updates or preventing legitimate updates.

**Unauthorized Price Updates** If the approval threshold is reached due to incorrect counting of approvals, an unauthorized price update could be applied. This could have severe consequences, as it could potentially allow malicious actors to manipulate the USD prices used in the contract.

An example of how the bug can lead to an unauthorized price update:
```solidity
// Sender A proposes a price of 100
proposeUSDPrice(100, [...]);
// _usdProposalId = 1
// usdUpdateProposal.approvals[A] = 1

// Sender A proposes a price of 200 before any other approvals/disapprovals
proposeUSDPrice(200, [...]);
// _usdProposalId = 2
// usdUpdateProposal.approvals[A] = 2 (overwritten)

// Price feed B approves the proposal with _usdProposalId = 1 (incorrect due to the bug)
approveUSDPrice(1);

// Price feed C approves the proposal with _usdProposalId = 1 (incorrect due to the bug)
approveUSDPrice(1);

// The approval threshold is reached for the incorrect proposal with _usdProposalId = 1
// The price is updated to 100, even though the intended proposal was for 200
```
This can have severe consequences, as it can lead to unauthorized price updates or prevent legitimate updates, causing the contract to operate with incorrect USD prices.

_It's crucial to fix this by incrementing `_usdProposalId` after assigning it to `usdUpdateProposal.approvals[msg.sender]` to ensure correct tracking of approvals and disapprovals._

## Recommended Mitigation Steps
Should increment `_usdProposalId` after assigning it to `usdUpdateProposal.approvals[msg.sender]`.
```solidity
function proposeUSDPrice(
    uint256 _price,
    address[] calldata _contracts
)
    external
    onlyOneOfRoles(
        [
            Role.PriceFeed_1,
            Role.PriceFeed_2,
            Role.PriceFeed_3,
            Role.PriceFeed_4,
            Role.PriceFeed_5
        ]
    )
{
    if (usdUpdateProposal.proposer != address(0))
        revert ProposalInProgressError();
    if (_contracts.length == 0) revert ProposalInvalidContractsError();

    delete usdUpdateProposal;

    usdUpdateProposal.proposedDate = uint32(block.timestamp);
    usdUpdateProposal.proposer = msg.sender;
    usdUpdateProposal.proposedPrice = _price;
    usdUpdateProposal.contracts = _contracts;
    usdUpdateProposal.approvals[msg.sender] = _usdProposalId;
    usdUpdateProposal.approvalsCount++;

    emit ProposedUSDPrice(msg.sender, _price);

    ++_usdProposalId; // Increment _usdProposalId after assigning it
}
```
By making this change, the `usdUpdateProposal.approvals[msg.sender]` will always be set to the correct `_usdProposalId` value, ensuring accurate tracking of approvals and disapprovals.
