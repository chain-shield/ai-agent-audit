# Vulnerability details

## Impact

According to provided documentation, protocol does not implement any trusted role, which implicitly implies, that every role within the protocol should be treated as a non-trusted:

[File: README.md](https://github.com/code-423n4/2024-05-munchables/blob/main/README.md#all-trusted-roles-in-the-protocol)
```
All trusted roles in the protocol

N/A
```

Moreover, please notice, that each role might contain multiple of addresses (to confirm that, please take a look at `setRole()` function from `ConfigStorage.sol` - a single role can be assigned to multiple of addresses).


In the current attack scenario, we assume, that roles ` Role.PriceFeed_1` -  `Role.PriceFeed_5` can effectively block admin from changing the thresholds for executing proposal, by front-running every call to `setUSDThresholds()`.

Because thresholds can be changed only when there's no active proposal - malicious user can front-run `setUSDThresholds()` and set their own new proposals. This will block admin from changing the current proposal thresholds.

In some scenario, it's possible to completely break down the smart contract's functionality:

A). When some `Role.PriceFeed_1` -  `Role.PriceFeed_5` roles are being revoked, admin might decide to decrease the threshold. E.g., let's consider below scenario:

1) There are 6 users with roles `Role.PriceFeed_1` -  `Role.PriceFeed_5` (6 users can vote).
2) Both `APPROVE_THRESHOLD` and `DISAPPROVE_THRESHOLD` is set to 4. This basically means that 4 of 6 users need to approve or disapprove the proposal. This is very reasonable settings, since more than 50% decide if the proposal would be executed or disapproved.
3) Admin decides to revoke 3 users from `Role.PriceFeed_1` -  `Role.PriceFeed_5`. This basically means, that there are only 3 users left who can vote on the proposal, but the threshold is set to 4 (thus it's unreachable - there are only 3 users who can vote and we need 4 votes to either approve or disapprove a proposal).
4) To fix this issue, admin needs to decrease the threshold. Admin decides to call `setUSDThresholds()` and decrease the threshold to 2.
5) One of the user front-runs `setUSDThresholds()` and calls `proposeUSDPrice()`.
6) New proposal is being created - that proposal still contains old threshold (4).
7) Because of the front-run, `setUSDThresholds()` reverts (when there's an active proposal, we cannot change the threshold, thus revert occurs).
8) Since new proposal is active, it's not possible to change the threshold unless that proposal becomes either executed or disapproved.
9) However, the proposal will never reach executed or disapproved state, because it requires 4 votes, where there are only 3 voters!
10) Contract is blocked, it's not possible to change the threshold and it's not possible to create any new proposal (only one proposal can be active). And because this proposal will never be either accepted or rejected - contract is blocked forever.


Additionally, the impact of this issue is significantly high when the thresholds are low and admin decides to increase them. There are multiple of scenarios when this issue might occur:

A). New users are being added to roles `Role.PriceFeed_1` -  `Role.PriceFeed_5`. Since there are more users who are able to vote for the proposal - the threshold should be increased. However, a single user can front-run `setUSDThresholds()` and create new proposal which will be using old `APPROVE_THRESHOLD` value. Since there are more users who can vote, reaching that threshold is being more possible.

B). The initial thresholds are set to very low values:

```
    uint8 APPROVE_THRESHOLD = 3;
    /// @notice Threshold for removing a proposal
    uint8 DISAPPROVE_THRESHOLD = 3;
```

After contract deployment, admin might need to change these values to a higher values (especially, if there are many users with `Role.PriceFeed_1` -  `Role.PriceFeed_5` roles). However, a single user can effectively block changing those values by front-running `setUSDThresholds()` call.





## Proof of Concept

Setting thresholds (calling `setUSDThresholds()`) is only possible, when there's no active proposal in progress:

[File: LockManager.sol](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L129-L135)
```
    function setUSDThresholds(
        uint8 _approve,
        uint8 _disapprove
    ) external onlyAdmin {
        if (usdUpdateProposal.proposer != address(0))
            revert ProposalInProgressError();
        APPROVE_THRESHOLD = _approve;
```

This implies, that the admin can change the threshold only when the previous proposal had been either approved or disapproved and no new proposal has been proposed.

This opens the door for front-running attacks. A malicious user, scans the mem-pool and sees that admin wants to update `APPROVE_THRESHOLD` by calling `setUSDThresholds()`. Then, the user immediately front-runs that call with `proposeUSDPrice()` function:

```
1. Admin wants to change the threshold, thus he calls setUSDThresholds()
2. User notices setUSDThresholds() call in the mem-pool and front-runs it with proposedUSDPrice()
3. proposedUSDPrice() is being called first, thus new proposal becomes active (usdUpdateProposal.proposer does not point to address(0) anymore).
4. Now, front-runned setUSDThresholds() is being executed, however, since there's an active proposal, setUSDThresholds() reverts at line 133)
5. The thresholds were not changed.
```
