# Vulnerability details

## Impact
The `usdUpdateProposal` struct is not actually removed from storage after being "deleted" using the `delete` operation. Instead, its members are simply reset to their default values, which in the case of the struct, is an all-zero state.

This means that if another function or contract interacts with the `usdUpdateProposal` struct after it has been "deleted," it may treat the all-zero state as a valid proposal, leading to potential vulnerabilities or unexpected behavior.

**For example, consider the following scenario:**

A proposal is created and approved by the required number of price feeds.
The `disapproveUSDPrice` function is called, and the `usdUpdateProposal` struct is "deleted" using the `delete` operation.
Another function or contract attempts to interact with the `usdUpdateProposal` struct, assuming that it has been removed or invalidated.
However, since the struct is still present in storage with an all-zero state, the other function or contract may treat this as a valid proposal and proceed with its operations based on the all-zero values.
This could lead to unintended consequences, such as:

Updating the USD price to an incorrect value (e.g., 0) due to the all-zero state of the `usdUpdateProposal` struct.
Allowing unauthorized parties to approve or disapprove a "deleted" proposal, as the all-zero state may be treated as a valid proposal.
Causing other parts of the system to behave unexpectedly due to the presence of an all-zero proposal in storage.

## Proof of Concept
The issue is here in the following lines: [LockManager.sol#L237-L240](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L237-L241)
```solidity
if (usdUpdateProposal.disapprovalsCount >= DISAPPROVE_THRESHOLD) {
    delete usdUpdateProposal;
    emit RemovedUSDProposal();
}
```
The `delete` operation in Solidity resets the value of the specified variable to its default value, which is the same as if the variable was never assigned a value. In the case of the `usdUpdateProposal` struct, the default value is an all-zero state.

However, the code assumes that after deleting the `usdUpdateProposal` struct, it will no longer be accessible or considered as a valid proposal. This assumption may not hold true because the struct is still in storage, and its members are simply reset to their default values.

> If another function or contract interacts with the `usdUpdateProposal` struct after it has been "deleted," it may treat the all-zero state as a valid proposal, leading to unexpected behavior or potential vulnerabilities.

Let's consider a simplified example
```solidity
struct Proposal {
    uint256 value;
    bool approved;
    // other members...
}

Proposal public proposal;

function deleteProposal() public {
    delete proposal;
    // proposal is now: { value: 0, approved: false, ... }
}

function interactWithProposal() public {
    // This function may treat the all-zero state as a valid proposal
    if (proposal.approved) {
        // Perform some operations based on the "approved" proposal
        // ...
    }
}
```
After calling the `deleteProposal` function, the `proposal` struct is reset to an all-zero state. However, if the `interactWithProposal` function is called after the "deletion," it may treat the all-zero state as a valid proposal and perform operations based on that assumption, potentially leading to unintended behavior.

## Recommended Mitigation Steps
It would be better to introduce a separate state variable or flag to track whether a proposal is active or not, instead of relying on the struct being "deleted." Alternatively, you could consider removing the `usdUpdateProposal` struct from storage entirely when it is no longer needed, rather than just resetting its values.
```solidity
bool usdProposalActive;

// ...

if (usdUpdateProposal.disapprovalsCount >= DISAPPROVE_THRESHOLD) {
    usdProposalActive = false;
    delete usdUpdateProposal;
    emit RemovedUSDProposal();
}
```
