# Vulnerability details

## Impact
According to Documentation, 

```
the lockdrop period refers to a specific timeframe 
during which participants can lock up their tokens 
to receive rewards and benefits.
```

However, the [_lock() method](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L311-L398) can still be successfully called outside the lockdrop timeframe. In this case, the value of `remainder` is set to 0, leading to a loss of the player's funds.

## Proof of Concept
In line [LockManager.sol#L345](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L345) the local variable remainder is not initialized.
When the `_lock() method` is called outside the lockdrop timeframe, the lines [LockManager.sol#L352-L371](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L352-L371) are not executed. This is the right behavior because a player shouldn't mint a munchable outside the lockdrop timeframe. However, in this case, the value of `remainder` is not updated, and that variable remains uninitialized.

In line [LockManager.sol#L379](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L379) that variable is used to update the `lockedToken.remainder` value:

```
LockManager.sol#L379

379  lockedToken.remainder = remainder;
```

In case there was a remainder that the player accrued during the last `lockdrop` period, he/she will entirely lose it. We want to stress this: because the `lockdrop.start` and the `lockdrop.end` values are `uint32`, a player could wrongly call the `lock()` method outside the `lockdrop` timeframe just because his/her transaction has been processed 1 second later than the end of `lockdrop` period. So, we consider this an unwanted behavior that leads to losses of player's funds.
