# Vulnerability details

## Impact
The admin can invoke `configureLockdrop` to set the minimum lock duration. however, this minimum lock duration can be bypassed.

## Proof of Concept

First, the admin invokes `configureLockdrop` to set a minimum lock duration. 

Then, the user can invoke `setLockDuration` to set the `_duration` time. When there is no existing lock, the user can set the duration to any value.

When the user invokes `lock` to lock a specific amount of tokens, the protocol checks the player's set lock duration. If the value is zero, it is set to the `minLockDuration`.

```solidity
if (_lockDuration == 0) {
    _lockDuration = lockdrop.minLockDuration;
}
```

Therefore, if the player's set lock duration is smaller than the `minLockDuration`, the user can bypass the restriction and use any value they want.

add foundry test:
```solidity
function test_min_lock_duration() external {
    uint256 lockAmount = 100e18;
    deployContracts();

    // register me
    amp.register(MunchablesCommonLib.Realm(3), address(0));
    logSnuggery("Initial snuggery");

    uint32 minLockDuration = 86400;

    //reset lockdrop
    lm.configureLockdrop(
        ILockManager.Lockdrop({
            start: uint32(block.timestamp)+minLockDuration,
            end: uint32(block.timestamp) + minLockDuration*2,
            minLockDuration: minLockDuration
        })
    );

    //user set duration to 10
    lm.setLockDuration(10);
    
    // lock tokens
    lm.lock{value: lockAmount}(address(0), lockAmount);

    logLockedTokens("After Lock");
}
```
out:
```shell

  After Lock
  ETH Locked: 100000000000000000000
  Remainder: 0
  unlockTime: 11
  lastLockTime: 1
  -------------------------------
```
From above output we can see user's unlockTime is 11, when admin set minLockDuration is 86400
