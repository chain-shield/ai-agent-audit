# Vulnerability details

## Impact
Users will withdraw wrong amount of tokens (unlocking more/less than deserved) and danger of DOS is present for the last couple of people who try to unlock.

## Proof of Concept
Rebasing tokens (USDB) change their underlying balance based on certain condition. Balances can increase/decrease. The problem arises when we do a lock and we write in storage the amount of tokens that were transferred.

Code reference: [`link`](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L380)

```solidity
  lockedToken.quantity += _quantity;
```

After some time this amount can change and the contract will hold more or less tokens but the value in storage (quantity) will not change.

Based on the direction of the change users will either:
1. Claim more tokens than deserved (if the token balance decreases due to a rebase) and the last users who wish to [`unlock()`](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L401) will not be able because there won't be enough tokens remaining in the contract
2. Claim less tokens, causing tokens to be locked in the contract - if the token balance increases.

Code reference: [`link`](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L401-L427)
```solidity
function unlock(
    address _tokenContract,
    uint256 _quantity
) external notPaused nonReentrant {
    LockedToken storage lockedToken = lockedTokens[msg.sender][_tokenContract];
    ...
    lockedToken.quantity -= _quantity;
    ...
}
```

## Recommended Mitigation Steps

Consider implementing a system to handle rebasing tokens. The simplest solution I can think of is to convert the rebasing token to their wrapped version. This way the current accounting will work. In the case of USDB, the tokens should be converted to nrUSDB.
