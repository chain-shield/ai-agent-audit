# Vulnerability details

## Impact
Users can reduce the lockup duration they previously set breaching one of the protocol invariants that you shouldn't be able to reduce a lockup time once set.

## Proof of Concept
- User calls `setLockDuration` setting the lockup duration to 3 days aka 259200 in seconds
- A couple of hours elapse
- User calls `setLockDuration` again passing the `_duration` argument as 172800 aka 2 days
- Users' lockup duration has now been reduced from 3 days to 2 days
- User then proceeds to lock tokens for the first time on.

```solidity
function setLockDuration(uint256 _duration) external notPaused {
        if (_duration > configStorage.getUint(StorageKey.MaxLockDuration))
            revert MaximumLockDurationError();

        playerSettings[msg.sender].lockDuration = uint32(_duration);
        // update any existing lock
        uint256 configuredTokensLength = configuredTokenContracts.length;
        for (uint256 i; i < configuredTokensLength; i++) {
            address tokenContract = configuredTokenContracts[i];
            if (lockedTokens[msg.sender][tokenContract].quantity > 0) {
                // check they are not setting lock time before current unlocktime
                if (
                    uint32(block.timestamp) + uint32(_duration) <
                    lockedTokens[msg.sender][tokenContract].unlockTime
                ) {
                    revert LockDurationReducedError();
                }

                uint32 lastLockTime = lockedTokens[msg.sender][tokenContract]
                    .lastLockTime;
                lockedTokens[msg.sender][tokenContract].unlockTime =
                    lastLockTime +
                    uint32(_duration);
            }
        }

        emit LockDuration(msg.sender, _duration);
    }
```

```solidity
function test_reducedDuration() public{
        uint256 lockAmount = 1e18;
        console.log("Beginning run()");
        deployContracts();

        // register bob
        amp.register(MunchablesCommonLib.Realm(3), address(0));
        logSnuggery("Initial snuggery Bob");

        lm.setLockDuration(3 days);

        vm.warp(block.timestamp + 4 hours);

        lm.setLockDuration(2 days);

        // lock tokens
        lm.lock{value: lockAmount}(address(0), lockAmount);

        logPlayer("Bob after lock");
        logLockedTokens("After First Lock");

        vm.warp(block.timestamp + 2 days);

        // unlock
        lm.unlock(address(0), lockAmount);
        logLockedTokens("After Unlock");
    }
```

Since they haven't locked yet, the for loop code block will not be effective and this will be possible because they have 0 balances for the supported tokens at this time. Another way to also reduce the lock duration assuming you have already locked some tokens before realizing the loophole is to just wait out the current lock duration you set, unlock all tokens, call `setLockDuration` again to reduce your lock duration by a lot and then re-lock tokens. The first case which is reducing it before locking in the first place is more efficient.

## Tools Used
Manual review

## Recommended Mitigation Steps
Instead of only checking that the reduction may have happened inside the for loop block, check it also before the mutation of the calling users' `playerSettings[msg.sender].lockDuration` before setting the new duration as the effective one. If the duration delta from the check suggests they're trying to reduce the previously set duration, revert in that case just as has already been done inside the loop.
