# Vulnerability details

## Impact

According to provided [documentation](https://github.com/code-423n4/2024-05-munchables/blob/main/README.md#erc20-token-behaviors-in-scope), protocol accepts ERC-20 tokens with high decimals:

```
ERC20 token behaviors in scope
[...]
Low decimals ( < 6)	Yes
High decimals ( > 18)	Yes
```

However, the code-base does not respect the documentation and does not work properly with tokens with high decimals.

Tokens with more than 18 decimals are not supported by the protocol (even though, the documentation explicitly states that protocol supports them). Function `getLockedWeightedValue()` will revert with underflow when ERC-20 tokens will have more than 18 decimals.

## Proof of Concept

[File: LockManager.sol](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L472-L482)
```
                // We are assuming all tokens have a maximum of 18 decimals and that USD Price is denoted in 1e18
                uint256 deltaDecimal = 10 **
                    (18 -
                        configuredTokens[configuredTokenContracts[i]].decimals);
                lockedWeighted +=
                    (deltaDecimal *
                        lockedTokens[_player][configuredTokenContracts[i]]
                            .quantity *
                        configuredTokens[configuredTokenContracts[i]]
                            .usdPrice) /
                    1e18;
```

The comment at line 472 states that: `We are assuming all tokens have a maximum of 18 decimals and that USD Price is denoted in 1e18`. However, this assumption is wrong, because the documentation straightforwardly states that ERC-20 with high decimals (> 18) are in scope.

When provided ERC-20 have more than 18 decimals, the expression `(18 - configuredTokens[configuredTokenContracts[i]].decimals)` will underflow and revert.
This implies, that tokens with more than 18 decimals (e.g. YAM-V2 token has 24 decimal) won't work with the protocol.


## Tools Used

Manual code review


## Recommended Mitigation Steps

Do not assume that all tokens have a maximum of 18 decimals - because the documentation straightforwardly states that's not true. According to documentation, protocol should support tokens with both low ( < 6) and high ( > 18) decimals.
