# Vulnerability details

## Description
As per the [README.md](https://github.com/code-423n4/2024-05-munchables?tab=readme-ov-file#general-questions), which is the source of truth:
```md
USDB, WETH, (assume we can add more to the future for use in LockManager)
``` 
and:
[ERC20 token behaviors in scope](https://github.com/code-423n4/2024-05-munchables?tab=readme-ov-file#erc20-token-behaviors-in-scope)
```md
Balance changes outside of transfers | YES
```
This means that rebase tokens should be treated as in-scope and they can be added in the future to the LockManager contract.
Usage of rebase tokens can lead to players losing their funds. If a negative rebase happens, the users that have their tokens locked for the longest time will lose their funds.
## Proof of Concept
- 100 users have all deposited `1 stETH` each which can negative rebase as per [Lido.fi docs](https://docs.lido.fi/integrations/aave/specification/).
- The total amount deposited is `100 stETH`.
- A negative rebase happens of `-1%`.
- The total amount deposited is now `99 stETH`.
- 99 users call `LockManager.unlock()`, which takes the `quantity` that was deposited:
```javascript
    function unlock(
        address _tokenContract,
        uint256 _quantity
    ) external notPaused nonReentrant {
        ...
        } else {
            IERC20 token = IERC20(_tokenContract);
            token.transfer(msg.sender, _quantity);
        }
    ...
```
- This means that the 100th user will not be able get his initial `1 stETH` deposit, resulting in a `1 stETH` loss.
## Tools used
Manual Review
## Recommended Mitigation Steps
When using rebase tokens, assign a ratio claim to the users of said tokens.
