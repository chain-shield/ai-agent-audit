# Vulnerability details

## Impact
The handling of the remainder value In the loop that populates the tmpLockedTokens array, the remainder value is being copied from the lockedTokens mapping: [/LockManager.sol#L449](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L449-L451)
```solidity
tmpLockedToken.remainder = lockedTokens[_player][configuredTokenContracts[i]].remainder;
```
However, the `remainder` value in the `lockedTokens` mapping is only updated when a new lock operation is performed. It is not updated when tokens are unlocked.

This means that if a user has locked tokens, unlocked a portion of them, and then calls the `getLocked` function, the `remainder` value returned will still be the original remainder from the lock operation, not the updated remainder after the partial unlock.

#### Impact on Contract State Representation
The `getLocked` function is designed to provide a view into the current state of a user's locked tokens. However, due to the bug, the `remainder` value returned for each token contract may not accurately reflect the actual remaining locked tokens after partial unlocks.

This means that the data returned by the `getLocked` function may not match the contract's internal state, leading to inconsistencies and potential confusion for users or external systems relying on this data.

#### Impact on User Experience
For example, if a user has locked 10 tokens, unlocked 3, and then calls `getLocked`, the function may still show a remainder of 2 (from the original lock operation), instead of the correct value of 7. This can be misleading and confusing for the user, as they may not understand why the displayed information does not match their expectations.

## Proof of Concept
To illustrate the issue, let's consider the following scenario.

Alice locks 10 tokens, resulting in a `remainder` of 2 (assuming the `nftCost` is 8).
Alice unlocks 3 tokens, leaving her with 7 locked tokens.
Alice calls the `getLocked` function.

According to the current implementation of the `getLocked` function, the `remainder` value returned will still be 2, even though the correct `remainder` should be 7.

## Recommended Mitigation Steps
The `getLocked` function should recalculate the `remainder` value based on the `quantity` and `nftCost` values for each token contract.
```solidity
function getLocked(address _player) external view returns (LockedTokenWithMetadata[] memory _lockedTokens) {
    uint256 configuredTokensLength = configuredTokenContracts.length;
    LockedTokenWithMetadata[] memory tmpLockedTokens = new LockedTokenWithMetadata[](configuredTokensLength);

    for (uint256 i; i < configuredTokensLength; i++) {
        address tokenContract = configuredTokenContracts[i];
        LockedToken memory tmpLockedToken = lockedTokens[_player][tokenContract];
        uint256 nftCost = tokenConfigs[tokenContract].nftCost;
        uint256 remainder = tmpLockedToken.quantity % nftCost;

        tmpLockedTokens[i] = LockedTokenWithMetadata(
            tmpLockedToken,
            tokenContract,
            remainder
        );
    }

    _lockedTokens = tmpLockedTokens;
}
```
The `remainder` value is calculated by taking the `quantity` value from the `lockedTokens` mapping and computing the remainder when divided by the `nftCost` for that token contract. This ensures that the remainder value accurately reflects the remaining locked tokens after any partial unlocks.
