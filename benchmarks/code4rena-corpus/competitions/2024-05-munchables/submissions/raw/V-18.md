# Vulnerability details

## Impact
From the `README.md`, the protocol accepts the following tokens:
```solidity
USDB, WETH, (assume we can add more to the future for use in LockManager)
```
Also, it accepts tokens whose balances change outside transfers (`rebasing`). 

This means that in future, rebasing tokens e.g `stETH` will be accepted. However, as a rebasing token, the protocol needs to integrate them into the system. But as it is now the system is definitely not compatible with such tokens.

## Proof of Concept
The [_lock()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L373-L377) and any other accounting related functions perform operations using inputed/recorded amounts. They don't query the existing balance of tokens before or after receiving/sending in order to properly account for tokens that shift balance over time (`rebasing`).

```solidity
        // Transfer erc tokens
        if (_tokenContract != address(0)) {
            IERC20 token = IERC20(_tokenContract);
            token.transferFrom(_tokenOwner, address(this), _quantity);
        }
```
Depositing `rebasing` tokens into a system that does not support them can lead to several issues:

- Incorrect Balance Tracking:
The system may not account for balance changes due to rebases, leading to incorrect display or accounting of the user's holdings.
- Value Discrepancies:
The value of the user's deposit could be misrepresented, as the system might not update the user's balance in response to the token's supply changes.

## Tools Used
Manual review

## Recommended Mitigation Steps
Adjust the code to check the `token.balanceOf()` before and after doing any operation related to the token transfers.
