# Vulnerability details

## Impact
Since USDB and WETH are the tokens in-scope, and since balance changes outside of transfers is a token behavior which is in-scope for this audit as well, the lock manager is incompatible with both tokens as it's not designed to support yield-bearing tokens, and both USDB and WETH yield mode are AUTOMATIC by default.

## Proof of Concept

Similar to ETH, WETH and USDB on Blast is also rebasing and follows the same yield mode configurations.

However, unlike ETH where contracts have Disabled yield by default, WETH and USDB accounts have Automatic yield by default for both EOAs and smart contracts.

As per the Blast documentation: https://docs.blast.io/building/guides/weth-yield

When locking funds/tokens in the Lock Manager, the `amount` that we lock is saved as `quantity`:

```
        lockedToken.quantity += _quantity;
``` 

Later when unlocking tokens, the maximum amount of tokens that a user can unlock is the amount that they've locked, i.e. its based on internal accounting values.

```
        if (lockedToken.quantity < _quantity)
            revert InsufficientLockAmountError();
```

This means that any distributed yield won't be able to be claimed by users nor the protocol, i.e. is lost.

Manual Review

## Recommended Mitigation Steps
Implement a way to claim the yield / user balances to change accordingly to the rebases.

The yield mode can also be set as `CLAIMABLE` so that the balances can remain the same (i.e. internal accounting values can be used), but the yield can still be claimed separately: 

https://docs.blast.io/building/guides/weth-yield
