# Vulnerability details

## Impact
The current implementation requires users to set a single lock duration, affecting all existing and future token locks associated with their address. This inflexibility can be problematic for users who may want to manage multiple token locks with different deadlines independently. a deadline parameter should be included in the lock functions for users to specify how long each token lock should take.

Essentially the locking function lacks a deadline parameter similar to swapping functions, and the impact is temporary freeze of funds.

## Proof of Concept
At present, when a user sets a lock duration, it applies to all existing and future token locks associated with their address. This means that changing the lock duration affects all active locks uniformly, potentially leading to unintended consequences, such as extended lock periods.

Impact:

Users are constrained by a single lock duration, preventing them from managing different token locks with unique deadlines independently.
Changing the lock duration could inadvertently cause active locks to be extended, leading to unexpected consequences.

Lets say a user is expecting some money to be available for unlock in 3 days but finds another opportunity and would love to lock some other token for 30 days this means the lock will all reset to 30 days. this might not be a friendly approach if say the user needed to unlock the money urgently after the 3 days and use only half of it to lock again.
