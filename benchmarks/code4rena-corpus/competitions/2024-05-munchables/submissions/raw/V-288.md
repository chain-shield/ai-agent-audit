# Vulnerability details

## Impact
If a user tries to lock additional tokens for the same `_tokenContract` while they already have an active lock, the `_lock` function will overwrite the existing lock with the new lock.

Here's how it works:

The function retrieves the existing `LockedToken` struct from the `lockedTokens` mapping using the `_lockRecipient` and `_tokenContract` as keys.
It calculates the new quantity by adding the `_quantity` to the existing `lockedToken.remainder`.
It updates the `lockedToken.quantity` by adding the `_quantity` to the existing value.
It updates the `lockedToken.lastLockTime` to the current block timestamp.
It updates the `lockedToken.unlockTime` to the current block timestamp plus the new `_lockDuration`.
So, the existing lock duration, unlock time, and remaining quantity are effectively overwritten by the new values based on the _quantity and `_lockDuration` provided in the new lock call.

This behavior is not documented or handled in a separate case within the function. It silently overwrites the existing lock details with the new ones, which could lead to unexpected behavior or loss of data if not intended.

## Proof of Concept
**Impact on Lock Duration and Unlock Time**
When a user locks additional tokens for the same `_tokenContract`, the existing lock duration and unlock time are overwritten with the new values based on the `_lockDuration` provided in the new lock call. The user's original lock duration and unlock time are effectively reset, leading to unintended consequences.

For example, let's say a user initially locked tokens for a duration of 1 year, and after 6 months, they try to lock additional tokens for the same `_tokenContract` with a shorter duration of 3 months. In this case, the existing lock duration and unlock time will be overwritten, effectively reducing the overall lock duration from 1 year to 3 months, even for the tokens that were initially locked for a longer period.

This behavior can be problematic if users expect their initial lock duration and unlock time to remain intact when locking additional tokens. It can lead to confusion, unexpected token unlocks, or potential loss of benefits associated with longer lock durations.

**Impact on Remaining Quantity and Remainder**

The function calculates the new quantity by adding the `_quantity` to the existing `lockedToken.remainder`, and then updates the `lockedToken.quantity` by adding the `_quantity` to the existing value. While this correctly handles the addition of new tokens to the existing lock, it does not account for any potential changes in the token cost or NFT cost during the lock period.

For example, if the `nftCost` for the `_tokenContract` changes between the initial lock and the subsequent lock, the calculation of the remainder and the number of NFTs awarded may be affected. This could lead to inconsistencies or unexpected behavior, especially if users expect the NFT rewards to be calculated based on the token cost at the time of each individual lock.

Code that illustrates the overwriting behavior: [#L379-L384](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L379-L384)
```solidity
LockedToken storage lockedToken = lockedTokens[_lockRecipient][_tokenContract];
uint256 quantity = _quantity + lockedToken.remainder;
uint256 remainder;
// ...
lockedToken.remainder = remainder;
lockedToken.quantity += _quantity;
lockedToken.lastLockTime = uint32(block.timestamp);
lockedToken.unlockTime = uint32(block.timestamp) + uint32(_lockDuration);
```
In this code snippet, the existing `LockedToken` struct is retrieved, and its values are updated with the new `_quantity` and `_lockDuration`, effectively overwriting the previous lock details.

While this behavior may be intentional in certain scenarios, it can lead to unexpected consequences and potential issues if not properly documented or handled. It's essential to carefully consider the implications of overwriting existing locks and ensure that the behavior aligns with the intended design and user expectations.

## Recommended Mitigation Steps
The function could be modified to handle the case of an existing lock separately, either by reverting the transaction or by providing an option to extend the existing lock instead of overwriting it.
