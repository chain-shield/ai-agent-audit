# Vulnerability details

## Impact
Token with high decimal (> 18) not supported by protocol

## Proof of Concept
In contest page, there is a section named `ERC20 token behaviors in scope`
where it mentioned that `High decimals ( > 18)  = Yes`

But below code segment from `getLockedWeightedValue()` always revert for those type of token due to solidity `Underflow` behaviour

```solidity
    /// @inheritdoc ILockManager
    function getLockedWeightedValue(
        address _player
    ) external view returns (uint256 _lockedWeightedValue) {
...
...
                uint256 deltaDecimal = 10 **
                    (18 - // @audit
                        configuredTokens[configuredTokenContracts[i]].decimals);
                lockedWeighted +=
                    (deltaDecimal *
                        lockedTokens[_player][configuredTokenContracts[i]]
                            .quantity *
                        configuredTokens[configuredTokenContracts[i]]
                            .usdPrice) /
                    1e18;
            }
        }

        _lockedWeightedValue = lockedWeighted;
    }
```
https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L473-L483

So the Users who locked Those type of token(High Decimal Token) then calculation of their total lockedWeight always revert due to above reason.

## Tools Used
Manual review

## Recommended Mitigation Steps
For high Decimal, `deltaDecimal` should adjusted downward
