# Vulnerability details

## Impact
The documentation reports that:
```
The lockdrop period refers to a specific timeframe during which participants can lock up their tokens to receive rewards and benefits...
When tokens are locked using the lock function, the contract checks if the current timestamp is within the lockdrop period...... If it is [...], the tokens are successfully locked
```

Then, it ends with:
```
This mechanism allows the LockManager to handle token locks securely and according to the predefined rules of the lockdrop period, ensuring that participants can only lock their tokens during the specified timeframe and under the correct conditions...
```

Anyway, according to the code, the last sentence is wrong because it is currently possibile to lock some tokens outside the lockdrop timeframe, this means that there will be no NFTs in reward.

In conclusion, this unexpected behavior will cause the losing of funds for those players that perfom the locking outside the established lockdrop timeframe.

## Proof of Concept
The [_lock private method](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L311-L398) is called by the [lock external and payable method](https://github.com/code-423n4/2024-05-munchables/blob/main/src/managers/LockManager.sol#L296-L309). The external lock() method can be pushed by the player that wants to lock its funds and start the mint.

The _lock() can take place only during the lockdrop timeframe:
```
352      if (
353        lockdrop.start <= uint32(block.timestamp) &&
354        lockdrop.end >= uint32(block.timestamp)
355      ) {
```
Even if the condition isn't matched, the function doesn't revert, that's the error, and it continues with the transfer of the tokens: 

```
373      // Transfer erc tokens
374      if (_tokenContract != address(0)) {
375        IERC20 token = IERC20(_tokenContract);
376        token.transferFrom(_tokenOwner, address(this), _quantity);
377      }
```

That's the issue.

Due to the fact that the context includes only the LockManager.sol file and due to the available time for the analysis, the code has been manual inspected.
