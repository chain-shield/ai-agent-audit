# Vulnerability details

## Impact

Impact : Medium
Likelihood : High

In the current implementation of the `_lock` function, 
subsequent calls to lock tokens for a user extend the `unlockTime` for all previously locked tokens. 

1. Inflexibility: 
Users cannot manage multiple lock periods. 
Each new lock extends the lock period for all tokens, which can be inconvenient.

2. Unintended Lock Extensions: 
Users might accidentally extend the lock period for previously locked tokens 
when they only intended to lock a new batch.


## Proof of Concept

NFT Cost : 1000 USDB

Bob chooses to lock USDB inorder to avoid the volatility of ETH

_Step 1 : Initial Lock to mint 10 NFTs_

  On April 1, 2024 12:00 PM  
  Bob locks 10,000 USDB with a lock duration of 30 days.

```
  unlockTime = April 30, 12:00 PM
  lockedToken.quantity = 1000
  lockedToken.unlockTime = April 30, 12:00 PM
```

_Step 2 : Subsequent Lock to mint 1 NFT_

  On April 25, 2024 12:00 PM 
  Bob locks an additional 1000 USDB with the same lock duration of 30 days.

  The `unlockTime` for all tokens, 
  including the previously locked 10,000 USDB got extended to May 25, 12:00 PM.


_Original Expectation:_
  Bob expected the first batch of 10000 tokens to be unlocked on April 30.

_Reality:_ 
  Due to the subsequent lock, 
  the unlock time for all 11000 USDB tokens is now extended to May 25, 12:00 PM.

_Inflexibility:_ 
  Bob cannot manage multiple lock periods for different batches of tokens. 
  Each new lock extends the lock period for all previously locked tokens, 
  leading to unintentional delays in accessing his initially locked tokens.

## Recommended Mitigation Steps

Here’s a possible approach to improve this:

1. Introduce a Struct for Each Batch: 
Create a struct to store information about each batch of locked tokens.

```
struct LockedTokenBatch {
    uint256 quantity;
    uint32 lockTime;
    uint32 unlockTime;
}

```


2. Track Batches for Each User: 
Use a mapping to store an array of LockedTokenBatch for each user and token contract.

```
mapping(address => mapping(address => LockedTokenBatch[])) public lockedTokenBatches;

```

3. Update _lock Function: 
   Modify the _lock function to create a new batch each time tokens are locked.

4. Update unlock Function: 
   Modify the unlock function to handle unlocking specific batches.

#Benefits of the Fix

_Flexibility:_ 
  Users can manage multiple batches of locked tokens, each with its own lock 
  period.

_Clarity:_ 
  Lock and unlock operations are clearer, 
  as each batch is treated independently.

_Fairness:_ 
  Users are not unintentionally affected by subsequent lock operations.
  This approach ensures that each locking operation is independent, 
  allowing users to lock and unlock their tokens with greater flexibility and 
  control.
