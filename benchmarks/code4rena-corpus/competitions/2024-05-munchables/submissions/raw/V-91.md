# Vulnerability details

## Description
The current implementation doesn't handle properly `fee-on-tranfer ERC20 token` and since the contest's README indicates that this is in scope, I'm still submitting this report just in case, which seems to warrant `Medium` severity.

```
ERC20 token behaviors in scope
Fee on transfer:   Yes
```

## Impacts
`lock` function will not account for the proper amount of token internally as the amount being transfered from the player to the contract will be less then the original amount.
 1. `quantity` will be actually more then the real amount the contract will be receiving after the transfer. This means the `numberNFTs` might be inflate and player would get more NFT then they should.
 ```solidity
	        uint256 quantity = _quantity + lockedToken.remainder;
	
			...
	
            if (msg.sender != address(migrationManager)) {
                // calculate number of nfts
                remainder = quantity % configuredToken.nftCost;
                numberNFTs = (quantity - remainder) / configuredToken.nftCost;

                if (numberNFTs > type(uint16).max) revert TooManyNFTsError();

                // Tell nftOverlord that the player has new unopened Munchables
                nftOverlord.addReveal(_lockRecipient, uint16(numberNFTs));
            }
```
 2. Similar to previous impact, `lockedToken.quantity` will essentially have an inflated number, which might create side effects in the game, like receive rewards/point/bonus more then they should.
 ```solidity
        lockedToken.remainder = remainder;
        lockedToken.quantity += _quantity;
        lockedToken.lastLockTime = uint32(block.timestamp);
        lockedToken.unlockTime = uint32(block.timestamp) + uint32(_lockDuration);
 ```

## Recommended Mitigation Steps
Add proper support for `fee-on-transfer` ERC20 token
