# Vulnerability details

## Impact
The current implementation assumes that any token contract with a non-zero `nftCost` should have its USD price updated when a proposal is approved. However, this assumption may not hold true in all cases, as there could be scenarios where a token contract is configured with a non-zero `nftCost` but should not have its USD price updated during a particular proposal.

For example, consider a situation where the contract is initially configured with a set of token contracts and their corresponding USD prices and `nftCost` values. Later, a new proposal is made to update the USD prices of only a subset of those token contracts. In this case, the current implementation would update the USD prices of all token contracts with a non-zero `nftCost`, including those that were not intended to be updated by the proposal.

This unintended behavior could lead to inconsistencies in the USD price data and potentially cause issues for other parts of the system that rely on accurate USD price information for token contracts.

The problematic condition check is present in the following code snippet: [LockManager.sol#_execUSDPriceUpdate()](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L506-L526)

The condition `configuredTokens[tokenContract].nftCost != 0` is used to determine whether to update the USD price for a given token contract. However, as mentioned earlier, this condition may not accurately reflect the intended behavior in all cases.

## Proof of Concept
To illustrate the issue, consider the following scenario:

Initially, the contract is configured with two token contracts: `tokenA` and `tokenB`, both with non-zero `nftCost` values and different USD prices.
A proposal is made to update the USD price of `tokenA` only.
The proposal is approved, and the `_execUSDPriceUpdate` function is called.
Due to the condition `configuredTokens[tokenContract].nftCost != 0`, the USD prices of both `tokenA` and `tokenB` will be updated, even though the intention was to update only `tokenA`.

This unintended behavior could lead to incorrect USD price data for `tokenB`, which may cause issues in other parts of the system that rely on accurate USD price information.

## Recommended Mitigation Steps
Consider adding an additional check or flag within the `usdUpdateProposal` struct to explicitly indicate which token contracts should have their USD prices updated. This would provide more control and flexibility over the update process.
```solidity
struct USDUpdateProposal {
    // ...
    mapping(address => bool) contractsToUpdate;
    // ...
}

function _execUSDPriceUpdate() internal {
    if (
        usdUpdateProposal.approvalsCount >= APPROVE_THRESHOLD &&
        usdUpdateProposal.disapprovalsCount < DISAPPROVE_THRESHOLD
    ) {
        uint256 updateTokensLength = usdUpdateProposal.contracts.length;
        for (uint256 i; i < updateTokensLength; i++) {
            address tokenContract = usdUpdateProposal.contracts[i];
            if (usdUpdateProposal.contractsToUpdate[tokenContract]) {
                configuredTokens[tokenContract].usdPrice = usdUpdateProposal.proposedPrice;
                emit USDPriceUpdated(tokenContract, usdUpdateProposal.proposedPrice);
            }
        }

        delete usdUpdateProposal;
    }
}
```
The `USDUpdateProposal` struct includes a mapping `contractsToUpdate` that maps token contract addresses to a boolean value indicating whether the USD price should be updated for that contract. The condition check in the loop now uses this mapping to determine if the USD price should be updated for the current token contract.
