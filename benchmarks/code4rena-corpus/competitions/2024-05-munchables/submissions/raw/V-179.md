# Vulnerability details

## Impact

According to provided documentation, protocol does not implement any trusted role, which implicitly implies, that every role within the protocol should be treated as a non-trusted:

[File: README.md](https://github.com/code-423n4/2024-05-munchables/blob/main/README.md#all-trusted-roles-in-the-protocol)
```
All trusted roles in the protocol

N/A
```

In the current attack scenario, we assume, that roles `Role.PriceFeed_1` -  `Role.PriceFeed_5` can create a malicious proposal which will break down the whole protocol.

User can create a proposal which won't be executed (it will always revert during the execution). Since it's not possible to create multiple proposal at once - contract won't work at all!


## Proof of Concept

1. Create a malicious proposal, which contains multiple of addresses in `_contracts` array

[Fie: Lock.Manager.sol](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L142-L144)
```
    function proposeUSDPrice(
        uint256 _price,
        address[] calldata _contracts
    )
        external
        onlyOneOfRoles(
     [...]
     usdUpdateProposal.contracts = _contracts;
```

E.g., `proposeUSDPrice(2, [0x01, 0x02, ...])`.
Calling above function means, that there will be a lot of addresses in `usdUpdateProposal.contracts`.

2. Now other users vote for or against that proposal. Let's assume the default scenario. There are 5 roles `Role.PriceFeed_1` -  `Role.PriceFeed_5` who can vote, thus for the simplicity, let's assume that there are only 5 voters.
The default thresholds values are:
```
    uint8 APPROVE_THRESHOLD = 3;
    /// @notice Threshold for removing a proposal
    uint8 DISAPPROVE_THRESHOLD = 3;
```

This means that they need to be either 3 `yes` votes to execute the proposal or 3 `no` votes to disapprove the proposal.
Let's assume that 3 users voted for `yes` and proposal can be executed.

3. Since proposal can be executed, we will be calling `_execUSDPriceUpdate()`

Let's notice, that function `_execUSDPriceUpdate()` loops over unbounded array.

[File: LockManager.sol](https://github.com/code-423n4/2024-05-munchables/blob/57dff486c3cd905f21b330c2157fe23da2a4807d/src/managers/LockManager.sol#L511-L512)
```
            uint256 updateTokensLength = usdUpdateProposal.contracts.length;
            for (uint256 i; i < updateTokensLength; i++) {
```

This array contains multiple of addresses which were added via `proposeUSDPrice()` call. Because this array is so big, `execUSDPriceUpdate()` reverts with out of gas error.
It's not possible to execute the proposal - thus it will always revert with out of gas error.
It's not possible to reject the proposal either, because 3 of 5 users voted `yes`. This means that there are only 2 users who voted `no` - thus disapprove threshold is not being reached.

Moreover, it's not possible to change the threshold when the proposal is still active.
Moreover, it's not possible to propose any other proposal when one is still active.

This basically means, that protocol becomes broken down. There's one proposal which stuck the whole protocol.
We cannot execute it (it will revert with out of gas error). We cannot propose any new proposal (the old one needs to be either executed or rejected) and we cannot reject it (because the disapprove threshold cannot be met). Contract is blocked forever - no other proposal cannot be proposed - and the proposed one cannot be executed (or rejected).



## Tools Used

Manual code review


## Recommended Mitigation Steps

In `proposeUSDPrice()`, limit the number of elements which can be assigned to `_contracts`. It should not be possible to create a proposal with too many contract's addresses.
