# Vulnerability details

## Impact
One of the main attack vector to look at was that people shouldn't be able to reduce their lockup times that are previously set but in the code when setLockDuration function is called it sets the unlock time to wrong value thus allowing the users to reduce their lock up time.

## Proof of Concept
Following is the setLockDuration function
```solidity
 function setLockDuration(uint256 _duration) external notPaused {
        if (_duration > configStorage.getUint(StorageKey.MaxLockDuration))
            revert MaximumLockDurationError();

        playerSettings[msg.sender].lockDuration = uint32(_duration);
        // update any existing lock
        uint256 configuredTokensLength = configuredTokenContracts.length;
        for (uint256 i; i < configuredTokensLength; i++) {
            address tokenContract = configuredTokenContracts[i];
            if (lockedTokens[msg.sender][tokenContract].quantity > 0) {
                // check they are not setting lock time before current unlocktime
                if (
                    uint32(block.timestamp) + uint32(_duration) <
                    lockedTokens[msg.sender][tokenContract].unlockTime
                ) {
                    revert LockDurationReducedError();
                }

                uint32 lastLockTime = lockedTokens[msg.sender][tokenContract]
                    .lastLockTime;
                lockedTokens[msg.sender][tokenContract].unlockTime =
                    lastLockTime +
                    uint32(_duration);
            }
        }

        emit LockDuration(msg.sender, _duration);
    }
```
The following check if perfectly fine as it correctly checks that the lock time is not reduced
```
if (
                    uint32(block.timestamp) + uint32(_duration) <
                    lockedTokens[msg.sender][tokenContract].unlockTime
                ) {
                    revert LockDurationReducedError();
                }
```
But the main issue is in the following line
```
lockedTokens[msg.sender][tokenContract].unlockTime =
                    lastLockTime +
                    uint32(_duration);
```
For simplicity lets take lastLockTime = 0(it can be any value only for simplicity it is taken as follows)
 And let before calling the setLockDuration function 
lockedTokens[msg.sender][tokenContract].unlockTime was = 10sec

So now setLockDuration function is called 
Let block.timestamp = 5 sec

Now according to the following check
```
if (
                    uint32(block.timestamp) + uint32(_duration) <
                    lockedTokens[msg.sender][tokenContract].unlockTime
                ) {
                    revert LockDurationReducedError();
                }
```
value of _duration has to be greater than or equal to 5sec otherwise it would revert because if the value of _duration was less than 5 sec then it would mean that we are reducing the lock up time.
Now suppose that _duration = 6sec

So till now we have the if condition passing because 
uint32(block.timestamp) = 5sec
uint32(_duration) = 6sec 
lockedTokens[msg.sender][tokenContract].unlockTime = 10sec

Now following updation of lock up time happens
```
 uint32 lastLockTime = lockedTokens[msg.sender][tokenContract]
                    .lastLockTime;
                lockedTokens[msg.sender][tokenContract].unlockTime =
                    lastLockTime +
                    uint32(_duration);
```
we have assumed lockedTokens[msg.sender][tokenContract].lastLockTime = 0
Therefore 
```
 lockedTokens[msg.sender][tokenContract].unlockTime =0 + 6 = 6sec 
```
Thus it reduces the lock up time.

## Recommended Mitigation Steps
The value of the unlock time should be updated as follows
```
lockedTokens[msg.sender][tokenContract].unlockTime =
                    uint32(block.timestamp) +
                    uint32(_duration);
```
