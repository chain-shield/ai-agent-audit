# Vulnerability details

## Impact
In `LockManager.sol::approveUSDPrice(uint256)`, there is a check to prevent the proposer from approving the price. However, in `LockManager.sol::proposeUSDPrice(uint256, address[] calldata)`, the proposer is already added to the approval list. In the context of the `APPROVE_THRESHOLD` limit, this gives an advantage to the approvers, as they have one additional count at the proposal time. 

## Proof of Concept
In `LockManager.sol::approveUSDPrice(uint256)` code check for proposer
```solidity
192        if (usdUpdateProposal.proposer == msg.sender)
193            revert ProposerCannotApproveError();
```
However, in `LockManager.sol::proposeUSDPrice(uint256, address[] calldata)`,  `msg.sender` is set to `usdUpdateProposal.proposer` in line 167 and `usdUpdateProposal.approvalsCount` is incremented in line 171.

```solidity
166        usdUpdateProposal.proposedDate = uint32(block.timestamp);
167        usdUpdateProposal.proposer = msg.sender;
168        usdUpdateProposal.proposedPrice = _price;
169        usdUpdateProposal.contracts = _contracts;
170        usdUpdateProposal.approvals[msg.sender] = _usdProposalId;
171        usdUpdateProposal.approvalsCount++;
```
This conflicting logic may give the proposer an unfair advantage, as they have an additional approval count at the time of proposal, allowing them to more easily execute `_execUSDPriceUpdate();`.

Manual analysis

## Recommended Mitigation Steps

Removing line 170 and 171 from code in `LockManager.sol` will solve the issue.

```solidity
-170        usdUpdateProposal.approvals[msg.sender] = _usdProposalId;
-171        usdUpdateProposal.approvalsCount++;
```
