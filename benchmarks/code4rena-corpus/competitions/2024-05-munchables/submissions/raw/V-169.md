# Vulnerability details

## Vulnerability details
When a user lock asset for first time then his `lockDuration` is set to `lockDrop.minLockDuration` if his `lockDuration = 0`
```solidity
 function _lock(
        address _tokenContract,
        uint256 _quantity,
        address _tokenOwner,
        address _lockRecipient
    ) private {
    ...
        uint32 _lockDuration = playerSettings[_lockRecipient].lockDuration;

        if (_lockDuration == 0) {
            _lockDuration = lockdrop.minLockDuration;
        }
    ...

        // set their lock duration in playerSettings
        playerSettings[_lockRecipient].lockDuration = _lockDuration;
     ...
    }
```
Now a malicious user can set his `lockDuration` very low as compare to `minLockDuration` before locking his assets, as result user's `unlockTime` will `not` be setted to `minLockDuration` because `lockDuration != 0`.  `unlockTime` will be what user set `lockDuration` in `setLockDuration()`

As a result, user will be able to unlock() as soon as he lock()

//How this works
1. Malicious user set his `lockDuration` to 1 second(while minLockDuration = 30 days) using `setLockDuration()` 
2. User locks his asset, his unlockTime = 1 second as it doesn't set to minLockDuration because `lockDuration != 0`
3. User will be able to unlock() after 1 second, successfully bypassing minLockDuration


## Impact
User can bypass lockDrop.minLockDuration
