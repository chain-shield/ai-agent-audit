# Vulnerability details

Curator rewards are distributed not continuously in time, but at arbitrary moments in bulk. This opens a possibility 
for an attacker to temporarily increase they share amount, get a significant portion of rewards, and instantly dump shares.
The attack could be executed with the help of a flash loan in a single transaction. `SHARE_LOCK_PERIOD` was introduced
to prevent such attacks, however, the solution seems to be incomplete as it does not take into account reentrancy
exploitable by a share buyer.

Let's have a look at the code and discuss a possible attack vector in detail.

https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L638-L648:

```solidity
        if (isBuy) {
            cred.currentSupply += amount_;
            uint256 excessPayment = msg.value - price - protocolFee - creatorFee;
            if (excessPayment > 0) {
                _msgSender().safeTransferETH(excessPayment);
            }
            lastTradeTimestamp[credId_][curator_] = block.timestamp;
        } else {
            cred.currentSupply -= amount_;
            curator_.safeTransferETH(price - protocolFee - creatorFee);
        }
```

1. An attacker deploys a helper contract that does the following steps. Firstly, it buys a significant amount of shares
    of the targeted cred by invoking [buyShareCred](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L178). 
    A flash loan may be employed. Moreover, the attacker provides excess Ether, so a refund is triggered and the control 
    goes back to the attacker.

2. At the next step, while still inside `buyShareCred` callback (`_msgSender().safeTransferETH(excessPayment)`), the attacker distributes rewards by calling
    [CuratorRewardsDistributor.distribute](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/CuratorRewardsDistributor.sol#L77).
    The attacker receives an unfair portion of rewards since they have just bought many shares. Now the attacker can 
    [withdraw](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/abstract/RewardControl.sol#L92) the rewards.

3. At this moment, while still inside `buyShareCred` callback (`_msgSender().safeTransferETH(excessPayment)`), the attacker is able to dump all purchased shares.
    The `SHARE_LOCK_PERIOD` can not stop them since the `lastTradeTimestamp[credId_][curator_]` is not updated yet!

4. Now the attacker pocketed some rewards, distributor's royalty, and paid some fees.

## Impact

This attack unfairly deprives honest protocol users of their rewards. The attack is not always economically feasible
since an attacker has to pay protocol, gas, and creator fees. The attack is profitable for each such cred and amount of shares
that the rewards are greater than the fees. It's easy to automate the attack and rip any significant curator rewards
across the whole protocol, effectively draining `CuratorRewardsDistributor`.

## Recommended Mitigation Steps

One may suggest to just rearrange the timestamp update to prevent a flash loan attack like this:

```solidity
        if (isBuy) {
            cred.currentSupply += amount_;
+           lastTradeTimestamp[credId_][curator_] = block.timestamp;
            uint256 excessPayment = msg.value - price - protocolFee - creatorFee;
            if (excessPayment > 0) {
                _msgSender().safeTransferETH(excessPayment);
            }
-           lastTradeTimestamp[credId_][curator_] = block.timestamp;
        } else {
            cred.currentSupply -= amount_;
            curator_.safeTransferETH(price - protocolFee - creatorFee);
        }
```

However, I recommend protecting with reentrancy guards all protocol functions directly or indirectly dealing with 
assets or important state. Another important measure to consider is adhering to the [Checks-Effects-Interactions Pattern](https://docs.soliditylang.org/en/latest/security-considerations.html#use-the-checks-effects-interactions-pattern).
