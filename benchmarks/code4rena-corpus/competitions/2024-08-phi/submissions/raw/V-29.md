# Vulnerability details

## Impact
Storage collision in the first place. And this is highly likely to result in unpredictable behaviour, or even security vulnerabilities.

## Proof of Concept
One of the crucial points to bear in mind when implementing a proxy is the allocation of storage space before and after the update, in order to prevent storage conflicts.

https://docs.openzeppelin.com/contracts/4.x/upgradeable#storage_gaps

The implementation of the `UUPSUpgradeable` library in the following contracts `PhiNFT1155.sol`, `PhiFactory.sol` and `Cred.sol` are wrong. In fact, no empty space has been reserved in case the contracts updated in the future need additional space to store new storage variables. So if, during the update, one or more variables were added to one or more contracts, this would overwrite the storage variables already existing in their slot, resulting in a conflict and thus a disruption of the logic put in place before the update.

So all smart contracts that inherit from `UUPSUpgradeable` are likely to cause a storage collision during the update.

## Tools Used
Manual review.

## Recommended Mitigation Steps
Add a storage _gap variable in all contract who inherited from UUPSUpgradeable.
NB: The _gap variable should be located after all other storage variables in the contract. Better to place it in last line of the contract before the closing braket.
for example, in `PhiNFT1155` contract do this:


```diff
contract PhiNFT1155 is
    Initializable,
    UUPSUpgradeable,
    ERC1155SupplyUpgradeable,
    ReentrancyGuardUpgradeable,
    PausableUpgradeable,
    Ownable2StepUpgradeable,
    IPhiNFT1155,
    Claimable,
    CreatorRoyaltiesControl
{
    /... all the contract code

+   uint256[50] private __gap;
}
```
Please see this doc for more details:
https://docs.openzeppelin.com/upgrades-plugins/1.x/writing-upgradeable#storage-gaps
