# Vulnerability details

## Impact

Since there is no limitation that how many numbers of curator addresses can be distributed rewards, the TX of the CuratorRewardsDistributor#`distribute()` can be DOSed - due to reaching a gas limit in the `for-loop`.


## Proof of Concept

Within the CuratorRewardsDistributor#`distribute()`, the Cred#`getCuratorAddresses()` would be called to retrieve the **all curator addresses** and then it would be stored into the `distributeAddresses`.
Then, it would be **looped** based on the number of the `distributeAddresses` (`distributeAddresses.length`), which the **all curator addresses** are stored.
Finally, the PhiRewards#`depositBatch()` would be called with the `distributeAddresses` like this:
https://github.com/code-423n4/2024-08-phi/blob/main/src/reward/CuratorRewardsDistributor.sol#L84

```solidity
    function distribute(uint256 credId) external {
        ...
        uint256 totalBalance = balanceOf[credId];
        ...

        address[] memory distributeAddresses = credContract.getCuratorAddresses(credId, 0, 0); ///<-------- @audit - All curator addresses would be retrived.
        ...

        uint256[] memory amounts = new uint256[](distributeAddresses.length);
        bytes4[] memory reasons = new bytes4[](distributeAddresses.length);

        uint256 royaltyfee = (totalBalance * withdrawRoyalty) / RATIO_BASE;
        uint256 distributeAmount = totalBalance - royaltyfee;
        ...
        uint256 actualDistributeAmount = 0;
        for (uint256 i = 0; i < distributeAddresses.length; i++) { ///<-------- @audit - Looped based on the number of the "distributeAddresses", which the all curator addresses are stored.
            address user = distributeAddresses[i];

            uint256 userAmounts = credContract.getShareNumber(credId, user);
            uint256 userRewards = (distributeAmount * userAmounts) / totalNum;

            if (userRewards > 0) {
                amounts[i] = userRewards;
                actualDistributeAmount += userRewards;
            }
        }

        balanceOf[credId] -= totalBalance;

        _msgSender().safeTransferETH(royaltyfee + distributeAmount - actualDistributeAmount);

        //slither-disable-next-line arbitrary-send-eth
        phiRewardsContract.depositBatch{ value: actualDistributeAmount }(
            distributeAddresses, amounts, reasons, "deposit from curator rewards distributor" ///<--- @audit - "distributeAddresses", which the "Curator addresses" are stored.
        );
```

In this protocol desing, **anyone** can become a curator of a `credId` by buying the shares of the `credId` via the [Cred#`buyShareCred()`](https://github.com/code-423n4/2024-08-phi/blob/main/src/Cred.sol#L178-L180).
 
This is problematic because, in the following cases, a lot of the curator addresses can be created and stored into the `distributeAddresses`:
- If a lot of users would call the Cred#`buyShareCred()`, a lot of the curator addresses can be created and stored into the `distributeAddresses`. 

- If a malicious actor would call the Cred#`buyShareCred()` **many times** with a small amount respectively by using his **different (multiple) EOAs** in a short period, a lot of the curator addresses can be created and stored into the `distributeAddresses` in a short period. 

In these case above, once the **so many** numbers of the curator addresses would be stored into the `distributeAddresses`, **so many** numbers of loops would be executed in the CuratorRewardsDistributor#`distribute()`, which lead the TX of the CuratorRewardsDistributor#`distribute()` to being reverted - due to reaching a **gas limit** in the **for-loop** inside the CuratorRewardsDistributor#`distribute()`. 

This is because how many loops are executed would be determined based on the numbers of the curator addresses (`distributeAddresses.length`), which are stored into the `distributeAddresses`.

### Remarks:
As we can see the CuratorRewardsDistributor#`distribute()` above, the [PhiRewards#`depositBatch()` would **also** be called with the `distributeAddresses` in the CuratorRewardsDistributor#`distribute()` ](https://github.com/code-423n4/2024-08-phi/blob/main/src/reward/CuratorRewardsDistributor.sol#L124)above. 
And within the PhiRewards#`depositBatch()` (RewardControl#`depositBatch()`), the `distributeAddresses` would be assigned into the [`recipients` array parameter](https://github.com/code-423n4/2024-08-phi/blob/main/src/abstract/RewardControl.sol#L55) and it would also be used in the **for-loops** ([this loop](https://github.com/code-423n4/2024-08-phi/blob/main/src/abstract/RewardControl.sol#L70-L72) and [this loop](https://github.com/code-423n4/2024-08-phi/blob/main/src/abstract/RewardControl.sol#L78-L89)).
This also amplify the risk of causing the TX of the CuratorRewardsDistributor#`distribute()` to being DOSed.


## Tools Used
- Foundry


## Recommended Mitigation Steps

Within the CuratorRewardsDistributor#`distribute()`, consider adding a limitation that how many numbers of the curator addresses can be distributed rewards at once.
