# Vulnerability details

## Impact
```CuratorRewardDistributor.distribute()``` can be called by any EOA without restrictions to send rewards to each shareHolder according to their number of shares. The function ignores the time each user has been holding their shares to make the distribution, only current state is taken into account.

This encourages a malicious user to frontrun ```distribute()``` function by calling ```Cred.buyShareCred()``` using as param the credId being distributed. A user with great amount of ETH available can do this to get most part of the rewards to be distributed and the sell their share balance when the SHARE_LOCK_PERIOD has finished.

## Tools Used
Manual review

## Recommended Mitigation Steps
It is not advisable to prevent a user who has recently got shares from receiving rewards for a lapse of time as other user could take advantage to call ```distribute()``` then, knowing that user that bought will not get any rewards from the shares they had previously.

Best suggestion is to use a mapping that shows the number of shares got by a user  let's say in the last 7-8 minutes, so that those shares are not rewarded until that time has passed. It should also be implemented a mechanism that adds recent shares to normal shares balance when those 7-8 minutes have passed and resets therecentShareBalance.
