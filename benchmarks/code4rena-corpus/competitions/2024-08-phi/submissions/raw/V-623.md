# Vulnerability details

## SUMMARY

The confirmed vulnerability in the smart contracts of Phi Protocol relates to unchecked return values from ERC20 token operations. Specifically, the `Cred`, `PhiFactory`, and `PhiNFT1155` contracts exhibit patterns where ERC20 `transfer` and `transferFrom` functions are called without verifying their return values. This flaw can lead to incorrect state assumptions. The vulnerability arises because these functions return a boolean indicating success (`true`) or failure (`false`). When unchecked, the contracts assume the operations succeeded even if they didn't, potentially resulting in unauthorized state changes, incorrect token balances, and financial discrepancies. In particular, such unchecked operations are prevalent in functions like `mint` and `claimFromFactory`.

    uint256 credId_,
    uint256 amount_,
    bool isBuy,
    address curator_,
    uint256 priceLimit

    internal
    whenNotPaused
{
    if (amount_ == 0) {
        revert InvalidAmount();
    }

        revert InvalidCredId();

        IBondingCurve(cred.bondingCurve).getPriceData(credId_, supply, amount_, isBuy);

    if (isBuy) {
        if (priceLimit != 0 && price + protocolFee + creatorFee > priceLimit) revert PriceExceedsLimit();

            revert MaxSupplyReached();
        }

            revert InsufficientPayment();
        }

        if (priceLimit != 0 && price - protocolFee - creatorFee < priceLimit) revert PriceBelowLimit();

    if (isBuy) {
        cred.currentSupply += amount_;
        uint256 excessPayment = msg.value - price - protocolFee - creatorFee;
        if (excessPayment > 0) {
            _msgSender().safeTransferETH(excessPayment);
        }
        lastTradeTimestamp[credId_][curator_] = block.timestamp;

    );
    emit Royalty(creator, credId_, creatorFee);

    cred.latestActiveTimestamp = block.timestamp;

    emit Trade(curator_, credId_, isBuy, amount_, price, protocolFee, cred.currentSupply);
}

## VULNERABILITY DETAILS

The vulnerability in the Phi Protocol's smart contracts manifests from the unchecked return values of ERC20 token operations. Typically, ERC20 `transfer` and `transferFrom` functions should be checked for a `true` return value indicating successful completion. However, this oversight can lead to significant security flaws.

For example, within the `mint` function of the `PhiNFT1155` contract, ERC20 transfers take place under the assumption they succeed. This assumption extends to updating states based on these operations. Suppose these ERC20 operations fail (returning `false`), such failures won't be logged, leaving the system in a compromised state where ERC20 tokens haven't been successfully transferred, yet the state assumes they were, potentially leading to wrongful minting or reward distribution.

Furthermore, in the `claimFromFactory` function, the contract executes ERC20 token transfers, assuming success without verifying outcomes. The repercussions can be widespread across users, where incorrect token balances can trigger further unauthorized contract behaviors or state manipulations.

## TECHNICAL IMPACT

The identified vulnerability in the Phi Protocol's contracts primarily revolves around the unchecked return values from ERC20 token operations, specifically within the `cred.sol`, `PhiFactory.sol`, and `PhiNFT1155.sol` contracts. This issue can significantly affect the protocol's integrity and functionality in several ways:

### 1. Unauthorized State Changes

When ERC20 `transfer` and `transferFrom` methods are invoked, they return a boolean flag indicating success or failure. However, in the Phi Protocol, these return values are not being checked, leading to potential inconsistencies between contract state and actual token ownership. For instance, if a `transfer` call in the `mint` function of the `PhiNFT1155` contract fails (returns `false`), the smart contract will still proceed as if the transfer succeeded, resulting in unauthorized minting or distribution operations. Consequently, this can lead to minted NFTs or credentials being wrongly associated with an address without the corresponding ERC20 token having been transferred.

### 2. Financial Discrepancies and Unauthorized Access

Unchecked ERC20 operations may allow for scenarios where the protocol incorrectly assumes an ERC20 transfer appears successful. This can lead to several alarming consequences:
- **Financial Discrepancies:** Users may receive NFTs or credentials without matching token transfers, leading to economic imbalances where the contract state does not accurately reflect real token holdings. Such discrepancies could lead to inflated supply issues and mismatched balances, potentially impacting the protocol's economic model and bonding curves that rely on supply-demand dynamics.
- **Unauthorized Access:** Without verifying the success of ERC20 transfers, it carries the risk of allowing unauthorized entities to access functionalities and rewards predicated on having made these token transfers, thereby compromising the access control assumptions made elsewhere in the contract logic.

### 3. System Instability and Exploitability

The unchecked assumption that ERC20 operations succeed introduces a stark vulnerability that could be exploited by malicious actors. One could leverage this gap to perform denial of service attacks or exploit other contract functionalities dependent on these operations' outcomes, leading to systemic instability. For instance, an attacker could deliberate leverage this to affect price calculations and reward distributions in their favor without appropriate token commitments, manipulating market dynamics and reward mechanisms.

### 4. Data Corruption

The unchecked ERC20 transfers lead directly to data corruption regarding user balances and system state. For instance, when the `buyShareCred` and `sellShareCred` functions perform unchecked operations, the resulting state — such as curator balances and shareholdings — may not accurately encompass valid transactions. This can propagate data corruption to dependent systems or contracts interfacing with the Phi Protocol, further complicating resolution processes and data integrity assurance.

### Code-Level Mechanism

The primary culprit lies in functions like `mint` and the operations leveraging `_handleTrade` which fail to ensure ERC20 transfers complete successfully before proceeding with subsequent logic. Each unchecked transfer can lead to subsequent code assuming a state based on the false premise that the transfer succeeded, as demonstrated in the `PhiNFT1155` contract where mint-related operations are predicated on ERC20 transfers that might not actually complete.

In summary, the unchecked ERC20 operation return values in the Phi Protocol contracts pose a high risk of unauthorized state manipulation, financial loss, and exploitable conditions, requiring immediate augmentation to include proper checks after each ERC20 token-related operation to ensure stability, accuracy, and security in the protocol's execution flow.
