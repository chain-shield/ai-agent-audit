# Vulnerability details

The _updateCuratorShareBalance function manages the following mappings:

```
mapping(address curator => uint256[] credIds) private _credIdsPerAddress;
```

```    
mapping(address curator => mapping(uint256 credId => uint256 index)) private _credIdsPerAddressCredIdIndex;
```
```
mapping(address curator => uint256 arrayLength) private _credIdsPerAddressArrLength;
```

 These mappings are updated whenever Cred.sol::_handleTrade() or Cred.sol::_executeBatchTrade() invoke _updateCuratorShareBalance(). The issue arises because the functions _addCredIdPerAddress() and _removeCredIdPerAddress() can be called by anyone as they are public. This allows a malicious user to manipulate these mappings, potentially preventing legitimate users from fully sell their funds associated with a specific cred.

## Impact
Users will be unable to sell all funds from cred’s. Marked as high because everyone can manipulate _credIdsPerAddress, _credIdsPerAddressCredIdIndex and _credIdsPerAddressArrLength via _addCredIdPerAddress() and _removeCredIdPerAddress()

## Proof of Concept
A legitimate user wants to buy shares in a cred using buyShareCred(). This function calls _handleTrade(), which in turn invokes _updateCuratorShareBalance(). If this is the first time the user is buying into that particular cred, the credId must be added to _credIdsPerAddress via addCredIdPerAddress(). As a result of this operation:
`shareBalance[credId].tryGet(sender_)`, `credIdsPerAddress[sender]`, `credIdsPerAddressCredIdIndex[sender][credId]` are updated and `credIdsPerAddressArrLength[sender]` is incremented. 
A malicious user can then retrieve this data by calling getPositionsForCurator() with the victim's address. Once the attacker knows the credId where the legitimate user has funds, then can call _removeCredIdPerAddress() with the victim's address and credId. This action will decrement credIdsPerAddressArrLength[sender] back to 0. Now, if the legitimate user attempts to sell the funds they have in the cred via sellShareCred(), this function will call _handleTrade(), which again must update the curator's balance via _updateCuratorShareBalance(). Since the user intends to sell all their funds, the following condition in updateCuratorShareBalance() will be true:
```
else {
    if ((currentNum - amount) == 0) {
        removeCredIdPerAddress(credId, sender_);
        credIdExistsPerAddress[sender][credId] = false;
    }
    shareBalance[credId].set(sender, currentNum - amount);
}
```

 As a result, _removeCredIdPerAddress() will be executed. However, _removeCredIdPerAddress() performs the following check: 


```
if (credIdsPerAddress[sender].length == 0) revert EmptyArray();

```

Because the array length was previously manipulated by the malicious user, _removeCredIdPerAddress() will revert, and the legitimate user will be unable to sell all their funds.

## Tools Used
Manual review

## Recommended Mitigation Steps
Consider changing the visibility of _removeCredIdPerAddress() and _addCredIdPerAddress() from public to internal.
