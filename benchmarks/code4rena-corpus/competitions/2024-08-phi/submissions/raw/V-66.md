# Vulnerability details

## Impact
Lack of access control in `Cred:_removeCredIdPerAddress` allows for a malicious user to remove the credID from an existing user in the `_credIdsPerAddress` mapping. This affects the `_updateCuratorShareBalance` which in turn affects the `sellShareCred` when the victim tries to sell to 0.

## Proof of Concept (POC)
The function is set to public and removes the credID from a users mapping of `_credIdsPerAddress`.

In the following scenario these steps are taken:
- Participant creates a cred.
- anyone removes the cred from the participants mapping.
- logs are made to show the participant has no CredIds in the systems mapping.
- The Cred is shown as still active and the participant has one share.
- The Participant checks their positions in `getPositionsForCurator` which also shows 0
- The Participant tries to sell their share.
- The Participant buys another share.
- The Participant now sells the extra share successfully.
- The Participant is still unable to sell the remaining share.

Add the following getter functions to `Cred.sol`
```solidity
    //audit getter function
    function credIdExistsForAddress(address curator, uint256 credId) public view returns (bool) {
    return _credIdExistsPerAddress[curator][credId];

    function getCredIdsForAddress(address curator) public view returns (uint256[] memory) {
```

## Recommended Mitigation Steps

Change the visibility of the function to internal to prevent unwanted calling from users as this function is designed to be used internally by functions within the contract and not external users.
