# Vulnerability details

The factory contract performs external calls (including calls to itself) to protocol contracts 
and forwards Ether provided by a user. However, in one case the Ether gets stuck on the factory contract balance 
(and can be extracted by an attacker, see "Missing payment validation during `claim` allows an attacker to steal Ether from the PhiFactory contract").
The same problem exists in `PhiNFT1155` (introduced in the `Claimable` abstract base). A user can claim via an NFT contract,
however, any Ether refunded by an internal call gets stuck on the NFT contract balance.

For example, [here](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L737-L744) 
the factory does a refund duly:

```solidity
        // Handle refund
        uint256 mintFee = getArtMintFee(artId_, quantity_);
        if ((etherValue_ - mintFee) > 0) {
            _msgSender().safeTransferETH(etherValue_ - mintFee);
        }
        protocolFeeDestination.safeTransferETH(mintProtocolFee * quantity_);

        (bool success_,) = art.artAddress.call{ value: mintFee - mintProtocolFee * quantity_ }(
```

However, this is not always the case. Consider [this piece of code](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L318-L320)

```solidity
        for (uint256 i = 0; i < encodeDatas_.length; i++) {
            this.claim{ value: ethValue_[i] }(encodeDatas_[i]);
        }
```

Any Ether still residing on the factory balance after the claims gets stuck. The factory makes no attempts to issue 
a refund to the caller.

The same issue exists in `Claimable` code:

```solidity
    function signatureClaim() external payable {
        // ...
        phiFactoryContract.signatureClaim{ value: msg.value }(signature, claimData_, mintArgs_);
        // a refund gets stuck on the balance here
    }

    function merkleClaim() external payable {
        // ...
        phiFactory.merkleClaim{ value: msg.value }(proof, claimData, mintArgs, leafPart);
        // a refund gets stuck on the balance here
    }
```

`PhiNFT1155` is able to receive a refund from the factory because of `receive` 
[existence](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/art/PhiNFT1155.sol#L359-L361):

```solidity
    receive() external payable {
        // This function is intentionally left empty to allow the contract to receive ETH
    }
```

## Impact

Eventually, user funds get stuck on the factory contract balance and may be retrieved by an attacker because of another 
vulnerability illustrated in another finding. Funds may also get stuck on an NFT contract balance.
One may argue that it's a user's mistake. However, the protocol makes
a consistent effort to issue refunds, e.g. 
[here](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L737-L744), 
[here](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L207-L210), 
[here](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L640-L643).
The flaws discussed above undermine this effort.

## Recommended Mitigation Steps

One possible way of action is to compare the factory balance before and after a call and refund the excess to the sender,
if any. E.g.:

```solidity
+       uint startingBalance = address(this).balance - msg.value;
        for (uint256 i = 0; i < encodeDatas_.length; i++) {
            this.claim{ value: ethValue_[i] }(encodeDatas_[i]);
        }
+       if (address(this).balance > startingBalance) {
+           _msgSender().safeTransferETH(address(this).balance - startingBalance);
+       }
```

Another possible way of action is to avoid refunds altogether and revert a transaction if the value provided is 
incorrect. It would be beneficial to overall protocol security.
