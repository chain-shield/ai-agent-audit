# Vulnerability details

## Impact
We can have a Credential Creator which uses `multisig wallet`, which won't be uncommon, when some organizations want to use the Phi Protocol to create a Cred. 

Phi protocol supports **multichain interactions**.
Given that Cred Creator is multisig. Then if an artist goes onto another supported chain by Phi and creates an art for a Credential which was created on another chain and chooses "MERKLE" as verificationType, then Cred Creator is set to receive `verifier rewards`.

However, since he is `multisig`, he may not be able to claim them, on this chain or possibly someone could steal them.

## Proof of Concept
When Cred Creator is also the verifier for `PhiFactory.merkleClaim()` operation for an art, and is a multisig wallet contract, its possible that the wallet owners may not have control over the same address on different supported chain from the one they created the cred, causing the rewards to not be retrieved.

When _**creating**_ art, credCreator is taken from signature, so its a valid use-case that it can be from another chain:
```solidity
    function _initializePhiArt(PhiArt storage art, ERC1155Data memory createData_) private {
        (
            uint256 credId,
@>>         address credCreator,
            string memory verificationType,
            uint256 credChainId,
            bytes32 merkleRootHash
        ) = abi.decode(createData_.credData, (uint256, address, string, uint256, bytes32));

        art.credId = credId;
@>>     art.credCreator = credCreator;
        art.credChainId = credChainId;
```

When **_claiming_** art:
```solidity
    function merkleClaim(...) {
        (address minter_, address ref_, uint256 artId_) = abi.decode(encodeData_, (address, address, uint256));
        PhiArt storage art = arts[artId_];
        
        ..... skipping code .....
@>>     //@audit-info verifier is set to art.credCreator
        _processClaim(
@>>         artId_, minter_, ref_, art.credCreator, mintArgs_.quantity, leafPart_, mintArgs_.imageURI, msg.value
        );
    }
```
`depositRewards()` in PhiRewards is called upon claim, and in this [code snippet](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/PhiRewards.sol#L104), we increase balance of verifier so he can then withdraw it via` RewardControl.sol`

However there, we can **force-withdraw** anyone without a signature:
```solidity
@>>  function withdrawFor(address from, uint256 amount) external {
@>>     _withdraw(from, from, amount);
    }
```

In the worst case, since **force-withdraw** is possible, attacker could possibly steal the ETH rewards by taking control of the  address on chain where the art is claimed (Similar to [Wintermute hack](https://rekt.news/wintermute-rekt/)).

## Recommended Mitigation Steps

Deny option to use Merkle proofs for art when `chainId != block.chainId`. This way verified will always be the deployed backend.
This won't be a problem for `signature claim`, as then the backend which is hosted by protocol's team is responsible to secure this case, by ensuring they own the address on every chain, before deployment.

```diff
    function _createNewNFTContract(
        PhiArt storage art,
        uint256 newArtId,
        ERC1155Data memory createData_,
        uint256 credId,
        uint256 credChainId,
        string memory verificationType
 ```       
