# Vulnerability details

In `PhiFactory.sol`, the claim function decompresses and decodes the `encodeData_` parameter to get the `artId` and `quantity` values: [PhiFactory.sol#claim:L282](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L282)
```solidity
function claim(bytes calldata encodeData_) external payable {
    bytes memory encodedata_ = LibZip.cdDecompress(encodeData_);
    (uint256 artId) = abi.decode(encodedata_, (uint256));
    // ...
    uint256 mintFee = getArtMintFee(artId, quantity_);
    // ...
}
```
However, the [_validateAndUpdateClaimState](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L702-L721) function, which is called by `claim`, uses the `artId_` and `quantity_` parameters directly to check if the `msg.value` is sufficient: [PhiFactory.sol#L709](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L709)
```solidity
function _validateAndUpdateClaimState(uint256 artId_, address minter_, uint256 quantity_) private {
    // ...
    if (msg.value < getArtMintFee(artId_, quantity_)) revert InvalidMintFee();
    // ...
}
```
This inconsistency allows an attacker to provide different values for `artId` and `quantity` in the encoded data, bypassing the payment validation.

## Impact
The protocol suffers a loss of revenue as the attacker can claim art without paying the required mint fee. The attacker gains the art without incurring the intended cost.

## Proof of Concept
Internal pre-conditions:

1. The `PhiFactory` contract is initialized with valid parameters.
2. An art is created with a non-zero mint fee.

Attack Path:


* The attacker encodes the `artId` and a `quantity` of 1 in the `encodeData_` parameter.
* The attacker calls the `claim` function with the encoded data and a `msg.value` of 0.
* The `claim` function decompresses and decodes the `encodeData`_ to get the `artId`.
* The `_validateAndUpdateClaimState` function is called with the `artId_` and quantity_ parameters, which are different from the values used in the claim function.
* The `msg.value` is compared against the mint fee calculated using the `artId_` and `quantity_` parameters, which may not match the actual `artId` and quantity used in the `claim` function.
* The payment validation passes, and the attacker successfully claims the art without paying the required mint fee.

Manual review

## Recommended Mitigation Steps
Ensure that the `artId` and `quantity` values are consistently used throughout the `claim` function and its called functions. One way to achieve this is by decoding the `encodeData_` parameter in the claim function and passing the decoded values to the `_validateAndUpdateClaimState` function
```diff
function claim(bytes calldata encodeData_) external payable {
    bytes memory encodedata_ = LibZip.cdDecompress(encodeData_);
-   (uint256 artId) = abi.decode(encodedata_, (uint256));
+   (uint256 artId, uint256 quantity) = abi.decode(encodedata_, (uint256, uint256));
    // ...
-   _validateAndUpdateClaimState(artId, minter_, mintArgs_.quantity);
+   _validateAndUpdateClaimState(artId, minter_, quantity);
    // ...
}
```
