# Vulnerability details

## Description 

The `Cred` contract implements a `SHARE_LOCK_PERIOD` to prevent rapid buying and selling of shares, which is intended to stabilize the market and prevent manipulation. The [`_handleTrade` function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L588-L659) is responsible for handling both buy and sell operations of shares. However, the current implementation only enforces the `SHARE_LOCK_PERIOD` for sell operations and updates the `lastTradeTimestamp` only on buy operations. This creates a vulnerability where users can bypass the lock period by transferring shares to another address they control and then selling them immediately.

### Detailed Description
The `Cred` contract includes a `SHARE_LOCK_PERIOD` to prevent rapid trading. The `_handleTrade` function is central to this mechanism, handling both buy and sell operations. The function's logic is as follows:

- For buy operations, the function updates the `lastTradeTimestamp` to the current block timestamp.
- For sell operations, the function checks if the current timestamp is within the `SHARE_LOCK_PERIOD` since the last trade and reverts if it is.

This logic creates a loophole:
1. A user buys shares of a cred.
2. Immediately after buying, they transfer these shares to another address they control.
3. The new address can then immediately sell these shares, bypassing the `SHARE_LOCK_PERIOD`.

This undermines the purpose of the `SHARE_LOCK_PERIOD`, which is likely intended to prevent rapid buying and selling (pump and dump schemes) or other forms of market manipulation.

The relevant part of the `_handleTrade` function is as follows:

```solidity
function _handleTrade(
    uint256 credId_,
    uint256 amount_,
    bool isBuy,
    address curator_,
    uint256 priceLimit
)
    internal
    whenNotPaused
{
    if (isBuy) {
        // ... (buy logic)
        lastTradeTimestamp[credId_][curator_] = block.timestamp;
    } else {
        if (block.timestamp <= lastTradeTimestamp[credId_][curator_] + SHARE_LOCK_PERIOD) {
            revert ShareLockPeriodNotPassed(
                block.timestamp, lastTradeTimestamp[credId_][curator_] + SHARE_LOCK_PERIOD
            );
        }
        // ... (sell logic)
    }

    // ... (remaining code)
}
```



## Impact
This allows users to bypass the `SHARE_LOCK_PERIOD`, leading to potential market manipulation and rapid trading. This can significantly impact the platform's stability and fairness, as it allows for pump and dump schemes and other forms of market manipulation. 

## Proof of Concept
1. **User A** buys shares of a cred.
2. Immediately after buying, **User A** transfers these shares to **User B** (another address they control).
3. **User B** can then immediately sell these shares, bypassing the `SHARE_LOCK_PERIOD`.

## Tools Used
Manual review

## Recommended Mitigation Steps
To fix this issue, the `SHARE_LOCK_PERIOD` should be enforced for both buy and sell operations, and the `lastTradeTimestamp` should be updated for both operations.
