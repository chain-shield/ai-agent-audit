# Vulnerability details

## Impact
The curator will an approximate loss of the share amount they intended to buy. The attacker (curator) loses the payment for the shares but doesn't gain the corresponding share balance.

## Proof of Concept
The incorrect usage of the `curator_` parameter in `_executeBatchBuy` will cause the share balance to not be updated correctly for the curator when they buy shares for themselves.

The [_executeBatchBuy function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L785-L796)
```soldiity
function _executeBatchBuy(
    uint256[] calldata credIds_,
    uint256[] calldata amounts_,
    address curator_,
    uint256[] memory prices,
    uint256[] memory protocolFees,
    uint256[] memory creatorFees
)
    internal
{
    _executeBatchTrade(credIds_, amounts_, curator_, prices, protocolFees, creatorFees, true);
}
```
The choice to pass the `curator_` parameter directly to `_executeBatchTrade` is a mistake because it should be the` _msgSender()` (the actual buyer) instead of the `curator_` when the curator is buying shares for themselves.

It takes the curator to call [batchBuyShareCred](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L191-L211) with themselves as the `curator_` parameter.
In [Cred.sol:L666-L680, the _updateCuratorShareBalance](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L666-L682) function:
```solidity
function _updateCuratorShareBalance(uint256 credId_, address sender_, uint256 amount_, bool isBuy) internal {
    (, uint256 currentNum) = shareBalance[credId_].tryGet(sender_);

    if (isBuy) {
        if (currentNum == 0 && !_credIdExistsPerAddress[sender_][credId_]) {
            _addCredIdPerAddress(credId_, sender_);
            _credIdExistsPerAddress[sender_][credId_] = true;
        }
        shareBalance[credId_].set(sender_, currentNum + amount_);
    } else {
        if ((currentNum - amount_) == 0) {
            _removeCredIdPerAddress(credId_, sender_);
            _credIdExistsPerAddress[sender_][credId_] = false;
        }
        shareBalance[credId_].set(sender_, currentNum - amount_);
    }
}
```
The `sender_` parameter is used to update the `shareBalance` mapping, but it receives the `curator_` address instead of the actual buyer's address (`_msgSender()`).

Scenario

* Curator calls `batchBuyShareCred` with themselves as the `curator_` parameter.
* Inside `batchBuyShareCred`, the function `_validateAndCalculateBatch` is called to validate the input and calculate the total cost.
* The function proceeds to execute the batch buy operation by calling `_executeBatchBuy`.
* `_executeBatchBuy` calls `_executeBatchTrade` with the `curator_` parameter as the buyer's address.
* `_executeBatchTrade` calls `_updateCuratorShareBalance` with the `curator_` address as the `sender_` parameter.
* The share balance is updated using the `curator_` address instead of the actual buyer's address (`_msgSender()`).
* The curator's share balance remains unchanged, even though they paid for the shares.

## Tools Used
Manual review

Recommended Mitigation Steps
Modify the `_executeBatchBuy` function to pass the `_msgSender()` as the `curator_` parameter when calling `_executeBatchTrade`:
```diff
function _executeBatchBuy(
    uint256[] calldata credIds_,
    uint256[] calldata amounts_,
    address curator_,
    uint256[] memory prices,
    uint256[] memory protocolFees,
    uint256[] memory creatorFees
)
    internal
{
-   _executeBatchTrade(credIds_, amounts_, curator_, prices, protocolFees, creatorFees, true);
+   _executeBatchTrade(credIds_, amounts_, _msgSender(), prices, protocolFees, creatorFees, true);
}
```
