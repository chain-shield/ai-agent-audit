# Vulnerability details

## Impact
Inconsistencies in the `credIdCounte`r, leading to issues with cred ID sequencing and tracking. This can cause confusion and complications for users and other parts of the system that rely on accurate cred ID information.

Scenario:

1. The `createCred` function is called with valid parameters, including `creator`, `signedData`, `signature`, `buyShareRoyalty`, and `sellShareRoyalty`.
2. Inside the `createCred` function, the `_createCredInternal` function is called to create a new cred.
3. The `_createCredInternal` function updates the `creds` mapping with the new cred details and increments the `credIdCounter`.
4. However, after the `_createCredInternal` function call, the `createCred` function proceeds to call the `buyShareCred` function with the newly created `credIdCounter` value.
5. If the `buyShareCred` function fails for any reason (e.g., insufficient payment), it will revert the transaction.
6. As a result, the `credIdCounter` is not incremented, violating the expected behavior defined in the `protocolFeeTransferred` rule.

## Proof of Concept
A lack of error handling in the `createCred` function will cause inconsistencies in the `credIdCounter` for the protocol as an attacker will exploit the missing error handling to mint creds with incorrect `credIdCounter` values.

> The `createCred` function calls `_createCredInternal` to create a new cred and then immediately calls `buyShareCred` with the newly created `credIdCounter` value. If the `buyShareCred` function fails, it will revert the entire transaction, including the `credIdCounter` increment.
```solidity
function createCred(
    address creator_,
    bytes calldata signedData_,
    bytes calldata signature_,
    uint16 buyShareRoyalty_,
    uint16 sellShareRoyalty_
)
    public
    payable
    whenNotPaused
{
    // ...

    uint256 credId = _createCredInternal(
        creator_, credURL, credType, verificationType, bondingCurve, buyShareRoyalty_, sellShareRoyalty_
    );
    buyShareCred(credId, 1, 0);

    // ...
}
```

**Attack Scenario**

* The attacker calls the `createCred` function with valid parameters to create a new cred.
* Inside `createCred`, the `_createCredInternal` function is called, which creates a new cred and increments the `credIdCounter`.
* After the `_createCredInternal` call, the `buyShareCred` function is called with the newly created `credIdCounter` value.
* The buyShareCred function fails due to insufficient payment or other reasons, causing the entire transaction to revert.
* As a result, the `credIdCounter` is not incremented, but the new cred is still created with an incorrect `credIdCounter` value.

## Recommended Mitigation Steps
The `createCred` function should handle the failure of `buyShareCred` separately, ensuring that the `credIdCounter` is incremented regardless of the success or failure of the `buyShareCred` function call by wrapping the `buyShareCred` function call inside a try-catch block.
```diff
function createCred(
    address creator_,
    bytes calldata signedData_,
    bytes calldata signature_,
    uint16 buyShareRoyalty_,
    uint16 sellShareRoyalty_
)
    public
    payable
    whenNotPaused
{
    // ...

    uint256 newCredId = _createCredInternal(
        creator_, credURL, credType, verificationType, bondingCurve, buyShareRoyalty_, sellShareRoyalty_
    );

+   try buyShareCred(newCredId, 1, 0) {} catch {}

    // ...
}
```
By adding the try-catch block, the `credIdCounter` will be incremented even if the `buyShareCred` function fails, ensuring the consistency of the `credIdCounter` and preventing attackers from minting creds with incorrect ID values.
