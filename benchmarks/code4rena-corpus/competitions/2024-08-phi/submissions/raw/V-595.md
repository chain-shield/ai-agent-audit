# Vulnerability details

### Summary
In the Phi Protocol, NFT royalties are designed to provide creators with a percentage of the secondary sale price of their NFTs. This is managed through the `CreatorRoyaltiesControl` contract within the `PhiNFT1155` contract. The royalty system aims to ensure continuous income for creators from their digital assets.

The `updateRoyalties` function allows creators to adjust the royalty configuration, including the recipient and the percentage. However, this function lacks protective measures against front-running, which enables attackers to exploit the system.

## Vulnerability Details

The vulnerability arises from the immediate application of royalty updates. Attackers can monitor the mempool for transactions that indicate upcoming royalty increases. They can then:

1. **Purchase or Mint the NFT** at the existing lower royalty rate before the royalty update is processed.
2. **Sell the NFT** immediately after the creator's transaction is executed, benefiting from the difference in royalty amounts.

### Scenario
For instance, if an attacker sees a transaction that will increase the royalty rate from 5% to 10%, they can buy the NFT at the lower rate and sell it after the update, profiting from the increased royalty burden on the new buyer.

## Impact

### Financial Consequences
This vulnerability can lead to significant financial losses for creators, undermining the purpose of royalties. Attackers can siphon off potential earnings, which discourages creators from using the platform.

### Market Manipulation
The anticipation of royalty hikes can artificially inflate NFT prices, creating volatility and potential losses for genuine buyers. This undermines trust in the ecosystem.


## Proposed Fix

### Implementation of a Time Delay Mechanism
Introduce a time delay mechanism within the `_updateRoyalties` function:

```solidity
mapping(uint256 => uint256) public pendingRoyaltyUpdates;

function _updateRoyalties(uint256 tokenId, RoyaltyConfiguration memory configuration) internal {
    // Existing validation logic

    // Set a future timestamp for the update to take effect
    pendingRoyaltyUpdates[tokenId] = block.timestamp + 24 hours; 

    emit UpdatedRoyalties(tokenId, msg.sender, configuration);
}

// Modify getRoyalties to check for pending updates
function getRoyalties(uint256 tokenId) public view returns (RoyaltyConfiguration memory) {
    // Existing logic

    // If there's a pending update and it's time, apply it
    if (pendingRoyaltyUpdates[tokenId] != 0 && block.timestamp >= pendingRoyaltyUpdates[tokenId]) {
        delete pendingRoyaltyUpdates[tokenId]; // Clear the pending update
        return royalties[tokenId]; 
    }

    // Rest of the existing logic
}
```

### Explanation of the Fix
1. **Pending Updates Mapping**: A mapping is introduced to store the timestamp when a royalty update should take effect.
2. **Future Timestamp Setting**: When `_updateRoyalties` is called, it sets a future timestamp (e.g., 24 hours later) instead of applying the update immediately.
3. **Conditional Update Application**: The `getRoyalties` function checks for pending updates and applies them only after the specified time has passed, allowing the market to react.
