# Vulnerability details

## Description
In `Cred.sol` of a particular `CHAIN` the credentials are always created in ascending order. Meaning the `credId` would always start from `1` & proceed from there on.
Similiarly in `PhiFactory.sol` of the same `CHAIN` the artist will create the art representing the above `credId` & thus `artId` would always start from `1` as well.
Now `artId` is always increased when a NFT proxy of `PhiNFT1155` is successfully deployed. If it reverts for some reason `artId` would still be `1` for protocol
Conditions for the `PhiNFT1155` to be successfully deployed is in `PhiFactory::_createNewNFTContract` as below :
```solidity
        function _createNewNFTContract(..., uint256 newArtId, ... ,uint256 credId, ...){
@>          address payable newArt = payable(erc1155ArtAddress.cloneDeterministic(keccak256(abi.encodePacked(block.chainid, newArtId, credId))));
            ...
        }
```
Here we can see the `salt` for the new contract to be dployed is deterministic as `block.chainid`, `newArtId`, `credId`, Menaing the address of the about to be deployed contract depends on factors which could be controlled by
any malicious actor.
If the actor decides to deploy a contract outside the protocol in the particular chain, using `block.chainid`, `newArtId = 1`, `credId = 1`, now the protocol wont be able to deploy a contract as it would start reverting.
Also the `newArtId` of the protocol would always be `1` and never increase because the contract was not successfully deployed.

Now the protocol is DoS'ed unless the salt changes somehow, which could only change if `credId` changes.

But what if malicious actor creates mutliple credentials ranging from `credId` `1 to 100`, now no one could deploy contract. And this would keep going on.
Which will DoS the entire protocol forever.

## Impact
The protocol would be DoS'ed forever and thus no one could ever generate any art out of it cuzz `artId = 1` is already used outside the protocol and protocol is stuck at `artId = 1`

## Recommended Mitigation Steps
The `salt` must depend on something which is artist controllable, deterministic , but could not be able to access by a malicious actor.
It is the address of the artist, but as `msg.sender` as shown below :
```diff
        function _createNewNFTContract(..., uint256 newArtId, ... ,uint256 credId, ...){
-         address payable newArt = payable(erc1155ArtAddress.cloneDeterministic(keccak256(abi.encodePacked(block.chainid, newArtId, credId))));
+         address payable newArt = payable(erc1155ArtAddress.cloneDeterministic(keccak256(abi.encodePacked(block.chainid, newArtId, credId, msg.sender))));
            ...
        }
```
