# Vulnerability details

As it will be illustrated in a PoC, as a number of curators of a cred grows to about 825, enumerating them in 
`CuratorRewardsDistributor` and updating the mapping `PhiRewards.balanceOf` will require the amount of gas above 
the block gas limit.
Rewards distribution for this cred will be blocked because gas usage hits the block gas limit and the transaction
reverts.

`CuratorRewardsDistributor.distribute` gets curator addresses via `credContract.getCuratorAddresses` and then retrieves
a share balance of each curator using `credContract.getShareNumber` calls. That is a lot of static calls, although 
it's much cheaper to retrieve both addresses and balances using `Cred.getCuratorAddressesWithAmount`. 

Then `CuratorRewardsDistributor.distribute` creates calldata for `phiRewardsContract.depositBatch`. Note that memory 
costs in EVM grow *quadratically*. 

But the main culprits are balance updates inside `RewardControl`
(a part of `phiRewardsContract`). This is so because an update of a storage slot from zero to a non-zero value costs 20,000 gas.
It may be expected that there'll be many zero balances if curators withdraw their rewards in full.

Besides, take into account that storage access costs may increase significantly, rendering the discussed code unexecutable. Such a change may be introduced in a hardfork, e.g. the cost of the `sload` opcode was increased 10 times recently. Any code having prolonged loops and hoping that constants fine-tuning was done right is in danger.

## Impact

Assets are not at direct risk, but the function of the protocol or its availability could be impacted since some curators
won't get their rewards. However, there is a temporary workaround: deposit dust amounts of Ether to some curators with 
zero balances inside `PhiRewards` to reduce some zero-to-nonzero `sstore` costs.

## Proof of Concept

Please insert this test into `test/CuratorRewardsDistributor.t.sol` and run with 
`forge test --match-test testBigDistribute -vv --isolate`.

Please note that
* The PoC illustrates gas usage over 30Mgas (the current Ethereum block gas limit). Details of `sload` costs and block gas limit may vary from chain to chain.
* It took 825 shareholders to block rewards distribution (quite lower than the 999 limit) and the maximum share price is quite moderate: just 0.34 Ether.
* `--isolate` option is needed to "disable" slot re-read discounts which manifest themselves since `shareBalance`
    slots are actively read during the setup phase.

```solidity
    function testBigDistribute() public {
        uint256 credId = 1;
        uint256 depositAmount = 1 ether;
        uint256 backers = 825;

        uint256 totalCap = bondingCurve.getBuyPriceAfterFee(credId, 1, backers);
        console2.log("Total shares price: ", totalCap / 1 ether, "Ether");
        uint256 maxSharePrice = bondingCurve.getBuyPriceAfterFee(credId, backers, 1);
        console2.log("Max share price: ", maxSharePrice * 1000 / 1 ether, "milli Ether");

        // Deposit some ETH to the curatorRewardsDistributor
        curatorRewardsDistributor.deposit{ value: depositAmount }(credId, depositAmount);

        vm.deal(user1, totalCap);
        vm.startPrank(user1);
        for (uint i = 0; i < backers; i++) {
            cred.buyShareCredFor{value: maxSharePrice}(credId, 1, address(uint160(i + 1000)), 0);
        }
        vm.stopPrank();

        uint gas = gasleft();
        vm.prank(user2);
        curatorRewardsDistributor.distribute(credId);
        uint gasSpend = gas - gasleft();

        console2.log("distribute() gas: ", gasSpend);
    }
```

## Recommended Mitigation Steps

A simple improvement is to use `Cred.getCuratorAddressesWithAmount` in place of many calls to `Cred`.

However, a general and more fair solution is to use a scheme that accrues rewards continuously and tracks precise
per-token reward amounts. Such schemes are typical for staking, e.g. 
[see here](https://github.com/nominex/eth-smart-contracts/blob/7a14f0d13d0a51f06fa22e103bdf25ba8aeb43e8/contracts/StakingService.sol).
