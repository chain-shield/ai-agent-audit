# Vulnerability details

## Impact

Arbitrary royalty can be set by the creator for their art, e.g. 500%, leading to potentially large losses for users.

## Summary

Function [CreatorRoyaltiesControl::_updateRoyalties](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/abstract/CreatorRoyaltiesControl.sol#L58-L66), which is called from [PhiNFT1155::updateRoyalties](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/art/PhiNFT1155.sol#L195-L203), lacks any enforcement on the supplied royalties:

```solidity
function _updateRoyalties(uint256 tokenId, RoyaltyConfiguration memory configuration) internal {
    if (configuration.royaltyRecipient == address(0) && configuration.royaltyBPS > 0) {
        revert InvalidRoyaltyRecipient();
    }
    royalties[tokenId] = configuration;

    emit UpdatedRoyalties(tokenId, msg.sender, configuration);
}
```

It is worth contrasting this implementation with the implementation of [CuratorRewardsDistributor:updateRoyalty](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/CuratorRewardsDistributor.sol#L57-L63), which performs proper bounds enforcement:

```solidity
    function updateRoyalty(uint256 newRoyalty_) external onlyOwner {
        if (newRoyalty_ > MAX_ROYALTY_RANGE) {
            revert InvalidRoyalty(newRoyalty_);
        }
        withdrawRoyalty = newRoyalty_;
        emit RoyaltyUpdated(newRoyalty_);
    }
```

As stated in the [README: EIP compliance checklist](https://github.com/code-423n4/2024-08-phi/blob/main/README.md#eip-compliance-checklist), [PhiNFT1155](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/art/PhiNFT1155.sol) is supposed to be ERC1155 compatible. [ERC-2981](https://eips.ethereum.org/EIPS/eip-2981) states that

> ERC-721 and ERC-1155 compliant contracts MAY implement this ERC for royalties to provide a standard method of specifying royalty payment information.

Moreover, as detailed in the ERC-2981:

> Marketplaces that support this standard SHOULD implement some method of transferring royalties to the royalty recipient. Standards for the actual transfer and notification of funds will be specified in future EIPs.

> Marketplaces MUST pay the royalty in the same unit of exchange as that of the _salePrice passed to royaltyInfo(). This is equivalent to saying that the _salePrice parameter and the royaltyAmount return value MUST be denominated in the same monetary unit. For example, if the sale price is in ETH, then the royalty payment must also be paid in ETH, and if the sale price is in USDC, then the royalty payment must also be paid in USDC.

> Implementers of this standard MUST calculate a percentage of the _salePrice when calculating the royalty amount. Subsequent invocations of royaltyInfo() MAY return a different royaltyAmount. Though there are some important considerations for implementers if they choose to perform different percentage calculations between royaltyInfo() invocations.

As an example, at [Magic Eden](https://help.magiceden.io/en/articles/8995481-setting-up-royalties-on-magic-eden-s-evm-platform) the royalty setup for ERC2981 compliant contracts is automatic:

> ERC2981 setup: Initially, if a collection has ERC2981 setup on the contract, royalties will be distributed according to the specifications of this protocol. This ensures seamless and transparent royalty payments for creators. No further action is needed to be taken by the creator or the platform.

`PhiNFT1155` does indeed implement ERC-2981, thus marketplaces will have the assumption that the royalty will be calculated as a percentage of the sale price. But as detailed in the finding, `PhiNFT1155` fails to enforce any reasonable constraints on the percentage, thus leading to potential (and large) losses for users if a malicious creator sets a very high royalty.
