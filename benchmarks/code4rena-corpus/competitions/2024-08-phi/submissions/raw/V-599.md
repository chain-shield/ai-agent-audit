# Vulnerability details

### Summary
The Cred contract is responsible for managing user shares in various credentials (creds). It maintains internal mappings to track which creds a user owns and their respective amounts.

Two functions, `_addCredIdPerAddress` and `_removeCredIdPerAddress`, are mistakenly marked as `public` instead of `internal`. This oversight allows external actors to manipulate the mappings directly.

### Impact
1. **Unauthorized Addition of Creds**: External actors can call `_addCredIdPerAddress`, inflating a user's cred count or adding non-existent creds.
2. **Unauthorized Removal of Creds**: The same applies to `_removeCredIdPerAddress`, allowing removal of legitimate creds from a user's portfolio.
3. **Data Inconsistency**: These unauthorized actions can create discrepancies between the actual shares and the recorded mappings.
4. **Potential Economic Attacks**: Manipulating these mappings could lead to economic exploits, depending on how other system components rely on this data.

### Scenario
- An attacker could repeatedly call `_addCredIdPerAddress` to add fake creds.
- They could also use `_removeCredIdPerAddress` to eliminate legitimate creds from other users.
- Such actions could disrupt the integrity of the contract's record-keeping and lead to broader system vulnerabilities.

### Proposed Fix
Change the visibility of the functions from `public` to `internal`:

```solidity
function _addCredIdPerAddress(uint256 credId_, address sender_) internal { /* existing logic */ }
function _removeCredIdPerAddress(uint256 credId_, address sender_) internal { /* existing logic */ }
```
