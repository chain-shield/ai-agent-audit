# Vulnerability details

## Impact  

Whenever `distribute` is called in `CuratorRewardsDistributor`, all accumulated rewards from NFT minting are split and assigned to all curators on a given cred and then sent to `PhiRewards.sol` to be claimed. In order to calculate rewards for each curator, their addresses are fetched by invoking `getCuratorAddresses` on `Cred.sol` with start-stop indexes set as 0s meaning it would iterate through the entire length of `shareBalances` mapping 
```solidity
    function _getCuratorData(
        uint256 credId_,
        uint256 start_,                                                 // 0
        uint256 stop_                                                   // 0
    )
        internal
        view
        returns (CuratorData[] memory)
    {
        uint256 stopIndex;
        if (stop_ == 0 || stop_ > shareBalance[credId_].length()) {    // if stop = 0
            stopIndex = shareBalance[credId_].length();                // stopIndex set as the entire shareBalance length
        } else {
            stopIndex = stop_;
        }
    }
```
Afterwards, a for-loop is entered and checks the shareBalance of each address, stores each curator who has at least 1 share and proceeds further with reward split and distribution.  

The issue arises in the fact that `shareBalance` mapping is never shrank when signals are being sold. Instead, whenever a user sells all of their cred shares, their balance is simply set to 0 and they remain assigned in the `shareBalance` mapping  

```solidity
    function _updateCuratorShareBalance(uint256 credId_, address sender_, uint256 amount_, bool isBuy) internal {
        (, uint256 currentNum) = shareBalance[credId_].tryGet(sender_);


        if (isBuy) {
            if (currentNum == 0 && !_credIdExistsPerAddress[sender_][credId_]) {
                _addCredIdPerAddress(credId_, sender_);
                _credIdExistsPerAddress[sender_][credId_] = true;
            }
            shareBalance[credId_].set(sender_, currentNum + amount_);
        } else {                                                        // if selling cred 
            if ((currentNum - amount_) == 0) {
                _removeCredIdPerAddress(credId_, sender_);
                _credIdExistsPerAddress[sender_][credId_] = false;
            }
            shareBalance[credId_].set(sender_, currentNum - amount_);  // @audit curator remains within the mapping with 0 shares
        }
    }
```
Malicious actors can continuously buy-sell 1 share of a cred from different addresses to artificially inflate the `shareBalance` mapping with 0s until it becomes large enough to cause an out-of-gas error in `Cred._getCuratorData`, permanently DoS-ing distribute for a given cred since there is currently no way to shrink `shareBalance`.  

Impact - Permanent DoS, permanently stuck funds in `CuratorRewardsDistributor` since distribution will always revert

## Tools used

Manual review

## Recommendation mitigation steps  

Remove curator addresses from `shareBalance` mapping when their shares reach 0
