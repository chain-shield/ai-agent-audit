# Vulnerability details

## Impact
The _curve function in `BondingCurve.sol` includes a division operation that could result in division by zero if `targetAmount_` equals `TOTAL_SUPPLY_FACTOR`.
https://github.com/code-423n4/2024-08-phi/blob/main/src/curve/BondingCurve.sol#L118
```solidity
(TOTAL_SUPPLY_FACTOR * CURVE_FACTOR * 1 ether) / (TOTAL_SUPPLY_FACTOR - targetAmount_)
```
In `Cred.sol`, the check `supply + amount_ > MAX_SUPPLY` is located after the call to `getPriceData`. This order of operations allows the division by zero to potentially occur before the maximum supply validation is enforced.

A division by zero can cause the transaction to revert unexpectedly, which may disrupt the functionality of the smart contract. Depending on the context of the call, this can affect multiple users and lead to a denial of service (DoS).

## Proof of Concept
Here is the problematic code sequence in `Cred.sol`:
```solidity
// Call to BondingCurve contract's getPriceData  
(uint256 price, uint256 protocolFee, uint256 creatorFee) = IBondingCurve(cred.bondingCurve).getPriceData(credId_, supply, amount_, isBuy);  

// This validation is too late  
if (supply + amount_ > MAX_SUPPLY) {  
    revert SupplyExceedsMaxSupply();  
}
```

## Recommended Mitigation Steps
Add a check in the `_curve` function to handle cases when `targetAmount_` equals `TOTAL_SUPPLY_FACTOR` to ensure safe division.

```solidity
function _curve(uint256 targetAmount_) private pure returns (uint256) {
    require(targetAmount_ != TOTAL_SUPPLY_FACTOR, "Invalid targetAmount: equals TOTAL_SUPPLY_FACTOR");
    return (TOTAL_SUPPLY_FACTOR * CURVE_FACTOR * 1 ether) / (TOTAL_SUPPLY_FACTOR - targetAmount_)
        - CURVE_FACTOR * 1 ether - INITIAL_PRICE_FACTOR * targetAmount_ / 1000;
}
```
