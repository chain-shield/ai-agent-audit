# Vulnerability details

## Impact
Detailed description of the impact of this finding.
As described in the H-1 `Rewarddistribution is vulnerable to flash loan attacks` in the audit report, the distribution of rewards was prone to flashloan steals of the rewards distributed by allowing an attacked to buy => claim rewards => sell shares of a `Cred` in the same transaction. 

The mitigation of the issue was to add a `SHARE_LOCK_PERIOD` where the owner could not sell the shares. 
While this works for most of the usecases, it does not work when the sender sends more value in `msg.value` which then gets sent back before state updates:

```solidity
cred.currentSupply += amount_;
uint256 excessPayment = msg.value - price - protocolFee - creatorFee;
if (excessPayment > 0) {
    _msgSender().safeTransferETH(excessPayment); <=== refund
}
lastTradeTimestamp[credId_][curator_] = block.timestamp; <=== state update after
```

Due to the `lastTradeTimestamp` being updated after the eth refund, an attacker can exploit this to circumvent the `SHARE_LOCK_PERIOD` check present at lines 625-629
```solidity
if (block.timestamp <= lastTradeTimestamp[credId_][curator_] + SHARE_LOCK_PERIOD) {
    revert ShareLockPeriodNotPassed(
        block.timestamp, lastTradeTimestamp[credId_][curator_] + SHARE_LOCK_PERIOD
    );
}
```
