# Vulnerability details

## Impact
The vulnerability in the Cred contract allows malicious actors to manipulate the selling mechanism of Signals (shares), leading to several severe consequences:

1. **Forced Holding and Price Manipulation**: Attackers can prevent legitimate users from selling their shares, forcing them to hold while the attacker sells at a higher price. This directly results in financial losses for honest users.

2. **Front-Running and Theft**: By monitoring the mempool for buy orders with high slippage, attackers can front-run these transactions, buy shares at a lower price, prevent the legitimate user from selling for the cooldown period, and then sell at a higher price. This amounts to direct theft from honest users.

3. **System Abuse by Cred Owners**: Cred owners can exploit this vulnerability to artificially inflate and maintain high signal levels by preventing users from selling their shares, undermining the integrity of the signaling system.

4. **Denial of Service**: Users can be permanently locked out of selling their shares, effectively trapping their funds in the contract.

These impacts severely undermine the fairness, functionality, and trustworthiness of the Cred system, potentially leading to significant financial losses and erosion of user trust.

## Proof of Concept
The vulnerability stems from the public visibility of the `_removeCredIdPerAddress` function in the Cred contract. This function can be directly called by anyone, allowing them to remove a user's ability to sell shares.

To demonstrate this vulnerability:

1. Add the following test to the `TestCred` contract in `test/Cred.t.sol`.
2. Run the test using the command `forge test --mt test_AvoidSell`.

```js
    function test_AvoidSell() public {
        _createCred("BASIC", "SIGNATURE", 0x0);

        vm.startPrank(anyone);
        // participant buys cred share
        cred.buyShareCred{value: cred.getCredBuyPriceWithFee(1, 1)}(1, 1, 0);
        assertEq(cred.isShareHolder(1, anyone), true, "cred 1 is voted by anyone");
        vm.stopPrank();

        // cooldown period
        vm.warp(block.timestamp + 10 minutes + 1 seconds);

        // attacker sees the sell order in mempool and front-runs it to not let the sell go through
        address attacker = address(0x10002000);
        vm.startPrank(attacker);
        cred._removeCredIdPerAddress(1, anyone);
        vm.stopPrank();

        // anyone tries to sell cred share
        vm.startPrank(anyone);

        vm.expectRevert();
        cred.sellShareCred(1, 1, 0);
    }
```

This test demonstrates how an attacker can prevent a legitimate user from selling their shares by calling `_removeCredIdPerAddress` directly, causing the subsequent `sellShareCred` call to revert due to the check on line 703:

```js
703   if (_credIdsPerAddress[sender_].length == 0) revert EmptyArray();
```

## Recommended Mitigation Steps
Change the visibility of [`_removeCredIdPerAddress`](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L695) from `public` to `internal`. This prevents direct external calls to this function.

```diff
- 695      function _removeCredIdPerAddress(uint256 credId_, address sender_) public {
+ 695      function _removeCredIdPerAddress(uint256 credId_, address sender_) internal {
```
