# Vulnerability details

## SUMMARY

The identified vulnerability in the rewards management lies within the `PhiRewards` contract, particularly in its approach to handling reward claims. The contract applies a strategy where the rewards to be distributed are dependent on the contract’s current balance. If the claimant's rewards exceed the available balance, the excess claims are unfulfilled. Furthermore, the contract fails to properly track or handle these unclaimed rewards, which could ultimately mislead users through inaccurate event emissions, suggesting that full rewards processing took place irrespective of actual payments made.

## RELEVANT CODE

```solidity
function handleRewardsAndGetValueSent(
    uint256 artId_,
    uint256 credId_,
    uint256 quantity_,
    uint256 mintFee_,
    bytes calldata addressesData_,
    bool chainSync_
) external payable {
    if (computeMintReward(quantity_, mintFee_) != msg.value) {
        revert InvalidDeposit();
    }

    depositRewards(
        artId_,
        credId_,
        addressesData_,
        quantity_ * (mintFee_ + artistReward),
        quantity_ * referralReward,
        quantity_ * verifierReward,
        quantity_ * curateReward,
        chainSync_
    );
}

function depositRewards(
    uint256 artId_,
    uint256 credId_,
    bytes calldata addressesData_,
    uint256 artistTotalReward_,
    uint256 referralTotalReward_,
    uint256 verifierTotalReward_,
    uint256 curateTotalReward_,
    bool chainSync_
) internal {
    (address minter_, address receiver_, address referral_, address verifier_) =
        abi.decode(addressesData_, (address, address, address, address));

    if (receiver_ == address(0) || minter_ == address(0) || verifier_ == address(0)) {
        revert InvalidAddressZero();
    }

    balanceOf[verifier_] += verifierTotalReward_;
    balanceOf[receiver_] += artistTotalReward_;
    if (chainSync_ && address(curatorRewardsDistributor) != address(0)) {
        curatorRewardsDistributor.deposit{ value: curateTotalReward_ }(credId_, curateTotalReward_);
    } else {
        balanceOf[receiver_] += curateTotalReward_;
    }
}

function computeMintReward(uint256 quantity_, uint256 mintFee_) public view returns (uint256) {
    return quantity_ * (artistReward + mintFee_ + referralReward + verifierReward + curateReward);
}
```

## VULNERABILITY DETAILS

The vulnerability stems from the `handleRewardsAndGetValueSent` function within the `PhiRewards` contract, where reward computations and transfers do not account for the full extent of the contract's balance limitations, leading to partially fulfilled claims without any capture of these insufficiencies. The function computes total rewards using `computeMintReward`, but thereafter accepts claims only if the provided `msg.value` matches exactly with the required amount. However, the contract does not implement tracking or subsequent handling mechanisms for these unfulfilled rewards.

The issue is exacerbated by the `depositRewards` function which directly updates the reward balances for artists, verifiers, and possible referrers without additional checks against the current balance. If the available funds are insufficient, the function fails silently, leading to a state where events—specifically `RewardsDeposit`—might inaccurately reflect that full rewards were granted even when full funds were not available for distribution. This misleading communication can cause users to believe their entire claim was processed, whereas, in reality, a portion or all of it could be lost permanently due to balance constraints.

Overall, this replication of past vulnerabilities underscores the necessity for robust unclaimed rewards tracking and appropriate communications via events ensuring users are adequately informed of the true state of rewards distributed. This vulnerability could have significant financial repercussions, inadvertently leaving users without the full rewards they were led to believe they would obtain.

## TECHNICAL IMPACT

The identified vulnerability in the `PhiRewards` contract has significant technical implications on the rewards management system of the Phi Protocol. The primary issue manifests through the style of reward handling which depends strictly on the contract’s available balance. Specifically, the vulnerability occurs when the computed rewards to be distributed exceed the contract's current balance, resulting in only partial payment of claims without any mechanism to account for or recover unclaimed rewards, effectively resulting in permanent asset loss for users.

### How the Vulnerability Can Be Exploited

The vulnerability can be exploited by performing reward claims when the contract’s balance is below the required total distributions. When users stake or perform actions warranting rewards, the contract calculates the total rewards via the `computeMintReward` function. However, the actual reward distribution relies on sufficient balance, without accounting for scenarios of balance shortfalls. If the balance is insufficient, claims can only be fulfilled up to the available amount, leaving the remainder unaccounted for. This is due to the lack of a balance check in critical functions like `depositRewards`, which directly adjusts balances even when there isn't enough ETH to meet the claims fully.

### Affected Parts of the System

The following components and functionalities are directly affected:

1. **User Trust and Interaction**: Users expecting full payouts based on contract functionality will be misled by the emitted events that suggest full claims were processed. This could lead to dissatisfaction and distrust in the protocol.
   
2. **Reward Components**: The PhiRewards contract's lack of a tracking mechanism for unclaimed rewards leads to discrepancies in financial distributions. Artists, verifiers, and curators, typically expected to receive specified rewards, will be affected when distribution fails to meet contractual obligations.

3. **Event Emission**: The emission of events such as `RewardsDeposit` is misleading as it does not differentiate between partial and full distributions. This communication failure masks the true state of transactions, potentially masking audit issues.

4. **Financial Accounting**: This issue directly affects the contract's financial accounting system by failing to record and adjust for significant liabilities—for instance, unfulfilled claims. This can result in inaccurate financial reporting within the protocol.

### Consequences at the Code Level

- **Financial Irregularities**: Users can end up permanently losing rewards due to untracked unclaimed or partially fulfilled reward claims, which impacts financial fairness and equitability.
- **System Instability**: Continuously operating under this paradigm could lead to instability as users potentially lose incentives to participate if their rewards remain unmet, compounded by inaccurate event outputs that fail to represent the real execution outcomes.
- **Data Corruption**: The absence of recordings or logs for failed claims further creates data integrity issues by misaligning actual balances and perceived distributions.

In summary, the lack of balance adequacy checks and mechanisms to handle unclaimed rewards result in potential financial losses, misleading user communications, and system instability for the Phi Protocol. The technical impact of such vulnerabilities unerringly parallels past issues and necessitates immediate rectification to prevent exploitation and rebuild user trust.
