# Vulnerability details

## Impact

`_addCredIdPerAddress` and `_removeCredIdPerAddress` are public and have no caller restrictions, allowing anyone to change the credid -> share owner mappings.

1. This will DoS all the `sellShare...` functions if the mapping is removed before the sale
2. This affects `getPositionsForCurator`. This function is not used internally by the project, but may confuse the user or an external Frontend that may use this function to get curator positions

Case 1. Adding permamently invalid cred holder:
```solidity
function test_AccessControl() public {
    uint256 credId = createCred_helper(
        CURATOR_1,
        CRED_DEPLOYER_1,
        block.timestamp + 1,
        CURATOR_1,
        address(bondingCurve),
        "HighFee-uri",
        "BASIC",
        "SIGNATURE",
        hex"",
        500,
        500
    );
    cred._addCredIdPerAddress(credId, USER1); // @audit-high Anyone can call this function and add any cred id for
        // any address (But it does not cause any effect for the contracts in scope)
    buyShareCred_helper(USER1, credId, 1, 1 ether); // @audit-high this function internally also call
        // `_addCredIdPerAddress`, so if we call sellShareCred, `_removeCredIdPerAddress` called by it will have no
        // effect, since data is `_addCredIdPerAddress` is called twice
        // Because `_credIdsPerAddressCredIdIndex` is overriten, there is no way to delete this value, Using this
        // bug, attacker can create infinitly big (as much as he ready to pay for gas) non-deletable array,
        // which will cause every User that call this values via `getPositionsForCurator` for whatever
        // reasons to pay a lot of gas
}
```

## Recommended Mitigation Steps

Make `_addCredIdPerAddress` and `_removeCredIdPerAddress` private, as they are only called within the contract.
If these functions need to be public, add access control modifiers.
