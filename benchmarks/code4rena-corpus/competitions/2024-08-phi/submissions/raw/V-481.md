# Vulnerability details

## Impact
The function `distribute` doesn't implement any access control modifier allowing anyone to be able to call this function. A malicious user can call this function targeting a `credId` with a small `totalBalance` compared to a very large `totalnum` value therefore receiving very large amount as the difference between `distributeAmount` and `actualDistributeAmount`

## Proof of Concept
Lets carefully observe the `distribute()` and see how this vulnerability can play out 
https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/CuratorRewardsDistributor.sol#L77C1-L131
The specified link shows the logic implementation of the `distribute()`, as stated earlier the function doesn't use any access control modifier. However, it made some calls to certain function in the credContract; `getCuratorAddresses()` and `getShareNumber()`. observing below the code snippet for this two functions

```javascript
 /// @param credId_ The ID of the cred.
    /// @param start_ The starting index for pagination.
    /// @param stop_ The stopping index for pagination.
    /// @return The addresses that have the cred.
    function getCuratorAddresses(
        uint256 credId_,
        uint256 start_,
        uint256 stop_
    )
        public
        view
        returns (address[] memory)
    {
        CuratorData[] memory curatorData = _getCuratorData(credId_, start_, stop_);
        address[] memory result = new address[](curatorData.length);

        for (uint256 i = 0; i < curatorData.length; i++) {
            result[i] = curatorData[i].curator;
        }

        return result;
    }


 /// @notice Gets the number of share an address has for a cred.
    /// @param credId_ The ID of the cred.
    /// @param curator_ The address to check.
    /// @return The number of shares the address has for the cred.
    function getShareNumber(uint256 credId_, address curator_) external view returns (uint256) {
        return shareBalance[credId_].get(curator_);
    }

``` 

It can be seen that the `getCuratorsAddresses` also doesn't uses a access control modifier but return curator addresses related to the credId. This return value from the `getCuratorsAddresses()` which in turn is passed into the `getShareNumber()` as a parameter called `distributeAddresses`. 

This logic flow allows anyone one to be able to call this function with a valid credId, the user can further exploit the function to steal funds following the detailed explanation discussed below

Step 1: The malicious user finds an exploitable credId(small `totalBalance` compared to a very large `totalNum`)
Step 2: Calls `distribute()`
Step 3: Function performs calculation that leads to large rounding errors
Step 4: Due to this error the `actualDistributeAmount` is very much smaller than `dustributeAmount`, and the difference which is most likely the `distributeAmount` is sent to the malicious user

The malicious user gain ETH based on the discrepancy created by the rounding error successfully exploiting the contract function.

Example scenario 
Example Parameters:
totalBalance = 150 tokens
totalNum = 10,000 (total number of shares)
withdrawRoyalty = 100 (representing 1% in basis points)
RATIO_BASE = 10,000 (standard base for percentage calculation)
Step-by-Step Calculation:
Calculate the Royalty Fee:

royaltyfee = (totalBalance * withdrawRoyalty) / RATIO_BASE

Substituting the values: We have,

royaltyFee = (150 * 100) / 10_000 = 1.5


Since Solidity uses integer arithmetic, the result is rounded down, so royaltyfee equals 1 token.

Calculate the Distribute Amount:

distributeAmount = totalBalance − royaltyfee
Substituting the values: We have,

distributeAmount = 150 - 1 = 149 
Initialize Variables for Distribution:

Initialize amounts as an array to store the calculated rewards for each address, and reasons to store reasons associated with each distribution.
Initialize actualDistributeAmount to 0 to accumulate the total distributed amount.
Distribute Tokens Among Addresses:

Assume distributeAddresses.length = 3 and the shares (userAmounts) for each address are:
Address 1: 1 share
Address 2: 1 share
Address 3: 1 share
The total number of shares (totalNum) is 10,000.
For each address, the function calculates their reward:

Address 1:

userRewards1 = (distributeAmount * userAmounts1) / totalNum
userRewards1 = (149 * 1) / 10,000 = 0.0149
Since Solidity rounds down, userRewards will be 0 tokens.

This same calculation result is applicable to userRewards2 and userRewars3 since they have the same number of share

Since each reward is 0 due to rounding, the actualDistributeAmount becomes:

actualDistributeAmount=0 + 0 + 0 = 0
Balance Update:

The function updates the balance of the credId:

balanceOf[credId] =− totalBalance
Assuming the initial balance was 150, it now becomes 0.

ETH Transfer:

The ETH transfer statement:

_msgSender().safeTransferETH(royaltyfee + distributeAmount − actualDistributeAmount)
Substituting the values:

_msgSender().safeTransferETH(1 +149 − 0) = 150
Therefore, 150 tokens worth of ETH is transferred back to the sender to compensate for the rounding difference.

And in this case the sender is the malicious actor, therefore stealing the funds

## Recommended Mitigation Steps
Use Access control to allow only curators to be able to call the function and also ensure check to make sure the curator corresponds to the specified credId.
Also you can declared a constant e.g WAD = 10**18 and implement it in the function calculation to handle precision better
