# Vulnerability details

## Impact
Users will suffer a loss of any excess `msg.value` sent when calling the `batchBuyShareCred` function if the transaction fails. The excess funds are not refunded and remain stuck in the contract.

## Proof of Concept
A missing refund logic in the `batchBuyShareCred` function will cause a loss of funds for users as any excess `msg.value` sent will not be refunded if the `_executeBatchBuy` function reverts.

The refund logic is placed after the `_executeBatchBuy` function call. If the `_executeBatchBuy` function reverts due to any reason (e.g., insufficient shares, price exceeds limit, etc.), the refund logic is never reached. https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L191-L211
```solidity
function batchBuyShareCred(
    uint256[] calldata credIds_,
    uint256[] calldata amounts_,
    uint256[] calldata maxPrices_,
    address curator_
)
    public
    payable
{
    (uint256 totalCost, uint256[] memory prices, uint256[] memory protocolFees, uint256[] memory creatorFees) =
        _validateAndCalculateBatch(credIds_, amounts_, maxPrices_, true);

    if (totalCost > msg.value) revert InsufficientBatchPayment();

    _executeBatchBuy(credIds_, amounts_, curator_, prices, protocolFees, creatorFees);

    uint256 refund = msg.value - totalCost;
    if (refund > 0) {
        _msgSender().safeTransferETH(refund);
    }
}
```
When the `_executeBatchBuy` function revert due to any reason (e.g., insufficient shares, price exceeds limit, etc.).

**Attack Scenario**

* User calls `batchBuyShareCred` with `credIds`, `amounts`, `maxPrices`, and curator parameters.
* The `_validateAndCalculateBatch` function is called to calculate the total cost and other necessary values.
* The `_executeBatchBuy` function is called with the calculated values.
* If the `_executeBatchBuy` function reverts due to any reason, the refund logic is never reached.
* Any excess `msg.value` sent by the user is not refunded and remains stuck in the contract.

## Recommended Mitigation Steps
The refund logic should be moved outside the `_executeBatchBuy` function call and executed regardless of whether the batch buy operation succeeds or fails. This ensures that any excess `msg.value` is always refunded to the caller.
```diff
function batchBuyShareCred(
    uint256[] calldata credIds_,
    uint256[] calldata amounts_,
    uint256[] calldata maxPrices_,
    address curator_
)
    public
    payable
{
    (uint256 totalCost, uint256[] memory prices, uint256[] memory protocolFees, uint256[] memory creatorFees) =
        _validateAndCalculateBatch(credIds_, amounts_, maxPrices_, true);

    if (totalCost > msg.value) revert InsufficientBatchPayment();

+   uint256 refund = msg.value - totalCost;

    _executeBatchBuy(credIds_, amounts_, curator_, prices, protocolFees, creatorFees);

-   uint256 refund = msg.value - totalCost;
    if (refund > 0) {
        _msgSender().safeTransferETH(refund);
    }
}
```
By moving the refund logic before the `_executeBatchBuy` function call, any excess `msg.value` will be refunded to the user, even if the batch buy operation fails.
