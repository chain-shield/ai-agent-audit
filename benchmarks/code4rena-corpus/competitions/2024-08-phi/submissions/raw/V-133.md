# Vulnerability details

## Impact
The protocol suffers a loss of funds equal to the sum of the protocol fees and creator fees for each batch buy operation. The attacker gains the excess refund amount, which should have been deducted from the refund.

## Proof of Concept
The incorrect refund calculation in the `batchBuyShareCred` function will cause a loss of funds for the contract as the caller will receive an excess refund amount that does not account for the protocol fees and creator fees.

In Cred.sol:191-210, the refund amount is calculated as `msg.value - totalCost`, which does not consider the protocol fees and creator fees that are transferred during the `_executeBatchBuy` function. [Cred.sol#L205-L210](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L205-L210)
```solidity
uint256 refund = msg.value - totalCost;
if (refund > 0) {
    _msgSender().safeTransferETH(refund);
}
```
The attack happen when:

1. The `totalCost` variable should be less than the `msg.value` sent with the transaction.
2. The sum of the protocol fees and creator fees should be greater than zero.

Attack Scenario

1. The caller invokes the `batchBuyShareCred` function with valid `credIds_`, `amounts_`, `maxPrices_`, and curator_ parameters.
2. The `_validateAndCalculateBatch` function is called to validate the input and calculate the `totalCost`.
3. The `_executeBatchBuy` function is called with the calculated prices, protocol fees, and creator fees.
4. The protocol fees and creator fees are transferred to their respective destinations.
5. The refund amount is calculated as `msg.value - totalCost`, which does not account for the transferred protocol fees and creator fees.
6. The excess refund amount is transferred back to the caller, resulting in a loss of funds for the contract.

## Tools Used
Manual review

## Recommended Mitigation Steps
The refund calculation should take into account the total cost, including the protocol fees and creator fees. The refund amount should be calculated as follows:
```diff
- uint256 refund = msg.value - totalCost;
+ uint256 totalFees = totalProtocolFees + totalCreatorFees;
+ uint256 refund = msg.value - (totalCost + totalFees);
```
`totalProtocolFees` and `totalCreatorFees` represent the sum of all protocol fees and creator fees, respectively, for each batch buy operation. By subtracting the total fees from the `msg.value` along with the `totalCost`, the refund amount will be correctly calculated, ensuring that the contract does not suffer a loss of funds.
