# Vulnerability details

## Impact
The `PhiFactory` contract uses the `cloneDeterministic` function to create new art contracts. This function utilizes the `CREATE2` opcode, which determines the address of the new contract based on a salt argument. The vulnerability arises because the salt used is sequential thus predictable, being derived from `block.chainid`, `newArtId`, and `credId`. since the `newArtId` is squential, this will block all users to create arts on the `CredId`
```javascript
function _createNewNFTContract(
    PhiArt storage art,
    uint256 newArtId,
    ERC1155Data memory createData_,
    uint256 credId,
    uint256 credChainId,
    string memory verificationType
) private returns (address) {
    address payable newArt =
        payable(erc1155ArtAddress.cloneDeterministic(keccak256(abi.encodePacked(block.chainid, newArtId, credId))));

    art.artAddress = newArt;

    // ... rest of the function
}
```
I should note that `createERC1155Internal` doesn't handle the possibility of an existing contract correctly as it checks internal state variables which could be uninitialized but an adress of a contract has already been created by a malicious user externally
```javascript
function createERC1155Internal(uint256 newArtId, ERC1155Data memory createData_) internal returns (address) {
        // Todo check if artid exists, if artid exists, reverts
        _validateArtCreation(createData_);
        PhiArt storage currentArt = arts[newArtId];
        // initialize hte phi art using createData_
        _initializePhiArt(currentArt, createData_);

        (uint256 credId,, string memory verificationType, uint256 credChainId,) =
            abi.decode(createData_.credData, (uint256, address, string, uint256, bytes32));

        address artAddress;
        if (credNFTContracts[credChainId][credId] == address(0)) {
            artAddress = _createNewNFTContract(currentArt, newArtId, createData_, credId, credChainId, verificationType);
        } else {
            artAddress = _useExistingNFTContract(currentArt, newArtId, createData_, credId, credChainId);
        }

        return artAddress;
    }
```

The impact of this vulnerability is severe:

- Denial of Service (DoS): A malicious actor could preemptively deploy contracts to the addresses where art contracts are intended to be created, effectively blocking the creation of new art for competitor credentials.
- Platform Functionality Disruption: This could prevent legitimate users from creating art, significantly hampering the core functionality of the platform.
- Trust and Reputation Damage: Repeated failures in art creation could lead to frustration among users and damage the platform's reputation.
The vulnerability's impact is high and the likelihood is also high as anyone who wants people to use his own Cred to get Creator Rewards would be tempted to do this.

## Tools Used
1- Alice wants to create a new piece of art for credId 100.
2- Bob calculates the exact address where Alice's art contract would be deployed because the contract will be based on  based on the credId, newArtId, and chain ID.
3- He quickly deploys a simple contract to this address with minimal gas costs.
4- Alice initiates the art creation process for credId 100, The PhiFactory attempts to deploy the new art contract using cloneDeterministic.
5- The transaction fails because the calculated address is already occupied by Bob's contract.
## Recommended Mitigation Steps
 Use a Secure and Unpredictable Salt: Replace the current salt calculation with a more secure and unpredictable source. Instead of using predictable values like block.chainid, newArtId, and credId, incorporate more randomness into the salt. For example, you could use a hash of the user's address and a secure random value generated at the time of the transaction:
```javascript
bytes32 salt = keccak256(abi.encodePacked(msg.sender, newArtId, credId, block.timestamp, block.difficulty));```
