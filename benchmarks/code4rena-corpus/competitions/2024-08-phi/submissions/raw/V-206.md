# Vulnerability details

## Impact

The `distribute` function allows anyone to initiate the distribution of rewards among curators who have purchased shares of a particular credential. These rewards accumulate each time an NFT linked to the credential is minted. However, the current implementation can lead to unfair reward distribution:

1. **Reward Dilution for Early Investors**: If new shares are purchased after rewards have accumulated but before distribution occurs, early investors may experience dilution of their rewards. This happens because rewards are distributed equally among all current share holders, regardless of when their shares were acquired.

2. **Loss of Rewards for Sellers**: If a curator sells their shares after rewards have accumulated but before distribution, they forfeit any rewards earned up to that point. The rewards are distributed only to the remaining share holders, meaning the selling curator does not receive their rightful share.

**Example**: Consider a scenario where a curator buys a share and 10 NFTs associated with that share are minted, resulting in rewards of 10x. If another curator then buys a share in the same NFT, the rewards are distributed equally among both curators, despite the fact that no additional NFTs were minted after the second curator acquired their share. This results in an inequitable distribution of rewards and unfairly impacts the initial share holder's rewards.

```solidity
    function distribute(uint256 credId) external {
        if (!credContract.isExist(credId)) revert InvalidCredId();
        uint256 totalBalance = balanceOf[credId];
        if (totalBalance == 0) {
            revert NoBalanceToDistribute();
        }

        address[] memory distributeAddresses = credContract.getCuratorAddresses(credId, 0, 0);
        uint256 totalNum;

        for (uint256 i = 0; i < distributeAddresses.length; i++) {
            totalNum += credContract.getShareNumber(credId, distributeAddresses[i]);
        }

        if (totalNum == 0) {
            revert NoSharesToDistribute();
        }

        uint256[] memory amounts = new uint256[](distributeAddresses.length);
        bytes4[] memory reasons = new bytes4[](distributeAddresses.length);

        uint256 royaltyfee = (totalBalance * withdrawRoyalty) / RATIO_BASE;
        uint256 distributeAmount = totalBalance - royaltyfee;

        // actualDistributeAmount is used to avoid rounding errors
        // amount[0] = 333 333 333 333 333 333
        // amount[1] = 333 333 333 333 333 333
        // amount[2] = 333 333 333 333 333 333
        uint256 actualDistributeAmount = 0;
        for (uint256 i = 0; i < distributeAddresses.length; i++) {
            address user = distributeAddresses[i];

            uint256 userAmounts = credContract.getShareNumber(credId, user);
            uint256 userRewards = (distributeAmount * userAmounts) / totalNum;
// @> the last curator receives the same amount of rewards as the first one

            if (userRewards > 0) {
                amounts[i] = userRewards;
                actualDistributeAmount += userRewards;
            }
        }

        balanceOf[credId] -= totalBalance;

        _msgSender().safeTransferETH(royaltyfee + distributeAmount - actualDistributeAmount);

        //slither-disable-next-line arbitrary-send-eth
        phiRewardsContract.depositBatch{ value: actualDistributeAmount }(
            distributeAddresses, amounts, reasons, "deposit from curator rewards distributor"
        );

        emit RewardsDistributed(
            credId, _msgSender(), royaltyfee + distributeAmount - actualDistributeAmount, distributeAmount, totalBalance
        );
    }
```

## Proof of Concept

Add the following tests to `test/CuratorRewardsDistributor.t.sol`:

1. **Unfair Distribution When Buying**: Simulate a scenario where `user1` buys a share for `credId = 1`. Accumulate rewards by depositing ETH into the contract for this `credId`, which should result in rewards being split equally between the share creator and `user1`. Then, a new user, `user2`, buys another share for the same `credId`, but no additional rewards are deposited after `user2` acquires their share. When the `distribute` function is called, both `user1` and `user2` receive the same rewards, despite `user2` not contributing to the reward accumulation. This demonstrates an unfair distribution, as `user2` should not receive rewards when no new rewards have been collected since their purchase.

2. **Unfair Distribution When Selling**: Reproduce the scenario from the first test, but include the case where `user1` sells their share after `user2` has purchased theirs. When the `distribute` function is called, `user2` receives half of the rewards (with the other half going to the share creator), while `user1` receives no rewards. This is unfair because `user1` was entitled to rewards accrued while holding the share, and their contribution to the rewards should be recognized.

```solidity
function testUnfairDistributionBuy() public {
    uint256 credId = 1;
    uint256 depositAmount = 10 ether;

    // User1 buys 1 share
    vm.startPrank(user1);
    vm.deal(user1, bondingCurve.getBuyPriceAfterFee(credId, 1, 1));
    cred.buyShareCred{ value: bondingCurve.getBuyPriceAfterFee(credId, 1, 1) }(credId, 1, 0);
    vm.stopPrank();

    // Deposit ETH into the CuratorRewardsDistributor to simulate NFT minting
    // associated with the credential, which accumulates rewards for all curators
    // holding shares in that credential.
    curatorRewardsDistributor.deposit{ value: depositAmount }(credId, depositAmount);

    // User2 buys 1 share
    vm.startPrank(user2);
    vm.deal(user2, bondingCurve.getBuyPriceAfterFee(credId, 2, 1));
    cred.buyShareCred{ value: bondingCurve.getBuyPriceAfterFee(credId, 2, 1) }(credId, 1, 0);
    vm.stopPrank();

    assertEq(cred.getShareNumber(credId, user1), 1, "Signal count should be 1");
    assertEq(cred.getShareNumber(credId, user2), 1, "Signal count should be 1");
    assertEq(cred.getCurrentSupply(credId), 3, "Signal count should be 3");
    assertEq(cred.getCuratorAddressLength(credId), 3, "Signal count should be 3");

    // Record initial balances
    uint256 initialUser1Balance = phiRewards.balanceOf(user1);
    uint256 initialUser2Balance = phiRewards.balanceOf(user2);
    uint256 ownerBalance = owner.balance;

    // Distribute rewards
    vm.prank(owner);
    curatorRewardsDistributor.distribute(credId);

    // Check final balances
    uint256 finalUser1Balance = phiRewards.balanceOf(user1);
    uint256 finalUser2Balance = phiRewards.balanceOf(user2);
    uint256 finalOwnerBalance = owner.balance;

    // Assert the distribution of rewards. Both users receive the same amount,
    // despite no additional mints occurring after user2 purchased their shares.
    assertEq(
        finalUser1Balance - initialUser1Balance,
        (depositAmount - depositAmount / 100) / 3,
        "User1 should receive 1/3 of the rewards"
    );
    assertEq(
        finalUser2Balance - initialUser2Balance,
        (depositAmount - depositAmount / 100) / 3,
        "User2 should receive 1/3 of the rewards"
    );
    assertEq(
        finalOwnerBalance - ownerBalance, (depositAmount / 100), "Distributer should receive 1/100 of the rewards"
    );

    // Check that the balance in curatorRewardsDistributor is now 0
    assertEq(
        curatorRewardsDistributor.balanceOf(credId),
        0,
        "CuratorRewardsDistributor balance should be 0 after distribution"
    );
}
```

## Tools Used

Manual review.

## Recommended Mitigation Steps

Implement a MasterChef-style mechanism to track shares and trigger reward distribution each time a share is bought or sold, as well as before any rewards are withdrawn. For more information refer to [https://www.rareskills.io/post/staking-algorithm](https://www.rareskills.io/post/staking-algorithm)
