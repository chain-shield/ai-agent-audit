# Vulnerability details

## Impact
The `distribute` function in `CuratorRewardsDistributor.sol` can be called by anyone. It loops through all the "**Share Holders**" to perform its functionality. 

However, it is likely that the array being looped through could grow in size, which will result in `OOG/Out of gas` errors and possibly **permanent DoS** due to **reaching the gas limit per block**. 

Or otherwise the operation will cost an excessively high gas amount, making it so that **nobody will have an incentive** to call `distribute()` to receive the **tiny rewards**, as the gas cost will be **much higher.**

## Proof of Concept

In the `distribute()` function, we have two loops, so even though from an algorithmic standpoint the execution complexity will remain the same, in the EVM context the gas cost will grow more.

The protocol will be deploying on `L2s`, but gas costs will still be very high, as we are talking over **8 figures of gas cost**, and since the reward for the distributor itself is not much, the gas cost will easily overcome it on pretty much every `L2`. 

**The bigger problem** could arise when we reach the limit per block on the specific blockchain, this could happen with about  `700-800` shareholders. Since anyone can purchase shares and they get progressively more expensive, this isn't impossible. 
This will cost enough gas to not be able to include the transaction in a block on most chains, as their max is about `25-30 million` effective gas. Then **even the developer cannot rescue the funds**.

In the best case, where second scenario with `700-800` shareholders does not happen and block gas limit is not reached, still no one will have an incentive to distribute the rewards, so the developer will be forced to pay for that indefinitely as the `CuratorRewardsDistributor` is not upgradeable.

### Coded POC

Add this to `CuratorRewardsDistributorTest.t.sol` and use `forge test --match-test testDistributeCode4renaProof -vv`

```solidity
    function testDistributeCode4renaProof() public {
        uint256 credId = 1;
        uint256 depositAmount = 1 ether;

        // Deposit some ETH to the curatorRewardsDistributor
        curatorRewardsDistributor.deposit{ value: depositAmount }(credId, depositAmount);

        // Create 25 different Curators/Cred buyers
        for (uint160 i = 1; i < 25; i++) {
            vm.startPrank(address(i));
            vm.deal(address(i), bondingCurve.getBuyPriceAfterFee(credId, i, 1));
            cred.buyShareCred{ value: bondingCurve.getBuyPriceAfterFee(credId, i, 1) }(credId, 1, 10_000 ether);
            vm.stopPrank();
        }

        // Distribute rewards works fine, tho still costs over 800k gas
        vm.prank(owner);
        curatorRewardsDistributor.distribute(credId);

        // Now lets try a scenario where we have around 345 Curators/Share holders buyers
        for (uint160 i = 25; i < 345; i++) {
            vm.startPrank(address(i));
            vm.deal(address(i), bondingCurve.getBuyPriceAfterFee(credId, i, 1));
            cred.buyShareCred{ value: bondingCurve.getBuyPriceAfterFee(credId, i, 1) }(credId, 1, 10_000 ether);
            vm.stopPrank();
        }

        // Deposit some ETH to the curatorRewardsDistributor
        curatorRewardsDistributor.deposit{ value: depositAmount }(credId, depositAmount);

        // Track stats
        uint256 gasBefore = gasleft();

        // Distribute rewards
        vm.prank(owner);
        curatorRewardsDistributor.distribute(credId);

        uint256 gasAfter = gasleft();
        uint256 gasUsed = gasBefore - gasAfter;

        // Gas is over 10_500_000
        // If we increase the number of Curators/Share holders buyers, we would hit a point where we
        // cannot fit this transaction in a single block due to block gas limit, which would result in
        // permanently locking the funds in the contract
        assertTrue(gasUsed > 10_500_000);

        //==> Conclusions:
        // - Gas cost is incredibly high, no one will have incentive to call distribute() as the rewards are not worth
        // it.
        // - given enough Curators/Share holders buyers, the funds will be permanently locked in the contract, as the
        // gas limit per block will be reached, and the transaction will not be able to be included in any block.
    }
```

## Recommended Mitigation Steps
This currently gets all of the Curators, eligible for rewards:
```solidity
   address[] memory distributeAddresses = credContract.getCuratorAddresses(credId, 0, 0);
 ```  
Consider adding logic for calling distribute in batches and probably increase incentive rewards for the distributor, as they are close to 0.
