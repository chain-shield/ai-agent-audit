# Vulnerability details

The issue start with the following lines of code:
```solidity
if ((currentNum - amount_) == 0) {
    _removeCredIdPerAddress(credId_, sender_);
    _credIdExistsPerAddress[sender_][credId_] = false;
}
shareBalance[credId_].set(sender_, currentNum - amount_);
```
The problem is that the `_removeCredIdPerAddress` function is called before updating the `shareBalance` mapping. If the sell operation reduces the curator's balance to zero, the `_removeCredIdPerAddress` function removes the curator's entry from the `_credIdsPerAddress` mapping. However, the `shareBalance` mapping is updated afterwards, which means that the curator's balance is not actually zero at the time of removal.

This allows a curator to sell shares even when their balance becomes zero, violating the expected behavior. The `_removeCredIdPerAddress` function should be called after updating the `shareBalance` mapping to ensure that the curator's entry is removed only when their balance is truly zero.

## Impact
The curators of the Cred contract may experience loss of funds due to an inconsistency in the share balance updates during the sell operation. This issue allows curators to sell more shares than they possess, leading to discrepancies in the share balances.

## Proof of Concept
The function incorrectly removes the curator's entry from the `_credIdsPerAddress` mapping before updating the `shareBalance` mapping, allowing curators to sell shares even when their balance becomes zero.

1. The curator calls the `sellShareCred` function with a `credId`, `amount`, and `minPrice`.
2. The `_handleTrade` function is called internally to perform the sell operation.
3. Inside `_handleTrade`, the `_removeCredIdPerAddress` function is called before updating the `shareBalance` mapping.
4. If the sell operation reduces the curator's balance to zero, the curator's entry is removed from _`credIdsPerAddress`.
5. However, the `shareBalance` mapping is updated afterwards, which means that the curator's balance is not actually zero at the time of removal.
6. As a result, the curator can sell more shares than they possess, leading to inconsistencies in the share balances.

The `sellShareCred` function is called with `credId_ = 1`, `amount_ = 1`, and`minPrice_ = 0`. This function internally calls the `_handleTrade` function to perform the sell operation.

## Recommended Mitigation Steps
The order of operations in the should be adjusted. The `shareBalance` mapping should be updated before calling the _removeCredIdPerAddress.
```diff
- if ((currentNum - amount_) == 0) {
-     _removeCredIdPerAddress(credId_, sender_);
-     _credIdExistsPerAddress[sender_][credId_] = false;
- }
shareBalance[credId_].set(sender_, currentNum - amount_);
+ if ((currentNum - amount_) == 0) {
+     _removeCredIdPerAddress(credId_, sender_);
+     _credIdExistsPerAddress[sender_][credId_] = false;
+ }
```
By updating the `shareBalance` mapping before calling `_removeCredIdPerAddress`, the issue can be resolved.
