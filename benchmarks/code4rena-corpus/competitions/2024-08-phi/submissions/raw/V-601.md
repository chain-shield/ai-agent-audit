# Vulnerability details


## Description
The `createArtFromFactory` function in the `PhiNFT1155` contract is susceptible to a potential race condition, especially on high-throughput and parallel-processing blockchains like Base, Optimism, BeraChain, and other EVM-compatible chains. This vulnerability arises due to the way the `tokenIdCounter` is incremented after it has been used in critical operations. If exploited, this issue could lead to the assignment of the same `tokenId` to multiple art pieces, resulting in data corruption, loss of uniqueness, and potential disruption of the system's integrity.

The createArtFromFactory function is responsible for creating a new art token based on a given artId_. It maps this artId_ to a tokenId and manages these relationships using the _artIdToTokenId and _tokenIdToArtId mappings. The process involves the following key steps:

Mapping of `artId_` to `tokenIdCounter`:

```
_artIdToTokenId[artId_] = tokenIdCounter;
_tokenIdToArtId[tokenIdCounter] = artId_;

```
At this stage, the `artId_` is mapped to the current value of `tokenIdCounter`, and this tokenId is also mapped back to the artId_. This step is critical as it establishes the relationship between the art piece and its unique token identifier.

Incrementing tokenIdCounter:

```
unchecked {
    tokenIdCounter += 1;
}
```
After mapping the artId_ to tokenIdCounter, the tokenIdCounter is incremented to ensure that the next art piece created will receive a unique tokenId. However, this increment operation occurs after the critical mapping step.

The race condition arises from the possibility of concurrent transactions attempting to execute the createArtFromFactory function simultaneously. On high-throughput chains like Base, Optimism, and others, multiple transactions can be processed in parallel, especially during periods of high network activity. If two or more transactions call createArtFromFactory at the same time, they may both read the same initial value of tokenIdCounter. Without any locks or atomic operations, these transactions might map different artId_ values to the same tokenIdCounter before the counter is incremented. This would result in multiple artId_ values being associated with the same tokenId, leading to inconsistent data. 

The mappings `_artIdToTokenId` and `_tokenIdToArtId` would become unreliable, as multiple artId_ values could be erroneously linked to the same tokenId. This could cause issues such as:

- Incorrect art pieces being referenced or transferred.
- Difficulty in tracking ownership and provenance.
- Potential loss of funds if transactions are mistakenly routed based on incorrect mappings.
## Impact
The uniqueness of each art piece token is compromised, which is crucial for an NFT platform. Attackers could exploit this vulnerability to disrupt the system, potentially leading to financial loss for users and a loss of trust in the platform. The platform might face operational challenges, including resolving disputes arising from incorrect token mappings and ownership issues.
## Tools Used
Manual Review

## Recommendation
Use atomic operations to ensure that the entire process of mapping the artId_ to tokenIdCounter and incrementing the counter is done in a single, indivisible step. Implement reentrancy guards or mutex locks to prevent multiple instances of createArtFromFactory from executing simultaneously.
