# Vulnerability details

## Impact
Upgradeable contracts **require storage gap**, to maintain **storage compatibility** when adding new state variables. 

Without it, adding variables in an upgraded base contract it is very likely that some variables could get overridden in child contracts, leading to potential **loss of funds** or **serious malfunctions**. 
This makes it challenging to implement new upgrades safely.

Check this reference: [OpenZeppelin Upgradeable Contracts Guide](https://docs.openzeppelin.com/upgrades-plugins/1.x/writing-upgradeable).

> **Storage Gaps**
> Storage gaps are a convention for reserving storage slots in a base contract, allowing future versions of that contract > to use up those slots without affecting the storage layout of child contracts.


## Proof of Concept
And as mentioned in the docs [docs.philand.xyz/architecture](https://docs.philand.xyz/explore-phi/developers/architecture)

> The Cred, PhiFactory, and PhiNFT1155 contracts use the UUPS upgradeability pattern and can be upgraded by the owner.

And as shown down bellow Cred.sol, PhiFactory.sol, and PhiNFT1155.sol all implement the UUPSUpgradeable contract from OpenZeppelin:

```solidity
contract PhiNFT1155 is
    Initializable,
@>> UUPSUpgradeable,
    ERC1155SupplyUpgradeable,
    ReentrancyGuardUpgradeable,
    PausableUpgradeable,
    Ownable2StepUpgradeable,
    IPhiNFT1155,
    Claimable,
    CreatorRoyaltiesControl
{
```

```solidity
contract PhiFactory is Initializable, 
@>>UUPSUpgradeable, 
Ownable2StepUpgradeable, PausableUpgradeable, IPhiFactory {
```

```solidity
contract Cred is Initializable,
@>> UUPSUpgradeable, 
Ownable2StepUpgradeable, 
PausableUpgradeable, ICred {
```

However, all of those solidity contracts  **lack storage gaps** in their implementation, which are essential for safe upgrades. 
This **greatly limits the ability to upgrade** the contracts and poses a risk of possible malfunctions, that could lead to loss of funds. This is particularly dangerous when adding new variables or **changing the storage layout in any way**.

Additionally, there are some abstract classes that **also lack storage gaps**, when we have an upgradeable contract, it's common practice to also include gaps in the abstract classes from which it inherits.

## Tools Used
Manual review

## Recommended Mitigation Steps

Add the appropriate storage gaps at the end of upgradeable contracts like that:

```solidity
uint256[49] private __gap;
```

Please refer to OpenZeppelin's upgradeable contract documentation, as the source of truth.
