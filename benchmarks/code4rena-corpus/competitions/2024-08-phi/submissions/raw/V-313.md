# Vulnerability details

## Impact
If a user sends a value that is greater than the price but less than the sum of the protocol fee and creator fee, the transaction will still proceed. This results in the protocol and creator receiving less than their intended fees, while the user effectively pays less than the expected total cost.

## Proof of Concept
The current check only verifies that the sent value covers the sum of the price and fees. However, it does not account for the case where the sent value is less than the total fees alone. [Cred.sol#L620-L622](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L620-L622)
```solidity
if (msg.value < price + protocolFee + creatorFee) {
    revert InsufficientPayment();
}
```
Attacker can perform the following steps:

1. Call the `buyShareCred` function with a carefully crafted `msg.value` that is greater than the `price` but less than the sum of `protocolFee` and `creatorFee`.
2. The `_handleTrade` function will calculate the `price`, `protocolFee`, and `creatorFee` based on the provided parameters.
3. The `if` statement will pass since `msg.value` is greater than `price`, even though it is less than `protocolFee + creatorFee`.
4. The buy operation will proceed, with the protocol and creator receiving less than their expected fees.

As a result, the protocol and creator suffer a loss of expected revenue, while the attacker effectively pays less than the intended total cost.

## Tools Used
Manual review of the Cred contract's source code, focusing on the logic related to token transfers and payments.

## Recommended Mitigation Steps
The payment check in the `_handleTrade` function should be updated to ensure that the sent value covers both the total fees and the total cost.
```diff
- if (msg.value < price + protocolFee + creatorFee) {
+ if (msg.value < protocolFee + creatorFee || msg.value < price + protocolFee + creatorFee) {
      revert InsufficientPayment();
  }
```
