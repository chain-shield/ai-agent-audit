# Vulnerability details

## Impact
In the current implementation of `PhiFactory.sol` the `claim` function does not check whether a user actually sent `msg.value` to cover the mint fee and simply executes `merkleClaim/signatureClaim` with {value: mintFee}
```solidity
    function claim(bytes calldata encodeData_) external payable {     // @audit no checks that any msg.value had been sent
        bytes memory encodedata_ = LibZip.cdDecompress(encodeData_);
        (uint256 artId) = abi.decode(encodedata_, (uint256));
        PhiArt storage art = arts[artId];
        uint256 tokenId = IPhiNFT1155Ownable(art.artAddress).getTokenIdFromFactoryArtId(artId);
        if (art.verificationType.eq("MERKLE")) {
            (
                ,
                address minter_,
                bytes32[] memory proof,
                address ref_,
                uint256 quantity_,
                bytes32 leafPart_,
                string memory imageURI_
            ) = abi.decode(encodedata_, (uint256, address, bytes32[], address, uint256, bytes32, string));


            bytes memory claimData = abi.encode(minter_, ref_, artId);
            MintArgs memory mintArgs = MintArgs({ tokenId: tokenId, quantity: quantity_, imageURI: imageURI_ });
            uint256 mintFee = getArtMintFee(artId, quantity_);
            this.merkleClaim{ value: mintFee }(proof, claimData, mintArgs, leafPart_); // @audit mintFee sent here without checking msg.value 
        }
    }
```
Under normal circumstances this would not be an issue since factories usually do not hold any ETH and this attack would not be possible. However `PhiFactory.sol` will have ETH in it because of the following function during art creation.  

```solidity
    function createArtFromFactory(uint256 artId_) external payable onlyPhiFactory whenNotPaused returns (uint256) { // @audit msg.sender can be only phiFactory
        _artIdToTokenId[artId_] = tokenIdCounter;
        _tokenIdToArtId[tokenIdCounter] = artId_;


        uint256 artFee = phiFactoryContract.artCreateFee();


        protocolFeeDestination.safeTransferETH(artFee);
        emit ArtCreated(artId_, tokenIdCounter);
        uint256 createdTokenId = tokenIdCounter;


        unchecked {
            tokenIdCounter += 1;
        }
        if ((msg.value - artFee) > 0) {
            _msgSender().safeTransferETH(msg.value - artFee);   // @audit excess eth during art creation is sent back to factory
        }


        return createdTokenId;
    }
```

As we can observe, excess ETH sent in the flow of `createArt` is routed back to `msg.sender` which is always the factory address due to `onlyPhiFactory` modifier. Users can take advantage of this and claim art for free at the expense of the Phi team. Additionally, at the bottom of the factory contract we can see a sweeper `withdraw` function which sends all excess balance to the protocolFeeDestination, pointing that the team accounted for a scenario where the factory holds ETH.  

```solidity
    function withdraw() external onlyOwner {    // @audit sweeper function 
        protocolFeeDestination.safeTransferETH(address(this).balance);
    }
``` 
Loss of funds for the protocol
