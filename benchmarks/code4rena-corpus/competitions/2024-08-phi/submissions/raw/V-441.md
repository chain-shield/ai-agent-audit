# Vulnerability details

## Impact
The PhiNFT1155 contract lacks a mechanism to update its protocolFeeDestination after initialization. While it correctly initializes this value from the PhiFactory contract, there's no way to change it if the protocol fee destination in the factory is updated. This leads to a critical issue where all fees sent to this address (including art creation fees) may be directed to an outdated address.
The potential impact of this vulnerability is severe:

If the protocolFeeDestination in the PhiFactory contract is updated, let's say due to a compromise, the existing PhiNFT1155 contracts will continue to use the old address.
All art creation fees sent to protocolFeeDestination in existing NFT contracts will be misdirected to the old address.

```solidity 
function createArtFromFactory(uint256 artId_) external payable onlyPhiFactory whenNotPaused returns (uint256) {
    // ... other code ...
    protocolFeeDestination.safeTransferETH(artFee);
    // ... more code ...
}
```
The protocol loses control over updating these fee destinations for existing NFT contracts, potentially resulting in significant financial losses.
The loss would also include the royalties from NFT sales when default values are being used by art creators.

## Proof of Concept
1. Deploy PhiFactory with initial protocolFeeDestination as Address A.
2. Create multiple PhiNFT1155 contracts through PhiFactory.
3. Update protocolFeeDestination in PhiFactory to Address B.
4. Existing PhiNFT1155 contracts still use Address A for fee transfers.
5. Art creation fees and NFT royalties from these contracts continue to go to Address A, which may no longer be controlled by the protocol.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Instead of storing protocolFeeDestination as a state variable in PhiNFT1155, implement a function to dynamically fetch it from PhiFactory.
