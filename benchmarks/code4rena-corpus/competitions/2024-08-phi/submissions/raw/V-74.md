# Vulnerability details

The calculation of the `actualDistributeAmount` in the `distribute` function of the `CuratorRewardsDistributor` contract may lead to rounding errors or precision loss, causing a small remaining balance to stay in the contract instead of being fully distributed to the curators. This will cause an incomplete distribution of rewards for the curators as the `CuratorRewardsDistributor` contract will retain a non-zero balance after the distribute function is called.

```solidity
function distribute(uint256 credId) external {
    // ...

    uint256 actualDistributeAmount = 0;
    for (uint256 i = 0; i < distributeAddresses.length; i++) {
        // ...

        if (userRewards > 0) {
            amounts[i] = userRewards;
            actualDistributeAmount += userRewards;
        }
    }

    balanceOf[credId] -= totalBalance;

    _msgSender().safeTransferETH(royaltyfee + distributeAmount - actualDistributeAmount);

    // ...
}
```
In the calculation of the `actualDistributeAmount`. The code subtracts the `actualDistributeAmount` from the `distributeAmount` and transfers the remaining balance back to the caller (`_msgSender()`). However, if there are rounding errors or precision loss during the calculation of `userRewards`, the `actualDistributeAmount` may not match the `distributeAmount` exactly.

As a result, there could be a small remaining balance that is not distributed and stays in the contract. This violates the invariant that the balance should become zero after a successful distribution.

**Root Cause**
In `CuratorRewardsDistributor.sol`, the distribute function calculates the `actualDistributeAmount` by summing up the `userRewards` for each curator. However, due to potential rounding errors or precision loss during the calculation of `userRewards`, the `actualDistributeAmount` may not match the `distributeAmount` exactly. ## Impact
The curators suffer an approximate loss of the remaining balance that is not distributed. This remaining balance stays in the `CuratorRewardsDistributor` contract, leading to an incomplete distribution of rewards.

## Proof of Concept
Internal pre-conditions:

a. The `CuratorRewardsDistributor` contract needs to have a non-zero balance for a specific `credId`.
b. The `distribute` function needs to be called for the same `credId`.

**Attack Path:**

* The `distribute` function is called for a `credId` with a non-zero balance.
* The function calculates the `actualDistributeAmount` by summing up the `userRewards` for each curator.
* Due to rounding errors or precision loss, the `actualDistributeAmount` is slightly less than the `distributeAmount`.
* The function transfers the remaining balance (`royaltyfee + distributeAmount - actualDistributeAmount`) back to the caller.
* The `CuratorRewardsDistributor` contract retains a small non-zero balance for the `credId`, resulting in an incomplete distribution of rewards.

## Recommended Mitigation Steps
* Instead of calculating the `actualDistributeAmount`, directly use the `distributeAmount for the batch deposit to the PhiRewards contract.
* If there is any remaining balance after the batch deposit, transfer it to a designated address (e.g., the contract owner or the last curator in the loop) to ensure the contract balance becomes zero.
