# Vulnerability details

### Summary
The `PhiFactory` contract implements a signature-based claim mechanism for NFT art pieces. This mechanism is intended to allow authorized users to claim art pieces by providing a valid signature.

The current implementation of the signature claim mechanism is vulnerable to signature replay attacks. An attacker can reuse a valid signature to claim an art piece multiple times, potentially exceeding intended limits or draining resources.

## Details
The `signatureClaim` function in the `PhiFactory` contract verifies the signature but does not implement any mechanism to prevent the reuse of that signature. Once a valid signature is used, it remains valid for future transactions as long as the encoded data remains valid.

## Code Snippet
```solidity
function signatureClaim(
    bytes calldata signature_,
    bytes calldata encodeData_,
    MintArgs calldata mintArgs_
)
    external
    payable
    whenNotPaused
{
    (uint256 expiresIn_, address minter_, address ref_, address verifier_, uint256 artId_,, bytes32 data_) =
        abi.decode(encodeData_, (uint256, address, address, address, uint256, uint256, bytes32));

    if (expiresIn_ <= block.timestamp) revert SignatureExpired();
    if (_recoverSigner(keccak256(encodeData_), signature_) != phiSignerAddress) revert AddressNotSigned();

    _validateAndUpdateClaimState(artId_, minter_, mintArgs_.quantity);
    _processClaim(artId_, minter_, ref_, verifier_, mintArgs_.quantity, data_, mintArgs_.imageURI, msg.value);

    emit ArtClaimedData(artId_, "SIGNATURE", minter_, ref_, verifier_, arts[artId_].artAddress, mintArgs_.quantity);
}
```

## Impact
An attacker who obtains a valid signature can:
1. Claim the same art piece multiple times, potentially exceeding the intended supply.
2. Drain the contract's resources by repeatedly processing the same claim.
3. Manipulate the market by obtaining more NFTs than intended.

## Scenario
1. Alice is authorized to claim Art Piece #1 and receives a valid signature.
2. Alice claims Art Piece #1 using the signature.
3. Bob (an attacker) observes Alice's transaction and extracts the signature and encoded data.
4. Bob repeatedly calls `signatureClaim` with the same signature and data, successfully claiming multiple copies of Art Piece #1.

## Fix
Implement a nonce-based system to prevent signature reuse:

1. Add a nonce field to the encoded data and signature.
2. Track used nonces for each minter in the contract.
3. Verify and increment the nonce during each claim.

Example implementation:

```solidity
mapping(address => uint256) public nonces;

function signatureClaim(
    bytes calldata signature_,
    bytes calldata encodeData_,
    MintArgs calldata mintArgs_
)
    external
    payable
    whenNotPaused
{
    (uint256 expiresIn_, address minter_, address ref_, address verifier_, uint256 artId_, uint256 nonce_, bytes32 data_) =
        abi.decode(encodeData_, (uint256, address, address, address, uint256, uint256, bytes32));

    if (expiresIn_ <= block.timestamp) revert SignatureExpired();
    if (_recoverSigner(keccak256(encodeData_), signature_) != phiSignerAddress) revert AddressNotSigned();
    if (nonce_ != nonces[minter_]) revert InvalidNonce();

    nonces[minter_]++;
    _validateAndUpdateClaimState(artId_, minter_, mintArgs_.quantity);
    _processClaim(artId_, minter_, ref_, verifier_, mintArgs_.quantity, data_, mintArgs_.imageURI, msg.value);

    emit ArtClaimedData(artId_, "SIGNATURE", minter_, ref_, verifier_, arts[artId_].artAddress, mintArgs_.quantity);
}
```

This fix ensures that each signature can only be used once, preventing replay attacks and maintaining the integrity of the claiming process.
