# Vulnerability details

## Summary

The `_validateAndUpdateClaimState` function in the `PhiFactory` contract contains a compound condition that is intended to prevent unauthorized access to the function. However, due to the way the condition is structured, it can be easily bypassed, allowing unauthorized callers to execute the function. This could lead to unauthorized claims, manipulation of the contract state, and potential exploitation of the contract.

## Impact

The impact of this vulnerability is significant, as it allows unauthorized callers to bypass the access control check and execute the `_validateAndUpdateClaimState` function. This could lead to:

- **Unauthorized Claims**: Attackers could claim art rewards without proper authorization.
- **State Manipulation**: Attackers could manipulate the contract state, leading to incorrect or unintended behavior.
- **Potential Exploitation**: The vulnerability could be exploited in combination with other vulnerabilities to cause further damage.

## Vulnerable Code

The vulnerability is located in the `_validateAndUpdateClaimState` function, specifically on line 706:

https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L702-L708

```solidity
if (tx.origin != _msgSender() && msg.sender != art.artAddress && msg.sender != address(this)) {
    revert TxOriginMismatch();
}
```

## Proof of concept

The condition on line 706 is a compound condition using the logical AND (`&&`) operator. This means that **all** parts of the condition must be true for the `revert` statement to execute. If **any** part of the condition is false, the check will be bypassed, and the function will continue executing.

The condition is intended to ensure that the transaction's origin (`tx.origin`) matches the `_msgSender()` or that the `msg.sender` is either the art contract (`art.artAddress`) or the contract itself (`address(this)`). However, this logic is flawed for the following reasons:

1. **Bypassable Condition**:
   - If any one of the conditions is false, the entire compound condition will be false, and the function will bypass the `revert` statement. This means that an attacker can bypass the check by ensuring that one of the conditions is false.

2. **`tx.origin` Usage**:
   - The use of `tx.origin` is generally discouraged in Solidity because it can be manipulated in certain scenarios, such as when a contract calls another contract. An attacker could potentially exploit this by creating a contract that calls the `claim` function, bypassing the intended checks.


## Example Scenario

**Scenario: `tx.origin == _msgSender()`**
   - If `tx.origin` is equal to `_msgSender()`, the first condition (`tx.origin != _msgSender()`) will be false.
   - Since the first condition is false, the entire compound condition will be false, and the function will bypass the `revert` statement even if the other two conditions are true.

To address this vulnerability, the condition should be simplified and the use of `tx.origin` should be avoided. A more secure check would be:

```solidity
if (_msgSender() != art.artAddress && _msgSender() != address(this)) {
    revert UnauthorizedCaller();
```
