# Vulnerability details

## Vulnerability Details

In `Cred.sol`'s `createCred` function:
```solidity
  function createCred(
      address creator_,
      bytes calldata signedData_,
      bytes calldata signature_,
      uint16 buyShareRoyalty_,
      uint16 sellShareRoyalty_
  )
      public
      payable
      whenNotPaused
  {
      if (_recoverSigner(keccak256(signedData_), signature_) != phiSignerAddress) revert AddressNotSigned();
      (
          uint256 expiresIn,
          address sender,
@>        ,
          address bondingCurve,
          string memory credURL,
          string memory credType,
          string memory verificationType,
          bytes32 merkleRoot_
      ) = abi.decode(signedData_, (uint256, address, uint256, address, string, string, string, bytes32));
      ....
      ....
  }
```

In the function `createCred`, the `credChainId` (which is the argument denoted by the line "`@>`") is ignored and not checked whether this current chain(`block.chainid`) is the same chain as the chain which was given approval by `phiSignerAddress`.

Hence, this gives malicious users the opportunity to just re-use signatures that they managed to get approval for on a different chain and use it on this current chain without permission instead.

## Proof Of Concept

**Possible sequence of exploit:**

1. `Alice` gets approval through a signed signature to deploy a cred on `Chain X`.
2. She goes to `Chain Y` where this protocol is also deployed to call `createCred` with the same signature.
3. Since, as shown above `createCred` does not check whether this current chain is the same chain as which the signature is valid for, `Alice` ends up having permission to deploy this cred on `Chain Y` even though `phiSignerAddress` only wants `Alice` to deploy it on `Chain X`.
