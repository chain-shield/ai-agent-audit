# Vulnerability details

## Impact
The `withdrawFor` function in the `RewardControl.sol` file is designed to allow an authorized user to withdraw funds on behalf of another user. However, the function passes the same address for both the `from` and `to` parameters to the `_withdraw` function. This results in the funds being withdrawn from the `balanceOf[from]` amount and sent to the same `from` address, making it difficult to determine if the function had fulfilled its intended purpose. This could lead to confusion and potential misuse of the function because it doesn't allow the other user to specify the intended address to which they want funds withdrawn.

## Proof of Concept
The vulnerability arises from the redundant parameter usage in the `withdrawFor` function, which passes the same address for both the `from` and `to` parameters.

### Code Reference
Here is the relevant code from the `RewardControl.sol` file:

https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/abstract/RewardControl.sol#L97-L98

```solidity
function withdrawFor(address from, uint256 amount) external {
    _withdraw(from, from, amount);
}
```

### Proof of Concept Scenario

A user calls the `withdrawFor` function with the `from` address and an `amount`. The function calls the `_withdraw` function, passing the same `from` address for both the `from` and `to` parameters. The `_withdraw` function withdraws the funds from the `from` address and sends them back to the same `from` address, making the function redundant.

## Tools Used
Manual code review

## Recommended Mitigation Steps
To correct this issue, modify the `withdrawFor` function to allow specifying a `to` address. This ensures that the function fulfills its intended purpose of transferring funds on behalf of another user. Here is the corrected code:

```solidity
function withdrawFor(address from, address to, uint256 amount) external {
    _withdraw(from, to, amount);
}
```
