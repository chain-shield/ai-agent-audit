# Vulnerability details

## Impact

This issue might seem minor at first, but it results from two separate bugs in different parts of the code. Interestingly, these two issues interact in a way that diminishes the impact of each individual problem.

**First Issue:**
The `PhiFactory::createArt` function enables users to create an NFT by sending an amount equal to `NFT_ART_CREATE_FEE` as `msg.value`. However, neither `createArt` nor its internal functions (`PhiFactory::createERC1155Internal`, `PhiFactory::_createNewNFTContract`, and `PhiFactory::_useExistingNFTContract`) are designed to handle refunds for excess ETH sent by the user. Instead, all received ETH is forwarded to `PhiNFT1155::createArtFromFactory`. Because `PhiNFT1155::createArtFromFactory` is called by the `PhiFactory` contract, it cannot identify the original sender and thus cannot return any excess ETH. This flaw may cause excess ETH to be locked in the contract, rendering it inaccessible to the original sender.

**Second Issue:**
The `PhiNFT1155::createArtFromFactory` function, intended to create a new ERC1155 token instance, is designed to be called only by the `PhiFactory` contract, enforced by the `onlyPhiFactory` modifier. This function calculates the mint fee and includes logic to refund any excess ETH to the `PhiFactory` contract. However, the `PhiFactory` contract cannot receive ETH transfers because it lacks `receive` or `fallback` functions. As a result, any attempt by `PhiNFT1155::createArtFromFactory` to return excess ETH to `PhiFactory` will cause the transaction to revert.

```
    function createArtFromFactory(uint256 artId_) external payable onlyPhiFactory whenNotPaused returns (uint256) {
        _artIdToTokenId[artId_] = tokenIdCounter;
        _tokenIdToArtId[tokenIdCounter] = artId_;

        uint256 artFee = phiFactoryContract.artCreateFee();

        protocolFeeDestination.safeTransferETH(artFee);
        emit ArtCreated(artId_, tokenIdCounter);
        uint256 createdTokenId = tokenIdCounter;

        unchecked {
            tokenIdCounter += 1;
        }
        if ((msg.value - artFee) > 0) {
            //@> The following call will always revert due to the PhiFactory contract is not able to receive ETH via regular transactions.
            _msgSender().safeTransferETH(msg.value - artFee);
        }

        return createdTokenId;
    }
```

**Summary:**
In the current implementation, excess ETH sent during the `PhiFactory::createArt` function call would be locked in the contract. However, this issue is indirectly mitigated by the second bug—the absence of `receive` or `fallback` functions in the `PhiFactory` contract—which prevents the `createArtFromFactory` function from attempting to process refunds and, therefore, avoids locking excess ETH.

## Recommended Mitigation Steps

For `PhiFactory::createArt`, either ensure that `msg.value` exactly matches `NFT_ART_CREATE_FEE` or implement logic to return any excess ETH.

For `PhiNFT1155::createArtFromFactory`, enforce that `msg.value` equals `NFT_ART_CREATE_FEE` and remove the logic for refunding excess ETH, as the `PhiFactory` contract should not hold any ETH.
