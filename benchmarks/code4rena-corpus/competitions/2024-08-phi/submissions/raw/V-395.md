# Vulnerability details

Bonding curves are particularly susceptible to MEV, arbitrages, inflation/deflation mismanagement, etc. The `_handleTrade()` function in the `Cred.sol` contract interacts with a bonding curve that uses a fixed `CURVE_FACTOR` for pricing. This design does not account for dynamic market conditions. The fixed `CURVE_FACTOR` in the `BondingCurve.sol` contract introduces significant economic inefficiencies and risks to the protocol's financial health. By not adjusting to market conditions, the fixed factor can cause incorrect pricing of buy and sell operations.

The fixed nature of the `CURVE_FACTOR` means that price sensitivity to supply changes is static. Economically, this leads to pricing that might not reflect true market conditions:

Buy Side Impact: Users might pay a premium that does not match actual demand, causing a potential loss of user interest.

Sell Side Impact: Prices might drop too rapidly, causing the protocol to overpay when buying back tokens and draining funds.

## Impact
This vulnerability can cause the protocol to incur financial losses: the protocol may buy back tokens at excessively high prices or sell them at undervalued prices, and this can lead to severe price shocks during large transactions, destabilizing the market.

## Proof of Concept
In the `Cred.sol` buy and sell operations are being done via the following functions:

```solidity
    function buyShareCred(uint256 credId_, uint256 amount_, uint256 maxPrice_) public payable {
        _handleTrade(credId_, amount_, true, _msgSender(), maxPrice_);
    }

    function sellShareCred(uint256 credId_, uint256 amount_, uint256 minPrice_) public {
        _handleTrade(credId_, amount_, false, _msgSender(), minPrice_);
    }

    function buyShareCredFor(uint256 credId_, uint256 amount_, address curator_, uint256 maxPrice_) public payable {
        if (curator_ == address(0)) revert InvalidAddressZero();
        _handleTrade(credId_, amount_, true, curator_, maxPrice_);
    }
```

These functions in turn call `_handleTrade()`, and this in turn utilizes the bonding curve calculations to determine prices:

```solidity

        (uint256 price, uint256 protocolFee, uint256 creatorFee) =

```

Then `getPriceData()` from the `BondingCurve.sol` contract calls `getPrice()` which in turn calls `_curve()`:

```solidity
    function getPrice(uint256 supply_, uint256 amount_) public pure returns (uint256) {
        return _curve((supply_ + amount_) * 1 ether) - _curve(supply_ * 1 ether);
    }
```

The `_curve()` function calculates the price of tokens based on a fixed `CURVE_FACTOR`:

```solidity
    function _curve(uint256 targetAmount_) private pure returns (uint256) {
        return (TOTAL_SUPPLY_FACTOR * CURVE_FACTOR * 1 ether) / (TOTAL_SUPPLY_FACTOR - targetAmount_)
            - CURVE_FACTOR * 1 ether - INITIAL_PRICE_FACTOR * targetAmount_ / 1000;
    }
```

```solidity
    uint256 private constant CURVE_FACTOR = 10;
```

Numerical Example:

Let's assume:
     - `CURVE_FACTOR = 10`
     - `TOTAL_SUPPLY_FACTOR = 1000 ether`
     - `INITIAL_PRICE_FACTOR = 9`
     - Initial supply: `100 ether`

Buying Scenario:

Suppose a user wants to buy `10 ether` of tokens. The price is calculated using `_curve(10 ether)`:

```
Price = (1000 ether * 10 * 1 ether) / (1000 ether - 10 ether) - (10 * 1 ether) 
- (9 * 10 ether / 1000) = 0.0110 ether (approx).
```

   - If the market price outside the bonding curve is `< 0.0110 ether`, the protocol overcharges, making it uncompetitive and reducing buying activity.
   - Conversely, if the market price spikes to `> 0.0110 ether`, the bonding curve’s fixed factor allows users to buy at `0.0110 ether`, creating an arbitrage opportunity.

## Recommended Mitigation Steps

Implement a dynamic `CURVE_FACTOR` that adjusts based on market conditions or introduce an algorithmic adjustment mechanism to mitigate risks.
