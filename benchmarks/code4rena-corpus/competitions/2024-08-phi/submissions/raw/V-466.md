# Vulnerability details

## Impact

While the `CreatorRoyaltiesControl` contract aims to announce NFT Royalty Support (ERC-2981) through Standard Interface Detection (ERC-165 / supportInterface), it fails to properly implement the Standard Interface Detection (ERC-165) standard itself.

- Contracts or systems querying for basic ERC-165 support will incorrectly conclude that this contract does not support ERC-165 and therefore never proceed further to check for NFT Royalty Support (ERC-2981).
- The mismatch between intention (`ICreatorRoyaltiesControl is IERC2981`, `interface IERC2981 is IERC165`) and implementation may cause interoperability issues with systems that rely on proper ERC-165 interface reporting.
- Could lead to unexpected behavior in more complex systems that assume full ERC-165 compliance based on the interface inheritance structure.
- The contract's intended functionality of supporting NFT royalties may be entirely overlooked by systems that strictly adhere to the ERC-165 standard for interface detection.

## Recommended Mitigation Steps

change the current implementation to 
```
    /// @notice Checks if the contract supports a given interface
    /// @param interfaceId The interface identifier
    /// @return true if the contract supports the interface, false otherwise
    function supportsInterface(bytes4 interfaceId) public view virtual returns (bool) {
        return interfaceId == type(IERC2981).interfaceId ||
                interfaceId == type(IERC165).interfaceId;
    }
```

or have `CreatorRoyaltiesControl` inherit OZ's ERC165 and follow ERC2981 implementation of `supportsInterface` function as visible here: https://github.com/OpenZeppelin/openzeppelin-contracts/blob/29a953954d308d0786403155db1eff9addcf6e2b/contracts/token/common/ERC2981.sol#L54-L56
