# Vulnerability details

The `Cred.sol` contract is vulnerable to a signature replay attack that allows a malicious curator to repeatedly execute transactions with the same signature until it expires. This issue arises because the contract lacks proper mechanisms to ensure that a signature is used only once, which can lead to unauthorized and repeated access to certain functionalities within the contract.

The `createCred()` and `updateCred()` functions receive signed data and a signature. The contract uses `_recoverSigner(keccak256(signedData_), signature_)` to verify that the signature was signed by the correct address (`phiSignerAddress`). It decodes the signed data, extracting the `expiresIn` field, which specifies the expiration timestamp. The contract checks if `expiresIn <= block.timestamp`, reverting with `SignatureExpired()` if the signature has expired. Then checks `sender != _msgSender()`.

```solidity
        if (_recoverSigner(keccak256(signedData_), signature_) != phiSignerAddress) revert AddressNotSigned();
        (
            uint256 expiresIn,
            address sender,
            ,
            address bondingCurve,
            string memory credURL,
            string memory credType,
            string memory verificationType,
            bytes32 merkleRoot_
        ) = abi.decode(signedData_, (uint256, address, uint256, address, string, string, string, bytes32));
        if (expiresIn <= block.timestamp) revert SignatureExpired();

        if (sender != _msgSender()) revert Unauthorized();
```

The contract checks the `expiresIn` timestamp against the current `block.timestamp`. If the deadline hasn't been reached, the signature is still valid, allowing the user to use it repeatedly within the allowed timeframe. So this means that the function does not include logic to mark the signature as used, allowing it to be reused multiple times.

## Impact

The vulnerability allows a user to create multiple `Creds` using a single signature provided by the backend. Since there is no mechanism to mark signatures as used, a malicious user can repeatedly reuse the same signature to create an "unlimited" number of `Creds`, bypassing intended restrictions and controls, and if creating `Creds` has an associated cost this could be exploited for profit.

## Recommended Mitigation Steps

Implement a `nonce` mechanism to ensure that each signature is unique and can only be used once. Moreover, there is no `chainID` in the signature structure as well, this can be problematic when the blockchain undergoes a fork, or when working in different chains.
