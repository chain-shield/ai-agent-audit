# Vulnerability details

## Impact
Detailed description of the impact of this finding.

Cred contract has Unprotected Function _addCredIdPerAddress.

The _addCredIdPerAddress function is marked as public, which means it can be called by any external address. This lack of access control could allow malicious actors to manipulate the _credIdsPerAddress mapping, potentially leading to data corruption, unexpected behaviour, or exploitation of the contract’s logic.

Allowing external access to the _addCredIdPerAddress function can result in unauthorised additions of credIds to a curator’s address. This could lead to:

Inaccurate tracking of credIds associated with an address.

Potential manipulation of the internal state, affecting the logic of other functions relying on this mapping.

Possible exploitation of the contract’s functionality, leading to financial losses or incorrect distribution of rewards.

## Proof of Concept

Consider the following scenario where an external user calls the _addCredIdPerAddress function directly:
```sol
contract MaliciousContract {
    Cred credContract;

    constructor(address credContractAddress) {
        credContract = Cred(credContractAddress);
    }

    function exploit() external {
        uint256 fakeCredId = 9999; // Arbitrary fake credId
        address victim = msg.sender; // Victim's address
        credContract._addCredIdPerAddress(fakeCredId, victim); // Publicly accessible function
    }
}
```

In the above code, the MaliciousContract calls the _addCredIdPerAddress function on the Cred contract, adding an arbitrary credId to the victim’s address. This could cause unintended behaviour in the Cred contract, especially when querying or updating the victim’s credId list.

## Recommended Mitigation Steps

To mitigate this issue, the visibility of the _addCredIdPerAddress function should be changed to internal or private to restrict access to only the contract itself or its derived contracts. Additionally, review the access control for this function to ensure it is used securely within the contract’s logic.
```sol
// Original Function
function _addCredIdPerAddress(uint256 credId_, address sender_) public {
    _credIdsPerAddress[sender_].push(credId_);
    _credIdsPerAddressCredIdIndex[sender_][credId_] = _credIdsPerAddressArrLength[sender_];
    _credIdsPerAddressArrLength[sender_]++;
}

// Mitigated Function
function _addCredIdPerAddress(uint256 credId_, address sender_) internal {
    _credIdsPerAddress[sender_].push(credId_);
    _credIdsPerAddressCredIdIndex[sender_][credId_] = _credIdsPerAddressArrLength[sender_];
    _credIdsPerAddressArrLength[sender_]++;
}
```
By changing the visibility to internal, the function is no longer accessible to external contracts or users, mitigating the risk of unauthorised access and potential exploitation.

The lack of access control on the _addCredIdPerAddress function poses a significant security risk to the contract’s integrity. By restricting the visibility of this function, the contract will be protected from unauthorised modifications to the _credIdsPerAddress mapping, ensuring the contract’s logic remains secure and accurate.
