# Vulnerability details

## Impact
Within the protocol a user can encourage others to mint tokens by sharing a referral link, when using this link the referrer earns a small fee per art piece claimed via their link. At the smart contract level the referrer's address is passed as part of the `encodeData_` to one of the `PhiFactory` `claim`/`signatureClaim`/`merkleClaim` functions. 
In the case of signature claims the `ref_` provided is part of the signed data ensuring that only the correct referrer receives the mint reward. However for the case of `merkleClaim` there is no such validation meaning the person claiming is free to set an address of their own as the `ref_` meaning they are able to mint without paying this referral fee.
A deeper look at `PhiRewards:depositRewards` when the rewards for a claim are calculated shows the following check:
```
        if (referral_ == minter_ || referral_ == address(0)) {
            artistTotalReward_ += referralTotalReward_;
            referralTotalReward_ = 0;
        } else if (referral_ != address(0)) {
            balanceOf[referral_] += referralTotalReward_;
        }
```

This means that in the event of a self referral or no referral the `referralTotalReward_` should be added to the artist's cut of the total rewards. However this can be avoided by the caller by manually setting their `ref_` address to an address they control (but differs to the one they are minting with). This way they can complete the mint, and later withdraw the reward fee from the second address, effectively minting the art piece at a cheaper price than intended.

## Proof Of Concept
Consider the following scenarios:
### User A
1. User A intends to claim a piece of art from `PhiFactory` by calling `merkleClaim`.
2. The Philand frontend builds the user a transaction including `encodeData_` as an arg where `ref_ == address(0)` because he is not claiming via referral link.
3. The user sends the transaction with the total mint price and the `referralTotalReward_` is given to the artist.

### User B
1. User B intends to claim a piece of art from `PhiFactory` by calling `merkleClaim`.
2. The Philand frontend builds the user a transaction including `encodeData_` as an arg where `ref_ == address(0)` because he is not claiming via referral link.
3. However User B edits the calldata for the transaction by changing `ref_ == USER_B_SECONDARY_ADDRESS`
4. User B sends the transaction with the total mint price and the `referralTotalReward` is sent to his secondary address.
5. User B can then use this secondary address to withdraw the `referralTotalReward` meaning they minted for a significantly cheaper price than User A.

Because User B is slightly more savvy than User A they are able to mint at a lower price. 

## Recommended Mitigation
This is a difficult issue to work around without adding an additional data signed by `phiSignerAddress` and a signature check to the `merkleClaim` function.
One way this could be partially mitigated would be to require would-be referrers to register as a referrer within the contract (with a signature from `phiSignerAddress`) and then the `PhiRewards` contract would verify whether a given `referral_` address is that of a verifier referrer and then either allocate the rewards to that address or the artists address based on the result.
