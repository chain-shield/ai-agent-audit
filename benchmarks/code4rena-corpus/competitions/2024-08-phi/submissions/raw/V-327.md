# Vulnerability details

## Impact
Bypasses the signature claim fix and lead to signature replay attack

## Proof of Concept
From the audit the fix is using expiresIn. However it is vulnerable to 
Front-Running:
An attacker could potentially front-run a transaction by observing the expiresIn value and submitting their own transaction with the same signature before the original transaction is processed. If the attacker can predict or control the timing, they might exploit this to claim rewards or perform actions before the legitimate user.

Also it relies on the user to set an expiresIn some might set an extremely long expired value and makes the expire check basically redundant.


## Tools Used
Code review

## Recommended Mitigation Steps

Use a nonce instead

    function withdrawWithSig(address from, address to, uint256 amount, uint256 deadline, bytes calldata sig) external {
        if (block.timestamp > deadline) revert DeadlineExpired();
        if (!_verifySignature(from, to, amount, nonces[from], deadline, sig)) revert InvalidSignature();

        unchecked {
            ++nonces[from];
        }

        _withdraw(from, to, amount);
    }


A nonce is already used here in RewardControl.sol. Use nonce in the rest of the codebase instead of expiresIn.
