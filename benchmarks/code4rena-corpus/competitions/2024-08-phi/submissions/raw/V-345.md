# Vulnerability details

[getPriceDate function in the BondingCurve](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/curve/BondingCurve.sol#L51-L72) incorrectly calculates the creator fee when the supply is zero. This can lead to a scenario where the total fees (protocol fee + creator fee) exceed the value sent by the buyer during a buy operation.

```solidity
function getPriceData(
    uint256 credId_,
    uint256 supply_,
    uint256 amount_,
    bool isSign_
)
    public
    view
    returns (uint256 price, uint256 protocolFee, uint256 creatorFee)
{
    (uint16 buyShareRoyalty, uint16 sellShareRoyalty) = credContract.getCreatorRoyalty(credId_);

    price = isSign_ ? getPrice(supply_, amount_) : getPrice(supply_ - amount_, amount_);

    protocolFee = _getProtocolFee(price);
    if (supply_ == 0) {
        creatorFee = 0;
        return (price, protocolFee, creatorFee);
    }
    uint16 royaltyRate = isSign_ ? buyShareRoyalty : sellShareRoyalty;
    creatorFee = (price * royaltyRate) / RATIO_BASE;
}
```
The bug occurs when `supply_ == 0`. In this case, the function sets `creatorFee = 0` and immediately returns without considering the `royaltyRate`. This leads to a scenario where the total fees (protocol fee + creator fee) can exceed the sent value (`msg.value`) in a buy operation.

## Impact
In certain scenarios, the total fees charged to the buyer can exceed the value sent with the transaction, resulting in an inconsistent state and potential loss of funds.

## Proof of Concept
In the `getPriceData` function of [BondingCurve.so#L66-L71](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/curve/BondingCurve.sol#L66-L72)
```solidity
if (supply_ == 0) {
    creatorFee = 0;
    return (price, protocolFee, creatorFee);
}
uint16 royaltyRate = isSign_ ? buyShareRoyalty : sellShareRoyalty;
creatorFee = (price * royaltyRate) / RATIO_BASE;
```
When the `supply_` is zero, the function sets the `creatorFee` to zero and immediately returns without considering the `royaltyRate`. This can lead to a situation where the total fees exceed the value sent by the buyer.

Handling the zero supply case separately and setting the `creatorFee` to zero is a design mistake. It fails to account for the creator's royalty rate and can result in incorrect fee calculations.

**To exploit this vulnerability, the following preconditions must be met:**

* The `credId_` must correspond to a valid cred with a creator royalty rate set.
* The `supply_` of the cred must be zero.

**Scenario:**

* A creator creates a new cred with a non-zero royalty rate using the `createCred` function in the `Cred` contract.
* A buyer calls the `buyShareCred` function in the `Cred` contract to purchase shares of the cred.
* Inside the `buyShareCred` function, the `_handleTrade` function is called with `isBuy` set to true.
* The `getPriceData` function in the `BondingCurve` contract is invoked to calculate the price, protocol fee, and creator fee.
* Since the `supply_` is zero, the `getPriceData` function sets the `creatorFee` to zero and returns without considering the royalty rate.
* The `buyShareCred` function proceeds with the buy operation, but the total fees charged to the buyer (protocol fee + creator fee) may exceed the value sent with the transaction.

As a result, the protocol and creators may not receive the expected fees, and the buyer may be overcharged.

## Tools Used
Manual review of the smart contract code and analysis of the fee calculation logic.

## Recommended Mitigation Steps
`getPriceData` function should be modified to calculate the creator fee based on the royalty rate, even when the supply is zero. 
```diff
- if (supply_ == 0) {
-     creatorFee = 0;
-     return (price, protocolFee, creatorFee);
- }
uint16 royaltyRate = isSign_ ? buyShareRoyalty : sellShareRoyalty;
creatorFee = (price * royaltyRate) / RATIO_BASE;
```
By removing the special case for zero supply and always calculating the creator fee based on the royalty rate, the total fees will be correctly computed and will not exceed the value sent by the buyer.
