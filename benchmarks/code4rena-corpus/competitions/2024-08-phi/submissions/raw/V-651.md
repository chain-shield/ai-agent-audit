# Vulnerability details

## Summary
The Cred contract implements a share trading system using bonding curves for price determination. While it includes price limit checks, it lacks a dedicated slippage protection mechanism, which is crucial in decentralized trading systems to protect users from price movements between transaction submission and execution.

The contract uses fixed price limits (`maxPrice_` for buying and `minPrice_` for selling) instead of percentage-based slippage tolerances. This approach is less flexible and can lead to issues in volatile markets or when there's network congestion.

## Impact
1. **Unexpected Trade Failures**: In volatile markets, trades might fail unexpectedly if the price moves beyond the fixed limit, even if the user would have accepted a small percentage change.
2. **Inflexibility**: Users must specify exact price limits, which can be challenging in a dynamic market environment.
3. **Potential for Front-Running**: The lack of percentage-based slippage protection makes the system more vulnerable to front-running attacks, where malicious actors could manipulate prices within the fixed limit.
4. **Poor User Experience**: Users might need to repeatedly adjust and resubmit transactions in volatile markets, leading to a frustrating experience and potentially higher gas costs.

## Scenario
1. Alice wants to buy shares of Cred #1, which is currently priced at 1 ETH per share.
2. She submits a transaction to buy 1 share with a `maxPrice_` of 1.05 ETH, allowing for a 5% increase.
3. Due to network congestion, the transaction isn't processed immediately.
4. Meanwhile, the price of Cred #1 increases by 6% to 1.06 ETH.
5. When Alice's transaction is finally processed, it fails because the new price exceeds her specified `maxPrice_`.
6. If the contract had percentage-based slippage protection, Alice could have specified a 10% slippage tolerance, and her transaction would have succeeded despite the price increase.

## Recommendation
Implement a percentage-based slippage protection mechanism:

1. Add a `slippagePercentage` parameter to trading functions.
2. Calculate the maximum (for buy) or minimum (for sell) acceptable price based on this percentage.
3. Use this calculated value for price checks instead of the fixed price limit.

Example implementation for `buyShareCred`:

```solidity
function buyShareCred(uint256 credId_, uint256 amount_, uint256 slippagePercentage_) public payable {
    PhiCred storage cred = creds[credId_];
    (uint256 expectedPrice, uint256 protocolFee, uint256 creatorFee) =
        IBondingCurve(cred.bondingCurve).getPriceData(credId_, cred.currentSupply, amount_, true);
    
    uint256 maxAcceptablePrice = expectedPrice + (expectedPrice * slippagePercentage_ / 10000);
    
    if (expectedPrice + protocolFee + creatorFee > maxAcceptablePrice) revert PriceExceedsSlippageTolerance();
    
    // ... (rest of the function)
}
```

Similar changes should be applied to `sellShareCred` and batch trading functions. This approach provides more flexibility and better protection against price volatility and potential front-running attacks.
