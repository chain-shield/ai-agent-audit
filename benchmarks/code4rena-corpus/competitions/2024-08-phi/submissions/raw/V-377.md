# Vulnerability details

## Impact
As specified in the description of the contest on the C4 Page - [Reference here](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/README.md?plain=1#L138-L141) the **Minter should be trusted.** 

However **Anyone** can front-run the call to the `signatureClaim()` function ( or other claim function ) and change the `imageURI` for the NFT that's about to be claimed by a specific user who's eligible to claim it (Minter). 
This happens because the **imageURI** **is not set in the signature** itself but is arbitrarily specified as separate function param.

Since the **imageURI** could be displayed in the frontend, not having any validations for it could lead to security implications:
- NSFW images being displayed on website. 
- XSS scripts that can exploit vulnerabilities ( However, this won't have serious impact if the frontend is properly secured, this is the reason this issue is marked as **Medium**, as if everything else is secured, no loss of funds should occur )
- And additionally **CSRF Attacks** in some very very rare cases, where user uses very outdated browser, could be technically possible. Example: `<img src="https://target-site.com/perform-action?param=value" />`. However this should be protected from all modern browsers.
 

## Proof of Concept

MintArgs's **imageURI is arbitrary set**, rather than retrieved from the encodedData(signed data) and directly passed in the `_processClaim` without any validation.
```solidity
    function signatureClaim(
        bytes calldata signature_,
        bytes calldata encodeData_,
@>>     MintArgs calldata mintArgs_
    )
    {
@>>     (uint256 expiresIn_, address minter_, address ref_, address verifier_, uint256 artId_,, bytes32 data_) =
            abi.decode(encodeData_, (uint256, address, address, address, uint256, uint256, bytes32));

        if (expiresIn_ <= block.timestamp) revert SignatureExpired();
        if (_recoverSigner(keccak256(encodeData_), signature_) != phiSignerAddress) revert AddressNotSigned();

        _validateAndUpdateClaimState(artId_, minter_, mintArgs_.quantity);
@>>     _processClaim(artId_, minter_, ref_, verifier_, mintArgs_.quantity, data_, mintArgs_.imageURI, msg.value);
    }
```

Then its directly encoded for the low-level call to the NFT (PhiNFT1155)
```solidity
    function _processClaim(....) {
....
        (bool success_,) = art.artAddress.call{ value: mintFee - mintProtocolFee * quantity_ }(
            abi.encodeWithSignature("claimFromFactory(uint256,address,address,address,uint256,bytes32,string)",
                artId_, minter_, ref_, verifier_, quantity_, data_,
@>>             imageURI_
            )
        );
....
    }
```

And then in the `claimFromFactory()` function in PhiNFT1155, a new NFT is minted with the ImageURI. Its saved in the `advancedTokenURI` mapping.
```solidity
    function claimFromFactory(....)
    {
        uint256 tokenId_ = _artIdToTokenId[artId_];
        if (tokenId_ == 0) {
            revert InValdidTokenId();
        }
@>>     mint(minter_, tokenId_, quantity_, imageURI_, data_); //@audit-issue its possible imageURI to be arbitrary
....
```

## Recommended Mitigation Steps

To keep the functionality that allows someone else to execute the "claim" transaction and pay the fee, while also preserving the integrity of the protocol, consider the following suggestions:
- Include sensitive data fields like imageURI or even tokenId in the signedData itself to avoid arbitrary images being set, possibly including NSFW content.
- Apply a limit to the byte size of imageURI to ensure that no large XSS scripts can be injected.
