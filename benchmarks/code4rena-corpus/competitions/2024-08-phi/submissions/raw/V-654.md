# Vulnerability details


## Description
The `_verifySignature` function in your `RewardControl` contract is responsible for verifying EIP-712 signatures, primarily for enabling gasless withdrawals. While this function leverages the `SignatureCheckerLib` from Solady for signature verification, it is vulnerable to two critical issues: Signature Malleability and Front-Running Attacks. These vulnerabilities could undermine the integrity of the contract's operations, potentially allowing for replay attacks, unauthorized actions, and denial-of-service conditions.

Signature malleability occurs when a cryptographic signature can be modified without altering the underlying message, resulting in multiple valid signatures for the same message. This undermines the uniqueness of signatures, leading to potential replay attacks or other security issues.

In your `_verifySignature` function, the following code snippet is used to verify signatures:

```
return SignatureCheckerLib.isValidSignatureNowCalldata(from, digest, sig);
```
However, the `SignatureCheckerLib` documentation explicitly mentions that the library does not check if a signature is non-malleable. This means that it is possible to create alternative valid signatures for the same message, which could allow an attacker to bypass certain checks that rely on the uniqueness of the signature.


Front-running occurs when a malicious user intercepts a transaction and takes an action before the intended transaction is executed. In the context of your contract, a front-running attack could involve a malicious user intercepting a signature intended for one action and using it to perform a different action, thereby blocking the original action.

For example, if the same signature verification logic is used for both acknowledging and deacknowledging a transaction, a malicious user could use the signature intended for acknowledging to perform a deacknowledgment, thereby blocking the original acknowledgment.

In your contract, the _verifySignature function is used for verifying signatures, but it uses a single type hash (WITHDRAW_TYPEHASH) for this purpose:

```
bytes32 structHash = keccak256(abi.encode(WITHDRAW_TYPEHASH, from, to, amount, nonce, deadline));
bytes32 digest = _hashTypedData(structHash);
```
If the same signature type is reused for different actions, this creates a vulnerability where an attacker can misuse the signature for unintended actions.


## Impact
An attacker could reuse the same signature in multiple contexts, leading to unintended duplicate actions (e.g., multiple withdrawals). Systems that assume a signature is unique may be tricked by multiple valid signatures, leading to potential security breaches.

By front-running a transaction, a malicious user can prevent the original transaction from being executed, leading to denial of service. A valid signature for one action could be misused for another, leading to unauthorized or unintended actions.

Manual Review

## Recommendation
Ensure that nonces are properly managed and incremented after each use. Nonces should be unique for each signature to prevent replay attacks, where the same signature could be reused to authorize multiple transactions. Also try to split the `sig` and verify that the s value of the signature is in the lower half of the elliptic curve order.
