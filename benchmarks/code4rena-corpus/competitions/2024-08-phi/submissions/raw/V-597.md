# Vulnerability details

### Summary
The `withdrawFor` function in the RewardControl contract has a critical vulnerability that allows any address to withdraw funds on behalf of any other address without proper authorization. This flaw compromises the security and integrity of the reward system.

The RewardControl contract manages an ETH-based reward system with functions for depositing and withdrawing funds. The `withdrawFor` function is intended for authorized withdrawals, but it currently lacks essential access controls.

### Vulnerable Code
```solidity
function withdrawFor(address from, uint256 amount) external {
    _withdraw(from, from, amount);
}

function _withdraw(address from, address to, uint256 amount) internal {
    if (to == address(0)) revert InvalidAddressZero();
    uint256 balance = balanceOf[from];
    if (amount == FULL_BALANCE) {
        amount = balance;
    }
    if (amount > balance) revert InvalidAmount();
    unchecked {
        balanceOf[from] = balance - amount;
    }
    emit Withdraw(from, to, amount);
    to.safeTransferETH(amount);
}
```

### Description
The `withdrawFor` function allows any external caller to withdraw funds for any address (`from`) without authorization checks. While it sends funds to the `from` address, it enables unauthorized manipulation of user balances, leading to several issues:

1. **Unauthorized Balance Manipulation**: Attackers can deplete user balances.
2. **Denial of Service (DoS)**: Repeated calls can force users to receive minimal ETH, disrupting their contract interactions.
3. **Interference with Signed Withdrawals**: Users may find their balances depleted before executing signed withdrawal transactions.
4. **Privacy Violations**: Forced withdrawals expose user balance information.
5. **System Integrity Compromise**: Trust in the reward system is undermined.

The function directly manipulates the `balanceOf` mapping, which tracks ETH balances for users.

### Implications of Manipulation
1. **Unauthorized Changes**: Any caller can invoke `withdrawFor`, altering any user's balance.
2. **Bypassing User Intent**: Users expect their balances to change only through their actions.
3. **Potential for Draining**: Balances can be depleted without user consent.
4. **Interference with Other Operations**: Other functions relying on `balanceOf` may behave unexpectedly.
5. **State Inconsistency**: Unexpected balance changes could lead to failed operations.


### Attack Scenario
1. Alice has 10 ETH in her balance.
2. Malicious actor Bob notices Alice's balance.
3. Bob calls `withdrawFor(Alice's address, 1 ETH)` multiple times.
4. Alice's balance is drained without her consent.
5. The contract's event log is flooded with unauthorized `Withdraw` events.

### Recommended Fix
Implement proper access control for the `withdrawFor` function. A suggested fix includes an authorization system:
```solidity
mapping(address => mapping(address => bool)) public authorizedWithdrawers;

function setAuthorizedWithdrawer(address withdrawer, bool authorized) external {
    authorizedWithdrawers[msg.sender][withdrawer] = authorized;
    emit AuthorizationSet(msg.sender, withdrawer, authorized);
}

function withdrawFor(address from, uint256 amount) external {
    require(authorizedWithdrawers[from][msg.sender], "Not authorized");
    _withdraw(from, from, amount);
}

event AuthorizationSet(address indexed from, address indexed withdrawer, bool authorized);
```
