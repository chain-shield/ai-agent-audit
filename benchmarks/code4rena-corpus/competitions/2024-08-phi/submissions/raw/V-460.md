# Vulnerability details

The Phi protocol gives the users the ability to buy shares of creds they believe are worth being more popular or more expensive, thus becoming their curators. To stop flash loan attacks the `Cred.sol` contract enforces a 10 minute timeout between buying a share and selling the bought share back:
https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L625-L629
```sol
if (block.timestamp <= lastTradeTimestamp[credId_][curator_] + SHARE_LOCK_PERIOD) {
    revert ShareLockPeriodNotPassed(
        block.timestamp, lastTradeTimestamp[credId_][curator_] + SHARE_LOCK_PERIOD
    );
}
```
where `SHARE_LOCK_PERIOD` is equal to 10 minutes.
The `lastTradeTimestamp` is being updated when the curator buys shares regardless of whether it's their first share or a successive purchase:
https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L638-L644
```sol
if (isBuy) {
    cred.currentSupply += amount_;
    uint256 excessPayment = msg.value - price - protocolFee - creatorFee;
    if (excessPayment > 0) {
        _msgSender().safeTransferETH(excessPayment);
    }
    lastTradeTimestamp[credId_][curator_] = block.timestamp;
```

The flow works as intended in the case if the user buys shares for themselves by calling the function `buyShareCred` or `batchBuyShareCred` and sells those shares by calling the function `sellShareCred` or `batchSellShareCred`.

However the `Cred` contract gives users the ability to buy shares for other users by calling the function `buyShareCredFor`:
https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L186-L189
```sol
function buyShareCredFor(uint256 credId_, uint256 amount_, address curator_, uint256 maxPrice_) public payable {
    if (curator_ == address(0)) revert InvalidAddressZero();
    _handleTrade(credId_, amount_, true, curator_, maxPrice_);
}
```
this would allow a potential attacker to weaponize that functionality in the following way:
- When the attacker notices a cred share sell function call in the memory pool from another user, the attacker can front-run the sell function call and buy a single share for that user thus updating the victims `lastTradeTimestamp` and making it equal to `block.timestamp`, and when the victims transaction processes the call will revert because of the share lock period check.

## Impact
If the attacker is motivated enough they can DOS the cred sell indefinitely however the second more probable attack vector is gas greifing.
In the case of a single share sell DOS the gas greifing impact is not that significant however because the protocol allows the selling of multiple cred shares by batch sells, and even if one cred is in that lock period the whole transaction will revert, thus if the attacker completes a DOS attack against a batch cred sale the potential gas impact can be substantial enough to even outworth the expenses spent by the attacker depending on the price of the cred that's being DOS-ed.

## Recommended Mitigation Steps
The issue can be mitigated by making the selling process a 2 step flow. First the cred seller initiates a sell by appending the sell request in a mapping where the initiation time is being stored. Later the cred seller can finalize the sell by calling a finalization function which will check whether the queued sell request belongs to that user, then validates that the initiation timestamp has passed the threshold of 10 minutes and completes the sell.
