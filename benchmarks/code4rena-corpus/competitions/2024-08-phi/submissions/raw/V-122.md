# Vulnerability details


## Description 

The `Cred` contract manages curator share balances using the [`_handleTrade`](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L588-L659) and [`_updateCuratorShareBalance` functions](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L666-L682). When a curator sells all their shares of a particular cred, the `_credIdExistsPerAddress` mapping is set to `false`, but the `shareBalance` mapping still contains an entry for the curator with a value of 0. This discrepancy can lead to an inconsistent state, potential loss of curator's cred ownership record, and incorrect reporting of a curator's cred holdings.

The `_handleTrade` function is responsible for handling the trade logic and calls `_updateCuratorShareBalance` to update the curator's share balance:

```solidity
function _handleTrade(
    uint256 credId_,
    uint256 amount_,
    bool isBuy,
    address curator_,
    uint256 priceLimit
)
    internal
    whenNotPaused
{
    // ... (other checks and logic)

    _updateCuratorShareBalance(credId_, curator_, amount_, isBuy);

    // ... (rest of the function)
}
```

The `_updateCuratorShareBalance` function updates the curator's share balance and manages the `_credIdExistsPerAddress` mapping:

The issue arises when a curator sells all their shares:
1. `_credIdExistsPerAddress` is set to `false`.
2. `shareBalance` still contains an entry with a value of 0.

This discrepancy can cause the `_addCredIdPerAddress` function to not be called on subsequent purchases, leading to an inconsistent state.

## Impact
The inconsistent state between `_credIdExistsPerAddress` and `shareBalance` can lead to incorrect state management and reporting. This can cause significant issues in tracking curator holdings, potentially leading to incorrect reporting of a curator's cred holdings and loss of ownership records.

## Proof of Concept
1. A curator buys shares of a cred.
2. The curator sells all their shares.
3. The `_credIdExistsPerAddress` is set to `false`, but `shareBalance` still has an entry with a value of 0.
4. If the curator tries to buy shares again, the `_addCredIdPerAddress` function won't be called because `currentNum` is not 0 (it exists in `shareBalance` with a value of 0).

## Recommended Mitigation Steps
Modify the `_updateCuratorShareBalance` function to remove the entry from `shareBalance` when the balance becomes zero:

```diff
function _updateCuratorShareBalance(uint256 credId_, address sender_, uint256 amount_, bool isBuy) internal {
    (, uint256 currentNum) = shareBalance[credId_].tryGet(sender_);

    if (isBuy) {
        if (currentNum == 0 && !_credIdExistsPerAddress[sender_][credId_]) {
            _addCredIdPerAddress(credId_, sender_);
            _credIdExistsPerAddress[sender_][credId_] = true;
        }
        shareBalance[credId_].set(sender_, currentNum + amount_);
    } else {
-        if ((currentNum - amount_) == 0) {
+        if (currentNum == amount_) {
            _removeCredIdPerAddress(credId_, sender_);
            _credIdExistsPerAddress[sender_][credId_] = false;
+            shareBalance[credId_].remove(sender_);  // Remove the entry completely
        } else {

        }
```
