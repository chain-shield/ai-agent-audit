# Vulnerability details

## Impact
User can prevent the protocol fee from going where it's supposed to go, by reentering the `Cred::_handleTrade()` function

## Proof of Concept
Since in both `isBuy` and `!isBuy` scenarios, some amounts of ether are sent to the `msg.sender`, and since it can be a contract, the function can be reentered. The protocol fee transfer happens after the transfer of funds to the `msg.sender`. This means that he for example can make a couple of deposits and the fee will go where its supposed to go only in the last one, ultimately leaving the `protocolFeeDestination` address without the funds that should be send to it.
The following block of code represents the issue:
```
        if (isBuy) {
            cred.currentSupply += amount_;
            uint256 excessPayment = msg.value - price - protocolFee - creatorFee;
            if (excessPayment > 0) {
                //FIXME: Sending eth means possible reentrancy
                _msgSender().safeTransferETH(excessPayment);
            }
            lastTradeTimestamp[credId_][curator_] = block.timestamp;
        } else {
            cred.currentSupply -= amount_;
            curator_.safeTransferETH(price - protocolFee - creatorFee);
        }

        protocolFeeDestination.safeTransferETH(protocolFee);
        IPhiRewards(phiRewardsAddress).deposit{ value: creatorFee }(
            creator, bytes4(keccak256("CREATOR_ROYALTY_FEE")), ""
        );
        emit Royalty(creator, credId_, creatorFee);

        cred.latestActiveTimestamp = block.timestamp;

        emit Trade(curator_, credId_, isBuy, amount_, price, protocolFee, cred.currentSupply);
    }

```

## Recommended Mitigation Steps
add the `nonReentrant()` modifier to the `handleTrade()` function
