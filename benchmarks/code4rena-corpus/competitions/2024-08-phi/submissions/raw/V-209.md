# Vulnerability details

The `CuratorRewardsDistributor::distribute()` function contains multiple nested loops, which can lead to excessive gas consumption, especially as the number of `Curator Addresses` grows. As marked by the `@>` annotations, the function involves extensive iteration through curator addresses. In extreme cases, the gas consumption can exceed `30,000,000`, the typical gas limit per block on the Ethereum Virtual Machine (EVM). Since each block on the EVM has a gas limit that usually hovers around `30,000,000 Gas` (depending on the network state), any transaction consuming more than this limit will not be included in a block, leading to transaction failure. Consequently, if the gas consumption for this function surpasses the block limit, it may result in the transaction never successfully executing on the Ethereum mainnet.

## Impact
The `CuratorRewardsDistributor::distribute()` function may fail to execute if the number of `Curator Addresses` is large, due to the high gas consumption caused by extensive looping.
## Proof of Concept
To demonstrate this issue, add the following test code to `test/CuratorRewardsDistributor.t.sol` and execute it:

As seen from the test output, when `cred.getCuratorAddressLength(credId) == 900`, the gas consumption for calling `distribute()` is `29,573,748`. This gas consumption level is very close to the block gas limit, making it nearly impossible for this transaction to be executed normally. Given that the contract's design allows for up to `999` curators, this could pose a significant issue.

## Recommended Mitigation Steps
1. Step-by-Step Processing: Consider breaking down the `distribute()` function into smaller functions that can be executed sequentially over multiple transactions.
2. Batch Processing: Instead of processing all curators in a single transaction, split the operation into multiple transactions, processing curators in smaller batches across multiple blocks.
