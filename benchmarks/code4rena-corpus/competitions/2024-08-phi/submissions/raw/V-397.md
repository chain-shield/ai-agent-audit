# Vulnerability details

## Impact
Every time an NFT is minted for a given cred, curator rewards are sent to `CuratorRewardsDistributor.sol`. Whenever a cred has non-0 balance, `distribute` can be invoked by anyone, balance for the given credential is split across all its' curators based on their shareBalance/totalShares.
```solidity
    function distribute(uint256 credId) external {
        if (!credContract.isExist(credId)) revert InvalidCredId();
        uint256 totalBalance = balanceOf[credId];
        if (totalBalance == 0) {
            revert NoBalanceToDistribute();
        }


        address[] memory distributeAddresses = credContract.getCuratorAddresses(credId, 0, 0); // fetch all curators with at least 1 share
        uint256 totalNum;


        for (uint256 i = 0; i < distributeAddresses.length; i++) {
            totalNum += credContract.getShareNumber(credId, distributeAddresses[i]);           // fetch each curator's shares and totalNum shares
        }


        if (totalNum == 0) {
            revert NoSharesToDistribute();
        }
    }
```
Afterwards the distributable amount is split accordingly to each curators % of shares owned. 

```solidity
        for (uint256 i = 0; i < distributeAddresses.length; i++) {
            address user = distributeAddresses[i];                              // fetch each individual curator


            uint256 userAmounts = credContract.getShareNumber(credId, user);    // fetch shares of given curator
            uint256 userRewards = (distributeAmount * userAmounts) / totalNum;  // calculate reward based on what fraction of totalShares curator has


            if (userRewards > 0) {
                amounts[i] = userRewards;
                actualDistributeAmount += userRewards;
            }
        }
```
The issue here is that `getShareNumber` returns most recent share balances data which can be abused by whale depositors to front-run reward distribution by purchasing large number of shares, invoking `distribute` and selling their shares after the 10-minute timelock.  

Similar issue was observed in issue [H-1] in Phi's previous audit, which takes into consideration flashloan attacks. The proposed mitigation makes flashloan attacks impossible but does not take into consideration whale deposits. Honest curators are still discouraged to purchase and hold signals since distributions can be tampered with. Impact - stolen rewards.

## Tools Used  

Manual Review  

## Recommended Mitigation Steps  

Most feasible solution is to invoke `distribute` each time a deposit is made so a new depositor would not have any claim on rewards accumulated prior their purchase. In order for this to work, `distribute` needs to be edited in cases of totalBalance = 0, instead of reverting, simply returning so purchases would not be bricked.
