# Vulnerability details

## Description

The `PhiRewards` contract manages deposits and withdrawals for art rewards in the system. The [`handleRewardsAndGetValueSent()` function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/PhiRewards.sol#L123-L148) is responsible for processing rewards when a user mints an art piece. This function relies on the [`computeMintReward()` function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/PhiRewards.sol#L153-L155) to calculate the total reward amount and verify that the sent value matches the expected reward. However, there is a  flaw in the reward calculation logic that leads to the `mintFee_` being counted twice, resulting in overpayment by users and incorrect reward distribution.

The issue stems from the [`computeMintReward()` function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/PhiRewards.sol#L153-L155), which includes the `mintFee_` in its calculation:

```solidity
File: PhiRewards.sol
153:     function computeMintReward(uint256 quantity_, uint256 mintFee_) public view returns (uint256) {
154:         return quantity_ * (artistReward + mintFee_ + referralReward + verifierReward + curateReward);
155:     }

```

This calculated value is then used to verify the sent amount in `handleRewardsAndGetValueSent()`:

```solidity
File: PhiRewards.sol
134:         if (computeMintReward(quantity_, mintFee_) != msg.value) {
135:             revert InvalidDeposit();
136:         }

```

However, when distributing the rewards, the `mintFee_` is added again to the artist's reward:

```solidity
File: PhiRewards.sol
138:         depositRewards(
139:             artId_,
140:             credId_,
141:             addressesData_,
142:             quantity_ * (mintFee_ + artistReward),
143:             quantity_ * referralReward,
144:             quantity_ * verifierReward,
145:             quantity_ * curateReward,
146:             chainSync_
147:         );

```

This double counting of `mintFee_` leads to a discrepancy between the amount users are required to send and the actual distribution of rewards.

## Impact
This issue has several significant impacts on the system:

1. Overpayment by users: Minters are required to send more ETH than necessary for minting, as the `mintFee_` is counted twice in the verification process.

2. Incorrect reward distribution: The artist receives an additional `quantity_ * mintFee_` in rewards, which is not accounted for in the initial calculation. This leads to an unfair advantage for artists at the expense of minters.

3. Contract balance discrepancy: Over time, the contract will accumulate excess ETH due to the overpayment, as the extra `mintFee_` is not properly accounted for or distributed.



## Proof of Concept
Consider the following scenario:

1. The current reward values are set as follows:
   - `artistReward = 0.0001 ether`
   - `referralReward = 0.00005 ether`
   - `verifierReward = 0.00005 ether`
   - `curateReward = 0.00005 ether`

2. A user wants to mint 1 art piece with a `mintFee_` of 0.01 ether.

3. The `computeMintReward()` function calculates the required payment as:
   `1 * (0.0001 + 0.01 + 0.00005 + 0.00005 + 0.00005) = 0.01025 ether`

4. The user sends 0.01025 ether, which passes the verification check.

5. However, when distributing rewards, the `mintFee_` is added again to the artist's reward:
   - Artist receives: `1 * (0.01 + 0.0001) = 0.0101 ether`
   - Referral receives: `1 * 0.00005 = 0.00005 ether`
   - Verifier receives: `1 * 0.00005 = 0.00005 ether`
   - Curator receives: `1 * 0.00005 = 0.00005 ether`

6. The total distributed amount is 0.01025 ether, but the artist has received an extra 0.01 ether that wasn't accounted for in the initial calculation.

## Tools Used
Manual review

## Recommended Mitigation Steps
To fix this issue, the `computeMintReward()` function should be modified to exclude the `mintFee_` from its calculation. Additionally, the check in `handleRewardsAndGetValueSent()` should be updated to include the `mintFee_` separately.
