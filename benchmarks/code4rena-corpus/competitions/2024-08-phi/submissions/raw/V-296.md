# Vulnerability details

In [BondingCurve.sol:128-150](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/curve/BondingCurve.sol#L128-L150), the `_getCreatorFee` function calculates the creator fee based on the `buyShareRoyalty` and `sellShareRoyalty` values. However, it doesn't consider the case when the `supply_` is 0.

When the `supply_` is 0, the `creatorFee` is set to 0 regardless of the `buyShareRoyalty` and `sellShareRoyalty` values. This leads to a scenario where the buy price with fee and sell price with fee can be equal, violating the expected invariant.

## Impact
When the supply of a cred is 0, the buy price with fee and sell price with fee can be equal, which goes against the expected behavior of the bonding curve. This could lead to incorrect pricing and unexpected behavior in the Phi protocol. Buyers and sellers may be affected by this inconsistency, as the buy price with fee can be equal to the sell price with fee under certain conditions, violating the expected invariant of the bonding curve.

## Proof of Concept
In the `BondingCurve` contract, the [_getCreatorFee](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/curve/BondingCurve.sol#L128-L150) function calculates the creator fee based on the `buyShareRoyalty` and `sellShareRoyalty` values. However, it doesn't handle the case when the `supply_` is 0 correctly.
```solidity
function _getCreatorFee(
    uint256 credId_,
    uint256 supply_,
    uint256 price_,
    bool isSign_
)
    internal
    view
    returns (uint256 creatorFee)
{
    if (!credContract.isExist(credId_)) {
        return 0;
    }
    if (supply_ == 0) {
        creatorFee = 0;
    }

    (uint16 buyShareRoyalty, uint16 sellShareRoyalty) = credContract.getCreatorRoyalty(credId_);

    uint16 royaltyRate = isSign_ ? buyShareRoyalty : sellShareRoyalty;
    creatorFee = (price_ * royaltyRate) / RATIO_BASE;
}
```
The choice to set the `creatorFee` to 0 when the `supply_` is 0 is a mistake, as it leads to inconsistent pricing between buy and sell orders.

**Conditions**
a. The `supply_` of a cred needs to be exactly 0.
b. The `buyShareRoyalty` and `sellShareRoyalt`y values need to be set to non-zero values.

**Scenario**

a. A new cred is created with a `supply_` of 0 and non-zero `buyShareRoyalty` and `sellShareRoyalty` values.
b. A user calls the `buyShareCred` function to buy 1 share of the cred.
c. The `_getCreatorFee` function is called to calculate the creator fee for the buy order.
d. Since the s`upply_` is 0, the `creatorFee` is set to 0, regardless of the `buyShareRoyalty` value.
e. The user receives the buy price with fee, which doesn't include the creator fee.
f. Another user calls the `sellShareCred` function to sell 1 share of the cred.
g. The `_getCreatorFee` function is called to calculate the creator fee for the sell order.
h. Since the `supply_` is still 0, the `creatorFee` is set to 0, regardless of the `sellShareRoyalty` value.
i. The user receives the sell price with fee, which doesn't include the creator fee.
j. The buy price with fee and sell price with fee are equal, violating the expected invariant of the bonding curve.

## Recommended Mitigation Steps
The `_getCreatorFee` function in `BondingCurve.so`l should be updated to handle the case when `supply_` is 0 correctly. The creator fee calculation should take into account the `buyShareRoyalty` and `sellShareRoyalty` values even when the supply is 0.
```diff
function _getCreatorFee(
    uint256 credId_,
    uint256 supply_,
    uint256 price_,
    bool isSign_
)
    internal
    view
    returns (uint256 creatorFee)
{

    uint16 royaltyRate = isSign_ ? buyShareRoyalty : sellShareRoyalty;
    creatorFee = (price_ * royaltyRate) / RATIO_BASE;
}
```
By removing the check for `supply_ == 0` and directly calculating the `creatorFee` based on the `buyShareRoyalty` and `sellShareRoyalty` values, the pricing will be consistent between buy and sell orders, even when the supply is 0.
