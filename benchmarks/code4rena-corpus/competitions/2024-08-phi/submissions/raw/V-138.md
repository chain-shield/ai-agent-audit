# Vulnerability details

## Impact

The vulnerability in the `distribute` function from lines 77 to 130 is a reentrancy issue. The function first calculates the total balance and distributes it among curators based on their share numbers. However, before the actual distribution to the `phiRewardsContract`, the contract transfers the remaining balance (royalty fee and any rounding errors) back to the caller using `safeTransferETH`. This external call to `_msgSender()` can potentially trigger a fallback function in the caller's contract, allowing it to re-enter the `distribute` function before the state update (`balanceOf[credId] -= totalBalance`) is completed. This can lead to multiple withdrawals, draining the contract's funds. To mitigate this, the state update should occur before any external calls, or a reentrancy guard should be implemented.

## Recommended Mitigation Steps

To resolve the reentrancy vulnerability in the `distribute` function, adopt the following recommendations:

**Reentrancy Guard**: Implement a reentrancy guard using a modifier, such as OpenZeppelin's `ReentrancyGuard`, to prevent reentrant calls to the `distribute` function. This adds an additional layer of protection by ensuring that the function cannot be re-entered during its execution.

Here's a brief example of how you might implement these changes:

```solidity
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

contract CuratorRewardsDistributor is Logo, Ownable2Step, ICuratorRewardsDistributor, ReentrancyGuard {
    // ...

    function distribute(uint256 credId) external nonReentrant {
        if (!credContract.isExist(credId)) revert InvalidCredId();
        uint256 totalBalance = balanceOf[credId];
        if (totalBalance == 0) {
            revert NoBalanceToDistribute();
        }

        address[] memory distributeAddresses = credContract.getCuratorAddresses(credId, 0, 0);
        uint256 totalNum;

        for (uint256 i = 0; i < distributeAddresses.length; i++) {
            totalNum += credContract.getShareNumber(credId, distributeAddresses[i]);
        }

        if (totalNum == 0) {
            revert NoSharesToDistribute();
        }

        uint256[] memory amounts = new uint256[](distributeAddresses.length);
        bytes4[] memory reasons = new bytes4[](distributeAddresses.length);

        uint256 royaltyfee = (totalBalance * withdrawRoyalty) / RATIO_BASE;
        uint256 distributeAmount = totalBalance - royaltyfee;

        uint256 actualDistributeAmount = 0;
        for (uint256 i = 0; i < distributeAddresses.length; i++) {
            address user = distributeAddresses[i];

            uint256 userAmounts = credContract.getShareNumber(credId, user);
            uint256 userRewards = (distributeAmount * userAmounts) / totalNum;

            if (userRewards > 0) {
                amounts[i] = userRewards;
                actualDistributeAmount += userRewards;
            }
        }

        // Update state before external calls
        balanceOf[credId] -= totalBalance;

        _msgSender().safeTransferETH(royaltyfee + distributeAmount - actualDistributeAmount);

        phiRewardsContract.depositBatch{ value: actualDistributeAmount }(
            distributeAddresses, amounts, reasons, "deposit from curator rewards distributor"
        );

        emit RewardsDistributed(
            credId, _msgSender(), royaltyfee + distributeAmount - actualDistributeAmount, distributeAmount, totalBalance
        );
    }
}
```

By implementing this change, you can mitigate the risk of a reentrancy attack in the `distribute` function.
