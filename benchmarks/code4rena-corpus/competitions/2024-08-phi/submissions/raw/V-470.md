# Vulnerability details

## Impact
It is the intention of the protocol to launch difference instances of the `PhiFactory` contract across different EVM chains. The `artIdCounter` on each of these chains will start from 1. Additionally the art created with `artId = 1` on chain A will likely not be the same piece of art created with `artId = 1` on chain B or chain C.
This is a problem for the protocol as the signed data for `PhiFactory::signatureClaim` confirms only that the user mints only a specified `artId` with no check that they are minting the the `artId` on a specific `chainId`. The fields making up the signed data are shown here:
```solidity
        (uint256 expiresIn_, address minter_, address ref_, address verifier_, uint256 artId_,, bytes32 data_) =
            abi.decode(encodeData_, (uint256, address, address, address, uint256, uint256, bytes32));

```
This means that a user who receives a signature to mint an `artId` on chain A can also mint the same `artId` on any chain `PhiFactory` is deployed to despite them not being eligible to do so.

Additionally in this scenario, the `ref_` and `verifier_` passed as part of the signature being repeated may not be the correct referral or verifier addresses for the `artId` on the other chain meaning their rewards are sent to the wrong address. This could lead to some scenario where if a user is able to get a correct signature on Chain A where their address is either the `referral` or `verifier` addresses they could mint on Chain B (where the referral and/or verifier address if different) and avoid paying the fee altogether.  



## Proof Of Concept
Consider the following scenario:
1. A cred with `"SIGNATURE"` verification type is created via `Cred::createCred`.
2. A piece of art is created on Chain A (Base) that is linked this this cred's id. This is the first piece created on the `PhiFactory` instance on Base so gets the `artId = 1`
3. A different piece of art is created on Chain B (Optimism) that is linked to a different cred's id.  This is the first piece created on the `PhiFactory` instance on Optimism so also gets the `artId = 1`
4. A user eligible for the Base art work gets a signature from `phiSignerAddress` to claim their art piece on Base.
5. The user will also be able to claim the art piece with the same `artId` on Optimism.

## Recommended Mitigation
Part of the data signed by the `phiSignerAddress` for the `signatureClaim` function should include `chainId` to ensure that the signature can only be used to claim the `artId` on the chain that they are eligible for. An example of how this could be implemented is like so:
```solidity
    function signatureClaim(
        bytes calldata signature_,
        bytes calldata encodeData_,
        MintArgs calldata mintArgs_
    )
        external
        payable
        whenNotPaused
    {
        (uint256 chainId, uint256 expiresIn_, address minter_, address ref_, address verifier_, uint256 artId_,, bytes32 data_) =
            abi.decode(encodeData_, (uint256, uint256, address, address, address, uint256, uint256, bytes32));
        require(chainId == block.chainid, "Wrong Chain");
        
        // -- Snip 
    }
```
