# Vulnerability details

## Impact
The PhiRewards contract suffers from an unexpected balance increase when the `chainSync_` flag is set to `fals`e and the `curatorRewardsDistributor` is not being used. This allows an attacker to manipulate the contract's balance by minting tokens with a specific set of parameters, causing the contract to retain the additional curator rewards instead of keeping them in the contract as intended.

## Proof of Concept
The incorrect handling of curator rewards in the `depositRewards` function will cause an unexpected balance increase for the PhiRewards contract as an attacker will mint tokens with `chainSync_` set to `false` and `curatorRewardsDistributor` not being used.

In [PhiRewards.sol:108-115](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/PhiRewards.sol#L108-L116), the `depositRewards` function incorrectly adds the curator rewards to the receiver's balance when `chainSync_` is `false` and `curatorRewardsDistributor` is not being used.
```solidity
if (chainSync_ && address(curatorRewardsDistributor) != address(0)) {
    //slither-disable-next-line arbitrary-send-eth
    curatorRewardsDistributor.deposit{ value: curateTotalReward_ }(credId_, curateTotalReward_);
    rewardsData = abi.encode(artistTotalReward_, referralTotalReward_, verifierTotalReward_, curateTotalReward_);
} else {
    balanceOf[receiver_] += curateTotalReward_; // Bug: Curator rewards added to receiver's balance
    rewardsData =
        abi.encode(artistTotalReward_ + curateTotalReward_, referralTotalReward_, verifierTotalReward_, 0);
}
```
Conditions that'll warrant this.

* The `chainSync_` flag needs to be set to false
* The `curatorRewardsDistributor` address needs to be set to the zero address (not being used)

**Attack Scenario**

1. The attacker calls the `handleRewardsAndGetValueSent `function in `PhiRewards.sol` with the following parameters:

   * `artId_`: any valid art ID
   * `credId_`: any valid cred ID
   * `quantity_`: a desired quantity
   * `mintFee_`: a desired mint fee
   * `addressesData_`: encoded addresses with the attacker's address as the receiver
   * `chainSync_`: `false`
   * `msg.value`: the expected mint reward calculated using `computeMintReward`

2. Inside `handleRewardsAndGetValueSent`, the `depositRewards` function is called with the calculated reward amounts.

3. In `depositRewards`, since `chainSync_` is false and `curatorRewardsDistributor` is not being used, the curator rewards are incorrectly added to the receiver's balance (the attacker's address).

4. The PhiRewards contract's balance increases by the sum of all the distributed rewards, which is greater than the `msg.value` (expected mint reward) due to the additional curator rewards being retained in the contract.

5. The attacker can repeat this process multiple times to gradually inflate the PhiRewards contract's balance, potentially impacting the economic model of the system.

## Tools Used
Manual review

## Recommended Mitigation Steps
Modify the `depositRewards` function to keep the curator rewards in the contract when `chainSync_` is `false`, instead of adding them to the receiver's balance. By removing the line that adds the curator rewards to the receiver's balance and updating the `rewardsData` encoding, the curator rewards will be kept in the contract as intended, preventing the unexpected balance increase.
```diff
if (chainSync_ && address(curatorRewardsDistributor) != address(0)) {
    //slither-disable-next-line arbitrary-send-eth
    curatorRewardsDistributor.deposit{ value: curateTotalReward_ }(credId_, curateTotalReward_);
    rewardsData = abi.encode(artistTotalReward_, referralTotalReward_, verifierTotalReward_, curateTotalReward_);
} else {
-   balanceOf[receiver_] += curateTotalReward_;
    rewardsData =
-       abi.encode(artistTotalReward_ + curateTotalReward_, referralTotalReward_, verifierTotalReward_, 0);
+       abi.encode(artistTotalReward_, referralTotalReward_, verifierTotalReward_, curateTotalReward_);
}
```
