# Vulnerability details


## Description

The `Cred` contract implements a system for buying and selling shares of credentials (creds) using a bonding curve mechanism. The core functionality is implemented in the [`buyShareCred()`](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L178-L180) and [`sellShareCred()` functions](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L182-L184), which both internally call the [`_handleTrade()` function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L588-L659) to execute the trade logic.

The [`_handleTrade()` function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L588-L659) performs several critical operations, including updating share balances, transferring ETH, and interacting with external contracts. However, the `buyShareCred()` and `sellShareCred()` functions lack reentrancy protection, which exposes the contract to potential reentrancy attacks.

The issue arises from the following sequence of events in the `_handleTrade()` function:

1. State changes (updating share balances and supply)
2. ETH transfers to various parties (excess payment refund, curator payment, protocol fee, creator royalty)
3. External contract call to `IPhiRewards.deposit()`

An attacker could exploit this vulnerability by creating a malicious contract that repeatedly calls `buyShareCred()` or `sellShareCred()` within its fallback function. This could lead to:

1. Draining funds from the contract by exploiting the ETH transfers before state updates are finalized
2. Manipulating share balances and supply, potentially allowing the attacker to acquire more shares than intended or sell shares they don't actually own

Here's a simplified example of the vulnerable code:

```solidity
function buyShareCred(uint256 credId_, uint256 amount_, uint256 maxPrice_) public payable {
    _handleTrade(credId_, amount_, true, _msgSender(), maxPrice_);
}

function sellShareCred(uint256 credId_, uint256 amount_, uint256 minPrice_) public {
    _handleTrade(credId_, amount_, false, _msgSender(), minPrice_);
}

function _handleTrade(
    uint256 credId_,
    uint256 amount_,
    bool isBuy,
    address curator_,
    uint256 priceLimit
) internal whenNotPaused {
    // ... state updates ...
    
    if (isBuy) {
        // ... more state updates ...
        if (excessPayment > 0) {
            _msgSender().safeTransferETH(excessPayment);
        }
    } else {
        curator_.safeTransferETH(price - protocolFee - creatorFee);
    }
    
    protocolFeeDestination.safeTransferETH(protocolFee);
    IPhiRewards(phiRewardsAddress).deposit{ value: creatorFee }(
        creator, bytes4(keccak256("CREATOR_ROYALTY_FEE")), ""
    );
    
    // ... more state updates ...
}
```

The lack of reentrancy protection in these core functions poses a significant risk to the integrity and security of the entire system.

## Impact

The reentrancy vulnerability in the `buyShareCred()` and `sellShareCred()` functions could lead to severe financial losses and compromise the integrity of the entire cred trading system. Attackers could potentially drain funds from the contract, manipulate share balances, and disrupt the intended functionality of the bonding curve mechanism.


## Proof of Concept

1. Attacker deploys a malicious contract with a fallback function that calls `buyShareCred()` or `sellShareCred()`.
2. Attacker initiates a trade by calling `buyShareCred()` or `sellShareCred()` from their malicious contract.
3. When `_handleTrade()` executes the ETH transfer (e.g., `_msgSender().safeTransferETH(excessPayment)`), it triggers the attacker's fallback function.
4. The fallback function initiates another trade before the first one completes, exploiting the inconsistent state.
5. This process repeats, allowing the attacker to drain funds or manipulate share balances.

## Recommended Mitigation Steps

To mitigate this vulnerability, implement the `nonReentrant` modifier on both `buyShareCred()` and `sellShareCred()` functions. This will prevent reentrancy attacks by ensuring that these functions cannot be called again until the previous invocation is complete.
