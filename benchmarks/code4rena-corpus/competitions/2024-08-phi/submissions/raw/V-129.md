# Vulnerability details

## Impact
The refund amount is incorrect, and the remaining ETH is not properly refunded to the sender users suffer a loss of funds equal to the sum of the protocol fees and creator fees when making batch purchases with a payment exceeding the total cost of the shares.

## Proof of Concept
In the `batchBuyShareCred` function of the `Cred` contract, the refund amount is incorrectly calculated as `msg.value - totalCost`, which does not account for the protocol fees and creator fees deducted from the payment. This will cause a loss of funds for users as they will not receive the correct refund amount when making batch purchases with a payment exceeding the total cost of the shares.

In Cred.sol:191-211, the refund amount is calculated as `msg.value - totalCost`, which does not consider the protocol fees and creator fees deducted from the payment:
```solidity
function batchBuyShareCred(
    uint256[] calldata credIds_,
    uint256[] calldata amounts_,
    uint256[] calldata maxPrices_,
    address curator_
)
    public
    payable
{
    // ...

    uint256 refund = msg.value - totalCost;
    if (refund > 0) {
        _msgSender().safeTransferETH(refund);
    }
}
```
The `batchBuyShareCred` function needs to be called with a payment (`msg.value`) that exceeds the total cost of the shares being purchased.

Attack Scenario

1. A user calls the `batchBuyShareCred` function with a payment that exceeds the total cost of the shares being purchased.
2. The `_validateAndCalculateBatch` function is called to calculate the total cost, prices, protocol fees, and creator fees for the batch purchase.
3. The `_executeBatchBuy` function is called to execute the batch purchase, deducting the protocol fees and creator fees from the payment.
4. The refund amount is calculated as `msg.value - totalCost`, which does not account for the deducted fees.
5. The user receives an incorrect refund amount, resulting in a loss of funds equal to the sum of the protocol fees and creator fees.

## Tools Used
Manual review

## Recommended Mitigation Steps
The refund amount should be calculated as `msg.value - (totalCost + sum(protocolFees) + sum(creatorFees))` to account for all the fees deducted from the payment.
```diff
function batchBuyShareCred(
    uint256[] calldata credIds_,
    uint256[] calldata amounts_,
    uint256[] calldata maxPrices_,
    address curator_
)
    public
    payable
{
    // ...

-   uint256 refund = msg.value - totalCost;
+   uint256 totalFees = 0;
+   for (uint256 i = 0; i < protocolFees.length; i++) {
+       totalFees += protocolFees[i] + creatorFees[i];
+   }
+   uint256 refund = msg.value - (totalCost + totalFees);
    if (refund > 0) {
        _msgSender().safeTransferETH(refund);
    }
}
```
By calculating the total fees as the sum of the protocol fees and creator fees and subtracting it along with the total cost from the payment, the refund amount will be correctly calculated, ensuring that users receive the proper refund when making batch purchases with a payment exceeding the total cost of the shares.
