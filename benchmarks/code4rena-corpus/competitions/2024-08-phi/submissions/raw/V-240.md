# Vulnerability details

## Impact
The protocol has a flawed supply update process, enabling users to manipulate the supply of Cred shares without proper validation. This vulnerability enables malicious actors to decrease the supply of a Cred without actually selling shares, leading to inconsistencies in the system and potential financial losses for other users.

## Proof of Concept
The root cause of this vulnerability lies in the [_handleTrade](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L588-L659) function in the Cred.sol contract [Cred.sol#L638-L648](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L638-L648)
```solidity
if (isBuy) {
    cred.currentSupply += amount_;
    uint256 excessPayment = msg.value - price - protocolFee - creatorFee;
    if (excessPayment > 0) {
        _msgSender().safeTransferETH(excessPayment);
    }
    lastTradeTimestamp[credId_][curator_] = block.timestamp;
} else {
    cred.currentSupply -= amount_;
    curator_.safeTransferETH(price - protocolFee - creatorFee);
}
```
The vulnerability arises in the `else` block, where the [cred.currentSupply](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L646) is decreased by `amount_` without proper validation. This allows the supply to be decreased even if the sell operation fails due to insufficient shares or other conditions.

The choice to update the supply before validating the sell operation is a design flaw that introduces this vulnerability.

When the Cred contract is initialized with a created Cred, and attacker have a balance of Cred shares less than the amount they intend to sell. This scenario would happen.

**Scenario**

* The attacker calls the `buyShareCred` function to purchase a small number of shares for a specific Cred.
* The attacker then calls the `sellShareCred` function, attempting to sell a larger number of shares than they actually possess.
* Inside the `_handleTrade` function, the `else` block is executed since it is a sell operation.
* The `cred.currentSupply` is decreased by the `amount_` specified by the attacker, even though the attacker does not have sufficient shares to sell.
* The sell operation fails due to insufficient shares, but the supply has already been decreased, resulting in an inconsistent state.

This scenario allows the attacker to manipulate the supply of Cred without selling shares, leading to financial losses for other users who rely on accurate supply information.

## Recommended Mitigation Steps
It is recommended to modify the `_handleTrade` function to ensure that the `cred.currentSupply` is only decreased if the sell operation is valid and all the necessary conditions are met. The decrease operation should be moved inside the block that checks for sufficient shares and other validations.

```diff
 if (isBuy) {
     cred.currentSupply += amount_;
     uint256 excessPayment = msg.value - price - protocolFee - creatorFee;
     if (excessPayment > 0) {
         _msgSender().safeTransferETH(excessPayment);
     }
     lastTradeTimestamp[credId_][curator_] = block.timestamp;
 } else {
-    cred.currentSupply -= amount_;
     curator_.safeTransferETH(price - protocolFee - creatorFee);
+    if (/* Validation checks for sufficient shares and other conditions */) {
+        cred.currentSupply -= amount_;
+    }
 }
```
By moving the `cred.currentSupply` decrease operation inside the validation block, we ensure that the supply is only updated if the sell operation is valid and all the necessary conditions are satisfied.
