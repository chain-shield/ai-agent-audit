# Vulnerability details

The `PhiFactory::merkleClaim()` function lacks sufficient validation mechanisms, making it susceptible to replay attacks. Specifically, in the code snippet below, the part marked with `@>` shows that only the `MerkleProofLib::verifyCalldata()` function is used for validation. This approach does not include any additional safeguards, such as a `nonce`, to prevent the reuse of valid proof data. As a result, a malicious actor could repeatedly invoke this method to claim an unlimited number of tokens.
```js
    // PhiFactory::merkleClaim()
    function merkleClaim(
        bytes32[] calldata proof_,
        bytes calldata encodeData_,
        MintArgs calldata mintArgs_,
        bytes32 leafPart_
    )
        external
        payable
        whenNotPaused
    {
        (address minter_, address ref_, uint256 artId_) = abi.decode(encodeData_, (address, address, uint256));
        PhiArt storage art = arts[artId_];


        bytes32 credMerkleRootHash = credMerkleRoot[art.credChainId][art.credId];
        if (minter_ == address(0) || !art.verificationType.eq("MERKLE") || credMerkleRootHash == bytes32(0)) {
            revert InvalidMerkleProof();
        }
        if (
@>            !MerkleProofLib.verifyCalldata(
                proof_, credMerkleRootHash, keccak256(bytes.concat(keccak256(abi.encode(minter_, leafPart_))))
            )
        ) {
            revert InvalidMerkleProof();
        }


        _validateAndUpdateClaimState(artId_, minter_, mintArgs_.quantity);
        _processClaim(
            artId_, minter_, ref_, art.credCreator, mintArgs_.quantity, leafPart_, mintArgs_.imageURI, msg.value
        );


        emit ArtClaimedData(artId_, "MERKLE", minter_, ref_, art.credCreator, art.artAddress, mintArgs_.quantity);
    }
```
## Impact
A malicious user, once in possession of valid claim data, can replay the transaction to claim tokens multiple times, leading to a significant loss of tokens.

## Recommended Mitigation Steps

Introduce a `nonce` to the Merkle proof, ensuring that each claim request includes a unique nonce (this could be based on a timestamp or an incremental counter inside the contract). The contract should enforce that once a `nonce` has been used, it cannot be reused for future claims.
