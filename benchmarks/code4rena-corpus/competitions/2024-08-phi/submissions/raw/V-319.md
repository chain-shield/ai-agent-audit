# Vulnerability details

## Impact

The `distribute` function in the `CuratorRewardsDistributor` contract is used to distribute rewards to curators who have invested in shares of a particular credential whenever a related NFT is minted. Due to the function's need to repeatedly process the list of shareholders, it becomes highly gas-intensive. When the number of curators with shares in a single credential reaches 110 or more, the gas required can exceed the 30,000,000 block limit. This leads to transaction reverts, causing the rewards to become locked within the contract.


```solidity
function distribute(uint256 credId) external {
    if (!credContract.isExist(credId)) revert InvalidCredId();
    uint256 totalBalance = balanceOf[credId];
    if (totalBalance == 0) {
        revert NoBalanceToDistribute();
    }

// @> Gas intensive computation
    address[] memory distributeAddresses = credContract.getCuratorAddresses(credId, 0, 0);
    uint256 totalNum;

// @> Gas intensive computation
    for (uint256 i = 0; i < distributeAddresses.length; i++) {
        totalNum += credContract.getShareNumber(credId, distributeAddresses[i]);
    }

    if (totalNum == 0) {
        revert NoSharesToDistribute();
    }

    uint256[] memory amounts = new uint256[](distributeAddresses.length);
    bytes4[] memory reasons = new bytes4[](distributeAddresses.length);


    uint256 royaltyfee = (totalBalance * withdrawRoyalty) / RATIO_BASE;
    uint256 distributeAmount = totalBalance - royaltyfee;

    // actualDistributeAmount is used to avoid rounding errors
    // amount[0] = 333 333 333 333 333 333
    // amount[1] = 333 333 333 333 333 333
    // amount[2] = 333 333 333 333 333 333
    uint256 actualDistributeAmount = 0;
// @> Gas intensive computation
    for (uint256 i = 0; i < distributeAddresses.length; i++) {
        address user = distributeAddresses[i];

        uint256 userAmounts = credContract.getShareNumber(credId, user);
        uint256 userRewards = (distributeAmount * userAmounts) / totalNum;

        if (userRewards > 0) {
            amounts[i] = userRewards;
            actualDistributeAmount += userRewards;
        }
    }

    balanceOf[credId] -= totalBalance;

    _msgSender().safeTransferETH(royaltyfee + distributeAmount - actualDistributeAmount);

    //slither-disable-next-line arbitrary-send-eth
// @> Gas intensive computation
    phiRewardsContract.depositBatch{ value: actualDistributeAmount }(
        distributeAddresses, amounts, reasons, "deposit from curator rewards distributor"
    );

    emit RewardsDistributed(
        credId, _msgSender(), royaltyfee + distributeAmount - actualDistributeAmount, distributeAmount, totalBalance
    );
}
```

## Proof of Concept

Add the following test to `/test/CuratorRewardsDistributor.t.sol`:

First, ensure you import the `Strings` library from OpenZeppelin by adding the following line at the top of your test file:
```solidity
import "@openzeppelin/contracts/utils/Strings.sol";
```

Then, run the test using the `--block-gas-limit` flag set to 30,000,000, as the default block gas limit in Foundry is set to unlimited:
```bash
forge test --match-test testDoSDistribution -vvv --block-gas-limit 30000000
```

The test should include the following steps:
1. Create 110 accounts.
2. Purchase 1 share per account.
3. Deposit some ETH to simulate rewards accumulation.
4. Call the `distribute` function to attempt the distribution of rewards.

This setup will help verify if the `distribute` function exceeds the block gas limit when processing a large number of shareholders.

## Recommended Mitigation Steps

Implement a MasterChef-style mechanism to track shares and trigger reward distribution each time a share is bought or sold, as well as before any rewards are withdrawn. For more information refer to [https://www.rareskills.io/post/staking-algorithm](https://www.rareskills.io/post/staking-algorithm)

**DISCLAIMER:** I consider there is another issue related to the `distribute` function—the potential for unfair reward distribution. However, this issue should be considered separately from the function's gas intensity. The fairness of reward distribution is a matter of design mechanics, while the gas inefficiency is an issue of implementation. The fact that the function may be gas-intensive does not inherently mean it will distribute rewards unfairly, and vice versa. Thus, these two concerns should be addressed independently.
