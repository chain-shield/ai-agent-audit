# Vulnerability details

## Impact
ETH can be permanently locked in the PhiNFT1155 contract. This could lead to loss of funds for users or the protocol if ETH is accidentally sent to the contract. 

## Proof of Concept
The PhiNFT1155 contract has a `receive()` function that allows it to accept ETH:

[PhiNFT1155.sol#L348-L351](https://github.com/code-423n4/2024-08-phi/blob/main/src/art/PhiNFT1155.sol#L359)
```Solidity
receive() external payable {
    // This function is intentionally left empty to allow the contract to receive ETH
}
```

However, there is no function in the contract that allows for the withdrawal of this ETH. The only functions that interact with the contract's ETH balance are `createArtFromFactory` and `claimFromFactory`, but these do not provide a way to withdraw all ETH from the contract.

In `createArtFromFactory`, there's a potential for small amounts of ETH to be left in the contract:

```Solidity
function createArtFromFactory(uint256 artId_) external payable onlyPhiFactory whenNotPaused returns (uint256) {
    // ... other code ...
    uint256 artFee = phiFactoryContract.artCreateFee();
    protocolFeeDestination.safeTransferETH(artFee);
    // ... other code ...
    if ((msg.value - artFee) > 0) {
        _msgSender().safeTransferETH(msg.value - artFee);
    }
    return createdTokenId;
}
```

If `msg.value` is exactly equal to `artFee`, no refund occurs, potentially leaving a small amount in the contract.

A part also of this issue could be:
1. A user sends a small amount of ETH directly to the contract address.
2. The ETH is accepted due to the `receive()` function.
3. The ETH is now locked in the contract with no way to withdraw it.

## Tools Used
Manual Review

## Recommended Mitigation Steps
1. Implement an emergency withdrawal function that only the contract owner can call to retrieve any accidentally sent ETH.
2. Remove the `receive()` function if there's no intended use for direct ETH transfers to the contract.
