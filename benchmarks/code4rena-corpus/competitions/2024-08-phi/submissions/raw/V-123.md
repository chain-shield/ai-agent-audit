# Vulnerability details


The [`createCred` function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L232-L280) in the `Cred` contract is responsible for creating new credentials (creds) and assigning initial shares to the creator. However, there is a critical bug in the function that causes the initial share to be assigned to a non-existent cred ID. This issue arises from the incorrect usage of the `credIdCounter` when calling the [`buyShareCred` function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L178-L180).

## Description

The `createCred` function is designed to create a new cred and assign an initial share to the creator. The function performs several steps:
1. Validates the input parameters.
2. Calls the `_createCredInternal` function to create a new cred and returns its ID.
3. Assigns an initial share to the newly created cred by calling the `buyShareCred` function.
4. Increments the `credIdCounter` to prepare for the next cred creation.

The issue lies in the order of operations within the `createCred` function. Specifically, the `buyShareCred` function is called with the current value of `credIdCounter` before it is incremented. This results in the initial share being assigned to the next cred ID rather than the current one.

Here is the relevant code snippet from the `createCred` function:

```solidity
function createCred(
    address creator_,
    bytes calldata signedData_,
    bytes calldata signature_,
    uint16 buyShareRoyalty_,
    uint16 sellShareRoyalty_
)
    public
    payable
    whenNotPaused
{
    // ... (validation and decoding logic)

    uint256 credId = _createCredInternal(
        creator_, credURL, credType, verificationType, bondingCurve, buyShareRoyalty_, sellShareRoyalty_
    );
    if (verificationType.eq("MERKLE")) {
        credsMerkeRoot[credId] = merkleRoot_;
        emit MerkleTreeSetUp(_msgSender(), credId, merkleRoot_);
    }

    buyShareCred(credIdCounter, 1, 0);

    emit CredCreated(creator_, credIdCounter, credURL_, credType_, verificationType_);

    credIdCounter += 1;

    return credIdCounter - 1;
}
```

In this code, `buyShareCred(credIdCounter, 1, 0)` is called with the current value of `credIdCounter`, which is then incremented after the call. This means the initial share is assigned to the next cred ID, not the one that was just created.

## Impact

The incorrect initial share assignment can lead to several serious issues:
- The creator of the cred does not receive the initial share they are supposed to.
- The bonding curve calculations for the newly created cred will be incorrect, as they will start from 0 shares instead of 1.
- It may cause errors or unexpected behavior when trying to interact with the non-existent cred (ID `n+1`).
- When the next cred is actually created with ID `n+1`, it will already have an initial share assigned to it, causing further inconsistencies.

## Proof of Concept

1. **Initial State**:
   - `credIdCounter` is 1.

2. **Creating the First Cred**:
   - The `createCred` function is called.
   - `_createCredInternal` is called with `credIdCounter` (which is 1), creating a new cred with ID 1.
   - `buyShareCred(credIdCounter, 1, 0)` is called with `credIdCounter` (which is still 1).
   - `credIdCounter` is incremented to 2.
   - The first cred is created with ID 1, and the initial share is correctly assigned to cred ID 1.

3. **Creating the Second Cred**:
   - The `createCred` function is called again.
   - `_createCredInternal` is called with `credIdCounter` (which is 2), creating a new cred with ID 2.
   - `buyShareCred(credIdCounter, 1, 0)` is called with `credIdCounter` (which is still 2).
   - `credIdCounter` is incremented to 3.
   - The second cred is created with ID 2, and the initial share is correctly assigned to cred ID 2.

4. **Creating the Third Cred**:
   - The `createCred` function is called again.
   - `_createCredInternal` is called with `credIdCounter` (which is 3), creating a new cred with ID 3.
   - `buyShareCred(credIdCounter, 1, 0)` is called with `credIdCounter` (which is still 3).
   - `credIdCounter` is incremented to 4.
   - The third cred is created with ID 3, and the initial share is correctly assigned to cred ID 3.

## Recommended Mitigation Steps

To fix this issue, the `credIdCounter` should be incremented before calling `buyShareCred`:

```diff
function createCred(
    address creator_,
    bytes calldata signedData_,
    bytes calldata signature_,
    uint16 buyShareRoyalty_,
    uint16 sellShareRoyalty_
)
    public
    payable
    whenNotPaused
{
    // ... (validation and decoding logic)

+   uint256 newCredId = credIdCounter;
+   credIdCounter += 1;

    uint256 credId = _createCredInternal(
        creator_, credURL, credType, verificationType, bondingCurve, buyShareRoyalty_, sellShareRoyalty_
    );
    if (verificationType.eq("MERKLE")) {
        credsMerkeRoot[credId] = merkleRoot_;
        emit MerkleTreeSetUp(_msgSender(), credId, merkleRoot_);
    }

-   buyShareCred(credIdCounter, 1, 0);
+   buyShareCred(newCredId, 1, 0);

-   emit CredCreated(creator_, credIdCounter, credURL_, credType_, verificationType_);
+   emit CredCreated(creator_, newCredId, credURL_, credType_, verificationType_);

-   credIdCounter += 1;

-   return credIdCounter - 1;
+   return newCredId;
}
```
