# Vulnerability details

## Impact

Impact is off-by-one error in the share lock period check (using `<=` instead of `<`) allows trades at exactly `t+600` seconds, violating the intended `t+600+ε` lock duration. This precision loss creates a exploitable time-of-check to time-of-use `TOCTOU` bug, enabling microsecond-level front-running and disrupting the protocol's temporal invariants in cross-contract interactions.

## Proof of Concept
I found a bug in [Cred.sol](https://github.com/code-423n4/2024-08-phi/blob/main/src/Cred.sol), in [_handleTrade()](https://github.com/code-423n4/2024-08-phi/blob/main/src/Cred.sol#L588) which is called by [sellShareCred()](https://github.com/code-423n4/2024-08-phi/blob/main/src/Cred.sol#L182C1-L184C6), [bugShareCred()](https://github.com/code-423n4/2024-08-phi/blob/main/src/Cred.sol#L178C13-L178C26), and [buyShareCredFor()](https://github.com/code-423n4/2024-08-phi/blob/main/src/Cred.sol#L186C14-L186C29):

## Recommended Mitigation Steps

Change `_handleTrade()` so that it handles correct timestamp comparison:

```solidity
function _handleTrade(
    uint256 credId_,
    uint256 amount_,
    bool isBuy,
    address curator_,
    uint256 priceLimit
)
    internal
    whenNotPaused
{
    // rest
    if (!isBuy) {
        if (block.timestamp < lastTradeTimestamp[credId_][curator_] + SHARE_LOCK_PERIOD) {
            revert ShareLockPeriodNotPassed(
                block.timestamp,
                lastTradeTimestamp[credId_][curator_] + SHARE_LOCK_PERIOD
            );
        }
        // rest
    }

    // rest
    if (isBuy) {
        lastTradeTimestamp[credId_][curator_] = block.timestamp;
    }
}
```

Using above method will make sure that the share lock period is correctly set, as it should be, and that users cannot sell shares before the lock period has passed.
