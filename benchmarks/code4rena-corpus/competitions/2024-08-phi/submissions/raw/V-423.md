# Vulnerability details

## Impact
In order to create a new art or claim one, users are given signed data by Phi's API which is later verified in the function to be signed by Phi. The issue is that no input validation is made to check if the user calling the function is the intended receiver. Anyone can copy the signed data from the mempool and replay it, essentially using a signature that was not intended for them.

## Proof of Concept
Let's examine [`createArt()`](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L196-L213). After the `signedData_` and `signature_` are passed, it [validates them](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L589-L593).

```solidity
    function _validateArtCreationSignature(bytes calldata signedData_, bytes calldata signature_) private view {
        if (_recoverSigner(keccak256(signedData_), signature_) != phiSignerAddress) revert AddressNotSigned();
        (uint256 expiresIn_,,) = abi.decode(signedData_, (uint256, string, bytes));
        if (expiresIn_ <= block.timestamp) revert SignatureExpired();
    }
```

The only thing checked is that the signer of the data is the `phiSignerAddress` and that the signature hasn't expired. Nowhere is it checked that `msg.sender` is the receiver/the one that requested the signed data so this validation will always pass regardless who uses the signed data. If we take a look at creating a cred it's a different story as there [msg.sender is validated](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L256).

```solidity
    if (sender != _msgSender()) revert Unauthorized();
```

This allows any user to replay the signature for creating and claiming art as long as it hasn't expired, even if it wasn't meant for them.

## Tools Used
Manual review
## Recommended Mitigation Steps
Implement input validation the same way as it is in creating a cred.
