# Vulnerability details

## Vulnerability Details

In `PhiFactory.sol` , the function `claim(bytes calldata encodeData_)` calls `merkleClaim` and `signatureClaim` using `this.` while setting new `msg.value` to `mintFee`.
```solidity
this.merkleClaim{ value: mintFee }(proof, claimData, mintArgs, leafPart_);
```
```solidity
this.signatureClaim{ value: mintFee }(signature_, claimData, mintArgs);
```
This means that the context of the call will be reset, and the `msg.value` passed to `merkleClaim` or `signatureClaim` will be exactly `mintFee` instead of current `msg.value`. This means if `msg.value` contains some buffer value sent by user, it will not get refunded to the user. This causes potential eth accumulation which also **breaks one of the "attack ideas" in the audit repo's README**.

This behaviour is also inconsistent to the senario if the user just calls `signatureClaim` or `merkleClaim` directly, as **without** the `this.` call by `claim`, the `etherValue_` will be set to the original `msg.value` and `_processClaim` will refund the user accurately through `_msgSender().safeTransferETH(etherValue_ - mintFee);`.

Hence, the refund mechanism works perfectly if the user goes through `merkleClaim` and `signatureClaim` directly, but fails instead when the user claims through `claim`, causing **inconsistency** to the official protocol refund guidelines.

Malicious users can then steal accumulated ETH to pay for their claim fees through calling `claim` with `msg.value` lower than `mintFee`. Since `claim` does not check `msg.value` and just passes `mintFee` to either `merkleClaim` or `signatureClaim`. As long as `msg.value` + ETH accumulated in contract >= `mintFee`, the transaction will not revert. Thus, even before the owner can call [`withdraw`](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L786) to damage control and return the eth manually to the victim, the malicious user has already frontran the owner and stole the ETH to pay for their own mint fees.

## Proof Of Concept
Add the following function to `test/PhiFactory.t.sol:TestPhiFactory`
```solidity
function test_refund_wrong_sender() public {
    _createArt(ART_ID_URL_STRING);

    address Alice = address(0x123);
    address Bob = address(0x987);

    uint256 totalMintFee = phiFactory.getArtMintFee(1, 1);
    uint256 buffer = 0.0000001 ether;
    vm.deal(Alice, totalMintFee + buffer);
    vm.deal(Bob, totalMintFee);

    vm.prank(Alice);
    phiFactory.claim{ value: totalMintFee + buffer }(compressedDataPermission(1, Alice, 1));//Alice claims

    vm.prank(Bob);
    phiFactory.claim{ value: totalMintFee - buffer }(compressedDataPermission(1, Bob, 1));//Bob claims

    console2.log("Alice:",Alice.balance);
    console2.log("Bob  :",Bob.balance);
    // Alice first starts with more ether than Bob, then they are both required to pay the same fee, but
    // in the end, Bob ends up with more ether than Alice, as he uses Alice's money to pay for his claim
}
```
Run `forge test --match-test test_refund_wrong_sender -vv`

## Recommended Mitigation Steps
Refund the user if `msg.value` > `mintFee` in `claim` to align refund mechanism to users calling `merkleClaim` or `signatureClaim` directly so that users will not end up assuming they can have a buffer/**send an estimated value with no danger** and get refunded like calling `merkleClaim` and `signatureClaim` directly does.

Doing this will also fix the ETH accumulation part which is an attack idea to look out for under the repo's README.

```diff
function claim(bytes calldata encodeData_) external payable {
    ....
    if (art.verificationType.eq("MERKLE")) {
        ....
+       if(msg.value > mintFee) _msgSender().safeTransferETH(msg.value - mintFee);
        this.merkleClaim{ value: mintFee }(proof, claimData, mintArgs, leafPart_);
    } else if (art.verificationType.eq("SIGNATURE")) {
        ....
+       if(msg.value > mintFee) _msgSender().safeTransferETH(msg.value - mintFee);
        this.signatureClaim{ value: mintFee }(signature_, claimData, mintArgs);
    } else {
        revert InvalidVerificationType();
    }
}
```
