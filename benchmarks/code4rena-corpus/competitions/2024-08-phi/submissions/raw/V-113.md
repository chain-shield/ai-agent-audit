# Vulnerability details


## Description

The `CuratorRewardsDistributor` contract is responsible for managing deposits and withdrawals for curator rewards. It interacts with the `PhiRewards` contract to distribute rewards to curators. The [`distribute()` function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/CuratorRewardsDistributor.sol#L77-L130) in `CuratorRewardsDistributor` is designed to distribute rewards to curators based on their shares. However, there is a flaw in the implementation that allows the caller of this function to receive funds that should go to the contract owner or be retained in the contract.

The issue lies in the following code snippet from the [`distribute()` function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/CuratorRewardsDistributor.sol#L77-L130):

```solidity
uint256 royaltyfee = (totalBalance * withdrawRoyalty) / RATIO_BASE;
uint256 distributeAmount = totalBalance - royaltyfee;

// ... calculation of individual amounts ...

balanceOf[credId] -= totalBalance;

_msgSender().safeTransferETH(royaltyfee + distributeAmount - actualDistributeAmount);

phiRewardsContract.depositBatch{ value: actualDistributeAmount }(
    distributeAddresses, amounts, reasons, "deposit from curator rewards distributor"
);
```

The function calculates a `royaltyfee` and a `distributeAmount`. It then distributes the `actualDistributeAmount` to curators. However, instead of sending the `royaltyfee` to the contract owner and keeping any rounding errors (difference between `distributeAmount` and `actualDistributeAmount`) in the contract, it sends both of these to the caller of the function (`_msgSender()`).

This allows the caller to receive funds that they should not be entitled to, potentially draining the contract of significant amounts over time.

## Impact

The impact of this is severe. It allows any caller of the [`distribute()` function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/reward/CuratorRewardsDistributor.sol#L77-L130) to steal funds from the contract in this way:
- The caller receives the `royaltyfee`, which should go to the contract owner or a designated treasury.


## Proof of Concept

Consider the following scenario:

1. A `credId` has a balance of 1000 ETH.
2. The `withdrawRoyalty` is set to 1% (100 in the contract's representation).
3. There are three curators with equal shares.

Step-by-step exploitation:

1. Attacker calls `distribute(credId)`.
2. Function calculates:
   - `royaltyfee` = 1000 * 100 / 10000 = 10 ETH
   - `distributeAmount` = 1000 - 10 = 990 ETH
3. Each curator receives 330 ETH (990 / 3, rounded down).

**Result:** The attacker has stolen 10 ETH that should have gone to the contract owner.

## Tools Used

Manual review

## Recommended Mitigation Steps

To fix this issue, modify the `distribute()` function to correctly handle the `royaltyfee`
