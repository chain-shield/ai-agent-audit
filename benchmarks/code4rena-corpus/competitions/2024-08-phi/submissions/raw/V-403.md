# Vulnerability details

## Vulnerability Details
In `Cred.sol` the following mapping:
```solidity
mapping(uint256 credId => EnumerableMap.AddressToUintMap balance) private shareBalance;
```
The mapping's length **can exceed** `MAX_SUPPLY = 999`. Because it does not call `.remove` when the shareholders sell out all their shares, this results in ALL past shareholders being included inside the "`set`" of the `EnumerableMap`, causing the length to be unbounded. 

For popular creds where trading and speculation of shares is common, the length of the mapping could easily reach **thousands or more**. This will cause a **permanent** DoS in rewards distribution as it relies on looping through it.

## Impact
The affected function is `distribute(uint256 credId)` in `CuratorRewardsDistributor.sol`.
```solidity

function distribute(uint256 credId) external {
    .....
@>  address[] memory distributeAddresses = credContract.getCuratorAddresses(credId, 0, 0);
    .....
}
```
The function relies on `getCuratorAddresses` which is a function in `Cred.sol`. `getCuratorAddresses` will then call `_getCuratorData`. By passing in `stop_` as 0, `_getCuratorData` will set `stopIndex = shareBalance[credId_].length();` and loop from 0 to `stopIndex`. (which is essentially the whole array)

Since the length is unbounded, if it becomes too big then there will be a permanent DOS to any attempt to distribute rewards. It is **permanent** because `shareBalance` is set to `private` so even though `EnumerableMap` has a `.remove` function, the owner/admin will still **not** be able to call it. Thus, the impact is **permanent** and rewards will be stuck forever.

(Sidenote: `CuratorRewardsDistributor.sol` also doesnt have a function where the owner can withdraw rewards, so the deposited rewards of that specific cred, will **literally** be stuck in the `CuratorRewardsDistributor` contract **forever**.)

## Recommended Mitigation Steps
Since all changes to share balances of a curator goes through `_updateCuratorShareBalance` in `Cred.sol`, we can use that as a bottleneck to remove any shareholder that sold out his entire position. This way, we can guarantee that the length will be bounded by `MAX_SUPPLY = 999`, which will prevent the **permanent** DoS
```diff
function _updateCuratorShareBalance(uint256 credId_, address sender_, uint256 amount_, bool isBuy) internal {
    (, uint256 currentNum) = shareBalance[credId_].tryGet(sender_);

    if (isBuy) {
        if (currentNum == 0 && !_credIdExistsPerAddress[sender_][credId_]) {
            _addCredIdPerAddress(credId_, sender_);
            _credIdExistsPerAddress[sender_][credId_] = true;
        }
        shareBalance[credId_].set(sender_, currentNum + amount_);
    } else {
        if ((currentNum - amount_) == 0) {
            _removeCredIdPerAddress(credId_, sender_);
            _credIdExistsPerAddress[sender_][credId_] = false;
+           shareBalance[credId_].remove(sender_);
+           return;
        }
        shareBalance[credId_].set(sender_, currentNum - amount_);
    }
}
```
