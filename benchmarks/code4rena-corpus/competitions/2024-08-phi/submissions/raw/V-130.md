# Vulnerability details

## Impact
The protocol suffers a loss of protocol fees on each cred creation. The attacker loses the 1 wei they need to pay for the transaction.

## Proof of Concept
A missing price limit check in the `createCred` function will cause a loss of protocol fees for the protocol as any user will be able to create a cred without paying the protocol fee.

The `createCred` function calls `buyShareCred(credIdCounter, 1, 0)` with a price limit of 0: https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L570
```solidity
buyShareCred(credIdCounter, 1, 0);
```
This will always revert the `buyShareCred` call due to the check in: https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/Cred.sol#L614-L615
```solidity
if (isBuy) {
    if (priceLimit != 0 && price + protocolFee + creatorFee > priceLimit) revert PriceExceedsLimit();
    // ...
}
```
Since `priceLimit` is set to 0, the condition `price + protocolFee + creatorFee > priceLimit` will always be true, causing the transaction to revert and preventing the protocol fee from being transferred.

It only take the `createCred` function to be called with any valid parameters.

**Attack Scenario**

* User calls `createCred` with valid parameters.
* The `createCred` function internally calls `buyShareCred(credIdCounter, 1, 0)`.
* The `buyShareCred` call reverts due to the price limit check, preventing the protocol fee transfer.
* The cred is still created successfully without the protocol receiving the fee.

## Tools Used
Manual review

## Recommended Mitigation Steps
Call `buyShareCred` with a sufficiently high `priceLimit` to allow the protocol fee transfer to succeed.
```diff
- buyShareCred(credIdCounter, 1, 0);
+ buyShareCred(credIdCounter, 1, type(uint256).max);
```
By setting the `priceLimit` to `type(uint256).max`, it ensures that the `buyShareCred` call will not revert due to the price limit check, allowing the protocol fee to be transferred successfully.
