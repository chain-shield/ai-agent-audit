# Vulnerability details

## Impact
Even when following CEI pattern, if an external call(sending of ether) is made to a malicious user of the flow and execute a re-entrancy attack. 
See detailed explanation on how this can happen in your function

If you send Ether to an address controlled by a malicious user (e.g during the refund process) before performing the action of sending `mintProtocolFee` to its destination. If the refund process is executed first the fallback funcion can immediately callback into the vulnerable function `signatureClaim` opening a window for re-entrancy.

Because the state have not fully been updated or some critical operation have not been made (sending `mintProtocolFee`), they can trigger unintended behaviour or cause the contract to malfunction.

## Proof of Concept
Here is a simplified sequence of how the attacker can execute the attack
Step 1: The attacker calls the `signaturClaim()` with crafted parameters
Step 2: The function sends a refund to the attackers address
Step 3: The attacker fallback's function is triggered during the refund transfer and immediately calls back into `signatureClaim()`
Step 4: The re-entrant call occurs before the original completion of the `signatureClaim()`(transfer of the minted protocol fee)
Step 5: The attacker can manipulate this state change to their advantage

If you send Ether to a malicious user before doing any other critical operations like sending Ether to a trusted entity to provide a chance for re-entrancy
