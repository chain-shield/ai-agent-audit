# Vulnerability details

## Summary
An attacker could exploit the lack of validation in the credData field of the createArt process to craft malicious data. This malicious `credData` could include fake `credId`, unauthorized `credCreator`, or tampered `merkleRootHash`, all of which would bypass the current minimal to no checks in the smart contract. By submitting this crafted credData, the attacker could create NFTs that appear to be legitimate but are fraudulent.

## Impact
Creation of fraudulent or counterfeit NFTs, loss of trust in the platform.

## Proof of Concept
Issue: The `_validateArtCreation` function does not sufficiently mitigate the risk of credData manipulation in `createERC1155Internal`. While it ensures the basic validity of the art creation process (e.g., preventing duplicate art pieces and checking time configurations), it does not address the more specific concerns related to the security and integrity of credData.
### Exploiting the credData Vulnerability:
**Step 1: Understanding the credData Field** 
The attacker uses the credData field is used to pass encoded data that contains important information such as credId, credCreator, verificationType, credChainId, and merkleRootHash.

**Step 2: Identifying the Lack of Validation**
- The attacker observes that while credData is decoded to extract values, there are no comprehensive checks to ensure that the values are legitimate.
- There's room for malicious manipulation of credId, credCreator, and merkleRootHash.

**Step 3: Crafting Malicious credData**
- The attacker crafts a malicious credData payload that will be accepted by the smart contract but contains false or misleading information (like Fake credId, unauthorized or impersonation a popular credCreator, Tampered merkleRootHash).
```solidity
bytes maliciousCredData = abi.encode(
    999,  // A fake credId that supposedly belongs to a famous artist
    attackerAddress,  // Attacker's address masquerading as the credCreator
    "MERKLE",  // Verification type that normally requires a valid merkle root
    1,  // credChainId that maps to a popular blockchain
    bytes32(0)  // Tampered merkleRootHash
);
```
**Step 4: Submitting the Malicious Transaction**
- The attacker submits a transaction to the smart contract that includes their malicious credData. Because of the lack of proper validation, the contract decodes and uses the attacker’s data, assigning it to the newly created NFT.

**Step 5: Exploiting the Created NFT**
- The attacker leverages the fraudulent NFT to gain an advantage or cause harm through Fraudulent Sales (attacker lists the NFT on a marketplace, misleading buyers into thinking they are purchasing a legitimate, high-profile NFT and then profits from the sale of a counterfeit item) or Undermining trust in protocol (if the fraud is detected).

## Tools Used
Manual review

## Recommended Mitigation Steps
Pre-Processing Checks before calling _initializePhiArt.
```solidity
function _validateCredData(bytes calldata credData) internal view {
    (
        uint256 credId,
        address credCreator,
        string memory verificationType,
        uint256 credChainId,
        bytes32 merkleRootHash
    ) = abi.decode(credData, (uint256, address, string, uint256, bytes32));
    
    // Check if credId already exists
    if (arts[credId].credId != 0) revert("Cred ID already exists");

    // Validate that the credCreator is authorized
    if (!isAuthorizedCreator(credCreator)) revert("Unauthorized creator");

    // Validate the verification type
    if (!isValidVerificationType(verificationType)) revert("Invalid verification type");

    // Ensure the merkle root is valid if required
    if (verificationType.eq("MERKLE") && merkleRootHash == bytes32(0)) {
        revert("Invalid Merkle Root");
    }
}

// This would be called before _initializePhiArt in the flow
_validateCredData(createData_.credData);
```
Incorporating the validation checks above ensures that by the time _initializePhiArt is called, the credData has been thoroughly vetted and is safe to use. This approach directly addresses the vulnerabilities related to unvalidated or poorly validated data.
