# Vulnerability details

in the `_executeBatchTrade` function of the `Cred` contract
The function doesn't check if the batch operation would exceed the `MAX_SUPPLY` for each credential. This could lead to a situation where the total supply of a credential exceeds the intended maximum, which goes against the design principles of the system.

1. In the documentation, it's mentioned that there's a `MAX_SUPPLY` constant set to 999:

   ```solidity
   uint16 private constant MAX_SUPPLY = 999;
   ```

2. For individual buy operations, there's a check to ensure the supply doesn't exceed this maximum:

   ```solidity
   if (supply + amount_ > MAX_SUPPLY) {
       revert MaxSupplyReached();
   }
   ```

3. but in the `_executeBatchTrade` function, this check is missing for buy operations. It only updates the supply without checking if it exceeds the maximum :

   ```solidity
   if (isBuy) {
       creds[credId].currentSupply += amount;
   } else {
       creds[credId].currentSupply -= amount;
   }
   ```

This oversight could allow a malicious user to bypass the `MAX_SUPPLY` limit by using batch operations, potentially minting more shares than intended for a credential. This could disrupt the economic model of the system and potentially lead to inflation of credential shares.




## PoC

The bug can be triggered through the `batchBuyShareCred` function, which ultimately calls `_executeBatchTrade`. Here's why it's possible:

1. The `batchBuyShareCred` function doesn't perform any supply checks.
2. The `_validateAndCalculateBatch` function, which is called before `_executeBatchTrade`, only checks if individual credential supplies would exceed `MAX_SUPPLY`, but doesn't account for the cumulative effect of the batch operation.


Proof of Concept (PoC) Flow:


1. Assume a popular credential (ID: 1) already has 990 shares minted.

2. An attacker prepares a batch buy operation:
   ```solidity
   uint256[] memory credIds = new uint256[](2);
   credIds[0] = 1;
   credIds[1] = 1;
   
   uint256[] memory amounts = new uint256[](2);
   amounts[0] = 5;
   amounts[1] = 5;
   
   uint256[] memory maxPrices = new uint256[](2);
   // Set appropriate max prices
   
   address curator = attacker;
   ```

3. The attacker calls `batchBuyShareCred(credIds, amounts, maxPrices, curator)`.

4. In `_validateAndCalculateBatch`, each individual buy of 5 shares passes the check as 990 + 5 < 999.

5. However, in `_executeBatchTrade`, both operations are executed:
   ```solidity
   creds[1].currentSupply += 5;  // Now 995
   creds[1].currentSupply += 5;  // Now 1000, exceeding MAX_SUPPLY
   ```

6. The credential now has 1000 shares, exceeding the MAX_SUPPLY of 999.

This PoC demonstrates how an attacker could exploit the vulnerability to mint more shares than the intended maximum


## mitigation 

To fix this vulnerability, a check should be added in the `_executeBatchTrade` function to ensure that the total supply after the batch operation doesn't exceed `MAX_SUPPLY` for each credential involved in the batch trade.


```solidity
uint256 newSupply = creds[credId].currentSupply;
if (isBuy) {
    newSupply += amount;
    if (newSupply > MAX_SUPPLY) revert MaxSupplyReached();
    creds[credId].currentSupply = newSupply;
} else {
    creds[credId].currentSupply -= amount;
}
```
