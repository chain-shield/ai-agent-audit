# Vulnerability details

## Detail of Vulnerability
The attack scenario involves an attacker front-running a buyer's transaction to buy a cred. The attacker exploits the lack of proper synchronization between the cred buying mechanism and the bonding curve to manipulate the price of the cred.

**Here's a step-by-step breakdown:**

- The buyer initiates a transaction to buy a cred at the current price.
- The attacker front-runs the buyer's transaction, buying the cred at the current price.
- The attacker's transaction is executed before the buyer's transaction, causing the price of the cred to increase.
- The buyer's transaction is executed at the new, higher price, resulting in the buyer paying more for the cred than they intended.

**Root Cause:**

There is lack of proper synchronization between the cred buying mechanism and the bonding curve. Specifically:

The cred buying mechanism uses the current price of the cred to determine the amount of funds to transfer from the buyer to the seller.
The bonding curve uses the current supply of the cred to determine the price of the cred.
But, the cred buying mechanism and the bonding curve are not properly synchronized, allowing an attacker to exploit the price difference between the two.
The vulnerability is caused by the fact that the cred buying mechanism does not account for the potential price increase caused by the attacker's front-running transaction. This lead to the buyer forced to pay the higher price for the cred, resulting in a loss of funds.


**The vulnerability is evident in the following:**

```solidity
uint256 currentSupply = cred.credInfo(credId).currentSupply;
uint256 buyAmount = 1;
uint256 price = bondingCurve.getBuyPriceAfterFee(credId, currentSupply, buyAmount);
```
The getBuyPriceAfterFee function is used to determine the price of the cred based on the current supply. But this function does not account for the potential price increase caused by an attacker's front-running transaction.

## Impact

- Unintended purchase price: When an attacker front-runs a user's buy transaction, the user is forced to buy the cred at a higher price than they intended. This can result in significant financial losses for the user, especially if the price difference is substantial.

- Loss of funds: In the worst-case scenario, the attacker can manipulate the price to such an extent that the user's funds are completely drained. For example, if the attacker front-runs a user's buy transaction with a much higher price, the user's transaction may fail due to insufficient funds, resulting in a loss of funds.

- Opportunity cost: Even if the user's funds are not directly stolen, the front-running attack can still result in an opportunity cost. The user may have missed out on a better price or a more favorable investment opportunity due to the attacker's manipulation.

function testFrontRunningBuy() public {
    uint256 credId = 1;
    bytes32 merkleRoot = 0xdc4c272ceaa7b5ba9e0f3f9972f735f14e1b4ed191e15d0d17afc62792226428;

    // now we will create the initial cred
    _createCred("ADVANCED", "MERKLE", merkleRoot);

    address buyer = makeAddr("buyer");
    address attacker = makeAddr("attacker");

    vm.warp(START_TIME + 1);
    vm.deal(buyer, 11_000 ether);
    vm.deal(attacker, 11_000 ether);

    // Let us set up the buy transaction
    uint256 currentSupply = cred.credInfo(credId).currentSupply;
    uint256 buyAmount = 1;
    uint256 price = bondingCurve.getBuyPriceAfterFee(credId, currentSupply, buyAmount);

    // attacker front-run the buy transaction
    vm.startPrank(attacker);
    cred.buyShareCred{ value: price }(credId, buyAmount, 0);
    vm.stopPrank();

    // user attempt to buy the cred
    vm.startPrank(buyer);
    uint256 newPrice = bondingCurve.getBuyPriceAfterFee(credId, currentSupply + buyAmount, buyAmount);
    try cred.buyShareCred{ value: newPrice }(credId, buyAmount, 0) {
        // The buyer should be able to buy the cred at the new price
        assertEq(cred.getShareNumber(credId, buyer), buyAmount);
    } catch Error(string memory reason) {
        revert("Buyer should be able to buy the cred at the new price");
    }
    vm.stopPrank();

    // Assert that the attacker was able to buy the cred
    assertEq(cred.getShareNumber(credId, attacker), buyAmount);
    assertEq(cred.credInfo(credId).currentSupply, currentSupply + buyAmount + buyAmount);
}

## Recommended Mitigation Steps
- Implement a front-running protection mechanism: Use a mechanism such as a "batcher" contract, which aggregates multiple buy transactions and executes them in a single transaction, preventing front-running attacks.
