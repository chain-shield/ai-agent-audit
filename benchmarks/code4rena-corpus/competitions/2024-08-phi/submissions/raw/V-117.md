# Vulnerability details


## Description

The `PhiFactory` contract implements a signature-based claiming mechanism for NFTs through the [`signatureClaim()` function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L327-L346). This function is designed to allow users to claim NFTs based on a valid signature from an authorized signer. However, the current implementation contains a critical vulnerability in its signature verification process.

The [`signatureClaim()` function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L327-L346) takes three parameters: `signature_`, `encodeData_`, and `mintArgs_`. It first decodes `encodeData_` to extract relevant information such as expiration time, minter address, and art ID. Then, it verifies the signature using the [`_recoverSigner()` function](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L579-L581).

The vulnerability lies in the way the `encodeData_` is hashed before being passed to `_recoverSigner()`:

```solidity
File: PhiFactory.sol
340:         if (_recoverSigner(keccak256(encodeData_), signature_) != phiSignerAddress) revert AddressNotSigned();

```

The `keccak256` hash of `encodeData_` is passed to `_recoverSigner()`, which then uses `ECDSA.toEthSignedMessageHash()` to prepend the Ethereum Signed Message prefix to the hash. This creates a mismatch between the data that was originally signed and the data being verified.

The `_recoverSigner()` function is implemented as follows:

```solidity
File: PhiFactory.sol
579:     function _recoverSigner(bytes32 hash_, bytes memory signature_) private view returns (address) {
580:         return ECDSA.recover(ECDSA.toEthSignedMessageHash(hash_), signature_);
581:     }

```

This implementation means that the contract is not verifying the signature against the original data that was signed, but rather against a hash of that data.

## Impact

This issue allows an attacker to mint unauthorized NFTs by bypassing the signature verification process. The attacker can create a different `encodeData_` with malicious parameters (e.g., different minter address, art ID, or quantity) that hashes to the same value as a valid `encodeData_`. By using this crafted `encodeData_` with a valid signature, the attacker can claim NFTs they shouldn't be able to.



## Proof of Concept

1. Alice obtains a valid signature for `encodeData_A` from the authorized signer. This `encodeData_A` contains parameters for Alice to mint 1 NFT of Art ID 1.

2. Bob (the attacker) intercepts this signature and `encodeData_A`.

3. Bob crafts a new `encodeData_B` with different parameters (e.g., Bob's address as minter, Art ID 2, quantity 10) such that `keccak256(encodeData_A) == keccak256(encodeData_B)`.

4. Bob calls `signatureClaim()` with Alice's signature and his crafted `encodeData_B`.

5. The contract hashes `encodeData_B`, which results in the same hash as `encodeData_A`.

6. The signature verification passes because the hashes match.

7. Bob successfully mints 10 NFTs of Art ID 2, which he was not authorized to do.

## Tools Used

Manual review

## Recommended Mitigation Steps

To fix this issue, the contract should verify the signature against the original `encodeData_` without applying an additional `keccak256` hash.
