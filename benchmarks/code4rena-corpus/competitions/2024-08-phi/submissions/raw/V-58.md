# Vulnerability details

In the [_validateAndUpdateClaimState](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L702-L721) function of the `PhiFactory` contract, the `art.numberMinted` value is incremented unconditionally, regardless of whether the token has already been minted by the `minter_` before. This will cause the total token supply to be inflated as a minter can mint duplicate tokens by calling the claim function multiple times for the same `artId`.

**Root Cause**
In PhiFactory.sol, the `_validateAndUpdateClaimState` function has a logic flaw in updating the `art.numberMinted` value: [PhiFactory.sol#L716-L720](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L716-L721)
```solidity
if (!credMinted[art.credChainId][art.credId][minter_]) {
    credMinted[art.credChainId][art.credId][minter_] = true;
}
artMinted[artId_][minter_] = true;
art.numberMinted += quantity_;
```
The `art.numberMinted` value is incremented unconditionally, regardless of whether the token has already been minted by the `minter_` before. This allows a minter to inflate the total token supply by calling the claim function multiple times for the same `artId`.

## Impact
The token supply can be inflated by minters, leading to an inaccurate representation of the total number of unique tokens minted. This can have implications for token scarcity, value, and overall integrity of the token system.

## Proof of Concept
The scenario that triggers this bug is when a `minter_` calls the `claim` function multiple times for the same `artId_`. The `artMinted` mapping correctly prevents the token from being minted again for the same `minter_`, but the `art.numberMinted` value is still incremented. This violates the expected behavior, which asserts that the number of minted tokens should increase only when a new token is actually minted.

**Internal pre-conditions:**

1. The `PhiFactory` contract is deployed with a valid `artId_` and corresponding art data.
2. The `minter_` has sufficient funds to pay the minting fee.

**Attack Path:**

* The `minter_` calls the [claim](https://github.com/code-423n4/2024-08-phi/blob/8c0985f7a10b231f916a51af5d506dd6b0c54120/src/PhiFactory.sol#L264-L269) function with a valid `encodeData_` for a specific `artId_`.
* The `_validateAndUpdateClaimState` function is called, marking the token as minted for the `minter_` and incrementing the `art.numberMinted` value.
* The `minter_` calls the claim function again with the same `encodeData_` for the same `artId_`.
* The `_validateAndUpdateClaimState` function is called again, and although the token is already marked as minted for the `minter_`, the `art.numberMinted` value is incremented again.
* The `minter_` can repeat _steps 3_ and _4_ multiple times, inflating the `art.numberMinted` value each time, even though no new unique tokens are actually minted.

## Recommended Mitigation Steps
The `art.numberMinted` value should be incremented only if the token is being minted for the first time by the `minter_`. This can be achieved by moving the increment statement inside the if block that checks `credMinted`
```diff
if (!credMinted[art.credChainId][art.credId][minter_]) {
    credMinted[art.credChainId][art.credId][minter_] = true;
+   art.numberMinted += quantity_;
}
artMinted[artId_][minter_] = true;
- art.numberMinted += quantity_;
```
By incrementing `art.numberMinted` only when `credMinted` is updated, it ensures that the total token supply accurately reflects the number of unique tokens minted, preventing inflation caused by duplicate minting.
