# Vulnerability details

## Summary

**Context:**
The function claimFromFactory() (called from the PhiFactory contract when signature/merkle claiming) in the PhiNFT1155.sol contract calls the internal mint() function. In this mint() function, the minterData[tokenId][to] and advancedTokenURI[tokenId][to] are updated to store the data and imageURI passed as parameters. We can view the [docs](https://docs.philand.xyz/explore-phi/case-study/advanced-art-case-gasfire), which shows an example advanced art case on why and how the advanced token uri would be used. 

**Issue:**
This issue is that the signatureClaim() and merkleClaim() functions do not verify that the msg.sender is the minter and also do not validate the imageURI supplied by including it in the `encodeData_`, which is verified by the phiSignerAddress's signature.

**Impact:**
Due to this, an attacker can mint/claim for a user again and set the advanced token uri and minter data to different values or even erase them. This could also be exploited by malicious users themselves by passing an imageURI that does not represent the image i.e. NFT they should receive. For example, for the GasFire advanced art case example in the docs, the URI can be updated by the user to a higher tier of fire, which could be sold on an external marketplace for a higher price. Similarly, an attacker could change the URI to a lower tier of fire, which would then be less worth.

Overall, the issue is of high-severity since the value and social representation of the asset is compromised and does not reflect what it should've been, especially on external marketplaces. 

## Proof of Concept

Note: I'm referring to the GasFire example from the docs linked above. Let's say there are 3 tiers of fire for simplicity, hot, warm and cold respectively. Each of them has their own imageURI with the hot being the highest tier (most gas spent) and cold being the lowest (least gas spent).

1. We assume the malicious user uses the flow mentioned [here](https://docs.philand.xyz/explore-phi/case-study/advanced-art-case-gasfire#overview) in the docs to mint the NFT. Let's say the user receives the warm gas fire NFT i.e. tier 2.

Here is the execution path during minting:

signatureClaim()/merkleClaim() => _processClaim() => claimFromFactory() => mint()

2. In the mint() function, the advancedTokenURI is set to imageURI of the warm gas fire NFT i.e. tier 2. On Line 303, we mint the ERC1155 token to the user.

3. The malicious user now reuses the signature that was provided last time to mint again using function signatureClaim() or simply calls merkleClaim() if they're eligible in the merkle tree to mint the tokens. 
 - As we can see below though in both functions, the `encodeData_` does not include the imageURI and is part of the `MintArgs mintArgs_` parameter.
 - Due to this, the malicious user can provide an imageURI of a higher tier i.e. hot gas fire NFT that does not reflect the advancedTokenURI they should be receiving. 
 - Similarly instead of a malicious user, an attacker can call these functions with the signature a user had received and used in a previous tx or simply merkle claim. Since the imageURI is part of the `mintArgs` parameter and is not validated either by the signature or merkle tree, an attacker can provide the imageURI of a lower tier i.e. cold gas fire NFT that does not reflect the advancedTokenURI the user should have.

## Tools Used
Manual Review

## Recommended Mitigation Steps
In the signatureClaim() and merkleClaim() functions, consider checking if the minter is the msg.sender as well as include the imageURI or better the mintArgs parameter as part of the `encodeData_` as well.
