# Vulnerability details

```solidity
function batchSellShareCred(
    uint256[] calldata credIds_,
    uint256[] calldata amounts_,
    uint256[] calldata minPrices_
)
    public
{
    (uint256 totalPayout, uint256[] memory prices, uint256[] memory protocolFees, uint256[] memory creatorFees) =
        _validateAndCalculateBatch(credIds_, amounts_, minPrices_, false);

    _executeBatchSell(credIds_, amounts_, prices, protocolFees, creatorFees);

    _msgSender().safeTransferETH(totalPayout);
}
```

in the `batchSellShareCred` function it does not check for the share lock period before executing the batch sell operation.

In the documentation, it's stated that:

```
If block.timestamp <= lastTradeTimestamp[credId][curator] + SHARE_LOCK_PERIOD) {
    revert ShareLockPeriodNotPassed(
        block.timestamp, lastTradeTimestamp[credId][curator] + SHARE_LOCK_PERIOD
    );
}
```

This check is implemented in the individual `sellShareCred` function but is missing in the `batchSellShareCred` function. This oversight could allow users to bypass the share lock period when selling shares in batch, which goes against the intended design of the system.

The impact of this vulnerability is significant because:

1. It breaks the consistency of the protocol's rules between individual and batch operations.
2. It could be exploited by users to sell shares before the lock period expires, potentially manipulating the market or gaining unfair advantages.
3. It undermines the purpose of the share lock period, which is likely designed to prevent rapid trading and maintain stability in the cred shares market.



## PoC


Proof of Concept (PoC) Flow:

1. User buys shares in multiple creds:
   ```solidity
   cred.batchBuyShareCred([1, 2, 3], [10, 10, 10], [maxPrice1, maxPrice2, maxPrice3], userAddress);
   ```

2. Immediately after buying (within the lock period), user sells these shares:
   ```solidity
   cred.batchSellShareCred([1, 2, 3], [10, 10, 10], [minPrice1, minPrice2, minPrice3]);
   ```

3. This sale succeeds, bypassing the lock period that would have been enforced in individual sales.

4. The user can repeat this process, potentially manipulating share prices and liquidity.

Example Scenario:
1. Lock period is set to 10 minutes.
2. At t=0, Alice buys 10 shares each of Creds 1, 2, and 3.
3. At t=1 minute, there's a favorable market movement.
4. Alice immediately sells all shares using `batchSellShareCred`.
5. This sale succeeds, although it should have been blocked for another 9 minutes.
6. Alice profits from rapid trading, contrary to the protocol's intended design.


# mitigation 

To fix this, the `batchSellShareCred` function should include a check for the share lock period for each cred ID in the batch before proceeding with the sell operation. This would ensure that the same rules apply to both individual and batch sell operations, maintaining the integrity and intended functionality of the protocol.
