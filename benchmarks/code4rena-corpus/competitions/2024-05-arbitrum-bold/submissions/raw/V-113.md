# Vulnerability details

## Impact
- Draining of funds: An attacker can repeatedly withdraw funds, leading to depletion of the contract's balance.
- State manipulation: Reentrancy attacks can disrupt the logical flow of the contract, allowing attackers to manipulate the contract’s state in unexpected ways.
- Integrity compromise: The integrity and reliability of the staking pool can be compromised, undermining user trust and the overall security of the staking mechanism.

## Proof of Concept
The reentrancy risk can be found in functions where external calls are made before the internal state is updated. An example from the `AssertionStakingPool.sol` contract:

```solidity
function withdraw(uint256 amount) external {
    require(stakes[msg.sender] >= amount, "Insufficient balance");
    (bool success, ) = msg.sender.call{value: amount}("");
    require(success, "Transfer failed");
    stakes[msg.sender] -= amount;
```

## Tools Used
Manual Code Review

## Recommended Mitigation Steps
- Update the contract to use the Checks-Effects-Interactions pattern to ensure the internal state is updated before making any external calls.
- Utilize the nonReentrant modifier from OpenZeppelin's ReentrancyGuard contract to prevent reentrant calls to the function.
