# Vulnerability details

## Impact
Detailed description of the impact of this finding.

## Proof of Concept
According to the audit FAQ, 
> **All trusted roles in the protocol**
    
> **`excessStakeReceiver` →** will be set to a DAO controlled address. Used to reimburse honest validators
    

No mention was made of any other trusted role apart from the **`excessStakeReceiver`** which is controlled by the DAO, hence I am assume other admin roles as non-trusted by the sponsors and this particular case described below puts users asset at direct risk.

In the current implementation, user’s can create an assertion using the  `AssertionStakingPool::createAssertion(...)` function, at a high level the order of execution is as shown below

```solidity
  L0 -> AssertionStakingPool::createAssertion(...)
> L1 --> IERC20(stakeToken).safeIncreaseAllowance(rollup, ...)
  L2 --> IRollupUser(rollup)::newStakeOnNewAssertion(...)
  L3 ---> RollupUserLogic::newStakeOnNewAssertion(...)
...
```

```solidity
File: AssertionStakingPool.sol
40:     function createAssertion(AssertionInputs calldata assertionInputs) external {
41:         uint256 requiredStake = assertionInputs.beforeStateData.configData.requiredStake;
42:         // approve spending from rollup for newStakeOnNewAssertion call
43:  @>     IERC20(stakeToken).safeIncreaseAllowance(rollup, requiredStake);
44:         // reverts if pool doesn't have enough stake and if assertion has already been asserted
45:         IRollupUser(rollup).newStakeOnNewAssertion(requiredStake, assertionInputs, assertionHash, address(this));
46:     }
```

As seen above on `L1` and `L43`, the user gives the `RollupUser` approval to spend up to the `requiredStake` amount. This allows the proxy admin to perform many actions, including taking funds from users' wallets up to the `requiredStake` and is normally not a problem because the allowance can only be used by the `RollupUser`, but in this instance it is a problem because the `RollupUser` is upgradable and because it’s admin is not a trusted role, the problem is that the `RollupUser` admin can upgrade to another malicious `RollupUser` and transfer an amount equivalent of the `requiredStake` from users who have created assertions in the past.

## POC Summary

- Validators Alice and Bob once created honest assertions giving the `RollupUser` which is an upgradable contract allowance to spend up to the `requiredStake` amount.
- A malicious `RollupUser` admin upgrades to a malicious `RollupUserAttacker` that has a `rugValidator(…)` function to steal funds from Alice and Bob as shown below
```solidity
function rugValidator(address validators, address rugReceiver)
    external
{   
    IERC20(stakeToken).safeTransferFrom(validators, rugReceiver, requiredStake);
}
```

## Recommended Mitigation Steps
Safely reduce the allowance to zero in the the AssertionStakingPool::createAssertion(...) function as shown below
```solidity
File: AssertionStakingPool.sol
40:     function createAssertion(AssertionInputs calldata assertionInputs) external {
41:         uint256 requiredStake = assertionInputs.beforeStateData.configData.requiredStake;
42:         // approve spending from rollup for newStakeOnNewAssertion call
43:  @>     IERC20(stakeToken).safeIncreaseAllowance(rollup, requiredStake);
44:         // reverts if pool doesn't have enough stake and if assertion has already been asserted
45:         IRollupUser(rollup).newStakeOnNewAssertion(requiredStake, assertionInputs, assertionHash, address(this));
     +      IERC20(stakeToken).safeDecreaseAllowance(rollup, 0);

46:     }
```
