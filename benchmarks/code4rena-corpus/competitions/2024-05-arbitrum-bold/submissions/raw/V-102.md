# Vulnerability details

## Impact
The improper use of `tx.origin` in the access control check can lead to unauthorized users being able to submit batch spending reports and receive refunds, compromising the integrity of the system.

## Proof of Concept

The `addSequencerL2BatchFromBlobsImpl` function in the contract uses `tx.origin` to verify the caller's authenticity before submitting batch spending reports. This approach can potentially allow unauthorized users to submit spending reports and receive refunds. By relying on `tx.origin` instead of `msg.sender`, the function fails to properly authenticate the current sender, creating a security loophole.
Similarly, the `addSequencerL2BatchFromOriginDelayProof` function is used to add a batch from the origin delay proof, which is a mechanism to delay the processing of batches. This function is called by the sequencer to add a batch to the inbox, and it checks if the caller is the origin (i.e., the original sender of the transaction) using `tx.origin`. In this case, an attacker could potentially add unauthorized batches to the inbox from the origin delay proof, which could lead to unintended consequences in the system.
### Consider the following scenario:
While `tx.origin` is useful for verifying the authenticity of a transaction, it can also be a security risk if used incorrectly. [One common mistake is to use `tx.origin` instead of `msg.sender` when implementing an access control system.](https://docs.soliditylang.org/en/develop/security-considerations.html#tx-origin)
```
// victim's contract
function transferEther() public {
    require(msg.sender == tx.origin, "Unauthorized access");
    // transfer ether code
}
```
In the example above, the function `transferEther` uses `tx.origin` to check if the sender is authorized to perform the transfer. However, this is incorrect because `tx.origin` **represents the original sender of the transaction, not the current sender. An attacker can take advantage of this by creating a malicious contract that calls the **transferEther function on behalf of the original sender.
```
contract Attacker {
    function attack() public {
        address victim = address(this);
        victim.call(bytes4(keccak256("transferEther()")));
    }
}

```
In the example above, the Attacker contract creates a transaction to call the `transferEther` function on the victim contract. Since the `tx.origin` is the address of the Attacker contract and not the original sender, the require **statement in the **transferEther function(in the victim's contract) will pass and the attacker will be able to successfully transfer ether from the victim contract.

- In the context of sequencerInbox contract, nn attacker deploys a malicious contract called Attacker with the intention of exploiting the vulnerability in the `addSequencerL2BatchFromBlobsImpl` function.
- The Attacker contract contains a function attack that initiates a transaction to call the `addSequencerL2BatchFromBlobsImpl` function in the target contract.
- Since the `addSequencerL2BatchFromBlobsImpl` function uses `tx.origin` for access control checks, the attacker's contract can pass the authentication check based on the original sender of the transaction.
- By leveraging the incorrect use of `tx.origin`, the Attacker contract successfully submits a batch spending report, triggering the execution of unauthorized actions within the system.
- The `addSequencerL2BatchFromBlobsImpl` function uses `tx.origin` to authenticate the caller before allowing the submission of batch spending reports. This flawed approach can enable unauthorized users to exploit the system by submitting spending reports and potentially receiving refunds. By relying on `tx.origin` instead of `msg.sender`, the function overlooks the current sender's identity verification, introducing a significant security risk.

## Recommended Mitigation Steps
To address this issue, it is recommended to replace the usage of `tx.origin` with `msg.sender` in the access control check. By using `msg.sender`, the function can accurately verify the current sender's identity and prevent unauthorized access.
[You should use msg.sender for authorization (if another contract calls your contract msg.sender will be the address of the contract and not the address of the user who called the contract).](https://docs.soliditylang.org/en/develop/security-considerations.html#tx-origin)
