# Vulnerability details

## Impact
This can lead to a situation whereby attackers effortlessly spam the system with false assertions because they are not penalised according to the system’s design, this breaks protocol design and functionality

## Proof of Concept
A malicious user can create false assertions without losing stake. The problem exists due to missing access control  in the `setBaseStake(...)` function in the `RollupAdminLogic` contract 

Most functions mentioned below are permissionless so the attacker can call them directly

- malicious user calls [`RollupAdminLogic::setBaseStake(...)`](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupAdminLogic.sol#L223-L226) to set the `baseStake` to  say 1 wei so that his parent assertion will have its `configData.requiredStake` set to 1 wei when [`AssertionNodeLib.createAssertion(...)`](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupCore.sol#L488-L497) is called. This is to ensure that when the attacker creates his own assertion, his call to `RollupUserLogic::stakeOnNewAssertion(...)` will pass this [user `amountStaked(...)`](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupUserLogic.sol#L182) check
- Honest stakers challenge the malicious assertion with an edge
- Challenge period ends but the attacker looses only 1 wei instead of a substantial amount of the `baseStake` set by arbitrum to penalise malicious behaviour in the system
- The attacker can continue doing this for a while unnoticed.

## Tools Used
Manual review

## Recommended Mitigation Steps
Apply access control to all functions of the `RollupAdminLogic` contract.
