# Vulnerability details

## Impact
In the [forceInclusion function](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/bridge/SequencerInbox.sol#L287-L353), the calculation of the `delayBlocks_` variable. The code checks if `isDelayBufferable` is true, and if so, it updates the `buffer` and calculates `delayBlocks_` using `delayBufferableBlocks(buffer.bufferBlocks)`. However, if `isDelayBufferable` is false, `delayBlocks_` is not assigned a value and retains its default value of 0.

This could lead to a bug where the check `l1BlockAndTime[0] + delayBlocks_ >= block.number` always passes if `isDelayBufferable` is false, allowing force inclusion of messages before the intended delay period has elapsed.

## Proof of Concept
The potential bug in the `forceInclusion` function could have a significant impact on the security and correctness of the system. The `forceInclusion` function is designed to allow the inclusion of delayed messages into the system after a certain delay period has elapsed. This delay period is intended to provide a window of time for potential challenges or disputes to be raised before the messages are finalized and included.

The bug occurs when the `isDelayBufferable` flag is set to false. In this case, the code fails to assign the correct value of delayBlocks to the `delayBlocks_` variable, leaving it with a default value of 0. This means that the check `l1BlockAndTime[0] + delayBlocks_ >= block.number` will always pass, regardless of the actual delay period that should be enforced. [SequencerInbox.sol#L306-L314](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/bridge/SequencerInbox.sol#L306-L314)

```solidity
uint256 delayBlocks_ = delayBlocks;

if (isDelayBufferable) {
    // proactively apply any pending delay buffer updates before the force included message l1BlockAndTime
    buffer.update(l1BlockAndTime[0]);
    delayBlocks_ = delayBufferableBlocks(buffer.bufferBlocks);
}
// If isDelayBufferable is false, delayBlocks_ remains 0

// ...

// Can only force-include after the Sequencer-only window has expired.
if (l1BlockAndTime[0] + delayBlocks_ >= block.number) revert ForceIncludeBlockTooSoon();
```
The impact of this bug is that it allows messages to be force-included immediately, bypassing the intended delay period. This could potentially lead to the inclusion of invalid or malicious messages without proper challenge or dispute resolution. It undermines the security mechanisms in place and could compromise the integrity of the system.

**To illustrate the concept, consider the following scenario:**

A delayed message is submitted to the system.
The `isDelayBufferable` flag is set to `false`.
The `forceInclusion` function is called immediately after the message submission.
Since `delayBlocks_` is 0, the check `l1BlockAndTime[0] + delayBlocks_ >= block.number` will always pass, allowing the message to be force-included immediately.

This violates the intended behavior of the system, which is to enforce a delay period before messages can be force-included. The delay period is crucial for allowing challenges or disputes to be raised and resolved before finalizing the messages.

## Recommended Mitigation Steps
Assign the correct value of `delayBlocks` to `delayBlocks_` when `isDelayBufferable` is false. For example:

```solidity
uint256 delayBlocks_ = delayBlocks;

if (isDelayBufferable) {
    // proactively apply any pending delay buffer updates before the force included message l1BlockAndTime
    buffer.update(l1BlockAndTime[0]);
    delayBlocks_ = delayBufferableBlocks(buffer.bufferBlocks);
} else {
    delayBlocks_ = delayBlocks;
}
```
This way, the correct delay period is enforced regardless of the value of `isDelayBufferable`.
