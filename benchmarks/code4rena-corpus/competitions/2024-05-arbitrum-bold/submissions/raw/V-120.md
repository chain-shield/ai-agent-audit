# Vulnerability details

## Description
As per the documentation, a group up people can use the contracts in `assertionStakingPool/` to crowd-fund the creation of assertions or edges. In case of creating an edge, `EdgeStakingPoolCreator.createPool()` can be called:
```javascript
contract EdgeStakingPoolCreator is IEdgeStakingPoolCreator {
    function createPool(
        address challengeManager,
        bytes32 edgeId
    ) external returns (IEdgeStakingPool) {
        EdgeStakingPool pool = new EdgeStakingPool{salt: 0}(challengeManager, edgeId);
        emit NewEdgeStakingPoolCreated(challengeManager, edgeId);
        return pool;
    }
```

The problem here is that the usage of the `create` opcode opens up a grieving attack.

## Proof of Concept
Consider the following:
- A malicious user, Bob, does not want Alice to create an rivalry edge against a an edge hat he made.
- Alice calls `createPool()` to create an `EdgeStakingPool`, she wants to use it to create an edge.
- Bob front-runs this call and changes the parameters `challengeManager` and `edgeId`
- This will result in the same address due to the nature of the `create` opcode.
- Now, if Alice would want to call `EdgeStakingPool.createEdge()` to create the `edge`, this would fail.
- Bob can keep doing this for his competition, since there is real incentive to do this(Bob winning).

## Tools used
Manual Review

## Recommendation
Consider usage of `CREATE2` while using `msg.sender` as a part of the `salt`.
