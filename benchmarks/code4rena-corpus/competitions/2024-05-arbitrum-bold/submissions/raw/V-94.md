# Vulnerability details

## Impact
Every time the RollupUserLogic tries to transfer the calling validator's assertion stake to the `loserStakeEscrow` from its holding balance and its holding balance is less than enough to make the transfer, the call would fail as it assumes it already has a hold of the `requiredStake` amounts by then.

## Proof of Concept
When making an assertion stake from the deployed `AssertionStakingPool`, the contract is expected to transfer at least the specified amount from the pool to the `RollupUserLogic` e.g 10 WETH, then it logs the user's stake, then it makes the `stakeOnNewAssertion` call and after takes the staking token from the calling validator via `safeTransferFrom` inside the `receiveTokens` function logic. Since the contract receives tokens at the last step of the call and after the `stakeOnNewAssertion` call, when the below condition becomes false that the assertion being made is not the first child, the call would fail and the tokens will not be transferred:

```solidity
if (!getAssertionStorage(newAssertionHash).isFirstChild) { // @audit
            // We assume assertion.beforeStateData is valid here as it will be validated in createNewAssertion
            // only 1 of the children can be confirmed and get their stake refunded
            // so we send the other children's stake to the loserStakeEscrow
            // NOTE: if the losing staker have staked more than requiredStake, the excess stake will be stuck
            IERC20(stakeToken).safeTransfer(loserStakeEscrow, assertion.beforeStateData.configData.requiredStake);
            // @audit they don't seem to have possession of the tokens they intend to move to the loserStakeEscrow address yet at this point so, if this rollup contract address holds less tokens or none at all than the required stake amount e.g less than 10 WETH, then the assertion will fail and the token move from assertion will revert.
        }
```

And since we are taking tokens from the user to cover the cost in that less frequent case, we should be making the `safeTransferFrom(msg.sender, address(this), tokenAmount)` call first before the `stakeOnNewAssertion` call.

## Recommended Mitigation Steps
```diff
function newStakeOnNewAssertion(
        uint256 tokenAmount,
        AssertionInputs calldata assertion,
        bytes32 expectedAssertionHash,
        address withdrawalAddress
    ) public {
        require(withdrawalAddress != address(0), "EMPTY_WITHDRAWAL_ADDRESS");
        _newStake(tokenAmount, withdrawalAddress);
+       receiveTokens(tokenAmount);
        stakeOnNewAssertion(assertion, expectedAssertionHash);
        /// @dev This is an external call, safe because it's at the end of the function
-       receiveTokens(tokenAmount);
    }
```
