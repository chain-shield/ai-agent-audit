# Vulnerability details

## Impact
The `getPool()` function is susceptible to front-running attacks, where an attacker can deploy a contract first, causing the user's transaction to fail.

## Proof of Concept
The [getPool()](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/assertionStakingPool/StakingPoolCreatorUtils.sol#L13-L21) computes the address of a `staking pool` contract using the `Create2` opcode.

```solidity
    function getPool(bytes memory creationCode, bytes memory args) internal view returns (address) {
        bytes32 bytecodeHash = keccak256(abi.encodePacked(creationCode, args));
        address pool = Create2.computeAddress(0, bytecodeHash, address(this));
        if (Address.isContract(pool)) {
            return pool;
        } else {
            revert PoolDoesntExist();
        }
    }
```
However, this can easily be front-run by a malicious actor to grief users.

1. An attacker can monitor transactions and preemptively deploy a contract with the same `creationCode` and `args` as the user.
2. The user's `getPool()` call fails, leading to transaction reversion, gas wastage, and denial of service.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Use a unique `salt` with `msg.sender` passed as argument for `Create2`.
