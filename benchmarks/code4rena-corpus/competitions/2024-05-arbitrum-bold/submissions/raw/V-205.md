# Vulnerability details

In the following lines: [SequencerInbox.sol#L147-L151](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/bridge/SequencerInbox.sol#L147-L151)

```solidity
if (hostChainIsArbitrum) {
    if (reader4844_ != IReader4844(address(0))) revert DataBlobsNotSupported();
} else {
    if (reader4844_ == IReader4844(address(0))) revert InitParamZero("Reader4844");

```
The condition for reverting with the `DataBlobsNotSupported` error seems to be inverted. According to the code comments and the variable name `reader4844_`, it appears that the intention is to allow a non-zero `reader4844_` instance when `hostChainIsArbitrum` is false (i.e., not on the Arbitrum chain).

However, the current code is doing the opposite: it reverts with `DataBlobsNotSupported` if `reader4844_` is not the zero address when `hostChainIsArbitrum` is true (on the Arbitrum chain).

## Impact
> Incorrect Revert Conditions on Arbitrum Chain

When `hostChainIsArbitrum` is true (i.e., the contract is deployed on the Arbitrum chain), the code is currently reverting with `DataBlobsNotSupported` if `reader4844_` is a non-zero address.
However, the intended behavior, as per the code comments and variable naming, seems to be that a non-zero `reader4844_` instance should be allowed on the Arbitrum chain.
This means that on the Arbitrum chain, the contract will revert and fail to initialize if a valid `reader4844_` instance is provided, which is likely not the desired behavior.

> Incorrect Revert Conditions on Non-Arbitrum Chains:

When `hostChainIsArbitrum` is false (i.e., the contract is deployed on a non-Arbitrum chain), the code is currently reverting with `InitParamZero("Reader4844")` if `reader4844_` is the zero address.
However, the intended behavior seems to be that a zero `reader4844_` instance should be allowed on non-Arbitrum chains.
This means that on non-Arbitrum chains, the contract will revert and fail to initialize if a zero `reader4844_` instance is provided, which is likely not the desired behavior.

If the bug is not fixed, it could potentially allow an attacker to provide an invalid or malicious `reader4844_` instance on non-Arbitrum chains, as the contract will not revert in such cases.
This could lead to unintended behavior or potential security vulnerabilities, as the contract may interact with an untrusted or compromised `reader4844`_ instance.

## Recommended Mitigation Steps
The conditions should be inverted

```solidity
if (hostChainIsArbitrum) {
    if (reader4844_ == IReader4844(address(0))) revert InitParamZero("Reader4844");
} else {
    if (reader4844_ != IReader4844(address(0))) revert DataBlobsNotSupported();
}
```
With this change, the code will revert with `InitParamZero` if `reader4844_` is the zero address on the Arbitrum chain, and it will revert with `DataBlobsNotSupported` if `reader4844_` is a non-zero address on a non-Arbitrum chain.
