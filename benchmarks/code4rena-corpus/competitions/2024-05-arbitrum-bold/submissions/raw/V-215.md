# Vulnerability details

## Impact
Validators can delay on-chain confirmation of assertions which breaks the protocol's main invariant.

## Proof of Concept
Validators can delay assertions for several days and then confirm it on the last day of validator afk period so that they don't lose the validator whitelist. This can be done in order to delay on-chain confirmation of assertions. This breaks the invariant:
```
Honest assertions / layer zero edges are always confirmed under the BoLD paper’s assumptions within 2 challenge periods.
plus the security council grace period for assertions
```
(See Additonal context: Main Invariants for reference: https://code4rena.com/audits/2024-05-arbitrum-bold)

If a validator delays validation till the last day of validation afk period, the delay period will be greater than the max allowed time which is 2 challenge periods + the security council grace period for assertions. 
For example, Total delay time = x days. Validator Afk period = 28 days. Challenge period = 6.4 days. Assuming the security grace period = 6.4 days (They can change this over time).
Delay time = validator afk period - (2 challenge periods + security council period). 
Delay time = 28 - (12.8 + 6.4)  =  28 - 19.2 = 8.8 days.
Therefore, validators can delay on-chain confirmation of assertions for 8.8 more days than the max time stated in the BoLD paper’s assumptions.

The following test can be added to Rollup.t.sol to demonstrate the described scenario.

    function testSuccessDelayConfirmUnchallengedAssertions() public returns (bytes32, AssertionState memory, uint64) {
        (bytes32 assertionHash, AssertionState memory state, uint64 inboxcount) = testSuccessCreateAssertion();
        // delaying the confirmation till 28 days after in blocks. after 28 days, the validator whitelist might be removed.
        bytes32 inboxAccs = userRollup.bridge().sequencerInboxAccs(0);
        vm.roll(userRollup.getAssertion(assertionHash).createdAtBlock + userRollup.VALIDATOR_AFK_BLOCKS());
        vm.prank(validator1);
        userRollup.confirmAssertion(
            assertionHash,
            genesisHash,
            firstState,
            bytes32(0),
            ConfigData({
                wasmModuleRoot: WASM_MODULE_ROOT,
                requiredStake: BASE_STAKE,
                challengeManager: address(challengeManager),
                confirmPeriodBlocks: CONFIRM_PERIOD_BLOCKS,
                nextInboxPosition: firstState.globalState.u64Vals[0]
            }),
            inboxAccs
        );
        return (assertionHash, state, inboxcount);
    }
