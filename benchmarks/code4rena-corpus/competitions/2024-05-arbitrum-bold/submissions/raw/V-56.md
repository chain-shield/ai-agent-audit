# Vulnerability details

## Impact
The `forceRefundStaker` function in the `RollupAdminLogic` contract calls the `requireInactiveStaker` function within a loop that iterates over an array of stakers. If the `requireInactiveStaker` function performs expensive operations or has a high gas cost, it could lead to a Denial-of-Service (DoS) condition when processing a large number of stakers. 

The potential Denial-of-Service vulnerability in the `forceRefundStaker` function can have the following impacts:

Gas exhaustion: If the `requireInactiveStaker` function is gas-intensive and the `staker` array contains a large number of elements, the loop may consume a significant amount of gas, potentially leading to an Out-of-Gas exception.

Contract unavailability: If the gas limit is reached during the execution of the `forceRefundStaker` function, the transaction will revert, making the contract temporarily unavailable for other users.

Disruption of contract functionality: An attacker can intentionally trigger the DoS condition by passing a large array of stakers, causing the contract to become unresponsive and preventing legitimate users from interacting with it.

## Proof of Concept
Creates an array of `staker` addresses with a large number of elements, for example, 10,000 addresses.

The attacker calls the `forceRefundStaker` function, passing the large array of stakers.

The function enters the loop and starts calling the `requireInactiveStaker` function for each staker address and  the loop will consume a significant amount of gas for each iteration.

As the loop progresses, the gas consumption increases, potentially leading to an Out-of-Gas exception or exceeding the block gas limit.

If the gas limit is reached, the transaction will revert, causing the contract to become temporarily unavailable for other users.

## Recommended Mitigation Steps
Implement pagination or batching mechanisms to process stakers in smaller chunks, reducing the gas consumption per transaction.

Consider setting a maximum limit on the number of stakers that can be processed in a single transaction to prevent excessive gas consumption.

Use a pull-based approach, where stakers initiate the refund process themselves, rather than relying on a centralized function to process all stakers at once.
