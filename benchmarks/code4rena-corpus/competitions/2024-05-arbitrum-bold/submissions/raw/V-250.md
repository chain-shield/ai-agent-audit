# Vulnerability details

## Impact
 In depositIntoPool function, the order of operations when updating the `depositBalance` and transferring tokens is a problem. The current implementation first updates the `depositBalance` of the sender, and then transfers the tokens from the sender to the contract: 
[/AbsBoldStakingPool.sol:34-35](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/assertionStakingPool/AbsBoldStakingPool.sol#L34-L35)
```solidity
depositBalance[msg.sender] += amount;
IERC20(stakeToken).safeTransferFrom(msg.sender, address(this), amount);
```
This order of operations can lead to a reentrancy vulnerability. If the `safeTransferFrom` function triggers an external call to a malicious contract, that contract could call back into the `depositIntoPool` function before the token transfer is completed, resulting in an inconsistent state where the `depositBalance` is updated without the corresponding token transfer.

## Proof of Concept
#### Vulnerability Explanation
The [depositIntoPool](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/assertionStakingPool/AbsBoldStakingPool.sol#L29-L38) function first updates the `depositBalance` of the caller (`msg.sender`) by adding the `amount` to it.
After updating the `depositBalance`, it calls the `safeTransferFrom` function of the ERC20 token contract to transfer the amount of tokens from the caller to the contract itself.
The `safeTransferFrom` function is an external call, which means that it can potentially trigger code execution in an external contract (in this case, the ERC20 token contract).

#### Reentrancy Attack Vector
Suppose an attacker has deployed a malicious ERC20 token contract that overrides the `safeTransferFrom` function.
In the malicious `safeTransferFrom` implementation, the attacker can include a call back to the `depositIntoPool` function of the staking pool contract before completing the token transfer.
When the staking pool contract calls `safeTransferFrom` on the malicious token contract, the malicious contract can initiate a reentrancy attack by calling `depositIntoPool` again.
During the reentrancy call, the `depositBalance` of the attacker will be updated again, even though the token transfer has not been completed yet.
This way, the attacker can repeatedly call `depositIntoPool` and increase their `depositBalance` without actually transferring any tokens to the contract.

## Recommended Mitigation Steps
Follow the "Checks-Effects-Interactions" pattern, where you first perform all the necessary checks, then update the state variables, and finally interact with external contracts or perform external calls.
```solidity
function depositIntoPool(uint256 amount) external {
    if (amount == 0) {
        revert ZeroAmount();
    }

    IERC20(stakeToken).safeTransferFrom(msg.sender, address(this), amount);

    depositBalance[msg.sender] += amount;
    emit StakeDeposited(msg.sender, amount);
}
```
By performing the token transfer first, and then updating the `depositBalance`, that way the state changes are consistent and atomic, preventing reentrancy attacks.

For the function [withdrawFromPool function](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/assertionStakingPool/AbsBoldStakingPool.sol#L50-L51)
