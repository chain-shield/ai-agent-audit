# Vulnerability details

## Description
In the `refundStake` function, tokens are transferred using the `safeTransfer` function from the OpenZeppelin library. However, the return value of this transfer is not checked. The `safeTransfer` function is designed to revert the transaction if the transfer fails due to reasons such as insufficient allowance or contract conditions. Without checking the return value, the function continues execution even if the transfer fails.

## Impact
- If the transfer fails due to reasons such as insufficient allowance or contract conditions, the function will not revert the transaction. This leaves the edge in a refunded state without actually transferring tokens, potentially leading to inconsistencies in the contract state.
- Users expecting their stake to be refunded may not receive their tokens, leading to confusion and frustration. It could erode trust in the contract and its functionality.

## Proof of Concept
- Step 1: Stake Tokens:
An attacker stakes a significant amount of tokens in the contract, increasing their stake balance.
- Step 2: Initiate Refund:
The attacker initiates a refund request, triggering the `refundStake` function.
- Step 3: Exploit Unchecked Transfer:
Before the token transfer is completed, the attacker quickly triggers a re-entry into the refundStake function.
During this re-entry, the attacker's balance in the contract is still considered to be the original amount, allowing them to request another refund.
- Step 4: Repeat and Drain:
The attacker continues to exploit the re-entry vulnerability, repeatedly requesting refunds before the token transfers are completed.
Each time the function is re-entered, the attacker's balance is not updated to reflect the pending transfer, allowing them to request additional refunds.
- Step 5: Drain Contract:
By exploiting the re-entry vulnerability multiple times, the attacker drains the contract's token balance by requesting refunds that are not backed by actual token transfers.
The contract's balance is depleted, and legitimate users who attempt to withdraw their stakes are unable to do so due to insufficient funds.

## Recommended Mitigation Steps
- Always check the return value of token transfers to ensure they complete successfully. If a transfer fails, revert the transaction to maintain consistency in the contract state.
- Consider implementing error handling mechanisms to inform users of failed transfers and provide instructions on how to resolve the issue. This improves user experience and reduces confusion in case of transaction failures.
- Additionally, implementing a withdrawal queue or cooldown period between refund requests can mitigate the impact of re-entry attacks and prevent rapid depletion of the contract's token balance.
