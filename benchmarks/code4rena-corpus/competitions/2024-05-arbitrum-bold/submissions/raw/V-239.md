# Vulnerability details

## Impact
A large number of honest validators could be slashed --> threaten the liveness of network by:
- Trick multiple honest validators to challenge an assertion (of which the validity depends on data fetched from an oracle).
- Slash honest validators by manipulating data fetched from malicious/compromised oracle when the dispute resolution is settled on L1 chain.

## Proof of Concept

In a nutshell, this is a risk due to the ability to build and use custom oracle on Arbitrum. An attacker who controls one or multiple custom oracles, contracts using those oracles deployed on Arbitrum, custom sequencer inbox contract on L1 main net, could have the ability to determine the final outcome of associated challenges.

Attack scenario 1:
- Set up a fake oracle service that filters data requests based on calling smart contracts' address to distinguish between Arbitrum honest validators and Ethereum L1 custom sequencer inbox contract. Then based on that to respond with: a, right data to honest validators (to trick them challenge malicious assertions) and  b, wrong data to L1 custom sequencer inbox contract (to confirm "wrong" assertions --> honest validators would be lost the challenge)
- Run a malicious validator (optional)
- Deploy a contract which uses data fetched from malicious/compromised oracle on Arbitrum BOLD chain.
- Send a transaction to the contract and trigger the function of which final result depends solely on data retrieved from malicious/compromised oracle.
- The malicious validator will execute that transaction (with wrong data), then post the wrong assertion to Arbitrum L1's contract. Maybe a normal validator could be used but it will complicate the set up of fake oracle service in step 1.
- Honest validators would be tricked to challenge then lost. 

Attack scenario 2:
- The malicious validator can also play the role of challenger to an honest validator's assertion.
- The flow of the attack is the same as above. The difference is that an attacker can gain some profit in addition to slashing an honest validator.

## Recommended Mitigation Steps
- Should have a whitelist of oracles to be used in dispute resolution process.
- All custom oracles should be vetted and approved before being used.
