# Vulnerability details

## Impact
Detailed description of the impact of this finding.
- Liveness: creating a large number of assertion branches --> triggering many dispute resolutions, exhausting resources of honest validators.
- Attacker might be able to confirm "wrong assertions" and steal bond from honest validators by winning unfair challenges.

## Proof of Concept
Provide direct links to all referenced code in GitHub. Add screenshots, logs, or any other relevant proof that illustrates the concept.

The root causes of potential chaos is the fact that a **rouge oracle can create data race condition within Arbitrum network**. There are at least two related attack scenarios:
1. Liveness attack:
- Alex (attacker) runs a rouge oracle (using OffChainScript.py) by himself, deploy oracle contract (using Oracle.sol) and oracle's data consumer contract (using PriceConsumer.sol) on Arbitrum BOLD network.
- Then, Alex sends multiple transactions to trigger PriceConsumer contract.
- The oracle is configured to update Oracle's price feed with new data quickly enough to cause a data race condition across Arbitrum network --> a large number of  conflicted assertion branches are created, for example: M assertion branches.
- **Due to the parallel nature of BOLD's dispute resolution**, if there are N validators engaging in dispute resolution, the total number of resolutions will be MxN. And because at most one assertion can be right, (N-1) honest validators temporally can't access to their mini-bond and large amount of gas using in dispute resolution --> **severe impact on liveness property of network**. 
2. Confirm "wrong assertion":
- This attack's only possible if BOLD is fully permission-less aka Arbitrum DAO won't retain the right to intervene in case of incorrect dispute resolution.
- Oracle deployed on Arbitrum chain return right data to honest assertion posters --> posters submit assertions created using right data.
- Alex runs a validator to challenge assertions from posters. He submits assertions created using "wrong" data (which is the "backupPrice" in PriceConsumer.sol)
- The challenge process will eventually reduce to one-step-verification which is very likely involved data fetched from rogue oracle. Since Alex controls rouge oracle, he can reply with the data which will help his assertion to be confirmed.An easy way is not deploying Oracle.sol on L1 main net --> "backupPrice" is used in one-step-verification -> Alex wins.
- Without intervention from Arbitrum DAO, Alex's "wrong assertions" is confirmed and he can be rewarded by winning unfairly.

PriceConsumer.sol

```
pragma solidity ^0.8.0;

import "./Oracle.sol";

contract PriceConsumer {

  Oracle public oracle;
  uint256 public backupPrice = 100;  // Initialize backup price to 100

  constructor(address _oracle) public {
    oracle = Oracle(_oracle);
  }

  function getLatestPrice() public view returns (uint256) {
    uint256 price;

    try this.oracle.getPrice() returns (uint256 _price) {
      price = _price;
    } catch Error(string memory reason) {
      // Handle oracle failure - use backup price
      price = backupPrice;
    }

    return price;
  }
}
```
