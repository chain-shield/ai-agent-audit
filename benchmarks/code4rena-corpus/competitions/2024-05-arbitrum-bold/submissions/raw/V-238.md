# Vulnerability details

## Impact
An attacker can gain an unfair advantage by front-running the confirmation process, potentially earning rewards meant for legitimate users.


## Proof of Concept
### Scenario:

Let's say we have a decentralized application (`dApp`) built on top of the `EdgeChallengeManager` contract. The dApp allows users to create and confirm edges, and rewards users with tokens for confirming edges quickly.

Attack Vector:

An attacker, let's call them "Alice," wants to gain an unfair advantage by front-running the confirmation process. Alice sets up a bot that listens to the blockchain for `EdgeConfirmedByTime` events emitted by the `EdgeChallengeManager` contract.

Here's how the attack unfolds:

- Legitimate User Submits Confirmation: A legitimate user, Bob, submits a confirmation for an edge using the `confirmEdgeByTime` function.
- Contract Emits `EdgeConfirmedByTime` Event: The `EdgeChallengeManager` contract emits an `EdgeConfirmedByTime` event, which is broadcast to the blockchain.
- Alice's Bot Detects Event: Alice's bot detects the `EdgeConfirmedByTime` event and quickly submits a confirmation for the same edge using the `confirmEdgeByTime` function, but with a higher gas price.
- Alice's Confirmation is Processed First: Due to the higher gas price, Alice's confirmation is processed by the network before Bob's confirmation. As a result, Alice's confirmation is accepted, and Bob's confirmation is rejected as a duplicate.
- Alice Gains Unfair Advantage: Alice receives the reward tokens for confirming the edge, while Bob's effort is wasted. Alice has successfully front-run the confirmation process and gained an unfair advantage.

Consequences:
The front-running attack allows Alice to:

- Gain an unfair advantage in the confirmation process
- Deny legitimate users (like Bob) the opportunity to earn rewards
- Potentially manipulate the edge confirmation process to their advantage

Implementing a fair queuing mechanism for confirmations
