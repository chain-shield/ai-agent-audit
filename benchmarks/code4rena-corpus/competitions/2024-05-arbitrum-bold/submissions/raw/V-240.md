# Vulnerability details

## Vulnerability Details
The issue is that the `_validatorWalletCreator` parameter is of type `address`, but it is being assigned directly to the `validatorWalletCreator` state variable, which is expected to be a contract address implementing a specific interface.

code: [RollupCreator.sol:L70/79](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupCreator.sol#L70-L79)
```solidity
address _validatorWalletCreator,
...
validatorWalletCreator = _validatorWalletCreator;
```
The problem with this approach is that it does not validate whether the provided `_validatorWalletCreator` address is actually a contract address implementing the required interface. If an arbitrary address is passed as `_validatorWalletCreator`, it could lead to unexpected behavior or failures when interacting with the `validatorWalletCreator` contract.

## Impact and Risks
**Violation of Contract Invariants:** The `validatorWalletCreator` state variable is expected to hold the address of a contract that implements a specific interface or set of functions. By assigning an arbitrary address to this variable, the contract's invariants are violated, and the contract may behave unexpectedly when interacting with the `validatorWalletCreator`.

**Potential for Unexpected Behavior:** If an arbitrary address is assigned to the `validatorWalletCreator`, any function calls or interactions with this address may fail or produce unexpected results. This is because the address may not implement the required functions or may not be a contract at all.

**Potential for Denial of Service (DoS):** If an Externally Owned Account (EOA) address is assigned to the `validatorWalletCreator`, any function calls or interactions with this address will revert, as EOAs cannot execute contract code. This could potentially lead to a Denial of Service (DoS) situation, where certain functionalities of the contract become unavailable.

**Potential for Reentrancy Attacks:** If the `validatorWalletCreator` address is assigned to an untrusted contract, it could potentially open the door for reentrancy attacks. Reentrancy attacks occur when an untrusted contract is able to recursively call functions in the original contract before the original function has completed its execution.

In this code, the `_validatorWalletCreator` parameter is of type address, which means that any address, whether a contract address or an EOA address, can be passed to this function. However, the `validatorWalletCreator` state variable is expected to hold the address of a contract implementing a specific interface or set of functions.

By assigning the `_validatorWalletCreator` parameter directly to the `validatorWalletCreator` state variable without any validation or type checking, the contract's invariants are violated, and the contract may behave unexpectedly when interacting with the `validatorWalletCreator`.

## Recommended Mitigation Steps
/ Define an interface for the `ValidatorWalletCreator` that defines the required functions and methods for the `ValidatorWalletCreator` contract. Then, instead of using the address type for the `_validatorWalletCreator` parameter, use the interface type. This way, the compiler can ensure that the provided address is a contract implementing the required interface.

/ Validate the `_validatorWalletCreator` address before assigning the `_validatorWalletCreator` address to the `validatorWalletCreator` state variable, you can validate that the provided address is a contract address and implements the required interface. We can use the `isContract` function from OpenZeppelin's Address utility library to check if the address is a contract, and then use the `supportsInterface` function to check if the contract implements the required interface.
