# Vulnerability details

## Impact
Downcasting nextInboxPosition from uint256 to uint64 will make the RollUpCore.createNewAssertion function unable to work for next InboxPosition messages hash due to the truncating messages hash above 2^64.

## Proof of Concept
RollUpUserLogic.StakeOnNewAssertion is responsible for creating new assertion claim by providing new expected hash, this function checks the provided hash if it is a duplicate or not than it checks if the user who provided the new assertion hash has some staked or not later on it calls the internal createNewAssertion function under RollUpCore to create new assertion.
RollUpCore.createNewAssertion after checking certain condition like if the machine status is finished and the provided assertion hash should not be zero, after which it creates a new variable nextInboxposition and this variable ensure that message processing is handled correctly.
lets proceed to the actual part where the state update occur and downcasting happens.
```
AssertionNode memory newAssertion = AssertionNodeLib.createAssertion(
            prevAssertion.firstChildBlock == 0, // assumes block 0 is impossible
            RollupLib.configHash({
                wasmModuleRoot: wasmModuleRoot,
                requiredStake: baseStake,
                challengeManager: address(challengeManager),
                confirmPeriodBlocks: confirmPeriodBlocks,
                nextInboxPosition: uint64(nextInboxPosition)
            })
        );
```
here, nextInboxPosition is downcasted from uint256 to uint64 i.e. any message exceeding (2^{64} - 1) will lose that could lead to incorrect tracking of positions, potentially causing the contract to skip messages or incorrectly calculate the next position to process.
Consider a situation to how this inbox message could be skipped.
User calls StakeOnNewAssertion function and gave a expectedAssertionHash.
StakeOnNewAssertion function call createNewAssertion internal function in RollUpCore contract.
Uint256 nextInboxPosition created after successfully passing all conditions.
next it creates a new variable called currentInboxPosition to store Inbox position at the time of this assertion being created by calling ``bridge.sequencerMessageCount()`` function that stores unit256 return value.
Now if the afterInboxPosition (which store the return value uint64 from getInboxPosition function) is == to currentInboxPosition it will add 1 to the currentInboxPosition and save it to nextInboxPosition, but if afterInboxPosition  is greater or lesser than currentInboxPosition it simply save currentInboxPosition to nextInboxPosition which could be greater than 2^64.
At last it saves nextInboxPosition of new assertion created data by calling RollupLib.configHash function and truncates the messages from uint256 to uint64.
```// The next assertion must consume all the messages that are currently found in the inbox
            uint256 afterInboxPosition = afterGS.getInboxPosition();//@note process uint64
            if (afterInboxPosition == currentInboxPosition) {
                // No new messages have been added to the inbox since the last assertion
                // In this case if we set the next inbox position to the current one we would be insisting that
                // the next assertion process no messages. So instead we increment the next inbox position to current
                // plus one, so that the next assertion will process exactly one message.
                // Thus, no assertion can be empty (except the genesis assertion, which is created
                // via a different codepath).
                nextInboxPosition = currentInboxPosition + 1;
            } else {
                nextInboxPosition = currentInboxPosition;
            }
```
When someone calls stakeOnNewAssertion function by providing expectedAssertionHash he will unable to proceed with createNewAssertion function due to the mismatch of Inbox message that truncates during the previous call as I have mentioned above.
