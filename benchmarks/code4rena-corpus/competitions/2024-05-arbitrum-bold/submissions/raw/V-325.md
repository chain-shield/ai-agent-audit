# Vulnerability details

## Impact
The Arbitrum BoLD technical deep dive specifies that:

[(link)](https://github.com/OffchainLabs/bold/blob/main/docs/research-specs/TechnicalDeepDive.pdf)
"The next assertion to be posted onchain must consume, at least, the specified number of inbox messages from its parent."

However, the implementation is reversing that, requiring a user to supply an inboxPosition that consumes at most the target inbox position specified by the previos assertion:

[createAssertion()](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/main/src/rollup/RollupCore.sol#L425C1-L427C66) in Rollup.sol
```js
    int256 afterStateCmpMaxInbox =
        afterGS.comparePositionsAgainstStartOfBatch(assertion.beforeStateData.configData.nextInboxPosition);
    require(afterStateCmpMaxInbox <= 0, "INBOX_TOO_FAR");
```

As a result, creating a new assertion takes an after state inbox position parameter that does not have a singular valid value, but has valid values in a specific range. That range is anywhere from the previos assertion's inbox position to the previos assertions's next inbox position. So, an assertion can consume any number of messages in that range and more than one valid assertion hashes can exist. This means that if more than one valid assertion is created, stake from the second honest validator assertion onwards will be sent to the loser escrow.

## Proof of Concept
Let's analyse how inbox positions are compared when creating assertions. There are several checks that are done to validate the candidate assertion.

The assertions before and after state as fetched as follow:

[link](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/main/src/rollup/RollupCore.sol#L406C101-L408C79)
```js
    GlobalState calldata afterGS = assertion.afterState.globalState;
    GlobalState calldata beforeGS = assertion.beforeState.globalState;
```

The beforeGS is the end state of the previos assertion. It consumes messages up to beforeGS.getInboxPosition().

First, there is a sanity check that the new inbox position is not before the previos inbox position:
[link](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/main/src/rollup/RollupCore.sol#L424C1-L424C81)
```js
    require(afterGS.comparePositions(beforeGS) >= 0, "INBOX_BACKWARDS");
```

This makes sense, however the next assertion is not in line with the arbitrum bold technical deep dive specification:

[createAssertion()](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/main/src/rollup/RollupCore.sol#L425C1-L427C66) in Rollup.sol
```js
    int256 afterStateCmpMaxInbox =
        afterGS.comparePositionsAgainstStartOfBatch(assertion.beforeStateData.configData.nextInboxPosition);
    require(afterStateCmpMaxInbox <= 0, "INBOX_TOO_FAR");
```

Here, the afterGS is required to consume at most the specified next inbox position. So a user can pass in an assertion that consumes an after state inbox position:

*before global state inbox position < afterGS.getInboxPosition() < specified next inbox position*

So, there can be multiple valid assertions that are children of the same previous assertion.
Example:

    there are 10 new messages in the sequencer inbox.

    User A: Creates an assertion with all 10 new messages.
    User B: Creates an assertion only covering the first 5 new messages.

    Both assertions are valid.

The assertion hash is taking the nextInboxPosition as input:

[(link)](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/main/src/rollup/RollupCore.sol#L450)
[(link2)](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/main/src/rollup/RollupCore.sol#L471)
```
        uint256 afterInboxPosition = afterGS.getInboxPosition();
        .
        .
        sequencerBatchAcc = bridge.sequencerInboxAccs(afterInboxPosition - 1);
    }

    newAssertionHash = RollupLib.assertionHash(prevAssertionHash, assertion.afterState, sequencerBatchAcc);
```

So, there will be a different assertion hash for each user supplied afterGS.getInboxPosition().

Furthermore, there is no check on the size of the assertion, meaning an assertion that covers more messages than the specified maximum of 2^26 can be created.

An attacker can take advantage of this by frontrunning a valid assertion being posted with another valid assertion. As a result the frontrun transaction will have the stake sent to the loserEscrow, since the protocol only allows 1 stake per rollup block to be present in the rollup contract.

## Tools Used
Manual Review

## Recommended Mitigation Steps
As the bold deep dive suggests, require that an assertion consumes the specified number of messages from it's parent. Only allow this to not be the case if the assertion consumes the maximum number of messages specified by bold: 2^26 and mark it as overflown.
