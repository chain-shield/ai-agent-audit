# Vulnerability details

## Impact
Detailed description of the impact of this finding.

Firstly, modifiers are missing from the following functions which makes them vulnerable. So, anybody can call these functions:
```sol
depositIntoPool(uint256 amount)
withdrawFromPool(uint256 amount)
withdrawFromPool()
```

The emit StakeWithdrawn should come before the IERC20(stakeToken).safeTransfer call to prevent re-entrancy. 

Here’s why:

**Re-entrancy Risk:**

If safeTransfer is called before updating the state and emitting the event, a re-entrant call could exploit this.
Re-entrancy occurs when an external call is made before the state is updated, allowing the external contract to call back into the contract and manipulate the state.

**Best Practice:**

Update state variables before making external calls.
Emit events after state changes but before external calls.

**Description:**

The `AbsBoldStakingPool` contract is vulnerable to a reentrancy attack due to the order of operations in the `withdrawFromPool` function. Specifically, the contract emits events (`StakeWithdrawn`) after transferring tokens to the user. This sequence allows a malicious actor to re-enter the contract before the state is updated, potentially leading to inconsistent states or double withdrawals.

**Details:**

1. **Function `withdrawFromPool(uint256 amount)` (Lines 29-54):**
   - The function first checks if the `amount` is zero and reverts if true.
   - It then verifies if the `amount` exceeds the caller's balance and reverts if true.
   - The contract updates the `depositBalance` of the caller.
   - **Vulnerability:** The contract transfers the `amount` to the caller before emitting the `StakeWithdrawn` event. This order of operations can be exploited by a reentrant call, allowing the attacker to call `withdrawFromPool` again before the state is fully updated.

**Impact:**

An attacker can exploit this vulnerability to withdraw more tokens than they have deposited, leading to potential loss of funds from the staking pool.

**Recommendation:**

To mitigate this vulnerability, the contract should follow the Checks-Effects-Interactions pattern. Specifically, the state should be updated before any external calls (such as token transfers) are made. Additionally, emitting events should occur after the state update and before external calls to ensure the contract's state remains consistent.

**Revised Code:**

```solidity
function withdrawFromPool(uint256 amount) public {
    if (amount == 0) {
        revert ZeroAmount();
    }
    uint256 balance = depositBalance[msg.sender];
    if (amount > balance) {
        revert AmountExceedsBalance(msg.sender, amount, balance);
    }

    depositBalance[msg.sender] = balance - amount;

    // Emit event after state update and before transfer
    emit StakeWithdrawn(msg.sender, amount);
    
    // Transfer tokens after state update
    IERC20(stakeToken).safeTransfer(msg.sender, amount);
    
}
```

By following this pattern, the contract ensures that its state is updated before any external interactions, thereby preventing reentrancy attacks.

## Recommended Mitigation Steps
### Recommendation to Resolve Reentrancy Events Vulnerability

**Issue:**
The `withdrawFromPool` function in the `AbsBoldStakingPool` contract is vulnerable to reentrancy attacks due to the order of operations. Specifically, the contract transfers tokens to the user before emitting the `StakeWithdrawn` event, which can be exploited by a reentrant call.

**Recommendation:**
Place emit before safeTransfer to mitigate re-entrancy risks.

**Revised Code:**
```solidity
function withdrawFromPool(uint256 amount) public {
    if (amount == 0) {
        revert ZeroAmount();
    }
    uint256 balance = depositBalance[msg.sender];
    if (amount > balance) {
        revert AmountExceedsBalance(msg.sender, amount, balance);
    }

    // Update state before external interaction
    depositBalance[msg.sender] = balance - amount;

    // Emit event after state update and before transfer
    emit StakeWithdrawn(msg.sender, amount);
    
    // Transfer tokens after state update
    IERC20(stakeToken).safeTransfer(msg.sender, amount);
    
}
```

**Steps to Implement:**
1. **Update State First:** Ensure that the `depositBalance` is updated before any external calls are made.
2. **Emit Events Next:** Emit the `StakeWithdrawn` event after the state update.
3. **Transfer Tokens Last:** Perform the token transfer after the state has been updated and event emitted.

By following these steps, the contract ensures that its state is updated before any external interactions, thereby preventing reentrancy attacks and maintaining the integrity of the contract's state.
