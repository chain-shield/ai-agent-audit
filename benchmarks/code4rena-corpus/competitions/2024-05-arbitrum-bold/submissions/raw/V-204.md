# Vulnerability details

## Impact
In the `calcBuffer` function, the calculation of the `unexpectedDelay` variable: https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/bridge/DelayBuffer.sol#L48-L51

```solidity
uint256 unexpectedDelay = delay > threshold ? delay - threshold : 0;
if (unexpectedDelay > elapsed) {
    unexpectedDelay = elapsed;
}
```
The problem is that the second condition `unexpectedDelay > elapsed` is not sufficient to handle all cases where `unexpectedDelay` should be capped at elapsed.

**Consider the following scenario**

`delay` is greater than `threshold`
`delay - threshold` is less than `elapsed`

In this case, `unexpectedDelay` will be set to `delay - threshold`, which is less than `elapsed`. However, the second condition `unexpectedDelay > elapsed` will not be true, and `unexpectedDelay` will not be capped at elapsed.

## Proof of Concept
The issue with the calculation of `unexpectedDelay` in the [calcBuffer function](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/bridge/DelayBuffer.sol#L33-L63) can lead to incorrect buffer values being computed, which can have significant implications for the delay buffer mechanism used in the SequencerInbox contract.

_The delay buffer is a crucial component of the Arbitrum protocol, designed to ensure that the sequencer cannot withhold or delay messages indefinitely. The buffer is replenished at a certain rate based on the elapsed time, but it is also depleted when the sequencer delays messages beyond a specified threshold._

`calcBuffer` function is responsible for calculating the updated buffer value based on various inputs, including the elapsed time, the delay in sequencing messages, the replenishment rate, and the maximum buffer size.

The issue arises when the delay in sequencing messages (`delay`) is greater than the sum of the elapsed time (`elapsed`) and the threshold (`threshold`). In this scenario, the `unexpectedDelay` should be capped at elapsed, but the current implementation fails to do so correctly.

**To illustrate the problem:**

**Suppose we have the following values:**

`start` = 100 (the starting block number)
`end` = 200 (the current block number)
`buffer` = 1000 (the initial buffer value)
`sequenced` = 300 (the block number where the messages were sequenced)
`threshold` = 100 (the delay threshold)
`max` = 2000 (the maximum buffer size)
`replenishRateInBasis` = 1000 (the replenishment rate in basis points)

In this case, the correct values should be:

`elapsed` = 200 - 100 = 100
`delay` = 300 - 100 = 200
`unexpectedDelay` should be capped at elapsed = 100

However, with the current implementation, the `unexpectedDelay` calculation will be:

```solidity
uint256 unexpectedDelay = delay > threshold ? delay - threshold : 0;
// unexpectedDelay = 200 - 100 = 100
if (unexpectedDelay > elapsed) {
    unexpectedDelay = elapsed;
}
// This condition is false because 100 is not greater than 100
// So unexpectedDelay remains 100
```
The correct calculation should be:
```solidity
uint256 unexpectedDelay = delay > threshold ? delay - threshold : 0;
// unexpectedDelay = 200 - 100 = 100
if (delay > elapsed + threshold) {
    unexpectedDelay = elapsed;
}
// This condition is true because 200 is greater than 100 + 100
// So unexpectedDelay is capped at 100
```
By not capping `unexpectedDelay` correctly, the buffer value will be calculated incorrectly, potentially leading to situations where the buffer is depleted more than it should be or replenished less than it should be.

This can have severe consequences for the protocol's security and correctness. If the buffer is depleted too much, the sequencer may be able to withhold or delay messages beyond the intended limits, violating the protocol's guarantees. Conversely, if the buffer is replenished too much, it may allow the sequencer to delay messages for longer periods than intended, potentially impacting the liveness of the system.

## Recommended Mitigation Steps
The second condition should be changed to check if `delay` is greater than `elapsed + threshold`, like this

```solidity
uint256 unexpectedDelay = delay > threshold ? delay - threshold : 0;
if (delay > elapsed + threshold) {
    unexpectedDelay = elapsed;
}
```
This way, `unexpectedDelay` will be correctly capped at `elapsed` whenever delay exceeds `elapsed + threshold`.
