# Vulnerability details

In [withdrawStakerFunds function](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupUserLogic.sol#L358-L364) the order of operations first calls `withdrawFunds(msg.sender)` to calculate the `amount` to be withdrawn, and then it checks if the amount is greater than zero using the `require` statement.

However, if the `withdrawFunds` function has any side effects or state changes, such as updating balances or performing other operations, these changes will be executed before the `require` check.

If the `withdrawFunds` function returns zero, and it has already made state changes, those changes will persist even though the transaction will revert due to the `require` statement failing.

## Impact
If the `withdrawFunds` function performs any state changes or external interactions before returning the withdrawal amount, those changes will be executed even if the `require` statement fails due to a zero withdrawal amount. _This violates the principle of atomicity, where a transaction should either succeed completely or revert without any side effects._

## Proof of Concept
Let's assume that the `withdrawFunds` function has the following implementation:

```solidity
function withdrawFunds(address account) internal returns (uint256) {
    uint256 amount = withdrawableBalances[account];
    withdrawableBalances[account] = 0; // State change: resetting the withdrawable balance
    return amount;
}
```
In this example, the `withdrawFunds` function resets the `withdrawableBalances` mapping for the given account before returning the withdrawal amount.

**Now, consider the following scenario:**

Alice calls `withdrawStakerFunds`.
The `withdrawFunds(msg.sender`) function is called, which retrieves Alice's withdrawable balance (**let's say it's 0**).

Before returning the withdrawal **amount (0)**, the `withdrawFunds` function resets Alice's withdrawable balance to 0 in the `withdrawableBalances` mapping.
The `require(amount > 0, "NO_FUNDS_TO_WITHDRAW")` statement is evaluated, and since amount is 0, the transaction reverts.
Despite the transaction reverting, the state change made by `withdrawFunds` (resetting Alice's withdrawable balance to 0) persists, even though Alice did not successfully withdraw any funds.

This unintended state change can lead to unexpected behavior and potential vulnerabilities, such as:

Alice's withdrawable balance is incorrectly reset to 0, even though she did not withdraw any funds.
If Alice tries to withdraw her funds again, the contract may behave unexpectedly or fail to recognize her remaining withdrawable balance.
An attacker could potentially exploit this behavior by repeatedly calling `withdrawStakerFunds` with a zero withdrawal amount, effectively draining Alice's withdrawable balance without actually receiving any funds.

## Recommended Mitigation Steps
It would be better to check the condition before calling `withdrawFunds` and making any state changes. This way, if the condition fails, the function can revert without modifying the contract's state.

```solidity
function withdrawStakerFunds() external override whenNotPaused returns (uint256) {
    uint256 amount = withdrawFunds(msg.sender);
    if (amount == 0) {
        return 0;
    }
    IERC20(stakeToken).safeTransfer(msg.sender, amount);
    return amount;
}
```
By checking the condition `amount == 0` before making any state changes or external calls, the function ensures that no unintended modifications occur if the withdrawal amount is zero.
