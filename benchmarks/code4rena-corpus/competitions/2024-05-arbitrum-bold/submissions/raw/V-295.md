# Vulnerability details


## Impact
Assertions that overflow and result in a MachineStatus.ERRORED state are not marked as overflown. This means that an honest party will not be able to submit a valid assertion for the duration of the minimumAssertionPeriod, while a malicios actor
would be able to do that if their assertion results in MachineStatus.FINISHED. This means that there will be a period in which only malicios actors can submit assertions. Also, since the honest actor must eventually be able to submit and prove their honest assertion their transactions to submit it will revert unexpectedly.

## Proof of Concept
The createNewAssertion() function in the RollupCore contract will set the overflowAssertion flag only if both the machineStatus of the assertion is does not result in ERRORED and the afterStateCmpMaxInbox is strictly less than 0.

[createNewAssertion()](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/main/src/rollup/RollupCore.sol#L429) in RollupCore.sol
```js
    if (assertion.afterState.machineStatus != MachineStatus.ERRORED && afterStateCmpMaxInbox < 0) {
        // If we didn't reach the target next inbox position, this is an overflow assertion.
        overflowAssertion = true;
        // This shouldn't be necessary, but might as well constrain the assertion to be non-empty
        require(afterGS.comparePositions(beforeGS) > 0, "OVERFLOW_STANDSTILL");
    }
```

However, a valid assertion that results in an ERRORED state can overflow. If this happens, then the transaction will also go through an additional check for the minimumAssertionPeriod:

[createNewAssertion()](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/main/src/rollup/RollupUserLogic.sol#L204) in RollupUserLogic.sol
```js
    if (!overflowAssertion) {
        uint256 timeSincePrev = block.number - getAssertionStorage(prevAssertion).createdAtBlock;
        // Verify that assertion meets the minimum Delta time requirement
        require(timeSincePrev >= minimumAssertionPeriod, "TIME_DELTA");
    }
```

As we can see, by design overflow assertions should not have the minimumAssertionPeriod check applied to them. However, if the overflown assertion results in an ERRORED state this check will be applied regardless.

## Recommended Mitigation Steps
Allow assertions that result in errored state to skip the minumumAssertionPeriod by only checking for `if(afterStateCmpMaxInbox < 0)`.
