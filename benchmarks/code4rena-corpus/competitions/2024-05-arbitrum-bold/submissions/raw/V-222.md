# Vulnerability details

## Impact
`isDelayProofRequired` function In the condition `afterDelayedMessagesRead > totalDelayedMessagesRead` assumes that `totalDelayedMessagesRead` is always less than or equal to the current number of delayed messages read. However, this assumption may not hold true in certain scenarios.

For example, if the `totalDelayedMessagesRead` value is reset or modified elsewhere in the code, it could become greater than the current number of delayed messages read (`afterDelayedMessagesRead`). In such cases, the condition `afterDelayedMessagesRead > totalDelayedMessagesRead` would evaluate to `false`, even though there might be new delayed messages that require a delay proof.

## Proof of Concept
The function is responsible for determining whether a delay proof is required when updating the delay buffer, which is a crucial component in the Arbitrum protocol: [src\bridge\SequencerInbox.sol:628-636](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/bridge/SequencerInbox.sol#L628-L635)
```solidity
    function isDelayProofRequired(uint256 afterDelayedMessagesRead) internal view returns (bool) {
        // if no new delayed messages are read, no buffer updates can be applied, so no proof required
        // if the buffer is synced, the buffer cannot be depleted, so no proof is required
        return
            isDelayBufferable &&
            afterDelayedMessagesRead > totalDelayedMessagesRead &&
            !buffer.isSynced();
    }
```
The delay buffer is used to ensure that transactions are not processed too quickly, allowing for potential challenges and disputes to be resolved before the transactions are finalized. If the `isDelayProofRequired` function fails to correctly identify when a delay proof is needed, it could lead to:

>: The function incorrectly determines that a delay proof is not required when there are new delayed messages, the delay buffer may be updated without the necessary proof. This could potentially allow an attacker to manipulate the buffer state, leading to transactions being processed prematurely or incorrectly.

>: Arbitrum protocol relies on a consensus mechanism to ensure that all nodes agree on the state of the system. If the delay buffer is not updated correctly, it could lead to different nodes having different views of the system state, violating the consensus and potentially causing the network to fork or become inconsistent.

Let's consider the following scenario:

Suppose the `totalDelayedMessagesRead` value is reset or modified elsewhere in the code, causing it to become greater than the current number of delayed messages read (`afterDelayedMessagesRead`). In this case, the condition `afterDelayedMessagesRead > totalDelayedMessagesRead` would evaluate to `false`, even though there might be new delayed messages that require a delay proof.

Here's how this could play out:
```solidity
// Assume totalDelayedMessagesRead is initially 100
uint256 totalDelayedMessagesRead = 100;

// Some other part of the code incorrectly modifies totalDelayedMessagesRead
totalDelayedMessagesRead = 200;

// New delayed messages are added, and afterDelayedMessagesRead becomes 150
uint256 afterDelayedMessagesRead = 150;

// isDelayProofRequired is called
bool isProofRequired = isDelayProofRequired(afterDelayedMessagesRead);
// isProofRequired will be false because 150 is not greater than 200

// The delay buffer is updated without the required proof
updateDelayBuffer();
```
Even though there are new delayed messages (150 instead of 100), the `isDelayProofRequired` function incorrectly determines that no delay proof is required because `afterDelayedMessagesRead` (150) is not greater than the modified `totalDelayedMessagesRead` (200). As a result, the delay buffer is updated without the necessary proof, potentially compromising the security and correctness of the system.

## Recommended Mitigation Steps
A safer approach would be to compare `afterDelayedMessagesRead` directly with the previous value of `totalDelayedMessagesRead`, rather than relying on the assumption that `totalDelayedMessagesRead` is always less than or equal to the current number of delayed messages read.
```solidity
uint256 prevTotalDelayedMessagesRead = totalDelayedMessagesRead;

function isDelayProofRequired(uint256 afterDelayedMessagesRead) internal view returns (bool) {
    // If no new delayed messages are read, no buffer updates can be applied, so no proof required
    // If the buffer is synced, the buffer cannot be depleted, so no proof is required
    return
        isDelayBufferable &&
        afterDelayedMessagesRead > prevTotalDelayedMessagesRead &&
        !buffer.isSynced();
}
```
In this we store the previous value of `totalDelayedMessagesRead` in a separate variable `prevTotalDelayedMessagesRead` before calling the `isDelayProofRequired` function. Then, within the function, we compare `afterDelayedMessagesRead` with `prevTotalDelayedMessagesRead` instead of `totalDelayedMessagesRead`.
