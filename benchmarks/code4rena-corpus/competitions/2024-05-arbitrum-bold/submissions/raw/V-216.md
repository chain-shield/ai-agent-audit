# Vulnerability details

## Impact
Detailed description of the impact of this finding.
### Vulnerability: Re-entrancy Event in the `refundStake` Function

**Description:**

The `refundStake` function in the `EdgeChallengeManager` contract is vulnerable to a re-entrancy attack due to the order of operations within the function. Specifically, the function emits the `EdgeRefunded` event after calling the `safeTransfer` method to transfer the stake token back to the staker. This sequence of operations can potentially allow a malicious actor to exploit the re-entrancy vulnerability and cause the refund to be incorrectly doubled.

**Details:**

- **Location:** Lines 572 to 585 in the `EdgeChallengeManager` contract.
- **Function:** `refundStake`
- **Issue:** The `safeTransfer` method is called before emitting the `EdgeRefunded` event. This allows a re-entrant call to `refundStake` to occur before the event is emitted, potentially leading to multiple refunds for the same edge.
- **Impact:** A malicious actor could exploit this vulnerability to receive multiple refunds for the same stake, leading to a loss of funds from the contract.

**Recommendation:**

To mitigate this vulnerability, the `EdgeRefunded` event should be emitted before calling the `safeTransfer` method. This ensures that the state change (emitting the event) occurs before any external call, preventing re-entrancy attacks.

**Revised Code:**

```solidity
function refundStake(bytes32 edgeId) public {
    ChallengeEdge storage edge = store.get(edgeId);
    // setting refunded also do checks that the edge cannot be refunded twice
    edge.setRefunded();

    IERC20 st = stakeToken;
    uint256 sa = stakeAmounts[edge.level];

    emit EdgeRefunded(edgeId, store.edges[edgeId].mutualId(), address(stakeToken), stakeAmounts[edge.level]);

    // no need to refund with the token or amount where zero'd out
    if (address(st) != address(0) && sa != 0) {
        st.safeTransfer(edge.staker, sa);
    }
}
```

By emitting the `EdgeRefunded` event before the `safeTransfer` call, the contract ensures that the state change is recorded before any external interaction, thus preventing re-entrancy attacks.

### Recommendation: Mitigating Re-entrancy Vulnerability in the `refundStake` Function

**Issue Summary:**

The `refundStake` function in the `EdgeChallengeManager` contract is vulnerable to a re-entrancy attack due to the order of operations. Specifically, the `safeTransfer` method is called before emitting the `EdgeRefunded` event, which can potentially allow a malicious actor to exploit the re-entrancy vulnerability and cause the refund to be incorrectly doubled.

**Recommendation:**

To mitigate this vulnerability, the `EdgeRefunded` event should be emitted before calling the `safeTransfer` method. This ensures that the state change (emitting the event) occurs before any external call, preventing re-entrancy attacks.

**Explanation:**

1. **Emit Event Before External Call:** By emitting the `EdgeRefunded` event before the `safeTransfer` call, the contract ensures that the state change is recorded before any external interaction. This prevents re-entrancy attacks by ensuring that the state is updated before any external call is made.

2. **State Change Before External Call:** Emitting the event before the external call further solidifies this protection by ensuring that the state change is visible before any potential re-entrant call.

3. **Preventing Re-entrancy:** This change ensures that even if a re-entrant call is attempted, the state will already reflect that the refund has been processed, preventing multiple refunds for the same edge.

By following this recommendation, the `refundStake` function will be more secure against re-entrancy attacks, ensuring the integrity of the refund process.
