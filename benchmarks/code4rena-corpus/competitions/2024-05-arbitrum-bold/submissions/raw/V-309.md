# Vulnerability details

Quoting the sponsor's [comment](https://discord.com/channels/810916927919620096/1235688998480117790/1242767495241142333) on the contest's public Discord channel
> Which token is the stakedToken?
gzeon | OffchainLabs: it is assumed to be WETH or a token that is not fee-on-transfer, rebasing, have a transfer hook or otherwise have non-standard ERC20 logics.

There are multiple instances in different contracts where `safeTransferFrom` is used to send the `stakeToken` from the user to the desired contract.

Given the fact that the staking token is WETH, the issue is valid.

## Proof of Concept
The `depositIntoPool()` is used to send the staking tokens from the user to the staking pool contract.

```solidity
File: AbsBoldStakingPool.sol
     
29:  function depositIntoPool(uint256 amount) external {
     ...
35:    IERC20(stakeToken).safeTransferFrom(msg.sender, address(this), amount);
```
This happens again in the EdgeChallengeManager contract inside the `createLayerZeroEdge` function.

```solidity
File: EdgeChallengeManager.sol

434:    st.safeTransferFrom(msg.sender, receiver, sa);
```
Also, inside RollupUserLogic contract inside the `receiveTokens` function.

```solidity
File: RollupUserLogic

366:         function receiveTokens(uint256 tokenAmount) private {
377:             IERC20(stakeToken).safeTransferFrom(msg.sender, address(this), tokenAmount);
388:         }
```
However, the transfer done using `IERC20(stakeToken).safeTransferFrom`. This works fine on most chains (Ethereum, Optimism, Polygon, BSC) which uses the standard WETH9 contract that handles the case  when `src == msg.sender`:

```solidity
File: WETH9.sol

        if (src != msg.sender && allowance[src][msg.sender] != uint(- 1)) {
            require(allowance[src][msg.sender] >= wad);
            allowance[src][msg.sender] -= wad;
        }
```
The problem is that the WETH implementation on [Arbitrum](https://arbiscan.io/address/0x8b194beae1d3e0788a1a35173978001acdfba668#code) , Blast, uses a different contract, and does not have this `src == msg.sender` handling.

Also, the issue is presented in Wrapped Arbitrum and Wrapped Fantom.

As a result, any attempt to execute this line of code with WETH as the deposit token on Arbitrum, Blast will fail with an "ERC20: transfer amount exceeds allowance" error, effectively breaking the deposit functionality when users attempt to deposit ETH.

Test:
Setup a foundry environment, get an Arbitrum RPC endpoint url and run the following command: `forge test --match-test testTransferFromIssue --fork-url {YOUR_RPC}`. This will revert with a `ERC20: transfer amount exceeds allowance` error, because of the issue described above.

    }

            .target(address(WETH))
            .sig(WETH.balanceOf.selector)
            .with_key(alice)

      vm.startPrank(alice);
