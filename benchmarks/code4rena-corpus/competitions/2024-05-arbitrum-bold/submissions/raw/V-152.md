# Vulnerability details

## Impact

Lack of input validation in assertion pool allows malicious user to create a clearly invalid insertion to make staker lose fund.

## Proof of Concept

anyone can create an assertion pool [with an assertion hash](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/assertionStakingPool/AssertionStakingPool.sol#L34)

```solidity
 constructor(
        address _rollup,
        bytes32 _assertionHash
    ) AbsBoldStakingPool(IRollupCore(_rollup).stakeToken()) {
        rollup = _rollup;
        assertionHash = _assertionHash;
    }
```

then after there are enough user stake fund, an assertion [can be created permissionlessly](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/assertionStakingPool/AssertionStakingPool.sol#L40)

```solidity
  function createAssertion(AssertionInputs calldata assertionInputs) external {
        uint256 requiredStake = assertionInputs.beforeStateData.configData.requiredStake;
        // approve spending from rollup for newStakeOnNewAssertion call
        IERC20(stakeToken).safeIncreaseAllowance(rollup, requiredStake);
        // reverts if pool doesn't have enough stake and if assertion has already been asserted
        IRollupUser(rollup).newStakeOnNewAssertion(requiredStake, assertionInputs, assertionHash, address(this));
    }
```

the problem is that while the assertion hash is set in the constructor, 

the function takes arbitrary assertion assertion input:

```solidity
struct AssertionInputs {
    // Additional data used to validate the before state
    BeforeStateData beforeStateData;
    AssertionState beforeState;
    AssertionState afterState;
}
```

there is lack of input validation

```solidity
struct BeforeStateData {
    // The assertion hash of the prev of the beforeState(prev)
    bytes32 prevPrevAssertionHash;
    // The sequencer inbox accumulator asserted by the beforeState(prev)
    bytes32 sequencerBatchAcc;
    // below are the components of config hash
    ConfigData configData;
}
```

and

```solidity
struct AssertionState {
    GlobalState globalState;
    MachineStatus machineStatus;
    bytes32 endHistoryRoot;
}
```

when calling the function newStakeOnNewAssertion, the function [did some input validation for before state](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupUserLogic.sol#L184),

```solidity
bytes32 prevAssertion = RollupLib.assertionHash(
    assertion.beforeStateData.prevPrevAssertionHash,
    assertion.beforeState,
    assertion.beforeStateData.sequencerBatchAcc
);
getAssertionStorage(prevAssertion).requireExists();

// Staker can create new assertion only if
// a) its last staked assertion is the prev; or
// b) its last staked assertion have a child
bytes32 lastAssertion = latestStakedAssertion(msg.sender);
require(
    lastAssertion == prevAssertion || getAssertionStorage(lastAssertion).firstChildBlock > 0,
    "STAKED_ON_ANOTHER_BRANCH"
);
```

[more input validation](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupCore.sol#L371) beforeState in function createNewAssertion

but there is [insufficient validation](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupCore.sol#L378) on the parameter afterState

```solidity
struct AssertionState {
    GlobalState globalState;
    MachineStatus machineStatus;
    bytes32 endHistoryRoot;
}
```

a user can input clearly invalid endHistoryRoot or incorrect assertion.afterState.machineStatus to make sure the assertion cannot be confirmed and thus make the staker lose fund.

## Tools Used

Manual Review

## Recommended Mitigation Steps

I think the function createAssertion needs access control, only the assertion pool creator can create assertion 

or when the assertion pool is deployed, the assertion input needs to be set and not modified 

so the staker can do their only research when put fund in the staking pool to avoid the case when the staker stakes for a valid assertion hash but lose fund to input assertion inpput.
