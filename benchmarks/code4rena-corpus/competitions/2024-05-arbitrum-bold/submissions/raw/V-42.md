# Vulnerability details

## Impact
The `RollupAdminLogic` contract, which serves as the implementation contract behind the `RollupProxy`, is vulnerable to unauthorized access due to an improper proxy setup. The `RollupProxy` contract, which is intended to delegate calls to the implementation contract, lacks the necessary access control mechanisms to restrict access to critical functions in the `RollupAdminLogic` contract.

The root cause of this vulnerability lies in the incorrect implementation of the proxy contract. The `RollupProxy` contract inherits from the `TransparentUpgradeableProxy` contract, which is a standard proxy contract provided by the OpenZeppelin library. However, the proxy contract does not include any additional access control checks or modifiers to restrict access to the functions in the implementation contract.

As a result, any user can directly call the functions in the `RollupAdminLogic` contract through the proxy contract, regardless of whether they are the proxy admin or not. This includes critical functions such as `setValidator`, `setOwner`, `setMinimumAssertionPeriod`, `setConfirmPeriodBlocks`, and `setBaseStake`, which should only be accessible to authorized entities.

The improper proxy setup and lack of access control in the `RollupAdminLogic` contract can have severe consequences:

Unauthorized modification of critical contract parameters:

Attackers can exploit the lack of access control to call functions like `setValidator`, `setMinimumAssertionPeriod`, `setConfirmPeriodBlocks`, and `setBaseStake` and modify critical contract parameters without proper authorization.
This can lead to unintended changes in the contract's behavior, such as altering validation rules, modifying assertion periods, or changing the base stake amount, which can disrupt the normal operation of the contract.

Unauthorized ownership transfer:

An attacker can call the `setOwner` function through the proxy contract to gain unauthorized control over the `RollupAdminLogic` contract by setting themselves or another malicious address as the new owner.
This grants the attacker full control over the contract, allowing them to perform privileged actions, modify contract logic, or even steal funds (if applicable).

Bypassing intended access control:

The improper proxy setup effectively bypasses any intended access control mechanisms implemented in the `RollupAdminLogic` contract.
Even if the implementation contract has modifiers or checks to restrict access to certain functions, attackers can still directly call those functions through the proxy contract, rendering the access control ineffective.

Compromised contract integrity and security:

The ability for unauthorized users to modify critical contract parameters and gain control over the contract severely compromises its integrity and security.
Attackers can exploit this vulnerability to manipulate the contract's behavior, introduce malicious logic, or disrupt its normal functioning, leading to potential financial losses or reputational damage.

## Proof of Concept
An attacker can directly call the critical functions in the `RollupAdminLogic` contract through the `RollupProxy` contract.

The attacker can deploy their malicious contract, passing the address of the `RollupProxy` contract. They can then call the `attackSetOwner` function, providing their own address or any other malicious address as the `_newOwner` parameter. Since the proxy contract lacks access control, the call will be delegated to the `RollupAdminLogic` contract, and the ownership will be transferred to the attacker's specified address.

## Recommended Mitigation Steps
Properly implement access control mechanisms in both the proxy contract and the implementation contract.

Modify the `RollupProxy` contract to include access control modifiers that restrict access to critical functions based on the caller's role or permissions.

Implement access control modifiers in the `RollupAdminLogic` contract to ensure that only authorized entities can execute critical functions.
