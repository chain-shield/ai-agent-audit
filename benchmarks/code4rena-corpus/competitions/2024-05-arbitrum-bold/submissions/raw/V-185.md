# Vulnerability details

The [confirmAssertion function](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupUserLogic.sol#L82-L131) where the challenge grace period is only enforced when the previous assertion has more than one child. This could allow an attacker to potentially confirm an assertion prematurely by creating a challenge edge with a sufficiently early confirmedAtBlock value.

<details>
<summary>The [confirmAssertion function]</summary>
<br>

```solidity
    function confirmAssertion(
        bytes32 assertionHash,
        bytes32 prevAssertionHash,
        AssertionState calldata confirmState,
        bytes32 winningEdgeId,
        ConfigData calldata prevConfig,
        bytes32 inboxAcc
    ) external onlyValidator whenNotPaused {
        /*
        * To confirm an assertion, the following must be true:
        * 1. The assertion must be pending
        * 2. The assertion's deadline must have passed
        * 3. The assertion's prev must be latest confirmed
        * 4. The assertion's prev's child confirm deadline must have passed
        * 5. If the assertion's prev has more than 1 child, the assertion must be the winner of the challenge
        *
        * Note that we do not need to ever reject invalid assertion because they can never confirm
        *      and the stake on them is swept to the loserStakeEscrow as soon as the leaf is created
        */


        // The assertion's must exists and be pending and will be validated in RollupCore.confirmAssertionInternal
        AssertionNode storage assertion = getAssertionStorage(assertionHash);


        // prevAssertionHash is user supplied, but will be validated in RollupCore.confirmAssertionInternal
        AssertionNode storage prevAssertion = getAssertionStorage(prevAssertionHash);
        RollupLib.validateConfigHash(prevConfig, prevAssertion.configHash);


        // Check that deadline has passed
        require(block.number >= assertion.createdAtBlock + prevConfig.confirmPeriodBlocks, "BEFORE_DEADLINE");


        // Check that prev is latest confirmed
        require(prevAssertionHash == latestConfirmed(), "PREV_NOT_LATEST_CONFIRMED");


        if (prevAssertion.secondChildBlock > 0) {
            // if the prev has more than 1 child, check if this assertion is the challenge winner
            ChallengeEdge memory winningEdge = IEdgeChallengeManager(prevConfig.challengeManager).getEdge(winningEdgeId);
            require(winningEdge.claimId == assertionHash, "NOT_WINNER");
            require(winningEdge.status == EdgeStatus.Confirmed, "EDGE_NOT_CONFIRMED");
            require(winningEdge.confirmedAtBlock != 0, "ZERO_CONFIRMED_AT_BLOCK");
            // an additional number of blocks is added to ensure that the result of the challenge is widely
            // observable before it causes an assertion to be confirmed. After a winning edge is found, it will
            // always be challengeGracePeriodBlocks before an assertion can be confirmed
            require(
                block.number >= winningEdge.confirmedAtBlock + challengeGracePeriodBlocks,
                "CHALLENGE_GRACE_PERIOD_NOT_PASSED"
            );
        }


        confirmAssertionInternal(assertionHash, prevAssertionHash, confirmState, inboxAcc);
    }
```
</details>

The issue is related to the check for the challenge grace period:

 [#L125-L126](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupUserLogic.sol#L125-L127)
```solidity
require(
    block.number >= winningEdge.confirmedAtBlock + challengeGracePeriodBlocks,
    "CHALLENGE_GRACE_PERIOD_NOT_PASSED"
);
```
This check is performed only when `prevAssertion.secondChildBlock > 0`, which means that it is executed when the previous assertion has more than one child. However, the challenge grace period should be enforced for all assertions, regardless of whether the previous assertion has multiple children or not.

If the previous assertion has only one child, the code will skip this check, potentially allowing an assertion to be confirmed before the challenge grace period has elapsed. This could lead to a situation where an assertion is confirmed prematurely, potentially violating the protocol's rules or allowing for malicious behavior.

## Impact
The challenge grace period is a predetermined number of blocks that must elapse after a winning edge in a challenge is confirmed before the corresponding assertion can be confirmed. This grace period ensures that the result of the challenge is widely observable and gives participants enough time to verify and potentially challenge the outcome if necessary.

## Proof of Concept
The issue arises when the previous assertion has only one child. In this case, the code skips the check for the challenge grace period, as shown in the following code snippet: [#L115-L127](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupUserLogic.sol#L115-L128)

By skipping the check for the challenge grace period when the previous assertion has only one child, the protocol potentially allows assertions to be confirmed prematurely, before the required grace period has elapsed. This could lead to several issues:

<details>
<summary>Violation of Protocol Rules:</summary>
<br>

The protocol's rules dictate that the challenge grace period must be enforced for all assertions, regardless of whether the previous assertion has multiple children or not. Skipping this check violates the protocol's intended behavior and could lead to inconsistencies or unexpected outcomes.
</details>

<details>
<summary>Reduced Observability:</summary>
<br>

The challenge grace period is designed to ensure that the result of a challenge is widely observable before an assertion is confirmed. By allowing assertions to be confirmed prematurely, participants may not have sufficient time to verify and potentially challenge the outcome, reducing the transparency and accountability of the protocol.
</details>

<details>
<summary>Potential for Malicious Behavior:</summary>
<br>

If assertions can be confirmed before the grace period elapses, it could create opportunities for malicious actors to exploit this vulnerability. For example, an attacker could attempt to confirm an invalid assertion before others have a chance to challenge it, potentially leading to consensus issues or other undesirable consequences.
</details>

Consider the following scenario:

An assertion `A` is created, and a challenge is initiated against it.
The challenge results in a single winning edge, confirming assertion `B` as the correct assertion.
According to the protocol rules, there should be a challenge grace period (e.g., 100 blocks) before assertion B can be confirmed, allowing participants to verify and potentially challenge the outcome.
However, due to the bug in the `confirmAssertion` function, assertion `B` can be confirmed immediately after the winning edge is confirmed, without waiting for the grace period to elapse.
This premature confirmation could lead to consensus issues, as participants may not have had sufficient time to verify and potentially challenge the outcome of the challenge.

## Recommended Mitigation Steps
The check for the challenge grace period should be moved outside the `if` statement that checks for multiple children. This way, the grace period will be enforced for all assertions, ensuring that the required time has passed before confirming any assertion.

```solidity
// Check that deadline has passed
require(block.number >= assertion.createdAtBlock + prevConfig.confirmPeriodBlocks, "BEFORE_DEADLINE");

// Check that prev is latest confirmed
require(prevAssertionHash == latestConfirmed(), "PREV_NOT_LATEST_CONFIRMED");

// Enforce the challenge grace period for all assertions
ChallengeEdge memory winningEdge = IEdgeChallengeManager(prevConfig.challengeManager).getEdge(winningEdgeId);
require(winningEdge.confirmedAtBlock != 0, "ZERO_CONFIRMED_AT_BLOCK");
require(
    block.number >= winningEdge.confirmedAtBlock + challengeGracePeriodBlocks,
    "CHALLENGE_GRACE_PERIOD_NOT_PASSED"
);

if (prevAssertion.secondChildBlock > 0) {
    // if the prev has more than 1 child, check if this assertion is the challenge winner
    require(winningEdge.claimId == assertionHash, "NOT_WINNER");
    require(winningEdge.status == EdgeStatus.Confirmed, "EDGE_NOT_CONFIRMED");
}

confirmAssertionInternal(assertionHash, prevAssertionHash, confirmState, inboxAcc);
```
By making this change, the challenge grace period will be enforced for all assertions, ensuring that the protocol's rules are followed and reducing the risk of potential vulnerabilities or malicious behavior.
