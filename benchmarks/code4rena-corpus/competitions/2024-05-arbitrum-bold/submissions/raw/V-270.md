# Vulnerability details



## Impact
In the `AssertionStakingPool.sol`, people can stake their tokens in the pool to create an assertion on the rollup contract. However due to the nature of this contract, anyone can use the pooled user funds to make any assertion. Potentially causing loss of funds to all stakers if a wrong assertion is passed to the rollup contract.


## Proof of Concept
The `AssertionStakingPool::createAssertion` function is a permissionless function as seen below:

```solidity
    function createAssertion(AssertionInputs calldata assertionInputs) external {
        uint256 requiredStake = assertionInputs.beforeStateData.configData.requiredStake;
        // approve spending from rollup for newStakeOnNewAssertion call
        IERC20(stakeToken).safeIncreaseAllowance(rollup, requiredStake);
        // reverts if pool doesn't have enough stake and if assertion has already been asserted
        IRollupUser(rollup).newStakeOnNewAssertion(requiredStake, assertionInputs, assertionHash, address(this));
    }
```
In the rollup contract,`RollupCore::createNewAssertion` which is called internally from `newStakeOnNewAssertion` when creating a new assertion, verification of the `assertionHash` is skipped if `assertionHash == bytes32(0)`:
```solidity
 
        require(
            newAssertionHash == expectedAssertionHash || expectedAssertionHash == bytes32(0),
            "UNEXPECTED_ASSERTION_HASH"
        );

``` 
This allows a malicious user to cause all stakers in a pool to loose funds staked.


## Tools Used

Manual Review, Josephdara

## Recommended Mitigation Steps

During creation of pools using `AssertionStakingPoolCreator::createPool`, prevent passing `bytes32(0)` as a valid `_assertionHash`.
