# Vulnerability details

## Impact

There is a function `fastConfirmAssertion()` in the `RollupUserLogic` smart contract that allows to any trust fast confirmer to rapidly react in the case of some emergency. In the current implementation, the function doesn't require any stake to be put in the contract if the assertion is the first child of the previous assertion. However, if there is any rival already created, the function will need to put some stake amount into the `loserStakeEscrow`. The problem is that the caller may see that there is no child assertion currently created and call the function without putting any stake so there will be lack of funds to put. This will revert the tx and the caller will lose gas money.

## Proof of Concept

Let's say the trust confirmer want to submit a random assertion A as rapidly as possible and calls `fastConfirmAssertion()`:

https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/main/src/rollup/RollupUserLogic.sol#L273

An adversary watches closely the mempool and decides to submit his assertion before the trust confirmer would. That leads to a situation where the trust confirmer should be aware of the stake amount that would go into `loserStakeEscrow`. His tx may suddenly revert as the function doesn't require for the msg.sender to be a validator and therefore any unexpected assertion that has happened beforehand may create a scenario where there will be not enough funds to cover the stake for starting the dispute. The first staker may also confirm the right assertion (an honest party) so the dispute game would be senseless and he'll not lose any money but the trust confirmer would have to stake the amount in the next tx as this particular tx will revert:

https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/main/src/rollup/RollupUserLogic.sol#L291-296
