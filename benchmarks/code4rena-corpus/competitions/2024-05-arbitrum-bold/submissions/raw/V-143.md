# Vulnerability details

## Impact
if host chain is arbitrum, direct use of block.timestamp instead of `ArbSys.arbBlockNumber()` may cause buffer to be updated with wrong block number data in `setBufferConfig()`

## Proof of Concept
`ArbSys` is a system level contract used by other contracts to access core L2 data and other specific functionality on all arbitrum chains. The function `arbBlockNumber()` gets the arbitrum chain block number. In this case,  Using `ArbSys.arbBlockNumber()` instead of `block.number` on arbitrum chain  is better because block.number returns eth(L1) block number at which the sequencer received the tx. But `ArbSys.arbBlockNumber(`) returns the actual block number of arbitrum chain which starts counting at the genesis block 0. 

https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/bridge/SequencerInbox.sol#L863
```
    function _setBufferConfig(BufferConfig memory bufferConfig_) internal {
        if (!isDelayBufferable) revert NotDelayBufferable();
        if (!DelayBuffer.isValidBufferConfig(bufferConfig_)) revert BadBufferConfig();

        if (buffer.bufferBlocks == 0 || buffer.bufferBlocks > bufferConfig_.max) {
            buffer.bufferBlocks = bufferConfig_.max;
        }
        if (buffer.bufferBlocks < bufferConfig_.threshold) {
            buffer.bufferBlocks = bufferConfig_.threshold;
        }
        buffer.max = bufferConfig_.max;
        buffer.threshold = bufferConfig_.threshold;
        buffer.replenishRateInBasis = bufferConfig_.replenishRateInBasis;

        // if all delayed messages are read, the buffer is considered synced
        if (bridge.delayedMessageCount() == totalDelayedMessagesRead) {
            buffer.update(uint64(block.number));
        }
    }
```

The sequencerInbox may be deployed on arbitrum chains or non arbitrum chains. In the case where it is deployed on non-arbitrum chains, `block.number` can return the actual most recent block number of that chain. But if it is deployed on an arbitrum chain, block.number value doesnt mean the arbitrum chain most recent block but the most recent L1 block the sequcnecer synced with. Using another L1 chain's block number value in this context of a buffer update when sequencerInbox is deployed on arbitrum chain is innaccurate and will lead to buffer being updated with values that are not the actual arbitrum block numbers. For more info read [here](https://docs.arbitrum.io/build-decentralized-apps/arbitrum-vs-ethereum/block-numbers-and-time#arbitrum-block-numbers) and [here](https://docs.arbitrum.io/build-decentralized-apps/arbitrum-vs-ethereum/block-numbers-and-time#arbitrum-block-numbers).

## Recommended Mitigation Steps

add a if condition for if `hostChainIsArbitrum`, `ArbSys.arbBlockNumber()` should be used to fetch the correct arbitrum chain block number and use that to update the buffer. For example 

```
        if (hostChainIsArbitrum) {
            buffer.update(uint64(ArbSys.arbBlockNumber()));
         } else {
            buffer.update(uint64(block.number));
         }

```
