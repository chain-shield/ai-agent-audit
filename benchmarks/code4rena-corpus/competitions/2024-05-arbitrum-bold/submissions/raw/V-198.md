# Vulnerability details

## Impact
The handling of the staking amount when creating a new layer zero edge, the code checks if the `stakeToken` address is non-zero and the `stakeAmounts` for the given level is non-zero. If both conditions are true, it transfers the staking amount from the caller to either the contract itself or the `excessStakeReceiver` address.

However, the condition for determining the recipient address seems to be incorrect: [EdgeChallengeManager.sol#L433](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/challengeV2/EdgeChallengeManager.sol#L433)
```solidity
address receiver = edgeAdded.hasRival ? excessStakeReceiver : address(this);
```
The `edgeAdded.hasRival` flag indicates whether the newly created edge already has a rival edge. However, this flag is not a reliable indicator of whether the stake should be sent to the contract or the `excessStakeReceiver`.

The correct condition should be based on whether the newly created edge is the first edge in its group or not. If it's the first edge, the stake should be sent to the contract itself, as it may need to be refunded later. If it's not the first edge, the stake should be sent to the `excessStakeReceiver`, as it will never be refunded.

#### Intended Behavior
When a new layer zero edge is created, and it is the first edge in its group (identified by the `mutualId`), the staking amount should be sent to the contract itself. This is because the stake may need to be refunded later if the edge is confirmed.

However, if the newly created edge is not the first edge in its group, the staking amount should be sent to the `excessStakeReceiver` address, as it will never be refunded.

> If the condition is incorrect and the staking amount is sent to the `excessStakeReceiver` when it should have been sent to the contract, there is a risk of losing those funds permanently. The contract will not have a record of the stake, and it will be impossible to refund it later if the edge is confirmed.

Inability to Refund Stakes: Conversely, if the staking amount is sent to the contract when it should have been sent to the `excessStakeReceiver`, it will be stored in the contract's balance. However, since the edge is not the first in its group, it will never be eligible for a refund. This means that the funds will be locked in the contract indefinitely, leading to inefficient use of resources.

Code snippet that illustrates the issue is: [EdgeChallengeManager.sol#L429-L324](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/challengeV2/EdgeChallengeManager.sol#L429-L435)
```solidity
if (address(st) != address(0) && sa != 0) {
    // since only one edge in a group of rivals can ever be confirmed, we know that we
    // will never need to refund more than one edge. Therefore we can immediately send
    // all stakes provided after the first one to an excess stake receiver.
    address receiver = edgeAdded.hasRival ? excessStakeReceiver : address(this);
    st.safeTransferFrom(msg.sender, receiver, sa);
}
```
The condition `edgeAdded.hasRival` is used to determine the recipient address, which is incorrect. Instead, the condition should check if the `mutualId` of the newly created edge already exists in the contract's storage. If it doesn't exist, it means the edge is the first in its group, and the stake should be sent to the contract. Otherwise, it should be sent to the `excessStakeReceiver`.

## Recommended Mitigation Steps
The condition should be modified to check if the `mutualId` of the newly created edge already exists in the contract's storage. If it doesn't exist, it means the edge is the first in its group, and the stake should be sent to the contract. Otherwise, it should be sent to the `excessStakeReceiver`.

```solidity
bool isFirstEdge = !store.edgeExists(edgeAdded.mutualId);
address receiver = isFirstEdge ? address(this) : excessStakeReceiver;
```
