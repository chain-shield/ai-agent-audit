# Vulnerability details

## Impact
Calculation of the `postSize` variable: [MerkleTreeLib.sol:L173-L174](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/challengeV2/libraries/MerkleTreeLib.sol#L173-L174)
```solidity
uint256 meSize = treeSize(me);
uint256 postSize = meSize + 2 ** level;
```
The calculation `meSize + 2 ** level` assumes that the `subtree` being appended has a size of `2 ** level`. However, this may not always be the case, as the `subtree` could have a different size.

For example, if the current Merkle tree expansion `me` has a size of 8, and we try to append a subtree at level 2 (which should have a size of 4), the `postSize` will be calculated as `8 + 2 ** 2 = 12`. However, the correct size after appending the subtree should be 10.

This incorrect calculation of `postSize` can lead to issues in the subsequent logic that checks if the most significant bit of `postSize` is greater than the most significant bit of `meSize`. If the calculation is incorrect, it may result in unnecessary memory allocations or incorrect tree expansions.

#### Correctness Issues:
The primary concern is that the incorrect calculation of `postSize` can lead to an incorrect Merkle tree expansion, which violates the fundamental properties of a Merkle tree. A Merkle tree is a data structure where each non-leaf node is the hash of its child nodes, and the root hash represents the entire tree. If the tree expansion is incorrect, the root hash calculated from the resulting tree will not match the expected root hash, breaking the integrity of the Merkle proof system.

#### To illustrate the issue, here's an example 
Let's consider the case where the current Merkle tree expansion `me` has a size of 8, and we want to append a subtree at level 2 (which should have a size of 4). The correct Merkle tree expansion after appending the subtree should have a size of 10.

However, with the current implementation, the postSize will be calculated as 8 + 2 ** 2 = 12. This incorrect calculation will lead to the following issues:

The subsequent logic that checks if the most significant bit of postSize is greater than the most significant bit of meSize will be incorrect, potentially leading to unnecessary memory allocations or incorrect tree expansions.

The resulting Merkle tree expansion will have a size of 12 instead of the expected size of 10, which means that the root hash calculated from this tree will be different from the expected root hash.

This violation of the Merkle tree properties can have severe consequences, such as incorrect verification of inclusion proofs or incorrect state transitions in systems that rely on Merkle trees for data integrity and consistency.

**Performance Issues:**
In addition to correctness issues, the incorrect calculation of `postSize` can also lead to performance problems, particularly in terms of gas consumption and memory usage.

## Recommended Mitigation Steps
Calculate the `postSize` based on the actual size of the subtree being appended, rather than assuming a size of `2 ** level`. A way to do this would be to pass the size of the subtree as an additional parameter to the function, or calculate it within the function based on the subtree root and the level.
