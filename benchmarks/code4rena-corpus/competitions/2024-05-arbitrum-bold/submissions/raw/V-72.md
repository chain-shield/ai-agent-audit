# Vulnerability details

## Impact
If the contract deployment fails and this failure is not detected, the system could reference non-existent contracts. This could lead to failed transactions, disruption of the staking mechanisms, and potential loss of funds or denial of service for users trying to interact with the staking pools.
## Proof of Concept
In the provided `StakingPoolCreatorUtils`, `EdgeStakingPoolCreator`, and `AssertionStakingPoolCreator` contracts, the `createPool` functions deploy new staking pool contracts using the CREATE2 opcode. However, these functions do not check if the contract deployment was successful, which can lead to potential issues if the deployment fails. This oversight can result in referencing non-existent contracts, leading to unintended behavior or failures in subsequent contract interactions.

Here’s the relevant code snippet from `EdgeStakingPoolCreator`:
```solidity
  /// @inheritdoc IEdgeStakingPoolCreator
    function createPool(
        address challengeManager,
        bytes32 edgeId
    ) external returns (IEdgeStakingPool) {
        EdgeStakingPool pool = new EdgeStakingPool{salt: 0}(challengeManager, edgeId);
        emit NewEdgeStakingPoolCreated(challengeManager, edgeId);
        return pool;
    }
```
Similarly, in `AssertionStakingPoolCreator`:
```solidity
 /// @inheritdoc IAssertionStakingPoolCreator
    function createPool(
        address _rollup,
        bytes32 _assertionHash
    ) external returns (IAssertionStakingPool) {
        AssertionStakingPool assertionPool = new AssertionStakingPool{salt: 0}(_rollup, _assertionHash);
        emit NewAssertionPoolCreated(_rollup, _assertionHash, address(assertionPool));
        return assertionPool;
    }
```
In these functions, the deployment of the `EdgeStakingPool` and `AssertionStakingPool` contracts is attempted, but there is no verification step to confirm that the contracts were successfully deployed at the computed address. If the deployment fails, subsequent calls or interactions with these contracts could fail or lead to unintended behavior since the address might not contain any contract bytecode.
## Tools Used
Manual
## Recommended Mitigation Steps
The `createPool` functions should be enhanced to verify the existence of the contract bytecode at the computed address before proceeding. This can be achieved by checking the bytecode at the address after deployment and reverting the transaction if no bytecode is found.
