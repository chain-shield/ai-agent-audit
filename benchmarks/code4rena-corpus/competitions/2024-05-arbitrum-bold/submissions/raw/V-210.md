# Vulnerability details

## Impact
The check for `isDelayProofRequired(afterDelayedMessagesRead)` is performed before calling the `addSequencerL2BatchFromCalldataImpl` function. However, the `isDelayProofRequired` function checks if the `afterDelayedMessagesRead` value is greater than the `totalDelayedMessagesRead` value.

The problem arises when the `afterDelayedMessagesRead` value is equal to the `totalDelayedMessagesRead` value. In this case, the `isDelayProofRequired` function will return false, even though a delay proof might be required.

**Scenario where this bug could occur:**

The `totalDelayedMessagesRead` value is initially 0.
A batch is added with `afterDelayedMessagesRead` set to 0.
The `isDelayProofRequired(0)` check will return false, and the batch will be added without a delay proof.
However, in this case, a delay proof should have been provided because the `afterDelayedMessagesRead` value is equal to the `totalDelayedMessagesRead` value, and the batch should not be accepted without a delay proof.

## Proof of Concept
The issue in the [addSequencerL2BatchFromOrigin](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/bridge/SequencerInbox.sol#L366-L387) function is a security vulnerability that could allow an attacker to bypass the delay proof requirement under certain conditions.

The `isDelayProofRequired` function is defined as follows:
```solidity
function isDelayProofRequired(uint256 afterDelayedMessagesRead)
    public
    view
    returns (bool)
{
    return afterDelayedMessagesRead > totalDelayedMessagesRead;
}
```
This function checks if the `afterDelayedMessagesRead` value is greater than the `totalDelayedMessagesRead` value. If it is, then a delay proof is required. However, if `afterDelayedMessagesRead` is equal to `totalDelayedMessagesRead`, the function will return false, indicating that a delay proof is not required.

In the `addSequencerL2BatchFromOrigin` function, the `isDelayProofRequired` check is performed before calling `addSequencerL2BatchFromCalldataImpl`: [SequencerInbox.sol#L377-L385](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/bridge/SequencerInbox.sol#L377-L386)
```solidity
if (isDelayProofRequired(afterDelayedMessagesRead)) revert DelayProofRequired();

addSequencerL2BatchFromCalldataImpl(
    sequenceNumber,
    data,
    afterDelayedMessagesRead,
    prevMessageCount,
    newMessageCount,
    true
);
```
The vulnerability arises when `afterDelayedMessagesRead` is equal to `totalDelayedMessagesRead`. In this case, the `isDelayProofRequired` check will return `false`, allowing the batch to be added without a delay proof, even though a delay proof should be required.

This could be exploited by an attacker who is a batch poster. The attacker could submit a batch with `afterDelayedMessagesRead` equal to `totalDelayedMessagesRead`, bypassing the delay proof requirement and potentially including invalid or malicious transactions in the batch.

Consider the following scenario:

Initially, `totalDelayedMessagesRead` is 0.
An attacker, who is a batch poster, calls` addSequencerL2BatchFromOrigin` with `afterDelayedMessagesRead` set to 0.
The `isDelayProofRequired(0)` check returns `false` because `afterDelayedMessagesRead` (0) is not greater than `totalDelayedMessagesRead` (0).
The batch is added without a delay proof, even though a delay proof should have been required since `afterDelayedMessagesRead` is equal to `totalDelayedMessagesRead`

This could lead to invalid or malicious transactions being included in the batch, compromising the integrity and security of the system.

## Recommended Mitigation Steps
The `isDelayProofRequired` function should be modified to check if `afterDelayedMessagesRead` is greater than or equal to `totalDelayedMessagesRead`, instead of just greater than. Alternatively, the check for `isDelayProofRequired` could be moved inside the `addSequencerL2BatchFromCalldataImpl` function, where the actual batch processing happens.
