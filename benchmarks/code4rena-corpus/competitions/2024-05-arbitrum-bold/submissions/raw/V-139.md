# Vulnerability details

## Impact
Unauthorized stake withdrawals,asset transfers

## Proof of Concept
When a return value ```userRollup.returnOldDeposit()``` is mocked to simulate an inactive staker. This bypass the normal checks and validations that prevent the withdrawal of active stakes.

```solidity
function makeStakeWithdrawable() public {
        // this checks for active staker
        IRollupUser(rollup).returnOldDeposit();
    }
```
The ```makeStakeWithdrawable``` function check if stakes can be withdrawable by interacting with the ```IRollupUser``` through the ```returnOldDeposit``` function to communicate and check for active stakers to determine the state of their stakes for withdrawal based on the data retrieved from ```returnOldDeposit```

Manipulating the return value will trigger the ```RollupProxy``` contract to call ```newStakeOnNewAssertion``` with a specified stake amount to delegates the call to create a new assertion with the specified staked amount.

Attacker can potentially bypass the checks and validations that are typically performed before the creation of new assertion.

The manipulation may tricks the system into believing that the attacker is an inactive staker, allowing them to create a new assertion and stake through the ```newStakeOnNewAssertion``` function. Allowing the attacker to bypass the fraud proof validations that prevent honest participants from challenging the invalid assertion.

As described in here https://dl.acm.org/doi/10.1145/3631310.3633493

This allow the attacker to bypass the fraud proof validation temporarily.
Attacker ability to create new assertions will allow the attacker to introduce invalid or malicious state transitions to the cross-chain communication or asset transfers

```solidity
    /**
     * @notice Create a new stake on a new assertion
     * @param tokenAmount Amount of the rollups staking token to stake
     * @param assertion Assertion describing the state change between the old assertion and the new one
     * @param expectedAssertionHash Assertion hash of the assertion that will be created
     * @param withdrawalAddress The address the send the stake back upon withdrawal
     */
    function newStakeOnNewAssertion(
        uint256 tokenAmount,
        AssertionInputs calldata assertion,
        bytes32 expectedAssertionHash,
        address withdrawalAddress
    ) public {
        require(withdrawalAddress != address(0), "EMPTY_WITHDRAWAL_ADDRESS");
        _newStake(tokenAmount, withdrawalAddress);
        stakeOnNewAssertion(assertion, expectedAssertionHash);
        /// @dev This is an external call, safe because it's at the end of the function
        receiveTokens(tokenAmount);
    }
```

Here's a foundry test function that demonstrate the scenario:

Add the test function in ```Rollup.t.sol```

```solidity
function testWithdrawActiveStake() public {
    testSuccessConfirmEdgeByTime();
    vm.prank(validator2);

    // Bypassing the checks to allow the withdrawal of active stake
    vm.mockCall(
        address(userRollup),
        abi.encodeWithSelector(userRollup.returnOldDeposit.selector),
        abi.encode(true) // Mocking the return value
    );

    // Verify the withdrawal of stake
    assertEq(userRollup.amountStaked(validator2), 10);
}
```
Run the test 

```javascript
forge test --match-test testWithdrawActiveStake -vvvv
```

## Tools Used
Manual review 
## Recommended Mitigation Steps
Consider implementing more validation checks on ```returnOldDeposit``` function to prevent the manipulation of return value.
Ensure that honest participants can challenge invalid assertions.
