# Vulnerability details

There's an issue with the refund logic when the `_nativeToken` is not the zero address (i.e., when using an ERC-20 token). The code attempts to transfer the required fee amount from the caller to the inbox contract before calling the `perform` function. However, there is no check to ensure that the caller has approved the required amount for the contract to transfer from their account.

Here's the problematic code: [RollupCreator.sol:306-315](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupCreator.sol#L306-L316)
```solidity
} else {
    // Transfer fee token amount needed to pay for retryable fees to the inbox.
    uint256 totalFee = l2FactoriesDeployer.getDeploymentTotalCost(
        IInboxBase(_inbox),
        _maxFeePerGas
    );
    IERC20(_nativeToken).safeTransferFrom(msg.sender, _inbox, totalFee);

    // do it
    l2FactoriesDeployer.perform(_inbox, _nativeToken, _maxFeePerGas);
}
```
The `safeTransferFrom` will revert if the caller has not approved the contract to spend the required amount of tokens on their behalf. This could lead to the entire transaction failing, even if the caller has sufficient funds.

## Impact
The `_deployFactories` function is responsible for deploying the L2 factories (contracts) on the rollup chain. When the `_nativeToken` parameter is not the zero address (i.e., when using an ERC-20 token as the fee token), the function attempts to transfer the required fee amount from the caller's account to the inbox contract before calling the `perform` function to deploy the factories.

However, the code does not check if the caller has approved the contract to spend the required amount of tokens on their behalf. This means that if the caller has not approved the contract for the required amount, the `safeTransferFrom` function will revert, causing the entire transaction to fail, even if the caller has sufficient funds in their account.

> This could lead to unexpected behavior and failed transactions, potentially causing users to lose funds (the fee amount) without achieving the desired outcome (deploying the L2 factories).

## Proof of Concept
Alice wants to deploy the L2 factories using an ERC-20 token as the fee token.
Alice has sufficient funds (more than `totalFee`) in her ERC-20 token balance.
However, Alice has not approved the `RollupCreator` contract to spend the required amount of tokens on her behalf.
Alice calls the `_deployFactories` function with the appropriate parameters.
The `safeTransferFrom` function is called, attempting to transfer `totalFee` tokens from Alice's account to the inbox contract.
Since Alice has not approved the `RollupCreator` contract to spend the required amount of tokens, the `safeTransferFrom` function reverts.
The entire transaction fails, and the L2 factories are not deployed, despite Alice having sufficient funds.

## Recommended Mitigation Steps
Require the caller to approve the contract for the required amount before calling `_deployFactories`.
Use the `transferFrom` function instead of `safeTransferFrom`, and handle the potential revert scenario appropriately (e.g., by checking the return value or using a try/catch block).
