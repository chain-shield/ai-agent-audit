# Vulnerability details

## Vulnerability Detail
The vulnerability stems from the `getPool` function within the `StakingPoolCreatorUtils` library, which computes the address of a staking pool contract using the create2 opcode. By providing specific `creationCode` and `args` parameters, an attacker can craft inputs that result in the same address for different pool instances. This collision in address generation allows the attacker to deploy a malicious contract with an address that collides with the target staking pool contract.
These past issues have clearly explained the possibility of finding a collision, along with the exact methods and needed equipment
1. https://github.com/sherlock-audit/2023-07-kyber-swap-judging/issues/90
2. https://solodit.xyz/issues/m-2-routersol-is-vulnerable-to-address-collission-sherlock-kyberswap-git
## Impact
Address collision can cause pool to be drained or manipulated

## Proof of Concept
```

function getPool(bytes memory creationCode, bytes memory args) internal view returns (address) {
        bytes32 bytecodeHash = keccak256(abi.encodePacked(creationCode, args));
        address pool = Create2.computeAddress(0, bytecodeHash, address(this));
        if (Address.isContract(pool)) {
            return pool;
        } else {
            revert PoolDoesntExist();
        }
    }
```
## Tools Used
Manual review
## Recommended Mitigation Steps
Implement Unique Salts: Modify the `createPool` function to use unique salts for each pool instance, reducing the chance of address collisions.
