# Vulnerability details

## Impact
In the `SequencerInbox` contract, certain functions like `addSequencerL2BatchFromOrigin`, `addSequencerL2BatchFromOriginDelayProof`, etc. have the implementation of the `refundsGas` function modifier that is declared in the `GasRefundEnabled` contract. This modifier allows for an external contract (gasRefunder contract) to be called. The call's argument is another external contract which is an arbitrary `IReader4844` contract. 

The contract does not validate that these external contracts come from a trusted source, which might lead to calls to malicious third-party contracts. Also, any external call could potentially fail and could be used to deliberately manipulate state-changing operations in the `SequencerInbox` contract if not properly handled.

## Proof of Concept
The `addSequencerL2BatchFromOrigin` function declared in the `SequencerInbox` contract utilizes the `refundsGas` function modifier:

```solidity
/// @inheritdoc ISequencerInbox
function addSequencerL2BatchFromOrigin(
    uint256 sequenceNumber,
    bytes calldata data,
    uint256 afterDelayedMessagesRead,
    IGasRefunder gasRefunder,
    uint256 prevMessageCount,
    uint256 newMessageCount
) external refundsGas(gasRefunder, IReader4844(address(0))) {
    //...
}
```

Here, the `refundsGas` modifier is implemented as follows:

```solidity
modifier refundsGas(IGasRefunder gasRefunder, IReader4844 precompileReader) {
    if (!isBlockGasLimit() || address(gasRefunder) == address(0)) {
        _;
        return;
    }
    uint256 gasUsedBefore = gasleft();
    _;
    gasRefunder.onGasSpent(precompileReader, gasUsedBefore - gasleft());
}
```

As observed, the `gasRefunder.onGasSpent` function is called in the `refundsGas` modifier.

## Recommended Mitigation Steps

External contracts should be ideally isolated in their own `try-catch` block to contain failure. To protect against Reentrancy, the Checks-Effects-Interactions Pattern must be followed. Or use `reentrancyGuard` modifier to prevent reentrancy attacks.
