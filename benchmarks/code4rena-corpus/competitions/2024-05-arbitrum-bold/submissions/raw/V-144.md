# Vulnerability details

The main point of the `AssertionStakingPool` is "Allows users to deposit stake, create assertion once required stake amount is reached, and reclaim their stake when and if the assertion is confirmed" when the stake amount is reached the `createAssertion` function can be called.

```solidity

function createAssertion(AssertionInputs calldata assertionInputs) external {
        uint256 requiredStake = assertionInputs.beforeStateData.configData.requiredStake;
        // approve spending from rollup for newStakeOnNewAssertion call
        IERC20(stakeToken).safeIncreaseAllowance(rollup, requiredStake);
        // reverts if pool doesn't have enough stake and if assertion has already been asserted
        IRollupUser(rollup).newStakeOnNewAssertion(requiredStake, assertionInputs, assertionHash, address(this));
    }

```
[[Link]](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/assertionStakingPool/AssertionStakingPool.sol#L40)

The problem is that is not implementing any access control, this is problematic because a malicious user can just call the function with a false assertion and make that all the honest user loss his money because the assertion will be challenge since is not valid. 

## Impact
Users that stake in the `AssertionStakingPool` contract may loss all his stake is a malicious user or attacker call the `createAssertion` function with a false assertion.

## Proof of Concept

Run this test in `file: /test/stakingPool/AssertionStakingPool.t.sol`

  function testAttackerCreateAsseetion() external {

## Recommended Mitigation Steps

I think that there is not a easy recommendation for this but i let some options:

* Implement a single owner that is gonna call the `createAssertion` function, stakers now upfront which is the owner and they can decide if stake in that pool or not.
* Implement a enumerable set, and the `createAssertion` function can only be  called by the address in the set.
* Implement a governance contract.
