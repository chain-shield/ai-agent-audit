# Vulnerability details


## Proof of Concept

Take a look at https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupUserLogic.sol#L48-L51

```solidity
    uint256 public constant VALIDATOR_AFK_BLOCKS = 201600;

```

This is the number of blocks since the last confirmed assertion before the validator whitelist is removed and is to be 28 days, but this assumption has been made with a 12 seconds block minting time, however that's only valid on the mainnet. but protocol is to be deployed on both the mainnet and arbitrum https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/README.md#L127-L128

```markdown
| Chains the protocol will be deployed on | Ethereum,Arbitrum |
```

Considering block minting times are way shorter on arbitrum this then means that this value would be the wrong one for the arbitrum chain since the blocks would be minted in a different duration other than 28 days.

## Impact

The time to get to the `VALIDATOR_AFK_BLOCKS` blocks on arbitrum would be way different than on the mainnet showcasing a disparity in the protocol's implementation on both chains.

## Recommended Mitigation Steps

Consider passing in the `VALIDATOR_AFK_BLOCKS` as an argument when deploying the contract and passing in a chain specific value which in the case of arbitrum would be different.
