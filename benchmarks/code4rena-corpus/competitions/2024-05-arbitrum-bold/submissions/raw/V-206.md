# Vulnerability details

## Bug Description
In the way the `actualIsUsingFeeToken` variable is set. The code attempts to call the `nativeToken()` function on the `bridge_` contract and checks if the returned address is non-zero. However, this approach assumes that the `nativeToken()` function will always revert if it is not implemented, which may not be the case.

If the `nativeToken()` function is not implemented and does not revert, it will likely return the zero address (`address(0)`). In this case, the `actualIsUsingFeeToken` variable will be incorrectly set to `true`, even though the bridge is not using a fee token.

## Impact
The code attempts to determine whether the `bridge_` contract is using a fee token or not. This information is crucial because it affects how the `SequencerInbox` contract should handle fees and interact with the `bridge_` contract.

If the `actualIsUsingFeeToken` variable is set incorrectly, it could lead to the following issues:

> If `actualIsUsingFeeToken` is set to `true` when the bridge is not actually using a fee token, the `SequencerInbox` contract may attempt to transfer or handle fees incorrectly, potentially leading to loss of funds or incorrect state.

The `SequencerInbox` contract may interact with the `bridge_` contract in an incorrect manner, assuming it supports fee token functionality when it does not, or vice versa. This could lead to unexpected behavior, failed transactions, or potential security vulnerabilities.

> The code reverts with the `NativeTokenMismatch` error if `isUsingFeeToken` (the expected value) does not match `actualIsUsingFeeToken` (the detected value). If `actualIsUsingFeeToken` is set incorrectly, the contract may revert unexpectedly or fail to revert when it should.

## Proof of Concept
The assumption is that the `nativeToken()` function will always revert if it is not implemented. However, this assumption may not hold true in all cases.

The relevant code snippet is: [SequencerInbox.sol#L187-L192](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/bridge/SequencerInbox.sol#L187-L192)
```solidity
bool actualIsUsingFeeToken = false;
try IERC20Bridge(address(bridge_)).nativeToken() returns (address feeToken) {
    if (feeToken != address(0)) {
        actualIsUsingFeeToken = true;
    }
} catch {}
```
If the `nativeToken()` function is not implemented and does not revert, it will likely return the zero address (`address(0)`). In this case, the `actualIsUsingFeeToken` variable will be set to false, even if the bridge is using a fee token.

For example, consider the following implementation of the IERC20Bridge interface:
```solidity
interface IERC20Bridge {
    function nativeToken() external view returns (address) {
        // Not implemented, returns the zero address
        return address(0);
    }
}
```
In this case, even if the bridge is using a fee token, the `actualIsUsingFeeToken` variable will be set to `false`, leading to incorrect behavior and potential security issues.

## Recommended Mitigation Steps
The code should handle the case where the `nativeToken()` function is not implemented or returns the zero address explicitly, as suggested in my previous response.

```solidity
bool actualIsUsingFeeToken;
try IERC20Bridge(address(bridge_)).nativeToken() returns (address feeToken) {
    actualIsUsingFeeToken = (feeToken != address(0));
} catch {
    // nativeToken() function is not implemented, assume no fee token
    actualIsUsingFeeToken = false;
}
```
In this modified code, the `actualIsUsingFeeToken` variable is set to `true` only if the `nativeToken()` function returns a non-zero address. If the function is not implemented or reverts for any reason, the catch block sets `actualIsUsingFeeToken` to false.
