# Vulnerability details


## Impact
In the likelyhood of a Fork, some functionalities are enabled in the protocol. However, due to their implementation, the `RollupOwner` looses some control over alot of functions.

- In the SequencerInbox, the rollup owner has the ability to set the Max Time Variation using `SequencerInbox::setMaxTimeVariation()`. In the case of a fork, we have the `SequencerInbox::removeDelayAfterFork()` to initially remove the delay after a fork. However the delay can then be later set again by the rollup owner using `SequencerInbox::setMaxTimeVariation()`. However this function is no more useful since any user can call `SequencerInbox::removeDelayAfterFork()` again and again even though the fork happened only once and the rollup owner has changed the values after the Fork.

This is because the chainId would always be different from the deployment chainId, hence `_chainIdChanged()` would always be true after the both removeDelay is called and setMaxTimeVariation by the owner:
```solidity
    function _chainIdChanged() internal view returns (bool) {
        return deployTimeChainId != block.chainid;
    }
    function removeDelayAfterFork() external {
        if (!_chainIdChanged()) revert NotForked();
        delayBlocks = 1;
        futureBlocks = 1;
        delaySeconds = 1;
        futureSeconds = 1;
    }
```

Therefore the admin cannot control the delay after fork.


- In the rollup contract, a more severe issue arises pertaining to the activation and deactivation of whitelisted validators verification.
In the `RollupAdminLogic::setValidator()`, the rollup owner can whitelist the validator addresses, however this whitelist feature can be turned off/on using the  `RollupAdminLogic::setValidatorWhitelistDisabled` allowing general users to bypass the `onlyValidator` modifier. After a Fork, the function `RollupUserLogic::removeWhitelistAfterFork` allows any user to remove the whitelist requirement. 
When the RollUp Owner decides to reactivate whitelist after a Fork, any user can simply deactivate it again, thereby passing the whitelist. 

This is due to the same caveat as the first issue, `_chainIdChanged()` will always be true, even after the admin has reset the `validatorWhitelistDisabled`  after a fork.
```solidity
    function removeWhitelistAfterFork() external {
        require(!validatorWhitelistDisabled, "WHITELIST_DISABLED");
        require(_chainIdChanged(), "CHAIN_ID_NOT_CHANGED");
        validatorWhitelistDisabled = true;
    }

    function _chainIdChanged() internal view returns (bool) {
        return deployTimeChainId != block.chainid;
    }


```

## Recommended Mitigation Steps

Update the deployTimeChainId after `removeWhitelistAfterFork` and `removeDelayAfterFork` is called. So `_chainIdChanged` would return false after the first override has happened
