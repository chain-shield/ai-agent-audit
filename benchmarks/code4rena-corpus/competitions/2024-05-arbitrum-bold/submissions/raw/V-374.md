# Vulnerability details

## Impact
`firstChildBlock` value not set when assertion is created as the first child. Child properties not updated when assertion is created during `RollUpAdminLogic.initalize()`. first child assertion creation process is incomplete

## Proof of Concept
the `firstChildBlock` property is described to start at 0 and is set to a value when the first child is created as seen [here](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/Assertion.sol#L18C1-L20C28) but this property is not explicitly set via [AssertionNodeLib::createAssertion()](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/Assertion.sol#L70C1-L80C6). This means that when an assertion is created as the first child (_isFirstChild param is true), `firstChildBlock` will still be 0 and representing a state where by no first child assertion is created/made. This makes the first child assertion creation process to be incomplete.

 In `RollUpAdminLogic.initalize()`, we can see the way createAssertion are hardcoded  and isFirstChild is hardcoded to be true 
https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupAdminLogic.sol#L76C1-L77C18
