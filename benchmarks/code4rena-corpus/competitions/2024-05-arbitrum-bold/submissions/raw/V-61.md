# Vulnerability details

### Vulnerability Details

#### Incorrect Implementation of SafeERC20 Function

The `RollupUserLogic.sol` contract in the Arbitrum Foundation repository has multiple instances of incorrect implementations of the SafeERC20 functions. These functions are supposed to ensure safe and proper token transfers, which is critical for security in smart contracts.

##### Correct Implementations

According to OpenZeppelin's SafeERC20 library, the correct implementation should be as follows:

1. **Safe Transfer**
    ```solidity
    function safeTransfer(IERC20 token, address to, uint256 value) internal {
        _callOptionalReturn(token, abi.encodeCall(token.transfer, (to, value)));
    }
    ```
    [Link to correct implementation](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/255e27e6d22934ddaf00c7f279039142d725382d/contracts/token/ERC20/utils/SafeERC20.sol#L36-L38)

2. **Safe Transfer From**
    ```solidity
    function safeTransferFrom(IERC20 token, address from, address to, uint256 value) internal {
        _callOptionalReturn(token, abi.encodeCall(token.transferFrom, (from, to, value)));
    }
    ```
    [Link to correct implementation](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/255e27e6d22934ddaf00c7f279039142d725382d/contracts/token/ERC20/utils/SafeERC20.sol#L44-L46)

#### Recommendation

To ensure the safety and correctness of token transfers, the above instances should be updated to use the SafeERC20 functions correctly. This involves replacing the current unsafe transfer calls with the `_callOptionalReturn` method as provided by OpenZeppelin.

**Example Correction:**

For instance 1 and 2:
```solidity
SafeERC20.safeTransfer(IERC20(stakeToken), loserStakeEscrow, assertion.beforeStateData.configData.requiredStake);

For instance 3:

SafeERC20.safeTransfer(IERC20(stakeToken), msg.sender, amount);

For instance 4:
