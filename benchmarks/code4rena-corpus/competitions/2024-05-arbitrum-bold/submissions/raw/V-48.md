# Vulnerability details

## Impact
The `newStakeOnNewAssertion` function in the `RollupUserLogic` contract does not consistently follow the check-effect-interaction pattern. The function makes an external call to the `receiveTokens` function after performing internal state changes. This inconsistency can lead to a reentrancy vulnerability, where an attacker can potentially exploit the contract by recursively calling back into the `newStakeOnNewAssertion` function before the state changes are completed.

The reentrancy vulnerability in the `newStakeOnNewAssertion` function can have a severe impact on the contract's functionality and the security of user funds. An attacker can manipulate the contract's state, perform unauthorized actions, or steal funds by exploiting the lack of proper checks and state updates before making the external call to `receiveTokens`. The attacker could potentially create multiple stakes, bypass intended staking limits, or disrupt the staking process for other users. This vulnerability can result in financial losses, compromise of user funds, and damage to the protocol's integrity.


## Proof of Concept
An attacker identifies the reentrancy vulnerability in the `newStakeOnNewAssertion` function.

The attacker creates a malicious contract that implements the `receiveTokens` function and is capable of recursively calling the `newStakeOnNewAssertion` function.

The attacker calls the `newStakeOnNewAssertion` function with the necessary parameters, including the malicious contract's address as the `withdrawalAddress`.

The `newStakeOnNewAssertion` function performs the internal state changes, including updating the staker's information and creating a new stake.

The function then makes an external call to the `receiveTokens` function of the malicious contract.

Inside the `receiveTokens` function, the malicious contract recursively calls the `newStakeOnNewAssertion` function before the previous call has finished.

The recursive calls to `newStakeOnNewAssertion` execute with the same staker information, potentially creating multiple stakes or bypassing intended limits.

The attacker can then exploit the inconsistent state and perform unauthorized actions, such as withdrawing funds or manipulating the staking process.

## Recommended Mitigation Steps
To mitigate the reentrancy vulnerability, consistently follow the check-effect-interaction pattern throughout the `newStakeOnNewAssertion` function. Ensure that all state changes and internal updates are performed before making any external calls. Implement a reentrancy guard mechanism, such as the `nonReentrant` modifier from the OpenZeppelin library, to prevent recursive calls during the execution of the function.
