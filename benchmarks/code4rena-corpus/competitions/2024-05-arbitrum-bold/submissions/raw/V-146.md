# Vulnerability details

When an assertion is confirmed in a staking pool, user then can call `makeStakeWithdrawableAndWithdrawBackIntoPool` to get the tokens available to each staker make his withdraw:


```solidity
  function makeStakeWithdrawable() public {
        // this checks for active staker
        IRollupUser(rollup).returnOldDeposit();
    }

    /// @inheritdoc IAssertionStakingPool
    function withdrawStakeBackIntoPool() public {
        IRollupUser(rollup).withdrawStakerFunds();
    }

    /// @inheritdoc IAssertionStakingPool
    function makeStakeWithdrawableAndWithdrawBackIntoPool() external {
        makeStakeWithdrawable();
        withdrawStakeBackIntoPool();
    }
```
[[Link]](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/assertionStakingPool/AssertionStakingPool.sol#L60)

To make a `makeStakeWithdrawable` the staker(the whole pool) have to be inactive in the rollup contract

```solidity

 function returnOldDeposit() external override onlyValidator whenNotPaused { 
        requireInactiveStaker(msg.sender);  <-----
        withdrawStaker(msg.sender);
    }

```
[[Link]](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupUserLogic.sol#L222)

```solidity

function requireInactiveStaker(address stakerAddress) internal view {
        require(isStaked(stakerAddress), "NOT_STAKED");
        // A staker is inactive if
        // a) their last staked assertion is the latest confirmed assertion
        // b) their last staked assertion have a child
        bytes32 lastestAssertion = latestStakedAssertion(stakerAddress);
        bool isLatestConfirmed = lastestAssertion == latestConfirmed();  <--------
        bool haveChild = getAssertionStorage(lastestAssertion).firstChildBlock > 0;
        require(isLatestConfirmed || haveChild, "STAKE_ACTIVE");
    }

```
[[Link]](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupCore.sol#L565C5-L574C6)

The problem is that the an attacker can just front run the `makeStakeWithdrawableAndWithdrawBackIntoPool` transaction making an assertion (not matter is true or false assertions) and succesfully making revert the transaction since the staking pool is now active in the roll up contract(see the above arrow) and the `createAssertion` function is not implementing access control.

Note that this is not the same as "missing access control in `createAssertion` function" because first different impacts, and depending on the solution of the access control this issue can persist.

## Impact
Tokens in the staking pool can get stuck since an attacker can keep creating assertions.

As you can see in the arrow if a staker make and assertion front running the `makeStakeWithdrawableAndWithdrawBackIntoPool` the staker (staking pool) will be active, the withdraw is going to fail, an attacker can keep just doing this and user will be unable to unstake his money.

## Tools Used
Manual

## Recommended Mitigation Steps

* Implement a single owner that is gonna call the `createAssertion` function, stakers now upfront which is the owner and they can decide if stake in that pool or not.
* Implement a governance contract.
* Note that the implement a enumerable set solution here it does not resolve the issue.
