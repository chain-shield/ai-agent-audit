# Vulnerability details

## Impact
In the [stakeOnNewAssertion function](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupUserLogic.sol#L163-L182) there is a significant issue that can lead to unfair loss of stakes for stakers in certain scenarios.

The issue lies in the following lines: [#L210-L215](https://github.com/code-423n4/2024-05-arbitrum-foundation/blob/6f861c85b281a29f04daacfe17a2099d7dad5f8f/src/rollup/RollupUserLogic.sol#L210-L217)

```solidity
if (!getAssertionStorage(newAssertionHash).isFirstChild) {
    // We assume assertion.beforeStateData is valid here as it will be validated in createNewAssertion
    // only 1 of the children can be confirmed and get their stake refunded
    // so we send the other children's stake to the loserStakeEscrow
    // NOTE: if the losing staker have staked more than requiredStake, the excess stake will be stuck
    IERC20(stakeToken).safeTransfer(loserStakeEscrow, assertion.beforeStateData.configData.requiredStake);
}
```
The problem is that the code assumes that if the new assertion is not the first child, it must be a losing assertion, and its stake should be transferred to the `loserStakeEscrow`. However, _this assumption may not always be correct._

> In a scenario where multiple stakers create assertions on the same branch, and one of them is eventually confirmed, the other stakers' assertions would be considered "losing" assertions, even though they may have been created before the confirmed assertion.

_This means that the stakes of these "losing" assertions would be transferred to the `loserStakeEscrow`, even though they should be refunded to the respective stakers._

## Proof of Concept
In a scenario where multiple stakers create assertions on the same branch, the code fails to differentiate between assertions created before and after the eventually confirmed assertion. As a result, the stakes of assertions created before the confirmed assertion, which should be refunded to the respective stakers, are incorrectly transferred to the `loserStakeEscrow`.

This behavior violates the fairness principle of the system, as stakers who made valid assertions but were not the first to be confirmed would unfairly lose their stakes. It also introduces a potential economic incentive for stakers to prioritize being the first to create an assertion on a branch, rather than focusing on the correctness and validity of their assertions.

**Example:**
**Consider the following scenario:**

Staker A creates an assertion `A1` on a branch.
Staker B creates an assertion `B1` on the same branch, after `A1`.
Staker C creates an assertion `C1` on the same branch, after `B1`.
Eventually, assertion B1 is confirmed as the correct assertion for that branch.
According to the current implementation, when `C1` is created, it will be considered a "losing" assertion because it is not the first child of the previous assertion (`B1`). As a result, Staker C's stake will be transferred to the `loserStakeEscrow`.

However, this is incorrect because `C1` was created after `B1`, which was eventually confirmed. In this case, Staker C's stake should be refunded, not transferred to the `loserStakeEscrow`.

Similarly, when `B1` was created, it was not the first child of `A1`. According to the current implementation, Staker B's stake would have been transferred to the `loserStakeEscrow` when `B1` was created, even though `B1` was eventually confirmed as the correct assertion.

The relevant code snippet that illustrates the issue is the following:
```solidity
if (!getAssertionStorage(newAssertionHash).isFirstChild) {
    // We assume assertion.beforeStateData is valid here as it will be validated in createNewAssertion
    // only 1 of the children can be confirmed and get their stake refunded
    // so we send the other children's stake to the loserStakeEscrow
    // NOTE: if the losing staker have staked more than requiredStake, the excess stake will be stuck
    IERC20(stakeToken).safeTransfer(loserStakeEscrow, assertion.beforeStateData.configData.requiredStake);
}
```
This code block assumes that if the new assertion is not the first child of the previous assertion, it is a "losing" assertion, and its stake should be transferred to the `loserStakeEscrow`. However, as illustrated in the example above, this assumption is incorrect and can lead to unfair loss of stakes.

## Recommended Mitigation Steps
The code should keep track of the confirmed assertion for each branch and only transfer the stakes of assertions that were created after the confirmed assertion to the `loserStakeEscrow`. Assertions created before the confirmed assertion should have their stakes refunded to the respective stakers.
