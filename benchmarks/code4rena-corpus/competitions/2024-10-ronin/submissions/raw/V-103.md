# Vulnerability details

## Proof of Concept
The router never verifies that the callback msg.sender is actually a deployed pool. This gives chance for a provable address collision that can be used to drain all allowances to the router.

Looking at the `v3SwapRouter` in katana operation contracts we can see that the `katanaV3SwapCallback` uses `if (computePoolAddress(tokenIn, tokenOut, fee) != msg.sender) revert V3InvalidCaller();` to verify that the address that made the call is a valid katana pool from the factory.

However this method of verifying the caller is vulnerable to address collision, as the computation of the create2 address is done by truncating a 256 bit keccak256 hash to 160 bits, meaning that for each address we have 2^96 hashes that will result in it after being truncated. This means that if a combination of a tokenIn and a tokenOut results in an address controlled by a malicious user, all the allowances given to the router can be stolen.

This vulnerability can cause all allowances to be drained.

Same issues have been found. For detailed information on the attack please check out;
https://github.com/sherlock-audit/2023-07-kyber-swap-judging/issues/90
https://github.com/sherlock-audit/2024-01-napier-judging/issues/111

## Recommended Mitigation Steps
Verify with the factory that msg.sender is a valid pool
