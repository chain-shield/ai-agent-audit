# Vulnerability details

#### Description

The dispatch function allows multiple commands to be executed based on a given `commandType`, including token transfers via permit and `permitBatch` commands. The use of `permit` is vulnerable to frontrunning because the authorization can be observed on-chain and used by an attacker before the legitimate user, especially in a context where `PERMIT2.permit` or `permit2TransferFrom` commands authorize transfers on behalf of the signatory without enforcing specific conditions. If exploited, an attacker could intercept and execute the token transfer, exhausting the permission before the intended user.

#### Proof of Concept (PoC)

Consider the following scenario, assuming a frontrunning attacker monitors the mempool:

1. Legitimate user (Alice) signs a permit transaction authorizing a token transfer.
2. Alice submits a transaction to the blockchain to invoke dispatch with `commandType` set to `Commands.PERMIT2_TRANSFER_FROM` and provides the required permit authorization in inputs.
3. Attacker (Bob) observes Alice’s pending transaction, copies the signed permit, and submits a similar transaction with a higher gas price, resulting in frontrunning Alice’s transaction.
4. Bob’s transaction succeeds, exhausting Alice’s permit authorization.
5. When Alice’s transaction is mined, it fails because the permit has already been used.

This PoC demonstrates how an attacker can intercept the permit authorization and consume it first, thus invalidating the original user’s intent.

```
// Example PoC Code Snippet
address token = <Token Address>;
address recipient = <Recipient Address>;
uint160 amount = 100;

// Alice signs a permit for token transfer
bytes calldata permitData = abi.encodeWithSelector(PERMIT2.permit.selector, token, recipient, amount);
dispatch(Commands.PERMIT2_TRANSFER_FROM, permitData);

// Bob frontruns the transaction and uses the permit before Alice's transaction is mined.
```
