# Vulnerability details

## Summary
The Katana V3 SwapMath library has a critical vulnerability that can be exploited when there's zero liquidity in a price range. This allows attackers to manipulate the pool price with minimal cost, impacting oracle accuracy and creating arbitrage opportunities.

The vulnerability stems from a lack of validation for zero liquidity in the `computeSwapStep` function. When liquidity is zero, the price can be moved to any target within an empty range without any resistance. This breaks the fundamental principle of AMMs, where price changes are determined by the ratio of assets and the amount of liquidity available.

Attackers can exploit this by finding empty price ranges and executing minimal swaps to drastically shift the pool price. This manipulated price can then be used to exploit oracle integrations or create profitable arbitrage opportunities on other platforms.

First, let's look at where this vulnerability begins in the core swap calculation:

```solidity
function computeSwapStep(
    uint160 sqrtRatioCurrentX96,
    uint160 sqrtRatioTargetX96,
    uint128 liquidity,          // Key vulnerability: no minimum validation
    int256 amountRemaining,
    uint24 feePips
) internal pure returns (uint160 sqrtRatioNextX96, uint256 amountIn, uint256 amountOut, uint256 feeAmount) {
    bool zeroForOne = sqrtRatioCurrentX96 >= sqrtRatioTargetX96;
    bool exactIn = amountRemaining >= 0;
```

When a swap occurs and encounters a zero liquidity range, the following sequence happens:

For exact input swaps (amountRemaining >= 0):
```solidity
if (exactIn) {
    // Calculate amount after fees
    uint256 amountRemainingLessFee = FullMath.mulDiv(
        uint256(amountRemaining), 
        1e6 - feePips, 
        1e6

    // Critical: When liquidity = 0, amountIn becomes 0
    amountIn = zeroForOne
        ? SqrtPriceMath.getAmount0Delta(sqrtRatioTargetX96, sqrtRatioCurrentX96, liquidity, true)
        : SqrtPriceMath.getAmount1Delta(sqrtRatioCurrentX96, sqrtRatioTargetX96, liquidity, true);
        
    // Price can move to target with no cost
    if (amountRemainingLessFee >= amountIn) {
        sqrtRatioNextX96 = sqrtRatioTargetX96;
    }
}
```

For exact output swaps (amountRemaining < 0):
```solidity
else {
    // When liquidity = 0, amountOut becomes 0

        ? SqrtPriceMath.getAmount1Delta(sqrtRatioTargetX96, sqrtRatioCurrentX96, liquidity, false)
```

The vulnerability becomes exploitable because the final price and amount calculations don't properly account for zero liquidity:

```solidity
// Get final amounts

    amountIn = max && exactIn
        ? amountIn    // Will be 0 if liquidity = 0
        : SqrtPriceMath.getAmount0Delta(sqrtRatioNextX96, sqrtRatioCurrentX96, liquidity, true);
    
    amountOut = max && !exactIn
        ? amountOut   // Will be 0 if liquidity = 0
        : SqrtPriceMath.getAmount1Delta(sqrtRatioNextX96, sqrtRatioCurrentX96, liquidity, false);
}
```

The fix requires implementing proper liquidity checks:

```solidity
function computeSwapStep(
    uint160 sqrtRatioCurrentX96,
    uint160 sqrtRatioTargetX96,
    uint128 liquidity,
    int256 amountRemaining,
    uint24 feePips
) internal pure returns (...) {
    require(liquidity >= MINIMUM_LIQUIDITY, "Insufficient liquidity");
    
    uint256 priceMovement = getPriceMovement(sqrtRatioCurrentX96, sqrtRatioTargetX96);
    uint256 maxMove = getMaxPriceMove(liquidity);
    require(priceMovement <= maxMove, "Price movement too large for liquidity");

function getMaxPriceMove(uint128 liquidity) internal pure returns (uint256) {
    // Implement non-linear relationship between liquidity and allowed price movement
    return Math.sqrt(liquidity) * PRICE_MOVEMENT_MULTIPLIER;
}
```
