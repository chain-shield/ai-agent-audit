# Vulnerability details

## Proof of Concept
Multiple pools cannot be created for the same token pair with different fees. However, there is a potential issue in the pool creation logic, however KatanaV3Factory allows creating multiple pools for the same token pair using different fee tiers. This design enables potential market manipulation through liquidity fragmentation and creates arbitrage opportunities that could harm users trading in less liquid pools. In [src/core/KatanaV3Factory.sol:L77-L90](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Factory.sol#L77-L90)
```solidity
function createPool(address tokenA, address tokenB, uint24 fee) external override returns (address pool) {
    // @Issue - Position manager check can be bypassed if governance contract is compromised
    require(msg.sender == IKatanaGovernance(owner).getPositionManager(), "KatanaV3Factory: INVALID_POSITION_MANAGER");

    require(tokenA != tokenB);
    (address token0, address token1) = tokenA < tokenB ? (tokenA, tokenB) : (tokenB, tokenA);
    require(token0 != address(0));
    int24 tickSpacing = feeAmountTickSpacing[fee];
    require(tickSpacing != 0);
    // @Issue - Only checks pool existence for specific fee tier, allowing multiple pools for same token pair
    require(getPool[token0][token1][fee] == address(0));
    pool = deploy(address(this), token0, token1, fee, tickSpacing);
    getPool[token0][token1][fee] = pool;
    getPool[token1][token0][fee] = pool;
    emit PoolCreated(token0, token1, fee, tickSpacing, pool);
}
```
The factory allows creating multiple pools for the same token pair if they have different fee tiers. While this might be intentional for flexibility, it could lead to liquidity fragmentation and potential market manipulation.

**Let's say we,**

1. Call createPool(tokenA, tokenB, fee1)
2. Call createPool(tokenA, tokenB, fee2) where fee2 ≠ fee1
3. Now there are two pools for the same token pair with different fees

Multiple pools for the same token pair with different fee tiers. This is dangerous for several reasons:

1. **Liquidity Fragmentation:** Multiple pools for the same token pair split liquidity across different fee tiers, reducing market efficiency and potentially increasing slippage for traders.

2. **Market Manipulation:** Attackers could exploit price differences between pools with different fees for arbitrage, potentially harming users who interact with less liquid pools.

The test file KatanaV3Factory.t.sol lacks checks for this scenario
```solidity
function test_createPool() public {
    // @Issue - Test only verifies single pool creation, missing multiple fee tier checks
    vm.prank(positionManager);
    address pool = factory.createPool(token0, token1, fee);
}
```
## Recommended Mitigation Steps
I think we should

* Implement a governance-controlled whitelist for allowed fee tiers
* Add pool creation limits per token pair
* Consider implementing a single-pool-per-pair policy with governance-controlled fee adjustment mechanisms
