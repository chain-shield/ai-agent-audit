# Vulnerability details

## Proof of Concept
Flash loan mechanism that allows attackers to manipulate pool state and potentially drain funds through reentrancy during flash loan callbacks, stems from the pool updating critical state variables after external calls in the `flash` loan function. The fee growth and liquidity state updates occur after the callback, creating a window where an attacker can reenter the pool with inconsistent state

[KatanaV3Pool.sol.flash#L750-L784](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Pool.sol#L750-L784)

**The main vulnerability patterns are:-**

1. Missing access controls on flash loans
2. Callbacks before balance/fee verification
3. State updates after external calls
4. Reliance on `tx.origin` for authorization
5. Fee growth state modifications through uncontrolled paths

**These create potential attack vectors through:-**

* Reentrancy during callbacks
* State manipulation between callback and verification
* Unauthorized fee collection
* Router bypass through contract calls

The core issues stem from the ordering of operations and insufficient access controls around state-changing functions.

**The vulnerability connects to:-**

* Fee growth tracking
* Liquidity state management
* Protocol fee collection
* Pool balance verification

**Attack Path:-**

1. Attacker calls `flash()` with large amounts
2. During callback, attacker reenters the pool
3. State variables are inconsistent during reentry
4. Attacker exploits the inconsistency to drain funds

```solidity
contract AttackContract {
    KatanaV3Pool pool;
    
    function attack() external {
        // First flash loan
        pool.flash(address(this), 1000e18, 1000e18, "");
    }
    
    function katanaV3FlashCallback(uint256 fee0, uint256 fee1, bytes calldata) external {
        // Reenter during callback
        pool.flash(address(this), 1000e18, 1000e18, "");
        
        // Pay back first flash loan with manipulated state
        token0.transfer(address(pool), 1000e18 + fee0);
        token1.transfer(address(pool), 1000e18 + fee1);
    }
}
```

## Recommended Mitigation Steps
1. Implement checks-effects-interactions pattern
```diff
function flash(...) {
+   // Update state first
+   feeGrowthGlobal0X128 += calculateFees();
+   feeGrowthGlobal1X128 += calculateFees();

    // Transfer tokens and execute callback last
    IKatanaV3FlashCallback(msg.sender).katanaV3FlashCallback(...);
}
```
2. Add reentrancy guard specific to flash loans
```solidity
bool private flashLoanLocked;
modifier noFlashLoanReentrancy() {
    require(!flashLoanLocked, "No flash loan reentrancy");
    flashLoanLocked = true;
    _;
    flashLoanLocked = false;
}
```
3. Consider implementing a flash loan borrow limit to mitigate impact of potential exploits.
