# Vulnerability details

The fee growth calculation in the `swap` function incorrectly handles the order of operations between protocol fee deduction and fee growth updates. When protocol fees are enabled, the fee amount is reduced after the global fee growth is updated, leading to inconsistent fee growth values.

[swap#L648-L650](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Pool.sol#L648-L650) && [swap#641-L645](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Pool.sol#L641-L645)
```solidity
// <@Issue: Fee growth can decrease when updating global fee tracker
if (state.liquidity > 0) {
    state.feeGrowthGlobalX128 += FullMath.mulDiv(step.feeAmount, FixedPoint128.Q128, state.liquidity);
}

// <@Issue: Incorrect fee growth update after protocol fee deduction
if (cache.feeProtocolNum > 0) {
    uint256 delta = FullMath.mulDiv(step.feeAmount, cache.feeProtocolNum, cache.feeProtocolDen);
    step.feeAmount -= delta;
    state.protocolFee += uint128(delta);
}
```
**Impact**

* LP providers receive incorrect fee calculations
* Fee growth can decrease instead of monotonically increasing
* Protocol fee accounting becomes inaccurate
* Position values can be miscalculated

**Causes**

1. Protocol fee deduction happens after fee growth update
2. Fee growth uses the full amount before protocol fee is removed
3. No validation ensuring fee growth remains monotonically increasing
4. Lack of proper state management between fee updates

**Likelihood: High - This occurs whenever**

* Protocol fees are enabled (`feeProtocolNum > 0`)
* Swaps happen across price ranges
* Multiple LPs are providing liquidity

## Proof of Concept
The key issue is that when protocol fees are enabled, the `step.feeAmount` is reduced by the protocol fee portion before calculating the fee growth. This can lead to a situation where:

1. The initial fee growth is calculated based on the full fee amount
2. Protocol fee is deducted
3. The new fee growth is calculated with the reduced amount
4. This results in a lower fee growth value than before

The vulnerability manifests in the test file when protocol fees are enabled: [test_swap#L118-L123](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/test/core/KatanaV3Pool.t.sol#L118-L123)

## Recommended Mitigation Steps
The calculation should take into account the fees accrued during the swap and distribute them proportionally based on the liquidity at each tick.

We can implement the following
```diff
- if (state.liquidity > 0) {
-     state.feeGrowthGlobalX128 += FullMath.mulDiv(step.feeAmount, FixedPoint128.Q128, state.liquidity);
- }
- 
- if (cache.feeProtocolNum > 0) {
-     uint256 delta = FullMath.mulDiv(step.feeAmount, cache.feeProtocolNum, cache.feeProtocolDen);
-     step.feeAmount -= delta;
-     state.protocolFee += uint128(delta);
- }

+ // Calculate protocol fee first
+ uint256 protocolDelta = 0;
+ if (cache.feeProtocolNum > 0) {
+     protocolDelta = FullMath.mulDiv(step.feeAmount, cache.feeProtocolNum, cache.feeProtocolDen);
+     state.protocolFee += uint128(protocolDelta);
+ }
+ 
+ // Update fee growth with remaining amount
+ if (state.liquidity > 0) {
+     uint256 remainingFee = step.feeAmount - protocolDelta;
+     state.feeGrowthGlobalX128 += FullMath.mulDiv(remainingFee, FixedPoint128.Q128, state.liquidity);
+ }
```
This ensures protocol fees are deducted before updating fee growth, maintaining consistent and monotonic fee growth values.
