# Vulnerability details

## Proof of Concept
The `CREATE2` opcode in Solidity allows for the deterministic deployment of contracts based on a combination of the deployer's address, an initialization code hash, and a salt. While this can be beneficial in scenarios where predictable addresses are useful, improper use of `CREATE2` can lead to critical vulnerabilities, especially when predictable addresses are combined with insufficient security controls.

The following code snippet demonstrates the incorrect use of `CREATE2` that makes the contract vulnerable to front-running and replay attacks:
https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3PoolDeployer.sol#L31-L40
```solidity
// Vulnerable deployment using CREATE2
function deploy(address factory, address token0, address token1, uint24 fee, int24 tickSpacing)
    internal
    returns (address pool)
{
    bytes32 salt = keccak256(abi.encode(token0, token1, fee));
    bytes memory creationCode = IKatanaV3PoolBeaconImmutables(beacon).POOL_PROXY_INIT_CODE();
    pool = Create2.deploy(0, salt, creationCode);
}
```
The `salt` is derived deterministically from the token addresses (`token0, token1`) and `fee`. This makes the pool contract address predictable and prone to front-running or replay attacks.

An attacker can precompute the contract's address using the known `salt`, `factory address`, and initialization code hash before the legitimate pool deployment.
```solidity
bytes32 salt = keccak256(abi.encode(token0, token1, fee));
address predictedAddress = address(uint256(keccak256(abi.encodePacked(
    hex"ff", factory, salt, keccak256(creationCode)
))));
```
The attacker can then front-run the transaction by deploying their own malicious contract at the predicted address using `CREATE2`, ensuring that their contract is deployed at the same address where the legitimate contract would have been deployed.

Once the malicious contract is deployed, the legitimate deployment will fail, or even worse, users might interact with the malicious contract thinking it is the real one.

## Impact
1. Front-Running Attack
Attack Scenario: An attacker precomputes the address of the pool contract and deploys their own malicious contract at that address before the legitimate contract is deployed.
Impact: This could lead to loss of funds or incorrect user interactions with a counterfeit pool, as users may not realize they are interacting with the wrong contract.
2. Replay Attacks
Attack Scenario: Even after a legitimate contract is deployed, an attacker can later redeploy the same contract at the same address using the same salt, leading to potential state manipulations or contract tampering.
Impact: This could affect the integrity of the smart contract ecosystem by introducing instability and distrust in pool deployments.
3. Counterfeit Pool Deployment
Attack Scenario: Attackers can create counterfeit pools with the same address as a legitimate pool, manipulating users into interacting with the wrong contract.
Impact: Loss of funds, user trust issues, and network-wide disruption.

## Recommended Mitigation Steps
1. To prevent precomputing contract addresses, introduce additional randomness (e.g., a nonce or timestamp) to the `salt` generation. This ensures that the `CREATE2` deployment is unpredictable.
```solidity
bytes32 salt = keccak256(abi.encode(token0, token1, fee, block.timestamp));
```
2. Ensure that only authorized actors (e.g., the factory contract or governance contract) can trigger pool deployments.
```solidity
modifier onlyFactory() {
    require(msg.sender == factory, "Not authorized");
    _;
}
```
3. Implement a whitelist system where only known addresses are allowed to interact with the deployed contract, preventing malicious actors from interacting with the counterfeit pool.
```solidity
mapping(address => bool) public whitelist;

function addToWhitelist(address user) external onlyFactory {
    whitelist[user] = true;
}
```
