# Vulnerability details

## Proof of Concept
Reentrancy Vulnerability: Reentrancy vulnerabilities occur when a contract allows an external call to another contract that can modify its state before the initial execution completes. In this contract, while the isNotLocked modifier does not explicitly perform any external calls, the use of state variables (like lockedBy) before completing the function execution could allow reentrancy under certain conditions.

Proof of Concept: Consider a situation where the map function is used in a contract that calls an external contract that can call back into LockAndMsgSender. If the external contract has a fallback function that re-invokes the original function before the lock state resets, it can lead to unexpected results.
contract Attacker {
    LockAndMsgSender public target;

    constructor(address _target) {
        target = LockAndMsgSender(_target);
    }

    function attack() external {
        target.someFunction();  // Calls a function that uses isNotLocked
    }

    fallback() external {
        target.someFunction();  // Re-enter the function
    }
}
Impact: An attacker can exploit this to repeatedly call a function that should be protected, potentially draining funds or altering states unintentionally.

## Recommended Mitigation Steps
1. Use a reentrancy guard that prevents any reentrant calls, such as OpenZeppelin’s ReentrancyGuard.
2. Ensure state variables are updated before any external calls.
