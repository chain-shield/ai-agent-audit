# Vulnerability details

## Proof of Concept
The observation array has 65535 elements (indices 0-65534), but `uint16` allows values up to 65535, creating an off-by-one error when attempting to use the maximum `uint16` value.

[KatanaV3Pool.sol.increaseObservationCardinalityNext#L235-L240](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Pool.sol#L235-L242), [KatanaV3Pool.sol.increaseObservationCardinalityNext#L78](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Pool.sol#L78)
```solidity
  function increaseObservationCardinalityNext(uint16 observationCardinalityNext) external override lock {
    uint16 observationCardinalityNextOld = slot0.observationCardinalityNext; // for the event
    uint16 observationCardinalityNextNew = observations.grow(observationCardinalityNextOld, observationCardinalityNext); // <@Issue: Array bounds exceeded when observationCardinalityNext = maxUint16
    slot0.observationCardinalityNext = observationCardinalityNextNew;
    if (observationCardinalityNextOld != observationCardinalityNextNew) {
      emit IncreaseObservationCardinalityNext(observationCardinalityNextOld, observationCardinalityNextNew);
    }
  }

  /// @inheritdoc IKatanaV3PoolState
  Oracle.Observation[65535] public override observations; // <@Issue: Fixed array size prevents using max uint16
```
**The core issue stems from the mismatch between:-**

1. The fixed array size of 65535 elements
2. The uint16 parameter that can reach 65535
3. Zero-based array indexing meaning max valid index is 65534

This creates an edge case where setting the maximum `uint16` value will revert due to array bounds, even though the type supports that value.

The vulnerability is triggered when calling `increaseObservationCardinalityNext()` with the maximum uint16 value (65535), causing an array bounds violation.

The likelihood is high for pools requiring maximum observation capacity

```solidity
function testMaxCardinalityFails() public {
    uint16 maxUint16 = type(uint16).max; // 65535
    
    // This will revert due to array bounds
    vm.expectRevert();
    pool.increaseObservationCardinalityNext(maxUint16);
    
    // But this works
    pool.increaseObservationCardinalityNext(maxUint16 - 1); // 65534
}
```
Connects to critical oracle price tracking functionality used by:

* Price feeds
* TWAP calculations
* Position management
* Swap execution

This creates a systemic risk for protocols relying on maximum observation capacity for accurate price tracking.

## Impact
* During high volatility periods when maximum observations are needed, the pool cannot utilize its full intended capacity.
* Reduced observation capacity can impact time-weighted average price (TWAP) calculations.
* Attempts to use maximum capacity will revert, potentially disrupting critical operations.
* Protocols relying on maximum observation capacity for price tracking may face unexpected behavior.

## Recommended Mitigation Steps
Two potential fixes:

1. Increase array size to accommodate full uint16 range
```diff
- Oracle.Observation[65535] public override observations;
+ Oracle.Observation[65536] public override observations;
```
2. Add input validation:
```diff
function increaseObservationCardinalityNext(uint16 observationCardinalityNext) external override lock {
+   require(observationCardinalityNext < type(uint16).max, "Max cardinality exceeded");
    uint16 observationCardinalityNextOld = slot0.observationCardinalityNext;
    uint16 observationCardinalityNextNew = observations.grow(observationCardinalityNextOld, observationCardinalityNext);
    slot0.observationCardinalityNext = observationCardinalityNextNew;
    if (observationCardinalityNextOld != observationCardinalityNextNew) {
        emit IncreaseObservationCardinalityNext(observationCardinalityNextOld, observationCardinalityNextNew);
    }
}
```
I recommend the second approach as it provides bounds checking while maintaining the existing array structure.
