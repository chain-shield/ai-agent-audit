# Vulnerability details

## Proof of Concept
When updating a position with a negative `liquidityDelta` (i.e., removing liquidity), the function checks if the lower and upper ticks were flipped (liquidity changed from zero to non-zero or vice versa). If a tick was flipped, its data is cleared using `ticks.clear(tickLower)` or `ticks.clear(tickUpper)`. However, this clearing happens unconditionally, without checking if the liquidity at the tick has reached zero.
This can leave a tick in an inconsistent state where it has non-zero liquidity but is not marked as initialized.

In `KatanaV3Pool.sol`, in the `_updatePosition` function, lines [399-405](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Pool.sol#L399-L407)
```solidity
// clear any tick data that is no longer needed
if (liquidityDelta < 0) { // <= FOUND
    if (flippedLower) {
        ticks.clear(tickLower); // <= FOUND
    }
    if (flippedUpper) {
        ticks.clear(tickUpper); // <= FOUND
    }
}
```
1. Alice initializes a new `KatanaV3Pool` with a starting price of 1 (e.g., using `initialize(encodePriceSqrt(1, 1))`).
2. Alice mints a new position with a wide tick range that includes tick 0 (e.g., `mint(address(this), -10000, 10000, 1e18, "")`).
3. Alice decreases the position's liquidity by an amount that flips tick 0 but doesn't bring its liquidity to zero (e.g., `burn(-10000, 10000, 5e17)`).
4. Alice calls ticks(0) to check the state of tick 0.

**Expected result**: `ticks(0)` should return a struct with `liquidityGross > 0` and `initialized = true`.
**Actual result**: `ticks(0)` returns a struct with `liquidityGross > 0` but `initialized = false`, indicating an inconsistent state.

It specifically affects the consistency of tick data when liquidity is removed from a position. Inconsistent tick state can lead to incorrect calculations and behavior in other parts of the contract that rely on accurate tick data.

Because the `_updatePosition` function unconditionally clears the tick data when the `liquidityDelta` is negative, and a tick is flipped. The function does not check if the liquidity at the tick has reached zero before clearing the data. This can happen when a position is updated with a negative `liquidityDelta`, and the liquidity change flips a tick but doesn't bring its liquidity to zero, which is a relatively common scenario, especially in pools with concentrated liquidity and frequent position updates.

## Recommended Mitigation Steps
Update the `_updatePosition` function to only clear the tick data when the liquidity at the tick reaches zero by adding the condition to check if the liquidityGross is zero before clearing the tick data.
```diff
if (liquidityDelta < 0) {
-   if (flippedLower) {
+   if (flippedLower && ticks[tickLower].liquidityGross == 0) {
        ticks.clear(tickLower);
    }
-   if (flippedUpper) {
+   if (flippedUpper && ticks[tickUpper].liquidityGross == 0) {
        ticks.clear(tickUpper);
    }
}
```
