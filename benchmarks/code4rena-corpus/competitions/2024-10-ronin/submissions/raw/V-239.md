# Vulnerability details

## Summary

The KatanaV3Pool's swap function implements a loop-based price traversal system that can potentially consume significant amounts of memory when processing large swaps across multiple price ranges. At the heart of this issue lies the interaction between memory allocation patterns and Ethereum's block gas limits.

Let's examine the relevant code structure:

```solidity
function swap(
    address recipient,
    bool zeroForOne,
    int256 amountSpecified,
    uint160 sqrtPriceLimitX96,
    bytes calldata data
) external override returns (int256 amount0, int256 amount1) {
    SwapCache memory cache = SwapCache({
        liquidityStart: liquidity,
        blockTimestamp: _blockTimestamp(),
        fee: fee,
        feeProtocolNum: slot0Start.feeProtocolNum,
        feeProtocolDen: slot0Start.feeProtocolDen,
        tickSpacing: tickSpacing,
        secondsPerLiquidityCumulativeX128: 0,
        tickCumulative: 0,
        computedLatestObservation: false
    });

    SwapState memory state = SwapState({
        amountSpecifiedRemaining: amountSpecified,
        amountCalculated: 0,
        sqrtPriceX96: slot0Start.sqrtPriceX96,
        tick: slot0Start.tick,
        feeGrowthGlobalX128: zeroForOne ? feeGrowthGlobal0X128 : feeGrowthGlobal1X128,
        protocolFee: 0,
        liquidity: cache.liquidityStart
    });

    while (state.amountSpecifiedRemaining != 0 && state.sqrtPriceX96 != sqrtPriceLimitX96) {
        StepComputations memory step;
        // ... step initialization and computation logic
    }
}
```

The problem manifests in how memory is allocated and managed during swap execution. For each iteration of the while loop, a new `StepComputations` struct is allocated in memory:

```solidity
struct StepComputations {
    uint160 sqrtPriceStartX96;
    int24 tickNext;
    bool initialized;
    uint160 sqrtPriceNextX96;
    uint256 amountIn;
    uint256 amountOut;
    uint256 feeAmount;
}
```

When a large swap occurs, particularly one that crosses many tick boundaries, the function creates numerous `StepComputations` instances. Consider a scenario where a swap moves the price significantly, crossing hundreds of initialized ticks:

```solidity
// Example scenario:
// Starting at tick 100000
// Ending at tick 95000
// With ticks initialized every 60 ticks (standard 0.3% fee tier)
// This would result in approximately 83 iterations (5000/60)

while (state.amountSpecifiedRemaining != 0 && state.sqrtPriceX96 != sqrtPriceLimitX96) {
    StepComputations memory step;  // New memory allocation each iteration
    
    step.sqrtPriceStartX96 = state.sqrtPriceX96;
    
    (step.tickNext, step.initialized) = tickBitmap.nextInitializedTickWithinOneWord(
        state.tick,
        cache.tickSpacing,
        zeroForOne
    );
    
    // More memory operations within the loop...
    // Each iteration also involves complex calculations and state updates
}
```

The memory pressure becomes particularly acute because each iteration not only allocates the `StepComputations` struct but also performs various other memory operations:

1. Computing the next sqrt price:
```solidity
step.sqrtPriceNextX96 = TickMath.getSqrtRatioAtTick(step.tickNext);
```

2. Computing swap steps:
```solidity
(state.sqrtPriceX96, step.amountIn, step.amountOut, step.feeAmount) = SwapMath.computeSwapStep(
    state.sqrtPriceX96,
    targetPrice,
    state.liquidity,
    state.amountSpecifiedRemaining,
    cache.fee
);
```

3. Oracle updates when crossing initialized ticks:
```solidity
if (!cache.computedLatestObservation) {
    (cache.tickCumulative, cache.secondsPerLiquidityCumulativeX128) = observations.observeSingle(
        cache.blockTimestamp,
        0,
        slot0Start.tick,
        slot0Start.observationIndex,
        cache.liquidityStart,
        slot0Start.observationCardinality
    );
    cache.computedLatestObservation = true;
}
```

This creates several potential issues:

1. **Gas Limit Violations**: A sufficiently large swap could require so many iterations that it exceeds the block gas limit. This isn't just theoretical - in volatile market conditions where prices move significantly, a swap could easily need to traverse thousands of ticks.

2. **Memory Expansion Costs**: Ethereum's memory expansion costs grow quadratically. Each new memory allocation increases the cost of subsequent allocations, creating a compounding effect in gas costs.

3. **Denial of Service Vector**: A malicious actor could intentionally construct swaps that require maximum tick traversal, effectively creating a temporary denial of service by making swaps prohibitively expensive or impossible due to gas limits.

Here's a concrete example of how this could manifest:

```solidity
// Malicious swap construction
function executeHighMemorySwap() external {
    // Configure swap to cross maximum number of initialized ticks
    int24 startTick = 887272; // Near maximum tick
    uint160 sqrtPriceLimitX96 = TickMath.getSqrtRatioAtTick(-887272); // Near minimum tick
    
    pool.swap(
        address(this),
        true,  // zeroForOne
        type(int256).max,  // Maximum input amount
        sqrtPriceLimitX96,
        ""
    );
}
```

A recommended mitigation strategy would be to implement a maximum tick traversal limit:

```solidity
function swap(
    address recipient,
    bool zeroForOne,
    int256 amountSpecified,
    uint160 sqrtPriceLimitX96,
    bytes calldata data
) external override returns (int256 amount0, int256 amount1) {
    // ... existing initialization ...
    
    uint16 ticksTraversed = 0;
    uint16 constant MAX_TICK_TRAVERSAL = 1024; // Configurable limit
    
    while (state.amountSpecifiedRemaining != 0 && 
           state.sqrtPriceX96 != sqrtPriceLimitX96 &&
           ticksTraversed < MAX_TICK_TRAVERSAL) {
           
        StepComputations memory step;
        // ... existing swap logic ...
        
        ticksTraversed++;
    }
    
    // Ensure swap was completed
    require(
        state.amountSpecifiedRemaining == 0 || state.sqrtPriceX96 == sqrtPriceLimitX96,
        "Max tick traversal exceeded"
    );
}
```

This solution provides a safety rail against excessive memory usage while still allowing for substantial price movements. The MAX_TICK_TRAVERSAL value would need to be carefully chosen based on:
- Typical usage patterns
- Gas cost analysis
- Desired maximum price impact
- Block gas limit considerations

By implementing such a limit, we protect against potential DOS attacks while ensuring the protocol remains usable for legitimate trading activity. The tradeoff is that some large swaps might need to be broken into multiple transactions, but this is preferable to the potential for transaction failure or excessive gas costs.
