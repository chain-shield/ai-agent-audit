# Vulnerability details

For context, the vulnerable function in NonfungibleTokenPositionDescriptor.sol is here: 


```solidity
function tokenRatioPriority(address token, uint256 chainId) public view returns (int256) {
    if (token == WRON) {
      return TokenRatioSortOrder.DENOMINATOR;
    }
    if (chainId == 2020) {
      if (token == USDC) {
        return TokenRatioSortOrder.NUMERATOR_MOST;
      } else if (token == WETH) {
        return TokenRatioSortOrder.NUMERATOR_MORE;
      } else if (token == WBTC) {
        return TokenRatioSortOrder.DENOMINATOR_MOST;
      } else {
        return 0;
      }
    }
    return 0;
  }
```
The `flipRatio` function calls `tokenRatioPriority` twice, once for each input token (`token0` and `token1`). It then compares the returned values to determine the priority order. 

However, there is no check on whether `tokenRatioPriority` returns a valid value. If `tokenRatioPriority` returns an unexpected or invalid value (e.g., due to an error in its logic), it leads to incorrect comparisons, and potentially unintended behavior in `flipRatio`.

There is a lack of input validation within the `tokenRatioPriority` function, leading to an integer overflow.  While the exact impact depends on how `tokenRatioPriority` is implemented, a return value outside the expected range could disrupt the intended comparison logic in `flipRatio`, potentially leading to unexpected behavior, and an integer overflow.

Any token address or chainId can be passed into the `tokenRatioPriority` function, and if the parameters are manipulated with high values, the integer limits of int256 may be exceeded due to the lack of boundary checks, leading to overflow.

The tokenRatioPriority function in NonfungibleTokenPositionDescriptor.sol allows external calls to set arbitrary values for token and chainId without validation. In particular, the function returns priority values based on predefined token mappings (e.g., WRON, USDC), and checks if the chainId matches a specific ID (e.g., 2020).
