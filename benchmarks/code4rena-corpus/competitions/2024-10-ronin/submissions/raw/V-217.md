# Vulnerability details

## Summary
The NonfungiblePositionManager's positions() function returns potentially invalid tick values without validating against current pool requirements, leading to inconsistencies between stored position data and protocol rules.

## Impact
This issue can cause:
- Integration contract failures
- Incorrect position valuations 
- Failed trading strategies
- Invalid market making ranges
- System-wide inconsistencies in position management

## Description
The NonfungiblePositionManager allows positions to exist with tick values that may violate current pool tick spacing requirements. This occurs due to the relationship between three key components:

1. The Factory contract defines valid tick spacings for each fee tier:
```solidity
function initialize(address beacon_, address owner_, address treasury_) external {
    // 0.01% fee tier -> must use ticks in multiples of 1
    _enableFeeAmount(100, 1, 5, 10);     
    
    // 0.3% fee tier -> must use ticks in multiples of 60
    _enableFeeAmount(3000, 60, 5, 30);   
    
    // 1% fee tier -> must use ticks in multiples of 200
    _enableFeeAmount(10000, 200, 15, 100);
}
```

2. The Position Manager stores position ticks without validation against these spacings:
```solidity
struct Position {
    // ...
    int24 tickLower;
    int24 tickUpper;
    // ...
}

mapping(uint256 => Position) private _positions;
```

3. The positions() function blindly returns these ticks:
```solidity
function positions(uint256 tokenId) external view returns (...) {
    Position memory position = _positions[tokenId];
    require(position.poolId != 0, "Invalid token ID");
    PoolAddress.PoolKey memory poolKey = _poolIdToPoolKey[position.poolId];
    
    // Directly returns ticks without checking if they're valid for the pool's spacing
    return (
        position.nonce,
        position.operator,
        poolKey.token0,
        poolKey.token1,
        poolKey.fee,
        position.tickLower,  // Could be invalid
        position.tickUpper,  // Could be invalid
        // ...
    );
}
```

Here's why this is problematic:

Imagine a position created with the 0.01% fee tier (spacing = 1):
```solidity
// Initially valid position
tickLower = 5;    // Valid because 5 % 1 = 0
tickUpper = 10;   // Valid because 10 % 1 = 0
```

The factory allows governance to update fee tier settings:
```solidity
function enableFeeAmount(
    uint24 fee, 
    int24 tickSpacing,
    uint8 feeProtocolNum,
    uint8 feeProtocolDen
) public override onlyOwner {
    require(tickSpacing > 0 && tickSpacing < 16384, "KatanaV3Factory: INVALID_TICK_SPACING");
    feeAmountTickSpacing[fee] = tickSpacing;
    // ...
}
```

If governance updates the 0.01% fee tier to use spacing of 60:
```solidity
// Later: Update 0.01% fee tier
factory.enableFeeAmount(100, 60, 5, 10);  // Same fee, new spacing
```

Now we have a problem:
- The position's ticks (5,10) are stored in the Position struct
- These ticks don't align with the new spacing requirement (not multiples of 60)
- positions() function returns these invalid ticks without any warning
- Integrators assume returned ticks are valid for current pool rules

For instance, a contract using the position data might break:
```solidity
// This integration will fail
(,,,, uint24 fee, int24 tickLower, int24 tickUpper,,,,) = 
    positionManager.positions(tokenId);
    
int24 spacing = factory.feeAmountTickSpacing(fee);

// Fails because 5 % 60 != 0 and 10 % 60 != 0
require(tickLower % spacing == 0, "Invalid tick");
require(tickUpper % spacing == 0, "Invalid tick");
```


When governance updates a fee tier's tick spacing, positions created under previous rules may become invalid under new requirements. For example, if a 0.01% fee tier's spacing changes from 1 to 60, positions with ticks like 5 and 10 become invalid as they're not multiples of 60.

The positions() function continues returning these invalid values without any indication of their non-compliance, breaking a fundamental protocol invariant where ticks should always align with current spacing rules.

## Scenario
The issue manifests when:
1. A position is created with valid ticks under initial spacing rules
2. Governance updates the fee tier's tick spacing requirement
3. The position's ticks no longer comply with new spacing rules
4. positions() returns non-compliant values
5. Integrating systems assume returned ticks are valid
6. Operations fail or produce incorrect results due to invalid ticks

## Proof of Concept
1. Create position with 0.01% fee tier (spacing=1) using ticks 5,10
2. Governance updates 0.01% fee tier to spacing=60
3. Query position - returns ticks 5,10 without warning
4. Integrator assumes ticks are valid multiples of 60
5. Integration operations fail due to invalid tick spacing

## Fix Recommendation
The positions() function should at minimum:
1. Check ticks against current pool spacing
2. Validate tick range (-887272 to 887272)
3. Ensure tickLower < tickUpper
4. Return a flag indicating if the position's ticks are valid for current pool settings

This would allow integrators to handle invalid positions appropriately while maintaining backward compatibility with historical positions.
