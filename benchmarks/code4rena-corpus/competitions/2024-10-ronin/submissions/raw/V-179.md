# Vulnerability details

## Proof of Concept

For context, there exists an initialization logic vulnerability in the code exists here:

```solidity
    constructor(address poolImplementation) UpgradeableBeacon(poolImplementation) { }
```

The constructor of the `KatanaV3PoolBeacon` contract directly initializes the `UpgradeableBeacon` contract with the provided `poolImplementation` address. This approach lacks robust input validation for the `poolImplementation` parameter. An attacker can provide a malicious contract address during the beacon's deployment, leading to unintended consequences such as unauthorized code execution or manipulation of the pool's functionality.

This vulnerability is related to insufficient input validation in the constructor of the `KatanaV3PoolBeacon` contract.  Passing a malicious contract address to the `poolImplementation` parameter allows an attacker to control the behavior of the deployed pool proxy contracts through the `UpgradeableBeacon`.  

This lack of input verification creates a potential security gap, as an attacker can supply a malicious contract address, allowing unauthorized code execution or control over the beacon, and its linked proxy contracts.

Function Analysis and Potential Exploitation
The constructor setup:
```solidity
constructor(address poolImplementation) UpgradeableBeacon(poolImplementation) { }
```
immediately registers the poolImplementation as the upgradeable implementation without ensuring it is a legitimate, verified contract. 

This allows an attacker, during deployment, to provide an untrusted address, which the beacon then adopts as its implementation. This setup poses risks because beacon proxies, which delegate all calls to the UpgradeableBeacon, would rely on a malicious implementation, allowing arbitrary code execution, or unauthorized control of pool interactions.

Attack path via function calls analysis (eg, is this vuln exploitable):
---

Examining the function call analysis and exploitability of this vuln, there is a direct call vulnerability, as follows, in two main attack paths.

While UpgradeableBeacon enforces an owner-only upgradeTo() function, the initial setup in the constructor doesn’t validate poolImplementation as a legitimate contract, making it exploitable during the initial deployment.

There also exists indirect call risks via proxy patterns. Since beacon proxies use delegatecall to this implementation, all proxies relying on KatanaV3PoolBeacon would execute code in the attacker's implementation context if exploited, potentially affecting pool management, liquidity, or any delegated logic.

## Recommended Mitigation Steps

To protect against this initialization logic vulnerability, I'd recommend the following mitigations.

--> Require devs to do address validation in the constructor

Require devs to verify that poolImplementation is a legitimate contract by checking the code size, ensuring no unverified addresses are set as the beacon’s implementation.

For example, do something like this:
```solidity

constructor(address poolImplementation) UpgradeableBeacon(poolImplementation) {
    require(poolImplementation.code.length > 0, "Invalid implementation: must be a contract");
}
```


--> Require devs to prevent unauthorized initialization with OpenZeppelin’s _disableInitializers()

Use _disableInitializers() in the UpgradeableBeacon setup to prevent the beacon from being initialized multiple times, or by unauthorized addresses, locking down the initialization process post-deployment.

For example, do something like this: 

```solidity 
import "@openzeppelin/contracts/proxy/utils/Initializable.sol";

constructor(address poolImplementation) UpgradeableBeacon(poolImplementation) {
    require(poolImplementation.code.length > 0, "Invalid implementation: must be a contract");
    _disableInitializers();
}
```

--> Restrict upgradeable implementations to only trusted contracts

Restrict upgradeTo to verified, whitelisted addresses, and conduct integrity checks on new implementations.  This could be done like this: 

```solidity 
function upgradeTo(address newImplementation) public override onlyOwner {
    require(newImplementation.code.length > 0, "Invalid contract for upgrade");
    _setImplementation(newImplementation);
}
```
