# Vulnerability details

## Proof of Concept
The bug is in the protocol fee ratio validation in KatanaV3Factory.sol. Let's break it down: [#L46-L73](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Factory.sol#L46-L74), [#L121-L124](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Factory.sol#L121-L126)
```solidity
function initialize(address beacon_, address owner_, address treasury_) external {
    require(beacon == address(0), "KatanaV3Factory: ALREADY_INITIALIZED");

    // @Issue - No validation of fee protocol ratios in _enableFeeAmount calls
    // These hardcoded values could set invalid fee ratios during initialization
    _enableFeeAmount(100, 1, 5, 10);
    _enableFeeAmount(3000, 60, 5, 30);
    _enableFeeAmount(10000, 200, 15, 100);
}

function _enableFeeAmount(uint24 fee, int24 tickSpacing, uint8 feeProtocolNum, uint8 feeProtocolDen) private {
    // @Issue - Missing validation of feeProtocolNum < feeProtocolDen
    // This allows setting invalid fee ratios that could exceed 100%
    feeAmountTickSpacing[fee] = tickSpacing;
    feeAmountProtocol[fee] = Fraction(feeProtocolNum, feeProtocolDen);
    emit FeeAmountEnabled(fee, tickSpacing, feeProtocolNum, feeProtocolDen);
}
```
This allows setting invalid protocol fee ratios during initialization that could exceed 100% of trading fees, bypassing the safety checks present in the public interface. This can lead to excessive fee extraction from users and unfair fee distribution between liquidity providers and the protocol.

While there is a check in the public [enableFeeAmount():#L115](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Factory.sol#L115)
```solidity
require(feeProtocolNum < feeProtocolDen, "KatanaV3Factory: INVALID_FEE_PROTOCOL");
```
The private `_enableFeeAmount()` function used in `initialize()` lacks this validation, allowing invalid fee ratios to be set during initialization.

Protocol fees could be set higher than 100% during initialization and this breaks core business logic assumptions.

1. Protocol Risk:
* Invalid fee ratios where numerator ≥ denominator could be set during initialization
* This allows protocol fees to exceed 100% of trading fees
* Breaks core business assumptions about fee distribution between LPs and protocol

2. User Impact:
* Users could lose excessive amounts to protocol fees
* Trading becomes economically unviable if protocol takes majority of fees
* Liquidity providers receive less than expected share of fees

The public `enableFeeAmount()` has proper validation, but bypassing it through initialization creates a dangerous inconsistency in the protocol's fee ratio guarantees.

## Recommended Mitigation Steps
Add validation in the private function to ensure consistent fee ratio enforcement across all code paths. Consider adding additional upper bounds on protocol fee ratios (e.g., max 50%) to maintain reasonable fee splits between protocol and LPs.
