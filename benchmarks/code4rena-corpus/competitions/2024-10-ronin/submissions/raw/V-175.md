# Vulnerability details

## Proof of Concept
`enableFeeAmount` function in KatanaV3Factory contains vulnerability where fee parameters can be manipulated through a race condition. An attacker can exploit the non-atomic nature of fee enabling operations to potentially override existing fee configurations, leading to inconsistent protocol fee states.

The core issue lies in the non-atomic operation between checking fee existence and enabling new fee parameters: [#L105-L118](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Factory.sol#L105-L118)
```solidity
function enableFeeAmount(uint24 fee, int24 tickSpacing, uint8 feeProtocolNum, uint8 feeProtocolDen) {
    // @Issue - Race condition: State check and modification are not atomic
    require(feeAmountTickSpacing[fee] == 0, "KatanaV3Factory: FEE_AMOUNT_ALREADY_ENABLED");

    // @Issue - Vulnerable state transition without proper synchronization
    _enableFeeAmount(fee, tickSpacing, feeProtocolNum, feeProtocolDen);
}
```
```solidity
function test_createPool() public {
    // @Issue - Test doesn't verify fee parameter integrity across concurrent operations
    address token0 = makeAddr("token0");
    address token1 = makeAddr("token1");
    uint24 fee = 3000;
}
```
The bug occurs because:

1. The contract attempts to prevent re-enabling fees through the check `require(feeAmountTickSpacing[fee] == 0)`
2. However, there's a potential race condition where this check could be bypassed if multiple transactions try to enable the same fee tier simultaneously

Further explained in the code

```solidity
function enableFeeAmount(uint24 fee, int24 tickSpacing, uint8 feeProtocolNum, uint8 feeProtocolDen)
    public
    override
    onlyOwner
  {
    // @Issue - Insufficient validation of fee protocol parameters
    // Current check only verifies numerator < denominator, but doesn't enforce minimum values
    // This could allow setting extremely low protocol fees, potentially near-zero
    require(feeProtocolNum < feeProtocolDen, "KatanaV3Factory: INVALID_FEE_PROTOCOL");

    // @Issue - Race condition vulnerability in fee enabling
    // The check for feeAmountTickSpacing[fee] == 0 and the actual enabling are not atomic
    require(feeAmountTickSpacing[fee] == 0, "KatanaV3Factory: FEE_AMOUNT_ALREADY_ENABLED");

    _enableFeeAmount(fee, tickSpacing, feeProtocolNum, feeProtocolDen);
  }
```
The vulnerability occurs because the check for existing fee tiers and the actual enabling operation are separate steps, creating a time window where the state can be manipulated. `The feeAmountTickSpacing[fee]` check and `_enableFeeAmount` call are not executed atomically.

## Recommended Mitigation Steps
Implement synchronization mechanisms for fee parameter modifications and validation checks for fee configurations. Consider implementing a time-lock mechanism for fee parameter changes and additional access controls for fee-related operations.
