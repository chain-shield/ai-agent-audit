# Vulnerability details


## Impact
The `KatanaV3PoolDeployer.deploy()` function does not validate the order of token addresses (`token0` and `token1`). If a pool is deployed with the token addresses in the wrong order, it may result in swaps being executed at incorrect prices. This could lead to significant financial losses for users interacting with the pool, as the price calculations depend on the correct ordering of tokens. Additionally, improper token order may disrupt the expected functionality of the liquidity pool, causing further user confusion and risk.

## Proof of Concept
Refer to the following code in GitHub:
- [KatanaV3PoolDeployer.sol](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3PoolDeployer.sol#L31-L40)

In the `deploy()` function, the tokens are passed as parameters without any validation:

```solidity
function deploy(address factory, address token0, address token1, uint24 fee, int24 tickSpacing)
    internal
    returns (address pool)
{
    parameters = Parameters({ factory: factory, token0: token0, token1: token1, fee: fee, tickSpacing: tickSpacing });
    ...
}
```

The absence of a check like `require(token0 < token1, "Token addresses must be sorted: token0 < token1");` allows the deployment of a pool where `token0` could be greater than `token1`. This scenario would lead to the following potential issues:
- Incorrect pricing during swaps, as AMM algorithms rely on the token order.
- Users may experience unintended consequences, such as executing swaps at inflated prices or not being able to swap at all.

## Tools Used
- Manual code review
## Recommended Mitigation Steps
1. **Implement Token Order Check**: Add a requirement to validate the order of the token addresses before proceeding with the pool deployment:
   ```solidity
   require(token0 < token1, "Token addresses must be sorted: token0 < token1");
   ```
