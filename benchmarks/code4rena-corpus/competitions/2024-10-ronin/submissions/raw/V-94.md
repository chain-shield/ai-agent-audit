# Vulnerability details

### Vulnerability Overview

The Oracle library serves a crucial function in managing a circular buffer of observations that track historical price and liquidity data within an AMM pool. Central to this process is the `write` function, which adds new observations to the buffer. Unfortunately, this function contains a significant flaw in its logic concerning the expansion of the observation array's cardinality, or size. Specifically, when the cardinality is increased, the function fails to properly initialize the newly allocated slots. This oversight can result in uninitialized data being read or gaps in the data, leading to serious implications for data integrity.

### Vulnerable Code 


```solidity
  function write(
    Observation[65535] storage self,
    uint16 index,
    uint32 blockTimestamp,
    int24 tick,
    uint128 liquidity,
    uint16 cardinality,
    uint16 cardinalityNext
  ) internal returns (uint16 indexUpdated, uint16 cardinalityUpdated) {
    Observation memory last = self[index];

    // early return if we've already written an observation this block
    if (last.blockTimestamp == blockTimestamp) return (index, cardinality);

    // if the conditions are right, we can bump the cardinality
    if (cardinalityNext > cardinality && index == (cardinality - 1)) {
      cardinalityUpdated = cardinalityNext;
    } else {
      cardinalityUpdated = cardinality;
    }

    indexUpdated = (index + 1) % cardinalityUpdated;
    self[indexUpdated] = transform(last, blockTimestamp, tick, liquidity);
  }
```

The problem arises when the function determines whether to increase the cardinality. If `cardinalityNext` exceeds the current cardinality, the function prematurely switches to using the new, larger cardinality without initializing the new slots in the observation array.

The first aspect to note is the condition that checks whether an increase in cardinality is warranted. This check only triggers when the next cardinality is greater than the current and the current index has reached the last filled slot. 

Next, the function calculates the new index for writing the observation. It does this using a modular arithmetic approach, which ensures it wraps around based on the updated cardinality. The observation is then written to the calculated index.

The critical flaw emerges during this process. For instance, if the cardinality is increased from 6 to 11, the function will skip over the newly available indices (6 through 10) and immediately write to index 6, leaving these slots uninitialized. 

### Implications of the Flaw

This vulnerability carries several significant risks. First and foremost, the presence of uninitialized slots in the observation array can lead to considerable gaps in historical data, which may hinder effective analysis and decision-making. Additionally, when functions attempt to read from these uninitialized slots—like `observe` or `observeSingle`—they may return inaccurate or zero values, which can compromise price or liquidity calculations. Finally, this inconsistency can disrupt the state of the oracle, potentially affecting various operations that rely on accurate historical data.

### A Practical Example

To illustrate the potential consequences, consider a scenario where the oracle begins with a cardinality of 6, fully occupying the slots from index 0 to 5. When the `cardinalityNext` value is set to 11 and a new observation is written, the function will move forward with the increased cardinality. As a result, the index for the next observation will be set to 6, but slots 7 to 10 will remain uninitialized. If a user subsequently requests historical data, expecting it to be stored in those slots, they will instead receive uninitialized data.

### Suggested Remediation

To address this issue effectively, the `write` function should be modified to ensure that all new slots are properly initialized when the cardinality is increased. Below is the revised code:

```solidity
function write(
    Observation[65535] storage self,
    uint16 index,
    uint32 blockTimestamp,
    int24 tick,
    uint128 liquidity,
    uint16 cardinality,
    uint16 cardinalityNext
) internal returns (uint16 indexUpdated, uint16 cardinalityUpdated) {
    unchecked {
        Observation memory last = self[index];

        if (last.blockTimestamp == blockTimestamp) return (index, cardinality);

        if (cardinalityNext > cardinality && index == (cardinality - 1)) {
            for (uint16 i = cardinality; i < cardinalityNext; i++) {
                self[i] = transform(last, blockTimestamp, tick, liquidity);
            }
            cardinalityUpdated = cardinalityNext;
        } else {
            cardinalityUpdated = cardinality;
        }

        indexUpdated = (index + 1) % cardinalityUpdated;
        self[indexUpdated] = transform(last, blockTimestamp, tick, liquidity);
    }
}
```

This fix introduces a loop that ensures all newly allocated slots are initialized appropriately, thereby preventing any gaps in the observation history and maintaining the integrity of the data.
