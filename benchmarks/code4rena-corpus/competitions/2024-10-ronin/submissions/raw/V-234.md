# Vulnerability details

## Summary

The mint function lacks slippage protection, making it vulnerable to MEV attacks, particularly sandwich attacks. When users add liquidity, there's no mechanism to specify minimum acceptable amounts for their provided liquidity, allowing trades to be front-run and back-run, potentially resulting in significant value extraction through price manipulation.

The core issue begins in the mint function's signature:

```solidity
function mint(
    address recipient,
    int24 tickLower,
    int24 tickUpper,
    uint128 amount,
    bytes calldata data
) external override lock returns (uint256 amount0, uint256 amount1)
```

Notice there are no parameters for minimum expected amounts. The function calculates token amounts internally through `_modifyPosition`:

```solidity
(, int256 amount0Int, int256 amount1Int) = _modifyPosition(
    ModifyPositionParams({
        owner: recipient,
        tickLower: tickLower,
        tickUpper: tickUpper,
        liquidityDelta: int256(amount).toInt128()
    })
);

amount0 = uint256(amount0Int);
amount1 = uint256(amount1Int);
```

Here's how an MEV bot could exploit this. Consider this attack contract:

```solidity
contract SandwichAttacker {
    IKatanaV3Pool public pool;
    IERC20 public token0;
    IERC20 public token1;
    
    constructor(address _pool, address _token0, address _token1) {
        pool = IKatanaV3Pool(_pool);
        token0 = IERC20(_token0);
        token1 = IERC20(_token1);
    }
    
    function executeSandwich(
        address victim,
        uint256 attackAmount,
        int24 victimTickLower,
        int24 victimTickUpper
    ) external {
        // 1. Front-run: Observe victim's pending mint transaction
        // 2. Execute large swap to move price unfavorably
        pool.swap(
            address(this),
            true, // zeroForOne
            int256(attackAmount),
            encodePriceSqrtX96(/* calculated target price */),
            "" // callback data
        );
        
        // 3. Victim's mint executes at worse price
        // (happens in next transaction)
        
        // 4. Back-run: Swap back at better price
        pool.swap(
            address(this),
            false, // zeroForOne
            -int256(attackAmount),
            encodePriceSqrtX96(/* calculated target price */),
            "" // callback data
        );
    }
}
```

Let's walk through a concrete example of how this plays out:

1. Alice wants to add liquidity to the ETH/USDC pool:
```solidity
// Alice's transaction
pool.mint(
    aliceAddress,
    -100, // tickLower
    100,  // tickUpper
    1000, // amount
    ""    // data
);
```

2. MEV bot sees this transaction in the mempool and calculates that by sandwiching it with two trades, they can extract value:

```solidity
// Step 1: Front-running swap (price manipulation)
pool.swap(
    attackerAddress,
    true,             // buy ETH
    largeAmount,      // size of attack
    targetPrice,      // calculated for maximum impact
    ""               // data
);

// Step 2: Alice's mint executes at manipulated price
// She gets fewer tokens than expected because there's no slippage protection

// Step 3: Back-running swap (profit taking)
pool.swap(
    attackerAddress,
    false,            // sell ETH back
    -largeAmount,     // reverse the position
    targetPrice,      // back to approximately original price
    ""               // data
);
```

The price path might look like this:
```
Initial price: 1 ETH = 2000 USDC
After front-run: 1 ETH = 2100 USDC (price manipulated up)
After Alice's mint: Still around 2100 USDC (Alice gets worse rate)
After back-run: 1 ETH = 2005 USDC (attacker profits from spread)
```

## Fix
To fix this vulnerability, we need to add slippage protection. Here's how we could modify the mint function:

```solidity
function mint(
    address recipient,
    int24 tickLower,
    int24 tickUpper,
    uint128 amount,
    uint256 amount0Min,  // Added parameter
    uint256 amount1Min,  // Added parameter
    bytes calldata data
) external override lock returns (uint256 amount0, uint256 amount1) {
    require(msg.sender == positionManager, "IPM");
    require(amount > 0);
    
    (, int256 amount0Int, int256 amount1Int) = _modifyPosition(
        ModifyPositionParams({
            owner: recipient,
            tickLower: tickLower,
            tickUpper: tickUpper,
            liquidityDelta: int256(amount).toInt128()
        })
    );

    amount0 = uint256(amount0Int);
    amount1 = uint256(amount1Int);
    
    // Add slippage protection
    require(amount0 >= amount0Min, "Price slippage check amount0");
    require(amount1 >= amount1Min, "Price slippage check amount1");
    
    // Rest of the function remains the same
    ...
}
```

This updated version allows users to specify their maximum acceptable slippage:

```solidity
// Alice's protected transaction
pool.mint(
    aliceAddress,
    -100,              // tickLower
    100,               // tickUpper
    1000,              // amount
    minAmount0,        // minimum acceptable token0 amount
    minAmount1,        // minimum acceptable token1 amount
    ""                 // data
);
```

Now if an MEV bot tries to sandwich the transaction and the resulting amounts would be less than `minAmount0` or `minAmount1`, the transaction reverts instead of executing at an unfavorable price.
