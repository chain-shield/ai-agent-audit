# Vulnerability details

## Proof of Concept
When we call the `IKatanaGovernance::isAuthorized` function in the `AuthorizationLib::checkPair` function, we pass it an `address[]` (array) instead of an `address` (single element). The signature of the `isAuthorized` function expects a `token` address and an `account` address, not several tokens. Passing a wrong argument like this to the `IKatanaGovernance::isAuthorized` function will always result in a runtime revert.
- Here is the `IKatanaGovernance::isAuthorized` function signature:
```solidity
i   nterface IKatanaGovernance {
  
        /// ... The other code

@>      function isAuthorized(address token, address account) external view returns (bool);
    
        /// ... The other code

    }
```
- And here is where me passed the wrong argument in the `AuthorizationLib::checkPair` function:
```solidity
    function checkPair(address governance, address token0, address token1) internal view {
@>      address[] memory tokens = new address[](2);
        tokens[0] = token0;
        tokens[1] = token1;
        // @audit type mismatch
@>      require(IKatanaGovernance(governance).isAuthorized(tokens, msg.sender), "UA");
    }
```

## Impact
The mismatch should result in either a compile-time error or runtime revert, preventing the function from being executed. However, if somehow deployed and bypassed, it could lead to critical security issues.

## Recommended Mitigation Steps
```diff
    function checkPair(address governance, address token0, address token1) internal view {
        address[] memory tokens = new address[](2);
        tokens[0] = token0;
        tokens[1] = token1;
-       require(IKatanaGovernance(governance).isAuthorized(tokens, msg.sender), "UA");
+       for (uint256 i = 0; i < tokens.length; i++) {
+           require(IKatanaGovernance(governance).isAuthorized(tokens[i], msg.sender), "UA");
+       }
    }
```
