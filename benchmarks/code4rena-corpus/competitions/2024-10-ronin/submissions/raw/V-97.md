# Vulnerability details

### Front-running Vulnerability in `swap` Function of **KatanaV3Pool.sol**

---

### **Proof of Concept**

#### Issue Summary:
The current implementation of the `swap` function in **KatanaV3Pool.sol** is vulnerable to **front-running attacks**. The slippage protection mechanism (`sqrtPriceLimitX96`) sets a limit on how much the price can change during a swap, but it does not prevent **transaction ordering manipulation** by malicious actors. Front-running occurs when an attacker detects a pending swap transaction in the public mempool and submits a competing transaction with a higher gas price, forcing the miner to execute the attacker’s transaction first. This allows the attacker to manipulate the price in their favor before the original transaction is processed.

#### Vulnerable Code:
The vulnerability lies in the lack of protection mechanisms within the core of the `swap` logic. Here’s the relevant part of the code from the **KatanaV3Pool.sol** contract:

```solidity
function swap(
    address recipient,
    bool zeroForOne,
    int256 amountSpecified,
    uint160 sqrtPriceLimitX96,
    bytes calldata data
) external override lock returns (int256 amount0, int256 amount1) {
    ...
    while (state.amountSpecifiedRemaining != 0 && state.sqrtPriceX96 != sqrtPriceLimitX96) {
        (state.sqrtPriceX96, step.amountIn, step.amountOut, step.feeAmount) = SwapMath.computeSwapStep(
            state.sqrtPriceX96,
            sqrtPriceLimitX96,
            state.liquidity,
            state.amountSpecifiedRemaining,
            feeProtocol
        );
        ...
        // Callback to the recipient's swap logic (external call)
        if (data.length > 0) IKatanaV3SwapCallback(msg.sender).katanaV3SwapCallback(amount0Delta, amount1Delta, data);
    }
}
```

1. **Price Movement During Swap**: 
   The `sqrtPriceLimitX96` parameter restricts how much the price can move within a swap transaction. However, this control is **ineffective against front-running**, since the price movement happens after the transaction is included in the mempool, and attackers can still exploit this gap by submitting competing transactions.

2. **External Call Vulnerability**:
   The `katanaV3SwapCallback` external function call introduces additional risk. Attackers may take advantage of the callback execution, especially if they can manipulate the order of execution in a block, impacting the price before the original transaction is finalized.

#### Example of a Front-running Attack:
Consider the following example:
1. **User Transaction**: A user initiates a swap to exchange a significant amount of Token A for Token B, setting a slippage limit to prevent price manipulation.
2. **Attacker Detection**: An attacker monitors the mempool and identifies the pending swap transaction.
3. **Attacker Exploit**: The attacker submits a swap transaction with a higher gas price, front-running the user’s swap and adjusting the pool’s price in their favor.
4. **User Loss**: When the original user’s transaction is processed after the attacker’s swap, the price has moved against them, causing them to receive fewer tokens than expected despite setting a slippage limit.

The attacker profits by manipulating the price for a short period, effectively **sandwiching** the user’s transaction.

#### Direct Code Example:
The `sqrtPriceLimitX96` prevents excessive slippage, but does nothing to prevent a front-running attack:

```solidity
while (state.amountSpecifiedRemaining != 0 && state.sqrtPriceX96 != sqrtPriceLimitX96) {
    (state.sqrtPriceX96, step.amountIn, step.amountOut, step.feeAmount) = SwapMath.computeSwapStep(
        state.sqrtPriceX96,
        sqrtPriceLimitX96,
        state.liquidity,
        state.amountSpecifiedRemaining,
        feeProtocol
    );
    ...
}
```

In this section, the pool’s price (`sqrtPriceX96`) is updated based on the remaining amount to be swapped. However, this occurs after the transaction has been included in the mempool, and attackers can manipulate this step by submitting a higher-priority transaction.

#### Potential Impact:
- **Slippage Controls**: While the contract prevents large slippage through the price limit, it is still vulnerable to minor, profitable front-running attacks.
- **Price Manipulation**: Attacks can cause the price to move briefly, allowing malicious users to profit by trading against the manipulated price.
- **User Loss**: Users who perform large swaps are more likely to experience adverse effects, such as receiving significantly fewer tokens than expected.

### **Recommended Mitigation Steps**

To mitigate front-running vulnerabilities in the `swap` function, several improvements can be implemented:

1. **Use of Flashbots or Private Transaction Methods**:
   Implement mechanisms for users to submit private transactions, such as **Flashbots**, to bypass the public mempool. By submitting transactions directly to miners, users can prevent front-runners from detecting and exploiting their swaps.

   - **Flashbots Integration**: Educate users to use Flashbots when performing large or sensitive transactions.

2. **Commit-Reveal Scheme**:
   Introduce a **commit-reveal** scheme for swaps. Users would first commit to a trade by submitting a hash of their trade parameters, which would be mined in one transaction. In the second transaction, they would reveal the details of the trade, and the swap would be executed. This two-step process hides the actual transaction details until execution, preventing front-runners from exploiting the trade.

   ```solidity
   function commitSwap(bytes32 commitment) external {
       // Store commitment hash
   }

   function revealSwap(bytes calldata swapData) external {
       // Validate commitment and execute swap
   }
   ```

3. **Time-weighted Average Price (TWAP)**:
   Incorporate a **TWAP mechanism** to smooth out price changes over time, reducing the impact of temporary price manipulations. By using TWAP, the contract ensures that the price used for swaps is an average over a certain time period, making it more resistant to short-term price fluctuations caused by front-runners.

   ```solidity
   uint256 twapPrice = getTWAPPrice(poolAddress);
   // Use twapPrice for swap calculations
   ```

4. **Front-running Resistance via Delay Mechanisms**:
   Consider adding a **small delay** between a transaction being submitted and when it can be executed. This makes it more difficult for front-runners to precisely predict the final price movement of a swap.

5. **User-defined Max Gas Price**:
   Allow users to define a **maximum gas price** they are willing to pay for their swap. By limiting the maximum gas price, users can make front-running less profitable for attackers, who rely on submitting transactions with higher gas fees to front-run the original transaction.

By implementing these strategies, the contract can effectively mitigate front-running vulnerabilities and provide users with a safer and more transparent trading experience.
