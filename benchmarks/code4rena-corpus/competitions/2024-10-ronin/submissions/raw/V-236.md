# Vulnerability details

## Summary
The mint function's balance checking mechanism is vulnerable to rebasing tokens, where token balances can change independently of transfers. The current implementation assumes token balances only change through explicit transfers, but rebasing tokens can modify balances automatically between the initial check and final verification, potentially leading to incorrect liquidity provisioning and pool imbalances.

In the KatanaV3Pool contract, the handling of token balances assumes traditional ERC20 behavior where balances only change through transfers. Let's examine how this assumption breaks down with rebasing tokens:

```solidity
function mint(
    address recipient,
    int24 tickLower,
    int24 tickUpper,
    uint128 amount,
    bytes calldata data
) external override lock returns (uint256 amount0, uint256 amount1) {
    // ... initial code ...
    
    // Balance checks that assume stable token amounts
    uint256 balance0Before;
    uint256 balance1Before;
    if (amount0 > 0) balance0Before = balance0();
    if (amount1 > 0) balance1Before = balance1();
    
    IKatanaV3MintCallback(msg.sender).katanaV3MintCallback(amount0, amount1, data);
    
    // Vulnerable balance validation
    if (amount0 > 0) require(balance0Before.add(amount0) <= balance0(), "M0");
    if (amount1 > 0) require(balance1Before.add(amount1) <= balance1(), "M1");
```

Let's look at how this interacts with a rebasing token. Here's a simplified rebasing token for illustration:

```solidity
contract RebasingToken is IERC20 {
    mapping(address => uint256) private _balances;
    uint256 private _totalSupply;
    uint256 private _rebaseMultiplier = 1e18;
    
    function balanceOf(address account) public view override returns (uint256) {
        // Balance increases over time
        return (_balances[account] * _rebaseMultiplier) / 1e18;
    }
    
    // Called periodically to increase all balances
    function rebase(uint256 newMultiplier) external {
        _rebaseMultiplier = newMultiplier;
    }
    
    function transfer(address to, uint256 amount) external override returns (bool) {
        // Transfers must account for rebasing
        uint256 rawAmount = (amount * 1e18) / _rebaseMultiplier;
        _balances[msg.sender] -= rawAmount;
        _balances[to] += rawAmount;
        return true;
    }
}
```

Now let's see how this creates problems. Consider this sequence of events:

```solidity
contract RebaseExploiter {
    IKatanaV3Pool pool;
    RebasingToken token;
    
    function demonstrateRebaseIssue(
        int24 tickLower,
        int24 tickUpper,
        uint128 amount
    ) external {
        // Step 1: Initial state
        uint256 initialBalance = token.balanceOf(address(pool));
        
        // Step 2: Begin mint process
        pool.mint(
            address(this),
            tickLower,
            tickUpper,
            amount,
            "" // callback data
        );
    }
    
    function katanaV3MintCallback(
        uint256 amount0,
        uint256 amount1,
        bytes calldata
    ) external {
        // Step 3: During callback, token rebases
        token.rebase(2e18); // Double all balances
        
        // Step 4: Transfer tokens to pool
        // But now the amounts are mismatched due to rebase
        token.transfer(address(pool), amount0);
    }
}
```

Let's walk through how this breaks the pool's accounting:

1. Initial State:
```solidity
// Pool has 1000 rebasing tokens
initialBalance = 1000

// User wants to mint with 100 tokens
amount0 = 100
```

2. During Mint Process:
```solidity
// Pool records initial balance
balance0Before = 1000

// Rebase occurs during callback (doubles all balances)
// Pool's actual balance is now 2000
```

3. Transfer and Verification:
```solidity
// User transfers 100 tokens
// But due to rebase, this is now worth 200 in old terms

// Final balance check:
require(balance0Before.add(amount0) <= balance0())
// Becomes:
require(1000 + 100 <= 2200)  // Passes, but accounting is wrong
```

The pool thinks it received 100 tokens worth of liquidity, but actually received 200 tokens worth due to the rebase. This leads to several issues:

1. Incorrect Liquidity Calculation:
```solidity
liquidity = LiquidityMath.addDelta(liquidityBefore, params.liquidityDelta);
// Liquidity token amount doesn't match actual value
```

2. Skewed Price Calculations:
```solidity
amount0 = SqrtPriceMath.getAmount0Delta(
    _slot0.sqrtPriceX96,
    TickMath.getSqrtRatioAtTick(params.tickUpper),
    params.liquidityDelta
);
// Amount calculations don't reflect real token values
```

## Fix
To fix this, we need to implement rebasing-aware balance checks. Here's one approach:

```solidity
function mint(
    address recipient,
    int24 tickLower,
    int24 tickUpper,
    uint128 amount,
    bytes calldata data
) external override lock returns (uint256 amount0, uint256 amount1) {
    // ... initial code ...
    
    // Track actual token amounts, not just balances
    uint256 balance0Before;
    uint256 balance1Before;
    uint256 token0Scale;
    uint256 token1Scale;
    
    if (amount0 > 0) {
        balance0Before = balance0();
        token0Scale = IRebasingToken(token0).getScale();
    }
    if (amount1 > 0) {
        balance1Before = balance1();
        token1Scale = IRebasingToken(token1).getScale();
    }
    
    IKatanaV3MintCallback(msg.sender).katanaV3MintCallback(amount0, amount1, data);
    
    // Adjust expectations based on any rebasing that occurred
    if (amount0 > 0) {
        uint256 newScale = IRebasingToken(token0).getScale();
        uint256 scaledAmount = amount0 * newScale / token0Scale;
        require(balance0Before.add(scaledAmount) <= balance0(), "M0");
    }
    if (amount1 > 0) {
        uint256 newScale = IRebasingToken(token1).getScale();
        uint256 scaledAmount = amount1 * newScale / token1Scale;
        require(balance1Before.add(scaledAmount) <= balance1(), "M1");
    }
    
    // Update pool accounting to account for rebasing
    _updateRebaseTracking();
}
```

Additionally, the pool should implement regular rebase synchronization:

```solidity
function _updateRebaseTracking() internal {
    // Update stored ratios of token amounts
    // Adjust internal accounting for new token scales
    // Potentially adjust liquidity calculations
}
```

This fix helps ensure:
- Pool accounting remains accurate despite rebases
- Liquidity providers receive fair value
- Price calculations remain accurate
- Pool remains balanced between tokens

However, supporting rebasing tokens adds significant complexity and may still have edge cases. Some protocols choose to explicitly disallow rebasing tokens rather than handle all these cases.
