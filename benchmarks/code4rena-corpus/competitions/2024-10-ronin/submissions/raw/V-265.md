# Vulnerability details

## Description

The following function is responsible for deploying a pool with the given parameters:
```
function deploy(address factory, address token0, address token1, uint24 fee, int24 tickSpacing) internal returns (address pool) {
    parameters = Parameters({ factory: factory, token0: token0, token1: token1, fee: fee, tickSpacing: tickSpacing });
    bytes memory creationCode = IKatanaV3PoolBeaconImmutables(beacon).POOL_PROXY_INIT_CODE();
    bytes32 salt = keccak256(abi.encode(token0, token1, fee));
    pool = Create2.deploy(0, salt, creationCode);
    delete parameters;
}
```
## Issue Overview

The vulnerability arises from the use of the `Create2` opcode, which allows for deterministic contract address generation. Specifically, a malicious actor can preemptively deploy a pool with specific token pairs and fee parameters by calculating the deterministic address. This results in a denial-of-service condition for legitimate actors attempting to deploy pools with the same parameters, as the `Create2` deployment fails due to the existing contract at that address.

## Impact

* Denial of Service: The use of `Create2` to generate deterministic pool addresses can be exploited by a malicious actor to deploy pools with popular token pairs ("hot tokens") and desirable fee parameters.

* This prevents legitimate users from creating pools with the same tokens and fees since `Create2` prevents deployment if the address is already occupied, leading to a system crash or failed transaction attempts.

* As a result, this attack could hinder the creation of key liquidity pools and negatively impacts the usability of the protocol.

## Exploit Scenario

1. A malicious actor identifies popular token pairs and fees that are expected to be in high demand.

2. They use the `Create2` opcode with the same parameters to deploy a pool contract at the deterministic address before a legitimate user.

3. When a legitimate user subsequently attempts to deploy a pool with the same parameters, the deployment fails because a contract already exists at that address, thereby causing a denial of service for genuine users.

## Recommendation

* Don't allow the user to control the `salt` used.
