# Vulnerability details

## Proof of Concept
The `KatanaV3Pool` contract contains an error in how it calculates the global fee growth, potentially leading to incorrect fee distribution among liquidity providers. This vulnerability can result in liquidity providers receiving more or fewer fees than they are entitled to, leading to profit imbalances and undermining the integrity of the pool.

In the `KatanaV3Pool` contract, the global fee growth is updated during swaps, which determines how fees are distributed among liquidity providers. The error arises from the incorrect use of the `FullMath.mulDiv` function to compute the growth of fees relative to liquidity, which leads to overflows or inaccurate calculations when the liquidity value is high, or when large swaps occur.

Vulnerable Code:
The following is the vulnerable part of the fee growth calculation in the swap function, which updates `feeGrowthGlobalX128` incorrectly when the liquidity is large:
```solidity
if (state.liquidity > 0) {
    state.feeGrowthGlobalX128 += FullMath.mulDiv(step.feeAmount, FixedPoint128.Q128, state.liquidity);
}
```
In this snippet, the calculation of the global fee growth uses `FullMath.mulDiv`, but the interaction between fee amounts, liquidity, and the precision of `FixedPoint128.Q128` leads to imprecise results.

When the liquidity (`state.liquidity`) is very large, or the `step.feeAmount` is high, the calculation can result in inaccurate fee growth that disproportionately favors or harms liquidity providers.

PoC:
The PoC demonstrates how the error in fee growth calculation leads to an imbalanced distribution of fees when the liquidity is large and swaps are frequent.

The test checks how the fee growth changes when a large liquidity pool and a large swap amount are used. It simulates a swap and observes how fees are distributed.

```javascript
const { expect } = require("chai");
const { ethers } = require("hardhat");

describe("Fee Growth Calculation Errors", function () {
    let katanaPool;
    let token0;
    let token1;
    let liquidityProvider1;
    let liquidityProvider2;

    beforeEach(async function () {
        // Deploy tokens and KatanaV3Pool contract
        const Token = await ethers.getContractFactory("MockERC20");
        token0 = await Token.deploy("Token0", "TK0", ethers.utils.parseEther("1000000"));
        token1 = await Token.deploy("Token1", "TK1", ethers.utils.parseEther("1000000"));

        const KatanaV3Pool = await ethers.getContractFactory("KatanaV3Pool");
        katanaPool = await KatanaV3Pool.deploy(token0.address, token1.address);

        // Setup two liquidity providers
        [liquidityProvider1, liquidityProvider2] = await ethers.getSigners();

        // Add liquidity
        await token0.connect(liquidityProvider1).approve(katanaPool.address, ethers.utils.parseEther("10000"));
        await token1.connect(liquidityProvider1).approve(katanaPool.address, ethers.utils.parseEther("10000"));
        await katanaPool.connect(liquidityProvider1).addLiquidity(ethers.utils.parseEther("10000"), ethers.utils.parseEther("10000"));

        await token0.connect(liquidityProvider2).approve(katanaPool.address, ethers.utils.parseEther("50000"));
        await token1.connect(liquidityProvider2).approve(katanaPool.address, ethers.utils.parseEther("50000"));
        await katanaPool.connect(liquidityProvider2).addLiquidity(ethers.utils.parseEther("50000"), ethers.utils.parseEther("50000"));
    });

    it("Should show incorrect fee growth calculation when liquidity is large", async function () {
        // Perform a large swap to trigger fee calculation
        const swapAmount = ethers.utils.parseEther("10000");
        await katanaPool.connect(liquidityProvider1).swap(liquidityProvider1.address, true, swapAmount, 0, []);

        // Check the fee growth calculation
        const feeGrowthGlobal0X128 = await katanaPool.feeGrowthGlobal0X128();
        const feeGrowthGlobal1X128 = await katanaPool.feeGrowthGlobal1X128();

        console.log("Fee Growth Global 0:", feeGrowthGlobal0X128.toString());
        console.log("Fee Growth Global 1:", feeGrowthGlobal1X128.toString());

        // Check if fee growth is distributed incorrectly
        const liquidity1Fees = await katanaPool.getLiquidityProviderFees(liquidityProvider1.address);
        const liquidity2Fees = await katanaPool.getLiquidityProviderFees(liquidityProvider2.address);

        console.log("Liquidity Provider 1 Fees:", liquidity1Fees.toString());
        console.log("Liquidity Provider 2 Fees:", liquidity2Fees.toString());

        expect(liquidity1Fees).to.not.equal(liquidity2Fees);
    });
});
```

The impact of this vulnerability is significant as it affects the fair distribution of fees among liquidity providers. When liquidity providers are not receiving their correct share of fees, it could lead to:
1. Liquidity providers may receive more or fewer fees than they are entitled to, creating an unfair profit distribution.
2. Affected liquidity providers may withdraw their liquidity from the pool if they perceive that they are being unfairly compensated.
3. Inconsistent fee growth calculations could create arbitrage opportunities, where sophisticated actors exploit these imbalances.

Also, the `mulDiv` function is designed to perform full precision multiplication and division of 512-bit values, ensuring that intermediate overflows do not lead to loss of precision. This is critical when dealing with large numbers, as typical 256-bit arithmetic would fail in such cases.

In the `KatanaV3Pool` contract, a vulnerability arise if the combination of high liquidity and large fee amounts results in an imprecise division outcome due to limits on the precision of the intermediate results.

Let's check this simplified code for calculating the growth of fees relative to liquidity:
```solidity
state.feeGrowthGlobalX128 += FullMath.mulDiv(step.feeAmount, FixedPoint128.Q128, state.liquidity);
```
Here, `step.feeAmount` is multiplied by `FixedPoint128.Q128` (a large constant representing 2^128) and then divided by `state.liquidity`. When `state.liquidity` is very large (as it often can be in high-liquidity pools), the division in `mulDiv` may lose precision. Even though mulDiv handles 512-bit intermediate values, if the denominator (`state.liquidity`) is much larger than the numerator, precision issues can arise due to truncation or rounding errors.

This imprecision can lead to incorrect fee growth values being assigned to liquidity providers, potentially causing disproportionate distribution of fees.

The `mulDiv` function is robust for most general purposes but may still experience precision issues due to the nature of floating-point-like operations when interacting with extremely large or small numbers. In this case:

Step 1: The product `a * b` (which is `step.feeAmount * FixedPoint128.Q128`) is calculated.
Step 2: The product is then divided by `state.liquidity`.
If `state.liquidity` is extremely large compared to `step.feeAmount`, the result could be truncated or lose significant digits, especially if precision is not managed properly.

Key problem:
Even though `FullMath` handles overflows and division errors gracefully, it can still lead to precision loss when the ratio between the numerator and denominator becomes extreme, as often happens in decentralized finance (DeFi) protocols when dealing with vast liquidity pools.

## Recommended Mitigation Steps
1. If possible, impose limits on the range of liquidity values that the contract can handle to prevent extreme scenarios that could lead to precision loss.
2. Rework the fee growth calculation to avoid using large constants like FixedPoint128.Q128 when interacting with liquidity. This might involve adjusting how fee growth is tracked (e.g., using smaller scaling factors or tracking fee growth in a more granular way).
3. Use a library or a solution that allows for double-precision arithmetic to ensure that large liquidity values do not result in lost precision. This would require expanding the current logic to handle 1024-bit numbers, which could be costly in terms of gas but would mitigate the precision loss.
