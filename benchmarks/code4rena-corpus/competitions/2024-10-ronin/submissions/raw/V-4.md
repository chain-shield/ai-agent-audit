# Vulnerability details

## Vulnerability
In the mint() function of the NonfungiblePositionManager, the unchecked increment of the token ID (_nextId++) poses a potential vulnerability. Specifically, a "dust amount" of tokens (tiny amounts of token0 or token1) could cause a new token ID to be minted without proper validation, potentially overwriting an existing token ID. This could lead to severe consequences such as:
1. Token ID Collisions: If the token ID is incremented without checking its uniqueness, the new mint could overwrite an existing token, leading to a loss of control over existing positions.
2. Loss of Funds: The overwriting of an existing token ID would mean that liquidity providers may lose access to their funds, as their NFT representing liquidity is effectively replaced by a new one with different attributes.

## Proof of Concept
A malicious user could potentially exploit the lack of checks on _nextId by repeatedly calling mint() of NonfungiblePositionManager contract to eventually overflow the token ID counter. If this occurs, new tokens could receive the ID 0, potentially replacing an original token and leading to unintended behavior or losses.
The follow test code is updated in KatanaV3Pool.t.sol. After this function, the tokenId = 1000 and only 1000 of token0 tokens are consumed.

## Recommended Mitigation Steps
Ensure that each new token ID is unique before incrementing and assigning it to a position and _nextId is incremented after the new token is safely minted to avoid skipping or reusing token IDs.
```
require(liquidity > 0, "Insufficient liquidity");
tokenId = _nextId;
require(!_exists(tokenId), "Token ID collision");
_nextId++;
```

Ensure that the token minting only proceeds when there are significant amounts of token0 and token1, and avoid allowing dust amounts (insignificant tiny amounts) from minting new tokens. 
```
require(params.amount0Desired > MIN_AMOUNT && params.amount1Desired > MIN_AMOUNT, "Amount too small");
```
