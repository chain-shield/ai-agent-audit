# Vulnerability details

## **Summary**

The Katana V3 pool factory leverages the `CREATE2` opcode for **deterministic address deployment** of liquidity pools. An attacker can **precompute the address** of the pool and deploy a **malicious contract with infinite token allowances** at the same address before the legitimate pool deployment. This **contract collision attack** allows the attacker to **drain all liquidity** from the pool once it goes live.



## **Vulnerability Detail**

The attack hinges on the **predictability of the pool address** in the `deploy()` function of the `KatanaV3PoolDeployer`. The factory uses `CREATE2` to deploy pools with the following logic:

```solidity
bytes32 salt = keccak256(abi.encode(token0, token1, fee));
pool = Create2.deploy(0, salt, creationCode);
```

Since the salt is derived from publicly known parameters (i.e., token pair and fee), the attacker can precompute the pool address using the same logic.

### Attack Steps:
Address Precomputation:
The attacker uses the same logic as the factory to precompute the pool’s future address.

Deploy Malicious Contract:
Before the pool is deployed, the attacker deploys a malicious contract at the precomputed address using CREATE2. This contract:

Grants infinite token allowances to the attacker’s wallet.
Self-destructs to make the address appear empty for the factory’s deployment.
Drain the Pool:
Once the legitimate pool is deployed at the same precomputed address, the attacker uses the pre-approved allowance to drain all tokens from the pool.

## **Impact**

The impact of this attack is severe, as it enables the attacker to completely drain the pool’s liquidity. Since DeFi pools typically hold significant amounts of assets, the financial damage could be catastrophic. A successful attack would:

- Allow the attacker to approve unlimited token transfers from the pool.
- Make it appear as though no contract existed prior to the pool deployment (due to the self-destruction of the malicious contract).
- Enable the attacker to instantly drain the pool’s liquidity once it goes live.

## **Recommendation**

1. **Check for Code Presence at the Address:**  
   Add a validation step to ensure the target address does not already contain bytecode before deploying a pool. This prevents deploying to an address that was previously occupied by a malicious contract.

2. **Incorporate Non-Deterministic Elements into the Salt:**  
   Add elements such as block numbers or timestamps to the salt used in the `CREATE2` deployment. This makes it significantly harder for an attacker to predict the address in advance.

3. **Incorporate Non-Deterministic Elements into the Salt:**  
   Add elements such as block numbers or a timestamp to the salt used in the `CREATE2` deployment. This makes it significantly harder for an attacker to predict the address in advance.

4. **Deploy Placeholder Contracts:**  
   Deploy temporary placeholder contracts at precomputed addresses to reserve those addresses and prevent malicious contracts from being deployed.

5. **Use a Timelock Mechanism:**  
   Introduce a timelock between the announcement of a pool deployment and the actual deployment, giving time to monitor the address for suspicious activity.

---

## **Conclusion**

This PoC demonstrates the feasibility of an address collision attack using `CREATE2`. The attack leverages the deterministic nature of the `CREATE2` opcode to precompute the pool’s address, deploy a malicious contract, and drain the pool’s liquidity. With advances in computational power, such attacks are becoming increasingly feasible. 

Implementing the recommended mitigations will safeguard the Katana V3 protocol from this serious security vulnerability.
