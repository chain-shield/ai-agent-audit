# Vulnerability details

The `swap` function in KatanaV3Pool.sol is susceptible to flow, particularly in handling the `amountSpecified` parameter and subsequent calculations. This could lead to incorrect swap amounts, manipulated pool balances, and potential loss of funds for users.

The is because the `swap` function assumes that `amountSpecified` and related calculations will always remain within the valid range of `int256`, which is not guaranteed. The function performs unchecked arithmetic operations on large integers without proper bounds checking or SafeMath-like protections.

For example, in the swap loop: [#L632-L637](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Pool.sol#L632-L638)

These operations can overflow or underflow with extreme input values, leading to incorrect state updates and potentially allowing an attacker to manipulate the pool's balance.

## Impact
Incorrect swap amounts being processed
Manipulation of pool balances

## Proof of Concept
While most normal transactions would not trigger this issue, it becomes more likely with extreme values or in scenarios where an attacker intentionally crafts transactions to exploit this vulnerability.

Consider the following scenario:

1. Alice initializes a KatanaV3Pool with some liquidity.

2. Bob, an attacker, calls the swap function with the following parameters:

   * `recipient`: Bob's address
   * `zeroForOne`: true
   * `amountSpecified`: type(int256).max
   * `sqrtPriceLimitX96`: A valid price limit
   * `data`: Empty bytes

> This call would likely cause an overflow in the `amountSpecifiedRemaining` calculation, leading to unexpected behavior in the `swap` logic. The exact outcome would depend on the pool's current state, but it could result in incorrect token transfers, manipulated pool balances, or a complete failure of the swap operation.

3. The swap function processes this input:

```solidity

  address recipient,
  bool zeroForOne,
  int256 amountSpecified, // <= @audit Vulnerable to integer overflow
  uint160 sqrtPriceLimitX96,
  bytes calldata data

  // ...

  SwapState memory state = SwapState({
    amountSpecifiedRemaining: amountSpecified, // <= @audit Potential overflow

  // ...

  while (state.amountSpecifiedRemaining != 0 && state.sqrtPriceX96 != sqrtPriceLimitX96) {
    // ...

      state.amountCalculated = state.amountCalculated.sub(step.amountOut.toInt256()); // <= @audit Potential underflow
    } else {
      state.amountSpecifiedRemaining += step.amountOut.toInt256(); // <= @audit Potential overflow
```

4. The large `amountSpecified` causes an overflow in calculations, leading to incorrect token transfers and manipulated pool balances.

## Recommended Mitigation Steps
I have multiple recommendations on this.

1. Implement input validation for the `amountSpecified` parameter
```diff
function swap(
  address recipient,
  bool zeroForOne,
  int256 amountSpecified,
  uint160 sqrtPriceLimitX96,
  bytes calldata data
) external override returns (int256 amount0, int256 amount1) {
+  require(amountSpecified > type(int256).min && amountSpecified < type(int256).max, "Invalid amount");
  // ...
}
```
2. Use SafeMath or Solidity 0.8.x's built-in overflow checks for all arithmetic operations
```diff
- state.amountSpecifiedRemaining -= (step.amountIn + step.feeAmount).toInt256();
+ state.amountSpecifiedRemaining = state.amountSpecifiedRemaining.sub((step.amountIn + step.feeAmount).toInt256());
```
3. Consider adding upper bounds for swap amounts to prevent potential economic attacks
```diff
+ uint256 constant MAX_SWAP_AMOUNT = 1e27; // Example value, adjust based on your tokenomics
function swap(
  // ...
) external override returns (int256 amount0, int256 amount1) {
+  require(abs(amountSpecified) <= MAX_SWAP_AMOUNT, "Swap amount too large");
  // ...
}
```
