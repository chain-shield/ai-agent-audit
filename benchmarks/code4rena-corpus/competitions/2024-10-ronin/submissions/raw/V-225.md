# Vulnerability details

## Summary
The `_modifyPosition` function in KatanaV3Pool lacks minimum liquidity safeguards, potentially allowing the pool to reach a critically low or zero liquidity state. This creates serious issues for price discovery and pool stability.

Let's dive into the implementation:

```solidity
function _modifyPosition(ModifyPositionParams memory params)
    private
    returns (Position.Info storage position, int256 amount0, int256 amount1)
{
    checkTicks(params.tickLower, params.tickUpper);
    Slot0 memory _slot0 = slot0; 

    position = _updatePosition(params.owner, params.tickLower, params.tickUpper, params.liquidityDelta, _slot0.tick);

    if (params.liquidityDelta != 0) {
        if (_slot0.tick < params.tickUpper) {
            // Current tick is inside the passed range
            uint128 liquidityBefore = liquidity; // SLOAD for gas optimization

            // ... oracle updates ...

            liquidity = LiquidityMath.addDelta(liquidityBefore, params.liquidityDelta);
        }
    }
}
```

The issue occurs in the liquidity update. When removing liquidity (`liquidityDelta` is negative), there's no check to ensure a minimum amount remains. The liquidity can be reduced to zero or near-zero levels:

```solidity
// In _modifyPosition
liquidity = LiquidityMath.addDelta(liquidityBefore, params.liquidityDelta);
```

This vulnerability surfaces through the public `burn` function, which any user with a position can call:

```solidity
function burn(int24 tickLower, int24 tickUpper, uint128 amount)
    external
    override
    lock
    returns (uint256 amount0, uint256 amount1)
{
    (Position.Info storage position, int256 amount0Int, int256 amount1Int) = _modifyPosition(
        ModifyPositionParams({
            owner: msg.sender,
            tickLower: tickLower,
            tickUpper: tickUpper,
            liquidityDelta: -int256(amount).toInt128() // Converts to negative for removal
        })
    );
    // ... rest of function
}
```

The impact is severe because near-zero liquidity allows for extreme price manipulation. Consider this scenario:

1. Pool has substantial liquidity and normal trading activity
2. Large liquidity provider removes almost all liquidity through burn()
3. Pool now has minimal liquidity
4. Attacker can cause massive price swings with small trades
5. Oracle prices become unreliable
6. Users performing swaps receive terrible execution prices

Here's a technical scenario demonstrating the vulnerability:

```solidity
// Initial state: Pool with 1000 units of liquidity
// Large LP removes 999 units
function demonstrateMinLiquidityVulnerability() {
    // Initial state
    uint128 initialLiquidity = pool.liquidity();  // 1000
    
    // Remove most liquidity
    largeLPPosition.burn(tickLower, tickUpper, 999);
    
    // Pool now has 1 unit of liquidity
    uint128 remainingLiquidity = pool.liquidity();  // 1
    
    // Small trade causes massive price impact
    uint256 preBefore = pool.slot0.sqrtPriceX96;
    attacker.swap(true, smallAmount, sqrtPriceLimitX96);
    uint256 priceAfter = pool.slot0.sqrtPriceX96;
    
    // Price delta is enormous due to low liquidity
    assert((priceAfter - priceBefore) / priceBefore > 0.5); // >50% price change
}
```

The fix should implement minimum liquidity thresholds:

```solidity
function _modifyPosition(ModifyPositionParams memory params)
    private
    returns (Position.Info storage position, int256 amount0, int256 amount1)
{
    // ... existing code ...

    if (params.liquidityDelta < 0) {
        uint128 newLiquidity = LiquidityMath.addDelta(liquidityBefore, params.liquidityDelta);
        require(newLiquidity >= MIN_LIQUIDITY, "Insufficient remaining liquidity");
    }
    
    liquidity = LiquidityMath.addDelta(liquidityBefore, params.liquidityDelta);
    
    // ... rest of function
}
```
