# Vulnerability details

### Vulnerability Overview

The `transform` function serves as a fundamental part of the Oracle system, crucial for maintaining accurate observations of the pool's state over time. These observations are essential for providing reliable price feeds, calculating liquidity, and managing reward distributions. However, there is a significant flaw in how the function handles the liquidity parameter, particularly when it is zero.

The implementation currently employs a ternary operator to prevent division by zero. While this avoids triggering an error, it introduces inaccuracies into the calculation of `secondsPerLiquidityCumulativeX128` during instances when the pool lacks liquidity.

---

### Analysis of the Code

The problematic line in the code is as follows:

```solidity
  function transform(Observation memory last, uint32 blockTimestamp, int24 tick, uint128 liquidity)
    private
    pure
    returns (Observation memory)
  {
    uint32 delta = blockTimestamp - last.blockTimestamp;
    return Observation({
      blockTimestamp: blockTimestamp,
      tickCumulative: last.tickCumulative + int56(tick) * delta,
      secondsPerLiquidityCumulativeX128: last.secondsPerLiquidityCumulativeX128
        + ((uint160(delta) << 128) / (liquidity > 0 ? liquidity : 1)),
      initialized: true
    });
  }
```

In cases where liquidity equals zero, the function resorts to dividing by one instead of zero. While this prevents the function from failing, it inadvertently introduces a logical error into the liquidity calculations.

---

### Consequences of the Flaw

The ramifications of this vulnerability are significant. When the liquidity is zero, the function continues to accumulate time as if one unit of liquidity exists. This leads to an exaggerated estimate of the time-weighted average liquidity.

Moreover, any system relying on this oracle for accurate liquidity data will receive misleading information. This distortion can have adverse effects on trading decisions, risk evaluations, and other mechanisms that depend on precise liquidity reporting.

---
### Illustrative Scenario

Imagine a pool that fluctuates between having liquidity and being empty. For instance, at time T=0, the pool has a liquidity of 1500. At T=120, liquidity drops to zero, then at T=240, liquidity increases to 2500. Finally, an observation is recorded at T=360.

Using the current implementation, the following occurs:

- From T=0 to T=120, the function accurately accumulates 120 seconds worth of liquidity.
- However, between T=120 and T=240, the function incorrectly continues to accumulate 120 seconds as if there was one unit of liquidity, despite the pool being empty.
- Lastly, from T=240 to T=360, it correctly accumulates another 120 seconds worth of liquidity.

As a result, this flawed logic leads to an overestimation of the average liquidity over the observation period.

### Recommendation

To rectify this issue, the `transform` function needs to be modified so that it skips the accumulation step when liquidity is zero. The corrected code would look like this:

```solidity
function transform(
    Observation memory last,
    uint32 blockTimestamp,
    int24 tick,
    uint128 liquidity
) private pure returns (Observation memory) {
    unchecked {
        uint32 delta = blockTimestamp - last.blockTimestamp;
        uint160 secondsPerLiquidityCumulativeX128 = last.secondsPerLiquidityCumulativeX128;
        if (liquidity > 0) {
            secondsPerLiquidityCumulativeX128 += ((uint160(delta) << 128) / liquidity);
        }
        return Observation({
            blockTimestamp: blockTimestamp,
            tickCumulative: last.tickCumulative + int56(tick) * int56(uint56(delta)),
            secondsPerLiquidityCumulativeX128: secondsPerLiquidityCumulativeX128,
            initialized: true
        });
    }
}
```

This revision ensures that `secondsPerLiquidityCumulativeX128` is only updated when there is actual liquidity in the pool, thereby eliminating any inaccuracies.
