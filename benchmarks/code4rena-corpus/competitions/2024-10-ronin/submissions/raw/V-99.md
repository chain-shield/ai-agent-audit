# Vulnerability details

## Proof of Concept
In the `V2SwapRouter::_v2Swap` function, we have used the keyword `unchecked` for a block of code which means that all the arithmetic operations in this block will never fail due to an overflow/underflow. However, in this block, certain operations can result in an `underflow`, such as the following operation: `uint256 amountInput = ERC20(input).balanceOf(pair) - reserveInput;`. Over a period of time, it is possible that the value of `reserveInput` will be greater than `ERC20(input).balanceOf(pair)`, resulting in a negative value which will be converted to an `uint256` type due to non-revert on underflow/overflow; and this will lead to a large value of `amountInput` to swap. A malicious user can exploit this by entering a small `amountInput` value but swapping more than is supposed to be done.

example of a scenario: Ongoing Swap Before Reserves Update

Imagine a scenario where the pair contract is in the middle of a swap operation:
1. Step 1: Initial State
    - The pair holds 1000 tokens of `TokenA` and 500 tokens of `TokenB`.
    - The reserves stored in the pair contract are `reserve0 = 1000` for `TokenA` and `reserve1 = 500` for `TokenB`.
2. Step 2: Swap Initiated
    - A user initiates a swap to trade 100 `TokenA` for `TokenB`.
    - The user transfers 100 `TokenA` into the pair contract, temporarily increasing the balance of `TokenA` to 1100.
    - The pair calculates how much `TokenB` to send to the user based on the reserves and executes the swap.
    - After sending out 45 `TokenB` to the user, the pair now has 1100 `TokenA` and 455 `TokenB` in balance.
3. Step 3: Reserves Update
    - At this moment, before the reserves are updated, the pair still has reserves of `reserve0 = 1000` for `TokenA` and `reserve1 = 500` for `TokenB`, but the balances are `1100 TokenA` and `455 TokenB`.
If the `V2SwapRouter::_v2Swap` function is called at this point, the balance of `TokenB` (455) is lower than its reserve (500). When we calculate `amountInput` using:
```solidity
    uint256 amountInput = ERC20(input).balanceOf(pair) - reserveInput;
```
If `input` is `TokenB`, this calculation would be `455 - 500`, which would normally be reversed due to underflow in Solidity version 0.8.0 and higher, or result in an error; but as we're using `unchecked` to wrap the whole block in this code, no revert will occur and the negative result will be converted to type `uint256` and it's this erroneous value that will be stored as `amountInput` for the swap.

## Impact 
Inappropriate behaviour and theft of funds: a malicious user can use this vulnerability to swap very large amounts of Tokens with a minimal initial investment.
