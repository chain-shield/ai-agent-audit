# Vulnerability details

## Summary

In the KatanaV3Pool contract, there's a concerning use of tx.origin in the swap function's authorization logic. This implementation choice creates potential security risks that could compromise the pool's intended access controls. Let's examine the problematic code and understand its implications.

The vulnerability begins in the swap function's authorization check:

```solidity
function swap(
    address recipient,
    bool zeroForOne,
    int256 amountSpecified,
    uint160 sqrtPriceLimitX96,
    bytes calldata data
) external override returns (int256 amount0, int256 amount1) {
    // when quoting, we don't need to check authorization
    if (tx.origin != address(0)) {
        require(msg.sender == IKatanaGovernance(governance).getRouter(), "IR");
    }
    require(amountSpecified != 0, "AS");
    // ... rest of swap implementation
}
```

The intention here appears to be providing a way to bypass router restrictions for certain types of calls, particularly price quotes. However, this creates several security issues due to how tx.origin works in Ethereum.

Let's break down why this is problematic. The tx.origin global variable refers to the original externally owned account (EOA) that initiated the transaction, regardless of how many contract calls deep the execution is. In contrast, msg.sender refers to the immediate caller of the function. Here's how this difference manifests in practice:

```solidity
// Normal flow:
User (EOA) -> Router -> Pool
tx.origin = User
msg.sender = Router

// Potentially malicious flow:
User (EOA) -> Malicious Contract -> Pool
tx.origin = User
msg.sender = Malicious Contract
```

Consider this attack scenario:

```solidity
contract MaliciousContract {
    IKatanaV3Pool private immutable pool;
    
    constructor(address _pool) {
        pool = IKatanaV3Pool(_pool);
    }
    
    function executeSwap(
        address recipient,
        bool zeroForOne,
        int256 amountSpecified,
        uint160 sqrtPriceLimitX96
    ) external {
        // This call will pass the tx.origin check if called through a contract deployment
        // where tx.origin is address(0)
        pool.swap(
            recipient,
            zeroForOne,
            amountSpecified,
            sqrtPriceLimitX96,
            ""
        );
    }
    
    function deploy() external {
        // Deploy new instance of malicious contract
        // During contract creation, tx.origin can be manipulated
        new MaliciousContract(address(pool));
    }
}
```

The vulnerability becomes particularly dangerous in scenarios involving contract deployment transactions. During contract creation, certain properties of the transaction can be manipulated, potentially allowing an attacker to bypass the intended access controls.

Here's a more detailed attack flow:

The proper way to implement this authorization check should be:

```solidity
function swap(
    address recipient,
    bool zeroForOne,
    int256 amountSpecified,
    uint160 sqrtPriceLimitX96,
    bytes calldata data
) external override returns (int256 amount0, int256 amount1) {
    // Option 1: Simple router check
    require(msg.sender == IKatanaGovernance(governance).getRouter(), "Not router");
    
    // OR Option 2: More flexible but still secure approach
    require(
        IKatanaGovernance(governance).isValidCaller(msg.sender),
        "Unauthorized caller"
    );
    
    require(amountSpecified != 0, "AS");
    // ... rest of implementation
}
```

And in the governance contract:

```solidity
contract KatanaGovernance {
    address public router;
    mapping(address => bool) public authorizedCallers;
    
    function isValidCaller(address caller) external view returns (bool) {
        return caller == router || authorizedCallers[caller];
    }
    
    function setRouter(address _router) external onlyOwner {
        router = _router;
        emit RouterUpdated(_router);
    }
    
    function setCallerAuthorization(address caller, bool authorized) external onlyOwner {
        authorizedCallers[caller] = authorized;
        emit CallerAuthorizationUpdated(caller, authorized);
    }
}
```

This revised implementation:

1. Removes the dangerous tx.origin check
2. Provides clear, deterministic authorization
3. Maintains flexibility for authorized callers
4. Uses proper access control patterns
5. Is resistant to contract creation exploits

The key issue here is that tx.origin should never be used for authorization purposes, as it creates subtle vulnerabilities that can be exploited through contract deployment mechanics and other advanced attack vectors. Instead, always use msg.sender and implement proper role-based access control systems.
