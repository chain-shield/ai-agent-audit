# Vulnerability details

### Description of the Issue

The `initializeImmutables` function presents a significant attack vector through frontrunning, as we can see in the following code:

```solidity
/// @inheritdoc IKatanaV3PoolImmutables
function initializeImmutables(address factory_, address token0_, address token1_, uint24 fee_, int24 tickSpacing_)
    public
    virtual
    override
{
    require(factory == address(0), "AII"); 

    (factory, token0, token1, fee, tickSpacing) = (factory_, token0_, token1_, fee_, tickSpacing_);

    // cache these immutable addresses for gas savings when swaps, mints, or burns are performed
    governance = IKatanaV3Factory(factory_).owner();
    positionManager = IKatanaGovernance(governance).getPositionManager();

    maxLiquidityPerTick = Tick.tickSpacingToMaxLiquidityPerTick(tickSpacing_);
}
```

### Analysis of the Function

This function is designed to initialise essential parameters for a new pool. The line:

```solidity
require(factory == address(0), "AII");
```

is critical because it ensures that the `factory` variable has not been set before proceeding. However, this logic creates a vulnerability as it allows an attacker to potentially execute a frontrunning attack.

### Attack Vector

1. **Initial Legitimate Transaction:** A user (Alice) attempts to create a new pool by invoking the `initializeImmutables` function with specific parameters.
2. **Frontrunning by the Attacker:** An attacker (Eve) monitors the mempool and observes Alice’s transaction. Eve can then submit her transaction first, manipulating the parameters such as `fee` or `tickSpacing_` to her advantage.
3. **Reversion of the Legitimate Transaction:** As a result of Eve's transaction being processed first, the `factory` no longer satisfies the condition `factory == address(0)`, causing Alice's transaction to fail with the revert reason "AII".

### Consequences

The ability for an attacker to modify parameters before the legitimate transaction is processed introduces a risk of Denial of Service (DoS) against genuine users. Legitimate users may be unable to complete their transactions due to reverts caused by the attacker’s actions, which disrupts the expected functioning of the protocol.

### Suggested Mitigation

To address this vulnerability, it is recommended to improve the access control logic surrounding the `initializeImmutables` function. Specifically, consider restricting who can invoke this function to mitigate the risk of frontrunning. 

Alternatively, explore mechanisms that reduce the likelihood of frontrunning attacks, such as implementing a commit/reveal strategy or introducing time delays for certain actions. These approaches could significantly diminish the attack surface while maintaining the functionality of the contract.
