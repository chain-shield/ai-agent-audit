# Vulnerability details

## Proof of Concept
From the modifier:

modifier lock() {
    require(slot0.unlocked, "LOK");
    slot0.unlocked = false;
    _;
    slot0.unlocked = true;
  }

This only prevent direct reentrancy mid execution of the flash function. The recipient address(if it is a contract) or IkatanaV3FlashCallback under the flash function will trigger a fallback(or receive) function. The reentrancy effect of this isn't prevented in external functions without the lock modifier like initialize and  especially swap.

Hence an attacker can execute reentrant logic in katanaV3FlashCallback and manipulate the values of balance0() and balance1(). And with the swap calculations depending on token balance, attackers 
reenter the swap to manipulate token reserves or prices

## Recommended Mitigation Steps
A lock modifier should be placed in the swap function and other sensitive functions to prevent or mitigate the chances of cross function and callback reentrancy
