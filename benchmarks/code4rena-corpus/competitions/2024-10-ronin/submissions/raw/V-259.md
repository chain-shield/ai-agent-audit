# Vulnerability details

## Vulnerability details

Note about contest scope: `Oracle::transform` is being called from `KatanaV3Pool::_modifyPosition()` and `KatanaV3Pool::swap()` (line 308, line 693 in KatanaV3Pool.sol), and the KatanaV3Pool contract is in scope of this contest.

The function `Oracle::transform()` is used to update observations of the pool state over time, which are critical for accurate price feeds, liquidity calculations, and potentially reward distributions. However, there is an issue with the handling of the `liquidity` parameter when it is 0.

The current implementation uses a ternary operator to avoid division by zero, but this approach can lead to inaccurate accumulation of secondsPerLiquidityCumulativeX128 when the pool has no liquidity (line 40 katana-v3-contracts/src/core/libraries/Oracle.sol):

```solidity
+ ((uint160(delta) << 128) / (liquidity > 0 ? liquidity : 1)),
```

With 0 liquidity it is dividing by 1 instead of zero to avoid reverting, but this introduces a logical error in the calculations.

## Impact

Overestimation of time-weighted average liquidity:
During periods of zero liquidity, the function is still accumulating time as if there was 1 unit of liquidity.

Misleading Oracle Data: Any system relying on this oracle for liquidity data will receive inaccurate information. This could affect trading decisions, risk assessments, or any other mechanisms that depend on accurate liquidity reporting.

## Example

We have a pool that alternates between having liquidity and being empty:

T0: Liquidity = 1000

T100: Liquidity drops to 0

T200: Liquidity increases to 2000

T300: Observation is taken

With our current implementation:

From T0 to T100 and from T200 to T300 we accumulate 100 seconds worth of liquidity.

However from T100 to T200, we incorrectly accumulate 100 seconds as if there was 1 unit of liquidity.

This results in an overestimation of the average liquidity over this period.

## Recommended Mitigation Steps

Modify `Oracle::transform()` in order to skip accumulation if `liquidity` is 0, so that `secondsPerLiquidityCumulativeX128` is only accumulated if there is liquidity in the pool.
