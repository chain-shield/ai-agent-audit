# Vulnerability details

In the KatanaV3Pool contract, in the swap function, when performing a swap where `token1` is being exchanged for `token0` (`zeroForOne` is false), the function incorrectly checks the balance of `token0` instead of `token1`. This allows users to drain the pool of `token0` without providing the correct amount of `token1`.

In the else branch of the `zeroForOne` condition, the balance check uses `balance0()` instead of `balance1()`: [KatanaV3Pool.sol#L734](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Pool.sol#L734)
```solidity
    require(balance1Before.add(uint256(amount1)) <= balance0(), "IIA");
```
This means that for swaps where `token1` is being provided, the contract is not verifying if the correct amount of `token1` has been transferred to the pool. Instead, it's checking the balance of `token0`, which is irrelevant for this part of the swap.

## Impact
* Draining of `token0` from the pool without providing the correct amount of `token1`.
* Manipulation of the pool's price and liquidity.
* Unfair profit for attackers at the expense of other liquidity providers.
* Potential complete breakdown of the pool's economic model.

It directly affects the core functionality of the pool and can lead to significant financial losses.

## Proof of Concept
Consider the following scenario

1. The pool starts with 1000 of `token0` and 1000 of `token1`.
2. An attacker initiates a swap to exchange 100 of `token1` for `token0`.
3. The swap function calculates that the attacker should receive 98 of `token0` (assuming a 2% fee).
4. In the [katanaV3SwapCallback](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Pool.sol#L733), the attacker's contract doesn't transfer any `token1` to the pool.
5. The swap succeeds because the check is against `balance0()` instead of `balance1()`.
6. The pool now has 902 of token0 and still 1000 of `token1`, creating an imbalance.

KatanaV3Pool.sol#
```solidity
if (zeroForOne) {
  if (amount1 < 0) TransferHelper.safeTransfer(tokenOut, recipient, uint256(-amount1));

  uint256 balance0Before = balance0();
  IKatanaV3SwapCallback(msg.sender).katanaV3SwapCallback(amount0, amount1, data);
  require(balance0Before.add(uint256(amount0)) <= balance0(), "IIA");
} else {
  if (amount0 < 0) TransferHelper.safeTransfer(tokenOut, recipient, uint256(-amount0));

  uint256 balance1Before = balance1();
  IKatanaV3SwapCallback(msg.sender).katanaV3SwapCallback(amount0, amount1, data);
  require(balance1Before.add(uint256(amount1)) <= balance0(), "IIA"); // <-- Bug here
}
```
In the balance check for the non-zeroForOne case. The condition is checking `balance0()` instead of `balance1()`, which could lead to inconsistent fee growth calculations and potentially allow for manipulation of the pool's state.

## Recommended Mitigation Steps
The balance check in the else branch should be corrected to use `balance1()` instead of `balance0()`.
```diff
if (zeroForOne) {
  if (amount1 < 0) TransferHelper.safeTransfer(tokenOut, recipient, uint256(-amount1));

  uint256 balance0Before = balance0();
  IKatanaV3SwapCallback(msg.sender).katanaV3SwapCallback(amount0, amount1, data);
  require(balance0Before.add(uint256(amount0)) <= balance0(), "IIA");
} else {
  if (amount0 < 0) TransferHelper.safeTransfer(tokenOut, recipient, uint256(-amount0));

  uint256 balance1Before = balance1();
  IKatanaV3SwapCallback(msg.sender).katanaV3SwapCallback(amount0, amount1, data);
-  require(balance1Before.add(uint256(amount1)) <= balance0(), "IIA");
+  require(balance1Before.add(uint256(amount1)) <= balance1(), "IIA");
}
```
