# Vulnerability details

In mint function:
```
amount0 = uint256(amount0Int); // casting int256 to uint256
amount1 = uint256(amount1Int); // casting int256 to uint256
```

Description:
In the `mint` function of the `KatanaV3Pool`, when liquidity is added to a position, the protocol calculates the amount of `token0` and `token1` owed. These amounts are represented as signed integers (`amount0Int` and `amount1Int`). However, these signed integers are always cast to unsigned integers (`uint256`). If either of these amounts is negative (i.e., the protocol owes tokens to the user), casting the negative values to unsigned integers results in large, incorrect values due to integer underflow. This can lead to incorrect tracking of tokens owed, potentially resulting in mismanagement of balances during the mint process.

Impact:
The incorrect casting of negative amounts to unsigned integers can lead to several problems:

 - Users may receive incorrect amounts of tokens (either too much or too little).
 - Incorrect accounting within the protocol could cause systemic issues with token balance management.
 - If a large positive value is incorrectly calculated from a negative owed amount, it could even disrupt the correct operation of liquidity pools.

Proof of Concept:

1. A user mints liquidity for a position where the protocol owes them tokens (negative amounts).
2. The amounts (`amount0Int` and `amount1Int`) are negative but are cast into unsigned integers, resulting in extremely large values.
3. This incorrect calculation can lead to either an underpayment or overpayment when the user attempts to `collect` their tokens via the collect function.

example:
```
amount0 = uint256(-5); // Negative amount cast to unsigned, resulting in an extremely large value.
amount1 = uint256(-10); // Same issue with token1.

```
This value is then stored, and during the collection of owed tokens, the user might receive an incorrect amount.

Recommended Mitigation:
The contract should correctly handle negative amounts when casting from signed to unsigned integers. There are two potential ways to address this:

1. Add explicit checks before casting signed integers to unsigned integers to handle negative cases properly.

2. Track the amounts owed separately (with the negative amounts), ensuring the user is credited when the pool owes them tokens.
