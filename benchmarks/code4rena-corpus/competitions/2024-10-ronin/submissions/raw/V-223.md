# Vulnerability details

## Summary
The Dispatcher contract's current implementation uses an unsafe pattern for parameter decoding that leads to scattered memory access, repeated assembly blocks, and potential stack pressure issues.


## Code
```solidity
if (command == Commands.V3_SWAP_EXACT_IN) {
    // Individual parameter declarations scattered across stack
    address recipient;
    uint256 amountIn;
    uint256 amountOutMin;
    bool payerIsUser;
    
    // Unsafe: Repeated assembly block with manual offset calculations
    assembly {
        recipient := calldataload(inputs.offset)
        amountIn := calldataload(add(inputs.offset, 0x20))
        amountOutMin := calldataload(add(inputs.offset, 0x40))
        payerIsUser := calldataload(add(inputs.offset, 0x80))
    }
    
    bytes calldata path = inputs.toBytes(3);
    address payer = payerIsUser ? lockedBy : address(this);
    v3SwapExactInput(map(recipient), amountIn, amountOutMin, path, payer);
}
```

Issues:
1. Manual memory offset calculations are error-prone
2. Stack variables are scattered across function scope
3. Similar assembly blocks are repeated for different commands
4. Parameter validation is mixed with decoding logic
5. Unclear separation between parameter loading and business logic

## Impact

Manual offset calculations in the assembly block can lead to data corruption and incorrect parameter loading.

In the current implementation:
```solidity
assembly {
    recipient := calldataload(inputs.offset)
    amountIn := calldataload(add(inputs.offset, 0x20))
    amountOutMin := calldataload(add(inputs.offset, 0x40))
    payerIsUser := calldataload(add(inputs.offset, 0x80))  // Notice this 0x80 offset
}
```

The danger lies in the manual offset calculations:

1. Each parameter's location is determined by adding hex values (0x20, 0x40, 0x80) to the base offset
2. These offsets assume specific parameter ordering and sizes in the calldata
3. If the calldata layout changes or a parameter size changes, these hard-coded offsets would still load data from the original positions

For example:
- If a new parameter were inserted earlier in the calldata sequence, all subsequent offsets would be wrong
- The 0x80 offset for payerIsUser jumps ahead, assuming specific positioning
- Loading from incorrect offsets would silently load wrong data - an address might be loaded where a uint256 was expected

This could corrupt the swap parameters where:
- amountIn could load recipient's address data 
- amounts could be dramatically wrong leading to bad swaps
- boolean flags could be misinterpreted leading to incorrect execution paths
- payerIsUser flag loading wrong data could change who pays for the swap

The reason this is particularly dangerous is that Solidity provides no type checking or bounds checking in assembly - it will happily load whatever data exists at the specified offset and interpret it as the expected type.


## Root Cause

The root cause is the lack of a structured approach to parameter decoding. The current implementation attempts to optimize gas costs by using direct assembly, but does so in a way that sacrifices code safety and maintainability.

## Fix

The fix introduces proper structure through a dedicated parameter struct and decoder:

```solidity
struct SwapParams {
    address recipient;
    uint256 amountIn;
    uint256 amountOutMin;
    bool payerIsUser;
    bytes path;
}

function decodeSwapParams(bytes calldata inputs) internal pure returns (SwapParams memory params) {
    assembly {
        // Single, consolidated assembly block with clear memory layout
        let ptr := inputs.offset
        params := mload(0x40)  // Get free memory pointer
        mstore(add(params, 0x00), calldataload(ptr))  // recipient
        mstore(add(params, 0x20), calldataload(add(ptr, 0x20)))  // amountIn
        mstore(add(params, 0x40), calldataload(add(ptr, 0x40)))  // amountOutMin
        mstore(add(params, 0x60), calldataload(add(ptr, 0x80)))  // payerIsUser
    }
    params.path = inputs.toBytes(3);
}
```

Usage in dispatch:
```solidity
if (command == Commands.V3_SWAP_EXACT_IN) {
    SwapParams memory params = decodeSwapParams(inputs);
    checkAuthorizedV3Path(params.path);
    
    address payer = params.payerIsUser ? lockedBy : address(this);
    v3SwapExactInput(
        map(params.recipient),
        params.amountIn,
        params.amountOutMin,
        params.path,
        payer
    );
}
```

## Benefits of Fix

1. **Parameter Encapsulation**: All swap parameters are grouped in a single struct
2. **Single Source of Truth**: Parameter decoding logic is centralized
3. **Clear Memory Layout**: Struct provides explicit memory organization
4. **Reduced Error Surface**: Assembly code is isolated to a single function
5. **Improved Readability**: Business logic is separated from parameter decoding
6. **Better Maintainability**: Adding new parameters only requires updating the struct and decoder
