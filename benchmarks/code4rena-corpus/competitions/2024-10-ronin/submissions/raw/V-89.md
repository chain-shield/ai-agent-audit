# Vulnerability details

## Proof of Concept
Unauthorized reduction of total pool liquidity during swap operations, violating a core invariant that liquidity should only decrease through explicit burn operations. The issue occurs because the `swap` function modifies liquidity state during tick crossings without proper validation. When computing `liquidityNet` during a tick crossing, the value can be negative and is directly applied to the pool's liquidity state without ensuring the total liquidity invariant is maintained.

[KatanaV3Pool.sol.swap](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Pool.sol#L603-L682)
```solidity
function swap(
    address recipient,
    bool zeroForOne,
    int256 amountSpecified,
    uint160 sqrtPriceLimitX96,
    bytes calldata data
) external override returns (int256 amount0, int256 amount1) {
    // @Issue: Liquidity state modification during swap
    while (state.amountSpecifiedRemaining != 0 && state.sqrtPriceX96 != sqrtPriceLimitX96) {
        if (step.initialized) {
            // @Issue: Unvalidated liquidity change
            int128 liquidityNet = ticks.cross(
                step.tickNext,
                (zeroForOne ? state.feeGrowthGlobalX128 : feeGrowthGlobal0X128),
                (zeroForOne ? feeGrowthGlobal1X128 : state.feeGrowthGlobalX128),
                cache.secondsPerLiquidityCumulativeX128,
                cache.tickCumulative,
                cache.blockTimestamp
            );
            // @Issue: Direct liquidity modification without bounds checking
            if (zeroForOne) liquidityNet = -liquidityNet;
            state.liquidity = LiquidityMath.addDelta(state.liquidity, liquidityNet);
        }
    }
}
```
Root Cause

* The swap function allows liquidity modifications during tick crossings without enforcing the total liquidity invariant
* No validation that liquidity changes maintain or increase total pool liquidity
* Direct state modification without proper bounds checking

```solidity
function exploitLiquidityDecrease() public {
    // Setup
    KatanaV3Pool pool = createPool();
    addInitialLiquidity(pool);
    
    // Record initial state
    uint128 liquidityBefore = pool.liquidity();
    
    // Execute attack
    pool.swap(
        address(this),
        true,  // zeroForOne
        1000000,  // large swap amount
        TickMath.MIN_SQRT_RATIO + 1,  // price limit near minimum
        ""  // empty callback data
    );
    
    // Verify liquidity decreased
    uint128 liquidityAfter = pool.liquidity();
    assert(liquidityAfter < liquidityBefore);
}
```

## Impact
* **Price Manipulation**: Reduced liquidity can lead to increased price impact and manipulation opportunities
* **Asset Loss**: Users may receive incorrect amounts during swaps due to compromised price calculations
* **Protocol Fee Issues**: Incorrect liquidity state affects protocol fee calculations
* **System Instability**: Violates core invariants of the AMM design
