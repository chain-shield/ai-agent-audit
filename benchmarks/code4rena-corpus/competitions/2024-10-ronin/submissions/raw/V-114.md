# Vulnerability details

## Proof of Concept
The `V3Migrator::migrate` function calls the `TransferHelper::safeApprove` function implemented in the `TransferHelper` library as follow:
```solidity
    function safeApprove(address token, address to, uint256 value) internal {
@>      (bool success, bytes memory data) = token.call(abi.encodeWithSelector(IERC20.approve.selector, to, value));
        require(success && (data.length == 0 || abi.decode(data, (bool))), "SA");
    }
```
As we can see on the line mark with `@>`, this `safeApprove` function use the Openzeppelin's `ERC20.approve` method to change allowance and it didn't manage the case which a non-zero value override a precedent non-zero value, this opens the door to the race condition as mentioned in the Openzeppelin documentation: https://docs.openzeppelin.com/contracts/4.x/api/token/erc20#IERC20-approve-address-uint256-

In addition, this `TransferHelper::safeApprove` function is called in the `V3Migrator::migrate` function without first resetting the old allowance to zero as we cas see:
```solidity
    function migrate(MigrateParams calldata params) external override {
    
        /// ... The rest of code

        // approve the position manager up to the maximum token amounts
@>      TransferHelper.safeApprove(params.token0, nonfungiblePositionManager, amount0V2ToMigrate);
@>      TransferHelper.safeApprove(params.token1, nonfungiblePositionManager, amount1V2ToMigrate);

        /// ... The rest of code
      
    }
```
So these calls to the `TransferHelper::safeApprove` function overwrites the current allowance regardless of whether the spender already used it or not. It allows the spender to front-run and spend the amount before the new allowance is set. The attack vector is explained here: https://docs.google.com/document/d/1YLPtQxZu1UAvO9cZ1O2RPXBbT0mooh4DYKjA_jp-RLM/edit?tab=t.0#heading=h.m9fhqynw2xvt

The `allowance` should only be cleaned up under certain conditions as implemented at the end of the `V3Migrator::migrate` function: 
```solidity
    function migrate(MigrateParams calldata params) external override {
    
        /// ... The rest of code
        
@>      // if necessary, clear allowance and refund dust
        if (amount0V3 < amount0V2) {
        if (amount0V3 < amount0V2ToMigrate) {
@>          TransferHelper.safeApprove(params.token0, nonfungiblePositionManager, 0);
        }

        /// ... The rest of code 

        }
        if (amount1V3 < amount1V2) {
        if (amount1V3 < amount1V2ToMigrate) {
@>          TransferHelper.safeApprove(params.token1, nonfungiblePositionManager, 0);
        }

        /// ... The rest of code

        }
    }
```
Instead, the `allowance` must be reset to zero at any time before a new value is set, to avoid any risk of race condition or front-run.

## Impact
Loss of Funds: A malicious spender with an unlimited allowance can transfer an unlimited number of tokens, resulting in potential loss of all assets from the token holder’s balance

## Recommended Mitigation Steps
