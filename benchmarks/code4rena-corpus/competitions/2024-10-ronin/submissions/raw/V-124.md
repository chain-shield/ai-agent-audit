# Vulnerability details



## Proof of Concept

The `KatanaV3Factory` contract allows fee tiers to be configured through the `enableFeeAmount` function without an explicit check to prevent setting `fee = 0`. If a zero fee tier is enabled, it could lead to several issues, such as:

- **Zero Revenue Pools**: A zero-fee pool would allow users to swap tokens without paying fees, resulting in no protocol or liquidity provider revenue.
- **Incentive Mismatch for Liquidity Providers**: LPs would be disincentivized from providing liquidity to zero-fee pools, potentially reducing the overall liquidity in the protocol.
- **Exploit Potential**: Malicious actors could create multiple zero-fee pools, undermining the protocol's revenue model.

### Code Reference:
The vulnerability is located in the `enableFeeAmount` function in `KatanaV3Factory.sol`:
- [View on GitHub](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Factory.sol#L110-L119) (link this to the line where `enableFeeAmount` is defined)

Relevant code snippet:
```solidity
function enableFeeAmount(uint24 fee, int24 tickSpacing, uint8 feeProtocolNum, uint8 feeProtocolDen)
    public
    override
    onlyOwner
{
    require(fee < 1000000, "KatanaV3Factory: FEE_TOO_HIGH");
    // Missing check for `fee > 0`
    ...
}
```


## Recommended Mitigation Steps

Add a check in the `enableFeeAmount` function to ensure `fee > 0` before enabling a new fee tier:

```solidity
require(fee > 0, "KatanaV3Factory: INVALID_FEE");
```

This will prevent the creation of zero-fee pools and protect the protocol's revenue and incentives structure.
