# Vulnerability details

## Summary
The inputs of the fee amount aren't validated well, as a result could result in improper actions on the pool, and other functions where the fee is processed with different amounts. As we can see that there is no validation if the `fee` amount is equal to `0` . Also the `feeProtocolNum` can also be `0`. There should be dedicated minimum value for the `fee` as well. Or else there will be a risk of centralization as a malicious owner can set a fee to 0. 

This is the following code/function : 
```
function enableFeeAmount(
        uint24 fee,
        int24 tickSpacing,
        uint8 feeProtocolNum,
        uint8 feeProtocolDen
    ) public override onlyOwner {
        require(fee < 1000000, "KatanaV3Factory: FEE_TOO_HIGH");
        // tick spacing is capped at 16384 to prevent the situation where tickSpacing is so large that
        // TickBitmap#nextInitializedTickWithinOneWord overflows int24 container from a valid tick
        // 16384 ticks represents a >5x price change with ticks of 1 bips
        require(
            tickSpacing > 0 && tickSpacing < 16384,
            "KatanaV3Factory: INVALID_TICK_SPACING"
        );
        require(
            feeProtocolNum < feeProtocolDen,
            "KatanaV3Factory: INVALID_FEE_PROTOCOL"
        );
        require(
            feeAmountTickSpacing[fee] == 0,
            "KatanaV3Factory: FEE_AMOUNT_ALREADY_ENABLED"
        );

        _enableFeeAmount(fee, tickSpacing, feeProtocolNum, feeProtocolDen);
    }
```

## Impact 
There is a risk of setting the fee to zero or if feeProtocolNum is set to zero, then there would be calculation mistakes as it can be seen in the following contract - KatanaV3Pool.sol::flash(). There are two checks which are made in order to transfer the token to treasury. 
Also it is stated in natspec that - `Returns the default protocol fee ratio for a given fee amount, if enabled, or 0 if not enabled` however even if someone sets it to 0 it will be enabled, but users might believe it to be disabled.

```
      if (paid0 > 0) {
        uint256 fees0 = FullMath.mulDiv(paid0, slot0.feeProtocolNum, slot0.feeProtocolDen);
        if (fees0 > 0) TransferHelper.safeTransfer(_token0, treasury, fees0);
        feeGrowthGlobal0X128 += FullMath.mulDiv(paid0 - fees0, FixedPoint128.Q128, _liquidity);
      }
      if (paid1 > 0) {
        uint256 fees1 = FullMath.mulDiv(paid1, slot0.feeProtocolNum, slot0.feeProtocolDen);
        if (fees1 > 0) TransferHelper.safeTransfer(_token1, treasury, fees1);
        feeGrowthGlobal1X128 += FullMath.mulDiv(paid1 - fees1, FixedPoint128.Q128, _liquidity);
      }
```
So in here fees0 and fees1 would account to 0 and hence will result in loosing funds/tokens to be transferred to treasury.
