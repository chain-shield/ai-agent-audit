# Vulnerability details

## Description

The `transform` function in the Oracle system of Katana V3 is responsible for updating key observations of pool states over time. These updates are critical for accurate price feeds, liquidity calculations, and other dependent mechanisms such as reward distributions.

However, an issue arises when the `liquidity` parameter is zero. The current implementation uses a ternary operator to prevent a division-by-zero error, but this leads to incorrect accumulation of the `secondsPerLiquidityCumulativeX128` value during periods where the pool has no liquidity.

### Problematic Code
```solidity
  function transform(Observation memory last, uint32 blockTimestamp, int24 tick, uint128 liquidity)
    private
    pure
    returns (Observation memory)
  {
    uint32 delta = blockTimestamp - last.blockTimestamp;
    return Observation({
      blockTimestamp: blockTimestamp,
      tickCumulative: last.tickCumulative + int56(tick) * delta,
      secondsPerLiquidityCumulativeX128: last.secondsPerLiquidityCumulativeX128
        + ((uint160(delta) << 128) / (liquidity > 0 ? liquidity : 1)),
      initialized: true
    });
  }
```

### Issue

The critical line is:
```solidity
((uint160(delta) << 128) / (liquidity > 0 ? liquidity : 1))
```
When `liquidity` is zero, the code divides by `1` instead of `0` to avoid a runtime error. While this prevents the contract from reverting, it introduces a logical flaw by accumulating time as if there was 1 unit of liquidity, even when the pool is empty. This results in incorrect values being recorded in the Oracle, leading to inaccurate liquidity data.

## Impact

1. **Inaccurate Liquidity Tracking**: During zero liquidity periods, the Oracle erroneously records liquidity, causing an overestimation of time-weighted average liquidity.
   
2. **Misleading Oracle Data**: Systems depending on accurate liquidity data from this Oracle, such as trading platforms or risk assessment algorithms, could make faulty decisions based on inflated liquidity metrics.

### Scenario

Imagine a pool with the following liquidity changes:
- **T=0**: Liquidity is 1000
- **T=100**: Liquidity drops to 0
- **T=200**: Liquidity increases to 2000
- **T=300**: An observation is recorded

With the current implementation:
- Between **T=0 and T=100**, the liquidity is tracked correctly.
- Between **T=100 and T=200**, the Oracle incorrectly assumes 1 unit of liquidity and accumulates data.
- Between **T=200 and T=300**, the liquidity is tracked correctly again.

This results in an overestimated average liquidity for the entire period.

## Fix

The solution is to modify the `transform` function to skip the accumulation of `secondsPerLiquidityCumulativeX128` when liquidity is zero.

### Proposed Fix:
```solidity
function transform(
    Observation memory last,
    uint32 blockTimestamp,
    int24 tick,
    uint128 liquidity
) private pure returns (Observation memory) {
    unchecked {
        uint32 delta = blockTimestamp - last.blockTimestamp;
        uint160 secondsPerLiquidityCumulativeX128 = last.secondsPerLiquidityCumulativeX128;
        if (liquidity > 0) {
            secondsPerLiquidityCumulativeX128 += ((uint160(delta) << 128) / liquidity);
        }
        return Observation({
            blockTimestamp: blockTimestamp,
            tickCumulative: last.tickCumulative + int56(tick) * int56(uint56(delta)),
            secondsPerLiquidityCumulativeX128: secondsPerLiquidityCumulativeX128,
            initialized: true
        });
    }
}
```

### Benefits of the Fix:
- Ensures accurate tracking by only accumulating time-weighted liquidity when there is actual liquidity in the pool.
- Prevents misleading Oracle data, maintaining the integrity of systems relying on the Oracle for liquidity and price information.

This approach ensures that the Oracle's data is precise, especially during periods where the pool experiences zero liquidity.
