# Vulnerability details

## Summary

The Katana V3 Pool's collect function has a significant design inconsistency in its security model. While position creation and burning require interaction through the position manager (enforcing NFT ownership), the collect function allows direct pool interaction. This means users who have transferred their position NFTs can still collect fees directly from the pool, breaking the core security assumption that position NFTs represent complete control over a position. While this doesn't enable direct theft of funds, it undermines protocol composability and could break higher-level DeFi protocols that rely on position NFT ownership as a source of truth for position control.

The issue centers around the relationship between the Katana V3 Pool and its Position Manager system. In Uniswap V3-style protocols, positions are meant to be managed through an NFT-based position manager - this is evident from the pool's initialization where the position manager is stored as a critical protocol component:

```solidity
contract KatanaV3Pool is IKatanaV3Pool {
    // Position Manager address stored at contract level
    address public override positionManager;
    
    // Position storage mapping
    mapping(bytes32 => Position.Info) public override positions;
}
```

When we examine the core position manipulation functions, we see a deliberate pattern of restricting access to the position manager. Let's look at the position creation flow:

```solidity
function mint(
    address recipient,
    int24 tickLower,
    int24 tickUpper,
    uint128 amount,
    bytes calldata data
) external override lock returns (uint256 amount0, uint256 amount1) {
    require(msg.sender == positionManager, "IPM");
    // ... position creation logic
}
```

This same pattern continues with position burning:

```solidity
function burn(
    int24 tickLower,
    int24 tickUpper,
    uint128 amount
) external override lock returns (uint256 amount0, uint256 amount1) {
    // ... burning logic
}
```

However, when we reach the `collect` function, this security pattern breaks down:

```solidity
function collect(
    address recipient,
    int24 tickLower,
    int24 tickUpper,
    uint128 amount0Requested,
    uint128 amount1Requested
) external override lock returns (uint128 amount0, uint128 amount1) {
    Position.Info storage position = positions.get(msg.sender, tickLower, tickUpper);
    
    amount0 = amount0Requested > position.tokensOwed0 ? position.tokensOwed0 : amount0Requested;
    amount1 = amount1Requested > position.tokensOwed1 ? position.tokensOwed1 : amount1Requested;

    if (amount0 > 0) {
        position.tokensOwed0 -= amount0;
        TransferHelper.safeTransfer(token0, recipient, amount0);
    }
    if (amount1 > 0) {
        position.tokensOwed1 -= amount1;
        TransferHelper.safeTransfer(token1, recipient, amount1);
    }

    emit Collect(msg.sender, recipient, tickLower, tickUpper, amount0, amount1);
}
```

The vulnerability here is subtle but significant. While the function correctly uses `msg.sender` to look up positions (preventing direct theft of other users' positions), it breaks the protocol's intended security model of position management through NFTs.

Let's walk through how this creates a real-world problem:

When Alice interacts with the protocol normally, she:
1. Mints a position through the position manager
2. Receives an NFT representing her position
3. The position data is stored in the pool with her address as the key

Now imagine Alice transfers her NFT to Bob. In a proper implementation, all control over the position should transfer with the NFT. However, because `collect` allows direct pool interaction, Alice can still collect fees from the position even after transferring the NFT.

The issue becomes more complex when we consider protocol integrations. Many DeFi protocols build on top of these pool positions, using the NFT ownership as a source of truth for who can manage the position. For example, a lending protocol might accept these position NFTs as collateral, expecting that controlling the NFT means controlling the position's assets and fees.

The root of the problem lies in the divergence from the established security model. Looking at the pool's initialization code:

```solidity
function initializeImmutables(
    address factory_,
    address token0_,
    address token1_,
    uint24 fee_,
    int24 tickSpacing_
) public virtual override {
    require(factory == address(0), "AII");
    
    // ... initialization logic ...
    
    // Position manager is treated as a core protocol component
    positionManager = IKatanaGovernance(governance).getPositionManager();
}
```

The protocol clearly intends for the position manager to be a fundamental part of the security model, not an optional component. The `collect` function's direct access creates a parallel, unintended control mechanism.

## Fix
The fix needs to align the `collect` function with this security model:

```solidity
function collect(
    address recipient,
    int24 tickLower,
    int24 tickUpper,
    uint128 amount0Requested,
    uint128 amount1Requested
) external override lock returns (uint128 amount0, uint128 amount1) {
    require(msg.sender == positionManager, "IPM");
    Position.Info storage position = positions.get(recipient, tickLower, tickUpper);
    
    // ... rest of collection logic ...
}
```

This change ensures that all position management - creation, modification, fee collection, and destruction - follows the same security pattern through the position manager. It maintains the protocol's intended invariant that position NFTs represent complete control over the underlying position.

The impact of this vulnerability isn't in direct fund theft - the position mapping prevents that. Instead, it's in the breaking of protocol composability and security assumptions. Any protocol building on top of Katana V3 positions needs to be aware that position NFTs don't guarantee exclusive control over fee collection, potentially breaking higher-level security mechanisms built on this assumption.
