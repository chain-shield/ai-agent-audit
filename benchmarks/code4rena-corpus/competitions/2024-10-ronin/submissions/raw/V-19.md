# Vulnerability details

## Proof of Concept
In the `NonfungibleTokenPositionDescriptor` contract, the token addresses for USDC, WETH, and WBTC are hardcoded:
https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/periphery/NonfungibleTokenPositionDescriptor.sol#L19-L21
```solidity
address private constant USDC = 0x0B7007c13325C48911F73A2daD5FA5dCBf808aDc;
address private constant WETH = 0xc99a6A985eD2Cac1ef41640596C5A5f9F4E19Ef5;
address private constant WBTC = 0x7E73630F81647bCFD7B1F2C04c1C662D17d4577e;
```
The issue arises because these addresses are static and tied to a specific chain. If the contract is deployed on a different blockchain network or a new version of these tokens is deployed, the hardcoded addresses may no longer be correct. This could cause the contract to fail when attempting to retrieve information about these tokens, potentially breaking functionality such as token metadata generation or token ratio calculations.

These addresses are used in the contract to determine token ratios and to fetch token metadata, and incorrect addresses could result in the wrong tokens being referenced or errors in metadata generation.

## Impact

1. The contract will fail to retrieve correct token metadata for USDC, WETH, and WBTC if the contract is deployed on a different chain or if new versions of these tokens are deployed with different addresses.
2. Functions that rely on fetching token data (such as metadata generation or token ratio calculations) will fail or return incorrect results. This could lead to DoS in the functionality that depends on correct token metadata.
3. The contract cannot easily adapt to changes in token contracts or deployments on different chains, making it less robust and more prone to failure.

The vulnerability is classified as Medium because while it does not directly affect security (such as unauthorized access or fund theft), it has a significant impact on the functionality of the contract. Incorrect token addresses can lead to failed transactions, incorrect metadata, and broken functionality, especially in multi-chain deployments or if token contracts are upgraded.

## Recommended Mitigation Steps
1. Instead of hardcoding the token addresses, the contract should allow these addresses to be passed dynamically, either through the constructor or via an upgradable setter function. This would allow the addresses to be updated if the contract is deployed on a different network or if new versions of the tokens are deployed.

Example:
```solidity
address public USDC;
address public WETH;
address public WBTC;

constructor(address _USDC, address _WETH, address _WBTC) {
    USDC = _USDC;
    WETH = _WETH;
    WBTC = _WBTC;
}
```
2. Allow governance or a trusted admin to update the token addresses if necessary, especially in case of a token contract upgrade. This ensures that the contract can remain functional even if the underlying token contracts change.
3. Add logic to detect the chain ID dynamically and assign the appropriate token addresses based on the chain. This would allow the contract to be deployed on multiple chains without hardcoding specific addresses.

Example:
```solidity
if (chainId == 1) {  // Mainnet
    USDC = mainnetUSDC;
    WETH = mainnetWETH;
    WBTC = mainnetWBTC;
} else if (chainId == 4) {  // Rinkeby
    USDC = rinkebyUSDC;
    WETH = rinkebyWETH;
    WBTC = rinkebyWBTC;
}
```
