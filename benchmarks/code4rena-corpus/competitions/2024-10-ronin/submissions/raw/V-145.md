# Vulnerability details

## Summary
The `swap` function in `KatanaV3Pool.sol` is vulnerable to reentrancy attacks due to external calls to `katanaV3SwapCallback` before critical state variables are securely locked. This allows malicious contracts to re-enter the function and manipulate the pool’s state, leading to unauthorized swaps or token drainage.

## Proof of Concept
1. **State Locking Issue**: 
- The function locks the state by setting `slot0.unlocked = false;` at the beginning of the function, but the function doesn't unlock the state immediately after performing the swap calculations.
- Instead, `slot0.unlocked = true;` is only set at the **end** of the function, which may leave room for reentrancy if an external call is made before this point.

2. **External Call Risk**: 
- The function makes an **external call** to `IKatanaV3SwapCallback(msg.sender).katanaV3SwapCallback(amount0, amount1, data);` without locking the function state at a critical section.
- This callback function is implemented by an external contract, and since it is external, it could be a malicious contract. The contract could re-enter the `swap` function and perform malicious actions because the function hasn’t finished updating its state.

3. **Balance Checks Post-Callback**: 
- After the external callback is executed, the function performs a balance check with `require(balance0Before.add(uint256(amount0)) <= balance0(), "IIA");` and `require(balance1Before.add(uint256(amount1)) <= balance1(), "IIA");`.
- This pattern is intended to ensure that sufficient tokens have been sent to the pool, but if the state hasn’t been locked properly, the external contract could interfere with the token balances before the check is made.

## How Reentrancy Could Happen:
- A malicious contract could re-enter the `swap` function by calling the callback during the `katanaV3SwapCallback` invocation.
- The reentrancy could allow the attacker to manipulate the pool’s state, potentially withdrawing more tokens than they should or making unauthorized swaps.

## Recommended Mitigation Steps
1. **Lock State Before External Call**: Ensure `slot0.unlocked = true;` is set only after critical state updates and balance checks.

2. **Use `ReentrancyGuard`**: Implement OpenZeppelin’s `ReentrancyGuard` to prevent reentrant calls.

3. **Perform Balance Checks Before Callback**: Move balance checks before the external callback to minimize the risk of manipulation.
