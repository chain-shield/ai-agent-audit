# Vulnerability details

`flash` function in KatanaV3Pool.sol allows flash loans even when the pool has insufficient liquidity to cover the requested amounts, because the function only checks if the liquidity is greater than zero, but doesn't verify if the pool has enough balance to cover the requested flash loan amounts.

It only check if `_liquidity > 0`. This check is insufficient as it doesn't correlate with the actual token balances or the requested flash loan amounts. The function proceeds to transfer tokens even if the requested amounts exceed the pool's current balances, potentially leading to underflows or economic imbalances.

## Impact
Users could extract more tokens from the pool than are available, leading to insolvency issues.

## Proof of Concept
While it verifies that liquidity is non-zero, it doesn't ensure that the requested flash loan amounts are actually available in the pool. It is highly likely to occur in scenarios where pools have very low liquidity. Any user interacting with such pools could trigger this vulnerability, making it a significant risk for the protocol.

Consider this

1. Alice deploys a KatanaV3Pool with minimal liquidity, say 1 wei of each token.
2. The factory contract has flash loans enabled.
3. Bob calls the flash function with amounts larger than the pool's balance:

```solidity
pool.flash(
    bob,
    pool.balance0() * 2,  // Request twice the available balance
    pool.balance1() * 2,
    "0x"
);
```
This call will succeed despite the pool not having sufficient funds to cover the flash loan. The function will attempt to transfer more tokens than are available in the pool.

## Recommended Mitigation Steps
This bug could potentially lead to economic vulnerabilities. Add an additional check in the `flash()` function to ensure that the requested amounts are available in the pool.
