# Vulnerability details

## Summary

The NonfungiblePositionManager's positions() function exposes complete economic data about liquidity positions (including exact liquidity amounts and uncollected fees) through a public view function. MEV bots can combine this detailed position data with pending collection/withdrawal transactions in the mempool to execute precise sandwich attacks. By knowing the exact amounts of fees to be collected or liquidity to be withdrawn before these transactions execute, attackers can optimize their front-running strategies with zero uncertainty about position sizes or expected returns. The transparency of position data, while useful for the protocol's operation, creates a deterministic attack vector for MEV extraction that's particularly difficult to defend against without significant architectural changes.

The heart of this vulnerability lies in how the NonfungiblePositionManager exposes sensitive position details through its public positions() function:

```solidity
function positions(uint256 tokenId)
    external
    view
    override
    returns (
        uint96 nonce,
        address operator,
        address token0,
        address token1,
        uint24 fee,
        int24 tickLower,
        int24 tickUpper,
        uint128 liquidity,          // Exposed liquidity amount
        uint256 feeGrowthInside0LastX128,
        uint256 feeGrowthInside1LastX128,
        uint128 tokensOwed0,        // Exposed uncollected fees
        uint128 tokensOwed1         // Exposed uncollected fees
    )
```

This function reveals critical economic data about positions - specifically their liquidity and uncollected fees. While transparency is generally good for DeFi, in this case it creates a perfect storm for MEV extractors.

## The Attack Surface

Consider a position with substantial accumulated fees:
```solidity
// Position data
struct Position {
    // ...
    uint128 liquidity;    // Large liquidity amount
    // ...
    uint128 tokensOwed0;  // Significant uncollected fees
    uint128 tokensOwed1;  // Significant uncollected fees
}
```

When a user prepares to call collect() to claim their fees, they must send a transaction like:

```solidity
function collect(CollectParams calldata params)
    external
    payable
    override
    isAuthorizedForToken(params.tokenId)
    returns (uint256 amount0, uint256 amount1)
{
    require(
        params.amount0Max == type(uint128).max && 
        params.amount1Max == type(uint128).max,
        "Must collect all tokens owed"
    );
    // ... fee collection logic
}
```

A MEV bot can monitor the mempool for such collect() calls while simultaneously querying the position's data:

```solidity
// MEV bot monitoring
(,,,,,,, uint128 liquidity, , , uint128 tokensOwed0, uint128 tokensOwed1) = 
    positionManager.positions(targetTokenId);

// If significant fees are available
if (tokensOwed0 > PROFITABLE_THRESHOLD || tokensOwed1 > PROFITABLE_THRESHOLD) {
    // Front-run the collection
    // ...
}
```

## The Front-running Attack

The MEV bot can construct a sandwich attack around the collect() transaction. Here's how it plays out:

1. User submits collect() transaction
2. MEV bot sees the pending transaction
3. Bot queries positions() to see uncollected fees
4. Bot performs pre-transaction market manipulation:
```solidity
// Pre-transaction by MEV bot
// 1. Flash loan assets
// 2. Move price in advantageous direction
// 3. Wait for user's collect() to execute
// 4. Move price back
// 5. Repay flash loan with profit
```

Similarly for decreaseLiquidity() calls, the exposed liquidity amount allows MEV bots to calculate exact slippage and sandwich the removal:

```solidity
function decreaseLiquidity(DecreaseLiquidityParams calldata params)
    external
    payable
    override
    isAuthorizedForToken(params.tokenId)
    checkDeadline(params.deadline)
    returns (uint256 amount0, uint256 amount1)
{
    // User's transaction to remove liquidity
    // MEV bot can calculate exact amounts based on public position data
}
```

## Impact

This exposure creates a particularly damaging form of MEV because:

1. Position Data Precision: The attacker knows exact amounts:
```solidity
// Exact knowledge of:
uint128 liquidity;    // Precise position size
uint128 tokensOwed0;  // Exact fee amounts
uint128 tokensOwed1;  // Exact fee amounts
```

2. Predictable Actions: When fees are large enough:
```solidity
// MEV bot logic
if (tokensOwed0 + tokensOwed1 > MIN_PROFITABLE_FEES) {
    // Almost certain user will collect soon
    // Can prepare front-running infrastructure
}
```

3. No Uncertainty: Unlike many MEV opportunities, the bot has perfect information:
```solidity
// No guessing about:
- Position size
- Fee amounts
- Price ranges
- Expected returns
```


The fundamental issue is that the positions() function provides too much economic data without any time-delay or access controls. Every piece of position data it exposes becomes a potential MEV vector when combined with pending transaction information.

## Fix

```solidity
contract NonfungiblePositionManager {
    // Separate view functions for public vs owner position data
    function publicPositions(uint256 tokenId) 
        external 
        view 
        returns (
            address token0,
            address token1,
            uint24 fee,
            int24 tickLower,
            int24 tickUpper
        )
    {
        Position memory position = _positions[tokenId];
        require(position.poolId != 0, "Invalid token ID");
        PoolAddress.PoolKey memory poolKey = _poolIdToPoolKey[position.poolId];
        
        return (
            poolKey.token0,
            poolKey.token1,
            poolKey.fee,
            position.tickLower,
            position.tickUpper
        );
    }

    // Only owner/approved can see full position details
    function positionDetails(uint256 tokenId)
        external
        view
        returns (
            uint128 liquidity,
            uint128 tokensOwed0,
            uint128 tokensOwed1
        )
    {
        require(
            msg.sender == ownerOf(tokenId) || 
            msg.sender == getApproved(tokenId) ||
            isApprovedForAll(ownerOf(tokenId), msg.sender),
            "Not authorized"
        );
        
        Position memory position = _positions[tokenId];
        return (
            position.liquidity,
            position.tokensOwed0,
            position.tokensOwed1
        );
    }
}
```

Key changes:
- Split positions() into two functions
- Public function only shows non-sensitive data (tokens, ticks, fee)
- Private function requires ownership to view economic data (liquidity, fees)
- Keeps original state/storage intact

The fix prevents MEV bots from accessing exact liquidity/fee amounts while maintaining necessary protocol transparency.
