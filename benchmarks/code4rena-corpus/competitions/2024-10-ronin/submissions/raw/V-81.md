# Vulnerability details

Liquidity updates in `_modifyPosition()` only happen when the current tick is within the position's range. When burning positions where the current tick is outside the range, the function calculates token amounts but fails to decrease the total pool liquidity.

This creates a scenario where:
```solidity
totalLiquidity before burn == totalLiquidity after burn
```
Even though position liquidity was burned, breaking the fundamental invariant that burning must decrease total liquidity.

The key vulnerability path is when burning liquidity for a position where the current tick is outside the position's range - the burn succeeds but fails to decrease the total liquidity as required by the invariant.

**Root Cause**

* When burning liquidity, the function modifies `state.liquidity` through `LiquidityMath.addDelta()`
* The liquidity update only happens if the current tick is within the position's range
* This creates an edge case where burning can succeed without decreasing total liquidity

## Proof of Concept
```diff
function burn(int24 tickLower, int24 tickUpper, uint128 amount) {
    // @Issue: No validation that burn decreases liquidity
    (Position.Info storage position, int256 amount0Int, int256 amount1Int) = _modifyPosition(
      ModifyPositionParams({
        liquidityDelta: -int256(amount).toInt128()
      })
    );
}

function _modifyPosition() {
    if (_slot0.tick < params.tickLower) {
        // @Issue: Returns token amounts but doesn't update liquidity
        amount0 = SqrtPriceMath.getAmount0Delta(
            TickMath.getSqrtRatioAtTick(params.tickLower),
            TickMath.getSqrtRatioAtTick(params.tickUpper),
            params.liquidityDelta
        );
    } else if (_slot0.tick < params.tickUpper) {
        // Only path where liquidity is updated
        liquidity = LiquidityMath.addDelta(liquidityBefore, params.liquidityDelta);
    }
}
```
Attack Sequence

1. Attacker creates position with 1000 liquidity in range [100, 200]
2. Price moves below tick 100
3. Attacker burns 500 liquidity
4. Position tokens are returned but pool liquidity remains at 1000
5. Pool state becomes inconsistent

Impact

High severity due to:

* Broken core invariants around liquidity accounting
* Incorrect pool state affecting all subsequent operations
* Potential for price manipulation through artificial liquidity
* Affects core AMM functionality including swaps and pricing

## Recommended Mitigation Steps
Add validation in `burn()`
```diff
function burn(int24 tickLower, int24 tickUpper, uint128 amount) {
+   uint128 liquidityBefore = liquidity;
    (Position.Info storage position, int256 amount0Int, int256 amount1Int) = _modifyPosition(...);
+   require(liquidity == liquidityBefore - amount, "Invalid liquidity decrease");
}
```
Alternative fix - update liquidity in all branches
```diff
function _modifyPosition() {
    if (_slot0.tick < params.tickLower) {
        amount0 = SqrtPriceMath.getAmount0Delta(...);
+       liquidity = LiquidityMath.addDelta(liquidityBefore, params.liquidityDelta);
    }
}
```
This way we ensures liquidity is properly decreased regardless of current tick position.
