# Vulnerability details

#### **Issue Description:**
In the `KatanaV3Factory` contract, the constructor is commented to suggest that it disables initialisation (// disable initialization), but the proper use of the `_disableInitializers()` function, recommended by OpenZeppelin, is missing. Without this function, the implementation contract is vulnerable to being taken over by an attacker if deployed as part of a proxy setup.

#### **Impact:**
1. **Risk of contract takeover**: Failing to use `_disableInitializers()` leaves the implementation contract exposed to being controlled by an attacker.
2. **Risk of double initialisation**: The current structure could potentially allow multiple initialisations of the contract, depending on how it is deployed and upgraded, posing a threat to the security and internal logic of the protocol.

#### **PoC**
In the contract `KatanaV3Factory` the constructor look like:
```solidity
  constructor() {
    // disable initialization
    beacon = address(1);
  }
```

#### **Recommendation:**
To mitigate these risks, the `_disableInitializers()` function should be added within the constructor of the contract. This function, provided by OpenZeppelin, locks the initialiser functions, preventing the implementation contract from being initialised or re-initialised.

**Example fix:**

```solidity
constructor() {
    _disableInitializers();  // Correctly disables initialisation
}
```

This ensures that the implementation contract is secure and cannot be re-initialised or taken over by an attacker.
