# Vulnerability details

For context, there is a gas limit vuln in the following code snippet: 

```solidity 

function _setBeacon(address beacon, bytes memory data) internal virtual override {
    (address factory, address token0, address token1, uint24 fee, int24 tickSpacing) =
      IKatanaV3PoolDeployer(msg.sender).parameters();

    beacon = IKatanaV3PoolDeployer(msg.sender).beacon();
    data = abi.encodeWithSelector(
      IKatanaV3PoolImmutables.initializeImmutables.selector, factory, token0, token1, fee, tickSpacing
    );

    super._setBeacon(beacon, data);
}
```
There is a possible gas limit vuln in the above snippet, due to the use of `abi.encodeWithSelector` within the `_setBeacon` function. This function call dynamically constructs an ABI encoded message based on the provided selector and parameters.  While this is generally safe, if the number of parameters passed to `abi.encodeWithSelector` is large or complex, it can lead to a significant increase in gas consumption. 

An attacker could craft malicious input that results in a very large data payload being encoded, leading to a high gas cost for the transaction. This could either exhaust the user's gas limit, preventing the transaction from completing, or result in unexpectedly high fees.

The exploit contract’s constructor takes the address of KatanaV3PoolProxy, setting it as the target and confirming the setup with console output.

The exploit uses abi.encodeWithSelector to prepare a message for initializeImmutables with large or placeholder values, crafted to reach or exceed typical gas limits.

Console output tracks this payload construction, logging the payload bytes to ensure visibility into the data being sent.

The exploit sends the payload to the target contract with target.call{value: 0}(data). This forces _setBeacon to process the payload, and potentially exhaust gas if the encoded message size hits the limit.

Console output confirms whether the attempt to reach the gas limit succeeded or failed.

## Recommended Mitigation Steps

Some useful code-level mitigations include the following.  

-> Optimize payload handling through requiring that devs reduce the size and complexity of parameters passed to abi.encodeWithSelector in _setBeacon. Avoid excessive data encoding by optimizing inputs, focusing on concise data that minimizes gas usage.

-> Limit input data complexity, requiring that devs restrict inputs, such as token or factory addresses, to valid known addresses and ensure minimal data is encoded. This limits the risk of large payloads driving up gas costs.

-> Set gas limits on calls to _setBeacon, require that devs set an upper gas threshold for the _setBeacon function to prevent overload. For added security, implement checks to restrict how much gas abi.encodeWithSelector is allowed to consume within _setBeacon.
