# Vulnerability details

```solidity
uint256 refund0 = amount0V2 - amount0V3;
```
## Vulnerability Details

There is a logic error in the refund calculation during the migration process from V2 to V3 liquidity pools. The current implementation calculates the refund amount based on the total liquidity burned from the V2 pool (`amount0V2`) instead of the amount intended to be migrated (`amount0V2ToMigrate`). This can lead to excessive refunds when users migrate only a portion of their liquidity.

If you look at this concept

 A user has 1000 tokens in a V2 liquidity pool.
 The user decides to migrate 50% of their liquidity to V3 (500 tokens).
 The V2 position is burned, returning 1000 tokens.
 The V3 position is created with 495 tokens (assuming some slippage).
 The current logic would refund 505 tokens (1000 - 495) instead of the correct 5 tokens (500 - 495).

This could be exploited by users to receive more tokens than intended, potentially draining liquidity from the protocol over time.

## Recommended Mitigation Step

The refund calculation should be based on the amount intended to be migrated (`amount0V2ToMigrate`) instead of the total amount received from burning V2 liquidity (`amount0V2`).

```solidity
uint256 refund0 = amount0V2ToMigrate - amount0V3;
```

This will ensures that only the dust amount from the intended migration is refunded, preventing excessive refunds in partial migration scenarios. The same fix should be applied to the calculation for `token1` as well.
