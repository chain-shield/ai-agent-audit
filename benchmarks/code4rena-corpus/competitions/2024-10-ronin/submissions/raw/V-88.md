# Vulnerability details

`flash` loan mechanism of KatanaV3Pool where the balance validation checks are insufficient to prevent manipulation of pool liquidity. Attackers can drain pool liquidity by manipulating balance checks

The vulnerability stems from two key issues in the flash loan implementation:-

1. The balance validation uses weak comparison (`<=` instead of `<`)
```solidity
require(balance0Before.add(fee0) <= balance0After, "F0");
require(balance1Before.add(fee1) <= balance1After, "F1");
```
2. Token transfers occur before securing repayment:-
```solidity
if (amount0 > 0) TransferHelper.safeTransfer(_token0, recipient, amount0);
if (amount1 > 0) TransferHelper.safeTransfer(_token1, recipient, amount1);
```
This allows an attacker to manipulate pool balances within the same transaction while technically satisfying the repayment checks.

## Proof of Concept
[KatanaV3Pool.sol#flash](https://github.com/ronin-chain/katana-v3-contracts/blob/03c80179e04f40d96f06c451ea494bb18f2a58fc/src/core/KatanaV3Pool.sol#L747-L791)
```solidity
function flash(address recipient, uint256 amount0, uint256 amount1, bytes calldata data) external override lock {
    // @Issue: No validation of recipient address
    require(IKatanaV3Factory(factory).flashLoanEnabled(), "FD");

    uint128 _liquidity = liquidity;
    require(_liquidity > 0, "L");

    uint256 paid0;
    uint256 paid1;

    {
        address _token0 = token0;
        address _token1 = token1;
        uint256 fee0 = FullMath.mulDivRoundingUp(amount0, fee, 1e6);
        uint256 fee1 = FullMath.mulDivRoundingUp(amount1, fee, 1e6);
        uint256 balance0Before = balance0();
        uint256 balance1Before = balance1();

        // @Issue: Funds transferred before validation
        if (amount0 > 0) TransferHelper.safeTransfer(_token0, recipient, amount0);
        if (amount1 > 0) TransferHelper.safeTransfer(_token1, recipient, amount1);

        IKatanaV3FlashCallback(msg.sender).katanaV3FlashCallback(fee0, fee1, data);

        uint256 balance0After = balance0();
        uint256 balance1After = balance1();
        address treasury = IKatanaV3Factory(factory).treasury();

        // @Issue: Weak validation using <= instead of <
        require(balance0Before.add(fee0) <= balance0After, "F0"); 
        require(balance1Before.add(fee1) <= balance1After, "F1");

        // @Issue: Balance difference calculation after weak validation
        paid0 = balance0After - balance0Before;
        paid1 = balance1After - balance1Before;

        if (paid0 > 0) {
            // @Issue: Protocol fee calculation after weak validation
            uint256 fees0 = FullMath.mulDiv(paid0, slot0.feeProtocolNum, slot0.feeProtocolDen);
            if (fees0 > 0) TransferHelper.safeTransfer(_token0, treasury, fees0);
            feeGrowthGlobal0X128 += FullMath.mulDiv(paid0 - fees0, FixedPoint128.Q128, _liquidity);
        }
    }
}
```
The main vulnerability paths are:

1. Initial transfer of funds before validations
2. Weak validation checks using `<=` comparison
3. Fee calculations occurring after the weak validations
4. No final balance verification after fee transfers

This creates an attack vector where an attacker could manipulate the balance checks while extracting value from the pool.

**Attack Vector:-**
1. Attacker calls `flash()` with large amounts
2. Receives tokens before repayment validation
3. Manipulates balances to exactly match required amount
4. Withdraws funds in same transaction
5. Pool loses liquidity while checks pass

Likelihood: High - easily exploitable since it requires:-

* No special permissions
* Standard flash loan interface
* No complex prerequisites

The vulnerability creates a risk for the protocol and its users.

**Impact**

* Direct loss of pool liquidity
* Bypass of protocol fee mechanism
* Risk to all liquidity providers
* Potential for complete pool insolvency

Here's exactly how attackers can drain pool liquidity through balance manipulation

Attack Flow

1. Initial State
```solidity
// Pool has 1000 token0 and 1000 token1
// Attacker has minimal initial balance
```

2. The attacker executes flash loan
```solidity
function attack() external {
    // Request maximum possible flash loan
    uint256 poolLiquidity = pool.liquidity();
    pool.flash(address(this), poolLiquidity, 0, "");
}
```
3. During flash callback
```solidity
function katanaV3FlashCallback(uint256 fee0, uint256 fee1, bytes calldata) external {
    // Let's say borrowed = 1000 token0, fee0 = 3 token0
    
    // Step 1: Repay exactly borrowed + fee (1003 token0)
    token0.transfer(address(pool), 1003);
    
    // Step 2: Immediately execute another pool interaction
    // that withdraws the same amount through a different mechanism
    // This could be through positions, swaps, or other pool features
    pool.someOtherFunction(); // Withdraws 1003 tokens
    
    // Result: Balance check passes because at check time:
    // balance0After (1003) >= balance0Before (1000) + fee0 (3)
    // But funds are immediately extracted
}
```

4. Final State
```solidity
// Pool balance is drained
// Attacker has gained the funds
// Balance checks passed but pool lost liquidity
```
This attack works because:-

1. The `<=` comparison allows exact balance matching
2. No verification of sustained balance after all operations
3. Multiple pool entry points can be used within the same transaction
4. The flash loan callback gives attacker control during the transaction

The attack can be repeated across multiple tokens and pool positions, draining significant liquidity while passing all current validations.

## Recommended Mitigation Steps
1. Implement strict balance validation
```diff
- require(balance0Before.add(fee0) <= balance0After, "F0");
- require(balance1Before.add(fee1) <= balance1After, "F1");
+ require(balance0Before.add(fee0) < balance0After, "F0");
+ require(balance1Before.add(fee1) < balance1After, "F1");
```
2. Add post-operation balance verification
```solidity
uint256 finalBalance0 = balance0();
uint256 finalBalance1 = balance1();
require(finalBalance0 >= balance0Before.add(fee0), "Invalid final balance");
require(finalBalance1 >= balance1Before.add(fee1), "Invalid final balance");
```
