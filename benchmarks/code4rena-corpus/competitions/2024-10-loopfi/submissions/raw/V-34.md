# Vulnerability details


## Proof of Concept

Take a look at https://github.com/code-423n4/2024-10-loopfi/blob/d219f0132005b00a68f505edc22b34f9a8b49766/src/quotas/PoolQuotaKeeperV3.sol#L161-L179

```solidity
    function addQuotaToken(
        address token,
        uint16 rate
    )
        external
        override
        gaugeOnly // U:[PQK-3]
    {
        if (quotaTokensSet.contains(token)) {
            revert TokenAlreadyAddedException(); // U:[PQK-6]
        }

        // The rate will be set during a general epoch update in the gauge
        quotaTokensSet.add(token); // U:[PQK-5]
        totalQuotaParams[token].cumulativeIndexLU = 1; // U:[PQK-5]
        totalQuotaParams[token].rate = rate;
        emit AddQuotaToken(token); // U:[PQK-5]
    }
```

This function is used to add a new token. In the previous scope, when the token is added [the rates are set to `0` by default](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/quotas/PoolQuotaKeeperV3.sol#L172) up until a general epoch update before the real rate gets set for the token via https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/quotas/GaugeV3.sol#L77-L92, which is why [this bug case](https://github.com/code-423n4/2024-07-loopfi-findings/issues?q=is%3Aissue+is%3Aopen+Zero+rates+on+new+quoted+tokens+allow+an+attacker+to+take+an+interest+free+quota) existed where an attacker can request a very high quota and pay zero fees all through.

Now, in order to mitigate that, Loopfi now atomically updates the rates when adding the tokens. The issue, however, is that the rates being set are not favorable to the protocol. Consider `minRates` are hardcoded to be passed for whatever type of tokens to be added, see https://github.com/code-423n4/2024-10-loopfi/blob/d219f0132005b00a68f505edc22b34f9a8b49766/src/quotas/GaugeV3.sol#L231-L260

```solidity
    /// @notice Adds a new quoted token to the gauge and sets the initial rate params
    ///         If token is not added to the quota keeper, adds it there as well
    /// @param token Address of the token to add
    /// @param minRate The minimal interest rate paid on token's quotas
    /// @param maxRate The maximal interest rate paid on token's quotas
    function addQuotaToken(
        address token,
        uint16 minRate,
        uint16 maxRate
    )
        external
        override
        nonZeroAddress(token) // U:[GA-04]
        configuratorOnly // U:[GA-03]
    {
        if (isTokenAdded(token) || token == IPoolV3(pool).underlyingToken()) {
            revert TokenNotAllowedException(); // U:[GA-04]
        }
        _checkParams({minRate: minRate, maxRate: maxRate}); // U:[GA-04]

        quotaRateParams[token] = QuotaRateParams({
            minRate: minRate,
            maxRate: maxRate,
            totalVotesLpSide: 0,
            totalVotesCaSide: 0
        }); // U:[GA-05]

        IPoolQuotaKeeperV3 quotaKeeper = _poolQuotaKeeper();
        if (!quotaKeeper.isQuotedToken(token)) {
            quotaKeeper.addQuotaToken({token: token, rate: minRate}); // U:[GA-05] @audit
        }

        emit AddQuotaToken({token: token, minRate: minRate, maxRate: maxRate}); // U:[GA-05]
    }
```

This function calls the `PoolQuotaKeeperV3#addQuotaToken()` which was linked above. Evidently, and as [per the documentation](https://github.com/code-423n4/2024-10-loopfi/blob/d219f0132005b00a68f505edc22b34f9a8b49766/src/quotas/GaugeV3.sol#L230-L231), we have two different rates for said asset, either the minimum or maximum.

As hinted by the `@audit` tag, we always set the minimum rate for whichever token gets added, which does not fit the logic. Different tokens have different risks, so their quota and Loopfi should decide on a token-by-token basis if the rate should be the minimum or maximum.

Also, note that after the initial addition of the new quoted token, [the next time rates can be updated is only during the next epoch](https://github.com/code-423n4/2024-10-loopfi/blob/d219f0132005b00a68f505edc22b34f9a8b49766/src/quotas/GaugeV3.sol#L94), which then allows anyone, regardless of the type of token, to request the maximum quota for any asset in the first epoch before it gets updated and pay the minimum possible interest for this requested quota.

## Impact

Loopfi always uses unfavorable rates for them when adding fresh quoted tokens, which in this case allows a malicious/tech-savvy user to be able to request a very high quota and pay very minimal interest all through the period when the rate is set as the `minRate`. The shortest time frame in this case would be an epoch when the rates can now be updated.

## Recommended Mitigation Steps

Consider having a case-by-case basis depending on the type of quoted token being added if the rate would be minimum or maximum.

Apply these changes:

```diff
    function addQuotaToken(
        address token,
        uint16 minRate,
        uint16 maxRate,
+       bool useMaxRate
    )
        external
        override
        nonZeroAddress(token) // U:[GA-04]
        configuratorOnly // U:[GA-03]
    {
        if (isTokenAdded(token) || token == IPoolV3(pool).underlyingToken()) {
            revert TokenNotAllowedException(); // U:[GA-04]
        }
        _checkParams({minRate: minRate, maxRate: maxRate}); // U:[GA-04]

        quotaRateParams[token] = QuotaRateParams({
            minRate: minRate,
            maxRate: maxRate,
            totalVotesLpSide: 0,
            totalVotesCaSide: 0
        }); // U:[GA-05]

        IPoolQuotaKeeperV3 quotaKeeper = _poolQuotaKeeper();
        if (!quotaKeeper.isQuotedToken(token)) {
+            if (useMaxRate) {

+            quotaKeeper.addQuotaToken({token: token, rate: maxRate}); // U:[GA-05]
+            }
+            else {

+            quotaKeeper.addQuotaToken({token: token, rate: minRate}); // U:[GA-05]
+            }
+        }

        emit AddQuotaToken({token: token, minRate: minRate, maxRate: maxRate}); // U:[GA-05]
    }
```
