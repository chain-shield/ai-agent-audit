# Vulnerability details

Overview: 

The unstake function in the StakingLPEth.sol contract uses a problematic comparison operator (>=) when checking against block.timestamp, which could lead to off-by-one errors.

Description:

In the unstake function, there's a conditional statement that compares block.timestamp to userCooldown.cooldownEnd using the >= operator. This comparison method introduces off-by-one errors due to the discrete nature of block.timestamp updates. Block timestamps are only updated once per block, remaining constant throughout the block's execution. If an operation occurs precisely when the block.timestamp changes, it may result in unexpected behavior.

CodeLocation: https://github.com/code-423n4/2024-10-loopfi/blob/main/src/StakingLPEth.sol#L88-L92
```solidity
if (block.timestamp >= userCooldown.cooldownEnd || cooldownDuration == 0) {
```

Proof of Code:

Add the following test to the `StakingLP.t.sol` contract.

```solidity
function test_unstake_off_by_one_error() public {

        // Set up initial conditions
        stakingLpEth.setCooldownDuration(1 days);


        // User 1 deposits and initiates cooldown
        vm.startPrank(user1);
        liquidityPool.approve(address(stakingLpEth), 0.1 ether);
        stakingLpEth.deposit(0.1 ether, user1);
        stakingLpEth.cooldownShares(stakingLpEth.balanceOf(user1));
        vm.stopPrank();


        // Fast forward to exactly 1 day (cooldown period) minus 1 second
        vm.warp(block.timestamp + 1 days - 1);

  

        // Attempt to unstake should fail
        vm.prank(user1);
        vm.expectRevert(StakingLPEth.InvalidCooldown.selector);
        stakingLpEth.unstake(user1);


        // Fast forward 1 more second to reach exactly the cooldown end
        vm.warp(block.timestamp + 1);

        // Attempt to unstake should now succeed due to >= comparison
        vm.prank(user1);
        stakingLpEth.unstake(user1);


        // Verify that user1 has received their staked amount back
        assertApproxEqAbs(liquidityPool.balanceOf(user1), 0.1 ether, 1);


        // Verify that user1's staked balance is now 0
        assertEq(stakingLpEth.balanceOf(user1), 0);

    }
```

Impact:

This vulnerability allows users to unstake their assets slightly earlier than intended, bypassing the full duration of the cooldown period. While a one-second difference might seem insignificant, in DeFi contexts, this can have substantial implications:

- **Front-Running**: Malicious actors could use this vulnerability to front-run other transactions, potentially manipulating market conditions or liquidity pools to their advantage.
- **Compromised Economic Models**: Many DeFi protocols rely on precise timing for their economic models. This off-by-one error could disrupt carefully balanced tokenomics, especially if exploited at scale.
- **Compounding Effect**: If multiple users consistently exploit this vulnerability, it could lead to a cumulative effect that significantly impacts the protocol's intended behavior over time.
- **Integration Risks**: As DeFi protocols often interact with each other, this timing discrepancy could have cascading effects when integrated with other systems that assume strict adherence to cooldown periods


Recommended mitigations:

1. Replace the >= operator with a strict > operator:
   ```solidity
   if (block.timestamp > userCooldown.cooldownEnd || cooldownDuration == 0) {
   ```
2. If exact timing is crucial, consider adding a small buffer to the cooldown period to account for potential discrepancies.

While the immediate impact of this off-by-one error might seem minor, its potential for exploitation in LoopFi's protocol and having this issue be present on such a critical function, coupled with the cumulative effect of multiple users leveraging this vulnerability, elevates this to a medium severity issue.
