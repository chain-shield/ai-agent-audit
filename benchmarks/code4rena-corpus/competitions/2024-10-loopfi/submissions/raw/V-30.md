# Vulnerability details


## Proof of Concept

There is a new locking.sol contract that allows for users to deposit and then withdraw after a `cooldownduration` has passed, in order to interact with the contract, here are the core methods being used: https://github.com/code-423n4/2024-10-loopfi/blob/d219f0132005b00a68f505edc22b34f9a8b49766/src/Locking.sol#L47-L93

```solidity
    function deposit(uint256 _amount) external {
        if (_amount == 0) revert AmountIsZero();

        deposits[msg.sender].amount += _amount;
        token.safeTransferFrom(msg.sender, address(this), _amount);

        emit Deposited(msg.sender, _amount);
    }

    function initiateCooldown(uint256 _amount) external {
        if (_amount == 0) revert AmountIsZero();
        if (deposits[msg.sender].amount < _amount) revert InsufficientBalanceForCooldown();
        deposits[msg.sender].cooldownStart = block.timestamp;
        deposits[msg.sender].cooldownAmount = _amount;

        emit CooldownInitiated(msg.sender, block.timestamp, _amount);
    }

    /// @notice Withdraw tokens from the contract
    /// @dev If there's a cooldown period set, the tokens can be withdrawn after the cooldown period has passed
    function withdraw() external {
        uint256 _amount;
        if (cooldownPeriod > 0) {
            if (deposits[msg.sender].cooldownAmount == 0) revert NoTokensInCooldown();
            if (block.timestamp < deposits[msg.sender].cooldownStart + cooldownPeriod) revert CooldownPeriodNotPassed();
            _amount = deposits[msg.sender].cooldownAmount;
        } else {
            _amount = deposits[msg.sender].amount;
        }

        deposits[msg.sender].amount -= _amount;
        deposits[msg.sender].cooldownAmount = 0;
        deposits[msg.sender].cooldownStart = 0;
        token.safeTransfer(msg.sender, _amount);

        emit Withdrawn(msg.sender, _amount);
    }

```

The `cooldownDuration` could be set in the `StakingLPEth.sol`, which then means that users are expected to wait [for this duration to pass before being able to claim their stakes](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L92).

Evidently, after a user deposits, in order to withdraw they first have to [initate the cooldown](https://github.com/code-423n4/2024-10-loopfi/blob/d219f0132005b00a68f505edc22b34f9a8b49766/src/Locking.sol#L56) and then later on they can query withdraw.

Problem however is the fact that even though a user can call `initiateCooldown` whenever with whatever amount of assets, the protocol wrongly keeps only one track of the attempted withdrawal, this then means that with every withdrawal attempt, [the cooldown end is freshly set for the amount of asset](https://github.com/code-423n4/2024-10-loopfi/blob/d219f0132005b00a68f505edc22b34f9a8b49766/src/Locking.sol#L59-L66).

Additionally, the value for the cooldown period can be changed via https://github.com/code-423n4/2024-10-loopfi/blob/d219f0132005b00a68f505edc22b34f9a8b49766/src/Locking.sol#L40-L44

```solidity
    function setCooldownPeriod(uint256 _cooldownPeriod) external onlyOwner {
        cooldownPeriod = _cooldownPeriod;
        emit CooldownPeriodSet(_cooldownPeriod);
    }

```

And in the case where the value of the previous cooldownPeriod is < the new cooldownPeriod, users are then DOS'd from their assets for that duration.

## Impact

Users are essentially DOS'd from their assets if they decide to make any consequent withdrawals by intiating a new cooldown which should not be the case, this means a user could be [unfairly locked off from their assets for an extra cooldownPeriod (_potentially 30 days_)](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L92) if they only decide to do one consequent withdrawal.

If they don't notice that this is the bug case it could even go for longer since they might try multiple consequent withdrawals over weeks, essentially locking their assets for even longer in the protocol.

Second case where the value of `cooldownPeriod` is incremented, this means users would be DOS'd from their assets for the duration of `new cooldownPeriod - previous cooldownPeriod `, due to a revert here: https://github.com/code-423n4/2024-10-loopfi/blob/d219f0132005b00a68f505edc22b34f9a8b49766/src/Locking.sol#L74

```solidity
            if (block.timestamp < deposits[msg.sender].cooldownStart + cooldownPeriod) revert CooldownPeriodNotPassed();
```

## Recommended Mitigation Steps

Consider having a case by case attempt for each cooldown being initiated for withdrawals

This way once a specific withdrawal's request end time passes that withdrawal can be withdrawn and user passing in a new request does not reset the previous one.

Also this approach means even if the cooldown period gets changed, users can still access their withdrawals after the cooldown duration of when they had requested their withdrawals.
