# Vulnerability details


## Impact
The current reward distribution mechanism is vulnerable to manipulation, allowing users to artificially inflate their rewards by directly transferring tokens to the vault. This can lead to unfair distribution of rewards, dilution of legitimate rewards, and potential draining of reward tokens from the system. The impact is significant as it undermines the fairness and sustainability of the entire reward system.

## Proof of Concept
The vulnerability exists in the [`_updateRewardIndex`](https://github.com/code-423n4/2024-10-loopfi/blob/main/src/pendle-rewards/RewardManager.sol#L44) function of the `RewardManager` contract:

```Solidity
function _updateRewardIndex()
    internal
    virtual
    override
    returns (address[] memory tokens, uint256[] memory indexes)
{
    // ... [previous code]

    for (uint256 i = 0; i < tokens.length; ++i) {
        address token = tokens[i];

        RewardState memory _state = rewardState[token];
        (uint256 lastBalance, uint256 index) = (_state.lastBalance, _state.index);

        uint256 accrued = IERC20(tokens[i]).balanceOf(vault) - lastBalance;

        // ... [rest of the function]
    }
}
```

The issue arises from the calculation of `accrued` rewards. It assumes that any increase in the vault's token balance is due to legitimate rewards. However, this assumption can be exploited:
- An attacker observes the current balance of a reward token in the vault.
- The attacker transfers additional tokens directly to the vault address.
- When `_updateRewardIndex` is next called, the `accrued` value will include the attacker's transferred tokens.
- This inflated `accrued` value increases the reward index, benefiting the attacker unfairly.

This issue allows an attacker to increase their share of rewards without actually contributing to the protocol.

Manual Review

## Recommended Mitigation Steps
Implement a tracking mechanism for rewards that doesn't rely on balance differences. Instead of using the vault's token balance, maintain a separate accounting system for rewards. This could involve:
. Directly tracking the amount of rewards received from `market.redeemRewards(address(vault))`.
. Updating a dedicated rewards accumulator instead of relying on token balances.
