# Vulnerability details


Overview:

Loopfi protocol's code contains critical instances where function parameters of type `address` are directly compared against state variables. This practice can be exploited in the case of proxy tokens or tokens with multiple addresses, leading to security checks being bypassed and potentially resulting in significant financial losses or unauthorized access to protocol functions.

Description:

In multiple core functions within the contract, there are direct comparisons between an `address` parameter and a state variable (typically `address(underlyingToken)`). While this check aims to ensure operations are performed only on the intended token, it fails to account for the complexities of modern token implementations, particularly proxy tokens.

Proxy tokens often use a fixed proxy address with a separate implementation contract address. By relying solely on address comparison, the contract may fail to recognize legitimate calls from a token's proxy address, even when the underlying logic and token are correct. This oversight can lead to severe unintended behavior, including the bypassing of critical security checks in key protocol operations.

Impact:

This vulnerability could allow an attacker to bypass critical security checks by using a proxy token address that differs from the expected `underlyingToken` address. The potential consequences are severe:

1. Unauthorized access to flash loans: An attacker could potentially borrow funds without proper validation, leading to direct financial losses for the protocol.
2. Incorrect fee calculations: The protocol may charge incorrect fees or fail to charge fees altogether, resulting in economic losses.
3. Manipulation of lever operations: An attacker could potentially manipulate leverage positions, leading to unfair advantages or destabilization of the protocol's financial mechanisms.
4. Bypassing of quota restrictions: In the case of the `setGauge` function, an attacker might be able to manipulate quota settings, potentially leading to over-allocation of resources.

These impacts could result in significant financial losses for the protocol and its users, as well as undermine the integrity of the system's core operations.

Recommended mitigations:

1. Implement a robust token registry or whitelist that includes all valid addresses for each supported token (including proxy and implementation addresses). This registry should be carefully managed and updated.
2. Use interface checks or function calls to verify token behavior rather than relying solely on address comparisons. For example, implement a `isValidToken(address token)` function that performs necessary checks.

The current implementation's reliance on direct address comparisons for token validation creates a significant security vulnerability that could be exploited in systems using proxy tokens or tokens with multiple valid addresses. Addressing this issue is crucial to ensure the robust security of the contract's token-related operations and to protect the protocol and its users from potential financial losses.
