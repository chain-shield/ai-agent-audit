# Vulnerability details

The provided PoolV3 contract, which implements the ERC4626 standard, lacks explicit slippage protection mechanisms. This omission could potentially lead to unexpected losses for users due to price fluctuations or manipulations during transactions.

- https://eips.ethereum.org/EIPS/eip-4626#security-considerations

## Vulnerability Details

The ERC4626 standard [recommends](https://eips.ethereum.org/EIPS/eip-4626#security-considerations) implementing slippage protection for functions that interact with the underlying vault, especially for operations initiated by EOA (Externally Owned Accounts). The current implementation of PoolV3 does not include such protections in its `deposit`, `mint`, `withdraw`, and `redeem` functions.

For example, in the `deposit` function:

```solidity
function deposit(
    uint256 assets,
    address receiver
)
    public
    override(ERC4626, IERC4626)
    whenNotPaused
    nonReentrant
    nonZeroAddress(receiver)
    returns (uint256 shares)
{
    uint256 assetsReceived = _amountMinusFee(assets);
    shares = _convertToShares(assetsReceived);
    _deposit(receiver, assets, assetsReceived, shares);
}
```

There is no mechanism to ensure that the number of shares received meets a minimum expectation set by the user.

## Impact

Without slippage protection:

1. Users may receive fewer shares than expected when depositing or minting.
2. Users may receive fewer assets than expected when withdrawing or redeeming.
3. The contract is vulnerable to sandwich attacks, where an attacker could manipulate the exchange rate just before and after a user's transaction.

These issues could result in financial losses for users, especially in volatile market conditions or when dealing with less liquid assets.

## Recommended Mitigation

1. Implement slippage protection by adding minimum output parameters to relevant functions:

```solidity
function deposit(
    uint256 assets,
    address receiver,
    uint256 minSharesOut
) public returns (uint256 shares) {
    // ... existing code ...
    require(shares >= minSharesOut, "Slippage: insufficient shares out");
    // ... rest of the function ...
}
```

2. Similarly, add maximum input parameters for withdrawal and redemption functions:

```solidity
function withdraw(
    uint256 assets,
    address receiver,
    address owner,
    uint256 maxSharesBurned
) public returns (uint256 shares) {
    // ... existing code ...
    require(shares <= maxSharesBurned, "Slippage: excessive shares burned");
    // ... rest of the function ...
}
```

3. Consider implementing a time-bound slippage protection mechanism to prevent long-pending transactions from executing under unexpected conditions.

4. Add similar protections to `mint`, `redeem`, and other relevant functions.

5. Educate users about the importance of setting appropriate slippage parameters when interacting with the contract.
