# Vulnerability details

## Proof of Concept
Echidna Fuzz testing on the Locking.sol contract was able to uncover a failure with the test_double_withdrawal() test which indicated that after the first successful withdrawal, the Locking.sol contract is allowing a second withdrawal with an amount of 0. This is not the expected behavior, as the second withdrawal should fail after all tokens have already been withdrawn.

Cause:
After the first withdrawal, the contract correctly resets the user's cooldown and deposit state. However, the second withdrawal does not revert properly, and it proceeds with a transfer of 0 tokens, which results in an erroneous transfer and an event emission.

Fix:
We need to ensure that after the first withdrawal, subsequent withdrawals are not allowed if the user's cooldownAmount or depositAmount is 0. The withdraw() function should revert if the amount to withdraw is 0, preventing any erroneous transactions or emissions of events.

Steps to Fix:
Add a Check for Zero Amount in withdraw(): 
In the withdraw() function, add a condition to check whether the amount to withdraw is 0. If it is, the function should revert. 

Conclusion:
The primary risk is misleading information being propagated to users, dApps, or external systems due to the erroneous emission of a Withdrawn event with 0 tokens. While this doesn't impact the integrity of the contract's core logic or security, it can cause confusion, incorrect off-chain handling, and inaccurate financial reporting.

Impact Level:
If off-chain systems, financial records, or automated processes rely on accurate event logs, this can have a Medium impact due to the potential for confusion and erroneous actions.
In cases where event emissions are not critical for external processes, the impact would be Low, but it still presents a usability and clarity issue.

        // Expected behavior
    }
}

## Recommended Mitigation Steps

Updated withdraw() Function in the Locking Contract: 
// Ensure that the withdrawal amount is greater than zero
    require(_amount > 0, "Withdrawal amount is zero");

function withdraw() external {
    uint256 _amount;
    if (cooldownPeriod > 0) {
        if (deposits[msg.sender].cooldownAmount == 0) revert NoTokensInCooldown();
        if (block.timestamp < deposits[msg.sender].cooldownStart + cooldownPeriod) revert CooldownPeriodNotPassed();
        _amount = deposits[msg.sender].cooldownAmount;
    } else {
        _amount = deposits[msg.sender].amount;
    }
    // line 79, Ensure that the withdrawal amount is greater than zero
    require(_amount > 0, "Withdrawal amount is zero");
    deposits[msg.sender].amount -= _amount;
    deposits[msg.sender].cooldownAmount = 0;
    deposits[msg.sender].cooldownStart = 0;
    token.safeTransfer(msg.sender, _amount);
    emit Withdrawn(msg.sender, _amount);
}


This updated withdraw() function ensures that no withdrawal is allowed if the amount to withdraw is 0. The require(_amount > 0, "Withdrawal amount is zero"); line ensures that any attempt to withdraw 0 tokens is reverted.
