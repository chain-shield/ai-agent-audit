# Vulnerability details

## Proof of Concept

Description: In the ```initiateCooldown``` function, if a user initiates a cooldown request again before the previous cooldown period has passed or before they have withdrawn the available tokens, the ```cooldownAmount``` and ```cooldownStart``` values are updated. However, the ```deposits[msg.sender].amount``` is not decreased accordingly.

Impact: This issue can potentially allow users to withdraw their tokens twice:

1- Once by withdrawing the cooldownAmount after the cooldown period ends.

2- Again by withdrawing the remaining amount in deposits[msg.sender].amount if it was not reduced when the cooldown was initiated.

Step-by-Step Attack Scenario:

1- Setup and Deposit:

* The malicious user starts by depositing a significant amount of tokens (e.g., 1000 tokens) into the Locking contract using the deposit function.

* The user's balance in the contract (deposits[msg.sender].amount) now reflects 1000 tokens.

2- Initiating the Cooldown:

* The user calls the initiateCooldown function with the full deposit amount (1000 tokens).
The contract sets deposits[msg.sender].cooldownAmount to 1000 tokens and records the current timestamp in deposits[msg.sender].cooldownStart.

* However, the deposits[msg.sender].amount remains unchanged at 1000 tokens.

3- Cooldown Period Elapses:

* The user waits for the cooldown period to pass. Once the required time has elapsed, the user can withdraw their tokens.

* The user calls the withdraw function. The contract checks that the cooldown period has passed and allows the withdrawal of the 1000 tokens set in cooldownAmount.

* The user now has 1000 tokens back in their wallet, but the contract still shows deposits[msg.sender].amount as 1000 tokens.

4-Second Withdrawal:

* Exploiting the fact that deposits[msg.sender].amount was not reduced during the cooldown initiation, the user calls the withdraw function again.

* This time, since there is no active cooldown and deposits[msg.sender].amount is still 1000 tokens, the user is able to withdraw an additional 1000 tokens.

* The user now ends up with a total of 2000 tokens, effectively doubling their initial deposit due to the logical flaw.

## Recommended Mitigation Steps

* To prevent this issue, the contract should immediately decrease ```deposits[msg.sender].amount``` by the ```cooldownAmount``` when the ```initiateCooldown``` function is called. This ensures that the total token balance is accurately managed, and users cannot withdraw more tokens than they have deposited.
