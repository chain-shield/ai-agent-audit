# Vulnerability details



## Impact
The Treasury contract inherits PaymentSplitter's public `release` functions without any additional restrictions. This allows any external actor to call these functions and release funds to payees as soon as they are received by the Treasury. The lack of time-based restrictions, vesting periods, or access controls on releases creates a risk of premature fund depletion, potentially disrupting the intended distribution schedule and economic model of the protocol.

## Proof of Concept
The Treasury contract inherits from PaymentSplitter without overriding the `release` functions:

[Treasury.sol#L15-L20](https://github.com/code-423n4/2024-10-loopfi/blob/main/src/Treasury.sol#L12)
```solidity
contract Treasury is AccessControl, PaymentSplitter {
    constructor(address[] memory payees, uint256[] memory shares_, address fundsAdmin) PaymentSplitter(payees, shares_) {
        _setupRole(DEFAULT_ADMIN_ROLE, msg.sender);
        _setupRole(FUNDS_ADMINISTRATOR_ROLE, fundsAdmin);
    }
}
```

This means the public `release` functions from PaymentSplitter are directly accessible in Treasury:
Note: you need to check the PaymentSplitter in the project after running forge build then forge test.
```solidity
function release(IERC20 token, address account) public virtual {
        require(_shares[account] > 0, "PaymentSplitter: account has no shares");

        uint256 payment = releasable(token, account);

        require(payment != 0, "PaymentSplitter: account is not due payment");

        // _erc20TotalReleased[token] is the sum of all values in _erc20Released[token].
        // If "_erc20TotalReleased[token] += payment" does not overflow, then "_erc20Released[token][account] += payment"
        // cannot overflow.
        _erc20TotalReleased[token] += payment;
        unchecked {
            _erc20Released[token][account] += payment;
        }

        SafeERC20.safeTransfer(token, account, payment);
        emit ERC20PaymentReleased(token, account, payment);
    }
```

This allows funds to be released as soon as they are received by the contract. Any external actor can call these functions repeatedly to release funds to payees, potentially draining the Treasury rapidly.

## Recommended Mitigation Steps
Implement time-based vesting or rate limiting for fund releases in the Treasury contract. Override the `release` functions to add access controls, ensuring only authorized roles can initiate releases. Consider implementing a distribution schedule that aligns with the protocol's economic model.
