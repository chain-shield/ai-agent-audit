# Vulnerability details

#### **Description**:
The `StakingLPEth` contract, which extends the ERC4626 standard, handles the withdrawal and redemption of assets through its `withdraw` and `redeem` functions. However, these functions lack a slippage protection mechanism, potentially exposing users to loss of funds due to price slippage.

When interacting with the contract, users may experience changes in the exchange rate between assets and shares (the ERC4626 rate) during the time between transaction submission and finalization. This could result in users receiving fewer shares or assets than expected, which can be problematic, especially when large withdrawals or redemptions are performed. The contract currently does not allow users to set a slippage tolerance that could prevent the execution of transactions if the slippage exceeds a certain threshold.

#### **Functions Affected**:
1. **`withdraw(uint256 assets, address receiver, address _owner)`**:
   - This function allows users to withdraw a specific amount of assets from the vault. The exchange rate between shares and assets could change significantly between the initiation and execution of the transaction. This fluctuation could result in users receiving fewer assets than expected without any mechanism to protect them from this potential slippage.

2. **`redeem(uint256 shares, address receiver, address _owner)`**:
   - Similar to `withdraw`, this function allows users to redeem their shares for assets. The exchange rate may be manipulated or naturally fluctuate, leading to fewer assets being received for the given shares. Users are unable to protect themselves from such changes in value, as no slippage protection exists.

#### **Impact**:
Without slippage protection, users are exposed to the risk of receiving fewer assets or shares than they intended when calling the `withdraw` and `redeem` functions. This can happen if the exchange rate in the ERC4626 vault changes due to market conditions, external manipulation, or other factors while a user's transaction is pending. In a worst-case scenario, a user might receive no shares or an insignificant amount in return, losing value while the vault retains the assets.

#### **Example Scenario**:
1. **Withdraw Function**:
   A user calls the `withdraw` function to withdraw 100 assets. While the transaction is pending, the exchange rate in the vault shifts significantly. As a result, the user only receives 80 assets instead of 100, without any way to revert the transaction or set slippage protection.

2. **Redeem Function**:
   A user calls `redeem` to convert 50 shares into assets. During the time it takes to finalize the transaction, the share-to-asset exchange rate drops, and the user only receives 40 assets instead of the expected 50.

#### **Recommended Mitigation**:
To prevent slippage-related losses, it is recommended to introduce a slippage protection mechanism within the `withdraw` and `redeem` functions. This would allow users to set a slippage tolerance, ensuring that if the conversion rate changes by more than a specified percentage, the transaction is reverted.

Possible mitigation strategies include:
- Allowing users to specify the **minimum number of assets** they expect to receive when calling `withdraw`.
- Allowing users to specify the **maximum number of shares** they are willing to redeem for a specific amount of assets.

By incorporating slippage control parameters, users will have greater protection against adverse changes in the vault's exchange rate, reducing the risk of unexpected fund losses.
