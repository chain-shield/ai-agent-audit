# Vulnerability details

## Proof of Concept
Description: The contract initializes `userIndex` to `INITIAL_REWARD_INDEX.Uint128()` when the user’s index is zero. This approach is problematic if users interact with the system after rewards have already started accruing.

* If rewards accumulate in the system before the user’s first interaction, the global reward index for that token would have already increased from its initial state.

* By setting `userIndex` to `INITIAL_REWARD_INDEX` (instead of the current global reward index), the system effectively "short-changes" the user, as they begin accruing rewards from an outdated starting point rather than from the correct, updated index.

This discrepancy can lead to incorrect reward distributions and, potentially, underpayment for users who join after the initial reward distribution begins.

Impact :

* Inconsistent Reward Distribution:

1-Users who join the system later will accrue rewards from INITIAL_REWARD_INDEX instead of the current global index.

2-This results in these users receiving fewer rewards than they are entitled to, given the state of the system.

* Economic Impact on Users:

Over time, the cumulative effect of this discrepancy may significantly affect users, especially those who join the system when it is well-established.

Reasons for High-Risk Classification:

* Direct Financial Impact:

The bug affects how rewards are calculated and distributed, which can lead to financial losses for users who join later. They may receive less than they are entitled to, which undermines the fairness and trust in the reward system.

* Systemic Impact:

If the system operates for a long time with this issue unaddressed, the cumulative effect could lead to significant discrepancies in reward distribution. This might affect user behavior, causing dissatisfaction or even a decline in participation.

* Potential for Exploitation:

Users could potentially manipulate the timing of their interactions to maximize their rewards, especially if they notice this discrepancy. Exploiting this vulnerability could lead to further inconsistencies and unfair advantage.

## Recommended Mitigation Steps

To address this issue, the user’s reward index should be updated to match the current global index for the token when they interact with the system for the first time. This ensures consistency in reward accrual for all users, regardless of when they join.

Proposed Solution:

Instead of initializing `userIndex` to `INITIAL_REWARD_INDEX` , set it to the current global index for the token:

```
if (userIndex == 0) {
    userIndex = getCurrentGlobalIndex(token).Uint128();
}
```

Explanation:

* `getCurrentGlobalIndex(token)` should return the most up-to-date global index for the token, ensuring users start accruing rewards from the correct point in time.

* This approach guarantees that all users, regardless of when they join, receive rewards based on the state of the system at the time of their first interaction.
