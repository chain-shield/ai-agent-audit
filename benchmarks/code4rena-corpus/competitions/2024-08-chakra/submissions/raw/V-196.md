# Vulnerability details

Note: In this submission, the vulnerability is referred to the solidity codebase. 

## Vulnerability details 
If users want to lock tokens on chain A and unlock on chain B, they call `'ChakraSettlementContract::cross_chain_erc20_settlement'`, in the field `'to_handler'` they decide in which handler the cross chain call will happen.

So, initially they lock a certain token amount on the source chain in order to be able to unlock on the destination chain. 

The problem is that in the `ChakraSettlementHandler` and `ChakraSettlement` contracts, no check is done to see if there is the minimum amount to unlock in the destination chain, if this happens users will lose their funds since they locked on chain A but they did not unlocked on chain B. 

Let's imagine a scenario where an user wants to lock a large amount of token on chain A and unlock a large amount of tokens on chain B, on the chain B there couldn't be the required amount to unlock and for this reason the call will fail, resulting in a loss for the user. 

This vulnerability is also amplified by another vulnerability in the protocol, the fact that for the standard ERC20 tokens (all those tokens who do not implement the `ChakraToken` structure) won't be possible to utilize the modes `LockMint` and `MintBurn`, and so for these standard ERC20 tokens is not possible to mint them on the chain B and will only possible to use the mode `LockUnlock` or the mode `BurnUnlock`.
  
## Impact
User could lose their funds by locking them in the handler in the source chain and receiving nothing on the destination chain since there is not the required amount to unlock.

## Tools Used
Manual review, Foundry

## Recommended Mitigation Steps
When standard ERC20 token are used, consider adding a logic that allow the contract to know beforehand if there is the minimum balance required in order to unlock in the destination chain, if the minimum balance required exist, consider adding a logic that allows to set a quantity of tokens in pending mode for a specific address in the handler contract in the destination chain, in this way malicious people cannot front-run legitimate users and will not be able to unlock the funds before someone else try it.
