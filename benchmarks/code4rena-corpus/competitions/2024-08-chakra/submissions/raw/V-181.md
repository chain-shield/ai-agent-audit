# Vulnerability details

Note: In this submission, the vulnerability is referred to the solidity codebase. 

## Vulnerability details
In the Chakra protocol, all the standards ERC20 token are supposed to work and to be utilized, but in some modes and cases this is not possible. 

The modes where this is not possible are: `MintBurn`, `LockMint` and `BurnUnlock`. 

When cross chains transactions are sent using these Handler modes, they will always fail since the standards ERC20 tokens (such as LINK etc) do not implement the `'ChakraToken'` infrastructure. 

In the detail, these standards tokens do not implement the functions `'mint_to'` and `'burn_from'` that are used in the chakra protocol in order to burn and mint tokens. 

## Impact
The impact of this problem vary depending on the SettlementHandler mode, let's see what would the impact of each of them: 

1) `LockMint`, `MintBurn`: In these modes, people can lock their funds on the chain A but then they can't mint others tokens on the chain B. They can't because a standard ERC20 (for example LINK) does not implement the function `mint_to`. 
Generally, in this case, on the chain B, an unlock will be performed, but may be not happen if on destination chain there is not the minimum amount to unlock. 
If this happens, the calls on the destination chain will fail, and the users will not receive nothing on the chain B.
Additionally, in the mode `MintBurn`, where the callback is performed, the transaction will fail since the standard ERC20 token do no implement `burn_from`. 

2) `BurnUnlock`: in this mode, the impact will be smaller since when users will try to burn tokens on chain A, the transaction will revert do not letting them to burn those tokens. The impact here is smaller than MintBurn and LockMint, because here users do not spend any tokens since the transaction will revert instantly.


## Proof of Concept
Here we have a test (done in Foundry) simulating a cross chain transaction using the `BurnUnlock` mode. 

```solidity
function test_SomeERC20CantBeUsedInSomeModalities() public {
//Note: the required validators is setted to 1, all the contracts have been initializated and the mode is setted to BurnUnlock.
uint256 privateKeyValidator1 = 0x12D; 
address validator1 = vm.addr(privateKeyValidator1);

address UserAccount1 = makeAddr("UserAccount1");

//Here owner Adds managers to both chains (arbitrum and ethereum)
vm.selectFork(arbFork);
vm.startPrank(owner);
settlementSignatureVerifierArb.add_manager(bob);
vm.selectFork(ethFork);
settlementSignatureVerifierEth.add_manager(bob);
vm.stopPrank(); 

//Here owner Adds validators to both chains (arbitrum and ethereum)
vm.startPrank(bob);
vm.selectFork(arbFork);
settlementSignatureVerifierArb.add_validator(validator1);
vm.selectFork(ethFork);
settlementSignatureVerifierEth.add_validator(validator1);
vm.stopPrank();

//Here owner adds valid handler on ethereum
vm.selectFork(ethFork);
vm.startPrank(owner); 
chakraSettlementHandlerEth.add_handler("Arbitrum", uint160(address(chakraSettlementHandlerArb)));
vm.stopPrank();

vm.startPrank(UserAccount1);
vm.selectFork(arbFork);

//Give 100 LINK token to user on arbitrum
deal(address(LINK_arb), UserAccount1, 100e18); 
//Approve the handler 
IERC20(address(LINK_arb)).approve(address(chakraSettlementHandlerArb), 100e18);

//This call will fail since LINK in this case, does not implement a 'burn_from' function.
vm.expectRevert(); 
chakraSettlementHandlerArb.cross_chain_erc20_settlement("Ethereum", uint160(address(chakraSettlementHandlerEth)), uint160(address(LINK_eth)), uint160(UserAccount1), 100e18);
vm.stopPrank();

}
```

## Tools Used
Manual review, Foundry

## Recommended Mitigation Steps
Do not allow to use ERC20 standards tokens (Any tokens that does not implement the ChakraToken structure) on the following `'ChakraHandlerSettlement'` modes and chains: 
`MintBurn` on chain A and on chain B. 
`LockMint` on chain B. 
`BurnUnlock` on chain A and on chain B.
