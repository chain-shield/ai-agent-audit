# Vulnerability details

## Impact
The `decode_message` function doesnt correctly parse the `message_id` field from the payload due to an off-by-one error. Because of this, `message_id` will be misaligned, which can lead to incorrect message processing, potential misinterpretation of the message, and downstream errors in any logic that relies on the correct `message_id`.

## Proof of Concept
In the `decode_message` function, the `message_id` is supposed to be extracted from the payload as a 32-byte field. However, the current implementation incorrectly processes 33 bytes instead of 32, leading to an incorrect `message_id`.

https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/codec.cairo#L23-L44

```cairo
23: pub fn decode_message(payload: Array<u8>) -> Message{
24:     let mut version = 0;
25:     let mut payload_type = 0;
26:     let mut message_id_array = ArrayTrait::new();
27:     let mut message_payload = ArrayTrait::new();
28:     let mut i = 0;
29:     loop{
30:         if i <= 0{
31:             version = * payload.span().at(i);  // Version is correctly extracted
32:         }else if i<= 32{                       // Off-by-one error here.  ❌❌❌❌❌
33:             message_id_array.append(* payload.span().at(i));  // This block processes 33 bytes instead of 32
34:         }else if i <= 33{
35:             payload_type = * payload.span().at(i);  // Payload type is extracted
36:         }else if i <= payload.span().len()-1{
37:             message_payload.append(* payload.span().at(i));  // Remaining bytes are treated as payload
38:         }else{
39:             break;
40:         }
41:         i+=1;
42:     };
43: 
44:     let message_id: u256 = u8_array_to_u256(message_id_array.span());  // Incorrect message_id due to the off-by-one error
```

The `message_id` is supposed to be 32 bytes long.
The condition `i <= 32` causes the loop to process 33 bytes (from index 1 to 32), which is one byte too many.


This results in the `message_id` being misaligned, as it includes an extra byte and misses the first byte of the actual `message_id`.

## Recommended Mitigation Steps

The condition should be changed to `i < 32` to ensure that exactly 32 bytes are processed for the `message_id` starting from index 1 and ending at index 31,


```diff
-         }else if i<= 32{
+         }else if i < 32{
```
