# Vulnerability details

## **Impact**

The struct `Message` in `Message.sol` contains `id` which was defined as a `uint256`, but in the contract `MessageV1Codec.sol`, the function `id` is extracted from `_msg[1:33]` which contains 32 bytes and was cast to `byte8` which was further cast to `uint64`. This results in **truncation** of the `id`, where only the lower 64 bits of the value are retained, and the higher 192 bits are discarded. This truncation can lead to:

1. **Loss of Data**: The full `uint256` `id` is not preserved, which can cause incorrect behavior if the `id` is used for critical operations.
   
2. **Collision Risk**: Different `uint256` values could map to the same `uint64` value, leading to **id collisions**. An attacker could exploit this to manipulate the contract's behavior, especially if the `id` is used for transaction identification, cross-chain message handling, or access control.

3. **Incorrect Logic**: If the contract logic relies on the full `uint256` `id` for uniqueness or correctness, truncating it to `uint64` could lead to incorrect behavior, such as misidentifying transactions or allowing unauthorized access.


### **Proof of Concept**

#### Code Reference:

- **`Message.sol`**: The `id` is defined as a `uint256` in the `Message` struct.

  ```solidity
  function id(bytes calldata _msg) internal pure returns (uint64) {
      return uint64(bytes8(_msg[ID_OFFSET:PAYLOAD_TYPE_OFFSET]));
  }
  ```

#### Vulnerability Demonstration:

1. **Truncation Example**:
   - If the `id` is a `uint256` with the value:
     ```solidity
     uint256 id = 0x1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef;
     ```
   - The current code in `MessageV1Codec.sol` will extract only the first 8 bytes and cast it to `uint64`:
     ```solidity
     uint64 truncatedId = uint64(bytes8(_msg[ID_OFFSET:PAYLOAD_TYPE_OFFSET]));
     ```
   - This results in the truncated value:
     ```solidity
     truncatedId = 0x1234567890abcdef;
     ```
   - The higher-order bytes (`0x1234567890abcdef1234567890abcdef1234567890abcdef`) are lost, and only the lower 64 bits (`0x1234567890abcdef`) are retained.

2. **Collision Example**:
   
Two different `bytes calldata _msg` can be give exactly the same id

### **Recommended Mitigation Steps**

1. **Update the `id` function in `MessageV1Codec.sol`** to extract the full 32 bytes and cast it to `uint256`, rather than truncating it to `uint64`. Here's the updated code:

   ```solidity
   function id(bytes calldata _msg) internal pure returns (uint256) {
       require(_msg.length >= PAYLOAD_TYPE_OFFSET, "Message too short");
       return uint256(bytes32(_msg[ID_OFFSET:PAYLOAD_TYPE_OFFSET]));
   }
   ```

2. **Ensure consistency** between the `id` type in `Message.sol` and `MessageV1Codec.sol`. If the `id` is defined as `uint256` in `Message.sol`, it should be handled as `uint256` throughout the codebase.
