# Vulnerability details

## Impact

If the `ChakraSettlementHandlers` are all deployed on the same addresses with the `CREATE2` opcode, cross-chain replays will be possible.

## Proof of Concept

In order cross-chain message to arrive at the destination, a set of validators should sign a special `message_hash` that contains all the important params to prevent replaying the tx except one: destination contract’s `contract_chain_name`:

[ChakraSettlement.sol](https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/settlement/contracts/ChakraSettlement.sol#L170C5-L193C1)

```solidity
function receive_cross_chain_msg(
    uint256 txid,
    string memory from_chain,
    uint256 from_address,
    uint256 from_handler,
    address to_handler,
    PayloadType payload_type,
    bytes calldata payload,
    uint8 sign_type, // validators signature type /  multisig or bls sr25519
    bytes calldata signatures // signature array
) external {
    {
        // verify signature
        bytes32 message_hash = keccak256(
            abi.encodePacked(
                txid,
                from_chain,
                from_address,
                from_handler,
                to_handler,
                keccak256(payload)
            )
        );
```

As we can see, nowhere destination chain is passed to the hash and once signed by the validators, it can be used by malicious users to be replayed across all the `to_handlers`.

Another pre-condition that is needed is for the `to_handler` to have the same address on the other chain as well, which will be most likely the case because contracts are identical and can be deployed like that.

When `to_handlers` are the same, replays are possible because currently, all the params of the hash are destination chain agnostic. ChakraSettlement has another replay protection which will be effectively bypassed because on another chain there won’t be a record with that `txid`:

[ChakraSettlement.sol](https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/settlement/contracts/ChakraSettlement.sol#L199C13-L202C15)

```solidity
require(
      receive_cross_txs[txid].status == CrossChainMsgStatus.Unknow,
      "Invalid transaction status"
  );

```

The impact of replaying cross-chain transactions will be that the user will be able to mint/unlock the X times the number of tokens that he has locked in the source chain, where X is the number of handlers that have the same address.

Example of an attack:

1. `SettlementMode` is `LockMint`
2. User locks 1e18 tokens in chain A to chain B
3. Transaction is signed by the validators and is executed by trusted parties, the user receives 1e18 tokens on chain B
4. 3 more `ChakraSettlementHandler` contracts have the same address as the handler on chain B
5. The user manually replays the transaction across these 3 handlers, receiving 4e18 tokens in total.

## Recommended Mitigation Steps

Include the `contract_chain_name` or `chain_id` in the `message_hash`:

```diff
bytes32 message_hash = keccak256(
    abi.encodePacked(
        txid,
        from_chain,
        from_address,
        from_handler,
        to_handler,
+       contract_chain_name,
+       chain_id,
        keccak256(payload)
    )
```
