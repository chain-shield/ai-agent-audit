# Vulnerability details

## Impact
Users of the ChakraSettlementHandler contract may experience financial losses due to incorrect handling of cross-chain transaction statuses.

## Proof of Concept
The `receive_cross_chain_callback` function in the ChakraSettlementHandler contract
```solidity
// ChakraSettlementHandler.sol, lines 383-393
if (status == CrossChainMsgStatus.Success) {
    if (mode == SettlementMode.MintBurn) {
        _erc20_burn(address(this), create_cross_txs[txid].amount);
    }

    create_cross_txs[txid].status = CrossChainTxStatus.Settled;
}

if (status == CrossChainMsgStatus.Failed) {
    create_cross_txs[txid].status = CrossChainTxStatus.Failed;
}
```
The issue is that the function updates the transaction status to Settled or Failed based on the received status parameter without validation or checks to ensure that the transaction has been successfully processed on the destination chain.

When a user wants to initiate a cross-chain ERC20 token settlement, they call the `cross_chain_erc20_settlement` function. This function performs the necessary steps to lock or burn the tokens on the source chain and creates a new cross-chain transaction with a `Pending` status. The transaction details, including the `txid`, are stored in the `create_cross_txs` mapping.

Now, an attacker who observes the `txid` of this pending transaction can attempt to exploit the vulnerability in the `receive_cross_chain_callback` function. The attacker calls this function directly, passing the observed `txi`d and a `status` of either `Success` or `Failed`, even though the transaction has not been processed on the destination chain yet.

The issue lies in how the `receive_cross_chain_callback` function handles the received `status`. If the `status` is `Success`, the function updates the transaction status to `Settled` and, depending on the settlement mode, may also burn the tokens on the source chain. Similarly, if the `status` is `Failed`, the function updates the transaction status to `Failed`.

The problem is that the `receive_cross_chain_callback` function does not validate whether the transaction has been settled or failed on the destination chain. It blindly trusts the received `status` and updates the transaction status accordingly, without any additional checks or verification.

As a result, the attacker can manipulate the transaction status by calling the `receive_cross_chain_callback` function with a fabricated `status`, even though the transaction has not been processed on the destination chain. This leads to an inconsistency between the actual state of the cross-chain settlement and the recorded transaction status in the ChakraSettlementHandler contract.

Manual review

## Recommended Mitigation Steps
The `receive_cross_chain_callback` function should include additional checks and validation before updating the transaction status. 
```diff
// ChakraSettlementHandler.sol, lines 365-374
if (status == CrossChainMsgStatus.Success) {
+   // Verify that the transaction has been successfully processed on the destination chain
+   require(isTransactionSettled(txid), "Transaction not settled on destination chain");

    if (mode == SettlementMode.MintBurn) {
        _erc20_burn(address(this), create_cross_txs[txid].amount);
    }

    create_cross_txs[txid].status = CrossChainTxStatus.Settled;
}

if (status == CrossChainMsgStatus.Failed) {
+   // Verify that the transaction has indeed failed on the destination chain
+   require(isTransactionFailed(txid), "Transaction not failed on destination chain");

    create_cross_txs[txid].status = CrossChainTxStatus.Failed;
}
```
The added `isTransactionSettled` and `isTransactionFailed` functions should be implemented to verify the actual status of the transaction on the destination chain before updating the status in the ChakraSettlementHandler contract by querying the destination chain or using a reliable oracle mechanism.
