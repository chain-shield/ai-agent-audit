# Vulnerability details

## Impact

When a cross-chain ERC20 transfer is initiated, and the destination `ChakraSettlement` contract processes the message via `receive_cross_chain_msg`, it emits a `CrossChainHandleResult` event. Chakra validators then detect this event and invoke `ChakraSettlement::receive_cross_chain_callback` on the source chain to finalize the cross-chain message. The issue is that the signatures used for validation do not include the `from_chain` information. This omission creates a vulnerability where a malicious user can front-run the `receive_cross_chain_callback` and provide a fraudulent `from_chain` value that is not approved for the `from_handler`. This results in the cross-chain message status being set to `Failed`, thereby blocking the transaction from being finalized.
```solidity
function receive_cross_chain_callback(
    uint256 txid,
    string memory from_chain,
    uint256 from_handler,
    address to_handler,
    CrossChainMsgStatus status,
    uint8 sign_type,
    bytes calldata signatures
) external {
>>>    verifySignature(txid, from_handler, to_handler, status, sign_type, signatures);
    processCrossChainCallback(txid, from_chain, from_handler, to_handler, status, sign_type, signatures);
    emitCrossChainResult(txid);
}

function verifySignature(
    uint256 txid,
    uint256 from_handler,
    address to_handler,
    CrossChainMsgStatus status,
    uint8 sign_type,
    bytes calldata signatures
) internal view {
    bytes32 message_hash = keccak256(
>>>        abi.encodePacked(txid, from_handler, to_handler, status)
    );

    require(signature_verifier.verify(message_hash, signatures, sign_type),"Invalid signature");
}
```
In the above code, the `from_chain` is not included in the signatures, which enables an attacker to exploit this vulnerability by front-running the `receive_cross_chain_callback` function with an invalid `from_chain` for the `from_handler`. As a result, the `ChakraSettlementHandler::receive_cross_chain_callback` will return `false`, marking the transaction as `Failed`:
```solidity
function processCrossChainCallback(
    uint256 txid,
    string memory from_chain,
    uint256 from_handler,
    address to_handler,
    CrossChainMsgStatus status,
    uint8 sign_type,
    bytes calldata signatures

        ISettlementHandler(to_handler).receive_cross_chain_callback(

        create_cross_txs[txid].status = status;
    } else {
>>>        create_cross_txs[txid].status = CrossChainMsgStatus.Failed;

```
`ISettlementHandler(to_handler).receive_cross_chain_callback` returns `false` if the `from_handler` is not approved for the `from_chain`:

After the malicious's user transaction is executed, the original validator transaction will be unable to execute due to the cross-chain message status already being set to `Failed`:
```solidity
 function processCrossChainCallback(
    uint256 txid,
    string memory from_chain,
    uint256 from_handler,
    address to_handler,
    CrossChainMsgStatus status,
    uint8 sign_type,
    bytes calldata signatures
) internal {
    require(
        create_cross_txs[txid].status == CrossChainMsgStatus.Pending,
        "Invalid transaction status"

    // --SNIP
}
```

As a result, malicious users can monitor the mempool on the source chain and front-run any `receive_cross_chain_callback` to prevent the cross-chain message from being finalized. In addition, if the settlement mode is `MintBurn`, the tokens on the source chain will be never be burned.

## Proof Of Concept
Consider the following scenario:
1. A cross-chain ERC20 transfer was already initiated from Ethereum to Polygon, and the `ChakraSettlement` already received the message on Polygon and emitted the event `CrossChainHandleResult`
2. Chakra validators detect the `CrossChainHandleResult` event, sign the message, and initiate a transaction to call `ChakraSettlement::receive_cross_chain_callback` on Ethereum to finalize the cross-chain message.
3. Bob, a malicious user, monitors Ethereum’s mempool and identifies the `receive_cross_chain_callback` transaction. He copies the function arguments (including the `signatures`) and front-runs the transaction by calling `ChakraSettlement::receive_cross_chain_callback` with a `from_chain` that is not approved for the `from_handler`.
4. Bob's transaction is executed first, and the signature verification passes because `from_chain` is not included in the verification.

    4.1 The function [interacts with the handler contract](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/settlement/contracts/ChakraSettlement.sol#L318) to process the message, but since the `from_chain` is not approved for the handler, the function [returns `false`](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/ChakraSettlementHandler.sol#L374-L376).
    
    4.2 As a result, the cross-chain message status is [set to `Failed`](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/settlement/contracts/ChakraSettlement.sol#L329).

5. When the validators' transaction attempts to execute, it [will revert](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/settlement/contracts/ChakraSettlement.sol#L312-L315) since the cross-chain message status is already set to `Failed`.
