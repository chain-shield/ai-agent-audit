# Vulnerability details

## Impact
A single signature is enough to bypass the  `required_validators` threshold, due to inefficient validation for duplicate signatures.

## Description
The `receive_cross_chain_callback()` & `receive_cross_chain_msg()` methods of `ChakraSettlement.sol` use signatures to validate the provided parameters before executing the trx/msg:

In both functions the validation is executed like this:

https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/ChakraSettlement.sol#L194-L197

```solidity
  require(
                signature_verifier.verify(message_hash, signatures, sign_type),
                "Invalid signature"
            );
```

It calls a separate contract(`signature_verifier.verify()`) which validates the signatures like this:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/settlement/contracts/SettlementSignatureVerifier.sol#L193-L215

```solidity
...

 for (uint256 i = 0; i < len; i += 65) {
            bytes memory sig = signatures[i:i + 65];
            if (
                validators[msgHash.recover(sig)] && ++m >= required_validators
            ) {
                return true;
            }
        }
...
```

The problem is that if the recovered address from the signature is from a valid validator the incrementer (`m`) get's increased regardless if that signature was used in a previous loop already.

There is no additional logic in  `receive_cross_chain_callback()` & `receive_cross_chain_msg()` as well that make sure the array of provided signatures does NOT contain duplicate entries.


## Proof of Concept
- `required_validators` is set to 5 and we have 5 addresses set as validators - this assumes the protocol expects that 5 different validators have signed the transaction before it can be executed
- only `validator 1` creates a signature and  `receive_cross_chain_callback()` is called with the signatures array containing 5 times the signature of `validator 1`. Since there are no duplicate checks, the loop will validate the signature is valid 5 times and the check will pass
- the transaction is executed even though only 1 validator actually signed it


## Tools Used
Manual review

## Recommended Mitigation Steps
Inside the Verifier contracts in both the `handler` and `settler` folders modify the `verifyECDSA()` function with an additional check that makes sure the provided `signatures` array does not contain duplicate signature, but only unique ones.
