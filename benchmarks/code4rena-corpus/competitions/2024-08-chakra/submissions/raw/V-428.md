# Vulnerability details

## Impact
Vulnerability arises when `tokens` with different `decimal` are transferred across chains without proper conversion. This can lead to a situation where users may receive an `incorrect amount of tokens` on the destination chain, either more or less than intended.

## Proof of Concept
The core issue lies in the `cross_chain_erc20_settlement()` and `receive_cross_chain_msg()` functions, where token amounts are transferred without considering the `decimal` differences between the `source` and `destination` tokens.

1. [`cross_chain_erc20_settlement()`](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L123-L131): 
This function `locks` or `burns` a specified `amount` of tokens on the `source` chain. It assumes that the `amount` specified is directly transferable to the `destination` chain without any conversion.
```solidity
        if (mode == SettlementMode.MintBurn) {
            _erc20_lock(msg.sender, address(this), amount); // @audit-info Lock amount
        } 
        ---SNIP---
        } else if (mode == SettlementMode.BurnUnlock) {
            _erc20_burn(msg.sender, amount); // @audit-info Burn amount
        }
```
2. [`receive_cross_chain_msg()`](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L321-L350):
This function is responsible for `minting` or `unlocking` tokens on the `destination` chain. It directly uses the `amount` from the cross-chain message(`transfer_payload.amount`) without adjusting for any `decimal differences` between the tokens on the `source` and `destination` chains.
```solidity
                // Decode transfer payload
                ERC20TransferPayload memory transfer_payload = codec
                    .deocde_transfer(msg_payload);

                if (mode == SettlementMode.MintBurn) {
                    _erc20_mint(

                } else if (mode == SettlementMode.LockUnlock) {
                    _erc20_unlock(
                        AddressCast.to_address(transfer_payload.to),
                        transfer_payload.amount  // @audit-info Unlock same amount
                    );

                    return true;
                } 
                ---SNIP---
```
**Issue:** 
The direct transfer of `amounts` without considering `decimal` differences can lead to significant discrepancies.

**Scenario**
For example, if `TokenA` on `ChainA` has `18 decimals` and `TokenB` on `ChainB` has `6 decimals`, transferring `1 TokenA` would result in `1,000,000 TokenB` being minted/unlocked, which is incorrect.

## Recommended Mitigation Steps
Implement a conversion mechanism to adjust token amounts based on their decimals at destination
```diff

+   // Normalization function
+   function normalizeAmount(uint256 amount, uint8 fromDecimals, uint8 toDecimals) internal pure returns (uint256) {

+           return amount / (10 ** (fromDecimals - toDecimals));
+       } else if (fromDecimals < toDecimals) {
+           return amount * (10 ** (toDecimals - fromDecimals));
+       } else {
+           return amount;
+       }
```
