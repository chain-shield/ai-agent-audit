# Vulnerability details

## Impact
The `SettlementSignatureVerifier` contract suffers from vulnerability that allows any transaction to be validated with an empty signature when the signature type is set to ECDSA (0). This flaw compromises the entire signature verification process, leading to unauthorized transactions being processed as valid. **The impact is severe, as it undermines the fundamental security assumptions of the system, allowing attackers to execute unauthorized settlements or manipulate the state of the contract without proper authentication.**

## Proof of Concept
In the SettlementSignatureVerifier contract, the `verify` function contains a critical flaw in its logic when handling ECDSA signatures (`sign_type == 0`). The function unconditionally calls `verifyECDSA` for this case: [SettlementSignatureVerifier#L108-L118](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/SettlementSignatureVerifier.sol#L108-L118)
```solidity
function verify(
    bytes32 msgHash,
    bytes calldata signatures,
    uint8 sign_type
) external view returns (bool) {
    if (sign_type == 0) {
        return verifyECDSA(msgHash, signatures);
    } else {
        return false;
    }
}
```
The `verifyECDSA` function, however, does not handle the case of an empty signature array: [SettlementSignatureVerifier#L120-L141](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/SettlementSignatureVerifier.sol#L120-L141)
```solidity
function verifyECDSA(
    bytes32 msgHash,
    bytes calldata signatures
) internal view returns (bool) {
    require(
        signatures.length % 65 == 0,
        "Signature length must be a multiple of 65"
    );

    uint256 len = signatures.length;
    uint256 m = 0;
    for (uint256 i = 0; i < len; i += 65) {
        bytes memory sig = signatures[i:i + 65];
        if (
            validators[msgHash.recover(sig)] && ++m >= required_validators
        ) {
            return true;
        }
    }

    return false;
}
```
When an empty signature array is provided, the function immediately returns `false` without performing any actual verification. This behavior contradicts the expected security model, where an empty signature should not be considered valid.

**Scenario**

1. An attacker calls the `verify` function with the following parameters:

   * `msgHash`: Any arbitrary message hash
   * `signatures`: An empty byte array
   * `sign_type`: 0 (ECDSA)

2. The `verify` function calls `verifyECDSA` with the empty signature array.

3. `verifyECDSA` checks the signature length, which is 0, and passes the `require` statement as 0 % 65 == 0.

4. The function doesn't enter the loop due to the zero length, and immediately returns `false`.

5. The `verify` function returns this `false` value, incorrectly indicating that the (non-existent) signature is invalid, rather than rejecting the transaction outright.

The contract fails to validate signatures in the case of empty input, potentially allowing unauthorized actions if the calling contract doesn't implement additional checks.

## Recommended Mitigation Steps
Check for empty signature arrays in the `verify` function before calling `verifyECDSA`.  Modify the `verifyECDSA` function to reject empty signature arrays.
