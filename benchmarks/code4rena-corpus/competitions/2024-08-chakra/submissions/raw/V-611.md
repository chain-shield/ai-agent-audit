# Vulnerability details

## Impact

BurnUnlock Mode in the Handler Contract Can Prevent Users From Accessing Their Tokens on either chain if the transaction reverts during the settlement:`receive_cross_chain_msg` in the settlement contact that calls the destination handler:`receive_cross_chain_msg`.

When a validator tries to execute the transaction settlement:`receive_cross_chain_message` on the destination chain handler contract and there isn't sufficient balance to satisfy the transaction amount sent by the user on the destination handler contract, this leaves the user with no token balance on either chain until the balance has been topped up in the destination handler contract and after that, the validator retrying to send the user transaction again via the settlement:`receive_cross_chain_message`.

This can happen if there's a demand for tokens on one chain over the other for various reasons, and high amounts of tokens are being sent from the chain with low demand to high demand for tokens.


## Proof of Concept

BurnUnlock Mode in The Handler Contract Can Prevent Users From Accessing Their Tokens on either chain if the transaction reverts during the settlement:`receive_cross_chain_msg` in the settlement contact that calls the destination handler:`receive_cross_chain_msg`
here: 

```solidity
else if self.mode.read() == SettlementMode::BurnUnlock{
    token.transfer(u256_to_contract_address(transfer.to), transfer.amount);
}
```
This revert can occur when the handler on the destination chain doesn't have enough balance to satisfy the unlock call that the validator is executing and therefore reverts on token transfer.

Once this revert happens, no matter how long or how many times the validator retries the transaction, it would keep reverting until the sufficient balance is topped up in this handler contract to satisfy the cross chain transaction amount, in turn, rendering the user inaccessible to his funds on the source chain and on the destination chain until the balance is topped and the validator retries sending the cross chain message. This also leaves the cross chain message status in the settlement:`received_tx` on the destination chain as Unknown, whereas this is a Failed transaction as it wasn't able to satisfy the user on either chain.

This same issue occurs with Lock/Unlock mode but I treated them as different issues because with Lock/Unlock mode, the tokens are `locked` and not `burnt` i.e lost forever. A solution would be to instead of preventing the user from access to his funds on either chain, due to the balance check revert, would be to return a false boolean in the handler contract that has the insufficient balance to handle the tx amount rather than revert with "Insufficient balance".
A callback can then be processed back to the source chain with that boolean to unlock the users token for them. With burn you cannot unlock whats been burnt.

See code below from the handler:`cross_chain_erc20_settlement` :

```solidity
  if self.mode.read() == SettlementMode::MintBurn{
      token.transfer_from(get_caller_address(), get_contract_address(), amount);
  }else if self.mode.read() == SettlementMode::LockMint{
      token.transfer_from(get_caller_address(), get_contract_address(), amount);
  }else if self.mode.read() == SettlementMode::BurnUnlock{
      // BurnUnlock mode burns the tokens before sending the cross chain tx
      token_burnable.burn_from(get_caller_address(), amount);
  }else if self.mode.read() == SettlementMode::LockUnlock{
     // LockUnlock mode locks the tokens before sending the cross chain tx
      token.transfer_from(get_caller_address(), get_contract_address(), amount);
  }
```


## Recommended Mitigation Steps

Rather than burning the tokens on initiating the cross chain transaction the tokens can be locked and then on successful callback, be burnt.
Also, instead of reverting when the balance is insufficient and preventing the user from having access to tokens on both chains temporarily, due to the balance check revert, return a false boolean instead and process a callback to unlock the tokens that were supposed to be burnt.
Then the user can try again when the balance of tokens on destination chain is sufficient for their transaction.
