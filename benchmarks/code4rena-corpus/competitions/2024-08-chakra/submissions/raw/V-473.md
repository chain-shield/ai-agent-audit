# Vulnerability details

Note: In this submission, the vulnerability is referred to the Cairo codebase, and this does not apply also for the solidity codebase. 

## Vulnerability details
In the Chakra protocol, the validators call `settlement::receive_cross_chain_msg` by signing the `message_hash` in the field `signatures`.

The problem is that differently from the Solidity codebase, in the Cairo codebase, when `settlement::receive_cross_chain_msg` is triggered, is not checked if the `txid` has an `Unknown` status or not. Since the status of a transaction is not checked, malicious users could continuously call the function `settlement::receive_cross_chain_msg` with the same `txid` and the used signatures of the validators without reverting. 

## Impact
Since people are able to continuously call `settlement:receive_cross_chain_msg`, they are able to mint / unlock tokens from a certain handler, and in this way, they could drain the funds of the entire handler contract. 

## Proof of Concept
When users want to send cross chain transactions, they need to pass through `handler_erc20::cross_chain_erc20_settlement` on the source chain, then, once a event is emitted, the validators will call `settlement::receive_cross_chain_msg` on the destination chain using the data of the event and by signing the transaction. 

After the cross chain transaction is completed, the malicious users (those who already sent the previous legit cross chain transaction) could use the same signature of the validator and pass the same arguments to `settlement::receive_cross_chain_msg`. In this way they can drain the funds in a certain handler. 

The handler where malicious users could steal funds or mint others tokens is respectively located in the field `to_handler` when calling `settlement::receive_cross_chain_msg`. 

Let's make a practical example: 
Let's imagine that Luca (a malicious user) send a legitimate cross chain transaction between `Ethereum` and `Starknet` by locking and unlocking 100 LINK. 

He calls `handler_erc20::cross_chain_erc20_settlement` and locks 100 LINK on `Ethereum`, and then he receives 100 LINK on Starknet when the validators call `settlement::receive_cross_chain_msg`. 
Now Luca could start his malicious intention where he could call `settlement::receive_cross_chain_msg` on `Starknet` with the same data and signature of the validators (he has it because it has already been used). 
By doing so, every time Luca does this, he will unlock 100 LINK tokens on `Starknet` for free.

## Recommended Mitigation Steps
As in `settlement::receive_cross_chain_callback`, make sure that the status of the transaction ids is always checked in `settlement::receive_cross_chain_msg`, and allow users to call this function only if the status is set to `Unknown`. 

Consider adding this line of code in `settlement::receive_cross_chain_msg`:

```javascript

assert(self.created_tx.read(cross_chain_msg_id).tx_status ==
CrossChainMsgStatus::UNKOWN, 'tx status error');

```
