# Vulnerability details

## Impact
The transaction Id that was generated in the handler contract can differ from the transaction id that would be used in the settlement contract and further processing of the cross chain transaction.
This happens when a user calls the `ChakraSettlement:send_cross_chain_msg()` directly with random values and uses another users address in the `from_address` parameter thereby affecting that users nonce tracking.
e.g user B directly calling  `ChakraSettlement:send_cross_chain_msg()` with the `from_address` value as  user B
This increases user A's nonce without user A ever initiating any cross chain transaction from  the handler.

```solidity
 function send_cross_chain_msg(
        string memory to_chain,
        address from_address,
        uint256 to_handler,
        PayloadType payload_type,
        bytes calldata payload
) external {
```

This causes transaction Id discrepancies between the handler and settlement contract. Thus, all following transactions from the handler contract by the affected user would remain in a pending state forever and prevent the cross chain callbacks from happening for those transactions because the transaction Id that was generated in the handler contract was not the same transaction Id generated in the settlement contract that handled the cross chain interaction.

```solidity
require(
    create_cross_txs[txid].status == CrossChainTxStatus.Pending,
    "invalid CrossChainTxStatus"
);
```

This check exists in the source chain handler contract, the txid processed/sent into this callback check is the txid generated in the settlement which differs from the one generated in the handler thereby always reverting.

Additionally,
If the Mode of the Handler is in MintBurn this can also lead to the tokens that were initially locked for burning not getting burnt and instead always reverting.

```solidity
 if (status == CrossChainMsgStatus.Success) {
      if (mode == SettlementMode.MintBurn) {
          _erc20_burn(address(this), create_cross_txs[txid].amount);
      }
  
      create_cross_txs[txid].status = CrossChainTxStatus.Settled;
  }
```

## Proof of Concept

In the handler contract where the txid is created, it makes use of the users incremented nonce in the generation process i.e the `nonce_manager[msg.sender]`

```solidity
  // Create a new cross chain tx
    uint256 txid = uint256(
        keccak256(
            abi.encodePacked(
                chain,
                to_chain,
                msg.sender, // from address for settlement to calculate txid
                address(this), //  from handler for settlement to calculate txid
                to_handler,
                nonce_manager[msg.sender]
            )
        )
    );
```

If you take a look at the chakra settlement contract that receives this txid, it tries to reconstruct it from the very beginning using a `from_address` function parameter to track the users nonce value to be in line with whats in the handler contract.

```solidity
uint256 txid = uint256(
            keccak256(
                abi.encodePacked(
                    contract_chain_name, // from chain
                    to_chain,
                    from_address, // msg.sender address
                    from_handler, // settlement handler address
                    to_handler,
                    nonce_manager[from_address]
                )
            )
        );
```

The problem is that this function is an external function that anyone can call and it uses the `from_address` function parameter.
Meaning that another user can increment the nonce of a user so that when the user finally sends in their transaction from a handler a discrepancy can occur in the two tx's id when they are supposed to be the same.

This can prevent callbacks from happening and transactions to be in a pending state because when validators are trying to process cross chain call backs and calling the handlers `receive_cross_chain_callback` the transaction ID passed wasnt the tx id that was originally created in sending the cross chain message from the handler contract.
So this check reverts the tx:

```solidity
require(
    create_cross_txs[txid].status == CrossChainTxStatus.Pending,
    "invalid CrossChainTxStatus"
 );
```

I replaced the test contracts in the handler folder that simulated the chakra settlement contract with the actual settlement contracts and put it into a folder called MyTestsContracts and tested with that using foundry.

## Recommended Mitigation Steps
Switch away from using the `from_address` without checks as function parameter that anyone can use to affect users cross chain message transaction ID generation.
