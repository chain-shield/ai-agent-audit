# Vulnerability details

## Abstract

The full lifecycle of cross-chain message 

1. User start cross-chain ERC20 transaction in [ChakraSettlementHandler.cross_chain_erc20_settlement](https://github.com/code-423n4/2024-08-chakra/blob/f61c899c22492bdf5bdcb07cdb62ea9b4cd38825/solidity/handler/contracts/ChakraSettlementHandler.sol#L111)
This is going to generate `txid` and keep a record in `create_cross_txs[txid]`.
1. The handler from step 1 calls [ChakraSettlement.send_cross_chain_msg](https://github.com/code-423n4/2024-08-chakra/blob/f61c899c22492bdf5bdcb07cdb62ea9b4cd38825/solidity/settlement/contracts/ChakraSettlement.sol#L111) 
which is going to create another `txid` and keep a record in `create_cross_txs[txid]`.
1. The message is now send to destination chain and a call to [ChakraSettlement.receive_cross_chain_callback](https://github.com/code-423n4/2024-08-chakra/blob/f61c899c22492bdf5bdcb07cdb62ea9b4cd38825/solidity/settlement/contracts/ChakraSettlement.sol#L256) is expected.
1. The callback will call [ChakraSettlementHandler.receive_cross_chain_callback](https://github.com/code-423n4/2024-08-chakra/blob/f61c899c22492bdf5bdcb07cdb62ea9b4cd38825/solidity/handler/contracts/ChakraSettlementHandler.sol#L365)
In this step the call is only processed if the status is pending, this is important to make sure that we only process any given message once.
```
require(
  [txid].status == CrossChainTxStatus.Pending,
  invalid CrossChainTxStatus"
);
```

## Attack
An attacker can watch the mempool for a valid `success` calls to `ChakraSettlement.receive_cross_chain_callback` and frontrun it with same parameters except for `from_chain`, this will result in the transaction marked as `Failed` and the success call will not be processed.

1. `ChakraSettlement.receive_cross_chain_callback` does not validate `from_chain` input parameter.
2. It is then passed to `ChakraSettlementHandler.receive_cross_chain_callback`
if the `from_chain` is invalid this function will simply return `false` https://github.com/code-423n4/2024-08-chakra/blob/f61c899c22492bdf5bdcb07cdb62ea9b4cd38825/solidity/handler/contracts/ChakraSettlementHandler.sol#L374
3. Then in [ChakraSettlement.receive_cross_chain_callback](https://github.com/code-423n4/2024-08-chakra/blob/f61c899c22492bdf5bdcb07cdb62ea9b4cd38825/solidity/settlement/contracts/ChakraSettlement.sol#L317) will be marked as failed `create_cross_txs[txid].status = CrossChainMsgStatus.Failed;`.
4. When the valid call is received it will [revert](https://github.com/code-423n4/2024-08-chakra/blob/f61c899c22492bdf5bdcb07cdb62ea9b4cd38825/solidity/settlement/contracts/ChakraSettlement.sol#L312) because the status was changed to `Failed`.


## Impact

- All successful transaction can be marked as `failed`.
- Tokens are not burnt when the cross-chain message was successful, and depending on how this is handled by the protocol this could be a double spend.
- Watching the mempool and frontrunning is trivial so the attack can be created easily.
- Leaving the protocol in an inconsistent sate, as the transaction is marked as `Failed` in `ChakraSettlement` but it is still `Pending` in `ChakraSettlementHandler` which is [breaking invariant](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/README.md?plain=1#L108) .
