# Vulnerability details

## Impact

In the `cross_chain_erc20_settlement()`, users submit their cross-chain transactions to transfer tokens and release them on the destination handler contract. Additionally, `txId` is generated inside of the function. The problem is that this id is derived using different information on different chain breaking compatibility and violating the spec.


## Proof of Concept

Take a look at how txId is generated on the Starknet:

https://github.com/code-423n4/2024-08-chakra/blob/main/cairo/handler/src/handler_erc20.cairo#L183
```
 let tx_id = LegacyHash::hash(get_tx_info().unbox().transaction_hash, self.msg_count.read());

```

Here we use transaction hash and `msg_count` state variable that's increased with each call to the `cross_chain_erc20_settlement()`. On Ethereum, different approach is used:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/ChakraSettlementHandler.sol#L139-149
```
uint256 txid = uint256(
            keccak256(
                abi.encodePacked(
                    chain,
                    to_chain,
                    msg.sender, // from address for settlement to calculate txid
                    address(this), //  from handler for settlement to calculate txid
                    to_handler,
                    nonce_manager[msg.sender]
                )
            )
        );

```

As per docs:

```
Cross-chain transaction IDs are uniquely generated based on the source and destination chain information, sender, handler addresses, and nonce.
```

As you can see, `txId` generation is done correctly on Ethereum and the wrong way on Starknet. This can result in an unexpected behavior violating the spec and affecting offchain services when transferring cross-chain messages.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Change the way `txId` is generated on the Starknet chain.
