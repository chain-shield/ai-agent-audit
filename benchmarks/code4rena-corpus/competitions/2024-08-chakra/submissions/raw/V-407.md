# Vulnerability details

## Impact
In both `settlement.cairo` and `handler_erc20.cairo` contracts there is a `receive_cross_chain_callback()` function as the last step in a cross-chain transaction. In both cases, these functions just set the final transaction status either to Success or to Failed. 

The problem occurs if the transaction fails on the destination chain and user has already locked his tokens on the source chain. None of the callback methods implement any kind of refund mechanism in case the transaction status is set to Failed. This leads to the loss of funds for the user.  

## Proof of Concept
Simple steps describing the problem: 

1. Alice initiates a cross-chain transaction from Chain A to Chain B
2. Alice locks her tokens on the Chain A
3. The processing continues and all events are emitted correctly
4. The transaction fails on the Chain B for any reason (gas, invalid handler, etc.) 
5. The transaction will emit event with the proper status
6. Validators will trigger the callback function on the Chain A 
7. The Chain A will go over the message, and set the final status of the whole transaction
8. Even if the transaction's status is Failed in this case, Alice's tokens are lost and there is no refund 

## Tools Used
Manual Review, VS Code
## Recommended Mitigation Steps
Implement a proper refund mechanism so that users can get their tokens (transfer.amount) back if the transaction on the other chain fails. 

A solution can vary from simple ones to more sophisticated based on your preferences. But one simple suggestion would be to have a mapping to store locked funds for the user until the transaction is processed. 
However it is important to handle this mapping correctly and to clear it afterwards so that the user can't get his refund multiple times.
