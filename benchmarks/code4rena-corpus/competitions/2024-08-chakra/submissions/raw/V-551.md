# Vulnerability details

## Description: 
In `BaseSettlementHandler.sol` and `BaseSettlement.sol`, the `_Settlement_handler_init` function and `_Settlement_init` function don't have any initializer modifier or any access control respectively and these are public functions, because of this anyone can call these function and manipulate state of the contract. These functions are responsible for initializing critical state variables of the protocol like Owner, settlement, verifier, mode, token, chain, managers, chain name, chained, and other important variables.

An Attacker can call the `_Settlement_handler_init` function and can manipulate the `mode` state variable and then the attacker can send a transaction from `ChakraSettlementHandler::cross_chain_erc20_settlement` with any amount and if the `mode` variable is not intended according to function Then the transaction will become successful and Attacker can take that amount of funds from another chain.

## Impact: 
Potential for unauthorized parties to control the contract completely. State Manipulation, Business Logic Disruption, Loss of Funds, Incorrect Cross-Chain Transactions, Ownership Takeover, Reinitialization Attack, Upgradeability Exploit

## Scenario Breakdown:

- During Initialization :

  - The `initialize` function is called with proper arguments, and it internally calls `_Settlement_handler_init` to set key state variables (such as owner, token, settlement, etc.).

  - The `initializer` modifier ensures that this initialization logic is executed only once.

- After Initialization :

  - The `initialize` function cannot be called again.

  - However, since `_Settlement_handler_init` is a public function, it remains exposed. Anyone can call `_Settlement_handler_init` directly and reinitialize critical state variables like owner, token, settlement, etc.

  - This leads to a vulnerability where an attacker can call `_Settlement_handler_init` and reinitialize the contract, taking control of the contract and manipulating important functionality.

## Proof of Concept:
For State Manipulation, Ownership Takeover, Reinitialization Attack, Upgradeability Exploit :

- An attacker can call the `BaseSettlementHandler::_Settlement_handler_init` and `BaseSettlement::_Settlement_init` functions to manipulate the state and reinitialize the contracts because these functions don't have any access control and it is public.

For Loss of Funds, Incorrect Cross-chain Transactions :

1. An attacker reinitializes the `BaseSettlementHandler::_Settlement_handler_init` function.
2. Attacker changes `mode` to anything like 4 and enums in Solidity are treated as their underlying integer representation, and Solidity doesn't perform automatic bounds checking when assigning values to enums.
3. Now the attacker calls `ChakraSettlementHandler::cross_chain_erc20_settlement` this function with unexpected `mode` and any amount they need on another chain. Also, this function is not payable.
4. According to the `cross_chain_erc20_settlement` function, funds are only deposited into this contract when `mode` is MintBurn, LockUnlock, LockMint, BurnUnlock.
5. In this case, an attacker can claim any amount of money on another chain
   See [cross_chain_erc20_settlement](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L111).

## Recommended Mitigation:

1. Add the `initializer` Modifier to `_Settlement_handler_init` and `_Settlement_init` to ensure it can only be called once.
2. Add Access Control (e.g., onlyOwner) to restrict who can call `_Settlement_handler_init directly`.
3. Make `_Settlement_handler_init` Internal to prevent external calls.
