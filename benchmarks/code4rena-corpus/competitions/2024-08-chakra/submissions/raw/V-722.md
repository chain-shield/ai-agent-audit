# Vulnerability details

in fn `message_hash_receive`

```cairo
fn message_hash_receive(self: @ContractState, cross_chain_msg_id: u256, from_chain: felt252, to_chain: felt252, from_handler: u256, to_handler: ContractAddress, payload: Array<u8>) -> felt252{
    let mut message_hash: felt252 = LegacyHash::hash(from_chain, (cross_chain_msg_id, to_chain, from_handler, to_handler));
    let payload_span = payload.span();
    let mut i = 0;
    loop {
        if i > payload_span.len()-1{
            break;
        }
        message_hash = LegacyHash::hash(message_hash, * payload_span.at(i));
        i += 1;
    };
    return message_hash;
}
```

The bug in this function is that it doesn't include the `to_chain` parameter in the initial hash calculation. This omission can have a significant impact on the security and integrity of cross-chain messages.

 why this is problematic ?:

1. Incomplete message identification: The `to_chain` is an essential part of a cross-chain message's identity. By not including it in the initial hash, the function fails to fully capture the intended destination of the message.

2. Potential for replay attacks: Without the `to_chain` in the initial hash, an attacker could potentially replay a message on a different destination chain, as the message hash would remain the same regardless of the intended destination.

3. Inconsistency with other parts of the system: The README mentions that cross-chain transaction IDs are uniquely generated based on source and destination chain information. This function, however, doesn't fully adhere to this principle by omitting the `to_chain` in the initial hash.

4. Violation of the stated invariants: The README lists several invariants, including "Cross-chain transaction IDs are uniquely generated based on the source and destination chain information, sender, handler addresses, and nonce." The current implementation doesn't fully satisfy this invariant.

To fix this issue, the initial hash calculation should include the `to_chain` parameter:

```cairo
let mut message_hash: felt252 = LegacyHash::hash(from_chain, (cross_chain_msg_id, to_chain, from_handler, to_handler));
```

This change would ensure that the message hash accurately represents all crucial aspects of the cross-chain message, including its intended destination, thereby improving the security and integrity of the cross-chain messaging system.

Exploitability:
The exploitability of this bug depends on how this hash is used in the verification process. Let's examine the relevant parts of the system:

1. In the `receive_cross_chain_msg` function of the `ChakraSettlement` contract, we see:

```cairo
let mut message_hash: felt252 = self.message_hash_receive(cross_chain_msg_id, from_chain, to_chain, from_handler, to_handler, payload);
self.check_chakra_signatures(message_hash, signatures);
```

2. The `check_chakra_signatures` function then verifies the signatures against this hash.

Impact and Potential Exploit:

when attacker can exploit this bug, they could potentially execute a cross-chain replay attack. Here's a potential flow for such an exploit:

1. A legitimate cross-chain transaction is initiated from Chain A to Chain B.
2. The attacker observes this transaction and its signatures.
3. The attacker attempts to replay this transaction on Chain C, using the same `from_chain` (Chain A), `cross_chain_msg_id`, `from_handler`, `to_handler`, and `payload`.
4. Because the `to_chain` is not included in the hash calculation, the `message_hash_receive` function would produce the same hash for both the legitimate (A to B) and the replayed (A to C) transactions.
5. The `check_chakra_signatures` function would then validate the signatures, as they match the calculated hash.
6. If no additional checks are in place, the replayed transaction could be accepted on Chain C.

Proof of Concept:

Let's say we have a legitimate transaction:
- `cross_chain_msg_id`: 123
- `from_chain`: "ChainA"
- `to_chain`: "ChainB"
- `from_handler`: 0x1234
- `to_handler`: 0x5678
- `payload`: [1, 2, 3, 4]

And a malicious replayed transaction:
- `cross_chain_msg_id`: 123
- `from_chain`: "ChainA"
- `to_chain`: "ChainC"  // Different destination chain
- `from_handler`: 0x1234
- `to_handler`: 0x5678
- `payload`: [1, 2, 3, 4]

Both of these would produce the same hash in `message_hash_receive`, potentially allowing the replayed transaction to be accepted.
