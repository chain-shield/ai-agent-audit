# Vulnerability details

## Impact
Increasing `m` value for every signature, whether be it of a validator or not, in `verifyECDSA` function, can give opportunity for validator to act maliciously, and get benefit for themselves and grief users.

Where validator can pass invalid signatures for n-1 number of times (n = required_validators), and at the very last can add its own valid signature, and process receiving cross chain message, which is not intended by design

## Proof of Concept
Receiving a cross chain message is being done by validators, where they sign the message offchain, and their digital signatures are being concatenated and passed as parameter while calling `receive_cross_chain_msg` function in Settlement contract.

Then further the signatures are being verified by externally calling a `verify` function, which internally calls `verifyECDSA`.

Then the verification of signature takes place, where two conditions should be true : 
1) The address recovered from the signature & message_hash should be of a Validator
2) The number of validators signed the message should be greater than `required_validator`. This is implemented for preventing any validator to act maliciously.

`BUT THE IMPLEMENTATION HAS A FLAW :`

```javascript
function verifyECDSA(
        bytes32 msgHash,
        bytes calldata signatures
    ) internal view returns (bool) {
        require(
            signatures.length % 65 == 0,
            "Signature length must be a multiple of 65"
        );

        uint256 len = signatures.length;
        uint256 m = 0;
        for (uint256 i = 0; i < len; i += 65) {
            bytes memory sig = signatures[i:i + 65];
            if (
                validators[msgHash.recover(sig)] && ++m >= required_validators
            ) {
                return true;
            }
        }
        return false;
    }
```

In the line :
```javascript
         if (
                validators[msgHash.recover(sig)] && ++m >= required_validators
            ) {
                return true;
```

The `m` value is always been increased, whether the recovered address is of a TRUE validator or not.

`m` VALUE SHOULD ONLY INCREASE IF THE RECOVERED ADDRESS IS OF A TRUE VALIDATOR.
But even if it won't be of a validator, it will be increased because of current implementation.

This opens a very easy opportunity for validator to act maliciously

`A validator can add invalid signatures (n-1) number of times, [n = required_validators], and then at the end can add its own valid signature, to pass the verification`

For every invalid signature, `validators[msgHash.recover(sig)]` will return `FALSE` but `++m >= required_validators` this will increase the m value.

Hence lets say required_validators = 10.
Then first 9 signatures would be invalid.
And for them , the function will not return true.
But after the 9 invalid signatures the `m` value will be equal to 9.

Then for the last iteration, there will be the valid signature present.

For which `validators[msgHash.recover(sig)] = TRUE` & ++m = 10 i.e >= `required_validators`.

Hence both conditions will meet, and the if block will be implemented, and the function will return `TRUE`.

And like this a validator would be able to byPass verification, with invalid signatures and his own valid signature at the end, and further process the cross chain message.

And since from his single signature, he can process receiving cross chain message.
This clearly opens a very easy opportunity , to benefit himself OR grief any user.

`LETS SEE HOW HE CAN ACT MALICIOUSLY AND CAUSE ISSUE FOR USERS`

A malicious validator, can create a message off chain, using a specific user's txId and changing other parameters in order to cause loss for user, and then sign it.

For example.
In payload, the validator can set payload.amount less than the actual amount
OR
it can set the `to` parameter to its own address, so that the tokens would unlock/mint to its own address rather than user's address.

And then while calling receive_cross_chain_msg, he will pass the parameter that were used to create the `MALICIOUS MESSAGE` and the `txID` of that particular user, and will pass signature as discussed above. 

The verification of signature would pass, and then `receive_cross_chain_msg` of Handler contract, will handle the unlocking/minting of tokens according to the parameter. 
Which as explained above, can benefit the validator OR cause loss for user.

AND THEN FURTHER, THE NON-MALICIOUS VALIDATORS, EVEN IF THEY TRY TO PROCESS RECEIVING USER'S SETTLEMENT TRUELY, THEY WON'T BE ABLE TO DO IT SINCE IT WILL ALWAYS REVERT, BECAUSE 

```javascript
receive_cross_txs[txid] = ReceivedCrossChainTx(
            txid,
            from_chain,
            contract_chain_name,
            from_address,
            from_handler,
            address(this),
            payload,
            CrossChainMsgStatus.Pending
        ); 
```

The receive_cross_txs will store the malicious parameters input for `txid`, and will set the Status = Pending & Then as SUCCESS.

And hence because of the following check : 
```javascript
require(
                receive_cross_txs[txid].status == CrossChainMsgStatus.Unknow,
                "Invalid transaction status"
            );
```

It will always revert.

Hence it gives opportunity for a validator to act maliciously, and benefit himself, or grief users.

`ALSO GETTING KNOWING ABOUT WHICH VALIDATOR ACTED MALICIOUSLY, IN ORDER TO REMOVE HIM , WOULD BE VERY DIFFICULT`
Since there's is no access control on the `receive_cross_chain_msg` function.

A validator can call this function with a different address which is not stored or is with the protocol, and can process receiving the message.

## Recommended Mitigation Steps
The `m` value should only be increased if the signature is valid i.e the recovered address is of a validator 

This mitigation is already present in the CAIRO contract but NOT implemented in SOLIDITY contracts

Hence can be implemented in `SettlementSignatureVerifier::verifyECDSA` as follows : 

```javascript
for (uint256 i = 0; i < len; i += 65) {
            bytes memory sig = signatures[i:i + 65];
            if (
                validators[msgHash.recover(sig)]
            ) {
                m++;
            }
            if(m>=required_validators) 
                { return true;}
        }
 return false;
```
