# Vulnerability details

## Impact
Setting two corresponding handlers(that communicate with each other) on two different chains to BurnUnlock type, will make them unusable.

## Proof of Concept
There is currently no restriction in the protocol regarding setting both handlers on source and destChain to be BurnUnlock. But it will be very problematic doing so.
Example:

- both handlers are set as BurnUnlock
- Alice does a cross chain transfer, which burns her tokens on source chainA
- tokens get unlocked on dest chainB(assuming there is enough liquidity)
  Let's say she wants to send them back to source chain:
- the tokens get burned on chainB(which is wrong cos those tokens just got unlocked, not minted)
- the tokens get "unlocked" on chainA, but remember there are actually no tokens available on chainA because they got burned.

## Tools Used
Manual Review

## Recommended Mitigation Steps
- Ensuring that chainA is LockMint while chainB is BurnUnlock, won't fix this issue because each chain handler can interact with handlers on multiple chains.

I believe BurnUnlock types are suitable only between two chains(where the other would be of type LockMint), not multiple(which is not the case in this protocol)
