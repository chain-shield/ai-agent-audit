# Vulnerability details

## Vulnerability details
Function outputs of `send_cross_chain_msg()`  do not correlate with cairo function `receive_cross_chain_msg()` input in the `ChakraSettlement` contacts of these two versions. This could result in errors when starknet is in involved in any cross-chain message.

## Impact
Stakrtnet will be unable to receive cross-chain messages sent from or using the protocol.

## Proof Of Concept
Let's look at the output of the `send_cross_chain_msg()` in the solidity version along with the input of the `receive_cross_chain_msg()` of the cairo version.

 ```cairo
         fn receive_cross_chain_msg(
            ref self: ContractState,
            cross_chain_msg_id: u256,
            from_chain: felt252,
            to_chain: felt252,
            from_handler: u256,
            to_handler: ContractAddress,
            sign_type: u8,
            signatures: Array<(felt252, felt252, bool)>,
            payload: Array<u8>,
            payload_type: u8,
        ) -> bool { ... }
  ```
  Let's look at how they will match: (left side is solidity version)
  txid = cross_chain_msg_id
  contract_chain_name = from_chain
  to_chain = to_chain
  from_address (address) = from_handler (u256)
  from_handler = to_handler
  to_handler = sign_type
  payload = signatures
  CrossChainMsgStatus.Pending = payload
   ... = payload_type
   
   As can be seen above the `payload_type` will have no input and the `from_address` is a address of the msg.sender while `from_handler` is designated as a `u256`. An address in solidity is compatible with a `felt252` not `u256` in the cairo language. On top that the `to_handler` and `payload` are matched with the signature variable and array 
   This will result in the function either not operating or if it does operate it will not work as intended.
