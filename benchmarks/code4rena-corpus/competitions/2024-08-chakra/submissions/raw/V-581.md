# Vulnerability details

## Description
One of the main invariants for the settlemtntHandler contract is that the cross-chain transaction statuses are properly tracked and updated (Pending, settled or failed). 
These lines of code are meant to be executed when receive_cross_chain_callback function In the handler contract is invoked by the processcrosschaincallback funtion of the settlement contract,
```solidity
if (status == CrossChainMsgStatus.Success) {
if (mode == SettlementMode.MintBurn) {
_erc20_burn(address(this), create_cross_txs[txid].amount);
}

create_cross_txs[txid].status = CrossChainTxStatus.Settled;
}

if (status == CrossChainMsgStatus.Failed) {
create_cross_txs[txid].status = CrossChainTxStatus.Failed;
}

return true;
```
These lines of code is meant to check if the status of the cross chain message is success in order to burn when the mode is MintBurn and update the cross chain transaction status to settled. Also, it is meant to check if the cross chain message status is failed so as to update the cross chain transaction status to failed. However, the issue arises because the [**processcrosschaincallback** ](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/ChakraSettlement.sol#L303)function that invoked the receive crosschain callback funtion has a check that ensures that the only status that is allowed is “PENDING” as as shown

```solidity
function processCrossChainCallback(
uint256 txid,
string memory from_chain,
uint256 from_handler,
address to_handler,
CrossChainMsgStatus status,
uint8 sign_type,
bytes calldata signatures
) internal {
require(
create_cross_txs[txid].status == CrossChainMsgStatus.Pending,
"Invalid transaction status"
);

if (
ISettlementHandler(to_handler).receive_cross_chain_callback(
txid,
from_chain,
from_handler,
status,
sign_type,
signatures
)
) {
create_cross_txs[txid].status = status;
} else {
create_cross_txs[txid].status = CrossChainMsgStatus.Failed;
}
}
```
The require function will fail if the CrossChainMsgStatus is not “Pending”. Therefore, the status will be pending. Even before now the status was set to pending when the transaction was sent. I can’t see where it was updated to success or failed in the codebase.

Ofcourse, this means cross chain message status will never be set to success or failed which will make the check **“if (status == CrossChainMsgStatus.Success)“** to fail all the time since the cross message status is “Pending”. The rest of the code that depends on the check passing will not be performed.
Hence breaking one of the main invariant of the handler contract. 
An attacker can also exploit this to cause loss of fund.


## Impact

1. Breaks one the main invariant of the handler contract
2. The cross chain transaction status will never be set to settled.
3. An attacker can exploit this to cause the protocol loss of fund.


This is a possible pathway of attack by a malicious
1. Set the Settlement mode to MintBurn
2. When the receive_cross_chain_message function is invoked, it mints the given amount of token
3. When the receive_cross_chain_callback function is invoked, it fails to burn update cross chain transaction status because cross chain message status was never set to success or failed.
4. The attacker can invoke the receive_cross_chain_message function again to mint the given amount of token again because the cross chain transactions status will still be pending instead of settled.



## Tools Used
Vscode, Manual Review
## Recommended Mitigation Steps
The cross chain message status should be updated to success or failed before receive_cross_chain_call back is invoked. Also the require check can be done at the end of the external call.
