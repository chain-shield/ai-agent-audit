# Vulnerability details

## Impact
The current three-way handshake protocol (send-receive-callback) is inadequate for the MintBurn mode in cross-chain token transfers. Unlike other modes where the final action (unlock or mint) occurs on the destination chain, the MintBurn mode's final action (burn) takes place on the source chain. This discrepancy means that the destination chain is not aware of potential failures during the burn process, which could lead to inconsistencies in token supply across chains.
This is issue is present in both cairo and solidity contracts.

## Proof of Concept
In the cross_chain_erc20_settlement function, tokens are locked for MintBurn mode:
```solidity
if (mode == SettlementMode.MintBurn) {
    _erc20_lock(msg.sender, address(this), amount);
}
```

The receive_cross_chain_msg function on the destination chain mints tokens:
```solidity
if (mode == SettlementMode.MintBurn) {
    _erc20_mint(
        AddressCast.to_address(transfer_payload.to),
        transfer_payload.amount
    );
    return true;
}
```

The receive_cross_chain_callback function attempts to burn tokens on the source chain:
```solidity
if (status == CrossChainMsgStatus.Success) {
    if (mode == SettlementMode.MintBurn) {
        _erc20_burn(address(this), create_cross_txs[txid].amount);
    }
    create_cross_txs[txid].status = CrossChainTxStatus.Settled;
}
```

If the burn operation fails in step 3, tokens have been minted on the destination chain without a corresponding burn on the source chain, potentially leading to token inflation. There is an event emitted CrossChainResult but no handler for using it.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Implement a four-step handshake for the MintBurn mode:

Step 1: Lock tokens on source chain
Step 2: Mint tokens on destination chain
Step 3: Burn tokens on source chain
Step 4: Confirm burn success to destination chain
