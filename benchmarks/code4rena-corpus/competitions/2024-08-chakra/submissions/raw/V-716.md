# Vulnerability details





in function: set_required_validators_num



```solidity
function set_required_validators_num(
    uint256 _required_validators
) external virtual onlyRole(MANAGER_ROLE) {
    uint256 old = required_validators;
    required_validators = _required_validators;
    emit RequiredValidatorsChanged(msg.sender, old, required_validators);
}
```

The vulnerability is:

The function doesn't check if the new `_required_validators` value is less than or equal to the current number of validators (`validator_count`).

This oversight can lead to a situation where the required number of validators is set higher than the actual number of validators in the system. This could potentially break the cross-chain message verification process, as it might become impossible to gather enough valid signatures to meet the new requirement.

The impact on the project :

1. It could lead to a deadlock in the cross-chain message verification process if the required number of validators is set higher than the actual number of validators.

2. This could potentially freeze cross-chain operations, as no messages would be able to be verified and processed.

3. It could be exploited by a malicious manager to intentionally disrupt the system's operations.

To fix this vulnerability, the function should include a check to ensure that the new `_required_validators` value doesn't exceed the current `validator_count`:

```solidity
function set_required_validators_num(
    uint256 _required_validators
) external virtual onlyRole(MANAGER_ROLE) {
    require(_required_validators <= validator_count, "Required validators cannot exceed total validators");
    uint256 old = required_validators;
    required_validators = _required_validators;
    emit RequiredValidatorsChanged(msg.sender, old, required_validators);
}
```

This check ensures that the system always maintains a feasible number of required validators, preventing potential deadlocks in the cross-chain message verification process.



### Why it can be triggered:

1. The function is callable by any address with the MANAGER_ROLE.
2. There's no upper bound check on the `_required_validators` parameter.
3. The `validator_count` and `required_validators` are managed separately.

### Impact and PoC Flow:

1. Initial Setup:
   - Assume the system starts with 5 validators and `required_validators` set to 3.

2. Triggering the Vulnerability:
   - A manager calls `set_required_validators_num(10)`.
   - This succeeds, setting `required_validators` to 10.

3. Cross-Chain Operation Attempt:
   - A user initiates a cross-chain ERC20 settlement using `cross_chain_erc20_settlement`.
   - The `ChakraSettlement` contract creates a cross-chain message.

4. Message Verification Failure:
   - When receiving the cross-chain message on the destination chain, `receive_cross_chain_msg` is called.
   - This function calls `signature_verifier.verify()`.
   - In `SettlementSignatureVerifier.verifyECDSA()`, it tries to collect 10 valid signatures.
   - Since there are only 5 validators, this is impossible, causing all cross-chain messages to fail.

5. System Deadlock:
   - No cross-chain operations can be completed.
   - Funds sent for cross-chain transfers are stuck in the source chain's contract.

6. Potential for Malicious Exploitation:
   - A malicious manager could intentionally set an impossibly high `required_validators` to halt the system.
   - This could be used in combination with other attacks, like front-running large cross-chain transfers to trap funds.

Detailed PoC Example:

1. Deploy contracts with 5 validators and `required_validators` set to 3.
2. User Alice initiates a cross-chain transfer of 100 tokens from Chain A to Chain B.
3. Before the message reaches Chain B, a manager calls `set_required_validators_num(10)` on Chain B.
4. The cross-chain message arrives on Chain B, but fails verification in `SettlementSignatureVerifier.verify()`.
5. Alice's tokens are locked in the contract on Chain A, but never minted/unlocked on Chain B.
6. All subsequent cross-chain operations fail similarly.

The impact is severe because:

1. It can cause a complete halt of cross-chain operations.
2. User funds can become trapped in contracts.
4. Recovery from this state would require emergency governance actions, potentially harming the network's reputation.
