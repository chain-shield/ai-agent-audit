# Vulnerability details

It is mentioned in the contest page that "The handler receiving a cross-chain message must be on the whitelist for the source chain". This requirement is met for function `cross_chain_erc20_settlement` in handler_erc20.cairo:
```
fn cross_chain_erc20_settlement(ref self: ContractState, to_chain: felt252, to_handler: u256, to_token: u256, to: u256, amount: u256) -> felt252{
            assert(self.support_handler.read((to_chain, to_handler)), 'not support handler');
...
```
However, function `cross_chain_erc20_settlement` in ChakraSettlementHandler.sol does not check whether the receiving handler is on the whitelist or not. This issue enables the attacker to send the cross chain message to an arbitrary handler at the destination chain. It is worth noting that to_handler address is not even checked in ChakraSettlement.sol and settlement.cairo. For example, the attacker can create a malicious handler at Starknet chain and initiate a cross-chain ERC20 settlement by calling `cross_chain_erc20_settlement` in ChakraSettlementHandler and passing the malicious handler address as to_handler parameter. The message will be sent and function `receive_cross_chain_msg` in settlement.cairo will be called, which calls `receive_cross_chain_msg` function in Starknet malicious handler. The malicious contract returns true as the result, causing the status to be CrossChainMsgStatus::SUCCESS and emit CrossChainHandleResult event.

## Recommended Mitigation Steps
Adding `require (is_valid_handler(to_chain, to_handler) == true, "Not Valid Handler")` in the beginning of function `cross_chain_erc20_settlement` in ChakraSettlementHandler.sol can fix the issue.
