# Vulnerability details

## Impact
By design, it being intended that any cross_chain_msg should be signed by a minimum number of validators , then only the message/settlement would be processed further. 

But a single validator can pass its own signature , `required_validators` number of times, to pass the requirement, and hence then would be able to process receiving cross chain message, `WITH ONLY HIS SIGNATURE` which is not intended by the design.

AND THIS CAN ALLOW ANY VALIDATOR TO ACT MALICIOUSLY , CAUSING DIRECT LOSS FOR USERS.

## Proof of Concept
`NOTE : I HAVE DISCUSSED ONLY RELATED TO SOLIDITY CODE/CONTRACTS BELOW, BUT THE SAME ISSUE IS ALSO PRESENT IN CARIO CONTRACTS, HENCE ACCORDINGLY MITIGATION SHOULD BE APPLIED THERE ALSO`

Validators sign the cross chain message offchain, and then their signatures are being used to call the `recieve_cross_chain_msg`.

Which is further verified externally in `SettlementSignatureVerifier` contract , with `verify` function which internally calls `verifyECDSA`, that contains the main logic of verification

```javascript
function verifyECDSA(
        bytes32 msgHash,
        bytes calldata signatures
    ) internal view returns (bool) {
        require(
            signatures.length % 65 == 0,
            "Signature length must be a multiple of 65"
        );
        
        uint256 len = signatures.length;
        uint256 m = 0;
        for (uint256 i = 0; i < len; i += 65) {
            bytes memory sig = signatures[i:i + 65];
            if (
                validators[msgHash.recover(sig)] && ++m >= required_validators
            ) {
                return true;
            }
        }

        return false;
    }
```
As you can see above,`++m >= required_validators` this makes sure the number of validators that have signed the transaction is greater than the `required_validators`.

And then if condition meets, it returns TRUE, else it returns FALSE 

`BUT THE ISSUE IS : `

Any single validator can pass its own signature, the `required_validator` numbers of times and byPass the intended requirement by design, for any cross chain message to be processed further.

`THIS ISSUE ARISES BECAUSE, THERE'S NO CHECK WHETHER THE SIGNATURE HAS ALREADY BEEN VERIED OR NOT `

```javascript
 for (uint256 i = 0; i < len; i += 65) {
            bytes memory sig = signatures[i:i + 65];
            if (
                validators[msgHash.recover(sig)] && ++m >= required_validators
            ) {
                return true;
            }
        }
```
Every time `sig`, will be same, it will recover the validator's address correctly , and `validators[msgHash.recover(sig)]`, will be true.

And `m` will also increase everytime.

There's is no check whether one signature has already been verified or not.

Because of which it opens opportunity for validator to pass its own signatures multiple number of times till the `required_validator` condition meets.

Hence a single validator then would be able to process receiving cross chain message, with only his signature, which is against the design.

The validator, since can process receiving cross chain message alone.

`LETS SEE HOW HE CAN ACT MALICIOUSLY AND CAUSE ISSUE FOR USERS`

A malicious validator, can create a message off chain, using a specific user's txId and changing other parameters in order to cause loss for user, and then sign it.

For example.
In payload, the validator can set payload.amount less than the actual amount
OR
it can set the `to` parameter to its own address, so that the tokens would unlock/mint to its own address rather than user's address.

And then while calling receive_cross_chain_msg, he will pass the parameter that were used to create the `MALICIOUS MESSAGE` and the `txID` of that particular user, and his own signature multiple times concatenated. 

The verification of signature would pass, and then `receive_cross_chain_msg` of Handler contract, will handle the unlocking/minting of tokens according to the parameter. 
Which as explained above, can benefit the validator OR cause loss for user.

AND THEN FURTHER, THE NON-MALICIOUS VALIDATORS, EVEN IF THEY TRY TO PROCESS RECEIVING USER'S SETTLEMENT TRUELY, THEY WON'T BE ABLE TO DO IT SINCE IT WILL ALWAYS REVERT, BECAUSE 

```javascript
receive_cross_txs[txid] = ReceivedCrossChainTx(
            txid,
            from_chain,
            contract_chain_name,
            from_address,
            from_handler,
            address(this),
            payload,
            CrossChainMsgStatus.Pending
        ); 
```

The receive_cross_txs will store the malicious parameters input for `txid`, and will set the Status = Pending & Then as SUCCESS.

And hence because of the following check : 
```javascript
require(
                receive_cross_txs[txid].status == CrossChainMsgStatus.Unknow,
                "Invalid transaction status"
            );
```

It will always revert.

Hence it gives opportunity for a validator to act maliciously, and benefit himself, or grief users.

`ALSO GETTING KNOWING ABOUT WHICH VALIDATOR ACTED MALICIOUSLY, IN ORDER TO REMOVE HIM , WOULD BE VERY DIFFICULT`
Since there's is no access control on the `receive_cross_chain_msg` function.

Hence the validator can call this function with a different address which is not stored or is with the protocol, and can process receiving the message.

## Recommended Mitigation Steps
A check should be implemented for checking whether a particular signature is being already verified or not.

It can be checked using a local `mapping (address=>bool) verified`, which if is a valid signature/the address recovered is of a validator then will set equal to TRUE.

And a check should be made as `verified[msgHash.recover(sig)]` should be FALSE before verifying.

Also access for `receieve_cross_chain_message` in Settlement contract should be restricted to only validators.

And similar changes should be added in CAIRO contracts too.
