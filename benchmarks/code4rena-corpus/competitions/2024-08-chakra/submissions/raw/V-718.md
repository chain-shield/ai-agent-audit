# Vulnerability details


in function: verifyECDSA


```solidity
function verifyECDSA(
    bytes32 msgHash,
    bytes calldata signatures
) internal view returns (bool) {
    require(
        signatures.length % 65 == 0,
        "Signature length must be a multiple of 65"
    );

    uint256 len = signatures.length;
    uint256 m = 0;
    for (uint256 i = 0; i < len; i += 65) {
        bytes memory sig = signatures[i:i + 65];
        if (
            validators[msgHash.recover(sig)] && ++m >= required_validators
        ) {
            return true;
        }
    }

    return false;
}
```



The function doesn't check if the total number of valid signatures meets or exceeds the `required_validators` threshold after processing all signatures. Instead, it returns `true` as soon as the number of valid signatures reaches `required_validators`, potentially ignoring additional valid signatures.

This could lead to a situation where:

1. The function returns `true` after finding the minimum required number of valid signatures.
2. Some of the remaining unprocessed signatures could be invalid or duplicates.
3. The total number of unique, valid signatures might actually be less than `required_validators` when considering the entire set.


To fix this vulnerability, the function should:

1. Process all signatures.
2. Count the total number of unique, valid signatures.
3. Only return `true` if the total count of unique, valid signatures meets or exceeds `required_validators`.

This change would ensure that the signature verification process is more robust and aligns with the project's security requirements for cross-chain message validation.


### Why it can be triggered:

1. The `SettlementSignatureVerifier` is a crucial component used by the `ChakraSettlement` contract for validating cross-chain messages.
2. The `required_validators` value is set by managers and can be changed, which means the system relies on this verification for its security.
3. There's no check for uniqueness of validator signatures or processing of all provided signatures.

### Impact and PoC Flow:

Let's consider a scenario where `required_validators` is set to 3, but there are 5 total validators.

PoC Flow:
1. An attacker prepares a malicious cross-chain message.
2. The attacker creates a signature array with the following structure:
   [ValidSignature1, ValidSignature1, ValidSignature1, InvalidSignature, InvalidSignature]

3. The attacker calls `receive_cross_chain_msg` on the `ChakraSettlement` contract with this malicious message and signature array.

4. Inside `ChakraSettlement`, it calls `verify` on the `SettlementSignatureVerifier`:
   ```solidity
   require(
       signature_verifier.verify(message_hash, signatures, sign_type),
       "Invalid signature"
   );
   ```

5. The `verify` function calls `verifyECDSA`:
   ```solidity
   if (sign_type == 0) {
       return verifyECDSA(msgHash, signatures);
   }
   ```

6. In `verifyECDSA`:
   - It processes the first signature, finds it valid, increments `m` to 1.
   - It processes the second signature (same as first), finds it valid, increments `m` to 2.
   - It processes the third signature (same as first), finds it valid, increments `m` to 3.
   - Since `m >= required_validators` (3 >= 3), it returns true.

7. The signature verification passes, despite only having one unique valid signature instead of the required three.

8. The malicious cross-chain message is accepted and processed by the `ChakraSettlement` contract.

Full Impact:

Malicious cross-chain messages could be accepted with fewer unique validator signatures than intended, compromising the security of the entire cross-chain communication system.

Fund Loss: In cases of token transfers or other value-moving operations, this could lead to unauthorized movement of funds across chains.

It could create inconsistent states between different blockchain networks, as invalid operations might be accepted on one chain but not on others.
