# Vulnerability details

## Impact

The `TokenRoles.sol` contract is meant to be upgradeable as it inherits from `OpenZeppelins`'s `UUPSUpgradeable` contract. However, it fails to properly initialize it, which could lead to severe security vulnerabilities.

## Proof of Concept

Upgradeable contracts do not have the general flow of using a `constructor` and rely on `initializers`. The same goes for contracts inheriting from the `UUPSUpgradeable` contract. `TokenRoles` is a proper example of this, however, it fails to initialize the `UUPSUpgradeable` contract properly and does not call the `__UUPSUpgradeable_init` function in its initializer. This function initializes the UUPS upgradeability mechanism. It sets up the storage slot for the implementation address and disables future initialization.

Failure to do so could lead to numerous issues:

1. Lack of Upgrade Protection:

The `_upgradeToAndCall` function in UUPS relies on a storage slot being set to a specific value to prevent unauthorized upgrades. If `__UUPSUpgradeable_init()` is not called, this slot is not set, potentially allowing anyone to upgrade the contract.


2. Vulnerability to Front-Running:

In a scenario where you deploy a proxy and an implementation separately, if `__UUPSUpgradeable_init()` is not called immediately, an attacker could front-run your initialization transaction and take control of the contract.


3. Initialization Replay:

`__UUPSUpgradeable_init()` also sets a flag to prevent multiple initializations.
Without this, an attacker might be able to call the initialization function multiple times, potentially resetting or manipulating the contract's state.


4. Unexpected Behavior in Upgrades:

Even if you have other access controls (like `onlyOwner`), the internal workings of the UUPS pattern might not function as expected without proper initialization.
This could lead to failed upgrades or unexpected behavior when trying to use UUPS-specific functions.
