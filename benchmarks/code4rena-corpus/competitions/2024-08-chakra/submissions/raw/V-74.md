# Vulnerability details

## Impact

`ChakraTokenUpgradeTest` smart contract handles the minting / burning logic by the operator. However, it uses `_authorizeUpgrade()` function (UUPS Proxy) but does not initialize proxy in the `initialize()` function not allowing to use upgradeability in the future.

## Proof of Concept

The contract is supposed to use UUPS upgradeability functionality:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/ChakraTokenUpgradeTest.sol#L25-27
```
 function _authorizeUpgrade(
        address newImplementation
    ) internal override onlyOwner {}
```

But the UUPS Proxy is not initialized in the `initialize()` function:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/ChakraTokenUpgradeTest.sol#L13-23
```
 function initialize(
        address _owner,
        address _operator,
        string memory _name,
        string memory _symbol,
        uint8 _decimals
    ) public initializer {
        __TokenRoles_init(_owner, _operator);
        __ERC20_init(_name, _symbol);
        set_decimals = _decimals;
    }
```

So it cannot basically use the UUPS upgradeability as it's required to initialize both proxy and `_authorizeUpgrade()`.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Add `__UUPSUpgradeable_init()` in the `initialize()`:

https://github.com/OpenZeppelin/openzeppelin-contracts-upgradeable/blob/master/contracts/proxy/utils/UUPSUpgradeable.sol#L65-66
```
 function __UUPSUpgradeable_init() internal onlyInitializing {
    }
```
