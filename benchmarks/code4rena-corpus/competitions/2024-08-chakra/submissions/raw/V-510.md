# Vulnerability details

## Impact

The `Chakra` system lacks an expiration mechanism for messages, introducing an issue where outdated or previously invalid messages become valid if the required validator threshold is lowered.

## Vulnerability Details

In the current implementation, messages have no expiration time. This allows messages to be replayed, at a latter time, even if they initially failed to get enough signatures. If the `required_validators` is later lowered, previously invalid messages suddenly become valid and executable.

Looking at the relevant code,`verifyECDSA` counts the valid signatures:

[solidity/settlement/contracts/SettlementSignatureVerifier.sol#L186-L215](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/SettlementSignatureVerifier.sol#L186-L215)

```js
function verifyECDSA(bytes32 msgHash, bytes calldata signatures) internal view returns (bool) {
// ... signature parsing ...
uint256 m = 0;
    for (uint256 i = 0; i < len; i += 65) {
            bytes memory sig = signatures[i:i + 65];
            if (validators[msgHash.recover(sig)] && ++m >= required_validators) {
            return true;
        }
    }

return false;
}
```

If a message initially fails the verify check `++m >= required_validators` due to insufficient signatures, it can be replayed at any time in the future. If `required_validators` was lowered, the message passes verification and is now valid, long after its intended timeframe.

## Proof of Concept

- A message is sent requiring 3 validator signatures, but only receives 4, message should be invalid.
- The message remains in the system indefinitely.
- Later, required_validators is reduced to 2.
- The previously rejected message can now be replayed and will pass verification.

Manual review.

## Recommended Mitigation Steps

Implement an expiration timestamp for each cross-chain message.
