# Vulnerability details

## Impact
Complete DoS in `setttlement::receive_cross_chain_msg()` and `settlement::receive_cross_chain_callback()` when validator/proposer calls these function as the signature componet `r` and `s` would not fit in `felt252`.
This is a critical issue as it will completely disrupts the protocol on starknet side.

## Proof of Concept
The `settlement::check_chakra_signatures()` implements a signature verification logic using starknet corelib `ecdsa.cairo`.
The implementation recovers the public key of validator using the message_hash and the signature component v, r, s then it compares it to the saved public key of the validator, if matched the pass_count is incremented and if required number of pass_count is reached then the verification is successfull.

The `settlement::check_chakra_signatures()` takes signatures as array of : `Array<(felt252, felt252, bool)`. The settlement contract also stores the validator public key as type felt252 `chakra_validators_pubkey: LegacyMap<felt252, u8>`

However this implementation for verifying signature is incorrect and will lead to revert of transaction when validator/proposer calls `setttlement::receive_cross_chain_msg()` or `settlement::receive_cross_chain_callback()` because of the working of `ecdsa.cairo` ( the corelib used by `settlement.cairo` contract) which slightly deviates from the standard ecdsa.
Reference : https://github.com/starkware-libs/cairo/blob/main/corelib/src/ecdsa.cairo#L13

The Chakra Validator network uses ecdsa `Seck256k1` algorithm to sign the message on offchain then sumbit it onchain for all the blockchain networks including Starkent. However due to differences in how starknet corelib `ecdsa.cairo` implements ecdsa, the curve used by this library is `STRAK_CURVE` and its order is `STARK_ORDER` which is different and smaller then order used for `Secp256k1` .
- `STARK_ORDER` ( `p` ) = `3618502788666131213697322783095070105623107215331596699973092056135872020481` [ 252 bits ]
- `Secp256k1_ORDER` ( `n` )= `115792089237316195423570985008687907852837564279074904382605163141518161494337` [ 256 bits ]
- and `STARK_ORDER` < `Secp256k1_ORDER`

Since the Chakra Validator network uses ecdsa `Seck256k1` the range for `r` and `s` of signature is `[ 1, n - 1 ]` . Because of this the values of `r` and `s` can be greater than `p` which will not fit in `felt252` which is expected in `settlement::check_chakra_signatures()`. This will cause revert of the transaction.

## Recommended Mitigation Steps
Fixing this issue require changes in the design of signature verification in `settlement::check_chakra_signatures()`. It needs to implement a signature verification logic which uses ecdsa `Secp256k1_ORDER`.
For this protocol can consider using the starknet corelib `eth_signature.cairo` library which uses the `secp256k1` curve.
Reference to library : https://github.com/starkware-libs/cairo/blob/main/corelib/src/starknet/eth_signature.cairo
Also in `settlement.cairo` the storage mapping  `chakra_validators_pubkey: LegacyMap<felt252, u8>,` needs to be changed to `chakra_validators_pubkey: LegacyMap<u256, u8>,` as public key in `secp256k1` curve is of 256 bits.
