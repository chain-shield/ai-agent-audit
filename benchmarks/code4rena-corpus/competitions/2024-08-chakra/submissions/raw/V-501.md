# Vulnerability details

## Impact

`receive_cross_chain_msg` in both `settlement` and `handler` contract for `Cairo` are missing checks for the status of the `CrossChainMsgStatus` and allow anyone to reply valid transaction indefinitely.

## Proof of Concept

Transactions in `Starknet` same as in `Ethereum` are public with [visible](https://www.starknet.io/faqs/) payloads and any user that have performed single valid cross chain call can reply it indefinitely and steal the entire balance of the `Cairo` handler. This is because there is no validation for the `CrossChainMsgStatus` to be equal to `UNKNOW`:

[settlement.cairo](https://github.com/code-423n4/2024-08-chakra/blob/main/cairo/handler/src/settlement.cairo#L325C9-L383C10)

```rust
fn receive_cross_chain_msg(
    ref self: ContractState,
    cross_chain_msg_id: u256,
    from_chain: felt252,
    to_chain: felt252,
    from_handler: u256,
    to_handler: ContractAddress,
    sign_type: u8,
    signatures: Array<(felt252, felt252, bool)>,
    payload: Array<u8>,
    payload_type: u8,
) -> bool {
    assert(to_chain == self.chain_name.read(), 'error to_chain');

    // verify signatures
    let mut message_hash: felt252 = LegacyHash::hash(from_chain, (cross_chain_msg_id, to_chain, from_handler, to_handler));
    let payload_span = payload.span();
    let mut i = 0;
    loop {
        if i > payload_span.len()-1{
            break;
        }
        message_hash = LegacyHash::hash(message_hash, * payload_span.at(i));
        i += 1;
    };
    self.check_chakra_signatures(message_hash, signatures);

    // call handler receive_cross_chain_msg
    let handler = IHandlerDispatcher{contract_address: to_handler};
    let success = handler.receive_cross_chain_msg(cross_chain_msg_id, from_chain, to_chain, from_handler, to_handler , payload);

    let mut status = CrossChainMsgStatus::SUCCESS;
    if success{
        status = CrossChainMsgStatus::SUCCESS;
    }else{
        status = CrossChainMsgStatus::FAILED;
    }

    self.received_tx.write(cross_chain_msg_id, ReceivedTx{
        tx_id:cross_chain_msg_id,
        from_chain: from_chain,
        from_handler: from_handler,
        to_chain: to_chain,
        to_handler: to_handler,
        tx_status: status
    });

    // emit event
    self.emit(CrossChainHandleResult{
        cross_chain_settlement_id: cross_chain_msg_id,
        from_chain: to_chain,
        from_handler: to_handler,
        to_chain: from_chain,
        to_handler: from_handler,
        cross_chain_msg_status: status,
        payload_type: payload_type
    });
    return true;
}
```

In order for anyone to pull this attack he needs:

- valid `cross_chain_erc20_settlement` from any supported chain to `Starknet`
- collected signatures of the validators
- non failing initial `receive_cross_chain_msg`

All the requirements will be collected when validators first execute the `receive_cross_chain_msg` to mint/unlock tokens on Starknet, then user can use the values from the tx payload and reply the transaction as many times as possible until all the supply is minted to him or all the balance is stolen from the handler, depending on the mode used. This attack can’t be stopped because there is no such mechanism which will allow admins to prevent users from replying transactions.

Another less severe impact is that this breaks an invariant defined in the README:

> *vi. A cross-chain message can only be received once. The status of a received transaction in `receive_cross_txs` must be `CrossChainMsgStatus.Unknow` before it can be processed.*
>
