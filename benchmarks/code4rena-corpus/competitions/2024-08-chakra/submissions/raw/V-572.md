# Vulnerability details

## Impact
Critical Issue in `handler_erc20.cairo` as despite calling `burn_from()`, tokens are not actually burned due to a zero amount. This leads to token inflation as the supply continuously increases. As a MintBurn bridge, the contract is expected to mint tokens when it receives messages and burn them when it sends messages. However, the burning functionality is not working correctly.

Because of this message can never be settled as mapping keeps pointing to random empty `CreatedCrossChainTx` struct, the actully mapping is never updated to `CrossChainTxStatus::SETTLED`. It also don't follow the said invariant of `handler` which is "Cross-chain transaction statuses are properly tracked and updated (Pending, Settled, or Failed)." 

## Proof of Concept
The `handler_erc20.cairo` and `settlement.cairo` contracts maintain the nonces/counters `msg_count` and `tx_count`, respectively, to track the messages/transactions sent and to compute the keys `tx_id` and `cross_chain_settlement_id`. 
The keys are computed as : 
In handler
`let tx_id = LegacyHash::hash(get_tx_info().unbox().transaction_hash, self.msg_count.read());`
https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/cairo/handler/src/handler_erc20.cairo#L184
In settlement
`let cross_chain_settlement_id = LegacyHash::hash(get_tx_info().unbox().transaction_hash, self.tx_count.read());`
https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/cairo/handler/src/settlement.cairo#L289

These keys are used to store message information in the contracts. To complete the message/transaction lifecycle, the validator invokes the callback `settlement::receive_cross_chain_callback()` with the `cross_chain_msg_id`. This function internally calls `handler_erc20::receive_cross_chain_callback` to burn the tokens and finalize the settlement of the message/transaction.



However since `cross_chain_msg_id` is used during `settlement::receive_cross_chain_callback()`, reading `self.created_tx.read(cross_chain_msg_id).amount` will return 0 and the message status to `CrossChainTxStatus::SETTLED` won't be set to intended `created_tx` mapping becasue when message/transaction was initiated `tx_id` was used as key for the `created_tx` mapping but now in callback key `cross_chain_msg_id` is used which will point to an empty `CreatedCrossChainTx` struct. The issue arises when `tx_id` inside the `handler_erc20` and `cross_chain_settlement_id` inside the `settlement` don't remain in sync. As their is one settlement contract and many handlers contract,   `msg_count` and `tx_count` will reamin out of sync.

We can also make nonces `tx_count` and `msg_count` out of sync by directly calling the `settlement::send_cross_chain_msg()`

**Test :** 
For testing, there are two handlers handler1, handler1 and one settlement contract.
- user1 calls `cross_chain_erc20_settlement()` of handler1 |  counters value after call :: [ msg_count = 1, tx_count = 1 ]
- user2 calls `cross_chain_erc20_settlement()` of handler1 |  counters value after call ::  [ msg_count = 2, tx_count = 2 ]
- user3 calls `cross_chain_erc20_settlement()` of handler2 |  counters value after call ::  [ msg_count = 1, tx_count = 3 ]

For user3 :
- `tx_id` =  `LegacyHash::hash(get_tx_info().unbox().transaction_hash, 0)`
- `cross_chain_msg_id` = `LegacyHash::hash(get_tx_info().unbox().transaction_hash, 2)`
- Since `get_tx_info().unbox().transaction_hash` reamins same both in handler and settlement, but due to msg_count and tx_count being out of sync the keys are changed.

## Recommended Mitigation Steps

Fixing this issue require changes in the design of `handler_er20.cairo` and `settlement.cairo` how nonces/counter is managed. Proposed solution is that :
- For `handler_erc20.cairo`, it can keep track of total message/transaction `transaction_counter` sent from the handler plus also maintains a mapping to keep track of nonces of caller, a mapping (User=>nonce) for example : `nonce_manager: LegacyMap<(ContractAddress, u256)>,`
- For `settlement.cairo`, it can keep individual record for each handler, a maping of (Handler=>UserAddress ) => nonce ) for example : `nonce_manager:LegacyMap<((ContractAddress, ContractAddress),u256)` this will make sure that nonces never go out of sync in handler and settlement.
