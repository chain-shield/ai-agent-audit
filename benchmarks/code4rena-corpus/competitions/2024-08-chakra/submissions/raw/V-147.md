# Vulnerability details

## Impact

The current implementation of `ChakraToken` has `burn_from` function that burns a token from user's account. The problem is that the token does not reset allowance that has to be reset violating the ERC20 specification.

## Proof of Concept

Take a look at the implementation of `burn_from()`:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/ChakraToken.sol#L79-84
```
  function burn_from(
        address account,
        uint256 value
    ) external onlyRole(OPERATOR_ROLE) {
        _burn(account, value);
    }

```

As you can see, only internal `_burn()` is called. In contrary, `burnFrom()` from the ERC20 specification has the following functionality:

```
    function burnFrom(address account, uint256 value) public virtual {
        _spendAllowance(account, _msgSender(), value);
        _burn(account, value);
    }

```

In this case, `_spendAllowance()` is first called and only after then the tokens are burnt. Such deviation allows the deployer of the handler that got allowance from the user violate the allowance and burn more than it was allowed.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Implement `_spendAllowance()` in `_burnFrom()` as internal `_burn()` does not have such functionality.
