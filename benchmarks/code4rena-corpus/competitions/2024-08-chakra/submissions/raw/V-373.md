# Vulnerability details

## Impact
Because of lack of `access control` in `send_cross_chain_msg()` function in ChakraSettlement contract 

Any malicious actor , can call this function , and pass anyone's address in `from_address` paramter, and increase the `nonce_manager` of that address, causing discrepancies in any further `txID's` of cross chain erc20 settlement transactions in Handler and Settlement contracts. 

Since the nonce_manager of that address will not be same in both the contracts, and hence the txID's will be different on both the contracts

Which will lead to callback function i.e `recieve_cross_chain_callback()`, to `ALWAYS REVERT` whenever a validator calls it.

## Proof of Concept
Consider the following scenario with complete explaination of each steps below better understanding .
`I have explained using solidity contracts, but same issue is present in Cairo contracts, hence same mitigation should be applied in Cairo contracts too`

Lets say Alice wants to do cross_chain_erc20_settlement.
Currently in ChakraSettlementHandler & ChakraSettlement contract, her `nonce_manager[Alice] = 1`

`LETS GO THROUGH IDEAL CASE FIRST`

Now, if no issue happens, then in Handler contract, while `cross_chain_erc20_settlement()` function call, the `txID` will be made using all the other parameters and the increased nonce in the function, i.e `2` .

```javascript
        {
            // Increment nonce for the sender
            nonce_manager[msg.sender] += 1;
        }

        // Create a new cross chain tx
uint256 txid = uint256(
            keccak256(
                abi.encodePacked(
                    chain,
                    to_chain,
                    msg.sender, // from address for settlement to calculate txid
                    address(this), //  from handler for settlement to calculate txid
                    to_handler,
                    nonce_manager[msg.sender]
                )
            )
        );
```

Similarly when `send_cross_chain_msg()` function of ChakraSettlement contract will be called internally in the current function flow, `txid` will be calculated with all the same parameters and the increased nonce in the function i.e `2`.
```javascript
uint256 txid = uint256(
            keccak256(
                abi.encodePacked(
                    contract_chain_name, // from chain
                    to_chain,
                    from_address, // msg.sender address
                    from_handler, // settlement handler address
                    to_handler,
                    nonce_manager[from_address]
                )
            )
        );
```

Hence it would be expected , to have same txID in both the contracts for this ERC20 settlement transaction of ALICE.
And hence further , when `receive_cross_chain_callback()` of `Settlement`, will be called by validator, this `txID` will be used, which will be further used in calling `receive_cross_chain_callback()` of `Handler` contract.

```javascript
ISettlementHandler(to_handler).receive_cross_chain_callback(
                txid,
                from_chain,
                from_handler,
                status,
                sign_type,
                signatures
            )
```

And the function call will be successful.

`BUT , NOW COMES THE NON IDEAL CASE, WHERE A MALICIOUS ACTOR COME INTO PLAY.`

Before Alice initiating and calling `cross_chain_erc20_settlement` function.

Bob (Malicious Actor) calls `send_cross_chain_msg` in Settlement contract, and passed Alice's address in the `from_address` parameter.
Which will hence lead to increasing `nonce_manager` of Alice.

```javascript
function send_cross_chain_msg(
        string memory to_chain,
        address from_address,
        uint256 to_handler,
        PayloadType payload_type,
        bytes calldata payload
    ) external {

        nonce_manager[from_address] += 1;
```
Hence now, the nonce_manager[Alice] , in `Handler = 1` , but in `Settlement = 2`.

Hence now, when Alice will initiate her settlement , the `txId's` in Handler contract and Settlement contract, `for the same transaction/settlement call` will be DIFFERENT, since the nonce is different now.

Lets say in handler it is `tx1`, and in settlement its `tx2`.

`tx1` will be made using `nonce = 2` & `tx2` will be made using `nonce = 3`,hence would be different.

Now when validator will call `recieve_cross_chain_callback`, if he passes `tx1`,then it will revert because of following check in `processCrossChainCallback` function : 

```javascript
function processCrossChainCallback(
        uint256 txid,
        string memory from_chain,
        uint256 from_handler,
        address to_handler,
        CrossChainMsgStatus status,
        uint8 sign_type,
        bytes calldata signatures
    ) internal {
        require(
            create_cross_txs[txid].status == CrossChainMsgStatus.Pending, 
            "Invalid transaction status"
        );
```
Since for `tx1`, in Settlement Contract's `create_cross_txs` mapping the status would be `CrossChainMsgStatus.Unknown` 

And if validator passes, `tx2`, then it will revert in the Handler contract's `receive_cross_chain_callback` function call, because of the same check present in it.
Since for `tx2`,in Handler Contract's `create_cross_txs` mapping the status would be `CrossChainMsgStatus.Unknown`.

Hence callback function will always revert for the ALICE's settlement transaction. 
Which breaks the fucntionality of callback functions in the protocol.

And if the settlement mode was `MintBurn`, it will not burn the tokens from Handler contract

```javascript
 if (status == CrossChainMsgStatus.Success) {
            if (mode == SettlementMode.MintBurn) {
                _erc20_burn(address(this), create_cross_txs[txid].amount);
            }
```

Which were being locked, while `cross_chain_erc20_settlement` function call.

```javascript
if (mode == SettlementMode.MintBurn) {
            _erc20_lock(msg.sender, address(this), amount);
```
Causing discrepancy in the supply of tokens, and increasing inflation of token on the source chain. 

`AND THIS WILL HAPPEN FOR EVERY NEXT SETTLEMENT REQUESTS/TRANSACTIONS FROM ALICE`.

Manual Review 

## Recommended Mitigation Steps
Proper access control should be added, where the `ChakraSettlement::send_cross_chain_msg()` function should be only callable by ChakraSettlementHandler contract.

And this should be done in both Solidity and Cairo contracts. 


## Assessed type

Access Control
