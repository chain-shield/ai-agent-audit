# Vulnerability details

## Impact

Consider the following two statements:

1. According to the documentation, the protocol is deployed on multiple chains: Ethereum, Base, Arbitrum, BSC, Optimism, Polygon and zkSync. For all these chains except zkSync, the address of the deployed contract depends on the sender's address and nonce. Thus, like many cross-chain DeFi protocols, the address of the `ChakraSettlementHandler` contract could be the same on some of these chains.

2. In `ChakraSettlement::receive_cross_chain_msg`, the hash on which the signatures are based depends on six factors([link](https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/settlement/contracts/ChakraSettlement.sol#L183-L192)): `txid`, `from_chain`, `from_address`, `from_handler`, `to_handler`, and `keccak256(payload)`. Among these factors, the only one that depends on the target chain is `to_handler`, which is the address of the `handler/contracts/ChakraSettlementHandler` contract. Additionally, while `payload` contains the target chain name, there is no `require` statement to validate this.

Combining the above two issues with the fact that the `ChakraSettlement::receive_cross_chain_msg` function is `external` and has no access control for calling, a request to mint or unlock tokens for a desired user can be executed across all chains with the same `handler/contracts/ChakraSettlementHandler` contract address.

## Proof of Concept

The hash on which the signatures are based is calculated here:  
([link](https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/settlement/contracts/ChakraSettlement.sol#L183-L192))

```javascript
ChakraSettlement::receive_cross_chain_msg

    bytes32 message_hash = keccak256(
        abi.encodePacked(
            txid,
            from_chain,
            from_address,
            from_handler,
            to_handler,
            keccak256(payload)
        )
    );
```

Then, the `to_handler` address is used to call the `ChakraSettlementHandler::receive_cross_chain_msg` function:  
([link](https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/settlement/contracts/ChakraSettlement.sol#L216-L225))

```javascript
ChakraSettlement::receive_cross_chain_msg

    bool result = ISettlementHandler(to_handler).receive_cross_chain_msg(
        txid,
        from_chain,
        from_address,
        from_handler,
        payload_type,
        payload,
        sign_type,
        signatures
    );
```

In the `receive_cross_chain_msg` function, it only checks the payload validity and extracts `receiverAddress` and `amount` from it. There is no check for target chain validation, and finally, mint or unlock tokens to the target user is executed:  
([code](https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/ChakraSettlementHandler.sol#L300-L355))

```javascript
ChakraSettlementHandler::receive_cross_chain_msg

    ERC20TransferPayload memory transfer_payload = codec
        .deocde_transfer(msg_payload);

    if (mode == SettlementMode.MintBurn) {
        _erc20_mint(
            AddressCast.to_address(transfer_payload.to),
            transfer_payload.amount
        );
        return true;
    } else if (mode == SettlementMode.LockUnlock) {
        _erc20_unlock(
            AddressCast.to_address(transfer_payload.to),
            transfer_payload.amount
        );

        return true;
    }
```

## Recommended Mitigation Steps

To mitigate this issue, consider adding `chain.id` or `chain_id` to the calculation of the hash to ensure that the signatures are unique to each chain:

```diff
ChakraSettlement::receive_cross_chain_msg

    bytes32 message_hash = keccak256(
        abi.encodePacked(
+           chain.id,
            txid,
            from_chain,
            from_address,
            from_handler,
            to_handler,
            keccak256(payload)
        )
    );
```
