# Vulnerability details

## Impact

Receiving operations can be potentially replayed across different chains. This can lead to some unexpected scenarios as users would be able to repeatedly execute the transaction.

## Proof of Concept

To prevent replay attacks, the signature should depend on chainId:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/settlement/contracts/ChakraSettlement.sol#L293-295
```
  bytes32 message_hash = keccak256(
            abi.encodePacked(txid, from_handler, to_handler, status)
        );
```

Now when getting the hash of the message, it can be seen that there is no chainId included.

The same issue is present on the Starknet chain:

https://github.com/code-423n4/2024-08-chakra/blob/main/cairo/handler/src/settlement.cairo#L340
```
 let mut message_hash: felt252 = LegacyHash::hash(from_chain, (cross_chain_msg_id, to_chain, from_handler, to_handler));

```

## Tools Used

Manual review.

## Recommended Mitigation Steps

Include chainId when calculating `message_hash`.
