# Vulnerability details

## Impact
Discrepancy in datatype of parameters while processing sending cross chain message, can lead to validators scan and sign a different message_hash, causing failure while signature verification at the time of processing receiving cross chain message.

## Proof of Concept
According to the DOCS flow chart, Chakra validators `scan event` emitted while `send_cross_chain_msg` function.

From scanning the event, the parameters are being used to create `message_hash`, and then the validators sign the hash and call `receive_cross_chain_msg` function in Settlement contract by passing their signatures concatenated.

Then their signatures are being verified against the message_hash created by the parameters passed in `receive_cross_chain_msg`

`BUT THE ISSUE IS :`

The datatype of parameters in the event and the datatype of same parameter while generating message_hash for verification of signatures is different.

```javascript
function send_cross_chain_msg(
        string memory to_chain,
        address from_address,
        uint256 to_handler,
        PayloadType payload_type,
        bytes calldata payload
    ) external {
        nonce_manager[from_address] += 1;

        address from_handler = msg.sender;
        
        uint256 txid = uint256(
            keccak256(
                abi.encodePacked(
                    contract_chain_name, // from chain
                    to_chain,
                    from_address, // msg.sender address
                    from_handler, // settlement handler address
                    to_handler,
                    nonce_manager[from_address]
                )
            )
        );
        
        create_cross_txs[txid] = CreatedCrossChainTx(
            txid,
            contract_chain_name,
            to_chain,
            from_address,
            from_handler,
            to_handler,
            payload,
            CrossChainMsgStatus.Pending
        );

        emit CrossChainMsg(
            txid,
            from_address,
            contract_chain_name,
            to_chain,
            from_handler,
            to_handler,
            payload_type,
            payload
        );
    }
```

```javascript
function receive_cross_chain_msg(
        uint256 txid,
        string memory from_chain,
        uint256 from_address,
        uint256 from_handler,
        address to_handler,
        PayloadType payload_type,
        bytes calldata payload,
        uint8 sign_type, // validators signature type /  multisig or bls sr25519
        bytes calldata signatures // signature array
    ) external {
        {
            // verify signature
            bytes32 message_hash = keccak256(
                abi.encodePacked(
                    txid,
                    from_chain,
                    from_address,
                    from_handler,
                    to_handler,
                    keccak256(payload)
                )
            );
```

In the event the datatype of parameters is :
`from_handler : address`
`from_address : address`
`to_handler   : uint256`

Hence the validators will scan these parameters in the above format, and the message_hash will made and will be signed.

But while receiving the msg :
`from_handler : uint256`
`from_address : uint256`
`to_handler   : address`

The datatype is different.

Hence while generating the message_hash [bytes32 message_hash = keccak256(abi.encodePacked(....)].

The hash will be generated with the different parameter values/datatype

Which will generate a different hash than the original one the validators signed.

Hence while `verify` function call, the verification will fail and it will revert with `INVALID SIGNATURE`.

Also while sending, the same parameter values with datatypes is being stored and saved on `create_cross_tx[txId]` mappings.

Hence the validators while scanning, if not scanned from event, and if checked from storage variables, will only get the parameters in the same format, and hence will proceed signing the message_hash generated using same format.

Hence there's discrepancy in the datatypes in the storage/saving mappings & events too.

## Tools Used
Manual Review

## Recommended Mitigation Steps
While processing `receive_cross_chain_msg`, the input  parameters datatypes should be processed similar to `send_cross_chain_msg` parameters datatype

i.e

`from_handler should be address`
`from_address should be address`
`to_handler   should be uint256`.
