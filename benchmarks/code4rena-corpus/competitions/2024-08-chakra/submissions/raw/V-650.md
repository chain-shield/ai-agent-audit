# Vulnerability details

## Impact
Critical Issue in `ChakraSettlement.sol` as the subsequent internal transaction  `ChakraSettlementHandler::receive_cross_chain_callback()` will simply revert as `ChakraSettlementHandler.sol` expects the message status to be of `CrossChainTxStatus.Pending` i.e 1 but due to issue discovered the status is 0. This will cause complete DoS for the validator which will lead to at least following problems : 
- Message can never be settled, this violoates the said invariant of `handler` which is "Cross-chain transaction statuses are properly tracked and updated (Pending, Settled, or Failed)." 
- Tokens are not burned, leading to token inflation as the supply continuously increases, which results in a decrease in the token's price.

## Proof of Concept
The `ChakraSettlementHandler.sol` and `ChakraSettlement.sol` contracts maintain the nonces  `nonce_manager`, to track the messages/transactions sent and to compute the keys `txid` for the mapping `create_cross_txs` in both `ChakraSettlementHandler` and `ChakraSettlement`.
The keys are computed as :
In handler
https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L139

In settlement
https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/ChakraSettlement.sol#L122

These keys are used to store message information in the contracts. To complete the message/transaction lifecycle, the validator invokes the callback `ChakraSettlement::receive_cross_chain_callback()` with the `txid`. This function internally calls `ChakraSettlementHandler::receive_cross_chain_callback()` to burn the tokens and finalize the settlement of the message/transaction.

However as per the sytem design of the protocol `txid` generated in  `ChakraSettlement.sol` is used during `ChakraSettlement::receive_cross_chain_callback()` call by the validator/proposer, but inside the internal call to `ChakraSettlementHandler::receive_cross_chain_callback` `create_cross_txs[txid].status` will return 0 and require statement `  require(create_cross_txs[txid].status == CrossChainTxStatus.Pending, "invalid CrossChainTxStatus");` will fail because while initially calling `ChakraSettlementHandler::cross_chain_erc20_settlement()` `txid` generated inside `ChakraSettlementHandler` was used to upadate `create_cross_txs[txid]` mapping.
https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L139

The issue arises when the `nonce_manager` in the `ChakraSettlementHandler` and the `nonce_manager` in the `ChakraSettlement` are not synchronized. Because there is only one `ChakraSettlement` contract but multiple `ChakraSettlementHandler` contracts, the `nonce_manager` values will become out of sync when a user sends or transfers different tokens. Each different token has its dedicated `ChakraSettlementHandler`, so for a user the nonces will always reamin out of sync.

## Recommended Mitigation Steps
Fixing this issue require change in the state variable which track `nonce_manager` in `ChakraSettlement.sol`.
The mapping should set like that it accounts for user nonces orginated from each handler, so instead of using 

```
-   mapping(address => uint256) public nonce_manager;
+   mapping( address => mapping(address => uint256) public nonce_manager; // [ ( Handler => User ) => nonce ]
```
