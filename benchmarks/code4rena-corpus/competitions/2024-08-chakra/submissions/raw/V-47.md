# Vulnerability details

## Impact
The protocol supports bridging both ERC20 tokens and Chakra tokens across chains using `ChakraHandlerSettlement::cross_chain_erc20_settlement`. When the `LockUnlock` or `BurnUnlock` settlement mode is employed, an equivalent amount of tokens is expected to be unlocked on the destination chain:

On the destination chain, unlocking involves transferring the tokens from the handler contract to the recipient:
```solidity
function _erc20_unlock(address to, uint256 amount) internal {
    _safe_transfer(to, amount);
}

function _safe_transfer(address to, uint256 amount) internal {
    require(
        IERC20(token).balanceOf(address(this)) >= amount,
        "Insufficient balance"
    );

    // transfer tokens
>>>    IERC20(token).transfer(to, amount);
}
```

The problem is that there is no mechanism in place to ensure that the handler contract on the destination chain has a sufficient balance of the ERC20 tokens being transferred. If users initiate a cross-chain ERC20 transfer with a large amount on the source chain, and the handler contract on the destination chain lacks the necessary balance, the settlement process will **revert**, causing the cross-chain message to remain unresolved.

This scenario creates a **deadlock**: the cross-chain message is successfully sent from the source chain and the amounts are locked/burned on the source chain but can never be settled on the destination chain. Additionally, the source chain remains unaware of this failure because the `CrossChainHandleResult` event is not emitted on the destination chain's Settlement contract, preventing Chakra nodes from triggering the necessary callback on the source chain.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Introduce a mechanism to verify that the handler contract on the destination chain holds a sufficient balance of the required tokens before the cross-chain message is initiated on the source chain
