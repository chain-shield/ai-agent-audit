# Vulnerability details


## **Summary**

The `cross_chain_erc20_settlement` function in `ChakraSettlementHandler` contract is used to initiate cross-chain ERC20 transactions between Layer 1 (ETH) and Layer 2 (Starknet). However, the function passes addresses such as `to`, `to_token`, and `to_handler` as `uint256`, which raises concerns regarding the validity of these addresses on Starknet, where addresses are represented as `felt252`. Without proper validation, there is a risk that addresses larger than Starknet’s finite field limit could be passed, leading to cross-chain transaction failures.


## **Impact**

- Passing `uint256` addresses from ETH (L1) to Starknet (L2) can result in invalid conversions if the address exceeds the Starknet finite field limit (`p`). This could cause the transactions to fail or be processed incorrectly on Starknet.

- If an invalid or mismatched address is used in the cross-chain message, the funds or tokens may be incorrectly routed, potentially leading to loss of assets or transaction rejections on the Starknet side.

- Cross-chain messages that include invalid addresses may cause the Starknet contract to reject the transaction, preventing successful cross-layer communication.


## **Recommendation**

Implement a validation check to ensure that addresses (such as `to`, `to_token`, `to_handler`) passed from L1 are within the allowable range for Starknet addresses (`felt252`). Specifically, validate that the addresses are less than the finite field limit `p` of Starknet:
     ```solidity
     require(to < STARKNET_FIELD_PRIME, "Invalid L2 address");
     ```

Along with this ensure that all necessary addresses used in the cross-chain transaction (`to`, `to_token`, `to_handler`) are properly validated before sending the cross-chain message.
