# Vulnerability details


Whenever the txs are to be received the signatures need to be verified via `self.check_chakra_signatures()`:
https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/settlement.cairo#L173-L190

```cairo
        fn check_chakra_signatures(
            self: @ContractState, message_hash: felt252, signatures: Array<(felt252, felt252, bool)>
        ){
            let mut pass_count = 0;
            let mut i = 0;
            loop {
                if i > signatures.len()-1{
                    break;
                }
                let (r,s,y) = * signatures.at(i);
                let pub_key: felt252 = recover_public_key(message_hash,r,s,y).unwrap();
                if self.chakra_validators_pubkey.read(pub_key) > 0{
                    pass_count += 1;
                }
                i += 1;
            };
            assert(pass_count >= self.required_validators_num.read(), 'Not enough validate signatures');
        }
```

Now per the [documentation](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/settlement.cairo#L170), validated signatures should be more than required_validators_num.

Issue however is that when checking the signatures, no checks that the address gotten from the pub key has not already being counted in the loop, which then allows for signatures to be counted multiple times and as such the invariant with signatures pertaining threshold logic is broken since less than required amount of signatures can be used to validate the signatures, all that's needed to be done is to repeat the signature in the loop.

Note that the required amount of validators has been carefully set by the manager to ensure if not enough validators sign then the message or callback should not be received/processed: https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/settlement.cairo#L195-L202


## Impact

Main invariants hinted in the documentation: https://github.com/code-423n4/2024-08-chakra/tree/main?tab=readme-ov-file#main-invariants are being broken, since the required number of signatures would not be reached and the tx would be validated, which goes agains the required number of signatures set by the admin and the two hinted invariants below:

```markdown
    5. Received cross-chain messages are verified using signatures before being processed.
    10. Signature verification is required for both receiving cross-chain messages and cross-chain callbacks.
```

## Recommended Mitigation Steps

Apply a check in the loop to ensure that signatures are not repeated in it, this can easily be achieved by requiring that the signatures being passed must be in an ascending/descending order.
