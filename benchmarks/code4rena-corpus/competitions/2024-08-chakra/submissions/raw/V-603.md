# Vulnerability details

## Description
[send_cross_chain_msg](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/ChakraSettlement.sol#L111) is called during the execution of [cross_chain_erc20_settlement](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L111) as shown here;
```solidity
settlement.send_cross_chain_msg(
                to_chain,
                msg.sender,
                to_handler,
                PayloadType.ERC20,
                cross_chain_msg_bytes
            );
        }
```
 Then, send_cross_chain_msg in the settlement contract would generate, save and emit the same tx id in the handler contract as seen here. 
```solidity
nonce_manager[from_address] += 1;

        address from_handler = msg.sender;

        uint256 txid = uint256(
            keccak256(
                abi.encodePacked(
                    contract_chain_name, // from chain
                    to_chain,
                    from_address, // msg.sender address
                    from_handler, // settlement handler address
                    to_handler,
                    nonce_manager[from_address]
                )
            )
        );

        create_cross_txs[txid] = CreatedCrossChainTx(
            txid,
            contract_chain_name,
            to_chain,
            from_address,
            from_handler,
            to_handler,
            payload,
            CrossChainMsgStatus.Pending
        );

        emit CrossChainMsg(
            txid,
            from_address,
            contract_chain_name,
            to_chain,
            from_handler,
            to_handler,
            payload_type,
            payload
        );
    }
```

This ensures consistency between the settlement and handler contract.The function is external which means it can be called by any outside contract. Any malicious user can invoke send_cross_chain_msg in the settlement contract to generate, save and emit as many tx ids that are not saved in the handler contract. This will lead to inconsistency and difference in the transaction ids saved in handler contract and those in settlement contract.
## Impact
send_cross_chain_msg in the settlement contract can be called by anyone leading to inconsistency in the transaction ids saved in the handler contract and those in settlement contract.

Furthermore, all the part of the protocol, both now and in the upgraded contracts, that take the tx ids saved in the settlement contract as valid without checking if it was also saved in the handler contract would malfunction.
Also, an attacker can find a way to exploit this critical difference to cause great havoc. Better safe than sorry.

## Tools Used
manual review
## Recommended Mitigation Steps
send_cross_chain_msg should only be called by the handler contract to prevent inconsistency in the tx id of the user. There should be a check that ensures that send_cross_msg is called only the handler contract.
