# Vulnerability details

## Impact
Implementation contracts can be self-destructed which would completely brick the Proxies.

## Description
All of the upgradeable contracts from the Chakra protocol use the UUPS pattern (e.g they inherit `UUPSUpgradeable` from OpenZeppelin). This means that the proxy realies on the implementation contract to upgrade to another implementation. More specifically [the `upgradeToAndCall()` function](https://github.com/OpenZeppelin/openzeppelin-contracts-upgradeable/blob/master/contracts/proxy/utils/UUPSUpgradeable.sol#L92-L95).

Since that function [executes a delegatecall](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/master/contracts/proxy/ERC1967/ERC1967Utils.sol#L72), it is absolutely imperative that the implementation initializers are disabled, because a malicious user can take over the implementation, destroy it and brick the proxy, since it will not be able to upgrade to another contract

The major problem here is that none of the protocols have disabled their initializers and are prone to the vulnerability ([OZ docs explicitly warn about this](https://docs.openzeppelin.com/upgrades-plugins/1.x/writing-upgradeable#initializing_the_implementation_contract))

Among the affected protocols are:
- `ChakraToken.sol`
- `BaseSettlement.sol` and all contracts inheriting from it
- `BaseSettlementHandler.sol` and all contracts inheriting from it
- and all upgradeable contracts basically

## Proof of Concept
I'll use the `ChakraToken.sol` contract as an example:

- Chakra token proxy is deployed with `implementation 1`
- Since `disableInitialziers` is not called in the constructor of the implementation, it remains uninitialized - meaning anyone can call `initialize()` on the implementation (NOT the proxy) contract
- Bob is malicious and calls `initialize()` on `implementation 1` and sets himself as the owner. Then he calls `upgradeToAndCall()` providing a malicious contract that executes a self-destruct. Since it is a delegate call this will destroy the implementation
- Proxy has no way to upgrade to another contract

## Tools Used
Manual review

## Recommended Mitigation Steps
Disable the initializers for all upgradeable contracts like this:

```solidity
/// @custom:oz-upgrades-unsafe-allow constructor
constructor() {
    _disableInitializers();
}
```
