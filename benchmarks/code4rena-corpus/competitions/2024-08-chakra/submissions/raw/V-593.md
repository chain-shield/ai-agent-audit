# Vulnerability details

## Impact
Although the likelihood of a manager setting the number of required validators to zero is low, the impact would be extreme: it would allow any user to successfully submit any cross chain message to the protocol.

This would essentially unlock all tokens held by the relevant handler contract to any user, and also allow any other handlers to be compromised.

## Proof of Concept
The functions `set_required_validators_num()` have no checks on the value of the argument `new_num`. It can be zero.

If `required_validators_num` is zero, any non-empty array of signatures will be approved by `self.check_chakra_signatures()`. A public key returned by `core::ecdsa::recover_public_key()` does not need to be a registered validator; it simply needs to not revert and so the signature checking loop can break:
```
if i > signatures.len()-1{
    break;
}
```
And then the `assert` test at the end of the function will always pass if `required_validators_num` is zero:
```
assert(pass_count >= self.required_validators_num.read(), 'Not enough validate signatures');
```

And so any cross chain message is now valid and the protocol on Starknet has effectively no signature protection.

Note that this vulnerability does not exist in the Solidity code because, to return true, `verifyECDSA()` will always need at least one valid signature from a validator because of the short circuit effect of the `&&` operator in this test:
```
if (
validators[msgHash.recover(sig)] && ++m >= required_validators
) {
return true;
}
```

## Tools Used
Manual inspection

## Recommended Mitigation Steps
Add a requirement in `set_required_validators_num` that `new_num` be greater than zero.
