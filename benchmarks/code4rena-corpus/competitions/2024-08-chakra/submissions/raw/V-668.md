## Proof of Concept

Evidently there is a check that ensures that the current status of the txId must be `Unknown`, now attempts are then made to settle and receive the cross chain message via: `ISettlementHandler(to_handler).receive_cross_chain_msg()`, now per the documentation and as shown in the code snippets, this cross chain tx can then only be moved either to the `Failed`/`Success` status, pending if there is an error in the receiving in the handler, which could happen for multiple reasons one of which would be an insufficient balance, issue however is that whereas Chakra expects transactions to fail there is no transaction retryal logic, this then inconveniences users, considering it could even cause stuck assets, consider the following scenario:

- `SettlementMode` is `LockUnlock`
- User requests a cross chain transfer payload tx.
- Erc20 tokens gets locked since we have a transfer payload.
- When recieving the tx fails due to an insufficient balance for a successful erc20 unlock.
- The status gets set to `FAILED`
- The initially locked tokens are forever lost to the `to`/`from` since no retryal logic is available.

## Impact

Tokens could get permanently lost to both the sending/receiving parties of a cross chain requested tx, [considering when receiving it there is a need to always ensure the status is at `Unknown`](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/settlement/contracts/ChakraSettlement.sol#L199-L203).

## Recommended Mitigation Steps

Integrate a retryal logic for failed cross chain txs or have the sender of the address be able to cancel the tx on the originating chain in the case it fails on the receiving chain.
