# Vulnerability details

## Vulnerability details
The `verifySignature` function in the `ChakraSettlement` contract does not properly validate the provided signatures. It constructs a `message_hash` by concatenating the `txid`, `from_handler`, `to_handler`, and `status` values using `abi.encodePacked`. However, it then passes this `message_hash` directly to the `signature_verifier.verify` function without hashing it first.

According to the `ISettlementSignatureVerifier` interface, the `verify` function expects the first argument to be the hash of the message, not the raw message itself. By skipping the hashing step, an attacker can provide signatures that match the raw concatenated message instead of its hash, bypassing the signature verification.

## Impact
This vulnerability allows an attacker to execute unauthorized cross-chain transactions by providing signatures that match the raw concatenated message. The attacker can construct a `message_hash` that satisfies the signature verification without possessing valid signatures from the required validators. 

This can lead to the execution of malicious cross-chain callbacks, potentially resulting in the loss or manipulation of funds and breaking the integrity of the settlement process. Attackers could steal funds, block legitimate transactions, or cause other disruptions.

## Proof of Concept
1. Attacker constructs a malicious cross-chain callback with desired `txid`, `from_handler`, `to_handler`, and `status` values.

2. Attacker calculates the raw concatenated message: 
   ```solidity
   bytes32 message = abi.encodePacked(txid, from_handler, to_handler, status);
   ```

3. Attacker generates signatures that match the raw message instead of its hash, either by signing the raw message directly or finding signatures that coincidentally match.

4. Attacker calls `receive_cross_chain_callback` with the malicious callback data and crafted signatures. 

5. `verifySignature` constructs `message_hash` using `abi.encodePacked` and passes it to `signature_verifier.verify`.

6. Since the signatures match the raw message, the verification succeeds, even though the signatures are invalid for the actual message hash.

7. The malicious callback is processed, bypassing the intended signature verification.

## Tools Used
- Manual code review
- Solidity compiler 

## Recommended Mitigation Steps
Hash the `message_hash` using `keccak256` before passing it to `signature_verifier.verify`, ensuring signatures are verified against the actual message hash:

```solidity
bytes32 hashed_message = keccak256(message_hash);
require(
    signature_verifier.verify(hashed_message, signatures, sign_type),
    "Invalid signature"
);
```
