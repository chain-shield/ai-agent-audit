# Vulnerability details

## Impact

In Solidity contracts, cross-chain transaction IDs (`txid`) are uniquely generated based on the source and destination chain information, sender address, handler addresses, and the sender's nonce. These transaction IDs are expected to be identical on both the handler and settlement contracts, as shown below:
```solidity
// ChakraSettlementHandler

function cross_chain_erc20_settlement(
    string memory to_chain,
    uint256 to_handler,
    uint256 to_token,
    uint256 to,
    uint256 amount
) external {
    // --SNIP

    // Create a new cross chain tx
    uint256 txid = uint256(
        keccak256(
            abi.encodePacked(
                chain,
                to_chain,
                msg.sender, // from address for settlement to calculate txid
                address(this), //  from handler for settlement to calculate txid
                to_handler,
                nonce_manager[msg.sender]
            )
        )
    );

    // --SNIP
    // Send the cross chain msg
    settlement.send_cross_chain_msg(
        to_chain,
        msg.sender,
        to_handler,
        PayloadType.ERC20,
        cross_chain_msg_bytes
    );

    // --SNIP
}
```
```solidity
// ChakraSettlement

function send_cross_chain_msg(
    string memory to_chain,
    address from_address,
    uint256 to_handler,
    PayloadType payload_type,
    bytes calldata payload
) external {
    // --SNIP
    address from_handler = msg.sender;
    uint256 txid = uint256(
        keccak256(
            abi.encodePacked(
                contract_chain_name, // from chain
                to_chain,
                from_address, // msg.sender address
                from_handler, // settlement handler address
                to_handler,
                nonce_manager[from_address]
            )
        )
    );

    // --SNIP
}
```
The transaction ID (`txid`) **must** be identical across both the handler and settlement contracts because Chakra nodes deliver cross-chain messages to the destination chain using the event `CrossChainMsg` and handle callbacks to the source chain using `CrossChainHandleResult` events emitted by the settlement contract. Any discrepancy between `txid` generation on the handler and settlement contracts can cause the system to break, as validators will rely on the `txid` emitted by the settlement contract.

The vulnerability arises from the independent management of `nonce_manager` on both `ChakraSettlement` and `ChakraSettlementHandler` contracts. **This opens the door for malicious users to manipulate the `nonce_manager` on the settlement contract**, which will desynchronize the `txid` generation process between the handler and settlement contracts. As a result, the cross-chain transaction can be blocked.

A malicious user can directly call `ChakraSettlement::send_cross_chain_msg` and pass the `from_address` of a legitimate user, causing the `nonce_manager` for that user to increment on the settlement contract but not on the handler contract.
```solidity
>>>nonce_manager[from_address] += 1;

address from_handler = msg.sender;

uint256 txid = uint256(keccak256(abi.encodePacked(contract_chain_name, to_chain, from_address,  from_handler, to_handler, nonce_manager[from_address])));
```
This results in mismatched txid values on the handler and settlement contracts, causing any subsequent legitimate cross-chain message initiated by the user to fail during the callback process because the `txid` received by the handler contract is different and unkown from the one it was calculated originally:

```solidity
>>>            txid,

        create_cross_txs[txid].status = status;
```

Below is a summary of the exploit:
1. The malicious user calls `ChakraSettlement::send_cross_chain_msg`, using the target user’s `from_address`. This increments the user's `nonce_manager` on the settlement contract only.
2. When the legitimate user initiates a cross-chain ERC20 transaction, the `nonce_manager` is incremented and used to calculate the `txid` on the handler contract. However, due to the earlier manipulation, the `nonce_manager` on the settlement contract is already ahead, leading to a different `txid` calculation.
3. The `txid` calculated on the handler contract does not match the one calculated on the settlement contract. During the callback process, the mismatch causes the handler contract to revert, preventing the cross-chain message from being finalized.

## Proof Of Concept
Consider the following scenario:
1. Alice’s `nonce_manager` on both the settlement and handler contracts is `2`.
2. Bob, a malicious user, calls `ChakraSettlement::send_cross_chain_msg`, passing Alice’s `from_address` as the input. This increments Alice’s `nonce_manager` to `3` on the settlement contract but leaves it at `2` on the handler contract.
3. Alice initiates a legitimate cross-chain ERC20 transaction. The `nonce_manager` is [incremented to `3`](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L135) on the handler contract, and a `txid` is [calculated based on the updated nonce](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L147).

    3.1 The settlement contract recalculates the `txid` using its `nonce_manager`, [which is now 4](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/ChakraSettlement.sol#L118), resulting in a mismatch.

    3.2 `ChakraSettlement::send_cross_chain_msg` will emit the event `CrossChainMsg` with the `txid` calculated on the settlement contract.
4. The cross-chain message is received on the destinatino chain B and the event `CrossChainHandleResult` is emitted.
5. When Chakra nodes process the cross-chain message and attempt to execute the callback via `receive_cross_chain_callback`, the handler contract reverts due to the mismatched `txid`.
    
    5.1 the `processCrossChainCallback` will call the handler contract passing the `txid`:
    ```solidity
    if (ISettlementHandler(to_handler).receive_cross_chain_callback(
    >>>        txid,
            from_chain,
            from_handler,
            status,
            sign_type,
            signatures
        )
    ) {
        create_cross_txs[txid].status = status;
    } else {
        create_cross_txs[txid].status = CrossChainMsgStatus.Failed;
    }

    ```

    5.2 Since the `txid` passed to the handler contract does not match the one generated on the handler side, the transaction will revert because the cross-chain message is unkown:
    ```solidity
    function receive_cross_chain_callback(uint256 txid, string memory from_chain, uint256 from_handler, CrossChainMsgStatus status, uint8, bytes 
    ) external onlySettlement returns (bool) {
        require(create_cross_txs[txid].status == CrossChainTxStatus.Pending,"invalid CrossChainTxStatus");
    }
    ```

As a result, the cross-chain message can not be finalized, if the contract's mode is `MintBurn`, the initial amount of the tokens bridged will not be burned on `receive_cross_chain_callback`

## Recommended Mitigation Steps
It is recommended to centralize the nonce management and txid calculation on the handler contract. The handler contract should generate the txid and pass it to the settlement contract, rather than recalculating the txid separately on the settlement contract.

###### `ChakraSettlementHandler::cross_chain_erc20_settlement`
```diff

    uint256 to_handler,
```
