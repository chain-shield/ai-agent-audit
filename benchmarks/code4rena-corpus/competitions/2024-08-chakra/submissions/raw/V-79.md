# Vulnerability details

## Impact

`ChakraSettlement` contract in cairo code is vulnerable to a replay attack where a single malicious validator can reuse their signature multiple times to bypass the security checks. This vulnerability allows a malicious validator to manipulate the `receive_cross_chain_msg function`, potentially leading to unauthorized token minting, or token transfers. The exploit leverages the `check_chakra_signatures` function, which only counts the total number of valid signatures but does not verify that each signature corresponds to a unique validator. By repeatedly using the same valid signature, a single validator could meet the required number of validators (required_validators_num), thus compromising the integrity of the cross-chain message validation.

## Proof of Concept

The vulnerability is in the `check_chakra_signatures` function in the Cairo code of the ChakraSettlement contract.This function counts the number of valid signatures without checking if each signature comes from a unique validator. Consequently, a single malicious validator can reuse their signature multiple times to meet the required number of validator signatures (required_validators_num). This oversight allows a malicious validator to bypass the security check

```cairo
        fn check_chakra_signatures(
            self: @ContractState, message_hash: felt252, signatures: Array<(felt252, felt252, bool)>
        ){
            let mut pass_count = 0;
            let mut i = 0;
            loop {
                if i > signatures.len()-1{
                    break;
                }
                let (r,s,y) = * signatures.at(i);
                let pub_key: felt252 = recover_public_key(message_hash,r,s,y).unwrap();
                if self.chakra_validators_pubkey.read(pub_key) > 0{
                    pass_count += 1;
                }
                i += 1;
            };
            assert(pass_count >= self.required_validators_num.read(), 'Not enough validate signatures');
        }
```
Similarly, in the receive_cross_chain_msg function, there is no check for unique signatures or validators. A malicious validator could submit multiple instances of their valid signature to pass the verification check.This allows attacker to send malicious payload which would allow him  exploit the contract by minting tokens or transferring tokens to himself.

```
       fn receive_cross_chain_msg(
            ref self: ContractState,
            cross_chain_msg_id: u256,
            from_chain: felt252,
            to_chain: felt252,
            from_handler: u256,
            to_handler: ContractAddress,
            sign_type: u8,
            signatures: Array<(felt252, felt252, bool)>,
            payload: Array<u8>,
            payload_type: u8,
        ) -> bool {

                if i > payload_span.len()-1{
                    break;
                }
                message_hash = LegacyHash::hash(message_hash, * payload_span.at(i));
                i += 1;
            };
            self.check_chakra_signatures(message_hash, signatures);
```
