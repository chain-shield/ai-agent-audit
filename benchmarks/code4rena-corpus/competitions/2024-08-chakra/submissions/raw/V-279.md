# Vulnerability details

## Impact
The current implementation of the `verifyECDSA` function does not validate the source or correctness of the `msgHash`. This leaves the system vulnerable to signature forgery and replay attacks. An attacker could potentially submit a valid signature for a malicious or incorrect `msgHash`, leading to unauthorized actions within the system.

By not verifying that the `msgHash` corresponds to a legitimate transaction, validators could unknowingly sign off on illegitimate or fraudulent transactions, allowing attackers to execute unintended operations, such as replaying previous valid signatures in a different context, resulting in repeated execution of certain actions.

## Proof of Concept
Consider the following example of the current function implementation:
```javascript
function verifyECDSA(bytes32 msgHash, bytes calldata signatures) internal view returns (bool) {
    require(signatures.length % 65 == 0, "Signature length must be a multiple of 65");
    uint256 len = signatures.length;
    uint256 m = 0;
    for (uint256 i = 0; i < len; i += 65) {
        bytes memory sig = signatures[i:i + 65];
        if (validators[msgHash.recover(sig)] && ++m >= required_validators) {
            return true;
        }
    }
    return false;
}
```
* Issue:

There is no check to ensure that the `msgHash` provided to the `verifyECDSA` function is valid or derived from trusted sources. It could potentially be a hash of manipulated or fraudulent data.

* Example Attack Scenario:
A malicious actor submits a previously valid signature for a manipulated msgHash, triggering the same action as before but in a new context.
The function will proceed with verification as long as the signature is valid, even though the underlying transaction data represented by msgHash has been altered.
Without further validation, the system could authorize unintended actions, like unauthorized asset transfers or the re-execution of previous valid transactions.

The core issue arises from the lack of validation of the source and correctness of the `msgHash` in the `verifyECDSA` function. The function assumes that the `msgHash` passed is already legitimate, which could be exploited by a malicious actor. Here’s a breakdown of how this vulnerability can be exploited:

* Forgery Risk:

Since the function does not verify that the msgHash is tied to legitimate transaction data (e.g., specific transaction parameters like txid, from_handler, or to_handler), an attacker could craft their own msgHash containing fraudulent or arbitrary data.
The attacker can then supply a previously valid signature for the manipulated hash. If the signature matches the structure expected by the msgHash.recover function, the system will treat it as legitimate, potentially allowing unauthorized actions.


Replay attacks occur when a previously valid signature is reused in a different context or for a different transaction.
Since the msgHash is not tied to unique transaction parameters like a nonce or timestamp, the attacker can reuse the same signature to replay the transaction multiple times.
if a validator was to previously sign off on a transaction that executed a transfer of assets, the attacker can submit the same signature with the same `msgHash` to replay the transfer, even though the context of the transaction has changed.

## Recommended Mitigation Steps
msgHash should be derived from known, expected transaction parameters, and it should be tied to the specific transaction context to ensure the integrity of the message.

```javascript
function verifySignature(
    uint256 txid,
    uint256 from_handler,
    address to_handler,
    CrossChainMsgStatus status,
    uint8 sign_type,
    bytes calldata signatures
) internal view {
    // Construct the expected message hash from known parameters
    bytes32 expectedMessageHash = keccak256(abi.encodePacked(txid, from_handler, to_handler, status));

    // Verify the message hash is the real one
    require(expectedMessageHash == msgHash, "Unexpected message hash");

    // Perform signature verification
    require(
        signature_verifier.verify(expectedMessageHash, signatures, sign_type),
        "Invalid signature"
    );
}

```
