# Vulnerability details

## Impact
`is_valid_handler` check should be made before completion of sending the cross chain settlement on the destination chain, instead of while receiving the cross chain message

It can cause direct loss for users, if `is_valid_handler` returns FALSE while receiving the message.

## Proof of Concept
Once sending a cross chain erc20 settlement is being completed.
Receiving the cross chain msg on the destination chain is being processed by validators by passing the parameters.

But in `receive_cross_chain_msg`, `is_valid_handler` check is being made, for which if the `from_chain` & `from_handler` is not valid for the `destination handler`, it will return FALSE.

```javascript
function receive_cross_chain_msg(
        uint256 /**txid */,
        string memory from_chain,
        uint256 /**from_address */,
        uint256 from_handler,
        PayloadType payload_type,
        bytes calldata payload,
        uint8 /**sign type */,
        bytes calldata /**signaturs */
    ) external onlySettlement returns (bool) {
        //  from_handler need in whitelist
        if (is_valid_handler(from_chain, from_handler) == false) {
            return false;
        }
```

But the issue is, while sending itself, tokens are being locked/burned based on mode of settlement, which are unlocked/minted on destination chain while receiving

```javascript
function cross_chain_erc20_settlement(
        string memory to_chain,
        uint256 to_handler,
        uint256 to_token,
        uint256 to,
        uint256 amount
    ) external {
        require(amount > 0, "Amount must be greater than 0");
        require(to != 0, "Invalid to address");
        require(to_handler != 0, "Invalid to handler address");
        require(to_token != 0, "Invalid to token address");

        if (mode == SettlementMode.MintBurn) {
            _erc20_lock(msg.sender, address(this), amount);
        } else if (mode == SettlementMode.LockUnlock) {
            _erc20_lock(msg.sender, address(this), amount);
        } else if (mode == SettlementMode.LockMint) {
            _erc20_lock(msg.sender, address(this), amount);
        } else if (mode == SettlementMode.BurnUnlock) {
            _erc20_burn(msg.sender, amount);
        }
....
```

But if the handler from where the user called and locked/burned his tokens is not a valid_handler on the `to_handler`/destination handler, then the `is_valid_handler` will return FALSE, because of which the status of receiving would be set to FAILED, and then further no `UNLOCKING/MINTING` would take place.

And further retrying is also not possible , based on current design

Which directly causes loss for users.

Hence in order to prevent users making mistake, and losing their tokens, this check should be made, while sending itself, hence if handler will not be valid, then to revert it while sending only, and prevent permanently locking/burning of user's tokens.

## Recommended Mitigation Steps
THE FOLLOWING CHECK SHOULD BE ADDED IN THE `send_cross_chain_msg` function in SETTLEMENT CONTRACT

```javascript
require(ISettlementHandler(to_handler).is_valid_handler(contract_chain_name,from_handler),"Invalid handler");
```

This will check whether handler is valid on destination handler or not , and prevent loss.
