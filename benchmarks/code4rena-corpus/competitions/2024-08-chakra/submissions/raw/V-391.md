# Vulnerability details

## Impact
If any `receive_cross_chain_msg`, fails by any reason i.e Handler contract's `receive_cross_chain_msg` returns `FALSE`, there's no way to retry receiving the message, since the function call will always revert & there's no current mechanism which REFUNDS back the locked/burned tokens if recieving message failed.

This leads to DIRECT loss of funds, locked/burned tokens(based on mode of settlement) of that user, since no further unlocking/minting would happen for their equivalent amount of locked tokens. 

## Proof of Concept
Once an cross chain ERC20 settlement is being initiated, based on the mode of settlement, users erc20 tokens are locked/burned into the `Handler` contract.

```javascript
if (mode == SettlementMode.MintBurn) {
            _erc20_lock(msg.sender, address(this), amount);
        } else if (mode == SettlementMode.LockUnlock) {
            _erc20_lock(msg.sender, address(this), amount);
        } else if (mode == SettlementMode.LockMint) {
            _erc20_lock(msg.sender, address(this), amount);
        } else if (mode == SettlementMode.BurnUnlock) {
            _erc20_burn(msg.sender, amount);
        }
```
_erc20_lock means , tokens are transferred from user, to the HANDLER contract, and _erc20_burn means the tokens are being burnt.

After the `send_cross_chain_msg` function call is being completed.

A validator calls , `receive_cross_chain_msg` function .

Where first it is checked whether the status of `receive_cross_txs[txid]` is `UNKNOWN OR NOT`, and reverts if not UNKNOWN.
```javascript
require(
                receive_cross_txs[txid].status == CrossChainMsgStatus.Unknow,
                "Invalid transaction status"
            );
```
Further in the same function, an internal function call is being made to `SettlementHandler::receive_cross_chain_msg`, and the result is being stored and checked of this internal function call, and then the `receive_cross_txs[txid].status` is being updated 

```javascript
bool result = ISettlementHandler(to_handler).receive_cross_chain_msg(
            txid,
            from_chain,
            from_address,
            from_handler,
            payload_type,
            payload,
            sign_type,
            signatures
        );

        CrossChainMsgStatus status = CrossChainMsgStatus.Failed;
        if (result == true) {
            status = CrossChainMsgStatus.Success;
            receive_cross_txs[txid].status = CrossChainMsgStatus.Success;
        } else {
            receive_cross_txs[txid].status = CrossChainMsgStatus.Failed;
        }
```

`NOW THE ISSUE IS :`

If by any reason , the `ISettlementHandler(to_handler).receive_cross_chain_msg` fails, i.e returns `false`, the `receive_cross_txs[txid].status`  is set to `CrossChainMsgStatus.Failed`.

And then further , retrying receiving the same msg, will always revert, because of the check showed above, that the `STATUS SHOULD BE UNKNOWN OR ELSE IT WILL REVERT`

`NOW, HOW CAN THE FUNCTION CALL FAIL OR RETURN FALSE WOULD BE A QUESTION`.

There can be various reasons.

1.) On the destination, the `from_handler` was in the whitelist while user initiating the settlement.
But then afterwards , before receiving the msg, the owner, due to some reason, `removes the handler from whitelist` from calling `remove_handler` function.
```javascript
function remove_handler(
        string memory chain_name,
        uint256 handler
    ) external onlyOwner {
        handler_whitelist[chain_name][handler] = false;
    }
```
Because of which , in the following check in `receive_cross_chain_msg` of Handler contract :
```javascript
function receive_cross_chain_msg(
        uint256 /**txid */,
        string memory from_chain,
        uint256 /**from_address */,
        uint256 from_handler,
        PayloadType payload_type,
        bytes calldata payload,
        uint8 /**sign type */,
        bytes calldata /**signaturs */
    ) external onlySettlement returns (bool) {
        //  from_handler need in whitelist
>>        if (is_valid_handler(from_chain, from_handler) == false) {
            return false;
        }
```
It will return false, because of which ,then status will be set to failed.

2.) Might happen that user mistakenly input some other handler, which might not be valid on that particular chain.

There can be such cases where the function would return false.

For such cases , there should be an option for retrying receiving the message.

Or else.

`The locked/burn tokens will forever remain locked/will not be minted, and which will cause direct loss for the user.`

## Recommended Mitigation Steps
If the status is failed of the receive_cross_tx[txId], it should be allowed and not revert, so tht retrying is possible, hence preventing loss of funds/tokens of user.
```diff
require(
-                receive_cross_txs[txid].status == CrossChainMsgStatus.Unknow 
+                receive_cross_txs[txid].status == CrossChainMsgStatus.Unknow || receive_cross_txs[txid].status == CrossChainMsgStatus.Failed ,
                "Invalid transaction status"
            );
```

`OR A BETTER OPTION WOULD BE :`

If failed, then via callback function in the Handler's `receive_cross_chain_callback`, the locked function should be unlocked and returned to back to the user, and if burnt, then tokens should be minted back again to the user.

Hence if failed, the users funds will be returned back and it will not cause any loss to them.
