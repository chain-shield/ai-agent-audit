# Vulnerability details

## Impact
The `send_cross_chain_msg` function allows any caller to invoke it without verifying if the caller is indeed the `from_handler`. the function also asssumes that the from address will always be the msg.sender which is not always tha case as there are no checks to ensure that.

```javascript
abi.encodePacked(
                    contract_chain_name, // from chain // @ audit what about the chain id
                    to_chain,
                    from_address, // msg.sender address
          @>>             from_handler, // settlement handler address
                    to_handler,
                    nonce_manager[from_address]
                )
```

This lack of access control could allow unauthorized entities to send cross-chain messages, potentially leading to unauthorized transactions or the disruption of cross-chain communication. This can compromise the integrity of the entire cross-chain communication system.

At the moment owners are able to add handlers and remove them if need be

Additionally: The `receive_cross_chain_msg` is designed to handle the reception of cross-chain messages. However, the function does not include any mechanism to verify that the `from_handler` is indeed authorized to send messages from the specified `from_chain`. This oversight could lead to accepting messages that should never be accepted in the first place, which would allow an attacker to impersonate a valid handler and send fraudulent cross-chain messages, leading to unauthorized actions being taken by the receiving contract. This vulnerability could be exploited to manipulate or disrupt the cross-chain communication process, potentially causing loss of funds or other serious consequences.

## Proof of Concept
The send_cross_chain_msg function is intended to be called by the `from_handler` handlers can be set by onwers, at the moment it is automatically set to msg.sender. meaning anyone who calls this function is the handler. The function does not perform any checks to confirm that the caller is indeed the legitimate handler `from_handler` in this case. As a result, any external account can call this function and set themselves as the `from_handler`, bypassing any intended restrictions.

Consider the following scenario:

A malicious actor calls the `send_cross_chain_msg` function.
They set themselves as the from_handler (which is msg.sender in the function).
The function proceeds to send a cross-chain message without any further verification, potentially leading to unauthorized transactions.
 
Additionally attacker sends a cross-chain message with a different, unauthorized from_handler, which is not on a whitelist or authorized to send messages from the from_chain.
Since the current implementation does not verify the legitimacy of the from_handler, the message is processed as if it were legitimate, potentially leading to unauthorized actions.

## Recommended Mitigation Steps
Implement access control in the `send_cross_chain_msg` function to ensure that only the legitimate from_handler can invoke this function. Add require statement that checks if msg.sender is authorized as the from_handler and verify that the `from_handler` is authorized for the specified `from_chain`.
