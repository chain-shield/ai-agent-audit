# Vulnerability details

## Impact
After initiating a cross-chain ERC20 transaction, the settlement contract on the source chain [emits an event](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/settlement/contracts/ChakraSettlement.sol#L146-L155) upon which authorized validators sign the message and invoke the `ChakraSettlement::receive_cross_chain_msg` on the destination chain to inform the Settlement contract. This function first verifies the signature to ensure it was signed by approved validators and that the minimum required number of validators has signed the message:
```solidity
function receive_cross_chain_msg(
    uint256 txid,
    string memory from_chain,

    uint256 from_handler,
    address to_handler,
    PayloadType payload_type,

    uint8 sign_type, // validators signature type /  multisig or bls sr25519
    bytes calldata signatures // signature array

    // verify signature
>>>     bytes32 message_hash = keccak256(

    require(
        signature_verifier.verify(message_hash, signatures, sign_type),

```
We can see that the signature does **NOT** include the `payload_type`. This is significant because `payload_type` is passed to `ChakraSettlementHandler::receive_cross_chain_msg` to handle the cross-chain message:

If the `receive_cross_chain_msg` returns false, the function marks the cross-chain message status as `Failed`, and the transaction [cannot be settled again](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/settlement/contracts/ChakraSettlement.sol#L199-L202). Currently, the only supported `payload_type` is `PayloadType.ERC20`. If an unsupported payload type is provided, `ChakraSettlementHandler::receive_cross_chain_msg` will return `false`:
```solidity

    bytes calldata payload,

    // --SNIP
    if (payload_type == PayloadType.ERC20) {

    }

```

A malicious user can monitor the mempool and front-run `ChakraSettlement::receive_cross_chain_msg` transactions by providing an **unsupported** `payload_type`, causing the cross-chain message status to be marked as `Failed`. Consequently, the original transaction will not be able to be handled on the destination chain since the cross-chain message status has already been set:
```solidity
// ChakraSettlement::receive_cross_chain_msg
require(receive_cross_txs[txid].status == CrossChainMsgStatus.Unknow, "Invalid transaction status");
```

As a result, malicious actors can effectively block any cross-chain message from being correctly received on the destination chain (Ethereum, Polygon, or any chain with public mempool in which front-run is possible).

## Proof Of Concept
Consider the following scenario:
1. Alice initiates a token transfer from Polygon to Ethereum by calling `ChakraSettlementHandler::cross_chain_erc20_settlement` on Polygon, which emits a `CrossChainLocked` event.
2. Chakra validators detect the `CrossChainLocked` event, sign the message, and initiate a transaction to call `ChakraSettlement::receive_cross_chain_msg` on Ethereum.
3. Bob, a malicious user, monitors Ethereum’s mempool and identifies the `receive_cross_chain_msg transaction`. He copies the function arguments (including the `signatures`) and front-runs the transaction by calling `ChakraSettlement::receive_cross_chain_msg` with a `payload_type` different from `PayloadType.ERC20`.
4. Bob's transaction is executed first, and the signature verification passes because `payload_type` is not included in the verification.

    4.1 The function [interacts with the handler contract](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/settlement/contracts/ChakraSettlement.sol#L216) to process the message, but since the `payload_type` is unsupported, the function [returns `false`](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/ChakraSettlementHandler.sol#L354).
    
    4.2 As a result, the cross-chain message status is [set to `Failed`](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/settlement/contracts/ChakraSettlement.sol#L232).

5. When the validators' transaction attempts to execute, it [will revert](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/settlement/contracts/ChakraSettlement.sol#L199-L202) since the cross-chain message status is already set to Failed.

## Recommended Mitigation Steps
The `payload_type` [is already encoded in the `payload`](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/ChakraSettlementHandler.sol#L193). Therefore, either pass the `payload_type` coded value to `ChakraSettlementHandler::receive_cross_chain_msg` or include `payload_type` in the signature.
