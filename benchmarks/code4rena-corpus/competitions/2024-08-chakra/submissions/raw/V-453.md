# Vulnerability details

## Impact
`created_tx` variable is present in both the `settlement.cairo` and in the `handler_erc20.cairo`. This variable has id that points to the new created transaction. This 2 mappings in the contract must be the same because this is how the protocol intends to use them. The same transaction in the mappings must point to the same id. We can confirm this in the `receive_cross_chain_callback` in `settlement.cairo` because it takes the id and gets the transaction from the `created_tx` and also passes this id as argument so it can be used in the `receive_cross_chain_callback()` in the `handler_erc20.cairo` as well.

The problem is that anyone can call `send_cross_chain_msg` and increment the nonce by 1, so a malicious user can do this and successfully misalign the hashes for the new upcoming transaction. This will result in breaking the whole protocol and make it unuseable because the new transactions will be overriding the previous ones.

## Proof of Concept

This is how the hashes for the ids are generated in `cross_chain_erc20_settlement` in `handler_erc20.cairo`

They are meant to be the same because the 2 mappings are connected. This works fine but the problem comes when the `send_cross_chain_msg()` in `settlement.cairo` is just called by a malicious user once. This will increment the nonce in it by 1 and now everytime a new transaction is created the ids will be different because the hashes will be different and the attacker would have succesfully broken the protocol.

```solidity
>>          self.created_tx.write(cross_chain_msg_id, CreatedCrossChainTx{

```

So now the transaction ids in the `settlement.cairo` will be with 1 nonce bigger than the one in the `handler_erc20.cairo` so the protocol will be overriding the old transactions in the `created_tx` mapping with the new ones in `handler_erc20::receive_cross_chain_callback` which breaks the whole protocol. Also if the mode is set to MintBurn it will try to burn 0 because such transaction does not exist in the `created_tx` in `handler_erc20.cairo`

## Recommended Mitigation Steps
Implement a modifier that makes the `settlement::send_cross_chain_msg` to be callable only by a whitelisted handler
