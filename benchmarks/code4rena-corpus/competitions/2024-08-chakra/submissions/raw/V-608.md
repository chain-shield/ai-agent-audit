# Vulnerability details

## Impact
As `TokenRoles.sol` contract inherits `UUPSUpgradeable.sol`, it must have initializng function that has `initializer` modifier and calls `__UUPSUpgradeable_init()`. If the implementation contract is left not fully initialized, it is possible for any user to gain ownership of the onlyOwner role in the implementation contract for TokenRoles.sol. For example `ChakraToken.sol` inherits `TokenRoles.sol` and in its `initialize` function calls `__TokenRoles_init` and depends on it as it must call `__UUPSUpgradeable_init()`. [ChakraToken::initialize](https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/ChakraToken.sol#L26-#L36)
Once the user has ownership they are able to perform an upgrade of the implementation contract's logic contract and delegate call into any arbitrary contract, allowing them to self-destruct the proxy's implementation contract. Consequently, this will prevent all `TokenRoles.sol` interactions until a new implementation contract is deployed.

In addition it is also missing the `_authorizeUpgrade` function that is required when inheriting `UUPSUpgradeable`

## Proof of Concept
Initial information about this issue was found [here](https://forum.openzeppelin.com/t/security-advisory-initialize-uups-implementation-contracts/15301)

## Tools Used
Manual review.

## Recommended Mitigation Steps
1. Update the __TokenRoles_init function as followed:

```diff
-function __TokenRoles_init(address _owner, address _operator) public {
+function __TokenRoles_init(address _owner, address _operator) public initializer {
        __Ownable_init(_owner);
+       __UUPSUpgradeable_init();
        _grantRole(DEFAULT_ADMIN_ROLE, _owner);
        _grantRole(OPERATOR_ROLE, _operator);
    }
```

2. Add the _authorizeUpgrade function:

```javascript
function _authorizeUpgrade(
    address newImplementation
) internal override onlyOwner {}
```
