# Vulnerability details

## Abstract
The function [ChakraSettlementHandler.cross_chain_erc20_settlement](https://github.com/code-423n4/2024-08-chakra/blob/f61c899c22492bdf5bdcb07cdb62ea9b4cd38825/solidity/handler/contracts/ChakraSettlementHandler.sol#L119) is checking supplied parameters are not zero, this is to satisfy the protocol invariant [Cross-chain ERC20 settlements can only be initiated with a valid amount (greater than 0), a valid recipient address, a valid handler address, and a valid token address.](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/README.md?plain=1#L101)

But this check is not appropriate for Starknet addresses, which are represented as felt252 (field elements) rather than uint256.

In Starknet, a valid address can be any non-zero value in the range of 0 to P-1, where P is the prime number used in the Starknet field (which is a very large number, approximately 2^251 + 17 * 2^192 + 1).


## Impact

Tokens can be sent to invalid destination. This is a high risk because it explicitly break the protocol invariant.

## Proof of Concept

https://secure-contracts.com/not-so-smart-contracts/cairo/L1_to_L2_address_conversion/index.html

## Tools Used

Manual review.

## Recommended Mitigation Steps

Ensure the parameters are less that Starknet prime.
```
assert(to != 0 && to < STARKNET_PRIME, 'Invalid to address');
assert(to_handler != 0 && to_handler < STARKNET_PRIME, 'Invalid to handler address');
assert(to_token != 0 && to_token < STARKNET_PRIME, 'Invalid to token address');
```
