# Vulnerability details



## Summary
There is an issue in the cross-chain messaging system of chakra where unauthorized handlers can potentially execute cross-chain messages. While the system implements signature verification, it lacks an explicit authorization check for the destination handler (`to_handler`), potentially allowing malicious actors to execute unauthorized operations. This vulnerability directly contradicts the security requirements specified in the notion docs [here](https://s3labs.notion.site/Contract-Design-Document-f4aa296f71fb40b1818c0890c40be55c#e0bdd961a2f746b29a851b12fba7c229:~:text=Warning,are%20authorized%20addresses.).

## Vulnerability Details
The `receive_cross_chain_msg` function in the settlement contract verifies the signature of incoming messages but does not explicitly verify if the `to_handler` is authorized on the receiving chain. After signature verification, the function directly calls the `receive_cross_chain_msg` method on the `to_handler` without additional authorization checks.

Relevant code snippet:
```solidity
bool result = ISettlementHandler(to_handler).receive_cross_chain_msg(
    txid,
    from_chain,
    from_address,
    from_handler,
    payload_type,
    payload,
    sign_type,
    signatures
);
```

Importantly, the project documentation explicitly states:
> **Warning**: **from_handler and to_handler must verify whether they are authorized addresses.**

However, the Solidity implementation does not include validation for `to_handler`, creating a significant security gap.

## Impact
- Execution of malicious code through unauthorized handlers
- Potential theft or misdirection of cross-chain assets
- Compromise of the cross-chain messaging system's integrity
- Bypass of intended security models and access controls
- Violation of explicitly stated security requirements in the docs


## Proof of Concept
1. Attacker deploys an unauthorized handler contract on the destination chain.
2. Attacker manages to include this unauthorized handler's address in a validly signed cross-chain message (e.g., by exploiting vulnerabilities in the signing process or through collusion).
3. The message passes signature verification in `receive_cross_chain_msg`.
4. The function calls `receive_cross_chain_msg` on the unauthorized handler, executing potentially malicious code.
5. This occurs despite the docs explicitly requiring validation of both handlers.

## Recommendation
Implement an explicit authorization check for the `to_handler` after signature verification as done in cairo side.
