# Vulnerability details

## Impact

Invalid `from_address` is emitted in the `settlement::receive_cross_chain_callback::CrossChainResult` event, which could lead to unwanted behavior when picked up by the protocol validators, leading to potential DoS of user actions.

## Proof of Concept

Proper event emission is crucial for the Chakra protocol, as it is the main point that allows validators to properly invoke the correct logic on the corresponding chain. However, it seems that the `settlement::receive_cross_chain_callback(...)` incorrectly sets the `from_address` in the emitted `CrossChainResult` event to `get_tx_info().unbox().account_contract_address`, which in this case would be the smart contract that invoked the validator to execute the `receive_cross_chain_callback` function on the L2 chain. There are no EOA accounts in Starknet as every account is a [smart contract](https://github.com/OpenZeppelin/cairo-contracts/blob/main/packages/presets/src/account.cairo), and `get_tx_info().unbox().account_contract_address` utilizes the address of the contract that [signed the incoming transaction](https://book.starknet.io/ch02-14-security-considerations.html):

> In Solidity, `tx.origin` is a global variable that stores the address of the transaction initiator, while `msg.sender` stores the address of the transaction caller. In Cairo, we have the `account_contract_address` global variable and `get_caller_address` function, which serve the same purpose. Using `account_contract_address` (the equivalent of `tx.origin`) for authentication in your smart contract functions can lead to phishing attacks. Attackers can create custom smart contracts and trick users into placing them as intermediaries in a transaction call, effectively impersonating the contract owner.


The above has been properly applied for the `from_address` in the `settlement::send_cross_chain_msg(...)` function, as in its case `get_tx_info().unbox().account_contract_address` will be the smart contract that signed the transaction, which invoked `settlement::send_cross_chain_msg(...)`. This transaction is the `handler_erc20::cross_chain_erc20_settlement(...)`, which in turn is signed by the user (a.k.a `from_address`).

This is not the case for the `settlement::receive_cross_chain_callback(...)` invocation, as this function is called by the validator. The transaction that will invoke the validator will not be signed by the initial user as it will probably executed by a keeper or other automated tool. Because of this, the event emitted will incorrectly indicate that the `from_user` is the previously mentioned automated tool.

## Recommended Mitigation Steps

Adopt the same approach as with the Solidity code, where the `from_address` is saved in the newly created cross-chain transaction in the `send_cross_chain_msg` method:

```solidity
create_cross_txs[txid] = CreatedCrossChainTx(
            txid,
            contract_chain_name,
            to_chain,
@>          from_address, // from address is saved when creating the 
            from_handler,
            to_handler,
            payload,
            CrossChainMsgStatus.Pending
        );
```

Then it can be properly set in the emitted `CrossChainResult` event:

```solidity
function emitCrossChainResult(uint256 txid) internal {
        emit CrossChainResult(
            txid,
            create_cross_txs[txid].from_chain,
            create_cross_txs[txid].to_chain,
@>          create_cross_txs[txid].from_address, // proper from_address
            create_cross_txs[txid].from_handler,
            create_cross_txs[txid].to_handler,
            create_cross_txs[txid].status
        );
    }
```
