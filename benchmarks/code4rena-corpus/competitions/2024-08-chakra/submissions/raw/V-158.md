# Vulnerability details

## Description

The `ChakraSettlement` contract is responsible for handling cross-chain transactions. It includes functions to send and receive cross-chain messages, ensuring the integrity and proper processing of these transactions. One critical aspect of this process is the generation of a unique transaction ID (`txid`) for each cross-chain message. The `txid` is generated using the [`send_cross_chain_msg()` function](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/settlement.cairo#L284-L314), which relies on several parameters, including a nonce specific to the sender's address.

The current implementation of [`send_cross_chain_msg()`](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/settlement.cairo#L284-L314) generates the `txid` as follows:

```js
uint256 txid = uint256(
    keccak256(
        abi.encodePacked(
            contract_chain_name, // from chain
            to_chain,
            from_address, // msg.sender address
            from_handler, // settlement handler address
            to_handler,
            nonce_manager[from_address]
        )
    )
);
```

This approach has two significant issues:
1. The `nonce_manager` is specific to the `from_address`, ensuring uniqueness only per address, not globally.
2. The `txid` generation does not include a unique identifier for the chain, which can lead to collisions if the same `contract_chain_name` is used across different chains.

### Detailed Description

The `send_cross_chain_msg()` function is designed to create a new cross-chain transaction and emit an event with the transaction details. The `txid` is a crucial part of this process, as it uniquely identifies each transaction. However, the current method of generating the `txid` can result in collisions under certain conditions.

Consider the following scenario:
1. User A on Chain X sends a cross-chain message to Chain Y, generating `txid1`.
2. User B on Chain Z (a different chain) sends a cross-chain message to Chain Y, using the same `to_handler` and with the same `nonce_manager` value.
3. If User B happens to have the same address as User A (possible across different chains), and if Chain Z happens to have the same `contract_chain_name` as Chain X, this will generate the exact same `txid1`.

This scenario can lead to:
- Confusion in transaction processing
- Potential overwriting of transaction data
- Exploitation by malicious actors

### Example

1. **User A on Chain X:**
   ```js
   string memory contract_chain_name = "ChainX";
   string memory to_chain = "ChainY";
   address from_address = 0x123...; // User A's address
   address from_handler = 0xabc...; // Handler address
   uint256 to_handler = 0xdef...; // Destination handler
   uint256 nonce = 1; // Nonce for User A

   uint256 txid1 = uint256(
       keccak256(
           abi.encodePacked(
               contract_chain_name,
               to_chain,
               from_address,
               from_handler,
               to_handler,
               nonce
           )
       )
   );
   ```

2. **User B on Chain Z:**
   ```js
   string memory contract_chain_name = "ChainX"; // Same as Chain X
   string memory to_chain = "ChainY";
   address from_address = 0x123...; // Same address as User A
   address from_handler = 0xabc...; // Handler address
   uint256 to_handler = 0xdef...; // Destination handler
   uint256 nonce = 1; // Same nonce as User A

   uint256 txid2 = uint256(
       keccak256(
           abi.encodePacked(
               contract_chain_name,
               to_chain,
               from_address,
               from_handler,
               to_handler,
               nonce
           )
       )
   );
   ```

In this scenario, `txid1` and `txid2` will be identical, leading to a collision.

## Impact
Cross-chain transaction conflicts, incorrect transaction processing, potential loss of funds or unintended token transfers, and compromised integrity of the cross-chain messaging system.

## Proof of Concept
1. User A on Chain X sends a cross-chain message to Chain Y, generating `txid1`.
2. User B on Chain Z (a different chain) sends a cross-chain message to Chain Y, using the same `to_handler` and with the same `nonce_manager` value.
3. If User B has the same address as User A and Chain Z has the same `contract_chain_name` as Chain X, this will generate the exact same `txid1`.

## Tools Used
Manual review

## Recommended Mitigation Steps
To ensure global uniqueness for each `txid`, introduce a `global_nonce` and include `contract_chain_id` in the `txid` generation.
