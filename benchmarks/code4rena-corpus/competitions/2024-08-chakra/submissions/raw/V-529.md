# Vulnerability details

## Vulnerability description
The `receive_cross_chain_callback` settlement function is intended to only be called by validators, however it is open for everyone but it must assert that the signatures provided match with the message provided in the function:
```
    function receive_cross_chain_callback(
        uint256 txid,
        string memory from_chain,
        uint256 from_handler,
        address to_handler,
        CrossChainMsgStatus status,
        uint8 sign_type,
        bytes calldata signatures
    ) external {
        verifySignature(
            txid,
            from_handler,
            to_handler,
            status,
            sign_type,
            signatures
        );
        processCrossChainCallback(
            txid,
            from_chain,
            from_handler,
            to_handler,
            status,
            sign_type,
            signatures
        );
        emitCrossChainResult(txid);
    }
```
Someone can think it is save because even though someone frontruns the transaction and tries to change any parameter it will fail because the message with the parameters has been signed by offchain validators and it must comply that the parameters match. However not all parameters are hashed in the signed message. That is really important because someone can change it and the signatures will still pass.

In this case, the particular parameter that is not signed in the message is the `from_chain` parameter.
```
    function verifySignature(
        uint256 txid,
        uint256 from_handler,
        address to_handler,
        CrossChainMsgStatus status,
        uint8 sign_type,
        bytes calldata signatures
    ) internal view {
        bytes32 message_hash = keccak256(
            abi.encodePacked(txid, from_handler, to_handler, status)
        );

        require(
            signature_verifier.verify(message_hash, signatures, sign_type),
            "Invalid signature"
        );
    }
```

That means that a message that has been signed with the other data can be provided to the function with any arbitrary `from_chain` and it will pass the signature check.

## Proof of concept
1. A user initiates an ERC20 MintBurn type
2. Tokens are minted in the destination chain
3. The validator submits the data in the mempool to call the callback function
4. A malicious user monitors it and frontruns the function call providing the exact same parameters but changing the `from_chain` parameter to any arbitrary string
5. The settlement calls the handler and it returns false because it will not have whitelisted the handler address on this other invented chain string.
```
        if (is_valid_handler(from_chain, from_handler) == false) {
            return false;
        }
```
6. The end result will be the cross transaction marked as failed when it has minted the tokens in the destination chain and the source chain not being able to burn the tokens.
7. The validators call will fail because the cross transaction has a different state of `PENDING`.
```
        require(
            create_cross_txs[txid].status == CrossChainMsgStatus.Pending,
            "Invalid transaction status"
        );
```



## Impact
The impact of this issue is high because it can be performed by anyone on any message and it prevents executing the logic from the callback function. The current implementation of the callback function in the handler only involves burning tokens but in the future can be more logic that will be skipped. Also the `create_cross_txs` transaction will be marked as failed when in reality the tokens where minted succesfully on the destination chain.

## Recommended Mitigation Steps
Add the `from_chain` parameter into the message hashing.
```diff
    function receive_cross_chain_callback(
        uint256 txid,
        string memory from_chain,
        uint256 from_handler,
        address to_handler,
        CrossChainMsgStatus status,
        uint8 sign_type,
        bytes calldata signatures
    ) external {
        verifySignature(
            txid,
++          from_chain,
            from_handler,
            to_handler,
            status,
            sign_type,
            signatures
        );
        processCrossChainCallback(
            txid,
            from_chain,
            from_handler,
            to_handler,
            status,
            sign_type,
            signatures
        );
        emitCrossChainResult(txid);
    }

    function verifySignature(
        uint256 txid,
++      string calldata from_chain,
        uint256 from_handler,
        address to_handler,
        CrossChainMsgStatus status,
        uint8 sign_type,
        bytes calldata signatures
    ) internal view {
        bytes32 message_hash = keccak256(
--          abi.encodePacked(txid, from_handler, to_handler, status)
++          abi.encodePacked(txid, from_chain, from_handler, to_handler, status)
        );

        require(
            signature_verifier.verify(message_hash, signatures, sign_type),
            "Invalid signature"
        );
    }
```
