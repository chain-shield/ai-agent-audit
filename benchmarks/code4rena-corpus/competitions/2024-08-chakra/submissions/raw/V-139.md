# Vulnerability details

## Impact
The contract should check whether the handler receiving a cross-chain message is on the whitelist for the source chain. This is a main invariant of the protocol stated in the Readme. 

However, the check was implemented incorrectly/not fully.

This leads to potentially malicious handler being used or handlers that were already removed from the whitelist/not supported.
## Proof of Concept
The check is partially implemented in the `handler_erc20` contract, `receive_cross_chain_msg()`:
```
            assert(self.support_handler.read((from_chain, from_handler)) && 
                    self.support_handler.read((to_chain, contract_address_to_u256(to_handler))), 'not support handler');
```

However, the current check:
- It only verifies that the `to_handler` is valid on the destination chain (to_chain).
- It only verifies that the `from_handler` is valid on the source chain(from_chain)

It does not verify if the to_handler is valid on the source chain (from_chain). Which is what the invariant states:
- The handler receiving a cross-chain message must be on the whitelist for the source chain.

## Tools Used
Manual review
## Recommended Mitigation Steps
Add a check that verifies that the handler receiving a cross-chain message must be on the whitelist for the source chain. Something like that:
```
assert(self.support_handler.read((from_chain, contract_address_to_u256(to_handler))), 'not support handler');
```
