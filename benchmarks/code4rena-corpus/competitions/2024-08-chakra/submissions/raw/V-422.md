# Vulnerability details

## Impact
The `SettlementSignatureVerifier` contract's `verifyECDSA` function fails to correctly verify signatures due to improper handling of Ethereum's signed message format causing any signature to be rejected, even if it's valid, effectively breaking the contract's core functionality.

The impact of this issue is severe:
* All legitimate signature verifications will fail, rendering the contract unusable for its intended purpose.
* Any system relying on this contract for signature verification will fail to verify signatures.

## Proof of Concept
The vulnerability exists in the `verifyECDSA` function:

```solidity
function verifyECDSA(
    bytes32 msgHash,
    bytes calldata signatures
) internal view returns (bool) {
    require(
        signatures.length % 65 == 0,
        "Signature length must be a multiple of 65"
    );

    uint256 len = signatures.length;
    uint256 m = 0;
    for (uint256 i = 0; i < len; i += 65) {
        bytes memory sig = signatures[i:i + 65];
        if (
            validators[msgHash.recover(sig)] && ++m >= required_validators
        ) {
            return true;
        }
    }

    return false;
}
```

The issue arises because the function uses msgHash.recover(sig) directly, which expects a raw hash. However, standard Ethereum libraries and wallets (including ethers.js used in the test suite) prepend the Ethereum Signed Message prefix when signing messages.

To demonstrate:

1. In the test file, signatures are created using:
```solidity
typescriptCopyconst signature = await validators[i].signMessage(hre.ethers.getBytes(messageHash));
```
2. The `signMessage` function in ethers.js automatically prepends the Ethereum Signed Message prefix.
3. When these signatures are verified in the contract, the `recover` function fails to match them with the correct addresses because it's not accounting for this prefix.

NOTE: Not prepending the Ethereum Signed Message prefix also exposes the contract to potential signature malleability and replay attacks, as described in EIP-191.

## Recommended Mitigation Steps

```solidity
function verifyECDSA(
    bytes32 msgHash,
    bytes calldata signatures
) internal view returns (bool) {
    require(
        signatures.length % 65 == 0,
        "Signature length must be a multiple of 65"
    );

    // FIX: Convert the message hash to an Ethereum Signed Message
    bytes32 ethSignedMessageHash = MessageHashUtils.toEthSignedMessageHash(msgHash);

    uint256 len = signatures.length;
    uint256 m = 0;
    for (uint256 i = 0; i < len; i += 65) {
        bytes memory sig = signatures[i:i + 65];
        address recoveredAddress = ethSignedMessageHash.recover(sig);
        if (validators[recoveredAddress] && ++m >= required_validators) {
            return true;
        }
    }

    return false;
}
```

These changes ensure that the contract correctly verifies signatures created by standard Ethereum libraries and wallets, aligning with expected Ethereum signing practices and resolving the vulnerability.
