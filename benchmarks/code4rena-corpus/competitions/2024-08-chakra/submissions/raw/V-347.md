# Vulnerability details

## Impact
It is possible to perform a replay attack on multiple chains (on Polygon for example) since there is no check if the settlement contract is on the correct chain. 

`ChakraSettlement.sol` contract have two parameters `chain_id` and `contract_chain_name` that will be set when the contract is initialized. On different chains, these variables will be different. 

When the user successfully executes one cross-chain transaction (e.g., on Ethereum), anyone can call the `receive_cross_chain_msg` function on any other chain with the same parameters. This code block inside the `receive_cross_chain_msg` function checks the `msg.hash` and the signatures

```
{
            // verify signature
            bytes32 message_hash = keccak256(
                abi.encodePacked(
                    txid,
                    from_chain,
                    from_address,
                    from_handler,
                    to_handler,
                    keccak256(payload)
                )
            );

            require(
                signature_verifier.verify(message_hash, signatures, sign_type),
                "Invalid signature"
            );

            require(
                receive_cross_txs[txid].status == CrossChainMsgStatus.Unknow,
                "Invalid transaction status"
            );
        }
```
However, even though `to_chain` is encoded in the `tx.id` field, this check only checks the integrity of the message, that is if the message has been changed or not. It does not verify if the `chain_id` or `contract_chain_name` of this specific `ChakraSettlement` contract is equal to `to_chain` provided in the transaction. The latest `require` statement will also pass (from the code block above) since the transaction with this `txid` most likely does not exist on the other chain and therefore will have its status set to `Unknow` per default. 

This enables anyone to use the signatures and replay the message on all other chains. 

P.S. It is possible to have the same address on multiple chains, so this is also not a protection. 

## Proof of Concept
Scenario from the above described in steps.

1. Alice wants to lock 20 WETH on Ethereum and unlock them on BSC
2. The transaction goes through smoothly and Alice gets her tokens
3. Alice can take all input parameters from the successfull call to `receive_cross_chain_msg` and call `receive_cross_chain_msg` again but this time on Polygon
4. As there is no check if the Settlement contract is correct and there is no check if the `to_chain` is the right one, Alice gets her tokens minted on Polygon as well.

## Tools Used
VS Code, Manual Review

## Recommended Mitigation Steps
Make sure to pass the `to_chain` to the `receive_cross_chain_msg` function as well and add following check 

`require(to_chain == contract_chain_name), "Invalid Chain");`
