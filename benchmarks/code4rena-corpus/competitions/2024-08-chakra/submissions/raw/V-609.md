# Vulnerability details

## Impact

The `ChakraSettlementHandler` contract misses to unlock tokens back to users when sending a message fails in locking modes (modes that locks tokens on the source-chain initially. i.e, `MintBurn`, `LockUnlock`, and `LockMint`). This critical vulnerability leads to permanent loss of user funds, as tokens remain locked in the contract without a mechanism to unlock them back.

*Note that the same issue persists in the Cairo code.*


## Vulnerability details

The current implementation introduces 4 settlement modes:

- `MintBurn`: Tokens are burned on the source chain and minted on the destination chain. This mode is used when you want to permanently move tokens from one chain to another.
- `LockUnlock`: Tokens are locked on the source chain and unlocked on the destination chain. This mode is used when you want to temporarily move tokens from one chain to another.
- `LockMint`: Tokens are locked on the source chain and minted on the destination chain. This mode is used when you want to move tokens from one chain to another and increase the supply on the destination chain.
- `BurnUnlock`: Tokens are burned on the source chain and unlocked on the destination chain. This mode is used when you want to move tokens from one chain to another and decrease the supply on the source chain.

Among the four modes, three of them initially lock tokens in to initiate sending a message.

In the `receive_cross_chain_callback()` function, there's no mechanism to unlock tokens when sending tokens fails:

```js
function receive_cross_chain_callback(
    uint256 txid,
    string memory from_chain,
    uint256 from_handler,
    CrossChainMsgStatus status,
    uint8 /* sign_type */,
    bytes calldata /* signatures */
) external onlySettlement returns (bool) {
    //  from_handler need in whitelist
    if (is_valid_handler(from_chain, from_handler) == false) {
        return false;
    }

    require(
        create_cross_txs[txid].status == CrossChainTxStatus.Pending,
        "invalid CrossChainTxStatus"
    );

    if (status == CrossChainMsgStatus.Success) {
        if (mode == SettlementMode.MintBurn) {
            _erc20_burn(address(this), create_cross_txs[txid].amount);
        }
        create_cross_txs[txid].status = CrossChainTxStatus.Settled;
    }

    if (status == CrossChainMsgStatus.Failed) {
        create_cross_txs[txid].status = CrossChainTxStatus.Failed;
        //@audit should unlock tokens back on failure
    }

    return true;
}
```

When `status == CrossChainMsgStatus.Failed` for any reason, for instance due to insufficient validator signatures, the function only updates the transaction status to Failed without unlocking the tokens back to the user.

## Proof of Concept

Here's a scenario to illustrate:

- Alice initiates a cross-chain transfer of 1000 CHKR tokens using the `MintBurn` mode (or any of the other two modes).
- The `cross_chain_erc20_settlement` function is called, locking 1000 CHKR tokens from Alice's account in the contract.
- The cross-chain message fails to be processed on the destination chain due to insufficient validator signatures (or any other reason).
- The `receive_cross_chain_callback` function is called with `CrossChainMsgStatus.Failed`.
- The function updates the transaction status to Failed but doesn't unlock Alice's 1000 CHKR tokens.
- Alice's 1000 CHKR tokens remain locked in the contract indefinitely.
  Alice has no way to recover her tokens, resulting in a permanent loss of 1000 CHKR.
