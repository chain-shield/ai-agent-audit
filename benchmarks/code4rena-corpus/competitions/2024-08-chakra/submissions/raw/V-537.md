# Vulnerability details

## Vulnerability explanation
There are 2 instances where tx.origin is used in Cairo settlement contract.
1. In the `send_cross_chain_msg` function it is used to determine who the `from_address` is.
```
        fn send_cross_chain_msg(
            ref self: ContractState, to_chain: felt252, to_handler: u256, payload_type :u8,payload: Array<u8>,
        ) -> felt252 {
            let from_handler = get_caller_address();
            let from_chain = self.chain_name.read();
            let cross_chain_settlement_id = LegacyHash::hash(get_tx_info().unbox().transaction_hash, self.tx_count.read());

            self.created_tx.write(cross_chain_settlement_id, CreatedTx{
                tx_id:cross_chain_settlement_id,
                tx_status: CrossChainMsgStatus::PENDING,
                from_chain: from_chain,
                to_chain: to_chain,
                from_handler: from_handler,
                to_handler: to_handler
            });
            
            self
                .emit(
                    CrossChainMsg {
                        cross_chain_settlement_id: cross_chain_settlement_id,
                        from_address: get_tx_info().unbox().account_contract_address,       // @audit tx.origin used here
                        from_chain: from_chain,
                        to_chain: to_chain,
                        from_handler: from_handler,
                        to_handler: to_handler,
                        payload_type: payload_type,
                        payload: payload
                    }
                );
            self.tx_count.write(self.tx_count.read()+1);
            return cross_chain_settlement_id;
        }
```
This can be a design choice but it can prevent aggregators to work with Chakra protocol. Imagine that ther is a protocol that is an aggregator which essentially gather users funds and bridge it to an other chain where there is an other aggregator which will distribute the tokens to receivers. The `from_address` here should be the aggregator contract itself, but since it uses tx.origin it will be the user who initiated the transaction. In this case, I would use the caller address so that in the example would be the aggregator contract, just as Solidity implementation does.

2. There is an other instance of the tx.origin which is confirmed to be wrong, whis one is in the `receive_cross_chain_callback`.
```
        fn receive_cross_chain_callback(
            ref self: ContractState,
            cross_chain_msg_id: felt252,
            from_chain: felt252,
            to_chain: felt252,
            from_handler: u256,
            to_handler: ContractAddress,
            cross_chain_msg_status: u8,
            sign_type: u8,
            signatures: Array<(felt252, felt252, bool)>,
        ) -> bool {
            ...

            self.emit(CrossChainResult {
                cross_chain_settlement_id: cross_chain_msg_id,
                // @audit-issue from_address points to the offchain validator when it should be the initial from_address
                from_address: get_tx_info().unbox().account_contract_address,
                from_chain: to_chain,
                from_handler: to_handler,
                to_chain: from_chain,
                to_handler: from_handler,
                cross_chain_msg_status: state,
            });
            return true;
        }
```
The `from_address` in this case is also determined by tx.origin. However, in this scenario it is completely wrong, because the `receive_cross_chain_callback` is intended to be called by validators, so the tx.origin will be the address of the validator calling the function. Actually there is also the possibility for someone to frontrun the function call from the validator, and in this case the `from_address` will be from the user that frontrun the function call.

## Impact
Wrong data will be emitted in the events that are really important for the protocol integrity because of the bridging component.

## Tools Used
Manual review

## Recommended Mitigation Steps
In the first instance I would use the address of the caller instead of the tx.origin and in the second one the address of the `from_address` field of the message.
