# Vulnerability details

## Summary

A vulnerability is present in the `ChakraSettlementHandler` contract, specifically in the `_safe_transfer()` function. This function, crucial for unlocking and transferring ERC20 tokens, uses the `transfer()` method, which is limited to 2300 gas. This limitation can lead to failed transfers under certain conditions, potentially resulting in tokens becoming permanently locked in the contract. The severity of this issue is significantly amplified by the protocol's planned deployment on multiple chains, including **zkSync**, where the use of `transfer()` can lead to severe consequences.

## Vulnerability Details

The vulnerability is located in the `_safe_transfer()` function:

```solidity
function _safe_transfer(address to, uint256 amount) internal {
    require(
        IERC20(token).balanceOf(address(this)) >= amount,
        "Insufficient balance"
    );

    // transfer tokens
    IERC20(token).transfer(to, amount); // 2300 gas @audit
}
```

Problems it can create:
1. The function uses the ERC20 `transfer()` method, which forwards only 2300 gas to the recipient.
2. This gas limitation is insufficient for contracts with complex receive functions or those behind proxy contracts.
3. The use of `transfer()` is particularly problematic on zkSync, where it can lead to funds being permanently stuck.

This function is used in the critical `_erc20_unlock()` function, which is called during cross-chain message processing:

```solidity
function _erc20_unlock(address to, uint256 amount) internal {
    _safe_transfer(to, amount);
}
```

## Impact

The impact of this vulnerability is severe and multi-faceted:

1. **Token Locking**: Tokens may become permanently locked in the contract if sent to addresses requiring more than 2300 gas for receipt.

2. **Failed Cross-Chain Transfers**: Cross-chain token transfers to certain smart contracts may fail silently, disrupting the core functionality of the system.

3. **User Fund Loss**: Users may lose access to their funds if they can't be transferred to their desired addresses.

4. **Reduced Interoperability**: The contract's ability to interact with other smart contracts is significantly limited.

5. **zkSync-Specific Issues**: On zkSync, the use of `transfer()` can lead to catastrophic outcomes:
   - Even transfers to EOAs may fail due to insufficient gas.
   - There's a precedent of [921 ETH being stuck on zkSync Era](https://medium.com/coinmonks/gemstoneido-contract-stuck-with-921-eth-an-analysis-of-why-transfer-does-not-work-on-zksync-era-d5a01807227d) due to similar issues.
   - zkSync explicitly recommends against using `transfer()` for sending ETH, and this caution extends to token transfers as well.

## Recommendations

Implement OpenZeppelin's `SafeERC20` library, which provides a `safeTransfer()` function. This function uses a low-level `call` with proper gas forwarding and return value checking.

Be acutely aware of gas limit variations across different blockchain networks, especially zkSync, and adjust the implementation accordingly.

For zkSync deployment, follow their best practices by using `call` instead of `transfer` or `send`. This applies to both ETH and token transfers.
