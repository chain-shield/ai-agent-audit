# Vulnerability details

## Summary

The Chakra protocol's cross-chain messaging system is vulnerable to replay attacks across different EVM-compatible chains due to insufficient chain-specific verification in the message processing mechanism.

Attacker can basically replay users messages that havent yet been executed on other chains yet. ;

## Description

The `ChakraSettlement` contract, deployed on multiple EVM-compatible chains (e.g., Ethereum, Arbitrum, BSC), uses a nonce-based system for transaction uniqueness `-nonce_manager[from_address] += 1`. However, the current implementation does not adequately differentiate between messages originating from different EVM chains.

In `ChakraSettlement.sol:111-156`, the cross-chain message creation process uses:

```solidity
uint256 txid = uint256(
    keccak256(
        abi.encodePacked(
            contract_chain_name,
            to_chain,
            from_address,
            from_handler,
            to_handler,
            nonce_manager[from_address]
        )
    )
);
```

While this includes the `contract_chain_name`, the receiving end `(settlement.cairo:325-383)` only checks the `to_chain`:

```cairo
assert(to_chain == self.chain_name.read(), 'error to_chain');
```
This asymmetry in chain verification creates a replay attack vulnerability.


## Impact

An attacker could Capture a legitimate transaction from one EVM chain (e.g., Ethereum). Replay this transaction on another EVM chain where the protocol is deployed (e.g., Arbitrum).
If the nonce is crafted to match, the transaction would be accepted and processed on the unintended chain.

This could lead to:

1. Unauthorized asset transfers
2. Duplicate execution of cross-chain actions
3. Inconsistent state across the protocol's multi-chain deployment

## Illustration

```solidity
Chain A (Ethereum)         Chain B (Arbitrum)
+------------------+       +------------------+
| ChakraSettlement |       | ChakraSettlement |
+------------------+       +------------------+
         |                           |
         | Tx(nonce=5, from=ETH)     |
         |-------------------------->|
         |                           |
         |  Tx'(nonce=5, from=ETH)|
         |<--------------------------|
         |                           |
    [Processed]                 [Also Processed]
```


## Recommendation

- Incorporate a chain identifier in the message hash that is verified on the receiving end.
- Implement strict checking of both from_chain and to_chain in the receiving cairo contract.
- Use a unique identifier for each chain deployment that is included in the transaction signature.
- Implement a chain-specific nonce system to prevent nonce reuse across different chains.
Consider using a more robust cross-chain identification system, such as including block hashes or timestamps in the verification process.
