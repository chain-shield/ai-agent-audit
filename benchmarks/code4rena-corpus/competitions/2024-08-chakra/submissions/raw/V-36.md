# Vulnerability details

## Impact
Detailed description of the impact of this finding.

ChakraSettlementUpgradeTest has Hash Collisions With Multiple Variable Length Arguments in send_cross_chain_msg function

The send_cross_chain_msg function in the ChakraSettlementUpgradeTest contract uses abi.encodePacked to concatenate multiple variable-length arguments before hashing them to generate a unique txid. This approach can lead to hash collisions where different input combinations produce the same hash.

Using Foundry, we can demonstrate how a hash collision can occur using abi.encodePacked:
```sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "forge-std/Test.sol";
import "../contracts/ChakraSettlementUpgradeTest.sol";

contract ChakraSettlementTest is Test {
    ChakraSettlementUpgradeTest chakraSettlement;

    function setUp() public {
        // Deploy the contract
        chakraSettlement = new ChakraSettlementUpgradeTest();

        // Initialize the contract with example values
        string memory chainName = "ChainA";
        uint256 chainId = 1;
        address owner = address(this);
        address;
        managers[0] = owner;
        uint256 requiredValidators = 1;
        address verifyContract = address(0x123456); // example address

        chakraSettlement.initialize(chainName, chainId, owner, managers, requiredValidators, verifyContract);
    }

    function testHashCollisionInSendCrossChainMsg() public {
        // First transaction that could cause a collision
        string memory toChain1 = "ChainB";
        address fromAddress1 = address(0xdeadbeef);
        uint256 toHandler1 = 0x1;
        ChakraSettlementUpgradeTest.PayloadType payloadType1 = ChakraSettlementUpgradeTest.PayloadType.Raw;
        bytes memory payload1 = abi.encodePacked("def");

        // Second transaction that could cause a collision
        string memory toChain2 = "ChainB";
        address fromAddress2 = address(0xdeadbee);
        uint256 toHandler2 = 0x1;
        ChakraSettlementUpgradeTest.PayloadType payloadType2 = ChakraSettlementUpgradeTest.PayloadType.Raw;
        bytes memory payload2 = abi.encodePacked("cdef");

        // Call send_cross_chain_msg for both transactions
        chakraSettlement.send_cross_chain_msg(toChain1, fromAddress1, toHandler1, payloadType1, payload1);
        chakraSettlement.send_cross_chain_msg(toChain2, fromAddress2, toHandler2, payloadType2, payload2);

        // Retrieve the txid for both transactions
        uint256 txid1 = uint256(
            keccak256(
                abi.encodePacked(
                    chakraSettlement.contract_chain_name(),
                    toChain1,
                    fromAddress1,
                    address(this),
                    toHandler1,
                    chakraSettlement.view_nonce(fromAddress1),
                    payloadType1,
                    payload1
                )
            )
        );

        uint256 txid2 = uint256(
            keccak256(
                abi.encodePacked(
                    chakraSettlement.contract_chain_name(),
                    toChain2,
                    fromAddress2,
                    address(this),
                    toHandler2,
                    chakraSettlement.view_nonce(fromAddress2),
                    payloadType2,
                    payload2
                )
            )
        );

        // Check if both txids are the same (indicating a collision)
        assertEq(txid1, txid2, "Hash collision did not occur");
    }
}
```

Explanation:

SetUp Function:
The setUp() function initializes the ChakraSettlementUpgradeTest contract with sample data, setting the chain name, chain ID, owner, and other required parameters.

Test Function:
testHashCollisionInSendCrossChainMsg() simulates two different cross-chain messages that could potentially produce the same txid.

The test compares the transaction IDs (txid1 and txid2) generated by send_cross_chain_msg for these two transactions.

If both transactions produce the same txid, the test will pass, indicating a hash collision (which is undesirable in production).

When running the test, it would assert true, demonstrating that abi.encodePacked can lead to hash collisions when concatenating variable-length arguments.

## Recommended Mitigation Steps
Use abi.encode Instead of abi.encodePacked:
Replace abi.encodePacked with abi.encode in the send_cross_chain_msg function. This ensures that each argument is padded and its boundaries are preserved, reducing the risk of collision.
```sol
uint256 txid = uint256(
    keccak256(
        abi.encode(
            contract_chain_name,
            to_chain,
            from_address,
            from_handler,
            to_handler,
            nonce_manager[from_address],
            payload_type,
            payload
        )
    )
);
```
Whenever possible, use fixed-length types (e.g., address, uint256) instead of variable-length types like string or bytes. This reduces ambiguity and the risk of collisions.

If abi.encodePacked must be used, consider inserting unique delimiters between arguments to clearly distinguish their boundaries.
```sol
uint256 txid = uint256(
    keccak256(
        abi.encodePacked(
            contract_chain_name, "|",
            to_chain, "-",
            from_address, "&",
            from_handler, "+",
            to_handler, "\",
            nonce_manager[from_address], "/",
            payload_type, ";",
            payload
        )
    )
);
```
