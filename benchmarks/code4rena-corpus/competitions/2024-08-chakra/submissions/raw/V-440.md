# Vulnerability details

## Impact

In the current implementation of the `settlement` contract, `message_hash` is being reassigned inside of `receive_cross_chain_msg()` function. This is an unexpected behavior as eventually incorrect value will be verified.

## Proof of Concept

Take a look at `receive_cross_chain_msg()` functionality:

https://github.com/code-423n4/2024-08-chakra/blob/main/cairo/handler/src/settlement.cairo#L340-350
```
 let mut message_hash: felt252 = LegacyHash::hash(from_chain, (cross_chain_msg_id, to_chain, from_handler, to_handler));
            let payload_span = payload.span();
            let mut i = 0;
            loop {
                if i > payload_span.len()-1{
                    break;
                }
                message_hash = LegacyHash::hash(message_hash, * payload_span.at(i));
                i += 1;
            };
            self.check_chakra_signatures(message_hash, signatures);

```

First, `message_hash` is generated from the parameters that are submitted from the Chakra Network. Then the `message_hash` is regenerated using `message_hash` and the value from the payload (during iteration). Eventually, it leads to a situation where `message_hash` has the hashed value of `message_hash` and the last member of the payload array. This is an unexpected behavior as the signatures should be verified against this message hash:

https://github.com/code-423n4/2024-08-chakra/blob/main/cairo/handler/src/settlement.cairo#L340
```
let mut message_hash: felt252 = LegacyHash::hash(from_chain, (cross_chain_msg_id, to_chain, from_handler, to_handler));
```

`check_chakra_signatures` may revert as the initial message hash that was signed by the network has different parameters.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Use proper values when verifying `message_hash` and signatures.
