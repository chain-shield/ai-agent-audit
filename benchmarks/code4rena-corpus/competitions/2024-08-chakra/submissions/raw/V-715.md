## Vulnerability details
The `check_chakra_signatures` function is vulnerable to a flaw where duplicate signatures are not checked. The function counts each occurrence of a valid signature without checking if it is unique. This makes it possible to submit the array of the same signatures, thereby artificially increasing the count of `valid validators`. This behavior undermines the requirement for signatures from multiple distinct validators, as it allows validation with fewer unique validators than intended.
```
fn check_chakra_signatures(
            self: @ContractState, message_hash: felt252, signatures: Array<(felt252, felt252, bool)>
        ){
            let mut pass_count = 0;
            let mut i = 0;
            loop {
                if i > signatures.len()-1{
                    break;
                }
                let (r,s,y) = * signatures.at(i);
                let pub_key: felt252 = recover_public_key(message_hash,r,s,y).unwrap();
                if self.chakra_validators_pubkey.read(pub_key) > 0{
                    pass_count += 1;
                }
                i += 1;
            };
            assert(pass_count >= self.required_validators_num.read(), 'Not enough validate signatures');
        }
    }
```

## Proof of Concept
- Assume the contract requires three validator signatures (`self.required_validators_num = 3`).
- The array of the 3 same valid signatures from a single validator is submitted to the `check_chakra_signatures`.
- The function incorrectly increments `pass_count` for each occurrence of the same signature, leading to a successful pass even though only one validator's signature is used.

This behavior contradicts the protocol's intent of requiring a **minimum number of validators** for message validation, making it possible to bypass this requirement and approve messages with fewer validators than intended.
## Impact
This vulnerability makes it possible to bypass the **minimum number of different validator signatures** required to validate a message. By submitting duplicate signatures, it is possible to maliciously approve transactions or messages that should not pass without the necessary **number of different validators**. This undermines the core security of the contract, allowing unauthorized actions.

## Recommendation
Consider modifying the `check_chakra_signatures` function to prevent the use of duplicate signatures. By adding logic that identifies and rejects multiple identical signatures, you can strengthen the security and integrity of the signature validation process.
