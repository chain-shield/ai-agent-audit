# Vulnerability details

## Summary
The contract inherits a public initialization function from its base contract (BaseSettlementHandler) without proper access control or protection against multiple calls. This vulnerability allows an attacker to reinitialize the contract, potentially taking over ownership and modifying critical contract parameters, even after the contract has been properly set up by the legitimate owner.

## Proof of Concept
https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/BaseSettlementHandler.sol#L113-#L128

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/ChakraSettlementHandler.sol#L82-101


The vulnerability stems from the inheritance structure and initialization pattern used in the ChakraSettlementHandler contract:

- The BaseSettlementHandler contract contains a public initialization function:

```solidity
// In BaseSettlementHandler.sol
function _Settlement_handler_init(
    address _owner,
    SettlementMode _mode,
    address _token,
    address _verifier,
    string memory _chain,
    address _settlement
) public {
    __Ownable_init(_owner);
    __UUPSUpgradeable_init();
    // ... (additional initialization)
}
```

- The ChakraSettlementHandler contract inherits from BaseSettlementHandler and introduces its own initialize function:

```solidity
// In ChakraSettlementHandler.sol
function initialize(
    address _owner,
    SettlementMode _mode,
    string memory _chain,
    address _token,
    address _codec,
    address _verifier,
    address _settlement
) public initializer {
    _Settlement_handler_init(
        _owner,
        _mode,
        _token,
        _verifier,
        _chain,
        _settlement
    );
    codec = IERC20CodecV1(_codec);
}
```

The critical issue is that while the initialize function in `ChakraSettlementHandler` is protected by the initializer modifier, the inherited _Settlement_handler_init function remains public and unprotected. This allows anyone to call this function directly on the deployed contract, potentially overwriting critical contract state and taking over ownership.

Attacker will have access to update following params 
           ```solidity
            _owner,
            _mode,
            _token,
            _verifier,
            _chain,
            _settlement
            ```
which are most important to make sure cross chain msgs/transfers works as intended.


An attacker can exploit this vulnerability using the following steps:

1. Wait for the ChakraSettlementHandler contract to be deployed and initialized by the legitimate owner.
2. Call the _Settlement_handler_init function directly on the deployed contract address:

```js
const ChakraSettlementHandler = await ethers.getContractFactory("ChakraSettlementHandler");
const deployedContract = ChakraSettlementHandler.attach("DEPLOYED_CONTRACT_ADDRESS");

await deployedContract._Settlement_handler_init(
    attackerAddress,
    1, // SettlementMode.MintBurn (could be any as per attacker wish)
    "0x1234...", // target token address
    "0x5678...", // New verifier address
    "MaliciousChain",
    "0x9ABC..." // New settlement address
);
```

3. Verify that the attacker is now the owner:

```js
const newOwner = await deployedContract.owner();
console.assert(newOwner === attackerAddress, "Ownership takeover failed");
```

## Impact
- Unauthorized Ownership Transfer: An attacker can become the owner of the contract, gaining full control over owner-only functions.
- Critical Parameter Modification: The attacker can modify essential contract parameters such as the token address, verifier, and settlement contract address.
- Disruption of Cross-Chain Operations: By changing critical addresses and parameters, the attacker can disrupt or redirect cross-chain token transfers.
- Loss of Funds: In scenarios where the contract holds or manages funds, the attacker could potentially drain or misdirect these assets.
- Loss of Trust: Such a vulnerability severely undermines trust in the protocol, potentially leading to reputational damage and loss of users.

## Recommended Mitigation Steps
Here are few recommendations, any one of them can be used:

1. Remove Public Visibility from Base Initializer:
Change the _Settlement_handler_init function in BaseSettlementHandler to internal:

```solidity
function _Settlement_handler_init(
    address _owner,
    SettlementMode _mode,
    address _token,
    address _verifier,
    string memory _chain,
    address _settlement
) internal {
    // ... (rest of the function)
}
```

2. Implement Proper Inheritance of Initializable:
Ensure both contracts correctly inherit from OpenZeppelin's Initializable:

```solidity
contract BaseSettlementHandler is Initializable {
    // ...
}

contract ChakraSettlementHandler is BaseSettlementHandler {
    // ...
}
```

3. Single Initialization Point:
Ensure that ChakraSettlementHandler's initialize function is the only entry point for initialization:

```solidity
function initialize(
    address _owner,
    SettlementMode _mode,
    string memory _chain,
    address _token,
    address _codec,
    address _verifier,
    address _settlement
) public initializer {
    _Settlement_handler_init(
        _owner,
        _mode,
        _token,
        _verifier,
        _chain,
        _settlement
    );
    codec = IERC20CodecV1(_codec);
}
```
