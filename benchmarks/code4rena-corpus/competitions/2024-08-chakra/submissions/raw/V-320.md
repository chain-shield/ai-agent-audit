# Vulnerability details

## Impact
The function `receive_cross_chain_msg` uses the same logic in the [solidity version](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/ChakraSettlement.sol#L170-L244) and the [cairo version](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/cairo/settlement/src/settlement.cairo#L327-L385). The function takes a number of arguments used to receive a cross chain message and execute the handler function for this message. As the protocol utilizes off chain validators to ensure the right messages get executed, it hashes the message and verifies enough validators signed the hash. While doing so, both implementations do no include the [payload_type](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/libraries/Message.sol#L5-L20) in the hash. This mean that the hash can be changed without invalidating the signatures.

There are different payload types:
- Raw,
- BTCDeposit,
- BTCWithdraw,
- BTCStake,
- BTCUnStake,
- ERC20,
- ERC721

Right now there is only one payload type implemented (ERC20, see [cairo](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/cairo/handler/src/handler_erc20.cairo#L119), [solidity](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L286-L290)). Therefor it is not possible to exploit the issue in a way to execute a different payload type, but that might be an issue with future updates. It is possible that a messaged indented to execute with type A to be frontrun and execute type B.
