# Vulnerability details

## Summary

**Context:**
Here is the execution path when a cross-chain ERC20 transfer call occurs:

Source chain:
[cross_chain_erc20_settlement()](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L111) => [send_cross_chain_msg()](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/ChakraSettlement.sol#L111)

Destination chain:
[receive_cross_chain_msg()](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/ChakraSettlement.sol#L170) => [receive_cross_chain_msg()](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L300)

Source chain:
[receive_cross_chain_callback()](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/ChakraSettlement.sol#L256) => [receive_cross_chain_callback()](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L365)

**Issue:**
The issue in this execution path lies in the receive_cross_chain_callback() call on the source chain. When the signature verification occurs [here](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/ChakraSettlement.sol#L265C8-L272C11), it does not include the `from_chain` parameter (i.e. the destination chain) for the message verification.

**Impact:**
Due to this, an attacker could frontrun the relayer's [receive_cross_chain_callback()](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/ChakraSettlement.sol#L256) call with the same call. The only difference would be that the attacker supplies the `from_chain` parameter as a random uint256.

Since the `from_chain` parameter was not validated by the signature and is now a random value, the call to the [receive_cross_chain_callback()](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L374C8-L376C10) function on the ChakraSettlementHandler.sol contract would return false due to check [here](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L374C8-L376C10). This would set the tx status to FAILED on the ChakraSettlement.sol contract [here](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/ChakraSettlement.sol#L329) even though the call had succeeded on the destination chain. 


The impact of this is that successful MINT_BURN mode calls would not have their tokens burnt on the source chain and would remain locked in the ChakraSettlementHandler.sol contract (see [here](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L383C9-L389C10)). 

## Proof of Concept

Let's go through the issue step by step:

1. We assume an ERC20 cross-chain call occurs from chain A to chain B. The call succeeds on chain B. The settlement mode is MINT_BURN.

2. The relayer calls the receive_cross_chain_callback() function on the ChakraSettlement.sol contract. The attacker sees this incoming call in the mempool and frontruns it with the exact same parameters except for the `from_chain` parameter, which would be some invalid chain not supported by the ChakraSettlementHandler.sol contract.
 - First, the verifySignature() function is called. As we can see from the parameters passed, it does not even use the `from_chain` parameter anyway. We'll see this in step 3.
 - Second, the processCrossChainCallback() function is called. We'll see this in  step 4.

4. The processCrossChainCallback() function does the following:
 - Checks if the status of txid is PENDING (meaning the call was sent from source but has not received a callback)
 - Makes a call to the processCrossChainCallback() function on the ChakraSettlementHandler.sol contract.
 - If the call returns true, it sets the status of the transaction to the `CrossChainMsgStatus status` parameter (which represents that the call validly failed or succeeded on the destination chain).
 - If the call returns false, it simply treats the callback as invalid and sets the status to FAILED.

5. The receive_cross_chain_callback() call to the ChakraSettlementHandler.sol contract would return false. This is because although the `from_handler` was validated by the signature verification in step 3, the `from_chain` is invalid. Due to this, Line 388 returns false to the processCrossChainCallback() function and marks it as FAILED even if the call on the destination succeeded i.e. `CrossChainMsgStatus status` = CrossChainMsgStatus.Success. 
 - Due to this, if the MINT_BURN call had succeeded on the destination chain (see Line 397), the tokens that were transferred to the contract by the user in step 1 are not burnt and remain in the contract locked. Additionally, the status remains PENDING and does not transition in ChakraSettlementHandler.sol even though it is marked FAILED in the ChakraSettlement.sol contract.
