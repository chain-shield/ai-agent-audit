# Vulnerability details

## Impact

In `handler_erc20` smart contract, there is a `support_handler` mapping that checks whether the chain and its handler is supported or not. The problem is that at the moment `receive_cross_chain_callback()` checks whether `to_chain` and `to_handler` are supported on the chain where this function is called. This can lead to incorrect behavior as protocols are supposed to set handler that's supported on the destination chain and not the source chain handler itself.

## Proof of Concept

https://github.com/code-423n4/2024-08-chakra/blob/main/cairo/handler/src/handler_erc20.cairo#L144-145
```
            assert(self.support_handler.read((from_chain, from_handler)) && 
                    self.support_handler.read((to_chain, contract_address_to_u256(to_handler))), 'not support handler');
```

As you can see from the logic above, the function verifies if the `to_chain` and `to_handler` is supported on the source chain. The problem is that `support_handler` mapping is created to set destination handler to accept calls from them. But if the function checks whether the `to_chain` is the chain where this function is called, `support_handler` may just not set this handler as supported handler leading to unnecessary DoS. In contrary, here's the corresponding logic on Ethereum:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/ChakraSettlementHandler.sol#L374-376
```
  if (is_valid_handler(from_chain, from_handler) == false) {
            return false;
        }
```

So it only checks whether `from_handler` from the `from_chain` is supported to make calls to the source chain and the source handler.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Remove the check for `to_chain` and `to_handler`.
