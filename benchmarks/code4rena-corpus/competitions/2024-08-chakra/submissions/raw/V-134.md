# Vulnerability details

## Impact
To grant and revoke roles, you need help from the `role’s admin`. However, within the protocol, a `manager` can grant/revoke the role from any other `manager`. 

The `owner` and `managers` are not of the same rank. i.e `owner` is the admin of `MANAGER_ROLE`. Therefore, if the `owner` adds/removes a `manager` while another `manager` performs the opposite of the owner's actions, this inconsistency in role management poses governance risk.

## Proof of Concept
In [`SettlementSignatureVerifier`](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/SettlementSignatureVerifier.sol#L62-L70) only the `owner` can grant or revoke `MANAGER` role:
```solidity
    function add_manager(address _manager) external onlyOwner {
        grantRole(MANAGER_ROLE, _manager);
        emit ManagerAdded(msg.sender, _manager);
    }

    function remove_manager(address _manager) external onlyOwner {
        revokeRole(MANAGER_ROLE, _manager);
        emit ManagerRemoved(msg.sender, _manager);
    }
```

However, in [`ckr_btc`](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/ckr_btc.cairo#L134-L161) any `MANAGER` can add or remove another `MANAGER`:
```solidity
        fn add_manager(ref self: ContractState, new_manager: ContractAddress) -> bool {
>>          let caller = get_caller_address();
>>          assert(self.chakra_managers.read(caller) == 1, Errors::NOT_MANAGER);
            assert(self.chakra_managers.read(new_manager) == 0, Errors::ALREADY_MANAGER);

            self.chakra_managers.write(new_manager, 1);
            self
                .emit(
                    ManagerAdded {
                        operator: caller, new_manager: new_manager, added_at: get_block_timestamp()
                    }
                );
            return self.chakra_managers.read(new_manager) == 1;
        }
        fn remove_manager(ref self: ContractState, old_manager: ContractAddress) -> bool {
>>          let caller = get_caller_address();
>>          assert(self.chakra_managers.read(caller) == 1, Errors::NOT_MANAGER);
        
            self.chakra_managers.write(old_manager, 0);
            self
                .emit(
                    ManagerRemoved {
                        operator: caller,
                        old_manager: old_manager,
                        removed_at: get_block_timestamp()
                    }
                );
            return self.chakra_managers.read(old_manager) == 0;
        }
```
This allows a `MANAGER` to add or remove another `MANAGER` even though they are not the admin for that role. It is true that the `owner` also has this role:
```solidity
    self.chakra_managers.write(owner, 1); // @audit Granted in the constructor
```
However, the fact that any other manager can perform such admin duties, breaks the chain of governance.

- [`settlement::remove_manager()`](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/settlement.cairo#L261-L262)

## Recommended Mitigation Steps
To fix this, the `add_manager()` and `remove_manager()` functions in `ckr_btc` should be called by only the `owner`:
```diff
-   let caller = get_caller_address();
-   assert(self.chakra_managers.read(caller) == 1, Errors::NOT_MANAGER);

+   // This function can only be called by the owner
+   self.ownable.assert_only_owner();
```
