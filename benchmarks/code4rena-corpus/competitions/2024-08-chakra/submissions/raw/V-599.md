# Vulnerability details

## Impact
If the cross chain callback fails for a token transfer, then the sending user's tokens will remain locked in the handler contract on the source chain or, in the case of `BurnUnlock` mode, the user's tokens would remain burned.

If sending from an EVM chain, the callback could register as having failed and `create_cross_txs[txid].status` would be updated, but this does not give the user any way to retrieve their tokens.

Additionally, users may be unwilling to trust the protocol with their assets if they are aware that there is no rescue procedure. So this issue can harm the protocol regardless of how confident the protocol may be in the reliability of the cross chain relaying system.

## Proof of Concept
When initiating a cross chain movement of tokens from either an EVM chain or Starknet, the settlement contract sends a cross chain message and expects a callback confirming the successful receipt of the original message. We will consider two scenarios.

First scenario: no callback message is ever received because the original outgoing message failed.

In this case, for both EVM and Starknet, the tokens would be lost in the initial call to `cross_chain_erc20_settlement()`. They would be either locked or burned, depending on the mode. These handler contracts do not provide a mechanism for rescuing these tokens. No tokens would be minted or unlocked on the destination chain, as the message was never received.

It might be submitted that the cross chain message should not simply fail. However, it is quite possible that a network or hardware failure or a misconfiguration of validators on the receiving chain might cause this to happen and some messages might fail to be sent.

Second scenario: the callback message is received, but with a failure status.

In this case, the EVM chains would update `create_cross_txs[txid].status` to `CrossChainTxStatus.Failed` within the function [`receive_cross_chain_callback` (link)](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L391-L393). However, this does not give the user any way to retrieve their tokens.

On Starknet, the cairo code processes the callback regardless. This is discussed in another submission.

## Tools Used
Manual inspection

## Recommended Mitigation Steps
If a callback is not received after a certain period of time, allow a user to retrieve their tokens from the handler contract.

If a callback is received and it has a failure status for a pending status transaction, allow a user to retrieve their tokens from the handler contract after a cooldown period.
