# Vulnerability details


## Proof of Concept

Starknet is an L2, unlike whereas optimistic rollups like Optimist or Arbitrum, Starknet is a validity rollup that also integrates a core sequencer logic.

The above means that Starknet is also susceptible to reorgs, with the most recent happening in Q2 this year, see _[source](https://www.fxleaders.com/news/2024/04/09/starknet-hit-by-block-reorganization-bug-new-dai-version-launched-on-starknet/)_.

Now Chakra integrates with an access control logic that restricts some functionality to the managers that can be set via `add_manager()` & `remove_manager()`: https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/ckr_btc.cairo#L134-L161

```cairo
        fn add_manager(ref self: ContractState, new_manager: ContractAddress) -> bool {
            let caller = get_caller_address();
            assert(self.chakra_managers.read(caller) == 1, Errors::NOT_MANAGER);
            assert(self.chakra_managers.read(new_manager) == 0, Errors::ALREADY_MANAGER);

            self.chakra_managers.write(new_manager, 1);
            self
                .emit(
                    ManagerAdded {
                        operator: caller, new_manager: new_manager, added_at: get_block_timestamp()
                    }
                );
            return self.chakra_managers.read(new_manager) == 1;
        }
        fn remove_manager(ref self: ContractState, old_manager: ContractAddress) -> bool {
            let caller = get_caller_address();
            assert(self.chakra_managers.read(caller) == 1, Errors::NOT_MANAGER);
            self.chakra_managers.write(old_manager, 0);
            self
                .emit(
                    ManagerRemoved {
                        operator: caller,
                        old_manager: old_manager,
                        removed_at: get_block_timestamp()
                    }
                );
            return self.chakra_managers.read(old_manager) == 0;
        }
```

Issue however is the fact that when removing the managers there is no check to ensure that tghe protocol is not left in a state where we have `0` managers, see `remove_manager` attached above.

This then means that in the case the only manager is to be swapped to a new one, the flow would be:
Assume current manager is `A`
New manager is `B`

- `A` [calls add_manager()](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/ckr_btc.cairo#L133-L134) with `B's` contract address. -> `tx1`
- `A` is now the old manager.
- `A` calls remove_manager() with their address to renounce their role. -> `tx2`.

If a block reorg happens, that's quite common with rollups, then we could have `tx2` come before `tx1`, which would then mean the contract would be left without any managers cause since `A` now renounces their role first, when attempting to pass `B's` address to give them the role, the transaction always reverts [here](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/ckr_btc.cairo#L136), since they no longer would be an admin.

## Impact

The contract can be left in a state where there are no longer any managers unintentionally, which would then mean that functionalities restricted to managers would no longer be accessible, for e.g [adding/removing operators would no longer be possible](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/ckr_btc.cairo#L169-L196).

Considering these measures are placed to restrict who can mint/burn tokens, this then means that the whole intended functionality is broken, cause:

- If a current operator goes malicious, there is no longer access to the functionality to remove the operator, [leaving them access to mint/burn the tokens as they like](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/ckr_btc.cairo#L199-L217).
- If a current operator loses keys to their account, there is no longer access to the functionality to remove the operator and add them in as a new operator, [causing a DOS to the whole minting/burning logic](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/ckr_btc.cairo#L199-L217).

Would be key to note that the same bug window is applicable to _settlement_ contract, see [settlement.cairo#L245-L273](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/settlement.cairo#L245-L273), and in our case would then mean that the contract could be left without any accesss control, so [validators would no longer be setable](https://github.com/code-423n4/2024-08-chakra/blob/main/cairo/handler/src/settlement.cairo#L197C1-L203C1) as such if the required threshold was set quite high previously and the new manager was to add in new validators, then nothing (cross chain messages/ callbacks) can get processed cause of [this check](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/settlement.cairo#L189) when validating the signatures, also if a validator turns malicious or is to be deprecated/changed then there is [**no longer** access to the functionality](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/settlement.cairo#L208-L239) to sort this out.

Which then means that cross chain messages can no longer be received since not enough signatures would exist: https://github.com/code-423n4/2024-08-chakra/blob/main/cairo/handler/src/settlement.cairo#L350C1-L351C1 And even callbacks: https://github.com/code-423n4/2024-08-chakra/blob/main/cairo/handler/src/settlement.cairo#L413

## Recommended Mitigation Steps

Include a check to ensure that at least one manager is left before removing the current one, if there is a need to make the contract completely permisionless in the future, then introduce a different `renounce()` functionality that removes all current managers.
