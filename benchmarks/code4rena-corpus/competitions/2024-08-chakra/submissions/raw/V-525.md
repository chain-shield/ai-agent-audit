# Vulnerability details

## Impact
The `to` parameter is the address that will receive the bridged tokens in the destination chain. In both solidity and cairo implementations are passed as uint256 data type.
```
function cross_chain_erc20_settlement(
        string memory to_chain,
        uint256 to_handler,
        uint256 to_token,
        uint256 to,             <--
        uint256 amount
    ) external
```
```
fn cross_chain_erc20_settlement(
    ref self: ContractState,
    to_chain: felt252,
    to_handler: u256,
    to_token: u256,
    to: u256,                   <--
    amount: u256) -> felt252
```
However, in the supported chains, we only have 2 different address types. EVM compatible chains use addresses with 160 bits whereas Starknet uses 252 bits. As we can see the `to` parameter has more bits than both of these type addresses and since there is no validation in the parameter it can lead to the user locking his tokens in the bridge contract forever if the value is greater than the maximum acceptable value of the address type.

That is because when the user initiates a bridge transfer the transaction goes through because there is no validation on this parameter. After that, when Chakra validators will initate the receiving token execution, if the `to` value is greater than the maximum value of the address type, it will try to type cast but will fail.

For this error to occur it is needed that the `to` value exceeds 2^251 + 17 * 2^192.

This error happens because there is a first execution by the user where he transfer his tokens to the bridge and the second exection, Chakra validators will mint/transfer the tokens in the destination chain, but it will fail. So the user has no way to recover his tokens.

There are other parameters that have the same issue like `to_token` or `to_handler`. The `to_token` parameter is not used but it can lead to problems in the future if it gets used. And `to_handler` happens the same issue as the `to`, because it will be the address where the token will be minted/transfered, hence it will try to type cast it and fail.

There is an other issue related to type casting an address. In this case is done offchain but can lead to problems too. When an EVM chain initiates a message bridge it will send a `to_handler` address which has to be passed as a uint256 and will be emitted in the event with the same type. However, when this message will be received in Starknet, it will execute the following:
```
        fn receive_cross_chain_msg(

```
As we can see, the parameter of the funcion is a `ContractAddress` which is essentially a felt252. That means that the validator has type casted it offchain. What if the uint256 exceeds the felt252 maximum acceptable value? Will it overflow? It can lead to problems

## Proof of Concept
1. User calls `cross_chain_erc20_settlement` with a `to` parameter exceeding max address type of the destination chain.
2. Tokens are transfered to the bridge contract
3. Chakra validator tries to execute `receive_cross_chain_msg` but fails
4. User can not cancel bridging or recover his tokens

Manual review

## Recommended Mitigation Steps
Validate the parameters that are meant to be addresses to fit in the destination chain address type.
