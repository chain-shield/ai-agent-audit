# Vulnerability details


## Impact
Imagine a cross-chain settlement system with two distinct components, `BaseSettlement` and `SettlementSignatureVerifier`, that each have their own `required_validators` parameters. Due to improper synchronization, changing the `required_validators` value in `BaseSettlement` has no effect on the actual signature verification process because the system fails to update the `required_validators` in `SettlementSignatureVerifier`. This can lead to unintended consequences, including improper security thresholds, confusion, and potential exploitation.

## Proof of Concept
Both `BaseSettlement` and `SettlementSignatureVerifier` is using `required_validators` and is allowing to change the param via a setter.

```solidity
SettlementSignatureVerifier
    function set_required_validators_num(
        uint256 _required_validators
    ) external virtual onlyRole(MANAGER_ROLE) {
        uint256 old = required_validators;
        required_validators = _required_validators;
        emit RequiredValidatorsChanged(msg.sender, old, required_validators);
    }
BaseSettlement
    function set_required_validators_num(
        uint256 _required_validators
    ) external onlyRole(MANAGER_ROLE) {
        uint256 old = required_validators;
        required_validators = _required_validators;
        emit RequiredValidatorsChanged(msg.sender, old, required_validators);
    }
```

The problem is that `BaseSettlement::set_required_validators_num` is not taking any effect at all since it is not calling `SettlementSignatureVerifier::set_required_validators_num` to sync the `required_validators`.

1. **Initial Setup:**
• The protocol is set up with a `required_validators` threshold of 5 in both `BaseSettlement` and `SettlementSignatureVerifier` by default.
• The `BaseSettlement` component manages general settings and overall transaction logic, while the `SettlementSignatureVerifier` handles the actual signature verification process.

2. **Changing the Threshold in BaseSettlement:**
• The protocol operator decides to change the required_validators from 3 to 5 in BaseSettlement using the `set_required_validators_num` function in `BaseSettlement`.
• The operator believes this action successfully updates the validator threshold for cross-chain settlement verification.

3. **Discrepancy:**
• The operator does not realize that `BaseSettlement` and `SettlementSignatureVerifier` are not synchronized.
• The change in `BaseSettlement` does not propagate to `SettlementSignatureVerifier`, where the actual verification of signatures takes place.
• As a result, `SettlementSignatureVerifier` still expects 3 signatures, while the operator and users assume the required number of signatures has been increased to 5.


4. **Result:**
• **Operational Confusion:** The protocol operators and users are confused, as transactions may get rejected unexpectedly, and changes in the system’s behavior are inconsistent with their understanding.
• **Security Vulnerability:** In a worst-case scenario, the system’s inconsistency could be exploited by malicious actors, leading to improper verification of cross-chain transactions, loss of funds, and significant security breaches.

## Tools Used
Manual

## Recommended Mitigation Steps
To resolve this issue, the system should ensure that any changes to `required_validators` in `BaseSettlement` automatically propagate to `SettlementSignatureVerifier`.
