# Vulnerability details

## Critical: Unbounded Token Minting/Burning via Cross-Chain Message Replay

The `receive_cross_chain_msg` function in the `ERC20Handler` contract is responsible for handling cross-chain messages related to ERC20 token transfers. However, it has been identified that this function is vulnerable to signature replay attacks, which could allow malicious actors to mint and transfer tokens without proper authorization.

## Vulnerability Details

1. **Signature Replay Attack**:
   - The function does not adequately verify the authenticity of the incoming cross-chain message. If an attacker can capture a valid message (including its signature), they can replay it to the contract, causing unintended token minting or transfers.
   - The lack of nonce or timestamp checks means that the same message can be processed multiple times, leading to potential double spending or unauthorized token creation.

2. **Minting and Transferring Tokens**:
   - The function allows for the minting of tokens through the `erc20.mint_to` method when the mode is set to `MintBurn` or `LockMint`. If an attacker replays a valid message, they can exploit this to mint tokens to their own address.
   - Similarly, the function allows for transferring tokens using the `token.transfer` method. A replayed message could result in unauthorized transfers of tokens from the contract.

## Recommendations

- **Implement Nonce or Timestamp Checks**: Introduce a nonce or timestamp mechanism to ensure that each cross-chain message can only be processed once. This will prevent replay attacks by requiring that each message has a unique identifier.

  
- **Signature Verification**: Ensure that the sender of the cross-chain message is verified through a robust signature verification process. This could involve using a public key associated with the sender to validate the authenticity of the message.

- **Audit and Testing**: Conduct a thorough audit and testing of the contract to identify any other potential vulnerabilities and ensure that the implemented fixes effectively mitigate the risks.

        from_handler: u256, to_handler: ContractAddress, payload: Array<u8>) -> bool{
            assert(to_handler == get_contract_address(),'error to_handler');

            assert(self.settlement_address.read() == get_caller_address(), 'not settlement');

            assert(self.support_handler.read((from_chain, from_handler)) && 
                    self.support_handler.read((to_chain, contract_address_to_u256(to_handler))), 'not support handler');

            let message :Message= decode_message(payload);
            let payload_type = message.payload_type;
            assert(payload_type == PayloadType::ERC20, 'payload type not erc20');
            let payload_transfer = message.payload;
            let transfer = decode_transfer(payload_transfer);
            assert(transfer.method_id == ERC20Method::TRANSFER, 'ERC20Method must TRANSFER');
            let erc20 = IERC20MintDispatcher{contract_address: self.token_address.read()};
            let token = IERC20Dispatcher{contract_address: self.token_address.read()};
            if self.mode.read() == SettlementMode::MintBurn{
                erc20.mint_to(u256_to_contract_address(transfer.to), transfer.amount);
            }else if self.mode.read() == SettlementMode::LockMint{
                erc20.mint_to(u256_to_contract_address(transfer.to), transfer.amount);
            }else if self.mode.read() == SettlementMode::BurnUnlock{
                token.transfer(u256_to_contract_address(transfer.to), transfer.amount);
            }else if self.mode.read() == SettlementMode::LockUnlock{
                token.transfer(u256_to_contract_address(transfer.to), transfer.amount);
            }
            
            return true;
        }
