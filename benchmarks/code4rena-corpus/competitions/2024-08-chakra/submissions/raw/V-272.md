# Vulnerability details

## Impact
The `from_address` parameter is represented as an address in the function `send_cross_chain_msg` but incorrectly represented as a uint256 instead of an address in the function `receive_cross_chain_msg`. From the comments

```
 * @param from_address The address the message is from
```
This means that message_hash will have from_address as type uint256 instead of type address

```javascript
function receive_cross_chain_msg(
        uint256 txid,
        string memory from_chain,
        uint256 from_address, // @audit should this be address?
        uint256 from_handler, 
        address to_handler,
        PayloadType payload_type,
        bytes calldata payload,
        uint8 sign_type, // validators signature type /  multisig or bls sr25519
        bytes calldata signatures // signature array
    ) external {}
```

This type mismatch could lead to incorrect address handling, potential signature verification failures, and unexpected behavior within the smart contract. If the from_address is misinterpreted or manipulated, it could open up the contract to potential exploits, such as bypassing access controls or altering transaction outcomes.

By doing this our message_hash now contains a `from_address` that is a type uint256 but in real sense it should be type address. this miss representation might cause some issues.

```javascript
bytes32 message_hash = keccak256(
                abi.encodePacked(
                    txid,
                    from_chain,
                    from_address,
                    from_handler,
                    to_handler,
                    keccak256(payload)
                )
            );
```

## Proof of Concept
In the send_cross_chain_msg function, the from_address is correctly passed as an address and included in the transaction ID (txid) generation:

```javascript
uint256 txid = uint256(
    keccak256(
        abi.encodePacked(
            contract_chain_name,
            to_chain,
            from_address, // `from_address` as `address`
            from_handler,
            to_handler,
            nonce_manager[from_address]
        )
    )
);
``` 
When the cross-chain message is received, the `from_address` is incorrectly treated as a uint256 in the `receive_cross_chain_msg` function:

```javascript
function receive_cross_chain_msg(
    uint256 txid,
    string memory from_chain,
    uint256 from_address, // `from_address` as `uint256`
    uint256 from_handler,
    address to_handler,
    PayloadType payload_type,
    bytes calldata payload,
    uint8 sign_type,
    bytes calldata signatures
) external {
    // Signature verification logic
}
```
Due to this type mismatch, the message_hash used for signature verification is generated from a type uint256 value but it should be from type of address which may cause inconsintencies.

## Recommended Mitigation Steps
Ensure consistent data types, represent `from_address` as an address in both the `send_cross_chain_msg` and `receive_cross_chain_msg`

```javascript
function receive_cross_chain_msg(
    uint256 txid,
    string memory from_chain,
    address from_address, // Corrected to `address`
    uint256 from_handler,
    address to_handler,
    PayloadType payload_type,
    bytes calldata payload,
    uint8 sign_type,
    bytes calldata signatures
) external {
    // Corrected function implementation
}
```
