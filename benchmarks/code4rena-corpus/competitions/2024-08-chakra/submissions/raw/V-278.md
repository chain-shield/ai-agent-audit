# Vulnerability details

## Impact
There is no nonce in verifyECDSA functions or any mechanism to ensure the uniqueness of the message being signed and verified. This could lead to potential replay attacks, where an attacker could reuse a valid signed message to execute unintended actions multiple times. This could lead to significant security risks, including unauthorized state changes, double-spending, or other forms of malicious activity on the blockchain.

## Proof of Concept
IF a validator signs a valid message or a transaction and submits it to the smart contract. The tx is processed correctly, and the desired action is executed on the blockchain.

An attacker could resubmit the msg or transaction to the smart contract without any modification. Since the `verifyECDSA` function only checks the validity of the signature against the msgHash without ensuring the uniqueness of the message, the contract processes the message again.
As a result, the same action is executed multiple times, leading to unintended and potentially harmful consequences, such as unauthorized transfers of assets or repeated state changes.

```javascript
function verify(
    bytes32 msgHash,
    bytes calldata signatures,
    uint8 sign_type
) external view returns (bool) {
    if (sign_type == 0) {
        return verifyECDSA(msgHash, signatures);
    } else {
        return false;
    }
}

function verifyECDSA(
    bytes32 msgHash,
    bytes calldata signatures
) internal view returns (bool) {
    require(
        signatures.length % 65 == 0,
        "Signature length must be a multiple of 65"
    );

    uint256 len = signatures.length;
    uint256 m = 0;
    for (uint256 i = 0; i < len; i += 65) {
        bytes memory sig = signatures[i:i + 65];
        if (
 @>>           validators[msgHash.recover(sig)] && ++m >= required_validators
        ) {
            return true;
        }
    }

    return false;
}
```
As we can see no mechanism to prevent the same `msgHash` and signatures from being reused in a replay attack.
This vulnerability is similar to the [Taiko H-05](https://solodit.xyz/issues/h-05-signatures-can-be-replayed-in-withdraw-to-withdraw-more-tokens-than-the-user-originally-intended-code4rena-taiko-taiko-git) where users could reuse signatures to gain more tokens.

## Recommended Mitigation Steps
Incorporate a nonce or deadline into the message hash before verifying the signature

```javascript
bytes32 uniqueHash = keccak256(abi.encodePacked(msgHash, nonce));

    if (sign_type == 0) {
```
