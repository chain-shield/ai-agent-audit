# Vulnerability details

## Impact
Due to improper validation in `receive_cross_chain_callback()` in `ChakraSettlement.sol` a malicious user can take over the execution and fail any transaction at will. Leading to stuck user funds - since those transactions cannot be replayed

## Description
`ChakraSettlement.receive_cross_chain_callback()` internally calls the following code:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/settlement/contracts/ChakraSettlement.sol#L256

```solidity
function receive_cross_chain_callback(
        uint256 txid,
        string memory from_chain, //@audit- not in signature
        uint256 from_handler,
        address to_handler,
        CrossChainMsgStatus status,
        uint8 sign_type,
        bytes calldata signatures
    ) external {

        verifySignature(
            txid,
            from_handler,
            to_handler,
            status,
            sign_type,
            signatures
        );
        processCrossChainCallback(
            txid,
            from_chain,
            from_handler,
            to_handler,
            status,
            sign_type,
            signatures
        );
        emitCrossChainResult(txid);
    }

```
1. It verifies the signatures
2. It calls the handler to finalize the transaction
3. Based on the returned result from the handler call it finalizes the status of the trx

The main problem here is that from the parameters provided to `receive_cross_chain_callback()` the  `from_chain` is the only one that is not included in the signature and respectively not validated:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/settlement/contracts/ChakraSettlement.sol#L293C7-L300C11

```solidity
  bytes32 message_hash = keccak256(
            abi.encodePacked(txid, from_handler, to_handler, status)
        );

        require(
            signature_verifier.verify(message_hash, signatures, sign_type),
            "Invalid signature"
        );
```

This is a problem because of the following check conducted in `ChakraSettlementHandler::receive_cross_chain_callback()`:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/ChakraSettlementHandler.sol#L374-L375
```solidity
 if (is_valid_handler(from_chain, from_handler) == false) {
            return false;
        }
```

If false is returned from it, then the transaction in `ChakraSettlement` will be marked as `Failed` :
https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/settlement/contracts/ChakraSettlement.sol#L317-L331

```solidity
if (
            ISettlementHandler(to_handler).receive_cross_chain_callback(
                txid,
     ---->           from_chain,
                from_handler,
                status,
                sign_type,
                signatures
            )
        ) {
            create_cross_txs[txid].status = status;
        } else {
            create_cross_txs[txid].status = CrossChainMsgStatus.Failed;
        }
    }
```

This creates an opportunity for a malicious user to front-run any pending `ChakraSettlement::receive_cross_chain_callback()` transactions (submitted with valid signatures) , re-use the parameters from them but set the `from_chain` parameter to invalid one and fail the transaction

## Proof of Concept
- 5 valid signatures are collected and an executor node ( probably belonging to the Chakra team) submits `receive_cross_chain_callback()` with all the validated data.
- Bob sees the pending transactions and creates and exact copy of it - with the valid signatures and paramaters
- He only changes the `from_chain` parameter to an invalid one - which will pass, since it is NOT validated in the signature
- The handler validation will return false and the transaction will be marked as Failed
- The funds that were transferred initially with that transaction are lost

## Recommended Mitigation Steps

Add the `from_chain` parameter to the data that is hashed inside the signature, this will prevent non verified data from being used
