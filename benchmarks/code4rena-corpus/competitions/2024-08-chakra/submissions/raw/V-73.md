# Vulnerability details

## Impact

`TokenRoles` contract is the contract that helps to add / remove operators. The problem is that the contract inherits `UUPSUpgradeable` functionality but does not initialize it in the initialization function not allowing to use upgradeability.

## Proof of Concept

Take a look at the current initialization process:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/TokenRoles.sol#L6
```
import "@openzeppelin/contracts-upgradeable/proxy/utils/UUPSUpgradeable.sol";
```

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/TokenRoles.sol#L8-12
```
abstract contract TokenRoles is
    OwnableUpgradeable,
    UUPSUpgradeable,
    AccessControlUpgradeable
{

```

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/TokenRoles.sol#L19-23
```
    function __TokenRoles_init(address _owner, address _operator) public {
        __Ownable_init(_owner);
        _grantRole(DEFAULT_ADMIN_ROLE, _owner);
        _grantRole(OPERATOR_ROLE, _operator);
    }
```

But the problem is that the upgradeability is not initialized anyhow. Therefore, the contract cannot be upgraded in the future.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Add `__UUPSUpgradeable_init()` and `_authorizeUpgrade` to be able to use upgradeability logic:


https://github.com/OpenZeppelin/openzeppelin-contracts-upgradeable/blob/master/contracts/proxy/utils/UUPSUpgradeable.sol#L65-66
```
  function __UUPSUpgradeable_init() internal onlyInitializing {
    }
```

https://github.com/OpenZeppelin/openzeppelin-contracts-upgradeable/blob/master/contracts/proxy/utils/UUPSUpgradeable.sol#L132
```

  function _authorizeUpgrade(address newImplementation) internal virtual;
```
