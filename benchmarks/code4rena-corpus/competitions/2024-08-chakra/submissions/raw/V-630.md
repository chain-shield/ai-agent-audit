# Vulnerability details

The automated bot report does not include the Cairo handler contract, even though the same issue is present in Solidity handler contract.

Not all `IERC20` implementations `revert()` when there's a failure in `transfer()`/`transferFrom()`. The function signature has a `boolean` return value and they indicate errors that way instead. By not checking the return value, operations that should have marked as failed, may potentially go through without actually making a payment.
Also, some tokens do not implement the ERC20 standard properly, and do not return booleans as the specification requires. Instead, they have no return value.

## Impact
In the context of `cross_chain_erc20_settlement` function of `handler_erc20.cairo`, in case any of the transfers silently fails, the protocol would still proceed with cross chain transaction minting/unlocking tokens on destination chain which might lead to a total loss of protocol's funds on destination chain.
In the context of `receive_cross_chain_msg` function, in unlikely case of the protocol insolvency, the transfer might silently fail while still returning true and eventually emitting successfull `CrossChainHandleResult` event.

## Tools Used

Manual review

## Recommended Mitigation Steps

Use the Cairo version of OpenZeppelin's `SafeERC20`'s `safeTransfer()`/`safeTransferFrom()` instead.
