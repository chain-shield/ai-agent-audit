[Official document address](https://s3labs.notion.site/Contract-Design-Document-f4aa296f71fb40b1818c0890c40be55c#2286a74561ce4765909db58db373eaee)
Refer to the attached flowchart for a detailed explanation. Due to the complexity of the code and the steps involved, this report will focus on steps 2 and 6 of the process.

Part 1 (Corresponding to Step 2 in the Flowchart):
When the `ChakraSettlementHandler::cross_chain_erc20_settlement()` function is called to perform a cross-chain settlement, both the `ChakraSettlementHandler` and `ChakraSettlement` contracts utilize their respective `nonce_manager` mappings to generate random numbers, which are used to create a `txid`. The status of the `txid` is then updated in the `create_cross_txs[txid]` mapping to `CrossChainTxStatus.Pending`.

However, due to the absence of access restrictions in the `ChakraSettlement::send_cross_chain_msg()` function, and since `from_address` is passed as a parameter, a malicious user can arbitrarily modify the value of `nonce_manager[from_address]`. Consequently, the `txid` generated in the `ChakraSettlementHandler` and `ChakraSettlement` contracts will not match.

Part 2 (Corresponding to Step 6 in the Flowchart):
When the `ChakraSettlement::receive_cross_chain_callback()` function is called, it invokes `ChakraSettlementHandler::receive_cross_chain_callback()` through `ChakraSettlement::processCrossChainCallback()`. At this stage, `txid` is passed as a parameter to execute the call. However, since the `txid` generated in Part 1 does not match, the condition `create_cross_txs[txid].status == CrossChainMsgStatus.Pending` will fail. This mismatch will prevent the expected execution of the program, potentially leading to a failure in processing the cross-chain transaction.

## Impact
The ability of anyone to call `ChakraSettlement::send_cross_chain_msg()` and maliciously update the `nonce_manager` mapping can result in unequal `txid` values within the contract. This inconsistency compromises the reliability of the entire system, especially in cross-chain operations involving funds or critical assets. The resulting discrepancies can lead to irrecoverable losses or complete system failures.
## Proof of Concept
To demonstrate this vulnerability, you can add the following test code to `settlement/test/ChakraSettlementTest.t.sol` and execute it:

contract ChakraSettlementTest is Test {

    using ECDSA for bytes32;

    address owner = makeAddr("owner");
    address manager = makeAddr("manager");

    function setUp() public {

        settlementSignatureVerifier = new SettlementSignatureVerifier();
        settlementSignatureVerifier.initialize(owner,100);
        assertEq(settlementSignatureVerifier.required_validators(),100);

        address[] memory managers = new address[](1);
        managers[0] = manager;

## Recommended Mitigation Steps
1. Centralized Management of Nonce:Implement centralized management for the nonce values to ensure consistency across all related contracts. All contracts should retrieve and update the nonce values through a central contract.

2. Two-Way Verification Mechanism:Implement a verification mechanism that checks and synchronizes nonce values across all related contracts both before the cross-chain transaction begins and after it is completed.

3. Restrict Parameter Input:Avoid allowing addresses to be passed as parameters to prevent malicious actors from altering related states arbitrarily.
