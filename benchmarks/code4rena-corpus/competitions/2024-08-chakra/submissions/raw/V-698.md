# Vulnerability details

## Summary

The `verifyECDSA` function in the `SettlementSignatureVerifier` both present in the handler and the settlement contracts contains vulnerabilities related to signature malleability and potential replay attacks. These issues could compromise the integrity of the signature verification process, potentially allowing unauthorized actions within the settlement system.

## Description

The protocol has decided to implement a custom ECDSA to verify signatures and the function is implemented as follows:

```solidity
function verifyECDSA(
    bytes32 msgHash,
    bytes calldata signatures
) internal view returns (bool) {
    require(
        signatures.length % 65 == 0,
        "Signature length must be a multiple of 65"
    );

    uint256 len = signatures.length;
    uint256 m = 0;
    for (uint256 i = 0; i < len; i += 65) {
        bytes memory sig = signatures[i:i + 65];
        if (
            validators[msgHash.recover(sig)] && ++m >= required_validators
        ) {
            return true;
        }
    }

    return false;
}

```

The function iterates through the provided signatures, recovering the signer's address for each signature and checking if it's a valid validator. It returns true if the number of valid signatures meets or exceeds the required number of validators.

However, this implementation has two main issues:

Signature Malleability: The function doesn't check if the 's' value of the ECDSA signature is in the lower half of the curve's order. This omission allows for signature malleability, where an attacker could create a valid signature by flipping the 's' value without knowing the private key.

Potential Replay Attacks: The function uses a simple counter (m) to track the number of valid signatures. This approach could be vulnerable to replay attacks if the same signature is used multiple times within the same transaction.


## Impact

These vulnerabilities could lead to:

1. Unauthorized actions: Exploiting signature malleability could allow an attacker to forge valid signatures, potentially authorizing unintended actions within the settlement system.

2. Replay attacks: The lack of protection against signature reuse could allow an attacker to artificially inflate the number of valid signatures, potentially meeting the required threshold with fewer unique signers than intended.

3. Compromised integrity: These issues undermine the reliability of the signature verification process, which is crucial for the security of the entire settlement system.



## Recommendations
Implement s-value check: Add a check to ensure the 's' value of each signature is in the lower half of the curve's order. This can prevent signature malleability attacks.

```solidity
require(uint256(sig[32:64]) <= 0x7FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF5D576E7357A4501DDFE92F46681B20A0, "Invalid s value");
```
