# Vulnerability details

After the `CrossChainMsg` event is emitted, the `receive_cross_chain_msg` function is invoked by validator. Because validators are not trusted (only operators are), each transaction initiated by them, has to be properly checked.

For instance, Solidity contract `ChakraSettlement` has the following check in `receive_cross_chain_msg` to only allow processing the message once:
```solidity
    require(
        receive_cross_txs[txid].status == CrossChainMsgStatus.Unknow,
        "Invalid transaction status"
    );
```
[ChakraSettlement.sol#L199-L202](https://github.com/code-423n4/2024-08-chakra/blob/f61c899c22492bdf5bdcb07cdb62ea9b4cd38825/solidity/settlement/contracts/ChakraSettlement.sol#L199-L202)

However, this check is not present in the Cairo implementation allowing any malicious validator running the `receive_cross_chain_msg` function even if the message status is already set to `SUCCESS` or `FAILED`. 

## Impact
`receive_cross_chain_msg` can be exploited to mint or withdraw all available funds locked in the handler contract depending on the settlement mode, stealing the funds from the protocol and its users.

## Proof of Concept
Let's consider two settlement modes.

The settlement mode is set to `MintBurn` or `LockMint`:
1. Malicious user calls the `cross_chain_erc20_settlement` function indicating his intention to burn/lock 10 tokens on the source chain A and mint 10 tokens on destination chain B.
2. The `CrossChainMsg` event is emitted as 10 tokens are successfully transferred from the user to handler contract (locked) on chain A.
3. Malicious validator, scans the event, and invokes `receive_cross_chain_msg` to mint 10 tokens to the user on chain B.
This would write the transaction status `CrossChainMsgStatus` as `SUCCESS` or `FAILED`.
4. Due to the lack of checks for `CrossChainMsgStatus`, after the tokens are minted, instead of invoking `receive_cross_chain_callback`, validator calls `receive_cross_chain_msg` function again minting another 10 tokens. Validators can repeat calling this function and minting the tokens on destination chain as many times as they like.

The settlement mode is set to `BurnUnlock` or `LockUnlock`:
- Let's assume the handler contract on chain B has a balance of 50 tokens.
1. Malicious user calls the `cross_chain_erc20_settlement` function indicating his intention to burn/lock 10 tokens on the source chain A and receive (unlock) 10 tokens on destination chain B.
2. The `CrossChainMsg` event is emitted as 10 tokens are successfully transferred from the user to handler contract (locked) on chain A.
3. Malicious validator, scans the event, and invokes `receive_cross_chain_msg` to transfer 10 tokens from handler (unlock) to the user on chain B. 
This would write the transaction status `CrossChainMsgStatus` as `SUCCESS` or `FAILED`.
4. Due to the lack of checks for `CrossChainMsgStatus`, after the tokens are transferred(unlocked), instead of invoking `receive_cross_chain_callback`, validator calls `receive_cross_chain_msg` function 4 times more stealing the other 40 tokens from the handler. Validators can repeat calling this function and minting the tokens on destination chain as long as the token balance of handler contract on chain B allows to.

## Recommended Mitigation Steps
Add proper message status checks to the `receive_cross_chain_msg` function in `settlement.cairo` contract allowing to only process messages with status `PENDING`. For instance, add the below line of code before signature verifications in `receive_cross_chain_msg`:
```cairo
    assert(self.received_tx.read(cross_chain_msg_id).tx_status == CrossChainMsgStatus::PENDING, 'msg status error');
```
