# Vulnerability details

## Impact
The `ChakraSettlement::processCrossChainCallback` will be monitored off-chain and invoked, it takes status as argument which can be either `Sucess` or `Failed`. The problem is that if the transaction has to be rejected for some reason and the status should be set to `Failed` the user will have no way in returning his tokens back. They will just remain stuck in the `ChakraSettlementHandler`. The status has number of reasons for it to be set to `Failed`, for example the protocol team might decide to pause their bridge because of emergency and just send `Failed` status to every new transaction. 

## Proof of Concept

This is the `processCrossChainCallback()`

```solidity

function processCrossChainCallback(
        uint256 txid,
        string memory from_chain,
        uint256 from_handler,
        address to_handler,
        CrossChainMsgStatus status,
        uint8 sign_type,
        bytes calldata signatures
    ) internal {
        require(
            create_cross_txs[txid].status == CrossChainMsgStatus.Pending,
            "Invalid transaction status"
        );

        if (
            ISettlementHandler(to_handler).receive_cross_chain_callback(
                txid,
                from_chain,
                from_handler,
                status,
                sign_type,
                signatures
            )
        ) {
            create_cross_txs[txid].status = status;
        } else {
            create_cross_txs[txid].status = CrossChainMsgStatus.Failed;
        }
    }

```

Once the transaction's status is set to `Failed` it can no longer be changed and can't proceed further so the user will just lose his tokens

## Tools Used
Manual review

## Recommended Mitigation Steps
Implement a functionality in the `ChakraSettlementHandler.sol` that gives the user an option if his tx has status `Failed` to get back his tokens on the current chain
