# Vulnerability details

## Impact
Signature malleability allows an attacker to modify a valid ECDSA signature in such a way that the signature remains valid, but the transaction details (like recipient address or amount) could be altered. This could result in unauthorized transactions being processed on the settlement contract, potentially causing serious security risks, including unauthorized asset transfers, replay attacks, or double-spending.

## Proof of Concept
The ECDSA key recovery mechanism is not inherently resistant to signature malleability. Without additional checks, an attacker could submit a modified signature that is still considered valid by the protocol. In cross-chain setups, this could allow replay attacks or double-signing of transactions.

Example: An attacker submits a transaction from Chain A to Chain B with a valid signature, then modifies the signature to replay the same transaction on Chain C, resulting in duplicated transfers or unauthorized asset minting.

## Tools Used
1. Cryptographic Verification Tools: Using libsecp256k1 or OpenZeppelin’s ECDSA libraries to verify non-malleability in signatures.
2. Static Analysis: MythX for detecting malleability weaknesses in signature handling.
3. Unit Testing: StarkNet testing framework to simulate signature replay and tampering attempts.
## Recommended Mitigation Steps
1. Enforce stricter checks on the ECDSA signature verification process, ensuring non-malleability by rejecting signatures where the S-value is greater than half of the curve order.
2. Implement a test case to verify that modified signatures (even if syntactically valid) are rejected.
3. Use fuzz testing to evaluate different edge cases for signatures.
4. Consider switching to EdDSA for improved cryptographic security, as it natively avoids malleability issues.
