# Vulnerability details

### Description:
The `txid` (transaction ID) is generated using the `keccak256` hash function, a cryptographic hash function that maps an arbitrary amount of input data into a fixed-length output of 256 bits. While this ensures a unique output for different inputs, the large input space and repetitive parameters in the input to `keccak256` open up the possibility of a **birthday attack**, where two different inputs generate the same hash output.

The birthday attack exploits the **birthday paradox**, which reduces the complexity of finding a hash collision from `2^256` to approximately `2^128`, making collisions significantly more feasible with enough attempts.

### Code Snippet:
```solidity
uint256 txid = uint256(
    keccak256(
        abi.encodePacked(
            contract_chain_name, // from chain
            to_chain,
            from_address, // msg.sender address
            from_handler, // settlement handler address
            to_handler,
            nonce_manager[from_address]
        )
    )
);
```

### Expected Behavior:
The `txid` generated for each cross-chain transaction should be unique, ensuring that no two transactions collide and share the same `txid`. This uniqueness guarantees that every transaction is properly isolated and can be tracked independently, as `keccak256` produces a seemingly random, evenly distributed 256-bit output for distinct inputs.

### Actual Behavior:
Due to the principles of the **birthday paradox**, there is a non-negligible chance of hash collisions, even though `keccak256` produces 256-bit outputs. Given enough transactions, the probability of two different sets of inputs resulting in the same hash (`txid`) increases. This would allow an attacker to maliciously craft different inputs that result in the same `txid`, potentially overwriting or duplicating transactions in the `create_cross_txs` mapping.

#### **Birthday Paradox Breakdown:**
The probability \(P\) of a collision after \(n\) attempts (transactions in this case) can be approximated using the formula:
\[
P \approx 1 - e^{-\frac{n^2}{2m}}
\]
Where:
- \(n\) is the number of attempts (i.e., the number of transactions).
- \(m = 2^{256}\) is the number of possible outputs of `keccak256`.

For example, after **2^128** transactions, the probability of a collision becomes significant (about 50%). This means even with a small fraction of the possible transaction space, the chances of a collision increase rapidly due to the square nature of the birthday paradox. With a high-volume cross-chain system, the probability of hash collisions grows over time.

### Impact of Collisions:
1. **Overwritten Transactions**: The contract could overwrite an existing transaction in the `create_cross_txs` mapping, leading to data corruption or incorrect state transitions.

### Mitigation for the Birthday Attack:
To prevent a birthday attack, it's important to add more **entropy** to the input data passed into `keccak256`. The current `abi.encodePacked` structure uses several deterministic parameters (e.g., chain names and addresses), which may not change frequently between transactions. Adding additional, unpredictable data like the block timestamp or transaction gas limit can help prevent hash collisions by increasing the input's variability.

#### Mitigated Code Snippet:
```solidity
uint256 txid = uint256(
    keccak256(
        abi.encodePacked(
            contract_chain_name, 
            to_chain,
            from_address, 
            from_handler, 
            to_handler,
            nonce_manager[from_address],
            block.timestamp,  // Adding block timestamp for more uniqueness
            block.gaslimit     // Adding gas limit to increase randomness
        )
    )
);
```
