# Vulnerability details

## Impact

In the current implementation of `ChakraSettlementHandler`, there is a function `cross_chain_erc20_settlement()` that serves as entry point for user cross-chain transactions. There are also different settlement modes for token operations. The problem is that `MintBurn` mode is incorrectly handled as the tokens are first minted on the destination chain and not burnt on the source chain.

## Proof of Concept

Take a look at `cross_chain_erc20_settlement()` functionality:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/ChakraSettlementHandler.sol#L123-131
```
 if (mode == SettlementMode.MintBurn) {
            _erc20_lock(msg.sender, address(this), amount);
        } else if (mode == SettlementMode.LockUnlock) {
            _erc20_lock(msg.sender, address(this), amount);
        } else if (mode == SettlementMode.LockMint) {
            _erc20_lock(msg.sender, address(this), amount);
        } else if (mode == SettlementMode.BurnUnlock) {
            _erc20_burn(msg.sender, amount);
        }
```

As you can see, when the mode is `MintBurn`, the following function is called:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/ChakraSettlementHandler.sol#L244-246
```
function _erc20_lock(address from, address to, uint256 amount) internal {
        _safe_transfer_from(from, to, amount);
    }
```

So the tokens are just transferred to the contract imitating `LockUnlock` operation instead of burning tokens on the source chain and minting them on the destination chain:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/ChakraSettlementHandler.sol#L229-236
```
  function _erc20_burn(address account, uint256 amount) internal {
        require(
            IERC20(token).balanceOf(account) >= amount,
            "Insufficient balance"
        );

        IERC20Burn(token).burn_from(account, amount);
    }

```

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/ChakraSettlementHandler.sol#L225-227
```
  function _erc20_mint(address account, uint256 amount) internal {
        IERC20Mint(token).mint_to(account, amount);
    }

```

This leads to a potential DoS or malicious minting as the message can be delivered on the destination chain and not burnt on the source chain if the `receive_cross_chain_callback()` fails, for instance. This would put the protocol in an undesired state when there are tokens minted on the destination chain but not minted on the source chain.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Burn tokens first on the source chain and mint on the destination chain.
