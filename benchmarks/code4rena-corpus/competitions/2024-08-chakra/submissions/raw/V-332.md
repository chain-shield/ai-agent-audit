# Vulnerability details

## Impact
A mismatch risk occurs when the verification process allows validators' signatures to be incorrectly matched to unrelated transactions or data, potentially authorizing incorrect or malicious actions. This can lead to serious security vulnerabilities, where an attacker could manipulate the verification process by associating signatures with the wrong transactions, allowing unauthorized actions or bypassing multi-signature requirements.
The mismatch risk can arise due to inadequate or inconsistent validation of the relationship between signatures and the messages they are intended to authenticate. Without ensuring that each signature is correctly tied to its associated transaction or payload, the system is susceptible to exploitation.

## Proof of Concept
The `verifyECDSA` function processes a set of signatures without fully verifying that each signature belongs to the correct transaction or validator context:
```solidity
function verifyECDSA( 
        bytes32 msgHash,
        bytes calldata signatures 
    ) internal view returns (bool) { 
        require(
            signatures.length % 65 == 0,
            "Signature length must be a multiple of 65"
        );

        uint256 len = signatures.length;
        uint256 m = 0;
        for (uint256 i = 0; i < len; i += 65) {
            bytes memory sig = signatures[i:i + 65];
            if (
                validators[msgHash.recover(sig)] && ++m >= required_validators 
            ) {
                return true;
            }
        }

        return false;
    }
```
In this case:
Each signature is checked to see if it matches one of the validators.
However, there's no strict check that ensures each signature corresponds to the right validator or is correctly tied to the current transaction (i.e., msgHash). This opens up the possibility of a mismatch, where signatures may be counted toward validation even though they don't belong to the intended message or transaction.
Vulnerability Scenario:
Assume that Transaction A requires signatures from Validators 1, 2, and 3.
Validator 1 signs Transaction A, but their signature is mistakenly or maliciously associated with a different transaction (Transaction B).
Transaction B now appears to have a valid signature from Validator 1, even though they did not authorize it, leading to unauthorized approval.

## Tools Used
Manual Review

## Recommended Mitigation Steps
To mitigate the mismatch risk, implement stricter checks to ensure that each signature is correctly associated with its corresponding message and validator. Ensure that signatures are explicitly tied to specific validators by tracking which signature belongs to which validator and verifying this association.
