# Vulnerability details

## Impact

The `receive_cross_chain_msg` function in the `ChakraSettlement` contract lacks proper access control for validators. An attacker can front-run the validator's call with their valid signatures and call `receive_cross_chain_msg` with his own address to steal tokens.

*Note that the same issue persists in the Cairo code.*

```js
    if (payload_type == PayloadType.ERC20) {
        // Cross chain transfer
        {
            // Decode transfer payload
            ERC20TransferPayload memory transfer_payload = codec.deocde_transfer(msg_payload);

            if (mode == SettlementMode.MintBurn) {

                return true;
            }
            // ...
        }

```

The problem is that the code above lacks access control to ensure the caller is indeed a validator, we demonstrate in the next section a viable exploit scenario to steal innocent Alice funds.

## Proof of Concept

Here's the scenario to illustrate:

- Alice initiates a cross-chain transfer of 100 tokens from Chain A to Chain B.
- Validators observes Alice's transaction and prepares to call `receive_cross_chain_msg` on Chain B with enough valid signatures.
- Bob, a malicious actor, monitors the mempool for the validator's transaction.
- Bob frontruns the validator's transaction, calling `receive_cross_chain_msg` with the same valid signatures but replacing `payload.to` with his own address.
- Bob's transaction is processed first, minting or unlocking the tokens to his address, Bob has successfully stole innocent Alice's tokens.
