# Vulnerability details

## Impact
Detailed description of the impact of this finding.
Title: SettlementSignatureVerifier contract has a Missing Protection against Signature Replay Attacks in msgHash
•	Severity: Medium
•	Impact: The SettlementSignatureVerifier contract currently lacks measures to protect against signature replay attacks.
•	Status: Unresolved
•	File: SettlementSignatureVerifier.sol
•	Lines Affected: 193-214

The SettlementSignatureVerifier contract currently lacks measures to protect against signature replay attacks. Specifically, the verify and verifyECDSA functions rely solely on the msgHash for signature verification. Without incorporating additional context, such as a nonce or unique message identifier, the same signature can be reused across multiple different transactions, leading to potential security vulnerabilities.

Without protection against replay attacks, an attacker could reuse a valid signature from a previously signed transaction to authorize unintended transactions. This could result in unauthorized actions being performed, such as unauthorized transfers, approvals, or any other actions that are gated by the signature verification process.

Consider the following scenario:

1. A validator signs a message hash msgHash for a transaction.
2. The transaction is successfully processed.
3. An attacker captures the signature and the corresponding msgHash.
4. The attacker then replays this signature with the same msgHash in a different context, potentially causing unintended actions.
```sol
// Original Transaction
bytes32 msgHash = keccak256(abi.encodePacked(transactionDetails));

// Verification and execution of the first transaction

// Replay Attack
// The attacker reuses the same msgHash and signature for a different transaction
require(verify(msgHash, signature, 0));  // returns true and the replayed transaction is executed
```

## Recommended Mitigation Steps
To mitigate this issue, a nonce or unique identifier should be included in the message hash that is signed and subsequently verified. This nonce should be unique for each transaction to prevent the reuse of signatures in different contexts.

Coded Mitigation

1. Introduce a Nonce Mechanism:
• Add a nonce for each validator to track the number of transactions they have authorized.
• Include the nonce in the msgHash generation to ensure each signature is unique to a specific transaction.

2. Update the verify and verifyECDSA functions to incorporate the nonce:
```sol
// Mapping to store nonces for validators
mapping(address => uint256) public validatorNonces;

function verify(
    bytes32 msgHash,
    bytes calldata signatures,
    uint8 sign_type
) external view returns (bool) {
    if (sign_type == 0) {
        return verifyECDSA(msgHash, signatures);
    } else {
        return false;
    }
}

function verifyECDSA(
    bytes32 msgHash,
    bytes calldata signatures
) internal view returns (bool) {
    require(
        signatures.length % 65 == 0,
        "Signature length must be a multiple of 65"
    );

    uint256 len = signatures.length;
    uint256 m = 0;
    for (uint256 i = 0; i < len; i += 65) {
        bytes memory sig = signatures[i:i + 65];
        address signer = msgHash.recover(sig);
        bytes32 nonceHash = keccak256(abi.encodePacked(msgHash, validatorNonces[signer]));

        if (
            validators[signer] && ++m >= required_validators && msgHash == nonceHash
        ) {
            return true;
        }
    }

    return false;
}

function incrementNonce(address validator) external onlyOwner {
    validatorNonces[validator]++;
}
```
In this mitigation, every time a message is signed, it includes the validator’s current nonce, which is unique to each transaction. After a transaction is verified, the nonce is incremented to ensure that the same signature cannot be reused.
