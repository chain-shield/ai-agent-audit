# Vulnerability details

## Impact

Cross-chain tx do not enforce order (`nonce`), making them vulnerable to block reorgs.

## Proof of Concept

Every cross-chain tx starts via `Handler.cross_chain_erc20_settlement()` and the `CrossChainMsg` event emitted by `Settlement.send_cross_chain_msg()` is what validators will watch for to continue the flow on the destination chain.

```solidity
function send_cross_chain_msg(
    string memory to_chain,
    address from_address,
    uint256 to_handler,
    PayloadType payload_type,
    bytes calldata payload
) external {
    require(msg.sender == handler, "Not Handler");

    nonce_manager[from_address] += 1;

    address from_handler = msg.sender;

    uint256 txid = uint256(
        keccak256(
            abi.encodePacked(
                contract_chain_name, // from chain
                to_chain,
                from_address, // msg.sender address
                from_handler, // settlement handler address
                to_handler,
                nonce_manager[from_address]
            )
        )
    );

    create_cross_txs[txid] = CreatedCrossChainTx(
        txid,
        contract_chain_name,
        to_chain,
        from_address,
        from_handler,
        to_handler,
        payload,
        CrossChainMsgStatus.Pending
    );

    emit CrossChainMsg(
        txid,
        from_address,
        contract_chain_name,
        to_chain,
        from_handler,
        to_handler,
        payload_type,
        payload
    );
}
```

But all these cross-chain tx have no enforced parameter like `nonce` to order them, ensuring that the first created will be the first processed.

This will not guarantee that if user A deposits X amount of `USDC` to Polygon, he will be the one to receive it on Optimism if another user also transfers the same shortly after him, but his event is processed first.

Although, if validators execute all transactions in their event broadcast order based on the blockchain explorer, in case of block reorganizations the user tx will be ordered differently than the original one, and since there are no values that provide an order, the first user might not get their funds on the destination chain there aren’t enough, even if they were first.

Since the chains include Polygon, block reorgs problems are possible. Here is a proof:

Polygon: https://polygonscan.com/block/36757444/f?hash=0xf9aefee3ea0e4fc5f67aac48cb6e25912158ce9dca9ec6c99259d937433d6df8 - Dec 2022, this is with 120 blocks depth which means 4 minutes of re-written tx's since the block rate is ~2 seconds

https://protos.com/polygon-hit-by-157-block-reorg-despite-hard-fork-to-reduce-reorgs/ - February 2023, 157 blocks depth.

We can also observe the LayerZero idea for the same type of protocol (cross-chain infrastructure contracts). They always use a `nonce` for all their events to ensure that the logic in the destination chains is in the same sequence as it was initiated in the source chain - https://github.com/LayerZero-Labs/LayerZero/blob/a1fb11a3b9c0ac449291816e71eacede4e36613e/contracts/Endpoint.sol#L94, https://github.com/LayerZero-Labs/LayerZero/blob/a1fb11a3b9c0ac449291816e71eacede4e36613e/contracts/UltraLightNodeV2.sol#L135

> ***NOTE:** Everything described above also applies to the Cairo part and the problem should be fixed there also.*
>

## Recommended Mitigation Steps

Include a `nonce` in the events to ensure they are executed in the same way as in the source chain.
