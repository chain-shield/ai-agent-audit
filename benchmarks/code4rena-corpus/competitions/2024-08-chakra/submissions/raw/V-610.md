# Vulnerability details

## Impact

Reusing a valid signature can be verified by multiple signatures, resulting in all funds in the contract being transferred
In the `check_chakra_signatures` function, there is a vulnerability in the signature verification process. The function does not ensure that each signature is unique and from different validators. This oversight could allow an attacker to reuse a valid signature, resulting in multiple signature verification passes. An attacker can repeatedly submit the same signature, and the system will mistakenly think that multiple validators have signed the transaction, thereby bypassing the required number of unique validator signatures.

The vulnerability in the signature verification process is located in the `check_chakra_signatures` method, which is called in two key methods: `receive_cross_chain_msg` and `receive_cross_chain_callback`. These two methods are critical when processing cross-chain transactions to ensure that cross-chain messages and callbacks are verified by a sufficient number of validator signatures.

If signature uniqueness is not enforced, an attacker can reuse the same valid signature and pass verification multiple times. The specific impact is as follows:

1. **`receive_cross_chain_msg`**: This method handles cross-chain messages. If signature verification can be bypassed through duplicate signatures, attackers can inject forged messages, resulting in unauthorized asset transfers, which can ultimately lead to a complete loss of funds or approval of malicious transactions.For example, this method can call handler.receive_cross_chain_msg(cross_chain_msg_id, from_chain, to_chain, from_handler, to_handler, payload) to transfer all funds.
2. **`receive_cross_chain_callback`**: This method handles the callback for cross-chain transactions. If signature verification is bypassed, attackers may forge callbacks to mark the transaction status as "successful" even if the transaction is not actually completed. This may lead to incorrect cross-chain transaction settlement, double spending, or the completion of invalid transactions.

### Consequences:

- **Fund loss**: An attacker can exploit the `receive_cross_chain_msg` method to process forged transactions, resulting in unauthorized transfers of assets across chains or contracts.
- **Double spending**: By exploiting the `receive_cross_chain_callback` method, an attacker can forge the transaction completion status, causing the system to release assets for the same transaction multiple times.
- **Network-wide impact**: Since cross-chain transactions usually involve multiple blockchain systems, this vulnerability may lead to cascading failures within the multi-chain system or a large-scale loss of funds.

In the following code, the `check_chakra_signatures` method does not check whether the signature is from a unique verifier:

```
        // validate signatures should > required_validators_num
        // @param message_hash the perdsen hash of message 
        // @param the signatures corresponding to each verifier

        fn check_chakra_signatures(
            self: @ContractState, message_hash: felt252, signatures: Array<(felt252, felt252, bool)>
        ){
            let mut pass_count = 0;
            let mut i = 0;
            loop {
                if i > signatures.len()-1{
                    break;
                }
                let (r,s,y) = * signatures.at(i);
                let pub_key: felt252 = recover_public_key(message_hash,r,s,y).unwrap();
                if self.chakra_validators_pubkey.read(pub_key) > 0{
                    pass_count += 1;
                }
                i += 1;
            };
            assert(pass_count >= self.required_validators_num.read(), 'Not enough validate signatures');
        }
```

The `check_chakra_signatures` method increments `pass_count` each time it verifies a signature, but does not ensure that each signature comes from a different verifier. If the same signature is submitted multiple times, the function will still consider it valid, resulting in an inaccurate `pass_count` count.

In the following code snippet, `check_chakra_signatures` is called by `receive_cross_chain_msg` and `receive_cross_chain_callback`, but the function does not ensure that each signature is unique.

## Recommended Mitigation Steps

1. **Enforce unique validator signatures**: Modify the `check_chakra_signatures` method to ensure that each validator can only contribute one valid signature per transaction. This can be achieved by maintaining a record of validators that have been credited with signatures, ensuring that duplicate signatures are not accepted.
2. **Add signature uniqueness check**: In the `check_chakra_signatures` method, add logic to track which public keys have signed, ensuring that the same public key cannot sign the same transaction multiple times.
