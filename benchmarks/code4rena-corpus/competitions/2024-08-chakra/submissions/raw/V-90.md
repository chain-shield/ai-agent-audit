# Vulnerability details

## Summary
The `cross_chain_erc20_settlement` function `ChakraSettlementHandler` , has inadequate input validation for the critical parameter. This oversight could lead to the processing of invalid or malicious inputs, potentially causing unexpected behaviour, contract state inconsistencies, or vulnerabilities in the cross-chain transaction process.

## Vulnerability Details
The cross_chain_erc20_settlement function in `ChakraSettlementHandler` and related functions in other contracts lack comprehensive validation for the main input parameter.

Chain Name: No validation against a list of known or allowed chains.

```solidity
function cross_chain_erc20_settlement(
    string memory to_chain,
    uint256 to_handler,
    uint256 to_token,
    uint256 to,
    uint256 amount
) external {
    // ... (token locking/burning logic)

    nonce_manager[msg.sender] += 1;

    // Create a new cross chain tx
    uint256 txid = uint256(
        keccak256(
            abi.encodePacked(
                chain,
                to_chain,
                msg.sender,
                address(this),
                to_handler,
                nonce_manager[msg.sender]
            )
        )
    );

    // ... (create cross-chain transaction record)

    settlement.send_cross_chain_msg(
        to_chain,
        msg.sender,
        to_handler,
        PayloadType.ERC20,
        cross_chain_msg_bytes
    );
}
```

```solidity
function send_cross_chain_msg(
    string memory to_chain,
    address from_address,
    uint256 to_handler,
    PayloadType payload_type,
    bytes calldata payload
) external {
    // ... (create cross-chain message record)

    emit CrossChainMsg(
        txid,
        from_address,
        contract_chain_name,
        to_chain,
        from_handler,
        to_handler,
        payload_type,
        payload
    );
}
```

- No Chain ID Validation: There is no explicit validation of the to_chain parameter in either cross_chain_erc20_settlement or send_cross_chain_msg.
- Message Creation: The cross-chain message is created and an event is emitted - 
  regardless of the validity of the to_chain.
- Transaction Status: The status of the transaction is set to CrossChainTxStatus.Pending in create_cross_txs.
- Execution Continuation: The execution does not stop or revert based on the chain ID validity.


## Impact

- Message in Limbo: The cross-chain message will be created and remain in a pending state indefinitely, as there's no mechanism to validate or process messages for non-existent chains.
- Potential Token Lock: In lock/mint modes, tokens will be locked in the contract without the possibility of being unlocked on the non-existent destination chain.
- Potential Token Burn: In burn/mint modes, tokens will be burned on the source chain without the possibility of being minted on the non-existent destination chain.
- No Recovery options: There's no mechanism to detect and handle messages sent to invalid chains.

## Recommended Mitigation Steps
This can be prevented by implementing a mapping for valid chains and check the input chain id against it.

```solidity

mapping(string => bool) public validChains;

function validateChain(string memory _chain) internal view {
    require(validChains[_chain], "Invalid destination chain");
}

```
