# Vulnerability details

## Impact
Signatures in `ChakraSettlement::verifySignature()` can be easily replayed because the message hash does not include a nonce and also the check for the `required_validators` can be bypassed by a malicious user who will just get a valid signature from the mempool and pass it multiple times in the `signatures` bytes array

```solidity
 function verifySignature(
        uint256 txid,
        uint256 from_handler,
        address to_handler,
        CrossChainMsgStatus status,
        uint8 sign_type,
        bytes calldata signatures
    ) internal view {
        
>>      bytes32 message_hash = keccak256(
>>          abi.encodePacked(txid, from_handler, to_handler, status)
        );

        require(
            signature_verifier.verify(message_hash, signatures, sign_type),
            "Invalid signature"
        );
    }

```

## Proof of Concept
A malicious user can just monitor the mempool and when he sees a valid signature he can just get it and use it. 
He will then get the arguments and pass the same arguments to the `ChakraSettlement::receive_cross_chain_callback()` to generate the same `message_hash` to sign the message with someone else signature. The `verifySignature()` takes an array of signatures and verifies them. In order for it to pass the `SettlementSignatureVerifier::verify()` must return true. The other problem is that the `SettlementSignatureVerifier::verifyECDSA` does not check if a signature has been used or not. The same signature can be passed multiples times in the signatures bytes array and the check for the `required_validators` will be bypassed

```solidity

function verifyECDSA(
        bytes32 msgHash,
        bytes calldata signatures
    ) internal view returns (bool) {
       
        require(
            signatures.length % 65 == 0,
            "Signature length must be a multiple of 65"
        );

        uint256 len = signatures.length;
        uint256 m = 0;
        for (uint256 i = 0; i < len; i += 65) {
            bytes memory sig = signatures[i:i + 65];
            if (              
>>              validators[msgHash.recover(sig)] && ++m >= required_validators
            ) {
                return true;
            }
        }
       
    }

```

This way a malicious user can just sign a message with someone else signature. Also if there is a scenario where the transaction should revert because the `required_validators` are not enough the attacker will be able to bypass it because he will pass a valid signature multiple times and he will be able to sign the message.

## Tools Used
Manual review

## Recommended Mitigation Steps
Add nonce to the `message_hash` and also add a mapping in the `SettlementSignatureVerifier.sol` that tracks which signature is used so a single signature cannot be passed multiple times to bypass the check for the `required_validators`
