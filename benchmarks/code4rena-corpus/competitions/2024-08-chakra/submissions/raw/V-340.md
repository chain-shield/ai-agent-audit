# Vulnerability details

## Impact
The `SettlementSignatureVerifier` contract performs signature verification using the `verifyECDSA` function. While this approach ensures the integrity of transactions, it could become computationally intensive and inefficient as the number of signatures increases. Each signature is verified in a loop, and the length of the signature array directly impacts the gas cost of execution.
In Ethereum and other EVM-based chains, gas cost is a critical consideration. The current implementation could result in significant gas costs for transactions with a large number of signatures. Furthermore, the increased computational load could lead to transaction failures due to exceeding gas limits, especially when validators are many or when used in conjunction with other on-chain operations.

## Proof of Concept
The current signature verification logic in the [`verifyECDSA`](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/settlement/contracts/SettlementSignatureVerifier.sol#L193-L214) function loops through each 65-byte signature and checks if it was signed by a validator. Here is the function in question:
```solidity
    function verifyECDSA(
        bytes32 msgHash,
        bytes calldata signatures
    ) internal view returns (bool) {
        require(
            signatures.length % 65 == 0,
            "Signature length must be a multiple of 65"
        );


        uint256 len = signatures.length;
        uint256 m = 0;
        for (uint256 i = 0; i < len; i += 65) {
            bytes memory sig = signatures[i:i + 65];
            if (
                validators[msgHash.recover(sig)] && ++m >= required_validators
            ) {
                return true;
            }
        }


        return false;
    }
```
The loop runs over the length of the signatures array, and for each 65-byte segment (the length of a standard ECDSA signature), the `recover()` function is called to extract the signer’s address. This process is repeated until the required number of validators has been met.While this works for a small number of validators, the gas cost scales linearly with the number of signatures. The more signatures you have, the more expensive the function becomes due to the repeated use of `recover()`. For a large number of signatures, the function could become prohibitively expensive, leading to higher transaction fees or even out-of-gas errors.

## Recommended Mitigation Steps
Consider breaking down the signature verification process into multiple transactions or batches. This allows you to avoid exceeding gas limits for transactions involving a large number of validators. However, this may introduce complexity in managing multiple transactions.
