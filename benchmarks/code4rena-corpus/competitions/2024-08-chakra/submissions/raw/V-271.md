# Vulnerability details

## Impact
In the current implementation there is no checks to make sure that the payload used is unique and has not already been used. it is important to verify the uniqueness of the payload when processing cross-chain messages. As a result, the same payload could be reused across different transactions, leading to potential replay attacks. 

The current txid generation logic omits the `payload_type` and `payload` fields, which can lead to potential issues:

The absence of `payload_type` and `payload` in the txid hash makes the system susceptible to replay attacks or message forgery, where an attacker might reuse an old message with altered payloads, bypassing checks and causing unintended consequences. The txid should uniquely identify the cross-chain message, including its content. By not incorporating the payload, it becomes harder to trace accurate txids

```javascript
  uint256 txid = uint256(
            keccak256(
                abi.encodePacked(
                    contract_chain_name, // from chain //
                    to_chain,
                    from_address, // msg.sender address
                    from_handler, // settlement handler address
                    to_handler,
                    nonce_manager[from_address]
                )
            )
        );
```

## Proof of Concept
Imagine a scenario where an attacker intercepts a cross-chain message and modifies its payload before resending it.

- Original Message:

```
contract_chain_name = "ChainA"
to_chain = "ChainB"
from_address = 0x123
from_handler = 0xABC
to_handler = 0xDEF
nonce = 1
payload_type = 1
payload = "Send 100 tokens"
```

- Attacker's Modified Message:

```
contract_chain_name = "ChainA"
to_chain = "ChainB"
from_address = 0x123
from_handler = 0xABC
to_handler = 0xDEF
nonce = 1
payload_type = 1
payload = "Send 1000 tokens"
```

The txid serves as a unique identifier for the transaction. If the payload and payload_type are not included in the txid, two different messages (with different payloads) could end up generating the same txid. This can lead to issues where one transaction could be mistaken for another, especially if an attacker intercepts and modifies a message. An attacker could use old message by changing its payload. Since the txid would be the same as the original message, the receiving contract might process the altered message as if it were the original

## Recommended Mitigation Steps
Modify the txid generation logic to include both `payload_type` and `payload` in the hash. This ensures that even if all other parameters are the same, different payloads will generate unique txids.

Updated txid Calculation:

```javascript
uint256 txid = uint256(
    keccak256(
        abi.encodePacked(
            contract_chain_name,
            to_chain,
            from_address,
            from_handler,
            to_handler,
            nonce_manager[from_address],
            payload_type,
            payload
        )
    )
);
```
