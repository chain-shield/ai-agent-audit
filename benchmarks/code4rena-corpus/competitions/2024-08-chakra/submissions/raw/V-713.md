# Vulnerability details

### Summary
The `ChakraSettlement` and `ChakraSettlementHandler` contracts facilitate cross-chain transactions by managing the sending and receiving of messages between different blockchain networks. These contracts maintain mappings of created and received cross-chain transactions and emit events to signal the status of these transactions. Block reorgs can disrupt this process, leading to inconsistencies or failures in the cross-chain transactions.

### Vulnerability Details
Block reorganization (block reorg) occurs when a blockchain network replaces a portion of its chain with a new chain of greater length. This can happen due to simultaneous block mining by different miners or other network conditions. When a block reorg occurs, transactions in the replaced blocks may be invalidated or duplicated, leading to potential issues in the cross-chain transaction process.

- `ChakraSettlement`: `send_cross_chain_msg`, `receive_cross_chain_msg`, `receive_cross_chain_callback`
- `ChakraSettlementHandler`: `cross_chain_erc20_settlement`, `receive_cross_chain_msg`, `receive_cross_chain_callback`

<details>

<summary>POC</summary>

1. A user initiates a transfer, and the transaction is included in Block A.
The cross_chain_erc20_settlement function locks the tokens and emits a CrossChainLocked event.


2. The cross_chain_erc20_settlement function calls the send_cross_chain_msg function.
The send_cross_chain_msg function generates a transaction ID (txid) and emits a CrossChainMsg event.

3. Block Reorg Occurs
A competing chain with Block B replaces Block A.
The transaction from Block A is invalidated and not included in Block B.

4. Event Scanning (Step 3)
The Chakra Validators initially detect the CrossChainMsg event from Block A.
Due to the reorg, the event is lost, and the validators do not detect it in Block B.

Receiving Cross-Chain Message (Step 4)
Since the event is lost, the receive_cross_chain_msg function is not invoked on the destination chain.
The tokens are not transferred, and the transaction remains incomplete.

6. Callback Handling (Steps 6 and 7)
Since the cross-chain message is not sent, the callback functions are not invoked.

The transaction status is not updated, and the user does not receive the tokens on the destination chain.
</details>


### Impact

1. **Transaction Invalidity**: If the initial transaction that invokes the cross-chain functions is part of a block that gets reorganized, the entire process could be invalidated. This means the cross-chain message may not be sent or received.
2. **Event Loss or Duplication**: Events emitted by the functions may be lost or duplicated if the block containing the transaction is reorganized. This can lead to inconsistencies in the cross-chain transaction process.
3. **Message Sending Issues**: If the message sending transaction is part of a block that gets reorganized, the message may not be sent or may be sent multiple times, leading to potential double-spending or loss of tokens.
4. **Callback Handling Issues**: If the callback transaction is part of a block that gets reorganized, the callback may not be executed or may be executed multiple times, leading to inconsistencies in the final state of the cross-chain transaction.
