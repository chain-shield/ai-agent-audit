# Vulnerability details

## Impact
The ChakraSettlementHandler contract has a vulnerability due to insufficient validation of cross-chain message handlers, enabling unauthorized access to process cross-chain messages.

**Affected Parties:**

  * The ChakraSettlementHandler contract itself
  * Users relying on the proper functioning and security of the cross-chain settlement process

**Potential Consequences:**

  * Unauthorized handlers can process cross-chain messages, leading to unintended or malicious actions
  * Compromise of the integrity and reliability of the cross-chain settlement process

## Proof of Concept
The root cause of the vulnerability lies in the `receive_cross_chain_msg` function in the `ChakraSettlementHandler.sol` contract. The function performs a check to validate if the [from_handler](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/ChakraSettlementHandler.sol#L311) is on the whitelist for the [from_chain](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/ChakraSettlementHandler.sol#L311) using the [is_valid_handler](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/ChakraSettlementHandler.sol#L311) function. However, even if the check fails, indicating an invalid handler, the function continues executing instead of immediately returning or reverting.

Affected Code: [ChakraSettlementHandler.sol#L300-L313](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/ChakraSettlementHandler.sol#L300-L313)
```solidity
// ChakraSettlementHandler.sol

function receive_cross_chain_msg(
    uint256 /**txid */,
    string memory from_chain,
    uint256 /**from_address */,
    uint256 from_handler,
    PayloadType payload_type,
    bytes calldata payload,
    uint8 /**sign type */,
    bytes calldata /**signaturs */
) external onlySettlement returns (bool) {
    //  from_handler need in whitelist
    if (is_valid_handler(from_chain, from_handler) == false) {
        return false;
    }
    // ...
}
```
To continue execution after the `is_valid_handler` check fails is a vulnerability. It allows unauthorized handlers to process cross-chain messages, violating the intended security model.

**Scenario:**

1. An attacker calls the `receive_cross_chain_msg` function with a `from_chain` and `from_handler` that is not on the whitelist.

   * `from_chain`: "chain1"
   * `from_handler`: 000 (not on the whitelist)

2. Inside the `receive_cross_chain_msg` function, the `is_valid_handler` function is called to check if the `from_handler` is on the whitelist for the` from_chain`.

3. The `is_valid_handler` function returns `false` because the `from_handler` (000) is not on the whitelist for the `from_chain` ("chain1").

4. Despite the `from_handler` being invalid the attacker's cross-chain message is processed, potentially leading to unintended or malicious actions.

Even though the `is_valid_handler` check fails, indicating that the `from_handler` is not on the whitelist, the function continues executing instead of immediately returning or reverting.

## Recommended Mitigation Steps
It is recommended to modify the receive_cross_chain_msg function to immediately return or revert when the is_valid_handler check fails. This ensures that only whitelisted handlers can process cross-chain messages. By reverting the transaction when an invalid handler is detected.

```diff
function receive_cross_chain_msg(
    uint256 /**txid */,
    string memory from_chain,

-       return false;
+       revert("Invalid handler");
    }
    // ... rest of the function ...
}
```
