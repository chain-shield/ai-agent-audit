# Vulnerability details

## Impact
Due to the lack of checks for CrossChainTxStatus, an attacker can replay a CrossChainTx, specifically one that involves burning of a users token. When a user someone uses the MintBurn mode, an attacker can monitor the chain, and reuse the ticket, until all of that user's token has been burnt.


The invariant stated in the docs (Settlement Contract) :
8. Cross-chain callbacks can only be processed for transactions that have a Pending status in the create_cross_txs mapping.

is broken

This attack can be done by another and focuses on the mode MintBurn instead
The error is in the receive_cross_chain_callback part.


## Proof of Concept




The current implementation of the receive_cross_chain_callback function does not check whether the transaction has already been settled. This can lead to a replay vulnerability, where an attacker could resend the callback and cause the same transaction to be processed multiple times, potentially resulting in unintended consequences such as multiple burns of the same tokens.

            assert(to_handler == get_contract_address(),'error to_handler');

            assert(self.settlement_address.read() == get_caller_address(), 'not settlement');

            assert(self.support_handler.read((from_chain, from_handler)) &&

How the Vulnerability Works:






1.Initial Callback: A legitimate cross-chain callback is processed, and tokens are burned based on the transaction details.

2.Malicious Resend: An attacker observes the transaction and resends the same callback with the same cross_chain_msg_id.

3.Reprocessing: Since there is no check to see if the transaction has already been settled, the contract processes the callback again, leading to additional burns of tokens.
