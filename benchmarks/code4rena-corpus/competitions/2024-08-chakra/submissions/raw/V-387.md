# ChakraSettlementHandler Vulnerability Report

## Summary

A critical Denial of Service (DoS) vulnerability has been identified in the `ChakraSettlementHandler` and `ChakraSettlement` contracts. The issue arises when the same user interacts with multiple `ChakraSettlementHandler` contracts connected to the same `ChakraSettlement` contract. Nonce mismatches between these handlers and the settlement contract lead to failed cross-chain settlement callbacks, which block further settlement operations for that user.

## Impact

The impact of this vulnerability is severe, as it results in a Denial of Service (DoS) for users interacting with multiple `ChakraSettlementHandler` contracts. Specifically, once the nonces become out of sync, no further callbacks can be processed for that user, leading to the inability to complete critical settlement operations.

## Proof of Concept

### Vulnerability Description

The vulnerability is centered around the handling of nonces for users across multiple `ChakraSettlementHandler` contracts, all interacting with the same `ChakraSettlement` contract. Each settlement transaction relies on a nonce to ensure transaction uniqueness and proper cross-chain message processing.

When the same user interacts with multiple `ChakraSettlementHandler` contracts, the nonce in `ChakraSettlement` and the individual `ChakraSettlementHandler` contracts can get out of sync. This nonce mismatch results in the generation of different `txId`s for the same transaction, depending on whether the `txId` is calculated using the nonce from `ChakraSettlement` or the specific `ChakraSettlementHandler`.

As a result, the `receive_cross_chain_callback` function will revert, preventing any further cross-chain settlement callbacks for the user.

### Steps to Reproduce

The vulnerability can be reproduced by following these steps:

1. **Initial Setup and Transaction**:

   - The user `user` performs a cross-chain ERC20 settlement through the first `ChakraSettlementHandler`.
   - The nonce in both `ChakraSettlement` and `ChakraSettlementHandler` is incremented to 1 after this transaction.

2. **Nonce Mismatch Setup**:

   - The same user interacts with a second `ChakraSettlementHandler`, performing another cross-chain ERC20 settlement.
   - The nonce in `ChakraSettlement` is incremented to 2, while the nonce in the second `ChakraSettlementHandler` remains 1.

3. **Callback Failure**:

   - The `txId` generated by `ChakraSettlement` is based on nonce 2, while the `txId` generated by the second `ChakraSettlementHandler` is based on nonce 1.
   - When calling `receive_cross_chain_callback`, the mismatched `txId`s cause a revert due to the invalid `CrossChainTxStatus` or `Invalid transaction status`.

4. **Denial of Service (DoS)**:
   - Since the nonces are out of sync, the callback function for the user `receive_cross_chain_callback` is blocked, and there is no mechanism to resynchronize the nonces.

### Code Snippet

The nonce management for `ChakraSettlement` and `ChakraSettlementHandler` uses the same mapping `nonce_manager` to track nonces for users. This design is prone to out-of-sync issues when multiple handlers interact with the same settlement contract.

```solidity
mapping(address => uint256) public nonce_manager;
```

### Recommendation

To resolve this vulnerability, nonce management should account for the specific ChakraSettlementHandler being used. Instead of a single nonce mapping, introduce a two-dimensional mapping that tracks nonces by both the user and the handler:

```solidity
mapping(address => mapping(address => uint256)) public nonce_managerConsideringHandler;
```

Then, increment the nonce based on both the user address and the handler address:

```solidity
nonce_managerConsideringHandler[from_address][from_handler] += 1;
```

This ensures that each handler maintains its own nonce for each user, preventing nonce mismatches and resolving the out-of-sync txId generation issue.
