# Vulnerability details

## Impact
The protocol supports cross-chain transfers of ERC-777 tokens through `ChakraSettlementHandler::cross_chain_erc20_settlement`, ERC-777 tokens are ERC-20 tokens also and the process will go smoothly when calling `cross_chain_erc20_settlement`. When a cross-chain message is received on the destination chain, `ChakraSettlement::receive_cross_chain_msg` is invoked to handle the transfer. The function first verifies the signatures and ensures the transaction has not been previously processed before interacting with the handler contract to execute the transfer. Finally, it updates the transaction status:

The function `ISettlementHandler(to_handler).receive_cross_chain_msg` is responsible for processing the token transfer and unlocking the tokens to the recipient:

The vulnerability lies in the fact that this process is susceptible to reentrancy attacks when handling ERC-777 tokens. Specifically, a recipient implementing the `tokensReceived` hook can repeatedly re-enter `ChakraSettlement::receive_cross_chain_msg` as long as the handler contract has sufficient balance to unlock the amount. The reentrancy is not prevented because all critical checks will pass:
1. The [signatures verification](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/settlement/contracts/ChakraSettlement.sol#L194-L196) will succeed since the parameters are public, and a malicious user monitoring the mempool can even front-run the `receive_cross_chain_msg` call by a validator.
2. The [transaction status verification](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/settlement/contracts/ChakraSettlement.sol#L199-L202) will pass because the status is not updated before the re-entrance.

This allows a malicious user to initiate an ERC-777 transfer to a contract that implements the `tokensReceived` hook, monitor the `receive_cross_chain_msg` transaction in the destination chain's mempool, obtain the necessary signatures, and front-run the `receive_cross_chain_msg` transaction with all the required parameters. This will lead to draining the protocol's funds.

## Recommended Mitigation Steps
Since the message status needs to be updated after that the handler contract processes the transfer, consider using `ReentrancyGuard` from OpenZeppeling
