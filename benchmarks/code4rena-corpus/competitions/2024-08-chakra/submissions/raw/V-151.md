# Vulnerability details


## Description

The `ERC20Handler` contract is designed to handle cross-chain ERC20 token transfers. It includes functions for initiating cross-chain settlements and handling callbacks when cross-chain transactions are completed. The [`cross_chain_erc20_settlement()` function](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/handler_erc20.cairo#L167-L232) transfers tokens from the caller to the contract's address, while the [`receive_cross_chain_callback()` function](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/handler_erc20.cairo#L138-L165) is responsible for finalizing the transaction on the source chain.

In the [`cross_chain_erc20_settlement()` function](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/handler_erc20.cairo#L167-L233), tokens are transferred from the caller to the contract's address. However, the original sender's address is not stored in the `CreatedCrossChainTx` struct. This becomes problematic in the `receive_cross_chain_callback()` function, where tokens are burned from the contract's address instead of the original sender's address. This leads to the contract holding the tokens that should have been burned, causing supply inconsistencies.

## Impact
The incorrect token burning mechanism leads to several serious consequences:
- **Token Supply Inconsistency**: The total token supply on the source chain will be higher than intended, as the original sender's tokens are not burned.
- **Potential for Theft**: If the contract owner can withdraw tokens from the contract, they could steal all tokens that should have been burned.
- **Broken Cross-Chain Mechanism**: The core principle of burning on one side and minting on the other is violated, potentially leading to inflation of the token supply across chains.

## Proof of Concept
1. **User** initiates a cross-chain transaction using `cross_chain_erc20_settlement()`, transferring tokens from their address to the contract's address.
2. The `CreatedCrossChainTx` struct does not store the original sender's address.
3. When the cross-chain transaction is completed, `receive_cross_chain_callback()` is called.
4. The function attempts to burn tokens from the contract's address instead of the original sender's address.
5. The contract ends up holding the tokens that should have been burned, leading to supply inconsistencies.

## Tools Used
Manual review

## Recommended Mitigation Steps
1.  Modify the `CreatedCrossChainTx` struct to include the original sender's address.
2. Use the stored sender's address to burn tokens in the `receive_cross_chain_callback()` function.
