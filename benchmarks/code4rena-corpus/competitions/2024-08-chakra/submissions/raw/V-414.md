# Vulnerability details


## Summary
The contract on cairo codebase contains a vulnerability in its manager management system. A compromised or malicious manager can remove all other managers, including the contract owner, effectively taking complete control of the protocol. This issue is compounded by the fact that the owner, who is initially set as a manager in the constructor, can be removed from the manager role with no mechanism to regain control.

## Impact
The vulnerability in the `ckr_btc`, `handler settlement.cairo` and `settlement settlement.cairo` contracts can have catastrophic consequences:

1. Centralization of Power: A single malicious manager can remove all other managers, centralizing all control to themselves.
2. Owner Lockout: The contract owner, despite having ownership rights, can be removed as a manager and lose the ability to perform critical management functions.
3. Protocol Hijacking: With exclusive manager rights, an attacker could manipulate all aspects of the protocol, including validator sets, cross-chain operations.
4. Irrecoverable State: Once the owner and other managers are removed, there is no mechanism to reinstate them or appoint new managers, leaving the protocol in an potentially irrecoverable state.
5. Complete System Compromise: This vulnerability essentially allows for a complete takeover of the cross-chain messaging system, potentially leading to unauthorized fund transfers, manipulated operations, and loss of trust in the entire ecosystem.
6. ERC20 Token Theft: As managers have control over the protocol, a malicious manager could potentially empty the contract of ERC20 tokens, leading to significant financial losses.
7. Signature Bypass: The ability to add or remove validators and update the threshold allows a malicious manager to bypass the Chakra signature verification process, compromising the entire security model of cross-chain operations.

## Proof of Concept
This vulnerability is present in the `ChakraSettlement` contract. Here are the relevant code snippets:

In [`ckr_btc.cairo`](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/cairo/handler/src/ckr_btc.cairo#L134-L161), [`Handler settlement.cairo`](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/cairo/handler/src/settlement.cairo#L245-L273) and [`Settlement settlement.cairo`](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/cairo/settlement/src/settlement.cairo#L246-L274).

```rust
    self.ownable.initializer(owner);
    self.chakra_managers.write(owner, 1);

```

2. Manager addition and removal functions:
```rust
fn add_manager(ref self: ContractState, new_manager: ContractAddress) -> bool {
    let caller = get_caller_address();
    assert(self.chakra_managers.read(caller) == 1, 'Caller is not a manager');
    assert(caller != new_manager, 'Caller is a manager already');
    self.chakra_managers.write(new_manager, 1);
    self.emit(ManagerAdded { operator: caller, new_manager: new_manager, added_at: get_block_timestamp() });
    return self.chakra_managers.read(new_manager) == 1;
}

fn remove_manager(ref self: ContractState, old_manager: ContractAddress) -> bool {
    let caller = get_caller_address();
    assert(self.chakra_managers.read(caller) == 1, 'Caller is not a manager');
    self.chakra_managers.write(old_manager, 0);
    self.emit(ManagerRemoved { operator: caller, old_manager: old_manager, removed_at: get_block_timestamp() });
    return self.chakra_managers.read(old_manager) == 0;
}
```

3. Critical functions controlled by managers:

In `ckr_btc.cairo`, the malicious manager can arbitrarily add or remove operator:
```rust
fn add_operator(ref self: ContractState, new_operator: ContractAddress) -> bool {
    let caller = get_caller_address();
    assert(self.chakra_managers.read(caller) == 1, Errors::NOT_MANAGER);

    return self.chakra_operators.read(new_operator) == 1;

fn remove_operator(ref self: ContractState, old_operator: ContractAddress) -> bool {
    let caller = get_caller_address();
    assert(self.chakra_managers.read(caller) == 1, Errors::NOT_MANAGER);
    assert(self.chakra_operators.read(old_operator) == 1, Errors::NOT_OPERATOR);
    self.chakra_operators.write(old_operator, 0);
    self.emit(OperatorRemoved { old_operator: old_operator, removed_at: get_block_timestamp() });
    return self.chakra_operators.read(old_operator) == 0;
}
```

4. Function to update required validators number:
```rust
fn set_required_validators_num(ref self: ContractState, new_num: u32) -> u32 {
    let caller = get_caller_address();
    assert(self.chakra_managers.read(caller) == 1, 'Caller is not a manager');
```

Exploit Scenario:
1. A malicious actor gains manager status (either by being appointed or by compromising an existing manager's keys).
2. The malicious manager calls `remove_manager` for all other managers, including the owner.
3. The malicious manager now has exclusive control over all manager functions, including:
   - Managing operators (adding an infinite number or removing all of them)
   - Updating the required validators number to bypass signature checks
   - Potentially manipulating cross-chain messages to steal ERC20 tokens
4. The owner, despite retaining ownership, cannot add new managers or remove the malicious manager.

## Recommended Mitigation Steps

1. Separate Owner and Manager Roles:
   ```rust
   fn remove_manager(ref self: ContractState, old_manager: ContractAddress) -> bool {
       let caller = get_caller_address();
       assert(caller == self.ownable.owner(), 'Only owner can remove managers');
       assert(old_manager != self.ownable.owner(), 'Cannot remove owner as manager');
       self.chakra_managers.write(old_manager, 0);
       self.emit(ManagerRemoved { operator: caller, old_manager: old_manager, removed_at: get_block_timestamp() });
       return self.chakra_managers.read(old_manager) == 0;
   }
   ```

2. Implement a Two-Step Manager Removal Process:
   ```rust
   struct PendingManagerRemoval {
       manager: ContractAddress,
       proposed_by: ContractAddress,
       timestamp: u64,
   }

   // In contract storage
   pending_manager_removals: LegacyMap<ContractAddress, PendingManagerRemoval>,

   fn propose_manager_removal(ref self: ContractState, manager: ContractAddress) {
       let caller = get_caller_address();
       assert(self.chakra_managers.read(caller) == 1, 'Caller is not a manager');
       assert(manager != self.ownable.owner(), 'Cannot remove owner as manager');
       self.pending_manager_removals.write(manager, PendingManagerRemoval {
           manager: manager,
           proposed_by: caller,
           timestamp: get_block_timestamp(),
       });
   }

   fn execute_manager_removal(ref self: ContractState, manager: ContractAddress) {
       let caller = get_caller_address();
       assert(caller == self.ownable.owner(), 'Only owner can execute removal');
       let proposal = self.pending_manager_removals.read(manager);
       assert(get_block_timestamp() >= proposal.timestamp + REMOVAL_DELAY, 'Waiting period not over');
       self.chakra_managers.write(manager, 0);
       self.pending_manager_removals.write(manager, PendingManagerRemoval { manager: 0, proposed_by: 0, timestamp: 0 });
       self.emit(ManagerRemoved { operator: caller, old_manager: manager, removed_at: get_block_timestamp() });
   }
   ```

3. Ensure Owner Always Retains Manager Status:
   ```rust
   fn is_manager(self: @ContractState, manager: ContractAddress) -> bool {
       return manager == self.ownable.owner() || self.chakra_managers.read(manager) == 1;
   }
   ```

4. Implement Emergency Recovery Function:
   ```rust
   fn emergency_reset_managers(ref self: ContractState) {
       assert(get_caller_address() == self.ownable.owner(), 'Only owner can reset');
       self.chakra_managers.write(self.ownable.owner(), 1);
       // Optionally, clear all other managers
       self.emit(ManagersReset { reset_by: get_caller_address(), reset_at: get_block_timestamp() });
   }
   ```

Additional Recommendations:
1. Implement multi-signature requirements for critical operations like changing the required validators number or processing large cross-chain transfers.
2. Add time-locks and/or value limits on cross-chain operations to provide a window for intervention in case of suspicious activity.
