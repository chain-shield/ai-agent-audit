There are 2 different `nonce_manager` mapping for the handler and the settlement which increments each time a user initiates a bridging.
When a message is initiated, it is first saved an instance of the `txid` computed with the handler `nonce_manager` in the `create_cross_txs` mapping of the handler contract. However, the actual `txid` that is sent thorugh the events to the other chain and returned is the `txid` computed with the `nonce_manager` of the settlement contract. So when the message comes back will call this function with the `txid` computed with the settlement's `nonce_manager`.
```
    function receive_cross_chain_callback(
        uint256 txid,
        string memory from_chain,
        uint256 from_handler,
        CrossChainMsgStatus status,
        uint8 /* sign_type */, // validators signature type /  multisig or bls sr25519
        bytes calldata /* signatures */
    ) external onlySettlement returns (bool) {
        if (is_valid_handler(from_chain, from_handler) == false) {
            return false;
        }

        require(
            create_cross_txs[txid].status == CrossChainTxStatus.Pending,
            "invalid CrossChainTxStatus"
        );

        if (status == CrossChainMsgStatus.Success) {
            if (mode == SettlementMode.MintBurn) {
                _erc20_burn(address(this), create_cross_txs[txid].amount);
            }

            create_cross_txs[txid].status = CrossChainTxStatus.Settled;
        }

        if (status == CrossChainMsgStatus.Failed) {
            create_cross_txs[txid].status = CrossChainTxStatus.Failed;
        }

        return true;
    }
```
Here we can see that it has a check that the `create_cross_txs` at the `txid` from the message has to be in PENDING state. This instance has been initialized into the PENDING state at the beggining of the bridging but with the `txid` computed of the handler contract. Hence, if there the `nonce_manager` of the handler and the settlement are different, this check will fail because the `txid` will be different and the instance will not be in PENDING state.

The issue main issue is that the `send_cross_chain_msg` function in the settlement is permissionless, anybody can call this function. The end result of this is that the `nonce_manager` of the settlement contract will increment without incrementing the handler one. Thus, since these 2 nonces will be desynced, when the targeted user will initiate a bridging, his callback will not be executed due to this difference in the `txid`. 
```
    function send_cross_chain_msg(
        string memory to_chain,
        address from_address,           <-- anybody can change the nonce of any arbitrary account
        uint256 to_handler,
        PayloadType payload_type,
        bytes calldata payload
    ) external {
        nonce_manager[from_address] += 1;

        ...
    }
```
The end result of this issue is that the callback function will fail everytime and will prevent the handler of burning the tokens for the `MintBurn` type and the final state for created transaction will not be able to be set as FAILED or SETTLED.

For the Cairo implementation there exist a similar issue but will happen most of the time and does not need to be triggered by an attacker. In this case, there are 2 different nonces, the `msg.count` for the handler contract and the `tx_count` in the settlement contract.

Since these 2 nonces are global and not specific for each user, it is really easy for them to be different. It is as easy as 2 different handlers on the same chain initiate messages. This simple fact will just make the ids to be different because in the first message, the handler will have `msg_count` of 0 and settlement `tx_count` will also be 0, but in the following messages a different handler initiates a message, now this other handler will have a `msg_count` of 0 but the `tx_count` will be 1 because of the previous message. At this point any handler will have his `msg_count` desynced with the settlement.
In the first execution when a user sends a message it will create an instance with a PENDING state and then in the callback function will have a different id (due to `msg_count` and `tx_count` discrepancy). In this case, it does not revert if the id of `created_tx` instance is not in PENDING state but creates a new instance with all its fields having 0s because the new id will be pointing into a non-existing instance but will set the state to SETTLED.

## Proof of Concept

For solidity
1. Attacker call `send_cross_chain_msg` on the solidity settlement with the `from_address` being set to the victim address
2. Anytime the victim initiates a message bridge, will not have the callback function executed

For cairo
1. A user creates a message in handler A that will interact with settlement C
2. The message callback will be executed properly
3. An other user creates a message in handler B that will interact with settlement C
4. At this point this message and the following ones will have its callback broken

## Impact
High, it prevents the burning of the tokens and setting the transaction final state for solidity and wrong `created_tx` instances for Cairo

## Tools Used
Manual review

## Recommended Mitigation Steps
I would not have 2 different nonces, having 1 in any of the contracts will prevent replaying a message properly. Also making the `send_cross_chain_msg` function of the settlement contract permissionless can lead to problems because it is only intended to be called by handlers.
