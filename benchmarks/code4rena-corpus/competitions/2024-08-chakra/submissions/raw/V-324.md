# Vulnerability details

## **Impact**
The Chakra Protocol claims to provide self-custodian staking by allowing users to stake Bitcoin without transferring assets out of their wallets. This is supposed to be achieved through time-lock scripts, which ensure that assets are not exposed to third-party risks. However, the current implementation of key cross-chain settlement functions, including `receive_cross_chain_msg`, `receive_cross_chain_callback`, and `cross_chain_erc20_settlement`, does not enforce any time-locks on assets. As a result, assets that should remain locked for a defined period can be settled or unlocked prematurely. This introduces risks of premature asset release and potential double-spending exploits, undermining the security guarantees of the protocol.

From the Chakra Documentation It states that:
- Self-custodian staking
Bitcoin enthusiasts trust in Bitcoin due to its highly decentralized nature and robust security. Consequently, the idea of compromising security to gain staking yield may be a significant concern. Our solution allows Bitcoin holders to engage in staking without transferring assets out of their own wallets. This is achieved using time-lock scripts, ensuring there's no third-party risk involved.


Here are the relevant functions in the Chakra Protocol codebase:

- [`receive_cross_chain_msg`](#): This function handles cross-chain messages and processes transfers (minting, unlocking) based on settlement modes (MintBurn, LockUnlock, etc.), but lacks any time-lock logic.
- [`receive_cross_chain_callback`](#): This function handles the callbacks from cross-chain transactions and updates the status, but also without time-lock enforcement.
- [`cross_chain_erc20_settlement`](#): This function initiates cross-chain settlement and handles locking or burning of assets based on the settlement mode, but does not implement any time-locking functionality.

In the following code snippet from the `receive_cross_chain_msg` function:

There is no mention of time-lock logic in the settlement modes (MintBurn, LockUnlock, etc.), which contradicts the protocol's claims of locking mechanisms for secure staking.

This missing functionality exposes a critical discrepancy between the expected behavior (self-custodian staking via time-lock) and the actual implementation, potentially allowing for security breaches, premature unlocking, and asset manipulation.

## **Recommended Mitigation Steps**
- Implement time-lock logic in the cross-chain settlement functions where applicable, especially in modes like `LockUnlock` and `LockMint`. Assets should remain locked for a predefined period before they can be unlocked or transferred.
- Introduce a time-lock mechanism that is integrated with the settlement mode logic to ensure that assets cannot be prematurely released, especially in self-custodian staking scenarios.
