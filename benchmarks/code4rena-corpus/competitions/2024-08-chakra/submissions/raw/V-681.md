# Vulnerability details

## Impact
A malicious/attacker validator can steal token from pool or can cause other distruption in the protcol normal working flow as the malicious/attacker validator have full control to craft any malicious message and use it over `settlement::receive_cross_chain_callback()` or `settlement::receive_cross_chain_msg()`

## Proof of Concept
The `settlement.cairo` implements internal function `check_chakra_signatures()` which is invoked/used two times during  `settlement::receive_cross_chain_msg()` and `settlement::receive_cross_chain_callback()`.
However function `check_chakra_signatures()` doesn't check for uniqueness in `signatures` array which makes it vulnerable to signatre replay attack.

The system design for Chakra protocol is that between two chains chakra validator network is involved which listen for onchain messaing event, interecpts it and  signs it then  calls the  `receive_cross_chain_callback()` or `receive_cross_chain_msg()` as per the nature of message.
These are the workings/propertise of chakra validator network as mentioned by their developer/docs.
- Anyone can permissionlessly become validator in chakra network by staking enough tokens.
- Validator network listen for `settlement::CrossChainMsg` event then calls the respective `receive_cross_chain_msg()` of the destination chain.
- Validator network also listen for `settlement::CrossChainHandleResult` event then calls the respective `receive_cross_chain_callback()` of the source chain.
- Validators are consensused, each validator performs the same operation and maintains the same state. Each round will select a proposer, and the proposer will call `receive_cross_chain_msg()` or `receive_cross_chain_callback()` depending on nature of message with message hash and signatures of all the other validator.
- Proposer is choosen from the set of validators using DPoS.
- If required number of validator is acheived onchain, the transaction is accpeted by the contract.

A malicious/attacker validator will wait for its turn to be chosen proposer to call the `receive_cross_chain_msg()`. The  malicious/attacker validator will crafts its own custom malicious message signs it, use the same signature for the `signatrues` array while calling `receive_cross_chain_msg()`.

As malicious/attacker validator will be registered onchain, so `self.chakra_validators_pubkey.read(pub_key) > 0 ` will hold true. And due to lack of uniqueness check in `signatures` array, the attacker can inflate the `pass_count` and evetually satisfy the assertion `assert(pass_count >= self.required_validators_num.read(), 'Not enough validate signatures')`.
