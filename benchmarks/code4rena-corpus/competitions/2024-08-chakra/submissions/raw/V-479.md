# Vulnerability details

## Impact
The absence of destination chain validation in the cross-chain message processing mechanism, combined with the possibility of identical handler addresses across different L2 networks, creates a critical vulnerability. This flaw allows malicious actors to replay valid signatures from one chain to another, potentially leading to unauthorized fund transfers, double-spending, or other malicious actions across different blockchain networks.
The impact of this vulnerability is severe, which can lead to unauthorized fund drainage from affected chains. The issue is not present in cairo version as contract version has a check present for to_chain `assert(to_chain == self.chain_name.read(), 'error to_chain');` in `receive_cross_chain_msg`.

## Proof of Concept
The vulnerability stems from three main factors:

**Lack of destination chain validation**:
In ChakraSettlement.sol, the receive_cross_chain_msg function does not verify if the incoming message is intended for the current chain:
```solidity
function receive_cross_chain_msg(
    uint256 txid,
    string memory from_chain,
    uint256 from_address,
    uint256 from_handler,
    address to_handler,
    PayloadType payload_type,
    bytes calldata payload,
    uint8 sign_type,
    bytes calldata signatures
) external {
    // No check for intended destination chain
    // ...
}
```

**Reliance on transaction ID for replay protection**:
The contract only checks if the transaction ID has been seen before:
```solidity
require(
    receive_cross_txs[txid].status == CrossChainMsgStatus.Unknow,
    "Invalid transaction status"
);
```

This check is insufficient across multiple chains, as each chain maintains its own state.

**Possibility of identical handler addresses**:
The ChakraSettlementHandler.sol initialization doesn't ensure unique addresses across L2s, which may end up as same due to deterministic addresses.
```solidity
function initialize(
    address _owner,
    SettlementMode _mode,
    string memory _chain,
    address _token,
    address _codec,
    address _verifier,
    address _settlement
) public initializer {
    // No mechanism to ensure unique address across chains
    // ...
}
```

Exploit Scenario:

1. A valid transaction is processed on Chain A initiated from chain X. Can be initiated by the attacker itself as normal transaction.
2. An attacker observes the transaction and its signature.
3. The attacker submits the same transaction data and signature to Chain B, where the handler contract has the same address.
4. Chain B's contract processes the transaction as new, having no record of the transaction ID, potentially leading to unauthorized token minting or transfers.
