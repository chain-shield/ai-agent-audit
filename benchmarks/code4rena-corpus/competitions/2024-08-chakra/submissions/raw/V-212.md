# Vulnerability details

## Impact
The implementation of signature verification for cross-chain callbacks omits the `from_chain` parameter from the message hash. This could allow attackers to replay valid callbacks across different chains (e.g., from Ethereum to Arbitrum, or from Polygon to BSC), bypassing the intended chain-specific security measures. [Hinted in the READMe](https://github.com/code-423n4/2024-08-chakra#general-questions), the multi-chain deployment plan including Ethereum, Base, Arbitrum, BSC, Optimism, Polygon, and zkSync, this issue significantly increases the attack surface.

This can also happen when there is a fork in the chain.

## Proof of Concept
Here is the [`verifySignature` function](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/settlement/contracts/ChakraSettlement.sol#L285-L302):

```solidity
function verifySignature(
    uint256 txid,
    uint256 from_handler,
    address to_handler,
    CrossChainMsgStatus status,
    uint8 sign_type,
    bytes calldata signatures
) internal view {
    bytes32 message_hash = keccak256(
        abi.encodePacked(txid, from_handler, to_handler, status)
    );

    require(
        signature_verifier.verify(message_hash, signatures, sign_type),
        "Invalid signature"
    );
}
```

The `message_hash` does not include the `from_chain` parameter. As a result, a valid callback signature from one chain (e.g., Ethereum) could be reused on another chain (e.g., Arbitrum) if the other parameters remain the same. This allows for cross-chain replay attacks.

For example, if an attacker obtains a valid callback signature for a transaction on Ethereum, they could replay this callback on Arbitrum or any other supported chain. The contract would consider this signature valid as long as the `txid`, `from_handler`, `to_handler`, and `status` match, regardless of the originating chain.

## Recommended Mitigation Steps
The `verifySignature` function should include the `from_chain` parameter in the message hash calculation. Update the function signature to accept `from_chain` as an input parameter, and incorporate it into the `keccak256` hash. Additionally, ensure that the `receive_cross_chain_callback` function passes the `from_chain` parameter to `verifySignature` when calling it. 

Like this;

```diff
 function verifySignature(
     uint256 txid,
+    string memory from_chain,
     uint256 from_handler,
     address to_handler,
     CrossChainMsgStatus status,
     uint8 sign_type,
     bytes calldata signatures
 ) internal view {
     bytes32 message_hash = keccak256(
-        abi.encodePacked(txid, from_handler, to_handler, status)
+        abi.encodePacked(txid, from_chain, from_handler, to_handler, status)
     );

     require(
         signature_verifier.verify(message_hash, signatures, sign_type),
         "Invalid signature"
     );
 }

 function receive_cross_chain_callback(
     uint256 txid,

     uint256 from_handler,
     address to_handler,
     CrossChainMsgStatus status,

         txid,
+        from_chain,

     // ... rest of the function doesnt change
 }
```
