# Vulnerability details

## Impact

In the `cross_chain_erc20_settlement()`, users submit their cross-chain transactions to transfer tokens and release them on the destination handler contract. Additionally, `cross_chain_msg_id` is generated inside of the function. The problem is that this id is derived using different information on different chain breaking compatibility with the contracts deployed on EVM chains and deviating from the specification of the contract.

## Proof of Concept

Take a look at how `cross_chain_msg_id` is generated on the Starknet:

https://github.com/code-423n4/2024-08-chakra/blob/main/cairo/handler/src/handler_erc20.cairo#L198
```
   let message_id = tx_id;

```
So `message_id` is just a `tx_id` which is a hash of transaction hash plus `msg.count`.


That's how it's derived on Ethereum:

https://github.com/code-423n4/2024-08-chakra/blob/main/solidity/handler/contracts/ChakraSettlementHandler.sol#L170-179
```
  uint256 cross_chain_msg_id = uint256(
                keccak256(
                    abi.encodePacked(
                        cross_chain_msg_id_counter,
                        address(this),
                        msg.sender,
                        nonce_manager[msg.sender]
                    )
                )
            );

```
So it as well contains the address of the sender + handler contract address + nonce of the sender. These differencies can result in an unexpected behavior as it's a deviation from the spec and `cross_chain_msg_id` is then used as a part of `cross_chain_msg_bytes` that's transferred to the settlement contract and then to the destination chain by the Chakra network.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Change the way `cross_chain_msg_id` (it's called just `message_id` on Starknet) that is generated on the Starknet chain.
