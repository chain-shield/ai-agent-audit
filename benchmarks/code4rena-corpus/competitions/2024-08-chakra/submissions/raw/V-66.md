# Vulnerability details

## Impact
The `ChakraSettlementHandler` contract is vulnerable in the `cross_chain_erc20_settlement` function where the nonce is incremented unconditionally, even if the settlement fails due to invalid input parameters.

**The affected parties are:**

  * Users who initiate cross-chain ERC20 settlements with invalid parameters (e.g., zero amount). They may lose the ability to retry the settlement with the same nonce.
  * The protocol itself, as it may have inconsistent nonce values for users, leading to potential replay attacks and incorrect transaction handling.

Proof of Concept
The `cross_chain_erc20_settlement` function increments the nonce for the sender unconditionally, even if the settlement fails due to invalid input parameters: [ChakraSettlementHandler.sol#L135](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/ChakraSettlementHandler.sol#L133-L136)
```solidity
// ChakraSettlementHandler.sol
function cross_chain_erc20_settlement(
    string memory to_chain,
    uint256 to_handler,
    uint256 to_token,
    uint256 to,
    uint256 amount
) external {
    require(amount > 0, "Amount must be greater than 0");
    require(to != 0, "Invalid to address");
    require(to_handler != 0, "Invalid to handler address");
    require(to_token != 0, "Invalid to token address");

    // ...

    {
        // Increment nonce for the sender
        nonce_manager[msg.sender] += 1;
    }

    // ...
}
```
The choice to increment the nonce before validating the input parameters is a mistake, as it can lead to nonce desynchronization if the settlement fails.

**This scenario will happen When the user calls `cross_chain_erc20_settlement` with an amount of 0.**

1. User calls `cross_chain_erc20_settlement` with `amount = 0`.
2. The `nonce_manager[msg.sender`] is incremented by 1.
3. The function reverts due to the [require(amount > 0, "Amount must be greater than 0")](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/ChakraSettlementHandler.sol#L118) check.
4. The user's nonce has been incremented, but the settlement did not occur.
5. If the user tries to retry the settlement with the same parameters and the correct `amount`, it will fail because the nonce has already been used.

When a user `calls the cross_chain_erc20_settlement` function with `amount = 0`, the following happens:

 1. The `nonce_manager[msg.sender]` is incremented by 1.
 2. The function reverts due to the `require(amount > 0, "Amount must be greater than 0")` check.

At this point, the user's nonce has been incremented, but the settlement did not occur because the function reverted.

Now, let's say the user realizes their mistake and tries to retry the settlement with the same parameters (i.e., `same to_chain`, `to_handler`, `to_token`, and `to`) but with a correct `amount` value greater than 0.

5. If the user tries to retry the settlement with the same parameters and the correct `amount`, it will fail because the nonce has already been used.

This is because the `create_cross_txs` mapping in the `ChakraSettlementHandler` contract uses the `txid` as the key, which is calculated based on the `chain`, `to_chain`, `msg.sender`, `address(this)`, `to_handler`, and n`once_manager[msg.sender]`: [ChakraSettlementHandler.sol#L139-L150](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/ChakraSettlementHandler.sol#L139-L150)
```solidity
// ChakraSettlementHandler.sol
uint256 txid = uint256(
    keccak256(
        abi.encodePacked(
            chain,
            to_chain,
            msg.sender, // from address for settlement to calculate txid
            address(this), //  from handler for settlement to calculate txid
            to_handler,
            nonce_manager[msg.sender]
        )
    )
);
```
Since the `nonce_manager[msg.sender]` was incremented in the first attempt (which failed), when the user retries the settlement with the same parameters, the `txid` will be different because the nonce is now higher. This will cause the settlement to fail because the `create_cross_tx`s mapping will not have an entry for the new `txid`.

This can lead to two main issues:

1. Nonce desynchronization: The user's nonce is incremented, but the settlement did not occur, leading to inconsistencies in the nonce value.
2. Inability to retry settlement: If the user tries to retry the settlement with the same parameters and the correct `amount`, it will fail because the nonce has already been used, as explained in the previous response.

## Recommended Mitigation Steps
The nonce increment should be moved after all the input validation checks and only executed if the settlement proceeds successfully. Moving the nonce increment after the input validation checks and the settlement logic, we ensure that the nonce is only incremented when the settlement actually occurs, maintaining the uniqueness of transaction IDs and preventing nonce desynchronization and potential replay attacks.
```diff
function cross_chain_erc20_settlement(
    string memory to_chain,
    uint256 to_handler,
    uint256 to_token,
    uint256 to,
    uint256 amount
) external {
    require(amount > 0, "Amount must be greater than 0");
    require(to != 0, "Invalid to address");
    require(to_handler != 0, "Invalid to handler address");
    require(to_token != 0, "Invalid to token address");

    // Perform settlement logic...

-   {
-       // Increment nonce for the sender
-       nonce_manager[msg.sender] += 1;
-   }

+   // Increment nonce for the sender after successful settlement
+   nonce_manager[msg.sender] += 1;

    // ...
}
```
