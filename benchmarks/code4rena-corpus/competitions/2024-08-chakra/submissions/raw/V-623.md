# Vulnerability details

## Impact
In the AddressCast contract the toAddress() will change the type of an input from bytes32 and uint256 to an address:
uint256 -> address
bytes32 -> address

https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/libraries/AddressCast.sol#L14-L24

and this function is being used by the contract to properly handle the payload message.

and when the off-chain actors forward the message, and let the target on-chain contract to validate the message, this can bring up a risk of address truncating, because the toAddress() function that being used will truncate the uint256 and bytes32 address to the correct address format.

for example other chain initiate a message that will interacting this address.

0x000000000000000000C02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2 (WETH)
after toAddress() this WETH address will become 
0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2 (WETH)


However, this address 
0xAA0000000000000000C02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2 (malicious WETH)
through toAddress() will also resolve to valid WETH address
0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2 (WETH)

solidity example to test this 
```
uint256 public wethAddress = uint256(uint160(address(0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2)));

uint256 public maliciousWETH = 0xAA0000000000000000C02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2;

function to_address( uint256 _address) external view returns (address result) {
	result = address(uint160(_address));
}
```
