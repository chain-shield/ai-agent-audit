# Vulnerability details

## Impact
The absence of chainId in the hash used to generate transaction IDs (txid) in cross-chain transactions makes the ChakraSettlementHandler vulnerable to replay attacks. This issue arises because the transaction ID, while unique within a single chain due to the nonce, could be valid on other chains if the nonce and other parameters are identical. An attacker could exploit this by replaying the transaction on a different chain, potentially causing duplicate transactions, unintended execution, or other inconsistencies in cross-chain settlement processes.

## Proof of Concept
1. *Affected Code:*
   - **Sending Function:** `cross_chain_erc20_settlement`
     - *Link to code:* (#https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L111-L223) 
     - **Issue:** The transaction ID (txid) is generated without including the chainId, making it possible for the transaction to be replayed on other chains.
     - **Affected Code:**
       ```solidity
       uint256 txid = uint256(
           keccak256(
               abi.encodePacked(
                   chain,                // No chainId included
                   to_chain,
                   msg.sender,
                   address(this),
                   to_handler,
                   nonce_manager[msg.sender]
               )
           )
       );
       ```

   - *Receiving Function:* receive_cross_chain_msg
     - Link to code: [https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ChakraSettlementHandler.sol#L300-L355]
     - *Issue:* The function does not verify the chainId of the incoming transaction, making it susceptible to processing replayed transactions from other chains.
     - **Affected Code:**
       ```solidity
       function receive_cross_chain_msg(
           uint256 /**txid */,
           string memory from_chain,
           uint256 /**from_address */,
           uint256 from_handler,
           PayloadType payload_type,
           bytes calldata payload,
           uint8 /**sign type */,
           bytes calldata /**signatures */
       ) external onlySettlement returns (bool) {
           // from_handler needs to be in whitelist
           if (is_valid_handler(from_chain, from_handler) == false) {
               return false;
           }
           // No chainId verification
          if (payload_type == PayloadType.ERC20) {
            // Cross chain transfer
            {
                // Decode transfer payload
                ERC20TransferPayload memory transfer_payload = codec
                    .deocde_transfer(msg_payload);


                    ///q is it burnt from the source chain
                if (mode == SettlementMode.MintBurn) {
                    _erc20_mint(
                        AddressCast.to_address(transfer_payload.to),
                        transfer_payload.amount
                    );
                    return true;
                } else if (mode == SettlementMode.LockUnlock) {
                    _erc20_unlock(
                        AddressCast.to_address(transfer_payload.to),
                        transfer_payload.amount
                    );

                    return true;
                } else if (mode == SettlementMode.LockMint) {
                    _erc20_mint(
                        AddressCast.to_address(transfer_payload.to),
                        transfer_payload.amount
                    );
                    return true;
                } else if (mode == SettlementMode.BurnUnlock) {
                    _erc20_unlock(
                        AddressCast.to_address(transfer_payload.to),
                        transfer_payload.amount
                    );
                    return true;
                }
            }
        }

        return false;
    
       }
       ```
       

2. *Explanation:*
   - *Sending Function:* The txid is based on parameters including msg.sender and the nonce but lacks chainId. This omission allows transactions to be potentially valid on multiple chains if the other parameters are the same.
   - *Receiving Function:* The function processes transactions without verifying chainId, which allows transactions replayed from other chains to be processed as valid.

## Recommended Mitigation Steps

   **Include chainId in Transaction Hash:**

   - Update the cross_chain_erc20_settlement function to include the chainId in the hash used to generate the transaction ID:
   

   - Modify the receive_cross_chain_msg function to include checks for chainId to ensure the transaction is from the correct chain.
