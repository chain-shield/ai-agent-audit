# Vulnerability details

`SettlementSignatureVerifier` contract, which is responsible for verifying signatures for cross-chain settlement requests. The contract supports different signature types, with ECDSA (type 0) being the primary one.

The problem specifically occurs in the `verify` function: [#L108-L118](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/SettlementSignatureVerifier.sol#L108-L118)
```solidity
function verify(
    bytes32 msgHash,
    bytes calldata signatures,
    uint8 sign_type
) external view returns (bool) {
    if (sign_type == 0) {
        return verifyECDSA(msgHash, signatures);
    } else {
        return false;
    }
}
```
The `verify` function takes a message hash, signatures, and a signature type (`sign_type`) as input. It aims to verify the provided signatures against the given message hash using the specified signature scheme.

The issue is in the `else` block of the `verify` function. For any `sign_typ`e other than 0 (ECDSA), the function simply returns `false` without attempting to verify the signatures using the appropriate signature scheme. This means that even if valid signatures are provided for a non-ECDSA `sign_type`, they will incorrectly fail verification.

## Impact
If a legitimate cross-chain settlement request with a non-ECDSA signature type is submitted. Despite providing valid signatures, the request would be rejected due to the incorrect logic in the verify function. This could lead to failed settlements, causing inconvenience and potential financial losses for users relying on the settlement system.

**Consider this Scenario**
1. A user initiates a cross-chain settlement request with a non-ECDSA signature type (e.g., `sign_type = 1`).
2. The user provides valid signatures for the settlement request.
3. The settlement request is forwarded to the `SettlementSignatureVerifier` contract for signature verification.
4. The `verify` function is called with the message hash, signatures, and the non-zero sign_type.
5. Due to the incorrect logic in the `else` block, the function returns `false`, indicating that the signatures are invalid, even though they may be valid for the specified signature scheme.
6. The settlement request is rejected, and the user's transaction fails, potentially leading to financial losses or inconvenience.
