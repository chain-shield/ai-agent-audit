# Vulnerability details

## Impact
The `verifyECDSA` function eventually invoked by `ChakraSettlement::receive_cross_chain_msg` allows a vulnerability where duplicate signatures can be submitted to bypass the `required_validators` check. Since there is no validation to ensure that a signature has not been reused, a malicious actor could submit the same valid signature multiple times, allowing them to meet the required number of validators and successfully pass the verification process. This replay attack poses a serious security risk to the protocol.

## Proof of Concept

The `receive_cross_chain_msg` function takes signatures as an input and verifies them using the `verifyECDSA` function, which counts the number of `valid signatures (m)`, and checks it against the `required_validators` threshold.

```solidity
    function receive_cross_chain_msg(
        uint256 txid,
        string memory from_chain,
        uint256 from_address,
        uint256 from_handler,
        address to_handler,
        PayloadType payload_type,
        bytes calldata payload,
        uint8 sign_type, // validators signature type /  multisig or bls sr25519
        bytes calldata signatures // signature array
    ) external {
			...
		    // verify signature
            bytes32 message_hash = keccak256(
                abi.encodePacked(
                    txid,
                    from_chain,
                    from_address,
                    from_handler,
                    to_handler,
                    keccak256(payload)
                )
            );

            require(
@=>             signature_verifier.verify(message_hash, signatures, sign_type),
                "Invalid signature"
            );
			...
	}
```

So, the generated `message_hash` and `signatures` will be passed to `SettlementSignatureVerifier::verify` which will further call `verifyECDSA`.

```solidity
    function verify(
        bytes32 msgHash,
        bytes calldata signatures,
        uint8 sign_type
    ) external view returns (bool) {
        if (sign_type == 0) {
            return verifyECDSA(msgHash, signatures);
        } else {
            return false;
        }
    }
```

In the `verifyECDSA` function, the number of `valid signatures (m)` is incremented if the signature is verified by a known validator. However, there is no check to prevent the same signature from being used multiple times:

```solidity
    function verifyECDSA(
        bytes32 msgHash,
        bytes calldata signatures
    ) internal view returns (bool) {
        require(
            signatures.length % 65 == 0,
            "Signature length must be a multiple of 65"
        );

        uint256 len = signatures.length;
        uint256 m = 0;
        for (uint256 i = 0; i < len; i += 65) {
            bytes memory sig = signatures[i:i + 65];
            if (
@=>             validators[msgHash.recover(sig)] && ++m >= required_validators
            ) {
                return true;
            }
        }

        return false;
    }
```

Without a duplication check, an attacker can submit the same valid signature multiple times in the `signatures` , allowing `m` to reach `required_validators` and bypass the signature verification process.

Imagine the following scenario:
1. The required_validators is set to `3`, meaning three valid signatures are needed to approve the transaction.
2. The attacker has only signature from `Validator A` and obtains a valid signature (`sig_A`) for a particular `message_hash`.
3. Normally this would not work. But instead of providing three distinct signatures from three validators, the attacker submits a signature bytes (`signatures`) consisting of `sig_A` repeated `3` times. Thus the validation is bypassed and the transaction is approved.
## Tools Used
Manual

## Recommended Mitigation Steps
To prevent this replay attack, implement a duplication check for signatures. One way to do this is by using a `mapping` to track the addresses that have already provided valid signatures for the message hash.
