# Vulnerability details

## Impact
The impact is high as the adversary can submit for instance the message sent from Starknet to Optimism to other L2/L1 (Ethereum, polygon, etc) due to missing `to_chain` validation on the destination chain. Destination chains only validate if it comes from the valid handler (source chain contract address), but they don’t check if a message is sent specifically to this chain or the destination chain where they are processing the message. And impact is not just tied to Starknet to Optimism it can be between EVM chains also.

The `receive_cross_chain_msg` only validates if the message comes from a valid chain and valid handler. From the above source Starknet chain code snippet the `from_handler` is the contract address of `handler_erc20.cairo` contract in Starknet.

`from_handler` and `from_chain` are the same for every other chain. The `handler_erc20.cairo` contract in starknet is essentially the `from_handler` in EVM or another chain than starknet itself. As this only validates if it originates from valid handler that's in contract whitelist and one of invariant mentioned in audit docs. Now the `handler_erc20.cairo` contract would be deployed once for each mode (there are 4 modes from 0 to 3 of different mint, burn, lock, etc) A single instance of `handler_erc20` contract of each mode with the same other parameters would be deployed on Starknet and managers/operators on EVM across deployed chain would add the same handler in whitelist with `from_chain = starknet` and `from_handler = 0xabcmintmodeone`  Thus message emitted from the Starknet to Optimism can be submitted to Polygon as contract doesn’t check if message was intended to be in Optimism or Polygon. Similarly, there would be a group of validators for EVM who would sign the message and the same message they signed for Optimism can be submitted to Polygon. Very little chance that there would be individual signers for each chain as a quorum or consensus also needs to be built alone singer can introduce the centralization risks.

Now by just observing the block explorer and picking the already processed message parameters in Optimism chain adversary can call the function `receive_cross_chain_message` of a `settlement.sol` contract in different other chains like Polygon, ZkSync, etc other than Optimism in this case. As the `to_chain` is not validated and adversary can benefit from multiple token mints/transfer causing extreme loss to the protocol.

The attack is also relevant for EVM to EVM chains but to Starkent is not possible, as Starknet has checks in place to validate if `to_chain` is indeed Starknet.

## Recommended Mitigation Steps
Since `to_chain` is already passed or gets emitted from the source chain. Pass the `to_chain` in the destination chain contract function `receive_cross_chain_message` in `settlement.sol` and add checks for it.
```
require(to_chain == this_chain_name, "invalid destination chain")
```
