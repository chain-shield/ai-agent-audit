# Vulnerability details

## Impact
Attacker will be able to steal funds on other evm chains by reusing signature that was meant for a particular EVM chain

## Proof of Concept

When calling receive_cross_chain_msg on a dest chain, caller must supply a "signatures" field.

This signature is expected to be from validators, and the message signed includes: [txid, from_chain, from_address, from_handler, to_handler, keccak256(payload)].

The issue is, the signed message does not include the to_chain_id. This allows reuse of the same signature across multiple EVM chains:
```solidity
    function receive_cross_chain_msg(
        uint256 txid,
        string memory from_chain,
        uint256 from_address,
        uint256 from_handler,
        address to_handler,
        PayloadType payload_type,
        bytes calldata payload,
        uint8 sign_type, // validators signature type /  multisig or bls sr25519
        bytes calldata signatures // signature array
    ) external {
        {
            // verify signature
            bytes32 message_hash = keccak256(
                abi.encodePacked(
                    txid,
                    from_chain,
                    from_address,
                    from_handler,
                    to_handler,
                    keccak256(payload)
                )
            );

            require(
                signature_verifier.verify(message_hash, signatures, sign_type),
                "Invalid signature"
            );
            ...
      }
}

```

If the address of to_handler on EVM chainA and EVM chainB are the saame, the receive_cross_chain_msg call will succeed

It is not an uncommon thing to deploy a contract to same address on multiple evm chains. If this is done for certain to_handler contracts, attacker will be able to steal funds

## Tools Used
Manual Review

## Recommended Mitigation Steps
The signed message should include the chain_id. This chain_id should not be supplied by user
