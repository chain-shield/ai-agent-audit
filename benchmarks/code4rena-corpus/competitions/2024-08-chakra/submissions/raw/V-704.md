# Vulnerability details

## Impact
A malicious/attacker validator can steal token from pool or can cause other distruption in the protcol normal working flow as the malicious/attacker validator have full control to craft any malicious message and use it over ChakraSettlement::receive_cross_chain_callback() or ChakraSettlement::receive_cross_chain_msg()

## Proof of Concept

The SettlementSignatureVerifier.sol implements internal function verifyECDSA() which is invoked/used two times during ChakraSettlement::receive_cross_chain_msg() and ChakraSettlement::receive_cross_chain_callback().
However function verifyECDSA() doesn't check for uniqueness in signatures array which makes it vulnerable to signature replay attack.

The system design for Chakra protocol is that between two chains chakra validator network is involved which listen for onchain messaing event, interecpts it and signs it then calls the receive_cross_chain_callback() or receive_cross_chain_msg() as per the nature of message.
These are the workings/propertise of chakra validator network as mentioned by their developer/docs.

- Anyone can permissionlessly become validator in chakra network by staking enough tokens.
- Validator network listen for ChakraSettlement::CrossChainMsg event then calls the respective receive_cross_chain_msg() of the destination chain.
- Validator network also listen for ChakraSettlement::CrossChainHandleResult event then calls the respective receive_cross_chain_callback() of the source chain.
- Validators are consensused, each validator performs the same operation and maintains the same state. Each round will select a proposer, and the proposer will call receive_cross_chain_msg() or receive_cross_chain_callback() depending on nature of message with message hash and signatures of all the other validator.
- Proposer is choosen from the set of validators using DPoS.
- If required number of validator is acheived onchain, the transaction is accpeted by the contract.
A malicious/attacker validator will wait for its turn to be chosen proposer to call the receive_cross_chain_msg(). The malicious/attacker validator will crafts its own custom malicious message signs it, use the same signature for the signatrues calldata while calling receive_cross_chain_msg().

As malicious/attacker validator will be registered onchain, so ```validators[msgHash.recover(sig)] && ++m >= required_validators``` will hold true. And due to lack of uniqueness check in signatures array, the attacker can inflate the `m` count and evetually satisfy the condition
```
if (
       validators[msgHash.recover(sig)] && ++m >= required_validators
   ) 
```
