# Vulnerability details

## Impact

LockUnlock Mode in the Handler Contract Can Prevent Users From Accessing Their Tokens on either chain if the transaction reverts during the settlement:`receive_cross_chain_msg` in the settlement contact that calls the destination handler:`receive_cross_chain_msg`.

When a validator tries to execute the transaction settlement:`receive_cross_chain_message` on the destination chain handler contract and there isn't sufficient balance to satisfy the transaction amount sent by the user on the detsination handler contract, this leaves the user with no token balance on either chain until the balance has been topped up in the destination handler contract and after that, the validator retrying to send the user transaction again via the settlement:`receive_cross_chain_message`.

This can happen if there's a demand for tokens on one chain over the other for various reasons, and high amounts of tokens are being sent from the chain with low demand to high demand for tokens.


## Proof of Concept

LockUnlock Mode in The Handler Contract Can Prevent Users From Accessing Their Tokens on either chain if the transaction reverts during the settlement:`receive_cross_chain_msg` in the settlement contract that calls the destination handler:`receive_cross_chain_msg`
here: 

```solidity
else if (mode == SettlementMode.LockUnlock) {
    _erc20_unlock(
        AddressCast.to_address(transfer_payload.to),
        transfer_payload.amount
    );

    return true;
}
```

This revert can occur when the handler on the destination chain doesn't have enough balance to satisfy the unlock call that the validator is executing and therefore reverts inside the `_erc20_unlock` function as such:

```solidity
 require(
        IERC20(token).balanceOf(address(this)) >= amount,
        "Insufficient balance"
 );
```

Once this revert happens, no matter how long or how many times the validator retries the transaction, it would keep reverting until the sufficient balance is topped up in this handler contract to satisfy the cross chain transaction amount, in turn, rendering the user inaccessible to his funds on the source chain and on the destination chain until the balance is topped and the validator retries sending the cross chain message. This also leaves the cross chain message status in the settlement:`receive_cross_txs` mapping on the destination chain as Unknown, whereas this is a Failed transaction as it wasn't able to satisfy the user on either chain.

This same issue occurs with Burn/Unlock mode but I treated them as different issues because with Lock/Unlock mode, the tokens are `locked` and not `burnt` i.e lost forever. A solution would be to instead of preventing the user from access to his funds on either chain, due to the balance check revert, would be to return a false boolean in the handler contract that has the insufficient balance to handle the tx amount rather than revert with "Insufficient balance".
A callback can then be processed back to the source chain with that boolean to unlock the users token for them. With burn you cannot unlock whats been burnt.

See code below from the handler:`cross_chain_erc20_settlement` :

```solidity
 if (mode == SettlementMode.MintBurn) {
      _erc20_lock(msg.sender, address(this), amount);
  } else if (mode == SettlementMode.LockUnlock) {
       // LockUnlock mode locks the tokens before sending the cross chain tx
      _erc20_lock(msg.sender, address(this), amount);
  } else if (mode == SettlementMode.LockMint) {
      _erc20_lock(msg.sender, address(this), amount);
  } else if (mode == SettlementMode.BurnUnlock) {
      // BurnUnlock mode burns the tokens before sending the cross chain tx
      _erc20_burn(msg.sender, amount);
  }
```


## Recommended Mitigation Steps

Instead of reverting when the balance is insufficient and preventing the user from having access to tokens on both chains temporarily, due to the balance check revert, return a false boolean and process a callback to unlock the tokens that were initially locked and the transaction status as failed.
Then the user can try again when the balance of tokens on destination chain is sufficient for their transaction.
