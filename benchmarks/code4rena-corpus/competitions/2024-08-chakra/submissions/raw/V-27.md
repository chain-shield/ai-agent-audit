# Vulnerability details

## Vulnerability details
The `verifyECDSA` function in the `SettlementSignatureVerifier` contract does not properly verify the required number of validator signatures. The function iterates over the `signatures` bytes and verifies each signature individually.

The issue arises in the condition that checks if the recovered signer is a valid validator and increments the counter `m`:

```solidity
if (
    validators[msgHash.recover(sig)] && ++m >= required_validators
) {
    return true;
}
```

This condition returns `true` as soon as the counter `m` reaches the `required_validators` threshold, even if some of the previous signatures were invalid. An attacker can provide a combination of valid and invalid signatures, and as long as there are enough valid signatures to reach the `required_validators` threshold, the function will return `true`.

For example, if `required_validators` is set to 3, an attacker can provide 4 signatures where the first 2 are valid and the last 2 are invalid. The function will return `true` when it reaches the 3rd signature (which is invalid), bypassing the requirement for 3 valid signatures.

## Impact
This vulnerability has severe consequences for the security and integrity of the Chakra settlement process:

1. Unauthorized Transactions: An attacker can execute unauthorized cross-chain transactions by providing a combination of valid and invalid signatures, as long as the number of valid signatures meets the `required_validators` threshold. This bypasses the intended security measures.

2. Reduced Security Threshold: The vulnerability effectively reduces the security threshold of the settlement process. Instead of requiring the prescribed number of valid validator signatures, an attacker can succeed with fewer valid signatures, undermining the distributed trust model.

3. Potential Financial Losses: If exploited, this vulnerability can lead to financial losses for users and the ecosystem. Malicious transactions can result in the theft of funds or manipulation of asset balances.

4. Reputational Damage: The presence of such a vulnerability can damage the reputation of the Chakra protocol and erode trust in its security and reliability.

## Proof of Concept
Here's a step-by-step proof of concept:

1. Assume `required_validators` is set to 3.

2. Attacker prepares a `signatures` bytes array with:
   - Signature 1: Valid signature from a valid validator
   - Signature 2: Valid signature from a valid validator
   - Signature 3: Invalid signature
   - Signature 4: Invalid signature

3. Attacker calls `verifyECDSA` with the prepared `signatures`.

4. Function iterates over signatures:
   - Signature 1: Valid, `m` incremented to 1.
   - Signature 2: Valid, `m` incremented to 2.
   - Signature 3: Invalid, but `++m >= required_validators` becomes true as `m` is incremented to 3, equal to `required_validators`.

5. Function returns `true`, indicating signature verification passed, even though only 2 out of 3 required signatures were valid.

## Recommended Mitigation Steps
Modify the `verifyECDSA` function to ensure all required signatures are valid before returning `true`:

```solidity
if (validators[msgHash.recover(sig)]) {
    m++;
    if (m >= required_validators) {
        return true;
    }
}
```

With this modification, the function will only return `true` if all required signatures are valid. If any signature is invalid, the function will continue iterating until all signatures are processed and return `false` if the required number of valid signatures is not met.
