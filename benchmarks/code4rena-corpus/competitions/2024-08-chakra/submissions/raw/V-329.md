# Vulnerability details

## Impact
The current method used for generating transaction IDs (`txid`) in the `ChakraSettlement` contract exposes the system to potential front-running and txid manipulation attacks. These vulnerabilities could result in:

Front-running attacks-Malicious actors can observe transactions in the mempool (pending transactions) and submit similar transactions with higher gas prices, ensuring their transactions are processed before the legitimate ones. This can disrupt the transaction order and cause loss of control over cross-chain messages.

`txid` manipulation-Since `txid` is derived from publicly known parameters, attackers could potentially generate conflicting txids, causing issues such as overwriting existing transactions or preventing valid transactions from being processed.

Replay attacks-Without ensuring uniqueness or proper handling of txid, attackers could reuse a valid txid to replay transactions, leading to potential duplicate execution of operations.

## Proof of Concept
In the current `send_cross_chain_msg` function, `txid` is generated as follows:
```solidity
uint256 txid = uint256(
    keccak256(
        abi.encodePacked(
            contract_chain_name, // from chain
            to_chain,
            from_address,        // msg.sender address
            from_handler,        // settlement handler address
            to_handler,
            nonce_manager[from_address]
        )
    )
);
```
This `txid` is deterministic, based on publicly observable parameters such as from_address, to_handler, and nonce_manager. An attacker monitoring pending transactions could replicate these parameters and submit their transaction with a higher gas price to ensure it gets processed first.

Attack Simulation:
An honest user initiates a transaction with the following parameters:
to_chain = "ChainB"
from_address = 0xABC
to_handler = 0xDEF
nonce_manager[from_address] = 1
An attacker observes this transaction and submits the same transaction but with a higher gas fee. The attacker's transaction is mined first, resulting in the same `txid`, causing the original transaction to either fail or be overwritten.

## Recommended Mitigation Steps
IncorporatE unpredictable parameters like block.timestamp or blockhash, `the txid` will be harder to predict and manipulate.
```diff
uint256 txid = uint256(
    keccak256(
        abi.encodePacked(
            contract_chain_name,
            to_chain,
            from_address,
            from_handler,
            to_handler,
            nonce_manager[from_address],
+           block.timestamp,            // Add block timestamp
+           blockhash(block.number - 1)  // Add blockhash for randomness
        )
    )
);
```
This ensures that each `txid` is not only dependent on user inputs but also on the current block's state, making it highly unpredictable.
