# Vulnerability details

## Impact

In the Cairo contracts, cross-chain transaction IDs (`tx_id`) are generated using the transaction hash and the current transaction count on the protocol. These IDs must remain synchronized across both the handler and settlement contracts for proper cross-chain communication.
```rs
// handler_erc20

fn cross_chain_erc20_settlement(ref self: ContractState, to_chain: felt252, to_handler: u256, to_token: u256, to: u256, amount: u256) -> felt252{
    // --SNIP
    let tx_id = LegacyHash::hash(get_tx_info().unbox().transaction_hash, self.msg_count.read());
    
    // --SNIP
    self.msg_count.write(self.msg_count.read()+1);
}
```
```rs

// settlement

fn send_cross_chain_msg(ref self: ContractState, to_chain: felt252, to_handler: u256, payload_type :u8,payload: Array<u8>) -> felt252 {
    // --SNIP
    let cross_chain_settlement_id = LegacyHash::hash(get_tx_info().unbox().transaction_hash, self.tx_count.read());
    // --SNIP
    self.tx_count.write(self.tx_count.read()+1);

}
```
The cross-chain messages IDs **must** be identical across both the handler and settlement contracts because Chakra nodes deliver cross-chain messages to the destination chain using the event `CrossChainMsg` and handle callbacks to the source chain using `CrossChainHandleResult` events emitted by the settlement contract. Any discrepancy between cross-chain messages IDs generation on the handler and settlement contracts can cause the system to break, as validators will rely on the cross-chain messages IDs emitted by the settlement contract.

The vulnerability stems from the independent management of transaction counts between the `handler_erc20` and `settlement` contracts. A malicious user can exploit this by manipulating the transaction count on the settlement contract without corresponding changes in the handler contract by directly calling `settlement::send_cross_chain_msg`. This desynchronization leads to mismatched transaction IDs when initiating further cross-chain messages, causing the cross-chain ERC20 message to be blocked during the callback process. This will result in transaction reverts, and halting cross-chain transfers.

```rs

    to_handler: ContractAddress,

    sign_type: u8,

    // --SNIP
    assert(self.created_tx.read(cross_chain_msg_id).tx_id == cross_chain_msg_id, "message id error");
    // --SNIP

```

Below is a summary of the exploit:
1. The malicious user calls `settlement::send_cross_chain_msg`. This increments the `tx_count` on the settlement contract only.
2. When the legitimate user initiates a cross-chain ERC20 transaction through `handler_erc20::cross_chain_erc20_settlement`, the `msg_count` is used to calculate the `tx_id` on the handler contract. However, due to the earlier manipulation, the `tx_count` on the settlement contract is already ahead of `msg_count`, leading to a different `tx_id` calculation.
3. The `tx_id` calculated on the handler contract does not match the one calculated on the settlement contract. During the callback process, the mismatch causes the handler contract to revert, preventing the cross-chain message from being finalized.

## Proof Of Concept
Consider the following scenario, assuming that `4` cross-chain messages were initiated already
1. A malicious user, calls `settlement::send_cross_chain_msg`. This increments the `tx_count` to `5` on the settlement contract but leaves `msg_count` at `4` on the handler contract.
3. A user initiates a legitimate cross-chain ERC20 transaction through `handler_erc20::cross_chain_erc20_settlement`. The `tx_id` is calculated based on the `msg_count` which is `4`.

    3.1 The settlement contract recalculates the `tx_id` using its `tx_count`, which is `5`, resulting in a mismatch.

    3.2 `settlement::send_cross_chain_msg` will emit the event `CrossChainMsg` with the `tx_id` calculated on the settlement contract.
4. The cross-chain message is received on the destinatino chain B and the event `CrossChainHandleResult` is emitted.
5. During the callback process, the `handler_erc20::receive_cross_chain_callback` function reverts, as the `tx_id` received by the handler contract does not match the one calculated, preventing message finalization.
    
    5.1 the `settlement::receive_cross_chain_callback` will call the handler contract passing the `tx_id`:
    ```rs
    fn receive_cross_chain_callback(ref self: ContractState, cross_chain_msg_id: felt252, from_chain: felt252, to_chain: felt252, from_handler: u256,
        to_handler: ContractAddress,
        cross_chain_msg_status: u8,
        sign_type: u8,
        signatures: Array<(felt252, felt252, bool)>,
    ) -> bool {
        // --SNIP
        let success = handler.receive_cross_chain_callback(cross_chain_msg_id, from_chain, to_chain, from_handler, to_handler , cross_chain_msg_status);
        // --SNIP
    }
    ```

    5.2 Since the `tx_id` passed to the handler contract does not match the one generated on the handler side, the transaction will revert:
    ```rs
    fn receive_cross_chain_callback(ref self: ContractState, cross_chain_msg_id: felt252, from_chain: felt252, to_chain: felt252, from_handler: u256,
        to_handler: ContractAddress,
        cross_chain_msg_status: u8,
        sign_type: u8,
        signatures: Array<(felt252, felt252, bool)>,
    ) -> bool {
        // --SNIP
        assert(self.created_tx.read(cross_chain_msg_id).tx_id == cross_chain_msg_id, "message id error");
        // --SNIP
    }
    ```

As a result, the cross-chain message can not be finalized. In addition, if the contract operates in `MintBurn` mode, the failure to finalize the cross-chain message will also prevent the burning of the tokens originally bridged.

## Recommended Mitigation Steps
It is recommended to centralize the transactions counts and `tx_id` calculation on the handler contract. The handler contract should generate the `tx_id` and pass it to the settlement contract, rather than recalculating the `tx_id` separately on the settlement contract.
###### `handler_erc20::cross_chain_erc20_settlement`
```diff
fn cross_chain_erc20_settlement(ref self: ContractState, to_chain: felt252, to_handler: u256, to_token: u256, to: u256, amount: u256) -> felt252{
    // --SNIP

    settlement.send_cross_chain_msg(to_chain, to_handler, PayloadType::ERC20, encode_message(message),
+        tx_id
    );
}
```
