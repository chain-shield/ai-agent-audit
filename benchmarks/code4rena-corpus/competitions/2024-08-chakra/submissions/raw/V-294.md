# Vulnerability details

## Impact

The `handler.receive_cross_chain_callback` is called with wrong `txid`, causing the tokens that should be burned to be locked in the contract, that is, tokens are issued additionally, breaking the consistent state.      

## Proof of Concept

```solidity

/// settlement.send_cross_chain_msg

nonce_manager[from_address] += 1;
address from_handler = msg.sender;

uint256 txid = uint256(
    keccak256(
        abi.encodePacked(
            contract_chain_name, // from chain
            to_chain,
            from_address, // msg.sender address
            from_handler, // settlement handler address
            to_handler,
            nonce_manager[from_address]
        )
    )
);


/// handler.cross_chain_erc20_settlement

nonce_manager[msg.sender] += 1;

uint256 txid = uint256(
    keccak256(
        abi.encodePacked(
            chain,
            to_chain,
            msg.sender, // from address for settlement to calculate txid
            address(this), //  from handler for settlement to calculate txid
            to_handler,
            nonce_manager[msg.sender]
        )
    )
);


/// handler.receive_cross_chain_callback

if (is_valid_handler(from_chain, from_handler) == false) {
    return false;
}

/// @audit may revert here
require(
    create_cross_txs[txid].status == CrossChainTxStatus.Pending,
    "invalid CrossChainTxStatus"
);

enum CrossChainTxStatus {
    Unknow,
    Pending,
    Minted,
    Settled,
    Failed
}
```

The above code seems to use the same `txid` for settlement and handler, but in fact the `nonce_manager` of the two contracts is not necessarily consistent.       
One settlement may correspond to multiple handlers, or call `settlement.send_cross_chain_msg` directly can also break the synchronization. If the user's `nonce_manager` is not synchronized, the `txid` is different.     
According to the `handler.receive_cross_chain_callback` code, subsequent verification will fail, causing the callback to keep reverting and unable to update the message execution status.      
What's more serious is the tokens that should be burned to be stuck in the contract, and additional tokens are issued in disguise.      
The same is true for cairo, only the generation of `txid` is different.
