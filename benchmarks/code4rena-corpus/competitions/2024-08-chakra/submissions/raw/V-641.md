# Vulnerability details

## Impact
The current implementation of the bridge is incompatible with Starknet's unique L1 <-> L2 messaging mechanism. This incompatibility renders the bridge non-functional on Starknet.

## Proof of Concept

Let's say a message [is sent from L1 to L2](https://docs.starknet.io/architecture-and-concepts/network-architecture/messaging-mechanism/#l1-l2-messages):

Quoting step 1:
> An L1 contract induces a message to an L2 contract on Starknet by calling the `sendMessageToL2` function on the Starknet Core Contract with the message parameters.

However, the current implementation doesn't include any `sendMessageToL2`.

Quoting step 2:
> The message is then decoded into a Starknet transaction that invokes a function annotated with the `l1_handler` decorator on the target contract. Transactions like this on L2 are called L1 handler transactions.
> The Starknet sequencer, upon receiving enough L1 confirmations for the transaction that sent the message, initiates the corresponding L2 transaction.
> The L2 transaction invokes the relevant l1_handler function.

However, the current implementation lacks the required `@l1_handler` decorator for processing L1 messages, as specified in Starknet's documentation.

These two sections are sufficient to demonstrate the incompatibility. 


## Tools Used

Manual code review and [Starknet documentation](https://docs.starknet.io/architecture-and-concepts/network-architecture/messaging-mechanism/).


## Recommended Mitigation Steps

Implement a distinct contract that is incompatible with Starknet's L1 <-> L2 unique messaging system. If the `from_chain` and `to_chain` is Starknet and Ethereum, route the calls to the specific implementation.
