# Vulnerability details

## Impact
The ChakraSettlementHandler contract allows the `mode` state variable to be changed after initialization

## Proof of Concept
Lack of proper access control on the `initialize` function in the `ChakraSettlementHandler` contract. This allows the `mode` variable to be changed after the contract has been initialized, which violates the expected behavior of the contract.

In `ChakraSettlementHandler.so`l, the initialize function is defined as follows:  [ChakraSettlementHandler.sol#initialize](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/ChakraSettlementHandler.sol#L73-L101)
```solidity
function initialize(
    address _owner,
    SettlementMode _mode,
    string memory _chain,
    address _token,
    address _codec,
    address _verifier,
    address _settlement
) public initializer {
    // Initialize the base settlement handler
    _Settlement_handler_init(
        _owner,
        _mode,
        _token,
        _verifier,
        _chain,
        _settlement
    );
    codec = IERC20CodecV1(_codec);
}
```
The issue arises because there is no check to prevent the `initialize` function from being called multiple times. Each time it's called, it re-initializes the contract state, allowing `mode` to be changed.

This violates the expected behavior defined in [BaseSettlementHandler.sol#66](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/BaseSettlementHandler.sol#L66) // [BaseSettlementHandler.sol#_Settlement_handler_init](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/BaseSettlementHandler.sol#L113-L128)
```solidity
SettlementMode public mode;

function _Settlement_handler_init(
    address _owner,
    SettlementMode _mode,
    address _token,
    address _verifier,
    string memory _chain,
    address _settlement
) public {
    __Ownable_init(_owner);
    __UUPSUpgradeable_init();
    settlement = ISettlement(_settlement);
    verifier = ISettlementSignatureVerifier(_verifier);
    mode = _mode;
    token = _token;
    chain = _chain;
}
```
Here, `mode` is expected to be set only once during initialization and not change afterwards.

The choice to allow `initialize` to be called multiple times without restriction is a mistake, as it breaks the expected immutability of the `mode` variable after initialization.

### Scenario

1. The contract owner deploys the `ChakraSettlementHandler` contract and calls initialize with `_mode` set to `SettlementMode.LockMint`.
2. Users interact with the contract, expecting it to operate in `LockMint` mode.
3. The attacker, who may be the contract owner or someone who has gained access to the owner account, calls initialize again with `_mode` set to `SettlementMode.BurnUnlock`.
4. The contract's `mode` is now changed to `BurnUnlock`, which may lead to unexpected behavior and potential loss of funds for users who were expecting the contract to operate in `LockMint` mode.

## Tools Used
Manual review 

## Recommended Mitigation Steps
Add a control in the `initialize` function to only be called once
```diff
+ bool private initialized;
  
  function initialize(...) public {
+     require(!initialized, "Contract already initialized");
+     initialized = true;
      // ... rest of initialize logic ...
  }
```
