# Vulnerability details

## Impact
In the context of cross-chain transactions, it is crucial to ensure that the `token` received on the destination chain is indeed the one intended by the sender from the source chain. Without this validation at destination:
1. Recipients end up with the wrong token.
2. Chances are that the recipients will therefore have to perform `swaps` to obtain the `intended tokens` which will incur them `fees`. Therefore, the `net value` received will be lower given the fee deductions.

## Proof of Concept
One of the `Main invariants` in `Settlement Handler Contract` is this:
> Only the specified token contract (set during initialization) can be used for transfers, mints, and burns within this handler.

As such, when users lock/burn tokens at the source, only specified token at the destination will be minted/unlocked for the recipient.

During initiatiation of a cross-chain ERC20 settlement in `ChackraSettlementHandler::cross_chain_erc20_settlement()`, the user who wishes to lock/burn their tokens specifies the [`to_token`](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/ChakraSettlementHandler.sol#L114) which they want to be unlocked/minted at the `destination` for the recipient.
This `to_token` is then included in the [`ERC20TransferPayload`](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/ChakraSettlementHandler.sol#L186):
```solidity
            // Create a erc20 transfer payload
            ERC20TransferPayload memory payload = ERC20TransferPayload(
                ERC20Method.Transfer,
                AddressCast.to_uint256(msg.sender),
                to,
                AddressCast.to_uint256(token),
>>              to_token,
                amount
            );
```

However, in the `receive_cross_chain_msg()` function, the `to_token` is not checked to be the configured token at destination. The [`ChackraSettlementHandler::receive_cross_chain_msg()`](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/solidity/handler/contracts/ChakraSettlementHandler.sol#L321-L331) decodes the transfer payload then simply proceeds to mint/unlock `transfer_payload.amount` of the `token` configured at destination to the recipient (`transfer_payload.to`).
```solidity
                // Decode transfer payload
                ERC20TransferPayload memory transfer_payload = codec
                    .deocde_transfer(msg_payload);

                if (mode == SettlementMode.MintBurn) {
                    _erc20_mint(
>>                      AddressCast.to_address(transfer_payload.to),
>>                      transfer_payload.amount
                    );
                    return true;
                }
                ---SNIP---
                function _erc20_mint(address account, uint256 amount) internal {
>>                  IERC20Mint(token).mint_to(account, amount); //@audit-info `token` configured at destination
                }
```
The issue arises when the recipient expects `tokenA` but gets minted/unlocked `tokenB`

## Scenario
- `Bob` locks `USDC` at source
- He specifies `to_token` as `USDT`
- At destination, the configured token is `WETH`
- `Alice` (recipient) expects to be minted `USDT` but winds up with `WETH`

**Other instances**:
- [`handler_erc20::receive_cross_chain_msg()`](https://github.com/code-423n4/2024-08-chakra/blob/abef77d95866f2fec93270491fc5abc9ab14f86d/cairo/handler/src/handler_erc20.cairo#L120-L133)

## Recommended Mitigation Steps
Validate the `to_token` at destination to ensure it matches the `token` configured at destination.
Revert if these tokens do not match.
- `ChackraSettlementHandler::receive_cross_chain_msg()`
```diff
        // Decode transfer payload
        ERC20TransferPayload memory transfer_payload = codec
            .deocde_transfer(msg_payload);

+       require(transfer_payload.to_token == token, "Invalid destination token");

        // @audit Proceed with minting/unlocking
        ---SNIP--
```

- `handler_erc20::receive_cross_chain_msg()`
```diff
    let payload_transfer = message.payload;
    let transfer = decode_transfer(payload_transfer);
    ---SNIP---
    let token = IERC20Dispatcher{contract_address: self.token_address.read()};
+   assert(token == transfer.to_token, 'Invalid destination token');   
```
