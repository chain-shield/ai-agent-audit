# Vulnerability details

## Vulnerability description
When a user sends ERC20 tokens to an other chain, he expects to receive these bridged ERC20 on the destination chain. However, there are some factors that can fail during the way. Fortunately, there is a callback function that updates the status of the bridging on the source chain. However, there is a big problem with this callback implementation.
```
    function receive_cross_chain_callback(
        uint256 txid,
        string memory from_chain,
        uint256 from_handler,
        CrossChainMsgStatus status,
        uint8 /* sign_type */, // validators signature type /  multisig or bls sr25519
        bytes calldata /* signatures */
    ) external onlySettlement returns (bool) {
        //  from_handler need in whitelist
        if (is_valid_handler(from_chain, from_handler) == false) {
            return false;
        }

        require(
            create_cross_txs[txid].status == CrossChainTxStatus.Pending,
            "invalid CrossChainTxStatus"
        );

        if (status == CrossChainMsgStatus.Success) {
            if (mode == SettlementMode.MintBurn) {
                _erc20_burn(address(this), create_cross_txs[txid].amount);
            }

            create_cross_txs[txid].status = CrossChainTxStatus.Settled;
        }

        if (status == CrossChainMsgStatus.Failed) {
            create_cross_txs[txid].status = CrossChainTxStatus.Failed;
            // @audit-issue it should return the funds to the user because it failed
        }

        return true;
    }
```
As we can see, if the bidging was successful, it just burn the source tokens in case the mode is `MintBurn`. Whereas if it failed, which means that the user did not receive the tokens on the destination chain, it will just update the state of the transaction as `Failed`.
This if branch that manages a failed message should return back the transfered tokens to the user that initiated the bridging.
An example of a failed message would happen here:
```
    function receive_cross_chain_msg(
        uint256 /**txid */,
        string memory from_chain,
        uint256 /**from_address */,
        uint256 from_handler,
        PayloadType payload_type,
        bytes calldata payload,
        uint8 /**sign type */,
        bytes calldata /**signaturs */
    ) external onlySettlement returns (bool) {
        //  from_handler need in whitelist
        if (is_valid_handler(from_chain, from_handler) == false) {
            return false;
        }

        ...

        return false;
    }
```

## Proof of concept
1. User initiates an ERC20 bridging from chain A to chain B
2. The tokens are transfered to the handler from chain A
3. Validator call the receive function in the handler on chain B
4. The function returns false because the handler of chain A is not whitelisted in the handler of chain B
5. The result of the receive function leads to a failed status and no tokens are transfered or minted in the destination chain
6. The validator call the callback function on chain A with a failed status
7. The callback just sets the message as failed but not transfer back the tokens to the user


## Impact
High, loss of funds by the user


## Tools Used
Manual review
