# Vulnerability details

## Impact
The decoding function assumes a fixed message structure, meaning that the `index 0` will always be the `version`, `index 1–32` will always be the `message_id`, `index 33` will always be the `payload_type`, and the remaining indexes will be the `payload`.
However, if `message_id_array` do not conform to the expected size during encoding, the `message` might be malformed, leading to errors during decoding.

## Proof of Concept
The [`encode_message()`](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/cairo/handler/src/codec.cairo#L93-L117) function simply appends data (`message_id_array`) into `array_u8`  without enforcing any boundaries:
```solidity

>>      let message_id_array: Array<u8> = u256_to_u8_array(message.message_id); // @audit-info Converts `message_id` to array
```

The issue is that without enforcing boundaries during `encoding`, the process rely on the the `u256_to_u8_array()` function itself to provide correctly sized `message_id_array`. If this does not conform to the expected sizes, the `message` might be malformed, leading to errors during `decoding`.

For instance, during decoding, the `message_id_array` is expected to have a length of `32`. If during encoding `message_id_array` was longer than this, it will occupy more slots in the `array_u8` past `index 32`.

However, when decoding, the `decode_message()` will take only the [elements from `index 1` to `index 32`](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/cairo/handler/src/codec.cairo#L32-L33) as `message_id_array` then [convert this array to `message_id`](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/cairo/handler/src/codec.cairo#L44) before returning the whole [`Message`](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/cairo/handler/src/codec.cairo#L46-L51).

### Scenario:
Let's say during message encoding, `message_id_array` has a length of `40` and transfer `payload` has a length of `161`
Therefore:
- `version` -> index 0
- `message_id_array` -> index 1 to 40
- `payload_type` -> index 41
- `payload` -> index 42 to 202

During decoding, the `message_id_array` will truncated to a length of `32`:
- `version` -> index 0
- `message_id_array` -> index 1 to 32
- `payload_type` -> index 33 // @audit-info Now at 33 from 41
- `payload` -> index 34 to 202 // @audit-info Longer length: Also not checked

This decoding is done at destination and used as follows in [`receive_cross_chain_msg()`](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/cairo/handler/src/handler_erc20.cairo#L117-L133):
```solidity
>>          let message :Message= decode_message(payload); // @audit-info Decode message
```

Here are the potential issues:

1. **Panic on incorret `payload_type`**
During encoding, the [`payload_type` is set to `ERC20` value](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/cairo/handler/src/handler_erc20.cairo#L211) and got appended at `index 41`. If at destination the received `payload_type` now at `index 33` is not `ERC20`, the function will panic as shown above with `'ERC20Method must TRANSFER'` error.

2. **Incorrect amount transfered to incorrect recipient**
The `message_id_array` is truncated to a length of `32` during decoding. This means that the transfer payload received has longer length than what was encoded. i.e `Encoded -> index 42 to 202` and `Received -> index 34 to 202`
Upon [decoding](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/cairo/handler/src/codec.cairo#L62-L90), the `transfer.amount` and `transfer.to` may not match the ones that were actually encoded resulting in incorrect token amounts being sent to incorrect recipients.
