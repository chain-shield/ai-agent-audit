# Vulnerability details

`send_cross_chain_msg` function in ChakraSettlement.sol can be invoked directly, enabling attackers to bypass handler contracts and cause permanent system malfunction.

## Proof of Concept
Based on ChakraChain design documents, ChakraChain users can bridge a token by calling `cross_chain_erc20_settlement` function in ChakraSettlementHandler contract. Then, `cross_chain_erc20_settlement` calls `send_cross_chain_msg` function in ChakraSettlement contract:
```
...
            // Send the cross chain msg
            settlement.send_cross_chain_msg(
                to_chain,
                msg.sender,
                to_handler,
                PayloadType.ERC20,
                cross_chain_msg_bytes
            );
...
```
However, function `send_cross_chain_msg` does not check whether the caller is a valid handler or not, and it allows anybody to call it directly. Consequently, an attacker can bypass the `cross_chain_erc20_settlement` function in ChakraSettlementHandler contract and call `send_cross_chain_msg` function directly:
```
/**
     * @dev Function to send cross-chain message
     * @param to_chain The chain to send the message to
     * @param from_address The address sending the message
     * @param to_handler The handler to handle the message
     * @param payload_type The type of the payload
     * @param payload The payload of the message
     */
    function send_cross_chain_msg(
        string memory to_chain,
        address from_address,
        uint256 to_handler,
        PayloadType payload_type,
        bytes calldata payload
    ) external {
        nonce_manager[from_address] += 1;

        address from_handler = msg.sender;

        uint256 txid = uint256(
            keccak256(
                abi.encodePacked(
                    contract_chain_name, // from chain
                    to_chain,
                    from_address, // msg.sender address
                    from_handler, // settlement handler address
                    to_handler,
                    nonce_manager[from_address]
                )
            )
        );

        create_cross_txs[txid] = CreatedCrossChainTx(
            txid,
            contract_chain_name,
            to_chain,
            from_address,
            from_handler,
            to_handler,
            payload,
            CrossChainMsgStatus.Pending
        );

        emit CrossChainMsg(
            txid,
            from_address,
            contract_chain_name,
            to_chain,
            from_handler,
            to_handler,
            payload_type,
            payload
        );
    }
```
### An Example Attack Scenario:
There are two generated transaction IDs (txid) in function `cross_chain_erc20_settlement` in ChakraSettlementHandler contract and function `send_cross_chain_msg` in ChakraSettlement contract. These two txid need to be matched in order to system functions correctly (the one which is generated in `send_cross_chain_msg` will be sent to handler at callback).
Assume Alice bridges some tokens to a Starknet address. She needs to first call function `cross_chain_erc20_settlement` in ChakraSettlementHandler. `cross_chain_erc20_settlement` creates a new cross chain txid with nonce_manager[msg.sender] as one parameter:
```
// Create a new cross chain tx
        uint256 txid = uint256( 
            keccak256(
                abi.encodePacked(
                    chain,
                    to_chain,
                    msg.sender, // from address for settlement to calculate txid
                    address(this), //  from handler for settlement to calculate txid 
                    to_handler,
                    nonce_manager[msg.sender]
                )
            )
        );
```
Then, it calls function `send_cross_chain_msg` which generates a new cross chain txid with nonce_manager[from_address] as one parameter:
```
uint256 txid = uint256(
            keccak256(
                abi.encodePacked(
                    contract_chain_name, // from chain
                    to_chain,
                    from_address, // msg.sender address
                    from_handler, // settlement handler address
                    to_handler,
                    nonce_manager[from_address] 
                )
            )
        );
```
These two nonce_manager arrays are separated and defined in two different contracts. However, the generated txids should be equal because the one which is generated in ChakraSettlement will be sent to the handler when function `receive_cross_chain_callback` is called:
```
        if (
            ISettlementHandler(to_handler).receive_cross_chain_callback(
                txid,
                from_chain,
                from_handler,
                status,
                sign_type,
                signatures
            )
        ) {
            create_cross_txs[txid].status = status; 
        } else {
            create_cross_txs[txid].status = CrossChainMsgStatus.Failed;
        }
```
An attacker can call `send_cross_chain_msg` function in ChakraSettlement.sol directly, without a need to burn or lock tokens in the handler contract. The attacker can pass the address of Alice as from_address parameter to `send_cross_chain_msg`. By doing so, nonce_manager[Alice_address] will be increased by one and a new txid will be generated in ChakraSettlement. Indeed, the attacker made nonce_manager and txids in two contracts ChakraSettlementHandler and ChakraSettlement unsynchronized. 
As a result, Alice's future transactions with ChakraChain will be failed at callback function due to this inconsistency. The attacker can repeat this attack for all the existing ChakraChain users, causing the whole system malfunction with no need to transfer tokens to handler.

## Recommended Mitigation Steps
Function send_cross_chain_msg in ChakraSettlement.sol needs to check whether the caller address is a valid handler or not. This can be done either by defining a modifier or checking the existence of the caller address in a handler_whitelist.
