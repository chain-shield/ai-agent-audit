# Vulnerability details

## Impact

Setting two corresponding handlers on two different chains to LockMint type, will eventually make them unusable or devalue the associated token

## Proof of Concept
There is currently no restriction in the protocol regarding setting both handlers on source and destChain to be LockMint. But it will be very problematic doing so.

For instance:

- both handlers get set as LockMint
- Bob does a cross chain transfer, which locks his tokens on source chainA
- tokens get minted on dest chainB
  Let's say he wants to send them back to source chain:
- minted tokens get locked on chainB
- tokens get minted on chainA, which is wrong as totalSupply of the token will grow indefinitely, making the token worthless.

## Tools Used
Manual Review

## Recommended Mitigation Steps
- Ensuring that chainA is LockMint while chainB is BurnUnlock, won't fix this issue because each chain handler can interact with handlers on multiple chains.

I believe LockMint type is suitable only between two chains(where the other is a BurnUnlock type), not multiple(which is the case in this protocol)
