# Vulnerability details

## Description
[deocde_transfer](https://github.com/code-423n4/2024-08-chakra/blob/d0d45ae1d26ca1b87034e67180fac07ce9642fd9/solidity/handler/contracts/ERC20CodecV1.sol#L65C5-L65C29) is used to decode payload and this function is external. As seen from the code, there is no check to ensure that the payload lenght is within the acceptable range. Omitting the length check in decode_transfer function can lead to several potential issues, including:
    1. Unexpected Behavior: If the payload is not the expected length, the function may try to access memory beyond the end of the provided data, leading to unexpected results or incorrect decoding. For example, if the payload is shorter than expected, accessing byte slices beyond its end could result in garbage data or uninitialized memory.
    2. Security Vulnerabilities: Without a length check, you might inadvertently expose your contract to security vulnerabilities. For instance, attackers could send payloads of incorrect lengths to exploit your contract. This could lead to out-of-bounds memory access, which might be used to manipulate the contract state or reveal sensitive information.
    3. Data Corruption: If the payload is longer than expected, the function might read additional bytes that are not part of the intended data. This can cause the decoded fields to be incorrect, potentially leading to data corruption or erroneous state changes.
    4. Gas Costs: Improperly sized payloads could lead to inefficient gas usage. Accessing out-of-bounds memory or performing unnecessary operations could increase gas costs, making your contract less efficient and more expensive to use.
    5. Revert on Failed Decoding: If the payload length is not what the function expects, the function might fail to decode some fields correctly, leading to incorrect or partial results. This could trigger unexpected reverts or errors during contract execution.
    6. Difficult Debugging: Debugging issues caused by unexpected payload lengths can be challenging. Without proper checks, identifying and fixing problems related to incorrect payload lengths might become more complex.

## Impact
If _payload is shorter or longer than 161 bytes, it could cause:
    • Index Out of Bound Errors: Reading from _payload slices that do not exist.
    • Garbage Data: Decoding beyond the end of the payload could introduce invalid or unintended values.
    • Inconsistent Results: Inconsistent behavior depending on payload length, making the contract unpredictable.

In settlement handler contract, in receive_cross_chain_msg, it was implemented here
```solidity
bytes calldata msg_payload = MessageV1Codec.payload(payload);

ERC20TransferPayload memory transfer_payload = codec
.deocde_transfer(msg_payload);
```
The recipient address was recovered from the decoding in uint256 and casted to address type. IT WAS THEN USED TO PERFORM THE NECESSARY ACTION FOR EACH MODE, SUCH AS
```solidity
if (mode == SettlementMode.MintBurn) {
_erc20_mint(
AddressCast.to_address(transfer_payload.to),
transfer_payload.amount
);
return true;
} else if (mode == SettlementMode.LockUnlock) {
_erc20_unlock(
AddressCast.to_address(transfer_payload.to),
transfer_payload.amount
);
```
Therefore if there is any error while decoding the msg_payload like index Out of bound errors, it would lead to grave consequences.

## Recommended Mitigation Steps
Always perform a length check to ensure that the payload is of the expected length before proceeding with decoding. 
```Solidity

function decode_transfer(
    bytes calldata _payload
) external pure returns (ERC20TransferPayload memory transferPayload) {
    require(_payload.length == 161, "Invalid payload length");

    transferPayload.method_id = ERC20Method(uint8(_payload[0]));
    transferPayload.from = uint256(bytes32(_payload[1:33]));
    transferPayload.to = uint256(bytes32(_payload[33:65]));
    transferPayload.from_token = uint256(bytes32(_payload[65:97]));
    transferPayload.to_token = uint256(bytes32(_payload[97:129]));
    transferPayload.amount = uint256(bytes32(_payload[129:161]));

    return transferPayload;
}
```
Adding the length check ensures that the function operates on properly formatted payloads and helps prevent potential issues related to unexpected payload sizes.
