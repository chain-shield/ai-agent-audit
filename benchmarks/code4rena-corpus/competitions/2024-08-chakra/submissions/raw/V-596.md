# Vulnerability details

## Impact
Tokens can be stolen from the protocol by any user because of this vulnerability. A valid cross chain message sent to one chain which mints or unlocks tokens can be replayed on any other EVM chain with the same handler contract addresses, thus allowing an attacker to potentially extract multiple copies of assets.

Other handlers that receive cross chain messages from `ChakraSettlement` and have the same contract addresses across multiple networks would also be exploitable.

Also, as the events of `receive_cross_chain_msg()` would be emitted on each chain, it is possible that off chain systems and bridges that monitor this event could also be exploited.

## Proof of Concept
The function `ChakraSettlement.receive_cross_chain_msg()` does not receive the destination chain in its parameters and is therefore unable to check that it is not receiving a replayed message from another chain.

The functions verify signatures, and check the transaction has not been seen before, but then go on to call handlers and emit the event and return `true`. It would therefore be possible for any address to resubmit a valid received cross chain message from another chain. 

However, this would require certain conditions:
1) The validators that have signed the message would need to be valid on both chains.
2) The handler on both receiving chains would need to have the same contract address. However, this is quite possible if they have the same code and were deployed in the same manner.

Within `ChakraSettlementHandler`, its function `receive_cross_chain_msg` would be called by the `ChakraSettlement` contract on this line:
```
bool result = ISettlementHandler(to_handler).receive_cross_chain_msg(
    txid,
    from_chain,
    from_address,
    from_handler,
    payload_type,
    payload,
    sign_type,
    signatures
);
```
The code of `ChakraSettlementHandler.receive_cross_chain_msg()` also has no way to check the chain ID of the received message as the settlement contract does not have this information to pass on.

## Tools Used
Manual inspection

## Recommended Mitigation Steps
The protocol should include the `to_chainid` in its calls to `ChakraSettlement.receive_cross_chain_msg()`.

In `ChakraSettlement.receive_cross_chain_msg()` perform a check on the `to_chain` against `block.chainid`.

It is also recommended to pass the `to_chain` to handlers so that they can also potentially check it, although this is an additional layer of security and should not be necessary if `ChakraSettlement` is already checking the destination chain id.
