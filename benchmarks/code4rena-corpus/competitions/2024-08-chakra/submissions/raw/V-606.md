# Vulnerability details

## Impact
The transaction Id that was generated in the handler contract can differ from the transaction id that would be used in the settlement contract and further processing of the cross chain transaction.
This happens when a user calls the `ChakraSettlement:send_cross_chain_msg()` directly. 
e.g user A directly calling  `ChakraSettlement:send_cross_chain_msg()` with the any set of values.

This means any user sending a cross chain transaction from a handler after user A's action,  would always have the transaction Id to be different from the actual generated transaction Id because the `tx_count` and `msg_count` would no longer be in sync.

In settlement contract: send_cross_chain_msg, the tx_count can be increased by anyone directly calling the function with any set of values
```solidity
let cross_chain_settlement_id = LegacyHash::hash(get_tx_info().unbox().transaction_hash, self.tx_count.read());
 ...
 self.tx_count.write(self.tx_count.read()+1);
```

Handler contract is not aware of the update to the tx_count in settlement contract leading to discrepancies
```solidity
 let tx_id = LegacyHash::hash(get_tx_info().unbox().transaction_hash, self.msg_count.read());
```

Thus, all following transactions from the handler contract would remain in a pending state forever and prevent the cross chain callbacks from happening for those transactions because the transaction Id that was generated in the handler contract was not the same transaction Id generated in the settlement contract that handled the cross chain interaction.

```solidity
  let created_tx = self.created_tx.read(cross_chain_msg_id);
```

This line of code in the source chain handler contract, the cross_chain_msg_id processed/sent into this callback check is the txid generated in the settlement which differs from the one generated in the handler thereby always reverting.

Additionally,
If the Mode of the Handler is in MintBurn this can also lead to the tokens that were initially locked for burning not getting burnt and instead always reverting.

```solidity
 if self.mode.read() == SettlementMode::MintBurn{
      erc20.burn_from(get_contract_address(), self.created_tx.read(cross_chain_msg_id).amount);
}
```

## Proof of Concept
When a user initiates a transaction on the source chain Handler contract it generates a transaction id using the `msg_count` as one of the parameters and increments it afterwards for the following transaction to maintain uniqueness as such:

```solidity
let tx_id = LegacyHash::hash(get_tx_info().unbox().transaction_hash, self.msg_count.read());
 ...
self.msg_count.write(self.msg_count.read()+1);
```

Once the message details have been constructed in the handler:`cross_chain_settlement` function they are sent to the settlement contract which then tries to re-generate the transaction ID using the `tx_count` in place of the `msg_count` in the settlement:`send_cross_chain_msg` function and increments the `tx_count` for the following transactions.

```solidity
 let cross_chain_settlement_id = LegacyHash::hash(get_tx_info().unbox().transaction_hash, self.tx_count.read());
 ...
 self.tx_count.write(self.tx_count.read()+1);
```

The transaction Id in the settlement contract and the handler contract are supposed to be the same.
The problem arises due to the fact that anyone can call this function, settlement:`send_cross_chain_msg` in the chakra settlement contract directly with any values and it would not revert, instead, on every direct call it increases the `tx_count`.
This would cause differences in the `tx_count` and the `msg_count` and cause different txid to be generated in the settlement and handler contracts.

The settlement then processes the transaction using a different txid from the one in the handler, after the wrong transaction ID is picked up by the validator and processed, when a cross_chain_callback is being processed, it uses the txid that was generated in the source chain settlement contract which is different from what was generated in the handler contract.

since the cross_chain_msg_id processed in the callback never existed in the source chain handler this would cause a revert as such:

```solidity
if self.mode.read() == SettlementMode::MintBurn{
    erc20.burn_from(get_contract_address(), self.created_tx.read(cross_chain_msg_id).amount);
}
```

If the handler mode is also in MintBurn mode, this would cause a revert as well
Or when it tries to read the cross_chain_msg_id from the created_tx
```solidity
 let created_tx = self.created_tx.read(cross_chain_msg_id);
```


## Recommended Mitigation Steps
Make sure that the tx_count and msg_count are always in sync between the handler and settlement contract
