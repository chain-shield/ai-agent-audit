# Vulnerability details

## Impact
Detailed description of the impact of this finding.
Title: BaseSettlement contract has _Settlement_init Function is public but should be internal
•	Severity: Medium
•	Impact: The _Settlement_init function in the BaseSettlement contract is marked with public visibility, which allows it to be called by external contracts and users.
•	Status: Unresolved
•	File: BaseSettlement.sol
•	Lines Affected: 54-74

The _Settlement_init function in the BaseSettlement contract is marked with public visibility, which allows it to be called by external contracts and users. However, the function name starts with a prefixed underscore (_), which conventionally indicates that the function is intended for internal use only. The current visibility setting can lead to unintended exposure of this function, potentially allowing unauthorized initialization or reconfiguration of the contract’s critical parameters.

If the _Settlement_init function remains public, external actors could exploit it to reinitialize or manipulate the contract, leading to potential security risks such as unauthorized access or modification of roles, validators, and other critical configuration settings. This could undermine the integrity of the contract’s operation and expose the system to attacks.

## Proof of Concept

The following code demonstrates the _Settlement_init function currently marked as public:
```sol
function _Settlement_init(
    string memory _chain_name,
    uint256 _chain_id,
    address _owner,
    address[] memory _managers,
    uint256 _required_validators,
    address _signature_verifier
) public {
    __Ownable_init(_owner);
    __UUPSUpgradeable_init();
    _grantRole(DEFAULT_ADMIN_ROLE, _owner);

    for (uint256 i = 0; i < _managers.length; i++) {
        _grantRole(MANAGER_ROLE, _managers[i]);
    }

    chain_id = _chain_id;
    contract_chain_name = _chain_name;
    required_validators = _required_validators;
    signature_verifier = ISettlementSignatureVerifier(_signature_verifier);
}
```
An attacker could create a contract to call this function and potentially reinitialize or misconfigure the contract:
```sol
// Attacker's script
contract SettlementExploit {
    function exploit(BaseSettlement targetContract) external {
        targetContract._Settlement_init(
            "FakeChain",
            9999,
            msg.sender,
            new address ,
            1,
            address(0)
        );
    }
}
```

## Recommended Mitigation Steps
To mitigate this issue, the visibility of the _Settlement_init function should be changed to internal to restrict its access to within the contract itself or by derived contracts. Here’s the corrected implementation:
```sol
function _Settlement_init(
    string memory _chain_name,
    uint256 _chain_id,
    address _owner,
    address[] memory _managers,
    uint256 _required_validators,
    address _signature_verifier
) internal {
    __Ownable_init(_owner);
    __UUPSUpgradeable_init();
    _grantRole(DEFAULT_ADMIN_ROLE, _owner);

    for (uint256 i = 0; i < _managers.length; i++) {
        _grantRole(MANAGER_ROLE, _managers[i]);
    }

    chain_id = _chain_id;
    contract_chain_name = _chain_name;
    required_validators = _required_validators;
    signature_verifier = ISettlementSignatureVerifier(_signature_verifier);
}
```
