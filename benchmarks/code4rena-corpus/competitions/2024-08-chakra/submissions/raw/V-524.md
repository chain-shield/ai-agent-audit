# Vulnerability details

## Impact
A nonce is not used in the `message_hash` and every other parameter for it in `receive_cross_chain_msg()` comes as a function argument. This means that a malicious user can just monitor the mempool and get a valid signature that he can use to sign the message. Moreover the messages in the `verify()` function from `SettlementSignatureVerifier.sol` are not checked if they have been used or not. This means that the attacker can not only sign the message but he can also bypass the check for the `required_validators` by submiting the signature multiple times in the `signatures` array which means that he can sign a transaction that should have reverted because not enough validators have signed.

## Proof of Concept
This is the `receive_cross_chain_msg()` in `ChakraSettlement.sol`

```solidity

 function receive_cross_chain_msg(
        uint256 txid,
        string memory from_chain,
        uint256 from_address,
        uint256 from_handler,
        address to_handler,
        PayloadType payload_type,
        bytes calldata payload,
        uint8 sign_type, // validators signature type /  multisig or bls sr25519
        bytes calldata signatures // signature array
    ) external {
        {
            // verify signature
>>          bytes32 message_hash = keccak256(
                abi.encodePacked(
                    txid,
                    from_chain,
                    from_address,
                    from_handler,
                    to_handler,
                    keccak256(payload)
                )
            );

            require(
 >>             signature_verifier.verify(message_hash, signatures, sign_type),
                "Invalid signature"
            );

            require(
                receive_cross_txs[txid].status == CrossChainMsgStatus.Unknow,
                "Invalid transaction status"
            );
        }

        receive_cross_txs[txid] = ReceivedCrossChainTx(
            txid,
            from_chain,
            contract_chain_name,
            from_address,
            from_handler,
            address(this),
            payload,
            CrossChainMsgStatus.Pending
        );

        bool result = ISettlementHandler(to_handler).receive_cross_chain_msg(
            txid,
            from_chain,
            from_address,
            from_handler,
            payload_type,
            payload,
            sign_type,
            signatures
        );

        CrossChainMsgStatus status = CrossChainMsgStatus.Failed;
        if (result == true) {
            status = CrossChainMsgStatus.Success;
            receive_cross_txs[txid].status = CrossChainMsgStatus.Success;
        } else {
            receive_cross_txs[txid].status = CrossChainMsgStatus.Failed;
        }

        emit CrossChainHandleResult(
            txid,
            status,
            contract_chain_name,
            from_chain,
            address(to_handler),
            from_handler,
            payload_type
        );
    }


```
As we can see the `message_hash` is only constructed from the function arguments and a nonce is missing which means that this signature is replayable. Now let's examine the `verify()` from `SettlementSignatureVerifier.sol` which inside invokes `verifyECDSA()` where the signature is verified

```solidity

 function verifyECDSA(
        bytes32 msgHash,
        bytes calldata signatures
    ) internal view returns (bool) {
        require(
            signatures.length % 65 == 0,
            "Signature length must be a multiple of 65"
        );

        uint256 len = signatures.length;
        uint256 m = 0;
        for (uint256 i = 0; i < len; i += 65) {
            bytes memory sig = signatures[i:i + 65];
            if (
>>              validators[msgHash.recover(sig)] && ++m >= required_validators
            ) {
                return true;
            }
        }

        return false;
    }

```

The `msgHash.recover(sig)` function will return the address of the signer which means that this check will be bypassed and also the check for the `required_validators` can be bypassed as well by submiting the same signature multiple times in the `signatures` array. So a message that should have reverted because not enough validators signed it can be successfully signed by an attacker

Manual Review

## Recommended Mitigation Steps
Add a nonce to the `message_hash` in `receive_cross_chain_msg()` to prevent signatures from being replayed. The validators are considered trusted but just for security reasons you can add a mapping that tracks already used signatures so a single signature can not be passed multiple times in the `signatures` array to bypass the `required_validators`
