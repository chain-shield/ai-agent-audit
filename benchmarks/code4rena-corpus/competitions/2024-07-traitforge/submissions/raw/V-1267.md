# Vulnerability details

## Vulnerability details
As per current implementation of `TraitForgeNft` contract, 
each generation is only supposed to hold a maximum of 10000 NFTs.

`generationMintCounts[]` is the critical mapping 
used to track the number of NFTs minted in a particular generation 


This mapping is designed to be incremented parallelly
by two different functions as follows

1. Minting via `_mintInternal`

		Only mints NFTs in the currentGeneration.

2. Minting via _mintNewEntity:

		Can mint NFTs in subsequent generations as well, 
		even when the currentGeneration is still lower.

The issue arises from the following statement in the `_incrementGeneration` function, 

```
generationMintCounts[currentGeneration] = 0;

```
which resets this count to 0, 
potentially overwriting a non-zero count.


## Impact

Number of NFTs minted in subsequent generations 
will exceed the intended maximum limit per generation.

## Proof of Concept

Example Scenario

1. Generation 1 (currentGeneration = 1) has maxTokensPerGen = 10000.

2. `_mintNewEntity` mints some NFTs for generation 2 thru forging, 
		incrementing generationMintCounts[2].

3. When generationMintCounts[1] reaches 10000 through `_mintInternal`, 
		`_incrementGeneration` is called.

4. `_incrementGeneration` resets generationMintCounts[2] to 0, 
		losing the count of NFTs already minted in generation 2.

The same loss of count could happen for subsequent generations as well.

## Tools Used

Foundry, Manual review

## Recommended Mitigation Steps

One possible mitigaton is to remove the redundant reset statement
```
 generationMintCounts[currentGeneration] = 0;
```
there's no need to explicitly set it. 
This solution maintains the integrity of the mint counts across generations, 
even when forging occurs in subsequent generations.
