# Vulnerability details

## Impact
`mergerEntropy` must be greater than 10 and exactly divisible by 10 otherwise, it can lead to precision loss and `forgeWithListed` function of `EntityForging.sol` can give unexpected results and ultimately generate wrong `tokenId`.

## Proof of Concept

The code snippet below is from `forgeWithListed` function:
```js
    uint256 mergerEntropy = nftContract.getTokenEntropy(mergerTokenId);
    require(mergerEntropy % 3 != 0, 'Not merger');
@>  uint8 mergerForgePotential = uint8((mergerEntropy / 10) % 10);
```
This line :
```
require(mergerEntropy % 3 != 0, 'Not merger'); 
```
Ensures that `mergerEntropy` is not divisible by 3, otherwise it reverts.

In the next line :
```js
uint8 mergerForgePotential = uint8((mergerEntropy / 10) % 10)
```
In this part 
1. `mergerEntropy / 10` it will lead to precision loss. Any number which is not exactly divisible by 10, the decimal part will be truncated.
   E.g. : In solidity
   11/10=1 (not 1.1)
   29/10=2 (not 2.9) and so on.
  Hence, it leads to precision loss. In case only values that are divisible by 10 are allowed, checks must be implemented.

2. If `mergerEntropy` is less than 10, then `mergerEntropy / 10` will give `0` as result. Because the decimal part will be truncated.
   E.g. : In solidity
   4/10=0 (not 0.4)
   8/10=0 (not 0.8)
  Hence, it gives 0 result. In case only values that are greater than 10 are allowed, checks must be implemented.
Both the above scenarios occur due to precision loss, but both are mentioned separately to ensure better understanding.

>**_NOTE:_**
>Similar situation occurs in `listForForging` function, in the calculation of `forgePotential` variable.
>Precision loss is not handled properly, throughout the contracts in scope.
