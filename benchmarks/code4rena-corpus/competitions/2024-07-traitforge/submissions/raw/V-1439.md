# Vulnerability details

## Impact

The smart contract makes use of integer division that may not provide the expected results. In Solidity, integer division truncates the fraction. As such, any integer division operation can drop significant digits that could lead to monetary loss or manipulation of the system.

In the forgeWithListed() function, devFee is calculated as forgingFee / taxCut. Given the integer division, it could round down and miscalculate the fees. This can either lead to a smaller fee being extracted than expected or a larger forgerShare being credited.

## Proof of Concept

Affected code in the forgeWithListed() function:
```solidity
uint256 forgingFee = _forgerListingInfo.fee;
uint256 devFee = forgingFee / taxCut;
uint256 forgerShare = forgingFee - devFee;
```

## Recommended Mitigation Steps

A Right logic would be to calculate forgerShare and then subtract it from forgingFee on the go rather than dividing forgingFee again.
```solidity
uint256 forgingFee = _forgerListingInfo.fee;
uint256 forgerShare = forgingFee * (100 - taxCut)/100;
uint256 devFee = forgingFee - forgerShare;
``` 
However, the above code has hardcoded percentage (100) and that should be calculated from taxCut itself. If all these parameters (forgingFee, taxCut, etc.) are stored in contract using a decimal standard like wei, you can perform the calculation safely and then convert back to the original unit.

The suggested changes will make sure the contract calculates devFee and forgerShare accurately and prevent any potential loss or manipulation.
