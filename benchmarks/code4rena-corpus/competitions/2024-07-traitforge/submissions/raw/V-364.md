# Vulnerability details

`TraitForgeNft` contract which implements an ERC721 token with additional functionality, contains a flaw in its token transfer mechanism. Specifically, the `_beforeTokenTransfer()` function, which is called internally before any token transfer, fails to consistently update the token balance of the sender (`from` address) during transfers.

The contract extends OpenZeppelin's `ERC721Enumerable`, `ReentrancyGuard`, `Ownable`, and `Pausable` contracts, and implements custom logic for token minting, forging, and transfer restrictions. The `_beforeTokenTransfer()` function is overridden to add custom behavior: [TraitForgeNft.sol#function _beforeTokenTransfer](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L367-L396)


The function updates the `lastTokenTransferredTimestamp` for the token being transferred and handles the cancellation of forging listings. However, it does not update the token balances of the `from` and `to` addresses. While this is typically handled by the parent `ERC721` implementation, there are scenarios where the balance update is not occurring as expected.

## Impact

Inaccurate token ownership records, potentially allowing users to retain spending power over tokens they've transferred.
Discrepancies between the actual token ownership and the reported balances, leading to confusion and potential exploitation.
Violation of the ERC721 standard, which may cause incompatibility with third-party applications and services.
Potential for double-spending attacks if the balance is not correctly decremented.

## Proof of Concept
1. User A has a balance of 1 token (TokenID: 1).
2. User A initiates a transfer of TokenID 1 to User B.
3. The `_beforeTokenTransfer()` function is called, updating the `lastTokenTransferredTimestamp` and handling forging listings.
4. The transfer completes, but User A's balance remains at 1 instead of decreasing to 0.
5. User A can potentially initiate another transfer of the same token, leading to a double-spend scenario.

## Recommended Mitigation Steps
The `super._beforeTokenTransfer()` call is correctly updating the balances. If not, implement balance updates within the function.
```diff
function _beforeTokenTransfer(
    address from,
    address to,
    uint256 firstTokenId,
    uint256 batchSize
) internal virtual override {
    super._beforeTokenTransfer(from, to, firstTokenId, batchSize);

+   // Ensure balance update for non-minting transfers
+   if (from != address(0)) {
+       _balances[from] -= 1;
+   }
+   if (to != address(0)) {
+       _balances[to] += 1;
+   }

    // ...
}
```
