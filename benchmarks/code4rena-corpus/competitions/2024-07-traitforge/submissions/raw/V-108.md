# Vulnerability details

## Impact
The mapping `EntityForging::forgingCounts` is used to track how many times a user has used the token to merge it with another. When calling `EntityForging::forgeWithListed`, the function implements the corresponding check for the mergers:

```javascript
require(
    mergerForgePotential > 0 &&
        forgingCounts[mergerTokenId] <= mergerForgePotential,
    "forgePotential insufficient"
);
```

While for the forgers is not performed there because it has already been checked when calling `EntityForging::listForForging`:

```javascript
require(
    forgePotential > 0 && forgingCounts[tokenId] <= forgePotential, 
    "Entity has reached its forging limit"
);
```

The issue arises with the fact that the increment in the `forgingCounts` mapping for the forger is performed after the check while for the merger before. Therefore when the forger reaches his potential he will be allowed to forge one more time, resulting in a final `forgingCounts` = `forgePotential+1`.

## Proof of Concept
I coded the PoC using Foundry, for it to work, I recommend using the dault Anvil config: `forge test --mt test_forgePotential`.

        traitForgeNft.setRootHash(rootHash);
        vm.stopPrank();

        traitForgeNft.mintToken{value: 1 ether}(proof);
        uint256 tokenIdAlice = tokenIdBob + 1;
        // Mint until fertile and merger
        while (
            ((traitForgeNft.tokenEntropy(tokenIdAlice) / 10) % 10 == 0) ||
            (traitForgeNft.tokenEntropy(tokenIdAlice) % 3 == 0)

## Recommended Mitigation Steps
Since the increment is performed post check in `EntityForging::listForForging`, I recommend using the strictly less operator instead of less than or equal to:

```diff 
require(
-   forgePotential > 0 && forgingCounts[tokenId] <= forgePotential
+   forgePotential > 0 && forgingCounts[tokenId] < forgePotential, 
    "Entity has reached its forging limit"
);
```
