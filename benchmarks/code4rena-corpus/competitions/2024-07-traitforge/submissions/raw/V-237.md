# Vulnerability details

## Impact
The current implementation of the `TraitForgeNft` contract enforces `whitelisting` only during the `minting` process. However, once a `token` is minted, it can be freely `transferred` to any `address`, including `non-whitelisted` addresses. 

This creates a loophole where `non-whitelisted` users can indirectly obtain `tokens` by having `whitelisted` users mint and then transfer tokens to them before the `whitelist period` elapses.

## Proof of Concept
1. **Minting with Whitelisting**:
- The [`mintToken()`](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L188) and [`mintWithBudget()`](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L209) functions enforce `whitelisting` using the [`onlyWhitelisted`](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L51-L59) modifier.
```solidity
  modifier onlyWhitelisted(bytes32[] calldata proof, bytes32 leaf) {
    if (block.timestamp <= whitelistEndTime) {
      require(
        MerkleProof.verify(proof, rootHash, leaf),
        'Not whitelisted user'
      );
    }
    _;
  }
```
This modifier ensures that only `whitelisted` users can mint tokens during `whitelist period`.

2. **Transfer Logic**:
- The [`_beforeTokenTransfer()`](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L367-L395) function does not enforce any `whitelist` checks.
```solidity
  function _beforeTokenTransfer(
    address from,
    address to,
    uint256 firstTokenId,
    uint256 batchSize
  ) internal virtual override {
    super._beforeTokenTransfer(from, to, firstTokenId, batchSize);

    uint listedId = entityForgingContract.getListedTokenIds(firstTokenId);
    /// @dev don't update the transferred timestamp if from and to address are same
    if (from != to) {
      lastTokenTransferredTimestamp[firstTokenId] = block.timestamp;
    }

    if (listedId > 0) {
      IEntityForging.Listing memory listing = entityForgingContract.getListings(
        listedId
      );
      if (
        listing.tokenId == firstTokenId &&
        listing.account == from &&
        listing.isListed
      ) {
        entityForgingContract.cancelListingForForging(firstTokenId);
      }
    }

    require(!paused(), 'ERC721Pausable: token transfer while paused');
  }
```
### Exploit Scenario:
1. *Whitelisted User Transfers Token*:
- The `whitelisted` user transfers the minted token to a `non-whitelisted` user.
- The `_beforeTokenTransfer()` function does not enforce any `whitelist` checks, allowing the transfer to proceed.

2. *Non-Whitelisted User Receives Token*:
- The `non-whitelisted` user now possesses a `token` that was intended to be restricted to `whitelisted` users only.
- They can therefore participate in all activities during this time similar to `whitelisted` users which is against protocol.

## Tools Used
Manual Review

## Recommended Mitigation Steps
1. Implement a mechanism to lock token transfers during the `whitelist` period.
2. Require that if transfers are done during `whitelist` period, the `recipient` must also be `whitelisted`.
