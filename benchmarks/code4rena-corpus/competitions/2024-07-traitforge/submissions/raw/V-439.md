# Vulnerability details

`cancelListing()` function can mark a listing as inactive without removing the token ID from the `listedTokenIds` mapping. This violates the assumption that listed token IDs should always map to a valid and active listing index invariantly checked, and let's look at the relevant parts of the `cancelListing()` function: [EntityTrading.sol#L94-L109](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityTrading/EntityTrading.sol#L94-L109)
```solidity
function cancelListing(uint256 tokenId) public whenNotPaused nonReentrant {
    Listing storage listing = listings[listedTokenIds[tokenId]];

    // check if caller is the seller and listing is active
    require(
      listing.seller == msg.sender,
      'Only the seller can cancel the listing.'
    );
    require(listing.isActive, 'Listing is not active.');

    nftContract.transferFrom(address(this), msg.sender, tokenId); // transfer the nft back to seller

    delete listings[listedTokenIds[tokenId]]; // mark the listing as inactive or delete it

    emit ListingCanceled(tokenId, msg.sender);
}
```
As you can see, the function deletes the listing from the `listings` mapping using `delete listings[listedTokenIds[tokenId]]`. However, it does not remove the token ID from the `listedTokenIds` mapping.

This means that after calling `cancelListing()`, the `listedTokenIds` mapping will still contain the token ID, but the corresponding listing will be inactive or deleted. This violates the `validListedTokenIds` invariant, which expects the listing to be active if the token ID is present in `listedTokenIds`.

## Impact
The presence of inactive listings in the `listedTokenIds` mapping can lead to incorrect assumptions and unexpected behavior in other parts of the contract or external systems relying on this mapping. It can cause confusion and inconsistencies when querying or iterating over the listed token IDs.

Moreover, if the `listedTokenIds` mapping is used for any critical decision-making or calculations, the presence of inactive listings could lead to incorrect results or even enable unintended exploitation.

## Proof of Concept
1. User A lists their NFT with token ID 1 using `listNFTForSale()`.
2. The token ID 1 is added to `listedTokenIds`, and a new active `Listing` is created.
3. User A decides to cancel the listing by calling `cancelListing()` for token ID 1.
4. The `isActive` flag for the listing is set to `false`, but the token ID 1 remains in `listedTokenIds`.
5. The `validListedTokenIds` invariant is now violated, as token ID 1 exists in `listedTokenIds` but points to an inactive listing.

While it deletes the listing from the `listings` mapping, it does not remove the corresponding entry from the `listedTokenIds` mapping. This means that after canceling a listing, the `listedTokenIds` mapping will still contain the `tokenId`, but it will point to a non-existent or inactive listing in the `listings` mapping.

## Recommended Mitigation Steps
the `cancelListing()` function should also delete the entry from `listedTokenIds` when a listing is canceled, by adding the following line after deleting the listing from `listings`:

```diff
  delete listings[listedTokenIds[tokenId]];
+ delete listedTokenIds[tokenId];
```
