# Vulnerability details

### [H-03] Entropy Of Every Entity Can Be Predicted

**Description:**
To get the next entropy for a direct mint, the function **getNextEntropy()** of EntropyGenerator is called inside **mintToken()**. 
It then calls **getEntropy(currentSlotIndex, currentNumberIndex)** to determine the value of the next entropy to be retrieved.
Initially both **currentSlotIndex** and **currentNumberIndex** start from 0 and are being incremented inside each iteration or possibly reset to 0 after some time to then start over again. 
The core issue is that even though both vars are private, their value is still visible on the blockchain.

It is also notable that the block producer can easily pre-calculate all **entropySlots[i]** values when confirming the **writeEntropy{1,2,3}** transactions.
This is due to the fact that the validator has control of all arguments (block.number and i which is in the range [0;770]) used in the generation formula: 
```solidity
uint256 pseudoRandomValue = uint256(
keccak256(abi.encodePacked(block.number, i))
) % uint256(10) ** 78;
```

**Impact:** The entropy for every token id can be predicted (pre-calculated). 
This implies that the moment the NFT Golden God is going to be mint for a particular generation can also be predicted and then possibly this transaction can be front run by the malicious actor.

**Proof of Concept:**
To read the private variables **currentSlotIndex** and **currentNumberIndex**, one just needs to know their corresponding storage slot number.
Then knowing the current values of those variables, the malicious user can calculate the entropy of the next tokenId himself using the maths in **getEntropy()**
or even easier - call **getPublicEntropy()** by just passing the next indices.

**Recommended Mitigation:** The way the randomization algorithm is used should be redesigned, possibly considering the usage of Chainlink VRF.
It should at no cost rely on some publicly visible parameters in order to generate an entropy.
