# Vulnerability details

## Summary

Each generation can have up to 10,000 entities as defined in the whitepaper as well as the code with the variable `maxTokensPerGen = 10000`. The white paper states that with each mint, the price of the next token will `increment linearly` until the final token for that gen is minted i.e the 10000th token is minted.

For Generation 1 entities, The start price is set at 0.005 ether and price Increment is set at 0.0000245 ether. After each generation is completed, the price increment is increased by 0.000005 ether for the next generation which means that the next generation's first token will be minted for 0.005 ether again but the increment will be increased.

There is a mapping of uint256 to uint256 which keeps record of the current generation's mint count i.e. `generationMintCounts[currentGeneration]`

The count of the token starts at 0 and at 10000 count, the generation is considered complete with 10000 tokens minted.

The issue arises when the count is at 10000. The next token which is going to be minted will be from the next generation, the minting itself works as intended but the pricing is incorrect.

## Vulnerability

When a user wants to mint a single token through `mintToken()` or batch mint tokens through `mintWithBudget()` functions. The function first calculates the mintPrice of the next token through the following code

```solidity
    uint256 mintPrice = calculateMintPrice();
    require(msg.value >= mintPrice, 'Insufficient ETH send for minting.');
```

The `calculateMintPrice()` function contains the following code
```solidity
function calculateMintPrice() public view returns (uint256) {
    uint256 currentGenMintCount = generationMintCounts[currentGeneration];
    uint256 priceIncrease = priceIncrement * currentGenMintCount;
    uint256 price = startPrice + priceIncrease;
    return price;
  }
```

Here consider that the `currentGenMintCount is 10000`, the price returned will be calculated with this count. Once the price is returned, the minting functions call the 
`_mintInternal(msg.sender, mintPrice)` function 

This function has the following code at the start 
```
function _mintInternal(address to, uint256 mintPrice) internal {
    if (generationMintCounts[currentGeneration] >= maxTokensPerGen) {
      _incrementGeneration();
    }

   // more code 
    }
```

This if check will pass and the following code will be executed
```solidity
function _incrementGeneration() private {
    require(
      generationMintCounts[currentGeneration] >= maxTokensPerGen,
      'Generation limit not yet reached'
    );
    currentGeneration++;
    generationMintCounts[currentGeneration] = 0; 
    priceIncrement = priceIncrement + priceIncrementByGen;
    entropyGenerator.initializeAlphaIndices();
    emit GenerationIncremented(currentGeneration);
  }
```

Here the generation is incremented and the count for that generation is set to 0, the call will return back to `_mintInternal()` where the remaining code will be executed
```solidity
    _tokenIds++;
    uint256 newItemId = _tokenIds;
    _mint(to, newItemId);
    uint256 entropyValue = entropyGenerator.getNextEntropy();

    tokenCreationTimestamps[newItemId] = block.timestamp;
    tokenEntropy[newItemId] = entropyValue;
    tokenGenerations[newItemId] = currentGeneration;
    generationMintCounts[currentGeneration]++;
    initialOwners[newItemId] = to;

    // More code
```

Now in this part of the code, the count is increased to 1 for the generation indicating that the first token has been minted. According to the docs the price should reset here and user only has to pay the startPrice on the first token of the new generation but the user will pay the price calculated using the previous generations calculations in the `calculateMintPrice()` function.

From the whitepaper : 
> "The Mint fee for generation 1 starts at 0.005 ETH and ends at 0.25ETH after 10,000. Generation 2 starts at 0.005 ETH and ends at 0.3ETH. Generation 3 starts at 0.005 ETH and ends at 0.35 ETH, and so on."

## Impact

The user will be paying way more for the first token of each generation. The impact is over-charging of entity and this will occur at the completion of each generation.

Considering that the `mintWithBudget()` function allows user to mint multiple entities, if the price of the first entity of the priced incorrectly than the user might not be able to receive the amount of entities they expected to receive and might not receive the calculated refund they expected (refund case applies to `mintToken()` aswell).

## Tools Used

Manual Review

## Recommended Mitigation Steps

Calculate the price after verifying the generation of the token to be minted. The functions `mintToken()` and `mintWithBudget()` calculate price first before checking the count and generation, the calculation should be moved after the verification on count and generation has been completed.
