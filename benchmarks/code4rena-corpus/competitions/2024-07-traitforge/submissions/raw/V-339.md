# Vulnerability details

# Improper `entropy` calculation generates unrandom parameters
## Vulnerablity details
Function writeBatchEntropy's in `EntropyGenerator.sol` are based on the math model:  
>770 UINT256’s, each UINT = 78 digits / 13 = 13 x 6 digit entropies. 

Every `entropySlot[]` is expected to contain a 78-digit number.    
Take `writeEntropyBatch1()` as an example:
```solidity
    function writeEntropyBatch1() public {
        require(lastInitializedIndex < batchSize1, 'Batch 1 already initialized.');

        uint256 endIndex = lastInitializedIndex + batchSize1;
        unchecked {
            for (uint256 i = lastInitializedIndex; i < endIndex; i++) {
@>          uint256 pseudoRandomValue = uint256(
@>              keccak256(abi.encodePacked(block.number, i))
@>          ) % uint256(10) ** 78;
            require(pseudoRandomValue != 999999, 'Invalid value, retry.');
            entropySlots[i] = pseudoRandomValue;
            }
        }
        lastInitializedIndex = endIndex;
    }
```
Although `pseudoRandomValue` is generated in a range between `0` and `10^78-1` theoretically by pure mod calculation, it is impossible here to guarantee a 78-digit number to save in `entropySlot[]`. Due to the limit of `uint256 <= 2^256-1 ≈ 1.16*10^77`, there can be no 78-digit numbers to be finally slotted considering the randomness of `keccak256()` algorithm at the same time. Tests have shown that numbers in `entropySlot[]` are mainly 77-digit.    
Then the `entropy` is got by function `getEntropy()`:
```solidity
function getEntropy(
    uint256 slotIndex,
    uint256 numberIndex
) private view returns (uint256) {
    require(slotIndex <= maxSlotIndex, 'Slot index out of bounds.');

    if (
    slotIndex == slotIndexSelectionPoint &&
    numberIndex == numberIndexSelectionPoint
    ) {
    return 999999;
    }

    uint256 position = numberIndex * 6;
    require(position <= 72, 'Position calculation error');

    uint256 slotValue = entropySlots[slotIndex];
    uint256 entropy = (slotValue / (10 ** (72 - position))) % 1000000;
    uint256 paddedEntropy = entropy * (10 ** (6 - numberOfDigits(entropy)));

    return paddedEntropy;
}
```
`slotValue` is read from the slots written by function writeBatchEntropy's, which contain majorly 77-digit numbers or numbers with even less digits.    
Under this condition, when `position = 0` initially in every slot traversal, `entropy <= ((a * 10 ** 76) / (10 ** 72)) % 1000000 = a * 10 ** 4` is a 5-or-less-digit number.    
Then `paddedEntropy` pads the last digit with `0`.  
This leads to a certainty that the first `entropy` got from each of 770 `entropySlot[]`s is always a mutiple of 10, which undermines the endeavour of entropy to ensure randomness.

## Impact
The issue is that the crucial NFT parameters like `performanceFactor` is subject to `entropy` to some extent, and the unrandomness of `entropy` will lead to unbalanced parameter settings and potential award decreasement.
```solidity
    function deriveTokenParameters(
        uint256 slotIndex,
        uint256 numberIndex
    )
        public
        view
        returns (
        uint256 nukeFactor,
        uint256 forgePotential,
        uint256 performanceFactor,
        bool isForger
        )
    {
        uint256 entropy = getEntropy(slotIndex, numberIndex);

        nukeFactor = entropy / 4000000;
        forgePotential = getFirstDigit(entropy);
@>      performanceFactor = entropy % 10;

        uint256 role = entropy % 3;
        isForger = role == 0;

        return (nukeFactor, forgePotential, performanceFactor, isForger);
    }
```
`performanceFactor` is the most directly affected parameter for being more likely `0` when the probability of `entropy` as a multiple of 10 improperly elevated. The excessive probability can be roughly calculated as $ P = \frac{770}{10000} * 1 + \frac{9230}{10000} * \frac{1}{10} = 16.93\% > 10\%$.    
Since `performanceFactor` dictates how quickly an Entity matures and finally dicides `finalNukeFactor` which reflects NFT holder's dividend in NukeFund if Entity nuked, more zero value disincentivizes the players more and breaks fairness of the game.

## Proof of Concept
The following code demonstrates the scenario, where current calculation fails to generate 78-digit numbers in `entropySlot[]`:
1. Add to `EntropyGenerator.sol`:
```solidity
function countDigits() public view returns (uint256[] memory) {
    uint256[] memory digitCounts = new uint256[](5);
    for (uint i = 0; i < 770; i++) {
    uint256 number = entropySlots[i];
    uint256 digits = 0;
    while (number != 0) {
        ++digits;
        number /= 10;
    }
    if (digits == 78) {digitCounts[0]++;}
    else if (digits == 77) {digitCounts[1]++;}
    else if (digits == 76) {digitCounts[2]++;}
    else if (digits == 75) {digitCounts[3]++;}
    else {digitCounts[4]++;}
    }
    return digitCounts;
}
```
