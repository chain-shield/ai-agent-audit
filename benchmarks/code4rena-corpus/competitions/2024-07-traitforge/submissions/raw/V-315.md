# Vulnerability details

## Impact
At each generation change, the counter for the number of tokens of this new generation becomes erroneous. It goes to 0, even though there are already tokens of this generation thanks to the possibility of forging. This distorts all the token counters from generation 2 to 10. The 10,000 tokens per generation is no longer respected and can be much more numerous.

## Proof of Concept
https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/TraitForgeNft/TraitForgeNft.sol#L280
https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/TraitForgeNft/TraitForgeNft.sol#L351
Within the _mintInternal function, when a token generation is full (at 10,000 units) the _incrementGeneration function is called. This sets the counter for the number of tokens in the new generation to 0: 
```typescript
currentGeneration++;
generationMintCounts[currentGeneration] = 0
```
 However, with the possibility of forging tokens of generation n+1 with the _mintNewEntity function, we have generationMintCounts[currentGeneration] which is not 0 and corresponds to the actual number of tokens of this new generation. 


### Test: 

The aim of the following test is to show that the generationMintCounts[currentGeneration] counter resets to 0 when there are already tokens of this generation in existence.
To achieve this, I'll mint 9999 tokens of gen 1. Then with a forger token (potential forge of 9) and with a merger token (potential forge of 7) I'll forge 7 tokens of generation 2.
Finally, I'll mint 2 new tokens so that the _incrementGeneration function can be called.
In the console log, we can see that generationMintCounts[generation2] is 1 when it should be 8, and that the owner and user1 have a total of 1008 tokens.
