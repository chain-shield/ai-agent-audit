# Vulnerability details

## Impact

Impact: Medium
Likelihood: Medium

Two occurrences of unchecked address, whether the address per se can receive ERC721 tokens.
Namely,
1. https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityTrading/EntityTrading.sol#L81
2. https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityTrading/EntityTrading.sol#L104

From OpenZeppelin Contracts `(token/ERC721/IERC721.sol)`:
https://github.com/OpenZeppelin/openzeppelin-contracts/blob/e3786e63e6def6f3b71ce7b4b30906123bffe67c/contracts/token/ERC721/IERC721.sol#L78

From the link of the documentation above:
WARNING: Note that the caller is responsible to confirm that the recipient is capable of receiving ERC721
or else they may be permanently lost. Usage of {safeTransferFrom} prevents loss, though the caller must understand this adds an external call which potentially creates a reentrancy vulnerability.

## Proof of Concept
By calling any of the functions:
1. `EntityTrading::buyNFT`
2. `EntityTrading::cancelListing`
If the receiver address is not checked whether it can receive ERC721 then the ERC721s may be permanently lost.

## Tools Used
Solidity, VSCode

## Recommended Mitigation Steps

Use safeTransferFrom instead of transferFrom.

In `EntityTrading::buyNFT`:
```solidity
function buyNFT(uint256 tokenId) external payable whenNotPaused nonReentrant {
    ...
+    nftContract.safeTransferFrom(address(this), msg.sender, tokenId); // transfer NFT to the buyer
-    nftContract.transferFrom(address(this), msg.sender, tokenId); // transfer NFT to the buyer
    ...
}
```

In `EntityTrading::cancelListing`:
```solidity
function cancelListing(uint256 tokenId) public whenNotPaused nonReentrant {
    ...
+    nftContract.safeTransferFrom(address(this), msg.sender, tokenId); // transfer the nft back to seller
-    nftContract.transferFrom(address(this), msg.sender, tokenId); // transfer the nft back to seller
    ...
}
```

Please note that as per the documentation from OZ above, `safeTransferFrom` adds an external call which potentially creates a reentrancy vulnerability. However, in the case of this two functions, there is a nonReentrant modifier which fixes this potential problem.
