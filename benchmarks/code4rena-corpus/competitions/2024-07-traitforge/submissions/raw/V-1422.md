# Vulnerability details

## Description 
The `forgeWithListed` function is responsible for executing the forging process between two NFTs, which involves transferring fees and updating the contract state. The bug arises from the sequence of operations and the way errors are handled during the ETH transfers.
```
(bool success, ) = nukeFundAddress.call{ value: devFee }('');
require(success, 'Failed to send to NukeFund');
(bool success_forge, ) = forgerOwner.call{ value: forgerShare }('');
require(success_forge, 'Failed to send to Forge Owner');
```
Here's the issue broken down:

- The function first sends the `devFee` to the `nukeFundAddress`.
- If this transfer succeeds, it then attempts to send the `forgerShare` to the `forgerOwner`.
- If the second transfer (to the `forgerOwner`) fails, the function will revert due to the require statement.

The problem is that if the second transfer fails, the first transfer (to the `nukeFundAddress`) has already been completed and won't be reversed automatically. This leads to an inconsistent state where:

- The NukeFund has received its fee
- The forger owner hasn't received their share
- The forging operation hasn't actually completed
- The listing hasn't been cancelled
## Impact
- Fund Lock: The `devFee` sent to the `nukeFundAddress` becomes locked if the subsequent transfer fails. This results in the contract losing funds that should have been refunded or used for the forging process.
- Inconsistent State: The contract's state becomes inconsistent because:
1. A new NFT is minted but the forging process is not completed.
2. The `devFee` is paid, but the forger doesn't receive their share.
- Unfair Fee Distribution: The `nukeFund` receives fees for operations that didn't fully complete, which is unfair to the users.
## Proof of concept
If `success_forge` is false, the function will revert. However, by this point:
- A new NFT has been minted
- The devFee has been sent to the nukeFundAddress
- The contract's state (like forgingCounts) may have been updated
None of these changes are automatically reversed when the function reverts.

## Tools Used
Manual code review

## Recommended Mitigation Steps
Use a pull payment pattern instead of push payments, allowing users to withdraw their funds later if a transfer fails.
