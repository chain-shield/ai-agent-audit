# Vulnerability details

## Impact

The `EntityForging.forgeWithListed` function is used to forge a new `TraitForgeNft` by combining a forger NFT and a merger NFT. In the function execution of the `forgeWithListed` function `forgingCounts` mapping value for the given `forgerTokenId` is incremented as shown below:

```solidity
    forgingCounts[forgerTokenId]++;
```

Similarly the `forgingCounts` mapping value for the given `mergerTokenId` is incremented as shown below:

```solidity
    forgingCounts[mergerTokenId]++;
    require(
      mergerForgePotential > 0 &&
        forgingCounts[mergerTokenId] <= mergerForgePotential,
      'forgePotential insufficient'
    );
```

Even though the `forgingCounts[mergerTokenId] <= mergerForgePotential` check is performed for the `mergerTokenId` after the `forgingCounts[mergerTokenId]++` incremented the same `forgingCounts[tokenId] <= forgePotential` check is performed for the `forgerTokenId` in the `EntityForging.listForForging` before the `forgingCounts[forgerTokenId]++` incremented.

Since the `forgingCounts[tokenId] <= forgePotential` check is performed for the `forgerTokenId` in the `EntityForging.listForForging` before the `forgingCounts[forgerTokenId]++` incremented, the `forgingCounts[forgerTokenId]++` value can now exceed the `forgePotential` value of the `forger tokenId` by one. This happens when the `forgingCounts[tokenId] == forgePotential` state has already reached and again the `EntityForging.listForForging` is called. This will allow the `forgerTokenId` to be listed for forging again and when `forgeWithListed` is called for this `forgerTokenId` the `forgingCounts[forgerTokenId]++` will exceed the `forgePotential` value of the respective `forger tokenId` by one.

This gives extra advantage to the `forger token owner` since now he can `forge` the `forgerTokenId`, `forgerPotential + 1` times and this breaks the expected behaviour of the protocol. 

Since the `forgerTokenId` should only be allowed to be forged `forgerPotential` times per year, and it should not exceed that limit within the considered time duration (which is one year since forge reset timestamp).

## Recommended Mitigation Steps

Hence it is recommended to update the `forgingCounts[tokenId] <= forgePotential` check in the `EntityForging.listForForging` function as `forgingCounts[tokenId] <= forgePotential` where `==` state is omitted. This will prevent the `forgerTokenId` from being forged once more after the `forgerPotential` limit is reached.

The modified conditional check of the `EntityForging.listForForging` is shown below:

```solidity
    require(
      forgePotential > 0 && forgingCounts[tokenId] < forgePotential,
      'Entity has reached its forging limit'
    ); 
```
