# Vulnerability details


## Description

The `EntityForging` contract manages the listing and forging of tokens. It utilizes two key mappings: `listings` to store listing information and `listedTokenIds` to track which tokens are listed. The `listForForging()` function allows users to list their tokens for forging, while `_cancelListingForForging()` is used to cancel listings.

The issue arises in the `_cancelListingForForging()` function. When a listing is cancelled, the function correctly removes the listing from the `listings` mapping:

[EntityForging.sol#L193-L197](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityForging/EntityForging.sol#L193-L197)
```solidity
File: EntityForging.sol
193:   function _cancelListingForForging(uint256 tokenId) internal {
194:     delete listings[listedTokenIds[tokenId]];
195: 
196:     emit CancelledListingForForging(tokenId); // Emitting with 0 fee to denote cancellation
197:   }

```

However, it fails to update the `listedTokenIds` mapping. This creates an inconsistent state where `listedTokenIds[tokenId]` still points to a now-deleted listing.

The problem manifests when a user attempts to re-list a previously cancelled token. The `listForForging()` function checks if a token is already listed:

[EntityForging.sol#L67-L73](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityForging/EntityForging.sol#L67-L73)
```solidity

68:     uint256 tokenId,
69:     uint256 fee
70:   ) public whenNotPaused nonReentrant {
71:     Listing memory _listingInfo = listings[listedTokenIds[tokenId]];
72:

         // ... rest of the function
}
```

Due to the inconsistent state, this check will incorrectly identify the token as still listed, preventing the user from re-listing their token.

## Impact
The inconsistent state caused by not updating `listedTokenIds` can prevent users from re-listing their tokens after cancellation, leading to a poor user experience and potential loss of functionality. It can also create confusion in the contract state, making it difficult to track active listings accurately.


## Proof of Concept
1. Alice lists her token (ID: 1) for forging:
   - `listForForging(1, 1 ether)` is called
   - `listings[1]` is set with Alice's listing info
   - `listedTokenIds[1]` is set to 1

2. Alice decides to cancel her listing:
   - `cancelListingForForging(1)` is called, which internally calls `_cancelListingForForging(1)`
   - `listings[1]` is deleted
   - `listedTokenIds[1]` remains set to 1

3. Alice tries to re-list her token:
   - `listForForging(1, 2 ether)` is called
   - The function checks `listings[listedTokenIds[1]]`
   - Despite the listing being deleted, `listedTokenIds[1]` still points to index 1
   - The function incorrectly determines the token is already listed and reverts

4. Alice is now unable to re-list her token for forging

## Recommended Mitigation Steps
Update the `_cancelListingForForging()` function to also reset the `listedTokenIds` mapping:

```diff
function _cancelListingForForging(uint256 tokenId) internal {
    delete listings[listedTokenIds[tokenId]];
+   delete listedTokenIds[tokenId];
    emit CancelledListingForForging(tokenId);
}
```

This change ensures that both `listings` and `listedTokenIds` are consistently updated when a listing is cancelled, allowing users to re-list their tokens as intended.
