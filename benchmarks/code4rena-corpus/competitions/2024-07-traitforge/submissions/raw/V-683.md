# Vulnerability details

## Impact
The current generation can go over the maximum as no checks are enforced which breaks one of the core protocol invariants

## Proof of Concept
The protocol has a maximum generation variable which the current generation should not go over:
```solidity
uint256 public maxGeneration = 10;
```
However, that is not enforced besides in one case. Note, that the one case it is enforced in, it is not successfully done however that is a separate issue and they should not be duplicated to each other. This one is about some minting paths having no validation, not insufficient validation.

Users can call `mintToken()` to mint themselves an NFT. We go over some checks and then we mint an NFT, however none of those checks enforce in any way, shape or form, the maximum generation limit. To prove that in the simplest way possible, simply CTRL + F the variable name (`maxGeneration`) in `TraitForgeNft` and see all of the instances of the variable. It is only instantiated, then we have a setter function for it and the following check in `forge()`:
```solidity
require(newGeneration <= maxGeneration, "can't be over max generation");
```
The only check for that variable is in the `forge()` function which is not connected to the `mintToken()` flow, thus we can easily go over the maximum generation. As noted, the check in `forge()` is insufficient and that is a separate issue, they should not be duplicated.
