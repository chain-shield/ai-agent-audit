# Vulnerability details

## Description

The `EntityTrading` contract manages NFT listings and trades using two key mappings: `listedTokenIds` and `listings`. The `buyNFT()` and `cancelListing()` functions are designed to remove listings after successful transactions. However, the current implementation using the `delete` keyword on the `listings` mapping entry does not fully clear the listing data, potentially leading to security vulnerabilities.

In Solidity, using `delete` on a mapping entry resets the value to its default state but does not remove the key. For the `Listing` struct, this means all fields are reset to their default values. The critical issue is that the `listedTokenIds` mapping still retains the old index for the token ID, creating a mismatch between the two mappings.

This mismatch can lead to scenarios where stale or invalid listing data is accessed, potentially allowing malicious actors to exploit the system by interacting with listings that should no longer be active.

## Impact

The incorrect use of `delete` can lead to inactive listings being reused, causing potential conflicts or incorrect behavior when the same `tokenId` is listed again. This could result in users being unable to list their NFTs properly or encountering unexpected behavior when interacting with the contract.


## Proof of Concept

Consider the following scenario:

1. Alice lists her NFT (tokenId: 1) for 5 ETH.
   - `listedTokenIds[1] = 1`
   - `listings[1] = Listing(Alice, 1, 5 ETH, true)`

2. Bob buys the NFT, triggering `buyNFT(1)`.
   - `delete listings[listedTokenIds[1]]` is executed, resetting the `Listing` struct but not removing the entry from `listedTokenIds`.

3. Alice lists the same NFT (tokenId: 1) again, but for 10 ETH.
   - Due to the stale data in `listedTokenIds`, the new listing might overwrite the old index or cause unexpected behavior.

4. A malicious actor, Charlie, observes this and attempts to interact with both the old (non-existent but not properly cleared) and new listings, potentially exploiting the system.

## Recommended Mitigation Steps

To address this vulnerability, implement a more robust listing removal process:

1. Instead of using `delete`, set the `isActive` flag to `false` to mark the listing as inactive.
2. Implement a function to clean up old listings and reset the `listedTokenIds` mapping.
3. Add additional checks in `buyNFT()` and other relevant functions to ensure they're interacting with active listings only.

Here's a diff for the `buyNFT()` function:

```diff
function buyNFT(uint256 tokenId) external payable whenNotPaused nonReentrant {
    uint256 listingIndex = listedTokenIds[tokenId];
    Listing storage listing = listings[listingIndex];
    require(listing.isActive, "Listing is not active");
    // ... (other checks)

    // Process the sale
    // ... (transfer logic)

    // Mark the listing as inactive instead of deleting
-   delete listings[listedTokenIds[tokenId]];
+   listing.isActive = false;
+   delete listedTokenIds[tokenId];

    emit NFTSold(tokenId, listing.seller, msg.sender, msg.value, nukeFundContribution);
}
```

Similar changes should be applied to the `cancelListing()` function.
