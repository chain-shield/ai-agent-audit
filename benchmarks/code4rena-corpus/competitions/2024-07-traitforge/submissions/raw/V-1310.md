# Vulnerability details

## Impact
Entropy sequence can be predicted and bad actors can monitor the contract to know when is the right time to mint given the entropy sequence reference that was generated. It will deny fairness and allow others to take advantage.


## Proof of Concept
From the whitepaper, the following was stated:
```
Genesis entropy is seeded using blockhash. Setting all 770 uint256 slots cost 15m gas, and due to contract & block size limits, this cannot be set in contract initialisation. Instead a function writes in entropy in 3 passes after the contract is deployed. 
```

On each of the `writeEntropyBatch` functions, the following code for generating entropy is:
```
     for (uint256 i = lastInitializedIndex; i < maxSlotIndex; i++) {
        uint256 pseudoRandomValue = uint256(
          keccak256(abi.encodePacked(block.number, i))
        ) % uint256(10) ** 78;
        entropySlots[i] = pseudoRandomValue;
      }
    }
```

This uses the block number. Given the block after it was triggered, the batch entropies can be inferred when we run the calculation of pseudoRandomValue on own. These functions are also public and can be triggered by anyone so it might mess up the genesis functions.

After we can recreate the entropies written during the `writeEntropyBatch` calls, we can determine when is the right time to mint by listening to `Minted` events. The entropy is assigned when the nft contract calls `entropyGenerator.getNextEntropy()` assigning the next predetermined entropy.

A bot can monitor these and check for the following:
- the current number of mints using `totalSupply()`
- the next entropy to be assigned through `entropyGenerator.getNextEntropy()` 
- refer to the sequence of all the entropies generated and predict the `tokenId` given an entropy value.
