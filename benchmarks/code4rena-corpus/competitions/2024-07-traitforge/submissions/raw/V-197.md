# Vulnerability details

## Impact
The `nuke` function incorrectly calculates the claim amount. This can result in users receiving more or less ETH than intended.

## Proof of Concept
Look at the claim amount calculation within the [`nuke` function](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/NukeFund/NukeFund.sol#L170): 

```solidity
function nuke(uint256 tokenId) public whenNotPaused nonReentrant {
    // ... (earlier parts of the function omitted for brevity)

    uint256 finalNukeFactor = calculateNukeFactor(tokenId); // finalNukeFactor has 5 digits
    uint256 potentialClaimAmount = (fund * finalNukeFactor) / MAX_DENOMINATOR;
    uint256 maxAllowedClaimAmount = fund / maxAllowedClaimDivisor;

    uint256 claimAmount = finalNukeFactor > nukeFactorMaxParam
      ? maxAllowedClaimAmount
      : potentialClaimAmount;

    // ... (rest of the function)
}
```

The bug is in the comparison used to determine the `claimAmount`. The `claimAmount` is determined based on the `finalNukeFactor` value, but the comparison is made against the `nukeFactorMaxParam` instead of comparing the `potentialClaimAmount` with the `maxAllowedClaimAmount`.

It compares `finalNukeFactor` with `nukeFactorMaxParam`, which are not directly related to the actual claim amounts. There a 2 problematic issues as a result of this:

1. If `finalNukeFactor > nukeFactorMaxParam` but `potentialClaimAmount < maxAllowedClaimAmount`, the user will receive `maxAllowedClaimAmount` instead of the smaller `potentialClaimAmount` potentially draining the fund unnecessarily.

2. If `finalNukeFactor <= nukeFactorMaxParam` but `potentialClaimAmount > maxAllowedClaimAmount`, the user will receive the full `potentialClaimAmount`, exceeding the intended maximum claim limit.

Both scenarios violate the intended behavior of capping claims at `maxAllowedClaimAmount`.


Consider a scenario:

Let's assume the following values:
- `fund = 1000000` (1,000,000 units of the fund)
- `MAX_DENOMINATOR = 100000`
- `maxAllowedClaimDivisor = 2` (which means `maxAllowedClaimAmount = fund / 2 = 500000`)
- `nukeFactorMaxParam = 50000`
- `defaultNukeFactorIncrease = 250`

Let's consider two tokens with different `finalNukeFactor` values:

#### Token A
- `finalNukeFactor = 60000` (greater than `nukeFactorMaxParam`)
- `potentialClaimAmount = (fund * finalNukeFactor) / MAX_DENOMINATOR = (1000000 * 60000) / 100000 = 600000`

#### Token B
- `finalNukeFactor = 40000` (less than `nukeFactorMaxParam`)
- `potentialClaimAmount = (fund * finalNukeFactor) / MAX_DENOMINATOR = (1000000 * 40000) / 100000 = 400000`

### Current Implementation

```solidity
uint256 claimAmount = finalNukeFactor > nukeFactorMaxParam
  ? maxAllowedClaimAmount
  : potentialClaimAmount;
```

#### Token A
- `finalNukeFactor (60000) > nukeFactorMaxParam (50000)`, so `claimAmount = maxAllowedClaimAmount = 500000`
- Even though `potentialClaimAmount` is 600000, the claim is capped at 500000, which is correct.

#### Token B
- `finalNukeFactor (40000) <= nukeFactorMaxParam (50000)`, so `claimAmount = potentialClaimAmount = 400000`
- This is also correct.

### Now here is the problematic scenario:

Consider a case where `finalNukeFactor` is just slightly above `nukeFactorMaxParam` but `potentialClaimAmount` is still less than `maxAllowedClaimAmount`. Lets call it Token C

#### Token C
- `finalNukeFactor = 51000` (slightly greater than `nukeFactorMaxParam`)
- `potentialClaimAmount = (fund * finalNukeFactor) / MAX_DENOMINATOR = (1000000 * 51000) / 100000 = 510000`

With the current implementation:
- `finalNukeFactor (51000) > nukeFactorMaxParam (50000)`, so `claimAmount = maxAllowedClaimAmount = 500000`
- This is incorrect because `potentialClaimAmount` (510000) is less than `maxAllowedClaimAmount` (500000).

### The correct smplementation should rather be:

```solidity
uint256 claimAmount = potentialClaimAmount > maxAllowedClaimAmount
  ? maxAllowedClaimAmount
  : potentialClaimAmount;
```

#### Token A
- `potentialClaimAmount (600000) > maxAllowedClaimAmount (500000)`, so `claimAmount = maxAllowedClaimAmount = 500000`
- Correctly capped at 500000.

#### Token B
- `potentialClaimAmount (400000) <= maxAllowedClaimAmount (500000)`, so `claimAmount = potentialClaimAmount = 400000`
- Correctly set to 400000.

#### Token C
- `potentialClaimAmount (510000) > maxAllowedClaimAmount (500000)`, so `claimAmount = maxAllowedClaimAmount = 500000`
- Correctly capped at 500000.


As seen above, the current implementation incorrectly assigns `maxAllowedClaimAmount` based on the `finalNukeFactor` comparison, which can lead to incorrect claim amounts. The fix ensures that the claim amount is always correctly capped based on the actual calculated `potentialClaimAmount` and `maxAllowedClaimAmount`, preventing users from claiming more than they should.

## Recommended Mitigation Steps
Replace the incorrect comparison with a direct comparison between `potentialClaimAmount` and `maxAllowedClaimAmount`:

```diff
function nuke(uint256 tokenId) public whenNotPaused nonReentrant {
    // ... (earlier parts of the function remain unchanged)

    uint256 finalNukeFactor = calculateNukeFactor(tokenId);
    uint256 potentialClaimAmount = (fund * finalNukeFactor) / MAX_DENOMINATOR;
    uint256 maxAllowedClaimAmount = fund / maxAllowedClaimDivisor;

-   uint256 claimAmount = finalNukeFactor > nukeFactorMaxParam
+   uint256 claimAmount = potentialClaimAmount > maxAllowedClaimAmount
      ? maxAllowedClaimAmount
      : potentialClaimAmount;

    // ... (rest of the function omitted for brevity but remains unchanged)
}
```

This change ensures that the `claimAmount` is always the lesser of `potentialClaimAmount` and `maxAllowedClaimAmount`, correctly implementing the intended claim limit logic.
