# Vulnerability details

To mint new tokens using the [mintWithBudget()](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L202-L225) function. This function takes a proof parameter to verify that the caller is whitelisted, and allows them to mint multiple tokens in a single transaction, as long as they have sufficient budget (`msg.value`) to cover the total cost of minting.
```solidity
function mintWithBudget(
    bytes32[] calldata proof
)
    public
    payable
    whenNotPaused
    nonReentrant
    onlyWhitelisted(proof, keccak256(abi.encodePacked(msg.sender)))
{
    uint256 mintPrice = calculateMintPrice();
    uint256 amountMinted = 0;
    uint256 budgetLeft = msg.value;

    while (budgetLeft >= mintPrice && _tokenIds < maxTokensPerGen) {
        _mintInternal(msg.sender, mintPrice);
        amountMinted++;
        budgetLeft -= mintPrice;
        mintPrice = calculateMintPrice();
        // The following line is missing and should be added:
        // if (generationMintCounts[currentGeneration] >= maxTokensPerGen) {
        //     _incrementGeneration();
        // }
    }

    if (budgetLeft > 0) {
        (bool refundSuccess, ) = msg.sender.call{ value: budgetLeft }('');
        require(refundSuccess, 'Refund failed.');
    }
}
```
The issue is the `while` loop does not check if the generation needs to be incremented after each token is minted. The missing lines that should be added are:
```solidity
if (generationMintCounts[currentGeneration] >= maxTokensPerGen) {
    _incrementGeneration();
}
```
These lines should be placed inside the `while` loop, after updating the `mintPrice` and before the loop condition is checked again. This ensures that the generation is incremented when the mint count for the current generation reaches the `maxTokensPerGen` limit.

The contract keeps track of the current generation of tokens using the `currentGeneration` variable, and limits the number of tokens that can be minted in each generation to `maxTokensPerGen`. When the mint count for the current generation reaches this limit, the `_incrementGeneration()` internal function is called to increment the generation number and reset the mint count for the new generation.

However, there is an issue in the `mintWithBudget()` function where it does not correctly increment the generation when the mint count reaches the limit. The function uses a `while` loop to mint tokens as long as the user has sufficient budget and the total number of tokens minted (`_tokenIds`) is less than `maxTokensPerGen`. Inside the loop, it calls the _mintInternal() function to mint each token and update the relevant state variables.

The issue is that `mintWithBudget()` does not check if the generation needs to be incremented after each token is minted. As a result, if the mint count reaches `maxTokensPerGe`n in the middle of the loop, the function will continue minting tokens in the same generation, exceeding the intended limit.

The `incrementGenerationRule` is failing when the mint count for the current generation reaches `maxTokensPerGen`, calling a public function that internally calls `_incrementGeneration()` should increment the generation number and reset the mint count for the new generation to 0. However, this is not happening correctly in the `mintWithBudget()` function.

## Impact
If the generation is not incremented correctly when the mint count reaches the limit, it could lead to several issues:

   1. More tokens than intended could be minted in a single generation, breaking any assumptions or limitations based on the `maxTokensPerGen` variable.
   2. The `currentGeneration` variable might not accurately reflect the actual generation of the minted tokens, leading to inconsistencies in token metadata and potential confusion for users.
   3. If the generation is not incremented, the minting price (`calculateMintPrice()`) might not be updated correctly, as it depends on the `priceIncrement` and `priceIncrementByGen` variables, which are adjusted when a new generation starts.

## Proof of Concept
1. Assume `maxTokensPerGen` is set to 10, and the current generation is 1.
2. User Alice calls `mintWithBudget()` with a budget of 15 ETH, enough to mint 15 tokens at the current price.
3. The function starts minting tokens in a loop, calling `_mintInternal()` for each token.
4. When the 10th token is minted, the mint count for generation 1 reaches `maxTokensPerGen`.
5. However, the function continues minting the remaining 5 tokens without incrementing the generation, resulting in a total of 15 tokens minted in generation 1, exceeding the intended limit of 10.

```diff
while (budgetLeft >= mintPrice && _tokenIds < maxTokensPerGen) {
    _mintInternal(msg.sender, mintPrice);
    amountMinted++;
    budgetLeft -= mintPrice;
    mintPrice = calculateMintPrice();

```
