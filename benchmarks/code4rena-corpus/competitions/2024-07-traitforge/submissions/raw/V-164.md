# Vulnerability details

## Description
There is a bug in `mintWithBudget` which `prevent minting the entire budget` if the end of a generation 1 is reach which seems unexpected and warrant `Medium` severity.

The root cause is due to the fact that the loop is bounded against `_tokenIds < maxTokensPerGen` which will limit the minting to generation 1 (the first 10000 NFT). Afterward, calling this function will not mint any NFT, so just waste gas and refund the player.

```solidity
  function mintWithBudget(
    bytes32[] calldata proof
  )
    public
    payable
    whenNotPaused
    nonReentrant
    onlyWhitelisted(proof, keccak256(abi.encodePacked(msg.sender)))
  {
    uint256 mintPrice = calculateMintPrice();
    uint256 amountMinted = 0;
    uint256 budgetLeft = msg.value;

    while (budgetLeft >= mintPrice && _tokenIds < maxTokensPerGen) { // <------------------------------
      _mintInternal(msg.sender, mintPrice);
      amountMinted++;
      budgetLeft -= mintPrice;
      mintPrice = calculateMintPrice();
    }
    if (budgetLeft > 0) {
      (bool refundSuccess, ) = msg.sender.call{ value: budgetLeft }('');
      require(refundSuccess, 'Refund failed.');
    }
  }
```  


## Impact
- Player calling `mintWithBudget` once generation 1 is almost all minted, will not have their entire budget spent in minting, as the minting will stop once generation 1 is fully minted.
- Player calling `mintWithBudget` after generation 1 is fully minted will just `waste gas`, as the function will not even enter the loop, hence not minting, and the player will get refunded almost entirely (minus the gas spent in this function).
- Player sending a big amount of ETH will have their transaction `run out of gas` and revert.

## Recommended Mitigation Steps
Apply the following patch to resolve this issue. Be aware that the `gasleft() > 100_000` condition is important, as otherwise the transaction could run out of gas. Note that I didn't dig much into fine tuning 100k gas, so that could be reduce a bit probably.
