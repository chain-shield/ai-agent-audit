# Vulnerability details

## Description
There is a bug in `EntityForging::getListedTokenIds` when the player is unlisting a forger NFT which still return the previous id as if the NFT would `still be listed` which is innacurate and seems to warrant `Medium` severity. 

Be aware that this issue is also present in `EntityTrading` but in a more hidden way as there is not official getter, but `EntityTrading::listedTokenIds` is public and will present the same issue as `EntityTrading` is not cleaning it up either.

The root cause is due to the fact that `_cancelListingForForging` is `not reseting listedTokenIds` but only listings state variable when unlisting a forger NFT. This oversight doesn't seems to cause major damage in the moment, but it's not clear either as it will affect anyone that rely on getListedTokenIds function. `TraitForgeNft::_beforeTokenTransfer` use it, but that doesn't seem to cause any issues.

## Impact
`getListedTokenIds` is not returning the proper information when an NFT is being unlisted.

## PoC
Add the following changes `EntityForging.test.ts` and run `yarn test`
We can see that the function still return 1 as if the NFT was listed.

```solidity
    it.only('getListedTokenIds should return zero if a token as been unlisted', async () => {
      const tokenId = FORGER_TOKEN_ID;
      const fee = FORGING_FEE;
      await entityForging.connect(owner).listForForging(tokenId, fee);
      await entityForging.connect(owner).cancelListingForForging(tokenId);
      const listingId = await entityForging.getListedTokenIds(tokenId);

      expect(listingId).to.equal(0);
    }); 
```

## Recommended Mitigation Steps
Apply the following patch to resolve this issue.

```diff
  function _cancelListingForForging(uint256 tokenId) internal {
    delete listings[listedTokenIds[tokenId]];
+   listedTokenIds[tokenId] = 0;

    emit CancelledListingForForging(tokenId); // Emitting with 0 fee to denote cancellation
  }
```
