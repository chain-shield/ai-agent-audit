# Vulnerability details

## Impact

Currently `EntropyGenerator` uses `blockhash` and `block.number` to generate some pseudo-random entropies. The problem is that it also uses them to generate the best entropy that's possible to obtain with `999999` feature. And as `blockhash` and `block.number` are pretty predictable values and can be gained by validators - it makes the whole process unfair towards other participants.


## Proof of Concept

`initializeAlphaIndices` uses `blockhash` and `block.number` to determine slot index selection and number index selection point of `999999` entropy:

https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/EntropyGenerator/EntropyGenerator.sol#L207-209
```
 uint256 hashValue = uint256(
      keccak256(abi.encodePacked(blockhash(block.number - 1), block.timestamp))
    );
```

The problem is that these values can be known by validators beforehand and hence their slot index selection point and number index selection point can be easily determined:

https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/EntropyGenerator/EntropyGenerator.sol#L211-215
```
  uint256 slotIndexSelection = (hashValue % 258) + 512;
    uint256 numberIndexSelection = hashValue % 13;

    slotIndexSelectionPoint = slotIndexSelection;
    numberIndexSelectionPoint = numberIndexSelection;

```

Manual review.

## Recommended Mitigation Steps

Use Chainlink VRF services or some alternative source of randomness.
