# Vulnerability details

## Impact
Hackers could drain the funds because of the reentrancy of claim().

## Proof of Concept
(1)
An attacker can reenter the DevFund.sol::claim() function, since info.pendingRewards is not set to the Checks-Effects-Interactions (CEI) pattern.

(2)
An attacker can reenter the DevFund.sol::claim() function, since info.rewardDebt is not set to the Checks-Effects-Interactions (CEI) pattern.

uint256 pending = info.pendingRewards +
      (totalRewardDebt - info.rewardDebt) *
      info.weight;


Exploitation Steps:
Attacker is a malicious contract, the malicious contract calls DevFund::claim().
On receive, the malicious contract executes a crafted receive().
In attacker::receiver(), attacker calls DevFund::claim() again.

## Tools Used
Manually reviewed.

## Recommended Mitigation Steps
Adhere to the Checks-Effects-Interactions (CEI) pattern.

      function claim() external whenNotPaused nonReentrant {
        DevInfo storage info = devInfo[msg.sender];

        uint256 pending = info.pendingRewards +
          (totalRewardDebt - info.rewardDebt) *
          info.weight;

        if (pending > 0) {
          info.rewardDebt = totalRewardDebt;
          info.pendingRewards = 0;
          uint256 claimedAmount = safeRewardTransfer(msg.sender, pending);
          info.pendingRewards = pending - claimedAmount ;
          emit Claim(msg.sender, claimedAmount);
        }
      }
