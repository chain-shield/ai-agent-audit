# Vulnerability details

## Impact

The `TraitForgeNft.mintToken` function is used to mint new `TraitForgeNfts`. The `mintToken` function initially calculates the `mintPrice` of the NFT to be minted and then passes this value to the `TraitForgeNft._mintInternal` function call. The `_mintInternal` function will mint the respective NFT and update the state variables pertaining to the newly minted NFT accordingly.

But there is a issue with the `mintPrice` of the `TraitForgeNfts` when the `currentGeneration` is incremented and the `NFTs` are starting to be minted in the new generation.

Now let's consider the following scenario:

1. We are currently minting in the `Generation 1` and `9999` NFTs have been minted in the `Gen 1`.
2. User A calls the `TraitForgeNft.mintToken` function to mint the `10000` NFT. 
3. The `mintPrice` is calculated as : 0.005 ether + 0.0000245*9999 ether = 0.2499755 ether.
4. Once the `10000th` NFT is minted the `generationMintCounts[currentGeneration]` is updated to `10000`.
5. Now User B calls the `TraitForgeNft.mintToken` token to mint a new token and this will be the first token of the `Generation 2`. 
6. The price of this `1st token of Gen 2` is : 0.005 ether + 0.0000245*10000 ether = 0.25 ether.
7. After this first mint the `currentGeneration` is updated to `2`, `priceIncrement` is updated to `0.0000295` and the `generationMintCounts[currentGeneration]` is updated to `1`.
7. And if the User B mints the `2nd token of Gen 2` the mintPrice will be:  0.005 ether + 0.0000295*1 ether = 0.0050295 ether.
8. Hence it is clear the first NFT minted of Gen 2 is more expensive than the 2nd NFT mited of Gen 2. (0.25 ether > 0.0050295 ether). This is not the expected mint price behavior of the protocol where each subsequent NFT of a particular generation is expected to linearly rise by the `respective priceIncrement value for that Generation`.
10. Due to this issue the `User B` has to pay more `funds (Eth)` to mint the first NFT of the `Gen 2` than he should, due to this error in logic implementation, resulting in loss of funds to User B.
11. This further contradicts the documentation of the `TraitForge` protocol where the last NFT mintPrice of the `Gen 1` is expected to be `0.25 ether` but it is currently calculated to `0.2499755 ether` as it was shown above. 
12. Hence it is clear the `mintPrice` calculation logic is broken and it contradicts the expected `mintPrice` calculation required by the protocol.

The above vulnerability occurs since the `_incrementGeneration()` is called at the beginning of the `_mintInternal` function before the `currentGeneration` and the `generationMintCounts[currentGeneration]` states are updated. Hence the code is unable to correctly identify the `completion` of a generation.

## Recommended Mitigation Steps

Hence it is recommended to execute the `_incrementGeneration()` and its related logic after the `currentGeneration` and the `generationMintCounts[currentGeneration]` states are updated. By doing so the `generation will be incremented` if all the `10000 NFTs` are minted of the current generation, before the `mintPrice` for the `next NFT mint` is calculated.

The modified code snippet is as follows:

```solidity
  function _mintInternal(address to, uint256 mintPrice) internal {

    _tokenIds++;
    uint256 newItemId = _tokenIds;
    _mint(to, newItemId);
    uint256 entropyValue = entropyGenerator.getNextEntropy();

    tokenCreationTimestamps[newItemId] = block.timestamp;
    tokenEntropy[newItemId] = entropyValue;
    tokenGenerations[newItemId] = currentGeneration;
    generationMintCounts[currentGeneration]++;
    initialOwners[newItemId] = to;

    if (generationMintCounts[currentGeneration] >= maxTokensPerGen) {
      _incrementGeneration();
    }    

    if (!airdropContract.airdropStarted()) {
      airdropContract.addUserAmount(to, entropyValue);
    }

    emit Minted(
      msg.sender,
      newItemId,
      currentGeneration,
      entropyValue,
      mintPrice
    );

    _distributeFunds(mintPrice);
  }
```
