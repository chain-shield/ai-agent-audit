# Vulnerability details

## Details
- The forge potential is reset every year and starts accounting from the mint timestamp as mentioned in the docs, [here](https://github.com/TraitForge/GitBook/blob/main/TraitForger%20Entity/Forge%20Potential%20.md?plain=1#L9)
- So, initially when for a entity the `_resetForgingCountIfNeeded` is called for first time then their `lastForgeResetTimestamp` would be 0, and to allow forge potential to reset exactly after 1 year from mint, then it is expected that `lastForgeResetTimestamp` should be set to the mint time stamp but instead it is set to the current block timestamp.
- Setting it to the current timestamp will make the forge potential to be reset after more than a year from the mint time, as current block timestamp maybe much later than the mint timestamp depending on when the user has actually called the `listForForging` or `forgeWithListed` function.

- Similarly, for the case when `_resetForgingCountIfNeeded` is called after 1 year from `lastForgeResetTimestamp`, then it resets the `lastForgeResetTimestamp` to current timestamp instead of `lastForgeResetTimestamp[tokenId] + oneYear`.
- The point is that the forge potential is to be reset every year from the last reset timestamp after mint, and in order to reset it every year it should be set to the `its current value + oneYear`.


## Impact
Entity's forge potential will not be reset every year from mint timestamp, due to incorrect assignment of `lastForgeResetTimestamp` in `_resetForgingCountIfNeeded`.

## Proof of Concept
```solidity
  function _resetForgingCountIfNeeded(uint256 tokenId) private {
    uint256 oneYear = oneYearInDays;
    if (lastForgeResetTimestamp[tokenId] == 0) {
      lastForgeResetTimestamp[tokenId] = block.timestamp;
    } else if (block.timestamp >= lastForgeResetTimestamp[tokenId] + oneYear) {
      forgingCounts[tokenId] = 0; // Reset to the forge potential
      lastForgeResetTimestamp[tokenId] = block.timestamp;
    }
  }
```

### Case 1 (for if block):
- Suppose that a forger lists their entity half a year after mint, then their `lastForgeResetTimestamp` will be set to current block timestamp.
- Now, as per docs, their forge potential should reset after 1 year from mint, but as their `lastForgeTimestamp` was set to `mint time stamp + half year`, then their forge potential would only reset 1.5 year after mint instead of 1 year.

### Case 2 (for else if block):
- Consider that entity's `lastForgeResetTimestamp` was set correctly to mint timestamp.
- Now, after 1 year from mint timestamp their forge potential would be reset.
- Now, consider the case where forger lists their entity after `1.5` year after mint, then it would allow the execution of `else if` block, and in their the `lastForgeResetTimestamp` is set to current block timestamp.
- Now the next forge potential reset will occur 2.5 year after mint, but according to docs it should occur every year from mint timestamp, i.e, it was expected to occur after 2 year.

Thus, due to incorrect set up of `lastForgeResetTimestamp` in `_resetForgingCountIfNeeded`, the forge potential is not reset every year after mint timestamp.

## Recommended Mitigation Steps
Perform changes as below:
```diff
  function _resetForgingCountIfNeeded(uint256 tokenId) private {
    uint256 oneYear = oneYearInDays;
+   uint256 nftMintTimestamp = nftContract.getTokenCreationTimestamp(tokenId);
+   uint256 timePassedFromMint = block.timestamp - nftMintTimestamp;
+   uint256 timePassedInYears = timePassedFromMint / oneYear;
    if (lastForgeResetTimestamp[tokenId] == 0) {
-     lastForgeResetTimestamp[tokenId] = block.timestamp;
+     lastForgeResetTimestamp[tokenId] = nftMintTimestamp + timePassedInYears * oneYear;
    } else if (block.timestamp >= lastForgeResetTimestamp[tokenId] + oneYear) {
      forgingCounts[tokenId] = 0; // Reset to the forge potential
-     lastForgeResetTimestamp[tokenId] = block.timestamp;
+     lastForgeResetTimestamp[tokenId] = nftMintTimestamp + timePassedInYears * oneYear;
    }
  }
```
