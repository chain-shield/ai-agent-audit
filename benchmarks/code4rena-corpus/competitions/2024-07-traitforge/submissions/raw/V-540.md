# Vulnerability details

## Vulnerability Details
There are two important variables while calculation of the claim amount:
- nukeFactorMaxParam
- maxAllowedClaimDivisor
Those are highly related with each other, their initial values are 50000 and, 2 respectively. In order to understand the problem, we need to understand why are they highly related with each other. 
```solidity
uint256 finalNukeFactor = calculateNukeFactor(tokenId); // finalNukeFactor has 5 digits
    uint256 potentialClaimAmount = (fund * finalNukeFactor) / MAX_DENOMINATOR; // Calculate the potential claim amount based on the finalNukeFactor
    uint256 maxAllowedClaimAmount = fund / maxAllowedClaimDivisor; // Define a maximum allowed claim amount as 50% of the current fund size

    // Directly assign the value to claimAmount based on the condition, removing the redeclaration
    uint256 claimAmount = finalNukeFactor > nukeFactorMaxParam // MAX_DENOMINATOR / 2
      ? maxAllowedClaimAmount
      : potentialClaimAmount;
```
In the lines above, we see a percentage calculation. Player will receive some rewards based on the the nuke factor but it also limited at nukeFactorMaxParam (50000) point. MAX_DENOMINATOR is equal to 100000. Basicly, with that parameters we can say that user can get 50% of the fund at max and, this is why maxAllowedClaimDivisor is equal to 2. Because MAX_DENOMINATOR / nukeFactorMaxParam = maxAllowedClaimDivisor. 

The separate set functions for maxAllowedClaimDivisor and nukeFactorMaxParam is pointless because maxAllowedClaimDivisor always should be equal to MAX_DENOMINATOR / nukeFactorMaxParam in order to make the calculation of claimAmount correctly.

In the attack vector, idea is same. If owner decrease the maxAllowedClaimDivisor. Player can nuke his/her NFT for extra reward. 

## Impact
Miscalculation of claimAmount ( loss of funds )

## Proof of Concept
In the scenario, let say Alice has a NFT which has 26000 nuke factor and the parameters are equal to following values (25000, 4). 

If owner set the maxAllowedClaimDivisor to 2, every NFT which has more nuke factor than 25000 will get 50% of the fund because nukeFactorMaxParam is still 25000 and maxAllowedClaimDivisor is 2. 

Alice has 26000 nuke factor and her potential yield will be 26%. Then she will get 50% of the fund which is higher than her potential because max divisor is equal to 2 and it allows to get 50% of the fund

```solidity
function test_setMaxDivisor() public {

        vm.roll(20456836); // deterministic entropy
        vm.startPrank(Alice);
        uint256 entropy;
        uint256 tokenId = 0;

        // Skipping non-aging NFTs (It's another findings topic :) )
        while (entropy % 10 == 0){
            tokenId++;
            traitForgeNft.mintToken{value: 1 ether}(proof);
            entropy = traitForgeNft.getTokenEntropy(tokenId);
        }

        vm.warp(block.timestamp + 365 days);
        uint256 nukeFactor = nukeFund.calculateNukeFactor(tokenId);
        console.log("Entropy: %s", entropy);
        console.log("Nuke factor: %s", nukeFactor);
        vm.stopPrank();

        uint256 MAX_DENOMINATOR = 100000;

        // setting maxValue to 10000 for easy calculation, maxAllowedClaimDivisor * nukeFactorMaxParam = MAX_DENOMINATOR
        vm.startPrank(Owner);
        nukeFund.setMaxAllowedClaimDivisor(10);
        nukeFund.setNukeFactorMaxParam(10000);
        vm.stopPrank();


        uint256 fund = nukeFund.getFundBalance();
        uint256 potential_value = fund * nukeFactor / MAX_DENOMINATOR;
        console.log("Fund balance: %s", fund);
        console.log("Potential value: %s", potential_value);
        console.log("Percentage of potential value: %s%", potential_value * 100 / fund);

        // Right now we can claim 10% of fund which is lower than potential value because of nukeFactorMaxParam but
        // after setting maxAllowedClaimDivisor to 2, we can claim 50% of fund

        vm.startPrank(Owner);
        nukeFund.setMaxAllowedClaimDivisor(2);
        vm.stopPrank();

        vm.startPrank(Alice);
        traitForgeNft.approve(address(nukeFund), tokenId);
        uint256 balance_before = address(Alice).balance;
        nukeFund.nuke(tokenId);
        uint256 balance_after = address(Alice).balance;
        console.log("Claimed value: %s", balance_after - balance_before);
        console.log("Percentage of claimed: %s%", (balance_after - balance_before) * 100 / fund);
        vm.stopPrank();

    }
```

Setting the maxAllowedClaimDivisor separately is vulnerable because player can get higher value than potential value ( Opposite scenario can also occur, player can get less value than expected while increasing the divisor). Let say owner tried to modify both maxAllowedClaimDivisor and nukeFactorMaxParam in the same time in order to save the following equation balance: 
```console
MAX_DENOMINATOR / nukeFactorMaxParam = maxAllowedClaimDivisor
``` 
This time front run problems can occur. Players can use this opportunity with front run.

## Recommended Mitigation Steps

I believe best approach is removing maxAllowedClaimDivisor and if the nuke factor higher than max value, calculating the claimAmount with following way is correct:

```solidity
uint256 claimAmount = finalNukeFactor > nukeFactorMaxParam 
      ? (fund * nukeFactorMaxParam) / MAX_DENOMINATOR
      : potentialClaimAmount;
```
