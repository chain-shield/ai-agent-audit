# Vulnerability details

## Impact
As there is no check that forgingCounts[tokenId] <= forgePotential after  forgingCounts[forgerTokenId]++  in function forgeWithListed, as a result forgingCounts can be bigger than forgePotential for a tokenid.


## Proof of Concept
1. Let’s assume, a tokenid’s forgePotential = 5, currently forgingCounts[tokenId] = 5(i.e Entity has reached its forging limit) and lastForgeResetTimestamp[tokenId] is 1 january, 2024 for this tokenid.

2. So lastForgeResetTimestamp will be updated after 1 january,2025 and the tokenid owner should not get chance to list for forging for this tokenid before 1 january , 2025 as currently forgingCounts[tokenId] = 5(i.e Entity has reached its forging limit).

3. But the  tokenid owner again calls function listForForging before 1 january 2025, see the require statement in this function i.e require(
      forgePotential > 0 && forgingCounts[tokenId] <= forgePotential,
      'Entity has reached its forging limit'
    );
As forgePotential > 0 and  forgingCounts[tokenId] i.e 5 is equal to forgePotential i.e 5, so the tokenid is again listed for forging.


4. Now a mergerTokenId owner calls function forgeWithListed with this forgerTokenId, now forgingCounts for this forgerTokenId is updated to 6 i.e forgingCounts[forgerTokenId] = 6. This forgerTokenId’s forgePotential is 5, but the  forgerTokenId is forged 6 times which is unintentional for the protocol.


## Tools Used
manual review
## Recommended Mitigation Steps
After increasing forgingCounts for a tokenid(i.e forgingCounts[forgerTokenId]++), check forgingCounts can’t  be bigger than forgePotential i.e forgingCounts[tokenId] <= forgePotential in the function forgeWithListed.
