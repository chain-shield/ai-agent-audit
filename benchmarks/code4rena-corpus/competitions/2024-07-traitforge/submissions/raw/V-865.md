# Vulnerability details

## Impact

"The Golden God" is an exceptionally rare NFT with a perfect entropy value of "999999." To ensure its rarity, the protocol is designed to keep this specific value out of the `EntropyGenerator::entropySlots` array during the first two passes of entropy generation, and only deliberately set it in the final pass. The `EntropyGenerator::entropySlots` array consists of 770 slots, each slot containing 13 pseudo-random 6-digit values, forming a 78-digit number per slot.

The issue arises in the way the protocol checks whether the pseudo-randomly generated value matches the "Golden God" entropy value. The check is implemented in the functions `EntropyGenerator::writeEntropyBatch1()` and `EntropyGenerator::writeEntropyBatch2()` as follows:

`require(pseudoRandomValue != 999999, 'Invalid value, retry.');`

The problem is that this check is fundamentally flawed because the `pseudoRandomValue` being generated and checked is not a simple 6-digit number; instead, it is a 78-digit number composed of 13 concatenated 6-digit values. The check, as written, attempts to compare this 78-digit number against "999999," a 6-digit number.

Since the pseudo-random value generated is a large composite number and not a single 6-digit value, the comparison `pseudoRandomValue != 999999` is meaningless. It will never trigger correctly because it is trying to compare an entire 78-digit number to a simple 6-digit number. As a result, the check to exclude the "Golden God" entropy value during the initial passes is ineffective.

This makes "The Golden God" NFT not so rare and breaks a key invariant of the protocol - "The Golden God" should only exist in the third batch (from slot 512 to slot 770).

## Proof of Concept

If we look at `EntorpyGenerator::writeEntropyBatch1()` we can see how the pseudo-random value is generated and then compared to the perfect entropy:

```solidity
  function writeEntropyBatch1() public {
    require(lastInitializedIndex < batchSize1, 'Batch 1 already initialized.');

    uint256 endIndex = lastInitializedIndex + batchSize1; // calculate the end index for the batch
    unchecked {
      for (uint256 i = lastInitializedIndex; i < endIndex; i++) {
        uint256 pseudoRandomValue = uint256(
          keccak256(abi.encodePacked(block.number, i))
        ) % uint256(10) ** 78; // generate a  pseudo-random value using block number and index
@->        require(pseudoRandomValue != 999999, 'Invalid value, retry.');
        entropySlots[i] = pseudoRandomValue; // store the value in the slots array
      }
    }
    lastInitializedIndex = endIndex;
  }
```

The `pseudoRandomValue` is a 78-digit value but we compare it to a 6-digit one. The same goes for the `EntorpyGenerator::writeEntropyBatch2()` function.

## Recommended Mitigation Steps

In `EntorpyGenerator::writeEntropyBatch1()` and `EntorpyGenerator::writeEntropyBatch2()` the `pseudoRandomValue` should be checked if it containts the "999999" entropy instead of directly comparing it.
