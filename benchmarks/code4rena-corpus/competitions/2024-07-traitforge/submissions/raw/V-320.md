# Vulnerability details

## Impact
In the `TraitForgeNft` contract, the `_beforeTokenTransfer()` function is designed to cancel any pending `ListingForForging` for the `tokenId` being transferred. This is to ensure that the `new owner` has full control over their `NFT`, including the decision to list it for `forging`. 

However, this `cancellation` also occurs when the `from` address is the same as the `to` address, which means there is no actual change in `ownership`. This unnecessary cancellation can lead to `user inconvenience`.

## Proof of Concept
Current [`_beforeTokenTransfer()`](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L367-L395) Implementation:
```solidity
function _beforeTokenTransfer(
    address from,
    address to,
    uint256 firstTokenId,

  ) internal virtual override {
    super._beforeTokenTransfer(from, to, firstTokenId, batchSize);

    /// @dev don't update the transferred timestamp if from and to address are same

>>  if (listedId > 0) { //@audit-info If listed, cancel

        listedId
      );
      if (
        listing.tokenId == firstTokenId &&
        listing.account == from &&
        listing.isListed

>>      entityForgingContract.cancelListingForForging(firstTokenId);
      }
    }

  }
```
**Issue**:
The `listing cancellation` logic does not distinguish between `actual transfers` and `self-transfers`. As a result, `listings` are unnecessarily canceled even when there is no change in `ownership`. Users may find their listings canceled unexpectedly when they perform self-transfers, leading to inconvenience.

## Recommended Mitigation Steps
Just as done with `lastTokenTransferredTimestamp`, modify `_beforeTokenTransfer()` function to check if the `from` address is different from the `to` address before canceling any `listings`. This ensures that `listings` are only canceled when there is an actual change in `ownership`.
