# Vulnerability details

## Impact

The `TraitForgeNft._incrementGeneration` function is called by the `_mintInternal` and `_mintNewEntity` functions. The `_incrementGeneration` is called when the total number of NFTs of the `currentGeneration` have been minted. In this scenario we need to move to the next generation for the NFT minting thus the `_incrementGeneration` is called to increment the generation to the next level.

In the `TraitForgeNft._incrementGeneration` function the following logic is executed. 

```solidity
    currentGeneration++;
    generationMintCounts[currentGeneration] = 0; 
```

The `generationMintCounts[currentGeneration]` is set to `0` when the `current generation is incremented`. But this state update is errorneous. This is because the `generationMintCounts[gen]` for any higher `generation (gen)` can be incremented via `forging` of two previous generation `forger` and `merger`. 

As a result the `generationMintCounts[gen] > 0` (where `gen > currentGeneration`) state will occur when the `forging` has happened and the `NFTs` are minted in the higher generations. This is evident in the `_mintNewEntity` function where the `generationMintCounts[gen]++;` is executed for the higher generation (gen). 

But the issue is when the total NFT amount (10000) of the `currentGeneration` is minted the `currentGeneration` is incremented and the  `generationMintCounts[currentGeneration]` set to `0` thus erasing the state of the existing NFT count of the `generation` which was set via the forging operations. 

This will completely break the `NFT minting` logic of the `TraitForgeNFTs` in the `higher generations`. Since now more than `10000` NFTs can be minted for a particular `higher generation` since the `generationMintCounts[currentGeneration]` is reset to `0`. 

Secondly the `mintPrice` for subsequent `NFT mints` will also be errorneous. Since now the `generationMintCount` will start from `0` rather than the `exisitng mint count which occurred via forging`. 

This issue will make more funds to the `protocol` than the documented amount since more than `10000` NFTs can be minted per `higher generation`.

## Recommended Mitigation Steps

Hence it is recommended to remove the `generationMintCounts[currentGeneration] = 0;` logic execution from the `_incrementGeneration` function thus keeping the `generationMintCounts[gen]` state inplace for subsequent generations (gen) without resetting them. This will allow the correct tracking of the `generationMintCounts` amount for all the generations which are minted via both `forge` and `mint`.

The modified `_incrementGeneration` should be as follows:

```solidity
  function _incrementGeneration() private {
    require(
      generationMintCounts[currentGeneration] >= maxTokensPerGen,
      'Generation limit not yet reached'
    );
    currentGeneration++;
    priceIncrement = priceIncrement + priceIncrementByGen;
    entropyGenerator.initializeAlphaIndices();
    emit GenerationIncremented(currentGeneration);
  }
```
