# Vulnerability details

## Impact

Impact: High
Likelihood: High

When a function is internal this means that everyone can call the function if they inherit the contract the function is in and have a function which calls the parent function. In this vulnerability the case is the same as the function `EntityForging::_cancelListingForForging`


## Proof of Concept
1. Deploy all contracts in the project. 
2. Attacker waits for the project to be unpaused and everything starts working normally.
3. Attacker creates a new contract X which inherits `EntityForging.sol`
4. Attacker creates a function inside the contract X which calls `_cancelListingForForging` of its parent contract with different valid tokenIds as parameter, thus canceling listings for forging.

## Tools Used
Solidity, VSCode

## Recommended Mitigation Steps

Two propositions for a bug fix:

1. First one requires to check the owner of the tokenId before deleting it:
```solidity
  function _cancelListingForForging(uint256 tokenId) internal {
+   require(
+      nftContract.ownerOf(tokenId) == msg.sender ||
+        msg.sender == address(nftContract),
+      'Caller must own the token'
+    );
    delete listings[listedTokenIds[tokenId]];

    emit CancelledListingForForging(tokenId); // Emitting with 0 fee to denote cancellation
  }
```

2. Second one is simpler, just change the function from internal to private:
```solidity
+  function _cancelListingForForging(uint256 tokenId) private { // <---- make private
-  function _cancelListingForForging(uint256 tokenId) internal {

    delete listings[listedTokenIds[tokenId]];

    emit CancelledListingForForging(tokenId); // Emitting with 0 fee to denote cancellation
  }
```
For bug fix 2 has to be considered whether the protocol team desires to enable everyone who inherits the `EntityForging.sol` contract to be able to do so, if that is the case then solution 2 will not be a potential solution and will have to resort to solution 1.
