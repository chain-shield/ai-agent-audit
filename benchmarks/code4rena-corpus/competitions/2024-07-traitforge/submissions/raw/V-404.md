# Vulnerability details

## Description 

The vulnerability is in the range check for the `writeEntropyBatch2` function. The current implementation uses `batchSize2` (set to 512)
 ```uint256 private batchSize2 = 512;``` as the upper bound for the `lastInitializedIndex` check, which allows the function to write into the first slot of Batch 3. This creates an overlap between Batch 2 and Batch 3, violating the intended separation of batches.


The inconsistency is in the values of `batchSize2` and `maxSlotIndex`:

`batchSize2` is set to `512`, meaning the end of Batch 2 should be at index `511` (batchSize2 - 1), however, `maxSlotIndex` is set to `770`, suggesting the total slots available, given the current logic:

Batch 1 initializes indices 0 to 255 (256 slots).
Batch 2 should initialize indices 256 to 511 (256 slots).
Batch 3 should initialize indices 512 to 769 (258 slots).
The issue is that the end index for Batch 2 is defined by `batchSize2`, which equals 512, indicating the next slot (512) would fall under Batch 2's range. However, this should not be the case since Batch 3 starts at index `512`.



## Impact

This vulnerability can lead to multiple issues:

1. incorrect initialization sequence, potentially resulting in unintended behavior or conflicts when accessing and using entropy values.

2. Data Corruption: Batch 2 could overwrite the first slot of Batch 3, leading to data inconsistency.

3. Incorrect Entropy Distribution: an overlap may cause an uneven distribution of entropy values, potentially affecting the randomness quality.




## Proof of Concept
```
const { expect } = require('chai');
const { ethers } = require('hardhat');

describe('EntropyGenerator', function () {
  let EntropyGenerator;
  let entropyGenerator;
  let owner;
  let allowedCaller;

  beforeEach(async function () {
    [owner, allowedCaller] = await ethers.getSigners();

    // Deploy EntropyGenerator contract
    EntropyGenerator = await ethers.getContractFactory('EntropyGenerator');
    entropyGenerator = await EntropyGenerator.deploy(allowedCaller.address);
    await entropyGenerator.deployed();
  });

  it('should allow Batch 2 to overwrite Batch 3 indices due to incorrect range check', async function () {
    // Initialize Batch 1
    await entropyGenerator.writeEntropyBatch1();

    // Manually set lastInitializedIndex to 511 (end of Batch 2's range)
    await ethers.provider.send('hardhat_setStorageAt', [
      entropyGenerator.address,
      ethers.utils.hexZeroPad('0', 64), // Slot 0 for lastInitializedIndex
      ethers.utils.hexZeroPad(ethers.BigNumber.from(511).toHexString(), 32),
    ]);

    // Attempt to initialize Batch 2 starting from index 511
    await entropyGenerator.writeEntropyBatch2();

    // Fetch lastInitializedIndex after writing Batch 2
    const lastInitializedIndex = await entropyGenerator.getLastInitializedIndex();

    // This test demonstrates the vulnerability by allowing lastInitializedIndex to be 512, overlapping with Batch 3
    console.log('Last Initialized Index after Batch 2:', lastInitializedIndex.toString());

    // The incorrect behavior here is that lastInitializedIndex should not reach 512, but it does.
    expect(lastInitializedIndex).to.be.above(511);
  });
});
```

## Recommended Mitigation Steps

1. Redefine `batchSize2`

```
uint256 private batchSize2 = 511;
```

OR 

2. Adjust the range check in writeEntropyBatch2:

```
require(lastInitializedIndex >= batchSize1 && lastInitializedIndex < batchSize2 - 1, 'Batch 2 not ready or already initialized.');
```
