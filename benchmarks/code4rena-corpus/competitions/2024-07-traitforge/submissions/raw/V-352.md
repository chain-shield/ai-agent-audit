# Vulnerability details

## Description

The `NukeFund` contract implements a mechanism to prevent premature "nuking" (burning for a claim) of tokens through the `canTokenBeNuked()` function. This function is designed to ensure that a token has been held for a minimum period before it can be nuked. However, the current implementation has a flaw that allows users to bypass this restriction.

The `canTokenBeNuked()` function relies on the `getTokenLastTransferredTimestamp()` method from the `nftContract` to determine the token's holding period. It calculates the token's age by subtracting this timestamp from the current block timestamp:

[NukeFund.sol#L184-L194](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/NukeFund/NukeFund.sol#L184-L194)
```solidity
File: NukeFund.sol
184:   function canTokenBeNuked(uint256 tokenId) public view returns (bool) {
185:     // Ensure the token exists
186:     require(
187:       nftContract.ownerOf(tokenId) != address(0),
188:       'ERC721: operator query for nonexistent token'
189:     );
190:     uint256 tokenAgeInSeconds = block.timestamp -
191:       nftContract.getTokenLastTransferredTimestamp(tokenId);
192:     // Assuming tokenAgeInSeconds is the age of the token since it's holding the nft, check if it's over minimum days held
193:     return tokenAgeInSeconds >= minimumDaysHeld;
194:   }

```

The issue lies in the fact that this method only considers the most recent transfer, rather than the cumulative holding period. As a result, users can reset the holding period by transferring the token to another address and then back to themselves, effectively bypassing the minimum holding period requirement.

## Impact
Users can bypass the minimum holding period by transferring the token multiple times within a short period. This allows them to "nuke" the token and claim funds from the contract without adhering to the required holding period. This undermines the intended functionality of the contract and can lead to unfair advantages and potential financial losses for the protocol.


## Proof of Concept
1. Alice mints or acquires a token.
2. Alice waits for a period shorter than `minimumDaysHeld`.
3. Alice transfers the token to Bob (who could be a separate account controlled by Alice).
4. Bob immediately transfers the token back to Alice.
5. The `getTokenLastTransferredTimestamp()` is now updated to the time of the last transfer.
6. Alice can now successfully call `canTokenBeNuked()`, as the function will only consider the time since the last transfer.
7. Alice can proceed to nuke the token, bypassing the intended holding period.

## Tools Used
Manual review

## Recommended Mitigation Steps
To address this issue, the contract should track the cumulative holding time for each token, rather than relying solely on the last transfer timestamp.
