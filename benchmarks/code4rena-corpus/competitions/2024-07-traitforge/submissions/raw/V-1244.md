# Vulnerability details

## Impact
In the EntityForging contract, the devFee is calculated during the forging process as follows:
```js
uint256 devFee = forgingFee / taxCut;
```
Here, forgingFee is essentially the _forgerListingInfo.fee. There is no validation check applied on the setter function for taxCut, which is a crucial parameter in the contract. If the admin mistakenly sets taxCut to a value greater than minimumListFee (in terms of ether), it will cause the devFee calculation to produce 0 due to integer division, effectively bypassing the devFee.

## Proof of Concept
1. The admin mistakenly sets taxCut to a value greater than minimumListFee.
2. When forgeWithListed() is called, the devFee calculation results in 0.
3. The protocol’s revenue collection via devFee is bypassed, the nukeAddress receives 0 ether.

## Tools Used
Manual Code Review

## Recommended Mitigation Steps
1. Add Validation to Setter Functions:
```js
function setTaxCut(uint256 _taxCut) external onlyOwner {
    require(_taxCut > 0, "Tax cut must be greater than 0");
    require(_taxCut <= minimumListFee, "Tax cut must be less than or equal to minimum listing fee");
    taxCut = _taxCut;
}
```
2. Add Validation to Minimum Listing Fee:
```js
function setMinimumListingFee(uint256 _fee) external onlyOwner {
    require(_fee > 0, "Listing fee must be greater than 0");
    minimumListFee = _fee;
}
```
3. Update the forgeWithlisted() function to include the following logic
```js
uint256 devFee = forgingFee / taxCut;
require(devFee > 0, "Dev fee calculation resulted in 0");
```
