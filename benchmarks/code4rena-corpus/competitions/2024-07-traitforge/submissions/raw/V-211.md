# Vulnerability details

### Impact

Block parameters including block.timestamp, block.number and blockhash are not random as they only incrementally increase allowing anyone to simply predict alphaindices for the 999999 entropy token, manipulate entropy outcomes and potentially snipe the best and rarest of items at the expense of other users.

### Proof of Concept

1. Context

To generate entropy, the protocol uses block parameters to get the random values that will determine the characteristics of the TraitNFT minted. The generated entropy is then granted to the minted NFT to serve as its characteristics. If a token gets an entropy of 999999, it is considered as the best, and the golden god. Using block parameters, in this case block.number and blockhash to generate entropy, and to initialize the golden god's indices is however not advisable.
From this [article](https://ethereum.org/en/developers/docs/oracles/#generating-verifiable-randomness)

> The original approach was to use pseudorandom cryptographic functions, such as blockhash, but these could be manipulated by miners solving the proof-of-work algorithm. 

And [here](https://docs.base.org/base-learn/docs/error-triage/#out-of-gas) with regards to use of block.timestamp:

> block.timestamp can be manipulated. DO NOT use this as a source of randomness if any value can be derived from one outcome over another!

2. Bug Location

In EntropyGenerator.sol, we can see that when initializing entropy, block.number is in use to generate the `psuedoRandomValue` parameter.

```solidity
  function writeEntropyBatch1() public {
//...
      for (uint256 i = lastInitializedIndex; i < endIndex; i++) {
        uint256 pseudoRandomValue = uint256(
          keccak256(abi.encodePacked(block.number, i))
        ) % uint256(10) ** 78; // generate a  pseudo-random value using block number and index
        require(pseudoRandomValue != 999999, 'Invalid value, retry.');
//...
  }
```

```solidity
  function writeEntropyBatch2() public {
//...
    unchecked {
      for (uint256 i = lastInitializedIndex; i < endIndex; i++) {
        uint256 pseudoRandomValue = uint256(
          keccak256(abi.encodePacked(block.number, i))
        ) % uint256(10) ** 78;
        require(pseudoRandomValue != 999999, 'Invalid value, retry.');
        entropySlots[i] = pseudoRandomValue;
      }
//...
  }
```
```solidity
  // allows setting a specific entropy slot with a value
  function writeEntropyBatch3() public {
//...
    unchecked {
      for (uint256 i = lastInitializedIndex; i < maxSlotIndex; i++) {
        uint256 pseudoRandomValue = uint256(
          keccak256(abi.encodePacked(block.number, i))
        ) % uint256(10) ** 78;
        entropySlots[i] = pseudoRandomValue;
      }
//...
  }
```

And to generate the indices for the golden god, blockhash, block.number and block.timestamp are all in use.

```solidity
  function initializeAlphaIndices() public whenNotPaused onlyOwner {
    uint256 hashValue = uint256(
      keccak256(abi.encodePacked(blockhash(block.number - 1), block.timestamp))
    );
//...
  }
```

3. Final Effect

As has been established that block parameters can be manipulated and known in advance by miners and more sophisticated. This knowledge can be used to mint the best NFTs, earning them an advantage over other users. By calling the `mintToken` or `mintWithBudget` functions at certain points when the `getNextEntropy` function would provide the best entropy values for the minted tokens, malicious users can easily gain an unfair advantage.


### Tools Used
Manual code review

### Recommended Mitigation Steps

Recommend using VRFs instead. Gelato VRF can be used since its [recommended](https://docs.base.org/docs/tools/oracles/#gelato) on Base.
