# Vulnerability details

## Impact
Incorrectly updating the `lasttransferredtimestamp` variable will unfairly affect the nuking time period of the entity.

## Proof of Concept
In the EntityTrading contract, when a user lists an NFT for sale, and then cancels this listing, the entities `lasttransferredtimestamp` is updated even though there was no transfer of the NFT. 

1. User calls listNFTForSale() function, which in turn calls the transferFrom function to transfer the NFT to address(this) to facilitate the transfer.
(https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityTrading/EntityTrading.sol#L53)

2. The transferFrom function internally calls the _beforeTokenTransfer function in TraitForgeNFT contract. Which updates the `lastTokenTransferredTimestamp` variable.

3. The same updation happens when the listing is cancelled.(https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityTrading/EntityTrading.sol#L104)

This is an unintended behavior as there is no transfer of the NFT in a general sense.
## Tools Used
Manual Review

## Recommended Mitigation Steps
Update the _beforeTokenTransfer() function in TraitForgeNFT.sol as the following (line 377):
`if (from != to && from != address(EntityTradingContract) to != address(EntityTradingContract)) {`
     ` lastTokenTransferredTimestamp[firstTokenId] = block.timestamp;`
 `   }`
