# Vulnerability details

## Impact

Each NFT has an entropy number from which we can extract the 5th number which is the forging potential (it corresponds to the number of times the token can be forged). When a user wants to list for forging he should call `EntityForging::listForForging()` and then it is checked if the user can perform a forge for this NFT:

```solidity
    require(
      forgePotential > 0 && forgingCounts[tokenId] <= forgePotential,
      'Entity has reached its forging limit'
    );
```

The problem here is that `forgingCounts[tokenId]` is incremented after this require statement in `forgeWithListed()` which gives the user a right to forge the NFT one more time than supposed to because it is <= forgePotential. This means that even if the user used all of the NFT's forge potential, he can still execute that function because `forgingCounts[tokenId] == forgePotential`. So then when `forgeWithListed()` is executed the user will have forged `forgePotential + 1` instead of just the `forgePotential`.

## Proof of Concept

Let's look at the following example:

1. Bob has an NFT with a forging potential equal to 1. (This NFT is a forger type)
2. Bob calls `EntityForging::listForForging()` to list it for forging.
3. A random user with a merger type NFT matches Bob's and then Bob's `forgingCounts[tokenId] = 1` after being incremented in the `forgeWithListed()`
4. Bob again calls `EntityForging::listForForging()` with the same tokenId and the function will execute because now `forgingCounts[tokenId] == forgePotential`.
5. After the NFT is forged Bob's `forgingCounts[tokenId] = 2`

Bob effectively forged his NFT twice instead of once (his forgePotential is 1).

## Recommended Mitigation Steps

```diff
    require(
-      forgePotential > 0 && forgingCounts[tokenId] <= forgePotential,
+      forgePotential > 0 && forgingCounts[tokenId] < forgePotential,
      'Entity has reached its forging limit'
    );
```
