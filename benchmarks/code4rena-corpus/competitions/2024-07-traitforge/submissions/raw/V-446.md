# Vulnerability details

## Impact
All contracts in the `TraitForge` protocol utilize OpenZeppelin's `Ownable` package, allowing modular access control on functionalities using the `onlyOwner` modifier. Suppose the package is used directly out of the box. In that case, it sets the underlying contract owner to be the [_msgSender()](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/dc44c9f1a4c3b10af99492eed84f83ed244203f6/contracts/access/Ownable.sol#L29), which means that whichever address deploys the code is the owner of the contract. In most cases, this would be sufficient to enforce proper only owner access to specific functionalities, however, in the context of `TraitForge` it will cause ownable issues.

## Proof of Concept

The `TraitForgeNft.sol` contract interacts with the `EntropyGenearator.sol`, where it calls the `_incrementGeneration()` function that has the `onlyOwner` modifier:

```solidity
  function _incrementGeneration() private {
__SNIP__
@>    entropyGenerator.initializeAlphaIndices(); // onlyOwner function
__SNIP__
  }
```

This function is invoked whenever the generation cap is reached to start a new one. From the above snippet, it can be seen that the only way for the `TraitForgeNft.sol` contract to be able to call this function is by being the owner of the `EntropyGenerato.sol` contract, which is not the case, as the contract does not transfer the ownership to the NFT contract (the `EntropyGenerato.sol` contract sets the NFT contract as an [allowedCaller](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntropyGenerator/EntropyGenerator.sol#L31) but this is not sufficient). Because of this whenever the maximum generation cap is reached, users will be blocked from minting due to `Ownable: caller is not the owner` errors.

> [!IMPORTANT]  
> The ownership-related issues are not only connected to the `EntropyGenerator.sol` contract. The NFT contract also interacts with the `Airdrop.sol` contract and invokes the `subUserAmount(...)` and `addUserAmount(...)` functions, whenever an NFT is minted or burned. Both of these functions are protected with the `onlyOwner` modifier, which means that the `TraitForgeNft` contract needs to be set as the airdrop's owner, otherwise minting will not be possible. I have added PoC to showcase this issue, even though the `Airdrop.sol` contract is out of scope.

For the following tests I have used Foundry following HardHat's foundry [integration](https://hardhat.org/hardhat-runner/docs/advanced/hardhat-and-foundry) guide. The following tests can be run with `forge test --mt testMintIsBlockedDueToOwnership` + `forge test --mt testGenerationIncreaseBlockedDueToOwnership`.

## Recommended Mitigation Steps

Use the `trasnferOwnership(...)` function from OZ's `Ownable` package, to properly set the owner of the `Airdrop.sol` and `EntropyGenerator.sol` contracts to be the `TraitForgeNft.sol` contract.

`EntropyGenerator.sol`

```diff
@@ -30,6 +30,8 @@ contract EntropyGenerator is IEntropyGenerator, Ownable, Pausable {
   constructor(address _traitForgetNft) {
     allowedCaller = _traitForgetNft;
     initializeAlphaIndices();
+
+    transferOwnership(_traitForgetNft);
   }
```

If the `EntropyGenerator.sol` needs to have a different owner, so that the NFT contract is just an `allowedCaller`, then the modifier of the `initializeAlphaIndices()` function needs to be changed to `onlyAllowedCaller`.

`Airdrop.sol` - even though it is out of scope

```diff
@@ -17,6 +17,10 @@ contract Airdrop is IAirdrop, Ownable, ReentrancyGuard, Pausable {
 
   mapping(address => uint256) public userInfo;
 
+  constructor(address _traitForgeNft) {
+    transferOwnership(_traitForgeNft);
+  }
+
```

Again, if the owner and NFT contract need to be different entities for the Airdrop, add a proper modifier and set it as per function access control requirements.
