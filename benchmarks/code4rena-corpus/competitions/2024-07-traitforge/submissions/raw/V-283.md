# Vulnerability details

## Impact
The `_incrementGeneration()` function in the `TraitForgeNft` contract resets the `generationMintCounts` for the `new generation`, leading to inconsistencies when tokens are `forged` across generation boundaries.

## Proof of Concept
According to [Docs](https://github.com/TraitForge/docs), this is given:
> Entities evolve through generations, with each generation capped at 10,000 entities. Generation 1 directly mints Generation 2 entities via forging, up to Generation 10. When the entire generation mints out, the minting will begin at the point of how many entities exist in the next gen. eg, Gen-1 mints out, 50 gen-2s already exist from forging, gen-2 minting will start at #51.

However, this will not hold. Let`s dive:

1. **Forging New Tokens**:
- [Forging](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L163-L176) creates tokens of the `next generation`.
```solidity
  function forge(

    uint256 parent2Id,
    string memory

    require(

>>  uint256 newGeneration = getTokenGeneration(parent1Id) + 1;

```
2. **Minting New Tokens**:
- [Minting](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L280-L294) continues in the current generation until the generation limit is reached.

3. **Increment Generation**:
- When the mint count for the current generation reaches the limit, [`_incrementGeneration()`](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L345-L355) is called.
```solidity
  function _incrementGeneration() private {
    require(
      generationMintCounts[currentGeneration] >= maxTokensPerGen,
      'Generation limit not yet reached'
    );
    currentGeneration++;
>>  generationMintCounts[currentGeneration] = 0;
    priceIncrement = priceIncrement + priceIncrementByGen;
    entropyGenerator.initializeAlphaIndices();
    emit GenerationIncremented(currentGeneration);
  }
```
**Problem:**
The `generationMintCounts[currentGeneration] = 0;` line resets the count for the `new generation`, causing inconsistencies if tokens have already been forged for the `new generation`.

### Scenario:
- `currentGeneration`: 3
- *Forging*: Creates tokens of `generation 4`.
- *Minting*: Continues to create tokens of `generation 3` until `generationMintCounts[3] >= maxTokensPerGen`.
**Issue**:
- When `_incrementGeneration()` is called, it resets `generationMintCounts[4]` to `0`, even though `generation 4` already has tokens from `forging`.
This leads to inconsistencies in the `count of tokens` in `generation 4`.

Manual Review

## Recommended Mitigation Steps
Instead of resetting `generationMintCounts[currentGeneration]` to `0`, we should preserve the existing count.
```diff
  function _incrementGeneration() private {
    require(
      generationMintCounts[currentGeneration] >= maxTokensPerGen,
      'Generation limit not yet reached'
    );
    currentGeneration++;
-   generationMintCounts[currentGeneration] = 0; //@audit Do not reset count to 0
    priceIncrement = priceIncrement + priceIncrementByGen;
    entropyGenerator.initializeAlphaIndices();
    emit GenerationIncremented(currentGeneration);
  }
```
