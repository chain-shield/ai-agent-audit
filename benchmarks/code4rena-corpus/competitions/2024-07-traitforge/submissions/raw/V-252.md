# Vulnerability details

## Impact

Impact: High
Likelihood: Low

In `EntityForging::_cancelListingForForging`, we have deletion from a map using `delete listings[listedTokenIds[tokenId]];`:

```solidity
  function _cancelListingForForging(uint256 tokenId) internal {
    delete listings[listedTokenIds[tokenId]]; // audit-high

    emit CancelledListingForForging(tokenId); // Emitting with 0 fee to denote cancellation
  }
```

The problem with that deletion is that if `listedTokenIds` in `listedTokenIds[tokenId]` does NOT contain the tokenId it will return 0 which means that `delete listings[0]` will be executed. This behaviour is incorrect unless the listing required to be deleted is 0 which is highly unlikely.

## Proof of Concept
1. Deploy all contracts in the project. 
2. Attacker waits for the project to be unpaused and everything starts working normally.
3. Attacker creates a new contract X which inherits `EntityForging.sol`
4. Attacker creates a function inside the contract X which calls `_cancelListingForForging` of its parent contract with invalid tokenId as parameter, thus canceling listings for forging.

## Tools Used
Solidity, VSCode

## Recommended Mitigation Steps

Change the listedTokenIds mapping value from uint256 to an object which contains that same uint256 but also a bool which will be used to confirm whether the listedTokenId actually exists.

Add the following changes afterwards:

```solidity
  function _cancelListingForForging(uint256 tokenId) internal {
+   require(
+     listedTokenIds[tokenId].isListed, // new object will have a bool which has to be checked (bool name e.g. isListed)
+     'Token not listed'
+   );
+   require(
+     listings[listedTokenIds[tokenId]].isListed,
+     'Token not listed for forging'
+   );
    delete listings[listedTokenIds[tokenId]];

    emit CancelledListingForForging(tokenId); // Emitting with 0 fee to denote cancellation
  }
```
