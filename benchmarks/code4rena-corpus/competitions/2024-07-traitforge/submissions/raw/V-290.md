# Vulnerability details

### Impact

Due to an incorrect validation when lisitng for forging, a forger token can be listed more than its forge potential, and can therefore be forged more. This goes against the intended design as can be seen with the merger tokens which can only be merged up to their merge potential.



### Proof of Concept

1. Context

A forger token has to first be listed before forging and each forger has a `forgePotential` which determines how much times the forger can be forged. This is further tracked by the `forgingCounts` parameter. And is ensured that the forging count never exceeds its `forgePotential`.

```solidity
  function listForForging(
    uint256 tokenId,
    uint256 fee
  ) public whenNotPaused nonReentrant {
//...
    uint256 entropy = nftContract.getTokenEntropy(tokenId); // Retrieve entropy for tokenId
    uint8 forgePotential = uint8((entropy / 10) % 10); // Extract the 5th digit from the entropy
    require(
      forgePotential > 0 && forgingCounts[tokenId] <= forgePotential,
      'Entity has reached its forging limit'
    );

    bool isForger = (entropy % 3) == 0; // Determine if the token is a forger based on entropy
    require(isForger, 'Only forgers can list for forging');
//...
  }
```

2. Bug Location

When a user attempts to forge with a merger token, the `forgeWithListed` function first inceases the `forgingCounts` of the forger and doesn't check against the forge potential since it's already checked when listing.

The same process is then repeated for the merger token, with a key difference, the merger token's increased first, before checking against its mergerpotential (same as forgerpotential but for merger). 
```solidity
  function forgeWithListed(
    uint256 forgerTokenId,
    uint256 mergerTokenId
  ) external payable whenNotPaused nonReentrant returns (uint256) {
//...
    forgingCounts[forgerTokenId]++;

    // Check and update for merger token's forge potential
    uint256 mergerEntropy = nftContract.getTokenEntropy(mergerTokenId);
    require(mergerEntropy % 3 != 0, 'Not merger');
    uint8 mergerForgePotential = uint8((mergerEntropy / 10) % 10); // Extract the 5th digit from the entropy
    forgingCounts[mergerTokenId]++;
    require(
      mergerForgePotential > 0 &&
        forgingCounts[mergerTokenId] <= mergerForgePotential,
      'forgePotential insufficient'
    );
//...
    return newTokenId;
  }
```

The inconsistency here is than for forgers, their `forgingCounts` is first compared against their `forgePotential` before finally increasing its value, whereas for mergers, their `forgingCounts` is first incremented before the comparison.

3. Final Effect

To carefully understand this, lets imagine, two tokens forgerA and mergerB, both happen to have the same `forgePotential` of 1, and have `forgingCounts` 0. Having the forge potential of 1 means that ideally, they both should be forgable once, since a forger token with 0 `forgePotential` cannot be forged.

However, when listing for forging, forgerA easily bypasses this check, since his `forgingCounts` is 0, and its less than his `forgePotential` of 1.

```solidity
    require(
      forgePotential > 0 && forgingCounts[tokenId] <= forgePotential,
      'Entity has reached its forging limit'
    );
```

When a user now attempts to merge forgerA and mergerB together, in the `forgeWithListed` function, forgerA's `forgingCounts` increases to 1. The same occurs with mergerA, whose `forgingCounts` is also increased to 1. mergerA then passes the below check since the `forgingCounts` equals 1 which matches its `mergerForgePotential`.

```solidity
    forgingCounts[forgerTokenId]++;
//...
    forgingCounts[mergerTokenId]++;
    require(
      mergerForgePotential > 0 &&
        forgingCounts[mergerTokenId] <= mergerForgePotential,
      'forgePotential insufficient'
    );

```

Repeating the listing process again, we find that forgerA can still be listed for forging, since his `forgingCounts` is 1, and its equal to his `forgePotential` of 1.

And upon attempts to forge, we find out that increasing forgerA's `forgingCounts` to 2 has no effect, since there's no check to see if the `forgingPotential` is bypassed. Unlike with mergerA, whose `forgingCounts` is also 2, but will not pass the potential check, since his count is now greater than his potential.

Therefore, as a result of a missing check, or an incorrect validation, a user can list and potentially have their forgers forged with for one more than its potential.

### Recommended Mitigation Steps

Recommend changing the operator to the < instead. Since the increment is performed after the listing.
```diff
  function listForForging(
    uint256 tokenId,
    uint256 fee
  ) public whenNotPaused nonReentrant {
//...
    require(
-      forgePotential > 0 && forgingCounts[tokenId] <= forgePotential,
+      forgePotential > 0 && forgingCounts[tokenId] < forgePotential,
      'Entity has reached its forging limit'
    );
//...
  }
```
