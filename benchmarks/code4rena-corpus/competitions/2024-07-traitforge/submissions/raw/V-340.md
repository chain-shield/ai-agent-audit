# Vulnerability details

# Description

The `mintWithBudget` function in the `TraitForgeNft` contract is designed to allow users to mint multiple tokens within a specified budget. The function calculates the mint price once before entering a loop that mints tokens until the budget is exhausted. However, the mint price can change if the `_incrementGeneration` function is called within `_mintInternal`, which is not accounted for in the current implementation.

The `mintWithBudget` function starts by calculating the mint price using the `calculateMintPrice` function. It then enters a loop where it mints tokens and deducts the mint price from the budget until the budget is insufficient to mint another token. The `_mintInternal` function, which is called within the loop, can trigger the `_incrementGeneration` function if the number of tokens minted in the current generation exceeds the maximum allowed (`maxTokensPerGen`). This changes the generation and, consequently, the mint price. However, the `mintWithBudget` function does not recalculate the mint price after each mint, leading to potential underpricing of tokens.

## Impact
The failure to recalculate the mint price after each mint operation can result in users minting tokens at a lower price than intended. This can lead to a loss of revenue for the contract owner and an unfair advantage for users who exploit this issue. The impact is significant as it undermines the pricing mechanism and can result in financial discrepancies.

## Proof of Concept
1. A user calls the `mintWithBudget` function with a sufficient budget to mint multiple tokens.
2. The function calculates the initial mint price and enters the loop.
3. The `_mintInternal` function is called, which mints a token and increments the generation if the maximum tokens for the current generation are reached.
4. The generation is incremented, changing the mint price.
5. The loop in `mintWithBudget` continues to use the old mint price, allowing the user to mint tokens at a lower price than intended.

1. **Initial State (for example)**:
   - `currentGeneration = 1`
   - `maxTokensPerGen = 10000`
   - `startPrice = 0.005 ether`
   - `priceIncrement = 0.0000245 ether`
   - `priceIncrementByGen = 0.000005 ether`
   - `generationMintCounts[1] = 9999`
   - User sends `0.01 ether` to `mintWithBudget`.

2. **Execution Before Mitigate the bug**:
   - `mintPrice` is calculated as `0.005 + (9999 * 0.0000245) = 0.2499755 ether`.
   - The loop starts, and `_mintInternal` is called.
   - `_mintInternal` increments `generationMintCounts[1]` to `10000` and calls `_incrementGeneration`.
   - `currentGeneration` is incremented to `2`, and `priceIncrement` is updated to `0.0000295 ether`.
   - The loop continues with the old `mintPrice` of `0.2499755 ether`, allowing the user to mint tokens at a lower price than intended for the new generation.

3. **Execution After Mitigate the bug (_see the Recommended part_)**:
   - The loop starts, and `calculateMintPrice` is called, returning `0.2499755 ether`.
   - `_mintInternal` is called, and `_incrementGeneration` is triggered.
   - `currentGeneration` is incremented to `2`, and `priceIncrement` is updated to `0.0000295 ether`.
   - The loop recalculates `mintPrice` as `0.005 + (0 * 0.0000295) = 0.005 ether` for the new generation.
   - The user is charged the correct price for the new generation, ensuring accurate pricing.

## Recommended Mitigation Steps
Recalculate the mint price after each call to `_mintInternal` to ensure the price reflects any changes due to generation increments. The fix involves moving the `calculateMintPrice` call inside the loop.

-    uint256 mintPrice = calculateMintPrice();

-    while (budgetLeft >= mintPrice && _tokenIds < maxTokensPerGen) {
+    while (budgetLeft >= calculateMintPrice() && _tokenIds < maxTokensPerGen) {

    }
