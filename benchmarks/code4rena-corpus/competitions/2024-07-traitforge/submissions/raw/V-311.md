# Vulnerability details

## Impact
Legitimate users cannot mint tokens as long as the DoS attack continues.

## Proof of Concept
The mintToken function in the provided code is susceptible to a Denial of Service (DoS) attack, specifically through a pattern known as "Failed Send" or "Unexpected Revert." This vulnerability arises from the way the function handles refunds for excess payments. Let's break down the potential DoS scenario in great detail:

The vulnerable part of the code is within the refund logic:

```
if (excessPayment > 0) {
  (bool refundSuccess, ) = msg.sender.call{ value: excessPayment }('');
  require(refundSuccess, 'Refund of excess payment failed.');
}
```
https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L196-L199

An attacker could exploit this vulnerability by creating a malicious contract that interacts with the mintToken function:

- The attacker deploys a malicious contract with a fallback or receive function that always reverts
- The attacker calls the mintToken function through their malicious contract, sending more ETH than necessary for minting.
- The mintToken function processes the mint successfully.
- When trying to refund the excess payment, the call to the attacker's contract reverts due to the malicious fallback/receive function.
- he require(refundSuccess, 'Refund of excess payment failed.') statement causes the entire transaction to revert.

Here's a practical example:

- The attacker calls mintToken through their malicious contract, sending 2 ETH.
- The function mints the token (1 ETH cost).
- It then tries to refund 1 ETH to the attacker's contract.
- The refund fails, causing the entire transaction to revert.
- No token is minted, and the attacker's 2 ETH is returned (minus gas costs).

The attacker can repeat this process indefinitely, preventing any legitimate users from minting tokens.

Note that this attack could be very cheap for an attacker considering the contract would be deployed on the Base chain which is a L2 blockchain.

Further note that this same attack can be done by calling mintWithBudget function.

## Recommended Mitigation Steps
Implement a "Pull over Push" pattern for refunds instead. For instance:

```
mapping(address => uint256) public refundBalances;

function mintToken(bytes32[] calldata proof) public payable whenNotPaused nonReentrant onlyWhitelisted(proof, keccak256(abi.encodePacked(msg.sender))) {
    uint256 mintPrice = calculateMintPrice();
    require(msg.value >= mintPrice, 'Insufficient ETH send for minting.');

    _mintInternal(msg.sender, mintPrice);

    uint256 excessPayment = msg.value - mintPrice;
    if (excessPayment > 0) {
        refundBalances[msg.sender] += excessPayment;
    }
}

function withdrawRefund() public {
    uint256 refundAmount = refundBalances[msg.sender];
    require(refundAmount > 0, "No refund available");
    
    refundBalances[msg.sender] = 0;
    (bool success, ) = msg.sender.call{value: refundAmount}("");
    require(success, "Refund transfer failed");
}

```
