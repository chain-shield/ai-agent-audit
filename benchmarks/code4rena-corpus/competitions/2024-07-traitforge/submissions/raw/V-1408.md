# Vulnerability details

## Impact
in the current implementation of the protocol, GEN2 can be minted in 2 ways. 
1. by forging, using `EntropyForging` contract, which will call eventually `TraitForgeNft::forge` function.
2. or by minting (when GEN1 is sold out, GEN2 will be the next generation minted) using `TraitForgeNft::mintToken` (or `mintWithBudget1` function).
whenever we use the `forge` function, the `_mintNewEntity` function is being called, and whenever we use the `mintToken` function, the `_mintInternal` function is being called.

Whenever we use the `forge` function, we pass to the `_mintNewEntity` the *NEXT* generation as a parameter:
```
    function forge(address newOwner, uint256 parent1Id, uint256 parent2Id, string memory)
        external
        whenNotPaused
        nonReentrant
        returns (uint256)
    {
        require(msg.sender == address(entityForgingContract), "unauthorized caller");
        @> uint256 newGeneration = getTokenGeneration(parent1Id) + 1;

        /// Check new generation is not over maxGeneration
        require(newGeneration <= maxGeneration, "can't be over max generation");

        // Calculate the new entity's entropy
        (uint256 forgerEntropy, uint256 mergerEntropy) = getEntropiesForTokens(parent1Id, parent2Id);
        uint256 newEntropy = (forgerEntropy + mergerEntropy) / 2;

        // Mint the new entity
        @> uint256 newTokenId = _mintNewEntity(newOwner, newEntropy, newGeneration);

        return newTokenId;
    }
```

and inside the `_mintNewEntity` function we increase the mapping `generationMintCounts` of the next gen (e.g. in this case) - 
```
        generationMintCounts[gen]++; //generationMintCounts[2]; 
```

this mapping is tracking each gen count.
when GEN1 is sold out, and `TraitForgeNft::mintToken` is being called, it will call `_mintInternal` function, which checks:
```
    if (generationMintCounts[currentGeneration] >= maxTokensPerGen) {
      _incrementGeneration();
    }
```
since GEN1 is sold out, it will call `_incrementGeneration`.
the `_incrementGeneration` will increase the `currentGeneration` and will RESET the `generationMintCounts` mapping of the GEN2 that was updated everytime `forge` function got called.

```
function _incrementGeneration() private {
    require(
      generationMintCounts[currentGeneration] >= maxTokensPerGen,
      'Generation limit not yet reached'
    );
    currentGeneration++; //it was 1, now it sets to 2.
    @>generationMintCounts[currentGeneration] = 0;
    priceIncrement = priceIncrement + priceIncrementByGen;
    entropyGenerator.initializeAlphaIndices();
    emit GenerationIncremented(currentGeneration);
  }
```

This will cause the following GENs after GEN1 to have a larger unexpected token supply, and might cause additional errors with other calculations (such as mint price and more).



## Proof of Concept
let's assume the following scenario:
1. 3000 GEN2 got generated from "forging"
2. GEN1 is sold out
3. a user call mint (when at the moment, the mapping responsible of counting GEN2 tokens is set to 3000) 
4. mint function together with `_incrementGeneration` sets generationMintCounts[2] = 0.
5. since all requirements and checks are depends on `generationMintCounts`, it might lead to scenarios where there are much more GEN2 tokens than expected, and lead to unexpected errors.
