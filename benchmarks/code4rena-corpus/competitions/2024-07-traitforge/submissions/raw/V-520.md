# Vulnerability details

## Impact
Wrong implementation of percentages could lead to wrong fee calculations

## Proof of Concept
Whenever the `nukeFund` contract receives funds, we end up in the `receive()` function where we have the following piece of code:
```solidity
uint256 devShare = msg.value / taxCut; // Calculate developer's share (10%)
```
We can see that the developer share is a percentage of `msg.value`, currently set to 10% but could be changed in the future using `setTaxCut()`. As the variable name and the code comment next to the piece of code imply (`Calculate developer's share (10%)`), the tax cut should be the percentage of `msg.value` the developers receive. However, that is not actually correctly implemented.

Even though, due to the choice of 10%, the code accidentally functions properly, that will change at the very moment the tax cut is changed.

Let's say the tax cut is changed to 20 which would imply that 20% of the `msg.value` should be for the developers. The following scenario would occur:
1. 1 ETH is sent to `nukeFund`
2. `devShare` is now equal to $1e18 / 20 = 5e16$ which is 0.05 ETH or 5%

As seen, instead of 20%, the developers only received 5%. The code functions properly now due to the lucky choice of 10%. As it is likely for the tax cut to change in the future, this is a valid scenario that can occur. It is also important to note that this is not an admin error as they didn't do anything wrong or malicious, they simply used the function as intended, however the error occurs due to the mistake in the code.
## Tools Used
Manual Review

## Recommended Mitigation Steps
```diff
-uint256 devShare = msg.value / taxCut;
+uint256 devShare = msg.value * taxCut / 100;
```
