# Vulnerability details

## Impact
`EntropyGenerator` does not generate uniformly random numbers. This skews the population of NFTs in a way that contradicts the spec. For example, entropy distribution has a bias towards values divisible by `10`. 

The least significant decimal digit of entropy corresponds to performance factor. The proportion of NFT minted with performance factor of 0 will be higher than 25%.

## Vulnerability Details
There is a number of compounding issues with how entropy is generated:

1. [The whitepaper](https://docs.google.com/document/d/1pihtkKyyxobFWdaNU4YfAy56Q7WIMbFJjSHUAfRm6BA/edit#heading=h.zdjqn66fqffl) says, 
> Entropy is set into uint256 slots, with each slot able to contain a 78 digit number - or 13 concatenated entropies. Thus 770 slots are needed to contain 10,000 entropies.

This is not true. The largest number that can fit into uint256 is roughly `1.1579e77`. This number does have 78 decimal digits. However, `uint256` certainly not large enough to represent 78 decimal digits of entropy.

2. To fill out entropy `EntropyGenerator` does the following:
```
    unchecked {
      for (uint256 i = lastInitializedIndex; i < endIndex; i++) {
        uint256 pseudoRandomValue = uint256(
          keccak256(abi.encodePacked(block.number, i))
        ) % uint256(10) ** 78; // generate a  pseudo-random value using block number and index
        require(pseudoRandomValue != 999999, 'Invalid value, retry.');
        entropySlots[i] = pseudoRandomValue; // store the value in the slots array
      }
    }
```
[Link](https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/EntropyGenerator/EntropyGenerator.sol#L51-L59)

`uint256(10) ** 78` is used as a modulo. However, overflows inside the `unchecked` block and is equal to `73663286101470436611432119930496737173840122674875487684339327936694962880512`. 

This number has 77 decimal digits. So, using it as a modulo can't result in a 78 digit number (on top of the fact that a 78 digit number likely won't fit into `uint256`).

If an entropy slot is interpreted as a 78 digit number, the most significant decimal digit is always 0, and second most significant decimal digit is never above 7.

3. The final entropy used to mint an NFT is padded in a way that further skews the distribution.

```
    uint256 paddedEntropy = entropy * (10 ** (6 - numberOfDigits(entropy)));
```
[Link](https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/EntropyGenerator/EntropyGenerator.sol#L182)

Most significant decimal digit can't be zero, and least significant digit is more likely to be zero.

## Proof of Concept
The following test case added to `test/EntropyGenerator.test.ts` illustrates that:
1. first digit of entropy in the first index of every slot is always zero.
2. first digit of entropy is zero for more than 25% of generated entropy. 
```
  it('first digit of entropy is very likely zero', async function () {
    var total = 0;
    var divisibleByTen = 0;
    for (let i = 0; i < 770; i++) {
      for (let j = 0; j < 13; j++) {
        const entropy = await entropyGenerator.connect(allowedCaller).getPublicEntropy(i, j);

        expect(entropy).to.not.equal(0);

        // first digit of entropy in the first index of every slot is always zero, unless it's "the Golden God"
        if (j == 0 && entropy != 999999n) {
          expect(entropy % 10n).to.equal(0);
        }

        if (entropy % 10n == 0n) {
          divisibleByTen++;
        }
      }
    }
    expect(divisibleByTen).to.greaterThan(2500);
    console.log(divisibleByTen);
  });
```


## Recommended Mitigation Steps
`uint256` can't fit a number with 78 decimal digits, i.e. it can't fit 13 concatenated entropies. My recommendation is to store only 12 entropies in a `uint256` slot.
