# Vulnerability details

##Impact

A potential vulnerability exists where malicious contracts set as `forgerOwner` or `listing.seller` can disrupt the intended functionality of the `forgeWithListed` and `buyNFT` functions. This can lead to significant financial and operational impacts for users.

## Proof of Concept

1. **Malicious Contract Assignment:** A malicious contract is intentionally set as the `forgerOwner` or `listing.seller`.
2. **Transaction Manipulation:** The malicious contract has custom logic in its fallback or receive function to specifically revert transactions. This occurs when certain game conditions aren't met from the malicious contract's perspective.
3. **User Transaction Interception:** A user attempts to utilize the `forgeWithListed` or `buyNFT` functions, leading to the transfer of funds to the malicious contract.
4. **Conditional Transaction Reversion:** The malicious contract evaluates the game state. If the conditions it seeks is at its advantage by not accepting the trade, it can deliberately reverts the transaction it receives.
5. **Function Failure:** Due to the reverted transaction, the `.call` method used within `forgeWithListed` or `buyNFT` fails. The subsequent `require` statement encounters this failure, causing the entire user transaction to revert.

This chain of events effectively prevents the execution of `forgeWithListed` and `buyNFT` functions under these circumstances, hindering the game's intended flow. This situation can lead to financial losses (as user lose funds for gas) and diminished user trust in the platform's reliability.

The vulnerability arises from the reliance on the `.call` method, which requires successful execution by the recipient contract. If the recipient is malicious, it has the ability to disrupt the transaction flow by reverting.

## Tools Used
Manual review

## Recommended Mitigation Steps
To mitigate this risk, it's recommended to enhance the contract's ability to handle potential reverts from the receiving contracts. This can be achieved through two methods:

1. **Try/Catch Mechanism:** Implementing a try/catch block around the `.call` method allows for graceful handling of reverts by the recipient.
2. **Revert Handling Logic:** Modifying the core contract logic to manage reverts in a way that doesn't automatically revert the entire user transaction.

By implementing one or both of these recommendations, the contract can become more resilient against malicious `forgerOwner` or `listing.seller` contracts, ensuring a smoother user experience.
