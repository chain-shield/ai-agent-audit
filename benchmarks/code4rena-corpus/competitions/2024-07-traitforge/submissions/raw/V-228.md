# Vulnerability details

## Impact
The `getEntropy` function in the EntropyGenerator contract incorrectly pads entropy values, causing errors. This affects airdrop data and NFT's attributes, such as the `forgePotential` and `initialNukeFactor`.

## Proof of Concept

The `getEntropy` function in the EntropyGenerator contract retrieves entropy values from a specified slot and position. The code is as follows:

```solidity
function getEntropy(
    uint256 slotIndex,
    uint256 numberIndex
  ) private view returns (uint256) {
    require(slotIndex <= maxSlotIndex, "Slot index out of bounds.");

    if (
      slotIndex == slotIndexSelectionPoint &&
      numberIndex == numberIndexSelectionPoint
    ) {
      return 999999;
    }

    uint256 position = numberIndex * 6; // calculate the position for slicing the entropy value
    require(position <= 72, "Position calculation error");

    uint256 slotValue = entropySlots[slotIndex]; // slice the required part of the entropy value
    uint256 entropy = (slotValue / (10 ** (72 - position))) % 1000000; // adjust the entropy value based on the number of digits
    uint256 paddedEntropy = entropy * (10 ** (6 - numberOfDigits(entropy)));

    return paddedEntropy; // return the calculated entropy value
  }
```

However, there is a logical error which could lead to incorrect entropy values being retrieved.

Specifically, consider that the 78-digit decimal number in the first slot is:
```md
123450 \
012345 \
012345 \
012345 \ 
012345 \
012345 \
012345 \
012345 \
012345 \
012345 \
012345 \
012345 \
012345
```
In this case, the entropy extracted from the first slot and position would be 123450, as it is a 6-digit number and does not require padding. However, for other entropies extracted subsequently, the value will be 12345 after computation (which is insufficient to be 6 digits), padding will make the `paddedEntropy` equal to 123450. Thus, both the original number `123450` and `012345` end up resulting in the same entropy value, which is logically incorrect.

The padding logic is flawed as it pads with zeros to the right side instead of the left side (e.g., turning `12345` into `123450` instead of `012345`). Although proper padding may seem difficult for uint types.

The faulty `getEntropy` function is called within `getNextEntropy`, and further utilized in the TraitForgeNft contract:

```solidity
function _mintInternal(address to, uint256 mintPrice) internal {
    if (generationMintCounts[currentGeneration] >= maxTokensPerGen) {
      _incrementGeneration();
    }

    _tokenIds++;
    uint256 newItemId = _tokenIds;
    _mint(to, newItemId);
    uint256 entropyValue = entropyGenerator.getNextEntropy();

    tokenCreationTimestamps[newItemId] = block.timestamp;
    tokenEntropy[newItemId] = entropyValue;
    tokenGenerations[newItemId] = currentGeneration;
    generationMintCounts[currentGeneration]++;
    initialOwners[newItemId] = to;

    if (!airdropContract.airdropStarted()) {
      airdropContract.addUserAmount(to, entropyValue);
    }

    emit Minted(
      msg.sender,
      newItemId,
      currentGeneration,
      entropyValue,
      mintPrice
    );

    _distributeFunds(mintPrice);
  }
```

As a result, incorrect entropy values will affect the user data in the `airdropContract`, potentially impacting subsequent airdrops.

Additionally, the incorrect entropy will affect the computation of NFT attributes. For instance, in the NukeFactory calculation:

```solidity
function calculateNukeFactor(uint256 tokenId) public view returns (uint256) {
    require(
      nftContract.ownerOf(tokenId) != address(0),
      'ERC721: operator query for nonexistent token'
    );

    uint256 entropy = nftContract.getTokenEntropy(tokenId);
    uint256 adjustedAge = calculateAge(tokenId);

    uint256 initialNukeFactor = entropy / 40; // calculate initialNukeFactor based on entropy, 5 digits

    uint256 finalNukeFactor = ((adjustedAge * defaultNukeFactorIncrease) /
      MAX_DENOMINATOR) + initialNukeFactor;

    return finalNukeFactor;
  }
```

The incorrect padding will result in the `initialNukeFactor` being inflated.

What's more, as the docs says:
```md
10% of the population is infertile from birth
```

"infertile from birth" means the 5th number (forgePotential) of entropy is 0, and "10% of the population" is guaranteed by a normal random distribution between 0-99999. However, due to the logic error above, the proportion of "infertile from birth" will increase a bit, which is not expected.

Specifically, as the code below, the population of "infertile from birth" will increase to 10.9%.

```python
def pad_number(n):
    padded = str(n).zfill(6)
    no_leading_zeros = padded.lstrip('0')
    shifted = no_leading_zeros + '0' * (6 - len(no_leading_zeros))
    return shifted

def main():
    zero_in_fifth_place_count = 0

    for num in range(1000000):
        padded_num = pad_number(num)
        if padded_num[4] == '0':
            zero_in_fifth_place_count += 1

    total_numbers = 1000000
    probability = zero_in_fifth_place_count / total_numbers
    print(f"Total numbers: {total_numbers}")
    print(f"Count of zeros in the fifth place after padding: {zero_in_fifth_place_count}")
    print(f"Probability of zero in fifth place after padding: {probability:.4f}")

if __name__ == "__main__":
    main()
```
