# Vulnerability details

## Impact
All the  contract in scope features a `whenNotPaused` modifier that is currently used to allow some operations only when these contracts are not `paused`. However, this `pausing` functionality leaves critical operations exposed during `emergencies`, potentially jeopardizing the `safety of assets` and  `distributions` since it is not implemented in all cases.

## Proof of Concept
For example, in `DevFund.sol`, there is no any other `payable` function to fetch funds from user to the contract. This contract only receives funds from `NukeFund` contract.i.e When users send ether to `NukeFund` contract, a portion of those funds are sent to `devAddress` as shown here.

When this happens, the [`DevFund:receive()`](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/DevFund/DevFund.sol#L14-L28) will receive and distribute these funds (`devShare`) as shown here:

### Note:
Note that even though both the contracts are `pausable`, they can be paused indipendently. i.e, 

- `DevFund` contract is `paused` ---> No transfers should occur during pause
- `NukeFund` is `unpaused` --> fund transfers allowed in `NukeFund` during this time.
- However, the `DevFund:receive()` function does not check the `pausable` state.  
- If any ether is sent to `NukeFund`, the `DevFund` contract will still receive funds even when `paused`.

As seen, users will still be in a position to send funds into the contract at the same time triggering transfers e.g to `owner`.

## Impact
The lack of comprehensive `pause` functionality exposes the contract to potential issues if the contract needs to be `paused` for maintenance or in response to an attack. 
By not restricting all non-migration functions during a `pause`, users can still interact with the contract in ways that may not be intended during a `paused` state, i.e. if an emergency occurs (e.g., a security vulnerability is discovered), the contract cannot be `fully paused` to protect funds and prevent unauthorized transactions. 

This could lead to:
1. Increased risk to user assets, as pausing is a common safeguard to mitigate damage during incidents.
