# Vulnerability details

## Impact
Whitelisted users who mint tokens before entropy generation is complete will receive tokens with zero entropy, significantly affecting their ability to interact with the protocol as intended.

**Zero entropies leads to major limitations: Inability to Forge and Nuke**

Entropy plays a crucial role in the forging and nuking processes within the protocol. Specifically, `forgePotential` and `age` depend on the 5th and 6th decimal digits of entropy, respectively.

- The `forgePotential` variable determines forging effectiveness:
  ```javascript
  uint8 forgePotential = uint8((entropy / 10) % 10); // Extract the 5th digit from entropy
  ```
  If `forgePotential` is 0, the entity cannot forge. This means it cannot earn money with the `forger` role or forge new generation NFTs with the `merger` role. Essentially, the entity is unable to use the forging feature of the protocol at all.

- The `age` and `initialNukeFactor` variables affect the effectiveness of nuking:
  ```javascript
  uint256 performanceFactor = nftContract.getTokenEntropy(tokenId) % 10;
  ```
  If `age` is 0, the entity cannot age, which means it cannot increase the nuke amount it can receive. The entity will only receive a fixed percentage of funds from the NukeFund, depending entirely on its entropy. This severely limits their nuking potential, reducing their possible earnings from a maximum of 50% with aging to only 5% to 25% of the NukeFund based on entropy.

```javascript
    uint256 initialNukeFactor = entropy / 40; // calcualte initalNukeFactor based on entropy, 5 digits
```

If `entropy` is 0, an entity cannot nuke any amount from the NukeFund due to the following logic:
```javascript
uint256 finalNukeFactor = ((adjustedAge * defaultNukeFactorIncrease) / MAX_DENOMINATOR) + initialNukeFactor;
```
Since `finalNukeFactor` depends on both `age` and `initialNukeFactor`, if both are 0, the entity cannot claim any funds from the NukeFund, rendering the nuking feature of the protocol ineffective.

Players who mint tokens with zero entropy will be unable to forge new tokens or enhance their value through the nuke and forge functions. Additionally, tokens with zero entropy will have minimal trading value. These tokens provide no real utility, resulting in a total financial loss for users.

**Whitelisted users who mint tokens before entropy generation is complete will receive tokens with zero entropy**

Entropy values are stored in the `entropySlots` array. In Solidity, the default values of an array are 0, meaning that all positions in the `entropySlots` array initially contain the value 0. Consequently, all entropy values in the 770 slots of the `entropySlots` variable will be 0 before the `writeEntropyBatch1` function is called.

The `getNextEntropy` and `getEntropy` functions retrieve values from the `entropySlots` array and multiply them by `10**((6 - numberOfDigits(entropy))`. If a slot’s value is 0, the resulting entropy will also be 0. Users can mint tokens before the `writeEntropyBatch` functions are executed. Since the entropy values are present in the `entropySlots` array but initially set to 0, tokens minted during this period will have zero entropy.

Currently, `writeEntropyBatch1`, `writeEntropyBatch2` and `writeEntropyBatch3` functions of `EntropyGenerator` contract can only be called after the deployement of the `EntropyGenerator` contract. There is a 24-hour period during which only whitelisted users can mint tokens. Once the deployer sets the root hash, whitelisted users can start minting. If the root hash is set before the `writeEntropyBatch` functions are executed, there is a gap where any whitelisted user who mints tokens will receive 0 entropy NFTs.

In the current deployment script, whitelisted users are added before entropy generation occurs. Due to the high gas costs associated with these functions, each batch of entropies is generated in subsequent blocks to ensure that the previous batch is completed. This creates the aforementioned gap.

As a result, any whitelisted user who mints tokens during these blocks, before the entropy batches are fully generated, will receive tokens with zero entropy. This prevents them from accessing the protocol's features despite having paid for the tokens, leading to a financial loss.


## Proof of Concept
Consider this scenario:

1. Traitforge announces the launch date to whitelisted users.
2. Whitelisted users monitor for the transaction that sets the root hash.
3. Once this transaction occurs, users mint tokens with additional gas to ensure their transactions are included as early as possible, aiming to mint tokens with minimal ether.
4. Any tokens minted after the root hash transaction but before the entropy generation transaction will have zero entropy.
5. This issue can arise in the next block if more tokens are minted than the current entropy generated batch. For example, writeEntropyBatch1 generates 3,328 entropies and if 3,350 tokens are minted before `writeEntropyBatch2` is executed, then 22 tokens will have zero entropies.

Foundry is used in the Proof of Concept (PoC). You can set up the Foundry environment by following the instructions provided here: https://hardhat.org/hardhat-runner/docs/advanced/hardhat-and-foundry

Copy the test file to run the test using: `forge test --match-test testrootentropysequence -vv`

Impact: High

## Tools Used
Manual Review

## Recommended Mitigation Steps
Add access control to the `writeEntropyBatch1`, `writeEntropyBatch2`, and `writeEntropyBatch3` functions in the `EntropyGenerator` contract by applying the `onlyOwner` modifier. Alternatively, these functions could be included in the constructor of the `EntropyGenerator` contract, as they are intended to be called only once.
