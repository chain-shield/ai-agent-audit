# Vulnerability details

## Description
There seems to be a bug in how the entropy is being stored which is a `design flaw` which seems unexpected and warrant `Medium` severity.

The traits and parameters per each NFT are derived from an `Entropy` value, a 6-digit pseudo-random number associated with each Gen 1 NFT.
- There are a total of 10000 NFT (again we store only generation 1 entropy).
- The max entropy value is 999999 (the Golden God), that represent in hex F423F, which require 20 bits of storage.

So in total we need 834 slots (256 bits each slot), not 770 as currently specified and implemented, as you can store only 12 values per slots, as the 13th one doesn't fit in the slot (lacking 4 bits).
10000 entities / 12 slots = 833.33 rounded up --> 834.


## Impact
Entropy accounting seems currently `inaccurate` as the contract assume 13 values per slot, but that means 12 values will have the proper lenght (20 bits) but the `first value of the slot` will only have `16 bits` and will be `zero padded` (LSB side, either with 00 or 000) to fill 20 bits which can bring some side effects. It's hard to know if this is by design or not. 

One of these would be `forcing the entity to be a Forger`, as 3 LSB will always be 0 (as padded), but it's not fully clear from the `deriveTokenParameters` implementation as it use `%` to establish the value, so it doesn't exactly use the 3 LSB but instead the whole number, which is a bit counter intuitive.

## Recommended Mitigation Steps
- You would need to consider only `12 values per slot`, as the 13th one doesn't fit in the slot (lacking 4 bits).
- This means you would need a total of 834 slots.

So you would at least needs to adjust that, but that might require further changes in the contract.
