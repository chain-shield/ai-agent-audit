# Vulnerability details

## Impact

The contract uses block.number and timestamps as inputs for the `keccak256` function to generate pseudo-random numbers, which is a weak implementation of random number generation in Ethereum.

This can lead to vulnerabilities where an attacker could, in theory, influence the outcome of these "random" numbers.

## Proof of Concept

The pseudo-random numbers are generated in the following method:
``` solidity
function writeEntropyBatch1() public {
    ...
    uint256 pseudoRandomValue = uint256(keccak256(abi.encodePacked(block.number, i))) % uint256(10) ** 78;
    ...
}
```
It uses `block.number` to generate what's supposed to be a random value. Similar pseudo-random number generation is found in other parts of the code such as 'writeEntropyBatch2' function, 'writeEntropyBatch3', and 'initializeAlphaIndices' functions.

## Recommended Mitigation Steps

As best practice, a contract should never use `block.number`, `block.timestamp` or any other block variables to create randomness because smart contracts run on an environment where miners can manipulate those values. 

A reliable mechanism to generate pseudo-random numbers in solidity hasn't been standardized yet. However, possible alternatives could be to use oracle services like Chainlink VRF (Verifiable Random Function) which provides provably-fair and verifiable randomness, or alternatively, build or use an on-chain commit-reveal scheme, or generate the random number off-chain and provide a proof on-chain (like a VDF or zkProof).

In addition to that, if randomness is not required to be on-chain, it would be better to move it off-chain, where it is easier to generate random numbers securely. In this case, an off-chain server generates the random number, and interactions between the smart contract and the server are done using signatures or oracle services. 

The chosen solution would depend on the specifics of the dapp and the level of trust, decentralization, and verifiable fairness required by the specific use case.
