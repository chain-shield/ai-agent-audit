# Vulnerability details

## Impact
Forge Potential can be abused intentionally or unintentionally by the users, which will break the dynamics of the protocol.

## Proof of Concept
In [whitePaper](https://docs.google.com/document/d/1pihtkKyyxobFWdaNU4YfAy56Q7WIMbFJjSHUAfRm6BA/edit) forgePotential defined as:
'The “Forge Potential” (number of times that they can forge before becoming infertile) is set randomly on Gen 1 mint' and from the [code](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityForging/EntityForging.sol#L86) it can be seen it is the fifth digits of entropy:
```solidity
uint8 forgePotential = uint8((entropy / 10) % 10); // Extract the 5th digit from the entropy
```
now let's say Bob has a forger with entropy 123456.Based on the info about forgePotential provided above, Bob can forge his entity 5 times. However this is wrong.In the function [listForForging]( https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityForging/EntityForging.sol#L95) listingCount is increased once it is listed. Then in function [forgeWithListed]( https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityForging/EntityForging.sol#L133),after a forge, forgingCounts is increased. Hence it is clear listing happens before forging. Let's advance the time with the forger that Bob has:
Initial Conditions:
Forger Token's Entropy: 123456
Forge Potential: 5 (5th digit of entropy)
Current Forge Count: 4
Current Listing Count: 4
Bob lists his token for 5th time by calling `listForForging()`,Alice forges her merger  with Bob's forger by calling `forgeWithListed()`.forgingCounts for Bob is increased to 5.Bob intentionally or uintentionally calls listForForging(), the following check:
```solidity
 require(
      forgePotential > 0 && forgingCounts[tokenId] <= forgePotential,
      'Entity has reached its forging limit'
    );
``` 
will be passed. listingCount will be increased to 6 for Bob.
```solidity
++listingCount;
```
Now Bob has listed his forger for 6 times and a user has merger can  forge with Bob's token again by calling forgeWithListed(), Which will make Bob's forgingCounts  6. The flow can be seen better in the following table:
| *Step* | *Action*                     | *forgingCounts[forgerTokenId]* | *listingCount* | *Description*                            | *Function*       |
|----------|--------------------------------|----------------------------------|------------------|--------------------------------------------|--------------------|
| 1        | Initial State                  | 4                                | 4                | Forger token has been forged 4 times       |                    |
| 2        | List for the 5th time          | 4                                | 5                | Listed successfully, count doesn't increment | listForForging     |
| 3        | Forge with merger (5th forge)  | 5                                | 5                | Increment forge count to 5                 | forgeWithListed    |
| 4        | List for the 6th time          | 5                                | 6                | Listed successfully, count doesn't increment | listForForging     |
| 5        | Forge with merger (6th forge)  | 6                                | 6                | Increment forge count to 6                 | forgeWithListed    |

 The issue arises due to the wrong assumption of dev in the following [code](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityForging/EntityForging.sol#L131C5-L133C36):
```solidity
// Check forger's breed count increment but do not check forge potential here
// as it is already checked in listForForging for the forger
    forgingCounts[forgerTokenId]++;
```
Even if Bob has forgePotential=5, he is able to forge his token(s) one more time, which means he will get unfair gain. Besides the users who are aware of the bug will abuse this.

```solidity
    // Check forge potential after incrementing the count
++    require(
        forgePotential > 0 && forgingCounts[forgerTokenId] <= forgePotential,

    require(
        mergerForgePotential > 0 &&
        forgingCounts[mergerTokenId] <= mergerForgePotential,
        'forgePotential insufficient'
    );

    //SKIPPED
 
    return newTokenId;
}
```
