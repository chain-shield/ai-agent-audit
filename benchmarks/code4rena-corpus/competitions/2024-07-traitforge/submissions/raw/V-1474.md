# Vulnerability details

## Summary

Each generation of entities can have up to 10000 entities. Users can either mint the current generation's entities or forge two same generation entities to create a next-gen entity.

There is a mapping of uint256 to uint256 which holds the count of entities of each generation i.e. `mapping(uint256 => uint256) public generationMintCounts;`

When any entity is minted, this is incremented to show the new count of entities minted.

In normal process of minting the current gen's entity, the count works as intended, if a next-gen entity is forged through `TraitForgeNft::forge()` function then the count for the next-gen is increased by 1. The issue occurs when the current generation is completed, upon completion, the `currentGeneration` variable is incremented to show that the next generation has started but the `generationMintCount` mapping is reset to 0, this causes the count to be corrupted as there are already forged entities belonging to this new generation.

## Vulnerability

Suppose that 10000 generation 1 entities have been minted and there are 90 generation 2 entities obtained through forging.

The current mapping will look like this
`generationMintCounts[1] = 10000`
`generationMintCounts[2] = 90`

The next entity which will be minted will increment the variable `currentGeneration` from 1 to 2.

The process in the code looks like the following

The user calls `mintToken()` or `mintWithBudget()` function, the report will follow the `mintToken()` function but the issue persists if any of the two are called.

The `mintToken()` contains the following code
```solidity

    uint256 mintPrice = calculateMintPrice();
    require(msg.value >= mintPrice, 'Insufficient ETH send for minting.');

    _mintInternal(msg.sender, mintPrice);

    // more code
```

The function will first calculate the mint price and then call `_mintInternal()` function

The `_mintInternal()` function contains the following code
```solidity
function _mintInternal(address to, uint256 mintPrice) internal {
    if (generationMintCounts[currentGeneration] >= maxTokensPerGen) {
      _incrementGeneration();
    }

    _tokenIds++;
    uint256 newItemId = _tokenIds;
    _mint(to, newItemId);
    uint256 entropyValue = entropyGenerator.getNextEntropy();

    tokenCreationTimestamps[newItemId] = block.timestamp;
    tokenEntropy[newItemId] = entropyValue;
    tokenGenerations[newItemId] = currentGeneration;
    generationMintCounts[currentGeneration]++; // 0 , 1 , 
    initialOwners[newItemId] = to;
```

The function first checks if the count of the current generation exceeds or is equal to the `maxTokensPerGen`, the supposed count currently is `10000` hence the `_incrementGeneration()` function will be called

The _incrementGeneration() function contains the following code
```solidity
function _incrementGeneration() private {
    require(
      generationMintCounts[currentGeneration] >= maxTokensPerGen,
      'Generation limit not yet reached'
    );
    currentGeneration++;
    generationMintCounts[currentGeneration] = 0; // @audit-issue we set the count to 0 for the gen
    // without saving the count of the forged gens
    priceIncrement = priceIncrement + priceIncrementByGen;
    entropyGenerator.initializeAlphaIndices();
    emit GenerationIncremented(currentGeneration);
  }
```

Here the final check is made and since 10000 >= 10000 is true, we move forward to increment the `currentGeneration to 2` and set the `generationMintCounts[2] = 0`. This creates the issue as there are already generation 2 entities created through forging. This corrupts the count and allows for more entities to be created for the same generation where as the limit is `10000`,

According to the count supposed in this report, The price of the 91st entity from generation 2 will be higher than the 1st entity from generation 2. The issue allows for newer entities to be minted for cheaper which ruins the ecosystem of the game more as the `distributeFunds()` function is called after every mint which sends the funds into `NukeFund.sol`, This will create an imbalance and diversion from the plans intended by the developers.

## Impact

The count will be corrupted and the limit for the number of entities per generation will be bypassed.
The reset of the count will allow cheaper entities to be minted further more there will be an imbalance of funds in the `NukeFund.sol` contract

## Tools Used

Manual Review

## Recommended Mitigation Steps

Do not reset the count for the new generation when incrementing the generation or create a new mapping to hold the number of Forged Entities per each generation and then when checking the count against the limit, add both the count through minting and count through forging and compare it with the limit.
