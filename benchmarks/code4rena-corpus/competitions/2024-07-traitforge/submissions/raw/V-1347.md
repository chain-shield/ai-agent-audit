# Vulnerability details

## Impact
A user can start forging eventhough the `forgingCounts[forgerTokenId]` exceeds the value of `forgePotential`.

## Proof of Concept


https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityForging/EntityForging.sol#L131-L134
```solidity
    // Check forger's breed count increment but do not check forge potential here
    // as it is already checked in listForForging for the forger
    forgingCounts[forgerTokenId]++;
```


Here in the function `forgeWithListed()` , contract is assuming that `forgingCount` value is always less than `forgingPotential` since  there is a check for the current forgingCount of the tokenId when it gets listed in `listForForging()` function. (mentioned in their comments)

Lets go through that check in `listForForging()`, 

https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityForging/EntityForging.sol#L87-L90
```solidity
    require(
=>      forgePotential > 0 && forgingCounts[tokenId] <= forgePotential, 
      'Entity has reached its forging limit'
    );
```

Means, even if the forgingCounts[tokenId] == forgePotential , we are continuing the execution and listing that tokenId for forging.

So the same  token Id can be used for forging even though it reaches its forgingPotential.

## Tools Used
Manual.

## Recommended Mitigation Steps
A check before incrementing the forgingCount
