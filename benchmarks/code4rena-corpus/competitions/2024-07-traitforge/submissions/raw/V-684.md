# Vulnerability details

## Impact
The limit of 10k entities per generation can be broken, which will affect
nuke fund as well as mint price to the users

## Proof of Concept
The vulnerability stems from resetting generationMintCounts[currentGeneration] = 0, not accounting for entities that were forged 

Example: We have 9500 minted gen1 entities, and we have forged/bred through them 4000 gen2 entities,
so we have in total 9500 gen1 entities and 4000 gen2 entities (mint 1 is still ongoing),
1 hour has passed, we hit the 10k gen1 entities and we run the _incrementGeneration() to go into 
the next generation

In _incrementGeneration(), we increment the currentGeneration and then we assign it to generationMintCounts[currentGen] = 0.

This will delete any accounting that we previously had for the minted gen2,
which will cause trouble in all of the application.

Firstly, it will make it possible to have more than 10k entities per generation,
which is an invariant of the protocol.

Secondly, it will give the user incorrect mint price, in this case we can expect a lower value,
so the protocol will collect less to the nuke fund.

This will result in minting a lot more entities per generation, thus dilluting them leading to a potential loss for the users that've minted/forged
and as well as contributing less to the nuke fund, which is the main monetary incentive in the project.

Taking those into account, there is a enormous chance that the protocol will suffer highly due to less funds in the nuke fund + more entities,
thus losing the trust of the users in it.

The vulnerability above has been confirmed by the sponsor as well.
## Tools Used
Manual review

## Recommended Mitigation Steps
Remove generationMintCounts[currentGeneration] = 0; from _incrementGeneration()
