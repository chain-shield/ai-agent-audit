# Vulnerability details

## Impact
Forge NFTs can forge 1 more time than their potential

## Proof of Concept
Users with forge NFTs can put up their NFTs for others to forge with in return of a fee. Each forge NFT has a forging potential that is calculated like this:
```solidity
uint8 forgePotential = uint8((entropy / 10) % 10);
```
Then, we have the following __require__ statement that allows users to only forge their NFTs based on their forge potential:
```solidity
require(forgePotential > 0 && forgingCounts[tokenId] <= forgePotential, 'Entity has reached its forging limit');
```
Then, a different user can call `forgeWithListed()` to forge his merger NFT with the forger NFT in the listing. There, all of the merging and forging occurs and we also have this line:
```solidity
forgingCounts[forgerTokenId]++;
```
There are no checks that would disallow the scenario that I will explain below to occur:
1. Bob has an NFT with a forge potential of 5
2. He has already forged his NFT 5 times, thus he has reached the full potential
3. He tries to forge one more time and enters this check:
```solidity
require(forgePotential > 0 && forgingCounts[tokenId] <= forgePotential, 'Entity has reached its forging limit');
```
4. It successfully passes as the forging counts variable is equal to 5 as well as the forge potential
5. Then, we increment the forging counts to 6, there is no check that disallows that there
6. Bob has successfully forged his NFT 1 more time than the limit

Note that the merger NFTs can not do that, the error is only for the forger NFTs due to the fact that the check for the forge potential is before the increase of the forge count, that is not the case with the merger NFTs.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Use `<` instead of `<=` for the forger NFTs
