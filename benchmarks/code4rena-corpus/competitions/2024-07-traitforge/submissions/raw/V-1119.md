# Vulnerability details

## Summary

In the documentation, it is stated that `Entity can forge before becoming infertile for the rest of the year` which implies
that implies until New Year (for example 01/01/2025). While the code is implemented for one calendar year, leading to misunderstanding and potential 
loss of trust from the users to the project.

## Vulnerability Details

The `EntityForging::_resetForgingCountIfNeeded` is coded to make the entity infertile for the next calendar year, which is
not clearly stated in the documentation. 

[EntityForging.sol#L199-L207](https://github.com/FBro-s/TraitForge/blob/c6eb9a273dafdd3fb01b94567111799ed3a3007c/contracts/EntityForging/EntityForging.sol#L199C3-L207C4)

```solidity
  function _resetForgingCountIfNeeded(uint256 tokenId) private {
    uint256 oneYear = oneYearInDays;
    if (lastForgeResetTimestamp[tokenId] == 0) {
        lastForgeResetTimestamp[tokenId] = block.timestamp;
    } else if (block.timestamp >= lastForgeResetTimestamp[tokenId] + oneYear) {
        forgingCounts[tokenId] = 0; // Reset to the forge potential
        lastForgeResetTimestamp[tokenId] = block.timestamp;
    }
}
```

## Impact

With the code implementing one calendar year and not properly explaining in the documentation, users, and more over
non-technical users, can be misled and their trust in the project can be lost. 
Which can lead to potential financial losses and the end of the project.

## Tools used

Manual Review

## Recommendations

In the documentary, it should be clearly stated that the `Entity can forge before becoming infertile for the next calendar year` ( 365 days )
to avoid misunderstanding and potential loss of trust from the users. It should also be mentioned that year ALWAYS means 365 days, so no leap
years are taken into account.
