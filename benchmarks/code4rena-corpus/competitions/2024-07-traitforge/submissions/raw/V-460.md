# Vulnerability details

## Summary

The TraitForge Ecosystem allows players to list their entities for forging, but a malicious forger can prevent others from merging with their entity by reverting the transfer of the forgerFee. This vulnerability can be exploited to forge with oneself (using another address) at a reduced cost, breaking the protocol's logic and resulting in lost funds for the protocol.

## Vulnerability Details

After a successful forge, 90% of the listing fee will be transferred to the forger address, this is where the problem is, the forger can make this call revert `(bool success_forge, ) = forgerOwner.call{ value: forgerShare };` to prevent others from merging with their Entity.

A malicious forger can prevent everyone else except a selected merger from merging with their Entity by writing logic within the receive function of their listing contract so that when an unauthorized merger tries to merge with their Entity, it will revert.

## Impact

1. Self-Forging: A malicious forger can list their desirable token at the minimum listing fee, prevent everyone from merging with the Entity, use another address to merge with the Entity, and receive 90% of the fee back, allowing them to forge at a significantly reduced cost. 

E.g 

The minimum listing fee is (0.01 eth), since the minimum cost of minting an Entity is (0.005 eth), and 90% of the fee is going back to them and the new Entity will have desirable traits, this becomes very profitable as they would spend around 0.001 ether.

10% of 0.01 eth to mint this new entity, this is about 5 times less than the amount that they will spend to mint a new Entity. It becomes more profitable to do something like this when the price of minting Entities increases, e.g 5000 Entities have been minted the minting price would be: 0.005 + 0.0000245 * 5000 = 0.1275 eth at this price more people with merger token would rather forge than mint new Entities and the listing price would be close to 0.1275 eth, but because the lister knows that they can list and be the only one allowed to merge with the Entity, they will list at the minimum price of 0.01 ether and merge with themselves. Which is poor market logic, and also the protocol losing funds in dev fees. 



2. Preventing Others from Merging: By reverting the transfer of the forgerFee, a malicious forger can prevent others from merging with their listed entity, breaking the protocol's logic.

## Recommendation

Donot transfer the token to the forger during the forging process rather use the "pull over push" method.

Create a mapping to track forging fees and a forger and record it

```diff
+  //mapping of forgeOwner address to earnings
+  mapping(address => uint256) public forgerEarnings;
```

Update the mapping during forging.

```diff
  function forgeWithListed(
    uint256 forgerTokenId,
    uint256 mergerTokenId
  ) external payable whenNotPaused nonReentrant returns (uint256) {
    Listing memory _forgerListingInfo = listings[listedTokenIds[forgerTokenId]];
    ...
-   (bool success_forge, ) = forgerOwner.call{ value: forgerShare }('');
-    require(success_forge, 'Failed to send to Forge Owner');
+    forgerEarnings[forgerOwner] += forgerShare;
    ...
  }
```
Create a claim function so that the forger can claim their earnings.

```diff

+   function claimForgeEarnings () external {
+       (bool success, ) = forgerOwner.call{ value:   forgerEarnings[forgerOwner] }('');
+       require(success, 'Failed to send to Forge Owner');
+   }

```
