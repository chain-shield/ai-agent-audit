# Vulnerability details

## Impact
In `removeDev()` the inconsistencies in the function can lead to the locking up of rewards in the contract when `removeDev()` is called

## Proof of Concept
```solidity
  function removeDev(address user) external onlyOwner {
    DevInfo storage info = devInfo[user];
    require(info.weight > 0, 'Not dev address');
    totalDevWeight -= info.weight;
    info.pendingRewards += (totalRewardDebt - info.rewardDebt) * info.weight;
    info.rewardDebt = totalRewardDebt;
    info.weight = 0;
    emit RemoveDev(user);
  }
```
from the code above we can see the weight of the user is initialized and after the user weight is subtracted and from the `totalDevWeight`, the `pendingRewards` is updated followed by the `info.rewardDebt`, and `info.weight` is set to 0. 

Incase `info.pendingRewards` is not zero and user wants to claim after he has been removed, user won't be able to claim since `claim()` is dependant on `info.weight` that is already set to 0 in the removeDev

`uint256 pending = info.pendingRewards + (totalRewardDebt - info.rewardDebt) * info.weight;`

as we see the pending value will always be zero after `removeDev` is called.
This will cause the check below to always fail and lock up rewards

```solidity
    if (pending > 0) {
      uint256 claimedAmount = safeRewardTransfer(msg.sender, pending);
      info.pendingRewards = pending - claimedAmount;
      emit Claim(msg.sender, claimedAmount);
    }
```


## Tools Used
Manual review(Vs Code)

## Recommended Mitigation Steps
In the `removeDev()` make sure the `pendingRewards` of the user being removed is also removed or implement a way he can get his rewards when he is removed
