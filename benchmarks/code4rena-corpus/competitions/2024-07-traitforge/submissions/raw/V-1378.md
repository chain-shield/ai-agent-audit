# Vulnerability details

## Vulnerability details

According to the docs
```
 The game has a timestamp from mint 
 that will reset the mapping count back to the [5] digit entropy number 
 once 1 year has been passed in blocks.
```
`_resetForgingCountIfNeeded` is the function used to handle the reset logic.

However , The reset is only calculated from the last time an user listed for forging.
instead of being reset every year

```
function _resetForgingCountIfNeeded(uint256 tokenId) private {
    uint256 oneYear = oneYearInDays;
    if (lastForgeResetTimestamp[tokenId] == 0) {
      lastForgeResetTimestamp[tokenId] = block.timestamp;
    } else if (block.timestamp >= lastForgeResetTimestamp[tokenId] + oneYear) {
      forgingCounts[tokenId] = 0; // Reset to the forge potential
      lastForgeResetTimestamp[tokenId] = block.timestamp;
    }
}
```

An user who owns a merger NFT listsForForging after 300 days day for example 
has to wait for another year before the count is reset

## Impact

Detailed description of the impact of this finding.

## Proof of Concept

1. MINT DATE
	 Bob mints a merger entity on Jan 1st 2024 (with a forgingPotential = 1)

2. Bob waits, so he can forge with an appropriate listing from a forger entity.

3. FIRST FORGE
   Bob finally finds a good listing and proceeds to forge 
   on Dec 26th 2024 (360 days after minting)

This is the timestamp his `lastForgeResetTimestamp[bob]` mapping 
gets updated for the first time.

```
    if (lastForgeResetTimestamp[tokenId] == 0) {
      lastForgeResetTimestamp[tokenId] = block.timestamp;
    }
```
   
4. Now instead of the `forgingCounts[Bob] ` resetting after an year from mint (i.e, Dec 31st 2025), 
   Bob now has to wait another 365 days (till Dec 26th 2025) from the day of his first forge,
   before he could forge again.

   
5. Hence the `forgingCount` doesnt reset every year as the protocol intends. 
   but only resets after an year has passed from the time of every subsequent forging.
