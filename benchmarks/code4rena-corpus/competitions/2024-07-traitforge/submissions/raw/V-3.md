# Vulnerability details

## Impact
When a user list an NFT for forging and sets a fee, when a mergerToken holder wants to forge the NFT’s and accidentally sents too much ETH, the ETH will be stuck in the contract and not transferred back to the merger.

## Proof of concept

Imagine listing a NFT for Forging with a fee of 0.5 ETH

When the merger calls the `forgeWithListed` with a `msg.value` of 5 ETH the following happens

```solidity
uint256 forgingFee = _forgerListingInfo.fee; // fee was set to 0.5ETH
require(msg.value >= forgingFee, 'Insufficient fee for forging'); // msg.value was 5 ETH >= 0.5ETH
```

But when calculating the amount sent as devFee and to the NFT Lister it is calculated based on the fee set when listing. 

The left over ETH is not sent back to the merger, resulting in loss of ETH as the contract doesn’t have a function to withdraw this ETH and it will be stuck forever.

```solidity
// 0.5 ETH / 10 = 0.05ETH or 5e16 
uint256 devFee = forgingFee / taxCut;

// 0.5 ETH - 0.05ETH = 0.45 ETH
uint256 forgerShare = forgingFee - devFee;

// Total of 0.5 ETH will be sent to recipients
// 0.05 ETH
(bool success, ) = nukeFundAddress.call{ value: devFee }('');
require(success, 'Failed to send to NukeFund');
// 0.45 ETH
(bool success_forge, ) = forgerOwner.call{ value: forgerShare }('');
require(success_forge, 'Failed to send to Forge Owner');

// 4.5ETH is stuck in contract
```

## Recommended Mitigation Steps

Pay back the differences to the user or update validation

```
// pay back left over ETH
uint256 leftOverETH = msg.value - forgingFee;

(bool payback_owner, ) = payable(msg.sender).call{ value: leftOverETH }('');
require(payback_owner, 'Failed to pay back left over ETH');
```

```diff
// or validate msg.value with forgingFee
- require(msg.value >= forgingFee, 'Insufficient fee for forging');
+ require(msg.value == forgingFee, 'Insufficient fee for forging');
```
