# Vulnerability details

## Impact
The current implementation of the `buyNFT` function allows the seller to receive proceeds from the sale before the NFT is transferred to the buyer. This sequence creates a risk where, if the NFT transfer fails, the seller would still retain the ETH while the buyer would not receive the NFT. This situation results in the buyer losing their funds without receiving the purchased NFT.

```javascript
function buyNFT(uint256 tokenId) external payable whenNotPaused nonReentrant {
    Listing memory listing = listings[listedTokenIds[tokenId]];
    require(
      msg.value == listing.price,
      'ETH sent does not match the listing price'
    );
    require(listing.seller != address(0), 'NFT is not listed for sale.');

    //transfer eth to seller (distribute to nukefund)
    uint256 nukeFundContribution = msg.value / taxCut;
    uint256 sellerProceeds = msg.value - nukeFundContribution;
    transferToNukeFund(nukeFundContribution); // transfer contribution to nukeFund

    // transfer NFT from contract to buyer
    (bool success, ) = payable(listing.seller).call{ value: sellerProceeds }( //@audit seller can receive and burn
      ''
    );
    require(success, 'Failed to send to seller');
    nftContract.transferFrom(address(this), msg.sender, tokenId); // transfer NFT to the buyer

    delete listings[listedTokenIds[tokenId]]; // remove listing

    emit NFTSold(
      tokenId,
      listing.seller,
      msg.sender,
      msg.value,
      nukeFundContribution
    ); // emit an event for the sale
  }
```

The fact that msg.value is checked when the buyNFT is called means that the buyer has already committed their money in and there is no way out. all the computations that require msg.value will definitly run. 

Priority should not be seller getting the proceeds because they will still get the proceeds after NFT is transferred. this is because there are already checks to make sure that buyer will have to send the actual msg.value in see below

If it happens that maybe the protocol now might get into a situation where the seller never receives the money, considering buyer can only get the NFT after they send the required `msg.value`, lets think of a situation where the buyer got their NFT but seller did not receive payment, what this means is that since buyer can only get the NFT after sending the required `msg.value`. the money is in the contract and project owner can just figure out what went wrong and pay seller. But if seller gets the money first before NFT is transfered then it will be impossible to reverse. To show the better approach, think of the buyer getting the NFT first, this way; at least the NFT is still in the contract and the situation is manageable because. you will have only NFT to deal with and its already in the contract, the admin can pause contract just to fix the issue, this way the situation can be handled, but if seller gets paid and NFT is not transferred to buyer now the seller received the money already and still has the ownership of the NFT. Even if admin was to pause contract to resolve the eth sent cannot be reversed.


## Proof of Concept
The vulnerability can be demonstrated as follows:

Scenario Setup:
Assume a buyer initiates a purchase by sending ETH to the contract to buy an NFT.
The contract processes the payment and immediately transfers the proceeds to the seller.
If the NFT transfer fails due to any issue (e.g Non existent tokenId as there is no check to make sure the NFT being bought actually exists), the ETH has already been sent to the seller.
Failure Condition:
Since Ethereum transactions are not reversible, the funds sent to the seller cannot be recovered.
The buyer will have lost their ETH, but the NFT will not have been transferred.
