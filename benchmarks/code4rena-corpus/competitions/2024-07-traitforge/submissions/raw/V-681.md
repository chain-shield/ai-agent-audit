Fairness Impact: Users expect a capped supply per generation. Violating this could erode trust in the system.

## Proof of Concept

Bypassing the (generationMintCounts[currentGeneration] < maxTokensPerGen) check with exposing functionality in _mintNewEntity to outperfoorm the generation of tokens for the current generation(10000)

Stack trace of the problem 

Here the newGeneration parameter is declared - https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L153-L179

It allows to execute the _mintNewEntity for the currentgenration or 1 above since the check :
 require(
      generationMintCounts[gen] < maxTokensPerGen,
      'Exceeds maxTokensPerGen'
    );
won't pass for previous generation that already have 10000 tokens

In case newGeneration is currentGeneration +1 -------->it is passed as a fucntion parameter for the following fucntion 

Here in the _mintNewEntity function - https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L310-L343

After the newly forged nft is minted we execute the following line

generationMintCounts[gen]++;

This increments the count on the new generation (parameter variable gen)

Vulnerable Scenario:

In case :

gen = 2

State
currentGeneration = 1

Here the vuln line of code :

 require(
      generationMintCounts[gen] < maxTokensPerGen,
      'Exceeds maxTokensPerGen'
    );

This will result in 0 < 10000 since the default value of uint256 is 0 in the mapping(uint256 => uint256) public generationMintCounts;
