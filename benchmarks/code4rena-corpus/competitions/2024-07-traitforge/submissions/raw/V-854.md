# Vulnerability details

## Impact

In the current implementation of `EntropyGenerator`, there are 770 slots that contain multiple entropies for 10000 tokenIds in each generation. The problem is that there is a special entropy that should be of entropy `999999` (meaning it's the most powerful one) but the contract does not check if such number exists in any of the slots when creating pseudo number for each slot. This result in a situation where there are initialized number index and slot index (selection point) but this number itself is not `999999`.

## Proof of Concept

The slots are written in batches of 3 with the last one 770. There is also `initializeAlphaIndices()` function that assigns slot index and number index to the special entropy:

https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/EntropyGenerator/EntropyGenerator.sol#L211-212
```
  uint256 slotIndexSelection = (hashValue % 258) + 512;
  uint256 numberIndexSelection = hashValue % 13;
```

But when we write the last batch:


https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/EntropyGenerator/EntropyGenerator.sol#L84-98
```

function writeEntropyBatch3() public {
    require(
      lastInitializedIndex >= batchSize2 && lastInitializedIndex < maxSlotIndex,
      'Batch 3 not ready or already completed.'
    );
    unchecked {
      for (uint256 i = lastInitializedIndex; i < maxSlotIndex; i++) {
        uint256 pseudoRandomValue = uint256(
          keccak256(abi.encodePacked(block.number, i))
        ) % uint256(10) ** 78;
        entropySlots[i] = pseudoRandomValue;
      }
    }
    lastInitializedIndex = maxSlotIndex;
  }

```

It just creates random value for each slot and does not check for any selection point which makes it impossible to get `999999` entropy.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Change the functionality so that the pseudorandom value in one of the slots would contain exactly `999999` entropy.
