# Vulnerability details

## Impact
The `EntropyGenerator` contract is responsible for generating entropy, which determines the traits and attributes of the minted tokens.

*Taken from the [whitepaper](https://docs.google.com/document/d/1pihtkKyyxobFWdaNU4YfAy56Q7WIMbFJjSHUAfRm6BA/edit)*:
"The traits and parameters per Entity are derived from “Entropy” a 6-digit random number associated with each Gen 1 Entity. The entropy is established at the genesis of the game and cannot be changed.
Entropy is set into uint256 slots, with each slot able to contain a 78 digit number - or 13 concatenated entropies. Thus 770 slots are needed to contain 10,000 entropies. Genesis entropy is seeded using blockhash. Setting all 770 uint256 slots cost 15m gas, and due to contract & block size limits, this cannot be set in contract initialisation. Instead a function writes in entropy in 3 passes after the contract is deployed.
There is a certain entropy, “999999” which is referred to as “the Golden God”, since it has perfect parameters and will exceed all other entities if played correctly. The Golden God is scanned for and is kept out of the first 2 passes, but is deliberately set in the final pass (at some random point). The Golden God should be the most valuable entity."

It doing so by three functions, `writeEntropyBatch1`, `writeEntropyBatch2` and `writeEntropyBatch3`.
However, since all the data is stored on-chain, this source of randomness is very weak. This weakness can lead to front-running on NFTs with better traits and result in severe gas wars.

## Proof of Concept
Consider a scenario where the next token to be minted is the "Golden God", "999999" entropy with perfect parameters. Every user in the game can easily know that the next token will be the best in the game. This knowledge might lead to significant front-running, causing severe gas wars, and potentially resulting in users losing substantial amounts of ETH due to higher gas fees.
the same scenario can happen to any other token with good parameters.

manual review

## Recommended Mitigation Steps
To mitigate this issue, consider implementing a different source of randomness, that will not store the traits onchain. A robust solution might be utilizing [Chainlink VRF](https://docs.chain.link/vrf), which provides verifiable randomness and can prevent the predictability and subsequent front-running issues observed with the current on-chain entropy generation method.
