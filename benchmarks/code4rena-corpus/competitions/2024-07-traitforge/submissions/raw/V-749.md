# Vulnerability details

The check for preventing the Golden God to be in a pseudoRandomValue in EntropyGenerator.sol, when writeEntropyBatch1 and writeEntropyBatch2  are executed  is wrong, which makes it possible to have the Golden God generated as entropy in the first or second batch, which is incorrect according to the code itself and the docs [here](https://docs.google.com/document/d/1pihtkKyyxobFWdaNU4YfAy56Q7WIMbFJjSHUAfRm6BA/edit):
> The Golden God is scanned for and is kept out of the first 2 passes, but is deliberately set in the final pass (at some random point). The Golden God should be the most valuable entity. 

## Impact
Allowing the Golden god in the first or second batch, reduces its rarity and just breaks the intended behaviour of the protocol.

## Proof of Concept
In writeEntropyBatch1 and writeEntropyBatch2 we have `require(pseudoRandomValue != 999999, "Invalid value, retry."); `
```solidity
  function writeEntropyBatch1() public {
    require(lastInitializedIndex < batchSize1, 'Batch 1 already initialized.');

    uint256 endIndex = lastInitializedIndex + batchSize1; // calculate the end index for the batch
    unchecked {
      for (uint256 i = lastInitializedIndex; i < endIndex; i++) {
 @>>    uint256 pseudoRandomValue = uint256(
       keccak256(abi.encodePacked(block.number, i))
        ) % uint256(10) ** 78; // generate a  pseudo-random value using block number and index
@>>     require(pseudoRandomValue != 999999, 'Invalid value, retry.');
        entropySlots[i] = pseudoRandomValue; // store the value in the slots array
      }
    }
    lastInitializedIndex = endIndex;
  }
```

This is completely wrong, as the Golden God is represented by an entropy ( i.e. 6 digit number ), and the pseudoRandomValue is the whole uint256 slot value, containing 13 entropies, as maximum number stored by a uint256 has 78 digits. Thus 6 digit entropies x 13 = 78 digits.
Entropy logic is explained [here](https://docs.google.com/document/d/1pihtkKyyxobFWdaNU4YfAy56Q7WIMbFJjSHUAfRm6BA/edit)

Its also nearly impossible for a 6 digit number to be generated from the `uint256(keccak256(abi.encodePacked(block.number, i))) % uint256(10) ** 78;` 
It would mostly generate 74-77 digit numbers, as the values produced by keccak256 are very high.

The odds of getting a 6-digit number are certainly less than picking a specific atom in our galaxy, the Milky Way, randomly on the first try. Also, having a number with fewer than 72 digits would result in the getNextEntropy() returning 0 due to the way it's implemented.



The correct check should not be checking the whole value, but rather the 13 possible entropies in it.

## Recommended Mitigation Steps
Add this additional checks to the writeEntropyBatch2 and writeEntropyBatch1, we MUST use the same way of retrieving entropy as in getEntropy function, as follows:

```diff
    function writeEntropyBatch2() public {
        require(
            lastInitializedIndex >= batchSize1 && lastInitializedIndex < batchSize2,
            "Batch 2 not ready or already initialized."
        );

        uint256 endIndex = lastInitializedIndex + batchSize1;
        unchecked {
            for (uint256 i = lastInitializedIndex; i < endIndex; i++) {
                uint256 pseudoRandomValue = uint256(keccak256(abi.encodePacked(block.number, i))) % uint256(10) ** 78;
-                require(pseudoRandomValue != 999999, "Invalid value, retry.");
+                for (uint256 j = 0; j < 13; j++) {
+                    uint256 position = j * 6;
+                    uint256 entropy = (pseudoRandomValue / (10 ** (72 - position))) % 1000000;
+                    uint256 paddedEntropy = entropy * (10 ** (6 - numberOfDigits(entropy)));
+                    require(paddedEntropy != 999999, "Invalid value, retry.");
+                }
                entropySlots[i] = pseudoRandomValue;
            }
        }
        lastInitializedIndex = endIndex;
    }
```
