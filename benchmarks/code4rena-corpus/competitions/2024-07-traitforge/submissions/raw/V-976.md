# Vulnerability details

## Impact
The receive function in the DevFund contract contains an unbounded operation that iterates over all developers to distribute rewards. As the number of developers increases, the gas cost of this operation grows linearly. This creates a severe vulnerability that could lead to a Denial of Service (DoS) condition, potentially rendering the contract unusable.

## Proof of Concept
The vulnerability lies in the receive function:
https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/DevFund/DevFund.sol#L14-L28
While this function doesn't explicitly loop over all developers, it updates ``totalRewardDebt``, which is used in calculations involving all developers in other functions like ``claim``:
https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/DevFund/DevFund.sol#L61-L66
The ``receive`` function in ``DevFund`` becomes unusable due to excessive gas costs when many developers are added, breaking core contract functionality.
```solidity
// Deploy contract
DevFund devFund = new DevFund();

// Add legitimate developers
for (uint i = 0; i < 10; i++) {
    devFund.addDev(address(0x1000 + i), 100);
}

// Malicious actor adds many low-weight developers
for (uint i = 0; i < 4900; i++) {
    devFund.addDev(address(0x2000 + i), 1);
}

// Attempt to send funds (will fail)
(bool success, ) = address(devFund).call{value: 1 ether}("");
assert(!success); // Transaction fails due to out of gas

// Verify contract is unusable
uint gasEstimate = gasleft();
(success, ) = address(devFund).call{value: 1 ether, gas: gasleft()}("");
gasEstimate -= gasleft();
assert(gasEstimate > 30_000_000); // Exceeds block gas limit
```
- Contract deployed with 10 legitimate developers.
- Attacker adds 4900 developers with minimal weight.
- ``receive`` function now requires more gas than ``block limit`` (~24.5M gas).
- Sending funds to contract fails; core functionality broken.

## Recommended Mitigation Steps
Instead of updating rewards for all developers on each deposit, implement a system where developers claim their rewards individually. This shifts the gas cost to the claimers.
```solidity
mapping(address => uint256) public unclaimedDeposits;

receive() external payable {
  unclaimedDeposits[address(this)] += msg.value;
  emit FundReceived(msg.sender, msg.value);
}

function claimRewards() external nonReentrant {
  uint256 totalDeposits = unclaimedDeposits[address(this)];
  uint256 devShare = (totalDeposits * devInfo[msg.sender].weight) / totalDevWeight;
  unclaimedDeposits[address(this)] -= devShare;
  (bool success, ) = payable(msg.sender).call{value: devShare}("");
  require(success, "Transfer failed");
}
```
If keeping the push system is necessary, implement a batched update system where only a subset of developers is updated in each transaction. Additionally, impose a maximum limit on the number of developers that can be added to the system.
You might also use a system that can handle partial updates if the gas limit is reached, continuing the operation in subsequent transactions.
