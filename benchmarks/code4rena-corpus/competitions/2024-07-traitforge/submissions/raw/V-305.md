# Vulnerability details



## Proof of Concept

Take a look at https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/DevFund/DevFund.sol#L61-L92

```solidity
  function claim() external whenNotPaused nonReentrant {
    DevInfo storage info = devInfo[msg.sender];

    uint256 pending = info.pendingRewards +
      (totalRewardDebt - info.rewardDebt) *
      info.weight;

    if (pending > 0) {
      uint256 claimedAmount = safeRewardTransfer(msg.sender, pending);
      info.pendingRewards = pending - claimedAmount;
      emit Claim(msg.sender, claimedAmount);
    }

    info.rewardDebt = totalRewardDebt;
  }
```

This functionality is used for claiming by the devs, issue however is that the `DevFund` contract's reward distribution mechanism is flawed, leading to unfair allocation of rewards among developers with equal weights. This issue is particularly problematic when new developers are added and additional funds are received.

Coded POC:

> Attach the POC to: https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/test/DevFund.test.ts#L19
> Run with the command: ` yarn hardhat test test/DevFund.test.ts`

```javascript
it.only('POC: Unfair reward distribution with new devs and additional funds', async function () {
  const [owner, dev1, dev2, dev3, dev4, dev5] = await ethers.getSigners();
  const devFund = await ethers.deployContract('DevFund');

  // Add three initial developers with equal weights
  await devFund.addDev(dev1.address, 100);
  await devFund.addDev(dev2.address, 100);
  await devFund.addDev(dev3.address, 100);

  // Send 3 ETH to the contract
  await owner.sendTransaction({
    to: await devFund.getAddress(),
    value: ethers.parseEther('3'),
  });

  // Dev1 claims their reward
  await devFund.connect(dev1).claim();

  // Add two new developers with the same weight
  await devFund.addDev(dev4.address, 100);
  await devFund.addDev(dev5.address, 100);

  // Send 2 more ETH to the contract
  await owner.sendTransaction({
    to: await devFund.getAddress(),
    value: ethers.parseEther('2'),
  });

  // Log pending rewards after adding new devs and funds
  console.log(
    'Dev1 pending rewards after new funds:',
    (await devFund.pendingRewards(dev1.address)).toString()
  );
  console.log(
    'Dev2 pending rewards after new funds:',
    (await devFund.pendingRewards(dev2.address)).toString()
  );
  console.log(
    'Dev3 pending rewards after new funds:',
    (await devFund.pendingRewards(dev3.address)).toString()
  );
  console.log(
    'Dev4 pending rewards after new funds:',
    (await devFund.pendingRewards(dev4.address)).toString()
  );
  console.log(
    'Dev5 pending rewards after new funds:',
    (await devFund.pendingRewards(dev5.address)).toString()
  );
});
```

This POC reveals the following issues:

1. Unequal distribution despite equal weights:

   - Dev1: 0.4 ETH (after having already claimed 1 ETH)
   - Dev2 and Dev3: 1.4 ETH each
   - Dev4 and Dev5: 0.4 ETH each

2. Dev1 receives new rewards despite having already claimed.

3. New developers (Dev4 and Dev5) receive significantly less rewards than Dev2 and Dev3, despite having the same weight.

## Impact

Developers with the same weight (100) receive vastly different amounts of rewards. Dev2 and Dev3 receive 3.5 times more rewards than Dev4 and Dev5, despite all having equal weights.

Dev1 continues to accrue rewards (0.4 ETH) even after claiming their initial share. This allows a developer to unfairly benefit multiple times from the reward pool _(this can be protected against by the owner removing them)_

This shows how the fundamental principle of distributing rewards based on equal weights is violated, as developers with the same weight receive drastically different rewards.

## Recommended Mitigation Steps

Implement a mechanism to ensure that new funds are distributed equally among all active developers with **the same weight**, regardless of when they were added. Additionally after a developer claims their rewards, they should be automatically removed from the active reward pool. This prevents developers from receiving additional rewards without being explicitly re-added
