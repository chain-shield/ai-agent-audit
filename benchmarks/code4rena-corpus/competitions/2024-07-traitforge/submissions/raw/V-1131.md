# Vulnerability details

## Bug description
Entropy is generated in 3 batches and recorded into 770 slots. 
[EntropyGenerator.sol#L51-L59](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntropyGenerator/EntropyGenerator.sol#L51-L59)
```solidity
unchecked {
    for (uint256 i = lastInitializedIndex; i < endIndex; i++) {
        uint256 pseudoRandomValue = uint256(
            keccak256(abi.encodePacked(block.number, i))
        ) % uint256(10) ** 78; // generate a  pseudo-random value using block number and index
        require(pseudoRandomValue != 999999, 'Invalid value, retry.');
        entropySlots[i] = pseudoRandomValue; // store the value in the slots array
    }
}
```

To calculate entropy hash of the `block.number` and `i` is taken and modulo `uint256(10) ** 78` is applied to ensure that entropy is at most 78-digit number.

The problem is that `uint256(10) ** 78` overflows uint256, but because of an unchecked block the function does not revert and the value wraps around to be equal to `73663286101470436611432119930496737173840122674875487684339327936694962880512`.
This is at most a 77-digit number, meaning that at least one entropy in the slot will always get padded to 6 digits when it's being queued for an NFT, because it's expected that each slot contains exactly a 78-digit number.

[Generator.sol#L181-L182](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntropyGenerator/EntropyGenerator.sol#L181-L182)
```solidity
uint256 entropy = (slotValue / (10 ** (72 - position))) % 1000000; // adjust the entropy value based on the number of digits
uint256 paddedEntropy = entropy * (10 ** (6 - numberOfDigits(entropy)));
```

The possible solution would be to store entropies in 834 slots where each slot would be occupied by a 72-digit number or 12 concatenated entropies, but even then there would be a problem of not ensuring that entropy is indeed a 72-digit number, since taking a modulo `N` only ensures us that the final value is within the range of 0 and `10**N - 1`

1/13 of NFTs will always have a `performanceFactor` of 0 since it's derived by extracting the last digit of entropy and possibly `forgePotential` of 0 since it's derived by extracting the 5th digit of entropy.

## Impact
One entropy in a slot will always get padded to 6 digits, meaning that 1/13 of NFTs will always have a performance factor of 0 and possibly a `forgePotential` of 0.

## Recommended Mitigation
Storing entropies in slots of 78-digit numbers is not feasible, since `type(uint256).max itself is a 78-digit number starting with 1.
It's better to store entropies in 834 slots where each slot would be occupied by a 72-digit number or 12 concatenated entropies. Even then you would need to ensure that the entropy generated is indeed a 72-digit number.

This is how you would do it:
```solidity
function writeEntropyBatch1() public {
    require(
        lastInitializedIndex < batchSize1,
        'Batch 1 already initialized.'
    );
    uint256 endIndex = lastInitializedIndex + batchSize1; // calculate the end index for the batch
    unchecked {
        for (uint256 i = lastInitializedIndex; i < endIndex; i++) {
            uint256 pseudoRandomValue = uint256(
                keccak256(abi.encodePacked(block.number, i))
            );
            // Ensure the value is a 72-digit number
            uint256 minValue = 10 ** 71;
            uint256 maxValue = 10 ** 72 - 1;
            pseudoRandomValue =
                minValue +
                (pseudoRandomValue % (maxValue - minValue + 1));
            entropySlots[i] = pseudoRandomValue; // store the value in the slots array
        }
    }
    lastInitializedIndex = endIndex;
}
```
