# Vulnerability details

## Impact
When Entities are minted, they are minted by generations, which have by design a max tokens per generation, and if it reaches that mark, the code increases the `currentGeneration` variable, and set the mintCount to zero, but what the code did not consider before that action was that generation are not guaranteed to be minted linearly, this means that if that assumption of the code was followed the next gen will only be in action when the currentGen reaches the max mints, but with the forging functionality, this is not so, this will result into setting the current mint count to zero disregarding the ones that have being minted due to forging leading to underestimation of minted tokens and reduction of the true price of minting tokens leading to loss of funds for the `NukeFund` and the Protocol

## Proof of Concept
There are two ways Entities are minted, by normal mint, and by forging, when you forge you must forge between a merger and a forger of the same gen, the result of this is a new entity with entropy of the combination of the two, and the new entity becomes a new gen entity

When it increments, it sets the new gen mint count to zero, which is the root cause of this issue and it stems from an assumption on how entity are minted and which generation they belong too, as how i will explain below with an example

- Lets starts from gen 1 a merger and forger forge together to make a gen 2 entity
- This happens multiple times and mints multiple merger and forgers in gen 2
- Now those gen 2 merge together to make multiple gen 3 tokens, even though the current gen of the contract is gen 1
- Now once gen 1 has being minted completely and we are in gen 2, this vulnerability can show, when we get to the end of gen 2 also now, it tries to increment the current gen and sets the mint count to zero even though for already minted gen 3 the mint count has already being updated multiple times, making the protocol underestimate the amount of tokens minted for that particular generation
- Notice how tricky this issue is because it does not occur on the transition to gen 2, this is because inside the `_mintNewEntity` the gen parameter can never be  1 because, it is increased in the `forge` function and hereby this check will never pass to enter to increment that curentGen,

And about the impact, the protocol use the generationMintCounts to calculate the price at which users will mint new entities as shown below 
```solidity
function calculateMintPrice() public view returns (uint256) {
    uint256 currentGenMintCount = generationMintCounts[currentGeneration];
    uint256 priceIncrease = priceIncrement * currentGenMintCount;
    uint256 price = startPrice + priceIncrease;
    return price;
  }
```

Underestimating the mint count of a gen leads to loss of funds to the `NukeFund` and the Protocol.
