# Vulnerability details

## Impact
`EntropyGenerator::getEntropy()` calculations allows to produce multiple entropies with best value '999999'. Documentation states that there should be only one per generation

## Proof of Concept
Calculation of entropy is by taking 78-digit number and slicing it to 13 6-digits numbers. There is possibility that one of the slices will be `999999` number and code does not protect agaist it.

```solidity
    uint256 slotValue = entropySlots[slotIndex]; // slice the required [art of the entropy value
    uint256 entropy = (slotValue / (10 ** (72 - position))) % 1000000; // adjust the entropy value based on the number of digits
    uint256 paddedEntropy = entropy * (10 ** (6 - numberOfDigits(entropy)));
```
When for example slotValue is 78-digit number similar to this:
`123456...999999123456`
then entropy of `numberIndex=11` will be `999999`

Additionaly there is missing value check in writeEntropyBatch3
https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntropyGenerator/EntropyGenerator.sol#L76
https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/EntropyGenerator/EntropyGenerator.sol#L94-L95

Documentation states that the value of `999999` should be in third batch but code does not insert this value anywhere. It just compares selected indexes and returns `999999` when they match. It means that the same require check in writeEntropyBatch3 is needed as in writeEntropyBatch1 and writeEntropyBatch2 to avoid multiple best values.

## Recommended Mitigation Steps
1. Add require check to writeEntropyBatch3
```diff
  function writeEntropyBatch3() public {
    require(
      lastInitializedIndex >= batchSize2 && lastInitializedIndex < maxSlotIndex,
      'Batch 3 not ready or already completed.'
    );
    unchecked {
      for (uint256 i = lastInitializedIndex; i < maxSlotIndex; i++) {
        uint256 pseudoRandomValue = uint256(
          keccak256(abi.encodePacked(block.number, i))
        ) % uint256(10) ** 78;
        entropySlots[i] = pseudoRandomValue;
+       require(pseudoRandomValue != 999999, 'Invalid value, retry.');
      }
    }
    lastInitializedIndex = maxSlotIndex;
  }
```
2. As we operate on slices of bigger value, with current implementation of `EntropyGenerator::getEntropy()` the only solution I see is to assign other value when we get '999999' value
```diff
  function getEntropy(
    uint256 slotIndex,
    uint256 numberIndex
  ) private view returns (uint256) {
    require(slotIndex <= maxSlotIndex, 'Slot index out of bounds.');

    if (
      slotIndex == slotIndexSelectionPoint &&
      numberIndex == numberIndexSelectionPoint
    ) {
      return 999999;
    }

    uint256 position = numberIndex * 6; // calculate the position for slicing the entropy value
    require(position <= 72, 'Position calculation error');

    uint256 slotValue = entropySlots[slotIndex]; // slice the required [art of the entropy value
    uint256 entropy = (slotValue / (10 ** (72 - position))) % 1000000; // adjust the entropy value based on the number of digits
    uint256 paddedEntropy = entropy * (10 ** (6 - numberOfDigits(entropy)));

+    if(paddedEntropy == 999999){
+      return 123456;
+    }

    return paddedEntropy; // return the caculated entropy value
  }
```
That don't look like the good solution.
Rethink implementation of `EntropyGenerator::getEntropy()`.
Consider using decentralized oracle like Chainlink to get random numbers
