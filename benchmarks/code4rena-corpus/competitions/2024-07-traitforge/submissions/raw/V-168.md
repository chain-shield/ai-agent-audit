# Vulnerability details

## Impact
It's documented that the god NFT, having entropy of 999999, is the most powerful NFT, and thus it has special mint conditions. However due to the "randomness" more than 1 god NFTs can be minted per generation.

## Proof of Concept
[getEntropy](https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/EntropyGenerator/EntropyGenerator.sol#L164) has a special case when both `slotIndex` and `numberIndex` match their predefined values a NFT with ID of 999_999 will be returned.

```solidity
        if (slotIndex == slotIndexSelectionPoint && numberIndex == numberIndexSelectionPoint) {
            return 999999;
        }
```

However in the case if the entropy randomly has a slot with 999_999 that value will also be returned, minting a second god NFT.

### 1 Why the system doesn't stop us from getting another god NFT
Getting such a number is possible as [writeEntropyBatch](https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/EntropyGenerator/EntropyGenerator.sol#L47) function don't actually protect against it, because the modulo operator doesn't do the right math. It actually doesn't do anything, since when `x <= 1.17e77` then `x % 10e78 = x`.

```solidity
   for (uint256 i = lastInitializedIndex; i < endIndex; i++) {
      uint256 pseudoRandomValue = uint256(keccak256(abi.encodePacked(block.number, i))) % uint256(10) ** 78;
      require(pseudoRandomValue != 999999, "Invalid value, retry.");
      entropySlots[i] = pseudoRandomValue;
            }
```

### 2 How to get another god NFT
When [getEntropy](https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/EntropyGenerator/EntropyGenerator.sol#L164) is triggered it will get a 6 digit number from the index of the array. Example is if the array is `012345678910` it will get `012345` first and if called again it will get `678910`.

```solidity
    // get position
    uint256 position = numberIndex * 6;

    require(position <= 72, "Position calculation error");

    //extract 6 digit number
    uint256 slotValue = entropySlots[slotIndex]; 

    uint256 entropy = (slotValue / (10 ** (72 - position))) % 1000000; 

    //increase if less 6 digits
    uint256 paddedEntropy = entropy * (10 ** (6 - numberOfDigits(entropy))); 
    return paddedEntropy; 
```

This means that if inside the entropy there is a slot with 999_999 that slot will be another god NFT.

To get such a slot would be easy as the entropy generation is public, predictable and controllable. That is because it's [generated based on block.number](https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/EntropyGenerator/EntropyGenerator.sol#L73-L76), where `block.number` is predictable and controllable. It can be controlled by:
1. Calling it the next block
2. If on purpose the builders doesn't include it in the batch for this block.

## Recommended Mitigation Steps
Note that it's not the way it's generated that is the issue. ChainLink VRF can still return a number with a slot of 999_999. The way that they are checked needs to be redone, but that will cost too much gas. An easy solution would be to make [getEntropy](https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/EntropyGenerator/EntropyGenerator.sol#L182-L184) return a different number if the slot is 999_999.

Example code:

```diff
    uint256 paddedEntropy = entropy * (10 ** (6 - numberOfDigits(entropy)));
    
+   if (paddedEntropy == 999_999){
+       return uint256(keccak256(abi.encode(paddedEntropy))) % 1_000_000;
+   }

    return paddedEntropy; 
```
