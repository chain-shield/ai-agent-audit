# Vulnerability details

## Impact
`EntityForging::forgeWithListed` function allows users to forge with a listed Forger and pay a fee. However, the function includes the following requirement:
```
    require(msg.value >= forgingFee, 'Insufficient fee for forging');
```
This can result in any extra Ether sent via msg.value being locked in the smart contract indefinitely.


## Proof of Concept
Consider a scenario where a Forger is listed with a fee of 0.1 ETH. If a user calls the forgeWithListed function with a value exceeding 0.1 ETH:

1. Forger is listed with a fee of 0.1ETH
2. a user call `forgeWithListed` function with value of 1ETH (which is just an additional 0 in wei).
3. all math calculations in the function are being calculated by `forgingFee` and not msg.value:
```
        uint256 devFee = forgingFee / taxCut;
        uint256 forgerShare = forgingFee - devFee;
        address payable forgerOwner = payable(nftContract.ownerOf(forgerTokenId));

        uint256 newTokenId = nftContract.forge(msg.sender, forgerTokenId, mergerTokenId, "");
        (bool success,) = nukeFundAddress.call{value: devFee}("");
        require(success, "Failed to send to NukeFund");
        (bool success_forge,) = forgerOwner.call{value: forgerShare}("");
        require(success_forge, "Failed to send to Forge Owner");
```
4. The transaction will go through, and there is no mechanism to check or refund any excess payment.
5. All additional Ether sent by the user will remain locked in the smart contract permanently.

## Tools Used
Manual review

## Recommended Mitigation Steps
To prevent the loss of funds, replace the requirement with:
```
require(msg.value == forgingFee, 'Insufficient fee for forging');
```
This ensures that no excess Ether will be sent or locked in the smart contract.
