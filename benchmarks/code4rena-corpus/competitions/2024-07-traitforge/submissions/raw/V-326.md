# Vulnerability details

One of the key features of the `TraitForgeNft` contract is tracking the timestamp of the last transfer for each token using the `lastTokenTransferredTimestamp` mapping.

The [_beforeTokenTransfer()](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L367-L396) function is an internal hook that is called before a token transfer occurs. It is responsible for updating the `lastTokenTransferredTimestamp` and handling the unlisting of tokens from forging if they are being transferred.

However, there is an issue with the logic that updates the `lastTokenTransferredTimestamp`. The condition `if (from != to)` is meant to update the timestamp only when the `from` and `to` addresses are different, indicating a genuine transfer. 

The bug lies in the implementation of the timestamp update logic. Even though the condition `if (from != to)` is correct, the `lastTokenTransferredTimestamp` is not being updated as expected when `from` and `to` are different. [TraitForgeNft.sol#L375-L379](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L375-L379)

```solidity
uint listedId = entityForgingContract.getListedTokenIds(firstTokenId);
/// @dev don't update the transferred timestamp if from and to address are same
if (from != to) {
    // Bug: The lastTokenTransferredTimestamp is not being updated correctly when from and to addresses are different.
    lastTokenTransferredTimestamp[firstTokenId] = block.timestamp;
}
```

The root cause of the issue needs to be investigated further to determine why the timestamp is not being updated correctly within the `if (from != to)` block.

The issue is in the order of operations and the side effects of the `entityForgingContract.getListedTokenIds(firstTokenId)` function call.

   1. The [getListedTokenIds(firstTokenId)](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L375) is called before the `if (from != to)` block.
   2. One possible scenario is that the `getListedTokenIds(firstTokenId)` may revert or throw an exception under certain conditions. If this happens, the execution of the `_beforeTokenTransfer()` function will be halted, and the [lastTokenTransferredTimestamp](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/TraitForgeNft/TraitForgeNft.sol#L378) will not be updated.
  
## Impact

1. The `lastTokenTransferredTimestamp` mapping will not accurately reflect the timestamp of the last transfer for tokens. This can lead to incorrect tracking of token transfer history and any functionality that relies on this timestamp.

4. Any external system or off-chain process that relies on the accuracy of the `lastTokenTransferredTimestamp` may make incorrect assumptions or decisions based on the outdated timestamp.

## Proof of Concept

A scenario where `from` and `to` are different addresses, but `lastTokenTransferredTimestamp` remains unchanged after the token transfer.

1. Alice owns a token with ID 1.

2. Alice transfers the token to Bob using the `transferFrom()` function.

5. The `_beforeTokenTransfer()` function is called as part of the transfer process.

6. Despite Alice's address being different from Bob's, the `lastTokenTransferredTimestamp` for token ID 1 is not updated correctly.

7. The `lastTokenTransferredTimestamp` remains unchanged, even though the token has been transferred from Alice to Bob.

As a result, the `lastTokenTransferredTimestamp` does not accurately reflect the timestamp of the last transfer for the token.

## Recommended Mitigation Steps

Refactor the timestamp update logic to ensure that it is reliable and accurate.
  - One approach could be to move the `getListedTokenIds(firstTokenId)` call outside the `_beforeTokenTransfer()` function and handle the unlisting of tokens separately.
