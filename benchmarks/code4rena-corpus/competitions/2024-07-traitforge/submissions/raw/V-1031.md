# Vulnerability details

## Impact
The current ``DevFund`` implementation contract suffers from precision loss due to integer division. This can lead to unfair reward distribution, especially for developers with smaller weights or when dealing with small amounts of incoming funds. Over time, this could result in significant discrepancies between expected and actual rewards, potentially undermining the fairness and integrity of the reward system.

## Proof of Concept
The vulnerability lies in the ``receive`` function:
https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/DevFund/DevFund.sol#L14-L18
Three developers with different weights:
Dev A, with a weight of 100 out of 131, should receive approximately 76.34% of the funds.
Dev B, with a weight of 30 out of 131, should receive approximately 22.90% of the funds.
Dev C, with a weight of 1 out of 131, should receive approximately 0.76% of the funds.
Send 131 wei to the contract
Expected distribution:
Dev A: ```100 wei (approximately 76.34% of 131 wei)```
Dev B: ```30 wei (approximately 22.90% of 131 wei)```
Dev C: ```1 wei (approximately 0.76% of 131 wei)```
Actual distribution due to precision loss:
Dev A: ```100 wei```
Dev B: ```30 wei```
Dev C: ```0 wei```
Remaining (sent to owner): ```1 wei```
The remaining ```1 wei```, which was supposed to go to Dev C, ends up not being distributed due to the truncation effect of integer division

## Recommended Mitigation Steps
To mitigate this issue, implement a more precise reward calculation mechanism using a larger scale factor. Here's a proposed solution:
```solidity
    DevFund is IDevFund {
    uint256 private constant PRECISION = 1e18;
    uint256 public accRewardPerWeight;
    
    struct DevInfo {
        uint256 weight;
        uint256 rewardDebt;
    }
    
    mapping(address => DevInfo) public devInfo;
    uint256 public totalDevWeight;
    
    receive() external payable {
        if (totalDevWeight > 0) {
            accRewardPerWeight += (msg.value * PRECISION) / totalDevWeight;
        }
        emit FundReceived(msg.sender, msg.value);
    }
    
    function addDev(address user, uint256 weight) external override onlyOwner {
        DevInfo storage dev = devInfo[user];
        if (dev.weight > 0) {
            uint256 pending = (dev.weight * accRewardPerWeight / PRECISION) - dev.rewardDebt;
            dev.rewardDebt = dev.weight * accRewardPerWeight / PRECISION;
            // Transfer pending rewards or store for later claiming
        }
        totalDevWeight = totalDevWeight + weight - dev.weight;
        dev.weight = weight;
        dev.rewardDebt = weight * accRewardPerWeight / PRECISION;
        emit AddDev(user, weight);
    }
    
    function claim() external override {
        DevInfo storage dev = devInfo[msg.sender];
        uint256 pending = (dev.weight * accRewardPerWeight / PRECISION) - dev.rewardDebt;
        if (pending > 0) {
            dev.rewardDebt = dev.weight * accRewardPerWeight / PRECISION;
            // Transfer pending to msg.sender
            emit Claim(msg.sender, pending);
        }
    }
    
    function pendingRewards(address user) external view override returns (uint256) {
        DevInfo storage dev = devInfo[user];
        return (dev.weight * accRewardPerWeight / PRECISION) - dev.rewardDebt;
    }
    
    // Implement other required functions: removeDev, etc.
}
```
This solution uses an accumulated reward per weight approach with a high precision factor. It ensures fair distribution even for small weights and amounts, significantly reducing the impact of precision loss.
