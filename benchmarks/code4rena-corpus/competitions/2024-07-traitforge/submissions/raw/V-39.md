# Vulnerability details

## Impact
`NFT` approvals remain even after token transfers/sale. This allows a malicious users to sell their NFT then drain everything after sale due to previous approvals.

## Proof of Concept
In the `EntityTrading` contract, when a user lists their `tokenId` for sale via [`listNFTForSale()`](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityTrading/EntityTrading.sol#L38-L60), there is no explicit revokation of approvals:
```solidity
function listNFTForSale(
    uint256 tokenId,
    uint256 price
  ) public whenNotPaused nonReentrant {
    require(price > 0, 'Price must be greater than zero');
    require(
      nftContract.ownerOf(tokenId) == msg.sender,
      'Sender must be the NFT owner.'
    );
    require(
      nftContract.getApproved(tokenId) == address(this) ||
        nftContract.isApprovedForAll(msg.sender, address(this)),
      'Contract must be approved to transfer the NFT.'
    );

    nftContract.transferFrom(msg.sender, address(this), tokenId); // trasnfer NFT to contract

    ++listingCount;
    listings[listingCount] = Listing(msg.sender, tokenId, price, true);
    listedTokenIds[tokenId] = listingCount;

    emit NFTListed(tokenId, msg.sender, price);
  }
```
Then when another user buys this `tokenId` via the [`buyNFT()`](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/EntityTrading/EntityTrading.sol#L63-L92), this NFT will be transfered from the contract to their wallet. As such, all the previous approvals will come attached to this NFT.
```solidity
function buyNFT(uint256 tokenId) external payable whenNotPaused nonReentrant {
    Listing memory listing = listings[listedTokenIds[tokenId]];
    require(
      msg.value == listing.price,
      'ETH sent does not match the listing price'
    );
    require(listing.seller != address(0), 'NFT is not listed for sale.');

    //transfer eth to seller (distribute to nukefund)
    uint256 nukeFundContribution = msg.value / taxCut;
    uint256 sellerProceeds = msg.value - nukeFundContribution;
    transferToNukeFund(nukeFundContribution); // transfer contribution to nukeFund

    // transfer NFT from contract to buyer
    (bool success, ) = payable(listing.seller).call{ value: sellerProceeds }(
      ''
    );
    require(success, 'Failed to send to seller');
    nftContract.transferFrom(address(this), msg.sender, tokenId); // transfer NFT to the buyer

    delete listings[listedTokenIds[tokenId]]; // remove listing

    //...
  }
```
The issue here is that functions such as [`NukeFund::nuke()`](https://github.com/code-423n4/2024-07-traitforge/blob/279b2887e3d38bc219a05d332cbcb0655b2dc644/contracts/NukeFund/NukeFund.sol#L153-L182) allow the approved spender to nuke the `tokenId`.
```solidity
  function nuke(uint256 tokenId) public whenNotPaused nonReentrant {
    require(
>>    nftContract.isApprovedOrOwner(msg.sender, tokenId), // @audit-info Approved user can nuke
      'ERC721: caller is not token owner or approved'
    );
    
    //...
>>  (bool success, ) = payable(msg.sender).call{ value: claimAmount }(''); // @audit-info Approved user earns claimAmount
    require(success, 'Failed to send Ether');
    //...
  }
```

### Scenario:
`ERC721` token `approval` persist regardless of the owner of the NFT. The result is that approvals set by one owner can be accessed after a token has been sold or transferred. This allows the following attack:
- User A owns `tokenId = 1`
- User A sets approval to themselves
- User A sells `tokenId = 1` to User B
- User A uses persistent approval to `nuke` this `tokenId`
---> As such, a previously approved spender may `nuke` a given NFT without the current owner's permision and earn `claimAmount` for this action.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Consider revoking all existing approvals from the NFT whenever an NFT is transferred/sold.
