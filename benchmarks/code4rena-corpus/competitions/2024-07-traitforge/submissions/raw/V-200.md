# Vulnerability details

## Impact
The rewards that devs can receive will be affected by MEV.

The attacker can manipulate the rewards that dev can obtain by modifying the sorting results.

## Proof of Concept
In `DevFund`, whenever the contract receives native tokens, `totalRewardDebt` is increased.

https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/DevFund/DevFund.sol#L14-L18
```solidity
  receive() external payable {
    if (totalDevWeight > 0) {
      uint256 amountPerWeight = msg.value / totalDevWeight;
      uint256 remaining = msg.value - (amountPerWeight * totalDevWeight);
      totalRewardDebt += amountPerWeight;
```

At `addDev`, the current `totalRewardDebt` will be assigned to `devInfo[user].rewardDebt`, serving as the starting point for recording the user's reward.

https://github.com/code-423n4/2024-07-traitforge/blob/main/contracts/DevFund/DevFund.sol#L30-L34
```solidity
  function addDev(address user, uint256 weight) external onlyOwner {
    DevInfo storage info = devInfo[user];
    require(weight > 0, 'Invalid weight');
    require(info.weight == 0, 'Already registered');
    info.rewardDebt = totalRewardDebt;
```

The problem here is that, within the same block, the execution of `receive()` before or after `addDev()` has different effects. For example:

`receive` occurring before `addDev`:
1. Initial state: There is one dev named Alice with weight 1, and totalRewardDebt is 0.
2. 10 tokens are sent to receive, and totalRewardDebt becomes 10.
3. addDev is executed, adding Bob with weight 1, so Bob's rewardDebt is 10.
4. Another 10 tokens are sent to the contract, and totalRewardDebt becomes 10+10/2=15.
5. Alice can claim 15, and Bob can claim 5.

`receive` occurring after `addDev`:
1. Initial state: There is one dev named Alice with weight 1, and totalRewardDebt is 0.
2. addDev is executed, adding Bob with weight 1, so Bob's rewardDebt is 0.
2. 10 tokens are sent to receive, and totalRewardDebt becomes 10/2=5.
4. Another 10 tokens are sent to the contract, and totalRewardDebt becomes 5+10/2=10.
5. Alice can claim 10, and Bob can claim 10.

In `removeDev` and `updateDev`, the same problem exists.

The order of transactions within a block can be easily changed in MEV by simply creating a bundle and passing it to the builder for execution.

## Recommended Mitigation Steps
Before all operations, update rewardPerWeight, and rewardPerWeight can only be updated once within a block, so that the reward that can be obtained is only based on the data up to the previous block, and will not be affected by the operations in the current block.

Similar to most yield farming protocols, like the classic MasterChef contract.

https://github.com/pancakeswap/pancake-farm/blob/master/contracts/MasterChef.sol#L210

```solidity
    // Update reward variables of the given pool to be up-to-date.
    function updatePool(uint256 _pid) public {
        PoolInfo storage pool = poolInfo[_pid];
        if (block.number <= pool.lastRewardBlock) {
            return;
        }
        uint256 lpSupply = pool.lpToken.balanceOf(address(this));
        if (lpSupply == 0) {
            pool.lastRewardBlock = block.number;
            return;
        }
        uint256 multiplier = getMultiplier(pool.lastRewardBlock, block.number);
        uint256 cakeReward = multiplier.mul(cakePerBlock).mul(pool.allocPoint).div(totalAllocPoint);
        cake.mint(devaddr, cakeReward.div(10));
        cake.mint(address(syrup), cakeReward);
        pool.accCakePerShare = pool.accCakePerShare.add(cakeReward.mul(1e12).div(lpSupply));
        pool.lastRewardBlock = block.number;
    }
```
