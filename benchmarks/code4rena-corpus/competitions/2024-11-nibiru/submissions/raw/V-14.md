# Vulnerability details

## Finding description and impact

The Nibiru project uses CometBFT 0.37.5 as specified in its `go.mod`, which is affected by a medium severity vulnerability ([ASA-2024-009](https://github.com/cometbft/cometbft/security/advisories/GHSA-g5xx-c4hv-9ccc)). The vulnerability allows a malicious state sync node to provide an invalid state of the proposer selection algorithm, which could lead to a chain split.

When validators state sync from RPC endpoints with invalid proposer priority states, they will:
1. Disagree with other validators about block proposer selection
2. Reject valid blocks due to proposer mismatch
3. Have their own proposed blocks rejected by the network
4. Eventually contribute to network halt if enough validators are affected

The impact is medium severity because:
1. It requires malicious or misconfigured RPC endpoints
2. It primarily affects new validators joining the network via state sync
3. The network can continue operating as long as a sufficient number of validators have valid states
4. There is no direct risk of asset loss, but network availability could be impacted

## Proof of Concept

The vulnerability exists in CometBFT versions:
- >= 0.34.0, <= 0.34.33
- >= 0.37.0, <= 0.37.10 (includes Nibiru's v0.37.5)
- >= 0.38.0, <= 0.38.11

The issue occurs because the light client protocol used during state sync validates the validator set but not the `ProposerPriority` field of each validator. This allows a malicious RPC endpoint to provide an invalid proposer selection state that will be accepted by the syncing validator.

To reproduce:
1. Run a malicious RPC node that serves altered `ProposerPriority` values
2. Configure a new validator to state sync from this node
3. Observe the validator rejecting valid blocks and having its proposals rejected
4. Repeat with multiple validators to observe network degradation

## Recommended mitigation steps

1. Upgrade CometBFT to version 0.37.11 or later, which includes the patch for this vulnerability. The patch adds validation of `ProposerPriority` fields during state sync.

2. Until the upgrade is completed:
   - Maintain a list of trusted RPC endpoints for validators to use during state sync
   - Document the risk and mitigation steps for validators joining the network
   - Monitor for validators with invalid proposer states by comparing `/validators?height=_` RPC endpoint outputs across nodes
   - Consider temporarily disabling state sync if network stability is at risk
