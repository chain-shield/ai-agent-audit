# Vulnerability details

## Finding description and impact

The current functionality of `evmante_increment_sender_seq` is designed to increment a nonce parameter of an account (sender). The problem is that there is no check whether the operation is a contract creation leading to a situation where a nonce will be incremented NOT during the contract creation process.

## Proof of Concept

At the moment `AnteHandle()` just increments a nonce for a specific sender:

https://github.com/code-423n4/2024-11-nibiru/blob/main/app/evmante/evmante_increment_sender_seq.go#L52-68
```
acc := issd.accountKeeper.GetAccount(ctx, msgEthTx.GetFrom())
		if acc == nil {
			return ctx, errors.Wrapf(
				sdkerrors.ErrUnknownAddress,
				"account %s is nil", gethcommon.BytesToAddress(msgEthTx.GetFrom().Bytes()),
			)
		}
		nonce := acc.GetSequence()

		// we merged the nonce verification to nonce increment, so when tx includes multiple messages
		// with same sender, they'll be accepted.
		if txData.GetNonce() != nonce {
			return ctx, errors.Wrapf(
				sdkerrors.ErrInvalidSequence,
				"invalid nonce; got %d, expected %d", txData.GetNonce(), nonce,
			)
		}

```

However, there is a following requirement:

https://github.com/code-423n4/2024-11-nibiru/blob/main/app/evmante/evmante_increment_sender_seq.go#L28-30
```
// AnteHandle handles incrementing the sequence of the signer (i.e. sender). If the transaction is a
// contract creation, the nonce will be incremented during the transaction execution and not within
// this AnteHandler decorator.
```

There is currently no check for whether the operation is a contract creation (`to` == `nil`) or not.

## Recommended mitigation steps

Add a check for `to` == `nil` situation to indicate that operation is a contract creation and the nonce behavior has to be handled differently.
