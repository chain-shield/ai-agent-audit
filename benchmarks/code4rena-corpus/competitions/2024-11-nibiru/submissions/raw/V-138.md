# Vulnerability details

## Issue Description

Functions like Transfer and Mint interact with external contracts, but there is no reentrancy protection.

Functions like Transfer and Mint interact with external contracts without implementing reentrancy protection. This lack of safeguards can leave the contract vulnerable to reentrancy attacks, where a malicious contract calls back into the original contract before the first invocation is complete, leading to undesired or malicious behavior.

## Proof of Concept #1:

Consider the Transfer function. When transferring tokens to a potentially malicious contract, the recipient contract can call back into the Transfer function before the balance update completes.

Example Attack Scenario
An attacker deploys a malicious contract with the following functionality:

    contract Malicious {
    ERC20 public target;
    address public attacker;

    constructor(address _target) {
        target = ERC20(_target);
        attacker = msg.sender;
    }

    function attack() public {
        // Initiates the transfer call
        target.transfer(address(this), 100);
    }

    fallback() external payable {
        // Reenters the vulnerable contract during the transfer
        target.transfer(address(this), 100);
    }
    }


In the provided Go code:

    resp, err = e.CallContract(ctx, e.ABI, from, &contract, true, Erc20GasLimitExecute, "transfer", 
    to, amount)


The external call (e.CallContract) allows the recipient (to) to execute its fallback function, potentially reentering the Transfer function.

## Proof of Concept #2:

An attacker could exploit a reentrancy vulnerability to drain tokens.

## Impact

The entire token supply could be drained in a reentrancy attack.

#1. Token Drain: An attacker could repeatedly call the Transfer or Mint functions, draining the contract’s funds or minted tokens.

#2. Contract Disruption: Unintended recursion could cause the contract to enter an inconsistent state or fail altogether.

## Risk

High – This could result in catastrophic losses.

Reentrancy attacks are among the most damaging vulnerabilities in smart contracts, often resulting in total loss of funds.

## Mitigation #1:

Use Reentrancy Guards Implement a simple reentrancy guard to prevent multiple simultaneous executions of the vulnerable functions. This involves using a locking mechanism to disallow reentry.

Add a reentrancy lock:

    import "sync"

    var reentrancyLock sync.Mutex

    func (e erc20Calls) Transfer(
    contract, from, to gethcommon.Address, amount *big.Int,
    ctx sdk.Context,
    ) (balanceIncrease *big.Int, resp *evm.MsgEthereumTxResponse, err error) {
    reentrancyLock.Lock()
    defer reentrancyLock.Unlock()

    // Existing logic follows
    recipientBalanceBefore, err := e.BalanceOf(contract, to, ctx)
    if err != nil {
        return balanceIncrease, nil, errors.Wrap(err, "failed to retrieve recipient balance")
    }

    resp, err = e.CallContract(ctx, e.ABI, from, &contract, true, Erc20GasLimitExecute, "transfer", 
    to, amount)
    if err != nil {
        return balanceIncrease, nil, err
    }

    // Process response and balances
    // ...
    }


## Mitigation #2:

Update Contract State Before External Calls Ensure all contract state changes (e.g., balance updates, transfer logs) are completed before any external calls.

Revised Transfer Logic:

    // Update internal balances or state here before calling the external contract
    updateBalance(from, to, amount)

    // External call after updating the state

    to, amount)
