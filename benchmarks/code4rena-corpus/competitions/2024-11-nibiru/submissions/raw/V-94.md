# Vulnerability details

## Issue Description: 

The contract's sendToBank method does not validate inputs comprehensively. The argument parsing (parseArgsSendToBank) assumes that inputs will always be of the expected type and format. If malformed input is passed, the contract will crash or behave unpredictably.

- The amount parameter in sendToBank is validated only as amount.Cmp(big.NewInt(0)) != 1, which excludes nil but doesn't ensure sufficient precision (e.g., very small amounts).

- The to parameter validation relies solely on sdk.AccAddressFromBech32, which doesn’t verify if the address is active or capable of receiving tokens.

## Proof of Concept:

If an attacker or faulty client calls sendToBank with invalid arguments (e.g., a non-Ethereum address or a non-positive amount), the contract might break or misbehave.

## Impact:

- Untrusted or invalid inputs could lead to unexpected behavior, contract failures, or vulnerabilities (e.g., denial of service attacks).

- This could also result in a loss of funds or undetected errors.

- Token transfers with insufficient amounts may waste gas or create negligible ledger entries.

- Tokens might be sent to invalid or dormant accounts.

## Risk:

- Security vulnerabilities from malicious or incorrect inputs could lead to token theft or loss of funds.
- Contract instability from unhandled edge cases.

## Mitigation:

Implement more thorough input validation (e.g., checking address formats, ensuring amounts are non-zero and positive).

Ensure that proper error messages are thrown when inputs don't conform to expected formats.
