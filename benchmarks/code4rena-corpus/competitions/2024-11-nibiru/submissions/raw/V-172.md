# Vulnerability details

## Finding description and impact

The `Transfer` function in `erc20.go` encounters a significant point when handling USDT and similar tokens that do not return a boolean value upon transfer. This non-standard behavior breaks the ABI unpacking process, leading to  error in the function. As a result, even though the transfer is successfully executed on the EVM side, the function returns an error, causing the Cosmos SDK to perceive the transaction as failed.

USDT, like some other tokens, does not conform to the standard ERC20 behavior of returning a boolean value upon a successful transfer. This deviation causes the ABI unpacking process to fail, resulting in an error being returned by the `Transfer` function. Consequently, the Cosmos SDK, which relies on this function's return value to update its state, perceives the transaction as unsuccessful.

Here´s the USDT contract´s `transfer` method:
```solidity
    /**
    * @dev transfer token for a specified address
    * @param _to The address to transfer to.
    * @param _value The amount to be transferred.
    */
    function transfer(address _to, uint _value) public onlyPayloadSize(2 * 32) {
        uint fee = (_value.mul(basisPointsRate)).div(10000);
        if (fee > maximumFee) {
            fee = maximumFee;
        }
        uint sendAmount = _value.sub(fee);
        balances[msg.sender] = balances[msg.sender].sub(_value);
        balances[_to] = balances[_to].add(sendAmount);
        if (fee > 0) {
            balances[owner] = balances[owner].add(fee);
            Transfer(msg.sender, owner, fee);
        }
        Transfer(msg.sender, _to, sendAmount);
    }
```
[Code Source](https://vscode.blockscan.com/ethereum/0xdac17f958d2ee523a2206206994597c13d831ec7)

As can be seen, there are no boolean returns.


This leads to a critical state inconsistency: the EVM reflects the correct token balances post-transfer, but the Cosmos bank module does not update, leaving users with incorrect balance information. This discrepancy is also problematic for FunTokens, which rely on accurate mappings between ERC20 tokens and Cosmos bank coins.
```go
func (e erc20Calls) Transfer(...) {
    // Transfer executes successfully in EVM
    resp, err = e.CallContract(...)

    // Attempt to unpack boolean return
    var erc20Bool ERC20Bool
    err = e.ABI.UnpackIntoInterface(&erc20Bool, "transfer", resp.Ret)
    // Fails here for USDT, which doesn't return a boolean

    // Function returns error, never reaching balance check
    if !success {
        return balanceIncrease, nil, fmt.Errorf("transfer executed but returned success=false")
    }
}
```


To summarize the flow:

The `Transfer` function in `erc20.go` calls the `CallContract` method, which is responsible for executing the actual transfer on the EVM side. This method sends the transaction to the EVM, where it is processed according to the smart contract logic.

```go

func (e erc20Calls) Transfer(...) {
    // Execute the transfer on the EVM
    resp, err = e.CallContract(ctx, e.ABI, from, &contract, true, Erc20GasLimitExecute, "transfer", to, amount)
    // The EVM processes this call and updates its state
}
```

Once the `CallContract` method is invoked, the EVM processes the transaction and updates the token balances accordingly. 
This means that the transfer is effectively completed on the EVM side, and the token balances are adjusted.


After the EVM call, the `Transfer` function attempts to unpack the return value to check for a boolean success indicator.
If the token, like USDT, does not return a boolean, the unpacking fails, and the function returns an error.
```go
// Attempt to unpack boolean return
var erc20Bool ERC20Bool
err = e.ABI.UnpackIntoInterface(&erc20Bool, "transfer", resp.Ret)
// Fails here for USDT, which doesn't return a boolean
```

Despite the successful execution on the EVM, the error in unpacking causes the Cosmos SDK to perceive the transaction as failed. The Cosmos state does not update to reflect the EVM's changes, leading to a discrepancy in token balances.

The EVM, which is responsible for executing the smart contract logic, correctly updates the token balances. Therefore, the actual token balances on the EVM are accurate, preventing double spending at the contract level.

Besides, the tokens are not lost; they are correctly transferred on the EVM side. The issue is with the Cosmos state not reflecting this transfer, not with the actual movement of tokens.

This clearly breaks the state integrity at Cosmos level.
## Recommended mitigation steps

-  Modify the `Transfer` function to prioritize checking the balance change over relying on the boolean return. This ensures that even if the boolean unpacking fails, the function can still verify the transfer's success by comparing pre- and post-transfer balances.

OR
- Implement a mechanism to handle tokens like USDT that do not return a boolean. This could involve a fallback process that defaults to balance checks when the boolean unpacking fails.
