# Vulnerability details

The PendingTransactions function returns the transactions that are still unconfirmed in the current transaction pool. The goal of the function is to retrieve unconfirmed transactions, decode them, and process them further.

https://github.com/code-423n4/2024-11-nibiru/blob/main/eth/rpc/backend/chain_info.go#L74

```go
// PendingTransactions returns the transactions that are in the transaction pool
// and have a "from" address that is one of the accounts this node manages.
func (b *Backend) PendingTransactions() ([]*sdk.Tx, error) {
	mc, ok := b.clientCtx.Client.(tmrpcclient.MempoolClient)
	if !ok {
		return nil, errors.New("invalid rpc client")
	}

	res, err := mc.UnconfirmedTxs(b.ctx, nil)
	if err != nil {
		return nil, err
	}

	result := make([]*sdk.Tx, 0, len(res.Txs))
	for _, txBz := range res.Txs {
		tx, err := b.clientCtx.TxConfig.TxDecoder()(txBz)
		if err != nil {
			return nil, err
		}
		result = append(result, &tx)
	}

	return result, nil
}
```

In this function, a slice is initialized using make, and then the function iterates over the transactions in the pool. It decodes each transaction and appends the decoded transaction to the result slice.

```go
result := make([]*sdk.Tx, 0, len(res.Txs)) // <--------
for _, txBz := range res.Txs {
    tx, err := b.clientCtx.TxConfig.TxDecoder()(txBz)
    if err != nil {
        return nil, err
    }
    result = append(result, &tx)     // <--------
}
```

However, the use of append here adds elements directly to the end of the result slice instead of inserting them starting from index 0.

This causes two main issues:

1. **Unutilized Space**: The slice’s indices from 0 to len(res.Txs)-1 are filled with zero values, as they are never used. When the result slice is returned, other functions that iterate over this slice will encounter zeros in positions 0 through len(res.Txs)-1.
2. **Slice Reallocation**: The slice may continuously expand, wasting memory space and reducing program efficiency.

### First Function Affected by the Faulty Slice:

The getTransactionByHashPending function searches the transaction pool (mempool) for a pending transaction (i.e., one not yet included in a block).

This function receives the faulty slice returned by PendingTransactions and iterates over it. Since the slice's indices from 0 to len(res.Txs)-1 are filled with zeros, it triggers repeated failures in UnwrapEthereumMsg, which tries to unpack the data.

### Impact

This issue leads to several significant problems:

- **Incorrect Transaction Data**: When txs contains invalid transaction elements, further operations on these elements fail. This causes errors like evm.UnwrapEthereumMsg(tx, txHash) to be triggered, but these errors don't prevent subsequent attempts to unpack other transactions.
- **Performance Waste**: Even if the transaction pool doesn't contain valid transactions, getTransactionByHashPending will still iterate over every element of the slice, including those filled with zeros. This results in unnecessary CPU cycles being consumed, which increases system load and reduces efficiency.
- **Denial of Service (DoS)**: Malicious actors can inject a large number of invalid transactions, causing the system to repeatedly attempt invalid unpacking operations. This will consume CPU resources and severely degrade the performance of the getTransactionByHashPending function, potentially making the system slow or completely unresponsive to legitimate transaction queries.

### Second Function Affected by the Faulty Slice:

The getAccountNonce function is designed to query and return the transaction nonce for an account. It handles two scenarios:

1. Retrieves the nonce for confirmed transactions.
2. If the pending flag is true, it also includes pending transactions to calculate the final nonce and ensure the account’s transaction sequence is intact.

The function receives the incorrect slice returned by PendingTransactions and iterates over it. Due to the slice containing zero values, this causes several detrimental effects.

https://github.com/code-423n4/2024-11-nibiru/blob/main/eth/rpc/backend/utils.go#L87


### Impact

The specific consequences are as follows:

a. **Iteration over Invalid Transactions**:

When PendingTransactions returns invalid transaction data (such as zero values or uninitialized transactions), iterating over it may result in:

- **Empty Transaction Objects**: This can trigger (*tx).GetMsgs() to cause a nil pointer exception, crashing the program or leading to logic errors.
- **Incorrect Data Parsing**: Failure to parse transaction data (such as GetSender method failing) may disrupt the normal flow.

b. **Handling of Non-Ethereum Transactions**:

If the transaction data is not an Ethereum transaction, the code skips over these transactions.

- **Malformed Format**: Invalid or incomplete transactions will continue to be skipped, causing the nonce to fail to update correctly.

c. **Incorrect Nonce Calculation**:

Nonce calculation depends on valid pending transactions:

- **Invalid Sender Addresses**: If the GetSender method fails to identify the correct sender address, it will prevent proper incrementing of the nonce.

### Fix Recommendations

Instead of using append to add elements at the end of the slice, you should assign values directly to specific positions in the slice.

```go
result := make([]*sdk.Tx, len(res.Txs))
for i, txBz := range res.Txs {
    tx, err := b.clientCtx.TxConfig.TxDecoder()(txBz)
    if err != nil {
        return nil, err
    }
    result[i] = &tx // Directly assign to the specified slice index
}
```

This approach ensures that elements are added to the slice starting from the appropriate index and avoids unnecessary slice reallocation.

The same approach should be applied to the other functions affected by this issue.
