# Vulnerability details

The AllTxLogsFromEvents function is designed to extract transaction logs from a series of events and return a two-dimensional slice containing all the transaction logs.

It first creates a slice with a length of 0 and a capacity of 4, and then uses append to add parsed logs to the allLogs slice.

[Source](https://github.com/code-423n4/2024-11-nibiru/blob/main/eth/rpc/backend/utils.go#L226)

```go
// AllTxLogsFromEvents parses all ethereum logs from cosmos events
func AllTxLogsFromEvents(events []abci.Event) ([][]*gethcore.Log, error) {
    allLogs := make([][]*gethcore.Log, 0, 4) // <-------
    for _, event := range events {
        if event.Type != proto.MessageName(new(evm.EventTxLog)) {
            continue
        }

        logs, err := ParseTxLogsFromEvent(event)
        if err != nil {
            return nil, err
        }

        allLogs = append(allLogs, logs) // <-------
    }
    return allLogs, nil
}
```

However, this use of append is incorrect because it leads to unused slots (0-3) in the allLogs slice, with those positions storing zeros. When traversing allLogs later, this will result in various issues.

Additionally, the GetLogsFromBlockResults function accepts the incorrect slice returned by AllTxLogsFromEvents. This function also misuses append and returns a faulty slice, leading to errors in the blockLogs slice, which will also contain unused memory.

[Source](https://github.com/code-423n4/2024-11-nibiru/blob/main/eth/rpc/backend/utils.go#L281)

```go
// GetLogsFromBlockResults returns the list of event logs from the tendermint block result response
func GetLogsFromBlockResults(blockRes *tmrpctypes.ResultBlockResults) ([][]*gethcore.Log, error) {
    blockLogs := [][]*gethcore.Log{} // <-------
    for _, txResult := range blockRes.TxsResults {
        logs, err := AllTxLogsFromEvents(txResult.Events)
        if err != nil {
            return nil, err
        }

        blockLogs = append(blockLogs, logs...) // <-------
    }
    return blockLogs, nil
}
```

Following the call chain, it can be seen that the blockLogs function also has an incorrect use of append and accepts the erroneous slice returned by GetLogsFromBlockResults. This leads to incorrect logs being returned by the function.

[Source](https://github.com/code-423n4/2024-11-nibiru/blob/main/eth/rpc/rpcapi/filters.go#L202)

```go
// blockLogs returns the logs matching the filter criteria within a single block.
func (f *Filter) blockLogs(blockRes *tmrpctypes.ResultBlockResults, bloom gethcore.Bloom) ([]*gethcore.Log, error) {
    if !bloomFilter(bloom, f.criteria.Addresses, f.criteria.Topics) {
        return []*gethcore.Log{}, nil
    }

    logsList, err := rpcbackend.GetLogsFromBlockResults(blockRes) // <-------
    if err != nil {
        return []*gethcore.Log{}, errors.Wrapf(err, "failed to fetch logs block number %d", blockRes.Height)
    }

    unfiltered := make([]*gethcore.Log, 0) // <-------
    for _, logs := range logsList {
        unfiltered = append(unfiltered, logs...) // <-------
    }

    logs := FilterLogs(unfiltered, nil, nil, f.criteria.Addresses, f.criteria.Topics)
    if len(logs) == 0 {
        return []*gethcore.Log{}, nil
    }

    return logs, nil
}
```

Because these three functions are interdependent and all misuse append, while also returning faulty slices, I am submitting a single report to address these issues across all three functions.

### Impact

- **Memory Waste**: The use of append triggers frequent slice reallocations, leading to unused memory spaces being allocated, particularly when processing large datasets. This results in significant memory waste.
- **Performance Degradation**: Repeated append operations may cause multiple reallocations and data copying, which can degrade performance, especially when dealing with large datasets.
- **Denial of Service (DoS)**: Attackers could inject a large number of fake event data, forcing the system to perform frequent reallocations and consume excessive memory and computational resources. This could slow down or crash the system, leading to a DoS. Malicious data injection could exhaust the system's resources, affecting the normal operation of the service and potentially triggering a DoS attack.
- **Replay Attacks**: Memory reallocations may cause data processing errors or loss of data in memory, leading to invalid or incorrect logs in allLogs. This could affect subsequent transaction logs, potentially allowing replay attacks to succeed and compromising the system's security.

### Suggested Fix

The size of the slice should first be estimated based on the number of relevant events, and the slice should be preallocated accordingly.

Then, instead of using append, logs should be assigned directly to the slice using the appropriate index.

```go
// First, estimate the number of events that meet the criteria
estimatedSize := 0
for _, event := range events {
    if event.Type == proto.MessageName(new(evm.EventTxLog)) {
        estimatedSize++
    }
}

// Initialize allLogs based on the estimated size
allLogs := make([][]*gethcore.Log, estimatedSize)

index := 0
allLogs[index] = logs
index++
```

The same approach should be applied to the other functions to avoid unnecessary memory allocation and ensure optimal performance.
