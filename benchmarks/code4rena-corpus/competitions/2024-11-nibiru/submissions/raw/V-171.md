# Vulnerability details


## Proof of Concept

Take a look at [x/evm/keeper/msg_server.go#L208-L399](https://github.com/code-423n4/2024-11-nibiru/blob/8ed91a036f664b421182e183f19f6cef1a4e28ea/x/evm/keeper/msg_server.go#L208-L399):

```go
// If msg comes from user, we apply refundQuotient capping the refund to 20% of used gas
// If msg is internal (funtoken), we refund 100%
refundQuotient := params.RefundQuotientEIP3529
if fullRefundLeftoverGas {
    refundQuotient = 1 // 100% refund
}
```

The EVM module allows internal transactions (like funtokens) to bypass EIP-3529's gas refund cap of 20%, permitting 100% gas refunds for these transactions. This violates EIP-3529 which explicitly requires all gas refunds to be capped at 1/5 (20%) of gas used, with no exceptions for internal transactions or special cases.

See [EIP-3529](https://eips.ethereum.org/EIPS/eip-3529):

> ...
> The capping of refunds to 1/5 of gas expended means that this refund can only be used to increase the amount of storage write operations needed to process a block by at most 25%, limiting the ability to use this mechanic for storage-write-focused denial-of-service attacks.

## Impact

From the readMe and code snippets protocol would like to be in compliance with EIP-3529 and also other EVM like chains, however this is not achieved and broken, which then means more refunds (_leakage of funds_) considering we now refund 100% instead of 20%.

1. **Gas Token Exploitation**: Internal transactions could be used to create new forms of gas tokens, which EIP-3529 was specifically designed to prevent.

2. **Block Size Variance**: The 100% refund allowance for internal transactions means blocks could experience high variance in gas usage that EIP-3529 aimed to fix.

3. **DoS Vector**: Could enable storage-write-focused denial-of-service attacks through internal transactions.

4. **Protocol Deviation**: Implementation deviates from Ethereum's specification, potentially leading to unexpected behaviors.

## Recommended Mitigation Steps

1. Remove the special case for internal transactions and always apply the EIP-3529 refund quotient:

```go
// Always use EIP-3529 refund quotient
refundQuotient := params.RefundQuotientEIP3529
// Remove the fullRefundLeftoverGas special case
```

2. If internal transactions require special handling, consider alternative mechanisms that don't bypass core EIP-3529 security measures.

3. Add explicit documentation if any deviations from EIP specifications are intentional, explaining the rationale and potential risks.

## QA-14 Missing London Fork Validation Could Lead to Incorrect Fee Processing

### Proof of Concept

In Nibiru's `app/evmante/evmante_validate_basic.go`, the transaction validation lacks proper London hardfork checks:

```go
// Nibiru's implementation
baseFeeMicronibi := vbd.evmKeeper.BaseFeeMicronibiPerGas(ctx)

// Only validates dynamic fee transactions
if baseFeeMicronibi == nil && txData.TxType() == gethcore.DynamicFeeTxType {
    return ctx, errorsmod.Wrap(
        gethcore.ErrTxTypeNotSupported,
        "dynamic fee tx not supported",
    )
}
```

Compare this with Ethermint's implementation which properly validates London hardfork conditions:

```go
// Ethermint's implementation
params := vbd.evmKeeper.GetParams(ctx)
chainID := vbd.evmKeeper.ChainID()
ethCfg := params.ChainConfig.EthereumConfig(chainID)

// Validates London hardfork specific rules
if evmtypes.IsLondon(ethCfg, ctx.BlockHeight()) {
    if baseFee == nil {
        return ctx, sdkerrors.Wrap(
            evmtypes.ErrInvalidBaseFee,
            "base fee is supported but evm block context value is nil",
        )
    }
    if coreMsg.GasFeeCap().Cmp(baseFee) < 0 {
        return ctx, sdkerrors.Wrapf(
            sdkerrors.ErrInsufficientFee,
            "max fee per gas less than block base fee (%s < %s)",
            coreMsg.GasFeeCap(), baseFee,
        )
    }
}
```

The key differences are:

1. Ethermint explicitly checks for London hardfork activation
2. Validates base fee existence when London is active
3. Ensures gas fee cap meets minimum requirements
4. Properly handles both legacy and EIP-1559 transactions

### Impact

QA considering this could as well be intended by NIbiru, however, the lack of proper London hardfork validation could lead to:

1. Acceptance of invalid transactions that should be rejected under London rules
2. Incorrect fee calculations for EIP-1559 transactions
3. Inconsistent transaction processing between Nibiru and Ethereum

### Recommended Mitigation Steps

Add proper London hardfork validation:

```go
params := vbd.evmKeeper.GetParams(ctx)
ethCfg := params.ChainConfig.EthereumConfig(chainID)
baseFee := vbd.evmKeeper.BaseFeeMicronibiPerGas(ctx)

if evmtypes.IsLondon(ethCfg, ctx.BlockHeight()) {
    if baseFee == nil {
        return ctx, errorsmod.Wrap(
            evmtypes.ErrInvalidBaseFee,
            "base fee is supported but evm block context value is nil",
        )
    }
    // Add EIP-1559 fee validation
    if txData.GasFeeCap().Cmp(baseFee) < 0 {
        return ctx, errorsmod.Wrapf(
            sdkerrors.ErrInsufficientFee,
            "max fee per gas less than block base fee (%s < %s)",
            txData.GasFeeCap(), baseFee,
        )
    }
}
```

## QA-1 M Missing Coin Validation in Fee Handling

### Proof of Concept

In `app/evmante/evmante_validate_basic.go`, fees are constructed without proper validation:

```go
txFee = txFee.Add(
    sdk.Coin{
        Denom:  evm.EVMBankDenom,
        Amount: sdkmath.NewIntFromBigInt(txData.Fee()),
    },
)
```

The Cosmos SDK provides `NewCoin` which includes important validations:

```go
func NewCoin(denom string, amount Int) Coin {
    coin := Coin{
        Denom:  denom,
        Amount: amount,
    }

    if err := coin.Validate(); err != nil {
        panic(err)
    }

    return coin
}

func (coin Coin) Validate() error {
    if err := ValidateDenom(denom); err != nil {
        return err
    }

    if coin.Amount.IsNegative() {
        return fmt.Errorf("negative coin amount: %v", coin.Amount)
    }

    return nil
}
```

These validations ensure:

1. Valid denomination format
2. Non-negative amounts
3. Proper coin structure

### Impact

Low. The direct construction of `sdk.Coin` without proper validation could lead to invalid fee calculations and potential panics in production.

### Recommended Mitigation Steps

Replace direct coin construction with `sdk.NewCoin`:

```go
txFee = txFee.Add(sdk.NewCoin(evm.EVMBankDenom, sdkmath.NewIntFromBigInt(txData.Fee())))
```

This ensures proper validation of:

- Denomination format
- Amount constraints
- Overall coin structure integrity

To put this in retrospect, this is also the exact approach being used by the inspired Ethermint's implementation, see [https://github.com/kshlsa/ethermint/blob/v0.15.0/app/ante/eth.go#L435](https://github.com/kshlsa/ethermint/blob/v0.15.0/app/ante/eth.go#L435).
