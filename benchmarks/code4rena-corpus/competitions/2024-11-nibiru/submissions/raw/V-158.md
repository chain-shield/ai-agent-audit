# Vulnerability details

## Finding description and impact
While the creation of bank tokens is permissionless (for any ERC20 token that exists on Nibiru's EVM) it opens up a vulnerability. The lack of any access control or whitelist, allows for malicious users to deploy a single ERC20 contract with minimal code in it as an implementation and a ton of minimal proxies for it. From then on, the attackers can create a canonical bank token for each of the proxies via `CreateFunToken()` and send 1 wei worth of ERC20 to, again, a ton of SDK accounts (`x/bank` module's `SendMulti()` rpc method can be used for gas efficiency).

Now the next time the supply variant of the `x/bank` module is to be ran in the `x/crisis` module's `EndBlocker`, it'll start looping over all accounts and all balances that we've just polluted the application's state with.

This is an attack vector that [Cosmos's security book](https://docs.cosmos.network/main/build/building-apps/security-part-1#poorly-chosen-looprecursion-exit-condition) warns about:

> *Poorly Chosen Loop/Recursion Exit Condition*
>
> This is a consideration that seems trivial but comes up much more frequently than one might expect. If a loop in unmetered code is never exited or a recursion base case is never hit, it might lead to an expensive chain halt.

## Proof of Concept
1. Deploy a minimal ERC20 token implementation.
2. Deploy a thousand minimal proxies using that implementation.
3. Create a bank coin (FunToken) for every proxy address. Now we have a thousand new bank coins.
4. Convert a fixed amount of each ERC20 token proxy to its bank coin representation.
5. Disperse the now converted bank coins to a hundred or a thousand new SDK addresses (the `x/bank` module will create a new account for each of these addresses automagically, so we don't need them to be already existing)
6. Next time the `x/bank` module's supply invariant is running, it'll run out of time, causing the chain to become to a halt.
## Recommended mitigation steps
This one is though one to fix as the only sensible solutions I can think of include some sort of a limit or a whitelist. Wrapping the supply invariant in a context with a custom gas meter or only enforcing the invariant for `unibi` is probably worth giving a try.
