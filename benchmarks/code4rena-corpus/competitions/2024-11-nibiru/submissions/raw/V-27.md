# Vulnerability details

## Finding description and impact
In the function `BlockNumber()`, the block height is incorrectly compared against `math.MaxInt64` instead of the intended `math.MaxUint64`. This oversight causes the function to incorrectly reject valid block heights that are larger than the maximum value of a signed 64-bit integer (`9223372036854775807`), but still within the valid range for an unsigned 64-bit integer (`18446744073709551615`).

## Proof of Concept
[`BlockNumber()`](https://github.com/code-423n4/2024-11-nibiru/blob/8ed91a036f664b421182e183f19f6cef1a4e28ea/eth/rpc/backend/blocks.go#L50-L52):
```solidity
    height, err := strconv.ParseUint(blockHeightHeader[0], 10, 64) // @audit-info height retrieved
	---SNIP---

>>	if height > math.MaxInt64 { // @audit-info Incorrect validation
		return 0, fmt.Errorf("block height %d is greater than max uint64", height)
	}

    return hexutil.Uint64(height), nil
```
The `block height` may be valid for a `uint64` but rejected due to this comparison. A height of `18446744073709551615` would trigger this incorrect rejection since it's greater than `9223372036854775807` (the maximum for `math.MaxInt64`), though it's still valid for `uint64`.

Furthermore, notice that the error message thrown as well indicates that `uint64` has been exceeded which is not in line with the implementation.

## Recommended mitigation steps
Update the validation to check against `math.MaxUint64` instead of `math.MaxInt64`:
```diff
    height, err := strconv.ParseUint(blockHeightHeader[0], 10, 64)
	---SNIP---

-   if height > math.MaxInt64 {
+   if height > math.MaxUint64 { // @audit Correct validation
	return 0, fmt.Errorf("block height %d is greater than max uint64", height)
    }
```
