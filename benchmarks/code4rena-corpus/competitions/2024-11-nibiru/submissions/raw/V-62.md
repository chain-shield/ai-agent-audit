# Vulnerability details

## Finding description and impact

Currently, the gas limits for several operations are hardcoded in the `erc20` file. This can create a situation where the future calls / deployments will fail due to the opcodes cost changes.

## Proof of Concept

Take a look at the current implementation:

https://github.com/code-423n4/2024-11-nibiru/blob/main/x/evm/keeper/erc20.go#L17-27
```
const (
	// Erc20GasLimitDeploy only used internally when deploying ERC20Minter.
	// Deployment requires ~1_600_000 gas
	Erc20GasLimitDeploy uint64 = 2_000_000
	// Erc20GasLimitQuery used only for querying name, symbol and decimals
	// Cannot be heavy. Only if the contract is malicious.
	Erc20GasLimitQuery uint64 = 100_000
	// Erc20GasLimitExecute used for transfer, mint and burn.
	// All must not exceed 200_000
	Erc20GasLimitExecute uint64 = 200_000
)
```

Such imposed hardcoded limitations can create a situation where the gas limit for, for instance, deployment, would not be simply enough (as currently it's `1_600_000 gas` as stated in the comment but can easily become more than `2_000_000` if there was some new EIP suggested to the network). There are currently a huge number of different Ethereum proposals that introduce some changes to the opcodes' costs.

## Recommended mitigation steps

Don't use hardcoded gas limits.
