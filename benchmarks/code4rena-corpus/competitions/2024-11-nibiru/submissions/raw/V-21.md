# Vulnerability details

## Finding description and impact

The Nibiru EVM implementation maintains a restriction that transaction senders must be Externally Owned Accounts (EOAs) and not contracts. This is enforced in `evmante_verify_eth_acc.go` via the `IsContract` check. However, there is an inconsistency in how contract code status is tracked in the state DB.

When a new contract is created through `msg_server.go`, the code hash is never properly set in the state DB via `SetCode`. This means that newly created contract accounts will appear as EOAs when checked via `IsContract`, allowing them to bypass the EOA-only transaction restriction.

The only place where contract code is properly set is during genesis initialization in `genesis.go`, making the `IsContract` check effectively useless for any contracts created after genesis.

## Proof of Concept

The key pieces of code that demonstrate this issue are:

1. Contract creation in msg_server.go ([line 324](https://github.com/code-423n4/2024-11-nibiru/blob/84054a4f00fdfefaa8e5849c53eb66851a762319/x/evm/keeper/msg_server.go#L324)):
```go
if contractCreation {
    // take over the nonce management from evm:
    // - reset sender's nonce to msg.Nonce() before calling evm.
    // - increase sender's nonce by one no matter the result.
    stateDB.SetNonce(sender.Address(), msg.Nonce())
    ret, _, leftoverGas, vmErr = evmObj.Create(
        sender,
        msg.Data(),
        leftoverGas,
        msgWei,
    )
    stateDB.SetNonce(sender.Address(), msg.Nonce()+1)
}
```
Note that there is no `SetCode` call after contract creation.

2. The EOA check in evmante_verify_eth_acc.go ([line 70](https://github.com/code-423n4/2024-11-nibiru/blob/84054a4f00fdfefaa8e5849c53eb66851a762319/app/evmante/evmante_verify_eth_acc.go#L70)):
```go
} else if acct.IsContract() {
    return ctx, errors.Wrapf(sdkerrors.ErrInvalidType,
        "the sender is not EOA: address %s, codeHash <%s>", fromAddr, acct.CodeHash)
}
```

3. Genesis code setting in genesis.go ([line 65](https://github.com/code-423n4/2024-11-nibiru/blob/84054a4f00fdfefaa8e5849c53eb66851a762319/x/evm/evmmodule/genesis.go#L65)):
```go
k.SetCode(ctx, codeHash.Bytes(), code)
```

This issue affects both regular CREATE operations and CREATE2, since neither will properly record the contract code status in the state DB. The fix is easier for the ones that are created via CREATE from an EOA because there is special code handling these.

## Recommended mitigation steps

The code needs to be properly set in the state DB when creating new contracts. As a first step, a `SetCode` call after successful contract creation in `msg_server.go` can be added:
```go
if contractCreation {
    stateDB.SetNonce(sender.Address(), msg.Nonce())
    ret, _, leftoverGas, vmErr = evmObj.Create(
        sender,
        msg.Data(),
        leftoverGas,
        msgWei,
    )
    if vmErr == nil {
        // Add SetCode call here
        codeHash := crypto.Keccak256Hash(ret)
        k.SetCode(ctx, codeHash.Bytes(), ret)
    }
    stateDB.SetNonce(sender.Address(), msg.Nonce()+1)
}
```

However, note that contracts that are created from another contract (i.e. during running a transaction) also need to be tracked to get the full picture.
