# Vulnerability details


### Proof of Concept

In `app/evmante/evmante_validate_basic.go`, fees are constructed without proper validation:

https://github.com/code-423n4/2024-11-nibiru/blob/8ed91a036f664b421182e183f19f6cef1a4e28ea/app/evmante/evmante_validate_basic.go#L125-L130

```go
		txFee = txFee.Add(
			sdk.Coin{
				Denom:  evm.EVMBankDenom,
				Amount: sdkmath.NewIntFromBigInt(txData.Fee()),
			},
		)
```

Note that the `txfee` is `sdk.Coins` and not because it is a list of coins, see:
https://github.com/code-423n4/2024-11-nibiru/blob/8ed91a036f664b421182e183f19f6cef1a4e28ea/app/evmante/evmante_validate_basic.go#L89

```go
	txFee := sdk.Coins{}
```

Now querying `Add()` with a `coin` on this list is crucial and needs to be carefully done, see the cosmos sdk documentation of `Add`:

```go
// Add adds two sets of coins.
//
// e.g.
// {2A} + {A, 2B} = {3A, 2B}
// {2A} + {0B} = {2A}
//
// NOTE: Add operates under the invariant that coins are sorted by
// denominations.
//
// CONTRACT: Add will never return Coins where one Coin has a non-positive
// amount. In otherwords, IsValid will always return true.
// The function panics if `coins` or  `coinsB` are not sorted (ascending).
func (coins Coins) Add(coinsB ...Coin) Coins {
	return coins.safeAdd(coinsB)
}

```

Now we can see that this function would never return coins if one has a non-positive amount, which is why the Cosmos SDK provides `NewCoin` which includes important validations that ensures that the amount is not negative and that the denomination is valid which Ethermint use when adding the fee to the transaction _(which Nibiru's implementation is based on)_, see [https://github.com/kshlsa/ethermint/blob/v0.15.0/app/ante/eth.go#L435](https://github.com/kshlsa/ethermint/blob/v0.15.0/app/ante/eth.go#L435):

Below is the `NewCoin` function from the Cosmos SDK:

```go
// Coin

// NewCoin returns a new coin with a denomination and amount. It will panic if
// the amount is negative or if the denomination is invalid.
func NewCoin(denom string, amount Int) Coin {
    coin := Coin{
        Denom:  denom,
        Amount: amount,
    }

    if err := coin.Validate(); err != nil {
        panic(err)
    }

    return coin
}

func (coin Coin) Validate() error {
    if err := ValidateDenom(denom); err != nil {
        return err
    }

    if coin.Amount.IsNegative() {
        return fmt.Errorf("negative coin amount: %v", coin.Amount)
    }

    return nil
}
```

These validations ensure that the following conditions are met:

1. Valid denomination format
2. Non-negative amounts
3. Proper coin structure

### Impact

Borderline, considering the direct construction of `sdk.Coin` without proper validation could lead to not only invalid fee calculations and potential panics in production, but also the fact that the `Add` function would never return coins i.e when we have the amount to be non-negative for one of the coins, see documentation from `Add()` above.

### Recommended Mitigation Steps

Replace direct coin construction with `sdk.NewCoin`:

```diff
-		txFee = txFee.Add(
-			sdk.Coin{
-				Denom:  evm.EVMBankDenom,
-				Amount: sdkmath.NewIntFromBigInt(txData.Fee()),
-			},
-		)
+
+   txFee = txFee.Add(sdk.NewCoin(evm.EVMBankDenom, sdkmath.NewIntFromBigInt(txData.Fee())))
```

This ensures proper validation of:

- Denomination format
- Amount constraints
- Overall coin structure integrity

To put this in retrospect, this is also the exact approach being used by the inspired Ethermint's implementation, see [https://github.com/kshlsa/ethermint/blob/v0.15.0/app/ante/eth.go#L435](https://github.com/kshlsa/ethermint/blob/v0.15.0/app/ante/eth.go#L435).
