# Vulnerability details

The primary purpose of the `Accounts` function is to return all the available account addresses for the current node.

It first initializes an empty address slice using `make`, and then, in a `for` loop, extracts public keys and appends them to the address slice using `append`.

**Link to the code**: [node_info.go](https://github.com/code-423n4/2024-11-nibiru/blob/main/eth/rpc/backend/node_info.go#L29)

```go
// Accounts returns the list of accounts available to this node.
func (b *Backend) Accounts() ([]gethcommon.Address, error) {
    addresses := make([]gethcommon.Address, 0) // <--------
    // return [] instead of nil if empty

    ...

    for _, info := range infos {
        pubKey, err := info.GetPubKey()
        if err != nil {
            return nil, err
        }
        addressBytes := pubKey.Address().Bytes()
        addresses = append(addresses, // <-------
            gethcommon.BytesToAddress(addressBytes))
    }

    return addresses, nil
}
```

However, this approach is incorrect. While `make` initializes an empty slice, using `append` to add elements in this way is problematic for the following reasons:

### Issues with `append` on an Empty Slice

The capacity of a slice in Go typically doubles as elements are appended:

- When the slice size is 0, after `append`, the slice grows to a size of 1.
- When the slice size is 1, after `append`, the slice grows to a size of 2.
- When the slice size is 2, after `append`, the slice grows to a size of 4.
- When the slice size is 4, after `append`, the slice grows to a size of 8.

At this point, the memory space from index 4 to 7 remains unused, containing zeros. This leads to several issues:

- **Memory Waste**: Every time `append` is called, the slice must be reallocated and expanded, often resulting in unused memory slots filled with zeros.
- **Performance Loss**: As `append` is repeatedly called, especially with a large number of accounts, the system will experience significant performance degradation due to frequent reallocations and data copying. This becomes particularly problematic when handling thousands or more accounts.
- **Denial of Service (DoS)**: While `append` itself does not insert invalid data, a malicious user can potentially cause a DoS by returning an exceptionally large account list from `Keyring.List()`. This could force the system to handle an excessive amount of address data, degrading performance or even causing the service to become unavailable. Attackers could inject large amounts of fake account data, causing the process of generating and returning the account list to take an unreasonable amount of time.
- **Replay Attacks**: Improper handling of account retrieval could lead to nonce calculation errors, increasing the risk of replay attacks.

Additionally, this incorrect `append` usage also affects the function's output, which is used in `eth/rpc/rpcapi/eth_api.go`:

**Link to the code**: [eth_api.go](https://github.com/code-423n4/2024-11-nibiru/blob/main/eth/rpc/rpcapi/eth_api.go#L236)

```go
// Accounts returns the list of accounts available to this node.
func (e *EthAPI) Accounts() ([]common.Address, error) {
    e.logger.Debug("eth_accounts")
    return e.backend.Accounts()
}
```

This can lead to data processing issues, as the returned slice may contain zero-value elements, which could be misprocessed and affect subsequent logic.

### Recommended Fix

First, the size of `infos` should be calculated, and the slice should be preallocated accordingly:

```go
addresses := make([]gethcommon.Address, 0, len(infos))
```

Then, instead of using `append`, public keys should be assigned directly to the slice by index:

```go
index := 0
addresses[index] = gethcommon.BytesToAddress(addressBytes)
index++
```
