Issue however is that there is an enforcal during actions like transfers that require the `success` value to be `true` to be executed, see:

https://github.com/code-423n4/2024-11-nibiru/blob/8ed91a036f664b421182e183f19f6cef1a4e28ea/x/evm/keeper/erc20.go#L76-L122

```go
func (e erc20Calls) Transfer(
	contract, from, to gethcommon.Address, amount *big.Int,
	ctx sdk.Context,
) (balanceIncrease *big.Int, resp *evm.MsgEthereumTxResponse, err error) {
	recipientBalanceBefore, err := e.BalanceOf(contract, to, ctx)
	if err != nil {
		return balanceIncrease, nil, errors.Wrap(err, "failed to retrieve recipient balance")
	}

	resp, err = e.CallContract(ctx, e.ABI, from, &contract, true, Erc20GasLimitExecute, "transfer", to, amount)
	if err != nil {
		return balanceIncrease, nil, err
	}

	var erc20Bool ERC20Bool
	err = e.ABI.UnpackIntoInterface(&erc20Bool, "transfer", resp.Ret)
	if err != nil {
		return balanceIncrease, nil, err
	}

	// Handle the case of success=false: https://github.com/NibiruChain/nibiru/issues/2080
	//@audit trying to use the success value of transfers here would fail for tokens like `USDT`.
	success := erc20Bool.Value
	if !success {
		return balanceIncrease, nil, fmt.Errorf("transfer executed but returned success=false")
	}

	recipientBalanceAfter, err := e.BalanceOf(contract, to, ctx)
	if err != nil {
		return balanceIncrease, nil, errors.Wrap(err, "failed to retrieve recipient balance")
	}

	balanceIncrease = new(big.Int).Sub(recipientBalanceAfter, recipientBalanceBefore)

	// For flexibility with fee on transfer tokens and other types of deductions,
	// we cannot assume that the amount received by the recipient is equal to
	// the call "amount". Instead, verify that the recipient got tokens and
	// return the amount.
	if balanceIncrease.Sign() <= 0 {
		return balanceIncrease, nil, fmt.Errorf(
			"amount of ERC20 tokens received MUST be positive: the balance of recipient %s would've changed by %v for token %s",
			to.Hex(), balanceIncrease.String(), contract.Hex(),
		)
	}

	return balanceIncrease, resp, err
}
```

However tokens intended to be supported by Nibiru include does that do not return boolean values like USDT which would then have the methodology broken [here](https://github.com/code-423n4/2024-11-nibiru/blob/8ed91a036f664b421182e183f19f6cef1a4e28ea/x/evm/keeper/erc20.go#L96-L102).

Also the intended transfer method being used as hinted via solidity in the `erc20.go`:
https://github.com/code-423n4/2024-11-nibiru/blob/8ed91a036f664b421182e183f19f6cef1a4e28ea/x/evm/keeper/erc20.go#L66-L75

```go
/*
Transfer implements "ERC20.transfer"

	/// @dev Moves `amount` tokens from the caller's account to `to`.
	/// Returns a boolean value indicating whether the operation succeeded.
	/// Emits a {Transfer} event.
	function transfer(address to, uint256 amount) external returns (bool);
*/
```

But see `L199, L340 & L344` from `USDT`'s contract https://etherscan.io/token/0xdac17f958d2ee523a2206206994597c13d831ec7#code

We can see that the definition of the classic ERC20 functions do not have a bool return value

```rust
    function approve(address _spender, uint _value) public
(...snip)
    function transfer(address _to, uint _value) public
(...snip)
    function transferFrom(address _from, address _to, uint _value)
```

This will then lead to different opcodes compiled by the compiler when talking about classic solidity implementations since there would be a need to check the length of the return data, `usdt.approve/transfer/transferFrom()` requires the length of the return data to be 0, while `ERC20.approve/transfer/transferFrom()` requires the length of the return data to be 1, therefore, the **tx always reverts**.

## Impact

Broken functionality considering the USDT token and its likes are expected to be supported, but transfers cannot be processed for these tokens.

_That is we can't use the sendToBank method for these tokens, considering in funToken.go we have the following:_

```go
	// Caller transfers ERC20 to the EVM account
	transferTo := evm.EVM_MODULE_ADDRESS

```

## Recommended Mitigation Steps

Consider first checking if the token supports a return value first before trying to decode the success of the transfer using the return value or if the token does not return a boolean value but the tx does not revert then assume that the transfer was successful.

Alternatively, outrightly state that these type of tokens are not supported.
