# Vulnerability details

## Impact
The `decodeWellData` function contains a logical error that prevents the second token's decimals from being properly set to the default value of 18 when it's 0. This leads to incorrect decimal handling for the second token, potentially causing miscalculations in other parts of the protocol that rely on accurate decimal information. 


This bug leads to incorrect handling of token decimals, particularly when the second token in the pair has 0 decimals. Instead of being set to the default value of 18, it will retain its 0 value. Lets look at the affected functions:

1. `getScaledReserves`:
   This function directly uses the decimals returned by `decodeWellData` to scale the reserves. If `decimal1` is incorrectly 0, it will result in:
   ```solidity
   scaledReserves[1] = reserves[1] * 10 ** (18 - 0) = reserves[1] * 1e18
   ```
   This would massively inflate the scaled reserve for the second token, potentially by a factor of 1e18.

2. `calcLpTokenSupply`:
   Uses `getScaledReserves`, so it would work with incorrectly scaled reserves. This will lead to overestimation of LP token supply and incorrect liquidity representation.
  

3. `calcReserve`:
   Also uses `getScaledReserves`. The bug could cause:
   - Incorrect reserve calculations
   - Potential underflow when scaling back to original precision

4. `calcRate`:
   Relies on `getScaledReserves` and `calcLpTokenSupply`. The bug would result in:
   - Incorrect rate calculations

## Proof of Concept
Take a look at the `decodeWellData` function: https://github.com/code-423n4/2024-07-basin/blob/7d5aacbb144d0ba0bc358dfde6e0cc913d25310e/src/functions/Stable2.sol#L310-L327

```solidity
function decodeWellData(bytes memory data) public view virtual returns (uint256[] memory decimals) {
        (uint256 decimal0, uint256 decimal1) = abi.decode(data, (uint256, uint256));

        // if well data returns 0, assume 18 decimals.
        if (decimal0 == 0) {
            decimal0 = 18;
        }
        if (decimal0 == 0) {
            decimal1 = 18;
        }
        if (decimal0 > 18 || decimal1 > 18) revert InvalidTokenDecimals();

        decimals = new uint256[](2);
        decimals[0] = decimal0;
        decimals[1] = decimal1;
    }

```

The second condition incorrectly checks `decimal0` again instead of `decimal1`. As a result:
1. If `decimal0` is 0, it's correctly set to 18.
2. The second condition will always be false because `decimal0` is now 18.
3. `decimal1` is never set to 18 even if it's 0.

This means that if the second token has 0 decimals in the input data, it will be incorrectly processed as having 0 decimals instead of the intended default of 18.

## Recommended Mitigation Steps
The fix is straightforward. Change the second condition to check `decimal1` instead of `decimal0`:

```diff
function decodeWellData(bytes memory data) public view virtual returns (uint256[] memory decimals) {
    (uint256 decimal0, uint256 decimal1) = abi.decode(data, (uint256, uint256));

    // if well data returns 0, assume 18 decimals.
    if (decimal0 == 0) {
        decimal0 = 18;
    }
-   if (decimal0 == 0) {
+   if (decimal1 == 0) {
        decimal1 = 18;
    }
    if (decimal0 > 18 || decimal1 > 18) revert InvalidTokenDecimals();

    decimals = new uint256[](2);
    decimals[0] = decimal0;
    decimals[1] = decimal1;
}
```
