# Vulnerability details

## Impact
On the call [`decodeWellData()`](https://github.com/code-423n4/2024-07-basin/blob/7d5aacbb144d0ba0bc358dfde6e0cc913d25310e/src/functions/Stable2.sol#L310C1-L325C6), the code line checks the wrong condition before it sets up the decimal for `token1`, allowing for a incorret decimal to be used for `token1`, this i'll affect the following critical functions in turn since the rely on the `decodeWellData()` 
- `calcReserveAtRatioLiquidity()`.
- `calcReserveAtRatioSwap()`.
- `calcRate()`
- `calcReserve()`.
- `calcLpTokenSupply()`.

These functions are view but the are used in the core protocol function when making calculation for either swaps, adding of liquidity and many more in `wells.sol` if the wrong decimal for a token is used in the process the protocol can be broken, or exploited.

> Please check code snippet for detailed info.

```solidity
324:        decimals[1] = decimal1;

```
The issue stems from checking the decimal of `token0` in `Line-317` before setting the decimal to `18` in the next line, supposing the `token1` is of a different decimal due to checking `token0` if `token0` is of `0` is explicitly sets `18` as the decimal for the two tokens even when `token1` is of a different decimal.

Example of Issue.
- The two token data to be decoded is ETh and USDC.
- Eth is of zero decimal as per the `data` and USDC is of 6 decimal as per the data.
- On the call to `decodeWellData()` the decimal of USDC is made to be 18 instead of left to be 6, leading to incorrect scaling and calculations in underlying calculations.
- Supposing a swap, the user will get more USDC token than they're supposed to recieve in this scenario.
