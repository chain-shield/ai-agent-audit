# Vulnerability details

## Impact

The `WellUpgradeable` contract inherits from the `Well` contract. Currently, `Well` does not use any storage variables. However, the absence of storage gaps in `Well` poses a risk if storage variables are added in the future. This could disrupt the storage layout of `WellUpgradeable`, potentially leading to data corruption and security vulnerabilities.

## Proof of Concept

The OpenZeppelin [documentation](https://docs.openzeppelin.com/upgrades-plugins/1.x/writing-upgradeable#storage-gaps) highlights the importance of including storage gaps in upgradeable contracts to maintain compatibility and avoid storage conflicts. While `Well` is not currently upgradeable, adding storage gaps can still be beneficial.

### Example of Potential Issue

1. **Current State**:
   - `Well` has no storage variables.
   - `WellUpgradeable` inherits from `Well`.

2. **Future Change**:
   - If `Well` introduces a storage variable later without gaps, it could overwrite data in `WellUpgradeable`. Additionally, if users of Basin create their own upgradeable Well implementations with storage variables, this could lead to unexpected behavior, stuck funds, and other unintended security vulnerabilities. For this reason, it is recommended to add storage gaps even if a contract is not currently intended to be upgradeable, as a precautionary measure.

manual code review

## Recommended Mitigation Steps

To avoid potential storage corruption and ensure flexibility, it is recommended to add storage gaps to `Well`. This practice helps future-proof the contract and maintain compatibility with any derived contracts.

```solidity
uint256[50] __gap; // Reserved space for future variable additions
```
