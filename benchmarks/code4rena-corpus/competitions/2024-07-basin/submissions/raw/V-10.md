# Vulnerability details

## Impact
In `calcReserve` the `b` variable is calculated incorrectly, as a result, its value will be lower than intended, causing `calcReserve`, `calcReserveAtRatioSwap` and `_calcRate` to return inaccurate data.

## Proof of Concept
Here is how `b` is currently calculated in the `getBandC` function:
```solidity
b = reserves + ((lpTokenSupply * A_PRECISION) / Ann);
```
The issue is that the value passed as the `reserves` parameter, when `getBandC` is called, is either one of the two `scaledReserves`:
```solidity
(uint256 c, uint256 b) = getBandC(a * N * N, lpTokenSupply, j == 0 ? scaledReserves[1] : scaledReserves[0]);
```

This is an issue, due to the fact that in the Curve implementation of the function, which should operate the same, the value used in place of `reserves` is the sum of the reserves:
https://github.com/curvefi/curve-stablecoin/blob/176e637a4b82874c49c90883ee1afc7e317ca051/contracts/Stableswap.vy#L708C1-L719C51
```solidity
    for _i in range(N_COINS_128):
        if _i == i:
            _x = x
        elif _i != j:
            _x = xp[_i]
        else:
            continue
        S_ += _x
        c = c * D / (_x * N_COINS)

    c = c * D * A_PRECISION / (Ann * N_COINS)
    b: uint256 = S_ + D * A_PRECISION / Ann  # - D
```

Here we see that `S_` (plays the same role as `reserves` in `getBandC`), is a sum of `_x`(single reserve).

Therefore, the value of `b` will always be smaller than intended, causing `_calcReserve` to return a larger value(the smaller the number you divide by the bigger the result). As a result of that, `calcReserve` will always return larger values than what is correct.

## Tools Used
Manual review

## Recommended Mitigation Steps
Supply the sum of both `scaledReserves` in `getBandC`.
