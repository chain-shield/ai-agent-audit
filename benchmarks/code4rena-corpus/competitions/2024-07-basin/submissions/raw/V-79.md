# Vulnerability details

## Impact

The contract Stable2.sol does not validate the length of input arrays in several functions which take in array parameters. 

This exposes the contract functions to potential out-of-bounds issues. 

There is no check to verify if the `reserves` array is of the expected length, which could cause unexpected errors or misbehaviors in the contract.

Moreover, the smart contract does not perform any validation on address inputs before proceeding with execution. 

This might expose the contract to potential invocation of the zero address, which may result in unexpected contract behavior.

## Proof of Concept

Some affected functions are `calcLpTokenSupply`, `calcReserve`, `calcRate`, `calcReserveAtRatioSwap`, and `calcReserveAtRatioLiquidity`.

## Recommended Mitigation Steps

Adding parameter validation checks, such as checking if the length of arrays is as expected and addresses are non-zero, is recommended. 

It's crucial to ensure that input addresses are not null and also make sure that input arrays `reserves`, `scaledReserves`, `ratios` and `decimals` have a length of at least 2 before performing operations on them. 

This way, you'd prevent potential underflow/overflow errors and avoid potential edge cases with invalid addresses. 

A potential way to fix this is adding require statements to validate the parameters. These will throw an exception, undo all changes and stop execution if something fails. 

Here is a code snippet of how it could be done:

 ```solidity
  require(reserves.length >= 2, "Expected length of reserves array not met");
  
  // check if the address is a non-zero address
  require(lut != address(0), "Zero address input");
```
