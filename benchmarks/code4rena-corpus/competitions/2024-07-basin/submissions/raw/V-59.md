# Vulnerability details

In the `calcLpTokenSupply` function, there is a potential division by zero when `scaledReserves[0]` or `scaledReserves[1]` is zero. This can cause the function to fail or behave unpredictably.

## Impact
This can lead to unexpected failures and could potentially be exploited by malicious actors to disrupt the contract's functionality.

## Proof of Concept

Proof of Concept:

To demonstrate the division by zero vulnerability in the `calcLpTokenSupply` function of the `Stable2` contract, use the following test case:
1. Declare and Initialize the Reserves Array:
```solidity
uint256;
reserves[0] = 0;
reserves[1] = 0; // Setting reserves to zero to trigger the vulnerability
```
2. Prepare the Data Argument:
```solidity
bytes memory data = abi.encode(18, 18);
```
3. Invoke the Vulnerable Function and Observe Behavior:

```solidity
try stable2.calcLpTokenSupply(reserves, data) returns (uint256 result) {
    // If the function executes, log the result
    emit log_uint(result);
} catch {
    // If a division by zero error occurs, log an error message
    emit log("Error: Division by zero occurred");
}
```
Expected Outcome: The test should trigger a division by zero error due to the zero values in the reserves array.

## Tools Used
Manual code review

## Recommended Mitigation Steps
Add checks to ensure `scaledReserves[0]` and `scaledReserves[1]`are not zero before performing the division operations.
