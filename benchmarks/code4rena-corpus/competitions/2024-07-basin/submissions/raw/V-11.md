# Vulnerability details

## Description: 

The `Stable2` contract implements a gas-efficient StableSwap pricing function for Wells with 2 tokens. A critical component of this contract is the `decodeWellData()` function, which is responsible for decoding and setting the decimal places for the two tokens involved in the Well. This function plays a crucial role in ensuring accurate calculations throughout the contract's operations.

The `decodeWellData()` function is designed to extract the decimal places of two tokens from the provided `data` parameter. If either token's decimal value is zero, it should default to 18 decimals. However, there is a logical error in the implementation of this function.

The problematic code section is as follows:

```solidity
File: Stable2.sol
310:     function decodeWellData(bytes memory data) public view virtual returns (uint256[] memory decimals) {
311:         (uint256 decimal0, uint256 decimal1) = abi.decode(data, (uint256, uint256));
312: 
313:         // if well data returns 0, assume 18 decimals.
314:         if (decimal0 == 0) {
315:             decimal0 = 18;
316:         }
317:         // @audit : This should be checking decimal1 instead of decimal0
318:         if (decimal0 == 0) {
319:             decimal1 = 18;
320:         }
321:         if (decimal0 > 18 || decimal1 > 18) revert InvalidTokenDecimals();
322: 
323:         decimals = new uint256[](2);
324:         decimals[0] = decimal0;
325:         decimals[1] = decimal1;
326:     }

```

The issue lies in the second conditional statement, which incorrectly checks `decimal0` again instead of `decimal1`. This means that if `decimal1` is zero, it will not be properly set to the default value of 18, potentially leading to incorrect decimal handling for the second token.


## Impact

The incorrect handling of token decimals could lead to severe miscalculations throughout the contract's operations. Functions that rely on accurate decimal information, such as `calcLpTokenSupply()`, `calcReserve()`, and `calcRate()`, may produce incorrect results and loss of funds for users. 


## Proof of Concept

1. A Well is created with two tokens: TokenA with 18 decimals and TokenB with 6 decimals.
2. The `data` parameter passed to `decodeWellData()` correctly encodes these values: `(18, 6)`.
3. In `decodeWellData()`, `decimal0` is correctly set to 18.
4. Due to the bug, the function fails to set `decimal1` to 6, instead leaving it at 0.
5. The function returns `[18, 0]` instead of the correct `[18, 6]`.
6. A user attempts to swap 1,000,000 TokenB for TokenA.
7. Due to the incorrect decimal handling, the contract treats this as 1,000,000,000,000 TokenB (applying 18 decimals instead of 6).
8. The user receives 1000 times more TokenA than they should, draining the pool and causing significant losses to liquidity providers.

## Recommended Mitigation Steps

The fix for this issue is straightforward. The second conditional statement should check `decimal1` instead of `decimal0` :

```diff
function decodeWellData(bytes memory data) public view virtual returns (uint256[] memory decimals) {
    (uint256 decimal0, uint256 decimal1) = abi.decode(data, (uint256, uint256));

    if (decimal0 == 0) {
        decimal0 = 18;
    }
-   if (decimal0 == 0) {
+   if (decimal1 == 0) {
        decimal1 = 18;
    }
    // ... rest of the function
}
```
