# Vulnerability details

## Proof of Concept

Take a look at https://github.com/code-423n4/2024-07-basin/blob/7d5aacbb144d0ba0bc358dfde6e0cc913d25310e/src/functions/Stable2.sol#L309-L325

```solidity

    function decodeWellData(bytes memory data) public view virtual returns (uint256[] memory decimals) {
        (uint256 decimal0, uint256 decimal1) = abi.decode(data, (uint256, uint256));

        // if well data returns 0, assume 18 decimals.
        if (decimal0 == 0) {
            decimal0 = 18;
        }
        if (decimal0 == 0) {
            decimal1 = 18;
        }
        if (decimal0 > 18 || decimal1 > 18) revert InvalidTokenDecimals();

        decimals = new uint256[](2);
        decimals[0] = decimal0;
        decimals[1] = decimal1;
    }
```

This function is used to decode the data encoded in the well and it then returns an array of the decimals of the tokens in the well.

Issue however is that the `if (decimal0 == 0)` check is repeated twice, which then means that no checks are applied on `decimal1` and as such would cause for the wrong array to be returned in the case where `deciimal0 != decimal1`.

Now would be key to note that the array being returned is crucial to the calculation logics present in `Stable2.sol`, which then means that all the instances linked below could then have their calculations with the wrong array in the case where `deciimal0 != decimal1`.

- [Stable2#calcLpTokenSupply()](https://github.com/code-423n4/2024-07-basin/blob/7d5aacbb144d0ba0bc358dfde6e0cc913d25310e/src/functions/Stable2.sol#L79)
- [Stable2#calcReserveAtRatioSwap()](https://github.com/code-423n4/2024-07-basin/blob/7d5aacbb144d0ba0bc358dfde6e0cc913d25310e/src/functions/Stable2.sol#L181)
- [Stable2#calcReserveAtRatioSwap()](https://github.com/code-423n4/2024-07-basin/blob/7d5aacbb144d0ba0bc358dfde6e0cc913d25310e/src/functions/Stable2.sol#L181)
- [Stable2#calcReserveAtRatioLiquidity()](https://github.com/code-423n4/2024-07-basin/blob/7d5aacbb144d0ba0bc358dfde6e0cc913d25310e/src/functions/Stable2.sol#L254)

## Impact

As hinted under _Proof of Concept_, in the case where `deciimal0 != decimal1` crucial calculations would be done on wrong data, which goes ahead to heavier impact accross the whole protocol.

To take one of the instances, i.e `calcLpTokenSupply()`, this then means that whe reserves are provided, the amount of lp tokens attahced to this reserve would be wrong and the `calcLpTokenSupply()` is used all around scope with multiple instances even in the core well itself:
