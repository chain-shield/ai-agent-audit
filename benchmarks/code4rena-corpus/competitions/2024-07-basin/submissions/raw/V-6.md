# Vulnerability details

## Impact
In the `decodeWellData` function of `Stable2.sol` wrong decimal configuration is performed, which may cause the decimals of one of the tokens to be wrong. As a result, `calcLpTokenSupply`, `calcReserve`, `calcRate`, `calcReserveAtRatioSwap` and `calcReserveAtRatioLiquidity` will return critically wrong data.

## Proof of Concept
The following validation is performed in `decodeWellData`:
```solidity
if (decimal0 == 0) {
    decimal0 = 18;
}
if (decimal0 == 0) {
    decimal1 = 18;
}
```

The issue is that in the second `if` statement `decimal0` is used instead of `decimal1`. As a result, if `decimal0` is 0, `decimal1` will also always be equal to 18, even if it's actual value is different, for example:
1/ `decimal0` is 0, therefore its value should be 18
2/ `decimal1` is 6, but it is overridden to 18

Thus, `calcLpTokenSupply`, `calcReserve`, `calcRate`, `calcReserveAtRatioSwap` and `calcReserveAtRatioLiquidity` may return wrong values, which may be much larger than the intended results.

## Tools Used
Manual review

## Recommended Mitigation Steps
Update to the following:
```solidity
if (decimal0 == 0) {
    decimal0 = 18;
}
if (decimal1 == 0) {
    decimal1 = 18;
}
```
