# Vulnerability details

## Impact
Permanent DoS due to an upgrade to a malicious implementation that reverts critical functions like `upgradeTo`, `upgradeToAndCall`, `removeLiquidity`, etc. This would result in locked user funds and prevent further upgrades.

## Proof of Concept
The `WellUpgradeable.sol` contract is designed as a template for upgradeable Well logic contracts, with minimal proxies (Wells) created by the Aquifer that delegatecalls to this contract. Well owners have the autonomy to choose which implementation their Wells delegate to and how the logic should operate. However, there is a vulnerability in the current design that could allow an arbitrary malicious user to harm users who have deposited assets into Wells.

While the documentation and whitepapers advise users to exercise caution when depositing into Wells, there is a vulnerability in the current implementation that could be addressed and make the contract more safer. The issue stems from the fact that the current upgrade functionality in `WellUpgradeable` takes effect instantly after a successful transaction. For example, if `upgradeTo` is called and the transaction succeeds, the proxy will immediately delegate calls to the new implementation. This poses a significant risk, as it could be exploited by malicious actors, leading to permanently locked user funds and preventing further upgrades to the Well.

Consider the following scenario:
1. The Basin team deploys an audited `WellUpgradeable` contract, and users start creating minimal proxies (Wells) that point to this logic.
2. Alice deploys a new Well for TokenA and TokenB.
3. Bob deploys a new Well for TokenC and TokenD.
4. Eve deploys a new Well for TokenX and TokenY.
5. Everything functions as expected, with DeFi users depositing and utilizing the Wells deployed by Alice, Bob, and Eve.
6. Suddenly, a malicious user decides to disrupt the system. This user creates a new, malicious UUPS-compatible implementation where critical functions like `upgradeTo`, `upgradeToAndCall`, `removeLiquidity`, etc. are designed to revert.
7. The malicious user then calls `upgradeTo` with this new implementation address. The proxy contract delegate calls the `WellUpgradeable` contract.
8. The [`_authorizeUpgrade`](https://github.com/code-423n4/2024-07-basin/blob/7d5aacbb144d0ba0bc358dfde6e0cc913d25310e/src/WellUpgradeable.sol#L65-L85) function will pass because the call originates from a proxy, and the malicious implementation is UUPS-compatible. Since there are no `onlyWellOwner` access control modifiers and the update is instant, user funds will be permanently locked, and the Well will be stuck in this broken state, preventing further upgrades.

The following PoC test demonstrates that an arbitrary user can upgrade an arbitrary Well to point to a new malicious implementation contract, effectively bricking the Well's functionality and locking user funds.

### PoC Test:
1. Copy and paste the following contract in `WellUpgradeable.t.sol`:
```solidity
contract MaliciousWellUpgradeable is WellUpgradeable {
    function upgradeTo(address newImplementation, uint256 randomNumber) public {
        revert();
    }
}
```

2. Copy and paste the following test case in `WellUpgradeable.t.sol`:
```solidity 
    function testUpgradeToMaliciousImplementation() public {
```

## Recommended Mitigation Steps
The current 'instant' upgrade functionality is highly risky, as it allows an arbitrary malicious user to permanently brick the Well's functionality and lock all user funds deposited in the Well. To mitigate this risk, I propose implementing a cooldown period before changing implementations, allowing users to verify the new implementation's behavior. If any issues are detected, users should be able to withdraw their funds before the upgrade takes effect and also warn other users of potential danger.

Additionally, a Well-level governance mechanism could be implemented for emergency implementation changes, which could be executed instantly. For example, users could receive voting tokens upon depositing their assets into the Well. While this approach is not foolproof and could be subject to abuse (e.g., creating multiple accounts to gain more voting power), safeguards could be put in place, such as requiring a certain deposit amount to obtain voting tokens, thereby disincentivizing malicious behavior and making such attacks less profitable.
