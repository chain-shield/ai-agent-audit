# Vulnerability details

## Impact
Malicious operator can evade slashing after in case of doing something malicious.

## Proof of Concept
Karak protocol implements the `MIN_STAKE_UPDATE_DELAY` in order to allow the `DSS` to have enough time to slash an `operator` in case of malicious activity.
```solidity
    uint256 public constant SNAPSHOT_EXPIRY = 7 days;
    uint256 public constant SLASHING_WINDOW = 7 days;
    uint256 public constant SLASHING_VETO_WINDOW = 2 days;
>   uint256 public constant MIN_STAKE_UPDATE_DELAY = SLASHING_WINDOW + SLASHING_VETO_WINDOW;
```

But there exist a way a malicious `operator` can do a malicious activity and still evade the slashing from the `DSS`.
The `DSS` can slash an `operator` through the [requestSlashing](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/Core.sol#L220C14-L220C29) function of the `Core.sol`, the dss will be subjected `SLASHING_VETO_WINDOW` cooldown in order to allow the [VETO_COMMITEE](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/entities/SlasherLib.sol#L129) to cancel the slashing request if its deemed unfair.
```solidity
129        if (queuedSlashing.timestamp + Constants.SLASHING_VETO_WINDOW > block.timestamp) {
            revert MinSlashingDelayNotPassed();
        }
```

The issue here is, a malicious operator that staked in their vault can do malicious activities and evade being slash, consider this:

* Operator calls the [requestUpdateVaultStakeInDSS](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/Core.sol#L130C14-L130C42) unstaking their vault from the `DSS`
* The `9 days` coolDOwn is now active
* At the 9th day, the malicious operator now do something malicious
* Due how the system works, the `operator` can now front-run the dss and call the  [finalizeUpdateVaultStakeInDSS](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/Core.sol#L146C14-L146C43)

When the `DSS` now realize of the behavior and request for slashing, the call will revert due to the [isVaultStakeToDSS](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/entities/SlasherLib.sol#L51) call  where the operator is no longer part of that `DSS`
```solidity
uint256 maxSlashPercentageWad = getDSSMaxSlashablePercentageWad(self, dss);
        for (uint256 i = 0; i < slashingRequest.vaults.length; i++) {
>            if (!self.operatorState[slashingRequest.operator].isVaultStakeToDSS(dss, slashingRequest.vaults[i])) {
                revert VaultNotStakedToDSS();
            }
            if (slashingRequest.slashPercentagesWad[i] == 0) revert ZeroSlashPercentageWad();
            if (slashingRequest.slashPercentagesWad[i] > maxSlashPercentageWad) revert MaxSlashPercentageWadBreached();
        }
```

## Recommended Mitigation Steps

The cool-down period is overall good in order to avoid front-running in case of slashing, but more should be done.

I'm recommending that a limitations should be applied on the activities of the `operator` after calling the [requestUpdateVaultStakeInDSS](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/Core.sol#L130) function, the overall of it or  when he's specifically trying to unstake.

A modifier should work fine to check for when the function has been called for unstake.
