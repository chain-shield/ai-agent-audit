# Vulnerability details

## Impact
Vault that been slashed in previous times poses overflow risk which allows user funds to remain stuck in the contract permanently!

The root cause of this is that when vault are slashed and funds are sent to the SlashHandler, no share is burnt in the vault, so TotalSupply keeps increasing and there is no max value for what a unit of token should mint as shares in a vault.

## Proof of Concept
Let us consider the case of Vault_A.
1. After a total deposit of 1e24_DAI($1M), it get slashed by 100% leaving the vault with;
```
TotalAsset = 0;
TotalShares/TotalSupply = 1e24;
```

2. On the second go, it manages to get another deposit of 1e24_DAI($1M), this time vault has;
```
TotalAsset = 1e24;
TotalShares/TotalSupply = 1e48;
```

3. DSS slashes the vault of 100% again, now the vault has;
```

TotalShares/TotalSupply = 1e48;
```

4. On the next run, if the vault is deposited to; $1 worth of DAI will now amount to 1e66 worth of shares to be minted.(it will take $10b worth of DAI to cause overflow revert  when depositing, so nothing happens @ deposit at the moment)
```
$1_DAI = (1e18 * 1e48) / 1 = 1e66 shares!
$1,000,000,000_DAI = (1e27 * 1e48) = 1e75 shares!
```
5. Irrespective of how much have now been deposited(as stated earlier, could take up to $10b worth of DAI can come in), no amount can be withdrawn.
6. Now this time, the vault is running without slashing this time.
7. The problem now is that redeeming of shares will never be possible.

## Recommended Mitigation Steps
Consider having a check for what a unit of token can mint as shares in a vault.
In this case, at the initial normal state, a token should mint 1e18 shares(1:1), then in worst case scenerio, it should revert when minting over (1e30 - 1e36) per unit of DAI(1e18).

Using 1e36 for instance, it will be possible to deposit and redeem up to $100B worth of DAI without overflowing.
