# Vulnerability details

## Impact
The `finishRedeem` function in the Vault smart contract is vulnerable to misuse due to the absence of a check for slashed withdrawals. This allows users to withdraw slashed assets.

## Proof of Concept
Allowing slashed withdrawals to be processed can lead to significant financial losses for the vault, as slashed assets are intended to cover penalties or losses due to operator misbehavior. This vulnerability undermines the protocol's penalty mechanisms and can result in unfair advantages for users whose assets were legitimately slashed.

The `finishRedeem` function processes withdrawal requests by [converting shares to assets and transferring them to the beneficiary](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/Vault.sol#L168). However, it lacks a check to prevent processing withdrawals that have been flagged as slashed.
```
function finishRedeem(bytes32 withdrawalKey)
    external
    nonReentrant
    whenFunctionNotPaused(Constants.PAUSE_VAULT_FINISH_REDEEM)
{
    (VaultLib.State storage state, VaultLib.Config storage config) = _storage();

    WithdrawLib.QueuedWithdrawal memory startedWithdrawal = state.validateQueuedWithdrawal(withdrawalKey);

    uint256 shares = startedWithdrawal.shares;
    if (shares > maxRedeem(address(this))) revert RedeemMoreThanMax();
    uint256 redeemableAssets = convertToAssets(shares);

    delete state.withdrawalMap[withdrawalKey];

    _withdraw({
        by: address(this),
        to: startedWithdrawal.beneficiary,
        owner: address(this),
        assets: redeemableAssets,
        shares: shares
    });

    emit FinishedRedeem(
        startedWithdrawal.staker,
        startedWithdrawal.beneficiary,
        config.operator,
        startedWithdrawal.shares,
        redeemableAssets,
        withdrawalKey
    );
}
```
***Redeemer Gains (Exploits the System):***
In a staking and vault system, assets can be slashed due to operator misconduct or failure to fulfill certain criteria as Karak implements this. Slashed assets are meant to be penalties that cover potential damages or failures, ensuring the integrity and security of the system.

However, users can withdraw assets from the vault even though their assets have been slashed;
`UserA` calls `startRedeem` to initiate a withdrawal for 100 shares.

The system generates a withdrawal key and queues the withdrawal with a timestamp.
An operator associated with `UserA` is found to be misbehaving or failing to meet performance criteria.

A slashing event is triggered, and `UserA’s` assets are partially or fully slashed.

The withdrawal was not marked as slashed, Another user, `AttackerB`, observes that UserA's withdrawal is queued and knows the exact timestamp.
`AttackerB` predicts that UserA's withdrawal will soon be processed by `finishRedeem`.

`UserA` (or Attacker B) calls `finishRedeem` to complete the withdrawal *before* the slashHandler in the [slashHandler.sol](https://github.com/code-423n4/2024-07-karak/blob/main/src/SlashingHandler.sol) set by the [Core contract](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/Vault.sol#L322) calls the handleSlash(https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/SlashingHandler.sol#L52) .

The `finishRedeem` function processes the withdrawal without checking if it has been slashed.

The system converts `UserA's` shares to assets and transfers them to `UserA`.
`UserA` receives the full amount of assets despite the slashing event, bypassing the penalty.

> `UserA` gains assets that were supposed to be forfeited due to the slashing event.

The vault loses assets that were intended to cover penalties or damages, leading to financial imbalances.

***Redeemer Loses (System Integrity Compromised)***
`UserA` initiates a withdrawal by calling startRedeem for 100 shares.
The system queues the withdrawal with a timestamp and a withdrawal key.

An operator associated with UserA’s assets is found to be at fault.
A slashing event occurs, reducing the value of `UserA's` assets or marking the withdrawal as slashed.

The system `slashHandler` calls the `slashHandling`  to burn some asset before `UserA` (or another user) calls `finishRedeem` to complete the withdrawal .

The `finishRedeem` function processes the withdrawal without checking if it has been slashed.

The system converts UserA's shares to assets, but the actual amount of redeemable assets is lower due to the slashing.

`UserA` receives fewer assets than expected, reflecting the penalty imposed by the slashing event.

## Recommended Mitigation Steps
There should be a flag on users whose withdrawals or asset to be withdrawn who has been slashed by the contract, so when any withdrawal is made it should indicate that this withdrawal to be made has been slashed, and the amount of slashed from the user should be deducted from the user actual withdrawable asset so he doesn't lose either ways.

And always try to ensure user who wants to finish a redeeem on the behalf of another user they should know if the user withdrawals has been slashed or not then the calc above said can be done.
