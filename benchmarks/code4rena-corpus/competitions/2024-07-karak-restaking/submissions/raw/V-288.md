# Vulnerability details

## Bug description
Karak native restaking utilizes a balance snapshot system to keep the `NativeNode` aware of the balance changes on the beacon chain. `NativeVault` updates the node owner's shares based on the balance changes on their `NativeNode` and the beacon chain balance of the validators.

There is a potential underflow of the `NativeVault.totalAssets()` and `node.totalRestakedETH` that can occur because an increase of the `NativeNode's` balance is not snapshotted before the slashing event.

Assume a scenario where a `NativeVault` has one staker (Alice) with 32 ETH restaked from the BeaconChain.
* NativeVault's totalAssets = 32 ETH.
* Alice.totalRestakedETH = 32 ETH.
* Current balance of the Alice's NativeNode = 0 ETH.
* 2 ETH accrues on Alice's NativeNode balance due to rewards from BeaconChain. (not yet snapshotted)
* A vault is slashed for 2 ETH.
* NativeVault's totalAssets becomes 30 ETH.
* startSnapshot() is called for Alice.

When `startSnapshot()` is called for Alice, the internal `_startSnapshot()` function is invoked, where `_transferToSlashStore(Alice)` is called.

[NativeVault.sol#L448-L456](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/NativeVault.sol#L448-L456)
```solidity
function _startSnapshot(
    NativeVaultLib.NativeNode storage node,
    bool revertIfNoBalanceChange,
    address nodeOwner
) internal {
    if (node.currentSnapshotTimestamp != 0)
        revert PendingIncompleteSnapshot();
    // Sweep slashed ETH from node balance before locking in snapshot node balance.
    // This allows all the ETH that was theoritically slashed in `slashAssets` function call can be moved to a slash store,
    // which can decide what to do with this slashed ETH.
    _transferToSlashStore(nodeOwner);
```

`_transferToSlashStore()` will sweep all of the slashed ETH from the NativeNode's balance.

[NativeVault.sol#L430-L439](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/NativeVault.sol#L430-L439)
```solidity

    convertToAssets(balanceOf(nodeOwner));
// sweepable ETH = min(ETH available on node address, total slashed ETH)

    node.nodeAddress.balance,
    slashedAssets
);

    self.slashStore,
    slashedWithdrawable
);
// update total restaked ETH available (node + beacon)

```

In the above code snippet `slashedAssets` will equal 2 ETH and `node.totalRestakedETH` will be decremented to 30 ETH.

After this, `_startSnapshot()` will proceed to create a snapshot that would need to be validated later.

Since both `snapshot.nodeBalanceWei` and `snapshot.balanceDeltaWei` are 0, `totalDeltaWei` results in 0. Because of that `_updateBalance()` does not update the balance of the `nodeOwner`. 

Because `_updateBalance()` is called with `totalDeltaWei = 0`, `NativeVault.totalAssets()` and `Alice.totalRestakedETH` both remain equal to 30 ETH, while Alice has 32 ETH restaked in Karak.
Now if Alice were to withdraw her 32 ETH, 2 ETH would get stuck due to an underflow.

## Recommended Mitigation
To fix this issue, `_transferToSlashStore()` should be called last after all of the snapshots were submitted.
