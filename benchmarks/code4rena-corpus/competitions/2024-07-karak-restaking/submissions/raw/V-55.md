# Vulnerability details

## Impact
From calling `startRedeem` and `finishRedeem` there is a long delay.

When redeeming, the assets the user receives depends on the balances of the underlying asset and the total supply

Since there is time between starting a redemption and withdrawing, users are exposed to a very high level of slippage, where balances can change a lot during this time, directly effecting how many assets the user receives for their shares

There needs too be a slippage check to ensure that users are not receiving drastically less tokens than they expect


## Proof of Concept

ConvertToAssets depends on the balance of asset and total supply of lp which can dramatically change between a withdrawal redemption request and the actual withdrawal 

```
   function convertToAssets(uint256 shares) public view virtual returns (uint256) {
        uint256 supply = totalSupply; // Saves an extra SLOAD if totalSupply is non-zero.

        return supply == 0 ? shares : shares.mulDivDown(totalAssets(), supply);
    }
```
