# Vulnerability details

## Impact

Using `isSmartContract()` to distinguish between Externally Owned Accounts (EOAs) and contracts in Ethereum is no longer reliable due to proxy contracts and contract creation during transaction execution. This method may inaccurately classify contracts as EOAs or vice versa, especially post-transaction. 

## Proof of Concept
 
When a Distributed Secure Service (DSS) is being registered in the `Core.sol` contract, it does the following check:

> if (!self.isVaultImplAllowlisted(newVaultImpl)) revert VaultImplNotAllowlisted();

However, this check can be false-positive:


* Function is called in the constructor. Address.isContract() checks for the code length, but during construction code length is 0.

* A smart contract that has not been deployed yet can be used. The CREATE2 opcode can be used to deterministically calculate the address of a smart contract before it is created. This means that the user can bypass this check by calling this function before deploying the contract.


## Tools Used

Manual review

## Recommended Mitigation Steps

It is generally not recommended to enforce an address to be only EOA or vice-versa and AFAIK, this is impossible to implement due to the aforementioned cases. I recommend the protocol team take a closer look at this and build the protocol with the assumption that `address(dss) != EOA`. OpenZeppelin's Address library deprecated `isContract()` (which uses the same logic) recognizing these limitations.
