# Vulnerability details

## Impact
Operators could get away without being slashed due to rounding error while calculating `EarmarkedStakes`

## Proof of Concept
The root of cause of this bug is because of two reasons
1. Allowing all ERC20's that means `totalAssets()` function could return a value with 6 decimal places if asset is usdc.
2. The assumption that DSS will provide a wad percentage with 18 decimals

Let's elaborate this
1. We start with `registerDSS` that is responsible for DSS registration by setting the `maxSlashablePercentageWad` provided by the DSS:
https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/Core.sol#L262

As we can see, even though the function is expecting to provide a wad value, which will be let's say 30e18, it does not check if the input value is actually 18 decimal places or not.
Nor, the internal call to `setDSSMaxSlashablePercentageWad` here:

https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/entities/SlasherLib.sol#L174-L185

It only checks 2 things with input param. 
a.  should not be zero
b. should be greater than MAX
`This means that if DSS is passing 1 as a value , it will be accepted`

2. Now comes `requestSlashing` where DSS is providing the `slashPercent` in request metadata in an array of vault address and their respective values

https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/Core.sol#L220-L231

This goes to SlasherLib:
https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/entities/SlasherLib.sol#L101

We have a validation function before this 
https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/entities/SlasherLib.sol#L59
which checks
a. length mismatch of vault array and slash percent array
b. one more internal call 
https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/entities/SlasherLib.sol#L42
that reverts on 0 input and greater than MAX. 

`That means, there's no way to stop if slash percent is not with 18 decimal places.`

Now the call goes to mulDiv via `fetchEarmarkedStakes` where `totalAssets()` in vault is Usdc ( 6 decimals ) and DSS hasn't provided correct 18 decimal places ( let's say 30 instead of 30e18 )
so formula in terms of decimals will become.

```
10(from input value 30)  * 1e6 (usdc)
------------------------------------
          1e18(MAX WAD)
```

This will ultimately round down to 0. Moreover, as long has the numerator value is smaller than 18 decimal places, this value will remain 0. 
Since this value will be used to check the amount of assets to be slashed from vaults via `slashAssets` in `finalizeSlashing`
https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/entities/SlasherLib.sol#L135

We can say that no assets will be slashed in case of any malicious act done by Operators. 

One could argue that this is the DSS's responsibility to provide correct values upon registering and requesting for slash but since DSS service and any operator could become a part of ecosystem we have to make sure that even though DSS's devs should be aware of the difference between normal value and wad, a mistake like this should not penetrate into the system. 

## Tools Used
Manual Review

## Recommended Mitigation Steps
A simple check to ensure that the final value after dividing by 1e18 should be greater than 0 in `registerDSS` and `requestSlashing` could mitigate this.
