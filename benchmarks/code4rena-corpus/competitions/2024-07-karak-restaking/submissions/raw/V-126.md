# Vulnerability details

## Impact
The `initialize` function in the vault contract relies on a fallback constant `_DEFAULT_UNDERLYING_DECIMALS` to set the `decimal` value of the deposit token if the token's decimals cannot be retrieved. This constant is not defined in the current implementation, leading to potential severe bugs during the contract initialization process. 

## Proof of Concept
```
function initialize(
    address _owner,
    address _operator,
    address _depositToken,
    string memory _name,
    string memory _symbol,
    bytes memory _extraData
) external initializer {
    _initializeOwner(_owner);
    __Pauser_init();

    (bool decimalsSuccess, uint8 result) = _tryGetAssetDecimals(address(_depositToken));
    VaultLib.Config storage config = _config();
    config.decimals = decimalsSuccess ? result : _DEFAULT_UNDERLYING_DECIMALS; <--@audit, was never defined!!
}
```
- The `_DEFAULT_UNDERLYING_DECIMALS` constant is not defined in the contract.
- When `_tryGetAssetDecimals` fails to retrieve the decimals of the deposit token, the fallback value `_DEFAULT_UNDERLYING_DECIMALS` is used.
- Since `_DEFAULT_UNDERLYING_DECIMALS` is not set, it can lead to unexpected behavior or compiler errors.

Deploy the vault contract with a token that does not implement the decimals() function.

The `config.decimals` is set to `_DEFAULT_UNDERLYING_DECIMALS`, which is not defined.
This can lead to config.decimals being an unintended value, such as 0.`

The `_tryGetAssetDecimals` function attempts to retrieve the decimals of the _depositToken.
If the token does not implement the `decimals()` function or the function call fails for some reason (e.g., the token is not compliant with the expected interface), the decimalsSuccess variable will be false.

When `decimalsSuccess` is false, the contract will try to use `_DEFAULT_UNDERLYING_DECIMALS` as the fallback value for `config.decimals`.
If `_DEFAULT_UNDERLYING_DECIMALS` is not defined, this results in an incorrect value being assigned to `config.decimals`.

All calculations relying on `config.decimals` become incorrect.
For example, converting 1000 tokens to shares using `config.decimals` results in incorrect share amounts.

Assume a token `TokenA` correctly implements the `decimals()` function and returns 18.
`_tryGetAssetDecimals(address(TokenA))` successfully retrieves the decimals, setting decimalsSuccess to true and result to 18.
`config.decimals` is correctly set to 18.
There is no vulnerability in this case.

Assume a token `TokenB` does not implement the `decimals()` function.
`_tryGetAssetDecimals(address(TokenB))` fails to retrieve the decimals, setting decimalsSuccess to false.
The contract attempts to set config.decimals to `_DEFAULT_UNDERLYING_DECIMALS`.
If `_DEFAULT_UNDERLYING_DECIMALS` is not defined, config.decimals might be set to 0 or another unintended value.

If `config.decimals` is set to an incorrect value, all calculations that depend on the decimal precision of the token will be incorrect.
For instance, if `config.decimals` is set to 0, a deposit of 1 token might be interpreted as 1 * 10^0 = 1 share instead of 1 * 10^18 = `1,000,000,000,000,000,000` shares.

Users depositing or withdrawing tokens will receive incorrect amounts due to the miscalculated conversions between tokens and shares.
This leads to financial losses and distrust in the vault contract.

The vault contract is deployed.
A non-standard token `TokenB` is used as `_depositToken`, which does not implement the `decimals()` function.

The `initialize `function is called with TokenB.
`_tryGetAssetDecimals(address(TokenB))` fails because `TokenB` does not implement the `decimals()` function, resulting in `decimalsSuccess = false`.
The contract attempts to set `config.decimals` to `_DEFAULT_UNDERLYING_DECIMALS`.
Since `_DEFAULT_UNDERLYING_DECIMALS` is not defined, `config.decimals` might be set to an incorrect value, such as 0.

A user deposits 1000 `TokenB` into the vault.
Due to `config.decimals` being 0, the conversion logic misinterprets the deposit:
The correct calculation should have been 1000 * 10^decimals, but with `decimals = 0`, the user receives 1000 shares instead of the correct amount.
When the user attempts to withdraw, the shares-to-tokens conversion is also incorrect.
The user might receive a significantly higher or lower number of tokens than expected.

## Recommended Mitigation Steps
Ensure that `_DEFAULT_UNDERLYING_DECIMALS` is defined, the contract maintains correct behavior even when the token decimals cannot be retrieved, preventing severe bugs and potential financial losses.
```
uint8 private constant _DEFAULT_UNDERLYING_DECIMALS = 18;
```
>OR
```
 (bool decimalsSuccess, uint8 result) = _tryGetAssetDecimals(address(_depositToken));
    VaultLib.Config storage config = _config();

}
```
