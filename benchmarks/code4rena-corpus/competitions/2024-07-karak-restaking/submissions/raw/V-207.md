# Vulnerability details

## Impact
The specification in the contest's Code4rena page states clearly that fee on transfer tokens are in scope. The issue is that ERC4626 vaults do not support these types of tokens and their implementation may be problematic. As a result, users will receive more shares than intended.

## Proof of Concept
Fee on transfer tokens require a fee to be paid from the number of tokens that is transferred, for example, if user A transfers `amount` of tokens to user B, user B will receive `amount - fees`. This is an issue as when deposits are made in ERC4626 vaults the number of shares minted is calculated using the number of tokens prior to the subtraction of the fees:

```solidity
    function deposit(uint256 assets, address to) public virtual returns (uint256 shares) {
        if (assets > maxDeposit(to)) _revert(0xb3c61a83); // `DepositMoreThanMax()`.
        shares = previewDeposit(assets);
        _deposit(msg.sender, to, assets, shares);
    }
```
Above we can see that the number of shares is calculated using the `assets` variable.
And in the `_deposit` function we see that the same `assets` variable is the amount of tokens transferred to the user, while the actual amount received by the vault will be `assets - fees`:
```solidity
 function _deposit(address by, address to, uint256 assets, uint256 shares) internal virtual {
        SafeTransferLib.safeTransferFrom(asset(), by, address(this), assets);
        _mint(to, shares);
        /// @solidity memory-safe-assembly
        assembly {
            // Emit the {Deposit} event.
            mstore(0x00, assets)
            mstore(0x20, shares)
            let m := shr(96, not(0))
            log3(0x00, 0x40, _DEPOSIT_EVENT_SIGNATURE, and(m, by), and(m, to))
        }
        _afterDeposit(assets, shares);
    }
```

Due to this, different deposits of the same value may receive a different number of shares, for example:
User A makes 1 deposit of 1000 tokens with a fee of 10% and user B makes 2 deposits of 500 tokens with the same fee percent.

1/ User A's deposit would mint 1000 shares, while only 900 tokens would have been transferred: `convertToShares(1000) = _initialConvertToShares(1000) = 1000 shares`.

2/ User B's first deposit of 500 would mint 555 shares, while only 450 tokens have been transferred: `convertToShares(500) = assets * totalSupply / totalAssets = 500 * 1000 / 900 = 555 shares`.

3/ Now on User B's second transfer of 500 again 450 tokens will be transferred to the vault, but the number of shares minted will be: `convertToShares(uint256 assets) = assets * totalSupply / totalAssets = 500 * 1555 / 1350 = 575 shares`

As a result User B received 130 more shares than User A for the same amount of assets.

## Tools Used
Manual review

## Recommended Mitigation Steps
For the vaults that would support fee on transfer tokens the amount, used to calculate the number of shares should be the amount excluding the fee.
