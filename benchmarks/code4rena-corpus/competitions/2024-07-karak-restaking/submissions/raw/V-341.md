# Vulnerability details

## Issue
There is an issue in this function related to how it handles the input `bytes32` value.

https://github.com/code-423n4/2024-07-karak/blob/main/src/entities/BeaconProofsLib.sol#L54

```solidity
function fromLittleEndianUint64(bytes32 lenum) internal pure returns (uint64 n) {
    n = uint64(uint256(lenum >> 192));
    return (n >> 56) | ((0x00FF000000000000 & n) >> 40) | ((0x0000FF0000000000 & n) >> 24)
        | ((0x000000FF00000000 & n) >> 8) | ((0x00000000FF000000 & n) << 8) | ((0x0000000000FF0000 & n) << 24)
        | ((0x000000000000FF00 & n) << 40) | ((0x00000000000000FF & n) << 56);
}

```


1. The function first extracts the least significant 64 bits from the input `bytes32` using:

```solidity
n = uint64(uint256(lenum >> 192));
```

2. This operation effectively discards the most significant 192 bits of the input, keeping only the least significant 64 bits.

3. The rest of the function then proceeds to swap the byte order of these 64 bits.

The issue is that this function will always operate on the least significant 64 bits of the input, regardless of where the actual uint64 value is located within the `bytes32` input.

This becomes problematic in the context of how it's used elsewhere in the contract. For example, in the `validateBalance` function:

```solidity
uint256 bitShiftAmount = (validatorIndex % 4) * 64;
return uint256(fromLittleEndianUint64(bytes32((uint256(proof.balanceRoot) << bitShiftAmount)))) * 1 gwei;
```

Here, `bitShiftAmount` can be 0, 64, 128, or 192. When it's anything other than 192, the `fromLittleEndianUint64` function will be operating on the wrong part of the `bytes32` value, leading to incorrect results.

## Impact

- The BeaconProofs library is designed to work with Ethereum 2.0 beacon chain data, specifically for verifying proofs and extracting validator information. The validateBalance function is crucial as it extracts and converts individual validator balances from the beacon state.

- Due to the error, it may extract the wrong 64-bit chunk, leading to incorrect balance reporting. In a worst-case scenario, the reported balance could be completely unrelated to the actual validator balance. This could result in reporting balances that are orders of magnitude different from the true values.

- Validators with indices not divisible by 4 (i.e not at the least significant position in the bytes32) will have incorrect balances reported. 75% of validators (those with indices 1, 2, or 3 mod 4) would be affected.

## Potential Exploit Scenario

Misreporting of balances could potentially be exploited if an attacker can manipulate which part of the bytes32 is read.
This could lead to artificial inflation or deflation of reported validator balances.

## Mitigation

To fix this issue, the `fromLittleEndianUint64` function should take an additional parameter to specify which 64-bit chunk of the `bytes32` to operate on, or the shifting should be done before calling the function.

A corrected version might look like this:

```solidity
function fromLittleEndianUint64(bytes32 lenum, uint256 bitShiftAmount) internal pure returns (uint64) {
    uint64 n = uint64(uint256(lenum) >> bitShiftAmount);
    return (n >> 56) | ((0x00FF000000000000 & n) >> 40) | ((0x0000FF0000000000 & n) >> 24)
        | ((0x000000FF00000000 & n) >> 8) | ((0x00000000FF000000 & n) << 8) | ((0x0000000000FF0000 & n) << 24)
        | ((0x000000000000FF00 & n) << 40) | ((0x00000000000000FF & n) << 56);
}
```

And it would be called like this:

```solidity
uint256 bitShiftAmount = (validatorIndex % 4) * 64;
return uint256(fromLittleEndianUint64(proof.balanceRoot, bitShiftAmount)) * 1 gwei;
```

This modification will ensure that the function operates on the correct 64-bit chunk of the input `bytes32`, regardless of its position within the larger value.
