# Vulnerability details

### [M-1] Lack of access control on `SlashingHandler::handleSlashing` function allows users to accidentally burn their tokens

**Description:** The intended purpose of the `SlashingHandler::handleSlashing` function is to be part of the `Core` contract slashing flow. After a `DSS` calls the `Core::requestSlashing` function for a given `operator+vault` to record a slashing request, anyone can "finalize a queued slashing and send the slashed assets notice to the slashing handler". The `Core` contract will use the `SlasherLib::finalizeSlashing` function, to call the `Vault::slashAssets` function, which is guarded by an `onlyCore` modifier. Inside the `Vault::slashAssets` function the system calls the `SlashingHandler::handleSlashing` function which takes the tokens from the `Vault` before burning them.

Based on the above flow, it seems natural that the `SlashingHandler::handleSlashing` should have some form of access control, like an `onlyVault` modifier for example, that will allow only the `Vault` contracts to call this function.

Below is the current implementation of the `SlashingHandler::handleSlashing` function

```javascript
    //@audit | no access controls
    function handleSlashing(IERC20 token, uint256 amount) external {
        //..
        //..
        SafeTransferLib.safeTransferFrom(address(token), msg.sender, address(this), amount);
        // Below is where custom logic for each asset lives
        SafeTransferLib.safeTransfer(address(token), address(0), amount);
    }

```

**Impact:** A user can call this function and accidentally burn his tokens. Based on the current implementation, the `SlashingHandler` contract will transfer the tokens from `msg.sender`, which can be any user, to `address(this)` before burning them by sending the tokens to the zero address.

**Tools used:** Manual review

**Recommended mitigation:** Consider adding access control on the `SlashingHandler::handleSlashing` function so that it can only be called in the intended flow.
