# Vulnerability details

## Impact
The current implementation of the `createVault` function uses a predictable salt value for creating new vaults. Specially, the salt is derived from the operator's address, deposit token, and a nonce value that is incremented with each vault creation. This predictable pattern could potentially allow a malicious actor to front-run the transaction by observing the current state and submitting a similar transaction wit higher gas price. This vulnerability could lead to unauthorized vault creating and discruption in the intended operations of the protocol.

## Proof of Concept
```
bytes32 salt = keccak256(abi.encodePacked(operator, depositToken, self.vaultNonce++));
```
* The `self.vaultNonce` is predictable.
* An attacker monitoring the network can observe the current nonce value and predict the next salt.
* By submitting a similar transaction with a higher gas price, the attacker can front-run the original transaction, leading to potential misuse and exploitation.

## Tools Used
Manual code review.


## Recommended Mitigation Steps
```diff
+ bytes32 salt = keccak256(abi.encodePacked(operator, depositToken, self.vaultNonce++, block.timestamp));
```
By incorporating `block.timestamp`, the salt becomes significantly harder to predict, thereby reducing the probability of successful front-running attacks.
