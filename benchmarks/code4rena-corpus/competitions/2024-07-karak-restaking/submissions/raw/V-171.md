# Vulnerability details

## Impact

In the current implementation of the `Core` smart contract, anybody can register DSS with implemented IDSS interface. It should only be a smart contract and it has to assign max slashing percentage. So a malicious operator can create its own DSS with slashing percentage == 100% and register to any other DSS with any slashing percentage. The problem is that when another DSS will request slashing, a malicious operator can front-run the tx by requesting the slashing from its own DSS and slash everything by himself.

## Proof of Concept

1. Operator registers his own DSS with slashing percentage == 100%.
2. Operator stakes his vault to another DSS with any percentage.
3. When another DSS requests slashing, operator front-runs the tx by slashing himself

In this scenario, the second DSS can be DoSed. Additionally, currently slashing handlers functionality is not unified and it's mostly custom so this problem can impact the future functionality if the slashed funds are transferred to another account or DSS itself instead of being burnt.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Check whether the leveraging works correctly and the vault is staked correctly with correct slashing percentages: for instance, vault cannot be staked in the DSS with slashing percentage == 70% if it's already staked in such DSS with the same slashing percentage.
