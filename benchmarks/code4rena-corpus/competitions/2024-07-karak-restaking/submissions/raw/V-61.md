# Vulnerability details

## Impact
Operators could evade slashing by quickly unregistering from a DSS immediately after unstaking all their vaults. 

## Proof of Concept
According to the [ReadMe:](https://github.com/code-423n4/2024-07-karak?tab=readme-ov-file#operators)

```
The Operator is subject to a MIN_STAKE_UPDATE_DELAY of 9 days to prevent front-running a slashing event.
```

However, `Operator.sol` does not fully enforce this delay, particularly for the DSS unregistration process.

First of all, in `Constants.sol`, the delay is correctly defined:

```solidity
uint256 public constant MIN_STAKE_UPDATE_DELAY = SLASHING_WINDOW + SLASHING_VETO_WINDOW;
uint256 public constant SLASHING_WINDOW = 7 days;
uint256 public constant SLASHING_VETO_WINDOW = 2 days;
```

which makes the `MIN_STAKE_UPDATE_DELAY` = 9 days

The [`validateQueuedStakeUpdate`](https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/entities/Operator.sol#L89-L101) function in Operator.sol does enforce this delay for individual stake updates:

While this correctly enforces the delay for individual stake updates, including unstaking, it does not prevent an operator from unregistering from a DSS immediately after all vaults have been unstaked.

The [`unregisterOperatorFromDSS`](https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/entities/Operator.sol#L181-L202) function lacks any time-based check:

```solidity
function unregisterOperatorFromDSS(
        CoreLib.Storage storage self,
        IDSS dss,
        address operator,
        bytes memory unregistrationHookData
    ) external {
        State storage operatorState = self.operatorState[operator];
        // Checks if all operator delegations are zero
        address[] memory vaults = getVaultsStakedToDSS(operatorState, dss);
        if (vaults.length != 0) revert AllVaultsNotUnstakedFromDSS();
        if (!isOperatorRegisteredToDSS(self, operator, dss)) revert OperatorNotValidatingForDSS();

        self.operatorState[operator].dssMap.remove(address(dss));
        HookLib.callHookIfInterfaceImplemented({
            dss: dss,
            data: abi.encodeWithSelector(dss.unregistrationHook.selector, operator, unregistrationHookData),
            interfaceId: dss.unregistrationHook.selector,
            ignoreFailure: true, // So it can't prevent the operator from unregistering
            hookCallGasLimit: self.hookCallGasLimit,
            supportsInterfaceGasLimit: self.supportsInterfaceGasLimit,
            hookGasBuffer: self.hookGasBuffer
        });
```

This function only checks if all vaults are unstaked and if the operator is registered to the DSS. It does not enforce any delay after the last unstaking operation before allowing unregistration.

As a result, an operator could:
1. Initiate unstake requests for all their vaults, waiting the required 9 days for each if necessary.
2. Once all vaults are unstaked, immediately call `unregisterOperatorFromDSS`.
3. Successfully unregister from the DSS without any additional waiting period.

This sequence of actions could allow an operator to evade potential slashing if they become aware of an impending slashing event which contradicts the ReadMe.


## Tools Used
Manual review

## Recommended Mitigation Steps
Consider implementing a time-based check in the `unregisterOperatorFromDSS` function. This check should ensure that at least `MIN_STAKE_UPDATE_DELAY` (9 days) has passed since the last successful unstake operation for any vault associated with the DSS before allowing the operator to unregister. This can be achieved by introducing a new timestamp variable that records the time of the last unstake operation for each DSS an operator is registered with. The `unregisterOperatorFromDSS` function should then verify that this timestamp plus MIN_STAKE_UPDATE_DELAY is less than or equal to the current block timestamp before proceeding with the unregistration.
