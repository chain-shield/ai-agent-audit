# Vulnerability details

## Impact
This will result in incorrect balance calculations for most validator indices, leading to severe misrepresentations of validator balances throughout the protocol.



## Proof of Concept
Take a look at: https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/entities/BeaconProofsLib.sol#L114-L135

```solidity
function validateBalance(bytes32 balanceRoot, uint40 validatorIndex, BalanceProof calldata proof)
        internal
        view
        returns (uint256 validatorBalanceWei)
    {
        if (proof.proof.length != 32 * (BALANCE_HEIGHT + 1)) revert InvalidBalanceProof();

        uint256 balanceIndex = uint256(validatorIndex / 4);

        if (
            !Merkle.verifyInclusionSha256({
                proof: proof.proof,
                root: balanceRoot,
                leaf: proof.balanceRoot,
                index: balanceIndex
            })
        ) revert InvalidBalanceProof();

        /// Extract the individual validator's balance from the `balanceRoot`
        uint256 bitShiftAmount = (validatorIndex % 4) * 64;
        return uint256(fromLittleEndianUint64(bytes32((uint256(proof.balanceRoot) << bitShiftAmount)))) * 1 gwei;
    }
```

The problem lies in the left shift operation (`<<`) used to extract the balance. This operation shifts the desired bits out of the 64-bit range that `fromLittleEndianUint64` expects resulting in incorrect balance calculations.

To demonstrate:
1. For `validatorIndex = 0`, `bitShiftAmount = 0`, so the correct 64 bits are used.
2. For `validatorIndex = 1`, `bitShiftAmount = 64`, shifting all relevant bits out of range.
3. For `validatorIndex = 2`, `bitShiftAmount = 128`, again shifting all relevant bits out of range.
4. For `validatorIndex = 3`, `bitShiftAmount = 192`, once more shifting all relevant bits out of range.

This pattern repeats for all validator indices, resulting in correct calculations only when `validatorIndex % 4 == 0`.

This error further propagates to `NativeVaultLib.sol` especially in the [`validateSnapshotProof.sol` function:](https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/entities/NativeVaultLib.sol#L110-L144)

As seen above, `validateSnapshotProof` function calls `BeaconProofs.validateBalance`:

   ```solidity
   uint256 newBalanceWei = BeaconProofs.validateBalance(balanceRoot, validatorIndex, proof);
   ```
As a result, `newBalanceWei` will be incorrect for most validator indices (specifically, when `validatorIndex % 4 != 0`).

So this cause: 
   - Incorrect Balance Updates:
      ```solidity
      validatorDetails.restakedBalanceWei = newBalanceWei;
      ```
      This line updates the validator's restaked balance with an incorrect value.

   - Faulty Balance Change Detection:
      ```solidity
      if (newBalanceWei != prevBalanceWei) {
          emit ValidatorBalanceChanged(nodeOwner, nodeAddress, validatorIndex, timestamp, newBalanceWei);
          balanceDeltaWei = int256(newBalanceWei) - int256(prevBalanceWei);
      }
      ```
      This comparison and the resulting event emission and balance delta calculation will be based on incorrect values.

      The `balanceDeltaWei` returned by this function is used to update the node's overall balance. Incorrect values here will lead to misrepresentation of the node's total restaked ETH.

## Recommended Mitigation Steps
Replace the left shift operation with a right shift operation. This will make sure that the correct 64-bit chunk is passed to `fromLittleEndianUint64` for all validator indices.

