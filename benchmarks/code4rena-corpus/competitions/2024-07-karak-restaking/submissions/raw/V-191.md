# Vulnerability details

## Impact
Users can potentially avoid the slashing mechanism by transferring their shares to the vault, the user holds shares is record to `withdrawalMap`. If dss try to slash vault , user can withdraw assets before it. 

## Proof of Concept
Firstly, user can invoke [vault.sol::startRedeem](https://github.com/code-423n4/2024-07-karak/blob/main/src/Vault.sol#L125-L149) anytime, the shares which user hold transfer from user to vault
```solidity
function startRedeem(uint256 shares, address beneficiary)
    external
    whenFunctionNotPaused(Constants.PAUSE_VAULT_START_REDEEM)
    nonReentrant
    returns (bytes32 withdrawalKey)
{
    if (shares == 0) revert ZeroShares();
    if (beneficiary == address(0)) revert ZeroAddress();

    (VaultLib.State storage state, VaultLib.Config storage config) = _storage();
    address staker = msg.sender;

    uint256 assets = convertToAssets(shares);

    withdrawalKey = WithdrawLib.calculateWithdrawKey(staker, state.stakerToWithdrawNonce[staker]++);

    state.withdrawalMap[withdrawalKey].staker = staker;
    state.withdrawalMap[withdrawalKey].start = uint96(block.timestamp);
    state.withdrawalMap[withdrawalKey].shares = shares;
    state.withdrawalMap[withdrawalKey].beneficiary = beneficiary;

    this.transferFrom(msg.sender, address(this), shares);

    emit StartedRedeem(staker, config.operator, shares, withdrawalKey, assets);
}
```

After a period of 9 days, these shares become withdrawable, allowing users to withdraw them at their discretion. Although these shares can be called by anyone, users do not incur any asset loss during this process. They have the option to re-deposit these assets and repeat the aforementioned procedure. Consequently, users have a significant probability of evading the intended slashing penalties。

## Recommended Mitigation Steps
it is recommended to implement a comparative asset tracking mechanism. This system would record the asset value at the initiation of the redeem process (startRedeem) and compare it with the asset value at the conclusion of the redeem process (finishRedeem). The protocol should then utilize the lesser of these two values for final calculations
