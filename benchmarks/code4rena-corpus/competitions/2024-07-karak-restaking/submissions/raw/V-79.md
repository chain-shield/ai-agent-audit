# Vulnerability details

## Impact
Since most ERC20 tokens do not support transfers to the zero address, `SlashingHandler::handleSlashing()` will fail with a revert when trying to slash those tokens.

## Proof of Concept

The `SlashingHandler::handleSlashing()` function throws out a certain amount of ERC20-compatible tokens to zero address which will be out-of-circulation.

```solidity
    function handleSlashing(IERC20 token, uint256 amount) external {
        ... ...
        SafeTransferLib.safeTransfer(address(token), address(0), amount);
        ... ...
    }
```

But, Openzeppelin ERC20 and some most popular ERC20-compatible tokens like USDC and USDT do not allow transfers to zero address.

- Openzeppelin ERC20
```solidity
    function _transfer(address from, address to, uint256 value) internal {
        ... ...
        if (to == address(0)) {
            revert ERC20InvalidReceiver(address(0));
        }
        _update(from, to, value);
    }
```

- USDC
```solidity
    function _transfer(
        address from,
        address to,
        uint256 value
    ) internal override {
        ... ...
        require(to != address(0), "ERC20: transfer to the zero address");
        ... ...
    }
```

- The `transfer()` function of USDT does not validate the to parameter for the zero address. However, since the zero address (`address(0)`) is blacklisted in USDT contract, transfers to the zero address are not permitted.
