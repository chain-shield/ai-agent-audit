# Vulnerability details

## Bug description
> The [contest page](https://code4rena.com/audits/2024-07-karak-restaking#top) explicitly states that tokens that revert on transfer to the zero address are in scope.

DSS has the ability to slash the funds that operators have delegated if malicious behavior is noticed. 
In order for DSS to slash an operator, it must call `requestSlashing()` function of the Core contract. After `SLASHING_VETO_WINDOW` delay has passed, a slashing can be finalized by DSS.
During a call to `finalizeSlashing()` `slashAssets()` function of the vault will be invoked, where the vault will call the slashingHandler.
[Vault.sol#L193-L205](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/Vault.sol#L193-L205)
```solidity
 // Approve to the handler and then call the handler which will draw the funds
 SafeTransferLib.safeApproveWithRetry(
     asset(),
     slashingHandler,
     transferAmount
 );
 ISlashingHandler(slashingHandler).handleSlashing(
     IERC20(asset()),
     transferAmount
 );
```

slashingHandler will pull the funds from the vault and will try to send them to address(0), which will always revert for some of the tokens.
[SlashingHandler.sol#L52-L59](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/SlashingHandler.sol#L52-L59)
```solidity
function handleSlashing(IERC20 token, uint256 amount) external {
    if (amount == 0) revert ZeroAmount();
    if (!_config().supportedAssets[token]) revert UnsupportedAsset();
    SafeTransferLib.safeTransferFrom(
        address(token),
        msg.sender,
        address(this),
        amount
    );
    // Below is where custom logic for each asset lives
    SafeTransferLib.safeTransfer(address(token), address(0), amount);
}
```


## Impact
Slashing will be DoS'ed for some of the underlying tokens.

## Recommended Mitigation
Slashing logic for tokens reverting on transfer to the zero address must be changed.
