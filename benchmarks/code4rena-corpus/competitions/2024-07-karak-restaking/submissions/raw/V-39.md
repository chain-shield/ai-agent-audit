# Vulnerability details

## Impact
Due to a transfer to `address(0)` in the `handleSlashing` function, it will be impossible to slash vaults with assets that do not allow transfers to the zero address, for example USDC.

## Proof of Concept
As we can see in the `SlashingHandler.sol` `handleSlashing` function, in order to burn the slashed tokens, they are transferred to `address(0)`:

```solidity
SafeTransferLib.safeTransfer(address(token), address(0), amount);
```

This however is an issue as many tokens do not allow transfers to the zero address, for instance, USDC (this is code from the USDC implementation contract):
https://etherscan.io/address/0x43506849d7c04f9138d1a2050bbf3a0c054402dd#code#F14#L309
```solidity
function _transfer(
    address from,
    address to,
    uint256 value
) internal override {
    require(from != address(0), "ERC20: transfer from the zero address");
    //@audit Reverts on transfer to address(0)
    require(to != address(0), "ERC20: transfer to the zero address");
    require(
        value <= _balanceOf(from),
        "ERC20: transfer amount exceeds balance"
    );

    _setBalance(from, _balanceOf(from).sub(value));
    _setBalance(to, _balanceOf(to).add(value));
    emit Transfer(from, to, value);
}
```

It is also important to note that on the contest's page, it is directly stated that tokens that `Revert on transfer to the zero address` are `In scope`.

As a result, the `handleSlashing` function will revert, and some vaults will not be slashable.
