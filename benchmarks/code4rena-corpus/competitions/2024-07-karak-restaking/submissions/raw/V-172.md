# Vulnerability details

## Impact

In the current implementation of `Core` functionality, veto committee is supposed to put veto on the slashings that seem to be unfair. However, the problem is that the veto committee may be able to veto any time it wants after slashing request is created which can break the following invariant:

```
DSS can slash any malicious behavior occurring before the withdrawal initiation for up to 7 days.
```


## Proof of Concept

1. Let's say the DSS requested slashing and has waited for 2 days now it's able to slash during 7 days window according to the specification.

2. However, `cancelSlashing()` does not check whether the cancel operation is performed during `VETO_WINDOW` that allows to cancel anytime it wants:


https://github.com/code-423n4/2024-07-karak/blob/main/src/entities/SlasherLib.sol#L153-168
```
function cancelSlashing(CoreLib.Storage storage self, QueuedSlashing memory queuedSlashing) external {
        bytes32 slashRoot = calculateRoot(queuedSlashing);
        if (!self.slashingRequests[slashRoot]) revert InvalidSlashingParams();
        delete self.slashingRequests[slashRoot];
        IDSS dss = queuedSlashing.dss;

        HookLib.callHookIfInterfaceImplemented({
            dss: dss,
            data: abi.encodeWithSelector(dss.cancelSlashingHook.selector, queuedSlashing.operator),
            interfaceId: dss.cancelSlashingHook.selector,
            ignoreFailure: true,
            hookCallGasLimit: self.hookCallGasLimit,
            supportsInterfaceGasLimit: self.supportsInterfaceGasLimit,
            hookGasBuffer: self.hookGasBuffer
        });
    }
```

This effectively means that DSS may not have the whole 7 days to slash and the operation can be cancelled anytime during these 7 days.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Add the check to `cancelSlashing()` to make sure that `VETO_WINDOW` is still active and it's not interfere with actual slashing window.
