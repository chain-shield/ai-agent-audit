# Vulnerability details

The current `Vault.sol` contract includes slippage protection by specifying a minimum amount of shares to mint during deposits. However, it lacks a mechanism to set a deadline for these transactions, which can lead to exploits involving delayed transactions and slippage due to price changes.

When a transaction remains pending in the mempool for an extended period, it can be executed at an inopportune time, leading to significant slippage. This scenario is particularly dangerous for deposits and minting of shares, where the asset value may fluctuate.

```solidity
    function deposit(uint256 assets, address to, uint256 minSharesOut) // @audit not only slippage, they need deadline too
        external
        nonReentrant
        whenFunctionNotPaused(Constants.PAUSE_VAULT_DEPOSIT_SLIPPAGE)
        returns (uint256 shares)
    {
        if (assets == 0) revert ZeroAmount();
        shares = super.deposit(assets, to);
        if (shares < minSharesOut) revert NotEnoughShares();
    }
```

## Impact

The lack of a `deadline` for `deposit` and `mint` transactions allows them to remain pending in the mempool, becoming vulnerable to slippage and MEV attacks due to price fluctuations.

## Proof of Concept

1. Alice submits a transaction to deposit assets into the vault, specifying a minimum amount of shares to be minted to protect against slippage.
2. The transaction is submitted with a low gas fee and remains pending in the mempool.
3. While the transaction is pending, the price of the underlying asset changes significantly.
4. The minimum shares specified by Alice are now outdated due to the price change.
5. A MEV bot detects the pending transaction and takes advantage of the outdated slippage protection.
6. The bot manipulates the transaction to benefit from the price change, resulting in a significant loss for Alice.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Add slippage to the `mint` function and introduce a `deadline` parameter in the `deposit` and `mint` functions.
