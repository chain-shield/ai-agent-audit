# Vulnerability details

## Impact
User can completely escape being slashed in most cases.

## Proof of Concept
A user can continue creating multiple withdrawals (by calling the `startWithdrawal()` function) as his `withdrawableWei()` keeps increasing, and when a slashing occurs, he can frontrun this and withdraw his staked amount.

## Example (when 
1. Bob has 10ETH as withdrawableWei().
2. Bob creates a withdrawal with weiAmount = 10ETH
3. After 9 days (`MIN_WITHDRAWAL_DELAY`) this would mature, and Bob will be able to frontrun any future slashing event and completely withdraw his eth.
4. After a snapshot his withdrawableWei() increases by 5ETH
5. Bob can create another withdrawal with weiAmount = 5ETH, and be immune to slashing after 9 days.

The only scenario in which Bob is unable to escape slashing is when he is slashed within 9 days of starting a withdrawal which should be a rare occurrence since slashing is something that ideally happens rarely.

Do note that even though in this scenario, the amount in the validator can be slashed during withdrawal, this won't work if Bob's restaked eth is all present in the native node (by doing a fully withdrawal from the validator to the native node prior to the example given above) thus making it possible for anyone to do this attack.
## Tools Used
Manual
## Recommended Mitigation Steps
One way to mitigate this is to keep a time limit on how long a withdrawal can be kept open.
This can be done by adding the following check at line 277 in nativevault.sol:
`if (startedWithdrawal.start + Constants.MAX_WITHDRAWAL_TIME < block.timestamp)`
`revert MaxWithdrawableTimePassed();`
