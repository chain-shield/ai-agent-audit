# Vulnerability details

## Impact
In `Core.sol` the `finalizeUpdateVaultStakeInDSS` function calls `validateAndUpdateVaultStakeInDSS` where `finishUpdateStakeHook` is invoked. The issue is that `msg.sender` is set as the operator parameter, which will often be incorrect, as `finalizeUpdateVaultStakeInDSS` can be called by any address, even if they are not the operator.

As a result, the corresponding DSS will execute the `finishUpdateStakeHook` on the wrong address, which, depending on the hook implementation, may result in fund losses to the actual operator.

## Proof of Concept
Here we can see that `finishUpdateVaultStakeInDSS` can be called by anyone:
https://github.com/code-423n4/2024-07-karak/blob/a9658bccc884eb72538875c3940c6b507e06d4ca/src/Core.sol#L143

And here we see that `finishUpdateStakeHook` is supplied `msg.sender` instead of the operator:
https://github.com/code-423n4/2024-07-karak/blob/a9658bccc884eb72538875c3940c6b507e06d4ca/src/entities/Operator.sol#L126

It is also important to note that the same issue was found in the Karak Pro League audit, but is yet to be fixed. Furthermore, as the issue is not mentioned in the Known Issues, it should not be neglected.

## Recommended Mitigation Steps
In `validateAndUpdateVaultStakeInDSS` use the operator instead of `msg.sender`:
https://github.com/code-423n4/2024-07-karak/blob/a9658bccc884eb72538875c3940c6b507e06d4ca/src/entities/Operator.sol#L126
```solidity
HookLib.callHookIfInterfaceImplemented({
    dss: dss,
    data: abi.encodeWithSelector(dss.finishUpdateStakeHook.selector, queuedStakeUpdate.operator),
    interfaceId: dss.finishUpdateStakeHook.selector,
    ignoreFailure: true,
    hookCallGasLimit: self.hookCallGasLimit,
    supportsInterfaceGasLimit: self.supportsInterfaceGasLimit,
    hookGasBuffer: self.hookGasBuffer
});
```
