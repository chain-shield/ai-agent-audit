# Vulnerability details

## Impact
Permanent DOS of ```validateSnapshotProofs()```
Since ```validateSnapshotProofs()``` is required to update ```node.lastSnapshotTimestamp``` and freshness of ```node.lastSnapshotTimestamp```   is required for user to process a withdraw(offcos after slash deduction), DOS of validation leads to lock of user funds(balance).

## Proof of Concept
1. Slashing is a norm when vault operator behave maliciously, DSS can send in a slash request to slash such vault.
2. Slashing operates differently with NativeVault, since funds are on Beacon chain, totalAsset is reduced, so that NodeOwners shares will only be able to convert to less asset when trying to withdraw.
3. A day to NodeOwner snapshot expiry, user decides to exit Beacon, a process that involves full withdrawal of user stake, which requires an initial **[27hrs](https://eth2book.info/capella/part2/deposits-withdrawals/withdrawal-processing/#full-withdrawals:~:text=being%20continually%20skimmed.-,Full%20withdrawals,about%2027%20hours%20after%20making%20its%20way%20through%20the%20exit%20queue%2C,-but%20a%20slashed)**(provided that the validator have not been slashed in the past) lock period before withdrawal is processed and sent to NativeNode.
4. All an attacker needs to do is to monitor when validators exit Beacon, then time  a call to ```validateSnapshotProofs()``` 27hrs later(when withdrawal have been pushed and effective balance is zero, but yet to arrive in nativeNode...it could take 5days max, if all 576,000 are eligible for withdrawal....**[ref](https://eth2book.info/capella/part2/deposits-withdrawals/withdrawal-processing/#:~:text=If%20every%20validator%20were%20eligible%20for%20a%20withdrawal%2C%20and%20if%20the%20beacon%20chain%20is%20performing%20perfectly%2C%20then%20a%20full%20sweep%20of%20576%2C000%20validators%20would%20take%205%20days.%20That%20is%2C%20a%20validator%20could%20expect%20to%20receive%20a%20partial%20withdrawal%20payout%20every%205%20days.)**) with nodeOwner address so the node.balance is still zero and the blockRoot to be passed is one that has the validator balance as zero(process full withdrawal).

The root cause of this issue is the fact that when validators exit Beacon and consensus layer sent stake to Node, the balance difference when ``` validateSnapshotProofs()``` is called is equal to the entire stake that was withdrawn from Beacon, and ```_updateSnapshot()``` will require to burn an amount of shares equal to that stake from the NodeOwner shares.
5. Let assume a 50% slash from DSS, ```totalAssets``` becomes 16_ETH(assuming just one deposit),

## Recommended Mitigation Steps
Allow NodeOwners to restart snapshot if when a validator has exited to give room for accurate node.balance update. This will allow the NodeOwner in this attack to restart snapshot when node balance has been increase and ```totalDeltaWei``` can accurately cancel out to correctly. In this case ```32_ETH + (-32_ETH) = 0```

With no amount burnt, NodeOwner can burn 32e18 shares to withdraw 16e18_ETH after slash is withdrawn to the slashStore address.

Another option will be to observe change in node.balance and update snapshot.nodeBalanceWei before ```int256 totalDeltaWei = int256(snapshot.nodeBalanceWei) + snapshot.balanceDeltaWei;```
