# Vulnerability details

## Impact
Considering a case when a DSS uses a flashBot to request slashing from a Vault, and the transaction did go through before an innocent user(Alice) deposit calls go through, it means Alice's funds would be slashed as well even when the slashed amount does not include Alice funds(since it's a new deposit).

The reason this cannot be considered a user error is the fact that a slash request on the vault might be justifiable based on the operator's activity, what cannot be confirmed from the request is the amount currently in the vault as at the time of operator malicious activities, DSS might front-run a huge deposit with a valid slash request(one that is likely to be justified by veto committee). 

## Proof of Concept
Under normal circumstances, when a DSS requests the slashing of a vault, it goes through a waiting period of 2 days to give the veto committee the allowance to council slashing if need be, if not, the slashing is finalized and money is sent from the vault to the slashHandler for burning purpose.

Now, let us consider the case of a Vault_A that has 1,000_USDC as ```totalAsset``` and 1,000 as total shares/totalSuppy

If vault_A gets a slash request of 100%, this means when not canceled, 1,000_USDC(total assets) of the vault is moved to the slashHandler.

More so, the slashing process is protected against users that might want to game the system and run before slashing is finalized by queuing withdrawal for 7days 

Also, note that the amount to be slashed has been calculated in ```fetchEarmarkedStakes()```
``` solidity
   function fetchEarmarkedStakes(SlashRequest memory slashingMetadata)
        internal
        view
        returns (uint256[] memory earmarkedStakes)
    {
        earmarkedStakes = new uint256[](slashingMetadata.vaults.length);
        for (uint256 i = 0; i < slashingMetadata.vaults.length; ++i) {
            earmarkedStakes[i] = Math.mulDiv(
                slashingMetadata.slashPercentagesWad[i],
                IKarakBaseVault(slashingMetadata.vaults[i]).totalAssets(),
                Constants.MAX_SLASHING_PERCENT_WAD
            );
        }
    }
```
So, in this case, 100% of the asset which amounts to 1_000_USDC has been marked to be slashed.

If the slashing had been finalised before Alice's deposit, she would have minted ```(1000 *  1000+1) / 1 = 1,001,000 shares!``` and if any previous depositor(that had their funds slashed tries to withdraw, it will amount to zero asset ```(1000 * 1000+1) / (1,001,000 + 1000) = 0 asset! and reverted```

But in this case, since slash request have been placed directly before Alice deposit, 1,000 shares is minted to Alice. so vault has;
```
totalAsset = 2,000
totalSupply = 2,000
```
When slashing is finalized, the predetermined amount of 1,000 USDC is removed from the vault to leave the vault with 1,000_USDC and 2,000 shares, meaning Alice can only get 50% of her deposit without being involved in the slash request since previous shares remain there

## Recommended Mitigation Steps
When there is a slash request on a vault, a flag should be set and deposit should revert if there is a pending slash to be canceled/finalised.

1. Include a slashPending variable in Vault
```soldity
bool slashPending
```
2. Include a setter function in vault
```solidity
function setSlashPending(bool slashPendingRequest)
        external
        onlyCore
    {
        slashPending = slashPendingRequest;
    }
```
3. Appropriately set slashPending in ```requestSlashing()``` to true, in ```cancelSlashing()``` and ```finalizedSlashing()``` to false 

``` solidity
 function requestSlashing(
        CoreLib.Storage storage self,
        IDSS dss,
        SlashRequest memory slashingMetadata,
        uint256 nonce
    ) external returns (QueuedSlashing memory queuedSlashing) {
        validateRequestSlashingParams(self, slashingMetadata, dss);
        uint256[] memory earmarkedStakes = fetchEarmarkedStakes(slashingMetadata);
        queuedSlashing = QueuedSlashing({
            dss: dss,
            timestamp: uint96(block.timestamp),
            operator: slashingMetadata.operator,
            vaults: slashingMetadata.vaults,
            earmarkedStakes: earmarkedStakes,
            nonce: nonce
        });
        self.slashingRequests[calculateRoot(queuedSlashing)] = true;
        self.operatorState[slashingMetadata.operator].nextSlashableTimestamp[dss] =
            block.timestamp + Constants.SLASHING_COOLDOWN;
+++ //indicate that slash request is pending on each vault
+++ for (uint256 i = 0; i < slashingMetadata.vaults.length; i++) {
+++ IKarakBaseVault(queuedSlashing.vaults[i]).setSlashPending(true);
+++ }
        HookLib.callHookIfInterfaceImplemented({
            dss: dss,
            data: abi.encodeWithSelector(
                dss.requestSlashingHook.selector, slashingMetadata.operator, slashingMetadata.slashPercentagesWad
            ),
            interfaceId: dss.requestSlashingHook.selector,
            ignoreFailure: true,
            hookCallGasLimit: self.hookCallGasLimit,
            supportsInterfaceGasLimit: self.supportsInterfaceGasLimit,
            hookGasBuffer: self.hookGasBuffer
        });
    }
```
```solidity
    function cancelSlashing(CoreLib.Storage storage self, QueuedSlashing memory queuedSlashing) external {
```

```solidity
       function finalizeSlashing(CoreLib.Storage storage self, QueuedSlashing memory queuedSlashing) external {
        bytes32 slashRoot = calculateRoot(queuedSlashing);
        if (!self.slashingRequests[slashRoot]) revert InvalidSlashingParams();

            revert MinSlashingDelayNotPassed();

            hookCallGasLimit: self.hookCallGasLimit,
            supportsInterfaceGasLimit: self.supportsInterfaceGasLimit,
            hookGasBuffer: self.hookGasBuffer
```

4. Require that slashPending is false before depositing or minting in the vault.
