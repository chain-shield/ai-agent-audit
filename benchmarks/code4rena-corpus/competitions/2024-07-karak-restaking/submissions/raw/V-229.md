# Vulnerability details

## Impact
Any user staking in a vault can be slashed unfairly if for any reason the vault is paused by the manager or the owner before the users finish a redemption.

## Proof of Concept
In the karak system, the Operators can deploy vaults to allow the users/stakers to stake in these vaults and participate in the restaking system, then an operator can register in a DSS to earn rewards for doing the tasks the DSS requires from the operator, but this vault registered in a DSS can also be slashed if they fail in doing a task correctly.

the `Core.sol` contract allows any operator to deploy vaults, and then when users stake assets in these vaults, they can be registered in a DSS to earn rewards, the `Core.sol` contract also allows the operators or the owner to pause the vaults deployed, this can create an edge case where any user trying to redeem can get unfairly slashed while the vault is paused.

let's follow the next scenario:

1. An operator creates a vault using the `Core` contract.
2. Users stake assets in this vault.
3. Operator registers the vault in a DSS.
4. After some time some users start a redemption calling the `startRedeem` function in the vault.
5. During or after the `Withdrawal Delay Time` is over the manager pauses the vault.
6. Users try to redeem but they cannot do it because the `finishRedeem` function reverts because the vault is paused.
7. Some time passes and the vault gets slashed, because the core contract can slash a vault even when it is paused.
8.- Now the user lost assets and was unfairly slashed since he was trying to redeem before the slashing event passed.

Here I add a test to show the problem. this test can be added to vault.t.sol contract.

```solidity
    /**
     * TESTING AUDIT POINTS *********************
     */
    error EnforcedPauseFunction(uint8 functionIndex);

    function mintAndDeposit(uint256 amount, address user) public returns (uint256 shares) {
        depositToken.mint(user, amount);
        depositToken.approve(address(vault), amount);
        uint256 expectedShares = vault.convertToShares(amount);
        console.log("Expected shares: ", expectedShares);
        shares = vault.deposit(amount, user, expectedShares);
        console.log("minted shares: ", shares);
    }

    function test_startRedeem_PauseSlash_FinishRedeem() public {
        uint256 depositAmount = 10 ether;
        uint256 depositAmount2 = 5 ether;
        uint256 slashAmount = 2 ether;
        address user2 = address(2);
        // user 1 deposit to the vault
        console.log("User 1: ");
        mintAndDeposit(depositAmount, address(this));

        // user 2 deposit to the vault
        vm.startPrank(user2);
        console.log();
        console.log("User 2: ");
        mintAndDeposit(depositAmount2, user2);

        // After some time user 2 tries to redeem from the vault,
        uint256 shares2 = vault.balanceOf(user2);
        vault.approve(address(vault), shares2);
        bytes32 withdrawalKey2 = vault.startRedeem(shares2, user2);
        console.log("Shares to withdraw : ", shares2);
        vm.stopPrank();

        // Now, the withdrawal delay is over, so the user can finish the redemption
        vm.warp(Constants.MIN_WITHDRAWAL_DELAY + 1);

        // but before the user can finish the redemption process the manager/owner decides to pause the vault for any reason
        core.pauseVault(IKarakBaseVault(vault), type(uint256).max);

        // assets the user should get after finishing the redemptions.
        console.log();
        uint256 expectedAssets2 = vault.convertToAssets(shares2);
        console.log("Fair Expected Assets for User 2: ", expectedAssets2);

        // Now the user can't finish the redemption.
        vm.prank(user2);
        vm.expectRevert(abi.encodeWithSelector(EnforcedPauseFunction.selector, 4));
        vault.finishRedeem(withdrawalKey2);

        //Then some time passes and the vault gets slashed, even when the vault is still paused,
        // and the user couldn't finish the redemption.
        vm.warp(25 days);
        depositToken.burn(address(vault), slashAmount);

        // The user loses assets unfairly because he can finish the redemption when he wants it due to the paused vault.
        uint256 expectedAssets_afterSlash = vault.convertToAssets(shares2);
        console.log("expected Assets After unfair Slash User 2: ", expectedAssets_afterSlash);
    }
```

## Recommended Mitigation Steps
it's difficult to make a specific recommendation for this, because this depends on what the protocol wants to do in these cases, but maybe the protocol should allow the withdrawal of assets from stakers that shouldn't be penalized even when a vault is paused, or if the owner of the core protocol pauses the vault maybe the slash assets function in the vault should be pause too.
