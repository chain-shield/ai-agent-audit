# Vulnerability details

## Impact

Due to the incorrect resetting of `withdrawalMap[withdrawalKey]`, a malicious user can repeatedly call [`NativeVault::finishWithdrawal()`](https://github.com/code-423n4/2024-07-karak/blob/main/src/NativeVault.sol#L262) with the same `withdrawalKey` to withdraw all their assets, effectively bypassing the `MIN_WITHDRAWAL_DELAY`.



## Proof of Concept

In the M-1 of the [Renascence report](https://github.com/code-423n4/2024-07-karak/blob/main/audits/eth-native-restaking/Renascence%20-%20Karak%20Native%20Restaking%20Audit%20Report.pdf) the following fix was implemented to reset the `withdrawalMap[withdrawalKey]` storage:

```diff
_decreaseBalance(startedWithdrawal.nodeOwner, startedWithdrawal.assets);
        INativeNode(node.nodeAddress).withdraw(startedWithdrawal.to, startedWithdrawal.assets);
        node.withdrawableCreditedNodeETH -= startedWithdrawal.assets;

+        delete self.withdrawalMap[withdrawalKey];
```

The issue is that `withdrawalMap` is a nested mapping in the [`Storage struct`](https://github.com/code-423n4/2024-07-karak/blob/main/src/entities/NativeVaultLib.sol#L90) and will not be reset this way. The `delete` operation does not traverse nested mappings as it lacks key set information.

Thus, the fix in the [Renascence report](https://github.com/code-423n4/2024-07-karak/blob/main/audits/eth-native-restaking/Renascence%20-%20Karak%20Native%20Restaking%20Audit%20Report.pdf) has introduced a new issue that needs to be mitigated.
