# Vulnerability details


## Proof of Concept

Take a look at https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/entities/Operator.sol#L111-L133

```solidity
    function validateAndUpdateVaultStakeInDSS(CoreLib.Storage storage self, QueuedStakeUpdate memory queuedStakeUpdate)
        external
    {
        State storage operatorState = self.operatorState[queuedStakeUpdate.operator];
        validateQueuedStakeUpdate(operatorState, queuedStakeUpdate);
        updateVaultStakeInDSS(
            operatorState,
            queuedStakeUpdate.updateRequest.vault,
            queuedStakeUpdate.updateRequest.dss,
            queuedStakeUpdate.updateRequest.toStake
        );
        delete operatorState.pendingStakeUpdates[queuedStakeUpdate.updateRequest.vault];
        IDSS dss = queuedStakeUpdate.updateRequest.dss;
        HookLib.callHookIfInterfaceImplemented({
            dss: dss,
            data: abi.encodeWithSelector(dss.finishUpdateStakeHook.selector, msg.sender),
            interfaceId: dss.finishUpdateStakeHook.selector,
            ignoreFailure: true,
            hookCallGasLimit: self.hookCallGasLimit,
            supportsInterfaceGasLimit: self.supportsInterfaceGasLimit,
            hookGasBuffer: self.hookGasBuffer
        });
    }
```

This function is used to validate and then update the vault stake in the DSS, issue here is that the `ignoreFailure` bool is set to `true`, but unlike in the [Operator#unregisterOperatorFromDSS()](https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/entities/Operator.sol#L198) where this is done to ensure an operator is not prevented from unregistering, here the application is wrong, cause before using the `HookImplementation` to call the `dss.finishUpdateStakeHook`, the queued stake update requests for the vaults are deleted [here](https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/entities/Operator.sol#L122), which would then cause that if the query to the `dss.finishUpdateStakeHook.selector` fails in the interface implementation fails, since `ignoreFailure` has been set to `true` then the tx would not revert as can be seen here https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/entities/HookLib.sol#L68.

## Impact

In the case where the call to `dss.finishUpdateStakeHook.selector` fails the already queued stake update requests for the vaults would be left deleted.

> Additional Note: There is a similar logical case in the _SlasherLib.sol_, where the slash roots are deleted and the call to the DSS to [finish the slashing](https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/entities/SlasherLib.sol#L146) or [cancel the slashing](https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/entities/SlasherLib.sol#L163) could fail _(the failure could be due to any reason, for e.g per the readMe for the contest we are to expect tokens that revert on transfer to the `0x0` to be supported, now slashing these tokens would revert [here](https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/SlashingHandler.sol#L58), (however this would not be logged cause the `ignoreFailure` has been set to `true`)_, so consider fixing these too to ensure a deletion only occur when a tx was in-fact successful.

## Recommended Mitigation Steps

Consider not having the `ignoreFailure` as `true` and only delete the queued stake update requests if the call to the DSS is not successful.
