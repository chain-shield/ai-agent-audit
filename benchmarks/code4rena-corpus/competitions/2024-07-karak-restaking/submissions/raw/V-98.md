# Vulnerability details

## Impact
**`deposit()`** is used to deposit tokens and mint the corresponding shares. However, the problem arises with fee-on-transfer tokens (which are within the scope of the contest specifications). These tokens deduct a percentage during the transaction, resulting in a smaller actual deposit in the vault. Despite this, the vault uses the full amount to mint shares, causing an over-minting of shares. This discrepancy can be exploited to mint more shares than intended.
## Proof of Concept
**`deposit()`** is implemented as follows:
```Solidity
function deposit(uint256 assets, address to)
        public
        override(ERC4626, IVault)
        whenFunctionNotPaused(Constants.PAUSE_VAULT_DEPOSIT)
        nonReentrant
        returns (uint256 shares)
    {
        if (assets == 0) revert ZeroAmount();
        return super.deposit(assets, to);
    }
```
As you can see, it calls the [deposit()](https://github.com/Vectorized/solady/blob/1f43cc8005cc3b3c8361dd7dbdd2cdeaf0f99e66/src/tokens/ERC4626.sol#L376) from the Solady ERC4626 contract.
```Solidity
function deposit(uint256 assets, address to) public virtual returns (uint256 shares) {
        if (assets > maxDeposit(to)) _revert(0xb3c61a83); // `DepositMoreThanMax()`.
@>      shares = previewDeposit(assets);
        _deposit(msg.sender, to, assets, shares);
    }

function _deposit(address by, address to, uint256 assets, uint256 shares) internal virtual {
        SafeTransferLib.safeTransferFrom(asset(), by, address(this), assets);
@>      _mint(to, shares);
        /// @solidity memory-safe-assembly
        assembly {
            // Emit the {Deposit} event.
            mstore(0x00, assets)
            mstore(0x20, shares)
            let m := shr(96, not(0))
            log3(0x00, 0x40, _DEPOSIT_EVENT_SIGNATURE, and(m, by), and(m, to))
        }
        _afterDeposit(assets, shares);
    }
```
As you can see, it uses the pre-fee amount to calculate the shares, resulting in the minting of more shares than it should.

Here's an example to illustrate the impact of this issue:

A **`deposit(10000)`** should result in the same shares as two deposits of **`deposit(5000)`** but it does not because amount is the pre-fee amount. Assume a fee-on-transfer of 20%. Assume current **`totalAmount = 10000`**, **`totalShares = 10000`** for simplicity.

**`deposit(10000) = 10000 / totalAmount * totalShares = 1000 shares`**
**`deposit(5000) = 5000 / totalAmount * totalShares = 5000 shares`**. Now the **`totalShares`** increased by 5000 but the **`totalAssets`** only increased by **`(100% - 20%) * 500 = 4000`**. Therefore, the second **`deposit(5000) = 5000 / (totalAmount + 4000) * (newTotalShares) = 5000 / (14000) * 15000 = 5357.14286 shares`**.

In total, the two deposits lead to **`357`** more shares than a single deposit of the sum of the deposits. This discrepancy can be exploited to mint more shares than intended.
## Tools Used
Manual review.
## Recommended Mitigation Steps
**`assets`** should be the amount excluding the fee, i.e., the amount the contract actually received. This can be done by subtracting the pre-contract balance from the post-contract balance.
