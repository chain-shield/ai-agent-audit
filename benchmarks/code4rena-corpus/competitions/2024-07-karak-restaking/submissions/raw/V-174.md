# Vulnerability details

## Impact

In the current implementation of the `Core` functionality, only operator can unregister himself from the DSS as `msg.sender` inside of `unregisterOperatorFromDSS` is operator. However, this goes in deviation with the specification regarding jailing implementation:

```
Jailing: Operators can be jailed by the DSS arbitrarily usually valid reasons like if they are too overleveraged for a DSS' liking
The effects of jailing are also arbitrary and can be decided by the DSS. This can range from no rewards to not allowing the operator to perform any tasks and forcing them to unallocate from the DSS. Jailing is optional and is implemented inside the DSS contract and not the core contract.
```

## Proof of Concept

Currently DSS cannot force an operator to unallocate from it as DSS is not the `msg.sender`:

https://github.com/code-423n4/2024-07-karak/blob/main/src/Core.sol#L113-118
```
 function unregisterOperatorFromDSS(IDSS dss, bytes memory unregistrationHookData)
        external
        nonReentrant
        whenFunctionNotPaused(Constants.PAUSE_CORE_UNREGISTER_FROM_DSS)
    {
        address operator = msg.sender;
```

So operator's vault can be staked inside of DSS whenever he wants even if the vault has no funds for slashing. This may put significant burden on DSS functionality as the operator will be in the system and still it'd not be possible to slash him. Therefore, such implementation where DSS cannot force operator to unallocate from it goes with deviation with the described intended behavior.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Add a function like `forceUnregisterOperatorFromDSS()` so that DSS can unregister operator itself in case of jailing.
