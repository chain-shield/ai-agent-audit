# Vulnerability details

## Impact
1. Updating the state the of node (`startSnapshot`) would be close to impossible, and the impact can be worse in case of frequent slashing.

2. `nodeOwners` minting  after the slashing will have more shares than they should, like 100e18 deposited will mint them 101e18 approx each, meaning even after vault has been slashed (ETH out of node) will have the vault being slashed again anytime any of these `nodeOwners` tries updating their balances(startSnapshort).

This will allow the vault to loss more ETH than it should.

## Bug Description
When a vault is slashed, the emulation of the slashed assets will occur in the [slashAssets](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/NativeVault.sol#L315) function
```solidity
function slashAssets(uint256 totalAssetsToSlash, address slashingHandler)
        external
        onlyOwner
        nonReentrant
        whenFunctionNotPaused(Constants.PAUSE_NATIVEVAULT_SLASHER)
        returns (uint256 transferAmount)
    {
        NativeVaultLib.Storage storage self = _state();

        if (slashingHandler != self.slashStore) revert NotSlashStore();

        // avoid negative totalAssets if slashing amount is greater than totalAssets
        if (totalAssetsToSlash > self.totalAssets) {
            totalAssetsToSlash = self.totalAssets;
        }

>        self.totalAssets -= totalAssetsToSlash;
        emit Slashed(totalAssetsToSlash);
        return totalAssetsToSlash;
    }
```

But there exist a bug where a `nodeOwner` cannot  start a [snapShort](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/NativeVault.sol#L112), this is due to the implementation of the protocol.

## Proof Of Concept

When a `validator` or the `node operator` himself deposits (validateWithdrawalCredentials pointing to the node address) into the vault, the `solady's`  [fullMulDiV](https://github.com/Vectorized/solady/blob/1f43cc8005cc3b3c8361dd7dbdd2cdeaf0f99e66/src/utils/FixedPointMathLib.sol#L439) calculation would be used, which is from the [_increaseBalance](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/NativeVault.sol#L203) to issue the initial share.

```solidtiy
uint256 o = _decimalsOffset();
        if (o == 0) {
            return FixedPointMathLib.fullMulDiv(assets, totalSupply() + 1, _inc(totalAssets()));
```

consider this:

* Alice restake 100 ETH to a nodeOwner (lets call the nodeOwner MUSA)
* now 100e18 shares would be minted to `MUSA` since thats the initial deposit
* Now the `totalAssets` is now 100e18 and `totalSupply()` also.
* Another 20 nodeOwners have validators staked the same 100e18 to each.
* The `totalAssets` and `totoalSupply()` are  now 2000e18
* The operator now did something malicious and have his vault [slashed](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/NativeVault.sol#L299) lets say 20e18
* Now MUSA (the node owner) wants to update  the node balance and call the [startSnapShort](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/NativeVault.sol#L112) and it turns out that `alice` had withdrawn his stakes (100e18)
* The [_decreaseBalance](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/NativeVault.sol#L507) will now be called because the balance is negative(alice unstakes)

The call will now revert because `totalAssets` is now 1980e18 ( minus the slahsed) while the `totalSupply()` is still `2000e18`

This is because when the `previewWithdraw` is called, it  calculates the shares to burn like this:
```solidity
uint256 o = _decimalsOffset();
        if (o == 0) {
            return FixedPointMathLib.fullMulDivUp(assets, totalSupply() + 1, _inc(totalAssets()));
        }
```
making the shares
```solidity 
100e18 * 2000e18 + 1  / 1980e18 + 1 = around `101009591115598182735`
```

This will revert because there's no that amount of shares to  the node owner (`MUSA`), his amount is `100e18`

## Recommended Mitigation Steps

This can be mitigated by burning the same amount of `shares` that was slashed from the vault, the call to [_transfertoSlashStore](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/NativeVault.sol#L425) should be the best place for that to happen or immediately after slashing

A lot of thought should be put in finding the right place to burn the slashed shares.
