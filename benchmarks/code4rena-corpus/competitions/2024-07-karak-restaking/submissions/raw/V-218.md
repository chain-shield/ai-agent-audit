# Vulnerability details

## Impact

The access control of [allowlistAssets](https://github.com/code-423n4/2024-07-karak/blob/main/src/Core.sol#L85-L91) in [Core](https://github.com/code-423n4/2024-07-karak/blob/main/src/Core.sol) can be bypassed if a user creates a smart contract and calls the function directly from `CoreLib`. This allows anyone to add or remove assets from the `allowlist`.

## Proof of Concept

In the contract [Core](https://github.com/code-423n4/2024-07-karak/blob/main/src/Core.sol) the user is able to stake/unstake a restaking vault to a DSS, with the manager controlling which assets can be used for vault creation. The Manager/Owner can call [allowlistAssets](https://github.com/code-423n4/2024-07-karak/blob/main/src/Core.sol#L85-L91) in order to update the allowlist, where the modifier `onlyRolesOrOwner` makes sure only allowed users can call the function. Its main functionality is calling the function [allowlistAssets](https://github.com/code-423n4/2024-07-karak/blob/main/src/entities/CoreLib.sol#L67-L75) from [CoreLib](https://github.com/code-423n4/2024-07-karak/blob/main/src/entities/CoreLib.sol) - where the first parameter `self` is the most important one, as it specifies the storage slot where the Core's storage is located. The needed value is already initialized as a constant in the contract as [STORAGE_SLOT](https://github.com/code-423n4/2024-07-karak/blob/main/src/Core.sol#L39), which can just be copy-pasted by the user once the [Core](https://github.com/code-423n4/2024-07-karak/blob/main/src/Core.sol) contract is deployed.

An issue arises due to [allowlistAssets](https://github.com/code-423n4/2024-07-karak/blob/main/src/entities/CoreLib.sol#L67-L75)’s visibility being external in `CoreLib`, which would allow anyone to call the function by simply deploying their own smart contract as such:

```solidity
import "./CoreLib.sol";

contract MyContract {
    address public coreLibAddress;
    CoreLib.Storage coreLibStruct;

    constructor(address _libraryAddress) {
        coreLibAddress = _libraryAddress;
    }

    function selfStorage() internal pure returns (CoreLib.Storage storage coreLibStruct) {
      // Here's where the CoreLib.Storage struct will get filled 
      // once the malicious user reads the state all of the needed storage slots
    }

    function updateAllowList(address[] memory assets, address[] memory slashingHandlers) public view returns (uint256) {
        coreLibAddress.allowList(selfStorage(), assets, slashingHandlers);
    }
}
```

The flow of the attack will roughly look like this:
- A malicious user creates their own smart contract
- Then they will copy the value of `STORAGE_SLOT` and the address of `CoreLib` 
- After that they will use web3.js, truffle (and possibly foundry/remix) to get the value of the `Storage` struct of `CoreLib`
- The last step is to call `updateAllowList`  and set the assets/slashingHandlers as they wish.

### Coded Poc

This coded [PoC](https://gist.github.com/Vancelott/8ce9c4d42ea4e3b55aee73da4285764b) will demonstrate the issue better - the test has to simply be placed in `test/core/operatorCRUD.t.sol`

Please note that this is not a centralization issue, as there's no access control implemented for the function, in the library `CoreLib`, in the first place.

## Recommended Mitigation Steps

After speaking briefly with the sponsor, I learned that some of the library's functions were made external in order for the library to be deployed separately from the `Core` contract, otherwise the size limit of the `Core` contract is reached. That is why my suggestion is to add an additional parameter to [allowlistAssets](https://github.com/code-423n4/2024-07-karak/blob/main/src/entities/CoreLib.sol#L67-L75) that checks the caller's address to see if they are a Manager or Owner. Another way to mitigate the issue is to refactor that function specifically, so that it can be an internal one.
