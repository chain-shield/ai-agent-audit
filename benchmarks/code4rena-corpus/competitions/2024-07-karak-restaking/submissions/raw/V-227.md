# Vulnerability details

## Impact
In Native Restaking, users `totalRestakedETH` can be reduced prematurely thus reducing his potential rewards.

## Proof of Concept
After a slashing is done on the native vault, the slashed amount is collected from the users according to how much ETH is present in their native nodes, and the rest is collected in the following snapshots when their balance increases. 

But an attacker can transfer the entire supposed "slashed_amount" of the user to him via the requestOwnershipHandover() function in Ownable.sol that the NativeNode contract is inheriting. This would cause the `totalRestakedETH` amount to be reduced by the entire "slashed_amount".

# Path
Assume the following scenario
1. Bob has `totalRestakedETH = 32 ETH`, amounting to 50% of the totalAssets, and 0ETH as node.balance (in his nativenode)

2. The NativeVault is slashed for 20ETH, which means Bob must be slashed 10ETH

# Scenario 1 (No attack)
3. Bob calls the `startSnapshot()` function, and the function doesnt transfer anything to the slashstore since his node.balance = 0. Which means Bobs reward until next snapshot will be calculate with `totalRestakedETH = 32 ETH` since `slashedWithdrawable = 0`.

# Scenario 2 (attack)
3. A malicious attacker transfers 10ETH to bobs native node by calling the `requestOwnershipHandover()` payable function in the Ownable contract which native node is inheriting. 

4. Bob calls the `startSnapshot()` function, and since his node.balance = 10ETH, this 10ETH is transferred to the slashstore, and `totalRestakedETH = 22 ETH` will be updated. So till the next snapshot Bob's rewards will be calculated with a lesser `totalRestakedETH`.

This can be used by malicious attackers to reduce the potential rewards earned by users.
(Note: A user can also increase his own potential rewards without staking eth using this method)

## Tools Used
Manual

## Recommended Mitigation Steps
One way to mitigate this bug is to override the `requestOwnershipHandover()` function and make it a non payable function.
