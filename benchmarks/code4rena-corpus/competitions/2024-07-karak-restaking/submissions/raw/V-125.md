# Vulnerability details

## Impact
NodeOwners lose partial/full remaining stake after NativeVault suffers a slash request

## Proof of Concept
1. Native node is deployed on a NativeVault
2. One withdraw credentials was verified with the node.
3. ```node.lastSnapshotTimestamp``` is updated to the current time after ```validateSnapshotProofs()``` is called.
4. Few days after ```node.lastSnapshotTimestamp```, Node owner observed a slash request of 50% on the vault and decided to exit the validator on beacon.
5. After exiting on beacon, stakes are locked for about 27hrs before being pushed to withdraw queue.
6. Node owner waited to call ```startSnapshot()``` after withdrawal arrived, so that slash funds can be transferred to slash store.
7. Funds arrive to native node, node owner calls ```startSnapshot()``` and ``` _startSnapshot()``` is triggered.
8. In ``` _startSnapshot()```, ```_transferToSlashStore(nodeOwner)``` is triggered.
9. In ```_transferToSlashStore(nodeOwner)```, slash assets of node is computed to be the difference between the original restakedEth of the node which is 32_ETH, and what the shares now worth, which is 16_ETH ```32 - 16 = 16```
10. ```slashedWithdrawable``` is then computed to be the minimum between ```slashedAsset``` and node balance(which is 32_ETH atm!) ```min(32, 16) = 16```
11. ```slashedWithdrawable``` is then withdrawn from node to slash store
12. By now, node.balance is now 16_ETH
13. When flow is returned to ``` _startSnapshot()``` where ``` nodeBalanceWei``` is computed to be the difference between ```node.nodeAddress.balance``` which is now 16_ETH and ``` node.withdrawableCreditedNodeETH```(which could be assume to be zero considering that no previous reward update yet) ```16 - 0 = 16```
14. ```node.snapshot``` was then updated with 16_ETH as ``` nodeBalanceWei```

## Recommended Mitigation Steps
Add ```paidSlashAmount``` in snashot struct, increase it when node transfers to slash store inside ```_transferToSlashStore(nodeOwner)```, then deduct paidSlashAmount from total amount available to withdraw.
```solidity
    function _startSnapshot(NativeVaultLib.NativeNode storage node, bool revertIfNoBalanceChange, address nodeOwner)
        internal
    {
        if (node.currentSnapshotTimestamp != 0) revert PendingIncompleteSnapshot();

        // Sweep slashed ETH from node balance before locking in snapshot node balance.
        // This allows all the ETH that was theoritically slashed in `slashAssets` function call can be moved to a slash store,
        // which can decide what to do with this slashed ETH.
---        _transferToSlashStore(nodeOwner);

        // Calculate unattributed node balance
+++    uint256 nodeBalanceWei;
+++    if( node.nodeAddress.balance > node.withdrawableCreditedNodeETH ) {
+++         nodeBalanceWei = node.nodeAddress.balance - node.withdrawableCreditedNodeETH;
+++    }
+++        _transferToSlashStore(nodeOwner);
```
```solidity
 ---  node.withdrawableCreditedNodeETH += snapshot.nodeBalanceWei;
 +++  node.withdrawableCreditedNodeETH += snapshot.nodeBalanceWei - snapshot.paidSlashAmount;
```

The fix above ensures;
1. ```totalDeltaWei``` will be adequately updated, zero in this case and no share is burnt.
2. slashed funds is sent to slash store
3. Node owner withdraws correct balance, in this case converting 32 shares give 16_ETH
