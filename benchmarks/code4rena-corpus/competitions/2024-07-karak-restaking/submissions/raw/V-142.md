# Vulnerability details

## Impact
Slashing can be DoSed for fee on transfer Tokens
According to the context readMe Fee on transfer tokens are in scope for this audit.
In [SlashingHandler.handleSlashing(IERC20, uint256)](https://github.com/code-423n4/2024-07-karak/blob/a9658bccc884eb72538875c3940c6b507e06d4ca/src/SlashingHandler.sol#L52-L59) , amount of tokens are slashed . This function is called by the vault after approval inside [slashAssets(uint256,address)](https://github.com/code-423n4/2024-07-karak/blob/a9658bccc884eb72538875c3940c6b507e06d4ca/src/Vault.sol#L193-L205) Slashing involve transferring tokens from the vault and then burning them.
However, for fee on transfer tokens slashing can be DoSed resulting in an inhability of 
the DSS to slash any amount of token.

## Proof of Concept
Consider a scenario where the DSS want to slash a vault, DSS call **slashAssets()** which approve the SlashingHandler and calls **handleSlashing()**, inside this function amount to slash is transferred from the vault to the **SlashingHandler** contract and then burned (this is assuming thje DSS is using the current implementation of the SlashingHandler, and even if they are using their own implementation internal accounting can, be messed up if they do not implement the fix recommanded).
In this case if the token to transfer is a fee on transfer token, the accounting of the amount transferred will be messed up after transferring from the vault. Essentially if the fee on transfer percentage is 10% and the **SlashingHandler** is transferring 100 token from the vault, it will receive only 90 tokens. In the next step when attempting to burn 100 tokens, the transaction will revert because the **SlashingHandler** do not have enough tokens to burn.
Lets see the code for slashing the assets.
```solidity
function  handleSlashing(IERC20 token, uint256 amount) external {

if (amount ==  0) revert  ZeroAmount();

if (!_config().supportedAssets[token]) revert  UnsupportedAsset();

  

SafeTransferLib.safeTransferFrom(address(token), msg.sender, address(this), amount);

// Below is where custom logic for each asset lives

SafeTransferLib.safeTransfer(address(token), address(0), amount);

}
```
At this line: [SafeTransferLib.safeTransferFrom(address(token), msg.sender, address(this), amount);](https://github.com/code-423n4/2024-07-karak/blob/a9658bccc884eb72538875c3940c6b507e06d4ca/src/SlashingHandler.sol#L56)
assets are trabsferred from the v ault to the SlashingHandler and if there is a fee, only the amount after fee will be transferred to the SlashingHandler. In the next line of code [SafeTransferLib.safeTransfer(address(token), address(0), amount);](https://github.com/code-423n4/2024-07-karak/blob/a9658bccc884eb72538875c3940c6b507e06d4ca/src/SlashingHandler.sol#L58) the amount transferred is burned without checking if the exact amount have been received or not. This transaction will revert because the SlashingHandler  does not have enough token to burn. The consequence as the title of this report says is a complete DoS of slashing for fee on transfer tokens.

## Recommended Mitigation Steps
Only burn the effective amount of tokens that the SlashingHandler receive from the vault. One way to do so is like this:
```diff
function  handleSlashing(IERC20 token, uint256 amount) external {

if (amount ==  0) revert  ZeroAmount();

if (!_config().supportedAssets[token]) revert  UnsupportedAsset();

  
+uint256 balBefore = address(token).balanceOf(address(this));
SafeTransferLib.safeTransferFrom(address(token), msg.sender, address(this), amount);
+uint256 balReceivedToBurn = address(token).balanceOf(address(this)) - balBefore;

// Below is where custom logic for each asset lives

-SafeTransferLib.safeTransfer(address(token), address(0), amount);
+SafeTransferLib.safeTransfer(address(token), address(0), balReceivedToBurn);

}
```
