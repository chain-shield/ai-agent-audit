# Vulnerability details

## Impact
The redeem process consists of two stages:
1. Vault.startRedeem()
2. Vault.finishRedeem()

After running the Vault.startRedeem() function, the user starts the "redeem" process. It performs the transfer:
this.transferFrom(msg.sender, address(this), shares);
https://github.com/code-423n4/2024-07-karak/blob/main/src/Vault.sol#L146

## Proof of Concept
However, after the delay and call of the finishRedeem() function, a check is triggered:
if (shares > maxRedeem(address(this))) revert RedeemMoreThanMax();
https://github.com/code-423n4/2024-07-karak/blob/main/src/Vault.sol#L167

If this check fails, the user will lose their funds. They will not be able to call the _withdraw() function and have already transferred their share to https://github.com/code-423n4/2024-07-karak/blob/main/src/Vault.sol#L146.

## Tools Used
Manual review

## Recommended Mitigation Steps
Provide the ability to return shares to the user or refuse the two-step withdrawal.
