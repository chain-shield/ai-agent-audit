# Vulnerability details

The `NativeVault` contract allows users to start a withdrawal request using the `startWithdrawal` function, specifying the recipient address and the amount of ETH to withdraw. This function records the withdrawal request details, including the start timestamp, in the `withdrawalMap` mapping.

To complete a withdrawal, the `finishWithdrawal` function is called with the corresponding `withdrawalKey`. This function is supposed to enforce a minimum withdrawal delay, ensuring that a certain amount of time has passed since the withdrawal request was started before allowing it to be finished.

However, the current implementation of `finishWithdrawal` does not properly enforce the minimum withdrawal delay. The issue lies in the following lines: [#L272-L274](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/NativeVault.sol#L272-L274)

```solidity
if (startedWithdrawal.start + Constants.MIN_WITHDRAWAL_DELAY > block.timestamp) {
    revert MinWithdrawDelayNotPassed();
}
```

The condition `startedWithdrawal.start + Constants.MIN_WITHDRAWAL_DELAY > block.timestamp` is incorrect. It allows the withdrawal to be finished if the current timestamp exceeds the start timestamp plus the minimum withdrawal delay. However, this condition should be reversed to ensure that the minimum withdrawal delay has passed before the withdrawal is finished.

_As a result, an attacker can bypass the withdrawal delay enforcement by calling `finishWithdrawal` immediately after starting a withdrawal request, effectively allowing them to withdraw funds without waiting for the intended delay period._

## Impact

The incorrect withdrawal delay enforcement in `finishWithdrawal` allows users to bypass the minimum withdrawal delay and withdraw funds immediately after starting a withdrawal request. This violates the intended behavior of the contract and can lead to premature withdrawal of funds, potentially impacting the contract's liquidity and the expected time-lock on withdrawals.

## Proof of Concept

1. User starts a withdrawal request by calling `startWithdrawal`, specifying the recipient address and the amount of ETH to withdraw.
2. The `startWithdrawal` function records the withdrawal request details, including the start timestamp, in the `withdrawalMap` mapping.
3. Immediately after starting the withdrawal request, the user calls `finishWithdrawal` with the corresponding `withdrawalKey`.
4. Due to the incorrect condition in `finishWithdrawal`, the function allows the withdrawal to be finished without enforcing the minimum withdrawal delay.
5. The user successfully withdraws the funds without waiting for the intended delay period.

## Recommended Mitigation Steps

Update the condition in `finishWithdrawal` to check if the minimum withdrawal delay has passed

```diff
- if (startedWithdrawal.start + Constants.MIN_WITHDRAWAL_DELAY > block.timestamp) {
+ if (block.timestamp < startedWithdrawal.start + Constants.MIN_WITHDRAWAL_DELAY) {
    revert MinWithdrawDelayNotPassed();
}
```

By changing the condition to `block.timestamp < startedWithdrawal.start + Constants.MIN_WITHDRAWAL_DELAY`, the function will revert if the current timestamp is less than the start timestamp plus the minimum withdrawal delay, effectively enforcing the intended delay period before allowing the withdrawal to be finished.
