# Vulnerability details


## Impact
- The DSS will not be able to slash Vaults that use fee-on transfer tokens as the asset.
- The vault will mint more share than it should during deposits.

## Proof of Concept
The `SlashingHandler` contract uses the pattern of pulling the funds to slash from the `Vault` contract and then transfer this tokens to the zero address. We can see in the code that they use the same `amount` parameter for both transfer calls:

```solidity
SafeTransferLib.safeTransferFrom(address(token), msg.sender, address(this), amount);
SafeTransferLib.safeTransfer(address(token), address(0), amount);
```
The issue with this pattern is that for fee-on transfer tokens is that a fee is deducted from `amount` before it is transferred to the `recipient`. Therefore, the second transfer will fail due to insufficient balance.

A similar problem exists in the `deposit` and `mint` functions of the vault. For example, the `deposit` function will compute the `shares` to mint using the intended amount of assets to be transferred:

```solidity
function deposit(uint256 assets, address to) public virtual returns (uint256 shares) {
	if (assets >  maxDeposit(to)) _revert(0xb3c61a83); // `DepositMoreThanMax()`.
	shares =  previewDeposit(assets); // @audit Intended amount of assets
	_deposit(msg.sender, to, assets, shares);
}
```
However, as discussed previously the vault will receive a smaller amount during `_deposit`. Therefore, the vault will overestimate the shares to mint to the depositor.

## Recommended Mitigation Steps
It is important to either document the no support for these types of tokens or not to rely on the `amount` parameter during transfers, instead use the actual token balance of the contract.
