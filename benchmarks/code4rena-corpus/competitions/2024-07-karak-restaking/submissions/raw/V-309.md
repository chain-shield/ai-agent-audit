# Vulnerability details

## Summary

The decision on how to distribute rewards lies with the DSS, and in the DeFi sector, it's typical for the amount restaked to be proportional to the Operator's rewards. It’s reasonable to expect DSSes to favor this approach. However, if the NativeVault's totalAssets do not accurately reflect the restaked Ethereum, rewards distribution could end up being unfair.

## Vulnerability Details
If an Operator’s validator (represented by NativeNodes) is slashed at the snapshot's start by the beacon chain and the balance snapshotProof for the validator has been already submitted, the NativeVault’s totalAssets remain unchanged. This is because new proof submissions must wait 7 days due to the constraints of not validating validators twice in one active snapshot. This is enforced by the code snippet below, in [validateSnapshotProofs()](https://github.com/code-423n4/2024-07-karak/blob/f5e52fdcb4c20c4318d532a9f08f7876e9afb321/src/NativeVault.sol#L150)

```solidity
   if (validatorDetails.lastBalanceUpdateTimestamp >= node.currentSnapshotTimestamp) {
       revert ValidatorAlreadyProved();
    }
```

This issue also applies when one or more validators fully withdraw. Both full withdrawals and significant slashing events from the beacon chain can drastically affect the assets, potentially impacting them by 100s of ETH when multiple validators are involved. Consequently, any rewards distributed by the DSS during this period could be higher than appropriate, or just any system that relies on the accuracy of the restaked amount, could have complications.

Ideally, the safest time to distribute rewards would be after the snapshot proof has been submitted. However, since a slash targets the NativeVault itself and could potentially involve hundreds of validators, there is no perfectly safe time to distribute rewards. The accuracy of totalAssets is likely to decrease as more validators are added.

It should not fall upon the DSS to find the perfect timing for distributing rewards, instead, it is the responsibility of the NativeVault to ensure the accuracy of data. This cannot be achieved by limiting balance update proofs to the current frequency.

EigenLayer's Restaking protocol addresses those problems by allowing the [EigenPod](https://github.com/Layr-Labs/eigenlayer-contracts/blob/dev/src/contracts/pods/EigenPod.sol) which is similar to NativeNode, to receive constant updates. 

> _Other potential issues include the overall security of the protocol being compromised by infrequent updates of actual restaked assets. Not having up-to-date information about the amount of ETH an Operator contributes can limit the DSS's ability to act promptly if assets significantly decrease after proofs submissions._

## Recommendations

To mitigate such issues effectively, it would be beneficial to enable more frequent updates of a validator's balance, rather than limiting updates to once per snapshot every 7 days. A commendable example is the approach taken by EigenPod, which facilitates more dynamic balance management. - [EigenPod](https://github.com/Layr-Labs/eigenlayer-contracts/blob/dev/src/contracts/pods/EigenPod.sol)
