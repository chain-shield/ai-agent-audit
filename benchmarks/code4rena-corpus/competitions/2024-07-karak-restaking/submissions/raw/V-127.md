# Vulnerability details

## Impact

Malicious operators may deploy the native vaults with their own native node implementation addresses. With these customized native nodes, they can run bad actions, such as stealing node owners' withdrawn ETHs that must be sent to the owners' intended addresses.

## Proof of Concept

When creating a native vault, the implementation address of Native Node is provided through the `extraData` parameter.

Neither `CoreLib::deployVaults()` nor `CoreLib::createVault()` conduct a whitelist validation of the native node implementation, and any contract can be a logic contract address of the deployed native node proxy.

As being an operator doesn't require owner's approval, anybody can be an operator without any problem.

Consequently, a malicious operator may create a native vault with a bad native node implementation. Or after creating a vault with a normal node implementation, he may change it to malicious code later through the `NativeVault::changeNodeImplementation()` function.

## Recommended Mitigation Steps

Consider implementing an allowlist for native node implementations, similar to the vault implementation allowlist, to be managed under the Core owner's authority. And then add performing whiteness validation check of `implementation` from `extraData` parameter in `CoreLib::deployVaults()` or `CoreLib::createVault()` functions.

This allowlist check should also be conducted for `NativeVault::changeNodeImplementation()` function.
