# Vulnerability details

## Impact
The current implementation of bitwise operations in the `validateBalance` function leads to inaccurate representation of validator balances, potentially affecting the integrity of financial transactions and rewards distribution within the protocol.

## Proof of Concept
Refer to the following section in the `BeaconProofsLib.sol` contract: [Source Code Link](https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/entities/BeaconProofsLib.sol#L114-L135)

```solidity
function validateBalance(bytes32 balanceRoot, uint40 validatorIndex, BalanceProof calldata proof)
        internal
        view
        returns (uint256 validatorBalanceWei)
    {
        if (proof.proof.length != 32 * (BALANCE_HEIGHT + 1)) revert InvalidBalanceProof();

        uint256 balanceIndex = uint256(validatorIndex / 4);

        if (
            !Merkle.verifyInclusionSha256({
                proof: proof.proof,
                root: balanceRoot,
                leaf: proof.balanceRoot,
                index: balanceIndex
            })
        ) revert InvalidBalanceProof();

        /// Extract the individual validator's balance from the `balanceRoot`
        uint256 bitShiftAmount = (validatorIndex % 4) * 64;
        return uint256(fromLittleEndianUint64(bytes32((uint256(proof.balanceRoot) << bitShiftAmount)))) * 1 gwei;
    }
```

The core issue arises from the misuse of the left shift operation (`<<`) instead of right shift operation (`>>`) for extracting the balance associated with a validator index. This causes the function to interpret the balance incorrectly for all validators except those whose indices are multiples of 4.

### Proof of concept:
- When `validatorIndex = 0`, the calculation is correct due to no shift occurring.
- For any other `validatorIndex` (e.g., 1, 2, 3), the left shift operation (`<<`) displaces the significant bits beyond the 64-bit boundary processed by `fromLittleEndianUint64`, leading to incorrect balance extraction.

This flaw not only affects the immediate calculation within `validateBalance` but also extends through other dependent functionalities, such as the `validateSnapshotProof` function in `NativeVaultLib.sol`, which relies on accurate balance information for validator snapshots.

## Impact on Dependent Functionality
The `validateSnapshotProof` function in `NativeVaultLib.sol` uses the `BeaconProofs.validateBalance` method to update validator balances and determine changes in stake. Incorrect balance calculations directly impact the accuracy of these operations, leading to potential discrepancies in reported balances and stake changes.

```solidity
uint256 newBalanceWei = BeaconProofs.validateBalance(balanceRoot, validatorIndex, proof);
```

This line within `validateSnapshotProof` is particularly sensitive to the accuracy of balance calculations, as it directly influences the perceived financial status of validators within the system.

## Recommended mitigation steps
The identified bug in the `validateBalance` function should be corrected to ensure the integrity of validator balance calculations across the protocol. Adjusting the bitwise operation to correctly use right shift (`>>`) instead of left shift (`<<`) will rectify the balance extraction process, ensuring accurate representation of validator balances and maintaining the reliability of the contract.
