# Vulnerability details

## Impact
Karak uses an implementation of the ERC4626 tokenized vault standard as the default vault to handle ERC20 tokens as restaked assets. Each asset has a dedicated vault.
However, the ERC4626 `deposit/mint` functions do not work well with fee-on-transfer tokens. The `amount` variable represents the pre-fee amount, including the fee, whereas the `totalAssets` no longer include the fee.

Vaults that handle tokens with fee-on-transfer can be exploited to mint more shares than intended.
```solidity
File:ERC4626.sol
function _deposit(address by, address to, uint256 assets, uint256 shares) internal virtual {
    SafeTransferLib.safeTransferFrom(asset(), by, address(this), assets);
    _mint(to, shares);
    /// @solidity memory-safe-assembly
    assembly {
        // Emit the {Deposit} event.
        mstore(0x00, assets)
        mstore(0x20, shares)
        let m := shr(96, not(0))
        log3(0x00, 0x40, _DEPOSIT_EVENT_SIGNATURE, and(m, by), and(m, to))
    }
    _afterDeposit(assets, shares);
}
```
At the same time, users that mint directly the assets using `mint()` function in `Vault.sol` will be disadvantage, receiving fewer assets than intended.

## Proof of Concept
A `deposit(1000)` should result in the same number of shares as two deposits of `deposit(500)` but it does not because `amount` is the pre-fee amount.
Assume a fee-on-transfer of `20%`. For simplicity, let's assume the current `totalAmount = 1000` and `totalShares = 1000`.

- `deposit(1000) = 1000 / totalAmount * totalShares = 1000 shares`
- `deposit(500) = 500 / totalAmount * totalShares = 500 shares`. Now the `totalShares` increased by 500, but the `totalAssets` only increased by `(100% - 20%) * 500 = 400`. Therefore, the second `deposit(500) = 500 / (totalAmount + 400) * (newTotalShares) = 500 / (1400) * 1500 = 535.714285714 shares`.

In total, the two deposits result in `35` more shares than a single deposit of the sum of the deposits.

Manual review.

## Recommended Mitigation Steps
`amount` should be the amount excluding the fee, i.e., the amount the contract actually received. This can be achieved by subtracting the pre-contract balance from the post-contract balance.

Additioally, `previewDeposit` should be overwritten by vaults supporting fee-on-transfer tokens to predict the post-fee `amount` and perform the shares computation based on that amount. However, `afterDeposit` will still be called with the original `amount`, and implementers need to be aware of this.
