# Vulnerability details

## Impact

If an allowed vault is found to be malicious in the future, it can be re-deploy for future `Vault` creation with his malicious behavior(s), which potentially impact all the users of Karak protocol. 

## Proof of Concept

The team/admin can allow a new implementation for the creation of `Vault` and `NativeVault`. Theses potentials new implementations are assumed to be audited and assumed safe by the team.

```solidity
    function allowlistVaultImpl(Storage storage self, address implementation) internal {
        self.allowlistedVaultImpl[implementation] = true;
    }
```
But if in the future we find an issue of a possible malicious bahevior in an added implementation. There are no way to remove an implementation in the `allowlistedVaultImpl` mapping.


For `Vault` and `NativeVault`, owner/admin can change the implementation address with `changeImplementationForVault()` but it can take time to make it and let a windows of time for malicious actions and it cost gas for the team. 
Undeniably, this can cause problems and a bad image for the protocol. 

## Tools Used

Manual Review

## Recommended Mitigation Steps

Add a way for the owner/admin to delete an implementation on the `allowlistedVaultImpl` mapping.
