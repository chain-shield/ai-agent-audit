# Vulnerability details

## Impact

Vaults won't be initalized with a underlying token, whose symbol is a type of `bytes32` instead of `string`, as it would lead to a revert.

## Proof of Concept

Although most of the tokens have got a symbol function implemented, it is completely optional therefore any token which doesn't implement it, or has made changes to the function, will still be compliant as per the [EIP](https://eips.ethereum.org/EIPS/eip-20#symbol):
> OPTIONAL - This method can be used to improve usability, but interfaces and other contracts MUST NOT expect these values to be present.

Following the contest's readme all ERC20 tokens should be supported by the protocol: 
> Any (all possible ERC20s)

Whenever a new `vault` gets initialized, the underlying token's address, name, decimals and symbol are used in the [initialize](https://github.com/code-423n4/2024-07-karak/blob/main/src/Vault.sol#L51-L71) function. This means that if any of these parameters are not set correctly, a revert will occur, and the `vault` will not be initialized. Such is the case when a token like [MKR](https://etherscan.io/token/0x9f8f72aa9304c8b593d555f12ef6589cc3a579a2#code) or [RING](https://etherscan.io/token/0x9469d013805bffb7d3debe5e7839237e535ec483) is used, where the returned symbol is with type of `bytes32`. The non-string `symbol` won't be converted to a string, causing a revert and preventing the `vault` from being initialized.

## Tools Used

Manual Review

## Recommended Mitigation Steps

One way to mitigate this issue is to first determine whether the symbol is a `string` or `bytes32` - if it's `bytes32`, the value should be converted to a string and then used for the config of the vault.
