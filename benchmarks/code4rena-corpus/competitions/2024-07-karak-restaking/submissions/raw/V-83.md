# Vulnerability details

## Impact
```solidity
    function handleSlashing(IERC20 token, uint256 amount) external {
        if (amount == 0) revert ZeroAmount();
        if (!_config().supportedAssets[token]) revert UnsupportedAsset();

        SafeTransferLib.safeTransferFrom(address(token), msg.sender, address(this), amount);
        // Below is where custom logic for each asset lives
        SafeTransferLib.safeTransfer(address(token), address(0), amount);
    }
```

The `handleSlashing()` function in the `SlashingHandler` contract employs a two-step transfer process:
1. It transfers the `amount` of tokens from `msg.sender` to the current contract.
2. It then transfers these tokens to `address(0)`.

If the `token` is a fee-on-transfer token, after step (1), the balance in `address(this)` will be less than `amount`, causing step (2) to fail.

Consequently, the DSS might not be able to finalize a slashing if the underlying asset in the vault is a fee-on-transfer token.

## Tools Used

Manual Review

## Recommended Mitigation Steps

Either:
1. Do not allowlist fee-on-transfer tokens, or
2. Implement a compatible version of `SlashingHandler` for fee-on-transfer tokens.
