# Vulnerability details

## Vulnerability Detail
handleSlashing function in the contract SlashingHandler burns ERC20 tokens incorrectly. which will revert slashing attempts from the Vault contracts.

### Example
Vault calls slashAssets, which calls slashingHandler. slashingHandler tries to burn tokens through safeTransfer to address 0, transaction reverts because the `to` address cannot be zero

From Vault.sol
```solidity
function slashAssets(uint256 totalAssetsToSlash, address slashingHandler){
.
// Approve to the handler and then call the handler which will draw the funds
SafeTransferLib.safeApproveWithRetry(asset(), slashingHandler, transferAmount);
ISlashingHandler(slashingHandler).handleSlashing(IERC20(asset()), transferAmount);
```

in SlashingHandler.sol
```solidity
function handleSlashing(IERC20 token, uint256 amount) external 
{
if (amount == 0) revert ZeroAmount();
if (!_config().supportedAssets[token]) revert UnsupportedAsset();

SafeTransferLib.safeTransferFrom(address(token), msg.sender, address(this), amount);
// Below is where custom logic for each asset lives
@-> SafeTransferLib.safeTransfer(address(token), address(0), amount);
//@audit wrong way to burn
}
```

In USDC.sol impl
```solidity
    function transfer(address _to, uint256 _value) whenNotPaused notBlacklisted(msg.sender) notBlacklisted(_to) public returns (bool) {
        require(_to != address(0));
.
.
```

## Impact
Funds cannot be slashed for assets that revert when `to` address is zero, like USDC
