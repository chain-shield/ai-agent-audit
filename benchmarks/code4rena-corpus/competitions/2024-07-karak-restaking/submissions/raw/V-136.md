# Vulnerability details


## Proof of Concept

Take a look at https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/Vault.sol#L78-L120

```solidity
    function deposit(uint256 assets, address to)
        public
        override(ERC4626, IVault)
        whenFunctionNotPaused(Constants.PAUSE_VAULT_DEPOSIT)
        nonReentrant
        returns (uint256 shares)
    {
        if (assets == 0) revert ZeroAmount();
        return super.deposit(assets, to);
    }

    function deposit(uint256 assets, address to, uint256 minSharesOut)
        external
        nonReentrant
        whenFunctionNotPaused(Constants.PAUSE_VAULT_DEPOSIT_SLIPPAGE)
        returns (uint256 shares)
    {
        if (assets == 0) revert ZeroAmount();
        shares = super.deposit(assets, to);
        if (shares < minSharesOut) revert NotEnoughShares();
    }


    function mint(uint256 shares, address to)
        public
        override(ERC4626, IVault)
        whenFunctionNotPaused(Constants.PAUSE_VAULT_MINT)
        nonReentrant
        returns (uint256 assets)
    {
        if (shares == 0) revert ZeroShares();
        assets = super.mint(shares, to);
    }

```

These three functions are used to interact with the underlying ERC4626 vault, evidently, in the case where a user wants to deposit assets in a vault they have the option to use the slippage protected deposit() to ensure they can protect themselves from any malicious frontrunning in ERC4626, issue however is that option does not exist when users are directly trying to mint, which would then leave them vulnerable to any malicious frontruns.

## Impact

No slippage applied when minting, so an attacker can maliciously frontrun minting to make honest user receive assets converted by a bad rate.

## Recommended Mitigation Steps

Consider also integrating a slippage backed `mint` function, i,e

