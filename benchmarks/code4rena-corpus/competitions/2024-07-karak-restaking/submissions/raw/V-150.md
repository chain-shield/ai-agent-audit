# Vulnerability details

### [M-2] `NativeVault::finishWithdrawal` updates the state after an external call and opens up the possibility for cross-function reentrancy calls.

**Description:** The `NativeVault` is supposed to work with native Ether, see Karak docs [here](https://docs.karak.network/protocol/v2/native-restaking#full-withdrawals). This implies that there will be instances where the `receiver` of the native ETH transfer from the `finishWithdrawal(...)` function call will be a smart contract that can have a `receive()` function which gets to execute arbitrary logic.

The issue arises from the fact that the `NativeVault::finishWithdrawal` function updates the `node.withdrawableCreditedNodeETH` variable and deletes the `withdrawalKey` from the `withdrawalMap` after doing the external call.

See the function below

```javascript
    function finishWithdrawal(bytes32 withdrawalKey) external nonReentrant whenFunctionNotPaused(Constants.PAUSE_NATIVEVAULT_FINISH_WITHDRAWAL) {
        //..
        //..
        //@audit here we call `NativeNode::withdraw` function which sends native ETH to the `to` address
        INativeNode(node.nodeAddress).withdraw(startedWithdrawal.to, startedWithdrawal.assets);

        //@audit | updating state variables after processing withdrawal
        node.withdrawableCreditedNodeETH -= startedWithdrawal.assets;
        delete self.withdrawalMap[withdrawalKey];

        //..
    }
```

Considering how flexible Karak protocol is meant to be and the fact that other protocols will integrate or build on top of their protocol by using these vaults, doing these state changes after doing an external call opens up the possibility for cross-function reentrancy calls inside Karak and inside 3rd party protocols that rely on the data that Karak smart contracts provide.

Suppose that the `receiver` is malicious, their balance at the time of the `INativeNode(node.nodeAddress).withdraw` will not be updated properly. As per the @natspec in `NativeVaultLib::NativeNode.withdrawableCreditedNodeETH` this variable tracks the amount of "withdrawable ETH with shares awarded". This means that the protocol believes that the user still has shares available which he can use to redeem more ETH, which is wrong because the withdrawal was already processed at this point.

The 2nd variable which is updated after the withdrawal is `delete self.withdrawalMap[withdrawalKey]`. This is complementary to the first one in the sense that the protocol still deems this `withdrawalKey` valid even after the `withdrawal` has been effectively processed. If it weren't for the `nonReentrant` modifier, this would've been a "textbook" reentrancy attack case because both the amount `withdrawableCreditedNodeETH` and the key `withdrawalKey` are updated after processing the withdrawal.

**Impact:** Even if a user can not reenter in the same `NativeVault::finishWithdrawal` function, they can still attempt cross-function reentrancy calls inside Karak or 3rd party protocols that rely on Karak. Problems will arise with future integrations. If at any point a 3rd party protocol will rely on the accuracy of the `NativeVaultLib::NativeNode.withdrawableCreditedNodeETH` amount and the validity of the `withdrawalKey` then these protocols will be vulnerable because of this.

**Tools used:** Manual review

**Recommended mitigation:** Do the state changes before calling the `INativeNode(node.nodeAddress).withdraw` function as they have no impact on that function's execution. This will ensure that the `NativeVault::finishWithdrawal` function properly follows the CEI pattern.

```diff
    function finishWithdrawal(bytes32 withdrawalKey) external nonReentrant whenFunctionNotPaused(Constants.PAUSE_NATIVEVAULT_FINISH_WITHDRAWAL) {
        //..
        //..
+       node.withdrawableCreditedNodeETH -= startedWithdrawal.assets;
+       delete self.withdrawalMap[withdrawalKey];
        INativeNode(node.nodeAddress).withdraw(startedWithdrawal.to, startedWithdrawal.assets);
-       node.withdrawableCreditedNodeETH -= startedWithdrawal.assets;
-       delete self.withdrawalMap[withdrawalKey];
        //..
    }
```
