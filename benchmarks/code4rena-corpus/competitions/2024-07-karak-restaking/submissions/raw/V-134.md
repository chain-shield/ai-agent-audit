# Vulnerability details


## Proof of Concept

First note that this has been indicated in the readMe https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/README.md#L146-L158

> ### ERC20 token behaviors in scope

| Question                                                                                                                                | Answer   |
| --------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| [Revert on transfer to the zero address](https://github.com/d-xo/weird-erc20?tab=readme-ov-file#revert-on-transfer-to-the-zero-address) | In scope |

Now take a look at https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/SlashingHandler.sol#L52-L59

```solidity
    function handleSlashing(IERC20 token, uint256 amount) external {
        if (amount == 0) revert ZeroAmount();
        if (!_config().supportedAssets[token]) revert UnsupportedAsset();

        SafeTransferLib.safeTransferFrom(address(token), msg.sender, address(this), amount);
        // Below is where custom logic for each asset lives
        SafeTransferLib.safeTransfer(address(token), address(0), amount);
    }
```

This function is used to slash the specific _amount_ of the token, and what this function does is that it pulls the assets form the vault and send them to address(0), issue however is that from the scope we can see that protocol expects to use integrate with tokens that revert on transfer to `address(0)` which would then mean that slashing these tokens would never work cause the attempt always [reverts on this line](https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/SlashingHandler.sol#L58).

And this revert bubbles up the Vault itself in the @audit tagged instance below https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/Vault.sol#L192-L205

```solidity

    function slashAssets(uint256 totalAssetsToSlash, address slashingHandler)
        external
        onlyCore
        returns (uint256 transferAmount)
    {
        transferAmount = Math.min(totalAssets(), totalAssetsToSlash);

        // Approve to the handler and then call the handler which will draw the funds
        SafeTransferLib.safeApproveWithRetry(asset(), slashingHandler, transferAmount);
        ISlashingHandler(slashingHandler).handleSlashing(IERC20(asset()), transferAmount);//@audit

        emit Slashed(transferAmount);
    }
```

## Impact

Core functionality of slashing some supported tokens would never work cause the attempt always [reverts on this line](https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/SlashingHandler.sol#L58), and this reverts [bubbles back to the vault](https://github.com/code-423n4/2024-07-karak/blob/ab18e1f6c03e118158369527baa2487b2b4616b1/src/Vault.sol#L202), which further proves how assets in the vault can't get slashed.

## Recommended Mitigation Steps

Consider not supporting these tokens.

Alternatively consider transferring the tokens to the `dead` address and not `0x0`, i.e apply these changes:

```diff
    function handleSlashing(IERC20 token, uint256 amount) external {
        if (amount == 0) revert ZeroAmount();
        if (!_config().supportedAssets[token]) revert UnsupportedAsset();

        SafeTransferLib.safeTransferFrom(address(token), msg.sender, address(this), amount);
        // Below is where custom logic for each asset lives
-        SafeTransferLib.safeTransfer(address(token), address(0), amount);
+        SafeTransferLib.safeTransfer(address(token), address(0x000000000000000000000000000000000000dEaD), amount);

    }

```
