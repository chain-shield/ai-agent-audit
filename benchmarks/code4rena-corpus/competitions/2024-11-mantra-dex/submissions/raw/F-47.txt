Inconsistent fee validation logic during pool creation leads to incorrect payment rejections
Tigerfrake
19
Sufficient
383d ago
Finding description and impact

The validate_fees_are_paid() function employs inconsistent methods for validating fee payments based on the length of denom_creation_fee. When the token factory fee has only one option, it uses cw_utils::must_pay() which strictly requires a single payment entry, while other cases use get_paid_pool_fee_amount() which can aggregate multiple payments of the same denomination.

This inconsistency can cause valid fee payments to be incorrectly rejected.

Proof of Concept

Here's how the validation differs in the current implementation:

    pub fn validate_fees_are_paid(
        pool_creation_fee: &Coin,
        denom_creation_fee: Vec<Coin>,
        info: &MessageInfo,
    ) -> Result<Vec<Coin>, ContractError> {
        // ... 
        if denom_creation_fee.len() == 1usize {
            let total_fee_amount = tf_fee.amount.checked_add(pool_creation_fee.amount)?;
            // @audit-info Strict single payment validation
>>          let paid_fee_amount = cw_utils::must_pay(info, pool_fee_denom)?; // REVERTS HERE! ❌
            
            ensure!(
                paid_fee_amount == total_fee_amount,
                ContractError::InvalidPoolCreationFee {
                    amount: paid_fee_amount,
                    expected: total_fee_amount,
                }
            );
        } else {
            // @audit-info Flexible payment validation that can handle multiple entries
>>          let paid_fee_amount = get_paid_pool_fee_amount(info, pool_fee_denom)?;
            // ...
        }

Scenario:

User needs to pay 2000 uusd as a fee
User sends two transactions of 800 uusd and 1200 uusd each due to wallet constraints
info.funds contains:
    vec![
        Coin { denom: "uusd", amount: 800 },
        Coin { denom: "uusd", amount: 1200 }
    ]
If denom_creation_fee.len() == 1, the transaction reverts because must_pay() expects exactly one entry
However, if denom_creation_fee.len() > 1, the same payment structure would be accepted because get_paid_pool_fee_amount() correctly sums the amounts.

Recommended mitigation steps

Use get_paid_pool_fee_amount() consistently for all cases to allow flexible payment structures:

    if denom_creation_fee.len() == 1usize {
        let total_fee_amount = tf_fee.amount.checked_add(pool_creation_fee.amount)?;
-       let paid_fee_amount = cw_utils::must_pay(info, pool_fee_denom)?;
+       let paid_fee_amount = get_paid_pool_fee_amount(info, pool_fee_denom)?;
        
        ensure!(
            paid_fee_amount == total_fee_amount,
            ContractError::InvalidPoolCreationFee {
                amount: paid_fee_amount,
                expected: total_fee_amount,
            }
        );
    }

This change ensures consistent behavior regardless of the payment structure, as long as the total amount matches the required fee.
