Before going too deep into the report, we should understand that on Mantra, we can have either a constant product (xyk) pool or a stable swap pool: https://github.com/code-423n4/2024-11-mantra-dex/blob/26714ea59dab7ecfafca9db1138d60adcf513588/contracts/pool-manager/schema/pool-manager.json#L588-L612

      "PoolType": {
        "description": "Possible pool types, it can be either a constant product (xyk) pool or a stable swap pool.",
        "oneOf": [
          {
            "description": "A stable swap pool.",
            "type": "object",
            "required": [
              "stable_swap"
            ],
            "properties": {
              "stable_swap": {
                "type": "object",

As shown in the snippet above however, we allow for the amp value to be 0, which is not a valid value.

This can even be seen to be hinted even in the test scope, where we correctly pass in a valid minimum value for amp:

https://github.com/code-423n4/2024-11-mantra-dex/blob/26714ea59dab7ecfafca9db1138d60adcf513588/contracts/pool-manager/src/helpers.rs#L948-L958

mod tests {
    use cosmwasm_std::coin;
    use proptest::prelude::*;
    use rand::Rng;

    use sim::Model;

    use super::*;

    /// Minimum amplification coefficient.
    pub const MIN_AMP: u64 = 1;

    // ..snip

However the above is not replicated in the main code implementation, which then means that while creating the pool we allow for an amp value of 0, as there is not a validation populated against the amp value during pool creation see create_pool() above, and besides,from the second snippet attached to the report we see how the minimum has been proclaimed to be 0.

But having this value completely causes a permanent DOS on swaps due to computational errors.

The compute_y_raw() function is used to calculate the output amount in a stableswap pool. It contains this key line:

https://github.com/code-423n4/2024-11-mantra-dex/blob/26714ea59dab7ecfafca9db1138d60adcf513588/contracts/pool-manager/src/helpers.rs#L831-L832

    let ann = amp_factor.checked_mul(n_coins.into())?; // A * n ** n


Now when amp_factor is 0:

ann becomes 0 (0 * n_coins)
Later in the function, there's a division by ann:
https://github.com/code-423n4/2024-11-mantra-dex/blob/26714ea59dab7ecfafca9db1138d60adcf513588/contracts/pool-manager/src/helpers.rs#L855-L861
    let b = d
        .checked_div(ann.into())
        .unwrap()
        .checked_add(swap_in.into())
        .unwrap()
        .checked_add(no_swap.into())
        .unwrap();
d.checked_div(ann.into()) would be division by zero when ann is 0, which would error out in the checked_div implementation
    pub fn checked_div(self, other: Self) -> Result<Self, DivideByZeroError> {
        self.0
            .checked_div(other.0)
            .map(Self)
            .ok_or(DivideByZeroError)
    }



And this division by zero would cause the swap to fail with an error/panic.

To go into a bit more details using mathematical notations, we already understand that the amp factor (A) is a critical parameter in the stableswap invariant formula:

https://github.com/code-423n4/2024-11-mantra-dex/blob/26714ea59dab7ecfafca9db1138d60adcf513588/contracts/pool-manager/src/helpers.rs#L819

/// y**2 + y * (sum' - (A*n**n - 1) * D / (A * n**n)) = D ** (n + 1) / (n ** (2 * n) * prod' * A)

When A = 0:
The term (A*n**n - 1) becomes -1
The division by A * n**n becomes division by 0
This makes the entire equation mathematically undefined.

Impact

Multiple impacts, rounding up to a very substantial case.

First, as shown in the first code snippet attached in the report, in order to create a pool, the creator must pay multiple fees, for the creation and the token factory... this bug case means a direct loss of funds (the fees paid) as the pool can never be used.

Secondly, as shown in the snippet too, when creating a pool, we must enforce that for that same identifier no pool has been previously created, which then causes for a permanent DOS to a pool creator, as once they've created the pool if there is any issue with the pool there is no way to delete a pool to then recreate it, allowing them not to be able to use their wanted identifier.

Thirdly, any user who's provided liquidity to the pool would then have to withdraw their liquidity as the pool can't be used, causing them loss of funds for processing the tx to provide liquidity, and also the fact that the first user who provided liquidity would unfairly have MINIMUM_LIQUIDITY_AMOUNT of liquidity taken from them to the contract which no one can access.

Recommended Mitigation Steps

Integrate a valid min amp value as 1 in the real code implementation, as is done in the test module:
https://github.com/code-423n4/2024-11-mantra-dex/blob/26714ea59dab7ecfafca9db1138d60adcf513588/contracts/pool-manager/src/helpers.rs#L957-L958

    /// Minimum amplification coefficient.
    pub const MIN_AMP: u64 = 1;

Then during pool creation, ensure that the amp value is validated to be atleast this minimum value.
