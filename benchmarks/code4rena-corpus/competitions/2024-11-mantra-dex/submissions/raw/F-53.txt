Epoch duration can be updated breaking a core invariant
Bauchibred
27
Sufficient
383d ago
Proof of Concept

From the readMe we have:

https://github.com/code-423n4/2024-11-mantra-dex/blob/26714ea59dab7ecfafca9db1138d60adcf513588/README.md#L188-L191

Main invariants:

- Genesis epoch and epoch duration, not intended to changed once set up.

Which indicates how we shouldn't be able to change the epoch duration once it's set up, this however is not followed by the implementation, considering the update_config function in the epoch manager contract allows updating the entire epoch configuration without proper validation of the genesis epoch:

https://github.com/code-423n4/2024-11-mantra-dex/blob/26714ea59dab7ecfafca9db1138d60adcf513588/contracts/epoch-manager/src/commands.rs#L19-L23

/// Updates the config of the contract.
pub fn update_config(
    deps: DepsMut,
    info: &MessageInfo,
    epoch_config: Option<EpochConfig>,
) -> Result<Response, ContractError> {
    cw_ownable::assert_owner(deps.storage, &info.sender)?;

    let mut config = CONFIG.load(deps.storage)?;

|>    if let Some(epoch_config) = epoch_config.clone() {
|>        validate_epoch_duration(epoch_config.duration)?;
|>        config.epoch_config = epoch_config;
|>        CONFIG.save(deps.storage, &config)?;
|>    }

    Ok(Response::default().add_attributes(vec![
        ("action", "update_config".to_string()),
        (
            "epoch_config",
            epoch_config.unwrap_or(config.epoch_config).to_string(),
        ),
    ]))
}

While the duration is validated, there are no checks on the new genesis epoch value. This contrasts with the instantiation where genesis epoch is properly validated:

ensure!(
    msg.epoch_config.genesis_epoch.u64() >= env.block.time.seconds(),
    ContractError::InvalidStartTime
);
Impact

The current implementation violates this core invariant.

Also Since farm rewards are calculated based on epochs, changing the genesis epoch can manipulate reward distributions:

Setting genesis epoch to the future could temporarily freeze reward distributions
Setting it to the past could cause incorrect reward calculations and potentially drain farm rewards

Changing genesis epoch after farms are active disrupts the continuous epoch sequence.

Also note that from the documentation we don't have the epoch manager as a trusted role.

Would be key to note that this also has other massive security implications;

Considering the current epoch id is calculated as: current_epoch = (current_time - genesis_epoch_time) / epoch_duration/

So assume the epoch duration is changed, i.e:


Initial duration: 1 day (86,400s)
Time since genesis: 200,000s
Current epoch: 200,000/86,400 = epoch 2
If duration changes to 2 days (172,800s):

Same time since genesis: 200,000s
New epoch: 200,000/172,800 = epoch 1

This then means that the check below for calculating rewards would be completely broken, allowing for users to get double, in the minimalistic case hinted above, assume a user has claimed rewards both in epoch 1 and 2. after the duration is changed, we go back to epoch 1, so the check when calculating attached below would be bypassed cause user's last_claimed_epoch_for_user is 2 where as current_epoch_id is back at 1:

https://github.com/code-423n4/2024-11-mantra-dex/blob/26714ea59dab7ecfafca9db1138d60adcf513588/contracts/farm-manager/src/farm/commands.rs#L139-L153


pub(crate) fn calculate_rewards() {


    // ..snip
    // Check if the user ever claimed before
    if let Some(last_claimed_epoch) = last_claimed_epoch_for_user {
        // if the last claimed epoch is the same as the current epoch, then there is nothing to claim

Recommended Mitigation Steps

Add proper validation:

Ensure new genesis epoch maintains continuity with existing epochs
Validate impact on active farm positions
Add checks for reward calculation consistency.

Alternatively for the second case hinted under Impact then enforce that the check is not a strict equal check, but a greater than or equal to check, i.e:


pub(crate) fn calculate_rewards() {


    // ..snip
    // Check if the user ever claimed before
    if let Some(last_claimed_epoch) = last_claimed_epoch_for_user {
        // if the last claimed epoch is the same as the current epoch, then there is nothing to claim
-        if current_epoch_id == last_claimed_epoch {
+        if current_epoch_id >= last_claimed_epoch {
            return if is_claim {
                Ok(RewardsResponse::ClaimRewards {
                    rewards: vec![],
                    modified_farms: HashMap::new(),
                })
            } else {
                Ok(RewardsResponse::QueryRewardsResponse { rewards: vec![] })
            };
        }
    }
// ..snip
                }
