S-379
Spread calculation in `compute_swap` can lead to revert due to underflow
carrotsmuggler
77
Sufficient
383d ago
Finding description and impact

The compute_swap function in the helpers.rs file calculates the result of the swap. It also has an inbuilt spread calculation. We are interested only in the logic in the constant product part.

let return_amount: Uint256 =
    Decimal256::from_ratio(ask_pool.mul(offer_amount), offer_pool + offer_amount)
        .to_uint_floor();

let exchange_rate = Decimal256::checked_from_ratio(ask_pool, offer_pool)
    .map_err(|_| ContractError::PoolHasNoAssets)?;
let spread_amount: Uint256 = (Decimal256::from_ratio(offer_amount, Uint256::one())
    .checked_mul(exchange_rate)?
    .to_uint_floor())
.checked_sub(return_amount)?;

Point to note is that the last line uses checked_sub, which reverts if the result is negative. In this place, the spread_amount is calculated and sent to the parent function. The spread itself is checked elsewhere after this function returns.

The issue is that this calculation here can underflow, triggering an error. This is because the exchange_rate calculation does a division, followed by a multiplication in spread_amount leading to a precision loss, resulting in an underflow. For this to trigger, exchange_rate needs to evaluate to 0, so there needs to be at least 18 orders of magnitude difference between the constituents of the pool. This is possible if the tokens are of different decimals as well as different balances.

This can lead to failed swaps even when spread conditions are met, just owing to the way it is calculated.

Proof of Concept

Let us investigate the following case:

Here, the pool state is:

ask_pool = 10e18
offer_pool = 100e36

And we are trying to swap in 1e36 tokens. So offer_amount=1e36.

In this scenario, return_amount evaluates to 10e18*1e36 / (101e36), which is some non-zero amount. The value is not important here.

However, exchange_rate evaluates to 10e18 * 1e18 / 100e36 = 0. The extra 1e18 in the numerator comes from the usage of Decimal256, which does 18 precision calculations. Still, exchange_rate evaluates to 0.

Now, spread_amount = 1e36 * 0 - return_amount = -return_amount. This is a negative value, which will trigger a revert.

So any situation where the exchange_rate evaluates to 0 will trigger a revert. This mainly happens due to a division before a multiplication.

When calculating return_amount, the ask_pool is multiplied by offer_amount and then divided by offer_pool (ignoring offer_amount as we are interested in the magnitudes only). However in exchange_rate, the ask_pool is first divided by offer_pool and then multiplied by offer_amount. But by this time, due to the division, the precision is lost and the result is 0.

Then when spread_amount is calculated, the result is negative since exchange_rate is 0. This triggers a revert.

Recommended mitigation steps

Calculate exchange_rate in 1e36 precision instead of 1e18. This will prevent the precision loss. Another way is to do all the multiplications first before dividing by the offer_pool amount. This will prevent the precision loss as well.
