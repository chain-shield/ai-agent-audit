S-201
Incorrect Reward Distribution Due To Mutable Epoch Duration
Lambda
00
Sufficient
383d ago
Description

The epoch manager contract allows updating the epoch duration via ExecuteMsg::UpdateConfig, but the farm manager implicitly relies on constant epoch duration for its reward calculations and position tracking. An epoch duration change causes reward distribution errors, breaks position weight calculations, and makes historical LP weight data unreliable.

The issue stems from the farm manager storing only epoch IDs in maps like LP_WEIGHT_HISTORY and using these epoch IDs for period-based calculations, while the actual time duration these epochs represent can be changed by the admin. When epoch duration changes, all calculations that map epoch IDs to time periods become invalid.

This impacts:

Farm emission rate calculations which assume fixed epoch lengths
Position weight and claim tracking across epochs
Historical LP weight data used for reward distribution
The claim period validation for users

Note that this does not constitute an admin mistake in my opinion. The problem is not that the admin uses the wrong parameters for the update, the problem is that the contracts are inherently incompatible with all updates to these parameters, so any update (even if carefully reviewed) will break the system. Moreover, the update happens in one contract (epoch manager) and breaks another contract and it is not documented anywhere that the function will break the other contract, so such a call by the owner of the epoch manager seems natural (as this is a global contract that is intended to be used by other protocols, which may handle updates without issues) and not a mistake (if any update were a mistake, it would not make sense to even have the update possibility).

Proof of Concept

First, epoch duration and the epoch start timestamp can be modified by admin:
https://github.com/code-423n4/2024-11-mantra-dex/blob/26714ea59dab7ecfafca9db1138d60adcf513588/contracts/epoch-manager/src/contract.rs#L58-L61

This duration and the start timestamp are directly used to calculate epochs:
https://github.com/code-423n4/2024-11-mantra-dex/blob/26714ea59dab7ecfafca9db1138d60adcf513588/contracts/epoch-manager/src/queries.rs#L21-L29

The farm manager queries the epoch manager in various places:

is_farm_expired: https://github.com/code-423n4/2024-11-mantra-dex/blob/bdfc2797860790a8a3ce47e4cd550cab25fba3f5/contracts/farm-manager/src/helpers.rs#L250-L258
query_rewards to get the current epoch: https://github.com/code-423n4/2024-11-mantra-dex/blob/bdfc2797860790a8a3ce47e4cd550cab25fba3f5/contracts/farm-manager/src/queries.rs#L101-L102
claim to get the current epoch: https://github.com/code-423n4/2024-11-mantra-dex/blob/bdfc2797860790a8a3ce47e4cd550cab25fba3f5/contracts/farm-manager/src/farm/commands.rs#L34-L37
create_farm to get the current epoch: https://github.com/code-423n4/2024-11-mantra-dex/blob/bdfc2797860790a8a3ce47e4cd550cab25fba3f5/contracts/farm-manager/src/manager/commands.rs#L60-L63
update_weights to get the current epoch: https://github.com/code-423n4/2024-11-mantra-dex/blob/bdfc2797860790a8a3ce47e4cd550cab25fba3f5/contracts/farm-manager/src/position/commands.rs#L463-L466
clear_lp_weight_history to get the current epoch: https://github.com/code-423n4/2024-11-mantra-dex/blob/bdfc2797860790a8a3ce47e4cd550cab25fba3f5/contracts/farm-manager/src/position/helpers.rs#L245-L248

All of this functions would be broken if the epoch configuration changes because they assume that epochs are consecutive (for instance when looping from the last claimed epoch to the current epoch), which is no longer the case when they are updated. The consequences vary by function and range from DoS to loss of funds.

Here's one example what can happen, but you could come up with such examples for every usage listed:
Let's assume there are two users Alice and Bob. Alice has 50% of the weights until epoch 20 (when she withdraws), while Bob has 50% until epoch 20 and 100% afterwards.
At epoch 20 the epoch manager configuration is changed such that we are now at epoch 10 again.
When the weights are now updated, LP_WEIGHT_HISTORY for epoch 11 is updated a second time The weights are set such that Bob owns 100% of them (which would be correct for epoch 21, but of course not for epoch 10, where he had 50% in theory). Bob has not claimed yet, so he can claim for epoch 11 and gets 100% of the emission rate. But Alice has already claimed 50% of the rate, meaning we get 150% of the tokens for this epoch and the tokens will not be sufficient to cover all claims.

Recommended Mitigation Steps

I see two possible mitigations:

Remove epoch duration mutability

When the epoch configuration is changed, perform migrations to update all data (e.g. transforming all epochs to the new system)

The recommended solution is option 1 - removing epoch duration mutability. The epoch is used in so many places that such migrations would be extremely hard to develop and get right.
