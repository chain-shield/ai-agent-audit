S-291
Unrestricted `amp` factor could lead to price manipulation
OxElliot
00
Sufficient
383d ago
Finding description and impact

The StableSwap pool creation mechanism in the DEX protocol allows users to specify an unbounded amplification factor (amp) during pool creation. If the PoolType is StableSwap, the user must specify the amp value (a u64) and there are no restrictions on the value of amp factor. This oversight enables the creation of pools with extreme amplification values, leading to significant price discrepancies and allowing arbitrage exploitation between pools.

An attacker can leverage this vulnerability to manipulate the price dynamics of the pools, systematically draining liquidity and extracting value from liquidity providers. If the PoolType is StableSwap, the user must specify the amp value (a u64).

Root Cause

The implementation permits any u64 value for the amplification factor during the pool creation process, and whenever the d is computed for a swap, either for liquidity addition or swaps,
compute_swap, calculate_stable_swap, compute_next_d etc, are called and they take user provided amp_factor for calculation:

// ann = amp * n_coins
    let ann = Decimal256::from_ratio(Uint256::from_u128((*amp).into()).checked_mul(n_coins)?, 1u8);
 d = compute_next_d(amp_factor, d, d_prod, sum_x, n_coins).unwrap();

The protocol also allows to create pools with radically different pricing behavior for the same token pair.

Impact

This vulnerability allows systematic value extraction from liquidity providers and introduces severe instability in the protocol:
An attacker can create two pools with drastically different amp values for the same token pair:

Pool A: Low amp (approximates constant product, x * y = k).
Pool B: High amp (approximates constant sum, x + y = C).

By executing swaps between these pools, the attacker can profit from the price discrepancies. Legitimate liquidity providers may withdraw liquidity due to unpredictable pool behavior, reducing the overall utility of the protocol.

Proof Of Concept
Arbitrage Setup

The attacker creates two pools with the same token pair (Token X and Token Y):

Pool A (Low Amp):
• amp = 1 (Constant Product behavior).
• Initial liquidity: Token X = 1000, Token Y = 1000.

Pool B (High Amp):
• amp = 10^9 (Constant Sum behavior).
• Initial liquidity: Token X = 1000, Token Y = 1000.

Arbitrage Execution
1. Swap Token X in Pool A to create slippage and reduce the price of Token Y.
2. Swap the received Token Y in Pool B to recover Token X with minimal slippage.

Profit Analysis

For a single arbitrage cycle:

Low Amp Pool (Pool A):
Swap 100 Token X: Output ≈ 90.91 Token Y.
Price Impact: ~9.09%.
High Amp Pool (Pool B):
Swap 90.91 Token Y: Output ≈ 99.99 Token X.
Price Impact: ~0.01%.

Net Profit per Cycle for 100 tokens:

Initial input: 100 tokens
Output from low amp pool: 90.91 tokens
Input to high amp pool: 90.91 tokens
Final output: ≈ 99.99 tokens
Gross profit: 8.86 tokens (8.86%)

After accounting for protocol fees:

let pool_fees = PoolFee {
    protocol_fee: Fee { share: Decimal::from_ratio(1u128, 1000u128) },
    swap_fee: Fee { share: Decimal::from_ratio(1u128, 10_000_u128) },
};
Total fees per cycle: 0.22% (0.11% * 2 swaps)
Net profit: ≈8.64% per cycle
Recommended Remediation

Implement strict bounds for amplification factors:

const MIN_AMP_FACTOR: u64 = 100;
const MAX_AMP_FACTOR: u64 = 1_000;

fn validate_amp_factor(amp: u64) -> Result<(), ContractError> {
    ensure!(
        amp >= MIN_AMP_FACTOR && amp <= MAX_AMP_FACTOR,
        ContractError::InvalidAmpFactor {
            provided: amp,
            min: MIN_AMP_FACTOR,
            max: MAX_AMP_FACTOR,
        }
    );
    Ok(())
}

Add validation in pool creation:

pub fn create_pool(
    deps: DepsMut,
    env: Env,
    info: MessageInfo,
    asset_denoms: Vec<String>,
    asset_decimals: Vec<u8>,
    pool_fees: PoolFee,
    pool_type: PoolType,
    pool_identifier: Option<String>,
) -> Result<Response, ContractError> {
    match pool_type {
        PoolType::StableSwap { amp } => validate_amp_factor(amp)?,
        _ => {}
    }
    // ... rest of the implementation
}
