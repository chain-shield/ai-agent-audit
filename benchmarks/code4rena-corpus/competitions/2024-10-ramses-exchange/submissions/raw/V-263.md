# Vulnerability details

## Proof of Concept
Explain and rationalize the potential impact. Provide:

Within this source code snippet below, there is a reentrancy vulnerability: 


```solidity
    /// @dev Deploys a pool with the given parameters by transiently setting the parameters storage slot and then
    /// clearing it after deploying the pool.
    /// @param token0 The first token of the pool by address sort order
    /// @param token1 The second token of the pool by address sort order
    /// @param tickSpacing The tickSpacing of the pool
    function deploy(address token0, address token1, int24 tickSpacing) external returns (address pool) {
        require(msg.sender == RamsesV3Factory);
        pool = address(new RamsesV3Pool{salt: keccak256(abi.encodePacked(token0, token1, tickSpacing))}());
    }
```

In the above snippeet, the `deploy` function is vulnerable to reentrancy attacks. 

An attacker can call this function and then within the constructor of the newly deployed `RamsesV3Pool` contract, call back into the `deploy` function again before the storage slot for parameters is cleared. 

This would allow the attacker to potentially manipulate the state of the contract, or drain funds.

Here's an example PoC that would exploit this vulnerability in the code: 

```solidity
pragma solidity ^0.8.20;

contract Attacker {
    address public immutable target;

    constructor(address _target) {
        target = _target;
    }

    function attack() public {
        // Trigger reentrancy by calling deploy again within the constructor of RamsesV3Pool
        IRamsesV3PoolDeployer(target).deploy(address(0), address(0), 100);
    }
}
```


This above exploit code defines a contract `Attacker` that takes the address of the vulnerable `RamsesV3PoolDeployer` contract as input. 

The `attack()` function calls the `deploy` function of the target contract, passing arbitrary addresses for `token0`, `token1`, and `tickSpacing`.

The key to this exploit is that the constructor of `RamsesV3Pool` (which is implicitly called when deploying a new instance) could potentially contain another call to `deploy`. 

This creates a reentrancy loop where the attacker's contract can repeatedly call `deploy` before the storage slot for parameters in the `RamsesV3PoolDeployer` contract is cleared.

This allows the attacker to manipulate the state of the contract or drain funds, depending on how the vulnerable `RamsesV3Pool` contract is implemented.

## Recommended Mitigation Steps

Ok, some possible Mitigation steps are as follows...

--Implement OpenZeppelin's ReentrancyGuard in the contract to prevent reentrant calls to the deploy function. This ensures that the function can only be executed once per transaction
one example of this is as follows: 

```solidity
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

contract RamsesV3PoolDeployer is ReentrancyGuard {
    function deploy(address token0, address token1, int24 tickSpacing) external nonReentrant returns (address pool) {
        require(msg.sender == RamsesV3Factory);
        pool = address(new RamsesV3Pool{salt: keccak256(abi.encodePacked(token0, token1, tickSpacing))}());
    }
}
```

--Second mitigation recommendation is to consider clearing state before external calls.  This means clearing any mutable state variables (such as storage slots for parameters) before making any external calls, including contract deployment. 

This prevents an attacker from modifying the state during a reentrant call.

```solidity
function deploy(address token0, address token1, int24 tickSpacing) external returns (address pool) {
    require(msg.sender == RamsesV3Factory);
    // this clears the parameters before any external calls...
    address _token0 = token0;
    address _token1 = token1;
    int24 _tickSpacing = tickSpacing;
    token0 = address(0);
    token1 = address(0);
    tickSpacing = 0;

    pool = address(new RamsesV3Pool{salt: keccak256(abi.encodePacked(_token0, _token1, _tickSpacing))}());
}
```

The third mitigation is to make limitations on deployment attempts.  The idea here would be to introduce logic that limits how often the deploy function can be called in a single transaction or within a specific time frame. 

This could prevent rapid reentrant deployments.

Here's an example of this mitigation: 

```solidity 
uint256 lastDeployTime;

function deploy(address token0, address token1, int24 tickSpacing) external returns (address pool) {
    require(block.timestamp > lastDeployTime + 1 minutes, "Deployment cooldown active");
    lastDeployTime = block.timestamp;
    require(msg.sender == RamsesV3Factory);
    pool = address(new RamsesV3Pool{salt: keccak256(abi.encodePacked(token0, token1, tickSpacing))}());
}
```

The fourth mitigation is a general recommendation to really minimize external calls within critical functions to reduce the risk of reentrancy.   Ideally, suggest that the devs move external contract deployment OUTSIDE of sensitive areas, or requiring a separate transaction.
