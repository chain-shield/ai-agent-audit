# Vulnerability details

## Proof of Concept
```
   function newPeriod(
        Observation[65535] storage self,
        uint16 index,
        uint256 period
    ) external returns (uint160 secondsPerLiquidityCumulativeX128) {
        Observation memory last = self[index];
        PoolStorage.PoolState storage $ = PoolStorage.getStorage();

        unchecked {
            uint32 delta = uint32(period) * 1 weeks - 1 - last.blockTimestamp;

            secondsPerLiquidityCumulativeX128 =
                last.secondsPerLiquidityCumulativeX128 +
                ((uint160(delta) << 128) / ($.liquidity > 0 ? $.liquidity : 1));

            self[index] = Observation({
                blockTimestamp: uint32(period) * 1 weeks - 1,
                tickCumulative: last.tickCumulative + int56($.slot0.tick) * int56(uint56(delta)),
                secondsPerLiquidityCumulativeX128: secondsPerLiquidityCumulativeX128,
                initialized: last.initialized
            });
        }
    }
```
Protocol implemented this function can be callable by anyone .First off, let's talk about timestamp manipulation. If someone were to mess with the blockTimestamp value, it could really screw up the chronological order of observations. This could lead to all sorts of issues, like incorrect price calculations, manipulation of time-weighted average prices (TWAP), and even potential arbitrage or flash loan attacks. Not good!
Next up, price manipulation. If someone starts altering the tickCumulative value, it could directly impact the calculated price of the pool. This could result in incorrect swap prices, unfair liquidations. That's a recipe for disaster.
Moving on to liquidity manipulation. If someone gets their hands on the secondsPerLiquidityCumulativeX128 value and starts modifying it, it could affect calculations related to liquidity provision rewards. This might lead to unfair distribution of fees, incorrect liquidity incentives, and even the potential for draining funds from the pool. Yikes!

Vulnerability
In the newPeriod function:
solidity
```
unchecked {
    uint32 delta = uint32(period) * 1 weeks - 1 - last.blockTimestamp;
    // ... rest of the code
}
```
The delta calculation is performed within an unchecked block, which means that underflow will not revert the transaction but instead wrap around.
Potential Exploit Scenario
If last.blockTimestamp is greater than uint32(period) * 1 weeks - 1, delta will underflow.
For example:

If period = 1, then uint32(period) * 1 weeks - 1 = 604799 (1 week in seconds minus 1)
If last.blockTimestamp = 604800 (exactly 1 week), then delta = 604799 - 604800 = 4294967295 (2^32 - 1)


Impacts

Incorrect Seconds Per Liquidity Calculation:
```solidityCopysecondsPerLiquidityCumulativeX128 =
    last.secondsPerLiquidityCumulativeX128 +
    ((uint160(delta) << 128) / ($.liquidity > 0 ? $.liquidity : 1));
```
An inflated delta will cause secondsPerLiquidityCumulativeX128 to increase dramatically, leading to incorrect fee calculations and liquidity provider rewards.

Tick Cumulative Manipulation:
```solidityCopytickCumulative: last.tickCumulative + int56($.slot0.tick) * int56(uint56(delta)),```
The inflated delta will cause the tickCumulative to change significantly, potentially in either a positive or negative direction depending on the current tick. This can lead to:

1. Incorrect price calculations
2. Manipulation of time-weighted average prices (TWAP)
3. Potential for arbitrage attacks

Potential Exploit Path

1. An attacker identifies a situation where last.blockTimestamp is close to wrapping around.
2. They call newPeriod with a carefully chosen period value to cause delta to underflow.
3. This results in a massive spike in secondsPerLiquidityCumulativeX128 and tickCumulative.
4. The attacker then quickly performs trades or liquidity provisions to take advantage of the incorrect state.
5. They might also manipulate oracle-dependent protocols that rely on this pool's data.
