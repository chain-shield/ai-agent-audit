# Vulnerability details

## Proof of Concept

Here's the vulnerable code snippet in the above solidity contract. 
```solidity
    require(msg.sender == RamsesV3Factory);
```

The code snippet ,above, demonstrates a potential access control vulnerability. The line `require(msg.sender == RamsesV3Factory);` restricts the `deploy` function to only be callable by the address stored in the `RamsesV3Factory` variable. 

This means that any malicious actor who gains control of the `RamsesV3Factory` contract could potentially deploy arbitrary pools with their own chosen parameters, bypassing intended authorization mechanisms.


The code enforces access control by requiring that the `msg.sender` (the address initiating the transaction) must be equal to the `RamsesV3Factory` contract address. If an attacker gains control of the `RamsesV3Factory` contract, they can impersonate it and call the `deploy` function, potentially deploying malicious pools with unintended parameters.

Explain and rationalize the potential impact. 

Some potential impacts are as follows. 

One impact is that there is unauthorized pool creation.  An attacker who gains control over the RamsesV3Factory contract could deploy arbitrary pools with malicious or unintended parameters. 

This would allow them to manipulate key characteristics of the pools, which could disrupt normal operations on the Ramses blockchain.

Another impact is that there is the possible deployment of malicious pools.  Malicious pools could be deployed with fake tokens, incorrect tick spacing, or vulnerable parameters that could be exploited further. 

This could lead to drained liquidity from legitimate pools or manipulated pricing within the exchange.

Yet a third possible impact would be general systemic risk to the liquidity providers.  What I mean by this is that if attackers can deploy malicious pools that impersonate valid ones, liquidity providers (LPs) might unknowingly provide liquidity to these pools, putting their funds at risk. LPs could suffer financial losses as attackers exploit the pool's vulnerabilities or manipulate fees and rewards

Such an exploited vulnerability could indeed also cause loss of trust in the protocol, causing a cascade effect of devaluation of the protocol, etc.

There is also the potential for other contract manipulations through exploitation of this vuln. If the attacker deploys pools with contracts they control, they may interact with other parts of the Ramses ecosystem to further exploit incentives, rewards, or governance, potentially creating system-wide instability.

## Recommended Mitigation Steps

There are several mitigation steps I'd advise.   

--the first mitigation I'd recommend is implementing ownership validation.  Using OpenZeppelin’s Ownable contract or similar mechanisms ensures that only authorized entities, such as the contract owner, can deploy pools. 

This prevents an attacker from gaining unauthorized control in this way. 

Here's an example of what I mean: 

```solidity

import "@openzeppelin/contracts/access/Ownable.sol";

contract RamsesV3PoolDeployer is Ownable {
    function deploy(address token0, address token1, int24 tickSpacing) external onlyOwner returns (address pool) {
        require(msg.sender == RamsesV3Factory);
        pool = address(new RamsesV3Pool{salt: keccak256(abi.encodePacked(token0, token1, tickSpacing))}());
    }
}
```

--the second mitigation I'd recommend is the use of Role based access control (or RBAC)... This  role-based access control using OpenZeppelin's AccessControl contract to ensure only designated roles (e.g., deployer role) have access to the deploy function.

Here's an example of this: 

```solidity

import "@openzeppelin/contracts/access/AccessControl.sol";

contract RamsesV3PoolDeployer is AccessControl {
    bytes32 public constant DEPLOYER_ROLE = keccak256("DEPLOYER_ROLE");
    
    constructor() {
        _setupRole(DEFAULT_ADMIN_ROLE, msg.sender);
        _setupRole(DEPLOYER_ROLE, msg.sender);
    }

    function deploy(address token0, address token1, int24 tickSpacing) external onlyRole(DEPLOYER_ROLE) returns (address pool) {
        pool = address(new RamsesV3Pool{salt: keccak256(abi.encodePacked(token0, token1, tickSpacing))}());
    }
}
```

--the third mitigation I'd recommend is to verify the factory address at deployment time.  

Specifically, this means ensuring that the RamsesV3Factory address is set immutably at the contract's deployment and cannot be altered by unauthorized users. This prevents attackers from modifying the factory address to their own malicious contract.

An example of this is: 

```solidity

address public immutable RamsesV3Factory;

constructor(address _factory) {
    require(_factory != address(0), "Invalid factory address");
    RamsesV3Factory = _factory;
}

function deploy(address token0, address token1, int24 tickSpacing) external returns (address pool) {
    require(msg.sender == RamsesV3Factory, "Not authorized factory");
    pool = address(new RamsesV3Pool{salt: keccak256(abi.encodePacked(token0, token1, tickSpacing))}());
}
```

--the fourth recommendation I'd make in the source code to avoid vulnerabilities such as this one would be to deploy via factory contract ONLY.  This requires that all pool deployments are handled through the factory contract and not directly by any external address. The factory contract itself should enforce strong access controls and validations.

One example of this in code is as follows: 

```solidity

function deploy(address token0, address token1, int24 tickSpacing) external returns (address pool) {
    require(msg.sender == address(RamsesV3Factory), "Only factory can deploy pools");
    pool = RamsesV3Factory.createPool(token0, token1, tickSpacing);
}
```

--finally, I'd also recommend that the contract is audited before deployment.  This is to look for edge cases that have access control vulns.
