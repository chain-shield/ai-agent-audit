# Vulnerability details

## Description

The `createPool` function is currently exposed as an external function without any access controls:

```solidity
function createPool(
    address tokenA,
    address tokenB,
    int24 tickSpacing,
    uint160 sqrtPriceX96
) external override returns (address pool) {
    // Function body...
}
```

This means that any external actor can call this function and create new pools at will. In a decentralized finance (DeFi) protocol, especially one dealing with automated market making, this is a severe security risk.

## Exploit Scenarios

1) Spam Attack:
An attacker could create a large number of pools with various token pairs and tick spacings. For example:

```solidity
for (int24 i = 1; i < 1000; i++) {
    factory.createPool(address(0x123), address(0x456), i, 1);
}
```

This could flood the protocol with useless pools, making it difficult for legitimate users to find valid trading pairs.

2) Fake Token Pools:
A malicious actor could deploy fake tokens and create pools with them:

```solidity
address fakeToken1 = deployFakeToken();
address fakeToken2 = deployFakeToken();
factory.createPool(fakeToken1, fakeToken2, 10, 1);
```

This could trick users into trading with these fake pools, potentially leading to financial losses.

3) Resource Exhaustion:
Unchecked pool creation could lead to excessive gas consumption and storage bloat on the blockchain. Each pool creation stores data in the contract's state:

```solidity
getPool[token0][token1][tickSpacing] = pool;
getPool[token1][token0][tickSpacing] = pool;
```

An attacker could create many pools, increasing the contract's storage size significantly.

4) Manipulation of Protocol Parameters:
The function sets initial fees based on the tick spacing:

```solidity
uint24 fee = tickSpacingInitialFee[tickSpacing];
```

An attacker could potentially create pools with specific tick spacings to take advantage of certain fee structures.

## Impact

- Users can't trust that all pools in the protocol are legitimate.
- The protocol's economic model could be distorted by an abundance of fake or spam pools.
- The system's performance could degrade due to the increased number of pools.
- Users might incur higher gas costs when interacting with the protocol due to the increased state size.

## Code Snippet

```solidity
function createPool(
    address tokenA,
    address tokenB,
    int24 tickSpacing,
    uint160 sqrtPriceX96
) external override returns (address pool) {
    require(tokenA != tokenB, IT());
    (address token0, address token1) = tokenA < tokenB ? (tokenA, tokenB) : (tokenB, tokenA);
    require(token0 != address(0), A0());
    uint24 fee = tickSpacingInitialFee[tickSpacing];
    require(fee != 0, F0());
    require(getPool[token0][token1][tickSpacing] == address(0), PE());

    parameters = Parameters({
        factory: address(this),
        token0: token0,
        token1: token1,
        fee: fee,
        tickSpacing: tickSpacing
    });
    pool = IRamsesV3PoolDeployer(ramsesV3PoolDeployer).deploy(token0, token1, tickSpacing);
    delete parameters;

    getPool[token0][token1][tickSpacing] = pool;
    getPool[token1][token0][tickSpacing] = pool;
    emit PoolCreated(token0, token1, fee, tickSpacing, pool);

    if (sqrtPriceX96 > 0) {
        IRamsesV3Pool(pool).initialize(sqrtPriceX96);
    }
}
```

While the function includes checks for valid inputs (non-zero addresses, non-existent pools), it lacks any verification of the caller's authority to create pools.

## Recommended Fix

To address this vulnerability, implement access control using OpenZeppelin's `AccessControl`. Here's how you could modify the contract:

```solidity
import "@openzeppelin/contracts/access/AccessControl.sol";

contract RamsesV3Factory is IRamsesV3Factory, AccessControl {
    bytes32 public constant POOL_CREATOR_ROLE = keccak256("POOL_CREATOR_ROLE");

    constructor(address accessManager) AccessManaged(accessManager) {
        _setupRole(DEFAULT_ADMIN_ROLE, msg.sender);
        _setupRole(POOL_CREATOR_ROLE, msg.sender);
    }

    function createPool(
        address tokenA,
        address tokenB,
        int24 tickSpacing,
        uint160 sqrtPriceX96
    ) external override onlyRole(POOL_CREATOR_ROLE) returns (address pool) {
        // Existing function body...
    }

    function grantPoolCreatorRole(address account) external onlyRole(DEFAULT_ADMIN_ROLE) {
        grantRole(POOL_CREATOR_ROLE, account);
    }
}
```

This modification ensures that only addresses with the `POOL_CREATOR_ROLE` can create new pools.
