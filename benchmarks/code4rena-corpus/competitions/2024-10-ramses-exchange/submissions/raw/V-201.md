# Vulnerability details

## Summary
The `update` function in the Tick library lacks a minimum liquidity threshold check when modifying tick liquidity. While it prevents excessive liquidity through `maxLiquidity`, it allows ticks to maintain near-zero liquidity (anything > 0). This creates thin liquidity zones that are vulnerable to price manipulation, as extremely low liquidity in active ticks can lead to excessive price impacts from small trades. The issue is particularly severe in concentrated liquidity AMMs where price changes are inversely proportional to available liquidity.s

The issue centers around how liquidity adjustments are handled in the AMM's tick system. The vulnerability lies in this section of the update function:

```solidity
uint128 liquidityGrossBefore = info.liquidityGross;
uint128 liquidityGrossAfter = liquidityDelta < 0
    ? liquidityGrossBefore - uint128(-liquidityDelta)
    : liquidityGrossBefore + uint128(liquidityDelta);

if (liquidityGrossAfter > maxLiquidity) revert LO();
```

While this code appears to handle liquidity changes safely at first glance, it only implements an upper bound check through the `maxLiquidity` comparison. The function assumes that any non-zero liquidity amount is acceptable, which creates subtle but exploitable issues in the AMM's price discovery mechanism.

Consider how liquidity affects price movement in concentrated liquidity AMMs. When liquidity is extremely low in a tick range, even small trades can cause significant price movements. The function allows liquidity to be reduced to any value above zero:

```solidity
// Example scenario
int128 liquidityDelta = -(info.liquidityGross - 1); // Reduce to minimal liquidity
update(..., liquidityDelta, ...);  // This would succeed
```

This becomes particularly problematic when we examine how the tick system interacts with price calculations. In a healthy AMM, each tick should have sufficient liquidity to maintain price stability. When a tick has minimal liquidity, it creates what's effectively a "thin ice" scenario where price manipulation becomes feasible.

The vulnerability manifests in practice through the interaction with the pool's swap function (not shown in this contract). Here's how an attacker could exploit this:

1. First, they identify a tick range with moderate liquidity:
```solidity
// Initial state
tick 100: liquidityGross = 10000
tick 200: liquidityGross = 10000
```

2. They can then reduce the liquidity to a minimal amount through multiple small transactions:
```solidity
// Attacker reduces liquidity
function performAttack(int24 targetTick) {
    int128 reduceAmount = -9999; // Leaves 1 unit of liquidity
    update(
        ticks,
        targetTick,
        currentTick,
        reduceAmount,
        feeGrowth0,
        feeGrowth1,
        ...
    );
}
```

3. With minimal liquidity in place, they can execute trades that cause extreme price movements:
```solidity
// Price manipulation potential
// Assuming 1 unit of liquidity remains
// Even a small trade can now move price significantly across this tick
swap(small_amount); // Results in large price impact
```

The root cause becomes clearer when we examine how concentrated liquidity AMMs calculate price impact. The price change (Δp) is inversely proportional to liquidity (L):

```solidity
// Simplified price impact formula
// Δp ∝ Δx/L
// As L approaches 1, Δp becomes very large for any Δx
```

## Fix
The fix requires implementing a minimum liquidity threshold that maintains market stability. Here's how we could modify the update function:

```solidity
function update(
    mapping(int24 => TickInfo) storage self,
    int24 tick,
    int24 tickCurrent,
    int128 liquidityDelta,
    ...
) internal returns (bool flipped) {
    TickInfo storage info = self[tick];
    uint128 liquidityGrossBefore = info.liquidityGross;
    uint128 liquidityGrossAfter = liquidityDelta < 0
        ? liquidityGrossBefore - uint128(-liquidityDelta)
        : liquidityGrossBefore + uint128(liquidityDelta);

    // Add minimum liquidity check
    uint128 constant MIN_LIQUIDITY = 100; // Example threshold
    if (liquidityGrossAfter > maxLiquidity) revert LO();
    if (liquidityGrossAfter < MIN_LIQUIDITY && liquidityGrossAfter != 0) {
        revert("Insufficient liquidity");
    }
    
    // Rest of the function...
}
```


The fix ensures that any active tick maintains enough liquidity to resist basic manipulation attempts while still allowing positions to be fully closed (liquidityGrossAfter = 0). This creates a binary state where ticks are either properly funded or completely inactive, eliminating the dangerous middle ground of minimal liquidity.

A proper implementation would also consider the relationship between minimum liquidity and tick spacing, as tighter tick spacing typically requires higher minimum liquidity to maintain the same level of price stability. The exact minimum liquidity value should be determined through economic analysis of the expected trading volumes and desired price impact limits.
