# Vulnerability details

## Proof of Concept
The `FeeCollector` contract includes inefficient gas usage and suboptimal execution order, which could result in excess gas consumption and potentially unexpected behavior in the `collectProtocolFees` function. By restructuring the execution flow and gas optimization, we can mitigate unnecessary costs and improve the contract’s performance. Additionally, the vulnerability allows for funds to be collected when certain conditions (e.g., token or gauge being inactive) are not properly checked, leading to incorrect fee distributions.

The `collectProtocolFees` function is designed to collect protocol fees from a pool, check for a gauge, and distribute fees either to the treasury or the fee distributor. However, the execution order is suboptimal, leading to higher gas consumption, and under certain conditions, could cause fees to be collected and transferred without validation checks.

Key points of the vulnerability:

1. Inefficient Execution Order: The function calls `pool.collectProtocol` to collect fees regardless of whether a gauge is active or alive, or whether the token is live. This leads to unnecessary fee collection when fees should not be collected, especially when no valid gauge exists or when `isTokenLive` is false.
2. Unnecessary Operations: Even if the condition for a valid gauge or isTokenLive is not met, the function performs redundant operations like transferring fees, which increases the overall gas cost.
3. Missing Early Exit: The function continues executing after determining that no valid gauge exists or when `isTokenLive` is false, instead of exiting early.
```solidity
function collectProtocolFees(IRamsesV3Pool pool) external override {
    /// @dev get tokens
    IERC20 token0 = IERC20(pool.token0());
    IERC20 token1 = IERC20(pool.token1());

    /// @dev check if there's a gauge
    IVoter _voter = voter;
    address gauge = _voter.gaugeForPool(address(pool));
    bool isAlive = _voter.isAlive(gauge);

    /// @dev check if it's a cl gauge redirected to another gauge
    if (gauge == address(0) || !isAlive) {
        address toPool = _voter.poolRedirect(address(pool));
        gauge = _voter.gaugeForPool(address(toPool));
        isAlive = _voter.isAlive(gauge);
    }

    /// @dev if there's no gauge, there's no fee distributor, send everything to the treasury directly
    if (gauge == address(0) || !isAlive || !isTokenLive) {
        (uint128 _amount0, uint128 _amount1) = pool.collectProtocol(
            treasury,
            type(uint128).max,
            type(uint128).max
        );

        emit FeesCollected(address(pool), 0, 0, _amount0, _amount1);
        return;
    }

    /// @dev get the fee distributor
    IFeeDistributor feeDist = IFeeDistributor(
        _voter.feeDistributorForGauge(gauge)
    );

    /// @dev using uint128.max here since the pool automatically determines the owed amount
    pool.collectProtocol(
        address(this),
        type(uint128).max,
        type(uint128).max
    );
```

## Impact
The vulnerability affects the efficiency of the contract, increasing the gas cost of the `collectProtocolFees` function. Additionally, it allows for fee collection even when certain conditions, such as gauge inactivity or the token being non-live, should prevent it.

The function could perform unnecessary fee collection, costing users or protocols additional gas.

Fees may be sent to the treasury or fee distributor without proper checks, leading to incorrect distributions.

## Recommended Mitigation Steps
1. Perform initial checks (e.g., whether the gauge is valid or `isTokenLive` is true) before calling `pool.collectProtocol` and performing other expensive operations.
2. Return early if conditions are not met, such as when no gauge exists or `isTokenLive` is false, to avoid redundant operations.
3. Ensure that unnecessary external calls are avoided when the conditions for fee collection are not met.
```solidity

    IVoter _voter = voter;
```
