# Vulnerability details

## Proof of Concept
The [`setFee()`](https://github.com/code-423n4/2024-10-ramses-exchange/blob/236e9e9e0cf452828ab82620b6c36c1e6c7bb441/contracts/CL/core/libraries/ProtocolActions.sol#L75-L82) function is esential for setting `$.fee`:
```solidity
    function setFee(uint24 _fee, address factory) external {
        PoolStorage.PoolState storage $ = PoolStorage.getStorage();
        if (msg.sender != factory) revert Unauthorized();
>>      if (_fee > 100000) revert InvalidFee();
        uint24 _oldFee = $.fee;
>>      $.fee = _fee;
        emit FeeAdjustment(_oldFee, _fee);
    }
```
Here, the `fee` is constrained by the check `if (_fee > 100000) revert InvalidFee();`, where the maximum allowed value of `_fee` is `100,000`, corresponding to a `10% fee` in basis points. This check is too restrictive and does not reflect real-world requirements, where fees greater than `10%` might be justified.

However, the check requires that `_fee` should not exceed `100000` which is `10%` considering its application. Here is how is is used in [`flash()`](https://github.com/code-423n4/2024-10-ramses-exchange/blob/236e9e9e0cf452828ab82620b6c36c1e6c7bb441/contracts/CL/core/RamsesV3Pool.sol#L690-L691) to detemine `fee0` and `fee1` from `amount0` and `amount1`:
```solidity
        uint256 fee0 = FullMath.mulDivRoundingUp(amount0, $.fee, 1e6);
        uint256 fee1 = FullMath.mulDivRoundingUp(amount1, $.fee, 1e6);
```
The fees (`fee0` and `fee1`) are computed by multiplying the loan amount by `$.fee` and dividing by `1_000_000` (basis points).
With the current cap, the `maximum fee` is limited to `10% `of the `amount` (`100000/1e6 = 0.1`), even though there might be scenarios where higher fees are necessary.

**Note**:
Indeed `ProtocolActions.sol` is OOS but the `setFee()` in it is in only callabe from `factory` contract (*in scope*) and as seen, the set value impacts operation in the pool contract (*also in scope*). As such, it is worth reporting.

## Impact
The current `fee` cap in the `ProtocolActions.setFee()` function is limited to `10%`, which is unnecessarily restrictive and does not align with the intended design or flexibility required by the protocol. This constraint could prevent setting higher fees for certain operations where a higher fee might be necessary, leading to reduced protocol functionality or inefficient capital use.

If the protocol needs to charge more than `10%`, this limitation restricts potential revenue for the protocol, especially in scenarios that justify higher fees.

## Recommended Mitigation Steps
Set an appropriate upper limit that reflects the highest realistic fee the protocol would want to charge is crucial.
