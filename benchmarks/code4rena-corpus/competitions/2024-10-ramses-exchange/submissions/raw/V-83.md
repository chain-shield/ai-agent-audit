# Vulnerability details

## Vulnerability Details
Ramses introduces a new concept of weekly periods registered in the Oracle's observations. 

Problem is that due to the logic of how a period is calculated: 
https://github.com/code-423n4/2024-10-ramses-exchange/blob/236e9e9e0cf452828ab82620b6c36c1e6c7bb441/contracts/CL/core/RamsesV3Pool.sol#L429

```solidity
uint256 period = _blockTimestamp() / 1 weeks;
```

This causes the Oracle to override a previously registered observation(without the newPeriod logic, for instance when the user calls `swap` or `modifyLiquidity`) and vice versa. When user swaps or modify liquidity, the current timestamp is used to register/update the observation. i.e:

```solidity
 function _modifyPosition(
        ModifyPositionParams memory params
    ) private returns (PositionInfo storage position, int256 amount0, int256 amount1) {
   ...
   ($.slot0.observationIndex, $.slot0.observationCardinality) = Oracle.write(
                    $.observations,
@>                    _slot0.observationIndex,
@>                    _blockTimestamp(),
                    _slot0.tick,
                    liquidityBefore,
                    _slot0.observationCardinality,
                    _slot0.observationCardinalityNext
                );
  ...
```

Now that we understand how observations are handled let's understand why this is a problem: 

The calculation for the period rounds the value down which makes sense as `newPeriods` are created once a new week has been reached. 

```solidity
uint256 period = _blockTimestamp() / 1 weeks;
```

And they are registered as following 
```solidity
           self[index] = Observation({
@>                blockTimestamp: uint32(period) * 1 weeks - 1,
                tickCumulative: last.tickCumulative + int56($.slot0.tick) * int56(uint56(delta)),
                secondsPerLiquidityCumulativeX128: secondsPerLiquidityCumulativeX128,
                initialized: last.initialized
            });
```

See that we convert it back to timestamp, but as it truncates when converting from timestamp to period, it will always return the start of the last week instead of the current block time stamp that was converted to period.






## Proof of Concept
The problem with this is the following:

1. The week starts, and a user adds liquidity 10 hours later. The `advancePeriod` modifier is triggered, registering the new period with the truncated value that points to the start of the week, rather than the actual time.

```solidity
blockTimestamp: uint32(period) * 1 weeks - 1
```

2. There are two new entries in the observations: 
 - One registered 10h ago made by the `Oracle.newPeriod` call.
 - One 10h after(current time stamp) made by the addition of liquidity.

3. This creates a price/time discrepancy: although the events happened within a 1-minute interval, when querying the oracle for prices from, say, 30 minutes ago, it will return a different price than what actually occurred. **Due to the observations having a different of 10h those entries.** 


## Impact

**Inaccurate price data**: Oracle readings could return incorrect prices due to the time discrepancy, leading to misinformed trading decisions or price manipulations.

**Unreliable historical data**: Time-based queries for past prices may yield misleading results, impacting protocols relying on precise price history for calculations like TWAP (Time-Weighted Average Price).


## Recommended Mitigation Steps
The observations should always be stored respecting the current time stamp. Therefore, replace the current `blockTimestamp: uint32(period) * 1 weeks - 1` by the current timestamp, a.k.a `_blocktimeStamp()`
