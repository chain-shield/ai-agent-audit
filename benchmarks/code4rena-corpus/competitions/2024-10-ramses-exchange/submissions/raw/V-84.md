# Vulnerability details

## Vulnerability Details
When a user modifies liquidity multiple times within the same period within the same tick range (thus generating the same hash for their position), the `initializeSecondsStart` function is only triggered during the **first liquidity update**. 

While the position hash remains the same, subsequent liquidity changes do not correctly update the reward-tracking variables (`secondsPerLiquidityPeriodX128` and `secondsDebtX96`), resulting in over-rewarding or under-rewarding the user due to stale values being used.

Let's see how this happens: 
`mint/burn` => `_modifyPosition` => `_updatePosition`: 

```solidity
    function _updatePosition(UpdatePositionParams memory params) external returns (PositionInfo storage position) {
         …
	
             // @audit hash can be the same when modifying position
@>        bytes32 _positionHash = positionHash(params.owner, params.index, params.tickLower, params.tickUpper);

             // @audit position already exists/intialized
@>        position = $.positions[_positionHash];
       …

            // @audit getting the `secondsPerLiquidityPeriodX128` based on the current timestamp/liquidity
@>        uint160 secondsPerLiquidityPeriodX128 = Oracle.periodCumulativesInside(
            uint32(period),
            params.tickLower,
            params.tickUpper,
            params._blockTimestamp
        );


             // @audit as position is already initialized and liquidity > 0, the call to `initializeSecondsStart` is skipped
             // leaving the `secondsDebtX96` and the position `secondsPerLiquidityPeriodStartX128` unchanged.
@>        if (!position.periodRewardInfo[period].initialized || position.liquidity == 0) {
@>            initializeSecondsStart(
                position,
                PositionPeriodSecondsInRangeParams({
                    period: period,
                    owner: params.owner,
                    index: params.index,
                    tickLower: params.tickLower,
                    tickUpper: params.tickUpper,
                    _blockTimestamp: params._blockTimestamp
                }),
                secondsPerLiquidityPeriodX128
            );
        }
    }

```

In a nutshell, after the first liquidity update in a period, the `initialized` flag prevents re-initialization of reward tracking for further liquidity changes, resulting in over-rewarding or under-rewarding the user.


## Proof of Concept
1. A user adds liquidity at the start of the period, and `initializeSecondsStart` is correctly called. The user receives the appropriate reward share for the time their liquidity is active.

2. Later in the same period, the user removes the liquidity leaving only dust left but yet keeping the the **same position (same ticks)**. The initialization logic won’t run again because `position.periodRewardInfo[period].initialized` is true. As a result, the starting point for the new liquidity isn’t updated properly.

3. At the end of the period, the user’s rewards are calculated as all the liquidity was present from the start of the period, leading to over-rewarding the user.

## Recommended Mitigation Steps
Ensure that `secondsPerLiquidityPeriodX128` and `secondsDebtX96` are updated dynamically for every liquidity change, **even if the position hash remains the same** a.k.a same hash, to correctly track the reward for each liquidity modification within the period.
