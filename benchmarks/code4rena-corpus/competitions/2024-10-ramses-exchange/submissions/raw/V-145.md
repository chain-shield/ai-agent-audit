# Vulnerability details

## Vulnerability details

Note: I am using `F` in this report which indicates the value of the state var `RamsesV3Factory.feeProtocol`.

Only the owner is allowed to set the protocol fee for a `RamsesV3Pool`, according to the interface `IRamsesV3PoolOwnerActions` see line 727-728 in RamsesV3Pool.sol:

```solidity
/// @inheritdoc IRamsesV3PoolOwnerActions
function setFeeProtocol() external override lock {
    ProtocolActions.setFeeProtocol(factory);
}
```

However `RamsesV3Pool::setFeeProtocol()` may be called by anybody since it's lacking the appropriate access modifiers. This function may be used by a malicious actor to update any pool's protocol fee which was 0 before.

This happens because `ProtocolActions::setFeeProtocol()` which is subsequently called is fetching the new protocol fee via `RamsesV3Factory::poolFeeProtocol()` to update the pool's protocol fee (line 34-37 ProtocolAction.sol). And `RamsesV3Factory::poolFeeProtocol()` returns `RamsesV3Factory.feeProtocol` if `_poolFeeProtocol[pool]` is 0 (line 165 RamsesV3Factory.sol).

Example:

* There are some pools with 0 protocol fee, where `_poolFeeProtocol[pool]` is 0.

* Governance calls `RamsesV3Factory::setFeeProtocol`, which updates the state variable `RamsesV3Factory.feeProtocol` to a new value `F`.

* Now a malicious actor may update the fee protocol of any pool who's protocol fee is 0 to the new value `F` that was set in the last step.

## Impact

Since `RamsesV3Pool::setFeeProtocol()` is lacking appropriate access protection, any actor may update any pool's protocol fee from 0 to the new value `F`.

This may cause harm to the protocol's integrity, and also cause that normal actors have to pay protocol fees that they shouldn't have to pay, since the pool should have 0 protocol fee.

## Recommended Mitigation Steps

Consider protecting `RamsesV3Pool::setFeeProtocol()` by adding some appropriate access protection, similar to `RamsesV3Pool:setFee()`:

```solidity
if (msg.sender != factory) revert Unauthorized();
```
