# Vulnerability details

**Title**: Possible Front-Running Attack on Reward Distribution in GaugeV3

**Description**:
The GaugeV3 contract allows for the addition of new reward tokens and the notification of reward amounts. There's a potential vulnerability where a malicious user could front-run the `notifyRewardAmount` function call to unfairly claim rewards.

**Vulnerable Code**:
```solidity
function notifyRewardAmount(
    address token,
    uint256 amount
) external override pushFees lock {
    require(isReward[token], "!Whitelisted");
    IRamsesV3Pool(pool)._advancePeriod();
    uint256 period = _blockTimestamp() / WEEK;

    uint256 balanceBefore = IERC20(token).balanceOf(address(this));
    IERC20(token).safeTransferFrom(msg.sender, address(this), amount);
    uint256 balanceAfter = IERC20(token).balanceOf(address(this));

    amount = balanceAfter - balanceBefore;
    tokenTotalSupplyByPeriod[period][token] += amount;
    emit NotifyReward(msg.sender, token, amount, period);
}
```

**Impact**:
A malicious user could monitor the mempool for `notifyRewardAmount` transactions. If they see a large reward being added, they could potentially:

1. Front-run the transaction with a large stake in the gauge.
2. Allow the `notifyRewardAmount` transaction to process.
3. Immediately claim a disproportionate amount of rewards.
4. Unstake their position.

This could result in the attacker unfairly claiming a large portion of the rewards, leaving less for legitimate long-term stakers.

**Proof of Concept**:
1. Attacker monitors mempool for `notifyRewardAmount` calls.
2. When a large reward is being added, attacker quickly stakes a large amount.
3. `notifyRewardAmount` processes, adding rewards.
4. Attacker calls `getReward` to claim their unfair share.
5. Attacker unstakes their position.

**Recommendation**:
1. Implement a time-lock mechanism for newly staked positions before they can claim rewards.
2. Consider using a vesting period for rewards to discourage short-term exploitation.
3. Implement an average balance mechanism over time to determine reward distribution, rather than using the current balance at the time of reward distribution.
