# Vulnerability details

The protocol is relying on `Oracle.periodCumulativesInside` to calculate the correct amount of time `secondsPerLiquidity` in a period, with the following assumptions:
- Whenever a tick is crossed in the swap action in a period, it's `TickInfo.periodSecondsPerLiquidityOutsideX128` is set to the correct amount for that period.
- `TickInfo.periodSecondsPerLiquidityOutsideX128` assumes that previous `secondsPerLiquidiy` from previous periods all happened below all ticks.
- If a tick is not crossed, and it is below the `Period.startTick`, then it's `secondsPerLiquidityOutside` will be set to `lastPeriod.endSecondsPerLiqudity`.
- If a tick is not crossed, and it is above the `Period.startTick` then it's value is considered to be `0`. Since all the previous accruals from previous periods has happened below it, and the tick is not crossed yet.

However, the main problem is that, these assumptions will not hold true for newly created positions, as **Uniswap only crossed the intialized ticks**. This means that if the `tick` is different than `startTick` in the period, then the considerations above would be incorrect.

### Impact
This will cause certain invariants in the protocol to break. This issue has a similar impact as the issue "`Oracle.periodCumulativesInside` calculates the durations incorrectly in the first period", but it only inludes newly created positions.

### Proof of Concept
1. Consider intial tick being `190_000`
2. A position active since the start of the period includes ranges `[100_000, 200_000)`
3. If the tick is reduced by `10_000` to `180_000`
4. And a new position is made from `[185_000, 195_000)`
5. `Oracle.periodCumulativesInside` sees the `TickInfo.periodSecondsPerLiquidityOutsideX128` are unset and considers the ticks not crossed, and since one is lower and `secondsOutsideLower` will be set to `endSecondsPerLiqudity` and the `secondsOutsideUpper` will be set to 0.
6. The result would be `secondsOutsideLower` - `secondsOutsideUpper` which will underflow and due to the unchecked value will not fail.

### Mitigation
Keep a range of touched ticks in this period, and when the tick is being initialized, set the `upper/lower.periodSecondsPerLiquidityOutsideX128` to the correct amount.
