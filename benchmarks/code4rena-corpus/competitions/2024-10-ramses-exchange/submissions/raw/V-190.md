# Vulnerability details

## Summary

**Context:**
When users call mint(), burn(), swap() on a pool, the _advancePeriod() function is called, which advances the period to the current period and does not allowing period advancements until a week has passed. 

We know that it is possible for unpopular & low-activity pools to have their pool functions mint(), burn() and swap() called significantly after the beginning of a new period (i.e a block timestamp that is an even multiple of 1 weeks).

**Issue:**
The issue is that if a period is skipped, the periodSecondsInsideX96 of an existing position will be returned as 0. Since the GaugeV3 reward [here](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/gauge/GaugeV3.sol#L321C2-L325C11) utilizes periodSecondsInsideX96 (i.e. 0) to calculate the rewards to transfer to the LP position owner, the rewards calculated would be 0.

## Proof of Concept

How to use this POC:
-  The below foundry test contract uses the existing setup from the test coverage invitational so no additional setup is required other than git cloning the test coverage repo and installing the dependencies.
 - Add the POC to the `test` folder and name it `TestHistoricalDataIssue.sol`
 - Run the test using `forge test --mt testHistoricalDataIssue -vvvvv`
 - The test displays the console.log statements in the traces, where we can see the affected periodSecondsInsideX96 value to be 0.
 - I've left helpful comments in the POC to help navigate the actions taking place.

Here's what the POC does:
 - Enter period 1
 - Mint position in period 1
 - Enter period 2
 - No mint(), burn() or swap() interactions in period 2 (since it is an unpopular and low-activity pool)
 - Enter period 3
 - _advancePeriod() called in period 3 through a swap, mint or burn. In the test, we just call _advancePeriod() directly for simplicity to showcase the bug.
 - We call the positionPeriodSecondsInRange() function on the pool to retrieve the periodSecondsInsideX96 for the position for period 1 and 2. Since the liquidity of the position was provided for the full duration of the first period and the second period, the periodSecondsInsideX96 should be (1 weeks * 2**96) for both period 1 and 2 each. But as we can see, the value returned is 0 for both period 1 and 2. This occurred because the pool had no interactions during period 2, essentially skipping it. When we call _advancePeriod() in period 3, we can see the damage the done i.e. periodSecondsInsideX96 being returned as 0, which means the LP position owner would not receive any rewards for those two periods even though active liquidity was provided.
 - We know the bug arises from skipping a period and then receiving a mint(), burn() or swap() call (indirectly calling _advancePeriod()) in a future period.

## Recommended Mitigation Steps
The simplest solution would be to implement an off-chain script that regularly calls _advancePeriod() for low-activity pools. This is definitely an additional overhead for the team, both in terms of cost and effort. I'm still looking into how to resolve this bug so I cannot provide a robust mitigation for it as of now.
