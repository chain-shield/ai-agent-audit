# Vulnerability details

## Proof of Concept
https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/gauge/GaugeV3.sol#L493C1-L533C1

**Description**: The loop that iterates through periods to claim rewards (for (uint256 period = lastClaim; period <= currentPeriod; ++period)) updates the lastClaimByToken mapping outside of the loop. This means that if a user claims rewards for multiple tokens, and some tokens have rewards available in the current period (currentPeriod) while others don't, the lastClaimByToken for the tokens without rewards in the current period will be incorrectly set to currentPeriod - 1. Consequently, rewards for those tokens in the next period might be skipped and become unclaimable.

Token A: Periods 1, 2, and 3
Token B: Only Period 3
The user calls getReward to claim rewards for both Token A and Token B.
Token A: The loop correctly claims rewards for periods 1, 2, and 3. lastClaimByToken[tokenA] is updated to 3.
Token B: The loop only runs for period 3 (as there are no rewards in periods 1 and 2).
The Bug: lastClaimByToken[tokenB] is incorrectly set to 2 (currentPeriod - 1), even though rewards were only claimed up to period 3.
Next Claim: In the next period (period 4), when the user tries to claim rewards:
The loop for Token A starts from period 4 (correct).
The loop for Token B starts from period 2 (incorrect), skipping the rewards from period 3.


1. Victim and Reward Pattern: Let's say the vulnerable gauge distributes rewards in tokenA and tokenB. tokenA has rewards in every period, while tokenB only has rewards in periods 2, 4, 6, etc. The attacker identifies a victim who has earned rewards in both tokenA and tokenB.

2. Triggering the Flaw:

Period 3: The victim, unaware of the bug, decides to claim their rewards. They call the getReward function, specifying both tokenA and tokenB.
Loop Execution:
For tokenA, the loop runs correctly through all periods (1, 2, and 3), claiming rewards and updating lastClaimByToken[tokenA] to 3.
For tokenB, the loop only runs for period 2 (as there are no rewards in periods 1 and 3).
Incorrect Update: The crucial flaw occurs here. Because the lastClaimByToken[tokenB] update is outside the inner loop, it gets set to currentPeriod - 1, which is 2, even though the last claimed period for tokenB was actually 2.
3. Exploiting the Misinformation:

Period 4: tokenB now has rewards available. The attacker, knowing the victim's lastClaimByToken[tokenB] is incorrectly set to 2, calls getReward for the victim's position, specifying only tokenB.
Profiting from the Skip: The loop for tokenB starts at period 2 (the incorrect lastClaimByToken[tokenB] value) and goes up to period 4. This causes the attacker to claim the rewards for period 3, which rightfully belonged to the victim.
## Impact 
Due to the flawed update placement, if a user is claiming rewards for multiple tokens, and some tokens have rewards available in the current period while others don't, the lastClaimByToken for the tokens without rewards in the current period will be incorrectly set to currentPeriod - 1. This leads to skipping the next period's rewards for those tokens in subsequent claims.



## Recommended Mitigation Steps
```
    function _getAllRewards(
        // ... other parameters ...
    ) internal {
        // ... other code ...

        for (uint256 i = 0; i < tokens.length; ++i) {
            lastClaim = Math.max(
                lastClaimByToken[tokens[i]][_positionHash],
                firstPeriod
            );
            for (
                uint256 period = lastClaim;
                period <= currentPeriod;
                ++period
            ) {
                _getReward(
                    period,
                    tokens[i],
                    owner,
                    index,
                    tickLower,
                    tickUpper,
                    _positionHash,
                    receiver
                );

                // Update lastClaimByToken here, after processing each period
                lastClaimByToken[tokens[i]][_positionHash] = period; 
            }
            // lastClaimByToken[tokens[i]][_positionHash] = currentPeriod - 1; // Remove this line
        }
    }
```
This ensures that lastClaimByToken is updated correctly for each token after processing its rewards for each period, preventing any rewards from being skipped or becoming unclaimable.
