# Vulnerability details

## Proof of Concept
[RamsesV3Pool._advancePeriod()](https://github.com/code-423n4/2024-10-ramses-exchange-test-coverage/blob/9da1c98ab902b2dbcb1e121542de28022099b1e7/contracts/CL/core/RamsesV3Pool.sol#L749) fails to correctly link periods when multiple periods are advanced at once.

**POC TEST:**
```typescript
    it("should correctly link multiple periods when advancing", async () => {
        const initialLastPeriod = await pool.lastPeriod();
    
        // Advance time by five weeks
        await time.increase(5 * WEEK);
        await mine();
    
        // Call _advancePeriod
        await pool._advancePeriod();
    
        const newLastPeriod = await pool.lastPeriod();
        // Check that the period has advanced by 5
        expect(newLastPeriod - initialLastPeriod).to.equal(5n);
    
        // See that all intermediate periods are correctly linked
        for (let i = 1n; i <= 5n; i++) {
            const currentPeriod = initialLastPeriod + i;
            const periodInfo = await pool.periods(currentPeriod);
            const expectedPreviousPeriod = i === 1n ? initialLastPeriod : initialLastPeriod + i - 1n;
            expect(periodInfo.previousPeriod).to.equal(expectedPreviousPeriod, `Incorrect previous period for period ${currentPeriod}`);
        }
    });
```

**Test output:**

**Impact:**
So this bug can open a path to a loss of historical data and incorrect period tracking. When multiple periods are advanced, only the most recent period is updated, intermediate periods are not properly linked. 

Resulting in:
1. Inability to accurately track historical price data
2. Issues with fee calculations that rely on period data
3. Wrong state of the pool, which could lead to wrong dynamics in other functions that rely on period information

## Recommended Mitigation Steps

Change `_advancePeriod` to handle multiple period advancements correctly:

```solidity
function _advancePeriod() public {
    PoolStorage.PoolState storage $ = PoolStorage.getStorage();

    uint256 currentPeriod = _blockTimestamp() / 1 weeks;
    uint256 _lastPeriod = $.lastPeriod;

    if (currentPeriod != _lastPeriod) {
        Slot0 memory _slot0 = $.slot0;

        // Handle multiple period advancements
        for (uint256 period = _lastPeriod + 1; period <= currentPeriod; period++) {
            uint160 secondsPerLiquidityCumulativeX128 = Oracle.newPeriod(
                $.observations,
                _slot0.observationIndex,
                period
            );

            // Record data for the previous period
            if (period == _lastPeriod + 1) {
                $.periods[_lastPeriod].lastTick = _slot0.tick;
                $.periods[_lastPeriod].endSecondsPerLiquidityPeriodX128 = secondsPerLiquidityCumulativeX128;
            }

            // Create new period
            PeriodInfo memory _newPeriod;
            _newPeriod.previousPeriod = uint32(period - 1);
            _newPeriod.startTick = _slot0.tick;
            $.periods[period] = _newPeriod;

            // Update _lastPeriod for the next iteration
            _lastPeriod = period;
        }

        // Update lastPeriod in storage
        $.lastPeriod = currentPeriod;
    }
}
```

I did above modifications to address the following issues:
- Correctly handle multiple period advancements by using a loop.
- Making sure that all intermediate periods are created and linked properly.
- Correctly setting the `previousPeriod` for each new period.

Also update functions that rely on period data so they handle the new period linking correctly, and you can add a gas (mana) limit check to prevent excessive gas consumption when advancing a large number of periods:

```solidity
require(currentPeriod - _lastPeriod <= MAX_PERIODS_TO_ADVANCE, "Too many periods to advance");
```

Where `MAX_PERIODS_TO_ADVANCE` is constant defining the max number of periods that can be advanced in a single call.
