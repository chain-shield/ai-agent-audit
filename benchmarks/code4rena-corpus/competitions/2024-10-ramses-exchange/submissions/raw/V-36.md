# Vulnerability details

## Proof of Concept
The function `cachePeriodEarned()` inside the GaugeV3 contract, is responsible for showing how much an LP has earned reward. This function calculates the earned amount of a LP position by computing the position's periods in seconds which is in the target range of upper and lower ticks that makes the position eligible, as well as the total supply of the reward token which is injected via the `notifyRewardAmounts()` function. The mentioned earning amount is then computed as:

$$ amount = \frac{totalSupply \times periodsInSecond_{X96}}{week_{X96}} $$

The point here is that, the contract's timing system depends on the present time (now or 'block.timestamp`) rather than the pool creation time. In other words, if the LPs start to add liquidity and hence, the LTs start to trade after one period (week), but the admin calls `notifyRewardAmounts()` in the present period, those rewards would get stuck inside the contract and couldn't be released:

The problem here is that the total supply of the reward is not a single storage (e.g. a `uint256`), but instead a mapping. The `tokenTotalSupplyByPeriod[period][token]` is a mapping to keep record of the rewards added by a period, and thus, if a period lacks of any liquidity inside the pool, its value wouldn't be used anymore and leads to the reward token loss of the admin or any entity responsible for calling the `notifyRewardAmounts()`. Inside the `cachePeriodEarned()` function it does not accumulate the non-distributed rewards from the past.

This scenario shows the impact of this issue:

1. The pool is created on Day 5 of the week, leaving 30 hours before the week ends and the new period begins.No liquidity has been added yet.
2. On Day 6, the `notifyRewardAmount()` function is called, adding 1 ether worth of reward tokens to the pool for distribution. The reward is set to be distributed during the current period.
3. The next day, on Day 7 (which marks the start of a new week/period), LPs begin to add liquidity and Liquidity Takers start to trade. The period has shifted due to the transition to the new week.
`tokenTotalSupplyByPeriod` is Reset to 0 for New Period.
4. Since the new period begins, `tokenTotalSupplyByPeriod` is reset to 0 for the new week. This creates an issue as the system does not recognise any token supply from the previous period in the new period context.
5. As a result of the period transition, the rewards that were intended for distribution during the previous period are now "stuck" inside the GaugeV3 contract. These rewards remain inaccessible because the mechanism does not account for transitioning rewards between periods and resets the total supply.




## Recommended Mitigation Steps

I think these steps could help preventing this problem:

1. Introducing a mechanism to extract the stuck reward tokens after a period is finished.
2. Accumulating the previous rewards to be distributed in the next periods.
3. Introduce a timing system for the period from the creation time of the pool rather than the now or `block.timestamp`
