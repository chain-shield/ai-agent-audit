# Vulnerability details

## Summary

The `increaseLiquidity` function in the Ramses V3 Position Manager contains an arithmetic overflow vulnerability in its liquidity accounting due to an unchecked addition operation on a uint128 value. The vulnerability exists where new liquidity is added to an existing position's balance within an unchecked block, likely implemented as a gas optimization.

```solidity
// The vulnerable pattern
unchecked {
    position.liquidity += liquidity;  // uint128 overflow risk
}
```

A silent overflow in position liquidity tracking could lead to incorrect position accounting, fee calculations, and pool share computations throughout the protocol.

## Impact

When examining the integer overflow vulnerability in the `increaseLiquidity` function, we need to understand how it propagates through the contract's core accounting mechanisms. The vulnerability originates in the unchecked liquidity addition:

```solidity
function increaseLiquidity(IncreaseLiquidityParams calldata params) external payable {
    Position storage position = _positions[params.tokenId];
    
    (liquidity, amount0, amount1, pool) = addLiquidity(
        AddLiquidityParams({
            token0: poolKey.token0,
            token1: poolKey.token1,
            tickSpacing: poolKey.tickSpacing,
            tickLower: position.tickLower,
            tickUpper: position.tickUpper,
            amount0Desired: params.amount0Desired,
            amount1Desired: params.amount1Desired,
            amount0Min: params.amount0Min,
            amount1Min: params.amount1Min,
            recipient: address(this),
            index: params.tokenId
        })
    );

    unchecked {
        position.liquidity += liquidity;  // Overflow point
    }
}
```

This overflowed liquidity value then flows into the fee growth calculations:

```solidity
unchecked {
    position.tokensOwed0 += uint128(
        FullMath.mulDiv(
            feeGrowthInside0LastX128 - position.feeGrowthInside0LastX128,
            position.liquidity,  // Corrupted liquidity propagates
            FixedPoint128.Q128
        )
    );
    position.tokensOwed1 += uint128(
        FullMath.mulDiv(
            feeGrowthInside1LastX128 - position.feeGrowthInside1LastX128,
            position.liquidity,  // Affects both token calculations
            FixedPoint128.Q128
        )
    );
}
```

The corrupted state extends to pool interactions, where the position's liquidity is used to calculate proportional ownership and fees. The pool contract uses this value to determine swap pricing and fee distribution:

```solidity
bytes32 positionKey = PositionKey.compute(
    address(this),
    params.tokenId,
    position.tickLower,
    position.tickUpper
);

(, uint256 feeGrowthInside0LastX128, uint256 feeGrowthInside1LastX128, , ) = pool.positions(positionKey);
```

When users attempt to decrease liquidity or collect fees, the corrupted values affect their withdrawals:

```solidity
function decreaseLiquidity(DecreaseLiquidityParams calldata params) external {
    Position storage position = _positions[params.tokenId];
    uint128 positionLiquidity = position.liquidity;
    require(positionLiquidity >= params.liquidity);  // Check bypassed with corrupted value

    (amount0, amount1) = pool.burn(
        params.tokenId,
        position.tickLower,
        position.tickUpper,
        params.liquidity
    );
}
```

The vulnerability creates a cascading effect in the protocol's core economics. When calculating pool invariants and price impacts, the AMM relies on accurate liquidity reporting:

```solidity
function collect(CollectParams calldata params) external returns (uint256 amount0, uint256 amount1) {
    Position storage position = _positions[params.tokenId];
    
    if (position.liquidity > 0) {  // Corrupted check
        pool.burn(params.tokenId, position.tickLower, position.tickUpper, 0);
        (, uint256 feeGrowthInside0LastX128, uint256 feeGrowthInside1LastX128, , ) = pool.positions(
            PositionKey.compute(address(this), params.tokenId, position.tickLower, position.tickUpper)
        );
        
        // Fee calculations use corrupted liquidity
        tokensOwed0 += uint128(
            FullMath.mulDiv(
                feeGrowthInside0LastX128 - position.feeGrowthInside0LastX128,
                position.liquidity,
                FixedPoint128.Q128
            )
        );
    }
}
```

The gauge reward system also inherits these incorrect values:

```solidity
function getReward(uint256 tokenId, address[] calldata tokens) external {
    Position storage position = _positions[tokenId];
    IGaugeV3 gauge = IGaugeV3(IVoter(voter).gaugeForPool(
        PoolAddress.computeAddress(deployer, poolKey)
    ));
    
    // Rewards calculated based on corrupted liquidity
    gauge.getRewardForOwner(tokenId, tokens);
}
```

The severity is compounded by the fact that these calculations involve complex fixed-point arithmetic and fee growth tracking, making the impact of corrupted values exponentially more severe as they interact with the protocol's various mathematical operations.

The vulnerability fundamentally breaks the protocol's invariants around liquidity accounting, position management, and fee distribution, creating a systemic risk that affects every aspect of the protocol's operation. The mathematical precision required for AMM operations makes this overflow particularly dangerous, as it introduces subtle but critical errors into the core economic calculations that maintain the protocol's stability.

## Fix

Remove unchecked block to leverage Solidity 0.8.x's built-in overflow protection:
```solidity
// Safe version
position.liquidity += liquidity;  // Will revert on overflow
```
