# Vulnerability details

## Description

The Oracle library is designed to maintain a circular buffer of observations for tracking historical price and liquidity data in an AMM pool. The write function is responsible for adding new observations to this buffer.

The write function has a flaw in its logic for increasing the cardinality (size) of the observation array. When increasing the cardinality, it fails to properly initialize new slots, which can lead to gaps in the data or reading of uninitialized data.

## Code

```solidity
function write(
    Observation[65535] storage self,
    uint16 index,
    uint32 blockTimestamp,
    int24 tick,
    uint128 liquidity,
    uint16 cardinality,
    uint16 cardinalityNext
) internal returns (uint16 indexUpdated, uint16 cardinalityUpdated) {
    unchecked {
        Observation memory last = self[index];

        if (last.blockTimestamp == blockTimestamp) return (index, cardinality);

        if (cardinalityNext > cardinality && index == (cardinality - 1)) {
            cardinalityUpdated = cardinalityNext;
        } else {
            cardinalityUpdated = cardinality;
        }

        indexUpdated = (index + 1) % cardinalityUpdated;
        self[indexUpdated] = transform(last, blockTimestamp, tick, liquidity);
    }
}
```

The issue lies in how the function handles increasing the cardinality (the number of observations stored). When `cardinalityNext` is greater than `cardinality`, the function immediately jumps to using the new, larger cardinality without initializing the new slots in the observation array.


a. Cardinality Increase Condition:
```solidity
if (cardinalityNext > cardinality && index == (cardinality - 1)) {
    cardinalityUpdated = cardinalityNext;
} else {
    cardinalityUpdated = cardinality;
}
```
This condition checks if we should increase the cardinality. It does so when `cardinalityNext` is larger and we've filled the current array (index is at the end).

b. Index Update:
```solidity
indexUpdated = (index + 1) % cardinalityUpdated;
```
This calculates the next index to write to, wrapping around based on the new cardinality.

c. Writing the New Observation:
```solidity
self[indexUpdated] = transform(last, blockTimestamp, tick, liquidity);
```
This writes the new observation to the calculated index.

When we increase cardinality, say from 5 to 10, the function will jump from using indices 0-4 to suddenly writing to index 5, leaving indices 6-9 uninitialized. This creates gaps in our observation history.

## Impact

This bug can lead to several serious issues:

a. Data Gaps: Large portions of the observation array may be left uninitialized, creating gaps in historical data.

b. Incorrect Readings: Functions that read from these uninitialized slots (like `observe` or `observeSingle`) may return incorrect or zero values, leading to inaccurate price or liquidity calculations.

c. Inconsistent State: The oracle's state becomes inconsistent, potentially affecting various pool operations that rely on accurate historical data.

## Example Scenario

Imagine this sequence of events:
1. Oracle starts with cardinality 5, all slots filled (indices 0-4).
2. `cardinalityNext` is set to 10.
3. New observation is written, triggering cardinality increase.
4. `indexUpdated` becomes 5, slots 6-9 remain uninitialized.
5. Next write goes to index 6, leaving 7-9 still uninitialized.

Now, if someone calls `observe` asking for historical data that should be in slots 7-9, they'll get uninitialized data.

## Fix

Modify the `write` function to properly initialize new slots when increasing cardinality.

```solidity
function write(
    Observation[65535] storage self,
    uint16 index,
    uint32 blockTimestamp,
    int24 tick,
    uint128 liquidity,
    uint16 cardinality,
    uint16 cardinalityNext
) internal returns (uint16 indexUpdated, uint16 cardinalityUpdated) {
    unchecked {
        Observation memory last = self[index];

        if (last.blockTimestamp == blockTimestamp) return (index, cardinality);

        if (cardinalityNext > cardinality && index == (cardinality - 1)) {
            for (uint16 i = cardinality; i < cardinalityNext; i++) {
                self[i] = transform(last, blockTimestamp, tick, liquidity);
            }
            cardinalityUpdated = cardinalityNext;
        } else {
            cardinalityUpdated = cardinality;
        }

        indexUpdated = (index + 1) % cardinalityUpdated;
        self[indexUpdated] = transform(last, blockTimestamp, tick, liquidity);
    }
}
```

This fix adds a loop to initialize all new slots when increasing cardinality, ensuring no gaps in the data.
