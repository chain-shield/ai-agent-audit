# Vulnerability details

## Summary

The `removeRewards` function has a vulnerability where it fails to validate whether a reward token was actually found in the `rewards` array before proceeding with removal operations. When attempting to remove a token that exists in `isReward` mapping but not in the `rewards` array, the function will remove the first token in the array (at index 0) due to Solidity's default value initialization of `uint256 idx` to 0.

While this issue requires pre-existing state inconsistency between `rewards` array and `isReward` mapping to be exploitable, it represents a failure of defensive programming that could lead to unintended reward token removals and disruption of the reward distribution system.

## Code
```solidity
function removeRewards(address reward) external {
    require(msg.sender == voter, "!AUTH");
    if (isReward[reward]) {
        uint256 idx;  // Initialized to 0 by default

        for (uint256 i; i < rewards.length; ++i) {
            if (rewards[i] == reward) {
                idx = i;
                break;
            }
        }

        // No validation that we found the reward
        for (uint256 i = idx; i < rewards.length - 1; ++i) {
            rewards[i] = rewards[i + 1];
        }

        rewards.pop();
        isReward[reward] = false;

        emit RewardRemoved(reward);
    }
}
```

The issue lies in how Solidity handles uninitialized variables and the lack of validation after the search loop. When a `uint256` is declared without initialization (`uint256 idx;`), it defaults to 0. The function assumes that if `isReward[reward]` is true, the token must exist in the `rewards` array, but this assumption isn't validated.

Let's examine how this could manifest in contract state. Assume the following initial state:
```solidity
// Initial contract state
rewards = [TokenA, TokenB, TokenC]
isReward = {
    TokenA: true,
    TokenB: true,
    TokenC: true,
    TokenD: true  // Somehow became true without being in rewards array
}
```

When `removeRewards(TokenD)` is called:
```solidity
if (isReward[TokenD]) {  // This check passes
    uint256 idx;  // idx = 0
    
    // Search loop
    for (uint256 i; i < rewards.length; ++i) {
        if (rewards[i] == TokenD) {  // Never finds TokenD
            idx = i;
            break;
        }
    }
    // Loop completes without finding TokenD, idx remains 0
```

The shifting operation then proceeds with `idx = 0`:
```solidity
    // Starts shifting from index 0
    for (uint256 i = idx; i < rewards.length - 1; ++i) {
        rewards[i] = rewards[i + 1];
    }
    // Results in:
    // rewards = [TokenB, TokenC, TokenC]
    
    rewards.pop();
    // rewards = [TokenB, TokenC]
    
    isReward[TokenD] = false;
```

## Impact
The end result is that `TokenA` is unintentionally removed instead of `TokenD`. This creates several problematic conditions:

1. State mutation:
```solidity
// Before
rewards = [TokenA, TokenB, TokenC]
isReward[TokenA] = true
isReward[TokenD] = true

// After
rewards = [TokenB, TokenC]
isReward[TokenA] = true  // TokenA still marked as reward but removed from array
isReward[TokenD] = false // TokenD marked as non-reward but was never in array
```

2. This affects reward distribution since the contract maintains period reward tracking:
```solidity
mapping(uint256 => mapping(address => uint256)) public tokenTotalSupplyByPeriod;
```

The reward calculations might still attempt to process TokenA rewards since `isReward[TokenA]` remains true, but the token can no longer be properly managed through the rewards array.

## Fix
Add explicit validation of token discovery before proceeding with removal operations.


A proper implementation should validate the token's existence:
```solidity
function removeRewards(address reward) external {
    require(msg.sender == voter, "!AUTH");
    if (isReward[reward]) {
        uint256 idx;
        bool found;
        
        for (uint256 i; i < rewards.length; ++i) {
            if (rewards[i] == reward) {
                idx = i;
                found = true;
                break;
            }
        }
        
        require(found, "Reward not found in array");  // Critical validation

        for (uint256 i = idx; i < rewards.length - 1; ++i) {
            rewards[i] = rewards[i + 1];
        }

        rewards.pop();
        isReward[reward] = false;

        emit RewardRemoved(reward);
    }
}
```

In practice, this vulnerability requires some form of state corruption since both `addRewards` and `removeRewards` are voter-controlled and maintain consistent state between `rewards` and `isReward`. However, in smart contract security, we must consider the possibility of state corruption through:

1. Contract upgrades
2. Direct state manipulation through delegatecall
3. Bugs in other privileged functions
4. Future modifications to the contract that might bypass normal state management

The impact is primarily operational rather than financial - it could lead to the removal of active reward tokens instead of failing gracefully when invalid operations are attempted. This could disrupt the protocol's reward distribution system and require administrative intervention to correct.
