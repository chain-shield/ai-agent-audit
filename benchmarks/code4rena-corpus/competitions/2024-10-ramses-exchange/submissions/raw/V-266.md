# Vulnerability details

## Proof of Concept

For context, here's the vulnerable code allowing reentrancy to be exploited: 

```solidity

    /// @inheritdoc IClGaugeFactory
    function createGauge(
        address pool
    ) external override returns (address gauge) {
        require(msg.sender == voter, "AUTH");
        require(getGauge[pool] == address(0), "GE");
        gauge = address(new GaugeV3(voter, nfpManager, feeCollector, pool));
        getGauge[pool] = gauge;
        emit GaugeCreated(pool, gauge);
    }

```

The `createGauge` function is vulnerable to a reentrancy attack.  An attacker can create a malicious contract that implements the `IClGaugeFactory` interface and calls the `createGauge` function with a malicious address as the `pool`. This malicious contract can then call back into the `createGauge` function before the state changes are fully committed, allowing it to manipulate the contract's state or drain funds.

## Recommended Mitigation Steps


There are a couple things I'd strongly recommend the devs start doing in Ramses Exchange.  

a.  Require immediate state updates. To mitigate part of the attack chain above in the reentrancy vector, Ramses devs could update getGauge[pool] before deploying GaugeV3, ensuring that recursive calls fail due to the pre-existing state.

b.  Require reentrancy guard.  If Ramses Exchange devs add a nonReentrant guard, it would prevent any reentrant access during function execution, particularly from external contracts capable of invoking fallback functions.  This is ESSENTIAL to preventing this corner case vector of attack in the future.

c.  Implement a whitelist, or other validation mechanisms, on the pool parameter to confirm that it is a valid contract address. Ensure that the pool address is NOT allowed to execute callback functions, reducing potential reentrant calls from malicious contract addresses.


d. Require access controls beyond `voter`.  Reinforce the access control by adding an additional access mechanism beyond the voter check, such as multi-signature approval, for critical functions like createGauge.  This will go a long way in preventing exploits like this one.
