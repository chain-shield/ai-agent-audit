# Vulnerability details

## Proof of Concept
Let's consider the `collectProtocolFees` function specifically the handling of redirected pools and gauges.

https://github.com/code-423n4/2024-10-ramses-exchange/blob/236e9e9e0cf452828ab82620b6c36c1e6c7bb441/contracts/CL/gauge/FeeCollector.sol#L77-L87

```solidity
/// @dev check if there's a gauge
IVoter _voter = voter;
address gauge = _voter.gaugeForPool(address(pool));
bool isAlive = _voter.isAlive(gauge);

/// @dev check if it's a cl gauge redirected to another gauge
if (gauge == address(0) || !isAlive) {
    address toPool = _voter.poolRedirect(address(pool));
    gauge = _voter.gaugeForPool(address(toPool));
    isAlive = _voter.isAlive(gauge);
}
```

The issue here iss that when a pool is redirected, the function updates the `gauge` and `isAlive` variables, but it continues to use the original `pool` for fee collection. This could cause a mismatch between the pool from which fees are collected and the gauge/fee distributor to which those fees are sent.

Specifically:
-- If the original pool has no gauge or an inactive gauge, the function looks for a redirected pool.
-- It then gets the gauge for the redirected pool and checks if it's alive.
-- But when it comes to actually collecting the fees, [it still uses the original `pool` object](https://github.com/code-423n4/2024-10-ramses-exchange/blob/236e9e9e0cf452828ab82620b6c36c1e6c7bb441/contracts/CL/gauge/FeeCollector.sol#L107-L111).

```solidity
pool.collectProtocol(
    address(this),
    type(uint128).max,
    type(uint128).max
);
```

This means that fees are being collected from the original pool but distributed based on the gauge of a different (redirected) pool. This mismatch could lead to incorrect fee distribution or some other unexpected issue.


## Recommendations
1. Collect fees from the redirected pool if one is found, or
2. Not use the redirected pool's gauge at all and treat the original pool as having no valid gauge if its own gauge is not active.
