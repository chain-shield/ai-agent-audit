# Vulnerability details

## Summary

**Context:**
Function cachePeriodEarned() calculates rewards for liquidity providers using the equation below (see [here](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/gauge/GaugeV3.sol#L321C9-L326C1)):
```solidity
        amount = FullMath.mulDiv(
            tokenTotalSupplyByPeriod[period][token],
            periodSecondsInsideX96,
            WEEK << 96
        );
```

**Issue & Impact:**
The issue is that a liquidity provider with a 1 wei position receives the same rewards as a liquidity provider with a 10 ether position. In short, to earn rewards from GaugeV3, liquidity providers are not incentivised to mint a position any more than 1 wei. This is because only their position's periodSecondsInsideX96 is considered. This issue is being reported as high-severity since it affects the core functionality around reward accounting for LPs, which does not meet the invariant described in the README [here](https://github.com/code-423n4/2024-10-ramses-exchange#attack-ideas-where-to-focus-for-bugs) - `reward accounting being accurate and not substantially inflated or deflated from reality are crucial.`

## Proof of Concept

1. Let's assume the tokenTotalSupplyByPeriod[period][token] is 10e18.

2. The coded POC below proves that the periodSecondsInsideX96 for both liquidity provider's position's is the same i.e. approximately (1 weeks * 2^96).

3. Since the periodSecondsInsideX96 is same, both positions would receive the same rewards according to the equation below from cachePeriodEarned(), which is utilized by functions like getPeriodReward() in GaugeV3.sol.

```solidity
        amount = FullMath.mulDiv(
            tokenTotalSupplyByPeriod[period][token],
            periodSecondsInsideX96,
            WEEK << 96
        );
```

## Coded POC

 - The below foundry test contract uses the existing setup from the test coverage invitational so no additional setup is required other than git cloning the test coverage repo and installing the dependencies.
 - Add the POC to the `test` folder and name it `TestLiquidityIssue.sol`
 - Run the tests using `forge test --mt testPositionPeriodsSecondsInRange1 -vvvvv` and `forge test --mt testPositionPeriodsSecondsInRange2 -vvvvv`
 - The test `testPositionPeriodsSecondsInRange1` demonstrates how the periodSecondsInsideX96 for a 1 wei position is (1 weeks * 2^96). The test `testPositionPeriodsSecondsInRange2` demonstrates how the periodSecondsInsideX96 for a 10 ether position is (1 weeks * 2^96) as well.

## Recommended Mitigation Steps
We should account a position's liquidity as a factor. We track the total liquidity in a period and divide an active position's liquidity by that total liquidity. It is easy to know whether a position is active or not in a period by just checking its seconds in range to be positive. So in short, position liquidity in the period / total liquidity in the period.
