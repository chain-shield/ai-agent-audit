# Vulnerability details

## Summary

**Context:**
When a pool is created using the function [createPool()](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/RamsesV3Factory.sol#L71), we know it is possible to not initialize it in the same call as seen [here](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/RamsesV3Factory.sol#L99C9-L102C10). 

This behaviour is further backed by the fact that we know functions swap(), flash(), increaseObservationCardinalityNext(), mint(), collect(), burn(), setFee(), setFeeProtocol() and collectProtocol() are disallowed from calling until the pool is initialized. This is because the functions apply the `lock` modifier on them. 

**Root cause:**
Function [_advancePeriod()](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/RamsesV3Pool.sol#L749) though is allowed to call even when a pool is uninitialized. This oversight allows an attacker to call the function _advancePeriod() before the pool is initialized. When the external party (that created the pool) initializes the pool now, the first observation index gets overwritten to store blockTimestamp as 0, tickCumulative as 0 and secondsPerLiquidityCumulativeX128 as 0 and initialized to true.

**Impact:**
The values of `blockTimestamp` and `secondsPerLiquidityCumulativeX128` in the first observation index would remain as 0 until a position is minted. When the position is minted in the same period as the initialization, these two variables will start storing the correct values. But if not minted in the same period as the initialization, they would store incorrect values for that first period.
 
The main issue is that the tickCumulative value is permanently affected and stores an incorrect value for current and all future observations. Since the tickCumulative would be affected, contracts/periphery libraries such as OracleLibrary.sol would return incorrect results as well. 

This breaks the main invariant mentioned in the [README](https://github.com/code-423n4/2024-10-ramses-exchange#attack-ideas-where-to-focus-for-bugs) - `Finding cases where the math is irregular or returns improper results. Namely ensuring pool integrity.`

## Proof of Concept

First let's take a look at the difference between the [initialize()](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/RamsesV3Pool.sol#L152) function in the RamsesV3Pool contract and the UniswapV3Pool contract. As we can see below, the main difference is in how the [initialize()](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/libraries/Oracle.sol#L48) function is called on the Oracle.sol library. In RamsesV3Pool, we pass the blockTimestamp as 0 unlike Uniswap. But soon after that [_advancePeriod()](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/RamsesV3Pool.sol#L749) is called, which makes the necessary state changes to create a new period by calling [Oracle.newPeriod()](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/libraries/Oracle.sol#L338) and most importantly, it assigns the correct values to the blockTimestamp, secondsPerLiquidityCumulativeX128 and tickCumulative as seen [here](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/libraries/Oracle.sol#L353C13-L358C16).

UniswapV3Pool:
```

        (uint16 cardinality, uint16 cardinalityNext) = observations.initialize(_blockTimestamp());
```

RamsesV3Pool:
```solidity
    function initialize(uint160 sqrtPriceX96) external {
        PoolStorage.PoolState storage $ = PoolStorage.getStorage();

        if ($.slot0.sqrtPriceX96 != 0) revert AI();

        ...

        (uint16 cardinality, uint16 cardinalityNext) = Oracle.initialize($.observations, 0);

        _advancePeriod();

        ...
    }
```

Now let's have a simple walkthrough of how the issue arises:

1. External party creates a pool using createPool() but does not initialize it at the same time.
2. Attacker calls _advancePeriod() on the uninitialized pool, where the following occurs:
 - On Line 758, we enter the if block since the _lastPeriod (i.e. 0) is not equal to the current period (a non-zero value depending on block.timestamp)
 - On Line 761, the lastPeriod is set to the current period. This just means the last recorded period is now the current period and we will not be able to advance to the next period until the current period is over. This will be an important point later on.
- On Line 764, Oracle.newPeriod() is called, which for observation index 0 updates blockTimestamp to the current block.timestamp (i.e. incorrect value), tickCumulative to 0 (i.e. incorrect value) and secondsPerLiquidityCumulativeX128 to its correct value as seen [here](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/libraries/Oracle.sol#L353C13-L358C16). Note that at this point, the observation index 0 is still uninitialized since initialized [here](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/libraries/Oracle.sol#L357) is still false.

3. External party calls function initialize() to initialize the pool, where the following occurs:
 - On Line 155, we pass the check since sqrtPriceX96 is 0.
 - On Line 159, we call initialize() on Oracle.sol (which is similar to the Uniswap implementation). The only difference is that we pass 0 for the blockTimestamp parameter. Over here, the observation index 0 becomes initialized. The values of blockTimestamp, tickCumulative and secondsPerLiquidityCumulativeX128 are all overwritten to 0.
 - On Line 161, we call _advancePeriod(), where we do not enter the if block [here](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/RamsesV3Pool.sol#L755) since the lastPeriod was already assigned to be the current period in the attacker's call. This is where the necessary state changes were expected to occur but they do not occur due to the attacker's call. What has happened at this point is that all the values of blockTimestamp, tickCumulative and secondsPerLiquidityCumulativeX128 for observation index 0 are now 0 and the observation has been initialized to true [here](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/libraries/Oracle.sol#L56).

4. Through this, we see how the attacker becomes successful in performing the attack and leading the team into overwriting the values and initializing the observation from false to true as well. The attacker could've initialized the pool as well but doesn't do so to avoid suspicion, increasing the likelihood of the external party falling prey to the attack and initializing the affected pool.

5. Now let's see the affected values through the coded POC below and what minting a position would do.

### Coded POC

 - The below foundry test contract uses the existing setup from the test coverage invitational so no additional setup is required other than git cloning the test coverage repo and installing the dependencies.
 - Add the POC to the `test` folder and name it `TestAttackAP.sol`
 - Run the tests using `forge test --mt testAttackAP -vvvvv` and `forge test --mt testRegularAP -vvvvv`
 - The test `testAttackAP` demonstrates the attack the attacker performs. The test `testRegularAP` demonstrates the normal execution path without the involvement of the attacker.
 - Both tests display the console.log statements in the traces, where we can see the affected values.
 - The traces have been added below the POC.
 - I've left helpful comments in the POC to help navigate the actions taking place.
```solidity

        factory.initialize(address(poolDeployer));

        tokenA = new TestERC20(0);
        tokenB = new TestERC20(0);

        vm.prank(team);

    // @dev This contract is the access manager (check restricted modifier in AccessManaged)
    function canCall(address, address, bytes4) external view returns (bool allowed) {
        allowed = true;
    }

    function uniswapV3MintCallback(uint256 amount0Owed, uint256 amount1Owed, bytes calldata data) external {
        //console.log("%e", amount0Owed);
        //console.log(amount1Owed);
        address token0 = pool.token0();
        address token1 = pool.token1();
        TestERC20(token0).mint(address(pool), amount0Owed);
        TestERC20(token1).mint(address(pool), amount1Owed);
    }

    function uniswapV3SwapCallback(int256 amount0Delta, int256 amount1Delta, bytes calldata data) external {
        bool zeroForOne = abi.decode(data, (bool));
        if (zeroForOne) {

            TestERC20(token0).mint(address(this), uint256(amount0Delta));

            TestERC20(token1).mint(address(this), uint256(amount1Delta));

        skip(1 weeks);
        // Attacker calls _advancePeriod() on uninitialized() pool

        vm.prank(team);
        pool.initialize(10e18);

        // Assume 1 day passes before a position is minted
        skip(1 days);

        // At this point, the attack should work with incorrect data being initialized i.e. 0 for blockTimestamp, tickCumulative, secondsPerLiquidityCumulativeX128 and initialized to true.

        console.log("Initialized:", initialized);

        int24 tickUpper = TickMath.MAX_TICK;
```

### Traces/Logs
 - The logs for each test are divided into two parts: before minting and after minting of position.
 - If we compare "Before minting" of testRegularAP() and testAttackAP(), we can see the damage done by the attacker in testAttackAP(), where all the values are 0 and the observation index is initialized to true.
 - If we compare "After minting" of testRegularAP() and testAttackAP(), we notice that the block timestamp and secondsPerLiquidityCumulativeX128 are the restored to the correct values i.e. it is the same as in testRegularAP. This means if a position is minted **"in the same period"**, these values are unaffected. But if we view the tickCumulative values (i.e. -39389289368 and -315107476684), we can see the difference the attack made. Since tickCumulative keeps on adding onto the `last.tickCumulative` (see [here](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/libraries/Oracle.sol#L35) and [here](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/libraries/Oracle.sol#L355)), the issue extends to future observations and periods as well. This incorrect value is then consumed by periphery contracts/libraries such as OracleLibrary.sol.

## Recommended Mitigation Steps
Add an initialization check to _advancePeriod() to ensure it cannot be called while the pool is in an uninitialized state. The below check is a suggestion:

```solidity
    function _advancePeriod() public {
        (, , , bool initialized) = pool.observations(0);
        require(initialized, "Pool not initialized!");
```
