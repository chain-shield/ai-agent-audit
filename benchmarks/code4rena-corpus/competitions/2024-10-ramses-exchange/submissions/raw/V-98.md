# Vulnerability details

## Proof of Concept
The RamsesV3Pool contract contains a critical vulnerability that allows for the manipulation of oracle price data, specifically exploitable at the transition between weekly periods. This vulnerability arises from two interrelated issues:

Short-term manipulation: The Oracle.write function records the initial tick (slot0Start.tick) instead of the final tick (state.tick) after a swap.
Long-term manipulation: The startTick for each new period is set at the beginning of the first swap in that period, allowing for manipulation of the reference price for the entire week.

Exploitation process:

The attacker precisely times a large swap to execute just before the weekly period change (e.g., milliseconds before midnight UTC on Sunday).
This swap significantly alters the pool price.
The Oracle.write function records the pre-swap price.
The period changes, and the manipulated price is set as the startTick for the new weekly period.
The attacker quickly reverses their swap, but the manipulated data remains as the reference for the entire week.

Relevant code:
Period transition check:
uint256 period = _blockTimestamp() / 1 weeks;
if (period != _lastPeriod) {
    // ... (period transition logic)
    _newPeriod.startTick = slot0Start.tick;
    $.periods[period] = _newPeriod;
}
Oracle write function (recording incorrect tick):
if (state.tick != slot0Start.tick) {
    (uint16 observationIndex, uint16 observationCardinality) = Oracle.write(
        $.observations,
        slot0Start.observationIndex,
        cache.blockTimestamp,
        slot0Start.tick,  // Uses initial tick, not final tick
        cache.liquidityStart,
        slot0Start.observationCardinality,
        slot0Start.observationCardinalityNext
    );
    // ...
}

Impact:

The manipulated price becomes the reference point for the entire week.
This can lead to mispricing in all protocols that rely on this pool for oracle data.
Potential for unjustified liquidations, unfair arbitrage, and overall ecosystem instability.
The attacker can repeat this process weekly, creating long-term distortions in price data.

The precision timing required for this attack makes it particularly insidious, as it exploits the exact moment of period transition to maximize impact while minimizing the window of obvious price manipulation.

## Recommended Mitigation Steps

Maybe just modify the Oracle.write function to record state.tick instead of slot0Start.tick:

(uint16 observationIndex, uint16 observationCardinality) = Oracle.write(
    $.observations,
    slot0Start.observationIndex,
    cache.blockTimestamp,
    state.tick,  // Use final tick
    state.liquidity,  // Use final liquidity
    slot0Start.observationCardinality,
    slot0Start.observationCardinalityNext
);
