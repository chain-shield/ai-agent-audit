# Vulnerability details

## Proof of Concept

For context, the vulnerable function showing an Authorization Bypass:

```solidity
if (params.liquidityDelta < 0) {
            if (flippedLower) {
                Tick.clear($._ticks, params.tickLower, period);
            }
            if (flippedUpper) {
                Tick.clear($._ticks, params.tickUpper, period);
            }
        }
```

The code snippet demonstrates an authorization bypass vulnerability. The `if (params.liquidityDelta < 0)` condition allows for the clearing of tick data based on a negative liquidity delta.  An attacker can potentially manipulate the `params.liquidityDelta` value to trigger this condition, even if they do not have the necessary permissions to clear tick data. 

This can lead to unauthorized modification of the state of the smart contract.

## Recommended Mitigation Steps

I'd recommend several mitigation steps to fix the attack path and vulnerability above:

a.  Require input validation for liquidityDelta.  Require devs to ensure liquidityDelta values are validated to prevent negative values from unauthorized users. This could include role-based checks to confirm that only privileged addresses can initiate tick-clearing actions.

b.  Role-Based Access Control (RBAC) requirements; require that devs introduce granular RBAC specifically for functions involving tick manipulation. For example, limit tick-clearing permissions to certain privileged roles or contracts, thus preventing unauthorized state changes.

c.  Pre-Condition check requirements: require devs to add conditions that verify if the caller has proper authorization and permissions before clearing any tick data. This can be enforced at the beginning of functions that modify liquidity ranges or tick data.
