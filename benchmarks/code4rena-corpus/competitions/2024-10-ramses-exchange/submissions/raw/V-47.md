# Vulnerability details

## Proof of Concept

Hash collision occurs when hash function creates the same output for two different inputs. This is undesirable since hash function should always produce unique outputs. Keccak256 would produce a unique output for every unique input. But, here because abi.encodePacked is used, it is possible to produce the same output with different inputs.

In the below `positionHash` function, it is possible to generate same output hash for two different inputs.

```solidity
   function positionHash(
        address owner,
        uint256 index,
        int24 tickLower,
        int24 tickUpper
    ) internal pure returns (bytes32) {
        return keccak256(abi.encodePacked(owner, index, tickLower, tickUpper));
    }
```

Example: In the below, it is possible to pass two different `tickLower` and `tickUpper` values and generate the same position hash.

```
    bytes32 _positionHash1 = positionHash(0x0AAA,1,5,560);
    bytes32 _positionHash2 = positionHash(0x0AAA,1,55,60);
```    

In the above example, while the `tickLower` and `tickUpper` values passed are different, they will still produce the same positionHash.

In GaugeV3 contract, the positionHash is assumed to be unique to track the reward claims. Hence it is possible for the attacker to abuse the `tickLower` and `tickUpper` values to claim rewards.


## Recommended Mitigation Steps
Replace `abi.encodePacked` with `abi.encode` to prevent this vulnerability. 
Using abi.encode, each argument gets padded to a fixed 32-byte size, reducing the risk of ambiguity between arguments. But, this will eliminate the potential risk that arises from using `abi.encodePacked`.
