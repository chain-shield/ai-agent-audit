# Vulnerability details

## Vulnerability details

In the `RamsesV3Factory.createPool` function, the input tokens (`tokenA` and `tokenB`) are lexicographically sorted to determine the final `token0` and `token1`. However, the `sqrtPriceX96` parameter, which represents the square root of the initial price of the pool, is passed by the external caller assuming the price reflects the ratio between `tokenA` and `tokenB`.

Since the function internally reorders the tokens based on their address values (`token0 = min(tokenA, tokenB)`), there is a mismatch in the interpretation of `sqrtPriceX96`. If the tokens are reordered, the price ratio changes (it should be inverted), but the external caller may not account for this, resulting in an incorrect initialization of the pool’s price.

### Impact:

This incorrect price initialization can lead to the following issues:

- Arbitrage opportunities, as the incorrect price might create a gap between the actual market price and the pool's price.
- Liquidity providers (LPs) might suffer losses due to incorrect pool pricing.
- Traders relying on accurate pool pricing may experience slippage or receive incorrect swap rates.

This issue can occur frequently, as token reordering is done internally without an automatic adjustment of the price, making it easy for external pool creators to initialize the pool with an incorrect price.

## Proof of Concept

In the `RamsesV3Factory.createPool` function, the input tokens `tokenA` and `tokenB` are lexicographically reordered internally:

```solidity
(address token0, address token1) = tokenA < tokenB ? (tokenA, tokenB) : (tokenB, tokenA);
```

However, the `sqrtPriceX96` parameter is passed externally, assuming the original order of `tokenA` and `tokenB`, without considering this internal reordering. The passed `sqrtPriceX96` is directly used to initialize the pool:

```solidity
IRamsesV3Pool(pool).initialize(sqrtPriceX96);
```

If the tokens are swapped internally, the `sqrtPriceX96` value should reflect the inverted price ratio, but it does not. This results in the pool being initialized with an incorrect price.

For example, if `tokenA` is `USDC` and `tokenB` is `DAI`, and `tokenA`'s address is higher than `tokenB`'s address, `sqrtPriceX96` is based on the ratio of `USDC/DAI`. After the reordering, the contract expects the price to represent `DAI/USDC`, leading to a significant mismatch.

### Steps to Reproduce:

1. Create a pool with tokens `tokenA` and `tokenB` where `tokenA`'s address is greater than `tokenB`'s address.
2. Pass a `sqrtPriceX96` value assuming the ratio between `tokenA` and `tokenB`.
3. Observe that the pool is initialized with an incorrect price due to the internal reordering of tokens.

## Recommended Mitigation Steps

There are two potential mitigation steps:

1. Require the external caller to pass `sqrtPriceX96` with awareness of the internal token reordering. The contract can document this requirement clearly.
2. Alternatively, adjust the `sqrtPriceX96` internally after token reordering. In the `createPool` function, after determining the correct `token0` and `token1`, check if the tokens were swapped, and if so, invert the `sqrtPriceX96` value before calling `initialize`:

```solidity
if (token0 != tokenA) {
    // Invert the sqrtPriceX96 if tokens were swapped
    sqrtPriceX96 = uint160((uint256(1) << 192) / sqrtPriceX96);
}
```

This adjustment ensures that the price passed to the pool matches the correct token order, preventing incorrect pool initialization.
