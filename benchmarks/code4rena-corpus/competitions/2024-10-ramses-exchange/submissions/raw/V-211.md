# Vulnerability details

The initialize function starts the first period before setting the correct tick of the market:
```solidity
        _advancePeriod();

        $.slot0 = Slot0({
            sqrtPriceX96: sqrtPriceX96,
            tick: tick,
            observationIndex: 0,
            observationCardinality: cardinality,
            observationCardinalityNext: cardinalityNext,
            feeProtocol: 0,
            unlocked: true
        });
```

This means that for the first period, `periods[lastPeriod].lastTick == 0` and `periods[currentPeriod].startTick == 0`, while it should be set to the corresponding amount of the input price of the initializer.

The contract is calculating the `Oracle.periodCumulativesInside` values based on the start tick, as an example, if a tick is bigger than the start tick and has never been crossed, is assumed that it has been above the tick for the whole period and has a `secondsPerLiquidityOutside` of zero. While this is in place, the calculation of the final `secondsPerLiquidityInside` for a tick is based on the actual current tick, these two combined can lead to unexpected situations.

### Impact
This will impact the internal calculations of the protocol. The oracle function `periodCumulativesInside` which is important to the rewards calculation is using the start tick to figure out the correct value of `secondsPerLiquidityOutside` which are tracked for reward and fee accrual.
```solidity
            int24 startTick = $.periods[period].startTick;
            uint256 previousPeriod = $.periods[period].previousPeriod;

            snapshot.secondsPerLiquidityOutsideLowerX128 = uint160(lower.periodSecondsPerLiquidityOutsideX128[period]);

            if (tickLower <= startTick && snapshot.secondsPerLiquidityOutsideLowerX128 == 0) {
                snapshot.secondsPerLiquidityOutsideLowerX128 = $
                    .periods[previousPeriod]
                    .endSecondsPerLiquidityPeriodX128;
            }

            snapshot.secondsPerLiquidityOutsideUpperX128 = uint160(upper.periodSecondsPerLiquidityOutsideX128[period]);
            if (tickUpper <= startTick && snapshot.secondsPerLiquidityOutsideUpperX128 == 0) {
                snapshot.secondsPerLiquidityOutsideUpperX128 = $
                    .periods[previousPeriod]
                    .endSecondsPerLiquidityPeriodX128;
            }
```
This section's assumptions will be incorrect, and the `Oracle.periodCumulativesInside` will be incorrectly calculated.
As an example, imagine:
- `startTick` is considered 0
- the actual tick is set to `200,000`
- for a range in [-10,000, 100,000), the protocol considers `secondsPerLiquidityUpper` to be 0, and `secondsPerLiquidityLower` to be equal to last period's ending `secondsPerLiquidity`.
- The first periods `secondsPerLiquidity` is equal to the timestamp at the time of creation at initialization because of the [initial time being set to zero](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/core/RamsesV3Pool.sol#L159).
- When `tick` is higher that both ticks in a position, it should be impossible for `secondsPerLiquidityOutside` of the higher tick to be smaller than the lower tick. The invariant here should be that `if tick > upperTick > lowerTick`, then `secondsPerLiquidityOutsideUpper > secondsPerLiquidityOutsideLower`.
```
  lower       0             upper            Actual Tick        
----|----|----|----|----|----|----|----|----|----|----
```

### Proof of Concept
In the example Below, the `testFirstTick` function is testing three positions with the actual starting tick of `198,000` (the first period considers it as zero):
- Alice's position should be active but the `Oracle.periodCumulativesInside` is outputing zero. -> incorrect
- Bob's position should never be active but it is considered active but Oracle library. -> incorrect
- Charlie's position should never be active. -> correct

### Mitigation
Correctly advance the period after setting the `slot0`.
