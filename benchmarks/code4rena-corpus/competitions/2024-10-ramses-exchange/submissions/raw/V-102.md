# Vulnerability details

## Proof of Concept

The `periodCumulativesInside` function of the Oracle library being used to liquidity data for seconds interval inside a tick range has a flaw in that it treats cases whereby the `currentPeriod` is still in session as a new session leading to inaccurate seconds per liquidity data being retrieved and used for a tick range


In the function below, let's suppose the call to `periodCumulativesInside` is initiated from the `_updatePosition` function of the Position library:

```solidity
function _updatePosition(UpdatePositionParams memory params,uint256 counter) external returns (PositionInfo storage position) {
        
    PoolStorage.PoolState storage $ = PoolStorage.getStorage();

    /// @dev calculate the period once, and reuse it
@>    uint256 period = params._blockTimestamp / 1 weeks;
    // 1,576,800,000 / 604,800 = 2,607.1428571429

    /// @dev get the seconds per liquidity period cumulatives
    uint160 secondsPerLiquidityPeriodX128 = Oracle.periodCumulativesInside(
@>        uint32(period),
        params.tickLower,
        params.tickUpper,
        params._blockTimestamp
    );
    ...
}
```

```solidity
function periodCumulativesInside(
        uint32 period,
        int24 tickLower,
        int24 tickUpper,
        uint32 _blockTimestamp
    ) external view returns (uint160 secondsPerLiquidityInsideX128) {   

        PoolStorage.PoolState storage $ = PoolStorage.getStorage();

        ...

        int24 lastTick;
@>        uint256 currentPeriod = $.lastPeriod; // e.g 2607

        {
            /// @dev if period is already finalized, use period's last tick, if not, use current tick
@>            if (currentPeriod > period) { // 2607 > 2607
                console.log("inside if");
                lastTick = $.periods[period].lastTick;
            } else {
                console.log("inside else");
                lastTick = $.slot0.tick;
            }
        }
```

Given that we are still within the `currentPeriod` e.g `$.lastPeriod` = 2607, `period` = 2607, instead of using the period's last tick, it goes ahead to use the current tick of the pool even though a new period (week) has not ensued yet.

For the record, the very first time we run into the `periodCumulativesInside` function, both `currentPeriod` && `period` will be the same e.g 2607, a week later, `period` will outgrow `currentPeriod` and this is when we typically would enter the else block to return the current tick of the pool to later be used for the calculation, not entering the else block even though a new period is not yet in session.

In essence, the returned data is not calculated correctly when the current period is still in session and a new session is yet to begin.

## Recommended Mitigation Steps
The diff below should replace the current `if` check of the Oracle library in the `periodCumulativesInside` function:

```diff
+ if (currentPeriod >= period) {
- if (currentPeriod > period) { 
```
