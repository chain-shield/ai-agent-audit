# Vulnerability details

### Proof of Concept

##### Problem Overview

In the observed code, the primary concern revolves around potential division by zero in the `observeSingle` function, which can impact critical functions responsible for calculating liquidity, tick accumulators, and other pool-related metrics. These calculations are central to the protocol’s operations, and a division by zero could lead to transaction failures, inaccurate metrics, or even a denial of service (DoS) attack vector.

##### Explanation of the Issue

The variable `uint32 observationTimeDelta = atOrAfter.blockTimestamp - beforeOrAt.blockTimestamp` on `observeSingle` function can potentially result in zero. This situation arises when atOrAfter.blockTimestamp is equal to beforeOrAt.blockTimestamp. In this case, the subtraction yields a value of zero, which may lead to division by zero issues in subsequent calculations.

```Solidity
/// @dev we're in the middle
uint32 observationTimeDelta = atOrAfter.blockTimestamp - beforeOrAt.blockTimestamp;
uint32 targetDelta = target - beforeOrAt.blockTimestamp;
return (
  beforeOrAt.tickCumulative +
  ((atOrAfter.tickCumulative - beforeOrAt.tickCumulative) / int56(uint56(observationTimeDelta))) *
  int56(uint56(targetDelta)),
  beforeOrAt.secondsPerLiquidityCumulativeX128 +
  uint160(
  (uint256(
  atOrAfter.secondsPerLiquidityCumulativeX128 -
  beforeOrAt.secondsPerLiquidityCumulativeX128
  ) * targetDelta) / observationTimeDelta
  )
);
```

This value is obtained by `getSurroundingObservations` function, that uses only `if (!lte(time, beforeOrAt.blockTimestamp, target)) revert OLD()` line to verify it.

The function `lte`, defined as follows:

```Solidity
function lte(uint32 time, uint32 a, uint32 b) private pure returns (bool) {
    unchecked {
        if (a <= time && b <= time) return a <= b;

        uint256 aAdjusted = a > time ? a : a + 2 ** 32;
        uint256 bAdjusted = b > time ? b : b + 2 ** 32;

        return aAdjusted <= bAdjusted;
    }
}
```

is designed to compare timestamps and ensures that both a and b are chronologically before or equal to time. However, it does not inherently prevent `observationTimeDelta` from being zero. If beforeOrAt and atOrAfter are the same, the check only confirms their chronological order but does not affect the potential for a zero difference in timestamps.

This oversight can result in significant issues in the contract, particularly if observationTimeDelta is used in subsequent calculations that involve division. A division by zero can cause the transaction to revert, leading to loss of functionality or unintended behaviors within the contract.

##### Functions Impacted by This Issue

1. observe
Functionality: Computes cumulative values for tick and liquidity over time for various points (secondsAgos).
Impact: If the liquidity is zero at any point, it will revert or cause inaccuracies across multiple secondsAgo points. This would directly impact the protocol’s ability to accurately compute historical liquidity and ticks.

2. snapshotCumulativesInside
Functionality: Takes a snapshot of cumulative tick and liquidity for a specific range of ticks.
Impact: If liquidity is zero during the observation, this function will either fail or produce inaccurate snapshots, which could result in inaccurate accounting of liquidity within the tick range.
3. periodCumulativesInside
Functionality: Calculates liquidity over a given period for a specific range of ticks.
Impact: A division by zero could prevent the correct calculation of historical liquidity, impacting liquidity providers (LPs) relying on these values for calculating their rewards or managing positions.

### Impact

The division by zero vulnerability has several serious implications:

- Transaction Reverts: The protocol’s core functions will revert when liquidity is zero, preventing essential operations such as calculating historical liquidity and tick data.
- Denial of Service (DoS): If an attacker can manipulate liquidity to be zero, they could exploit this to cause a DoS condition by repeatedly triggering the division by zero and making it impossible to execute certain functions.
- Inaccurate Calculations: In cases where the code handles division by zero by returning fallback values (e.g., 1), the accuracy of liquidity and tick calculations may degrade, potentially leading to mispriced swaps and incorrect position calculations for liquidity providers.

#### Recommended Mitigation Steps

1. Implement a check for zero before performing division: Ensure that observationTimeDelta is greater than zero before any division operations.
2. Add error handling: Introduce proper error messages or revert reasons to handle scenarios where observationTimeDelta could be zero.
3. Review and test: Conduct thorough testing with scenarios where atOrAfter and beforeOrAt are equal to ensure that the system behaves as expected.
