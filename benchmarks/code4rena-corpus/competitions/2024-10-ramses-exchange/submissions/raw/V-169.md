# Vulnerability details

## Proof of Concept
Insecure Reward Tracking Mechanism: The contract’s reward tracking (periodClaimedAmount) could be manipulated through repeated calls if there is improper tracking in claims for multiple periods. Attackers could call reward functions repeatedly to claim more than intended.

Proof of Concept:A malicious user can repeatedly call claimReward() from different addresses to drain the rewards pool for each week, as there is no proper check against each address’s contribution or entitlement. Additionally, reentrancy attacks are possible due to improper state updates. Repeated calls to cachePeriodEarned might also cause an overflow in reward claims if limits are not set:
await gauge.getReward(tokenId, tokens);
here is a code snippet:
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.13;

import "@openzeppelin/contracts/token/ERC20/IERC20.sol";

contract InsecureRewardTracker {
    IERC20 public rewardToken;

    uint256 public constant WEEK = 1 weeks;
    uint256 public immutable startTime;

    // Maps user address to reward amount claimed
    mapping(address => uint256) public claimedRewards;

    // Maps week period to total reward pool for that period
    mapping(uint256 => uint256) public weeklyRewards;

    // Maps user address to the last week they claimed rewards
    mapping(address => uint256) public lastClaimWeek;

    constructor(address _rewardToken) {
        rewardToken = IERC20(_rewardToken);
        startTime = block.timestamp;
    }

    function claimReward() external {
        uint256 currentWeek = (block.timestamp - startTime) / WEEK;
        uint256 lastClaimed = lastClaimWeek[msg.sender];

        // Calculate reward for all weeks since the last claim
        uint256 rewardAmount;
        for (uint256 week = lastClaimed; week < currentWeek; week++) {
            rewardAmount += weeklyRewards[week];
        }

        require(rewardAmount > 0, "No rewards to claim");

        // Update last claimed week without reentrancy protection
        lastClaimWeek[msg.sender] = currentWeek;

        // Vulnerable: reward calculation is based on the total rewards without properly checking user’s share
        rewardToken.transfer(msg.sender, rewardAmount);
    }

    function setWeeklyRewards(uint256 week, uint256 amount) external {
        // Update reward pool for a specific week
        weeklyRewards[week] = amount;
    }
}

Impact: If exploited, users could claim more rewards than entitled, causing contract funds to deplete quickly
## Recommended Mitigation Steps
1. Use Access Control for Reward Adjustment: Only authorized addresses (e.g., contract owner) should set weekly rewards.
2. Track Individual Contributions: Use per-user accounting by calculating and storing each user’s share of rewards per week. Use a mapping structure such as mapping(address => mapping(uint256 => uint256)) userWeeklyRewards;.
3. Prevent Reentrancy: Apply the checks-effects-interactions pattern by updating lastClaimWeek[msg.sender] only after the transfer.
4.Add Tests and Validation: Ensure users cannot claim rewards for weeks when they had no stake.
