# Vulnerability details

## Description

The Oracle library is designed to manage price and liquidity observations for an AMM pool. The grow function is meant to increase the capacity of the observation array, allowing for more historical data to be stored.

The grow function allows for increasing the size of the observation array without an upper bound check.

## Code

```solidity
function grow(Observation[65535] storage self, uint16 current, uint16 next) internal returns (uint16) {
    unchecked {
        if (current <= 0) revert I();
        /// @dev no-op if the passed next value isn't greater than the current next value
        if (next <= current) return current;
        /// @dev store in each slot to prevent fresh SSTOREs in swaps
        /// @dev this data will not be used because the initialized boolean is still false
        for (uint16 i = current; i < next; i++) self[i].blockTimestamp = 1;
        return next;
    }
}
```

## Impact
This can lead to several issues:

1. Unbounded Growth:
   The function allows `next` to be any value up to 65535 (the maximum value of uint16) without any upper bound check. This can lead to the array growing to an impractically large size.

2. Gas Limit Vulnerability:
   If `next` is set to a very large value, the for-loop could consume an enormous amount of gas, potentially exceeding block gas limits. This could make the function unusable or, worse, could be exploited to create a denial-of-service condition.

3. Inconsistent State:
   The function doesn't update any global state variable to reflect the new size of the array. This could lead to inconsistencies between the actual array size and what other parts of the contract believe the size to be.

4. Economic Attacks:
   An attacker could intentionally grow the array to its maximum size, making future operations that iterate over the array (like `write` or `observe`) prohibitively expensive.

## Scenario

```solidity
// Assume current size is 100
uint16 current = 100;
uint16 malicious_next = 65535;

// This call would be extremely expensive and could exceed block gas limits
oracle.grow(current, malicious_next);

// Future calls to write would now be extremely expensive
oracle.write(65534, block.timestamp, 0, 0, 65535, 65535);
```

In this scenario, the `grow` function would attempt to initialize over 65,000 storage slots, consuming an enormous amount of gas. Subsequent `write` operations would then have to iterate over this massive array, making them impractically expensive.

## Fix

To fix this issue, we need to implement several safeguards:

1. Add an upper bound to the array size.
2. Update a state variable to track the current array size.
3. Implement a more gas-efficient way of growing the array.


```solidity
uint16 public constant MAX_OBSERVATIONS = 1000; // Choose a reasonable maximum
uint16 public observationCardinality;

function grow(Observation[65535] storage self, uint16 current, uint16 next) internal returns (uint16) {
    if (current <= 0) revert I();
    if (next <= current) return current;
    if (next > MAX_OBSERVATIONS) revert MaxObservationsExceeded();
    
    // Only initialize new slots
    for (uint16 i = observationCardinality; i < next; i++) {
        self[i].blockTimestamp = 1;
    }
    
    // Update the cardinality
    observationCardinality = next;
    return next;
}
```

This fixed version:

1. Introduces a `MAX_OBSERVATIONS` constant to cap the array size.
2. Uses an `observationCardinality` variable to track the current size.
3. Only initializes new slots, rather than reinitializing all slots.
4. Updates the `observationCardinality` to reflect the new size.

Additionally, you should review and update other functions that interact with the observation array to use `observationCardinality` instead of assuming a fixed size.
