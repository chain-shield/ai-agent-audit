# Vulnerability details

## Proof of Concept
Solidity rounds down the result of an integer division, and because of that, it is always recommended to multiply before dividing to avoid that precision loss. In the case of a prior division over multiplication, the final result may face serious precision loss as the first answer would face truncated precision and then multiplied to another integer.
The problem arises in Oracle's observation part when it tries to calculate the tick cumulative. After checking the timestamps, the next step is to calculate the tick cumulative and seconds per liquidity cumulative.
If we look deeply at the function `observeSingle()` we can see the tick cumulative calculation is presented as:

If the target is between the `beforeOrAt` or `atOrAfter`, the `tickCumulative` will be computed as:

$$ tickCumulative = tickCumulative_{before} + ( \frac{tickCumulative_{after} - tickCumulative_{before}}{observationTime} \times targetDelta ) $$

The problem here is that, in some cases, the tick cumulative would be calculated wrongly, as this pattern prioritizes division over multiplication. This model also lacks sufficient sensitivity for division accuracy.

You can run this code to see the difference between the results:

```Solidity
    function test_precissionLoss() public {

        uint beforeOrAtTickCumulative = 212814;
        uint atOrAfterTickCumulative = 617253;
        uint observationTimeDelta = 562310;
        uint targetDelta = 524790;

        uint tickCumulative_actual = beforeOrAtTickCumulative + (((atOrAfterTickCumulative - beforeOrAtTickCumulative) / observationTimeDelta) * (targetDelta));
        uint tickCumulative_precise = beforeOrAtTickCumulative + (((atOrAfterTickCumulative - beforeOrAtTickCumulative) * targetDelta) / (observationTimeDelta));
        
        console.log("Current Implementation: ", tickCumulative_actual);
        console.log("Accurate Implementation: ", tickCumulative_precise);
    }
```

The result would be:

```  
     Current Implementation:  212814
     Accurate Implementation:  590266
```
Thus, we can see that the actual implementation produces less fee amount than the precise method. This huge diversity here arises from the fact that the division part truncates the result to 0. Thus, in the cases where the `targetDelta` is bigger than the `beforeOrAtTickCumulative` and `atOrAfterTickCumulative` differences.

Furthermore, it is better to mention that some protocols implement this pattern to have an integer part of the division (usually in time-related situations). However, we can clearly see if the abovementioned criteria hold, the tick cumulative calculations break.
