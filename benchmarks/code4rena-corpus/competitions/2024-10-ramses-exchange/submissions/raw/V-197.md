# Vulnerability details

## Summary

The current `removeRewards` function implementation uses a shifting pattern that incurs significant gas costs, particularly for large arrays:

```solidity
// Current inefficient implementation
for (uint256 i = idx; i < rewards.length - 1; ++i) {
    rewards[i] = rewards[i + 1];  // Multiple SSTORE operations
}
rewards.pop();
```

Each shift operation costs approximately 3000 gas (SLOAD + SSTORE), and removing an element at index `i` requires `(n-i-1)` shifts. For a rewards array of size n, this results in O(n) gas complexity, making it prohibitively expensive for large arrays.

The optimal solution is to use swap-and-pop:
```solidity
// Gas-efficient swap-and-pop
if (rewardIdx != lastIndex) {
    rewards[rewardIdx] = rewards[lastIndex];  // Single SSTORE
}
rewards.pop();  // Single SSTORE
```

This reduces the operation to O(1) complexity with only two storage writes, regardless of array size or removal position. While this changes array ordering, it's an acceptable tradeoff since reward token order isn't functionally important in this contract.

The gas savings are substantial - potentially thousands of gas per operation - making this optimization critical for protocol scalability and resistance to gas-based DOS attacks.

## Impact

The array shifting implementation creates several severe operational and economic implications:

**Protocol Level Impact:**
```solidity
// Current vulnerable code that can lead to excessive gas costs
for (uint256 i = idx; i < rewards.length - 1; ++i) {
    rewards[i] = rewards[i + 1];  // Each iteration: ~3000 gas
}
```

Let's quantify this with real numbers. Assume a rewards array with 100 tokens:
```solidity
// Removing first token (worst case)
Gas cost = (n-1) shifts * (SLOAD + SSTORE cost)
        = 99 shifts * (~3000 gas)
        = ~297,000 gas
```

This leads to three critical issues:

1. **Transaction Failure Risk**
```solidity
function removeRewards(address reward) external {
    // If rewards array is large enough, this function could hit block gas limit
    // Current block gas limit: ~30M gas
    // Could fail with: "out of gas" error
}
```

2. **Economic Denial of Service (eDoS)**
```solidity
// Attacker strategy:
// 1. Wait for rewards array to grow large
// 2. Protocol needs to remove early reward token
// 3. Transaction costs become prohibitively expensive
rewards = [TokenA, TokenB, ..., TokenZ];  // Large array
// Removing TokenA becomes extremely expensive
```

3. **Protocol Administration Paralysis**
```solidity
// Scenario: Critical protocol management
try gauge.removeRewards(compromisedToken) {
    // Transaction reverts due to gas limit
    // Protocol stuck with compromised token
} catch {
    // No fallback mechanism
}
```

Real-world impact quantification:
```solidity

Cost = 297,000 gas * 50 gwei * $3,000/ETH
```

The impact severity increases with:
1. Larger rewards arrays
2. Higher gas prices
3. Higher ETH price
4. More frequent reward token management

This creates a compounding problem:
```solidity
// Time t0: Small array, manageable gas costs
rewards = [TokenA, TokenB, TokenC];  // 3 tokens

// Time t1: Array grows, costs increase
rewards = [TokenA, ..., TokenZ];     // 26 tokens

// Time t2: Protocol scale increases, costs become prohibitive
rewards = [TokenA, ..., Token100];   // 100 tokens
```

The inefficiency could force the protocol to:
1. Limit the number of reward tokens
2. Pay excessive gas fees
3. Delay critical token removals
4. Deploy new contracts to reset state

## Fix

Mitigation requires implementing the swap-and-pop pattern:
```solidity
function removeRewards(address reward) external {
    // ...
    uint256 lastIndex = rewards.length - 1;
    if (rewardIdx != lastIndex) {
        rewards[rewardIdx] = rewards[lastIndex];  // Single SSTORE
    }
    rewards.pop();  // Single SSTORE
    // ...
}
```

This changes the gas cost from O(n) to O(1), making the function:
- Consistently cheap to execute
- Immune to array size scaling
- Resistant to gas-based DoS
- Reliable for protocol management

The improved efficiency is critical for protocol sustainability and operational security.
