# Vulnerability details

## Summary
In FeeCollector.sol, it is possible for the treasury fee percentage to be updated using function [setTreasuryFees()](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/gauge/FeeCollector.sol#L57), 

The issue is that the new percentage is directly applied to the previous accumulated rewards/fees from all the pools. This could lead us into two issues:

If the new treasury fee percentage is set to a lower value at time `t`, the previous fees accumulated uptil time `t` would not be collected at the rate they were earned at and are instead received at the lower rate.

Similarly, if the new treasury fee percentage is updated to a higher value at time `t`, the previous fees accumulated uptil time `t` are collected at the higher rate. This could be seen as a problem by the voters since the accumulated fees earned and allocated to them uptil time `t` were higher. (Context: see how the fees are distributed between voters and treasury [here](https://discord.com/channels/810916927919620096/1290740440873697320/1293674297616896093))

This is also an invariant suggested in the README - `reward accounting being accurate and not substantially inflated or deflated from reality are crucial.` In our case, the previous rewards/fees would be collected at a lower or higher rate than they were actually earned at.

## Proof of Concept

1. Let's assume the fees accumulated are 1e18 of token A and B each for a specific pool. This is uptil time `t`. The [`treasuryFees`](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/gauge/FeeCollector.sol#L22) variable value is 100 (i.e. 1%).

2. The treasury decides to update the value of `treasuryFees` to 1000 (i.e. 10%) using function [setTreasuryFees()](https://github.com/code-423n4/2024-10-ramses-exchange/blob/4a40eba36bc47eba8179d4f6203a4b84561a4415/contracts/CL/gauge/FeeCollector.sol#L57) at time `t`. 

```solidity

        uint256 _treasuryFees

        require(_treasuryFees <= BASIS, FTL());
        emit TreasuryFeesChanged(treasuryFees, _treasuryFees);

        treasuryFees = _treasuryFees;
    }
```

3. ## Recommended Mitigation Steps
While implementing a solution for this looks complicated considering every pool needs to be considered, there is a simple solution to this:

Since we know the fees are earned on swap() and flash() actions, everytime the `feeProtocol` variable is charged in the pool fees, retrieve the treasuryFees value from the FeeCollector and apply it on the value returned from the `feeProtocol` operation. Set the value to a accumulatedTreasuryFees variable on the pool itself and the remaining to the voters so that when the FeeCollector collects the fees, the treasuryFees can be directly retrieved from there.

For example, let's assume fees earned from a single swap() or flash() action is 1e18 for simplicity. When `feeProtocol` is applied on this, 80% (default value) is allocated to the FeeCollector. Now this 80% value can be further split to the treasury and voters right there. The treasury rate can retrieved from the FeeCollector directly. We would need to introduce two variables to track the accumulated amounts. This way, the fees earned by the treasury are always earned at the rate they were accumulated at. Now the fee collector can just read these values from the specific pool and collect them.
