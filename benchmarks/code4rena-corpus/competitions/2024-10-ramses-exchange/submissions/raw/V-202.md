# Vulnerability details

## Summary
The `update` function lacks safeguards against overlapping liquidity positions, allowing multiple positions to occupy overlapping tick ranges without restrictions. This can lead to liquidity fragmentation, distorted price curves, and potential manipulation of fee accumulation across overlapping ranges. The core issue stems from independent tracking of net liquidity changes without considering the cumulative effect of position overlaps.

In concentrated liquidity AMMs, liquidity positions are defined by their tick ranges [tickLower, tickUpper]. The `update` function handles liquidity changes for these positions through a crucial piece of code:

```solidity
info.liquidityNet = upper 
    ? info.liquidityNet - liquidityDelta 
    : info.liquidityNet + liquidityDelta;
```

This logic tracks net liquidity changes at tick boundaries, but it operates in isolation without considering the broader context of existing positions. The fundamental issue becomes clear when we examine how liquidity accumulates across tick ranges.

Consider this scenario:
```solidity
// Initial position
Position A: [tick 100, tick 200] with 1000 liquidity

// Net liquidity changes:
tick 100: +1000 (lower tick)
tick 200: -1000 (upper tick)

// Everything looks normal
```

However, the system allows creation of overlapping positions:
```solidity
// Overlapping position
Position B: [tick 150, tick 250] with 2000 liquidity

// Net liquidity changes now:
tick 100: +1000
tick 150: +2000
tick 200: -1000
tick 250: -2000
```

The issue manifests in several ways due to how the AMM handles liquidity and fee accounting:

1. Fee Calculation Distortion:
```solidity
// From getFeeGrowthInside:
feeGrowthInside0X128 = feeGrowthGlobal0X128 - feeGrowthBelow0X128 - feeGrowthAbove0X128;
```
When positions overlap, fee growth calculations become complex and potentially inaccurate because the function assumes discrete liquidity ranges rather than overlapping ones.

2. Price Impact Calculations:
```solidity
// Simplified virtual reserves calculation (not in code)
uint256 virtualLiquidity = getVirtualLiquidityForTick(currentTick);
// With overlaps, virtualLiquidity might not accurately represent available liquidity
```

3. Liquidity Fragmentation:
```solidity
function update(
    // ...
    int128 liquidityDelta,
    // ...
) internal returns (bool flipped) {
    // No checks for existing positions in the range
    info.liquidityGross = liquidityGrossAfter;
    info.liquidityNet = upper ? info.liquidityNet - liquidityDelta : info.liquidityNet + liquidityDelta;
}
```

An attacker could exploit this by creating multiple overlapping positions:

```solidity
// Attack scenario
// 1. Create base position
update(tick: 1000, liquidityDelta: 1000, upper: false);
update(tick: 2000, liquidityDelta: 1000, upper: true);

// 2. Create overlapping positions
update(tick: 1500, liquidityDelta: 2000, upper: false);
update(tick: 2500, liquidityDelta: 2000, upper: true);

// 3. Create more overlaps
update(tick: 1750, liquidityDelta: 3000, upper: false);
update(tick: 2750, liquidityDelta: 3000, upper: true);
```

This creates a liquidity distribution that's difficult to predict and potentially manipulate. When the price moves through these ranges, the actual available liquidity might not match what traders expect, leading to unexpected price impacts.

## Fix
A proper fix would require tracking position overlaps and implementing restrictions:

```solidity
struct TickInfo {
    uint128 liquidityGross;
    int128 liquidityNet;
    // Add position tracking
    mapping(bytes32 => uint128) positionLiquidity; // position ID -> liquidity
    uint256 activePositions;
}

function update(
    mapping(int24 => TickInfo) storage self,
    int24 tick,
    int24 tickCurrent,
    int128 liquidityDelta,
    bytes32 positionId,  // New parameter
    // ...
) internal returns (bool flipped) {
    TickInfo storage info = self[tick];
    
    // Track individual position liquidity
    uint128 positionLiquidityBefore = info.positionLiquidity[positionId];
    uint128 positionLiquidityAfter = liquidityDelta < 0
        ? positionLiquidityBefore - uint128(-liquidityDelta)
        : positionLiquidityBefore + uint128(liquidityDelta);
        
    // Update position tracking
    if (positionLiquidityBefore == 0 && positionLiquidityAfter > 0) {
        info.activePositions++;
    } else if (positionLiquidityBefore > 0 && positionLiquidityAfter == 0) {
        info.activePositions--;
    }
    
    // Implement overlap restrictions
    if (info.activePositions > MAX_OVERLAPPING_POSITIONS) 
        revert("Too many overlapping positions");
        
    // Update position liquidity
    info.positionLiquidity[positionId] = positionLiquidityAfter;
    
    // Rest of the function...
}
```
