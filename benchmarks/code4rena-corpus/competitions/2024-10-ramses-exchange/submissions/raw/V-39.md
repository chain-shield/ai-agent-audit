# Vulnerability details

## Description

There is a critical vulnerability in the `enableTickSpacing` function of the `RamsesV3Factory` contract. This bug could potentially lead to severe inefficiencies in the protocol and open up avenues for Denial of Service (DoS) attacks.

## Code

```solidity
function enableTickSpacing(int24 tickSpacing, uint24 initialFee) external override restricted {
    require(initialFee < 1_000_000, FTL());
    require(tickSpacing > 0 && tickSpacing < 16384, 'TS');
    require(tickSpacingInitialFee[tickSpacing] == 0, 'TS!0');

    tickSpacingInitialFee[tickSpacing] = initialFee;
    emit TickSpacingEnabled(tickSpacing, initialFee);
}
```

The issue lies in the lenient validation of the `tickSpacing` parameter. While it does check that `tickSpacing` is greater than 0 and less than 16384, it allows for extremely small tick spacings, including a value of 1.

## Impact

To understand why this is problematic, we need to consider how tick spacings are used in the broader context of the Ramses V3 protocol, which is based on Uniswap V3's design.

In Uniswap V3 (and by extension, Ramses V3), the price range for a pool is divided into "ticks". The tick spacing determines the granularity of these price ranges. A smaller tick spacing allows for more precise liquidity provision but comes with significant drawbacks:

1. Gas Inefficiency:
   Operations that need to iterate over ticks (like swaps that cross multiple price ranges) become more expensive as the number of ticks increases. With a tick spacing of 1, you're effectively allowing for the maximum possible number of ticks.

2. Storage Bloat:
   Each initialized tick consumes storage. With a very small tick spacing, many more ticks can be initialized, leading to excessive storage usage.

3. DoS Vulnerability:
   An attacker could create a pool with a tiny tick spacing and initialize a large number of ticks across a wide price range. This would make operations like swapping or providing liquidity prohibitively expensive for normal users.

## Exploit Scenario

```solidity
// In RamsesV3Factory
factory.enableTickSpacing(1, 500000); // Enables a tick spacing of 1 with a 0.5% fee

// Later, in pool creation
factory.createPool(tokenA, tokenB, 1, initialSqrtPrice);

// Now, an attacker could initialize a large number of ticks in this pool
for (int24 tick = -887272; tick < 887272; tick++) {
    pool.initialize(tick);
}
```

This would create a pool with an enormous number of initialized ticks, making it extremely gas-intensive to perform operations that cross tick boundaries.

## Fix

To fix this issue, we should implement a minimum tick spacing value. Here's a suggested fix:

```solidity
// Add this constant to the contract
int24 private constant MIN_TICK_SPACING = 10; // Or another appropriate minimum value

function enableTickSpacing(int24 tickSpacing, uint24 initialFee) external override restricted {
    require(initialFee < 1_000_000, FTL());
    require(tickSpacing >= MIN_TICK_SPACING && tickSpacing < 16384, 'Invalid TS');
    require(tickSpacingInitialFee[tickSpacing] == 0, 'TS!0');

    tickSpacingInitialFee[tickSpacing] = initialFee;
    emit TickSpacingEnabled(tickSpacing, initialFee);
}
```

This change ensures that the tick spacing cannot be set to a value smaller than `MIN_TICK_SPACING`.

To further illustrate the importance of this fix, let's consider the impact on the `swap` function in the `RamsesV3Pool` contract:

```solidity
while (state.amountSpecifiedRemaining != 0 && state.sqrtPriceX96 != sqrtPriceLimitX96) {
    StepComputations memory step;

    step.sqrtPriceStartX96 = state.sqrtPriceX96;

    (step.tickNext, step.initialized) = $.tickBitmap.nextInitializedTickWithinOneWord(
        state.tick,
        tickSpacing,
        zeroForOne
    );

    // ... rest of the swap logic
}
```

With a very small tick spacing, this loop could potentially iterate many more times than intended, consuming excessive gas and possibly hitting the block gas limit, effectively breaking the swap functionality for large trades.
