# Vulnerability details

`cachePeriodEarned` function in the GaugeV3.sol contract contains a bug in the caching logic that can lead to incorrect reward calculations for users. The issue lies in the condition `period < _blockTimestamp() / WEEK && caching`, which determines whether to cache the `periodSecondsInsideX96` value in the `periodNfpSecondsX96` mapping.

When the `period` parameter is greater than or equal to the current block timestamp divided by `WEEK`, and `caching` is set to `true`. In this scenario, the `periodSecondsInsideX96` value is not cached, resulting in a mismatch between the calculated reward and the cached reward value.

As a result, when users call functions like `getReward` that rely on `cachePeriodEarned` for reward calculations, they may receive incorrect reward amounts.

## Impact
When a user calls the `getReward` function or any other function that relies on the `cachePeriodEarned` function to calculate rewards, they may receive incorrect reward amounts.

        if (!periodAmountsWritten[period][_positionHash]) {
            (bool success, bytes memory data) = address(pool).staticcall(

                    IRamsesV3PoolState.positionPeriodSecondsInRange,
                    (period, owner, index, tickLower, tickUpper)

            if (!success) {
                return 0;
            }

            (periodSecondsInsideX96) = abi.decode(data, (uint256));

            // @audit The caching logic is incorrect, leading to a mismatch between the calculated reward and the cached reward value
            if (period < _blockTimestamp() / WEEK && caching) {
                periodAmountsWritten[period][_positionHash] = true;
                periodNfpSecondsX96[period][
                    _positionHash
                ] = periodSecondsInsideX96;
            }
        } else {
            periodSecondsInsideX96 = periodNfpSecondsX96[period][_positionHash];
        }

        amount = FullMath.mulDiv(
            tokenTotalSupplyByPeriod[period][token],
            periodSecondsInsideX96,
            WEEK << 96
        );

        uint256 claimed = periodClaimedAmount[period][_positionHash][token];
        if (amount >= claimed) {
            amount -= claimed;
        } else {
            amount = 0;
        }

        return amount;

**Reproduction Steps**

1. Call `cachePeriodEarned` with a `period` value that is greater than or equal to the current block timestamp divided by `WEEK`, and set `caching` to `true`.
2. Ensure that `periodAmountsWritten[period][_positionHash]` is `false`.
3. The `periodSecondsInsideX96` value will not be cached, resulting in a mismatch between the calculated reward and the cached reward value.

**Consider the following scenario**

1. The current block timestamp is 1000000, and WEEK is defined as 604800 (7 days in seconds).
2. A user calls the `getReward` function, which internally calls `cachePeriodEarned` with the following parameters:

   * `period`: 2 (representing a period in the past)
   * `token`: 0x1234567890123456789012345678901234567890 (a reward token address)
   * `owner`: 0xabcdef0123456789abcdef0123456789abcdef01 (the user's address)
   * `index`: 1 (the position index)
   * `tickLower`: -100 (the lower tick of the position)
   * `tickUpper`: 100 (the upper tick of the position)
   * `caching`: true (indicating that caching should be performed)

3. Inside `cachePeriodEarned`, the condition `period < _blockTimestamp() / WEEK && caching` evaluates to `false` because `2 < 1000000 / 604800` is `false`.
4. Consequently, the `periodSecondsInsideX96` value is not cached in the `periodNfpSecondsX96` mapping.
5. The function calculates the reward amount based on the uncached `periodSecondsInsideX96` value, which may be incorrect or outdated.
6. The user receives an incorrect reward amount due to the mismatch between the calculated reward and the cached reward value.

## Recommended Mitigation Steps
Update the caching logic in the `cachePeriodEarned` function to ensure that the `periodSecondsInsideX96` value is always cached when `caching` is set to `true`, regardless of the `period` value. Removing the condition `period < _blockTimestamp() / WEEK`, the `periodSecondsInsideX96` value will be cached whenever `caching` is `true`, ensuring consistency between the calculated reward and the cached reward value.
```diff
if (!periodAmountsWritten[period][_positionHash]) {
    // ...

-   if (period < _blockTimestamp() / WEEK && caching) {
+   if (caching) {
        periodAmountsWritten[period][_positionHash] = true;
        periodNfpSecondsX96[period][_positionHash] = periodSecondsInsideX96;
    }
} else {
    periodSecondsInsideX96 = periodNfpSecondsX96[period][_positionHash];
}
```
