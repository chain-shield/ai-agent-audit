# Vulnerability details

### Proof of Concept

Protocol will be deploying on chains based on zero knowledge EVM (Scroll) as well as other EVM compatible chains in the future (potentially zksync) according to the informaton provided in the readme. However, a large number of pool operations rely on the `computeAddress` function in PoolAddress.sol library.


```solidity
function computeAddress(address deployer, PoolKey memory key) internal pure returns (address pool) {
        require(key.token0 < key.token1, TokenOrder());
        pool = address(
            uint160(
                uint256(
                    keccak256(
                        abi.encodePacked(
                            hex'ff',
                            deployer,
                            keccak256(abi.encodePacked(key.token0, key.token1, key.tickSpacing)),
                            POOL_INIT_CODE_HASH
                        )
                    )
                )
            )
        );
    }
```
ZKEVMs utilizes a different prefix than most other EVM based chains. Instead of using "ff" it uses zksynceCreate2. This causes `computeAddress` to return incorrect pool addresses. Due to this the protocol will be broken when deployed there. Functions like [`getReward`](https://github.com/code-423n4/2024-10-ramses-exchange/blob/236e9e9e0cf452828ab82620b6c36c1e6c7bb441/contracts/CL/periphery/NonfungiblePositionManager.sol#L425), [`decreaseLiquidity`](https://github.com/code-423n4/2024-10-ramses-exchange/blob/236e9e9e0cf452828ab82620b6c36c1e6c7bb441/contracts/CL/periphery/NonfungiblePositionManager.sol#L281) and [`collect`](https://github.com/code-423n4/2024-10-ramses-exchange/blob/236e9e9e0cf452828ab82620b6c36c1e6c7bb441/contracts/CL/periphery/NonfungiblePositionManager.sol#L338) will be inaccessible which will lead to loss of funds as positions can be minted and lqiudity increased.

### Recommended Mitigation Steps

As zkEVMs differs in some points from the EVM, i would consider writing a slightly adjusted version of the contract for zkEVM.
