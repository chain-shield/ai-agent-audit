# Vulnerability details

## Description

The NonfungiblePositionManager contract manages liquidity positions as NFTs and handles fee collection for liquidity providers. The fee calculation relies on tracking fee growth values for each position.

The issue is in the decreaseLiquidity function. When liquidity is decreased, the fee growth calculation doesn't account for the reduced liquidity, potentially leading to an overestimation of fees owed.

The fee calculation uses the full position liquidity (positionLiquidity) instead of the remaining liquidity after the decrease. This can result in overpayment of fees when a user partially removes liquidity.

## Code Snippet

```solidity
function decreaseLiquidity(
    DecreaseLiquidityParams calldata params
)
    external
    payable
    override
    isAuthorizedForToken(params.tokenId)
    checkDeadline(params.deadline)
    returns (uint256 amount0, uint256 amount1)
{
    require(params.liquidity > 0);
    Position storage position = _positions[params.tokenId];

    uint128 positionLiquidity = position.liquidity;
    require(positionLiquidity >= params.liquidity);

    // ... (pool interaction code)

    unchecked {
        position.tokensOwed0 +=
            uint128(amount0) +
            uint128(
                FullMath.mulDiv(
                    feeGrowthInside0LastX128 - position.feeGrowthInside0LastX128,
                    positionLiquidity,  // Bug is here
                    FixedPoint128.Q128
                )
            );
        position.tokensOwed1 +=
            uint128(amount1) +
            uint128(
                FullMath.mulDiv(
                    feeGrowthInside1LastX128 - position.feeGrowthInside1LastX128,
                    positionLiquidity,  // And here
                    FixedPoint128.Q128
                )
            );
    }

    // ... (rest of the function)
}
```

When calculating `tokensOwed0` and `tokensOwed1`, the function uses `positionLiquidity`, which represents the full liquidity of the position before the decrease. This is incorrect for partial liquidity removals.

When a user decreases liquidity, they're essentially splitting their position into two parts: the part they're removing and the part that remains. The fees earned up to this point should be proportionally split between these two parts.

The `amount0` and `amount1` variables represent the tokens returned from the removed liquidity, including any fees earned by that portion.

The additional fee calculation (using `FullMath.mulDiv`) should only apply to the remaining liquidity, as it represents the fees that will continue to accrue on the position going forward.

## Impact

- Overestimation of Fees: By using the full `positionLiquidity` instead of the remaining liquidity, the contract calculates fees as if the user still had their full position, even after removing some liquidity.
- Unfair Distribution: Users who partially decrease their liquidity will receive more fees than they're entitled to, at the expense of other liquidity providers.
- Compound Error: If a user makes multiple partial decreases, the error will compound, potentially leading to significant discrepancies over time.

## Fix

The fee calculation should be based on the remaining liquidity after the decrease. Here's how it should work:

```solidity
uint128 remainingLiquidity = positionLiquidity - params.liquidity;

unchecked {
    position.tokensOwed0 +=
        uint128(amount0) +
        uint128(
            FullMath.mulDiv(
                feeGrowthInside0LastX128 - position.feeGrowthInside0LastX128,
                remainingLiquidity,  // Use remaining liquidity here
                FixedPoint128.Q128
            )
        );
    position.tokensOwed1 +=
        uint128(amount1) +
        uint128(
            FullMath.mulDiv(
                feeGrowthInside1LastX128 - position.feeGrowthInside1LastX128,
                remainingLiquidity,  // And here
                FixedPoint128.Q128
            )
        );
}
```
