Excessive Fee Rate Allows Complete Denial of Service to Traders
ChainSentry
00
Sufficient
383d ago
Finding description and impact

The contract owner can set the trading fee rate (feeRate) to 100%, causing all user inputs in trades (buying or selling) to be captured entirely as fees. This effectively nullifies any return to the user and turns the exchange into a black hole, discouraging or outright blocking normal usage of the protocol. In short, a malicious or compromised owner can at will halt all trading by making trades yield zero outputs, amounting to a Denial of Service (DoS).

Impact:

Denial of Service: By imposing a 100% fee, the protocol effectively stops functioning as a viable exchange since no user can make profitable trades.
Centralization Risk: A malicious owner (or a compromised owner key) can unilaterally halt trading, undermining trust and damaging the protocol’s reputation.
User Loss of Funds: Unsuspecting users may attempt trades and end up losing their entire input to fees.
Proof of Concept

Location and Cause:
Within LamboVEthRouter.sol, the feeRate can be updated by the owner with updateFeeRate(uint256 newFeeRate). This parameter can be set equal to feeDenominator (which is 10000), representing a 100% fee. The fee calculation involves deducting (amountIn * feeRate) / feeDenominator from the user’s input. At a 100% fee, (amountIn * 10000)/10000 = amountIn, leaving nothing to swap into the desired token.

Key Math Detail:
For a given trade input amountIn:

Fee = amountIn * feeRate / feeDenominator.
With feeRate = feeDenominator = 10000, Fee = amountIn.
Effective amount for swap = amountIn - Fee = amountIn - amountIn = 0.

Thus, no tokens are returned to the user, making trades pointless and achieving a de facto DoS.

Proof of Code (PoC Test):
Below is an example Foundry test code snippet demonstrating how setting feeRate = 100% results in user funds being fully captured by fees and no tokens returned. This serves as a direct proof of the vulnerability:


    function testOwnerCanSetFeeTo100PercentAndCauseDOS() public {
        vm.startPrank(multiSigAdmin);
        router.updateFeeRate(10000); // 100% fee
        vm.stopPrank();

        vm.startPrank(user);
        uint256 initialUserBalance = user.balance;

        // Attempting to buy with 1 ETH
        // 100% fee means user effectively receives 0 tokens back.
        // All 1 ETH will be taken as fees.
        (bool success,) = address(router).call{value: 1 ether}(
            abi.encodeWithSignature("buyQuote(address,uint256,uint256)", address(0xDEAD), 1 ether, 0)
        );

        assertTrue(success, "Call should not revert");
        uint256 finalUserBalance = user.balance;
        uint256 userSpent = initialUserBalance - finalUserBalance;

        // User lost the entire 1 ETH input to fees, receiving nothing in return.
        assertEq(userSpent, 1 ether, "User got completely drained by fees");
    }
}

##Tools used

Foundry and Manual review

Recommended mitigation steps

Implement a Maximum Fee Cap:
Enforce a significantly lower maximum fee ceiling (e.g., no more than 5%) to prevent a 100% siphoning of user funds.

Introduce Governance Constraints:

Use time-locks or multi-sig approvals for fee changes.
Require a delay between fee updates, giving users time to react and withdraw liquidity.
