Lack of Flexibility in VirtualToken Contract for Supporting ETH and ERC20 Tokens
Coldless
00
Sufficient
383d ago
Finding description and impact

The VirtualToken contract is designed to handle ETH and specific ERC20 tokens based on an immutable underlyingToken variable. However, the current design introduces a significant limitation: the contract is unable to dynamically handle both ETH and multiple ERC20 tokens (e.g., USDC and USDT) in a single instance. The affected functions (cashIn, _transferAssetFromUser, and _transferAssetToUser) use conditional logic to handle ETH or ERC20 transfers, but the lack of flexibility creates a rigid structure that requires separate contract instances for each token.

This design flaw has multiple impacts:

Limited Scalability
The protocol must deploy a new VirtualToken instance for each supported token, increasing deployment costs and administrative overhead.
This hinders the ability to adapt quickly to new tokens or integrate new features.
Operational Complexity
Users and developers must interact with multiple contract instances, creating a fragmented user experience.
This increases the likelihood of user errors, such as interacting with the wrong instance for a specific token.
High Maintenance Overhead
Adding support for additional tokens (e.g., USDC and USDT) requires deploying and managing separate instances, complicating the protocol's governance and maintenance.

Without a flexible mechanism to handle both ETH and multiple ERC20 tokens dynamically, the contract's usability and scalability are significantly compromised.

Proof of Concept

The design flaw can be observed in one of the aforementioned three functions, cashIn():

https://github.com/code-423n4/2024-12-lambowin/blob/main/src/VirtualToken.sol#L73-L77

        if (underlyingToken == LaunchPadUtils.NATIVE_TOKEN) {
            require(msg.value == amount, "Invalid ETH amount");
        } else {
            _transferAssetFromUser(amount);
        }
The function uses the immutable underlyingToken to determine whether the token is ETH (LaunchPadUtils.NATIVE_TOKEN) or an ERC20 token.
If underlyingToken is set to an ERC20 token like USDC, any attempt to use the contract with ETH or another ERC20 token (e.g., USDT) will revert due to the conditional logic that further triggers _transferAssetFromUser:

https://github.com/code-423n4/2024-12-lambowin/blob/main/src/VirtualToken.sol#L124-L130

    function _transferAssetFromUser(uint256 amount) internal {
        if (underlyingToken == LaunchPadUtils.NATIVE_TOKEN) {
            require(msg.value >= amount, "Invalid ETH amount");
        } else {
            IERC20(underlyingToken).safeTransferFrom(msg.sender, address(this), amount);
        }
    }

Example Scenario:

Deploy a VirtualToken instance with underlyingToken = USDC.
Attempt to deposit ETH or USDT using the cashIn function:
The function will fail, as it only accepts USDC for this instance when IERC20(underlyingToken).safeTransferFrom is executed.
Deploy another VirtualToken instance for USDT:
Any attempt to interact with the USDT instance using USDC or ETH will similarly fail.
Deploy another VirtualToken instance for NATIVE_TOKEN:
Any attempt to interact with the NATIVE_TOKEN instance using USDC or USDT will also fail because the else clause will be skipped.

This rigid structure demonstrates the contract's inability to handle multiple tokens or ETH dynamically, requiring separate deployments for each new token.

Recommended mitigation steps

To resolve this issue and improve the contract's scalability, the following steps are recommended:

replacing the immutable underlyingToken with a dynamic parameter that can accept any token address, including address(0) for ETH.
modifying cashIn, _transferAssetFromUser, and _transferAssetToUser functions to handle ETH and ERC20 tokens based on the provided token address.

Here's one of the example code refactoring:

function cashIn(address token, uint256 amount) public payable onlyWhiteListed {
    if (token == address(0)) {
        // Handle ETH
        require(msg.value == amount, "Incorrect ETH amount sent");
    } else {
        // Handle ERC20
        require(msg.value == 0, "ERC20 does not accept ETH");
        IERC20(token).transferFrom(msg.sender, address(this), amount);
    }
}
