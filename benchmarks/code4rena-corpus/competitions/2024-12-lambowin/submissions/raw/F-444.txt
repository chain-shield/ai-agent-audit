S-756
If underlying token is not NATIVE_TOKEN and ETH is sent to VirtualToken.sol, it will be locked
hubble
00
Sufficient
383d ago
Finding description

In VirtualToken.sol, the function cashIn is payable. In the case where the underlying token is not LaunchPadUtils.NATIVE_TOKEN,
and by user mistake, when using the functions createLaunchPadAndInitialBuy or buyQuote, which are payable and ETH is sent along with the transaction,
the protocol does not give any error, and transaction succeeds.

Its expected that this corner case is handled properly in the protocol and loss to user is avoided.

Impact

The ETH sent along with the transactions in the above situation is locked and cannot be recovered.
Since this is user initiated mistake, filing this issue as Medium instead of High.

Proof of Concept

As POC, add the below test case VirtualTokenBug.t.sol and run forge test --match-path test/VirtualTokenBug.t.sol
Additionally add the missing code as given in recommendation of the high priority issue filed titled "If underlying token is not NATIVE_TOKEN, the createLaunchPadAndInitialBuy() function is broken", before running the test.

Recommended mitigation steps

The above corner case scenario can be avoided by adding a check, require(msg.value == 0) , in else part as below in VirtualToken.sol

    function cashIn(uint256 amount) external payable onlyWhiteListed {
        if (underlyingToken == LaunchPadUtils.NATIVE_TOKEN) {
            require(msg.value == amount, "Invalid ETH amount");
        } else {
            require(msg.value == 0);
            _transferAssetFromUser(amount);
        }
