# Vulnerability details

## Impact
when calling `function transferToUnoccupiedPlot(uint256 tokenId, uint256 plotId)` the `toilerState[tokenId].plotId` is not set to the new `plotId`.
This means that when unstaking with `function unstakeMunchable(uint256 tokenId)`, the new plot to which the stake was transferred is not erased.
The impact is that when a stake is transferred to an occupied plot, it is set permanently and cannot be erased even if the user un-stakes.

## Proof of Concept

consider the following, there are two unoccupiedPlots, `uint256 plotId1` and `uint256 plotId2`,
user Bob wants to stake the token `uint256 tokenId` to `address landlord` at `plotId1`.

after staking
```solidity
plotOccupied[landlord][plotId1] = Plot({
            occupied: true,
            tokenId: tokenId
        });
```

while 
```solidity
plotOccupied[landlord][plotId2] = Plot({
            occupied: false,
            tokenId: 0
        });
```

user bob then calls `function transferToUnoccupiedPlot(uint256 tokenId, uint256 plotId)`, with `plotId2` as the second argument
at the end of the call

```solidity
plotOccupied[landlord][plotId1]` = Plot({
            occupied: false,
            tokenId: 0
        });
```

while 
```solidity
plotOccupied[landlord][plotId2]` = Plot({
            occupied: true,
            tokenId: tokenId
        });
```

when user Bob then un-stakes the token, since the `plotOccupied` was not updated when `function transferToUnoccupiedPlot` was called, the storage remains the same, and `plotOccupied[landlord][plotId2]` is permanently occupied.

## Tools Used
Manual Audit

## Recommended Mitigation Steps
in `transferToUnoccupiedPlot(uint256 tokenId, uint256 plotId)`  set the `poolId` in the `toilerState` with

```solidity
toilerState[tokenId].plotId = poolId;
```
