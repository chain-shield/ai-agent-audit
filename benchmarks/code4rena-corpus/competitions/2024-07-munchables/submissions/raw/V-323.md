# Vulnerability details

Taxes are calculated and distributed for a player's stakes using `_farmPlots(address player)` funtion, which is only reachable through `stakeMunchable`, `unstakeMunchable`, `transferToUnoccupiedPlot` and `farmPlots`. Each of these pass `msg.sender` as the player's address. 

This makes it impossible for a landlord to manually trigger reward distribution incase a staker becomes inactive or doesn't perform a required action.

## Impact
The issue negatively affects rewards in 2 ways, in both of which the staker's inaction punishes the landlord also, which had no responsibility for the staker:
### If staker not interacting with LandManager
In this case `_farmPlots` will not get called and no rewards will be distributed for this staker's plots, and the plot remains occupied.

### If staker not transferring/unstaking stake from an `dirty` plot
If an user stakes on a plot that becomes dirty due to change in landlord's locked assets value (due to price changes, or unlocking), that plot will no longer contribute to taxes (or player rewards) after a single time after becoming dirty.

Due to a future change in locked assets value, that plot may become available again, but since the `dirty` bit is set, it doesn't generate rewards anymore until the staker specifically transfers or unstakes from that `plotId`, which resets `dirty` to false.

This behavior can happen quite often if locked asset's prices are not stable.

## Proof of Concept
### Valid plot becoming dirty due to temporary change in locked value
Due to incorrect check for valid plot in `_farmPlots#258` this issue needs `_getNumPlots` to temporarily change by atleast 2 plots in either direction. If the check was correct, a change of 1 would have been enough.
```solidity
function test_dirtyOnChange() external {
    lockManager.mockPlayerWeightedValue(LANDLORD, PRICE_PER_PLOT * 5); // The landlord starts with 5 plots

    vm.prank(STAKER);
    landManager.stakeMunchable(LANDLORD, 0, 4); // Staker stakes on plot 4

    lockManager.mockPlayerWeightedValue(LANDLORD, PRICE_PER_PLOT * 3); // num plots decrease to 3

    vm.prank(STAKER);
    landManager.farmPlots();
    assertEq(landManager.getToilerState(0).dirty, true);

    // Now after the locked assets increase back to 5 plots, the toiler state is still dirty and occupied
    // preventing both reward generation and new staking on plot 4
    lockManager.mockPlayerWeightedValue(LANDLORD, PRICE_PER_PLOT * 5);
    assertEq(landManager.getToilerState(0).dirty, true);
    assertEq(landManager.getPlotOccupied(LANDLORD, 4).occupied, true);
}
```

## Tools Used
Manual Review, Foundry

## Recommended Mitigation Steps
A combination of these can be used to remedy this issue. The focus should be that a landlord does not get wrongly punished due to a staker's actions (or lack thereof).
- Allow landlords to evict stakers from their plots.
- Let anyone call `_farmPlots` for any player address. 
- If on a future `_farmPlots` call by staker, a dirty `plotId` staked on becomes valid, then reset the dirty bit.
