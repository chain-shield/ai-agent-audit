# Vulnerability details

## Overview
The landlord charges a tax amount from the MUnchables stakers of their schnibbles reward. This tax amount is based on the tax rate that is, first attached to the toiler state when it is staked, and, updated every time the staker farms plots or transfers the Munchable to a different plot of the same landlord.

However, when the landlord updates his tax rate using the ```updateTaxRate(uint256 newTaxRate)``` function, he would not have it reflected in the current states of the Munchables plot on his plots. This may result in a loss of value for the landowner.

## Proof of Concept
Below is a step-by-step PoC explaining the issue in detail.

To start with, let us suppose:

```
MIN_TAX_RATE = 20%
MAX_TAX_RATE = 75%
```

Suppose, on day 1, a user X stakes a Munchable (for ease of reference, assume tokenId = 55) on plot 9 of a landlord Y using the ```stakeMunchable(address landlord, uint256 tokenId, uint256 plotId)```:

https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L131

```solidity
    function stakeMunchable(
        address landlord,
        uint256 tokenId,
        uint256 plotId
    ) external override forceFarmPlots(msg.sender) notPaused {
        (address mainAccount, ) = _getMainAccountRequireRegistered(msg.sender);
        if (landlord == mainAccount) revert CantStakeToSelfError();
        if (plotOccupied[landlord][plotId].occupied)
            revert OccupiedPlotError(landlord, plotId);
        if (munchablesStaked[mainAccount].length > 10)
            revert TooManyStakedMunchiesError();
        if (munchNFT.ownerOf(tokenId) != mainAccount)
            revert InvalidOwnerError();

        uint256 totalPlotsAvail = _getNumPlots(landlord);
        if (plotId >= totalPlotsAvail) revert PlotTooHighError();

        if (
            !munchNFT.isApprovedForAll(mainAccount, address(this)) &&
            munchNFT.getApproved(tokenId) != address(this)
        ) revert NotApprovedError();
        munchNFT.transferFrom(mainAccount, address(this), tokenId);

        plotOccupied[landlord][plotId] = Plot({
            occupied: true,
            tokenId: tokenId
        });

        munchablesStaked[mainAccount].push(tokenId);
        munchableOwner[tokenId] = mainAccount;

        toilerState[tokenId] = ToilerState({
            lastToilDate: block.timestamp,
            plotId: plotId,
            landlord: landlord,
            latestTaxRate: plotMetadata[landlord].currentTaxRate,
            dirty: false
        });

        emit FarmPlotTaken(toilerState[tokenId], tokenId);
    }
```

The ```plotMetadata[landlord].currentTaxRate``` was 25% on day 1, that is, at the time of stake.

Now, on day 5, the landlord updates his tax rate to 70% using ```updateTaxRate(uint256 newTaxRate)``` function:

https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L92

```solidity
    function updateTaxRate(uint256 newTaxRate) external override notPaused {
        (address landlord, ) = _getMainAccountRequireRegistered(msg.sender);
        if (newTaxRate < MIN_TAX_RATE || newTaxRate > MAX_TAX_RATE)
            revert InvalidTaxRateError();
        if (plotMetadata[landlord].lastUpdated == 0)
            revert PlotMetadataNotUpdatedError();
        uint256 oldTaxRate = plotMetadata[landlord].currentTaxRate;
        plotMetadata[landlord].currentTaxRate = newTaxRate;
        emit TaxRateChanged(landlord, oldTaxRate, newTaxRate);
    }
``` 

Please notice that for tokenId = 55, we still have:

```
toilerState[55].latestTaxRate = 25e6 (or 25%)
```

Now, on day 60, X farms the plot using:

https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L228

```solidity
    function farmPlots() external override notPaused {
        _farmPlots(msg.sender);
    }
```

X would have to pay a tax of just 25% and not 70% as seen in:

https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L288

```solidity
                (schnibblesTotal * _toiler.latestTaxRate)
```

since ```_toiler.latestTaxRate``` would be ```25e6``` (or 25%). 

This would be a loss for the landlord as, after he updated his tax to 70%, all farming should pay him 70% tax from then onwards. However, he would lose 45% tax ( = 70 - 25) on 55 days worth of reward (day 60 - day 5) when X would farm token 55. 

One more impact that comes out of this issue is that: Suppose a landlord submits a transaction to increase his tax from 25% to 70%. A staker sees this and front runs the landlord's transaction to get one of his plots at just 25% tax. The landlord, unaware of this, would lose on the tax amount he would be entitled to.

On the other side, a staker would lose on tax benefits if the landlord decreases the tax (suppose, in the above example, on day 5 the landlord decreased the tax rate to 20%; the staker would still pay 25% tax upon farming on day 60).

## Severity
Impact: The landlord would lose value. He would lose the tax that he should get. This becomes more serious if a staker from runs the landlord (as stated above). The staker could also lose value if the tax rate is decreased. So, the impact seems High.

Likelihood: A landlord would frequently update tax rates, to increase the demand for his plots according to the market, so the likelihood seems High.

Therefore, the severity seems High.

## Recommended Mitigation Steps
Loop over all the plots of the landlord and call ```_farmPlots(address _sender)``` if the plot is occupied:

In ```updateTaxRate(uint256 newTaxRate)```:

```diff
    function updateTaxRate(uint256 newTaxRate) external override notPaused {
        (address landlord, ) = _getMainAccountRequireRegistered(msg.sender);
        if (newTaxRate < MIN_TAX_RATE || newTaxRate > MAX_TAX_RATE)
            revert InvalidTaxRateError();
        if (plotMetadata[landlord].lastUpdated == 0)
            revert PlotMetadataNotUpdatedError();
        uint256 oldTaxRate = plotMetadata[landlord].currentTaxRate;
        plotMetadata[landlord].currentTaxRate = newTaxRate;
+      for (uint256 i = 0; i < _getNumPlots(landlord); i++) {
+          {
+               if (plotOccupied[landlord][i].occupied) {
+                   tokenId = plotOccupied[landlord][i].tokenId;
+                   owner = munchableOwner[tokenId];
+                   _farmPlots(owner); 
+               }
+          }
        emit TaxRateChanged(landlord, oldTaxRate, newTaxRate);
    }
```

This could be more optimized by enabling the ```_farmPlots(address _owner)``` function to accept a variable ```address landlord```. So, in the above mitigation, instead of using:

```
_farmPlots(owner);
```

we could use:

```
_farmPlots(owner, landlord);
```

to save looping over other landlords of the owner. 

To save on gas consumption while inside the for loop, the total number of plots per landlord could be restricted to a certain value, let's say, 20. This can be done by the following changes in ```_getNumPlots(address _account)``` function:

```diff
    function _getNumPlots(address _account) internal view returns (uint256) {
-       return lockManager.getLockedWeightedValue(_account) / PRICE_PER_PLOT;
+      uint256 plots = lockManager.getLockedWeightedValue(_account) / PRICE_PER_PLOT;
+      if (plots > 20) {
+          return 20;
+      }
+      else {
+          return plots;
+      }
    }
```

Considering the protocol is to be deployed on a Layer-2 (Blast, as per the Readme), the mitigation should cost sustainable gas expenditure for the landlords.
