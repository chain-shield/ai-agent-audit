# Vulnerability details

## Impact
Users can be DOS from using staking or unstaking all of their NFTs.

## Proof of Concept
1. [_farmPlots](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L232) is triggered in all of the main functions - [transferToUnoccupiedPlot](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L202), [unstakeMunchable](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L175) and [stakeMunchable](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L135). If that function reverts those will revert too.

2. If a user triggers [_farmPlots](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L258-L261) and his `plotId` is bigger than the available plots, his `timestamp` (for reward math) will get set to `plotMetadata[landlord].lastUpdated`.

```solidity
   if (_getNumPlots(landlord) < _toiler.plotId) {
       timestamp = plotMetadata[landlord].lastUpdated;
       toilerState[tokenId].dirty = true;
   }

   ...

   //@audit but what if _toiler.lastToilDate > timestamp ? 
   schnibblesTotal = (timestamp - _toiler.lastToilDate) * BASE_SCHNIBBLE_RATE;
```

3. [_getNumPlots](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L344-L346) calculates the available plots using - `weight / price` formula, where the weight is calculated inside [getLockedWeightedValue](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LockManager.sol#L481-L491) to be - `quantity * price / 1e18`.
- `quantity` is the amount of tokens the landlord deposits.
- `price` is a custom price variable that is updated by oracles.


---


With the above 3 an issue can appear, where `_toiler.lastToilDate` is bigger than `timestamp`, leading to an underflow and a revert. This will cause a completed DOS for every user that has a plot, considered as dirty. This can happen with price updates, lowering the landlord's weight, causing his plots to decrease.

Example:
1. Landlord has 500 tokens, valued at 1 each, with 100 for a single plot - 5 plots total
2. User1 stakes 1 of his 10 NFTs to this landlord's last plot.
3. Oracles update the price with [proposeUSDPrice](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LockManager.sol#L142) from 1 to 0.995 (0.5% decrease), causing the landlord's weight to decrease to 497,5, marking his last plot as dirty.
4. Our user tries to unstake to be no longer on a `dirty` plot, however the TX fails as `_toiler.lastToilDate > plotMetadata[landlord].lastUpdated`, causing [timestamp - _toiler.lastToilDate](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L281) to underflow.
5. His 9 other NFTs are also stuck as [_farmPlots](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L232) harvest for all 10 of them at the same time.

Now there are 2 solutions for this DOS to stop
1. The landlord update his metadata with [updatePlotMetadata](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L116-L129), by locking some tokens - not user dependent, he can do it if he wants to.
2. There is a bug, described in another of my issues, where the user can lock for the landlord and update his metadata - the user relaying on a bug/another procedure to unlock his tokens.

Notice how the only solutions to this DOS are a bug/another procedure and for the user to wait on other entities.

## Tools Used
Manual review

## Recommended Mitigation Steps
With the current implementation I am unaware of how this can be fixed. My suggestion is to redo the reward math and think of other ways to lower rewards for dirty plots.
