# Vulnerability details

In [`LandManager::_farmPlots`](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L228-L230), a conditional statement [checks](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L258-L261) if the saved `plotId` in a `ToilerState` exceeds the number of currently available plots. If `_toiler.plotId` is greater than the available plots, it means the plot is no longer valid because the landlord has unlocked tokens, reducing the number of allocated plots. As a result, the local timestamp variable is set to `plotMetadata[landlord].lastUpdated`, which is expected to reflect the `block.timestamp` at the time of the token unlock. This allows the staker to receive [schnibbles](https://munchables.gitbook.io/munchables/explorers-guide/glossary/schnibbles) for the period during which the plot was still valid.

However, this assumption doesn’t always hold true, as any further lock/unlock activity after the initial unlock would also update `plotMetadata[landlord].lastUpdated`, leading to inaccurate calculation of the valid staking period for that now-invalid `plotId` and as a consequence the schnibbles that are to be distributed.

## Impact

Relying solely on `plotMetadata[landlord].lastUpdated` to determine the valid staking period for a now-invalid `plotId` can lead to inaccuracies in schnibbles distribution. This is because it assumes `plotMetadata[landlord].lastUpdated` points to the initial unlock time, when that `plotId` become invalid, however it actually reflects the `block.timestamp` of the most recent lock/unlock action by the landlord.

## Recommended Mitigation Steps:

According to sponsor, invalid plots should still receive rewards for the valid staking time, which is also the reason why we are setting the local timestamp variable to `plotMetadata[landlord].lastUpdated` as it should properly point to the `block.timestamp` value of the initial unlock, when that `plotId` was invalidated, if that landlord hasn’t performed any other locking/unlocking operations.

However, a more appropriate implementation would be to discontinue schnibbles distribution for plots that are no longer active. This ensures that landlords have no incentive to unlock tokens and invalidate plots, as doing so would disqualify both the landlord and the staker from receiving rewards.

Allowing landlords to unlock tokens while remaining eligible for rewards on inactive plots undermines the incentive structure designed to keep tokens locked. Although this change would result in both the staker and the landlord losing rewards for invalid plots, it is unlikely that a landlord would intentionally invalidate a plot, given the shared distribution of schnibbles. Therefore, landlords should be fully aware that unlocking tokens will affect their eligibility for rewards on plots that are to become invalid.

Instead of relying on `plotMetadata[landlord].lastUpdated`, which may not accurately reflect the timestamp of plot invalidation if recent locking/unlocking operations have occurred, proceed with the following steps to address this issue:

1. Set the `dirty` flag to true for outdated `ToilerState` entries. This will ensure that these entries are skipped in subsequent calls to `LandManager::_farmPlots`.
2. Skip the current iteration of the loop for any `ToilerState` marked as dirty to prevent rewards from being distributed for invalid plots.

This approach ensures that outdated `ToilerState` entries are properly identified and excluded from reward calculations, so rewards are only distributed for valid plots.
