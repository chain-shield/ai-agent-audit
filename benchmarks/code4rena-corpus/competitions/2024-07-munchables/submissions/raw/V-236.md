# Vulnerability details

## Description
When a user's plot id is bigger than the max amount of plots a landlord stake can currently hold, farming at the plot will make the toiler state for a tokenId dirty, meaning the token from that point on will unrecoverably stop accruing rewards:
```solidity
function _farmPlots(address _sender) internal {
...
if (_getNumPlots(landlord) < _toiler.plotId) {
                timestamp = plotMetadata[landlord].lastUpdated;
                toilerState[tokenId].dirty = true;
            }
...
}
```

At the call in which the toiler state becomes dirty, the lastUpdated parameter is utilized as the latest timestamp to accrue the amount of schibbles to distribute:\
```solidity
schnibblesTotal =
                (timestamp - _toiler.lastToilDate) *
                BASE_SCHNIBBLE_RATE;
```

There are two ways a plotMetadata's lastUpdated parameter can get updated. The first one is the triggerPlotMetadata function, callable only by the plot owner.
The second one is the updatePlotMetadata function, callable by the AccountManager contract. This second function can be called by anyone by calling the lockOnBehalf function, at the LockManager contract. 

By locking some tokens to the land owner, a user is able to change lastUpdated to block.timestamp, here's the reason for that:
at the LockManager contract.
```solidity
function _lock(
...
accountManager.forceHarvest(_lockRecipient);
...
}
```

at the AccountManager contract.
```solidity
function forceHarvest(
        ...
        if (player.registrationDate != 0) {
            _harvest(_player);
            if (
                msg.sender == configStorage.getAddress(StorageKey.LockManager)
            ) {
                landManager.updatePlotMetadata(_player);
            }
        }
    }
```

Since locking tokens on behalf of someone updates the target's plot metadata, anyone can call this function to keep the lastUpdated value as close as possible to block.timestamp.

Now, if a user notices his toiler state is about to become dirty, he/she just has to lock a small amount of tokens on behalf of the landlord and get the most amount of schnibbles as possible. 
## Impact
Users who know about this specific sequence of actions may earn more rewards than the users who don't.
The rewards distribution mechanism unfairly distributes more rewards to users who know about the exploit.
## Tools Used
Manual review
## Recommended Mitigation Steps
Make sure farm actions update the plot's lastUpdated value to block.timestamp, as this diminishes the opportunity for users to earn different rewards for equal stake power.

Consider introducing timestamp-based epochs/periods to determine a toiler state's dirty status. This mechanism is interesting because it creates precise time cuts when certain sets of users ought to stop receiving rewards.
