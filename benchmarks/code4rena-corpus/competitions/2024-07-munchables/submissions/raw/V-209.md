# Vulnerability details

## Vulnerability details
accountManager::getPlayer() or _getMainAccountRequireRegistered() returns `mainAccount` & `player` struct for given address. Also player struct is stored in a mapping whose `key` is mainAccount, not the given address
```solidity
 function getPlayer(address _account)
        external
        view
        returns (address _mainAccount, MunchablesCommonLib.Player memory _player){

     @>   address _caller = _getMainAccount(_account);
     @>   _player = players[_caller];
          _mainAccount = _caller;
    }
```
Again, accountManager::updatePlayer() updates the players mapping by taking mainAccount as input
```solidity
 function updatePlayer(address _account, MunchablesCommonLib.Player calldata _player) external
    {
    @>  players[_account] = _player;
    }
```
Now the problem is in _farmPlots() while updating the player struct of landlord. For accessing landlord player struct, we calling _getMainAccountRequireRegistered(landlord) which returns player struct based on landlord's mainAccount.
```solidity
   (
     ,
     MunchablesCommonLib.Player memory landlordMetadata
   ) = _getMainAccountRequireRegistered(landlord);
```

But while updating player struct of landlord, instead of passing landlord's mainAccount in updatePlayer(), it directly pases landlord's address.
```solidity
     accountManager.updatePlayer(landlord, landlordMetadata);
```

This is problematic because for accessing player struct, we are using landlord's mainAccount but for updating we are using landlord address. Also landlord & his mainAccount can be different.


## Impact
Two player struct will be created for same user ie one with landlord address & one with landlord's mainAccount address
