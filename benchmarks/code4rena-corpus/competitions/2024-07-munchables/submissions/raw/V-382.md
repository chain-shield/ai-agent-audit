# Vulnerability details

## Impact
Staker will not be able to farm plots, stake more munchables, unstake existing munchables or transfer to unoccupied plots. This is due to a subtraction underflow [here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L281) when lastToilDate time is greater than timestamp. 

## Proof of Concept

Currently, we make the assumption in the codebase that lastUpdated would be updated every time a landlord locks or unlocks in LockManager.sol. This is because the functions in the LockManager.sol contract call the [forceHarvest()](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LockManager.sol#L420) function and ultimately the [updatePlotMetadata()](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/AccountManager.sol#L154) function. We are interested in the unlocking aspect. When a landlord unlocks and decreases the quantity locked, it decreases the locked weighted value and thus the total number of plots available. 

In this case, if any staker in LandManager.sol is staking on a plotId that does not fit anymore, it should stop earning rewards. This is achieved by the [if block here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L258C11-L261C14), which sets the `timestamp` memory variable to the lastUpdated metadata time i.e. the time the landlord made the unlock and decreased the quantity in LockManager.sol. Due to the way, the subtraction [here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L281) works, the `timestamp` (i.e. the time the landlord unlocked) would be greater than the `lastToilDate`.

The logic in the _farmPlots() function though does not consider two cases through which number of plots could also decrease:
1. A token being deactivated
2. The USD price of the token decreasing

When a token is deactivated, it's value is essentially removed from the function getLockedWeightedValue() [see here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LockManager.sol#L478) and thus decreases the number of plots. This is also true when the USD price of the token reported by the PRICE_FEED roles has decreased [here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LockManager.sol#L488C1-L489C41), which also decreases the number of plots. 

Now let's take an example to understand the impacts:

1. Assume a landlord had lastUpdated the metadata at time = 100.

2. Now let's say user A in LandManager.sol stakes on plotId 5 when total plots available = 6 at time = 200. Following this user A may or may not farm plots depending on whether they want to continue staking or just unstake once with all rewards.

3. Now let's say a token was deactivated or USD price of a token dropped, causing the locked weighted value to decrease and thus the total number of available plots. For this example, let's say plots decrease by 2.

4. Since user A staking on plotId 5 does not fit anymore due to range being [0,3] i.e. total plots available = 4, user A tries exiting the system by calling unstakeMunchable().

5. The modifier forceFarmPlots() calls the _farmPlots() function, where the following occurs:
 - [Line 258](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L258C11-L261C14) - We enter the if block, which sets the `timestamp` variable to `lastUpdated` = 100.

6. On Line 280 [here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L280C10-L282C37), when we try to subtract, it does `timestamp - lastToilDate` = 100 - 200, thus causing a revert.

Through this, we see that in the cases where a token is deactivated or USD price of a token has decreased, the locked weighted value decreases and thus the number of available plots. But unlike the unlock() action by the landlord in LockManager.sol, which updates the lastUpdated to the recent timestamp (that would be greater than the lastToilDate), these other two scenarios do not update the lastUpdated time, which causes the underflow.

## Recommended Mitigation Steps
Due to the complexity in the current LockManager and LandManager interactions, I am not able to provide a full-proof solution for this. 

One solution I thought of was to add another condition in the if condition [here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L258), which would check lastUpdated to be greater than lastToilDate. If it is not greater (i.e. the underflow would occur), it could add some logic in that if block to set the timestamp variable (to a value greater than lastToilDate) and set the dirty flag to true.
