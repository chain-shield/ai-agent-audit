# Vulnerability details

## Summary

**Context:**
In function _farmPlots(), we enter this [if block](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L258C12-L261C14) if the plotId does not fit in the available range anymore. The if block sets the timestamp to the last time the metadata was updated and sets the dirty flag to true. This is done to disallow munchables (staked on plotIds that do not fit in range anymore) from earning rewards. 

**Root cause:**
The issue is that the if condition uses < instead of <=. The available plotIds start from 0 upto the getNumPlots(landlord) - 1 as seen in stakeMunchable() [here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L145C7-L146C66). Since the _farmPlots() checks `_getNumPlots(landlord) < _toiler.plotId`, the user staking on _toiler.plotId = _getNumPlots(landlord) does not enter the if block and continues earning rewards. 

**Impact:**
The staker continues earning rewards on a plotId that does not fit anymore. This would be unfair to users staking on plotIds strictly greater than _getNumPlots(landlord) since they are forced to claim their rewards and unstake their munchables.

## Proof of Concept

1. Let's say total plots available = 6 (i.e. 0 to 5). Assume user A has been staking on plotId 5.

2. Now let's assume the total plots available decrease by 1 due to the landlord unlocking some locked weighted value from LockManager.sol. This makes the available plotId range to be [0,4]. 

3. Since user A is now staking on plotId 5, which is out of range, the user should not be earning anymore rewards.

4. When A calls farmPlots() though, we do not enter the if block below since the condition evaluates as 5 < 5 i.e. false. Due to this, the user A staking at plotId 5 continues earning rewards.

Use <= instead of <.
