# Vulnerability details

## Overview 
In the ```stakeMunchable(address landlord, uint256 tokenId, uint256 plotId)``` function, there is no check for ```plotMetadata[landlord].lastUpdated != 0```. This would lead to a staker use a landlord that does not exit.

## Proof of Concept
Below is a step-by-step PoC explaining the issue in detail.

Let us suppose a user X stakes one of his Munchables using:

https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L131

```solidity
    function stakeMunchable(
        address landlord,
        uint256 tokenId,
        uint256 plotId
    ) external override forceFarmPlots(msg.sender) notPaused {
        (address mainAccount, ) = _getMainAccountRequireRegistered(msg.sender);
        if (landlord == mainAccount) revert CantStakeToSelfError();
        if (plotOccupied[landlord][plotId].occupied)
            revert OccupiedPlotError(landlord, plotId);
        if (munchablesStaked[mainAccount].length > 10)
            revert TooManyStakedMunchiesError();
        if (munchNFT.ownerOf(tokenId) != mainAccount)
            revert InvalidOwnerError();

        uint256 totalPlotsAvail = _getNumPlots(landlord);
        if (plotId >= totalPlotsAvail) revert PlotTooHighError();

        if (
            !munchNFT.isApprovedForAll(mainAccount, address(this)) &&
            munchNFT.getApproved(tokenId) != address(this)
        ) revert NotApprovedError();
        munchNFT.transferFrom(mainAccount, address(this), tokenId);

        plotOccupied[landlord][plotId] = Plot({
            occupied: true,
            tokenId: tokenId
        });

        munchablesStaked[mainAccount].push(tokenId);
        munchableOwner[tokenId] = mainAccount;

        toilerState[tokenId] = ToilerState({
            lastToilDate: block.timestamp,
            plotId: plotId,
            landlord: landlord,
            latestTaxRate: plotMetadata[landlord].currentTaxRate,
            dirty: false
        });

        emit FarmPlotTaken(toilerState[tokenId], tokenId);
    }
```

Basically, X calls the ```stakeMunchable(address landlord, uint256 tokenId, uint256 plotId)``` function with the ```landlord``` as an address that has tokens in LockManager, but, is not a landowner, that is:

```solidity
plotMetadata[landlord].lastUpdated == 0
plotMetadata[landlord].currentTaxRate == 0
```

This is possible as there is no check, such as:

```solidity
        if (plotMetadata[landlord].lastUpdated == 0)
            revert LandlordDoesNotExistError();
```

in the ```stakeMunchable(address landlord, uint256 tokenId, uint256 plotId)``` function.

A user can have tokens in LockManager without being a landlord by:

1. Not updating his token balance on LockManager for sometime after the deployment of LandManager.
2. Not calling the ```triggerPlotMetadata()``` function:

https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L104

```solidity
    function triggerPlotMetadata() external override notPaused {
        (address mainAccount, ) = _getMainAccountRequireRegistered(msg.sender);
        if (plotMetadata[mainAccount].lastUpdated != 0)
            revert PlotMetadataTriggeredError();
        plotMetadata[mainAccount] = PlotMetadata({
            lastUpdated: block.timestamp,
            currentTaxRate: DEFAULT_TAX_RATE
        });

        emit UpdatePlotsMeta(mainAccount);
    }
```

The main point of concern is:

https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L166

```solidity
            latestTaxRate: plotMetadata[landlord].currentTaxRate,
```

The ```latestTaxRate``` of the toiler is set to ```plotMetadata[landlord].currentTaxRate``` which is 0.

This would let the staker earn schnibbles rewards by-passing any taxes:

https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L287

```solidity
            schnibblesLandlord =
                (schnibblesTotal * _toiler.latestTaxRate) /
                1e18;
```

## Severity
Impact: The protocol adds extra rewards to the malicious staker balance. The landlord might not even know about this; his address would be used by the malicious staker to by pass taxes. Therefore, the landlord would also not get the reward portion they are entitled to. Moreover, this is an invariant that must not be broken but stands so. Therefore, the impact seems to be High.

Likelihood: Since the staking mechanism is not access-controlled as well as there would be users who would have tokens in the LockManager without being a landlord, the likelihood seems High.

Therefore, the severity seems High.
