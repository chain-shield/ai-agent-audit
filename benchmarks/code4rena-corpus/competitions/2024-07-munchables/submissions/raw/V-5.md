# Vulnerability details

## Impact
There are cases in which users munchables can be stuck inside a plot for an undefined amount of time due to lack of precautions in `LandManager::_farmPlots`

## Proof of Concept
When a user tries to unstake their Munchables the modifier `forceFarmPlots` automatically calls `_farmPlots` in order to ensure the user gets all the rewards they are entitled to. Inside the function there is an edge case stated by the developers where a landlord has unlocked some of his funds and as a result owns less plots and and plot which the user is trying to farm doesn't exist anymore. In that situation the following changes are made.

```solidity
            if (_getNumPlots(landlord) < _toiler.plotId) {
@>              timestamp = plotMetadata[landlord].lastUpdated;
                toilerState[tokenId].dirty = true;
            }
```

The important part is that the timestamp is set to some time in the past (the last time the land owner updated their `currentTaxRate`). The issue lies in this calculation:

```solidity
...
            schnibblesTotal =
@>              (timestamp - _toiler.lastToilDate) *
                BASE_SCHNIBBLE_RATE;
...
```

There is no guarantee that `_toiler.lastToildDate` is smaller than `timestamp` quite the opposite it is very likely that is the case if the landlord has withdrawn funds and we are in the said situation. Because of that this would force a revert to happen as `schnibblesTotal` is of type uint256 and the compiler version is 0.8.25 which reverts on underflow. Because of that the whole transaction which tries to unstake the munchables will revert and the users will not be able to get their munchables back until the landlord updates their `currentTaxRate` making `timestamp > _toiler.lastToilDate` and allowing the transaction to continue

## Recommended Mitigation Steps

Find another way to handle the edge case where the landlord has withdrawn funds from their lock.
