# Vulnerability details

## Impact
The vulnerability lies in the `transferToUnoccupiedPlot` function which fails to update the `toilerState` correctly when a toiler (represented by a tokenId) moves from an old plot to a new plot. When the `toilerState` is updated after changing plots, the current implementation updates the `latestTaxRate` and adjusts the `plotOccupied` mappings, yet does not update the `toilerState[tokenId].plotId` to the new `plotId`. 

This causes a logical discrepancy where the toiler is visually in the new plot but their state still reflects the old plotId, leading to potential inconsistencies and issues with further interactions that depend on the correct `plotId`. This bug has a wide scale of impact on MANY things, to name a few:
1. Erroneous interactions by other functions that rely on accurate `plotId`. For example, the `toilerState[tokenId].dirty` can be totally messed up, because in the `_farmPlots` function there is a piece of logic to update this state variable relying on the `toilerState[tokenId].plotId`;
2. This discrepancy can also be exploited by sophisticated users to find loopholes in tax calculations exploiting the mismatch in staking visibility vs actual location in the contract's logic;
3. ...etc.

Therefore, it is absolutely a `High` severity bug.

## Proof of Concept
1. **Initial Setup:**
   - Assume a user `Alice` has a toiler with `tokenId=123` staked in `plotId=5` on a land owned by `landlordBob`. The `toilerState` for `tokenId=123` shows `plotId=5`.
   
2. **Triggering the Transfer:**
   - Alice decides to move her toiler `tokenId=123` from `plotId=5` to an unoccupied `plotId=10` within the same landlord space or another.
   - She executes `transferToUnoccupiedPlot(tokenId=123, plotId=10)`.

3. **Behind the Scenes:**
   - The function verifies that `plotId=10` is not occupied (`plotOccupied[_toiler.landlord][plotId].occupied == false`).
   - It proceeds to execute the transfer: it sets the old `plotOccupied[landlordBob][5]` to unoccupied and the new `plotOccupied[landlordBob][10]` to occupied by `tokenId=123`.
   - It updates `toilerState[tokenId=123].latestTaxRate` to the current tax rate for the new plot.
   - **However, it fails to update `toilerState[tokenId=123].plotId` to `10`, leaving it as `5`.**

4. **Post-Transfer State:**
   - Anyone querying the state of `tokenId=123` will see it incorrectly still staked at `plotId=5`, even though interactions and tax computations apply as if it is on `plotId=10`.
   - This can lead to misleading information displayed to the user, potentially incorrect tax calculations, or even erroneous interactions by other functions that rely on accurate `plotId`.

## Recommended Mitigation Steps
Just add a line to update the `plotId`:
```solidity
    ...
    toilerState[tokenId].latestTaxRate = plotMetadata[_toiler.landlord]
        .currentTaxRate;
    toilerState[tokenId].plotId = plotId; // Add this line to update the plotId correctly
    plotOccupied[_toiler.landlord][oldPlotId] = Plot({
        occupied: false,
        tokenId: 0
    });
    ...
```
