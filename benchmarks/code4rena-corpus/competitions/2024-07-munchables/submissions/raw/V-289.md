# Vulnerability details

## Summary

**Context:**
Currently the LockManager.sol contract has already been deployed onchain. This means that there are already existing locks created on it. When [locks](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LockManager.sol#L341), [unlocks](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LockManager.sol#L420) and [duration changes](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LockManager.sol#L251) occur in the LockManager.sol contract, it calls the forceHarvest() function on the AccountManager.sol contract, which further calls the [updatePlotMetadata()](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/AccountManager.sol#L154) on the LandManager.sol contract, which just returns currently since the contract has not been deployed yet. Once deployed, the config for the land manager contract would be updated to the current contract being audited in this contest. 

Function [triggerPlotMetadata()](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L104) - This function would be used by users/landlords who have existing locks in order to initialize their plot metadata once.

Function [stakeMunchable()](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L131) - This function is used by stakers to stake their munchables on a landlord's plot. The function initializes a ToilerState struct in the toilerState mapping [here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L162C7-L168C12), which holds many details, one of them being the landlord's current tax rate that is charged on the schnibbles a staker earns.

**Root cause:**
The issue is that since the function [stakeMunchable()](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L131) does not check if the landlord's metadata was triggered, specifically the PlotMetadata.lastUpdated is not 0, it allows a malicious user/attacker to pre-stake and receive a 0 tax-rate since PlotMetadata.currentTaxRate would be 0.

The attack works on existing locks only since their locked weighted value and thus total plots available is positive, allowing the attacker to bypass [this check](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L145C2-L146C66).

**Impact:**
Due to this, even though the landlord had not trigger the metadata, the attacker was able to stake, use the landlord's plot and earn schnibbles with a tax-free rate.

## Proof of Concept

Since most of the vulnerability has been described above, I will represent simple step-by-step actions taken by the malicious user:

1. Malicious user checks the existing LockManager.sol contract to observe which landlord has atleast 1 plot. This would be determined by dividing the locked weighted value (due to the existing lock) divided by `PRICE_PER_PLOT` (where `PRICE_PER_PLOT = 30e18` as per scripts and sponsor). [See [getNumPlots()](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L344) for reference].
2. The user simply calls the stakeMunchable() function once the LandManager.sol contract is deployed with the landlord and plotId as parameters.
3. Since stakeMunchable() [here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L137C7-L146C66) does not check if the plot metadata of the landlord was triggered i.e. lastUpdated is not zero, the call goes through and uses the landlord's currentTaxRate [here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L166), which is 0. 
4. Assuming the landlord initializes the plot metadata after some time with the tax rate or even if they do not, the malicious user keeps on accumulating schnibbles.
5. The malicious user can then simply call [unstakeMunchable()](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L173) to receive the schnibbles at a tax-free rate.

## Tools Used
Manual Review

## Recommended Mitigation Steps
In function stakeMunchable(), check if the lastUpdated variable in landlord's PlotMetadata is 0 or not. If 0 (meaning not yet triggered), we revert.
