# Vulnerability details

## Impact
- Attackers can get more NFTs than they originally staked
- Contracts can lose track of which NFTs are staked and which are not
- Attackers can stake multiple NFTs without any internal state

## Proof of Concept
The contract does not have reentrancy protection. in the `stakeMunchable` and `unstakeMunchable` functions, the Contract transfers the NFT before updating the internal state, which can lead to reentrancy attacks.

stakeMunchable Function:
https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L131-L171
1. External Call Before State Update:
`munchNFT.transferFrom(mainAccount, address(this), tokenId);`
- This line transfers the NFT from `mainAccount` to the contract.
- If the `MunchNFT` contract is malicious or compromised, it can call back the ‘stakeMunchable’ function before the internal state is updated.
2. State Update After External Call:
```
plotOccupied[landlord][plotId] = Plot({
    occupied: true,
    tokenId: tokenId
});

munchablesStaked[mainAccount].push(tokenId);
munchableOwner[tokenId] = mainAccount;

toilerState[tokenId] = ToilerState({
    lastToilDate: block.timestamp,
    plotId: plotId,
    landlord: landlord,
    latestTaxRate: plotMetadata[landlord].currentTaxRate,
    dirty: false
});
```
- These lines update the internal state to reflect new staking information.
- If a reentrancy attack occurs, the internal state may not accurately reflect the current state of the contract, resulting in a potential breach

unstakeMunchable Function:
https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L173-L197
1. External Call Before State Update:
`munchNFT.transferFrom(mainAccount, address(this), tokenId);`
- This line transfers the NFT back to the `mainAccount`.
- Similar to `stakeMunchable`, if the `MunchNFT` contract is malicious or compromised, it can call back the unstakeMunchable function before the internal state is updated.
2. State Update After External Call:
```
plotOccupied[_toiler.landlord][_toiler.plotId] = Plot({
    occupied: false,
    tokenId: 0
});
toilerState[tokenId] = ToilerState({
    lastToilDate: 0,
    plotId: 0,
    landlord: address(0),
    latestTaxRate: 0,
    dirty: false
});
munchableOwner[tokenId] = address(0);
_removeTokenIdFromStakedList(mainAccount, tokenId);
```
- These lines update the internal state to reflect information that is not at stake.
- If a reentrancy attack occurs, the internal state may not accurately reflect the current state of the contract, potentially causing inconsistencies and vulnerabilities.

Reentrancy Exploit Scenario:

stakeMunchable Function:
1. Initial Call by Attacker:
- Attackers invoke `stakeMunchable` to compromise their NFTs.
- The contract transfers the NFT from the attacker's account to the contract.
2. External Call to `munchNFT.transferFrom`:
- Before the internal state is updated, the `MunchNFT` contract (if malicious or compromised) calls back the `stakeMunchable` function.
3. Recursive Call:
- The recursive call to `stakeMunchable` is executed again, transferring another NFT (or the same NFT, depending on the attack) before the internal state is updated.
- This can continue over a single round, allowing an attacker to stake multiple NFTs without the internal state correctly reflecting the number of NFTs staked.
4. State Inconsistency:
- Internal states (for example, `plotOccupied`, `munchablesStaked`, `munchableOwner`, `toilerState`) were not updated correctly, causing inconsistencies and potential vulnerabilities.

unstakeMunchable Function:
1. Initial Call by Attacker:
- Attackers call `unstakeMunchable` to unstake their NFTs.
- The contract transfers the NFT back to the attacker's account.
2. External Call to 'munchNFT.transferFrom':
- Before the internal state is updated, the `MunchNFT` contract (if malicious or compromised) calls back the 'unstakeMunchable' function.
3. Recursive Call:
- The recursive call to `unstakeMunchable` is executed again, transferring another NFT (or the same NFT, depending on the attack) back to the attacker's account before the internal state is updated.
- This can continue within a single round, allowing an attacker to unstake some NFTs without the internal state correctly reflecting the number of unstaken NFTs.
4. State Inconsistency:
- Internal states (e.g., `plotOccupied`, `toilerState`, `munchableOwner`, `munchablesStaked`) were not updated properly, causing inconsistencies and potential vulnerabilities.
- An attacker could get more NFTs than were originally staked, or the contract could lose track of which NFTs were staked and which were not.

## Recommended Mitigation Steps
Use of OpenZeppelin's `ReentrancyGuard` in `MunchNFT` contracts does not automatically protect `LandManager` contracts interacting with it.
Use OpenZeppelin's `ReentrancyGuard` and the `nonReentrant` Modifier on functions that change state and are at risk of reentrancy attacks in the `LandManager` contract
