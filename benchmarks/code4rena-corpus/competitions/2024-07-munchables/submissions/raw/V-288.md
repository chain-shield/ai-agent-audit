# Vulnerability details

## Impact

As AccountManager.addSubAccount() can arbitrarily overwrite anyone’s main account, an attacker can prevent a chosen victim from unstaking their staked MunchNFT, resulting in the NFT being stuck in the contract forever.

## Proof of Concept

Consider the following scenario:

1. Assume Alice has registered her account usually via `AccountManager.register()`
2. Alice successfully stakes her NFT (`tokenId = 1`) via `LandManager.stakeMunchable()`. Note that at this point, `mainAccount = alice`. The token will be transferred to the LandManager contract and the contract’s `munchableOwner[1]` will be set to Alice.
3. Bob calls `AccountManager.addSubAccount(alice)` which sets `AccountManager`'s `mainAccounts[alice]` to Bob’s address.
4. Alice wants to unstake her token but her `LandManager.unstakeMunchable(1)` call will revert due to `InvalidOwnerError`. This is because `mainAccount` is now set to Bob’s address, so `munchableOwner[1]` does not equal to `mainAccount`. Alice will never be able to unstake her token, resulting in loss of funds.

Manual review

## Recommended Mitigation Steps

The AccountManager logic must be reworked to ensure that no authorized party can arbitrarily modify someone’s main account address. The simplest fix would be to remove the entire concept of subaccount. If that’s not feasible, one potential mitigation is to require an approval signature from the original main account’s address in order to override the original main account address.

It is also critical for the LandManager contract to ensure that unstaking can be performed by the original staker even if the main account changed to prevent the token from being stuck in the contract forever. One potential mitigation is to keep track of the original staker’s address for each token and in the unstaking function, it should always allow the original staker to withdraw their tokens. In such a case, it is also important that farmed schnibbles are properly calculated for the original staker as well.
