# Vulnerability details

## Impact

The `updateTaxRate` function is used to update the tax rate for a landlord's plots. This tax rate impacts the split of schnibbles rewards between the renter and the landlord. Here’s a detailed explanation of its logic:

`LandManager.sol#updateTaxRat()` function:

```solidity
function updateTaxRate(uint256 newTaxRate) external override notPaused {
    (address landlord, ) = _getMainAccountRequireRegistered(msg.sender);
    if (newTaxRate < MIN_TAX_RATE || newTaxRate > MAX_TAX_RATE)
        revert InvalidTaxRateError();
    if (plotMetadata[landlord].lastUpdated == 0)
        revert PlotMetadataNotUpdatedError();
    
    uint256 oldTaxRate = plotMetadata[landlord].currentTaxRate;
    plotMetadata[landlord].currentTaxRate = newTaxRate;

    // Update all toilerStates for this landlord
    for (uint256 plotId = 0; plotId < _getNumPlots(landlord); plotId++) {
        Plot memory plot = plotOccupied[landlord][plotId];
        if (plot.occupied) {
            toilerState[plot.tokenId].latestTaxRate = newTaxRate;
        }
    }

    emit TaxRateChanged(landlord, oldTaxRate, newTaxRate);
}

```

The `schnibbles` rewards in `LandManager.sol` contract are highly dependent on state variables like `REALM_BONUSES`, `RARITY_BONUSES`, and `currentTaxRate`. When these variables are updated without first harvesting accrued rewards, it leads to inconsistencies and unfairness in reward calculations. Specifically:

1. **`REALM_BONUSES` and `RARITY_BONUSES`**: These bonuses directly affect the schnibbles reward calculations. If updated without harvesting, the new bonuses retroactively impact accrued rewards.
2. **`currentTaxRate`**: Changes in this tax rate affect the distribution of schnibbles between the renter and the landlord. Without harvesting before updating, the new rate applies retroactively, leading to incorrect reward splits.

The issue arises when user rewards are not harvested before the update. Users may receive incorrect schnibbles rewards if these state variables are updated without prior harvesting. This can lead to scenario, where some users might get more or fewer rewards than they should. Basically, user rewards are not harvested during **`currentTaxRate`**, **`REALM_BONUSES` or `RARITY_BONUSES` u**pdates, leading to inconsistencies in accrued rewards between users.

## Proof of Concept

A user stakes a Munchable NFT token, accrues rewards, and then the `currentTaxRate` is updated without harvesting. The new tax rate retroactively applies, leading to incorrect reward distribution.

### **Example Scenario**:

1. User A stakes a Munchable NFT token:
    - User A stakes their Munchable NFT, and `toilerState[tokenId].dirty` is initially set to `false`.
    - Initial reward parameters:
        - `REALM_BONUSES = 5`
        - `RARITY_BONUSES = 10`
        - `currentTaxRate = 0.1`
2. Accrual of Rewards:
    - Over time, User A accrues schnibbles rewards based on the initial reward parameters.
3. Check Rewards Before Update:
    - User A's accrued rewards are calculated using the initial `REALM_BONUSES`, `RARITY_BONUSES`, and `currentTaxRate`.
    - Assume the user has accrued 1000 schnibbles.
4. Landlord Updates `currentTaxRate`:
    - The landlord calls the `updateTaxRate` function to change the tax rate from `0.1` to `0.2`.
    - Without the harvesting logic, the rewards accrued are not harvested before updating the tax rate.
5. Accrual of Rewards Post-Update:
    - After the update, User A continues to accrue rewards with the new `currentTaxRate = 0.2`.
6. Unstaking or Harvesting Rewards:
    - When User A unstakes or harvests rewards, the rewards are recalculated using the new tax rate.
    - The new rewards calculation includes the entire staking period but uses the new tax rate, leading to incorrect reward distribution.

## Recommended Mitigation Steps

1. Ensure rewards are harvested before updating any configuration variables that affect reward calculations, such as `REALM_BONUSES`, `RARITY_BONUSES`, and `currentTaxRate`.
    
    Change the `updateTaxRate()` function as follow:
    
    ```solidity
    function updateTaxRate(uint256 newTaxRate) external override notPaused {
        (address landlord, ) = _getMainAccountRequireRegistered(msg.sender);
        if (newTaxRate < MIN_TAX_RATE || newTaxRate > MAX_TAX_RATE)
            revert InvalidTaxRateError();
        if (plotMetadata[landlord].lastUpdated == 0)
            revert PlotMetadataNotUpdatedError();
    
        // Harvest rewards before updating the tax rate
        for (uint256 plotId = 0; plotId < _getNumPlots(landlord); plotId++) {
            Plot memory plot = plotOccupied[landlord][plotId];
            if (plot.occupied) {
                accountManager.forceHarvest(toilerState[plot.tokenId].landlord);
            }
        }
    
        uint256 oldTaxRate = plotMetadata[landlord].currentTaxRate;
        plotMetadata[landlord].currentTaxRate = newTaxRate;
    
        // Update all toilerStates for this landlord
        for (uint256 plotId = 0; plotId < _getNumPlots(landlord); plotId++) {
            Plot memory plot = plotOccupied[landlord][plotId];
            if (plot.occupied) {
                toilerState[plot.tokenId].latestTaxRate = newTaxRate;
            }
        }
    
        emit TaxRateChanged(landlord, oldTaxRate, newTaxRate);
    }
    
    ```
    
2. Implement similar harvesting logic in functions that update `REALM_BONUSES` and `RARITY_BONUSES`.
