# Vulnerability details

## Impact

The transferToUnoccupiedPlot() function can be exploited to front-run and DOS another user from staking

## Proof of Concept

An attacker can monitor the chain for transactions attempting to stake a munchable on a specific plot.The attacker can then front run call to transferToUnoccupiedPlot to occupy desired plots just before the victim's stakeMunchable transaction gets mined. This makes the plot occupied by the time the victim's transaction is processed, causing it to revert due to OccupiedPlotError.

Consider User A wants to stake a munchable on plot ID 3 for a landlord.
They send a transaction for ``` stakeMunchable(landlord, tokenId, 3) ```

Attacker B monitors the chain and sees User A's pending transaction, sends a transaction to ``` transferToUnoccupiedPlot(tokenId, 3) ``` using a higher gas price to ensure it gets mined first. When User A's transaction is finally processed, plot ID 3 is already occupied, causing a revert.

Especially possible when attacker has majority of the plots occupied, of a landlord.

## Tools Used

Manual Review

## Recommended Mitigation Steps

Introduce a cooldown period for plot transfers in function transferToUnoccupiedPlot() to prevent rapid and continuous plot switching.

```Solidity
plotCooldown[_toiler.landlord][plotId] = block.timestamp + T; // Set cooldown period T 
```
