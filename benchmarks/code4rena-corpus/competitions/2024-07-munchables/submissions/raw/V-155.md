# Vulnerability details

## Impact
In `LandManager::_farmPlots(...)`, `schnibblesTotal` is repeatedly being typecasted to `int256` to be multiplied by `finalBonus` as such:

```solidity
finalBonus =
    int16(
        REALM_BONUSES[
            (uint256(immutableAttributes.realm) * 5) +
                uint256(landlordMetadata.snuggeryRealm)
        ]
    ) +
    int16(
        int8(RARITY_BONUSES[uint256(immutableAttributes.rarity)])
    );
schnibblesTotal =
    (timestamp - _toiler.lastToilDate) *
    BASE_SCHNIBBLE_RATE;
schnibblesTotal = uint256(
    (int256(schnibblesTotal) +
        (int256(schnibblesTotal) * finalBonus)) / 100
);
```

However, if `finalBonus` is negative, then `int256(schnibblesTotal) +(int256(schnibblesTotal) * finalBonus))` will be negative, and casting it to `uint256` directly will cause `schnibblesTotal` to overflow into a huge value. This will cause `_farmPlots(...)` to always revert whenever it is called, making it impossible for the user to work with his NFT collection in the `LandManager` contract, as every function calls `_farmPlots(...)`.

As NFT attributes are randomly generated, the following test scenario takes values for the REALM_BONUSES and RARITY_BONUSES as seen in the provided [deployment constants](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/deployments/utils/consts.ts#L129)

1. Naruto has a collection of munchables, and wants to stake some of them into Sasuke's plots, where Sasuke's snuggery is in the `Drench` realm.

2. Naruto initially stakes a munchable from the `Everfrost` realm with a `Common` rarity.

3. The `stakeMunchable(...)` call will succeed because `_farmPlots(...)` will not go through any stakes, because Naruto does not have any staked munchables and `munchablesStaked[mainAccount].length = 0`.

4. After some time, Naruto wants to get his munchable NFT back and tries to unstake from Sasuke's plots.

5. This time the logic in `_farmPlots(...)` will be initiated.

6. From the realm and rarity bonuses of Naruto's staked munchable, the `finalBonus` will be:

```solidity
finalBonus = int16(REALM_BONUSES[(uint256(immutableAttributes.realm) * 5) + uint256(landlordMetadata.snuggeryRealm)]) + int16(int8(RARITY_BONUSES[uint256(immutableAttributes.rarity)]));

finalBonus = int16(REALM_BONUSES[uint256(0)*5 + uint256(1)]) + int16(int8(RARITY_BONUSES[uint256(1)]));

finalBonus = int16(-10) + int16(0) // REALM_BONUSES[1] = -10, RARITY_BONUSES[1] = 0

finalBonus = -10
```

7. Let's presume that `schnibblesTotal` is something like `10e18`.
8. With these values we can now observe the following overflow:

```bash
➜ uint256 schnibblesTotal = 10e18;
➜ int256 finalBonus = -10;
➜ schnibblesTotal = uint256((int256(schnibblesTotal) + (int256(schnibblesTotal) * finalBonus)) / 100);
➜ schnibblesTotal
Type: uint256
├ Hex: 0xfffffffffffffffffffffffffffffffffffffffffffffffff3828ec4b6260000
├ Hex (full word): 0xfffffffffffffffffffffffffffffffffffffffffffffffff3828ec4b6260000
└ Decimal: 115792089237316195423570985008687907853269984665640564039456684007913129639936
```
9. Afterwards `schnibblesTotal` is further multiplied, which will lead to EVM reverts, making it impossible for Naruto to get his NFT back, or even stake new NFT's as `_farmPlots(...)` will always go through the above-described overflow.

NB: I also contacted the sponsors to confirm that the `finalBonus` can be negative and [they confirmed it](https://gist.github.com/Welith/ea2793529f7d62d241ecbcb89b3e2249).

## Recommended Mitigation Steps

The mitigation here may not be straightforward, as the easiest solution is to add a `-` sign to the `int256` value if it is negative, before casting it to `uint256`.

```solidity
diff --git a/src/managers/LandManager.sol b/src/managers/LandManager.sol
index 4da770a..10ab9fb 100644
--- a/src/managers/LandManager.sol
+++ b/src/managers/LandManager.sol
@@ -280,10 +280,13 @@ contract LandManager is BaseBlastManagerUpgradeable, ILandManager {
             schnibblesTotal =
                 (timestamp - _toiler.lastToilDate) *
                 BASE_SCHNIBBLE_RATE;
-            schnibblesTotal = uint256(
-                (int256(schnibblesTotal) +
-                    (int256(schnibblesTotal) * finalBonus)) / 100
-            );
+            int256 potentialSchnibbles = (int256(schnibblesTotal) +
+                    (int256(schnibblesTotal) * finalBonus)) / 100;
+            if (potentialSchnibbles < 0) {
+                schnibblesTotal = uint256(-potentialSchnibbles);
+            } else {
+                schnibblesTotal = uint256(potentialSchnibbles);
+            }
```

Another solution could be to set `schnibblesTotal` to `0` if `finalBonus < 0`, so that no `schnibbles` are awarded for the NFT, but this will make it unfavorable for the user to stake this specific NFT.

```diff
diff --git a/src/managers/LandManager.sol b/src/managers/LandManager.sol
index 4da770a..810a831 100644
--- a/src/managers/LandManager.sol
+++ b/src/managers/LandManager.sol
@@ -280,10 +280,13 @@ contract LandManager is BaseBlastManagerUpgradeable, ILandManager {
             schnibblesTotal =
                 (timestamp - _toiler.lastToilDate) *
                 BASE_SCHNIBBLE_RATE;
-            schnibblesTotal = uint256(
-                (int256(schnibblesTotal) +
-                    (int256(schnibblesTotal) * finalBonus)) / 100
-            );
+            int256 potentialSchnibbles = (int256(schnibblesTotal) +
+                    (int256(schnibblesTotal) * finalBonus)) / 100;
+            if (potentialSchnibbles < 0) {
+                schnibblesTotal = 0;
+            } else {
+                schnibblesTotal = uint256(potentialSchnibbles);
+            }
```

All in all, the core logic for a negative `finalBonus` should be revised so that it best suits the protocol needs.
