# Vulnerability details

## Impact
Under circumstances when toiler state is marked as dirty for a token, the `unfedSchnibbles` eligible for renter and landlord are not being account and hence not credited to the eligible parties.

So, when a token with toiler state marked as dirty is unstaked, the logic does not compute and credit the eligible unfedSchnibbles to renter and landlord. So, parties with such staked tokens will loose eligible unfedSchnibbles if they `unstake` the token while it is dirty.

As a result, the renter and landlord could potentially loose the `unfedSchnibbles` they were eligible for.

## Proof of Concept

```solidity
 function _farmPlots(address _sender) internal {
   ...
   for (uint8 i = 0; i < staked.length; i++) {
            timestamp = block.timestamp;
            tokenId = staked[i];
            _toiler = toilerState[tokenId];
   ==>     if (_toiler.dirty) continue;
   }
   ...
```
All the staked tokens for the user whose toiler state was marked dirty is being excluded from the computation of `unfedSchnibbles` for renter and landlord.


## Tools Used
Manual review

## Recommended Mitigation Steps
At the time of `unstaking`, if the toiler state for the token is dirty, then the unstaking logic should compute the `unfedSchnibbles` for renter and landlord. These computed `unfedSchnibbles` should be credited to both parties before competing the `unstaking` process.
