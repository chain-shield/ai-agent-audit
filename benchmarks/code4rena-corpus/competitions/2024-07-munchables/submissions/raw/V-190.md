# Vulnerability details

## Vulnerability Description 

Main purpose of [transferToUnoccupiedPlot](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L199) function is to transfer Munchable (TokenId) from one Plot to another plot and it then update the [plotOcuppied](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L215-L222) mapping correctly and update the tax to [latestTaxRate](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L213). But, The issues lies in the [transferToUnoccupiedPlot](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L199) function where it neglects to update the plotId of Munchable TokenId in it's [Toiler'sState Mapping](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L29) leading to an incorrectness between the actual location of the Munchable and its recorded state.

## Code Snippet

[transferToUnoccupiedPlot](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L199)

```solidity
function transferToUnoccupiedPlot(
        uint256 tokenId,
        uint256 plotId
    ) external override forceFarmPlots(msg.sender) notPaused {
        (address mainAccount, ) = _getMainAccountRequireRegistered(msg.sender);
        ToilerState memory _toiler = toilerState[tokenId];
        uint256 oldPlotId = _toiler.plotId;
        uint256 totalPlotsAvail = _getNumPlots(_toiler.landlord);
        if (_toiler.landlord == address(0)) revert NotStakedError();
        if (munchableOwner[tokenId] != mainAccount) revert InvalidOwnerError();
        if (plotOccupied[_toiler.landlord][plotId].occupied)
            revert OccupiedPlotError(_toiler.landlord, plotId);
        if (plotId >= totalPlotsAvail) revert PlotTooHighError();

        toilerState[tokenId].latestTaxRate = plotMetadata[_toiler.landlord]
            .currentTaxRate;
        plotOccupied[_toiler.landlord][oldPlotId] = Plot({
            occupied: false,
            tokenId: 0
        });
        plotOccupied[_toiler.landlord][plotId] = Plot({
            occupied: true,
            tokenId: tokenId
        });
        //@audit  Missing: Update toilerState[tokenId].plotId
        emit FarmPlotLeave(_toiler.landlord, tokenId, oldPlotId);
        emit FarmPlotTaken(toilerState[tokenId], tokenId);
    }
```

## Proof of Concept

1. Initial State:
   - Alice is a landlord with 200 plots (0 to 199).
   - Bob owns Munchable NFT with tokenId 42.
   - Bob has staked his Munchable on Alice's plot 100.
   - Current state:
     * `plotOccupied[alice][100] = Plot(occupied: true, tokenId: 42)`
     * `toilerState[42] = ToilerState(lastToilDate: X, plotId: 100, landlord: alice, latestTaxRate: Y, dirty: false)`

2. Bob decides to move his Munchable to plot 150:
   - Bob calls `transferToUnoccupiedPlot(42, 150)`.
   - The function executes successfully, updating `plotOccupied`:
     * `plotOccupied[alice][100] = Plot(occupied: false, tokenId: 0)`
     * `plotOccupied[alice][150] = Plot(occupied: true, tokenId: 42)`
   - However, due to the vulnerability, `toilerState` is not fully updated:
     * `toilerState[42]` still has `plotId: 100` (should be 150)

3. Inconsistency Established:
   - Now we have a situation where:
     * The Munchable is actually on plot 150.
     * But `toilerState` says it's on plot 100.
4. Now, if Bob try to interact with the Munchable based on the toilerState, they might encounter issues because the plotId is incorrect.

## Impact
By not updating the ToilerState of TokenId while transferring tokenId from one plot to another unOccupied plot, The `_farmPlots` function may use the wrong plot ID, results in wrong or missed reward calculation. 

## Potential Issues 

Making this section as it creates multiple issues 

a) Incorrect Farming Calculations:

as,farmPlots function, which would typically use the plotId from toilerState, provided situation can occur

- When `_farmPlots` is called, it uses `toilerState[tokenId].plotId` to determine the plot.

- It might try to farm from plot 100, which is now empty, instead of 150.

- This could lead to missed farming rewards or incorrect calculations.

b) Incorrect Plot Management:

- If Alice tries to assign another Munchable to plot 100, the contract might allow it, thinking it's unoccupied but actually it had tokenId store of previous Munchable that is still stored there.

c) Worst case scenario:

- Multiple Munchables could end up with incorrect plot assignments in `toilerState`.

## Recommended Mitigation 

To fix this, the `transferToUnoccupiedPlot` function should be updated to include toilerState mapping changes as below:

```solidity
toilerState[tokenId].plotId = newPlotId;
```

This simple addition would ensure that all state variables remain consistent, preventing the potential issue.
