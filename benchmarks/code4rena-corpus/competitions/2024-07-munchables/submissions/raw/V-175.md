# Vulnerability details

## Impact
The incorrect plot range check can cause transactions to fail due to a wrongly implemented validation, while we have both the plot and the NFT. This disrupts the staking process, leading to losing the opportunity for both parties, staker and landlord.

## Proof of Concept

The issue lies in the incorrect validation of the plot range, which can cause transactions to fail even when both the plot and the NFT are available.

```solidity
uint256 totalPlotsAvail = _getNumPlots(landlord);
if (plotId >= totalPlotsAvail) revert PlotTooHighError();
```
```solidity
function _getNumPlots(address _account) internal view returns (uint256) {
   return lockManager.getLockedWeightedValue(_account) / PRICE_PER_PLOT;
}
```
The current validation uses >=, which incorrectly allows for the possibility of staking to an invalid plot index.
This results in a transaction failure despite having both the plot and the NFT available.

**Example scenario:**

Let's consider a scenario where the landlord has exactly one plot. This means totalPlotsAvail will be 1.

Landlord: Has only one plot.
Staker: Attempts to stake an NFT to plotId 1.

This scenario will lead to a failed transaction, causing the staking process to be disrupted. Both the staker and the landlord lose the opportunity to:

1. Earn Points: The staking process is tied to farming points or other incentives. By failing to stake, both parties miss out on potential rewards and benefits.
2. Utilize Assets: Despite having the necessary plot and NFT, the faulty validation prevents their proper use, leading to frustration and inefficiency.

## Tools Used

Manual review

## Recommended Mitigation Steps

By correcting the condition to use >, we ensure the plot index is correctly validated:
```solidity
if (plotId > totalPlotsAvail) revert PlotTooHighError();
```
