# Vulnerability details

## Impact

There is a known critical issue described in the contest README related to an edge case in the `_farmPlots()` function. However, the current code implementation has an even more critical attack vector that allows a malicious user to obtain farm rewards at almost zero cost (only gas) after unlocking funds, leads to a more severe impact of the vulnerability than what is described in the README.

## Proof of Concept

Before we dive into this vulnerability, it's important to understand the details of the edge case as described in the [README file](https://github.com/code-423n4/2024-07-munchables/blob/main/README.md?plain=1#L19-L20).

In the `_farmPlot` function, the [code snippet](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L251-L261):

```solidity
            if (_toiler.dirty) continue;
            landlord = _toiler.landlord;
            // use last updated plot metadata time if the plot id doesn't fit
            // track a dirty bool to signify this was done once
            // the edge case where this doesnt work is if the user hasnt farmed in a while and the landlord
            // updates their plots multiple times. then the last updated time will be the last time they updated their plot details
            // instead of the first
            if (_getNumPlots(landlord) < _toiler.plotId) {
                timestamp = plotMetadata[landlord].lastUpdated;
                toilerState[tokenId].dirty = true;
            }
```

code details:
- Dirty Flag: If the dirty flag is set, the function skips processing the plot.
- PlotMetadata lastUpdated: If the `plotID` doesn't fit within the landlord's plots, the system uses the last updated plot metadata time, which will be updated on lock/unlock operations.

**Edge Case**: If the user hasn't farmed in a while and the landlord updates their plots multiple times, the last updated time will reflect the latest update rather than the first. 
This allows farming based on the latest update time, even if the funds are not locked for a long time.

Consider a scenario like this:

1. landlord locks for 100 plots
2. user puts a munchable on plot 90
3. landlord unlocks 50 plots (plot 90 is invalid)
4. landlord locks 100 plots (or locks and unlocks multiple times)
5. user farms on plot 90

since the user never farmed, the plot will never be triggered as dirty
so he will farm for the entire length of time as long as he is inactive.

The above description makes the edge case clear, but let's take a look at the [`setlockduration` function in the LockManager contract](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LockManager.sol#L247-L275).

```solidity
    function setLockDuration(uint256 _duration) external notPaused {
        if (_duration > configStorage.getUint(StorageKey.MaxLockDuration))
            revert MaximumLockDurationError();

        accountManager.forceHarvest(msg.sender);
        playerSettings[msg.sender].lockDuration = uint32(_duration);
        // update any existing lock
        uint256 configuredTokensLength = configuredTokenContracts.length;
        for (uint256 i; i < configuredTokensLength; i++) {
            address tokenContract = configuredTokenContracts[i];
            if (lockedTokens[msg.sender][tokenContract].quantity > 0) {
                // check they are not setting lock time before current unlocktime
                uint32 lastLockTime = lockedTokens[msg.sender][tokenContract]
                    .lastLockTime;
                if (
                    lastLockTime + uint32(_duration) <
                    lockedTokens[msg.sender][tokenContract].unlockTime
                ) {
                    revert LockDurationReducedError();
                }

                lockedTokens[msg.sender][tokenContract].unlockTime =
                    lastLockTime +
                    uint32(_duration);
            }
        }

        emit LockDuration(msg.sender, _duration);
    }
```

This function also can update the plot metadata time which trigger by this line of code:

```solidity
        accountManager.forceHarvest(msg.sender);
```

And [the `accountManager.forceHarvest` function](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/AccountManager.sol#L139-L157):

So let's go back to the above scenario, the landlord can unlock all the funds by calling `setLockDuration` anytime to update the time of the plot metadata, it's only costs gas and doesn't need to lock the funds, which will freeze the landlord's funds for at least 30 days (refer MINLOCKDuration).

The impact of this attack vector is more severe than the edge case described in the README, which describes the unlock/lock scenario.

## Recommended Mitigation Steps

The solution to this issue caused by the `setLockDuration` attack vector is to not trigger updateplotMetaData when calling setLockDuration.

There are several alternative solutions to mitigate the edge case issue. The following outlines the general frameworks of these mitigation measures, which developers can refine further according to specific needs.

#### A. Tracking Effective Plot Time

Ensure accurate reward calculations by tracking only periods when the landlord has locked funds.

1. Add New Fields:
   - `unclaimFarmTime` in `ToilerState` to accumulate effective farming time.
   - `lastLockTime` and `lastUnlockTime` in `Plot` to track locking periods.
2. When Updating Plot Metadata:
   - Step 1: If plots are being unlocked, iterate over the affected plots (from `currentNumPlots` to `lastNumPlots`). For each affected plot:
     - If the plot is occupied, update the toiler's `unclaimFarmTime` with the difference between `block.timestamp` and `lastToilDate`.
     - Set the plot’s `lastUnlockTime` to the current timestamp and mark the toiler as `dirty`.
   - Step 2: If plots are being locked, iterate over the affected plots (from `lastNumPlots` to `currentNumPlots`). For each affected plot:
     - Update the plot’s `lastLockTime` to the current timestamp and reset `lastUnlockTime` and `dirty`.
3. In the `_farmPlots` Function:
   - Step 3: If the `dirty` flag is set, calculate rewards using `unclaimFarmTime`.
   - Step 4: If the `dirty` flag is not set, calculate rewards using `timestamp - lastToilDate + unclaimFarmTime`.
   - Step 5: Update the `lastToilDate`, reset `unclaimFarmTime`, and clear the `dirty` flag.

#### B. Tracking Plot Updates with Historical Data

Add New State Variable: `landlord_updatetime_and_plotnum` to record timestamps and the number of active plots each time `plotMetadata[landlord].lastUpdated` is modified.

1. Record the current timestamp and the number of active plots in `landlord_updatetime_and_plotnum` each time the landlord locks/unlocks plots.
2. Traverse `landlord_updatetime_and_plotnum` to find the earliest plot expiration time, using this as the computation time for the pet's labor.
3. Calculate rewards based on the valid farming period.
4. Identify the minimum start labor time `A` among all laboring pets for the current landlord (`min(toilerState[plotOccupied[i].tokenId].lastToilDate, ...)`).
   - Step 5: Remove any data from `landlord_updatetime_and_plotnum` that is earlier than time `A` to keep the data structure efficient.

#### C. Immediate Reward Settlement on Unlock

1. When the landlord unlocks plots, immediately settle rewards for the affected plots.
2. Calculate and distribute rewards based on the farming duration up to the unlock time.
3. End farming sessions for the unlocked plots, releasing any associated munchable pledges.
4. Update plot metadata to reflect the unlock operation accurately.

Benefits:
- Immediate and accurate reward distribution.
- Simplifies state management by settling rewards in real-time.
- Prevents long-term inconsistencies in reward allocation.
