# Vulnerability details

## Impact

There are two cases for this issue:

1. Inadequate handling of the exit mechanism in the `_farmPlots` function may result in scenarios where valid plots remain invalid, preventing users from earning rewards. Additionally, the landlord's plot utilization rate may be reduced by 20% or more due to the impact of currency price fluctuations.
2. The second case, while theoretically possible, is less likely to occur but can still affect users. In this situation, the landlord cannot receive rewards if the staked user does not perform any operations, and the landlord cannot do anything to trigger the rewards. Although this situation exists in theory, users will be motivated to collect rewards to end this state. However, the landlord's time will be affected as it depends on the actions of the staked user.

## Proof of Concept

For the second case, the issue is clear.

The main focus here is the first case, the key point [code snippet](https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L251) in the `_farmPlots` function:

```solidity
            if (_toiler.dirty) continue;
```

```solidity
            landlord = _toiler.landlord;
            // use last updated plot metadata time if the plot id doesn't fit
            // track a dirty bool to signify this was done once
            // the edge case where this doesnt work is if the user hasnt farmed in a while and the landlord
            // updates their plots multiple times. then the last updated time will be the last time they updated their plot details
            // instead of the first
            if (_getNumPlots(landlord) < _toiler.plotId) {
                timestamp = plotMetadata[landlord].lastUpdated;
                toilerState[tokenId].dirty = true;
            }
```

Consider the following scenario:

1. A plot becomes invalid due to reduced locked funds or token price drop, and the dirty flag will be set after the user's daily farm (user behavior is uncertain, but what is clear is that users may have a need for daily harvesting that).
2. If funds are relocked or the price rises, the plot remains invalid since the dirty flag isn't reset.
3. Users must restake to earn rewards; otherwise, they receive nothing even if the plot is valid again.

For the landlord, he has to wait for other users to perform operations. Even if he wants to lock more funds to remedy the invalid plot caused by the price drop, it will be of no avail. If the staked user wants to act maliciously or doesn't notice this, it could result in a denial of service for the landlord.

Unlike the effect of calling lock/unlock directly, price changes are beyond the control of users.

As an example, ETH's price fluctuations in the last month have ranged from around [2800-3500 (refer CMC)](https://coinmarketcap.com/currencies/ethereum/), the percentage change in the price of ETH over the last 30 days is approximately 20%.
 ​
This means that for a landlord who locks in ETH, 20% of his plots may remain “invalid” due to price fluctuations, while the ETH price will keep changing, which will reduce the landlord's utilization of his plots by 20%.

## Recommended Mitigation Steps

1. If the plot is no longer available (unlocking funds/price change), remove the munchable occupying the plot directly during function processing (unlock) or give the landlord the option of triggering an unstake operation (Since no revenue is generated when plots are invalidated after farming and dirty flag are set up, there is no loss for staked munchable users and there is an opportunity to shift the gas cost).

2. Landlords should have the option to set a maximum farming time for plots. This should be a two-way choice. Once farming is complete, both the landlord and the user can opt out (or harvest) and move on to the next round of farming. This mitigation is also an alternative solution to the known critical problem described in the README (the edge case where plots are updated multiple times) by adding a variable that keeps a record of the actual farming time, and the validity time of the plots affected by the lock/unlock operations is stored.
