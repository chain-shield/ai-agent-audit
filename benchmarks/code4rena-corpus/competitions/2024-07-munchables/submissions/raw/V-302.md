# Vulnerability details

## Impact

Whenever admin roles update the price of the a configured token in the LockManager Contract Through a proposal successfully. If its a decrease in price it can render some existing plot Id's dirty when calculating rewards for present and future in the `_farmPlots()` function even without the landlord locking or unlocking their tokens.

In some cases a users NFT can be stuck in the contract until the Landlord locks, unlocks tokens or increases lock duration forcing a plot metadata update.

## Proof of Concept

Lets look at the following actions:
- A landlord has `10 plots` of lands existing and decides to increase his lock duration in the LockManager contract. This in turn calls the `accountManager.forceHarvest()` which updates the plot metadata. Lets take the time this happened at `second x + 100`. Where x is a starting time at some point for all future times.

- A user stakes onto the landlords `plot Id 9` in the LandManger contract. Then at `second x + 160` decides to manually farm his plots via `farmPlots()` or `transferToUnoccupiedPlot()` if he's moving to another plot Id.

- At `second x + 200` there is a proposal in the lockManager that was accepted to decrease the usd price of a configured token the landlord has locked. This in turn reduces the number of plots that the landlord has via the `_getNumPlots` function.

- If the number of plots the landlord has reduces to 7. It means the users plot Id is now dirty without the landlord locking or unlocking any tokens.

- When the user decides to call `unstakeMunchable` the `_farmPlots()` function is called and this function reverts because of an arithmetic underflow in the `_farmplots()`:

`if (_getNumPlots(landlord) < _toiler.plotId) {
    timestamp = plotMetadata[landlord].lastUpdated;
    toilerState[tokenId].dirty = true;
`}
Since the users plot Id is now less, due to the proposal to decrease the price of a configured token in the LockManager has passed.
The toiler plot Id : `9` is now dirty and the timestamp for calculating rewards for the toiler is now the last updated timestamp of the landlord plotMetadata.
Which was the last time the landlord, locked, unlocked or increased lock duration and that was at `second x + 100`

Further down in the `_farmPlots()` function,

`schnibblesTotal = (timestamp - _toiler.lastToilDate) * BASE_SCHNIBBLE_RATE;`

The schnibblesTotal is a uint256 value.
The timestamp is the last updated plot metadata of the landlord which is `second x + 100`
The toiler last toil date was the last time the toiler directly or indirectly called `_farmPlots()` which was at `second x + 160`.

`schnibblesTotal = ((x+100) - (x+160)) * BASE_SCHNIBBLE_RATE;`


This means the schnibblesTotal would revert every time due to the arithmetic underflow in the logic when the user tries to `transferToUnoccupiedPlot()`, `unstakeMunchable()` or `farmPlot()` until the landlord associated with the toiler(tokenId) either locks more tokens, unlocks tokens or increases his lock duration. 

## Recommended Mitigation Steps
Another function for a user to unstake their token Id without farming plots in the process.
