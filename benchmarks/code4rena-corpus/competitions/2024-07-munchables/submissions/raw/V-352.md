# Vulnerability details

## Impact
1.  All tax rates and the price per plot could be set to zero, fundamentally breaking the economic model of the system.
2.  With MIN_TAX_RATE and MAX_TAX_RATE potentially set to zero, the updateTaxRate() function's checks become meaningless allowing any tax rate to be set.
3.  If PRICE_PER_PLOT is zero, users might be able to acquire land for free leading to economic imbalance and potential system abuse.
4.  Zero-value BASE_SCHNIBBLE_RATE could disrupt any reward or incentive mechanisms based on this rate.

## Proof of Concept
In the `LandManager` contract's `_reconfigure()` function, critical parameters such as `MIN_TAX_RATE`, `MAX_TAX_RATE`, `DEFAULT_TAX_RATE`, `BASE_SCHNIBBLE_RATE`, and `PRICE_PER_PLOT ` are being initialized using incorrect storage keys. Instead of using keys specific to these parameters, the function is using keys that appear to be related to other contract addresses or unrelated configurations


These keys `(LockManager, AccountManager, ClaimManager, MigrationManager)` are likely meant for retrieving contract addresses not numerical values for tax rates and prices. Moreover, the getUint() function does not revert on non-existent keys but returns zero. This means that if these incorrect keys don't exist in the configuration (which is likely), all these critical parameters will be silently initialized to zero.

## Recommended Mitigation Steps
1. Use the correct keys for each parameter ensuring they match the keys used when setting these values in the configuration contract.
2. Implement checks in the `_reconfigure` function to ensure that retrieved values are non-zero and within expected ranges: i.e
```
MIN_TAX_RATE = configStorage.getUint(StorageKey.MinTaxRate);
require(MIN_TAX_RATE > 0, "MIN_TAX_RATE not set");

MAX_TAX_RATE = configStorage.getUint(StorageKey.MaxTaxRate);
require(MAX_TAX_RATE > MIN_TAX_RATE, "Invalid MAX_TAX_RATE");

//similar for the other two values.

```
