# Vulnerability details

## Overview
The protocol uses a mechanism to restrict dirty staked Munchables or dirty toilers from harvesting schnibbles. This is done by the following snippet in the ```_farmPlots(address _sender)``` function:

https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L251

```solidity
            if (_toiler.dirty) continue;
```

Suppose a previously non-dirty toiler has become dirty. In that case, it is marked dirty when the ```_farmPlots(address _sender)``` function is called with ```_sender == owner of the staked Munchable``` or ```_sender == sub-account of the owner of the staked Munchable```:

https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L258

```solidity
            if (_getNumPlots(landlord) < _toiler.plotId) {
                timestamp = plotMetadata[landlord].lastUpdated;
                toilerState[tokenId].dirty = true;
            }
```

However, when the ```updatePlotMetadata(address landlord)``` function is called, by the AccountManager (this happens when the landlord locks in or withdraws out tokens from LockManager), there is no check to account for the increment or decrement of the total number of plots available with the landowner. This gives rise to 2 vulnerable scenarios:

1. Suppose a user stakes his Munchable on day 1 on plot-id = 9 (assuming the availability of sufficient plots with the landowner). On day 2, the landowner withdraws sufficient tokens from LockManager such that his total number of plots decreased to 8. The toiler, previously on plot 9, is now dirty. On day 29, the landowner deposits tokens in LockManager such that his total number of plot again rise to 20. The toiler on plot 9 is now not dirty. On day 30, the owner of the toiler calls ```farmPlots()``` and gets harvested schnibbles as if the toiler toiled for a full 30 days.

2. A user stakes his Munchable on day 1 on plot 9. On day 30, the landowner withdraws tokens from the LockManager such that his total number of plots becomes 8. The toiler is dirty now. On day 60, the owner of the dirty toiler calls ```farmPlots()``` and gets schnibbles worth 30 days. On day 70, the landowner deposits tokens in LockManager such that his total number of plots becomes 20. The toiler, on plot 9, should not be dirty now, but its ```toilerState.dirty``` is not set to ```false```. On day 120, when the owner of the toiler would call ```farmPlots()```, neither he would get any harvested schnibbles nor the landowner would collect any tax because the loop execution would be forced to continue as the toiler would still be dirty:

https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L251

```solidity
            if (_toiler.dirty) continue;
```

## Proof of Concept
Detailed step-by-step PoC has been provided for both the impacts and their respective root cause.

## PoC for Impact 1
Let us suppose, on day 1, a user X stakes his Munchable (for ease of reference, suppose token id = 55) on plot 9 of the landowner Y. X would do this via the ```stakeMunchable(address landlord, uint256 tokenId, uint256 plotId)``` function:

https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L131

```solidity
    function stakeMunchable(
        address landlord,
        uint256 tokenId,
        uint256 plotId
    ) external override forceFarmPlots(msg.sender) notPaused {
        (address mainAccount, ) = _getMainAccountRequireRegistered(msg.sender);
        if (landlord == mainAccount) revert CantStakeToSelfError();
        if (plotOccupied[landlord][plotId].occupied)
            revert OccupiedPlotError(landlord, plotId);
        if (munchablesStaked[mainAccount].length > 10)
            revert TooManyStakedMunchiesError();
        if (munchNFT.ownerOf(tokenId) != mainAccount)
            revert InvalidOwnerError();

        uint256 totalPlotsAvail = _getNumPlots(landlord);
        if (plotId >= totalPlotsAvail) revert PlotTooHighError();

        if (
            !munchNFT.isApprovedForAll(mainAccount, address(this)) &&
            munchNFT.getApproved(tokenId) != address(this)
        ) revert NotApprovedError();
        munchNFT.transferFrom(mainAccount, address(this), tokenId);

        plotOccupied[landlord][plotId] = Plot({
            occupied: true,
            tokenId: tokenId
        });

        munchablesStaked[mainAccount].push(tokenId);
        munchableOwner[tokenId] = mainAccount;

        toilerState[tokenId] = ToilerState({
            lastToilDate: block.timestamp,
            plotId: plotId,
            landlord: landlord,
            latestTaxRate: plotMetadata[landlord].currentTaxRate,
            dirty: false
        });

        emit FarmPlotTaken(toilerState[tokenId], tokenId);
    }
```

We assume Y has a total of 20 plots available. 

On day 2, Y withdraws tokens from LockManager such that he has now only 8 plots available (we assume that Y's lock duration is over in LockManager and he could withdraw on day 2; this is not a hypothetical assumption but a common one). This makes the toiler on plot 9 dirty. However, it is not marked so.

On day 29, Y deposits tokens in LockManager such that he again has 20 plots available. The toiler on plot 9 is now not dirty. But there's no need to set its ```toilerState.dirty as false``` as it is already ```false```.

On day 30, X decides to call ```farmPlots()```. Everything happens fine except the calculation of the total schnibbles harvested. The timestamp is taken as:

https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L248

```solidity
            timestamp = block.timestamp;
```

and the time delta is calculated as:

https://github.com/code-423n4/2024-07-munchables/blob/main/src/managers/LandManager.sol#L281

```solidity
                (timestamp - _toiler.lastToilDate)
```

which is equal to:

```
block.timestamp - (block.timestamp - 30 days) = 30 days
```

This should not happen as the toiler, on plot 9, toiled only for 2 days and was granted a reward worth 30 days.

The root cause for this issue is that there is no callback to the ```_farmPlots(address _sender)``` function from the ```updatePlotMetadata(address landlord)``` function when Y withdrew and deposited tokens in LockManager. More on this in the Recommended Mitigation section below.

## Severity
For Impact 1:

Impact: At first, the impact could be seen as an unnecessary award of schnibbles to the staker. However, upon a bit of thinking it seems that this issue could allow a malicious landowner to first deposit tokens to let a staker use one of his plots, withdraw tokens out and use it for other purposes, and finally lock in tokens just before the staker would farm the plot to collect tax on the harvested schnibbles. So, the impact is two-fold: unnecessary reward to a staker with a dirty toiler as well as allowing a landowner to collect tax he is not entitled to. This seems to be the case of loss of value for the protocol and so is High.

Likelihood: There is neither any restriction to stop landowners from withdrawing tokens from LockManager (except their lockDuration) nor any check to make sure dirty toilers are not rewarded. So, the likelihood seems Medium.

For Impact 2:

Impact: There is a loss of value for the staker. He would lose reward for his toiler which is actually non-dirty. So, the impact is High.

Likelihood: There is no mechanism to reset the dirty state of a toiler once it has become dirty. Moreover, any staker can call the ```farmPlots()``` function since it is an external function. So, the likelihood seems High.

Based upon the above impact-likelihood classification, the severity seems to be High.

## Recommended Mitigation

It is recommended to follow the following steps:

1. Add a ```numPlots``` arm in the ```PlotMetadata``` struct:

```diff
    struct PlotMetadata {
        uint256 lastUpdated;
        uint256 currentTaxRate;
+      uint256 numPlots;
    }
```

In the ```plotMetadata``` mapping this arm would indicate the current total number of plots for a landlord.

2. Construct an internal function ```_check()``` as follows:

```solidity
function _check(address landlord) internal {
    prevNumPlots = plotMetadata[landlord].numPlots;
    currentNumPlots = _getNumPlots(landlord);
    
    if (currentNumPlots < prevNumPlots) {
        for (uint256 i = currentNumPlots; i < prevNumPlots; i++) {
            if (plotOccupied[landlord][i].occupied) {
                tokenId = plotOccupied[landlord][i].tokenId;
                toiler = toilerState[tokenId];
                owner = munchableOwner[tokenId];
    
                if (!toiler.dirty) {
                    _farmPlots(owner);
                    toiler.dirty = true;
                }
            }
        }
    }
   
    else {
        for (uint256 i = prevNumPlots; i < currentNumPlots; i++) {
            if (plotOccupied[landlord][i].occupied) {
                tokenId = plotOccupied[landlord][i].occupied;
                owner = munchableOwner[tokenId];
                toiler = toilerState[tokenId];
           
                if (toiler.dirty) {
                    toiler.dirty = false;
                    toiler.lastToilDate = block.timestamp;
                }
            }
        }         
    }
}    
```

As can be seen now, both the impacts are now gone. The toiler state is updated properly whenever the landlord deposits/withdraws his tokens. This is done by adding ```_check(address landlord)``` in the ```updatePlotMetadata(address landlord)```, which calls the ```_farmPlots(address  _sender)``` function, when necessary, to reward a non-dirty toiler as well as marks a toiler as dirty / non-dirty when appropriate.

This mitigation could be more optimized by enabling the ```_farmPlots(address _owner)``` function to accept a variable ```address landlord```. So, in the above mitigation, instead of using:

```
_farmPlots(owner);
```

we could use:

```
_farmPlots(owner, landlord);
```

to save looping over other landlords of the owner.

To save on gas consumption while inside the for loop, the total number of plots per landlord could be restricted to a certain value, let's say, 20. This can be done by the following changes in ```_getNumPlots(address _account)``` function:

