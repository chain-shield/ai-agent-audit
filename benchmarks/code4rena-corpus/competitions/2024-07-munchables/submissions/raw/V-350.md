# Vulnerability details

## Impact
After transferring the `tokenId` to a new unoccupied plot, the `plotId` in the `toiletState` is not updated with the new `plotId`.

Imagine we have the following scenario (for the example below, the landlord is not changed):
1. Bob stakes his `tokenId` to `plotId = 1`.
2. Bob decides to transfer his `tokenId` to a new unoccupied plot after 3 days, for example, `plotId = 3`.
3. After 10 days, Bob unstakes his `tokenId`.
4. After a few days, he stakes his `tokenId` again to the same plotId = 3, but his transaction will fail because `plotOccupied[landlord][plotId].occupied == ture`.


This happens because after unstaking a munchable token, the `plotOccupied` is reset, as the `_toiler.plotId` is equal to the old `tokenId`.

```solidity
//@audit _toiler.plotId = oldPlotId
plotOccupied[_toiler.landlord][_toiler.plotId] = Plot({
            occupied: false,
            tokenId: 0
        });
```

During the transfer, the `toiletState` is not updated with the new `plotId`, as only the `plotOccupied` is changed.

```solidity
plotOccupied[_toiler.landlord][oldPlotId] = Plot({
            occupied: false,
            tokenId: 0
        });

        plotOccupied[_toiler.landlord][plotId] = Plot({
            occupied: true,
            tokenId: tokenId
        });
```

This breaks the following sequence of actions: `transferring` -> `unstaking` -> `staking` to the same plotId where the token was transferred. 

This limits users because if they transfer a token and unstake, they cannot stake their token to the same plot again, which may lead to earning fewer schnibbles.

## Recommended Mitigation Steps
For the toilerState struct, after transferring the token to a new unoccupied plot, change the `plotId` to the new `plotId`.
