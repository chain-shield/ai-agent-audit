# Vulnerability details

## Summary

**Context:**
The function [transferToUnoccupiedPlot()](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L199) is used by stakers to transfer their munchable to another available and unoccupied plot. The function deletes and adds appropriate state changes to reflect the transfer.

**Root cause:**
The issue is that we do not update the toilerState[tokenId].plotId value to the new plot the munchable is being transferred to. 

**Impact:**
Due to this, the plotting system breaks since toilerState[tokenId].plotId stores the old plotId (oldest plotId if multiple transfers occur later on). This has numerous impacts:
1. Since the toilerState stores incorrect plotId, we could enter this [if block](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L258C12-L261C14) while farming plots if the old plotId (which was previously available when the user transferred to a lower plotId value) is not available anymore. This would mean decreased rewards for the staker since the BASE_SCHNIBBLE_RATE would be multiplied by lastUpdated - lastToilDate (small difference) instead of block.timestamp - lastToilDate (higher difference).
2. If same staker transfers to other unique unoccupied plots, all plots that were previously occupied through these transfers would be permanently occupied. This is because [over here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L215C7-L218C12) the same old plotId would be set to false again and again instead of the actual ones.
3. Since [over here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L215C7-L218C12) the same old plotId would be set to false again and again, if another user B occupies that unoccupied plot by staking, following which the original user A makes another transfer, the plotOccupied for the plotId that user B is staking on would be deleted and available for someone to occupy. This way 2 or more users could occupy the same plotId. 

## Proof of Concept

Let's go through each impact:

### Impact 1

1. Let's assume user A wants to transfer from plotId 5 to plotId 1 (assume both plots are fit within total plots available). He calls the transfer functionality to do so. Since we know the toilerState[tokenId].plotId is not updated to the latest plotId 1, it remains plotId 5. 

2. Let's assume that plotId 5 does not fit anymore due to being greater than totalPlotsAvail. When the user A farms plots, we enter the [if block here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L258C12-L261C14) due to _toiler.plotId i.e. 5 being greater than totalPlotsAvail. The actual _toiler.plotId should've been 1 and we should not have entered the if block. 

3. The if block sets the `timestamp` memory variable to `plotMetadata[landlord].lastUpdated` instead of the block.timestamp and sets dirty flag to true. This would mean decreased schnibblesTotal (i.e. rewards) for the staker since the BASE_SCHNIBBLE_RATE would be multiplied by lastUpdated - lastToilDate (small difference) instead of block.timestamp - lastToilDate (higher difference).

### Impact 2

1. Let's assume user A wants to transfer from plotId 1 to plotId 2 to plotId 3 to plotId 4 over some period of time. We assume these plots are available and unoccupied. 

2. When the transfer functionality is called to transfer from plotId 1 to 2, toilerState[tokenId].plotId is not set to 2 and remains 1. Next time user A calls the transfer function to transfer from plotId 2 to 3, since `_toiler.plotId` [here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L205) stores 1, the oldPlotId = 1. Due to this, the occupied status on 2 is never deleted [here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L215C6-L218C12) and instead plotId 1 is deleted again. The same occurs for plotId 3 to 4 transfer, where plotId 3 would remain permanently occupied. 

3. Through this, we observed how plotIds 2 and 3 remain permanently occupied.

### Impact 3

1. Let's assume user A wants to transfer from plotId 1 to plotId 2 to plotId 3 over some period of time. We assume these plots are available and unoccupied. 

2. When the transfer functionality is called to transfer from plotId 1 to 2, toilerState[tokenId].plotId is not set to 2 and remains 1.

3. Now let's assume a user B stakes on plotId 1, which is unoccupied since it was deleted [here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L215C6-L218C12). Now if user A transfers from plotId 2 to 3, since `_toiler.plotId` [here](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L205) stores 1, the oldPlotId = 1. Due to this, the occupied status of plotId 1 is deleted on which user B is currently staked on. 

4. Since the plotId 1 becomes unoccupied, another user C could stake on it. This means two users B and C are occupying the same plot and toiling on it. 

## Tools Used
Manual Review

## Recommended Mitigation Steps
Update the toilerState[tokenId].plotId to the new plotId the staker is transferring to.
