# Vulnerability details

## Impact
The `transferToUnoccupiedPlot` function is vulnerable to front-running, allowing a malicious user to cause a transaction to revert by occupying the `plotId` before the original caller's transaction is executed.

```solidity
function transferToUnoccupiedPlot(
	uint256 tokenId,
	uint256 plotId
) external override forceFarmPlots(msg.sender) notPaused {
	(address mainAccount, ) = _getMainAccountRequireRegistered(msg.sender);
	ToilerState memory _toiler = toilerState[tokenId];
	uint256 oldPlotId = _toiler.plotId;
	uint256 totalPlotsAvail = _getNumPlots(_toiler.landlord);
	if (_toiler.landlord == address(0)) revert NotStakedError();
	if (munchableOwner[tokenId] != mainAccount) revert InvalidOwnerError();
	if (plotOccupied[_toiler.landlord][plotId].occupied)
		revert OccupiedPlotError(_toiler.landlord, plotId);
	if (plotId >= totalPlotsAvail) revert PlotTooHighError();

	toilerState[tokenId].latestTaxRate = plotMetadata[_toiler.landlord]
		.currentTaxRate;
	plotOccupied[_toiler.landlord][oldPlotId] = Plot({
		occupied: false,
		tokenId: 0
	});
	plotOccupied[_toiler.landlord][plotId] = Plot({
		occupied: true,
		tokenId: tokenId
	});

	emit FarmPlotLeave(_toiler.landlord, tokenId, oldPlotId);
	emit FarmPlotTaken(toilerState[tokenId], tokenId);
}
```

A malicious user can front-run and occupy the plotId intended by another user, causing the original caller's transaction to revert. This can be exploited to continuously target and disrupt specific users by causing all their `transferToUnoccupiedPlot` calls to fail.

## Proof of Concept
1. User A attempts to call `transferToUnoccupiedPlot` with `plotId` equal to 2, which is currently unoccupied.
2. A malicious user detects this transaction in the mempool and front-runs it by submitting a transaction with the same `plotId` (2).
3. The `plotId` equal to 2 becomes occupied due to the malicious user's transaction.
4. User A's transaction reverts because the `plotId` is already occupied.

A malicious user can repeatedly perform this attack to specifically target and cause disruptions to a particular user.

## Tools Used
Manual review

## Recommended Mitigation Steps
To mitigate this issue, implement a commit-reveal scheme to obfuscate the `plotId` until the reveal phase. This will prevent front-running by making it difficult for malicious users to identify the `plotId` being targeted in the initial commit phase. Alternatively, consider implementing a blacklisting mechanism as proposed by the sponsor to prevent repeated targeting of specific users.
