# Vulnerability details

## Impact
The ``_farmPlots`` function in the ``LandManager`` contract contains a calculation that may lead to precision loss due to integer division. This could result in unfair distribution of schnibbles, potentially allowing informed users to gain an advantage over others. In extreme cases, this could lead to a drain of the contract's resources or significant imbalances in the game economy.

## Proof of Concept
The vulnerability exists in the _farmPlots function. 
An attacker analyzes the finalBonus calculation to find values that lead to favorable rounding.
They strategically choose munchables with specific realm and rarity combinations to maximize the rounding errors in their favor.
Over multiple transactions, the attacker accumulates more schnibbles than they should, gaining an unfair advantage.
Example:
Let's say schnibblesTotal is 1000 and finalBonus is 3.
The calculation would be: (1000 + (1000 * 3)) / 100 = 40
But the integer division loses the decimal, so it's actually: 1000 + 30 = 1030
An attacker could strategically time their actions to always fall just before these rounding points, accumulating extra schnibbles over time
Single Transaction Impact.Assuming thesevalues:
```
BASE_SCHNIBBLE_RATE = 1 schnibble per second
Time elapsed (timestamp - _toiler.lastToilDate) = 1 day (86400 seconds)
finalBonus = 5 (5% bonus)
```
Normal calculation:
```
CopyschnibblesTotal = 86400 * 1 = 86400
bonusAmount = (86400 * 5) / 100 = 4320
totalSchnibbles = 86400 + 4320 = 90720
Actual calculation with integer division:
CopyschnibblesTotal = 86400
bonusAmount = (86400 * 5) / 100 = 4320
totalSchnibbles = 90720
```
In this case, there's no loss due to precision in a single transaction.
An attacker could exploit rounding by choosing specific time intervals:
```bash
Assume finalBonus = 1 (1% bonus)
For a 100-second interval:
schnibblesTotal = 100 * 1 = 100
bonusAmount = (100 * 1) / 100 = 1
totalSchnibbles = 101
```
For two 50-second intervals:
First interval:
```
schnibblesTotal = 50 * 1 = 50
bonusAmount = (50 * 1) / 100 = 0
totalSchnibbles = 50
```
Second interval:
```
schnibblesTotal = 50 * 1 = 50
bonusAmount = (50 * 1) / 100 = 0
totalSchnibbles = 50
```
Total for both intervals: 100
The attacker gains 1 extra schnibble by timing their actions to avoid rounding down.
Long-term Cumulative Effect assuming an attacker exploits this consistently over a year:
```
365 days * 24 hours * 60 minutes = 525,600 minutes
```
If the attacker calls ``_farmPlots`` every minute perfectly timed:
Normal user: 
```
525,600 * 60 * 1.01 = 31,861,440 schnibbles
```
Attacker: 
```
525,600 * 61 = 32,061,600 schnibbles
```
The attacker gains an extra 200,160 schnibbles over the year, which is about 0.63% more than a normal user.
Scenario 4: Large-scale Operation
Consider a large-scale farmer with 1000 munchables, each with different bonuses ranging from 1% to 10%.
In a single day:
Worst case (all 1% bonus): 86,400,000 schnibbles
Best case (all 10% bonus): 95,040,000 schnibbles
Actual case (mixed bonuses with rounding errors): ~90,720,000 schnibbles

The difference between the worst and best case is 8,640,000 schnibbles per day. If schnibbles have any real-world value (e.g., $0.01 per 1000 schnibbles), this could translate to $86.40 per day or $31,536 per year in potential manipulated gains.
The precision loss leads to a competitive advantage in several ways:
Over time, exploiters can accumulate more schnibbles than fair players, giving them an edge in the game economy.
Knowledgeable players can time their actions to always benefit from favorable rounding, consistently outperforming others.
The larger a player's operation, the more they can benefit from these small rounding errors, creating a "rich get richer" effect.
While the impact per transaction is small, the cumulative effect over time and across many users can be substantial.

## Recommended Mitigation Steps
Use a higher precision for calculations and only round at the final step:
```solidity
uint256 constant PRECISION = 1e18;
function _farmPlots(address _sender) internal {
    // ... (earlier code)

    for (uint8 i = 0; i < staked.length; i++) {
        // ... (other calculations)

        int256 finalBonusScaled = int256(finalBonus) * PRECISION / 100;
        uint256 schnibblesTotal = (timestamp - _toiler.lastToilDate) * BASE_SCHNIBBLE_RATE;
        schnibblesTotal = uint256(
            (int256(schnibblesTotal) * (PRECISION + finalBonusScaled)) / PRECISION
        );

        // ... (remaining code)
    }
}
```
Consider using a library like PRBMath for fixed-point arithmetic:
```solidity
import "@prb/math/contracts/PRBMath.sol";
function _farmPlots(address _sender) internal {
    // ... (earlier code)

    for (uint8 i = 0; i < staked.length; i++) {
        // ... (other calculations)

        int256 finalBonusScaled = PRBMath.mulDiv(int256(finalBonus), 1e18, 100);
        uint256 schnibblesTotal = (timestamp - _toiler.lastToilDate) * BASE_SCHNIBBLE_RATE;
        schnibblesTotal = uint256(
            PRBMath.mulDiv(int256(schnibblesTotal), 1e18 + finalBonusScaled, 1e18)
        );

        // ... (remaining code)
    }
}
```
Implement a minimum schnibble increment to prevent exploitation of small rounding errors:
```solidity
function _farmPlots(address _sender) internal {
    // ... (earlier code)

    for (uint8 i = 0; i < staked.length; i++) {
        // ... (other calculations)

        uint256 newSchnibbles = uint256(
            (int256(schnibblesTotal) +
                (int256(schnibblesTotal) * finalBonus)) / 100
        );
        
        if (newSchnibbles - schnibblesTotal < MIN_SCHNIBBLE_INCREMENT) {
            newSchnibbles = schnibblesTotal + MIN_SCHNIBBLE_INCREMENT;
        }
        
        schnibblesTotal = newSchnibbles;

        // ... (remaining code)
    }
}
```
These changes will significantly reduce the impact of precision loss in the schnibble calculations, ensuring fairer distribution and preventing potential exploitation of rounding errors.
