# Vulnerability details

## Impact
The `schnibblesTotal` calculation in `LandManager::_farmPlots` contains two critical flaws:

1. ***Incorrect Percentage Calculation:*** The current implementation fails to properly apply the percentage bonus or penalty represented by `finalBonus`. This results in users receiving inaccurate amounts of schnibbles, either more or less than intended.
2. ***Overflow Vulnerability:*** When `finalBonus` is negative, the calculation of `schnibblesTotal` is going to overflow, resulting in unexpectedly large values. This can lead to users receiving vastly inflated rewards, where initially, the `schnibblesTotal` should decrease according to the negative `finalBonus` value.

## Proof of Concept
According to `config-consts.ts` file, `REALM_BONUSES` and `RARITY_BONUSES` should have those value:
```
export const REALM_BONUSES = [
  10, -10, -5, 0, 5, -10, 10, -5, 5, 0, -5, 0, 10, 5, -10, 0, -5, 10, 10, -10, 5, 10, 0, -10, 10,
];

export const RARITY_BONUSES = [0, 0, 10, 20, 30, 50];
```
Now, after `schnibblesTotal` completes it's first calculation, it should apply the calculation of `finalBonus`, if the `finalBonus`  is 10, `schnibblesTotal` should be increased by 10% its value, if the `finalBonus`  is -10, `schnibblesTotal` should decrease for 10%.

But the current implementation incorrectly calculates the percentage changes:

1. ***If `finalBonus` is positive:***
Let's work through an example to demonstrate this.

Assume:

- (timestamp - _toiler.lastToilDate) = 1 day = 86400 seconds
- BASE_SCHNIBBLE_RATE = 1e15 (as mentioned in the code)
- finalBonus = 10 (representing a desired 10% increase)

Step 1: Calculate initial schnibblesTotal schnibblesTotal = 86400 * 1e15 = 86400000000000000000

Step 2: Apply the current calculation schnibblesTotal = uint256( (int256(86400000000000000000) + (int256(86400000000000000000) * 10)) / 100 )

= uint256((86400000000000000000 + 864000000000000000000) / 100) = uint256(950400000000000000000 / 100) = 9504000000000000000

The result is 11.01% larger than the expected 10%.

2. ***If `finalBonus` is negative:***
When `finalBonus` is negative, the result of the calculation inside the parentheses can be negative. Casting this negative int256 to uint256 causes an overflow, resulting in an unexpectedly large value for `schnibblesTotal`.

Coded a minimal proof of concept on Remix:
```
// SPDX-License-Identifier: GPL-3.0
pragma solidity 0.8.25;

contract OverFlow {
    int256 public finalBonus;
    uint256 public schnibblesTotal;

    function setFinalBonus(int8 _finalBonus) public {
        finalBonus = _finalBonus;
    }
    function setSchnibblesTotal(uint256 _schnibblesTotal) public {
        schnibblesTotal = _schnibblesTotal;
    }

    function calulate() public {
        schnibblesTotal = uint256(
            (int256(schnibblesTotal) +
                    (int256(schnibblesTotal) * finalBonus)) / 100);
    }    
}
```
When we set `finalBonus` to -10 and `schnibblesTotal` to an intended number (such as 86400000000000000000), we end up with an unexpectedly large value for  `schnibblesTotal` due to overflow:
[Proof](https://github.com/user-attachments/assets/c8fb1888-d44a-4854-8d68-6260a320f443)

Manual Review, Remix

## Recommended Mitigation Steps
Implement a safe calculation method that handles both positive and negative bonuses correctly:
```
if (finalBonus >= 0) {
    schnibblesTotal = schnibblesTotal * (100 + uint256(finalBonus)) / 100;
} else {
    schnibblesTotal = schnibblesTotal * uint256(100 - int256(-finalBonus)) / 100;
}
```
