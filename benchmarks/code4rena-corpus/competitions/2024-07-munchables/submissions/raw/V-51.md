# Vulnerability details

## Impact

Under specific conditions, the conversion to uint256 underflows, allowing a user to farm an extraordinarily large amount of Schnibbles (over 1e77 Schnibbles). These conditions are easily achievable, making the vulnerability exploitable. Exploiting this would result in a drastic inflation of Schnibbles.

## Root cause and summary 

After staking a Munchable, the user can farm a plot. The function `_farmPlots` first calculates a uint256 `schnibblesTotal`. For that it calculates a `finalBonus` value [1](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L270-L279):
```
finalBonus =
  int16(
    REALM_BONUSES[
      (uint256(immutableAttributes.realm) * 5) +
      uint256(landlordMetadata.snuggeryRealm)
    ]
  ) +
  int16(
    int8(RARITY_BONUSES[uint256(immutableAttributes.rarity)])
);
```

The `finalBonus` depends on two internal arrays with these values:
- REALM_BONUSES: [10, -10, -5, 0, 5, -10, 10, -5, 5, 0, -5, 0, 10, 5, -10, 0, -5, 10, 10, -10, 5, 10, 0, -10, 10] [2](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/deployments/utils/consts.ts#L129)
- RARITY_BONUSES: [0, 0, 10, 20, 30, 50] [3](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/deployments/utils/consts.ts#L133)

For the `REALM_BONUSES` index, the code uses the user's Munchable realm and the landlord's `snuggeryRealm`. To get a negative `finalBonus`, the user needs to pick a realm so that `index = realm * 5 + snuggeryRealm` equals one of these indexes: [1, 2, 5, 7, 10, 14, 16, 19, 23]. With those the first part of the addition will be -5 or -10. The `RARITY_BONUSES` index is based on the rarity of the user's Munchable. For the exploit the user needs to use a rarity of 0 or 1 (aka Primordial or Common). This guarantees that the second part of the addition is 0.
With those values, the `finalBonus` can either be -5 or -10, either one works to ensure an underflow will happen.

The function than calculates `schnibblesTotal` based on the time since the last toil date and the `BASE_SCHNIBBLE_RATE` [4](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L280-L282). Afterwards it adjusts that total based on the `finalBonus` [5](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L283-L286):
```
schnibblesTotal = uint256(
  (int256(schnibblesTotal) +
  (int256(schnibblesTotal) * finalBonus)) / 100
);
```
This implementation contains an error. It first calculates the bonus amount `(int256(schnibblesTotal) * finalBonus)` and then adds the total amount. With the described settings, this can be simplified to one of the following cases:
- `x + x * (-5) => (-4) * x`
- `x + x * (-10) => (-9) * x`

Either case results in a negative value that is divided by 100 and then cast to a uint256. This conversion causes a large positive value due to the negative int256 underflowing into the uint256 type. Additionally, there is no check to limit the maximum number of schnibbles farmed.

```
    function test_POC() public {

        amp.register(MunchablesCommonLib.Realm(1), address(0));

        // landlord lock ETH
```

Next the POC approves the LandManager for that Munchable and stakes it with the landlord [18](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L131). After that it waits for 15sec (amount is irrelevant for the exploit) and calls the `farmPlot` function [19](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L228):

The contract calculates:
`schnibblesTotal = timePassed * schnibblesBaseRate = 15sec * 1e15 = 15e15` [20](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L280-L282)
and:
`schnibblesTotal  = (schnibblesTotal + schnibblesTotal * -5) / 100 = -6e14` [21](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L283-L286)
converting that to uint256:
`schnibblesTotal = uint256(schnibblesTotal) = uint256(-6e14) = ~1.15792e77` [22](https://github.com/code-423n4/2024-07-munchables/blob/94cf468aaabf526b7a8319f7eba34014ccebe7b9/src/managers/LandManager.sol#L283-L286)

## Recommended Mitigation Steps

The main issue with this vulnerability is the incorrect placement of the brackets. To ensure the addition result is always positive, adjust the brackets so that the bonus is divided by 100 first:
```
schnibblesTotal = uint256(
  int256(schnibblesTotal) +
  (int256(schnibblesTotal) * finalBonus) / 100)
);
```

Alternatively consider using a more verbose code like:
```
int256 schnibblesBonus = (int256(schnibblesTotal) * finalBonus) / 100;
schnibblesTotal = uint256(int256(schnibblesTotal) + schnibblesBonus);
```

This version breaks down the calculation into separate steps, making the code easier to understand and maintain.
