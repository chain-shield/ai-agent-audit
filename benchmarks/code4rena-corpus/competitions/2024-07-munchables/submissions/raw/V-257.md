# Vulnerability details

## Summary
Users can farm on invalid plots as long as they stake and unstake in times when their plot id is valid. In the meantime landlord can unlock funds - and make the plot invalid.

## Impact
Users who staked their Munchable on a plot that is no longer valid at a later point in time can still collect those points farmed as if they have always been valid if the landlord locks some funds later on and makes the plot valid again.
This is enabled because the plot validity will be checked only twice - when staking and unstaking (during farming). Landlord can unlock funds in the meantime.

This opens incentive for landlords and users to collude in "cheating" the protocol. Landlord offers minimum tax rate in order for the users to stake on their land. Landlords then unlock their funds while users will not lose farmed points as they wait for the funds to be locked again.

Therefore - their plot status and farmed points must be updated as soon as their plots are not valid anymore.

Since landlords can already lock their funds - for some of them the 30 day waiting period to unlock - has already finished.

## Proof of Concept
1. Users stakes his Munchable while there are 5 plots available on plot id 4.
2. Landlord unlocks his funds - making only 3 of his plots available - and this fact is NOT stored or updated on the contract
3. Time passes
4. Landlord locks his funds again, making the invalid plot available again.
5. User hasn't farmed since staking, he can farm points as if his plot never was unavailable - because plot validity is only assessed during farming (see links to affected code)

## Recommended Mitigation Steps
Here we will describe a potential solution to this problem. It requires a somewhat change in the design of the contract.

First we introduce one new field to both ```ToilerState``` and ```PlotMetadata``` struct. 
```
    struct ToilerState {
...
        uint32 wentOutOfRange;
    }
```
```
    struct PlotMetadata {
...
        uint256 totalPlots;
    }
```

```wentOutOfRange``` is a timestamp that marks the time the plot was marked invalid and user can no longer farm on it. ```totalPlots``` keeps track of the total valid plots a landlord has. We need to have it stored because we are going to update user plots when there is a decrease in landlord valid plots.

Our main improvement is that plots are invalidated at the exact moment they become so - when a landlord is unlocking funds. So ```updatePlotMetadata(address)``` function has to be updated to reflect that:
This goes in the else clause in the updatePlotMetadata function:
```
            uint256 oldTotalPlots = plotMetadata[landlord].totalPlots;
            uint256 newTotalPlots = _getNumPlots(landlord);
            if (newTotalPlots < oldTotalPlots) {
                for (uint256 i = newTotalPlots; i < oldTotalPlots; i++) {
                    Plot memory plot = plotOccupied[landlord][i];
                    if (plot.occupied) {
                        ToilerState storage toiler = toilerState[plot.tokenId];
                        if (toiler.wentOutOfRange == 0) {
                            toiler.wentOutOfRange = uint32(block.timestamp);
                            address owner = munchableOwner[plot.tokenId];

                            _farmPlots(owner);
                        }
                    }
                }
            }

            plotMetadata[landlord].lastUpdated = block.timestamp;
            plotMetadata[landlord].totalPlots = newTotalPlots;

```

Everytime ```updatePlotMetadata(address)``` is called it will look for out-of-range toilers and update their ```wentOutOfRange``` field to the current timestamp. This way we know when they stopped farming.
Also, concluding from the current design - there is no need to make them valid once the plot is available again.

If plot is out of range function will ```_farmPlots(owner)``` in the same block to collect outstanding rewards. We have to force the farming in order to be sure that the user collected his rewards and can not do that again with the same Munchable. This check is now handled by using the ```dirty``` attribute. On further attempts to farm with the same Munchable - it will not pass because we add this check to ```_farmPlots``` function.

```
if (toilerState[tokenId].wentOutOfRange == toilerState[tokenId].lastToilDate) continue;
```

When unstaking or moving to a different plot, ```wentOutOfRange``` will be reset to 0.

Also, we do not have to check if he went out of range in the farmPlots function since its already accounted for.
