# Vulnerability details

## Impact
If the landlord is able to buy multiple plotId using the same tokenId then it will impact the economics of the protocol, hence directly affecting the rates for future stakers. This anamoly of having similar tokenId in the munchablesStaked mapping allows the landlord to unstake and claim bonus multiple times with same tokenId.

## Proof of Concept
In the `stakeMunchable` function there is no check for tokenId -> plotId. If a tokenId which already has a plotId mapped to it is passed again in the function with a different plotId then it passes all checks. If the 
`munchNFT.transferFrom(mainAccount, address(this), tokenId);` line does not account of success or failure of the transferFrom then the same tokenId will pushed again `munchablesStaked[mainAccount].push(tokenId);`.

## Recommended Mitigation Steps
```
function stakeMunchable(
        address landlord,
        uint256 tokenId,
        uint256 plotId
    ) external override forceFarmPlots(msg.sender) notPaused {
        (address mainAccount, ) = _getMainAccountRequireRegistered(msg.sender);
        if(tokenToPlot[tokenId] != 0) revert TokenIdAlreadyUsed();
        if (landlord == mainAccount) revert CantStakeToSelfError();
        if (plotOccupied[landlord][plotId].occupied)
            revert OccupiedPlotError(landlord, plotId);
        if (munchablesStaked[mainAccount].length > 10)
            revert TooManyStakedMunchiesError();
        if (munchNFT.ownerOf(tokenId) != mainAccount)
            revert InvalidOwnerError();
      ...
}
```

In the line `if(tokenToPlot[tokenId] != 0) revert TokenIdAlreadyUsed();` a mapping named tokenToPlot(uint256 -> uint256) will check if the tokenId is already used or not. Then if all the checks are passed then `tokenToPlot[tokenId] = plotId`.
