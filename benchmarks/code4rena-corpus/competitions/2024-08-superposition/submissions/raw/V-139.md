# Vulnerability details



The SeawaterAMM , designed for Arbitrum's Stylus environment and based on Uniswap v3, contains an issue in its liquidity management system. The issue lies in the [`StoragePool::update_position()` function](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/pool.rs#L90-L251), which is responsible for updating the liquidity of a position by modifying the liquidity at the lower and upper ticks.

The core of the AMM's functionality relies on accurate liquidity tracking across different price ranges. Each position in the pool is defined by a lower and upper tick, representing the price range in which the liquidity is concentrated. When a user adds or removes liquidity, the `update_position()` function is called to adjust the liquidity at these ticks.

The function interacts with the [`StorageTicks::update()` method](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/tick.rs#L70-L122) to modify the liquidity at each tick. Here's the relevant part of the `update_position()` function:

```rust
pub fn update_position(&mut self, id: U256, delta: i128) -> Result<(I256, I256), Revert> {
    // ... (earlier code omitted for brevity)

    if delta != 0 {
        flipped_lower = self.ticks.update(
            lower,
            cur_tick,
            delta,
            &fee_growth_global_0,
            &fee_growth_global_1,
            false,
            max_liquidity_per_tick,
        )?;

        flipped_upper = self.ticks.update(
            upper,
            cur_tick,
            delta,  // This should be -delta
            &fee_growth_global_0,
            &fee_growth_global_1,
            true,
            max_liquidity_per_tick,
        )?;

        // ... (rest of the function)
    }

    // ... (later code omitted for brevity)
}
```

The critical issue is that the same `delta` value is passed to both the lower and upper tick updates without modification. This leads to incorrect liquidity accounting because the `delta` should be negated for the upper tick.

To understand why this is problematic, let's examine the `StorageTicks::update()` function:

```rust
impl StorageTicks {
    pub fn update(
        &mut self,
        tick: i32,
        cur_amm_tick: i32,
        liquidity_delta: i128,
        fee_growth_global_0: &U256,
        fee_growth_global_1: &U256,
        upper: bool,
        max_liquidity: u128,
    ) -> Result<bool, Error> {
        // ... (earlier code omitted for brevity)

        let new_liquidity_net = match upper {
            true => info
                .liquidity_net
                .get()
                .checked_sub(I128::lib(&liquidity_delta))
                .ok_or(Error::LiquiditySub),
            false => info
                .liquidity_net
                .get()
                .checked_add(I128::lib(&liquidity_delta))
                .ok_or(Error::LiquidityAdd),
        }?;

        info.liquidity_net.set(new_liquidity_net);

        // ... (rest of the function)
    }
}
```

In this function, the `liquidity_net` is adjusted based on the `upper` flag. If `upper` is `true`, `liquidity_net` is decreased by `liquidity_delta`, and if `false`, it's increased. However, because the `update_position()` function passes the same `delta` to both lower and upper ticks, it results in incorrect liquidity accounting.

The correct behavior should be:
1. When adding liquidity (positive delta):
   - Lower tick: increase `liquidity_net` by `delta`
   - Upper tick: decrease `liquidity_net` by `delta`
2. When removing liquidity (negative delta):
   - Lower tick: decrease `liquidity_net` by `delta`
   - Upper tick: increase `liquidity_net` by `delta`

The current implementation fails to achieve this, leading to a scenario where liquidity is incorrectly accounted for, potentially being "created" or "destroyed" improperly.

## Impact

This issue leads to severe economic implications for the AMM protocol. Incorrect liquidity accounting can result in mispricing, slippage issues, and the creation of artificial arbitrage opportunities. This can lead to significant financial losses for liquidity providers and traders, undermining the integrity and reliability of the entire protocol.

## Proof of Concept

Consider the following scenario:

1. Alice adds liquidity to a pool, creating a new position with a lower tick of 1000 and an upper tick of 2000.
2. The `update_position()` function is called with a `delta` of 1000000 (representing the amount of liquidity to add).
3. For the lower tick (1000), the `update()` function is called with `upper = false`, correctly increasing the `liquidity_net` by 1000000.
4. For the upper tick (2000), the `update()` function is called with `upper = true`, but the `delta` is still 1000000 (not negated). This incorrectly increases the `liquidity_net` by 1000000 instead of decreasing it.
5. As a result, the pool now has an extra 1000000 liquidity that shouldn't exist, creating an imbalance in the AMM's economics.

This scenario can be repeated multiple times, compounding the issue and severely distorting the pool's liquidity distribution and pricing mechanism.

## Recommended Mitigation Steps

To fix this, the `delta` should be negated for the upper tick update in the `StoragePool::update_position()` function
