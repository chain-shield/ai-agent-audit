# Vulnerability details

## Impact

In the current implementation of `tick_math.rs` library, `MAX_SQRT_RATIO` that's initialized as the constant has different value than the same variable in UniswapV3.

## Proof of Concept

`MAX_SQRT_RATIO` represents the maximum price at maximum tick. But its value differs from the UniV3 value. And as the protocol must be UniV3 compliant in terms of math, such deviations can potentially lead to an unexpected behavior as the incorrect values are used:

https://github.com/Uniswap/v3-core/blob/main/contracts/libraries/TickMath.sol#L16
```
  uint160 internal constant MAX_SQRT_RATIO = 1461446703485210103287273052203988822378723970342;
```

This is the value from UniV3 `TickMath` library and this is the value set by the protocol:

https://github.com/code-423n4/2024-08-superposition/blob/main/pkg/seawater/src/maths/tick_math.rs#L16-17
```
pub const MAX_SQRT_RATIO: U256 =
    U256::from_limbs([6743328256752651558, 17280870778742802505, 4294805859, 0]);

```

Moreover, the variable has type of `uint256` instead of `uint160`.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Initialize `MAX_SQRT_RATIO` with the value from UniV3.
