# Vulnerability details


The [`pool.rs::swap()` function](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/pool.rs#L303-L536)  is responsible for executing token swaps and updating fee growth for the involved tokens. However, there is a issue in the fee accrual logic that could lead to incorrect fee accounting and potential financial losses for liquidity providers.

The function updates the `fee_growth_global` variable only for the token being swapped in, neglecting to update it for the token being swapped out. This oversight can result in inaccurate fee calculations and improper distribution of fees to liquidity providers.

The core of the issue lies in the following section of the `swap()` function:

```rust
// update fees
if fee != 0 {
    match zero_for_one {
        true => {
            self.fee_growth_global_0.set(state.fee_growth_global);
            if state.protocol_fee > 0 {
                let new_protocol_fee =
                    self.protocol_fee_0.get() + U128::lib(&state.protocol_fee);
                self.protocol_fee_0.set(new_protocol_fee);
            }
        }
        false => {
            self.fee_growth_global_1.set(state.fee_growth_global);
            if state.protocol_fee > 0 {
                let new_protocol_fee =
                    self.protocol_fee_1.get() + U128::lib(&state.protocol_fee);
                self.protocol_fee_1.set(new_protocol_fee);
            }
        }
    }
}
```

In this code snippet, the `fee_growth_global` is updated only for the token being swapped in (`fee_growth_global_0` for `zero_for_one` true, and `fee_growth_global_1` for `zero_for_one` false). The token being swapped out does not have its `fee_growth_global` updated, leading to incomplete fee accounting.

This issue is particularly concerning because it directly contradicts one of the main invariants stated in the project's README:

> Users should receive a correct fee amount.

The `swap()` function is a critical component of the AMM system, and its correct functioning is essential for maintaining the economic balance of the protocol. The `swap_internal()` function in the `Pools` struct (@pkg/seawater/src/lib.rs) relies on this `swap()` function, potentially propagating the issue throughout the system.

In the highest impact scenario, this bug could lead to significant financial losses for liquidity providers over time, as they would not receive the full amount of fees they are entitled to for the token being swapped out.

## Impact
Liquidity providers may receive incorrect (lower) fee amounts, potentially resulting in substantial financial losses over time. This undermines the economic incentives of the protocol and could lead to a loss of trust in the system.

## Proof of Concept
1. Alice provides liquidity to a pool for both Token A and Token B.
2. Bob initiates a swap of Token A for Token B (i.e., `zero_for_one` is true).
3. The `swap()` function is called:
   ```rust
   let (amount_0, amount_1, _ending_tick) =
       pools
           .pools
           .setter(pool)
           .swap(zero_for_one, amount, price_limit_x96)?;
   ```
4. Inside `swap()`, the fee growth is updated only for Token A (`fee_growth_global_0`), but not for Token B.
5. Alice checks her accrued fees and notices that she has received fewer fees for Token B than expected.
6. Over time, as more swaps occur, Alice's loss of fees for Token B compounds, resulting in significant financial loss.

## Tools Used
Manual review

## Recommended Mitigation Steps
To address this issue, the `swap()` function should be modified to update the `fee_growth_global` for both tokens involved in the swap.
