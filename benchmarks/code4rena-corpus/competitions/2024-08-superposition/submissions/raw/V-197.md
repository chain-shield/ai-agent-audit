# Vulnerability details

## Description
In projects contest documentation they stated as Main invariant Quote:"We should follow Uniswap V3's math faithfully", however in the current implementation of `get_next_sqrt_price_from_amount_0_rounding_up` this is not exactly as uniswap v3. If we looked at `getNextSqrtPriceFromAmount0RoundingUp` in SqrPriceMath.sol [of uniswap v3](https://github.com/Uniswap/v3-core/blob/main/contracts/libraries/SqrtPriceMath.sol#L28-L56) we will see that on each return statement we always fit the result in 160 bits but this is not being followed in sqrt_price_math.rs as you can verify from the code bellow 
```rust
pub fn get_next_sqrt_price_from_amount_0_rounding_up(
    sqrt_price_x_96: U256,
    liquidity: u128,
    amount: U256,
    add: bool,
) -> Result<U256, Error> {
    ...
                //@audit against uniswap you need to fit 160 bit look at 1st return in getNextSqrtPriceFromAmount0RoundingUp in SqrtPriceMath.sol
                return mul_div_rounding_up(numerator_1, sqrt_price_x_96, denominator);
    ...
    .......
```
The same issue also exist in get_next_sqrt_price_from_amount_1_rounding_down since at the end we dont fit the result in 160 bit as  [this line from uni v3 states](https://github.com/Uniswap/v3-core/blob/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/libraries/SqrtPriceMath.sol#L94), the project function is using overflowing_sub.

## Impact
The project isnt faithfully following uniswap math.

## Tools Used
Manual Analysis

## Recommended Mitigation Steps
Change the way getNextSqrtPriceFromAmount0RoundingUp and get_next_sqrt_price_from_amount_1_rounding_down return the results so that it always fits in 160bits

Uniswap
