# Vulnerability details

## Impact

In `lib.rs` there is an initialization function called `ctor()` that is supposed to set `seawater_admin`, `nft_manager`, `emergency_council` addresses. The problem is that the function (and any other external function in the Rust implementation) does not have any access control which allows anybody to call it directly without usage of the proxy.

## Proof of Concept

The current implementation of `ctor()`:

https://github.com/code-423n4/2024-08-superposition/blob/main/pkg/seawater/src/lib.rs#L968-985
```
 pub fn ctor(
        &mut self,
        seawater_admin: Address,
        nft_manager: Address,
        emergency_council: Address,
    ) -> Result<(), Revert> {
        assert_eq_or!(
            self.seawater_admin.get(),
            Address::ZERO,
            Error::ContractAlreadyInitialised
        );

        self.seawater_admin.set(seawater_admin);
        self.nft_manager.set(nft_manager);
        self.emergency_council.set(emergency_council);

        Ok(())
    }

```

As it can be seen, the function does not check who is `msg.sender` and this creates a situation where anybody can front-run admin and call it before. And as `seawater_admin()` will be set, it'll be not possible to reset it:

https://github.com/code-423n4/2024-08-superposition/blob/main/pkg/seawater/src/lib.rs#L961
```
#[cfg_attr(feature = "admin", external)]
```

This block of admin functions has "external" visibility allowing anybody to call them externally.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Check for `msg.sender` to be `onlyProxy`, for instance, in the case of the `ctor()`. This mitigation also applies to any other external function that can be called directly in the Rust contract bypassing the proxy delegatecall.
