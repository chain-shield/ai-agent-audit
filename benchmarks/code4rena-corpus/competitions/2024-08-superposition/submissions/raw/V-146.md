# Vulnerability details

## Impact
Detailed description of the impact of this finding.

The contract makes external calls to the SEAWATER contract using the staticcall function within ownerOf and balanceOf. If the SEAWATER contract becomes complex or inefficient (e.g., grows to include more data or complex logic), these calls could potentially exceed the block gas limit. This would result in transactions reverting due to insufficient gas, which can deny service to legitimate users attempting to query ownership or balances, effectively leading to a Denial-of-Service (DoS) attack.

The functions ownerOf and balanceOf call the external contract SEAWATER using staticcall to retrieve the owner of a position and the balance of positions, respectively. If the SEAWATER contract becomes more complex (e.g., due to increased state size or computational intensity), the external calls may exceed the block gas limit. This could result in users being unable to execute these functions, leading to a DoS attack scenario.

Vulnerable function (please see POC section for exploit)
```sol
function ownerOf(uint256 _tokenId) public view returns (address) {
        (bool ok, bytes memory rc) = address(SEAWATER).staticcall(abi.encodeWithSelector(
            SEAWATER.positionOwnerD7878480.selector,
            _tokenId
        ));
        require(ok, "position owner revert");
        (address owner) = abi.decode(rc, (address));
        return owner;
    }
```

## Recommended Mitigation Steps
To mitigate the potential for gas exhaustion, the contract can limit the complexity of the external contract calls or refactor the logic to minimize the dependency on the external contract for simple queries like ownership and balances. One approach is to cache the data locally or add gas-efficient mechanisms for the SEAWATER contract to interact with the OwnershipNFTs contract. Alternatively, limits could be set on the complexity of operations within the SEAWATER contract.

A potential Solidity-based mitigation is to set reasonable gas constraints when interacting with external contracts, but a more effective approach would be redesigning how data is accessed.
```sol
// Optimized solution: Local caching or off-chain querying can reduce dependency on gas-heavy external contract calls.
// Consider caching ownership locally in OwnershipNFTs to reduce frequent external calls.
mapping(uint256 => address) private cachedOwners;

function ownerOf(uint256 _tokenId) public view returns (address) {
    address owner = cachedOwners[_tokenId];

    if (owner == address(0)) {
        (bool ok, bytes memory rc) = address(SEAWATER).staticcall(abi.encodeWithSelector(
            SEAWATER.positionOwnerD7878480.selector,
            _tokenId
        ));
        require(ok, "position owner revert");
        (owner) = abi.decode(rc, (address));
    }

    return owner;
}

function updateOwnerCache(uint256 _tokenId) external {
    (bool ok, bytes memory rc) = address(SEAWATER).staticcall(abi.encodeWithSelector(
        SEAWATER.positionOwnerD7878480.selector,
        _tokenId
    ));
    require(ok, "position owner revert");
    (address owner) = abi.decode(rc, (address));

    cachedOwners[_tokenId] = owner;
}
```

This solution introduces a local cache for ownership information in the OwnershipNFTs contract. Instead of always querying the SEAWATER contract for ownership data, the contract can use locally stored values, which can be updated when necessary (e.g., after transfers or other critical changes).

This minimizes reliance on potentially expensive external calls while still maintaining correctness by allowing external updates to the cache when required.
