# Vulnerability details

## Impact

In the current implementation of `tick_math.rs`, `getSqrtRatioAtTick()` differentiates from the implementation in UniswapV3. As the protocol claims to follow UniswapV3 math faithfully, this can result in unexpected behavior due to such deviations.

## Proof of Concept

Firstly, `getSqrtRatioAtTick()` returns a value of different type (uint256) rather than uint160 sqrtPriceX96:

https://github.com/Uniswap/v3-core/blob/main/contracts/libraries/TickMath.sol#L23
```
function getSqrtRatioAtTick(int24 tick) internal pure returns (uint160 sqrtPriceX96) 
```

This is the function from uniswapV3 code. This is the protocol's implementation:

https://github.com/code-423n4/2024-08-superposition/blob/main/pkg/seawater/src/maths/tick_math.rs#L20
```
pub fn get_sqrt_ratio_at_tick(tick: i32) -> Result<U256, Error> 
```

Additionally, tick value has type of `i32` instead of `i24`.

Such deviations can lead to mistakes in calculations as different types for values are used and possible DoS.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Consider changing the current implementation of the function to be UniV3 compliant.
