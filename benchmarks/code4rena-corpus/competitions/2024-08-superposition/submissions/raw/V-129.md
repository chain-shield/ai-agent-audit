# Vulnerability details


The `OwnershipNFTs` contract is designed to track ownership of positions in the `Seawater` contract. One of its functions, [`_onTransferReceived`](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/sol/OwnershipNFTs.sol#L74-L97), is responsible for ensuring that the recipient of an NFT can handle ERC721 tokens. This is done by calling the `onERC721Received` function on the recipient contract and checking its return value.

The ERC721 standard specifies that the `onERC721Received` function should return a specific selector (`0x150b7a02`) to confirm that the contract can handle the token. If the returned value does not match this selector, the transfer should be reverted.

However, the current implementation of `_onTransferReceived` contains a bug. The `require` statement incorrectly uses `!=` instead of `==`, which means it will revert if the returned data is equal to the expected selector. This is the opposite of the intended behavior. The function should revert if the returned data is **not** equal to the expected selector.

The relevant code is as follows:

```solidity

74:     function _onTransferReceived(
75:         address _sender,
76:         address _from,
77:         address _to,
78:         uint256 _tokenId
79:     ) internal {
80:         // only call the callback if the receiver is a contract
81:         if (_to.code.length == 0) return;
82: 
83:         bytes4 data = IERC721TokenReceiver(_to).onERC721Received(
84:             _sender,
85:             _from,

89:             // the contract we're confirming is able to receive NFTs
90:             ""

92:         // @audit - This should be == instead of !=. It's currently rejecting valid transfers and allowing invalid ones.
93:         require(
94:             data != IERC721TokenReceiver.onERC721Received.selector,
95:             "bad nft transfer received data"
96:         );
97:     }

```

## Impact
This causes the contract to reject valid NFT transfers and allow invalid ones. This could lead to a situation where NFTs are transferred to contracts that cannot handle them, potentially resulting in the loss of NFTs. Conversely, valid transfers to compliant contracts will be incorrectly reverted, disrupting the intended functionality of the contract.

## Proof of Concept
1. Alice attempts to transfer an NFT to Bob's contract, which correctly implements `onERC721Received`.
2. The `_onTransferReceived` function is called, and Bob's contract returns the correct selector (`0x150b7a02`).
3. The `require` statement incorrectly reverts the transaction because it checks for `!=` instead of `==`.
4. The valid transfer is rejected, and Alice's NFT remains with her.

Conversely:
1. Alice attempts to transfer an NFT to Charlie's contract, which does not implement `onERC721Received`.
2. The `_onTransferReceived` function is called, and Charlie's contract returns an incorrect value.
3. The `require` statement does not revert the transaction because it checks for `!=` instead of `==`.
4. The invalid transfer is allowed, and the NFT is sent to a contract that cannot handle it.

## Tools Used
Manual review

## Recommended Mitigation Steps
The `require` statement should be corrected to use `==` instead of `!=` to comply with the ERC721 standard. This ensures that the transfer is only accepted if the recipient contract correctly implements the `onERC721Received` function.
