# Vulnerability details

## Impact

`wasm_erc20::call_optional_return` doesn’t check whether the token that is being called has non-zero length and can be used by pool deployed to honeypot the users directly.

## Proof of Concept

According to the sponsor and the fact that the code should be AMM similar to `UniswapV3` anyone is able to create pools.

In the `README` it was mentioned that **it is possible for someone to grief the protocol by creating a pool with bad configuration.** 

But this issue allows a pool deployer to steal all the tokens of pool participants directly. It will happen because `call_optional_return` doesn’t validate whether the length of the code is non-zero. Low-level calls to empty addresses won’t revert and will return no data, which is a scenario that is assumed as successful in this function:

[wasm_erc20.sol](https://github.com/code-423n4/2024-08-superposition/blob/main/pkg/seawater/src/wasm_erc20.rs#L34C1-L51C2)

```rust
fn call_optional_return(contract: Address, data: &[u8]) -> Result<(), Error> {
  // the call reverted if there's return data and the return data is falsey
  match RawCall::new().call(contract, data) {
      // reverting calls revert
      Err(revert) => Err(Error::Erc20Revert(revert)),
      Ok(data) => {
          match data.get(31) {
              // first byte of a 32 byte word
              // nonreverting with no return data is okay
              None => Ok(()),
              // nonreverting with falsey return data reverts
              Some(0) => Err(Error::Erc20RevertNoData),
              // nonreverting with truthy return data is okay
              Some(_) => Ok(()),
          }
      }
  }
}
```

Same known issue is in this [library](https://github.com/Vectorized/solady/blob/main/src/utils/SafeTransferLib.sol#L11), while OpenZeppelin handles in in their [`SafeERC20`](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/master/contracts/token/ERC20/utils/SafeERC20.sol#L161) implementation.

As per our understanding Superposition inherits most of the characteristics of the Arbitrum One, but even if not the address computation is still a formula which will be used from the attacker to create honeypot by passing the address of token that is not yet deployed as a pool token and create new pool. 

1. Then he will start adding liquidity for both this non-existent token and fUSDC.
2. Transfers will pass because the low-level call performed in `call_optional_return` won’t revert but will return empty data, which is considered okay according to code.
3. By supplying the fake token he will allow users to supply only  `token1 (fUSDC)` due to pool being imbalanced, note that due to `Superposition` being relatively new chain it will be super easy to trick users that this token is legitimate.
4. User can manipulate all the pool params, including `sqrt_price`, `fee_growth_global` and `liquidity`.
5. All the users who will be performing `token1` → `token0` swaps, will lose their `fUSDC` tokens without receiving anything in return, because as we mentioned transfers will be passing without reverts.

Add check for the code length of the contract that is being called in the `call_optional_return`.
