# Vulnerability details


The [`lib.rs::swap_internal()` function](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/lib.rs#L144-L196) is responsible for executing token swaps and interacts with the [`swap()` function](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/pool.rs#L303-L536) in `pool.rs` to perform the actual swap calculations.

The root cause of the issue lies in the incorrect handling of token amounts for different types of swaps. Specifically, the function assumes that `amount_0` is always positive and `amount_1` is always negative for `zero_for_one` swaps, and vice versa for non-`zero_for_one` swaps. However, this assumption is flawed because the signs of these amounts actually depend on whether the swap is an "exact input" or "exact output" swap, which is determined by the sign of the `amount` parameter.

This incorrect assumption leads to a scenario where users could potentially receive more tokens than they should or the protocol could take fewer tokens than it should, especially in "exact output" swap scenarios. This could be exploited to drain funds from the protocol, causing significant financial losses for both users and the protocol itself.

The highest impact scenario occurs during an "exact output" swap, where the signs of `amount_0` and `amount_1` are opposite to what the function expects. This results in incorrect token transfers, potentially allowing a user to receive more tokens than they should or pay fewer tokens than required.

## Impact
This can lead to incorrect token transfers, allowing users to receive more tokens than they should or pay fewer tokens than required, potentially draining the protocol's reserves.

## Proof of Concept
1. Alice initiates an "exact output" swap with `zero_for_one` set to `true`, requesting 100 FUSDC tokens.
2. The `swap()` function in `pool.rs` calculates that Alice needs to provide 105 tokens of the pool token (accounting for fees and slippage).
3. `swap()` returns `amount_0` as 105 (positive) and `amount_1` as -100 (negative).
4. In `swap_internal()`, the function incorrectly interprets these amounts:
   - It attempts to take 105 tokens from Alice (correct)
   - It attempts to send 100 FUSDC to Alice (correct amount, but incorrect direction)
5. As a result, Alice receives 100 FUSDC but only provides 105 pool tokens, potentially less than she should due to fees and slippage.
6. This scenario can be repeated to gradually drain the protocol's FUSDC reserves.

## Recommendation
To address this issue, the `swap_internal()` function should be modified to correctly handle both "exact input" and "exact output" swaps.
