# Vulnerability details


The [`swap()` function ](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/pool.rs#L303-L536)in the `StoragePool` struct is responsible for handling token swaps within the pool. This function is a critical component of the AMM (Automated Market Maker) system, managing liquidity, updating prices, and calculating fees during swap operations.

The core issue lies in how the fee growth is tracked and updated during the swap process. Currently, the function uses a single `state.fee_growth_global` variable to track fee growth for both tokens involved in the swap. This approach can lead to inaccuracies in fee calculations, especially when the swap involves both tokens.

The problematic part of the code is as follows:

```rust
File: pool.rs
456:             if state.liquidity > 0 {
457:                 // normalise fee growth
458:                 state.fee_growth_global += full_math::mul_div(
459:                     step_fee_amount,
460:                     full_math::Q128,
461:                     U256::from(state.liquidity),
462:                 )?;
463:             }

```

This code updates the `state.fee_growth_global` variable without distinguishing between the two tokens involved in the swap. As a result, the fee growth for one token may be incorrectly attributed to the other token, leading to discrepancies in fee distribution and protocol fee calculations.

The issue is further compounded when the function updates the global fee growth variables at the end of the swap:

```

507:         if fee != 0 {

```

This code assigns the `state.fee_growth_global` to either `fee_growth_global_0` or `fee_growth_global_1` based on the `zero_for_one` flag, potentially overwriting the correct fee growth for one token with the incorrect value calculated for the other token.

The highest impact scenario occurs when a series of swaps involving both tokens takes place. In this case, the fee growth for one token could be consistently overestimated while the other is underestimated, leading to significant discrepancies in fee distribution over time.

## Impact
The inaccurate tracking of fee growth can lead to incorrect fee distribution among liquidity providers and miscalculation of protocol fees. This could result in some users receiving more fees than they should, while others receive less, potentially undermining the fairness and economic incentives of the AMM system.

## Proof of Concept
1. Alice provides liquidity to the pool for both Token A and Token B.
2. Bob performs a swap from Token A to Token B, which updates `state.fee_growth_global`.
3. Charlie performs a swap from Token B to Token A, but the `state.fee_growth_global` is not correctly differentiated between the two tokens.
4. The `swap()` function updates `fee_growth_global_0` and `fee_growth_global_1` based on the last swap direction, potentially overwriting the correct fee growth for one token.
5. When Alice attempts to collect her fees, the amount is incorrect due to the inaccurate fee growth tracking.

## Tools Used
Manual review

## Recommended Mitigation Steps
To address this issue, it's recommended to track fee growth separately for both tokens throughout the swap process.
