# Vulnerability details

# 



The `SeawaterAMM` contract contains a logical issue in its swap functions [`swapIn32502CA71()`](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/sol/SeawaterAMM.sol#L262-L278) and [`swapOut5E08A399()`](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/sol/SeawaterAMM.sol#L304-L319). These functions are designed to facilitate token swaps with slippage protection, but they fail to implement this protection effectively.

The root cause of the issue lies in how these functions set the `price_limit` parameter when calling the underlying `swap904369BE()` function. In both cases, `price_limit` is set to `type(uint256).max`, which effectively disables any price limit protection:

```solidity
File: SeawaterAMM.sol
263:         (bool success, bytes memory data) = _getExecutorSwap().delegatecall(abi.encodeCall(
264:             ISeawaterExecutorSwap.swap904369BE,
265:             (
266:                 token,
267:                 true,
268:                 int256(amountIn),
269:                 type(uint256).max  // @audit - This disables the price limit protection
270:             )
271:         ));
```

This means that the swap can proceed regardless of how much the price moves during the transaction, leaving users vulnerable to significant slippage.

Furthermore, the slippage check is performed after the swap has already occurred:

```solidity
File: SeawaterAMM.sol
276:         require(-swapAmountOut >= int256(minOut), "min out not reached!");

```

While this check can cause the transaction to revert if the slippage exceeds the user's specified limit, it happens too late in the process. By this point, the swap has already impacted the pool's state, potentially leaving it in an inconsistent condition if the transaction reverts.

This vulnerability has several serious consequences:

1. Users are exposed to potentially unlimited slippage during the swap.
2. If a transaction reverts due to slippage after the swap has occurred, it could leave the pool in an inconsistent state.


## Impact

The bug allows unlimited slippage during swaps, exposing users to financial losses and potential pool inconsistencies.



## Proof of Concept

- Alice calls `swapIn32502CA71()` with `amountIn` set to 1000 TokenA and `minOut` set to 950 TokenB.
- During the transaction, the price of TokenB drops significantly due to normal market volatility.
- The `swapIn32502CA71()` function sets `price_limit` to `type(uint256).max`, effectively disabling any price limit protection. 
- The swap function is executed, and the price of TokenB has dropped significantly due to market volatility.
- After the swap, Alice receives only 800 TokenB.
- The slippage check is performed after the swap:
     ```solidity
     require(-swapAmountOut >= int256(minOut), "min out not reached!");
     ```
- Since 800 < 950, the transaction reverts


## Recommendation

To fix this , the `swapIn32502CA71()` and `swapOut5E08A399()` functions should calculate an appropriate `price_limit` based on the `minOut` parameter before calling the `swap904369BE()` function. This ensures that the swap will fail early if the price moves beyond the user's specified slippage tolerance.

A similar modification should be made to the `swapOut5E08A399()` function. Additionally, implement a `calculatePriceLimit()` function that computes an appropriate price limit based on the input amount, minimum output, and swap direction.
