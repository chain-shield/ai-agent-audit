# Vulnerability details


The SeawaterAMM implements a fee collection mechanism for both liquidity providers and the protocol itself. The core functionality revolves around the [`collect_protocol()` function](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/pool.rs#L538-L559) in the `StoragePool` struct, which is responsible for collecting protocol fees. This function interacts with the global fee tracking mechanism and individual position fee calculations.

The [`collect_protocol()` function](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/pool.rs#L538-L559) in `pool.rs` is designed to collect protocol fees:

The issue arises because this function only updates the `protocol_fee_0` and `protocol_fee_1` values, which represent the accumulated protocol fees. It does not update the `fee_growth_global_0` and `fee_growth_global_1` values, which are crucial for calculating fees owed to individual positions.

The fee calculation for individual positions relies on these global fee growth values. In `position.rs`, the `update()` function uses `fee_growth_global_0` and `fee_growth_global_1` to calculate the fees owed to positions:

```rust
File: position.rs

54:                 .checked_sub(info.fee_growth_inside_0.get())
55:                 .ok_or(Error::FeeGrowthSubPos)?,

57:             full_math::Q128,

```

The root cause of the issue is that when protocol fees are collected, the global fee growth values remain unchanged. This discrepancy can lead to a scenario where liquidity providers can claim more fees than they should be entitled to, as the global fee growth values do not accurately reflect the fees that have been collected by the protocol.

## Impact
This issue can result in financial losses for the protocol as liquidity providers may overclaim fees. 

## Proof of Concept
1. Alice provides liquidity to a pool.
2. The pool accumulates fees over time, increasing both protocol fees and global fee growth.
3. The protocol admin calls `collect_protocol()` to collect protocol fees.
4. The `protocol_fee_0` and `protocol_fee_1` values are updated, but `fee_growth_global_0` and `fee_growth_global_1` remain unchanged.
5. Alice calls the function to collect fees for her position.
6. The fee calculation uses the outdated `fee_growth_global_0` and `fee_growth_global_1` values, which are higher than they should be after protocol fee collection.
7. Alice receives more fees than she should, effectively claiming a portion of the fees that were already collected by the protocol.

## Tools Used
Manual review

## Recommended Mitigation Steps
To address this issue, the `collect_protocol()` function should be modified to update the global fee growth values when collecting protocol fees.
