# Vulnerability details


The [`swap` function](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/pool.rs#L303-L331) in the `StoragePool` struct within `pool.rs` contains incorrect price limit checks that can lead to invalid trades. The `swap` function is responsible for handling token swaps within the pool, and it includes logic to ensure that the price limit is within acceptable bounds. However, the current implementation of these checks does not align with the expected behavior for `zero_for_one` and non-`zero_for_one` swaps.

### Summary of Functionalities:
- The [`swap` function](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/pool.rs#L303-L331) handles token swaps within the pool.
- It includes logic to ensure that the `price_limit` is within acceptable bounds.
- The `price_limit` should be less than the current price for `zero_for_one` swaps (token0 for token1) and greater than the current price for non-`zero_for_one` swaps (token1 for token0).

### Relevant Components:
- `StoragePool` struct in `pool.rs`
- `swap` function in `StoragePool`
- `tick_math::MIN_SQRT_RATIO` and `tick_math::MAX_SQRT_RATIO` constants

### Interaction:
- The `swap` function uses the `price_limit` to determine the bounds within which the swap can occur.
- The `tick_math::MIN_SQRT_RATIO` and `tick_math::MAX_SQRT_RATIO` constants define the minimum and maximum allowed price ratios.

### Root Cause:
The current implementation of the `price_limit` checks in the `swap` function does not correctly enforce the expected price direction for `zero_for_one` and non-`zero_for_one` swaps. Specifically:
- For `zero_for_one` swaps, the `price_limit` should be less than the current price (`self.sqrt_price.get()`) and not less than the minimum allowed price (`tick_math::MIN_SQRT_RATIO`).
- For non-`zero_for_one` swaps, the `price_limit` should be greater than the current price (`self.sqrt_price.get()`) and not greater than the maximum allowed price (`tick_math::MAX_SQRT_RATIO`).

Current implementation in `swap` function:
```rust
pub fn swap(
    &mut self,
    zero_for_one: bool,
    amount: I256,
    mut price_limit: U256,
) -> Result<(I256, I256, i32), Revert> {
    assert_or!(self.enabled.get(), Error::PoolDisabled);

    // ensure the price limit is within bounds
    match zero_for_one {
        true => {
            if price_limit == U256::MAX {
                price_limit = tick_math::MIN_SQRT_RATIO + U256::one();
            }
            if price_limit >= self.sqrt_price.get() || price_limit <= tick_math::MIN_SQRT_RATIO {
                Err(Error::PriceLimitTooLow)?;
            }
        }
        false => {
            if price_limit == U256::MAX {
                price_limit = tick_math::MAX_SQRT_RATIO - U256::one();
            }
            if price_limit <= self.sqrt_price.get() || price_limit >= tick_math::MAX_SQRT_RATIO {
                Err(Error::PriceLimitTooHigh)?;
            }
        }
    };

    // ... existing code ...
}
```

- For `zero_for_one` swaps, the current check incorrectly allows the `price_limit` to be greater than or equal to the current price, which is not the intended behavior.
- For non-`zero_for_one` swaps, the current check incorrectly allows the `price_limit` to be less than or equal to the current price, which is not the intended behavior.

## Impact
- This bug can lead to invalid trades, allowing trades that should be rejected due to price impact or rejecting valid trades.
- It could be exploited to perform trades at unfavorable prices, leading to losses for liquidity providers or unfair advantages for certain traders.

1. **Scenario**: A user attempts a `zero_for_one` swap with a `price_limit` greater than the current price.
   - **Step 1**: User initiates a `zero_for_one` swap with `price_limit` set to a value greater than `self.sqrt_price.get()`.
   - **Step 2**: The current check allows this swap to proceed, even though the `price_limit` should be less than the current price.
   - **Step 3**: The swap occurs at an invalid price, leading to potential losses for liquidity providers.

   - **Step 3**: The swap occurs at an invalid price, leading to potential losses for liquidity providers.
