# Vulnerability details

## Impact

Incorrect accounting which will lead to the owner still having a position count but not owning a position.

## Proof of Concept

This is the mapping of `position_owners`:

```
    // ID => owner
    position_owners: StorageMap<U256, StorageAddress>,
```

`remove_position()` is an internal function. The function `remove_position` erases the storage of `position_owners` with the id, and decreases the `self.owned_positions` by one..

```
   fn remove_position(&mut self, owner: Address, id: U256) {
        // remove owner
>        self.position_owners.setter(id).erase();

        // decrement count
>        let owned_positions_count = self.owned_positions.get(owner) - U256::one();
        self.owned_positions
            .setter(owner)
            .set(owned_positions_count);
    }
```

This function is called through `transfer_position_E_E_C7_A3_C_D()` which is used by the NFT manager to transfer the position. The transfer function does not check that the id being removed from the `from` address is the owner of the position.

```
    /// Transfers a position's ownership from one address to another. Only usable by the NFT
    /// manager account.
    ///
    /// # Calling requirements
    /// Requires that the `from` address is the current owner of the position.
    ///
    /// # Errors
    /// Requires the caller be the NFT manager.
    #[allow(non_snake_case)]
    pub fn transfer_position_E_E_C7_A3_C_D(
        &mut self,
        id: U256,
        from: Address,
        to: Address,
    ) -> Result<(), Revert> {
        assert_eq_or!(msg::sender(), self.nft_manager.get(), Error::NftManagerOnly);

>       self.remove_position(from, id);
>       self.grant_position(to, id);

        #[cfg(feature = "log-events")]
        evm::log(events::TransferPosition { from, to, id });

        Ok(())
    }
```

A mistake like this can occur:

- Let's say Bob has 5 positions.
- Alice has 1 position, one of the position is id 10.
- NFT manager wants to transfer Alice's position to Bob
- NFT manager calls `transfer_position_E_E_C7_A3_C_D()` for id 10, but did not put the `from` address as Alice but Bob instead. `to` is Bob.
- `remove_position()` is called, which erases the storage of id 10.

In the contract's perspective:

- Alice now still has 1 position in `owned_position`
- Bob has 5 position in `owned_position` because 5 - 1 + 1 = 5

The correct outcome:

- Alice should have 0 positions in `owned_positions`
- Bob should have 6 positions in `owned_positions`.

## Recommended Mitigation Steps

One recommendation is checking that the owner of the address that is set in the parameter of `remove_position` is actually the owner of the id position, something like:

```
 fn remove_position(&mut self, owner: Address, id: U256) {
         assert_eq_or!(
            self.position_owners.get(id),
            owner,
            Error::PositionOwnerOnly
        );

        // remove owner
        self.position_owners.setter(id).erase();
```
 
Another way is to do the check in the `transfer_position()` itself, like how `burn_position_AE401070()` does it.
