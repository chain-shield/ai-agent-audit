# Vulnerability details

## Impact
`burn_position` does not check whether the pool is `enabled`, causing the administrator function to become invalid.

## Proof of Concept

The comment to the burn_position_AE401070 function says:
> Requires the pool to be enabled.

In fact, however, it is not determined whether the pool is enabled.

```rust
    /// Requires the position be owned by the caller. Requires the pool to be enabled.
    #[allow(non_snake_case)]
    pub fn burn_position_AE401070(&mut self, id: U256) -> Result<(), Revert> {
        let owner = msg::sender();
        assert_eq_or!(
            self.position_owners.get(id),
            owner,
            Error::PositionOwnerOnly
        );

        self.remove_position(owner, id);

        #[cfg(feature = "log-events")]
        evm::log(events::BurnPosition { owner, id });

        Ok(())
    }
```

When `create_position` is called in `mint_position_B_C5_B086_D`,`create_position` determines enabled, so `mint` does not have this problem:


`remove_position` is invoked when `burn` is generated. `pool enable` is not determined by `remove_position`.
