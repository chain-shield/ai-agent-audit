# Vulnerability details

### Impact

Operations that rely on fee growth may sometimes revert due to lack of support for the overflow/underflow wrapping behaviour.

### Proof of Concept


1. Context


Based on [this](https://github.com/Uniswap/v3-core/issues?q=is%3Aissue+573+is%3Aclosed) issue reported to uniswap, handling fee growth relies on int256 underflow/overflow behaviour. Therefore when protocols fork/implement similar functions, they're required to take into consideration the necessity of this wrapping behaviour. 

2. Bug Location

When analyzing the contracts, calculations involving fee_growth are handled with "checked" arithmetic, mostly the `checked_sub` function. The function performs an overflowing sub and returns None (potentially returning an error in integrations) if overflow or underflow occurs.

```rs
    /// Computes `self - rhs`, returning [`None`] if overflow occurred.
    #[inline(always)]
    #[must_use]
    pub const fn checked_sub(self, rhs: Self) -> Option<Self> {
        match self.overflowing_sub(rhs) {
            (value, false) => Some(value),
            _ => None,
        }
    }
```

And looking through various places where fee growth is calculated, most importantly in the `get_fee_growth_inside` (others include the `cross` function and `update` functions). We can see that `checked_sub` function is used to calculate the fee growth, potentially limiting its wrapping underflow potential. 


```rust

        &mut self,
        lower_tick: i32,
        upper_tick: i32,
        cur_tick: i32,

    ) -> Result<(U256, U256), Error> {
//...
            (
                fee_growth_global_0
                    .checked_sub(lower.fee_growth_outside_0.get())
                    .ok_or(Error::FeeGrowthSubTick)?,
                fee_growth_global_1
                    .checked_sub(lower.fee_growth_outside_1.get())
                    .ok_or(Error::FeeGrowthSubTick)?,

        };
//...
            (
                fee_growth_global_0
                    .checked_sub(upper.fee_growth_outside_0.get())
                    .ok_or(Error::FeeGrowthSubTick)?,
                fee_growth_global_1
                    .checked_sub(upper.fee_growth_outside_1.get())
                    .ok_or(Error::FeeGrowthSubTick)?,

//...

            fee_growth_global_0
                .checked_sub(fee_growth_below_0)
                .and_then(|x| x.checked_sub(fee_growth_above_0))
                .ok_or(Error::FeeGrowthSubTick)?,
            fee_growth_global_1
                .checked_sub(fee_growth_below_1)
                .and_then(|x| x.checked_sub(fee_growth_above_1))

```

3. Final Effect
 
This could impact crucial operation that rely on this call, such as `update_position`, could revert unexpectedly, potentially dossing the operations. This behavior is quite often especially for pools that use lower fees.

More information can be found [here](https://solodit.xyz/issues/h-04-underflow-could-happened-when-calculating-uniswap-v3-positions-fee-growth-and-can-cause-operations-to-revert-code4rena-particle-protocol-particle-protocol-git), [here](https://github.com/Jeiwan/uniswapv3-book/issues?q=is%3Aissue+45+is%3Aclosed) and [here](https://github.com/Uniswap/v3-core/issues?q=is%3Aissue+573+is%3Aclosed).

And as can also be seen from Uniswap 0.8, which is based on solc that revert on overflow/underflow, the `getFeeGrowthInside` wraps the fee growth calculation in unchecked blocks to allow for the wrapping behaviour.

```solidity
    function getFeeGrowthInside(
        mapping(int24 => Tick.Info) storage self,
        int24 tickLower,
        int24 tickUpper,
        int24 tickCurrent,
        uint256 feeGrowthGlobal0X128,
        uint256 feeGrowthGlobal1X128
    ) internal view returns (uint256 feeGrowthInside0X128, uint256 feeGrowthInside1X128) {
        unchecked {
            Info storage lower = self[tickLower];
            Info storage upper = self[tickUpper];

            // calculate fee growth below
            uint256 feeGrowthBelow0X128;
            uint256 feeGrowthBelow1X128;
            if (tickCurrent >= tickLower) {
                feeGrowthBelow0X128 = lower.feeGrowthOutside0X128;
                feeGrowthBelow1X128 = lower.feeGrowthOutside1X128;
            } else {
                feeGrowthBelow0X128 = feeGrowthGlobal0X128 - lower.feeGrowthOutside0X128;
                feeGrowthBelow1X128 = feeGrowthGlobal1X128 - lower.feeGrowthOutside1X128;
            }

            // calculate fee growth above
            uint256 feeGrowthAbove0X128;
            uint256 feeGrowthAbove1X128;
            if (tickCurrent < tickUpper) {
                feeGrowthAbove0X128 = upper.feeGrowthOutside0X128;
                feeGrowthAbove1X128 = upper.feeGrowthOutside1X128;
            } else {
                feeGrowthAbove0X128 = feeGrowthGlobal0X128 - upper.feeGrowthOutside0X128;
                feeGrowthAbove1X128 = feeGrowthGlobal1X128 - upper.feeGrowthOutside1X128;
            }

            feeGrowthInside0X128 = feeGrowthGlobal0X128 - feeGrowthBelow0X128 - feeGrowthAbove0X128;
            feeGrowthInside1X128 = feeGrowthGlobal1X128 - feeGrowthBelow1X128 - feeGrowthAbove1X128;
        }
    }
```

### Recommended Mitigation Steps

Recommend using `overflow_sub` or a overflowing subtraction equivalent.
