# Vulnerability details

While certain functions in the contract include a check to ensure the pool is enabled (assert_or!(self.enabled.get(), Error::PoolDisabled)), not all functions consistently enforce this restriction. Functions such as adjust_position and init can still be called when the pool is in a disabled state. Allowing these functions to execute when the pool is disabled could result in unexpected behavior, such as adjusting liquidity positions in an inactive pool or reinitializing pool settings.

Exploitation Example:
An attacker or malicious actor could call adjust_position while the pool is disabled, which may lead to unintended liquidity adjustments or leave the pool in an inconsistent state.
Impact:
The impact of this oversight could result in:
Unintended changes to liquidity positions while the pool is inactive.
Potential manipulation of pool state in ways that compromise the pool’s functionality.
Inconsistent behavior across functions, leading to unpredictable results.



Mitigation:
A consistent PoolDisabled check should be enforced across all relevant functions, particularly those that alter the pool's state or liquidity. Implementing a global guard condition can ensure no critical operations occur while the pool is disabled.
