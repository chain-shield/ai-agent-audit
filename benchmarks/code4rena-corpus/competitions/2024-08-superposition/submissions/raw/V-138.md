# Vulnerability details


The SeawaterAMM, designed for Arbitrum's Stylus environment and based on Uniswap v3, contains an issue in its tick management system. The core of this issue lies in the [`StorageTicks::update()` function](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/tick.rs#L70-L122) within the `tick.rs` file, which is responsible for updating tick information when liquidity is added or removed from a position.

The [`StorageTicks::update()` function](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/tick.rs#L70-L122) is called by `update_position_internal()` in `pool.rs` to manage liquidity changes at specific price points (ticks). It updates the `liquidity_net` value, which represents the change in liquidity when crossing a tick. However, the current implementation incorrectly handles the `upper` boolean parameter:

```rust
let new_liquidity_net = match upper {
    true => info
        .liquidity_net
        .get()
        .checked_sub(I128::lib(&liquidity_delta))
        .ok_or(Error::LiquiditySub),
    false => info
        .liquidity_net
        .get()
        .checked_add(I128::lib(&liquidity_delta))
        .ok_or(Error::LiquidityAdd),
}?;
```

This implementation is reversed from the correct logic. When `upper` is true (indicating the upper tick of a range), it subtracts the `liquidity_delta`, and when `upper` is false (indicating the lower tick), it adds the `liquidity_delta`. This is opposite to how liquidity should be accounted for when crossing ticks in a Uniswap v3-style AMM.

The correct implementation should add liquidity for the upper tick and subtract for the lower tick:

```rust
let new_liquidity_net = match upper {
    true => info
        .liquidity_net
        .get()
        .checked_add(I128::lib(&liquidity_delta))
        .ok_or(Error::LiquidityAdd),
    false => info
        .liquidity_net
        .get()
        .checked_sub(I128::lib(&liquidity_delta))
        .ok_or(Error::LiquiditySub),
}?;
```

This affects the core functionality of the AMM, potentially leading to incorrect liquidity distribution across price ranges and affecting swap calculations.

## Impact
This can lead to severe economic implications, including incorrect pricing, unfair advantages for users who understand and exploit the bug, and potential arbitrage opportunities that shouldn't exist. It undermines the fundamental operation of the AMM and could result in significant financial losses for liquidity providers and traders.

## Proof of Concept
1. Alice creates a new position in the AMM, providing liquidity between ticks 1000 and 2000.
2. The `update_position_internal()` function in `pool.rs` is called, which in turn calls `StorageTicks::update()` for both the lower and upper ticks.
3. For the lower tick (1000), `update()` is called with `upper = false`, incorrectly adding liquidity instead of subtracting it.
4. For the upper tick (2000), `update()` is called with `upper = true`, incorrectly subtracting liquidity instead of adding it.
5. As a result, the `liquidity_net` values for both ticks are inverted, leading to incorrect liquidity accounting.
6. When the price moves and crosses these ticks, the AMM will apply the wrong liquidity changes, potentially allowing Bob to execute trades at incorrect prices or exploit arbitrage opportunities that shouldn't exist.
