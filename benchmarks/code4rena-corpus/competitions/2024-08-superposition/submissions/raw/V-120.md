# Vulnerability details

## Impact

The current implementation of the `lib.rs` smart contract allows users to perform 2 stage swaps using `swap_2_exact_in_41203_F1_D()` function. The function calls several internal functions where the last ones are `swap_2_internal()` and `swap()` from the pool. The problem is that the `swap_2_internal()` only allows to specify `minOut` amount not taking into account price limit that's used in the pool `swap()` function for slippage protection. This leads to a situation where user will be subjected to MEV attacks and may not be able to perform the swap during a huge amount of time as `min_out` will be repeatedly < `amount_out`.

## Proof of Concept

Take a look at the current functionality of `swap_2_internal()`:

https://github.com/code-423n4/2024-08-superposition/blob/main/pkg/seawater/src/lib.rs#L210-215
```
  let (amount_in, interim_usdc_out, final_tick_in) = pools.pools.setter(from).swap(
            true,
            amount,
            // swap with no price limit, since we use min_out instead
            tick_math::MIN_SQRT_RATIO + U256::one(),
        )?;

```

https://github.com/code-423n4/2024-08-superposition/blob/main/pkg/seawater/src/lib.rs#L223-227
```
let (amount_out, interim_usdc_in, final_tick_out) = pools.pools.setter(to).swap(
            false,
            interim_usdc_out,
            tick_math::MAX_SQRT_RATIO - U256::one(),
        )?;

```

As you can see, both time `price_limit` value is set to maximum effectively meaning that there is no slippage. Therefore, users can be subjected to the MEV attacks and not being able to perform the swap successfully as the `min_out` will be repeatedly less than `amount_out`.

## Tools Used

Manual review.

## Recommended Mitigation Steps

Allow users specify `price_limit` when performing 2 stage swaps.
