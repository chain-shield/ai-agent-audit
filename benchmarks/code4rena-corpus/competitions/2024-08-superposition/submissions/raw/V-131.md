# Vulnerability details


The [`update` function](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/position.rs#L43-L93) in the [`StoragePositions` struct](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/position.rs#L25-L28) calculates fees using the old liquidity value before updating it with the delta. This can lead to incorrect fee calculations, potentially causing significant financial discrepancies.

### Relevant Components

- **`StoragePositions` Struct**: Contains a map of position IDs to position details.
- **`update` Function**: Responsible for updating a position's liquidity and calculating the fees owed.
- **`StoragePool` Struct**: Contains core AMM functions and interacts with `StoragePositions`.

### Interaction Flow

1. **Position Update**: The [`update_position` function](https://github.com/code-423n4/2024-08-superposition/blob/4528c9d2dbe1550d2660dac903a8246076044905/pkg/seawater/src/pool.rs#L90-L252) in `StoragePool` calls the `update` function in `StoragePositions`.
2. **Fee Calculation**: The `update` function calculates fees using the old liquidity value before updating it with the delta.

### Issue

The `update` function calculates fees using the old liquidity value before updating it with the delta:
```rust

let owed_fees_0 = full_math::mul_div(
    fee_growth_inside_0
        .checked_sub(info.fee_growth_inside_0.get())
        .ok_or(Error::FeeGrowthSubPos)?,
    U256::from(info.liquidity.get()),
    full_math::Q128,
)?;

// ... similar calculation for owed_fees_1 ...

let liquidity_next = liquidity_math::add_delta(info.liquidity.get().sys(), delta)?;

if delta != 0 {
    info.liquidity.set(U128::lib(&liquidity_next));
}
```

#### Potential Issue

- **Adding Liquidity (Positive Delta)**: Users will pay less in fees than they should because the fee calculation uses the old, lower liquidity amount.
- **Removing Liquidity (Negative Delta)**: Users will pay more in fees than they should because the fee calculation uses the old, higher liquidity amount.


## Impact

Incorrect fee calculations can lead to users either paying too much or too little in fees, depending on whether they are adding or removing liquidity. Users could potentially exploit this bug to minimize their fee payments by strategically adding or removing liquidity.

## Proof of Concept

1. **Initial State**: 
   - Current liquidity: 1000
   - Fee growth since last update: 5000

2. **User Action**: User adds 500 liquidity.

3. **Current Calculation**:
   ```rust
   owed_fees = (5000 * 1000) / 2^128
   ```

4. **Correct Calculation**:
   ```rust
   owed_fees = (5000 * 1500) / 2^128
   ```

5. **Impact**: The user pays less in fees than they should, leading to financial discrepancies.

The fee calculation should be done after updating the liquidity to ensure accurate fee calculations. Here's the corrected version of the `update` function.
