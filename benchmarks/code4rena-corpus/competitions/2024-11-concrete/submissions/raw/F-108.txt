S-439
`takeFees` may mint less fee shares than intended
trachev
56
Insufficient
383d ago
Finding description and impact

In the takeFees modifier it is possible for fees to have been accumulated, whilst the totalSupply is 0. In that case feeInShare, which is the number of shares the fee recipient will be minted, is set to totalFee. This, however, is wrong as even if totalSupply is 0, share tokens should be scaled by 9 decimals.

This will cause the fee recipient to be minted much less fee shares than intended.

Proof of Concept

Here we can see that feeInShare is set to a value with the decimals of the asset and is not converted to shares:

            uint256 feeInShare = supply == 0
                ? totalFee
                : totalFee.mulDiv(supply, _totalAssets - totalFee, Math.Rounding.Floor);

Furthermore, the logic of _convertToShares should also be used when supply is more than 0, in order to mint the correct number of shares in all scenarios.

Recommended mitigation steps

Use the _convertToShares function:

            uint256 feeInShare = supply == 0
                ? _convertToShares(totalFee)
                : totalFee.mulDiv(supply + 10 ** decimalOffset, _totalAssets - totalFee + 1, Math.Rounding.Floor);

Shares are not worthless if the total supply is 0
Edited: Feb 22
trachev
OP

The issue has been incorrectly invalidated with the reasoning that if the total supply is 0 the shares are worthless. This is incorrect as the value of the shares is dependent on the total assets in the vault. Therefore, if there are assets in the vault, the value of the minted fee shares will be based on the total assets, even if the total supply is 0.

Furthermore, due to the fact that the fee shares are not properly scaled, they will lose their value once users deposit into the vault, as the shares that depositors receive from will be scaled to 9 decimals.

My apologies for posting this comment post-QA, while the judge is going through the escalations, but during QA I did not have enough time to write a PoC for this submission, and, since I was very intrigued about this report, I made some time to code a proper PoC and see what really happens when taking fees with 0 vault shares and some assets in the vault.

The result is that the shares minted to the feeRecipient will indeed lose some value after a user makes a deposit on the vault, but, this difference is minimal, for example, in the next PoC, the base asset is of 18 decimals, and, the loss of assets that can be claimed by the feeReceiver are less than 1e9.
Just to visualize how minimal the lost is, these are values of 1e18 and 1e9.

1e18 => 1000000000000000000
1e9 => 1000000000

Please use the next PoC to validate my previous claim:

Add it on the ConcreteMultiStrategyVault.t.sol test file, and run it with the command:

forge test --match-test test_PoC_submission_439 -vvvv

function test_PoC_submission_439() public {
        asset.mint(address(vault), 1 ether);

        vault.takePortfolioAndProtocolFees();

        address feeRecipient = vault.feeRecipient();
        uint256 feeRecipientShares = vault.balanceOf(feeRecipient);

        uint256 withdrawableAssetsBeforeDeposit = vault.previewRedeem(feeRecipientShares);

        asset.mint(jimmy, 1 ether);
        vm.startPrank(jimmy);

        uint256 withdrawableAssetsAfterDeposit = vault.previewRedeem(feeRecipientShares);

        assertApproxEqAbs(withdrawableAssetsBeforeDeposit, withdrawableAssetsAfterDeposit, 1e9);
        console2.log("withdrawableAssetsBeforeDeposit: ", withdrawableAssetsBeforeDeposit);
        console2.log("withdrawableAssetsAfterDeposit: ", withdrawableAssetsAfterDeposit);
}

@trachev to me this report is trying to make a Medium severity out of an edge case of the code without showing how we can end up here. I still think it should be invalidated.

Of course, we can have in theory totalAssets > 0 and totalSupply = 0 but what is a reasonable scenario that ends up here during the normal lifecycle of a vault? This report doesn't discuss this at all. I see 2 possibilities (although it's not up to me to build up such a scenario):

at initialization -> then it's of low severity as it's up to the admin to properly configure the vault
if everyone withdraws -> then the last withdrawers withdraw the remaining assets. So we need everyone to withdraw (including the admin withdrawing its previously earned fees) and someone to then make a donation to the vault. I guess in this scenario we don't really care where the donated assets go in the end.
