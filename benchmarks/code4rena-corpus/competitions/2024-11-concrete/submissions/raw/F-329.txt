S-1241
Withdrawal request cannot be claimed or finished and withdrawal queue cannot be changed for tokens with balance changes outside of transfers, such as deflationary tokens
rbserver
71
Sufficient
383d ago
Finding description and impact

According to https://github.com/code-423n4/2024-11-concrete?tab=readme-ov-file#erc20-token-behaviors-in-scope, this protocol intends to support tokens with balance changes outside of transfers, such as deflationary tokens. Yet, due to the changes of the vault's token balance held by itself and the vault's token amounts held by the strategies caused by the rebasing events, the withdrawal request, which has a stored and fixed token amount, can fail to be claimed or finished, which also causes the withdrawal queue to be unable to be changed.

Proof of Concept

When the ConcreteMultiStrategyVault._withdraw function is called, if the available assets for withdrawal is not enough to cover the assets_ input, then the withdrawalQueue.requestWithdrawal function is called to create a withdrawal request with such assets_ token amount.

https://github.com/code-423n4/2024-11-concrete/blob/91cee384d5eb5e98cfad07efd8d1c1a2ad7b8162/src/vault/ConcreteMultiStrategyVault.sol#L419-L435

    function _withdraw(uint256 assets_, address receiver_, address owner_, uint256 shares, uint256 feeShares) private {
        if (msg.sender != owner_) {
            _approve(owner_, msg.sender, allowance(owner_, msg.sender) - shares);
        }
        _burn(owner_, shares);
        if (feeShares > 0) _mint(feeRecipient, feeShares);
        uint256 availableAssetsForWithdrawal = getAvailableAssetsForWithdrawal();
        if (availableAssetsForWithdrawal >= assets_) {
            _withdrawStrategyFunds(assets_, receiver_);
        } else {
            if (address(withdrawalQueue) == address(0)) {
                revert InsufficientVaultFunds(address(this), assets_, availableAssetsForWithdrawal);
            }
@>          withdrawalQueue.requestWithdrawal(receiver_, assets_);
        }
        emit Withdraw(msg.sender, receiver_, owner_, assets_, shares);
    }

Later, the ConcreteMultiStrategyVault.batchClaimWithdrawal function would be called to further call the ConcreteMultiStrategyVault.claimWithdrawal function, which eventually calls the ConcreteMultiStrategyVault._withdrawStrategyFunds function, for claiming the stored and fixed assets_ token amount from the previously requested withdrawal.

https://github.com/code-423n4/2024-11-concrete/blob/91cee384d5eb5e98cfad07efd8d1c1a2ad7b8162/src/vault/ConcreteMultiStrategyVault.sol#L1059-L1084

When calling the ConcreteMultiStrategyVault._withdrawStrategyFunds function, the amount_ input is the previously stored and fixed assets_ token amount. However, when the token is a deflationary token, the vault's current balance of such token held by itself can be deflated to be smaller than the fixed assets_ token amount so asset_.safeTransfer(receiver_, amount_) would not be executed. Similarly, the vault's total withdrawable amount of such token held by the strategies can be deflated to be smaller than the difference between the fixed assets_ token amount and the vault's current balance of such token held by itself so diff.mulDiv(strategy.allocation.amount, MAX_BASIS_POINTS, Math.Rounding.Ceil) > withdrawable would be true for at least one strategy. This reverts the ConcreteMultiStrategyVault._withdrawStrategyFunds function call. Thus, the previously requested withdrawal with the fixed assets_ token amount cannot be claimed.

https://github.com/code-423n4/2024-11-concrete/blob/91cee384d5eb5e98cfad07efd8d1c1a2ad7b8162/src/vault/ConcreteMultiStrategyVault.sol#L444-L482

Moreover, since the previously requested withdrawal with the stored and fixed assets_ token amount cannot be claimed and finished, withdrawalQueue.unfinalizedAmount() != 0 would remain true in the ConcreteMultiStrategyVault.setWithdrawalQueue function. This would cause such function call to revert with the UnfinalizedWithdrawl error so the withdrawal queue cannot be changed as well.

https://github.com/code-423n4/2024-11-concrete/blob/91cee384d5eb5e98cfad07efd8d1c1a2ad7b8162/src/vault/ConcreteMultiStrategyVault.sol#L769-L779

    function setWithdrawalQueue(address withdrawalQueue_) external onlyOwner {

    }
Recommended mitigation steps

Like many other protocols, this protocol can consider not supporting tokens with balance changes outside of transfers.

serial-coder

This issue is not a duplicate of S-1267. S-1267 refers to a blockage attack on the withdrawal queue by a blocked recipient. Meanwhile, this issue refers to a transaction revert due to negative rebasing, which is unlikely.

Further, this issue should have LOW risk at best based on the judgment of S-1293:

None of the lenders used in the strategies accept rebase tokens. Deploying a vault that accepts rebase tokens will require a new implementation.
