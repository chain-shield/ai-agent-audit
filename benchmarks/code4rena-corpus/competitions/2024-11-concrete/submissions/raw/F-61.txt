S-554
New withdrawals can be executed before any of the already queued withdrawals.
sl1
68
Sufficient
383d ago
Bug description

When withdrawing assets from a vault, the _withdraw() function checks if there are available assets and if not, requests a withdrawal on the WithdrawalQueue contract.

ConcreteMultiStrategyVault.sol#L426-L433

if (availableAssetsForWithdrawal >= assets_) {
    _withdrawStrategyFunds(assets_, receiver_);
} else {
    if (address(withdrawalQueue) == address(0)) {
        revert InsufficientVaultFunds(
            address(this),
            assets_,
            availableAssetsForWithdrawal
        );
    }
    withdrawalQueue.requestWithdrawal(receiver_, assets_);
}

After withdrawal is registered within the queue, the amount returned by WithdrawalQueue::unfinalizedAmount() is incremented to signal the amount of assets that are yet to be finalized.

WithdrawalQueue.sol#L109-L111

function unfinalizedAmount()
    external
    view
    virtual
    onlyOwner
    returns (uint256)
{
    return
        _requests[lastRequestId].cumulativeAmount -
        _requests[lastFinalizedRequestId].cumulativeAmount;
}

Because finalizing withdrawals is a manual process and since unfinalized amount is not substracted from available assets, new withdrawals can be executed prior to the ones already queued.

ConcreteMultiStrategyVault.sol#L511-L524

function getAvailableAssetsForWithdrawal()
    public
    view
    returns (uint256 totalAvailable)
{
    totalAvailable = IERC20(asset()).balanceOf(address(this));
    uint256 len = strategies.length;
    for (uint256 i; i < len; ) {
        Strategy memory strategy = strategies[i];
        //We control both the length of the array and the external call
        //slither-disable-next-line calls-loop
        totalAvailable += strategy
            .strategy
            .getAvailableAssetsForWithdrawal();
        unchecked {
            i++;
        }
    }
    return totalAvailable;
}

Assume available assets equal 50, a user requests a withdrawal of 100 assets, and his withdrawal is registered in the queue. Available assets would still return 50 after that and this would allow another user to execute a withdrawal of 50 assets right away.

Another example would be a scenario where current available assets are 0 and there are withdrawals waiting in the queue. As stated by the docs the protocol should automatically transfer funds to the users that have withdrawals in the queue as soon as funds become available. However, that's not the case, as if new assets become available, the transaction to batchClaimWithdrawal() can still be frontrun and a new withdrawal can be executed before requested withdrawals have a chance to be finalized.
This defeats the purpose of a queue as the sequential order of withdrawals is not preserved.

Impact

New withdrawals can be executed before any of the old ones can be finalized.

Recommended Mitigation

Substracting unfinalized amounts from available assets is not enough to mitigate this issue. Ideally, no new withdrawals should be made while unfinalized is still greater than 0. To achieve this _withdraw() function of the ConcreteMultiStrategyVault can be modified in a way so it checks unfinalized amount first, and if it's positive, puts the requested withdrawal into the queue instead of executing it immediately. This change will ensure no new withdrawals can be made before the old ones are finalized and preserve the sequential order of withdrawals.

I think sponsor misunderstood this issue, therefore requesing a re-evaluation after providing further input. There is no DoS attack vector if the mitigation is implemented, it's quite the opposite as currently withdrawal queue can be DoS'ed and all of the requests there can be denied fulfillment indefinetely. The current implementation directly contradicts what's stated in the docs, and funds are not transferred nor reserved for the requestes waiting to be finalized. Because of that if admin attemps to finalize requests sitting in the queue, the call to batchClaimWithdrawals() can always be front-run.

Assume there are 100 assets worth of withdrawals waiting in the queue and 0 assets available. 100 assets become available after some time, and admin calls batchClaimWithdrawal(), but is front-run by another user with a transaction to withdraw 100 assets. This user's transaction will go through as currently getAvailableAssetsForWithdrawal() does not subtract unfinalized amounts (which is currently equal to 100), thus reducing available assets back to 0, meaning that a withdrawal that was in the queue (was attempted EARLIER than the second withdrawal) will not be finalized. This can be done perpetually and given the fact that currently there is no way to remove your withdrawal from the queue, users will be locked in the queue having no ability to withdraw their funds.

Thank you for your time!
