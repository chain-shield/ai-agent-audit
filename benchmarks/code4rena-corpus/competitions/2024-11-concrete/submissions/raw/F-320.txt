S-1189
The `ConcreteMultiStrategyVault.withdraw` does not account for the `unfinalized withdraw amount` during withdrawals
Udsen
27
Sufficient
383d ago
Finding description and impact

The ConcreteMultiStrategyVault.withdraw function is called to withdraw a specified amount of assets for the caller. During its execution flow the ConcreteMultiStrategyVault._withdraw function is called. In this function there is a check performed to ensure if the available assets to withdraw is greater than or equal to the requested amount to withdraw. If it is the case then the _withdrawStrategyFunds function is called to withdraw the requested amount from the ConcreteMultiStrategyVault contract and registered strategies and if there is not enough withdrawable assets to fulfill requested withdraw amount, withdraw request is queued in the withdrawalQueue.

The following code snippet shows the implementation of the above logic:

        uint256 availableAssetsForWithdrawal = getAvailableAssetsForWithdrawal(); //@audit-info - get the availale assets for withdrawal
        if (availableAssetsForWithdrawal >= assets_) { //@audit-info - if there is enough available assets to withdraw from 
            _withdrawStrategyFunds(assets_, receiver_);  //@audit-info - withdraw the asset amount to the receiver_
        } else { 
            if (address(withdrawalQueue) == address(0)) { //@audit-issue - The `getAvailableAssetsForWithdrawal()` function above does not account for the `withdrawalQueue.unfinalizedAmount()` amount. Thus the queued withdrawal amount is also considered available for the current withdrawal which is errorneous. 
                revert InsufficientVaultFunds(address(this), assets_, availableAssetsForWithdrawal);
            } 
            withdrawalQueue.requestWithdrawal(receiver_, assets_); //@audit-info - else queue the withdrawal requests to the withdrawal queue
        } 

The getAvailableAssetsForWithdrawal is as follows:

    function getAvailableAssetsForWithdrawal() public view returns (uint256 totalAvailable) {
        totalAvailable = IERC20(asset()).balanceOf(address(this));
        uint256 len = strategies.length;
        for (uint256 i; i < len; ) {
            Strategy memory strategy = strategies[i];
            //We control both the length of the array and the external call
            //slither-disable-next-line calls-loop
            totalAvailable += strategy.strategy.getAvailableAssetsForWithdrawal();
            unchecked { //@audit-info - get the available assets for withdrawal of each strategy
                i++;
            }
        } //@audit-issue - We are not accounting for the unfinalized asset amount for withdrawal in the queue and that amount should be deducted from `totalAvailable` amount
        return totalAvailable;
    }

As per the above getAvailableAssetsForWithdrawal calculation the returned value does not account for the unfinalizedAmount of underlying asset of the withdrawalQueue. As a result the getAvailableAssetsForWithdrawal function returns the totalAvailable amount. Hence the if (availableAssetsForWithdrawal >= assets_) check performed in the _withdraw() function is incorrect since assets_ amount is compared against a large availableAssetsForWithdrawal value instead of the correct value (correct value is availableAssetsForWithdrawal - unfinalizedAmount). As a result the later withdrawers has the ability to withdraw their respective withdrawal amounts using the liquidity that should have been reserved for the queued withdrawals in the withdrawalQueue. As a result the withdrawals in the withdrawalQueue can be delayed for an extended period to be claimed.

Recommended mitigation steps

Hence it is recommended to update the if (availableAssetsForWithdrawal >= assets_) check in the ConcreteMultiStrategyVault._withdraw function to if (availableAssetsForWithdrawal - withdrawalQueue.unfinalizedAmount() >= assets_) to ensure that the queued withdrawals are not affected by the later withdrawers and the withdrawals in the withdrawalQueue can be claimed in a timely manner.
