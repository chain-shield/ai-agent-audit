S-1293
`WithdrawalQueue` does not work with rebasing or airdrop tokens
serial-coder
78
Sufficient
383d ago
Finding Description

Note: per the contest's readme, any ERC20 tokens with balance modifications outside of the transfers (rebasing/airdrops) are in scope.

When a user calls the ConcreteMultiStrategyVault contract's redeem() or withdraw() to burn their shares for withdrawing assets, if available assets are less than the expected amount to withdraw, the user's withdrawal request will be enqueued for later withdrawal through the WithdrawalQueue contract.

The WithdrawalQueue will record the expected asset amount to withdraw. Once sufficient assets are available, the recipient will later receive the expected amount of assets when an admin executes the batchClaimWithdrawal().

Assume that the underlying asset is a rebasing (or airdrop) token. If the token balance changes due to rebasing or airdrop events while the withdrawal request is pending in the queue, the recipient will receive the same amount of assets as when the request was created. This can have a negative impact on the recipient or other users who are staking assets in the vault.

Finding Impact

Rebasing or airdrop events on the vault's underlying asset (while the asset withdrawal request is pending in the queue) can cause a negative impact on the asset recipient or other users staking assets in the vault.

In the case of profit rebasing or airdrop, the asset balance is increased. The recipient will receive fewer assets than they should, like the recipient eating the loss compared to a direct call to redeem() or withdraw().

Conversely, in the case of loss rebasing, the asset balance is decreased. The recipient will receive more assets than they should, like hedging against loss. A clever investor can exploit this vulnerability to guarantee their position not to eat or limit the loss and pass the loss on to other users who are staking assets in the vault.

Proof of Concept

This section will walk you through the code.

The redeem() and withdraw() will internally call the _withdraw() to burn the user's shares (see @1) for withdrawing underlying assets.

If available assets are less than the expected amount, the _withdraw() will execute the withdrawalQueue::requestWithdrawal() (@2) to enqueue the request for later withdrawal. The requestWithdrawal() will record the expected asset amount in terms of the cumulative amount (@3).

    function _withdraw(uint256 assets_, address receiver_, address owner_, uint256 shares, uint256 feeShares) private {
        if (msg.sender != owner_) {
            _approve(owner_, msg.sender, allowance(owner_, msg.sender) - shares);
        }
        //@audit -- The redeem() and withdraw() internally call the _withdraw() to 
        //          burn the user's shares for withdrawing underlying assets.
@1      _burn(owner_, shares);

        if (feeShares > 0) _mint(feeRecipient, feeShares);
        uint256 availableAssetsForWithdrawal = getAvailableAssetsForWithdrawal();
        if (availableAssetsForWithdrawal >= assets_) {
            _withdrawStrategyFunds(assets_, receiver_);
        } else {
            if (address(withdrawalQueue) == address(0)) {
                revert InsufficientVaultFunds(address(this), assets_, availableAssetsForWithdrawal);
            }
            //@audit -- If available assets are less than the expected amount,
            //          the _withdraw() will execute the withdrawalQueue::requestWithdrawal()
            //          to enqueue the request for later withdrawal.
@2          withdrawalQueue.requestWithdrawal(receiver_, assets_);
        }
        emit Withdraw(msg.sender, receiver_, owner_, assets_, shares);
    }

    // FILE: https://github.com/code-423n4/2024-11-concrete/blob/main/src/queue/WithdrawalQueue.sol
    function requestWithdrawal(address recipient, uint256 amount) external virtual onlyOwner {
        uint256 _lastRequestId = lastRequestId;
        WithdrawalRequest memory lastRequest = _requests[_lastRequestId];

        //@audit -- The requestWithdrawal() will record the asset amount for later withdrawal
        //          in terms of the cumulative amount.
@3      uint128 cumulativeAmount = lastRequest.cumulativeAmount + SafeCast.toUint128(amount);

        uint256 requestId = _lastRequestId + 1;
        lastRequestId = requestId;
        WithdrawalRequest memory newRequest = WithdrawalRequest(
            cumulativeAmount,
            recipient,
            uint40(block.timestamp),
            false
        );
        _requests.push(newRequest);
        assert(_requestsByOwner[recipient].add(requestId));
        emit WithdrawalRequested(requestId, msg.sender, recipient, amount);
    }

Once an admin executes the batchClaimWithdrawal(), the function will call the claimWithdrawal().

The claimWithdrawal() will load the withdrawal-request details (e.g., recipient, amount, etc.) (@4) via the withdrawalQueue::prepareWithdrawal(). The loaded amount will always be a static value. Hence, if the underlying asset is a rebasing or airdrop token and its balance changes while the withdrawal request is pending in the queue, the recipient will receive the same amount of assets as when the request was created.

Finally, the claimWithdrawal() invokes the _withdrawStrategyFunds() (@5) to transfer the assets (static amount) to the recipient.

Recommended Mitigation Steps

Improve the WithdrawalQueue to support rebasing and airdrop tokens (e.g., burning shares and withdrawing assets when the withdrawal request is claimed; however, this may introduce other security issues that may require considering the secure-by-design principles) or do not support these kinds of asset tokens.
