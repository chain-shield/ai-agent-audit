S-1228
In `ConcreteMultiStrategyVault.harvestRewards` function, there could be multiple entries of the same `rewardToken` into the `rewardAddresses` array
Udsen
27
Sufficient
383d ago
Finding description and impact

The ConcreteMultiStrategyVault.harvestRewards function harvestRewards from each of the registered strategies and then adds the rewardTokens returned from the respective strategy to the rewardIndex mapping if the rewardIndex[rewardToken] == 0 as shown below :

                if (amount != 0) {
                    if (rewardIndex[rewardToken] == 0) rewardAddresses.push(rewardToken); 
                    rewardIndex[rewardToken] += amount.mulDiv(PRECISION, totalSupply, Math.Rounding.Floor);
                }                     

But the issue is the same rewardToken can be added multiple times into the rewardAddresses array, if the amount.mulDiv(PRECISION, totalSupply, Math.Rounding.Floor) calculation rounds down to 0.

This can happen in the following scenario:

The concrete protocol can work with tokens which has decimals > 18.
If there is a token with 28 decimals then the vault shares will have (28 + 9) 37 decimals.
If the rewardToken has an amount = 1 wei then the above calculation wll round down to zero since 1 * 1e36 / 1e37 rounds down to zero. Since amount != 0 the rewardToken is added into the rewardAddresses array. But due to the rounding down to zero in the above calculation still the rewardIndex[rewardToken] == 0 and if the same reward token is quried next time it will again be added to the rewardAddresses array since the rewardIndex[rewardToken] == 0 is satisfied.
As a result the same rewardToken can be added multiple times to the rewardAddresses array.

This will cause the ConcreteMultiStrategyVault.getUserRewards() to return the same rewardToken multiple times in the returned ReturnedRewards[] array thus leading to erroneous results for the user who calls the getUserRewards() function.

This will further cause the rewardAddresses array to grow with redundant data which could lead to inefficiencies such as gas costs and in the worst case DoS due to Tx or block gas limit exceed if this array grows very large in the future. It is worth to note there is no logic to remove elements from the rewardAddresses array. Hence it is important to insert only valid reward tokens to the rewardAddresses array.

Proof of Concept
                if (amount != 0) {
                    if (rewardIndex[rewardToken] == 0) rewardAddresses.push(rewardToken);
                    rewardIndex[rewardToken] += amount.mulDiv(PRECISION, totalSupply, Math.Rounding.Floor);
                }

https://github.com/code-423n4/2024-11-concrete/blob/main/src/vault/ConcreteMultiStrategyVault.sol#L1012-L1015

Recommended mitigation steps

Hence it is recommended to use a address -> boolean mapping and make it true for a particular rewardToken when it is added. And for every new reward token being added this mapping should be checked to see if the particular rewardToken has previously been added. This logic can be used in place of the rewardIndex[rewardToken] == 0 which can round down and cause double entry into the rewardAddresses array as explained above.
