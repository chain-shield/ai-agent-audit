S-1104
`withdrawalQueue` burns users' shares while still lending out the user's assets, causing loss of yield for users in the withdrawal queue
rscodes
92
Sufficient
383d ago
Vulnerability Details

When an user trys to withdraw but there isnt enough liquidity, the order gets sent to the withdrawal queue.

function _withdraw(uint256 assets_, address receiver_, address owner_, uint256 shares, uint256 feeShares) private {
        if (msg.sender != owner_) {
              _approve(owner_, msg.sender, allowance(owner_, msg.sender) - shares);
        }
1.)-->  _burn(owner_, shares);
        if (feeShares > 0) _mint(feeRecipient, feeShares);
        uint256 availableAssetsForWithdrawal = getAvailableAssetsForWithdrawal();
        if (availableAssetsForWithdrawal >= assets_) {
              _withdrawStrategyFunds(assets_, receiver_);
        } else {
              if (address(withdrawalQueue) == address(0)) {
                  revert InsufficientVaultFunds(address(this), assets_, availableAssetsForWithdrawal);
              }
 2.)-->       withdrawalQueue.requestWithdrawal(receiver_, assets_);
        }
        emit Withdraw(msg.sender, receiver_, owner_, assets_, shares);
}

As shown, regardless of whether the user gets their withdrawal processed immediately or if their order has been sent to the queue, the code burns their shares.

This leads to loss of yield for the users as their assets are still being lent out (which is why they cannot withdraw). By burning their shares they will not be able to receive the yield from their assets that are still being lent out.

Impact

Let's put that in diagram form:

          |---------------------------------|----------------------------------|----------------------|
       Time 0                             Time X                             Time Y                 Time Z
Alice deposits 10ether     Vault lends Alice's assets to ClaimRouter  Alice calls withdraw   CR repays debt + reward


At time Y, after Alice calls withdraw, the order will be sent to the withdrawalQueue as Alice's assets are being lent out and can't be withdrawn immediately.

However, the code burns all of Alice's shares, causing Alice to lose all the yield from Time X to Time Z.

Since Alice's assets was being lent out from time X to time Z, it is rightful for Alice to receive yield/rewards during that time period since the yield/rewards was generated from her tokens being lent out

Note that I am just using lending to ClaimRouter as an example, it could also be lending on individual strategies(like Aave).

In that case all reward distribution by individual strategies during time Y to Z, which is through harvestRewards, will end up not distributing any rewards to Alice even though it is Alice's tokens that are still being lent out, as Alice has not legitimately withdrew yet (only waiting in the queue, thats all)

This is because distribution of rewards from individual strategies use userBalance of shares to distribute, and since withdrawalQueue has prematurely burned all of Alice's shares, the vault gets to lend out Alice's tokens without giving Alice any reward.

As shown, instead of getting 15 ether, Alice only gets back her original balance which is 10 ether. Despite lending out Alice's tokens the whole time, Alice fully loses the 5 ether yield.

Recommendation

Don't burn the shares immediately.

Note that instead of pushing in the amount of assets, withdrawalQueue should push in the amount of shares instead. (This is because assets can change during the actual withdrawal just like the example i provided above)

Only during the actual withdrawal, read the shares that are pushed into the queue, then burn it.
