S-1270
Insufficient withdrawal liquidity of some `Strategies` can break users' legit withdrawals
serial-coder
78
Sufficient
383d ago
Finding Description

The ConcreteMultiStrategyVault::getAvailableAssetsForWithdrawal() returns the sum of all available assets for withdrawal across all strategies, including the floating assets residing in the vault. This returned value only represents the total (overall) amount of available assets. However, it cannot guarantee that every strategy will always have sufficient available assets for withdrawal in proportion to its assigned asset allocation percentage at all times.

When transferring assets to a user, the ConcreteMultiStrategyVault::_withdrawStrategyFunds() calculates the asset amount to withdraw (amountToWithdraw) from each strategy according to its assigned asset allocation percentage. If the resulting amountToWithdraw is greater than the strategy's available assets, the transaction will be reverted.

The root cause of this issue stems from the imbalance between the available asset amount and the asset allocation percentage of each strategy. The issue can occur even if the expected amount of assets to withdraw is less than the total amount of available assets.

Please refer to the Proof of Concept and Coded PoC sections for details.

Finding Impact

This issue breaks the protocol's core functionality. Users may not be able to withdraw their assets (via the withdraw(), redeem(), or batchClaimWithdrawal()) even if their expected amount of assets is legit and less than the total amount of available assets.

Proof of Concept

This section will walk you through the code.

As described previously, the getAvailableAssetsForWithdrawal() (@1) returns the sum of all available assets for withdrawal across all strategies, including the floating assets residing in the vault. This returned value only represents the total (overall) amount of available assets. However, it cannot guarantee that every strategy will always have sufficient available assets for withdrawal in proportion to its assigned asset allocation percentage at all times.

The _withdraw() will execute the _withdrawStrategyFunds() (@2) to transfer assets to a receiver as long as the total amount of available assets is greater than or equal to the expected amount of assets regardless of the balance between the available asset amount and the asset allocation percentage of each strategy.

Then, the _withdrawStrategyFunds() will calculate the asset amount to withdraw (amountToWithdraw (@3)) from each strategy according to its assigned asset allocation percentage.

If the resulting amountToWithdraw is greater than the strategy's available assets, the transaction will be reverted (@4). This issue can occur even if the expected amount of assets to withdraw is less than the total amount of available assets if some strategies' available asset amount and asset allocation percentage are imbalanced.

1. The main test function

The PoC shows that Jimmy deposits 100 ether into the Vault. The Vault then distributes all deposited assets to Strategy0 and Strategy1, 50 ether each. In other words, each strategy has an asset allocation percentage of 50% equally.

Later on, the PoC demonstrates that if Strategy0 locks 30 ether of the deposited assets for its use (i.e., there are only 20 ether left for withdrawal for Strategy0), the total amount of available assets returned from the vault.getAvailableAssetsForWithdrawal() is 70 ether left, which is the correct value.

For this reason, if Jimmy wants to withdraw 45 ether from the Vault, it should work because there are 70 ether available for withdrawal in total. However, due to the protocol's design flaw, the transaction is reverted because the expected amount to withdraw from Strategy0 is 22.5 ether, whereas Strategy0 has only 20 ether available for withdrawal.

function test_poc_insufficient_liquidity_strategy_breaks_legit_withdrawal() public {
    _setup();

    // Mint 100 ether for Jimmy
    asset.mint(jimmy, 100 ether);
    assertEq(asset.balanceOf(jimmy), 100 ether, "Mint 100 ether");

    // Jimmy deposits 100 ether
    vm.startPrank(jimmy);
    asset.approve(address(vault), 100 ether);
    vault.deposit(100 ether, jimmy);
    vm.stopPrank();

    // Asset distribution percentages for the Strategy0 and Strategy1 are 50% equally
    assertEq(asset.balanceOf(address(strategies[0].strategy)), 50 ether, "Strategy0's asset balance");
    assertEq(asset.balanceOf(address(strategies[1].strategy)), 50 ether, "Strategy1's asset balance");
    assertEq(asset.balanceOf(address(vault)), 0, "Vault's asset balance");

    // Assume the available assets managed by Strategy0 are only 20 ether left
    // Set the Strategy0 to lock 30 ether (now, available assets for withdrawal are only 20 ether)
    IStrategyModified(address(strategies[0].strategy)).setAvaliableAssetLessThanOrEqualTo20e18(true);
    assertEq(
        IMockStrategy(address(strategies[0].strategy)).getAvailableAssetsForWithdrawal(), 
        20 ether, 
        "Strategy0's available assets for withdrawal"
    );

    // Set the Strategy1 to lock 0 ether (so available assets for withdrawal are all 50 ether)
    IStrategyModified(address(strategies[1].strategy)).setAvaliableAssetLessThanOrEqualTo20e18(false);
    assertEq(
        IMockStrategy(address(strategies[1].strategy)).getAvailableAssetsForWithdrawal(), 
        50 ether, 
        "Strategy1's available assets for withdrawal"
    );

    // Total available assets for withdrawal (across all Strategies) are 70 ether
    assertEq(
        vault.getAvailableAssetsForWithdrawal(), 
        70 ether, 
        "Total available assets for withdrawal (across all Strategies)"
    );

    // Withdraw 45 ether (it should work because there are 70 ether available for withdrawal in total)
    //
    // However, due to the design flaw, the transaction is expected to be reverted!!!
    vm.expectRevert(
        abi.encodeWithSelector(
            ERC4626.ERC4626ExceededMaxWithdraw.selector,
            address(vault),
            22.5 ether, // Expect to withdraw 22.5 ether from Strategy0
            20 ether    // Strategy0 has only 20 ether available
        )
    );
    vm.prank(jimmy);
    vault.withdraw(45 ether, jimmy, jimmy);
}

## Recommended Mitigation Steps

Implement a fallback mechanism to handle this strategy's asset availability vs. asset allocation imbalance vulnerability.
