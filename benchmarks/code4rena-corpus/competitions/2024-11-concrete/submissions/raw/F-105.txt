S-354
loss of assets for Recipient due to rounding issues when redeeming
Sancybars
20
Insufficient
383d ago
Vulnerability Discussion
    function redeem(
        uint256 shares_,
        address receiver_,
        address owner_
    ) public override nonReentrant whenNotPaused returns (uint256 assets) {
        if (receiver_ == address(0)) revert InvalidRecipient();
        if (shares_ == 0) revert ZeroAmount();
        if (shares_ > maxRedeem(owner_)) revert MaxError();

        uint256 feeShares = shares_.mulDiv(uint256(fees.withdrawalFee), MAX_BASIS_POINTS, Math.Rounding.Ceil);

        assets = _convertToAssets(shares_ - feeShares, Math.Rounding.Floor);//@audit-issue should round up

        _withdraw(assets, receiver_, owner_, shares_, feeShares);
    }

The amount of assets to send to the recipient is rounded downassets = _convertToAssets(shares_ - feeShares, Math.Rounding.Floor); due to this users/recipients will lose assets if the asset amount is rounded down to zero.

POC

This test will be in two phases, first redeeming with rounding down to show the loss of assets using the feeRecipient as the redeemer.

in this case we rounded up and the recipient got the asset.

In scenarios where the feeRecipients share results in fractional assets (e.g., 0.99 assets), these are rounded down to 0. This causes the feeRecipient to lose their accumulated assets entirely, which is an unintended and unfair behavior.

Recommendation

round up instead of down when calculating the assets amount.
assets = _convertToAssets(shares_ - feeShares, Math.Rounding.Ceil);
