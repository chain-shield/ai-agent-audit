S-885
Radiant Token Is Upgradeable And IncentiveController Could Be Changed In The Future
EPSec
88
Sufficient
383d ago
Finding description and impact

The RadiantV2Strategy contract interacts with the rToken (Radiant's AToken implementation), specifically using its getIncentivesController() function to fetch the incentives controller. However, the incentiveController is stored in memory during initialization instead of dynamically fetched whenever required. Since rToken is part of an upgradeable system, its incentives controller can be updated, leading to potential inconsistencies in reward distribution.

The relevant code in AToken.sol shows the getIncentivesController() function, which is subject to change:

function getIncentivesController() external view override returns (address) {
    return _incentivesController;
}

This design assumes the incentiveController will remain static, which may not always be the case.

Incorrect Rewards: Rewards may not be calculated or distributed correctly.

Operational Risks: Strategies dependent on this contract may malfunction if incentives are updated.

Proof of Concept

In RadiantV2Strategy, the incentiveController is fetched once during the constructor:

incentiveController = IChefIncentivesController(rToken.getIncentivesController());

If _incentivesController in AToken is updated, the strategy will still point to the outdated controller, causing incorrect reward calculations, missed updates, or operational failures.

Recommended Mitigation Steps

Refactor the code to dynamically fetch the incentiveController when needed:

function _getCurrentIncentiveController() internal view returns (IChefIncentivesController) {
    return IChefIncentivesController(rToken.getIncentivesController());
}

Update all reward-related functions to call _getCurrentIncentiveController() instead of using a stored reference. This ensures compatibility with future updates to the AToken's incentives controller.
