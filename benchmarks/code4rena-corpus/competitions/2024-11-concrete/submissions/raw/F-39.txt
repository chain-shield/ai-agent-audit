S-947
Missing validation for `ctAssetToken_` in `swapTokensForReward` allows attacker to drain treasury account of reward tokens
nnez
87
Sufficient
383d ago
Impact

The vulnerability allows malicious actors to exploit the swapTokensForReward function by supplying a malicious vault token (ctAssetToken_). By manipulating the convertToAssets function of the fake vault, attackers can inflate the converted asset amount arbitrarily. This inflated amount can then be used to claim excessive amounts of registered reward tokens from the treasury.

Description

Swapper contract allows users to swap their ctAssetToken for a registered reward token held in the treasury by invoking swapTokensForReward function.

See: https://github.com/code-423n4/2024-11-concrete/blob/main/src/swapper/Swapper.sol#L78-L98

// File: 2024-11-concrete/src/swapper/Swapper.sol
function swapTokensForReward(
    address ctAssetToken_,
    address rewardToken_,
    uint256 ctAssetAmount_
) external nonReentrant {
    if (!_tokenRegistry.isRewardToken(rewardToken_)) revert Errors.NotValidRewardToken(rewardToken_);

    uint256 rewardAmount = _quoteSwapFromCtAssetToReward(ctAssetToken_, rewardToken_, ctAssetAmount_);

    if (!amountAvailableForWithdrawal(rewardToken_, rewardAmount)) {
        revert Errors.NotAvailableForWithdrawal(rewardToken_, rewardAmount);
    }

    // first send the ctAsset tokens to the treasury
    IERC20(ctAssetToken_).safeTransferFrom(msg.sender, address(_treasury), ctAssetAmount_);
    // this isn't an issue because the msg,sender first need to pay with the ctAsset token
    // slither-disable-next-line arbitrary-send-erc20
    IERC20(rewardToken_).safeTransferFrom(address(_treasury), msg.sender, rewardAmount);

    emit Swapped(msg.sender, ctAssetToken_, rewardToken_, ctAssetAmount_, rewardAmount);
}

The function works as follows:

Reward token validation
The function first checks if the reward token provided is registered in the TokenRegistry contract. Only registered tokens are eligible for reward swaps.
Conversion to stable amount
The _convertFromCtAssetTokenToStable function is used to convert the user's ctAssetToken_ amount into its stablecoin equivalent.
The conversion involves:
Retrieving the underlying asset of the ctAssetToken_ using the asset() function.
Converting the ctAssetAmount_ into the amount of the underlying asset using convertToAssets().
Converting the underlying asset amount to stable amount using price from Oracle.
Reward calcuation
The stablecoin amount is used to calculate the reward rate and determine the amount of reward token to transfer.

The issue lies in the lack of validation for ctAssetToken_ in _convertFromCtAssetTokenToStable.
See: https://github.com/code-423n4/2024-11-concrete/blob/main/src/swapper/OraclePlug.sol#L57-L67

File: 2024-11-concrete/src/swapper/OraclePlug.sol
function _convertFromCtAssetTokenToStable(
    address ctAssetToken_,
    uint256 ctAssetAmount_
) internal view returns (uint256 stableAmount) {
    // get asset and amount from ctAssetToken
    IERC4626 vaultToken = IERC4626(ctAssetToken_);
    address asset = vaultToken.asset();
    uint256 assetAmount = vaultToken.convertToAssets(ctAssetAmount_);
    // convert assetAmount to stable
    stableAmount = _convertFromTokenToStable(asset, assetAmount);
}

An attacker can supply a malicious vault token that:

Implements the IERC4626 interface.
Returns a legitimate asset from asset().
Manipulates the convertToAssets() function to return an arbitrarily inflated value.

As a result, attacker can drain all reward tokens from treasury account using a fake vault.

Proof-of-Concept

The following test creates a malicious contract that returns legitimate asset and arbitrary amount when calling convertToAssets then use it to swap for reward token via Swapper contract.

It does so by adding an attack scenario at the end of test_swapTokensForReward as this can be seen as a legitimate setup of Swapper contract.
