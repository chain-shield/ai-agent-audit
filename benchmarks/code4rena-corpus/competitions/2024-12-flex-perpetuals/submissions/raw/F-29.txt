Low Justification Rationale
Edited: Feb 22
0xsomeone

The submission and its duplicates outline that the AerodromeDexter is incompatible with fee-on-transfer / rebasing tokens. While the documentation of the project outlines that all types of tokens are supported, this broad recommendation does not necessarily apply to every contract on the codebase (as different contracts within the same project could be present to accommodate each use case).

In this particular instance, fee-on-transfer tokens are not de-facto expected to be supported by the AerodromeDexter and the codebase does not seem to indicate that a FOT token is meant to be used with the contract. I was unable to find any concerns around FOT tokens on the audits performed in the system, on the documentation of the project, and on its forked project's resources. Thus, I conclude that support for FOT tokens is not meant to be present in the current version of the codebase on this particular module.

Even if we consider that support was meant to be present, the maximum impact of this exhibit would be failed AMM interactions that, as aforementioned, are not integral to any canonical execution flow of the Flex Perpetuals system. Unless demonstrated otherwise, these conclusions render the submission to be a valid albeit low-severity observation in the codebase.

Valid but inflated
Edited: Feb 22
0xRobocop

The report is valid; however, I doubt the severity is greater than low, as the AerodromeDexter contract is merely a configuration parameter that can be changed at any time by the owner if support for FOT is deemed crucial.

The report fails to provide evidence of a more serious impact, such as a loss of funds. For instance, it does not explain whether anyone would have lost funds due to the unknown fact that the code does not actually support FOT tokens.
