The AerodromeDexter.sol contract doesn't support tokens that revert on large approvals
alix40
68
Sufficient
383d ago
Finding description and impact

The AerodromeDexter.sol contract doesn't support tokens that revert on large approvals and/or transfers
As mentioned in the readme such tokens are in scope

Proof of Concept

Revert on large approvals
https://github.com/code-423n4/2024-12-flex-perpetuals/blob/b84a0812c3368866964b8a16e7c36f6e7a50b655/src/extensions/dexters/AerodromeDexter.sol#L39-L53

    function run(
        address _tokenIn,
        address _tokenOut,
        uint256 _amountIn
    ) external override returns (uint256 _amountOut) {
        // Check
        if (routeOf[_tokenIn][_tokenOut].length == 0) {
            revert AerodromeRouterSwitchCollateralExt_BadPath();
        }

        // Approve tokenIn to Router if needed
        ERC20 _tIn = ERC20(_tokenIn);
        if (_tIn.allowance(address(this), address(router)) < _amountIn)
            _tIn.safeApprove(address(router), type(uint256).max);
        // Approve UniUniversalRouter to spend tokenIn in Permit2 if needed

The problem arises from the fact that especially when we will try to swap such tokens the first time, (allowance is 0) we will call approve with type(uint256).max), which will revert.
e.g for UNI, the max allowed value is uin96.max, trying to approve more will revert.

Recommended mitigation steps

Approve exact amount of tokens each time instead of max

    function run(
        address _tokenIn,
        address _tokenOut,
        uint256 _amountIn
    ) external override returns (uint256 _amountOut) {
        // Check
        if (routeOf[_tokenIn][_tokenOut].length == 0) {
            revert AerodromeRouterSwitchCollateralExt_BadPath();
        }

        // Approve tokenIn to Router if needed
        ERC20 _tIn = ERC20(_tokenIn);
-        if (_tIn.allowance(address(this), address(router)) < _amountIn)
-            _tIn.safeApprove(address(router), type(uint256).max);
+        _tIn.safeApprove(address(router), _amountIn);
        // Approve UniUniversalRouter to spend tokenIn in Permit2 if needed

Low Justification Rationale
Edited: Feb 22
0xsomeone

The submission and its duplicates attempt to formulate a vulnerability around the lack of accommodation for tokens that revert on large approvals in the AerodromeDexter.

I believe that this particular concern is inexistent as the token referenced (UNI) will properly handle approval of type(uint256).max by replacing it with type(uint96).max and most tokens demonstrate this behavior. Additionally, I could not find evidence that such tokens are explicitly meant to be supported by the AerodromeDexter, and do not foresee that this issue would result in any severity beyond QA (L).

Valid but inflated
Edited: Feb 22
0xRobocop

The finding seems valid and the README does say this behavior is in scope. However, I think the finding is inflated and should be low.

Only one token is presented as evidence to not work with the current code. Also the report fails to describe or provide an analysis on how this issue impacts the protocol security and not a mere UX problem.

In other words, by only relying on the explanation given in this report, it seems that the problem is that users will not be able to use the run function to swap the UNI token.
