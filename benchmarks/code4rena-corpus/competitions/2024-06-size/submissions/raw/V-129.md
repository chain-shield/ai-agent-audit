# Vulnerability details

## Impact
A malicious user can easily exploit the logic in `AccountingLibrary :: getCreditAmountIn()`, especially he will utilize the `credit fractionalization` logic in order to get even higher `creditAmountIn` than what he could have got under the `no credit fractionalization` logic, which was supposed to be the max he could be able to get (invariant breached). To summarize, this malicious user has a way to spend less cash but get more credit, which directly leads to wrong accounting and will impact the counterparty users.

## Proof of Concept
Just look at this relevant piece of logic, it's easy math:

```
       if (maxCashAmountOut >= state.feeConfig.fragmentationFee) {
            maxCashAmountOutFragmentation = maxCashAmountOut - state.feeConfig.fragmentationFee;
        }

        // slither-disable-next-line incorrect-equality
        if (cashAmountOut == maxCashAmountOut) {
            // no credit fractionalization

            creditAmountIn = maxCredit;
            fees = Math.mulDivUp(cashAmountOut, swapFeePercent, PERCENT);
        } else if (cashAmountOut < maxCashAmountOutFragmentation) {
            // credit fractionalization

            creditAmountIn = Math.mulDivUp(
                cashAmountOut + state.feeConfig.fragmentationFee, PERCENT + ratePerTenor, PERCENT - swapFeePercent
            );
            fees = Math.mulDivUp(cashAmountOut, swapFeePercent, PERCENT) + state.feeConfig.fragmentationFee;
        }
```

The malicious user can use a number for `cashAmountOut` which is just extremely slightly smaller than `maxCashAmountOutFragmentation`, like only `1 wei` smaller, then it gets into the `credit fractionalization` logic.

Then, let's look at what's the calculation inside the Math.mulDivUp():

1. `cashAmountOut + state.feeConfig.fragmentationFee` --- because `cashAmountOut` is just slightly smaller than `maxCashAmountOutFragmentation`, so the `cashAmountOut + state.feeConfig.fragmentationFee` makes it approximately equal to the `maxCashAmountOut`, just slightly smaller.

2. `PERCENT + ratePerTenor` and `PERCENT - swapFeePercent` --- it's obvious that the `PERCENT + ratePerTenor` must be larger than `PERCENT - swapFeePercent`

So, the `mulDivUp()` calculation can easily produce a `creditAmountIn` number which is even larger than the one from the `no credit fractionalization` situation (`maxCredit`), and this means the invariant has been breached. Moreover, the user provided less cash in the `credit fractionalization` than he has to if in the `no credit fractionalization`, as there at least a reduced amount of `state.feeConfig.fragmentationFee`. So, he effectively stole some extra credit into his pocket.

## Tools Used
Manual review.

## Recommended Mitigation Steps
Use a wider buffer between the determination of `no credit fractionalization` and `credit fractionalization`. Do now use `cashAmountOut < maxCashAmountOutFragmentation` for that `else if` clause.
