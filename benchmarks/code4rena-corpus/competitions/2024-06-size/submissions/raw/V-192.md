# Vulnerability details

## Impact
This does Not actually affect the protocol funds or smomething, But users mistakenly sent funds  are swept away and also users who promptly notice will try calling the function right away, thus creating a sufficient congestion.

## Proof of Concept
The [deposit](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/Size.sol#L153) function of the `size.Sol` allow users to deposit funds(`collateral` or `borrow token)` into the protocol.

we can see the actual implementation of the [executedDeposit](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/Deposit.sol#L64) function of the `Deposit.Sol`  library :

```js
function executeDeposit(State storage state, DepositParams calldata params) public {
        address from = msg.sender;
        uint256 amount = params.amount;
        if (msg.value > 0) {
            // do not trust msg.value (see `Multicall.sol`)
            amount = address(this).balance;
            // slither-disable-next-line arbitrary-send-eth
            state.data.weth.deposit{value: amount}();
            state.data.weth.forceApprove(address(this), amount);
            from = address(this);
        }

        if (params.token == address(state.data.underlyingBorrowToken)) {
            state.depositUnderlyingBorrowTokenToVariablePool(from, params.to, amount);
            // borrow aToken cap is not validated in multicall,
            //   since users must be able to deposit more tokens to repay debt
            if (!state.data.isMulticall) {
                state.validateBorrowATokenCap();
            }
        } else {
            state.depositUnderlyingCollateralToken(from, params.to, amount); // 
        }

        emit Events.Deposit(params.token, params.to, amount);
    }
```
What can possibly go wrong here? We can see from the implementation that if the `msg.value` is > `0` the amount variable is being updated to `address(this).balance` (ETH balance of the contract).

This means an attacker or even a normal user can call the `deposit` function  with 1 `wei` and also same with `param.amount` ( to not have problem with validate), this will allow the caller to mint a collateral amount that didn't correspond to what he/she deposited if there's a balance of ether within the contract.

Scenario where `Ether` can be in the contract:

1. It is so normal for users to mistakenly sent ether directly to a contract


Consider this:

>An attacker or a user call the `deposit` function with `1 wei` of ether.

>And also to say there's a thousand `ether` sent mistakenly by other users.

>This will allow the attacker to mint a `collateral token` ( which correspond to ether deposited) more than that of the amount he actually deposited.


This happens due to the change in `amount`  variable to the balance of the contract:
```

if (msg.value != 0 && (msg.value != params.amount || params.token != address(state.data.weth))) {
            revert Errors.INVALID_MSG_VALUE(msg.value);
        }
```
