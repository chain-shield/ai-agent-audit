# Vulnerability details

## Summary

A critical vulnerability exists in the Size protocol's fee calculation mechanism, enabling attackers to manipulate the swap fee calculation, thereby significantly reducing borrowing costs. This exploit leverages the computation of the swap fee within the `getSwapFee` function, allowing malicious actors to avoid proper fees, resulting in considerable financial loss for the protocol and an unfair advantage for attackers.

## Vulnerability Detail

The exploit leverages the calculation of the swap fee in the `getSwapFee` and related functions. By carefully choosing the `tenor` and manipulating the input values, an attacker can create conditions where the fees calculated are lower than intended, thus avoiding the full fee mechanism.

1. **Swap fee calculation mechanism**:

- The swap fee is calculated based on the tenor and the cash amount involved in the transaction.
- The formula used for fee calculation is:

```solidity
function getSwapFee(State storage state, uint256 cash, uint256 tenor) internal view returns (uint256) {
    return Math.mulDivUp(cash, getSwapFeePercent(state, tenor), PERCENT);
}
```
- This function takes into account the cash amount and the tenor to compute the fee, using the `Math.mulDivUp` function.

- The `getSwapFeePercent` function calculates the fee percentage based on the tenor:

```solidity
function getSwapFeePercent(State storage state, uint256 tenor) internal view returns (uint256) {
    return Math.mulDivUp(state.feeConfig.swapFeeAPR, tenor, YEAR);
}
```

The `Math.mulDivUp` function performs the multiplication and division:

```solidity
function mulDivUp(uint256 x, uint256 y, uint256 z) internal pure returns (uint256) {
    return FixedPointMathLib.mulDivUp(x, y, z);
}
```

2. **Manipulation strategy**:

- The attacker manipulates the `cash` parameter and sets the tenor to the minimum value such that the resulting fee is reduced.
- By choosing a specific cash amount just below the threshold and setting the tenor to certain values, the multiplication and division operations in the fee calculation can be manipulated to produce a reduced fee.
- For example, setting the cash amount to a value where the product of `cash * getSwapFeePercent(state, tenor)` is slightly less than what would trigger the higher fee bracket results in a lower fee due to integer division rounding down. This is achieved through manipulation of the integer division and multiplication operations, leading to reduced fees due to rounding errors.

For further reference, see the governance variables and fees at:

> https://docs.size.credit/technical-docs/governance-variables-and-fees

## Impact

This vulnerability allows an attacker to borrow funds from the protocol with reduced fees, leading to:

- **Financial loss**: The protocol loses out on fee revenue, which can be substantial given the volume of transactions.
- **Unfair advantage**: Malicious actors gain an unfair advantage by borrowing with lower fees than other users.
- **Repeated exploitation**: Continuous exploitation could lead to significant financial imbalance and damage the trust in the protocol.

Regardless of the contract's involved constraints, here we've managed to set 4.86 usdc as the cash amount and left 365 days as the tenor, which allows us to reach a fee of 24300-24301 units. In a normal scenario with 5 usdc as the cash it would've been 25000-25001 instead.

The minimum threshold in the testcase has been calculated as follows:

Given:

- **Cash**: 4860000 (4.86 USDC)
- **Swap fee APR**: 0.005 (0.5%)
- **Tenor**: 1 year (31536000 seconds)

The fee calculation is:

**fee = cash * swapFeeAPR * tenor​ / 365 days**

**fee = 4860000 * 0.005 * 31536000​ / 31536000**

This simplifies to:

**fee = 4860000 * 0.005 = 24300**

If we were to consider a legitimate swap with no rounding, the general minimum range fee would have been:

**fee = 5000000 * 0.005 = 25000**

so knowing that:

Legitimate user fee: 25000

Exploit user fee: 24300

**Difference per transaction: 25000 - 24300 = 700 units/tx**

Now, assuming 1000 transactions:

**Total savings = 700 * 1000 = 700000**

Thus, we deduce that **the attacker can save 700000 units of the base currency (assuming USDC) over 1000 transactions by exploiting this vulnerability compared to a legitimate user**. This significant saving demonstrates the vulnerability's impact and risk of abuse.

## Tools Used

Mind power.

## Recommended Mitigation Steps

1. Implement checks to ensure that the fee calculated is always within an expected range. Introduce a minimum fee threshold.
   - Example:
     ```solidity
     uint256 constant MINIMUM_FEE = 25000; // Define an appropriate minimum fee value

     function getSwapFee(State storage state, uint256 cash, uint256 tenor) internal view returns (uint256) {
         uint256 fee = Math.mulDivUp(cash, getSwapFeePercent(state, tenor), PERCENT);
         require(fee >= MINIMUM_FEE, "Fee too low");
         return fee;
     }
     ```

2. Implement monitoring and alerting mechanisms to detect unusual patterns in fee calculations and transactions, enabling quick response to these kind of exploits.
