# Vulnerability details


#### Impact

In the current protocol, the `KEEPER` role can call the `LiquidateWithReplacement` function to initiate a liquidation with replacement. This function validates necessary parameters and rewards the `KEEPER` with a 5% liquidation fee from the collateral. However, the protocol incorrectly sends all profits obtained from the borrower's `borrowAToken` directly to the fee receiver, failing to distribute a portion of this profit to the `KEEPER`. 

This issue undermines the incentivization of the `KEEPER`, as they receive only the standard collateral liquidation fee but not a share of the profits from the borrowed assets, reducing their motivation to initiate replacement borrow positions, which are more beneficial to the protocol due to additional fees.
Liquidation bot will prefer to call the liquidation function as liquidate with replacement will charge more gas fee(ethereum chain) and there is no incentive to calling liquidate with replacement over liquidation for the bot.

### Proof of Concept

**Key Issues**:
- **Improper Profit Distribution**: The `KEEPER` does not receive a share of the borrower's `borrowAToken` profits.
- **Inadequate Incentives**: The `KEEPER` has less incentive to initiate liquidations with replacement, despite its higher profitability for the protocol. 

 ** Code and Exploitation Example**

**Code Snippet**:

1. **Liquidation with Replacement**:
    ```solidity
    function LiquidateWithReplacement(
        uint256 creditPositionId,
        uint256 newDebtAmount,
        address newBorrower
    ) external {
        // Validation and liquidation logic
        // ...

        // Profit distribution - Issue lies here
         state.data.borrowAToken.transferFrom(address(this), params.borrower, issuanceValue);
        state.data.borrowAToken.transferFrom(address(this), state.feeConfig.feeRecipient, liquidatorProfitBorrowToken);
    }
    ```

2. ** Keeper Reward Logic from liquidation logic**:
    ```solidity
   state.data.collateralToken.transferFrom(debtPosition.borrower, msg.sender, liquidatorProfitCollateralToken);
    ```

Protocol also gets their share of the fee below 

 ```solidity
state.data.collateralToken.transferFrom(
            debtPosition.borrower, state.feeConfig.feeRecipient, protocolProfitCollateralToken
        );
```

3. But Protocol takes ALL in Liquidate with Replacement without sharing with KEEPER

**Exploitation Scenario**:

1. **Setup**: The `KEEPER` initiates a liquidation with replacement, handling the necessary validations and executing the liquidation.
2. **Protocol Behavior**: The protocol calculates the profits from the borrower's `borrowAToken` but sends all profits to the fee receiver instead of sharing a portion with the `KEEPER`.
3. **Outcome**: The `KEEPER` receives only the standard 5% collateral fee and misses out on the profits from the liquidation, reducing their incentive to initiate replacement borrow positions.

**Example Code Update**:

```solidity
function LiquidateWithReplacement(
    uint256 creditPositionId,
    uint256 newDebtAmount,
    address newBorrower
) external {
    // Validation and liquidation logic
    // ...

    // Corrected profit distribution
      state.data.borrowAToken.transferFrom(address(this), params.borrower, issuanceValue);
        state.data.borrowAToken.transferFrom(address(this), state.feeConfig.feeRecipient, liquidatorProfitBorrowToken);
}
```

** Potential Consequences**

- **Reduced Participation**: `KEEPERs` are less incentivized to initiate liquidations with replacement due to inadequate rewards, potentially leading to fewer such liquidations.
- **Missed Revenue Opportunities**: The protocol may miss out on the increased profitability of liquidations with replacement due to fewer `KEEPER` initiations.
- **Unbalanced Reward Structure**: The reward structure does not reflect the additional effort and benefit brought by the `KEEPER` in initiating these transactions.
