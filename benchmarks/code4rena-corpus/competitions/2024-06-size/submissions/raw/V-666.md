# Vulnerability details

## Issue:
The executeDeposit function of the Deposit library incorrectly calculates the amount of ETH to be deposited when msg.value is greater than zero. Instead of using the validated params.amount, it uses the entire balance of the contract (address(this).balance). This can lead to unintended behavior, including the deposit of more ETH than the user intended, potentially draining the contract's existing ETH balance.


## Code:

https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/Deposit.sol#L64

```solidity
function executeDeposit(State storage state, DepositParams calldata params) public {
    address from = msg.sender;
    uint256 amount = params.amount;
    if (msg.value > 0) {
        // do not trust msg.value (see `Multicall.sol`)
        amount = address(this).balance;
        // slither-disable-next-line arbitrary-send-eth
        state.data.weth.deposit{value: amount}();
        state.data.weth.forceApprove(address(this), amount);
        from = address(this);
    }
    // ... rest of the function
}
```

The function overwrites the validated params.amount with address(this).balance when msg.value > 0. This assumes that the entire balance of the contract is the amount being deposited in this transaction. If the contract already had an ETH balance before this transaction, it would incorrectly use that entire balance for the deposit, not just the msg.value sent with this transaction.

The root cause appears to be an attempt to protect against potential msg.value manipulation in multicall scenarios. However, the implemented solution introduces a more severe vulnerability by using the contract's entire balance instead of the transaction-specific amount.

## Impact:
- Unintended large deposits: Users might deposit more ETH than they intended, potentially their entire balance.
- Contract balance drainage: The contract could inadvertently use its entire ETH balance for a single deposit, affecting other users or operations.
- Inconsistent state: The emitted Deposit event would show an amount larger than what the user actually sent, leading to inconsistencies in off-chain systems or audits.
- Potential for exploitation: Malicious actors could potentially manipulate this behavior to their advantage, especially in multi-transaction scenarios.

## Reproduction Steps:
- Deploy the contract with an initial ETH balance (e.g., 5 ETH).
- Call executeDeposit with a small msg.value (e.g., 1 ETH).
- Observe that the entire contract balance (6 ETH) is used for the deposit, not just the 1 ETH sent.

## Recommended Fix:
Replace the problematic line with:
```solidity
amount = params.amount;
```

## Corrected code:
```solidity
function executeDeposit(State storage state, DepositParams calldata params) public {
    address from = msg.sender;
    uint256 amount = params.amount;
    if (msg.value > 0) {
        state.data.weth.deposit{value: amount}();
        state.data.weth.forceApprove(address(this), amount);
        from = address(this);
    }
    // ... rest of the function remains the same
}
```

This ensures that only the amount specified and validated in params.amount (which should equal msg.value for ETH deposits) is used for the deposit.
