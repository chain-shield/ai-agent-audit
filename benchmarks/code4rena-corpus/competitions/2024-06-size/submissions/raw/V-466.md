# Vulnerability details

## Impact
According to intended design, ```fragmentationFee``` should be deducted whenever there is a credit split.

>fragmentationFee so that it better reflects the intended behavior of this fee, which is to be charged only when there is a credit fractionalization/split.

During the call to ```compensate```, fragmentation of ```creditPositionToCompensateId``` is checked and fragmentation fee is deducted from the caller's collateral.

```solidity
uint256 exiterCreditRemaining = creditPositionToCompensate.credit - amountToCompensate; 
...

        if (exiterCreditRemaining > 0) {
            // charge the fragmentation fee in collateral tokens, capped by the user balance
            uint256 fragmentationFeeInCollateral = Math.min(
                state.debtTokenAmountToCollateralTokenAmount(state.feeConfig.fragmentationFee),
                state.data.collateralToken.balanceOf(msg.sender)
            );
            state.data.collateralToken.transferFrom(
                msg.sender, state.feeConfig.feeRecipient, fragmentationFeeInCollateral
            );
        }
```

However, the problem with the ```exiterCreditRemaining``` is that it does not include the difference between the ```creditPositionWithDebtToRepayId``` before compensation and ```creditPositionWithDebtToRepayId``` after compensation, in the case where ```RESERVED_ID``` was provided as ```creditPositionToCompensate```, ```exiterCreditRemaining``` will definitely be zero since ```creditPositionToCompensate.credit = amountToCompensate```
```solidity
@>  uint256 amountToCompensate = Math.min(params.amount, creditPositionWithDebtToRepay.credit);

        CreditPosition memory creditPositionToCompensate;
        if (params.creditPositionToCompensateId == RESERVED_ID) {
            creditPositionToCompensate = state.createDebtAndCreditPositions({
                lender: msg.sender,
                borrower: msg.sender,
        @>      futureValue: amountToCompensate,
             dueDate: debtPositionToRepay.dueDate
            });
        } else {
```
From the snippet above, if an amount lower than the creditPositionWithDebtToRepay.credit was provided with the ```params.creditPositionToCompensateId == RESERVED_ID```, a new debtPosition will be created for the borrower and a new creditPosition will be created for the Lender  of ```creditPositionWithDebtToRepay```, this has fragmented a credit position as well and fragmentation fee should be charged.

## Proof of Concept
Consider a credit position with;
borrower: Alice
futureValue: 1500

If Alice calls ```compensate``` on the credit position above with ```RESERVED_ID``` as the ```creditPositionToCompensateId```, and 500 as the amount.
A new credit position with 500 is opened for the lender and a 500 debt position is opened for Alice. Lender's credit position was split and no fragmentation fee since  ```creditPositionToCompensate.credit = amountToCompensate``` and lender's credit difference was not checked.

One way to abuse this is that when the borrower of a credit position notices that the lender wants to sell the credit position(a large one), they might compensate it multiple times with RESERVED_ID as the creditPositionId to create smaller creditPosition and avoid fragmentation fee.

In this case, if the lender wants to sell the 1,500 credit position and Alice wants to buy part without paying frag fee with another address, Alice compensate with 500 and uses the other address to buy the new creditPosition without paying fragmentation fee. 

## Tools Used
Manual review.

## Recommended Mitigation Steps
Deduct fragmentation fee when a credit position is not compensated in full.
