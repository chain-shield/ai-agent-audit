# Vulnerability details

DOS is possible via lots of the smallest possible positions created with the help of `Compensate` run with `params.creditPositionToCompensateId == RESERVED_ID` and `params.amount == minimumCreditBorrowAToken` by the debtor for all related credit positions (i.e. `creditPositionWithDebtToRepay` will go around all credit positions for the debt position where attacker is the borrower).

## Impact

Borrower can create a large number of credit positions of the minimal allowed size without incurring any fragmentation fees. Since `minimumCreditBorrowAToken = 50 USDC` and a substantial number of positions can be created this way it can impose increasing/blocking costs on claiming run on the Ethereum mainnet deployment.

## Recommended Mitigation Steps

Consider making `exiterCreditRemaining` a boolean, that is `false` if `amountToCompensate == creditPositionWithDebtToRepay.credit` when `id == RESERVED_ID` (i.e. when no credit position supplied, but existing position of the lender is fully exchanged to the new one), and if `amountToCompensate == creditPositionWithDebtToRepay.credit || amountToCompensate == creditPositionToCompensate.credit` otherwise (i.e. when credit position was supplied and either it or lender's position was fully converted to a new one). This way fragmentation fee will not be charged when any of the existing credit positions (borrower's or lender's) was closed fully.

If neither is the case then some new credit position was created and total future claiming costs went up, so do charge the fragmentation fee:

[Compensate.sol#L146-L147](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/Compensate.sol#L146-L147)

```diff

+       if (exiterCreditRemaining) {
            // charge the fragmentation fee in collateral tokens, capped by the user balance
```
