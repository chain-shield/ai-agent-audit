# Vulnerability details

## Impact
For upgradeable contracts, there should be storage gaps to allow developers to add new state variables in the future without compromising the storage compatibility with existing deployments.

However, the Size contract packs all variables into a `State` struct without storage gaps between sub-config structs.

```
struct State {
    // the fee configuration struct
    FeeConfig feeConfig;
    // the risk configuration struct
    RiskConfig riskConfig;
    // the oracle configuration struct
    Oracle oracle;
    // the protocol data (cannot be updated)
    Data data;
}
```

```
abstract contract SizeStorage {
    State internal state;
}
```

In future upgrades, if a new fee variable needs to be added, the developer cannot include it in the `FeeConfig` struct. Instead, they can only append it to the `State` struct. This limitation would decrease the code quality and readability.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Consider using [EIP-7201 - namespaced storage layout](https://eips.ethereum.org/EIPS/eip-7201) for `feeConfig`, `riskConfig`, `oracle`, and `data` variables respectively. This way, new variables can be easily added in future upgrades. This storage layout is also what OpenZeppelin library adopted since version 5.0.
