# Vulnerability details

## Bug Description
The `liquidateWithReplacement` function will replace an unhealthy borrower of an existing loan with a new healthy borrower. As a result, the borrowed funds are transferred to the new borrower during this operation and an additional amount of assets ("profit" from spread), is sent to the `feeRecipient`. After this operation, the new borrower and the `feeRecipient` should be able to withdraw their received assets from Size. However, Size does not consider the "profit" when checking the available liquidity:

[Size::liquidateWithReplacement](https://github.com/code-423n4/2024-06-size/blob/main/src/Size.sol#L229-L243)
```solidity
229:    function liquidateWithReplacement(LiquidateWithReplacementParams calldata params)
230:        external
231:        payable
232:        override(ISize)
233:        whenNotPaused
234:        onlyRole(KEEPER_ROLE)
235:        returns (uint256 liquidatorProfitCollateralToken, uint256 liquidatorProfitBorrowToken)
236:    {
237:        state.validateLiquidateWithReplacement(params);
238:        uint256 amount;
239:        (amount, liquidatorProfitCollateralToken, liquidatorProfitBorrowToken) = // @audit: amount -> borrower & liquidatorProfitBorrowToken -> feeRecipient
240:            state.executeLiquidateWithReplacement(params);
241:        state.validateUserIsNotBelowOpeningLimitBorrowCR(params.borrower);
242:        state.validateMinimumCollateralProfit(params, liquidatorProfitCollateralToken);
243:        state.validateVariablePoolHasEnoughLiquidity(amount); // @audit: only assets sent to borrower considered for liquidity check
```

[LiquidateWithReplacement::executeLiquidateWithReplacement](https://github.com/code-423n4/2024-06-size/blob/main/src/libraries/actions/LiquidateWithReplacement.sol#L120-L162)
```solidity
120:    function executeLiquidateWithReplacement(State storage state, LiquidateWithReplacementParams calldata params)
121:        external
122:        returns (uint256 issuanceValue, uint256 liquidatorProfitCollateralToken, uint256 liquidatorProfitBorrowToken)
123:    {
...
160:        state.data.debtToken.mint(params.borrower, debtPosition.futureValue);
161:        state.data.borrowAToken.transferFrom(address(this), params.borrower, issuanceValue); // @audit: borrower can withdraw issuanceValue

```

As we can see above, Size is only guaranteeing that `amount` of liquidity is available even though `amount + liquidatorProfitBorrowToken` of assets have been pulled from contract. This can lead to a scenario in which only one party (borrower or `feeRecipient`) will be able to withdraw all of their received assets after this operation (assuming no new liquidity enters the system before then). For reference, the `buyCreditMarket` function correctly uses an asset value that encompasses all of the assets sent to the borrower and `feeRecipient` when performing the available liquidity check:

[Size::buyCreditMarket](https://github.com/code-423n4/2024-06-size/blob/main/src/Size.sol#L178-L184)
```solidity
178:    function buyCreditMarket(BuyCreditMarketParams calldata params) external payable override(ISize) whenNotPaused {
179:        state.validateBuyCreditMarket(params);
180:        uint256 amount = state.executeBuyCreditMarket(params); // @audit: amount of assets pulled from lender 
181:        if (params.creditPositionId == RESERVED_ID) {
182:            state.validateUserIsNotBelowOpeningLimitBorrowCR(params.borrower);
183:        }
184:        state.validateVariablePoolHasEnoughLiquidity(amount); // @audit: checking liquidity against actual amount of assets pulled
```

[BuyCreditMarket::executeBuyCreditMarket](https://github.com/code-423n4/2024-06-size/blob/main/src/libraries/actions/BuyCreditMarket.sol#L121-L196)
```solidity
121:    function executeBuyCreditMarket(State storage state, BuyCreditMarketParams memory params)
122:        external
123:        returns (uint256 cashAmountIn) // @audit: cashAmountIn is equal to total assets pulled from lender 
124:    {
...
195:        state.data.borrowAToken.transferFrom(msg.sender, borrower, cashAmountIn - fees); // @audit: assets, excluding fees, sent to borrower
196:        state.data.borrowAToken.transferFrom(msg.sender, state.feeConfig.feeRecipient, fees); // @audit: fees sent to feeRecipient
```

As we can see above, the `buyCreditMarket` function will always guarantee that after the call executes, both parties have the ability to withdraw all of their received assets from Size. However, the `liquidateWithReplacement` function does not guarantee this expectation.

## Impact
There is an edge case in which a `liquidateWithReplacement` call is successful, but due to an insufficient liquidity check, only one party is able to withdraw their received assets immediately after the operation. The most impactful scenario would be if the `feeRecipient` withdraws all their received assets first and this would result in the borrower being unable to withdraw all of their borrowed assets (assuming no new liquidity has yet entered the system). The opposite scenario is less impactful and would result in the `feeRecipient` being griefed.

## Recommended Mitigation
When checking for available liquidity, the `liquidatorProfitBorrowToken` amount should be considered in addition to the `amount`:

```diff
diff --git a/src/Size.sol b/src/Size.sol
index a41e289..7d88542 100644
--- a/src/Size.sol
+++ b/src/Size.sol
@@ -240,7 +240,7 @@ contract Size is ISize, SizeView, Initializable, AccessControlUpgradeable, Pausa
             state.executeLiquidateWithReplacement(params);
         state.validateUserIsNotBelowOpeningLimitBorrowCR(params.borrower);
         state.validateMinimumCollateralProfit(params, liquidatorProfitCollateralToken);
-        state.validateVariablePoolHasEnoughLiquidity(amount);
+        state.validateVariablePoolHasEnoughLiquidity(amount + liquidatorProfitBorrowToken);
     }
```
