# Vulnerability details

## Impact
When `params.creditPositionId` is equal to RESERVED_ID, indicating that a new credit position should be created, the function calls `state.createDebtAndCreditPositions` with both the lender and borrower set to `msg.sender.` This means the lender and borrower of the newly created debt and credit positions will be at the same address.

However, when selling credit as a market order, the lender should be `params.lender`, not `msg.sender`. The current implementation incorrectly sets the lender to the function caller (`msg.sender`) instead of the lender specified in the function parameters.
[SellCreditMarket.sol#184-191](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/SellCreditMarket.sol#L184-L191)

> When creating a new credit position using `SellCreditMarket`, the lender is incorrectly set to `msg.sender` instead of `params.lender`. This means that the caller of the function becomes the lender of the newly created debt and credit positions, even though the intended lender is specified in the function parameters.

> The incorrect lender assignment results in inconsistent ownership of the newly created debt and credit positions. The borrower and lender are set to `msg.sender`, which goes against the intended design of separate borrower and lender roles.

**Example Scenario**
1. Alice (`params.lender`) wants to sell credit to Bob (`msg.sender`) using the `SellCreditMarket` function.
2. Bob calls the `SellCreditMarket` function with `params.lender` set to Alice's address and `params.creditPositionId` set to `RESERVED_ID`.
3. Due to the bug, when creating the new debt and credit positions, the lender and borrower are set to Bob's address (`msg.sender`).
4. As a result, Bob becomes both the lender and borrower of the newly created positions, even though Alice was intended to be the lender.
5. This leads to incorrect accounting and ownership, as Alice is not correctly credited as the lender, and Bob gains control over the positions meant for Alice.

## Proof of Concept
**1. The `SellCreditMarket` function is called with the following parameters:**
     - `params.lender`: Alice's address (0xF428...)
     - `params.creditPositionId`: `RESERVED_ID` (indicating a new credit position should be created)
     - `params.amount`: 1000 (the amount of credit to sell)
     - `params.tenor`: 30 days (the tenor of the loan)
     - `params.deadline`: current timestamp + 1 hour (the deadline for the transaction)
     - `params.maxAPR`: 10% (the maximum APR for the loan)
     - `params.exactAmountIn`: true (indicating that the amount represents the exact credit to sell)

     - `borrower`: `msg.sender` (Bob's address, the caller of the `SellCreditMarket` function)

4. **Inside the `createDebtAndCreditPositions` function, the following actions are performed:**

       * `lender`: Bob's address
       * `debtPositionId`: the ID of the newly created `DebtPosition`
       * `credit`: 1000

5. The newly created `DebtPosition` and `CreditPosition` are stored in the `state.data.debtPositions` and `state.data.creditPositions` mappings, respectively.

## Recommended Mitigation Steps
By setting `lender: params.lender`, the newly created debt and credit positions will have the correct lender as specified in the function parameters. At the same time, the borrower will be the caller of the function (`msg.sender`).
```solidity
if (params.creditPositionId == RESERVED_ID) {
    // slither-disable-next-line unused-return
    state.createDebtAndCreditPositions({
        lender: params.lender,
        borrower: msg.sender,
        futureValue: creditAmountIn,
        dueDate: block.timestamp + tenor
    });
}
```
