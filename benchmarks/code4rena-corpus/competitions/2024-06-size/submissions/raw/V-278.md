# Vulnerability details

## Description
`Multicall::multicall` is allowed to process nested `Multicall::multicall` functions in the calldata, while the `state.data.isMulticall` variable in `Multicall::multicall` [L27](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/Multicall.sol#L27) does not support different levels of nesting between these calls.

##  Impact
The caller can reenter `Multicall::multicall` by passing the function as calldata one or multiple times. The variables `state.data.borrowAToken` and `state.data.debtToken` will hold inconsistent values until the execution of the initial parent calldata is complete.

## Proof of Concept
1. The user calls `Size.multicall` with calldata containing regular functions and nested multicalls. For example, a `buyCreditMarket` function is executed first, affecting the values of `state.data.borrowAToken` and `state.data.debtToken`
2. Another multicall is executed before the new state has been checked in `validateBorrowATokenIncreaseLteDebtTokenDecrease`
3. This second multicall can reenter the original function since `state.data.isMulticall` has not yet reset to `false` from the previous execution
4. This multicall can now exploit the inconsistent states and manipulate the `borrowAToken` balance and `debtToken` supply to exceed the token cap and inflate the debt reduction 
5. The `validateBorrowATokenIncreaseLteDebtTokenDecrease` check will perform correctly for the last nested multicall
6. When the previous multicall reenters, the state has already been manipulated. `state.data.borrowAToken` and `state.data.debtToken` will differ from their original values, causing the reentered check to be based on manipulated balances

## Recommended Mitigation Steps

Reentrancy exploits can be mitigated by ensuring atomic state changes. Instead of setting the `state.data.isMulticall` flag alone at the beginning and the end of the function, it is recommended to use [OpenZeppelin's ReentrancyGuard](https://docs.openzeppelin.com/contracts/5.x/api/utils#ReentrancyGuard) pattern. This involves checking the status of the flag variable before updating it to `true`.

Here's a suggestion for updating the `Multicall:multicall` function:
```diff
library Multicall {
+   error Multicall_NESTED_MULTICALL_NOT_SUPPORTED();
    //...
    function multicall(State storage state, bytes[] calldata data) internal returns (bytes[] memory results) {
+        if (state.data.isMulticall == true){
+           revert Multicall_NESTED_MULTICALL_NOT_SUPPORTED();
+        }
        state.data.isMulticall = true;
        //...
```

By using the ReentrancyGuard pattern, we ensure that each state change is handled securely and accurately, preventing reentrancy and protecting the protocol from nested multicall exploits.
