# Vulnerability details

## Impact
Due to the way `cashAmountOut` and `maxCashAmountOut` are calculated whenever a user takes a borrow using a credit position he has and with a specified `cashAmountOut`, it is very hard for him not to get fragmented and pay extra fees due to that even if he calculates everything thoroughly. That causes users to almost always have to pay a fragmentation fee in the above scenario and only users with pure luck will be able to avoid paying it.

## Proof of Concept
Users can borrow money with an existing credit position they have whenever they specify a credit position ID instead of `RESERVED_ID`. They can also specify whether they want to receive an exact amount of money they will borrow and from that pay the calculated credits for that borrow or vice versa (they can do it by specifying an `exactAmountIn` boolean).

Whenever they specify `false` for that boolean upon borrowing, they have essentially specified the money they will receive and then the credit they have to pay for that amount will be calculated as follows:
```solidity
(creditAmountIn, fees) = state.getCreditAmountIn({
                cashAmountOut: cashAmountOut,
                maxCashAmountOut: params.creditPositionId == RESERVED_ID
                    ? cashAmountOut
                    : Math.mulDivDown(creditPosition.credit, PERCENT - state.getSwapFeePercent(tenor), PERCENT + ratePerTenor),
                maxCredit: params.creditPositionId == RESERVED_ID
                    ? Math.mulDivUp(cashAmountOut, PERCENT + ratePerTenor, PERCENT - state.getSwapFeePercent(tenor))
                    : creditPosition.credit,
                ratePerTenor: ratePerTenor,
                tenor: tenor
            });
```
Then, this is the `getCreditAmountIn()` function:
```solidity
function getCreditAmountIn(
        State storage state,
        uint256 cashAmountOut,
        uint256 maxCashAmountOut,
        uint256 maxCredit,
        uint256 ratePerTenor,
        uint256 tenor
    ) internal view returns (uint256 creditAmountIn, uint256 fees) {
        uint256 swapFeePercent = getSwapFeePercent(state, tenor);

        uint256 maxCashAmountOutFragmentation = 0;

        if (maxCashAmountOut >= state.feeConfig.fragmentationFee) {
            maxCashAmountOutFragmentation = maxCashAmountOut - state.feeConfig.fragmentationFee;
        }

        // slither-disable-next-line incorrect-equality
        if (cashAmountOut == maxCashAmountOut) {
            // no credit fractionalization

            creditAmountIn = maxCredit;
            fees = Math.mulDivUp(cashAmountOut, swapFeePercent, PERCENT);
        } else if (cashAmountOut < maxCashAmountOutFragmentation) {
            // credit fractionalization

            creditAmountIn = Math.mulDivUp(cashAmountOut + state.feeConfig.fragmentationFee, PERCENT + ratePerTenor, PERCENT - swapFeePercent);
            fees = Math.mulDivUp(cashAmountOut, swapFeePercent, PERCENT) + state.feeConfig.fragmentationFee;
        } else {
            // for maxCashAmountOutFragmentation < amountOut < maxCashAmountOut we are in an inconsistent situation
            //   where charging the swap fee would require to sell a credit that exceeds the max possible credit

            revert Errors.NOT_ENOUGH_CASH(maxCashAmountOutFragmentation, cashAmountOut);
        }
    }
```
As you can see, if `cashAmountOut == maxCashAmountOut`, then no extra fragmentation fees will have to be paid. If they are not, however, then the user has to pay extra fees (`fragmentationFee`) because the user is essentially splitting his credit position. The issue is that it is extremely hard for the user to avoid paying that fee and not split his credit position. That is because of how `maxCashAmountOut` is calculated:
```solidity
Math.mulDivDown(creditPosition.credit, PERCENT - state.getSwapFeePercent(tenor), PERCENT + ratePerTenor)
```
It uses `tenor` and `ratePerTenor` for the calculations. Clearly both rely on the `tenor` value which is calculated using `block.timestamp` (calculated in the `else` statement after checking whether the credit position ID is equal to the reserved ID):
```solidity
tenor = debtPosition.dueDate - block.timestamp;
```
This means that even if a user is extremely careful to not split his position and to not pay that fragmentation fee, it will be extremely hard to do so because he can never know what the `block.timestamp` of the transaction will be. Here, even a delay of a few seconds will make `cashAmountOut` and `maxCashAmountOut` with different values leading to him paying extra fees. Since this is a matter of seconds, only lucky users will be able to avoid paying those fees.

Also, since there is no kind of slippage type protection as to whether the user has to pay those fragmentation fees, there is no way to avoid this situation in the case explained above. The only `block.timestamp` check is the deadline parameter being checked but that is absolutely insufficient and has a completely different purpose. The timestamp of function execution has to be between a range of a few seconds which the deadline parameter doesn't check/enforce.

A similar issue also happens in `BuyCreditMarket.sol`.

For the POC, create a Log event in `SellCreditMarket.sol` and paste the following 2 events in the `else` block of the `if` statement checking `params.exactAmountIn`:
```solidity
emit Log(cashAmountOut);
emit Log(Math.mulDivDown(creditPosition.credit, PERCENT - state.getSwapFeePercent(tenor), PERCENT + ratePerTenor));
```
This logs `cashAmountOut` and `maxCashAmountOut` and thus, makes the POC significantly easier to make without having to add code logic to see whether a user has been fragmented. Note that I have not tried to make `cashAmountOut` and `maxCashAmountOut` equal, the goal of the POC is just to show that `maxCashAmountOut` can never be properly calculated from the users and just a few seconds different of the timestamp causes different values for it, thus they will never be able to guarantee that it will equal `cashAmountOut`.

## Recommended Mitigation Steps
Accept a boolean input as to whether the user expects to pay fragmentation fees and refactor the code a little bit to revert in case he has specified false but has to pay such fees. Alternatively, you can just incorporate a check similar to the deadline check you are doing but with a range instead of just a deadline.
