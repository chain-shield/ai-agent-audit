# Vulnerability details


At the end of the `multicall` function, the code checks if the increase in the `borrowToken` supply has exceeded the `borrowTokenCap`. If so, it ensures that the total debt of the system has decreased more. This validation is done by calling the function `validateBorrowATokenIncreaseLteDebtTokenDecrease`, which performs the following check:

```solidity
if (borrowATokenSupplyIncrease > debtATokenSupplyDecrease) {
   // revert
   revert Errors.BORROW_ATOKEN_INCREASE_EXCEEDS_DEBT_TOKEN_DECREASE(
        borrowATokenSupplyIncrease, debtATokenSupplyDecrease
   );
}
```

For this purpose, the `multicall` code takes snapshots of the `borrowToken` and `debtToken` total supplies before and after executing the operations. However, the issue is that the `multicall` code is taking snapshots of the `borrowToken` balance of the current contract instead of the total supply:

```solidity
uint256 borrowATokenSupplyBefore = state.data.borrowAToken.balanceOf(address(this));

// ........

uint256 borrowATokenSupplyAfter =state.data.borrowAToken.balanceOf(address(this));
```

## Impact
The `borrowATokenCap` limit can be bypassed by using `multicall`.

## Proof of Concept
Suppose a user performs a deposit using `multicall`. This deposit increases the `borrowToken` total supply past the limit imposed by `borrowATokenCap`. However, due to the described mistake, the validation in `validateBorrowATokenIncreaseLteDebtTokenDecrease` will be executed as follows:

```solidity
if (0 > 0) {
	// revert
	revert Errors.BORROW_ATOKEN_INCREASE_EXCEEDS_DEBT_TOKEN_DECREASE(
		borrowATokenSupplyIncrease, debtATokenSupplyDecrease
	);
}
```
Since  `0`  is not greater than  `0`, the code will not revert.

## Recommended Mitigation Steps
The snapshots should be taken as:

```solidity
state.data.borrowAToken.totalSupply();
```
