# Vulnerability details

## Impact
`debtTokenAmountToCollateralTokenAmount` does not properly handle cases where the borrow token is USDC and the collateral token is WETH. Specifically, the function assumes that the debt token amount is always in WAD (18 decimals), but in the case of a reverse market, the debt token amount would be in USDC (6 decimals). This can cause the function to return incorrect values, leading to issues with further calculations or transfers.

Additionally, the `collateralRatio` function may be affected if the `crOpening` and `crLiquidation` values are not correctly escalated for the reverse market. Suppose these values are not changed to 6 decimals. In that case, the function may return values escalated to 6 decimals, which can cause the function to revert when validating if a user is below the limit borrow collateral ratio.

## Proof of Concept
[src/libraries/AccountingLibrary.sol#debtTokenAmountToCollateralTokenAmount](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/AccountingLibrary.sol#L26-L35)
```solidity
    function debtTokenAmountToCollateralTokenAmount(State storage state, uint256 debtTokenAmount)
        internal
        view
        returns (uint256 collateralTokenAmount)
    {
        uint256 debtTokenAmountWad = Math.amountToWad(debtTokenAmount, state.data.underlyingBorrowToken.decimals());
        collateralTokenAmount = Math.mulDivUp(
            debtTokenAmountWad, 10 ** state.oracle.priceFeed.decimals(), state.oracle.priceFeed.getPrice()
        );
    }
```
The function uses a `debtTokenAmount` and a `state` object as input parameters. It first converts the `debtTokenAmount` to WAD using the `amountToWad` function from the `Math` library, using the number of decimals for the underlying borrow token. It then multiplies the WAD value by 1e18 and divides it by the price returned by the price feed to calculate the collateral token amount.

The issue arises when the borrow token is USDC (6 decimals) instead of WETH (18 decimals). In this case, the `debtTokenAmount` should be converted to WAD using 6 decimals instead of 18. However, the function does not account for this and always uses the number of decimals for the underlying borrow token. This can cause the function to return incorrect values, leading to issues with further calculations or transfers.

**To illustrate the impact, consider the following scenario:**
1. A user deposits 1000 USDC as collateral and borrows 500 WETH.
2. The user then wants to repay the debt using USDC.
3. The `debtTokenAmountToCollateralTokenAmount` function is called with a `debtTokenAmount` of 500 WETH and a `state` object that specifies the underlying borrow token as USDC (6 decimals).
4. The function converts the `debtTokenAmount` to WAD using 6 decimals, resulting in a value of 500e6.
5. The function then multiplies this value by 1e18 and divides it by the price returned by the price feed, resulting in a collateral token amount of 500e6 * 1e18 / 1000e6 = 500e12.
6. However, the correct collateral token amount should be 500e6, since the borrow token is USDC (6 decimals) and the collateral token is WETH (18 decimals).

This incorrect calculation can cause issues with further calculations or transfers, potentially leading to loss of funds or other security vulnerabilities.

## Recommended Mitigation Steps
The `debtTokenAmountToCollateralTokenAmount` function should be updated to handle cases where the borrow token is USDC and the collateral token is WETH. The `crOpening` and `crLiquidation` values should be escalated appropriately for the reverse market.
