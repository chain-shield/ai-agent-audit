# Vulnerability details

## Impact
The issue lies in the transfer of collateral tokens to the caller (`msg.sender`) at the end of the function. [src/libraries/actions/SelfLiquidate.sol#L70](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/SelfLiquidate.sol#L70)
```solidity
state.data.collateralToken.transferFrom(debtPosition.borrower, msg.sender, assignedCollateral);
```
In a self-liquidation scenario, the collateral should be transferred back to the borrower (`debtPosition.borrower`) rather than the caller (`msg.sender`). The current implementation allows anyone to call the `executeSelfLiquidate` function and receive the collateral tokens, even if they are not the borrower.

The `executeSelfLiquidate` function is part of the `SelfLiquidate` library, which allows borrowers to self-liquidate their credit positions. Self-liquidation allows borrowers to close their positions and reclaim their collateral when they are unable to repay their debt.

[src/libraries/actions/SelfLiquidate.sol#SelfLiquidate.sol](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/SelfLiquidate.sol#L59-L71)
```solidity
/// @notice Executes the self-liquidation of a credit position
/// @param state The state
/// @param params The input parameters for self-liquidating a credit position
function executeSelfLiquidate(State storage state, SelfLiquidateParams calldata params) external {
    emit Events.SelfLiquidate(params.creditPositionId);

    CreditPosition storage creditPosition = state.getCreditPosition(params.creditPositionId);
    DebtPosition storage debtPosition = state.getDebtPositionByCreditPositionId(params.creditPositionId);

    uint256 assignedCollateral = state.getCreditPositionProRataAssignedCollateral(creditPosition);

    // debt and credit reduction
    state.reduceDebtAndCredit(creditPosition.debtPositionId, params.creditPositionId, creditPosition.credit);

    state.data.collateralToken.transferFrom(debtPosition.borrower, msg.sender, assignedCollateral);
}
```
In the last line of the function, where the collateral tokens are transferred to `msg.sender` instead of `debtPosition.borrower`.

> With the current implementation, anyone can call the `executeSelfLiquidate` and specify any credit position ID. If a valid credit position ID is provided, the caller will receive the collateral tokens associated with that position, even if they are not the borrower. This allows unauthorized individuals to steal collateral from other users' positions.

> Since the collateral is transferred to the caller instead of the borrower, the actual borrower will not receive their collateral back during the self-liquidation process. This goes against the intended purpose of self-liquidation, which is to allow borrowers to reclaim their collateral.

## Proof of Concept
Let's consider a scenario where a borrower has a credit position with ID 719 and has deposited 10 ETH as collateral. An attacker can exploit this vulnerability by calling the `executeSelfLiquidate` function with the following parameters.
```solidity
SelfLiquidateParams memory params = SelfLiquidateParams({
    creditPositionId: 719
});

size.executeSelfLiquidate(params);
```
In this case, the attacker will receive the 10 ETH collateral associated with credit position ID 719, even though they are not the borrower. The actual borrower will not receive their collateral back.

## Recommended Mitigation Steps
The line should be modified to transfer the collateral tokens to the borrower instead. Transferring the collateral tokens back to the borrower ensures that only the borrower can reclaim their collateral during a self-liquidation process.
```solidity
state.data.collateralToken.transferFrom(debtPosition.borrower, debtPosition.borrower, assignedCollateral);
```
