# Vulnerability details


## Impact
Borrower cannot save himself from liquidation by paying partial debt using compensate due to the underwater check. This issue is very relevant in Multicalls. 

## Proof of Concept

A borrower can use compensate to create  a new debtPosition/creditPosition pair to repay the new `debtPosition.futureValue` inorder to avoid ffrom the liquidation. This is done by passing the `RESERVE_ID` to `creditPositionToCompensateId`.

Borrower can also compensate the some credit of the existing `creditPositiontoCompensate` of his to the lender whom he needs to repay irrespective of whether the msg.sender is underwater or not.(borrower for `creditPositionToCompensateId` is checked)
https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/Compensate.sol#L42-L101.

But after executing the `compensate` we are checking whether the sender/borrower is underwater. This check only works if the borrower is compensating his current creditPOsition to repay.

https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/Size.sol#L247-L251

function compensate(CompensateParams calldata params) external payable override(ISize) whenNotPaused {
    state.validateCompensate(params);
    state.executeCompensate(params);
=>  state.validateUserIsNotUnderwater(msg.sender);
}

Suppose  if borrower, whose `collateralRatio` went below `minimumCRLiquidation` ,  decided to repay the lender by doing partial liquidation. 
the flow will be   `compensate` -> `repay`

When the `executeCompensate` is executed a new credit-debtPosition is created where the borrower is the same msg.sender.

But the borrower's `debt` balance wouldnt get changed untill he `repay` the created debtPosition.

So the underwater check will revert and wouldnt allow the borrower to repay.
