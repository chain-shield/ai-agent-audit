# Vulnerability details

## Impact

The insufficient fee check in the `getCreditAmountOut` function can lead to underflows in credit calculations, potentially resulting in incorrect credit issuance.

## Proof of Concept

Take a look at the `getCreditAmountOut` function of the `AccountingLibrary`:  https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/AccountingLibrary.sol#L274-L301

```solidity
function getCreditAmountOut(
    State storage state,
    uint256 cashAmountIn,
    uint256 maxCashAmountIn,
    uint256 maxCredit,
    uint256 ratePerTenor,
    uint256 tenor
) internal view returns (uint256 creditAmountOut, uint256 fees) {
    if (cashAmountIn == maxCashAmountIn) {
        // no credit fractionalization
        creditAmountOut = maxCredit;
        fees = getSwapFee(state, cashAmountIn, tenor);
    } else if (cashAmountIn < maxCashAmountIn) {
        // credit fractionalization
        if (state.feeConfig.fragmentationFee > cashAmountIn) {
            revert Errors.NOT_ENOUGH_CASH(state.feeConfig.fragmentationFee, cashAmountIn);
        }

        uint256 netCashAmountIn = cashAmountIn - state.feeConfig.fragmentationFee;

        creditAmountOut = Math.mulDivDown(netCashAmountIn, PERCENT + ratePerTenor, PERCENT);
        fees = getSwapFee(state, netCashAmountIn, tenor) + state.feeConfig.fragmentationFee;
    } else {
        revert Errors.NOT_ENOUGH_CREDIT(maxCashAmountIn, cashAmountIn);
    }
}
```

The issue occurs in the credit fractionalization case (when `cashAmountIn < maxCashAmountIn`). 

The function checks if `cashAmountIn` is greater than `fragmentationFee`:

```solidity
if (state.feeConfig.fragmentationFee > cashAmountIn) {
    revert Errors.NOT_ENOUGH_CASH(state.feeConfig.fragmentationFee, cashAmountIn);
}
```

If it passes this check, it calculates `netCashAmountIn`:

```solidity
uint256 netCashAmountIn = cashAmountIn - state.feeConfig.fragmentationFee;
```

It then calculates `creditAmountOut` based on this `netCashAmountIn`:

```solidity
creditAmountOut = Math.mulDivDown(netCashAmountIn, PERCENT + ratePerTenor, PERCENT);
```

Finally, it calculates the total `fees`:

```solidity
fees = getSwapFee(state, netCashAmountIn, tenor) + state.feeConfig.fragmentationFee;
```

The problem is that the swap fee is not considered in the initial check or in the `netCashAmountIn` calculation. For small `cashAmountIn` values, the total fees (swap fee + fragmentation fee) could exceed the `cashAmountIn`, leading to an underflow when calculating `netCashAmountIn` or incorrect credit calculation.

For example, consider this scenario:
- `cashAmountIn` = 100
- `fragmentationFee` = 50
- `swapFee` = 60

The function would proceed because 100 > 50, but then it would try to calculate:
```solidity
netCashAmountIn = 100 - 50 = 50
fees = getSwapFee(state, 50, tenor) + 50 ≈ 60 + 50 = 110
```

This results in `fees` being greater than the original `cashAmountIn`, which is problematic.

## Recommended Mitigation Steps

The function should calculate the total fees upfront and ensure that `cashAmountIn` is greater than the total fees before proceeding with the calculations. Something like this:

    State storage state,
    uint256 cashAmountIn,
    uint256 maxCashAmountIn,
    uint256 maxCredit,
    uint256 ratePerTenor,
    uint256 tenor

        // no credit fractionalization
        creditAmountOut = maxCredit;
        fees = getSwapFee(state, cashAmountIn, tenor);
    } else if (cashAmountIn < maxCashAmountIn) {
        // credit fractionalization
-       if (state.feeConfig.fragmentationFee > cashAmountIn) {
-           revert Errors.NOT_ENOUGH_CASH(state.feeConfig.fragmentationFee, cashAmountIn);
-       }
-
-       uint256 netCashAmountIn = cashAmountIn - state.feeConfig.fragmentationFee;

+       uint256 swapFee = getSwapFee(state, cashAmountIn, tenor);
