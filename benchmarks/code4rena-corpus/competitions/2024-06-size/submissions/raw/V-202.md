# Vulnerability details

## Impact
In an unprofitable liquidation scenario (where `assignedCollateral <= debtInCollateralToken`), the code aims to provide the liquidator with all the assigned collateral (`liquidatorProfitCollateralToken = assignedCollateral`). However, it fails to account for the fact that the liquidator needs to provide the full `debtPosition.futureValue` to the pool, which might be larger than the `assignedCollateral`.

> This oversight allows a liquidator to repay a portion of the borrower's debt using less collateral, effectively profiting from an unprofitable liquidation. This violates the intended functionality and can lead to inconsistencies in the protocol's accounting.

**Example:**
   - `assignedCollateral = 90`
   - `debtInCollateralToken = 100`
   - `debtPosition.futureValue = 105` (due to interest)

The liquidator would only need to provide 90 units of collateral to clear the debt position, gaining a profit of 15 units of borrow tokens.

```solidity
function executeLiquidate(State storage state, LiquidateParams calldata params)
    external
    returns (uint256 liquidatorProfitCollateralToken)
{
    // ... 

    // ... (profitable liquidation logic)

    } else {
        // unprofitable liquidation
        liquidatorProfitCollateralToken = assignedCollateral; <// BUG: Doesn't consider full debt repayment
    }

    state.data.borrowAToken.transferFrom(msg.sender, address(this), debtPosition.futureValue); // Liquidator repays debt
    state.data.collateralToken.transferFrom(debtPosition.borrower, msg.sender, liquidatorProfitCollateralToken); // Liquidator receives collateral
    // ...
}
```
**`transferFrom` function (ERC20)**
The `transferFrom` (used for both `borrowAToken` and `collateralToken`) will revert if the sender (liquidator) doesn't have sufficient balance. However, the bug allows the liquidator to send a lower amount of `borrowAToken` than required.

**Illustrative Example**

**Let's assume:**
   - 1 Collateral Token = 1 USD
   - 1 Borrow Token = 1 USD (_for simplicity_)
   - `assignedCollateral = 90 USD`
   - `debtInCollateralToken = 100 USD`
   - `debtPosition.futureValue = 105 USD` (_due to accrued interest_)

**Exploitation Scenario**
1. The liquidator calls `executeLiquidate` with only 90 USD worth of `borrowAToken`.
2. Ideally, the `transferFrom` call for `borrowAToken` should revert as the liquidator doesn't have enough to cover the full `debtPosition.futureValue` (105 USD).
3. Due to the bug, `liquidatorProfitCollateralToken` is set to 90 USD (the `assignedCollateral`), allowing the liquidator to receive all the collateral.
4. The liquidator effectively pays off a 105 USD debt with only 90 USD, gaining a 15 USD profit.

## Proof of Concept
While the `transferFrom` function should prevent this scenario, the bug in calculating `liquidatorProfitCollateralToken` bypasses this safeguard. The liquidator is not required to provide enough `borrowAToken` to cover the full debt, leading to exploitation.

## Tools Used
Manual Audit

## Recommended Mitigation Steps
Ensure that the liquidator always provides enough borrow tokens to cover the full `debtPosition.futureValue`, even in unprofitable liquidations. This might involve requiring the liquidator to add additional funds or adjusting the calculation of `liquidatorProfitCollateralToken` in such scenarios.
