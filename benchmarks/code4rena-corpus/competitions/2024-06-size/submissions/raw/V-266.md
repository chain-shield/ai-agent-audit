# Vulnerability details

## Impact
The *lack of validation* for the **min** and **max** prices from **Chainlink Aggregators** allows the system to accept **invalid** or **manipulated** prices. This leads to **incorrect calculations** and potential **financial loss** for the protocol and its users. 
If the protocol does not check the **min** and **max** prices, it can trust **stale** or **out-of-bound** prices, leading to severe consequences such as *erroneous liquidations*, *incorrect borrow limits*, and *overall protocol instability*.
The issue affects a core functionality of the protocol and price manipulation attacks on oracles are not uncommon in DeFi. 
Furthermore, as the protocol expands to integrate new tokens in the future, this vulnerability could potentially escalate to a high-risk issue. The increased number of price feeds associated with a broader range of tokens amplifies the potential attack surface, making the implementation of robust price validation mechanisms more critic.


## Proof of Concept

### Initial code
The current implementation of ``validateInitializeOracleParams`` in ``Initialize.sol`` only checks if the price feed is not a zero address and ensures it returns a price, without verifying the min and max prices.

```solidity
function validateInitializeOracleParams(InitializeOracleParams memory o) internal view {
    // validate priceFeed
    if (o.priceFeed == address(0)) {
        revert Errors.NULL_ADDRESS();
    }
    // slither-disable-next-line unused-return
    IPriceFeed(o.priceFeed).getPrice();
}
```

### Workflow 
To demonstrate the impact of this issue, let's consider the following scenario.

#### Scenario: ETH/USD price manipulation

##### Initial/Normal state
- ETH/USD price: $3,000
- Borrowing limit: 50% of collateral value

A user deposits 10 ETH as collateral:
- Collateral value: 10 * $3,000 = $30,000
- Borrowing limit: $30,000 * 0.5 = $15,000

##### Oracle manipulation
- Manipulated ETH/USD price: $4,000

The protocol accepts the new price without verification:
- New collateral value: 10 * $4,000 = $40,000
- New borrowing limit: $40,000 * 0.5 = $20,000

The user borrows the maximum possible amount:
They borrow $20,000 in stablecoins based on the new valuation.

The price returns to normal:
- ETH/USD price: $3,000
- Real collateral value: 10 * $3,000 = $30,000

##### Result
- User's debt: $20,000
- Collateral value: $30,000

This demonstrates how the lack of min/max price verification can lead to:
- Excessive borrowing based on incorrect valuations.
- Insolvency risk for the protocol.
- Potential losses for other protocol users.

By implementing the recommended checks, the protocol could have rejected the manipulated price of $40,000 if it was outside predefined min/max limits (e.g., ±2% of the last valid price), thus avoiding this over-borrowing situation.

## Recommended mitigation steps
**Implement Min/Max Price Validation**, enhancing the ``validateInitializeOracleParams`` function to include checks for ``getMinPrice`` and ``getMaxPrice``.
Additionally, in standard liquidation, the *collateral remainder* is implicitly capped by ``crLiquidation``. This is because users can only be liquidated if they are underwater.

### Enhanced code
Add checks for ``getMinPrice`` and ``getMaxPrice`` in ``Initialize.sol``:

```solidity
function validateInitializeOracleParams(InitializeOracleParams memory o) internal view {
    // validate priceFeed
    if (o.priceFeed == address(0)) {
        revert Errors.NULL_ADDRESS();
    }

    uint256 price = IPriceFeed(o.priceFeed).getPrice();
    uint256 minPrice = IPriceFeed(o.priceFeed).getMinPrice();
    uint256 maxPrice = IPriceFeed(o.priceFeed).getMaxPrice();

    // validate minPrice and maxPrice
    if (price < minPrice || price > maxPrice) {
        revert Errors.INVALID_PRICE_RANGE(price, minPrice, maxPrice);
    }

    // validate the price is non-negative
    if (price <= 0) {
        revert Errors.NEGATIVE_PRICE(price);
    }
}
```

Add the two new error definitions in ``Errors.sol``:
```solidity
error INVALID_PRICE_RANGE(uint256 price, uint256 minPrice, uint256 maxPrice);
error NEGATIVE_PRICE(uint256 price);
```
