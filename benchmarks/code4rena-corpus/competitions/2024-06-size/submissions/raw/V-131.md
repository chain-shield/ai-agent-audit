# Vulnerability details

## Impact
In the assumption that the collateral token (`collateralToken`) and the price returned by the oracle (`state.oracle.priceFeed.getPrice()`) are both denominated in the exact decimals (18 decimals in this case, as the code is designed for WETH as collateral).

However, in a reverse market scenario where USDC is the collateral token, the `collateralToken.balanceOf(account)` would return the USDC balance with 6 decimals. In comparison, the price feed would still return the price in 18 decimals. This mismatch in decimals would lead to incorrect calculations in the `collateralRatio` function.

## Proof of Concept
The `collateralRatio` function in the [RiskLibrary contract:L53-L64](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/RiskLibrary.sol#L53-L64)
```solidity
function collateralRatio(State storage state, address account) public view returns (uint256) {
    uint256 collateral = state.data.collateralToken.balanceOf(account);
    uint256 debt = state.data.debtToken.balanceOf(account);
    uint256 debtWad = Math.amountToWad(debt, state.data.underlyingBorrowToken.decimals());
    uint256 price = state.oracle.priceFeed.getPrice();

    if (debt != 0) {
        return Math.mulDivDown(collateral, price, debtWad);
    } else {
        return type(uint256).max;
    }
}
```
Let's consider a scenario where the protocol is deployed with the following configuration:
   - Borrow Token: USDC (6 decimals)
   - Collateral Token: WETH (18 decimals)
   - Price Feed: Returns the price of WETH in USDC, scaled to 18 decimals
   - `crLiquidation`: Set to 150% (1.5 * 10^18)

Suppose a user has the following positions:
   - USDC Debt: 1000 USDC (1000 * 10^6)
   - WETH Collateral: 1 WETH (1 * 10^18)
   - Price of WETH: 2000 USDC (2000 * 10^18)
   
Now, let's trace the execution of the `collateralRatio` function
```solidity
uint256 collateral = 1 * 10^18; // WETH balance with 18 decimals
uint256 debt = 1000 * 10^6; // USDC debt with 6 decimals
uint256 debtWad = 1000 * 10^18; // Debt in Wad (18 decimals)
uint256 price = 2000 * 10^18; // Price of WETH in USDC, scaled to 18 decimals

uint256 ratio = Math.mulDivDown(collateral, price, debtWad);
// ratio = (1 * 10^18) * (2000 * 10^18) / (1000 * 10^18)
// ratio = 2 * 10^18 (200%)
```
In this case, the calculated collateral ratio is 200%, which is correct.

However, let's consider the reverse market scenario where WETH is the borrow token, and USDC is the collateral token:
```solidity
uint256 collateral = 2000 * 10^6; // USDC balance with 6 decimals
uint256 debt = 1 * 10^18; // WETH debt with 18 decimals
uint256 debtWad = 1 * 10^18; // Debt in Wad (18 decimals)
uint256 price = 5 * 10^17; // Price of USDC in WETH, scaled to 18 decimals (0.5 WETH per USDC)

uint256 ratio = Math.mulDivDown(collateral, price, debtWad);
// ratio = (2000 * 10^6) * (5 * 10^17) / (1 * 10^18)
// ratio = 1000 * 10^5 (10%)
```
In this reverse market scenario, the collateral ratio needs to be correctly calculated as 10% due to the mismatch in decimals between USDC and WETH. The correct ratio should be 100% (2000 USDC / 1 WETH).

This incorrect collateral ratio can lead to issues in other functions like `isUserUnderwater`
```solidity
bool underwater = isUserUnderwater(state, account);
// underwater = (1000 * 10^5) < (1.5 * 10^18)
// underwater = true (incorrectly flagged as underwater)
```
In this case, the user's position would be incorrectly flagged as underwater because the crLiquidation value (1.5 * 10^18) is compared against the incorrectly calculated collateral ratio (1000 * 10^5).

Similarly, the `debtTokenAmountToCollateralTokenAmount` function would also produce incorrect results in the reverse market scenario
```solidity
uint256 debtTokenAmount = 1 * 10^18; // 1 WETH
uint256 collateralTokenAmount = debtTokenAmountToCollateralTokenAmount(state, debtTokenAmount);
// collateralTokenAmount = (1 * 10^18) * (1 * 10^18) / (5 * 10^17)
// collateralTokenAmount = 2 * 10^19 (incorrect result)
```
The function incorrectly calculates the equivalent collateral token amount as 2 * 10^19 USDC, much higher than the actual value of 2 USDC (2 * 10^6).

These examples demonstrate how the mismatch in decimals between the borrow token and collateral token can lead to incorrect calculations and potentially cause issues in various protocol functions.

## Recommended Mitigation Steps
1. Introduce a configuration value or a separate function to handle the reverse market case, where the collateral token decimals are considered.

2. Modify the collateralRatio function to scale the collateral value based on the decimals of the collateral token. For example:
```solidity
uint256 collateral = Math.amountToWad(state.data.collateralToken.balanceOf(account), state.data.collateralToken.decimals());
```
