# Vulnerability details

## Impact
The `collateralRatio` function does not consider the decimals of the `collateralToken` when calculating the collateral ratio. The function correctly converts the debt to a wad (18 decimal places) using `Math.amountToWad` and the decimals of the `underlyingBorrowToken`. However, it directly uses the balance of the `collateralToken` without adjusting for its decimals.

## Proof of Concept
The `collateralRatio` function in [RiskLibrary.sol#L53-L64](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/RiskLibrary.sol#L53-L64)
```solidity
function collateralRatio(State storage state, address account) public view returns (uint256) {
    uint256 collateral = state.data.collateralToken.balanceOf(account);
    uint256 debt = state.data.debtToken.balanceOf(account);
    uint256 debtWad = Math.amountToWad(debt, state.data.underlyingBorrowToken.decimals());
    uint256 price = state.oracle.priceFeed.getPrice();

    if (debt != 0) {
        return Math.mulDivDown(collateral, price, debtWad);
    } else {
        return type(uint256).max;
    }
}
```
The `amountToWad` function in [Math.sol:L31-L33](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/Math.sol#L31-L33)
```solidity
function amountToWad(uint256 amount, uint256 decimals) internal pure returns (uint256) {
    return amount * 10**(18 - decimals);
}
```
The `mulDivDown` function in [Math.sol:L27-L29](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/Math.sol#L27-L29)
```solidity
    function mulDivDown(uint256 x, uint256 y, uint256 z) internal pure returns (uint256) {
        return FixedPointMathLib.mulDiv(x, y, z);
    }
```
The bug occurs because the `collateralRatio` function does not consider the decimals of the `collateralToken` when calculating the collateral ratio. It directly uses the balance of the `collateralToken` (collateral) in the calculation without converting it to a wad (18 decimal places).

On the other hand, the debt is correctly converted to a wad using `Math.amountToWad` and the decimals of the `underlyingBorrowToken`. This inconsistency leads to an incorrect collateral ratio calculation.

The impact of this bug can be significant:
   - If the `collateralToken` has fewer decimals than 18, the collateral value will be underestimated, resulting in a lower collateral ratio than the actual value.
   - If the `collateralToken` has more decimals than 18, the collateral value will be overestimated, resulting in a higher collateral ratio than the actual value.

This bug can lead to incorrect risk assessments and potential financial losses for users and the protocol.

Assume the `collateralToken` has 6 decimals (e.g., USDC).
Assume the `underlyingBorrowToken` has 18 decimals (e.g., ETH or DAI).
User A has a balance of 1,000,000 `collateralToken` (equivalent to 1,000 USDC).
User A has a debt of 500,000,000,000,000,000,000 `debtToken` (equivalent to 500 DAI).
The price of the `collateralToken` is 1 (1 USDC = 1 USD).

**Expected behavior:**
   - The collateral value should be converted to a wad (18 decimal places) before the calculation.
   - The expected collateral ratio should be: (1,000 * 10^18) / 500 = 2 * 10^18 (200% collateral ratio).

**Actual behavior with the bug:**
   - The `collateralRatio` function directly uses the balance of the `collateralToken` without converting it to a wad.
   - The actual calculation performed is: (1,000,000 * 1) / 500 = 2,000 (0.2% collateral ratio).

## Recommended Mitigation Steps
The collateral value should also be converted to a wad using `Math.amountToWad` and the decimals of the `collateralToken`, ensuring consistency with the debt calculation. The collateral ratio calculation will be accurate and consistent by converting both `collateral` and `debt` to wads based on their respective token decimals.
```solidity
uint256 collateralWad = Math.amountToWad(collateral, state.data.collateralToken.decimals());
```
