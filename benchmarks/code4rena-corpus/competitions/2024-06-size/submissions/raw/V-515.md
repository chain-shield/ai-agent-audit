# Vulnerability details

## Description
The contract initializes the Aave variable pool address during its setup phase and subsequently does not offer an option to update this address. According to Aave’s [documentation](https://docs.aave.com/developers/core-contracts/pooladdressesprovider), the pool address from their `PoolAddressesProvider` should not be hardcoded because it is subject to change [proof](https://github.com/aave/aave-v3-core/blob/6070e82d962d9b12835c88e68210d0e63f08d035/contracts/protocol/configuration/PoolAddressesProvider.sol#L57). Instead, it is recommended to query the `PoolAddressesProvider` every time the pool address is needed to ensure the address used is current.

This configuration is a critical design oversight because Aave administrators have the ability to migrate the pool to a new address at any time, a functionality that has been in place since Aave V1. This migration feature addresses the need for flexibility in response to evolving blockchain conditions and is crucial for maintaining operational continuity.

Historically, from Aave V1 through to V3, the documents have emphasized that the `LendingPool` address can be added or modified. This is why the documentation for V2 and V3 explicitly advises fetching the pool address from `PoolAddressesProvider` each time it’s needed. By hardcoding the pool address, our current implementation not only goes against these recommendations but also risks the contract becoming non-functional if the pool address changes. Redeploying the contract to fix such an issue is not viable because it’s labor-intensive and does not constitute an easy fix. Instead, an ideal solution would allow the contract to continue operating without needing a redeploy, simply by fetching the current pool address dynamically.

## Impact
This limitation is significant because it restricts the contract’s ability to adapt to changes in the Aave protocol. If the Aave pool address changes, the inability to update the address means that all interactions with the Aave pool would fail, leading to operational disruptions. This is a critical issue since it could render the affected functionalities of the smart contract obsolete.

## Proof of Concept
The initialization of the Aave variable pool address is handled in the `executeInitializeData` function within the `Initialize` library, where it sets the pool address at deployment. However, the `executeUpdateConfig` function, which handles updates to configuration settings, does not include functionality to update the Aave pool address.

Here are the relevant code sections:
- Setting the Aave pool address during initialization (only at deployment):
  ```solidity
  function executeInitializeData(State storage state, InitializeDataParams memory d) internal {
      ...
      state.data.variablePool = IPool(d.variablePool);
      ...
  }
  ```
- The `executeUpdateConfig` function lacks the capability to update the `variablePool`:
  ```solidity
  function executeUpdateConfig(State storage state, UpdateConfigParams calldata params) external {
      ...
      // No case for updating 'variablePool'
      ...
  }
  ```

## Recommended Mitigation Steps
**Modify Contract Code**: Update the contract code to remove the hardcoded pool address. Instead, insert a function call to `PoolAddressesProvider.getPool()` within every function that interacts with the Aave pool.
