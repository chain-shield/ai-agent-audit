# Vulnerability details

I have discovered some potential weaknesses and attack vectors that a malicious actor could exploit. Here is a comprehensive report outlining these issues:

1. Reentrancy vulnerability

I found a potential reentrancy vulnerability in the `withdraw()` function of the `NonTransferrableScaledToken` contract (`src/token/NonTransferrableScaledToken.sol`). A malicious actor could potentially exploit this vulnerability to drain funds from the contract. Here is the vulnerable code:

```solidity
function withdraw() public {
    uint256 amount = balanceOf[msg.sender];
    balanceOf[msg.sender] = 0;
    payable(msg.sender).transfer(amount);
}
```

An attacker can recursively call the `withdraw()` function while the first call is still being processed. This can result in the attacker draining more funds than they should be able to. To mitigate this vulnerability, the `balanceOf[msg.sender]` variable should be set to 0 after the `transfer()` function call, like this:

```solidity
function withdraw() public {
    uint256 amount = balanceOf[msg.sender];
    payable(msg.sender).transfer(amount);
    balanceOf[msg.sender] = 0;
}
```

2. Integer overflows and underflows

I also found some potential integer overflows and underflows in the `Math` library (`src/libraries/Math.sol`). These can lead to security vulnerabilities and incorrect contract behavior. Here are some examples:

* In the `add()` function:
```csharp
function add(uint256 a, uint256 b) internal pure returns (uint256) {
    return a + b;
}
```
If `a` and `b` are both the maximum value of `uint256`, the result of the addition will be 0, which may not be the expected behavior.
* In the `sub()` function:
```csharp
function sub(uint256 a, uint256 b) internal pure returns (uint256) {
    require(b <= a, "Math: sub underflow");
    return a - b;
}
```
If `b` is greater than `a`, the `sub()` function will revert the transaction, but if `b` is equal to `a`, the result will be 0. This may not be the desired behavior.

To prevent integer overflows and underflows, you should use the `SafeMath` library or check for overflow and underflow conditions using the `require()` statement.

3. Centralized trust

The `PriceFeed` contract (`src/oracle/PriceFeed.sol`) relies on a centralized price feed for obtaining the price of assets. This can lead to a single point of failure, as the contract is only as reliable as the price feed it depends on. If the price feed is compromised or becomes unavailable, the contract's functionality can be affected. To mitigate this risk, you can use decentralized price feeds or multiple price feeds to ensure redundancy and reliability.
