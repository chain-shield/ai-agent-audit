# Vulnerability details

## Impact
This logic vulnerability occurs in the `createCreditPosition` function, specifically when handling the existing credit limit. When the requested credit limit (credit) is not equal to the existing credit limit (exitCreditPosition.credit), the `reduceCredit` function is called to adjust it, but after the operation, the `forSale` of the existing credit limit is not marked as `false`.

## Proof of Concept
The specific exploit flow is as follows:

1. **Amount mismatch when creating a credit line:**
- Assume that a `creditPosition` (e.g. `exitCreditPositionId`) exists with a credit line of 1000 units.
- Some other entity (not the lender of the original `creditPosition`) calls `createCreditPosition`, intending to create a new position by providing an `exitCreditPositionId` and setting `credit = 200`.

2. **Reduction of the original credit line:**
- Since the requested credit line (200) is not equal to the existing credit line (1000), the `reduceCredit` function is called to subtract 200 units from the original credit line, leaving 800 units (`exitCreditPosition.credit = 800`).

3. **Subsequent interactions:**
- The original `CreditPosition` (now holding 800 units) remains `forSale = true`. This state allows other entities to interact with this credit under the assumption that it is fully available for trading, even though some of the credit has been allocated elsewhere.

4. **Multiple transactions:**
- Multiple entities may interact with the original credit under the assumption that its full credit is available for new transactions, resulting in over-selling or incorrect double allocation of credit.

### Assume we have a CreditPosition whose initial state is as follows:

	•	exitCreditPositionId: 1
	•	exitCreditPosition.credit: 1000
	•	exitCreditPosition.forSale: true

**First call to createCreditPosition**
1.Calling parameters:
```sol
createCreditPosition(state, 1, 0xLenderA, 200);
```
2. Processing logic:
• exitCreditPosition.credit = 1000
• credit = 200
• Because credit is not equal to exitCreditPosition.credit, call reduceCredit function.
3. After reduceCredit is executed:
• exitCreditPosition.credit = 1000 - 200 = 800
4. Create a new CreditPosition:
• New creditPosition:
```sol
CreditPosition({
    lender: 0xLenderA,
    credit: 200,
    debtPositionId: exitCreditPosition.debtPositionId,
    forSale: true
});
```
• The forSale state of exitCreditPosition is not changed and remains true.
**Second call to createCreditPosition**
1.Calling parameters:
```sol
createCreditPosition(state, 1, 0xLenderB, 300);
```
2. Processing logic:
• exitCreditPosition.credit = 800
• credit = 300
• Because credit is not equal to exitCreditPosition.credit, call reduceCredit function.
3. After reduceCredit is executed:
• exitCreditPosition.credit = 800 - 300 = 500
4. Create a new CreditPosition:
• New creditPosition:
```sol
CreditPosition({
    lender: 0xLenderB,
    credit: 300,
    debtPositionId: exitCreditPosition.debtPositionId,
    forSale: true
});
```
• The forSale state of exitCreditPosition is not changed and remains true.

In this case, the credit line of exitCreditPosition has been partially allocated to other lenders multiple times, but its forSale state remains true. This causes the system to believe that the remaining units are still available and can continue to be traded by other entities.

The potential result of this vulnerability is that the same credit in `exitCreditPosition` can be inappropriately utilized in multiple transactions while still marked as `forSale = true`, which may cause significant inconsistencies and confusion in the handling of credits in the system, affecting the integrity of financial activities.

## Recommended Mitigation Steps
Modify the `reduceCredit` function or the `createCreditPosition` function to include a step to set `forSale` to `false` if the credit portion of the `exitCreditPosition` is transferred out (i.e., every time `reduceCredit` is used). This ensures that the credit remaining in the `exitCreditPosition` cannot ambiguously attract further transactions until explicitly marked for sale again.

```sol
function reduceCredit(State storage state, uint256 creditPositionId, uint256 amount) public {
    CreditPosition storage creditPosition = state.getCreditPosition(creditPositionId);
    
    require(creditPosition.credit >= amount, "Insufficient credit to reduce");
    
    creditPosition.credit -= amount;
    creditPosition.forSale = false; // Set forSale to false when credit is reduced
    state.validateMinimumCredit(creditPosition.credit);

    emit Events.UpdateCreditPosition(
        creditPositionId, creditPosition.lender, creditPosition.credit, creditPosition.forSale
    );
}
```
