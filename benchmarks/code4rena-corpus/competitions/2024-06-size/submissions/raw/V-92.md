# Vulnerability details

## Impact
Whales can DoS the usage of the protocol for users

## Proof of Concept
Upon depositing USDC into the protocol, there is a check that enforces a maximum total supply of the `borrowAToken`. If that cap is reached, then deposits will revert.
```solidity
if (params.token == address(state.data.underlyingBorrowToken)) {
            state.depositUnderlyingBorrowTokenToVariablePool(from, params.to, amount);
            // borrow aToken cap is not validated in multicall,
            //   since users must be able to deposit more tokens to repay debt
            if (!state.data.isMulticall) {
                state.validateBorrowATokenCap();
            }
        }
```
Depending on the cap (sponsors have confirmed that this the cap might be used for a guarded launch and the cap might be $1M), USDC whales can frontrun deposits of users that they want to DoS and deposit an amount that would put the total supply of `borrowAToken` right at the cap and thus DoS the user as the user would put the total supply of `borrowAToken` over the cap with his deposit. Then, the whale can simply backrun his transaction and withdraw his tokens, essentially DoS-ing any user (or even all users) that he doesn't want in the protocol. This will cost him absolutely nothing as there are no penalties for exiting, he will only have to pay for gas.
## Tools Used
Manual Review
## Recommended Mitigation Steps
An option would be to implement a penalty depending on how quick users exit the system or disallow users from exiting in the same block they deposited in (second option wouldn't really solve the issue completely but at least, it would make the whales stay for the block). Also, implementing a minimum amount of blocks users have to stay in the system is an option.
