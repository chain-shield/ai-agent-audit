# Vulnerability details

## Impact
The size protocol recently added a feature that enables borrowers to partially repay debt. This can be done as follows:

1. Alice Borrows 100,000 from Bob.
2. Alice wants to repay 30,000.
3. Alice executes the compensate function, which creates a new debt/credit pair worth 30,000, and reduces original debt/credit pair with 30,000.
4. Alice executes the repay function using the new partial debt position, and will now have an outstanding debt of 70,000.

This process can be executed in a single multicall, with:

1. Debt fragmentation via compensation in first call.
2. Partial repayment of debt fragment in second call via repay function.

The ability for a borrower to partially repay debt is critical, especially if the borrower's position suddenly becomes underwater. By partially repaying, the borrower can promptly adjust their positions without full repayment to avoid liquidation. In addition, allowing users to partially repay debt when underwater should be incentivized by the protocol, since it improves the overall health of the system.

However, with the current design, it is not possible for a user to partially repay debt if they are already underwater. This is because the call to the compensate function will always revert if the user is already underwater, before giving them the ability to repay the partial debt.

        function compensate(CompensateParams calldata params) external payable override(ISize) whenNotPaused {
        state.validateCompensate(params);
        state.executeCompensate(params);
        // @audit, if user is already underwater, this will revert,
        // meaning subsequent attempts to partially repay will never execute
        state.validateUserIsNotUnderwater(msg.sender);
    }

The code above highlights the issue, after any compensation call is complete, validation that the user is not underwater is done via validateUserIsNotUnderwater. but if this check fails. then the user will never be able to call the repay on partial debt in the multicall.

The impact of not being able to partially repay debt while underwater is unfair liquidations, and total loss of collateral.

THE POC above demonstrates the following:

1. Bob takes out a loan of 120000e6 from alice via sellCreditMarket.
2. price of collateral drops, and Bob's position is underwater.
3. Bob attempts to fragment his debt via compensate function, in order to later on call repay on partial new debt position.
4. call to compensate reverts with error "USER_IS_UNDERWATER".

## Recommended Mitigation Steps
One suggestion is to modify the compensate function within the Size.sol contract. If the objective of the compensation is to partially fragment debt, then the underwater check should not be performed. please note that  given the complex role of the compensate function, it is advised to add this feature carefully in order to not introduce additional bugs.
