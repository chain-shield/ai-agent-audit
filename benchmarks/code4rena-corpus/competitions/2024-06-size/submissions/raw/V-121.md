# Vulnerability details

User can deposit collateral if they want to borrow or borrow tokens if they wan to lend, here is the function:

```solidity
 function deposit(DepositParams calldata params) public payable override(ISize) whenNotPaused {
        state.validateDeposit(params);
        state.executeDeposit(params);
    }
```
[[Link]](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/Size.sol#L153)

First the function validate the params and then execute the Deposit:

```solidity

 function executeDeposit(State storage state, DepositParams calldata params) public {
        address from = msg.sender;
        uint256 amount = params.amount;
        ...
        if (params.token == address(state.data.underlyingBorrowToken)) {
            state.depositUnderlyingBorrowTokenToVariablePool(from, params.to, amount);
            // borrow aToken cap is not validated in multicall,
            //   since users must be able to deposit more tokens to repay debt
            if (!state.data.isMulticall) {
                state.validateBorrowATokenCap();  <------
            }
        } else {
            state.depositUnderlyingCollateralToken(from, params.to, amount);
        }

        emit Events.Deposit(params.token, params.to, amount);
    }
```
[[Link]](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/Deposit.sol#L81)

If the call is not through multicall and the deposit is borrow token. there is a check if the deposit does not surpass the cap.(see arrow above)

The problem if that since there is not a mechanism to prevent lenders to deposit and withdraw in the same timestamp or seconds. An attacker can a always  DoS the deposit functions. 


## Impact
An attacker can always make revert a deposit borrow token of the honest user, successfully Dos the deposit function. (specialist attacker have a lot funds and knowledge to make this attack successfully, this can be scaled to let the project unusable).

## Proof of Concept
To understand the vuln and see the snipped code see the description.

This is the step step of the attack:

1. Attacker see a deposit borrow token honest user transaction.
2. attacker fill the cap front runing the user transaction.
3. deposit transaction revert for the user because the cap is full.
4. Then attacker withdraw successfully DoS the deposit function.

## Tools Used

## Recommended Mitigation Steps
Add mechanism to prevent lenders to deposit and withdraw in the same timestamp ,seconds, or days. another solution is add some kind of fees for withdrawing.
