# Vulnerability details

## Impact
A malicious user can exploit the function to trick the system into thinking he made several repayment causing unintended behavior for the protocol

## Proof of Concept
To illustrate a potential reentrancy exploit with a scenario involving value, let's consider an example where an attacker takes advantage of the vulnerability in the executeRepay function.

Scenario Setup
Smart Contract: The vulnerable contract with the executeRepay function.
Attacker Contract: A malicious contract created by the attacker.
Attacker: A user controlling the malicious contract and initiating the attack.
Token: An ERC20 token being used for repayment in the executeRepay function.

Attacker Contract
The attacker contract is designed to exploit the reentrancy vulnerability by calling the executeRepay function recursively before the state changes are completed.

```javascript
contract AttackerContract {
    VulnerableContract public vulnerableContract;
    uint256 public debtPositionId;

    constructor(address _vulnerableContract, uint256 _debtPositionId) {
        vulnerableContract = VulnerableContract(_vulnerableContract);
        debtPositionId = _debtPositionId;
    }

    function attack() external {
        // Initiate the attack by calling executeRepay
        vulnerableContract.executeRepay(debtPositionId, address(this));
    }

    function onERC20Received(address, address, uint256, bytes calldata) external returns (bytes4) {
        // Reenter the executeRepay function before state changes are finalized
        if (address(vulnerableContract).balance > 0) {
            vulnerableContract.executeRepay(debtPositionId, address(this));
        }
        return this.onERC20Received.selector;
    }
}
```
Attack Flow
Setup: The attacker deploys the AttackerContract with the address of the VulnerableContract and the debtPositionId they wish to exploit.
Initiate Attack: The attacker calls the attack function on the AttackerContract.
First Call to executeRepay:
The executeRepay function is called on the VulnerableContract.
The transferFrom function is called, transferring tokens from the AttackerContract to the VulnerableContract.
Before the function can update the state and mark the debt as repaid, the onERC20Received function in the AttackerContract is triggered.
Reentrancy:
The onERC20Received function calls executeRepay again, reentering the function before the state update is completed.
This allows the attacker to call the function multiple times, transferring tokens repeatedly and causing multiple repayments without properly updating the state.
Drain Funds:
By repeatedly reentering the executeRepay function, the attacker can drain the funds or tokens from the contract.
Result
The attacker successfully exploits the reentrancy vulnerability, causing the contract to transfer more tokens than intended and potentially draining the contract of its funds or causing an incorrect state.

## Recommended Mitigation Steps
To prevent such attacks, the executeRepay function should follow the "Checks-Effects-Interactions" pattern, ensuring that state changes occur before any external calls. Additionally, using reentrancy guards from libraries like OpenZeppelin can add an extra layer of protection.
