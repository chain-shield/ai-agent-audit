# Vulnerability details

## Impact
- Validation for cap limit violoations in `multicall` is ineffective thus allowing anyone to bypass the deposit cap limit.  

## Description
`Deposit.sol#executeDeposit` checks that a deposited borrow token (USDC) does not exceed the total cap limit.  
See: [Deposit.sol#L64-L89](https://github.com/code-423n4/2024-06-size/blob/main/src/libraries/actions/Deposit.sol#L64-L89)  
```solidity
    function executeDeposit(State storage state, DepositParams calldata params) public {
        address from = msg.sender;
        uint256 amount = params.amount;
        if (msg.value > 0) {
            // do not trust msg.value (see `Multicall.sol`)
            amount = address(this).balance;
            // slither-disable-next-line arbitrary-send-eth
            state.data.weth.deposit{value: amount}();
            state.data.weth.forceApprove(address(this), amount);
            from = address(this);
        }

        if (params.token == address(state.data.underlyingBorrowToken)) {
            state.depositUnderlyingBorrowTokenToVariablePool(from, params.to, amount);
            // borrow aToken cap is not validated in multicall,
            //   since users must be able to deposit more tokens to repay debt
            if (!state.data.isMulticall) {
                state.validateBorrowATokenCap(); <@ the check
            }
        } else {
            state.depositUnderlyingCollateralToken(from, params.to, amount);
        }

        emit Events.Deposit(params.token, params.to, amount);
    }
```
The check is in `CapsLibrary.sol#validateBorrowATokenCap`.  
It explicitly checks taht the `totalSupply` of a borrow token does not exceed config limit.  
See: [CapsLibrary.sol#L52-L58](https://github.com/code-423n4/2024-06-size/blob/main/src/libraries/CapsLibrary.sol#L52-L58)  
```solidity
    function validateBorrowATokenCap(State storage state) external view {
        if (state.data.borrowAToken.totalSupply() > state.riskConfig.borrowATokenCap) {
            revert Errors.BORROW_ATOKEN_CAP_EXCEEDED(
                state.riskConfig.borrowATokenCap, state.data.borrowAToken.totalSupply()
            );
        }
    }
```

However, after an audit with Spearbit, a concern was raised that cap limit mechanism can prevent users from repaying their debt since they are unable to deposit the amount exceeding total cap limit.  

See [2024-05-30-Spearbit-draft.pdf](https://github.com/code-423n4/2024-06-size/blob/main/audits/2024-05-30-Spearbit-draft.pdf)  
Page 19 / Issue 6.7  

Therefore, another mechanism is introduced in the `Multicall` library to allow users to deposit more than the cap limit and repay their debt. Note that it should allow users to deposit beyond the cap *if and only if* they are using that amount to repay their debt.  

Size enforces this by waiving the deposit cap limit if the deposit function is called via multicall and do the validation at the end of multicall.  
See: [Multicall.sol#L26-L46](https://github.com/code-423n4/2024-06-size/blob/main/src/libraries/Multicall.sol#L26-L46)  
```solidity
    function multicall(State storage state, bytes[] calldata data) internal returns (bytes[] memory results) {
        state.data.isMulticall = true;

        uint256 borrowATokenSupplyBefore = state.data.borrowAToken.balanceOf(address(this));
        uint256 debtTokenSupplyBefore = state.data.debtToken.totalSupply();

        results = new bytes[](data.length);
        for (uint256 i = 0; i < data.length; i++) {
            results[i] = Address.functionDelegateCall(address(this), data[i]);
        }

        uint256 borrowATokenSupplyAfter = state.data.borrowAToken.balanceOf(address(this));
        uint256 debtTokenSupplyAfter = state.data.debtToken.totalSupply();

        state.validateBorrowATokenIncreaseLteDebtTokenDecrease(
            borrowATokenSupplyBefore, debtTokenSupplyBefore, borrowATokenSupplyAfter, debtTokenSupplyAfter
        ); @< validates whether the post-condition is satisfied

        state.data.isMulticall = false;
    }
```  

It attempts to check that the increase in supply is corresponding with the decrease in debt, effectively checking that a new deposit is used only to repay the debt.  
See: [CapsLibrary.sol#L19-L44](https://github.com/code-423n4/2024-06-size/blob/main/src/libraries/CapsLibrary.sol#L19-L44)
```solidity
    function validateBorrowATokenIncreaseLteDebtTokenDecrease(
        State storage state,
        uint256 borrowATokenSupplyBefore,
        uint256 debtTokenSupplyBefore,
        uint256 borrowATokenSupplyAfter,
        uint256 debtTokenSupplyAfter
    ) external view {
        // If the supply is above the cap
        if (borrowATokenSupplyAfter > state.riskConfig.borrowATokenCap) {
            uint256 borrowATokenSupplyIncrease = borrowATokenSupplyAfter > borrowATokenSupplyBefore
                ? borrowATokenSupplyAfter - borrowATokenSupplyBefore
                : 0;
            uint256 debtATokenSupplyDecrease =
                debtTokenSupplyBefore > debtTokenSupplyAfter ? debtTokenSupplyBefore - debtTokenSupplyAfter : 0;

            // and the supply increase is greater than the debt reduction
            if (borrowATokenSupplyIncrease > debtATokenSupplyDecrease) {
                // revert
                revert Errors.BORROW_ATOKEN_INCREASE_EXCEEDS_DEBT_TOKEN_DECREASE(
                    borrowATokenSupplyIncrease, debtATokenSupplyDecrease
                );
            }
            // otherwise, it means the debt reduction was greater than the inflow of cash: do not revert
        }
        // otherwise, the supply is below the cap: do not revert
    }
```
However, the validation mechanism is flawed because it retrieves the `borrowAToken` supply from the wrong source. Specifically, the multicall function gets the `borrowAToken` supply before and after executing operations, but it uses `balanceOf(address(this))` instead of `totalSupply()`.  

`borrowAToken.balanceOf(address(this))` represents an amount of token being repaid, not the acutual supply of `borrowAToken`. This leads to an incorrect validation of the cap limit violation.  

Here is an illustrative example.  

**Initial state**  
```
borrowATokenCap = 1_000_000 USDC
Alice's deposit = 1_000_000 USDC
borrowATokenSupply = 1_000_000 USDC
balanceOf(address(this)) = 0 USDC @< assume there is no repayment of any debts
```  

Alice then uses `multicall` to deposit another 100_000 USDC. The `borrowATokenSupplyAfter` in validation's function would be `0` since it uses `balanceOf(address(this))` which will pass validation: `0 > 1_000_000` is false.  

However, the actual `borrowATokenSupply` would be 1_100_000 USDC which violates the cap limit of 1_000_000 USDC.  
This, in turn, renders the validation ineffective, and allow anyone to bypass the cap limit.  

## Proof-of-Concept
The test below demonstrates that anyone can deposit more than cap limit via multicall.  
**Steps**
1. Add below test in `2024-06-size/test/local/actions/Multicall.t.sol`  
2. Run `forge test --match-contract MulticallTest --match-test test_Multicall_multicall_bypasses_cap_for_deposit -vv`  
3. Observe that the test passes proving that `borrowAToken.totalSupply()` is greater than `borrowATokenCap`

```solidity
function test_Multicall_multicall_bypasses_cap_for_deposit() public {
    // set cap at 100e6
    uint256 cap = 100e6;
    _updateConfig("borrowATokenCap", cap);

    // bob deposits 100e6 at maximum cap
    // _deposit already did mint, approve and prank for bob
    _deposit(bob, usdc, 100e6);

    _approve(bob, address(usdc), address(size), 100e6);
    _mint(address(usdc), bob, 100e6);
    // normal deposit fail due to excedding cap
    vm.expectRevert(abi.encodeWithSelector(Errors.BORROW_ATOKEN_CAP_EXCEEDED.selector, cap, cap + 100e6));
    vm.prank(bob);
    size.deposit(DepositParams({token: address(usdc), amount: 100e6, to: bob}));

    // deposit via multicall bypass the cap limit
    bytes[] memory data = new bytes[](1);
    data[0] = abi.encodeCall(size.deposit, DepositParams({token: address(usdc), amount: 100e6, to: bob}));
    vm.prank(bob);
    size.multicall(data);

    assertGt(size.data().borrowAToken.totalSupply(), size.riskConfig().borrowATokenCap );
}
```
