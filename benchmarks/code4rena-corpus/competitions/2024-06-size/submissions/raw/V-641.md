# Vulnerability details

## Summary

The Size credit marketplace has a critical vulnerability in its multicall function implementation that allows for manipulation of the liquidation logic, basically leading to substantial financial losses. This vulnerability arises due to improper handling of post-condition checks within multicalls, enabling attackers to manipulate the protocol's state and exploit liquidations in a malicious manner.

## Vulnerability Detail

The vulnerability lies in the `multicall` function of the Size protocol, within the `Multicall` library.
The `multicall` function allows users to batch multiple operations into a single transaction, which is particularly useful for complex interactions such as liquidations. However, during the execution of multicalls, certain post-condition checks are waived, creating a window of opportunity for exploitation.

```solidity
function multicall(bytes[] calldata data) external payable override(IMulticall) whenNotPaused returns (bytes[] memory results) {
    state.data.isMulticall = true;

    uint256 borrowATokenSupplyBefore = state.data.borrowAToken.balanceOf(address(this));
    uint256 debtTokenSupplyBefore = state.data.debtToken.totalSupply();

    results = new bytes[](data.length);
    for (uint256 i = 0; i < data.length; i++) {
        results[i] = Address.functionDelegateCall(address(this), data[i]);
    }

    uint256 borrowATokenSupplyAfter = state.data.borrowAToken.balanceOf(address(this));
    uint256 debtTokenSupplyAfter = state.data.debtToken.totalSupply();

    state.validateBorrowATokenIncreaseLteDebtTokenDecrease(
        borrowATokenSupplyBefore, debtTokenSupplyBefore, borrowATokenSupplyAfter, debtTokenSupplyAfter
    );

    state.data.isMulticall = false;
}
```

Specifically, the issue occurs because the function does not adequately validate the cumulative effects of the batched operations, especially concerning the health and collateralization of positions involved in liquidations. This can be exploited as follows:

1. **Initial state manipulation**: An attacker with a position close to the liquidation threshold can start by manipulating the protocol state through a series of operations in a multicall. For instance, they might deposit collateral, initiate a borrow, and then withdraw the collateral in a carefully crafted sequence.

2. **Bypassing liquidation checks**: During the multicall, the protocol's checks on collateral ratios and health of positions can be bypassed. This allows the attacker to create a scenario where their position appears healthy throughout the individual operations but ends up in an undercollateralized state by the end of the multicall.

3. **Exploit liquidation**: Once the multicall completes, the protocol does not correctly validate the overall state, enabling the attacker to liquidate their own position or others in an unfairly advantageous manner. This can result in either avoiding liquidation penalties or profiting from liquidations that should not have been allowed.

## Impact

The impact of this vulnerability is significant, as it can lead to:

- **Unfair liquidation avoidance**: Attackers can avoid liquidation penalties by manipulating their position's state during multicalls.
- **Profit from invalid liquidations**: Malicious actors can exploit the system to trigger liquidations that should not occur, profiting at the expense of other users and the protocol.
- **Financial losses**: The protocol and its users may suffer substantial financial losses due to these exploitative actions.

## Proof of Concept

To reproduce the vulnerability, follow these steps:

1. Create a position with collateral and borrow tokens that are close to the liquidation threshold.
2. Construct a multicall transaction that manipulates the state, such as depositing and withdrawing collateral in a sequence that bypasses intermediate checks.
3. Execute the multicall and observe the resulting state, noting any discrepancies in collateral ratios and liquidation eligibility.
4. Trigger a liquidation and analyze the financial outcome, demonstrating the ability to manipulate the protocol state to achieve unfair advantages.

        uint256 afterLiquidatorWETH = weth.balanceOf(liquidator);

        // Assertions

        assertEq(_after.liquidator.borrowATokenBalance, _before.liquidator.borrowATokenBalance, 0);
        assertEq(_after.liquidator.collateralTokenBalance, _before.liquidator.collateralTokenBalance, 0);
        assertGt(_after.feeRecipient.collateralTokenBalance, _before.feeRecipient.collateralTokenBalance, "feeRecipient has liquidation split");
        assertEq(beforeLiquidatorWETH, 0);
        assertGt(afterLiquidatorWETH, beforeLiquidatorWETH);
        assertEq(beforeLiquidatorUSDC, futureValue);
        assertEq(afterLiquidatorUSDC, 0);
    }
}
