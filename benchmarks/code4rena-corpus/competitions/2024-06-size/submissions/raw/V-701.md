# Vulnerability details

## impact

The current validation logic in the **`validateBorrowATokenIncreaseLteDebtTokenDecrease`** function allows **`borrowATokenSupply`** to exceed the configured cap if the increase in **`borrowATokenSupply`** is offset by a greater or equal decrease in **`debtTokenSupply`**. This allow a  malicious user can manipulate the token supplies to bypass the cap, this will  **break the system rules** and increasing risk exposure.


## Proof of Concept

The `Multicall` library allows batching multiple functions. The library checks the token balances before and after the multicall to ensure all operations in the batch are done correctly.
```js

 function multicall(State storage state, bytes[] calldata data) internal returns (bytes[] memory results) {
        state.data.isMulticall = true;

        uint256 borrowATokenSupplyBefore = state.data.borrowAToken.balanceOf(address(this));
        uint256 debtTokenSupplyBefore = state.data.debtToken.totalSupply();

        results = new bytes[](data.length);
        for (uint256 i = 0; i < data.length; i++) {
            results[i] = Address.functionDelegateCall(address(this), data[i]);
        }

        uint256 borrowATokenSupplyAfter = state.data.borrowAToken.balanceOf(address(this));
        uint256 debtTokenSupplyAfter = state.data.debtToken.totalSupply();

        state.validateBorrowATokenIncreaseLteDebtTokenDecrease(
            borrowATokenSupplyBefore, debtTokenSupplyBefore, borrowATokenSupplyAfter, debtTokenSupplyAfter
        );

        state.data.isMulticall = false;
    }

```
Using `validateBorrowATokenIncreaseLteDebtTokenDecrease` to ensure that in case the cap is exceeded, the increase in borrow token supply is less than or equal to the decrease in debt token supply, means the tokens deposited are used to repay or liquidate a debt position, and not a regular deposit.
```js
function validateBorrowATokenIncreaseLteDebtTokenDecrease(
        State storage state,
        uint256 borrowATokenSupplyBefore,
        uint256 debtTokenSupplyBefore,
        uint256 borrowATokenSupplyAfter,
        uint256 debtTokenSupplyAfter
    ) external view {
        // If the supply is above the cap
        if (borrowATokenSupplyAfter > state.riskConfig.borrowATokenCap) {
            uint256 borrowATokenSupplyIncrease = borrowATokenSupplyAfter > borrowATokenSupplyBefore
                ? borrowATokenSupplyAfter - borrowATokenSupplyBefore
                : 0;
            uint256 debtATokenSupplyDecrease =
                debtTokenSupplyBefore > debtTokenSupplyAfter ? debtTokenSupplyBefore - debtTokenSupplyAfter : 0;

            // and the supply increase is greater than the debt reduction
            if (borrowATokenSupplyIncrease > debtATokenSupplyDecrease) {
                // revert
                revert Errors.BORROW_ATOKEN_INCREASE_EXCEEDS_DEBT_TOKEN_DECREASE(
                    borrowATokenSupplyIncrease, debtATokenSupplyDecrease
                );
            }
            // otherwise, it means the debt reduction was greater than the inflow of cash: do not revert
        }
    }
 
```
The function does not revert as long as the increase in **`borrowATokenSupply`** is less than or equal to the decrease in **`debtTokenSupply`**, even if the **`borrowATokenSupply`** exceeds the cap. This allows a user to manipulate the system to exceed the cap limit by performing a series of operations.

### Scenario

**Initial State:**

- **Cap**: 1,000,000
- **borrowATokenSupplyBefore**: 900,000
- **debtTokenSupplyBefore**: 200,000

A user wants to deposit 200k but cannot do so through a normal deposit because this will exceed the cap. So the user will do the following:

1. **Action**: User deposits 100,000 **borrowAToken**.
   - **Result**: 
     - **borrowATokenSupply** increases by 100,000 (900,000 + 100,000 = 1,000,000, cap reached).
     - **debtTokenSupply** remains 200,000.

2. **Action**: User buys a credit from themselves with 100,000, so they get a debt position and credit position, and their balance of borrowAToken remains the same (assume no fees for easy calculation and they set APR to 0).
   - **Result**: 
     - **debtTokenSupply** increases by 100,000 (200,000 + 100,000 = 300,000).

3. **Action**: User calls multicall to do the following actions:
   - Deposit 100,000 borrow tokens and repay their debt of 100,000.
   - **Result**: 
     - **debtTokenSupply** decreases by 100,000 (300,000 - 100,000 = 200,000).
     - **borrowATokenSupply** increases by 100,000 (1,000,000 + 100,000 = 1,100,000, exceeding the cap by 100,000).

In this case, multicall does not revert even though **`borrowATokenSupply`** exceeds the cap because the increase in **`borrowATokenSupply`** (100,000) is equal to the decrease in **`debtTokenSupply`** (100,000). This way, a user can manipulate the system to exceed the cap limit without triggering a revert, effectively bypassing the intended cap enforcement. The user can deposit any amount above the cap by repeatedly creating debt positions and credit positions, repaying the credit, and using the decreased amount to deposit more.

> Notice: This issue is different from the issue of using `balanceOf(address(this))` instead of `totalSupply` to check the cap. This one assumes correct validation of the total supply of `borrowAToken`.
