# Vulnerability details

## Description:
The contract initialization process implemented in the `executeInitializeData` function of the Initialize library is vulnerable to blockchain reorganization events. This vulnerability could lead to inconsistent contract states, potentially compromising the entire protocol's functionality and security.


## Code:

https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/Initialize.sol#L230

The vulnerability is present in the `executeInitializeData` function:

```solidity
   function executeInitializeData(State storage state, InitializeDataParams memory d) internal {
       // ... other initializations ...

       state.data.collateralToken = new NonTransferrableToken(
           address(this),
           string.concat("Size ", IERC20Metadata(state.data.underlyingCollateralToken).name()),
           string.concat("sz", IERC20Metadata(state.data.underlyingCollateralToken).symbol()),
           IERC20Metadata(state.data.underlyingCollateralToken).decimals()
       );
       state.data.borrowAToken = new NonTransferrableScaledToken(
           state.data.variablePool,
           state.data.underlyingBorrowToken,
           address(this),
           string.concat("Size Scaled ", IERC20Metadata(state.data.underlyingBorrowToken).name()),
           string.concat("sza", IERC20Metadata(state.data.underlyingBorrowToken).symbol()),
           IERC20Metadata(state.data.underlyingBorrowToken).decimals()
       );
       state.data.debtToken = new NonTransferrableToken(
           address(this),
           string.concat("Size Debt ", IERC20Metadata(state.data.underlyingBorrowToken).name()),
           string.concat("szDebt", IERC20Metadata(state.data.underlyingBorrowToken).symbol()),
           IERC20Metadata(state.data.underlyingBorrowToken).decimals()
       );
   }
```

## Vulnerability Details:
- The function uses the CREATE opcode (via Solidity's `new` keyword) to deploy three new contracts.
- The addresses of these contracts are determined by the deployer's address and nonce at the time of deployment.
- In a blockchain reorg, if this transaction is re-executed in a different block or order, it may result in different contract addresses.

## Impact
- Inconsistent State: The protocol's state may contain incorrect addresses for critical contract components.
- Broken Functionality: Other parts of the system relying on these addresses may interact with non-existent or incorrect contracts.
- Asset Vulnerability: User funds managed through these contracts could potentially become inaccessible or vulnerable.
- Protocol Instability: The overall stability and reliability of the protocol could be severely compromised.

## Affected Components:
- collateralToken (NonTransferrableToken)
- borrowAToken (NonTransferrableScaledToken)
- debtToken (NonTransferrableToken)

## Potential Exploits:
- An attacker could potentially exploit this vulnerability by manipulating the network to force reorgs during critical initialization periods.
- In a worst-case scenario, an attacker might be able to front-run the initialization with their own contracts at the expected addresses.

## Mitigation:

1. Use CREATE2 for Deterministic Addressing:
Implement the CREATE2 opcode to ensure consistent contract addresses regardless of deployment order or timing:

```solidity
   bytes32 salt = keccak256(abi.encodePacked("collateralToken"));
   address collateralTokenAddress = Create2.deploy(0, salt, type(NonTransferrableToken).creationCode);
   state.data.collateralToken = NonTransferrableToken(collateralTokenAddress);
```

2. Implement Single-Use Initialization:
Add a mechanism to prevent multiple executions of the initialization function:

```solidity
   bool private initialized;
   
   modifier initializer() {
       require(!initialized, "Already initialized");
       initialized = true;
       _;
   }
   
   function executeInitializeData(...) internal initializer {
       // Existing implementation
   }
```

3. Develop a Recovery Mechanism:
Implement a function to verify and potentially update contract addresses in case of a detected discrepancy:

```solidity
   function verifyContractAddresses() external {
       address expectedCollateralToken = computeCreate2Address(COLLATERAL_SALT);
       require(address(state.data.collateralToken) == expectedCollateralToken, "Collateral token address mismatch");
       // Similar checks for borrowAToken and debtToken
   }
```

4. Use a Factory Pattern:
Consider implementing a factory contract for deploying these tokens, which can provide an additional layer of address management and verification.
