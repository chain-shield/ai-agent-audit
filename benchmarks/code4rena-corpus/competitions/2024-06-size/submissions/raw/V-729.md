# Vulnerability details

## Impact
Users can be liquidated by force.

## Proof of Concept
A malicious actor can put a used underwater and put them in a liquidation state,
let's check [isDebtPositionLiquidatable](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/RiskLibrary.sol#L105) method:
```Solidity
return state.isDebtPositionId(debtPositionId)
        // case 1: if the user is underwater, only ACTIVE/OVERDUE DebtPositions can be liquidated
        && (
            (isUserUnderwater(state, debtPosition.borrower) && status != LoanStatus.REPAID)
            // case 2: overdue loans can always be liquidated regardless of the user's CR
            || status == LoanStatus.OVERDUE
        );
```
if `isUserUnderwater(state, debtPosition.borrower)` returns true, then the user will be able to be liquated, there is a way actully to make this happen.

isUserUnderwater method is checking if `collateralRatio(state, account) < state.riskConfig.crLiquidation`, assuming the user collateralRatio is greater than `crLiquidation`, then the user is protected. but unfortunately this condition can be manipulated.

A malicious actor can send `debtToken` to `debtPosition.borrower` address to cause the `collateralRatio` of the borrower's account balance to be less than `state.riskConfig.crLiquidation`, causing the user to be underwater, as a result the user is enforced to be liquidated.


## Tools Used
Manual review

## Recommended Mitigation Steps
Try to find a solution to store borrow balance some where in the protocol instead of relying on his address balance.





## Assessed type

DoS
