# Vulnerability details

## Impact

In the `AccountingLibrary::debtTokenAmountToCollateralTokenAmount` function, there was an accidental input of `state.data.underlyingBorrowToken.decimals()` instead of `state.data.underlyingCollateralToken.decimals()`. This mistake results in the returned value from `debtTokenAmountToCollateralTokenAmount` being in 6 decimals instead of 18 decimals. The `debtTokenAmountToCollateralTokenAmount` function is used in the Liquidate library within `Liquidate.sol` to calculate the debt token amount in terms of the collateral token amount.

This is a critical mistake because it will indicate unprofitable liquidation as a profitable liquidation since `(x - 1)e18` is always greater than `xe6`. This could result in the protocol charging a fee even when the liquidation is not actually profitable. Such an error disrupts the protocol's mechanism and the liquidation process. Consequently, lenders may end up paying some of their tokens to the protocol as a fee in situations where the liquidation is unprofitable.

## Proof of Concept

```javascript
    function debtTokenAmountToCollateralTokenAmount(State storage state, uint256 debtTokenAmount) internal view returns (uint256 collateralTokenAmount) {
        uint256 debtTokenAmountWad = Math.amountToWad(debtTokenAmount, state.data.underlyingBorrowToken.decimals());
        collateralTokenAmount = Math.mulDivUp(debtTokenAmountWad, 10 ** state.oracle.priceFeed.decimals(), state.oracle.priceFeed.getPrice());
    }
```

`AccountingLibrary::debtTokenAmountToCollateralTokenAmount` is a function designed to convert a debt token amount to a collateral token amount. Given this, the `collateralTokenAmount` must be represented with 18 decimals (the decimals of the collateral token) and not 6 decimals (the decimals of the borrow token). This distinction is crucial in the DeFi ecosystem because many tokens have various decimals.


`(x - 1)e18` is always greater than `xe6`. For example, 19e18 will always be greater than 20e6. This mistake will incorrectly indicate an unprofitable liquidation as a profitable one. As shown in the code, if the liquidation is profitable, `protocolProfitCollateralToken` will not be zero. However, in an unprofitable liquidation, `protocolProfitCollateralToken` should be zero.

Due to this mistake, unprofitable liquidations will be counted as profitable. Consequently, `protocolProfitCollateralToken` will not be zero, because `collateralRemainder` is calculated as `assignedCollateral` (18 decimals) minus `liquidatorProfitCollateralToken` (6 decimals), which will always result in a non-zero value.

Let's take a look at following scenario:

1. assignedCollateral = 18e18, debtInCollateralToken = 20e6. This situation will be mistakenly counted as a profitable liquidation because 18e18 is greater than 20e6.
2. ETH Price: $2000
3. `liquidatorReward` is 40000e6 * 5% = `2000e6` because assignedCollateral - debtInCollateralToken has bigger amount.
4. `liquidatorProfitCollateralToken` is 20e6 + 2000e6 = `64000000000064000000`.
5. `collateralRemainder` is 18e18 - `64000000000064000000` = `39282408075296473575424`.
6. `collateralRemainderCap` is 20e6 * 130% = 26e6
7. `protocolProfitCollateralToken` is 26e6 * 10% = 26e5
8. The lender will loss `26e5` amount of collateral token to the protocol treasury as protocol profit even though it supposed to be zero because of unprofitable liquidation.
