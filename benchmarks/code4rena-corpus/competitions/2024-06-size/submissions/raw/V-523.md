# Vulnerability details

## Impact
The `borrowATokenCap` will be reached earlier than expected

## Proof of Concept
Whenever users try to deposit, they will not be able to in certain cases because of this check:
```solidity
    function validateBorrowATokenCap(State storage state) external view {
        if (state.data.borrowAToken.totalSupply() > state.riskConfig.borrowATokenCap) {
            revert Errors.BORROW_ATOKEN_CAP_EXCEEDED(state.riskConfig.borrowATokenCap, state.data.borrowAToken.totalSupply());
        }
    }
```
The goal here is to not allow users to deposit when the specified cap has been reached. Whenever a user deposits, tokens are minted like this (showing just parts of the code there):
```solidity
uint256 scaledBalanceBefore = aToken.scaledBalanceOf(address(this));
uint256 scaledAmount = aToken.scaledBalanceOf(address(this)) - scaledBalanceBefore;
state.data.borrowAToken.mintScaled(to, scaledAmount);
```
It caches the scaled balance before and mints the difference afterwards. The scaled tokens are the amount of tokens the user deposits ignoring the liquidity index. For example, if a user deposits 1000 tokens, he will get minted 1000 tokens. The issue is how the total supply is being checked against the cap:
```solidity
if (state.data.borrowAToken.totalSupply() > state.riskConfig.borrowATokenCap)
```
```
function totalSupply() public view override returns (uint256) {
        return _unscale(scaledTotalSupply());
    }
```
`totalSupply()` is called on the tokens which unscales the scaled supply. Essentially, that means that the liquidity index is taken into consideration. Let's imagine a scenario with very simple values to see how that could be an issue:
1. The cap is 1000 tokens and the liquidity index is 1
2. User deposits 500 tokens
3. Liquidity index changes to 1.01
4. Another user tries to deposit 500 tokens which he should be able to as there are 500 tokens left until the cap is reached
5. The cap is checked against the unscaled total supply which is 1010 due to the liquidity index growth and the user will not be able to do so

This is a very simplified example, in reality the liquidity index is a value with a lot more decimals and there is also `RAY` (1e27) in the calculations for unscaling but the point is clear, the liquidity index will grow and the check against the cap would revert in some cases it shouldn't.
