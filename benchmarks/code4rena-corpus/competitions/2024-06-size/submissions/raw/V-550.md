# Vulnerability details

## Impact
The borrower(caller) will always end up paying more for fragmentation

## Proof of Concept
when AccountingLibrary::getCreditAmountIn is called, it is meant to calculate the amount of credit a lender is meant to receive for supply a certain amount of cash, also because in this flow, the lender is the paying for both swap and fragmentation fee in cash
```
 (https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/SellCreditMarket.sol#L201-L202)
```
, the credit received is meant to increase to cover this loss ie 
total credit = (normal credit value of position) + swap fees + frag fees 

this credit is calculated using the formaula 
```
  creditAmountIn = Math.mulDivUp(
                cashAmountOut + state.feeConfig.fragmentationFee, PERCENT + ratePerTenor, PERCENT - swapFeePercent
            );
```
the idea itself if correct for calculationg the credit that the lender should receive accounting for swap fees, but the issue lies with the fragmentation fee 

the above formula is equivalent to 

```

              cashAmountOut * PERCENT + ratePerTenor / PERCENT - swapFeePercent + 
            
               state.feeConfig.fragmentationFee * PERCENT + ratePerTenor/ PERCENT - swapFeePercent
            
```
PERCENT + ratePerTenor/ PERCENT - swapFeePercent will always be a value greater than one meaning the actual amount added for fragmentation is 
```
fragmentation fee * 1.x(where x is arbitrary)
```
while the lender only pays for 1.0 * fragmentation fee 

As a result the lender is minted more credit than should and the borrower has to pay for this extra when repaying 
## Tools Used
manual analysis 

## Recommended Mitigation Steps

The credit amount in should be calculated as 

  creditAmountIn = Math.mulDivUp(
                cashAmountOut , PERCENT + ratePerTenor, PERCENT - swapFeePercent
            ) + state.feeConfig.fragmentationFee;

this would ensure the lender is minted as much extra credit as the fees they pay for
