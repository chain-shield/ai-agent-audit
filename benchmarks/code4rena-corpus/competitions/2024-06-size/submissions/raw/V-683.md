# Vulnerability details

## Issue

Lack of slippage control in some market operations could lead to unexpected results in volatile market conditions. The issue here is that while these functions do check for a minimum APR in `validateBuyCreditMarket` or maximum APR in `validateSellCreditMarket`, they don't include a mechanism for the user to specify a minimum amount out or maximum amount in. This lack of slippage control could lead to some problems.

The issue primarily affects the `BuyCreditMarket` and `SellCreditMarket` functions.

## Impact:

1. Front-running: In volatile market conditions, an attacker could front-run a transaction, causing the market rate to change unfavorably for the user before their transaction is processed.

2. Unexpected outputs: Users might receive significantly less credit or cash than they expected due to rapid market movements.

3. Sandwich attacks: An attacker could manipulate the market rate just before and after a user's transaction, profiting at the user's expense.


## Mitigation
To mitigate this issue, the contract should allow users to specify a minimum amount out (for buy operations) or maximum amount in (for sell operations). Here's an example of how this could be implemented:

For BuyCreditMarket:

```solidity
struct BuyCreditMarketParams {
    // ... (existing fields)
    uint256 minCreditAmountOut; // New field
}

function executeBuyCreditMarket(State storage state, BuyCreditMarketParams memory params)
    external
    returns (uint256 cashAmountIn)
{
    // ... (existing code)

    if (params.exactAmountIn) {
        // ... (existing code)
    } else {
        // ... (existing code)
    }

    // Add slippage check
    if (creditAmountOut < params.minCreditAmountOut) {
        revert Errors.SLIPPAGE_LIMIT_EXCEEDED(creditAmountOut, params.minCreditAmountOut);
    }

    // ... (execute the transaction)
}
```

Similar changes should be made to the SellCreditMarket function, adding a `maxCashAmountIn` parameter and corresponding check.
