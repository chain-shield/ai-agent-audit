# Vulnerability details

## Issue Description
The logic for calculating `maxCashAmountOut` when `exactAmountIn` is false (lines 171-173). The code ensures that the `cashAmountOut` doesn't exceed the maximum possible given the available credit and fees. The calculation needs to be fixed. [SellCreditMarket.sol#173-175](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/SellCreditMarket.sol#L173-L175)
```solidity
maxCashAmountOut: params.creditPositionId == RESERVED_ID
    ? cashAmountOut
    : Math.mulDivDown(creditPosition.credit, PERCENT - state.getSwapFeePercent(tenor), PERCENT + ratePerTenor),
```
   1. `creditPosition.credit` represents the total credit available in the specified credit position.
   2. `PERCENT - state.getSwapFeePercent(tenor)`: This calculates the percentage of credit remaining after deducting the swap fee.
   3. `PERCENT + ratePerTenor` represents the total percentage after factoring in the interest rate.

The issue is that dividing the credit amount (reduced by the swap fee) by the total percentage (including interest) doesn't yield the correct `maxCashAmountOut`. This calculation would underestimate the maximum cash obtainable.

## Impact
**Impact of the **`SellCreditMarket.sol` `maxCashAmountOut`** Calculation Error**

1. The flawed calculation of `maxCashAmountOut` results in a lower value than the user should receive. This happens because the code incorrectly factors the interest rate (`ratePerTenor`) when determining the maximum cash obtainable from the available credit.

2. Due to the underestimated `maxCashAmountOut`, users trying to sell existing credit positions will face artificial limitations. They will need access to the total cash equivalent of their credit, making it less attractive to trade existing positions. This ultimately reduces the liquidity of credit positions within the Size protocol.

3. While the code doesn't directly expose a vulnerability for attackers to steal funds, the miscalculation creates an economic inefficiency. Savvy users could exploit this by purchasing credit positions at a discount due to the artificially deflated `maxCashAmountOut` and potentially profiting by utilizing the credit themselves or finding buyers willing to pay closer to the actual value.

## Proof of Concept
Illustration of the issue with an example.
   * Assume creditPosition.credit = 1000, state.getSwapFeePercent(tenor) = 1%, and ratePerTenor = 5%.
   * The user wants to sell their entire credit position (cashAmountOut = ?).

**Flawed Calculation:**
```solidity
maxCashAmountOut = (1000 * (100 - 1) / (100 + 5)) = 947.61
```
This implies the user can receive a maximum of 947.61 in cash.

**Correct Calculation:**
```solidity
maxCashAmountOut = (1000 * (100 - 1) / 100) = 990
```
**Scenario:**
A user attempts to sell an existing credit position using the `executeSellCreditMarket` function with `exactAmountIn` set to false. This means they specify the desired `cashAmountOut`, and the contract calculates the corresponding `creditAmountIn`.

**Assumptions:**
   * `creditPosition.credit = 1000` (User's total credit in the position)
   * `state.getSwapFeePercent(tenor) = 1%` (Swap fee for the given tenor)
   * `ratePerTenor = 5%` (Interest rate per tenor)
   * `cashAmountOut = 990` (User's desired cash amount)

## Recommended Mitigation Steps
By removing `ratePerTenor` from the denominator, we correctly calculate the maximum cash amount obtainable based on the available credit and the swap fee. This ensures that the borrower receives the correct amount of cash while accounting for the fee.
The calculation should be adjusted
```solidity
maxCashAmountOut: params.creditPositionId == RESERVED_ID
    ? cashAmountOut
    : Math.mulDivDown(creditPosition.credit, PERCENT - state.getSwapFeePercent(tenor), PERCENT),
```
