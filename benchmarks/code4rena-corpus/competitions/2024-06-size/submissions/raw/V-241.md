# Vulnerability details


## Proof of Concept

Take a look at https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/oracle/PriceFeed.sol#L63-L82

```solidity
    function getPrice() external view returns (uint256) {
        if (address(sequencerUptimeFeed) != address(0)) {
            // slither-disable-next-line unused-return
            (, int256 answer, uint256 startedAt,,) = sequencerUptimeFeed.latestRoundData();

            if (answer == 1) {
                // sequencer is down
                revert Errors.SEQUENCER_DOWN();
            }

            if (block.timestamp - startedAt <= GRACE_PERIOD_TIME) {
                // time since up
                revert Errors.GRACE_PERIOD_NOT_OVER();
            }
        }

        return Math.mulDivDown(
            _getPrice(base, baseStalePriceInterval), 10 ** decimals, _getPrice(quote, quoteStalePriceInterval)
        );
    }
```

Evidently protocol integrates a grace period checker in the case where the sequencer is back up, issue however is that this duration is too much.

See https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/oracle/PriceFeed.sol#L25

```solidity
    uint256 private constant GRACE_PERIOD_TIME = 3600;
```

Having it in mind that the `getPrice` ends up being queried for liquidations and other core functionalities having this being blocked for one hour easily means that accumulation of bad debts could occur, or even other core functionalities of protocol would be DOS'd which could put protocol in an unwanted state.

## Impact

Protocol would be easily put in an unwanted state since it allows for bad debt positions to be accumulating for a long duration even after the sequencer comes up (and these positions could be more than one in this case, exarcebating the issue).

> NB: Even if transactions are passed via the delayed inbox, the sequencer only includes the message from the inbox after a delay of ~ 10 minutes when it comes back up which is so as to ensure that the transaction/message’s arrival will not be affected by a reorganisation of the base layer chain... which would mean that the current implementation of 1 hour just puts protocol in a position of heavy risk, where 10/15 minutes would suffice.

## Recommended Mitigation Steps

Consider shortening the duration to like 10/15 minutes, cause within this time all re-orgs and what not would have been sorted out.
