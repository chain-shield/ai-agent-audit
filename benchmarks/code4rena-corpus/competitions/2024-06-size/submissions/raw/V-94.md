# Vulnerability details

## Impact
Numerous different ways for users to create offers that are impossible to take. This creates issues such as legitimate users trying to accept these offers and reverting over and over again while having to pay gas for the transactions.

## Proof of Concept
The first way to do that is simply creating an offer without having any tokens. That is possible as there is no check in regards to that and tokens are not transferred in upon offer creation.

Another way to do that is here:
```solidity
   if (params.maxDueDate < block.timestamp + state.riskConfig.minTenor) {
        revert Errors.PAST_MAX_DUE_DATE(params.maxDueDate);
   }
```
The user can specify the `maxDueDate` such that if, for example, `block.timestamp` is 150 and `minTenor` is 50, `maxDueDate` can be 200. This means that whenever `block.timestamp` is just 1 second later so 151, the offer will not be acceptable as the difference between `block.timestamp` and `maxDueDate` will never be more than `minTenor` anymore and will always cause reverts upon someone trying to accept the offer.

Another option is for a user to change his `openingLimitBorrowCR` to an extremely high value and it would always revert here:
```solidity
state.validateUserIsNotBelowOpeningLimitBorrowCR(params.borrower);
```

All of these options allow for offers that can never be accepted. If they have good terms, then users will be interested to accept that offer and will keep having to pay gas fees. There is also no way for anyone besides the offer creator to actually remove these offers, they will be there for an eternity unless the creator doesn't remove them.
## Tools Used
Manual Review
## Recommended Mitigation Steps
The best way to fix the issue without having to significantly change the code is to just allow owners to remove offers. That way, at least, the offers will not stay there forever.
