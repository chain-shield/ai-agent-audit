# Vulnerability details


## Impact
msg.sender/attacker can fill all the debtPosition and creditPosition slots available with the same data without facing any loss, using Compensate.

## Proof of Concept

When `CompensateParams.creditPositionToCompensateId == RESERVE_ID` , the sender/borrower can execute `executeCompensate` with `CompensateParams.amount == creditPositionToRepay.credit`.

In this case a new creditPosition and debtPosition is created with `futureValue = amountToCompensate = creditPositionToRepay.credit`.

https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/Compensate.sol#L106-L156

```solidity
if (params.creditPositionToCompensateId == RESERVED_ID) {
            creditPositionToCompensate = state.createDebtAndCreditPositions({
                lender: msg.sender,
                borrower: msg.sender,
                futureValue: amountToCompensate,
                dueDate: debtPositionToRepay.dueDate
            }); 
}
```

> That means the sender can create `new exact copies `of the already existing `creditPositionToRepay` and `debtPositionToRepay` , before reducing their futureValue and credit respectively to `0`  using `reduceDebtAndCredit`.
https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/AccountingLibrary.sol#L153-L158

Also , there are no changes in the state of any users or positions except the protocols storage is getting utilised inefficiantly.

Sender/attacker can go on and execute multiple similar transactions (type(uint256).max / 2)  and grief the protocol.


## Tools Used
Manual review
## Recommended Mitigation Steps

In case of `CompensateParams.creditPositionToCompensateId == RESERVE_ID` protocol shouldnt allow compensate if `CompensateParams.amount == creditPositionToRepay.credit` by adding this validation in `validateCompensate()` .
