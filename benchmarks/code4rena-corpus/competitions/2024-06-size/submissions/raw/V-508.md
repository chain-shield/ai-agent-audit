# Vulnerability details

## Impact
`isMultiCall` boolean value can be easily manipulated.

By encoding a `multicall` function inside the function data of the original `multicall` function, the boolean variable `isMulticall` will be set to `false` at the end of the nested `multicall` even before the original `multicall` function ends. 

This poses a risk if the developers decide to implement functions in _future developments_ that restricts access when `multicall` is ongoing, since the variable `isMulticall` can be easily manipulated.

Another implication is that user's deposit may revert wrongly if they nest `multicall` due to this part in the deposit function, which will cause `state.validateBorrowATokenCap()` to run when it is **not supposed** to.

```solidity
function executeDeposit(State storage state, DepositParams calldata params) public {
    ....
    if (params.token == address(state.data.underlyingBorrowToken)) {
        ....
        if (!state.data.isMulticall) { //@audit isMulticall may be wrongly set to false
            state.validateBorrowATokenCap();
        }
    } else {
        ....
    }
    ....
}
```
 

## Proof of Concept

```solidity
function test_my_nested_multicall () public {
```

## Recommended Mitigation Steps

To fix the issue change `isMulticall` to an `uint` and use it like a counter instead; to protect against nested call manipulations.

For example:

~~`state.data.isMulticall = true;`~~
**should be changed to**
`state.data.isMulticall += 1;`

and

~~`state.data.isMulticall = false;`~~
**__should be changed to__**
`state.data.isMulticall -= 1;`


Then change all checks to `if(state.data.isMulticall > 0)` to find out if a `multicall` is ongoing.
