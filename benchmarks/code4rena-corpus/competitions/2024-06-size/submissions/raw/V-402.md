# Vulnerability details

The [getCreditAmountOut()](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/AccountingLibrary.sol#L274-L301) function in the `AccountingLibrary.sol` contract may inconsistently apply the fragmentation fee, potentially violating the `FEES_01` invariant and causing a denial of service in certain scenarios.

## Impact
The current implementation applies the fragmentation fee only when `cashAmountIn < maxCashAmountIn`. However, this condition doesn't accurately capture all scenarios where credit fractionalization occurs. This can lead to:

1. Violation of `FEES_01`: Fragmentation fees are not applied in all cases of credit fractionalization.
2. The function may revert due to insufficient cash when it should have applied the fragmentation fee.
3. Users may be charged differently for similar operations.

## Proof of Concept
Consider the following scenario:

1. `maxCashAmountIn` is 1000 tokens
2. `maxCredit` is 1100 tokens
3. `cashAmountIn` is 1000 tokens
4. The swap fee is 10 tokens
5. The fragmentation fee is 5 tokens

In this case:

- The function enters the first branch (`cashAmountIn == maxCashAmountIn`)
- It sets `creditAmountOut = maxCredit` (1100 tokens)
- It calculates `fees = getSwapFee(state, cashAmountIn, tenor)` (10 tokens)

However, this results in credit fractionalization (1000 tokens in, 1100 tokens out) without applying the fragmentation fee. Moreover, if the swap fee (10 tokens) is greater than the cash amount in (1000 tokens), the function will revert due to insufficient cash, even though applying the fragmentation fee might have prevented this.

## Recommended Mitigation Steps
To ensure compliance with the `FEES_01` invariant while preventing potential DOS, consider modifying the `getCreditAmountOut()` function as follows:
```solidity
function getCreditAmountOut(
    State storage state,
    uint256 cashAmountIn,
    uint256 maxCashAmountIn,
    uint256 maxCredit,
    uint256 ratePerTenor,
    uint256 tenor
) internal view returns (uint256 creditAmountOut, uint256 fees) {
    uint256 swapFee = getSwapFee(state, cashAmountIn, tenor);
    uint256 potentialCreditOut = Math.mulDivDown(cashAmountIn - swapFee, PERCENT + ratePerTenor, PERCENT);

    if (potentialCreditOut < maxCredit) {
        // Credit fractionalization occurs
        if (cashAmountIn <= state.feeConfig.fragmentationFee + swapFee) {
            revert Errors.NOT_ENOUGH_CASH(state.feeConfig.fragmentationFee + swapFee, cashAmountIn);
        }

        fees = swapFee + state.feeConfig.fragmentationFee;
        uint256 netCashAmountIn = cashAmountIn - fees;
        creditAmountOut = Math.mulDivDown(netCashAmountIn, PERCENT + ratePerTenor, PERCENT);
    } else {
        // No credit fractionalization
        fees = swapFee;
        creditAmountOut = maxCredit;
    }

    if (creditAmountOut > maxCredit || cashAmountIn > maxCashAmountIn) {
        revert Errors.NOT_ENOUGH_CREDIT(maxCashAmountIn, cashAmountIn);
    }
}
```
1. The fragmentation fee is applied whenever credit fractionalization occurs, regardless of the relationship between `cashAmountIn` and `maxCashAmountIn`.
2. The function reverts with a clear error message if there's not enough cash to cover both the swap fee and the fragmentation fee when needed.
3. The `FEES_01` invariant is consistently upheld.
4. The potential for DOS due to unexpected fee application is mitigated.
