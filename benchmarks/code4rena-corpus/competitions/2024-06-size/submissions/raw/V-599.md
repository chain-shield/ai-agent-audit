# Vulnerability details

## Description
When a user wants to buy or sell credit, he have to call either ```buyCreditMarket()``` or ```sellCreditMarket()``` and pass the amount of credit or the amount of cash, passing accordingly ```amount``` and ```exactAmountIn``` parameters. Also, protocol has an invariant LOAN_01 that no credit position should be exist with less than ```minimumCreditBorrowAToken``` value. This invariant is holding due to this [check](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/RiskLibrary.sol#L31) which is in both ```createCreditPosition()``` and ```createDebtAndCreditPositions()```. However, there is one more check on ```validateBuyCreditMarket()``` and ```validateSellCreditMarket()``` which prevents users who will actually open positions with credit more than ```minimumCreditBorrowAToken``` to do it. In both validation functions there is this check : 

```solidity
    function validateBuyCreditMarket(State storage state, BuyCreditMarketParams calldata params) external view {
        // ...

        // validate amount
        if (params.amount < state.riskConfig.minimumCreditBorrowAToken) {
            revert Errors.CREDIT_LOWER_THAN_MINIMUM_CREDIT(params.amount, state.riskConfig.minimumCreditBorrowAToken);
        }

        // ...
    }
```
```solidity
    function validateSellCreditMarket(State storage state, SellCreditMarketParams calldata params) external view {
        // ...

        // validate amount
        if (params.amount < state.riskConfig.minimumCreditBorrowAToken) {
            revert Errors.CREDIT_LOWER_THAN_MINIMUM_CREDIT(params.amount, state.riskConfig.minimumCreditBorrowAToken);
        }

        // ...
    }
```

These checks forget that ```params.amount``` can actually be specified as cash and not as credit accordingly with ```params.exactAmountIn```. The credit, in these cases, will be later calculated using the ```apr``` and can be more than ```minimumCreditBorrowAToken``` which will also be checked in the creation of the positions. However, the transaction will have already reverted since the ```cash``` was , wrongly, compared to the ```minimumCreditBorrowAToken``` and was less than it.

## Impact
Users will not be able to buy or sell credit with amounts that they actually were supposed to be able to. This results either for loss of funds for the protocol (no fees/profit/tvl) because user will not open positions, or the user will have to use more funds than what he actually wants and is within limits of the protocol but incorrectly implemented.

## Proof of Concept
To understand this vulnerability better, consider this scenario :
1. Alice has 45 szaUSDC and wants to ```buyCreditMarket()``` with 20% apr.
2. She calls ```buyCreditMarket()``` with ```amount``` = 45 and ```exactAmountIn``` = true.
3. The transaction will revert, even though it shouldn't since the credit will be calculated as 45 * 1.2 = 54 which is more than ```minimumCreditBorrowAToken``` = 50.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Consider checking the ```params.exactAmountIn``` and if it is about cash, do not compare it with ```minimumCreditBorrowAToken```. Also, consider removing totally the check in ```validate``` function since a proper check will happen when the positions will open.
