# Vulnerability details

##  Issue:
The current implementation of the Deposit library, when used in conjunction with the Multicall library, allows for a scenario where multiple deposit operations within a single multicall transaction can access the same ETH balance. This can lead to unintended behavior where the total amount deposited exceeds the actual ETH sent with the transaction.

## Affected Components:
1. Deposit library
2. Multicall library

## Description:
The issue arises from the way the Deposit library handles ETH deposits in combination with how the Multicall library executes multiple calls. When a deposit operation involving ETH is executed, the Deposit library uses `address(this).balance` to determine the amount to deposit. However, in a multicall scenario, this balance remains unchanged across multiple deposit operations within the same transaction.

Consider the following sequence of events:
1. A user initiates a multicall transaction with 5 ETH and includes multiple deposit operations.
2. The first deposit operation correctly identifies the balance as 5 ETH and processes the deposit.
3. Subsequent deposit operations in the same multicall will also see a balance of 5 ETH, despite the fact that this ETH has already been used in the first deposit.

This can lead to a situation where the contract attempts to deposit more ETH than was actually sent with the transaction, potentially resulting in failed operations or, worse, unintended token minting if the checks are not properly implemented.

## Proof of Concept:
```solidity
function exploitMulticallDeposit(State storage state) external payable {
    require(msg.value == 5 ether, "Send exactly 5 ETH");

    bytes[] memory calls = new bytes[](3);

    // Create three deposit calls, each attempting to deposit 5 ETH
    for (uint256 i = 0; i < 3; i++) {
        calls[i] = abi.encodeWithSelector(
            Deposit.executeDeposit.selector,
            DepositParams({
                token: address(state.data.weth),
                amount: 5 ether,
                to: msg.sender
            })
        );
    }

    // Execute the multicall
    Multicall.multicall(state, calls);
}
```

In this exploit, the user sends 5 ETH but attempts to deposit 15 ETH (5 ETH in each of the three calls). Due to the current implementation, this could potentially succeed, leading to an inconsistency between the actual ETH deposited and the tokens minted or recorded in the contract state.

## Impact:
1. Potential over-minting of tokens representing deposited ETH.
2. Inconsistency between the contract's recorded deposits and actual ETH balance.
3. Possible exploitation to gain more tokens or benefits than entitled based on the actual ETH sent.

## Recommended Mitigation:
1. Implement a running total of ETH used within a multicall transaction:
   - At the start of the multicall, store the initial ETH balance.
   - For each deposit operation, subtract the deposited amount from this running total.
   - Ensure that subsequent deposits can only use the remaining ETH balance.

2. Consider using a more explicit method for ETH deposits, such as requiring users to specify the exact ETH amount for each deposit operation and validating it against the remaining balance.

3. Implement additional checks in the Deposit library to ensure that the total ETH deposited across all operations in a multicall does not exceed the initial ETH balance of the transaction.
