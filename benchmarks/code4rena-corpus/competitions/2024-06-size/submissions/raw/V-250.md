# Vulnerability details

## Impact
- The user will be able to bypass the check in the `validateMinimumCredit` function in the `RiskLibrary.sol` contract, this way the user will be able to claim everything and the credit left in the protocol for him will be less than the `minimumCreditBorrowAToken` which is not supposed to happen as it is said in the natspec in this function.
- The natspec:
```solidity
    /// @notice Validate the credit amount during an exit
->  /// @dev Reverts if the remaining credit is lower than the minimum credit
    /// @param state The state
    /// @param credit The remaining credit
```


## Proof of Concept
- The user calls the `claim` function in `Size.sol`. Here the `claim` function first calls the `validateClaim` and than the `executeClaim` function. 
- We assume that everything went well and the checks in `validateClaim` passed, now we get to the `executeClaim` function which is represented in the next way:
```solidity
function executeClaim(State storage state, ClaimParams calldata params) external {
        CreditPosition storage creditPosition = state.getCreditPosition(params.creditPositionId);
        DebtPosition storage debtPosition = state.getDebtPositionByCreditPositionId(params.creditPositionId);

        uint256 claimAmount = Math.mulDivDown(
            creditPosition.credit, state.data.borrowAToken.liquidityIndex(), debtPosition.liquidityIndexAtRepayment
        );
        state.reduceCredit(params.creditPositionId, creditPosition.credit);
        state.data.borrowAToken.transferFrom(address(this), creditPosition.lender, claimAmount);

        emit Events.Claim(params.creditPositionId, creditPosition.debtPositionId);
    }
```
- Now let's say the user has 100 credit for his credit position and all of the 100 are specified in the params.
- The `reduceCredit` function is called with his `creditPositionId` and `creditPosition.credit`.
- This is how the `reduceCredit` function is represented:
```solidity
 function reduceCredit(State storage state, uint256 creditPositionId, uint256 amount) public {
        CreditPosition storage creditPosition = state.getCreditPosition(creditPositionId);
        creditPosition.credit -= amount;
        state.validateMinimumCredit(creditPosition.credit);

        emit Events.UpdateCreditPosition(
            creditPositionId, creditPosition.lender, creditPosition.credit, creditPosition.forSale
        );
    }
```
- The `amount` parameter in this function will be the `creditPosition.credit` for the user and as we said that was 100.
- Now this function deducts the `creditPosition.credit` by the `amount` which will result in the `creditPosition.credit` being equal to 0(`creditPosition.credit -= amount`). 
- After this happens the `validateMinimumCredit` function is called with the `creditPosition.credit` parameter as the credit, we must not forget that this was set to 0 prior to calling this function, this is how it is represented:
```solidity
 function validateMinimumCredit(State storage state, uint256 credit) public view {
        if (0 < credit && credit < state.riskConfig.minimumCreditBorrowAToken) { 
            revert Errors.CREDIT_LOWER_THAN_MINIMUM_CREDIT(credit, state.riskConfig.minimumCreditBorrowAToken);
        }
    }
```
- Both conditions must be true for the revert statement to be executed because they are combined using the logical && (AND) operator.
- The problem lies in the first part of the check because if `credit` equals to 0 the first condition will be false and this function will pass without reverting, making the user able to claim even if the credit is lower than the `minimumCreditBorrowAToken`.
- This way the funds will be transfered to the user even if the leftover credit is lower than the `minimumCreditBorrowAToken`.

## Recommended Mitigation Steps
To prevent this from happening you can do the next steps:

- Instead of calling the `reduceCredit` function with the `creditPosition.credit` call it with the `claimAmount` parameter.
```solidity
  function executeClaim(State storage state, ClaimParams calldata params) external {
        CreditPosition storage creditPosition = state.getCreditPosition(params.creditPositionId);
        DebtPosition storage debtPosition = state.getDebtPositionByCreditPositionId(params.creditPositionId);

        uint256 claimAmount = Math.mulDivDown(
            creditPosition.credit, state.data.borrowAToken.liquidityIndex(), debtPosition.liquidityIndexAtRepayment
        );
+       state.reduceCredit(params.creditPositionId, claimAmount);
        state.data.borrowAToken.transferFrom(address(this), creditPosition.lender, claimAmount);

        emit Events.Claim(params.creditPositionId, creditPosition.debtPositionId);
    }
```

- Instead of just checking if `0 < credit` check if `0 <= credit`.
```solidity
 function validateMinimumCredit(State storage state, uint256 credit) public view {
 +       if (0 <= credit && credit < state.riskConfig.minimumCreditBorrowAToken) {
            revert Errors.CREDIT_LOWER_THAN_MINIMUM_CREDIT(credit, state.riskConfig.minimumCreditBorrowAToken);
        }
    }
```

- This way in the `reduceCredit` function the amount parameter will be the `claimAmount` and the `claimAmount` will be reduced from the `creditPosition.credit` instead of reducing the credit of that credit position by itself which will set it as 0 and make the vulnerability possible to happen. 
- You can see what i mean in the next example:
```solidity
 function reduceCredit(State storage state, uint256 creditPositionId, uint256 amount) public {
        CreditPosition storage creditPosition = state.getCreditPosition(creditPositionId);
        creditPosition.credit -= amount; //(`The amount specified here will be set as the claimAmount not creditPosition.credit`)
        state.validateMinimumCredit(creditPosition.credit);

        emit Events.UpdateCreditPosition(
            creditPositionId, creditPosition.lender, creditPosition.credit, creditPosition.forSale
        );
    }
```
