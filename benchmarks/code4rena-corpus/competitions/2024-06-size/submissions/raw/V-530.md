# Vulnerability details

## Summary

The `SelfLiquidate` mechanism in the Size protocol has a critical vulnerability that allows a malicious lender to manipulate their collateral ratios and extract undue collateral from the protocol. This exploit stems from flaws in the precision handling and validation logic within the `validateSelfLiquidate` function, despite using the `FixedPointMathLib` library for precise calculations.

## Vulnerability Detail

The `validateSelfLiquidate` function in the `SelfLiquidate.sol` contract is intended to enable lenders to self-liquidate their credit positions when a borrower’s collateral ratio falls below a predefined threshold. However, the current implementation inadequately addresses edge cases involving precision calculations and transaction timing. This opens an avenue for attackers to manipulate the system for unfair collateral extraction.

Here’s a detailed explanation of the issue:

```solidity
function selfLiquidate(SelfLiquidateParams calldata params) external payable override(ISize) whenNotPaused {
    state.validateSelfLiquidate(params);
    state.executeSelfLiquidate(params);
}
```
- This function orchestrates the self-liquidation process by first validating the parameters and then executing the liquidation.

```solidity
function validateSelfLiquidate(State storage state, SelfLiquidateParams calldata params) external view {
    CreditPosition storage creditPosition = state.getCreditPosition(params.creditPositionId);
    DebtPosition storage debtPosition = state.getDebtPositionByCreditPositionId(params.creditPositionId);

    // Validate creditPositionId
    if (!state.isCreditPositionSelfLiquidatable(params.creditPositionId)) {
        revert Errors.LOAN_NOT_SELF_LIQUIDATABLE(
            params.creditPositionId,
            state.collateralRatio(debtPosition.borrower),
            state.getLoanStatus(params.creditPositionId)
        );
    }
    if (state.collateralRatio(debtPosition.borrower) >= PERCENT) {
        revert Errors.LIQUIDATION_NOT_AT_LOSS(params.creditPositionId, state.collateralRatio(debtPosition.borrower));
    }

    // Validate msg.sender
    if (msg.sender != creditPosition.lender) {
        revert Errors.LIQUIDATOR_IS_NOT_LENDER(msg.sender, creditPosition.lender);
    }
}
```
- This function ensures that only eligible credit positions can be self-liquidated and checks if the caller is the lender.

```solidity
function executeSelfLiquidate(State storage state, SelfLiquidateParams calldata params) external {
    emit Events.SelfLiquidate(params.creditPositionId);

    CreditPosition storage creditPosition = state.getCreditPosition(params.creditPositionId);
    DebtPosition storage debtPosition = state.getDebtPositionByCreditPositionId(params.creditPositionId);

    uint256 assignedCollateral = state.getCreditPositionProRataAssignedCollateral(creditPosition);

    // Debt and credit reduction
    state.reduceDebtAndCredit(creditPosition.debtPositionId, params.creditPositionId, creditPosition.credit);

    state.data.collateralToken.transferFrom(debtPosition.borrower, msg.sender, assignedCollateral);
}
```
- This function executes the actual self-liquidation by reducing the debt and credit, and transferring the collateral.

The issue here is:

1. **Collateral ratio calculation**: The current logic calculates the collateral ratio with a specific precision. Small changes in the borrower’s account balance or debt can significantly affect the calculated ratio.

2. **Precision handling**: The `FixedPointMathLib` functions `mulDivUp` and `mulDivDown` are employed for precision arithmetic, but their precision can still be exploited to manipulate the final ratio.

3. **Transaction timing**: An attacker can exploit the timing of transactions to temporarily lower their collateral ratio below the liquidation threshold, triggering self-liquidation, and then revert the ratio back to a profitable state immediately after.

An attacker can:

1. Monitor / interact the protocol to identify / create opportune moments when their collateral ratio is near the liquidation threshold.
2. Execute a transaction that temporarily lowers the collateral ratio just below the threshold, triggering the self-liquidation.
3. Immediately execute another transaction to revert the collateral ratio, ensuring the liquidation occurs at a profitable state.

## Impact

The impact of this vulnerability is severe. It allows a malicious lender to extract more collateral than they are entitled to by manipulating their collateral ratio and exploiting the precision and timing handling in the protocol. This could lead to significant financial losses / damage for the protocol and other users, as the attacker can repeatedly exploit this to drain the protocol’s collateral pool.

2. Call the `selfLiquidate` function with the manipulated parameters.
3. Verify that the collateral extracted is higher than it should be, demonstrating the exploit.

## Recommended Mitigation Steps

To mitigate this vulnerability:

1. Ensure calculations involving collateral ratios are handled with higher precision.
2. Implement a cooldown period or other timing controls to prevent rapid, repeated self-liquidation attempts.
3. Validate the collateral ratio over a period to prevent temporary manipulations.

```solidity
function validateSelfLiquidate(State storage state, SelfLiquidateParams calldata params) external view {
    CreditPosition storage creditPosition = state.getCreditPosition(params.creditPositionId);
    DebtPosition storage debtPosition = state.getDebtPositionByCreditPositionId(params.creditPositionId);

    // validate creditPositionId
    if (!state.isCreditPositionSelfLiquidatable(params.creditPositionId)) {
        revert Errors.LOAN_NOT_SELF_LIQUIDATABLE(
            params.creditPositionId,
            state.collateralRatio(debtPosition.borrower),
            state.getLoanStatus(params.creditPositionId)
        );
    }

    uint256 collateralRatio = state.collateralRatio(debtPosition.borrower);

    if (collateralRatio >= PERCENT) {
        revert Errors.LIQUIDATION_NOT_AT_LOSS(params.creditPositionId, collateralRatio);
    }

    // Implement cooldown period to prevent rapid self-liquidation attempts
    if (block.timestamp - creditPosition.lastSelfLiquidation < state.riskConfig.cooldownPeriod) {
        revert Errors.COOLDOWN_PERIOD_NOT_OVER();
    }

    // validate msg.sender
    if (msg.sender != creditPosition.lender) {
        revert Errors.LIQUIDATOR_IS_NOT_LENDER(msg.sender, creditPosition.lender);
    }
}

function executeSelfLiquidate(State storage state, SelfLiquidateParams calldata params) external {
    emit Events.SelfLiquidate(params.creditPositionId);

    CreditPosition storage creditPosition = state.getCreditPosition(params.creditPositionId);
    DebtPosition storage debtPosition = state.getDebtPositionByCreditPositionId(params.creditPositionId);

    uint256 assignedCollateral = state.getCreditPositionProRataAssignedCollateral(creditPosition);

    // Update the last self-liquidation timestamp
    creditPosition.lastSelfLiquidation = block.timestamp;

    // debt and credit reduction
    state.reduceDebtAndCredit(creditPosition.debtPositionId, params.creditPositionId, creditPosition.credit);

    state.data.collateralToken.transferFrom(debtPosition.borrower, msg.sender, assignedCollateral);
}
```

By implementing these changes, the protocol can prevent the described exploit and ensure a fairer and more secure self-liquidation process.
