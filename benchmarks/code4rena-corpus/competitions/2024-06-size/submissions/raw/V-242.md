# Vulnerability details


## Proof of Concept

First note that the below has been documented here https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/README-sponsor.md#L77-L79

```markdown
##### Variable Pool Borrow Rate Feed

In order to set the current market average value of USDC variable borrow rates, we perform an off-chain calculation on Aave's rate, convert it to 18 decimals, and store it in the Size contract. For example, a rate of 2.49% on Aave v3 is represented as 24900000000000000. The admin can disable this feature by setting the stale interval to zero. If the oracle information is stale, orders relying on the variable rate feed cannot be matched.
```

This implementation has been done to solve the #5 issue from the solidified audit here: https://github.com/code-423n4/2024-06-size/blob/main/audits/2024-03-26-Solidified.pdf that talks about how a malicious user would manipulate the Aave rate slightly, borrow at the lowest point of the yield curve and then deploy the liquidity to to Aave to lower the higher sections of the yield curve further which allows them to then borrow more offers on Size at a reduced yield.

Now the fix Size applied is to have this calculation now done off-chain via a TWAP, which is the current implementation of how variable rates are being set, i.e https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/Size.sol#L120-L129

```solidity
    function setVariablePoolBorrowRate(uint128 borrowRate)
        external
        override(ISizeAdmin)
        onlyRole(BORROW_RATE_UPDATER_ROLE)
    {
        uint128 oldBorrowRate = state.oracle.variablePoolBorrowRate;
        state.oracle.variablePoolBorrowRate = borrowRate;
        state.oracle.variablePoolBorrowRateUpdatedAt = uint64(block.timestamp);
        emit Events.VariablePoolBorrowRateUpdated(oldBorrowRate, borrowRate);
    }
```

Issue however is that this now opens protocol to a new bug case, cause now a malicious user can just front/back run the update the Size Protocol is attempting to do to the variable rates in order to position themselves to make the most profit.

In short since in whatever case _the rate_ used to calculate the position of the yield curve to which the users would place _borrows_ is always _stored_, this means that in _all cases_ the rates would be **stale** in comparison to the real time value from getting the rates from AAVE directly.

A rough POC would be that following an update to the borrow variable rate by Size, a malicious tech savvy user, can front run the tx with a borrow that gives them an upper hand in a relatively lower position at the yield curve and when this rate gets updated they immediately have a profit.

## Impact

A user can still time their entries to have a lower position in the yield curve all they need to do is front/back run the attempt of the owner of the `BORROW_RATE_UPDATER_ROLE` to update the rates

## Recommended Mitigation Steps

Consider having a duration between how users can integrate with the protocol, i.e entering/leaving positions.
