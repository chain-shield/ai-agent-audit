# Vulnerability details

## Impact
This credit check could disrupt normal, valid trades for lenders and borrowers.
## Proof of Concept
The protocol utilizes a minimum credit check to prevent users from initiating a small credit position. This check verifies if the future value of credit (not the opening cash) falls below a minimum threshold.

However, the check in `validateBuyCreditMarket` verifies both cases where the `exactAmountIn` is true (cash) and false (credit).

```jsx

            revert Errors.CREDIT_LOWER_THAN_MINIMUM_CREDIT(params.amount, state.riskConfig.minimumCreditBorrowAToken);
        }

     ...SNIP...

        // validate exactAmountIn
        // N/A
    }

```

If `exactAmountIn` is true, the lender is trying to acquire credit for an exact amount of cash. However, here the minimum credit check is performed with the user-specified cash, not the future credit that this cash can generate.

Example:

Let's assume CREDIT_LOWER_THAN_MINIMUM_CREDIT = 5e6.

If the `params.amount` is 4e6 and the user desires a 200% interest, the future value of the debt, i.e., credit, will be 16e6. Now, the transaction will revert due to the check because 4e6 < 5e6. But it shouldn't, as the credit is well above the threshold.

`CREDIT_LOWER_THAN_MINIMUM_CREDIT` can be increased by an admin to any value. If it is set to 20e6 in the future, it implies that the lender’s call with amount < 20e6 (cash) will fail, which is incorrect.

To validate this issue, let's refer to the same function when `exactAmountIn` is false, and the credit check is performed correctly.

Example

If the params.amount is `16e16` with 200% interest and `exactAmountIn` is false, signifying that 16e6 is a future value (credit) and the lent amount(cash) will be 4e6, a value below the threshold, the transaction will still execute successfully.
