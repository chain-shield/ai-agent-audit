# Vulnerability details

## Impact

As we know, the borrowAToken needs to be scaled because it represents a debt position that accrues interest over time. The LiquidityIndex uses the `getReserveNormalizedIncome` function to indicate the yield that has been accrued over time. According to the documentation, the growth of the value returned by `getReserveNormalizedIncome` indicates the accrued yield: ([Reference](https://docs.aave.com/developers/v/2.0/the-core-protocol/lendingpool#getreservenormalizedincome))

`A return value of 1𝑒27 indicates no income. As time passes, the income is accrued. A value of 2 ∗ 1𝑒27 indicates that for each unit of asset, two units of income have been accrued.`

However, instead of increasing, their token value decreases due to the scaling mechanism where the scaled amount is divided by the liquidity index. Conversely, in the unscale function, the token amount increases significantly because the amount is multiplied by the liquidity index, resulting in more tokens being produced.

Due to this condition, there is a potential for miscalculating the accrued yield for users. This could potentially disrupt the core logic of the protocol, where user deposits of borrow tokens (such as USDC) are automatically supplied to the Variable Pool (Aave v3) and start accruing yield immediately, whereas a fixed-rate loan is not matched.

## Proof of Concept

According to the protocol documentation on deposits, yield begins accruing immediately after users deposit borrow tokens. ([Reference](https://docs.size.credit/technical-docs/contracts/3.1-deposit-and-withdraw))

According to the protocol's logic and documentation, yield accrual stops when a fixed-rate loan is matched. We will examine the code where this occurs, specifically in the BuyCreditMarket library and SellCreditMarket library. Both libraries use `transferFrom` to transfer scaled amounts, where the receiver expects their tokens to either remain scaled or increase.

BuyCreditMarket:

```javascript
state.data.borrowAToken.transferFrom(msg.sender, borrower, cashAmountIn - fees);
```

SellCreditMarket:

```javascript
state.data.borrowAToken.transferFrom(params.lender, msg.sender, cashAmountOut);
```

However, there is a critical error in the `NonTransferableScaledToken::transferFrom` where scaling is implemented. The scaledAmount is calculated by dividing the value by the liquidityIndex instead of multiplying it.

```javascript
    function transferFrom(address from, address to, uint256 value) public virtual override onlyOwner returns (bool) {
        uint256 scaledAmount = Math.mulDivDown(value, WadRayMath.RAY, liquidityIndex());

        _burn(from, scaledAmount);
        _mint(to, scaledAmount);

        emit TransferUnscaled(from, to, value);

        return true;
    }
```

The `NonTransferableScaledToken::_unscale` function also faces a similar issue where unscaled amounts increase. This implementation deviates from the @dev documentation, which states that the unscaled amount should be divided by the current liquidity index. However, in the code, the `scaledAmount` is multiplied by the liquidity index, leading to the production of more tokens than originally intended.

```javascript
    /// @dev The unscaled amount is the scaled amount divided by the current liquidity index
    function _unscale(uint256 scaledAmount) internal view returns (uint256) {
        return Math.mulDivDown(scaledAmount, liquidityIndex(), WadRayMath.RAY);
    }
```

If yield has been accrued, the liquidityIndex() will increase. For instance, let's assume liquidityIndex() is 2 * 1e27 and the value is 2e6:

`scaledAmount` = 2e6 * 1e27 / 2 * 1e27 = 1e6.
`_unscale` = 1e6 * 2 * 1e27 / 1e27 = 2e6.

In `NonTransferrableScaledToken::transferFrom`, the `scaledAmount` will be burned and minted to the recipient's address. However, the recipient will receive an amount less than the original amount.
