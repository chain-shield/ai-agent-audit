# Vulnerability details

## Impact
The presence of potential reentrancy vulnerabilities in the `DepositTokenLibrary` contract's deposit and withdraw functions can lead to significant security risks. Specifically, an attacker can exploit these vulnerabilities to perform recursive calls to the deposit and withdraw functions, allowing them to manipulate the state in ways that could result in unauthorized minting or withdrawal of tokens. This can lead to a draining of funds from the protocol, financial losses for users, and a compromise of the protocol's integrity.

## Proof of Concept
#### Initial Deposit:
- An attacker calls the `depositUnderlyingCollateralToken` function to deposit tokens.
- The `safeTransferFrom` function is called, which transfers tokens to the contract.
#### Reentrant Call:
- Before the mint function is called, the control is transferred to an attacker-controlled contract via the `safeTransferFrom` function.
- The attacker-controlled contract makes a recursive call back to the `depositUnderlyingCollateralToken` function.
- This recursive call allows the attacker to manipulate the state and potentially mint more tokens than intended.
#### Initial Withdraw:
- An attacker calls the `withdrawUnderlyingCollateralToken` function to withdraw tokens.
- The `burn` function is called, which burns the specified amount of tokens.
#### Reentrant Call:
- Before the `safeTransfer` function is called, the control is transferred to an attacker-controlled contract via the `safeTransfer` function.
- The attacker-controlled contract makes a recursive call back to the `withdrawUnderlyingCollateralToken` function.
- This recursive call allows the attacker to withdraw more tokens than they should be able to.

## Tools Used
Manual code review

## Recommended Mitigation Steps
Very simple but effective - `nonReentrant` modifier should be added to the deposit and withdraw functions
