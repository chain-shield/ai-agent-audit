# Vulnerability details

### Impact

If an attacker exploits this vulnerability, they can trigger liquidations that exceed the borrower’s debt. This can drain the contract's funds, leading to significant financial losses for users and potentially causing the contract to become insolvent. This undermines the integrity of the liquidation process and could result in a loss of trust in the protocol.

### Proof of Concept

Consider this scenario, which is possible due to the nature of the `liquidate()` function:

1.  **Attacker Identifies Target:** An attacker identifies a borrower with an outstanding loan and a healthy collateralization ratio above the liquidation threshold.
2.  **Manipulating the Oracle:** The attacker manipulates the price oracle (e.g., through a flash loan attack) to artificially inflate the price of the borrowed asset. This makes the borrower's position appear undercollateralized, even though it's not in reality.
3.  **Triggering Liquidation:** The attacker calls the `liquidate()` function, specifying the target borrower's debt position and a liquidation amount that significantly exceeds the actual outstanding debt.
4.  **Insufficient Validation:** The `liquidate()` function in `Size.sol` and `Liquidate.sol` does not include a check to ensure that the liquidation amount is less than or equal to the borrower's actual debt.
5.  **Over-Liquidation:** Due to the lack of validation, the contract processes the liquidation, seizing and transferring an excessive amount of the borrower's collateral to the attacker. The attacker profits from the difference between the inflated liquidation amount and the actual debt.
6.  **Consequences:** The borrower suffers a significant loss of collateral, potentially exceeding the value of their original loan. This can lead to a cascade of liquidations if other borrowers are also affected by the manipulated oracle price. The protocol's solvency may be threatened if the attacker successfully drains a substantial amount of funds.

### Tools Used

*   Manual code review
*   Understanding of flash loan attacks and price oracle manipulation techniques

### Recommended Mitigation Steps

To mitigate this vulnerability, it is crucial to add a validation check within the `liquidate()` function to ensure that the `liquidateAmount` does not exceed the borrower's actual outstanding debt. This can be achieved by comparing the `liquidateAmount` with the `debtToCover` which is derived from the `debtPosition.futureValue`.

```solidity
// Liquidate.sol
function liquidate(LiquidateParams calldata params) external returns (uint256 liquidatorProfitCollateralToken) {
    // ... existing code ...

    // Add validation check
    require(params.liquidateAmount <= debtToCover, "Liquidation amount exceeds debt");

    // ... rest of the liquidation logic ...
}
```

This additional check will prevent attackers from initiating liquidations with excessive amounts, thus protecting borrowers from over-liquidation and safeguarding the protocol's funds.
