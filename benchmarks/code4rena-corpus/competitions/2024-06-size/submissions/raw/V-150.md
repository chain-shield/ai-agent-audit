# Vulnerability details

## Impact
Borrowers can avoid getting liquidated under certain conditions

## Proof of Concept
Users can liquidate borrowers if their collateral ratio is below the liquidation threshold. In return, they receive a reward that is supposed to incentivize users to liquidate borrowers that have a non-healthy collateral ratio. 

With that in mind, if a borrower can make his position into such that if liquidated, there would be no actual incentive for the liquidator, then it is likely that no one would actually liquidate the borrower. The borrower can do exactly that by compensating his position. That functionality allows borrowers to repay only a part of their debt instead of the full amount they can repay using `repay()`. That happens by the borrower splitting his debt position and then using `repay()` on one of those split positions thus repaying only a part of his debt. The thing is that the borrower can split his position into as many positions that have at least the minimum allowed amount for a position (5e6 or 5\$ according to deployment scripts). Then, here is what happens whenever he is liquidatable:
```solidity
uint256 liquidatorReward = Math.min(
                assignedCollateral - debtInCollateralToken,
                Math.mulDivUp(debtPosition.futureValue, state.feeConfig.liquidationRewardPercent, PERCENT)
            );
```
The liquidator reward (the net profit the liquidator receives as a reward) is calculated in the way shown above. While there is another issue here that makes all liquidations non-incentivized, we will ignore it (the issue is in the second input of Math.min, that's why we choose the first input even though we would actually get the second one in this scenario) and we will choose the first input as the reward (that's the larger amount thus liquidations would be even more incentivized than usual).

Let's assume the following scenario (all values like thresholds, minimum allowed amounts and others are based on the actual deployment scripts which as mentioned by the sponsors are valid examples):
1. Price of ETH is 3000\$
2. Alice borrows money from Bob and her collateral ratio is the minimum possible at time of borrow (1.5e18), she puts 1e18 as collateral (1 ETH = 3000\$) and takes out 2000\$ as USDC
3. Her collateral ratio drops to 1.29e18 and is liquidatable (threshold is 1.3e18) and thus, price of ETH is 2580\$
4. Alice, at an earlier point, has already split her positions into the minimum allowed amounts (5e6 or 5\$)
5. Now, upon a liquidation, `debtInCollateralToken` is 1937984490000000 (5\$ of ETH at 2580\$ price) and `assignedCollateral` is 1.29 times that so 2500000000000000
6. The liquidation profit is `2500000000000000 - 1937984490000000 = 562015510000000` which is \$1.45 at price of ETH at \$2580.

There are 2 things to consider now. We chose the biggest input of Math.min() when we should have chosen the lower one but due to a mistake in the code (at least I believe so), we chose the bigger option. With the mistake in the code, the reward for the liquidator is a lot less than a cent (that is the actual scenario that would occur). Whenever the mistake is fixed (according to my proposed fix), the reward would be \$0.25 (the issue I am talking about is the fact that the second input in Math.min is in 6 decimals and the rewards are super low as they are added to a collateral amount, however if the code is changed and it uses `debtInCollateralToken` instead of `futureValue` for the Math.min input, then rewards would be \$0.25 as specified above).

\$0.25 would pretty much always be higher than the gas fees making the liquidation non-incentivized. \$1.45 is debatable but gas fees would still be higher in some cases. However, since the profit for the liquidator wouldn't actually be \$1.45 but much smaller than that (a lot less than a cent in current code and \$0.25 when fixed), the issue will definitely occur.

Paste the following POC into `Compensate.t.sol`:
```solidity
        function testLiquidatorsAreNotIncentivized2() public {
        _setPrice(3000e18); // ETH price is 3000$

        _deposit(bob, usdc, 2_000e6);
        _deposit(alice, weth, 1e18); // Bob and Alice deposit

        _buyCreditLimit(bob, type(uint256).max, YieldCurveHelper.pointCurve(1 hours, 0));
        uint256 debtPositionId = _sellCreditMarket(alice, bob, RESERVED_ID, 2000e6, 1 hours, true); // Alice takes a loan from Bob
        uint256 creditPositionId = size.getCreditPositionIdsByDebtPositionId(debtPositionId)[0];

        vm.prank(alice);
        size.compensate(CompensateParams({creditPositionWithDebtToRepayId: creditPositionId, creditPositionToCompensateId: RESERVED_ID, amount: 5e6}));

        _setPrice(2580e18); // Price drops to 2580$ and now Alice is liquidatable

        _deposit(liquidator, usdc, 5e6);

        assertEq(size.getDebtPosition(debtPositionId + 1).futureValue, 5e6);

        uint256 liquidatorProfit = _liquidate(liquidator, debtPositionId + 1, 0);
        assertEq(1937984496374032, liquidatorProfit); // $5.00000000065 at current prices (that is with the issue explained in the report)
    }
```
