# Vulnerability details

## Impact
The `sellCreditMarket` transfers the borrowed amount to the caller (borrower) even if the `params.creditPositionId` is not equal to `RESERVED_ID`. If the borrower is selling an existing credit position `(params.creditPositionId != RESERVED_ID)`, they will receive the borrowed amount again, doubling their borrowed funds.

## Proof of Concept
Here's how an attacker could exploit this bug.

   1. The attacker opens a new credit position by calling `sellCreditMarket` with `params.creditPositionId == RESERVED_ID`. They receive the borrowed amount as expected.

   2. The attacker then calls `sellCreditMarket` again, but this time with `params.creditPositionId` set to the ID of the previously opened credit position. According to the current implementation, the attacker will receive the borrowed amount again, doubling their funds without providing additional collateral or being subject to proper checks.

The attacker can repeat this process multiple times, each time gaining unauthorized funds from the protocol.

The Code that illustrates this vulnerability is in the [@>/sellCreditMarket](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/Size.sol#L188-L195)
```solidity
function sellCreditMarket(SellCreditMarketParams memory params) external payable override(ISize) whenNotPaused {
    state.validateSellCreditMarket(params);
    uint256 amount = state.executeSellCreditMarket(params);
    if (params.creditPositionId == RESERVED_ID) {
        state.validateUserIsNotBelowOpeningLimitBorrowCR(msg.sender);
    }
    state.validateVariablePoolHasEnoughLiquidity(amount);
}
```
As you can see, the `validateVariablePoolHasEnoughLiquidity` check and the transfer of the borrowed amount happen regardless of the value of `params.creditPositionId`. This allows the attacker to receive the borrowed amount multiple times by selling existing credit positions.

Consider an example:

   1. The attacker calls `sellCreditMarket` with `params.creditPositionId == RESERVED_ID` and `params.amount == 1000`. They receive 1000 tokens as the borrowed amount.

   2. The attacker calls `sellCreditMarket` again, this time with `params.creditPositionId` set to the ID of the previously opened credit position and `params.amount == 1000`. They receive another 1000 tokens, bringing their total unauthorized funds to 2000 tokens.

   3. The attacker can repeat this process, each time gaining an additional 1000 tokens without providing any additional collateral or being subject to proper checks.

## Recommended Mitigation Steps
Only transfer the borrowed amount to the borrower if `params.creditPositionId == RESERVED_ID`, indicating a new credit position is being opened. If an existing credit position is being sold, the borrowed amount should not be transferred again.
```diff
function sellCreditMarket(SellCreditMarketParams memory params) external payable override(ISize) whenNotPaused {
    state.validateSellCreditMarket(params);
    uint256 amount = state.executeSellCreditMarket(params);
    if (params.creditPositionId == RESERVED_ID) {
+       state.validateUserIsNotBelowOpeningLimitBorrowCR(msg.sender);
        state.validateVariablePoolHasEnoughLiquidity(amount);
    }
}
```
With this, the `validateVariablePoolHasEnoughLiquidity` check and the transfer of borrowed amount will only happen for new credit positions, preventing the double transfer of funds for existing positions.
