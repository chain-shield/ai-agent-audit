# Vulnerability details

## Impact
Borrower can avoid liquidation and also discourage `liquidators` from doing their job.

## Proof of Concept
The size protocol allow users (lenders) or even normal users to liquidate an `underWater` position, or an `overDue` position, this is happening via the [liquidate](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/Size.sol#L210) function
```js
 function liquidate(LiquidateParams calldata params)
        external
        payable
        override(ISize)
        whenNotPaused
        returns (uint256 liquidatorProfitCollateralToken)
    {
        state.validateLiquidate(params);
        liquidatorProfitCollateralToken = state.executeLiquidate(params);
        state.validateMinimumCollateralProfit(params, liquidatorProfitCollateralToken);
    }
```
But there is a scenario where the `borrower` can avoid liquidation, and its by the borrower front-running the `liquidator` whenever he's to liquidate and call the [repay](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/Repay.sol#L46) function.

The `liquidator's` call to the `liquidate` function will now revert because the position is no longer liquidatable.

In a scenario where the `liquidator` is aware of the front-running risk ( which in most cases, he'll not be) and decided to tip the block builder (miner) due to the `5% reward on top of the liquidation repayment` in order to get his call included first, but this doesn't mean the `borrower` can't risk doing the same in order to make sure his call succeed, this will discourage the `liquidator`.

And also, since the `liquidators`  will not assume such thing, the possibility is very high, liquidators would be in a hot spot of whether they would be front-run or not

Coded POC 

paste in `liquidate.t.Sol`

```js
function test_Liquidate_liquidate_repays_loan() public {
        _setPrice(1e18);

        _deposit(alice, weth, 100e18);
        _deposit(alice, usdc, 100e6);
        _deposit(bob, weth, 100e18);
        _deposit(bob, usdc, 100e6);
        _deposit(liquidator, weth, 100e18);
        _deposit(liquidator, usdc, 100e6);

        _buyCreditLimit(alice, block.timestamp + 365 days, YieldCurveHelper.pointCurve(365 days, 0.03e18));
        uint256 debtPositionId = _sellCreditMarket(bob, alice, RESERVED_ID, 15e6, 365 days, false);

        // Liquidation price
        _setPrice(0.2e18);

        // bob repays right before liquidation(front-run)
        vm.prank(bob);
        size.repay(RepayParams({debtPositionId: debtPositionId}));

        // This will revert because loan is not liquidatable
        _liquidate(liquidator, debtPositionId);
    }
```

## Recommended Mitigation Steps

I recommend either disallowing repayment when the position is `underWater` or (most likely solution) add another 5% penalty in case if repaying an `underwater` position.

This recommendation will at least discourage front-running liquidations.
