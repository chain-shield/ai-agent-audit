# Vulnerability details

## Impact
There are different variations of liquidations in Size, the standard liquidation via `liquidate()`, the self liquidation via `selfLiqiuidate()` and the [liquidateWithReplacement()](https://docs.size.credit/technical-docs/contracts/3.5-liquidations#id-3.5.3.3-liquidation-with-replacement) whcih liquidates a loan and immediately reassigns the retrieved value to another loan/ borrow offer. 

So we can say `liquidateWithReplacement()` is a combination of` liquidate()` + `buyCreditMarket()` (this is used to fill borrow orders). 

The size protocol has several global limits which are enforced through the system to limit user behaviour and are stored as riskConfigs. I will focus on  `state.riskConfig.minimumCreditBorrowAToken` here. `riskConfig.minimumCreditBorrowAToken` is a global limit which specifies the [minumum amount that can be borrowed as a loan](https://docs.size.credit/technical-docs/governance-variables-and-fees#protocol-safety-parameters). `liquidateWithReplacement()` liquidates a loan and then fills another borrowOffer/ loan,  but does not check that the amount given as loan is not lower than `state.riskConfig.minimumCreditBorrowAToken`.  Do note that  `buyCreditMarket()` validates this as seen [here](https://github.com/code-423n4/2024-06-size/blob/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/BuyCreditMarket.sol#L90C1-L93C10). This ensures that the borrowAtoken amount that is transferred to the borrower is not lower than the `riskConfig.minimumCreditBorrowAToken`. ### Scenario 
- user B(borrower) takes min loan amount financed by user A(lender)
- governance decides to update risk config and increase value of `state.riskConfig.minimumCreditBorrowAToken`
- loan position gets underwater/ ripe for liquidation and gets liquidated via `liquidateWithReplacement()`
- new loan with amount which is lower than the set `minimumCreditBorrowAToken` is created via `liquidateWithReplacement()`

While governance parameters will not be changed everyday, there is a possiblilty that once there is a change/update made it will still be possible for new loans amounts below minimumCreditBorrowAToken to be created. 
The creation of a new loan which is smaller than the set minimum amount for loans violates the protocol governance parameters. This loophole can be exploited by some users to bypass the governance rules/decision.  

## Proof of Concept
- paste test code below in `test/local/actions/LiquidateWithReplacement.t.sol`
- add `import {UpdateConfigParams} from "@src/libraries/actions/UpdateConfig.sol";` to the imports 
- run test with `forge test --mt test_LiquidateWithReplacement_liquidateWithReplacement_updates_new_borrower_borrowAtoken_amount_smaller_than_riskConfigMinAToken  -vvv`

```solidity
    function test_LiquidateWithReplacement_liquidateWithReplacement_updates_new_borrower_borrowAtoken_amount_smaller_than_riskConfigMinAToken()
        public
    {
        _setPrice(1e18);
        _updateConfig("swapFeeAPR", 0);
        _updateConfig("liquidationRewardPercent", 0.1e18);
        _deposit(alice, weth, 100e18);
        _deposit(alice, usdc, 100e6);
        _deposit(bob, weth, 100e18);
        _deposit(bob, usdc, 100e6);
        _deposit(candy, weth, 400e18);
        _deposit(candy, usdc, 100e6);
        _deposit(liquidator, weth, 100e18);
        _deposit(liquidator, usdc, 100e6);
        _buyCreditLimit(
            alice,
            block.timestamp + 365 days,
            YieldCurveHelper.pointCurve(365 days, 0.03e18)
        );
        _sellCreditLimit(candy, 0.03e18, 365 days);
        uint256 amount = 15e6;
        uint256 debtPositionId = _sellCreditMarket(
            bob,
            alice,
            RESERVED_ID,
            amount,
            365 days,
            false
        );
        uint256 futureValue = Math.mulDivUp(
            amount,
            (PERCENT + 0.03e18),
            PERCENT
        );
        uint256 delta = futureValue - amount;

        _setPrice(0.2e18);

        Vars memory _before = _state();

        assertEq(size.getDebtPosition(debtPositionId).borrower, bob);
        assertGt(size.getDebtPosition(debtPositionId).futureValue, 0);
        assertEq(size.getLoanStatus(debtPositionId), LoanStatus.ACTIVE);

        // here amount is the issuance value, so we adjust the state.riskConfig.minimumCreditBorrowAToken to be more than amount before liquidating
        size.updateConfig(
            UpdateConfigParams({
                key: "minimumCreditBorrowAToken",
                value: amount + 1e6
            })
        );

        assertTrue(size.riskConfig().minimumCreditBorrowAToken == amount + 1e6);

        // now liquidation happens and a new borrow order is filled with an amount lower than the minimumCreditBorrowAToken.
        _liquidateWithReplacement(liquidator, debtPositionId, candy);

        Vars memory _after = _state();

        assertEq(_after.alice, _before.alice);
        assertEq(
            _after.candy.debtBalance,
            _before.candy.debtBalance + futureValue
        );
        assertEq(
            _after.candy.borrowATokenBalance,
            _before.candy.borrowATokenBalance + amount
        );
        assertEq(
            _after.feeRecipient.borrowATokenBalance,
            _before.feeRecipient.borrowATokenBalance + delta
        );
        assertEq(size.getDebtPosition(debtPositionId).borrower, candy);
        assertGt(size.getDebtPosition(debtPositionId).futureValue, 0);
        assertEq(size.getLoanStatus(debtPositionId), LoanStatus.ACTIVE);
    }

```

## Recommended Mitigation Steps

add check below to `executeLiquidateWithReplacement()` logic before transfer of BorrowAtoken to the borrower. 

```solidity
        if (issuanceValue < state.riskConfig.minimumCreditBorrowAToken) {
            revert Errors.CREDIT_LOWER_THAN_MINIMUM_CREDIT(
                issuanceValue,
                state.riskConfig.minimumCreditBorrowAToken
            );
        }

        state.data.borrowAToken.transferFrom(address(this), params.borrower, issuanceValue);
```
