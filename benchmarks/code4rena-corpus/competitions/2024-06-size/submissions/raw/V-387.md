# Vulnerability details

## Summary

The `compensate` function in the Size protocol has insufficient validation, allowing for strategic misuse and miscalculation of debt and credit positions. This vulnerability enables borrowers to underpay their debt or over-claim compensation, leading to financial losses for the protocol and its users.

## Vulnerability Detail

The `Compensate` function allows users to compensate a borrower's debt with their credit from another loan. However, the validation logic for this function has exploitable gaps:

Here is a problematic snippet from the `compensate` function highlighting the lack of necessary validations:

```solidity
function validateCompensate(State storage state, CompensateParams calldata params) external view {
    CreditPosition storage creditPositionWithDebtToRepay =
        state.getCreditPosition(params.creditPositionWithDebtToRepayId);
    DebtPosition storage debtPositionToRepay =
        state.getDebtPositionByCreditPositionId(params.creditPositionWithDebtToRepayId);

    uint256 amountToCompensate = Math.min(params.amount, creditPositionWithDebtToRepay.credit);

    // Missing validation for ensuring the credit position hasn't been used before for another compensation
    if (params.creditPositionToCompensateId != RESERVED_ID) {
        CreditPosition storage creditPositionToCompensate =
            state.getCreditPosition(params.creditPositionToCompensateId);
        amountToCompensate = Math.min(amountToCompensate, creditPositionToCompensate.credit);
    }

    // Missing checks to ensure proper decrement in available credit
}
```

1. **Insufficient validation on credit position usage**:

- There is no check to ensure that the credit position (`creditPositionToCompensateId`) has not been previously used in another transaction for compensation.
   
2. **Risk of multiple compensations**:

- A user can call `Compensate` multiple times using the same `creditPositionToCompensateId`, leading to a scenario where they over-compensate and reduce their debt more than they should without a proper decrement in the available credit.

3. **Misalignment in accounting**:

- If a user creates multiple debt positions and uses the same credit position for compensation, it can lead to a misalignment in the accounting of debt and credit, resulting in an incorrect state in the protocol's records.

## Impact

The primary impact of this vulnerability is financial loss due to improper handling of debt and credit positions. Borrowers can reduce their debt more than allowed, leading to a misbalance in the protocol's accounting and consecutive financial losses for lenders. In extreme cases, this could result in insolvency scenarios where the total outstanding debt exceeds the available collateral, risking the protocol's solvency.

## Proof of Concept

1. Create debt and credit positions for a borrower and a lender.
2. Use the `Compensate` function with the same `creditPositionToCompensateId` multiple times to compensate different debt positions.
3. Observe that the credit is not correctly decremented, allowing for overcompensation.
4. Verify the state of the protocol and notice the discrepancy in debt reduction and credit assignment, confirming the exploit.

## Recommended Mitigation Steps

To address these issues, the `compensate` and its associated functions need enhanced validation logic to ensure that the `creditPositionToCompensateId` is correctly managed. Below is an example refactored impl of the interested functions with the recommended changes.

Add the following check in validateCompensate:

```solidity
// New validation to ensure the credit position is not reused
if (state.isCreditPositionUsedForCompensation(params.creditPositionToCompensateId)) {
    revert Errors.CREDIT_POSITION_ALREADY_USED(params.creditPositionToCompensateId);
}
```

Also, add another check in executeCompensate:

```solidity
// Mark the credit position as used for compensation
state.markCreditPositionAsUsed(params.creditPositionToCompensateId);
```

Supporting functions (assumed to be added to the contract's state management):

These would be part of the State storage contract or `Compensate` library to support the new validation and marking logic:

```solidity
// Check if a credit position has been used for compensation
function isCreditPositionUsedForCompensation(State storage state, uint256 creditPositionId) internal view returns (bool) {
    return state.data.usedCreditPositions[creditPositionId];
}

// Mark a credit position as used for compensation
function markCreditPositionAsUsed(State storage state, uint256 creditPositionId) internal {
    state.data.usedCreditPositions[creditPositionId] = true;
}
```

State variable to track used credit positions:

This would be part of the state variables in the storage contract:

```solidity
// Mapping to track used credit positions
mapping(uint256 => bool) usedCreditPositions;
```

These additions ensure that the credit position is not reused, effectively preventing the multiple compensations issue identified in the original vulnerability.
