# Vulnerability details

## Impact
The protocol have a `Compensate` contract that should allow borrowers to partially repay their loan or have a borrower early exit (as stated in the docs and readme). The way this should work is that the borrower can repay some loan he have (existing credit position if `creditPositionToCompensateId ` is not `RESERVED_ID`) with the credit he have (which mean he must lend someone money in order to get that credit so now he is also lender in this case). So one of the most important thing in this process to work is that the credit he is using to repay (in our case this is `creditPositionWithDebtToRepayId`) another credit (in our case this is `creditPositionToCompensateId`) should have due date before the due date of desired credit he want to repay. Which make sense because when time comes to repay that credit position he want to compensate he already have funds from the credit that another borrower owed him.

## Proof of Concept
The issue comes up with this check in `validateCompensation` :
```
            if (
                debtPositionToRepay.dueDate
                    < state.getDebtPositionByCreditPositionId(params.creditPositionToCompensateId).dueDate
            ) {
                revert Errors.DUE_DATE_NOT_COMPATIBLE(
                    params.creditPositionWithDebtToRepayId, params.creditPositionToCompensateId
                );
            }
```
It check if `dueDate` of `debtPositionToRepay` is less that the `dueDate` of the credit position he wants to compensate and if true it will throw an error. 
The problem is that the `debtPositionToRepay` is the debt position of the credit that he want to use to repay the credit he try to compensate as we can see here:
```
        DebtPosition storage debtPositionToRepay =
            state.getDebtPositionByCreditPositionId(params.creditPositionWithDebtToRepayId);
```
Link of that part of the code: 
https://github.com/code-423n4/2024-06-size/blame/8850e25fb088898e9cf86f9be1c401ad155bea86/src/libraries/actions/Compensate.sol#L45-L46

So as we can see the `debtPositionToRepay` we got from the `creditPositionWithDebtToRepayId` which is the credit user will use to repay the credit he want's to compensate (in this case `creditPositionToCompensateId`).

So in simple terms this check checks if dueDate of `creditPositionWithDebtToRepay` is less than dueDate of `creditPositionToCompensate` and if `true` it will revert with compatibility error.
This fundamentally breaks  the most important invariant for compensation to work correctly and that is that dueDate of the credit user want to use to repay another credit must always be before dueDate of that credit in other words :
`creditPositionWithDebtToRepay` < `creditPositionToCompensate` - their dueDate must always holds like this and be `true` in order this to work and make sense.

But in this case it does not and it will revert if this is `true` and for correct users who should not revert and allow wrong or malicious users to compensate. For the correct users this can be `make or break` function because they can be liquidated if they don't have enough funds and compensation don't work for them even thou it's purpose is to help them.
While the malicious users can exploit this and compensate with credit that `dueDate` is later than the `dueDate` of the credit position they are trying to compensate (and their debt will be reduced and on accounting side they would be all good) which can lead to further exploit and loss of the borrower that debt is used for compensation (the borrower of this position `debtPositionToRepay` which we got from `creditPositionWithDebtToRepayId`) which can make him loss collateral due to overdue debt althrough he should not because his due date still is not reached. Or the lender of the credit position the borrower want to compensate (`creditPositionToCompensate`) could not claim and receive funds because there are not funds or the wrong borrower would be punished for that. In either scenario it will mess up protocol, accounting and it can be a big problem for the protocol and it's users.

## Recommended Mitigation Steps
In `validateClaim` instead of reverting and giving error when `dueDate` of `debtPositionToRepay` is less than `dueDate` of `creditPositionToCompensateId` it should revert when it is not less (when it is bigger) so this would be my recommendation:
```
            if (
                debtPositionToRepay.dueDate
                    > state.getDebtPositionByCreditPositionId(params.creditPositionToCompensateId).dueDate
            ) {
                revert Errors.DUE_DATE_NOT_COMPATIBLE(
                    params.creditPositionWithDebtToRepayId, params.creditPositionToCompensateId
                );
            }
```
