# Vulnerability details

## Description
In the context of Pendle joins, the transferAndJoin function at the PoolAction contract takes the maximum amounts possible from the caller (`from` argument) to be able to join the Pendle pool within the user defined token limits:
```solidity
function transferAndJoin(
        address from,
        PermitParams[] calldata permitParams,
        PoolActionParams calldata poolActionParams
    ) external {
        ...
                        else if(poolActionParams.protocol == Protocol.PENDLE) {
                (, , TokenInput memory input,) = abi.decode(poolActionParams.args, (address, ApproxParams, TokenInput , LimitOrderData));
                
                if (input.tokenIn != address(0)) {
                    _transferFrom(input.tokenIn, from, address(this), input.netTokenIn, permitParams[0]);
                }
...
    }
```

Then it calls the join public payable function, which will call `_pendleJoin`.
The contract approves the max amounts to the pendleRouter then calls pendleRouter.addLiquiditySingleToken:`
```solidity
function _pendleJoin(PoolActionParams memory poolActionParams) internal {
       ...
        
        if (input.tokenIn != address(0)) {
                IERC20(input.tokenIn ).forceApprove(address(pendleRouter),input.netTokenIn);
            }

        pendleRouter.addLiquiditySingleToken{value: msg.value}(poolActionParams.recipient, market, poolActionParams.minOut, guessPtReceivedFromSy, input, limit);
    }
```

If we take a look at pendleRouter's addLiquiditySingleToken implementation, we notice the calltrace leads us to the `_fillLimit` function at ActionBase.sol [pendle-core-v2-public/contracts/router/base/ActionBase.sol at 7b3d0eb9362fd7f4e861d58856e2ac2262367c3d · pendle-finance/pendle-core-v2-public (github.com)](https://github.com/pendle-finance/pendle-core-v2-public/blob/7b3d0eb9362fd7f4e861d58856e2ac2262367c3d/contracts/router/base/ActionBase.sol#L340) This function checks if the actualTaking value is within the user-defined bounds at maxAmountsIn then transfers t *only the amount required to do the join operation.* This means the max amount in that was sent to the PoolAction contract is not fully utilized.

The other parts of the function at the PoolAction contract, however, do not return the excess funds to the user. This makes the maxAmountsIn values not the limit, but always the amount the user spends.
## Impact
Users that call pendle joins will not have their excess tokens returned in case they set a maxAmountIn bigger than the strictly necessary.
## Tools Used
Manual review
## Recommended Mitigation Steps
Make sure to return the funds that we're not consumed by the Pendle vault during the join call. 

An interesting way do to such a thing would be to keep track of the tokens' balances before and after the pendleRouter.addLiquiditySingleToken call. If the balance difference was smaller than the maxAmountIn for a token, then return to the user maxAmountIn - difference units of the token.
