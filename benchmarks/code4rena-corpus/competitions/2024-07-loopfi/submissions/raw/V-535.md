# Vulnerability details

## Impact
An attacker can use donation attack immediately the AuraVault.sol is deployed.  this will manipulate share price so that users that deposit to the AuraVault.sol after the donation attack will receive zero shares or lesser shares that they are supposed to recieve.

## Proof of Concept
The main issue is that the AuraVault.sol is using its balance of the `rewardPool` receipt token to calculate the amount of `shares` it will mint to a user when the user deposits. 

Using the token balance of a contract to make critical calculations like the amount of `shares` can be easily manipulated by simply directly sending the particular tokens to the contract. The attacker donates the amount of token to the contract, increasing the balance there by affecting the output of the calculations of shares.

Using the `balanceOf(addrress(this))` in AuraVault.sol is the root of what makes AuraVault.sol vulnerable to donation attack.

```Solidity
File: AuraVault.sol
    function totalAssets() public view virtual override(IERC4626, ERC4626) returns (uint256) {
        return IPool(rewardPool).balanceOf(address(this));
    }
```

Let's go into detail starting from the deposit function.
```solidity
File: AuraVault.sol
function deposit(uint256 assets, address receiver) public virtual override(IERC4626, ERC4626) returns (uint256) {
        uint256 shares = previewDeposit(assets);
        _deposit(_msgSender(), receiver, assets, shares);

        // Deposit  in reward pool
        IERC20(asset()).safeApprove(rewardPool, assets);
        IPool(rewardPool).deposit(assets, address(this));

        return shares;
    }
```
As seen in the `deposit(...)` function above, the amount of `shares` to send to the user is calculated with the `previewDeposit` function, the `previewDeposit` function in turn calls the `_convertToShares` function.

```solidity
File: AuraVault.sol
function _convertToShares(uint256 assets, Math.Rounding rounding) internal view virtual override returns (uint256) {
        return assets.mulDiv(totalSupply() + 10 ** _decimalsOffset(), totalAssets() + 1, rounding);
    }
```

In the above, we can see that the amount of `shares` is calculated with by multiplying the `asset` by (totalSupply + 10) then dividing by the `totalAssets()`.


`totalAsset()` function can be increased by anyone by just sending the rewardPool token to the AuraVault.sol contract.

Also note that the `totalAsset()` is the `denomenator` in the calculation of shares.

So a malicious user just directly send `rewardPool` receipt token to the AuraVault.sol contract immediately it is deployed. let's say the attacker directly sent 1000  reward pool token to the contract before any user deposits on the contract.
When a first user deposits lesser than 1000 reward pool receipt token, the user will get zero shares in return causing the user to lose the deposited asset.

## Exploit Scenario
1. Bob is the attacker and Alice is the victim
2. Bob directly send 1000 rewardPool receipt token to AuraVault.sol immediately it is deployed.
3. Alice deposits 10 asset token 
4. Since the the formular to calculate amount of `shares` token is: `assets.mulDiv(totalSupply() + 10 ** _decimalsOffset(), totalAssets() + 1, rounding);`

5. The the amount of shares Alice will receive will be:
10 * (0 + 10) / (1000 + 1)

This will be 100/1000 = 0; The result is zero in Solidity 

6. Alice receives zero shares causing her to lose her 10 asset token.

Manual review


## Recommended Mitigation Steps
Consider creating a `_totalAsset_` that is only updated when users make deposits and withdraw. Then is the created `_totalAsset_` in calculating the amount of shares instead of the current `IPool(rewardPool).balanceOf(address(this))` that is in the `totalAssets()` function of AuraVault.sol
