# Vulnerability details


## Proof of Concept

The `cooldownDuration` could be set in the `StakingLPEth.sol`, which then means that users are expected to wait [for this duration to pass before being able to claim their stakes](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L92).

> NB: This particular bug case is applicable to both `cooldownAssets` & `cooldownShares` however this report would only focus on `cooldownAssets`.

Problem however is the fact that even though a user can call `cooldownAssets` whenever with whatever amount of assets, the protocol wrongly keeps only one track of the attempted withdrawal, this then means that with every withdrawal attempt, the cooldown end is freshly set for all the withdrawals, i.e the ones in the queue and the fresh one that's being queried see [StakingLPEth#cooldownAssets()](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L104-L114)

```solidity
function cooldownAssets(uint256 assets) external ensureCooldownOn returns (uint256 shares) {
  if (assets > maxWithdraw(msg.sender)) revert ExcessiveWithdrawAmount();

  shares = previewWithdraw(assets);

  cooldowns[msg.sender].cooldownEnd = uint104(block.timestamp) + cooldownDuration;
  cooldowns[msg.sender].underlyingAmount += uint152(assets);

  _withdraw(msg.sender, address(silo), msg.sender, assets, shares);
}

```

### Coded POC

Attach this test at the end of [StakingLP.t.sol](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/test/unit/StakingLP.t.sol#L117-L148).

```solidity
function test_multiple_cooldown_attempts_reset_cooldown() public {
  stakingLpEth.setCooldownDuration(7 days);
  test_deposit_user1();
  _sendRewards();

  vm.startPrank(user1);

  // First cooldown attempt
  uint256 totalBalance = stakingLpEth.balanceOf(user1);
  uint256 halfBalance = totalBalance / 2;
  stakingLpEth.cooldownShares(halfBalance);

  // Wait 6 days
  vm.warp(block.timestamp + 6 days);

  // Second cooldown attempt for the remaining balance
  stakingLpEth.cooldownShares(halfBalance);

  // Try to unstake after 7 days from the first attempt
  vm.warp(block.timestamp + 1 days);
  vm.expectRevert(StakingLPEth.InvalidCooldown.selector);
  stakingLpEth.unstake(user1);

  // Wait another 6 days (13 days total from the first attempt)
  vm.warp(block.timestamp + 6 days);
  stakingLpEth.unstake(user1);

  // Check that the user received their funds
  assertApproxEqAbs(liquidityPool.balanceOf(user1), 0.199999999999999999 ether, 1);

  vm.stopPrank();
}

```

This test demonstrates the following scenario:

1. User1 deposits funds and receives rewards.
2. User1 initiates a cooldown for half of their balance.
3. After 6 days, User1 initiates another cooldown for the remaining half.
4. The test attempts to unstake after 7 days from the first cooldown, which fails because the second cooldown reset the cooldown period.
5. The test waits for another 6 days (13 days total from the first cooldown attempt) and successfully unstakes.

This test proves that multiple cooldown attempts reset the cooldown period for all assets, effectively locking users out of their funds for longer than the intended cooldown duration. In this case, the user had to wait 13 days instead of the intended 7 days to access their full balance.

Use the following command to run the POC:

```
forge test --match-test test_multiple_cooldown_attempts_reset_cooldown -vv
```

This test demonstrates the unfair locking of assets and the potential DOS vulnerability in the current implementation of the cooldown mechanism, would be key to note that in real life scenario the [`COOLDOWN_DURATION` is allowed to be as long as 30 days](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L34) and users could want to even request more withdrawals within that time frame forcing them to encounter even longer DOS.

## Impact

Users are essentially DOS'd from their assets if they decide to make any consequent withdrawals which should not be the case, considering the [`MAX_COOLDOWN_DURATION` is 30 days](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L34), this means a user could be [unfairly locked off from their assets for an extra 30 days](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L92) if they only decide to do one consequent withdrawal.

If they don't notice that this is the bug case it could even go for longer since they might try multiple consequent withdrawals over weeks, essentially locking their assets for even longer in the protocol.

> NB: The value of [`cooldownDuration` is initialized as 30 days/MAX_COOLDOWN_DURATION in the constructor](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L60).

## Recommended Mitigation Steps

Consider having a case by case attempt for each withdrawal request.

This way once a specific withdrawal's request end time passes that withdrawal can be withdrawn and user passing in a new request does not push the previous one farther

Pseudo fix:
