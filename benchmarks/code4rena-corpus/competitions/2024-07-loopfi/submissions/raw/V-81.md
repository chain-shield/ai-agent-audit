# Vulnerability details

## Impact
The mistakes of the deployer of `Flashlender.sol` aren't validated leading to scenarios where `protocolFee` might be set to 0 or an arbitrary large number.

## Proof of Concept
https://github.com/code-423n4/2024-07-loopfi/blob/main/src/Flashlender.sol#L26
https://github.com/code-423n4/2024-07-loopfi/blob/main/src/Flashlender.sol#L53

`protocolFee` in `Flashlender.sol` is an immutable variable meaning that it can be set inside the constructor but cannot be modified afterwards. Once set, it is used to calculate the amount that the flashloan receiver will have to pay back, i.e

```
uint256 fee = wmul(amount, protocolFee);
uint256 total = amount + fee;
```

If `protocolFee` was mistakenly set to 0 in the constructor, `fee` will also be 0 cause `wmul` will just be
`(amount * 0) / WAD`
leading to a situation where the fee to be paid back by the flashloan receiver is 0.

There will be no way to rectify this cause `protocolFee` is an immutable variable.

Also when `protocolFee` is mistakenly set to a very high number, say `1_000_000`, the fees to be paid back by the flashloan receiver will also be very high disincentivizing taking flashloans from the protocol reducing revenue collected by LoopFi through protocol fees charged when taking flashloans.

## Note
I do acknowledge that the deployer of `Flashlender.sol` is trusted. For that matter, the severity and even eligibility of this issue is debatable. But, in the case where a mistake happens, i.e `protocolFee` is set to 0 or very large number, the effects will be catastrophic.



## Tools Used
VS Code, manual review

## Recommended Mitigation Steps

1. Include a check in the constructor to bound `protocolFee` in between a range, say 0 to 100.
2. Don't make `protocolFee` an immutable variable and include a protected function that can be used to change `protocolFee` to a sensible value when mistakes happen.
