# Vulnerability details

## Vulnerability Detail
The `join` function in `PoolAction.sol` is marked as payable, allowing it to receive ETH. However, the handling of this ETH is inconsistent across different protocols:

- For Pendle joins, the ETH is forwarded to the Pendle Router.
- For Balancer joins, there's no mechanism to handle or forward the received ETH.
This inconsistency creates a scenario where ETH sent with Balancer join operations could become locked in the contract, as there's no mechanism to use or return it.
## Impact
- Permanent loss of user funds: ETH sent with Balancer join operations will be locked in the contract with no way to recover it.
- User confusion: The inconsistent behavior between protocols can lead to users mistakenly sending ETH when it's not needed or expected.

## Proof of Concept
```
// In PoolAction.sol
function join(PoolActionParams memory poolActionParams) public payable {
    if (poolActionParams.protocol == Protocol.BALANCER) {
        _balancerJoin(poolActionParams);
    } else if(poolActionParams.protocol == Protocol.PENDLE) {
        _pendleJoin(poolActionParams);
    } else {
        revert PoolAction__join_unsupportedProtocol();
    }
}

function _balancerJoin(PoolActionParams memory poolActionParams) internal {
    // No handling of msg.value
    // ...
}

function _pendleJoin(PoolActionParams memory poolActionParams) internal {
    // ...
    pendleRouter.addLiquiditySingleToken{value: msg.value}(poolActionParams.recipient, market, poolActionParams.minOut, guessPtReceivedFromSy, input, limit);
}
```
In this implementation, if a user sends ETH with a Balancer join operation, that ETH will be transferred to the contract but never used or returned, effectively becoming locked.
## Tools Used
Manual code review
## Recommended Mitigation Steps
- Create separate functions for joining Balancer and Pendle pools
- Add a refund mechanism for any unused ETH
