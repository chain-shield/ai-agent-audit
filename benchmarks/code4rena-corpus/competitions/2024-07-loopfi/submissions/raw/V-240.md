# Vulnerability details

In the PoolV3, the `_withdraw()` function incorrectly updates the available liquidity, potentially leading to a liquidity underflow. This issue arises from the `_updateBaseInterest()` function call within `_withdraw()`, where the `availableLiquidityDelta` parameter is passed as the negative of `assetsSent`.

The problemat is located in [PoolV3.sol#L412-L416](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L412-L416)
```solidity
    // The _updateBaseInterest() function call is affected, potentially leading to liquidity underflow
    _updateBaseInterest({
        expectedLiquidityDelta: -assetsSent.toInt256(),
        availableLiquidityDelta: -assetsSent.toInt256(),
        checkOptimalBorrowing: false
    }); // U:[LP-8,9]

    IERC20(underlyingToken).safeTransfer({to: receiver, value: amountToUser}); // U:[LP-8,9]
    if (assetsSent > amountToUser) {
        unchecked {
            IERC20(underlyingToken).safeTransfer({to: treasury, value: assetsSent - amountToUser}); // U:[LP-8,9]
        }
    }
```
Although the intention is to subtract `assetsSent` from the available liquidity, the resulting `availableLiquidity` after the update becomes a large number, indicating an underflow or incorrect calculation within `_updateBaseInterest()`.

## Impact
Even if the underflow does not directly enable fund drainage, having an incorrect available liquidity value can disrupt the pool's internal accounting and lead to unexpected behavior in other functions that rely on accurate liquidity information.

   - In the worst case, if the availableLiquidity underflows and becomes an extremely large number, it could allow users to withdraw more assets than the pool actually holds, effectively draining the pool's funds.

## Proof of Concept
Consider the following scenario:

1. The pool has an initial available liquidity of 0.
2. A user calls the `withdraw()` function with `assetsSent = 1` and `amountToUser = 1`.
3. Inside `withdraw()`, the `_withdraw()` function is called with the same parameters.
4. In `_withdraw()`, the `_updateBaseInterest()` function is called with `availableLiquidityDelta = -1`.
5. After the update, the `availableLiquidity` becomes an extremely large number (e.g., `115792089237316195423570985008687907853269984665640564039457584007913129639935`), indicating an underflow.

At this point, the pool's available liquidity is incorrectly set to a very high value, potentially allowing users to withdraw more assets than the pool actually holds.

The `_updateBaseInterest()` is called in multiple places, not just in the `_withdraw()` function.

## Recommended Mitigation Steps
check within `_updateBaseInterest()` to ensure that the resulting `availableLiquidity` does not underflow:
```diff
function _updateBaseInterest(int256 expectedLiquidityDelta, int256 availableLiquidityDelta, bool checkOptimalBorrowing) internal {
    // ...
    availableLiquidity += availableLiquidityDelta;
+   require(availableLiquidity >= 0, "Available liquidity underflow");
    // ...
+   assert(availableLiquidity <= totalAssets());
}
```
