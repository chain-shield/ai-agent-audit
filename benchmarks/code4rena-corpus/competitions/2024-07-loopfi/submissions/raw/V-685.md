# Vulnerability details

## Title
AuraVault is vulnerable to donation attack.

## Impact

The Initial deposit on AuraVault can be front-runned by malicious users to inflate share price then all users after the first (the attacker) will receive no shares in return for their deposit. The root cause of the issues arises in the function `AuraVault::totalAssets()` where the `totalAssets` is calculated like this:

```solidity
    function totalAssets() public view virtual override(IERC4626, ERC4626) returns (uint256) {
        return IPool(rewardPool).balanceOf(address(this));
    }

``` 
A malicious user can inflate the `balanceOf(address(this)` and manipulate the share accounting by donating a small amount to the vault.

The attack vector is same as explained in the [blog](https://mixbytes.io/blog/overview-of-the-inflation-attack). 

The malicious user can mint a very small number of shares, then donate assets to the Vault. 

Thereby he manipulates the exchange rate and later depositors lose funds due to rounding down in the number of shares they receive.

Then attacker can burn shares to withdraw assets.

Here, the exploit path is exactly the same, only the donate step is different. In the regular exploit, the user can just transfer the asset in but the user needs to call this function below to complete the donation step.

https://etherscan.io/address/0x032b676d5d55e8ecbae88ebee0aa10fb5f72f6cb#code#F18#L196
```solidity
    function stakeFor(address _for, uint256 _amount)
        public
        returns(bool)
    {
        _processStake(_amount, _for);

        //take away from sender
        stakingToken.safeTransferFrom(msg.sender, address(this), _amount);
        emit Staked(_for, _amount);
        
        return true;
    }
```

## Proof of Concept
The function [AuraVault::totalAssets()](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/vendor/AuraVault.sol#L175) is used to calculate the `totalAssets`

```solidity
    function totalAssets() public view virtual override(IERC4626, ERC4626) returns (uint256) {
        return IPool(rewardPool).balanceOf(address(this));
    }

``` 
The amount if totalAssets is used in two function [_convertToShares()](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/vendor/AuraVault.sol#L182) and [_convertToAssets()](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/vendor/AuraVault.sol#L189)

```solidity
    function _convertToShares(uint256 assets, Math.Rounding rounding) internal view virtual override returns (uint256) {
        return assets.mulDiv(totalSupply() + 10 ** _decimalsOffset(), totalAssets() + 1, rounding);
    }

    /**
     * @dev Internal conversion function (from shares to assets) with support for rounding direction.
     */
    function _convertToAssets(uint256 shares, Math.Rounding rounding) internal view virtual override returns (uint256) {
        return shares.mulDiv(totalAssets() + 1, totalSupply() + 10 ** _decimalsOffset(), rounding);
    }
```
From the above two function we can see that the `totalAssets()` plays a crucial role to calculation the shares and assets. These two functions are being used in the minting/withdrawing of the AuraVault. 

## Tools Used
Manual Review

## Recommended Mitigation Steps
This issue can be mitigated by requiring a minimum deposit of assets or mint a share to deadline address first and track total asset using internal variable. 

Thereby the attacker cannot manipulate the exchange rate to be so low as to enable this attack.
