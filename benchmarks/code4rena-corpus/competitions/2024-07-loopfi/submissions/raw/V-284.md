# Vulnerability details

## Description

The `ChefIncentivesController` contract implements a reward distribution system that supports both fixed and scheduled emission rates. The contract uses a [`rewardsPerSecond` variable](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/ChefIncentivesController.sol#L42) to determine the rate at which rewards are distributed. This rate can be updated dynamically based on an emission schedule, which is implemented in the [`setScheduledRewardsPerSecond()` function](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/ChefIncentivesController.sol#L352-L368) and called via [`_updateEmissions()`](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/ChefIncentivesController.sol#L439-L447).

The core issue lies in the fact that `_updateEmissions()` is only called in the `addPool()` and `claim()` functions, but not in `_handleActionAfterForToken()` or `afterLockUpdate()`. These latter two functions are responsible for updating user balances and rewards, and they rely on the `_updatePool()` function, which uses the current `rewardsPerSecond` value.

As a result, when users interact with the contract through functions that trigger `_handleActionAfterForToken()` or `afterLockUpdate()`, the `rewardsPerSecond` value may not reflect the current scheduled rate. This can lead to incorrect reward calculations and distributions, potentially favoring some users over others depending on when they interact with the contract.

For example, in the `_handleActionAfterForToken()` function:

```solidity
function _handleActionAfterForToken(
    address _token,
    address _user,
    uint256 _balance,
    uint256 _totalSupply
) internal {
    VaultInfo storage pool = vaultInfo[_token];
    if (pool.lastRewardTime == 0) revert UnknownPool();
    // _updateEmissions() is not called here, potentially using outdated rewardsPerSecond
    _updatePool(pool, totalAllocPoint);
    // ... rest of the function
}
```

The `_updatePool()` function is called without first updating the `rewardsPerSecond`, which could lead to incorrect reward calculations.

## Impact
The impact of this issue is significant as it affects the fairness and accuracy of the reward distribution system. Users interacting with the contract between `addPool()` or `claim()` calls may receive incorrect rewards based on outdated emission rates. This could lead to some users receiving more rewards than they should, while others receive less.

The severity of the impact depends on how frequently the emission schedule changes and how often users interact with the contract. In a worst-case scenario, if the emission schedule decreases the reward rate significantly, users interacting with the contract before a `claim()` or `addPool()` call could receive substantially more rewards than intended, depleting the reward pool faster than planned and shortchanging later participants.

## Proof of Concept
1. The contract owner sets an emission schedule that decreases the `rewardsPerSecond` over time.
2. User A interacts with the contract, triggering `_handleActionAfterForToken()`.
3. The `rewardsPerSecond` is not updated, and rewards are calculated using the old, higher rate.
4. User A receives more rewards than they should under the current schedule.
5. Later, User B calls `claim()`, which updates the `rewardsPerSecond`.
6. User B and subsequent users receive fewer rewards due to the pool being depleted faster than intended.

## Recommended Mitigation Steps
To address this issue, the `_updateEmissions()` function should be called in both `_handleActionAfterForToken()` and `afterLockUpdate()` before updating the pool or user balances. This ensures that the most current `rewardsPerSecond` value is used for all reward calculations.

Here's the recommended fix for `_handleActionAfterForToken()`:

```diff
function _handleActionAfterForToken(
    address _token,
    address _user,
    uint256 _balance,
    uint256 _totalSupply
) internal {
    VaultInfo storage pool = vaultInfo[_token];
    if (pool.lastRewardTime == 0) revert UnknownPool();
+   _updateEmissions();  // Ensure rewardsPerSecond is up to date
    _updatePool(pool, totalAllocPoint);
    // ... rest of the function
}
```

And for `afterLockUpdate()`:

```diff
function afterLockUpdate(address _user) external {
    if (eligibilityMode != EligibilityModes.DISABLED) {
        if (msg.sender != address(mfd)) revert NotMFD();
        bool isCurrentlyEligible = eligibleDataProvider.refresh(_user);
        if (isCurrentlyEligible) {
+           _updateEmissions();  // Ensure rewardsPerSecond is up to date
            _updateRegisteredBalance(_user);
        } else {
            _processEligibility(_user, isCurrentlyEligible, true);
        }
    }
}
```

By implementing these changes, the contract will ensure that the most up-to-date `rewardsPerSecond` value is used for all reward calculations, maintaining fairness and accuracy in the reward distribution system.
