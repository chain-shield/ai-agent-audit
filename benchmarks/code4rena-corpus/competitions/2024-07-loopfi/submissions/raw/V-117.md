# Vulnerability details

## Impact
Incorrect reward updates for scheduled emissions may lead to incorrect reward emissions until there is a new pool added or a claim is triggered.

## Proof of Concept
The `ChefIncentivesController` contract supports two methods of distributing rewards, that is:

1. the protocol can either set a fixed value for `rewardsPerSecond` as seen in function `initialize` [here](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/reward/ChefIncentivesController.sol#L234-L259) i.e 

    `rewardsPerSecond = _rewardsPerSecond;`

2. or change the `rewardsPerSecond` value according to an emission schedule as seen [here](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/reward/ChefIncentivesController.sol#L342-L347).

Usage of emission schedules requires a frequent check on the current rewards per second value against the schedule to determine when emissions should be adjusted. This logic is implemented in the `setScheduledRewardsPerSecond` function as:

```solidity
function setScheduledRewardsPerSecond() internal {
        if (!persistRewardsPerSecond) {
            uint256 length = emissionSchedule.length;
            uint256 i = emissionScheduleIndex;
            uint128 offset = uint128(block.timestamp - startTime);
            for (; i < length && offset >= emissionSchedule[i].startTimeOffset; ) {
                unchecked {
                    i++;
                }
            }
            if (i > emissionScheduleIndex) {
                emissionScheduleIndex = i;
                _massUpdatePools();
                rewardsPerSecond = uint256(emissionSchedule[i - 1].rewardsPerSecond);
            }
        }
    }
```

that is triggered by the internal `_updateEmissions` function as 
```solidity
    function _updateEmissions() internal {
        if (block.timestamp > endRewardTime()) {
            _massUpdatePools();
            lastRPS = rewardsPerSecond;
            rewardsPerSecond = 0;
            return;
        }
        setScheduledRewardsPerSecond();
    }
```

However, the `_updateEmissions` function is only used by function `addPool` as seen [here](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/reward/ChefIncentivesController.sol#L301-L311) and function `claim`, also as seen [here](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/reward/ChefIncentivesController.sol#L518-L550) - but, it is not used in function `_handleActionAfterForToken` as seen [here](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/reward/ChefIncentivesController.sol#L627-L654) or in function `afterLockUpdate` as seen [here](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/reward/ChefIncentivesController.sol#L674-L684).

The latter two functions(`_handleActionAfterForToken` and `afterLockUpdate`) both call the `_updatePool` function in order to update pool rewards using the `rewardsPerSecond` value, but do not support emission schedule updates, which may lead to incorrect reward emissions until there is a new pool added or a claim is triggered.


## Tools Used
Manual review

## Recommended Mitigation Steps
Call `_updateEmissions` whenever rewards need to be recalculated, to ensure that the `rewardsPerSecond` value tracks the current scheduled emission rate as closely as possible.
