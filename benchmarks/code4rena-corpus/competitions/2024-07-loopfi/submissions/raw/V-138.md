# Vulnerability details

## Impact
Potential malicious depletion of receiver's token balance through excessive fees.

## Proof of Concept
The `flashLoan` function lacks a check on the approval amount. If the approval amount is excessively large and there are leftover funds in the receiver contract, any address can exploit the `flashLoan` function to drain the remaining funds through fees.

Consider the following scenario:

1. Alice acquires a large amount of tokens, either through a flash loan or by purchasing them.
2. Alice temporarily stores these tokens in the receiver contract.
3. A malicious actor discovers this situation and exploits the `flashLoan` function to drain the leftover tokens from the receiver contract through fees. The attacker only needs to pay minimal gas fees to significantly deplete the token balance in the receiver contract.
4. As a result, Alice suffers substantial token losses.

## Recommended Mitigation Steps
1. Implement a check to ensure the approval amount is within reasonable limits.
2. Prevent unlimited approvals by setting a maximum allowable approval amount.
3. After each flash loan is completed, reduce the approved amount accordingly. This can be implemented similarly to the following function:
```
    function _spendAllowance(address owner, address spender, uint256 value) internal virtual {
        uint256 currentAllowance = allowance(owner, spender);
        if (currentAllowance != type(uint256).max) {
            if (currentAllowance < value) {
                revert ERC20InsufficientAllowance(spender, currentAllowance, value);
            }
            unchecked {
                _approve(owner, spender, currentAllowance - value, false);
            }
        }
    }
```
