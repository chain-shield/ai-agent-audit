# Vulnerability details

## Impact
The vulnerability in accountedRewards could result in inaccurate tracking of distributed rewards. This may lead the contract to distribute more rewards than are actually available, potentially exhausting the reward pool prematurely.
## Proof of Concept
### `_newRewards` Fucntion
```
// Example of the flaw in the _newRewards function:
function _newRewards(
    VaultInfo memory pool,
    uint256 _totalAllocPoint
) internal view returns (uint256 newReward, uint256 newAccRewardPerShare) {
    uint256 lpSupply = pool.totalSupply;
    if (lpSupply > 0) {
        uint256 duration = block.timestamp - pool.lastRewardTime;
        uint256 rawReward = duration * rewardsPerSecond;

        uint256 rewards = availableRewards();
        if (rewards < rawReward) {
            rawReward = rewards; // Potential for incorrect reward adjustment
        }
        newReward = (rawReward * pool.allocPoint) / _totalAllocPoint;
        newAccRewardPerShare = (newReward * ACC_REWARD_PRECISION) / lpSupply;
    }
}
```
A scenario where the calculation of newReward is incorrect due to external factors.
### accountrewards Function snippet
```
 (uint256 reward, uint256 newAccRewardPerShare) = _newRewards(pool, _totalAllocPoint);
accountedRewards = accountedRewards + reward;
```
- Trigger a reward distribution event. The incorrect value of accountedRewards will lead to:
- Over-distribution, depleting the reward pool faster than intended.

## Recommended Mitigation Steps
To mitigate this, ensure the reward calculations are correctly validated, especially when adding to accountedRewards. Introduce safeguards that verify reward calculations against expected values or available funds.

- Implement sanity checks before incrementing accountedRewards.
- Consider resetting or auditing accountedRewards periodically to ensure it 
  reflects the correct amount of distributed rewards.
