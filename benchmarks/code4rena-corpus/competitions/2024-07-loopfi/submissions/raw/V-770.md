# Vulnerability details

## Impact
Contracts such as `PositionAction.sol` and `SwapAction.sol` contains functions that has a call to the function `_transferFrom` which grants users allowance to deposit and transfer their tokens. However the permit functionality can be front run causing it to DoS the users deposits.

## Proof of Concept
The permit functionality validates that the provided signature matches the signer of the message, but it does not validate the executor of the permit. But when the permit call is a part of a larger call chain, front running the permit call directly can force the honest users transaction to be reverted, since calling permit on a used signature will obviously fail.

Consider the following example:
- Alice calls the `transferAndSwap` function which calls the `_transferFrom` function with the required inputs.
- Bob sees the transaction in the mempool and calls with premit2 directly to the contract and use the signature.
- This will cause the transaction to revert.

For more explanation : https://www.trust-security.xyz/post/permission-denied

## Recommended Mitigation Steps
Add a try/catch block, to prevent already granted permissions from reverting the entire call-chain as recommended in the article linked above.
