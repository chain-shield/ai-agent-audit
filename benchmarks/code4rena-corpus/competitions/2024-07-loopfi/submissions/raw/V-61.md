# Vulnerability details

## Impact
The functions `_convertToShares` and `_convertToAssets` do not account for the current status of the pool, instead converting assets and shares on a one-to-one basis. When a lender deposits WETH, they receive an equivalent number of shares. However, even after the pool accrues additional WETH from borrowers, the lender can only withdraw the initial amount of WETH they deposited, missing out on expected profits. [1](https://code4rena.com/audits/2024-07-loopfi)

This issue doesn't just affect individual users; it has broader implications. The one-to-one conversion also impacts CDPVaults and other credit managers utilizing the conversion functions. It affects all accounting within the pool, leading to potential discrepancies across the system.

## Proof of Concept
The POC is based on other unit tests and the full code is at the bottom.

In this POC we have three accounts, `liquidityPool`, `lender` and `borrower`:
- The `liquidityPool` has an initial balance of 1_000_000 mockWETH
- The `borrower` has an initial balance of 1_000_000 mockWETH and represents different users
- The `lender` has an initial balance of 100_000 mockWETH

First the example lender deposits his mockWETH into the liquidityPool. The pool sends him 100_000 shares for his mockWETH:
```
mockWETH.approve(address(liquidityPool), lenderAmount);
liquidityPool.deposit(lenderAmount, lender);
```


Afterwards different users create their positions in the `CDPVault`. They are represented by a single big example user:
```
token.approve(address(vault), usersAmount);
uint256 usersInitalDebt = (usersAmount * 5) / 10;
vault.modifyCollateralAndDebt(borrower, borrower, borrower, toInt256(usersAmount), toInt256(usersInitalDebt));
```

Next we warp ahead one year. The user tops up on mockWETH, repays his debt and exits his position. After one year he has a debt of ~600_000 tokens:
```
uint256 usersVirtualDebt = vault.virtualDebt(borrower);
assertGt(usersVirtualDebt, usersInitalDebt, "wrong intrest");
mockWETH.balanceOf(borrower);
StdCheats.deal(address(mockWETH), borrower, usersVirtualDebt);
vm.startPrank(borrower);
mockWETH.approve(address(vault), usersVirtualDebt);
vault.modifyCollateralAndDebt(borrower, borrower, borrower, -toInt256(usersAmount), -toInt256(usersVirtualDebt));
```

Finally the lender redeem his shares to get back his mockWETH. He still has 100_000 shares and redeems them all:
```
uint256 maxRedeemLender = liquidityPool.maxRedeem(lender);
liquidityPool.redeem(maxRedeemLender, lender, lender);
```
The pool burns his shares and returns 100_000 mockWETH, the same as his initial balance. The POC produces the following logs:
- lenderTokensBefore:  100_000
- poolTokensBefore:  1_000_000
- usersVirtualDebt:  603_975.94
- lenderTokensAfter:  100_000
- poolTokensAfter:  1_103_975.94
- lenderTokensDelta:  0
- poolTokensDelta:  103_975.94

The pool collected over 100k mockWETH, while the user did not earn any LP fees.

        uint256 poolTokensAfter = mockWETH.balanceOf(address(liquidityPool));

        // log change
        console.log("lenderTokensDelta: ", lenderTokensAfter - lenderTokensBefore);
        console.log("poolTokensDelta: ", poolTokensAfter - poolTokensBefore);

## Recommended Mitigation Steps
The existing contract already has some code [2](https://github.com/code-423n4/2024-07-loopfi/blob/1b32965bc1ce36b885df687069880140073c6285/src/PoolV3.sol#L427-L439) to accommodate users earning fees:
```
function _convertToShares(uint256 assets, Math.Rounding rounding) internal pure returns (uint256 shares) {
    uint256 supply = totalSupply();
    return (assets == 0 || supply == 0) ? assets : assets.mulDiv(supply, totalAssets(), rounding);
}
```
And also:
```
function _convertToAssets(uint256 shares, Math.Rounding rounding) internal pure returns (uint256 assets) {
    uint256 supply = totalSupply();
    return (supply == 0) ? shares : shares.mulDiv(totalAssets(), supply, rounding);
}
```

Reverting those changes mitigates the described bug. The `mulDiv` is important to convert the shares and assets based on the `totalSupply` and the `totalAssets`. The `totalAssets` function [3](https://github.com/code-423n4/2024-07-loopfi/blob/1b32965bc1ce36b885df687069880140073c6285/src/PoolV3.sol#L221-L225) respects the accumulated fees and makes sure that the conversion is fair for each participant.

Here are the logs of the same POC:
- lenderTokensBefore:  100_000
- poolTokensBefore:  1_000_000
- usersVirtualDebt:  603_975.94
- lenderTokensAfter:  100_751.42
- poolTokensAfter:  1_103_224.52
- lenderTokensDelta:  751.42
- poolTokensDelta:  103_224.52

With the changes the lender now gets a share of the earnings based on his shares.

Besides updating the `_convertToShares` and `_convertToAssets` functions, one also has to add the necessary rounding direction. A full diff can be seen below.
