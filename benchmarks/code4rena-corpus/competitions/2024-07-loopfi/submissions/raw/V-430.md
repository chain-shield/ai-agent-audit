# Vulnerability details


## Proof of Concept

Take a look at https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/proxy/PositionAction.sol#L338-L371

```solidity
function decreaseLever(
  LeverParams calldata leverParams,
  uint256 subCollateral,
  address residualRecipient
) external onlyDelegatecall {
  if (
    leverParams.primarySwap.swapType != SwapType.EXACT_OUT ||
    leverParams.primarySwap.recipient != self
  ) revert PositionAction__decreaseLever_invalidPrimarySwap();
  if (
    leverParams.auxSwap.assetIn != address(0) && (leverParams.auxSwap.swapType != SwapType.EXACT_IN)
  ) revert PositionAction__decreaseLever_invalidAuxSwap(); //@audit
  if (leverParams.auxSwap.assetIn == address(0) && residualRecipient == address(0))
    revert PositionAction__decreaseLever_invalidResidualRecipient();
  IPermission(leverParams.vault).modifyPermission(leverParams.position, self, true);
  uint256 loanAmount = leverParams.primarySwap.amount;
  flashlender.creditFlashLoan(
    ICreditFlashBorrower(self),
    loanAmount,
    abi.encode(leverParams, subCollateral, residualRecipient)
  );
  IPermission(leverParams.vault).modifyPermission(leverParams.position, self, false);
}

```

This function is used to decrease the leverage of a position by taking out a credit flash loan to withdraw and sell collateral, problem however is the fact that when an aux swap exists, the function checks if the `auxSwap.swapType` is `EXACT_IN`, this is wrong however and should only be used in `increaseLever()` [as is correctly done](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/proxy/PositionAction.sol#L313).

## Impact

The current implementation creates a logical inconsistency in the contract. The `decreaseLever` function is meant to reduce the leverage of a position by selling collateral, which naturally aligns with an `EXACT_OUT` swap type. However, the function is checking for `EXACT_IN`, which is more appropriate for buying collateral (as seen in the `increaseLever` function). This then means that the execution would [revert](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/proxy/PositionAction.sol#L356) _valid_ decrease lever operations that use `EXACT_OUT` swaps,..

## Recommended Mitigation Steps

Modify the `decreaseLever` function to expect an `EXACT_OUT` swap type for the aux swap:

```diff

        LeverParams calldata leverParams,

        address residualRecipient

-        if (leverParams.auxSwap.assetIn != address(0) && (leverParams.auxSwap.swapType != SwapType.EXACT_IN))
+        if (leverParams.auxSwap.assetIn != address(0) && (leverParams.auxSwap.swapType != SwapType.EXACT_OUT))
            revert PositionAction__decreaseLever_invalidAuxSwap();
        if (leverParams.auxSwap.assetIn == address(0) && residualRecipient == address(0))
            revert PositionAction__decreaseLever_invalidResidualRecipient();
        IPermission(leverParams.vault).modifyPermission(leverParams.position, self, true);
        uint loanAmount = leverParams.primarySwap.amount;
        flashlender.creditFlashLoan(
            ICreditFlashBorrower(self),
            loanAmount,
            abi.encode(leverParams, subCollateral, residualRecipient)
        );
        IPermission(leverParams.vault).modifyPermission(leverParams.position, self, false);
    }
```

Additionally, update the documentation and any related interfaces to reflect this change. Ensure that the `onCreditFlashLoan` callback function and any other parts of the contract that interact with the `decreaseLever` function are adjusted to handle the `EXACT_OUT` swap type correctly.

This change will make the `decreaseLever` function consistent with its purpose and the overall design of the leverage management system in the contract.
