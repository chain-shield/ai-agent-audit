# Vulnerability details

## Proof of Concept
In the `setScheduledRewardsPerSecond` function, there is a potential issue in the loop that iterates over the `emissionSchedule`. The loop's condition depends on the value of `offset`, which is calculated as follows:
```solidity
uint128 offset = uint128(block.timestamp - startTime);
```
And:
```solidity
  function start() public onlyOwner {
        if (startTime != 0) revert AlreadyStarted();
        startTime = block.timestamp;
    }
```
This `offset` represents the time elapsed since the `startTime` of the rewards schedule. The loop is designed to increment the index `i` as long as the following condition is true:
```solidity
for (; i < length && offset >= emissionSchedule[i].startTimeOffset; ) {
    unchecked {
        i++;
    }
}
```
However, if `offset` is zero (which is possible immediately after the start function is called), the loop will only increment `i` if `emissionSchedule[i].startTimeOffset` is also zero. If the first element of `emissionSchedule` has a `startTimeOffset` greater than zero, the loop will not execute even once, leaving `i` unchanged.

The `setScheduledRewardsPerSecond` function is intended to adjust the rewards per second according to a predefined schedule (`emissionSchedule`). The loop is supposed to iterate through the `emissionSchedule` and apply the relevant rewards rate depending on the elapsed time (`offset`). The incorrect behavior of this loop could lead to an improper application of the rewards schedule.

Example Scenario:

- Suppose the `emissionSchedule` is designed to adjust the rewards after specific intervals.
- If the `offset` is zero, and the first element in `emissionSchedule` has a `startTimeOffset` greater than zero, the loop does not increment `i`. As a result, the subsequent code may fail to apply the correct rewards adjustment.

## Impact
The primary impact is that the rewards schedule may not update correctly, leading to an inaccurate calculation of `rewardsPerSecond`. Since [_updateEmissions](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/ChefIncentivesController.sol#L439-L447) is responsible for setting the correct reward rate based on the current timestamp, a failure here means that participants may receive incorrect reward amounts when they call claim.
If the loop fails to execute as intended, it could result in the contract not updating the rewards schedule correctly. This could lead to incorrect rewards distribution, where the intended adjustment to the rewards per second is not applied, potentially affecting the fairness and accuracy of rewards distribution to participants.

## Recommended Mitigation Steps
Ensure that the loop's condition properly accounts for the case where `offset` is zero. One approach is to initialize `i` based on the first element of `emissionSchedule` that satisfies the condition:
```solidity
while (i < length && offset >= emissionSchedule[i].startTimeOffset) {
    unchecked {
        i++;
    }
}

if (i == 0 && offset == 0) {
    // Handle the case where the offset is zero and ensure at least one iteration
    i = 1;
}
```
