# Vulnerability details

## Description
When liquidating a position, at CDPVault's liquidatePosition function, the position is checked to see if it doesn't have bad debt, if the amount taken as collateral is not bigger than its total collateral and if the position is indeed undercollateralized, as can be seen in the following code snippet:
```solidity
function liquidatePosition(address owner, uint256 repayAmount) external whenNotPaused {
...
if (calcTotalDebt(debtData) > wmul(position.collateral, spotPrice_)) revert CDPVault__BadDebt();
...
if (takeCollateral > position.collateral) revert CDPVault__tooHighRepayAmount();
if (_isCollateralized(calcTotalDebt(debtData), wmul(position.collateral, spotPrice_), config.liquidationRatio))
            revert CDPVault__liquidatePosition_notUnsafe();
...
```

Then the position is liquidated, the pool receives the collateral repayment from the liquidator and repays the credit account.

After the position is modified, by calling `_modifyPosition`, there is no sanity check ensuring the position is now collateralized nor a state change ensuring the position cannot be liquidated again. `_modifyPosition` doesn't do such a thing either.

While this is a nice-to-have feature, as allows partial liquidations, a liquidation may put a position even more under water depending on how the CDPVault is parameterized.

### In-depth
Lets use the config.js file as an example of parameters. 
The discount price is 0.98 and liquidation penalty is 0.99.

```solidity
function liquidatePosition(address owner, uint256 repayAmount) external whenNotPaused {
...
uint256 takeCollateral = wdiv(repayAmount, discountedPrice);
        
uint256 deltaDebt = wmul(repayAmount, liqConfig_.liquidationPenalty);
...
}
```

We apprehend takeCollateral= repayAmount / 0.98 and deltaDebt  = repayAmount * 0.99.

A loan's health is determined by the following function:
```solidity
function _isCollateralized(
        uint256 debt,
        uint256 collateralValue,
        uint256 liquidationRatio
    ) internal pure returns (bool) {
        return (wdiv(collateralValue, liquidationRatio) >= debt);
    }
```

If collateralValue * liquidationRation >= debt holds true, then the loan is healthy. 
As previously shown, liquidating a position removes more collateral then it does debt. Naturally the position will remain undercollateralized, therefore becoming subject to new liquidations, even if the amount that was owed is not as big as all those future liquidations.
## Impact
Loans that are liquidated become unhealthier and don't have any mechanism to prevent them from being liquidated multiple times.

## Recommended Mitigation Steps
There are many different ways protocols handle such cases:

Compound: [https://docs.compound.finance/liquidation/](https://docs.compound.finance/liquidation/) When an account’s borrow balance exceeds the limits set by liquidation collateral factors, it is eligible for liquidation. A liquidator (a bot, contract, or user) can call the absorb function, which relinquishes ownership of the accounts collateral, and returns the value of the collateral, minus a penalty (liquidationFactor), to the user in the base asset. The liquidated user has no remaining debt, and typically, will have an excess (interest earning) balance of the base asset.

Aave: [https://github.com/aave/aave-v3-core/blob/b74526a7bc67a3a117a1963fc871b3eb8cea8435/contracts/protocol/libraries/logic/LiquidationLogic.sol#L165C5-L177C6](https://github.com/aave/aave-v3-core/blob/b74526a7bc67a3a117a1963fc871b3eb8cea8435/contracts/protocol/libraries/logic/LiquidationLogic.sol#L165C5-L177C6) If the actual debt to liquidate is fulfilled, the contracts set borrowing for that asset as false and this protects the liquidated user from being liquidated again.

Both of these options could be implemented in the protocol as means to stop undercollateralized positions from paying more than owed due to liquidations worsening their loan health factor.
