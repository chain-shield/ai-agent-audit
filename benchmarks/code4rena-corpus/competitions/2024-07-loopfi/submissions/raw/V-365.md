# Vulnerability details

## Impact
The pool may issue more liquidity to the user than entitled to, diluting the value of tokens held by other participants.

## Proof of Concept
The primary purpose of this function is to update the parameters required to join the liquidity pool when a user is leveraging a flashloan in combination with their own upfront capital. This allows the user to provide more liquidity than they could with their capital.
```solidity
function updateLeverJoin(
        PoolActionParams memory poolActionParams,
        address joinToken,
        address upFrontToken,
        uint256 flashLoanAmount,
        uint256 upfrontAmount,
        address poolToken
    ) external pure returns (PoolActionParams memory outParams) {
        outParams = poolActionParams;

        if (poolActionParams.protocol == Protocol.BALANCER) {
            (bytes32 poolId, address[] memory assets, uint256[] memory assetsIn, uint256[] memory maxAmountsIn) = abi
                .decode(poolActionParams.args, (bytes32, address[], uint256[], uint256[]));

            uint256 len = assets.length;
            // the offset is needed because of the BPT token that needs to be skipped from the join
            bool skipIndex = false;
            uint256 joinAmount = flashLoanAmount;
            if (upFrontToken == joinToken) {
                joinAmount += upfrontAmount;
            }

            // update the join parameters with the new amounts
            for (uint256 i = 0; i < len; ) {
                uint256 assetIndex = i - (skipIndex ? 1 : 0);
                if (assets[i] == joinToken) {
                    maxAmountsIn[i] = joinAmount;
                    assetsIn[assetIndex] = joinAmount;
                } else if (assets[i] == upFrontToken && assets[i] != poolToken) {
                    maxAmountsIn[i] = upfrontAmount;
                    assetsIn[assetIndex] = upfrontAmount;
                } else {
                    skipIndex = skipIndex || assets[i] == poolToken;
                }
                unchecked {
                    i++;
                }
            }

            // update the join parameters
            outParams.args = abi.encode(poolId, assets, assetsIn, maxAmountsIn);
        }
    }
```

Specifically, the function fails to ensure that the total amount of tokens being added as liquidity(`joinAmount`) does not exceed the actual balance of the tokens of the user. This oversight can be exploited by an attacker to overstate the liquidity than they could with their capital.

In the `updateLeverJoin` function, user can leverage their position by combining a flash loan with their own capital(token contribution) to add liquidity to the Balancer Pool. When the `joinAmount` is the same as the `upFrontToken` the function sums these amounts into `joinAmounts`.

However, there is no mechanism in place to validate that the sum of [`flashAMount`]() and [`upfrontAMount`] does not exceed the user's.

- In the below given scenario:
A user can initiate a flashloan for a large amount of Token A(`frontAmount`), also contribute a small TokenA from her wallet(`upfrontAmount`) or no tokens
Since both `joinToken` and `upfrontToken` are tokens, the function combines these into `joinAMount`.

>The `updateleverJoin` assumes the user has sufficient tokens to cover this combined amount, without checking the actual balance.
The function updates and therefore the user can use this when Joining the Balancer pool, leading to overstated additional liquidity.

The pool becomes under-collateralized because the user only repays the flash loan but does not actually add the full `joinAMount` to the pool.

`JoinAmount` assumes it's fully backed by the user wallet and proceeds to allocate the amount to the pool, since `joinAMount` will be `maxAmountIn` the user can provide more liquidity to the pool without having enough balancer.

`updateLeverJoin` has the user left with the high privilege of Joining the pool without her having any actual balance.

The provision of liquidity to the pool is not for users who don't have enough upfront capital.

Also if you don't upfront amount or token the function will update allowing users to use this updated info while joining the pool which shouldn't be.

If a user, chooses to call the function without providing a valid `joinToken`, `upFrontToken`, or a `upfrontAmount`, the function could still proceed without reverting. This could result in an overestimation of the liquidity provided to the pool, as the function may assume more liquidity has been contributed than what was actually transferred.

## Tools Used
Manual Review

## Recommendation
Ensure that a valid and non-zero joinToken is provided. The function should check that `joinToken != address(0)` / `upfrontToken != address(0)` / `poolToken != address(0)` and that the token is one of the accepted tokens in the pool.

Introduce a check that enforces the provision of all the input parameters non-zero upfrontAmount when adding liquidity. If a upFrontToken is specified, the function should require that upfrontAmount > 0, the same as the others.
