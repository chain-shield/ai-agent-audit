# Vulnerability details

## Impact

In the `flashLoan` and `creditFlashLoan` functions, there is an external call to `receiver.onFlashLoan` and `receiver.onCreditFlashLoan` methods respectively. 

However, the return values of these functions are not being checked for correctness, resulting in potential issues if these functions do not complete as expected.

There is a check against the `CALLBACK_SUCCESS` and `CALLBACK_SUCCESS_CREDIT` constants but that's insufficient as the receiver's contract might contain an error and still return the correct constant.


## Proof of Concept

In the `flashLoan` and `creditFlashLoan` methods:

```solidity
if (receiver.onFlashLoan(msg.sender, token, amount, fee, data) != CALLBACK_SUCCESS)
    revert Flash__flashLoan_callbackFailed();

// and

if (receiver.onCreditFlashLoan(msg.sender, amount, fee, data) != CALLBACK_SUCCESS_CREDIT)
    revert Flash__creditFlashLoan_callbackFailed();
```

The contract just checks if constants match and not the full range of possible return values or potential reverts.

## Recommended Mitigation Steps

To prevent potential issues, it is advised to encapsulate calling external functions in `try` / `catch` blocks to check for failed external calls, and handle them appropriately. 

Doing this provides a way to recover from failures in external calls, or at least handle such failures in a graceful way. Without it, an unsuccessful external call could cause the whole transaction to fail. 

Moreover, I would also recommend to verify that borrowed token amounts are correctly returned before assuming the 'loan' operation was successful. Untracked amounts can cause vulnerabilities in token balances. 

In the case of `receiver.onFlashLoan` and `receiver.onCreditFlashLoan`, use `require` to check for the successful execution rather than relying solely on checking the returned flags.
