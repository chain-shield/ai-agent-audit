# Vulnerability details

## Proof of Concept
The `claim` function is designed to allow users to claim accumulated rewards by depositing a specified amount of `WETH` into a vault. The function ensures that the `amountIn` (computed as the required amount of `WETH` to be deposited) does not exceed the `maxAmountIn` parameter provided by the user, preventing excessive input. However, the function does not account for potential slippage during the token swaps or conversions, which can lead to unfavorable conditions for the user.

Here is the relevant portion of the `claim` function:
```solidity
    function claim(uint256[] memory amounts, uint256 maxAmountIn) external returns (uint256 amountIn) {
        // Claim rewards from Aura reward pool
        IPool(rewardPool).getReward();

        // Compute assets amount to be sent to the Vault
        VaultConfig memory _config = vaultConfig;
        amountIn = _previewReward(amounts[0], amounts[1], _config);

        // Transfer assets to Vault
        require(amountIn <= maxAmountIn, "!Slippage");
        IERC20(asset()).safeTransferFrom(msg.sender, address(this), amountIn);

        // Compound assets into "asset" balance
        IERC20(asset()).safeApprove(rewardPool, amountIn);
        IPool(rewardPool).deposit(amountIn, address(this));

        // Distribute BAL rewards
        IERC20(BAL).safeTransfer(_config.lockerRewards, (amounts[0] * _config.lockerIncentive) / INCENTIVE_BASIS);
        IERC20(BAL).safeTransfer(msg.sender, amounts[0]);

        // Distribute AURA rewards
        if (block.timestamp <= INFLATION_PROTECTION_TIME) {
            IERC20(AURA).safeTransfer(_config.lockerRewards, (amounts[1] * _config.lockerIncentive) / INCENTIVE_BASIS);
            IERC20(AURA).safeTransfer(msg.sender, amounts[1]);
        } else {
            // after INFLATION_PROTECTION_TIME
            IERC20(AURA).safeTransfer(_config.lockerRewards, IERC20(AURA).balanceOf(address(this)));
        }

        emit Claimed(msg.sender, amounts[0], amounts[1], amountIn);
    }
```
The `claim` function primarily checks that the `amountIn` does not exceed the `maxAmountIn`, ensuring that the user does not deposit more than they intended. However, the function does not implement a corresponding check for `minAmountOut`, which would ensure that the user receives a minimum amount of rewards (`BAL` and `AURA`) relative to the `amountIn`.

In a situation where slippage occurs during the internal swaps, the function might still succeed in transferring the expected amount of `WETH` to the vault (`amountIn`), but the user may end up receiving less `BAL` or `AURA` than anticipated due to the lack of `minAmountOut` verification. This can result in the user receiving a disproportionate amount of rewards relative to their deposit, potentially leading to a loss in value.
## Impact
A user could deposit an expected amount of `WETH` only to receive fewer rewards (`BAL` or `AURA`) than anticipated, which could lead to a significant loss in value due to slippage during the swaps. This discrepancy arises because the function does not verify that the output of the rewards meets a minimum expected threshold (`minAmountOut`), which would otherwise protect against adverse market conditions or price changes during the transaction.

Manual
## Recommended Mitigation Steps
The function should include a check for `minAmountOut` before completing the reward distribution. This ensures that the rewards claimed (`BAL` and `AURA`) meet a minimum threshold relative to the `amountIn`, thereby safeguarding users from receiving disproportionately low rewards due to slippage.
