# Vulnerability details

## Proof of Concept
In the `_updatePool` function, there is a significant issue related to the handling of user rewards and `rewardDebt`. This vulnerability arises from the fact that the function does not account for the `rewardDebt` when updating the pool's reward information.

Function Overview:
```solidity
function _updatePool(VaultInfo storage pool, uint256 _totalAllocPoint) internal {
    uint256 timestamp = block.timestamp;
    uint256 endReward = endRewardTime();
    if (endReward <= timestamp) {
        timestamp = endReward;
    }
    if (timestamp <= pool.lastRewardTime) {
        return;
    }

    (uint256 reward, uint256 newAccRewardPerShare) = _newRewards(pool, _totalAllocPoint);
    accountedRewards = accountedRewards + reward; // @audit consider the value of rewardDebt
    pool.accRewardPerShare = pool.accRewardPerShare + newAccRewardPerShare;
    pool.lastRewardTime = timestamp;
}

```
The `_updatePool` function is designed to update the pool's reward variables based on the time elapsed since the last update. The function calculates new rewards and updates the pool's `accRewardPerShare` and `lastRewardTime` accordingly. Here is how the reward is calculated:
```solidity
(uint256 reward, uint256 newAccRewardPerShare) = _newRewards(pool, _totalAllocPoint);
```
`reward` represents the total amount of rewards that should be distributed to the pool during the period since the last update.

```solidity
accountedRewards = accountedRewards + reward;
```
The `accountedRewards` variable is incremented by the newly calculated `reward`. This variable tracks the total rewards that have been accounted for, but it does not directly handle individual user rewards or their `rewardDebt`.

The `rewardDebt` is crucial for calculating how much reward a user has already earned but not yet claimed. It is a way to keep track of the rewards that have been distributed to a user but are yet to be withdrawn. The `rewardDebt` for a user is typically calculated as:
[ChefIncentivesController.sol#L538](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/ChefIncentivesController.sol#L538)
```solidity
uint256 rewardDebt = (user.amount * pool.accRewardPerShare) / ACC_REWARD_PRECISION;
```
This value ensures that when rewards are claimed, the correct amount is distributed based on the user's share and the current `accRewardPerShare`.

However, in the `_updatePool` function, there is no consideration of `rewardDebt` when updating the pool’s reward information. This means:
- **Inconsistent Reward Distribution**: If the `rewardDebt` is not updated correctly, users might receive incorrect reward amounts. For instance, if a user's `rewardDebt` is not recalculated or updated after the pool’s reward information changes, they might end up with an incorrect amount of rewards when they claim them.
- Potential Reward Overlaps or Shortfalls: Without adjusting for `rewardDebt`, there could be overlaps where users receive rewards they have already been accounted for or shortfalls where they do not receive their rightful share. This can lead to discrepancies between the total rewards calculated and what is actually distributed to users.

Example Scenario:

Suppose the pool has distributed rewards for a certain period, and a user’s `rewardDebt` was calculated based on the previous `accRewardPerShare`. If the `_updatePool` function is called to update the rewards without adjusting for the existing `rewardDebt`, the user may not get an accurate amount of rewards upon claiming. 
For example:
- **Before Update**:
   - User’s `rewardDeb`t = $100$ rewards
   - Total rewards in the pool = $500$ rewards
- **After Update (without adjusting `rewardDebt`)**:
   - New rewards = $200$ rewards
   - User’s actual reward (without adjusting for `rewardDebt`) might incorrectly account for the overlap or miss the correct amount.
This mismatch can cause users to receive incorrect amounts of rewards, leading to potential disputes and loss of trust.

## Impact
The `rewardDebt` is crucial for accurately tracking rewards that each user has already earned but not yet claimed. By not considering `rewardDebt` directly in `_updatePool`, there is a risk that the rewards distributed to users might be miscalculated when users claim them, leading to potential discrepancies in reward allocations. This could result in users receiving incorrect amounts of rewards, which could undermine trust in the system and affect user satisfaction.

## Recommended Mitigation Steps
The `_updatePool` function should include logic to update each user's `rewardDebt` when the pool’s reward information is updated.
