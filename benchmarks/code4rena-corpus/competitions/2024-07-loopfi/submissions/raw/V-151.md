# Vulnerability details

## Proof of Concept
The `updateEpoch` function in the `GaugeV3` contract is publicly accessible, allowing any user to call it. This function updates the epoch and potentially triggers rate updates in the connected quota keeper contract by calling the internal `_checkAndUpdateEpoch()` function.
```solidity
function updateEpoch() external override {
    _checkAndUpdateEpoch(); // U:[GA-14]
}
```
The `_checkAndUpdateEpoch()` function retrieves the current epoch from the `IGearStakingV3` contract and updates the `epochLastUpdate` variable if a new epoch has begun. If the gauge is not frozen (`epochFrozen` is `false`), it triggers the `updateRates()` function in the quota keeper contract, which adjusts the quota rates based on the votes.
```solidity
function _checkAndUpdateEpoch() internal {
    uint16 epochNow = IGearStakingV3(voter).getCurrentEpoch(); // U:[GA-14]

    if (epochNow > epochLastUpdate) {
        epochLastUpdate = epochNow; // U:[GA-14]

        if (!epochFrozen) {
            _poolQuotaKeeper().updateRates(); // U:[GA-14]
        }

        emit UpdateEpoch(epochNow); // U:[GA-14]
    }
}

```
Since `updateEpoch` can be called by any user, there is a risk that a malicious actor could exploit this function by calling it at a moment when they know the epoch has just changed. This could lead to a situation where the attacker ensures that the rates are updated based on their prior actions or votes, locking in advantageous rates before other users have the chance to react or vote.
## Example Scenario:
Imagine a scenario where the voting period for the next epoch is about to end. The current epoch's rates have not been updated yet, and the last update was close to the end of the previous epoch. A sophisticated user, aware of this timing, monitors the voting contract and notices that their preferred rates (favoring either the LP side or CA side) are leading in the votes.

As soon as the new epoch begins, the user quickly calls the `updateEpoch` function before anyone else. By doing so, they lock in the new rates based on the votes at that exact moment. Since the function doesn't have access control, the user is able to update the epoch and trigger the rate adjustment in the quota keeper, solidifying their advantageous rates for the entire new epoch.

Other users who were planning to vote or adjust their votes after the epoch change find that the rates are already updated and locked in, and their votes no longer have an impact. This results in the rates being skewed to favor the user who manipulated the timing of the `updateEpoch` function call, potentially leading to financial gains for that user at the expense of others.
## Impact
A malicious actor can manipulate the timing of epoch updates to ensure that the rates are updated in their favor. This can lead to unfair advantages in the system, where the attacker secures better quota rates before other users are aware that an epoch update is due.
## Tools Used
Manual
## Recommended Mitigation Steps
Implement access control on the `updateEpoch` function. Restrict its execution to a specific authorized address or a trusted contract to prevent arbitrary users from manipulating the timing of epoch updates.
