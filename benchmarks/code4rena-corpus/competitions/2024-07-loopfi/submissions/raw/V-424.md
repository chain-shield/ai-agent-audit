# Vulnerability details

## Vulnerability details
With the goal to defend against [vault inflation attacks](https://mixbytes.io/blog/overview-of-the-inflation-attack), LoopFi has implemented a minimum shares amount that must be kept into the `StakingLPEth` contract.
This `MIN_SHARES` amount is checked during withdrawals after assets have been transfered to user, and shares have been burnt:

```solidity

142:         uint256 _totalSupply = totalSupply();
143:         if (_totalSupply > 0 && _totalSupply < MIN_SHARES) revert MinSharesViolation();
144:     }
...:
...:      //* ---- some code ---- *//
...:
166:     function _withdraw(
167:         address caller,
168:         address receiver,
169:         address _owner,
170:         uint256 assets,
171:         uint256 shares
172:     ) internal override nonReentrant {
173:         super._withdraw(caller, receiver, _owner, assets, shares);
174:         _checkMinShares();
175:     }
```
If after withdrawal, the share supply is below `MIN_SHARES` the withdrawal will revert.
This means the last user to withdraw will have to forfeit `MIN_SHARES` worth of underlying tokens.

This value is a constant set to `0.01 ether`, and the shares here represent lpETH amounts from `PoolV3`, [which is minted 1:1 against `ETH`](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/PoolV3.sol#L429-L439) deposits, so we can consider its price to be very similar.

At the current price, this represents $25 which can represent a non neglegible amount for many users.

The vault defense burden is entirely put on the last withdrawer, while this could have been distributed over all depositors using [a virtual offset](https://docs.openzeppelin.com/contracts/4.x/erc4626#defending_with_a_virtual_offset) as it has been used in the [`AuraVault` contract](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/vendor/AuraVault.sol#L182-L191)

## Impact
Last withdrawer will not be able to withdraw its full deposit

## Tools Used
Manual review

## Recommended Mitigation Steps
Implement [a virtual offset](https://docs.openzeppelin.com/contracts/4.x/erc4626#defending_with_a_virtual_offset) defense mechanism rather than relying on the last withdrawer incuring a loss.
