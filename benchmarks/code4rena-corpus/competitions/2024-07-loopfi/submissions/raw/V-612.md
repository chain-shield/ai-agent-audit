# Vulnerability details

## Description
The PoolQuotaKeeperV3 updateRates function updates the quotaRevenue by multiplying the amount of amount borrowed by a credit manager and the current rate, then it call setQuotaRevenue at the Pool contract:
```solidity
function updateRates()
        external
        override
        gaugeOnly // U:[PQK-3]
    {
    ...
                quotaRevenue += (IPoolV3(pool).creditManagerBorrowed(creditManagers[token]) * rate) / PERCENTAGE_FACTOR; // U:[PQK-7]
...
	 IPoolV3(pool).setQuotaRevenue(quotaRevenue); // U:[PQK-7]
	 ...
}
```
Notice this quotaRevenue relies on the amount instantly borrowed by the creditManager:
```solidity
function creditManagerBorrowed(address creditManager) external view override returns (uint256) {
        return _creditManagerDebt[creditManager].borrowed;
    }
```

This borrowed amount can be increased by lending to a credit account and decreased by repaying a loan.

This creates the opportunity for malicious users to repay their loans right before a Gauge calls updateRates in order to decreased the total amount of quotaRevenue.
In the context of Mainnet, this is a realistic risk through front-runs.

## Impact
Malicious parties can opt to repay their borrows right before a rates update call in order to harm the Pool's accrual of quota revenue.
This harms the whole Pool contract, as a smaller-than-it-should-be quota revenue value harms the calculation of quota revenue accrued:
```solidity
function _calcQuotaRevenueAccrued(uint256 timestamp) private view returns (uint256) {
        return quotaRevenue().calcLinearGrowth(timestamp);
    }
```

This calculation function is utilized in different parts that matter for the proper functioning of the PoolV3 contract, such as its expectedLiquidity, its calculated accrued quota interest and its base interest.
Since the updateRates function can be externally called by anyone by calling the updateEpoch function at the GaugeV3 contract, this attack-vector is of easy execution - as one could repay their loans then call update epoch right away:
```solidity
function updateEpoch() external override {
        _checkAndUpdateEpoch(); // U:[GA-14]
    }

    /// @dev Implementation of `updateEpoch`
    function _checkAndUpdateEpoch() internal {
        ...
                _poolQuotaKeeper().updateRates(); // U:[GA-14]
        ...
    }
```

## Recommended Mitigation Steps
There are two different ways to mitigate the issue: 
The first one would be through the usage of private mempools for capital-sensitive operations. Through the usage of Flashbots, one could maintain a certain level of tx privacy that would decrease the risk of these front-runs happening.
The second one would be by introducing checkpoints to the quota revenue and its index to ensure no update reflects an incorrect borrow state.
