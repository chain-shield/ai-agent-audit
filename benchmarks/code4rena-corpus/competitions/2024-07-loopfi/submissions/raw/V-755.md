# Vulnerability details

### Issue
The `withdraw` and `redeem` functions in the `PoolV3` contract face potential slippage issues. These functions allow users to withdraw underlying tokens or redeem pool shares, but they do not account for fluctuations in the pool's underlying token balance that may occur between the time the user initiates the transaction and when it is executed.

### Details
1. **Withdraw Function**: The `withdraw` function allows users to withdraw a specified amount of underlying tokens. If the pool's balance changes due to concurrent withdrawals or deposits, the user may receive fewer tokens than expected.

2. **Redeem Function**: The `redeem` function allows users to redeem a specified number of pool shares for underlying tokens. Similar to the withdraw function, if the pool's balance changes during the transaction, the user may end up receiving fewer tokens than anticipated.

### Code Snippets

#### Withdraw Function
```solidity
function withdraw(
    uint256 assets,
    address receiver,
    address owner
) public override(ERC4626, IERC4626) whenNotPaused whenNotLocked nonReentrant returns (uint256 shares) {
    uint256 assetsToUser = _amountWithFee(assets);
    uint256 assetsSent = _amountWithWithdrawalFee(assetsToUser);
    shares = _convertToShares(assetsSent);
    _withdraw(receiver, owner, assetsSent, assets, assetsToUser, shares);
}
```

#### Redeem Function
```solidity
function redeem(
    uint256 shares,
    address receiver,
    address owner
) public override(ERC4626, IERC4626) whenNotPaused whenNotLocked nonReentrant returns (uint256 assets) {
    uint256 assetsSent = _convertToAssets(shares);
    uint256 assetsToUser = _amountMinusWithdrawalFee(assetsSent);
    assets = _amountMinusFee(assetsToUser);
    _withdraw(receiver, owner, assetsSent, assets, assetsToUser, shares);
}
```

### Impact
The lack of slippage handling in these functions can lead to users receiving fewer underlying tokens than expected during withdrawals or redemptions, especially in scenarios with high transaction volume or concurrent transactions.

### Scenario
1. User A initiates a withdrawal of 100 underlying tokens.
2. Before the transaction completes, User B also withdraws 50 tokens, increasing the pool's underlying balance.
3. User A's transaction calculates the amount to be withdrawn based on the original balance, leading to a situation where User A receives fewer tokens than expected.

### Proposed Fix
Introduce a user-defined slippage parameter. This parameter will allow users to specify the maximum acceptable slippage for their transactions.

#### Modified Withdraw Function
```solidity
function withdraw(
    uint256 assets,
    address receiver,
    address owner,
    uint256 slippage // New parameter for user-defined slippage
) public override(ERC4626, IERC4626) whenNotPaused whenNotLocked nonReentrant returns (uint256 shares) {
    uint256 assetsToUser = _amountWithFee(assets);
    uint256 assetsSent = _amountWithWithdrawalFee(assetsToUser);
    shares = _convertToShares(assetsSent);

    // Calculate the minimum shares expected based on slippage
    uint256 minShares = shares * (100 - slippage) / 100;
    require(shares >= minShares, "Slippage exceeded"); // Revert if slippage is too high

    _withdraw(receiver, owner, assetsSent, assets, assetsToUser, shares);
}
```
