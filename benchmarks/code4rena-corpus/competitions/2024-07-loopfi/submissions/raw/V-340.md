# Vulnerability details

## Proof of Concept
The `AuraVault` contract's `deposit` and `mint` functions utilize the `safeApprove` method to set allowances for transferring assets to the `rewardPool`. However, the contract does not reset the allowance to zero before assigning a new value. This can be seen in the following code snippets:
`deposit` Function:
```solidity
function deposit(uint256 assets, address receiver) public virtual override returns (uint256 shares) {
    ...
    IERC20(asset()).safeApprove(rewardPool, assets);
    IRewardPool(rewardPool).stake(assets);
    ...
}

```

`mint` function:
```solidity
function mint(uint256 shares, address receiver) public virtual override returns (uint256 assets) {
    ...
    IERC20(asset()).safeApprove(rewardPool, assets);
    IRewardPool(rewardPool).stake(assets);
    ...
}
```
In both functions, `safeApprove` is used directly to approve assets for the `rewardPool`. However, this method does not reset the existing allowance to zero before setting a new allowance. According to the ERC-20 standard, this practice can be prone to race conditions, where an approved spender could manipulate the amount of tokens allowed before the new allowance is set, potentially causing unintended transfers.
## Impact
If an external entity has partial control over the approval process (for example, through a re-entrancy attack or by front-running transactions), it might exploit the lack of a zero reset, leading to unauthorized or unexpected token transfers. This could compromise the integrity of the vault's operations and potentially cause financial loss to users interacting with the contract.
## Tools Used
Manual
## Recommended Mitigation Steps
The allowance should be reset to zero before setting a new allowance value.
