# Vulnerability details

## Description

The `PoolV3` contract implements a lending and borrowing protocol compatible with the ERC-4626 standard. It includes functions for depositing, withdrawing, minting, and redeeming assets in exchange for pool shares. The conversion between assets and shares is handled by the [`_convertToShares()`](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L429-L432) and [`_convertToAssets()`](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L436-L439) functions.

These conversion functions are critical for maintaining the correct ratio between the pool's total assets and total shares. However, the current implementation uses a simplistic 1:1 mapping:

This implementation fails to account for the actual total supply of shares or the total assets in the pool. As a result, the conversion ratio remains constant at 1:1, regardless of the pool's state. This can lead to severe miscalculations when users deposit, withdraw, mint, or redeem, potentially allowing an attacker to manipulate the pool's state and extract more value than they should be able to.

The issue affects core functionalities of the pool, such as `deposit()`, `withdraw()`, `mint()`, and `redeem()`. These functions rely on `_convertToShares()` and `_convertToAssets()` to calculate the correct amount of shares or assets involved in each operation.

The `_convertToShares()` function is used to calculate the number of shares to mint. With the current implementation, this calculation will always result in a 1:1 ratio, regardless of the pool's actual state.

## Impact

An attacker can repeatedly deposit, withdraw, mint, and redeem assets to manipulate the pool's state and extract more value than they should be able to. This can lead to significant financial loss for the pool and its participants. The attacker can drain the pool of its assets, undermining the integrity of the protocol and causing a loss of funds for other users.


## Proof of Concept

Consider the following scenario:

1. The pool starts with 1000 assets and 1000 shares (1:1 ratio).
2. An attacker deposits 1000 assets and receives 1000 shares due to the 1:1 conversion.
3. The pool now has 2000 assets and 2000 shares, maintaining the 1:1 ratio.
4. The attacker withdraws 1000 assets, burning 1000 shares.
5. The pool now has 1000 assets and 1000 shares again.
6. The attacker mints 1000 shares. Due to the flawed conversion, this only requires 1000 assets.
7. The attacker now has 1000 shares, which they can redeem for 1000 assets.
8. The attacker has effectively drained 1000 assets from the pool without contributing any value.

This process can be repeated to continually drain the pool.

## Recommended Mitigation Steps

To fix this issue, the `_convertToShares()` and `_convertToAssets()` functions should be updated to correctly account for the total supply of shares and the total assets in the pool. Here's a recommended implementation:

```solidity
function _convertToShares(uint256 assets) internal view returns (uint256 shares) {
    uint256 supply = totalSupply();
    uint256 totalAssets = totalAssets();
    return (supply == 0 || totalAssets == 0) ? assets : assets.mulDiv(supply, totalAssets);
}

function _convertToAssets(uint256 shares) internal view returns (uint256 assets) {
    uint256 supply = totalSupply();
    return (supply == 0) ? shares : shares.mulDiv(totalAssets(), supply);
}
```

These updated functions ensure that the conversion between assets and shares correctly accounts for the current state of the pool, maintaining the appropriate share-to-asset ratio and preventing the described exploit.
