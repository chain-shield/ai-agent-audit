# Vulnerability details

Impact
Users will always receive lesser fewer tokens than they are due when exiting the pool, leading to potential financial losses.

## Proof of Concept
When exiting Pool, there would be times where Balancer Pool will be imbalanced experiencing pool changes where by users are making too many withdraw of the same single token that token's balance in the pool decreases, making the pool disproportionately weighted toward the remaining token. 

This imbalance could lead to less favorable rates for future swaps and exits, negatively impacting Alice when she decides to withdraw or swap tokens in the future.
```solidity

            poolId,

```
Te main reason to join with all the pool's tokens in exact proportions is to minimize the price impact or slippage of the join. If the deposited tokens are imbalanced, they are often swapped internally within the pool, incurring slippage or fees.
However, the concept of proportional join to minimize slippage does not always hold with the current implementation of the restoreVault function.

If a user tries to exit a pool the `minAmountOut` will always be set at default(0) meaning opening door for slippage attack. However [PoolActionParams](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/proxy/PoolAction.sol#L27) has `minOut` that a user can specify when existing, the `minAmountOut` request passed was never referring to `minOut` of user making the MinAmountOut to have default 0 value when existing pool.

## Recommended Mitigation Steps
The function should directly adjusts the `minAmountsOut` array using the `minOut` value from `PoolActionParams`. This ensures that the minimum acceptable amount for the token at the specified outIndex is set.
```solidity
Adjust minAmountsOut using minOut from PoolActionParams
    minAmountsOut[outIndex] = poolActionParams.minOut
```
