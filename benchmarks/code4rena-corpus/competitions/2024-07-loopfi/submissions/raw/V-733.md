# Vulnerability details

## Impact
The setAllowed function allows a controller to grant or revoke withdrawal and redemption permissions for specific accounts even when the pool is locked. However, there is no limitation or logging mechanism on who can be added or removed, which could be exploited by a malicious or compromised controller to allow unauthorized accounts to access pool funds during a lock period.


```

function setAllowed(address account, bool status) external controllerOnly {
    _allowed[account] = status;
}
```


Lack of Granular Control: The function allows any controller to add or remove accounts from the _allowed mapping, granting them privileges to withdraw or redeem from the pool even when it is locked. There is no mechanism to limit or monitor these changes, which could be abused.

Potential for Exploitation: A malicious controller could whitelist their own or an accomplice’s address, allowing unauthorized withdrawals or redemptions when the pool is locked, potentially draining the pool’s funds.

Insufficient Auditing: The absence of logging for changes to the _allowed mapping means that such changes could go unnoticed, making it difficult to detect and respond to unauthorized access.


## Proof of Concept
A malicious controller gains access to the contract and uses the setAllowed function to grant themselves withdrawal privileges even when the pool is locked.

The attacker calls setAllowed to add their address to the _allowed mapping.
They then proceed to withdraw or redeem assets from the pool while it is locked, bypassing the intended restrictions.


```
// Malicious controller adds their own address to the allowed list
pool.setAllowed(maliciousAddress, true);

// Attacker then withdraws funds while the pool is locked
pool.withdraw(1000e18, maliciousAddress, maliciousAddress);
```

The attacker successfully withdraws funds from the pool during a lock period, potentially draining significant assets and causing financial loss to the protocol.


Financial Loss: Unauthorized accounts could withdraw or redeem large amounts of assets from the pool during a lock period, leading to significant financial loss for the protocol.
Security Risk: The ability to bypass lock periods undermines the security mechanisms of the pool, making it vulnerable to exploitation.
Operational Risk: The lack of monitoring for changes to the _allowed mapping could result in undetected abuse, further compounding the financial and security risks.

## Recommended Mitigation Steps


Implement Access Control Restrictions: Restrict the use of the setAllowed function to trusted roles and consider adding multi-signature approval for changes to the _allowed mapping.

Add Event Logging: Implement event logging for every change made to the _allowed mapping, ensuring that all modifications are auditable.

Conduct Regular Audits: Regularly audit the _allowed mapping to ensure that no unauthorized accounts have been granted privileges.
