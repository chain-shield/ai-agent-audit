# Vulnerability details

## Impact

This will lead to inconsistencies between current cooldown duration and the cool down duration applied to users after a change of cool down duration potentially allowing some users to bypass the intended cooldown period or forcing others to wait longer than necessary. Users who initiated cooldowns before a period increase can bypass the new, longer cooldown. Users who initiated cooldowns before a period decrease are forced to wait longer than necessary. This can also be exploited through front-running, where users anticipate changes to the cooldown period and act to gain an advantage. This is particularly important as the cooldown duration can range anywhere from 1 day to 30 days, making it crucial to ensure that each user's cooldown period is accurately applied

## Proof of Concept
This issue occurs when a new cooldown duration is set via the function `setCooldownDuration`
```
function setCooldownDuration(uint24 duration) external onlyOwner {
    if (duration > MAX_COOLDOWN_DURATION) {
        revert InvalidCooldown();
    }

    uint24 previousDuration = cooldownDuration;
    cooldownDuration = duration;
    emit CooldownDurationUpdated(previousDuration, cooldownDuration);
}

```
This function only updates the `cooldownDuration` state variable. However, existing cooldowns are stored in the `cooldowns` mapping;
```
mapping(address => UserCooldown) public cooldowns;

struct UserCooldown {
    uint104 cooldownEnd;
    uint256 underlyingAmount;
}

```
The cooldownEnd for each user is set when they initiate a cooldown:
```
cooldowns[msg.sender].cooldownEnd = uint104(block.timestamp) + cooldownDuration;

```
ones a new cool down duration is set, its not immediately enforced because `cooldownEnd` is unaffected by current cooldownDuration. As a result:
If the cooldown duration is increased, users who have already started their cooldown will be able to unstake earlier than intended(current coodownduration).
If the cooldown duration is decreased, users who have already started their cooldown will have to wait longer than the new intended(current coodownduration).
Users with knowledge of an impending cooldown period change can initiate cooldowns just before the change.
This allows them to lock in a shorter cooldown period before it is increased(they can do this by also frontrunning the transaction to change duration in mempool).

## Recommended Mitigation Steps
Modify the UserCooldown struct to store the duration and start time instead of the end time. update the unstake function to calculate the end time based on the stored duration and start time.
This approach allows for immediate updates to the cooldown duration for all users.
```
struct UserCooldown {
    uint104 cooldownStart;
    uint256 underlyingAmount;
}

function cooldownAssets(uint256 assets) external ensureCooldownOn returns (uint256 shares) {
    // ... existing code ...
    cooldowns[msg.sender].cooldownStart = uint104(block.timestamp);
    cooldowns[msg.sender].cooldownDuration = cooldownDuration;
    // ... rest of the function ...
}

function unstake(address receiver) external {
    UserCooldown storage userCooldown = cooldowns[msg.sender];
    uint256 assets = userCooldown.underlyingAmount;

    if (block.timestamp >= userCooldown.cooldownStart + cooldownDuration || cooldownDuration == 0) {
        // ... rest of the function ...
    } else {
        revert InvalidCooldown();
    }
}

```
