# Vulnerability details

## Overview
Overview
The identified issue pertains to a critical flaw within the `join()` function of the Balancer pool's smart contract, specifically concerning the simultaneous handling of both ETH (native Ether) and WETH (Wrapped Ether). This flaw, embedded within the code at lines [132]() and [147]() of PoolAction.sol, can cause transaction failures and consequentially lead to the irrevocable loss of user funds. This report outlines the vulnerability, its impact, and provides a recommended remediation strategy.


 ## Impact
***High Severity:*** The core of the vulnerability arises from the join() function's mismanagement of transactions that involve both ETH and WETH. The Balancer protocol enforces a strict rule prohibiting the simultaneous use of ETH and WETH in a single JoinPool operation. However, the current implementation of the `join()` function fails to enforce this rule, leading to the following potential issues:

- Undefined Behavior: When both ETH and WETH are present in the same transaction, the Balancer Vault is unable to process them simultaneously. This results in unpredictable behavior, often leading to a transaction revert. The revert means that the user's ETH remains locked within the Vault without being utilized for liquidity provision or being refunded appropriately.

- Loss of Funds: In the scenario where the transaction does not revert, the failure to correctly process the combination of ETH and WETH could lead to a situation where the ETH is not properly wrapped into WETH, or the assets are not accurately allocated within the pool. This could result in the permanent loss of the user's ETH, as it may neither be credited to the pool nor returned to the user.

- Failure to Refund Non-Excess ETH: Notably, the contract's current refund mechanism only accounts for excess ETH. If no excess ETH is sent, the ETH might be lost permanently, especially if the transaction fails to revert or properly handle the error.

The vulnerability is rooted in the incorrect handling of the assets array within the join() function, where both ETH and WETH may be included in a single transaction. [The Balancer protocol mandates that if ETH is sent as part of the transaction](https://github.com/balancer/balancer-v2-monorepo/blob/36d282374b457dddea828be7884ee0d185db06ba/pkg/interfaces/contracts/vault/IVault.sol#L361), any WETH in the assets array must be replaced with the zero address (0x0). The failure to enforce this rule can result in the Balancer Vault encountering both ETH and WETH, leading to a transaction revert or, worse, the loss of ETH without compensation.

## Proof of Concept
Consider the following scenario:

Alice attempts to provide liquidity to a Balancer pool by contributing 1 ETH and some WETH she holds.
Alice's assets array includes the WETH address, and she sends 1 ETH along with her transaction.
The join() function does not replace the WETH address with 0x0, violating the Balancer protocol’s rule.
When the Balancer Vault processes the JoinPool request, it encounters both ETH and WETH, leading to a transaction revert. As a result, Alice's 1 ETH is locked in the Vault, and she receives no pool tokens in return.
If the function does not correctly handle the revert or refund, Alice's ETH could be permanently lost, exacerbating the severity of the issue.

## Recommended Mitigation Steps
To mitigate this vulnerability, it is imperative to implement a logic check within the join() function to prevent the inclusion of both ETH and WETH in the same transaction. Specifically:

- Add Conditional Checks: Prior to invoking balancerVault.joinPool(), the function should verify whether ETH is being sent (indicated by msg.value > 0) and if WETH is included in the assets array.
- Enforce Protocol Rules: If both ETH is sent and WETH is present in the assets array, the function should immediately revert with a clear and descriptive error message, ensuring that the transaction does not proceed under invalid conditions.
Enhance Refund Logic: Modify the refund logic to ensure that any non-excess ETH is properly handled and returned to the user in case of transaction failure.
