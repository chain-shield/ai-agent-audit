# Vulnerability details

## Impact
The vulnerability due to the absence of slippage controls in the `_deposit` and `mint` functions can lead to substantial financial risks for users. Specifically, during high market volatility, the actual amount of shares minted or assets deposited might not correspond with the expected amounts. Even though the conversion ratio of assets to shares is fixed at 1:1, the real value of assets can fluctuate significantly between the initiation and execution of a transaction. This discrepancy can result in users receiving fewer shares than the actual market value of their deposited assets, leading directly to potential financial losses.

## Proof of Concept:
The vulnerability manifests in the absence of checks or mechanisms to handle slippage between the assets sent (`assetsSent`) and the assets that should have been received (`assetsReceived`) in the `_deposit` function. The code:

```solidity
function _deposit(address receiver, uint256 assetsSent, uint256 assetsReceived, uint256 shares) internal {
  IERC20(underlyingToken).safeTransferFrom({from: msg.sender, to: address(this), value: assetsSent});
  _updateBaseInterest({
    expectedLiquidityDelta: assetsReceived.toInt256(),
    availableLiquidityDelta: 0,
    checkOptimalBorrowing: false
  });
  _mint(receiver, shares);
  emit Deposit(msg.sender, receiver, assetsSent, shares);
}
```
In this function, there is no comparison or validation to ensure that the `assetsSent` match the `assetsReceived` which could be adjusted for market conditions. Similarly, in the `mint` function:
```solidity
function mint(uint256 shares, address receiver) public override(ERC4626, IERC4626) whenNotPaused nonReentrant nonZeroAddress(receiver) returns (uint256 assets) {
  uint256 assetsReceived = _convertToAssets(shares);
  assets = _amountWithFee(assetsReceived);
  _deposit(receiver, assets, assetsReceived, shares);
}
```
The absence of a validation mechanism to ensure that the shares calculated from the assets are correctly aligned with market rates before depositing exacerbates this vulnerability.

Consider a scenario where a user intends to deposit `$100` into the smart contract, expecting to receive 100 shares, assuming a 1:1 conversion ratio of `$1` per share. If the market value of the deposited asset drops to `$0.90` per asset immediately after the deposit but before the transaction is processed, the user would still receive only 100 shares. However, to match their initial `$100` deposit's intended value, they should receive approximately 111 shares based on the new asset value of `$0.90` per share. This misalignment demonstrates how users can lose value due to market volatility affecting asset prices, which the current implementation does not accommodate.

## Recommended Mitigation Steps

1. **Implement Slippage Verification**: Introduce a mechanism to verify the slippage before finalizing the deposit in the `_deposit` function. This could include a check that the `assetsSent` are within a permissible range of the `assetsReceived` (e.g., within a 1% tolerance).

2. **User Confirmation for High Slippage**: If the slippage exceeds a predefined threshold, require user confirmation before proceeding with the transaction, or automatically revert the transaction.
