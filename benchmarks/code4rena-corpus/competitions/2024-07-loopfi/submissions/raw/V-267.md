# Vulnerability details

## Description

The `PoolQuotaKeeperV3` contract is responsible for managing quotas that limit the system's exposure to risky assets. The [`updateRates()` function](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/quotas/PoolQuotaKeeperV3.sol#L183-L221) is a critical component of this system, updating quota rates and cumulative indexes for all quoted tokens. However, the current implementation contains a logical flaw in the order of operations that could lead to inaccurate financial calculations.

The `updateRates()` function performs the following key operations:
1. Retrieves current rates for all quoted tokens from the gauge contract.
2. Iterates through each token, updating its cumulative index and rate.
3. Calculates and sets the new pool quota revenue.
4. Updates the `lastQuotaRateUpdate` timestamp.

The issue lies in the order of these operations within the token iteration loop. Specifically:

1. The cumulative index is calculated using the old rate:

2. The new rate is then set immediately after:
```solidity
tokenQuotaParams.rate = rate;
```

This sequence means that the cumulative index is always calculated using the previous rate, not reflecting the current update. In a rapidly changing market, this could lead to significant discrepancies in quota calculations.

Furthermore, the `lastQuotaRateUpdate` is only set at the end of the function, which could cause inconsistencies if the function is called multiple times in quick succession.

## Impact
The incorrect order of operations in `updateRates()` can lead to inaccurate quota calculations, potentially resulting in financial discrepancies across the system. This could affect the distribution of quota-related fees and interest, leading to unfair advantages or disadvantages for certain users.

The severity of the impact depends on the frequency of rate updates and the volatility of the rates. In a stable market with infrequent updates, the impact might be minimal. However, in a volatile market with frequent updates, the cumulative effect of these inaccuracies could be substantial, potentially leading to significant misallocations of funds or incorrect risk assessments.

## Proof of Concept
Consider the following scenario:

1. The current rate for Token A is 5%.
2. `updateRates()` is called, and the new rate for Token A is 10%.
3. The function calculates the cumulative index using the old 5% rate.
4. The rate is then updated to 10%.
5. The next time `updateRates()` is called, it will use 10% for the entire period since the last update, even though it should have used 5% for part of that time.

This leads to an overestimation of the cumulative index, which could result in users paying more in quota-related fees than they should.

### Detailed Example

1. **Initial State**:
   - `Token A` has a `rate` of 5%.
   - `cumulativeIndexLU` for `Token A` is 1.0 (for simplicity).

2. **First Call to `updateRates()`**:
   - The `gauge` returns a new `rate` of 10% for `Token A`.
   - The function calculates the new `cumulativeIndexLU` using the old rate of 5%:
     ```solidity
     tokenQuotaParams.cumulativeIndexLU = QuotasLogic.cumulativeIndexSince(
         1.0, // old cumulative index
         5%,  // old rate
         timestampLU
     );
     ```
   - Assume the calculated `cumulativeIndexLU` is now 1.05.
   - The `rate` is then updated to 10%:
     ```solidity
     tokenQuotaParams.rate = 10%;
     ```

3. **Second Call to `updateRates()`**:
   - The `gauge` returns the same `rate` of 10% for `Token A`.
   - The function calculates the new `cumulativeIndexLU` using the previous cumulative index of 1.05 and the new rate of 10% for the entire period:
     ```solidity
     tokenQuotaParams.cumulativeIndexLU = QuotasLogic.cumulativeIndexSince(
         1.05, // previous cumulative index
         10%,  // new rate
         timestampLU
     );
     ```
   - This calculation assumes that the rate was 10% for the entire period, leading to an overestimation of the cumulative index.
