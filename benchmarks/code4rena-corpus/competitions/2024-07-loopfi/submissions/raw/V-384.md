# Vulnerability details

## Proof of Concept
The `cooldownAssets` and `cooldownShares` functions in the `StakingLPEth` contract lack proper validation for the cooldown end time. These functions are designed to allow users to initiate a cooldown period for their staked assets or shares. However, they do not check if the calculated cooldown end time exceeds the `MAX_COOLDOWN_DURATION`. This oversight could lead to unexpected behavior in the contract.
Here's the relevant code snippet from both functions:
```solidity
function cooldownAssets(uint256 assets) external ensureCooldownOn returns (uint256 shares) {
    if (assets > maxWithdraw(msg.sender)) revert ExcessiveWithdrawAmount();

    shares = previewWithdraw(assets);

    cooldowns[msg.sender].cooldownEnd = uint104(block.timestamp) + cooldownDuration;
    cooldowns[msg.sender].underlyingAmount += uint152(assets);

    _withdraw(msg.sender, address(silo), msg.sender, assets, shares);
}

function cooldownShares(uint256 shares) external ensureCooldownOn returns (uint256 assets) {
    if (shares > maxRedeem(msg.sender)) revert ExcessiveRedeemAmount();

    assets = previewRedeem(shares);

    cooldowns[msg.sender].cooldownEnd = uint104(block.timestamp) + cooldownDuration;
    cooldowns[msg.sender].underlyingAmount += uint152(assets);

    _withdraw(msg.sender, address(silo), msg.sender, assets, shares);
}
```
These functions are designed to initiate a cooldown period when users want to unstake their assets or shares. The cooldown end time is calculated by adding the current `cooldownDuration` to the current timestamp. However, neither `cooldownAssets` nor `cooldownShares` checks if the calculated `cooldownEnd` exceeds this maximum duration.
This oversight can lead to several issues:
1. If `block.timestamp + cooldownDuration` overflows the `uint104` type, it could result in an unexpectedly short cooldown period.
2. If `block.timestamp + cooldownDuration` is greater than `MAX_COOLDOWN_DURATION`, it violates the intended maximum cooldown constraint.
## Impact
Users might be locked into cooldown periods longer than the maximum intended duration, potentially leading to extended asset illiquidity and frustration.

## Recommended Mitigation Steps
Add a check in both `cooldownAssets` and `cooldownShares` functions to ensure that the calculated cooldown end time does not exceed `MAX_COOLDOWN_DURATION`. If it does, the function should revert with an `InvalidCooldown` error. Here's an example of how to implement this check:
```solidity
if (uint104(block.timestamp) + cooldownDuration > MAX_COOLDOWN_DURATION) revert InvalidCooldown();
```
