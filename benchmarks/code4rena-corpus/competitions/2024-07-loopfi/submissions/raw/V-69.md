# Vulnerability details

## Impact
The purpose of the persistRewardsPerSecond flag is to allow the owner to persist the reward per second used to calculate rewards. This can be called to disable making the RPS follow the emission schedule.

The rewards per second can be persisted by owner via setting persistRewardsPerSecond to true in  ChefIncentivesController.sol by calling the setRewardsPerSecond. In addition, The default value for persistRewardsPerSecond is set to true on contract initialization. 

RPS helps determine how much rewards are available since last reward time and also the accrued reward per share. It is used by the following function:

````
    /**
     * @dev Returns new rewards since last reward time.
     * @param pool pool info
     * @param _totalAllocPoint allocation point of the pool
     */
    function _newRewards(
        VaultInfo memory pool,
        uint256 _totalAllocPoint
    ) internal view returns (uint256 newReward, uint256 newAccRewardPerShare) {
        uint256 lpSupply = pool.totalSupply;
        if (lpSupply > 0) {
            uint256 duration = block.timestamp - pool.lastRewardTime;
            uint256 rawReward = duration * rewardsPerSecond;

            uint256 rewards = availableRewards();
             console.log("available rewards are:", rewards);
            if (rewards < rawReward) {
                rawReward = rewards;
            }
            newReward = (rawReward * pool.allocPoint) / _totalAllocPoint;
           
            newAccRewardPerShare = (newReward * ACC_REWARD_PRECISION) / lpSupply;
        }
    }
````
The above confirms that if RPS is 0, it means there will be no rewards to distribute to users.

The problem with setting it to true becomes evident if we look at the function below:

````
function _updateEmissions() internal {
        if (block.timestamp > endRewardTime()) {
            _massUpdatePools();
            lastRPS = rewardsPerSecond;
            rewardsPerSecond = 0;
            return;
        }
        setScheduledRewardsPerSecond();
    }
````


The function above is responsible for updating em missions during an epoch. its triggered in two locations:

1. when a user makes a call to claim rewards.
2. or when the owner wants to add a new pool.

The end of the epoch is determined by the endRewardTime function, if it has been reached the _updateEmissions resets RPS to 0. It also makes a call to the setScheduledRewardsPerSecond function which ensures RPS is set according to the emmision schedule. 

````   
 /**
     * @dev Updates RPS.
     */
    function setScheduledRewardsPerSecond() internal {
        if (!persistRewardsPerSecond) {
            uint256 length = emissionSchedule.length;
            uint256 i = emissionScheduleIndex;
            uint128 offset = uint128(block.timestamp - startTime);
            for (; i < length && offset >= emissionSchedule[i].startTimeOffset; ) {
                unchecked {
                    i++;
                }
            }
            if (i > emissionScheduleIndex) {
                emissionScheduleIndex = i;
                _massUpdatePools();
                rewardsPerSecond = uint256(emissionSchedule[i - 1].rewardsPerSecond);
            }
        }
    }
````

Notice how the schedule is skipped if persistRewardsPerSecond is set to true, which is correct.

However the fact that reward per second is set to 0 once epoch ends within _updateEmissions, and the schedule will also not be applied by setScheduledRewardsPerSecond, means that all other future epochs will always have a reward per second of 0, hence not only will RPS not persist, but users will not be able to claim any future rewards. 

This is somewhat mitigated by saving the current RPS into the lastRPS, but this mitigation will not be sufficient as will be show later in report.

````    
/**
     * @notice Add new rewards.
     * @dev Only callable by owner.
     * @param _amount new deposit amount
     */
    function registerRewardDeposit(uint256 _amount) external onlyOwner {
        depositedRewards = depositedRewards + _amount;
        _massUpdatePools();
        // @audit this safety check below will fail is lastRPS is also 
        // set to 0
        if (rewardsPerSecond == 0 && lastRPS > 0) {
            rewardsPerSecond = lastRPS;
        }
        emit RewardDeposit(_amount);
    }
````


Consider the following scenario, and for the sake of argument we assume that an emission schedule will be followed and so persistRewardsPerSecond is set to false.

1. from epoch 1 to 5, RPS is set as per schedule, and the owner distributes rewards accordingly at start of every epoch. user claim rewards normally.
2. in epoch 6, owner wants to persist the RPS to a certain rate, this could be for a number of reasons(governance, emergency etc). So they call the setRewardsPerSecond with an RPS of 10 and persist flag of true.
3. The owner also distributes rewards for epoch 6 by calling the registerRewardDeposit function.
4. Alice claims her rewards after end of epoch 6 by calling the claims function, but before rewards are distributed by owner for epoch 7. this triggers the _updateEmissions function, which in turn sets RPS to 0. lastRPS is set to equal the last RPS value of 10.
5. Bob also immediately claims rewards, this will reset both the RPS and last RPS to 0.
6. Owner distributes rewards for epoch 7.
7. Alice and Bob attempt to claim rewards for epoch 7, but will be unable to since the persisted RPS has been cleared out. Any attempt to claim rewards by all users will revert with  NothingToVest().
8. Admin is made aware of the critical issue close to end of epoch 10, so they can either set a new RPS(which can and will reset again to 0 due to the logic bug) or disable persisting RPS entirely and resume the RPS schedule.
