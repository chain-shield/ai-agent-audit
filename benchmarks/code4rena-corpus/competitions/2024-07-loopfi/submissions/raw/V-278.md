# Vulnerability details

## Impact
Detailed description of the impact of this finding.

The removeVault function in the VaultRegistry contract introduces a data inconsistency between the registeredVaults mapping and the vaultList array. 

This inconsistency arises when a vault is marked as unregistered in the mapping before it is successfully removed from the list. 

If _removeVaultFromList fails to find the vault, the vault remains in vaultList but is marked as unregistered in registeredVaults. This can lead to:

	•	Operational inconsistencies where functions relying on accurate vault lists fail or behave incorrectly.
	•	Challenges in protocol integrity, where administrative and maintenance functions may operate on stale or incorrect data.
	•	Potential disruptions in data aggregation processes or reporting tools that rely on vault data.

***Historical Use Case***

A similar issue was observed in the MakerDAO protocol, where inconsistent state management between different components of their system led to unexpected behaviours in vault liquidation processes. 

This inconsistency in vault state management required careful coordination and updates across different components to resolve, emphasising the importance of maintaining consistent state across all data structures.

## Proof of Concept

The inconsistency occurs due to the order of operations in the removeVault function. Here’s a simplified breakdown:

1.	Check if the vault is registered:
```sol
if (!registeredVaults[vault]) revert VaultRegistry__removeVault_vaultNotFound();
```

2.	Attempt to remove the vault from the list:
```sol
_removeVaultFromList(vault);
```

3.	Mark the vault as unregistered in the mapping:
```sol
registeredVaults[vault] = false;
```

In this sequence, _removeVaultFromList could fail to find the vault in vaultList, especially if other concurrent operations affect list integrity or due to prior mismanagement.

## Recommended Mitigation Steps
To resolve this issue, the removeVault function should update the registeredVaults mapping only after confirming successful removal from the vaultList. 

The code should be modified as follows:
```sol
function removeVault(ICDPVault vault) external override(IVaultRegistry) onlyRole(VAULT_MANAGER_ROLE) {
    if (!registeredVaults[vault]) revert VaultRegistry__removeVault_vaultNotFound();

    _removeVaultFromList(vault); // Ensure successful removal before proceeding
    registeredVaults[vault] = false; // Update mapping after removal
    emit VaultRemoved(vault);
}

function _removeVaultFromList(ICDPVault vault) private {
    uint256 vaultLen = vaultList.length;
    bool found = false;
    for (uint256 i = 0; i < vaultLen; ) {
        if (vaultList[i] == vault) {
            vaultList[i] = vaultList[vaultLen - 1];
            vaultList.pop();
            found = true; // Mark as found for confirmation
            break;
        }
        unchecked {
            ++i;
        }
    }
    if (!found) revert VaultRegistry__removeVault_vaultNotFound();
}
```
This ensures the mapping is only updated after the list integrity is confirmed, maintaining consistency.
