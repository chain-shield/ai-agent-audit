# Vulnerability details

## Description
In the context of Balancer joins, the transferAndJoin function at the PoolAction contract takes the maximum amounts possible from the caller (`from` argument) to be able to join the Balancer pool within the user defined token limits:
```solidity
function transferAndJoin(
        address from,
        PermitParams[] calldata permitParams,
        PoolActionParams calldata poolActionParams
    ) external {
        ...
                        _transferFrom(assets[i], from, address(this), maxAmountsIn[i], permitParams[i]);
                    }
...
    }
```

Then it calls the join public payable function, that will call `_balancerJoin`.
The contract approves the max amounts to the balancerVault then calls balancerVault.joinPool:
```solidity
function _balancerJoin(PoolActionParams memory poolActionParams) internal {
        ...
        for (uint256 i = 0; i < assets.length; ) {
            if (maxAmountsIn[i] != 0) {
                IERC20(assets[i]).forceApprove(address(balancerVault), maxAmountsIn[i]);
            }

            unchecked {
                ++i;
            }
        }

        balancerVault.joinPool(
            poolId,
            address(this),
            poolActionParams.recipient,
            JoinPoolRequest({
                assets: assets,
                maxAmountsIn: maxAmountsIn,
                userData: abi.encode(JoinKind.EXACT_TOKENS_IN_FOR_BPT_OUT, assetsIn, poolActionParams.minOut),
                fromInternalBalance: false
            })
        );
    }
```

If we take a look at balancerVault's joinPool implementation, we notice the calltrace leads us to the `_processJoinPoolTransfers` function at PoolBalances.sol ([balancer-v2-monorepo/pkg/vault/contracts/PoolBalances.sol at 36d282374b457dddea828be7884ee0d185db06ba · balancer/balancer-v2-monorepo (github.com)](https://github.com/balancer/balancer-v2-monorepo/blob/36d282374b457dddea828be7884ee0d185db06ba/pkg/vault/contracts/PoolBalances.sol#L231)). This function checks if the amountIn is within the user-defined bounds at maxAmountsIn then transfers to the vault *only the amount required to do the join operation.* This means the max amount that was sent to the PoolAction contract is not fully utilized.

The `_balancerJoin` or the transferAndJoin functions at the PoolAction contract, however, do not return the excess funds to the user. This makes the maxAmountsIn values not the limit, but always the amount the user spends.
## Impact
Users that call balancer joins will not have their excess tokens returned in case they set a maxAmountIn bigger than the strictly necessary.
## Tools Used
Manual review
## Recommended Mitigation Steps
Make sure to return the funds not consumed by the Balancer vault during the join call. 

An interesting way do to such a thing would be to keep track of the tokens balances before and after the balancerVault.joinPool call. If the balance difference was smaller than the maxAmountIn for a token, then return to the user maxAmountIn - difference units of the token.
