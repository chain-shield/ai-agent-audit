# Vulnerability details

## Impact
The value of `newAccRewardPerShare` is lower than expected due to loss of precision in calculation.
## Proof of Concept
- Solidity rounds down the result of an integer division, and because of that, it is always recommended to multiply before dividing to avoid that precision loss. In the case of a prior division over multiplication, the final result may face serious precision loss as the first answer would face truncated precision and then multiplied to another integer.
- If we look deeply at the function `_newRewards()` we can see the `newAccRewardPerShare` calculation procedure is presented as: [here](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/ChefIncentivesController.sol#L995-L996)
```
995            newReward = (rawReward * pool.allocPoint) / _totalAllocPoint;
996            newAccRewardPerShare = (newReward * ACC_REWARD_PRECISION) / lpSupply;
```
- We can see there is a hidden division before a multiplication that makes round down the whole expression. This is bad as the precision loss can be significant,  which leads the value of `newAccRewardPerShare` is lower than expected. Furthermore, the mentioned error will escalate, especially when the `(rawReward * pool.allocPoint)` is bigger but close to the `_totalAllocPoint` value.
## Tools Used
Manual review
## Recommended Mitigation Steps
Consider modifying the fee shares calculation to prevent such precision loss and prioritize the multiplication over division:
```diff
995            newReward = (rawReward * pool.allocPoint) / _totalAllocPoint;
--- 996            newAccRewardPerShare = (newReward * ACC_REWARD_PRECISION) / lpSupply;
+++ 996            newAccRewardPerShare = (rawReward * pool.allocPoint * ACC_REWARD_PRECISION) / (_totalAllocPoint * lpSupply);
```
