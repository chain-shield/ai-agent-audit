# Vulnerability details

## Impact

The `token` in the smart contract is not required to comply with a specific interface. Particularly, the token does not need a price feed. 

Hence, it may be possible to provide unpriceable tokens in the CDPVault, which can lead to position manipulation and imbalanced debt positions. 

The issue is in this piece of code:

```
import {ICDPVaultBase, CDPVaultConstants, CDPVaultConfig} from "./interfaces/ICDPVault.sol";
...
interface IPoolV3Loop is IPoolV3 { function mintProfit(uint256 profit) external; }
...
CDPVault is AccessControl, Pause, Permission, ICDPVaultBase {
IERC20 public immutable token;

uint256 public immutable tokenScale;
...
constructor(CDPVaultConstants memory constants, CDPVaultConfig memory config) {
...
token = constants.token;
...
```

In the constructor of `CDPVault`, the contract expects the ERC-20 tokens from constants passed. However, there is no check if the token has a corresponding price feed in the oracle's smart contract.

## Recommended Mitigation Steps

Ensure that every token being provided to the `CDPVault` has a corresponding price feed in the oracle being used. 

This could be achieved by calling the oracle and checking the token's price immediately after it is provided. 

If the price is zero or some other sentinel value indicating non-support, reject the token during initialization. This way, unpriceable tokens will not be allowed into the system.
