# Vulnerability details


## Description

The `ChefIncentivesController` contract inherits from the `RecoverERC20` contract, which provides a function [`_recoverERC20`](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/RecoverERC20.sol#L19-L22) to recover any ERC20 tokens. The `ChefIncentivesController` contract uses this function in its [`recoverERC20` function](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/ChefIncentivesController.sol#L430-L432), allowing the owner to recover tokens from the contract. However, there is no check to ensure that the tokens being recovered are not reward tokens. This can lead to a situation where reward tokens are accidentally or maliciously recovered, disrupting the reward distribution mechanism.

The `MultiFeeDistribution` contract manages reward tokens and has a mapping [`isRewardToken`](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/MultiFeeDistribution.sol#L155) to track which tokens are reward tokens. The `ChefIncentivesController` contract should use this mapping to ensure that only non-reward tokens can be recovered.

> The relevant code in `ChefIncentivesController` is as follows:

```solidity
File: ChefIncentivesController.sol
430:     function recoverERC20(address tokenAddress, uint256 tokenAmount) external onlyOwner {
431:         _recoverERC20(tokenAddress, tokenAmount);
432:     }

```

The `_recoverERC20` function in `RecoverERC20` is as follows:

```solidity
File: RecoverERC20.sol
19:     function _recoverERC20(address tokenAddress, uint256 tokenAmount) internal {
20:         IERC20(tokenAddress).safeTransfer(msg.sender, tokenAmount);
21:         emit Recovered(tokenAddress, tokenAmount);
22:     }

```

## Impact
The ability to recover reward tokens can lead to significant financial loss for users and disrupt the core functionality of the reward distribution system. If reward tokens are recovered, users may lose their entitled rewards, and the integrity of the reward distribution mechanism can be compromised.

## Proof of Concept
1. The owner calls the `recoverERC20` function with a reward token address.
2. The `recoverERC20` function calls the `_recoverERC20` function from `RecoverERC20`.
3. The `_recoverERC20` function transfers the reward tokens to the owner, disrupting the reward distribution mechanism.

**Example:**
1. Assume `RDNT` is a reward token.
2. The owner calls `recoverERC20(RDNT, 1000)`.
3. The `recoverERC20` function transfers 1000 `RDNT` tokens to the owner, reducing the reward pool and affecting all users entitled to `RDNT` rewards.

## Tools Used
Manual review

## Recommended Mitigation Steps
Add a check in the `recoverERC20` function to ensure that the token being recovered is not a reward token. This can be done by checking the `isRewardToken` mapping in the `MultiFeeDistribution` contract.

```diff
function recoverERC20(address tokenAddress, uint256 tokenAmount) external onlyOwner {
+    require(!IMultiFeeDistribution(mfd).isRewardToken(tokenAddress), "Cannot recover reward tokens");
    _recoverERC20(tokenAddress, tokenAmount);
}
```

This ensures that only non-reward tokens can be recovered, preventing potential issues with the reward distribution mechanism.
