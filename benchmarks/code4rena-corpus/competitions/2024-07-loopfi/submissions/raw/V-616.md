# Vulnerability details

## Description
The claim function at the AuraVault contract works by calculating the amount of underlying assets a user has to send so he/she can claim certain amounts of BAL and AURA tokens.
This can be seen as follows:
```solidity
// @audit first it figures the amount of underlying asset to pay
// @audit amounts[0] represents the amount of BAL tokens and amounts[1] of AURA.
amountIn = _previewReward(amounts[0], amounts[1], _config);
// @audit the _previewReward function does no sanity checks.
...
// @audit then the contract sends BAL and AURA to the user
// Distribute BAL rewards
        IERC20(BAL).safeTransfer(_config.lockerRewards, (amounts[0] * _config.lockerIncentive) / INCENTIVE_BASIS);
        IERC20(BAL).safeTransfer(msg.sender, amounts[0]);
        
// @audit if the INFLATION_PROTECTION_TIME is not passed yet, the user will also receive AURA tokens, else the lockerRewards address receives the whole AURA balance.
if (block.timestamp <= INFLATION_PROTECTION_TIME) {
            IERC20(AURA).safeTransfer(_config.lockerRewards, (amounts[1] * _config.lockerIncentive) / INCENTIVE_BASIS);
            IERC20(AURA).safeTransfer(msg.sender, amounts[1]);
        } else {
            // after INFLATION_PROTECTION_TIME
            IERC20(AURA).safeTransfer(_config.lockerRewards, IERC20(AURA).balanceOf(address(this)));
        }
```

The function charges users for the AURA amounts they want to receive, even after INFLATION_PROTECTION_TIME, when it is impossible for the user to claim those. 

## Impact
Users who attempt to claim AURA tokens after the INFLATION_PROTECTION_TIME will be charged but not receive any AURA.

## Tools Used
Manual review
## Recommended Mitigation Steps
Make sure to add a sanity check that amounts[1] - that is the amount of desired Aura tokens -  cannot be different than zero if block.timestamp > INFLATION_PROTECTION_TIME.
