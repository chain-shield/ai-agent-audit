# Vulnerability details

`setCreditManagerDebtLimit()` allows setting a new debt limit for a credit manager, this can be exploited by a credit manager to borrow a tremendous amount, causing the pool's `_totalBorrowed` to increase, violating the invariant that the total borrowed amount should not change.

Because after updating the credit manager's debt limit, the `addCollateral()` function can be called on the credit manager with an enormous amount value, such as 115792089237316195423570985008687907853269984665640564039457584007913129639935. Inside `addCollateral()`, `_totalBorrowed` is increased by this amount.

While `setCreditManagerDebtLimit()` does not directly modify `_totalBorrowed`, it enables the credit manager to subsequently borrow a massive sum, indirectly leading to the increase in `_totalBorrowed`, violating the expected behavior: _"Borrowed amount should not_ change";

## Impact
After updating the credit manager's debt limit, the `addCollateral` function is called on the credit manager with a very large amount. Inside `addCollateral`, `_totalBorrowed` is increased by this amount.

So while `setCreditManagerDebtLimit` does not directly change `_totalBorrowed`, it allows the credit manager to subsequently borrow a large amount, thus indirectly leading to the increase in `_totalBorrowed`, violating the assertion.

```solidity
    function setCreditManagerDebtLimit(
        address creditManager,
        uint256 newLimit
    )
        external
        override
        controllerOnly // U:[LP-2C]
        nonZeroAddress(creditManager) // U:[LP-25A]
    {
        if (!_creditManagerSet.contains(creditManager)) {
            if (address(this) != ICreditManagerV3(creditManager).pool()) {
                revert IncompatibleCreditManagerException(); // U:[LP-25C]
            }
            _creditManagerSet.add(creditManager); // U:[LP-25D]
            emit AddCreditManager(creditManager); // U:[LP-25D]
        }
        // The line below is affected, as it sets the debt limit for the credit manager
        _creditManagerDebt[creditManager].limit = _convertToU128(newLimit); // <-- Affected line
        emit SetCreditManagerDebtLimit(creditManager, newLimit); // U:[LP-25D]
    }
```
The `setCreditManagerDebtLimit()` function itself is affected, particularly the line that updates the `_creditManagerDebt[creditManager].limi`t with the `newLimit` value. This is where the debt limit for the credit manager is set, which can be exploited if set to an extremely high value.

## Proof of Concept

1. Alice, the pool admin, calls `setCreditManagerDebtLimit()` in PoolV3.sol with the following parameters:

   * `creditManager` = `0x179b6b1cb6755e31` (address of the credit manager)
   * `newLimit` = `1000000000000000000000000` (a very high debt limit)

2. Inside `setCreditManagerDebtLimit()`, the following actions occur:

   * The function checks if the `creditManager` is already in the `_creditManagerSet`. If not, it adds the `creditManager` to the set and emits the `AddCreditManager` event.
   * The `_creditManagerDebt[creditManager].limit` is updated with the newLimit value using _convertToU128(newLimit).
   * The `SetCreditManagerDebtLimit` event is emitted.

3. Bob, a malicious credit manager, calls `deposit()` on their credit manager contract with the following parameter:

   * `amount` = `500000000000000000000000` (a very high amount)

4. Inside deposit(), the following actions occur:

   * The function checks if the credit manager has sufficient debt limit by comparing `amount` with `_creditManagerDebt[creditManager].limit`. Since Alice set a very high debt limit, this check passes.
   * The `_totalBorrowed` variable is increased by amount.
   * Other necessary updates and checks are performed.

5. As a result, the pool's `_totalBorrowed` is now inflated by the large `amount` value added by Bob's credit manager. This violates the expected invariant that the total borrowed amount should not change when setting the credit manager debt limit.

6. The inflated `_totalBorrowed` can lead to various issues, such as:

   * Breaking the pool's solvency if `_totalBorrowed` exceeds the total assets.
   * Disrupting the pool's accounting and other functions that rely on accurate `_totalBorrowed` values.
   * Potentially causing loss of funds for liquidity providers and other users if the inflated borrowed amount is not properly managed or repaid.

In this scenario, Alice's action of setting a very high debt limit using `setCreditManagerDebtLimit()` enables Bob's malicious credit manager to exploit the system by borrowing a large amount, inflating the pool's `_totalBorrowed`, and violating the expected behavior.

## Recommended Mitigation Steps
Check to ensure that the `newLimit` does not exceed the pool's `totalAssets()`. This prevents setting a debt limit that is higher than the total assets in the pool.

Also add a check to ensure that the `newLimit` does not exceed the maximum value of `uint128`. This prevents setting an extremely high debt limit that could cause issues with the `_convertToU128() function`.

```solidity
    function setCreditManagerDebtLimit(
        address creditManager,
        uint256 newLimit
    )
        external
        override
        controllerOnly // U:[LP-2C]
        nonZeroAddress(creditManager) // U:[LP-25A]
    {
        if (!_creditManagerSet.contains(creditManager)) {
            if (address(this) != ICreditManagerV3(creditManager).pool()) {
                revert IncompatibleCreditManagerException(); // U:[LP-25C]
            }
            _creditManagerSet.add(creditManager); // U:[LP-25D]
            emit AddCreditManager(creditManager); // U:[LP-25D]
        }
+       // Check if the new debt limit is within reasonable bounds
+       require(newLimit <= totalAssets(), "Debt limit exceeds total assets");
+       require(newLimit <= type(uint128).max, "Debt limit too high");
        _creditManagerDebt[creditManager].limit = _convertToU128(newLimit);
        emit SetCreditManagerDebtLimit(creditManager, newLimit); // U:[LP-25D]
    }
```
