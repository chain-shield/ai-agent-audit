# Vulnerability details

## Proof of Concept
The [_processEligibility](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/ChefIncentivesController.sol#L735) function is responsible for determining whether a user should be disqualified based on their eligibility status. Within the [afterLockUpdate](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/ChefIncentivesController.sol#L674-L684) function, `_processEligibility` is called as follows:
```solidity
function afterLockUpdate(address _user) external {
    if (eligibilityMode != EligibilityModes.DISABLED) {
        if (msg.sender != address(mfd)) revert NotMFD();
        bool isCurrentlyEligible = eligibleDataProvider.refresh(_user);
        if (isCurrentlyEligible) {
            _updateRegisteredBalance(_user);
        } else {
            _processEligibility(_user, isCurrentlyEligible, true);
        }
    }
}
```
In this code, `_processEligibility` is called with `_isEligible` set to false (as `isCurrentlyEligible` is `false`), and `_execute` set to true. 
If `_execute` is always `true`, the function `_processEligibility` will always perform disqualification actions (i.e., `stopEmissionsFor` and emitting `Disqualified`) whenever `issueBaseBounty` is true. This means that users might be disqualified every time `_processEligibility` is called, which could incorrectly affect eligible users if `issueBaseBounty` is set to true under incorrect conditions.


The `_processEligibility` function has the following logic:

```solidity
function _processEligibility(
    address _user,
    bool _isEligible,
    bool _execute
) internal returns (bool issueBaseBounty) {
    bool hasEligDeposits = hasEligibleDeposits(_user);
    uint256 lastDqTime = eligibleDataProvider.getDqTime(_user);
    bool alreadyDqd = lastDqTime != 0;

    if (!_isEligible && hasEligDeposits && !alreadyDqd) {
        issueBaseBounty = true;
    }
    if (_execute && issueBaseBounty) {
        stopEmissionsFor(_user);
        emit Disqualified(_user);
    }
}

```
If `_processEligibility` always returns `true` regardless of the actual conditions, the result will be:
1. Every call to `_processEligibility` within `afterLockUpdate` will result in the `stopEmissionsFor` function being executed.
2. This will disqualify users and emit a `Disqualified` event even if they are actually eligible.
## Impact
The impact of this issue is that users who are actually eligible will be incorrectly disqualified and will not receive rewards, potentially disrupting user rewards and system functionality.

## Tools Used
Manual
## Recommended Mitigation Steps
Modify the `_execute` parameter to set based on whether the user is not eligible (`!isCurrentlyEligible`) and has eligible deposits (`hasEligibleDeposits(_user)`). This ensures that disqualification actions are only performed when the user is actually ineligible and should be disqualified.
