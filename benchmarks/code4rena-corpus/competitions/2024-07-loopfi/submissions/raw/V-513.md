# Vulnerability details


## Proof of Concept

The contract integrates a logic that ensures users wait till the stipulated cooldown duration at the time of their unstake passes before the final withdrawal can be processed, this can be seen from here: https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L88-L101

```solidity
function unstake(address receiver) external {
  UserCooldown storage userCooldown = cooldowns[msg.sender];
  uint256 assets = userCooldown.underlyingAmount;

  if (block.timestamp >= userCooldown.cooldownEnd || cooldownDuration == 0) {
    //@audit
    userCooldown.cooldownEnd = 0;
    userCooldown.underlyingAmount = 0;

    silo.withdraw(receiver, assets);
  } else {
    revert InvalidCooldown();
  }
}

```

Now per [these functionalities](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L41-L53) and the [setCooldownDuration() function](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04cc9a53dc1a78223719164/src/StakingLPEth.sol#L130-L138) we can see that the cooldown logic is expected to be set on and off, reasons for switching this could be from a black swan event or whatsoever.

Now whenever users want to apply for a cool down of their assets, the `cooldownDuration` gets added [here](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L109), issue however is the fact that if the `cooldownDuration` was previously 10 days, and then gets reset to `0` after a user has already placed an attempt at cooldown a day before, which means they should have 9 more days left to process their unstake, they can easily sidestep the 9 days wait due to the way the conditional check is written [here](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53d.c1a78223719164/src/StakingLPEth.sol#L92).

### Coded POC

Attach this test at the end of [StakingLP.t.sol](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/test/unit/StakingLP.t.sol#L117-L148).

```solidity
function test_bypass_cooldown_with_reset_duration() public {
  stakingLpEth.setCooldownDuration(10 days);
  test_deposit_user1();
  _sendRewards();
  vm.startPrank(user1);

  // User initiates a cooldown
  stakingLpEth.cooldownShares(stakingLpEth.balanceOf(user1));

  // At this point, the user has 10 days until their cooldown ends
  // we can confirm by the below
  // Try to unstake after 2 days from the cooldown attempt
  vm.warp(block.timestamp + 2 days);
  vm.expectRevert(StakingLPEth.InvalidCooldown.selector);
  stakingLpEth.unstake(user1);
  vm.stopPrank();

  // Admin turns off the cooldown mechanism for future unstakes
  stakingLpEth.setCooldownDuration(0);
  vm.startPrank(user1);
  // Now, despite having initiated a cooldown with a 10-day duration,
  // the user can immediately withdraw their assets, sidestepping the previous cooldownDuration set for them

  stakingLpEth.unstake(user1);
  // Check that the user received their funds
  assertApproxEqAbs(liquidityPool.balanceOf(user1), 0.199999999999999999 ether, 1);
  vm.stopPrank();
}

```

Use the following command to run the POC:

````
forge test --match-test test_bypass_cooldown_with_reset_duration -vv```
````

## Impact

Intended functionality of having users wait for `cooldownDuration` is somewhat broken, since naturally the `cooldownDuration` could be made active to curb users who are trying to come make risk free integration with the protocol, but having them wait for a duration is a risk most would not be willing to take, but while waiting the users can directly sidestep this if it gets reset to zero.

## Recommended Mitigation Steps

Instead of having the `if (block.timestamp >= userCooldown.cooldownEnd || cooldownDuration == 0)` check, break it into two, if at all `userCooldown.cooldownEnd != 0` then enforce `block.timestamp` other wise just withdraw from the silo
