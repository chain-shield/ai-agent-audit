# Vulnerability details

## Proof of Concept
1. Available Rewards Calculation:

If `depositedRewards` equals `accountedRewards`, the value of `availableRewards` will be zero. Here’s how it impacts the `_newRewards` function:
```solidity
uint256 rewards = availableRewards(); // availableRewards = depositedRewards - accountedRewards
```
Since `depositedRewards` equals `accountedRewards`, `availableRewards` will be zero:
```solidity
availableRewards = depositedRewards - accountedRewards = 0
```
2. Raw Reward Calculation:

```solidity
uint256 rawReward = duration * rewardsPerSecond;
```
This calculates the raw reward based on the time elapsed and reward rate. However, since `availableRewards` is zero, the raw reward might be set to zero if `rawReward` exceeds `availableRewards`:
```solidity
if (rewards < rawReward) {
    rawReward = rewards; // rawReward will be set to 0 if rewards is 0
}
```
3. New Reward Calculation:
```solidity
newReward = (rawReward * pool.allocPoint) / _totalAllocPoint;
```
If `rawReward` is zero, then `newReward` will also be zero:
```solidity
newReward = (0 * pool.allocPoint) / _totalAllocPoint = 0
```
4. New Accumulated Reward Per Share Calculation:
```solidity
newAccRewardPerShare = (newReward * ACC_REWARD_PRECISION) / lpSupply;
```
Since `newReward` is zero, `newAccRewardPerShare` will also be zero:
```solidity
newAccRewardPerShare = (0 * ACC_REWARD_PRECISION) / lpSupply = 0
```
### Bug Analysis
1. Update Pool Function (`_updatePool`):
```solidity

    function _updatePool(VaultInfo storage pool, uint256 _totalAllocPoint) internal {
        uint256 timestamp = block.timestamp;
        uint256 endReward = endRewardTime();
        if (endReward <= timestamp) {
            timestamp = endReward;
        }
        if (timestamp <= pool.lastRewardTime) {
            return;
        }

        (uint256 reward, uint256 newAccRewardPerShare) = _newRewards(pool, _totalAllocPoint);
        accountedRewards = accountedRewards + reward;
        pool.accRewardPerShare = pool.accRewardPerShare + newAccRewardPerShare;
        pool.lastRewardTime = timestamp;
    }
```
This function calculates new rewards and updates `accountedRewards` and `pool.accRewardPerShare`. If `depositedRewards` equals `accountedRewards`, `availableRewards` will be zero. Thus, `_newRewards` will return zero for `reward` and `newAccRewardPerShare`. Consequently, `accountedRewards` will not be updated with new `rewards`, and `pool.accRewardPerShare` will remain unchanged even though new rewards might have accumulated.
*Potential Issue* :
This results in `accountedRewards` not being incremented, and `pool.accRewardPerShare` remains unchanged. Therefore, even though time has passed and rewards should be updated, no actual reward is recorded or reflected in the pool.

2. Pending Rewards Function (`pendingRewards`):
```solidity
    function pendingRewards(address _user, address[] memory _tokens) public view returns (uint256[] memory) {
        uint256[] memory claimable = new uint256[](_tokens.length);
        uint256 length = _tokens.length;
        for (uint256 i; i < length; ) {
            address token = _tokens[i];
            VaultInfo storage pool = vaultInfo[token];
            UserInfo storage user = userInfo[token][_user];
            uint256 accRewardPerShare = pool.accRewardPerShare;
            if (block.timestamp > pool.lastRewardTime) {
                (, uint256 newAccRewardPerShare) = _newRewards(pool, totalAllocPoint);
                accRewardPerShare = accRewardPerShare + newAccRewardPerShare;
            }
            claimable[i] = (user.amount * accRewardPerShare) / ACC_REWARD_PRECISION - user.rewardDebt;
            unchecked {
                i++;
            }
        }
        return claimable;
    }
```
This function calculates the rewards pending for a user by considering the `accRewardPerShare`. If `availableRewards` was zero in the past (when `depositedRewards` was equal to `accountedRewards`), and then new rewards are calculated later, `pool.accRewardPerShare` might not accurately reflect the new rewards. If `pool.accRewardPerShare` was not updated correctly due to the zero `newAccRewardPerShare`, then the claimable rewards calculated might be incorrect.
*Potential Issue* :
*Example Scenario*
- `depositedRewards`: $10,000$ tokens
- `accountedRewards`: $10,000$ tokens
- `availableRewards`: $depositedRewards$ - $accountedRewards$ = $10,000 - 10,000 = 0$
- Pool Total Supply (`lpSupply`): $1,000$ tokens
- Pool Allocation Point (`pool.allocPoint`): $100$
- Total Allocation Points (`_totalAllocPoint`): $1,000$
- Rewards Per Second (`rewardsPerSecond`): $5$ tokens per second
- Accumulated Reward Per Share (`accRewardPerShare`): $0$ initially
-Assume 10 seconds have passed since the last reward update.

Final Outcome
Pool Reward Per Share (`accRewardPerShare`):
Remains at 0 because no new rewards were added.
Pending Rewards Calculation: 
Users’ pending rewards are calculated using the unchanged `accRewardPerShare`. If users have accrued rewards based on the pool’s allocation, they will see incorrect values due to the static reward per share.
Example User Calculation
User Info:

`user.amoun`t: $100$ tokens
`user.rewardDebt`: $0$
Claimable Rewards:
```solidity
claimable[i] = (user.amount * accRewardPerShare) / ACC_REWARD_PRECISION - user.rewardDebt;
claimable[i] = (100 * 0) / 1e18 - 0 = 0
```
In this scenario, even though rewards should have been distributed based on the elapsed time, the system incorrectly shows zero claimable rewards because the `accRewardPerShare` did not update due to zero available rewards. This can lead to users being unfairly deprived of their rightful rewards.

## Impact
Impact on `_updatePool`: 
When `depositedRewards` equals `accountedRewards`, `availableRewards` is zero. Consequently, `_newRewards` returns zero for both `reward` and `newAccRewardPerShare`.
This results in `accountedRewards` not being incremented, and `pool.accRewardPerShare` remains unchanged. Therefore, even though time has passed and rewards should be updated, no actual reward is recorded or reflected in the pool.
Impact on `pendingRewards`:
The `pendingRewards` function relies on `accRewardPerShare` to compute the rewards a user can claim.
If `newAccRewardPerShare` was zero (because `availableRewards` was zero), the `accRewardPerShare` for the pool does not update correctly. This results in incorrect calculations for pending rewards, potentially causing users to receive inaccurate reward amounts.

## Recommended Mitigation Steps
Ensure that reward calculations in `_newRewards` are robust even when `depositedRewards` equals `accountedRewards`. One approach is to verify that the contract correctly accounts for scenarios where rewards might be zero or handle the case explicitly.
