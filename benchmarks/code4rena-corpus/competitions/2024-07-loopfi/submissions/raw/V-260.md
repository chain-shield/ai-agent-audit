# Vulnerability details

## Description

The `StakingLPEth` contract implements a staking mechanism with a cooldown period for withdrawals. Two key functions, [`cooldownAssets()`](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L104-L113) and [`cooldownShares()`](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/StakingLPEth.sol#L117-L126), allow users to initiate the cooldown process for their assets or shares respectively. These functions are designed to start a cooldown period before users can claim their underlying assets.

The contract maintains a `UserCooldown` struct for each user, which includes a `cooldownEnd` timestamp and an `underlyingAmount`. When a user calls either `cooldownAssets()` or `cooldownShares()`, the contract updates these values:

```solidity

112:         _withdraw(msg.sender, address(silo), msg.sender, assets, shares);

```

The issue lies in the fact that these functions do not check whether a cooldown period is already in progress for the user. As a result, users can call these functions repeatedly, each time resetting their `cooldownEnd` to a new future timestamp and increasing their `underlyingAmount`. This allows users to indefinitely extend their cooldown period and accumulate larger amounts in their `underlyingAmount` without ever reaching the end of the cooldown period.

This behavior contradicts the intended purpose of the cooldown mechanism, which is to enforce a waiting period before asset withdrawal. It potentially allows users to manipulate the system by continuously delaying their withdrawal while still participating in other aspects of the protocol.

## Impact
Users can extend the cooldown period indefinitely by repeatedly calling `cooldownAssets()` or `cooldownShares()` before the cooldown period ends. This could allow users to manipulate the cooldown mechanism and delay the claiming of their assets, potentially leading to an unfair advantage over other users who are not aware of this issue. This could undermine the intended incentive structure and lead to an uneven distribution of rewards among stakers.


## Proof of Concept

1. Alice stakes 100 tokens and calls `cooldownAssets(100)`.
   - `cooldowns[Alice].cooldownEnd` is set to `block.timestamp + cooldownDuration`
   - `cooldowns[Alice].underlyingAmount` is set to 100

2. Just before the cooldown period ends, Alice calls `cooldownAssets(50)` again.
   - `cooldowns[Alice].cooldownEnd` is reset to a new `block.timestamp + cooldownDuration`
   - `cooldowns[Alice].underlyingAmount` is increased to 150

3. Alice repeats step 2 indefinitely, always extending her cooldown period and increasing her underlying amount.

4. At any point, Alice can stop extending the cooldown and wait for it to finish, then withdraw a larger amount than initially staked.

## Recommended Mitigation Steps

To fix this issue, implement a check in both `cooldownAssets()` and `cooldownShares()` to ensure that a user cannot start a new cooldown period if one is already in progress. Here's a suggested fix:

```diff
function cooldownAssets(uint256 assets) external ensureCooldownOn returns (uint256 shares) {
    if (assets > maxWithdraw(msg.sender)) revert ExcessiveWithdrawAmount();
    
+   if (cooldowns[msg.sender].cooldownEnd > block.timestamp) revert CooldownAlreadyStarted();
    
    shares = previewWithdraw(assets);

    cooldowns[msg.sender].cooldownEnd = uint104(block.timestamp) + cooldownDuration;
    cooldowns[msg.sender].underlyingAmount += uint152(assets);

    _withdraw(msg.sender, address(silo), msg.sender, assets, shares);
}
```

Apply a similar change to the `cooldownShares()` function. This ensures that users can only start a new cooldown period after their current one has expired, maintaining the integrity of the cooldown mechanism.
