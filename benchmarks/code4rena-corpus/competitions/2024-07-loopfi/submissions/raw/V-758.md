# Vulnerability details

## Impact
The `join()` function, when interacting with a Balancer pool via the balancerVault.joinPool() method, fails to appropriately handle cases where a user sends ETH instead of WETH. This oversight is critical, as the function neglects to replace the WETH address in the assets array with the zero address (0x0), leading to scenarios where the Balancer Vault does not correctly wrap ETH into WETH. This fundamental mismanagement can precipitate transaction failures or, more gravely, the irreversible loss of user funds.


When a user intends to contribute ETH to a Balancer pool, the protocol provides a mechanism to automatically convert the ETH into WETH. However, this requires the assets array to contain the zero address (0x0) in place of the WETH address. The `join()` function, tasked with preparing and dispatching the necessary parameters to the balancerVault.joinPool() function, should ensure that any WETH address in the assets array is replaced with 0x0 whenever ETH is involved.

## Proof of Concept
Alice, a user, initiates a transaction to join a Balancer pool by sending 50 ETH. She expects this ETH to be converted into WETH and deposited into the pool in exchange for pool tokens.
Key Details:

Protocol: The transaction is intended for a Balancer pool.
Arguments: The encoded parameters include the poolId, an assets array (which erroneously includes the WETH address), assetsIn, and maxAmountsIn.
msg.value: Alice sends 50 ETH along with the transaction.
During the execution of the `_balancerJoin()` function:

Assets Array: The assets array incorrectly retains the WETH address instead of replacing it with 0x0.
Token Approvals: The function attempts to approve the maximum amounts for the tokens in the assets array, including the WETH address, which is erroneous.
JoinPoolRequest: The function then calls balancerVault.joinPool() with the incorrect assets array.
Failure in `balancerVault.joinPool():`

ETH Handling: The Balancer Vault, expecting either WETH or 0x0 to represent ETH, fails to recognize the 50 ETH sent by Alice due to the incorrect assets array.
Result: The transaction fails or reverts, as the Vault cannot wrap the ETH into WETH.
Because the join() function did not correctly substitute the WETH address with 0x0, Alice's 50 ETH is not processed correctly by the Balancer Vault. This could lead to the ETH remaining in the contract, unwrapped and unused, leaving Alice without the pool tokens she anticipated and with her funds potentially locked or lost.

Scenario Where WETH Is in the assets Array
If a user intends to join a Balancer pool that accepts WETH, the assets array in the joinPool() function call typically includes the address of the WETH token. For instance, depositing 10 WETH would result in an assets array that looks like [WETH_ADDRESS, OTHER_TOKEN_ADDRESS]. This configuration informs the Balancer Vault that the user is sending WETH tokens.

However, if ETH is sent instead of WETH, the Balancer Vault allows the user to send ETH directly, which it then automatically wraps into WETH. To signal that ETH is being sent, the assets array must contain the zero address (0x0) in place of the WETH address. Failure to replace the WETH address with 0x0 causes the Vault to expect WETH but receive ETH, leading to a failure in the deposit process. This might result in a transaction revert or the ETH becoming stuck in the contract.

## Recommended Mitigation Steps
To mitigate this issue, it is essential to ensure that the join() function correctly handles the substitution of WETH with 0x0 when ETH is sent. The following modifications are recommended:

Amend the `_balancerJoin()` Function: Introduce a check to determine if any asset in the assets array is WETH and if msg.value > 0. If both conditions are met, replace the WETH address in the assets array with 0x0 before invoking balancerVault.joinPool().

Sanity Check: Before calling balancerVault.joinPool(), include a sanity check to verify that the assets array accurately reflects the use of ETH and that msg.value corresponds to the intended ETH deposit.

For example, if Alice sends 50 ETH, the assets array should appear as [0x0, OTHER_TOKEN_ADDRESS] before the joinPool() function is called.

By implementing these changes, the contract will ensure that ETH is correctly handled, preventing transaction failures and safeguarding user funds from potential loss.
