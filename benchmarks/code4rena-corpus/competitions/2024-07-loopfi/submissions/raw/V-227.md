# Vulnerability details

## Impact
Detailed description of the impact of this finding.

The cooldownAssets and cooldownShares functions in the StakingLPEth contract allow users to initiate a cooldown for withdrawing assets or shares. 

However, these functions do not reset the user’s previous cooldown state before setting a new one. 

This oversight can lead to an accumulation of cooldown periods and underlying amounts if these functions are called multiple times before the existing cooldown period expires.

User Funds Access: 
Users may experience delayed access to their assets because of extended cooldown periods. 
This unintended behavior can disrupt users’ financial plans and lead to a loss of trust in the platform.

Financial Risk: 
The inability to access funds promptly in volatile markets can expose users to financial risk, as they may miss opportunities to sell or reposition assets.

Operational Overhead: 
Increased user inquiries and support requests due to confusion over the unexpected accumulation of cooldown periods.
## Proof of Concept

Consider the following scenario:

1. Initial Cooldown: A user calls cooldownAssets to initiate a cooldown for 100 assets. This sets the cooldownEnd to block.timestamp + cooldownDuration and underlyingAmount to 100.

2. Additional Cooldown Call: Before the initial cooldown period expires, the user calls cooldownAssets again for another 50 assets.

3. Accumulated State: Instead of resetting, the underlyingAmount becomes 150, and the cooldownEnd is extended by another full cooldownDuration from the current time, potentially delaying access to the original 100 assets.

This can be represented in a simple test scenario:

```sol
// Initial cooldown for 100 assets
stakingContract.cooldownAssets(100);

// Before cooldown ends, initiate another cooldown for 50 assets
stakingContract.cooldownAssets(50);

// Expected state
// cooldownEnd = currentTime + cooldownDuration
// underlyingAmount = 50

// Actual state
// cooldownEnd = newCurrentTime + cooldownDuration
// underlyingAmount = 150
```

## Recommended Mitigation Steps
To mitigate this issue, reset the user’s cooldown state before setting a new one, ensuring each cooldown period is independent and accurately reflects the user’s current intent:

```sol
function cooldownAssets(uint256 assets) external ensureCooldownOn returns (uint256 shares) {
    if (assets > maxWithdraw(msg.sender)) revert ExcessiveWithdrawAmount();

    shares = previewWithdraw(assets);

    // Reset user's cooldown state before setting a new one
    UserCooldown storage userCooldown = cooldowns[msg.sender];
    userCooldown.cooldownEnd = uint104(block.timestamp) + cooldownDuration;
    userCooldown.underlyingAmount = uint152(assets);

    _withdraw(msg.sender, address(silo), msg.sender, assets, shares);
}

function cooldownShares(uint256 shares) external ensureCooldownOn returns (uint256 assets) {
    if (shares > maxRedeem(msg.sender)) revert ExcessiveRedeemAmount();

    assets = previewRedeem(shares);

    // Reset user's cooldown state before setting a new one
    UserCooldown storage userCooldown = cooldowns[msg.sender];
    userCooldown.cooldownEnd = uint104(block.timestamp) + cooldownDuration;
    userCooldown.underlyingAmount = uint152(assets);

    _withdraw(msg.sender, address(silo), msg.sender, assets, shares);
}
```
