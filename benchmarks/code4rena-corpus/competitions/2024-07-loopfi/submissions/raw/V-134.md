# Vulnerability details

## Impact
The current implementation uses the transfer recipient (`to`) as the spender in the ERC20 permit approval which is incorrect. This error prevents the contract from successfully transferring tokens using the permit mechanism, as the contract itself is not granted the necessary approval. As a result, all transfers using the PERMIT approval type will fail, rendering this feature non-functional.

## Proof of Concept
Let's  look at tthe `_transferFrom` function: https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/proxy/TransferAction.sol#L65-L83

```solidity
} else if (params.approvalType == ApprovalType.PERMIT) {
    // Consume a standard ERC20 permit message
    IERC20Permit(token).safePermit(
        from,
        to,  <----------
        params.approvalAmount,
        params.deadline,
        params.v,
        params.r,
        params.s
    );
    IERC20(token).safeTransferFrom(from, to, amount);
}
```

Here, the `safePermit` function is called with `to` as the second argument, which represents the spender. However, `to` is actually the recipient of the transfer, not the entity that should be approved to spend tokens. The correct spender should be the contract itself (`address(this)`), as it's the one executing the `transferFrom` operation.

This mistake means that the subsequent `safeTransferFrom` call will fail because the contract (`address(this)`) has not been granted approval to spend tokens on behalf of the `from` address.

## Recommended Mitigation Steps
Replace the `to` address with `address(this)` in the `safePermit` call:

```diff
} else if (params.approvalType == ApprovalType.PERMIT) {
    // Consume a standard ERC20 permit message
    IERC20Permit(token).safePermit(
        from,
-       to,
+       address(this),
        params.approvalAmount,
        params.deadline,
        params.v,
        params.r,
        params.s
    );
    IERC20(token).safeTransferFrom(from, to, amount);
}
```
