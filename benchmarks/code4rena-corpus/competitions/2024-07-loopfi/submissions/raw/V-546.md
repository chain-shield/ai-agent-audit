# Vulnerability details

## Impact
When users attempt to cool down additional shares while an existing cooldown is in progress, the entire cooldown period is reset for all shares, including those already in the cooldown process.This can lead to extended lock-up periods for users, potentially beyond their expectations

## Proof of Concept
The vulnerability lies in the `cooldownShares` function:
```
function cooldownShares(uint256 shares) external ensureCooldownOn returns (uint256 assets) {
    if (shares > maxRedeem(msg.sender)) revert ExcessiveRedeemAmount();

    assets = previewRedeem(shares);

    cooldowns[msg.sender].cooldownEnd = uint104(block.timestamp) + cooldownDuration;
    cooldowns[msg.sender].underlyingAmount += uint152(assets);

    _withdraw(msg.sender, address(silo), msg.sender, assets, shares);
}

```
Consider the following scenario:

- The cooldown duration is set to 30 days.
- User A calls cooldownShares with 100 shares on Day 1.
- On Day 20, User A decides to cool down an additional 50 shares.
- Upon calling cooldownShares again, the cooldownEnd is reset to 30 days from Day 20.
- User A now has to wait until Day 50 to unstake any shares, including the initial 100 shares that have already been cooling for 20 days

## Recommended Mitigation Steps
To address this issue, consider implementing the following changes:

Modify the UserCooldown struct to track multiple cooldown entries:
```
struct CooldownEntry {
    uint104 cooldownEnd;
    uint256 assets;
}

struct UserCooldown {
    CooldownEntry[] entries;
    uint256 totalAssets;
}

```
Update the cooldownShares function to add a new cooldown entry instead of resetting the existing one:
```
function cooldownShares(uint256 shares) external ensureCooldownOn returns (uint256 assets) {
    if (shares > maxRedeem(msg.sender)) revert ExcessiveRedeemAmount();

    assets = previewRedeem(shares);

    UserCooldown storage userCooldown = cooldowns[msg.sender];
    userCooldown.entries.push(CooldownEntry({
        cooldownEnd: uint104(block.timestamp) + cooldownDuration,
        assets: assets
    }));
    userCooldown.totalAssets += assets;

    _withdraw(msg.sender, address(silo), msg.sender, assets, shares);
}

```
Modify the unstake function to allow partial unstaking of matured cooldown entries:
```
function unstake(address receiver) external {
    UserCooldown storage userCooldown = cooldowns[msg.sender];
    uint256 assetsToWithdraw = 0;

    for (uint i = 0; i < userCooldown.entries.length; i++) {
        if (block.timestamp >= userCooldown.entries[i].cooldownEnd) {
            assetsToWithdraw += userCooldown.entries[i].assets;
            userCooldown.entries[i] = userCooldown.entries[userCooldown.entries.length - 1];
            userCooldown.entries.pop();
            i--;
        }
    }

    if (assetsToWithdraw > 0) {
        userCooldown.totalAssets -= assetsToWithdraw;
        silo.withdraw(receiver, assetsToWithdraw);
    } else {
        revert InvalidCooldown();
    }
}

```
These changes allow users to cool down additional shares without affecting their existing cooldown periods. Each cooldown entry is tracked separately, and users can unstake matured assets without waiting for all their cooled shares to complete the cooldown period.
