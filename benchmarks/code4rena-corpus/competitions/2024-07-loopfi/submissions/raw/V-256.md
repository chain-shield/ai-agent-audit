# Vulnerability details

`repayCreditAccount()` logic can lead to incorrect debt reduction when the `repaidAmount` parameter exceeds `type(uint128).max`. This problem arises from the conversion of `repaidAmount` to `uint128` before updating the `_totalDebt.borrowed` and `cmDebt.borrowed` variables.
```solidity
File: src/PoolV3.sol

540:         uint128 repaidAmountU128 = repaidAmount.toUint128();

572:         _totalDebt.borrowed -= repaidAmountU128; // U:[LP-14B,14C,14D]
573:         cmDebt.borrowed = cmBorrowed - repaidAmountU128; // U:[LP-14B,14C,14D]
```
The root cause of the issue is the conversion of `repaidAmount` from `uint256` to `uint128` using the `toUint128()` on [line 540](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L540). This conversion can lead to a loss of precision if `repaidAmount` exceeds `type(uint128).max`.

The affected [lines, 572 - 573](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L572-L573), use the `repaidAmountU128` variable to update the `_totalDebt.borrowed` and `cmDebt.borrowed` variables, respectively. Due to the precision loss during the conversion, these updates may result in incorrect debt reduction.

## Impact
**1. Highest Impact:** If an attacker crafts a `repaidAmount` value that exceeds `type(uint128).max`, the conversion to `uint128` will result in a loss of precision. This can lead to a significant underestimation of the actual debt reduction, allowing the attacker to manipulate the pool's debt state and potentially steal funds.

**2. Lesser Impact:** Even in the absence of an active attack, the precision loss can cause inconsistencies in the pool's debt calculations, leading to incorrect accounting and potential financial losses for the pool and its users.

## Proof of Concept
Consider the following scenario:

1. An attacker, Alice, has borrowed a large amount of funds from the pool through a credit manager.
2. Alice calls the `repayCreditAccount()` function with a crafted `repaidAmount` value that exceeds `type(uint128).max`.
3. Inside the function, `repaidAmount` is converted to `uint128` and stored in `repaidAmountU128` ([PoolV3.sol:540](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L540)).
4. The `_totalDebt.borrowed` and `cmDebt.borrowed` variables are updated using `repaidAmountU128` ([PoolV3.sol:572-573](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L572-L573)).
5. Due to the precision loss during the conversion, the actual debt reduction is much smaller than the intended `repaidAmount`.
6. As a result, Alice's debt is not fully repaid, and the pool's debt state becomes inconsistent.

## Recommended Mitigation Steps
1. Use a larger data type, such as `uint256`, for all debt calculations to avoid precision loss.
2. Ensure that the `repaidAmount` parameter is validated and sanitized before using it in debt calculations.
```diff
- uint128 repaidAmountU128 = repaidAmount.toUint128();
+ uint256 repaidAmount256 = repaidAmount;

// ...

- _totalDebt.borrowed -= repaidAmountU128;
+ _totalDebt.borrowed -= repaidAmount256;

- cmDebt.borrowed = cmBorrowed - repaidAmountU128;
+ cmDebt.borrowed = cmBorrowed - repaidAmount256;
```
