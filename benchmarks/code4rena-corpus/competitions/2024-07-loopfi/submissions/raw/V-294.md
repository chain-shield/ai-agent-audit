# Vulnerability details

## Impact

Both the function `deposit` and `mint` call `_deposit`. However, both calling function never check if the assets are lower than `maxDeposit` or `maxMint`. A technical limit like uint256.max is not a deliberate or economically driven global lending limit (which is implied here); rather, it's a technical constraint imposed by the Ethereum's architecture. A global lending limit, in contrast, would typically be set based on risk management considerations and liquidity requirements. Hence, a greater risk exists.

## Proof of Concept

The vulnerability arises from the protocol's deposit functions (`deposit` and `mint`), where there is an absence of checks against the global lending limit based on the total assets lent. Here’s a breakdown:

- The `deposit` function computes the number of shares to be issued based on the assets received after fees and proceeds to deposit these assets (currently the same value is returned). The critical oversight is that it does not verify if adding these assets will exceed the global lending limit, rather there is no upper limit. That means, the max value which can fit in uint256.max.

```solidity
function deposit(
        uint256 assets,
        address receiver
    )
        public
        override(ERC4626, IERC4626)
        whenNotPaused // U:[LP-2A]
        nonReentrant // U:[LP-2B]
        nonZeroAddress(receiver) // U:[LP-5]
        returns (uint256 shares)
    {
        uint256 assetsReceived = _amountMinusFee(assets); // U:[LP-6]
        shares = _convertToShares(assetsReceived); // U:[LP-6]
        _deposit(receiver, assets, assetsReceived, shares); // U:[LP-6]
    }
```

- In the `mint` function, assets corresponding to the requested number of shares are calculated and deposited without a preliminary check to ensure these additional assets do not breach the lending cap (currently implied at uint256.max). To be honest, there should be an upper bound.

```solidity
function mint(
        uint256 shares,
        address receiver
    )
        public
        override(ERC4626, IERC4626)
        whenNotPaused // U:[LP-2A]
        nonReentrant // U:[LP-2B]
        nonZeroAddress(receiver) // U:[LP-5]
        returns (uint256 assets)
    {
        uint256 assetsReceived = _convertToAssets(shares); // U:[LP-7]
        assets = _amountWithFee(assetsReceived); // U:[LP-7]
        _deposit(receiver, assets, assetsReceived, shares); // U:[LP-7]
    }
```

This faulty logic is evident from the given code snippets, where no reference or comparison against a defined global lending limit is visible, neither in terms of total assets nor in terms of the shares representing those assets.

## Recommended Mitigation Steps

1. **Define Global Lending Limit**: Clearly define a global lending limit in terms of total assets that can be safely lent out by the protocol.
2. **Implement Check in Deposit Functions**: In the `deposit`, `depositWithReferral`, and `mint` functions, implement a check prior to the asset deposit to ensure that adding the new assets will not exceed the global lending limit.
