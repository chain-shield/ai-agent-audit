# Vulnerability details

## Impact
The PoolQuotaKeeperV3 calculates a wrong quota revenue if there are more than one credit managers per pool. In that case the state of the pool diverges form the actual state. The `calcQuotaRevenueAccrued` function [1](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L736-L738) would return a wrong value. This affects `expectedLiquidity()` [2](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L208-L210) and `totalAssets()` [3](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L223-L225).

## Description
The `PoolQuotaKeeperV3.sol` calculates the quota revenue based on `creditManagerBorrowed(..)` of the credit manager set. The credit manager is a one-to-one mapping. It maps a token with a credit manager [4](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/quotas/PoolQuotaKeeperV3.sol#L63).
The `PoolV3.sol` on the other hand allows for a one-to-many connection of many credit managers [5](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L103-L104). 

The `poolQuotaRevenue` and `updateRates` functions both begin by retrieving a rate per token. The `poolQuotaRevenue` uses a cached value, while the `updateRates` fetches a new value from the `GaugeV3`. Only looking at the `updateRates` function, it then calculates the new `quotaRevenue` [6](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/quotas/PoolQuotaKeeperV3.sol#L210C13-L210C117):
```
quotaRevenue += (IPoolV3(pool).creditManagerBorrowed(creditManagers[token]) * rate) / PERCENTAGE_FACTOR;
```

It fetches the amount borrowed for the configured credit manager and multiplies it with the rate. Afterwards it updates the pools quota revenue [7](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/quotas/PoolQuotaKeeperV3.sol#L219). The pool uses the quota revenue to calculate the `totalAssets()` ([totalAssets()](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L223-L225) => [expectedLiquidity()](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L208-L210) => [_calcQuotaRevenueAccrued()](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L717-L721) => [_calcQuotaRevenueAccrued(uint256 timestamp)](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L736-L738)).

Therefore, it is crucial to have an accurate calculation of the quota revenue. The current version fails to compute the correct quota revenue when there is more than one credit manager (or if the `PoolQuotaKeeperV3` is not configured properly).


## Proof of Concept
The POC is based on existing tests. It inherits from the `TestBase`.

First create two vaults:
```
CDPVault vaultA = createCDPVault(token, 5_000_000 ether, 0, 1.25 ether, 1.0 ether, 0);
CDPVault vaultB = createCDPVault(token, 5_000_000 ether, 0, 1.25 ether, 1.0 ether, 0);
```

Create a gauge and add both vaults. Notice that `createGaugeAndSetGauge` is part of `TestBase.sol`. It create a gauge, configures it and adds the vaultA. Afterwards the vaultB is added (this will overwrite vaultA [see](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/quotas/PoolQuotaKeeperV3.sol#L238-L247)):
```
createGaugeAndSetGauge(address(vaultA)); 
quotaKeeper.setCreditManager(address(token), address(vaultB));
```

Then create a position on vaultA, as `borrowerA`:
```
token.approve(address(vaultA), amount);
vaultA.modifyCollateralAndDebt(borrowerA, borrowerA, borrowerA, toInt256(amount), toInt256((amount * 75) / 100));
```

Afterwards update the quota revenue:
```
vm.prank(address(gauge));
quotaKeeper.updateRates();
```

Next create the second position, and update the rate again:
```
token.approve(address(vaultB), amount);
vaultB.modifyCollateralAndDebt(borrowerB, borrowerB, borrowerB, toInt256(amount), toInt256((amount * 75) / 100));

vm.prank(address(gauge));
quotaKeeper.updateRates();
```

This will produce the following logs:
- quotaRevenue before adding the first position:  0
- quotaRevenue after adding the first position:  0
- quotaRevenue after adding the second position:  375000000000000000000 [3.75e23]

This demonstrates that the quota revenue is not correctly calculated after the first vault borrows from the pool. Although it is updated after the second vault creates a position, the value remains incorrect. It should be 3.75e23 per vault, resulting in a total of 7.5e23.

#### Full POC:
This should be placed in `src/test/poc.t.sol`:
```
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.19;

import {CDPVault} from "../CDPVault.sol";
import {toInt256} from "../utils/Math.sol";

import {TestBase} from "./TestBase.sol";

import {console} from "forge-std/console.sol";
import {StdCheats} from "forge-std/StdCheats.sol";

contract POCTest is TestBase {
    address borrowerA = address(1337);
    address borrowerB = address(1338);

    uint256 amount = 0.5e24;

    function test_poc() public {
        // setup
        vm.label(borrowerA, "borrowerA");
        vm.label(borrowerB, "borrowerB");

        StdCheats.deal(address(token), borrowerA, amount);
        StdCheats.deal(address(token), borrowerB, amount);

        CDPVault vaultA = createCDPVault(token, 5_000_000 ether, 0, 1.25 ether, 1.0 ether, 0);
        CDPVault vaultB = createCDPVault(token, 5_000_000 ether, 0, 1.25 ether, 1.0 ether, 0);

        // create gauge and add vaultA
        createGaugeAndSetGauge(address(vaultA)); 
        // add vaultB
        quotaKeeper.setCreditManager(address(token), address(vaultB));

        // update rates
        vm.prank(address(gauge));
        quotaKeeper.updateRates();

        // log rate
        console.log("quotaRevenue before adding the first position: ", liquidityPool.quotaRevenue());

        // borrowerA create position
        vm.startPrank(borrowerA);
        token.approve(address(vaultA), amount);
        vaultA.modifyCollateralAndDebt(borrowerA, borrowerA, borrowerA, toInt256(amount), toInt256((amount * 75) / 100));
        vm.stopPrank();

        // update rates
        vm.prank(address(gauge));
        quotaKeeper.updateRates();

        // log rate, one active credit manager
        console.log("quotaRevenue after adding the first position: ", liquidityPool.quotaRevenue());

        // borrowerB create position
        vm.startPrank(borrowerB);
        token.approve(address(vaultB), amount);
        vaultB.modifyCollateralAndDebt(borrowerB, borrowerB, borrowerB, toInt256(amount), toInt256((amount * 75) / 100));
        vm.stopPrank();

        // update rates
        vm.prank(address(gauge));
        quotaKeeper.updateRates();

        // log rate, two active credit manager
        console.log("quotaRevenue after adding the second position: ", liquidityPool.quotaRevenue());
    }
}

```

## Recommended Mitigation Steps

The `PoolQuotaKeeperV3` should use the already existing `totalBorrowed()` [8](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/interfaces/IPoolV3.sol#L77) function, which returns the aggregate sum of all borrows from all credit managers. The updated version produces the following logs for the same POC:
- quotaRevenue before adding the first position:  0
- quotaRevenue after adding the first position:  375000000000000000000 [3.75e23]
- quotaRevenue after adding the second position:  750000000000000000000 [7.5e23]

This approach would also allow for a refactor of `PoolQuotaKeeperV3`, removing the credit manager logic entirely as it is no longer needed.
