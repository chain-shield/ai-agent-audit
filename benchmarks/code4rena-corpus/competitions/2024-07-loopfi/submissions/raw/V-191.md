# Vulnerability details

## Impact
When checking if the liquidator is making a full liquidation or not, liquidatePosition uses `deltaDebt` which is equivalent to `repayAmount` (inputed by the user) but with the penalty subtracted to it. So, for the liquidator to make a full liquidation on an unhealthy position he would have to calculate the precise value of `repayAmount` that he has to input so that the following check passes and he can execute a full liquidation:

```solidity
if (deltaDebt == maxRepayment) { 
	(...)
}
```

The formula to arrive at that value can be:

```solidity
uint256 repayAmount = wdiv(virtualDebt(position), liqConfig.liquidationPenalty)+1;
```

The problem is that this transaction will only succeed under very specific circumstances, and some of which are not under the protocol’s control. Most of the times an attempt of fully liquidating an unhealthy position will just revert when it reaches this check:

```solidity
if (takeCollateral > position.collateral) revert CDPVault__tooHighRepayAmount();
```

It reverts here because by recalculating `repayAmount` to match the total amount of debt of the target position, like it was explained above, the liquidator also increases the value of `takeCollateral`, which is `repayAmount` adjusted to the liquidation discount. In case the circumstances are not the right ones `takeCollateral` will be superior to the position's collateral, and the transaction will revert.

Given a `liquidationPenalty`  $p$, a `spotPrice_` $s$ and the position's collateral $c$, the value of `liquidationDiscount` $d$ from which the transaction stops reverting with the above error is given by the following formula:
$$
d ≈ \frac{repayAmount * wad^2}{c*s} + 2
$$

The value $d$ returned by this equation will give us the `liquidationDiscount` that will keep `takeCollateral` bellow $c$ (so that the transaction doesn't revert) for a `repayAmount` that equals `totalDebt`.

For example:
Imagine an instance of a `CDPVault` with a `liquidationPenalty` of `1%` (`9.9e17`), a `liquidationRatio` of `1.25e18` and a `liquidationDiscount` of `2%` (`9.8e17`)
Bob deposits `100 pendle` of collateral and borrows `80 weth`.
After sometime the price is updated to `0.9e18` leaving Bob's position in an unhealthy state and subject to liquidation. With some interest accrued, suppose his `totalDebt` is `88081505882352941176` (≈ 88 eth).
If someone tries to fully liquidate Bob the `repayAmount` that has to be inputed is `88971218062982768865` (≈ 88.9 eth). This way `deltaDebt` will be exactly `88081505882352941176`  and a full liquidation can be executed. Except that it reverts with `CDPVault__tooHighRepayAmount()` because `takeCollateral`, that was calculated using `repayAmount`, is `100874396896805860391` (≈ 100.8 eth) which is larger than the user's collateral (100 eth).
So to keep `takeCollateral < collateral` and prevent the liquidator's transaction from reverting the `liquidationDiscount` that should be in place can be arrived at using the already given formula. In this case $d$ should be equal to `988569089588697433` which is equivalent to a `liquidationDiscount` of `1.14%`. 

The bug, however is not yet resolved, because if we increase the collateral and borrow amount a bit so that Bob deposits `125 pendle` and borrows `100 weth`, the previous calculated `liquidationDiscount` won't be enough. The transaction will revert if someone tries to fully liquidate him. To allow for both scenarios to work we should calculate a new `liquidationDiscount` with the new collateral and debt values. $d$ should now be equal to `988573314847824652` which is only a little bit higher than the previous $d$. And this goes ad infinitum until the debt ceiling is hit. We can conclude that the closest $d$ is to 0% the bigger the collateral and borrow amounts must be so that the transaction reverts, and the less the error occurs. Setting $d$ to `0` completely avoids this problem, but not having a `liquidationDiscount` removes all incentives for users to liquidate unhealthy positions which is not desirable for the protocol.

But as we can see in the above formula, $d$ also depends on the value of `spotPrice_` which is not under control of the protocol. This means that, in Bob's case, if the price lowered to `0.89e18` instead, $d$ value would already be a different one. And this is why it's almost impossible to keep full liquidations of unhealthy positions properly working. $d$ should keep being updated at least each time the oracle gives a new price for the tokens.

The big consequence of not being able to fully liquidate an unhealthy position is that the protocol must wait until the position has bad debt so that `liquidatePositionBadDebt` can be used. And for this reason I believe this bug can lead to the loss of unnecessary funds since loss will be reported to the pool when a normal full liquidation could have been made instead and report profits.

```solidity
    function test_cid_tsNotPossibleToFullyLiquidate_poc() public {
        address bob = makeAddr("bob");
        address alice = makeAddr("alice");

        (liqConfig.liquidationPenalty, liqConfig.liquidationDiscount) = vault.liquidationConfig();

        // alice deposits 100 ether
        uint256 collateral = 100 ether;
        deal(address(token), alice, collateral);
        vm.startPrank(alice);
        token.approve(address(vault), collateral);
        vault.deposit(alice, collateral);

        // alice borrows 80 ether
        uint256 borrowAmount = 80 ether;
        vault.borrow(alice, alice, borrowAmount);
        vm.stopPrank();

        // position becomes unhealthy due to price movement
        vm.warp(block.timestamp + 365 days);
        _updateSpot(0.9 ether);
        uint256 totalDebt = virtualDebt(vault, alice);
        uint256 spotPrice_ = vault.spotPrice();
        uint256 discountedPrice = wmul(spotPrice_, liqConfig.liquidationDiscount);        
        
        //equation that allows deltaDebt to equal totalDebt
        uint256 repayAmount = wdiv(totalDebt, liqConfig.liquidationPenalty)+1;  
        //this calculates the value of `liquidationDiscount` so that the full liquidation would work.
        //If it doesn't work try adding 1 or 2 wei to the discount.
        uint256 d = ((repayAmount * WAD * WAD))/(collateral * spotPrice_) + 2;
        console.log(d);

        mockWETH.mint(bob, repayAmount);
        vm.startPrank(bob);
        mockWETH.approve(address(vault), repayAmount);
        if (d > liqConfig.liquidationDiscount) {
            vm.expectRevert(CDPVault__tooHighRepayAmount.selector);
            vault.liquidatePosition(alice, repayAmount);    
            console.log("the transaction is reverting.");
        } else {
            vault.liquidatePosition(alice, repayAmount);    
            uint256 totalDebtAfter = virtualDebt(vault, alice);
            assertEq(totalDebtAfter, 0); //Alice was fully liquidated
        }
    }                
    error CDPVault__tooHighRepayAmount();
    struct LiquidationConfig {
        /// @notice Penalty applied during liquidation [wad]
        uint64 liquidationPenalty;
        /// @notice Discount on collateral during liquidation [wad]
        uint64 liquidationDiscount;
    }  
```

Consider checking if `repayAmount == maxRepayment` instead of using `deltaDebt`
