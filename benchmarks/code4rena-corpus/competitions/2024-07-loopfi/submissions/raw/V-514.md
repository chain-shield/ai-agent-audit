# Vulnerability details

## Impact
Within PoolV3.sol, in the ``supplyRate()`` function, if the ``_totalDebt.borrowed`` amount approaches the ``totalAssets`` value, the interest rate calculation could result in truncation due to division. The ``baseInterestRate`` is in RAY form ``(scaled by 1e27)``, and when it's multiplied by ``_totalDebt.borrowed`` and then divided by ``totalAssets``, it could lead to rounding down to the nearest integer value.

## Proof of Concept
https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/PoolV3.sol#L603-L611
```solidity
function supplyRate() public view override returns (uint256) {
    uint256 assets = expectedLiquidity();
    uint256 baseInterestRate_ = baseInterestRate();
    if (assets == 0) return baseInterestRate_;
    return
        ((baseInterestRate_ * _totalDebt.borrowed) * (PERCENTAGE_FACTOR - withdrawFee)) /
        PERCENTAGE_FACTOR /
        assets;
}
```
The division by ``PERCENTAGE_FACTOR`` (which is 1e4) and then by assets could result in truncation. However, since this value determines the interest rate paid to depositors, it should be rounded up to ensure users receive at least the correct amount of interest, if not slightly more.

## Recommended Mitigation Steps

Consider modifying the calculation to:
```solidity
return
    (((baseInterestRate_ * _totalDebt.borrowed) * (PERCENTAGE_FACTOR - withdrawFee) + PERCENTAGE_FACTOR - 1) /
    PERCENTAGE_FACTOR + assets - 1) /
    assets;
```
Updating the code to this, ensures that the supply rate is always rounded up, preventing users from receiving less interest than they should due to truncation.
