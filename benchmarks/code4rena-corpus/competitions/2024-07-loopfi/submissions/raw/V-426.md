# Vulnerability details


## Proof of Concept

The `withdrawAndRepay` function in the PositionAction contract is designed to allow users to withdraw collateral and repay debt in a single transaction. However, the current implementation performs these operations in the wrong order, which can lead to significant issues.

Take a look at the [current implementation:](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/proxy/PositionAction.sol#L254)

```solidity
function withdrawAndRepay(
  address position,
  address vault,
  CollateralParams calldata collateralParams,
  CreditParams calldata creditParams,
  PermitParams calldata permitParams
) external onlyRegisteredVault(vault) onlyDelegatecall {
  _repay(vault, position, creditParams, permitParams);
  _withdraw(vault, position, collateralParams);
}

```

The function first calls `_repay` and then `_withdraw`. This order of operations assumes that the user already has the necessary funds to repay the debt before withdrawing collateral. However, this assumption may not always hold true, especially in scenarios where users intend to use the _withdrawn collateral_ to facilitate the _repayment_.

### Coded POC

Attach the code below to [PositionAction20.t.sol](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/test/integration/PositionAction20.t.sol#L287)

Run with `forge test --match-test test_withdrawAndRepay_FailsDueToIncorrectOrder -vv`

```solidity
function test_withdrawAndRepay_FailsDueToIncorrectOrder() public {
  uint256 depositAmount = 1000 ether;
  uint256 borrowAmount = 500 ether;

  // First, deposit and borrow
  _depositAndBorrow(userProxy, address(vault), depositAmount, borrowAmount);

  // User spends the borrowed amount
  vm.prank(user);
  underlyingToken.transfer(address(0x1), borrowAmount);

  // Verify that the user has spent the borrowed amount
  assertEq(underlyingToken.balanceOf(user), 0);

  // Now, attempt to withdraw and repay
  uint256 repayAmount = borrowAmount; // Assuming no interest for simplicity

  CollateralParams memory collateralParams = CollateralParams({
    targetToken: address(token),
    amount: depositAmount,
    collateralizer: address(userProxy), // Changed to userProxy
    auxSwap: emptySwap
  });

  CreditParams memory creditParams = CreditParams({
    amount: repayAmount,
    creditor: address(userProxy), // Changed to userProxy
    auxSwap: emptySwap
  });

  vm.startPrank(user);

  // This should fail because the userProxy doesn't have funds to repay
  vm.expectRevert('ERC20: transfer amount exceeds balance');
  userProxy.execute(
    address(positionAction),
    abi.encodeWithSelector(
      PositionAction.withdrawAndRepay.selector,
      address(userProxy),
      address(vault),
      collateralParams,
      creditParams,
      emptyPermitParams
    )
  );

  vm.stopPrank();

  // Verify that the position remains unchanged
  (uint256 collateral, uint256 debt, , , , ) = vault.positions(address(userProxy));
  assertEq(collateral, depositAmount);
  assertEq(debt, borrowAmount);
}

```

## Impact

If users don't have sufficient funds to repay before withdrawal, their transactions to `withdrawAndRepay()` will fail.

## Recommended Mitigation Steps

To address this issue, the order of operations in the `withdrawAndRepay` function should be reversed. Here's the recommended implementation:

```diff
function withdrawAndRepay(
    address position,
    address vault,
    CollateralParams calldata collateralParams,
    CreditParams calldata creditParams,
    PermitParams calldata permitParams
) external onlyRegisteredVault(vault) onlyDelegatecall {
-    _repay(vault, position, creditParams, permitParams);
    _withdraw(vault, position, collateralParams);
+    _repay(vault, position, creditParams, permitParams);
}
```

By performing the withdrawal before the repayment, this implementation allows users to:

1. First withdraw their collateral.
2. Then use the withdrawn funds (if needed) to repay their debt.
