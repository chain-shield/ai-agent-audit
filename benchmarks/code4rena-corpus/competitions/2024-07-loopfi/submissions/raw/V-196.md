# Vulnerability details

## Overview
The vulnerability identified within the`PoolAction.sol`, `PositionAction.sol`, and `SwapAction.sol` contracts poses a threat utilizing the [Permit2](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/proxy/TransferAction.sol#L55) mechanism. The core issue arises from an inadequate validation process within the _transferFrom function, which allows for the unauthorized transfer of ERC20 tokens. 

`TrnasferAction::_transferFrom` function, which allows for the unauthorized transfer of ERC20 tokens. Specifically, the function fails to ensure that the token specified in the TokenPermissions structure matches the intended token provided by the user, thereby exposing the contract to potential exploitation.

## Proof of concept
The`TrnasferAction::_transferFrom` function is designed to facilitate the transfer of ERC20 tokens via the Permit2 mechanism, which enables off-chain approval of token transfers through cryptographic signatures. However, the implementation of this function across the affected contracts lacks a crucial validation step—verifying that the token defined within the [TokenPermissions](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/proxy/TransferAction.sol#L57) structure (hereafter referred to as TokenPermissions.token) aligns with the token the user intended to transfer (referred to as input.tokenIn).

This flaw is particularly dangerous because it allows an attacker to craft a permit signature for any ERC20 token, which the contract may erroneously accept as the intended token. The failure to cross-check the `TokenPermissions.token| with `input.tokenIn` can result in the unauthorized transfer of tokens, leading to substantial financial losses within the protocol.
```
 function _transferFrom(
        address token,
        address from,
        address to,
        uint256 amount,
        PermitParams memory params
    ) internal {
        if (params.approvalType == ApprovalType.PERMIT2) {
            // Consume a permit2 message and transfer tokens.
            //@audit No check,if the vault accepts the token provided
            ISignatureTransfer(permit2).permitTransferFrom(
                ISignatureTransfer.PermitTransferFrom({
                    permitted: ISignatureTransfer.TokenPermissions({token: token, amount: params.approvalAmount}),
                    nonce: params.nonce,
                    deadline: params.deadline
                }),
                ISignatureTransfer.SignatureTransferDetails({to: to, requestedAmount: amount}),
                from,
                bytes.concat(params.r, params.s, bytes1(params.v)) // Construct signature
            );
        } else if (params.approvalType == ApprovalType.PERMIT) {
            // Consume a standard ERC20 permit message
            IERC20Permit(token).safePermit(
                from,
                to,
                params.approvalAmount,
                params.deadline,
                params.v,
                params.r,
                params.s
            );
            IERC20(token).safeTransferFrom(from, to, amount);
        } else {
            // No signature provided, just transfer tokens.
            IERC20(token).safeTransferFrom(from, to, amount);
        }
    }
```

The code demonstrates a glaring omission of a verification mechanism that ensures TokenPermissions.token corresponds to input.tokenIn. Consequently, an attacker can exploit this vulnerability by crafting a permit for an entirely different ERC20 token than what the user intended.
- Scenario
> Alice’s Intent: ***Alice seeks to join a Pendle liquidity pool by transferring 100 units of TokenA via the transferAndJoin function. She provides input.tokenIn = TokenA and input.netTokenIn = 100 as her transaction parameters.***

> Eve’s Exploit: ***Eve, a malicious actor, intercepts Alice’s transaction or crafts a new one. She manipulates the TokenPermissions structure by setting TokenPermissions.token to TokenB, a token under her control. Eve then submits this modified transaction.***

> Resulting Exploit: ***Due to the lack of proper validation, the _transferFrom function processes the transaction without confirming that TokenPermissions.token matches input.tokenIn. As a result, the contract may erroneously transfer TokenB instead of TokenA, leading to the unauthorized transfer and potential theft of funds.***

## Impact
This vulnerability presents a high-severity risk to the affected Loopfiprotocol. By exploiting this flaw, an attacker can craft a permit signature for any ERC20 token, allowing them to manipulate the token being transferred, resulting in the loss of user funds.

## Recommendation
To mitigate this vulnerability, it is essential to implement a strict validation mechanism within the _transferFrom function. Specifically, the contract must enforce a check that verifies the alignment between TokenPermissions.token and input.tokenIn. If a discrepancy is detected, the transaction should be reverted to prevent any unauthorized transfers.

```solidity
require(token == params.permitted.token, "Token mismatch: The token in TokenPermissions does not match the intended token");
```
By incorporating this validation, the protocol can ensure that the correct token is being transferred, thereby safeguarding user funds and maintaining the security of the protocol.
