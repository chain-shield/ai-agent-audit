# Vulnerability details


## Proof of Concept

Take a look at https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/proxy/PoolAction.sol#L128-L153

```solidity
function _balancerJoin(PoolActionParams memory poolActionParams) internal {
  (
    bytes32 poolId,
    address[] memory assets,
    uint256[] memory assetsIn,
    uint256[] memory maxAmountsIn
  ) = abi.decode(poolActionParams.args, (bytes32, address[], uint256[], uint256[]));

  for (uint256 i = 0; i < assets.length; ) {
    if (maxAmountsIn[i] != 0) {
      IERC20(assets[i]).forceApprove(address(balancerVault), maxAmountsIn[i]);
    }

    unchecked {
      ++i;
    }
  }

  balancerVault.joinPool(
    poolId,
    address(this),
    poolActionParams.recipient,
    JoinPoolRequest({
      assets: assets,
      maxAmountsIn: maxAmountsIn,
      userData: abi.encode(JoinKind.EXACT_TOKENS_IN_FOR_BPT_OUT, assetsIn, poolActionParams.minOut),
      fromInternalBalance: false
    })
  );
}

```

This function is used to perform a join using the Balancer protocol, would be key to note that this function is externally called via both `join()` & `transferAndJoin()`.

Per balancer docs: https://docs.balancer.fi/reference/joins-and-exits/pool-joins.html#userdata

For the JoinKind

> Exact Tokens Join (EXACT_TOKENS_IN_FOR_BPT_OUT)
> User sends precise quantities of tokens, and receives an estimated but unknown (computed at runtime) quantity of BPT.

Issue however is [in our instance](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/proxy/PoolAction.sol#L149) the `userData` field is encoding `assetsIn` instead of `maxAmountsIn` which does not take into account the acceptable slippage for the user, this then causes a revert when the pool needs more than the amount specified in `assetsIn` to join but less than `maxAmountsIn`, causing an unfair DOS.

## Impact

Slippage checks are incorrectly applied and instead forced to be zero percent, since the `maxAmountsIn` is not attached to the `userData` causing a revert even when the amount of tokens needed to join is `X` and `assetsIn < X < maxAmountsIn`

## Recommended Mitigation Steps

Update the `userData` encoding in the `_balancerJoin` function to use `maxAmountsIn` instead of `assetsIn`:

```diff
balancerVault.joinPool(
    poolId,
    address(this),
    poolActionParams.recipient,
    JoinPoolRequest({
        assets: assets,
        maxAmountsIn: maxAmountsIn,
-       userData: abi.encode(JoinKind.EXACT_TOKENS_IN_FOR_BPT_OUT, assetsIn, poolActionParams.minOut),
+       userData: abi.encode(JoinKind.EXACT_TOKENS_IN_FOR_BPT_OUT, maxAmountsIn, poolActionParams.minOut),
        fromInternalBalance: false
    })
);
```

This change ensures that the maximum amounts the user is willing to input are correctly passed to the Balancer Vault, allowing for proper slippage protection.
