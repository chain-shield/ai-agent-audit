# Vulnerability details

## Description
The 3 PositionAction contracts (ERC20, ERC4626 and Pendle) implement the `_onIncreaseLever` function. The PositionAction4626 implementation, however, always reverts.
As the 3 contracts inherit the PositionAction contract, it is known `_onIncreaseLever` is called in the context of the onFlashLoan function.
The latter function calls the former and, at a later point, modifies the collateral and the debt at the vault contract:
```solidity
function onFlashLoan(
        address /*initiator*/,
        address /*token*/,
        uint256 amount,
        uint256 fee,
        bytes calldata data
    ) external returns (bytes32) {
    ...
    uint256 collateral = _onIncreaseLever(leverParams, upFrontToken, upFrontAmount, swapAmountOut);
    ...
    ICDPVault(leverParams.vault).modifyCollateralAndDebt(
            leverParams.position,
            address(this),
            address(this),
            toInt256(collateral),
            toInt256(addDebt)
        );
    ...
}    
```

The modifyCollateralAndDebt function will then transfer tokens from the caller to the vault, provided it has enough approval.

By comparing the 3 `_onIncreaseLever` implementations, there's an unecessary action taken by the 4626 implementation. Let's take a look:
PositionAction20:
```solidity
function _onIncreaseLever(
        LeverParams memory leverParams,
        address upFrontToken,
        uint256 upFrontAmount,
        uint256 swapAmountOut
    ) internal override returns (uint256) {
    ...
    IERC20(leverParams.collateralToken).forceApprove(leverParams.vault, addCollateralAmount);
        return addCollateralAmount;
    }
```

PositionActionPendle:
```solidity
function _onIncreaseLever(
        LeverParams memory leverParams,
        address upFrontToken,
        uint256 upFrontAmount,
        uint256 swapAmountOut
    ) internal override returns (uint256) {
    ...
    IERC20(leverParams.collateralToken).forceApprove(leverParams.vault, addCollateralAmount);
        // deposit into the CDP Vault
        return addCollateralAmount;
    }
```

PositionAction4626:
```solidity
function _onIncreaseLever(
        LeverParams memory leverParams,
        address upFrontToken,
        uint256 upFrontAmount,
        uint256 swapAmountOut
    ) internal override returns (uint256) {
    ...
    // deposit into the CDP vault
        IERC20(leverParams.collateralToken).forceApprove(leverParams.vault, addCollateralAmount);
        return ICDPVault(leverParams.vault).deposit(address(this), addCollateralAmount);
    }
```

The 4626 implementation spends the vault approval by itself and deposits the collateral at the vault, while the other two implementations don't.

Since the onFlashLoan function at the PositionAction contract will attempt to deposit the collateral at the vault with the approval amounts set during `onIncreaseLever` execution, the ERC4626 implementation will revert as it will attempt to deposit the approved amount twice.

## Impact
The PositionAction4626 contract will not be able to execute flashloans as it will attempt to double-spend the collateral in deposits.
In case the contract has a max approval, it will deposit double the intended amount.
## Tools Used
Manual review
## Recommended Mitigation Steps
Make sure not to deposit the collateral at the vault in the PositionAction4626's `onIncreaseLever` implementation as it will already be deposited at the onFlashLoan function at the PendleAction parent contract.
