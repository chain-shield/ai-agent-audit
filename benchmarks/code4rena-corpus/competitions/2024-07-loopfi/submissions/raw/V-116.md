# Vulnerability details

## Proof of Concept
The `StakingLPEth` contract modifies the `withdraw` and `redeem` functions with the `ensureCooldownOff` modifier, which ensures that these functions can only be called when the cooldown is off (i.e., `cooldownDuration == 0`). When the cooldown is enabled (i.e., `cooldownDuration > 0`), these functions will revert with the `OperationNotAllowed` error.
```solidity
function withdraw(
    uint256 assets,
    address receiver,
    address _owner
) public virtual override ensureCooldownOff returns (uint256) {
    return super.withdraw(assets, receiver, _owner);
}

function redeem(
    uint256 shares,
    address receiver,
    address _owner
) public virtual override ensureCooldownOff returns (uint256) {
    return super.redeem(shares, receiver, _owner);
}
```
The purpose of the `withdraw` and `redeem` functions in the ERC4626 standard is to allow users to withdraw or redeem their assets without any additional restrictions. However, in the `StakingLPEth` contract, these functions are effectively disabled when the cooldown is enabled, preventing users from withdrawing or redeeming their assets as intended by the ERC4626 standard.
## Impact
When the cooldown is enabled, users will not be able to withdraw or redeem their assets using the `withdraw` and `redeem` functions, which may lead to user frustration and loss of trust in the contract. Additionally, the contract's behavior deviates significantly from the ERC4626 standard, making it more difficult for users and developers to understand and interact with the contract.

## Recommended Mitigation Steps
The contract should remove the `ensureCooldownOff` modifier from the `withdraw` and `redeem` functions, allowing users to withdraw or redeem their assets without any additional restrictions, as intended by the ERC4626 standard. If the contract still requires cooldown periods for withdrawals and redemptions, alternative mechanisms should be implemented without breaking the ERC4626 standard.
