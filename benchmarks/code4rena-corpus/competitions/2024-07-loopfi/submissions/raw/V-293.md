# Vulnerability details

## Impact

A malicious actor can exploit `PositionAction::increaseLever` function by front-running users, using their signature approvals to increase the collateral of the attacker's position instead of the intended user's. This allows the attacker to steal assets by taking advantage of the `Permit2` functionality, effectively transferring the victim's tokens to their own benefit.

## Proof of Concept

The `PositionAction` contract is designed to be used by a user proxy, with most functions protected by the `onlyDelegatecall` modifier. This modifier ensures that only proxy contracts can call these functions. One of these functions is `PositionAction::increaseLever`, which performs the following operations:

```solidity
 function increaseLever(
        LeverParams calldata leverParams,
        address upFrontToken,
        uint256 upFrontAmount,
        address collateralizer,
        PermitParams calldata permitParams
    ) external onlyDelegatecall {
        // validate the primary swap
        if (
            leverParams.primarySwap.swapType != SwapType.EXACT_IN ||
            leverParams.primarySwap.assetIn != address(underlyingToken) ||
            leverParams.primarySwap.recipient != self
        ) revert PositionAction__increaseLever_invalidPrimarySwap();

        // validate aux swap if it exists
        if (
            leverParams.auxSwap.assetIn != address(0) &&
            (leverParams.auxSwap.swapType != SwapType.EXACT_IN ||
                leverParams.auxSwap.assetIn != upFrontToken ||
                leverParams.auxSwap.recipient != self)
        ) revert PositionAction__increaseLever_invalidAuxSwap();

        // transfer any up front amount to the LeverAction contract
        if (upFrontAmount > 0) {
            if (collateralizer == address(this)) {
                IERC20(upFrontToken).safeTransfer(self, upFrontAmount); // if tokens are on the proxy then just transfer
            } else {
                _transferFrom(upFrontToken, collateralizer, self, upFrontAmount, permitParams);
            }
        }

        // take out flash loan
        IPermission(leverParams.vault).modifyPermission(leverParams.position, self, true);
        flashlender.flashLoan(
            IERC3156FlashBorrower(self),
            address(underlyingToken),
            leverParams.primarySwap.amount,
            abi.encode(leverParams, upFrontToken, upFrontAmount)
        );
        IPermission(leverParams.vault).modifyPermission(leverParams.position, self, false);
    }
```

The `increaseLever` function performs several actions:

1. Validates the primary and auxiliary swaps.
2. Transfers any upfront token amount to the contract for use in the flash loan callback.
3. Modifies permissions and initiates a flash loan ([PositionAction::onFlashLoan](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/proxy/PositionAction.sol#L379-L427)  is the flashloan callback that handles swapping and modifying the position).

The `_transferFrom` function handles token transfers, depending on the approval type:

```solidity
    function _transferFrom(
        address token,
        address from,
        address to,
        uint256 amount,
        PermitParams memory params
    ) internal {
        if (params.approvalType == ApprovalType.PERMIT2) {
            // Consume a permit2 message and transfer tokens.
            ISignatureTransfer(permit2).permitTransferFrom(
                ISignatureTransfer.PermitTransferFrom({
                    permitted: ISignatureTransfer.TokenPermissions({token: token, amount: params.approvalAmount}),
                    nonce: params.nonce,
                    deadline: params.deadline
                }),
                ISignatureTransfer.SignatureTransferDetails({to: to, requestedAmount: amount}),
                from,
                bytes.concat(params.r, params.s, bytes1(params.v)) // Construct signature
            );
        } else if (params.approvalType == ApprovalType.PERMIT) {
            // Consume a standard ERC20 permit message
            IERC20Permit(token).safePermit(
                from,
                to,
                params.approvalAmount,
                params.deadline,
                params.v,
                params.r,
                params.s
            );
            IERC20(token).safeTransferFrom(from, to, amount);
        } else {
            // No signature provided, just transfer tokens.
            IERC20(token).safeTransferFrom(from, to, amount);
        }
    }
```

The vulnerability arises when `Permit2::permitTransferFrom` is used. According to [EIP-2612](https://eips.ethereum.org/EIPS/eip-2612#security-considerations), which defines the permit function for ERC-20 tokens, the function allows a token holder to approve a spender using a signed message without requiring an on-chain transaction from the token holder. This mechanism introduces a potential for front-running.

Per the EIP, while the signer of a Permit may intend for a specific party to submit the transaction, another party can always front-run the transaction and call permit before the intended party does. The function does not check who initiates the call because its security relies on the signature's validity rather than the caller's identity. The end result is that the tokens are transferred as permitted by the signature, regardless of who actually submitted the transaction.

The same applies for `Permit2`; no matter who initiates the call, the end result will always be the same. In this case, the funds will be transferred to `self`, which is the `PositionAction` contract.

In the context of `PositionAction::increaseLever`, the `position` parameter is never validated. This allows an attacker to front-run the user by calling `PositionAction::increaseLever`, extracting the user's signature but passing their own position. This leads to the user's funds being added as collateral in the attacker's position.

## Exploitation Scenario

**1. Victim executes the transaction:** The victim signs a Permit2 message to transfer the tokens to the proxy contract and calls `PositionAction::increaseLever`. 
**2. Attacker front-runs:** The attacker sees this pending transaction, then extracts the signature and calls `increaseLever` using the victim's signature, but passes `leverActions.position=attacker's position`.
**3. Collateral theft:** The victim’s tokens are transferred to the attacker's position, increasing their collateral instead of the victim’s.

## Tools Used
Manual Analysis

## Recommended Mitigation Steps

Consider using `Permit2::permitWitnessTransferFrom` and pass any additional data that makes sure that, if anybody executes the transaction the outcome will be the same.
