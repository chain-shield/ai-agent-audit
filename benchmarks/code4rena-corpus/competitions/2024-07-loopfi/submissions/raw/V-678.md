# Vulnerability details

## Impact
The `rewardPool` is approved to psend tokens using OpenZeppelin's `safeApprove` function when depositing assets or minting shares or claiming of rewards. However, this is done without approving to 0 prior to that. OpenZeppelin's `safeApprove` does not allow to change a non zero allowance to another to anything other than zero. This means that, all calls to `safeApprove` will revert if there is some dust allowance that currently exists.

```solidity
    function safeApprove(
        IERC20 token,
        address spender,
        uint256 value
    ) internal {
        // safeApprove should only be called when setting an initial allowance,
        // or when resetting it to zero. To increase and decrease it, use
        // 'safeIncreaseAllowance' and 'safeDecreaseAllowance'
        require(
            (value == 0) || (token.allowance(address(this), spender) == 0),
            "SafeERC20: approve from non-zero to non-zero allowance"
        );
        _callOptionalReturn(token, abi.encodeWithSelector(token.approve.selector, spender, value));
    }
```
The first call to `safeApprove` won't fail but the calls after that will fail. Effectively DOSing these methods.
