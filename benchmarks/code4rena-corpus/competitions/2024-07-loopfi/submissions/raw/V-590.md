# Vulnerability details

## Description
According to the Readme `Pool and swap actions can use any ERC-20 to perform swaps`, As both `PoolAction` and `SwapAction` inherit the `TransferAction` contract to perform the transferFrom using ` _transferFrom` function, In the case ApprovalType is `permit`, Some tokens are not compatible with this approval type e.g WETH. if the swap is performed using the `PERMIT` approval type and WETH is the token being the `assetIn` which then triggers the `_transferFrom` function, but as WETH does not have the permit functionality, it will trigger its fallback function, and it will allow the functions execution to continue and perform an `transferFrom`. this can be exploited where attacker can drain users if the token is not permit Compatible.

Leaving some additional info, where exactly WETH + permit() was the reason which lead to Multichain's (previously AnySwap) exploit:
<https://medium.com/zengo/without-permit-multichains-exploit-explained-8417e8c1639b>

## Impact
Loss of funds for users/disruption of protocol functionality

## Proof of Concept
1. Attacker crafts the parameters to function in a way that from is the users address, token and to are the contracts deployed by the attacker

```javascript
function _transferFrom(
        address token,
        address from,
        address to,
        uint256 amount,
        PermitParams memory params
    ) internal {
        if (params.approvalType == ApprovalType.PERMIT2) {
            // Consume a permit2 message and transfer tokens.
            ISignatureTransfer(permit2).permitTransferFrom(
                ISignatureTransfer.PermitTransferFrom({
                    permitted: ISignatureTransfer.TokenPermissions({token: token, amount: params.approvalAmount}),
                    nonce: params.nonce,
                    deadline: params.deadline
                }),
                ISignatureTransfer.SignatureTransferDetails({to: to, requestedAmount: amount}),
                from,
                bytes.concat(params.r, params.s, bytes1(params.v)) // Construct signature
            );
        } else if (params.approvalType == ApprovalType.PERMIT) {
            // Consume a standard ERC20 permit message
            IERC20Permit(token).safePermit(
                from,
                to,
                params.approvalAmount,
                params.deadline,
                params.v,
                params.r,
                params.s
            );
            IERC20(token).safeTransferFrom(from, to, amount);
        } else {
            // No signature provided, just transfer tokens.
            IERC20(token).safeTransferFrom(from, to, amount);
        }
    }
}

```
2. Attacker passes a bogus signature using the PermitParams 
3. As quoted e.g if token in context is `WETH`, since it does not have permit functionality, it will trigger its fallback function but the execution will continue.
4. `IERC20(token).safeTransferFrom(from, to, amount)` if we reached this line, that means that signature in the above line was verified and now we can use the approval granted by it to actually move the `amount` from user to attacker created `to` address

## Tools Used
Manual
## Recommended Mitigation Steps
If the approval type is `permit`, use try/catch blocks to check if the token supports the permit function before calling it.
