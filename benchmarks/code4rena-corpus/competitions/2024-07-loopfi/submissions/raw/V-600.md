# Vulnerability details

## Description
When a partial repayment is made at the CDPVault, the calcDecrease function is executed to update the debt, cumulative index, profit, and cumulative quota interest for the position.

In cases where the partial repayment is sufficient to cover the cumulative quota interest but not the entire accrued interest, the calculation of the new cumulative index is incorrect.

```solidity
{
    // If the amount is insufficient to repay interest, send all to the stakers and update the index
    profit += amountToRepay; // U:[CL-3]
    amountToRepay = 0; // U:[CL-3]

    newCumulativeIndex =
        (INDEX_PRECISION * cumulativeIndexNow * cumulativeIndexLastUpdate) /
        (INDEX_PRECISION *
            cumulativeIndexNow -
            (INDEX_PRECISION * profit * cumulativeIndexLastUpdate) /
            debt); // U:[CL-3]
}
```

In this context, the `newCumulativeIndex` calculation uses the `profit` variable, which is supposed to represent the amount repaid of the accrued interest.
If we take a look at Gearbox's V3 implementation( [core-v3/contracts/libraries/CreditLogic.sol at bbe94b9bfcae21708ae32022439a9035fcf813e8 · Gearbox-protocol/core-v3 (github.com)](https://github.com/Gearbox-protocol/core-v3/blob/bbe94b9/contracts/libraries/CreditLogic.sol#L258C20-L270C14)), a similar calculation is made using only the amount of accrued interest (considering the fee) available for repayment for this operation:
```solidity
{
{
    // If the amount is insufficient to repay base interest + DAO fee, it is split pro-rata between them
    uint256 amountToPool = (amountToRepay * PERCENTAGE_FACTOR) / (PERCENTAGE_FACTOR + feeInterest);

    profit += amountToRepay - amountToPool; // U:[CL-3]
    amountToRepay = 0; // U:[CL-3]

    newCumulativeIndex = (INDEX_PRECISION * cumulativeIndexNow * cumulativeIndexLastUpdate)
        / (
            INDEX_PRECISION * cumulativeIndexNow
                - (INDEX_PRECISION * amountToPool * cumulativeIndexLastUpdate) / debt
        ); // U:[CL-3]
}
```

From this, it is evident that only the amountToRepay available during this code block should be used to calculate the new cumulative index.

However, in the calcDecrease function, the profit variable is used instead of amountToRepay. This profit variable is larger than amountToRepay because it has already accounted for the quota interest repayment:

```solidity
function calcDecrease(
    uint256 amount,
    uint256 debt,
    uint256 cumulativeIndexNow,
    uint256 cumulativeIndexLastUpdate,
    uint128 cumulativeQuotaInterest
)
    internal
    pure
    returns (uint256 newDebt, uint256 newCumulativeIndex, uint256 profit, uint128 newCumulativeQuotaInterest)
{
    ...
    if (cumulativeQuotaInterest != 0 && amountToRepay != 0) {
        ...
        profit += cumulativeQuotaInterest; // U:[CL-3]
        ...
    }

    if (amountToRepay != 0) {
        ...
    } else {
        // If the amount is insufficient to repay interest, send all to the stakers and update the index
        profit += amountToRepay; // U:[CL-3]
        amountToRepay = 0; // U:[CL-3]

        newCumulativeIndex =
            (INDEX_PRECISION * cumulativeIndexNow * cumulativeIndexLastUpdate) /
            (INDEX_PRECISION *
                cumulativeIndexNow -
                (INDEX_PRECISION * profit * cumulativeIndexLastUpdate) /
                debt); // U:[CL-3]
    }
}
```
## Impact
The new cumulative indexes of partial repayments of accrued interest will be much smaller than expected. This means users that execute partial repayments will have to pay less interest than the ones that execute entire repayments.
The impact on repayment is that the cumulative quota interest repayment will be considered for both its own repayment and for the accrued interest repayment.
## Tools Used
Manual review
## Recommended Mitigation Steps
Make sure to utilize the available amount to repay to calculate to calculate the newCumulativeIndex variable. Only after this operation, set amountToRepay to zero.
