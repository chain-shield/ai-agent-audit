# Vulnerability details

Impact
The updateLeverJoin function allows users to contribute liquidity to a Balancer pool using a combination of a flash loan and an upfront token amount. However, the function does not adequately validate the presence or value of `joinToken`, `upFrontToken`, and `upfrontAmount`. This oversight can lead to scenarios where users opt not to provide required tokens or amounts, potentially resulting in inaccurate or misleading liquidity contributions to the pool.

## Proof of Concept
The `updateLeverJoin` function is designed to facilitate the addition of liquidity to a Balancer pool by combining a flash loan with an upfront contribution of tokens. However, the function does not enforce any checks to ensure that when an `upFrontToken` is specified, an actual corresponding upfrontAmount is provideda and also `joinToken`.

If a user, such as Alice, chooses to call the function without providing an `upFrontToken` or an `upfrontAmount`, the function could still proceed without reverting. This could result in an overestimation of the liquidity provided to the pool, as the function may assume more liquidity has been contributed than what was actually transferred. Consequently, this could lead to under-collateralization of the pool, potentially destabilizing it.

> Flash Loan Initiation:
Alice initiates a flash loan of TokenA (flashLoanAmount).

> No Upfront Contribution:

Alice decides not to provide any upfront tokens (`upFrontToken` is set to address(0)).
Consequently, upfrontAmount is set to 0.

> Call to updateLeverJoin:

Alice calls the `updateLeverJoin` function with the specified flashLoanAmount, no joinToken, no `upFrontToken` or `upfrontAmount`.
The function combines the flashLoanAmount with 0 (the `upfrontAmount`), assuming all provided liquidity comes from the flash loan.

The lack of validation for `joinToken`, `upFrontToken`, and `upfrontAmount` in the updateLeverJoin function presents a significant risk of pool under-collateralization and potential exploitation.

Manual review, GitHub. 

## Recommended Mitigation Steps
Ensure that a valid and non-zero `joinToken` is provided. The function should check that `joinToken != address(0)` `upfrontoken != address(0)` and that the token is one of the accepted tokens in the pool. 

Introduce a check that enforces the provision of an `upFrontToken` and a non-zero upfrontAmount when adding liquidity. If an upFrontToken is specified, the function should require that `upfrontAmount > 0.`

```solidity
if (upFrontToken != address(0)) {
    require(upfrontAmount > 0, "upfrontAmount must be greater than 0 when upFrontToken is specified");
}
```
