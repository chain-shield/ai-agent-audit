# Vulnerability details


  ## TITLE: [M-7] Lack of Adherence to Checks-Effects-Interaction Pattern in zapVestingToLp Function
**Description:**
The `MultidistridbutionFee::zapVestingToLp` function in the contract is designed to allow a user to convert their vested tokens into liquidity provider tokens (LP tokens). However, this function does not adhere to the checks-effects-interaction pattern, which is crucial for preventing potential reentrancy attacks.

The function performs external calls to transfer tokens and update the price provider before updating the user's balance, which could open up vulnerabilities if the external contract being called is malicious or compromised. Specifically, the function first transfers tokens using `safeTransfer` and then updates the price via an external call to `MultidistridbutionFee::IPriceProvider.update()`, both of which occur before the user's balances are updated.

**Impact:**
Failure to adhere to the checks-effects-interaction pattern can lead to reentrancy vulnerabilities, where an attacker could potentially manipulate the state of the contract during the execution of the external calls. This could allow the attacker to drain funds or cause inconsistencies in the contract's state, leading to loss of funds or unexpected behaviors in the system.

**Proof of Concept:**

An attacker could deploy a malicious contract that interacts with the zapVestingToLp function.
The attacker calls the function and during the external `safeTransfer` or update() call, the attacker reenters the contract and calls`MultidistridbutionFee::zapVestingToLp` again before the balances are updated.
This reentrancy could result in the function being executed multiple times, allowing the attacker to zap more tokens than they actually have vested, effectively draining the contract's funds.

**Recommended Mitigation:**
To mitigate this risk, reorder the operations in the function to follow the checks-effects-interaction pattern:

Perform all necessary checks at the beginning of the function.
Update the user's balances immediately after the checks.
Interact with external contracts (e.g., safeTransfer, update()) only after the internal state has been updated. like so:
