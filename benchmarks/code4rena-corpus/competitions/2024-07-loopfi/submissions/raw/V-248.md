# Vulnerability details

## Summary

The `repayCreditAccount` function in the PoolV3 contract assumes that the required amount (repaidAmount + profit + loss) has been correctly transferred to the pool without performing an internal verification. This omission can lead to significant financial discrepancies, including underfunded pool states, incorrect financial accounting, potential exploits, loss to the treasury, and ultimately, the erosion of protocol


## Impact
The insufficient verification of token transfers in the `repayCreditAccount` function can lead to several critical issues that impact the integrity, stability, and reliability of the pool, as well as the broader protocol. Here are the key impacts:

1. Underfunded Pool
If the repaidAmount, profit, and loss are not fully covered by the transferred tokens, the pool's actual liquidity becomes less than what the internal records state. This underfunded state can severely impact the pool's ability to meet future obligations.
Consequence: Liquidity providers may face withdrawal issues as the pool may not have enough tokens to honor redemption requests. This can lead to a loss of trust in the protocol.
2. Incorrect Financial Accounting
The function updates the pool’s internal state, minting or burning shares and adjusting debt parameters based on the assumption that the correct amount has been transferred. With insufficient transfers, the state is updated incorrectly.
Consequence: This can lead to misleading financial data, where the protocol’s metrics and health indicators do not reflect the true state of liquidity and debts. It can mask underlying issues until they manifest in more severe failures.
3. Potential Exploits
Malicious actors can exploit this vulnerability to deliberately underfund the pool while making it appear as though debts have been repaid. This can be especially critical if coordinated across multiple accounts.
Consequence: Attackers can drain the pool's resources, leading to financial losses for legitimate users and potentially collapsing the pool's structure.
4. Loss to Treasury
In cases where profit is specified but not actually transferred, the protocol mints new shares to the treasury based on non-existent profits, leading to inflation of shares without corresponding value.
Consequence: This could devalue the shares held by other users and disrupt the expected returns for liquidity providers.

## Proof of Concept
Demonstrate how the `repayCreditAccount` function can be called without transferring the required amount of tokens, leading to potential financial discrepancies.

Scenario Outline
Initial Setup:
Assume a credit manager has previously borrowed from the pool.
The credit manager attempts to repay part of the debt without transferring sufficient tokens to the pool address.

Key Insight
The `repayCreditAccount` function does not internally check whether the amount needed has actually been transferred to the pool's address before adjusting the pool's state and debt parameters.

Concrete Example
Variables:

repaidAmount = 300 ether
profit = 400 ether
loss = 100 ether
totalNeeded = repaidAmount + profit + loss = 800 ether
Attempt Repayment with Insufficient Tokens:

Assume the credit manager transfers only 100 ether to the pool.

The `repayCreditAccount` function processes the repayment without verifying the total transferred amount:

```solidity

function repayCreditAccount(
        uint256 repaidAmount,
        uint256 profit,
        uint256 loss
    )
        external
        override
        creditManagerOnly // U:[LP-2C]
        whenNotPaused // U:[LP-2A]
        nonReentrant // U:[LP-2B]
    {
        uint128 repaidAmountU128 = repaidAmount.toUint128();

        DebtParams storage cmDebt = _creditManagerDebt[msg.sender];
        uint128 cmBorrowed = cmDebt.borrowed;
        if (cmBorrowed == 0) {
            revert CallerNotCreditManagerException(); // U:[LP-2C,14A]
        }

        if (profit > 0) {
            _mint(treasury, convertToShares(profit)); // U:[LP-14B]
        } else if (loss > 0) {
            address treasury_ = treasury;
            uint256 sharesInTreasury = balanceOf(treasury_);
            uint256 sharesToBurn = convertToShares(loss);
            if (sharesToBurn > sharesInTreasury) {
                unchecked {
                    emit IncurUncoveredLoss({
                        creditManager: msg.sender,
                        loss: convertToAssets(sharesToBurn - sharesInTreasury)
                    }); // U:[LP-14D]
                }
                sharesToBurn = sharesInTreasury;
            }
            _burn(treasury_, sharesToBurn); // U:[LP-14C,14D]
        }

        _updateBaseInterest({
            expectedLiquidityDelta: -loss.toInt256(),
            availableLiquidityDelta: 0,
            checkOptimalBorrowing: false
        }); // U:[LP-14B,14C,14D]

        _totalDebt.borrowed -= repaidAmountU128; // U:[LP-14B,14C,14D]
        cmDebt.borrowed = cmBorrowed - repaidAmountU128; // U:[LP-14B,14C,14D]

        emit Repay(msg.sender, repaidAmount, profit, loss); // U:[LP-14B,14C,14D]
    }

```
Result
Expected Behavior: The function assumes that 800 ether has been transferred.
Actual Outcome: Only 100 ether was transferred, but the function proceeds, causing an inconsistency in the pool's accounting.
