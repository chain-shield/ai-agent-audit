# Vulnerability details

## Summary

The `Flashlender` contract allows for flash loans and credit flash loans without implementing adequate authorization checks. A malicious actor can initiate an unwanted large flash loan on behalf of a legitimate user by specifying their contract address as the receiver. In this scenario, the malicious actor indirectly forces the user to handle the borrowed amount and associated fees, which can potentially lead to the user's tokens being drained or burned.

```solidity

function flashLoan(
        IERC3156FlashBorrower receiver,
        address token,
        uint256 amount,
        bytes calldata data
    ) external override nonReentrant returns (bool) {
        if (token != address(underlyingToken)) revert Flash__flashLoan_unsupportedToken();
        uint256 fee = wmul(amount, protocolFee);
        uint256 total = amount + fee;

        pool.lendCreditAccount(amount, address(receiver));

        emit FlashLoan(address(receiver), token, amount, fee);

        if (receiver.onFlashLoan(msg.sender, token, amount, fee, data) != CALLBACK_SUCCESS)
            revert Flash__flashLoan_callbackFailed();

        
        underlyingToken.transferFrom(address(receiver), address(pool), total);
        pool.repayCreditAccount(total - fee, fee, 0);

        return true;
    }

    
    function creditFlashLoan(
        ICreditFlashBorrower receiver,
        uint256 amount,
        bytes calldata data
    ) external override nonReentrant returns (bool) {
        uint256 fee = wmul(amount, protocolFee);
        uint256 total = amount + fee;

        pool.lendCreditAccount(amount, address(receiver));

        emit CreditFlashLoan(address(receiver), amount, fee);

        if (receiver.onCreditFlashLoan(msg.sender, amount, fee, data) != CALLBACK_SUCCESS_CREDIT)
            revert Flash__creditFlashLoan_callbackFailed();

        // reverts if not enough Stablecoin have been send back
        underlyingToken.transferFrom(address(receiver), address(pool), total);
        pool.repayCreditAccount(total - fee, fee, 0);

        return true;
    }

```

## Impact

The lack of authorization checks in the `flashLoan` and `creditFlashLoan` functions of the `Flashlender` contract allows malicious actors to initiate flash loans on behalf of any user-specified contract address. 

Token Drainage: A malicious actor can force a receiving contract to handle large amounts of tokens abruptly. If the receiving contract is not designed to protect against such attacks, it may result in the drainage of tokens from the receiver's balance to cover the loan amount and associated fees.


## Proof of Concept

Setup:

A legitimate user deploys a receiver contract (VictimReceiver) which implements the IERC3156FlashBorrower interface.

Malicious Actor:

A malicious actor identifies the receiver contract of the legitimate user.
The malicious actor invokes the `flashLoan` function on the Flashlender contract, specifying the VictimReceiver contract as the receiver.

Steps in Exploit
Flash Loan Invocation:

The attacker calls Flashlender.flashLoan() with the following parameters:
receiver: Address of VictimReceiver.
token: Address of the stablecoin being used.
amount: A large amount to cause significant financial strain.
data: Any arbitrary data (optional).
Execution in Flashlender:

The Flashlender contract checks if the token parameter matches the underlyingToken in its storage.
It calculates the fee based on the provided amount.
It interacts with the pool to lend out the specified amount to the receiver.
Callback to VictimReceiver:

The Flashlender contract calls `receiver.onFlashLoan()` on the VictimReceiver contract.
The VictimReceiver contract processes this callback.

The Flashlender contract transfers the amount + fees from the VictimReceiver contract back to the Flashlender contract

The legitimate user's VictimReceiver contract ends up with significantly reduced token holdings.

The user suffers financial losses due to the unauthorized flash loan initiated by the attacker.

## Tools Used

Foundry

## Recommended Mitigation Steps

Add authorization checks to ensure that only authorized users can initiate a flash loan on behalf of a specified receiver contract. This can be achieved by implementing a check to verify that msg.sender is authorized to make a flash loan for the specified receiver before allowing the loan to proceed.
