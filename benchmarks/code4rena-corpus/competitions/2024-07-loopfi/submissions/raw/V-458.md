# Vulnerability details

## Impact

Protocols that integrate with `LoopFI` may wrongly assume that the functions are EIP-4626 compliant. This may cause integration problems in the future that can lead to wide range of issues for relevant parties.

In addition, this will damage `LoopFI's` brand and limit `LoopFI's` growth in the market. The protocol is failing to comply with the standard, which is a necessity, as mentioned in the [ERC-4626 specification](https://eips.ethereum.org/EIPS/eip-4626).

## Proof of Concept

Let's observe the `maxWithdraw` and `maxRedeem` functions:

[PoolV3.sol#L366-L373](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/PoolV3.sol#L366-L373)
```javascript
    function maxWithdraw(address owner) public view override(ERC4626, IERC4626) returns (uint256) {
        return
            paused()
                ? 0
                : _amountMinusFee(
                    _amountMinusWithdrawalFee(Math.min(availableLiquidity(), _convertToAssets(balanceOf(owner))))
                ); // U:[LP-11]
    }
```

[PoolV3.sol#L376-L378](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/PoolV3.sol#L376-L378)
```javascript
    function maxRedeem(address owner) public view override(ERC4626, IERC4626) returns (uint256) {
        return paused() ? 0 : Math.min(balanceOf(owner), _convertToShares(availableLiquidity())); // U:[LP-11]
    }
```

The [specification](https://eips.ethereum.org/EIPS/eip-4626) mentions that these functions `"MUST factor in both global and user-specific limits, like if withdrawals are entirely disabled (even temporarily) it MUST return 0."`.

However, the case where the `withdraw()` and `redeem()` functions are `locked` is not considered.

The `PoolV3` contract constructor sets `locked` to true:

[PoolV3.sol#L186)](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/PoolV3.sol#L186)
```javascript
locked = true;
```

This can be changed at anytime by the `controller`:

[PoolV3.sol#L844-L846](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/PoolV3.sol#L844-L846)
```javascript
    function setLock(bool status) external controllerOnly {
        locked = status;
    }
```

The `withdraw` function incorporates the `whenNotLocked` modifier:

[PoolV3.sol#L292-L309](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/PoolV3.sol#L292-L309)
```javascript
    function withdraw(
        uint256 assets,
        address receiver,
        address owner
    )
        public
        override(ERC4626, IERC4626)
        whenNotPaused // U:[LP-2A]
@>      whenNotLocked
        nonReentrant // U:[LP-2B]
        nonZeroAddress(receiver) // U:[LP-5]
        returns (uint256 shares)
    {
        uint256 assetsToUser = _amountWithFee(assets);
        uint256 assetsSent = _amountWithWithdrawalFee(assetsToUser); // U:[LP-8]
        shares = _convertToShares(assetsSent); // U:[LP-8]
        _withdraw(receiver, owner, assetsSent, assets, assetsToUser, shares); // U:[LP-8]
    }
```

This will cause all withdrawals to revert, as long as the `msg.sender` is not in the `_allowed` whitelist:

[PoolV3.sol#L121-L128](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/PoolV3.sol#L121-L128)
```javascript
    modifier whenNotLocked() {
        if (_allowed[msg.sender]) {
            _;
        } else {
            _revertIfLocked();
            _;
        }
    }
```

We can see that `maxWithdraw` doesn't account for this case, therefore not complying with the `EIP-4626` standard.

This exact issue applies `maxRedeem`.

The `redeem` function incorporates the `whenNotLocked` modifier:

[PoolV3.sol#L316-L333](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/PoolV3.sol#L316-L333)
```javascript
    function redeem(
        uint256 shares,
        address receiver,
        address owner
    )
        public
        override(ERC4626, IERC4626)
        whenNotPaused // U:[LP-2A]
@>      whenNotLocked
        nonReentrant // U:[LP-2B]
        nonZeroAddress(receiver) // U:[LP-5]
        returns (uint256 assets)
    {
        uint256 assetsSent = _convertToAssets(shares); // U:[LP-9]
        uint256 assetsToUser = _amountMinusWithdrawalFee(assetsSent);
        assets = _amountMinusFee(assetsToUser); // U:[LP-9]
        _withdraw(receiver, owner, assetsSent, assets, assetsToUser, shares); // U:[LP-9]
    }
```

This will cause all redemptions to revert, as long as the `msg.sender` is not in the `_allowed` whitelist.

We can see that `maxRedeem` doesn't account for this case, therefore not complying with the `EIP-4626` standard:

[PoolV3.sol#L376-L378](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/PoolV3.sol#L376-L378)
```javascript
    function maxRedeem(address owner) public view override(ERC4626, IERC4626) returns (uint256) {
        return paused() ? 0 : Math.min(balanceOf(owner), _convertToShares(availableLiquidity())); // U:[LP-11]
    }
```

## Recommended Mitigation Steps

`PoolV3::maxWithdraw` and `PoolV3::maxRedeem` must return 0 if `locked = true`. However, we must also account for the whitelist incorporated within the lock mechanism, which allows them to continue using `PoolV3::withdraw` and `PoolV3::redeem` despite the lock. Therefore, whitelisted accounts should still be able to call `PoolV3::maxWithdraw` and `PoolV3::maxRedeem` without it returning 0 when `locked = true`.

```diff
    function maxWithdraw(address owner) public view override(ERC4626, IERC4626) returns (uint256) {
+       if(locked && !isAllowed(owner)){
+           return 0;
+       }
        return
            paused()
                ? 0
                : _amountMinusFee(
                    _amountMinusWithdrawalFee(Math.min(availableLiquidity(), _convertToAssets(balanceOf(owner))))
                ); // U:[LP-11]
    }
```

```diff
    function maxRedeem(address owner) public view override(ERC4626, IERC4626) returns (uint256) {
+       if(locked && !isAllowed(owner)){
+           return 0;
+       }
        return paused() ? 0 : Math.min(balanceOf(owner), _convertToShares(availableLiquidity())); // U:[LP-11]
    }
```
