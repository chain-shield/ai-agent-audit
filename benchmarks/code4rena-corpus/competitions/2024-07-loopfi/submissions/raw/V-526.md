# Vulnerability details

## Impact
When a user initiates a partial redeem or withdrawal of their staked assets using the ``cooldownAssets`` or ``cooldownShares`` functions, the cooldown period is reset for all of the user's initialized redeem/withdrawal requests. If the user makes a subsequent request to redeem or withdraw additional assets before the initial cooldown period expires, the cooldown timer is reset for the entire amount. This causes an unintended extension of the cooldown period for the assets originally requested, forcing users to wait longer than expected to access their funds.
This could lead to frustration and potential financial inconvenience for users who need timely access to their assets.

## Proof of Concept
1) ## Initial Setup
- User A has 100 tokens staked.
- User A initiates a withdraw process for 50 tokens by calling ``cooldownAssets(50)`` at timestamp 10.
- The cooldown duration is 10, so the tokens should be available at timestamp 20.

2) ## Scenario
- Before the cooldown ends, at timestamp 15, User A decides to withdraw the remaining 50 tokens by calling ``cooldownAssets(50)`` again.

3) ## Unexpected Behavior
- Instead of allowing the first 50 tokens to be redeemable at timestamp 20, the cooldown for all 100 tokens is reset, causing the cooldown to end at timestamp 25 for both requests.
- User A now has to wait an additional 5 timestamp periods for the initial 50 tokens that should have been available at timestamp 20.
