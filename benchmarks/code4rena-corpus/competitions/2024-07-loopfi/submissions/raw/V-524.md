# Vulnerability details

## Impact

The `PositionAction::increaseLever` function contains a flash loan mechanism that is used to increase leverage by depositing collateral into a `CDPVault`. When `PositionAction4626::_onIncreaseLever` is called, it deposits shares from the `ERC4626` collateralToken into the `CDPVault` at `PositionAction4626#L129`. Subsequently, another deposit action to the `CDPVault` occurs at `PositionAction#L416`, leading to a double deposit of ERC4626 shares. In contrast, `PositionAction20::_onIncreaseLever` only approves the collateral amount to the vault without performing the deposit, which is correctly handled at `PositionAction#L416`.

This will cause two problems:
- Users who have granted maximum approval for ERC4626 shares tokens will spend twice the amount when using the `PositionAction4626::increaseLever` function.
- If users only approve the tokens they intend to deposit, then the `increaseLever` function will always be reverted because not enough ERC4626 shares tokens have been approved.

## Proof of Concept

In the `PositionAction::increaseLever` function, there is a flash loan that is utilized to call `PositionAction::onFlashLoan`, which subsequently invokes `_onIncreaseLever` on `PositionAction#L410`. ## Recommended Mitigation Steps

Ensure that the `_onIncreaseLever` function for `PositionAction4626` does not perform the deposit itself but only prepares the collateral (similar to `PositionAction20::_onIncreaseLever`):

```diff
    function _onIncreaseLever(
        LeverParams memory leverParams,
        address upFrontToken,
        uint256 upFrontAmount,
        uint256 swapAmountOut
    ) internal override returns (uint256) {
        ...
        ...
        // deposit into the CDP vault
        IERC20(leverParams.collateralToken).forceApprove(leverParams.vault, addCollateralAmount);
-       return ICDPVault(leverParams.vault).deposit(address(this), addCollateralAmount);
+       return addCollateralAmount;
    }
```
