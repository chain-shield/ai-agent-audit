## Vulnerabilities

### 1. DAI Permit Incompatibility

The `_transferFrom` function in the `TransferAction` contract uses a standard ERC20 permit function signature when `ApprovalType.PERMIT` and `ApprovalType.PERMIT2` are specified. However, DAI uses a non-standard permit function signature.

DAI's permit function:
```solidity
function permit(address holder, address spender, uint256 nonce, uint256 expiry,
                bool allowed, uint8 v, bytes32 r, bytes32 s) external
```

Heigh parameters are needed DAI permit function.

This mismatch means that DAI, despite supporting permit-based interactions, cannot be used with signed messages for depositing into vaults that inherit from `TransferAction`. DTransactions using DAI with will revert due to the function signature mismatch.

### 2. WETH Silent Failure

WETH (Wrapped Ether) does not implement a permit function. When attempting to use `permit` with WETH, the function will fail silently due to WETH's fallback function. This creates a potential vulnerability where transactions involving WETH might appear to succeed but actually fail to transfer the tokens.


## Recommended Mitigation Steps

1. For DAI: Implement a separate handling for DAI that uses its specific permit function signature.
2. For WETH: Add a check to verify if the token supports the permit function before attempting to use it. If not supported, either revert the transaction or fall back to the standard approval process.
3. Consider implementing a token whitelist or blacklist to manage tokens with non-standard behaviors.

## Additional Notes

The use of `SafeERC20` for both `IERC20` and `IERC20Permit` is a good practice that helps prevent some common ERC20 pitfalls. However, it doesn't protect against the specific vulnerabilities mentioned above.

For more information on issues related to WETH and silent failures, refer to the article ["Phantom Functions and the Billion-Dollar No-Op"](https://medium.com/dedaub/phantom-functions-and-the-billion-dollar-no-op-c56f062ae49f).
