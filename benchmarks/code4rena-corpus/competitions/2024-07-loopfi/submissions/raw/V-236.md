# Vulnerability details

## Description
Look at this code:
```

        address address_,

        if (limit_ == 0) limit_ = _userLocks[address_].length;

        if (isRelockAction && address_ != msg.sender && _lockZap != msg.sender) revert InsufficientPermission();


```
See, that verification?
Well, so if ``isRelockAction`` is false, the verification will pass and will not be executed to revert, because that verification requires ``true && true && true`` to execute.

That means anyone can call the function when ``isRelockAction`` is false, at first glance there seems to be no problem there. 

But take a look at the following line of code[L1369](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/MultiFeeDistribution.sol#L1369):
```
        if (isRelockAction || (address_ != msg.sender && !autoRelockDisabled[address_])) {
            _stake(amount, address_, defaultLockIndex[address_], true);
```
Since ``isRelockAction`` is false and then ``(address_ != msg.sender && !autoRelockDisabled[address_]))`` is true, this will trigger the ``_stake`` function.

``!autoRelockDisabled[address_]`` is true, assume the user never call ``setRelock`` to sets ``autoRelockDisabled[address_]`` to true, so ``autoRelockDisabled[address_]`` is always false.

As a result, anyone can relock a user's funds after the user's lock is expired.

## Impact
- attacker can lock users' funds once they expire

## Proof of Concept 
- users do a ``stake`` then after that their lock period expires.
- The attacker sees this and performs ``withdrawExpiredLocksForWithOptions(users, 0, false)``.
- As a result, the user's funds are locked again.

#### Run PoC
- Paste the code below into ``MultiFeeDistribution.t.sol``
- run it with ``forge test --match-test test_griefing_user_balance``
