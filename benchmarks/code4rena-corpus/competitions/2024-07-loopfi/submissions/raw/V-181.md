# Vulnerability details

## Proof of Concept
```solidity
function _newRewards(
    VaultInfo memory pool,
    uint256 _totalAllocPoint
) internal view returns (uint256 newReward, uint256 newAccRewardPerShare) {
    uint256 lpSupply = pool.totalSupply;
    if (lpSupply > 0) {
        uint256 duration = block.timestamp - pool.lastRewardTime;
        uint256 rawReward = duration * rewardsPerSecond;

        uint256 rewards = availableRewards();
        if (rewards < rawReward) {
            rawReward = rewards;
        }
        newReward = (rawReward * pool.allocPoint) / _totalAllocPoint;
        newAccRewardPerShare = (newReward * ACC_REWARD_PRECISION) / lpSupply;
    }
}
```
The function calculates rewards based on the `rewardsPerSecond` which should ideally be updated according to the current emission schedule. The `EmissionPoint` struct, which tracks reward rates over time, is not referenced or updated within this function.



## Impact
Incorrect Reward Calculations: Since `_newRewards` relies on a static `rewardsPerSecond`, not updated with the emission schedule, the function will incorrectly calculate rewards. This results in either over-distribution or under-distribution of rewards, affecting users' earnings and potentially causing discrepancies in the reward system.
## Tools Used
Manual
## Recommended Mitigation Steps
Update the `_newRewards` function to consider the current emission rate based on the `emissionSchedule`. This involves integrating the `emissionSchedule` to get the appropriate `rewardsPerSecond` for the given time period.
