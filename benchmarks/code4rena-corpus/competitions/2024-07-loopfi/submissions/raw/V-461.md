# Vulnerability details

## Impact

`StakingLPEth` acts as an `ERC4626 vault` that allows users to deposit `LPEth` in return for shares which they can later use to redeem. The protocol incorporates a `minimum amount of shares` check, which is not incorporated within `maxWithdraw, maxRedeem` functions, and thus do not comply with ERC-4626 standards.

In addition, `withdraw` and `redeem` functions revert when `cooldown period` is on, however `maxWithdraw` and `maxRedeem` do not account for this, breaking compliance with the ERC-4626 standard.

Protocols that integrate with `LoopFI` may wrongly assume that the functions are EIP-4626 compliant. This may cause integration problems in the future that can lead to wide range of issues for relevant parties.

In addition, this will damage `LoopFI's` brand and limit `LoopFI's` growth in the market. The protocol is failing to comply with the standard, which is a necessity, as mentioned in the [ERC-4626 specification](https://eips.ethereum.org/EIPS/eip-4626).

## Proof of Concept

The internal [_withdraw](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/StakingLPEth.sol#L174) calls `_checkMinShares()`. Note that this function is called within `withdraw()` and `redeem()` calls.

[StakingLPEth.sol#L141-L144](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/StakingLPEth.sol#L141-L144)
```javascript
    function _checkMinShares() internal view {
        uint256 _totalSupply = totalSupply();
        if (_totalSupply > 0 && _totalSupply < MIN_SHARES) revert MinSharesViolation();
    }
```

This check exists to prevent vault inflation attacks:

[StakingLPEth.sol#L27-L28](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/StakingLPEth.sol#L27-L28)
```javascript
    /// @notice Minimum non-zero shares amount to prevent donation attack
    uint256 private constant MIN_SHARES = 0.01 ether;
```

If the amount of shares issued is between 0 and 0.01 ether, all withdraw and redeem calls will revert.

Looking at the [EIP 4626 documentation](https://eips.ethereum.org/EIPS/eip-4626) for `maxWithdraw()`, `maxRedeem()`, the following is stated:

maxWithdraw: `"MUST return the maximum amount of assets that could be transferred from owner through withdraw and not cause a revert"`.
maxRedeem: `"MUST return the maximum amount of shares that could be transferred from owner through redeem and not cause a revert"`.

If the maximum amount the user withdraws/redeems causes the totalSupply() to be between 0 and `MIN_SHARES`, withdraw/redeem calls will revert. Therefore `maxWithdraw` and `maxRedeem` must return 0 in this case, however, that is not the case. The `StakingLPEth` contract inherits from openzeppelin's [ERC4626 implementation](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/master/contracts/token/ERC20/extensions/ERC4626.sol), and is therefore using the default implementation for these functions, which does not account for the `MIN_SHARES` check.

These functions will not follow the requirements stated above, therefore breaking EIP-4626 standard.

In addition, the `StakingLPEth` contract incorporates a cooldown mechanism for unstaking, which burns user's shares and allows them to receive `lpETH` only after their cooldown period has passed.

`StakingLPEth::withdraw` and `StakingLPEth::redeem` revert when the `cooldown period` is on:

[StakingLPEth.sol#L42-L46](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/StakingLPEth.sol#L42-L46)
```javascript
    /// @notice ensure cooldownDuration is zero
    modifier ensureCooldownOff() {
        if (cooldownDuration != 0) revert OperationNotAllowed();
        _;
    }
```

The modifier is placed in both `withdraw` and `redeem` functions:

[StakingLPEth.sol#L66-L83](https://github.com/code-423n4/2024-07-loopfi/blob/main/src/StakingLPEth.sol#L66-L83)
```javascript
    function withdraw(
        uint256 assets,
        address receiver,
        address _owner
    ) public virtual override ensureCooldownOff returns (uint256) {
        return super.withdraw(assets, receiver, _owner);
    }

    /**
     * @dev See {IERC4626-redeem}.
     */
    function redeem(
        uint256 shares,
        address receiver,
        address _owner
    ) public virtual override ensureCooldownOff returns (uint256) {
        return super.redeem(shares, receiver, _owner);
    }
```

Looking at the [EIP 4626 documentation](https://eips.ethereum.org/EIPS/eip-4626) for `maxWithdraw()`, `maxRedeem()`, the following is stated:

maxWithdraw: `"MUST factor in both global and user-specific limits, like if withdrawals are entirely disabled (even temporarily) it MUST return 0."`.
maxRedeem: `"MUST factor in both global and user-specific limits, like if redemption is entirely disabled (even temporarily) it MUST return 0."`.

Therefore, if `cooldown` is on, `maxWithdraw` and `maxRedeem` must return 0, however that currently isn't this case since the default openzeppelin functions are used, as mentioned above. This violates EIP-4626 standards.

> Although withdrawal and redemption are still possible via `unstake()` after cooldown period has passed, the ERC-4626 `withdraw()` and `redeem()` functions are still disabled, so `maxWithdraw()` and `maxRedeem()` MUST return 0.

## Recommended Mitigation Steps

Add `maxWithdraw()`, `maxRedeem()` functions in the `StakingLPEth` contract and override them. Proceed to return 0 if the user's max withdrawal/redemption reverts due to MIN_SHARES violation. Note that underflow from the subtraction is not a concern because owner shares can never exceed the total shares issued.

In addition, ensure to return 0 if `cooldown period` is on.

```diff
+   function maxWithdraw(address owner) public view virtual override returns (uint256) {
+       uint256 sharesAfterMaxWithdraw = totalSupply() - balanceOf(owner);
+       if ((sharesAfterMaxWithdraw > 0 && sharesAfterMaxWithdraw < MIN_SHARES) || cooldownDuration != 0) return 0;
+       return _convertToAssets(balanceOf(owner), Math.Rounding.Down);
+   }
```

```diff
+   function maxRedeem(address owner) public view virtual override returns (uint256) {
+       uint256 sharesAfterMaxRedeem = totalSupply() - balanceOf(owner);
+       if ((sharesAfterMaxRedeem > 0 && sharesAfterMaxRedeem < MIN_SHARES) || cooldownDuration != 0) return 0;
+       return balanceOf(owner);
+   }
```

I will also note that although `maxWithdraw()` and `maxRedeem()` functions are used in `cooldownAssets` and `cooldownShares`, these functions returning 0 will not be an issue because a user can only burn as many shares as they hold. So if they attempt to specify an amount of assets for withdrawal that exceeds how much they deposited, the call will revert when attempting to burn the corresponding shares.
