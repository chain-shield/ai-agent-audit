# Vulnerability details

Error in debt repayment calculation. The issue is with the interaction between the vault and the pool. Technically, the `liquidatePositionBadDebt()` performs these key steps: [#L610](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/CDPVault.sol#L610)
1. Transfers `repayAmount` from the liquidator to the pool:
```solidity
poolUnderlying.safeTransferFrom(msg.sender, address(pool), repayAmount);
```
2. Calculates the loss based on the total debt and repayment amount: [#L607](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/CDPVault.sol#L607)
```solidity
uint256 loss = calcTotalDebt(debtData) - repayAmount;
```
3. Calls the pool's `repayCreditAccount()` function with the total debt amount: [#L624](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/CDPVault.sol#L624)
```solidity
pool.repayCreditAccount(debtData.debt, 0, loss);
```
The error occurs in step 3, where `debtData.debt` is used instead of `repayAmount`. This leads to a discrepancy between the actual amount transferred to the pool and the amount recorded as repaid.

This mismatch the intention that the pool's balance should increase by exactly the repayment amount after liquidation. It can result in incorrect accounting, leading to fund losses or gains for either the protocol or users, depending on whether `debtData.debt` is greater or less than `repayAmount`.

## Impact
* Incorrect pool balance updates after liquidations
* Inconsistent state between the vault and the pool
* Violation of core accounting invariants

## Proof of Concept
The issue occurs in the liquidatePositionBadDebt() function of the CDPVault contract: [#L609/L624](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/CDPVault.sol#L609-L624)
```solidity
function liquidatePositionBadDebt(address owner, uint256 repayAmount) external whenNotPaused {
    // ...

    // Transfer the repay amount from the liquidator to the vault
    poolUnderlying.safeTransferFrom(msg.sender, address(pool), repayAmount);

    // ...

    // Incorrect debt repayment calculation
    pool.repayCreditAccount(debtData.debt, 0, loss);

    // ...
}
```
The function transfers `repayAmount` from the liquidator to the pool, but then calls `pool.repayCreditAccount()` with `debtData.debt` instead of `repayAmount`. This discrepancy leads to incorrect accounting:

* Alice, a liquidator, calls `liquidatePositionBadDebt()` with a `repayAmount` of 100 tokens.
* The function transfers 100 tokens from Alice to the pool.
* The function calculates `loss` based on the total debt and `repayAmount`.
* The function calls `pool.repayCreditAccount(debtData.debt, 0, loss)`, where `debtData.debt` might be different from the `repayAmount`.

This sequence results in the pool's balance increasing by 100 tokens, but the debt repayment being recorded as `debtData.debt`, which could be more or less than 100 tokens.

## Recommended Mitigation Steps
Update the to use `repayAmount` instead of `debtData.debt` when calling `pool.repayCreditAccount()`.
```solidity
function liquidatePositionBadDebt(address owner, uint256 repayAmount) external whenNotPaused {
    // ...

    poolUnderlying.safeTransferFrom(msg.sender, address(pool), repayAmount);

    // ...

-   pool.repayCreditAccount(debtData.debt, 0, loss);
+   pool.repayCreditAccount(repayAmount, 0, loss);

    // ... (remaining code unchanged)
}
```
