# Vulnerability details

## Impact
Admin function ```registerRewardDeposit()``` updates ```depositRewards``` before calling ```_massUpdatePools()```, this will lead to unequal distribution of rewards even when pools have the same ```allocPoint```


## Proof of Concept
If we take a look at _newRewards() method that is used to calculate newReward and newAccRewardPerShare of a pool, it is observed that when rawRewards > availableRewards, only the available rewards is used to get pool reward.
```solidity
  function _newRewards(
        VaultInfo memory pool,
        uint256 _totalAllocPoint
    ) internal view returns (uint256 newReward, uint256 newAccRewardPerShare) {
        uint256 lpSupply = pool.totalSupply;
        if (lpSupply > 0) {
            uint256 duration = block.timestamp - pool.lastRewardTime; //@audit duration not capped!
            uint256 rawReward = duration * rewardsPerSecond;

            uint256 rewards = availableRewards();
            if (rewards < rawReward) {
 @>>>              rawReward = rewards;
            }
            newReward = (rawReward * pool.allocPoint) / _totalAllocPoint; //@audit-issue UNDISTRIBUTED REWARD
            newAccRewardPerShare = (newReward * ACC_REWARD_PRECISION) / lpSupply;
        }
    }
```

### Instance
```
Pool_A alloc = 50
Pool_B alloc = 50
totalDuration = 100
rewardPerSecond = 10
poolA.lastRewardTime = 1 //init
poolB.lastRewardTime = 1 //init
```
All things being equal, both pools should get same amount of reward, but this is not so.
1. At t1 = 50; ```availableRewards()``` returns 0 //NO_REWARDS
2. A call from CDPVault_A to ```handleActionAfter()```, which calls _handleActionAfterForToken()
3. In _handleActionAfterForToken(), ```_updatePool(poolA, 100)``` is called.
4. When reward is calculated in ```_newRewards()```, ```rawReward = 0```
```
newReward = (0 * 50) / 100 = 0
```
5. After the computation, ```accountRewards``` is updated in ```_updatePool()```, this implies that availableRewards will be 0.
```solidity
 (uint256 reward, uint256 newAccRewardPerShare) = _newRewards(pool, _totalAllocPoint);
@>>>        accountedRewards = accountedRewards + reward;
        pool.accRewardPerShare = pool.accRewardPerShare + newAccRewardPerShare;
        pool.lastRewardTime = timestamp;
```
6. Now to the problem, at t2=100 admin calls
```registerRewardDeposit(1,000)``` which then increases ```availableRewards``` to 1,000.
7. When ```_massUpdatesPools()``` runs, 
```
pool_A reward = (50 * 10 * 50) / 100 = 250
pool_B reward = (100 * 10 * 50) / 100 = 500
```
8. In total pool_A reward increased by 250, while pool_B reward increased by 500.(Same point same lastRewardTime) Note pool_A lastRewardTime is now set to the current time

The design choice not to call _updateEmissions() on every interaction due to gas cost on users is an underlying reason for why pools could get reward updated at different times. 
```solidity
  // Although we would want the pools to be as up to date as possible when users
        // transfer rTokens or dTokens, updating all pools on every r-/d-Token interaction would be too gas intensive.
        // _updateEmissions();
        _updatePool(pool, totalAllocPoint);
```


However, to ensure equal splitting of rewards whenever admin registers a reward deposit, update all pools with the current available rewards before increasing ```depositedRewards```
