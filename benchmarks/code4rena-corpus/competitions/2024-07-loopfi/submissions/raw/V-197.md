# Vulnerability details

## Description
The Flashlender contract facilitates flash loans but lacks a crucial balance verification step after the flash loan is completed. This makes the contract susceptible to exploitation by tokens that do not correctly update their internal accounting, despite reporting successful transfers.

### Impact
An attacker could exploit this vulnerability by using a token that reports a successful transfer without updating the internal balance. This could lead to the protocol believing that the flash loan has been fully repaid when, in reality, it has not. The result could be a loss of funds equivalent to the entire balance of the affected token within the protocol.

In particular, tokens like USDT, which do not return true on a successful transfer, could introduce subtle bugs or even be upgraded in the future to exploit this vulnerability, leading to significant financial losses.

## Proof of Concept
An attacker deploys or uses an existing ERC20 token that does not properly update balances after a transfer but still reports success.
The attacker requests a flash loan in this token, borrowing the maximum amount available.
After using the loaned funds, the attacker returns less than the borrowed amount.
Due to the lack of a balance check, the contract does not detect the shortfall, and the protocol suffers a loss.

### Recommended Mitigation
To safeguard the protocol, implement a balance check after the flash loan is completed. Specifically, after the transferFrom function is called to repay the loan, the contract should verify that the token balance of the contract has increased by at least the borrowed amount plus the fee. This can be done by recording the contract's token balance before the loan and comparing it to the balance after the repayment. If the balance is insufficient, the transaction should be reverted.

Here’s how you might implement this:

```soliidty
function flashLoan(
    IERC3156FlashBorrower receiver,
    address token,
    uint256 amount,
    bytes calldata data
) external override nonReentrant returns (bool) {
    if (token != address(underlyingToken)) revert Flash__flashLoan_unsupportedToken();
    uint256 fee = wmul(amount, protocolFee);
    uint256 total = amount + fee;

    uint256 preBalance = underlyingToken.balanceOf(address(this));

    pool.lendCreditAccount(amount, address(receiver));

    emit FlashLoan(address(receiver), token, amount, fee);

    if (receiver.onFlashLoan(msg.sender, token, amount, fee, data) != CALLBACK_SUCCESS)
        revert Flash__flashLoan_callbackFailed();

    // reverts if not enough Stablecoin have been send back
    underlyingToken.transferFrom(address(receiver), address(pool), total);

    // Balance verification check
    uint256 postBalance = underlyingToken.balanceOf(address(this));
    if (postBalance < preBalance + fee) {
        revert Flash__flashLoan_insufficientRepayment();
    }

    pool.repayCreditAccount(total - fee, fee, 0);

    return true;
    }
    
```
This additional check ensures that the protocol is protected from potential exploits, where the loaned amount might not be fully repaid due to non-standard token behavior.
