# Vulnerability details

## Impact
The `_onIncreaseLever` function in the `PositionActionPendle` contract contains a logical flaw where it approves the entire balance of the collateral token for deposit but does not actually perform the deposit. This could leave the contract vulnerable if the deposit isn't performed immediately after, potentially leading to loss of funds or incorrect state.

### Specific Impact:
1. **Funds at Risk**: The approved tokens could be transferred by any entity that has access to the approved address, leading to potential loss of funds.
2. **Incorrect State**: The function returns the balance of the collateral token without ensuring that the deposit has been made, leading to an incorrect state in the contract.
3. **Security Vulnerability**: The approved tokens could be exploited by malicious actors if they gain access to the approved address.

## Proof of Concept
The logical flaw is present in the `_onIncreaseLever` function:

### `_onIncreaseLever` Function:
```solidity
function _onIncreaseLever(
    LeverParams memory leverParams,
    address /*upFrontToken*/,
    uint256 /*upFrontAmount*/,
    uint256 /*swapAmountOut*/
) internal override returns (uint256 addCollateralAmount) {
    if (leverParams.auxAction.args.length != 0) {
        _delegateCall(
            address(poolAction), abi.encodeWithSelector(poolAction.join.selector, leverParams.auxAction)
        );
    }
    addCollateralAmount = ICDPVault(leverParams.vault).token().balanceOf(address(this));
    IERC20(leverParams.collateralToken).forceApprove(leverParams.vault, addCollateralAmount);
    // deposit into the CDP Vault
    return addCollateralAmount;
}
```

### Proof of Concept Steps:
1. The function approves the entire balance of the collateral token for deposit.
2. However, it does not actually perform the deposit, leaving the approved tokens at risk.
3. The function returns the balance of the collateral token without ensuring that the deposit has been made.
