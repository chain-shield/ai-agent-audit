# Vulnerability details

## Impact
The ` transferAndJoin` function in the provided PoolAction.sol codebase does not utilize the `queryJoin` function from the balancerQueries contract to estimate the amount of Balancer Pool Tokens(BPT) received for provided amounts. The lack of [pre-check for slippage](https://docs.balancer.fi/reference/contracts/query-functions.html#queryjoin) and `maxAmountIn` tokens pose a significant risk for users overpaying due to changes in the pool's state between the time the transaction is sent and executed.

## Proof of Concept
When a user joins the Balancer, they must specify `maxAmointIn` which is the upper limit of each token willing to provide. This safeguard is essential for protecting against slippage-- unexpected changes in the pool state that might require more tokens than initially intended.
```solidity
function transferAndJoin(
        address from,
        PermitParams[] calldata permitParams,
        PoolActionParams calldata poolActionParams
    ) external {
        if (from != address(this)) {
            if (poolActionParams.protocol == Protocol.BALANCER) {
                (, address[] memory assets, , uint256[] memory maxAmountsIn) = abi.decode(
                    poolActionParams.args,
                    (bytes32, address[], uint256[], uint256[])
                );

                if (assets.length != permitParams.length) {
                    revert PoolAction__transferAndJoin_invalidPermitParams();
                }

                for (uint256 i = 0; i < assets.length; ) {
                    if (maxAmountsIn[i] != 0) {
                        _transferFrom(assets[i], from, address(this), maxAmountsIn[i], permitParams[i]);
                    }

                    unchecked {
                        ++i;
                    }
                }
            } else {
                revert PoolAction__transferAndJoin_unsupportedProtocol();
            }
        }

        join(poolActionParams);
    }
```

The absence of the `queryJoin` check means that the function does not estimate the expected BPT  and corresponding token amounts. Consequently, users might end up paying more tokens than necessary due to changes in the pool's state or high slippage(Balancer is Pool low) leading to potential losses.

> Scenerio without-cheking QueryJoin:

1. Alice wants to join a Balancer Pool
2. She intends to provide 1000 tokenA and 500 token , expecting to recieve 50BPT.

>Process:

- Alice sends a transaction to join the pool with `maxAMountIn` set to 1000 Token A and 500TokenB
- Just Before her transaction executes, another trade occurs, altering the pools state.
- As a result the require amount of TokenA and TokenB increases to 1200 and 600 repectively for the same amount of BPT.

>Outcome:

- Alice transaction proceeds with original `maxAmountIn` of 1000 TokenA and 500TokenB
- She ends up providing  more tokens than intended(1200TokenA and 600TokenB) but receives only 50BPT
- Alice incurs loss due to unexpected slippage

>Scenerio with QueryJoin:

1. Alice wants to join a Balancer Pool.
2. She estimates `QueryJoin` that for 1000tokenA and 500 TokenB, considering 1% slippage, she should set `maxAmountIn` to 1010TokenA and 505TokenB.

>Process:

- Alice uses the `queryJoin` fuunction to estimate BPT and adjust `maxAmountsIn` accordingly.
- She sets `maxAmountIn` to 1010TokenA and 505TokenB.
- If the Pool state changes and the required amounts exceeded these limit, the transaction will revert protecting Alice from overpaying.

>Outcome:

- Alice transaction either succeeds within acceptable limits or revert if limit are exceeed.
- She avoids unexpected losses due to slippage and maintains control over her token amount.
