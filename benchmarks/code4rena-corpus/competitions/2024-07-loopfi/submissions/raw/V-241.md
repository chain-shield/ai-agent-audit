# Vulnerability details

## Impact

A malicious user can brick the `StakingLp` contract by donating a minuscule amount of `LpEth` to the contract. It is not unusual for the `StakingLp.Eth` pool to hold no `LpETH` as well as no shares since users will stake them immediately. This will burn their shares and transfer the `LpEth` to the `Silo` contract leaving the pool empty. 

## Proof of Concept: 2024-07-loopfi/src/test/unit

**Prerequisites for an Attack:**

- Empty Pool
- 0 Total Supply

Add the test below to `2024-07-loopfi/src/test/unit/StakingLp.t.sol`:

```solidity
function test_deposit_user1() public {

    vm.startPrank(user2);         // Malicious user aims to brick the contract
    liquidityPool.transfer(address(stakingLpEth), 1e13);
    vm.stopPrank();

    vm.startPrank(user1);
    liquidityPool.approve(address(stakingLpEth), 2 ether);
    vm.expectRevert();
    stakingLpEth.deposit(2 ether , user1);
    vm.stopPrank();

}
```
`Run the Following Command`
```shell
forge test --match-contract StakingLP --match-test test_deposit_user1 -vvvv
```
This attack is possible because the fix for a common donation attack vulnerability was to set a minimum deposit value using _checkMinShares. While this requirement prevents the typical donation attack, it inadvertently introduces another vulnerability. An attacker can exploit this by disrupting the deposit mechanism, effectively bricking the contract.

## Tools Used

- Foundry

## Recommended Mitigation Steps

The simplest approach, though it incurs a cost to the protocol, is to deposit the minimum required shares and assets during the protocol's creation, making these values immutable. Alternatively, virtual assets and shares could be used to avoid this cost.
