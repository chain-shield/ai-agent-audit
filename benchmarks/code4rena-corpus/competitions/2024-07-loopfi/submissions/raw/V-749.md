# Vulnerability details

### Issue
The `_deposit` function in the `PoolV3` contract allows users to deposit underlying tokens into the pool in exchange for pool shares. However, the current implementation does not account for slippage, which can lead to users receiving fewer shares than expected when the pool's underlying token balance changes between the time the deposit is initiated and completed.

There should be a `slippage` parameter in the `_deposit` function that represents the maximum percentage of slippage the user is willing to accept. Before proceeding with the deposit, validate that the actual shares minted do not fall below the expected shares adjusted for the slippage.

### Code

```solidity
function _deposit(address receiver, uint256 assetsSent, uint256 assetsReceived, uint256 shares) internal {
        IERC20(underlyingToken).safeTransferFrom({from: msg.sender, to: address(this), value: assetsSent}); // U:[LP-6,7]

        _updateBaseInterest({
            expectedLiquidityDelta: assetsReceived.toInt256(),
            availableLiquidityDelta: 0,
            checkOptimalBorrowing: false
        }); // U:[LP-6,7]

        _mint(receiver, shares); // U:[LP-6,7]
        emit Deposit(msg.sender, receiver, assetsSent, shares); // U:[LP-6,7]
    }
```

### Impact
Loss of assets

### Scenario
1. User A wants to deposit 100 underlying tokens and is willing to accept a maximum slippage of 2%.
2. The `_deposit` function calculates that they should receive 100 shares.
3. If the actual shares minted fall below 98 shares (100 - 2%), the transaction will revert, preventing the user from proceeding with an unfavorable deposit.

### Fix
Introduce a user-defined slippage parameter that allows users to specify the maximum acceptable slippage for their deposit. This will enable users to manage their risk and ensure they receive a minimum number of pool shares based on their expectations.
