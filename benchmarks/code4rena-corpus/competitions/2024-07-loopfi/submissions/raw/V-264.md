# Vulnerability details


## Description 

The `ChefIncentivesController` contract is responsible for managing and distributing rewards to stakers in the protocol. It utilizes an emission schedule and a reward per second rate to calculate and distribute rewards over time. The [`_updateEmissions()` function](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/ChefIncentivesController.sol#L439-L447) plays a crucial role in this process by updating the reward emission rate based on the current time and available rewards.

The `_updateEmissions` function calls the [`endRewardTime()` function](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/ChefIncentivesController.sol#L872-L902) to determine if the reward distribution should stop. The `endRewardTime()` function calculates the end time for reward distribution based on the available rewards and the current [`rewardsPerSecond`](https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/reward/ChefIncentivesController.sol#L150). If the current time exceeds the calculated end time, it sets `rewardsPerSecond` to 0, effectively stopping the reward distribution.

However, there is a flaw in the `_updateEmissions()` function that can lead to premature cessation of reward distribution. The function relies on the `endRewardTime()` method to determine when to stop emissions, but it does not consider whether there are still rewards available for distribution.

The problematic code is located in the `_updateEmissions()` function:

```solidity
File: ChefIncentivesController.sol
439:     function _updateEmissions() internal {
440:         if (block.timestamp > endRewardTime()) {
441:             _massUpdatePools();
442:             lastRPS = rewardsPerSecond;
443:             rewardsPerSecond = 0;
444:             return;
445:         }
446:         setScheduledRewardsPerSecond();
447:     }

```

The issue arises because the function sets `rewardsPerSecond` to 0 based solely on the current time exceeding `endRewardTime()`, without checking if there are still rewards available. This can result in a scenario where rewards are no longer distributed even though there are unclaimed rewards in the contract.

## Impact

The premature stopping of reward distribution can lead to an unfair allocation of rewards among stakers. Some stakers may miss out on rewards they are entitled to, while others may receive a disproportionate share. 

Moreover, if the contract owner adds more rewards after the distribution has stopped, these new rewards may become locked in the contract, as the `rewardsPerSecond` will remain at 0, preventing any further distribution.

While the total amount of rewards is still bounded by the contract's balance, the uneven distribution and potential locking of rewards represent a significant deviation from the expected behavior of the reward system.

## Proof of Concept

1. **Initial Setup**:
   - The contract has 1000 tokens available for rewards.
   - The `rewardsPerSecond` is set to 10 tokens per second.
   - The `endRewardTime()` function calculates that rewards should end at time T based on the current `rewardsPerSecond` and available rewards.

2. **Time Progression**:
   - At time T-1, the contract is distributing rewards as expected.
   - At time T, the `endRewardTime()` function determines that the reward distribution should stop because the calculated end time has been reached.

3. **Function Call**:
   - At time T+1, a user interaction triggers the `_updateEmissions()` function.
   - The `_updateEmissions()` function calls `endRewardTime()` to check if the reward distribution should stop.

4. **Issue Occurrence**:
   - The `endRewardTime()` function returns a time less than the current block timestamp (T+1), indicating that the reward distribution should stop.
   - The `_updateEmissions()` function sets `rewardsPerSecond` to 0, effectively stopping the reward distribution.

5. **Remaining Rewards**:
   - There are still 100 tokens left for rewards in the contract.
   - Despite the remaining rewards, they are no longer distributed because `rewardsPerSecond` is now 0.

6. **Impact on Users**:
   - Users who are supposed to receive rewards after time T+1 will not receive any rewards because the reward distribution has stopped.
   - This results in an unfair allocation of rewards, as some users may miss out on rewards they are entitled to, while others may receive a disproportionate share.

7. **Adding More Rewards**:
   - If the contract owner adds more rewards after the distribution has stopped, these new rewards may become locked in the contract.
   - The `rewardsPerSecond` will remain at 0, preventing any further distribution of the newly added rewards.

## Recommended Mitigation Steps

To fix this issue, the `_updateEmissions()` function should check if there are still rewards available before setting `rewardsPerSecond` to 0. Here's the recommended change:

```diff
function _updateEmissions() internal {
-   if (block.timestamp > endRewardTime()) {
+   if (block.timestamp > endRewardTime() && availableRewards() == 0) {
        _massUpdatePools();
        lastRPS = rewardsPerSecond;
        rewardsPerSecond = 0;
        return;
    }
    setScheduledRewardsPerSecond();
}
```

This change ensures that reward distribution only stops when both the end time has passed and there are no more rewards available. It prevents the premature stopping of reward distribution and ensures all available rewards are properly allocated to stakers.
