About a year ago, the Balancer team announced a vulnerability related to read-only reentrancy in the Balancer Vault.

The issue involves a race condition between data reported by the Balancer Vault and data reported by Balancer pools. Any piece of external code querying both simultaneously:

Data from the Balancer Vault (usually token balances via Vault.getPoolTokens()).
Data from Balancer pools, can be manipulated by an attacker via a pool join or exit, as the mismatched data at the point of reentrancy will be used to compute highly inaccurate prices. Some calls to just the pool such as `update()`  also query the Vault, thus fulfilling both data requests with only a single call from the integrating code base.

The Balancer team introduced a very simple fix: any piece of code querying the data mentioned above should protect itself by calling VaultReentrancyLib.ensureNotInVaultContext() to force a trigger of the Balancer Vault's internal reentrancy check within a read-only call.
