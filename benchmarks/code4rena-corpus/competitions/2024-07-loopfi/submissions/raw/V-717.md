# Vulnerability details

## Impact
The setPoolQuotaKeeper function, which is responsible for setting a new Pool Quota Keeper contract, lacks adequate protection against reentrancy attacks. While some functions in the contract are protected using the nonReentrant modifier, this critical function is not, leaving it susceptible to potential reentrancy attacks that could exploit the state of the contract during the update process.

```
function setPoolQuotaKeeper(address newPoolQuotaKeeper)
    external
    override
    configuratorOnly
    nonZeroAddress(newPoolQuotaKeeper)
{
    if (IPoolQuotaKeeperV3(newPoolQuotaKeeper).pool() != address(this)) {
        revert IncompatiblePoolQuotaKeeperException();
    }

    poolQuotaKeeper = newPoolQuotaKeeper;

    uint256 newQuotaRevenue = IPoolQuotaKeeperV3(poolQuotaKeeper).poolQuotaRevenue();
    _setQuotaRevenue(newQuotaRevenue);

    emit SetPoolQuotaKeeper(newPoolQuotaKeeper);
}
```

The setPoolQuotaKeeper function interacts with external contracts (IPoolQuotaKeeperV3), specifically calling functions like poolQuotaRevenue() which could potentially introduce reentrancy points if the external contract is malicious or compromised.


Lack of Reentrancy Protection: Unlike other functions in the contract that are protected with the nonReentrant modifier, this function lacks such protection, increasing the risk of reentrancy attacks.


An attacker could exploit this by re-entering the function before the state updates are finalized, potentially manipulating the poolQuotaKeeper or the quotaRevenue calculations, leading to financial discrepancies or other unintended consequences.


## Proof of Concept
An attacker deploys a malicious contract as the new PoolQuotaKeeper and tricks the protocol into accepting it.

The malicious contract could include a fallback function that calls setPoolQuotaKeeper again before the original call completes.
This could lead to unintended state changes, including inconsistent updates to the poolQuotaKeeper and quotaRevenue, potentially allowing the attacker to manipulate funds.


```
contract MaliciousPoolQuotaKeeper {
    address poolV3;

    constructor(address _poolV3) {
        poolV3 = _poolV3;
    }

    function pool() external view returns (address) {
        return poolV3;  // Returns the address of PoolV3, passing the check
    }

    function poolQuotaRevenue() external returns (uint256) {
        // Reenter the `setPoolQuotaKeeper` function
        IPoolV3(poolV3).setPoolQuotaKeeper(address(this));
        return 0;
    }
}
```

By exploiting this, the attacker could cause the PoolV3 contract to enter an inconsistent state, potentially allowing them to manipulate the quotaRevenue or even crash the protocol by looping the reentrancy attack.

Financial Loss: The attacker could manipulate the pool’s quota revenue, resulting in incorrect fund distribution or even siphoning funds from the protocol.
Operational Instability: Reentrancy could lead to unpredictable behavior, making the protocol unstable and potentially causing it to freeze or crash.
Security Risk: If exploited, this vulnerability could be used to drain funds or disrupt the pool's operations, causing significant financial and reputational damage to the protocol.

## Recommended Mitigation Steps
Apply Reentrancy Protection: Add the nonReentrant modifier to the setPoolQuotaKeeper function to prevent reentrant calls.

```
function setPoolQuotaKeeper(address newPoolQuotaKeeper)
    external
    override
    configuratorOnly
    nonZeroAddress(newPoolQuotaKeeper)
    nonReentrant  // Add this line
{
    ...
}
```

Ensure that any external contracts interacted with are thoroughly audited and cannot be compromised or used to launch a reentrancy attack.
