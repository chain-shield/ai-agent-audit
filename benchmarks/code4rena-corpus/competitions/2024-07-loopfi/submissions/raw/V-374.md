# Vulnerability details

## Proof of Concept
The `PoolV3` contract allows for separate calls to `mintProfit` and `repayCreditAccount`, which can lead to an inconsistent pool state. The `mintProfit` function increases the pool's expected liquidity, while `repayCreditAccount` decreases it based on any losses. However, these operations are not atomic and don't account for each other, potentially resulting in incorrect calculations of the pool's expected liquidity.
Consider the following sequence:
1. Credit manager calls `mintProfit`:
```solidity
function mintProfit(uint256 amount) external creditManagerOnly {
    _mint(treasury, amount);

    _updateBaseInterest({
        expectedLiquidityDelta: amount.toInt256(),
        availableLiquidityDelta: 0,
        checkOptimalBorrowing: false
    });
}
```
This increases the pool's expected liquidity by `amount`.

2. Credit manager then calls `repayCreditAccount`:
```solidity
function repayCreditAccount(
    uint256 repaidAmount,
    uint256 profit,
    uint256 loss
) external override creditManagerOnly {
    // ... (other operations)

    _updateBaseInterest({
        expectedLiquidityDelta: -loss.toInt256(),
        availableLiquidityDelta: 0,
        checkOptimalBorrowing: false
    });

    // ... (other operations)
}
```
This decreases the pool's expected liquidity by `loss`, without considering the previously minted profit.

The core issue lies in the fact that these operations can be called separately and in any order. If `mintProfit` is called before `repayCreditAccount`, it leads to the following problems:
1. Incorrect liquidity calculation: The `expectedLiquidityDelta` in `repayCreditAccount` only considers the loss (`-loss.toInt256()`), ignoring any previously minted profit.
2. Inconsistent state updates: The pool's state is updated twice, potentially with conflicting information.

For example, consider this sequence:
1. Credit manager calls `mintProfit`($100$).
- Expected liquidity increases by $100$.
- $100$ shares are minted to the treasury.
2. Credit manager then calls `repayCreditAccount`($200$, $100$, $50$).
- Another $100$ shares are minted to the treasury (double minting).
- Expected liquidity is decreased by $50$ (the loss), ignoring the previous increase of $100$.
This sequence results in:
- $200$ shares minted to the treasury instead of the intended $100$.
- Expected liquidity is decreased by $50$ (the loss), ignoring the previous increase of $100$.

## Impact
The primary impact of this vulnerability is the potential for significant mispricing of loans and incorrect assessment of the pool's liquidity. Due to the inconsistent pool state, interest rates may be calculated incorrectly, leading to either underpriced or overpriced loans. This could result in unfair advantages for some users while potentially causing financial losses for others or the protocol itself. The inaccurate liquidity assessment could also lead to over-borrowing, putting the pool at risk of insolvency in extreme cases.
## Tools Used
Manual
## Recommended Mitigation Steps
Combine profit minting and repayment into a single atomic operation within the `repayCreditAccount` function.
