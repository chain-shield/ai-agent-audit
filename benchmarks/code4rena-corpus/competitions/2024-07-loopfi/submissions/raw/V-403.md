# Vulnerability details

### [M-1] Discrepancy between `ChefIncentivesController::depositedRewards` and contract balance can lead to Inflated Rewards

**Description:** 
The `ChefIncentivesController::registerRewardDeposit` function allows the owner to register a reward deposit without ensuring that the corresponding tokens are transferred to the contract. If the owner registers a reward deposit with a given amount, but transfers a lower value (or none at all), the `ChefIncentivesController::depositedRewards` variable will be artificially high. This discrepancy can affect reward calculations, enabling users to claim higher rewards than they should, according to the real contract balance, potentially exhausting the protocol's funds.

The core issue is that the `ChefIncentivesController::depositedRewards` variable does not require to transfer that token amount to the contract, leading to discrepancies in the contract's token balance and the recorded deposited rewards.


This opens the door of reward manipulation by the owner: users would expect higher rewards than the protocol can really afford.

```javascript
    function registerRewardDeposit(uint256 _amount) external onlyOwner {
        depositedRewards = depositedRewards + _amount; 
        _massUpdatePools();
        if (rewardsPerSecond == 0 && lastRPS > 0) {
            rewardsPerSecond = lastRPS;
        }
        emit RewardDeposit(_amount);
    }
```

**Impact:** 
Under the above circumstance, users that claim rewards immediately, will get a higher amount than the expected one. Subsequently, late users will not be able to claim any rewards at all since the contract will run out of funds, as demonstrated in the proof of concept below.

Furthermore, once the variable `ChefIncentivesController::depositedRewards` is increased it cannot be decreased by any circumstance. 
The only way to proceed from this situation would be to transfer the miss-match amount of tokens to the contract. If the owner does not have such amount, the rewards system will be broken. Then, a subsequent solution would be to mint more tokens and transferring it to the contract, but this will affect the overall tokenomics of the protocol.


**Proof of Concept:**
As an owner, we mint and transfer an amount of 2_000 tokens, whereas when calling the `registerRewardDeposit` function, we register a reward deposit of 3_000 tokens (1_000 tokens higher than the actual amount we transfer).
Then, we simulate 2 users eraning rewards, and we can see how user1 is able to claim more rewards than what they should, given the current contract real balance, whereas user2 is not able to claim any rewards at all, since the protocol didn't have enough funds `(1_500+1_500 > 2_000)`.

1. Paste this function into the `Tokenomics.t.sol` file
2. Run `forge test --mt test_pocDespositedRewardsAbuse -vvvv`
3. See how user1 is able to claim rewards
4. Uncomment `incentivesController.claim(user2, vaults);` line
5. See how user2 is not able to claim rewards after user1 has claimed, as the protocol runs out of rewards
6. Updated the `incentivesController.registerRewardDeposit(3_000 ether);` to 2_000 ether value
7. Run again the tests
8. See how both users are now able to `claim` the rewards

```javascript
function test_pocDespositedRewardsAbuse() public {
    // Mint and transfer tokens
    loopToken.mint(address(this), 2_000 ether);
    loopToken.transfer(address(incentivesController), 2_000 ether);

    // Incorrectly set a higher amount in the registerRewardDeposit function
    // Nothing prevents this call to revert, as there is no check that this value matches the toke transfer amount  
    incentivesController.registerRewardDeposit(3_000 ether);

    // Users Setup
    address user1 = vm.addr(uint256(keccak256("user1")));
    address user2 = vm.addr(uint256(keccak256("user2")));

    // User 1 operations
    _borrow(user1, 100 ether, 50 ether);
    uint256 depositNeededForReward = 2.51 ether / 2;
    _depositInPool(user1, depositNeededForReward);

    vm.startPrank(user1);
    uint256 balance1 = ERC20(address(govWeightedPool)).balanceOf(user1);
    ERC20(address(govWeightedPool)).approve(address(multiFeeDistribution), balance1);
    multiFeeDistribution.stake(balance1, user1, 0);
    vm.stopPrank();

    // User 2 operations
    _borrow(user2, 100 ether, 50 ether);
    _depositInPool(user2, depositNeededForReward);

    vm.startPrank(user2);
    uint256 balance2 = ERC20(address(govWeightedPool)).balanceOf(user2);
    ERC20(address(govWeightedPool)).approve(address(multiFeeDistribution), balance2);
    multiFeeDistribution.stake(balance2, user2, 0);
    vm.stopPrank();

    // Simulate time passing
    vm.warp(block.timestamp + 30 days);

    address[] memory vaults = new address[](1);
    vaults[0] = address(vault);

    // Log pending rewards before claiming
    // See they are inflated 1500000000000000000000 instead of 1000000000000000000000
    emit log_named_uint("inflated pending rewards for user 1", incentivesController.allPendingRewards(user1)); //1500000000000000000000
    emit log_named_uint("inflated pending rewards for user 2", incentivesController.allPendingRewards(user2)); //1500000000000000000000

    // Claim rewards for user1
    // This action will go through as the protocol has enough LOOP tokens
    incentivesController.claim(user1, vaults);

    // Claim rewards for user2
    // This action won't go through as the protocol won't have enough LOOP tokens to accomodate the 2 inflated reward values
    // Uncomment line below to see the revert
    // incentivesController.claim(user2, vaults);
    
    // Log pending rewards after claiming
    emit log_named_uint("pendingRewardsUser1After", incentivesController.allPendingRewards(user1));
    //emit log_named_uint("pendingRewardsUser2After", incentivesController.allPendingRewards(user2));

    // Simulate time passing for vesting period
    (, , EarnedBalance[] memory earnedBalancesUser1) = multiFeeDistribution.earnedBalances(user1);
    vm.warp(block.timestamp + 100 days);
    
    // Log loop token balance before and after withdrawing for user1
    vm.startPrank(user1);
    emit log_named_uint("balanceBeforeUser1", loopToken.balanceOf(user1));
    multiFeeDistribution.withdraw(earnedBalancesUser1[0].amount);
    emit log_named_uint("balanceAfterUser1", loopToken.balanceOf(user1));
    vm.stopPrank();
}
```

**Recommended Mitigation:** 
Ensure that an equal or higher amount of `rewardAmount` is transferred, when calling `ChefIncentivesController::depositedRewards` before updating depositedRewards variable.
Revert if such transfer doesn't happen.

**Risk Rating:**
- Impact: High
- Likelihood: Low
