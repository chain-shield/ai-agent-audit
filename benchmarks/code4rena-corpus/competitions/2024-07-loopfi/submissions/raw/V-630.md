# Vulnerability details

## Impact
Denial of Service to Users Who want Zero Slippage in MultiFeeDistribution contract even when the slippage value is within the maximum allowed which would cause lose of value to users who intend to work with zero slippage.
## Proof of Concept
```solidity
   // Maximum slippage allowed to be set by users (used for compounding).
    uint256 public constant MAX_SLIPPAGE = 9000; //10%
    uint256 public constant PERCENT_DIVISOR = 10000; //100%
```
The code above shows that the maximum allowed slippage in the contract should be 10% by setting MAX_SLIPPAGE as 9000, this means since the percent divisor is 10000, 10000 would mean 0% slippage, 9900 means 1% slippage, 9800 means 2% slippage, 9700 means 3% slippage, 9500 means 5% slippage and so on all the way to 9000 being 10% slippage.

The code above shows how users slippage is set, it can be noted based on the pointer above that a validation is done to ensure slippage stays within the limited range of maximum of 10% in between MAX_SLIPPAGE and PERCENT_DIVISOR. However there seems to be a flaw as code would revert when slippage is exactly equal PERCENT_DIVISOR or 0% slippage. This would denial users who intend to work with a zero percent slippage.
An assumption might be made that since zero slippage might not always be the case in transactions, so setting zero slippage would revert user transactions but this does not change the fact that user should be allowed to aim for zero slippage if they wish to since it is still within the maximum allowed

## Recommended Mitigation Steps
As adjusted below setting user slippage should only revert if slippage is above the percent divisor and not when it is equal it which will ensure that users who intends to work with zero slippage are allowed to.
