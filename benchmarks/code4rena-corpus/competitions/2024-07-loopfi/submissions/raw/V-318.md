# Vulnerability details

## Impact
Users funds can become stuck, if their transfer method is `Permit2`.

## Proof of Concept

The PositionAction contract inherits from the TransferAction contract to use the `_transferFrom` function:

```solidity
    function _transferFrom(
        address token,
        address from,
        address to,
        uint256 amount,
        PermitParams memory params
    ) internal {
        if (params.approvalType == ApprovalType.PERMIT2) {
            // Consume a permit2 message and transfer tokens.
            ISignatureTransfer(permit2).permitTransferFrom(
                ISignatureTransfer.PermitTransferFrom({
                    permitted: ISignatureTransfer.TokenPermissions({token: token, amount: params.approvalAmount}),
                    nonce: params.nonce,
                    deadline: params.deadline
                }),
                ISignatureTransfer.SignatureTransferDetails({to: to, requestedAmount: amount}),
                from,
                bytes.concat(params.r, params.s, bytes1(params.v)) // Construct signature
            );
        } else if (params.approvalType == ApprovalType.PERMIT) {
            // Consume a standard ERC20 permit message
            IERC20Permit(token).safePermit(
                from,
                to,
                params.approvalAmount,
                params.deadline,
                params.v,
                params.r,
                params.s
            );
            IERC20(token).safeTransferFrom(from, to, amount);
        } else {
            // No signature provided, just transfer tokens.
            IERC20(token).safeTransferFrom(from, to, amount);
        }
    }
```

The function has 3 approval types:

1. Permit2 (directly transfers the tokens to the recipient using a signature)
2. ERC20Permit (gives approval using a signature) and then transfers them
3. Regular transferFrom (user approved the caller of spending the tokens)

As per [EIP-2612](https://eips.ethereum.org/EIPS/eip-2612#security-considerations), which defines the permit function for ERC-20 tokens, the function is designed to allow a token holder to approve a spender using a signed message without requiring an on-chain transaction from the token holder. This mechanism introduces a potential for front-running.

Per the EIP, while the signer of a Permit may intend for a specific party to submit the transaction, another party can always front-run the transaction and call permit before the intended party does. The function does not check who initiates the call because its security relies on the signature's validity rather than the identity of the caller. The end result is that the tokens are transferred as permitted by the signature, regardless of who actually submitted the transaction.

Which means, that a malicious actor can front-run the user  extracting the signature from his transaction and call `Permit2::permitTransferFrom` to transfer the tokens to the recepient ultimately leaving the tokens stuck in the contract.


One example can be the `PositionAction::increaseLever`:


```solidity
    function increaseLever(
        LeverParams calldata leverParams,
        address upFrontToken,
        uint256 upFrontAmount,
        address collateralizer,
        PermitParams calldata permitParams
    ) external onlyDelegatecall {
        // validate the primary swap
        if (
            leverParams.primarySwap.swapType != SwapType.EXACT_IN ||
            leverParams.primarySwap.assetIn != address(underlyingToken) ||
            leverParams.primarySwap.recipient != self
        ) revert PositionAction__increaseLever_invalidPrimarySwap();

        // validate aux swap if it exists
        if (
            leverParams.auxSwap.assetIn != address(0) &&
            (leverParams.auxSwap.swapType != SwapType.EXACT_IN ||
                leverParams.auxSwap.assetIn != upFrontToken ||
                leverParams.auxSwap.recipient != self)
        ) revert PositionAction__increaseLever_invalidAuxSwap();

        // transfer any up front amount to the LeverAction contract
        if (upFrontAmount > 0) {
            if (collateralizer == address(this)) {
                IERC20(upFrontToken).safeTransfer(self, upFrontAmount); // if tokens are on the proxy then just transfer
            } else {
                _transferFrom(upFrontToken, collateralizer, self, upFrontAmount, permitParams);
            }
        }

        // take out flash loan
        IPermission(leverParams.vault).modifyPermission(leverParams.position, self, true);
        flashlender.flashLoan(
            IERC3156FlashBorrower(self),
            address(underlyingToken),
            leverParams.primarySwap.amount,
            abi.encode(leverParams, upFrontToken, upFrontAmount)
        );
        IPermission(leverParams.vault).modifyPermission(leverParams.position, self, false);
    }
```

If there is `upfrontAmount` the function transfers the tokens from the collateralizer to `self` which is the `PositionAction` contract.

If the user's approval type is Permit2 the attacker can do this:

1. User calls `PositionAction::increaseLever` passing the required params and the signature for the Permit2.
2. Attacker sees this and front-runs him by calling `Permit2::permitTransferFrom` 
 with his signature transferring the tokens to the implementation contract
3. The user transaction executes after that, but reverts due to the fact that the signature had already been used.
4. The tokens are now transfered to the implementation, with no way of getting them out.
