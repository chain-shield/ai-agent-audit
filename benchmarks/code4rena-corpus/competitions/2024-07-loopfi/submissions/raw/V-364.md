# Vulnerability details

## Impact
When a function utilizing the `_transferFrom` method in TransferAction is called with Permit2 data, the caller can set the permitted token to any token address, not necessarily the intended asset. This allows a malicious user to potentially transfer worthless tokens instead of the expected valuable assets, clearing their obligations without actually providing the correct asset.

## Proof of Concept
Take a look at the _transferFrom function in TransferAction.sol:



https://github.com/code-423n4/2024-07-loopfi/blob/57871f64bdea450c1f04c9a53dc1a78223719164/src/proxy/TransferAction.sol#L46-L81

```solidity
function _transferFrom(
        address token,
        address from,
        address to,
        uint256 amount,
        PermitParams memory params
    ) internal {
        if (params.approvalType == ApprovalType.PERMIT2) {
            // Consume a permit2 message and transfer tokens.
            ISignatureTransfer(permit2).permitTransferFrom(
                ISignatureTransfer.PermitTransferFrom({
                    permitted: ISignatureTransfer.TokenPermissions({token: token, amount: params.approvalAmount}),
                    nonce: params.nonce,
                    deadline: params.deadline
                }),
                ISignatureTransfer.SignatureTransferDetails({to: to, requestedAmount: amount}),
                from,
                bytes.concat(params.r, params.s, bytes1(params.v)) // Construct signature
            );
        } else if (params.approvalType == ApprovalType.PERMIT) {
            // Consume a standard ERC20 permit message
            IERC20Permit(token).safePermit(
                from,
                to,
                params.approvalAmount,
                params.deadline,
                params.v,
                params.r,
                params.s
            );
            IERC20(token).safeTransferFrom(from, to, amount);
        } else {
            // No signature provided, just transfer tokens.
            IERC20(token).safeTransferFrom(from, to, amount);
        }
    }
```

As we can see, the `token` parameter is directly used in the `TokenPermissions` struct without any validation. There are no checks to ensure that the `token` address matches the intended asset of the contract or action being performed.

A malicious user could exploit this by:
1. Creating a worthless ERC20 token
2. Calling a function that uses _transferFrom with Permit2
3. Providing the address of their worthless token as the `token` parameter
4. Successfully "transferring" the worthless token instead of the valuable asset expected by the contract

## Tools Used
Manual review

## Recommended Mitigation Steps
Consider including a check that verifies the token being transferred is the expected one. This can be done by adding an `expectedToken` parameter to the _transferFrom function. or some sort of validation check to ensure that the `token` parameter matches the expected or intended token for the specific use case.
