S-851
deployVesting Allows Creation of Vesting Schedules with Past Start Times Enabling Immediate Token Claims
NexusAudits
31
Sufficient
383d ago
Summary

A vulnerability has been identified in the vesting schedule deployment mechanism of SecondSwap. The deployVesting function in SecondSwap_VestingDeployer lacks proper temporal validation, allowing the creation of vesting schedules that begin in the past. While the function validates that the start time precedes the end time, it fails to validate against the current blockchain timestamp.

The vulnerability stems from the interaction between SecondSwap_VestingDeployer and SecondSwap_StepVesting. When a vesting schedule is deployed with a past start time, the claimable() function in SecondSwap_StepVesting calculates token availability based on elapsed time since the start. This calculation doesn't protect against past start times, leading to immediate token availability that bypasses the intended vesting period.

The impact is that it undermines the core purpose of token vesting. Token owners can exploit this by deliberately setting past start times, making a significant portion of tokens immediately claimable upon deployment.

Proof of Concept

The vulnerability manifests through the interaction of two key components in the system. First, the deployer contract allows past start times:

function deployVesting(address tokenAddress, uint256 startTime, uint256 endTime, uint256 steps, string memory vestingId) external {
    require(startTime < endTime, "SS_VestingDeployer: start time must be before end time");
    // ... deployment logic
}

This incomplete validation then interacts with the vesting calculation logic:

function claimable(address _beneficiary) public view returns (uint256, uint256) {
    uint256 currentTime = Math.min(block.timestamp, endTime);
    uint256 elapsedTime = currentTime - startTime;
    uint256 currentStep = elapsedTime / stepDuration;
    uint256 claimableSteps = currentStep - vesting.stepsClaimed;
    // ... calculation of claimable amount
}

When startTime is set to a past timestamp, elapsedTime immediately becomes significant, resulting in multiple steps being instantly claimable. For example, a vesting schedule created with a start date from several months ago would have multiple steps already "elapsed," making a proportional amount of tokens immediately available for claiming.

Recommended Mitigation Steps

The vulnerability can be addressed by implementing proper temporal validation in the deployment function. The primary fix involves adding a timestamp check:

function deployVesting(
    address tokenAddress,
    uint256 startTime,
    uint256 endTime,
    uint256 steps,
    string memory vestingId
) external {
    require(startTime >= block.timestamp, "SS_VestingDeployer: start time must be in the future");
    require(startTime < endTime, "SS_VestingDeployer: start time must be before end time");
    // ... rest of the function
}

For additional security, consider implementing a minimum future buffer to account for potential block timestamp variations and a maximum vesting duration to prevent unreasonably long vesting periods. These changes ensure that vesting schedules function as intended, maintaining the security and integrity of the token distribution mechanism.

Hi, I disagree with low severity here.

For Low severity issues, the impact is typically localized, with minimal economic effect and no breaking of core protocol assumptions which is not the case for this issue.

This issue should be medium severity considering the platform's core purpose is facilitating secure secondary market trading of vesting rights by transferring whitelisted addresses for future token claims. By allowing vesting schedules with past start times, the issue undermines this purpose. Instead of properly managing transfers of future vesting rights as intended, contracts could be created with immediate claim rights, breaking the protocol's design of secure vesting rights trading.

This is especially serious because SecondSwap is specifically designed to make OTC trading of vesting rights more secure and efficient. When vesting schedules can be created with past start times, it introduces risks in the vesting rights trading system that the platform aims to prevent. While this doesn't affect broader market prices or token liquidity (since SecondSwap only handles address whitelisting for future claims, not the tokens themselves), it does undermine the platform's core mechanism for secure vesting rights trading.

In fact looking at how F-15 has been judged.
https://code4rena.com/evaluate/2024-12-secondswap/findings/S-900

Both issues require admin/owner trigger, but F-77 is more serious because it undermines a core platform mechanism in SecondSwap. While fee changes only impact profit margins on individual trades, the vesting bypass can completely break the platform's fundamental purpose of facilitating trades of future vesting rights.

The difference in impact is:

Fee changes (F-15):

Only affects marketplace transaction costs
Impact limited to individual trades on SecondSwap
Only affects direct marketplace participants

Vesting bypass (F-77):

Breaks SecondSwap's core mechanism for trading future vesting rights
Affects the integrity of vesting right transfers within the platform
Undermines the platform's guarantee of maintaining existing vesting schedules
Impacts protocols integrating with SecondSwap for vesting rights trading

F-77 severely impacts the platform's core functionality and security guarantees for vesting rights trading hence medium is more fitting.

Medium: Assets not at direct risk, but the function of the protocol or its availability could be impacted
