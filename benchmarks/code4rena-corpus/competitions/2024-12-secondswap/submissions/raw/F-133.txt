`VestingTransferred` event can be griefed with duplicate / forged transaction Ids leading off-chain data corruption
YouCrossTheLineAlfie
00
Sufficient
383d ago
Finding description and impact

The SecondSwap_VestingDeployer::transferVesting function can be used by the token issuer for transferring vesting.
This function uses a transactionId as an unique identifier, which is passed down in the emitted event as well

    function transferVesting(
        address _grantor,
        address _beneficiary,
        uint256 _amount,
        address _stepVesting,
        string memory _transactionId     <@ - // Used by off-chain mechanism for reconciliation
    ) external {

The issue lies with the way this function is being permissioned

        require(
            _tokenOwner[msg.sender] == address(SecondSwap_StepVesting(_stepVesting).token()),     <@ - // This allows a malicious _stepVesting contract to be passed
            "SS_VestingDeployer: caller is not the token owner"
        ); // 3.2. Arbitrary transfer of vesting

A greif attack can happen by following these steps:-

Create a malicious _stepVesting contract which has a token variable set as zero address and a dummy transferVesting function.
Front-run the token issuer transaction by simply using his _transactionId which should have been "unique" as per the code documentation.
Simply spamming events with any kind of _transactionId would also count as griefing.

This can simply overwhelm the off-chain mechanism here.

Impact

Griefing of off-chain mechanism and by-passing the unique transaction Id identifier design which is not optimal.

Recommended mitigation steps

It is recommended to use a registry contract instead to disallow such attacks
