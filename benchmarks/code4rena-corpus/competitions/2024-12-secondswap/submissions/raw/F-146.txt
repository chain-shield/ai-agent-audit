S-912
Creating a vesting for a user that is past the last claim step will lock the tokens
gesha17
57
Sufficient
383d ago
Finding description and impact

When creating a vesting, the amount that is being assigned to the benificiary is calculated based on how many steps are left. If the beneficiary has claimed past the last step, then the releaseRate is set to 0. This means that any new tokens that are assigned to this beneficiary will essentially become locked.

This can happen by chance or by an honest mistake E.g. a token owner decides to grant some extra tokens to a benificiary at the last step, seeing the beneficiary has not yet claimed his tokens, but the beneficiary decides to claim his tokens just before the owners transaction executes, so the tokens become locked.

This can be somewhat mitigated by the beneficiary - he can make a listing and spot purchase the amount using another address that has not claimed any steps, so the funds will be only temporarily locked, he will however have to pay buyer and seller fee. So impact is temporarily locked funds, broken protocol function and loss of fees.

Proof of Concept

The createVesting function will set the release rate to 0 if the user has already claimed all steps:

https://github.com/code-423n4/2024-12-secondswap/blob/main/contracts/SecondSwap_StepVesting.sol#L279

    function _createVesting(
        ...
            if (numOfSteps - _vestings[_beneficiary].stepsClaimed != 0) {
                _vestings[_beneficiary].releaseRate =
                    (_vestings[_beneficiary].totalAmount - _vestings[_beneficiary].amountClaimed) /
                    (numOfSteps - _vestings[_beneficiary].stepsClaimed);
            } else {
                // @audit if all steps are claimed by the beneficiary, set releaseRate to 0
                _vestings[_beneficiary].releaseRate = 0;
            }
        ...
    }
Recommended mitigation steps

If the beneficiary has already claimed all steps, make the transction revert instead of setting the releaseRate to 0.
