S-381
Using the `currentAllocation` to calculate the `sellLimit` breaks the functionality of the ´maxSellPercent´ variable
BenRai
74
Sufficient
383d ago
Impact

Because the currentAllocation is used to calculate the amount of unvested tokens a user can sell, after a while all unvested tokens will be sellable breaking the purpose of the ´maxSellPercent´ variable. This will increase the potential supply of listed vestings over time which will result in a lower marked price (assuming the same demand but higher supply). This will lead to substantial financial loss for users wanting to sell their listing since they will need to sell for a lower price.

Proof of Concept

The SecondSwap_VestingManager contract manages the vesting and selling of tokens through the listVesting() function. This function checks if the vesting plan is sellable and verifies the user's sellLimit tokens allowing a sale.

However, the logic for calculating the sellLimit is flawed.

The relevant code snippet is as follows:

uint256 sellLimit = userAllocation.bought;
uint256 currentAlloc = SecondSwap_Vesting(plan).total(seller);
if (currentAlloc + userAllocation.sold > userAllocation.bought) {
sellLimit +=
     ((currentAlloc + userAllocation.sold - userAllocation.bought) vestingSettings[plan].maxSellPercent) /
     BASE;
}

The sellLimit is calculated for the case a ´maxSellPercent´ is set for the vesting. The ´maxSellPercent´ should limit the amount of unvested tokens that can be sold. E.g. if ´maxSellPercent´ is set to 50%, only 50% of the unvested tokens should be sellable. So if we have vesting with a total of 1000 tokens, 10 steps and the maxSellPercent set to 50%, in the beginning of the vesting only 50% of the max tokens (500 tokens) should be sellable. When 5 steps are unlocked, only 50% of the remaining locked tokens (500 tokens * 50% = 250 tokens) should be sellable.

The issue arises from the fact that the currentAllocation is used to calculate the sellable amount without taking into account how many steps have been unlocked already. This means that with ´maxSellPercent´ set to 50% all unvested tokens will be sellable after half of the steps are unlocked

Scenario Illustration
Alice has an allocation of 200 tokens and the ´maxSellPercent´ for the vesting is set to 50%. The vesting has 10 steps and therefore the releaseRate of Alice is 200/10 = 20 tokens /step
5 steps are unlocked and Alice claims her unlocked tokens resulting in 20 * 5 = 100 claimed tokens and 100 tokens which are still locked
Since 5 steps are already unlocked and the ´maxSellPercent´ for the vesting is set to 50%, Alice should only be able to sell 50% * 100 tokens = 50 tokens of her unvested tokens. But since the currentAlocation is used to calculate the sellLimit, Alice can sell 200 * 50% = 100 tokens which is 100% of her unvested tokens
Recommended Mitigation Steps

Consider adjusting the currentAllocation by the number of steps unlocked before using it for the calculation of the sellLimit. E.g. if the currentAllocation is 200, the vesting has 10 steps and 5 steps are already unlocked, adjust the currentAllocation to 200 – (200/10 * 5) = 200 - 100 = 100 tokens

Hi Koolex, thank you for judging!

THIS ISSUE is not a duplicate of S-140. 140 describes how the maxSellPercentage can be broken because users can sell vestings they bought before even though they already claimed some of the bought vesting.

THIS ISSUE is about how the calculation of maxSellPercentage is broken even if no sales or buys have happens before.

Both issues are different which is also reflected in their different root causes.
The root of 140 is in the fact that any previously bought vestings can be sold again, no matter if they have been claimed in the meantime.

The root cause for THIS ISSUE is that the current allocation is used to calculate the sell limit without taking into account how many steps have already been unlocked.

The two different root causes need to be fixed in different ways therefore the two issues should not be the same.
