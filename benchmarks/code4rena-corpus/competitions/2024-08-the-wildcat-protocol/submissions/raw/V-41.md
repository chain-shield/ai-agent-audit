# Vulnerability details

## Description
The `WildcatMarketBase` contract's `_processExpiredWithdrawalBatch` function performs non-atomic state updates when processing expired withdrawal batches. This function updates multiple state variables and storage structures sequentially, including `_withdrawalData.unpaidBatches`, `state.pendingWithdrawalExpiry`, and `_withdrawalData.batches`. If the function reverts mid-execution due to out-of-gas errors, arithmetic issues, or external call failures, or for any reason, it could leave the contract in an inconsistent state.

Specifically, the following scenarios could occur:

1. A batch could be added to `unpaidBatches` without its state being updated in the batches mapping.
2. A batch could be processed multiple times if `pendingWithdrawalExpiry` is not reset.
3. Withdrawals could be lost if `pendingWithdrawalExpiry` is reset but the batch is not added to `unpaidBatches`.

The root cause of this vulnerability is the lack of atomicity in critical state updates, combined with insufficient error handling and recovery mechanisms. This makes the system susceptible to inconsistent states due to unexpected transaction reverts, which can lead to loss of user funds or denial of service, even without malicious intent.

## Impact
- loss of user funds if withdrawals are lost or processed incorrectly
- denial of service if the withdrawal system enters an inconsistent state
- Increased gas costs for users if batches are processed multiple times
- Reduced trust in the protocol if withdrawal processing becomes unreliable
- In a worst-case scenario, a significant portion of withdrawal requests in a batch could be lost or incorrectly processed, potentially leading to temporary or permanent loss of access to funds for affected users.


## Proof of Concept
This vulnerability could manifest in several realistic scenarios. Here are two scenarios:

Scenario 1: Out-of-Gas Error:

1. The Wildcat market has been operating for some time and has accumulated a large number of withdrawal batches.
2. A significant number of users queue withdrawals just before a batch expiry, causing the batch size to grow substantially.
3. The market's `totalAssets()` increases due to a large repayment from the borrower, making more liquidity available for withdrawals.
4. When `updateState()` is called (either by a user interaction or an automated process), it triggers `_processExpiredWithdrawalBatch()`.
5. The function starts processing the large batch, performing multiple storage reads and writes.
6. When attempting to push the batch to `_withdrawalData.unpaidBatches`, the transaction runs out of gas due to the array's large size.
7. The transaction reverts after adding the batch to `unpaidBatches` but before updating the batch in `_withdrawalData.batches`.
8. The market is left in an inconsistent state with a phantom batch in the unpaid queue.

Scenario 2: External Call Failure:

1. The Wildcat market is using an underlying asset that experiences technical issues (e.g., a stablecoin with periodic pauses, an underlying asset has a blacklist functionality and the user is blacklisted, underlying asset experiences transfer freeze or has dynamic transfer fees or is being upgraded, etc).
2. A withdrawal batch expires during a period of high market volatility, causing many users to attempt withdrawals simultaneously.
3. The `updateState()` function is called, triggering `_processExpiredWithdrawalBatch()`.
4. When calculating `availableLiquidity`, the function calls `totalAssets()`, which in turn calls `balanceOf()` on the underlying asset contract.
5. Due to network congestion or the temporary issue with the asset contract, this external call fails.
6. The transaction reverts after resetting `pendingWithdrawalExpiry` but before adding the batch to `unpaidBatches`.
7. The market loses track of the expired batch, potentially causing those withdrawals to be lost.

## Recommended Mitigation Steps
Implement a two-phase commit process for critical state updates:
First, mark the batch as "processing" in a single storage operation.
Then, perform the necessary updates.
Finally, mark the batch as "processed" or revert to the original state if there's an error.

Use a single storage slot to track critical batch state where possible, reducing the number of separate storage writes.

Implement additional checks in the `updateState` function to detect and correct inconsistencies:
- Verify that batches in `unpaidBatches` exist in the batches mapping.
- Ensure that `pendingWithdrawalExpiry` is consistent with the batch state.
