# Vulnerability details

## Description

The _executeWithdrawal function in the WildcatMarketWithdrawals contract currently lacks a validation check for sufficient funds in the market’s internal accounting before executing a withdrawal. This missing check can result in attempted withdrawals of amounts that exceed the market’s immediately available liquid reserves, causing the transaction to revert.

According to the sponsor on Discord ([see here](https://discord.com/channels/810916927919620096/1277986359893819433/1279744467951157248)), it is expected behavior for withdrawal requests to exceed the market’s liquid reserves. When this happens, all current liquid assets are moved to the withdrawal pool, and the borrower must repay the market to cover the withdrawal request and meet the required reserve limit. 

Despite this, withdrawals should only proceed when the market’s internal accounting (state.normalizedUnclaimedWithdrawals) confirms sufficient funds are available to prevent unexpected transaction failures.


Let's take a look at the current implementation:
```
function _executeWithdrawal(
    MarketState memory state,
    address accountAddress,
    uint32 expiry,
    uint baseCalldataSize
  ) internal returns (uint256) {
    WithdrawalBatch memory batch = _withdrawalData.batches[expiry];
    // If the market is closed, allow withdrawal prior to expiry.
    if (expiry >= block.timestamp && !state.isClosed) {
      revert_WithdrawalBatchNotExpired();
    }

    AccountWithdrawalStatus storage status = _withdrawalData.accountStatuses[expiry][
      accountAddress
    ];

    uint128 newTotalWithdrawn = uint128(
      MathUtils.mulDiv(batch.normalizedAmountPaid, status.scaledAmount, batch.scaledTotalAmount)
    );

    uint128 normalizedAmountWithdrawn = newTotalWithdrawn - status.normalizedAmountWithdrawn;

    if (normalizedAmountWithdrawn == 0) revert_NullWithdrawalAmount();

    hooks.onExecuteWithdrawal(accountAddress, normalizedAmountWithdrawn, state, baseCalldataSize);

    status.normalizedAmountWithdrawn = newTotalWithdrawn;
    state.normalizedUnclaimedWithdrawals -= normalizedAmountWithdrawn;

    if (_isSanctioned(accountAddress)) {
      // Get or create an escrow contract for the lender and transfer the owed amount to it.
      // They will be unable to withdraw from the escrow until their sanctioned
      // status is lifted on Chainalysis, or until the borrower overrides it.
      address escrow = _createEscrowForUnderlyingAsset(accountAddress);
      asset.safeTransfer(escrow, normalizedAmountWithdrawn);

      // Emit `SanctionedAccountWithdrawalSentToEscrow` event using a custom emitter.
      emit_SanctionedAccountWithdrawalSentToEscrow(
        accountAddress,
        escrow,
        expiry,
        normalizedAmountWithdrawn
      );
    } else {
      asset.safeTransfer(accountAddress, normalizedAmountWithdrawn);
    }

    emit_WithdrawalExecuted(expiry, accountAddress, normalizedAmountWithdrawn);

    return normalizedAmountWithdrawn;
  }
```
When _executeWithdrawal is called, it doesn't check if there are sufficient funds in the market to cover the withdrawal. It calculates the withdrawal amount based on the batch data, without considering the current balance of the market.

## Impact
Without this validation check, the function might allow withdrawals that exceed the market’s immediate liquid reserves, which could lead to:

1. Failed Transactions: As the sponsor noted, the market can go “notionally delinquent” if borrowing up to the reserve limit, and it becomes delinquent in the next block due to accrued interest or fees. This could cause withdrawals to revert unexpectedly.

2. Misalignment with Protocol Behavior: The missing check disrupts the intended behavior that withdrawals should only use assets counted as paid within the corresponding batch, a principle upheld by the contract’s main invariants.



## Proof of Concept
This vulnerability can be demonstrated through the following scenario:
1. A lender deposits a large amount and requests a withdrawal.
2. The borrower subsequently withdraws a significant portion of the market’s funds.
3. When the lender’s withdrawal is executed, if the total available funds (state.normalizedUnclaimedWithdrawals) have been depleted below the requested amount, the transaction would attempt to withdraw more than available, resulting in a revert.



Here is the test function

function testValidation() public {

    vm.startPrank(lender);

## Recommendation
To avoid this issue, implement the following check in the _executeWithdrawal function:
```
if (state.normalizedUnclaimedWithdrawals < normalizedAmountWithdrawn) {
    revert_InsufficientMarketFunds();
}
```
This check ensures that the internal accounting (state.normalizedUnclaimedWithdrawals) confirms sufficient liquid funds are available to cover the withdrawal amount before proceeding. This change aligns with the protocol’s design, which allows temporary depletion of reserves but expects borrowers to restore them promptly.

The sponsor have confirmed that this behavior is standard, and the market should operate under the assumption that reserves will be replenished, but the contract logic must still enforce vital checks.
