# Vulnerability details

## Summary
The WildcatMarketConfig contract currently contains functions, such as nukeFromOrbit, that are not related to configuration but rather to security and account management. These functions are out of place in a configuration contract and should be relocated to a more appropriate contract, such as WildcatMarketSecurity, if necessary.

Additionally, the WildcatMarketConfig contract’s inheritance from WildcatMarketBase seems unnecessary and introduces confusion.

## Vulnerability Details
The WildcatMarketConfig contract is designed to handle configuration settings like total supply, interest rates, and reserve ratios. However, the presence of non-configurational functions like nukeFromOrbit, which involves account blacklisting and sanctions, deviates from the core purpose of the contract.

Additionally, inheriting from WildcatMarketBase is unnecessary for a configuration contract. These issues make the contract less modular, harder to maintain, and potentially confusing for developers who expect it to strictly deal with market configurations.

## Impact
This design issue affects the modularity and clarity of the codebase. By mixing configuration-related logic with account security functions and unnecessary inheritance, the WildcatMarketConfig contract becomes more difficult to understand and maintain.

This could lead to increased complexity when scaling or auditing the contract, as non-related functionalities are bundled together.

## Proof of Concept
The nukeFromOrbit function is a security function that sanctions accounts by transferring balances to an escrow, which has nothing to do with setting market configuration parameters:

solidity

function nukeFromOrbit(address accountAddress) external nonReentrant sphereXGuardExternal {
    if (!_isSanctioned(accountAddress)) revert_BadLaunchCode();
    MarketState memory state = _getUpdatedState();
    hooks.onNukeFromOrbit(accountAddress, state);
    _blockAccount(state, accountAddress);
    _writeState(state);
}
This function should be part of a separate contract focused on security operations, not part of configuration logic.

## Tools Used
Manual code review

## Recommended Mitigation Steps
Move the nukeFromOrbit function and any other non-configurational functions to a separate contract, such as WildcatMarketSecurity, where account management and sanctions can be handled more appropriately.

The WildcatMarketConfig contract should be strictly used for managing configurational parameters like interest rates, total supply, and reserve ratios, to maintain clarity and modularity.

Also, the inheritance from WildcatMarketBase should be removed to ensure the contract is focused purely on configuration without introducing unnecessary functionality or dependencies.
