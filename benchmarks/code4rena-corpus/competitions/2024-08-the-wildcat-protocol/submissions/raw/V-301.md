# Vulnerability details

## Impact
Users can exploit the withdrawal batch mechanism to significantly reduce their waiting times for withdrawals, creating an unfair advantage over other users and potentially disrupting the intended fairness of the withdrawal process. This could lead to unequal treatment of users within the same withdrawal cycle.

## Proof of Concept
The root cause of this issue lies in the fixed expiry time for withdrawal batches and the lack of differentiation between early and late withdrawals within a batch. This allows users to strategically time their withdrawal requests to minimize their waiting period.

The key components enabling this are:

In [WildcatMarketWithdrawals.sol](https://github.com/code-423n4/2024-08-wildcat/blob/main/src/market/WildcatMarketWithdrawals.sol#L80-L99), the `_queueWithdrawal` function sets a fixed expiry for the entire batch:

```solidity
  function _queueWithdrawal(
    MarketState memory state,
    Account memory account,
    address accountAddress,
    uint104 scaledAmount,
    uint normalizedAmount,
    uint baseCalldataSize
  ) internal returns (uint32 expiry) {

    // Cache batch expiry on the stack for gas savings
    expiry = state.pendingWithdrawalExpiry;

    // If there is no pending withdrawal batch, create a new one.
    if (state.pendingWithdrawalExpiry == 0) {
      // If the market is closed, use zero for withdrawal batch duration.
      uint duration = state.isClosed.ternary(0, withdrawalBatchDuration);
      expiry = uint32(block.timestamp + duration);
      emit_WithdrawalBatchCreated(expiry);
      state.pendingWithdrawalExpiry = expiry;
    }  

```

The `withdrawalBatchDuration` is set as an immutable public variable in [WildcatMarketBase.sol](https://github.com/code-423n4/2024-08-wildcat/blob/main/src/market/WildcatMarketBase.sol#L64):

```solidity
/// @dev Time before withdrawal batches are processed.
uint public immutable withdrawalBatchDuration;
```

**Technical explanation**:
- A WildcatMarket is deployed with a specific `withdrawalBatchDuration` (let's say 7 days), This duration is stored as an immutable public variable.
- When the first withdrawal is queued and no batch exists, a new batch is created, The batch expiry is set to `current_timestamp + withdrawalBatchDuration`, This expiry is stored in `state.pendingWithdrawalExpiry`.  
Now what happens:
- All withdrawals queued before the batch expiry are added to the current batch.
- They all share the same expiry timestamp, regardless of when they were queued.
- Withdrawals can only be executed after the batch expiry (unless the market is closed).
- All withdrawals in a batch are processed simultaneously when executed.
- *Users queuing withdrawals early in the batch period wait longer than those queuing late.* The system doesn't differentiate between early and late withdrawals within a batch.
  


**Exploit Flow - Bob withdrawing before Alice**:
Certainly! Here's a flow for the PoC test function in a similar style:

Let's assume a 7-day withdrawal batch duration and that both Alice and Bob want to withdraw 100 tokens from their 1000 token deposits.
So Alice and Bob both deposit 1000 tokens into the market.

Day 1:
- Alice queues a withdrawal for 100 tokens.
- This creates a new withdrawal batch with expiry set to Day 8.

Day 7 (1 hour before batch closes):
- Bob monitors the blockchain and sees the batch will close soon.
- Bob queues a withdrawal for 100 tokens in the same batch.

Day 8 (just after batch expiry):
- The withdrawal batch expires.
- Both Alice and Bob can now execute their withdrawals.

Day 8 (moments after expiry):
- Both Alice and Bob execute their withdrawals simultaneously.
- Despite Alice queuing 7 days earlier, both withdrawals are processed at the same time.

**Result**:
- Alice waited 7 days for her withdrawal (7 days in the batch).
- Bob only waited 1 hour for his withdrawal (1 hour in the batch).
- Both Alice and Bob receive approximately 100 tokens.
- Bob effectively "cut the line" and got his funds out much quicker than Alice, despite Alice initiating the withdrawal much earlier.

If the market doesn't have enough liquidity to process all withdrawals, they're processed on a pro-rata basis, This means Bob's late entry doesn't penalize him in terms of withdrawal priority or amount. In a scenario with multiple batch cycles due to liquidity constraints, **Bob could repeatedly use this tactic to maintain shorter average waiting times compared to users like Alice who queue withdrawals early**.

This exploit doesn't break the system's rules, but it creates an unfair advantage for users who understand and leverage the batch mechanics, potentially at the expense of less savvy users or those who can't time their actions as precisely.

```Solidity
function test_withdrawalBatchTimingExploit() external {
    // Set up
    uint256 initialDeposit = 1000e18;
    uint256 withdrawalAmount = 100e18;
    
    // Alice and Bob both deposit
    _deposit(alice, initialDeposit);
    _deposit(bob, initialDeposit);
    
    // Fast forward to day 1
    vm.warp(block.timestamp + 1 days);
    
    // Alice queues a withdrawal on day 1
    vm.prank(alice);
    market.queueWithdrawal(withdrawalAmount);
    
    uint32 batchExpiry = market.currentState().pendingWithdrawalExpiry;
    
    // Fast forward to just before batch closes (day 7 in our example)
    vm.warp(batchExpiry - 1 hours);
    
    // Bob queues a withdrawal just before the batch closes
    vm.prank(bob);
    market.queueWithdrawal(withdrawalAmount);
    
    // Fast forward to just after batch expiry
    vm.warp(batchExpiry + 1);
    
    // Record balances before withdrawal
    uint256 aliceBalanceBefore = asset.balanceOf(alice);
    uint256 bobBalanceBefore = asset.balanceOf(bob);
    
    // Both execute withdrawals
    vm.prank(alice);
    market.executeWithdrawal(alice, batchExpiry);
    vm.prank(bob);
    market.executeWithdrawal(bob, batchExpiry);
    
    // Check that both Alice and Bob received approximately the same amount
    uint256 aliceWithdrawn = asset.balanceOf(alice) - aliceBalanceBefore;
    uint256 bobWithdrawn = asset.balanceOf(bob) - bobBalanceBefore;
    
    assertApproxEqRel(aliceWithdrawn, bobWithdrawn, 1e16, "Alice and Bob should receive approximately the same amount");
    assertApproxEqRel(aliceWithdrawn, withdrawalAmount, 1e16, "Withdrawn amount should be close to requested amount");
    
    // Verify that Bob waited much less time than Alice for the same outcome
    uint256 aliceWaitTime = (batchExpiry + 1) - (block.timestamp - 7 days);
    uint256 bobWaitTime = (batchExpiry + 1) - (batchExpiry - 1 hours);
    
    assertTrue(bobWaitTime < aliceWaitTime, "Bob's wait time should be significantly less than Alice's");
    assertApproxEqAbs(bobWaitTime, 1 hours, 1 minutes, "Bob's wait time should be about 1 hour");
    assertApproxEqAbs(aliceWaitTime, 7 days, 1 hours, "Alice's wait time should be about 7 days");
    
    // Log the actual wait times and withdrawn amounts for clarity
    console.log("Alice wait time (in days):", aliceWaitTime / 1 days);
    console.log("Bob wait time (in hours):", bobWaitTime / 1 hours);
    console.log("Alice withdrawn amount:", aliceWithdrawn);
    console.log("Bob withdrawn amount:", bobWithdrawn);
}
```

## Recommended Mitigation Steps
