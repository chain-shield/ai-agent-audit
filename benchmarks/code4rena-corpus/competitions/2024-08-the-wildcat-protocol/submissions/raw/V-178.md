# Vulnerability details

## POC

In the wildcat protocol there are AccessControlHooks and `FixedTermLoanHooks` contracts and thet both have a function that allows the borrow to block and unblock the lender from depositing. When blocking the lender the lender's credententials are unset  `status.unsetCredential();` that is when it becomes tricky because when unblocking the user the credentials were not set back using `status.setCredential()`, thus the unblocked lender is unable to deposit.

To prove this, add this code to the `BaseMarketTest.sol`

```solidity

function _unBlockLender(address account) internal asAccount(parameters.borrower) {
    hooks.unblockFromDeposits(account);
  }

```
To test that an unblocked lender cannot deposit anymore run the following:

```solidity
function test_lenderCantDepositAfterUnblocked() external {
    // Authorize the lender Alice
    _authorizeLender(alice);

    vm.startPrank(alice);
    uint256 amount = 50_000e18;

    //deposit in market
    market.deposit(amount);
    vm.stopPrank();

    // Block a lender
    _blockLender(alice);
    //unblock lender
    _unBlockLender(alice);

    vm.startPrank(alice);
    // @audit-info deposit again in market this time it will not pass and throw an error of NotApprovedLender
    // I decided to use expectRevert because I don't want to throw an error
    vm.expectRevert(IMarketEventsAndErrors.NotApprovedLender.selector);
    market.deposit(amount);
    vm.stopPrank();
  }

```

## Impact

A lender whose status is set to blocked will be permanently blocked and wont be able to deposit anymore even if the borrowers tries to unblock them.

## Recommended mitigation

The functions logic of `AccessControlHooks::unblockFromDeposits` should be updated with `status.setCredential()` to update the lender status.
