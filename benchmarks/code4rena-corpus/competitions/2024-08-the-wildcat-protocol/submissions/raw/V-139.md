# Vulnerability details

## Description
The Wildcat protocol's hook system allows for arbitrary `extraData` to be appended to certain function calls. This `extraData` is not directly handled by the market functions, but is instead extracted and processed by the corresponding hook functions. Crucially, the size of this `extraData` is not bounded, potentially allowing malicious actors to create transactions with extremely high gas costs.

The following functions in the Wildcat protocol allow for arbitrary `extraData` to be appended to their calldata:

- `deposit` and `depositUpTo`: These functions allow for extra data. They call `_depositUpTo` which uses the `hooks.onDeposit` function that processes extra data.
- `queueWithdrawal` and `queueFullWithdrawal`: These functions also allow for extra data, calling `_queueWithdrawal` which uses `hooks.onQueueWithdrawal`.
- `transfer` and `transferFrom`: These functions call `_transfer`, which allows for extra data, using `hooks.onTransfer`.
- `borrow`: This function allows for extra data, using `hooks.onBorrow`.
- `repay`: These functions allow for extra data, using `hooks.onRepay`.
(and more)

This unbounded `extraData` mechanism introduces a potential vector for gas griefing attacks. An attacker could exploit this vulnerability by appending a large amount of unnecessary data to a transaction, such as a deposit or withdrawal. For example, they could add megabytes of meaningless data to a deposit transaction, significantly increasing its gas cost.

This could be exploited to disrupt normal protocol operations by making certain functions prohibitively expensive for other users to call. This could potentially lead to denial of service conditions or allow the attacker to gain unfair advantages in market operations during critical periods.

The lack of an upper bound on the size of `extraData` creates a security risk that needs to be addressed.


## Impact
- Denial of Service (DoS): Critical functions that rely on hooks could become too expensive to call, preventing legitimate users from interacting with specific parts of the protocol. This could affect operations such as deposits, withdrawals, or transfers.

- Market Manipulation: Attackers could use this vulnerability to manipulate market conditions by making it too expensive for other users to perform certain actions, potentially gaining an unfair advantage in trading or liquidity provision.

- Unpredictable Transaction Costs: The variable size of `extraData` could lead to highly unpredictable transaction costs for users, potentially discouraging participation in the protocol and reducing overall liquidity.


## Proof of Concept
To demonstrate this vulnerability, an attacker could exploit the deposit function in the Wildcat protocol, which allows for arbitrary `extraData` to be appended. Here's a proof of concept:

1. The attacker prepares a deposit transaction for a Wildcat market, appending a large amount of meaningless data (e.g., several kilobytes) as `extraData`.

2. The attacker submits this transaction to the network.

3. When the transaction is processed, the deposit function executes normally, but the gas cost is much higher than usual due to the large `extraData`.

4. Other users attempting to interact with the same market function (e.g., making deposits) would now face prohibitively high gas costs, effectively pricing them out of using the protocol.

5. The attacker could repeat this process with multiple transactions, creating a sustained denial of service condition for regular users.

Scenario 2:

1. The attacker could append so much extra data that the transaction approaches or exceeds the Ethereum block gas limit (currently around 30 million gas). This could cause the transaction to fail entirely for other users.

2. By spamming multiple such transactions from different addresses, the attacker could potentially fill entire blocks, preventing any other transactions involving the targeted Wildcat functions from being processed.

3. This could result in a temporary Denial of Service condition, where legitimate users are unable to deposit, withdraw, or transfer funds(and are unable use other impacted functions) using the Wildcat protocol.

This attack could be timed to coincide with periods of high market activity for maximum impact. 

It's important to note that while theoretically the `extraData` could be unlimited in size, it would be practically constrained by Ethereum's block gas limits. However, even within these limits, the gas costs could be made high enough to disrupt normal protocol operations.

This proof of concept demonstrates how the unbounded `extraData` in hook functions could be exploited to create economic denial of service conditions in the Wildcat protocol, potentially disrupting market operations and fairness.

## Recommended Mitigation Steps
- Adding a constant MAX_EXTRA_DATA_SIZE (e.g., 1024 bytes) to the protocol.

- Modifying the hook calling functions to check the size of `extraData` before processing.

- Implement this check in relevant functions such as `onDeposit`, `onQueueWithdrawal`, `onTransfer`, etc.

This mitigation would maintain the flexibility of the hook system while preventing extreme gas consumption. The limit should be carefully chosen to allow for legitimate use cases (such as complex proofs or signatures) while preventing abuse. Additionally, consider implementing a gas limit for hook executions to ensure that individual hooks cannot consume an unreasonable amount of gas.

By implementing these measures, the protocol can significantly reduce the risk of gas griefing attacks while preserving the functionality of the hook system.
