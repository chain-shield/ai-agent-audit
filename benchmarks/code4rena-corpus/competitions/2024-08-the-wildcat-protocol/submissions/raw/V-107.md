# Vulnerability details

## Proof of Concept
The `queueWithdrawal` function in the contract allows users to request a withdrawal, which is then queued. This withdrawal process relies on available liquidity in the market. If all liquidity has been burnt or withdrawn from the contract, it becomes impossible to fulfill these withdrawal requests, even though they are still being queued.

Here's the relevant portion of the `queueWithdrawal` function:
```solidity
function queueWithdrawal(
    uint256 amount
  ) external nonReentrant sphereXGuardExternal returns (uint32 expiry) {
    MarketState memory state = _getUpdatedState();

    uint104 scaledAmount = state.scaleAmount(amount).toUint104();
    if (scaledAmount == 0) revert_NullBurnAmount();

    // Cache account data
    Account memory account = _getAccount(msg.sender);

    return
      _queueWithdrawal(state, account, msg.sender, scaledAmount, amount, _runtimeConstant(0x24));
  }

function queueFullWithdrawal()
    external
    nonReentrant
    sphereXGuardExternal
    returns (uint32 expiry)
  {
    MarketState memory state = _getUpdatedState();

    // Cache account data
    Account memory account = _getAccount(msg.sender);

    uint104 scaledAmount = account.scaledBalance;
    if (scaledAmount == 0) revert_NullBurnAmount();

    uint256 normalizedAmount = state.normalizeAmount(scaledAmount);

    return
      _queueWithdrawal(
        state,
        account,
        msg.sender,
        scaledAmount,
        normalizedAmount,
        _runtimeConstant(0x04)
      ); // @audit if a user calls queueFullWithdrawal after all liquidity has been burnt, their withdrawal will be queued but cannot be immediately fulfilled.
  }
```
In the `queueFullWithdrawal` function, the contract allows users to queue a full withdrawal of their funds. However, if all liquidity in the contract has already been burnt (i.e., no assets remain), users are still able to queue their withdrawal requests, but these requests cannot be immediately fulfilled. This results in users being placed in the withdrawal queue indefinitely without receiving their funds.
The issue occurs because the function `_queueWithdrawal` queues the withdrawal request even if the contract no longer has sufficient liquidity to process it. The withdrawal process depends on the `scaledAmount` (the user's balance) and `normalizedAmount` (the amount converted into a normalized form). However, if all liquidity is burnt, the queue will be filled with withdrawal requests that cannot be fulfilled due to the absence of assets in the contract.
This is highly likely to occur in cases where the contract has undergone liquidity burns, especially if users continue to interact with the contract after liquidity has been removed, assuming their withdrawals will still be processed.

## Impact
Users who attempt to withdraw their funds after liquidity is burnt will have their withdrawals queued but will not be able to access their funds, potentially indefinitely. This can lead to frustration among users and a loss of trust in the protocol, as it gives the false impression that withdrawals are still possible when in reality, there are no available assets to fulfill these requests.


## Tools Used
Manual
## Recommended Mitigation Steps
Add a liquidity check within the `queueFullWithdrawal` function to ensure that the contract holds enough assets to cover the withdrawal before queuing the request.
