# Vulnerability details

## Description:

The WildcatMarket contracts utilizes the Spherex `sphereXGuardExternal` protection for certain critical methods. However, when these methods are invoked within loops (or via MultiCall contracts), the Spherex protection requires an explicit allowance for every possible loop iteration or combination of called methods. This design leads to false positives in Transaction Flow (TF) and Control Flow (CF) protection modes, causing unintended reverts for integrators and users of the Wildcat protocol.

## Code Snippet:

The `executeWithdrawals` method in the `WildcatMarketWithdrawals` contract is guarded by the Spherex protection as follows:

```javascript
@-> function executeWithdrawals(address[] calldata accountAddresses, uint32[] calldata expiries)
        external
        nonReentrant
        sphereXGuardExternal
        returns (uint256[] memory amounts)
    {
        if (accountAddresses.length != expiries.length) revert_InvalidArrayLength();

        amounts = new uint256[](accountAddresses.length);

        MarketState memory state = _getUpdatedState();

        for (uint256 i = 0; i < accountAddresses.length; i++) {
            // Use calldatasize() for baseCalldataSize to indicate no data should be passed as `extraData`
            amounts[i] = _executeWithdrawal(state, accountAddresses[i], expiries[i], msg.data.length);
        }
        // Update stored state
        _writeState(state);
        return amounts;
    }
```

## Impact:

- **False Positives in Transaction Flow (TF):** If a third-party integrator calls the Spherex-guarded methods like `queueWithdrawal` or `executeWithdrawals` within a loop or via a MultiCall contract, the transaction will revert due to improper loop handling by the Spherex guard.
- **False Positives in Control Flow (CF):** If a protected method calls another protected method in a loop (e.g., `executeWithdrawals` calling `_executeWithdrawal` in a loop), the CF protection could lead to reverts even though the operations are legitimate.
- **Decreased Usability for Integrators:** Third-party contracts cannot realistically predict or control loop lengths or method combinations, making it challenging to integrate with Wildcat protocol’s withdrawal functionalities. This could deter integrators from utilizing these functions, reducing the overall attractiveness of the protocol.

## Proof of Concept (PoC):

Consider the method `executeWithdrawals(address[] calldata accountAddresses, uint32[] calldata expiries)` which processes withdrawals for multiple accounts. This method invokes the internal `_executeWithdrawal` method within a `for` loop. In Spherex's TF mode, if a third-party contract or user calls this method with multiple accounts using a MultiCall, the following scenario can occur:

#### Scenario:

1. A third-party contract or user calls `executeWithdrawals` with multiple `accountAddresses` and `expiries`:
   ```solidity
   WildcatMarketWithdrawals.executeWithdrawals(accounts, expiries);
   ```
2. Inside the method, `_executeWithdrawal` is called in a loop:

   ```solidity
   for (uint256 i = 0; i < accountAddresses.length; i++) {
       amounts[i] = _executeWithdrawal(state, accountAddresses[i], expiries[i], msg.data.length);
   }
   ```

3. Spherex's TF protection expects individual allowances for each possible loop length and each method combination. Since this allowance cannot realistically cover all possibilities, the transaction reverts even though the contract logic is sound.

4. For example, if there are 3 account addresses passed in the call, the Spherex guard may not have the correct allowance for each loop iteration, causing a false positive revert.

---

## Recommendation:

1. **Avoid Instrumentation of Loops:** Prohibit Spherex from applying guards to methods that are invoked within loops. In this case, consider disabling the Spherex guard for the entire `executeWithdrawals` method or ensuring that calls within loops are excluded from protection.

2. **Modify Spherex Guard Logic:** Update the Spherex guard to intelligently handle looped method calls by permitting variable-length loops and method combinations, or allow more flexible permissions to handle these edge cases.

3. **Consider Using an Allowance Buffer:** Implement a buffer mechanism in Spherex that allows for a predefined number of loop iterations without triggering false positives, reducing the need for explicit permissions.
