# Vulnerability details

## Summary
The Wildcat protocol architecture allows borrowers to deploy multiple markets with potentially conflicting sanction rules due to compliance requirements. The current implementation does not handle cases where an account may be sanctioned for one market but not for others, leading to ambiguity in sanction enforcement across multiple markets - deployed by the same borrower. This can result in inconsistent application of sanctions and potential misuse or exploitation by borrowers.

## Impact
This vulnerability can undermine the integrity and effectiveness of the sanction mechanism limiting borrower's specificity on which markets the sanction override should be applied to.

## Proof of Concept
### Code Snippets highlighting vulnerability:
1. Sanction Check Implementation: The `isSanctioned` function in `WildcatSanctionsSentinel` checks if an account is sanctioned but does not account for market-specific overrides.
```solidity
function isSanctioned(address borrower, address account) public view override returns (bool) {
    return !sanctionOverrides[borrower][account] && isFlaggedByChainalysis(account);
  }
```
2. Sanction Override Mechanism: The sanctionOverrides mapping allows borrowers to override sanctions, but it applies uniformly without considering market-specific contexts.
```solidity
mapping(address borrower => mapping(address account => bool sanctionOverride))
    public
    override sanctionOverrides;
```
### Ambiguity Scenario:

1. Borrower deploys two or more markets with different sanction rules (with intension to maintain the sanction in one market and override the sanction in the other market).
2. Borrower overrides a sanction in one market and not in the others.
3. Override applies uniformly without considering market-specific contexts which undermines the agreement that: **A market and its goings-on are between the borrowers and lenders alone**.

## Tools Used
Manual review, VSCode

## Recommended Mitigation Steps
1. Modify the sanction override logic to be aware of market-specific contexts and prevent conflicts between different markets.
```solidity
mapping(address borrower => mapping(address market => mapping(address account => bool))) public sanctionOverrides;
```
2. Ensure that all functions that interact with sanctions or overrides account for the market context. This includes modifying `overrideSanction` and `removeSanctionOverride` to take a market address or identifier.
```solidity
function isSanctioned(address borrower, address market, address account) public view override returns (bool) {
  return !sanctionOverrides[borrower][market][account] && isFlaggedByChainalysis(account);
}
```
