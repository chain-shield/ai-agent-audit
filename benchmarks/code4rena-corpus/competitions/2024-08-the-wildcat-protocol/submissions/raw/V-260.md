# Vulnerability details

## Proof of Concept
### Potential Problem: Mixing of `account` and `escrowContract`
The mapping `sanctionOverrides[borrower][account]` expects the inner key to represent an account. However, in the `createEscrow` function, the `escrowContract` is being used as the inner key instead of an `account`.
**Issue:** This would lead to confusion/unintended behavior because the mapping could end up storing two different types of entities (accounts and escrow contracts) under the same `account` keyspace. This is problematic because account is expected to represent only user accounts.

### Consequence
1. Ambiguity in keys: You would be mixing user accounts and escrow contracts in the same keyspace (account). This could lead to situations where the sanction overrides might apply in unintended ways. For example, if the same address is used both as an account and as an escrow contract (which is possible), this can lead to confusion in how overrides are applied especially since the borrower has the final say in both cases.

2. Clashing types of overrides

## Recommended Mitigation Steps
- Introduce a separate mapping for escrow overrides
```solidity
mapping(address borrower => mapping(address escrowContract => bool sanctionOverride)) public sanctionEscrowOverrides;
```
