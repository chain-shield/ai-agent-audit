# Vulnerability details

##Proof of Concept

A critical vulnerability has been identified in the WildcatMarketBase contract related to the misuse of inline assembly in the _isSanctioned function. This vulnerability allows an attacker to bypass sanction checks, enabling them to interact with the contract even if they are on a sanctions list. The issue arises due to incorrect placement of the function selector and improper alignment of arguments in the assembly code, which leads to malformed calldata being sent to the sentinel contract. 

The vulnerability is located in the _isSanctioned function, which uses inline assembly to call the isSanctioned function on the sentinel contract:

Incorrect Function Selector Placement >
The function selector 0x06e74444 (first 4 bytes of the Keccak-256 hash of isSanctioned(address,address)) is stored at memory address 0x00 using mstore(0, 0x06e74444).
However, mstore writes 32 bytes to memory, and since 0x06e74444 is only 4 bytes, it is stored in the most significant 4 bytes of the 32-byte word, leaving the least significant 28 bytes as zeros.
This misaligns the function selector in the calldata, as the Ethereum ABI expects the function selector to be in the first 4 bytes (least significant bytes) of the calldata.

Function Selector Misplacement:
Incorrect: mstore(0, 0x06e74444)
Stores the 4-byte selector in the most significant bytes of the 32-byte word at address 0x00.
Correct: mstore(0, shl(224, 0x06e74444))
Shifts the selector 28 bytes to the left, placing it in the least significant bytes.


Expected Calldata Layout:

To align with the Ethereum ABI and the EVM's memory model, the calldata should be constructed as follows >

- Bytes 0-3 (most significant bytes): Function selector (4 bytes).
- Bytes 4-35: First argument (borrower).
- Bytes 36-67: Second argument (account).
Note: In EVM memory, the function selector needs to be placed in the most significant 4 bytes of the 32-byte word at the starting memory address.
Actual Calldata Sent:

Due to misalignment, the calldata does not conform to the expected layout, leading to incorrect processing by the sentinel contract.

Note : The Ethereum ABI specifies that the function selector occupies the first 4 bytes of calldata, followed by arguments, each occupying 32 bytes.


Misaligned Arguments>
The first argument _borrower is stored at memory address 0x20 (32 bytes), and the second argument account is stored at 0x40 (64 bytes).
When constructing calldata, the function selector should be immediately followed by the arguments without any padding.
Incorrect Calldata Construction:
The staticcall uses an offset of 0x1c (28 bytes) and a size of 0x44 (68 bytes) for the calldata.
The offset of 0x1c is used to skip the initial 28 bytes of zeros before the function selector.
However, this approach is error-prone and relies on the assumption that the function selector and arguments are correctly aligned after the offset, which may not be the case.
Potential Impact >
Due to the misalignment, the sentinel contract may receive malformed calldata, causing it to either revert or process incorrect data.
If the sentinel contract does not properly validate the calldata, it might return an incorrect result, potentially indicating that a sanctioned address is not sanctioned.
This would allow an attacker on the sanctions list to bypass the checks and interact with the WildcatMarketBase contract.

##Recommended Mitigation Steps

Correct Function Selector Alignment:
Ensure that the function selector is placed in the least significant 4 bytes of the first 32-byte word.
Use bitwise shifting to align the function selector correctly.
solidity.

mstore(0, shl(224, 0x06e74444)) // We need to Shift left by 28 bytes to align the selector

We need maybe also to :

- Build the calldata by placing the function selector and arguments consecutively without unintended padding.

- Use a memory pointer to sequentially store the function selector and arguments.
