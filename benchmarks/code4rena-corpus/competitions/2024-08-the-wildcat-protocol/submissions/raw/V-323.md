# Vulnerability details

## Proof of Concept
In releaseEscrow(), the safetransfer function doesn't check the existence of code at the token address. This is a known issue while using solmate's libraries.

Also mentionned on the contract LibERC20.sol, derived from Solady, which is derived from Solmate library.
https://github.com/code-423n4/2024-08-wildcat/blob/main/src/libraries/LibERC20.sol#L16-L18

```solidity
/// @dev Note:
/// - For ERC20s, this implementation won't check that a token has code,
///   responsibility is delegated to the caller.
```

https://github.com/code-423n4/2024-08-wildcat/blob/main/src/WildcatSanctionsEscrow.sol#L41


```solidity
  function releaseEscrow() public override {
    if (!canReleaseEscrow()) revert CanNotReleaseEscrow();

    uint256 amount = balance();
    address _account = account;
    address _asset = asset;

 >  asset.safeTransfer(_account, amount);

    emit EscrowReleased(_account, _asset, amount);
  }
```

If safetransfer() is called on a token address that doesn't have contract in it, it will always return success. 

Due to this the protocol will think that Escrow has been released and successful, and records will be accordingly calculated, but in reality funds were never transferred.

This will lead to miscalculation and possibly loss of funds.

## Recommended Mitigation Steps
Consider checking that the token contract exist, for example:

```solidity
uint 256 codeSize;
assembly {
	codesize := extcodesize(_token)
}
if (codesize == 0) revert TokenContractDoesNotExist();
```
