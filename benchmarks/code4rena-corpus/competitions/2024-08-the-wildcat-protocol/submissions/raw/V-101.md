# Vulnerability details

## Proof of Concept
The contracts relies on `block.timestamp` to govern time-dependent logic. However, deploying this contract on both Ethereum L1 and L2 networks like Base, Arbitrum, and Polygon may lead to inconsistencies due to differences in how `block.timestamp` is handled across these chains.

For instance, the `_grantRole` function in the contract relies on `block.timestamp` to verify if a granted credential is valid by comparing the `newExpiry` calculated from the role provider with the current block timestamp. :
```solidity
function _grantRole(
    RoleProvider callingProvider,
    address account,
    uint32 roleGrantedTimestamp
) internal {
    LenderStatus memory status = _lenderStatus[account];

    uint256 newExpiry = callingProvider.calculateExpiry(roleGrantedTimestamp);

    // Check if the new credential is still valid
    if (newExpiry < block.timestamp) revert GrantedCredentialExpired();
    
    // Additional logic for checking previous credentials...

    _setCredentialAndEmitAccessGranted(status, callingProvider, account, roleGrantedTimestamp);
}

```
 However, since `block.timestamp` behaves differently on L1 (Ethereum) and L2 chains (like Base, Arbitrum, and Polygon), this can lead to inconsistencies in the role assignment logic.
On L2 networks, `block.timestamp` may not accurately reflect real-world time due to differences in how L2s synchronize block production with L1. As a result, the comparison between `newExpiry` and `block.timestamp` could allow expired credentials to pass the validity check, or prematurely revoke valid credentials.

For example, while Ethereum typically has 1 block every 12 seconds, resulting in a predictable auction duration of 7200 seconds for a one-day auction (5 blocks * 60 minutes * 24 hours), Layer 2 chains may have different block production times or timestamp logic, leading to discrepancies. If a similar time-based calculation is applied across multiple chains, it may lead to incorrect expiry or credential duration.

```solidity
// 1 block every 12 sec -> 5 blocks / min
uint256 auctionDuration = 7200; // Auction duration lasts for one day (5 * 60 * 24 = 7200)
```


The bug occurs because the contract depends on `block.timestamp`, which behaves differently on L2 networks due to synchronization or time offset issues. The logic in `_grantRole` and other functions assumes that `block.timestamp` will be consistent/ posses the same behaviour across all chains, which is not true in multi-chain environments involving L2 solutions.
This bug is highly likely to occur in contracts deployed on both L1 and L2 chains without addressing timestamp discrepancies. Given the popularity of multi-chain deployments for scalability and cost savings, this is a common risk.

## Impact
This inconsistency could cause credential expiration checks to fail or pass erroneously. As a result, users may receive or retain roles they are not eligible for, or their valid roles could be unjustly revoked. The misalignment between L1 and L2 timestamp mechanisms may lead to unfair access control or incorrect permissions in a multi-chain deployment.

## Tools Used
Manual Auditing
## Recommended Mitigation Steps
Replace `block.timestamp` with a trusted time oracle that provides consistent and accurate time information across all networks. Integrating an oracle like Chainlink’s time oracle would ensure uniform time-based credential validation.
