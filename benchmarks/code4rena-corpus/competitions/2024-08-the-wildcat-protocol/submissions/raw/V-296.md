# Vulnerability details

## Summary

The Wildcat protocol utilizes hooks for customized market logic, with AccessControlHooks being a prime example. This contract manages lender access and allows external role providers to validate credentials. The _tryValidateCredential function in AccessControlHooks is crucial for this validation process, using calldata to interact with external providers.

The _tryValidateCredential function in AccessControlHooks is designed to interact with external role providers to validate lender credentials. However, a flaw in its implementation causes it to revert even when a credential is successfully validated by the provider. 

This occurs because the function unconditionally throws an error if the external call succeeds but the returned data doesn't meet specific criteria, disregarding the possibility of a successful validation with different return data.

## Details

The function first retrieves the address of the role provider and checks if it exists. It then constructs calldata for the validateCredential function on the provider contract, including the lender's address and the provided credential data.

The function executes this call using assembly and checks the size of the returned data. If the returned data size is less than 32 bytes (0x20), it assumes an invalid credential and reverts with the InvalidCredentialReturned error. This behavior is incorrect because a successful validation might return less than 32 bytes of data.

The root cause of this issue lies in the assumption that a successful validation must always return at least 32 bytes of data. If the provider's validateCredential function is designed to return a simple boolean value (true for success, false for failure), or a smaller data structure, the check in the _tryValidateCredential function will always fail, leading to a revert even though the provider has validated the credential.

## Impact

This bug prevents the correct execution of the access control mechanism in Wildcat markets using the AccessControlHooks contract. If a role provider utilizes a validateCredential function that returns less than 32 bytes of data upon successful validation, the _tryValidateCredential function will consistently revert, preventing lenders from being recognized as having valid credentials. Consequently:

Lenders with valid credentials may be blocked from performing actions like deposits, transfers, or withdrawals that require access control checks.

The isKnownLenderOnMarket mapping might not be updated correctly, as successful validations are misinterpreted as failures.

## Scenario

- A borrower deploys a Wildcat market with AccessControlHooks as the hook contract, configured to use a role provider whose validateCredential function returns a boolean value indicating validation success (true for success, false for failure).
- A lender attempts to perform an action that requires a valid credential, for instance, depositing into the market.
- The _tryValidateCredential function is called, which in turn calls the validateCredential function on the role provider.
- The role provider successfully validates the lender's credential and returns true. However, because the returned data size is less than 32 bytes, the _tryValidateCredential function incorrectly throws the InvalidCredentialReturned error, causing the transaction to revert.

## Fix

To fix this issue, the assumption about the minimum size of the returned data from the validateCredential function should be removed. Instead of checking the size of the returned data, the function should check if the call to the role provider was successful. Only if the call fails should the function revert. Here's how the _tryValidateCredential function can be modified:

```solidity
// AccessControlHooks.sol

function _tryValidateCredential(
    LenderStatus memory status,
    address accountAddress,
    bytes calldata hooksData
) internal returns (bool) {
    // ... Existing code ...

    assembly {
        // ... Existing code ...

        // Call the provider
        if call(
            gas(),
            providerAddress,
            0,
            add(calldataPointer, 0x1c),
            add(dataLength, 0x64),
            0,
            0x20 // Allocate 32 bytes for the return data
        ) {
            // If the call succeeded, assume the credential is valid.
            // The return data is ignored.

            // ... Existing code for updating LenderStatus ...

            return true;
        }

        // ... Existing code for handling a failed call ...
    }

    // ... Existing code ...
}
```
