# Vulnerability details

## Summary

The Wildcat protocol is designed as a decentralized lending platform governed by an ArchController contract that manages critical aspects of the system, including protocol fees and their distribution. While the protocol aims to be secure and transparent, a vulnerability exists where a malicious user could manipulate the fee structure to redirect protocol fees to their own address, effectively stealing funds that should rightfully belong to the intended fee recipient.

## Details:

The Wildcat protocol allows for collecting protocol fees on market activities, with the fee recipient specified during the market deployment process. The HooksFactory contract deploys new markets and sets up the initial fee configuration, including the protocolFeeBips, which determines the percentage of fees allocated to the protocol.

The pushProtocolFeeBipsUpdates function in the HooksFactory contract is intended to update the protocolFeeBips for a specific hooks template and propagate this change to all markets associated with that template. Notably, this function can be called by anyone, not just the ArchController owner.

The pushProtocolFeeBipsUpdates function does not verify if the caller is authorized to modify the protocol fee structure. This lack of access control creates a dangerous vulnerability.

## Impact

The impact of this vulnerability is severe, potentially leading to:

Theft of Protocol Fees: A malicious actor could call the pushProtocolFeeBipsUpdates function, providing an address they control as the new fee recipient. Since the function lacks ownership verification, the attacker could successfully redirect all protocol fees from the intended recipient to their own address, resulting in substantial financial losses for the rightful owner of the fees.

Compromised Market Integrity: This exploit undermines the integrity of the Wildcat protocol by allowing the manipulation of a fundamental financial aspect. Such a breach could erode trust in the platform and discourage participation from both borrowers and lenders.

## Scenario

A malicious user identifies the vulnerability in the pushProtocolFeeBipsUpdates function of the HooksFactory contract.

They craft a transaction calling this function, specifying a hooks template and providing their own address as the new fee recipient for all markets associated with that template.

Due to the absence of ownership or authorization checks, the transaction succeeds, and the attacker gains control over the flow of protocol fees, diverting them from the intended recipient to their own address.

## Fix

To rectify this vulnerability, the pushProtocolFeeBipsUpdates function must incorporate robust access control mechanisms to ensure that only authorized entities, such as the ArchController owner or a designated governance mechanism, can modify the protocol fee configuration.

Implement Access Control: Modify the pushProtocolFeeBipsUpdates function to include a modifier or check that verifies if the caller is the ArchController owner. For instance, the existing onlyArchControllerOwner modifier used in other parts of the HooksFactory contract could be applied.
