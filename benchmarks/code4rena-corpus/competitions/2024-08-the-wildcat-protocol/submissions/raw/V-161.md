# Vulnerability details

##Proof of Concept

Overview:

The AccessControlHooks contract is designed to enforce access controls on certain market actions like deposits and transfers, ensuring only authorized users can perform them. This is achieved by validating user credentials through role providers. However, there's a critical flaw in how the contract handles the hooksData provided by users during these actions.

Vulnerability Details:

Affected Function: _handleHooksData
Issue: The contract fails to properly validate the length and content of hooksData. If hooksData is empty or shorter than expected, the credential validation process is skipped, allowing unauthorized users to perform restricted actions.
Location in Code:

The vulnerability lies within the _handleHooksData function:

function _handleHooksData(
    LenderStatus memory status,
    address accountAddress,
    bytes calldata hooksData
) internal returns (bool validCredential) {
    // Checks if hooksData contains only a provider address
    if (hooksData.length == 20) {
        // Process hooksData as provider address
        // ...
    } else if (hooksData.length > 20) {
        // Process hooksData with additional credential data
        // ...
    }
    // If hooksData.length < 20, the function does nothing
}


Explanation:

The function checks if hooksData.length is exactly 20 bytes (the size of an address) or greater.
If hooksData.length is less than 20 bytes, the function does not perform any action or validation.
This lack of action means that if a user provides empty hooksData or hooksData shorter than 20 bytes, the contract skips credential validation entirely.
Impact:

An attacker can exploit this vulnerability to bypass the access controls enforced by the contract. By providing insufficient or empty hooksData, an unauthorized user can perform restricted actions such as deposits and transfers without possessing valid credentials.


Step-by-Step Exploitation:

Preparation:
Assume there's a market that uses AccessControlHooks and requires credentials for deposits and transfers.
The attacker does not possess valid credentials and is blocked from performing these actions under normal circumstances.
Crafting Malicious Input:
The attacker calls the onDeposit or onTransfer function of the market contract.
They provide empty hooksData (an empty bytes array) or hooksData shorter than 20 bytes.
Bypassing Validation:
Inside the AccessControlHooks contract, the _tryValidateAccess function is invoked.
_tryValidateAccess calls _tryValidateAccessInner, which in turn calls _handleHooksData.
Since hooksData.length < 20, _handleHooksData does nothing and returns without validating credentials.
The contract fails to set hasValidCredential to false explicitly.
Performing Unauthorized Action:
The attacker proceeds with the deposit or transfer action.
The contract does not enforce the NotApprovedLender error because it mistakenly considers the attacker as authorized.
The unauthorized action is successfully executed.

=> It seems that This vulnerability undermines the entire access control mechanism of the contract and it also allows unauthorized users to participate in restricted markets, potentially leading to financial loss or system abuse.

##Recommended Mitigation Steps

Ensure that hooksData is properly validated for expected length and content before proceeding.
Modify _handleHooksData to revert if hooksData is empty or too short.

In _tryValidateAccessInner, ensure that if no valid credential is found, hasValidCredential is set to false.
Explicitly handle cases where credential validation does not occur due to invalid hooksData.
