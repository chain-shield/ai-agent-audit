# Vulnerability details

## Description
The vulnerability stems from the direct transfer of tokens to the lender's address without any checks on whether the address is a contract or if it can receive tokens. This allows a malicious actor to create a contract that can queue withdrawals but intentionally fails when receiving tokens, disrupting the withdrawal process.

The attack vector involves an attacker creating multiple wallet addresses, each depositing a minimal amount of funds, and then initiating withdrawals that are designed to fail consistently. Due to the current implementation of the withdrawal process, these failing withdrawals remain in the queue and are repeatedly processed, potentially blocking or significantly delaying legitimate withdrawal requests.

The vulnerability arises from a combination of factors:
- Unlimited withdrawal queueing:
The `queueWithdrawal` function allows any address to queue an unlimited amount of withdrawals 
- Continued processing of failed withdrawals without any skip or deprioritization mechanism in `_processUnpaidWithdrawalBatch`
- Sequential processing of withdrawal batches
- Lack of minimum withdrawal amounts to prevent dust attacks
- Direct token transfer without checks:
In the `_executeWithdrawal` function, tokens are transferred directly to the recipient without checking if it's a contract or if it can receive tokens



An attacker could exploit this by:

Creating numerous wallet addresses
Depositing minimal amounts in each address
Initiating withdrawals from each address that are designed to fail (e.g., through a reverting receiver contract)
Using a bot to continuously queue these failing withdrawals

This could result in the protocol being forced to continually process a large number of failing withdrawals, potentially preventing or significantly delaying the processing of legitimate withdrawal requests.

## Impact
- Severe delays in processing legitimate user withdrawals, potentially rendering the withdrawal function unusable

- Increased gas costs for users and the protocol due to repeated processing of failing withdrawals

- Soft Lock on User Funds: The attacker can sustain this attack indefinitely, effectively imposing a soft lock on users' funds within the Wildcat market. This results in:
a) Indefinite Withdrawal Delays: Users are unable to execute withdrawals for an extended, potentially unlimited period.
b) Forced Illiquidity: While not stolen, users' funds become inaccessible, leading to potential financial losses or missed opportunities.
c) Dependence on External Resolution: The situation can only be resolved by the attacker ceasing the attack or through significant intervention by the borrower.
d) Trust Erosion: Prolonged inability to access funds may severely damage user confidence in the protocol.

- Degraded overall performance of the protocol due to constant processing of failing withdrawals



## Proof of Concept
1. Attacker creates a malicious smart contract (Let's call it "RevertingReceiver") with a receive() function that always reverts.

2. Attacker uses 10000 different addresses.

3. Attacker funds each address with a small amount of the market's underlying token (e.g., 0.01 USDC if the market uses USDC).

4. With a smart contract and using each address, the attacker deposits the funds into the Wildcat market.

5. For each address, the attacker queues a withdrawal for its full balance, setting the `RevertingReceiver` contract as the recipient address.

6. Attacker sets up a bot to continuously call the `executeWithdrawal` function on the Wildcat market for each of the 10000 addresses.

7. When the withdrawal for each address is processed:
- The market attempts to send tokens to the `RevertingReceiver` contract
- Each transfer fails because the `RevertingReceiver`'s `receive()` function reverts
- The failed withdrawals remain in the queue


8. The bot continues to trigger `executeWithdrawal` for each address, causing the market to repeatedly attempt (and fail) to process these withdrawals.

9. To demonstrate the impact, a legitimate user attempts to queue and process a withdrawal:

- The legitimate withdrawal is added to the queue behind or interspersed with the attacker's withdrawals
- When `executeWithdrawal` is called for the legitimate user, it may be delayed significantly due to the system attempting to process the failing withdrawals first


10. The attacker can sustain this attack by keeping their bot running and potentially creating more address over time, effectively preventing or severely delaying legitimate withdrawals indefinitely.

Results:

- The legitimate user's withdrawal remains unprocessed due to the large number of preceding failing withdrawals.
- Attempts to process withdrawals result in higher gas costs due to repeated failed transactions, and they continue to be delayed indefinitely.
- The market's withdrawal functionality is effectively paralyzed for most users.

This proof of concept more reflects the protocol's functions and the multi-address nature of the attack, demonstrating how an attacker can exploit the vulnerability to cause a denial of service in the withdrawal process across multiple addresses.

In fact, a more sophisticated attacker could do an improved attack by:

- Setting up a bot to observe the mempool
- Frontrun users that try to withdraw with thousands of failing withdrawals from thousands of different address
- Backlog the withdrawal system and delay/deny withdrawals indefinitely.
- This would increase the denial of service effect by an order of magnitude.

Note: even if users set the batches to 100 or more, the attacker can front run them and always make more failing withdrawal requests than how many requests are in the batches. This allows the attacker to continuously stay ahead of withdrawal processing attempts, effectively maintaining the denial of service condition.

## Recommended Mitigation Steps
Implement checks to determine if the recipient address is a contract and whether it can receive tokens before initiating the transfer.

Consider adopting a pull payment pattern for withdrawals instead of pushing tokens directly to recipients. This allows recipients to claim their tokens when they're ready to receive them.

Implement a try/catch mechanism around the token transfer to handle failed transfers gracefully without disrupting the entire withdrawal process.

Introduce a limit on the number of pending withdrawals per unique address to prevent a single actor from flooding the system with withdrawal requests.

Implement a mechanism to skip or deprioritize consistently failing withdrawals. After a certain number of failed attempts, move the withdrawal to a separate queue that is processed less frequently.

Add a cooldown period for addresses with failed withdrawal attempts to prevent rapid re-queueing of failed withdrawals.
