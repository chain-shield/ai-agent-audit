# Vulnerability details

## Summary
The vulnerability exists in the `onDeposit`, `onBorrow` and the other 9 affected functions in the HookConfig.sol contract due to improper handling of calldata underflow. The function calculates the size of `extraCalldata` using the expression `let extraCalldataBytes := sub(calldatasize(), DepositCalldataSize)` with the assumption that `calldatasize()` would always return a value greater or equal to the `DepositCalldataSize`. However, if the call data size is smaller than the expected DepositCalldataSize, this calculation underflows leading to a very large value for `extraCalldataBytes` (since the result would be negative and solidity assembly treats integers as unsigned by default and hence a negative number would wrap around to a very large positive number - close to $2^{256}-1$. This would cause out-of-bounds memory corruption.

## Impact
The impact is severe and could have a chain effect including the following:
**1. Memory corruption:** The attacker can corrupt memory by causing the contract to copy an excessive amount of calldata to memory.
```solidity
// Copy `extraData` from end of calldata to hook calldata
        calldatacopy(
          add(headPointer, DepositHook_ExtraData_TailOffset),
          DepositCalldataSize,
          extraCalldataBytes
        )
```

**2. Denial-of-Service:** The underflow could lead to a situation where an extremely large size of data is requested to be copied into memory using calldatacopy. This could cause the contract to run out of gas before completing, effectively resulting in a Denial of Service (DoS). The attacker could repeatedly trigger this condition, blocking other users from interacting with the contract.

**3. Griefing Attack (for functions like `onSetAnnualInterestAndReserveRatioBips`):** An attacker could deliberately craft a malicious calldata that triggers the underflow and causes the function to revert. This would block legitimate calls to onSetAnnualInterestAndReserveRatioBips, resulting in a denial of service for users attempting to set new interest or reserve ratio values.

**4. Reentrancy Attacks:** By corrupting memory, attackers could manipulate external calls, potentially reentering the contract during execution and exploiting it in an inconsistent state, leading to fund theft or bypassing logic.

## Proof of Concept
Vulnerable Code Snippet:
```solidity
function onDeposit(
    HooksConfig self,
    address lender,
    uint256 scaledAmount,
    MarketState memory state
) internal {
    address target = self.hooksAddress();
    uint32 onDepositSelector = uint32(IHooks.onDeposit.selector);
    if (self.useOnDeposit()) {
      assembly {
        let extraCalldataBytes := sub(calldatasize(), DepositCalldataSize)
        // Memory manipulation begins here
        let cdPointer := mload(0x40)
        let headPointer := add(cdPointer, 0x20)
        // Write selector for `onDeposit`
        mstore(cdPointer, onDepositSelector)
        // Other calldata writes...
        // Copy `extraData` from end of calldata to hook calldata
        calldatacopy(
          add(headPointer, DepositHook_ExtraData_TailOffset),
          DepositCalldataSize,
          extraCalldataBytes
        )
        // Memory corruption occurs here due to underflow in `extraCalldataBytes`
        let size := add(DepositHook_Base_Size, extraCalldataBytes)
        // External call to the target address with corrupted calldata
        if iszero(call(gas(), target, 0, add(cdPointer, 0x1c), size, 0, 0)) {
          returndatacopy(0, 0, returndatasize())
          revert(0, returndatasize())
        }
      }
    }
}
```
#### Steps to Reproduce:
1. An attacker crafts a malicious transaction that passes less calldata than the expected DepositCalldataSize.
2. The subtraction calldatasize() - DepositCalldataSize will underflow, leading to a very large value for extraCalldataBytes.
3. The contract will attempt to copy an excessive amount of data into memory, causing memory corruption.
4. The corrupted memory could then lead to Denial of Service, Reentrancy risk, fund theft, or arbitrary code execution.

## Tools Used
Visual Studio Code, Manual review.

## Recommended Mitigation Steps
1. Validate Calldata size so that `calldatasize()` is at least as large as `DeposoitCalldataSize` before performing any operations with calldata. Add the following line:
```solidity
if lt(calldatasize(), DepositCalldataSize) {
    revert("Invalid calldata size");
}
```
2. Pre-Check Memory Allocation Size:
```solidity
uint256 maxAllowedSize = 1024; // Example: 1 KB limit on extra calldata

// Ensure extraCalldataBytes does not exceed the max allowed size
if (extraCalldataBytes > maxAllowedSize) {
    revert("Excessive memory allocation");
}
```
