# Vulnerability details

## Proof of Concept
The `WildcatSanctionsEscrow` contract initializes the `borrower`, `account`, and `asset` addresses in its constructor by calling the `tmpEscrowParams()` function from the `IWildcatSanctionsSentinel` interface. However, the contract does not perform any validation checks on the values returned by this function. This can lead to the contract being deployed with zero or invalid addresses,causing the contract to malfunction or become unusable.

### Code Reference
Let's look at the [constructor](https://github.com/code-423n4/2024-08-wildcat/blob/fe746cc0fbedc4447a981a50e6ba4c95f98b9fe1/src/WildcatSanctionsEscrow.sol#L17-L20) in the `WildcatSanctionsEscrow` contract:

```solidity
constructor() {
    sentinel = msg.sender;
    (borrower, account, asset) = IWildcatSanctionsSentinel(sentinel).tmpEscrowParams();
}
```

### Potential Impact
If `tmpEscrowParams()` returns zero addresses, the contract may fail to execute functions that rely on these addresses, such as transferring assets. Also, if the addresses do not correspond to the intended entities, the contract logic may operate incorrectly, leading to potential security vulnerabilities or loss of funds.

## Recommended Mitigation Steps
 Modify the constructor to include checks that ensure `borrower`, `account`, and `asset` are not zero addresses. This can be done using `require` statements.

   ```solidity
   constructor() {
       sentinel = msg.sender;
       (borrower, account, asset) = IWildcatSanctionsSentinel(sentinel).tmpEscrowParams();

       require(borrower != address(0), "Invalid borrower address");
       require(account != address(0), "Invalid account address");
       require(asset != address(0), "Invalid asset address");
   }
   ```
