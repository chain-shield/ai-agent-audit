# Vulnerability details

## Description
The `WildcatMarketBase` contract fails to properly reduce its asset balance when processing withdrawals, resulting in the retention of excess assets. Additionally, the contract credits users with interest without correspondingly increasing its actual asset holdings. This creates a significant discrepancy between the reported user balances (including accrued interest) and the actual assets held by the contract.

The root causes of this vulnerability are:
In `WildcatMarketBase.sol`, the `_applyWithdrawalBatchPayment` function updates internal accounting but doesn't actually transfer or reduce the contract's asset balance. This causes the improper withdrawal processing.

In `WildcatMarketBase.sol`, the `_getUpdatedState` function updates the `scaleFactor` (which affects all balances) without increasing the actual asset balance of the contract. This leads to the unbacked interest accrual.

These issues create a significant discrepancy between the reported user balances (including accrued interest) and the actual assets held by the contract. The test demonstrates this(Check PoC) by showing a large difference between the total supply and the actual asset balance after interest accrual and withdrawal operations.

## Impact
- Insolvency Risk: The contract operates with more liabilities (user balances including interest) than assets, making it technically insolvent.

- Withdrawal Failures: Later withdrawals will fail due to insufficient actual assets, even when user balances suggest funds should be available.

Potential for Bank Run: The discrepancy between reported balances and actual assets creates a risk of triggering a bank run:
1. Users may rush to withdraw funds upon realizing the discrepancy.
2. This can quickly deplete the contract's liquidity.
3. Later withdrawals may become difficult or impossible to process.
4. The mere perception of this risk can be enough to trigger such a run.

## Proof of Concept
Add the following test to `WildcatMarket.t.sol`.
```javascript
// SPDX-License-Identifier: Apache-2.0
pragma solidity >=0.8.20;

import "../BaseMarketTest.sol";
import "src/interfaces/IMarketEventsAndErrors.sol";
import "src/libraries/MathUtils.sol";
import "src/libraries/SafeCastLib.sol";
import "src/libraries/MarketState.sol";
import "src/libraries/LibERC20.sol";
import "solady/utils/LibPRNG.sol";
import "forge-std/console.sol";
import "../../src/market/WildcatMarketWithdrawals.sol";

contract WildcatMarketTest is BaseMarketTest {
    using MathUtils for int256;
    using MathUtils for uint256;
    using SafeCastLib for uint256;
    using LibPRNG for LibPRNG.PRNG;

    function testMarketRetainsExcessAssetsAndCreditsUnbackedInterest() public {
        // Deploy market and set up initial state
        deployMarket(parameters);
        _authorizeLender(alice);
        _authorizeLender(bob);

        // Initial deposit
        uint256 initialDeposit = 100000e18;
        deal(address(asset), address(alice), initialDeposit);
        vm.prank(alice);
        asset.approve(address(market), initialDeposit);
        vm.prank(alice);
        market.depositUpTo(initialDeposit);

        // Record initial state
        uint256 initialMarketBalance = asset.balanceOf(address(market));
        uint256 initialAliceBalance = market.balanceOf(alice);

        // Perform a withdrawal
        uint256 withdrawalAmount = 50000e18;
        vm.prank(alice);
        market.queueWithdrawal(withdrawalAmount);

        // Fast forward to batch expiry and process the withdrawal
        vm.warp(block.timestamp + market.withdrawalBatchDuration() + 1);
        vm.prank(borrower);
        market.updateState();

        // Check market's asset balance after withdrawal
        uint256 expectedMarketBalance = initialMarketBalance - withdrawalAmount;
        uint256 actualMarketBalance = asset.balanceOf(address(market));
        assertEq(
            actualMarketBalance, initialMarketBalance, "Market balance should decrease after withdrawal, but it didn't"
        );
        assertGt(
            actualMarketBalance,
            expectedMarketBalance,
            "Market is retaining more assets than it should after withdrawal"
        );

        // Fast forward time to accrue interest
        vm.warp(block.timestamp + 365 days);

        // Update market state to apply interest
        vm.prank(borrower);
        market.updateState();

        // Check Alice's balance after interest accrual
        uint256 aliceBalanceAfterInterest = market.balanceOf(alice);
        assertGt(
            aliceBalanceAfterInterest,
            initialAliceBalance - withdrawalAmount,
            "Alice's balance should reflect interest accrual"
        );

        // Check if the market's asset balance increased to match the interest accrual
        uint256 marketBalanceAfterInterest = asset.balanceOf(address(market));
        assertEq(
            marketBalanceAfterInterest,
            actualMarketBalance,
            "Market's asset balance should increase with interest, but it didn't"
        );

        // Attempt to withdraw all funds to demonstrate the discrepancy
        uint256 totalSupply = market.totalSupply();
        vm.prank(alice);
        market.queueWithdrawal(aliceBalanceAfterInterest);

        // Fast forward and process the withdrawal
        vm.warp(block.timestamp + market.withdrawalBatchDuration() + 1);
        vm.prank(borrower);
        market.updateState();

        // Try to withdraw Bob's funds (which should fail due to insufficient actual assets)
        uint256 bobDepositAmount = 1e18;
        deal(address(asset), address(bob), bobDepositAmount);
        vm.prank(bob);
        asset.approve(address(market), bobDepositAmount);
        vm.prank(bob);
        market.depositUpTo(bobDepositAmount);

        vm.prank(bob);
        market.queueWithdrawal(bobDepositAmount);

        // Fast forward and attempt to process Bob's withdrawal
        vm.warp(block.timestamp + market.withdrawalBatchDuration() + 1);
        vm.prank(borrower);
        market.updateState();

        // Attempt to execute Bob's withdrawal
        uint32 expiry = uint32(block.timestamp - (block.timestamp % market.withdrawalBatchDuration()));
        vm.expectRevert(); // This should revert due to insufficient funds
        vm.prank(bob);
        market.executeWithdrawal(bob, expiry);

        // Log final state for clarity
        console.log("Initial market balance:", initialMarketBalance);
        console.log("Final market balance:", asset.balanceOf(address(market)));
        console.log("Total supply (including interest):", totalSupply);
        console.log("Actual asset balance:", asset.balanceOf(address(market)));
    }
}
```

The Vulnerability:
The vulnerability consists of two main components:
Improper Withdrawal Processing:
The contract fails to correctly reduce its asset balance when users withdraw funds. This results in the contract retaining more assets than it should, creating a discrepancy between the reported user balances and the actual assets held by the contract.

Unbacked Interest Accrual:
The contract is crediting users with interest (as seen in the increased total supply) without actually increasing its asset holdings to match this interest. This creates a situation where the contract is promising more value to users than it actually holds.

## Recommended Mitigation Steps
Update Withdrawal Logic: Modify the `_applyWithdrawalBatchPayment` function in `WildcatMarketBase.sol` to correctly transfer and reduce the contract's asset balance when processing withdrawals. Ensure that the `totalAssets()` function accurately reflects the contract's holdings.

Align Interest Accrual with Asset Growth:
Modify the interest accrual mechanism in `_getUpdatedState` to only accrue interest based on actual asset growth. This prevents the creation of unbacked interest.

Implement Actual Balance Tracking:
Introduce a new variable to track the actual asset balance of the contract. Update this balance in all functions that affect the contract's assets.

Regular Reconciliation Checks:
Implement a function to regularly check and reconcile the contract's internal state with its actual asset balance. This can be called periodically or before critical operations.
