# Vulnerability details

## Description
The Wildcat protocol's withdrawal mechanism is vulnerable to a potential Denial of Service (DoS) attack through the exploitation of dust withdrawals. An attacker could flood the system with numerous small (dust) withdrawal requests. This attack vector takes advantage of the sequential processing of withdrawal batches in the `repayAndProcessUnpaidWithdrawalBatches` function.

The vulnerability arises from the following factors:

- There is no built-in minimum withdrawal amount in the core contract.
- Withdrawal batches are processed in a first-in-first-out (FIFO) order.
- The `repayAndProcessUnpaidWithdrawalBatches` function processes a limited number of batches per call, defined by the `maxBatches` parameter.

An attacker could create a very large number of dust withdrawal requests, filling up the withdrawal queue. This would force legitimate users' withdrawal requests to be processed only after the attacker's numerous small withdrawals, potentially causing significant delays or making withdrawals prohibitively expensive due to increased gas costs.

## Impact
- Denial of Service: Legitimate users may experience significant delays in processing their withdrawal requests, effectively denying them timely access to their funds. Especially since an attacker can continue to spam dust withdrawals indefinitely. 

- Increased Gas Costs: Users attempting to process withdrawals may face prohibitively high gas costs due to the need to process a large number of preceding dust withdrawals.

- Reduced Protocol Efficiency: The overall efficiency and usability of the market could be significantly impaired, potentially leading to a loss of user trust and engagement.

- Approaching Gas Limits: While the `maxBatches` parameter prevents directly hitting the block gas limit, processing a large number of dust withdrawals could push transactions close to practical gas limits on some networks. This could result in:
a) Transactions failing due to out-of-gas errors if not carefully parameterized.
b) Increased difficulty in including other complex operations in the same block.
c) Potential network congestion if multiple users attempt to process large batches simultaneously.

- Soft Lock on User Funds: The attacker can sustain this attack indefinitely, effectively imposing a soft lock on users' funds within the Wildcat market. This results in:
a) Indefinite Withdrawal Delays: Users are unable to execute withdrawals for an extended, potentially unlimited period.
b) Forced Illiquidity: While not stolen, users' funds become inaccessible, leading to potential financial losses or missed opportunities.
c) Dependence on External Resolution: The situation can only be resolved by the attacker ceasing the attack or through significant intervention by the borrower.
d) Trust Erosion: Prolonged inability to access funds may severely damage user confidence in the protocol.

## Proof of Concept

This proof of concept demonstrates how an attacker can exploit the withdrawal mechanism in the Wildcat protocol to cause a denial of service condition. 

Prerequisites:
A deployed Wildcat market with the following parameters:

- Asset: USDC
- Capacity: 1,000,000 USDC
- Annual Interest Rate: 5%
- Reserve Ratio: 10%
- Withdrawal Batch Duration: 24 hours


- An attacker account with 100 USDC
- A legitimate user account with 10,000 USDC
- The market has 100,000 USDC in liquidity

Step 1: Set up the attack
- The attacker deposits 100 USDC into the Wildcat market using the deposit function.
- The legitimate user deposits 10,000 USDC into the same market using the deposit function.

Step 2: Execute the attack
- The attacker creates a script that repeatedly calls the `queueWithdrawal` function with dust amounts (e.g., 0.0001 USDC).

- This script can run continuously, creating new withdrawal requests as fast as the network can process the transactions.
- Each call to `queueWithdrawal` will:
a. Add the withdrawal request to the current batch if one exists and hasn't expired.
b. Create a new batch and add the withdrawal to it if no current batch exists or if the existing one has expired.
- The attacker can run this script indefinitely, constantly adding new dust withdrawal requests to the system.
- As batches expire new batches are immediately created and filled with more dust withdrawals.

Step 3: Demonstrate the impact
-  The legitimate user attempts to withdraw 5,000 USDC by calling `queueWithdrawal`.
- This processes only a fraction of the attacker's withdrawals and doesn't reach the legitimate user's withdrawal.
- The legitimate user increases `maxBatches` to 100 and tries `repayAndProcessUnpaidWithdrawalBatches` again.
- This transaction either fails due to hitting the gas limit or costs an extremely high gas cost or continues to fail because this processes only a fraction of the attacker's withdrawals and doesn't reach the legitimate user's withdrawal.

Step 4: Demonstrate sustained attack

- While the legitimate user is attempting to process withdrawals, the attacker continues to queue small withdrawals, ensuring there's always a backlog of withdrawal requests.
- This creates a continuous cycle of expired batches filled with dust withdrawals, making it increasingly difficult for legitimate users to process their withdrawals.

Results:

- The legitimate user's withdrawal remains unprocessed due to the large number of preceding dust withdrawals.
- Attempts to process withdrawals result in extremely high gas costs or failed transactions due to gas limits or they continue to be delayed indefinitely.
- The market's withdrawal functionality is effectively paralyzed for most users.
- The borrower may need to intervene by repaying a significant amount to the market to process the backlog of withdrawals, or by closing the market entirely.

This PoC demonstrates how an attacker can exploit the batch withdrawal mechanism to cause a denial of service condition, making it difficult and expensive for legitimate users to process their withdrawals. 

In fact, a more sophisticated attacker could do an improved attack by:
- Setting up a bot to observe the mempool 
- Frontrun users that try to withdraw with thousands of dust withdrawals 
- Backlog the withdrawal system and delay/deny withdrawals indefinitely. 
- This would increase the denial of service effect by an order of magnitude.

Note: even if users set the batches to 100 or more, the attacker can front run them and always make more dust withdrawal requests than how many requests are in the batches. This allows the attacker to continuously stay ahead of withdrawal processing attempts, effectively maintaining the denial of service condition.

## Recommended Mitigation Steps
- Implement Minimum Withdrawal Amounts: Introduce a protocol-level minimum withdrawal amount. This could be a configurable parameter set by the borrower, with a reasonable default value to prevent dust withdrawals.

- Batch Consolidation: Implement a mechanism to consolidate multiple small withdrawals from the same address into a single batch entry. This would reduce the effectiveness of spam attacks while still allowing legitimate small withdrawals.

- Progressive Throttling: Introduce a system that imposes a cooldown period for addresses that make frequent small withdrawals. This would make sustained attacks more difficult without significantly impacting normal users.
