# Vulnerability details

Vulnerability Overview

The functions overrideSanction() and removeSanctionOverride() in the WildcatSanctionsSentinel contract allow borrowers to change the sanction status of accounts. These functions deal with sanction overrides, a sensitive area of the contract because they control whether a specific account can bypass Chainalysis sanctions.

However, there is no access control mechanism restricting who can call these functions, allowing any borrower to override sanctions for any account. This can lead to a privilege escalation issue, where unauthorized or malicious borrowers can misuse these functions, causing significant damage to the protocol's integrity and security.
Vulnerable Code

solidity

function overrideSanction(address account) public override {
    sanctionOverrides[msg.sender][account] = true;
    emit SanctionOverride(msg.sender, account);
}

function removeSanctionOverride(address account) public override {
    sanctionOverrides[msg.sender][account] = false;
    emit SanctionOverrideRemoved(msg.sender, account);
}

Bug Details

    Functionality: The above code allows anyone who calls the function (via msg.sender) to add or remove sanction overrides for any account.
    Risk: There are no restrictions on who can call these functions, allowing unauthorized entities to change the sanction status arbitrarily.
    Lack of Access Control: Neither of these functions implements proper access control. This opens the contract to abuse from malicious or unauthorized borrowers, who can override sanctions or remove overrides without any verification process.

Impact
Severity: High

The vulnerability is categorized as High Severity because of the following reasons:

    Critical Misuse Potential: Anyone who interacts with the contract as a borrower can remove the sanctions placed on their account, thereby circumventing critical compliance measures. This allows bypassing real-world sanctions checks (such as those from Chainalysis).
    Regulatory Violations: Bypassing sanctions can expose the protocol to legal and compliance risks. Allowing sanctioned addresses to interact freely can result in the protocol being in violation of financial regulations, which could trigger penalties or legal actions.
    Financial Risk: Malicious actors could use this exploit to launder money or engage in illegal activities by overriding sanction statuses. This undermines the entire security model of the protocol.

Exploit Scenario
Steps for Exploitation:

    Attacker’s Setup:
        The attacker is a borrower who has been sanctioned by Chainalysis, preventing them from participating in the protocol.
    Call the overrideSanction() function:
        The attacker simply calls the overrideSanction() function to override their sanction status, as there are no checks in place:

    solidity

    WildcatSanctionsSentinel.overrideSanction(address(attackerAccount));

    Outcome:
        The attacker is now able to freely bypass sanctions and interact with the protocol.
    Further Exploitation:
        The attacker could onboard multiple sanctioned accounts, repeatedly use the override function, or remove sanctions from critical participants like escrow contracts. This could lead to large-scale abuse.

Proof of Concept (PoC)

Here’s an example of how an attacker would exploit this vulnerability:

solidity

// Assume attacker is a borrower, attempting to override their sanction status
contract Exploit {
    WildcatSanctionsSentinel wildcat;

    constructor(address wildcatAddress) {
        wildcat = WildcatSanctionsSentinel(wildcatAddress);
    }

    function exploitSanctionOverride(address attackerAccount) public {
        // Bypass sanctions by calling overrideSanction
        wildcat.overrideSanction(attackerAccount);
    }
}

Mitigation

To mitigate this issue, access control should be enforced on the overrideSanction() and removeSanctionOverride() functions. Only authorized users, such as admins or verified contract roles, should have the power to override or remove sanction statuses.
