# Vulnerability details

## Description
The `executeWithdrawals` function in the `WildcatMarketWithdrawals` contract contains an unbounded loop that iterates over an array of account addresses and their corresponding expiries. This function processes multiple withdrawals in a single transaction, updating the market state and executing individual withdrawals for each account.

The core issue lies in the fact that there's no limit to the number of withdrawals that can be processed in a single call. As the number of accounts increases, the gas consumption of this function grows linearly. This design could lead to transactions that exceed the block gas limit(especially by attackers), causing them to fail and potentially rendering the function unusable for large batches of withdrawals.

## Impact
Denial of Service: Large batches of withdrawals could consistently fail due to exceeding the block gas limit, effectively causing a denial of service for users attempting to process multiple withdrawals at once.

Protocol Inefficiency: The protocol's ability to handle bulk operations is compromised, potentially limiting its scalability and efficiency in handling large-scale withdrawal scenarios.

Increased Transaction Costs: Users attempting to process large batches of withdrawals may face higher gas costs, as the function's gas consumption grows linearly with the number of withdrawals. This could make the withdrawal process prohibitively expensive for some users.


## Proof of Concept
Dust Withdrawal Spam Attack

This proof of concept demonstrates how an attacker could potentially render the `executeWithdrawals` function unusable by spamming the network with many dust withdrawals and withdrawals that revert on purpose.

Setup:

The attacker creates multiple accounts (e.g., 10000 accounts) using a script or bot.

Each account deposits a small amount of funds into the Wildcat market. (e.g. 0.001 USDC)

1. Attack Execution:

a) The attacker uses each account to queue a withdrawal for the full deposited amount.

b) After queuing all withdrawals, the attacker prepares two arrays: `accountAddresses` and `expiries`, containing the addresses and expiry timestamps for all the dust withdrawals.

c) The attacker calls the `executeWithdrawals` function with these large arrays, intentionally including more withdrawals than can be processed within the block gas limit.

2. Observation:

a) The `executeWithdrawals` transaction fails due to exceeding the block gas limit.

b) The function is now effectively blocked for large batches of withdrawals, as any attempt to process all pending withdrawals in one transaction will fail.

c) Legitimate users attempting to use `executeWithdrawals` for multiple accounts or large batches find their transactions failing due to out-of-gas errors.

3. Impact:

a) The `executeWithdrawals` function becomes unusable for processing large batches of withdrawals.

b) Users are forced to process withdrawals individually, increasing gas costs and complexity.

c) The overall efficiency of the withdrawal process in the Wildcat protocol is significantly reduced.

4. Mitigation Attempt:

a) A user attempts to clear the spam withdrawals by calling `executeWithdrawals` with smaller batches.

b) However the attacker is frontrunning attempts to clear the spam but creating more and more withdrawals.


This proof of concept demonstrates how an attacker could exploit the unbounded nature of the `executeWithdrawals` function to create a denial of service condition for batch withdrawals. It highlights the need for implementing protective measures such as a maximum limit on the number of withdrawals that can be processed in a single transaction.

## Recommended Mitigation Steps
- Implement a maximum batch size:
Add a constant `MAX_BATCH_SIZE` and modify the function to revert if the input arrays exceed this size. This ensures that gas consumption remains within predictable limits.

- Implement a pagination mechanism:
Modify the function to process a fixed number of withdrawals per transaction, allowing users to process large batches over multiple transactions.
