# Vulnerability details

## Proof of Concept
In the `HooksFactory` contract, the `_deployMarket` function uses `LibStoredInitCode` to deploy new markets via the `CREATE2` opcode. The potential vulnerability lies in how the market address is calculated and how the stored initialization code is reused, which can result in address collision and the deployment of stale contract logic.

1. Market Address Calculation Using CREATE2:
The market address is calculated using the `calculateCreate2Address` function from `LibStoredInitCode`:
```solidity
market = LibStoredInitCode.calculateCreate2Address(ownCreate2Prefix, salt, marketInitCodeHash);
```
This function computes the address based on three key inputs:
- `ownCreate2Prefix`: A unique prefix from the calling contract.
- `salt`: A value controlled by the caller, which must include the sender's address or be zero.
- `marketInitCodeHash`: A hash of the market initialization code stored in `marketInitCodeStorage`.
While this calculation is deterministic, it depends heavily on the salt and stored init code. If the salt is not unique per deployment or if stale init code is used, markets could deploy at the same address or with outdated logic.
2. Re-use of Stored Initialization Code:
The actual deployment of the market happens with the `create2WithStoredInitCode` function:
```solidity
LibStoredInitCode.create2WithStoredInitCode(marketInitCodeStorage, salt);
```
This function takes the stored initialization code (`marketInitCodeStorage`) and the salt to deploy the contract. The issue arises if `marketInitCodeStorage` contains stale or previously-used initialization code that was not updated between deployments. This leads to the creation of a market with incorrect parameters or logic, depending on the stale init code. Since the same init code can be re-used if not refreshed, the wrong contract logic can be deployed at an expected address.
3. Salt Validation and Address Collision Risk:
There is an attempt to ensure that the `salt` contains the sender’s address:
```solidity
if (!(address(bytes20(salt)) == msg.sender || bytes20(salt) == bytes20(0))) {
  revert SaltDoesNotContainSender();
}
```
This check guarantees that either the salt contains the sender's address or the salt is zero. However, this mechanism alone does not guarantee uniqueness of the salt across all market deployments. If the same salt is used multiple times (intentionally or unintentionally), different market deployments could result in the same computed address.
4. Existing Market Check:
There is a check to prevent the deployment of a market to an address that already contains contract code:
```solidity
if (market.code.length != 0) {
  revert MarketAlreadyExists();
}
```
While this prevents deploying a new market to an existing address, it doesn’t address the possibility of the wrong initialization code being used for the new deployment. If stale code is deployed, this check will not catch the issue since the contract will deploy correctly but with the wrong logic.
## Impact
The primary impact of this vulnerability is the potential deployment of a market contract with stale or incorrect logic. If the stored initialization code is reused without being updated, it could result in deploying a market that does not behave as expected or that contains outdated parameters. Additionally, using the same salt across deployments can lead to address collisions, causing markets to be deployed at the same address, which could overwrite or conflict with existing markets.

## Recommended Mitigation Steps
The stored initialization code (`marketInitCodeStorage`) must be refreshed before each deployment to reflect the correct logic and parameters. Clear the previous code after deployment and store the new initialization code for subsequent deployments. Also, before deploying each market, incorporate a mechanism that generates a unique salt for every deployment. This can be done by including a nonce or timestamp in the salt, ensuring it is never reused.
