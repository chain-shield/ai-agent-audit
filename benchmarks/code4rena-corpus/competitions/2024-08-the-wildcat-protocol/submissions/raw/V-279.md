# Vulnerability details

## Vulnerability Description: 

In the function `calculateCreate2Address` within the `LibStoredInitCode` library, the `create2Prefix, salt, and initCodeHash` are written to memory addresses that fall within the `reserved scratch space` (specifically 0x00 to 0x3f), which the EVM typically uses for hashing operations such as keccak256. This creates a risk of memory corruption if the same memory range is used during the hash operation.

## Impact: 

Since the EVM uses the memory range 0x00 to 0x3f as scratch space during operations like keccak256, the current usage of these memory slots for storing the create2Prefix and salt may lead to memory overwriting or incorrect behavior when calculating the hash. This can result in an incorrect keccak256 hash, potentially breaking the contract logic and creating unexpected results.

## Proof of Concept (PoC): 

In the calculateCreate2Address function:

```solidity
assembly {
    mstore(0x00, create2Prefix)  // Store create2Prefix at 0x00
    mstore(0x20, salt)  // Store salt at 0x20
    mstore(0x40, initCodeHash)  // Store initCodeHash at 0x40 (outside the scratch space)
    create2Address := and(keccak256(0x0b, 0x55), 0xffffffffffffffffffffffffffffffffffffffff)
}
```

The issue arises because `mstore` uses memory addresses 0x00 and 0x20, which are within the EVM's reserved scratch space. When the keccak256 function is called, it may use the same scratch space, leading to a potential overwrite and hash corruption.

## Recommended Fix: 

To avoid the risk of memory corruption, the storage locations for create2Prefix, salt, and initCodeHash should be shifted to a safer memory location outside the EVM’s reserved scratch space. For example, you can start storing the values at 0x60 to avoid interference with the EVM's scratch space:

```solidity
assembly {
    mstore(0x60, create2Prefix)  // Store create2Prefix at 0x60
    mstore(0x80, salt)  // Store salt at 0x80
    mstore(0xa0, initCodeHash)  // Store initCodeHash at 0xa0
    create2Address := and(keccak256(0x60, 0x55), 0xffffffffffffffffffffffffffffffffffffffff)
}
```

This ensures that the scratch space is preserved for EVM operations and avoids any potential conflicts. Once the operations are done you can reset original values on these memory slots (need to cache the original values before using them for this transaction).
