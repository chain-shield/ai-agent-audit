# Vulnerability details

## Summary

The `LibStoredInitCode` library’s `create2WithStoredInitCode` and `create2WithStoredInitCodeCD` functions improperly handle constructor arguments during contract deployment. This vulnerability can result in contracts not being initialized correctly, potentially leading to critical security flaws such as unauthorized access, broken logic, or even complete denial of service (DoS) if initialization is essential for the contract’s functionality.

## Impact

The vulnerability occurs when the library incorrectly passes constructor arguments during contract deployment, which can cause the following:

- **Uninitialized Contracts**: Contracts may not receive the expected initialization data, leading to critical contract components not being set, such as access control roles, token settings, or initial state variables.
- **Security Risks**: Improper initialization could allow attackers to exploit the contract due to uninitialized or incorrectly initialized states. This could include unauthorized access to privileged functions or modification of important state variables.
- **Logic Bugs**: Contracts could behave in unintended ways due to missing or malformed initialization data. This could lead to errors in financial operations, token transfers, or critical protocol functions.
- **Denial of Service (DoS)**: Contracts relying on correct initialization for essential functions may not operate at all, causing DoS situations for protocols or applications.



## Proof of Concept
The vulnerability lies in the `create2WithStoredInitCode` function's handling of constructor arguments. Specifically, the contract’s constructor might receive malformed or incomplete data, leading to incorrect initialization.

Example:

1. Deploy a contract using `create2WithStoredInitCode` that requires specific constructor arguments:

```solidity
bytes memory constructorArgs = abi.encode(0x1234); // Incorrectly encoded constructor arguments
address newContract = LibStoredInitCode.create2WithStoredInitCode(
initCodeStorage,
salt,
0,
constructorArgs // This argument will be improperly passed to the constructor
);
```

2. The constructor receives improperly formatted arguments, leading to:

- **Constructor not receiving the full set of arguments**.
- **Constructor receiving malformed or truncated data**.
- **Contract being deployed in an uninitialized or incorrect state**.

**Example Test Case**:

```solidity
contract VulnerableContract {
uint256 public importantValue;

constructor(uint256 _importantValue) {
require(_importantValue > 0, "Invalid value");
importantValue = _importantValue;
}
}
```

By deploying this contract via the vulnerable function with incorrect arguments, the `importantValue` might not be set, potentially allowing an attacker to exploit the contract’s logic or render it unusable.

## Recommended Mitigation Steps

#### 1. **Ensure Proper Memory Allocation**:
Before copying the constructor arguments, ensure that memory is properly allocated for both the code and constructor arguments to avoid truncation or misplacement of data.

#### 2. **Add Validation Checks**:
Implement checks to verify that the constructor arguments are properly copied and formatted before deployment. This can prevent the constructor from receiving malformed or incomplete arguments.

#### 3. **Improved Handling of Constructor Arguments**:
Modify the assembly logic to ensure that constructor arguments are appended correctly and that no data is lost or incorrectly formatted when passed to the `create2` opcode.

```solidity
// Modify assembly code to properly handle constructorArgs
let constructorArgsSize := mload(constructorArgs)
if iszero(constructorArgsSize) {
revert(0x00, 0x00) // Fail if constructor arguments are malformed or missing
}
mcopy(add(initCodePointer, initCodeSize), add(constructorArgs, 0x20), constructorArgsSize)
```
