# Vulnerability details

## Proof of Concept
The `_onCreateMarket` function is designed to configure various hooks, including `onQueueWithdrawal`, based on the borrower's provided configuration. According to the documentation, the `onQueueWithdrawal` hook should always be enabled but require access only if the borrower's configuration has `useOnQueueWithdrawal` set to true. However, in the current implementation, the hook is conditionally enabled or disabled depending on the value of `config.useOnQueueWithdrawal`, rather than being always enabled.

Here’s the code segment that highlights the issue:
```solidity
 HookedMarket memory hookedMarket = HookedMarket({
      isHooked: true,
      transferRequiresAccess: marketHooksConfig.useOnTransfer(),
      depositRequiresAccess: marketHooksConfig.useOnDeposit(),
      minimumDeposit: minimumDeposit.toUint128()
    });

    if (marketHooksConfig.useOnQueueWithdrawal()) {
      marketHooksConfig = marketHooksConfig.setFlag(Bit_Enabled_Transfer).setFlag(
        Bit_Enabled_Deposit
      );
}
```
In this implementation, the `onQueueWithdrawal` hook is entirely disabled if the `useOnQueueWithdrawal` flag is `false`. This contradicts the intent that the hook should always be enabled but only require access control when `useOnQueueWithdrawal` is `true`.
The original intent outlined in the documentation is that all markets should have the `onQueueWithdrawal` hook enabled, ensuring that a standard check or process is consistently applied across all markets. This would create a uniform experience where the hook is always present, although it might only require certain permissions or access control based on the borrower's configuration.

However, in the current implementation, the hook can be completely disabled if the borrower chooses not to enable `useOnQueueWithdrawal` in the configuration. This makes the handling of withdrawals vary across markets: some markets will have the `onQueueWithdrawal` hook active, while others will not.
By making the hook optional, markets that don’t enable it might miss out on important safeguards or custom behaviors associated with `onQueueWithdrawal`. If the hook plays a critical role in queuing or processing withdrawals in a secure manner, markets without it could be exposed to risks. By not having a uniform withdrawal process (i.e., ensuring that the hook is always enabled), the protocol allows each market to diverge in terms of how withdrawals are managed, which weakens overall consistency and predictability across markets. This can introduce inefficiencies and potential risks into the system.
## Impact
The hook being optional, rather than always enabled, could lead to unintended behavior where certain market operations do not have the expected withdrawal queue checks. This can introduce inconsistencies in how withdrawals are handled across markets, leading to potential risks of bypassing important hooks for withdrawal processes. Furthermore, it undermines the principle of having a uniform withdrawal queue hook across markets, creating unnecessary complexity in market operations.

## Recommended Mitigation Steps
The code should be modified to always set the `onQueueWithdrawal` hook to `true` and only apply access control when `useOnQueueWithdrawal` is `true`.
