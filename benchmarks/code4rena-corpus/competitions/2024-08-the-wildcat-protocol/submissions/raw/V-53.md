# Vulnerability details

## Impact

In `LenderStatus.sol` allowing the `setCredential` and `unsetCredential` functions to be called by anyone could potentially create a security vulnerability, as these functions modify the authorization status of the lender and interfere with critical information regarding permissions. If both functions can be called without any restrictions, malicious users may arbitrarily change the authorization of lenders. `setCredential` function uses important information such as `lastApprovalTimestamp`, `lastProvider`, and `canRefresh` are being updated. The issue: If these functions can be called by anyone, an attacker could authorize any lender and manipulate the situation. The attacker could renew the lender's authorization through a fake provider or modify their existing credentials. `unsetCredential` function completely resets the lender's authorization. It disables the possibility of authorization renewal `canRefresh` and resets the last authorization timestamp. The issue: If anyone can call this function, a malicious user could reset the authorization of any lender, leaving them unauthorized. This could lead to a significant loss of functionality for users and potential financial damage.

````solidity
function setCredential(
    LenderStatus memory status,
    RoleProvider provider,
    uint256 timestamp
  ) internal pure {
    // User is approved, update status with new expiry and last provider
    status.lastApprovalTimestamp = uint32(timestamp);
    status.lastProvider = provider.providerAddress();
    status.canRefresh = provider.isPullProvider();
  }

  function unsetCredential(LenderStatus memory status) internal pure {
    status.canRefresh = false;
    status.lastApprovalTimestamp = 0;
    status.lastProvider = address(0);
  }
````

## Proof of Concept

The vulnerability lies in the fact that the setCredential and unsetCredential functions can be called by anyone, allowing unauthorized users to modify or revoke credentials for a lender. This could lead to malicious manipulation of lender status, bypassing the intended access control.

Steps to Reproduce:


Deploy the LenderStatus contract and MockRoleProvider (or the actual RoleProvider).

Initialize a LenderStatus struct with default values.

Simulate a malicious user (any address other than the authorized RoleProvider).
The malicious user calls setCredential and unsetCredential directly on the LenderStatus object, updating or resetting the credential information.

Verify that the lastProvider, lastApprovalTimestamp, and canRefresh fields in LenderStatus have been modified or reset by an unauthorized user.

## Recommended Mitigation Steps

Functions Need to Be Protected
Functions that modify authorizations should not be callable by everyone. To prevent security vulnerabilities, the following approaches can be taken:

Authorization Check: The functions should only be callable by users with specific permissions (e.g., only admins or authorized providers). Modifiers like onlyOwner or onlyAdmin can be used for this purpose.

```diff

+    modifier onlyAuthorized(RoleProvider provider) {
    require(provider.isAuthorized(msg.sender), "Not authorized");
    _;
}

function setCredential(
  LenderStatus memory status,
  RoleProvider provider,
  uint256 timestamp
+   ) internal onlyAuthorized(provider) {
  status.lastApprovalTimestamp = uint32(timestamp);
  status.lastProvider = provider.providerAddress();
  status.canRefresh = provider.isPullProvider();
}

```



Internal Access: These functions are already marked as internal, meaning they can only be called by the same contract or inherited contracts. However, this alone may not provide complete security, as internal functions can still be called indirectly from an external contract (e.g., a malicious contract). Therefore, access should be restricted with authorization checks.
