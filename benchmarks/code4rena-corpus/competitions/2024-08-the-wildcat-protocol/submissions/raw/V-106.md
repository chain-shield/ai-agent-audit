**PoC: Finding a collision**
In `HookFactorys::computeMarketAddress`, `CREATE2` salt is user-supplied .

 Which is then passed to `LibStoredInitCode::calculateCreate2Address`

```solidity
function calculateCreate2Address(
    uint256 create2Prefix,
    bytes32 salt,
    uint256 initCodeHash
  ) internal pure returns (address create2Address) {
    assembly {
      // Cache the free memory pointer so it can be restored at the end
      let freeMemoryPointer := mload(0x40)

      // Write 0xff + address to bytes 11:32
      mstore(0x00, create2Prefix)

      // Write salt to bytes 32:64
  @>    mstore(0x20, salt)

      // Write initcode hash to bytes 64:96
      mstore(0x40, initCodeHash)

      // Calculate create2 address
  @>    create2Address := and(keccak256(0x0b, 0x55),  0xffffffffffffffffffffffffffffffffffffffff)

      // Restore the free memory pointer
      mstore(0x40, freeMemoryPointer)
    }
  }
```

The address collision an attacker will need to find are:

 - One undeployed Wildcard market address (1).
 - Arbitrary attacker-controlled wallet contract (2).

Both sets of addresses can be brute-force searched because wildcard market address that is to be deployed is computed using  the `initCodeHash` and `salt` which is user supplied and also 


-  By brute-forcing many salt values, we have obtained many different (undeployed) wallet accounts for (1). The user can know the address of the Wildcard market before deploying it, since as shown in the above code snippet, the result is deterministic.
- (2) can be searched the same way. 


An attacker can find any single address collision between (1) and (2) with high probability of success using the following meet-in-the-middle technique, a classic brute-force-based attack in cryptography:
    
    1. Brute-force a sufficient number of values of salt (2^80), pre-compute the 
       resulting account addresses, and efficiently store them e.g. in a Bloom 
       filter data structure.
    2. Brute-force contract pre-computation to find a collision with any address 
       within the stored set in step 1.

The feasibility, as well as detailed technique and hardware requirements of finding a collision, are sufficiently described in multiple references:

- A past issue on [Sherlock](https://github.com/sherlock-audit/2023-07-kyber-swap-judging/issues/90) and [Code4rena](https://github.com/code-423n4/2024-04-panoptic-findings/issues/482#issuecomment-2096043469) describing this attack.
- [ EIP-3607, which rationale is this exact attack.](https://eips.ethereum.org/EIPS/eip-3607) The EIP is in final state.
- [A blog post discussing the cost (money and time) of this exact attack.](https://mystenlabs.com/blog/ambush-attacks-on-160bit-objectids-addresses)

The [hashrate of the BTC network](https://www.blockchain.com/explorer/charts/hash-rate) has reached `6.5 x 10^20` hashes per second as of time of writing, taking only just 31 minutes to achieve 2^80 hashes. A fraction of this computing power will still easily find a collision in a reasonably short timeline.

**PoC: Draining the market**


Even given EIP-3607 which disables an EOA if a contract is already deployed on top, we show that it's still possible to drain the Wildcard market entirely given a contract collision.

Assuming the attacker has already found an address collision against an undeployed Wildcard market, let's say `0xCOLLIDED`. The steps for complete draining of the market are as follow:

First tx:

Deploy the attack contract onto address `0xCOLLIDED`.
Set infinite allowance for `{0xCOLLIDED ---> attacker wallet}` for any token they want.
Destroy the contract using `selfdestruct`.
Post Dencun hardfork, `selfdestruct` is still possible if the contract was created in the same transaction. The only catch is that all 3 of these steps must be done in one tx.

The attacker now has complete control of any funds sent to `0xCOLLIDED`.

Second tx:

Deploy the market to `0xCOLLIDED`.
Wait until a market deployed holds a significant amount of funds  and drain it.
The attacker has stolen all funds from the market.

Paste the following file onto Remix (or a developing environment of choice): [POC](https://gist.github.com/midori-fuse/087aa3248da114a0712757348fcce814)
Deploy the contract Test.
1. Run the function `Test.test()` with a `salt` of your choice, and record the returned address. The result will be:

   - `Test.getCodeSize()` for that address will return exactly zero.
   - This proves the second property.
2. Using the same salt in step 3, run `Test.test()` again. The tx will go through, and the result will be:
   - `Test.test()` returns the same address as with the first run.

   - `Test.getCodeSize()` for that address will still return zero.
   - This proves the first property. 

The provided PoC has been tested on Remix IDE, on the Remix VM - Mainnet fork environment, as well as testing locally on the Holesky testnet fork, which as of time of writing, has been upgraded with the Dencun hardfork.
