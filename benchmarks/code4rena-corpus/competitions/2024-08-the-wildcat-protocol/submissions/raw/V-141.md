# Vulnerability details

## Description
The `HooksFactory` contract contains a vulnerability in its `pushProtocolFeeBipsUpdates` function that could lead to a fee update deadlock. This function attempts to update protocol fees for multiple markets associated with a specific hooks template in a single transaction. However, if any individual market update fails, the entire transaction reverts, potentially blocking fee updates for all subsequent markets.

The vulnerable function uses a low-level call to update each market's protocol fee without proper error handling. If a market is in a state that causes the fee update to revert (e.g., closed market, temporary lock, etc), it prevents the fee update from being applied to all subsequent markets in the range. This all-or-nothing approach creates a single point of failure that could be exploited or lead to operational issues for the protocol.

## Impact
Financial Losses for the Protocol: This will result in a significant loss of revenue for the protocol, since the fees will not be able to be updated. It will be in malicious actors benefit to keep the fees low and to not allow fee updates to go through.

Protocol-wide fee adjustments could be blocked, leading to inconsistencies across markets. 

Vulnerability to Exploitation: Malicious actors could exploit this vulnerability to manipulate market dynamics. By strategically creating or modifying markets to fail fee updates, they could create arbitrage opportunities or disrupt the protocol's economic balance.

Scalability Concerns: As the number of markets in the protocol grows, this vulnerability becomes increasingly problematic. It could eventually render protocol-wide fee updates practically impossible, severely limiting the protocol's ability to scale effectively.


## Proof of Concept

Prerequisites:

- A `HooksFactory` contract is deployed and operational.
- Multiple markets are associated with the same hooks template.
- An account with the necessary permissions to call `pushProtocolFeeBipsUpdates` is available.

Steps to Reproduce:

- At least three markets (Market A, Market B, and Market C) associated with the same hooks template are deployed.
- As a malicious actor, modifies Market B to a state where it will revert on fee updates (e.g., runs a bot that frontruns `pushProtocolFeeBipsUpdates` with a call to a function that temporarily locks the market or closes it, etc).
- The protocol admin attempts to update the protocol fee for all markets associated with the hooks template by calling `pushProtocolFeeBipsUpdates` with a range that includes all three markets.

Outcome:

- The transaction calling `pushProtocolFeeBipsUpdates` will revert entirely.
- Market A's fee will be updated successfully.
- The update will fail when it reaches Market B due to its locked or closed state.
- As a result of the transaction reverting, Market C's fee will not be updated, even though it's in a valid state to receive updates.
- The protocol admin will be unable to update fees for Market C and any subsequent markets without first addressing the issue with Market B.

This PoC demonstrates how a single market in an unexpected state can block fee updates for multiple markets, potentially leading to inconsistent fee structures across the protocol and hindering the protocol's ability to adjust its economic model efficiently.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Use a try/catch mechanism for individual market updates to prevent a single failure from reverting the entire transaction.

Add a boolean flag to allow skipping problematic markets. Then implement functionality to update fees in the problematic markets tagged with the problematic flag.
