# Vulnerability details

## Summary

The `WildcatSanctionsSentinel` contract contains a vulnerability in its escrow deployment mechanism. An attacker can potentially frontrun legitimate transactions to deploy malicious contracts at predetermined escrow addresses, leading to potential loss of funds for sanctioned users when executing withdrawals through the `executeWithdrawal` and `executeWithdrawals` function.

## Description

The `WildcatSanctionsSentinel` contract implements a `createEscrow` function that uses CREATE2 to deploy escrow contracts for sanctioned users. This function is public and can be called by anyone. The function first calculates the expected address of the escrow contract and checks if a contract already exists at that address. If no contract exists, it deploys a new WildcatSanctionsEscrow contract. However, if the contract already exists, it just returns the ecrow contract

```solidity
    // Skip creation if the address code size is non-zero
    if (escrowContract.code.length != 0) return escrowContract; //@audit if there is already a contract at this address, it should revert and not return. this makes the lender lose money transfered to an escrow contrat that has already been deployed and controlled by an attacker.
```

The vulnerability arises from the lack of access control on the `createEscrow` function and the assumption that any existing contract at the calculated address is a legitimate escrow. An attacker can exploit this by frontrunning legitimate transactions that would create escrows for sanctioned users.

**Economy**

The economic impact and time needed to carry out this exploit is relatively cheap and fast compared to the rewards, as all an attacker needs to do is to read from the mempool for withdrawal transactions and frontrun such transaction.

**Attack Senario**
The attack scenario is as follows:

- A sanctioned user attempts to withdraw funds, triggering the creation of an escrow.
- An attacker observes this transaction in the mempool.
- The attacker frontrunns with their own call to `createEscrow`, using the same parameters.
- The attacker deploys a malicious contract at the calculated address.
- When the original transaction executes, it finds an existing contract at the expected address and proceeds to transfer funds to it.
- This vulnerability could result in sanctioned users' funds being sent to - attacker-controlled contracts instead of legitimate escrows.


## Impact

The impact of this vulnerability is severe. It could lead to:

1. Loss of funds for sanctioned users
2. Compromise of the sanction management system
3. Potential regulatory issues for the protocol
4. Loss of trust in the Wildcat protocol

## POC

Add the following test to the  ``WildcatMarketWithdrawals`` test suite and run the following command to run the test: `forge test --mt test_escrow_frontrunning -vvv`

```solidity
    function test_escrow_frontrunning() external {
    // Setup
    _deposit(alice, 1e18);
    _requestWithdrawal(alice, 1e18);
    fastForward(parameters.withdrawalBatchDuration + 1);
    
    // Attacker frontrunning
    vm.prank(bob);
    address attackerEscrow = sanctionsSentinel.createEscrow(borrower, alice, address(asset));

    // Verify attacker's contract is deployed
    assertTrue(attackerEscrow.code.length > 0, "Attacker's contract should be deployed");

    // Sanction Alice
    sanctionsSentinel.sanction(alice);

    // Legitimate withdrawal attempt
    uint256 aliceBalanceBefore = asset.balanceOf(alice);
    uint256 escrowBalanceBefore = asset.balanceOf(attackerEscrow);
    
    market.executeWithdrawal(alice, uint32(block.timestamp - 1));

    // Verify funds went to the attacker's escrow, not Alice
    assertEq(asset.balanceOf(alice), aliceBalanceBefore, "Alice's balance should not change");
    assertGt(asset.balanceOf(attackerEscrow), escrowBalanceBefore, "Attacker's escrow should receive funds");
}
```

## Illustration

- Alice is a sanctioned user attempting to withdraw 1000 USDC from a Wildcat market.

- The market detects Alice is sanctioned and initiates escrow creation.

- Malicious actor Bob sees this transaction in the mempool.

- Bob frontrunns with a call to createEscrow using Alice's parameters.

- Bob deploys a malicious contract at the calculated escrow address.

- Alice's original transaction executes, finds Bob's contract, and transfers 1000 USDC to it.

- Alice's funds are now under Bob's control.


## Recommendation

Implement access control on the `createEscrow` function, restricting it to trusted contracts or roles or make it an internal function referenced through an interface.

Furthermore, you can change the `createEscrow` logic to revert when there is an existing contract at the expected address instead of returning.

```diff
    function createEscrow(
    address borrower,
    address account,
    address asset
  ) public override returns (address escrowContract) {
    escrowContract = getEscrowAddress(borrower, account, asset);

    // Skip creation if the address code size is non-zero
-    if (escrowContract.code.length != 0) return escrowContract; 
+    if (escrowContract.code.length != 0) revert EscrowAlreadyDeployed();
```
