# Vulnerability details

## Description
The `HooksFactory` contract contains a vulnerability in the `pushProtocolFeeBipsUpdates` function that could allow a malicious borrower to cause a Denial of Service (DoS) condition. This function iterates over all markets associated with a specific hooks template to update protocol fees. A borrower could deploy an excessive number of markets, causing this function to exceed block gas limits and preventing protocol-wide fee updates.

## Impact
- Prevention of protocol-wide fee updates for specific hooks templates, potentially leading to outdated or inconsistent fee structures across the protocol.

- Potential degradation of the protocol's ability to respond quickly to market conditions or economic changes that require fee adjustments.

## Proof of Concept
An attacker with registered borrower status on the Wildcat protocol could exploit the gas limit vulnerability in the `pushProtocolFeeBipsUpdates` function of the `HooksFactory` contract through the following steps:

1. The attacker, leveraging their status as a registered borrower, deploys an excessive number of markets (e.g., 500-5000) using a single hooks template. This can be done by repeatedly calling the `deployMarket` or `deployMarketAndHooks` function on the `HooksFactory` contract, using the same hooks template address for each deployment.

2. Each market deployment increases the size of the `_marketsByHooksTemplate` array for the specific hooks template used. This array is iterated over in the `pushProtocolFeeBipsUpdates` function.

3. Once a sufficient number of markets have been deployed, the attacker (or any other user, as the function is public) attempts to call the `pushProtocolFeeBipsUpdates` function on the `HooksFactory` contract, passing in the address of the hooks template used for the mass market deployment.

4. As the function attempts to iterate over all markets associated with the hooks template, it will eventually reach the block gas limit. This occurs because each iteration involves a low-level call to the `setProtocolFeeBips` function on each market contract, consuming a significant amount of gas.

5. The transaction will revert due to exceeding the block gas limit, effectively preventing any updates to the protocol fee for all markets using this hooks template.

Outcome: The `pushProtocolFeeBipsUpdates` function call will fail, reverting the transaction due to out of gas error. This prevents the protocol from updating fees for the affected hooks template, potentially leading to inconsistencies in fee structures across the protocol and hindering the protocol's ability to adjust to market conditions.

## Recommended Mitigation Steps
- Enhance the existing batched update mechanism in `pushProtocolFeeBipsUpdates`:
a) Implement a maximum number of markets to update per transaction
b) Add a circuit breaker if gas consumption exceeds a predefined threshold
c) Allow the function to be called multiple times to complete all updates if necessary

- Refactor the `pushProtocolFeeBipsUpdates` function to use a more gas-efficient update mechanism. Consider implementing a pull pattern where markets query for updates rather than pushing updates to all markets. Alternatively, implement a batched update system that can handle partial updates across multiple transactions.

- Implement monitoring and alerting for rapid market deployments:
a) Add events for market creation and set up off-chain monitoring
b) Implement temporary freezes on market creation if unusual activity is detected

- Implement a limit on the number of markets a single borrower can deploy per hooks template. This can be enforced in the market deployment functions of the `HooksFactory` contract.

- Add administrative functions to the `HooksFactory` contract for bulk market management, such as temporarily disabling or removing markets associated with a specific borrower. This provides a mechanism to mitigate an ongoing attack.
