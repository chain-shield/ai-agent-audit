# Vulnerability details

## Impact
The mismatch between the key types in the `accountStatuses` mapping under the struct `WithdrawData` and the `expiry` parameter type could lead to unexpected behavior, including:

1. Storage collisions
2. Incorrect withdrawal status retrievals
3. Potential loss or corruption of user withdrawal data

```solidity
function getAccountWithdrawalStatus(
    address accountAddress,
    uint32 expiry
  ) external view nonReentrantView returns (AccountWithdrawalStatus memory status) {
AccountWithdrawalStatus storage _status = _withdrawalData.accountStatuses[expiry][accountAddress];
```

Here, `expiry` is defined as `uint32`, but it's being used as a key for a mapping that expects `uint256`.

Solidity implicitly converts smaller integer types to larger ones when used as mapping keys. In this case, `uint32` is converted to `uint256`. However, this conversion can lead to unexpected results:

1. If we have two different `uint32` values that differ only in their upper bits (which are normally ignored in `uint32`), they will map to different keys in the `uint256` mapping.

2. This could potentially allow multiple withdrawal statuses for what should be a single expiry time, or cause withdrawal statuses to be stored at unexpected keys.

To demonstrate:

```solidity
uint32 expiry1 = 0x00000001;  // 1 in uint32
uint32 expiry2 = 0x100000001; // This would also be 1 in uint32, but the upper bits are set

// These might end up pointing to different storage slots:
accountStatuses[uint256(expiry1)][address(0x123...)]
accountStatuses[uint256(expiry2)][address(0x123...)]
```

In practice, this could lead to:
- Lost withdrawal statuses
- Incorrect withdrawal amounts
- Users potentially able to withdraw multiple times for the same expiry

## Recommended Mitigation Steps

1. Align the types in the mapping declaration with the types used in the code:

   ```solidity
   mapping(uint32 => mapping(address => AccountWithdrawalStatus)) accountStatuses;
   ```

2. If `uint256` is intentionally used for future-proofing or other reasons, explicitly cast `expiry` to `uint256` when using it as a key:

   ```solidity
   AccountWithdrawalStatus storage _status = _withdrawalData.accountStatuses[uint256(expiry)][accountAddress];
   ```
