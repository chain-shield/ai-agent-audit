# Vulnerability details

## Impact
A user remains in the "known" state even after withdrawing their entire balance, which violates the intended behavior of the system. According to the design, a user should only be considered "known" if they pass the necessary checks, including having a non-zero balance. The current implementation allows a "known" user to withdraw all their balance and still remain marked as a known lender.

## Proof of Concept
1. **Deposit Logic:**
   The system attempts to validate the user's credentials during the deposit process and marks them as "known" once their credentials are validated:

```solidity
   (bool hasValidCredential, bool roleUpdated) = _tryValidateAccessInner(
      status,
      lender,
      hooksData
   );
```

   If valid, the user’s status is updated, and they are marked as a known lender:
  
```solidity
   function _writeLenderStatus(
```

2. **Withdrawal Logic:**
   However, during the withdrawal process, no check is made to see if the lender has withdrawn their entire balance. Even if the balance is zero, the lender remains marked as "known":

 ```solidity
   if (!isKnownLenderOnMarket[lender][msg.sender] && !_tryValidateAccess(status, lender, hooksData)) {
      revert NotApprovedLender();
   }
```

3. **Transfer Logic:**
   Similarly, during transfers, the system skips access control checks if the recipient is already marked as a "known" lender, even if their balance is zero:
   
```solidity
   if (!isKnownLenderOnMarket[to][msg.sender]) {
      (bool hasValidCredential, bool wasUpdated) = _tryValidateAccessInner(toStatus, to, extraData);
      // Revert if the recipient does not have a valid credential and the market requires one
      if (market.transferRequiresAccess.and(!hasValidCredential)) {
         revert NotApprovedLender();
      }
   }
```

4. **Credential and Balance Discrepancy:**
   The discrepancy arises because there is no check for a zero balance when a user’s status is updated, allowing the user to remain "known" even after withdrawing all their funds.

Scenario. 

1. Lender Deposit 1000 market tokens. - Account 1
2. Lender moves 500 tokens to another account/external/wallet. Account 2
3. Lender now has 2 accounts Known.
4. Borrower decides to stop Lender from depositing more funds by blocking the deposit to Account 2.
5. Lenders Credentials for Account 2 has expired because timetolive is reached.

6. Lender withdraws all token in Account 2. scaled balance for 2 = 0.
7. Now since Account 2 has been restricted by the Lender it should not be able to receive tokens when unknown and the credentials of this account has expired they should not be able to receive funds when market.transferRequiresAccess is required.
8. All conditions in 7 is bypassed an Account 2 still retains it ability to receive funds even though they do not have a Valid Credential.

## Recommended Mitigation Steps
To resolve this issue, implement a balance check during the withdrawal process to ensure that a user with a zero balance is no longer considered "known." Modify the `onQueueWithdrawal` hook to check the account's balance before updating the lender's status:

```solidity
function onQueueWithdrawal(
   address lender,
   uint32 /* expiry */,
   uint /* scaledAmount */,
   MarketState calldata /* state */,
   bytes calldata hooksData
) external override {
   LenderStatus memory status = _lenderStatus[lender];
   
  

   // Proceed with the normal validation process
   if (!isKnownLenderOnMarket[lender][msg.sender] && !_tryValidateAccess(status, lender, hooksData)) {
      revert NotApprovedLender();
   }

++  // Check if the balance is zero and revoke known lender status
++   if (getScaledBalance(lender) == 0) {
++      isKnownLenderOnMarket[lender][msg.sender] = false;
++   }
++ }
```

This ensures that a lender's "known" status is revoked if their balance drops to zero, aligning with the intended behavior of the system.
