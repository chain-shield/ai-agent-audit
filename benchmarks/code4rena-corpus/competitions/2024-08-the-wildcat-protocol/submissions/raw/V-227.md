# Vulnerability details

## Proof of Concept
Observing the `getEscrowAddress()` function through the link below

https://github.com/code-423n4/2024-08-wildcat/blob/fe746cc0fbedc4447a981a50e6ba4c95f98b9fe1/src/WildcatSanctionsSentinel.sol#L144-L174

Addressing issues with Offset and Length
Offset (0x0b): The offset 0x0b is likely intended to skip the first 11 bytes, which include the 0xff prefix and the first 20 bytes of the contract address. However, this is not typically how memory layout works for such calculations, as the data you want to hash starts right after the 0xff prefix.

Length (0x55): The length 0x55 seems incorrect if you're only hashing the relevant part of the data. It is important to ensure that you cover exactly the bytes that are relevant to the CREATE2 computation.
Corrected Implementation
For CREATE2, you usually hash the following bytes:

1 byte for the 0xff prefix.
20 bytes for the contract address.
32 bytes for the salt.
32 bytes for the initialization code hash.
This sums up to 1 + 20 + 32 + 32 = 85 bytes.

Thus, you would typically want to start from offset 0x00 and read 0x55 bytes (85 in decimal).

If the wrong bytes are hashed (due to an incorrect offset), the resulting address will vary even with the same inputs, leading to unpredictable and inconsistent outputs.

This can lead to several security vulnerabilities such as;
Incorrect Escrow Address Generation If the wrong bytes are hashed, the resulting address will not correspond to the intended contract. This means that any operations or transactions that rely on this address will fail or interact with the wrong contract.

Lost Funds: If funds are sent to the incorrect escrow address, retrieving them may be impossible, resulting in financial losses for users and possibly the platform.
