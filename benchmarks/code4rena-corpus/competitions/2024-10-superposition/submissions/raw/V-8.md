# Vulnerability details

## Proof of Concept
The issue arises in the [`update()`](https://github.com/code-423n4/2024-10-superposition/blob/7ad51104a8514d46e5c3d756264564426f2927fe/pkg/seawater/src/tick.rs#L91-L95) function within the liquidity update mechanism of ticks.
```solidity
    // if we're below the current tick then set fee growth outside
    if tick <= cur_amm_tick {
        info.fee_growth_outside_0.set(*fee_growth_global_0);
        info.fee_growth_outside_1.set(*fee_growth_global_1);
    }
```
The comment suggests that the system is supposed to update the `fee_growth_outside` values only for `ticks` that are below the current tick (`cur_amm_tick`). However, the check uses `<=` instead of `<`, which leads to ticks being incorrectly flagged as outside the current range even if they are equal to the current tick.

This logic error violates the intended functionality, as `ticks` equal to the `current tick` should be treated as "inside" the active range, not "outside" of it.

## Impact
Misclassifying `ticks` as outside the active range leads to incorrect calculations of `fee growth`. As a result, the amount of `fees` that `liquidity providers` are entitled to may be miscalculated.

## Recommended Mitigation Steps
Change the `<=` operator to `<`, ensuring that only `ticks` strictly below the current AMM tick are considered outside the range
```diff
    // if we're below the current tick then set fee growth outside
-   if tick <= cur_amm_tick {
+   if tick < cur_amm_tick {
        info.fee_growth_outside_0.set(*fee_growth_global_0);
        info.fee_growth_outside_1.set(*fee_growth_global_1);
    }
```
