# Vulnerability details

## Proof of Concept
In the [`swap_2_internal_erc20()`](https://github.com/code-423n4/2024-10-superposition/blob/7ad51104a8514d46e5c3d756264564426f2927fe/pkg/seawater/src/lib.rs#L287-L297) function, the contract pulls only the `amount_in` (*the amount required for the swap*) from the user, but it attempts to refund the difference between `original_amount` and `amount_in`. But, since only `amount_in` is pulled, there should be no excess tokens to  refund.

```solidity
    // Pulling only `amount_in` from the user
    erc20::take(from, amount_in, permit2)?;

    // Attempting to refund the difference between `original_amount` and `amount_in`
    if original_amount > amount_in {
        erc20::transfer_to_sender(
            to,
            original_amount
                .checked_sub(amount_in)
                .ok_or(Error::TransferToSenderSub)?,
        )?;
    }
```

While the refund may still succeed if the pool holds sufficient tokens, it is not guaranteed to work as intended because the contract only pulls `amount_in` from the user. The contract may end up refunding tokens that were not pulled from the user, possibly relying on leftover tokens in the contract or if none, a revert will occur.

## Impact
Users may receive refunds from the pool of tokens in the contract, which may belong to other users or serve other purposes, leading to inconsistencies in token accounting.

## Recommended Mitigation Steps
The contract should pull the entire `original_amount` from the user. This ensures that the refund logic functions as intended, and any excess tokens can be safely and accurately returned to the user.
```diff
-   erc20::take(from, amount_in, permit2)?;
+   erc20::take(from, original_amount, permit2)?;
```
