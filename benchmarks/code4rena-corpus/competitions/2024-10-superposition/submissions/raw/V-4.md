# Vulnerability details

The take_permit2 function in the contract calls the encode_permit2 function, passing the details.deadline parameter without checking if the deadline has already expired. This means that expired permits could still be processed by the contract, leading to unauthorized or replayed token transfers.

The details.deadline value is passed to the encode_permit2 function without validation against the current block's timestamp (block.timestamp), which could result in expired permits being accepted.
This vulnerability is easy to exploit because the contract directly accepts expired permits without checking the deadline. An attacker with an old signed message can simply reuse it without any additional complex setup.
Permits are designed to authorize token transfers for a limited time, ensuring that users cannot reuse old permits indefinitely. The details.deadline is the cutoff point after which the permit is no longer valid. If there’s no check to compare the details.deadline with the current block’s timestamp, the contract might process expired permits, violating the time-bound authorization.

This PoC demonstrates how an expired permit can be used to execute a token transfer. The attacker reuses an expired signature to call the take_permit2 function successfully.

Steps to Reproduce:
Setup: A user creates and signs a permit for transferring tokens with a deadline that is shortly in the future.
Expiration: The permit reaches the deadline and is now expired.
Exploit: A malicious actor reuses the expired permit by calling take_permit2, passing the expired details.deadline parameter.

The Fix:
Before executing the transfer, the contract should verify that the details.deadline has not already passed. This is typically done by comparing the current block timestamp (block.timestamp) to the details.deadline.
