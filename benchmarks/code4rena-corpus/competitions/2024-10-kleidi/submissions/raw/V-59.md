# Vulnerability details

`cleanup` function removes the expired operation from `_liveProposals` but fails to update the timestamps mapping. This leads to inconsistent state management for expired operations.

This bug can cause expired operations to remain in an ambiguous state. The `isOperation` function, which checks `timestamps[id] > 0`, will continue to return true for cleaned-up operations. This can lead to confusion and potential misuse of the contract's state.

## Proof of Concept
In the `cleanup` function, this function is not correctly updating the `operationStatus` mapping for expired operations.

The cleanup function is not consistently changing the status of expired operations. This is happening because the function may not be properly updating the `operationStatus` mapping for all cases.

We can confirm this by reproducing the bug.

1. Create an operation with a specific ID.
2. Let the operation expire.
3. Call the `cleanup` function on the expired operation.
4. Check the `operationStatus` before and after cleanup - they may be the same in some cases.

In [Timelock.sol:671-677](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L671-L677)
```solidity
function cleanup(bytes32 id) external whenNotPaused {
    require(isOperationExpired(id), "Timelock: operation not expired");
    /// unreachable state assert statement
    assert(_liveProposals.remove(id));
    // @Audit: Missing update to operationStatus[id]

    emit Cleanup(id);
}
```
It removes the expired operation from `_liveProposals`, but it doesn't update the `operationStatus` mapping. This explains why the `initialOperationStatus` and `operationStatus[id]` remain the same.

In `Timelock.t.sol`, we can add this test to verify this behavior:
```solidity
function testCleanupDoesNotChangeOperationStatus() public {
    bytes32 id = testScheduleProposalSafeSucceeds();
    
    // Wait for the operation to expire
    vm.warp(block.timestamp + MINIMUM_DELAY + EXPIRATION_PERIOD);
    
    bool initialStatus = timelock.isOperation(id);
    timelock.cleanup(id);
    bool finalStatus = timelock.isOperation(id);
    
    // @Audit: This assertion will pass, indicating the bug
    assertEq(initialStatus, finalStatus, "Operation status should change after cleanup");
}
```
This test would demonstrate that the operation status doesn't change after cleanup, confirming the vulnerability.

### PoC
1. Schedule an operation:
```solidity
bytes32 id = timelock.schedule(address(timelock), 0, abi.encodeWithSelector(timelock.updateDelay.selector, MINIMUM_DELAY), bytes32(0), MINIMUM_DELAY);
```
2. Wait for the operation to expire
```solidity
vm.warp(block.timestamp + MINIMUM_DELAY + timelock.expirationPeriod() + 1);
```
3. Call cleanup
```solidity
timelock.cleanup(id);
```
4. Check the operation status
```solidity
bool isStillOperation = timelock.isOperation(id);
assert(isStillOperation == true); // This will pass, showing the bug
```
5. Verify the inconsistency
```solidity
bool inLiveProposals = timelock.getAllProposals().length > 0 && timelock.getAllProposals()[0] == id;
assert(isStillOperation != inLiveProposals); // This will pass, showing the inconsistency
```
This demonstrates that after cleanup, the operation is removed from `_liveProposals` but still considered an active operation according to `isOperation`, creating an inconsistent state in the contract.

The reason for this inconsistency is that the cleanup function focuses solely on removing the operation from [_liveProposals:674](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L674)
```solidity
assert(_liveProposals.remove(id));
```
However, it doesn't update the `timestamps` mapping, which is checked in the [isOperation function:392-394](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L392-L394)
```solidity
function isOperation(bytes32 id) public view returns (bool) {
    return timestamps[id] > 0;
}
```
This discrepancy leads to a situation where an operation can be simultaneously considered cleaned up (not in `_liveProposals`) and active (still has a non-zero timestamp).

## Recommended Mitigation Steps
We recommend updating the `cleanup` function to ensure consistent state management
```diff
function cleanup(bytes32 id) external whenNotPaused {
    require(isOperationExpired(id), "Timelock: operation not expired");
    /// unreachable state assert statement
    assert(_liveProposals.remove(id));
+   delete timestamps[id];

    emit Cleanup(id);
}
```
Consider adding a specific "cleaned up" or "expired" status to the `timestamps` mapping to differentiate between active, executed, and cleaned-up operations.
