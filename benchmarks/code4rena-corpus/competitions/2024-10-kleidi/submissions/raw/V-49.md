# Vulnerability details

`Timelock.cancel` function fails to update the `totalOperations` counter when an operation is cancelled, leading to a state inconsistency between the actual number of live operations and the recorded total.

This's an issue because the `cancel` function only removes the operation from the `_liveProposals` set and deletes its timestamp, without decrementing the `totalOperations` counter. This causes the counter to remain unchanged even when operations are cancelled, gradually increasing the discrepancy between the reported and actual number of live operations.

1. The issue s in the `cancel` function of the Timelock contract.
2. The `cancel` function is called with a valid operation ID.
3. The operation is successfully cancelled, removing it from the `_liveProposals` set.
4. However, the `totalOperations` counter is not properly updated.

## Proof of Concept
```solidity
function cancel(bytes32 id) external onlySafe whenNotPaused {
    require(
        isOperation(id) && _liveProposals.remove(id),
        "Timelock: operation does not exist"
    );

    delete timestamps[id];
    emit Cancelled(id); // <= FOUND
}
```
1. Schedule multiple operations (e.g., 5)
2. Verify `totalOperations` is 5
3. Cancel 2 operations using `cancel`
4. Check `totalOperations` - it will still be 5
5. Verify `getAllProposals().length` returns 3
6. Observe the discrepancy between `totalOperations` (5) and actual live operations (3)

This sequence of events clearly shows how the contract state becomes inconsistent after cancelling operations. In a governance context, this could lead to incorrect quorum or voting power calculations if they depend on the total number of operations.

## Recommended Mitigation Steps
Decrement the `totalOperations` counter when an operation is cancelled. 
```diff
    );

    delete timestamps[id];
+   totalOperations--;
    emit Cancelled(id);
}
```
Additionally, i'll recommend:

1. Add a function to reconcile `totalOperations` with the actual number of live operations, in case discrepancies have already occurred.
2. Implement periodic checks to ensure `totalOperations` matches `_liveProposals.length()`.
3. Consider adding events to log changes in `totalOperations` for better off-chain tracking
