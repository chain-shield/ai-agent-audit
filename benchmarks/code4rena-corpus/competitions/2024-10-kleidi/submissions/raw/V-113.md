# Vulnerability details

## Proof of Concept
The expiration period logic, which determines when an operation can no longer be executed, relies heavily on accurate block timestamps. However, miners can manipulate the block.timestamp to allow an expired operation to be executed outside of its intended window. This could allow attackers to bypass the expiration check and execute malicious operations even after they should have expired.

```
function isOperationExpired(bytes32 id) public view returns (bool) {
    uint256 timestamp = timestamps[id];
    require(timestamp != 0, "Timelock: operation non-existent");
    require(timestamp != 1, "Timelock: operation already executed");

    return block.timestamp >= timestamp + expirationPeriod;
}

function cleanup(bytes32 id) external whenNotPaused {
    require(isOperationExpired(id), "Timelock: operation not expired");
    assert(_liveProposals.remove(id));

    emit Cleanup(id);
}
```

An attacker could wait until just before the expiration period and manipulate the block.timestamp to ensure an operation that should have expired is executed.

The attacker creates a transaction that will expire soon.
Just before the expiration, the attacker manipulates the block.timestamp by creating a custom transaction or block mining.
The transaction is executed even though it should have expired.

Attackers can execute operations that should have expired, potentially causing harm to the contract’s state or stealing funds.



## Recommended Mitigation Steps
Introduce a buffer or stricter checks that ensure operations are executed strictly within their valid period, and block any execution attempts close to expiration.
Use block.number or implement time validation based on multiple sources to prevent timestamp manipulation.
