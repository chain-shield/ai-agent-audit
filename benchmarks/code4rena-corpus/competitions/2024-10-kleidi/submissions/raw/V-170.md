# Vulnerability details

Based on the interaction between pause functionality and proposal management, when a Guardian pauses the contract, it automatically cancels all pending proposals. The `setGuardian` function also resets pause state without proper validation, creating a privilege escalation path. [src/Timelock.sol#L687-L700](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L687-L700)
```solidity
function pause() public override {
    super.pause(); // Guardian initiates pause // Guardian can pause and then manipulate proposal states
    
    // All proposals get cancelled automatically
    bytes32[] memory proposals = _liveProposals.values();
    for (uint256 i = 0; i < proposals.length; i++) {
        bytes32 id = proposals[i];
        delete timestamps[id]; // <@audit Allows cancellation of all proposals
        assert(_liveProposals.remove(id));
        emit Cancelled(id);
    }
}
```
The guardian role has pause capabilities but should not have access to core timelock functions. However, the access control checks are insufficient: [src/Timelock.sol#L960-L968](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L960-L968)
```solidity
function updateDelay(uint256 newDelay) external onlyTimelock {
    require(
        newDelay >= MIN_DELAY && newDelay <= MAX_DELAY,
        "Timelock: delay out of bounds"
    );
    emit MinDelayChange(minDelay, newDelay);
    minDelay = newDelay;
}
```
The Guardian role can effectively control and block timelock operations beyond its intended scope. The Guardian can pause the contract and force cancellation of all pending proposals, undermining the timelock's security guarantees.

Issue Path:

1. A guardian can potentially bypass the `onlyTimelock` modifier
2. This allows them to call [updateDelay](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L960-L968) and [schedule](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L521-L539) functions

Connected Paths:

1. `setGuardian() -> _setPauseTime() -> pause state manipulation`
2. `pause() -> proposal cancellation -> timelock bypass`
3. `schedule() -> pause check -> proposal blocking`

This creates a vulnerability where guardians can effectively control the timelock's operation beyond their intended scope.

Attack Sequence:

1. Alice submits important proposal through timelock
2. Guardian pauses contract
3. Alice's proposal gets cancelled automatically
4. Contract remains paused, blocking new proposals
5. Guardian effectively controls timelock operation
```solidity
function exploitGuardianPrivileges() public {
    // 1. Guardian pauses contract
    vm.prank(guardian);
    timelock.pause();
    
    // 2. All proposals are cancelled automatically
    assert(timelock.getAllProposals().length == 0);
    
    // 3. New proposals cannot be queued while paused
    vm.prank(address(safe));
    vm.expectRevert("Timelock: paused");
    timelock.schedule(address(target), 0, "", bytes32(0), MINIMUM_DELAY);
}
```
I believe there is a high likelihood due to:

* Guardians can block critical protocol upgrades
* Users lose queued proposals without recourse
* Timelock security guarantees compromised
* Protocol governance can be effectively controlled by Guardian
