# Vulnerability details

## Proof of Concept

This vulnerability is caused by the combination of reentrancy issues in Proposal._startBuild and Proposal._endBuild and the ignored return value in MultisigProposal._simulateActions. An attacker can exploit reentrancy during the proposal build process to call _simulateActions multiple times, causing unexpected proposal execution flow. The ignored return value in functionCall(data) allows failed multisig calls to be processed as though they succeeded, leading to inaccurate proposal states and bypassed validation.

### Impact
Proposal State Manipulation: Reentrancy within _startBuild and _endBuild enables an attacker to manipulate the proposal lifecycle, resulting in repeated or reordered actions.

Bypass of Validation: The ignored return in _simulateActions causes any failed actions to appear successful, enabling an attacker to bypass security checks and introduce inconsistent multisig execution states.

Critical Proposal Execution Vulnerability: This attack chain compromises the proposal’s integrity, allowing unauthorized or incorrect actions to pass as valid in the multisig process.

### Attack Scenario
Step 1: Call Proposal._startBuild to begin building a proposal, initiating reentrancy.
Step 2: During the execution, trigger _simulateActions multiple times through reentrant calls in _endBuild, altering the number and sequence of simulated actions.
Step 3: With the ignored return in _simulateActions, any failed calls in functionCall(data) are overlooked, allowing an attacker to bypass failures and misrepresent proposal success.

## Recommended Mitigation Steps
Add nonReentrant Modifiers: Apply nonReentrant guards to _startBuild and _endBuild to prevent the reentrant manipulation of proposals.

Handle Return Values in _simulateActions: Check return values of functionCall(data) and revert on failure, ensuring unsuccessful calls do not bypass validation.

Optimize External Calls in Loops: Reduce gas inefficiency by avoiding external calls within loops in Proposal.print and Proposal._getAddressLabel, minimizing potential gas-related exploits.
