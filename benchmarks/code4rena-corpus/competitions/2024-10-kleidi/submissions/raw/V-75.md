# Vulnerability details

## Proof of Concept
In the RecoverySpell.sol contract, the executeRecovery function relies on signatures provided by owners to validate the recovery process. It uses the ECDSA.recover function to recover the signer's address and ensures signatures are not duplicated. However, this process is handled using low-level assembly operations and lacks robustness, which could introduce security issues like signature replay, invalid signature acceptance, or bypassing owner thresholds.
```
for (uint256 i = 0; i < v.length; i++) {
    address recoveredAddress = ECDSA.recover(digest, v[i], r[i], s[i]);
    bool valid;

    assembly ("memory-safe") {
        valid := tload(recoveredAddress)
        if eq(valid, 1) { tstore(recoveredAddress, 0) }
    }

    require(
        valid && recoveredAddress != address(0),
        "RecoverySpell: Invalid signature"
    );
}
```
An attacker could attempt to manipulate the signature verification process by:

Reusing valid signatures from a previous recovery process.
Exploiting the contract’s low-level validation mechanism to introduce invalid or tampered signatures that bypass the verification logic.
While the contract prevents duplicate signatures using assembly operations, this method may not sufficiently protect against replay attacks or invalid signatures, potentially allowing an attacker to bypass the owner threshold and hijack the recovery process.

Steps to Reproduce:

collect a valid signature from a previous successful recovery.
Submit the reused signature or craft invalid signatures that still pass the low-level checks.
Trigger the recovery process with invalid or reused signatures.

Potential Impact
Unauthorized Access: An attacker could submit invalid or reused signatures to bypass the recovery threshold and gain control of the Safe.
Signature Replay Attack: If signatures are not properly tracked and validated, an attacker could replay previously valid signatures to execute the recovery process again, even after the Safe’s ownership has been updated.
Ownership Compromise: A successful exploitation could lead to unauthorized ownership changes, allowing an attacker to take control of the Safe and its funds.



## Recommended Mitigation Steps
Improve Signature Validation:

Use robust signature validation mechanisms that avoid relying on low-level assembly operations. OpenZeppelin’s ECDSA library provides safer validation methods.

```
for (uint256 i = 0; i < v.length; i++) {
    address recoveredAddress = ECDSA.recover(digest, v[i], r[i], s[i]);
    require(validOwners[recoveredAddress], "Invalid owner signature");
    require(!usedSignatures[recoveredAddress], "Signature reused");
    usedSignatures[recoveredAddress] = true;
}
```

Implement a mechanism that tracks which signatures have already been used to prevent replay attacks.
Add a mapping that tracks signatures to ensure that once used, they cannot be reused.
Use event logging to track signature usage and recovery attempts, allowing for better auditing and troubleshooting.
