# Vulnerability details

## Proof of Concept
The `executeWhitelistedBatch` function iterates through an array of targets, values, and payloads, executing each one. For each iteration, it calls `_execute`, which makes an external call to the target contract. This external call can reenter the Timelock contract, leading to unexpected behavior.

Based on the design of the `executeWhitelistedBatch` function. It iterates through an array of targets, executing each one sequentially. For each target, it calls the `_execute` function, which makes an external call. This external call is made before the function updates any state or completes its execution, creating a window for reentrancy.

The core issue lies in the fact that the function assumes that the whitelisted calls are safe and doesn't protect against the possibility of a malicious whitelisted contract. Even though the calldata is checked before execution, this check doesn't prevent reentrancy.

The vulnerable code is the `executeWhitelistedBatch` function in [Timelock.sol#743-751](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L743-L751)

One could create a malicious contract that, when called by the Timelock, reenters the Timelock and calls `executeWhitelistedBatch` again, potentially changing the `totalOperations` value. Any whitelisted operation that interacts with an attacker-controlled contract could potentially trigger this vulnerability. Given that the Timelock contract is designed to execute various operations, including interactions with external contracts, the risk is significant.

_Consider the following scenario_

1. A malicious contract is whitelisted in the Timelock.
2. An attacker calls `executeWhitelistedBatch` with the malicious contract as one of the targets.
3. When the Timelock executes the call to the malicious contract, it reenters the Timelock by calling `executeWhitelistedBatch` again.
4. This reentrancy allows the attacker to execute additional operations or manipulate state before the first batch execution completes.

## Recommended Mitigation Steps
Consider implementing the checks-effects-interactions pattern in the `executeWhitelistedBatch` function to ensure all state changes are made before external calls.
