# Vulnerability details

## Summary

A critical vulnerability has been identified in the `RecoverySpell.sol` contract of the Kleidi Wallet project. The issue arises from the improper use of assembly opcodes (`tload` and `tstore`) within the `executeRecovery` function, leading to flawed signature verification. This flaw either prevents the recovery mechanism from functioning or potentially allows unauthorized recovery operations, undermining the wallet's security.

## Vulnerability Details

### **Incorrect Assembly Opcode Usage**

The `executeRecovery` function employs non-existent EVM opcodes `tload` and `tstore` instead of the standard `sload` and `sstore` for storage operations. This misuse disrupts the intended signature verification process.

```solidity
assembly ("memory-safe") {
    valid := tload(recoveredAddress)
    if eq(valid, 1) { tstore(recoveredAddress, 0) }
}
```

**Explanation:**
- **Issue:** `tload` and `tstore` are **invalid EVM opcodes**. The correct opcodes for storage operations are `sload` (to read from storage) and `sstore` (to write to storage).
- **Consequence:** This results in **compilation errors**, preventing the contract from deploying successfully. If hypothetically bypassed, it would cause the function to **revert at runtime**, rendering the `executeRecovery` function inoperative.

### **Flawed Signature Verification Logic**

Even if the assembly were corrected to use valid opcodes, the improper handling of storage slots can compromise signature verification integrity.

```solidity
bytes32 digest = getDigest();
for (uint256 i = 0; i < v.length; i++) {
    address recoveredAddress = ECDSA.recover(digest, v[i], r[i], s[i]);
    bool valid;

    assembly ("memory-safe") {
        valid := sload(recoveredAddressSlot)
        if eq(valid, 1) { sstore(recoveredAddressSlot, 0) }
    }

    require(
        valid && recoveredAddress != address(0),
        "RecoverySpell: Invalid signature"
    );
}
```

**Explanation:**
- **Issue:** Even with valid opcodes, mapping `recoveredAddress` directly to storage slots without proper slot calculation can lead to **incorrect verification**, potentially allowing unauthorized signatures to pass or valid signatures to fail.
- **Consequence:** This can either **block legitimate recovery operations** or **enable unauthorized access**, depending on the implementation flaws.

## Impact

- **Denial of Service (DoS):** Legitimate users are **unable to perform recovery operations**, potentially losing access to their assets.
- **Unauthorized Access:** If signature verification is bypassed, malicious actors could **execute recovery operations**, gaining unauthorized control over user wallets.
- **Trust Erosion:** Users may lose trust in the security of the Kleidi Wallet, impacting the project's reputation and user base.

## Recommendations

### **1. Correct Assembly Opcode Usage**

- **Replace Invalid Opcodes:**
  
  ```solidity
  assembly ("memory-safe") {
      valid := sload(recoveredAddressSlot)
      if eq(valid, 1) { sstore(recoveredAddressSlot, 0) }
  }
  ```

  - **Action:** Use `sload` and `sstore` instead of `tload` and `tstore`.
  - **Note:** Ensure that `recoveredAddressSlot` correctly maps to the intended storage slot.

### **2. Utilize Established Libraries for Signature Verification**

- **Leverage OpenZeppelin's ECDSA Library:**
  
  ```solidity
  require(
      ECDSA.recover(digest, v[i], r[i], s[i]) == owners[i],
      "RecoverySpell: Invalid signature"
  );
  ```

  - **Action:** Replace manual signature verification with trusted library functions to ensure security and correctness.
