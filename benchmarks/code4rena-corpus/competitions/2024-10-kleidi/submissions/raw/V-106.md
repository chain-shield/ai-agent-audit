# Vulnerability details

## Summary

A critical vulnerability has been identified in the `RecoverySpell.sol` contract of the Kleidi Wallet project. The contract utilizes non-standard EVM opcodes `tstore` and `tload` within assembly blocks. These opcodes are not recognized by the Ethereum Virtual Machine (EVM), leading to compilation failures and rendering the contract non-deployable and non-functional. This flaw not only disrupts the intended recovery mechanisms but also poses severe security risks if attempted to be exploited through unconventional means.

## Vulnerability Details

### **Proof of Concept (PoC)**

#### **1. Identification of Undefined Opcodes**

```solidity
assembly ("memory-safe") {
    tstore(owner, 1)
}
```

**Explanation:**  
The `tstore` opcode is used within an assembly block to store a value in a specific location. However, `tstore` is **not** a standard EVM opcode. The correct opcode for storing a value in storage is `sstore`. The use of `tstore` will result in a compilation error.

---

#### **2. Attempt to Load Undefined Opcode**

```solidity
assembly ("memory-safe") {
    valid := tload(recoveredAddress)
    if eq(valid, 1) { tstore(recoveredAddress, 0) }
}
```

**Explanation:**  
Similarly, `tload` is used to load a value from a specific location within an assembly block. `tload` is **not** a recognized EVM opcode. The standard opcode for loading a value from storage is `sload`. The presence of `tload` will cause the contract to fail during compilation.

---

#### **3. Compilation Failure Due to Undefined Opcodes**

```bash
Error: Undeclared identifier.
    tstore(owner, 1)
    ^^^^^
```

**Explanation:**  
When attempting to compile the `RecoverySpell.sol` contract, the Solidity compiler will throw an error indicating that `tstore` is an undeclared identifier. This prevents the contract from being successfully compiled and deployed.

---

#### **4. Hypothetical Scenario with Custom EVM Implementation**

```solidity
function executeRecovery() external {
    for (uint256 i = 0; i < owners.length; i++) {
        address owner = owners[i];
        assembly ("memory-safe") {
            tstore(owner, 1)
        }
    }
}
```

**Explanation:**  
If, hypothetically, a custom EVM implementation or preprocessor defines `tstore` and `tload`, the `executeRecovery` function could manipulate storage in unintended ways. This could allow unauthorized access or modification of critical variables, undermining the contract's security and integrity.

---

## Impact

- **Contract Deployment Failure:** The use of undefined opcodes `tstore` and `tload` prevents the `RecoverySpell.sol` contract from being compiled and deployed using standard Solidity compilers.
  
- **Security Risks:** If a custom EVM implementation were to interpret these undefined opcodes, it could lead to unauthorized storage manipulations, allowing malicious actors to alter critical contract state variables.
  
- **Operational Disruption:** The failure to deploy the `RecoverySpell` contract disrupts the recovery mechanisms of the Kleidi Wallet, potentially locking users out of their funds without a reliable recovery method.

## Recommendations

1. **Remove Undefined Opcodes:**
   - **Eliminate `tstore` and `tload`:** Replace these with standard EVM opcodes such as `sstore` and `sload` for storage operations.
   
   ```solidity
   assembly {
       sstore(ownerSlot, 1)
   }
   ```
   
   **Explanation:**  
   Using `sstore` ensures that values are correctly stored in the designated storage slots, adhering to EVM standards.
