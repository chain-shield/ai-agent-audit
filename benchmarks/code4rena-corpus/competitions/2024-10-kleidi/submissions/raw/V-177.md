# Vulnerability details

## Summary

The **InstanceDeployer** contract is a crucial component of the Kleidi protocol, responsible for creating new wallet instances. However, a critical bug in the `createSystemInstance` function prevents the successful deployment of system instances. This issue lies in the construction of the signature used in the Safe's `execTransaction` function, which fails due to incorrect encoding, thereby blocking instance creation. Without functional instance creation, the Kleidi system is rendered unusable, as it heavily relies on this process to onboard users and create secure wallets.

## Vulnerability Details

The issue originates from the way the signature is crafted in the `createSystemInstance` function, specifically how the `Safe(payable(walletInstance.safe)).execTransaction` function is called. Below is the key section of the problematic code:

[InstanceDeployer.sol#L335-L380](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/InstanceDeployer.sol#L335-L380)
```solidity

        {
```

#### Signature Verification Failure in Safe Contract

The Safe contract’s `execTransaction` function uses the following logic to verify the provided signatures:

```solidity
function execTransaction(
        address to,
        uint256 value,
        bytes calldata data,
        Enum.Operation operation,
        uint256 safeTxGas,
        uint256 baseGas,
        uint256 gasPrice,
        address gasToken,
        address payable refundReceiver,
        bytes memory signatures
    ) public payable virtual returns (bool success) {
        bytes32 txHash;
        // Use scope here to limit variable lifetime and prevent `stack too deep` errors
        {
            bytes memory txHashData = encodeTransactionData(
                // Transaction info
                to,
                value,
                data,
                operation,
                safeTxGas,
                // Payment info
                baseGas,
                gasPrice,
                gasToken,
                refundReceiver,
                // Signature info
                nonce
            );
            // Increase nonce and execute transaction.
            nonce++;
            txHash = keccak256(txHashData);
 @>        checkSignatures(txHash, txHashData, signatures);
    }
```

This is how the `checkSignatures` function looks like: 
```solidity
function checkSignatures(bytes32 dataHash, bytes memory data, bytes memory signatures) public view {
    uint256 _threshold = threshold;
    require(_threshold > 0, "GS001");
    checkNSignatures(dataHash, data, signatures, _threshold);
}
```

The important part for us is that it invokes `checkNSignatures` function, where the protocol checks for the validity of the signature and this is where the issue actually occurs.


```solidity
 function checkNSignatures(bytes32 dataHash, bytes memory data, bytes memory signatures, uint256 requiredSignatures) public view {
        // Check that the provided signature data is not too short
        require(signatures.length >= requiredSignatures.mul(65), "GS020");
        // There cannot be an owner with address 0.
        address lastOwner = address(0);
        address currentOwner;
        uint8 v;
        bytes32 r;
        bytes32 s;
        uint256 i;
        for (i = 0; i < requiredSignatures; i++) {
            (v, r, s) = signatureSplit(signatures, i);
            if (v == 0) {
              ...
            } else if (v == 1) {
                // If v is 1 then it is an approved hash
                // When handling approved hashes the address of the approver is encoded into r
                currentOwner = address(uint160(uint256(r)));
                // Hashes are automatically approved by the sender of the message or when they have been pre-approved via a separate transaction
                require(msg.sender == currentOwner || approvedHashes[currentOwner][dataHash] != 0, "GS025");
            }
```

In this function, we extract the `(v, r, s)` values using the `signatureSplit` function. The `for` loop runs from 0 to 1 since our `requiredSignatures` is set to 1. This variable represents the threshold, which is set in the `InstanceDeployer::createSystemInstance` function [here](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/InstanceDeployer.sol#L149). You can see that when `Safe::checkSignature` calls `Safe::checkNSignatures`, it provides `_threshold` for the `requiredSignatures` parameter. The `_threshold` is derived from `uint256 _threshold = threshold;`, where `threshold` is a state variable in the Safe contract itself, as set in the aforementioned [place](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/InstanceDeployer.sol#L149). This means our `for` loop will run only once for `i == 0`. Upon entering the loop, the `signatureSplit` function is invoked with our signature and `0` for `i`, returning the `v, r, s` values.

In the `else if (v == 1)` condition, since we set `v` to be equal to 1 [here](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/InstanceDeployer.sol#L340), the `msg.sender == currentOwner` check will fail. Additionally, the condition `approvedHashes[currentOwner][dataHash] != 0` will fail as well, since we never called the `Safe::approveHash` function with `msg.sender == InstanceDeployer`.

```solidity 
pragma solidity 0.8.25;

import {Test} from "forge-std/Test.sol";

contract InstanceDeployer {
    function getSignature() external view returns (bool) {
        bytes memory signature;
        /// craft the signature singing off on all of the multicall
        /// operations
        {
            bytes32 r = bytes32(uint256(uint160(address(this))));
            uint8 v = 1;

            assembly ("memory-safe") {
                /// Load free memory location
                let ptr := mload(0x40)

                /// We allocate memory for the return data by setting the free memory location to
                /// current free memory location + data size + 32 bytes for data size value

                ///         4 -> 82
                mstore(0x40, add(ptr, 97))
                ///         4 -> 179

                /// Store the size of the signature in the first 32 bytes:
                /// 65 (r + s + v)
                mstore(ptr, 65)

                ///
                ///                              Data Offsets
                ///
                ///                 --------------------------------------
                ///  bytes length   |      32     |   32  |  32   |   1  |
                ///                 --------------------------------------
                ///      bytes      |     0-31    | 32-63 | 64-95 |  96  |
                ///                 --------------------------------------
                ///      data       | length = 65 |   r   |   s   |   v  |
                ///                 --------------------------------------
                ///

                /// store r at offset 32 to 64 in the allocated pointer
                mstore(add(ptr, 0x20), r)

                /// no need to store s, this should be 0 bytes

                /// store v at offset 96 to 97 in the allocated pointer
                mstore8(add(ptr, 0x60), v)

                /// Point the signature data to the correct memory location
                signature := ptr
            }
        }
        return checkNSignatures(signature);
    }

    function checkNSignatures(bytes memory signatures) public view returns (bool) {
        uint256 requiredSignatures = 1; // @audit threshold == 1
        require(signatures.length >= requiredSignatures * 65, "GS020");
        // There cannot be an owner with address 0.
        address lastOwner = address(0);
        address currentOwner;
        uint8 v;
        bytes32 r;
        bytes32 s;
        uint256 i;

        // @audit I removed the logic inside the original if statement (v == 0), as our v == 1;
        for (i = 0; i < requiredSignatures; i++) {
            (v, r, s) = signatureSplit(signatures, i);
            if (v == 0) {
                revert();
            } else if (v == 1) {
                // If v is 1 then it is an approved hash
                // When handling approved hashes the address of the approver is encoded into r
                currentOwner = address(uint160(uint256(r)));
                // Hashes are automatically approved by the sender of the message or when they have been pre-approved via a separate transaction

                // @audit I changed this line
                // require(msg.sender == currentOwner || approvedHashes[currentOwner][dataHash] != 0, "GS025");
                // to only  msg.sender == currentOwner and insteand of using require, I'm just simply returning the value to showcase the issue in the PoC test.
                return msg.sender == currentOwner;
            }
        }
    }

    function signatureSplit(bytes memory signatures, uint256 pos)
        internal
        pure
        returns (uint8 v, bytes32 r, bytes32 s)
    {
        // solhint-disable-next-line no-inline-assembly
        assembly {
            let signaturePos := mul(0x41, pos)
            r := mload(add(signatures, add(signaturePos, 0x20)))
            s := mload(add(signatures, add(signaturePos, 0x40)))
            /**
             * Here we are loading the last 32 bytes, including 31 bytes
             * of 's'. There is no 'mload8' to do this.
             * 'byte' is not working due to the Solidity parser, so lets
             * use the second best option, 'and'
             */
            v := and(mload(add(signatures, add(signaturePos, 0x41))), 0xff)
        }
    }
}
```

## Impact

The impact of this bug is severe, as it prevents the creation of new wallet instances, effectively halting the core functionality of the Kleidi system.

## Recommended Mitigation Steps

The fix is not easy. The signature creation should be changed and it must be thoroughly tested to ensure that it works as expected. However, here are some other potential solutions ot the issue:

1. **Use `approveHash` Before Executing the Transaction:**
Before calling `execTransaction`, the protocol should invoke `approveHash` on the Safe contract to pre-approve the `dataHash`. This ensures that the `approvedHashes` check inside `checkSignatures` passes correctly. The approved data hash will be unique, and it should be constructed as it is done in the `Safe::execTransaction` function.

```solidity
Safe(payable(walletInstance.safe)).approveHash(hashToApprove)
require(Safe(payable(walletInstance.safe)).execTransaction(
    ...
```

2. **Switch to Contract Signatures (`v == 0` Case):**
Alternatively, the protocol can consider using contract signatures (`v == 0`). This approach is suitable for contract-driven transactions and avoids the complexity of using the approved hash mechanism.
