# Vulnerability details

Timelock contract has a vulnerability that allows executed operations to be cancelled. This undermines the core functionality of the timelock mechanism and can lead to unexpected state changes in the system.

## Proof of Concept
1. Schedule an operation
2. Execute the operation
3. Call cancel on the executed operation ID

The cancel function will succeed, violating the intended behavior.

Because the `cancel` function only checks if the operation exists and is in the `_liveProposals` set. It does not verify whether the operation has already been executed. This oversight allows executed operations to be cancelled, violating the intended invariant that executed operations should be final.

The reason is that in the `cancel` function, we only check `isOperation(id) && _liveProposals.remove(id)`. Note that an executed operation still satisfies `isOperation(id)` because its timestamp is set to `_DONE_TIMESTAMP` (which is 1) instead of 0. The `_liveProposals` set is not cleared upon execution, allowing the cancellation to proceed. [Timelock.sol#L657-L665](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L657-L665)
```solidity
function cancel(bytes32 id) external onlySafe whenNotPaused {
    require( // =>
        isOperation(id) && _liveProposals.remove(id),
        "Timelock: operation does not exist"

    delete timestamps[id];
    emit Cancelled(id);

function cancel(bytes32 id) external onlySafe whenNotPaused {
    require( // =>
        isOperation(id) && _liveProposals.remove(id),
        "Timelock: operation does not exist"
    ); // <= FOUND

    delete timestamps[id];
    emit Cancelled(id);
}

function isOperation(bytes32 id) public view returns (bool) {
    return timestamps[id] > 0;
}

function isOperationDone(bytes32 id) public view returns (bool) {
    return timestamps[id] == _DONE_TIMESTAMP;
}
```
To reproduce and validate

1. Call `timelock.schedule(target, value, data, salt, delay)` to schedule an operation.
2. Wait for the delay period.
3. Call `timelock.execute(target, value, data, salt)` to execute the operation.
4. Call `timelock.cancel(operationId)` with the same operation ID.
5. Observe that the cancel function succeeds, even though the operation was already executed.

## Recommended Mitigation Steps
Modify the cancel function to include a check for executed operations to ensures that executed operations cannot be canceled, aligning with the intended behavior
```diff
function cancel(bytes32 id) external onlySafe whenNotPaused {
    require(
-       isOperation(id) && _liveProposals.remove(id),
+       isOperation(id) && !isOperationDone(id) && _liveProposals.remove(id),
        "Timelock: operation does not exist or is already executed"
    );

    delete timestamps[id];
    emit Cancelled(id);
}
```
Consider clearing the `_liveProposals` set when an operation is executed to maintain consistency
```diff
function _afterCall(bytes32 id) private {
    require(isOperationReady(id), "Timelock: operation is not ready");
    timestamps[id] = _DONE_TIMESTAMP;
+   _liveProposals.remove(id);
}
```
