# Vulnerability details

## Proof of Concept

For context, there is a self destruct vulnerability in the following code snippet: 

```solidity

timelock = address(
            new Timelock{
                salt: keccak256(abi.encodePacked(params.salt, msg.sender))
            }(
                safe,
                params.minDelay,
                params.expirationPeriod,
                params.pauser,
                params.pauseDuration,
                params.hotSigners
            )
        );
```

The `new Timelock(...)` construct creates a new instance of the `Timelock` contract and assigns its address to the `timelock` variable.  

If the `Timelock` contract contains a self-destruct function that can be called without proper authorization or safeguards, an attacker could potentially exploit this vulnerability by manipulating the input parameters to trigger the self-destruction of the newly created timelock contract. This would result in the loss of funds and control over the associated assets.

Ok, so the createTimelock function is *external*, meaning it can be called by any user, without specific access control restrictions in the function itself. This means anyone can call it and potentially create a Timelock under malicious parameters, assuming there are no other restrictions placed outside of this function in the contract system.

Also, there is no (currently) explicit access-based control, so there are No limitations on who can call the createTimelock function at every factory level.  While it is true that certain timelock actions are governed by roles like HOT_SIGNER_ROLE for execution purposes, these constraints do not restrict the initial creation of a Timelock.

Here are some exploit paths:
 
--> Since the createTimelock function is external and lacks any access control, any user could theoretically deploy a new Timelock contract with parameters of their choosing. This opens the door for malicious parameter inputs, such as reduced minDelay or incorrect safe addresses.

--> [this is more of the scorched earth method] Second way is through/if the malicious actor could potentially destroy the contract after its creation, disrupting governance and fund management processes.

## Recommended Mitigation Steps
Here are some mitigations I'd recommend:

->Implement access controls. Have devs ensure that the createTimelock function has proper access control by restricting who can call it. For instance, only specific roles or multisig owners should be able to create new Timelock contracts.  One example of how to do this: 

```solidity
modifier onlyAuthorized() {
    require(hasRole(CREATOR_ROLE, msg.sender), "Not authorized");
    _;
}

function createTimelock(address safe, DeploymentParams memory params) external onlyAuthorized returns (address timelock) {
    // this is the existing implementation
}

```

--> harden the self destruct mechanisms.  Make sure devs ensure that it is fully protected by robust authorization checks, such as ensuring only the owner or trusted entities can trigger self-destruct in highly controlled circumstances. 

--> salt management needs to be not easily manipulatable.   Have devs ensure that the salt used in keccak256(abi.encodePacked(params.salt, msg.sender)) is not easily manipulable. The current approach uses msg.sender, but the salt should be generated more securely to prevent collisions or malicious contract creations.
