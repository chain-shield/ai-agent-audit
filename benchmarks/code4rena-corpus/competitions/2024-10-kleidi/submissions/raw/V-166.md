# Vulnerability details

#### hash collisions of dynamic types 
summary
hash collision most likely will occur because `abi.encodePacked()` is used with hashing operations of `keccak256()` in  create2helper.sol
hash collisions are bound to occur because the parameters passed in `function calculateCreate2Address` for abi-encoding `creationCode, constructorParams` are both dynamic types. same issue with function `calculateCreate2Address`

In solidity documentation it is advised against to use abi.encodePacked with dynamic parameters

https://docs.soliditylang.org/en/v0.8.28/abi-spec.html#non-standard-packed-mode

### Proof of Concept
implications
-An attacker, Eve, crafts parameters to reproduce produce the inner hash.
-Eve runs guessing nodes to get to break the salt value of the outer hashing mechanism to get the deterministic address.
while running nodes to break the salt can be capitally expensive, but a hacker with the realization of funds at stake may be motivated to do it.

- Eve monitors the mempool for a large monetary deposit transaction .

- Eve quickly deploys and ovewrites the existing code with a malicious contract at the same address, front-running deposits and stealing funds.

## Recommended Mitigation Steps
-Use `abi.encode()` instead which will pad items to 32 bytes, so as to prevent hash collisions

-unless absolutely neccesary to use `abi.encodepacked()`;
1. use `bytes.concat()` to concatenate the dynamic bytes before the encoding the inner hash
2. use a very unique salt value
