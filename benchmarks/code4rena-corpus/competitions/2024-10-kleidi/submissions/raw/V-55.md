# Vulnerability details

`executeBatch` function makes external calls within a loop before updating the contract's state, violating the checks-effects-interactions pattern.

After calling `executeBatch`, the `totalOperations` value doesn't decrease as expected. This indicates that the function's vulnerable to reentrancy attacks, allowing multiple executions of the same operation.

Here's the bug: [function executeBatch](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L626-L650)
```solidity
function executeBatch(
    address[] calldata targets,
    uint256[] calldata values,
    bytes[] calldata payloads,
    bytes32 salt
) external payable whenNotPaused {
    // ...

    // @Audit: Reentrancy vulnerability starts here
    for (uint256 i = 0; i < targets.length; i++) {
        bytes calldata payload = payloads[i];

        _execute(targets[i], values[i], payload);
        emit CallExecuted(id, i, targets[i], values[i], payload);
    }
    // @Audit: Reentrancy vulnerability ends here

    _afterCall(id);
}
```

3. The `timestamps` mapping, which is updated in `_afterCall` to mark the operation as executed.

The combination of these factors creates a window where the contract's state is inconsistent, allowing for potential reentrancy attacks.

## Proof of Concept
The `executeBatch` function removes the proposal from `_liveProposals` at the beginning of the function, but doesn't update other critical state variables until after all external calls are made. This creates a window where an attacker can re-enter the function and execute the same proposal multiple times.

In `executeBatch`, we see:
```solidity
require(_liveProposals.remove(id), "Timelock: proposal does not exist");
// ... external calls are made here ...
_afterCall(id);
```
The `_afterCall` function, which updates the `timestamps` mapping to mark the operation as executed, is called only after all external calls have been made. This allows for potential reentrancy between the removal of the proposal and its final state update.

Attack scenario illustrating the vulnerability

1. Alice schedules a batch operation that includes a call to a malicious contract controlled by Bob.
2. Alice calls `executeBatch` to execute the scheduled operation.
3. The Timelock contract removes the proposal from `_liveProposals`.
4. During execution, the Timelock calls Bob's malicious contract.
5. Bob's contract calls back into `executeBatch` with the same parameters.
6. The second `executeBatch` call passes the initial checks because the proposal is no longer in `_liveProposals`.
7. The operation is executed again, potentially draining funds or manipulating the contract's state.

## Recommended Mitigation Steps
1. Implement a reentrancy guard in the executeBatch function.
```diff
+ bool private _executing;

function executeBatch(
    address[] calldata targets,
    uint256[] calldata values,
    bytes[] calldata payloads,
    bytes32 salt
) external payable whenNotPaused {
+   require(!_executing, "Reentrancy not allowed");
+   _executing = true;

    // ... 

+   _executing = false;
}
```
3. Use the "checks-effects-interactions" pattern:

   * Check conditions
   * Update state variables
   * Perform external calls last
