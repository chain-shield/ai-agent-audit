# Vulnerability details

When the Timelock.sol contract is paused, it fails to clear all active operations, allowing some operations to remain executable even after pausing.

The issue is because the `pause()` function only clears operations from the `_liveProposals` set, but doesn't fully clear the timestamps mapping. The `isOperation()` function, which determines if an operation is valid, checks the timestamps mapping rather than the `_liveProposals` set. This mismatch allows for operations to remain valid even after pausing.

Specifically, in the `pause()` function, we only iterate through and clear the `_liveProposals`: [Timelock.sol#691-L699](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L691-L699)
```solidity
bytes32[] memory proposals = _liveProposals.values();
for (uint256 i = 0; i < proposals.length; i++) {
    bytes32 id = proposals[i];
    delete timestamps[id];
    assert(_liveProposals.remove(id));
    emit Cancelled(id);
}
```
However, the `isOperation()` function checks the `timestamps` mapping: [Timelock.sol#L392-L394](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L392-L394)
```solidty
function isOperation(bytes32 id) public view returns (bool) {
    return timestamps[id] > 0;
}
```
> The root cause is the mismatch between how operations are tracked and how they're cleared during pausing. The `isOperation()` function checks the timestamps mapping, while the `pause()` function only clears entries from the `_liveProposals` set.

## Proof of Concept
Consider the following sequence

1. Alice schedules an operation through the Timelock contract using the `schedule()` function.
2. The operation becomes ready for execution after the delay period.
3. Bob executes the operation using the `execute()` function, which removes it from `_liveProposals` but keeps its entry in `timestamps`.
4. An emergency occurs, and the contract owner calls `pause()`.
5. Despite the contract being paused, Alice can still execute the operation because `isOperation()` returns true for that operation's ID.

We can see how the pause mechanism fails to provide complete protection in emergency situations.

```solidity
function pause() public override {
    /// check that msg.sender is the pause guardian, pause the contract
    super.pause();

    bytes32[] memory proposals = _liveProposals.values();
    for (uint256 i = 0; i < proposals.length; i++) {
        bytes32 id = proposals[i];

        delete timestamps[id];
        assert(_liveProposals.remove(id));

        emit Cancelled(id);
    }
} // <= FOUND

function isOperation(bytes32 id) public view returns (bool) {
    return timestamps[id] > 0; // <= FOUND
}
```
To validate the issue

1. Call `schedule(target, value, data, salt, delay)` to schedule an operation
2. Wait for the operation to become executable (delay period passes)
3. Call `execute(target, value, payload, salt)` to execute the operation
4. Call `pause()`
5. Check `isOperation(operationId)` - it will return true, despite the contract being paused

## Recommended Mitigation Steps
The `pause()` function should clear all entries from the timestamps mapping, not just those in `_liveProposals`. A possible fix
```diff

    super.pause();

    bytes32[] memory proposals = _liveProposals.values();

        bytes32 id = proposals[i];
        delete timestamps[id];
        assert(_liveProposals.remove(id));
        emit Cancelled(id);
    }
```
