# Vulnerability Details

## Impact

When a transaction by the safe is made, it is checked by `checkTransaction()` in `Guard.sol` that it is no self or delegate call so that no new modules, upgrades, owners or fallback handlers can be added or removed by the transaction.

It only allows self or delegate calls if the calldata is empty.

However, compromised signers of the safe could still make the safe call itself with non-empty calldata by using `Safe.handlePayment()`.

This means the invariant that the safe can only call itself with empty calldata is broken.

If the safe is configured in such a way that its security relies on that invariant (for example with fallback handler) then it is possible that an attack can be performed.

## Proof of Concept

1. The compromised signers make a transaction using `execTransaction()`.

2. They provide the address of the safe as the `gasToken`.

3. The guard will not revert the transaction, because it is not called when `handlePayment()` is executed.

4. `fallback()` will be called, which causes the fallback handler to be called when it is configured.

5. An attack could be performed due to the broken invariant.

## Recommended Mitigation Steps

Consider adding a check in `Guard.sol` that the `gasToken` is not the safe.
