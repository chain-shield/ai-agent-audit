# Vulnerability details

Timelock contract's `execute` function is vulnerable to reentrancy attacks. An attacker could execute the same operation multiple times before the operation's status is updated, leading to consequences such as draining funds or causing unexpected state changes in the target contract.

Because the external call to the target contract is made before updating the operation's status. _This violates the checks-effects-interactions pattern, which is crucial for preventing reentrancy attacks._

Scenario

1. An attacker schedules an operation in the Timelock that calls a malicious contract.
2. When the operation becomes ready, the attacker calls `Timelock.execute()`.
3. The `execute` function removes the operation from `_liveProposals` and checks if it's ready.
4. The function then calls the malicious contract via `_execute(target, value, payload)`.
5. The malicious contract's fallback function calls `Timelock.execute()` again with the same parameters.
6. This second call passes all checks because the operation status hasn't been updated yet.
7. The operation executes again, potentially causing unintended consequences.

## Proof of Concept
[Timelock.sol:execute](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L589-L609)
```solidity
function execute(
    address target,
    uint256 value,
    bytes calldata payload,
    bytes32 salt
) external payable whenNotPaused {
    bytes32 id = hashOperation(target, value, payload, salt);

    require(_liveProposals.remove(id), "Timelock: proposal does not exist");
    require(isOperationReady(id), "Timelock: operation is not ready");

    _execute(target, value, payload); // <= FOUND
    emit CallExecuted(id, 0, target, value, payload);

    _afterCall(id);
}
```
One could create a malicious contract with a fallback function that calls `Timelock.execute()` with the same parameters. When this contract is the target of a Timelock operation, it can trigger multiple executions of the same operation.

This is caused by not following the checks-effects-interactions pattern. The contract state is not updated before making an external call, which opens up the possibility of reentrancy.

## Recommended Mitigation Steps
Implement the checks-effects-interactions pattern in the `execute` function. Update the operation's status before making the external call.
```diff
function execute(
    address target,
    uint256 value,
    bytes calldata payload,
    bytes32 salt
) external payable whenNotPaused {
    bytes32 id = hashOperation(target, value, payload, salt);

    require(_liveProposals.remove(id), "Timelock: proposal does not exist");
    require(isOperationReady(id), "Timelock: operation is not ready");

+   timestamps[id] = _DONE_TIMESTAMP;

    _execute(target, value, payload);
    emit CallExecuted(id, 0, target, value, payload);

-   _afterCall(id);
}
```
