# Vulnerability details

## Proof of Concept
The issue is in the validation of the Safe address when creating a RecoverySpell. The code checks whether the Safe address exists by using safe.code.length != 0. While this might seem like a reasonable check, it doesn’t account for scenarios where the Safe contract has been destroyed or replaced, which could lead to the deployment of a RecoverySpell associated with an invalid or non-existent Safe.

vulnerable code in RecoverySpellFactory.sol:

```
require(safe.code.length != 0, "RecoverySpell: safe non-existent");
```
This line assumes that if the Safe contract has non-zero bytecode, it is valid, but this check can fail in certain edge cases, such as when the Safe has been destroyed or replaced.

Details:

The createRecoverySpell function uses the check safe.code.length != 0 to determine if the Safe contract exists. However, this check doesn’t handle situations where the Safe contract may have been destroyed (using the selfdestruct function), temporarily replaced, or is otherwise invalid.

If a RecoverySpell is created for a Safe that no longer exists, the recovery process will fail when it tries to interact with the Safe. This can cause broken recovery flows and result in a denial of service for legitimate users attempting to recover their Safe.


An attacker could intentionally destroy or replace the Safe contract, making it unavailable for interaction.
Despite the Safe being destroyed, the RecoverySpellFactory would still allow the creation of a RecoverySpell because the safe.code.length != 0 check only verifies the presence of bytecode at the time of creation.
The user might assume their recovery process is functioning correctly, but it would be bound to a non-existent Safe, leading to a failed recovery.


An attacker can submit a Safe address that has been destroyed to the RecoverySpellFactory contract. The factory will still create a recovery spell for the destroyed Safe, which will later fail when attempting to interact with the Safe.

Steps to Reproduce:

Deploy a Safe contract.
Destroy the Safe using selfdestruct().
Create a RecoverySpell using the destroyed Safe address in the RecoverySpellFactory.
Observe that the contract still allows the creation of the recovery spell, even though the Safe no longer exists.

PoC:

```
pragma solidity ^0.8.25;

contract Safe {
    // A simple Safe contract that can self-destruct
    function destroySafe() external {
        selfdestruct(payable(msg.sender));
    }
}

contract TestSafeDestruction {
    RecoverySpellFactory recoverySpellFactory;

    constructor(address _recoverySpellFactory) {
        recoverySpellFactory = RecoverySpellFactory(_recoverySpellFactory);
    }

    // This function creates a recovery spell with a destroyed Safe
    function createWithDestroyedSafe(
        bytes32 salt,
        address[] memory owners,
        address safe,
        uint256 threshold,
        uint256 recoveryThreshold,
        uint256 delay
    ) external {
        // Assume the Safe at address `safe` was destroyed
        recoverySpellFactory.createRecoverySpell(salt, owners, safe, threshold, recoveryThreshold, delay);
    }
}
```
The RecoverySpell is created, even though the Safe contract has been destroyed, leading to an invalid recovery process.
The contract should detect that the Safe no longer exists and reject the creation of a RecoverySpell linked to a destroyed or invalid Safe.

Invalid Recovery Process: Once the Safe has been destroyed, the RecoverySpell will be created for a non-existent or invalid Safe, resulting in a broken recovery process. This could lead to the inability to recover funds.
Denial of Service: If this vulnerability is exploited, it could prevent legitimate users from recovering their Safe by linking the recovery spell to an invalid or destroyed Safe address.



## Recommended Mitigation Steps
Implement stronger checks for the Safe's existence, such as checking that the Safe has not been destroyed or that it is a valid contract instance at the time of RecoverySpell creation.

One potential solution could be to ensure that the Safe's address not only contains bytecode but is also still valid and functional:

```
require(safe != address(0) && safe.code.length != 0, "RecoverySpell: Invalid or non-existent Safe");
```
Additionally, it may be worth considering stronger checks that ensure the Safe has not been destroyed or is still operational.

ensure that users are informed if the Safe address they are attempting to recover is invalid or has been destroyed, helping prevent confusion during the recovery process.
