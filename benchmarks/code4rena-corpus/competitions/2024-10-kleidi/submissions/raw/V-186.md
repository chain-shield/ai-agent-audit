# Vulnerability details

When cancelling an operation

1. The proposal is removed from `_liveProposals`
2. `timestamps[id]` is deleted (set to 0)
3. A subsequent execution could still pass the `isOperationReady()` check if the timestamps and expiration period align correctly

The vulnerability stems from improper invalidation of cancelled operations. When an operation is cancelled, its timestamp is set to 0 using `delete`. However, the `isOperationReady()` check can still pass with a timestamp of 0 due to how the arithmetic conditions are structured, allowing cancelled operations to be re-executed if timed correctly.

The issue occurs in the following sequence

1. Safe schedules an operation, setting:

   * `timestamps[id]` = future timestamp
   * `_liveProposals` contains operation id

2. Safe cancels the operation:

   * Removes from `_liveProposals`
   * Sets timestamps[id] to 0 via delete

3. Attacker executes cancelled operation:

   * If `block.timestamp < expirationPeriod`
   * `isOperationReady()` passes despite cancellation
   * Operation executes successfully

function cancel(bytes32 id) external onlySafe whenNotPaused {
    require(
        isOperation(id) && _liveProposals.remove(id),
        "Timelock: operation does not exist"
    );

    delete timestamps[id]; // <@audit Sets to 0 instead of invalidating // Using delete sets to 0 which can pass isOperationReady() check
    emit Cancelled(id);
}

function isOperationReady(bytes32 id) public view returns (bool) {
    uint256 timestamp = timestamps[id];
    return timestamp > _DONE_TIMESTAMP && timestamp <= block.timestamp // <@audit: Can pass with timestamp 0 // Cancelled ops with timestamp 0 can pass this check
        && timestamp + expirationPeriod > block.timestamp;
}

function execute(
    address target,
    uint256 value,
    bytes calldata payload,
    bytes32 salt
) external payable whenNotPaused {
    bytes32 id = hashOperation(target, value, payload, salt);

    require(_liveProposals.remove(id), "Timelock: proposal does not exist"); // <@audit First check
    require(isOperationReady(id), "Timelock: operation is not ready"); // <@audit Second check can pass for cancelled ops

    _execute(target, value, payload);
    emit CallExecuted(id, 0, target, value, payload);

    _afterCall(id);
}

## Proof of Concept
**Alice (Safe Owner)**
1. Schedules operation X to execute in 2 days
2. Later decides to cancel operation X
3. Calls `cancel(X)`

**Bob (Attacker)**
1. Waits for optimal timing where `block.timestamp < expirationPeriod`
2. Executes cancelled operation X successfully
3. Operation executes despite Safe's cancellation

The root cause is because the `cancel()` function uses `delete` which sets `timestamps[id]` to 0 rather than properly invalidating it. This interacts badly with `isOperationReady()` checks in the execution path.

```
1. Initial setup:
- Safe schedules operation with id X
- timestamp[X] = block.timestamp + delay
- _liveProposals contains X

2. Cancellation:
- Safe calls cancel(X)
- _liveProposals removes X
- timestamp[X] = 0 (due to delete)

3. Execution:
- Attacker waits for block.timestamp < expirationPeriod
- Calls execute() with same parameters
- isOperationReady() passes because:
  - 0 > 1 (false) BUT
  - 0 <= block.timestamp (true) AND
  - 0 + expirationPeriod > block.timestamp (true)
- Operation executes despite cancellation
```
The vulnerability connects

* `cancel()` → `timestamps` storage → `isOperationReady()` → `execute()`
* Missing test coverage in `testCancelActiveProposalSafeSucceeds()`

This creates a complete path for the vulnerability to manifest.

## Recommended Mitigation Steps
```diff
function cancel(bytes32 id) external onlySafe whenNotPaused {
    require(
        isOperation(id) && _liveProposals.remove(id),
        "Timelock: operation does not exist"
    );
-   delete timestamps[id];
+   timestamps[id] = _DONE_TIMESTAMP; // Use sentinel value that fails isOperationReady
    emit Cancelled(id);
}
```
