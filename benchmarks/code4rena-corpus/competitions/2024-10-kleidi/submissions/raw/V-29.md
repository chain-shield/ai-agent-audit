# Vulnerability details

### Proof of Concept

Kleidi Wallet is used to create a full self-custody wallet system for DeFi users and is designed to be used with Gnosis Safe multisigs. This requires that users with different safe versions be able to create a wallet in the spirit of compatibility. The wallet uses a guard contract which restrict the the multisig by disallowing delegate and self calls. This current guard's implementation however doesn't account for users with safe versions 1.5+ and as a result, users with these safe types will have compatibility issues.

For a user to create a wallet, he first has to deploy a timelock with his safe.

```solidity
    function createTimelock(address safe, DeploymentParams memory params)
        external
        returns (address timelock)
    {
        timelock = address(
            new Timelock{
                salt: keccak256(abi.encodePacked(params.salt, msg.sender))
            }(
                safe,
                params.minDelay,
                params.expirationPeriod,
                params.pauser,
                params.pauseDuration,
                params.hotSigners
            )
        );

        emit TimelockCreated(timelock, block.timestamp, msg.sender);
    }
```

After the timelock is successfully deployed, the user can finally initialize the wallet using the `createSystemInstance` function in InstanceDeployr. 
The function works fine until its time to set the guard.

```solidity
    function createSystemInstance(NewInstance memory instance)
        external
        returns (SystemInstance memory walletInstance)
    {
// ...

            calls3[index++].callData =
                abi.encodeWithSelector(GuardManager.setGuard.selector, guard);
// ...
```
The `setGuard` selector is called on the user's safe's GuardManager, trying to add the `guard`. 

The `setGuard function in the GuardManager, version 1.5+ looks like this. It attempts to check the guard contract to ensure that the supportsInterface matches.

```solidity
    function setGuard(address guard) external authorized {
        if (guard != address(0)) {
            require(Guard(guard).supportsInterface(type(Guard).interfaceId), "GS300");
        }
        bytes32 slot = GUARD_STORAGE_SLOT;
        /* solhint-disable no-inline-assembly */
        /// @solidity memory-safe-assembly
        assembly {
            sstore(slot, guard)
        }
        /* solhint-enable no-inline-assembly */
        emit ChangedGuard(guard);
    }

```

The expected Guard `supportsInterface` in the user's safe looks like this. 

```solidity
abstract contract BaseGuard is Guard {
    function supportsInterface(bytes4 interfaceId) external view virtual override returns (bool) {
        return
>>>         interfaceId == type(Guard).interfaceId || // 0x945b8148
            interfaceId == type(IERC165).interfaceId; // 0x01ffc9a7
    }
}
```

Whereas kleidi's Guard.sol's supportsInterface base on safe [1.4 version](https://github.com/safe-global/safe-smart-account/blob/bf943f80fec5ac647159d26161446ac5d716a294/contracts/base/GuardManager.sol) looks like this, notice the difference in interafceIds. 
```solidity 
abstract contract BaseGuard is Guard {
    function supportsInterface(bytes4 interfaceId) external view virtual override returns (bool) {
        return
>>>         interfaceId == type(Guard).interfaceId || // 0xe6d7a83a
            interfaceId == type(IERC165).interfaceId; // 0x01ffc9a7
    }
}
```

This is because safes 1.5+ Guard's interfaceId also incorporates the ModuleGuard into its Id. As can be seen from the [interface](https://github.com/safe-global/safe-smart-account/blob/810fad9a074837e1247ca24ac9e7f77a5dffce19/contracts/base/GuardManager.sol#L46-L52), the `checkModuleTransaction` function is also introduced which checks the module transaction details.

```solidity
    function checkModuleTransaction(
        address to,
        uint256 value,
        bytes memory data,
        Enum.Operation operation,
        address module
    ) external returns (bytes32 moduleTxHash);
```

Kleidi's own Guard lacks this function, hence, the different interfaceId to version 1.5+. As a result, users which these safe version types, will not be able to add Kleidi's guard to Kleidi wallets causing that the wallet creation will be impossible.
 
### Recommended Mitigation Steps

Recommend overriding the Guard's interface and `supportsInterface`, and adding expected Id of 0x945b8148 too.
For instance: 

```solidity 
abstract contract BaseGuard is Guard {
    function supportsInterface(bytes4 interfaceId) external view virtual override returns (bool) {
        return
            interfaceId == 0xe6d7a83a || 
            interfaceId == 0x945b8148 || 
            interfaceId == 0x01ffc9a7; 
    }
}
```

This provides backwards compatibility for all safe versions from < 1.3 to 1.5+
