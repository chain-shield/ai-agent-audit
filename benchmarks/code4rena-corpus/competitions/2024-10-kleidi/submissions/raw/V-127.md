# Vulnerability details

## Proof of Concept
The [`_addCalldataCheck`](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L1089-L1130) function cointains an issue related to array index management when adding new calldata checks.
The relevant code is
```solidity
Index[] storage indexes = _calldataList[contractAddress][selector];
uint256 targetIndex = indexes.length;
{
    bool found;
    for (uint256 i = 0; i < indexes.length; i++) {
        // ... SNIP ...
    }

    if (!found) {
        indexes.push();
        indexes[targetIndex].startIndex = startIndex;
        indexes[targetIndex].endIndex = endIndex;
    }
}
```
Vulnerability arise from the following sequence

1. Initial Setting: `targetIndex` is initially set to `indexes.length`. This is intended to be the position where a new index would be added if no matching index is found.

2. Pushing New Element: If no matching index is found, `indexes.push()` is called, which increases the length of the indexes array by one.

3. Accessing Out of Bounds: After pushing, indexes[`targetIndex`] is accessed. Since `targetIndex` was set to `indexes.length` before the push, it now points to an out-of-bounds index after the push.


## Recommended Mitigation Steps
Modify the code as follows
```diff
    Index[] storage indexes = _calldataList[contractAddress][selector];
    uint256 targetIndex = indexes.length;
    {
        bool found;
        for (uint256 i = 0; i < indexes.length; i++) {
            if (indexes[i].startIndex == startIndex && indexes[i].endIndex == endIndex) {
                targetIndex = i;
                found = true;
                break;
         }
        // ... SNIP ...
        }

        if (!found) {
+           targetIndex = indexes.length-1;
            indexes.push();
            indexes[targetIndex].startIndex = startIndex;
            indexes[targetIndex].endIndex = endIndex;
        }
    }
```
