# Vulnerability details

From the order of operations in the `execute` function, where an external call is made before the contract's state is updated to reflect the completion of the operation. This violates the checks-effects-interactions pattern, creating a window for reentrancy attacks because the `_execute` function, which makes an external call, is invoked before the contract's state is fully updated via the `_afterCall` function. This order of operations allows a malicious contract to reenter the execute function before the original operation is marked as completed.

For example, in the `execute` function

1. The operation is removed from `_liveProposals`.
2. An external call is made via `_execute`.
3. Only after the external call, `_afterCall` is invoked to update the operation's status.

This sequence creates a window where the same operation can be re-executed multiple times.

## Proof of Concept
A malicious contract could exploit this by:

1. Initiating a valid `timelock` operation.
2. In the fallback function of the target contract, calling back into the Timelock contract's `execute` function.
3. This could lead to multiple executions of the same operation before the state is properly updated.

[Timelock.sol:function execute](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L589-L609)
```solidity
function execute(
    address target,
    uint256 value,
    bytes calldata payload,
    bytes32 salt
) external payable whenNotPaused {
    bytes32 id = hashOperation(target, value, payload, salt);

    require(_liveProposals.remove(id), "Timelock: proposal does not exist");
    require(isOperationReady(id), "Timelock: operation is not ready");

    // @Audit: Reentrancy vulnerability - external call before state update
    _execute(target, value, payload);
    emit CallExecuted(id, 0, target, value, payload);

    _afterCall(id);
}
```
Attack scenario:

1. Attacker creates a malicious contract with a fallback function that calls `Timelock.execute()`.
2. Attacker schedules a legitimate operation through the Timelock.
3. When the operation is ready, attacker calls `Timelock.execute()`.
4. Inside `_execute()`, the malicious contract is called, triggering its fallback function.
5. The fallback function calls `Timelock.execute()` again with the same parameters.
6. This creates a loop where the same operation is executed multiple times before `_afterCall()` is reached.
7. Each execution could transfer funds or make state changes, multiplying the intended effect.

## Recommended Mitigation Steps
Consider the following recommendations

* Implement a reentrancy guard using a mutex pattern
```diff
+ bool private _locked;
+
+ modifier nonReentrant() {
+     require(!_locked, "Reentrant call");
+     _locked = true;
+     _;
+     _locked = false;
+ }

- function execute(address target, uint256 value, bytes calldata payload, bytes32 salt) external payable whenNotPaused {
+ function execute(address target, uint256 value, bytes calldata payload, bytes32 salt) external payable nonReentrant whenNotPaused {
    // Update state first
    require(_liveProposals.remove(id), "Timelock: proposal does not exist");
    require(isOperationReady(id), "Timelock: operation is not ready");
    
    // Then make the external call
    _execute(target, value, payload);
    
    emit CallExecuted(id, 0, target, value, payload);
    _afterCall(id);
}
```
* Update the contract's state before making the external call
```diff
function execute(address target, uint256 value, bytes calldata payload, bytes32 salt) external payable nonReentrant whenNotPaused {
    bytes32 id = hashOperation(target, value, payload, salt);

    require(_liveProposals.remove(id), "Timelock: proposal does not exist");
    require(isOperationReady(id), "Timelock: operation is not ready");

+   _afterCall(id);

    _execute(target, value, payload);
    emit CallExecuted(id, 0, target, value, payload);

-   _afterCall(id);
}
```
