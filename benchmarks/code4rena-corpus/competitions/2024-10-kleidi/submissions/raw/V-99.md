# Vulnerability details

The `updateDelay` function in the Timelock contract allows setting the `minDelay` to the same value as the current `minDelay` without reverting. This violates the expected behavior that updating the delay should only work if providing a different value.

[updateDelay#L960-L967](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L960-L968)
```solidity
// @Issue - Missing check that newDelay is different from current minDelay
function updateDelay(uint256 newDelay) external onlyTimelock {
    require(
        newDelay >= MIN_DELAY && newDelay <= MAX_DELAY,
        "Timelock: delay out of bounds"
    );

    emit MinDelayChange(minDelay, newDelay);
    minDelay = newDelay;
}
```
The function checks if the `newDelay` is within the allowed `MIN_DELAY` and `MAX_DELAY` range but does not verify that `newDelay` is different from the current `minDelay` value.

## Proof of Concept
1. Assume the `Timelock` contract is deployed with an initial `minDelay` value of 1 day.
2. The timelock itself calls `updateDelay(1 days)` to update the delay. This call succeeds since 1 day is within the allowed range.
3. Later, the timelock accidentally calls `updateDelay(1 days)` again, intending to update the delay but providing the same value.
4. The second call to `updateDelay` does not revert, even though the delay is the same as the current value.

This behavior is unexpected and could lead to confusion for users interacting with the timelock. They might assume that calling `updateDelay` with the same value would revert, but it silently succeeds without any effect.

test case
```solidity
function testUpdateDelayWithSameValueShouldRevert() public {
    uint256 initialDelay = timelock.minDelay();

    vm.prank(address(timelock));
    timelock.updateDelay(initialDelay);

    // The following call should revert but doesn't
    vm.prank(address(timelock));
    timelock.updateDelay(initialDelay);
}
```
In this test

1. We get the initial `minDelay` value from the `Timelock` contract.
2. We call `updateDelay` with the same `initialDelay` value from the timelock itself.
3. We expect the second call to `updateDelay` to revert since the delay is the same as the current value, but it doesn't.

## Recommended Mitigation Steps
Add a check in the `updateDelay` function to ensure that the `newDelay` is different from the current `minDelay` value
