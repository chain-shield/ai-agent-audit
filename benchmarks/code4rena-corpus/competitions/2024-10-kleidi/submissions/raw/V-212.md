# Vulnerability details

## Impact

The `deploy` function in the `SystemDeploy` contract lacks the `payable` modifier, preventing it from receiving native tokens (Ether) during contract creation. This is critical if any of the deployed contracts require Ether in their constructors. Without the ability to receive Ether, the deployment will fail when contracts attempt to access the funds needed for their initialization logic, resulting in potential system failures and inability to properly deploy essential components like the `TimelockFactory` or `Guard`.

### Vulnerability Explanation

The `SystemDeploy` contract is responsible for deploying multiple factory and utility contracts, including `TimelockFactory`, `Guard`, and `RecoverySpellFactory`. The relevant section of the `SystemDeploy` contract is as follows:

```solidity
function deploy() public override {
    if (!addresses.isAddressSet("TIMELOCK_FACTORY")) {
        TimelockFactory factory = new TimelockFactory{salt: salt}();
        addresses.addAddress("TIMELOCK_FACTORY", address(factory), true);
    }
    // ... (similar instantiation for other contracts)
}
```

Although the `CREATE2` opcode is not explicitly called, the instantiation of contracts using the `new` keyword can lead to scenarios where the underlying `CREATE` or `CREATE2` opcodes are invoked, especially if the constructors of these deployed contracts are designed to accept Ether.

If any of the constructors for these deployed contracts require Ether to be successfully executed, the lack of a `payable` modifier in the `deploy` function will cause the transaction to revert. This leads to an inability to deploy critical components, thereby affecting the overall functionality of the system.

## Recommended Mitigation Steps

**Add Payable Modifier**: Modify the `deploy` function in the `SystemDeploy` contract to include the `payable` modifier:

```solidity
function deploy() public override payable {
    // deployment logic...
}
```
