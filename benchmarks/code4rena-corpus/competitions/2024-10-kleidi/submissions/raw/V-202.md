# Vulnerability Details

## Impact

When a hot signer calls `executeWHitelisted()` or `executeWhitelistedBatch()` to execute a call to whitelisted contracts with whitelisted calldatas, he can provide one or more `values`, depending on which of the said functions he calls.

The `value` will be sent to the provided `target`, if `checkCalldata()` does not revert.

However, there is no validation that checks the amount of funds he provided.
This means that any hot signer can call this function and send any amount to a whitelisted contract and therefore drain the contract, as the timelock is the address that holds all funds.

The risk is definitely real, as the functions are payable and therefore suggest that it is intended use to have targets and selectors that allow `msg.value` to be passed.

Furtermore, `Timelock.sol` has a `receive()` function, which means that it is expected to receive and hold native funds.

## Proof of Concept

1. The calls that can be made by calling `executeWHitelisted()` or `executeWhitelistedBatch()` first need to be whitelisted. 

2. This can be done either when the system instance is created when `createSystemInstance()` in `InstanceDeployer.sol` gets called or when the timelock calls `addCalldataCheck()` or `addCalldataChecks()` in `Timelock.sol`, which can be done when a proposal that has been scheduled by the safe is executed.

3. Any hot signer can call `executeWhitelisted()` or `executeWhitelistedBatch()` to execute any of those whitelisted calls with any `value`.

4. This could be done anytime by any hot signer with any `value` until the contract has been drained.


## Recommended Mitigation Steps

For each (contract,selector) pair the maximum amount should also be whitelisted.

An alternative solution, if the timelock is not expected to hold ETH, is to not allow `executeWhitelisted()` and `executeWhitelistedBatch()` to access any funds in excess of `msg.value` that has been provided by the hot signer.
