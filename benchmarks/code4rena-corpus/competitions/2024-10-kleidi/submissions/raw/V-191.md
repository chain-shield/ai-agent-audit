# Vulnerability details

Whitelisted execution mechanism allows multiple hot signers to execute the same transaction, creating opportunities for MEV extraction through transaction ordering manipulation, occurs because `executeWhitelisted()` provides no ordering guarantees between different hot signers executing the same whitelisted transaction. When multiple hot signers attempt to execute identical transactions in the same block, their ordering can be manipulated by MEV bots through gas price competition.

[src/Timelock.sol#executeWhitelisted](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L715-L726)
```solidity
function executeWhitelisted(
    address target,
    uint256 value,
    bytes calldata payload
) external payable onlyRole(HOT_SIGNER_ROLE) whenNotPaused {
    // @audit MEV vulnerability: No transaction ordering protection between hot signers
    checkCalldata(target, payload);
    // @audit Direct execution allows front-running between hot signers
    _execute(target, value, payload);
    emit CallExecuted(bytes32(0), 0, target, value, payload);
}
```

```solidity
function _execute(address target, uint256 value, bytes calldata data)
    private
{
    // @audit No ordering guarantees or atomic execution
    (bool success,) = target.call{value: value}(data);
    require(success, "Timelock: underlying transaction reverted");
}
```
The core issue is that the execution flow allows different hot signers to compete for transaction ordering in the same block. This creates opportunities for MEV extraction through front-running.

* Multiple hot signers can execute the same whitelisted transaction
* No mechanism to prevent transaction ordering manipulation
* Direct execution without atomic guarantees

## Proof of Concept
Scenario between two hot signers Alice and Bob:

1. Alice submits a whitelisted DEX swap transaction with normal gas price
2. Bob sees Alice's transaction in mempool
3. Bob front-runs by submitting identical transaction with higher gas price
4. Bob's transaction executes first, potentially extracting value from Alice's transaction

## Recommended Mitigation Steps
Implement a commit-reveal scheme
```diff
+ struct CommitReveal {
+     bytes32 commitment;
+     uint256 revealTime;
+ }

+ mapping(address => CommitReveal) public commitments;

+ function commitTransaction(bytes32 commitment) external onlyRole(HOT_SIGNER_ROLE) {
+     commitments[msg.sender] = CommitReveal(commitment, block.timestamp + REVEAL_DELAY);
+ }

+ function executeWhitelisted(
     address target,
     uint256 value,
     bytes calldata payload,
+    bytes32 nonce
 ) external payable onlyRole(HOT_SIGNER_ROLE) {
+    bytes32 commitment = keccak256(abi.encode(target, value, payload, nonce));
+    require(commitments[msg.sender].commitment == commitment, "Invalid commitment");
+    require(block.timestamp >= commitments[msg.sender].revealTime, "Too early");
     checkCalldata(target, payload);
     _execute(target, value, payload);
 }
```
