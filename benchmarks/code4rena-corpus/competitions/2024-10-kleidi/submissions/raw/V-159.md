# Vulnerability details


## Description

The use of `Bytes32Set.values()` in multiple state-changing functions could lead to a denial of service (DoS).

This operation copies the entire storage to memory, which is costly, especially when the set grows large.

Since it can become prohibitively expensive to call functions like `pause()`, `_addCalldataCheck()`, `removeCalldataCheckDatahash()`, `_removeCalldataCheck()` and `_removeAllCalldataChecks()`, it may render them uncallable.

This could result in situations where the pause guardian doesn't desire to pause the contract, or the timelock refuses/is-unable to manage calldatas due to high-gas-costs/exceeding-block-gaslimit.

Without setting a proper limits on the number of live proposals timelock can have or calldatas that can be stored per index range, there's possiblity of Denial of Service, that can happen.

Also we can take a look at function natspec of `values(Bytes32Set storage set)` inside the `EnumerableSet.sol`, where OZ has warned us about it: [#L211-L228](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/28aed34dc5e025e61ea0390c18cac875bfde1a78/contracts/utils/structs/EnumerableSet.sol#L211-L228)

```javascript
    /**
     * @dev Return the entire set in an array
     *
     * WARNING: This operation will copy the entire storage to memory, which can be quite expensive. This is designed
     * to mostly be used by view accessors that are queried without any gas fees. Developers should keep in mind that
     * this function has an unbounded cost, and using it as part of a state-changing function may render the function
     * uncallable if the set grows to a point where copying to memory consumes too much gas to fit in a block.
     */
    function values(Bytes32Set storage set) internal view returns (bytes32[] memory) {
        bytes32[] memory store = _values(set._inner);
        bytes32[] memory result;

        assembly ("memory-safe") {
            result := store
        }

        return result;
    }

```

## Impact

Expensive gas operations could prevent critical timelock functions from being executed. like pause guardian refusing/notHavingEnoughFunds to pause the contract due to very high gas cost incase of emergency or timelock refusing/is-unable to manage calldatas due to high-gas-cost/exceeding-block-gas-limit.

## Proof Of Concept

`Bytes32Set.values()` is used in functions below:

- Whenever [pause guardian pauses the contract](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L685-L700), we retrieve all live proposals with [_liveProposals.values()](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L691) and since this is a function that modifies state, retrieving large number of proposals can cause DOS.
  
- in dataHash removal process with [removeCalldataCheckDatahash()](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L871-L934), if dataHash we removed was the last dataHash that was stored in `dataHashes`, we [remove that index](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L903-L920) by replacing last index `startIndex`, `endIndex` and all stored `dataHashes` with current index that we just removed an dataHash from. we first retrieve last index associated with that function, [specifically we retrieve last index dataHashes and replace it's values with the current index that we just removed dataHash from](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L911C1-L916C14).  as you can see we have for loop that basically, loops through all dataHashes of last Index and stores it to current Index we just removed dataHash from, and then pop the last Index. effectively removing the Index that Has no dataHashes stored in it. if dataHashes stored in last Index is way to many, that can cause DOS.

- third accurance of `Bytes32Set.values()` is in [_addCalldataCheck()](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L1028-L1155) function when we [emit an event](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L1153). this function itself has complex logic and many for loops, so for that reason it already costs alot of gas to execute this function. plus we emit event with all dataHashes that is stored in [indexes[targetIndex].dataHashes.values()](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L1153). calling this function either will result in having very high gas cost or revert due to exceeding block gas limit, for that reason, most likely is vulnerable to DOS.

- the function that is most likely vulnerable to DOS is [_removeCalldataCheck()](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L1189-L1243), for [same reasons](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L1207-L1232) explained above.

- last function that `Bytes32Set.values()` is used in is, [_removeAllCalldataChecks()](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L1245-L1286), [where we delete every single indexes with their stored dataHashes](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L1262-L1282), which can be very gas expensive.

## Recommended mitigation

1. add two new state variables to Timelock called `maxLiveProposals` and `maxDataHashPerIndexRange`.

    on Timelock Deployment, user sets a custom limit on total number of proposals that can be stored in `_liveProposals` and total number of hashed calldatas that can be stored in  `_calldataList.dataHashes` for each function and index range to avoid unbounded growth and potential DOS.
    
2. refactor `_addCalldataCheck()` in a way that does not allow new calldatas being added, if already has reached it's max limit for that function, specific index range. 
   
3. refactor `_schedule()` in a way that does not allow scheduling a new proposal if already has reached it's max proposal limit. 
   
4. also add a setter function so safe will be able to change `maxLiveProposals` and `maxDataHashPerIndexRange`, if they intended to.
   keep in mind that a require statement should put in place for such function to ensure `_newMaxLiveProposals` is greater than or equal to total number of live proposals and `_newMaxDataHashPerIndexRange` is greater than or equal to total number of calldatas stored for that function specific index range.
