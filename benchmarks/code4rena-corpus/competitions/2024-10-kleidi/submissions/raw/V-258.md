# Vulnerability details

## Proof of Concept

The `createTimelock()` function is using the `CREATE2` opcode to deploy the `Timelock` contract at a predetermined address. 

The address is computed using the `salt` parameter and the address of the sender, `msg.sender`. 
 
If a malicious actor could pre-compute the `salt` and `msg.sender` combination to be used in a future deployment, they could front-run the deployment of the new contract.

It opens a potential avenue for frontrunning attacks where an attacker determines the future address and deploys a malevolent contract before the genuine contract gets deployed.


Here, a malicious contract could be deployed with same details.

```solidity
function createTimelock(address safe, DeploymentParams memory params) external returns (address timelock) {
    timelock = address(new Timelock{ salt: keccak256(abi.encodePacked(params.salt, msg.sender)) }(
        safe, params.minDelay, params.expirationPeriod, params.pauser, params.pauseDuration, params.hotSigners
    ));
    emit TimelockCreated(timelock, block.timestamp, msg.sender);
}
```

## Recommended Mitigation Steps

To increase contract security, it is important to:

1. Add permission requirements on `createTimelock()` to allow only contracts and addresses that are expected to deploy other contracts.

2. Consider possible precautious measures to prevent frontrunning attacks. For instance, include a secret parameter, known only to the original transaction creator, during the transaction signing stage.
