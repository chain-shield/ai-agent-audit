# Vulnerability details

firstly let us explain how reschedule and its internal operations are working.
schedule function internally make a call to _schedule function, which is responsible to schedule the timestamp for a proposal or a transactions by setting timestamps[id] mapping to block.timestamp + delay.

And now in the execute function which can be called by anyone by providing target address, id, payload and a salt, which than make a internal call to _execute function that firstly removes the id from the _liveProposals and checks if the operation is ready to execute and make a call to _execute function to transfer value to the target address thereafter it make a call to _aftercall function which sets timestamps[id] to _DONE_TIMESTAMP, which means operation for a given id has successfully executed.

The first issue in the schedule is that it can be reschedule as soon as the time delay for the id get expired and can be reschedule again on purpose to make the transaction reschedule.

secondly in the execute function the execute function can be called again for the same id when it get reschedule again to make the transaction execute, which passes the require check to remove id since it was added again when the operation get reschedule and the isoperationReady also get successfully passed, which than call to _execute function and make transfer of value to provided target address thereafter it call _afterCall operation which simply override the timestamp[id] to Done_timestamp this is done because in the execute function it self their is no call performed to isOperationDone function which is required to check if the executed for id or not.

Recommendation:
Make a necessary call to isOperationDone under execute function to prevent execute operation been done for the already executed id.
