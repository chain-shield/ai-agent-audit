# Vulnerability details

## Proof of Concept
background:
1. The protocol hopes to use pause to ensure the safety of funds when the safe wallet loses control. After the pause, the attacker cannot perform any operations through safe.
2. In the pause function, all proposals will be looped and deleted.
3. If an attacker obtains the safe wallet, [he can freely create proposals](https://github.com/code-423n4/2024-10-kleidi/blob/ab89bcb443249e1524496b694ddb19e298dca799/src/Timelock.sol#L521).

```solidity
        bytes32[] memory proposals = _liveProposals.values();
        for (uint256 i = 0; i < proposals.length; i++) {
            bytes32 id = proposals[i];

            delete timestamps[id];
            assert(_liveProposals.remove(id));

            emit Cancelled(id);
        }
```

Therefore, an attacker can continue to create proposals after gaining control of the safe wallet. Let the number of proposals be huge. Until the pause function is called, it fails because the gas exceeds the gas limit of the transaction. This prevents pausing.

If we calculate the gas consumption of the pause function, we can get:
• Remove timestamps[id]: ~5,000 gas.
• Remove _liveProposals.remove(id): Assume ~15,000 gas.
• Trigger event emit Canceled(id): about 631 gas.
• Base cost for other memory operations, array accesses, and control flow: approximately 1,000 gas.
• The total gas consumption per loop is roughly: 5000 + 15000 + 631 + 1000 = 21,631 gas
Assuming that the gas limit of a single transaction is 15,000,000 gas, using the previously estimated gas of 21,631 gas per cycle, we can calculate the approximate number of cycles ≈ 15,000,000 / 21,631 ≈ 693 times

Although the attacker needs to pay some gas cost. But if the amount of timelock funds is huge, then the effort is worth it.

## Recommended Mitigation Steps
It is recommended not to include the operation of deleting proposals in pause. We can write another function for pause to call.
