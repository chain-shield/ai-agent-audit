# Vulnerability details

## Description

The `addCheckCalldata()` function in the `Timelock` contract, currently allows for the entire calldata to be arbitrary if wildcard is set. This poses a security risk, as malicious hot signers could take advantage of the wildcard for arbitrary function calls with harmful parameters in some scenarios.

instead the wildcard functionality should be implemented in a way that, Timelock allows certain parts of calldata related to a specific contract and function, to be arbitrary(wildcard) and certain parts of calldata have restrictions(whitelisted).

its true that safe owners should be extra cautious when choosing a function for granting wildcard to, but the way the wildcard functionality is implemented now, it simply allows the hot signer to input any arbitrary data to each parameter and there's no way for safe owners to grant a wildcard to only specific parameter of a function.

also seems like developer wanted to implement the wildcard functionality the way i described because if we take a look at [checkCalldata()](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L470-L504) function, specifically [this part](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L488-L493). we check if retrieved index has granted a wildcard or not, but developer hasn't noticed that he implemented wildcard functionality in a way that once a function is granted a wildcard, no more indexes can be added for that function because of [this part](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L1062-L1067) in [_addCalldataCheck()](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L1028-L1155).

## Impact

Once a function is granted wildcard access, it gives hot signers too much ability to act freely or even maliciously in some scenarios, if wildcard is granted to wrong function. This violates the principle of least privilege in security, enabling malicious or unexpected actions.

it's better that the wildcard functionality is implemented in such way, that if safe owners decided to grant wildcard access to specific part of calldata, they could, instead of allowing the whole calldata to arbitrary. also be able to restrict certain parts of calldata with whitelisting calldatas.

## Proof Of Concept

wildcard functionality is currently implemented this way:

* we can determine whether or not wildcard is set for a function, by checking first index struct of a function. specifically it's `startIndex` and `endIndex` values.
  if (`startIndex == endIndex` && `startIndex == 4` && `_calldataList[contractAddress][selector].length == 1`), it means wildcard is granted for that function. you can read [_addCalldataCheck()](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L1028-L1155) function, to understand wildcard functionality better, specifically [#L1058-L1078](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L1058-L1078).

* once wildcard is granted for a function, hot signer can execute that function with `executeWhitelisted()` or `executeWhitelistedBatch()` function with any arbitrary calldata, because [checkCalldata() for loop](https://github.com/solidity-labs-io/kleidi/blob/0d72b6cb5725c1380212dc76257da96fcfacf22f/src/Timelock.sol#L488-L503), once it sees `startIndex` and `endIndex` are equal for first Index Struct, it stops calldata validation process and allows hotsigner proceed with arbitrary data.


## Recommended Mitigation

refactor `addCheckCalldata()` and other calldata related functions, in a way that timelock can grant/remove a wildcard to/from specific parts of calldata and restrict other parts by whitelisting calldata.
