# Vulnerability details

## Description

The `_addCalldataCheck` function in the `Timelock` contract does not fully enforce the requirement that calldata checks must be isolated to distinct, non-overlapping segments. This could lead to ambiguity in calldata validation and potentially allow unauthorized transactions.

## Vulnerable Code

```solidity
function _addCalldataCheck(...) private {
    // ... (other validations) ...

    for (uint256 i = 0; i < indexes.length; i++) {
        require(
            startIndex > indexes[i].endIndex || endIndex < indexes[i].startIndex, 
            "CalldataList: Partial check overlap"
        ); 
    }

    // ... (rest of the function) ...
}
```

## Scenario

The current validation only prevents overlaps where one check completely encompasses another. It would still allow the following:

* **Check 1:** `startIndex = 4`, `endIndex = 10` (checks bytes 4 to 10 of the calldata)
* **Check 2:** `startIndex = 8`, `endIndex = 14` (checks bytes 8 to 14 of the calldata)

These checks overlap in bytes 8 to 10. This could lead to situations where:

* **Ambiguous Validation:** It's unclear which check should take precedence if there's a conflict in the expected data for the overlapping bytes.
* **Bypass:** A carefully crafted calldata could satisfy one check while violating the other, potentially bypassing the intended restrictions.


## Impact

This weakness increases the complexity of calldata validation and creates potential security risks if not addressed carefully.

## Recommendation

Strengthen the validation to prevent any overlap between calldata checks:

```solidity
function _addCalldataCheck(...) private {
    // ... (other validations) ...

    for (uint256 i = 0; i < indexes.length; i++) {
        require(
            endIndex <= indexes[i].startIndex || startIndex >= indexes[i].endIndex,  // Stricter check
            "CalldataList: Overlapping calldata check"
        ); 
    }

    // ... (rest of the function) ...
}
```

This revised check ensures that new checks either occur entirely before or after existing checks, eliminating any overlap and ensuring clear, unambiguous validation.

If feasible, consider refactoring the calldata check mechanism to use a data structure that inherently prevents overlaps (e.g., a sorted list or interval tree) to simplify the validation logic.
