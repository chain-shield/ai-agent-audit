# Vulnerability Details

## Impact

This issue is about how the scheduling and execution flow of the protocol can prevent a proposal to decrease the `expirationPeriod` from being executable, even though it has not yet expired.

This means that a safe has to schedule a new proposal and has to wait up to 30 days before it can get executed, which could revert again.

The fact that, when the contract is used as intended, it can lead to a user being unable to decrease the `expirationPeriod` and having to wait up to 30 days for the next proposal leads me to estimate this as a "Medium" severity issue.

## Proof of Concept

During the scheduling and execution flow of a proposal, the user has to consider two types of time periods:
1. `delay`, which represents the time a user has to wait for before anyone can execute it
2. `expirationPeriod`, which represents the timeperiod during which the proposal can be executed by anyone

Let's first look at the `_schedule(bytes32 id, uint256 delay)` function, which is wrapped by `schedule(address target, uint256 value, bytes calldata data, bytes32 salt, uint256 delay)`.

```solidity
function _schedule(bytes32 id, uint256 delay) private {
    /// this line is never reachable as no duplicate id's are enforced before this call is made
    require(!isOperation(id), "Timelock: operation already scheduled");
    /// this line is reachable
    require(delay >= minDelay, "Timelock: insufficient delay");
    timestamps[id] = block.timestamp + delay;
}
```
What is important is that the `timestamps[]` mapping saves the time after which anyone can execute the proposal.

Now we need to look at the `execute(address target,uint256 value, bytes calldata payload, bytes32 salt)` function in `Timelock.sol`, which is used to execute proposals that have been scheduled by the safe using `schedule(address target, uint256 value, bytes calldata data, bytes32 salt, uint256 delay)`.

```solidity
function execute(
    address target,
    uint256 value,
    bytes calldata payload,
    bytes32 salt
) external payable whenNotPaused {
    bytes32 id = hashOperation(target, value, payload, salt);

    /// first reentrancy check, impossible to reenter and execute the same
    /// proposal twice
    require(_liveProposals.remove(id), "Timelock: proposal does not exist");
    require(isOperationReady(id), "Timelock: operation is not ready");
    _execute(target, value, payload);
    emit CallExecuted(id, 0, target, value, payload);

    /// second reentrancy check, second check that operation is ready,
    /// operation will be not ready if already executed as timestamp will
    /// be set to 1
    _afterCall(id);
}
```

The important point here is the fact that `isOperationReady(bytes32 id)` is called twice: once before the proposal is executed, and once in `_afterCall(bytes32 id)`, AFTER the execution (which means that changes made to the contract by the proposal will be taken into account).

Now let's take a closer look at what happens in `isOperationReady(bytes32 id)`.

```solidity
function isOperationReady(bytes32 id) public view returns (bool) {
    /// cache timestamp, save up to 2 extra SLOADs
    uint256 timestamp = timestamps[id];
    return timestamp > _DONE_TIMESTAMP && timestamp <= block.timestamp
        && timestamp + expirationPeriod > block.timestamp;
}
```
We will be focusing on the following inequaility:

```
timestamp + expirationPeriod > block.timestamp
```

It should ensure that no proposal can be executed after it has expired.

Now we are in a position where we can take a look at a simple scenario in which a user is unable to change the `expirationPeriod`.

(The test should be added to the `Timelock.t.sol` test file)

```solidity
function testUpdateExpirationPeriodExecuteRevert() public {
    vm.prank(address(safe));
    timelock.schedule(
        address(timelock),
        0,
        abi.encodeWithSelector(timelock.updateDelay.selector, 30 days),
        bytes32(0),
        MINIMUM_DELAY
    );

    vm.warp(block.timestamp + MINIMUM_DELAY);
    timelock.execute(
        address(timelock),
        0,
        abi.encodeWithSelector(timelock.updateDelay.selector, 30 days),
        bytes32(0)
    );

    assertEq(timelock.minDelay(), 30 days, "minDelay incorrectly set");

    vm.prank(address(safe));
    timelock.schedule(
        address(timelock),
        0,
        abi.encodeWithSelector(timelock.updateExpirationPeriod.selector, 1 days),
        bytes32(0),
        30 days
    );

    vm.warp(block.timestamp + 31 days);
    vm.expectRevert("Timelock: operation is not ready");
    timelock.execute(
        address(timelock),
        0,
        abi.encodeWithSelector(timelock.updateExpirationPeriod.selector, 1 days),
        bytes32(0)
    );
}
```
In this test the following values were chosen for the important variables that i mentioned above:

```
delay = 30 days (maximum)
expirationPeriod = 5 days
```

What happens in the test is that first the `delay` gets changed to 30 days (just to showcase the impact the issue will have).
After that the safe schedules a proposal to decrease the `expirationPeriod` from 5 to 1 days.

After 31 days someone calls `execute()` to execute the proposal.
The inequality highlighted above will be checked twice.

The first check will be:

```
timestamp of `schedule()` call + 30 days + 5 days > timestamp of `schedule()` call + 31 days
```
This inequality is true. The proposal gets executed.

However, after the execution, `expirationPeriod` will be 1 days and `isOperationReady()` in `_afterCall` will be false and the function reverts:

```
timestamp of `schedule()` call + 30 days + 1 days > timestamp of `schedule()` call + 31 days
```
This inequality will continue to be false and cause the proposal to not be executable.

This results in the safe having to schedule another proposal and to wait another 30 days before it can be executed.


## Recommended Mitigation Steps

Consider changing how the `expirationPeriod` is updated so that it only affects proposals scheduled for the future. For example by snapshotting the current `expirationPeriod` for every proposal when it gets scheduled.
