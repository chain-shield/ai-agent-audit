# Vulnerability details

## Proof of Concept
An operation can simultaneously be in both "ready" and "expired" states. This inconsistency arises from the improper handling of state transitions in the `isOperationReady` and `isOperationExpired` functions. _Because the `isOperationReady` function does not check if an operation has expired, while the `isOperationExpired` function does not update the operation's status. This creates a time window where both functions can return true for the same operation, leading to an inconsistent state._

_For example_

1. Alice schedules an operation with a 1-day delay and a 2-day expiration period.
2. After 1 day and 1 hour, the operation is ready. `isOperationReady` returns true.
3. Another day passes, and the operation expires. `isOperationExpired` now returns true.
4. However, `isOperationReady` still returns true, creating an inconsistent state.

This inconsistency can lead to unexpected behavior in governance processes or dependent systems that rely on the Timelock contract.

```solidity
function isOperationReady(bytes32 id) public view returns (bool) {
    uint256 timestamp = timestamps[id];
    return timestamp > _DONE_TIMESTAMP && timestamp <= block.timestamp
        && timestamp + expirationPeriod > block.timestamp; // <@Audit: Doesn't check if operation has expired
}

function isOperationExpired(bytes32 id) public view returns (bool) {
    uint256 timestamp = timestamps[id];
    require(timestamp != 0, "Timelock: operation non-existent");
    require(timestamp != 1, "Timelock: operation already executed");
    return block.timestamp >= timestamp + expirationPeriod; // <@Audit: Doesn't update operation status
}
```
To validate this vulnerability, add the following test to Timelock.t.sol:
```solidity
function testOperationReadyAndExpired() public {
    bytes32 id = testScheduleProposalSafeSucceeds();
    
    vm.warp(block.timestamp + minDelay + 1 hours);
    assertTrue(timelock.isOperationReady(id), "Operation should be ready");
    
    vm.warp(block.timestamp + expirationPeriod);
    assertTrue(timelock.isOperationExpired(id), "Operation should be expired");
    assertTrue(timelock.isOperationReady(id), "Operation should still be considered ready");
}
```
This test demonstrates that an operation can be both ready and expired simultaneously.

**When you**

1. Schedule an operation
2. Wait until it becomes ready
3. Wait longer until it should expire
4. Check both `isOperationReady` and `isOperationExpired` - they'll both return true

## Recommended Mitigation Steps
Consider the following changes
```diff
function isOperationReady(bytes32 id) public view returns (bool) {
    uint256 timestamp = timestamps[id];
    return timestamp > _DONE_TIMESTAMP && timestamp <= block.timestamp
-        && timestamp + expirationPeriod > block.timestamp;
+        && block.timestamp < timestamp + expirationPeriod;
}

function isOperationExpired(bytes32 id) public view returns (bool) {
    uint256 timestamp = timestamps[id];
    require(timestamp != 0, "Timelock: operation non-existent");
    require(timestamp != 1, "Timelock: operation already executed");
-    return block.timestamp >= timestamp + expirationPeriod;
+    if (block.timestamp >= timestamp + expirationPeriod) {
+        timestamps[id] = _DONE_TIMESTAMP;
+        return true;
+    }
+    return false;
}
```
These changes ensure that an operation cannot be simultaneously ready and expired, maintaining the contract's intended state transitions and improving overall security and reliability of the governance process.
