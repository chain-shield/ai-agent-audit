# Vulnerability details

## Proof of Concept

**Summary**

When an operation(s) has been executed it is removed from the list of `_liveProposals` using it's id which is a hash of *target,value,payload and salt* and then the `timestamp[id]` is set to 1, meaning it's done. The problem arises in the schedule function which does not check whether the operation is done to avoid rescheduling it again. If the same operation gets scheduled in a batch of operations it will prevent other operations from executing because it won't pass the `isOperationReady` check in the `executeBatch` function.

**Vulnerability Details**
- When Bobs' operation that was previously scheduled gets executed it is removed from the list of live proposals and then its timestamp gets updated as shown below.
```solidity
function _afterCall(bytes32 id) private {
        
        require(isOperationReady(id), "Timelock: operation is not ready");
        timestamps[id] = _DONE_TIMESTAMP;
    }
```
- The operation is identified by its id which is a hash generated by `keccak256(abi.encode(target, value, data, salt))`. Even if this gets removed from the list of `_liveProposals` it can be added on calling the schedule function.
- When the safe schedules operations containing a batch of transactions and the already executed operation gets added to the list of scheduled calls, it will pass all checks and get scheduled.
- When delay time has passed and the operations are to be executed they will fail because of the check `isOperationReady` as shown below
```solidity
     function isOperationReady(bytes32 id) public view returns (bool) {
        /// cache timestamp, save up to 2 extra SLOADs
        uint256 timestamp = timestamps[id];
        return timestamp > _DONE_TIMESTAMP && timestamp <= block.timestamp
            && timestamp + expirationPeriod > block.timestamp;
    }
```
This will fail because on execution the timestamp[id] gets changed to `_DONE_TIMESTAMP`
- This will prevent all operations in the batch from executing.

## Recommended Mitigation Steps
```diff
function schedule(
        address target,
        uint256 value,
        bytes calldata data,
        bytes32 salt,
        uint256 delay
    ) external onlySafe whenNotPaused {
        bytes32 id = hashOperation(target, value, data, salt);
++       require(isOperationDone(id), "Timelock: operation is not ready");

        /// this is technically a duplicate check as _schedule makes the same
        /// check again
        require(_liveProposals.add(id), "Timelock: duplicate id");

        /// SSTORE timestamps[id] = block.timestamp + delay
        /// check delay >= minDelay
//maximum delay for timelocked operations
        _schedule(id, delay);

        emit CallScheduled(id, 0, target, value, data, salt, delay);
    }

```
```diff
   function scheduleBatch(
        address[] calldata targets,
        uint256[] calldata values,
        bytes[] calldata payloads,
        bytes32 salt,
        uint256 delay
    ) external onlySafe whenNotPaused {
        require(
            targets.length == values.length && targets.length == payloads.length,
            "Timelock: length mismatch"
        );

        bytes32 id = hashOperationBatch(targets, values, payloads, salt);
++       require(isOperationDone(id), "Timelock: operation is not ready");


        /// this is technically a duplicate check as _schedule makes the same
        /// check again
        require(_liveProposals.add(id), "Timelock: duplicate id");

        /// SSTORE timestamps[id] = block.timestamp + delay
        /// check delay >= minDelay
        _schedule(id, delay);

        for (uint256 i = 0; i < targets.length; i++) {
            emit CallScheduled(
                id, i, targets[i], values[i], payloads[i], salt, delay
            );
        }
    }

```
**N/B This bug does not affect execution of a single operation.**
