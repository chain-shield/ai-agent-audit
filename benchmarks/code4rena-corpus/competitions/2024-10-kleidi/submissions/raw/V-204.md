# Proof of Concept

## Vulnerability: Reentrancy in `execute` and `executeBatch` Functions (Timelock.sol)

The `execute` (lines 589-609) and `executeBatch` (lines 621-650) functions in `Timelock.sol` are vulnerable to reentrancy attacks. Reentrancy occurs when an external contract is called before the current execution is completed, allowing an attacker to re-enter the function and manipulate the state or drain resources.

### Impact:
- **Resource Draining:** An attacker could drain resources by repeatedly invoking the `execute` function before its first execution completes.
- **State Corruption:** The contract’s state could be corrupted due to incomplete execution, resulting in unpredictable outcomes.

### Exploit Scenario:
An attacker could craft a malicious contract that calls the `execute` function repeatedly before it finishes. This re-entrance would manipulate the contract’s state or drain resources.

### Example Code from `Timelock.sol` (Lines 589-650):

### Recommended Mitigation Steps

## Solution 1: Add Reentrancy Guard
To prevent reentrancy attacks, implement a reentrancy guard using OpenZeppelin’s ReentrancyGuard library:

```solidity
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

contract Timelock is ReentrancyGuard {
    function execute(
        address target,
        uint256 value,
        bytes calldata data
    ) external payable nonReentrant {
        require(isOperationReady(id), "Operation is not ready");
        require(address(this).balance >= value, "Insufficient balance");

        (bool success, ) = target.call{value: value}(data);
        require(success, "Transaction execution failed");

        emit CallExecuted(id, target, value, data);
    }

    function executeBatch(
        address[] calldata targets,
        uint256[] calldata values,
        bytes[] calldata datas
    ) external payable nonReentrant {
        require(targets.length == values.length && targets.length == datas.length, "Parameter length mismatch");

        for (uint256 i = 0; i < targets.length; i++) {
            (bool success, ) = targets[i].call{value: values[i]}(datas[i]);
            require(success, "Batch transaction execution failed");
        }

        emit BatchCallExecuted(id, targets, values, datas);
    }
}
```
## Solution 2: Apply the Checks-Effects-Interactions Pattern
In addition to using the nonReentrant modifier, follow the Checks-Effects-Interactions pattern to minimize risk:

Check Conditions: Perform all necessary checks at the beginning (e.g., balance verification, authorization checks).
Update State: Modify the contract state (e.g., mark the operation as complete) before interacting with external contracts.
Interaction: Interact with external contracts (e.g., using call, send, or transfer) only after the state updates.
