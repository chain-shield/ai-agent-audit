# Vulnerability details

## Proof of Concept

Create2Helper.sol calculates an Ethereum address for a contract that will be deployed with a `CREATE2` opcode, which was introduced in Ethereum's Constantinople upgrade. It utilizes `keccak256` to compute the hash of certain input parameters. 

However, the function doesn't validate the length of the `creationCode`. 

```solidity
function calculateCreate2Address(
    address creator,
    bytes memory creationCode,
    bytes memory constructorParams,
    bytes32 salt
) pure returns (address) {
    return address(
        uint160(
            uint256(
                keccak256(
                    abi.encodePacked(
                        bytes1(0xff),
                        creator,
                        salt,
                        keccak256(
                            abi.encodePacked(creationCode, constructorParams)
                        )
                    )
                )
            )
        )
    );
}
```

In circumstances where `creationCode` is of inappropriate or unexpected length, the function's behavior could vary and it may return incorrect addresses.

The functions 'calculateCreate2Address' and 'calculateCreate2Address' do not verify the length of `creationCode` before using it.

## Recommended Mitigation Steps

It's advisable to add input validation for `creationCode` and `constructorParams` before processing them. 

This could be done by checking their lengths and requirements. If they do not meet the requirements, the function should fail with a relevant error message. 

```solidity
require(creationCode.length > 0, "Length of creationCode is zero.");
require(constructorParams.length >= 0, "Length of constructorParams is invalid.");
```
