# Vulnerability details

Operations can be executed before their intended timelock period has fully elapsed. This issue stems from the order of operations in the `execute` function, where a proposal is removed from the `_liveProposals` set before its readiness is checked.

Due to a race condition in the `execute` function. The function first removes the proposal from `_liveProposals` and then checks if the operation is ready. This creates a window where multiple transactions can attempt to execute the same operation, potentially leading to premature execution.

```solidity
function execute(
    address target,
    uint256 value,
    bytes calldata payload,
    bytes32 salt
) external payable whenNotPaused {
    bytes32 id = hashOperation(target, value, payload, salt);

    require(_liveProposals.remove(id), "Timelock: proposal does not exist");
    require(isOperationReady(id), "Timelock: operation is not ready"); // <= FOUND

    _execute(target, value, payload);
    emit CallExecuted(id, 0, target, value, payload);

    _afterCall(id);
}
```
The issue arises because the `_liveProposals.remove(id)` operation is performed before checking if the operation is ready. This can lead to a scenario where an operation is executed slightly before its intended timelock period has fully elapsed.

## Proof of Concept
The `isOperationReady` check is correctly placed, but there's a logical inconsistency between removing the proposal from `_liveProposals` and checking if it's ready. This can lead to a race condition where an operation is executed before it's actually ready.

Users could execute operations before the intended timelock period has passed, bypassing the security measures put in place by the timelock mechanism.

Consider the following event.

1. A proposal is created with a timelock of 1 hour.
2. After 59 minutes and 59 seconds:

   * User A calls `execute`, which removes the proposal from `_liveProposals`.
   * Immediately after, but before User A's transaction is mined, User B calls `execute`.
   * User B's transaction gets mined first, executing the proposal 1 second early.

This sequence of events shows how the current implementation could allow a proposal to be executed before its timelock period has fully elapsed, potentially compromising the security guarantees of the timelock mechanism.

* We check if `!timelock.isOperationReady(id)` is true
* Then attempts to execute the operation
* The expectation is that execution should fail, but it succeeds

## Impact
It undermines the core functionality of the Timelock contract, which is designed to enforce a delay between the proposal and execution of operations. This could lead to:

1. Premature execution of sensitive operations.
2. Bypassing of governance processes that rely on the timelock for security.

## Recommended Mitigation Steps
Consider implementing the following changes
```diff
function execute(
    address target,
    uint256 value,
    bytes calldata payload,
    bytes32 salt
) external payable whenNotPaused {
    bytes32 id = hashOperation(target, value, payload, salt);

-   require(_liveProposals.remove(id), "Timelock: proposal does not exist");
```
