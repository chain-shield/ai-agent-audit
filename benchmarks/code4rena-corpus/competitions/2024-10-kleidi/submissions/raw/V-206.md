# Vulnerability details

## Proof of Concept

For context, there is a Delegatecall injection in the following function that leads to RCE: 

```solidity
require(
            Safe(payable(walletInstance.safe)).execTransaction(
                multicall3,
                0,
                abi.encodeWithSelector(IMulticall3.aggregate3.selector, calls3),
                Enum.Operation.DelegateCall,
                0,
                0,
                0,
                address(0),
                payable(0),
                signature
            ),
            "InstanceDeployer: Safe delegate call failed"
        );


The key here is that delegatecall allows code execution within the context of the Gnosis Safe wallet (walletInstance.safe). The attacker’s goal is to gain control over the data passed in calls3 and inject malicious delegate calls. Of note is that the calls3 array holds a series of calls that are passed to the Multicall3 contract. Since there is no authentication or access control enforcing who can propose or manage the calls3 array, an external and unauthorized attacker could inject arbitrary delegatecall transactions.

No Access Control on execTransaction: The execTransaction function of the Safe contract is exposed without additional access checks. This lack of authentication or authorization control at the point where calls3 is passed allows any external actor to potentially create malicious inputs for the calls3 array. The input is NOT validated or restricted, meaning that an attacker can insert malicious data targeting the Safe's critical functions, such as changing ownership or transferring funds.

This code involves a delegatecall via the Gnosis Safe's execTransaction function.

By using IMulticall3.aggregate3.selector and passing the calls3 array, the contract allows arbitrary transactions to be executed. Since delegatecall executes the code within the context of the calling contract (in this case, the Safe contract), an attacker can manipulate the calls3 array to execute (arbitrary) malicious code.


After reviewing the path that leads to this function call, I confirmed first that there is no specific access control or authentication mechanisms appear to restrict who can supply the calls3 data. In particular I examined:

--InstanceDeployer.sol does not impose checks on the origin of the calls3 array or the parameters within.
--The Safe contract's execTransactionFromModule function directly processes the delegatecall without validating the calls3 array.
--There is NO validation to ensure that only trusted addresses are used in the calls3 array, making this exploitable if an attacker can inject malicious data.


Ok, similar to the other delegatecall injection I have reported, first step to exploit this vuln is to create a malicious contract that includes a function to change the ownership of the Safe contract.

```solidity
contract MaliciousContract {
    function changeOwnership(address newOwner) public {
        GnosisSafe(targetSafe).transferOwnership(newOwner);
    }
}
```

Then, construct a calls3 array with a single malicious entry pointing to this contract:

```solidity 
IMulticall3.Call3;
calls3[0].target = address(maliciousContract);
calls3[0].callData = abi.encodeWithSelector(MaliciousContract.changeOwnership.selector, newOwner);
calls3[0].allowFailure = false;
```

Then, execute the transaction: 

```solidity 
Safe(walletInstance.safe).execTransactionFromModule(
    multicall3,
    0,
    abi.encodeWithSelector(IMulticall3.aggregate3.selector, calls3),
    Enum.Operation.DelegateCall
);
```
Since delegatecall executes in the context of the Safe, an attacker can gain complete control over Safe operations, including ownership changes and fund transfers, by crafting malicious calls3 entries.

Also, there is no verification or access control on who can manipulate the calls3 array and trigger execTransaction. This makes the Safe contract vulnerable to external manipulation.

Impacts from this vulnerability being exploited: 

-->> Ownership/takeover of the Gnosis Safe Wallet

     By crafting a malicious calls3 entry, an attacker can execute any code within the context of the 
     Gnosis Safe wallet. Specifically, as shown in the Proof of Concept (PoC), a malicious contract 
     can transfer ownership of the Safe contract, essentially giving full control to the 
     attacker.

     The Safe contract is responsible for managing assets. By transferring ownership to a malicious 
     actor, they can effectively control all assets within the wallet. This means they could:
     -Modify Safe's parameters
     -Disable security features
     -Prevent legitimate owners from accessing their assets

-->> Unrestricted funds transfer
      An attacker can not only take ownership, but also directly transfer funds by manipulating the 
      calls3 array to include instructions to send funds from the wallet to an arbitrary address

      Since delegatecall executes in the context of the Safe contract, any function that can be executed 
      within the Safe can be hijacked. This includes functions for transferring Ether or tokens stored 
      within the wallet.

-->> Execution of Arbitrary Code 
      The delegatecall mechanism allows arbitrary code execution within the Safe's context. An attacker 
      could inject a wide range of functions, not just changing ownership or transferring funds. For 
      example, they could:
       - Disable or modify critical security mechanisms.
       - Alter the Safe's configuration, making it more vulnerable to future attacks.
       - Deploy persistent backdoors into the wallet.

     Since the calls3 array is not authenticated or validated, any function within the Safe’s scope can 
     be called, making this vulnerability extremely dangerous.

 -->> Lack of Access Controls expands the attack surface 

     The absence of access control means any external actor can craft malicious inputs for the calls3 
     array. This broadens the range of attackers, from internal actors to external adversaries who have 
     no prior access or knowledge of the system.

     Without any form of input validation or role-based access control, the vulnerability becomes 
     accessible to anyone, increasing the chances of exploitation.


  -->> there is also the chance of DoS.

         An attacker could inject calls that modify the Safe in such a way that legitimate users are 
         locked out. This could be through modifying the ownership structure, locking the wallet in an 
         unusable state, or exhausting gas in a way that blocks future transactions.

         By modifying the logic of the Safe using delegatecall, an attacker could effectively "brick" 
         the wallet, rendering it non-functional.

## Recommended Mitigation Steps

Some recommended mitigations are as follows. 

-->>Input validation.  Introduce validation to ensure only trusted addresses, and calls can be made via calls3. Validate function selectors and target addresses.

-->>Role-Based Access Control.  Implement access control for who can execute transactions involving the Safe’s delegatecall functionality. This prevents unauthorized parties from initiating potentially dangerous calls.

-->>Limit the use of Delegatecall.  Reduce the use of delegatecall wherever possible, and avoid using it with user-provided data like calls3.
