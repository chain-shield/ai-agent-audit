# Vulnerability details

## Proof of Concept
The createSystemInstance function in the InstanceDeployer.sol contract is exposed publicly without any access control restrictions. This function allows anyone to create a new system instance, which includes configuring sensitive settings such as owners, recovery spells, and thresholds.

There is no mechanism to restrict who can call this function, which means any unauthorized user can deploy system instances, potentially with incorrect or malicious parameters. Although the contract checks that the caller must be a hot signer of the Timelock, this check might not be sufficient to prevent abuse.

This lack of access control could allow a malicious user to:

Deploy system instances with unsafe or compromised recovery spells.
Add themselves as owners or configure dangerous thresholds that could undermine the security of the Safe.
Deny legitimate users the ability to configure or deploy system instances correctly.
Without access control, this presents a medium-risk vulnerability since unauthorized deployment could lead to critical misconfigurations, especially in multi-user environments.

The function is marked as external and lacks access control, allowing any user to invoke it:

No validation on sensitive parameters such as owners and threshold:

The lack of validation on the owners and threshold allows malicious actors to configure system instances with arbitrary values:

Recovery spells can be added to the Safe without validation, potentially introducing backdoors:

The createSystemInstance function is publicly accessible without any restrictions:

Any external actor can call this function, leading to unauthorized system instance deployments:

No checks exist to validate whether the caller is authorized to deploy the system.
Recovery spells, owners, and threshold configurations can be manipulated without restriction.
Potential Impact
A malicious actor could deploy system instances with recovery spells that contain backdoors, allowing unauthorized access to the Safe.
Malicious owners could be added, and thresholds could be misconfigured, leading to compromised control over the Safe.
The ability for unauthorized users to create system instances opens up significant risks of denial of service or control over funds stored in the Safe.

## Recommended Mitigation Steps
Add proper access control to the createSystemInstance function. This could include:

Restricting access to only specific roles or addresses, such as the owner or a whitelist of trusted users.
Introducing an authorization mechanism, such as using OpenZeppelin’s AccessControl or Ownable, to limit who can deploy system instances.
Ensure that parameters like recovery spells and owners are validated before the system instance is deployed, adding further security against malicious configurations.

Implement stricter validation checks to ensure that the system instance being deployed follows the expected configuration and does not introduce backdoors or unintended access.
