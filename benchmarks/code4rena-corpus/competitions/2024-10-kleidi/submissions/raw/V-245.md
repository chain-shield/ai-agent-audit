# Vulnerability details

## Description

The RecoverySpell contract uses `block.timestamp` for two critical timing checks:
1. Setting initial recovery time: `recoveryInitiated = block.timestamp`
2. Enforcing delay period: `block.timestamp > recoveryInitiated + delay`

## Vulnerability Details
Miners/validators can manipulate `block.timestamp` within a certain range (typically up to 15 seconds in Ethereum). In the RecoverySpell contract, this could affect the delay enforcement mechanism.

## Vulnerable Code

```solidity
// Setting recovery time in constructor
constructor(
    address[] memory _owners,
    address _safe,
    uint256 _safeThreshold,
    uint256 _recoveryThreshold,
    uint256 _delay
) {
    // ... other initialization ...
    recoveryInitiated = block.timestamp;  // Vulnerable to manipulation
    emit RecoveryInitiated(block.timestamp, msg.sender);
}

// Checking delay in executeRecovery
function executeRecovery(
    address previousModule,
    uint8[] calldata v,
    bytes32[] calldata r,
    bytes32[] calldata s
) external {
    // Vulnerable to timestamp manipulation
    require(
        block.timestamp > recoveryInitiated + delay,
        "RecoverySpell: Recovery not ready"
    );
    // ... rest of function
}
```

## Impact

1. Delay Period Manipulation:
   - Miners could slightly reduce the effective delay period
   - For short delays (e.g., hours), the manipulation could be significant percentage-wise
   - Critical for emergency response timing

2. Timestamp Dependence:
   - Recovery events might be recorded with slightly incorrect timestamps
   - Could affect off-chain monitoring and response systems

## Attack Scenario

```solidity
1. Recovery spell is deployed at true time T
2. Miner manipulates block.timestamp to T - 15 seconds
3. recoveryInitiated is set to T - 15s
4. At time T + delay - 15s:
   - True delay hasn't passed
   - But block.timestamp > recoveryInitiated + delay is true
   - Recovery can be executed 15s early
```

## Fix

1. Primary Fix - Block Number Based Delay:

```solidity
contract RecoverySpell is EIP712 {
    // Use block numbers instead of timestamps
    uint256 public recoveryInitiatedBlock;
    uint256 public immutable delayInBlocks;  // ~15 sec/block
    
    constructor(
        address[] memory _owners,
        address _safe,
        uint256 _safeThreshold,
        uint256 _recoveryThreshold,
        uint256 _delayInSeconds
    ) {
        // Convert time delay to block delay (add buffer for safety)
        delayInBlocks = (_delayInSeconds / 15) + 1; 
        recoveryInitiatedBlock = block.number;
        
        // ... rest of initialization
        
        emit RecoveryInitiated(block.number, msg.sender);
    }
    
    function executeRecovery(
        address previousModule,
        uint8[] calldata v,
        bytes32[] calldata r,
        bytes32[] calldata s
    ) external {
        require(
            recoveryInitiatedBlock != type(uint256).max,
            "RecoverySpell: Already recovered"
        );
        
        require(
            block.number >= recoveryInitiatedBlock + delayInBlocks,
            "RecoverySpell: Recovery not ready"
        );
        
        // ... rest of function
    }
}
```

2. Alternative Fix - Minimum Timestamp Buffer:

```solidity
contract RecoverySpell is EIP712 {
    uint256 public constant TIMESTAMP_BUFFER = 15;
    
    function executeRecovery(
        address previousModule,
        uint8[] calldata v,
        bytes32[] calldata r,
        bytes32[] calldata s
    ) external {
        require(
            block.timestamp >= recoveryInitiated + delay + TIMESTAMP_BUFFER,
            "RecoverySpell: Recovery not ready"
        );
        // ... rest of function
    }
}
```

## Security Considerations

1. Block Number Based Delay:
   - More resistant to manipulation
   - Variable block times could affect delay precision
   - Better for shorter delays (hours/days)

2. Timestamp Buffer:
   - Simple to implement
   - Accounts for maximum timestamp manipulation
   - Slightly increases delay time
