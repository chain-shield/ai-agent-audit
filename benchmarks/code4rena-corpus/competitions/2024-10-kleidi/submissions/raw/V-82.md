# Vulnerability details

## Proof of Concept
The createRecoverySpell function allows users to supply arbitrary salts for deploying new RecoverySpell contracts using the CREATE2 opcode. However, there are no restrictions or rate-limiting mechanisms on the usage of salts, which can be exploited to create a Denial of Service (DoS) attack by front-running legitimate users.

```
recovery = new RecoverySpell{salt: salt}(
    owners, safe, threshold, recoveryThreshold, delay
);
```

By allowing arbitrary salts without any checks, attackers can use the CREATE2 opcode to deploy contracts with the same base parameters and different salts, effectively blocking legitimate users from creating their contracts by reserving the same expected contract addresses.

Details
The lack of control over salt usage in CREATE2 can allow attackers to deploy multiple contracts with different salts, creating contract address collisions and effectively front-running legitimate contract deployments. This could lead to a Denial of Service (DoS) where legitimate users cannot deploy their own contracts at the expected addresses, as those addresses will already be taken by the attacker.

Attackers could also deploy contracts with conflicting parameters, preventing legitimate users from creating their recovery spells and causing resource exhaustion.

An attacker can use the same Safe address, owners, and other parameters but deploy multiple contracts with different salts, effectively blocking legitimate users from creating their own RecoverySpell contracts at the expected address.

Steps to Reproduce:
Deploy the RecoverySpellFactory.sol contract.
Deploy multiple RecoverySpell contracts using the same parameters but different salts.
Observe that legitimate users trying to deploy their contracts at the expected addresses will not be able to do so because the contract addresses are already taken.


PoC
```
pragma solidity ^0.8.25;

contract TestSaltDoSAttack {
    RecoverySpellFactory recoverySpellFactory;

    constructor(address _recoverySpellFactory) {
        recoverySpellFactory = RecoverySpellFactory(_recoverySpellFactory);
    }

    // Deploy multiple contracts with different salts to create DoS
    function createWithDifferentSalts(
        address[] memory owners,
        address safe,
        uint256 threshold,
        uint256 recoveryThreshold,
        uint256 delay
    ) external {
        for (uint256 i = 0; i < 10; i++) {
            bytes32 salt = keccak256(abi.encodePacked(i));  // Generate salts
            recoverySpellFactory.createRecoverySpell(salt, owners, safe, threshold, recoveryThreshold, delay);
        }
    }
}
```

The attacker successfully deploys multiple contracts with different salts, blocking legitimate users from deploying their contracts to the same expected addresses.

Denial of Service (DoS): By deploying multiple contracts with different salts, an attacker can block legitimate users from creating their own RecoverySpell contracts at the expected addresses.
Resource Exhaustion: This type of attack could also lead to resource exhaustion, as the system is forced to handle numerous unnecessary contract deployments, wasting gas and slowing down the network.




## Recommended Mitigation Steps
Implement Rate-Limiting on Salt Usage:
Add rate-limiting or other mechanisms to control how frequently users can deploy contracts with different salts. This can prevent attackers from deploying large numbers of contracts with varying salts and creating a DoS situation.

Enforce Salt Uniqueness:
Consider enforcing more restrictive salt usage to ensure that the same contract cannot be repeatedly deployed with only slight modifications to the salt, preventing attackers from front-running legitimate users.
