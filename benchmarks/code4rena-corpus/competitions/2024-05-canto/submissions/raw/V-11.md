# Vulnerability details

## Impact
setupLegacyKeyTables function for subsequent keyTable initialization will be skipped and not initialized without the function reverting when a keyTable has been initialized.

## Proof of Concept
The setupLegacyKeyTables function is responsible for initializing the KeyTable for different subspaces based on their module names. 

However, the current implementation will lead to skipping of subsequent keyTable initialization after the first subspace has been initialized.

For instance:

1. The setupLegacyKeyTables function iterates over the subspaces obtained from k.GetSubspaces().

2. For each subspace, it checks the module name using a switch statement and assigns the corresponding KeyTable to the keyTable variable.

3. If none of the cases match, the default case is executed, and the loop continues to the next iteration without initializing keyTable.

4. After the switch statement, the code checks if the subspace has a KeyTable registered using !subspace.HasKeyTable().

5. If the subspace does not have a KeyTable registered, the code calls subspace.WithKeyTable(keyTable) to initialize the KeyTable.

`// HasKeyTable returns if the Subspace has a KeyTable registered.
func (s Subspace) HasKeyTable() bool {
	return len(s.table.m) > 0
}`

However, if a subspace has a KeyTable registered, subsequent KeyTable registration will skip the if statement:
`
if !subspace.HasKeyTable() {
			subspace.WithKeyTable(keyTable)
		}
`

This is because:

- The HasKeyTable function checks if the Subspace has a KeyTable registered by checking if the length of the table.m map is greater than zero.
- In the setupLegacyKeyTables function, after initializing the KeyTable for the first subspace that matches a case in the switch statement, the table.m map will have a non-zero length.
- For subsequent subspaces with different module names, the if !subspace.HasKeyTable() condition will evaluate to false because the Subspace now has a KeyTable registered.
- As a result, the code will never reach the subspace.WithKeyTable(keyTable) line for subsequent subspaces, effectively skipping the initialization of the KeyTable for those subspaces.

Furthermore, assuming the code gets to call the WithKeyTable function, the function will also panic if it is called on an already initialized subspace (if len(s.table.m) != 0).

`func (s Subspace) WithKeyTable(table KeyTable) Subspace {
	if table.m == nil {
		panic("WithKeyTable() called with nil KeyTable")
	}
	if len(s.table.m) != 0 {
		panic("WithKeyTable() called on already initialized Subspace")
	}

	maps.Copy(s.table.m, table.m)

	// Allocate additional capacity for Subspace.name
	// So we don't have to allocate extra space each time appending to the key
	name := s.name
	s.name = make([]byte, len(name), len(name)+table.maxKeyLength())
	copy(s.name, name)

	return s
}`

## Recommended Mitigation Steps
To fix this bug, the code needs to be refactored to handle the initialization of KeyTable for multiple subspaces correctly.
