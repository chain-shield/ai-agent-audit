Creating Denoms would be impossible for valid subdenoms
Bauchibred
27
Sufficient
383d ago
Proof of Concept

In order to create a denom we need to validate the creation:

https://github.com/code-423n4/2024-11-mantra/blob/37dedf312c3ea161792b8e1278978db23bb5a8b0/x/tokenfactory/keeper/createdenom.go#L13-L26

func (k Keeper) CreateDenom(ctx sdk.Context, creatorAddr, subdenom string) (newTokenDenom string, err error) {
	denom, err := k.validateCreateDenom(ctx, creatorAddr, subdenom)
	if err != nil {
		return "", err
	}
// ..snip
}

Now take a look at https://github.com/code-423n4/2024-11-mantra/blob/37dedf312c3ea161792b8e1278978db23bb5a8b0/x/tokenfactory/keeper/createdenom.go#L55-L74


func (k Keeper) validateCreateDenom(ctx sdk.Context, creatorAddr, subdenom string) (newTokenDenom string, err error) {
	// Temporary check until IBC bug is sorted out
	if k.bankKeeper.HasSupply(ctx, subdenom) {//@audit this check should be temporary
		return "", fmt.Errorf("temporary error until IBC bug is sorted out, " +
			"can't create subdenoms that are the same as a native denom")
	}

	denom, err := types.GetTokenDenom(creatorAddr, subdenom)
	if err != nil {
		return "", err
	}

	_, found := k.bankKeeper.GetDenomMetaData(ctx, denom)
	if found {
		return "", types.ErrDenomExists
	}

	return denom, nil
}

This function is called in the CreateDenom func, which is called in the MsgServer implementation of the CreateDenom RPC method, which is called when a user wants to create a new denom, in short all it does is calidate that the denom rto be created is valid in Mantra's case.

Issue however is that by documentation the check below should be temporary, "until the IBC bug is sorted out":

https://github.com/code-423n4/2024-11-mantra/blob/37dedf312c3ea161792b8e1278978db23bb5a8b0/x/tokenfactory/keeper/createdenom.go#L57-L62

	// Temporary check until IBC bug is sorted out
	if k.bankKeeper.HasSupply(ctx, subdenom) {
		return "", fmt.Errorf("temporary error until IBC bug is sorted out, " +
			"can't create subdenoms that are the same as a native denom")
	}


That is, after sorting it out we should then allow for the creation of subdenoms that are the same as a native denom.

Impact

2 — Med: Assets not at direct risk, but the function of the protocol or its availability could be impacted, or leak value with a hypothetical attack path with stated assumptions, but external requirements.

Considering this is a DOS to valid attempts at creating denoms with valid subdenoms.

Recommended Mitigation Steps

Have a flag that the admin can set to subside this check when needed.

Pseudo implementation:

    }

CreateDenom.go

{{ ... }}

func (k Keeper) validateCreateDenom(ctx sdk.Context, creatorAddr, subdenom string) (newTokenDenom string, err error) {
    params := k.GetParams(ctx)

    // Only check for native denom collision if not explicitly allowed
    if !params.AllowNativeDenomSubdenoms {
        if k.bankKeeper.HasSupply(ctx, subdenom) {
            return "", fmt.Errorf("can't create subdenoms that are the same as a native denom while AllowNativeDenomSubdenoms is false")
        }
    }

    denom, err := types.GetTokenDenom(creatorAddr, subdenom)
    if err != nil {
        return "", err
    }

    _, found := k.bankKeeper.GetDenomMetaData(ctx, denom)
    if found {
        return "", types.ErrDenomExists
    }

    return denom, nil
}
