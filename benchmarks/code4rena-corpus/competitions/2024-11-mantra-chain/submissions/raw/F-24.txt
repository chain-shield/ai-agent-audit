S-167
DOS Issue Caused by Lack of Gas Limitation in callBeforeSendListener Function during blockBeforeSend
gxh191
00
Sufficient
383d ago

The callBeforeSendListener function is an on-chain contract hook handler in the Cosmos SDK, primarily used to invoke smart contracts under certain conditions.

However, when the blockBeforeSend flag is set, it directly calls contractKeeper.Sudo to send a message without enforcing any gas limit. This is a standard contract call and can lead to a potential Denial of Service issue. I will demonstrate this issue in the proof of concept.

https://github.com/code-423n4/2024-11-mantra/blob/main/x/tokenfactory/keeper/before_send.go#L130

func (k Keeper) callBeforeSendListener(ctx context.Context, from, to sdk.AccAddress, amount sdk.Coins, blockBeforeSend bool) (err error) {
	c := sdk.UnwrapSDKContext(ctx)

	defer func() {
		if r := recover(); r != nil {
			err = types.ErrTrackBeforeSendOutOfGas
		}
	}()

	for _, coin := range amount {
		contractAddr := k.GetBeforeSendHook(ctx, coin.Denom)
		if contractAddr != "" {
			cwAddr, err := sdk.AccAddressFromBech32(contractAddr)
			if err != nil {
				return err
			}

			var msgBz []byte

			if blockBeforeSend {
				msg := types.BlockBeforeSendSudoMsg{
					BlockBeforeSend: types.BlockBeforeSendMsg{
						From:   from.String(),
						To:     to.String(),
						Amount: CWCoinFromSDKCoin(coin),
					},
				}
				msgBz, err = json.Marshal(msg)
			} else {
				msg := types.TrackBeforeSendSudoMsg{
					TrackBeforeSend: types.TrackBeforeSendMsg{
						From:   from.String(),
						To:     to.String(),
						Amount: CWCoinFromSDKCoin(coin),
					},
				}
				msgBz, err = json.Marshal(msg)
			}
			if err != nil {
				return err
			}

			if blockBeforeSend { // <-------------------

				_, err = k.contractKeeper.Sudo(c, cwAddr, msgBz)
				if err != nil {
					return errorsmod.Wrapf(err, "failed to call before send hook for denom %s", coin.Denom)
				}
			} else {
				childCtx := c.WithGasMeter
				(types2.NewGasMeter(types.TrackBeforeSendGasLimit)) // <-----------------
				_, err = k.contractKeeper.Sudo(childCtx, cwAddr, msgBz)
				if err != nil {
					return errorsmod.Wrapf(err, "failed to call before send hook for denom %s", coin.Denom)
				}

				// consume gas used for calling contract to the parent ctx
				c.GasMeter().ConsumeGas(childCtx.GasMeter().GasConsumed(), "track before send gas")
			}
		}
	}
	return nil
}
Impact

The impact of this issue is significant and does not require much elaboration. My PoC can directly cause the entire chain to halt.

Fix Recommendation

The following fix has been tested and can prevent the vulnerability from occurring.

When gas limits are applied, running the PoC will result in the following output, indicating that the vulnerability has been successfully fixed:

rpc error: code = Unknown desc = rpc error: code = Unknown desc = failed to execute message; message index: 0: gas meter hit maximum limit [cosmos/cosmos-sdk@v0.50.10/baseapp/baseapp.go:1023] with gas used: '107761': unknown request

The fix is as follows: apply a gas limit for the blockBeforeSend case as well.

Additional Notes

This is not the same vulnerability as the one submitted in my setBeforeSendHook function. The causes and fixes for the two vulnerabilities are different.

Regarding the effects, the other vulnerability allows passing an un-deployed contract address or invalid contract content. It doesn’t necessarily involve passing a gas-exhausting WASM contract. However, this vulnerability specifically involves passing a WASM contract that continuously consumes gas, resulting in a DOS.

Simulation and block gas limits are not configured, skewing the PoC outcome
Edited: Feb 22
berndartmueller

At first sight, this submission seems legit, showing how the node is DoS'ed.

However, looking more closely shows that there IS a gas meter for bank coin send messages (as expected), which prevents unbounded wasm contract calls. Only begin/endblocker are not gas metered, hence the explicit gas meter with TrackBeforeSendGasLimit.

In Cosmos, RPCs configure a max. simulation gas limit (simulation_gas_limit), which is set to infinite for a fresh node without any pre-configured config. However, in this case, the consensus max block gas acts as the upper bound for tx simulations.

Such a simulation gas limit and consensus max block gas (max_gas) are not set for the local test node. This would certainly not be the case in production!

The warden's PoC tx uses --gas auto for the attack, which means the RPC needs to simulate the tx. Due to the infinite loop in the cosmwasm contract, this leads to an actual infinite loop in the RPC as there's no upper bound on the simulation gas (both simulation_gas_limit and max_gas as not adequately configured, contrary to how it would be in production). However, it does not affect the network, only this particular RPC, as the tx is not broadcasted to peers.

The issue description makes it seem as if there is no gas meter/limit at all when executing the bank send message, which is not the case. Regular Cosmos SDK tx's have a gas limit, and execution is metered. Not so for e.g. EndBlocker(). Also, the cosmwasm Sudo() keeper applies the same gas limit/meter logic as regular Execute() messages. Thus, the cosmwasm execution is gas-metered, otherwise it would open up a general DoS vector via potential infinite loops.

Overall, only a particular RPC instance is affected. In production, it must be assumed that the RPC has those gas limits in place, otherwise it would allow an attacker to DoS the RPC by simply calling a cosmwasm contract with an infinite loop.
