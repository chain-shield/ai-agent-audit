Less than MCA tax would be charged cumulatively causing a leak of value when allocating rewards to the MCA address
Bauchibred
27

Proof of Concept

In the BeginBlocker we query and distribute the rewards from the previous block:
https://github.com/code-423n4/2024-11-mantra/blob/37dedf312c3ea161792b8e1278978db23bb5a8b0/x/tax/module/abci.go#L10-L36

// BeginBlocker sets the proposer for determining distribution during endblock
// and distribute rewards for the previous block.
func BeginBlocker(ctx sdk.Context, k keeper.Keeper) error {
	defer telemetry.ModuleMeasureSince(types.ModuleName, telemetry.Now(), telemetry.MetricKeyBeginBlocker)

	params, err := k.Params.Get(ctx)
	if err != nil {
		return err
	}
	// if the mca tax is zero, no need to continue
	if params.McaTax.IsZero() {
		return nil
	}

	// only allocate rewards if the block height is greater than 1
	if ctx.BlockHeight() > 1 {
		McaAddress, err := sdk.AccAddressFromBech32(params.McaAddress)
		if err != nil {
			return err
		}
		if err := k.AllocateMcaTax(ctx, params.McaTax, McaAddress); err != nil {
			return err
		}
	}

	return nil
}

Mantra has already specified a default/max value for the mca tax which is 40%.

Issue however is that in the core logic of allocating the tax, we don't take into account the change coins (in this case could be called the remainder) and instead we just charge the full coins, see:

https://github.com/code-423n4/2024-11-mantra/blob/37dedf312c3ea161792b8e1278978db23bb5a8b0/x/tax/keeper/keeper.go#L72-L94

func (k Keeper) AllocateMcaTax(ctx context.Context, mcaTax math.LegacyDec, mcaAddress sdk.AccAddress) error {
	feeCollector := k.authKeeper.GetModuleAccount(ctx, k.feeCollectorName)
	feesCollectedInt := k.bankKeeper.GetAllBalances(ctx, feeCollector.GetAddress())
	feesCollected := sdk.NewDecCoinsFromCoins(feesCollectedInt...)

	mcaTaxAllocation, _ := feesCollected.MulDec(mcaTax).TruncateDecimal()//@audit here we completely forgo the change coins

	// transfer allocated mca tax to the specified account
	err := k.bankKeeper.SendCoinsFromModuleToAccount(ctx, k.feeCollectorName, mcaAddress, mcaTaxAllocation)
	if err != nil {
		return err
	}
	// emit event
	sdkCtx := sdk.UnwrapSDKContext(ctx)
	sdkCtx.EventManager().EmitEvent(
		sdk.NewEvent(
			types.EventTypeMcaTaxAmount,
			sdk.NewAttribute(sdk.AttributeKeyAmount, mcaTaxAllocation.String()),
			sdk.NewAttribute(types.AttributeKeyRecipient, mcaAddress.String()),
		),
	)
	return nil
}

As shown in the code snippet, when we we attempt get the amount to be distributed by the value of the current mcaTax, we completely forgo the change coins, keep in mind that the 'TruncateDecimal' method returns both the full coins and the change coins:

// TruncateDecimal returns the coins with truncated decimals and returns the
// change. Note, it will not return any zero-amount coins in either the truncated or
// change coins.
func (coins DecCoins) TruncateDecimal() (truncatedCoins Coins, changeCoins DecCoins) {
	for _, coin := range coins {
		truncated, change := coin.TruncateDecimal()
		if !truncated.IsZero() {
			truncatedCoins = truncatedCoins.Add(truncated)
		}
		if !change.IsZero() {
			changeCoins = changeCoins.Add(change)
		}
	}

	return truncatedCoins, changeCoins
}

Which would then mean that cumulatively we charge less than the MCA tax, since we don't take into account the change coins.

Now would be key to note that from the readMe of the contest specifying what's in scope for the audit, we can see a hint has been made for the custom implementation of Mantra:

https://github.com/code-423n4/2024-11-mantra/blob/37dedf312c3ea161792b8e1278978db23bb5a8b0/README.md#L26-L27

Which makes a call to https://github.com/cosmos/cosmos-sdk/blob/abc5fd0226abb7942e563ff8e71de4b8e8c6e127/x/distribution/keeper/allocation.go#L18-L91:

func (k Keeper) AllocateTokens(ctx context.Context, totalPreviousPower int64, bondedVotes []comet.VoteInfo) error {
	// fetch and clear the collected fees for distribution, since this is
	// called in BeginBlock, collected fees will be from the previous block
	// (and distributed to the previous proposer)
	feeCollector := k.authKeeper.GetModuleAccount(ctx, k.feeCollectorName)
	feesCollectedInt := k.bankKeeper.GetAllBalances(ctx, feeCollector.GetAddress())

	//..snip
	// send to community pool and set remainder in fee pool
	amt, re := remaining.TruncateDecimal()//@audit we take the change coins too into account here
	if err := k.bankKeeper.SendCoinsFromModuleToModule(ctx, types.ModuleName, types.ProtocolPoolDistrAccount, amt); err != nil {
		return err
	}

	if err := k.FeePool.Set(ctx, types.FeePool{DecimalPool: feePool.DecimalPool.Add(re...)}); err != nil {
		return err
	}

As evident, issue with Mantra's implementation in comparison to the original Cosmos implementation is that whereas in the latter's case we are taking into account the change and storing it, then sending it from time to time to the community pool, in Mantra's case we are not doing this at all for the change and instead we just forgo it, showcasing a leak of value for Mantra.

Impact

Loss of funds (leak of value) for the MCA address, considering as hinted under Proof of Concept, we always charge less than the specified MCA tax due to truncation, also note that with even more blocks this value becomes higher assuming the tax is not changed.

Recommended Mitigation Steps

Apply a similar approach as the one in the Cosmos implementation, i.e. take into account the change and store it and then once in a while, could be every 100 blocks however since the tax is high send the full balance of the accumulated change coins to the mcaAddress.

Hi 3doc, regarding your point about the change coins' value, to give a short scenario: AllocateMcaTax is called in every block's BeginBlocker. For simplicity, let's say Y is what we see as a significant value and each block has a small remainder X that gets truncated, where X = Y/100.

Now while X itself might seem insignificant, after 100 blocks we've actually withheld 100X from the MCA tax address.   And this is why the original Cosmos implementation in the distribution module explicitly tracks these remainders and periodically sends the accumulated amount to the community pool (every 1000 blocks). By not implementing a similar mechanism for the MCA tax, we're systematically reducing their entitled X% share over time which is relevant here as the cumulative effect becomes significant over the chain's lifetime.

  Also per the order of the beginBlockers() that get called for each module set in the app, we can see how this means the charge coins always gets sent to the fee collector from the remaining funds to then be distributed in the distribution module, showing how leak of funds on the Mac address is done over time.
