Invariant of not allowing transfers from modules is broken for the tax module
Bauchibred
27
Sufficient
383d ago
Proof of Concept

The Mantra protocol implements a core security feature that prevents direct transfers to and from module accounts just as with the forked cosomos-sdk, this is implemented in the down level when querying the sendCoinsFromAccountToModule & sendCoinsFromModuleToAccount, for e.g:

// SendCoinsFromModuleToAccount transfers coins from a ModuleAccount to an AccAddress.
// It will panic if the module account does not exist. An error is returned if
// the recipient address is black-listed or if sending the tokens fails.
func (k BaseKeeper) SendCoinsFromModuleToAccount(
	ctx context.Context, senderModule string, recipientAddr sdk.AccAddress, amt sdk.Coins,
) error {
	senderAddr := k.ak.GetModuleAddress(senderModule)
	if senderAddr == nil {
		panic(errorsmod.Wrapf(sdkerrors.ErrUnknownAddress, "module account %s does not exist", senderModule))
	}

	if k.BlockedAddr(recipientAddr) {
|>		return errorsmod.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", recipientAddr)
	}

	return k.SendCoins(ctx, senderAddr, recipientAddr, amt)
}

Now the implementation of the blockedAddr is meant to protect this logic from being assesed for module accounts, the documentation around this can be seem down in the cosmos-sdk:

The withdraw address cannot be any of the module accounts. These accounts are blocked from being withdraw addresses by being added to the distribution keeper's blockedAddrs array at initialization.

This is enforced also in the app.go via:

https://github.com/code-423n4/2024-11-mantra/blob/37dedf312c3ea161792b8e1278978db23bb5a8b0/app/app.go#L1233-L1257

// GetMaccPerms returns a copy of the module account permissions
func GetMaccPerms() map[string][]string {
	dupMaccPerms := make(map[string][]string)
	for k, v := range maccPerms {
		dupMaccPerms[k] = v
	}

	return dupMaccPerms
}

// BlockedAddresses returns all the app's blocked account addresses.
func BlockedAddresses() map[string]bool {
	modAccAddrs := make(map[string]bool)
	for acc := range GetMaccPerms() {
		modAccAddrs[authtypes.NewModuleAddress(acc).String()] = true
	}

	// allow the following addresses to receive funds
	delete(modAccAddrs, authtypes.NewModuleAddress(govtypes.ModuleName).String())

	return modAccAddrs
}


Issue however is that this logic is broken for MAntra, cause with Mantra asides the already forked modules from the base cosmos-sdk, there are new modules introduced by Mantra, to mention one is the tax module, which is where the problem is, cosindering it is not registered in the maccPerms map defined in app.go:

https://github.com/code-423n4/2024-11-mantra/blob/37dedf312c3ea161792b8e1278978db23bb5a8b0/app/app.go#L174-L194

var maccPerms = map[string][]string{
    authtypes.FeeCollectorName:     nil,
    distrtypes.ModuleName:          nil,
    minttypes.ModuleName:           {authtypes.Minter},
    stakingtypes.BondedPoolName:    {authtypes.Burner, authtypes.Staking},
    stakingtypes.NotBondedPoolName: {authtypes.Burner, authtypes.Staking},
    govtypes.ModuleName:            {authtypes.Burner},
    nft.ModuleName:                 nil,
    // non sdk modules
    ibctransfertypes.ModuleName:  {authtypes.Minter, authtypes.Burner},
    ibcfeetypes.ModuleName:       nil,
    ratelimittypes.ModuleName:    nil,
    wasmtypes.ModuleName:         {authtypes.Burner},
    tokenfactorytypes.ModuleName: {authtypes.Minter, authtypes.Burner},
    // @audit missing: tax module accounts
}

This omission means that the bank keeper's security checks to prevent transfers to/from module accounts are bypassed for these modules. The check that verifies whether an address belongs to a module account relies on the maccPerms map, and since these modules are not registered, their accounts are not recognized as module accounts,

Impact

High. This vulnerability allows for the breakage of a fundamental security invariant of chains/apps utilizing cosmos-sdk, note that in the documentation that's inherited we have a logic and multiple invariants that need to be strictly hekd for modules otherwise chains could be halted if any of the invariant is broken, one of which includes the funds tracking of modules:

The x/bank module accepts a map of addresses that are considered blocklisted from directly and explicitly receiving funds.
Typically, these addresses are module accounts. If these addresses receive funds outside the expected rules of the state machine, invariants are likely to be broken and could result in a halted network.

To go into more native details as to Mantra

Direct transfers to/from module accounts that should be blocked are now possible for the tax module
The protocol's fee collection and burning mechanisms is broken, considering for the former we easily have an issue with the accounting of tokens, and for the latter burning of tokens whereas should nto be possible for a module would actually succeed.

TLDR: The invariant of not transferring tokens from/to module accounts is broken for these two modules since Mantra forgot to register them under the maccPerms map.

To hint another issue would be the fact that the tax module is now erroneously allowed the logic to sign txs, cause during the tip refund when we send coins it wouldn't revert if the module is the recipient, which should not be a state that's allowed on the chain at all:

I think there can be more of a issue if these module accounts are used (receive or send tokens) for the chain accounting. The maccPerms list is for all generated accounts that receive and send tokens, that is why you see accounts like stakingtypes.NotBondedPoolName and stakingtypes.BondedPoolName as both are used by the chain. It is also why the list of maccPerms is much shorter than the number of cosmos-sdk base modules wired into app.go. Only module accounts that send receive tokens are added to this list.

It is not strictly for all modules that are part of the chain if their generated account will not be used.

The generated tax module account is not used so I see little to no impact for this, granted it is clearer to explicitly add all modules into the module account list.
