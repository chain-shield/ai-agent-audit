S-495
Underbilling due to lack of inclusion of token transfer associated bytes in the execution cost
hash
87
Sufficient
383d ago
Impact

Lower calculation of execution cost hence underbilling

Proof of Concept

Each byte that is part of a transaction's data will incur a gas cost in the destination chain. This is accounted in the execution cost by using the destGasPerPayloadByte which stores the gas for one byte of such data. But when calculating the execution cost, only the bytes of message.data is considered. This leaves out the bytes that will be populated in the transaction due to the token transfers and the bytes overhead associated with each token transfer (these are not included in tokenTransferGas as it only considers amount of gas that will be forwarded)

https://github.com/code-423n4/2024-11-chainlink/blob/69452f45335defa5b41aefd341bff26394aace8c/contracts/src/ccip/FeeQuoter.sol#L591-L596

    uint256 executionCost = uint112(packedGasPrice)
      * (
        destChainConfig.destGasOverhead + (message.data.length * destChainConfig.destGasPerPayloadByte) + tokenTransferGas
          + _parseEVMExtraArgsFromBytes(message.extraArgs, destChainConfig).gasLimit
      ) * destChainConfig.gasMultiplierWeiPerEth;
Recommended Mitigation Steps

Include the bytes that will be populated for the token transfers and each of their overhead bytes

I reported the issue in submission S-443. In that report, I consider that destGasOverhead accounts for the fixed-length bytes of a token transfer message, as this value remains constant regardless of the token.

However, I pointed out that the extraData field is dynamic and varies between token transfer messages depending on the token involved. This means a fixed value as destGasOverhead cannot account for extraData. I showed that this oversight results in a non-trivial loss, which is not merely a rounding error.
