user is able to frontrun DON thereby breaking a core invariant
mxuse

Description

inside the execute flow the following check gets made:

      if (manualExecution) {
        tokenGasOverrides = manualExecGasExecOverrides[i].tokenGasOverrides;
        bool isOldCommitReport = (block.timestamp - timestampCommitted) > s_dynamicConfig.permissionLessExecutionThresholdSeconds;
        // Manually execution is fine if we previously failed or if the commit report is just too old.
        // Acceptable state transitions: UNTOUCHED->SUCCESS, UNTOUCHED->FAILURE, FAILURE->SUCCESS.
        if (!(isOldCommitReport || originalState == Internal.MessageExecutionState.FAILURE)) {
          revert ManualExecutionNotYetEnabled(sourceChainSelector);
        }

This check simply ensures that the DON has permissionLessExecutionThresholdSeconds to perform execute before allowing the user to do so by calling ManuallyExecute.

However, an issue arises if there’s a pause on the chain, or any form of temporary halt. When the chain resumes, a user could potentially front-run the DON and execute their own transaction before the DON has a chance to do so.

this will compromise a core invariant, as per the sponsor's statement:

the nodes in the executing DON attempt to execute your message first and we don't want users to execute their message before the DON.

This scenario is likely, especially with v1.6, which aims to support a wide array of chains, both EVM and non-EVM.

Scenario:

A commit is made.
The permissionLessExecutionThresholdSeconds is set.
The chain pauses for a duration longer than permissionLessExecutionThresholdSeconds.(note that this can also happen due to chain cursing which makes this attack vector even more probable).
When the chain resumes, a user front-runs the DON by calling ManuallyExecute.
Consequently, the DON doesn’t get the opportunity to perform this execution.
Impact

now we do not think this should be classified as a high severity, however, it should suffice for a medium as it compromises a core mechanism of the protocol.

Recommendation

consider mitigating this issue.
