Keystone updates will expose rounding errors for +18 decimals tokens and can truncate to `0` for `36` decimals tokens.
Al-Qa-qa
62
Sufficient
383d ago
Pre Conditions

As stated in the README:

There's an increased risk of rounding errors when working with tokens with >36 decimals in the FeeQuoter.

The statement tills that rounding errors will increase for tokens greater than 36 decimals. Still, our issue will prove that even +18 decimals tokens (24, 30, 36) token decimals will subjected to large rounding. Even a token with 36 decimals (NOTE: do not exceed 36 decimals as the README said), can get truncated to make the value zero.

Description

When receiving Keystone price updates, the price fee decimals have a constant value equals 18, we send the token decimals and price we want to update and calculate rebasedValue value.

FeeQuoter.sol#L515-L516

  function onReport(bytes calldata metadata, bytes calldata report) external {
    ...
    for (uint256 i = 0; i < feeds.length; ++i) {
      ...
      // Keystone reports prices in USD with 18 decimals, so we passing it as 18 in the _calculateRebasedValue function.
>>    uint224 rebasedValue =
        _calculateRebasedValue(uint8(KEYSTONE_PRICE_DECIMALS), feedConfig.tokenDecimals, feeds[i].price);

      ...
    }
  }

When calculating the rebasedValue we use excess decimals to represent whether we will divide or multiply

FeeQuoter.sol#L730-L734

  function _calculateRebasedValue( ... ) internal pure returns (uint224 rebasedValue) {
    ...
    // If excessDecimals > 36 => flip it to feedValue / (10 ** (excessDecimals - 36)).
>>  uint8 excessDecimals = dataFeedDecimal + tokenDecimal;
    uint256 rebasedVal;

    if (excessDecimals > FEE_BASE_DECIMALS) {
>>    rebasedVal = feedValue / (10 ** (excessDecimals - FEE_BASE_DECIMALS));
    } else {
      rebasedVal = feedValue * (10 ** (FEE_BASE_DECIMALS - excessDecimals));
    }

    if (rebasedVal > type(uint224).max) {
      revert DataFeedValueOutOfUint224Range();
    }

    return uint224(rebasedVal);
  }

Since the keystone decimal is 18, any token with +18 decimals will be calculated using the divide formula.

Proof of Concept

Let's say there is a token that worth 0.5$, let's see what will result for different token decimals

Decimals	Value	Number of truncated zeros
24	0.5e18 / (10 ^ (42 - 36)) = 0.5e18 / 1e6 = 0.5e12	6
30	0.5e18 / (10 ^ (48 - 36)) = 0.5e18 / 1e12 = 0.5e6	12
36	0.5e18 / (10 ^ (54 - 36)) = 0.5e18 / 1e18 = 0.5 = 0	All

Since the price is not a constant number like 0.5e18, keystone prices will be variable and contains a lot of numbers, so tokens with +18 decimals will possess rounding risks, and even for tokens that have 36 decimals, the rebasedValue can get truncated to reach zero.

This will affect any token with +18 decimals when using keystone price updates, as keystone decimals is 18. And it will have effects for normal ChainLink Price Feed Aggregators for large decimals tokens like 36 decimals, or when the decimals of the aggregator is 18 decimals.

Recommendations

Increase FEE_BASE_DECIMALS value to occupy tokens with +18 decimals
