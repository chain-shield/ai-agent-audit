# Vulnerability details

## Impact
In the current `AxelarAmplifierGateway` smart contract, the `rotateSigners` method allows the operator (`operator`) role to frequently update the signer list without strict verification. Due to the special processing logic for `operator` in the `rotateSigners` method, the operator is allowed to bypass the minimum delay check for signer rotation and the latest signer verification, which means that if the `operator` role is malicious, or its private key is leaked, the malicious operator can update the signer list to the signers he controls without restriction, thereby taking over the control of the entire multi-signature account. This behavior may cause the assets in the multi-signature account to be illegally transferred or stolen, seriously endangering the security of the account.

## Proof of Concept

In the `rotateSigners` method, there is the following key logic:

```
function rotateSigners(WeightedSigners memory newSigners, Proof calldata proof) external {
    bytes32 dataHash = keccak256(abi.encode(CommandType.RotateSigners, newSigners));

    bool enforceRotationDelay = msg.sender != _axelarAmplifierGatewayStorage().operator;
    bool isLatestSigners = _validateProof(dataHash, proof);
    
    if (enforceRotationDelay && !isLatestSigners) {
        revert NotLatestSigners();
    }

    _rotateSigners(newSigners, enforceRotationDelay);
}
```
In this code, the `rotateSigners` method first calculates `dataHash`, then calls `_validateProof` to verify the validity of the signer, and returns `isLatestSigners` to indicate whether these signers are the latest. However, for the `operator` role, `enforceRotationDelay` is set to `false`, which means that the rotation delay will not be enforced, and the signer rotation operation will not be prevented even if `isLatestSigners` is `false`.
The detailed process is as follows:

1. **Call `rotateSigners` method**:
- If the caller is `operator`, `enforceRotationDelay` will be set to `false`, which means that the minimum delay for signer rotation will not be checked.
- Call the `_validateProof` method to verify the passed signature proof. If the verification fails, it will directly `revert`. But if `proof` is valid (even if it is not the latest signer), the operation can still proceed.
2. **_validateProof method**:
- `_validateProof` mainly checks whether `proof` is valid and whether the signer is the latest set of signers.
- If `signerEpoch` does not match `currentEpoch` and `previousSignersRetention` exceeds the limit, the verification will fail.
- Call the `_validateSignatures` method to verify the signature of each signer. If the signature verification fails, it will directly `revert`, otherwise return `true`.
3. **_rotateSigners method**:
- If all previous verifications pass, encode the new signer information into `newSignersData` and calculate the hash value `newSignersHash`.
- Update the current `epoch` and associate `newSignersHash` with the `epoch`.
- If `newSignersHash` already exists (duplicate signer set), then `revert`.
- Emits the `SignersRotated` event, indicating that the signer rotation is successful.

## Recommended Mitigation Steps

1. **Strictly control `operator` permissions**:
- A single `operator` should not be given too many permissions. A multi-signature mechanism should be considered to manage key roles and reduce the risk of single point failure.
- Regularly change the private key of `operator` to ensure the security of operator permissions.
2. **Enhance signature verification logic**:
- Add additional restrictions on `operator` behavior. Even the `operator` role needs to provide the latest signer verification proof to prevent it from bypassing signature verification.
- Allow the `rotateSigners` method to be called only when `proof` meets the conditions, instead of skipping the check directly.
3. **Implement rotation frequency limit**:
- Introduce rotation frequency limit in smart contracts to prevent `operator` from frequently updating the signer list.
- Record the time of each signer rotation and set a cool-down period to avoid continuous signer updates in a short period of time.
