# Vulnerability details


### Proof of Concept

Take a look at https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/axelar-amplifier/interchain-token-service/src/contract.rs#L84-L105

```rust
pub fn execute(
    deps: DepsMut,
    _: Env,
    info: MessageInfo,
    msg: ExecuteMsg,
) -> Result<Response, axelar_wasm_std::error::ContractError> {
    let msg = msg.ensure_permissions(deps.storage, &info.sender, match_gateway)?;

    match msg {
        ExecuteMsg::Execute { ..snip } => { ..snip },
        ExecuteMsg::UpdateTrustedAddress { chain, address } => {
            execute::update_trusted_address(deps, chain, address)
        }
    }?
    .then(Ok)
}
```

This function is expected to handle both `Execute` and `UpdateTrustedAddress` messages. However, the permission check is incorrect for `UpdateTrustedAddress`, which is because [the query to msg.ensure*permissions() is done for only the \_gateway* address.](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/axelar-amplifier/interchain-token-service/src/contract.rs#L91)

Now, take look at the `ExecuteMsg` enum definition:

https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/axelar-amplifier/interchain-token-service/src/msg.rs#L18-L30

```rust
#[cw_serde]
#[derive(EnsurePermissions)]
pub enum ExecuteMsg {
    #[permission(Specific(gateway))]
    Execute { ... },
    #[permission(Elevated)]
    UpdateTrustedAddress { chain: ChainName, address: Address },
}
```

The `UpdateTrustedAddress` variant is annotated with `#[permission(Elevated)]`, indicating it requires elevated permissions. However, the `execute` function only checks against the gateway address for all message types.

### Impact

This incorrect permission check leads to broken functionality for updating trusted addresses. Considering elevated address can not query `UpdateTrustedAddress` as intended. This severely limits the ability to update trusted addresses, especially in cases where:

1. The gateway address is compromised and needs to be changed.
2. There's a legitimate need to update the trusted address by an elevated permission holder who is not the gateway.

In essence, this bug renders the `UpdateTrustedAddress` functionality inaccessible to the intended elevated permission holders, potentially locking out legitimate administrative actions.

Note that from the implementation [here](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/axelar-amplifier/packages/axelar-wasm-std/src/permission_control.rs#L12-L22) we can understand how the _Elevated_ addresses are intended to be the Admins/Governance:

```rust
flags! {
    #[repr(u8)]
    #[derive(Serialize, Deserialize)]
    pub enum Permission: u8 {
        NoPrivilege = 0b001, // this specifies that the user MUST NOT have an elevated role
        Admin = 0b010,
        Governance = 0b100,
        Elevated = (Permission::Admin | Permission::Governance).bits(),
        Any = (Permission::NoPrivilege | Permission::Elevated).bits(),
    }
}
```

### Recommended Mitigation Steps

Modify the `execute` function to perform the correct permission check based on the message type. Here's a suggested implementation:

```diff
pub fn execute(
    deps: DepsMut,
    _: Env,
    info: MessageInfo,
    msg: ExecuteMsg,
) -> Result<Response, axelar_wasm_std::error::ContractError> {
-    let msg = msg.ensure_permissions(deps.storage, &info.sender, match_gateway)?;
+    let msg = match msg {
+        ExecuteMsg::Execute { .. } => msg.ensure_permissions(deps.storage, &info.sender, match_gateway)?,
+        ExecuteMsg::UpdateTrustedAddress { .. } => msg.ensure_permissions(deps.storage, &info.sender, check_elevated_permission)?,
    };


    match msg {
        ExecuteMsg::Execute { ..snip } => { ..snip },
        ExecuteMsg::UpdateTrustedAddress { chain, address } => {
            execute::update_trusted_address(deps, chain, address)
        }
    }?
    .then(Ok)
}
```

Then implement the `check_elevated_permission` function to properly verify elevated permissions.
