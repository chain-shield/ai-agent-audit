# Vulnerability details

## Impact
Function setup() in TokenManager.sol can be called again through the TokenManagerProxy contract's fallback function. This occurs since the setup() function only applies the onlyProxy() modifier and not the onlyOwner() as well. 

Due to this, any malicious actor can call the function setup() through the TokenManagerProxy contract to set a another address as the FLOW_LIMITER and OPERATOR. This allows the address to change the flow limit values to a small amount to DOS interchain transfers occurring through ITS for that specific interchain token as well as provides access to the transferFlowLimiter(), addFlowLimiter() and removeFlowLimiter() functions in TokenManager.sol to take over the interchain token and remove the current operator and flow limiter addresses as well as the ITS contract to DOS interchain transfer calls. 

Note, a similar instance also exists in the AxelarAmplifierGateway.sol contract, where the AxelarAmplifierGatewayProxy inherits the Proxy.sol contract which inherits the BaseProxy contract with the fallback function. Since anyone can call the setup() function through the proxy on the AxelarAmplifierGateway implementation contract, it would allow rotating signers without any delay to malicious signer addresses. This would allow forging and approving malicious messages. The solution suggested in this report needs to be applied to the internal setup() function in AxelarAmplifierGateway as well.

## Proof of Concept

1. Attacker calls the fallback function on the TokenManagerProxy.sol contract, which is present in the inherited BaseProxy.sol contract. The calldata passed would be setup() function selector with the bytes parameter containing the malicious operator address.

```solidity
    fallback() external payable virtual {
        address implementation_ = implementation();
        assembly {
            calldatacopy(0, 0, calldatasize())

            let result := delegatecall(gas(), implementation_, 0, calldatasize(), 0, 0)
            returndatacopy(0, 0, returndatasize())

            switch result
            case 0 {
                revert(0, returndatasize())
            }
            default {
                return(0, returndatasize())
            }
        }
    }
```

2. This delegatecalls to the setup() function in the TokenManager.sol implementation contract. The setup() function has an onlyProxy() modifier that ensures the call only occurs from the proxy contract. But the function does not restrict the msg.sender to be the owner of the contract with onlyOwner() modifier.

```solidity
function setup(bytes calldata params_) external override(Implementation, IImplementation) onlyProxy {
        bytes memory operatorBytes = abi.decode(params_, (bytes));

        address operator = address(0);

        if (operatorBytes.length != 0) {
            operator = operatorBytes.toAddress();
        }

        // If an operator is not provided, set `address(0)` as the operator.
        // This allows anyone to easily check if a custom operator was set on the token manager.
        
        _addAccountRoles(operator, (1 << uint8(Roles.FLOW_LIMITER)) | (1 << uint8(Roles.OPERATOR)));
        // Add operator and flow limiter role to the service. The operator can remove the flow limiter role if they so chose and the service has no way to use the operator role for now.
        _addAccountRoles(interchainTokenService, (1 << uint8(Roles.FLOW_LIMITER)) | (1 << uint8(Roles.OPERATOR)));
    }
```

3. Due to this, the attacker can setup the contract with a new operator and flow limiter, which causes the impact mentioned in the impact section. 

## Tools Used
Manual Review

## Recommended Mitigation Steps
Add the onlyOwner() modifier to the setup() function or if it is expected to only allow the function to be called once, add a one-time initialization check to it so that it can't be called again.
