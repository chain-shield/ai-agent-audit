# Vulnerability details

## Impact


The logic bug in the `route_incoming_messages` function is in the message verification process. The function checks if each incoming message exists in storage and matches the stored message, but it does not actually verify that the message has been approved or is ready for routing.

Specifically:
1. It only checks if the message exists and matches, but not its status.
2. There's no check to ensure the message has been properly verified before routing.
3. It allows routing of messages that may still be pending verification.

To fix this, the function should:
1. Check the status of each message (e.g., verified, pending, rejected).
2. Only allow routing of messages that have been fully verified and approved.
3. Reject or postpone routing for messages that are still pending or have been rejected.

This oversight could potentially allow unverified or unapproved messages to be routed, compromising the security and integrity of the cross-chain communication system.

## Proof of Concept


1. The function doesn't verify the message status before routing.
2. Messages are saved in `incoming_msg` storage upon `call_contract`, without verification.
3. `route_incoming_messages` can be called by anyone, not just the router.

Impact and PoC:
1. Attacker calls `call_contract` with malicious payload, which saves the message.
2. Attacker immediately calls `route_incoming_messages` with the same message.
3. The function finds the message in storage and routes it without verification.
4. This bypasses the entire verification process (Voting Verifier, etc.).
5. Malicious message gets routed to the destination chain via the router.
