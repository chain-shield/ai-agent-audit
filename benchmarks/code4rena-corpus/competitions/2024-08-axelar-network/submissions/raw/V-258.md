# Vulnerability details

## Vulnerability Details
The FlowLimit contract aims to limit token flow between chains within specific epochs (6-hour periods). The `_addFlow` function doesn't properly account for epoch transitions, which could allow bypassing the flow limit.

The function checks the current flow against the limit, but it doesn't reset the flow counters at the start of a new epoch. This could allow accumulating large flows over multiple epochs, potentially exceeding the intended limit.


## Code Snippet

```solidity
function _addFlow(uint256 flowLimit_, uint256 slotToAdd, uint256 slotToCompare, uint256 flowAmount) internal {
    uint256 flowToAdd;
    uint256 flowToCompare;

    assembly {
        flowToAdd := sload(slotToAdd)
        flowToCompare := sload(slotToCompare)
    }

    if (flowToAdd + flowAmount > flowToCompare + flowLimit_)
        revert FlowLimitExceeded((flowToCompare + flowLimit_), flowToAdd + flowAmount, address(this));
    if (flowAmount > flowLimit_) revert FlowLimitExceeded(flowLimit_, flowAmount, address(this));

    assembly {
        sstore(slotToAdd, add(flowToAdd, flowAmount))
    }
}
```

## Reproduction Steps

- Select a specific blockchain within the ITS and a token that is subject to flow limits.
- Initiate Transfer Near Epoch End
- Query the FlowLimit contract to obtain the current epoch's end time and the flow limit for the chosen token.
- Initiate a token transfer from the selected chain to another chain within the ITS, ensuring the transfer amount is close to the maximum allowed flow limit.
- Time the transfer such that it occurs shortly before the current epoch ends.
- Wait for the current epoch to end and a new epoch to begin. This can be monitored by checking the block timestamp against the - EPOCH_TIME constant (6 hours) in the FlowLimit contract.
- As soon as the new epoch starts, initiate another token transfer with the same amount as in step 2.


## Expected Outcome

The second transfer should fail, triggering the FlowLimitExceeded error, as it violates the flow limit for the new epoch.

## Actual Outcome

The second transfer succeeds, allowing the user to bypass the flow limit and transfer twice the intended amount within a short period, potentially disrupting the system's stability and integrity.


The root cause of the flow limit bypass vulnerability lies in the lack of epoch-based flow tracking and reset within the _addFlow function.

The _addFlow function's primary responsibility is to add a flow amount (either flow in or flow out) to the cumulative flow for the current epoch, while ensuring that the total flow doesn't exceed the predefined limit.

However, the function fails to explicitly consider epoch boundaries. It calculates the correct storage slot for the current epoch's flow amount but doesn't reset this amount when a new epoch begins.

Consequently, the flow amounts from the previous epoch persist into the new epoch. This allows a user to transfer the maximum allowed amount near the end of an epoch and then, as soon as the new epoch starts, transfer the same amount again. The contract treats these transfers as part of the same cumulative flow, even though they belong to different epochs, leading to a bypass of the flow limit.

The _addFlow function focuses solely on comparing the current flow against the limit within a single invocation. It lacks the crucial logic to enforce limits on a per-epoch basis, enabling the accumulation of flows across epochs and facilitating the bypass.


## Impact

Users could potentially transfer more tokens than intended over multiple epochs, undermining the purpose of the flow limit.

## Fix

Implement epoch checking and resetting in the `_addFlow` function
