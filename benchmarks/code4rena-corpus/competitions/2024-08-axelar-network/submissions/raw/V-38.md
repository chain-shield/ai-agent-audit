# Vulnerability details

### Description
Whenever messages need to be executed, the `execute` function is invoked. Inside this function, the `update_msg_status` method is called to transition the state of `msgs` from `APPROVED` to `EXECUTED`:

```javascript
pub(crate) fn execute(
    store: &mut dyn Storage,
    api: &dyn Api,
    querier: QuerierWrapper,
    cc_id: CrossChainId,
    payload: HexBinary,
) -> Result<Response, Error> {
===>    let msg = state::update_msg_status(store, cc_id.clone())
           .change_context(Error::MessageStatusUpdateFailed(cc_id))?;
```

Following this, the function carries out some additional checks until it reaches the end, where it processes the messages by invoking the `add_message` method and subsequently, an event is emitted that displays the messages to be executed

```javascript
    // Call the destination contract
    // Apps are required to expose AxelarExecutableMsg::Execute interface
    Ok(Response::new()
===>        .add_message(executable.execute(msg.cc_id.clone(), msg.source_address.clone(), payload))
===>        .add_event(AxelarnetGatewayEvent::MessageExecuted { msg }.into()))
}
```

The `add_message` function is responsible for pushing the now `EXECUTED` messages into a list of messages to be processed:

```javascript
 /// This creates a "fire and forget" message, by using `SubMsg::new()` to wrap it,
    /// and adds it to the list of messages to process.
    pub fn add_message(mut self, msg: impl Into<CosmosMsg<T>>) -> Self {
        self.messages.push(SubMsg::new(msg));
        self
    }
```

There is a discrepancy, however, between message status and actual processing. Messages are labeled as `EXECUTED` while still pending in the processing queue. As per the [Axelar Docs](https://docs.axelar.dev/dev/general-message-passing/monitoring):  `EXECUTED: informs the executed result whether it is successful or not.` In reality, messages marked as `EXECUTED` may still be awaiting processing and are therefore not finalised. 

As for the event, it will emit a `MessageExecuted` event, even though the message might still be in the processing phase and, in some cases, could remain stuck for a while. Despite this, the event will still indicate that the message has been executed.

As per the [README](https://code4rena.com/audits/2024-08-axelar-network#top):

```
- Does the message validation function accurately validate messages and update their status?
```

We believe our finding showcases that the message validation can reflect an incorrect status. 
### Recommendation
We recommend introducing logic that accurately reflects the state of a message when it is still in processing mode.
