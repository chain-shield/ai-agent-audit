# Vulnerability details

### Impact
There would be incorrect accounting of tokens when tokens are given out and taken in. 

## Proof of Concept
In the TokenHandler contract `giveToken` and `takeToken` has a critical behavior when dealing with tokens, it either tokens are given out or taken out but these functions incorrectly accounts for tokens going out and coming in. The `giveToken` is indeed a function designed to handle the transfer of tokens to specified address via the token service, and also for the `takeToken` which accepts tokens. 

```solidity
function giveToken(bytes32 tokenId, address to, uint256 amount) external payable returns (uint256, address) {
        address tokenManager = _create3Address(tokenId);

        (uint256 tokenManagerType, address tokenAddress) = ITokenManagerProxy(tokenManager).getImplementationTypeAndTokenAddress();

        /// @dev Track the flow amount being received via the message
        ITokenManager(tokenManager).addFlowIn(amount);   <---------------

        if (tokenManagerType == uint256(TokenManagerType.NATIVE_INTERCHAIN_TOKEN)) {
            _giveInterchainToken(tokenAddress, to, amount);
            return (amount, tokenAddress);
        }
```
```soldity
function takeToken(
        bytes32 tokenId,
        bool tokenOnly,
        address from,
        uint256 amount
    ) external payable returns (uint256, string memory symbol) {
        address tokenManager = _create3Address(tokenId);
        (uint256 tokenManagerType, address tokenAddress) = ITokenManagerProxy(tokenManager).getImplementationTypeAndTokenAddress();

        if (tokenOnly && msg.sender != tokenAddress) revert NotToken(msg.sender, tokenAddress);

        if (tokenManagerType == uint256(TokenManagerType.NATIVE_INTERCHAIN_TOKEN)) {
            _takeInterchainToken(tokenAddress, from, amount);
        } else if (tokenManagerType == uint256(TokenManagerType.MINT_BURN)) {
            _burnToken(tokenManager, tokenAddress, from, amount);
        } else if (tokenManagerType == uint256(TokenManagerType.MINT_BURN_FROM)) {
            _burnTokenFrom(tokenAddress, from, amount);
        } else if (tokenManagerType == uint256(TokenManagerType.LOCK_UNLOCK)) {
            _transferTokenFrom(tokenAddress, from, tokenManager, amount);
        } else if (tokenManagerType == uint256(TokenManagerType.LOCK_UNLOCK_FEE)) {
            amount = _transferTokenFromWithFee(tokenAddress, from, tokenManager, amount);
        } else if (tokenManagerType == uint256(TokenManagerType.GATEWAY)) {
            symbol = IERC20Named(tokenAddress).symbol();
            _transferTokenFrom(tokenAddress, from, address(this), amount);
        } else {
            revert UnsupportedTokenManagerType(tokenManagerType);
        }

        /// @dev Track the flow amount being sent out as a message
        ITokenManager(tokenManager).addFlowOut(amount);      <-----------
```

However, these function respectively tries to account for tokens that are sent *out* or *in* but uses the function that does this logic incorrectly, for example the `giveToken`.
The `giveToken` function, which is designed to send tokens to users across different chains, is currently invoking `addFlowIn(amount)` during the distribution process.  [addFlowIn](https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/interchain-token-service/contracts/TokenHandler.sol#L51) is intrinsically designed to track tokens that enter the system, not those that exit it. Consequently, this results in an inaccurate representation of the system's token reserves.

> Technical Manifestation:

- ***Initial Inconsistency: Upon distribution of tokens to a user, the system erroneously logs the outflow as an inflow. For instance, if 100 tokens are sent to a user, the addFlowIn(100) function increases the internal tracker as though the system has received an additional 100 tokens, instead of deducting the distributed amount.***
- ***Cascading Errors: As the process repeats, the system's internal balance progressively diverges from the actual state, leading to an inflated perception of available tokens.***

However, an egregious misapplication of the `addFlowIn` function has been identified. The function erroneously logs outgoing token distributions as incoming flows, leading to a severe discrepancy in the internal accounting of available tokens. 


> The functions addFlowIn and addFlowOut are used to track the flow of tokens in and out, respectively. They do not update token balances directly but rather keep track of the amount of tokens that have flowed into or out of the system. If say the net flow amount is 100 USDC incoming, sending 50 USDC out, will change it to 50 USDC incoming.


However the above functions doesn't handle use this tracking method adequately.

## Recommended Mitigation Steps
Replace the erroneous call to `addFlowIn` [within the giveToken](https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/interchain-token-service/contracts/TokenHandler.sol#L51) function with a newly defined `addFlowOut(amount)`function anf also vice-versa for `takeToken`. This function will accurately track the tokens exiting the system, ensuring that the internal accounting reflects the true state of token reserves.
