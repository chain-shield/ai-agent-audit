# Vulnerability details

## Vulnerability Details

The InterchainToken contract implements a custom _spendAllowance function to handle token allowances. The function's comment suggests that it should explicitly revert if the allowance is insufficient. However, the implementation relies on Solidity's built-in arithmetic underflow protection to handle insufficient allowances.

The _spendAllowance function is an internal function called during token transfers on behalf of a token holder. While it does prevent unauthorized spending, it does so in a manner inconsistent with its documentation.

## Code Snippet

https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/interchain-token-service/contracts/interchain-token/InterchainToken.sol#L135C14-L135C29

```solidity
 /**
     * @notice A method to be overwritten that will decrease the allowance of the `spender` from `sender` by `amount`.
     * @dev Needs to be overwritten. This provides flexibility for the choice of ERC20 implementation used. Must revert if allowance is not sufficient.
     */
    function _spendAllowance(address sender, address spender, uint256 amount) internal override {
        uint256 _allowance = allowance[sender][spender];

        if (_allowance != UINT256_MAX) {
            _approve(sender, spender, _allowance - amount);
        }
    }
```


Actual Behavior:
1. If the allowance is UINT256_MAX, it allows any amount to be spent (effectively infinite allowance).

2. For any other allowance value, it attempts to subtract the spent amount from the current allowance.

3. If the allowance is insufficient, the transaction reverts due to Solidity 0.8.0+'s built-in arithmetic underflow protection.


## Impact

The function correctly prevents unauthorized spending, but not in the way described in the comments.


## Scenario

1. Alice approves Bob to spend 100 tokens.
2. Bob attempts to transfer 150 tokens from Alice's account.
3. The transaction reverts due to arithmetic underflow, preventing the unauthorized spend.
4. However, the revert occurs without a clear error message explaining the reason for failure.


## Fix

```solidity
function _spendAllowance(address sender, address spender, uint256 amount) internal override {
    uint256 _allowance = allowance[sender][spender];

    if (_allowance != UINT256_MAX) {
        if (_allowance < amount) {
            revert InsufficientAllowance(sender, spender, amount, _allowance);
        }
        unchecked {
            _approve(sender, spender, _allowance - amount);
        }
    }
}

error InsufficientAllowance(address sender, address spender, uint256 requested, uint256 available);
```

This fix adds a crucial check to ensure the allowance is sufficient before updating it. If the allowance is less than the amount being spent, it reverts the transaction with a custom error message, providing clear information about the insufficient allowance.
