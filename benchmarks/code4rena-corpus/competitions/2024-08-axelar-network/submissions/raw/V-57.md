# Vulnerability details

## Description
The `postTokenManagerDeploy` function is invoked after a token manager has been deployed to finalize its setup. This function performs essential tasks depending on the tokenManagerType, ensuring that the token manager is properly configured to interact with other components of the system.

For token managers of types `LOCK_UNLOCK` and `LOCK_UNLOCK_FEE`, the `postTokenManagerDeploy` function calls the approveService method. This method is responsible for setting up necessary approvals, enabling the token manager to interact with other services or contracts, such as gateways or token services, which are crucial for handling token operations like locking, unlocking, and fee management.

## Proof of Concept
The `approveService` function relies on the ability to fetch the tokenAddress from the TokenManagerProxy contract. This address is essential for the function to authorize interactions between the token manager and other components of the system, such as gateways or service contracts
```solidity
    function postTokenManagerDeploy(uint256 tokenManagerType, address tokenManager) external payable {
        if (tokenManagerType == uint256(TokenManagerType.LOCK_UNLOCK) || tokenManagerType == uint256(TokenManagerType.LOCK_UNLOCK_FEE)) {
            ITokenManager(tokenManager).approveService();
        }

        // Approve the gateway here. One-time infinite approval works for gateway wrapped tokens, and for most origin tokens.
        // Approval can be refreshed in the future if needed for certain tokens via an upgrade, but realistically should never be exhausted.
        if (tokenManagerType == uint256(TokenManagerType.GATEWAY)) {
            address token = ITokenManager(tokenManager).tokenAddress();
            _approveGateway(token, UINT256_MAX);
        }
    }
```

In this scenario, the `TokenManagerProxy` contract, which acts as a proxy delegating calls to the actual implementation contract (TokenManager), does not define or store the tokenAddress function. Since the proxy is expected to delegate calls but does not contain the logic or storage of the tokenAddress, any attempt by approveService to access this function results in failure.


```solidity
function approveService() external onlyService {
        /**
         * @dev Some tokens may not obey the infinite approval.
         * Even so, it is unexpected to run out of allowance in practice.
         * If needed, we can upgrade to allow replenishing the allowance in the future.
         */
        IERC20(this.tokenAddress()).safeCall(abi.encodeWithSelector(IERC20.approve.selector, interchainTokenService, UINT256_MAX));
    }
```

The `TokenManagerProxy` typically uses delegatecall to execute functions in the context of the implementation contract (TokenManager). However, when approveService attempts to retrieve tokenAddress, it is expecting the proxy to return this value, which it cannot because the proxy does not store or define it.

```solidity

    /**
     * @notice Returns token address that this token manager manages.
     * @return address The token address.
     */
    function tokenAddress() external view returns (address); // not storing value of tokenAddress from it constructor just like, [getTokenImplementationandType](https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/interchain-token-service/contracts/proxies/TokenManagerProxy.sol#L61) 
```

Since the `delegatecall` executes within the proxy's context, the approveService function mistakenly believes that the tokenAddress should be available within the proxy's storage, leading to a failed operation when it is not found.

## Impact
Due to the flaw in `approveService`, the `postTokenManagerDeploy` function cannot correctly configure the necessary approvals for token managers of type LOCK_UNLOCK and LOCK_UNLOCK_FEE. This failure could lead to these token managers being unable to interact with other critical components, rendering them non-functional or partially functional.

Manual Review

## Recommended Mitigation Steps
A direct solution would involve defining the tokenAddress function within the TokenManagerProxy contract or ensuring that the proxy correctly delegates the call to the implementation contract where the tokenAddress is stored.

Alternatively, the system could be redesigned to ensure that the tokenAddress is always retrieved from the correct context, possibly by accessing it directly from the implementation contract rather than relying on the proxy.
