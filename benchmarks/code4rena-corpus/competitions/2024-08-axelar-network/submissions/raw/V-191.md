# Vulnerability details

## Impact

- The vulnerability allows an attacker to reuse valid signatures from a previous epoch, bypassing the intended security checks. This enables the execution of unauthorized transactions, potentially compromising the integrity and security of the entire multisig system. If exploited, the attacker could perform malicious actions such as unauthorized fund transfers, contract modifications, or any other critical operations that rely on multisig approval.

## Proof of Concept
Explanation:

 -   Initialization and Retention Setting:
        During contract deployment, the previousSignersRetention parameter is set, determining how many previous signer sets are considered valid.
        If this value is greater than 0, older signers can still authorize transactions, leading to the vulnerability.

-    Validation Logic in _validateProof Function:
        The _validateProof function checks the validity of signatures by comparing them against the signer set of the current or any previous epoch within the retention limit.
        The code fails to distinguish between the latest epoch's signers and those from previous epochs, provided the proof meets the required threshold.

-    Signature Replay Attack:
        An attacker can capture valid signatures from a previous epoch and reuse them within the valid retention period.
        Due to the lack of strict enforcement of current epoch signatures, the contract accepts these outdated signatures as valid, allowing unauthorized actions.

Steps to Reproduce:

-    Deploy the Contract:
        Set previousSignersRetention to a value greater than 0.

-    Generate and Capture Signatures:
        Capture a valid signature from an authorized transaction during the initial epoch.

-    Epoch Rotation:
        Rotate signers to a new epoch, updating the signer set.

-    Replay the Captured Signature:
        Use the captured signature from the previous epoch to authorize a new transaction.
-        Observe that the contract accepts this outdated signature, executing the transaction without the approval of the current signers.

## Recommended Mitigation Steps

-    Enforce Strict Epoch Validation:
        Modify the _validateProof function to ensure that only signatures from the latest signer set (current epoch) are accepted.
        Reject any signatures associated with outdated epochs, even if they fall within the previousSignersRetention window.

-    Signature Invalidation Post-Rotation:
        Implement logic to invalidate or mark as stale any signatures once an epoch rotation occurs, rendering them unusable even if retained for historical purposes.
