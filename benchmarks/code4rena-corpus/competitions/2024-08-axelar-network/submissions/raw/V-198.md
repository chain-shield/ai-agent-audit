# Vulnerability details

### Impact

Rewards from these rebasing tokens will be lost forever. Also on blast, where tokens USDB and WETH have their rewards set automatically to claimable, the protocol has made no configurations to handle the reward collection, which could lead to loss of funds.

### Proof of Concept

For context, the provided readme information states that all tokens are to be used, including tokens with balance modifications.

> Balance changes outside of transfers	In scope


In the `takeToken` function in TokenHandler.sol, we can see that for `LOCK_UNLOCK` token types, the tokens are transferred to the token manager from the sender where they're "locked" until they're unlocked later when needed.


Since it has been established that rebasing tokens and tokens with balance modifications can be in use, e.g stETH, these tokens when sent to the TokenManager will rabse, accruing rewards. Now, going through TokenMnaager.sol and TokenHandler.sol (or even ITS contracts), we can see that internal accounting is used to track amount transferred and amount received, meaning that the extra rebasing amounts will not be taken into consideration when dealing with these tokens. 

And if we look through TokenManager.sol, we'll see that there's no extra logic or sweep function to help recover any of these excess tokens, which as a result, will be lost.

Also, according to [axelarscan](https://axelarscan.io/resources/chains) which holds information about the chains on which the contracts will be deployed, blast is one of the chains supported, and blast provides yield mode. USDB and WETH on blast are have their yield modes set as automatic by default, so upon deployment to blast and transferring tokens to these tokens to the token manager, the accrued yield due to automatic rebasing is lost as they cannot be claimed. Also, due to the lack of configuration for blast, there's no way to change the yield mode of the tokens.

### Tools Used
Manual code review

### Recommended Mitigation Steps

Recommend implementing a balance tracking system, and potentially a receover token function that can skim off any excess tokens. Also on blast, consider add the ability to set native RebasingERC20 token status, following the [docs](https://docs.blast.io/building/guides/weth-yield).
