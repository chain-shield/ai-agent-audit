# Vulnerability details

## Vulnerability Details

The `permit` function is designed to allow users to approve token spending without sending a transaction, using a signed message instead. This is part of the ERC20Permit standard (EIP-2612).

The function increments the nonce after using it in the message digest calculation:

```solidity
keccak256(abi.encode(PERMIT_SIGNATURE_HASH, issuer, spender, value, nonces[issuer]++, deadline))
```

This creates a race condition where multiple valid signatures for the same nonce can be created and used.

## Code Snippet

```solidity
bytes32 digest = keccak256(
            abi.encodePacked(
                EIP191_PREFIX_FOR_EIP712_STRUCTURED_DATA,
                DOMAIN_SEPARATOR(),
                keccak256(abi.encode(PERMIT_SIGNATURE_HASH, issuer, spender, value, nonces[issuer]++, deadline))
            )
```

## Impact

This vulnerability allows for potential replay attacks. An attacker could use the same signature multiple times if they can front-run the original transaction. Each use would be considered valid because the nonce is only incremented after the signature verification.

## Scenario

1. Alice signs a permit for Bob to spend 100 tokens.

2. Bob sees this signed permit and submits a transaction to use it.

3. An attacker sees Bob's transaction in the mempool and front-runs it with a higher gas price.

4. The attacker's transaction succeeds, using Alice's permit.

5. Bob's original transaction still succeeds because the nonce check passes.

6. Alice's tokens are spent twice, despite only signing once.

## Fix

The nonce should be read and incremented atomically. Here's the corrected code:

```solidity
uint256 currentNonce = nonces[issuer];
nonces[issuer] = currentNonce + 1;
bytes32 digest = keccak256(
    abi.encodePacked(
        EIP191_PREFIX_FOR_EIP712_STRUCTURED_DATA,
        DOMAIN_SEPARATOR(),
        keccak256(abi.encode(PERMIT_SIGNATURE_HASH, issuer, spender, value, currentNonce, deadline))
    )
);
```
