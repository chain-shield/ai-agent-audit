# Vulnerability details


### Proof of Concept

Take a look at the `migrate` function in the contract implementation at https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/axelar-amplifier/contracts/axelarnet-gateway/src/contract.rs#L50-L56

```rust
#[cfg_attr(not(feature = "library"), entry_point)]
pub fn migrate(
    deps: DepsMut,
    _env: Env,
    _msg: Empty,
) -> Result<Response, axelar_wasm_std::error::ContractError> {
    // any version checks should be done before here

    cw2::set_contract_version(deps.storage, CONTRACT_NAME, CONTRACT_VERSION)?;

    Ok(Response::default())
}
```

Evidently, the only thing being processed in this function is a simple change of name/version, however upgrades/migrates could need logic to update states, which is not possible in the current implementation.

### Impact

`migrate()` does not include any logic for migrating or transforming the state from one version to another. This oversight can lead to several critical issues:

- If the state structure changes between versions, the contract would completely not function as intended with the new logic, leading to inconsistencies in how data is accessed or interpreted.
- Without proper migration logic, updating the state to match new requirements could result in loss of existing data or corruption of the state, making the contract unreliable.

### Recommended Mitigation Steps

- Add explicit state migration logic within the `migrate` function to transform the state from the old version to the new version.
- Before applying any state changes, ensure the contract is being migrated from a version that is compatible with the update. Use `cw2::get_contract_version` to retrieve the current version and compare it against the new version.
