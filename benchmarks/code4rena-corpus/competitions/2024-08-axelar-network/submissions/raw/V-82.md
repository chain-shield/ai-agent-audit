# Vulnerability details

## Impact

The malicious actors can use this vulnerability in order to steal user funds or cause denial-of-service depending to the vulnerability exists in the aimed contract in the supported chain. This can affect multiple chains because Axelar-Amplifier supports executing messages between different chains.  

## Proof of Concept
The execute_message() function is designed to block messages coming from untrusted addresses by default and it assures this condition by following check:
```
  if source_address != trusted_source_address {
        return Err(report!(Error::UntrustedAddress(source_address)));
  }
```
However,the malicious actors can bypass this check by calling update_trusted_address() function because this function will update an untrusted address as a trusted address and won't check if the caller is privileged to save an untrusted address as trusted, since there is no any permission check mechanism that verifies if the caller is admin or another privileged user in execute.rs.The  update_trusted_address() updates any arbitrary address as trusted without controlling.
```
pub fn update_trusted_address(
    deps: DepsMut,
    chain: ChainName,
    address: Address,
) -> Result<Response, Error> {
    save_trusted_address(deps.storage, &chain, &address)
        .change_context(Error::InvalidStoreAccess)?;

    Ok(
        Response::new()
            .add_event(ItsContractEvent::TrustedAddressUpdated { chain, address }.into()),
    )
}
```
The malicious actor should provide only two valid parameters with the untrusted address while calling update_trusted_address(). These parameters are storage and chain then update_trusted_address() function will successfully call save_trusted_address() function and it will validate any untrusted address by adding it into [TRUSTED_ITS_ADDRESSES](https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/axelar-amplifier/interchain-token-service/src/state.rs#L87) mapping.
```
pub(crate) fn save_trusted_address(
    storage: &mut dyn Storage,
    chain: &ChainName,
    address: &Address,
) -> Result<(), Error> {
    TRUSTED_ITS_ADDRESSES
        .save(storage, chain, address)
        .map_err(Error::from)
}
``` 
Even through state.rs has a function to remove any trusted address called [remove_trusted_address()](https://github.com/code-423n4/2024-08-axelar-network/blob/main/axelar-amplifier/interchain-token-service/src/state.rs#L121-L128),the issue above can result with the loss of funds before identifying and removing untrusted address.
This scenario can be simulated as bypassing the 
`assert!(err_contains!(result, Error, Error::UntrustedAddress(..)))` assertion of
[execute_message_untrusted_address](https://github.com/code-423n4/2024-08-axelar-network/blob/main/axelar-amplifier/interchain-token-service/src/contract/execute.rs#L260-L278) as modifying it as below : 
```
   #[test]
```

## Recommended Mitigation Steps
This issue can be resolved by ensuring that only privileged addresses can call update_trusted_address() by implementing a permission check mechanism in the update_trusted_address() function and execute.rs file.
