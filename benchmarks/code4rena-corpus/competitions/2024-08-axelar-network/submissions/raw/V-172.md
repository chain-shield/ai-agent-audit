## Proof of Concept

Take a look at https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/interchain-token-service/contracts/InterchainTokenService.sol#L562-L572

```solidity
    function setFlowLimits(bytes32[] calldata tokenIds, uint256[] calldata flowLimits) external onlyRole(uint8(Roles.OPERATOR)) {
        uint256 length = tokenIds.length;
        if (length != flowLimits.length) revert LengthMismatch();

        for (uint256 i; i < length; ++i) {
            ITokenManager tokenManager_ = ITokenManager(validTokenManagerAddress(tokenIds[i]));
            // slither-disable-next-line calls-loop
            tokenManager_.setFlowLimit(flowLimits[i]);
        }
    }

```

This function is used to set a flow limit for a token manager that has the service as its operator.

Now per the docs shared, we can see that these limits in some cases are intended to be used for emergency operations, CC: https://bright-ambert-2bd.notion.site/ITS-Token-Hub-External-dd30ee912d1e48e683d9488acf75e350#dbce267e19c14106ae1e096a36e8a49a

> ### Risks
>
> _Highlight risks so your reviewers can direct their attention here._
> A compromise of the token hub could allow various exploits ranging from taking over token deployments, arbitrary mint/burn/unlock of token on existing chains. Having said that, the current model of ITS essentially treats every connected chain as a hub, and thus a compromise on any connected chain puts all other chains at risk.
> The damage from a compromise can be reduced due to the centralized ability to disconnect/pause per chain connections, the ability to set flow rate limits.
> ..snip

Issue however is that due to the access control placed on the function for setting the flow limits, it [allows](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/interchain-token-service/contracts/InterchainTokenService.sol#L562) only the _OPERATOR_ to set the limit, but going to the implementation of [Operator.sol](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/interchain-token-service/contracts/utils/Operator.sol#), there is no functionality whatsoever to set this limit which then means that in an emergent situation the risk from a compromise can't be minimized via setting the flow limit.

## Impact

Intended functionality is broken, this is because in the case where any of the party is compromised/or if Axelar wants to place a limit for interchain transfers, the intention is to set this flow limit and then during the transfer there is a [check that reverts](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/interchain-token-service/contracts/utils/FlowLimit.sol#L103-L104) when the limit is passed.

However in our case since the limit can't be set, this then allows for maximum loss to be reached due to the black swan/ compromisation event.

## Recommended Mitigation Steps

Consider integrating a functionality in [Operator.sol](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/interchain-token-service/contracts/utils/Operator.sol#) that sets the limit.
