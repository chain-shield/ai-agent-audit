# Vulnerability details

## Vulnerability Details

The `_create3` function in the `Create3Fixed` contract aims to deploy contracts with deterministic addresses. While it includes checks to prevent overwriting existing contracts, there's an edge case that could potentially allow contract redeployment under specific circumstances.

## Code Snippet

https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/interchain-token-service/contracts/utils/Create3Fixed.sol#L28

```solidity
function _create3(bytes memory bytecode, bytes32 deploySalt) internal returns (address deployed) {
    deployed = _create3Address(deploySalt);
    if (bytecode.length == 0) revert EmptyBytecode();
    if (deployed.isContract()) revert AlreadyDeployed();
    // Deploy using create2
    CreateDeploy createDeploy;
    bytes memory createDeployBytecode_ = CREATE_DEPLOY_BYTECODE;
    uint256 length = createDeployBytecode_.length;
    assembly {
        createDeploy := create2(0, add(createDeployBytecode_, 0x20), length, deploySalt)
    }
    if (address(createDeploy) == address(0)) revert DeployFailed();
    // Deploy using create
    createDeploy.deploy(bytecode);
}
```

The function includes a check `if (deployed.isContract()) revert AlreadyDeployed();` to prevent deployment to an address that already contains a contract. However, this check may not be sufficient in the following scenario:

1. A contract is deployed to address A using `_create3`.
2. The contract at address A self-destructs.
3. An attacker attempts to deploy a new contract to address A using the same `deploySalt`.

In this case, the `isContract()` check might not detect the previous existence of a contract at that address, potentially allowing redeployment.

## Impact

1. **Integrity of Deterministic Addresses**: The core premise of using deterministic addresses could be compromised in specific scenarios.
2. **Potential for Malicious Redeployment**: In cases where the original contract held critical roles or permissions, a malicious redeployment could lead to unauthorized control or access.
3. **Confusion and Inconsistency**: Users or other contracts interacting with the supposedly immutable address might encounter unexpected behavior if the contract is replaced.

## Scenario

1. Deploy Contract A using `_create3` with a specific `deploySalt`.
2. Contract A self-destructs.
3. Attempt to deploy Contract B using `_create3` with the same `deploySalt`.
4. Observe that the deployment succeeds, replacing the original contract at the same address.

## Recommended Mitigation

1. Implement a more comprehensive check that can detect the historical existence of a contract at the target address. This could involve maintaining a separate mapping of deployed addresses or using a more sophisticated checking mechanism.

2. Consider adding a time-lock or cooldown period for redeployments to the same address, allowing for intervention if unintended redeployments are detected.
