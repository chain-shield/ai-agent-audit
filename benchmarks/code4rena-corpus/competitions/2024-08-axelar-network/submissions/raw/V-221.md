# Vulnerability details

## Vulnerability Details
The current implementation of the _validateProof function does not adequately protect against replay attacks across different epochs. While the function checks if the signers' epoch is within a valid range, it does not prevent the reuse of a legitimate proof from a previous epoch. This oversight could potentially allow an attacker to replay old, but still valid, proofs to authorize actions in newer epochs, even if the signers are no longer authorized.

The vulnerability could lead to severe security breaches, allowing unauthorized actions to be performed on the contract. This is particularly dangerous in systems where signer rotations or permission changes occur between epochs.

if (signerEpoch == 0 || currentEpoch - signerEpoch > previousSignersRetention) revert InvalidSigners();

This code checks if the signers in the proof belong to a valid epoch (either the current one or within the retention period). However, it doesn't explicitly prevent the reuse of a valid proof from a previous epoch.

## Scenario

A valid multisig proof is generated and used successfully for a transaction or operation at epoch X.
The signers are rotated, and the system moves to a new epoch X+1.
An attacker attempts to reuse the proof from epoch X for a new transaction in epoch X+1.

Since the proof is still within the previousSignersRetention period, the _validateProof function would consider it valid, even though the signers might no longer be authorized in the current epoch. This could lead to unauthorized actions being performed.

## Fix

Introduce a mechanism to tie a proof to a specific epoch or transaction. One possible approach is to include a nonce or transaction identifier in the data being signed.

function messageHashToSign(bytes32 signersHash, bytes32 dataHash, uint256 nonce) public view returns (bytes32) {

}
