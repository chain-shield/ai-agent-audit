# Vulnerability details

# Arbitrary Message Approval in AxelarAmplifierGateway

## Impact
The `approveMessages` function in the `AxelarAmplifierGateway` contract allows any account to approve arbitrary messages if they can provide a valid proof. This vulnerability can be exploited by an attacker who obtains a valid proof through other means, such as a separate vulnerability, social engineering, or leaked keys.

Potential impacts include:
- Fraudulent token transfers that drain funds from bridge reserves
- Network congestion due to spam messages approved by the attacker
- Exploitation of vulnerabilities in destination chain contracts via crafted message payloads

The vulnerability poses a significant risk to the security and integrity of the Axelar Network. Malicious messages approved by an attacker can lead to substantial financial losses and damage the protocol's reputation.

## Proof of Concept
The vulnerable `approveMessages` function can be found in the `AxelarAmplifierGateway` contract:
[AxelarAmplifierGateway.sol#L80-L85](https://github.com/code-423n4/2024-08-axelar-network/blob/main/axelar-gmp-sdk-solidity/contracts/gateway/AxelarAmplifierGateway.sol#L80-L85)

Here's a Hardhat test that demonstrates the vulnerability:

```javascript
const { expect } = require("chai");
const { ethers } = require("hardhat");

describe("AxelarAmplifierGateway arbitrary message approval", function () {
  it("Should allow an attacker to get arbitrary messages approved with a valid proof", async function () {
    // Deploy the AxelarAmplifierGateway contract
    const Gateway = await ethers.getContractFactory("AxelarAmplifierGateway");
    const gateway = await Gateway.deploy(0, ethers.constants.HashZero, 0);
    await gateway.deployed();

    // Attacker generates malicious messages
    const maliciousMessages = [
      {
        sourceChain: "chainA", 
        messageId: "1",
        sourceAddress: attacker.address,
        contractAddress: gateway.address,
        payloadHash: ethers.constants.HashZero
      },
      // ... more malicious messages
    ];
    
    // Simulate attacker obtaining a valid proof (this would be done through other means in reality)
    const validProof = {
      signers: [], 
      threshold: 0,
      signatures: []
    };

    // Attacker calls approveMessages directly on the gateway contract
    await gateway.approveMessages(maliciousMessages, validProof);

    // Check that the malicious messages were approved
    expect(await gateway.isMessageApproved(
      maliciousMessages[0].sourceChain,
      maliciousMessages[0].messageId,
      maliciousMessages[0].sourceAddress, 
      maliciousMessages[0].contractAddress,
      maliciousMessages[0].payloadHash
    )).to.be.true;

    // ... check more messages
  });
});
```

## Recommended Mitigation Steps
1. Restrict access to the `approveMessages` function by making it `internal` or adding appropriate modifiers (e.g., `onlyOwner`, `onlyOperator`). Only trusted entities should be allowed to approve messages.

2. Implement additional validation checks on the messages being approved. Verify the authenticity, integrity, and validity of the message contents, origins, and destinations. Reject any messages that fail these checks.

3. Consider incorporating mechanisms to ensure the freshness of the provided proofs, such as including timestamps or nonces. This can help prevent replay attacks where an attacker reuses old valid proofs.

4. Implement robust monitoring and alerting systems to detect and respond to any suspicious activities or anomalies in message approvals.
