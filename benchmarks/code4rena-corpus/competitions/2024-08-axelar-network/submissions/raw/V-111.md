# Vulnerability details

### Description
Building the proof for `RotateSigners` happens [here](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/axelar-amplifier/contracts/multisig-prover/src/msg.rs#L62-L79): 

After this anyone is able to [query](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/axelar-amplifier/contracts/multisig-prover/src/msg.rs#L84-L94) the proof

This proof will be used inside `RotateSigners` which anyone is able to call, inside this function `_rotateSigners` is invoked:

```javascript
    function _rotateSigners(WeightedSigners memory newSigners, bool enforceRotationDelay) internal {
        BaseWeightedMultisigStorage storage slot = _baseWeightedMultisigStorage();

        _validateSigners(newSigners);

        _updateRotationTimestamp(enforceRotationDelay);

        bytes memory newSignersData = abi.encode(newSigners);
        bytes32 newSignersHash = keccak256(newSignersData);

        // assign the next epoch to the new signers
        uint256 newEpoch = slot.epoch + 1;
        slot.epoch = newEpoch;
        slot.signerHashByEpoch[newEpoch] = newSignersHash;

        // signers must be distinct, since nonce should guarantee uniqueness even if signers are repeated
=>        if (slot.epochBySignerHash[newSignersHash] != 0) revert DuplicateSigners(newSignersHash);

        slot.epochBySignerHash[newSignersHash] = newEpoch;

        emit SignersRotated(newEpoch, newSignersHash, newSignersData);
    }


```

This function will fail if the same `newSignerHash` is used, which comes down to the same exact signer set. This prevents a rotation to a duplicated signer set. 

Whenever a contract upgrade needs to be invoked function `_setup` will be inside this flow:

```javascript
    function _setup(bytes calldata data) internal override {
        (address operator_, WeightedSigners[] memory signers) = abi.decode(data, (address, WeightedSigners[]));

        // operator is an optional parameter. The gateway owner can set it later via `transferOperatorship` if needed.
        // This also simplifies setup for upgrades so if the current operator doesn't need to be changed, then it can be skipped, instead of having to specify the current operator again.
        if (operator_ != address(0)) {
            _transferOperatorship(operator_);
        }

        for (uint256 i = 0; i < signers.length; i++) {
=>            _rotateSigners(signers[i], false);
        }
    }
```

Inside here `_rotateSigners` is also called, this will fail if a repeat signer set is used. 

With all of this in mind the following can happen:

- The gateway owner decides to perform an upgrade which invokes `_setup` and plans to rotate to a new signer set B.
- A malicious user frontruns this by calling `RotateSigners`, rotating to the exact same signer set B.
- Because of this, the upgrade will fail since the malicious user frontran and set the signer set to B, causing the gateway owner's call to be perceived as a repeated signer set.
- The upgrade ultimately fails.

Note that this can also happen without any malicious intent, although unlikely, it can happen which will cause an upgrade to fail.

### Recommendation
whenever upgrading, the codebase could allow using a repeated signer set. Alternatively, different logic could be implemented to handle such scenarios.
