# Vulnerability details

## Description
The InterchainTokenFactory and InterchainTokenService contracts have a bridging payment logic on that decouples the msg.value from the desired payment amount.
Take a look at the deployRemoteInterchainToken function at the InterchainTokenFactory contract:
```solidity
function deployRemoteInterchainToken(
        string calldata originalChainName,
        bytes32 salt,
        address minter,
        string memory destinationChain,
        uint256 gasValue
    ) external payable returns (bytes32 tokenId) {
    ...
    tokenId = _deployInterchainToken(salt, destinationChain, tokenName, tokenSymbol, tokenDecimals, minter_, gasValue);
    }
```

It also happens at the deployTokenManager function at the InterchainTokenFactory contract:
```solidity
function deployTokenManager(
        bytes32 salt,
        string calldata destinationChain,
        TokenManagerType tokenManagerType,
        bytes calldata params,
        uint256 gasValue
    ) external payable whenNotPaused returns (bytes32 tokenId) {
    ...
    _deployRemoteTokenManager(tokenId, destinationChain, gasValue, tokenManagerType, params);
        }
    }
```
It doesn't sanity check msg.value, nor if it is worth at least the gasValue uint256.
## Impact
It is known the gateway will refund the excess payment made to bridge a message - if a user, however, sends a msg.value that is greater than gas value, he/she will not receive refunds for this difference.

Any native token left at the InterchainTokenService and at the InterchainTokenFactory contracts can be permissionless spent by any caller to pay for bridging a message. 
## Tools Used
Manual review
## Recommended Mitigation
Make sure to sanity check if the gasValue uint256 variable is equal to the msg.value, otherwise revert. This option would be optimal if maintaining the function's interface is crucial.
A second option would be to remove the gasValue parameter altogether from the function and utilize the native msg.value as the accounting mechanism.
