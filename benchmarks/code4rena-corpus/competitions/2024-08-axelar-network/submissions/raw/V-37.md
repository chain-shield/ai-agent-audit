# Vulnerability details

### Description 
When a user wants to register a canonical token as an interchain token, they can do so by calling the `registerCanonicalInterchainToken` function and providing the `tokenAddress`. As per the [Axelar Docs](https://docs.axelar.dev/dev/send-tokens/interchain-tokens/upgrade-tokens#canonical-tokens-simple-wrappers): This will deploy a [Lock/Release](https://docs.axelar.dev/dev/glossary#lockunlock) - [Token Manager](https://docs.axelar.dev/dev/glossary#token-manager) on the source chain. 

Note that the [Lock/Release](https://docs.axelar.dev/dev/send-tokens/glossary#lockunlock) section does not make any distinction between `LOCK_UNLOCK` & `LOCK_UNLOCK_FEE`, the code however is clear in its difference. The latter is simply used for tokens that have a FOT behaviour. 

```javascript
        LOCK_UNLOCK_FEE, // The token will be locked/unlocked at the token manager, which will account for any fee-on-transfer behaviour.
```

If we now look at the `registerCanonicalInterchainToken` function we can see that the passed `TokenManagerType` will always be set to `LOCK_UNLOCK`:

```javascript
    function registerCanonicalInterchainToken(address tokenAddress) external payable returns (bytes32 tokenId) {
        bytes memory params = abi.encode('', tokenAddress);

        if (_isGatewayToken(tokenAddress)) revert GatewayToken(tokenAddress);

        bytes32 salt = canonicalInterchainTokenSalt(chainNameHash, tokenAddress);
        tokenId = interchainTokenService.deployTokenManager(salt, '', =>TokenManagerType.LOCK_UNLOCK, params, 0);
    }
```

This behaviour is intentional because, as previously mentioned, only lock/release tokens can be registered as canonical interchain tokens.

However, there's an issue: users have no way of knowing that this function only accepts `LOCK_UNLOCK` tokens and do not support `LOCK_UNLOCK_FEE` tokens. The documentation does not clarify this, and as we analyse the function's flow, it has no check to ensure only `LOCK_UNLOCK` tokens are being used. Instead, it always sets the `tokenManagerType` to `LOCK_UNLOCK`, assuming this is the only type that will be used

This can lead to the following scenario:

- Bob calls `registerCanonicalInterchainToken` with a token of the `LOCK_UNLOCK_FEE` type.
- Bob expects the function to work, assuming that since the token is of a Lock/Release type, it should be supported. There’s no indication or check suggesting otherwise; on the contrary, the documentation states that Lock/Release tokens are supported.
- Due to the hardcoded parameter, the token will be deployed as `LOCK_UNLOCK` instead of `LOCK_UNLOCK_FEE`.
- Bob ends up with a deployed FOT token of the `LOCK_UNLOCK` type, contrary to his expectations.

The token logic will now cause for issues, for example, whenever transfers happen by invoking `transferTokenFrom` the following check is made:

```javascript
   function transferTokenFrom(bytes32 tokenId, address from, address to, uint256 amount) external payable returns (uint256, address) {
        address tokenManager = _create3Address(tokenId);
        (uint256 tokenManagerType, address tokenAddress) = ITokenManagerProxy(tokenManager).getImplementationTypeAndTokenAddress();

        if (
            tokenManagerType == uint256(TokenManagerType.NATIVE_INTERCHAIN_TOKEN) ||
            tokenManagerType == uint256(TokenManagerType.LOCK_UNLOCK) ||
            tokenManagerType == uint256(TokenManagerType.MINT_BURN) ||
            tokenManagerType == uint256(TokenManagerType.MINT_BURN_FROM) ||
            tokenManagerType == uint256(TokenManagerType.GATEWAY)
        ) {
            _transferTokenFrom(tokenAddress, from, to, amount);
            return (amount, tokenAddress);
        }

=>        if (tokenManagerType == uint256(TokenManagerType.LOCK_UNLOCK_FEE)) {
            amount = _transferTokenFromWithFee(tokenAddress, from, to, amount);
            return (amount, tokenAddress);
        }

        revert UnsupportedTokenManagerType(tokenManagerType);
    }
```

This check ensures that the appropriate transfer method is used, as FOT tokens require a specialised transfer process (in this case, `_transferTokenFromWithFee`) However, since the token is designated as `LOCK_UNLOCK`, it will default to using the `_transferTokenFrom` method.

This will lead to an inaccurate reflection of the `amount`, as the fees are included in the `amount` due to the use of the default transfer method.

It will also cause problems with any process that involves `takeToken`, as `takeToken` includes the following check:
```javascript

//..Ommitted code

```

It will once again ascribe the incorrect transfer method. 
### Recommendation
The `registerCanonicalInterchainToken` function should include a check to determine if the provided `tokenAddress` is of the FOT type. If it is, the function should not be allowed to proceed. Alternatively, create some other logic to prevent this from happening.
