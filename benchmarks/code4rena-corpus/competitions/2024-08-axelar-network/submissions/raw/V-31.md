# Vulnerability details

## Impact
[transferFrom](https://github.com/code-423n4/2024-08-axelar-network/blob/main/interchain-token-service/contracts/interchain-token/ERC20.sol#L80) does not handle approval right, and will reduce the allowance of `sender`, even if sender is `msg.sender`. This will result in revert as some of our contracts need to approve themselves.

## Proof of Concept
[transferFrom](https://github.com/code-423n4/2024-08-axelar-network/blob/main/interchain-token-service/contracts/interchain-token/ERC20.sol#L80) is incorrectly coded, because it is made to request approvals at all times. However this should not be the case when `msg.sender == sender`. There should be no need for msg.sender to approve himself before calling `transferFrom`.

```diff
    function transferFrom(address sender, address recipient, uint256 amount) external virtual override returns (bool) {
        uint256 _allowance = allowance[sender][msg.sender];
        if (_allowance != UINT256_MAX) {
            _approve(sender, msg.sender, _allowance - amount);
        }

        _transfer(sender, recipient, amount);

        return true;
    }
```

TokenHandler uses [_transferTokenFrom](https://github.com/code-423n4/2024-08-axelar-network/blob/main/interchain-token-service/contracts/TokenHandler.sol#L177-L180) in multiple places and in some cases it transfers tokens from himself to other contract. However code that grants approval to himself, resulting in some calls failing.

## Recommended Mitigation Steps

```diff
    function transferFrom(address sender, address recipient, uint256 amount) external virtual override returns (bool) {
        uint256 _allowance = allowance[sender][msg.sender];
-       if (_allowance != UINT256_MAX) {
+       if (msg.sender != sender && _allowance != UINT256_MAX) {
            _approve(sender, msg.sender, _allowance - amount);
        }

        _transfer(sender, recipient, amount);

        return true;
    }
```
