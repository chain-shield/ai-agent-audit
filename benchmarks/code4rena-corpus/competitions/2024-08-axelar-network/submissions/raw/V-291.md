# Vulnerability details

## Impact

Function `deployInterchainToken` is supposed to mint to `minter`, so it can immediately perform its duty. In fact, the initial supply is minted to `msg.sender`. This is not acceptable in case of mint/burn tokens since the sender can be delegated by `minter` who has real ownership of the token. The `msg.sender` may or may not decide to transfer tokens to `minter`.
## Proof of Concept

Despite comments stating that the initial supply is ditributed to `minter` parameter, it is distributed to `msg.sender`. The `minter` only receives mintership.

interchain-token-service/contracts/InterchainTokenFactory.sol
```
    /**
     * @notice Deploys a new interchain token with specified parameters.
...
     * @param minter The address to receive the initially minted tokens.
...
    function deployInterchainToken(
        bytes32 salt,
        string calldata name,
        string calldata symbol,
        uint8 decimals,
        uint256 initialSupply,
        address minter
    ) external payable returns (bytes32 tokenId) {
...
            token.mint(sender, initialSupply);

            token.transferMintership(minter);
...
        }
    }
```

This behaviour is even covered by a test case, see `wallet` instead of `minter`.

If we change the line
```
expect(await token.balanceOf(wallet.address)).to.equal(mintAmount);  
```
to
```
expect(await token.balanceOf(minter.address)).to.equal(mintAmount);  
```
the test case fails.
