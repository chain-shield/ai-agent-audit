# Vulnerability details

cription
A significant security flaw within the `callContract` function where the tx.origin is erroneously utilized as the refundAddress when invoking the `payNativeGasForContractCall` function. This improper use of `tx.origin` introduces a substantial risk of exploitation through phishing, reentrancy, and other malicious activities. The issue arises because tx.origin, representing the original external account that initiated the transaction, is inappropriately assigned to the refundAddress parameter, which governs the destination for gas refunds. 

This spans across so many Gas service providers [1](https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/interchain-token-service/contracts/utils/GatewayCaller.sol#L51), [2](https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/interchain-token-service/contracts/utils/GatewayCaller.sol#L61), [3](https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/interchain-token-service/contracts/utils/GatewayCaller.sol#L101) and [4](https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/interchain-token-service/contracts/utils/GatewayCaller.sol#L113)

***Using `tx.origin` as the `refundAddress` assumes that the original transaction initiator (an externally owned account, or EOA) is the correct recipient for any refunds. However, this assumption is flawed because an attacker can craft a malicious contract that tricks users into initiating a transaction. The transaction's `tx.origin` would be the user's address, but the attacker’s contract could manipulate the transaction flow, causing the refund to be unintentionally directed elsewhere.***


If an attacker manages to reenter the contract through recursive calls, tx.origin would remain constant across these calls, while `msg.sender` would vary depending on the caller in each execution context. This could allow an attacker to drain funds by repeatedly triggering refund mechanisms with their own address as the origin.

***The use of `tx.origin` instead of `msg.sender` deviates from best practices in Solidity programming. msg.sender represents the immediate caller of the function, making it a more reliable and secure method of identifying the party responsible for the transaction. Using tx.origin can lead to scenarios where the original EOA is not the intended recipient of the refund, leading to unintentional fund misallocation.***

## Impact
Attackers can exploit this flaw to redirect refunds to themselves, siphoning funds away from the rightful recipients. This can result in significant financial losses, particularly in a high-value contract environment where substantial amounts of gas fees might be refunded.

## Recommended Mitigation Steps
Replace `tx.origin` with `msg.sender`

The refundAddress should be set to msg.sender, which correctly identifies the immediate caller of the callContract function. This ensures that the refund is directed to the entity that directly interacts with the contract, minimizing the risk of misdirection.
```solidity
gasService.payNativeGasForContractCall{ value: gasValue }(
    address(this),
    destinationChain,
    destinationAddress,
    payload,
    msg.sender // Safer approach to determine refundAddress
);
```
