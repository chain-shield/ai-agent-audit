# Vulnerability details

## Vulnerability Details

The _validateSignatures function within the BaseWeightedMultisig contract aims to ensure the validity and sufficiency of multi-signatures. However, an edge case may allow redundant signatures to bypass the validation under specific conditions.

The issue stems from how the function handles signature validation and redundancy checks, potentially leading to the rejection of valid multi-signatures under certain conditions.

The core problem lies in the function's logic for checking if the signature threshold has been met. Currently, it may incorrectly flag legitimate signatures as redundant if the threshold is exceeded before all signatures are processed, due to the order in which they are provided.

## Scenario

The potential vulnerability lies in the interplay between the signature validation loop and the threshold check. Consider this scenario:

- Let's say there are three signers (A, B, C) with weights (2, 3, 4) and a threshold of 5.
- The provided signatures are: [signature_A, signature_C, signature_B] (note the order).
- When processing signature_C, the totalWeight becomes 4.
- Since 4 is less than the threshold (5), the loop continues.
- Next, signature_B is processed, and totalWeight becomes 7 (4 + 3).
- Now, totalWeight exceeds the threshold.
- However, the check if (i + 1 == signaturesLength) evaluates to false because there's still one more signature (signature_B) left to process.
- Consequently, the function incorrectly reverts with RedundantSignaturesProvided.

## Impact

This bug could lead to the rejection of legitimate multi-signatures where the order of signatures causes the threshold to be exceeded before all signatures are processed.

This undermines the security of the multi-signature scheme, as it could potentially allow unauthorized actions if an attacker can manipulate the order of signatures.
    
## Fix
The issue is that the redundancy check is tied to the loop index (i) rather than the actual number of signatures required to reach the threshold.
A potential fix involves introducing a new variable (e.g., requiredSignatures) to track how many signatures were actually needed to reach the threshold.
The redundancy check would then be modified to compare i + 1 with requiredSignatures.

Example Fix:

```Solidity
// ...
uint256 requiredSignatures = 0; 

// ... (inside the loop)
if (totalWeight >= weightedSigners.threshold) {
    if (requiredSignatures == 0) {
        requiredSignatures = i + 1; // Mark how many signatures were needed
    }

    if (requiredSignatures == signaturesLength) return; // All required signatures processed

    revert RedundantSignaturesProvided(requiredSignatures, signaturesLength);
}
// ...
```



The fix introduces a new variable, requiredSignatures, to explicitly track the number of signatures that were actually necessary to reach the threshold. This decoupling of the redundancy check from the loop index (i) allows for a more accurate assessment of whether any extra signatures are present.
