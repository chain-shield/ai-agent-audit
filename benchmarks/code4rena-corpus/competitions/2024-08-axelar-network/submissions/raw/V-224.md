# Vulnerability details

## Vulnerability Details
InterchainMultisig inherits from BaseWeightedMultisig. This means it inherits all the state variables and functions, including the storage layout defined in the base contract. InterchainMultisig introduces its own storage struct, InterchainMultisigStorage, and uses a similar pattern to calculate its dedicated storage slot (INTERCHAIN_MULTISIG_SLOT).

Here's how both BaseWeightedMultisig and InterchainMultisig calculate their storage slots.
- BaseWeightedMultisig uses keccak256('BaseWeightedMultisig.Slot') - 1.
- InterchainMultisig uses keccak256('InterchainMultisig.Slot') - 1.

This approach only works well as long as the contract is not inherited and extended by other contracts that also employ a similar storage slot calculation mechanism.

There's a possibility, although slim, that these hash calculations might result in the same value. If that happens, both BaseWeightedMultisigStorage and InterchainMultisigStorage would attempt to occupy the same storage slot, leading to a collision.

Hash functions like keccak256 take an input and produce a fixed-size output (a hash). Ideally, different inputs should produce different hashes. A collision occurs when two different inputs produce the same hash output. While hash functions are designed to minimize collisions, they are not entirely impossible. The probability of a collision increases more rapidly than one might intuitively expect. This is related to the Birthday Paradox, which states that in a group of just 23 people, there's a greater than 50% chance that two people share the same birthday.

## Scenario

The storage slot calculation involves:

- Taking a string literal (e.g., 'BaseWeightedMultisig.Slot' or 'InterchainMultisig.Slot')
- Passing it to keccak256 to get a hash
- Subtracting 1 from the hash result

The potential collision arises because:

- The input strings are different, but they have a similar structure.
- keccak256 produces a 256-bit hash, which has a vast number of possible outputs (2^256).
- However, the final step of subtracting 1 slightly reduces the range of possible outputs.

While the probability of these specific strings resulting in the same hash after the subtraction is low, it's not zero.


## Impact

If a collision does occur:

BASE_WEIGHTED_MULTISIG_SLOT and INTERCHAIN_MULTISIG_SLOT would have the same value.
When the contracts are deployed and their storage is initialized, both BaseWeightedMultisigStorage and InterchainMultisigStorage would try to write their data to the same storage slot.
This would lead to data overwriting and corruption.
The contract's behavior would become unpredictable and likely erroneous, as the state variables it relies on would be incorrect.


## Fix

Ensure that the storage slots for both structs are distinct. Here are a couple of approaches:

1. Incorporate a unique salt or identifier into the hash calculation, preferably something tied to the contract's identity. For example:
    
```Solidity
// In BaseWeightedMultisig
bytes32 internal constant BASE_WEIGHTED_MULTISIG_SLOT = keccak256(abi.encodePacked("BaseWeightedMultisig.Slot", uint256(type(BaseWeightedMultisig).creationCode)));

// In InterchainMultisig
bytes32 internal constant INTERCHAIN_MULTISIG_SLOT = keccak256(abi.encodePacked("InterchainMultisig.Slot", uint256(type(InterchainMultisig).creationCode)));
```

This leverages the type(Contract).creationCode feature, which returns the contract's creation bytecode. This ensures a high degree of uniqueness, as the creation bytecode is specific to each contract, even if they share the same source code.

2. If you anticipate more structs being added in future extensions or upgrades, a hierarchical approach can provide better organization and collision avoidance:


```Solidity
// In BaseWeightedMultisig
bytes32 internal constant BASE_SLOT = keccak256(abi.encodePacked("MyContracts.Base"));
bytes32 internal constant BASE_WEIGHTED_MULTISIG_SLOT = keccak256(abi.encodePacked(BASE_SLOT, "WeightedMultisig"));

// In InterchainMultisig
bytes32 internal constant INTERCHAIN_MULTISIG_SLOT = keccak256(abi.encodePacked(BASE_SLOT, "InterchainMultisig"));
```

This establishes a clear hierarchy, making it easier to manage storage slots as the contract evolves.

I recommend adopting one of these fixes to ensure the InterchainMultisig contract and any future extensions are resilient to storage collisions.
