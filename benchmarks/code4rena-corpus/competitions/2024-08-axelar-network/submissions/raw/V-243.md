# Vulnerability details

## Where is bug

[postTokenManagerDeploy()](https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/interchain-token-service/contracts/TokenHandler.sol#L164) of [TokenHandler.sol](https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/interchain-token-service/contracts/TokenHandler.sol).

## Impact

I found a bug that allows the deployment of token managers with invalid types and causes un-intended vectors with valid types. Here is the impact:
1. Deployment of token managers, unintended or maliciously.
2. Open path for DoS scenarios due to un-intended data returns.
3. Bypass of access controls and token management logic.

Located:
```solidity
function postTokenManagerDeploy(uint256 tokenManagerType, address tokenManager) external payable {
    // BUG: No validation of tokenManagerType
    if (tokenManagerType == uint256(TokenManagerType.LOCK_UNLOCK) || tokenManagerType == uint256(TokenManagerType.LOCK_UNLOCK_FEE)) {
        ITokenManager(tokenManager).approveService();
    }

    // BUG: No checks if tokenManager is a valid contract address
    if (tokenManagerType == uint256(TokenManagerType.GATEWAY)) {
        address token = ITokenManager(tokenManager).tokenAddress();
        _approveGateway(token, UINT256_MAX);
    }
    // BUG: Function is returning un-intended data
}
```

## Proof of Concept

Please place this poc in [TokenManager.js](https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/interchain-token-service/test/TokenManager.js) and use `npx hardhat test test/TokenManager.js` to run, to see output in terminal (also included below):

It shows = 
- Deploying with an invalid token type e.g., 999 does not revert as expected.
- Deploying with a valid token type but using an attacker’s address returns unexpected data, revealing the in-effective use of proper validation.
- An unauthorized attacker (user) can attempt to exploit this bug by calling `postTokenManagerDeploy()` directly.

describe("TokenHandler - Bug Test", function() {

    let tokenId, invalidType, validType;
  
    before(async function() {

        console.log("Vulnerability: Accepted invalid token manager type without reverting");

          console.log("Vulnerability: postTokenManagerDeploy returned unexpected data");
          console.log("Error message:", error.message);

          console.log("postTokenManagerDeploy reverted as expected for invalid type");
        }

      } catch (error) {
        console.log("Unexpected error with valid token type:", error.message);
      }

        await tokenHandler.connect(attacker).postTokenManagerDeploy(validType, attacker.address);

      } catch (error) {
        console.log("Attacker's call to postTokenManagerDeploy reverted as expected");
      }
    });

## Recommended Mitigation Steps

`01` - Use better input validation for `tokenManagerType` like so:
   ```solidity
   require(tokenManagerType >= MIN_TYPE && tokenManagerType <= MAX_TYPE, "Invalid token manager type");
   ```
`02` - Use a check to require `tokenManager` is a valid contract address:
   ```solidity
   require(tokenManager.code.length > 0, "Invalid token manager address");
   ```
`03` - Use better access control:
   ```solidity
   require(msg.sender == authorizedCaller, "Unauthorized");
   ```
