# Vulnerability details

## Impact

The `_validateSignatures` function might be subject to a Denial of Service (DoS) attack by the Block Gas Limit. 

As this function requires both signers and signatures to be sorted for operation, a large number of signers and signatures could make the `for-loop` excessively gas-consuming, resulting in exceeding the block gas limit, making it impractical or impossible in some cases.

## Proof of Concept

https://github.com/code-423n4/2024-08-axelar-network/blob/main/axelar-gmp-sdk-solidity/contracts/governance/BaseWeightedMultisig.sol#L192-L234

The function `_validateSignatures` has a nested `for-loop`:

```solidity
    for (uint256 i; i < signaturesLength; ++i) {
        address recoveredSigner = ECDSA.recover(messageHash, signatures[i]);

        // looping through remaining signers to find a match
        for (; signerIndex < signersLength && recoveredSigner != signers[signerIndex].signer; ++signerIndex) {}

        // checking if we are out of signers
        if (signerIndex == signersLength) revert MalformedSignatures();
       ...
```

This function iterates through each signature, recovers the signer from the signature, and then iterates through the list of signers to find a match. 

If the list of signatures and signers is too large, this loop could exceed Ethereum's block gas limit, causing the transaction to fail due to the computational heaviness of ECDSA.recover().

## Recommended Mitigation Steps

For instance, an option could be to use a mapping to check if a signer is in the signers list. But this would require maintaining the signers list and the mapping in sync. As there is no inherent ordering in a mapping, some changes would need to take place to ensure that signers are presented in an ascending manner.

Another way of handling it is by setting a limit on the number of signers and signatures. This limit should be set according to the block gas limit and the amount of gas the rest of the operations in the function need.
