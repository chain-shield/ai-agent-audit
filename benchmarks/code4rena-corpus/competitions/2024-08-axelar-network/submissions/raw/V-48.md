# Vulnerability details

`approveMessages()` approves an array of messages, signed by the Axelar signers.
If the message is approved once, it cannot be re-approved because its status is updated to executed.

In the event that the signers turn out to be malicious, the gateway operator can assign new signers by calling the `rotateSigners()`.

However it is possible that the old signers (including the attacker) can still keep on approving messages when they are not the latest signers. 

## Proof of Concept

```solidity
File: AxelarAmplifierGateway.sol

    function approveMessages(Message[] calldata messages, Proof calldata proof) external {
        bytes32 dataHash = keccak256(abi.encode(CommandType.ApproveMessages, messages));

        _validateProof(dataHash, proof);

        _approveMessages(messages);
    }
```
`_validateProof()` returns a bool value indicating if the current signer is the current signer or not. Later the difference between the `signerEpoch` & `currentEpoch` does not exceed `previousSignersRetention` is checked.

```solidity
File: BaseWeightedMultisig.sol

    function _validateProof(bytes32 dataHash, Proof calldata proof) internal view returns (bool isLatestSigners) {
        BaseWeightedMultisigStorage storage slot = _baseWeightedMultisigStorage();

        WeightedSigners calldata signers = proof.signers;

        bytes32 signersHash = keccak256(abi.encode(signers));
        uint256 signerEpoch = slot.epochBySignerHash[signersHash];
        uint256 currentEpoch = slot.epoch;

        isLatestSigners = signerEpoch == currentEpoch;   /// @note - this will result false for old signers

        if (signerEpoch == 0 || currentEpoch - signerEpoch > previousSignersRetention) revert InvalidSigners();    /// @note - can still sign for some period

        bytes32 messageHash = messageHashToSign(signersHash, dataHash);

        _validateSignatures(messageHash, signers, proof.signatures);
    }
```
As per the [link](https://bright-ambert-2bd.notion.site/C4E-Audit-Axelar-Amplifier-FAQs-Aug-2024-External-5ded3250fa504e3e882e9551179b7548),
*Q - What values would be set for `previousSignersRetention` and `minimumRotationDelay`?    
A - For the mainnet, these values are 15 and 1 day, respectively. The frequency of signer set updates on Axelar influences these values.*

At last, the signatures are checked if they are valid & since they are, there are no issues.

### Scenario
- Bob is assigned as the current signer. However Bob has ill intensions & he starts approving incorrect messages.
- The operator notices this & calls `rotateSigners()` to remove Bob. Now a Alice is the latest signer.
- However Bob can still continue his bad actions because `previousSignersRetention` is set to 15 days. (If signers are not rotated daily, then more than 15 days) 
- Plus there isn't any check in `approveMessages()` to check if the signer is the latest signer.

## Impact
Malicious signers can still keep on approving messages even if they are not the latest signer which ultimately prevents the ITS from executing messages through `expressExecute()`
