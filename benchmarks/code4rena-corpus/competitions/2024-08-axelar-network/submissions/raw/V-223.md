# Vulnerability details

## Vulnerability Details

The _validateSigners function aims to prevent duplicate signers by enforcing a strict ascending order of signer addresses. However, the check prevSigner >= currSigner is flawed. It allows a scenario where two consecutive signers have the same address, which essentially means a duplicate signer.

## Code Snippet

https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/axelar-gmp-sdk-solidity/contracts/governance/BaseWeightedMultisig.sol#L274

```Solidity
if (prevSigner >= currSigner) {
    revert InvalidSigners();
}
```

The incorrect check permits duplicate signers in the weightedSigners input. This could lead to a signer having undue influence in the multi-signature scheme, as their weight would be effectively doubled (or multiplied if the same address appears multiple times).

## Impact

Now, consider the scenario where the _validateSigners function fails to detect duplicate signers due to the flawed comparison.

1. Inflated Weight: If a signer's address appears multiple times in the weightedSigners input, their associated weight will be counted multiple times during the signature validation process (_validateSignatures). This effectively inflates their voting power, granting them undue influence over the outcome of the multi-signature approval.

2. Threshold Manipulation: With inflated weight, a malicious actor controlling a duplicate signer could potentially single-handedly reach the approval threshold, bypassing the need for genuine consensus from other signers. This subverts the fundamental purpose of a multi-signature scheme, which is to distribute decision-making power and prevent unilateral control.

3. Security Risks: The ability for a single entity to manipulate the approval process poses significant security risks. It could lead to unauthorized transactions, fund misappropriation, or other malicious actions, depending on the specific application of the multi-signature scheme.

## Scenario

Let's say we have a 3-of-5 multi-signature setup with the following signers and weights:

Signer A: Weight 2
Signer B: Weight 2
Signer C: Weight 1
Signer D: Weight 1
Signer E: Weight 1

The threshold for approval is 3.

Now, imagine a malicious actor controls Signer A and manages to introduce a duplicate entry for Signer A in the weightedSigners input. The effective weights become:

Signer A: Weight 2 + 2 = 4
Signer B: Weight 2
Signer C: Weight 1
Signer D: Weight 1
Signer E: Weight 1

In this scenario, Signer A alone can now approve transactions, completely bypassing the need for any other signer's consent.

## Fix

The comparison should be strictly greater than (>) instead of greater than or equal to (>=) to correctly prevent duplicate signers.

```Solidity

if (prevSigner > currSigner) { // Corrected comparison
    revert InvalidSigners();
}
```
