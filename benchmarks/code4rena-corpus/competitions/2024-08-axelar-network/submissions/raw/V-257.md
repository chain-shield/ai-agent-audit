# Vulnerability details

## Vulnerability Details
The `InterchainToken` contract's `init` function allows setting an arbitrary number of decimal places for the token without any validation. This lack of bounds checking on the `tokenDecimals` parameter creates a vulnerability that could be exploited to cause significant issues within the ecosystem.

## Code Snippet

https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/interchain-token-service/contracts/interchain-token/InterchainToken.sol#L86

```solidity
function init(bytes32 tokenId_, address minter, string calldata tokenName, string calldata tokenSymbol, uint8 tokenDecimals) external {
        if (_isInitialized()) revert AlreadyInitialized();

        _initialize();

        if (tokenId_ == bytes32(0)) revert TokenIdZero();
        if (bytes(tokenName).length == 0) revert TokenNameEmpty();
        if (bytes(tokenSymbol).length == 0) revert TokenSymbolEmpty();

        name = tokenName;
        symbol = tokenSymbol;
        decimals = tokenDecimals;
        tokenId = tokenId_;

        /**
         * @dev Set the token service as a minter to allow it to mint and burn tokens.
         * Also add the provided address as a minter. If `address(0)` was provided,
         * add it as a minter to allow anyone to easily check that no custom minter was set.
         */
        _addMinter(interchainTokenService_);
        _addMinter(minter);

        _setNameHash(tokenName);
    }
```

## Impact
1. Network Congestion: Tokens with extremely high decimal places can be used to execute dust attacks, flooding the network with tiny transactions and causing congestion.
2. Increased Gas Costs: Network congestion leads to higher gas prices, making transactions more expensive for all users.
3. Delayed Transactions: Legitimate transactions may be significantly delayed due to network congestion.
4. Denial of Service: In extreme cases, the network could become nearly unusable for regular transactions.
5. Precision Issues: Extremely high decimal values can lead to precision problems and potential overflows in calculations.
6. Interoperability Problems: Unusual decimal counts may cause issues when integrating with other DeFi protocols or exchanges.
7. User Confusion: Excessive precision can make token amounts difficult for users to understand and work with.

## Attack Scenario
1. An attacker creates a token with an extremely high number of decimals (e.g., 255).
2. The attacker then initiates a large number of transactions, sending tiny amounts of this token to numerous addresses.
3. These transactions, while involving negligible value, still consume network resources and require processing.
4. The network becomes congested, causing increased gas prices and transaction delays.
5. Regular users face higher costs and longer wait times for their transactions.
6. In a worst-case scenario, the network could become temporarily unusable for normal operations.

## Recommendation
1. Implement a maximum limit for the number of decimal places. A common maximum is 18, but this can be adjusted based on specific requirements.
2. Add a check in the `init` function to enforce this limit:

```solidity
function init(bytes32 tokenId_, address minter, string calldata tokenName, string calldata tokenSymbol, uint8 tokenDecimals) external {
    require(tokenDecimals <= 18, "Decimals exceed maximum allowed");
    // ... other initialization logic ...
    decimals = tokenDecimals;
    // ... rest of the function ...
}
```

3. Consider implementing dust limits to prevent transactions involving amounts below a certain threshold.
