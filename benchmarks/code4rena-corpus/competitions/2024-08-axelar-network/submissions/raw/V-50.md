# Vulnerability details


## Description

The `InterchainTokenService` contract is designed to facilitate interchain token transfers and related operations. A key component of this system is the [`_getExecuteParams()` function](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/interchain-token-service/contracts/InterchainTokenService.sol#L964-L991), which processes messages routed through the ITS Hub. This function extracts the message type from the payload and, if the message is from the ITS Hub (`MESSAGE_TYPE_RECEIVE_FROM_HUB`), it decodes the inner payload and updates the `messageType` to the inner message type.

The issue arises from the fact that the function does not verify if this new inner message type is valid for hub-routed messages. This oversight could potentially allow an attacker to craft a malicious payload that, when routed through the hub, might execute unauthorized actions or bypass intended restrictions.

The [`_getExecuteParams()` function](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/interchain-token-service/contracts/InterchainTokenService.sol#L964-L991) is called by both [`_execute()`](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/interchain-token-service/contracts/InterchainTokenService.sol#L900-L921) and [`_executeWithToken()`](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/interchain-token-service/contracts/InterchainTokenService.sol#L923-L951), which process the message based on the returned `messageType`. If the inner message type is not properly validated, it could lead to the execution of operations that were not intended to be allowed through the hub.

The core of the issue lies in the lack of validation for the inner `messageType` after it is updated. This could potentially allow an attacker to send a `MESSAGE_TYPE_RECEIVE_FROM_HUB` message with an inner payload containing a different message type that should not be allowed for hub-routed messages.

## Impact
An attacker could execute unauthorized actions or bypass intended restrictions, potentially leading to unauthorized operations within the protocol. This could compromise the security and integrity of the interchain token system.


## Proof of Concept
1. An attacker constructs a payload with `MESSAGE_TYPE_RECEIVE_FROM_HUB` as the outer message type.
2. The inner payload of this message contains a different message type that is not intended to be routed through the hub, along with malicious data.
3. This payload is sent through the ITS Hub to the `InterchainTokenService` contract.
4. The `_getExecuteParams()` function processes this message:
   - It verifies that the source is the ITS Hub.
   - It decodes the inner payload and updates the `messageType` to the potentially malicious inner type.
   - It does not verify if this new `messageType` is allowed for hub-routed messages.
5. The `_execute()` or `_executeWithToken()` function then processes this message based on the unverified `messageType`, potentially leading to unauthorized actions.

## Tools Used
Manual review

## Recommended Mitigation Steps
To address this issue, it's recommended to implement a verification step for the inner message type in hub-routed messages. This can be done by maintaining a list of allowed message types for hub-routed messages and checking against this list.
