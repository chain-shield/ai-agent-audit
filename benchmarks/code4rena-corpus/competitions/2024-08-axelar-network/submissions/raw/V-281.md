# Vulnerability details

## Impact

One of permissionless entry points of `axelarnet-gateway` contract is message `RouteMessages`. It can be used for short-term DoS attacks, also known as "block stuffing". The attacker needs to cover gas fees to maintain the attack, but can use this attack to gain front-running opportunities, significantly worsen existing network congestion, or to combine with other attacks to make them more effective. 
## Proof of Concept

When a `RouteMessages` message is coming from an arbitrary party (not `router`), it is directed to `execute::route_incoming_messages` function:

axelar-amplifier/contracts/axelarnet-gateway/src/contract.rs
```

            if info.sender == router.address {
                execute::route_outgoing_messages(deps.storage, msgs)
            } else {
                // Messages initiated via call contract can be routed again
                execute::route_incoming_messages(deps.storage, &router, msgs)

```

In this function, the contract first looks up a message with same id in `INCOMING_MESSAGES` mapping. If the incoming message differs from the stored one, it is rejected. However, if both messages are exactly same, execution proceeds (see `Some(_) => Ok(())` in the snippet below), last step of the function is sending the inner messages (can be just one) to the routing contract (using the `route` function which filters empty messages and generates `ExecuteMsg::RouteMessages`):

The `route_outgoing_messages` function returns `Ok` if the attempt to save the messages succeeded:
```
pub(crate) fn route_outgoing_messages(
    store: &mut dyn Storage,
    msgs: Vec<Message>,
) -> Result<Response, Error> {
    for msg in msgs.iter() {
        state::save_outgoing_msg(store, msg.cc_id.clone(), msg.clone())
            .change_context(Error::SaveOutgoingMessage)?;
    }

    Ok(Response::new().add_events(
        msgs.into_iter()
            .map(|msg| AxelarnetGatewayEvent::Routing { msg }.into()),
    ))
}
```

Last detail is that `save_outgoing_msg` function simply ignores duplicates without rejecting them:
```
pub(crate) fn save_outgoing_msg(
    storage: &mut dyn Storage,
    cc_id: CrossChainId,
    msg: Message,
) -> Result<(), Error> {
    let existing = OUTGOING_MESSAGES
        .may_load(storage, cc_id.clone())
        .map_err(Error::from)?;

    match existing {
        Some(MessageWithStatus {
            msg: existing_msg, ..
        }) if msg != existing_msg => Err(Error::MessageMismatch(msg.cc_id.clone())),
        Some(_) => Ok(()), // new message is identical, no need to store it
        None => OUTGOING_MESSAGES
            .save(
                storage,
                cc_id,
                &MessageWithStatus {
                    msg,
                    status: MessageStatus::Approved,
                },
            )
            .map_err(Error::from)?
            .then(Ok),
    }
}
```

Additionally, there is no deduplication of messages in `route_incoming_messages` and `route_outgoing_messages` functions. As a result, a malicious party can spend as much gas as it desires up to filling the whole block by submitting `RouteMessages` with many duplicates inside. Instead of rejection, the duplicates are passed between several smart contracts using external calls and redundant storage operations are involved. The malicious party can repeat same duplicates every block.

## Recommended Mitigation Steps

More strict validation is needed to reject duplicates early, so it cost very few of gas and would not occupy the whole block if a malicious party is interested in it.

Rejection of duplicates should be implemented both `route_incoming_messages` and `save_outgoing_msg` functions.
### Alternative
In case it's absolutely necessary to allow retrying routing requests, it's possible to implement it by storing number of retries and block number of the latest retry. The retry should be allowed only if certain time interval passed since last retry, this interval should increase with each attempt using predefined formula.
