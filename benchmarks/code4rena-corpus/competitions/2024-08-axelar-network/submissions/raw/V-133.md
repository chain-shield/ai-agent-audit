# ERC20Permit Vulnerability: Allowance Inflation and Persistent Approval Risks

## Impact

The `ERC20Permit.sol` contract contains a vulnerability that allows for allowance inflation and creates persistent approval risks. The core issue lies in the `permit` function, which sets allowances without verifying the token owner's current balance. This oversight enables users to create permits for amounts exceeding their available tokens, which remain valid even if the user's balance fluctuates.

The impact of this vulnerability is severe due to the following factors:

1. **Unrestricted Allowance Setting**: The `permit` function sets allowances without checking the current balance:

   ```solidity
   _approve(issuer, spender, value);
   ```

   This allows users to create permits for amounts potentially exceeding their current or future balance.

2. **Persistent Oversized Allowance**: These permits remain valid even if the user's balance fluctuates after creation, as there's no link between permit amount and current balance in the `_approve` call.

3. **Potential for Unexpected Token Drain**: Previously approved spenders can exploit this by waiting for the balance to increase and then using the permit to transfer more tokens than were initially available or intended.

4. **Bypass of User Expectations**: Users typically expect allowances to be constrained by their current balance, which is not the case here. This violates the principle of least privilege.

5. **Long-Term Risk**: The extended validity of permits (potentially up to the `deadline`) creates a long window of vulnerability, even after initial balance changes.

6. **Silent Failure Mode**: The vulnerability doesn't cause immediate failure, making it harder to detect and potentially more damaging over time.

7. **Ecosystem-Wide Impact**: As ERC20Permit is often used in DeFi protocols, this vulnerability could have cascading effects on integrated systems across the ecosystem.

The combination of unrestricted permit creation and lack of balance checks makes this vulnerability high-severity in the context of this `ERC20Permit.sol` implementation.

'use strict';
const { ethers } = require('hardhat');
const {

    getContractAt,
    utils: { parseEther, formatEther },
    constants: { MaxUint256 },
} = ethers;

const { expect } = require('chai');
const { getRandomBytes32, getChainId } = require('./utils');
const { deployContract } = require('../scripts/deploy');

describe('ERC20Permit Allowance Inflation Vulnerability - Extended PoC', () => {
    let token, owner, alice, bob, approvedSpender;
    const name = 'TestToken';
    const symbol = 'TEST';
    const decimals = 18;
    const initialBalance = parseEther('10000'); // 10,000 TEST

    before(async () => {
        [owner, alice, bob, approvedSpender] = await ethers.getSigners();

        const interchainToken = await deployContract(owner, 'InterchainToken', [owner.address]);

        const interchainTokenDeployer = await deployContract(owner, 'InterchainTokenDeployer', [interchainToken.address]);

        const salt = getRandomBytes32();
        const tokenId = getRandomBytes32();

        const tokenAddress = await interchainTokenDeployer.deployedAddress(salt);
        token = await getContractAt('InterchainToken', tokenAddress, owner);

        await interchainTokenDeployer.deployInterchainToken(salt, tokenId, owner.address, name, symbol, decimals);
        await token.mint(alice.address, initialBalance);
    });

    it('should demonstrate permit creation for more tokens than currently owned', async () => {
        const deadline = Math.floor(Date.now() / 1000) + 3600 * 24 * 7; // 1 week from now
        const excessiveValue = initialBalance.mul(2); // Double the initial balance
        const initialNonce = await token.nonces(alice.address);

        console.log("Alice's initial balance:", formatEther(await token.balanceOf(alice.address)));

        // Step 1: Alice creates a permit signature for more tokens than she owns
        const signature = await alice._signTypedData(
            {
                name,
                version: '1',
                chainId: await getChainId(),
                verifyingContract: token.address,
            },

            {
                Permit: [
                    { name: 'owner', type: 'address' },
                    { name: 'spender', type: 'address' },
                    { name: 'value', type: 'uint256' },
                    { name: 'nonce', type: 'uint256' },
                    { name: 'deadline', type: 'uint256' },
                ],
            },
            {
                owner: alice.address,
                spender: approvedSpender.address,
                value: excessiveValue,
                nonce: initialNonce,
                deadline,
            }
        );

        const { v, r, s } = ethers.utils.splitSignature(signature);

        // Step 2: Execute the permit

        await token.permit(alice.address, approvedSpender.address, excessiveValue, deadline, v, r, s);

        console.log("Allowance after permit:", formatEther(await token.allowance(alice.address, approvedSpender.address)));

        console.log("Alice's balance after permit:", formatEther(await token.balanceOf(alice.address)));

        // Step 3: Approved spender attempts to use the excessive allowance

        try {
            await token.connect(approvedSpender).transferFrom(alice.address, approvedSpender.address, excessiveValue);
            console.log("Excessive transfer succeeded (unexpected)");
        } catch (error) {
            console.log("Excessive transfer failed as expected:", error.message);
        }

        // Step 4: Approved spender uses allowance up to Alice's actual balance
        await token.connect(approvedSpender).transferFrom(alice.address, approvedSpender.address, initialBalance);

        console.log("Alice's final balance:", formatEther(await token.balanceOf(alice.address)));

        console.log("Approved spender's final balance:", formatEther(await token.balanceOf(approvedSpender.address)));

        console.log("Final allowance:", formatEther(await token.allowance(alice.address, approvedSpender.address)));

        // Assertions

        expect(await token.balanceOf(alice.address)).to.equal(0);

        expect(await token.balanceOf(approvedSpender.address)).to.equal(initialBalance);

        expect(await token.allowance(alice.address, approvedSpender.address)).to.equal(excessiveValue.sub(initialBalance));

        expect(await token.nonces(alice.address)).to.equal(initialNonce.add(1));

    });

});

## Why This Is a Significant Issue


1. **Violation of Least Privilege**: The inflated allowance violates the principle of least privilege, granting more permissions than necessary or intended.

2. **Persistent Vulnerability**: The inflated allowance persists even after balance changes, creating a long-term security risk.

3. **Future Fund Risk**: If a user receives additional tokens in the future, they could be immediately at risk due to the persisting inflated allowance.

4. **User Expectation Violation**: Users would typically expect allowances to be limited by their current balance, which isn't the case here.

5. **Silent Failure Mode**: The issue doesn't cause immediate failure, making it harder to detect and potentially more damaging over time.

6. **Ecosystem Impact**: As ERC20Permit is widely used in DeFi, this vulnerability could have far-reaching effects on integrated protocols.

7. **Bypasses Standard Checks**: While immediate over-spending is prevented by balance checks in transfer functions, the core issue of inflated allowances remains unaddressed.

8. **Potential for Confusion**: This behavior could lead to confusion in integrations or user interactions, potentially causing unexpected token losses.

## Recommended Mitigation Steps

To mitigate this vulnerability, implement a balance check in the `permit` function before approving the allowance. Here's the recommended fix:


```diff
function permit(address issuer, address spender, uint256 value, uint256 deadline, uint8 v, bytes32 r, bytes32 s) external {
    if (block.timestamp > deadline) revert PermitExpired();
    if (uint256(s) > 0x7FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF5D576E7357A4501DDFE92F46681B20A0) revert InvalidS();
    if (v != 27 && v != 28) revert InvalidV();

    bytes32 digest = keccak256(
        abi.encodePacked(
        
            EIP191_PREFIX_FOR_EIP712_STRUCTURED_DATA,
            DOMAIN_SEPARATOR(),
            keccak256(abi.encode(PERMIT_SIGNATURE_HASH, issuer, spender, value, nonces[issuer]++, deadline))
        )
    );

    address recoveredAddress = ecrecover(digest, v, r, s);
    if (recoveredAddress != issuer) revert InvalidSignature();

+   // Add balance check
+   if (value > balanceOf(issuer)) revert InsufficientBalance();
    _approve(issuer, spender, value);
}
```


This modification ensures that the permitted value doesn't exceed the issuer's current balance, preventing the vulnerability described in the finding. It maintains the original structure and purpose of the ERC20Permit function while significantly improving security.
  
By implementing these changes, the contract will align more closely with user expectations and standard ERC20 behavior, significantly reducing the risk of unexpected token losses and improving overall security.
