# Vulnerability details

## Description

The `InterchainTokenService` contract is designed to facilitate interchain token transfers. It includes an [`_executeWithToken()` function](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/interchain-token-service/contracts/InterchainTokenService.sol#L923-L950) that handles the execution of cross-chain token transfers. This function interacts with a gateway contract to validate and mint tokens, and then processes the transfer payload.

The function first calls `gateway.validateContractCallAndMint()`, which mints or transfers tokens to the contract. It then checks for an express execution by calling [`_getExpressExecutorAndEmitEvent()`](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/interchain-token-service/contracts/InterchainTokenService.sol#L1228-L1239). If an express execution has occurred, the [`_processInterchainTransferPayload()` function](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/interchain-token-service/contracts/InterchainTokenService.sol#L721-L776) is called, which transfers tokens to the express executor and returns early.

The critical issue lies in the fact that when an express execution occurs, the tokens minted or transferred by `validateContractCallAndMint()` are not properly accounted for. This creates a scenario where tokens can be double-spent or minted without authorization.

Here's the relevant code:

```solidity
function _executeWithToken(
    bytes32 commandId,
    string calldata sourceChain,
    string calldata sourceAddress,
    bytes memory payload,
    string calldata tokenSymbol,
    uint256 amount
) internal {
    // ... (code omitted for brevity)

    if (!gateway.validateContractCallAndMint(commandId, sourceChain, sourceAddress, payloadHash, tokenSymbol, amount))
        revert NotApprovedByGateway();

    // ... (code omitted for brevity)

    address expressExecutor = _getExpressExecutorAndEmitEvent(commandId, sourceChain, sourceAddress, payloadHash);

    _processInterchainTransferPayload(commandId, expressExecutor, originalSourceChain, payload);
}

function _processInterchainTransferPayload(
    bytes32 commandId,
    address expressExecutor,
    string memory sourceChain,
    bytes memory payload
) internal {
    // ... (code omitted for brevity)

    if (expressExecutor != address(0)) {
        _giveToken(tokenId, expressExecutor, amount);
        return;
    }

    // ... (rest of the function)
}
```

The issue arises because in the case of an express execution, the function returns early after giving tokens to the express executor, without properly handling the tokens minted or transferred by `validateContractCallAndMint()`.

## Impact
The improper handling of express executions in the `_executeWithToken` function can lead to double-spending or unauthorized token minting. This vulnerability allows an attacker to perform an express execution, receive tokens, and then have additional tokens minted or transferred to the contract during normal execution. 



## Proof of Concept

1. An attacker initiates a cross-chain token transfer with express execution.
2. The `_executeWithToken()` function is called, which mints/transfers tokens via `gateway.validateContractCallAndMint()`.
3. The function detects an express execution (`expressExecutor != address(0)`).
4. `_processInterchainTransferPayload()` is called, which transfers tokens to the express executor and returns early.
5. The tokens minted/transferred in step 2 remain unaccounted for in the contract.
6. The attacker can now withdraw these additional tokens, effectively double-spending.

## Tools Used

Manual review

## Recommended Mitigation Steps

To fix this , the contract should properly handle the tokens minted/transferred by `validateContractCallAndMint()` in all cases, including express executions.
