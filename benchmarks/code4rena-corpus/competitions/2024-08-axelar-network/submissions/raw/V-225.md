# Vulnerability details

## Impact

One of permissionless entry points of `axelarnet-gateway` contract is message `CallContract`. When handling messages of this type, new message id is generated. For this, a single counter is used (for all source chains). Upon reaching the counter limit, the gateway stops registering new `CallContract` messages and can only execute outgoing messages. Migrating state of the exhausted gateway is not possible. Axelar maintainers would have to deploy new version of the gateway with reset counter while keeping the current gateway live for some time to deliver already registered requests.

## Proof of Concept

axelar-amplifier/contracts/axelarnet-gateway/src/state.rs:
```
const COUNTER: Counter<u32> = Counter::new(COUNTER_NAME);
...
pub(crate) fn increment_msg_counter(storage: &mut dyn Storage) -> Result<u32, Error> {
    COUNTER.incr(storage).map_err(Error::from)
}
```

The `Counter` structure is implemented properly (out of scope) and when it reaches the maximum value it returns `OverflowError`. We could add the following test case in axelar-amplifier/packages/axelar-wasm-std/src/counter.rs:
```
#[test]
    fn test_overflow_u8() {
        let mut store = MockStorage::new();

        let counter: Counter<u8> = Counter::new("counter");
        assert_eq!(counter.cur(&store), 0);
        for _ in 1..u8::MAX {
            counter.incr(&mut store).unwrap();
        }
        assert_eq!(counter.incr(&mut store).unwrap(), 255);
        assert!(counter.incr(&mut store).is_err());
    }
```

In `axelarnet-gateway`, this `Counter` is used together with `u32` type (not `u8`), this provides much higher limit of `4_294_967_295`, but this number is still insufficient. This counter is incremented every time new `CallContract` message is processed:
axelar-amplifier/contracts/axelarnet-gateway/src/contract/execute.rs
```
pub(crate) fn call_contract(
    store: &mut dyn Storage,
    router: &Router,
    chain_name: ChainName,
    sender: Addr,
    destination_chain: ChainName,
    destination_address: Address,
    payload: HexBinary,
) -> Result<Response, Error> {
    let counter = state::increment_msg_counter(store).change_context(Error::InvalidStoreAccess)?;
```

This means that over time, especially if the service is actively used, the counter can exhaust without any active attack being performed against the service. When it happens, cross-chain messages will not be accepted anymore. Mitigation with current codebase is difficult, given that migration of the contract state is not implemented:
axelar-amplifier/contracts/axelarnet-gateway/src/contract.rs
```
pub fn migrate(
    deps: DepsMut,
    _env: Env,
    _msg: Empty,
) -> Result<Response, axelar_wasm_std::error::ContractError> {
    // any version checks should be done before here

    cw2::set_contract_version(deps.storage, CONTRACT_NAME, CONTRACT_VERSION)?;

    Ok(Response::default())
}
```

Additionally, a malicious party could perform active DoS attack against the contract and submit 4294967295 `CallContract` messages, paying only gas fees.

Upon reaching to the counter limit, the governance will need to take action in advance and deploy new version of the gateway with reset counter while continuing to deliver requests in the older gateway.

## Recommended Mitigation Steps

Possible solutions:
1. Using `u64` will make the limit significantly higher, practically unreachable.
2. Alternatively, separate counters for each source chain could be used.
