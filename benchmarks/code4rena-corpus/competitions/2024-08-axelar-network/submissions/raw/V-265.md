# Vulnerability details

## Impact

The `InterchainTokenDeployer` contract uses the `Create3Fixed` contract to deploy new instances of the `InterchainTokenProxy` contract. However, it does not verify if the bytecode of the implementation contract has changed before deploying new proxy contracts. This can lead to a situation where newly deployed proxies continue to point to an outdated implementation contract, resulting in unexpected behavior and potential inconsistencies across the deployed proxy contracts.

## Proof of Concept

The issue arises in the following scenario:

1. An initial implementation contract is deployed and its address is used by the `InterchainTokenDeployer` contract.
2. Multiple `InterchainTokenProxy` contracts are deployed, all pointing to this initial implementation.
3. Later, a new implementation contract is deployed (e.g., to upgrade the token logic or fix a bug).
4. The `InterchainTokenDeployer` continues to deploy new proxies pointing to the old implementation, as it does not check whether the implementation address has changed.

This results in a mixed environment where older proxies point to the outdated implementation, and any new proxies deployed with the same deployment logic also point to the outdated implementation. The new implementation is effectively ignored unless manually updated, leading to potential discrepancies in contract behavior.

## Recommended Mitigation Steps


- Add a mechanism to verify that the implementation contract's bytecode matches the expected version before deploying new proxy contracts.
- This could be done by storing a hash of the implementation's bytecode and comparing it with the current implementation's bytecode before deploying new proxies.
