# Vulnerability details

### Description
Inside the `axelar-amplifier/axelarnet-gateway/execute` flow, outgoing messages are processed by calling `route_outgoing_messages`
```javascript

    deps: DepsMut,
    _: Env,
    info: MessageInfo,
    msg: ExecuteMsg,
) -> Result<Response, axelar_wasm_std::error::ContractError> {
//..Ommitted code 
        ExecuteMsg::RouteMessages(msgs) => {
            if info.sender == router.address {
->                execute::route_outgoing_messages(deps.storage, msgs)

//..Ommitted code
}
```

Within this function, a batch of messages is processed and saved. If a message has already been processed, the function will not revert, Instead, it will skip saving the message again, as doing so would be redundant.

```javascript
pub(crate) fn save_outgoing_msg(
    storage: &mut dyn Storage,
    cc_id: CrossChainId,
    msg: Message,
) -> Result<(), Error> {
    let existing = OUTGOING_MESSAGES
        .may_load(storage, cc_id.clone())
        .map_err(Error::from)?;

    match existing {
        Some(MessageWithStatus {
            msg: existing_msg, ..
        }) if msg != existing_msg => Err(Error::MessageMismatch(msg.cc_id.clone())),
=>        Some(_) => Ok(()), // new message is identical, no need to store it
        None => OUTGOING_MESSAGES
            .save(
                storage,
                cc_id,
                &MessageWithStatus {
                    msg,
                    status: MessageStatus::Approved,
                },
            )
            .map_err(Error::from)?
            .then(Ok),
    }
}


```

After the batch of messages is saved and processed, an event will be triggered.

```javascript
pub(crate) fn route_outgoing_messages(
    store: &mut dyn Storage,
    msgs: Vec<Message>,
) -> Result<Response, Error> {
//..Ommitted code
->    Ok(Response::new().add_events(
        msgs.into_iter()
            .map(|msg| AxelarnetGatewayEvent::Routing { msg }.into()),
    ))
}
```
As we can see, when the `execute` function is called, `add_events` is invoked with the provided `msgs`. This means that previously processed messages will be included in a new event again. This also means that already processed messages that are not stored again will be included in this event. 

Since events are monitored and acted upon, a malicious user could repeatedly trigger events for already processed messages, resulting in redundant event generation and forcing relayers to repeatedly verify the status of each message before deciding whether to act on it.

This becomes unmanageable for the relayers, especially when dealing with large batches of messages where just one message has already been processed, forcing the relayers to find out which one has already been processed. 

### Recommendation
The events could provide more detailed information about which messages have already been processed and which are being processed for the first time, or alternatively, non-saved messages might be excluded from the events.
