# Vulnerability details

## Vulnerability Details

The `_approve` function is used to set the amount of tokens that a spender can transfer on behalf of the owner. It's a core part of the ERC20 standard's delegation mechanism. The main issue is that the `_approve` function unconditionally sets the allowance to the new value, without considering the current allowance. This can lead to a race condition where an attacker can front-run a transaction to change the allowance.

```solidity
function _approve(address owner, address spender, uint256 amount) internal virtual {
        if (owner == address(0) || spender == address(0)) revert InvalidAccount();

        allowance[owner][spender] = amount;
        emit Approval(owner, spender, amount);
    }
```
## Impact

An attacker can potentially spend more tokens than the owner intended to allow. This can lead to significant financial losses for token owners.

## Scenario
1. Alice approves Bob to spend 100 tokens.
2. Alice later decides to change Bob's allowance to 50 tokens and submits this transaction.
3. Bob sees this pending transaction and quickly submits a `transferFrom` transaction for 100 tokens with a higher gas price.
4. Bob's transaction gets processed first, spending 100 tokens.
5. Alice's transaction then processes, setting Bob's allowance to 50 tokens.
6. Bob can now spend an additional 50 tokens, totaling 150 tokens instead of the intended 50.

## Fix

Implement a "change" approach rather than a "set" approach for allowances.
