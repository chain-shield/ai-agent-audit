# Vulnerability details

## Impact
The `AxelarAmplifierGateway` contract implements an operator role that has significant privileges, including the ability to bypass certain checks during signer rotation. While this is likely intended for emergency situations or efficient management, it introduces a centralization risk that could potentially compromise the security and decentralization of the system if the operator account is compromised or acts maliciously.

Specific impacts include:
1. The operator can rotate signers without enforcing the minimum rotation delay.
2. The operator can potentially introduce an outdated or malicious signer set.
3. If the operator key is compromised, an attacker could quickly change the signer set, potentially disrupting the network's operations.

## Proof of Concept
The `rotateSigners` function in `AxelarAmplifierGateway.sol` contains this logic:

```solidity
function rotateSigners(WeightedSigners memory newSigners, Proof calldata proof) external {
    bytes32 dataHash = keccak256(abi.encode(CommandType.RotateSigners, newSigners));

    bool enforceRotationDelay = msg.sender != _axelarAmplifierGatewayStorage().operator;
    bool isLatestSigners = _validateProof(dataHash, proof);
    if (enforceRotationDelay && !isLatestSigners) {
        revert NotLatestSigners();
    }

    // If newSigners is a repeat signer set, this will revert
    _rotateSigners(newSigners, enforceRotationDelay);
}
```

The operator can bypass the rotation delay and the check for the latest signers.

## Recommended Mitigation Steps
To mitigate this centralization risk, consider implementing the following measures:

1. Implement a multi-signature wallet or a DAO for the operator role, reducing the risk associated with a single point of failure.

2. Add a time-lock mechanism for critical operations performed by the operator, allowing for community oversight and potential intervention.

3. Implement an emergency pause function that can be triggered by multiple trusted parties, not just the operator.

4. Create a tiered access system where different levels of operations require different levels of authorization.

5. Regularly rotate the operator key and use a key management system to enhance security.

6. Implement additional checks or require additional signatures for critical operations, even when performed by the operator.

7. Add events for all critical actions taken by the operator to ensure transparency and allow for external monitoring.

Example implementation of a time-lock mechanism:

```solidity

    emit SignerRotationProposed(newSigners, block.timestamp + TIME_LOCK_PERIOD);
}

function executeSignerRotation(WeightedSigners memory newSigners, Proof calldata proof) external onlyOperator {

    require(operationTimeLocks[operationHash] != 0 && block.timestamp >= operationTimeLocks[operationHash], "Time lock not expired");
    delete operationTimeLocks[operationHash];
```
