# Vulnerability details

### Overview
The `approveMessages` function in the A[xelarAmplifierGateway.sol](https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/axelar-gmp-sdk-solidity/contracts/gateway/AxelarAmplifierGateway.sol#L83) contract is designed to approve an array of messages that have been signed by a valid set of Axelar signers. The `rotateSigners` function is responsible for updating the signer set over time. Both functions rely on the validation of signatures and signers through the `_validateProof` and `_validateSignatures` mechanisms. However, there is a critical flaw in how the contract handles signer validation across different epochs, potentially allowing an attacker to exploit outdated signers to approve unauthorized messages.

## Description
The core issue lies in the [_validateProof](https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/axelar-gmp-sdk-solidity/contracts/governance/BaseWeightedMultisig.sol#L114) function, which is supposed to ensure that the proof (signatures) corresponds to the current set of signers (based on the latest epoch). However, the function lacks a robust mechanism to cross-check the signerHash against the correct epoch in which those signers are valid. Specifically, the function checks if the signer's epoch exists but does not rigorously enforce that the signers being validated are from the most current epoch.

This oversight can lead to a situation where outdated signer sets (from previous epochs) are mistakenly considered valid. If an attacker possesses the private keys of an outdated signer set, they could craft a proof using these keys and submit it via the `approveMessages` function, bypassing the intended security that should restrict actions to the most recent and legitimate signers.

## Proof of Concept
```solidity
function approveMessages(Message[] calldata messages, Proof calldata proof) external {
        bytes32 dataHash = keccak256(abi.encode(CommandType.ApproveMessages, messages));

        _validateProof(dataHash, proof);

        _approveMessages(messages);
    }
```
```solidity
function _validateProof(bytes32 dataHash, Proof calldata proof) internal view returns (bool isLatestSigners) {
        BaseWeightedMultisigStorage storage slot = _baseWeightedMultisigStorage();

        WeightedSigners calldata signers = proof.signers;

        bytes32 signersHash = keccak256(abi.encode(signers));
        uint256 signerEpoch = slot.epochBySignerHash[signersHash];
        uint256 currentEpoch = slot.epoch;

        isLatestSigners = signerEpoch == currentEpoch;

        if (signerEpoch == 0 || currentEpoch - signerEpoch > previousSignersRetention) revert InvalidSigners();

        bytes32 messageHash = messageHashToSign(signersHash, dataHash);

        _validateSignatures(messageHash, signers, proof.signatures);
    }
```
###### Epoch 1: Initial Signer Set

- Signers: The contract begins with SignerSet1.
    - Mappings:
 - signerHashByEpoch[1] = hash(SignerSet1): Associates SignerSet1 with Epoch 1.
 - epochBySignerHash[hash(SignerSet1)] = 1: Links SignerSet1 to Epoch 1.
###### Epoch 2: New Signer Set

- Signers: The contract updates to SignerSet2.
   - Mappings:
 - signerHashByEpoch[2] = hash(SignerSet2): Associates SignerSet2 with Epoch 2.
 - epochBySignerHash[hash(SignerSet2)] = 2: Links SignerSet2 to Epoch 2.
###### Epoch 3: Current Signer Set

- Signers: The contract now operates with SignerSet3.
   - Mappings:
 - signerHashByEpoch[3] = hash(SignerSet3): Associates SignerSet3 with Epoch 3.
 - epochBySignerHash[hash(SignerSet3)] = 3: Links SignerSet3 to Epoch 3.

The attacker, possessing the private keys of SignerSet1, crafts a message and signs it using `SignerSet1`.
The attacker submits this message to the contract using the approveMessages function.
Inside `approveMessages`, `_validateProof` is called to verify the proof. Due to the flawed validation logic, _validateProof checks if SignerSet1 is associated with any valid epoch, but it fails to enforce that the proof must correspond to the current epoch (Epoch 3).
Consequently, the contract mistakenly accepts the proof, believing it to be valid.
The attacker’s message is approved, allowing them to execute unauthorized actions, such as approving fraudulent cross-chain communications or manipulating contract state.

The `_validateProof` function retrieves the `signers` set hash (signersHash) and attempts to validate it against the current epoch. The epoch is determined based on the stored `epochBySignerHash`, but the crucial cross-validation with `signerHashByEpoch` is missing. The expected validation check, such as:

```solidity
require(slot.signerHashByEpoch[signerEpoch] == signersHash, "Signer hash mismatch for the given epoch");
```
is absent. This omission permits an attacker to potentially use an outdated signer set (signersHash) that corresponds to an earlier epoch to falsely validate a message in the current epoch.

### Impact
The attacker could approve messages that should only be valid if signed by the latest, authorized signers.

Manual Review

## Recommended Mitigation Steps
- Cross-Validation of Epoch and Signer Hash:

  - Implement a stricter validation mechanism within `_validateProof` to ensure that the signer set being validated is not only valid but also belongs to the current epoch. This could be achieved by adding a requirement that cross-validates the signerHash with the signerHashByEpoch mapping.

```solidity
require(slot.signerHashByEpoch[currentEpoch] == signersHash, "Signer hash mismatch for the current epoch");
```
