# Vulnerability details

## Impact
The `ERC20Permit` contract implements EIP-2612 functionality, which includes a domain separator containing the chain ID in the signature schema. However, the chain ID is fixed at the time of deployment. In the event of a post-deployment hard fork of the chain, the chain ID cannot be updated, and signatures may be replayed across both versions of the chain. If a change in the chain ID is detected, the domain separator can be cached and regenerated.

## Proof of Concept
EIP-2612 Permit plays a pivotal role in allowing users to modify the allowance using a signed message rather than relying solely on the `msg.sender` (more details: https://eips.ethereum.org/EIPS/eip-2612).

However, the way implementations handle the chain ID presents a potential security vulnerability.

The chainId is included in the [DOMAIN_SEPARATOR](https://github.com/code-423n4/2024-08-axelar-network/blob/4572617124bed39add9025317d2c326acfef29f1/interchain-token-service/contracts/interchain-token/ERC20Permit.sol#L53-L55). However, it is not updatable. This chain ID is fixed at the time of deployment. In the event of a post-deployment chain hard fork, the chain ID cannot be updated, and signatures may be replayed across both versions of the chain.
```solidity
  function permit(address issuer, address spender, uint256 value, uint256 deadline, uint8 v, bytes32 r, bytes32 s) external {
        if (block.timestamp > deadline) revert PermitExpired();

        if (uint256(s) > 0x7FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF5D576E7357A4501DDFE92F46681B20A0) revert InvalidS();

        if (v != 27 && v != 28) revert InvalidV();

        bytes32 digest = keccak256(
            abi.encodePacked(
                EIP191_PREFIX_FOR_EIP712_STRUCTURED_DATA,
                DOMAIN_SEPARATOR(),
                keccak256(abi.encode(PERMIT_SIGNATURE_HASH, issuer, spender, value, nonces[issuer]++, deadline))
            )
        );

        address recoveredAddress = ecrecover(digest, v, r, s);

        if (recoveredAddress != issuer) revert InvalidSignature();

        // _approve will revert if issuer is address(0x0)
        _approve(issuer, spender, value);
    }
```
As a result, an attacker could reuse signatures to receive user funds on both chains.

# Exploit Scenario
Bob holds tokens worth $1,000 on the mainnet. Bob submits a signature to permit Eve to spend those tokens on his behalf. Later, the mainnet is hard-forked and retains the same chain ID. As a result, there are two parallel chains with the same chain ID, and Eve can use Bob’s signature to transfer funds on both chains.

## Recommended Mitigation Steps
To solve this issue, dynamically update the chain ID on each permit call so it reflects the current and correct chain.

OpenZeppelin's [ERC20Permit](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/0b58a783b9b33b63eef2994af8958c0c6a72dc51/contracts/token/ERC20/extensions/ERC20Permit.sol#L44-L67) addresses this issue by incorporating the `_hashTypedDataV4` and `_domainSeparatorV4` functions, which acquire the chain ID each time they're called, enhancing security against chain fork vulnerabilities.
```solidity
    function permit(
        address owner,
        address spender,
        uint256 value,
        uint256 deadline,
        uint8 v,
        bytes32 r,
        bytes32 s
    ) public virtual {
        if (block.timestamp > deadline) {
            revert ERC2612ExpiredSignature(deadline);
        }

        bytes32 structHash = keccak256(abi.encode(PERMIT_TYPEHASH, owner, spender, value, _useNonce(owner), deadline));

        bytes32 hash = _hashTypedDataV4(structHash);

        address signer = ECDSA.recover(hash, v, r, s);
        if (signer != owner) {
            revert ERC2612InvalidSigner(signer, owner);
        }

        _approve(owner, spender, value);
    }
```
