# Vulnerability details

## Impact


```rust
pub fn start_token_balance(
    storage: &mut dyn Storage,
    token_id: TokenId,
    chain: ChainName,
    track_balance: bool,
) -> Result<(), Error> {
    let key = TokenChainPair { token_id, chain };

    match TOKEN_BALANCES.may_load(storage, key.clone())? {
        None => {
            let initial_balance = if track_balance {
                TokenBalance::Tracked(Uint256::zero())
            } else {
                TokenBalance::Untracked
            };

            TOKEN_BALANCES
                .save(storage, key, &initial_balance)?
                .then(Ok)
        }
        Some(_) => Err(Error::TokenAlreadyRegistered {
            token_id: key.token_id,
            chain: key.chain,
        }),
    }
}
```

The bug in this function is a logic issue. When TOKEN_BALANCES.save() succeeds, it returns Ok(()), but the .then(Ok) call transforms this into Ok(()) again, effectively doing nothing. This means the function will always return Ok(()) when saving a new balance, regardless of whether the save operation actually succeeded or not. This could lead to silent failures where balance initialization appears to succeed but actually failed.


## Proof of Concept


1. Silent failures in balance initialization: When initializing a new token balance, failures would go unnoticed.
2. Inconsistent state: The contract might think a balance is initialized when it's not, leading to discrepancies.
3. Potential fund loss: If a balance isn't properly initialized, subsequent operations might fail or behave unexpectedly.

PoC flow:
1. Deploy ITS contract on Axelar.
2. Call `execute_message` with a `DeployInterchainToken` payload.
3. The function calls `start_token_balance`, which silently fails to save the initial balance.
4. Later, when processing an `InterchainTransfer`, the contract assumes the balance exists, potentially leading to incorrect calculations or operations.
