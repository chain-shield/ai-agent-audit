# Vulnerability details


## Description

The `InterchainTokenService` contract is designed to facilitate interchain token transfers. It includes an [`expressExecute()` function](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/interchain-token-service/contracts/InterchainTokenService.sol#L375-L396) that allows users to expedite the processing of interchain transfers by pre-funding the transfer with their own tokens. However, this function contains an issue that could lead to unauthorized token transfers and potential theft of funds.

The [`expressExecute()` function](https://github.com/code-423n4/2024-08-axelar-network/blob/69c4f2c3fcefb1b8eb2129af9c3685a44ae5b6fe/interchain-token-service/contracts/InterchainTokenService.sol#L375-L396) is public and can be called by anyone. It performs the following checks:

1. Verifies that the message type is `MESSAGE_TYPE_INTERCHAIN_TRANSFER`
2. Checks if the command has already been executed using `gateway.isCommandExecuted(commandId)`

If these checks pass, it proceeds to execute the transfer using the `_expressExecute()` function. The issue lies in the fact that there's no verification of whether the `commandId` corresponds to a valid, pending interchain transfer, nor any check that the `sourceChain` and `sourceAddress` parameters match the expected values for the pending transfer.

This lack of validation creates a scenario where an attacker can front-run legitimate interchain transfers, potentially stealing funds or disrupting the transfer process.

## Impact
This  allows an attacker to intercept and potentially steal legitimate interchain transfers. The attacker can front-run the original transaction, executing the transfer with their own tokens instead of the intended ones. This not only results in the theft of funds but also disrupts the entire interchain transfer mechanism, undermining the trust and reliability of the system.

The impact is severe as it directly affects the core functionality of the interchain token service. Users could lose their funds, and the integrity of cross-chain transactions would be compromised. This could lead to a loss of trust in the protocol and potential financial losses for users.

## Proof of Concept
1. Alice initiates a legitimate interchain transfer of 100 tokens from Chain A to Chain B.
2. The attacker observes this pending transfer in the mempool.
3. The attacker quickly submits their own `expressExecute()` transaction with the same `commandId` and payload, but a higher gas price to ensure it's mined first.
4. The attacker's transaction is processed:
   - It passes the checks in `expressExecute()` as the command hasn't been executed yet.
   - `_expressExecute()` transfers 100 of the attacker's tokens to the destination address.
5. When Alice's original transaction is processed, it reverts due to `AlreadyExecuted`.
6. The result: The attacker's tokens are sent instead of Alice's, effectively stealing the transfer.

Manual review

## Recommended Mitigation Steps
To address this vulnerability, implement additional validation checks in the `expressExecute()` function:

1. Verify that the `commandId` corresponds to a valid, pending interchain transfer.
2. Check that the `sourceChain` and `sourceAddress` match the expected values for the pending transfer.
3. Implement a time-lock mechanism to prevent front-running.
