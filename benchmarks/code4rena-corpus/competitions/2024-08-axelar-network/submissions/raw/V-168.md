# Vulnerability details

## Impact
The `interchainTransfer` function in the `InterchainTokenService` contract calls the `_takeToken` method to facilitate a token transfer. However, `_takeToken` is invoked with `msg.sender` being the `InterchainTokenService` contract itself, rather than the external user who originally called `interchainTransfer`. This inconsistency introduces potential security vulnerabilities, especially if `_takeToken` relies on `msg.sender` for permission checks or token management.

If the `_takeToken` method assumes that `msg.sender` is the original external caller, it might inadvertently grant permissions or perform operations based on an incorrect identity. For instance, in scenarios where `_takeToken` is expected to burn, transfer, or mint tokens, the method could execute these operations on behalf of the contract instead of the intended user. This can lead to unauthorized token movements, including the minting of new tokens, the burning of existing ones, or the unintended transfer of tokens, all of which could result in financial losses and compromise the contract’s integrity.

## Proof of Concept
https://github.com/code-423n4/2024-08-axelar-network/blob/main/interchain-token-service/contracts/InterchainTokenService.sol#L463

The vulnerability can be traced to the following line in the `interchainTransfer` function:

```
(amount, symbol) = _takeToken(tokenId, msg.sender, amount, false);
```

Here, `msg.sender` references the `InterchainTokenService` contract rather than the original user who initiated the transaction. Consequently, when the `_takeToken` method is executed, it may perform sensitive operations based on the assumption that `msg.sender` is the user, leading to potential security issues.

### Detailed Example

Consider a situation where an external user initiates a call to `interchainTransfer`. The function then invokes `_takeToken`, passing `msg.sender`, which at this point is the contract itself. If `_takeToken` includes logic like burning tokens or checking permissions based on `msg.sender`, the contract’s address is mistakenly granted authority. This could lead to the following issues:

- **Unauthorized Token Minting/Burning:** If `_takeToken` calls a minting or burning function, the contract might mint or burn tokens based on its own authority rather than the user's, leading to unauthorized changes in token supply.
- **Incorrect Balance Management:** The function might transfer or manage tokens incorrectly, assuming the contract itself has permissions that were intended for the user, potentially leading to the transfer of funds without the user’s consent.

For instance, the following operations might be affected:

```
function _takeToken(bytes32 tokenId, address from, uint256 amount, bool tokenOnly) internal returns (uint256, string memory symbol) {
    ...
    if (tokenManagerType == uint256(TokenManagerType.MINT_BURN)) {
        _burnToken(tokenManager, tokenAddress, from, amount);
    }
    ...
}
```

In this case, the `from` address, which is expected to be the original user, is instead the contract itself, potentially leading to unintended token burns.

## Recommended Mitigation Steps

To address this issue, modify the _takeToken method to explicitly pass the original caller (external user) as an argument rather than relying on msg.sender. This change ensures that the correct caller is used for any permission checks or token operations, preserving the intended behavior of the contract. Additionally, review all instances where _takeToken is utilized to confirm that this adjustment is consistently applied, safeguarding the contract from similar vulnerabilities.
