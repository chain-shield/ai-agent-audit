# Vulnerability details

As per the [README](https://code4rena.com/audits/2024-08-axelar-network), FOT & Rebase tokens are in scope, however, issues will arise whenever using these particular tokens. For example whenever using `apply_balance_tracking`:

```javascript
fn apply_balance_tracking(
    storage: &mut dyn Storage,
    source_chain: ChainName,
    destination_chain: ChainName,
    message: &ItsMessage,
) -> Result<(), Error> {
    match message {
        ItsMessage::InterchainTransfer {
->            token_id, amount, ..
        } => {
            // Update the balance on the source chain
            update_token_balance(
                storage,
                token_id.clone(),
                source_chain.clone(),
->                *amount,
                false,
            )
            .change_context_lazy(|| Error::BalanceUpdateFailed(source_chain, token_id.clone()))?;

            // Update the balance on the destination chain
            update_token_balance(
                storage,
                token_id.clone(),
                destination_chain.clone(),
->                *amount,
                true,
            )
            .change_context_lazy(|| {
                Error::BalanceUpdateFailed(destination_chain, token_id.clone())
            })?
        }
```

 When tokens are bridged from Chain A to Chain B, the `amount` is subtracted and added accordingly. However, if the token undergoes a rebase during this process, the rebase will not be reflected on the destination chain, effectively causing the rebased amount to be lost.

The same applies to FOT tokens, which include fees within their `amount` when, for example, bridging. This leads to inaccurate balance tracking.

### Recommendation
Introduce the logic to handle these type of tokens
