# Vulnerability details

**Impact**
The impact of this vulnerability is potentially severe. An attacker could exploit the lack of execution time limits and message size restrictions to cause Denial of Service (DoS) on the Axelar network or destination chains. This could lead to:

1. Blocking or significant delays in legitimate cross-chain transactions.
2. Resource exhaustion on Axelar relayers and validators.

In a worst-case scenario, this vulnerability could temporarily halt cross-chain operations, affecting the entire ecosystem that relies on Axelar for interoperability.

**Proof of Concept**
The vulnerability stems from the lack of strict size limits and execution time checks in the cross-chain message processing pipeline. An attacker can initiate a cross-chain call from a source chain (e.g., Ethereum Sepolia) with an abnormally large or computationally complex payload. This payload then propagates through the Axelar network to the destination chain (e.g., Avalanche Fuji), potentially causing issues at various stages.

The attacker constructs an extremely large payload on the source chain. the payload ican be within acceptable limits for the source chain but may exceed processing capabilities of the Axelar network or destination chain.

Let’s go into the Flow of this issue:
1. An attacker initiates the exploit by calling the `callContract()` function on the source chain (e.g., Ethereum Sepolia). This function accepts a payload of arbitrary size:

```solidity
function callContract(string calldata destinationChain, string calldata contractAddress, bytes calldata payload) external payable {
    _callContract(destChain, destAddress, msg.sender, payload);
}
```

The attacker can craft an abnormally large payload (e.g., several megabytes) or one that triggers complex computations. The source chain may accept this transaction if it meets local gas limits, even if it's impractical for cross-chain execution.

2. The large message enters the Axelar network through the `verify_messages()` function:

```rust
pub fn verify_messages(deps: DepsMut, msgs: Vec<Message>) -> Result<Response, ContractError> {
    // Verification logic here
}
```

This function, along with `route_messages()`, lacks explicit checks for message size or computational complexity:

```rust
pub fn route_messages(deps: DepsMut, msgs: Vec<Message>) -> Result<Response, ContractError> {
    // Routing logic here
}
```

The absence of these checks allows the oversized message to progress through the system unchallenged.

3. Proof Construction:
The `construct_proof()` function is called to create a proof for the destination chain:

```rust
pub fn construct_proof(deps: DepsMut, message_ids: Vec<CrossChainId>) -> Result<Response, ContractError> {
    // Proof construction logic
}
```

For an excessively large or complex message, this step could consume significant resources or time.


4. Finally, the message reaches the destination chain (e.g., Avalanche Fuji) where it's processed by the `execute()` function:

```solidity
function execute(bytes32 commandId, string calldata sourceChain, string calldata sourceAddress, bytes calldata payload) external {
    (bool success, bytes memory result) = address(contractAddress).call(payload);
}
```

This function attempts to process the entire payload. 

For an abnormally large or complex payload, this could lead to:
- Excessive gas consumption, potentially exceeding block gas limits
- Extended execution time, causing transaction timeouts inside Axelar network


#### Here is extended flow for the issue step-by-step:

- An attacker could craft an extremely large or complex payload in the callContract() function.
There doesn't appear to be a size limit on the payload parameter in the provided code.

- The verify_messages() function processes the incoming message.
If this function doesn't implement strict size or complexity checks, it could be vulnerable.

- The route_messages() function handles message routing.
Large messages could potentially cause performance issues here.

- The construct_proof() function builds the proof for the destination chain.
Complex messages might lead to resource-intensive proof construction.

- The relayer sends the transaction with executeData to the destination chain.
If executeData is excessively large, it might exceed gas limits on Avalanche Fuji.

- The execute() function on the destination AxelarGateway contract processes the payload.
This is a critical point where execution time limits could be hit.

- The final step where the payload is executed on the destination contract.
Complex payloads could cause out-of-gas errors here.

#### This vulnerability opens up several attack vectors:

1. Denial of Service (DoS): By repeatedly sending large messages, an attacker could congest the Axelar network and slow down or halt legitimate cross-chain operations.
2. Resource Exhaustion: Axelar relayers and validators could experience CPU, memory, or storage strain while processing these large messages.

The lack of explicit safeguards against these scenarios in the current implementation makes this a significant vulnerability in the Axelar network's cross-chain message processing system.

**Tools Used**
Manual Review

**Recommended Mitigation Steps**
Implement strict size limits for payloads at the entry points of the Axelar network. Add checks in the `callContract()` function and other relevant entry points.
