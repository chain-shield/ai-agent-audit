S-352
Swaps that occur earlier can affect swap amount out for later swaps and lead to unexpected reverts
gesha17
57
Sufficient
383d ago
Finding description and impact

The checkUpkeep function will call i_uniswapQuoterV2.quoteExactInput to get the amount received for each swap according to the swap path:

https://github.com/code-423n4/2024-12-chainlink/blob/main/src/SwapAutomator.sol#L489

  function checkUpkeep(
    bytes calldata
  ) external whenNotPaused cannotExecute returns (bool upkeepNeeded, bytes memory performData) {
    ...
        if (asset != address(i_linkToken)) {
          (amountOutUniswapQuote,,,) = i_uniswapQuoterV2.quoteExactInput(swapParams.path, swapAmountIn);
    ...
  }

This call performs an individual check for each swap, irrespective of other swaps. The problem is that this may not be an accurate representation of how the swaps that will occur in performUpkeep(), where an earlier swap may affect the slippage rate for a later swap. As a result of this swaps may unexpectedly fail if the slippage goes beyond the minAmountOut calculated by checkUpkeep but still remains above the maximum price deviation specified by the admin.

Proof of Concept

Suppose there are two input tokens Token_A and Token_B for performUpkeep().

The swap path for Token_A is Token_A -> LINK
The swap path for Token_B is Token_B -> Token_A -> LINK

First Token_A is swapped, then Token_B. As a result of this the earlier swap of Token_A -> LINK is going to affect the slippage for Token_B and may lead to an unexpected revert if the slippage for Token_B goes beyond the swapInput.minAmountOut but still remains above the maximum price deviation:

https://github.com/code-423n4/2024-12-chainlink/blob/main/src/SwapAutomator.sol#L634

  function swapWithPriceFeedValidation(
    IV3SwapRouter.ExactInputParams calldata swapInput,
    address asset,
    uint256 linkPriceFromFeed
  ) external returns (uint256 amountOut) {
    if (msg.sender != address(this)) {
      revert Errors.AccessForbidden();
    }
    // @audit revert will happen here, even though the maxPriceDeviation check below would have passed.
    amountOut = i_uniswapRouter.exactInput(swapInput);

    SwapParams memory swapParams = s_assetSwapParams[asset];
    uint256 assetPriceFromPriceFeed = _getValidatedAssetPrice(swapParams.oracle);
    uint256 linkAmountOutFromPriceFeed =
      _convertToLink(swapInput.amountIn, assetPriceFromPriceFeed, linkPriceFromFeed, IERC20Metadata(asset));

    if (
      amountOut < linkAmountOutFromPriceFeed.percentMul(PercentageMath.PERCENTAGE_FACTOR - swapParams.maxPriceDeviation)
    ) {
      revert InsufficientAmountReceived();
    }
    return amountOut;
  }

Note that this will only cause that particular swap to fail, and not the entire transaction.

Recommended mitigation steps

Mitigation is non-trivial. An idea would be to use i_uniswapRouter.exactInput in checkUpkeep as well, to keep it consistent with performUpkeep and provide a more accurate swap quote.

Hello Judge,

Thank you for your efforts. You are making the case that this issue will have minimal consequences, however I disagree. Even though the impact is "only" reverting swaps, the likelihood of that happening is practically certain as I show with the mainnet-fork tests below.

The sponsor and validator make the point that tokens will be well known and have swap pools with large liquidity, however let's consider the top 6 LINK swap pools on mainnet, as of writing of this escalation these are their locked liquidities:

WETH/LINK - 44.4M
UNI/LINK(0.3%) - 1.9M
SDL/LINK - 903k
USDC/LINK - 420k
UNI/LINK(1%) - 370k
USDT/LINK - 80k

Those can be verified here under the Pools tab.

We can deduce from this that swap paths with overlapping swaps will absolutely have to be used. I think we can safely assume that all tokens will most likely end up using the same overlapping final swap - WETH/LINK. I want to also note that the rest of the paths for each swap path are also very likely have other overlapping swaps.

PoC of reverting swaps for WETH/LINK pool with 44mil liquidity(largest one)

The following are two mainnet-fork test cases which show how many swaps are needed to have a swap revert at 50k USD value per swap(test show configuration of 30k min swap amount and 50k maximum swap amount) and 0.5% slippage(taken from contest readme) in the WETH/LINK pool, with the slippage calculated from the quoter and CL price feed respectively.

    function test_swaps_weth_link_pool_Uni_quote() public givenAssetEligibleForSwap(WETH) givenAssetEligibleForSwap(LINK) {

    _changePrank(address(this));

    // Building input params for the swapping through router
    IV3SwapRouter.ExactInputParams[] memory inputParams = new IV3SwapRouter.ExactInputParams[](2);
    inputParams[0] = IV3SwapRouter.ExactInputParams({
      path:bytes.concat(bytes20(WETH), bytes3(uint24(3000)), bytes20(LINK)),
      recipient: address(this),
      amountIn: amountInWeth,
      amountOutMinimum: amountOutMin

Run with forge test --mt test_swaps_weth_link_pool_CL_quote -vv. These tests can be added to performUpkeep.t.sol.

The result we get from the uniswap quoter test is that at the current 44mil TVL is that the swap will revert after the 4th swap. When using the CL price feed quote for minAmountOut at 0.5% slippage, none of the swaps go through. Increasing the slippage to 0.6% only lets 1 swap through with the 2nd swap already failing. This is quite extreme, as we show that even in the pool with the highest liqudity, already the second swap fails. The implication of this is that if such a swap would have been done via performUpkeep at the time of writing this, no more than 1 swap will go through.

Also, note that historically that pool's liquidity was often much lower than 44mil, if this test was done just a couple of months ago, the liquidity would have been less than half as much - around 20mil(link) making it much more likely to have reverts.

Also, consider that this is a best case scenario test that is using the pool with the largest liqudity. In contrast, the second largest pool the UNI/LINK pool with 1.9m liqudity has overlapping swap paths just out of question. Also, on other chains, LINK pools liquidity does not even come to close to 44m, so using overlapping paths there is also going to lead to reverts.

Conclusion

I believe the PoC very clearly shows that this will not be an "occasional" issue but a very regular one. Any call to performUpkeep with more than a single asset is very likely to result in a failed second swap. Considering the function is expected to handle much more than that, I believe this should be a valid concern to the sponsor. The checkUpkeep function will constantly fail to fulfill its main purpose - provide accurate inputs for performUpkeep, as such I strongly believe medium severity is very much justified.

Hey @gesha17, thank you for your PJQA contribution! I appreciate the real-world applicability analysis, but consider it flawed in several regards. Let me elaborate a bit on this using some of the parameters utilized.

The daily volume of the 44M pool is currently 10.4M in USD. That results in about 433k being exchanged every hour, or 7.2k being exchanged every minute. A delay of roughly 7 minutes between the invocation of checkUpkeep and performUpkeep is a realistic scenario, and the contest explicitly acknowledges these delays as well as MEV exploitation. Thus, 50k being assumed as having been swapped between the evaluation of upkeep and its execution is considered acceptable.

Additionally, the slippage control parameters can be adjusted to an arbitrary degree, and a 0.5% slippage on non-stablecoin assets is quite small. As an example, the Uniswap V3 UI (without accounting for all the above) automatically proposes a slippage value of 1.84% as of 01/19/2025 at 2:29 PM UTC for the ETH/LINK swap path on V3. The example of the README file is quite arbitrary and is listed as an example explicitly. Given that the Chainlink swap automator must accommodate for:

Delays between the evaluation of upkeep and its execution
The price impact of the swap itself
The natural deviations between the oracle reported prices and the AMM pool prices themselves
Potential MEV arbitrage that would push the swap percentage a bit consistently
Existing "classic" percentage-based slippage that is inherent to all AMMs, such as the 1.84% proposed by Uniswap

It is likely that at least simultaneous swaps of overlapping asset paths that involve 3-4 tokens will succeed. Failed swaps beyond these 3-4 tokens are acceptable and are instead skipped for the next automation trigger, they do not result in any Denial-of-Service.

This analysis still relies on a single swap path being used. The second highest-volume swap path still has over 500k in daily volume and can consume a 50k USD swap adequately, and it is always preferable to use the minimum swap steps possible so as to avoid each AMM pool's swap fees.

Culminating the above analysis I believe that a QA (L) severity rating adequately reflects the exhibit's severity.
