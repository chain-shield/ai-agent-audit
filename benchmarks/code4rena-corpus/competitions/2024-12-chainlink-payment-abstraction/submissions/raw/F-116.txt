Payment Abstraction System Will get completely DoS'ed if `8` tokens or more are allowlisted

Finding description and impact

Payment System is working by first calling checkUpkeep() then do performUpKeep() using the returned data from the checkUpKeep().

When calling checkUpKeep() we are checking all allowlisted tokens and check which tokens are available for getting swapped and transferred to Reserve contract.

SwapAutomator.sol#L450

>>  address[] memory allowlistedAssets = s_feeAggregator.getAllowlistedAssets();
    IV3SwapRouter.ExactInputParams[] memory swapInputs = new IV3SwapRouter.ExactInputParams[](allowlistedAssets.length);
    ...

>>  for (uint256 i; i < allowlistedAssets.length; ++i) { ... }
  }

We can see that in checkUpKeep(), we are calling FeeAggregator::getAllowlistedAssets(), which loops through all allowed listed tokens to check which one is ready.

This Will be our first point to go from desciping the bug.

First, we need to understand how checking and performing functions are made.

Our System (SwapAutomator) relies on ChainLink automation service, which in simple terms can be configured to do an action in a given period of time, or when a given event triggered.

The ChainLink Automation Process (in case of periodic action) simply waits a certain amount of time, and when this time passes, the off-chain does a trigger. Then, DONs (chainlink decentralized nodes) check for that given action to know whether they will perform it or not.

The process is simply: DONs trigger -> ChainLink Automatio Registry call checkUpKeep() -> ChainLink Automatio Registry call performUpKeep() -> performUpKeep() calls Forwarder.forward() -> SwapAutomator::performUpKeep()

ChainLink Automation has some restrictions and Limits that in case it exceeds Automation return performUpKeep value as false, making DONs ignore and not call performUpKeep()

ChainLink Automation | Ethereum

Condition	Max value
Maximum Check Data Size	5,000
Check Gas Limit	10,000,000
Perform Gas Limit	5,000,000
Maximum Perform Data Size	2,000

There are two checks for both functions (gas used, and data size). For checkUpKeep() we send 0 bytes data, and 10M gas is enough. The problem is in performUpKeep() limits.

Gas Limit Check for performUpKeep()

The maximum gas that can be used is 5M gas, since we are swapping tokens using Uniswap, in for loop it seems we can estimate gas cost used.

Doing performUpKeep() with single token single Pool token, the gas used is 227,346 (using Fork Test setup), so this means we can accept from 20 tokens to 22 tokens be swapped, at one time (in a single call), but in case of increasing, Automation DONs will not call performUpKeep().

PerformUpKeep() is simulated by DONs to know the gas cost it will take. So The OOG error that developers talk about will not even occur for too many tokens, as our system will not even call the function if it exceeds just 5M gas. This will make ChainLink Automation DONs always return performUpKeep() as false in case of more than 22 tokens are to get swapped.

This is just the first check, the second check is more critical here, which is data size.

Data size for performUpKeep()

The maximum allowed data to be called in performUpKeep() is 2,000. in our performUpKeep(), the data passed is the encoding of ExactInputParams array + a deadline.

IV3SwapRouter.ExactInputParams struct contains 2 uint256, one address, and one bytes array.

Using Solidity encoding method we can conclude the following encoding.

The path is the Uniswap Path it contains at least two addresses and fees in uint24, this means 43 bytes, since we use abi.encode in checkUpKeep() it will get padded to 64 bytes.

We will use the single swap path for easier calculations, which will make path takes two memory slots (64 bytes).

each slot takes 32 bytes, so the length of bytes with respect to number of tokens can be concluded as following.

Bytes Number = 32 * (3 + number of tokens * (8))

If number of tokens is 8, the number of bytes will be: 32 * (3 + 8 * 8) = 2144, which exceeds 2000.

So if there is only 8 tokens to be swapped at a single call, the number of returned bytes from checkUpKeep() will exceeds the Automation maximum check which will make the checking from DONs side return false, prevent calling the performUpKeep().

Impact

Now, we discussed how only 8 tokens are enough to make prevent DONs from executing Forwarder::forward() function, where Forwarder contract is also a contract in ChainLink Automation system, that should implement forward() function that makes Forwarder call a given function.

The issue will not just be a temporal DoS, where as we mentioned in the first point in the description, checkUpKeep() forces checking all allow listed tokens, so if we have 8 allowlisted tokens or more, and we reach a point where 8 of them or more are available for swapping, performUpKeep() will not get fired from Automations DONs as explained.

The system will reach a complete DoS state, where SwapAutomator will not be able to mitigate this thing, and allowlisted tokens will get stucked in FeeAggregator, This will prevent sending Tokens to the Reserve contract to pay service providers.

Admins can mitigate this DoS risk using two things.

emergencyWithdraw
unallowlist some tokens

The problem from these two mitigations is that they will just fix the current DoS, but will not prevent the DoS from occurring again, the system will get subjected to DoS again and again if just 8 tokens are to be supported.

Hey @Al-Qa-qa, thanks for your PJQA feedback! Let me get back to your concerns in a concise manner.

In relation to multiple tokens passing the USD threshold simultaneously, the USD threshold is meant to prevent miniscule-value swaps from incurring significant gas costs. Given that the tokens are typically EIPs with similar gas costs involved in a swap, the USD threshold is expected to be uniform across tokens with minor variations for edge cases all of which would represent the same net USD output that the Chainlink team finds acceptable.

Based on this assumption, the likelihood of 7-8+ tokens or more bypassing the USD threshold simultaneously would infer simultaneous Chainlink bridging and fee accumulation activity on 7-8+ distinct blockchains. The likelihood of that is low, as blockchain activity naturally deviates between chains based on their fluctuating gas costs, adoption, etc.

Chainlink's custom logic automation keepers (which the current implementation represents) are meant to be invoked every block to determine whether a transaction should be submitted, so we would need all 7-8+ tokens to simultaneously exceed their USD thresholds (directly correlated to the fees accumulated via their activity) on a single block.

Even if we consider this scenario a possible one, it is still circumventable via on-chain means by adjusting the USD thresholds of certain tokens and permitting the swaps to be executed with a temporary Denial-of-Service impact to Chainlink which is negligible.

Combining all the statements above, we can understand that a QA (L) severity rating is appropriate as:

Likelihood is low (even if we consider it moderate, it would still be QA (L) due to the below point)

Hey @Al-Qa-qa, thank you for your PJQA feedback! I advise against utilizing authoritative language when making assumptions, or statements which are not provable.

For example, you mention that the USD thresholds are not a sufficient mitigation; they are. Configuring the minSwapSizeUsd to a value such that minSwapSizeUsd * assetUnit == type(uint256).max effectively prevents the application of the attack. In all cases, it will be impossible to amass that amount of funds in the token denomination as built-in flash-loan tokens cannot be utilized (due to the attack taking place as a sandwich attack). As such, this mitigation measure is adequate.

An alternative mitigation measure would be to configure the oracle to the address 0 which would cause it to be effectively bypassed when building the performUpkeep payload. In any case, mitigations are trivial to implement in the scenario outlined using existing code.

Providing a response to each of your chapters:

Chapter 1: Swap USD Threshold

Your chapter focuses on advising me that my statement was incorrect, however, I did denote that the thresholds will be uniform with slight variations which remains true. Quoting my earlier reply:

In relation to multiple tokens passing the USD threshold simultaneously, the USD threshold is meant to prevent miniscule-value swaps from incurring significant gas costs. Given that the tokens are typically EIPs with similar gas costs involved in a swap, the USD threshold is expected to be uniform across tokens with minor variations for edge cases all of which would represent the same net USD output that the Chainlink team finds acceptable.

The USD threshold is uniform with slight variations based on the profitability of swaps (i.e. a token that incurs 20$ USD to swap due to multiple steps etc. will have a higher USD threshold than a token that can be directly swapped and incurs less gas to transact). In turn, this infers that with the assumption of a steady inflow, the USD thresholds will simultaneously be reached.

As your statement correctly denotes, it is not possible to estimate how these USD thresholds will be met when we deal with the dynamicity of markets, their liquidities, and other such factors. The scenario of 8 or more tokens simultaneously breaching the threshold via simultaneous bridging operations on the same block is therefore a single scenario with an extremely low likelihood.

I will reiterate that the SwapAutomator is deployed on the payment chain (Ethereum per the documentation) and that the scenario relies on simultaneous bridging operations as well (given that fees aggregate on target chains rather than the payment chain). This precondition alone is of low likelihood, and we are further reducing the overall likelihood of the vulnerability by mandating that at least 8 tokens or more simultaneously aggregate beyond their respective thresholds.

Chapter 2: Likelihood of Attack

The likelihood of the attack was never said to vanish, and the severity classification criteria must take into account the likelihood of the attack taking place. The scenario under which this issue will occur has an extremely low likelihood to the point of never being faced in production and being acceptable to acknowledge by the Chainlink team.

The assumptions about pausability etc. cannot be a factor in the likelihood of the attack, as a paused state of the forwarder is already an emergency scenario that would reasonably be mitigated by the swaps occurring manually via extraction of funds from the aggregator. As such, stating that Chainlink will allow fees to be "locked" in the contract until the reactivation of the off-chain forwarder is an invalid assumption.

Chapter 3: Severity Classification

The Chainlink team has already acknowledged that swaps may occasionally fail. The vulnerability describes a batch swap operation that may fail under specific circumstances, which would fall under the category of swaps occasionally failing (an AMM pool's manipulation can simultaneously happen for all pairs in a batch operation, and this is acknowledged).

This "Denial-of-Service" can be circumvented by directly swapping the assets by extracting them and reconfiguring each swap path's USD allowance/oracle as the most reasonable mitigations. The distribution of a swap's output LINK tokens already happens via a multi-signature transaction (as earmarks must be configured), so the immediate availability of the LINK tokens is not a critical security concern.

As the time involved in accessing the underlying swapped funds of a SwapAutomator transaction is equivalent to the time necessary to apply the swap mitigation, there is no practical impact on the overall protocol from this Denial-of-Service. Thus, we cannot insinuate that a would-be attacker would attempt to exploit this as gas-expenditure vulnerabilities have been ruled out as out-of-scope in historical C4 discussions (i.e. an attacker wasting gas to waste the gas of another user).

Conclusion

I am well aware of all Supreme Court rulings (I have cited them in several contests I have judged) and C4's severity classification criteria. Even taking all these into account, I struggle to see how we can consider this a medium-risk vulnerability.

The triggers for it are outside user control (as there is no incentive or impact to exploit them), and the likelihood of the trigger conditions occurring naturally is extremely low to the point of being inexistent. We cannot assume that all fees will simultaneously aggregate with a moderate likelihood and that they will be bridged to the main Ethereum SwapAggregator on the same block with a moderate likelihood.

Even if we are generous, the likelihood of such a combination of events is low, which, coupled with the medium impact outlined, would still result in a low severity rating. Arguably, even the impact being considered medium is generous as there is no critical security aspect around the availability of swapped outputs (as swaps may occasionally fail naturally due to the oracle prices not matching the AMM prices, etc.).

The code of how the SwapAutomator clearly depicts that immediate availability and capability to swap fee tokens is not a necessary trait as it implements several conditions to permit a swap to occur, and the risk of a swap failing is explicitly acknowledged.

To conclude, I never argued that the vulnerability is invalid or that it can never occur. I simply analyzed that its impact is medium at most, and its likelihood is extremely low which would result in a low severity rating per standard classification criteria.
