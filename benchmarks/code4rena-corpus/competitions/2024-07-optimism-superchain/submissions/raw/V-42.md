# Vulnerability details

## Summary

`FaultDisputeGame.sol`'s `move()` requires participants to provide the index(in `claimData`) of the parent claim. After that, it checks that `Claim _disputed` provided by the user is equals to the `parent.claim` which was introduced after another re-org related bug was found in the previous optimism sherlock audit.

However, <ins>the function fails to check that the `Position` of the node remains the same</ins>, which makes it susceptible to a different re-org attack.


## Proof of code

Let's consider an oridinary binary tree.
```
              1
              |
         ----- -----
        |           |
        2           3
        |           |
     --- ---     --- ---
    |       |   |       |
    4       5   6       7
    
```
```solidity
function test_Before_Reorg() public {
    address Alice = address(0x5);
    address Miner = address(0x10);
    vm.deal(Alice, 100 ether);
    vm.deal(Miner, 100 ether);

    Claim honest_counter = _dummyClaim();
    uint256 reqBond = _getRequiredBond(0);
    (,,,, Claim disputed,,) = gameProxy.claimData(0);
    vm.prank(Alice);
    gameProxy.move{ value: reqBond }(disputed, 0, honest_counter, true); // this node will be at Position 2(in the game binary tree)


    Claim node6_claim = _dummyClaim(); // Miner submits the correct hash for Position 6(in the game binary tree) to create a node at Position 4 instead
    reqBond = _getRequiredBond(1);
    (,,,,disputed,,) = gameProxy.claimData(1);
    vm.prank(Miner);
    gameProxy.move{ value: reqBond }(disputed, 1, node6_claim, true); // this node will be at Position 4(in the game binary tree)


    honest_counter = _dummyClaim();
    reqBond = _getRequiredBond(2);
    (,,,,disputed,,) = gameProxy.claimData(2);
    vm.prank(Alice);
    gameProxy.move{ value: reqBond }(disputed, 2, honest_counter, true); // Alice attacks the node at Position 4 as the claim submitted by the Miner is inaccurate for Position 4
}
```
<ins>**Sequence Walkthrough:**<ins>

It can be assumed in the code that `Alice` is the honest challenger while `Miner` is the malicious actor.
1. `Alice` disagrees with the root claim and attacks it, providing a `claim` for the node at `Position 2`(`Position` here refers to the position in the game binary tree)
2. Malicious `Miner` comes along and <ins>attacks</ins> Alice's `claim`, providing the correct hash for `Position 6`, but at the `Position 4` node instead, as the Miner sets <ins>`isAttack` to `true`</ins>.
3. `Alice` sees that the hash at `Position 4` isnt what it is supposed to be, and hence attacks it since she is a honest challenger.

Afterwards, suppose a re-org occurs and the order of the 3 transactions remain the same, but the `Miner` himself makes a small change to his transaction
```diff
  vm.prank(Miner);
-  gameProxy.move{ value: reqBond }(disputed, 1, node6_counter, true); //Miner's transaction before re-org
+  gameProxy.move{ value: reqBond }(disputed, 1, node6_counter, false); //Miner's newly edited transaction after re-org
```

After toggling the value of `isAttack`, the `Miner's` node in the game tree will now be at `Position 6` and the original hash that it submitted will be correct.

However, Alice will still end up attacking the accurate claim. This is because the Miner did not change the hash `Claim` and it will bypass the check:
> if (Claim.unwrap(parent.claim) != Claim.unwrap(_disputed)) revert InvalidDisputedClaimIndex();

Which means that `Alice`'s challenge will not revert after the re-org and will end up challenging a node with a different `Position` in the game tree.

Now the malicious `Miner` gets to keep his bond since the original `Claim` hash he submitted is accurate for `Position 6` and he can go on to counter `Alice`'s attack of his now accurate claim and steal her bond unfairly.

## Extra Note:
There is also an alternative way for the `Miner` to change the `Position` of his node after a re-org without toggling `isAttack`. Out of the 4 parameters:
> function move(Claim _disputed, uint256 _challengeIndex, Claim _claim, bool _isAttack) public payable virtual {

The `Miner` can change `Claim _disputed, uint256 _challengeIndex` while keeping `Claim _claim` the same, which will cause `Alice`'s challenge to not revert as well, resulting in her challenging a node with a <ins>different `Position`</ins> but same `_claim`, making her lose her bond.

## Recommended Mitigation Steps
Making the below changes should fix all the above mentioned exploits.
```diff
-  function move(Claim _disputed, uint256 _challengeIndex, Claim _claim, bool _isAttack) public payable virtual {
+  function move(Claim _disputed, uint256 _challengeIndex, Position _challengePosition, Claim _claim, bool _isAttack) public payable virtual {

...

  if (Claim.unwrap(parent.claim) != Claim.unwrap(_disputed)) revert InvalidDisputedClaimIndex();
+  if (Position.unwrap(_challengePosition) != Position.unwrap(parent.position)) revert InvalidDisputedPosition();
  // now both Claim and Position are checked :)
```
