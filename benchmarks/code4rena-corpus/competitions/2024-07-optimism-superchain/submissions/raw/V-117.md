# Vulnerability details

## Description
In the `PreimageOracle` and user can add data to it via multiple functions. Two of these are the `LPP` functions and `loadKeccak256PreimagePart`. Both of these use the same key-prefix of `0x02` as seen here:
`loadKeccak256PreimagePart`: `key := or(and(h, not(shl(248, 0xFF))), shl(248, 0x02))`  
`squeezeLPP`: `finalDigest := or(and(finalDigest, not(shl(248, 0xFF))), shl(248, 0x02))`

The key for `loadKeccak256PreimagePart` is based on the user-controlled arbitrarily long input:

```solidity
calldatacopy(ptr, _preimage.offset, size)
// Note that it includes the 8-byte big-endian uint64 length prefix.
// this will be zero-padded at the end, since memory at end is clean.
part := mload(add(sub(ptr, 0x08), _partOffset))
let h := keccak256(ptr, size) // compute preimage keccak256 hash
```

That means that if we know what the hash used by `squeezeLPP` has resulted from, we can possibly add a new entry with the calldata being that content, overwriting a valid `LPP` with different content.


## Impact
The impact of this is quite severe as a user could overwrite data of the oracle which is deemed to be trusted. It is breaking an invariant of the protocol, that noone can overwrite content at a certain key with different content mapped to that key.


## Tools Used
Manual review


## Recommended Mitigation Steps
I would recommend using a different key-prefix for `LPP`s, ensuring that the keys always differ by at least one byte.
