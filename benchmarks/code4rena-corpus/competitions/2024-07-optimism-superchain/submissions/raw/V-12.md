# Vulnerability details

## Impact

The `l2BlockNumber()` function uses a hard-coded offset (0x54) to retrieve data from calldata:

```solidity
function l2BlockNumber() public pure returns (uint256 l2BlockNumber_) {
    l2BlockNumber_ = _getArgUint256(0x54);
}
```

This approach is inflexible and prone to errors if the contract's structure or initialization parameters change. If the calldata layout is modified in future versions of the contract, this function could return incorrect data, potentially leading to logical errors in the dispute game.

The impact is primarily on the contract's maintainability and upgradability. While it doesn't pose an immediate critical vulnerability, it could cause significant issues during future upgrades or modifications to the contract's interface.

## Proof of Concept

The current implementation relies on the L2 block number being located at a specific offset in the calldata. If the contract's constructor parameters or initialization data structure changes, this offset may no longer be correct, leading to the function returning incorrect data.

## Recommended Mitigation Steps

- Use named parameters or a struct for initialization instead of relying on specific calldata offsets. This makes the code more resistant to changes in the contract's structure.

- Store the L2 block number as a state variable during contract initialization, rather than reading it from calldata each time.

- If the L2 block number must be dynamically accessible from calldata for some reason, consider using a more robust encoding scheme like ABI encoding, which is less prone to offset errors.
