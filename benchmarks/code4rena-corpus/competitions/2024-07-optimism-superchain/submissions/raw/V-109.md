# Vulnerability details

## Impact
Immutable ABSOLUTE_PRESTATE forces freqent redeployments and allows proving invalid withdrawals in case of block number since `ABSOLUTE_PRESTATE` is bigger than `1 << SPLIT_INDEX`.

## Proof of Concept
Optimism introduces `ABSOLUTE_PRESTATE` immutable value, as an absolute prestate to execution trace, which is source of truth in case of Cannon disputes:

```javascript
contract FaultDisputeGame is IFaultDisputeGame, Clone, ISemver {
    ////////////////////////////////////////////////////////////////
    //                         State Vars                         //
    ////////////////////////////////////////////////////////////////

    /// @notice The absolute prestate of the instruction trace. This is a constant that is defined
    ///         by the program that is being used to execute the trace.
    Claim internal immutable ABSOLUTE_PRESTATE;
```

It's used as the last execution trace that is considered fully legit for given game type. All disputes then base their withdrawal claims based of this value. It's also used in the last step of trace execution bisection game, in case of both challenger and defender disputing over the first execution step after `ABSOLUTE_PRESTATE`:

```javascript
    function step(
        uint256 _claimIndex,
        bool _isAttack,
        bytes calldata _stateData,
        bytes calldata _proof
    )
        public
        virtual
    {
        // [...]
        if (_isAttack) {
            // If the step position's index at depth is 0, the prestate is the absolute
            // prestate.
            // If the step is an attack at a trace index > 0, the prestate exists elsewhere in
            // the game state.
            // NOTE: We localize the `indexAtDepth` for the current execution trace subgame by finding
            //       the remainder of the index at depth divided by 2 ** (MAX_GAME_DEPTH - SPLIT_DEPTH),
            //       which is the number of leaves in each execution trace subgame. This is so that we can
            //       determine whether or not the step position is represents the `ABSOLUTE_PRESTATE`.
@>          preStateClaim = (stepPos.indexAtDepth() % (1 << (MAX_GAME_DEPTH - SPLIT_DEPTH))) == 0
@>              ? ABSOLUTE_PRESTATE
                : _findTraceAncestor(Position.wrap(parentPos.raw() - 1), parent.parentIndex, false).claim;
```

Highlighted code parts show exactly this. In case that both defender and challenger attack each other claims each time, that means each move is moving to the left child in the trace execution bisection game. If `stepPos.indexAtDepth() % (1 << (MAX_GAME_DEPTH - SPLIT_DEPTH))) == 0` - that is index of the position is 0 (first element in trace execution tree, hence it's modulo with trace execution tree depth is 0) - we are making move from the trusted `ABSOLUTE_PRESTATE` to the trace index `0`.

Now, `ABSOLUTE_PRESTATE` is set once during construction in `FaultDisputeGame`, while `DisputeGameFactory` only creates a smart contract clone to the deployed implementation via Clone With Immutable Args:
```javascript
    function create(
        GameType _gameType,
        Claim _rootClaim,
        bytes calldata _extraData
    )
        // [...]
@>      proxy_ = IDisputeGame(address(impl).clone(abi.encodePacked(msg.sender, _rootClaim, parentHash, _extraData)));
        proxy_.initialize{ value: msg.value }();
```

That means that each game has the same `ABSOLUTE_PRESTATE`. This is problematic because of the fact that Optimism produces blocks every 2 seconds. Given that split index is `21`, just like now on mainnet, it's able to hold ~49 days of blocks until the tree is filled completely up to split index 21. Here are the calculations:
```
> (1 << 21) / (60 * 60 * 24 / 2)
48.54518518518518
```

There are 2 problems stemming from this:

1. In order to prevent the tree overflow, new game contract, hence new game type has to be deployed every ~48 days.
2. In case that the tree overflows, which happens after `2097152` (1 << 21) blocks since `ABSOLUTE_PRESTATE`, it's impossible to create a claim whose first trace execution index could be attacked. Let me explain that by example:

* ABSOLUTE_PRESTATE - block 1, trace index 1000 (I assume that each block has 1000 execution traces, for the ease of calculations).

* block 2 - trace index 2000. Claims posted here can be disputed for the trace indexes 1000-2000.
...

* block 2097153 - trace index 2097153000. Claims posted here can be disputed for the trace indexes 1000-2097153000.
With this block we reached 1 << 21 possible blocks that consist of the tree with `SPLIT_INDEX = 21`.

* block 2097154 - trace index 2097154000. Claims posted here can be disputed for the trace indexes **2000**-2097154000.
This block is a turning point, because tree of `SPLIT_INDEX = 21` can only hold 2097152 blocks worth of traces. That means that our `ABSOLUTE_PRESTATE` is not able to be represented in this tree right now. Hence, any attack dispute over trace index 0 of this tree can't be done. That's because `ABSOLUTE_PRESTATE` points to execution trace `1000`, and current execution trace index 0 points to index `2000`, so such attack would have to prove that VM step from `1000` to `2001` is valid, which of course can't be proven. Hence, that means that such claim can't be attacked. In such case basically any malicious claim can be proven, because challenger is unable to attack it.

## Recommended Mitigation Steps
Quick solution is increasing `SPLIT_INDEX`. Each increase by 1 doubles the blocks that are required to fill the block tree. The problem however isn't fully solved here. Allowing some kind of dynamic `ABSOLUTE_PRESTATE` could solve the problem completely. That is use AnchorStateRegistry to hold more than just the last anchor, and allow `ABSOLUTE_PRESTATE` to be based of off anchor. Of course, additional measures not to impact active and new games has to be taken to solve th eproblem in this way.
