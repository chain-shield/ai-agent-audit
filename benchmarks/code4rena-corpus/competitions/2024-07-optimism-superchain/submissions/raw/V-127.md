# Vulnerability details

## Description
In order to add a large preimage to the oracle, a user needs to init it and then add leaves to it. When initing they set a `_claimedSize` which is the size of the finalized preimage. In order to finalize a `LPP`, which is required to get the initial bond back, the `LPP`'s size needs to match the `_claimedSize`.
Now when a user wants to finalize their proposal, they set `_finalize` when calling `addLeavesLPP`.
  
The problem arises, when a user adds more content to the `LPP` than `_claimedSize`, which is not prevented in any way.

```solidity
if (_finalize) {
    metaData = metaData.setTimestamp(uint64(block.timestamp));

    // If the number of bytes processed is not equal to the claimed size, the proposal cannot be finalized.
    if (metaData.bytesProcessed() != metaData.claimedSize()) revert InvalidInputSize();
}
```
Since there is no functionality which either prevents too much content added or allows for removal of leaves, the user's funds will be stuck as they cannot finalize their proposal anymore.


## Proof of Concept
This PoC shows, that we revert with `InvalidInputSize`, making it impossible to finalize the proposal, keeping the initially provided bond locked in the contract.
In order to run it, please add it to the tests in `PreimageOracle.t.sol` and execute it with `forge test --match-test test_addLeaves_funds_stuck -vv`.

```solidity
function test_addLeaves_funds_stuck() public {
    // Allocate the preimage data.
    bytes memory data = new bytes(136 * 3);
    for (uint256 i; i < data.length; i++) {
        data[i] = 0xFF;
    }

    // Initialize the proposal.
    oracle.initLPP{ value: oracle.MIN_BOND_SIZE() }(TEST_UUID, 0, uint32(data.length - 136));
    // Ensure that the proposal keys are present in the array.
    (address claimant, uint256 uuid) = oracle.proposals(0);
    assertEq(oracle.proposalCount(), 1);
    assertEq(claimant, address(this));
    assertEq(uuid, TEST_UUID);

    // Add the leaves to the tree (2 keccak blocks.)
    LibKeccak.StateMatrix memory stateMatrix;
    bytes32[] memory stateCommitments = _generateStateCommitments(stateMatrix, data);

    console.log("Commitments length: %d", stateCommitments.length);
    console.log("Data length: %d", data.length);

    uint256 tripPoint = stateCommitments.length / 3;
    bytes32[] memory commitmentsA = new bytes32[](tripPoint);
    bytes32[] memory commitmentsB = new bytes32[](tripPoint);
    bytes32[] memory commitmentsC = new bytes32[](tripPoint);
    for (uint256 i = 0; i < tripPoint; i++) {
        commitmentsA[i] = stateCommitments[i];
        commitmentsB[i] = stateCommitments[i + tripPoint];
        commitmentsC[i] = stateCommitments[i + (tripPoint * 2)];
    }

    // Adding all leaves without finalizing
    oracle.addLeavesLPP(TEST_UUID, 0, Bytes.slice(data, 0, 136), commitmentsA, false);
    oracle.addLeavesLPP(TEST_UUID, 1, Bytes.slice(data, 136, 136), commitmentsB, false);
    oracle.addLeavesLPP(TEST_UUID, 2, Bytes.slice(data, 136 * 2, 136), commitmentsC, true);

    console.log("after adding leaves");
    // This call only finalizes the proposal without adding new content
    oracle.addLeavesLPP(TEST_UUID, 3, "", new bytes32[](1), true);
}
```

## Recommended Mitigation Steps
In order to prevent this, I would recommend either adding functionality to remove leaves from a not-finalized tree or make it check the `proposalBytes` against `_claimedSize` also if `_finalized = false`. This would prevent the user from adding too many leaves.
