In order to resolve a claim this function is queried, now asides other computational costs _gas wise_ this function loops through  _numToResolve or the total number of challenges (challengeIndicesLen), whichever is smaller. The purpose of this loop is to process a specified number of challenges (_numToResolve) or all challenges if _numToResolve is set to 0, updating the resolution checkpoint as it goes. The loop then checks each challenge to see if it has been resolved and updates the checkpoint with information about the left-most counter if the challenge is uncountered and further left than the current left-most counter. This is part of the logic to resolve claims in a dispute game, potentially updating the state to reflect the resolution of subgames and distributing bonds accordingly.

Issue however is that this is costly, considering the amount of S-prefixed opcodes we are going to use.

This then means that a valid claim might not get resolved and the game is essentially stuck due to how expensive the _looping_ would be and revert due to an OOG, since around ~2000+ challenges alone would be needed to fill up the gas limit.

And this would be a viable scenario, having it that the `_numToResolve` could be `0`, where we'd then have to go through the whole subgames and encounter this revert.



## Impact
An unwanted state would be reached where we would have an unresolvable claim.
## Recommended Mitigation Steps
Quite a complex logic, but I think a good thing to do would be to consider a safer approach to claim resolutions, even if `_numToResolve` is set to 0, have a possible `max` value of subgames to go through at a time.
