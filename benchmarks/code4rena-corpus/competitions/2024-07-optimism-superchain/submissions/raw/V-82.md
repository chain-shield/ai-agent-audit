# Vulnerability details

## Description
In the fault dispute game, if there is no winner until the game is at `MAX_GAME_DEPTH` there is one more possibility for someone to contest a claim which is doing a `step` in the `MIPS VM`. For this, the attacker/defender needs to provide the `_stateData` for the claim which needs to match with the one specified in the to be contested claim (done by comparing the hash). In order for the game to decide whether the step is a valid attack/defense, it compares the result with a `postState` to check whether the execution resulted in the alleged result:

`FaultDisputeGame::step()`:
```solidity
// [...]
bool validStep = VM.step(_stateData, _proof, uuid.raw()) == postState.claim.raw();
bool parentPostAgree = (parentPos.depth() - postState.position.depth()) % 2 == 0;
if (parentPostAgree == validStep) revert ValidStep();
// [...]
parent.counteredBy = msg.sender; // [1] <----
```

Now the problem is, that the `VM` will gladly revert if it encounters an error such as division by zero. If now the VM reverts instead of returning a state, it is impossible to prove this claim as incorrect as the `step` would need to return successfully with a certain state to prove that the claim is wrong.
More concretely, the issue is, that `FaultDisputeGame::step()` does not handle the case where the call to `VM.step()` reverts.


## Impact
The result of this, is that an incorrect claim cannot be proven to be incorrect, leading to an incorrect game result breaking the invariant that `Dishonest actors should never be able to win the Fault Dispute Game.`


## Proof of Concept

The already existing test `test_div_byZero_fails` shows, that the `VM` will revert if there is an error:

```solidity
function test_div_byZero_fails() external {
    uint32 insn = encodespec(0x9, 0xa, 0x0, 0x1a); // div t1, t2
    (MIPS.State memory state, bytes memory proof) = constructMIPSState(0, insn, 0x4, 0);
    state.registers[9] = 5; // t1
    state.registers[10] = 0; // t2

    vm.expectRevert("MIPS: division by zero");
    mips.step(encodeState(state), proof, 0);
}
```

As pointed out above, in `FaultDisputeGame::step()`, `VM.step()` is called, meaning that if it reverts, the whole call will revert, making it impossible to get to `[1]` where the claim gets set to be `countered`.

Putting this together, a dishonest user can do the following:
* Start a dispute game with a `rootClaim` that contains one invalid `VM` instruction further down the line
* Honest challengers will try to counter it, therefore playing the game as-intended
* Once the game comes to `MAX_GAME_DEPTH`, the dishonest user can make a claim based on the one faulty state transition
* The honest challenger now executes `step`, trying to show that the state transition is incorrect. In a game where the state transition executes but is invalid, the honest challenger would be able to counter it with that
* In this case though, the call to `step` will revert, making it impossible to prove to the game that the claim is incorrect
* The dishonest user wins because the honest challenger was not able to set `counteredBy` on the incorrect claim

## Recommended Mitigation Steps
In order to not let a revert decide the game in favor of the proposer, I would suggest adding a `try-catch` block around the call to `VM.step()` and handling cases, where the step reverts, separately (In favor of the challenger).
