# Vulnerability details

## Description
Inside `PreimageOracle.loadBlobPreimagePart()` function, the following lines of code ensure that partial reads are possible:

```javascript
// Clean the word at `ptr + 0x28` to ensure that data out of bounds of the preimage is zero, if the part
// offset requires a partial read.
mstore(add(ptr, 0x28), 0x00)
```

Data that is `Out Of Bound` should always be cleaned up to facilitate partial reads.

The problem is that the cleaning of dirty bits is not enforced everywhere.

Let's take a look at the `loadPrecompilePreimagePart()` function. `loadPrecompilePreimagePart()` also facilitates the need of partial reads, however, the cleaning of bits is not correctly implemented.

Run the following PoC inside `PreimageOracle.t.sol`, it mocks a 5 byte partial read(the 2's):
```javascript
    function test_poc() public {
        // This is the payload, requires a partial read for the second word. Total length is 37.
        // 1111111111111111111111111111111111111111111111111111111111111111
        // 2222222222
        bytes memory input = hex"11111111111111111111111111111111111111111111111111111111111111112222222222";
        // We want to read the 2222222222
        uint256 offset = input.length + 4;
        address precompile = address(bytes20(uint160(0x04)));
        vm.breakpoint('o');
        bytes32 key = precompilePreimageKey(precompile, input);
        oracle.loadPrecompilePreimagePart(offset, precompile, input);

        bytes32 part = oracle.preimageParts(key, offset);
    }
```

- `0x2222222222111111111111222222222200000000000000000000000000000000`

By running `forge debug test/cannon/PreimageOracle.t.sol --tc PreimageOracle_Test --sig "test_poc()"` we can debug and see what the memory does when stepping through it.
This is the return value we get from calling the precompile

We can already see that the memory is filled with dirty bits.

This is the part that will be stored, filled with dirty bits:
- [Screenshot Forge Debug](https://ibb.co/LzTZTZn)
The stored data should be `0x2222222222000000000000000000000000000000000000000000000000000000", but the stored data will be `0x2222222222111111111111222222222200000000000000000000000000000000", as we can also see from the `test_output`.

This discrepancy happens because in this `calldatacopy()`, the `ptr` is of value `0x80 + 20 = 0x94`:
```javascript
            calldatacopy(add(20, ptr), _input.offset, _input.length)
```

However, when storing the result from calling the precompiled contract, the `ptr` is of value `0x80 + 8 = 0x88`:
```javascript
            // write precompile result status to the first byte of `ptr`
            mstore8(ptr, res)
```
The `result.length` is the same as `input.length`, which leads to the dirty bits still in memory.
Given that data integrity is being enforced wrt partial reads by ensuring that the non-partial-read parts are zero'ed out, this can result in undefined behavior. Crafty users can craft crafty payloads such that it proofs something that should not be proven.

## Recommended Mitigation Steps
Require dirty bits to be cleaned inside `loadPrecompiledPreimage`.
