# Vulnerability details

## Description
In order to propose a `LPP` in the `PreimageOracle`, one has to call `initLPP` with a `_claimedSize` which is the size of the final preimage. In order to finalize the large preimage, it needs to contain exactly `_claimedSize` bytes. This is also the only way to retrieve the funds locked into that proposal.

Looking at `initLPP`, we can see there are some checks on `_claimedSize`:

```solidity
function initLPP(uint256 _uuid, uint32 _partOffset, uint32 _claimedSize) external payable {
    // The bond provided must be at least `MIN_BOND_SIZE`.
    if (msg.value < MIN_BOND_SIZE) revert InsufficientBond();

    // The caller of `addLeavesLPP` must be an EOA, so that the call inputs are always available in block bodies.
    if (msg.sender != tx.origin) revert NotEOA();

    // The part offset must be within the bounds of the claimed size + 8.
    if (_partOffset >= _claimedSize + 8) revert PartOffsetOOB();

    // The claimed size must be at least `MIN_LPP_SIZE_BYTES`.
    if (_claimedSize < MIN_LPP_SIZE_BYTES) revert InvalidInputSize();

    // Initialize the proposal metadata.
    LPPMetaData metaData = proposalMetadata[msg.sender][_uuid];
    proposalMetadata[msg.sender][_uuid] = metaData.setPartOffset(_partOffset).setClaimedSize(_claimedSize);
    proposals.push(LargePreimageProposalKeys(msg.sender, _uuid));

    // Assign the bond to the proposal.
    proposalBonds[msg.sender][_uuid] = msg.value;
}
```
We can see that there is a check on the minimum size of `_claimedSize` but no enforced maximum. Now since it is a `uint32` it can hold a value of up to `0xffffffff = 4294967295 ~= 4 GB`.
If we now look at `addLeavesLPP`, we can see the following check:  
`if (blocksProcessed > MAX_LEAF_COUNT) revert TreeSizeOverflow();`

`blocksProcessed` is a counter, counting the added blocks which consist of 136 bytes each.

Looking at the definition of `MAX_LEAF_COUNT`:

```solidity
uint256 public constant KECCAK_TREE_DEPTH = 16;
/// @notice The maximum number of keccak blocks that can fit into the merkle tree.
uint256 public constant MAX_LEAF_COUNT = 2 ** KECCAK_TREE_DEPTH - 1;
```

If we now do the math, we get the following: `(2 ** 16) - 1 = 65535 blocks (=leaves)  ->  65535 * 136 = 8912760 Bytes`.  
So we got a maximum size of our proposal of `8912760 Bytes`. Once it is reached we cannot add leaves and cannot finish the proposal.


## Impact
Since `8912760 < 4294967295`, any user setting a `_claimedSize > 8912760` will not be able to finalize their `LPP`. This will lead to the user's bond to be locked in the contract permanently.


## Proof of Concept
The following PoC inits a `LPP` with a size greater than `8912760`, showing that it will revert, locking the bond in the contract.
To execute it, please add it to the tests in `PreimageOracle.t.sol` and execute it with `forge test --match-test test_locked_funds_claimedSize -vv`

```solidity
function test_locked_funds_claimedSize() public {
    // Allocate the preimage data.
    bytes memory data = new bytes(136 * 68698);
    for (uint256 i; i < data.length; i++) {
        data[i] = 0xFF;
    }

    // Initialize the proposal.
    oracle.initLPP{ value: oracle.MIN_BOND_SIZE() }(TEST_UUID, 0, uint32(data.length));
    // Ensure that the proposal keys are present in the array.
    (address claimant, uint256 uuid) = oracle.proposals(0);
    assertEq(oracle.proposalCount(), 1);
    assertEq(claimant, address(this));
    assertEq(uuid, TEST_UUID);

    // Add the leaves to the tree (2 keccak blocks.)
    LibKeccak.StateMatrix memory stateMatrix;
    bytes32[] memory stateCommitments = _generateStateCommitments(stateMatrix, data);

    console.log("Commitments length: %d", stateCommitments.length);
    console.log("Data length: %d", data.length);

    uint256 tripPoint = stateCommitments.length / 3;
    bytes32[] memory commitmentsA = new bytes32[](tripPoint);
    bytes32[] memory commitmentsB = new bytes32[](tripPoint);
    bytes32[] memory commitmentsC = new bytes32[](tripPoint);
    for (uint256 i = 0; i < tripPoint; i++) {
        commitmentsA[i] = stateCommitments[i];
        commitmentsB[i] = stateCommitments[i + tripPoint];
        commitmentsC[i] = stateCommitments[i + (tripPoint * 2)];
    }

    console.log(data.length);
    console.log(stateCommitments.length);

    oracle.addLeavesLPP(TEST_UUID, 0, Bytes.slice(data, 0, tripPoint * 136), commitmentsA, false);
    console.log("first done");

    // Move ahead one block.
    vm.roll(block.number + 1);

    oracle.addLeavesLPP(TEST_UUID, tripPoint, Bytes.slice(data, tripPoint * 136, tripPoint * 136), commitmentsB, false);
    console.log("second done");

    // Move ahead one block.
    vm.roll(block.number + 1);

    oracle.addLeavesLPP(TEST_UUID, tripPoint*2, Bytes.slice(data, tripPoint * 2 * 136, tripPoint * 136), commitmentsC, false);
    console.log("third done");
}
```

## Recommended Mitigation Steps
I would recommend adding a check to `initLPP` for whether `_claimedSize > (MAX_LEAF_COUNT * 136)` and revert if that is the case in order to prevent loss of funds for users.
