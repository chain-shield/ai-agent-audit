# Vulnerability details

The AssetRegistry contract is like a phonebook for assets. It should only list one asset per phone number (ERC20 address). However, there's a bug that lets someone list two different assets with the same phone number. This can cause problems later when trying to find or use these assets.

## Impact
* The [size()](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/AssetRegistry.sol#L191-L193) function of the AssetRegistry contract which returns the number of registered ERC20s, may provide an inaccurate count of the actual number of registered assets.

* When multiple assets are registered with the same ERC20 address, it becomes ambiguous which asset should be returned when querying the AssetRegistry using the [toAsset()](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/AssetRegistry.sol#L126-L129) function.

* The internal state of the AssetRegistry contract becomes inconsistent, as the `_erc20s` set and the assets mapping may have different sizes and mappings. This can cause issues with asset management, registration, and interactions with other components that depend on the integrity of the AssetRegistry.

## Proof of Concept
* Initially, the AssetRegistry is empty, and the `size()` function returns 0.

* An asset "AssetA" with ERC20 address "0x1234" is registered using the register() function. The `_erc20s` set is updated to include "0x1234", and the assets mapping associates "0x1234" with "AssetA". The `size()` function now returns 1.

* Later, a different asset "AssetB" with the same ERC20 address "0x1234" is registered using the [register()](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/AssetRegistry.sol#L78-L80) function. The `_register()` function checks if the ERC20 address is already present in the `_erc20s` set and finds that it is. However, it does not add the ERC20 address to the set again, even though the asset being registered is different.

* As a result, the `_erc20s` set remains unchanged, and the `size()` function still returns 1, even though two different assets are now associated with the same ERC20 address in the assets mapping.

The code responsible for this issue `_register()` function [AssetRegistry.sol: Lines 201-208](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/AssetRegistry.sol#L201-L208)
```solidity
function _register(IAsset asset) internal returns (bool registered) {
    require(
        !_erc20s.contains(address(asset.erc20())) || assets[asset.erc20()] == asset,
        "duplicate ERC20 detected"
    );

    registered = _registerIgnoringCollisions(asset);
}
```

## Recommended Mitigation Steps
The _register() function should be modified to ensure that the `_erc20s` set is properly updated whenever a new asset is registered, even if the ERC20 address is already present but associated with a different asset.
```diff
function _register(IAsset asset) internal returns (bool registered) {
-   require(
-       !_erc20s.contains(address(asset.erc20())) || assets[asset.erc20()] == asset,
-       "duplicate ERC20 detected"
-   );
+   IERC20Metadata erc20 = asset.erc20();
+   if (_erc20s.contains(address(erc20))) {
+       require(assets[erc20] == asset, "duplicate ERC20 detected");
+       return false;
+   }
+   _erc20s.add(address(erc20));

    registered = _registerIgnoringCollisions(asset);
}
```
I believe with this modification, the `_register()` function first checks if the ERC20 address is already present in the `_erc20s` set. If so, it verifies that the asset being registered matches the existing asset associated with that ERC20 address. If there is a mismatch, it reverts with an error message. If the ERC20 address is not present in the set, it adds it before proceeding with the registration process.
