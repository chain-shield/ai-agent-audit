# Vulnerability details

## Description

The `RTokenP1` contract implements a token issuance and redemption system with throttling mechanisms to control the rate of these operations. The [`issueTo()` function](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/RToken.sol#L105-L156) is responsible for minting new tokens and updating both issuance and redemption throttles. However, there is a critical flaw in how the redemption throttle is updated during token issuance.

In the [`issueTo()` function](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/RToken.sol#L105-L156), the redemption throttle is updated with a negative amount:

```solidity
File: RToken.sol
105:     function issueTo(address recipient, uint256 amount) public notIssuancePausedOrFrozen {

    // ... other code ...
    
120:         // Revert if issuance exceeds either supply throttle
121:         issuanceThrottle.useAvailable(supply, int256(amount)); // reverts on over-issuance
122:         redemptionThrottle.useAvailable(supply, -int256(amount)); // shouldn't revert
  
    // ... rest of the function ...
}
```

The `useAvailable()` function is designed to decrease the available capacity of the throttle. By passing a negative value, the function inadvertently increases the available redemption capacity instead of decreasing it. This misuse of the throttle mechanism can lead to a situation where the redemption limit is artificially inflated, potentially allowing users to bypass intended redemption restrictions.

## Impact
The incorrect throttle calculation can lead to an unintended increase in the available redemption capacity, potentially allowing more redemptions than intended. This can undermine the intended rate limits and affect the stability of the token's redemption process. 


## Proof of Concept
1. Attacker observes the current state of the redemption throttle.
2. Attacker calls `issueTo()` with a large `amount`, causing `redemptionThrottle.useAvailable()` to be called with a large negative value.
3. The redemption throttle's available capacity is incorrectly increased instead of decreased.
4. Attacker immediately calls `redeem()` or `redeemTo()` with an amount larger than what should be allowed by the throttle.
5. The redemption succeeds, bypassing the intended rate limiting.

## Recommended Mitigation Steps
Remove the incorrect update to the redemption throttle in the `issueTo()` function. The redemption throttle should only be updated during actual redemption operations, not during issuance.

Here's the recommended fix:

```diff
function issueTo(address recipient, uint256 amount) public notIssuancePausedOrFrozen {
    require(amount != 0, "Cannot issue zero");

    // == Refresh ==
    assetRegistry.refresh();

    // == Checks-effects block ==
    address issuer = _msgSender();

    require(basketHandler.isReady(), "basket not ready");
    uint256 supply = totalSupply();

    // Revert if issuance exceeds the supply throttle
    issuanceThrottle.useAvailable(supply, int256(amount)); // reverts on over-issuance
    
-   redemptionThrottle.useAvailable(supply, -int256(amount)); // shouldn't revert

    // ... rest of the function ...
}
```


This change ensures that the redemption throttle is not incorrectly manipulated during the issuance process, maintaining the integrity of the rate limiting mechanism for both issuance and redemption operations.
