# Vulnerability details

The RToken contract allows users to redeem their RTokens for a customized basket of underlying tokens through the `redeemCustom()` function. This enables users to specify the desired proportions of each token they wish to receive in exchange for their RTokens. However, there is an issue in the validation logic that can result in users receiving less than the minimum expected amounts of the redeemed tokens.

The `redeemCustom()` function performs a series of checks and calculations to determine the amounts of tokens to transfer to the user. One of these steps involves bounding the withdrawal amounts by the prorata share of the backing manager's token balances as mentioned in the [comment here](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/RToken.sol#L296). This is done to handle cases where the backing manager may be under-collateralized.

The problem is in the following code block: [RToken.sol:296-306](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/RToken.sol#L296-L306)
```solidity
// RToken.sol: Lines 296-306

// Bound each withdrawal by the prorata share, in case we're currently under-collateralized
for (uint256 i = 0; i < erc20s.length; ++i) {
    // {qTok} = {qTok} * {qRTok} / {qRTok}
    uint256 prorata = mulDiv256(
        IERC20(erc20s[i]).balanceOf(address(backingManager)),
        amount,
        supply
    ); // FLOOR

    if (prorata < amounts[i]) amounts[i] = prorata;
}
```
The problem is that while the code adjusts the `amounts` array based on the prorata share, it does not make a corresponding adjustment to the `minAmounts` array. As a result, even if the actual transferred amounts are less than the specified `minAmounts`, the function proceeds without reverting.

## Impact
* Users may receive less than the minimum expected amounts of tokens when performing a custom redemption. This violates the intended behavior of the function and can result in users not receiving the desired quantities of tokens.
* The discrepancy between the actual transferred amounts and the minAmounts array can lead to unexpected behavior in the system. Other components or functions relying on the assumption that users receive at least the minAmounts may behave incorrectly.
* In extreme cases, if the backing manager is severely under-collateralized, users may receive significantly less value than expected during redemptions. This can result in a loss of funds for users who were expecting to receive a certain minimum amount of tokens.

## Proof of Concept
In a scenario where:

* User (Alice) calls `redeemCustom()` with the following parameters:

   * `amount`: 1000 RTokens
   * `expectedERC20sOut`: [TokenA, TokenB]
   * `minAmounts`: [500, 300]

* The backing manager's balances are:

   * TokenA: 200
   * TokenB: 100

* During the execution of redeemCustom(), the pro-rata calculation in the aforementioned code block determines that Alice should receive:

   * TokenA: 200
   * TokenB: 100

* The amounts array is updated to reflect these prorata amounts. However, the `minAmounts` array remains unchanged.

* The function proceeds to transfer the tokens to Alice, even though the transferred amounts are less than the specified `minAmounts`.

* Alice receives 200 TokenA and 100 TokenB, which is less than the expected minimum amounts of 500 TokenA and 300 TokenB.

## Recommended Mitigation Steps
ensure that the `minAmounts` array is adjusted based on the actual transferred amounts [RToken.sol: Lines 296-306](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/RToken.sol#L296-L306)

By updating the `minAmounts` array to match the adjusted amounts, the function ensures that the post-checks accurately validate the received amounts against the expected minimums. If the backing manager's balances are insufficient to meet the `minAmounts`, the function should revert to prevent unfulfilled redemptions.
