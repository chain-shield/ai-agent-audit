# Vulnerability details

## Impact
Less transfer amounts are calculated in the P1 distributor due to the precision loss

## Description 
Solidity rounds down the result of an integer division, and because of that, it is always recommended to multiply before dividing to avoid that precision loss. In the case of a prior division over multiplication, the final result may face serious precision loss as the first answer would face truncated precision and then multiplied to another integer.

The problem arises in the distributor's distribution part. After fetching the total shares, the next step is to calculate the `tokensPerShare` which is then used to compute the transfer amounts and sending them to the allowed recipients. 

If we look deeply at the function `distribute()` we can see the transfer amounts calculation procedure is presented as:

```Solidity
    function distribute(IERC20 erc20, uint256 amount) external {

    ...

            totalShares = isRSR ? revTotals.rsrTotal : revTotals.rTokenTotal;
            if (totalShares != 0) tokensPerShare = amount / totalShares;
            require(tokensPerShare != 0, "nothing to distribute");
        }

    ...

            if (numberOfShares == 0) continue;
            uint256 transferAmt = tokensPerShare * numberOfShares;

    ...

    }
```
we can see that inside this pattern, there is a hidden division before a multiplication that makes round down the whole expression. This is bad as the precision loss can be significant, which leads the distributor to send less `transferAmt` than actual.

At the Proof of Concept part, we can check this behavior precisely.

## Proof of Concept
You can run this code to see the difference between the results:

```Solidity
    function test_precissionLoss() public {

        uint256 amount = 4.512317e19; // This number represents the `amounts`
        uint256 totalShares = 6.525132e18; // This number represents the total shares
        uint256 numberOfShares = 2.14235e18;
        uint256 tokensPerShare = amount / totalShares;

        uint256 transferAmount1 = tokensPerShare * numberOfShares;
        uint256 transferAmount2 = amount * numberOfShares / totalShares;
        
        console.log("Current Implementation   ", transferAmount1);
        console.log("Accurate Implementation  ", transferAmount2);
        assertNotEq(transferAmount1, transferAmount2);
    }
```

The result would be:

```  
     Current Implementation    12854100000000000000
     Accurate Implementation   14814968225853515300
```

This test shows that for a sample real data, the relative loss is around ~15.2%. Thus, we can see that the actual implementation produces less transfer amount than the precise method.

## Recommended Mitigation Steps

Consider modifying the transfer amount calculation to prevent such precision loss and prioritize the multiplication over division.
