# Vulnerability details

## Vulnerability Details

The constructor allows the `feeRecipient` to be set to the zero address (address(0)) without any checks. If this occurs, fees will be sent to the zero address until the owner manually updates the fee recipient, resulting in permanent loss of funds.

## Code Snippets
Constructor:
```solidity
constructor(RoleRegistry roleRegistry, address feeRecipient) {
    if (address(roleRegistry) == address(0)) {
        revert DAOFeeRegistry__InvalidRoleRegistry();
    }
    roleRegistry = roleRegistry;
    feeRecipient = feeRecipient;
}
```

## Impact
If the `feeRecipient` is set to address(0) in the constructor, all fees collected will be sent to the zero address until the owner calls `setFeeRecipient`. This results in permanent loss of funds, as there's no way to recover tokens sent to the zero address.

## Scenario
1. The contract is deployed with `feeRecipient` set to address(0) in the constructor.
2. Fees are collected and sent to the zero address.
3. Funds are permanently lost until the owner notices and updates the fee recipient.

## Fix
Add a check in the constructor to prevent setting the `feeRecipient` to address(0) initially:

```solidity
constructor(RoleRegistry roleRegistry, address feeRecipient) {
    if (address(roleRegistry) == address(0)) {
        revert DAOFeeRegistry__InvalidRoleRegistry();
    }
    if (feeRecipient == address(0)) {
        revert DAOFeeRegistry__InvalidFeeRecipient();
    }
    roleRegistry = roleRegistry;
    feeRecipient = feeRecipient;
}
```

This change ensures that the fee recipient cannot be set to the zero address during contract deployment, preventing potential loss of funds.

Additionally, it might be beneficial to add a getter function for `feeRecipient` to allow easy verification of its current value:

```solidity
function getFeeRecipient() external view returns (address) {
    return feeRecipient;
}
```

These modifications will significantly reduce the risk of fee loss due to an uninitialized fee recipient address.
