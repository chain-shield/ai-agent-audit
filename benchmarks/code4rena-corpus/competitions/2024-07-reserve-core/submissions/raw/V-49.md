# Vulnerability details

`payoutRewards` Assign reward payouts to the staker pool modifying the stakeRSR and payoutLastPaid variables as appropriate, given the current value of rsrRewards().

This function is been used in the `forwardRevenue` function and `seizeRSR` in the StRSR token

```solidity
 function _payoutRewards() internal {

        if (block.timestamp < payoutLastPaid + 1) return; <---
        uint48 numPeriods = uint48(block.timestamp) - payoutLastPaid;
...
        if (totalStakes >= FIX_ONE) {
           ...
            stakeRSR += payout; <--
        }

        payoutLastPaid += numPeriods; <---
        rsrRewardsAtLastPayout = rsrRewards();  <---

        
        stakeRate = (stakeRSR == 0 || totalStakes == 0) <---
            ? FIX_ONE
            : uint192((totalStakes * FIX_ONE_256 + (stakeRSR - 1)) / stakeRSR); //@audit-issue can this round to zero?

        emit RewardsPaid(payout);
        emit ExchangeRateSet(initRate, exchangeRate());
    }
```

As we can see the _payoutRewards is modifying the `stakeRate`, `payoutLastPaid` and `rsrRewardsAtLastPayout`, those are important variables used in the StRSR contract. Also we can see in the first arrow above that `_payoutRewards` can only be called once by timestamp.

The problem is that an attacker can always front run the `seizeRSR`, `stake`, and `unstake` calling `payoutRewards()` making  `stakeRate`, `payoutLastPaid` and `rsrRewardsAtLastPayout` the wrong values therefore `seizeRSR`, `stake`, and `unstake` also going to work with the wrong values.

Note that the `seizeRSR` function is the more  affected in this since is being called by the `backingManager` and it sent Rtokens before the `seizeRSR` call.

## Impact
To be more specific here in the impact:

`seizeRSR` function. An attacker can front run the `backingManager`  `seizeRSR` call, calling `payoutLastPaid` first, this is a problem because the `seizeRSR`  is not really taking in consideration the change of the `stakeRate` and other variables in the calculations. (see the description).



## Proof of Concept

The `payoutRewards()` is not implementing any access control (desgin choice)

```solidity

   function payoutRewards() external {
        _payoutRewards();
    }

```

In the arrow below we can see that `_payoutRewards()` function can be called just once for timestamp, so an attacker can front run any of the functions mention above calling  `payoutRewards()` with higher gas.

## Recommended Mitigation Steps

The more easy solution is consider `payoutRewards()` be an access control function since there is not really an incentive to call this function for a normal user.
