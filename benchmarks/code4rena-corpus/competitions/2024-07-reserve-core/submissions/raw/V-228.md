# Vulnerability details

## Vulnerability Details
The GnosisTrade contract is designed to facilitate batch auctions using the Gnosis EasyAuction mechanism. The init function is responsible for setting up the auction parameters and initiating the auction. In the init function, the contract calculates two different versions of the sell amount:

- sellAmount: Stored as a contract state variable, calculated from the input req.sellAmount.
- _sellAmount: A local variable used for initiating the Gnosis auction, which is adjusted for fees.


1. Initial Setup:
   - `initBal`: Set to the full balance of sell tokens when `init` is called.
   - `_sellAmount`: A reduced amount (adjusted for fees) used to initiate the Gnosis auction.

2. After Auction Settlement:
   - `sellBal`: The remaining balance of sell tokens in the contract after the auction settles.

3. Calculation in `settle`:
   ```solidity
   if (sellBal < initBal) {
       soldAmt = initBal - sellBal;
   }
   ```

The potential inaccuracy arises because `soldAmt` is calculated based on `initBal`, not the actual amount put into the auction (`_sellAmount`).

## Scenario
- `initBal` = 1000 tokens
- `_sellAmount` (used in auction) = 990 tokens (assuming 1% fee)
- All tokens in the auction are sold

After settlement:
- `sellBal` = 10 tokens (1000 - 990)
- Calculated `soldAmt` = 1000 - 10 = 990 tokens

While this calculation correctly reflects the number of tokens that left the contract, it doesn't accurately represent the auction's performance. The auction sold 100% of the tokens it was given (990), but the `soldAmt` calculation makes it appear as if only 99% (990/1000) were sold.

This discrepancy can lead to several issues:

1. Misrepresentation of Auction Efficiency: It may appear that the auction didn't sell all tokens, when in fact it did.

2. Incorrect Violation Reporting: The clearing price check uses `soldAmt` in its calculations. If this value is higher than the actual amount auctioned, it could lead to false violation reports or missed actual violations.

3. Inconsistent Accounting: Systems relying on this contract for accounting purposes might record incorrect sale amounts.

4. User Confusion: The origin of the trade might receive back more tokens than expected (the fee-adjusted difference), potentially causing confusion.

## Impact
- Potential false positives or negatives in violation reporting
- Inaccurate performance metrics for the auction
- Possible misalignment between expected and actual token movements

## Fix

To address this, the contract should consider:
1. Using the fee-adjusted amount (`_sellAmount`) consistently throughout the contract.
2. Storing both the original and fee-adjusted amounts as separate state variables.
3. Adjusting the `soldAmt` calculation to accurately reflect the auction's performance.
