# Vulnerability details



#### Summary

The `AssetRegistryP1` contract contains a public `refresh` function that can be called by any address. This function iterates over all registered assets and invokes their `refresh` methods. While this public access may not inherently introduce a direct security vulnerability, it poses risks related to gas costs and potential abuse.

#### Details

**Function in Question:**

```solidity
function refresh() public {
    uint256 length = _erc20s.length();
    for (uint256 i = 0; i < length; ++i) {
        assets[IERC20(_erc20s.at(i))].refresh();
    }

    basketHandler.trackStatus();
    lastRefresh = uint48(block.timestamp);
}
```

**Potential Issues:**

1. **Gas Costs:**
   - **Description:** The `refresh` function calls the `refresh` method of each registered asset. If any of these methods are costly in terms of gas, calling `refresh` can lead to high gas expenses. This could be exploited by malicious actors to increase the gas costs of contract interactions or to exhaust the gas available for other functions.
   - **Impact:** High gas costs may deter legitimate users and may also lead to denial of service if the contract runs out of gas.

2. **Public Accessibility:**
   - **Description:** The function is public, allowing anyone to call it. This opens up the possibility for abuse, where an attacker could repeatedly call this function to drive up gas costs or cause unintended behavior.
   - **Impact:** Unauthorized users can abuse the function, potentially leading to a DoS attack or manipulation of contract operations.

3. **State Integrity:**
   - **Description:** The `refresh` function updates the state of assets by calling their `refresh` methods. If the internal `refresh` functions of the assets are vulnerable or misbehave, this could affect the integrity of the `AssetRegistryP1` contract’s state.
   - **Impact:** Inconsistent or incorrect state updates could lead to incorrect asset information, impacting the functionality relying on accurate asset data.

#### Recommendations

1. **Implement Rate Limiting or Access Control:**
   - **Description:** To prevent abuse and excessive gas costs, consider restricting access to the `refresh` function. This can be achieved by implementing rate limiting or access control mechanisms.
   - **Example Implementation:**
     ```solidity
     mapping(address => bool) public authorized;

     modifier onlyAuthorized() {

     }
     ```

2. **Monitor Gas Usage:**
   - **Description:** Regularly monitor the gas usage of the `refresh` function to ensure it remains within acceptable limits. Adjust the function or asset `refresh` methods if gas consumption becomes problematic.

3. **Review Asset `refresh` Implementations:**
   - **Description:** Ensure that the `refresh` methods of all assets are secure and only perform necessary operations. Inconsistent or vulnerable implementations could affect the `AssetRegistryP1` contract's state.

4. **Consider Function Restrictions:**
   - **Description:** Evaluate if the `refresh` function needs to be public. If its functionality is critical and should be controlled, restricting access to governance or specific roles may be more appropriate.

#### Conclusion

The `refresh` function’s public accessibility and the potential for high gas costs warrant careful consideration and action. Implementing access control, monitoring gas usage, and reviewing asset methods will help mitigate risks and ensure the contract operates securely and efficiently.
