# Vulnerability details

## Description 

The [`redeemCustom` function](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/RToken.sol#L253-L345) in the `RToken` contract allows users to redeem their RTokens for a custom combination of historical baskets. The function is designed to ensure that the sum of the `portions` array equals `FIX_ONE`, which represents 100% of the redemption value. However, the function does not validate that each element in the `portions` array is within the valid range (i.e., between 0 and `FIX_ONE`). This oversight can lead to incorrect redemption amounts and potential under-collateralization.

The [`redeemCustom` function](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/RToken.sol#L253-L345) performs several key steps:
1. Refreshes the asset registry.
2. Checks if the `amount` to be redeemed is non-zero and if the caller has sufficient balance.
3. Ensures that the sum of the `portions` array is equal to `FIX_ONE`.
4. Updates the issuance and redemption throttles.
5. Calculates the number of baskets to be redeemed using `_scaleDown`.
6. Gets the basket redemption amounts from the `BasketHandler`.
7. Prorates the redemption amounts to ensure they do not exceed the available balances.
8. Distributes the tokens to the recipient.
9. Performs post-checks to ensure the recipient received the minimum expected amounts.

The issue lies in step 3, where the function checks if the sum of the `portions` array is equal to `FIX_ONE` but does not validate that each element in the `portions` array is within the valid range. This can lead to scenarios where the `portions` array contains invalid values, resulting in incorrect redemption amounts and potential under-collateralization.

## Impact
If the `portions` array contains values outside the valid range, it can lead to incorrect calculations of redemption amounts. This can result in under-collateralization, where the contract does not hold enough collateral to back the issued tokens. This issue can undermine the stability and trustworthiness of the contract, as users may receive more or less than their fair share of collateral during redemptions.

## Proof of Concept
1. A user calls the `redeemCustom` function with an `amount` of 1000 RTokens and a `portions` array containing values outside the valid range (e.g., [1.5 * FIX_ONE, -0.5 * FIX_ONE]).
2. The function calculates the sum of the `portions` array, which equals `FIX_ONE`, and proceeds without validating the individual elements.
3. The function calculates the basket redemption amounts based on the invalid `portions` array.
4. The user receives an incorrect amount of collateral, leading to under-collateralization of the contract.

## Recommended Mitigation Steps
Add a check to ensure each element in the `portions` array is within the valid range (i.e., between 0 and `FIX_ONE`). This can be achieved by adding the following validation within the loop that calculates the sum of the `portions` array:

```diff
function redeemCustom(
    address recipient,
    uint256 amount,
    uint48[] memory basketNonces,
    uint192[] memory portions,
    address[] memory expectedERC20sOut,
    uint256[] memory minAmounts
) external notFrozen {
    // == Refresh ==
    assetRegistry.refresh();

    // == Checks and Effects ==

    require(amount != 0, "Cannot redeem zero");
    require(amount <= balanceOf(_msgSender()), "insufficient balance");
    uint256 portionsSum;
    for (uint256 i = 0; i < portions.length; ++i) {
+       require(portions[i] <= FIX_ONE, "portion out of range"); // @audit - Added validation
        portionsSum += portions[i];
    }
    require(portionsSum == FIX_ONE, "portions do not add up to FIX_ONE");

    uint256 supply = totalSupply();

    // Revert if redemption exceeds either supply throttle
    issuanceThrottle.useAvailable(supply, -int256(amount));
    redemptionThrottle.useAvailable(supply, int256(amount)); // reverts on over-redemption

    // {BU}
    uint192 baskets = _scaleDown(_msgSender(), amount);
    emit Redemption(_msgSender(), recipient, amount, baskets);

    // === Get basket redemption amounts ===

    (address[] memory erc20s, uint256[] memory amounts) = basketHandler.quoteCustomRedemption(
        basketNonces,
        portions,
        baskets
    );

    // ==== Prorate redemption ====
    // i.e, set amounts = min(amounts, balances * amount / totalSupply)
    //   where balances[i] = erc20s[i].balanceOf(backingManager)

    // Bound each withdrawal by the prorata share, in case we're currently under-collateralized
    for (uint256 i = 0; i < erc20s.length; ++i) {
        // {qTok} = {qTok} * {qRTok} / {qRTok}
        uint256 prorata = mulDiv256(
            IERC20(erc20s[i]).balanceOf(address(backingManager)),
            amount,
            supply
        ); // FLOOR

        if (prorata < amounts[i]) amounts[i] = prorata;
    }

    // === Save initial recipient balances ===

    uint256[] memory pastBals = new uint256[](expectedERC20sOut.length);
    for (uint256 i = 0; i < expectedERC20sOut.length; ++i) {
        pastBals[i] = IERC20(expectedERC20sOut[i]).balanceOf(recipient);
        // we haven't verified this ERC20 is registered but this is always a staticcall
    }

    // === Interactions ===

    // Distribute tokens; revert if empty redemption
    {
        bool allZero = true;
        for (uint256 i = 0; i < erc20s.length; ++i) {
            if (amounts[i] == 0) continue; // unregistered ERC20s will have 0 amount
            if (allZero) allZero = false;

            // Send withdrawal
            // slither-disable-next-line arbitrary-send-erc20
            IERC20Upgradeable(erc20s[i]).safeTransferFrom(
                address(backingManager),
                recipient,
                amounts[i]
            );
        }
        if (allZero) revert("empty redemption");
    }

    // === Post-checks ===

    // Check post-balances
    for (uint256 i = 0; i < expectedERC20sOut.length; ++i) {
        uint256 bal = IERC20(expectedERC20sOut[i]).balanceOf(recipient);
        // we haven't verified this ERC20 is registered but this is always a staticcall
        require(bal - pastBals[i] >= minAmounts[i], "redemption below minimum");
    }
}
```
