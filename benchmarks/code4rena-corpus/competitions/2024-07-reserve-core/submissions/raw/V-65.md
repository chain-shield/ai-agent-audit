# Vulnerability details

## Description

The `BasketHandlerP1` contract manages the basket configuration, definition, and evolution over time for the protocol. A critical function within this contract is [`refreshBasket()`](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/BasketHandler.sol#L158-L169), which is responsible for updating the basket composition. This function interacts with [`_switchBasket()`](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/BasketHandler.sol#L654-L680), an internal function that attempts to create a new basket.

The issue arises from the inconsistent handling of the basket's state between these two functions. In `_switchBasket()`, the basket is immediately marked as disabled:

```solidity
function _switchBasket() private {
    disabled = true;
    // ... rest of the function
}
```

If the subsequent attempt to create a new basket fails, the function exits without re-enabling the basket or updating the `lastStatus` variable. This leads to a discrepancy between the actual state of the basket (disabled) and the recorded state (`lastStatus`), which remains unchanged.

The root of the problem lies in the `refreshBasket()` function's requirement check:

```solidity
require(
    main.hasRole(OWNER, _msgSender()) ||
        (lastStatus == CollateralStatus.DISABLED && !main.tradingPausedOrFrozen()),
    "basket unrefreshable"
);
```

This check relies on `lastStatus` being `CollateralStatus.DISABLED` for non-owner calls. However, if `_switchBasket()` fails to create a new basket, `lastStatus` isn't updated to reflect the disabled state, even though `disabled` is set to `true`.

As a result, subsequent calls to `refreshBasket()` by non-owner addresses will fail, as the `lastStatus` doesn't accurately represent the basket's disabled state. This creates a situation where the basket becomes permanently disabled, with no mechanism for recovery without owner intervention.

## Impact

The protocol can be left in a permanently disabled state, preventing the issuance of new tokens and other critical functions. This creates a single point of failure in the basket refresh mechanism and can halt the protocol's core functionality. An attacker could potentially exploit this by causing `_newBasket.nextBasket` to fail consistently, leading to a denial of service.


## Proof of Concept

1. An event occurs that requires a basket refresh (e.g., a collateral becomes disabled).
2. The `refreshBasket()` function is called by a non-owner address.
3. Inside `_switchBasket()`, `disabled` is set to `true`.
4. The `_newBasket.nextBasket()` call fails for some reason (e.g., external dependency issue).
5. `_switchBasket()` exits without updating `lastStatus` or resetting `disabled`.
6. The basket is now in a disabled state, but `lastStatus` doesn't reflect this.
7. Future calls to `refreshBasket()` by non-owner addresses will fail due to the requirement check.
8. The basket remains permanently disabled, preventing critical protocol functions.
