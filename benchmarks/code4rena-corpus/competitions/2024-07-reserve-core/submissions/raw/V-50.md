# Vulnerability details

`melt function`  Performs any melting that has vested since last call. Also it control the payout balance:

```solidity

 function melt() public {
        if (uint48(block.timestamp) < uint64(lastPayout + 1)) return; <---

        // # of whole periods that have passed since lastPayout
        uint48 numPeriods = uint48((block.timestamp) - lastPayout);

        // Paying out the ratio r, N times, equals paying out the ratio (1 - (1-r)^N) 1 time.
        uint192 payoutRatio = FIX_ONE.minus(FIX_ONE.minus(ratio).powu(numPeriods));

        uint256 amount = payoutRatio.mulu_toUint(lastPayoutBal);

        lastPayout += numPeriods;
        lastPayoutBal = rToken.balanceOf(address(this)) - amount;
        if (amount != 0) rToken.melt(amount);
    }


```
[[Link]](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/Furnace.sol#L65)

As you can see in the arrow above this function can only be called once per timestamp, this open the door for attackers front running this function calling it before some important action  is triggered.

We can see the `_distributeTokenToBuy` function in the RevenueTrader:

```solidity
 function _distributeTokenToBuy() internal {
        uint256 bal = tokenToBuy.balanceOf(address(this));

        tokenToBuy.safeApprove(address(distributor), bal);

        // do not need to use AllowanceLib.safeApproveFallbackToCustom here because

```
[[Link]](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/RevenueTrader.sol#L189C4-L197C6)

The `distributor` then sent the tokens to the `Furnance` and call `melt` in the `Furnance ` but an attacker can front run this call calling melt first then the `_distributeTokenToBuy` is returning and not doing the corresponding `melt` when the `melt` is called successfully not distributing this tokens and affecting the variables involved

## Impact
An attacker can just call melt front running important actions of the protocol leading to misconfigure and undesirable behavior.

We also can read in the `issueTo` function in the `Rtoken`:

```
 // AT THIS POINT:
        //   all contract invariants hold
        //   furnace melting is up-to-date <---
        //   asset states are up-to-date
        //   throttle is up-to-date
```

It say that  furnace melting is up-to-date but that not true because an attacker can always front run the call.

Distributor (depend of the path) then sent the tokens to the `Funance` and then call melt function. this melt function then call `melt` function in the `Rtoken`:

```solidity
  function melt(uint256 amtRToken) external {
        address caller = _msgSender();
        require(caller == address(furnace), "furnace only");
        _burn(caller, amtRToken);  <----
        emit Melted(amtRToken);
```

`_burn` function is modifying the total supply, so an attacker can just call melt when he distributor tx is coming, front running the melt function and then  using this this not completely state to take advantage in the function that use the totalSupply in the rtoken.
