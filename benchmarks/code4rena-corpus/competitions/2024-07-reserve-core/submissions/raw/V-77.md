# Vulnerability details

`issueTo()` function has a flaw that causes token issuance to become inconsistent if the function is called multiple times in quick succession. The problem stems from the `_scaleUp()` function, which uses the current `totalSupply()` for its calculations, rather than the original supply. This leads to incorrect amounts of RTokens being minted during each subsequent call.

function _scaleUp(

This inconsistency results in users receiving fewer tokens than expected for the same amount of collateral in subsequent issuances within the same transaction or block, effectively increasing the price of RTokens for later issuances.

## Impact
* Users issuing RTokens in quick succession receive fewer tokens than expected for the same collateral amount.
* Inconsistent pricing of RTokens within the same transaction or block.

## Proof of Concept
When calculating the `amtRToken` to mint, it uses the current `totalSupply` instead of the initial supply. This causes the second issuance to mint fewer tokens than expected, as the total supply has already increased from the first issuance.

* Alice calls `issueTo()` with 100 units of collateral, receiving 100 RTokens.
* Bob immediately calls `issueTo()` with 100 units of collateral in the same transaction.
* Bob receives less than 100 RTokens due to the increased `totalSupply` from Alice's issuance.

## Recommended Mitigation Steps
Modify the `_scaleUp()` function to use the initial supply passed as an argument, rather than calling `totalSupply()` again.
```diff
function _scaleUp(
    address recipient,
    uint192 amtBaskets,
    uint256 initialSupply
) private {
    uint256 amtRToken = initialSupply != 0
-       ? amtBaskets.muluDivu(totalSupply(), basketsNeeded)
+       ? amtBaskets.muluDivu(initialSupply, basketsNeeded)
        : amtBaskets;
    // ...
}
```
