# Vulnerability details


## Proof of Concept

First look [M-15 from one of the previous audit reports](https://github.com/code-423n4/2024-07-reserve/blob/main/audits/Code4rena%20Reserve%20Audit%20Report%20-%20Release%202.1.0.md#m-15-the-furnacemelt-is-vulnerable-to-sandwich-attacks).

TLDR of the report was that malicious users can exploit Furnace.sol's `melt()` function to gain more RToken appreciation benefits through flashloan sandwich attacks, reducing the benefits for long-term RToken holders and potentially decreasing liquidity in RToken pools. To mitigate this, it is recommended to distribute rewards based on time-weighted shares or to use a very small reward period and reward ratio, lowering the upper limits of MAX_RATIO and MAX_PERIOD.

Now as a fix, [this](https://github.com/reserve-protocol/protocol/pull/571) was deployed by the Reserve team, where there is [now a `PERIOD` variable](https://github.com/reserve-protocol/protocol/blob/27a3472d553b4fa54f896596007765ec91941348/contracts/p1/Furnace.sol#L16) set ti the time it takes to mine a block and then this var is directly used to get the `numPeriods` while melting, see https://github.com/reserve-protocol/protocol/blob/27a3472d553b4fa54f896596007765ec91941348/contracts/p1/Furnace.sol#L70

```solidity
        uint48 numPeriods = uint48((block.timestamp) - lastPayout) / PERIOD;

```

Issue here is this division no longer exist in the scope neither does the `PERIOD` variable and this is how melting is being done https://github.com/code-423n4/2024-07-reserve/blob/825e5a98a8c94a7b4458b3b359a507edb9e662ba/contracts/p1/Furnace.sol#L65-L79

```solidity
function melt() public {
  if (uint48(block.timestamp) < uint64(lastPayout + 1)) return;

  // # of whole periods that have passed since lastPayout
  uint48 numPeriods = uint48((block.timestamp) - lastPayout);

  // Paying out the ratio r, N times, equals paying out the ratio (1 - (1-r)^N) 1 time.
  uint192 payoutRatio = FIX_ONE.minus(FIX_ONE.minus(ratio).powu(numPeriods));

  uint256 amount = payoutRatio.mulu_toUint(lastPayoutBal);

  lastPayout += numPeriods;
  lastPayoutBal = rToken.balanceOf(address(this)) - amount;
  if (amount != 0) rToken.melt(amount);
}

```

Which leaves it susceptible to the bug case from M-15 since it's now unfixed.

## Impact

As hinted in [M-15 from one of the previous audit reports](https://github.com/code-423n4/2024-07-reserve/blob/main/audits/Code4rena%20Reserve%20Audit%20Report%20-%20Release%202.1.0.md#m-15-the-furnacemelt-is-vulnerable-to-sandwich-attacks), malicious users can get more of the RToken appreciation benefit brought by `Furnace.melt()`, and long-term RToken holders will get less benefit.

RToken holders will be less willing to provide liquidity to RToken pools (such as uniswap pools), resulting in less liquidity of RToken.

## Recommended Mitigation Steps

Consider re-applying the fix deployed here: https://github.com/reserve-protocol/protocol/pull/571, but in this case have it in mind that since per the readMe the protocol is not only going to be deployed on the Ethereum mainnet then the `PERIOD` value should be decided based on that.
