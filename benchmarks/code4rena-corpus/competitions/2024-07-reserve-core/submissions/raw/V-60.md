# Vulnerability details

## Description 

The `RevenueTraderP1` contract is designed to settle trades and distribute the bought tokens. The [`settleTrade` function](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/RevenueTrader.sol#L54-L65) calls `super.settleTrade(sell)` to settle a trade and then attempts to distribute the bought tokens using `distributeTokenToBuy`. The error handling for `distributeTokenToBuy` is implemented using a `try-catch` block, which only reverts if the error data is empty, typically indicating an out-of-gas (OOG) error. This approach can lead to silent failures for any other type of error, resulting in incomplete operations and potential for stuck funds.

The [`settleTrade` function](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/RevenueTrader.sol#L54-L65) is intended to perform two main tasks: settle a trade and distribute the bought tokens. If the distribution fails and the error is ignored, the function will return successfully, misleading users and other parts of the system into thinking that both tasks were completed. This can lead to a situation where the contract's state is inconsistent with the expected state, specifically resulting in tokens being stuck in the contract without being distributed.

The relevant part of the code is as follows:


The issue arises because the `try-catch` block catches all errors and only reverts on OOG errors, ignoring other types of errors. This can lead to incomplete operations where the trade is settled, but the distribution fails without any indication. If the distribution fails consistently for reasons other than OOG, the bought tokens could accumulate in the contract without being distributed, effectively becoming stuck.

## Impact
The impact of this finding is significant because it can lead to a situation where the contract's state is inconsistent with the expected state. Specifically, it can result in tokens being stuck in the contract, which can affect the overall functionality and efficiency of the system. 

## Proof of Concept
1. A trade is successfully settled using `super.settleTrade(sell)`.
2. The `distributeTokenToBuy` function is called.
3. `distributeTokenToBuy` fails due to a reason other than OOG (e.g., a transfer fails, or there's a logic error in the distribution).
4. The error is caught in the catch block, but since it's not an OOG error, it's ignored.
5. The `settleTrade` function returns successfully, even though the distribution failed.
6. The bought tokens accumulate in the contract without being distributed, effectively becoming stuck.

## Recommended Mitigation Steps
To ensure that any failure in `distributeTokenToBuy` will cause `settleTrade` to revert, maintaining the atomicity of the operation, the error handling should be modified as follows:

```diff
function settleTrade(IERC20 sell) public override(ITrading, TradingP1) returns (ITrade trade) {
    trade = super.settleTrade(sell); // nonReentrant

-   // solhint-disable-next-line no-empty-blocks
-   try this.distributeTokenToBuy() {} catch (bytes memory errData) {
-       // untested:
-       //     OOG pattern tested in other contracts, cost to test here is high
-       // see: docs/solidity-style.md#Catching-Empty-Data
-       if (errData.length == 0) revert(); // solhint-disable-line reason-string
-   }
+   // Call distributeTokenToBuy and revert on any error
+   (bool success, bytes memory returnData) = address(this).call(abi.encodeWithSelector(this.distributeTokenToBuy.selector));
+   if (!success) {
+       // If the call was reverted, bubble up the revert reason
+       assembly {
+           revert(add(returnData, 32), mload(returnData))
+       }
+   }
    // unlike BackingManager, do _not_ chain trades; b2b trades of the same token are unlikely
}
```


This modification ensures that any failure in `distributeTokenToBuy` will cause `settleTrade` to revert, preventing silent failures and ensuring that the operation is atomic.
