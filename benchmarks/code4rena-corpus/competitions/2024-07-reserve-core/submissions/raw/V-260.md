# Vulnerability details

## Impact
The `Governance::cancel()` function overrides the `cancel` implementation from OpenZeppelin's `Governor.sol`. However, it is impossible to use `cancel` in a meaningful context because the require statement in `cancel` requires `startedInSameEra` to return false for the function to execute.

The critical problem here is that for a proposal to be queued or executed, `startedInSameEra` needs to return true, meaning it is impossible to `cancel` any proposal that is queueable or executable, and we cannot bypass this require with any role, making it completely impossible. If it is not the same era, `queue` and `execute` will not work anyway and *anyone can run cancel*. The sponsor has also tested it before [and is aware](https://github.com/code-423n4/2024-07-reserve/blob/main/test/Governance.test.ts#L568) that anyone can cancel if its different era.

As a result, it is impossible for the protocol to `cancel` malicious governance proposals if its the same era and it is impossible for governance to work if its the different era.

## Proof of Concept
As you can see, if it is the same era, `queue` and `execute` can be run but `cancel` cannot be run, if it is the different era, `queue` and `execute` cannot be run and everyone can run `cancel`;

Also, the lack of this access control can cause a lot of different problems.

## Tools Used

Neovim, Hardhat

## Recommended Mitigation Steps

Make sure that `cancel` *can be run* at a time when `execute` and `queue` can be run, or allow a special role to bypass this check.
