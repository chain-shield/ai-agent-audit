# Vulnerability details

## Impact
The `AssetRegistryP1` contract determines asset validity based on `this.version()`. However, the system does not verify if the version of `AssetRegistryP1` aligns with the version of the `deployer` or `main` contract. Furthermore, when the `VersionRegistry` invalidates a specific version, it does not synchronously update the validity of assets in that version within the `AssetPluginRegistry`. This discrepancy creates a potential vulnerability.

- Security Bypass: Malicious operators could intentionally provide an AssetRegistryP1 with a lower version(), exploiting previously established validity to bypass the assetPluginRegistry.isValidAsset() check for assets that should be invalid.  
- Unauthorized Asset Usage: This vulnerability could allow the use of deprecated or potentially unsafe assets within the system.  
- System Integrity Compromise: The ability to use invalid assets could lead to unexpected behavior and potentially compromise the entire system's integrity.    

## Proof of Concept
1. The system is initially deployed with version 3.0.0, and token A is registered as a valid asset.  
2. The system is upgraded to version 4.0.0. However, the VERSION constant in the Versioned contract (inherited by ComponentP1, which AssetRegistryP1 extends) is intentionally set to 3.0.0 instead of 4.0.0.  
3. In version 4.0.0, token A is marked as an invalid asset.  
4. When attempting to register token A, AssetRegistryP1's `this.version()` returns 3.0.0 (from the Versioned contract) instead of the expected 4.0.0. This causes the system to check token A's validity against version 3.0.0, where it's still considered valid, allowing successful registration of an asset that should be invalid in the current system version.

## Recommended Mitigation Steps
While no immediate profit-driven exploit has been identified, this vulnerability creates significant administrative gaps that could potentially serve as preconditions for other attacks. The core issue lies in the lack of strong consistency constraints in version management across contracts. To address this, we recommend the following steps:

- Enforce Version Registry Consistency:
Ensure that the versionRegistry address in the main contract is always consistent with the one in assetPluginRegistry when both plugins are in use.
Implement a mechanism to synchronize or validate these addresses regularly.

- Align Component Versions:
Ensure that the versions of components in the deployer's _implementations are consistent with both the main contract and the deployer itself.
Implement version checks during deployment and upgrade processes to prevent mismatches.

- Improve Version Deprecation Handling:
When a version is set as isDeprecated in the versionRegistry, automatically invalidate all assets registered under that version in the assetPluginRegistry.
Implement a cascading update mechanism to ensure version changes propagate correctly across the system.

- Enhance Asset Validation:
Modify the asset validation process to not only check if an asset is registered but also verify its validity in the current system version during runtime.
Implement periodic re-validation of registered assets against the current system version.

- Strengthen Coordination Between Key Components:
Improve the interaction between versionRegistry, assetPluginRegistry, and AssetRegistryP1:
  - When a version X becomes invalid, automatically invalidate all assets 
registered under version X.
  - When an asset's validity is revoked for version X, ensure that the corresponding AssetRegistryP1 for version X unregisters the related asset.

- Implement Version-Aware Asset Management:
Modify AssetRegistryP1 to always use the main system version for asset validation, rather than its own version.
Implement a version-aware asset registry that maintains asset validity across different system versions.
