# Vulnerability details

The `basketsNeeded` variable represents the number of baskets that the `backingManager` must hold for the RToken to be fully collateralized: [RToken.sol:L202-L204](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/RToken.sol#L202-L204)
```solidity
// {BU}
uint192 baskets = _scaleDown(caller, amount);
emit Redemption(caller, recipient, amount, baskets);
```
In this code, the `baskets` amount is calculated based on the total supply and the redemption amount using the `_scaleDown()` function. However, this calculation does not take into account the custom basket proportions specified by the portions parameter. As a result, the `basketsNeeded` variable is not accurately updated to reflect the actual baskets redeemed based on the custom proportions.

> If `basketsNeeded` is not properly updated based on the custom redemption proportions, it can lead to an inaccurate representation of the collateral needed to back the RTokens. This can potentially result in under-collateralization or over-collateralization of the system, compromising its stability and security.

> The inconsistency between the actual baskets redeemed and the `basketsNeeded` variable can propagate throughout the system and affect other functions that rely on the accuracy of `basketsNeeded`.

> The `redeemCustom()` function is designed to allow users to redeem their RTokens for a custom basket of underlying assets in specified proportions. However, the bug violates this intended behavior by not accurately updating the `basketsNeeded` variable based on the custom proportions, undermining the purpose and reliability of the custom redemption feature.

## Proof of Concept
1. Alice has a balance of 1000 RTokens and decides to perform a custom redemption.
2. Alice calls the `redeemCustom()` function with the following parameters:

   * `amount`: 500 RTokens
   * `portions`: [0.6, 0.4] (60% of Asset A, 40% of Asset B)

3. The `redeemCustom()` function calculates the baskets amount based on the total supply and the redemption amount using the `_scaleDown()` function.
4. The `basketsNeeded` variable is decreased by the baskets amount, without considering the custom proportions specified by the portions parameter.
5. As a result, the `basketsNeeded` variable is not accurately updated to reflect the actual baskets redeemed based on the custom proportions.

In this scenario you can see how the incorrect calculation and update of `basketsNeeded` can lead to an inaccurate representation of the collateral needed, resulting in under-collateralization or over-collateralization of the system.

## Recommended Mitigation Steps
Calculate and update the `basketsNeeded` variable based on the custom redemption proportions.
```diff
// {BU}
- uint192 baskets = _scaleDown(caller, amount);
+ uint192 baskets = 0;
+ for (uint256 i = 0; i < portions.length; i++) {
+     uint192 basketPortion = basketHandler.quote(basketNonces[i], portions[i], amount);
+     baskets += basketPortion;
+ }
+ _scaleDown(caller, baskets);
emit Redemption(caller, recipient, amount, baskets);
```
The baskets variable is initialized to zero. Then, a loop is introduced to iterate over the portions array. For each portion, the corresponding `basketPortion` is calculated using the `basketHandler.quote()` function, passing the `basketNonces`, portions, and amount as parameters. The calculated `basketPortion` is added to the baskets variable.

Finally, the `_scaleDown()` function is called with the caller and the updated baskets amount to accurately update the `basketsNeeded` variable based on the custom redemption proportions.
