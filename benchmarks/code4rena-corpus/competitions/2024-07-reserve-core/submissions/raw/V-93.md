# Vulnerability details

Users redeem their RToken balance for a custom basket of underlying assets through the `redeemCustom()` function. This function takes in parameters such as the recipient address, redemption amount, basket nonces, portions, expected ERC20 tokens, and minimum amounts. It performs various checks and effects, including refreshing the asset registry, verifying the redemption amount, applying throttles, and calculating the basket redemption amounts using the `quoteCustomRedemption()` function of the `basketHandler`.

The is issue in the post-checks section of the `redeemCustom()` function, specifically in the code block responsible for verifying that the received amounts of the expected output ERC20 tokens meet the specified minimum amounts ([RToken.sol:338-343](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/RToken.sol#L338-L343)).
```solidity
// Check post-balances
for (uint256 i = 0; i < expectedERC20sOut.length; ++i) {
    uint256 bal = IERC20(expectedERC20sOut[i]).balanceOf(recipient);
    // we haven't verified this ERC20 is registered but this is always a staticcall
    require(bal - pastBals[i] >= minAmounts[i], "redemption below minimum");
}
```
The code assumes that the recipient's balance of the expected ERC20 tokens will always increase by at least the specified minimum amounts. However, this assumption may not hold true in certain scenarios, such as when the `backingManager` does not have sufficient funds to fulfill the redemption request.

## Impact
* Users may not receive the expected minimum amounts of ERC20 tokens when redeeming their RTokens, even though the function execution completes successfully. This can cause confusion and erode trust in the protocol.

* In scenarios where the `backingManager` lacks sufficient funds to fulfill the redemption request, users may receive fewer tokens than expected or no tokens at all. This can result in financial losses for users who rely on the minimum redemption amounts.

## Proof of Concept
Consider this scenario

* Alice holds a balance of RTokens and decides to redeem them using the `redeemCustom()` function.
* Alice specifies the expected ERC20 tokens and the minimum amounts she wants to receive as part of the redemption.
* The `redeemCustom()` function performs the necessary checks and calculations, including prorating the redemption amounts based on Alice's share of the total RToken supply.
* However, the `backingManager` does not have sufficient funds to fulfill Alice's redemption request completely.
* The function transfers the available tokens from the `backingManager` to Alice's recipient address.
* In the post-checks section (RToken.sol:338-343), the function verifies that the received amounts meet the specified minimum amounts.
Since the `backingManager` did not have enough funds, Alice's received amounts are below the minimum specified, but the function still * passes the post-checks due to the insufficient validation.
* Alice receives fewer tokens than expected, potentially leading to financial losses.

## Recommended Mitigation Steps
Handle the cases where the `backingManager` may not have sufficient funds to fulfill the redemption request. Instead of using a require statement, the code should provide appropriate error handling and allow for partial redemptions when the minimum amounts cannot be met.
```diff
// Check post-balances
for (uint256 i = 0; i < expectedERC20sOut.length; ++i) {
    uint256 bal = IERC20(expectedERC20sOut[i]).balanceOf(recipient);
    // we haven't verified this ERC20 is registered but this is always a staticcall
-   require(bal - pastBals[i] >= minAmounts[i], "redemption below minimum");
+   if (bal - pastBals[i] < minAmounts[i]) {
+       // Handle insufficient redemption, e.g., emit an event or revert with a specific error message
+       emit InsufficientRedemption(recipient, expectedERC20sOut[i], bal - pastBals[i], minAmounts[i]);
+   }
}
```
