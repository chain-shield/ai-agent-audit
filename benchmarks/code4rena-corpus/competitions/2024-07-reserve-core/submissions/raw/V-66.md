# Vulnerability details

## Description 

The `BasketHandlerP1` contract is responsible for managing the basket configuration and its evolution over time. A key function in this contract is [`setBackupConfig()`](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/BasketHandler.sol#L284-L303), which allows governance to set a backup configuration for a given target name. This backup configuration is crucial as it serves as a fallback when the primary basket configuration fails.

The [`setBackupConfig()` function](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/BasketHandler.sol#L284-L303) checks if each ERC20 token in the `erc20s` array is a valid collateral at the time of setting the backup configuration. However, it does not implement any mechanism to ensure that these ERC20 tokens remain valid collaterals over time. This oversight can lead to potential issues when the backup configuration is needed.

The [`_switchBasket()` function](https://github.com/code-423n4/2024-07-reserve/blob/3f133997e186465f4904553b0f8e86ecb7bbacbf/contracts/p1/BasketHandler.sol#L654-L680), which is called internally by `refreshBasket()`, relies on the backup configuration to switch the basket based on the `BasketConfig` and `Collateral` statuses. If the backup configuration contains invalid collaterals due to changes in their status over time, it could cause the basket switch to fail, potentially leaving the basket in a disabled state.

The root cause of this issue lies in the `setBackupConfig()` function:

```solidity
File: BasketHandler.sol
284:     function setBackupConfig(
285:         bytes32 targetName,
286:         uint256 max,
287:         IERC20[] calldata erc20s
288:     ) external {
289:         requireGovernanceOnly();
290:         require(max <= MAX_BACKUP_ERC20S && erc20s.length <= MAX_BACKUP_ERC20S, "too large");
291:         requireValidCollArray(erc20s);
292:         BackupConfig storage conf = config.backups[targetName];
293:         conf.max = max;
294:         delete conf.erc20s;
295: 
296:         for (uint256 i = 0; i < erc20s.length; ++i) {
297:             // This is a nice catch to have, but in general it is possible for
298:             // an ERC20 in the backup config to have its asset altered.
299:             assetRegistry.toColl(erc20s[i]); // reverts if not collateral
300:             conf.erc20s.push(erc20s[i]);
301:         }
302:         emit BackupConfigSet(targetName, max, erc20s);
303:     }

```

While this function checks if each ERC20 is a valid collateral at the time of configuration, it doesn't implement any mechanism to ensure ongoing validity. This can lead to a scenario where the backup configuration becomes stale and contains invalid collaterals, potentially causing basket switching failures.

## Impact
The impact of this finding is that the protocol could use invalid or compromised collaterals in emergency situations, leading to potential failures during basket switching. This can leave the basket in a disabled state, pausing critical protocol functions. 

## Proof of Concept
1. Governance sets a backup configuration using `setBackupConfig()` with valid collaterals A, B, and C.
2. Over time, collateral B loses its collateral status or is removed from the asset registry.
3. The primary basket configuration fails, and `refreshBasket()` is called, which internally calls `_switchBasket()`.
4. `_switchBasket()` attempts to use the backup configuration, which still includes the now-invalid collateral B.
5. The basket switch fails due to the invalid collateral, leaving the basket in a disabled state.
6. Critical protocol functions are paused, affecting user interactions and potentially leading to loss of trust in the protocol.

## Tools Used
Manual review

## Recommended Mitigation Steps
To mitigate this issue, I recommend to implement a mechanism to regularly validate and update the backup configuration. This can be achieved by adding a new function to revalidate the backup configuration and modifying the `_switchBasket()` function to check the validity of collaterals before using them.
