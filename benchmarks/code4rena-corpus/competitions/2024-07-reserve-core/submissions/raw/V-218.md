# Vulnerability details

## Impact

The `lack of a CollateralStatus.SOUND status check` in the `BasketHandler._setPrimeBasket` function could potentially lead to an issue where defaulted collaterals are included in the prime basket, resulting in an imbalance between the `totalWeight` and `goodWeight` calculations in the `BasketLib.nextBasket` function.

Following is a detailed analysis of the issue:

In the `BasketHandler._setPrimeBasket` function, there is `no explicit` check to ensure that the collaterals being added to the `prime basket` are in the `CollateralStatus.SOUND state`. The function only checks if the collateral is registered `(assetRegistry.toAsset(erc20s[i]).isCollateral())` and if the target amount is within the allowed range `(0 < targetAmts[i] && targetAmts[i] <= MAX_TARGET_AMT)`.

This means that it is possible for `governance` to `add defaulted collaterals` (with a status other than SOUND) to the prime basket by calling the `setPrimeBasket` or `forceSetPrimeBasket` functions. This could happen when particular collateral or collterals default when the `setPrimeBasket` transaction is still in the mempool. Hence this is not a governance error, but an issue which could occur while setting the prime basket.

When the `BasketLib.nextBasket` function is called to calculate the new basket composition, it first calculates the `totalWeights array`, which includes the target weights of all prime collaterals, regardless of their status.

The `goodWeights array`, on the other hand, `only includes the target weights` of the `SOUND` prime collaterals.

If there are defaulted collaterals in the prime basket, their target weights will be included in the totalWeights array but not in the goodWeights array, resulting in a situation where `totalWeights[i] > goodWeights[i] for the corresponding target name`.

In this case, the `nextBasket` function will attempt to `add backup collaterals` to make up for the missing weight (`totalWeights[i] - goodWeights[i]`). The function calculates the required reference amounts for the backup collaterals based on this missing weight.

Since the good backup collaterals will divide the `missing weight` equally among the themselves the `nextBasket` will not represent the optimal collateral composition of the prime basket set by governance. This can lead to basket consisting of` sub-optimal collateral backing` which is not in the best interest of the RToken holders.

After a collateral is added to the `prime basket` it can get defaulted and under that scenario it is reasonable to add collaterals from the `backup configuration`. But it should be `disallowed to add defaulted collaterals from the outset` when calling the `_setPrimeBasket` function. Since this will lead to sub-optimal collateral compositions for baskets and is not in the best interest of the RToken holders.

## Recommended Mitigation Steps

Hence it is recommended to check whether a collateral is in the `CollateralStatus.SOUND` collateral status while adding it to the primeBasket when calling the `BasketHandler._setPrimeBasket` function and the transaction should revert if the collateral is not in the `CollateralStatus.SOUND` status.
