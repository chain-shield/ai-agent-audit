# Vulnerability details


## Proof of Concept

First see https://github.com/code-423n4/2024-07-reserve/blob/825e5a98a8c94a7b4458b3b359a507edb9e662ba/contracts/p1/AssetRegistry.sol#L15-L18

```solidity
    uint256 public constant GAS_FOR_BH_QTY = 100_000; // enough to call bh.quantity

    uint256 public constant GAS_FOR_DISABLE_BASKET = 900_000; // enough to disable basket on n=128


```

This constants have been set and are expected to be used in some checks to ensure enough gas still exists for some calls

That is the requirement here: https://github.com/code-423n4/2024-07-reserve/blob/825e5a98a8c94a7b4458b3b359a507edb9e662ba/contracts/p1/AssetRegistry.sol#L253-L265

```solidity
function _reserveGas() private view returns (uint256) {
  uint256 gas = gasleft();
  // Call to quantity() restricts gas that is passed along to 63 / 64 of gasleft().
  // Therefore gasleft() must be greater than 64 * GAS_FOR_BH_QTY / 63
  // GAS_FOR_DISABLE_BASKET is a buffer which can be considerably lower without
  // security implications.
  require(
    gas > (64 * GAS_FOR_BH_QTY) / 63 + GAS_FOR_DISABLE_BASKET,
    'not enough gas to unregister safely'
  );
  return GAS_FOR_BH_QTY;
}

```

Now keep in mind that the deployment of this protocol is to be done to multiple EVM chains, per the [readme](https://github.com/code-423n4/2024-07-reserve/blob/825e5a98a8c94a7b4458b3b359a507edb9e662ba/README.md#L140-L141)

| Chains the protocol will be deployed on | Ethereum,Arbitrum,Base,Optimism |

Issue now is that, this logic would not work as expected _Arbitrum_ , which is because _Arbitrum_ has a totally different gas model than Ethereum.

Differences are summarized in the following article: https://docs.arbitrum.io/devs-how-tos/how-to-estimate-gas.

As an example even a simple approve transaction requires more than 100_000 gas on Arbitrum: https://arbiscan.io/tx/0x04f97a39c6d03029518d1953226b343555ea585d2064a24a767155a548b0665e.

In our case here, this would then lead to scenarios where even if the [check](https://github.com/code-423n4/2024-07-reserve/blob/825e5a98a8c94a7b4458b3b359a507edb9e662ba/contracts/p1/AssetRegistry.sol#L259-L262) passes the transaction could still fail in any of the exerpts below:

- https://github.com/code-423n4/2024-07-reserve/blob/825e5a98a8c94a7b4458b3b359a507edb9e662ba/contracts/p1/AssetRegistry.sol#L90-L100

```solidity
function swapRegistered(IAsset asset) external governance returns (bool swapped) {
  require(_erc20s.contains(address(asset.erc20())), 'no ERC20 collision');
  //@audit
  try basketHandler.quantity{ gas: _reserveGas() }(asset.erc20()) returns (uint192 quantity) {
    if (quantity != 0) basketHandler.disableBasket(); // not an interaction
  } catch {
    basketHandler.disableBasket();
  }

  swapped = _registerIgnoringCollisions(asset);
}

```

- https://github.com/code-423n4/2024-07-reserve/blob/825e5a98a8c94a7b4458b3b359a507edb9e662ba/contracts/p1/AssetRegistry.sol#L108-L121

```solidity
function unregister(IAsset asset) external governance {
  require(_erc20s.contains(address(asset.erc20())), 'no asset to unregister');
  require(assets[asset.erc20()] == asset, 'asset not found');
  //@audit
  try basketHandler.quantity{ gas: _reserveGas() }(asset.erc20()) returns (uint192 quantity) {
    if (quantity != 0) basketHandler.disableBasket(); // not an interaction
  } catch {
    basketHandler.disableBasket();
  }

  _erc20s.remove(address(asset.erc20()));
  assets[asset.erc20()] = IAsset(address(0));
  emit AssetUnregistered(asset.erc20(), asset);
}

```

Now note that, this whole logic/check was deployed as a round about to these 3 previous windows in an attempt to curb the bug case, i.e: _all three issues were submitted in subsequent engagements between Code4rena & the Reserve team, with the last tagged issue being more relevant to this_

- https://github.com/code-423n4/2023-01-reserve-findings/issues/254
- https://github.com/code-423n4/2023-02-reserve-mitigation-contest-findings/issues/73
- https://github.com/code-423n4/2023-06-reserve-findings/issues/7

Which then indicates that on the Arbitrum chain the whole inability of not being able to unregister a bad collateral can easily be made possible by an attacker.

## Impact

As hinted under _Vulnerability Details_, this bug case would mean reverts on Arbitrum even if the [check](https://github.com/code-423n4/2024-07-reserve/blob/825e5a98a8c94a7b4458b3b359a507edb9e662ba/contracts/p1/AssetRegistry.sol#L259-L262) passes, considering it's gas logic is quite distinct from other EVM compatible chain.

Going to the linked issues to find the possible extensive impacts to this bug case, we'd then find out that this issue can cause the basket to get disabled, and would then have to require a basket refresh and after a basket refresh is done, an additional _warmup period_ has to pass for some functionality to be available again (issuance, rebalancing and forwarding revenue) _subtle DOS_ and in some cases this might trigger a basket switch that would require the protocol to rebalance via trading, trading can have some slippage which can also cause _a loss for the protocol_. And this bug case would be possible via the `quantity()` query in the _try/catch{}_ blocks attached above, where not enough gas would be attached, forcing a revert & an an unnecessary trade.

## Recommended Mitigation Steps

Implement logic to dynamically adjust the gas limit based on the destination chain. This can be achieved by mapping known chains to their typical gas requirements or using a configurable parameter that users can specify when initiating a transaction.
