# Vulnerability details


## Proof of Concept

First from the readMe, we can see that this has been hinted:
https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/README.md#L181-L186

```markdown
### ERC20 token behaviors in scope

| Question                  | Answer |
| ------------------------- | ------ |
| Doesn't revert on failure | Yes    |
```

Now protocol in many instances call these methods of transfers on a low level that are vulnerable to this same bug case however here we'd use the custom `safeTransferFrom` protocol implements to explain the bug idea.

See https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/ethereum/contracts/THORChain_Router.sol#L437-L453

```solidity
  // Safe transferFrom in case asset charges transfer fees
  function safeTransferFrom(
    address _asset,
    uint _amount
  ) internal returns (uint amount) {
    uint _startBal = iERC20(_asset).balanceOf(address(this));
    (bool success, bytes memory data) = _asset.call(
      abi.encodeWithSignature(
        "transferFrom(address,address,uint256)",
        msg.sender,
        address(this),
        _amount
      )
    );
    require(success && (data.length == 0 || abi.decode(data, (bool))));
    return (iERC20(_asset).balanceOf(address(this)) - _startBal);
  }
```

We can see that this is the protocol's custom implementation of transferfrom, and it is used in [depositing an asset with a memo where the ETH is forwarded & the ERC-20 stays in the ROUTER](https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/ethereum/contracts/THORChain_Router.sol#L142-L161), whereas this would work normally for some integrated tokens this wouldn't work in all instances, this is because of the logic attached to the line `require(success && (data.length == 0 || abi.decode(data, (bool))));`.

The function doesn't check to see that the returned `bool` is not `false`, and would then cause for protocol to assume the transfer was successful whereas it wasn't.

## Impact

Transfers and extentially depositing of some supported assets would be assumed to have been correctly processed whereas the transfers of these tokens were never successful

## Recommended Mitigation Steps

Consider having a safe custom transfer method for all supported assets, in this case consider checking the return bool not to be false.
