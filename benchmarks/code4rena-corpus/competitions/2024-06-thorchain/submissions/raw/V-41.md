# Vulnerability details

`THORChain_Router.sol` has a `transferAllowance()` function which has the following purpose according to the documentation:
>transferAllowance is used during “churns” (i.e. vault rotation). Retiring vaults transfer their allowance to spend ERC20 tokens on the router to the new vaults.

If the ERC20s are stored on the router contract on which this function is called then it only adjusts the allowances of the vaults.
If another router is specified then it approves it to spend tokens on the behalf of the old vault and calls the `depositWithExpiry()` function on the new router to deposit into the new vault.

The issues is that when calling `depositWithExpiry()` on the other router it does not specify an expiration of the deposit.

## Impact
If no expiration is set and the transaction hangs in the mempool for several days then the router will attempt to deposit into a vault that is no longer valid. This can cause loss of funds for the vault that initiated the transfer of allowances.

## Proof of Concept
Here is an explanation from one of the devs on discord of what the expiration is used for in `depositWithExpiry()`:
> this is a protection against vault rotation. vaults rotate every 3 days and generate new vault addresses. if a tx hangs in the mempool for several days it's possible it will be confirmed after vaults rotate, so the targeted vault will no longer be valid

If the targeted vault is no longer valid it can cause loss of funds:
>if ETH or ERC20s is transferred to a retired vault what happens is THORChain still observes the inbound and attempts to refund from the old vault. If enough validators still have the keyshares from the old vault it's possible the tx can be refunded, but this is not guaranteed

>When vaults rotate validators join/leave and new signing parties are created - so no guarantee that quorom of the old vaults will still exist

Here is the `transferAllowance()` function which calls `_routerDeposit` if the specified router is not the current contract:
```solidity
  function transferAllowance(address router, address newVault, address asset, 
  uint amount, string memory memo) external nonReentrant {
    if (router == address(this)) {
      _adjustAllowances(newVault, asset, amount);
      emit TransferAllowance(msg.sender, newVault, asset, amount, memo);
    } else {
      _routerDeposit(router, newVault, asset, amount, memo);
    }
  }
```
Below we can see that `_routerDeposit()` calls `depositWithExpiry()` on the specified router with `type(uint).max` as expiration which is like having no expriation at all:

## Recommended Mitigation Steps
Perhaps you could implement a variable that tracks when the last rotation happened and set the expiration to be equal to this variable + 3 days.
