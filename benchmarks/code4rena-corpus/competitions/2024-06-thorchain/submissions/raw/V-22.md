# Vulnerability details

## Impact
Insufficient validation allows the user to completely drain the contract of Ethereum.

## Proof of Concept
Users/vaults can call `transferOutV5()` that then calls the private `_transferOutV5()`:
```solidity
function _transferOutV5(TransferOutData memory transferOutPayload) private {
    if (transferOutPayload.asset == address(0)) {
      bool success = transferOutPayload.to.send(transferOutPayload.amount); // @audit Calls with user set amount instead of msg.value
      if (!success) {
        payable(address(msg.sender)).transfer(transferOutPayload.amount);
      }
    } else {
      _vaultAllowance[msg.sender][transferOutPayload.asset] -= transferOutPayload.amount;

      (bool success, bytes memory data) = transferOutPayload.asset.call(
        abi.encodeWithSignature(
          "transfer(address,uint256)",
          transferOutPayload.to,
          transferOutPayload.amount
        )
      );

      require(success && (data.length == 0 || abi.decode(data, (bool))));
    }
```
The function requires the `TransferOutData` struct which contains information like amount, asset and others. The asset can either be `address(0)` which is how you send Ether in this contract or an address of a particular asset. If the user provides `address(0)` signalizing that he wants to transfer Ethereum, he will send up in this if check:
```solidity
if (transferOutPayload.asset == address(0)) {
      bool success = transferOutPayload.to.send(transferOutPayload.amount);
      if (!success) {
        payable(address(msg.sender)).transfer(transferOutPayload.amount);
      }
    }
```
As you can see, there is clearly no validation of the `msg.value` sent essentially allowing for absolutely any user to drain the contract by specifying him as the receiver and the balance of the contract as the amount.

While there is no documented way of Ethereum being in the contract, there are currently at least 4 ways I can think of for Ethereum to end up in the contract that were introduced in V5:
1. Since a user is supposed to send ETH, it is very likely that he will expect that the amount variable in the struct should have a 0 value and just send `msg.value` with the transaction but that would lead to his ETH staying in the contract
2. The vulnerability explained above allows for the `msg.value` sent by the user to be more than the amount specified in the struct leading to leftover Ethereum sent staying in the contract. This is also possible in another one of the functions (another way to completely drain the contract which is explained in another one of my reports) so there is 2 functions where that could happen
3. There is a function used for swapping Ethereum for a token. If there is leftover Ethereum after the swap (possible in V5 as whitelist is being removed and many more implementations of swapper contracts could be used), then there will be Ethereum in the contract
4. A simple user mistake

Also, if there is no ETH available in the contract, that is still unintended behavior that would lead to reverts in a lot of cases.

## Recommended Mitigation Steps
Use `msg.value` instead however be careful when doing that as `batchTransferOutV5()` would use `msg.value` in a loop
