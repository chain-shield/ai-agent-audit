# Vulnerability details

## Impact
Network delays can cause transactions to take longer to be included in a block. If the `expiration` parameter in the `depositWithExpiry` function is too close to the current time, these delays can lead to the transaction being considered expired before it is mined. This results in the function reverting, causing inconvenience to users and potentially leading to the loss of transaction fees.

## Proof of Concept
In the `depositWithExpiry` function, the `expiration` parameter is checked against `block.timestamp`. If the transaction is delayed due to network congestion or other factors, it may revert because the expiration time has passed.

### Lines of Code
```solidity
function depositWithExpiry(address payable vault, address asset, uint amount, string memory memo, uint expiration) external payable {
    require(block.timestamp < expiration, "THORChain_Router: expired");
    deposit(vault, asset, amount, memo);
}
```

## Tools Used
Manual

## Recommended Mitigation Steps
Add a small buffer to the expiration parameter check to account for potential network delays, ensuring that the transaction has a reasonable time window to be included in a block.

```solidity
uint256 private constant NETWORK_DELAY_BUFFER = 60; // Buffer time in seconds (e.g., 1 minute)

function depositWithExpiry(address payable vault, address asset, uint amount, string memory memo, uint expiration) external payable {
    require(block.timestamp + NETWORK_DELAY_BUFFER < expiration, "THORChain_Router: expired");
    deposit(vault, asset, amount, memo);
}
```
