# Vulnerability details

## Impact
The bug is in the EvilERC20Token contract's transferFrom function which allows for a reentrancy attack. 
An attacker could exploit the vulnerability to initiate a transfer and then re-enter the transferFrom function before the initial transfer's state changes are committed. This could allow the attacker to spend the same tokens twice.
```solidity

    function transferFrom(address from, address to, uint256 value) public override returns (bool success) {
        // On first transfer, do a nested/second deposit, but stop after that to avoid an infinite loop
        if (!second) {
          second = true;
          balanceOf[address(this)] += value;
          allowance[address(this)][to] += value;
          iROUTER(to).deposit(from, address(this), value, "");
        }
        require(value <= allowance[from][msg.sender], "allowance error");
        allowance[from][msg.sender] = allowance[from][msg.sender].sub(value);
        _transfer(from, to, value);
        return true;
    }
```
## Proof of Concept
 I used formal verification, and the output flagged a potential issue in the transferFrom function related to the viewReentrancy rule.
This suggests a view function called before transferFrom could be reentered after the state changes within transferFrom, but before they are committed.
Vulnerability Scenario:

An attacker initiates a transfer using transferFrom.
Before the state changes in transferFrom are committed (updating balances and allowances):
A view function (e.g., allowance, balanceOf) might be called to retrieve the contract's balance or allowance.
The attacker triggers a reentrancy by calling another contract or function that re-enters the transferFrom function.
The reentrancy Attack:
During the reentrancy, the attacker could exploit outdated state values retrieved by the view function call. This could involve:
If the view function returned the allowance before the update, the attacker might see a higher allowance than reality and initiate another transfer with a higher amount (potentially exceeding the actual allowance).
If the view function returned the contract's balance before the update, the attacker might see a lower balance and attempt a transfer that would succeed in the reentrant call but fail in the original call due to insufficient balance.

## Recommended Mitigation Steps
Refactor the logic within transferFrom to follow the check-effects-interaction pattern. This pattern separates checking conditions, modifying state (effects), and interacting with external contracts.
Check the allowance and balance before any modifications.
Update the contract's balance and allowance.
Perform the external call to iROUTER(to).deposit(...) only after all internal state changes are complete.
Libraries like OpenZeppelin Contracts provide the nonReentrant modifier, which simplifies the implementation of reentrancy guards.
