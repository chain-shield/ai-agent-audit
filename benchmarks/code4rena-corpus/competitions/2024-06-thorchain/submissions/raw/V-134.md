# Vulnerability details



## Proof of Concept

First from the readMe we can see that this has been stated: https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/README.md#L184-L192

Take a look at https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/ethereum/contracts/THORChain_Router.sol#L465-L483

```solidity

  function _routerDeposit(
    address _router,
    address _vault,
    address _asset,
    uint _amount,
    string memory _memo
  ) internal {
    _vaultAllowance[msg.sender][_asset] -= _amount;
    safeApprove(_asset, _router, _amount);

    iROUTER(_router).depositWithExpiry(
      _vault,
      _asset,
      _amount,
      _memo,
      type(uint).max
    ); // Transfer by depositing
  }
```

This function is used to deposit with an expiry via the router and to do this it adjusts the allowance and forwards funds to new router which then credits the allowance to the desired vault, and is called from the externally available `returnVaultAssets()` &`transferAllowance()`.

Before querying the router's `depositWithExpiry()`, it implements a `safeApprove()` on the asset it wants to interact with on the router.

Now would be key to note that the implementation of `safeApprove()` is not like that of OpenZeppelin and is custom to protocol, i.e https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/ethereum/contracts/THORChain_Router.sol#L485-L494

```solidity
  function safeApprove(
    address _asset,
    address _address,
    uint _amount
  ) internal {
    (bool success, ) = _asset.call(
      abi.encodeWithSignature("approve(address,uint256)", _address, _amount)
    ); // Approve to transfer
    require(success);
  }
```

Problem however is that protocol has hinted they would accept mainstream tokens which include `USDT` and would then cause for this attempt at approving to be potentially broken for USDT or the likes of this token.

This is because tokens like USDT do not allow approving an amount` M > 0` when an existing amount `N > `0 is already approved. This is to protect from an ERC20 attack vector described [here](https://docs.google.com/document/d/1YLPtQxZu1UAvO9cZ1O2RPXBbT0mooh4DYKjA_jp-RLM/edit?tab=t.0#heading=h.b32yfk54vyg9), which would then mean that when the router gets left with an approval of `!=0`, either intentionally by an attacker or from normal executions, the normal depositing routes would be broken and become unavailable since the attempt at approving a new value via `  safeApprove(_asset, _router, _amount);` would fail for these assets.

## Impact

Core functionality of protocol would be DOS'd considering access to `THORChain_Router_routerDeposit()` would be broken.

## Recommended Mitigation Steps

Consider using the new implementation of `forceApprove()` from Openzeppelin.
