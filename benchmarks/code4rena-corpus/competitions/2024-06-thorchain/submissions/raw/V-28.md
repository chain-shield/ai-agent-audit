# Vulnerability details

auditing a smart contract like `THORChain_Router` is a complex process and usually requires a systematic and thorough approach, I can still point out some issues and potential vulnerabilities found during a brief review:

1. **Lack of input validation**: In some functions, such as `_deposit`, `_transferOutV5`, `transferOut`, and `transferOutV5`, the contract doesn't perform sufficient input validation on the `asset` parameter. For instance, if an invalid `asset` address is provided, it might lead to unexpected behavior.

2. **Unchecked call to external contracts**: In functions like `_deposit`, `transferOut`, `_transferOutV5`, and `_transferOutAndCallV5`, the contract uses `.call` to interact with external contracts without checking their return value. This might lead to the transaction continuing even if the external call fails, creating inconsistencies in the state.

3. **Reentrancy**: Although the contract uses a `nonReentrant` modifier, there is a potential reentrancy vulnerability in the `transferOutAndCall` function. The external contract `aggregator` can call back into the contract before the state is updated, causing issues.

4. **Gas limits**: Functions like `transferOutAndCall` and `_transferOutAndCallV5` forward all the received gas to the external contract. This can lead to out-of-gas exceptions if the external contract consumes too much gas.

5. **Missing event emissions**: In the `returnVaultAssets` function, an event should be emitted when the assets are successfully returned to the asgard.

6. **Missing access control**: The `vaultAllowance` function is `public` and does not check the caller's address. An attacker might manipulate the allowance of other addresses if they know the contract's implementation.

While these issues highlight potential vulnerabilities, it is essential to perform a more in-depth audit to ensure the contract's security completely. It's recommended to use formal verification tools and methodologies to validate the contract's behavior further.

I've noticed that the smart contract does not contain a function to withdraw ERC20 tokens when `asset != address(0)` in the `transferOut` function. This can lead to a loss of ERC20 tokens if users accidentally send ERC20 tokens to the contract instead of ETH.

Here's a proposed `withdrawToken` function to allow users to withdraw their ERC20 tokens:

```solidity
// Withdraw an ERC20 token from the contract
function withdrawToken(address _asset, uint _amount) external {
  require(_asset != address(0), "Invalid asset address");
  require(_vaultAllowance[msg.sender][_asset] >= _amount, "Insufficient allowance");

  _vaultAllowance[msg.sender][_asset] -= _amount;
  _vaultAllowance[address(this)][_asset] += _amount;

  iERC20(_asset).transfer(msg.sender, _amount);

  emit TransferOut(
    address(this),
    msg.sender,
    _asset,
    _amount,
    "Withdraw token"
  );
}
```
