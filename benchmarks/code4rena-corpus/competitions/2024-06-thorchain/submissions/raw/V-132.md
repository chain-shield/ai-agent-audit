# Vulnerability details


## Proof of Concept

Take a look at https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/ethereum/contracts/THORChain_Router.sol#L465-L483

```solidity

  function _routerDeposit(
    address _router,
    address _vault,
    address _asset,
    uint _amount,
    string memory _memo
  ) internal {
    _vaultAllowance[msg.sender][_asset] -= _amount;
    safeApprove(_asset, _router, _amount);

    iROUTER(_router).depositWithExpiry(
      _vault,
      _asset,
      _amount,
      _memo,
      type(uint).max
    ); // Transfer by depositing
  }
```

This function is used to deposit with an expiry via the router and to do this it adjusts the allowance and forwards funds to new router which then credits the allowance to the desired vault, and is called from the externally available `returnVaultAssets()` &`transferAllowance()`

Going to any specification of the router for this function we can see the below: https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/ethereum/contracts/THORChain_Failing_Aggregator.sol#L13-L21

```solidity
interface iROUTER {
  function depositWithExpiry(
    address payable vault,
    address asset,
    uint amount,
    string memory memo,
    uint expiration
  ) external payable;
}
```

Which indicates that the last attached `uint` should be a sufficient expiry for this depositing attempts, problem however is that in the `THORChain_Router` protocol hardcodes this value to typeuint256.max which would mean that the attempted deposit to the router could then be maliciously held still in the mempool for as long as possible and maliciously executed at the cost of the integrators.

## Impact

No sufficient deadline so transactions could be maliciously held in the mempool or maliciously held as a whole and executed at a wrong time.

## Recommended Mitigation Steps

Consider applying a valid deadline in the `depositWithExpiry()` call in `THORChain_Router_routerDeposit()`.
