# Vulnerability details

### Summary

`THORChain_Router::safeApprove` method contains several problems. The first is related to change the allowance  from an existing non-zero allowance value for some ERC20 tokens. Second problem is that if approve returns a false response, this is not checked, this means that even if the method returns a false as data, approve will be considered as successful. 

### Proof of concept

Some ERC20 tokens do not work when changing the allowance from an existing non-zero allowance value. For example Tether (USDT)'s approve() function will revert if the current approval is not zero, to protect against front-running changes of approvals. Also for the implementation of `safeApprove`, the result of the `approve` is not checked at all. 

### Impact

The impact of the issues in the `THORChain_Router::safeApprove` method can be significant, affecting both the functionality and security of the contract.

1. **Functionality Degradation**: Failure to reset the allowance to zero before increasing it can lead to issues with certain ERC20 tokens that revert when changing the allowance from a non-zero value. This can result in an inability to execute transactions involving such tokens, leading to a degradation in the contract's functionality.
    
2. **Security Risks**: Not checking the return value of the `approve` function poses security risks. If the `approve` function fails but its failure isn't detected, the contract may proceed with operations assuming the approval was successful. This could potentially lead to unauthorized or unintended transfers of tokens, posing financial risks to users.

```solidity 
function safeApprove(address _asset, address _address, uint _amount) internal {

	(bool success, ) = _asset.call(
		abi.encodeWithSignature("approve(address,uint256)", _address, _amount)	
	); // Approve to transfer	
	require(success);
}
```

### Recommendation Mitigation Steps

Consider setting the allowance to zero before increasing the allowance and use safeApprove/safeIncreaseAllowance and also checking the result of the approve. The updated code could look like this: 

```solidity
function safeApprove(address _asset, address _address, uint _amount) internal {

	(bool success, ) = _asset.call(
		abi.encodeWithSignature("approve(address,uint256)", _address, 0)	
	);
	(bool success, bytes data) = _asset.call(
		abi.encodeWithSignature("approve(address,uint256)", _address, _amount)	
	);	
	require(success && (data.length == 0 || abi.decode(data, (bool)))); // Check approval success
}
```

By resetting the allowance to zero before increasing it and checking the result of the `approve` function, you can mitigate potential issues and ensure the safe operation of the `safeApprove` method.
