# Vulnerability details

## Impact
The `transferAllowance` function moves assets between vaults or "churn" assets to a new Asgard vault. The function allows the caller (`msg.sender`) to transfer their allowance for a specific asset to a new vault.

However, the current function implementation has a bug that can lead to unauthorized allowance transfers. The issue lies in the fact that the function adjusts the allowances between the old vault (`msg.sender`) and the new vault without checking if the old vault has sufficient allowance for the asset being transferred. [chain/ethereum/contracts/THORChain_Router.sol#transferAllowance](https://github.com/code-423n4/2024-06-thorchain/blob/e5ae503d0dc2394a82242be6860eb538345152a1/chain/ethereum/contracts/THORChain_Router.sol#L165-L178)

```solidity
function transferAllowance(
    address router,
    address newVault,
    address asset,
    uint amount,
    string memory memo
) external nonReentrant {
    if (router == address(this)) {
        _adjustAllowances(newVault, asset, amount);
        emit TransferAllowance(msg.sender, newVault, asset, amount, memo);
    } else {
        _routerDeposit(router, newVault, asset, amount, memo);
    }
}
```
The _adjustAllowances function is called without any prior checks: [chain/ethereum/contracts/THORChain_Router.sol#_adjustAllowances](https://github.com/code-423n4/2024-06-thorchain/blob/e5ae503d0dc2394a82242be6860eb538345152a1/chain/ethereum/contracts/THORChain_Router.sol#L456-L463)
```solidity
function _adjustAllowances(
    address _newVault,
    address _asset,
    uint _amount
) internal {
    _vaultAllowance[msg.sender][_asset] -= _amount;
    _vaultAllowance[_newVault][_asset] += _amount;
}
```
This means that even if the old vault (`msg.sender`) doesn't have sufficient allowance for the asset, the function will still proceed to adjust the allowances, effectively allowing the caller to transfer allowances they don't have.

## Proof of Concept
1. It allows unauthorized transfers of allowances between vaults. A malicious actor can exploit this vulnerability to transfer allowances they don't possess to other vaults, potentially leading to loss of funds or disruption of the system's integrity.
2. It can lead to inconsistencies in the allowance tracking. If the old vault doesn't have sufficient allowance, the `_vaultAllowance` mapping will still be updated, resulting in incorrect allowance balances.
3. It violates the expected behavior of the `transferAllowance` function, which should only allow the transfer of allowances that the caller actually possesses.

## Recommended Mitigation Steps
Add a check to ensure that the old vault (`msg.sender`) has sufficient allowance for the asset before adjusting the allowances. `require` statement at the beginning of the function, it ensures that the old vault has sufficient allowance for the asset before proceeding with the allowance adjustment or router deposit.
```solidity
function transferAllowance(
    address router,
    address newVault,
    address asset,
    uint amount,
    string memory memo
) external nonReentrant {
    require(_vaultAllowance[msg.sender][asset] >= amount, "Insufficient allowance");
    
    if (router == address(this)) {
        _adjustAllowances(newVault, asset, amount);
        emit TransferAllowance(msg.sender, newVault, asset, amount, memo);
    } else {
        _routerDeposit(router, newVault, asset, amount, memo);
    }
}
```
