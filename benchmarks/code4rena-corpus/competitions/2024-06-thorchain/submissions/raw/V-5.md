# Vulnerability details

## Impact
The `batchTransferOutAndCallV5` function loops over the inputs and calls `_transferOutAndCallV5` to handle each input.

The issue is that if the `aggregationPayload.fromAsset` is the native asset (i.e. address(0)), the `_transferOutAndCallV5` internal function consumes all the `msg.value`, leaving no native asset for the subsequent iterations to use.

As a result, if there are more than one native asset transfer iterations in the `batchTransferOutV5` function, the transaction will fail.

## Proof of Concept
```solidity
pragma solidity ^0.8.0;

import {Test} from "forge-std/Test.sol";
import {THORChain_Router} from "../contracts/THORChain_Router.sol";

contract PoC is Test {
    THORChain_Router router;

    address vault = makeAddr("vault");
    address ETH = address(0);

    function setUp() public {
        router = new THORChain_Router();
        deal(vault, 100 ether);
    }

    function test_it() public {
        THORChain_Router.TransferOutAndCallData[] memory inputs = new THORChain_Router.TransferOutAndCallData[](2);
        inputs[0] = THORChain_Router.TransferOutAndCallData({
            target: payable(makeAddr("MockAggregator")),
            fromAsset: ETH,
            fromAmount: 1 ether,
            toAsset: makeAddr("MockToken"),
            recipient: makeAddr("recipient"),
            amountOutMin: 0,
            memo: "",
            payload: "",
            originAddress: ""
        });
        inputs[1] = THORChain_Router.TransferOutAndCallData({
            target: payable(makeAddr("MockAggregator")),
            fromAsset: ETH,
            fromAmount: 3 ether,
            toAsset: makeAddr("MockToken"),
            recipient: makeAddr("recipient"),
            amountOutMin: 0,
            memo: "",
            payload: "",
            originAddress: ""
        });

        vm.startPrank(vault);
        vm.expectRevert();
        router.batchTransferOutAndCallV5{value: 3 ether}(inputs);
        vm.stopPrank();
    }
}
```
The above POC shows that the `batchTransferOutAndCallV5` transaction fails because the first transfer consumes all the msg.value, leading to an out-of-fund error in the second transfer.

## Tools Used
Manual Review

## Recommended Mitigation Steps
Instead of using all the `msg.value`, use `aggregationPayload.fromAmount` amount of native assets in the `_transferOutAndCallV5` internal function.
