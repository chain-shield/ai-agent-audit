# Vulnerability details

## Impact
The router's function transferOutV5() takes a payload from the caller but never validates it. 
```solidity
function transferOutV5(
    TransferOutData calldata transferOutPayload
  ) public payable nonReentrant {
    _transferOutV5(transferOutPayload);
  }
```
Directly calling the internal function _transferOutV5() 

```solidity
  function _transferOutV5(TransferOutData memory transferOutPayload) private {
    if (transferOutPayload.asset == address(0)) {
      bool success = transferOutPayload.to.send(transferOutPayload.amount); 
      if (!success) {
        payable(address(msg.sender)).transfer(transferOutPayload.amount); // For failure, bounce back to vault & continue.
      }
    } else { ... // the rest dealing with ERC20's transfer
```
It checks to see if it is ETH transfer, it tries to send the stated amount to the "to" address if it does not succeed ( for example, if the sender doesn't have that amount ) it will return the "amount" back to the sender.


## Proof of Concept

The vulnerability stems from that there is no check that the sender has the ETH amount he intends to transfer  so, An attacker can form a payload with big amount of ETH that he doesn't have and when it fails the contract will send him that amount causing protocol's insolvency.

In ETH transfers, check "msg.value>= amount".
