# Vulnerability details

## Impact
THORChain_Router contract is designed to not hold ether with in the contract. But, batch functions like batchTransferOutV5() could cause a residual eth to get stuck on the THORChain_Router contract.

Such stuck eth can be stolen by any one using the flaw in the logic, that arises from legacy calls. 

## Proof of Concept
How is Ether stuck:
user calls batchTransferOutV5() function with 5.25 ether while passing an array of transfer instruction for ether summing to 5.07 ether. There is some ether needed to cover gas expenses. lets say, that about is 0.1 ether.

The residual which is 5.25 - 5.17 = 0.08 ether is not returned and left on the THORChain_Router contract.

How to steal the residual Eth:
The attacker can abuse the transferOut() function to steal the accumulated stuck ether as below.

```
   function transferOut(
    address payable to,
    address asset,
    uint amount,
    string memory memo
  ) public payable nonReentrant {
    uint safeAmount;
    if (asset == address(0)) {
      safeAmount = msg.value;
      bool success = to.send(safeAmount); // Send ETH.
      if (!success) {
        payable(address(msg.sender)).transfer(safeAmount); // For failure, bounce back to vault & continue.
      }
    } 
```
In the above function, "to" address is passed by the caller which uses "send" function() to transfer the ether.

The attacker creates a smart contract with a receive function() which then transfer the tokens to another contract. After transfer, the receive function 
will revert the transaction which comes in as false in the below call.

```
  bool success = to.send(safeAmount); // Send ETH.
```

If success is false, the caller sends the ether back to the caller as below. 

```
if (!success) {
        payable(address(msg.sender)).transfer(safeAmount); // For failure, bounce back to vault & continue.
      }
```

In order to steal the ether, the attacker needs to find out the exact amount of ether stuck in the router and then he will initiate the transaction by sending that exact amount of ether to transferOut().

First, the amount that came via msg.value will be forwarded to the target address as programmed by the attacker in the smart contract("to" address). But since the receive function reverts,

The !success flow will also get triggered and same amount will be returned back to the attacker. So, the attacker is able to take the eth amount twice and their by steal the stuck eth.

note: The whole case is build on the possibility that eth is stuck in the router and there are possibilities of that happening.


## Tools Used
Manual review.

## Recommended Mitigation Steps
Replace send and transfer calls with .call() function as that is the recommended way to transferring ether.
