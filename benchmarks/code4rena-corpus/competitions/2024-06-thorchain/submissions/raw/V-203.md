# Vulnerability details

## Impact
USDT has a non-standard implementation of the `approve` function, which can cause issues in smart contracts that expect standard ERC-20 behavior. USDT requires resetting the allowance to zero before setting a new value. If this is not handled correctly, it can lead to failed transactions and potential issues with token allowances.

## Proof of Concept
In the `_routerDeposit` function, the approval logic might fail for USDT

### Lines of Code
```solidity
function _routerDeposit(address _router, address _vault, address _asset, uint _amount, string memory _memo) internal {
    _vaultAllowance[msg.sender][_asset] -= _amount;
    (bool success,) = _asset.call(abi.encodeWithSignature("approve(address,uint256)", _router, _amount)); // Approve to transfer
    require(success);
    iROUTER(_router).depositWithExpiry(_vault, _asset, _amount, _memo, type(uint).max); // Transfer by depositing
}
```

## Recommended Mitigation Steps
Implement custom logic to handle USDT’s non-standard approval mechanism by resetting the allowance to zero before setting a new value:

```solidity
function _routerDeposit(address _router, address _vault, address _asset, uint _amount, string memory _memo) internal {
    _vaultAllowance[msg.sender][_asset] -= _amount;
    if (_asset == address(USDT)) {
        // Reset approval to zero before setting a new value for USDT
        (bool successReset,) = _asset.call(abi.encodeWithSignature("approve(address,uint256)", _router, 0));
        require(successReset, "Reset approval failed");
    }
    (bool success,) = _asset.call(abi.encodeWithSignature("approve(address,uint256)", _router, _amount)); // Approve to transfer
    require(success, "Approval failed");
    iROUTER(_router).depositWithExpiry(_vault, _asset, _amount, _memo, type(uint).max); // Transfer by depositing
}
```
