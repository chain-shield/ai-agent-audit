# Vulnerability details

## Impact
- Recipient Address gets Unauthorized Excess Fund from contract
- Msg.sender can steal and redirect contract fund to itself when sending to recipient Address fails naturally or artificially
## Proof of Concept
```solidity
 function transferOutV5(
    TransferOutData calldata transferOutPayload
  ) public payable nonReentrant {
>>>    _transferOutV5(transferOutPayload);
  }

  // bifrost to budget gas limits, no more than 50% than L1 gas limit
  function batchTransferOutV5(
    TransferOutData[] calldata transferOutPayload
  ) external payable nonReentrant {
    for (uint i = 0; i < transferOutPayload.length; ++i) {
>>>      _transferOutV5(transferOutPayload[i]);
    }
  }
```
The code above shows how _transferOutV5(...) function is called in the THORChain_Router contract, both in singularity and in batches, it should be noted that both functions above are payable functions and are called with msg value. However a look at the implementation of _transferOutV5(...) below shows that at no point was msg.value used in transfer implementation instead transferOutPayload.amount was used, The Protocol is wrongly assuming that msg.value used to call function would be equal to transferOutPayload.amount that is being transfered out.
There are three possibilities from this implementation
1. msg.value used to call function is indeed equal to transferOutPayload.amount and no issue at all
2. msg.value used to call function is greater than transferOutPayload.amount this will also not be an issue as based on Code4rena rule, this would be a user mistake and and the excess fund would be lost to the contract
3. However a third possibility which is the reason for this report is that a bad actor can as well call the function with a msg.value that is far below the transferOutPayload.amount that would be sent out, the msg.value can even be as low as just 1 wei and transferOutPayload.amount of larger value would be sent out to recipient or msg.sender, ofcourse this would be possible when contract has enough fund in it to cover the transferOutPayload.amount, this could be from the contract balance used to run normal operations or from excess funds sent to the contract by users, a bad actor simply needs to monitor the contract balance and call the _transferOutV5(...) with 1 wei but with transferOutPayload.amount that the contract can cover which can basically empty the contract balance.
```solidity
function _transferOutV5(TransferOutData memory transferOutPayload) private {
    if (transferOutPayload.asset == address(0)) {
>>>      bool success = transferOutPayload.to.send(transferOutPayload.amount); // Send ETH.
      if (!success) {
>>>        payable(address(msg.sender)).transfer(transferOutPayload.amount); // For failure, bounce back to vault & continue.
      }
    } else {
      _vaultAllowance[msg.sender][
        transferOutPayload.asset
      ] -= transferOutPayload.amount; // Reduce allowance

      (bool success, bytes memory data) = transferOutPayload.asset.call(
        abi.encodeWithSignature(
          "transfer(address,uint256)",
          transferOutPayload.to,
          transferOutPayload.amount
        )
      );

      require(success && (data.length == 0 || abi.decode(data, (bool))));
    }

    emit TransferOut(
      msg.sender,
      transferOutPayload.to,
      transferOutPayload.asset,
      transferOutPayload.amount,
      transferOutPayload.memo
    );
  }
```
In conclusion the msg.sender can also redirect the fund to itself artificially by making sure this code returns false _bool success = transferOutPayload.to.send(transferOutPayload.amount);_ , one of the ways could be to use "transferOutPayload.to" address that does not exist.

## Recommended Mitigation Steps
There are two ways to mitigate this issue, the first approach would be ensure to _transferOutV5(...) function interacts with msg.value directly instead of transferOutPayload.amount, this approach would prevent fund loss but it would not prevent the possible mismatch of msg value in comparison to transferOutPayload.amount that should be sent.
Therefore the best approach would be to ensure the total transferOutPayload.amount that is being sent is indeed the same as the msg.value used to call the function as adjusted below
```solidity
 function transferOutV5(
    TransferOutData calldata transferOutPayload
  ) public payable nonReentrant {
    _transferOutV5(transferOutPayload);
+++ require( transferOutPayload.amount == msg.value, "fund_Mismatch_Error" );
  }

  // bifrost to budget gas limits, no more than 50% than L1 gas limit
  function batchTransferOutV5(
    TransferOutData[] calldata transferOutPayload
  ) external payable nonReentrant {
+++ uint256 transferOutPayloadAmounts;
    for (uint i = 0; i < transferOutPayload.length; ++i) {
      _transferOutV5(transferOutPayload[i]);
+++   transferOutPayloadAmounts += transferOutPayload.amount;
    }
+++ require( transferOutPayloadAmounts == msg.value, "fund_Mismatch_Error" );
  }
```
