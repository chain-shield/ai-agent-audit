# Vulnerability details

## Impact
When handling ERC20 tokens, it is crucial not to rely solely on the token address for accounting because certain situations can lead to complications:

Tokens with Multiple Addresses:
Some tokens may exist under multiple addresses due to upgrades, forks, or deployments on different networks or testnets.
For example, the same token might have a different address on the mainnet and a testnet, or after a contract upgrade.

Potential Issues:
Inconsistencies in Balances: Systems that rely only on the token address might not aggregate balances correctly if they consider each address as a distinct token.
Potential Exploits: Attackers could exploit these inconsistencies to create situations of double counting or incorrect transfers.
Contract Updates: If a token migrates to a new address following a contract upgrade, old systems that do not recognize the new address might not handle transactions correctly.

## Recommended Mitigation Steps
Identify Tokens by Another Attribute:
Instead of relying solely on the contract address, use a unique and invariant attribute of the token, such as a symbolic identifier or a unique string defined by the issuing organization.

Centralized Token Database:
Maintain a centralized database where each token is associated with a unique identifier and all known addresses of that token are listed.
For example, for each known token, store the different contract addresses that can represent it.

Address Mapping System:
Use a mapping in the smart contract that associates the multiple addresses of the same token to a unique identity.
Example: 

    mapping(address => bytes32) public tokenIdentities; where each token address is associated with a unique identifier.

Balance and Transaction Verification:
Always verify balances and transactions by aggregating information from all known addresses for a given token.
