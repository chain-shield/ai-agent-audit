# Vulnerability details

## Impact

The transferOut function in the THORChain_Router contract has a vulnerability that can lead to inconsistent updates of the _vaultAllowance mapping. This mapping is used to track the allowance of each vault for each asset. The vulnerability can cause the allowance to be decremented before the transfer is attempted, leading to inconsistencies if the transfer fails.

## Proof of Concept

Here is a step-by-step example of how the vulnerability can be exploited:

1. A user calls the transferOut function to transfer an ERC20 token from the router to a recipient.
2. The function decrements the allowance for the user's vault by the amount of the transfer.
3. The function attempts to transfer the ERC20 token to the recipient.
4. The transfer fails, for example, because the recipient's contract is not implemented correctly.
5. The function does not update the allowance to its previous value, leaving it decremented.
    
    ```
      pragma solidity ^0.8.0;
    
    contract THORChain_Router {
        mapping(address => mapping(address => uint)) public _vaultAllowance;
    
        function transferOut(
            address payable to,
            address asset,
            uint amount,
            string memory memo
        ) public payable nonReentrant {
            _vaultAllowance[msg.sender][asset] -= amount; // Decrement allowance before transfer
            (bool success, bytes memory data) = asset.call(
                abi.encodeWithSignature("transfer(address,uint256)", to, amount)
            );
            if (!success) {
                emit TransferOut(msg.sender, to, asset, 0, memo); // Emit event with 0 amount
                return;
            }
        }
    }
    
    contract Attacker {
        address public router;
    
        constructor(address _router) public {
            router = _router;
        }
    
        function attack() public {
            THORChain_Router(router).transferOut(
                payable(address(0x0000000000000000000000000000000000000001)), // Recipient
                address(0x0000000000000000000000000000000000000002), // Asset
                100, // Amount
                "Test" // Memo
            );
        }
    }
    
    ```
    

Conclusion:

the **`THORChain_Router`** contract has a function **`transferOut`** that decrements the allowance before attempting to transfer the asset. The **`Attacker`** contract calls the **`transferOut`** function with a recipient, asset, amount, and memo. If the transfer fails, the allowance is not updated back to its previous value, leaving the allowance decremented.

This code demonstrates the vulnerability by showing how the allowance can be decremented before the transfer is attempted, which can lead to inconsistencies if the transfer fails.

## Recommended Mitigation Steps

To mitigate this vulnerability, the **`transferOut`** function should be modified to update the **`_vaultAllowance`** mapping only after the transfer is successful. Here is an example of the modified function:

```solidity
function transferOut(
    address payable to,
    address asset,
    uint amount,
    string memory memo
) public payable nonReentrant {
    uint safeAmount;
    if (asset == address(0)) {
        safeAmount = msg.value;
        bool success = to.send(safeAmount); // Send ETH.
        if (!success) {
            payable(address(msg.sender)).transfer(safeAmount); // For failure, bounce back to vault & continue.
        }
    } else {
        (bool success, bytes memory data) = asset.call(
            abi.encodeWithSignature("transfer(address,uint256)", to, amount)
        );
        if (!success) {
            emit TransferOut(msg.sender, to, asset, 0, memo); // Emit event with 0 amount
            return;
        }
        _vaultAllowance[msg.sender][_asset] -= amount; // Update allowance only if transfer is successful
        safeAmount = amount;
    }
    emit TransferOut(msg.sender, to, asset, safeAmount, memo);
}
```

The **`_vaultAllowance`** mapping is updated only after the transfer is successful. This ensures that the allowance is always consistent with the actual balance of the vault.

**Recommendations:**

1. Update the **`transferOut`** function to update the **`_vaultAllowance`** mapping only after the transfer is successful.
2. Test the modified function thoroughly to ensure that it works correctly and does not introduce any new vulnerabilities.
