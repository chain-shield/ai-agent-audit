# Vulnerability details

## Impact

The `safeApprove` function is used in both the `_routerDeposit` function which is used to transfer allowance and return Vault Assets (not in scope). The function's implementation doesn't account for tokens which do not have [a return value](https://medium.com/coinmonks/missing-return-value-bug-at-least-130-tokens-affected-d67bf08521ca) approval like `usdt`. This can lead to aprroval transactions that should be otherwise successful to revert as the compiler expects a return value but receives none. Thus asset movements between the vaults for these token types will always fail.
## Proof of Concept

1. Context
The protocol aims to work with all sorts ERC20 token while including a [whitelist](https://gitlab.com/thorchain/thornode/-/blob/develop/common/tokenlist/ethtokens/eth_mainnet_latest.json?ref_type=heads) and this whitelist includes tokens like USDT which do not return a return a bool on approval.

> ERC20 used by the protocol	Any (all possible ERC20s)
>ERC20 token behaviors in scope
> Missing return values	Yes

 

2. Bug location

As can be seen in the `safeApprove` function below, it correctly checks for the success of the approval which handles cases of tokens that return false on failure approval. However, unlike the standard `safeApprove` implementation from codebases like [openzeppelin](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/fd81a96f01cc42ef1c9a5399364968d0e07e9e90/contracts/token/ERC20/utils/SafeERC20.sol#L123), [uniswap](https://github.com/Uniswap/solidity-lib/blob/9642a0705fdaf36b477354a4167a8cd765250860/contracts/libraries/TransferHelper.sol#L10), a check for the returned datalength is neglected. This check helps to handle tokens that do not return a bool on approval

```solidity
  function safeApprove(
    address _asset,
    address _address,
    uint _amount
  ) internal {
    (bool success, ) = _asset.call(
      abi.encodeWithSignature("approve(address,uint256)", _address, _amount)
    ); // Approve to transfer
    require(success);
  }
```
3. Final effect

What this means that when the [`transferAllowance`](https://github.com/code-423n4/2024-06-thorchain/blob/e5ae503d0dc2394a82242be6860eb538345152a1/ethereum/contracts/THORChain_Router.sol#L176) function is called to move these types of assets between vaults, the `_routerDeposit` function is queried, the `safeApprove` function is queried, and as been established above, fails regardless of the whether the approval was successful or not since the function doesn't handle the lack of return value of the token. Hence these types of assets cannot be transferred between vaults.

```solidity
  function _routerDeposit(
    address _router,
    address _vault,
    address _asset,
    uint _amount,
    string memory _memo
  ) internal {
    _vaultAllowance[msg.sender][_asset] -= _amount;
    safeApprove(_asset, _router, _amount);

    iROUTER(_router).depositWithExpiry(
      _vault,
      _asset,
      _amount,
      _memo,
      type(uint).max
    ); // Transfer by depositing
  }
```

## Recommended Mitigation Steps

A check for datalength is needed. If it's 0, we assume it's one of these tokens and as long as the call itself didn't revert, it therefore must mean that the approval was successful and true should have been returned.

```solidity
  function safeApprove(
    address _asset,
    address _address,
    uint _amount
  ) internal {
    (bool success, ) = _asset.call(
      abi.encodeWithSignature("approve(address,uint256)", _address, _amount)
    ); // Approve to transfer
    require(success && (data.length == 0 || abi.decode(data, (bool))));
  }
```
