# Vulnerability details

## Impact
Inside the router contract, once a user has deposited some tokens/assets, the assigned vault can call `transferOutAndCallV5` function and swap them for another token (WETH). 

The problem lies inside the second branch of the `_transferOutAndCallV5` function. The router transfers the tokens to the `aggregator` and then calls `swapOutV5`. The slippage parameter(`amountOutMin`) can cause a revert - it was set too high by the caller, the impact of the trade was not accounted properly, the token being traded has fees on transfers or the tx got front-run. When this revert happens, the initially transfered tokens (L347-L355) are already inside the aggregator and can not be withdrawn back. This means somebody else can just immediately call `swapOutV5` inside the aggregator and steal them, without any way for the initial caller to get them back. Make sure to check if the `_dexAggSuccess` variable and if it is equals to `false`, just revert.

## Proof of Concept
1. Deposit funds into the router contract
2. Vault calls `transferOutAndCallV5`, in order to make a swap
3. Due to `amountOutMin` being too high and not well considered, the `swapOutV5` call inside `_transferOutAndCallV5` fails, but the tokens are already transfered
4. The fastest user/bot can call `swapOutV5` inside the aggregator and make a swap for free - the initial user loses its funds

## Tools Used
Manual review

## Recommended Mitigation Steps
Check whether or not the `_dexAggSuccess` variable is equal to `true` or `false`. If `false` - revert
