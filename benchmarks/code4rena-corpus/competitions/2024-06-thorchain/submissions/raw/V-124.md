# Vulnerability details

## Impact
Some non-standard tokens like USDT will revert when a contract or a user tries to approve an allowance when the spender allowance has already been set to a non-zero value.
Due to this if somehow, if the approval is not lowered to exactly 0 (due to a rounding error or another unforeseen situation) then the next approval in [_routerDeposit](https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/chain/ethereum/contracts/THORChain_Router.sol#L466) will fail (assuming a token like USDT is used), blocking all further deposits.
>**Note:** Set to medium risk because the probability of this happening is low but the impact would be high.

We also should note that OpenZeppelin has [officially deprecated](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/master/contracts/token/ERC20/utils/SafeERC20.sol#L38-L44) the safeApprove function, suggesting to use instead safeIncreaseAllowance and safeDecreaseAllowance.

## Recommended Mitigation Steps
Adopt a safer approach to cover edge cases such as the above mentioned USDT token and implement the following solution:
```diff

function _routerDeposit(
    address _router,
    address _vault,
    address _asset,
    uint _amount,
    string memory _memo
  ) internal {
    _vaultAllowance[msg.sender][_asset] -= _amount;
-    safeApprove(_asset, _router, _amount);
+    uint256 allowance = _asset.allowance(address(this), _router);
+    if (allowance > 0) {
+    token.safeDecreaseAllowance(_router, allowance);
+    }
+    token.safeIncreaseAllowance(_router, amount);


    iROUTER(_router).depositWithExpiry(// call the depositWithExpiry function of the router
      _vault,
      _asset,
      _amount,
      _memo,
      type(uint).max
    ); // Transfer by depositing
  }
```
