# Vulnerability details

## Impact
In the struct of [TransferOutData](https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/chain/ethereum/contracts/THORChain_Router.sol#L33) & [TransferOutAndCallData](https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/chain/ethereum/contracts/THORChain_Router.sol#L41) if `to` or `target` address gets blacklisted due to any illicit practice by USDC/USDT.
This will cause the for loop of batch transactions in [batchTransferOutV5](https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/chain/ethereum/contracts/THORChain_Router.sol#L247) & [batchTransferOutAndCallV5](https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/chain/ethereum/contracts/THORChain_Router.sol#L397) function to be prone to DOS.
## Proof of Concept
The current implementation of batch transactions follows a sequential way of doing transfers in the for loop.
But the transfer to a blacklisted recipient will revert, due to which the for loop will keep failing, bricking the whole batch transactions because the blacklisted address is never cleared.

## Tools Used
Manual review

## Recommended Mitigation Steps
 As these addresses are highly anomalistic in nature, I would suggest to simply skip the blacklisted addresses in the ***for*** loop.
