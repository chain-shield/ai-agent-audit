# Vulnerability details

## Impact
After [churning of vaults](https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/chain/ethereum/contracts/THORChain_Router.sol#L165), if the router address isn't the same as the router's contract address from which the function([transferAllowance](https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/chain/ethereum/contracts/THORChain_Router.sol#L165)) is being called funds will forward to a new router contract with the help of [_routerDeposit](https://github.com/code-423n4/2024-06-thorchain/blob/e3fd3c75ff994dce50d6eb66eb290d467bd494f5/chain/ethereum/contracts/THORChain_Router.sol#L466) in which the uint expiry parameter is set to `type(uint256).max` due to which these funds can never be transferred to any other address.
Hence making them locked forever. 
## Proof of Concept
 ```solidity
  function _routerDeposit(
    address _router,
    address _vault,
    address _asset,
    uint _amount,
    string memory _memo
  ) internal {
    _vaultAllowance[msg.sender][_asset] -= _amount;//decrease the allowance
    safeApprove(_asset, _router, _amount);// approve teh router to transfer the asset

    iROUTER(_router).depositWithExpiry(// call the depositWithExpiry function of the router
      _vault,
      _asset,
      _amount,
      _memo,
      type(uint).max // expiry parameter is being set to 2^256-1
    ); // Transfer by depositing
  }

```

## Tools Used
Manual review

## Recommended Mitigation Steps
Remove the max value and introduce a new expiry value in case if funds are being transferred to a new router.
