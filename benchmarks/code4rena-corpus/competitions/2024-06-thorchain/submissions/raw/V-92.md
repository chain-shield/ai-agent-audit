# Vulnerability details

## Impact
The current implementation of `depositWithExpiry` function only checks if the current block timestamp is less than the expiration timestamp at the time the function is called. However, it does not ensure the transaction is confirmed before the expiration timestamp.
Problematic code: [@chain/ethereum/contracts/THORChain_Router.sol#depositWithExpiry](https://github.com/code-423n4/2024-06-thorchain/blob/e5ae503d0dc2394a82242be6860eb538345152a1/chain/ethereum/contracts/THORChain_Router.sol#L131-L140)
```solidity
function depositWithExpiry(
    address payable vault,
    address asset,
    uint amount,
    string memory memo,
    uint expiration
) external payable {
    require(block.timestamp < expiration, "THORChain_Router: expired");
    _deposit(vault, asset, amount, memo);
}
```
The issue is that even if `block.timestamp < expiration` is true when the function is called, the transaction may not be confirmed until after the expiration timestamp due to network congestion or other factors. This means that expired transactions could still be accepted and processed. This can lead to several issues and unintended consequences:

   1. **Violation of expiration intent** The purpose of the `expiration` parameter is to set a time limit for the transaction to be confirmed. If expired transactions are still accepted, it defeats the purpose of having an expiration mechanism in place.
   2. In certain scenarios, accepting expired transactions could lead to financial risks or losses. For example, if the transaction involves a token swap or a time-sensitive operation, processing an expired transaction may result in unintended outcomes or losses for the users or the platform.

## Proof of Concept
Suppose a user wants to deposit tokens into the `THORChain_Router` contract using the `depositWithExpiry` function. They set the `expiration` timestamp to a specific value, expecting that the transaction will only be accepted if it is confirmed before that timestamp.
```solidity
uint expiration = block.timestamp + 1 hours;
router.depositWithExpiry(vault, asset, amount, memo, expiration);
```
However, due to network congestion or other factors, the transaction may not be confirmed until after the expiration timestamp. With the current implementation, the transaction would still be accepted and processed, even though it should have been rejected based on the expiration condition.

This violates the user's expectation and the intended behavior of the `depositWithExpiry` function. The user may have set the expiration timestamp to limit their exposure or to ensure that the transaction is processed within a specific timeframe. By accepting expired transactions, the contract fails to enforce the desired expiration mechanism.

## Recommended Mitigation Steps
The `depositWithExpiry` function checks the expiration timestamp against the block timestamp at the time the transaction is confirmed, rather than when the function is called. we calculate the `expirationBlock` by dividing the `expiration` timestamp by the average block time (assumed to be 15 seconds in this example). Then, we compare `block.number` with `expirationBlock` to ensure that the transaction is confirmed before the expiration block.
```solidity
function depositWithExpiry(
    address payable vault,
    address asset,
    uint amount,
    string memory memo,
    uint expiration
) external payable {
    uint expirationBlock = expiration / 15; // Assuming an average block time of 15 seconds
    require(block.number < expirationBlock, "THORChain_Router: expired");
    _deposit(vault, asset, amount, memo);
}
```
