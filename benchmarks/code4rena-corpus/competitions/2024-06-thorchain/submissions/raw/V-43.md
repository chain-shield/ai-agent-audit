# Vulnerability details

Thorchain has a whitelist of ERC20 tokens that includes USDT and KNC:
https://gitlab.com/thorchain/thornode/-/blob/develop/common/tokenlist/ethtokens/eth_mainnet_latest.json?ref_type=heads#L1294
https://gitlab.com/thorchain/thornode/-/blob/develop/common/tokenlist/ethtokens/eth_mainnet_latest.json?ref_type=heads#L6230
 
They both don't allow approving an amount bigger than 0 when an existing amount which is bigger than 0 is already approved. Instead you have to first reduce the address' allowance to zero. `THORChain_Router.sol` doesn't do that so it will have issues with these tokens.

## Impact
During vault rotations a revert can happen which will prevent a vault from transferring USDT or KNC to a new router. If the retiring vault has to transfer its allowances to a vault that uses the new router it will not be able to.

## Proof of Concept
In Thorchain there are vault rotations. Vaults rotate every 3 days and generate new vault addresses. There is a `transferAllowance()` function that allows retiring vaults to transfer their allowance to spend ERC20 tokens on the router to the new vaults:
```solidity
  function transferAllowance(address router, address newVault, address asset,
    uint amount,string memory memo) external nonReentrant {
    if (router == address(this)) {
      _adjustAllowances(newVault, asset, amount);
      emit TransferAllowance(msg.sender, newVault, asset, amount, memo);
    } else {
      _routerDeposit(router, newVault, asset, amount, memo);
    }
  }
```
If the router that is specified as a param for the function is different than the current contract then `transferAllowance()` calls `_routerDeposit()`. This function approves the new router on the behalf of the vault:
```solidity
  function _routerDeposit(address _router, address _vault, address _asset,
    uint _amount, string memory _memo) internal {
    _vaultAllowance[msg.sender][_asset] -= _amount;
    safeApprove(_asset, _router, _amount); //@audit-allowance not reset

    iROUTER(_router).depositWithExpiry(
      _vault,
      _asset,
      _amount,
      _memo,
      type(uint).max
    ); // Transfer by depositing
  }
```
As you can see it sets the allowance and calls `depositWithExpiry()` on the new router. However after that it does not reset the allowance.
Here is a scenario in which this will cause issues (there are 2 routers and 2 vaults for simplicity):
1. A vault rotation happens and `vaultA` transfers its allowances to `vaultB` by calling `transferAllowance()` on `routerA` and specyfing `routerB` as the `router` param. `vaultA` has now given `routerB` an allowance of 100 USDT for example.

2. A second rotation happens but this time `vaultB` transfers its allowance to `vaultA` but sets the `router` param to `routerA`

3. Third Rotation happens and `vaultA` again has to transfer its allowances to `vaultB` and specifies `routerB` as a `router` param again.

4. The transaction will revert because `vaultA` has already given `routerB` an allowance of 100 USDT. Funds cannot be deposited to new router.

## Recommended Mitigation Steps
Reset the allowance after depositing into the new router:

```diff
    safeApprove(_asset, _router, _amount);

    iROUTER(_router).depositWithExpiry(
      _vault,
      _asset,
      _amount,
      _memo,
      type(uint).max
    ); // Transfer by depositing

+   safeApprove(_asset, _router, 0);
```
