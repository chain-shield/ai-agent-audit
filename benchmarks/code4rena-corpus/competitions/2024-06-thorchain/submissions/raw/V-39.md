# Vulnerability details

The `_transferOutAndCallV5()` allows a vault to send ETH and swap it for another token which will be sent to the recipient. The implementation has a case in which if the swap fails it should send the ETH directly to the recipient. However it sends the ETH to the aggregator instead.

## Impact
The recipient will not receive any ETH and the vault will lose funds.

## Proof of Concept
Here is a snippet from `_transferOutAndCallV5()`:
```solidity
      (bool swapOutSuccess, ) = aggregationPayload.target.call{
        value: msg.value
      }(
        abi.encodeWithSignature(
          "swapOutV5(address,uint256,address,address,uint256,bytes,string)",
          aggregationPayload.fromAsset,
          aggregationPayload.fromAmount,
          aggregationPayload.toAsset,
          aggregationPayload.recipient,
          aggregationPayload.amountOutMin,
          aggregationPayload.payload,
          aggregationPayload.originAddress
        )
      );
      if (!swapOutSuccess) {
        bool sendSuccess = payable(aggregationPayload.target).send(msg.value); // If can't swap, just send the recipient the gas asset
```
As you can see it first calls `swapOutV5()` on the `aggregationPayload.target` which is the address of the aggregator that swaps tokens in a 3rd party protocol.

If the swap fails we enter the if statement below and according to the comment on the last line we should send the recipient the gas asset (ETH).

However as you can see it sends it to `aggregationPayload.target` which is the address of the aggregator not the recipient.

## Tools Used
Manual Review

## Recommended Mitigation Steps
```diff
      if (!swapOutSuccess) {
-       bool sendSuccess = payable(aggregationPayload.target).send(msg.value);
+       bool sendSuccess = payable(aggregationPayload.recipient).send(msg.value);
```
