# Vulnerability details

In `THORChain_Router.sol` we have `transferOutV5()` which allows any vault to transfer any asset to any recipient (including ETH).
It is a public payable function which calls the internal `_transferOutV5()`.
 
The issues is that the internal function doesn't check if the `amount` of `asset` a vault has specified to transfer to the recipient is equal to the `msg.value` that was sent (if we are sending ETH). This allows ETH to be stuck in the contract that an attacker can claim.

## Impact
Loss of funds. Attacker can claim stuck ETH.

## Proof of Concept
A vault calls `transferOutV5` and sends 5 ETH as `msg.value` but specifies the `amount` as `4e18` in the `transferOutPayload`. This will send `4e18` ETH to the recipient and the 1 ETH left will be stuck in the contract. 

```solidity
  function transferOutV5(
    TransferOutData calldata transferOutPayload
  ) public payable nonReentrant {
    _transferOutV5(transferOutPayload);
  }
```

```solidity
  function _transferOutV5(TransferOutData memory transferOutPayload) private {

      if (!success) {
        payable(address(msg.sender)).transfer(transferOutPayload.amount); // For failure, bounce back to vault & continue.
...
```
It will be especially easy for vaults to make such an error if they use the `batchTransferOutV5()` which can call `_transferOutV5()` multiple times with different payloads. Also this function doesn't check that msg.value is empty when transferring an ERC20 token (like it is done in `depositWithExpiry()`)

An attacker can steal that stuck ETH by setting `to` (address of the recipient) as himself in the payload. After that the contract will send an `amount` of ETH specified by the attacker to his address.

Manual Review

## Recommended Mitigation Steps
For the `transferOutV5()` function you can check that `msg.value == transferOutPayload.amount` before calling _transferOutV5().

There is also a `batchTransferOutV5()` function that is intended to call `_transferOutV5()` mulitple times. For it this fix will not work. Instead you can check that the `msg.value` that was sent is equal to the sum of all amounts entered in the payload in a second for loop.
