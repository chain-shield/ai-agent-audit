# H/M Validation Checklist

Your task: decide whether a reported finding is `Valid` and, if valid, whether it deserves `High`, `Medium`, or only `Low / QA`.

Primary objective: maximize recall of real approved-root H/M findings while keeping H/M precision near or above 50%.

That means:
- do not reject or downgrade a real H/M runtime bug merely because it is conditional, timing-sensitive, market-sensitive, or triggered during expected admin / keeper / governance workflows
- do not accept unsupported, speculative, derivative, or operationally minor reports as H/M just to boost recall

## Mandatory Stage 0: Scope And Known-Issue Screen

Before any bug-existence, severity, or exploitability analysis, read these benchmark artifacts first and treat them as authoritative for client-declared scope and known-issue filtering:

1. `README.md`
2. `olas-scope.md`
3. `olas-docs.md`
4. `v12-findings.md`
5. `v12-checklist.md`

Also check any other `*-scope.md` or `*-docs.md` files when relevant, but the files above are the mandatory first read.

If a finding can already be excluded at this stage as out-of-scope, client-known, duplicate-of-V12, unsupported-asset behavior, or deployment / setup only, exclude it immediately instead of carrying it deeper into severity analysis.

## Evidence Hierarchy

Evaluate in this order:

1. Current code path and live runtime invariant
2. Independent root cause and exploit path
3. Material H/M impact under expected operation
4. Supporting PoC or concrete exploit reasoning

Never collapse these into one question. A real bug can still be `Low / QA`, and a severe-sounding report can still be `Invalid`.

## Core Validation Principles

1. Separate bug existence, root-cause independence, and severity.
2. A real bug is not automatically an H/M finding.
3. A named safeguard only counts if it materially constrains the exact execution path at issue.
4. Realistic timing, sequencing, stale-state windows, and ordinary market conditions do not automatically make an issue low likelihood.
5. A workflow being owner-only, governance-triggered, or maintenance-triggered does not make a finding low by default if permissionless actors can still exploit the path once that workflow is used.
6. Unsupported ERC20 or exotic token semantics are out of scope unless the benchmark docs explicitly say the protocol supports them.
7. Unsupported integrations, future component failures, and deployment / setup mistakes are not current H/M code vulnerabilities by default.
8. In raw validation, do not dedupe report findings against other report findings. Evaluate each finding on its own code path, bug existence, and H/M impact.
9. Use `Needs Review` sparingly. It is for genuine unresolved ambiguity after tracing the code, not for severity indecision on an already-proven bug family.

## Pre-Gate Sanity Check: Verify The Bug Exists

Before any severity analysis:

- locate the exact code path mentioned in the report
- trace execution step by step
- verify the claimed invariant is real and relevant to the current path
- confirm the harmful state is reachable under current code

Mark `Invalid` if:
- the code path does not exist
- the report describes impossible execution flow
- the invariant is invented or contradicted by the code
- the PoC or reasoning does not actually produce the claimed failure mode

## Gate 1: Scope, Prior-Finding, And Per-Finding Materiality

Before deciding whether a report is an independent H/M issue, explicitly check the client-declared scope artifacts in the benchmark source root:

- `olas-scope.md`
- `olas-docs.md`
- `v12-findings.md` when present
- `v12-checklist.md`
- every `*-scope.md` file
- every `*-docs.md` file
- benchmark `README.md` when relevant

Treat those files as authoritative context for benchmark scope and V12 / client-known duplicate filtering.

V12 duplicate / out-of-scope rule:

```text
Same root cause as V12?
├─ NO → Submit
└─ YES → Same impact?
    ├─ NO → Submit
    └─ YES → Same severity?
        ├─ NO → Submit
        └─ YES → Exclude (duplicate)
```

If the report is already captured in `v12-findings.md` with the same root cause, same impact, and same severity, exclude it as duplicate / out of scope for this benchmark.

If the root is the same but the impact or severity is materially different, the finding can still be in scope and should be analyzed on the merits.

After V12 / client-known filtering, stop deduping against other report findings.

Evaluate each report finding as if it were unique.

Do not reject or downgrade a report because:
- another finding in the same family already exists
- another finding seems like a stronger or more canonical articulation
- multiple findings might later be merged in cleanup

Only judge whether this finding itself proves:
- a real bug on the described code path
- a realistic exploit or failure path under current code
- material H/M impact on its own merits

It is acceptable in raw validation to keep multiple same-family findings if each one independently satisfies the H/M standard. A later cleanup worker can merge duplicates more carefully. Early deduping is disallowed here because it creates avoidable false negatives.

## Gate 2: Supported-Behavior Check

Unsupported ERC20 behavior is out of scope unless the benchmark docs explicitly say that exact token class or semantic must be supported.

Mark `Invalid` or `Low / QA` if the H/M claim depends on:
- unsupported non-standard ERC20 behavior
- USDT-style missing return values or forced zero-reset allowance quirks when support is not explicitly declared in `README.md`, `olas-scope.md`, or `olas-docs.md`
- fee-on-transfer / rebasing / exotic-decimals semantics that are not explicitly supported
- view-only, event-only, or cosmetic inconsistencies without functional harm

Do not upgrade unsupported-token incompatibility into H/M merely because the token is common or widely used elsewhere. The question is whether this benchmark explicitly requires support for that token behavior.

Treat only explicitly supported assets and integrations as in-scope for this gate. Do not dismiss a bug just because the path touches an external system if the benchmark docs show the protocol currently depends on that exact supported path in normal operation.

## Gate 3: User Error Check

Mark `Invalid` if the exploit requires the victim to make the core mistake, for example:
- choosing an obviously bad recipient / target / route
- supplying bad slippage / deadline / amount parameters where the protocol already delegates that choice safely
- approving or signing malicious payloads that the protocol is not supposed to sanitize

Remain open to `Valid` H/M when the protocol should itself bind critical runtime fields and fails to do so, including:
- missing binding of value-bearing inputs
- missing output validation / `minOut` / settlement result checks
- stale authorization or replayable approvals

## Gate 4: Live Runtime Exposure, Not Speculation

Ask: does the root cause exist now, and can the harmful runtime path occur under today's code?

Mark `Invalid` if the claim depends on:
- future integrations or future upgrades that do not yet exist
- a trusted external component failing, pausing, or becoming malicious in the future
- hypothetical deployment posture that current code does not require

Do not downgrade a finding merely because an admin, keeper, or governance actor chooses the route / target / pool / schedule. If the code still fails to validate a critical runtime field or settlement result on that chosen path, the bug is live.

## Gate 5: Existing Safeguards Must Actually Bind The Path

A safeguard counts only if it materially prevents or bounds the exact attack on the exact execution path.

Do not give meaningful credit to safeguards that are:
- fail-open
- stale
- bypassable
- dead code
- self-canceling
- only on another path
- only a pre-check that does not bind settlement-time reality

Examples that can still be H/M despite nominal safeguards:
- oracle or price checks that exist but do not actually stop bad execution
- slippage logic that quotes or validates the wrong thing
- liveness or authorization checks that can be bypassed or go stale
- accounting logic that references guard rails but still corrupts reconciled state

## Gate 6: Impact And Severity

### High

- theft or permanent loss of user / protocol assets
- unauthorized transfer or seizure of value / privilege
- permanent bricking of a core workflow
- materially harmful exploit against a core runtime path with protocol-scale consequences

### Medium

- material DoS or liveness failure of a core workflow
- accounting drift, reconciliation failure, or state corruption causing non-dust loss or incorrect balances
- exploitable pricing / oracle / settlement errors causing material mispricing or value extraction
- stale authorization, replay, or missing runtime binding with material consequence
- missing execution-time output floors or value validation that can materially mis-settle funds

### Low / QA

- bounded nuisance griefing
- operational friction with easy recovery and no material exposure
- derivative symptoms without independent impact
- unsupported-asset behavior
- dust or cosmetic effects

Positive H/M guidance:
- fail-open or non-binding price / oracle guards can still be H/M
- missing execution-time output validation can still be H/M
- missing binding of payable / bridged / authorized values can still be H/M
- core accounting, reconciliation, and liveness failures can still be H/M even if manual cleanup or recovery is possible after the harm

## Gate 7: Likelihood

Use realistic exploitability, not perfectionism.

Common / Occasional still includes:
- permissionless exploitation when expected workflows are used
- realistic stale-state windows
- ordinary timing or sequencing races
- common market conditions
- governance / keeper / admin actions that are part of normal operation

Rare means genuinely unlikely multi-condition alignment, extreme assumptions, or attacks that are economically irrational relative to the harm.

Do not call a bug "rare" just because:
- a normal admin / governance / keeper action must happen first
- the attacker must wait for a realistic market condition
- the exploit is timing-sensitive but the timing window is live and permissionless

## Gate 8: Governance, Deployment, And By-Design

Mark `Invalid` or `Low / QA` if the issue is really:
- deployment misconfiguration
- missing setup by a responsible operator
- trusted-party choosing a malicious dependency
- documentation-only inconsistency with no runtime bug
- intentional behavior with no material user / protocol harm

But do not use these categories to dismiss real runtime failures that still happen after correct setup.

Documentation does not rescue a failing runtime path.
"By design" does not excuse missing runtime protections when the actual result is material user or protocol harm.

## Gate 9: Evidence Quality And PoC

Require code-grounded reasoning.

If the H/M claim depends on a specific exploit chain, the evidence must show that chain concretely enough to be believable.

Missing PoC is not fatal when the code itself already proves the live broken invariant directly. But hand-wavy exploit claims can be downgraded when the leap from bug to H/M impact is not actually demonstrated.

## Final Decision Rules

Use this rubric:

- `Invalid`
  - bug does not exist
  - report is speculative, unsupported, out-of-scope, or documentation-only
  - this finding itself does not prove a real materially harmful bug on its own path
- `Valid` + `Low / QA`
  - real issue exists, but this finding's own H/M materiality is not proven
  - impact is bounded, operationally minor, unsupported, or economically irrational
- `Valid` + `Medium` / `High`
  - real issue exists
  - this finding's own path is materially harmful
  - exploit path is realistic under current code and expected operation
- `Needs Review`
  - only when genuine ambiguity remains after tracing the code and applying the gates above

Tie-breaker:
- if bug existence is uncertain -> `Invalid`
- if bug exists but this finding's own H/M proof is not there -> `Low / QA`
- if bug exists and the only downgrade rationale is nominal safeguards, realistic timing, or expected workflow usage, do not auto-downgrade; ask whether the exposure remains materially live
- if bug exists and the only rejection rationale is similarity to another report finding, keep it in raw validation and leave dedupe to later cleanup
- once unsupported, speculative, derivative, and operationally minor reports are filtered out, prefer preserving recall of real H/M roots over squeezing extra precision out of borderline downgrade reasons
