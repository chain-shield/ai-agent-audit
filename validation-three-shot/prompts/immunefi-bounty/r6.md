PoC verification rules:
- The PoC must execute successfully.
- The PoC must be a non-harmful local simulation only.
- Prefer a local mainnet fork PoC whenever the finding affects a deployed in-scope mainnet contract and the PoC runtime artifact provides a matching address, network, and RPC env var.
- A local public-testnet fork is acceptable only when the affected in-scope asset itself is a public-testnet deployment, or when no matching mainnet deployment exists but a relevant in-scope public-testnet deployment does.
- A local non-fork test is not an acceptable primary proof for an Immunefi deployed-asset finding.
- Verify that every deployed address, network, and RPC env var used by the PoC matches the generated PoC runtime artifact, bounty rules, scope, or repo docs.
- If the command needs vars from the repo `.env`, you may source it locally while verifying, but the final recorded command must be judge-facing and must use env var placeholders instead of local absolute paths.
- Never paste raw RPC URLs into code, markdown, JSON, or commands.
- Do not assume RPC access. A fork PoC is valid only if it uses an approved RPC env var and actually passes in this environment.
- Do not assume Anvil is required. `forge test --fork-url ...` is usually enough for Foundry fork tests; start Anvil only if existing repo docs/tests require it and you can stop it cleanly.
- In-scope deployed addresses may appear in the generated Immunefi bounty rules/scope artifacts as explorer URLs. Verify that any address used by the PoC matches the finding and network.
- Reject or repair any PoC path that can broadcast to a live chain, mutate live mainnet/public-testnet state, steal funds, freeze funds, manipulate live governance, touch live private keys/accounts, or cause real protocol harm, even for a tiny amount.
- The PoC must prove the claimed vulnerability, not merely exercise a revert/success path.
- The PoC must be runnable when its full code block is copied into a fresh checkout at the exact repo/package test path recorded for the finding.
- Imports must work from that stated `Save as` location. Reject or repair PoCs whose imports only work from a generated local artifact path rather than the affected repo/package test folder.
- If the PoC requires fork config or RPC config, those requirements must be explicit in the recorded test command using repo-supported env var names.
- The PoC must not mock any contract-initiated calls.
- The PoC must not use mock contracts in place of actual in-scope implementations unless actual contract calls are impossible and client-provided mocks already exist in the repo test folder.
- The PoC should use one rigorous primary test unless helper tests are necessary to prove the bounty impact cleanly.
- The PoC must not contain icons, noisy comments, or irrelevant debug output.
- Avoid `console.log` by default. If the repo/test framework strongly expects runtime output for bounty reproduction, keep it minimal and ensure assertions prove the same values.
- Comments should explain the exploit setup, attacker action, vulnerable transition, and final proof. Repair PoCs whose comments are too terse for an Immunefi triager to follow.
- Comments must not narrate obvious Solidity or TypeScript mechanics.

Bug bounty reproduction-package review:

- `Invalid After PoC Review`: no valid PoC can be created and the finding appears unprovable or invalid.
