PoC verification rules:
- The PoC must execute successfully.
- The PoC must prove the claimed vulnerability, not merely exercise a revert/success path.
- The PoC must be runnable when its full code block is copied into a fresh checkout at the exact repo/package test path recorded for the finding.
- Imports must work from that stated `Save as` location. Reject or repair PoCs whose imports only work from a generated local artifact path rather than the affected repo/package test folder.
- The PoC must not mock any contract-initiated calls.
- The PoC must not use mock contracts in place of actual in-scope implementations unless actual contract calls are impossible and client-provided mocks already exist in the repo test folder.
- The PoC should use one rigorous primary test unless helper tests are necessary to prove the Critical/High impact cleanly.
- The PoC must not contain icons, noisy comments, or irrelevant debug output.
- Avoid `console.log` by default. If the repo/test framework strongly expects runtime output for bounty reproduction, keep it minimal and ensure assertions prove the same values.
- Comments should explain the exploit setup, attacker action, vulnerable transition, and final proof. Repair PoCs whose comments are too terse for a bounty reviewer to follow.
- Comments must not narrate obvious Solidity or TypeScript mechanics.

Bug bounty reproduction-package review:
- Verify the PoC is a complete reproduction package, not just a minimal regression test.
- Verify the attacker, victim/protocol state, starting balances or invariants, exploit trigger, and final broken state are explicit in code or comments.
- Verify assertions prove the claimed Critical/High security/economic impact, not merely call success or a revert.
- Verify the PoC quantifies impact whenever practical: stolen value, frozen value, bypassed accounting delta, incorrect shares, incorrect rewards, governance result manipulation, or the exact invariant violation.
- Verify forked mainnet or public-testnet simulation is used when deployed-state feasibility matters and the repo/runtime artifacts support it.
- Verify every helper needed by the report-ready PoC is included in the PoC file or is already part of the upstream repo and importable from the stated `Save as` location.

- Verify the Notes identify the expected success signal, including the key assertion or terminal result a bounty reviewer should see.
- Verify the judge-facing command is executable from a clean repo checkout after dependencies are installed and documented env vars are set.
